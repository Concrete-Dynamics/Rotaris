# Git Integration, Worktrees, and Checkpoints

## Overview

Rotaris can give each agent session a Git worktree of its own, so two concurrent runs never write into one checkout; it records an automatic Git-backed checkpoint at the close of each iteration whose tree differs from the last commit; and it lets the user roll a tree back to any recorded checkpoint, taking a safety checkpoint of the current state first. Completed isolated sessions can later be merged back into the base branch through a hidden, verified integration run that only ever moves the base by a fast-forward. The domain is exposed through a dedicated desktop Git view (worktree table, commit history, checkpoint browser, merge flow), the desktop session-launch and session-management surfaces, configuration keys, persisted session records, and a stored event stream. Nothing in the domain ever performs a network Git operation.

## Requirements

### Scope and Cross-Cutting Invariants

- **REQ-GIT-001** — No operation in this domain SHALL contact a Git remote. It SHALL never issue `git push`, `git pull`, `git fetch`, `git clone`, `git remote update`, `git ls-remote`, or any other Git subcommand that opens a network connection, and every merge it performs is local. The checkable consequence is: with the repository's configured remote pointed at an address that cannot be reached, every operation in this domain SHALL produce the same user-visible result as it does against a reachable remote, and SHALL finish inside the same bounds (REQ-GIT-146) rather than waiting on the network. With no remote configured at all, the only permitted difference is that the ahead and behind counters of REQ-GIT-105 read 0; those counters are computed from the locally stored upstream ref and are the only place in the domain where a remote is named at all. Two user-visible texts SHALL state the policy: the agent commit policy card (REQ-GIT-076), which says reviewing and pushing remain the user's job, and the repository-setup offer (REQ-GIT-114), which says it touches no remote.

- **REQ-GIT-002** — A worktree this domain created SHALL be removed only by an action the user confirmed. Exactly two removals SHALL occur without a confirmation of that removal, and they are the only such removals anywhere in the domain: the temporary integration worktree after a promotion has succeeded (best-effort, REQ-GIT-133), and a requirement-unit worktree whose unit has failed while `keep_failed_worktrees` is configured false (REQ-GIT-074, REQ-GIT-142). In particular: a worktree created to isolate a session SHALL still exist after that session ends, whatever the outcome (completed, failed, cancelled, or killed); the post-merge cleanup of REQ-GIT-135 SHALL delete only the worktrees listed in the dialog the user accepted, and SHALL delete nothing at all when its persisted preference has suppressed that dialog; and the integration worktree of a failed integration SHALL be retained on disk (REQ-GIT-134).

- **REQ-GIT-003** — A path SHALL count as excluded whenever its first component relative to the tree root is `.rotaris`, compared case-insensitively over the ASCII letters, so `.Rotaris/` and `.ROTARIS/` are excluded exactly as `.rotaris/` is and a case-insensitive filesystem cannot smuggle a path past the exclusion by respelling it. No working-tree read or write this domain performs SHALL touch an excluded path, which has all of the following checkable consequences: a tree whose only differences from the last commit lie under `.rotaris/` is reported clean (REQ-GIT-014) and a capture on it reports "nothing to record" (REQ-GIT-034); no checkpoint commit contains any path under `.rotaris/`, gitignored or not; no restore creates, rewrites, or deletes any file under `.rotaris/`; no drift comparison (REQ-GIT-056) and no diff total shown in the Git view (REQ-GIT-105, REQ-GIT-107) counts a path under `.rotaris/`; and the base-cleanliness gates of REQ-GIT-127 and REQ-GIT-133 pass on a tree whose only uncommitted changes lie there. Gitignored paths elsewhere in the tree are likewise absent from every checkpoint commit and are never deleted by a restore. The test SHALL be applied to the path as the tree names it and never to what that path points at: a symlink or junction is treated as an ordinary entry at its own path, so one lying under `.rotaris/` is excluded and one lying elsewhere is not, whatever its target. No read or write this domain performs on working-tree content SHALL follow such a link — a link is captured as a link and restored as a link, and its target is neither read, written, nor deleted — so a link aimed into `.rotaris/` cannot be used to reach an excluded path through an included one.

- **REQ-GIT-004** — Creating, previewing, and restoring a checkpoint SHALL leave the user's Git state untouched. All of the following SHALL be identical before and after the operation: the checked-out branch and the commit it points at, HEAD (including a detached HEAD), the symbolic-ref target, the on-disk index file byte for byte, the reflogs of HEAD and of every branch, the stash, the set of branches, and the set of staged entries. The one addition a capture makes to the repository is a single ref under `refs/rotaris/checkpoints/` together with the objects that ref reaches (REQ-GIT-029, REQ-GIT-030); whether that new ref carries a reflog of its own is not constrained here. The one thing a restore changes is the content and the presence of files in the working tree (REQ-GIT-040), so afterwards `git status` reports exactly the staged entries it reported before, while its unstaged and untracked sections reflect the restored files.

- **REQ-GIT-157** — Every refusal this domain produces SHALL be distinguishable, by what it left behind rather than by any numeric code, as one of exactly two kinds, and no operation SHALL invent a third. A **pre-work refusal** is one decided on the request, the configuration, or the state it named before anything was attempted: the worktree-option combinations of REQ-GIT-021, a rejected configuration value (REQ-GIT-071, REQ-GIT-138), a sequence the session does not record (gate 1 of REQ-GIT-058), and a restore the user declined at the confirmation of REQ-GIT-099. It SHALL leave no session record, no session lock, no checkpoint ref, and no modified file behind, so a repeat of the same request finds the workspace exactly as the refusal found it. An **after-acceptance refusal** is one raised once the request was accepted and work had begun: a lock held by a live run (REQ-GIT-020), a binding failure (REQ-GIT-023), a restore refused at gates 2 through 6 of REQ-GIT-058, and a restore that ran and failed. It SHALL report what it did change, which for a refused restore is the safety checkpoint and nothing else. Both kinds SHALL state their reason on the surface that asked for the operation, and neither SHALL be reported as a result a consumer could mistake for success. No outcome anywhere in this domain SHALL be expressed as a numeric code (REQ-SESSION-187).

### Isolated Worktree Creation

- **REQ-GIT-005** — Session worktrees SHALL be created at `<workspace>/.rotaris/<storage-subpath>/<session-id>`, where the storage subpath defaults to `worktrees` and is configurable. The subpath must be relative and must not contain `..`; a subpath whose resolved location falls outside `<workspace>/.rotaris` SHALL be rejected with the error `Worktree storage path must stay inside .rotaris.`

- **REQ-GIT-006** — Given a request to create a session worktree, when the workspace directory is not the root of its own Git worktree, the operation SHALL fail with `Workspace must be the root of its Git worktree.`; when the workspace checkout is on a detached HEAD, it SHALL fail with `Detached HEAD cannot host an isolated session or integration.`

- **REQ-GIT-007** — Creation defaults SHALL be: base branch = the workspace's currently checked-out branch; base revision = the workspace's current HEAD commit; branch name = `rotaris/session/<session-id>`. Callers MAY supply an explicit branch name, base revision, or base branch (requirement execution uses this to fork from a declared target instead of the current checkout).

- **REQ-GIT-008** — When the target worktree path already exists, creation SHALL fail with `Worktree path already exists: <path>` and SHALL NOT retry under some other path, because the location is fixed by the session id; only branch names ever receive collision suffixes. On success a new linked Git worktree exists at the path, checked out on a newly created branch pointing at the base revision, and the session's durable worktree binding records it as created by the session.

- **REQ-GIT-009** — A branch name is in normal form when the following transformation leaves it unchanged: trim surrounding whitespace, replace each remaining space with `-`, replace each backslash with `/`. A name SHALL be rejected when, in normal form, it is empty, is exactly `@`, starts with `-`, `/`, or `.`, ends with `/`, `.`, or `.lock`, contains `//`, `..`, `@{`, any whitespace character, or any of `~ ^ : ? * [ \`, or has any path component that starts with `.` or ends with `.lock`. The rejection error SHALL be `Invalid Git branch name: <value>`, quoting the value as supplied. A name the system derives for itself SHALL be transformed into normal form and created under the transformed name. A name supplied explicitly by a caller or typed by a user SHALL NOT be transformed: it is accepted only if it is already in normal form and passes the rejection rules, and otherwise draws the same error. An explicitly supplied name that is accepted is therefore always byte-identical to the branch created from it.

- **REQ-GIT-010** — Collision-safe creation (used for all run-launched isolation, since parallel launches routinely collide) SHALL try the requested or generated branch name first, and when that branch already exists as a ref or Git refuses with a branch/worktree collision, try deterministic suffixes `-2`, `-3`, … up to 50 total attempts, then fail with `Could not find a free branch name for <branch> after 50 attempts.` Only failures whose Git message matches (case-insensitively) "a branch named … already exists", "already checked out", or "already used by worktree" count as collisions; every other failure propagates unchanged without retrying.

- **REQ-GIT-011** — Attaching a session to an existing worktree SHALL validate that the path exists (`Worktree directory does not exist: <path>` otherwise), is a directory, and belongs to the same repository as the workspace (`Attached path is not a worktree of this workspace repository.` otherwise). The resulting binding records which branch the attached tree has checked out, which branch and which commit the base checkout is sitting on, and flags the worktree as one the session did not create.

- **REQ-GIT-012** — When worktree creation fails and the Git failure text (as REQ-GIT-013 defines that text) contains, matched case-insensitively, any of the substrings "filename too long", "file name too long", or "filename or extension is too long", the reported error SHALL consist of exactly two lines. Line 1 SHALL be "This worktree could not be created: a file in it needs a path longer than Windows allows (260 characters). Two things fix it — enable long paths in Git with `git config --global core.longpaths true`, or move the workspace somewhere shorter than <workspace>. Rotaris does not change your Git configuration for you." with `<workspace>` replaced by the workspace path. Line 2 SHALL be "Git reported: <detail>", where `<detail>` is the complete Git failure text and not merely the substring that matched. That two-line text SHALL be the error of the failed creation wherever creation errors surface (REQ-GIT-023, REQ-GIT-116). A Git failure text matching none of the three substrings SHALL be reported with Git's own wording (REQ-GIT-013); this is the only case in the domain in which Git's wording is replaced. No operation in this domain SHALL write to the user's Git configuration.

### Worktree-Layer Git Error Semantics

- **REQ-GIT-013** — Every Git invocation issued while creating, attaching, or removing a worktree SHALL be abandoned once that single invocation has run for 30 seconds, and the operation that issued it SHALL then report failure rather than wait longer; an operation issuing one such invocation therefore returns no later than 30 seconds after that invocation started. Git output SHALL be decoded as UTF-8 with each undecodable byte replaced by U+FFFD, so a Git message carrying arbitrary bytes still yields a reported error rather than an aborted operation. When Git cannot be started at all the error SHALL be `Could not run Git: <detail>`. When Git exits non-zero the error SHALL be Git's stderr verbatim; when stderr is empty, Git's stdout; when both are empty, `git command failed`. That text is what the rest of this domain calls the Git failure text. REQ-GIT-012 is the only exception to reporting Git's own wording. When the 30-second bound is exceeded the error SHALL be `Git timed out after 30s: <command>`, the same form the checkpoint layer uses in REQ-GIT-033 and with `<command>` rendered by the same rule, so that one timeout text serves the whole domain.

- **REQ-GIT-014** — Cleanliness checks of the base working tree SHALL include untracked files but exclude everything under `.rotaris/`, so session snapshots and worktrees stored there never make the base tree appear dirty.

### Session State and Persistence

- **REQ-GIT-015** — A session's durable worktree binding SHALL persist: worktree path, branch, base branch, base revision, a created-by-session flag (default true), a merge status (vocabulary exactly `ready`, `integrating`, `merged`, `merge_failed`; default `ready`), and an optional integration session id (default absent). This requirement is the product's single definition of the worktree binding record — those seven fields, the closed `merge_status` vocabulary, and every default — because this domain is what creates a binding (REQ-GIT-010, REQ-GIT-011, REQ-GIT-022) and what advances its merge status through integration (REQ-GIT-083, REQ-GIT-133). No requirement in any domain SHALL hold a second copy of those fields, that vocabulary, or those defaults; a requirement that needs them SHALL cite this one and state only what it adds.

- **REQ-GIT-016** — Each persisted checkpoint record SHALL carry: sequence (integer), Git ref name, commit id, creation timestamp, iteration number (default 0 when not produced by the iteration loop), attributed child-agent name (default empty), the list of file paths that differ between the checkpoint and its parent commit, and a kind, whose vocabulary is the one REQ-GIT-067 closes and which this requirement does not restate, defaulting to the `iteration` member of it.

- **REQ-GIT-017** — Session snapshots recorded before worktrees or checkpoints existed SHALL remain loadable: a missing worktree binding loads as "no worktree" and a missing checkpoint list loads as empty. An absence is reported as an absence; no substitute value is invented for those older runs.

- **REQ-GIT-018** — Each session's listing record (REQ-SESSION-030) SHALL carry that session's worktree binding in full (the fields of REQ-GIT-015), or `null` when the session has none, together with a `checkpoint_count` field whose value equals the number of checkpoint records the session holds (REQ-GIT-016). A session listing SHALL show, for every session, the worktree branch taken from that record and whether the session has at least one recorded checkpoint. Because the listing record alone determines both values, a listing SHALL produce identical output on a machine where Git is not installed, where the repository has been moved away, and where the checkpoint refs have been deleted, and SHALL read nothing but those listing records to do it (REQ-SESSION-042). Whether a recorded checkpoint's Git snapshot still exists is settled only at restore time, by gate 2 of REQ-GIT-058.

- **REQ-GIT-019** — Session state, diagnostics, and locks SHALL always belong to the base workspace's own session record, never to a worktree: the record is anchored to the workspace the run was started against, and binding a worktree SHALL NOT move it (REQ-SESSION-001). Nothing of a session's record SHALL be written inside a worktree, so integrating or discarding a worktree never takes a session's history with it. Where that record is held is REQ-SESSION-198's and is not fixed here. For an isolated session the run's effective workspace root is the worktree path while the session stays anchored to the base workspace; that anchoring is not written into the serialized configuration snapshot.

- **REQ-GIT-020** — A session SHALL be locked by a lock record held with the session's own record (REQ-SESSION-046), claimed by an operation that either takes the lock or reports its current holder, so that of two claims on the same session exactly one acquires the lock and the other does not run. That only one instance of the application runs (REQ-STARTUP-161) does not remove the need for it: the second claim arises from a further run started inside this same instance, from a lock an instance that crashed or was force-quit left behind, or from the brief overlap of an in-place update hand-over (REQ-STARTUP-121), and the lock refuses all three the same way (REQ-SESSION-050). The lock SHALL carry `pid` (integer), `host` (string) and `acquired_at` (ISO-8601 UTC timestamp), where `host` is a stable identifier of the machine whose process holds the lock; this field set is shared verbatim with REQ-SESSION-046 and neither domain may change it alone. When the claim fails because the lock is held, the holder SHALL be examined: if `host` names this machine and no process with that pid exists on it, the lock is released and the claim is attempted exactly once more; otherwise acquisition fails and the caller does not run, and it also fails when the second attempt fails. At most one such retry SHALL be made per acquisition, so a lock another party reclaims continuously cannot make an acquisition loop. A lock whose `host` is not this machine, and a lock that does not carry the three fields with their stated types, SHALL be treated as held by a live process, because this domain resolves every liveness ambiguity toward "live" (REQ-GIT-093, REQ-GIT-150); such a lock is never reclaimed automatically, by an acquisition or by any repair. The lock SHALL be released when the run holding it ends; a lock left behind by a dead process of this machine is therefore always reclaimable by the next acquisition, and is additionally released by the repairs of REQ-GIT-160 and REQ-GIT-094. A failed acquisition SHALL convey what REQ-SESSION-048 requires and SHALL say that the caller did not start: where the lock names this machine, that another run in this application holds the session, naming the recorded pid so the user can find or end the holder; where it names another machine, that the session is held by a different machine rather than that a lock is merely contended. The wording is left to the implementation. Nothing SHALL run: no agent work begins, no checkpoint is recorded, and the lock is left exactly as it was found. A failed acquisition is an after-acceptance refusal under REQ-GIT-157, because the request itself was well formed.

### Run Lifecycle Binding

- **REQ-GIT-021** — A run request SHALL support an isolation flag (default off), an attach-to-existing-worktree path, and an isolation branch name. Validation SHALL reject three combinations before anything is created, each refusal being a pre-work refusal under REQ-GIT-157 and recognizable as "never started" — no session id, no session record, no session lock, no log — and each carrying a message conveying which two choices conflict and what to do instead: isolation together with an attach path; a branch name without isolation; any worktree option combined with resuming an existing session. The wording is left to the implementation, and these are the same three refusals REQ-SESSION-082 states for the shared run request, so one validation serves both domains.

- **REQ-GIT-022** — Worktree binding SHALL happen only for new sessions, after the session record is created and before anything runs: isolation performs collision-safe creation (REQ-GIT-010); an attach path attaches (REQ-GIT-011). The resulting binding is saved with the session record, the run's configuration is re-rooted into the worktree, the worktree-rooted configuration is recorded in the session's config snapshot, and the session is flushed to disk before the run starts.

- **REQ-GIT-023** — Given a binding failure, the just-created session SHALL be deleted and its lock released, and the run SHALL fail before start with `Error: could not create or attach the requested worktree: <detail>`. A failed bind is always reported to the caller, and no agent work begins.

- **REQ-GIT-024** — Checkpoint machinery SHALL be wired into every run: an isolated run checkpoints its own worktree, though its session records remain under the base workspace; a non-isolated run checkpoints the base workspace tree (subject to the enablement policy of REQ-GIT-044).

### Retired Command-Line Surfaces (Runs and Sessions)

- **REQ-GIT-025** — *Withdrawn.* This product is one desktop application and has no command-line front end, so the single-front-end rule has nothing to constrain; the isolation choice, the branch name, and the attach-an-existing-worktree choice are collected by the session-launch dialog of REQ-GIT-118 and REQ-GIT-158, and carried into session execution by the run request of REQ-GIT-021 and REQ-SESSION-184.

- **REQ-GIT-026** — *Withdrawn.* The refused combination is unreachable: worktree options are offered only where a task is being started (REQ-GIT-118, REQ-SESSION-184), so no taskless request carrying them exists, and every remaining refusal in this domain is classified by REQ-GIT-157 rather than by a usage code.

- **REQ-GIT-027** — *Withdrawn.* The base-revision override for a requirement run is carried by REQ-GIT-159, which offers it where a requirement unit is started from the desktop.

- **REQ-GIT-028** — *Withdrawn.* Repairing stale sessions is a desktop action: the staleness test, the repair, its report, and the marking of a stale session in the session list are carried by REQ-GIT-160 together with REQ-SESSION-182, and the repair the desktop performs when a session's checkpoints are opened is REQ-GIT-094.

- **REQ-GIT-154** — *Withdrawn.* Process exit codes are a shell contract and this product has no shell surface; the distinction the three codes drew — refused before any work was attempted, versus accepted and then refused or failed — is carried by REQ-GIT-157, which states it in terms of what the refusal left behind.

### Checkpoint Recording (Git Layer)

- **REQ-GIT-029** — Checkpoints SHALL be recorded as ordinary Git commit objects reachable only from refs named `refs/rotaris/checkpoints/<session-id>/<sequence>` in the repository shared by the checkpointed tree, never touching the user's branches or HEAD.

- **REQ-GIT-030** — Checkpoint operations SHALL add nothing to the repository beyond the checkpoint refs and the objects those refs reach: no reflog entry is written for HEAD or for any branch, no repack or garbage collection is started, and the repository's index file is never refreshed, rewritten, or locked. Fingerprints of HEAD, the symbolic ref, the reflogs, the staged entries, and the branch list are identical before and after both a checkpoint creation and a restore; the unstaged and untracked portions of `git status` change after a restore exactly as REQ-GIT-004 describes and in no other way.

- **REQ-GIT-031** — Checkpoint operations SHALL ignore an inherited `GIT_INDEX_FILE` environment variable. With that variable set in the environment the application was started from — from inside a Git hook, for instance — checkpoint creation, preview, and restore SHALL produce results identical to those they produce with it unset, and the file the variable names SHALL be byte-identical afterwards. This is in addition to the guarantee of REQ-GIT-004, which covers the repository's own index file. The same SHALL hold for every other inherited Git environment variable that could redirect a checkpoint operation or change what it writes: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, and `GIT_COMMITTER_DATE`. Each SHALL be neutralised for the invocation, and the repository and the working tree SHALL instead be named explicitly on every Git invocation this domain makes, so that a checkpoint taken from inside a Git hook is identical to one taken with none of those variables set and no inherited file is altered. Environment variables outside that set SHALL be passed through unchanged, since a checkpoint must still run under the user's PATH and locale.

- **REQ-GIT-032** — Checkpoint commit objects SHALL carry the fixed identity name `rotaris`, email `rotaris@local`, as both their author and their committer, so a checkpoint commit is recognisable by that identity from either field and never carries a user's name in one of them. Checkpointing does not read or require any user-configured Git identity. The author and committer timestamps are the moment of capture; nothing else about them is constrained.

- **REQ-GIT-033** — Every Git invocation issued while recording, inspecting, or restoring a checkpoint SHALL be bounded by exactly one of two limits: 30 seconds for an invocation that only reads or updates refs, and 300 seconds for every other checkpoint invocation, which is to say every one that inspects or writes tree content (status, staging, reading or writing trees, and diffs). An invocation exceeding its limit SHALL be abandoned and reported as `Git timed out after <N>s: <command>`, `<N>` being the applicable limit in whole seconds. Failure to start Git SHALL be reported as `Could not run Git: <detail>`; a non-zero exit SHALL be reported as Git's stderr, else its stdout, else `git command failed`. `<command>` SHALL be rendered as the Git subcommand name followed by the arguments that were passed to it, in invocation order, separated by single spaces, with the path of the Git executable omitted and with no quoting, eliding, or truncation of any argument. The two limits are the whole time budget and not a target: a repository so large that staging or diffing it cannot finish inside 300 seconds SHALL produce this timeout error rather than a longer wait, and that outcome is a correct result of this requirement and not a defect in it.

- **REQ-GIT-034** — A capture SHALL record a tree containing every tracked path at its current working-tree content, including tracked paths that gitignore rules would otherwise cover, plus every untracked path gitignore does not cover when `checkpoints.include_untracked` is true. Everything under `.rotaris/` SHALL be absent from that tree (REQ-GIT-003), as SHALL a tracked path that has been deleted in the working tree. When the recorded tree equals the tree of HEAD, and when the repository has no commits and the recorded tree is empty, no checkpoint SHALL be produced and the outcome SHALL be reported as "nothing to record", which is a success and not a failure. Otherwise a commit SHALL be written whose parent is HEAD — parentless when there is no HEAD — and the ref for that sequence SHALL be created pointing at it. The comparison against HEAD SHALL be made against HEAD's tree with every excluded path removed from it, so a repository that already tracks paths under `.rotaris/` can still report "nothing to record" and that outcome is not made unreachable by the exclusion. The recorded tree SHALL preserve what Git itself records for a working tree: the executable bit of every captured file, and a symlink recorded as a symlink carrying its target text rather than as a copy of what it points at, so a restore puts back the mode and the link the capture saw. A submodule SHALL be recorded as the commit id the containing repository currently has for it and nothing more: the submodule's own working tree is never inspected, never captured, and never restored, and a restore may change only the recorded commit id in the containing tree.

- **REQ-GIT-035** — Checkpoint content rules: untracked files are captured by default (configurable through `checkpoints.include_untracked`, REQ-GIT-072); gitignored files are never captured; `.rotaris/**` is excluded from capture regardless of gitignore status. A capture restricted to tracked files records only edits to tracked files.

- **REQ-GIT-036** — Session ids used in checkpoint refs SHALL consist only of the characters `A–Z a–z 0–9 . _ -`, must be non-empty, must not start with `.`, and must not end with `.lock`; violations fail with `Session id is not usable in a Git ref name: <id>` (value quoted) before any Git call. A negative sequence fails with `Checkpoint sequence must not be negative: <n>`.

- **REQ-GIT-037** — Listing a session's checkpoint refs SHALL enumerate only that session's namespace (a session id that is a prefix of another session id never picks up the other's refs), keep only numeric sequence suffixes, and sort numerically (sequence 10 sorts after 9, not between 1 and 2).

- **REQ-GIT-038** — Resolving a checkpoint by session and sequence SHALL return nothing (not an error) when the ref no longer exists. The per-checkpoint file list SHALL be the set of paths the checkpoint's commit changed relative to its parent commit.

- **REQ-GIT-039** — A restore preview SHALL carry one entry per path the restore would touch. Each entry SHALL name a path as it appears in the working tree and SHALL carry a one-letter status chosen so that the letter states what the restore does to that path: `A` — the working tree holds the path and the checkpoint does not, so the restore removes it; `D` — the checkpoint holds the path and the working tree does not, so the restore recreates it; `M` — both hold the path with differing content, so the restore overwrites it; `R` — the path is the working tree's name for a path the checkpoint holds under a different name, so the restore puts the checkpoint's name back. Where an entry relates two paths, the path carried in the entry SHALL be the working-tree one. Rename detection SHALL be enabled at a similarity threshold of 50 per cent, and copy detection SHALL be disabled, so `A`, `D`, `M`, and `R` are the only statuses a preview can carry and a copied file is reported as an addition of the new path. A status letter outside that set SHALL nevertheless be carried through unchanged and rendered per REQ-GIT-063, so that a future Git that reports one cannot make a preview unrenderable.

- **REQ-GIT-040** — Restoring a checkpoint SHALL return the working tree's file contents to the checkpointed state, delete files created after the checkpoint (excluding gitignored and `.rotaris/**` paths), and return the touched-path list — the union of all paths that differed in either direction.

- **REQ-GIT-041** — Pruning SHALL remove every checkpoint ref of a session except its `keep` most recent ones (`keep <= 0` removes all) and return the number deleted; a second identical prune deletes zero. Deleting a session's entire checkpoint namespace SHALL remove every ref under it. Ref deletions verify the recorded commit id at deletion time so a concurrently moved ref is not silently clobbered.

- **REQ-GIT-042** — Checkpoint availability SHALL be true exactly when Git can be run and the target root lies inside a Git working tree; a plain folder or missing path degrades availability to false without raising. Attempting checkpoint operations while unavailable SHALL fail with `<path> is not inside a usable Git working tree.`

- **REQ-GIT-043** — Checkpoints and restores SHALL work on a detached HEAD (no branch is required) and inside a linked worktree: the ref is stored in the shared repository, the restore affects only the linked tree, and the main tree is untouched.

### Checkpoint Policy (Per-Session)

- **REQ-GIT-044** — Checkpoint enablement SHALL be three-valued via the `checkpoints.enabled` configuration key (REQ-GIT-070): explicit true = checkpoint everywhere; explicit false = never (isolation does not re-enable it); unset (the default) = enabled in worktree-isolated sessions, disabled elsewhere. A tree Git cannot manage resolves to disabled — a workspace without undo, not an error.

- **REQ-GIT-045** — Automatic capture SHALL never raise and never abort the run. It produces no checkpoint when disabled, when the tree matches HEAD (nothing to undo — not a failure), or when Git declines; that last case records a session warning diagnostic with kind `checkpoint`, severity `warning`, actor `checkpoints`, and message `Could not record a checkpoint after iteration <n>: <detail>`.

- **REQ-GIT-046** — A sequence number SHALL never be reused within one session: no existing checkpoint ref under `refs/rotaris/checkpoints/<session-id>/` SHALL ever be overwritten by a later capture, and no two checkpoint records of one session SHALL carry the same sequence. Every capture, automatic or otherwise, SHALL take its sequence from the maximum of two sources — the highest sequence in the session's recorded checkpoint list and the highest sequence among the live refs under that session's namespace — plus one, which is the same rule REQ-GIT-059 states for safety checkpoints. One rule therefore governs all numbering in this domain, and it upholds the invariant even when the two sources have diverged, so numbering keeps climbing across a prune, across a resume after an interruption, and across a ref deleted from outside. When the live refs cannot be listed at all, the recorded list alone SHALL be used and the capture SHALL still refuse to overwrite an existing ref, failing per REQ-GIT-045 rather than clobbering it.

- **REQ-GIT-047** — Automatic checkpoint commit messages SHALL be exactly `rotaris checkpoint <sequence> for session <session-id> (iteration <n>)`, with ` by <child-name>` appended inside the parentheses whenever the checkpoint is credited to a child agent.

- **REQ-GIT-048** — A `checkpoint.created` event SHALL NOT become observable to any consumer until all of the following are already durable: the session's persisted snapshot lists the new checkpoint; that list has been trimmed to the retention limit, with the refs of the trimmed entries deleted alongside their records (REQ-GIT-049); and the session's timeline (REQ-SESSION-134) holds an entry of kind `checkpoint_created` with actor `checkpoints`, message `Recorded checkpoint <seq> over <n> file(s).`, and metadata carrying the sequence, ref, commit id, iteration, child-agent name, kind, and file count. A consumer that reads the session's persisted snapshot on receipt of the event therefore always finds the checkpoint that event names, and always finds the retention limit already respected.

- **REQ-GIT-049** — Retention SHALL default to 50 checkpoints per session (minimum 1, enforced at configuration load) and SHALL trim the Git refs and the recorded list together, so that no operation of this domain ever leaves a recorded checkpoint without its ref. That guarantee covers this domain's own operations only: a ref removed from outside — pruned by hand, lost with a repository restored from a backup, gone with a repository that was moved — can still leave the list and the refs divergent, which is why REQ-GIT-058 gate 2 exists and why REQ-GIT-046 and REQ-GIT-059 number from the maximum of both sources. Pruning and whole-session discard never raise; discard deletes every ref and clears the recorded list, and runs before the session's record and files are removed (REQ-SESSION-166).

- **REQ-GIT-050** — Reading a session's checkpoint list for display SHALL use only the persisted session snapshot (no Git access), return checkpoints ascending by sequence, and return an empty list for an unreadable snapshot. The desktop checkpoints card of REQ-GIT-086 is the one surface that reads it.

- **REQ-GIT-051** — Exactly one capture SHALL be attempted for each iteration that closes, at the moment it closes, and none at any other moment: an iteration closing early because the task's todo list came back incomplete is captured like any other, and a run that closes no iteration yields no checkpoint. The attempt SHALL finish before the next iteration begins and before the run reports the session finished, so a session that has closed N iterations holds at most N checkpoints of kind `iteration`. The resulting checkpoint SHALL record the number of the iteration that just closed and the name of the child agent credited with that iteration's work, or an empty name when none is credited. That name SHALL be drawn from no fixed vocabulary: it is the identifier of the credited child agent, recorded verbatim as the iteration loop supplies it, so a workspace that defines its own child agents needs no change here. When more than one child agent contributed to the closing iteration, the credited name SHALL be empty, because the record holds one name and this domain SHALL NOT invent a joining format or pick a winner among them; the checkpoint is still recorded, and the iteration number still identifies the work. Checkpoints recorded before a run stopped SHALL still be listed when the session is resumed, and numbering SHALL continue from the highest sequence already recorded (REQ-GIT-046).
  > **Narrowed by [`PD-ORCH-005`](../product/directives/pd-orch-005.md#pd-orch-005) revision 6, 2026-10-06.** Clause 36: the
  > iteration that the record of an accepted explicit cancel closes, a close no run made, takes no capture; the next
  > iteration's capture records what the dead run wrote.

### Checkpoint Restore Policy

- **REQ-GIT-052** — Restore SHALL be a two-step operation: a preview that computes what would change without touching the tree, and the restore itself. Neither step raises; every refusal is a returned value with a human-readable blocked reason suitable for rendering in a dialog.

- **REQ-GIT-053** — The restore target tree SHALL be the session's own tree: for an isolated session, the path in its worktree binding; otherwise the base workspace root. Restoring an isolated session rewrites its worktree and never the base checkout.

- **REQ-GIT-054** — Two conditions SHALL be answered rather than raised: the named session is absent from the session store, and the tree the session would be restored into is not inside a Git working tree. Under either condition the session's checkpoint list SHALL be empty, no preview SHALL be produced, and a restore attempt SHALL return a refusal whose reason names the session. For the unmanaged-tree case the reason SHALL be the sentence given in gate 2 of REQ-GIT-058. The desktop presents such a refusal as a disabled "Restore checkpoint" button carrying the reason (REQ-GIT-089). For the unknown-session case the reason SHALL convey the session id as it was supplied and that the session store holds no session under it, so nothing can be previewed or restored for it; the wording is left to the implementation, and REQ-GIT-151 still requires it to read as a different sentence from the four other refusals it lists.

- **REQ-GIT-055** — Preview semantics: an unrecorded sequence yields nothing; a recorded checkpoint whose Git ref is gone yields a preview with no entries and a blocked reason; a Git inspection failure yields the reason `Git could not inspect checkpoint <n>: <detail>`; otherwise the preview carries the checkpoint, the per-path change entries (REQ-GIT-039 statuses), the dirty paths, and a blocked reason that is non-empty exactly when dirty paths exist.

- **REQ-GIT-056** — Before a restore, the drift check SHALL decide whether the restore would overwrite uncommitted work without warning. Its baseline SHALL be a recorded checkpoint of the session and never HEAD. It SHALL compare the working tree with a candidate set of the session's recorded checkpoints, newest first, using the same content rules a capture uses (REQ-GIT-034), so that `.rotaris/` and gitignored paths take no part in the comparison. The candidate set SHALL be the 10 most recent recorded checkpoints together with the checkpoint the session last restored into this tree (REQ-GIT-155) when that checkpoint is recorded and falls outside the 10, so restoring a checkpoint far back in the history never makes the very next restore demand force. A working tree equal to any candidate SHALL count as undrifted and SHALL NOT block the restore on this ground. Otherwise the newest candidate whose content can be read SHALL be the baseline, and the dirty set SHALL be every path that both differs between the working tree and that baseline and would be touched by the restore. Two residual cases resolve toward safety without raising: when the session has no recorded checkpoint at all the check SHALL report no drift and an empty dirty set, because gate 1 of REQ-GIT-058 refuses such a restore before drift can matter; and when no candidate's content can be read, because every candidate ref is gone or Git failed on each, the check SHALL report drift with the dirty set being every path the restore would touch, so the user is asked to force rather than silently overwritten.

- **REQ-GIT-057** — The dirty refusal reason SHALL be `<n> uncommitted change(s) would be overwritten: <paths>`, where `<n>` is the number of paths in the dirty set of REQ-GIT-056 and `<paths>` lists the first 5 of those paths in ascending path order, with ` and <k> more` appended when the set holds more than 5, `<k>` being `<n>` minus 5. The listed paths SHALL be delimited by `, ` — a comma followed by one space. The sentence `Restore again with force to overwrite them.` SHALL follow, separated from the first sentence by exactly one space, so the whole reason is a single line. Ascending path order, here and everywhere else in this domain, SHALL mean ascending byte order of the path's UTF-8 encoding, which is deterministic and independent of locale and of platform.

- **REQ-GIT-058** — Restore SHALL evaluate gates in this order, each refusal returning not-restored with no changed paths, the stated blocked reason, and a recorded warning issue of kind `checkpoint_restore`:
  1. Unknown sequence → `No checkpoint <n> is recorded for session <id>.`
  2. Missing Git ref, with two distinct sentences: tree unmanaged → `<tree-root> is not inside a Git working tree, so checkpoint <n> cannot be restored.`; ref pruned → `Checkpoint <n> is recorded for session <id> but its Git snapshot is gone, so it can no longer be restored.` Force bypasses neither.
  3. Git inspection failure → `Git could not inspect checkpoint <n>: <detail>`.
  4. Dirty paths without force → the REQ-GIT-057 reason. Force bypasses only this gate.
  5. The current tree is first recorded as a safety checkpoint (kind `pre_restore`, untracked files always included, commit message `rotaris pre-restore checkpoint <seq> for session <id> (before restoring checkpoint <target>)`). If it cannot be created or written, the restore does not proceed (`Could not record a safety checkpoint before the restore: <detail>` / `Could not persist the safety checkpoint on the session: <detail>` / `Could not read the session snapshot to record the safety checkpoint.`) and no file is modified. Benign exception: when the tree already matches HEAD, no safety checkpoint is needed and none is recorded.
  6. A restore failure after a successful safety checkpoint → refusal `Git could not restore checkpoint <n>: <detail>` that still reports the safety checkpoint, which is the sole surviving copy of the tree as it stood before the attempt.
  7. Success → restored, with the sequence, the safety checkpoint (or none), the changed paths, and an empty blocked reason.

- **REQ-GIT-059** — Safety-checkpoint numbering SHALL consult both the session's recorded checkpoints and the live refs (maximum of both, plus one), so a pruned record cannot yield a number that a surviving ref already uses. The safety checkpoint is appended to a freshly re-read session snapshot (checkpoints recorded by a still-running session since the restore began are not lost) and it is itself restorable on the same terms as any other checkpoint, so undoing a rollback needs no force flag.

- **REQ-GIT-060** — A forced restore SHALL preserve the overwritten uncommitted content inside the safety checkpoint: the discarded file contents are retrievable from the safety checkpoint's commit.

- **REQ-GIT-061** — A successful restore SHALL leave HEAD and the checked-out branch exactly where they were, and SHALL rewrite no commit history on any branch.

- **REQ-GIT-062** — Audit trail: a completed restore SHALL write a timeline entry of kind `checkpoint_restored` (actor `checkpoints`, message `Restored the working tree to checkpoint <n> over <k> file(s).`, metadata: sequence, ref, commit, safety sequence, changed-file count, dirty-path count, forced flag, tree root); a refusal SHALL record a warning issue reading `Restore of checkpoint <n> did not run: <reason>` with dirty paths, safety sequence, and tree root in metadata. Both land in the session's timeline and issue records (REQ-SESSION-134, REQ-SESSION-135), and both are obtainable outside this application through the export of REQ-SESSION-199.

- **REQ-GIT-063** — Every preview entry SHALL be presented to the user as a verb naming the effect the restore has on that path, and never as a status letter: `A` renders `delete`, `D` renders `recreate`, `M` renders `overwrite`, `R` renders `rename`, and every other status letter renders `change`. The same mapping SHALL apply on every surface that renders a preview (REQ-GIT-064, REQ-GIT-097).

- **REQ-GIT-064** — One textual format SHALL be defined once here and produced identically wherever a restore preview is presented. The fixed-width checkpoint listing table earlier drafts of this document defined alongside it was the output of a command that no longer exists; the same records are presented in the desktop table widget of REQ-GIT-086, with that requirement's column headings, the local-time timestamps of REQ-GIT-090, and its oldest-first row order.
  - **Restore preview text**: the line `Restoring checkpoint <n> would change <k> file(s):` followed by one line per entry reading `  <verb left-justified to width 9> <path>`, ordered by ascending path as REQ-GIT-057 defines that order, with `<verb>` taken from REQ-GIT-063. When the preview has no entries and no blocked reason, the single line `Restoring checkpoint <n> would change nothing.` replaces that whole block. When the preview has no entries but does carry a blocked reason — the checkpoint's ref is gone, or Git could not inspect it — the blocked reason alone SHALL be the whole text, on one line, and no `would change` line and no `would change nothing` line SHALL be produced, because nothing is known about what the restore would do. When the preview carries dirty paths, `Warning: <n> uncommitted change(s) would be overwritten:` followed by one line per dirty path, each indented by two spaces and in the same ascending path order, is appended. This text SHALL be produced character-for-character identically wherever a preview is shown, which is the desktop confirmation dialog of REQ-GIT-097.

- **REQ-GIT-155** — Each session record SHALL carry a last-restored sequence: an integer naming the checkpoint most recently restored into that session's tree, or absent when no restore has ever succeeded for the session. It SHALL be written as part of the same durable write that reports a restore successful (REQ-GIT-058 gate 7), SHALL be left unchanged by every refusal and by every failed restore, and SHALL default to absent when an older snapshot does not carry it (REQ-GIT-017). Its only use is to widen the drift candidate set of REQ-GIT-056; it SHALL NOT affect which checkpoints are listed, numbered, trimmed, or restorable, and a value naming a checkpoint that is no longer recorded SHALL simply contribute no candidate.

### Event Stream Contracts

- **REQ-GIT-067** — A `checkpoint.created` event SHALL carry exactly these five fields and no others: `sequence`, the integer sequence of the checkpoint, which climbs monotonically within a session (REQ-GIT-046); `ref`, the checkpoint's Git ref name; `kind`, drawn from the closed vocabulary `iteration`, `pre_restore`, `manual`; `iteration`, an integer that is `0` for a checkpoint not produced by the iteration loop (REQ-GIT-016); and `changed_paths`, a COUNT of the changed paths and never the paths themselves, so an event's size stays independent of how large the change was. It is published only after the snapshot and timeline entry are durably written; a publication failure is logged and never affects the checkpoint. Pre-restore safety checkpoints are also published as `checkpoint.created` with kind `pre_restore`.

  This requirement is the product's single definition of the `checkpoint.created` payload — its field set, each field's name and meaning, and the closed `kind` vocabulary. A document that publishes, records, exports, or documents that event SHALL cite this identifier rather than restating any of those, and a field a consumer needs is added here rather than declared elsewhere.

- **REQ-GIT-068** — A `checkpoint.restored` event SHALL carry exactly these five fields and no others: `sequence`, the integer sequence of the checkpoint the restore targeted; `restored`, a boolean; `safety_sequence`, the integer sequence of the safety checkpoint or null when none was recorded; `changed_paths`, a count that is `0` on refusal; and `blocked_reason`, the refusal's reason, empty on success. Exactly one such event is published per restore attempt, including refusals. A refused restore can still carry a safety sequence (safety checkpoint succeeded, then the restore failed) — consumers must read the field, never infer it from the restored flag. This requirement is the product's single definition of the `checkpoint.restored` payload and its field set; a document that publishes, records, exports, or documents that event SHALL cite this identifier rather than restating it.

### Session Deletion and Ref Lifecycle

- **REQ-GIT-069** — Deleting a session SHALL delete its checkpoint refs before removing the session's record and files, operating on whichever tree those refs live in (an isolated session's worktree, otherwise the recorded workspace root). Ref cleanup is best-effort: an unreadable snapshot, a moved or vanished repository, or any Git failure never blocks the deletion (a warning is logged that refs remain under `refs/rotaris/checkpoints/`). No branch or commit the user owns is affected.

### Configuration Keys

- **REQ-GIT-070** — `checkpoints.enabled` (boolean or null) SHALL default to null/unset with the per-session meaning of REQ-GIT-044. Workspace configuration layers over global configuration per field; a bare `checkpoints:` key loads as unset; an explicit `enabled: false` at workspace level is preserved as explicit false and never overridden.

- **REQ-GIT-071** — `checkpoints.max_per_session` (integer) SHALL default to 50 and SHALL be the per-session retention limit REQ-GIT-049 applies. A value below 1, zero and negative values included, and a value that is not an integer, SHALL be rejected while configuration is being loaded, so that the configuration containing it is not accepted and no run ever operates with a retention limit below 1. Any integer of 1 or more SHALL be accepted unchanged. Such a rejection is a pre-work refusal under REQ-GIT-157. The report SHALL convey the configuration key, the value that was rejected, and the constraint it broke; its wording is left to the implementation.

- **REQ-GIT-072** — `checkpoints.include_untracked` (boolean) SHALL default to true.

- **REQ-GIT-073** — `worktree_storage_subpath` (string, top-level) SHALL default to `worktrees`, placing session worktrees under `<workspace>/.rotaris/worktrees/` by default.

- **REQ-GIT-074** — Requirement-execution worktree configuration SHALL expose: `branch_template` (default `rotaris/req/{requirement_id}/{unit_id}`); `integration_branch_template` (default `rotaris/req/{req}/integration/{id}`); `target_branch` (default null, meaning the branch the workspace had checked out when the run started); `keep_failed_worktrees` (default true, meaning a failed unit's worktree and branch are left in place; when set false they are removed once the unit has failed); `retry_limit` (default 1); `unit_timeout_minutes` (default 120). In both templates `{req}` and `{requirement_id}` name the same placeholder, `{unit}` and `{unit_id}` name the same placeholder, and `{id}` and `{integration_id}` name the same placeholder; either spelling satisfies the required-placeholder check of REQ-GIT-139, which is why the default `branch_template` above is valid. This block SHALL expose no key naming an isolated-checkout directory: `worktree_subpath` is not a configuration key, and a `worktree_subpath` written here SHALL be reported and ignored rather than rejected — the workspace opens and every other key in the file loads as though it were absent — on the terms REQ-CONFIG-194 and REQ-CONFIG-183 fix, of which this document holds no copy. *This requirement formerly said such a key "is rejected as an unknown key". That is withdrawn: it cited REQ-CONFIG-194 for the terms while stating an outcome those terms no longer produce, so a build reading this sentence and a build reading the requirement it cites would have behaved differently over the same file. Nothing this document guarantees is lost — the key is still not a configuration key of any domain and still configures nothing.* The only key naming an isolated-checkout directory is `worktree_storage_subpath` (REQ-GIT-073, REQ-CONFIG-068). Where requirement-unit checkouts are placed is stated by REQ-GIT-137 and is not configurable.

- **REQ-GIT-156** — `integration.validation_command` (string or null, top-level) SHALL default to null and SHALL be the only way "the repository's own narrow validation" of REQ-GIT-132 is identified. When it is null the integration instruction SHALL carry no validation clause and no validation SHALL be run. When it holds a command, that command SHALL be quoted literally into the instruction text as the validation the agent is to run inside the integration worktree, and nowhere else in this domain SHALL it be executed: no gate of REQ-GIT-133 depends on it, so a validation the agent skipped or failed can still be caught only by the gates that are stated there. The value SHALL NOT be inferred from the repository's contents — no build file, test directory, or convention SHALL be sniffed for — and the agent SHALL NOT be asked to choose a validation for itself, so the instruction text remains checkable by reading it alone as REQ-GIT-132 requires.

Where a requirement here names a visual property — the monospace sync label of REQ-GIT-075, the monospace preview field of REQ-GIT-097, the danger styling of REQ-GIT-079, the visual tinting of a local commit in REQ-GIT-108 — that property SHALL hold, and everything else about the rendering is free.

Whether the post-merge cleanup prompt of REQ-GIT-135 appears is carried by the desktop preference `interface/worktreeCleanupPrompt`, registered with its type and default by REQ-CONFIG-405; what this domain relies on is that it is scoped to the user and not to a workspace, that its default leaves the prompt enabled, and that REQ-GIT-135 can clear it. The column split position of REQ-GIT-076 is an ordinary multi-pane divider position and is persisted with every other pane layout under REQ-SHELL-069, keyed for the `git` view; what this domain relies on is that the position is remembered per user rather than per workspace, and that a stored value that cannot be used restores the view's declared default split rather than raising an error. ### Desktop Checkpoint Flow

- **REQ-GIT-091** — Desktop checkpoint operations (list, preview, restore, repair) SHALL never block the interface, and no two of them SHALL overlap: a request that arrives while another is in flight, or during shutdown, is declined. A declined restore surfaces the toast `Rotaris is still reading checkpoints. Try again in a moment.` The UI remains responsive throughout.

- **REQ-GIT-092** — Before every preview and restore — and stamped onto listings — the desktop SHALL check whether the session is still running, with two distinct refusal texts: live run → `This session is still running. Restoring would race the run's own writes, so wait for it to finish or pause it first.`; check failed → `Rotaris could not confirm whether this session is still running, and will not risk a restore racing a live run. Try again in a moment.` A broken liveness check must never enable a restore.

- **REQ-GIT-093** — A session SHALL be reported live in exactly these cases: a run for it is under way in this application; or its persisted execution status says it is running and the process recorded in its lock (REQ-GIT-020) is still alive; or liveness cannot be established either way. A persisted running status on its own SHALL NOT make a session live. The verdict for one session SHALL depend only on that session's own records, so a neighbouring session whose records are missing or unreadable SHALL NOT change it. The liveness probe SHALL ask one question only — does a process bearing the recorded pid exist on this machine now — and SHALL NOT attempt to confirm that it is the same process that took the lock. Every residual case therefore resolves toward "live" by construction: a recycled pid answers yes and the session is reported live; a platform that still reports an exited process as present answers yes and the session is reported live; and a lock recorded by another host (REQ-GIT-020) is not probed at all and is reported live. Each of those verdicts costs the user a refusal that names a remedy, which this domain prefers to a restore or an integration racing a run that is in fact alive.

- **REQ-GIT-094** — Opening a session's checkpoints SHALL trigger a stale-session check: a persisted-busy session whose process is dead is repaired — its execution status set to `interrupted` (idempotent), the session flushed immediately, the orphaned lock removed, a timeline entry filed — and the desktop announces it with a warning notice titled `Session marked interrupted`: `This session was still marked '<previous>', but <reason>. Rotaris marked it interrupted, so its checkpoints can be restored again.` Exception: the integration precondition check passes over a stale session and leaves it alone, because checking preconditions must not mutate stored state.

- **REQ-GIT-095** — A request for a session's checkpoint listing SHALL show the card's reading state (REQ-GIT-087) and SHALL then settle exactly once, into rows, an unavailable listing, or an empty listing; the reading state SHALL appear as a state of its own on every request and SHALL never be skipped. A request arriving while another checkpoint operation is in flight SHALL be retried once, 150 ms later, against whichever session is selected at that moment, so a burst of rapid session switches SHALL end with the card showing the listing of the session selected last and SHALL never replay the listings of the sessions passed over. With no workspace open the listing SHALL be unavailable with the reason `Checkpoints are unavailable without a workspace.` A session store that cannot be read SHALL yield an empty listing together with the error dialog `Could not read this session's checkpoints` / `Rotaris could not reach the session store for this workspace.` A session with no tree that can be rolled back SHALL be unavailable with the reason `This session has no Git working tree Rotaris can roll back, so its checkpoints cannot be restored.`

- **REQ-GIT-160** — A session SHALL count as stale exactly when its persisted execution status still says it is running and the liveness probe of REQ-GIT-093 reports the process recorded in its lock (REQ-GIT-020) as not alive; a session whose liveness cannot be established, including one whose lock was recorded by another host, resolves toward live and is therefore never stale. Repairing stale sessions SHALL be a desktop action reachable from the session list (REQ-SESSION-182), offered both for one session and for every stale session in the workspace, and SHALL never run automatically from a read path. A repair SHALL set the execution status of every stale session, and of no other session, to `interrupted` — which makes that session eligible once more for checkpoint restore (REQ-GIT-092) and for integration (REQ-GIT-127) — and SHALL release the orphaned lock of every session it repairs, exactly as the repair of REQ-GIT-094 does, so that the two repair paths leave a session in the same state. Each repaired session SHALL be reported with its session id, the status it previously had, the status `interrupted`, and the reason it counted as stale; when no session was stale the action SHALL say so rather than reporting nothing. A second immediate repair SHALL find no stale session and change nothing. The session list SHALL also mark a stale session so that it cannot be mistaken for a genuinely running one, conveying that its recorded status is not trustworthy because the process behind it is gone, so a refused restore or a refused integration can be explained from the list alone. The wording and the arrangement of all of these are left to the implementation.

- **REQ-GIT-096** — Restore SHALL be preview-first: pressing "Restore checkpoint" opens a window-modal indeterminate progress dialog `Inspecting checkpoint <n>…` (window title "Checkpoints", no cancel button) and requests a preview. A sequence no longer recorded reports `Checkpoint <n> is no longer recorded for this session.`; a non-restorable preview shows the error dialog `Checkpoint <n> cannot be restored` with the blocked reason; a preview arriving for a session/sequence no longer pending is ignored. No preview SHALL be computed merely because a checkpoint row was selected: selecting a row changes only which row is selected, so the only latency this flow carries is the one the progress dialog covers, bounded by the Git limits of REQ-GIT-033, and no separate latency budget applies to it.

- **REQ-GIT-097** — The restore confirmation dialog SHALL use the window title `Restore checkpoint <n>?` and SHALL NOT be resizable below 560x400 px. It SHALL present the summary sentence `This replaces <k file(s)|nothing> in <tree-root> with the state recorded in checkpoint <n>. Rotaris records a safety checkpoint of the current tree first, so the rollback can itself be rolled back. Your branch history is not rewritten.`, with `<tree-root>` the path whose files the restore would change, and beneath it the restore preview text of REQ-GIT-064 in a read-only monospace field, character-for-character as that requirement fixes it, verbs included.

- **REQ-GIT-098** — When the preview carries dirty paths and a blocked reason, the dialog SHALL additionally show the warning text and a checkbox `Overwrite <n> uncommitted change(s)`; the destructive confirm button (labeled `Restore checkpoint <n>`) is disabled until the checkbox is ticked, with the stated reason `Confirm that the uncommitted changes above may be overwritten first.`

- **REQ-GIT-099** — Cancel SHALL be the dialog's default/focused button, and every exit path other than the confirm button (cancel, Escape, close box, destruction before shown) resolves exactly once to "do not restore"; dismissal is never treated as approval for a destructive action. The dialog is disposed after answering so a later restore can never see a stale preview.

- **REQ-GIT-100** — After confirmation the desktop SHALL show progress `Restoring checkpoint <n>…`. On failure it shows `Checkpoint <n> was not restored` with the blocked reason (or `The working tree was left unchanged.`). On success it publishes a persistent success notice titled `Restored checkpoint <n>` with body `<k> file(s) changed.` plus either `Safety checkpoint <m> holds the pre-restore state.` or `No safety checkpoint was needed: the tree already matched the last commit.`, then refreshes the Git state and the checkpoint listing. Cancelling notifies `Restore cancelled. The working tree was not changed.`

- **REQ-GIT-101** — Application shutdown SHALL wait for any in-flight checkpoint Git operation to finish rather than killing it mid-call; the wait is bounded only by the Git operation timeouts (REQ-GIT-033).

### Desktop Git Data Collection

- **REQ-GIT-102** — A desktop Git refresh SHALL always end in a rendered state and SHALL never raise a dialog or leave the window unusable: every Git read that fails or is abandoned contributes its empty value instead (REQ-GIT-112). Each individual Git read SHALL be abandoned after 15 seconds, so a refresh finishes within 15 seconds multiplied by the number of reads it makes. No console window SHALL appear on screen while a refresh runs. Exactly one refresh SHALL run at application start, beginning after the window has first been drawn and finishing before workspace onboarding is offered. The interface SHALL accept and act on user input for the whole time any refresh is running. Application shutdown SHALL wait for a refresh already under way to finish.

- **REQ-GIT-103** — Repository detection SHALL ask Git, not the filesystem: whether the folder is a repository is decided by a Git query, and whether Git is installed at all is decided by asking Git for its version (15-second timeout) — a `.git` folder on a machine without Git must not crash the window.

- **REQ-GIT-104** — When Git is not installed, a persistent informational notice with a fixed identity (so refreshes replace rather than stack it) SHALL be published, titled `Working without Git`: `Git is not installed or not on PATH, so this workspace has no history and no worktrees. Everything else works, and Rotaris makes its changes in place instead of in a worktree of its own.` The notice is scoped to a missing Git installation only: a folder that simply is not a repository opens without any notice.

- **REQ-GIT-105** — Each refresh SHALL collect: the branch the workspace has checked out; the number of commits that branch is ahead of and behind its upstream, both 0 when it has no upstream; the repository's list of worktrees — the main working tree and every linked worktree — each with its path, its branch shown without the `refs/heads/` prefix or the literal branch `detached` when it has none, and the number of commits its branch is ahead of and behind the base branch of REQ-GIT-106, both 0 for the base tree itself and both the empty value of REQ-GIT-112 when there is no base branch; the 30 most recent commits reachable from the checked-out branch, or from HEAD when the workspace is on a detached HEAD, each with an abbreviated hash, a subject line, an author name, and a relative-age label; the number of paths carrying uncommitted changes, counted under the exclusion of REQ-GIT-003; and the working tree's diff totals as an additions count, a deletions count, and a files count, counted under the same exclusion. The abbreviated hash SHALL be the first 8 characters of the full 40-character hash, which REQ-GIT-084 matches as a prefix in either direction. The uncommitted-path count SHALL include untracked paths, matching the cleanliness rule of REQ-GIT-014, so the count and the cleanliness gates never disagree about whether a tree is dirty. The relative-age label SHALL name exactly one whole unit and its count, taking the largest unit whose count is at least 1, over this ladder: an age under one minute is reported as "just now" rather than in a unit, then minutes up to 59, then hours up to 23, then days up to 29, then months of 30 days each up to 11, then years of 365 days. Singular and plural inflection and the surrounding phrasing are left to the implementation, provided the unit and the count are both conveyed. A value that a failed or abandoned read cannot supply SHALL be the empty value of REQ-GIT-112.

- **REQ-GIT-106** — A worktree SHALL be marked as the base tree when it is the repository's main working tree — the one checkout that is not a linked worktree — and as active when its resolved path equals the open workspace. The base tree SHALL NOT be identified by branch name: a repository whose trunk is called neither `main` nor `master` is treated no differently, and exactly one row is always the base tree, because a repository with linked worktrees always has exactly one main working tree. The base branch, wherever this domain uses that term for display purposes, SHALL be the branch the base tree has checked out; when the base tree is on a detached HEAD there is no base branch, and every figure that needs one takes the empty value of REQ-GIT-112.

- **REQ-GIT-107** — The additions, deletions, and files-touched figures shown for a worktree row SHALL be, in every case counted under the exclusion of REQ-GIT-003: for the base tree (REQ-GIT-106), the diff totals of its own uncommitted working-tree changes; for a worktree that is not the base tree, the totals of the diff between its branch tip and the merge base of its branch with the base tree's branch, which is the work committed on that branch since it last shared a commit with base, with no uncommitted work included; and for a non-base worktree that is also the active checkout, its committed totals combined with its own uncommitted working-tree totals, where the additions and the deletions add component-wise and the files figure is the size of the union of the two path sets, so a path appearing in both parts is counted once in the files figure and never twice. A worktree row whose figures cannot be computed because there is no base branch to compare against — the base tree is on a detached HEAD (REQ-GIT-106) — SHALL show the empty value of REQ-GIT-112 for all three figures rather than an approximation, while the base tree's own row still shows its uncommitted totals.

- **REQ-GIT-108** — A commit in the history listing SHALL be flagged local, and visually tinted, exactly when it is not reachable from the checked-out branch's upstream ref — that is, when it lies on the branch's side of the merge base with that upstream. The flag SHALL NOT be derived from position in the listing: a listing whose order differs from the divergence order, because a merge brought older commits in ahead of newer ones, still flags exactly the commits the branch holds and the upstream does not. When the branch has no upstream, or the listing is walked from a detached HEAD (REQ-GIT-105), no commit SHALL be flagged local, matching the 0 that REQ-GIT-112 gives the ahead counter in the same situation. The number of flagged commits inside the listed window therefore never exceeds the ahead counter of REQ-GIT-105, and equals it whenever the window is deep enough to hold them all.

- **REQ-GIT-109** — Persisted session bindings SHALL be joined onto the live worktree list by resolved path: a matched worktree carries the session id, that session's execution status, and the binding's merge status; failures reading sessions degrade silently; unassociated worktrees render `-` in the Session column.

- **REQ-GIT-110** — User-requested worktree creation from the desktop SHALL pre-validate the branch against the whole rule set of REQ-GIT-009, rejecting exactly the names that requirement rejects and no others, with a message conveying that the name is not a usable Git branch name; it SHALL reject a non-empty existing target directory (`Worktree path is not empty: <path>`); Git failures surface Git's own wording; a successful creation is followed by a refresh.

- **REQ-GIT-111** — Deleting a worktree at the user's request SHALL remove both its registration in the repository and its directory, so that afterwards the worktree appears neither in the repository's worktree list nor in the Git view's worktree table and its directory no longer exists; the Git view SHALL then refresh. A force variant SHALL exist that also removes a worktree Git would otherwise refuse to remove because it holds modified or untracked files. The user SHALL NOT be offered the force variant up front: deletion SHALL always be attempted without force first, and the force variant SHALL be reachable only from the second confirmation of REQ-GIT-117, shown after Git has refused for that reason. A user who never sees that refusal therefore has no way to discard uncommitted work by accident. Either outcome SHALL be reported: success notifies `Worktree deleted.`, and failure shows the dialog `Could not delete worktree` carrying the Git failure text (REQ-GIT-013, REQ-GIT-117).

- **REQ-GIT-112** — Read-path failures SHALL degrade to empty values rather than errors: a commit-less repository shows no log; no upstream means 0/0 ahead/behind; the view renders the empty version. When Git cannot be asked at all, the sentinel message is `Git is not available on this machine, so there is nothing to read or change.`

- **REQ-GIT-113** — The "set up Git here" offer SHALL be reachable from the notice action in the requirements area and from nowhere in the Git view. It SHALL carry out three steps in this order, each doing nothing when it has already been done: create a repository in the workspace when the workspace is not one already; append to `.gitignore`, creating that file when it is absent and altering none of the lines already in it, the comment line `# Rotaris keeps its sessions and delivery records here.` followed by the line `.rotaris/`, skipping this step entirely when a line reading exactly `.rotaris/` is already present; and stage every path the repository would then track — which, the gitignore step having run first, excludes everything under `.rotaris/` — and create one commit whose message is exactly `Initial commit`. A repository created by this offer SHALL be given the initial branch name `main`. The append SHALL be exact: when `.gitignore` is created by this step it receives the comment line, then the `.rotaris/` line, then a trailing newline, and nothing else; when it already exists it receives, in order, a newline first if and only if its current content does not already end in one, then one empty line, then the comment line, then the `.rotaris/` line, then a trailing newline. A file that already ends in a newline therefore gains exactly one blank line before the two added lines, and a file that does not is first terminated so the append cannot join itself to the user's last line. Taking the offer a second time therefore appends no second gitignore entry and creates no second commit, and the repository afterwards holds exactly one commit.

- **REQ-GIT-114** — Preconditions of the setup offer: Git must be installed, and a configured Git identity is checked FIRST — refusing with the message `Git does not know who you are yet, so it cannot make a commit. Set that once, from anywhere:` followed by the two indented commands `git config --global user.name "Your Name"` and `git config --global user.email "you@example.com"` and the line `Then take this offer again.` The system never invents an identity for user commits. A folder empty apart from `.rotaris` refuses with `There is nothing to commit yet — this folder is empty apart from what Rotaris keeps for itself. Add a file, then try again.` Success answers `Committed everything in this folder as "Initial commit".` plus `'.rotaris/' was added to .gitignore.` when it was. Nothing pushes.

### Desktop Worktree Creation and Deletion Dialogs

- **REQ-GIT-115** — The "New worktree" dialog (window title "Create Git worktree", heading "New worktree", description "Create an isolated branch directory for a separate Rotaris session.") SHALL offer a Branch field (placeholder `feature/short-name`) and a Directory field. Until the user edits the path by hand, the Directory field SHALL auto-derive from the branch as `<parent of the workspace directory>/<branch with each `/` replaced by `-`>`, and SHALL keep re-deriving as the branch is typed; once the user has edited it, no further derivation SHALL overwrite what they typed. The sibling-of-the-workspace location is the intended default and SHALL remain so: a manually created worktree is the user's own checkout, meant to be found and opened beside the project, and only session isolation, integration, and requirement execution place worktrees under `.rotaris/`. Manual worktrees are created at the user-chosen path, NOT under `.rotaris/`.

- **REQ-GIT-116** — The dialog SHALL validate live, disabling creation while any message applies. The messages SHALL distinguish these cases and SHALL convey, in wording left to the implementation: that no branch name has been entered; that the name holds characters or a shape Git does not allow, naming the offending part where it can be identified; that the named branch already has a worktree (checked against the current worktree table); that no directory has been chosen; and that the chosen directory already exists and a new empty path is needed. A creation failure shows the dialog `Could not create worktree` with the reported error, which is Git's own wording except in the long-path case of REQ-GIT-012.

- **REQ-GIT-117** — Deleting a worktree SHALL ask first with a confirmation box `Delete worktree?` / `Remove worktree at <path>?` followed by `This deletes the working directory and its Git metadata.`, offering Yes and Cancel with Cancel as the default. Success notifies `Worktree deleted.`; failure shows `Could not delete worktree`. When, and only when, that first deletion fails because the worktree holds modified or untracked files, a second confirmation SHALL be offered before anything else is reported: it SHALL convey that Git refused because the worktree still holds uncommitted work, that deleting anyway discards that work permanently, and which path is affected, and it SHALL offer a destructive confirm that performs the force variant of REQ-GIT-111 alongside Cancel, with Cancel the default and every dismissal path resolving to "do not delete". Declining SHALL leave the worktree untouched and report nothing further. Any other failure SHALL go straight to `Could not delete worktree` with no second confirmation, because force would not have helped.

### Worktree Integration (Merging Session Branches Into Base)

- **REQ-GIT-124** — Starting an integration from the Git view SHALL be refused, with no integration begun and with its own toast, in each of these situations, evaluated in this order with the first match deciding which toast appears: the application is running in demo mode → `Worktree integration is unavailable in demo mode.`; the open workspace is classified as replicated by a file-synchronisation agent (REQ-STARTUP-166) → a refusal conveying that the workspace sits on storage such an agent replicates to another machine, that the product therefore cannot guarantee that only one integration runs against this base branch, that no integration was started and nothing was changed, and that holding the workspace on this machine's own storage resolves it, its wording left to the implementation; that condition is evaluated ahead of the lock because it is exactly the condition under which the lock the next check reads does not mean what it says (REQ-GIT-128); an integration is already running for this workspace → the refusal REQ-GIT-128 fixes for a busy integration lock, whose text is that requirement's single definition and is deliberately not restated here, so that one condition cannot acquire two spellings; a run is active → `Finish or cancel the active run before integrating worktrees.` A run SHALL count as active here whenever it holds a session lock (REQ-GIT-020) in this workspace, whether it was started in the desktop foreground or detached into the background (REQ-SESSION-190). Because sessions are recorded machine-locally (REQ-SESSION-198), every session lock this check can see was taken by this instance; a lock naming another machine cannot arise from ordinary use and, where it does, it is evidence the session store is reachable from more than one machine (REQ-SESSION-054) and the integration is refused for that reason rather than reaped. The refusal is about what may be writing to the trees being merged, and a run with no view attached writes exactly as a foreground one does; this also keeps the check consistent with the base-worktree condition of REQ-GIT-127 and with the mandatory isolation of REQ-GIT-119 and REQ-GIT-120. When none of the four applies, the merge-order dialog of REQ-GIT-125 SHALL open.

- **REQ-GIT-125** — The merge-order dialog (title "Merge selected worktrees?", description "Selected worktree files may be staged and committed. A hidden integration agent merges them in the order below and resolves conflicts. The base branch changes only after all selected branches integrate cleanly.") SHALL show a reorderable list of `<branch> — <session-id>` entries with Move up / Move down buttons (disabled at the edges, tooltips "This branch is already merged first." / "This branch is already merged last."), Cancel focused by default, and a destructive confirm labeled "Start integration". The list SHALL hold exactly the eligible rows of REQ-GIT-083. When the selection also held ineligible rows, the dialog SHALL additionally state how many selected worktrees are not being merged and that they were left out because their session is not a completed isolated session whose merge status is `ready` or `merge_failed`; the wording is left to the implementation. The dialog's final order IS the merge order, delivered unchanged.

- **REQ-GIT-126** — While integrating, a window-modal indeterminate progress dialog titled "Merging worktrees" (no cancel button) SHALL show staged messages in order: `Preparing integration workspace…` → `Preparing isolated integration workspace…` → `Integration agent is merging selected worktrees…` → `Verifying integration and updating base branch…`.

- **REQ-GIT-127** — Integration preparation SHALL enforce, before anything changes, each failure with its own error: at least one source (`Select at least one completed isolated session.`); a clean base excluding `.rotaris` (`Base worktree has uncommitted changes. Commit or stash them first.`), checked before any source worktree is touched; no live session running in the base worktree (`A session is still running in the base worktree. Finish it before integrating.`) — a session that merely claims to be running but whose process is dead is skipped, not repaired; and per source: execution status exactly `completed` with a worktree binding (`Session <id> is not a completed isolated session.`), selected at most once (`A worktree may be selected only once.`), still belonging to this repository (`Session <id> no longer belongs to this workspace repository.`), and lockable (`Session <id> is active or already being integrated.`). Source sessions are reserved (locks held) for the duration.

- **REQ-GIT-128** — A workspace-wide integration lock SHALL be the file `<workspace>/.rotaris/integration.lock`, created with exclusive-create semantics, containing JSON `{"session_id", "pid", "host", "started_at"}`; a stale lock whose `host` names this machine and whose process is dead is reaped once, and a lock recorded by another host is never reaped, on the same reasoning REQ-GIT-020 gives for session locks. This lock stays a file beside the workspace, and stays there deliberately: what it protects is the base repository, which is the user's own material and travels with the workspace, so a second machine reaching the same checkout must meet the same lock. It is the one lock in the product that is not machine-local, and that is why `host` is load-bearing here in a way it is not for a session lock (REQ-SESSION-198). Moving it into the machine-local session store would let two machines promote into one base branch at once. Lock busy → `Another worktree integration is already running.`; unreapable → `Could not acquire worktree integration lock.` This requirement is the product's single definition of both of those texts: a document that needs to state either cites this identifier rather than restating the string, and no other requirement fixes a wording for either condition. There is one already-running refusal and not two — whether the condition is observed by the precondition check that holds its place in REQ-GIT-124's ordered refusal list or by an attempt on this lock that finds it held, the user is refused with the busy text exactly as written here, so a build that emits a second spelling of it is non-conformant. At most one integration runs per base workspace at a time.

  That cross-machine guarantee rests on exclusive create actually being exclusive, and there is one storage arrangement in which it is not. On a network filesystem exclusive create is a genuine primitive and this lock holds. Inside a file-synchronisation agent's tree it is not: such an agent replicates a file after it has been created, so two machines each create the lock locally, each succeed, and each believe they hold it. **The product SHALL NOT promise mutual exclusion it cannot enforce.** Where the open workspace is classified as replicated by a file-synchronisation agent, an integration SHALL be refused before anything is attempted, and the lock SHALL NOT be created at all — proceeding under a lock that does not lock is the outcome this refusal exists to prevent. That refusal is a pre-work refusal under REQ-GIT-157, leaving no lock, no worktree, no branch and no modified file behind, and it takes its place in the ordered refusal list of REQ-GIT-124.

  The classification is REQ-STARTUP-166's and SHALL NOT be made again here. This domain states no storage test of its own, consults the classification that requirement already produces for every workspace the product opens, and adds no notice of its own to the one REQ-STARTUP-166 already raises. Only the replicated classification refuses: storage another machine can reach directly does not, because exclusive create is real there and the lock does exactly what the paragraph above says it does. A workspace REQ-STARTUP-166 could not classify does not refuse either, and neither does one whose classification is not yet determined — an inconclusive answer is a silent negative there, it stays one here, and refusing a user's integration on a guess would be its own defect.

  **The strength of this response is under review.** Refusal is what this requirement specifies and what a conformant build does. Whether a warning the user may proceed past would be sufficient instead is left to the synchronised-storage measurement; what that measurement does not reopen is the direction, which is settled: the product does not proceed under a lock that does not lock. *That measurement has since been taken and it did not settle the strength: it confirmed that exclusive create is a genuine primitive over a network share, and could not reach the file-synchronisation case at all, which needs a second machine and an account with a synchronisation provider. It stated the closing experiment rather than inventing a result. This sentence therefore stands, and a reader is told the measurement has reported so they do not wait for an answer that has already come back empty.*

- **REQ-GIT-129** — During preparation, each source worktree's pending uncommitted changes SHALL be committed automatically with the fixed identity `rotaris <rotaris@local>` and the message `Rotaris: accept session <id> worktree changes`; a clean source is left alone.

- **REQ-GIT-130** — The integration workspace SHALL be a fresh worktree on branch `rotaris/integration/<integration-session-id>` at `<workspace>/.rotaris/<storage-subpath>/integrations/<integration-session-id>`, cut from the planned base revision; a path collision refuses with `Integration worktree path already exists: <path>`. Each source binding is stamped merge status `integrating` plus the integration session id and flushed. On ANY preparation failure all reservations and the lock are released.

- **REQ-GIT-131** — The integration itself SHALL be an ordinary hidden run: a new internal session attached to the integration worktree, single-agent, marked internal (durable for recovery but hidden from normal session lists), receiving the full run treatment — event stream, session start/end, lifecycle hooks, and per-iteration checkpoints. Hidden integration sessions and control metadata must not block later acceptance of the work.

- **REQ-GIT-132** — The instruction text delivered to the integration agent SHALL be checkable by reading it alone. It SHALL contain the branches to merge as a numbered list in the exact order supplied, and SHALL state each of the following: merge them in that numbered order; work only inside the integration worktree, changing neither the base worktree nor any source worktree; create one merge commit per branch with fast-forward suppressed; resolve every conflict in keeping with the conventions already visible in the repository, stage the resolution, and complete the merge commit; run the repository's own narrow validation where the repository provides one; report completion only when the integration worktree is clean and every named branch is an ancestor of the integration branch's HEAD; and never reset, never push, and never leave out a selected branch. The clause requiring the repository's own narrow validation SHALL be included exactly when a validation command is configured (REQ-GIT-156), SHALL name that command literally, and SHALL be omitted entirely when none is configured; the agent SHALL NOT be asked to infer a validation from the repository's contents. Whether the agent obeys is outside this requirement and outside this domain: no requirement here SHALL constrain the quality of the agent's conflict resolutions or the number of iterations it takes, and conformance SHALL be judged on this instruction text and on the promotion gates of REQ-GIT-133, which re-check the outcome before the base branch moves and which leave the base untouched whenever the agent fell short.

- **REQ-GIT-133** — Before the base branch moves, promotion SHALL re-check all of the following, in this order, and any failure SHALL leave the base branch and the base working tree exactly as they were while reporting its own error: the base working tree is clean apart from `.rotaris/` (the cleanliness rule of REQ-GIT-014); the base checkout is still on the branch and at the revision recorded when the integration was planned (`Base branch changed while integration ran. Base was left untouched.`); the integration worktree has no uncommitted changes (`Integration worktree still has uncommitted changes. Base was left untouched.`); and every source branch is an ancestor of the integration branch's tip (`Integration did not include source branch <branch>. Base was left untouched.`). The base branch is then advanced by fast-forward only: afterwards it points at the integration branch's tip and its previous tip is an ancestor of that commit, and no merge commit and no history rewrite is ever created on the base branch. On success every source binding's merge status becomes `merged`, the source worktrees are kept, and the temporary integration worktree and its branch are removed on a best-effort basis — a removal that fails is logged and does not turn a completed promotion into a reported failure. On failure every source binding's merge status becomes `merge_failed`. In both outcomes the source-session reservations and the integration lock are released. A fast-forward update that fails after every gate has passed SHALL be treated exactly as a failed gate: it is a promotion failure, the base branch and the base working tree are left as they were, the source bindings become `merge_failed`, and the integration worktree is retained (REQ-GIT-134). Its error SHALL convey that the base branch could not be advanced and that the base was left untouched, and SHALL carry the Git failure text of REQ-GIT-013 verbatim as its detail; the surrounding wording is left to the implementation. Because the update is fast-forward only, a failed update never leaves the base branch partly moved.

- **REQ-GIT-134** — Desktop integration outcomes: success closes the progress dialog, refreshes sessions and Git state, toasts `Selected worktree changes are now on the base branch.`, then offers cleanup (REQ-GIT-135). Failure shows a recovery dialog titled `Worktree integration needs recovery` with body `Base branch was left unchanged. Review the retained integration worktree and retry when ready.` and details carrying the underlying message — suffixed, when a plan existed, with `Base was left untouched. Retained integration worktree: <path> (branch <branch>).` The integration worktree of a failed integration is retained on disk.

- **REQ-GIT-135** — The post-merge cleanup prompt SHALL be governed by the desktop preference `interface/worktreeCleanupPrompt`, whose type and default REQ-CONFIG-405 registers and which this domain relies on being enabled by default (REQ-GIT-153). While that preference is disabled the prompt SHALL NOT appear and no worktree SHALL be deleted. While it is enabled the dialog `Delete merged worktrees?` — "The following worktrees were just merged into the base branch." / "Delete them to keep your workspace clean?" — SHALL list `<branch>  →  <path>` for each just-merged, non-base, non-active worktree and SHALL offer a "Don't ask again" checkbox, which clears the preference when ticked whether the user then chooses Delete or Keep, together with Delete and Keep buttons. Delete removes exactly the listed worktrees and nothing else; partial failure shows `Some worktrees could not be deleted` / `Deleted <k> of <n> worktrees.` with per-path details; full success toasts `Deleted <n> merged worktree(s).` Keep deletes nothing.

- **REQ-GIT-136** — While an integration runs: opening another project SHALL be refused with `Finish the worktree integration before opening another project.`; quitting the app SHALL be warned against with `Keep Rotaris open until the isolated worktree integration finishes.`; a second integration start and an empty selection are both refused.

### Requirement-Execution Worktrees (Shared Namespace Contracts)

- **REQ-GIT-137** — A worktree created for a requirement unit SHALL be subject to the same rules a caller can observe on a session worktree. Its branch name SHALL be accepted or rejected exactly as REQ-GIT-009 states, with the same `Invalid Git branch name: <value>` error. Creation SHALL fail with `Workspace must be the root of its Git worktree.` when the workspace is not the root of its own Git worktree, and with `Detached HEAD cannot host an isolated session or integration.` when the workspace checkout is on a detached HEAD (REQ-GIT-006). A branch name already taken SHALL receive the deterministic suffixes `-2`, `-3`, … up to the same 50 attempts, after which creation fails (REQ-GIT-010). Requirement-unit branches SHALL be created under the `rotaris/req/` prefix and their directories under `<workspace>/.rotaris/requirements/worktrees/`. That location is fixed here and is not named by any configuration key (REQ-GIT-074, REQ-CONFIG-194).

- **REQ-GIT-138** — The three branch namespaces `rotaris/session/`, `rotaris/integration/`, and `rotaris/req/`, and the worktree directories belonging to each, SHALL stay disjoint: no branch this domain creates SHALL fall under two of those prefixes, and no worktree directory of one namespace SHALL lie inside the directory of another. A violation SHALL be caught while configuration is loaded rather than when a branch or directory is created, so that the configuration is not accepted and nothing is ever created from it: a `branch_template` or `integration_branch_template` that would produce names under `rotaris/session/` or `rotaris/integration/` SHALL be rejected. No directory-side rejection arises, because no configuration key names a requirement checkout directory (REQ-GIT-074, REQ-CONFIG-194): the only configurable checkout directory is the session one named by `worktree_storage_subpath`, and it SHALL be rejected when it resolves to the fixed requirement checkout directory of REQ-GIT-137 or to any directory inside it. The template check SHALL be made on a rendered example name, not on the literal template prefix: every placeholder the template holds is substituted with a fixed non-empty sample value, the result is slugged and assembled exactly as REQ-GIT-139 assembles a real name, and the finished example is tested for the forbidden prefixes. A template that reaches a forbidden namespace only after substitution is therefore caught, which a literal prefix test would miss. Each rejection SHALL convey the configuration key, the value that was rejected, the namespace it collided with, and — for a template — the rendered example that demonstrated the collision; the wording is left to the implementation, and the process behaviour on rejection is the one REQ-GIT-071 fixes for every configuration value in this domain. The default `worktree_storage_subpath` resolves to `<workspace>/.rotaris/worktrees/` (REQ-GIT-073), which lies outside the fixed requirement checkout directory of REQ-GIT-137 and therefore passes this check.

  > another namespace, or the fixed requirement checkout container of REQ-GIT-137 (`<workspace>/.rotaris/requirements/worktrees/`);
  > it does not mean every directory that encloses that container. A session storage directory that merely contains it — a

- **REQ-GIT-139** — A requirement `branch_template` SHALL be rejected unless it contains a requirement placeholder (`{req}`, or its alias `{requirement_id}`) and a unit placeholder (`{unit}`, or its alias `{unit_id}`); REQ-GIT-074 fixes the alias pairs, so the default template validates. When the template contains no `{attempt}` placeholder, `-a<attempt>` SHALL be appended to the rendered name for every attempt from the second onward, so attempt 2 ends in `-a2`. For delivery cycles after the first, `-c<cycle+1>` SHALL be appended, so the second cycle ends in `-c2`. Every value substituted into a placeholder SHALL be reduced to a slug first, so no substituted id can introduce a `/` or any other path separator into the branch name. Slugging SHALL be exactly this, in this order: fold the value to lower case; replace every maximal run of characters outside `a`–`z`, `0`–`9`, `.`, `_`, and `-` with a single `-`; strip leading and trailing `-` and `.`; truncate to at most 40 characters and strip any `-` or `.` the truncation left at the end; and, when nothing remains, use the single character `x`. Both suffixes MAY appear on one name, and when they do the cycle suffix SHALL precede the attempt suffix, so the third attempt of the second cycle ends in `-c2-a3`; suffixes are appended after slugging and are never themselves slugged. The finished name SHALL then be subject to REQ-GIT-009 and rejected there if it fails.

- **REQ-GIT-140** — After a requirement-unit worktree has been provisioned, its repository root and its checked-out branch SHALL be read back and compared with what was requested; a mismatch SHALL fail provisioning rather than return the tree. A workspace path supplied by a caller that resolves to the base checkout SHALL be rejected, so unit work is never written into the base tree; the rejection SHALL convey the path as supplied, that it resolves to the base checkout, and that a requirement unit is never run there, and its wording is left to the implementation. At any moment: no branch and no directory SHALL be held by two units, and no unit SHALL hold two workspaces for the same attempt. Each attempt of a unit SHALL be given a directory of its own, so a failed attempt's tree is still on disk and inspectable while the next attempt runs. That directory SHALL be named for the attempt's own branch — the rendered branch name of REQ-GIT-139, including its cycle and attempt suffixes, with each `/` replaced by `-` — placed directly under `<workspace>/.rotaris/requirements/worktrees/`. Because REQ-GIT-139 gives every attempt of every unit a distinct branch name, and REQ-GIT-010 resolves any residual branch-name collision before the directory is derived, that name is unique per attempt and no two attempts can be handed the same directory. A directory of that name already existing SHALL fail provisioning with the error of REQ-GIT-008 rather than be reused.

- **REQ-GIT-141** — The base checkout's branch and revision SHALL be recorded before any requirement-execution Git work begins and read again after it ends; if either differs, the operation SHALL fail with a message reporting both the recorded and the observed value, of the form `the base checkout moved from <a> to <b> while a requirement unit was running…`. Every requirement-execution Git invocation SHALL be abandoned once that single invocation has run for 30 seconds, and the operation that issued it then fails. Worktree paths SHALL be compared after normalizing path separators and ignoring letter case, so one tree is recognized as itself however its path was spelled. The moved-base message SHALL convey all four of: the branch and revision recorded before the work began, the branch and revision observed after it ended, that a requirement unit was running in between, and that the operation was abandoned rather than completed; the wording that carries them is left to the implementation.

- **REQ-GIT-159** — Where a requirement run is started from the desktop (REQ-TRACE-464), the user SHALL be able to choose the commit its unit worktrees are cut from, defaulting to the workspace's current HEAD as REQ-GIT-007 states, so a run can be forked from a declared target instead of the current checkout. A value that does not resolve to a commit in this repository SHALL be refused before any worktree, branch, or session exists, as a pre-work refusal under REQ-GIT-157, with a message conveying the value as supplied and that it names no commit here. Leaving the choice untouched SHALL be indistinguishable from a run that was never offered it. The configured `target_branch` of REQ-GIT-074 continues to name the branch the work is destined for and is not affected by this choice.

- **REQ-GIT-142** — Failed unit worktrees SHALL be kept by default (`keep_failed_worktrees: true`), and trees created before a later provisioning failure stay recorded, since an existing tree is still evidence of what was attempted.

### Agent Commits and Attribution

- **REQ-GIT-143** — An agent SHALL be able to create a local commit only through a tool named `git_commit`, described as "Create a local git commit". The tool SHALL take exactly two parameters: `message` (string, required), the commit message used verbatim, and `files` (array of strings, optional, default empty), the paths to stage, each interpreted relative to the workspace root. When `files` is non-empty, exactly those paths SHALL be staged whatever their current state — a modified tracked file, an untracked file, and a tracked file deleted in the working tree are all staged as named — and a named path that resolves outside the workspace SHALL be rejected with the message `Path escapes workspace`. When `files` is empty or omitted, every tracked file carrying a modification SHALL be staged and so SHALL every tracked file deleted in the working tree, because a deletion is a change to a tracked file and leaving it out would produce a commit that does not match what the agent sees; no untracked file SHALL ever be staged by that form, so the agent cannot sweep a stray artefact into a commit by omitting `files`. Invoking the tool where the workspace is not a Git repository SHALL be an error whose message conveys that the workspace is not a Git repository and that no commit was made; its wording is left to the implementation. Having nothing staged to commit SHALL be an error whose message begins `No changes to commit`. In every error case no commit SHALL be created. The commit SHALL be authored with the identity the repository is configured with and never with an author supplied by the tool, and on success the tool SHALL return the full 40-character commit SHA together with the list of paths it staged. The tool SHALL perform no network operation (REQ-GIT-001).

- **REQ-GIT-144** — Commit authorship in the Git view SHALL be whatever the repository's log reports per commit. Rotaris-machinery commits are distinguishable by the fixed `rotaris <rotaris@local>` identity, which is used ONLY for checkpoint objects and integration acceptance commits — never for user or agent commits.

### Concurrency and Timing (Consolidated)

- **REQ-GIT-145** — Concurrency limits SHALL be: at most one desktop checkpoint operation in flight (REQ-GIT-091); one integration per base workspace — held by the integration lock where that lock can be exclusive, and by refusing the integration outright where the workspace's storage cannot make it exclusive, since the limit is never asserted on a lock that does not lock (REQ-GIT-128); one run per session (session lock, stale-reaped, REQ-GIT-020); and no fixed ceiling on how many isolated runs may proceed at once — host resources are the only limit.

- **REQ-GIT-146** — The following values SHALL hold, each defined by the requirement named beside it and gathered here so the whole set can be checked at once; every entry agrees with its defining requirement. Git-view rebuild coalescing 120 ms (REQ-GIT-082); checkpoint listing retry delay 150 ms (REQ-GIT-095); desktop Git read timeout 15 s (REQ-GIT-102) and Git version-check timeout 15 s (REQ-GIT-103); worktree-layer Git timeout 30 s (REQ-GIT-013); checkpoint ref timeout 30 s and checkpoint tree-walk timeout 300 s (REQ-GIT-033); requirement-execution Git timeout 30 s (REQ-GIT-141); drift-baseline lookback 10 checkpoints (REQ-GIT-056); branch-name collision attempts 50 (REQ-GIT-010); default checkpoint retention 50 per session, minimum 1 (REQ-GIT-049, REQ-GIT-071); commit history depth 30 commits (REQ-GIT-105); requirement unit timeout 120 minutes and retry limit 1 (REQ-GIT-074). Numeric constants outside this list — widget minimum sizes, the 9-character verb column of the preview text in REQ-GIT-064, the 5-path cut-off of REQ-GIT-057, and the single lock-acquisition retry of REQ-GIT-020 — are stated only by the requirements that define them.

### Edge Cases

- **REQ-GIT-147** — Empty/unborn repository: checkpoint creation with no HEAD produces a parentless commit (or no checkpoint for an empty tree); the desktop opens a commit-less repository without crashing; ahead/behind without an upstream is 0/0.

- **REQ-GIT-148** — Detached HEAD: checkpoints and restores work; session and integration worktree creation refuses (REQ-GIT-006); the status strip conveys that the checkout is on no branch (REQ-GIT-161); the desktop worktree list renders the branch as `detached`.

- **REQ-GIT-149** — A restore attempted immediately after a restore SHALL report no drift, so undoing a rollback needs no force flag. This holds however far back the checkpoint that was just restored lies, because REQ-GIT-155 keeps it in the drift candidate set of REQ-GIT-056 whether or not it falls inside the 10 most recent.

- **REQ-GIT-150** — A session that crashed mid-run remains marked running until repaired; the desktop repairs and announces it on the checkpoint path (REQ-GIT-094); integration skips it without repairing; every ambiguity about liveness resolves toward "live"/refusal. That rule is about liveness and reaches nothing else: an undetermined or unclassifiable workspace-storage classification is not a liveness ambiguity, and it does not refuse an integration (REQ-GIT-128, REQ-STARTUP-166).

- **REQ-GIT-151** — Deleting a session whose workspace or repository has vanished SHALL still succeed, with ref cleanup silently degrading (REQ-GIT-069). Legacy pre-worktree snapshots load per REQ-GIT-017. Refusal texts throughout the domain SHALL remain distinct sentences — "running" vs "could not confirm" vs "not a Git tree" vs "snapshot gone" vs "uncommitted changes" vs "this workspace is replicated to another machine" (REQ-GIT-128) — because each one points at a different remedy.

## Data & Formats

All formats below are externally observable on disk, in the repository, or on the event stream.

### On-disk layout (base workspace)

What a session records — its listing record with the worktree binding and `checkpoint_count`, its lock, its timeline entries and its recorded issues — is held in the durable session store, not on this layout. Where that store is, and what it holds, are REQ-SESSION-001's, REQ-SESSION-198's and REQ-SESSION-002's; this document names no path for any of them. What remains on disk in the base workspace is the working material below.

```
<workspace>/.rotaris/
  worktrees/<session-id>/            # isolated session worktrees (subpath configurable)
  worktrees/integrations/<integration-id>/   # temporary integration worktrees (under the same subpath)
  requirements/worktrees/<unit-id>/  # requirement-unit worktrees; this location is fixed by REQ-GIT-137 and no configuration key names it
  integration.lock       # exclusive-create; JSON {"session_id", "pid", "host", "started_at"}
                         # never created where the workspace's storage cannot make exclusive create
                         # exclusive; the integration is refused instead (REQ-GIT-128, REQ-STARTUP-166)
```

### Git namespaces

- Checkpoint refs: `refs/rotaris/checkpoints/<session-id>/<sequence>` (REQ-GIT-029; numeric sequences; commit objects carrying the fixed identity REQ-GIT-032 fixes).
- Session isolation branches: `rotaris/session/<session-id>` (REQ-GIT-007), with the collision suffixes `-2`, `-3`, … of REQ-GIT-010.
- Integration branches: `rotaris/integration/<integration-session-id>` (REQ-GIT-130).
- Requirement branches: `rotaris/req/...` (templates per REQ-GIT-074/139, placement per REQ-GIT-137); the three prefixes are mutually exclusive namespaces (REQ-GIT-138).

### Persisted records (behavioral schemas)

- Worktree binding: the record REQ-GIT-015 defines. That requirement is normative for the field set, the `merge_status` vocabulary and the defaults; this line names the record only so the layout above can refer to it.
- Checkpoint record: the record REQ-GIT-016 defines, which is normative for the field set and the defaults; its `kind` takes the vocabulary REQ-GIT-067 closes. The names by which the fields are written are `sequence` (int), `ref` (string), `commit` (string), `created_at` (timestamp), `iteration` (int, default 0), `child_name` (string, default empty), `files` (list of paths changed relative to the parent commit), and `kind`.
- Session record (checkpoint-related fields only): `checkpoint_count` (int), `last_restored_sequence` (int or null, default null — REQ-GIT-155).

### Commit message formats (fixed identity `rotaris <rotaris@local>`, which REQ-GIT-032 fixes and REQ-GIT-144 limits to checkpoint objects and integration acceptance commits)

- Iteration checkpoint: `rotaris checkpoint <sequence> for session <session-id> (iteration <n>[ by <child-name>])` (REQ-GIT-047)
- Safety checkpoint: `rotaris pre-restore checkpoint <sequence> for session <session-id> (before restoring checkpoint <target>)` (REQ-GIT-058, gate 5)
- Integration acceptance commit (in a source worktree): `Rotaris: accept session <session-id> worktree changes` (REQ-GIT-129)
- Repository-setup first commit (user identity, not the fixed identity): `Initial commit` (REQ-GIT-113)

### Event shapes (stored event stream)

- `checkpoint.created`: the payload REQ-GIT-067 defines. That requirement is normative for the field set, each field's name and meaning, and the closed `kind` vocabulary; this line names the event only so the stream can be located here.
- `checkpoint.restored`: the payload REQ-GIT-068 defines, which is normative for its field set and for the rule that `safety_sequence` may be set even when `restored` is false; this line adds nothing to it.

### Shared textual formats

- Checkpoint listing: presented only in the desktop table widget of REQ-GIT-086, with that requirement's column headings, the local-time timestamps of REQ-GIT-090, and rows oldest first. There is no textual listing format.
- Preview text (fixed character-for-character wherever a preview is shown, which is the desktop confirmation dialog, REQ-GIT-064/097): `Restoring checkpoint <n> would change <k> file(s):` then `  <verb padded to 9> <path>` lines in ascending path order; the nothing-to-change, blocked-reason-only, and dirty-warning variants per REQ-GIT-064.
- Ascending path order, everywhere in this domain: ascending byte order of the path's UTF-8 encoding (REQ-GIT-057).
- Desktop Files cell: `+<additions> -<deletions> / <files-touched>` (REQ-GIT-077, over the figures REQ-GIT-107 defines); sync label `ahead <n>  behind <m>` (REQ-GIT-075, over the counts REQ-GIT-105 collects, with the empty rendering of REQ-GIT-112); cleanup list rows `<branch>  →  <path>` (REQ-GIT-135); session rows `<branch or —> · <state>` (REQ-GIT-122); checkpoint picker entries `<session-id> · <branch>` (REQ-GIT-086).

### Configuration surface (layered YAML)

- `checkpoints.include_untracked`: bool (default true; see REQ-GIT-072)
