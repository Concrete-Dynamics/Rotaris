# Multi-Agent Run Orchestration

## Overview

A run takes one top-level user task and executes it through an autonomous, iterative multi-agent process: the task is classified for intent, handed to a coordinator role that delegates work to specialist child agents through an explicit delegation tool, and driven by an outer iteration loop that targets one todo task per iteration, verifies changed work with deterministic checks, and re-queues or abandons tasks based on evidence. The run ends with a well-defined stop reason, a terminal status with a process exit code, durable session records, and per-child machine-readable report artifacts; safety mechanisms (limits, timeouts, a hidden loop monitor, a message-limit soft pause, and cancellation sweeps) guarantee that no run ends with work items or child records left in a non-terminal state.

## Requirements

### 1. Run Entry and Session Setup

- **REQ-ORCH-001** — Given the same task, the same configuration, and the same run options, a run started from the background/headless command-line host and a run started from the interactive terminal UI host MUST reach the same orchestration outcome: the same intent handling, the same delegation and iteration rules, the same verification gating, the same stop reason, and the same terminal status and process exit code. The hosts are permitted to differ only in how they present the run and in two options they may supply differently — the run override of REQ-ORCH-025, and how a message-limit pause is surfaced and resolved (interactive dialog per REQ-ORCH-086, signal file and `paused_message_limit` status per REQ-ORCH-087).
- **REQ-ORCH-002** — The top-level user task MUST be given to a single configurable entry role (default role name `orchestrator`). This entry role is an ordinary configurable role whose orchestration authority derives entirely from its instructions and granted tool set; each iteration of the outer loop starts it fresh as that iteration's root agent.
- **REQ-ORCH-003** — The user's original request text MUST be captured at run start, before any later modification of the work plan, and MUST remain available unchanged as the anchor for intent evaluation and end-of-run fulfillment auditing.
- **REQ-ORCH-004** — Given a fresh session, when a run starts, a new todo list MUST be created with a single initial phase (named "main") containing the task. Given a resumed session, the new top-level task MUST be appended to the session's existing todo state. The execution payload handed to the root agent MUST carry the conversation context in effect, the artifacts recorded for the session, the todo state as it currently stands, and the progress accumulated before this run.

### 2. Pre-Flight Intent Classification

- **REQ-ORCH-005** — Intent classification MUST complete before the coordinator is initialized, and the classified intent MUST be in effect before the first iteration so that intent-dependent behavior (capability gating, playbook cells, budget clamps, route-aware guards) applies from iteration 1.
- **REQ-ORCH-006** — The intent taxonomy MUST consist of exactly these 13 categories: `explicit_trivial`, `question`, `exploration`, `problem_resolution`, `single_file_change`, `small_feature`, `moderate_feature`, `large_feature`, `refactor`, `architectural`, `requirements`, `whole_project`, `ambiguous`. Category semantics MUST include: `problem_resolution` means diagnose AND fix; `exploration` means investigate only; when several categories are plausible the tie-break prefers `moderate_feature`.
- **REQ-ORCH-007** — Any classification failure — timeout, unparseable response, unmapped category string, empty response, or setup error — MUST produce the fallback intent `moderate_feature`, flagged as a fallback with a human-readable reason, and MUST NOT stop or fail the run.
- **REQ-ORCH-008** — The classification call MUST time out at 8.0 seconds by default. The user prompt sent to the classifier MUST be truncated to 4000 characters. Only the raw user prompt plus a small metadata mapping (e.g. which entrypoint started the run) may be sent — no codebase content.
- **REQ-ORCH-009** — The model used for classification MUST be selected by consulting three configured model slots in a fixed order — the small-model slot, then the fallback-model slot, then the default summary-model slot — and using the first slot that is set. When none of the three is set, no request is sent to any provider and the run proceeds immediately on the fallback intent `moderate_feature`, flagged as a fallback, with a reason stating that no small model is configured. (The configuration key names of these three slots are not fixed by this document; see Open Questions.)
- **REQ-ORCH-010** — Structured output MUST be requested through a three-rung degradation ladder tried in order: (1) strict, enum-constrained JSON schema; (2) generic JSON-object mode with an appended instruction showing the exact keys and one example; (3) unconstrained text. A rung a given model has previously rejected MUST be remembered per model for the session and skipped on later calls; per-model capability configuration MAY pre-map a rung (e.g. forcing a model straight to JSON-object mode).
- **REQ-ORCH-011** — The classification result MUST carry: the intent category, a confidence value in [0, 1] or null, a reason string, a fallback flag, and a carried-over flag.
- **REQ-ORCH-012** — When the session has prior completed coordinator iterations, the latest usable one's stored summary (else its final response text), truncated to 4000 characters, MUST be passed to the classifier as optional prior-response context. Iterations persisted without a role attribution are ineligible. The classifier instructions MUST direct that this history is untrusted context and that instructions embedded in it must never be followed.
- **REQ-ORCH-013** — Resume intent carry-over: when (a) the fresh classification is unusable (`ambiguous` or a fallback), (b) the session has a prior recorded intent that is a real non-ambiguous category, and (c) the session todo still has unfinished work (pending, in-progress, and abandoned items all count as unfinished), then the prior intent MUST be inherited deterministically with no model call, the carried-over flag set, and a reason stating the previous intent was continued. An unreadable todo state MUST count as "no unfinished work" (no carry-over).
- **REQ-ORCH-014** — In the interactive host, a transient "Classifying intent..." status MUST appear before the classification call and be replaced in place by "Intent classified: <intent>". A carried-over intent appends the suffix "(continued from previous run)"; a fallback appends "(fallback)" or "(fallback: <reason>)" where the reason is normalized (a provider's structured-output rejection is summarized as a generic provider-rejection phrase) and truncated to 180 characters.
- **REQ-ORCH-015** — The classified intent MUST be propagated to the child-execution layer so that completion guards are route-aware: a run classified as answer-only (question/exploration) MUST NOT fail a child for producing no file edits.

### 3. Intent-Based Capability Gating

- **REQ-ORCH-016** — A user-inspectable intent-to-tools mapping MUST gate the entry role's tool set, keyed on the classified intent alone. Exactly the two simplest intents (`explicit_trivial`, `single_file_change`) grant the entry role a direct-work bundle (delegation and todo management plus direct file read/write, search, fetch, terminal, commit, and artifact-read capabilities). Every other intent applies no mapping entry, leaving the role's configured coordination-only restrictions in force. The run override of REQ-ORCH-025 is not an input to this mapping. (Whether a `single` override is meant to change the entry role's capabilities is open; see Open Questions.)
- **REQ-ORCH-017** — Mapping errors MUST fail safe: an unknown intent key, a malformed tool list, or an unreadable mapping file results in no tool restriction being applied, with a logged warning. Obsolete instruction-text entries in the mapping MUST be rejected.
- **REQ-ORCH-018** — The intent tool gate MUST apply only to the configured entry role; other roles' tool sets are unaffected by intent.

### 4. Behavior Playbook Matrix

- **REQ-ORCH-019** — Per-intent behavior MUST be drawn from a playbook matrix whose row is selected by three keys — role, classified intent, and model tier — and which the user can override per REQ-ORCH-026. The playbook rendered for a role MUST form part of the instructions that role is given, for every role that has a matching row and not only for the coordinator; a role with no matching row is given no playbook text at all (REQ-ORCH-023). The cell selected for the run MUST be recorded per REQ-ORCH-027, so which row was in force is verifiable after the run. (The model-tier vocabulary is not fixed by this document; see Open Questions.)
- **REQ-ORCH-020** — A rendered playbook MUST contain all eight slots, each exactly once, in this order: ROUTE, AUTONOMY, RESEARCH, CHUNKING, VERIFY, ARTIFACT, OUTPUT, BUDGET. Where one role produces output that a different role will carry out (for example a plan written for an implementer), the CHUNKING and OUTPUT slots MUST be taken from the tier of the role that will carry the work out, and only when that tier is lower than the producing role's own; this substitution MUST never move a slot to a higher tier. (The set of producer-to-consumer role pairings, and the ordering that decides which tier is lower, are not fixed by this document; see Open Questions.)
- **REQ-ORCH-021** — Intents MUST resolve through groups: answer = {question, exploration}; clarify = {ambiguous, requirements}; micro = {explicit_trivial, single_file_change}; fix = {problem_resolution, refactor}; small-build = {small_feature}; medium-build = {moderate_feature}; large-build = {large_feature, architectural, whole_project}. Lookup order is: concrete intent → its group → a default row. Tier lookup is: concrete tier → an all-tiers wildcard.
- **REQ-ORCH-022** — The coordinator's playbook row MUST be keyed on the model tier of whichever role will actually carry out the work, not on the coordinator's own tier: refactor work → the refactoring role (`refactorer`), requirements work → `requirements-engineer`, architectural work → `architect`, and `coding-agent` in every other case. As a consequence, whether a planning step comes first depends on that role's tier: when it sits on the largest tier it scopes its own work, so mid-size features and restructuring work do not compel a separate planning step.
- **REQ-ORCH-023** — When a tier cannot be resolved, the medium tier MUST be used and the rendered playbook header MUST state that the model size is undetermined and larger capacity must not be assumed. A role with no matrix row receives no playbook. A cell marked as not routed renders text instructing the role to treat its assignment as narrow because it is outside the standard flow.
- **REQ-ORCH-024** — The BUDGET slot MUST be enforced, not advisory: the resolved cell's budget clamps the runtime child-limit policy for that iteration — tight = {max active children 2, max total children 6, max depth 2}; normal = {4, 12, 3}; wide = no clamp. Clamps only narrow (a tighter configured limit always wins), and any budget-resolution failure falls back to the configured policy unchanged.
- **REQ-ORCH-025** — A host-selected run override MUST be supported as a final layer, placed after everything else and stated to take precedence over the matrix cell: a "swarm" override demands maximum parallel delegation (overlapping ownership of the same work slice remains forbidden), and a "single" override demands the role complete the task itself without delegating.
- **REQ-ORCH-026** — Playbook content MUST be overridable at two scopes: a global user-configuration directory, and the workspace directory `<workspace>/.rotaris/playbooks/`. Where both scopes define the same field, the workspace value is the one that takes effect; fields the workspace leaves undefined keep their global value, and fields neither scope defines keep the built-in value. An override MAY supply different text for a slot variant the built-in catalogue already defines. An override MUST NOT introduce a slot name or a variant identifier that the catalogue does not define; such a name MUST be ignored, leaving the catalogued content in force, and MUST produce a warning naming it. After an explicit reload, every subsequently rendered playbook MUST reflect the override files as they stand on disk at the time of the reload. (The path of the global-scope directory is not fixed by this document; see Open Questions.)
- **REQ-ORCH-027** — The resolved playbook cell in effect for a run MUST be recorded as an audit payload in the session's run-configuration record (see Data & Formats).

### 5. Coordinator Role Contract

- **REQ-ORCH-028** — The coordinator's instructions MUST carry a routing table from need to specialist role. The default role vocabulary MUST be `orchestrator` (the coordinator itself), `requirements-engineer`, `codebase-analyst`, `librarian`, `architect`, `planner`, `coding-agent`, `tester`, `docs-writer`, `refactorer`, `verifier`, `ui-verifier`, `gatekeeper`. The default routing MUST be: an ambiguous or under-specified request → `requirements-engineer`; a question about the repository as it stands → `codebase-analyst`, which reads the workspace but does not modify it; a question answerable only from outside the repository — third-party documentation, API references, the open web → `librarian`, which likewise does not modify the workspace; design → `architect`; producing an ordered plan, including commissioning whatever research that plan needs → `planner`; implementation → `coding-agent`; testing → `tester`; documentation → `docs-writer`; behavior-preserving restructuring → `refactorer`; final acceptance → `verifier`. Implementation of any one todo item MUST be assigned to at most one child at a time. Reporting the run as successful is conditioned on the acceptance role having signed off. (Whether that sign-off is enforced by the run or is an instruction the coordinator is expected to honour, and the granularity at which exclusive implementation ownership is measured, are open; see Open Questions.)
- **REQ-ORCH-029** — Constraints on the coordinator MUST hold no matter what playbook cell, override, or instruction text is in force, and each is externally checkable from the run's own records. While the entry role acts as coordinator: it makes no file-modifying tool call and emits no plan, code, or diff of its own authorship; every work item it takes on reaches a specialist through a `delegate` call; work spanning more than one step is accompanied by a todo list it keeps current; no two implementation delegations for the same todo item are outstanding at once; it does not report the run successful while a todo item is non-terminal or while a todo item's recorded state disagrees with what happened; and it issues no delegation whose child would sit deeper than delegation depth 3 (REQ-ORCH-046).
- **REQ-ORCH-030** — After three consecutive failed attempts at the same task, the coordinator MUST NOT delegate a fourth attempt at that task. Its next action for the task MUST instead be either a diagnosis delegation — to `codebase-analyst` when the unknown lies in the repository, to `librarian` when the unknown lies in a third-party dependency — carrying the accumulated failure context from those attempts, or a failure report to the user setting out what was attempted and how each attempt failed. (What counts as one failed attempt, whether this rule is enforced by the run or instructed, and the shape of the failure report, are open; see Open Questions.)

### 6. Delegation Contract

- **REQ-ORCH-031** — Delegation MUST be an explicit tool call (tool name `delegate`) with required parameters `persona` (target role), `task_name`, and `task`, plus optional `depends_on: list[task_id]`. The task text is instructed to use labeled sections: TASK, EXPECTED OUTCOME, MUST DO, MUST NOT DO, CONTEXT.
- **REQ-ORCH-032** — The delegation call MUST additionally accept: `inherited_context: list[task_id]` (forwards already-completed sibling reports as context without creating an ordering dependency; only succeeded tasks contribute; unknown or failed ids are silently skipped); `category` (`quick|deep|planning|research`, a routing hint, explicitly not a model name); `session_id` (reuse a prior delegation's session for retries/follow-ups); `run_in_background: bool` defaulting to **true**; `attach_artifacts: list` of artifact ids/slugs (full artifact bodies injected at the head of the payload; unknown ids reported as warnings; oversized sets partially elided); and `suppress_auto_context: bool` (turns off the automatically supplied index of earlier sibling artifacts; ORed with the equivalent per-role setting).
- **REQ-ORCH-033** — Each delegation MUST return an observation carrying the canonical task name, a status, a message, and (when queued) the task id. Statuses are: `queued`; `waiting_on_dependencies` with a message naming the blocking tasks; `waiting_on_model_slot` with a message naming the model key and its active/max counts; `rejected` with an error flag and reason. The model-visible rendering is of the form `Task '<canonical>': <status> — <message>` followed by a `task_id: <id>` line.
- **REQ-ORCH-034** — Role aliases MUST be resolved before spawn: `coder` → `coding-agent`, and `playwright` → `ui-verifier`. An alias resolves only when its target role actually exists in the current configuration. An unknown role MUST be rejected with a message listing the known role names and the supported aliases rendered as `<alias>-><target>`; when an alias was resolved, the observation message states which alias resolved to which role.
- **REQ-ORCH-035** — At spawn, a child's payload MUST be composed in this order: (1) a workspace-root block giving the resolved workspace path and stating that any other absolute path appearing in the task text is stale; (2) for the acceptance role only, the verification-evidence block of REQ-ORCH-129; (3) the index of earlier sibling artifacts, unless suppressed per REQ-ORCH-032; (4) the full bodies of the artifacts named by `attach_artifacts`; (5) the inherited-context block built from `inherited_context`; (6) the task text the caller supplied. A child spawned with dependencies additionally receives the prior-agent-context block of REQ-ORCH-047 at the moment it becomes ready; that block is placed ahead of (1) and is therefore the first content the child sees.
- **REQ-ORCH-036** — Every spawned child MUST be assigned a task id matching `^bg_[0-9a-f]{8}$`, unique within the session. `depends_on` entries are task ids and are normalized to canonical names at spawn; an unknown task id in `depends_on` MUST be rejected with an error naming it.
- **REQ-ORCH-037** — A successful delegation MUST end the parent's turn, whether the delegation was foreground or background: the delegation observation of REQ-ORCH-033 is the last content the parent emits, and the parent emits nothing further until it is resumed under Section 11. No separate suspend step exists for a caller to invoke, and none is observable in the transcript.
- **REQ-ORCH-038** — The following delegation attempts MUST be rejected with an error observation and no spawn: unknown role; depth limit exceeded ("Max depth N exceeded"); total-children limit reached ("Max total children N exceeded"); active-children limit reached ("Max active children N exceeded"); unknown dependency; dependency cycle ("Dependency cycle detected"); a dependency owned by a different parent (the rejection names both parents); a malformed inherited-context entry (e.g. empty string).
- **REQ-ORCH-039** — A delegation to the acceptance role MUST be refused, with no child spawned, while the most recent verification evidence available for the task in hand records at least one blocking check as `failed`. The refusal reason MUST name those checks, state that their output is already captured, state that the task is already set to be attempted again, and direct that acceptance be delegated only once those checks pass. Where no verification evidence exists for the task at all, the delegation MUST be allowed and proceeds on the empty-evidence path of REQ-ORCH-129. Checks recorded `timeout`, `skipped`, or `invalid` MUST NOT by themselves cause a refusal; they are disclosed to the acceptance role per REQ-ORCH-129. (The asymmetry between this rule and the gate semantics of REQ-ORCH-116 is open; see Open Questions.)

### 7. Child Task State Machine

- **REQ-ORCH-040** — Child task states MUST be exactly: `queued`, `starting`, `running`, `waiting_on_dependencies`, `waiting_on_model_slot`, `succeeded`, `failed`, `cancelled`, `blocked`. The terminal set is {succeeded, failed, cancelled, blocked}.
- **REQ-ORCH-041** — Valid transitions MUST be exactly: queued → {starting, running, waiting_on_dependencies, waiting_on_model_slot, cancelled, blocked}; waiting_on_dependencies → {queued, waiting_on_model_slot, blocked, cancelled}; waiting_on_model_slot → {queued, blocked, cancelled}; starting → {running, failed, cancelled, blocked}; running → {succeeded, failed, cancelled, blocked}. An invalid transition MUST raise an error of the form "Invalid transition: X → Y". Entering a terminal state stamps a completion timestamp in UTC. `cancelled` MUST be reachable from every non-terminal state so that cleanup sweeps can never fail partway.
- **REQ-ORCH-042** — `waiting_on_model_slot` MUST NOT count toward the active-children count (the child is idle, consuming no model connection), so children queued behind a model never trip the active limit. `starting` and `running` both hold a model slot.
- **REQ-ORCH-043** — The persisted per-child record MUST include at least: given and canonical names, role, task payload, dependencies, inherited context, state, spawn and completion timestamps, parent agent identity, depth, conversation identity, category, session id, background flag, task id, launch generation, produced/received artifact ids, resolved model key, the actually granted native tool set, the granted MCP tools per server, and the child's live serialized todo state.

### 8. Child Naming, Limits, and Dependency Graph

- **REQ-ORCH-044** — Child task names MUST be scoped per parent. A reused name is deterministically renamed `<name>_<n>`, where n is the smallest positive integer, counting up from 1, not already in use for that name, and the canonical name is used everywhere the task is referenced (transcripts, dependency resolution, artifacts).
- **REQ-ORCH-045** — Canonicalization of a task name MUST apply these steps in order: collapse each run of whitespace; replace every character outside `[A-Za-z0-9_.-]` with `-`; strip leading and trailing `-`, `.`, and `_`; and, when nothing remains, use `task`. The result MUST be at most 80 characters. A name that would exceed 80 characters MUST be shortened to 80 characters or fewer and MUST end in an 8-character lowercase hexadecimal suffix derived from the full name as it stood before shortening, so that the same long name always canonicalizes to the same string and two different long names never canonicalize to the same string. (The digest function and the separator preceding the suffix are not fixed by this document; see Open Questions.)
- **REQ-ORCH-046** — Spawn validation MUST be applied in this order, and the first check that fails MUST reject the delegation with the error observation of REQ-ORCH-038, creating no child record and issuing no task id: (1) depth — the entry role is at depth 0, a child of an agent at depth d is at depth d+1, and the spawn is rejected when the child's depth would exceed the configured maximum (default 3); (2) total children — the number of children already created in this iteration's ledger has reached the configured maximum (default 20); (3) active children — the number of children in `starting` or `running` has reached the configured maximum (default 6); (4) every id in `depends_on` names an existing child of the same parent; (5) the new dependency edges, added to the edges already present, close no cycle. A delegation that passes validation creates a child whose initial state is `waiting_on_dependencies` when `depends_on` was non-empty and `queued` otherwise; a child whose model key is already at its concurrency cap is reported as `waiting_on_model_slot` per REQ-ORCH-050.
- **REQ-ORCH-047** — A dependent child MUST start only after ALL of its dependencies have both reached `succeeded` AND had their mandatory report artifact stored; a dependency without a stored report does not count as succeeded. When a dependent becomes ready, the framework MUST prepend exactly once (never re-prefixed on later state hops such as promotion out of the model-slot queue) a prior-agent-context block flagged as authoritative — directing the reader to rely on the supplied findings rather than repeating that investigation — containing each dependency's final response (else last response) in per-dependency sections identifying name, role, and status. If reports are missing, no context block is injected.
- **REQ-ORCH-048** — When a child reaches `failed` or `cancelled`, every child depending on it that is in `queued`, `waiting_on_dependencies`, or `waiting_on_model_slot` MUST transition to `blocked`, cascading transitively to further dependents. Blocked children are never started automatically. Terminal-state callbacks MUST fire for cascaded records exactly as for directly completed ones.
- **REQ-ORCH-049** — A child MUST be started at most once, however many scheduling passes for the same parent are in flight at the same time. Over the whole run, the number of `child_start` timeline events recorded for any one task id MUST be exactly one for a child that started and zero for one that never did. An attempt to start a child that has already been started, or that has since moved on, MUST be suppressed rather than carried out, and MUST be recorded as a `child_launch_suppressed` timeline event together with a `stale_child_launch_claim` issue naming the child's canonical name and task id.

### 9. Per-Model Concurrency

- **REQ-ORCH-050** — A per-model concurrency cap MUST limit how many children bound to the same model key may be in `starting` or `running` at one time, where a model key is the identifier under which a model is configured (REQ-ORCH-145). A cap the user set for a model always applies; where the user set none, the default follows the provider that model is configured against — 3 for provider `deepseek`, 2 for provider `claude-code`, unlimited for every other provider. Exceeding the cap MUST NOT reject the delegation: the child is created, reported with status `waiting_on_model_slot` per REQ-ORCH-033, and held until a slot frees. Held children MUST be released in the order they were held, one returning to `queued` each time a child bound to the same model key reaches a terminal state. A held child that has itself reached a terminal state MUST be dropped rather than released. Where no cap applies to a model, no child bound to it is ever placed in `waiting_on_model_slot` on that account.

### 10. Terminal Marking, Sweeps, and Orphans

- **REQ-ORCH-051** — Marking a child terminal MUST: store its report retrievable by both canonical name and task id; enqueue a completion notification for background-flagged children (carrying task id, canonical name, description, state, duration since spawn, count of still-running siblings, and produced artifact ids) while foreground children produce no notification; cascade blocking on failure/cancellation; and release the model slot. A child's result lives only for the duration of the session unless an explicit artifact write is performed, which is the only way a durable artifact-store record comes into being.
- **REQ-ORCH-052** — An idempotent finalize-incomplete sweep MUST close every non-terminal child record as `cancelled` through the normal terminal-marking path (so slots release, blocking cascades, and callbacks fire), re-checking per record because closing one can cascade-block another. Every exit path from an iteration — blocked delegation, plain re-queue, cancellation, crash — MUST leave both the record for the iteration itself and every child record it holds in a terminal state, so that a finished run never leaves behind a record that still reads as running.
- **REQ-ORCH-053** — On session continue, a run that has just acquired the session lock MUST settle every non-terminal child record read back from the previous run (e.g. after a killed host or hard cancel) to `cancelled` before its first iteration, so reattached sessions never show phantom running agents.
- **REQ-ORCH-054** — A newly-terminal query MUST return terminal children the parent has not yet observed and mark them observed; calling it again immediately returns nothing.

### 11. Parent Suspension, Resume, and Notifications

- **REQ-ORCH-055** — A parent MUST be resumed whenever at least one direct child reaches a terminal state the parent has not observed; multiple terminal events may batch into one resume. On resume the parent receives the newly-terminal children's structured reports, the current state of all its direct children, and scheduling metadata, and may then continue orchestrating, work locally, spawn more children, or end generation again.
- **REQ-ORCH-056** — After a parent is resumed, the run MUST keep scheduling on that parent's behalf until all three of the following hold at the same time, and MUST then leave the parent idle: the parent has no outstanding wait request; no completion notification for it is still undelivered; and every child of it that could be started has been started at least once. A parent whose remaining children are all waiting on dependencies that have not been met MUST NOT be resumed again on that account alone: a child that has already been attempted does not by itself cause a further resume, so a run can never alternate between starting and resuming indefinitely without some child changing state.
- **REQ-ORCH-057** — Foreground pass: spawn ready children, wait for a terminal event among the freshly spawned only (never the outer task), discard now-duplicate notifications, then resume the parent with a message stating child task updates are available, including per-child report blocks; when other children still run, guidance states how many are still running in the background; when none remain, guidance states all background tasks finished and encourages issuing the next batch of delegations in parallel before ending the turn.
- **REQ-ORCH-058** — Background pass: spawn ready background children, then resume the parent immediately with a message stating background tasks have started, instructing it to continue productive work and to use the waiting tool only when specific results are needed, plus an active-background-tasks list of the form `- <canonical> \`<task_id>\`: <name>`.
- **REQ-ORCH-059** — For each background child that completed, a completion notification MUST be injected into the parent conversation without triggering generation (fire-and-forget), containing: a background-task-completed banner; the task id; the description (canonical name plus given name); the duration in seconds; published artifacts when any; when others still run, the remaining count with an explicit promise of notification when all complete and an instruction not to poll but continue productive work, plus a usage hint for the output-retrieval tool (summary and verbatim forms); otherwise a statement that all background tasks have completed. Open-todo reminder lines are appended. After injection, the parent is resumed with an empty message. This delivery MUST work even when the child completes while the parent is mid-turn (the parent is interrupted for injection without force-closing its conversation), and a completion delivered via a wait or foreground resume MUST have its matching notification discarded so it is announced exactly once.
- **REQ-ORCH-060** — Each per-child report block in a resume message MUST show the canonical name, role, and status, optional artifact descriptions, then the result text (final response, else last response, else key findings) capped at 4000 characters with a truncation marker stating how many characters were omitted.

### 12. Result Retrieval and Voluntary Waiting

- **REQ-ORCH-061** — A `background_output` tool MUST retrieve a completed task's report by task id, returning: `ok` with the report text; `still_running` with a message naming the id and its current state; or `not_found`. Lookups are parent-scoped: a task id belonging to a different parent also returns `not_found`. A `detail_level` of `summary` returns agent/status/summary/artifacts/key findings/last reply; `verbatim` additionally returns the exact last reply, the union of touched files (edited, created, artifact paths), and highlighted paths with snippets.
- **REQ-ORCH-062** — A `wait_for_tasks` tool MUST suspend the calling parent until every named task id has reached a terminal state; called with an empty list, it waits for every active background direct child of that parent. When nothing remains to wait for, it MUST return without suspending, with a message of the form "All N requested tasks already complete.", where N is the number of ids requested and N = 0 is a valid case. It MUST return an error and not suspend when the parent names its own task id, or names a task that is not one of its direct children — that error states that waits are limited to direct child tasks. A parent has at most one wait outstanding, and an outstanding wait does not survive the end of the parent's conversation. This document places no maximum duration on a wait; it ends when the waited-for set is terminal or the run is cancelled. (Whether a wait should be bounded is open; see Open Questions.)
- **REQ-ORCH-063** — Wait resolution: the drain spawns ready children, collects reports for the waited set, and resumes the parent with a message stating the waited-for background tasks completed, followed by the results, once the waited set is fully covered. A transient window where a task's execution handle has vanished but its record still reads running MUST NOT be treated as completion. Matching notifications are discarded so no completion is double-announced.
- **REQ-ORCH-064** — Time spent blocked in a voluntary wait MUST NOT register as in-flight tool activity for graceful-pause purposes, so a parent legitimately blocked for minutes is not force-closed.
- **REQ-ORCH-065** — Any role holding the `delegate` tool MUST be able to delegate in its turn, subject to REQ-ORCH-046. Every delegation made during one iteration, at any depth, MUST count against that iteration's own set of child records and against the same limits and scheduling as delegations made by the entry role; the counters do not restart at a deeper level, and one ledger covers the whole iteration (REQ-ORCH-072 creates one per iteration). A child MUST see only what its payload gives it (REQ-ORCH-035) and never its parent's conversation. Every child MUST run in the resolved workspace root; a delegation whose child would run in any other directory MUST fail with an error naming both the expected workspace root and the directory that differed.

### 13. Iteration Loop and Stop Conditions

- **REQ-ORCH-066** — The iteration-loop mode MUST be first-class for long-running autonomous work: usable by the entry role for the whole run or by a delegated child for a bounded subproblem, and functional in both attached (interactive) and background sessions.
- **REQ-ORCH-067** — Each iteration MUST: read the plan/progress state; select the next incomplete anchored task — the first pending task scanning phases in insertion order (so phase order "main" → queued-prompt phases → remediation phases is the priority order); do work for that one task only; verify; update progress; and hand the next iteration compacted state (todo, artifact set, progress, reports) rather than raw transcript. Iteration boundaries MUST be visible in session state and transcript via iteration-start and iteration-end events carrying iteration number, task id/name, outcome, and summary.
- **REQ-ORCH-068** — Before an iteration closes it MUST have updated the todo and progress records, resolved the task it selected into one of three outcomes (marked complete, given up on, or returned to the pending queue), and emitted a report artifact. On verification failure there is no silent roll-over into a second task: the iteration ends with the current task still anchored, set back to pending with a continuation payload.
- **REQ-ORCH-069** — Stop conditions MUST be evaluated between iterations (never mid-iteration; a long iteration may therefore overshoot the time limit), first match wins: (1) all non-abandoned tasks completed → stop reason "all tasks completed"; (2) completed iteration count ≥ the iteration limit → "iteration limit reached"; (3) elapsed wall time since run start ≥ the optional time limit → "time limit reached"; (4) no pending task → "no pending tasks". Loop-level stops: user stop → "stopped by user"; cancellation → "interrupted by user"; child escalation → "agent session aborted"; message-limit cancel → "user cancelled at message limit". A stop reason arrived at here is not necessarily final: REQ-ORCH-071 and REQ-ORCH-079 may extend the run before it ends, in which case the loop continues and stop conditions are evaluated again at the next boundary.
- **REQ-ORCH-070** — The iteration limit MUST default to 20; the time limit is optional with no default.
- **REQ-ORCH-071** — Queued prompts extend a finishing run only when the stop reason would be "all tasks completed": they are appended as a new phase named "Queued Prompts" with tasks named "Queued Prompt: <first 8 characters of the prompt id>", marked triggered, the total task count incremented, and the loop continues. The queued-prompt read MUST be scoped by session id so hosts running parallel loops do not cross-trigger. A queued prompt arriving under any other stop reason (e.g. iteration limit) MUST NOT extend the run.
- **REQ-ORCH-072** — Iteration mechanics: the selected task flips to in-progress; a fresh per-iteration child ledger is created under the budget-clamped policy; the root child is spawned with the entry role and the task's execution payload and transitioned to running; the root agent is given its own child identity (canonical name and task id) so output-retrieval and waiting lookups resolve for it.
- **REQ-ORCH-073** — An iteration that raises an unhandled error MUST be caught: the task is marked abandoned, the abandoned count incremented, and the loop continues with the next task.
- **REQ-ORCH-074** — Outcome dispatch on the iteration's (possibly rewritten) report status: `succeeded` → task completed; `failed`/`cancelled` → in-flight children cancelled, task abandoned, and if the report carries an escalation signal the run ends with stop reason "agent session aborted"; `blocked` → task reverted to pending, in-flight children NOT cancelled (the next iteration collects their results), and the iteration's own record recorded as succeeded rather than blocked, so that a host status display does not present a deliberate deferral as a failure; any other status (e.g. `partial`) → task reverted to pending.
- **REQ-ORCH-075** — Incomplete-todo re-queue: when a report says succeeded but the agent's own todo list still holds pending/in-progress items after correction retries are exhausted, the same top-level task MUST be re-queued (not abandoned) with a continuation payload built from the stripped base payload plus a continuation marker block stating that success was declared with N todo items incomplete (naming up to the first 5) and instructing the agent to continue from the todo list and not end its turn until every remaining item is complete. Still-running background children MUST be enumerated in the payload with an instruction not to re-delegate them.
- **REQ-ORCH-076** — Continuation and verification-failure marker blocks MUST be stripped from a task payload before a new one is appended, so that such markers do not pile up across repeated re-queues of the same task.
- **REQ-ORCH-077** — Consecutive-retry limit per task: consecutive pending-outcome iterations per task id are counted; when the count reaches the iteration limit (deliberately the same value as the global cap), the task MUST be abandoned to break the loop. The counter resets on any forward progress.
- **REQ-ORCH-078** — Todo-correction retries MUST reuse the validation-retry setting (default 0): with 0, an incomplete-todo success re-queues without an in-conversation retry; with a positive value, a correction message is sent into the same conversation up to that many times first.
- **REQ-ORCH-079** — Relentless mode (default off) MUST apply only where the run would otherwise stop for "all tasks completed" or "no pending tasks"; it MUST NOT apply to "stopped by user", "interrupted by user", "user cancelled at message limit", "iteration limit reached", "time limit reached", or "agent session aborted". Where it applies, a model call using the summarizer's model compares the summaries of the run's completed iterations against the original user request captured at run start (REQ-ORCH-003). Where the call reports the request fully met, or where the run has no completed iteration summaries to compare, the run stops with the stop reason it already had. Otherwise a phase named "Relentless Remediation <n>" MUST be appended — n is 1 for the first such phase in the run and increases by one for each further one — holding exactly one task whose payload carries the original request, the finding, and the gaps still outstanding, and the loop continues. At most the configured maximum number of cycles (default 3) of remediation phases MAY be appended in one run; once that many exist the run stops normally. (The audit call's timeout and its behavior on failure are not fixed by this document; see Open Questions.)
- **REQ-ORCH-080** — On stop with active background children, the loop MUST drain before stopping: wait up to the shutdown-drain timeout (default 120 s; 0 disables) for still-running background children without cancelling them; children still running afterwards are logged, a drain-timeout warning issue is recorded, and teardown then cancels them.
- **REQ-ORCH-081** — Exactly one session-start event (task, workspace, role, permission mode, sandboxed flag, iteration limit) and exactly one session-end event (status, stop reason, iterations completed, duration) MUST be emitted per run, with every exit path funnelling through a single final handler. A host that publishes richer versions MUST be able to disable loop-level publication so consumers never see doubles; session lifecycle observer hooks fire either way.
- **REQ-ORCH-082** — The run-progress summary MUST be derived by evaluating these rules in order and taking the first that matches: (1) stop reason "stopped by user" → status "paused", message "Run paused: interrupted by user.", severity warning; (2) no abandoned tasks → status "completed", message "Run completed.", severity information; (3) no completed tasks → status "failed", message "Run failed: <latest failure detail | N task(s) abandoned.>", severity error; (4) otherwise → status "completed", message "Run completed with failures: X completed, Y abandoned.", severity warning. This summary is a host-facing status line with its own vocabulary {paused, completed, failed}; it does NOT determine the terminal run result or the process exit code, which follow REQ-ORCH-083 and use a different vocabulary. (A run with neither completed nor abandoned tasks matches rule 2; see Open Questions.)
- **REQ-ORCH-083** — The terminal run result MUST use statuses {completed, failed, max_iterations, interrupted, error} with process exit codes completed = 0, failed = 1, error = 1, max_iterations = 2, interrupted = 130. Stop reasons {"stopped by user", "interrupted by user", "user cancelled at message limit"} map to interrupted; "agent session aborted" maps to failed regardless of completions; "iteration limit reached" maps to max_iterations. When no stop reason applies, the mapping falls back on the session execution status (completed → completed, failed → failed, paused states → interrupted, any non-terminal status → error). Result construction MUST never raise.

### 14. Message-Limit Soft Pause

- **REQ-ORCH-084** — A message limit MUST be configurable as a positive integer or null, defaulting to null (disabled). It is independent of and coexists with the iteration limit (the hard ceiling); whichever fires first governs. One "message" equals one completed iteration.
- **REQ-ORCH-085** — Each completed iteration MUST increase the run's message counter by one, and the counter MUST survive a host restart by forming part of the persisted session snapshot; a new session begins at zero. When the counter reaches the message limit in force, the pause MUST take effect at an iteration boundary: no further iteration begins, and while the run is paused the loop issues no model request and spawns no child. Background children left running by an earlier iteration under REQ-ORCH-074 are unaffected by the pause and continue. The host MUST be told the run has paused, together with the current count and the limit in force.
- **REQ-ORCH-086** — Pause resolution MUST offer exactly three actions: continue (resume; the counter keeps accumulating), double (the limit is doubled for this session only, then resume), and cancel (stop with stop reason "user cancelled at message limit"). The interactive host presents a modal showing the count, the limit, and estimated token usage, with keys `c`/Enter = Continue, `d` = Double, `x`/Escape = Cancel. Resolving "double" when the limit is null leaves it null without error.
- **REQ-ORCH-087** — In background mode the run MUST auto-pause at the same boundary, write a signal file `<session_dir>/.message_limit_paused`, set the session execution status to `paused_message_limit`, and never auto-continue. Reattaching immediately shows the confirmation dialog (and resolving it removes the signal file); a command-palette entry for continuing the paused session is active only in that state.

### 15. Child Execution Safeguards

- **REQ-ORCH-088** — A hard per-child timeout (default 1200 s) MUST bound each child's execution. On expiry: gracefully pause the child; then, if the role has a configured fallback model not yet attempted for this child, retry once on it; otherwise record the child failed with a timeout issue and a report of the form "Child timed out after <N>s" carrying the last/final response extracted from the transcript.
- **REQ-ORCH-089** — A stall watchdog MUST provide visibility only and never cancel work. Stall threshold = per-role override else the default 90 s; polling cadence = max(1, min(threshold/6, 5)) seconds; a warning ("child appears stalled: no model event or token for N seconds") is emitted on stall entry and at most every max(threshold, 30) seconds thereafter; a stall diagnostics issue records active tools, the last 5 tool calls, and the last model event type; a stall callback fires each poll with stalled/recovered so a UI badge can update. When active tool calls exist, the condition is reported at informational level as waiting on N active tool calls instead of as a stall.
- **REQ-ORCH-090** — An unresponsive-model fallback (default 120 s, minimum 30) MUST apply only before ANY model event has been received for the child and only when the threshold is below the child timeout. On expiry the conversation is gracefully paused (force-closed if stuck) and the role's fallback model is tried once per child by rebuilding the agent and transparently re-running — the child keeps running rather than being killed. Without a configured fallback, the child simply continues waiting under the full child timeout. A timeline event and an issue record the occurrence.
- **REQ-ORCH-091** — Rate-limit and quota handling MUST distinguish generic rate-limit errors (HTTP 429 / "Too Many Requests" / rate-limit phrasing) from provider quota exhaustion (structured insufficient-quota codes) and proceed in order: (a) models known exhausted are remembered session-wide and excluded from candidates; (b) at most one same-tier automatic model fallback per child, choosing a candidate of the failing model's tier (excluding exhausted and already-attempted pairs) and transparently re-running; (c) otherwise a suspended wait: wait time = the provider's Retry-After value when present (minimum 1 s), else exponential local backoff 60·2^(attempt−1) seconds capped at 300 s; generic rate limits auto-resume after the wait, but provider-exhausted models NEVER auto-resume (they wait indefinitely for a user decision); (d) the user may resolve a wait with keep-waiting, cancel-run, or change-model; a manual model change rebuilds the agent, re-runs, and persists the override in session state for the rest of the session.
- **REQ-ORCH-092** — A failed model call MUST be retried according to the class of the failure: a transient failure up to the configured transient-retry count (default 1), a validation failure up to the configured validation-retry count (default 0). The delay before retry attempt n MUST be min(2.0, n) seconds. A transient failure MUST be recorded as a `transient_llm_error` issue. When the applicable retry budget is exhausted, or the failure falls into neither class and no other recovery in this section applies to it, the child MUST be marked `failed` with a report of the form "Child failed: <formatted error>". (Which provider failures count as transient and which as validation is not fixed by this document; see Open Questions.)
- **REQ-ORCH-093** — A model call rejected because the conversation no longer fits the model's context MUST be recovered by condensing the conversation and retrying the call, at most twice for one call; where the condensation itself fails, the original rejection MUST be surfaced unchanged and the call fails. The same recovery MUST apply when a parent is resumed, and each parent-resume attempt MUST be bounded by the child timeout of REQ-ORCH-088. The occurrence MUST be recorded as an `llm_bad_request` issue for a child's own call and as a `parent_resume_bad_request` issue for a parent resume.
- **REQ-ORCH-094** — Pending user steering prompts for a child MUST be injected into the live conversation as clearly marked steering messages (from the watchdog loop and between execution passes), marked as delivered, and MUST reset the loop supervisor's consecutive-activation counter (steering counts as a new user instruction).
- **REQ-ORCH-095** — When a child's conversation run ends, what the child did MUST be assessed into exactly one of six categories: work was carried out; the request was answered; only bookkeeping took place; a tool call was attempted but malformed; text was produced and nothing was acted on; nothing happened at all. Only the first is accepted without further prompting. For each of the other five the child MAY be re-prompted once, and only once, in the same conversation — with one exception: on an answer-only route (REQ-ORCH-015) the answered category is accepted as success immediately. Where that single re-prompt has been used and the run still ends in the answered or text-only category, the child MAY be marked succeeded as a text-only completion. Any other non-work ending after the re-prompt MUST mark the child `failed` and MUST record an `incomplete_execution` issue naming the category assessed. (The exact category identifiers that appear in that issue are not fixed by this document; see Open Questions.)
- **REQ-ORCH-096** — Where the child runtime reports that it cannot make progress, the child MUST NOT be failed on that report alone: it receives one corrective message in its existing conversation and is resumed. Repeated such reports are governed by the same consecutive-activation rule as REQ-ORCH-102 — the third intervention with no intervening user instruction escalates the child per REQ-ORCH-106. A runtime error status, as distinct from a stuck report, MUST fail the child at once with no corrective attempt, and the terminal failure report MUST be built from what the transcript already holds. (How exhausted stuck-recovery is recorded in the issue vocabulary is not fixed by this document; see Open Questions.)
- **REQ-ORCH-097** — After each successful execution pass, per-child tool-call counters MUST be accumulated (feeding UI counters and the verifier's change detection), and cumulative token/cost snapshots MUST be replaced, not summed (summing cumulative totals would double-count).
- **REQ-ORCH-098** — Whatever terminal state a child reaches, and whether or not its execution raised, that child MUST be fully torn down: its conversation is closed, a `child_conversation_closed` timeline event is emitted for it, any wait or pending user prompt registered against it is discarded rather than left outstanding, and it no longer counts as an active child or against its model's concurrency cap. Teardown MUST NOT cost the run its responsiveness: an interrupt requested while a child is being torn down MUST still take effect and produce the outcome of REQ-ORCH-136.

### 16. Loop Supervision (Hidden)

- **REQ-ORCH-099** — Loop supervision MUST be invisible: the supervisor is not a role, is never registered or listed, has no observable side effect when no loop is detected, and its corrective messages read as natural user instructions that never mention monitoring, detection, or injection.
- **REQ-ORCH-100** — Supervisor defaults MUST be: classifier model `gpt-4o-mini`; classifier timeout 20.0 s; activation mode `independent` (alternative: `weighted`); tool-call threshold 60; message-count threshold 60; weights 0.6 (tools) / 0.4 (messages) with target score 1.0; recent-event window 24; transcript excerpt cap 8000 characters; repetition threshold 4; cycle threshold 3; enabled true. (See Open Questions for the historical divergence on thresholds and latency budget.)
- **REQ-ORCH-101** — For each observed child event, triggers MUST be evaluated in this order, and the first that fires wins: (1) repetition — the same action observed 4 times in a row fires "repeated action"; (2) cycles — a repeating sequence of 2 to 4 distinct actions, observed 3 times over, fires "repeated cycle"; (3) raw counts — in `weighted` mode a score of (tool calls / tool threshold)·0.6 + (messages / message threshold)·0.4 reaching 1.0 fires, and in `independent` mode either count reaching its own threshold fires on its own. Two actions count as the same action only when their tool name and the whole of their arguments are identical: no part of the argument content may be disregarded when comparing, so two long edits differing only near their end MUST be treated as different actions. Only the most recent events, up to the configured event window (default 24), are considered.
- **REQ-ORCH-102** — On trigger, the supervisor MUST snapshot the pending activation, increment the consecutive-activation counter, and pause the child. If the counter exceeds 2 (the third activation without an intervening user instruction), it MUST escalate regardless of classification, with an escalation signal carrying session id, activation count, and a repeated-loop reason. Otherwise an LLM classifier judges whether a loop exists over the recent transcript tail (bounded by the event window and character cap).
- **REQ-ORCH-103** — The classifier contract is JSON `{loop_detected: bool, reason, corrective_message}` where the corrective message is at most 90 words, in natural user voice, and redirects to a different concrete approach or asks for a viability assessment, drawing on the transcript (dynamic, never templated). `loop_detected = false` MUST result in an invisible no-op resume.
- **REQ-ORCH-104** — Classifier failure or timeout MUST fall back on evidence: for repetition/cycle triggers, always declare a loop with a deterministic "pause and reassess" message naming the circled tool and a path anchor; for raw-count triggers, declare a loop only from repeated identical assistant messages (last 3 normalized-equal) or ≥ 4 consecutive same-tool calls — never from counts alone; for stuck-mode triggers, ALWAYS recover with a deterministic corrective message, overriding even a classifier that declined recovery.
- **REQ-ORCH-105** — After every activation cycle, regardless of outcome, tool/message counters and fingerprints MUST reset to zero. The consecutive-activation counter resets only on a new user instruction — a real user message, injected steering, or a todo-correction message all count. Supervisor state MUST be strictly session-scoped, never leaking across sessions.
- **REQ-ORCH-106** — Supervisor escalation MUST surface as: the child transitioned to failed; an escalation error issue ("child aborted after repeated activations"); a report carrying the escalation signal; and, at loop level, a session abort ending the run with stop reason "agent session aborted".
- **REQ-ORCH-107** — Disabling supervision via configuration MUST construct no supervisor and no model client; the runtime distinguishes "intentionally disabled" from "not yet built" and tolerates the absence; the setting round-trips through configuration files; configurations without the field deserialize as enabled; a host-level toggle propagates into the run configuration.

### 17. Child Report Artifacts and Summarization

- **REQ-ORCH-108** — Every child reaching a terminal state MUST produce a machine-readable report artifact before its parent resumes. The report is produced by a low-cost summarizing pass whose instructions are narrow enough that it can only condense what already happened and can never carry the task forward. Parents consume the report in place of replaying raw transcript, and a dependency is treated as having succeeded only once its report has been stored.
- **REQ-ORCH-109** — The report schema is defined in Data & Formats. Runner-owned fields — verification results, completion-gate decision, repair record, gate state, requirement-coverage evidence, and scope-drift findings — MUST be structurally stripped from any model-produced payload before validation, so that a summarizing model can neither write nor overwrite deterministically produced evidence, cannot assert that its own work cleared the gate, cannot invent repair attempts, and cannot conceal files it failed to account for. This enforcement is structural, not dependent on prompt compliance.
- **REQ-ORCH-110** — The report-producing pass MUST be bounded and MUST always yield a report. The transcript it is given is capped at 12000 characters in total and 2000 characters for any one event. At most two attempts are made to obtain a well-formed report, the second being told what was wrong with the first. If the second attempt is also unusable, or the pass exceeds the summary timeout (default 120 s), a report MUST still be produced without any further model call: it carries an error entry of type "summary_failure", and its summary is taken from the first 220 characters of the child's final message or, where there is none, from the tools the child used. In every report, the agent name and role MUST equal the values the run holds for that child, whatever the summarizing pass produced. The final-response field MUST be populated only where the child's last assistant message was not followed by further tool activity; otherwise that text appears as the last response instead. Key findings MUST be rendered as bullet text.
- **REQ-ORCH-111** — A child MUST receive its report without any model call when all of the following hold: its role is `tester`; its terminal state is `succeeded`; its transcript holds at most 8 events; it made at least one tool call; and it produced a final response. The report is then built deterministically from the transcript, with status `succeeded` and a summary drawn from that final response. (The exact wording of that deterministic summary is not fixed by this document; see Open Questions.)
- **REQ-ORCH-112** — Report status maps to child terminal state as: succeeded → succeeded; partial → succeeded at the graph level (the loop, not the child ledger, decides what partial means for the task); failed → failed; cancelled → cancelled; blocked → blocked; anything else → failed. Note: because partial maps to a succeeded graph state, dependents unblock on a partial parent while the loop's task-level bookkeeping re-queues (see Open Questions).

### 18. Completion Classification and the Deterministic Completion Gate

- **REQ-ORCH-113** — With completion classification enabled (default true), every iteration whose report status is `succeeded` MUST be classified by exactly one small-model call into exactly one of `COMPLETE`, `NEEDS_ITERATION`, `UNCLEAR`. The call MUST be bounded by a 15 s timeout; a timeout, an error, or an answer outside those three values MUST yield `UNCLEAR`. `UNCLEAR` MUST have the same effect as `COMPLETE`, so a failed classification can never hold a run back. `NEEDS_ITERATION` MUST rewrite the report's status to `partial`, which re-queues the task under REQ-ORCH-074, and MUST set the report's message to the classifier's reason together with the original summary. Whichever of the three values results, a `completion_classified` timeline event MUST record it.
- **REQ-ORCH-114** — Classifier model resolution: small model → default summary model → the summarizer's model → skip classification entirely. Inputs are truncated (intent context to 2000 characters, summary to 1500) and open todo items are listed.
- **REQ-ORCH-115** — The completion classifier MUST be skipped for reports attributed to the coordinator role (a coordinator summary describes work handed to other roles and still in flight, which the classifier would routinely read as unfinished); the todo state machine and the child graph drive the outcome instead.
- **REQ-ORCH-116** — After the completion classifier, a deterministic completion gate MUST be applied, and its decision MUST override the classifier's verdict. The decision MUST be exactly one of `passed`, `gated`, `exempt`. Where a check suite executed: a check of severity `blocking` leaves the gate unsatisfied unless its status is exactly `passed`, so `failed`, `timeout`, and `skipped` — including a check the permission policy refused — all gate; the one exception is status `invalid`, which never gates. A check of severity `advisory` never gates, but a failing advisory check MUST be named in the recorded decision. Where no check suite executed, the decision MUST be `exempt`; the cases are an iteration that changed no file, a check-suite configuration that is explicitly empty, a workspace in which detection recognized nothing, and a verifier that was missing or failed (REQ-ORCH-131). Where no verification evidence exists at all, the decision MUST be `exempt` with a fixed reason string that is the same for every such decision. Where the gate's decision differs from the classifier's verdict, that verdict MUST be preserved on the decision record.
- **REQ-ORCH-117** — A gated succeeded report MUST be rewritten to status `partial` (reusing the existing re-queue semantics; no new status vocabulary), with the decision recorded on the report and emitted as a gate-decision timeline event (warning severity when gated). Gating is on by default; when configuration turns it off the checks still execute and their evidence is still reported, but the LLM verdict is what takes effect. An iteration in which no file changed is never subject to gating.
- **REQ-ORCH-118** — Bounded repair loop: a per-task-id repair budget (default 2; 0 = report failure without retrying) resets per run and is released when a task verifies clean (a later regression starts a fresh budget). The repair decision returns either retry — with a reason of the form "Verification failed (<checks>); starting repair attempt N of M." — or escalate, rewriting the report to failed with a message of the form "Verification still failing after M repair attempt(s): <checks>. Escalating instead of retrying." Escalation deliberately does NOT set the session-abort escalation signal, so one red check can never abort the whole session.
- **REQ-ORCH-119** — Repair context MUST render each failing blocking check — name, command, status, exit code, skip reason, full-log path, output excerpt — capped at 6000 characters total (head kept, with an omission marker stating how many characters were dropped), appended to the re-queued task payload after a verification-failure marker with any previous marker blocks stripped first. Timeline events record repair scheduling (warning) and repair escalation (error), and an optional observer hook is invoked on escalation.
- **REQ-ORCH-120** — Only a re-queue that the gate itself triggers MAY consume repair budget. A re-queue caused by unfinished todo items records the gate decision but leaves the budget untouched, so that two separate budgets never contend over one task. In all other respects a repair attempt is an ordinary iteration and counts toward both the message counter and the consecutive-same-task guard.

### 19. Deterministic Verification

- **REQ-ORCH-121** — The check-suite configuration MUST be three-valued: omitted = auto-detect; an explicit empty list = verification intentionally off (a visible decision); a non-empty list = explicit configuration that wins over detection with no fallback alternatives. The resolved suite records a source in {config, detected, explicit_empty, detection_empty}; an empty detection result MUST be surfaced as "nothing recognized", never as "intentionally off". Suite resolution never raises. The resolved suite and its source are persisted in the session snapshot and in the session's run-configuration record.
- **REQ-ORCH-122** — Auto-detection MUST consider only the project markers `pyproject.toml`, `package.json`, and `Makefile`, located at the workspace root and at subproject roots, and MUST synthesize at most one check for each of the semantic roles test, typecheck, and lint; checks of role `other` are not subject to that one-per-role limit. From `pyproject.toml`: declared pytest configuration, or the presence of a `tests/` directory, yields the check `pytest -q` (blocking, role test), narrowed to the test paths the project declares where it declares any; declared mypy configuration or a `mypy.ini` yields `mypy <declared scope, else .>` (blocking, role typecheck); declared ruff configuration or a `ruff.toml` yields `ruff check .` (advisory, role lint). From `package.json`, only the scripts named `test`, `typecheck`, and `lint` are interpreted, invoked as `npm test` for `test` and `npm run <script>` for the others, with `test` and `typecheck` blocking and `lint` advisory. From a `Makefile`, only the targets named `test`, `typecheck`, and `lint` are interpreted, invoked as `make <target>`, with the same severities; a target is recognized as a target name followed by `:` at the start of a line, and pattern rules and variable assignments are not targets. Build scripts and build targets MUST NOT be synthesized into checks. Detection MUST NOT fail the run: a marker that cannot be read or cannot be parsed contributes nothing. Every recognized marker MUST be recorded in the run-configuration record, including a marker whose implied check was dropped by the one-per-role limit. Where a role has more than one candidate, the order of preference is user-configured, then declared by the project (a script or a target), then synthesized; where the preferred command cannot be launched at all, the next candidate of the same role is used. A check detected in a subproject MUST have `:subdir` appended to its name and MUST carry a working directory expressed relative to the workspace root; an absolute working directory, or one resolving outside the workspace, MUST be rejected as a configuration error when the configuration is loaded. (How subproject roots are located, and what distinguishes a command that cannot be launched from one that exits non-zero, are not fixed by this document; see Open Questions.)
- **REQ-ORCH-123** — The check suite MUST run at most once per iteration, and only where that iteration changed at least one file in the workspace. The changed-file set MUST be the union of two independently gathered sources: the files observed to be modified by the iteration's tool calls, and the files the iteration's report declares as edited or created — a file present in only one of the two still counts. Where that union is empty, no check runs and a `verifier_run_skipped` timeline event records the reason. Checks MUST run one at a time, through the same command-execution path the run uses for any other command, which enforces each check's deadline itself rather than trusting the command to exit, applies the run's permission policy, and applies its sandboxing. A check whose command exits 0 while its output reports failing tests MUST be recorded `failed`, not `passed`. A check the permission policy refuses MUST be recorded `skipped`, naming the rule that refused it, and MUST NEVER be recorded `passed`. Check status MUST be one of `passed`, `failed`, `timeout`, `skipped`, `invalid`. The full output of every check MUST be written under `<session_dir>/evidence/verifier/`. (How failing-test output is recognized despite a zero exit code is not fixed by this document; see Open Questions.)
- **REQ-ORCH-124** — Verification budgets MUST be a per-check timeout (default 600 s) and a whole-suite timeout (default 900 s; null means unbounded). A check's effective timeout MUST be the smaller of its own timeout and the suite budget still remaining. A check for which no suite budget remained and which therefore never started MUST be recorded `skipped`; where that check is blocking, it leaves the completion gate unsatisfied on exactly the terms of REQ-ORCH-116, since it never answered its question. The calibration probe has its own timeout (default 30 s) that is not drawn from the suite budget.
- **REQ-ORCH-125** — The verification gate MUST be in exactly one of the lifecycle states `absent`, `pending`, `calibrated`, `stale`, and that state MUST be readable from `<workspace>/.rotaris/verifier.state.json`, a file the tooling writes and maintains and that users are not expected to hand-edit; the editable check suite stays in the user configuration. The state MUST become `stale` when the workspace's recognized project markers change — one added, one removed, or one whose content changed — and MUST NOT become stale for an ordinary source edit. A conventional test directory (`tests/`, per REQ-ORCH-122) MUST count by its presence alone, so adding or editing a test file does not make the state stale. A workspace with neither a recognized marker nor a test directory MUST be in state `absent`. A calibration probe MUST yield exactly one of `verified`, `empty`, `unavailable`, `undecidable`; `empty` is permitted only for a check of role test whose output positively reports that it collected nothing; a probe that was refused by policy, or whose result could not be read, MUST be `undecidable` and MUST leave the gate state unchanged. A `verifier_gate_calibrated` timeline event MUST be emitted when, and only when, at least one probe actually ran.
- **REQ-ORCH-126** — Gate authoring: on the transition from no recognized markers to markers present, a dedicated gate-authoring role (`gatekeeper`, reachable only through the gate-authoring path and never as an ordinary delegation target) MUST author the suite in a detached task beside the loop — never on the iteration's critical path — with the result binding the next iteration (by invalidating the cached suite). Authoring is on by default; when off, writes route to approval-gated proposals instead. The gate's current state travels on every child report, and a `pending` state means "code exists, nothing was verified". All writes go through a single write authority; the probe and gate-write capabilities are internal to the gate-authoring role and MUST NOT be grantable to any other role by configuration, with write authority evaluated at write time. Gate-weakening operations — dropping a role, lowering severity, emptying the suite — are outside all automatic authority and become improvement proposals deduplicated by content. An `invalid` check is repaired deterministically while the run continues — detection and probing are redone, preserving the check's role and severity — at most once for any given role within a session and without invoking a model. Timeline events record gate writes and skipped authoring.
- **REQ-ORCH-127** — Live verification visibility MUST include timeline events for suite start (size and source), each check start (index/total, command, deadline, severity), each check finish (status, exit code, duration, outcome kind, log path; warning severity on a blocking failure), and suite completion or skip — each mirrored by observer hooks for hosts.
- **REQ-ORCH-128** — While a check suite is running, the user MUST be able to skip the check currently executing; invoked at any other time the control MUST do nothing and report no error, so a host may offer it unconditionally. Skipping MUST interrupt the running command and every process it started, by delivering the terminal interrupt signal to the process group. A command that ignores that signal and keeps running MUST be terminated after a bounded grace period, and its terminal session torn down with it. A check the user skipped MUST be recorded with status `skipped` and never `failed`, and MUST NOT be counted or reported as a failing check; being blocking and unanswered, it still leaves the completion gate unsatisfied per REQ-ORCH-116. (The grace-period duration, and whether a user-initiated skip should be exempt from gating, are open; see Open Questions.)
- **REQ-ORCH-129** — Single execution authority: the acceptance role never re-runs the bound suite. The delegation layer injects into the acceptance role's payload a verification-evidence block whose heading states that the suite has already executed and must not be executed again, containing a per-check table (check, command, status, exit code, full-output path), an explicit list of checks that did not answer their question, and an instruction that any additionally needed command should name the missing role (feeding a gate-update proposal) rather than licensing a suite re-run. An empty evidence block is the fallback: the acceptance role runs commands itself and discloses that it did. The current iteration's evidence is published for host consumption.
- **REQ-ORCH-130** — Requirement-coverage evidence and scope-drift findings, when the workspace has a requirement store and files changed, MUST attach to the report as runner-owned fields that report but never gate, with a timeline event (warning severity when gaps or drift exist).
- **REQ-ORCH-131** — The loop MUST tolerate a missing or failed verifier entirely: no evidence → exempt gate; a broken verifier can never abort an iteration.

### 20. Cancellation and Shutdown

- **REQ-ORCH-132** — Cancelling a run MUST stop every descendant: the stop request sets the stop flag, releases any message-limit pause gate, cancels all pending question prompts and permission approvals (approvals fail safe as denied), gracefully pauses every active conversation (a forced stop additionally closes them), and cancels in-flight work thread-safely — a forced stop performs a second sweep for work created during the first.
- **REQ-ORCH-133** — Bulk child cancellation MUST cancel all active children, wait up to 5 s for them to settle, then mark any still-non-terminal record cancelled with a report stating it was cancelled during parent failure cleanup plus a force-cancelled warning issue. Single user-initiated cancellation MUST cancel the one child, wait up to 5 s, mark it cancelled with a report stating the user cancelled it, emit a user-cancelled timeline event, and return false for unknown or already-terminal children.
- **REQ-ORCH-134** — Graceful pause MUST honor a tool deadline (default 30 s, valid range 5–120): in-flight tool calls are awaited before force-closing. The pause performed to inject a parent notification MUST never force-close (the parent must keep its connections alive to be resumed). Pause and close operations MUST never block the run's event handling (a blocking close must not freeze interrupt handling).
- **REQ-ORCH-135** — An iteration cancelled mid-run MUST close its own record as cancelled with a report stating the run was cancelled before the agent finished, then sweep the ledger; bookkeeping errors during this cleanup are swallowed so they never replace the original exception. An iteration that raises closes its record as failed with a report stating it ended with an unhandled error.
- **REQ-ORCH-136** — A user interrupt (Ctrl+C-style) yields stop reason "interrupted by user", run status interrupted, and exit code 130. A child cancelled because the run concluded while it was in flight receives a diagnostic explaining exactly that.

### 21. Post-Run Improvement Pass

- **REQ-ORCH-137** — Once a task run has reached a terminal state, an improvement-collection pass MUST be handed to the host to run away from the run's own critical path, so that the run's duration, stop reason, terminal status, and exit code are the same whether that pass runs, is slow, or fails. It MUST be given a snapshot of the evidence it needs — the progress record, the todo state, the transcript events, the child reports, up to 5 improvement artifacts produced by earlier sessions in the same workspace, and the verification-gate evidence — and that snapshot MUST NOT change afterwards, whatever the run or any later run does to the originals. The pass MUST be skipped when the run is not a task run, when the collector is disabled (it is enabled by default), when the run has no session directory, or when the stop reason is "stopped by user", "interrupted by user", or "agent session aborted". It MUST be bounded by its own timeout (default 60 s), and any failure, that timeout included, MUST yield an empty improvement artifact rather than an error. (The run-type vocabulary that distinguishes a task run from other run types is not fixed by this document; see Open Questions.)

### 22. Observability

- **REQ-ORCH-138** — A host MUST be able to observe a run without taking on all of it: it may subscribe to any subset of the observation points this domain publishes — session start and end, iteration start and end, child lifecycle, todo state changes, verification events, repair escalation, message-limit pause, token metrics — and MUST NOT be required to supply the remainder. An exception raised by anything a host supplies MUST NOT change the run's outcome, stop the run, or be reported as a run failure: the run continues and reaches the same stop reason, terminal status, and exit code it would have reached with no host observing at all.
- **REQ-ORCH-139** — A run MUST record, in the session diagnostics, timeline events named only from the timeline-event vocabulary and issues named only from the issue-kind vocabulary set out in Data & Formats, and MUST NOT use any name outside those vocabularies for them. Those diagnostics form part of the session's durable record and MUST remain readable after the run has ended.
- **REQ-ORCH-140** — Every child's conversation transcript MUST form part of the run's own durable record, written under `<session_dir>/conversations/event_logs/` and not dependent on any host: a run observed by no host, and a run whose host observer raises, MUST both leave the same complete transcripts on disk.
- **REQ-ORCH-141** — Per-child tool-call timing MUST be recorded as diagnostics (call id, status, elapsed milliseconds, arguments/result, outcome kind, exit code), and replayed tool-call ids MUST be deduplicated.
- **REQ-ORCH-142** — The run's own usage aggregate is authoritative for per-iteration token/cost accounting; provider-reported totals are cumulative and MUST be replaced, never summed. Per-agent token, cost, and last-prompt-token snapshots feed the host UI.

### 23. Configuration Surface

- **REQ-ORCH-143** — All defaults in the Data & Formats configuration table MUST hold, and MUST be verified by configuration-default tests. Additional validation: duplicate check names are a load-time configuration error; the graceful-pause tool deadline is bounded to [5, 120] seconds; the unresponsive-model threshold has a floor of 30 seconds.
- **REQ-ORCH-144** — Per-role overrides MUST include: a per-role stall threshold (for slow reasoning models); a fallback model (used at most once per child on hard timeout or unresponsive model); a thinking toggle; a coordination-only tool profile (delegation and todo maintenance permitted; reading, editing, and execution withheld); a read-only profile; an allowed-delegates list; a suppress-sibling-context flag; an artifact-publishing flag; a summarizer-model override; and a permission mode.
- **REQ-ORCH-145** — Per-model settings MUST include: a per-model parallelism cap (REQ-ORCH-050); a per-model HTTP timeout overriding the runtime model timeout; and a per-model retry count overriding the provider default of 5.
- **REQ-ORCH-146** — For a provider that ships its own native agentic loop, a runtime toggle (default enabled) MUST run children on that provider under the native loop; disabling it falls back to a degraded single-shot mode that discards tool use and streaming. A deprecated intent-validation toggle (default false) is retained for configuration compatibility, superseded by completion classification.

### 24. Persistence

- **REQ-ORCH-147** — The session directory layout and workspace-level files in Data & Formats MUST be produced as described; session snapshots MUST durably hold at least: the resolved check suite, the message count and active message limit, the run intent, the todo state, the loop progress record, and improvement artifact ids.
- **REQ-ORCH-148** — The gate-state metadata file is tool-managed and never hand-authored; the editable gate lives in the user configuration (REQ-ORCH-125).
- **REQ-ORCH-149** — The session artifact store MUST be session-scoped, hydrated from the session directory when present (in-memory-only otherwise), shared across iterations, and the source of the auto-injected sibling summaries in child payloads.

## Data & Formats

All formats below are externally observable (on disk, in transcripts, in tool observations, or in host events). Exact wording of model-facing guidance messages may vary provided the specified informational content, ordering, and identifiers are preserved; enum values, statuses, stop reasons, exit codes, event names, and file paths are exact.

### Task identifiers

- Task id: `bg_` followed by 8 lowercase hex characters; regex `^bg_[0-9a-f]{8}$`; unique per session; assigned at spawn for every child.
- Canonical task names: character set `[A-Za-z0-9_.-]`, max 80 characters (longer names truncated with an 8-hex-character digest suffix), per-parent uniqueness via `_<n>` suffixes.

### Delegation observation (model-visible)

```
Task '<canonical>': <status> — <message>
task_id: <id>
```
Statuses: `queued`, `waiting_on_dependencies`, `waiting_on_model_slot`, `rejected` (error).

### Child task states

`queued`, `starting`, `running`, `waiting_on_dependencies`, `waiting_on_model_slot`, `succeeded`, `failed`, `cancelled`, `blocked`; terminal = last four. Transition table per REQ-ORCH-041.

### Child report artifact (behavioral schema)

Fields: agent name; role; status (`succeeded|failed|cancelled|blocked`, with `partial` flowing through internally); summary; key findings (bullet list); last response; final response; detail payload (highlighted paths + verbatim snippets); edited files (path, change type, commit hash); created files; artifacts; commands (command, exit code, summary); tests (name, status `passed|failed|skipped|not_run`, summary); errors (type, message); next recommended actions; escalation signal; tags (closed vocabulary: research, planning, implementation, review, verification, errors). Runner-owned, model-unwritable fields: verification results, completion-gate decision, repair record, gate state, requirement-coverage evidence, scope-drift findings.

### Timeline event vocabulary (session diagnostics)

`iteration_start`, `iteration_end`, `completion_classified`, `completion_gate_decision`, `repair_attempt_scheduled`, `repair_escalation`, `verifier_started`, `verifier_check_started`, `verifier_check_finished`, `verifier_run_completed`, `verifier_run_skipped`, `verifier_gate_calibrated`, `verifier_gate_written`, `verifier_gate_authoring_skipped`, `requirement_evidence`, `child_start`, `child_end`, `child_result`, `child_conversation_closed`, `child_launch_suppressed`, `child_user_cancelled`, `quota_fallback_model`, `fallback_model`, `llm_unresponsive`, plus one `session.start` and one `session.end` per run.

### Issue kinds (session diagnostics)

`stall`, `timeout`, `timeout_fallback`, `llm_unresponsive`, `llm_bad_request`, `parent_resume_bad_request`, `transient_llm_error`, `provider_quota_exhausted`, `quota_fallback`, `circuit_breaker_escalation` (loop-supervisor escalation), `incomplete_execution`, `child_exception`, `child_force_cancelled`, `stale_child_launch_claim`, `background_child_drain_timeout`.

### Stop reasons, run statuses, exit codes

- Stop reasons (exact strings): `all tasks completed`, `iteration limit reached`, `time limit reached`, `no pending tasks`, `stopped by user`, `interrupted by user`, `agent session aborted`, `user cancelled at message limit`.
- Run statuses and exit codes: `completed` = 0, `failed` = 1, `error` = 1, `max_iterations` = 2, `interrupted` = 130.
- Session execution status includes `paused_message_limit` for a background message-limit pause.

### Session directory layout

Under `<workspace>/.rotaris/sessions/<session_id>/`:
- `conversations/event_logs/` — per-conversation event logs.
- `evidence/verifier/` — full verification check outputs.
- `evidence/debug.log` — per-session log at the configured session log level.
- `evidence/memory.jsonl` — memory diagnostics when enabled.
- `state/run_config.json` — resolved check suite (with source) and the playbook-cell audit payload.
- `.message_limit_paused` — message-limit pause signal file (removed on resolution).
- Session snapshots holding the fields in REQ-ORCH-147.

### Workspace-level files

- `<workspace>/.rotaris/verifier.state.json` — gate lifecycle metadata: state (`absent|pending|calibrated|stale`), marker content fingerprint, probe records. Tool-managed.
- `<workspace>/.rotaris/playbooks/` — workspace-scope playbook overrides (field-wise deep merge over the global scope; may re-word variants only).
- The check suite itself lives in the user configuration (three-valued: omitted / empty list / explicit list) with per-check `timeout`, `severity` (`blocking|advisory`), `role` (`test|typecheck|lint|other`), and workspace-relative `cwd`.

### Intent categories

`explicit_trivial`, `question`, `exploration`, `problem_resolution`, `single_file_change`, `small_feature`, `moderate_feature`, `large_feature`, `refactor`, `architectural`, `requirements`, `whole_project`, `ambiguous`. Fallback: `moderate_feature`.

### Playbook slots and budget tiers

Slots (render order): `ROUTE`, `AUTONOMY`, `RESEARCH`, `CHUNKING`, `VERIFY`, `ARTIFACT`, `OUTPUT`, `BUDGET`. Budget clamps: tight = {active 2, total 6, depth 2}; normal = {active 4, total 12, depth 3}; wide = no clamp. Run overrides: `swarm`, `single`.

### Loop-supervisor classifier response

JSON object `{loop_detected: bool, reason: string, corrective_message: string}`; corrective message ≤ 90 words.

## Open Questions

1. Real-time timing behavior under live model calls (e.g. whether the loop-supervisor's activation-cycle latency budget holds in practice, and actual backoff wall-clock behavior) could not be verified statically; only configured values and stubbed-clock tests were available.
2. The plan-gating feature (a persistent plan-versus-auto mode with a user confirmation gate before execution: plan surfaced verbatim, execution blocked on explicit user response, direct plan editing, iterate-on-plan cycles, one-way transition to execution) exists only as approved/draft requirement text with no implementation in the reference, so its runtime behavior could not be determined. A rewrite must decide whether to implement it and from which text.
3. Exact rendered appearance and layout of interactive surfaces during orchestration (live agent tree, wait/limit modals, verification progress indicators) is only partially determinable; behavior contracts are test-corroborated but pixel-level presentation is not.
4. Low-level conversation-lifecycle semantics (threading behavior around pausing, running, and closing a conversation; the shape of streamed events; retry behavior below the level this spec governs) could only be inferred from observed behavior, so a rewrite should treat those details as its own design decisions rather than fixed requirements.
5. The full catalogue of per-slot playbook prompt-variant texts was not exhaustively transcribed, and the actual effect of each prompt variant on model behavior is inherently non-static; a rewrite must author its own variant texts to the slot semantics in REQ-ORCH-020/021.
6. Behavior under multiple concurrent runs sharing one process (thread/queue interleaving across parallel run hosts) is only partially covered by tests and could not be fully characterized statically.
7. One documented default (loop-supervisor trigger thresholds and latency budget) diverges between older requirement text (10/20 thresholds, 2-second activation budget) and the implemented values after a later false-positive fix (60/60 thresholds, 20-second classifier timeout, fingerprint-based primary triggers). The implemented values are recorded in REQ-ORCH-100; which figure a rewrite should treat as canonical is a reviewer judgment call.
8. Whether a dependency whose report resolves to "partial" should unblock its dependents is observed behavior (it does, because partial maps to a succeeded graph state) but the reference's intent is uncertain; confirm whether this is desired or an accident to fix.
9. When a model override cannot be applied during fallback/quota recovery (e.g. an agent factory that does not support overrides), the reference silently skips the override path; decide whether the rewrite should surface this as a visible diagnostic instead.
10. The exact tool-name vocabulary granted by the simple-intent capability bundle (REQ-ORCH-016) belongs to the tool-registry domain; this spec fixes only the capability categories, and the concrete tool list must be aligned with that domain's spec.
11. **REQ-ORCH-009** — The three model slots consulted for intent classification (small model, fallback model, default summary model) are named only descriptively. What are their configuration key names, and is the "fallback model" slot the run-level one or the per-role fallback model of REQ-ORCH-144? Without this, the resolution order cannot be tested.
12. **REQ-ORCH-019 / 020 / 022 / 023** — The model-tier vocabulary is never enumerated (only "medium", "largest", and an all-tiers wildcard are mentioned in passing), and no ordering over tiers is stated, yet REQ-ORCH-020's downgrade-only rule and REQ-ORCH-023's fallback both depend on one. What are the tier names and their order, and which producer-to-consumer role pairings trigger the CHUNKING/OUTPUT substitution?
13. **REQ-ORCH-026** — The workspace-scope override directory is fixed as `<workspace>/.rotaris/playbooks/`, but the global-scope configuration directory has no path. What is it?
14. **REQ-ORCH-016 vs REQ-ORCH-025 vs REQ-ORCH-029** — Contradiction. REQ-ORCH-025's `single` override demands the entry role complete the task itself without delegating; REQ-ORCH-029 forbids the coordinator from ever carrying out a work item, authoring code or diffs, or editing files, under any playbook cell; and REQ-ORCH-016 grants the direct-work tool bundle only for `explicit_trivial` and `single_file_change`. Under a `single` override at any other intent, the role is instructed to do work it is both forbidden to do and untooled to do. Which is canonical: does `single` also lift the REQ-ORCH-029 restrictions and grant the direct-work bundle, is it valid only for the two simplest intents, or is it advisory guidance the coordinator may not act on?
15. **REQ-ORCH-028** — Two facts are undetermined. (a) "the acceptance role's sign-off is required before the run may report success" — is this enforced by the run (and if so, where does it interact with REQ-ORCH-082/083, which derive status purely from completed and abandoned task counts), or is it an instruction the coordinator is expected to honour? (b) At what granularity is exclusive implementation ownership measured — one todo item, one file, one directory, or something else? The requirement has been narrowed to "one todo item at a time" pending an answer.
16. **REQ-ORCH-030** — What counts as one failed attempt at the same task for the three-strikes rule: a child reaching terminal state `failed`, a gate-driven re-queue, a completion-classifier `NEEDS_ITERATION`, or any of these? Is the rule enforced by the run or instructed? And what is the required shape of the "failure report to the user"?
17. **REQ-ORCH-039 vs REQ-ORCH-116** — Asymmetry. Delegation refusal now keys only on blocking checks recorded `failed`, while the completion gate treats `failed`, `timeout`, and `skipped` alike as unsatisfied. This is the only reading that leaves REQ-ORCH-129's "checks that did not answer their question" list reachable by the acceptance role. Confirm the asymmetry is intended, or align the two.
18. **REQ-ORCH-045** — For a name longer than 80 characters: which digest function produces the 8-character hexadecimal suffix, over exactly what input, and what separator (if any) precedes it? The 80-character result length is fixed by Data & Formats; the rest is not.
19. **REQ-ORCH-062 / REQ-ORCH-064** — Nothing in this document bounds the duration of a voluntary wait, and REQ-ORCH-064 deliberately exempts it from graceful-pause deadlines. Should `wait_for_tasks` have a maximum duration, and if so what happens when it elapses?
20. **REQ-ORCH-069 vs REQ-ORCH-077** — Contradiction in practice. REQ-ORCH-077 abandons a task once its consecutive pending-outcome count reaches the iteration limit, and REQ-ORCH-069 stops the whole run once the completed-iteration count reaches that same limit. Because a re-queued task is selected again by REQ-ORCH-067, the two counters advance together, so the per-task guard can never fire before the global stop. Should the per-task consecutive-retry cap be a separate, smaller, independently configurable value?
21. **REQ-ORCH-071 vs REQ-ORCH-079** — Both extend a run that would otherwise stop for "all tasks completed". Which is evaluated first when a queued prompt has arrived and relentless mode also finds unmet criteria, and may both extend the same stop?
22. **REQ-ORCH-079** — The relentless audit is a model call with no stated timeout and no stated behavior on failure. What bounds it, and does a failed or timed-out audit stop the run normally or retry?
23. **REQ-ORCH-082** — Under the stated first-match ordering, a run that completed no tasks and abandoned no tasks matches rule 2 and reports status "completed" with "Run completed." Is that intended, or should a run that resolved nothing report differently?
24. **REQ-ORCH-092** — Which provider failures are "transient" and which are "validation-class"? The two classes carry different retry budgets (default 1 and 0), so the classification is externally observable but is nowhere defined.
25. **REQ-ORCH-095** — The `incomplete_execution` issue names the assessed progress category, which makes the category vocabulary externally observable, but the six categories are described only in prose. What are their exact identifier strings?
26. **REQ-ORCH-096** — "Exhausted stuck-recovery is reported as recovery exhaustion" names no member of the issue-kind vocabulary in Data & Formats. Which issue kind and report text represent it — `circuit_breaker_escalation`, or a kind missing from the vocabulary?
27. **REQ-ORCH-111** — What is the text of the deterministic verification summary produced without a model call? It is user-visible in the report, so its content (if not its exact wording) needs fixing.
28. **REQ-ORCH-122** — Two facts are undetermined. (a) How are subproject roots located: by recursive scan, at what depth, honouring which ignore rules? (b) What distinguishes a preferred command that "cannot be launched" (triggering same-role fallback) from one that launches and exits non-zero (recorded `failed`)?
29. **REQ-ORCH-123** — A check that exits 0 while reporting failing tests must be recorded `failed`. How is that output recognized, and for which check roles or commands does the recognition apply?
30. **REQ-ORCH-128** — Two facts are undetermined. (a) How long is the grace period between the interrupt and termination of a check that ignores it? (b) A user-initiated skip is recorded `skipped`, which under REQ-ORCH-116 leaves the completion gate unsatisfied and can consume repair budget under REQ-ORCH-118. Should an explicit user skip instead be exempt from gating?
31. **REQ-ORCH-137** — The improvement pass is skipped when "the run type is not a task run", but no run-type vocabulary is defined anywhere in this document. What are the run types, and which of them are task runs?
