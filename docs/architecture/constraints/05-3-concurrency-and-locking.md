# Architectural constraints extracted from the specification — 3. Concurrency and locking

Part 5 of 22 of [the constraints](../constraints.md), which indexes every part.

## 3. Concurrency and locking

| # | Constraint | Label | Requirements |
|---|---|---|---|
| C-01 | **Re-derived: two locks, and they are deliberately in different media.** The **session lock** is "a record held in the same store as the session it locks" (`REQ-SESSION-046`), and `REQ-GIT-020` adds that the field set "is shared verbatim with `REQ-SESSION-046` and neither domain may change it alone". The **integration lock** is still a **file**: `REQ-GIT-128` fixes `<workspace>/.rotaris/integration.lock`, created with exclusive-create semantics, containing `{session_id, pid, host, started_at}` — four fields, a different timestamp name, and an owning session id, so **the two do not share a shape**. `REQ-GIT-128` states why it stays a file: what it protects is the base repository, which is the user's own material and travels with the workspace, so **a second machine reaching the same checkout must meet the same lock**. It is the one lock in the product that is not machine-local. See W-20 for the invariant this forces. **`REQ-GIT-128` now carries its own storage clause and it changes the shape of this row's residual risk**: where the open workspace is classified as replicated by a file-synchronisation agent (`REQ-STARTUP-166`), an integration SHALL be refused before anything is attempted and **the lock SHALL NOT be created at all**; the classification is `REQ-STARTUP-166`'s and this domain "states no storage test of its own"; and only the *replicated* classification refuses — storage another machine reaches directly does not, and neither does a workspace the product could not classify or has not classified yet, because "an inconclusive answer is a silent negative there, it stays one here". The refusal takes its place in `REQ-GIT-124`'s ordered list **ahead of** the lock check. | HARD | REQ-SESSION-046, REQ-GIT-020, REQ-GIT-124, REQ-GIT-128, REQ-STARTUP-166 |
| C-02 | On collision **at most one** stale-reap attempt is made and only when the content parses, the host names this machine and the pid probes dead here. **No waiting, no retry loop, no second reap.** **The reaping rule is what the two lock media share** — `REQ-GIT-128` states it "on the same reasoning `REQ-GIT-020` gives for session locks" — and it is the *rule*, not the shape, that is common. For the session lock the whole rule is now **one transaction**: insert, on collision read the row and apply the three conditions, delete-and-insert once if all hold, otherwise roll back leaving the row exactly as found — strictly stronger than the file, where read-check-delete-then-create was three operations with a window between each. | HARD | REQ-SESSION-047, REQ-GIT-020, REQ-GIT-128 |
| C-03 | A lock this machine cannot prove dead is **never reclaimed automatically**; exactly one explicit, user-confirmed action removes it, stating pid, host and acquisition time first. | HARD | REQ-SESSION-183 |
| C-04 | **The right to write a session's history is exactly the right to hold that session's lock.** A process not holding it must not write that session's history, and a run that cannot take the lock does not start. **Reading is unrestricted and needs no lock.** **Two clauses were added by the amendment and both are load-bearing.** Writes MUST be serialized **even where the store cannot corrupt**, because what is at stake is emission order and not integrity. And **"a reader MUST NOT be able to delay or block the writer… a store in which one blocks the other does not satisfy this requirement"** — which makes the store's concurrency model a **conformance property** rather than a tuning choice, and is the single sharpest constraint on the engine (W-03, W-21). | HARD | REQ-EVENTS-098, REQ-SESSION-056, REQ-SESSION-083 |
| C-05 | Releasing the lock **tears down session-scoped shared services holding long-lived subprocesses before the lock file is removed**. | HARD | REQ-SESSION-049 |
| C-06 | Liveness **resolves toward alive** in every uncertain case; `pid <= 0` is dead; permission-denied is alive; on Windows the probe **must deliver no signal or console control event** to the target. | HARD | REQ-SESSION-051 – REQ-SESSION-054, REQ-MONITOR-208, REQ-GIT-093 |
| C-07 | **One verdict**: lock reaping, liveness reporting, stale detection and the worktree-integration precondition must never disagree about one pid at one moment. | HARD | REQ-SESSION-047, REQ-SESSION-056, REQ-SESSION-064, REQ-SESSION-171 |
| C-08 | Stale detection reads only the listing record and the lock record, **writes nothing**, never raises, and reports an empty result over a broken store. **The amendment has landed and it changed the verification method, exactly as this row predicted it must.** `REQ-SESSION-058` now states that stale detection writes nothing "which a caller may verify by observing that nothing the session owns has changed". The old tree-fingerprint test would have **failed a conformant implementation**, because a store's write-ahead-log and shared-memory companions change without any record changing. The detector holds a read-only connection on which an attempted write raises rather than succeeds. | HARD | REQ-SESSION-058 |
| C-09 | Repair is **explicit and never triggered from a read path**, with a mandatory step order (status first, lock second), idempotent, never raising. | HARD | REQ-SESSION-060, REQ-SESSION-061, REQ-SESSION-063 |
| C-10 | **Re-derived: the accepted defect is withdrawn as unreachable, and the guarantee it sat inside is unchanged.** `REQ-LIBRARY-042` now requires the read-modify-write to **take effect as one indivisible step** and records ESC-3's accepted defect as withdrawn **"as unreachable, not as unimportant"**; `REQ-LIBRARY-043` states the atomicity observable and withdraws the mechanism, with `REQ-LIBRARY-158` giving the reason no ladder is needed — **no writer outside this application can reach a record in that store**. The scope note survives and still matters: these requirements govern the **improvement artifact store** and nothing else; they do not reach the delivery store, which no requirement subjects to this rule (ADR-0041 makes its transitions transactions on that ground). **What is still unowned** is `REQ-LIBRARY-047`'s best-effort history write, which under a transaction becomes a deliberate decision about whether that write stays outside it — OQ-45. **That clause has grown a consequence it did not have when it was filed**, and it is not a storage question any more: `REQ-LIBRARY-176` requires the improvement export to state where retention "has dropped intermediate versions … and how many", while `REQ-LIBRARY-047` makes recording a version best-effort and explicitly outside the write's all-or-nothing boundary — so a version can be absent because it was **never recorded** rather than because `REQ-LIBRARY-052` pruned it, and no requirement obliges the store to retain enough to tell a reader of the export which. ADR-0041 takes the export and names the fix (count versions *allocated* as well as retained); nobody owns the write path that would maintain it. | HARD | REQ-LIBRARY-042, REQ-LIBRARY-043, REQ-LIBRARY-158, REQ-LIBRARY-047, REQ-LIBRARY-052, REQ-LIBRARY-176 |
| C-11 | Concurrent traceability invocations are safe **without any lock, lease or coordination file**; **no invocation waits for another**; none ever fails, hangs or leaves a lock behind because another was running. **The property is now reached for invocations inside the application, and the reason is SR-1, not SR-4.** Two of the three premises behind the old failure are gone: the toolchain has no command line (`REQ-TRACE-142`, `REQ-TRACE-144` – `REQ-TRACE-151`, `REQ-TRACE-153`, `REQ-TRACE-184` – `REQ-TRACE-186` withdrawn), `REQ-TRACE-206` forbids launching the engine as a process, `REQ-EVENTS-178` gives no programmatic entry point, and `REQ-STARTUP-161` removes the second instance — so every invocation is in-process on ADR-0002's bounded worker pool; and `REQ-GIT-140` gives each isolated run its own worktree, so N runs read N copies rather than N readers of one file. ADR-0040 discharges the rest with a **single I/O owner** over the four written artifacts. **The residue is not closed, must not be recorded as closed, and has TWO halves with different owners and different remedies — a reader who sees only "regeneration can fail on Windows" will reach for one remedy for both.** (a) A `REQ-TRACE-182` **test session in the same checkout** is the `REQ-TRACE-502` conformance gap at its narrowed scope, because that requirement's subject is failing "because another invocation was running" — OQ-41. (b) A **foreign process** — an editor, a language server, an indexer, anti-malware, a sync client — holding the artifact is *not* a `REQ-TRACE-502` gap at all, because an editor is not an invocation; it is a `REQ-TRACE-061` re-raise problem — OQ-44. Both are real user-visible failures; only (a) is measured against a requirement. ***Two sentences here are WITHDRAWN as of the platform-defect round of 2026-09-02 and must not be cited: "In both, `REQ-TRACE-061` requires the failure **re-raised** and states no ladder" and "Bounded contention is exactly the condition under which a bounded ladder would suffice, and `REQ-TRACE-061` states none."*** `REQ-TRACE-061` **now states the ladder** — at most five attempts, delays of 0.05 / 0.1 / 0.2 / 0.4 s, the last beginning within 0.75 s of the first — and states it as **this domain's own**, covering the generated artifact, the three baselines, the retired-identifier log and the destination an export writes to, explicitly not derived from `REQ-SESSION-033`. **The clause that closes half (b) rather than half-closing it** is that the retry MUST NOT be conditioned on the product being able to attribute the failure to another process holding the target: the measured 6.2 % first-attempt failure had no other opener present at all, so a build that retries only where it can identify a foreign handle absorbs none of it. **Half (b) and OQ-44 are therefore closed.** Half (a) — a `REQ-TRACE-182` test session in the same checkout — is untouched by the ladder and remains OQ-41. **The store does not close this, and that is now stated by a requirement rather than argued**: `REQ-TRACE-513` (D-30) requires all four artifacts to be plain files in the user's own repository and forbids moving them into any store the application keeps, so they never reach a store whose readers do not block its writers. ***"The residue is unchanged in kind and sharper in contrast: the corpus states exactly one Windows replace ladder (`REQ-SESSION-033`, D-06) and it is in the wrong domain to be borrowed" is WITHDRAWN with the two sentences above.*** The corpus now states **two** ladders with two owners and each declares itself its domain's own, which is the outcome this row asked for rather than the borrowing it feared. **What would close half (b) is now known and priced, and it is not what this row used to say.** The remedy is not a runtime API exposing share-delete on open: `spikes/windows-writer-handle-compaction.md` §3.2 establishes that the runtime already requests share-delete and that the blocker is the replace-by-rename call, which fails 20/20 even against a holder that explicitly permits delete. The closer is a **replace primitive** — `ReplaceFileW`, measured succeeding 6/6 against a held reader with no torn or empty read — available out of process at p50 767 ms and unmeasured in process. The question is therefore *who owns a native replace primitive*, not *is a share flag available*. **This row may not assert `REQ-TRACE-502` satisfied.** | HARD; residual CONFLICT on Windows with REQ-TRACE-061 | REQ-TRACE-502 vs REQ-TRACE-061; REQ-TRACE-513, REQ-STARTUP-161, REQ-TRACE-206, REQ-EVENTS-178, REQ-GIT-140 |
| C-12 | Single-flight rules exist per subject and differ: one desktop checkpoint operation, declined if another is in flight; one integration per base workspace; one run per session; one traceability operation of a given kind, **refused with a stated reason rather than queued or raced**; one state-changing board action per requirement, with **no bound across different requirements**; one improvement analysis at a time in completion order; a refresh pass returning false rather than queueing; a batch during an in-flight read re-attempted after 150 ms, explicitly **not a debounce**; a cold board's concurrent reads coalesced to one. | HARD | REQ-GIT-091, REQ-GIT-128, REQ-GIT-136, REQ-GIT-145, REQ-TRACE-229, REQ-TRACE-349, REQ-TRACE-350, REQ-TRACE-388, REQ-TRACE-512, REQ-LIBRARY-123 |
| C-13 | **There is no ceiling on concurrent isolated runs** — host resources are the only limit. Unchanged, and still binding on the engine, the ledgers and the budgets. **Its store-facing half must not be used as an amplifier any more.** It never implied an unbounded number of concurrent *processes*: under `REQ-STARTUP-161` every run is inside one run host and every traceability pass inside one workspace service, and `REQ-GIT-140` gives each isolated run its own worktree, so the traceability artifacts are per-worktree working-tree files rather than one file with N readers. The use C-11 and OQ-41 made of this row is withdrawn. | HARD | REQ-GIT-145, REQ-GIT-140, REQ-STARTUP-161 |
| C-14 | The credential store and the discovery snapshot are under a **cross-process exclusive lock** with a 5-second acquisition budget; a lock left by a dead process is reclaimed, a lock held by a live process is never broken; **reads take no lock**. **The mechanism survives SR-1; only its stated reason changed.** `REQ-PROVIDER-152` no longer says "more than one application instance may run" — it says every window of the one instance reaches the same per-user files and several read-modify-write sequences can be in flight at once. The reclaim-a-dead-holder clause is the part SR-2 makes **more** important, not less: it is the only thing that settles a lock an instance that crashed left behind, and `REQ-STARTUP-164`'s reclaim path is one interval in which two processes of this application genuinely coexist. | HARD | REQ-PROVIDER-152, REQ-PROVIDER-087, REQ-STARTUP-161, REQ-STARTUP-164 |
| C-15 | Exactly one shared MCP connection per server per session, and for stdio **exactly one server process**, opened on first demand, reused by every agent, closed exactly once at session end; two concurrent first-demands yield one connection; calls to already-connected servers must not wait for another server's startup. | HARD | REQ-MCP-066, REQ-MCP-067 |
| C-16 | Concurrent calls over one MCP connection must all complete, each receiving its own response, and **the session keeps emitting its events while a call is outstanding**. | HARD | REQ-MCP-068 |
| C-17 | Each terminal session runs at most one foreground command; a second waits. Sessions belonging to different agents run concurrently. Background sessions never occupy a terminal session. | HARD | REQ-TOOLS-108, REQ-TOOLS-187, REQ-SANDBOX-089 |
