# Conversation, Composer, and Transcript — 9. Desktop Transcript Rendering

Part 3 of 7 of [domain 03](../03-conversation-composer-transcript.md), which indexes every part. Defines REQ-CHAT-055 – REQ-CHAT-165.

### 9. Desktop Transcript Rendering

- **REQ-CHAT-055** — The transcript MUST scale to long conversations: the work of painting and measuring MUST depend on how many rows are visible and how many rows changed, not on how many rows the transcript holds in total. With 1000 or more rows present, scrolling, expanding a row, and running a search MUST each respond within the latency budget of REQ-CHAT-157, and appending a row MUST cost no more than it does on an empty transcript.

  **What "cost" means here is fixed by this requirement, because the two available readings give opposite verdicts on the same build and the difference is not a detail.** Cost is the time a person waits: it is measured from the moment an update is applied to the moment the interface has finished showing that update's effect — the same instant the benchmark domain closes a phase's timing on (REQ-UIBENCH-051, REQ-UIBENCH-119), and the same instant REQ-CHAT-157's budget is measured to. It is **not** the duration of the synchronous call that submits an update, and **no build is judged against this requirement, in either direction, on a figure taken before the frame showing that update has been painted.** Every clause above is read at that one measurement point: the latency budget, the dependence on visible and changed rows rather than on the total, and the append comparison, which is therefore a comparison of two shown-update times — the time to show an appended row when the transcript holds a thousand or more rows against the time to show one on an empty transcript.

  **Work inside an update that scales with the total row count is consequently not forbidden in itself; it is forbidden to the extent that it moves that figure.** Some such work is unavoidable while the interface is handed the whole transcript on every update, which the benchmark domain's phases require (REQ-UIBENCH-055, REQ-UIBENCH-057, REQ-UIBENCH-058); this requirement neither licenses that work to grow nor treats its bare existence as a failure, and a residue that does not reach the shown-update figure is not a violation of it. The converse is not relaxed: a build whose shown-update figure grows with the number of rows the transcript holds fails this requirement, however small any individual step in it is argued to be, and the demonstration required is a measurement at that point rather than an account of which steps are proportional to what.

  **A conformance test that reads a synchronous figure is testing something this requirement does not state**, and a build that meets the shown-update comparison while missing the synchronous one satisfies this requirement. This paragraph settles a reading, not a budget: no figure, threshold or tolerance is fixed here that REQ-CHAT-157 does not already fix.
- **REQ-CHAT-056** — Rows of the agent-message category MUST render Markdown, with fenced code blocks in a monospace face on a shaded background of their own, bold text at a heavier weight than body text, italic text slanted, inline code spans in a monospace face, and hyperlinks in a colour distinct from body text and activatable per REQ-CHAT-076. Markdown that is still incomplete because it arrived mid-stream MUST render without raising an error and without altering the appearance of rows around it. Rendering MUST complete synchronously and MUST NOT issue any network request. **The dialect is fixed, and is fixed here.** Beyond the five treatments above, the following MUST render: headings, block quotes, ordered and unordered lists, task lists, tables, thematic breaks, and strikethrough; and a bare URL appearing as text MUST be treated as a hyperlink on the same terms as an authored one. **Raw HTML appearing in Markdown source MUST NOT be rendered as markup** and MUST be shown as the text it is — rendering agent output as markup would make every model response able to introduce elements into the surface the user reads their workspace through, and nothing this requirement fixes needs it. **No image is ever loaded from a Markdown image reference.** An image reference MUST render as its alternative text carrying an activatable reference, and MUST NOT cause image content to be fetched or read; this holds for a reference naming a location on this machine exactly as it holds for one naming a remote location, both because rendering may issue no network request and complete synchronously, and because a transcript that reads locations named by model output discloses whatever those locations hold. This governs what Markdown *syntax* may cause to be loaded and does not govern images the user attaches or image bodies the product itself holds (REQ-SESSION-002), which are unaffected. An artifact an agent publishes MUST appear as an ordinary agent-message row carrying an activatable reference that opens that artifact in the library surface: the transcript has no artifact row category of its own (REQ-CHAT-046 closes the vocabulary) and no partial / hidden / full artifact display setting exists anywhere in the product.
- **REQ-CHAT-057** — Row layout MUST use a timestamp column of 52 px, a role column of 112 px, a minimum row height of 30 px, and timestamps painted in the monospace stack at 8 pt. Attribution — the role line, plus a task line when the row belongs to a named task — MUST be drawn only on the first row of a block, a block beginning at every row whose role differs from the row above it. Continuation rows MUST instead show a 2 px bar in the role gutter, coloured by the persona. Row margins are **10 px horizontally** and **5 px vertically**, so consecutive rows sit closer together than a row sits to the edge of the transcript area.

- **REQ-CHAT-058** — Desktop transcript memory MUST stay bounded however long the conversation grows: retained row measurements and retained row renderings MUST each be held only up to a fixed limit, beyond which the least recently used are discarded. A retained rendering MUST be reused only while everything that determines the row's appearance is unchanged — its identity, its content, the width it was laid out for, and its expansion state — so that inserting, removing, or reordering rows can never make one row display another row's content. Rows that are live (a running tool, verifier, or group, or reasoning still streaming) MUST be redrawn on every repaint rather than reused, so their elapsed times keep advancing. Switching theme MUST redraw every row in the new theme while leaving every row's expanded or collapsed state exactly as the user set it.
- **REQ-CHAT-059** — Row expansion state MUST be keyed by stable identity — tool/verifier rows by their tool-call key (content-hash fallback), thinking rows by start time (text-hash fallback), delegation headers by agent, groups by the key of the group's **first** member — so an opened box stays open while the group grows, while rows are inserted above it, and across model resets.

- **REQ-CHAT-163** — Text taken from a model stream for display MUST satisfy three rules. A chunk carrying a tool call MUST NOT appear anywhere in the visible message text. Content the provider marks as internal deliberation MUST appear only in the reasoning channel — a streamed-reasoning row — and never in an agent-message row. A delta consisting only of whitespace MUST be kept exactly as received and MUST NOT be dropped or collapsed, since discarding it would join Markdown blocks that must stay apart; with REQ-CHAT-157 this means the finished message equals the concatenation of the deltas received, character for character. Reasoning MUST be recognized from all three shapes providers use to carry it — a dedicated reasoning field on the delta, a thinking block inside the content, and a list of reasoning items — so that no provider's deliberation reaches the answer body for want of being recognized.
- **REQ-CHAT-164** — While a model call is in flight and the provider has produced no output of any kind for **10 seconds**, the live row for that call MUST replace its animated indicator with a stalled indicator stating that the model is not producing output and showing the elapsed seconds, so that a stall is distinguishable from ordinary slow generation. The indicator MUST revert to the ordinary animated form as soon as any further output arrives. It MUST NOT append a row of its own, MUST NOT cancel or retry the call, and MUST NOT change what the model eventually receives or what the transcript records. When a streamed phase completes, its animation MUST stop where it stands and no completion row MUST be appended.
  > **Narrowed by [`PD-CHAT-006`](../../product/directives/pd-chat-006.md#pd-chat-006), 2026-09-15.** The stalled
  > indicator is **untouched**: the ten-second threshold, the text stating that the model is not
  > producing output, the elapsed seconds, the reversion as soon as further output arrives, and the
  > three prohibitions (no row of its own, no cancel or retry, no change to what the model receives or
  > the transcript records) all govern exactly as above. What the directive removes is the **ordinary
  > animated form** on a row that is neither a tool call nor streamed reasoning: there the stalled
  > indicator now appears where nothing was drawn, and reverting means drawing nothing again. A tool
  > row's `◉ running…` and a reasoning row's `◉ reasoning…` keep their animation, so "stop where it
  > stands" is unchanged for them. The text above states the behavioural target and is kept for that
  > reason.
- **REQ-CHAT-165** — The desktop MUST keep the whole conversation readable while holding only a bounded number of rows resident, so resident memory stays flat as a session grows without bound (REQ-CHAT-157). Rows beyond the resident bound MUST be released to the session record rather than lost, and MUST be brought back on demand: scrolling toward the top of the transcript MUST load the next older span and place it above the rows already shown, leaving the reader's position undisturbed by the anchor rule of REQ-CHAT-071 and leaving every row's expanded or collapsed state as the user set it. Loading MUST happen off the interface thread and MUST NOT block input. Reaching the oldest recorded row MUST be distinguishable from a load that failed; a failed load MUST report that older messages could not be loaded, MUST leave the rest of the transcript usable, and MUST be re-attemptable by scrolling again. A row brought back MUST be identical to the row that was released, so paging can never change what the transcript says. The residency this requirement depends on is not defined here: it is the bounded resident transcript of REQ-SESSION-192 and the retained released pages of REQ-SESSION-131. This requirement relies on those two for the resident row bound, for the whole-page release of rows past it, for the released page being retained unaltered, and for the preservation of each row's index across release — which is what lets a paged-in span be placed in its original position and be identical to the row released. This requirement states no bound, page size, or storage form of its own, and adds only what the desktop transcript does with them: when older rows are fetched, on which thread, how the reader's position is preserved, and how the oldest recorded row is distinguished from a failed load.
