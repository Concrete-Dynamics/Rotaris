**OQ-480 — May a diagnostics run directory carry the application log, and where does a window with no workspace write?** *(REQ-STARTUP-129, REQ-STARTUP-131, REQ-STARTUP-132, REQ-STARTUP-134, REQ-SHELL-163, PD-MONITOR-002. Raised 2026-11-03 by [R-091](../../../product/requests.md#r-091)'s hardening bundle D2 `log-sinks`, building the `light` level for the application log; numbered from the sub-range the plan gave the bundle, so it sits out of order here.)*

**What is open.** Two things the requirements do not settle. **(1) The stream.** The hardening finding is that a packaged Windows build writes its application log to a standard output nobody reads (`docs/architecture/hardening/02-the-findings.md` §3.4), and the plan closes it through the diagnostics `light` level. REQ-STARTUP-132 lists the run directory's artifacts — `manifest.json`, `metrics-NN.jsonl`, `spans-NN.jsonl`, snapshots, `summary.json`, `summary.md` — and the application log is not among them. REQ-STARTUP-134 forbids session content in any diagnostics file: no transcript or prompt text, no model or tool output, no file contents, no credentials. Main's log lines pass the one redaction pass (REQ-TOOLS-171), which masks credentials, but a line can still quote a path, a refused provider's error text or a child's stderr. Whether the list is closed, whether an application-log stream may join it, and what the content rule asks of the lines it carries, is open. **(2) The base.** REQ-STARTUP-131's default base is `<workspace>/.rotaris/diagnostics/rotaris`, and REQ-STARTUP-131 lets a window open with diagnostics inactive only when the base itself is unwritable. A main window can hold no workspace (`(no workspace)` in `main-windows.ts`); with no output folder chosen it has no base at all.

**What the build proceeds under.** (1) A window built while `diagnostics/level` is `light` or `deep` writes `app-log-NN.jsonl` beside its `manifest.json`: every line the application log records (PD-MONITOR-002's threshold, after the redaction pass) as one JSON record `{at, level, source, message}`, within REQ-STARTUP-133's four segments of 8 MiB; the manifest's `captured` list names it, so a reader knows the metric and span streams are unbuilt rather than lost. The lines are what the standard output carries, nothing filtered further. (2) A window with no workspace and no chosen folder opens with its capture inactive, and the card says why (`apps/desktop/src/main/diagnostics.ts`).

**What decides it.** A ruling on whether REQ-STARTUP-132's list admits the application-log stream (a directive extending it, or the stream withdrawn and the log sent elsewhere), what REQ-STARTUP-134's content rule asks of it, and where a window with no workspace writes.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended a directive adding `app-log-NN.jsonl` to REQ-STARTUP-132's list, REQ-STARTUP-134 applied as written with the obligation on the log's writers (paths and error text allowed, the card saying so), and a per-user default base under REQ-STARTUP-145 for a window with no workspace; Advocate B (the system's lens) recommended the same stream and a preferences-root base, with REQ-STARTUP-134 applied by provenance — every line of outside text reduced to source, level and byte length — and each window's stream filtered to the lines main attributes to it. Ruled: the stream stays, the content rule binds by kind at the point of writing, the stream is the instance's log unfiltered, and a window with no workspace writes under the per-user data directory. The grounds, by identifier. REQ-STARTUP-132's "Written artifacts SHALL be:" and the data-formats entry in `docs/spec/11-startup-distribution-updates/09-data-formats.md` enumerate a closed set, so the stream is a departure and is minted, not read in; REQ-TOOLS-171 already names "application log files" among the surfaces its one pass backs, REQ-STARTUP-133 already bounds "each JSON-lines stream", REQ-STARTUP-138 already reads a cut last line, and REQ-STARTUP-130 is untouched because at `off` nothing is created — which is also why lines recorded before a window's capture starts are not carried: a buffer held for a window not yet built would be work done at `off`, and REQ-STARTUP-131 lets no diagnostics data be written before the run directory exists. REQ-STARTUP-134's ban is on session content by kind — "transcript or prompt text, model or tool output, file contents, credentials" — and it confines base-name-only to snapshot stack frames, as REQ-STARTUP-136 confines path reduction to allocation sites, so a folder path, a provider's error text and a child process's own diagnostic lines are what the log is for and are not banned; B's provenance flag and its reduction of every forwarded line to a length would make the run-directory copy of the log weaker than the standard output precisely in the incident the hardening finding (`docs/architecture/hardening/02-the-findings.md` §3.4) exists to keep readable, and it departs from REQ-STARTUP-134's words where the record asks for no departure. B's point that trust is not a guarantee is taken where it stands: the obligation sits on each writer, as PD-MONITOR-002 already places the level there — a line that would quote a prompt, model output, a tool's result or a file's contents says its source, kind and length instead, whoever produced the text — and a test holds it; a line that quotes one is a defect of that writer under REQ-STARTUP-134, not a licence to filter the stream. The per-window split is refused: PD-MONITOR-002 defines this log as "the main process's log", one log of one instance, and the run host's lines cannot be attributed to a window reliably, which B concedes, so an attribution "only as good as the attribution" would promise a scope REQ-STARTUP-134 does not ask for and the build cannot keep; a run directory holds the instance's log for as long as its window lived, and its cost — paths and errors of workspace B under workspace A's `.rotaris/`, which REQ-GIT-003 keeps out of every capture — is said on the card in words. On the base, REQ-STARTUP-131 permits an inactive capture "only where no name at all can be created (the base directory itself being unwritable)" and says diagnostics "SHALL never silently disable itself", so the build's inactive no-workspace window already departs; the launch with no workspace (`(no workspace)` in `main-windows.ts`, a refused or failed open) is where a start-up fault leaves no other trace, and REQ-SHELL-163's card must display "the folder currently in force", which an inactive window has none of. The base is REQ-STARTUP-145's per-user data directory, not the preferences root: diagnostics are data describing this machine, exactly the class REQ-STARTUP-145 writes its machine-local clause for, and citing that identifier inherits the non-replicated location without restating it; the base is fixed when the window is built and does not move when a workspace is opened later (REQ-STARTUP-129, REQ-SHELL-163). PD-MONITOR-002 is the owner's and is applied, not revised: the threshold, the levels and `ROTARIS_APP_LOG_LEVEL` reach the stream unchanged, since the variable sets the log and not diagnostics (REQ-STARTUP-147). The departures from REQ-STARTUP-132's list and REQ-STARTUP-131's default base mint [`PD-STARTUP-011`](../../../product/directives/pd-startup-011.md#pd-startup-011), extending both; REQ-STARTUP-134, REQ-STARTUP-129, REQ-STARTUP-130, REQ-STARTUP-133 and REQ-SHELL-163 govern as written. What executes: in `apps/desktop/src/main/diagnostics.ts`, `diagnosticsBase` takes the per-user data directory as its third resolution and the "nowhere to be written" inactive reason goes, main passing that directory in `DiagnosticsCapturesDeps`; `main/diagnostics.test.ts` gains the no-workspace case under the per-user default; `settings/DiagnosticsCard.test.ts` holds the card's new sentences and the default folder it shows; the content obligation is held by a test beside each writer that handles session text (the run host's tool and provider lines, the MCP host's forwarding) asserting the log line names source, kind and length and never the text; one `pnpm app:drive` launch at `light` with no workspace finds `app-log-01.jsonl` under the per-user folder; first-execution notes on REQ-STARTUP-131 and REQ-STARTUP-132 and a row in `docs/architecture/first-executions.md`. Reopened by a measured finding of session content in a stream, repaired at the writer; or by an owner's request for a per-window log, which reopens PD-MONITOR-002's "the main process's log" and is the owner's.

**OQ-473 — Is 5 s the right bound on a utility process's first answer on a loaded host, now that a run host that misses it stays gone until a restart?** *(OQ-462, ADR-0002 consequence 1, REQ-STARTUP-156. Raised 2026-11-04 by [R-091](../../../product/requests.md#r-091)'s hardening bundle B1, building OQ-462 (2); numbered from the hardening plan's range OQ-469 – OQ-480.)*

**What is open.** OQ-462 (2) applies the run host's 5 s `hello` bound to both children and ends a child that misses it; (4) never forks the run host again. Together, a run host that answers in six seconds on a busy machine leaves the person without runs for the whole session. That is not hypothetical on this host: on 2026-11-03, with the CPU at 100 % from another session's proofs, a driven launch's run host wrote its first line about 5.8 s after main claimed the instance and missed the bound ("no reply to hello within 5000 ms"), and loc1's reviewer met the same miss on 2026-10-21 at 22 to 100 % CPU ([the note](../../defects/a-launch-whose-run-host-misses-the-hello-bound-ends-on-an-unhandled-main-rejection.md)). Before OQ-462 such a launch ended with no window at all; now it paints and says "The run host did not start". The specification states no bound on a child's start, and REQ-STARTUP-156 bounds the first paint, not the run host.

**What the build proceeds under.** The ruling as written: 5 s for both (`RUN_HOST_READY_BOUND_MS`, `WORKSPACE_SERVICE_READY_BOUND_MS` in `apps/desktop/src/main/child-supervision.ts`), the bound counted from the `hello` request main sends after `app.ready` and the provider service, not from the child's own start.

**What decides it.** A ruling on the bound — kept, lengthened, or counted from the child's `spawn` — or on one fresh fork after a missed ready only (never after a run host that ran, ADR-0002 consequence 1), which the specification does not address.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended lengthening both bounds to 20 s, still counted from the `hello` main sends, taking that `hello` off the first-paint path so the window paints while the run host is still starting, holding (not refusing) a request made in that interval, and recording for the owner a recommendation to allow one re-fork after a missed `hello` only; Advocate B (the system's lens) recommended the same 20 s on both children, counted from the child's `utilityProcess.fork`, `boundedReady` started at the fork and run in parallel with window construction, every run-host request made before the `hello` held on that readiness and refused through the existing `runHost.notStarted` on a miss, the proof logging the observed `hello` latency, and everything else in OQ-462 unchanged. Ruled: the bound is lengthened and leaves the paint path; the run host is not forked again. (1) `RUN_HOST_READY_BOUND_MS` and `WORKSPACE_SERVICE_READY_BOUND_MS` become 20 s, revising OQ-462 (2)'s figure, which was a consortium ruling under R-072 that carried no measured basis ("the 5 s main has always given it", `child-supervision.ts`), while ADR-0002 part 12 records three misses by a healthy child on this host under load (about 5.8 s at 100 % CPU on 2026-11-03, loc1's reviewer at 22 to 100 % CPU on 2026-10-21, and exit-trace-proof's own `orderly` launch); under ADR-0002 consequence 1 and OQ-462 (4) one such miss costs every run of the session, so a false miss is far dearer than a slow detection, and a bound of about 3.5 times the worst observed latency is taken over a re-fork. (2) The count is started at the fork: the `hello` request is issued immediately after `utilityProcess.fork`, before main awaits anything else, so the `ProcessLink` deadline it already carries is the bound and no second timestamp is kept — this is Advocate B's measurement of the child's own start achieved by Advocate A's mechanism, which is what the code does today at lines 366 and 619 for the run host and 483 and 524 for a service, with the awaits between them removed. (3) Main no longer awaits the run host's `hello` before it builds the first main window: `boundedReady` runs in parallel with the notice store and `MainWindows`, every run-host request made before it resolves (`session.list`, `hooks.summary`, a submit) waits on that readiness and is therefore held at most to the bound, and the composer draft is kept as OQ-462 (3) requires; a miss calls the existing `ProcessLink.end(runHostGoneRefusal('did-not-start'))`, ends the child through `endBeforeMain` and raises OQ-462 (1)'s one persistent `error` notice "The run host did not start", and the ready gate keeps part 12's repair that a refused `hooks.summary` raises no "No model provider is authenticated yet" over the loss notice. REQ-STARTUP-155 is the ground: its 5 s is measured on REQ-STARTUP-159's baseline, but a launch that spends its whole paint budget awaiting a child's answer before any window exists has no margin on any host, and a longer bound on that path would make the requirement worse rather than better, so the bound must leave it. (4) A workspace service that misses 20 s is still refused on the open's own surface (REQ-SHELL-112) with no second notice and is forked again at the next open, as OQ-462 (2) and (4) say. (5) The run host is never forked again, before or after a missed ready: ADR-0002 consequence 1 and OQ-462 (4) reserved that change for the owner, and this ruling does not touch it; the consortium records, for the owner to take up or leave, that consequence 1's three reasons (a run lost mid-iteration, sessions needing repair, a stale lock unreaped) do not reach a host that never answered and held no session, so one re-fork after a missed `hello` only would remove the residual cost without disturbing the rule for a host that ran. REQ-STARTUP-156 is the release-acceptance gate and states no child bound; REQ-SESSION-066 and REQ-NOTIFY-023 govern what follows a real loss and are unchanged; the specification is silent on a child's start bound, so this is an architecture choice and no directive is minted. The build proceeds under this ruling, citing REQ-STARTUP-155, ADR-0002 consequence 1, OQ-462 (1), (3) and (4) as they stand and OQ-462 (2) as revised here. What executes it: the two constants at 20 s and the file's header comment amended; `main/index.ts` issuing each `hello` at its fork and holding run-host requests on the ready promise instead of awaiting before `MainWindows`; in `child-supervision.test.ts`, on the fake clock, a `hello` at 6 s and at 19 s accepted, one at 21 s ended with the notice, and a request issued before the `hello` held and then answered or refused; in `exit-trace-proof`, the `not-ready-*` launches asserting at the new bound and a new `slow-ready` launch with the seam delaying the `hello` by about 8 s asserting the window painted within 5 s, no loss notice and a run that completes, the proof logging the observed `hello` latency from the fork; the first execution reports into ADR-0002 part 12 and appends a row to `first-executions.md`, `06-sequences/01-1` is redrawn with the `hello` off the paint path, and hardening §3.2 row 2 is amended to the new bound. The question returns if the first execution observes any `hello` latency above half the bound.

**Built 2026-11-05 by hrdb (`hrdb-child-ready-and-killed-renderer`).** As ruled: both constants 20 s; each `hello` asked at its fork through `readyAtFork` (`child-supervision.ts`); the launch no longer awaits the run host's `hello`, and every run-host request made before it settles is held on it by `ProcessLink.holdUntil` (`packages/shell/src/process-link.ts`), posted in order with its own bound once it is answered, refused `runHost.notStarted` at once when it is missed; main logs the `hello`'s latency from the fork and the first window's show with where the `hello` stood; the seam gains `slow` (`holdMessagesFor`, `packages/platform/src/utility-process.ts`). Pinned by `child-supervision.test.ts` (a `hello` at 6 s and 19 s accepted, 21 s missed with the notice, a request before it held and answered, and held and refused), `process-link.test.ts`, `utility-process.test.ts`, and `exit-trace-proof`'s `not-ready` launches at 20,000 ms and new `slow-ready` launch. Measured on Windows 11 ARM64 (the first execution in [ADR-0002 part 12](../../../architecture/adr/0002-process-topology/12-first-execution-2026-11-03-a-child-ends-on-its-own.md)): the `hello` latency in every launch the seam did not delay was 297 to 569 ms, under half the bound, so the question does not return; `slow-ready` showed its window about 0.2 s after the fork, accepted the `hello` at about 8.3 s, held and then acknowledged the open's 5 s `workspace.opened` hand-off, raised no notice and completed a run. One reading the ruling named could not be taken as written: the driver's endpoint opens only after the launch's open settles, which waits on the run host, so no driver request can precede the `hello`; the launch's own hand-off is the held request the proof reads.

**OQ-475 — Does an error React recovered from on its own owe the person a notice, or only a line in the log?** *(REQ-NOTIFY-001, REQ-NOTIFY-003, REQ-NOTIFY-023, PD-MONITOR-002. Raised 2026-11-04 by [R-091](../../../product/requests.md#r-091)'s hardening bundle B2, building [hardening §3.2 row 4](../../../architecture/hardening/02-the-findings.md#32-failure-handling-outside-main); numbered from the bundle's range OQ-475 – OQ-476.)*

**What is open.** Every window's root is now made with React's three error options, and each reports through `notice.report` (`apps/desktop/src/renderer/render-failure.tsx`). Two are failures the person sees — an error the window's boundary caught (its fallback is drawn) and one no boundary caught (the window's tree is removed) — and REQ-NOTIFY-003 makes a failure a persistent notice. The third, `onRecoverableError`, is React's report of an error it recovered from by drawing the tree again: the window looks as it did and nothing was lost. It is none of REQ-NOTIFY-003's three (a failure, a refusal, an outcome carrying a recovery action), so the specification asks no notice of it; but a renderer has no path to main's application log other than `notice.report`, and a recovered error that is only written to the window's console is the silence this bundle was built to end. The specification has no word on a renderer's own diagnostics.

**What the build proceeds under.** A persistent notice at `warning`, titled "This window recovered from a drawing error", its detail the error and both stacks, and so ONE `warning` line in main's log (`RENDER_RECOVERED_TITLE`, `renderFailureReport`); the two failures at `error`, as the hardening plan asks.

**What decides it.** A ruling on whether a recovered error is shown to the person at all — the notice at `warning`, at `info`, or none — and, if none, whether the renderer gains a log-only path to main (a command that writes one line and raises nothing), which would be a new member of the command union.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended no notice at any severity and one `warning` line in main's log through a new log-only command, the `caught` and `uncaught` paths unchanged and no directive; Advocate B (the system's lens) recommended the same line and the same command, with the recovered path given its own dedupe set and its own per-document cap so it never spends the failure budget, and no directive. Ruled with both, folding in the system's advocate's separate cap. An error React recovered from on its own is shown to no one: it is none of REQ-NOTIFY-003's three (a failure, a refusal, an outcome carrying a recovery action), and that requirement's last sentence says such an event "may be acknowledged transiently and reported nowhere else"; it is none of REQ-NOTIFY-001's six conditions either, since the window reached no state the person could tell apart. The decisive ground against the built `warning` is REQ-NOTIFY-024: a publication replaces whatever notice was current, whichever session either concerns, and the replaced notice does not return, so a redraw nobody saw would push a refusal, a run's failure or this window's own `caught` notice out of the one slot; and REQ-NOTIFY-268 would then write the redraw into the timeline of whatever run happened to be focused, which is the wrong owner of the fact. An `info` notice escapes 268 and not 024, so it fails on the same ground, and REQ-NOTIFY-023 obliges no notice to exist for a diagnostic. The silence the hardening bundle was built to end (R-091, hardening §3.2 row 4) is ended in the log: the renderer gains a log-only path to main, a new member of the command union that carries the two parts `renderFailureReport` already builds (the error, the window role, the component stack and the script stack, through the one redaction pass of REQ-TOOLS-171 before it leaves the renderer and again in main, bounded by `RENDER_FAILURE_DETAIL_MAX` and the limits of `contracts/src/limits.ts`) and no severity field; main writes it as exactly ONE `warning` line, the level PD-MONITOR-002's first execution fixed for a degraded, uninterrupted condition, kept at the default threshold, and touches neither the notice store nor the record of REQ-NOTIFY-268. The name is the builder's within CONTEXT-MAP's words and does not take the `diagnostics.` prefix, which REQ-SHELL-163's capture owns (`window.recovered`, say). `onRecoverableError` sends that command and never `notice.report`, with its own dedupe set and its own per-document cap, so a fault React retries cannot exhaust `RENDER_FAILURE_REPORTS_MAX` before a real failure needs it; `onCaughtError` and `onUncaughtError` stay as built, persistent `error` notices under REQ-NOTIFY-003; `RENDER_RECOVERED_TITLE` and the `recoverable` message are withdrawn. ADR-0049 decision B is not touched — a renderer still raises a persistent notice only by asking main — and gains a dated note that a renderer asks main for a log line by a sibling path that raises nothing. No requirement is departed from and no directive is minted: REQ-NOTIFY-003 already permits the silence, REQ-NOTIFY-024 and REQ-NOTIFY-268 are kept rather than displaced, and the line falls within PD-MONITOR-002's levels and threshold; the ruling fills the record's silence on a renderer's own diagnostics and stands in this entry. What executes: the command, its preload exposure and its handler by the "a command" seam of `04-seams.md`, the seams and process views and `views/README.md`'s date in the same commit, the comment in `render-failure.tsx` and hardening §3.2 row 4 citing this ruling; `render-failure.test.ts` asserting that a recovered error sends the new command and never `notice.report` and that its cap leaves the failure budget whole, a handler test asserting one `warning` line, `notices.current()` unchanged and no REQ-NOTIFY-268 entry, and the contracts property test covering the kind by generation; `exit-trace-proof`'s `render-fault` launch stays the caught path's evidence and its record states that the recovered path is proven at unit level, since a client-only root offers no seam that throws once and then draws. Reopened by an autopsy, live-run or `debug-ui` finding of a recovered error repeating in one window while the person was told nothing, which would reopen whether a repeat owes a notice; or by the owner's request to see recovered errors on screen.

**Built 2026-11-05 by hrdb.** As ruled: `window.recovered`, one `warning` line, no notice; read in the built app; [first-executions part 37](../../../architecture/first-executions/37-the-register-36.md).

**OQ-476 — Is a main window whose renderer was `killed` owed a reload or a notice, now that every other loss is reloaded and told?** *(REQ-STARTUP-161, REQ-SHELL-020, REQ-NOTIFY-001, REQ-NOTIFY-003, ADR-0055, PD-MONITOR-002. Raised 2026-11-04 by [R-091](../../../product/requests.md#r-091)'s hardening bundle B2, building [hardening §3.2 row 5](../../../architecture/hardening/02-the-findings.md#32-failure-handling-outside-main); numbered from the bundle's range OQ-475 – OQ-476.)*

**What is open.** `MainWindows` reloads a main window once within 60 s when its renderer is lost and raises a persistent error notice, for every reason Electron gives but `clean-exit` and `killed`, as the hardening plan asks (`RENDERER_ENDS_NOT_RELOADED`, `apps/desktop/src/main/main-windows.ts`). `killed` is what Chromium reports for a renderer ended from outside with an ordinary exit status: on Windows Node's `process.kill` and Task Manager's End task, both `TerminateProcess` with status 1 (measured on Windows on 2026-10-20 and again 2026-11-04 by `exit-trace-proof`), and, by Chromium's reading of a termination status and not measured here, a `SIGKILL` on Linux, the out-of-memory killer's among them. Such a window is left as it was before this bundle: open and blank, with main's `RENDERER GONE (killed, exit 1)` line at `error` and nothing said to the person. Whether a person ending the renderer means the window to stay blank, and whether the out-of-memory killer's end is a loss to recover from, the specification does not say.

**What the build proceeds under.** `killed` and `clean-exit` are neither reloaded nor told; every other reason is (`crashed`, `oom`, `abnormal-exit`, `launch-failed`, `integrity-failure`, `memory-eviction`).

**What decides it.** A ruling on `killed`: left as it is, told by a notice without a reload, or reloaded within the same bound as a crash.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended that `killed` be treated as a loss to recover from, reloaded once within `RENDERER_RELOAD_BOUND_MS` and told by the same persistent notice as a crash, with `clean-exit` alone left silent; Advocate B (the system's lens) recommended the same, rejecting "told without a reload" because the notice surface is drawn by the renderer that is gone, so a notice into a blank window reaches no one. Ruled: a main window whose renderer Chromium reports `killed` is reloaded within the same bound as a crash and told in the same way; `RENDERER_ENDS_NOT_RELOADED` shrinks to `clean-exit` alone. The grounds are the record's, and no requirement's words are departed from. REQ-NOTIFY-003 republishes every failure as a persistent notice, and a window left open and blank with nothing said is a failure of that window published nowhere the person can read: main's `RENDERER GONE (killed, exit 1)` line is kept at `error` under PD-MONITOR-002, but it is a log line, not a notice. REQ-NOTIFY-001 requires that any two conditions a workflow can reach present differently, and a blank window is indistinguishable from one still loading. REQ-STARTUP-161 and ADR-0055 settle that the window, its workspace, its followed session and its presenter registration are main's and outlive the renderer, so the reload creates no second instance, touches no run, and hands the followed session back as a held session focus (REQ-SHELL-020) exactly as the crash path already does. The premise the build proceeded under — `RENDERER_ENDS_NOT_RELOADED`'s "a renderer something ended on purpose" — is one the code cannot know: `killed` is Chromium's reading of `TerminateProcess` with an ordinary status on Windows (Task Manager's End task and `process.kill` alike, measured by `exit-trace-proof` on 2026-10-20 and 2026-11-04) and of a `SIGKILL` on Linux, the out-of-memory killer's among them, and main never ends its own renderers (no `forcefullyCrashRenderer` or kill of a renderer in `main-windows.ts` or `index.ts`; `exit.ts` marks `killed` as main's own only for the children it ends at quit). An invariant the code can guarantee must hold for every cause sharing the reason: "no main window is left blank and untold, except after an orderly end, within the reload bound, or once the quit has begun" does; "left blank because someone meant it" does not. A person who wants the window gone has the window's own close; ending the renderer process is no product gesture whose intent the product owes respect to, and the existing bound already makes a repeating external end finite — the second loss within 60 s leaves the window as it is, with the notice saying so.
