# Library, Artifacts, and Improvement Proposals — 11. Rollback of an applied improvement run

Part 3 of 7 of [domain 14](../14-library-artifacts-improvements.md), which indexes every part. Defines REQ-LIBRARY-067 – REQ-LIBRARY-101.

### 11. Rollback of an applied improvement run

**REQ-LIBRARY-067** — Improvement checkpoints MUST live under the dedicated Git ref namespace `refs/rotaris/improvements/<artifact_id>/<sequence>`, disjoint from the session-checkpoint namespace (`refs/rotaris/checkpoints/...`), so that neither feature's pruning can delete the other's refs.

**REQ-LIBRARY-068** — Checkpoint kinds MUST be `pre_improvement` (the state a rollback restores), `applied` (the state the run left, used to measure later user changes), and `pre_rollback` (safety point so an undo of the undo works). Each checkpoint record carries: `sequence` (≥ 0), `ref`, `commit`, `kind`, `created_at`, `files` (paths changed, display only), `proposal_ids` (proposals the guarded run was about to apply), and `tree_root` (the Git top-level it was taken against, enabling cross-worktree refusal).

**REQ-LIBRARY-069** — A workspace with nothing uncommitted MUST still receive a rollback point: the checkpoint records the state the tree is currently in, is registered under the artifact's own ref (REQ-LIBRARY-067), and a later rollback restores that state. The one case in which no checkpoint is produced is a repository holding neither a commit nor any file to record. That case MUST NOT be treated as an error and MUST be reported as the reason `The workspace has no committed content and no files to record, so no rollback point could be taken.`

**REQ-LIBRARY-070** — Before an improvement run edits the workspace, the artifact MUST hold exactly one usable rollback point. When it already holds a `pre_improvement` checkpoint that no rollback has consumed — that is, while `rolled_back_at` is null — that checkpoint MUST be kept and reused rather than superseded; a second attempt after a partly failed run therefore restores the state that existed before the first attempt. Once `rolled_back_at` is set, the next run MUST take a fresh checkpoint. A workspace outside a Git working tree MUST NOT block or fail the run: the run proceeds and its outcome carries the reason `<tree> is not inside a Git working tree, so no rollback point could be taken for this improvement run.`

**REQ-LIBRARY-071** — An artifact retains at most 10 checkpoints by default. A retained checkpoint MUST stay restorable for as long as it is retained, whatever happens to branches, resets, or repository housekeeping in the meantime; only retention pruning may remove one. When the limit is exceeded, the oldest checkpoints MUST be dropped first and their refs deleted with them, except that the newest `pre_improvement` checkpoint is never dropped, so an artifact cannot lose its rollback point to pruning. Sequence numbers MUST be unique within an artifact and MUST never be re-issued: a new checkpoint MUST NOT take a number already used by any ref under `refs/rotaris/improvements/<artifact_id>/`, even when the stored artifact itself records no checkpoint at that number. The limit of 10 is fixed by this document and MUST NOT be exposed as a configuration key: the configuration surface of this domain is exactly the three keys of section 6, and no other key of any scope changes checkpoint retention.

**REQ-LIBRARY-072** — Asking what a rollback would do MUST have no side effects: it MUST NOT touch the working tree, MUST NOT write to the store, and MUST NOT raise. Every refusal comes back as a finished sentence ready to display, and those sentences MUST be: `No improvement artifact <id> exists in this workspace.` when the artifact is unknown; `No rollback point was recorded for improvement <id>.`, or the non-Git reason of REQ-LIBRARY-070, when there is no usable point; `That rollback point was taken in <A>, not in <B>. Restoring it here would overwrite a working tree it never described.` when the recorded tree differs from the current one; `Improvement <id> has a recorded rollback point but its Git snapshot is gone, so it can no longer be rolled back.` when the recorded snapshot no longer resolves; and a sentence describing a failed repository inspection. A preview that succeeds MUST report every path that differs between the working tree and the rollback point, each labelled with what the rollback would do to that path stated from the user's side, together with the paths carrying work done since the run (REQ-LIBRARY-073) and the dirty-blocked reason when one applies. The label vocabulary is closed and holds exactly three values: `delete` for a path the run created, which the rollback removes; `restore` for a path the run deleted, which the rollback brings back; and `revert` for a path the run modified, which the rollback returns to the content the checkpoint recorded. Every previewed path carries exactly one of those three labels. The sentence reporting a failed repository inspection MUST name the improvement, convey that the workspace's Git repository could not be inspected and so no rollback can be previewed, and carry the reason the inspection gave; its wording is left to the implementation.

**REQ-LIBRARY-073** — Work done after an improvement run MUST be measured against the newest checkpoint that still resolves and whose `kind` is `applied` or `pre_rollback`. Neither the current HEAD nor the pre-run checkpoint may serve as that baseline: an edit the run itself made MUST NOT be reported as work done since the run. When the artifact has no resolvable post-run checkpoint, the rollback MUST report nothing at risk and MUST NOT block on that ground, and a working tree identical to the newest post-run checkpoint MUST likewise report nothing at risk. The search MUST consider every checkpoint the artifact still retains and MUST NOT be narrowed further: retention already bounds that list to at most 10 records (REQ-LIBRARY-071), so the search is bounded without a second limit, and a post-run checkpoint that is still retained can never be passed over because it is old.

**REQ-LIBRARY-074** — The dirty refusal MUST convey how many changes made since the improvement run would be overwritten, name at most the first 5 of those paths and state how many further paths there are, and tell the user that the rollback can be repeated with an explicit override that overwrites them; its wording is left to the implementation. That override (REQ-LIBRARY-170) bypasses only this one check and nothing else.

**REQ-LIBRARY-075** — Rollback MUST proceed in this order: load → point present → tree match → ref resolves → diff and dirty check → record a `pre_rollback` safety checkpoint first (failure here blocks with "Could not record a safety checkpoint before the rollback: <reason>" — an irreversible rollback is forbidden) → restore the tree → set the applied proposals back to `pending_review` and stamp `rolled_back_at`. Rollback never raises; every refusal returns a not-restored result with a blocked reason and an untouched tree.

**REQ-LIBRARY-076** — Post-restore status reversal MUST cover only proposals named in the checkpoint's `proposal_ids` that are currently `approved`; an older checkpoint with no recorded ids falls back to reverting every still-approved proposal. If persisting the reversal fails after the tree is restored, the result reports restored-with-warning: "The workspace was rolled back, but the reversal could not be recorded on improvement <id>: <err>. Its proposals still read as approved even though their changes are gone."

**REQ-LIBRARY-077** — After a restore, every path the checkpoint covers MUST hold the content that checkpoint recorded: a path the run created is gone, a path the run deleted is present again with its original content, and a path the run modified reads as it did before the run. The rollback MUST itself be undoable from the `pre_rollback` safety checkpoint of REQ-LIBRARY-075. Restoration goes through the repository, so the repository's own line-ending normalisation applies to restored files exactly as it does to session-checkpoint restores. The canonical guarantee is the normalised one: a restored path MUST hold exactly the content a fresh checkout of that checkpoint would produce in this working tree under the repository's configured normalisation, not necessarily the same bytes the path held before the run. Where those differ, the difference is a property of the repository's own configuration rather than of the rollback, and the product MUST NOT report it as a rollback anomaly.

**REQ-LIBRARY-078** — The tree-mismatch comparison MUST compare fully resolved paths, case-insensitively on Windows.

**REQ-LIBRARY-169** — Rolling an applied improvement run back MUST be reachable from the desktop interface, and from nowhere else. The improvement-artifact detail of REQ-LIBRARY-167 MUST carry a "Roll back" action, enabled exactly when that artifact has a rollback point per REQ-LIBRARY-012 and disabled otherwise with an explanation of why. Activating it MUST first compute the side-effect-free preview of REQ-LIBRARY-072 and show the result in a modal dialog before anything is written: given a preview that would change files, the dialog lists every previewed path in ascending path order, each with its label from the closed vocabulary of REQ-LIBRARY-072; given a preview that would change nothing, the dialog says so instead of listing paths; and given work done since the run (REQ-LIBRARY-073), the dialog additionally warns how many such changes would be overwritten and names those paths. Given a preview that came back refused, the dialog MUST show that refusal's sentence, offer no way to proceed, and leave the working tree and the stored artifact untouched.

**REQ-LIBRARY-170** — A rollback MUST NOT start until the user confirms it in the dialog of REQ-LIBRARY-169. The dialog's choices are a confirming action and Cancel, with Cancel selected by default; choosing Cancel MUST change nothing in the store, nothing in the working tree and nothing on screen. When the preview is blocked only by work done since the run, the dialog MUST additionally offer an explicit, separately activated override that proceeds anyway; that override is the force choice of REQ-LIBRARY-074 and REQ-LIBRARY-163, it MUST be off unless the user turns it on for this one rollback, and it MUST bypass only the dirty-tree check. When the preview is blocked for any other reason, no override may be offered.

**REQ-LIBRARY-171** — A rollback started from the desktop MUST report its outcome to the user rather than finish silently. A completed rollback MUST post a persistent success notice conveying which improvement was rolled back, how many files changed, how many proposals returned to `pending_review` and which they are when any did, and that a safety checkpoint now holds the pre-rollback state (REQ-LIBRARY-075). A refused rollback MUST post an error notice carrying the refusal's own displayable sentence (REQ-LIBRARY-072) and MUST leave the working tree and the stored artifact exactly as they were. A rollback that restored the tree but could not record the status reversal MUST post a warning notice carrying the discrepancy of REQ-LIBRARY-076 — the tree is already restored, so this is never reported as a failed rollback. In every case the improvement-artifact detail and the proposal surfaces MUST re-read the stored state afterwards (REQ-LIBRARY-164). The wording of these notices is left to the implementation.

### 12. Withdrawn command-line surface

**REQ-LIBRARY-079** — *Withdrawn.* The product is a single graphical desktop application with no command-line surface, so there is no command group to expose; inspecting the workspace's improvement artifacts is carried by REQ-LIBRARY-166 and REQ-LIBRARY-167, and rolling an applied improvement run back by REQ-LIBRARY-169 through REQ-LIBRARY-171.

**REQ-LIBRARY-080** — *Withdrawn.* There is no process exit status to define; the outcomes the exit codes distinguished — the action completed, the user declined the confirmation, the rollback was refused or failed, the artifact does not exist — are reported to the user by REQ-LIBRARY-167, REQ-LIBRARY-170 and REQ-LIBRARY-171.

**REQ-LIBRARY-081** — *Withdrawn.* There is no text listing to format; the same per-artifact information — identity, generation time, whether a rollback point exists, and the per-status proposal counts — is presented by the desktop improvement-artifact list of REQ-LIBRARY-166.

**REQ-LIBRARY-082** — *Withdrawn.* There is no text detail view to format; the artifact detail it printed is carried by REQ-LIBRARY-167 and its recorded-version history by REQ-LIBRARY-168.

**REQ-LIBRARY-083** — *Withdrawn.* There is no command invocation to parse and no printed preview to format; the rollback preview, including the per-path actions and the warning about work done since the run, is carried by REQ-LIBRARY-169.

**REQ-LIBRARY-084** — *Withdrawn.* There is no terminal prompt and no standard input to read; rollback confirmation and the deliberate override of the dirty-tree refusal are carried by REQ-LIBRARY-170.

**REQ-LIBRARY-085** — *Withdrawn.* There is no success output to format; what a completed rollback must tell the user is carried by REQ-LIBRARY-171.

**REQ-LIBRARY-086** — *Withdrawn.* There is no command-group output contract to bind, the command group having been withdrawn with REQ-LIBRARY-079; the cross-surface obligation it qualified — that the surfaces must agree about the stored state while each presents it in its own form — is stated by REQ-LIBRARY-164.

### 13. Session artifact store (agent reports and published deliverables)

**REQ-LIBRARY-087** — The per-session artifact store MUST hold, for each artifact, one full record together with a metadata entry in an index ordered by creation time, both kept in the durable store the application keeps for the workspace. A record and its index entry MUST be written together as one indivisible step, so no reader ever finds a record without its index entry or an index entry without its record. Each artifact's Markdown document — the rendered form REQ-LIBRARY-090 fixes, carrying that artifact's body — MUST be kept **on disk as a file the record references and never holds inside itself**: a body may be arbitrarily large, and the document exists so that a person or another tool can read the artifact without this application. That file is one of the artifact bodies REQ-SESSION-002 places beside the session's stored record, which is the single definition of where those files live and of what may live there; this domain names no location of its own and adds no fourth kind of per-session file. Every write MUST be atomic as seen by a reader on the terms of REQ-LIBRARY-043, mutations MUST be serialized within the application (REQ-LIBRARY-158), and the store MUST outlive loop iterations so earlier-phase findings remain available to later children.

**REQ-LIBRARY-088** — An artifact record MUST carry: `id`, formed as `art_` followed by 8 base62 characters; `slug`, kebab-case, at most 64 characters, made unique within the session by appending `-2`, `-3`, and so on; `title`; `kind`, one of `child_report`, `agent_published`, `system`; `source_task_id`; `canonical_name`; `source_persona`; `status`, which is `succeeded` unless set otherwise, `published` for an agent publish, and the report's own status for a materialised child report; `summary`; `key_findings`; `highlight_paths[]`; `snippets[]`; `edited_files[]`; `created_files[]`; `tags[]`; `supersedes` and `superseded_by`; `created_by`; `consumed_by[]`; the ids linking the record to its timeline entry and to its conversation, carried as `timeline_event_id` and `conversation_id`, both nullable and both null until the link exists; `importance`, which MUST be `high` when the record is a child report whose status is anything other than `succeeded` and `normal` in every other case; `created_at`; `edited_at`, null until a person edits the body; and `body_markdown`. `status` MUST hold a value from a closed set formed in exactly one way and in no other: every member of the child-report status vocabulary REQ-ORCH-112 defines, which is the product's single definition of that vocabulary and which this requirement does not restate and does not narrow — a materialised child report carries the report's own status unchanged, so every value a report can carry is a value an artifact record can carry — together with `published`, which only an agent publish produces (REQ-LIBRARY-093) and which no child report ever carries. The artifact status set is therefore that vocabulary plus one, it widens exactly when REQ-ORCH-112's widens, and a value outside it MUST fail validation and be skipped by hydration (REQ-LIBRARY-091). The "ready" of REQ-LIBRARY-136 is exactly `succeeded` or `published`; every other member is the unsuccessful group the sibling-index ordering of REQ-LIBRARY-097 places first.

**REQ-LIBRARY-089** — Artifact tags MUST come from a closed vocabulary of exactly six values: `research`, `planning`, `implementation`, `review`, `verification`, `errors`. A publish carrying any other tag MUST be refused whole — no record is created, no file is written, and no partial state is left behind — with an error that begins `Invalid tag(s): `, names the rejected tags, and continues `Valid tags are: ` followed by the six permitted values in the order given here. A supplied tag MUST be normalised before it is matched: surrounding whitespace is stripped and the remainder is compared case-insensitively, so ` Research ` is the tag `research` and is accepted. A tag that does not match after that normalisation is rejected, and the error MUST name it as the user supplied it rather than in its normalised form. A tag supplied more than once MUST be collapsed to one occurrence rather than rejected — a duplicate expresses no ambiguity, so refusing the publish over it would be gratuitous — and the record MUST store each tag in its normalised form, preserving the order of first occurrence. This requirement is the product's single definition of the artifact tag vocabulary and of the normalisation, duplicate collapsing and refusal that go with it: a document that publishes or accepts artifact tags cites this identifier rather than restating the set. A surface needing a new tag extends this list rather than admitting a value elsewhere.

**REQ-LIBRARY-090** — Each artifact MUST have a Markdown sidecar that opens with YAML frontmatter carrying `id`, `slug`, `title` (JSON-quoted), `kind`, `status`, the record's timestamps, and — only when the record has them — its source ids, its tags, and its supersession links. The frontmatter is followed by `# <title>` and then by these sections in this order: Summary; Key Findings; Highlight Paths, one line per path formatted `` - `path` — reason ``; Snippets, one fenced code block per path; Edited Files, one line per file formatted `` - `path` (change_type) ``; Created Files. A section with no content MUST be omitted entirely — no heading, no placeholder line — so a reader never has to tell an empty section from an absent one, and a record carrying only a body renders as frontmatter, title, and nothing else. The order of the sections that are present MUST still be the order given here. The frontmatter's optional members follow the same rule: `timeline_event_id`, `conversation_id`, the other source ids, `tags`, and the supersession links are written only when the record holds them.

**REQ-LIBRARY-091** — Store hydration MUST tolerate: a session whose store holds no artifacts at all (zero artifacts), an index that cannot be read (warning, zero artifacts), an index entry whose record cannot be found (warning, skipped), an artifact whose Markdown document (REQ-LIBRARY-087) cannot be read — which leaves the record itself usable and is reported by the surface that needed the body (REQ-LIBRARY-134) rather than dropping the artifact — and per-record validation failures (skipped). Hydration never raises. A store that cannot be opened at all is a different condition and is not hydration's to absorb: the session does not start, and that refusal is stated where the store is opened (REQ-SESSION-089).

**REQ-LIBRARY-092** — Materializing a child report MUST be idempotent keyed on the task id (falling back to the canonical agent name only for a record that carries no task id, so two children with different task ids never share or overwrite one artifact — accepted amendment 2026-09-29, OQ-113): a re-materialization updates in place, preserving id, slug, title, creation time, supersession links, consumers, and edit timestamp, instead of duplicating. Every terminal child report is materialized (kind `child_report`), and a timeline diagnostic event of kind `artifact_published` is recorded with the artifact id linked back onto the record.

**REQ-LIBRARY-093** — Publishing MUST create a record whose `kind` is `agent_published` and whose `status` is `published`, whose `body_markdown` is the submitted body unchanged, whose `key_findings` is that same body, and whose `summary` is the body's first line truncated to at most 280 characters. `created_by` MUST name the publishing agent instance by its canonical name rather than by its persona, so two instances sharing a persona stay distinguishable in every artifact listing. A publish that names a supersedes target by id or by slug MUST mark that target superseded by the new record and MUST record the reverse link on the new record (REQ-LIBRARY-095).

**REQ-LIBRARY-094** — Body editing MUST overwrite only the Markdown body and stamp `edited_at`; everything else on the record — its slug, its title, its tags, its snippets, and its source ids — stays immutable through every editing surface. **REQ-LIBRARY-096** — Listing MUST hide superseded artifacts by default, require ALL given tags when tags are supplied, and sort ascending by creation time; lookup accepts id or slug; marking an artifact consumed appends the actor at most once and persists.

**REQ-LIBRARY-097** — A newly created agent MUST be given a `PRIOR SIBLING ARTIFACT INDEX` context block listing the session's existing artifacts, one artifact per line, each line carrying that artifact's slug, id, persona, status, and its summary truncated to at most 160 characters. The block MUST NOT exceed 10,000 characters; when not every artifact fits, the block MUST end with a marker stating how many were left out and naming the `artifact_list` tool as the way to reach them. Artifacts whose status is neither `succeeded` nor `published` — every unsuccessful member of the set REQ-LIBRARY-088 forms, which this requirement does not enumerate — MUST be ordered ahead of artifacts whose status is `succeeded` or `published`, so a failure is never the entry elided while a success survives. Within each of those two groups the ordering MUST be newest first by creation time, ties broken by ascending artifact id, so the ordering is total and two readings of the same session produce the same block. Artifacts are dropped from the tail of that total order until the block fits. The elision marker MUST state how many artifacts were left out and MUST name the `artifact_list` tool as the way to reach them; its wording is left to the implementation.
