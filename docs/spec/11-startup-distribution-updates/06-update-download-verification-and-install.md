# Application Startup, Distribution, and Updates — Update download, verification, and install strategies

Part 6 of 10 of [domain 11](../11-startup-distribution-updates.md), which indexes every part. Defines REQ-STARTUP-122 – REQ-STARTUP-181.

### Update download, verification, and install strategies

**REQ-STARTUP-122** — The install sequence SHALL be strictly: fetch the `SHA256SUMS.txt` published with that release together with the signature published over it → verify that signature → parse the manifest, and parse it only after the signature has verified → stream the asset into a fresh temporary staging directory (name prefixed `rotaris-update-`) → verify → apply — never proceeding past a failure, and reporting every failure as a single sentence. The signature is checked before the manifest is parsed and before any asset is fetched, so a manifest this build cannot attribute to a publisher it trusts costs the user no download and reaches no parser (REQ-STARTUP-167).

> **Narrowed by [`PD-STARTUP-008`](../../product/directives/pd-startup-008.md#pd-startup-008), 2026-10-22.** The sequence pauses after the digest comparison: the verified download
> is kept as the pending update in per-user storage, not a fresh temporary directory (REQ-STARTUP-171), is verified again
> before it is applied (REQ-STARTUP-172), and is applied at the next start or by `Restart now` (REQ-STARTUP-173,
> REQ-STARTUP-174). The order up to the digest — the signature before the manifest is parsed and before any asset byte —
> still governs.


**REQ-STARTUP-123** — Verification SHALL enforce: a release publishing no checksum manifest is refused with `release <version> publishes no checksum file; refusing to install an unverifiable download`; a failed manifest fetch fails with `could not read the checksum file: HTTP <status>`; a downloaded file for which the manifest lists no hash is removed, reporting `no published hash for <name>; the download was discarded`; a hash mismatch deletes the file with `<name> does not match the published hash (expected <e>, got <a>); the download was discarded and nothing was installed`; comparison is case-insensitive.

Verification SHALL further enforce, before the manifest is parsed and before any asset is fetched (REQ-STARTUP-122), three signature outcomes, each of which refuses the install and leaves nothing downloaded: a release publishing no signature over its manifest is refused, conveying that the release publishes no signature for its checksum file and that an update whose publisher cannot be established is not installed; a signature that cannot be fetched fails, conveying that the signature could not be read and carrying the transport status, in the same shape as the manifest-fetch failure above; and a signature that does not verify against a key this build carries (REQ-STARTUP-167) is refused, conveying that the checksum file was not published by a holder of a key this build trusts, that nothing was downloaded and nothing installed, and that the release is to be obtained from the release page instead. The wording of these three is left to the implementation. The four hash outcomes above keep the exact sentences they state, which REQ-STARTUP-120 carries as the technical detail of a failed install.

No refusal in this requirement SHALL be overridable: there is no confirmation, setting, retry, or interface path by which an update whose manifest signature did not verify, or whose asset digest did not match, is installed anyway.

Together the two checks establish both what was downloaded and who published the manifest that names it. The digest comparison detects a corrupted or incomplete transfer. The signature establishes that the manifest came from a holder of a key this build was built to trust, rather than merely from the same connection the download came from — which is what the manifest alone established before REQ-STARTUP-167. Neither check establishes anything about the artifacts themselves carrying a code signature, which by design they do not (REQ-STARTUP-021, REQ-STARTUP-023).

**REQ-STARTUP-124** — Download staging SHALL stream in 1 MiB chunks (matching the hashing granularity), reporting `(bytes_so_far, claimed_total)` with the total possibly 0; a write failure deletes the partial file and fails with `could not write the download to <path>: <error>`.

**REQ-STARTUP-125** — The apply step SHALL be selected by installation flavour (REQ-STARTUP-106), not by operating system, and SHALL produce these observable results. In every case the target is the artifact REQ-STARTUP-106 identifies and never the running image: where the running image is a preparation the artifact made of itself (REQ-STARTUP-165), the replacement still lands on the artifact, so that the file the user holds is the one that becomes the new version and the preparation is left to be superseded on the next launch under REQ-STARTUP-165 (b). **AppImage** → the verified file SHALL first be placed next to the target as a hidden sibling named `.{name}.update` on the same filesystem as the target, then moved onto the AppImage path and left with mode `0755`; the replacement SHALL succeed while the application that is being replaced is still running; outcome replaced, message `The update is installed. Restart Rotaris to run it.`; on failure the sibling file SHALL be removed and the step SHALL report `could not replace <target>: <error>`; whether it succeeded or failed, no `.{name}.update` file and no staging directory SHALL remain. **Windows portable** → the verified file SHALL be placed beside the target, any previous backup SHALL be deleted, the target SHALL be renamed to `<name>.old`, and the new file SHALL then be moved into the target path; the replacement SHALL succeed while the application being replaced is still running, the target being the artifact rather than the file the process is executing; if that final move fails, the backup SHALL be renamed back to the target path before the step reports `could not install the update at <target>: <error>`, so the executable present after a failure is the original one; the `<name>.old` file SHALL remain until a later launch removes it (REQ-STARTUP-115); outcome replaced, with the same message as the AppImage case. Where the artifact sits on media that cannot be written — read-only or removed since launch — the step SHALL fail reporting that it could not install the update at the target, change nothing anywhere, and leave the running application and its preparation exactly as they were. **Windows installer** → the verified setup executable SHALL be started as a process that survives the application exiting, and the application SHALL make no edit of its own to the installed tree; outcome handed-off with quit required, message `Rotaris will close so the installer can replace it.`; if the process cannot be started the step SHALL report `could not start the installer at <path>: <error>`. **macOS** → the verified disk image SHALL be mounted and its mounted volume SHALL be opened in the platform's file browser so the drag-to-install of REQ-STARTUP-022 can be repeated; the installed application bundle SHALL be left byte-for-byte unchanged and SHALL never be replaced automatically; outcome handed-off, message `The verified disk image is open. Drag Rotaris to Applications, then reopen it.` **No released-artifact target** → the step SHALL fail with `this Rotaris was not installed from a released artifact` and change nothing on disk.

> **Narrowed by [`PD-STARTUP-008`](../../product/directives/pd-startup-008.md#pd-startup-008), 2026-10-22.** The installed flavour's installer is started without its pages, at the
> next start or by `Restart now`, and the updated installation is started when it completes (REQ-STARTUP-173). The
> portable's backup and replacement keep their end state, but the artifact's path names a complete executable at every
> instant (REQ-STARTUP-176), so the order "renamed to `<name>.old`, then moved in" no longer governs where it leaves the
> path empty. The AppImage, macOS and no-target cases still govern.


**REQ-STARTUP-126** — Invariant: not one file of the existing installation is moved or modified before the replacement has been fetched in its entirety and verified; should any stage fail, what is installed remains byte-for-byte what it was before the attempt.

**REQ-STARTUP-127** — With a hand-off strategy the ordering is reversed — the running application quits or yields to another installer before the replacement is actually in place — and the message shown SHALL describe that hand-off rather than telling the user to restart.

> **Narrowed by [`PD-STARTUP-008`](../../product/directives/pd-startup-008.md#pd-startup-008), 2026-10-22.** The installed flavour's ready notice does tell the user to restart
> (`Restart now`, REQ-STARTUP-174) before its hand-off. Every other hand-off message still governs.


**REQ-STARTUP-128** — Exactly one version, the desktop application's, is compared against the feed, and exactly one artifact, the desktop one, is downloaded; because a release carries a single product version (REQ-STARTUP-158), no other version the product reports can disagree with it.

### Background download, the pending update, and the next-start apply

> **Decided, not derived.** Every requirement in this subsection was minted on 2026-10-22 from the owner's request
> [R-084](../../product/requests.md#r-084), at the owner's explicit ask for requirement identifiers; none was derived from the
> behavioural target, and none is evidence about it. [`PD-STARTUP-008`](../../product/directives/pd-startup-008.md#pd-startup-008) states which
> derived requirements these displace, per identifier, and each of those carries its back-pointer. A clause marked
> *reserved* names an owner decision (`UD-n`) in [`../architecture/background-update-plan.md`](../../architecture/background-update-plan.md)
> §6 that is not taken; no build implements a reserved clause before it is. *Recorded, not built: no first execution.*

**REQ-STARTUP-169** — **The download starts on its own.** On a build classified updatable (REQ-STARTUP-106), when the check of REQ-STARTUP-114 finds an update REQ-STARTUP-107 offers, the product SHALL begin downloading that release's asset with no user action, provided that version is not the waved-off version of REQ-STARTUP-116, no pending update (REQ-STARTUP-171) of that version or a newer one exists, and no cancellation of that version is in force (REQ-STARTUP-170). The download SHALL follow REQ-STARTUP-122's order up to and including REQ-STARTUP-123's digest comparison: the manifest and its signature fetched, the signature verified against a key the running build carries before the manifest is parsed and before any byte of the asset is requested (REQ-STARTUP-167), the asset streamed in 1 MiB chunks (REQ-STARTUP-124), and its SHA-256 compared with the digest the manifest lists. It SHALL start only after the window is shown (REQ-STARTUP-043) and SHALL raise no modal dialog, open no window, take no keyboard focus and block no input; the window SHALL stay fully interactive throughout. Where the release feed states a non-zero size for the asset, the download SHALL NOT write more bytes than that size: a transfer that exceeds it SHALL be ended and treated as a failed download. Whether a download starts on a connection the platform reports as metered is *reserved* (UD-1). *Acceptance:* with a newer signed release published, the installed previous release shows its download progressing with no click and no modal while its composer accepts input; with that release's signature broken, a network sink observes no request for the asset.

**REQ-STARTUP-170** — **Its progress is visible and it can be cancelled.** While a download of REQ-STARTUP-169 runs, its progress SHALL be shown on the update notice, measured and repainted as REQ-STARTUP-118 fixes, and whenever that notice holds the banner it SHALL offer an action that cancels the download, enabled for the whole of the transfer and the verification. Cancelling SHALL end the transfer within 2 seconds of the activation, SHALL remove every byte the download wrote, SHALL leave the installation, any existing pending update and the preference store untouched (`updates/dismissedVersion` included), and SHALL NOT be reported as a failure. A cancel is not an update operation of REQ-STARTUP-114 and SHALL NOT be refused while the download runs. What the product does about the cancelled version afterwards, in that process and at later launches, is *reserved* (UD-2); where the progress and the cancel stay reachable while another notice holds the single persistent slot of REQ-SHELL-114 is *reserved* (UD-10). *Acceptance:* a cancel during the transfer leaves no file the download wrote, no pending record, and no error notice, within 2 seconds.

**REQ-STARTUP-171** — **The verified download is kept as the pending update.** A download whose digest matched SHALL be retained as the **pending update**, together with the exact bytes of the checksum manifest and of the signature that authorised it, in the per-user data directories of REQ-STARTUP-145 — local to this machine and never replicated — and never in the storage the platform designates for transient files, inside a workspace, beside the artifact, or in the preference store of REQ-STARTUP-146. Exactly one record per user account SHALL describe it, naming at least the version, the installation flavour and platform key it was selected for, the asset's exact name (REQ-STARTUP-108), the digest the manifest lists for it, its size, the running version that downloaded it, and its state. At most one pending update SHALL exist at a time. The record SHALL be written atomically on the terms of REQ-STARTUP-071 (a same-directory temporary file, flushed, then renamed), so that after any interruption it reads either as it was before the write or as it is after it. A record that is missing, unreadable, of a schema the build does not know, or naming files that are absent SHALL read as no pending update and never as an error, and the files it named SHALL be removed. Only the main process writes it; no renderer, child process, configuration value or environment variable reads or changes it. Its form and its place within those directories are implementation choices no surface reports.

**REQ-STARTUP-172** — **A pending update is verified again before it is applied.** Before a pending update is applied — at a next start (REQ-STARTUP-173) or by `Restart now` (REQ-STARTUP-174) — the product SHALL establish again, from the retained bytes alone and with no network request: that the retained signature verifies over the retained manifest against a key **the running build** carries (REQ-STARTUP-167); that the manifest, parsed only after that, lists the asset under its exact name (REQ-STARTUP-108); that the retained asset's SHA-256 equals the listed digest; that its version is strictly newer than the running version in REQ-STARTUP-109's order; and that its flavour and platform key are the ones the running build classifies itself as (REQ-STARTUP-106). Where any of these fails, the pending update SHALL be discarded, record and files, and nothing SHALL be applied: the installation SHALL remain byte-for-byte what it was (REQ-STARTUP-126), and no other file and no network source SHALL be substituted. A pending update whose version is not newer than the running one — the same or a newer build having been installed by other means — SHALL be discarded silently. How a discard for any other reason is reported is *reserved* (UD-4); it is never overridable (REQ-STARTUP-123). *Acceptance:* one byte changed in the retained asset, in the retained manifest or in the retained signature each leads the next start to discard the pending update and to run the version that was installed.

**REQ-STARTUP-173** — **It takes effect at the next start, without a click.** The next time the application is started after a pending update was verified, the version that runs SHALL be the pending version, and no user action SHALL be required. Where the flavour's apply step can replace its target while the application runs (the portable and AppImage strategies of REQ-STARTUP-125), the replacement MAY be made as soon as the pending update has been verified, the next start of the artifact then running the new version; whether it is made then or at the next start is *reserved* (UD-8). Where it cannot (the installed tree), the apply SHALL be made by the launch that has become the running instance (REQ-STARTUP-164 (1)), after REQ-STARTUP-172's verification, before any workspace is opened and before any run can start, so that no work in progress is ever interrupted: the verified installer is started without its pages, that launch ends, and the updated installation SHALL be started automatically once the installer has completed. A directory the applying launch carries SHALL first be persisted as the remembered workspace (REQ-STARTUP-041 (a)), so that the updated build opens it. That launch is exempt from REQ-STARTUP-155's first-paint bound for the apply and for nothing else; what it shows while the installer runs is *reserved* (UD-6). The apply SHALL need no network. A launch handed to a running instance, a demo window, and a build classified not updatable SHALL never apply a pending update, and the last SHALL leave the record and its files exactly as it found them. *Acceptance:* quit the installed previous release with a pending update, start it again with the network blocked, and the updated version paints with no click, opening the workspace the launch carried.

**REQ-STARTUP-174** — **`Restart now` applies it at once, behind the guards a clicked close already asks.** Once a pending update has been verified — or, where REQ-STARTUP-173 permits, already applied in place — the update notice SHALL become a persistent, non-modal success notice conveying that the named version has been downloaded and verified, that it will be installed the next time Rotaris starts, and that `Restart now` installs it now; the action is labelled `Restart now` and the rest of the wording is left to the implementation. Dismissing that notice SHALL hide it and SHALL NOT discard the pending update or prevent the next-start apply. Activating `Restart now` SHALL ask, in REQ-SHELL-119's order and as the update's own closes ask them, the unsaved-settings guard of every open main window (REQ-SHELL-124), the worktree-integration guard (REQ-SHELL-119 guard (2), REQ-NOTIFY-056) and the active-run confirmation (REQ-STARTUP-046), at the click and again immediately before anything is started; a decline at any of them SHALL start nothing, close nothing, and leave the pending update and the notice as they were. Accepted, on the portable flavour the restart is REQ-STARTUP-121's hand-over, unchanged; on the installed flavour the verified installer is started as REQ-STARTUP-173 starts it, the windows close only after it has started, and the updated installation is started when it completes. Where the installer or the successor cannot be started, nothing SHALL close and REQ-STARTUP-120's notice SHALL appear. *Acceptance:* each guard declined starts nothing; all accepted, the updated version is running and exactly one instance exists (REQ-STARTUP-161).

**REQ-STARTUP-175** — **Nothing restarts, installs or closes on its own while the application runs.** While the application runs, the product SHALL NOT restart itself, close a window, start an installer, or present a modal dialog, a countdown or a prompt that takes focus because an update is downloading, downloaded or pending; the only applies are the next-start apply of REQ-STARTUP-173, with the in-place replacement it permits, and the one the user chooses through `Restart now`. Quitting the application SHALL NOT install a pending update and SHALL NOT start an installer: the pending update survives the quit and is applied at the next start. A download still running at quit SHALL be abandoned within REQ-STARTUP-046's 5000 ms and SHALL leave no partial and no locked file (REQ-SHELL-121); the next launch downloads again from the first byte. *Acceptance:* with a pending update, closing every window and quitting starts no process and changes no file of the installation.

**REQ-STARTUP-176** — **An interrupted or failed update never leaves an installation that cannot start.** At every instant of a download, a verification, a cancel, a discard and an apply — and after the process is ended at any such instant, the machine's loss of power included — the installation SHALL start and run either the version installed before the attempt or, once the apply has completed, the new version, and never neither. In particular: nothing of the installation is moved or modified before REQ-STARTUP-172's verification has passed (REQ-STARTUP-126); on the portable flavour the artifact's path SHALL at every instant name a complete executable, the previous bytes or the new ones, and the previous executable SHALL be kept beside it as REQ-STARTUP-115's `<name>.old` until a later launch of the replaced artifact has painted its main window; on the installed flavour an apply that did not complete SHALL be detected by the next launch and resolved under REQ-STARTUP-177 rather than by starting a partly replaced installation. Whether a build that cannot start after an apply is rolled back automatically is *reserved* (UD-11). *Acceptance:* the process ended at each step of the download, the verification, the swap and the installer's run, and the next launch starts a version that paints.

**REQ-STARTUP-177** — **One apply at a time, and a launch during an apply waits.** At most one apply SHALL run per user account at a time, and only the launch that holds the instance record of REQ-STARTUP-161 SHALL start one. A launch that arrives while an apply is in progress — the installer started under REQ-STARTUP-173 or REQ-STARTUP-174 still running — SHALL NOT start the installation being replaced and SHALL NOT start the installer again; it SHALL wait until the apply has ended and then resolve under REQ-STARTUP-164 as any launch does, and while it waits it SHALL convey that Rotaris is being updated, on the terms REQ-STARTUP-162 states for a launch that waits on a shutdown: not an error, no refusal reported, no second instance offered. Waiting is not a third outcome of REQ-STARTUP-161. The wait is bounded by a limit the implementation states and the release gate measures; an apply whose installer is no longer running, or has outlived that limit, SHALL be read as an apply that did not complete, verified again (REQ-STARTUP-172) and retried a bounded number of times by a later launch that holds the instance record, after which the pending update SHALL be discarded; the number of attempts and how long an unapplied pending update is kept are *reserved* (UD-9). The several windows of the one instance share one download, one pending update and one update notice. *Acceptance:* a second launch during the installer's run starts no process of the installation being replaced and ends with the updated version on screen.

**REQ-STARTUP-178** — **What the update path leaves on disk.** Beside the installation itself the update path SHALL keep at most one pending update with its manifest and signature, at most one download in flight, and on the portable flavour the one backup of REQ-STARTUP-115. The partial files of a download that did not finish SHALL be removed when it ends, at quit (REQ-SHELL-121), and failing both at the next launch before any new download begins. A pending update SHALL be removed when it is superseded — a newer release verified in its place, the same or a newer version found running, a different flavour or platform key classified — and, once applied, by the first launch of the updated version that paints its main window; an installer started from it is run from it and removed by that same launch. A removal that fails SHALL be retried at a later launch and SHALL NOT be reported, on REQ-STARTUP-115's terms. Which release a pending update yields to when the feed later names a different one — newer, or older because a release was withdrawn — is *reserved* (UD-5).

**REQ-STARTUP-179** — **Failures of the background path.** A failure of the launch-time check stays invisible (REQ-STARTUP-110). A refusal on authenticity or integrity — no signature, a signature that does not verify, no manifest, no listed digest, a digest mismatch (REQ-STARTUP-123), an oversized transfer (REQ-STARTUP-169), or a pending update that fails REQ-STARTUP-172 — SHALL install nothing, SHALL offer no override, and SHALL NOT be retried for that release by the same process. Whether a transport failure of a download the user did not start, and each of those refusals, is shown, and on which surface, is *reserved* (UD-4); where one is shown, it is REQ-STARTUP-120's notice with the technical sentence as its detail. A failure of an apply the user started with `Restart now`, and of a next-start apply, SHALL always be visible (REQ-STARTUP-150).

**REQ-STARTUP-180** — **The disclosure names the download.** Beside the statements of REQ-STARTUP-160, the network-activity disclosure SHALL state that when the release endpoint names a newer release, a supported standalone build downloads it in the background from the host that serves that release's assets, and installs it the next time the application starts or when the user restarts it. It SHALL name no host, as REQ-STARTUP-160 requires.

**REQ-STARTUP-181** — **Acceptance of the background path rests on the published artifacts.** The behaviour of REQ-STARTUP-169 to REQ-STARTUP-180 SHALL be accepted only on observations of the published artifacts of the platform keys a release publishes, each launched as REQ-STARTUP-156 launches it, between two releases signed with a key both carry: (1) an installed previous release downloads the newer one with no click and no modal while its window accepts input; (2) a cancel ends the download and leaves nothing; (3) a quit with a pending update installs nothing, and the next start runs the newer version with no click; (4) `Restart now` with each guard declined starts nothing, and accepted leaves the newer version running as the one instance; (5) the process ended at each step of the download, the verification, the swap and the installer's run leaves an installation that starts; (6) a second launch during an installer apply starts nothing of the installation being replaced; (7) a tampered retained asset, manifest or signature is discarded at the next start with nothing installed. The portable flavour is accepted on the same observations through its launcher (REQ-STARTUP-165). An observation not made SHALL be recorded as not performed and SHALL fail the acceptance.
