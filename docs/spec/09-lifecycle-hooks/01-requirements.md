# User-Defined Lifecycle Hook Commands — Event Model

Part 1 of 6 of [domain 09](../09-lifecycle-hooks.md), which indexes every part. Defines REQ-HOOKS-001 – REQ-HOOKS-048.

## Requirements

### Event Model

- **REQ-HOOKS-001** — The system SHALL recognize exactly seven hook events in two families: tool events `pre_tool` and `post_tool`, and lifecycle events `session_start`, `session_end`, `iteration_end`, `child_completed`, and `verifier_finished`. No other event name is valid in configuration. This requirement is the product's single definition of the hook event vocabulary and of its division into the two families: a document that needs to name a hook event, to state how many there are, or to say which family one belongs to SHALL cite this identifier rather than restating the set, and a surface needing a new lifecycle point extends this list here rather than admitting an event name of its own.

- **REQ-HOOKS-002** — Only tool hooks SHALL be able to influence the run via exit code. Lifecycle hooks are strictly informational: given a lifecycle hook with any configuration (including `required: true`), when it exits with any code, then the run proceeds unaffected.

- **REQ-HOOKS-003** — Events SHALL fire at these points: `pre_tool` immediately before a permitted tool call runs; `post_tool` once a tool call has run; `session_start` once per run, ahead of the first iteration; `session_end` once per run, on each of the ways a run can finish: success, failure, a requested stop, cancellation, and interruption; `iteration_end` at the close of each finished iteration; `child_completed` once a delegated child agent has finished, whatever its final state; `verifier_finished` once for every completion-verifier pass, executed or skipped.
  > **Narrowed by [`PD-HOOKS-001`](../../product/directives/pd-hooks-001.md#pd-hooks-001), 2026-10-06.** `child_completed` fires only
  > for a child that finishes while a run's lifecycle hooks are live, after its `session_start` and before its
  > `session_end` begins; a child that finishes outside that window (cancelled at rest, after the run came to rest, by a
  > repair, in a run that never started, or while `session_end` runs) fires none, then or later. Every other event above
  > still fires as stated.

- **REQ-HOOKS-004** — Permission policy SHALL be evaluated before hooks: given a tool call the policy denies, no hook process starts and no hook event fires for that call. `post_tool` SHALL fire only for calls that ran to completion — not for a policy denial, and not for a call stopped by a `pre_tool` hook.

- **REQ-HOOKS-005** — Given a tool call that ran but did not succeed (the tool returned an error rather than an observation), the `post_tool` hooks SHALL still fire, and the payload's `result` field SHALL carry `{"error": "<text>"}`.

- **REQ-HOOKS-006** — Given a programmatic request to fire a lifecycle event name the system does not recognize, the engine SHALL do nothing and return zero outcomes (recording the fact at debug log level only), so that new event names can be introduced without breaking older components.

### Configuration Schema and Validation

- **REQ-HOOKS-007** — Hooks SHALL be declared under a `hooks:` key of the layered YAML agent configuration, in either the global scope (the per-user configuration directory's `agents.yaml`) or the workspace scope (`<workspace>/.rotaris/agents.yaml`).

- **REQ-HOOKS-008** — Each hook entry SHALL support exactly these fields with these defaults:
  - `event` (string, required, no default): must name one of the seven events listed in REQ-HOOKS-001; surrounding whitespace is removed before validation.
  - `command` (string, required): must not be blank or whitespace-only; otherwise kept exactly as written (no whitespace trimming).
  - `name` (string, default `""`): display label; if it reduces to empty after trimming, the hook's stable id is displayed instead, in the form REQ-HOOKS-018 fixes.
  - `matcher` (string, default `""`): empty selects every applicable occurrence; trimmed; must parse as a valid command pattern when configuration is loaded.
  - `timeout_seconds` (number, default `60.0`): must be strictly greater than 0.
  - `required` (boolean, default `false`): has meaning only for `pre_tool` (see REQ-HOOKS-048).
  - `enabled` (boolean, default `true`): `false` leaves the entry declared but non-executing; the entry keeps its place in the list, so ids assigned to the entries around it do not shift.
  - `source` (string, default `""`): filled in while loading; any value written by hand SHALL be replaced.

  This requirement is the product's single definition of the hook entry schema — the field set, each field's type, whether it is required, and its default: a document that presents, validates, stores, or documents a hook entry SHALL cite this identifier rather than restating any of those, and a field a surface needs is added here rather than declared elsewhere. Where such a document also needs the form of the stable id a nameless entry is reported by, it cites REQ-HOOKS-018 for that, which this requirement does not restate.

- **REQ-HOOKS-009** — The hooks section SHALL support: `enabled` (boolean, default `true`) as a single on/off control for the whole feature — when `false`, nothing runs but declarations remain; `entries` (list, default empty — no hooks ship with the product); and `superseded_entries` (list, default empty, filled in only while loading, never written by hand).

- **REQ-HOOKS-010** — A list-shorthand spelling `hooks: [ <entries> ]` SHALL be accepted and normalized to `hooks: { entries: [...] }`; both spellings produce identical behavior, including the recorded declaring scope.

- **REQ-HOOKS-011** — A bare `hooks:` key (YAML null) and a bare `entries:` key SHALL parse as *unset*, not *empty*: the inherited entry list is kept. A `hooks:` value that is neither a mapping nor a list SHALL fail loading with an error of the form: `Invalid 'hooks' section: expected a mapping or a list of hook entries, got <type>`.

- **REQ-HOOKS-012** — An invalid entry SHALL make configuration loading fail: the load SHALL surface an error naming the YAML path of the offending field, SHALL produce no configuration, and SHALL neither drop, ignore, nor repair the entry. `<i>` is the entry's position within the `entries` list of the scope being loaded, counted from `0` across every declared entry, entries with `enabled: false` included:
  - Unknown event name — path `hooks.entries.<i>.event`; message `hook event '<v>' is not a known lifecycle hook event; expected one of: ...`, quoting the rejected value and listing all seven names of REQ-HOOKS-001.
  - Matcher that will not tokenize, an unclosed quote for instance — path `hooks.entries.<i>.matcher`; message `hook matcher '<v>' is not a usable command pattern: ...`.
  - Blank or whitespace-only command — path `hooks.entries.<i>.command`; message `hook 'command' must not be blank`.
  - `timeout_seconds` of zero or less — path `hooks.entries.<i>.timeout_seconds`; the message SHALL quote the rejected value and state that the budget must be greater than zero.

  The YAML paths are a machine-readable contract and SHALL be produced exactly as given. The message texts are human-readable: each SHALL convey the information stated for it above — which field was rejected, the value that was rejected, and what was expected, listing all seven event names in the unknown-event case — and the exact wording is left to the implementation. Where several entries are invalid at once, the load SHALL report every one of them, in ascending `<i>` order within a scope and in scope-precedence order across scopes, each with its own path and message, so that a user correcting a configuration file is not led through the failures one at a time.

### Configuration Layering and Provenance

- **REQ-HOOKS-013** — Scope precedence SHALL be: built-in defaults, then global, then workspace. A scope that supplies an `entries` list SHALL substitute its own list for the inherited one in full, which lets a narrower scope remove an entry it inherited; a scope that supplies only `enabled` SHALL leave the inherited entries in place.

- **REQ-HOOKS-014** — Every entry SHALL be tagged with the scope that declared it (`default`, `global`, or `workspace`) while that scope is being loaded, ahead of the merge, so the tag is still accurate after merging. A configuration assembled in memory without going through the loader SHALL resolve as scope `default`.

- **REQ-HOOKS-015** — When one scope's `entries` list supersedes an inherited list, the displaced entries — together with anything previously displaced — SHALL be kept in the winning scope's `superseded_entries`. Keeping them is purely a record; it grants nothing and decides nothing about trust.

- **REQ-HOOKS-016** — *Withdrawn.* Its only surface was a command-line `--config <path>` override, and the product has no command-line entry point; the capability it carried — letting a deliberate act by the user, rather than the accident of opening a checkout, decide that a configuration source's hooks may run — is carried by the review dialog of REQ-HOOKS-104 to REQ-HOOKS-108 and by the decision management of REQ-HOOKS-136.

### Hook Identity and Ordering

- **REQ-HOOKS-017** — When `hooks.enabled` is `false`, both the effective hook set and the resolved superseded set SHALL be empty.

- **REQ-HOOKS-018** — Each resolved hook SHALL have a stable id of the form `<source>:<index>:<event>` (e.g. `workspace:0:post_tool`) unless it carries an explicit external identity (see REQ-HOOKS-114). `<index>` is the entry's ordinal within the list declared by its own scope, assigned while disabled entries are still present, so switching one entry off leaves every other entry's id unchanged. Each scope has its own independent index sequence.

- **REQ-HOOKS-019** — Selecting the hooks for one event SHALL preserve declaration order, and that same order SHALL govern execution, for tool events and lifecycle events alike (REQ-HOOKS-040).

- **REQ-HOOKS-020** — The scope names treated as trusted SHALL be exactly `default`, `global`, and `workspace` (the last only once approved, see REQ-HOOKS-090). Any other scope value SHALL be refused by the trust gate; there is no permissive branch for unfamiliar scopes. Imported external hooks use the scope value `external:claude-code`, which is intentionally not in this set.

### Matcher Semantics

- **REQ-HOOKS-021** — Matchers SHALL apply only to tool events. A lifecycle event has nothing to select against, so its hooks fire on every occurrence whatever `matcher` says.

- **REQ-HOOKS-022** — An empty matcher SHALL select every tool call, whether or not that call supplies a shell command.

- **REQ-HOOKS-023** — A hook that carries a non-empty set of tool names (only imported hooks do) SHALL match when the tool name is a member of that set, compared exactly; its string matcher plays no part.

- **REQ-HOOKS-024** — Where the call supplies a non-blank shell command, the matcher SHALL be read as a command pattern and tested against every segment of a command line built from several commands, so that in `git status && rm -rf /` the second command is examined too.

- **REQ-HOOKS-025** — A command pattern SHALL be evaluated as follows. The candidate command line is first divided, outside quotes, at each of `&&`, `||`, `;`, `|`, `&`, and a line break; the pattern is tested against each resulting segment, and a match on any segment is a match (so `rm -rf /` inside `git status && rm -rf /` is examined). Within a segment, both pattern and candidate are split into tokens under one quoting convention used on every platform alike: a token break falls at each run of whitespace that lies outside quotes; a single-quoted or double-quoted run groups its contents into the surrounding token and the quote characters themselves are removed; and a backslash is an ordinary literal character, never an escape and never a quote, so a Windows candidate such as `copy C:\repo\a C:\repo\b` splits into exactly three tokens with every separator intact. An unterminated quote makes the text untokenizable, which REQ-HOOKS-028 resolves as "no match". Tokens are compared position by position, each comparison a case-sensitive glob in which `*` is the only metacharacter and matches any run of characters, the empty run included; `?`, `[`, `]`, and every other character are compared literally, so `git push -?` matches the literal token `-?` and nothing else. The segment matches only when its token count equals the pattern's, with one exception: where the pattern's final token is a bare `*`, the segment may carry any number of further tokens, zero included. Matching is positional and never a substring search: `echo git push` does not match `git push *`. This requirement, together with REQ-HOOKS-027 for which text a matcher is compared against and REQ-HOOKS-029 for where that text is taken from, is the product's single definition of hook matcher evaluation: the separator set the command line is divided at, the quoting and tokenizing convention, the glob comparison, and the trailing-`*` rule are stated here and nowhere else, and a document that needs any of them SHALL cite this identifier rather than restating it. In particular no other document may state a separator set, a backslash convention, or a fallback to the tool name of its own; where one did, this requirement governs.

- **REQ-HOOKS-026** — Consequence to document and test: `git push *` (with space) matches both `git push` and `git push --force`; `git push*` (no space) is a two-token pattern that matches `git push` on its own and nothing longer.

- **REQ-HOOKS-027** — An empty matcher selects every tool call (REQ-HOOKS-008, REQ-HOOKS-022); what follows governs non-empty matchers only. Where the text a matcher is tested against (REQ-HOOKS-029) is empty or whitespace only, the matcher SHALL instead be compared with the tool name as one case-sensitive shell-style glob: `read_f*` selects `read_file` and does not select `READ_FILE`. Where that text is non-blank — a file-editing tool's requested action name included — the call SHALL be matched as a command pattern under REQ-HOOKS-024 and REQ-HOOKS-025, and the tool name SHALL play no part.

- **REQ-HOOKS-028** — Matching SHALL be defined for every input: a command line that cannot be tokenized (for example an unclosed quote), or a matcher that will not parse at match time, SHALL yield "no match" rather than turning the tool call into a failure.

- **REQ-HOOKS-029** — The text a matcher is tested against SHALL be the same facet the permission policy matches on, taken from the call's arguments: for the shell tool (`terminal`) that is the command line; for a file-editing tool it is the name of the action requested — one of `create`, `edit`, `overwrite`, `insert`, `undo` — so the matcher `create` selects every file creation whatever the path.

### Execution Engine

- **REQ-HOOKS-030** — Each invocation SHALL run the configured `command` as a newly started process handed to the host platform's command interpreter, so that operators, quoting, redirection, and executable lookup written into `command` take effect exactly as they would were the same line typed at that platform's shell prompt. The interpreter SHALL be, on a POSIX host, the standard shell at `/bin/sh` invoked with the command as a single argument to `-c`; and on a Windows host, the command processor named by the `ComSpec` environment variable, or `cmd.exe` where that variable is unset or blank, invoked with the command as a single argument to `/c`. No other interpreter SHALL be selected, and the choice SHALL NOT vary with the content of `command`, so that the same declaration behaves identically on every machine of a given platform. The process's working directory SHALL be the tree the run is changing: the isolated worktree for a run confined to one, and otherwise the workspace itself (REQ-HOOKS-084). The payload's `workspace` field reports the base workspace and not that working directory (REQ-HOOKS-057).

- **REQ-HOOKS-031** — The payload SHALL be delivered as exactly one UTF-8 JSON object written to the hook process's standard input, and standard input SHALL then be closed, so that a hook reading to end-of-input terminates. No part of the payload SHALL be placed on the process's command line or in its environment: a tool argument containing `; rm -rf /` reaches the hook only as text inside the JSON document and is never interpreted. A hook that writes to standard output or standard error before or while it reads the payload SHALL NOT stall the invocation. Whatever the process wrote SHALL be reported subject to the limits of REQ-HOOKS-037, except in the two cases where there is nothing to report: the grace period of REQ-HOOKS-033 also expired, or no process was started at all (REQ-HOOKS-035). The last byte written SHALL be the closing brace of the JSON object: no trailing newline, and no other trailing byte, SHALL follow it, so that a hook comparing raw bytes rather than parsing them sees exactly the document and nothing more.

- **REQ-HOOKS-032** — The hook process SHALL inherit the host environment, with any per-run variable overrides supplied by this application, which is the process that starts the hook, taking precedence. The product itself contributes no hook-specific environment variables. Per-run overrides are an embedding facility only: no host is required to offer them, the desktop application supplies none, and no configuration key, preference, or user interface for setting them SHALL exist. A hook that needs a variable therefore sets it in its own `command`, and a run started from the desktop application sees exactly the environment the application itself was started with.
  > **Narrowed by [`PD-STARTUP-004`](../../product/directives/pd-startup-004.md#pd-startup-004), 2026-10-06.** "Exactly the
  > environment the application itself was started with" is that environment less `APPIMAGE` and
  > `ROTARIS_PORTABLE_ARTIFACT`, which main removes before it starts any child.

- **REQ-HOOKS-033** — Each invocation SHALL be bounded by the hook's `timeout_seconds` of wall-clock time. On expiry the hook process SHALL be terminated, and at most a further 5.0 seconds SHALL be spent completing that termination and collecting output the process had already produced; where that grace period also expires, the outcome reports empty output rather than the run waiting any longer. Termination SHALL reach only the process that was started and SHALL NOT be widened to its process group. The fate of that process's descendants is deliberately left to the platform and SHALL NOT be constrained: a descendant is permitted to outlive both the hook process and the run, whether or not it detached first, and the run SHALL neither wait for it, track it, nor report it. In particular, collecting the terminated process's output SHALL NOT block on a stream a surviving descendant still holds open; the grace period bounds that collection and expiring it yields empty output. Where the host cannot complete the termination even after the grace period, the invocation SHALL nevertheless finish within the bound below: the outcome is completed and returned, the run continues, and the still-running process is recorded only as a log entry — no user-facing warning beyond the ordinary timeout warning of REQ-HOOKS-052 is produced, and no run status is affected. The outcome SHALL record `timed_out = true` and no exit status (surfaced per REQ-HOOKS-036). The invocation SHALL therefore return no later than `timeout_seconds` plus 5.0 seconds of grace plus the time taken to start one process: a hook given a 0.3 s budget whose command sleeps for 60 s SHALL return without waiting for that sleep, and far inside the 60 s.

- **REQ-HOOKS-034** — Given a resolved hook whose timeout is zero or negative because it was constructed programmatically without configuration validation, execution SHALL substitute the 60-second default instead of running with no limit.

- **REQ-HOOKS-035** — If the command cannot be launched at all (for example because the working directory does not exist), the outcome SHALL have no exit code, empty output, a description of the launch failure, and a user-facing warning containing "could not run"; no error propagates into the run.

- **REQ-HOOKS-036** — The state in which a hook returned no exit status at all (launch failure, termination on timeout, or a process ended by a signal from any other source) SHALL be represented by one fixed value that means the same thing on every operating system, rather than by whatever a platform reports for a signalled process; consumers must therefore read the `timed_out` flag rather than infer anything from an exit value. That fixed value is `-1`, and it is what appears wherever an outcome's exit code is recorded verbatim — the session timeline entry's `exit_code` metadata and its message text (REQ-HOOKS-119). On the session event stream the same state is normalized to `exit_code: null` (REQ-HOOKS-125), so a stream consumer never sees `-1`.

- **REQ-HOOKS-037** — Standard output and standard error SHALL be captured separately and decoded as UTF-8, with bytes that are not valid UTF-8 replaced rather than causing the capture to fail. Each stream SHALL be limited to 16384 bytes, the two limits applying independently of one another. The limit SHALL count bytes of the decoded text's UTF-8 encoding, and the cut SHALL be taken at a character boundary: the retained portion is the longest prefix of the decoded text whose UTF-8 encoding is at most 16384 bytes, so no partial character is ever retained. Where a stream exceeded that limit, the retained portion SHALL be followed by the marker `\n[truncated: <total> bytes of output, 16384 kept]`, `<total>` being the size the stream would have had untruncated. The marker SHALL be appended beyond the limit and SHALL NOT count toward it. A stream at or below the limit SHALL carry no marker. This rule — count the retained portion only, append any marker beyond the limit — governs every truncation in this domain (REQ-HOOKS-052, REQ-HOOKS-066). This requirement is the product's single definition of the cap on hook output: the 16384-byte figure, the fact that it applies to each stream separately rather than to the two combined, the character-boundary cut, and the truncation marker are stated here and nowhere else, and a document that reports, stores, or configures hook output SHALL cite this identifier rather than restating the figure or asserting that output beyond it is discarded.

- **REQ-HOOKS-038** — Each outcome SHALL record the elapsed wall-clock time as a whole number of milliseconds, measured over the entire invocation including any timeout handling.

- **REQ-HOOKS-039** — Every invocation SHALL yield an outcome, whatever the host does. An interpreter or executable that is not installed, a working directory that cannot be used, and a process ended by a signal SHALL each yield an outcome carrying one of the warnings defined in REQ-HOOKS-052, after which the tool call or lifecycle point continues. A hook process ended by a signal it did not receive from the timeout path SHALL be treated as a process that produced no exit status: the outcome carries the fixed no-exit-status value of REQ-HOOKS-036 (`-1` where an exit code is recorded verbatim, `null` on the session event stream), `timed_out = false`, and the abnormal-termination warning of REQ-HOOKS-052 — never the platform's raw signal number, and never the "exited `<code>`" warning, which is reserved for a process that did exit. A diagnostics location that cannot be written SHALL NOT produce a warning and SHALL NOT change the outcome; it degrades to a log entry per REQ-HOOKS-121. None of these conditions SHALL raise an error into the run, end the run, alter its terminal status, or leave it waiting beyond the bound of REQ-HOOKS-033.

- **REQ-HOOKS-040** — Every applicable hook for an event SHALL run, in declaration order, even after one of them has decided to stop the call; the decision that takes effect is the first stopping outcome, determined once all applicable hooks have finished. Dispatch SHALL NOT stop early on a refusal, and the difference is observable and relied upon: the later hooks' side effects on the working tree, their `hook.start`/`hook.finish` pairs, their `hook_run` timeline entries, and their contribution to the failure tallies of REQ-HOOKS-055 all occur exactly as they would have with no refusal. The hooks of one event occurrence SHALL run one after another rather than concurrently, in declaration order, each finishing — normally or under the bound of REQ-HOOKS-033 — before the next starts; this holds for tool events and lifecycle events alike, so an occurrence with N applicable hooks is bounded by the sum of their individual bounds.

- **REQ-HOOKS-041** — Where a session has no hook eligible to run for an event, that event SHALL yield zero outcomes and nothing observable: no process is started, no `hook.start` or `hook.finish` is published, no timeline entry and no issue is recorded, and nothing is read or written on account of hooks. The once-per-session announcement of hooks the trust gate withheld (REQ-HOOKS-127) is the only event this rule does not suppress.

- **REQ-HOOKS-042** — Where a session has several tool calls outstanding at the same moment, the following SHALL hold. A hook's failures count against one allowance per stable id for the whole session, whichever call produced them, so three failures spread over three simultaneous calls switch the hook off at precisely the point three consecutive failures would (REQ-HOOKS-055). Reaching that point SHALL yield one switch-off warning and one switched-off id and no repeat of either, however many outstanding calls met the failing hook at once. A hook that consumes its entire budget on one call SHALL NOT delay the hooks of any other outstanding call, which begin and finish on their own schedule. These are invariants, not best-effort behavior: no maximum number of simultaneously outstanding tool calls is fixed, and each guarantee — one failure tally per stable id for the whole session, one switch-off warning and one switched-off id however many calls met the failing hook at once, one `hook.start`/`hook.finish` pair and one timeline entry per invocation, and no cross-call delay — SHALL hold at every degree of concurrency the host reaches.

### Exit-Code Semantics and Blocking

- **REQ-HOOKS-043** — For `pre_tool`: exit `0` lets the call proceed with no feedback and no warning; exit `2` stops the call, and what the hook wrote to standard error becomes the refusal that reaches the agent in place of the tool's output; any other exit produces a warning and the call proceeds.

- **REQ-HOOKS-044** — For `post_tool`: exit `0` yields nothing; exit `2` puts what the hook wrote to standard error into the conversation in addition to whatever the tool itself produced (the call already happened and is not rolled back); any other exit produces a warning.

- **REQ-HOOKS-045** — For lifecycle events: any non-zero exit — `2` included — is a warning only; the outcome always records that nothing was stopped, whatever `required` says. A lifecycle hook exiting `2` does count as a failure against the switch-off allowance, unlike a tool hook exiting `2`.

- **REQ-HOOKS-046** — Exit `2` from a `pre_tool` or `post_tool` hook is the hook working as designed and SHALL NOT count against the failure allowance: a guard that correctly stops calls is never switched off for doing so (five consecutive stops leave it enabled and file no failure issue). Exactly four situations count as a failure: the budget expired, the process could not be started, the process ended abnormally without an exit status (REQ-HOOKS-039), and the process exited with a code this specification assigns no meaning to.

- **REQ-HOOKS-047** — Nothing except a `pre_tool` hook SHALL ever be capable of stopping a call, regardless of what any other resolution step concludes; this SHALL be enforced rather than merely assumed.

- **REQ-HOOKS-048** — `required: true` SHALL NOT be interpreted as "any non-zero exit stops the call". A `pre_tool` hook that ran to completion and exited 1, 3, or 127 is simply misbehaving: warning, call proceeds, `required` or not. `required` changes behavior only where the hook returned no verdict at all (timeout or launch failure): without it, such a case proceeds with a warning; with it, the call is stopped and the agent is told which of the two happened. On a `post_tool` hook and on any lifecycle hook the flag is simply ignored.
