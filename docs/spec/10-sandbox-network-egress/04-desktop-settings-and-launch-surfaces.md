# Command Sandboxing and Network Egress Policy — Desktop settings and launch surfaces

Part 4 of 6 of [domain 10](../10-sandbox-network-egress.md), which indexes every part. Defines REQ-SANDBOX-113 – REQ-SANDBOX-125.

### Desktop settings and launch surfaces

- **REQ-SANDBOX-113** — The desktop settings surface (runtime section) exposes all six sandbox/egress settings so that no YAML has to be edited by hand: a sandbox-mode selector; a writable-roots list with an entry field and add button; a toggle for allowing network inside the sandbox; an egress-policy selector; allowed-hosts and denied-hosts lists each with an entry field and add button; and a per-list problem label. All six round-trip: saving writes the workspace config the product loader reads back, and a reopened settings view shows every value on its control.
- **REQ-SANDBOX-114** — Each control validates on the same terms as the stored schema, so nothing invalid can reach the saved policy: entering a relative writable root is rejected at the control with a problem message mentioning "absolute path", with nothing stored and no unsaved-changes state; entering a host pattern with a wildcard other than a single leading one is rejected with a problem message describing the wildcard restriction and showing the supported form `*.example.com`.
- **REQ-SANDBOX-115** — The controls teach the two rules users most often get backwards: the egress-policy description states that a denied host stays denied (deny wins), and the host-lists description states that `*.example.com` does not match `example.com` on its own.
- **REQ-SANDBOX-116** — A label reflects the current availability result: that confinement is turned off, when it is; an active state naming the backend when a non-off mode is selected on a capable host; and, on a host that cannot deliver it, an unavailable state carrying the mechanism's reason and remediation and warning that sessions will fail to start rather than start unconfined. Selecting a mode on such a host is still STORED, since the setting exists for hosts that can honor it. Where the host provides no confinement mechanism at all, this label is not the whole of what the user must be told: the plain disclosure of REQ-SANDBOX-130 accompanies it, and is shown whatever mode is selected.
- **REQ-SANDBOX-117** — Loosening the default disposition to `allow` requires an explicit confirmation first; declining leaves both the stored policy and the control showing the earlier value.
- **REQ-SANDBOX-118** — Saving validates every value against the stored schema before anything is written. If any value is refused, the surface reports which one and writes nothing: the workspace configuration on disk is left exactly as it was and still loads. Reloading the workspace re-reads that file and refills the controls, without marking the form as holding unsaved changes and without writing anything back. Edits that have not been saved reach NOTHING: a run started while the settings surface holds unsaved sandbox or egress edits uses the configuration persisted on disk, since REQ-SANDBOX-038 reads the owning run's current configuration and that configuration is what the loader read from the file. Any other rule would make a run's confinement and egress policy depend on unwritten interface state that no record could later reproduce. Because that is easy to get wrong, the surface SHALL make it visible: while the runtime section holds unsaved changes to any of the six sandbox/egress settings, it shows an unsaved-changes indication, and starting a session in that state produces a warning conveying which settings differ from the saved configuration and that the run will use the saved values. The warning advises and does not block.
- **REQ-SANDBOX-119** — The per-session launch dialog offers an enable-OS-sandbox checkbox: checked launches the session with mode `workspace-write`; unchecked with `off`. On a host where the probe reports unavailable, the checkbox is disabled and cleared, and the mechanism's reason AND remediation appear both in the tooltip and as text visible without hovering, since a tooltip alone does not count as informing the user. A workspace that requests no confinement launches as usual.
- **REQ-SANDBOX-120** — Where the workspace configuration itself demands confinement on a host that cannot deliver it, the launch dialog's checkbox remains CHECKED and disabled, so the host never appears to switch the setting off. The run then fails before the agent loop begins, with a notice whose title conveys that the run did not get underway and whose body carries the reason and remediation. Neither a session nor a session lock remains afterwards.
- **REQ-SANDBOX-121** — A workspace indicator naming the backend appears only for a session whose recorded result is confined, and is hidden for sessions that are not. With several sessions open it tracks the focused one, and `sandboxed`/`sandbox_backend` are recorded in each session's snapshot.
  > **Narrowed by [`PD-SHELL-008`](../../product/directives/pd-shell-008.md#pd-shell-008), 2026-10-06.** The indicator is a status-strip
  > item after the file-access flag, reading `sandbox: <backend>`, or `sandbox: confined` for a record written before
  > the backend was recorded. The rest above is unchanged.
- **REQ-SANDBOX-122** — The confinement mode in force for a session has exactly two sources and no third: the layered configuration field `runtime.sandbox_mode` (REQ-SANDBOX-048, REQ-SANDBOX-005), and the per-session override offered by the launch dialog of REQ-SANDBOX-119. No environment variable, no launch argument, and no other route of any kind can select or change it, which agrees with REQ-TOOLS-114's rule that no launch-time override exists outside that dialog. A session started without touching the dialog control takes the configured value.
- **REQ-SANDBOX-129** — The runtime section of the desktop settings surface carries a re-check control beside the availability label of REQ-SANDBOX-116. Activating it discards the cached verdict of REQ-SANDBOX-067 and runs a fresh probe, so a user who has just installed the launcher or lifted a namespace restriction can make the product see it without restarting the application. The label enters a checking state within the product's 100 ms interface responsiveness budget and the probe runs off the interface thread, so neither the settings surface nor any other view blocks for the up-to-5.0-second trial of REQ-SANDBOX-069; when the probe finishes the label shows the new verdict's reason and remediation. A fresh verdict governs sessions started afterwards and never changes the recorded confinement fact of a session already running (REQ-SANDBOX-094, REQ-SANDBOX-096).
- **REQ-SANDBOX-130** — On a host for which no confinement mechanism exists at all — any operating system outside the closed two-member set of REQ-SANDBOX-065, native Windows included and most consequentially, it being the desktop platform this product expects most of its users to be on — the product SHALL state that plainly, in its own words, rather than leave the user to infer it from a remediation string, a disabled control, or the absence of an indicator. The fact to be conveyed is a single one and it is the same on both surfaces below: **this host cannot confine anything, so every command an agent runs executes with the same operating-system privileges as the account running the application, reaching whatever that account can read and whatever it can write, and no value of `runtime.sandbox_mode` changes that here.** The disclosure SHALL be text and SHALL NOT rely on colour or on a control's disabled appearance to carry it (REQ-SHELL-149). It SHALL name what would change the answer — running the workspace on a host the product can confine (REQ-SANDBOX-073) — and SHALL NOT present the host as misconfigured or as needing repair, because it is neither: this is a stated limit of the product on that platform, and telling a user to fix something that is not broken teaches them to ignore the notice.

  Two surfaces carry it, and both carry it whatever `runtime.sandbox_mode` is set to, `off` included — `off` being the shipped default (REQ-SANDBOX-048) and therefore the state in which nearly every such user will be:
  - **The settings surface.** The runtime section shows the disclosure alongside the availability label of REQ-SANDBOX-116, without the user having to select a confinement mode first. Selecting one is how a user *asks* about confinement, and a user who never asks is precisely the user who does not know to.
  - **The launch surface.** The per-session launch dialog of REQ-SANDBOX-119 shows the disclosure before the run begins, together with whatever advisory REQ-SANDBOX-107 produces. It is shown for attended and unattended sessions alike, and it is shown when that advisory is empty: an attended run on such a host is exactly as unconfined as an unattended one, so a launch surface that spoke only about who can answer approvals would tell the user the smaller half of what is true. REQ-SANDBOX-107's emptiness rule governs that advisory's own text and does not suppress this disclosure. Like the advisory, the disclosure advises and never blocks a launch.

  This requirement adds no capability and changes no verdict. The set of recognized platforms stays closed at two members and none may be added (REQ-SANDBOX-065); no opportunistic mode that could silently resolve to no confinement is offered (REQ-SANDBOX-048); a run that requests confinement on such a host still does not start (REQ-SANDBOX-095); and a run that requests none still starts and still runs unconfined. What it adds is that the user learns this from the product before their first command runs, rather than from a diagnostic string they would only see by asking for something the host cannot give them.

### Contracts with neighboring subsystems

- **REQ-SANDBOX-123** — Verification checks and probes run through the same terminal enforcement point as everything else, so permission policy, confinement, and timeout-termination semantics apply to them without modification; no separate, less-checked execution path exists for them.
- **REQ-SANDBOX-124** — Lifecycle hooks that the user configures sit deliberately OUTSIDE both confinement and the permission policy: they are the user's own code, executed in the user's shell on the host. Accountability for them rests on the audit trail, and the boundary must be stated in the documentation.
- **REQ-SANDBOX-125** — No model-provider integration may expose provider-side tool execution that steps around these layers: provider-supplied built-in tools are off by default, and any tool call routed from a provider is executed by the product's own execution path so that permission gating and confinement continue to apply.
