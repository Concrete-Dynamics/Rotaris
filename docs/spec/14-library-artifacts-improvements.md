# Library, Artifacts, and Improvement Proposals

## Overview

After every completed task run the product may perform an optional, strictly non-blocking background analysis that stores an "improvement artifact" containing evidence-backed improvement proposals authored by a dedicated analysis model. Users review, edit, approve, reject, defer, reset, or delete those proposals from two desktop surfaces — a Library view and a dashboard card — both of which read and mutate the same workspace-scoped artifacts in the one store. Approved proposals are applied only by a separately started improvement run whose workspace effects are checkpointed and reversible. The same domain covers the per-session store of agent-published reports and deliverables (browsable and editable in the Library and via agent-facing tools), per-persona memory files re-injected into future runs, and the saved-prompt stash and prompt history.

> **This domain carries a second analysis pass under [`PD-LIBRARY-002`](../product/directives.md#pd-library-002), 2026-09-17.** The domain
> carries a second kind of analysis pass beside the per-run one: a user-started **retrospective** that
> reads the workspace's own session history across runs and authors proposals in this domain's own
> vocabulary and lifecycle. Nothing below is changed for the per-run analyst; where the retrospective
> reaches, the directive says so.

## Requirements

### 1. Improvement lifecycle and run classification

**REQ-LIBRARY-001** — The improvement feature MUST implement a four-stage, human-gated lifecycle: (1) after a task run completes, an analysis pass authors evidence-backed proposals; (2) a human reviews each proposal; (3) a separate improvement run applies only approved proposals; (4) applied changes are reversible via rollback. A task run MUST never modify its own configuration, personas, or gates as a side effect of analysis.

**REQ-LIBRARY-002** — Every run MUST persist exactly one run-type value drawn from `task_run`, `improvement_run`, and `integration_run`, and that value MUST be readable from the session's persisted state. Every improvement artifact MUST carry it as `source_run_type`; a stored payload that omits the field reads as `task_run`. Only `task_run` is eligible for post-run analysis: wherever this document keys behaviour off the run type, `integration_run` is treated exactly as `improvement_run`, and neither produces analysis (REQ-LIBRARY-005, REQ-LIBRARY-032). The product therefore never writes an artifact whose `source_run_type` is anything but `task_run`; the schema still accepts one so that an imported or hand-written artifact remains readable, and REQ-LIBRARY-034 keeps it out of analysis history. What classifies a run as `integration_run` is owned elsewhere and this domain MUST NOT redefine it: the run-type marker itself is the persisted marker of REQ-SESSION-021, stamped at session creation and never changed on resume, and the runs that carry the `integration_run` value are the hidden worktree-integration runs of REQ-GIT-131. This domain consumes that value and does exactly one thing with it — treats it as ineligible for analysis, exactly as `improvement_run` is.

**REQ-LIBRARY-003** — Deterministic, non-model parts of the product may gather evidence but MUST never author user-reviewable proposals. Proposals are authored exclusively by the model-backed post-run analyst; each artifact records the authoring model identifier (`collector_model`, nullable).

  > **Extended by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002), 2026-09-17.** The
  > rule — only a model-backed pass authors proposals, deterministic parts gather evidence only —
  > now covers two passes: this requirement's per-run analyst, and the directive's user-started
  > retrospective. A retrospective artifact records its own authoring slot (`retrospective_model`)
  > under the same discipline, and no deterministic path authors proposals of either kind.

**REQ-LIBRARY-004** — Task completion MUST never be delayed or altered by improvement analysis. Given a completing task run, when it reaches its terminal state, then the terminal result is reported to the host before any analysis work begins, and the host receives a self-contained analysis job it may execute afterward.

**REQ-LIBRARY-005** — An improvement run MUST never trigger another improvement analysis (no self-chaining). Given a run of type `improvement_run` (or `integration_run`) reaching a terminal state, then no post-run analysis occurs and no new proposals appear. End-to-end, an approval-driven improvement run performs zero analysis passes.

### 2. Proposal data model and validation

**REQ-LIBRARY-006** — The proposal category vocabulary MUST be closed with exactly 10 values: `documentation_update`, `agents_md_update`, `workspace_note`, `config_change`, `tool_enablement`, `dependency_install`, `persona_or_prompt_adjustment`, `persona_memory_update`, `preflight_check`, `verifier_gate_update`.

  > **Extended by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002), 2026-09-17.** The set
  > is untouched — the directive's retrospective authors proposals from this same closed vocabulary
  > and no other, and this requirement remains its single definition. No value is added and none is
  > redefined; a retrospective proposal is distinguishable from a per-run one by its artifact, not by
  > its category.

**REQ-LIBRARY-007** — Review status MUST have exactly 4 values: `pending_review`, `approved`, `rejected`, `deferred`. Risk MUST have exactly 3 values: `low`, `medium`, `high`.

**REQ-LIBRARY-008** — A proposal MUST carry: `id` (format `imp_` + 8 base62 characters), `category`, `summary` (minimum length 1), `evidence` (list), `recommended_action` (minimum length 1), `risk` (default `low`), `status` (default `pending_review`), `target_persona` (nullable), `proposed_verifier_section` (nullable mapping), `created_at` (UTC timestamp, defaults to creation time).

**REQ-LIBRARY-009** — Proposal construction MUST be rejected — no proposal exists afterwards, and the reported error names the field at fault — in each of these cases: (a) `evidence` is empty; (b) `category` is `persona_memory_update` and `target_persona` is missing, empty, or entirely whitespace; (c) `category` is `verifier_gate_update` and `proposed_verifier_section` is missing, is not a mapping, or is not a self-contained, valid gate-configuration block. A reviewer can check the consequence directly: a gate change written only as prose in `summary` or `recommended_action` never becomes a proposal and never appears on a review surface. A `proposed_verifier_section` is self-contained and valid exactly when, taken on its own, it validates as a `verifier` section of the layered configuration surface — the section fields and their bounds of REQ-CONFIG-139 through REQ-CONFIG-144 together with the check-entry schema of REQ-CONFIG-145 — under the schema the running build enforces. There is no second, improvement-specific gate schema and none that is separately versioned: the same validation decides acceptance at construction time and again when the block is applied (REQ-LIBRARY-063), so a block that has become invalid because the configuration schema moved on is refused at application time rather than written.

**REQ-LIBRARY-010** — An evidence entry MUST carry `kind` (non-empty once surrounding whitespace is stripped), `text` (non-empty), the nullable ids `source_task_id`, `source_artifact_id`, and `source_session_id`, and an optional `excerpt`. `kind` is an open vocabulary: `transcript_observation`, `repeated_tool_failure`, `missing_resource`, `child_report_finding`, `repeated_search`, and `other` label analyst-authored evidence, while `verifier_gate_state` is reserved for the entry the product stamps onto a gate proposal (REQ-LIBRARY-029) and MUST NOT be the only entry a proposal carries (REQ-LIBRARY-159). What `excerpt` holds depends on the entry: quoted source text where the entry cites a transcript or a document, and the dedupe key on a `verifier_gate_state` entry. No consumer may assume `excerpt` is verbatim source text.

**REQ-LIBRARY-011** — The run-level artifact container MUST carry: `artifact_id` (format `impart_` + 8 base62 characters), `source_session_id` (the legacy input key `session_id` MUST be accepted as an alias), `source_run_type` (default `task_run`), `generated_at` (UTC), `collector_model` (nullable), `proposals` (list, may be empty), `considered_session_ids` (order-preserving, deduplicated), `notes` (nullable), `checkpoints` (list of rollback checkpoint records; may be absent on older artifacts), `rolled_back_at` (nullable timestamp).
  > **Narrowed by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002) revision 2, 2026-10-13** ([OQ-236](../architecture/open-questions.md#oq-236)). For a retrospective artifact: every artifact carries `source_kind` (`post_run` or
  > `retrospective`), and a retrospective artifact stores `source_session_id` null and names the sessions it read in
  > `considered_session_ids` (clause (a)). A post-run artifact is governed by the text above unchanged.

**REQ-LIBRARY-012** — An artifact's rollback point MUST be the entry of its `checkpoints` list whose `kind` is `pre_improvement` and whose `sequence` is the highest among entries of that kind; because sequence numbers are unique within an artifact (REQ-LIBRARY-071), that selection is never ambiguous. An artifact holding no such entry has no rollback point, and every surface MUST report the absence rather than fail on it — the artifact list states that the artifact has no rollback point (REQ-LIBRARY-166), the artifact detail says so in place of naming a checkpoint (REQ-LIBRARY-167), and the "Roll back" action is disabled with that explanation (REQ-LIBRARY-169). The current `applied` and `pre_rollback` checkpoints are chosen by the same rule applied to those kinds: highest `sequence`, otherwise none.

**REQ-LIBRARY-013** — Generated identifiers MUST be exactly 8 base62 characters (zero-padded) after the type prefix (`imp_`, `impart_`), and successive generations MUST differ even when produced in immediate succession.

**REQ-LIBRARY-014** — Validating a raw artifact payload MUST fail with an error message prefixed `malformed improvement artifact: ` when the payload does not satisfy the schema. An artifact whose `proposals` list is empty is valid. Re-validating an already-valid artifact round-trips losslessly.

### 3. Post-run analyst behavior

**REQ-LIBRARY-015** — The post-run analyst is a dedicated model-backed pass invoked at most once per terminal task run, with a configurable wall-clock timeout defaulting to 60 seconds. The analyst MUST never raise into its caller: every failure path yields an empty artifact whose `notes` field explains the failure.

  > **Extended by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002), 2026-09-17.** The
  > no-raise discipline and the two-outcome shape of an analysis pass govern a second pass now: the
  > user-started cross-session retrospective, bounded by its own timeout (default 120 seconds) on the
  > same recovery paths. This requirement's own scope — at most once per terminal task run — is
  > unchanged, and the retrospective is never invoked by a run at all.

**REQ-LIBRARY-016** — An analysis pass MUST end in one of exactly two ways: an artifact whose proposals all satisfy REQ-LIBRARY-009, or the recovery outcome of REQ-LIBRARY-022. A reply that offers nothing to propose is a success and MUST yield an artifact whose `proposals` list is empty, never an error. A reply that cannot be turned into valid proposals — because it is not the machine-readable form REQ-LIBRARY-020 accepts, or because its entries fail REQ-LIBRARY-009 — MUST take that recovery path, and nothing from it may reach a stored artifact or any review surface. Every proposal that does reach a review surface MUST consequently carry at least one evidence entry; name exactly one `target_persona` when its category is `persona_memory_update`; carry a complete `proposed_verifier_section` when its category is `verifier_gate_update` (REQ-LIBRARY-063); hold a category from the closed vocabulary of REQ-LIBRARY-006, an unrecognised value having been coerced under REQ-LIBRARY-021 rather than the proposal dropped; and not repeat an outstanding gate proposal (REQ-LIBRARY-026). This list is the whole of what the product guarantees about an analysis pass, and no further guarantee is expected of it or of the executor: whether a proposal is useful, novel, or non-speculative is a property of the model's judgement, is not decidable by the product, and MUST NOT be stated as a requirement. The product's answer to a poor proposal is the human gate — the proposal is rejected, and a rejected proposal suppresses nothing later (REQ-LIBRARY-030, REQ-LIBRARY-046) — not a quality test the product could not run.

**REQ-LIBRARY-017** — Analysis MUST draw only on material belonging to the run that triggered it: that run's progress, its todo state, its child reports, its gate evidence, its transcript, and the bounded prior-artifact history of REQ-LIBRARY-034. Data from another run, another session, or another workspace MUST NOT inform it. Every proposal in an artifact MUST therefore be attributable to material that existed in the session named by that artifact's `source_session_id` at the moment the run reached its terminal state, and every prior artifact that informed it MUST be named through `considered_session_ids` (REQ-LIBRARY-025).

  > **Extended by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002), 2026-09-17.** The
  > fence above governs the per-run analyst and still governs it exactly as written — it is the
  > reason that pass cannot meet a cross-session request, and the reason the corpus needed a new
  > mechanism rather than a widened one. The directive's retrospective is a different pass, scoped to
  > the workspace this requirement's third clause already names as the outermost boundary: it reads
  > across this workspace's own sessions and never outside the workspace, its evidence stays
  > attributable to the records that hold what it cites, and no clause here is relaxed for it.

**REQ-LIBRARY-018** — The volume of evidence one analysis pass consumes MUST be bounded, so that the outcome a user sees does not change with the size of the run: a very long transcript, a large set of child reports, or a workspace holding many prior artifacts MUST still produce a result within the timeout of REQ-LIBRARY-039. Wherever evidence text is shortened to respect a bound, the shortening MUST be marked with `…`, so that any excerpt reaching a stored artifact is either complete or visibly cut. The bounds themselves are fixed by REQ-LIBRARY-165 and are not configurable.

**REQ-LIBRARY-019** — Of the six evidence sources named in REQ-LIBRARY-017, one that could not be obtained MUST NOT be treated as one that was obtained and reported nothing; in particular a gate report that failed to run MUST NOT be indistinguishable from a gate that ran and found nothing. Neither case may cause the analysis to fail (REQ-LIBRARY-033). Where the difference reaches a stored artifact it MUST be visible there: a gate proposal made without a known gate state or configuration fingerprint records the literal `unknown` in place of the missing value (REQ-LIBRARY-029) instead of asserting a state nobody observed. The distinction MUST also be observable to a reader of the stored artifact: every one of the six sources that could not be obtained MUST be named in the produced artifact's `notes`, so an analysis made without the transcript is distinguishable from one made over an empty transcript. A source that was obtained and reported nothing MUST NOT be named there, and naming an unavailable source MUST NOT by itself make the analysis fail or the artifact invalid.

**REQ-LIBRARY-020** — Analyst output parsing MUST: strip one leading/trailing Markdown code fence if present; require a JSON object containing a `proposals` list of objects; assign a fresh proposal id when the model omits one; backfill each evidence entry's `source_session_id` with the current session id; and stringify a non-string `notes` value.
  > **Narrowed by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002) revision 2, 2026-10-13** ([OQ-236](../architecture/open-questions.md#oq-236)). For a retrospective the parser keeps an evidence entry's
  > `source_session_id` only when it names a session in the job's `considered_session_ids`, and otherwise stores null; it
  > never backfills one, since a retrospective has no current session (clause (b)).

**REQ-LIBRARY-021** — Given a proposal whose category value is not in the closed vocabulary, the proposal MUST be kept with its category coerced to `workspace_note` rather than dropped — surfacing evidence outranks category fidelity.

**REQ-LIBRARY-022** — On the first parse or validation failure the analyst MUST retry exactly once, re-issuing the same request augmented with the parse error and a demand for corrected machine-readable output only (at most 2 model calls total). If the retry also fails, the result is an empty artifact with `notes` = `collector parse failed: <err>`.

**REQ-LIBRARY-023** — On timeout the result MUST be an empty artifact with `notes` = `collector timed out after <t> seconds`. On any other crash, `notes` = `collector crashed: <exc>`.

**REQ-LIBRARY-024** — A provider that never answers MUST NOT extend anything the user is waiting on. Within `runtime.improvement_collector_timeout` seconds of the pass starting, the empty-artifact outcome of REQ-LIBRARY-023 MUST have taken effect and the analysis MUST read as finished on every surface — its activity indicators gone (REQ-LIBRARY-125) and its notice, if any, already posted — even though the provider call has not returned. For as long as that call stays outstanding the application MUST still accept composer input, MUST still start new runs on request, and MUST still begin shutting down on request. The process MUST NOT block on the outstanding call before it exits: shutdown abandons it (REQ-LIBRARY-127).

**REQ-LIBRARY-025** — The produced artifact's `considered_session_ids` MUST record the source-session id of each prior workspace artifact supplied as history, deduplicated in encounter order.

**REQ-LIBRARY-026** — After parsing, each `verifier_gate_update` proposal MUST be stamped with a citation of the gate evidence it was made from and dropped when it repeats a prior gate proposal that is still `pending_review` with the same dedupe key. This deduplication MUST be enforced by the product itself rather than merely requested of the model.

**REQ-LIBRARY-165** — The bounds REQ-LIBRARY-018 requires are fixed by this requirement, are the same in every workspace, and MUST NOT be exposed as configuration: the configuration surface of this domain is exactly the three keys of section 6. Applied to the six evidence sources of REQ-LIBRARY-017, they are: at most the 200 most recent transcript events, each event's text cut to at most 2,000 characters and the whole transcript block cut to at most 40,000 characters; at most the 100 most recent run-progress entries; at most 200 todo items; at most 20 child reports, each cut to at most 4,000 characters and the whole child-report block cut to at most 60,000 characters; the rendered gate-evidence text of REQ-LIBRARY-028 cut to at most 8,000 characters; and the at most 5 prior artifacts of REQ-LIBRARY-034, each rendered to at most 4,000 characters. Where more material exists than a bound admits, the material kept MUST be the most recent, so the evidence a pass consumes always ends at the moment the run reached its terminal state. Every cut MUST be marked with `…` per REQ-LIBRARY-018. Because the bounds are constants, two runs over the same session produce the same evidence regardless of how large the session grew.

### 4. Gate evidence

**REQ-LIBRARY-027** — Gate evidence MUST be a JSON value that survives being stored on an artifact and read back unchanged. One capture MUST yield one gate description: the text a person reads (REQ-LIBRARY-028), the evidence entry stored on a proposal, and the dedupe key computed for it (REQ-LIBRARY-029) MUST all describe that same captured state, so no two of them can disagree about the gate. The record MUST carry the gate's overall state; the fingerprint of the gate configuration it was taken from; where the check suite was obtained and the form in which it was declared; for every configured check its name, command, verification role, severity, and working directory; the probe results; the per-check outcomes; the checks that could not be executed; and the verification roles no configured check covers. The serialized key names MUST be exactly: `state`; `config_fingerprint`; `suite_origin` and `suite_declaration`; `checks`, each entry carrying `name`, `command`, `role`, `severity` and `cwd`; `probes`, each entry carrying `command`, `role`, `verdict` and `note`; `outcomes`, each entry carrying `name`, `status` and `exit_code`; `unrunnable_checks`; and `uncovered_roles`. `state` holds the completion-gate decision of REQ-ORCH-116, `config_fingerprint` the marker-content fingerprint the gate lifecycle record of REQ-ORCH-125 carries, `role` and `severity` values from the vocabularies of REQ-CONFIG-145, `status` a value from the check-status vocabulary of REQ-ORCH-123, and `verdict` a probe verdict from REQ-TOOLS-159. A value that was not observed MUST be written as JSON null or omitted entirely, never as the string `unknown`; only the rendered text of REQ-LIBRARY-029 substitutes that literal.

**REQ-LIBRARY-028** — Gate evidence MUST have exactly one text rendering, used both where a person reads it and where it is stored in an evidence entry, so the two can never differ. A record carrying no gate state MUST render as the empty string; a workspace whose gate is satisfied therefore contributes no gate text anywhere and produces no gate-related signal. Otherwise the rendering MUST contain one line beginning `gate state: ` and naming the state; one line per configured check beginning `check <name> [<role>/<severity>]`; one line per probe result; one line per check outcome; one sentence naming every check that could not be executed and therefore demonstrated nothing; and one sentence naming every verification role for which tooling is present but no configured check exists. The state named on the first line MUST be the completion-gate decision of REQ-ORCH-116 (`passed`, `gated`, `exempt`); a capture whose run recorded no completion-gate decision, and a capture whose decision was `passed` with no unanswered check and no uncovered role, MUST carry no state and therefore render as the empty string. A probe line MUST be rendered as `'<command>': <verdict> — <note>`, the form REQ-TOOLS-159 fixes for a probe result. An outcome line MUST begin `outcome <name>: <status>`, the status drawn from the check-status vocabulary of REQ-ORCH-123. Ordering is fixed: the per-check lines follow the order in which the resolved check suite declares the checks, the outcome lines follow that same order, and the probe lines follow it too with probes of commands no configured check declares placed after them. The two closing sentences MUST convey, respectively, the name of every check that did not answer its question and that it therefore demonstrated nothing, and the name of every verification role the workspace carries a marker for but no configured check covers; their wording is left to the implementation, subject to one rendering being used everywhere.

**REQ-LIBRARY-029** — After stamping, a gate proposal's `evidence` list MUST hold exactly one entry whose `kind` is `verifier_gate_state`, and that entry MUST be the last one: an entry of that kind already present is removed and the new one appended, so stamping twice never leaves two. That entry's `text` MUST read `gate state <state> at fingerprint <first 12 characters of the fingerprint>`, with the literal `unknown` in place of whichever of the two values is missing, and its `excerpt` MUST be the dedupe key. The dedupe key MUST be a 16-character lowercase hexadecimal digest covering both halves of the suggestion: the proposed gate-configuration block, and the gate situation it was made from (state, configuration fingerprint, the checks that could not run, and the uncovered verification roles). Changing either half MUST change the key, so the same block re-proposed against a materially different gate situation counts as a new suggestion and is not suppressed. Proposals of every other category MUST be left untouched by this step. The key MUST be the first 16 characters of the lowercase hexadecimal SHA-256 digest of a canonical UTF-8 JSON encoding of the pair, and that encoding MUST be canonical in exactly this sense: a JSON object holding the two members `section` (the proposed gate-configuration block) and `situation` (an object holding `state`, `config_fingerprint`, `unrunnable_checks` and `uncovered_roles`); every object member ordered ascending by the Unicode code points of its key; `unrunnable_checks` and `uncovered_roles` each deduplicated and sorted ascending by code point; an unobserved `state` or `config_fingerprint` written as JSON null; and no insignificant whitespace. Two implementations reading the same workspace therefore compute the same key from the same suggestion.

**REQ-LIBRARY-030** — Gate-proposal duplicate detection MUST compare the new proposal's key against the key recorded on each earlier gate proposal when that earlier proposal was created, never against a key freshly recomputed from current evidence. Only prior proposals still in `pending_review` suppress a new one; proposals in `rejected` or `approved` status MUST never suppress a new proposal.

**REQ-LIBRARY-031** — Uncovered-role detection MUST consider exactly three verification roles: `test`, `typecheck`, and `lint`. A role MUST be reported as uncovered when the workspace carries a marker for that role and no configured check declares it. A role for which the workspace carries no marker MUST NOT be reported, and neither MUST a role that some configured check declares — including a check that failed or could not be executed. A role counts as present in the workspace exactly when the check auto-detection of REQ-ORCH-122 recognises, at the workspace root or at a subproject root, a marker implying a check of that role — `pyproject.toml`, `package.json` or `Makefile`, read by the rules that requirement fixes. No other file, directory, or convention makes a role present, and a marker that cannot be read or parsed makes none present and MUST NOT fail the capture.

### 5. Post-run capture and eligibility

**REQ-LIBRARY-032** — Analysis capture MUST yield no job at all (not an empty artifact) when ANY of the following holds: the run type is not `task_run`; no analyst is configured; the setting `runtime.improvement_collector_enabled` is false; the run's recorded stop reason is one the skip list of REQ-ORCH-137 names, which is the single definition of when an improvement pass is not collected and which this domain does not restate; or the run has no persisted session record. What this domain relies on is that the skip list is stated in stop-reason tokens of the closed set of REQ-MONITOR-301 and is compared against the recorded stop reason by exact, case-sensitive equality, so a stop reason outside the list always yields a job. The last condition names the session's persisted record and not any directory: what makes a job impossible is that the run has no session record to be analysed from.

**REQ-LIBRARY-033** — Evidence MUST be frozen at capture time by taking independent snapshots of run progress, todo state, transcript events, child reports, workspace history, and gate evidence, so that subsequent work cannot mutate what is reviewed. A failing transcript-context supplier degrades to empty context; child-report coercion failures degrade to an empty list.

**REQ-LIBRARY-034** — Workspace history supplied to the analyst MUST be bounded and filtered: prior artifacts whose `source_run_type` is not `task_run` are excluded, the current session's own artifact is excluded, and at most 5 prior artifacts are included, newest first.
  > **Narrowed by [`PD-LIBRARY-002`](../product/directives.md#pd-library-002) revision 3, 2026-10-13** ([OQ-271](../architecture/open-questions.md#oq-271)). The
  > history also excludes every prior artifact whose `source_kind` is `retrospective`, and that exclusion is applied before
  > the five-artifact bound, so every artifact supplied has a source session (clause (h)). The rest is as stated.

**REQ-LIBRARY-035** — Running a captured analysis job MUST produce exactly one of the following observable outcomes, and MUST never propagate a failure into the run that produced it: (a) cancellation requested before the job starts — no artifact is stored and no notice is published; (b) the pass cannot be started, or fails in a way REQ-LIBRARY-022 and REQ-LIBRARY-023 do not already cover — no artifact is stored, no notice is published, and a warning is recorded in the application log; (c) cancellation observed after the artifact was produced but before it was stored — no artifact is stored and no notice is published; (d) the write fails — no artifact exists to report, the store is left exactly as it was (REQ-LIBRARY-047), and the failure stays out of the run's result (REQ-LIBRARY-161); (e) success — exactly one artifact is stored with cross-artifact duplicate suppression applied (REQ-LIBRARY-046), and the surfaces of REQ-LIBRARY-124 report that artifact and the number of proposals it holds.

**REQ-LIBRARY-036** — Session snapshots MUST persist the session's `run_type` and the list of improvement artifact ids produced for the session, so artifacts re-associate with a session across resumes.

**REQ-LIBRARY-037** — Post-run analysis MUST use the model named by `improvement_collector_model` when that setting holds a value, and the configured medium-tier model otherwise. An explicit request to enable the feature while neither resolves MUST be refused with the message `medium_model must be configured to enable the post-run improvement collector.` and MUST leave `runtime.improvement_collector_enabled` as it was. The refusal covers only an explicit enable: a workspace running on the default-on setting of REQ-LIBRARY-038 with no resolvable model MUST NOT fail — it takes the no-analyst path of REQ-LIBRARY-032, captures no job, and writes no artifact. That path MUST NOT be silent. The first time a task run in that workspace reaches a terminal state while `runtime.improvement_collector_enabled` reads true and no model resolves, the product MUST post one informational notice conveying that improvement analysis is switched on, that no model is configured for it, and that no proposals will be produced until one is; the notice MUST offer an action that opens the Settings view at the improvement-collector model slot, and its wording is left to the implementation. It MUST be posted at most once per workspace per application session, so a misconfiguration cannot become a notice after every run. A startup failure is expressly refused: an optional analysis that is not configured MUST never stop a user from working. The wall-clock bound on the pass is `runtime.improvement_collector_timeout` (REQ-LIBRARY-039).
  > **Narrowed by [`PD-MONITOR-007`](../product/directives.md#pd-monitor-007), 2026-10-06.** The named or medium-tier model
  > is followed through the session's override, and where the pair it reaches is held out of quota for the session the
  > analysis is skipped — no job captured, no artifact written — with a line in the application log saying why. The rest
  > is as stated.

### 6. Configuration

**REQ-LIBRARY-038** — Setting `runtime.improvement_collector_enabled` (boolean, default `true`) is the master switch. When false, no analysis runs and no completion notification of any kind is shown.

**REQ-LIBRARY-039** — Setting `runtime.improvement_collector_timeout` (integer seconds, default `60`, minimum `1`) bounds analyst wall-clock time before the empty-artifact fallback.

**REQ-LIBRARY-040** — `improvement_collector_model` (nullable string, default null) is a first-class startup model slot with an independent thinking-mode override, persisted and round-tripped like other model slots; the minimal bootstrap configuration template includes both keys as null. When unset it falls back to the medium-tier model.

**REQ-LIBRARY-041** — The desktop Settings view MUST expose the master switch as a runtime toggle row labelled "Improvement loop", loading from and saving back to `runtime.improvement_collector_enabled`, and participating in unsaved-changes detection.
  > **Extended by [`PD-CONFIG-003`](../product/directives.md#pd-config-003) revision 2, 2026-10-07.** Beside the toggle
  > row, Settings exposes "Improvement analysis timeout" over `runtime.improvement_collector_timeout`, in seconds clamped
  > 10–600, loading from and saving back to the key and participating in unsaved-changes detection.

### 7. Persistence of improvement artifacts

**REQ-LIBRARY-042** — Improvement artifacts MUST be held in a durable store the application keeps for the workspace. Nothing about how that store is organised is contractual — no path, no file, no document format — and what a user can observe of it is fixed here and by REQ-LIBRARY-043. That store is workspace-scoped and machine-local on the terms REQ-SESSION-197 and REQ-SESSION-198 fix, and an artifact held in it outlives the session that produced it and stays reachable both as that session's own artifact and at workspace scope (REQ-SESSION-007). The store is keyed by workspace, not by session: a review decision recorded by one session MUST still be present after the application restarts, and MUST be what every other session in the same workspace reports once it refreshes (REQ-LIBRARY-164). Every mutation MUST be a read-modify-write against what the store holds at that moment: the writer re-reads the artifact immediately before applying the change and writes back that freshly read state with the change applied, never a copy a surface has been holding on screen. That read-modify-write MUST take effect as one indivisible step, so that no other mutation can be interleaved between its read and its write. Decisions recorded on different proposals of the same artifact consequently both survive — always, and not merely when the later writer's read happened to follow the earlier writer's write. No reader ever observes a partly applied change. The agreement guarantee of REQ-LIBRARY-164 remains an agreement about what the store holds, not a promise that no decision can be overwritten: two decisions recorded on the *same* proposal still resolve to the later one, and whatever the store ends up holding is what every surface reports at its next refresh. **The concession this requirement used to close on is withdrawn as unreachable, not as unimportant.** It accepted that two writers whose read and write genuinely interleaved could lose one of the two changes; an indivisible read-modify-write admits no such interleaving, so the defect can no longer occur. Nothing else about this requirement has changed and no guarantee it stated has been relaxed.

**REQ-LIBRARY-043** — Every write to the store MUST be atomic as seen by a reader: at any instant a concurrent read returns either the complete previous state of the artifact or the complete new one, never a partial, empty, or unreadable one; a write interrupted by a crash or by loss of power MUST leave the artifact readable; and a write that failed MUST leave nothing behind that a later listing (REQ-LIBRARY-045) could mistake for an artifact. *Which of REQ-SESSION-034's three durability levels "readable" means here is that requirement's and not this one's* (accepted amendment 2026-09-06, OQ-12): this store owes level 1 unconditionally — a successful write survives the loss of this process whole — and an artifact written since the last acknowledged terminal commit is an intermediate update under level 3, which power loss may take. What this requirement fixes is that whatever survives is a complete artifact and never a partial one. How the store achieves that is not contractual and MUST NOT be relied on. The whole-document replacement this requirement used to fix, the transient file it staged beside the target, and the bounded Windows retry ladder that guarded that replacement are all mechanism, and they are withdrawn with the document layout they belonged to. The ladder in particular existed because a process outside this application could hold an artifact's file open at the moment of a replace; no writer outside this application can reach a record in this store (REQ-LIBRARY-158), so the condition it bounded no longer arises. What survives is the guarantee stated above, which is what a reader and an interrupted writer can actually observe.

**REQ-LIBRARY-044** — On first store access (list, load, or save), artifacts found at the legacy per-session on-disk location `.rotaris/sessions/<session_id>/improvement_artifacts/*.json` MUST be imported into the workspace store when absent there; malformed legacy files are skipped with a logged warning and are never fatal. This is a migration path out of a layout the product no longer writes, and it reads those files without ever writing one.

**REQ-LIBRARY-045** — Listing artifact ids returns the workspace's artifact ids in ascending lexicographic order; listing full artifacts returns newest-first by `generated_at`; a "latest artifact" query optionally filters by source session; loading an unknown id fails with a not-found error whose message is `improvement artifact not found: <artifact_id>`.

**REQ-LIBRARY-046** — Cross-artifact duplicate suppression, which MUST be applied to every save an analysis pass makes, drops a proposal from the artifact being written when some other artifact in the same workspace already holds an open proposal with the same key. The key is the triple (`category`, `target_persona`, `recommended_action`); text is compared ignoring letter case and ignoring differences in leading, trailing, and repeated whitespace, and two proposals that both lack a `target_persona` match on that element. Open means a status of `pending_review`, `approved`, or `deferred`; a `rejected` proposal MUST NOT suppress anything, so an idea the user turned down can be raised again. Whenever at least one proposal was dropped, the line `Suppressed duplicate proposals already covered by: <ids>.` MUST be appended to the written artifact's `notes`, naming the covering artifacts in ascending lexicographic order.

**REQ-LIBRARY-047** — A save MUST be all-or-nothing: either a schema-valid artifact lands in the store, or the artifact already stored is left exactly as it was and the save reports failure. An artifact that duplicate suppression (REQ-LIBRARY-046) has altered MUST still satisfy the schema after the alteration. Each successful save MUST also record a history version holding exactly the state that was stored (REQ-LIBRARY-049). Recording that version is best-effort: when the artifact is stored but its version cannot be, the save MUST still report success, the change the user asked for MUST still take effect, and the failure MUST appear only in the application log. Recording a version therefore lies **outside** the artifact write's all-or-nothing boundary, and a version that cannot be recorded MUST NOT undo the artifact write it was recording. Review decisions, edits, and deletions consequently keep working in a workspace whose recorded versions cannot be written. One consequence of placing it outside that boundary is stated here rather than discovered: a version can therefore be missing from an artifact's history because it was **never recorded**, which is a different thing from one REQ-LIBRARY-052's retention pruned. **The two MUST be distinguishable**, and the obligation that makes them so is this requirement's. Each artifact write MUST record, **inside** its own all-or-nothing operation, that a version was due for the state it stored, so that a version the best-effort recording then failed to write is afterwards known to be absent and countable rather than leaving no trace at all. What is retained MUST be enough to state **how many** of an artifact's versions were never recorded, and MUST NOT be a copy of what any of them would have held: this obligation records that a version is missing, never the version. Recording that a version was due is not recording the version, so nothing here brings version recording inside the boundary — recording a version stays best-effort, a version that cannot be recorded still MUST NOT undo the artifact write it was recording, and the change the user asked for still takes effect in a workspace whose versions cannot be written. The figure this obligation yields covers versions that were never recorded and nothing else; the figure for versions retention dropped is REQ-LIBRARY-052's, and how the export carries the two is REQ-LIBRARY-176's.

**REQ-LIBRARY-048** — When no explicit write cause is given, a write for an artifact with neither an existing file nor recorded history is attributed `collected` (only initial analysis writes first); any other implicit write defaults to `edit`. Explicit causes are used by review (`status_change`), editing (`edit`), deletion (`delete`), checkpointing (`checkpoint`), and rollback (`rollback`).

### 8. Versioned artifact history

**REQ-LIBRARY-049** — Every artifact write MUST also record the written state as a version of that artifact, carrying `version` (≥ 1, monotonically increasing within the artifact), `recorded_at` (UTC), `cause`, and a full copy of the artifact exactly as it was written. A recorded version MUST be atomic as seen by a reader on the terms of REQ-LIBRARY-043, MUST never be altered once recorded, and MUST be reachable afterwards by artifact id and version number alone. Version numbers are per artifact and are never re-issued. A recorded version MUST never be returned by an artifact listing and an artifact MUST never be returned by a version listing (REQ-LIBRARY-045, REQ-LIBRARY-053), so neither can ever be mistaken for the other.

**REQ-LIBRARY-050** — The history cause vocabulary MUST be exactly: `collected`, `status_change`, `edit`, `delete`, `checkpoint`, `rollback`, `unknown` (the last meaning a state that was already stored before any version was being recorded).

**REQ-LIBRARY-051** — Reading the history of a pre-history artifact MUST synthesize a version 1 from the artifact's current state with cause `unknown` and `recorded_at` equal to the artifact's `generated_at`, writing nothing — opening a workspace never writes to an artifact it was only asked to read. The first history-aware overwrite MUST first seed the pre-existing stored state as version 1 so it is preserved rather than lost.

**REQ-LIBRARY-052** — At most 25 versions per artifact are retained by default, and retention MUST be applied after each version is appended. For a keep count N ≥ 2 the retained set is version 1 together with the newest N−1 versions, so the state as first recorded is never what pruning gives up; with N = 1 only the newest version survives; with N ≤ 0 no version files are kept. Pruning MUST remove the oldest droppable version first, a droppable version being any version that is neither version 1 nor the newest. N is fixed at 25 by this document and MUST NOT be exposed as a configuration key: the configuration surface of this domain is exactly the three keys of section 6, and no other key of any scope changes history retention. The requirement states N generally so that the retention rule is well defined at every value, not so that a user can set one. **Where pruning has dropped versions of an artifact, the store MUST retain enough to say that it has and how many**, because a count taken over the versions that remain describes what is still retained rather than what was recorded, and the export of REQ-LIBRARY-176 must be able to state it. What is retained MUST be enough to state the number pruned, not the pruned versions themselves: this obligation does not defeat retention, and it is not a second copy of the history. It MUST be kept in the same durable operation that appends the version and applies the retention, so no reader can observe a stated number that disagrees with the versions it describes; a number maintained apart from the versions can drift from them, and an export that misstates how much is missing is worse than one that says it does not know. This obligation covers versions pruning dropped and nothing else — a version absent because REQ-LIBRARY-047's best-effort recording never wrote it was never pruned, and MUST NOT be counted here; that case is separately countable because REQ-LIBRARY-047 obliges the store to retain enough to state it, and the two figures reach the export as two (REQ-LIBRARY-176).

**REQ-LIBRARY-053** — History enumeration MUST be defensive: an unreadable or corrupt recorded version is skipped with a warning; listing returns newest-first; loading a missing version fails with `improvement artifact '<id>' has no recorded version <n>`; an unknown artifact yields an empty history.

**REQ-LIBRARY-054** — Given approve → edit → reject applied to one proposal, then four retrievable states exist — the initially collected state plus one recorded state for each mutation — with distinct causes and timestamps; and current-state reads MUST be completely unaffected by the presence or absence of history.

### 9. Review API (status, edit, delete)

**REQ-LIBRARY-055** — Setting a proposal's status MUST rewrite only the matching proposal, persist atomically with cause `status_change`, return the updated artifact, and survive being read back from the store after a restart. An unknown proposal id fails with `proposal '<pid>' not found in artifact '<aid>'`.

**REQ-LIBRARY-056** — Editing a proposal MUST be restricted to the two user-editable free-text fields, `summary` and `recommended_action`; evidence and category remain analyst-authored and immutable through this path. Blank replacement text fails schema validation; unknown proposals fail with the not-found error; the write cause is `edit`.

**REQ-LIBRARY-057** — Deleting a proposal MUST remove exactly the target proposal (others untouched), persist with cause `delete`, and fail with the not-found error for unknown ids. An artifact may end with zero proposals and remains valid.

**REQ-LIBRARY-058** — The approved-proposal filter MUST return only proposals whose status is `approved`.

### 10. Improvement executor (approval-gated application)

**REQ-LIBRARY-059** — The executor's instructions MUST declare: it executes approved proposals only; never resumes, reopens, or reinterprets the original user task; never proposes new improvements; makes the minimal change needed for each proposal; skips unsafe or ambiguous proposals with a stated reason; never expands scope; summarizes applied versus skipped work; and must not trigger another improvement run from its own output.

**REQ-LIBRARY-060** — An improvement run's work plan MUST be derived from the artifact's `approved` proposals and from nothing else. It MUST consist of a single phase named `improvement_run` holding one task per approved proposal whose category is not `verifier_gate_update`. When the artifact holds no approved proposal, building the plan MUST fail with an error stating that an improvement run cannot start without at least one explicitly approved proposal, and no run starts. When every approved proposal is a `verifier_gate_update`, the plan MUST contain no phases at all; those proposals are applied by the product itself (REQ-LIBRARY-063).

**REQ-LIBRARY-061** — Each generated task MUST embed, in its payload: `Proposal: <id> (<category>)`, `Risk: <level>`, `Summary:`, `Recommended action:`, optional `Target persona:`, and an `Evidence:` list of `- [<kind>] <text>` lines. The task name is `Apply improvement <id>: <first 60 characters of summary>`.

**REQ-LIBRARY-062** — `persona_memory_update` tasks MUST additionally name the workspace-relative file `.rotaris/persona_memory/<persona>.md` in the task payload and instruct the executor to append to or update that file while keeping it inside the 200-line cap.

**REQ-LIBRARY-063** — An approved `verifier_gate_update` MUST never become agent work. The product itself MUST write the proposal's `proposed_verifier_section` into the workspace's gate configuration through the same write path and the same validation as any other gate-configuration change, and MUST require no authorisation beyond the recorded human approval of that exact block. Each gate proposal handled this way MUST be reported as one line reading `<proposal_id>: <outcome>`, where `<outcome>` is drawn from exactly four values: `applied` (the block was written and the gate configuration now differs), `unchanged` (the block was already in effect, so the write changed nothing), `invalid` (the block no longer validates under REQ-LIBRARY-009(c) and was not written), and `failed` (validation passed but the write did not complete). Only `applied` and `unchanged` count as the proposal having been applied; `invalid` and `failed` MUST leave the gate configuration exactly as it was and MUST leave the proposal's status untouched.

**REQ-LIBRARY-064** — Preparing an improvement run MUST: load the artifact, filter to approved proposals, build the todo, apply gate proposals, and — as the last step before the run edits the workspace — record the pre-run rollback checkpoint (skippable for dry runs). Rejected proposals MUST never leak into the run payload. A workspace that is not a Git working tree still prepares the run and simply gets no rollback point.

**REQ-LIBRARY-065** — Completing an improvement run records a post-run `applied` checkpoint. This is the reference point a later rollback compares against to tell which changes the run itself produced from which changes the user produced after it. If recording it is skipped, only that distinction is lost; the pre-run point remains usable and rollback still works.

**REQ-LIBRARY-066** — End-to-end acceptance: a completed task run causes exactly one analyst invocation; the resulting artifact's proposals all start `pending_review`; user decisions survive reload; run preparation yields only approved proposals; and the resulting improvement run performs no second analysis pass.

### 11. Rollback of an applied improvement run

**REQ-LIBRARY-067** — Improvement checkpoints MUST live under the dedicated Git ref namespace `refs/rotaris/improvements/<artifact_id>/<sequence>`, disjoint from the session-checkpoint namespace (`refs/rotaris/checkpoints/...`), so that neither feature's pruning can delete the other's refs.

**REQ-LIBRARY-068** — Checkpoint kinds MUST be `pre_improvement` (the state a rollback restores), `applied` (the state the run left, used to measure later user changes), and `pre_rollback` (safety point so an undo of the undo works). Each checkpoint record carries: `sequence` (≥ 0), `ref`, `commit`, `kind`, `created_at`, `files` (paths changed, display only), `proposal_ids` (proposals the guarded run was about to apply), and `tree_root` (the Git top-level it was taken against, enabling cross-worktree refusal).

**REQ-LIBRARY-069** — A workspace with nothing uncommitted MUST still receive a rollback point: the checkpoint records the state the tree is currently in, is registered under the artifact's own ref (REQ-LIBRARY-067), and a later rollback restores that state. The one case in which no checkpoint is produced is a repository holding neither a commit nor any file to record. That case MUST NOT be treated as an error and MUST be reported as the reason `The workspace has no committed content and no files to record, so no rollback point could be taken.`

**REQ-LIBRARY-070** — Before an improvement run edits the workspace, the artifact MUST hold exactly one usable rollback point. When it already holds a `pre_improvement` checkpoint that no rollback has consumed — that is, while `rolled_back_at` is null — that checkpoint MUST be kept and reused rather than superseded; a second attempt after a partly failed run therefore restores the state that existed before the first attempt. Once `rolled_back_at` is set, the next run MUST take a fresh checkpoint. A workspace outside a Git working tree MUST NOT block or fail the run: the run proceeds and its outcome carries the reason `<tree> is not inside a Git working tree, so no rollback point could be taken for this improvement run.`

**REQ-LIBRARY-071** — An artifact retains at most 10 checkpoints by default. A retained checkpoint MUST stay restorable for as long as it is retained, whatever happens to branches, resets, or repository housekeeping in the meantime; only retention pruning may remove one. When the limit is exceeded, the oldest checkpoints MUST be dropped first and their refs deleted with them, except that the newest `pre_improvement` checkpoint is never dropped, so an artifact cannot lose its rollback point to pruning. Sequence numbers MUST be unique within an artifact and MUST never be re-issued: a new checkpoint MUST NOT take a number already used by any ref under `refs/rotaris/improvements/<artifact_id>/`, even when the stored artifact itself records no checkpoint at that number. The limit of 10 is fixed by this document and MUST NOT be exposed as a configuration key: the configuration surface of this domain is exactly the three keys of section 6, and no other key of any scope changes checkpoint retention.

**REQ-LIBRARY-072** — Asking what a rollback would do MUST have no side effects: it MUST NOT touch the working tree, MUST NOT write to the store, and MUST NOT raise. Every refusal comes back as a finished sentence ready to display, and those sentences MUST be: `No improvement artifact <id> exists in this workspace.` when the artifact is unknown; `No rollback point was recorded for improvement <id>.`, or the non-Git reason of REQ-LIBRARY-070, when there is no usable point; `That rollback point was taken in <A>, not in <B>. Restoring it here would overwrite a working tree it never described.` when the recorded tree differs from the current one; `Improvement <id> has a recorded rollback point but its Git snapshot is gone, so it can no longer be rolled back.` when the recorded snapshot no longer resolves; and a sentence describing a failed repository inspection. A preview that succeeds MUST report every path that differs between the working tree and the rollback point, each labelled with what the rollback would do to that path stated from the user's side, together with the paths carrying work done since the run (REQ-LIBRARY-073) and the dirty-blocked reason when one applies. The label vocabulary is closed and holds exactly three values: `delete` for a path the run created, which the rollback removes; `restore` for a path the run deleted, which the rollback brings back; and `revert` for a path the run modified, which the rollback returns to the content the checkpoint recorded. Every previewed path carries exactly one of those three labels. The sentence reporting a failed repository inspection MUST name the improvement, convey that the workspace's Git repository could not be inspected and so no rollback can be previewed, and carry the reason the inspection gave; its wording is left to the implementation.

**REQ-LIBRARY-073** — Work done after an improvement run MUST be measured against the newest checkpoint that still resolves and whose `kind` is `applied` or `pre_rollback`. Neither the current HEAD nor the pre-run checkpoint may serve as that baseline: an edit the run itself made MUST NOT be reported as work done since the run. When the artifact has no resolvable post-run checkpoint, the rollback MUST report nothing at risk and MUST NOT block on that ground, and a working tree identical to the newest post-run checkpoint MUST likewise report nothing at risk. The search MUST consider every checkpoint the artifact still retains and MUST NOT be narrowed further: retention already bounds that list to at most 10 records (REQ-LIBRARY-071), so the search is bounded without a second limit, and a post-run checkpoint that is still retained can never be passed over because it is old.

**REQ-LIBRARY-074** — The dirty refusal MUST convey how many changes made since the improvement run would be overwritten, name at most the first 5 of those paths and state how many further paths there are, and tell the user that the rollback can be repeated with an explicit override that overwrites them; its wording is left to the implementation. That override (REQ-LIBRARY-170) bypasses only this one check and nothing else.

**REQ-LIBRARY-075** — Rollback MUST proceed in this order: load → point present → tree match → ref resolves → diff and dirty check → record a `pre_rollback` safety checkpoint first (failure here blocks with "Could not record a safety checkpoint before the rollback: <reason>" — an irreversible rollback is forbidden) → restore the tree → set the applied proposals back to `pending_review` and stamp `rolled_back_at`. Rollback never raises; every refusal returns a not-restored result with a blocked reason and an untouched tree.

**REQ-LIBRARY-076** — Post-restore status reversal MUST cover only proposals named in the checkpoint's `proposal_ids` that are currently `approved`; an older checkpoint with no recorded ids falls back to reverting every still-approved proposal. If persisting the reversal fails after the tree is restored, the result reports restored-with-warning: "The workspace was rolled back, but the reversal could not be recorded on improvement <id>: <err>. Its proposals still read as approved even though their changes are gone."

**REQ-LIBRARY-077** — After a restore, every path the checkpoint covers MUST hold the content that checkpoint recorded: a path the run created is gone, a path the run deleted is present again with its original content, and a path the run modified reads as it did before the run. The rollback MUST itself be undoable from the `pre_rollback` safety checkpoint of REQ-LIBRARY-075. Restoration goes through the repository, so the repository's own line-ending normalisation applies to restored files exactly as it does to session-checkpoint restores. The canonical guarantee is the normalised one: a restored path MUST hold exactly the content a fresh checkout of that checkpoint would produce in this working tree under the repository's configured normalisation, not necessarily the same bytes the path held before the run. Where those differ, the difference is a property of the repository's own configuration rather than of the rollback, and the product MUST NOT report it as a rollback anomaly.

**REQ-LIBRARY-078** — The tree-mismatch comparison MUST compare fully resolved paths, case-insensitively on Windows.

**REQ-LIBRARY-169** — Rolling an applied improvement run back MUST be reachable from the desktop interface, and from nowhere else. The improvement-artifact detail of REQ-LIBRARY-167 MUST carry a "Roll back" action, enabled exactly when that artifact has a rollback point per REQ-LIBRARY-012 and disabled otherwise with an explanation of why. Activating it MUST first compute the side-effect-free preview of REQ-LIBRARY-072 and show the result in a modal dialog before anything is written: given a preview that would change files, the dialog lists every previewed path in ascending path order, each with its label from the closed vocabulary of REQ-LIBRARY-072; given a preview that would change nothing, the dialog says so instead of listing paths; and given work done since the run (REQ-LIBRARY-073), the dialog additionally warns how many such changes would be overwritten and names those paths. Given a preview that came back refused, the dialog MUST show that refusal's sentence, offer no way to proceed, and leave the working tree and the stored artifact untouched.

**REQ-LIBRARY-170** — A rollback MUST NOT start until the user confirms it in the dialog of REQ-LIBRARY-169. The dialog's choices are a confirming action and Cancel, with Cancel selected by default; choosing Cancel MUST change nothing in the store, nothing in the working tree and nothing on screen. When the preview is blocked only by work done since the run, the dialog MUST additionally offer an explicit, separately activated override that proceeds anyway; that override is the force choice of REQ-LIBRARY-074 and REQ-LIBRARY-163, it MUST be off unless the user turns it on for this one rollback, and it MUST bypass only the dirty-tree check. When the preview is blocked for any other reason, no override may be offered.

**REQ-LIBRARY-171** — A rollback started from the desktop MUST report its outcome to the user rather than finish silently. A completed rollback MUST post a persistent success notice conveying which improvement was rolled back, how many files changed, how many proposals returned to `pending_review` and which they are when any did, and that a safety checkpoint now holds the pre-rollback state (REQ-LIBRARY-075). A refused rollback MUST post an error notice carrying the refusal's own displayable sentence (REQ-LIBRARY-072) and MUST leave the working tree and the stored artifact exactly as they were. A rollback that restored the tree but could not record the status reversal MUST post a warning notice carrying the discrepancy of REQ-LIBRARY-076 — the tree is already restored, so this is never reported as a failed rollback. In every case the improvement-artifact detail and the proposal surfaces MUST re-read the stored state afterwards (REQ-LIBRARY-164). The wording of these notices is left to the implementation.

### 13. Session artifact store (agent reports and published deliverables)

Each artifact's Markdown document — the rendered form REQ-LIBRARY-090 fixes, carrying that artifact's body — MUST be kept **on disk as a file the record references and never holds inside itself**: a body may be arbitrarily large, and the document exists so that a person or another tool can read the artifact without this application. That file is one of the artifact bodies REQ-SESSION-002 places beside the session's stored record, which is the single definition of where those files live and of what may live there; this domain names no location of its own and adds no fourth kind of per-session file. Every write MUST be atomic as seen by a reader on the terms of REQ-LIBRARY-043, mutations MUST be serialized within the application (REQ-LIBRARY-158), and the store MUST outlive loop iterations so earlier-phase findings remain available to later children.

**REQ-LIBRARY-088** — An artifact record MUST carry: `id`, formed as `art_` followed by 8 base62 characters; `slug`, kebab-case, at most 64 characters, made unique within the session by appending `-2`, `-3`, and so on; `title`; `kind`, one of `child_report`, `agent_published`, `system`; `source_task_id`; `canonical_name`; `source_persona`; `status`, which is `succeeded` unless set otherwise, `published` for an agent publish, and the report's own status for a materialised child report; `summary`; `key_findings`; `highlight_paths[]`; `snippets[]`; `edited_files[]`; `created_files[]`; `tags[]`; `supersedes` and `superseded_by`; `created_by`; `consumed_by[]`; the ids linking the record to its timeline entry and to its conversation, carried as `timeline_event_id` and `conversation_id`, both nullable and both null until the link exists; `importance`, which MUST be `high` when the record is a child report whose status is anything other than `succeeded` and `normal` in every other case; `created_at`; `edited_at`, null until a person edits the body; and `body_markdown`. `status` MUST hold a value from a closed set formed in exactly one way and in no other: every member of the child-report status vocabulary REQ-ORCH-112 defines, which is the product's single definition of that vocabulary and which this requirement does not restate and does not narrow — a materialised child report carries the report's own status unchanged, so every value a report can carry is a value an artifact record can carry — together with `published`, which only an agent publish produces (REQ-LIBRARY-093) and which no child report ever carries. **REQ-LIBRARY-176** — **The improvement store exports.** A workspace's improvement artifacts MUST be obtainable as a file the user chooses, in a form that yields every field of every artifact, every proposal and every retained version to a stock parser on a machine with none of this product's code present. That guarantee is REQ-EVENTS-166's and is not restated in a second form here; this requirement applies it to the improvement store on the same terms REQ-SESSION-199 applies it to the timeline, the issues record, the metrics document and the permission audit. The export MUST be offered both for a single artifact and for every artifact of the workspace, MUST be reachable from the artifact detail of REQ-LIBRARY-167 and from the artifact list of REQ-LIBRARY-166, and MUST be available whether or not any session is live, because artifacts are workspace-scoped and outlive the session that produced them (REQ-LIBRARY-042).

What it MUST carry is the artifact container's fields (REQ-LIBRARY-011), each proposal's fields including its evidence entries (REQ-LIBRARY-008, REQ-LIBRARY-010) in stored order, and **the recorded version history REQ-LIBRARY-168 calls "the audit trail the write path keeps"** — every retained version with its `version`, its `recorded_at`, its cause from the closed vocabulary of REQ-LIBRARY-050, and the state that version holds, so the `summary` and `recommended_action` each proposal carried at each recorded decision point leave the machine with the artifact rather than being readable only on screen (REQ-LIBRARY-049, REQ-LIBRARY-162). **The history exports as an audit**: every retained version in the order the versions were recorded, none omitted, and — where retention has dropped intermediate versions (REQ-LIBRARY-052) — a statement that it has and how many, so a pruned history can never be mistaken for a complete one. REQ-LIBRARY-052 is what obliges the store to retain enough to say so; that obligation is stated there and is not restated here. A recorded version that cannot be read MUST be reported as skipped rather than dropped without trace, which is what REQ-LIBRARY-053 already requires of the listing.

That statement accounts for pruning and for nothing else. REQ-LIBRARY-047 makes recording a version best-effort and places it **outside** the artifact write's all-or-nothing boundary, so a version can also be absent because it was **never recorded** — a different thing from a pruned one, and one the user was told about only in the application log. **The export MUST tell the two apart.** It MUST carry, for each artifact, **two separate figures** — how many versions retention dropped (REQ-LIBRARY-052) and how many were never recorded (REQ-LIBRARY-047) — each identified by which of the two it is. It MUST NOT merge them into one figure for absent versions, MUST NOT state either without saying which it is, and MUST NOT carry either in a shape shared with the export of a store whose absences have only one cause (REQ-TRACE-514), because a shape that fits both erases the distinction. Where neither has occurred each figure MUST still be stated, as zero, so that a complete history says so and silence never has to be interpreted. The two mean different things to a user reading an audit trail — a pruned version is the record working as designed, a never-recorded one is a gap in the record — and an export that presented them alike would report a defect as a policy, or a policy as a defect. Neither obligation to retain enough to state a figure is this requirement's: they are REQ-LIBRARY-052's and REQ-LIBRARY-047's, stated there and not restated here. What this requirement adds is that the export MUST NOT convey, by its wording or by its shape, that the versions it carries together with those two figures are every version this artifact's mutations should have produced, since neither figure is a reconstruction of what a missing version held.

Exporting MUST write nothing to the store, MUST NOT create, restore or repair a version, and MUST NOT alter the current artifact — the same read-only discipline REQ-LIBRARY-168 places on the history surface. **It is not a channel**: it is a user-initiated action producing a file at the moment it is asked for, it MUST NOT refresh itself, and no surface may be built on repeating it. A workspace holding no artifacts, or an artifact holding no proposals or no readable version, MUST export an empty record of that kind rather than nothing at all, so that absence is distinguishable from failure. **The destination is the one write this domain makes whose target the product does not choose**, and it may be anywhere the user's save dialog reaches — removable media, storage shared with another machine, a folder a synchronisation client replicates, or a directory the user has the previous export open in. Where the file the user chose already exists, replacing it MUST take the retry ladder REQ-TRACE-061 states for a replacement onto storage this product does not choose; that requirement states the ladder and it is not restated here. **This domain states no replacement ladder of its own.** REQ-LIBRARY-043's was withdrawn with the document layout it governed, and the reason it gave — that no writer outside this application can reach a record **in the store** (REQ-LIBRARY-158) — does not reach a destination outside the store that the user named, so it is cited here as inapplicable rather than reinstated. A failure MUST be reported per REQ-LIBRARY-173 and MUST leave the store exactly as it stands.

**Why it exists and where its boundary is.** Improvement artifacts were material a user could open and read for themselves before they became records the application keeps (REQ-LIBRARY-042); without an export, moving them into that store would be a straight reduction in what a user owns about their own runs. A record gains an export when it carries no unredacted user or tool content, and the improvement store qualifies because what it holds is the analyst's own proposals and the evidence entries backing them, written to be reviewed. The export MUST therefore carry the artifact exactly as stored, adding nothing to it and reaching nothing it does not already hold: in particular it MUST NOT resolve an evidence entry's `source_session_id`, `source_artifact_id` or `source_task_id` into the material those ids name, because a session's tool-call evidence deliberately holds unredacted arguments and never gains an export of its own (REQ-SESSION-136). An export that followed those ids would become the export that record is denied.

### 19. Prompt stash and prompt history

**REQ-LIBRARY-137** — Prompt history MUST front-insert each sent or queued prompt and nothing else — composer text consumed locally as a slash command is neither sent nor queued and MUST NOT be recorded (REQ-LIBRARY-142) — suppressing only adjacent duplicates (a new entry equal to the current front item is not added). The stash front-inserts non-empty text. Popping a stash entry removes and returns it by index; an out-of-range index returns an empty string without error. Every mutation triggers the library-changed refresh-and-persist cycle.

**REQ-LIBRARY-138** — Saved prompts — the prompt history and the prompt stash — MUST persist in the durable store the application keeps for the workspace, and MUST still be there after the application restarts without the user having taken any action to save them. *This requirement once said "flushed to disk", the only durability verb the corpus carried, and that phrase promised a level it never named* (accepted amendment 2026-09-06, OQ-12): what is owed here is REQ-SESSION-034's level 1 — a write reported successful survives the loss of this process whole — and surviving a restart is exactly that. Prompts written since the last acknowledged terminal commit are intermediate updates under level 3 and MAY be lost to power loss; this requirement claims nothing stronger and no surface may. Each change to either list MUST be persisted as part of the library-change cycle it belongs to (REQ-LIBRARY-105, REQ-LIBRARY-137), and persisting one entry MUST NOT require rewriting the others: a library change that touches neither list writes neither list. A persistence failure MUST surface a persistent desktop error notice "Could not save prompt history" with detail "Rotaris will keep prompts in memory for this window.", and the prompts MUST stay usable in that window exactly as that detail says.

**REQ-LIBRARY-139** — History is capped at 200 entries and the stash at 100, enforced on both load and save with silent truncation of the oldest entries. Stored prompts that are absent, unreadable, or not of the expected shape load as empty state; loaded entries are stringified and blank entries removed. Those two limits are intended and are fixed by this document: neither is configurable, and no key of any scope changes them. They bound a convenience store rather than a record of work — the durable record of what a run was asked to do lives in the session, not here — so a user losing the two-hundred-and-first oldest prompt loses nothing that is not recoverable elsewhere.

**REQ-LIBRARY-140** — The workspace composer MUST show a ghost "Stash" button ("Stash prompt for later") that stashes the current composer text, and the transcript toolbar a ghost "Apply stash (<count>)" button (accessible name "Manage prompt stash", tooltip "Apply or pop a stashed prompt") whose count updates live.

**REQ-LIBRARY-142** — Two slash commands MUST mirror the stash controls. `/stash`, described as "Stash the composer prompt", stashes the composer's current text exactly as the composer's Stash button does (REQ-LIBRARY-140). `/pop`, described as "Apply a stashed prompt", opens the prompt stash dialog (REQ-LIBRARY-141); the command itself removes nothing, and the user's choice of Apply or Pop inside that dialog decides whether the entry stays in the stash. ### 22. Ordering, timing, and concurrency

**REQ-LIBRARY-156** — For a completed desktop run the observable ordering MUST be: terminal session state persisted → analysis job captured (evidence snapshotted) → queued to the background worker → analyst runs (within its timeout) → artifact saved with duplicate suppression → proposals re-read into the UI → notice published. The user may start follow-up work at any point after the first step.

**REQ-LIBRARY-157** — Analysis activity MUST be published as its own independent flag that never alters the run state or session status fields.

**REQ-LIBRARY-158** — Within the running instance, session-artifact-store mutations are serialized and the record and its index entry are persisted together (REQ-LIBRARY-087), and every window and every run shares that serialization because there is only one instance (REQ-STARTUP-161). Both the session artifact store and the improvement artifact store are the application's own: **no writer the application does not serialize can reach a stored record** — not the user's own editor, not a version-control operation over the workspace, not an instance left behind by a crash — so the uncoordinated-writer case this requirement used to arbitrate no longer arises, and the file locking it declined is not needed to replace it. What still moves underneath a surface is another surface or another run of this same instance, and that is what the desktop's reload-on-vanished-proposal path exists for (REQ-LIBRARY-173). It resolves exactly as REQ-LIBRARY-042 states: each mutation re-reads before it writes, the read-modify-write takes effect indivisibly, a later decision on the same proposal wins, and no reader ever sees a partial state. The artifact bodies that remain files on disk (REQ-LIBRARY-087, REQ-SESSION-002) sit outside that serialization, and nothing here claims otherwise.

### 23. Cross-cutting invariants

**REQ-LIBRARY-159** — No proposal with an empty `evidence` list may exist anywhere: construction MUST fail (REQ-LIBRARY-009), storing one MUST fail validation (REQ-LIBRARY-014, REQ-LIBRARY-047), and a proposal returned without evidence MUST NOT be repaired into existence by supplying evidence on its behalf. The `verifier_gate_state` entry the product stamps onto a gate proposal (REQ-LIBRARY-029) is not such a repair: it is added to a proposal that already carries at least one analyst-authored entry, and it MUST NOT be the only entry that proposal holds. Reading every stored artifact in a workspace MUST therefore find, on every proposal, at least one evidence entry, and at least one whose `kind` is not `verifier_gate_state`.

**REQ-LIBRARY-160** — A task run MUST NOT change the workspace as a consequence of its analysis. Across a completed task run, the only things analysis may create or modify are the improvement artifact and its recorded version in the store; **every path in the workspace** — configuration files, personas, persona memory, gate configuration, and all the rest — MUST hold the same content afterwards as before, and no path in the workspace may be created or deleted. The guarantee is consequently stronger than it was when the artifact was itself a file in the workspace, and it is stated that way deliberately rather than left to be inferred. A change a proposal describes takes effect only once that proposal's status is `approved` and a run of type `improvement_run` applies it; a `verifier_gate_update` takes effect only through the deterministic writer of REQ-LIBRARY-063, from the complete block already inside the proposal, and never through an agent.

**REQ-LIBRARY-161** — No analysis failure may show up in the task run itself. For every failure mode — the pass cannot be constructed, the model call raises, the output fails to parse twice, the timeout elapses, or the artifact cannot be written — the run's terminal state, its recorded result, and the moment that result is reported MUST match what the same run would have produced with `runtime.improvement_collector_enabled` set to false; in particular the result reaches the host before any analysis work begins (REQ-LIBRARY-004). The worst outcome a user may observe is an artifact holding no proposals whose `notes` names the failure, or no artifact at all.

**REQ-LIBRARY-162** — Every mutation of an artifact — a status change, an edit, a deletion, a recorded checkpoint, and a rollback — MUST go through the write path of REQ-LIBRARY-047 and MUST leave behind a recorded version naming its cause from the vocabulary of REQ-LIBRARY-050. For as long as those versions survive retention (REQ-LIBRARY-052), the exact `summary` and `recommended_action` a proposal carried at each recorded decision point MUST be readable back from history, and pruning MUST give up intermediate versions before it gives up either version 1 or the newest version.

**REQ-LIBRARY-163** — A rollback MUST never leave the workspace in a state the user cannot get back out of. It MUST refuse to proceed when a `pre_rollback` safety checkpoint cannot be recorded first, when the working tree holds work done since the run and the user has not deliberately overridden that refusal (REQ-LIBRARY-170), and when the recorded checkpoint belongs to a different working tree than the one being restored. Every refusal MUST leave both the working tree and the stored artifact exactly as they were and MUST come back as a displayable reason rather than a failure the caller has to handle (REQ-LIBRARY-072, REQ-LIBRARY-075). When a rollback does proceed, every proposal it undid MUST return to `pending_review`, so no proposal reads as `approved` while its changes are gone; when that update cannot be persisted, the discrepancy MUST be reported to the user (REQ-LIBRARY-076) rather than passed over. A workspace with no Git repository MUST lose only the rollback capability: analysis, review, and application all continue to work.

**REQ-LIBRARY-164** — Every surface that shows improvement proposals — the Library's proposals tab, its improvement-artifact list and detail (REQ-LIBRARY-166, REQ-LIBRARY-167), and the dashboard card — MUST read and write the same stored artifacts (REQ-LIBRARY-042), with the same review semantics. A decision recorded on any one of them MUST be the state each of the others reports at its next refresh — the Library's update cycle (REQ-LIBRARY-105) and the dashboard card's live update (REQ-LIBRARY-130) — and no surface may hold a private copy that can disagree with the store; a mutation reads the store immediately before writing it (REQ-LIBRARY-042). How each surface presents that state remains its own.

## Data & Formats

### Improvement artifact record

- Held in the durable store the application keeps for the workspace (REQ-LIBRARY-042). No path, file or document format is contractual; the observable contract is the field set below plus the atomicity of REQ-LIBRARY-043.
- Top level: `artifact_id` (`impart_` + 8 base62), `source_session_id` (input alias `session_id` accepted), `source_run_type` (`task_run` | `improvement_run` | `integration_run`), `generated_at` (UTC ISO), `collector_model` (string | null), `proposals[]`, `considered_session_ids[]`, `notes` (string | null), `checkpoints[]`, `rolled_back_at` (UTC ISO | null).
- Proposal: `id` (`imp_` + 8 base62), `category` (10-value vocabulary), `summary`, `evidence[]` (≥ 1), `recommended_action`, `risk` (`low`|`medium`|`high`), `status` (`pending_review`|`approved`|`rejected`|`deferred`), `target_persona` (string | null), `proposed_verifier_section` (mapping | null), `created_at`.
- Evidence: `kind`, `text`, `source_task_id`/`source_artifact_id`/`source_session_id` (nullable), `excerpt` (optional).
- Checkpoint record: `sequence`, `ref`, `commit`, `kind` (`pre_improvement`|`applied`|`pre_rollback`), `created_at`, `files[]`, `proposal_ids[]`, `tree_root`.

### Recorded artifact versions

Each recorded version carries `{version, recorded_at, cause, artifact}` with cause ∈ {`collected`, `status_change`, `edit`, `delete`, `checkpoint`, `rollback`, `unknown`}, is reachable by artifact id and version number, and is never altered once recorded (REQ-LIBRARY-049). Retention 25 versions per artifact (version 1 protected while keep ≥ 2); fixed by REQ-LIBRARY-052 and not configurable, which also obliges the store to retain enough to state how many versions pruning dropped. Recording a version sits outside the artifact write's all-or-nothing boundary (REQ-LIBRARY-047), so a version can be absent because it was never recorded rather than pruned; that count covers pruning only, the artifact write records inside its own boundary that a version was due so the never-recorded case is separately countable (REQ-LIBRARY-047), and the export carries the two as two figures (REQ-LIBRARY-176).

### Git ref namespaces

Improvement checkpoints: `refs/rotaris/improvements/<artifact_id>/<sequence>`. Session checkpoints (adjacent domain): `refs/rotaris/checkpoints/...`. The namespaces are disjoint and pruned independently. Checkpoint retention: 10 per artifact, newest `pre_improvement` exempt; fixed by REQ-LIBRARY-071 and not configurable.

### Gate evidence mapping

JSON-serializable record carrying: gate state; configuration fingerprint; where the check suite was obtained and how it was declared; one entry per configured check (name, command, verification role, severity, working directory); probe results; per-check outcomes; and optionally the checks that could not be run and the verification roles left uncovered. Serialized key names are fixed by REQ-LIBRARY-027: `state`, `config_fingerprint`, `suite_origin`, `suite_declaration`, `checks` (`name`, `command`, `role`, `severity`, `cwd`), `probes` (`command`, `role`, `verdict`, `note`), `outcomes` (`name`, `status`, `exit_code`), `unrunnable_checks`, `uncovered_roles`. Rendered text lines: one line starting `gate state: `, one line per check starting `check <name> [<role>/<severity>]`, one line per probe and per outcome, one sentence for checks that never ran and one for uncovered roles; empty string when there is no state. Stamped gate evidence entry: `kind` = `verifier_gate_state`, text `gate state <state> at fingerprint <12 chars>` (`unknown` substituted for a missing state or fingerprint), `excerpt` = the dedupe key — 16 lowercase hex characters digesting the proposed block together with the gate state, fingerprint, unrunnable checks, and uncovered roles.

### Analyst I/O

Input: the six frozen snapshots of REQ-LIBRARY-017 — run progress, todo state, child reports, gate evidence, transcript summary, recent workspace improvement history — with an unavailable source kept distinguishable from an empty one (REQ-LIBRARY-019) and at most 5 prior artifacts of history (REQ-LIBRARY-034). Volume is bounded and elisions are marked with `…`; the bound values are the fixed, non-configurable constants of REQ-LIBRARY-165. Accepted model reply: a single JSON object carrying a `proposals` list and optional `notes` (an enclosing Markdown fence is tolerated and stripped).

### Session artifact store

Held per session in the workspace store: one full record per artifact plus a metadata index ordered by creation time, record and index entry written together indivisibly; the artifact's Markdown document, carrying its body, is a file on disk that the record references, placed by REQ-SESSION-002 (REQ-LIBRARY-087). Record ids `art_` + 8 base62; slugs kebab-case ≤ 64 chars, uniquified `-2`, `-3`, …; kinds `child_report` | `agent_published` | `system`; `status` drawn from the set REQ-LIBRARY-088 forms — the child-report status vocabulary of REQ-ORCH-112 plus `published` — which this line neither restates nor closes; tags from the closed vocabulary of REQ-LIBRARY-089, which is the single definition of that set and of its normalisation and refusal. Sidecar: YAML frontmatter (`id`, `slug`, JSON-quoted `title`, `kind`, `status`, optional source ids/tags/supersession links, timestamps), then `# <title>`, then fixed sections: Summary; Key Findings; Highlight Paths; Snippets; Edited Files; Created Files. Timeline diagnostic event kind on materialization/publish: `artifact_published`.

### Injected context blocks

- `PRIOR SIBLING ARTIFACT INDEX` — every artifact rendered on its own single line carrying slug, id, persona, status and a ≤ 160-character summary; 10,000-char budget, unsuccessful statuses ordered ahead of `succeeded` (REQ-LIBRARY-097), elision marker naming the omitted count and the `artifact_list` tool.
- `PRIOR AGENT CONTEXT (FULL)` — full bodies of explicitly attached artifacts, 48,000-char budget, missing references and elided ids reported.
  > *Note, 2026-10-07:* the budget is 100,000 characters with skip-and-continue, by [`PD-TOOLS-006`](../product/directives.md#pd-tools-006) revision 5 (REQ-LIBRARY-098's back-pointer); the line above is kept as written.
- `persona_memory_<persona>` — the persona's memory file content (≤ 200 lines), injected at agent creation only.

### Saved prompts

Two ordered lists of strings — prompt history and prompt stash — held in the workspace store (REQ-LIBRARY-138); history ≤ 200 entries, stash ≤ 100 entries (REQ-LIBRARY-139). No path or document format is contractual.

### Persona memory files

`<workspace>/.rotaris/persona_memory/<persona>.md` — plain Markdown, ≤ 200 lines, newline-terminated, atomic writes; persona names constrained to `^[A-Za-z0-9_.\-]+$`. These stay **files** deliberately: REQ-LIBRARY-150 makes them visible, inspectable and hand-editable, and REQ-LIBRARY-153 reads a hand edit back on the next persona load.

### Configuration keys

- `runtime.improvement_collector_enabled: bool = true`
- `runtime.improvement_collector_timeout: int = 60` (min 1)
- `improvement_collector_model: string | null = null` (+ independent thinking override), fallback: medium-tier model.

These three are the whole configuration surface of this domain. Evidence bounds (REQ-LIBRARY-165), history retention (REQ-LIBRARY-052), checkpoint retention (REQ-LIBRARY-071), and the prompt-history and stash caps (REQ-LIBRARY-139) are fixed constants and are settable by no key of any scope. Desktop-only preferences, such as the Prompts tab's splitter position (REQ-LIBRARY-106), live in the per-user desktop preference store (REQ-SHELL-006) and not in this surface.

### Improvement-artifact inspection and rollback (desktop)

- Artifact list (REQ-LIBRARY-166): newest first by `generated_at`; per row the artifact id, generation time to whole-second precision, whether a rollback point exists, and per-status proposal counts in the order `pending_review`, `approved`, `rejected`, `deferred`, zero counts omitted.
- Artifact detail (REQ-LIBRARY-167): id, `generated_at`, `source_session_id`, status counts, rollback point identified by Git reference and 12-character abbreviated commit, `rolled_back_at` when set, the artifact's proposals in stored order, and the "Roll back" and "Start improvement run" actions.
- Version history (REQ-LIBRARY-168): retained versions newest first with version number, recorded time, and cause; read-only.
- Export (REQ-LIBRARY-176): one artifact or the whole workspace, written to a file the user chooses, carrying the artifact container, its proposals with their evidence, and every retained version in recorded order with **two** separate figures — how many versions retention dropped (REQ-LIBRARY-052) and how many were never recorded (REQ-LIBRARY-047) — never merged, each named for its cause, and each stated as zero when it has not occurred. Replacing an existing file at the chosen destination takes the ladder of REQ-TRACE-061; this domain states none of its own. Read-only, not a channel, and it never follows an evidence entry's source ids into the material they name.
- Rollback (REQ-LIBRARY-169 through REQ-LIBRARY-171): preview first, per-path labels `delete` / `restore` / `revert`, explicit confirmation defaulting to Cancel, a separate override for the dirty-tree refusal only, and a reported outcome in every case.
