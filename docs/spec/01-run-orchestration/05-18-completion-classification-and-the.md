# Multi-Agent Run Orchestration — 18. Completion Classification and the Deterministic Completion Gate

Part 5 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-113 – REQ-ORCH-155.

### 18. Completion Classification and the Deterministic Completion Gate

- **REQ-ORCH-113** — With completion classification enabled (default true), every iteration whose report status is `succeeded` MUST be classified by exactly one small-model call into exactly one of `COMPLETE`, `NEEDS_ITERATION`, `UNCLEAR`. The call MUST be bounded by a 15 s timeout; a timeout, an error, or an answer outside those three values MUST yield `UNCLEAR`. `UNCLEAR` MUST have the same effect as `COMPLETE`, so a failed classification can never hold a run back. `NEEDS_ITERATION` MUST rewrite the report's status to `partial`, which re-queues the task under REQ-ORCH-074, and MUST set the report's message to the classifier's reason together with the original summary. Whichever of the three values results, a `completion_classified` timeline event MUST record it.
- **REQ-ORCH-114** — Classifier model resolution: small model → default summary model → the summarizer's model → skip classification entirely. Inputs are truncated (intent context to 2000 characters, summary to 1500) and open todo items are listed.
  > **Narrowed by [`PD-MONITOR-007`](../../product/directives/pd-monitor-007.md#pd-monitor-007), 2026-10-06.** The resolved model is
  > followed through the session's override, and a resolved model held out of quota skips classification. The truncation
  > is as stated.
- **REQ-ORCH-115** — The completion classifier MUST be skipped for reports attributed to the coordinator role (a coordinator summary describes work handed to other roles and still in flight, which the classifier would routinely read as unfinished); the todo state machine and the child graph drive the outcome instead.
- **REQ-ORCH-116** — After the completion classifier, a deterministic completion gate MUST be applied, and its decision MUST override the classifier's verdict. The decision MUST be exactly one of `passed`, `gated`, `exempt`. Where a check suite executed: a check of severity `blocking` leaves the gate unsatisfied unless its status is exactly `passed`, so `failed`, `timeout`, and `skipped` — including a check the permission policy refused — all gate; there are exactly two exceptions — status `invalid`, which never gates, and a check the user skipped under REQ-ORCH-128, which never gates either and is instead named on the decision record. A check of severity `advisory` never gates, but a failing advisory check MUST be named in the recorded decision. Where no check suite executed, the decision MUST be `exempt`; the cases are an iteration that changed no file, a check-suite configuration that is explicitly empty, a workspace in which detection recognized nothing, and a verifier that was missing or failed (REQ-ORCH-131). Where no verification evidence exists at all, the decision MUST be `exempt` with a fixed reason string that is the same for every such decision. Where the gate's decision differs from the classifier's verdict, that verdict MUST be preserved on the decision record. This requirement is the product's single definition of the completion-gate decision — the three values, the point in the sequence at which the gate is applied, what does and does not gate, and the override of the classifier's verdict. A document that needs to name a gate decision, or to state what makes a check suite block completion, cites this identifier and holds no copy of the three values.
- **REQ-ORCH-117** — A gated succeeded report MUST be rewritten to status `partial` (reusing the existing re-queue semantics; no new status vocabulary), with the decision recorded on the report and emitted as a gate-decision timeline event (warning severity when gated). Gating is on by default; when configuration turns it off the checks still execute and their evidence is still reported, but the LLM verdict is what takes effect. An iteration in which no file changed is never subject to gating.
- **REQ-ORCH-118** — Bounded repair loop: a per-task-id repair budget (default 2; 0 = report failure without retrying) resets per run and is released when a task verifies clean (a later regression starts a fresh budget). The repair decision returns either retry — with a reason of the form "Verification failed (<checks>); starting repair attempt N of M." — or escalate, rewriting the report to failed with a message of the form "Verification still failing after M repair attempt(s): <checks>. Escalating instead of retrying." Escalation deliberately does NOT set the session-abort escalation signal, so one red check can never abort the whole session.
- **REQ-ORCH-119** — Repair context MUST render each failing blocking check — name, command, status, exit code, skip reason, full-log path, output excerpt — capped at 6000 characters total (head kept, with an omission marker stating how many characters were dropped), appended to the re-queued task payload after a verification-failure marker with any previous marker blocks stripped first. Timeline events record repair scheduling (warning) and repair escalation (error), and an optional observer hook is invoked on escalation.
- **REQ-ORCH-120** — Only a re-queue that the gate itself triggers MAY consume repair budget. A re-queue caused by unfinished todo items records the gate decision but leaves the budget untouched, so that two separate budgets never contend over one task. In all other respects a repair attempt is an ordinary iteration and counts toward both the message counter and the consecutive-same-task guard.

### 19. Deterministic Verification

- **REQ-ORCH-121** — The check-suite configuration MUST be three-valued: omitted = auto-detect; an explicit empty list = verification intentionally off (a visible decision); a non-empty list = explicit configuration that wins over detection with no fallback alternatives. The resolved suite records a source in {config, detected, explicit_empty, detection_empty}; an empty detection result MUST be surfaced as "nothing recognized", never as "intentionally off". Suite resolution never raises. The resolved suite and its source are persisted in the session snapshot and in the session's run-configuration record.
- **REQ-ORCH-122** — Auto-detection MUST consider only the project markers `pyproject.toml`, `package.json`, and `Makefile`, located at the workspace root and at subproject roots, and MUST synthesize at most one check for each of the semantic roles test, typecheck, and lint; checks of role `other` are not subject to that one-per-role limit. From `pyproject.toml`: declared pytest configuration, or the presence of a `tests/` directory, yields the check `pytest -q` (blocking, role test), narrowed to the test paths the project declares where it declares any; declared mypy configuration or a `mypy.ini` yields `mypy <declared scope, else .>` (blocking, role typecheck); declared ruff configuration or a `ruff.toml` yields `ruff check .` (advisory, role lint). From `package.json`, only the scripts named `test`, `typecheck`, and `lint` are interpreted, invoked as `npm test` for `test` and `npm run <script>` for the others, with `test` and `typecheck` blocking and `lint` advisory. From a `Makefile`, only the targets named `test`, `typecheck`, and `lint` are interpreted, invoked as `make <target>`, with the same severities; a target is recognized as a target name followed by `:` at the start of a line, and pattern rules and variable assignments are not targets. Build scripts and build targets MUST NOT be synthesized into checks. Detection MUST NOT fail the run: a marker that cannot be read or cannot be parsed contributes nothing. Every recognized marker MUST be recorded in the run-configuration record, including a marker whose implied check was dropped by the one-per-role limit. Where a role has more than one candidate, the order of preference is user-configured, then declared by the project (a script or a target), then synthesized; where the preferred command cannot be launched at all, the next candidate of the same role is used. A check detected in a subproject MUST have `:subdir` appended to its name and MUST carry a working directory expressed relative to the workspace root; an absolute working directory, or one resolving outside the workspace, MUST be rejected as a configuration error when the configuration is loaded. Subproject roots MUST be located by scanning for those same three markers to a maximum depth of 3 directory levels below the workspace root, skipping any directory whose name begins with `.`, any directory the workspace's version-control ignore rules exclude, and the conventional dependency and output directories `node_modules`, `venv`, `.venv`, `dist`, `build`, and `target`. At most 25 subproject roots MUST be considered, taken in ascending lexicographic order of their workspace-relative path; where more exist, detection stops at that many and records in the run-configuration record that it did, so a large monorepo degrades visibly rather than silently. A command "cannot be launched" when it never became a running process — the executable was not found, the operating system refused permission, the working directory does not exist, or the run's permission policy refused it — and only then; a command that started and exited with any status, zero or not, has been launched, and its result is recorded under REQ-ORCH-123 rather than falling through to the next candidate of the same role.
- **REQ-ORCH-123** — The check suite MUST run at most once per iteration, and only where that iteration changed at least one file in the workspace. The changed-file set MUST be the union of two independently gathered sources: the files observed to be modified by the iteration's tool calls, and the files the iteration's report declares as edited or created — a file present in only one of the two still counts. Where that union is empty, no check runs and a `verifier_run_skipped` timeline event records the reason. Checks MUST run one at a time, through the same command-execution path the run uses for any other command, which enforces each check's deadline itself rather than trusting the command to exit, applies the run's permission policy, and applies its sandboxing. A check whose command exits 0 while its output reports failing tests MUST be recorded `failed`, not `passed`. A check the permission policy refuses MUST be recorded `skipped`, naming the rule that refused it, and MUST NEVER be recorded `passed`. Check status MUST be one of `passed`, `failed`, `timeout`, `skipped`, `invalid`. The full output of every check MUST be retained in the session's durable record and MUST be reachable in full from that check's own record, by a path recorded with it, after the run that produced it has ended and without that run existing. Check output is held as a file on disk referenced from the record rather than kept inside it, so that an output of any size is readable as an ordinary file; where within the session's own storage those files live is fixed by the domain that owns the session's layout (REQ-SESSION-001, REQ-SESSION-002) and is not fixed here. The zero-exit rule applies to checks of role `test` and to no other role, and recognition MUST be by an explicit declared pattern and never by a heuristic: a check MAY declare a `failure_pattern` regular expression, and where one is declared and matches the check's combined standard output and standard error, the check is recorded `failed` whatever its exit status. A check declaring no pattern is recorded on its exit status alone. The synthesized `pytest -q` check of REQ-ORCH-122 MUST declare a pattern matching pytest's own failure-summary line; the synthesized `npm test` and `make test` checks MUST declare none, because what those commands print is decided by the project rather than by this product. A pattern that fails to compile is a load-time configuration error, reported as REQ-ORCH-143 reports a duplicate check name. The five-value check-status vocabulary named here is the product's single definition of a check's outcome, and it is closed: a document that renders, transports, or maps a check outcome cites this identifier rather than restating the values, and a rendering or mapping of check outcomes MUST be total over all five.
- **REQ-ORCH-124** — Verification budgets MUST be a per-check timeout (default 600 s) and a whole-suite timeout (default 900 s; null means unbounded). A check's effective timeout MUST be the smaller of its own timeout and the suite budget still remaining. A check for which no suite budget remained and which therefore never started MUST be recorded `skipped`; where that check is blocking, it leaves the completion gate unsatisfied on exactly the terms of REQ-ORCH-116, since it never answered its question. The calibration probe has its own timeout (default 30 s) that is not drawn from the suite budget.
- **REQ-ORCH-125** — The verification gate MUST be in exactly one of the lifecycle states `absent`, `pending`, `calibrated`, `stale`, and that state MUST be readable from `<workspace>/.rotaris/verifier.state.json`, a file the tooling writes and maintains and that users are not expected to hand-edit; the editable check suite stays in the user configuration. The state MUST become `stale` when the workspace's recognized project markers change — one added, one removed, or one whose content changed — and MUST NOT become stale for an ordinary source edit. A conventional test directory (`tests/`, per REQ-ORCH-122) MUST count by its presence alone, so adding or editing a test file does not make the state stale. A workspace with neither a recognized marker nor a test directory MUST be in state `absent`. A calibration probe MUST yield exactly one of `verified`, `empty`, `unavailable`, `undecidable`; `empty` is permitted only for a check of role test whose output positively reports that it collected nothing; a probe that was refused by policy, or whose result could not be read, MUST be `undecidable` and MUST leave the gate state unchanged. A `verifier_gate_calibrated` timeline event MUST be emitted when, and only when, at least one probe actually ran.
- **REQ-ORCH-126** — Gate authoring: on the transition from no recognized markers to markers present, a dedicated gate-authoring role (`gatekeeper`, reachable only through the gate-authoring path and never as an ordinary delegation target) MUST author the suite in a detached task beside the loop — never on the iteration's critical path — with the result binding the next iteration (by invalidating the cached suite). Authoring is on by default; when off, writes route to approval-gated proposals instead. The gate's current state travels on every child report, and a `pending` state means "code exists, nothing was verified". All writes go through a single write authority; the probe and gate-write capabilities are internal to the gate-authoring role and MUST NOT be grantable to any other role by configuration, with write authority evaluated at write time. Gate-weakening operations — dropping a role, lowering severity, emptying the suite — are outside all automatic authority and become improvement proposals deduplicated by content. An `invalid` check is repaired deterministically while the run continues — detection and probing are redone, preserving the check's role and severity — at most once for any given role within a session and without invoking a model. Timeline events record gate writes and skipped authoring.
- **REQ-ORCH-127** — Live verification visibility MUST include timeline events for suite start (size and source), each check start (index/total, command, deadline, severity), each check finish (status, exit code, duration, outcome kind, log path; warning severity on a blocking failure), and suite completion or skip — each mirrored by observer hooks for hosts.
- **REQ-ORCH-128** — While a check suite is running, the user MUST be able to skip the check currently executing; invoked at any other time the control MUST do nothing and report no error, so a host may offer it unconditionally. Skipping MUST interrupt the running command and every process it started, by delivering the terminal interrupt signal to the process group. A command that ignores that signal and keeps running MUST be terminated after a grace period of 5 seconds, and its terminal session torn down with it. A check the user skipped MUST be recorded with status `skipped` and never `failed`, MUST be marked as user-initiated, and MUST NOT be counted or reported as a failing check. A user-initiated skip MUST be exempt from the completion gate: it does not leave the gate unsatisfied under REQ-ORCH-116, and because it triggers no gate-driven re-queue it consumes no repair budget under REQ-ORCH-118 and REQ-ORCH-120. The gate decision MUST nonetheless name every user-skipped check, so the record shows exactly which question the user chose not to have answered. The exemption belongs to a skip the user asked for and to nothing else: a check skipped for any other reason — a permission refusal or an exhausted suite budget included — gates on exactly the terms of REQ-ORCH-116.
- **REQ-ORCH-129** — Single execution authority: the acceptance role never re-runs the bound suite. The delegation layer injects into the acceptance role's payload a verification-evidence block whose heading states that the suite has already executed and must not be executed again, containing a per-check table (check, command, status, exit code, full-output path), an explicit list of checks that did not answer their question, and an instruction that any additionally needed command should name the missing role (feeding a gate-update proposal) rather than licensing a suite re-run. An empty evidence block is the fallback: the acceptance role runs commands itself and discloses that it did. The current iteration's evidence is published for host consumption.
- **REQ-ORCH-130** — Requirement-coverage evidence and scope-drift findings, when the workspace has a requirement store and files changed, MUST attach to the report as runner-owned fields that report but never gate, with a timeline event (warning severity when gaps or drift exist).
- **REQ-ORCH-131** — The loop MUST tolerate a missing or failed verifier entirely: no evidence → exempt gate; a broken verifier can never abort an iteration.

### 20. Cancellation and Shutdown

- **REQ-ORCH-132** — Cancelling a run MUST stop every descendant: the stop request sets the stop flag, releases any message-limit pause gate, cancels all pending question prompts and permission approvals (approvals fail safe as denied), gracefully pauses every active conversation (a forced stop additionally closes them), and cancels in-flight work thread-safely — a forced stop performs a second sweep for work created during the first.
- **REQ-ORCH-133** — Bulk child cancellation MUST cancel all active children, wait up to 5 s for them to settle, then mark any still-non-terminal record cancelled with a report stating it was cancelled during parent failure cleanup plus a force-cancelled warning issue. Single user-initiated cancellation MUST cancel the one child, wait up to 5 s, mark it cancelled with a report stating the user cancelled it, emit a user-cancelled timeline event, and return false for unknown or already-terminal children.
- **REQ-ORCH-134** — Graceful pause MUST honor a tool deadline (default 30 s, valid range 5–120): in-flight tool calls are awaited before force-closing. The pause performed to inject a parent notification MUST never force-close (the parent must keep its connections alive to be resumed). Pause and close operations MUST never block the run's event handling (a blocking close must not freeze interrupt handling). Beyond the conversation-lifecycle facts this domain states — the tool deadline and its bounds, the no-force-close rule for a notification pause, the non-blocking rule above, the `child_conversation_closed` event and discarded waits of REQ-ORCH-098, and the context-overflow recovery of REQ-ORCH-093 — the threading model, the shape of streamed model events, and any retry below the classification of REQ-ORCH-092 are implementation design decisions that this document does not constrain and that no conformance claim here depends on.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 3).** A pause does not wait on a tool call suspended on a person: that call is cut off at once and recorded as interrupted; every other in-flight call is still awaited within the deadline.
- **REQ-ORCH-135** — An iteration cancelled mid-run MUST close its own record as cancelled with a report stating the run was cancelled before the agent finished, then sweep the ledger; bookkeeping errors during this cleanup are swallowed so they never replace the original exception. An iteration that raises closes its record as failed with a report stating it ended with an unhandled error.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 4, 2026-09-28.** Clauses 2, 3 and
  > 15: an iteration a pause, a stop or a quit leaves with an agent unfinished stays open, and the continue resumes
  > it. This requirement governs the explicit cancel, a run the product ends on its own account, and a rest that
  > finds nothing unfinished.
- **REQ-ORCH-136** — A user-requested interrupt yields stop reason `user_cancelled`, and the terminal run result that stop reason carries is REQ-MONITOR-301's to fix. A child cancelled because the run concluded while it was in flight receives a diagnostic explaining exactly that.

### 21. Post-Run Improvement Pass

- **REQ-ORCH-137** — Once a task run has reached a terminal state, an improvement-collection pass MUST be handed to the host to run away from the run's own critical path, so that the run's duration, stop reason, and terminal status are the same whether that pass runs, is slow, or fails. It MUST be given a snapshot of the evidence it needs — the progress record, the todo state, the transcript events, the child reports, up to 5 improvement artifacts produced by earlier sessions in the same workspace, and the verification-gate evidence — and that snapshot MUST NOT change afterwards, whatever the run or any later run does to the originals. The pass MUST be skipped when the run is not a task run, when the collector is disabled (it is enabled by default), when the run has no durable session record to draw that snapshot from, or when the stop reason is one of `user_cancelled`, `agent_session_aborted`, or `application_shutdown` (each a member of the closed set of REQ-MONITOR-301). That three-token skip list is the single definition of when an improvement pass is not collected, and a document that needs to name it cites this identifier rather than restating it. `application_shutdown` is on the list for the same reason as the other two: a run ended by the application being asked to quit produced no evidence about how the work went, only about when it was cut short, so a pass over it would learn from the shutdown rather than from the run. It MUST be bounded by its own timeout (default 60 s), and any failure, that timeout included, MUST yield an empty improvement artifact rather than an error. The run-type vocabulary is exactly two values. A `task` run carries a top-level user task through the iteration loop, which is every run the rest of this document describes. A `maintenance` run is one the product starts for its own upkeep and which carries no user task; the detached gate-authoring task of REQ-ORCH-126 is the only one this document defines. Only a `task` run performs the improvement pass.

### 22. Observability

- **REQ-ORCH-138** — A host MUST be able to observe a run without taking on all of it: it may subscribe to any subset of the observation points this domain publishes — session start and end, iteration start and end, child lifecycle, todo state changes, verification events, repair escalation, message-limit pause, token metrics — and MUST NOT be required to supply the remainder. An exception raised by anything a host supplies MUST NOT change the run's outcome, stop the run, or be reported as a run failure: the run continues and reaches the same stop reason and terminal status it would have reached with nothing observing it at all.
- **REQ-ORCH-139** — A run MUST record, in the session diagnostics, timeline events named only from the timeline-event vocabulary and issues named only from the issue-kind vocabulary set out in Data & Formats, and MUST NOT use any name outside those vocabularies for them. Those diagnostics form part of the session's durable record and MUST remain readable after the run has ended, whether or not the session is live and whether or not the run that produced them still exists. A user MUST also be able to obtain them outside this application: the timeline and the issue record are among the records the session domain's export reaches (REQ-SESSION-199, offered as an action by REQ-SESSION-191), so a reader holding only what was exported, on a machine carrying none of this product's code, can read every timeline event and every issue this domain requires a run to record, with the names fixed here intact. Reading them — from the store or from an export — is never a way to follow a run as it happens (REQ-SESSION-071): the export is a user-initiated action producing a file, and it is not a second channel onto a live run.
  > **Extended by [`PD-ORCH-014`](../../product/directives/pd-orch-014.md#pd-orch-014), 2026-10-06.** The vocabularies this requirement
  > closes the names to also hold the words that directive adds to domain 01's timeline list and issue kinds, the chat
  > domain's timeline words ([`PD-CHAT-009`](../../product/directives/pd-chat-009.md#pd-chat-009)) and domain 05's two presence words
  > ([`PD-TOOLS-011`](../../product/directives/pd-tools-011.md#pd-tools-011)). The closure itself is unchanged and still governs in full.
- **REQ-ORCH-140** — Every child's conversation transcript MUST form part of the run's own durable record, written by the run itself and not dependent on any host: a run observed by no host, and a run whose host observer raises, MUST leave transcripts that are identical and equally complete, and every event of every child's conversation MUST be recoverable from that record after the run has ended. Nothing about a host — its presence, its absence, the subset of observation points it subscribed to (REQ-ORCH-138), or an exception it raised — MUST change which events are recorded or how complete the record is. Where those transcripts are held is fixed by the domain that owns the session's persistence (REQ-SESSION-001, REQ-SESSION-198) and is not fixed here.
- **REQ-ORCH-141** — Per-child tool-call timing MUST be recorded as diagnostics (call id, status, elapsed milliseconds, arguments/result, outcome kind, exit code), and replayed tool-call ids MUST be deduplicated.
- **REQ-ORCH-142** — The run's own usage aggregate is authoritative for per-iteration token/cost accounting; provider-reported totals are cumulative and MUST be replaced, never summed. Per-agent token, cost, and last-prompt-token snapshots feed the host UI.
- **REQ-ORCH-155** — Every surface this domain requires a user to be shown MUST be reachable in the desktop interface, within the seven primary views of REQ-SHELL-023 and using the one action vocabulary of REQ-SHELL-048. Those surfaces are: the intent status of REQ-ORCH-014; the plan gate of REQ-ORCH-153; the live child graph with each child's state from REQ-ORCH-040 and its role, canonical name, and task id; the model-slot and rate-limit waits of REQ-ORCH-050 and REQ-ORCH-091 with their three resolutions; the message-limit dialog of REQ-ORCH-086; verification progress under REQ-ORCH-127 together with the skip control of REQ-ORCH-128; repair scheduling and repair escalation under REQ-ORCH-119; and the run-progress summary of REQ-ORCH-082. What each surface MUST convey is fixed by the requirement that names it and is normative. Its layout, typography, placement, and animation are not fixed by this domain and are governed by the desktop shell, including REQ-SHELL-149 (state never conveyed by colour alone), REQ-SHELL-135 (reduced motion), and REQ-SHELL-022 (every control reachable and fully labelled at the minimum window size). Each of these surfaces MUST reflect a state change the run has recorded within 100 ms of the run recording it, **at the 95th percentile**. That figure is a percentile and not a bound on every sample: a build meets this requirement when the 95th percentile of the interval, measured from the run recording a change to the surface showing it, is within 100 ms, and a single update that took longer is not by itself non-conformant. The percentile is stated rather than left to be inferred, so that the figure here and the one REQ-MONITOR-222 states are read the same way.
