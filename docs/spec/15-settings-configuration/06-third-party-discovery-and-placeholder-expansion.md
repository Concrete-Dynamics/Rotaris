# Settings and Configuration — Third-party discovery and placeholder expansion

Part 6 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-219 – REQ-CONFIG-247.

### Third-party discovery and placeholder expansion

- **REQ-CONFIG-219** — A discovered file's server map is read from a `mcpServers` key, falling back to a `servers` key — the cross-client interoperability point. A non-mapping value at either yields nothing, without a warning.
- **REQ-CONFIG-220** — A discovered server name must begin with an ASCII letter and may otherwise contain only ASCII letters, digits, underscores and hyphens; a name outside that shape is skipped with a warning naming both the name and the file. A non-object entry is skipped with a warning. Any failure while building a single entry skips **that entry only**, with a warning naming the server and the file.
- **REQ-CONFIG-221** — For a discovered entry with no explicit `type`, the transport is inferred: `http` when a `url` is present, otherwise `stdio`. An HTTP or SSE entry carries `url`, `headers`, `env` and `cwd`; a stdio entry carries `command`, `args` (defaulting to empty), `env` and `cwd`. Discovered entries therefore never set `request_timeout`, `disabled_tools`, `tool_name_map` or a cached tool list — those are configuration-file-only.
- **REQ-CONFIG-222** — Every tool server in the final configuration carries a provenance value observable to the user: `yaml` when the name appeared in either scope's `agents.yaml` `mcp_servers:` block (the union of both scopes, determined before the merge), otherwise the discovery source tag (`discovered-project` or `discovered-user`), otherwise `default`.
- **REQ-CONFIG-223** — There is no blanket environment-variable override mechanism over configuration keys. Environment variables enter configuration at four narrow points only: a tool server's `env` values, a tool server's `url`, discovered-file placeholders, and a model entry's `api_key_env`.
- **REQ-CONFIG-224** — In a configured tool server's `env` values, the placeholder pattern is **anchored**: only a value that is entirely `${VAR}` is expanded. `prefix-${VAR}` is preserved as a literal string. When the named variable is absent from the environment, **the key is omitted from the resolved environment entirely** — the literal placeholder is never handed to the server process. Non-placeholder values are preserved verbatim.
- **REQ-CONFIG-225** — In a configured tool server's `url`, the placeholder pattern is **unanchored**, so placeholders embedded within the address are substituted in place. The resolution order is shell environment first, then stored secrets, with the later overriding the earlier. A placeholder that neither source resolves is **left in the address literally** — it is never replaced with an empty string, because an address silently shortened by a missing key can reach an unintended host — and a warning is emitted naming the tool server, the variable and the file the entry came from. An entry whose resolved `url` still carries a placeholder is retained in the configuration and marked unavailable, so no request is ever sent to it and any attempt to use it is refused with a reason naming the unresolved variable. An unresolved placeholder never fails the load.
- **REQ-CONFIG-226** — Discovered files use a different placeholder dialect, applied to every `env` value and to `cwd` (which is additionally path-normalized): `${workspaceFolder}` expands to the workspace root path; `${env:NAME}` expands to the named environment variable **or the empty string when absent**; any other placeholder is left literally in place and logged as unknown.
- **REQ-CONFIG-227** — A discovered server entry may name an `envFile`. A relative path resolves **against the directory of the discovered file**, not the workspace. The file is read with a minimal dotenv grammar: blank lines and lines beginning with `#` are skipped; lines without `=` are skipped; key and value are trimmed; a value wrapped in matching single or double quotes is unquoted by one layer; later duplicates win. An unreadable file yields nothing with a warning naming the file.
- **REQ-CONFIG-228** — Values from an `envFile` are overlaid by the entry's explicit `env` map: an explicit entry beats the file.

### Validation and error reporting

- **REQ-CONFIG-229** — Validation has exactly two stages with different failure modes. **Schema validation** raises and is fatal: structural and typing problems abort the load. **Referential validation** returns a list of human-readable messages and **never raises**; an empty list means valid, and callers decide what to do with the list.
- **REQ-CONFIG-230** — Referential validation reads the discovery snapshot to determine whether any provider is configured; **any** failure reading it is swallowed and treated as "no snapshot". When no provider is present, an actionable sign-in hint is appended to the relevant messages; when a provider is present the messages stay terse. A user who has never signed in therefore gets guidance while a signed-in user gets a plain report of a genuine misconfiguration.
- **REQ-CONFIG-231** — Referential messages are produced in this order. An empty `models:` map reports that no models are configured, with the sign-in hint appended per REQ-CONFIG-230. Then, per role: `model` naming no configured model; `summary_model` naming no configured model, checked only where one is stated; a `delegates_to` entry naming no configured role; an `mcp_servers` entry naming no configured tool server; an `mcp_tools` key for a server the role does not list in `mcp_servers`, since such a grant confers nothing and must not read as a working restriction; a tool named more than once across `tools` and `custom_tools` taken together, reported sorted; and a name in `tools` that is neither an accepted public tool name nor the name of a configured tool server, reported together with the sorted list of accepted names. Tool names that exist for internal use only are outside the accepted set and are therefore reported by that last rule. The accepted set is exactly the public tool-name registry REQ-TOOLS-001 fixes: this specification fixes the validation rule, the order the messages are produced in and the requirement that the message carry the accepted names sorted, and reads the name set from that registry rather than restating it, so a name added there is accepted here with no change to this document. That registry also carries the per-tool capability declaration of REQ-TOOLS-001 — whether each name reads workspace files, writes workspace files, or runs commands — which this document neither restates nor varies. What this requirement relies on it for is only that the registry it validates names against is the same registry a rule elsewhere resolves a capability against, so a name this validation accepts always carries a declaration and a name it rejects never reaches one; a requirement in any domain that resolves a rule against a tool's capabilities cites REQ-TOOLS-001 for the declaration itself rather than this requirement, which fixes no capability of its own.
- **REQ-CONFIG-232** — Remaining referential rules: a `default_persona` naming no existing role; `default_summary_model` unset, or naming an unknown model; each of `small_model`, `medium_model` and `large_model` unset or naming an unknown model, and `fallback_model` naming an unknown model — it cannot be unset by the time this runs (REQ-CONFIG-067) — with the message naming both the field and the offending value; `compressor.model` naming an unknown model; and delegation cycles, reported as a cycle path sliced from the first repetition so that the message names the cycle itself rather than the whole traversal.
- **REQ-CONFIG-233** — The severity taxonomy across the whole load is a contract. **Fatal**: YAML syntax error; a primary configuration file that is not valid UTF-8 (REQ-CONFIG-462); non-mapping top level; a `hooks:` value that is neither mapping nor list; a bad hook event, matcher or blank command; a bad confinement mode, egress disposition or relative writable root; a bad check name, command, `cwd` or `failure_pattern` (REQ-CONFIG-146); a run-start mode outside `auto` and `plan` (REQ-CONFIG-476); a duplicate check name or duplicate requirement source id; an unknown key under `requirements:` that this specification has never defined (REQ-CONFIG-183). **Silent**: a missing or empty file; extra top-level keys in `models.yml` (REQ-CONFIG-004). **Warn and continue**: an unknown top-level key, and an unknown key inside a merged section other than `requirements`, each reported naming the key and the file and each contributing nothing (REQ-CONFIG-040); a key under `requirements:` that this specification itself defined and has since withdrawn, or that it names as not a configuration key of this domain, which is reported and ignored while the load completes and the workspace opens (REQ-CONFIG-183); a corrupt discovery snapshot; a circular startup-model alias chain; a reasoning override on an unconfigured or missing base model; a tool-server `url` left carrying an unresolved placeholder (REQ-CONFIG-225). **Coerce**: an unknown permission mode (runtime or per role) → `restricted`; an unknown non-interactive approval policy → behaves as `deny`; an unknown board role name → the workspace default role. **Report, not fatal**: every referential error. This requirement fixes the severity of each condition and nothing else; what a **fatal** outcome conveys to the user and what recovers from it is REQ-CONFIG-478's, and what the withdrawn-key warning conveys is REQ-CONFIG-183's.

### Startup configuration validation and recovery

- **REQ-CONFIG-234** — *Withdrawn.* Its whole surface was a `-c`/`--config` file named on a command line, and the product has no command-line invocation. No capability is lost: the layered configuration surface is the two scopes of REQ-CONFIG-001 and nothing else (REQ-CONFIG-031, REQ-STARTUP-111), a user who wants different configuration edits the global or the workspace file directly or through the settings screen (REQ-CONFIG-256, REQ-CONFIG-441), and the related question of letting a deliberate act rather than the accident of opening a checkout decide whose hooks may run is carried by the hook review of REQ-HOOKS-016.
- **REQ-CONFIG-235** — *Withdrawn.* It described how the file withdrawn by REQ-CONFIG-234 was folded in as a sixth layer; there is no sixth layer, and the fixed, total order of the five that remain is stated by REQ-CONFIG-031.
- **REQ-CONFIG-236** — *Withdrawn.* It described the post-merge passes applied to the file withdrawn by REQ-CONFIG-234 and the hook scope stamp that file carried. The passes themselves are unchanged and apply to every layer (REQ-CONFIG-035, REQ-CONFIG-036, REQ-CONFIG-037); the hook scope stamp vocabulary is exactly `default`, `global` and `workspace` (REQ-CONFIG-151, REQ-HOOKS-014).
- **REQ-CONFIG-237** — Schema failures are reported to the user as one line per problem: `<dotted.path>: <message>`, with an empty path rendered as `config`, and the framework's "field required" phrasing rewritten as "missing required field". If the conversion produces nothing, exactly one generic line stating the configuration is invalid is emitted — the list is never empty.
- **REQ-CONFIG-238** — Missing-field errors whose path is `models` → `<name>` → `<field>` are not reported one line per model. They are gathered and reported as exactly **two** lines: the first names every affected model, models in sorted order and each model's required fields in sorted order; the second states that a `models:` entry is replaced as a whole across configuration scopes, so an override of that model has to repeat `provider` and `model_id` even when only some other field is being changed.
- **REQ-CONFIG-239** — When at least one reported message starts with a model-incomplete prefix, mentions the incomplete-model phrasing, and names `model_id` or `provider`, the application reports that incomplete provider model overrides were detected, runs a model refresh across all providers **without prompting**, reports the refresh result, and **retries the configuration load once**. If the retry also fails, every message is reported to the user as a configuration error, each naming what it names, and the workspace does not open on that configuration; no internal diagnostic detail is shown with them.
- **REQ-CONFIG-240** — *Withdrawn.* It enumerated the flags of a run command, and the product has no command line. Every capability those flags carried is reached from the desktop: the workspace whose configuration directory is read through the chooser of REQ-SHELL-021 and REQ-STARTUP-041; resuming a session through REQ-SESSION-182 and REQ-SESSION-184; isolation, worktree use and the worktree branch name through the session-launch dialog of REQ-GIT-118 and REQ-GIT-158; the run's role and its iteration cap through the run overlays of REQ-CONFIG-263; access beyond the workspace through REQ-TOOLS-191 and the confirmation of REQ-CONFIG-327; and signing a provider out through REQ-CONFIG-383. The additional configuration file is withdrawn with REQ-CONFIG-234, and the machine-readable output format is withdrawn outright — a stream shaped for a script has no reader in a graphical application, and exporting a session's events is REQ-EVENTS-173.
- **REQ-CONFIG-241** — *Withdrawn.* It described two flags of REQ-CONFIG-240. Both settings survive as run overlays applied from the interface's live state (REQ-CONFIG-263): the run's default role comes from the composer's role selector and, unlike the flag, **is** checked against the configured role set before it is applied, and access beyond the workspace is the confirmed control of REQ-TOOLS-191 and REQ-CONFIG-327.
- **REQ-CONFIG-242** — *Withdrawn.* It stated that a flag's iteration cap was passed to the run rather than written into `runtime.max_iterations`. The capability — an iteration cap that governs one run without being committed to a file — is exactly the Tier B rule of REQ-CONFIG-262 and REQ-CONFIG-263, over the control of REQ-CONFIG-325.
- **REQ-CONFIG-243** — *Withdrawn.* Its whole surface was a sign-out flag. Signing out of a provider, clearing its stored credentials while retaining its configuration, is the Log out action of REQ-CONFIG-383 over the semantics of REQ-PROVIDER-143.
- **REQ-CONFIG-244** — *Withdrawn.* It specified argument-shape checks and process exit codes for the flags of REQ-CONFIG-240. Nothing is lost: each choice those flags carried is made through a control that offers only valid values, so an invalid selection is unreachable rather than diagnosed, and the product exposes no exit status to a user.
- **REQ-CONFIG-245** — Two recovery paths run when referential validation fails while a person is present. (1) If any message contains the sign-in hint, the user is told so and the sign-in flow is offered without leaving the workspace unopened (REQ-CONFIG-371, REQ-PROVIDER-142); on failure the sign-in's own message is reported and no configuration is loaded; on success the message is reported and the configuration is **reloaded and re-validated**. (2) If any remaining message mentions an unknown model, every message is reported as a configuration error, the user is told that the model slots need attention, and the Models category opens in a model-fixing state (REQ-CONFIG-272, REQ-CONFIG-329); the application continues normally once the user leaves it. Neither path is entered without the user seeing what was wrong first.
- **REQ-CONFIG-246** — For a run no person is watching — one the board scheduled, and any other run started without a person present (REQ-CONFIG-198) — both recovery paths of REQ-CONFIG-245 are skipped and referential errors are **always** fatal to that run: there is neither an inline sign-in nor a model editor to offer, so the run ends and every message is recorded against it as the reason it did not start. A referential failure never silently starts a run on a configuration the product could not validate.

- **REQ-CONFIG-478** — A configuration this build refuses to load MUST leave the user able to load it, and the product MUST say what to change. This is the single definition of what a **fatal** load failure (REQ-CONFIG-233) conveys and what recovers from it. It states a floor that the requirements fixing individual fatal conditions add to rather than replace — REQ-CONFIG-237 owns the line form the messages take, REQ-CONFIG-018, REQ-CONFIG-019 and REQ-CONFIG-462 each add what their own condition must name, and REQ-CONFIG-239 owns the one retry there is; none of them is restated here. It was minted because one such failure was reachable by writing a key this specification itself once defined, and **that route is now closed at its source rather than made survivable here**: a withdrawn key under `requirements:`, and a key this specification names as not a configuration key of this domain, no longer fail the load at all but are reported and ignored, on the terms REQ-CONFIG-183 states — which is also where what *that* report conveys is now fixed, this requirement's floor reaching only failures that are fatal. `requirements.delivery.store_subpath` (REQ-CONFIG-192) and `requirements.execution.worktree_subpath` (REQ-CONFIG-194) are exactly those keys and are consequently outside this requirement. What remains within it is every other fatal condition REQ-CONFIG-233 lists — an unrecognized key under `requirements:` that this specification has never defined among them — and the floor stated below is what each of those failures must meet.

  **What the report conveys.** It MUST identify the offending file by its full path and by which scope it belongs to (REQ-CONFIG-001), MUST identify the rejected key or value by its full path within that file, and MUST convey that this build does not recognize it. The additional obligations this requirement used to carry for a key the specification names as withdrawn, or as not a configuration key of this domain, are **not withdrawn but relocated**: that case is no longer fatal and is REQ-CONFIG-183's, which states what its report conveys, including the withdrawn-rather-than-mistyped statement and what became of what the key configured. Nothing that was owed to a user is owed less; it is owed by a different requirement about a different outcome. Opening a workspace is a workflow a user starts, so this failure MUST present as REQ-NOTIFY-001's *failed with one concrete next step named* rather than as a bare error, and the step it names is correcting the rejected key or value in the named file and opening the workspace again. Its wording is left to the implementation; what is fixed is what it conveys.

  **What recovers it, stated as a guarantee rather than left to be discovered.** Correcting the rejected key or value in the named file — removing the key, or replacing the value with one this build accepts — and loading again MUST be sufficient: no other change is required, nothing outside that file has to be repaired, and nothing has been written on the user's behalf in the meantime. The load fails as a whole rather than falling back to a default, repairing the value, or rewriting the file — the same rule REQ-GIT-071 fixes for the values that domain rejects, which this requirement states for this domain's fatal load failures and does not vary. The application MUST continue to run with that workspace's configuration unloaded; a fatal failure in one workspace's scope MUST NOT prevent any other workspace from opening; and nothing in the workspace other than that file is disturbed by the refusal — the repository, the requirement documents and the workspace's session history are untouched. Where the rejected key or value sits in the **global** scope, no workspace opens until it is corrected, which is why naming the scope is not optional: that difference is the whole difference between a five-second edit and an unexplained product. That consequence now falls only where the user's file states something this product has never defined; the one condition that could produce it over a key **this product itself invited** is out of this requirement and reported without failing the load (REQ-CONFIG-183), which is what keeps this floor a statement about genuine faults rather than about our own deprecations.

  **The remedy is available because configuration is a file the user owns and can edit with anything** (REQ-CONFIG-477, ground 3). This requirement adds no surface and grants the product no licence to edit the user's file for them; it fixes what must be true of the refusal so that the file remains a way out rather than a dead end.
- **REQ-CONFIG-247** — First-run onboarding review is detected as follows: the **raw** workspace `agents.yaml` has null for **all** of `small_model`, `medium_model`, `large_model`, `default_summary_model`, `fallback_model`, `improvement_collector_model`, while the **resolved** configuration has a non-null value for at least one of them. This is true after a browser-based sign-in whose slot assignments land only in the discovery snapshot, and false for endpoint providers that write slot assignments directly into `agents.yaml`.
