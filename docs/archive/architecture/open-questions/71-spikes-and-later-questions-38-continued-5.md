**OQ-541 — Which window is PD-STARTUP-011's "window that holds no workspace", when every main window is built for a folder and its capture is fixed then?** *(PD-STARTUP-011, REQ-STARTUP-131, REQ-STARTUP-129, REQ-SHELL-163, REQ-SHELL-010. Raised 2026-11-04 by [R-091](../../../product/requests.md#r-091)'s acceptance plan `hrda`, building [OQ-480](71-spikes-and-later-questions-38-continued-4.md#oq-480)'s ruling; numbered as the next free number on `origin/main` when it was filed.)*

**What is open.** [`PD-STARTUP-011`](../../../product/directives/pd-startup-011.md#pd-startup-011) gives a window "that holds no workspace and whose `diagnostics/outputDir` is unset" the base `<per-user data directory>/diagnostics/rotaris`, "fixed when the window is built", and its reasons name the windows it means: "the welcome window and a refused or failed open, the launches where a fault leaves no other trace". In the build every main window is built for a folder — `MainWindows.build` is called with the launch's folder, the remembered one or the working directory (REQ-SHELL-010's resolution, `resolveStartup`), the chooser's, or a hand-over's — and the `(no workspace)` sentinel is never passed to a build (`setWorkspace` has no caller), while the capture starts when the window is built, before its workspace is opened (`DiagnosticsCaptures.open` in `apps/desktop/src/main/diagnostics.ts`, called from the adapter's `create` in `main/index.ts`). Measured on 2026-11-04 with `pnpm app:drive` at `light` on Windows 11 ARM64: a launch given no folder built its window for the working directory and wrote its run directory under that folder's `.rotaris/`; a launch given a regular file had its open refused (`workspace.not-a-folder`, "This workspace is a file, not a folder") and its capture inactive with `ENOTDIR` under `<file>/.rotaris/diagnostics/rotaris`, so the refused open the directive names keeps no log at all. No launch reaches the per-user base.

**What the build proceeds under.** As ruled: a window built with no workspace and no chosen folder takes the per-user base, fixed when it is built (`diagnosticsBase`, `perUserDiagnosticsBase`, `main/diagnostics.test.ts`), and the card shows it as the folder in force (`DiagnosticsCaptures.folderFor`); a window built for a folder keeps that folder's default whatever its open then does, and is inactive where that base cannot be created.

**What decides it.** A ruling on which windows take the per-user base: (a) a window whose own default base cannot be created when it is built (a file, an unwritable or unreachable folder) takes the per-user base instead, so the base stays fixed at build and the inactive case is the per-user base itself being unwritable; (b) the capture waits for the open to settle and takes the per-user base when it was refused or failed, which moves the window's start and gives up the lines before the open; or (c) as built, the per-user base only for a window built with no folder, which the product does not build today.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended option (a) as a new directive beside PD-STARTUP-011: a window whose default base cannot be created when it is built takes the per-user base, fixed at build, with the card and the capture's first line naming the fallback, a chosen folder never redirected, and PD-STARTUP-011's no-workspace clause left standing though nothing reaches it; Advocate B (the system's lens) recommended option (a) as revision 2 of PD-STARTUP-011, deciding by a directory check at build so that the workspace default holds only for an existing directory where the run directory can be created, every other window taking the per-user base, and nothing created under a path whose open is refused. Ruled: option (a), as revision 2 of PD-STARTUP-011, with B's check at build; (b) and (c) are refused. The grounds, by identifier. PD-STARTUP-011's own reasons name the windows its per-user base is for — "a refused or failed open, the launches where a fault leaves no other trace" — and the 2026-11-04 measurement found that launch inactive with `ENOTDIR` and keeping no log, so (c) leaves the directive's stated purpose unmet in the one case it was minted for and REQ-STARTUP-131's "SHALL never silently disable itself" departed from again. (b) is refused on the record as it stands: PD-STARTUP-011 fixes the base "when the window is built", REQ-STARTUP-129 and REQ-SHELL-163 let a choice reach only windows built afterwards and never a capture already running, PD-STARTUP-011 starts the stream at the capture's start and REQ-STARTUP-130 forbids a buffer before it, so a capture that waited for the open would lose exactly the refusal and warning lines the directive exists to keep, and would tie its start to the workspace service's reply, which `MainWindows.launch` already treats as something that can be missed. (a) keeps every invariant: the decision is made inside `DiagnosticsCaptures.open`, called from the adapter's `create` before the open begins, and depends on nothing the open later does. B's directory check is adopted because `createRunDirectory` creates the base recursively, so a missing workspace path would gain a `.rotaris/diagnostics/rotaris` tree under a folder whose open is then refused with the promise that nothing was written to it; the check `resolveStartup` already makes for a remembered folder (REQ-SHELL-010 (b), `isDirectory`) is the same check, and a folder removed between the check and the create ends in the per-user retry, not inactive. The scope is held where REQ-STARTUP-129 draws it: an unset `outputDir` means "the default location of REQ-STARTUP-131", and it is only that default which is redirected; a folder the user chose through REQ-SHELL-163's chooser is their explicit choice, stays inactive when unwritable as REQ-STARTUP-131 says, and is never moved. REQ-STARTUP-145 supplies the per-user base and its machine-local clause by citation, as revision 1 already does; REQ-SHELL-163's "folder currently in force" is the base the capture actually writes under, so `folderFor` reads the base recorded at build rather than resolving the workspace again, and at `off`, where REQ-STARTUP-130 permits no check, the card shows the workspace default. It is a revision, not a second directive, because the case changes rather than sits beside the old one: revision 1's trigger, "a window that holds no workspace", is one way a default base cannot be created and is subsumed, the inactive clause changes with it, and A's reading would keep a clause the product never reaches beside a new one that overlaps it, which `docs/product/README.md` sends to a revision. Revision 2 leaves the `app-log-NN.jsonl` stream as revision 1 fixed it, so the directive still narrows REQ-STARTUP-132 and its back-pointer stands as it is; the revision retitles the directive, and the PD-STARTUP-011 row in `docs/product/directives.md` takes the new title. Not the owner's: PD-STARTUP-011 was minted by this consortium (OQ-480) and no ESC is involved. The build now proceeds under [`PD-STARTUP-011`](../../../product/directives/pd-startup-011.md#pd-startup-011) revision 2: a main window with `diagnostics/outputDir` unset takes its folder's default base only when that folder is an existing directory at build and the run directory can be created there, otherwise the per-user base, fixed at build and unmoved by the open or by a workspace opened later; nothing is created under a path that is not an existing directory; inactive only where the per-user base itself cannot be created, or where a chosen folder cannot be written; the manifest's `outputBase`, the capture's first line and the card name the base in force and, where the fallback was taken, that the workspace's own folder could not be written and why. What executes: in `apps/desktop/src/main/diagnostics.ts`, `DiagnosticsCapturesDeps` gains `isDirectory`, `open` tries the workspace default only for an existing directory and on a failure there retries once under `perUserDiagnosticsBase`, records the base used per window so `folderFor` and the manifest's `outputBase` answer with it, and names the fallback and its errno in the capture's first info line; a chosen `outputDir` never falls back; `main/diagnostics.test.ts` gains the file, missing-path (and no `<path>/.rotaris` created), unwritable-folder, unwritable-chosen-folder, unwritable-per-user and `folderFor` cases; `settings/DiagnosticsCard.test.ts` holds the card's sentence; one `pnpm app:drive` launch at `light` given a regular file finds `app-log-01.jsonl` under the per-user folder holding the `workspace.not-a-folder` line; the suite `pnpm verify:plan` names for `main/diagnostics.ts`; revision 2 written into PD-STARTUP-011 in place with revision 1's clause quoted beside it, the back-pointers on REQ-STARTUP-131 and REQ-SHELL-163 amended in place, REQ-STARTUP-132's back-pointer left as it stands (revision 2 does not touch the stream), the PD-STARTUP-011 entry in `docs/product/directives.md` taking revision 2's title, and the first execution reported into the directive with a row in `docs/architecture/first-executions.md`. Reopened by a measured finding of a refused or failed open of an existing directory whose log the user could not find, which reopens the check-at-build against an outcome-at-open; or by an owner's request to redirect a chosen folder, which reopens REQ-STARTUP-129's reading and is the owner's.

**OQ-542 — Does a first question saying that a damaged target's lock records could not be read meet REQ-SESSION-201's "stating how many there are"?** *(REQ-SESSION-201, REQ-SESSION-089, [OQ-477](69-spikes-and-later-questions-36-continued-4.md#oq-477), [ADR-0058 part 11](../../../architecture/adr/0058-the-workspace-database/11-corruption-domain-and-recovery-for-a-store.md). Raised 2026-11-04 by the hardening acceptance plan hrda's corrupt-store bundle, building OQ-477's ruling; raised as OQ-541, and renumbered OQ-542 when it landed, `main` having taken OQ-541 meanwhile.)*

**What is open.** REQ-SESSION-201's foreign-lock clause reads: "Where the target store holds such records, the restore MUST report them **together, as one condition covering all of them**, stating how many there are and what they mean". OQ-477 rules that no flow opens a target that failed C1's integrity check, and reads the clause as binding only where the product can establish that the target holds such records, which it cannot without reading them; so the restore's first question over such a target says that any lock records in it could not be read and states the clause's risk — a run on another machine reaching the store may be writing to it now, and the restore replaces what it writes — with proceeding never pre-selected (`unreadableTargetText`, `apps/desktop/src/main/store-resolution.ts`), and calls that the clause's purpose met with no words departed from. Building it found one case the reading does not reach: the clause's condition is the store holding such records, not the product knowing that it does, and a damaged store can hold them. `packages/workspace/src/workspace.test.ts`'s fixture for this ruling holds a lock row naming another machine on pages the restore never reads; the restore proceeds on the user's confirmation and no count was stated. The consortium's critic read the clause so when OQ-477 was ruled, and the ruling kept it as a reading. The specification does not say what a restore owes when such records may exist and cannot be read.

**What the build proceeds under.** OQ-477 as ruled, nothing minted: the first question states that the store failed its check with SQLite's report, that how many sessions it holds cannot be read and neither can any lock records in it, the risk the clause requires, and that every session in it will no longer be listed; Cancel is the default. The restore's own gates read no rows of such a target (`restoreStore`'s `targetUnreadable`).

**What decides it.** A ruling that the reading stands (the clause binds only where the records can be read, and is met), or that the words are departed from for a target that failed its integrity check — a directive narrowing REQ-SESSION-201's foreign-lock clause for that case, with what the confirmation states in place of the count.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended that the words are departed from for this one case and PD-SESSION-005 minted, narrowing REQ-SESSION-201's foreign-lock clause only for a target that failed C1's integrity check, the first question stating that the lock records cannot be read and the clause's risk, with no behaviour changed, citations moved to the directive and one test case added over the fixture's unread foreign-lock row. Advocate B (the system's lens) recommended the same directive with the first question also stating what such records would mean, and the confirmation's boundary moved into the workspace service by a second decision flag, `proceedWithForeignLocks` required beside `targetUnreadable`. Ruled: the words are departed from, and [`PD-SESSION-005`](../../../product/directives/pd-session-005.md#pd-session-005) is minted, narrowing REQ-SESSION-201's "stating how many there are" to a target that failed its integrity check, with B's sentence on what the records would mean and without B's second flag. The ground is the clause's own condition: "where the target store holds such records" is a fact about the store, not about what the product can establish, and `packages/workspace/src/workspace.test.ts`'s corrupt fixture holds a lock row naming another machine on pages the restore never reads, the restore proceeds on the user's confirmation and no count is stated, so OQ-477's "no words are departed from" does not survive its own fixture and is corrected by a dated note beside it, kept and not repaired. The count is not read because OQ-477's governing invariant stands untouched, nothing opens the damaged target except C1's read-only `checkIntegrity` (ADR-0058 part 11, "never deletes a store and never repairs one in place"), and a number read from damaged pages is not evidence (REQ-SESSION-089's reasoning): "0 lock records" read off them would be false reassurance at the moment the user decides whether to overwrite a store another machine may be writing to. "What they mean" is not departed from, because under the held refusal no store was handed to the run host (OQ-281, OQ-477), so "nothing on this machine writes under them" is true by construction and is stated. IC-4's discharged half stands: its failing cases are a report naming sessions as things to clear one at a time and a confirmation stating the condition without the risk, and the first question does neither. B's second flag is not adopted: the perform's `targetUnreadable` decision is already the record of the one confirmation the first question carries, and a second token for the same confirmation records it twice and adds a press without information (A's cost). The build now proceeds under PD-SESSION-005 over REQ-SESSION-201 for an unreadable target, and under the clause as written for a readable one (the third question, "Lock records name another machine"). What executes it: `docs/product/directives/pd-session-005.md` with REQ-SESSION-201's back-pointer in the same commit and `pnpm symbols` regenerated; `unreadableTargetText` (`apps/desktop/src/main/store-resolution.ts`) gains the sentence on what such records would mean and cites PD-SESSION-005, as does `restoreStore`'s `targetUnreadable` path; `store-resolution.test.ts` pins the wording (cannot be read, what they mean, the risk, `defaultId: 0`); `workspace.test.ts`'s corrupt-store suite gains the case the entry describes, the foreign-lock row on unread pages, the restore proceeding only under the confirmed decision, nothing opening the target, the displaced directory byte for byte; the corrupt-store case of `pnpm store-resolution-proof` is rerun; the report-back goes into ADR-0058 part 11 beside OQ-477's paragraph with one row in `first-executions.md`. Reopened by salvage (ADR-0058 part 11, steps 2 and 3) being built, since a salvaged copy could yield a count that is evidence, or by an owner's request that the damaged target be read for one.
