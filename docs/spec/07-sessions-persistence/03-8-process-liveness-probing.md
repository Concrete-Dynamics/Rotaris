# Session Persistence, Resume, and Background Sessions — 8. Process Liveness Probing

Part 3 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-051 – REQ-SESSION-187.

### 8. Process Liveness Probing

- **REQ-SESSION-051** — The pid liveness probe MUST answer "dead" for any pid ≤ 0, MUST never raise, and MUST answer "alive" whenever the outcome is uncertain. The two error directions are not equivalent: answering "dead" for a live process lets a restore run concurrently with work still in flight, while answering "alive" for a dead one costs the user nothing worse than invoking the explicit repair step.
- **REQ-SESSION-052** — On POSIX platforms: a process-not-found result proves death; a permission-denied result MUST count as alive (the probe was refused, not answered); any other probe error MUST count as dead only when the platform semantics prove absence, otherwise alive.
- **REQ-SESSION-053** — On Windows: the probe MUST NOT deliver any signal or console control event to the target process (in particular, implementing the probe as a null signal is a defect there, because it injects a real console interrupt into the target). Only an OS-level "no such process / invalid parameter" error proves absence; a still-running indication means alive; access denied or any other failure MUST count as alive.
- **REQ-SESSION-054** — The following residual limitations are accepted, documented behavior (not defects to be silently "fixed" in ways that break the resolve-toward-alive rule of REQ-SESSION-051): when the operating system recycles a pid onto an unrelated process, the session reports alive until that unrelated process exits; and on Windows an already-exited process can keep reporting alive while any open handle to it survives. Both resolve toward "live", which is the safe direction. A session held from a different machine is no longer among these limitations: the lock's `host` field (REQ-SESSION-046) makes that case detectable, and REQ-SESSION-056 resolves it toward "live" by construction, so such a lock is never reclaimed automatically. Since the store became machine-local (REQ-SESSION-198), a lock naming another machine is no longer the ordinary consequence of a workspace on shared storage but evidence that the store itself is reachable from more than one machine — a state that should not arise. The `host` field is kept as the defence against it and as what makes the pid probe sound at all, since probing a pid recorded by another machine would be meaningless; the condition is reported as that state rather than as a lock conflict (REQ-SESSION-048). **That inference is only sound because REQ-SESSION-046 fixes what supplies `host`.** A field taken from the machine's operating-system name would make renaming a machine produce the same evidence — every lock this machine wrote would name a machine that no longer exists, and the product would report a state that should not arise for a state that arises routinely. A machine that has been renamed MUST be indistinguishable here from one that has not. A lock that cannot be reclaimed automatically and that the user knows to be orphaned is released through the explicit action of REQ-SESSION-183.

### 9. Stale-Session Detection and Repair

- **REQ-SESSION-055** — Exactly six `execution_status` strings assert that a run is in progress: `starting`, `running`, `background`, `waiting`, `pausing`, `cancelling`. `waiting` is one of them because a run parked on a provider quota wait is still alive and the agents parked on that wait must remain visible as such (REQ-MONITOR-195, REQ-MONITOR-291). The test is exact, case-sensitive equality against that set; every other value — whether it belongs to the wider vocabulary of REQ-SESSION-073 or is unknown to this version — MUST answer "no run in progress". Given one persisted status, every surface that asks the question MUST give the same answer: stale detection and repair (REQ-SESSION-057), the worktree-integration precondition (REQ-SESSION-064), the stale marking in the desktop session list (REQ-SESSION-182), and the settling of displayed agent and tool state (REQ-SESSION-078, REQ-SESSION-079).
- **REQ-SESSION-056** — A session counts as **live** exactly when a lock record is present and it is not proved unheld: it is proved unheld only when the record carries the three fields of REQ-SESSION-046 with their stated types, its `host` names this machine, and the `pid` it records probes dead here. The absence of a lock record is the sole unambiguous signal that no process holds the session; every other case — a record that cannot be read, one that does not carry those fields, one whose `host` is absent or names another machine, one carrying no pid or a non-integer pid, a pid ≤ 0, or a failed probe — MUST report live. This is exactly the test REQ-SESSION-047 applies before reaping, so liveness and reapability can never disagree (REQ-SESSION-171). An empty session id is never live.
- **REQ-SESSION-057** — A session is **stale** if and only if its metadata `execution_status` is in the active set and the session is not live. Sessions in terminal statuses (`completed`, `failed`, `paused`, `idle`, `paused_message_limit`, `interrupted`, `stopped`, ...) are never stale regardless of lock state.
- **REQ-SESSION-058** — Stale detection MUST read only the listing record (including internal sessions) and the lock record, MUST write nothing at all — no state, no file, and no lock touched, which a caller may verify by observing that nothing the session owns has changed — and MUST report an empty result, not raise, over a store it cannot read.
- **REQ-SESSION-059** — Each detected stale session MUST report: the session id, the stuck execution status, `updated_at` exactly as the dead process left it (detection MUST NOT restamp it; an unparseable timestamp normalizes to the epoch); and a human-readable reason. Exactly two conditions can produce a stale session (REQ-SESSION-056), and the reason MUST say which applied: no lock is held for the session at all, or the lock names this machine and the pid it records is gone — the second naming that pid. The wording is left to the implementation; the same text is what REQ-SESSION-062 interpolates and what the desktop shows when it announces a repair.
- **REQ-SESSION-060** — Repair MUST be explicit — never triggered automatically from a read path. A repair MUST: re-check liveness; read the state (unreadable state means "nothing to do"); require an active status; set `execution_status` to `interrupted`; make that correction durable before going further, so it survives the process dying again at once; then best-effort release the orphaned lock; then write a diagnostics timeline entry. Ordering is mandatory — status first, lock second; releasing the lock first would open a window in which the record still asserts a running session with no lock behind it. A failure to make the correction durable MUST leave everything untouched. Repair MUST never raise.
- **REQ-SESSION-061** — The repaired status MUST be `interrupted`, an existing status word chosen because it sits outside the active set, so a repaired session can never again report as occupied.
- **REQ-SESSION-062** — The repair timeline entry MUST have type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, and metadata `{previous_execution_status, execution_status, reason}`. A diagnostics failure MUST NOT fail the repair. **One entry per repaired session, whatever the batch** (accepted amendment 2026-09-06, OQ-46): a repair that corrects several sessions at once writes this entry into each of their records, unchanged and unabbreviated, because the entry is the session's own record of what was done to it and a session whose entry was folded into another's has no record of its repair. What the *user* is shown for such a batch is one aggregate announcement and is REQ-SHELL-155's, not this requirement's; the two are deliberately separate, so a change to the announcement never silently reduces what is recorded.
- **REQ-SESSION-063** — Repair-all MUST repair every stale session and be idempotent: a second pass repairs nothing and rewrites nothing (fingerprint-verifiable). A live session next to a dead one MUST be untouched and keep its lock.
- **REQ-SESSION-064** — Worktree integration's "base not in use" precondition is the one read path allowed to *bypass* (not repair) staleness: a session in an active status whose process is dead MUST be skipped rather than blocking integration forever, with the durable status correction left to the explicit repair action of REQ-SESSION-182; a genuinely live session MUST block integration with the error `A session is still running in the base worktree. Finish it before integrating.`
- **REQ-SESSION-065** — When a run acquires the session lock and has not yet started work, it MUST settle orphaned children: every persisted child-agent record whose state is not in the terminal set `{succeeded, failed, cancelled, blocked}` is set to `cancelled`, given a completion timestamp (UTC ISO with `Z`, only if absent), and has its active-tool list cleared; terminal children keep everything. The operation reports how many records it moved and is idempotent. Holding the lock is itself proof that the previous owner has exited, so this settling step MUST NOT probe process liveness.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** The settle still runs, and no longer touches a `paused` agent: that agent is resumed with its iteration instead of being cancelled.
- **REQ-SESSION-066** — A session persisted in an active status whose owning process is gone MUST be observable in two ways at once: restoring one of its checkpoints is refused and restores nothing, leaving the working tree byte-identical (REQ-SESSION-164), and the desktop session list shows that session with its stored status marked stale (REQ-SESSION-182). After the repair action of REQ-SESSION-182 has reported that session repaired, the same restore MUST succeed and the same list MUST show `interrupted` with no stale marking.
- **REQ-SESSION-183** — Because a lock that cannot be read, or that names another machine, always counts as live (REQ-SESSION-056) and is never reclaimed automatically, the application MUST offer one explicit, user-confirmed action that releases such a lock. It MUST be offered only for a session that reports live and that no process in this application holds, MUST state before it acts what the lock records — the pid, the host, and when it was acquired — and, where that host is not this machine, what that means rather than only what it says: that the session is held by a different machine and that this instance cannot establish whether that run is still going (REQ-SESSION-048). It MUST state that releasing a lock a live run still holds risks two runs writing one session. On confirmation it releases the lock and nothing else; the session's `execution_status` is left exactly as it stands, so a session that then reads as stale is repaired by the ordinary explicit repair of REQ-SESSION-060. The action MUST never run automatically, MUST never be offered as a remedy inside an error the user did not ask to resolve, and is the only way a lock this machine cannot prove dead is ever removed.

### 10. Save Ordering and Durability

- **REQ-SESSION-067** — A save MUST be made durable when it is requested, whatever the session's status. No save is deferred behind a timer, parked, or coalesced with a later one. The ten-second window this requirement formerly imposed on `running` and `idle` sessions existed because a save rewrote whole documents and the cost had to be bounded; a save now records only what changed, so the window buys nothing and costs the one thing that mattered — it was the interval in which a change could be published before it was recorded, which persist-before-publish (REQ-MONITOR-221) forbids and which now cannot arise. Two consequences MUST hold: there is no state a caller must remember to flush, and REQ-SESSION-034's crash-loss budget is stated in saves rather than in seconds. An explicit flush remains available for callers that need to know a save has landed (REQ-SESSION-068, REQ-SESSION-070) and is a no-op where nothing is outstanding.
- **REQ-SESSION-068** — Saving MUST behave as follows from a caller's point of view. A save request captures the state as it stands at the instant of the request, so that changes made after the request cannot alter what a save already under way records and cannot produce a record mixing two states. Every save reaches the store without a further call from the caller and without a timer (REQ-SESSION-067). An explicit flush MUST make the newest requested state durable and MUST NOT return before it is; the flush entry point MUST be usable from any caller's context, including one where no asynchronous runtime is active.
- **REQ-SESSION-069** — When several saves for one session are requested in close succession, the state left in the store MUST correspond to the *last* request, never to an earlier request whose write happened to finish later. In particular, a `running` save requested before a `completed` save MUST NOT be the one that survives, whatever order the two writes complete in. This ordering rule applies within one session only: a save requested for one session MUST NOT suppress, delay, or discard a save requested for a different session. This requirement formerly also fixed the exact session-log line by which a write *abandoned* for this reason was reported. **That line is withdrawn, and no conformance test may look for it.** Because no save is deferred behind a timer, parked, or coalesced with a later one (REQ-SESSION-067), requested saves are made durable in the order they were requested and there is no write left in flight to be overtaken and discarded — the condition the message reported cannot arise. The ordering guarantee above is unaffected and is unchanged in strength: it now holds by construction rather than by detecting the race and abandoning the loser, which is what REQ-SESSION-173 states as an invariant. Nothing may manufacture an abandoned write in order to keep the message reachable, because deferring or parking a save to create that race is exactly what REQ-SESSION-067 forbids.
- **REQ-SESSION-070** — Two guarantees MUST hold at the call boundary. First, once a flush returns, the persisted state is never older than the newest state any caller has asked to have saved; a flush is permitted to return without writing only in the case where a later save has already made that true. Second, a save carrying a terminal status MUST NOT return before that status can be read back by any other reader of the store, so a caller that has been told the run finished can rely on the finish being durable.
- **REQ-SESSION-071** — No bound on write volume is stated and none is needed: a save records only what changed and is durable when requested (REQ-SESSION-067), and no supported configuration key changes when a save happens. What this requirement fixes is the rule that outlived the write-volume bound, and it has no exception anywhere in the product. A surface that shows a run as it progresses MUST take its updates from what the application publishes for that run as it produces them (REQ-SESSION-159, REQ-SESSION-161); re-reading persisted state on a timer is not a supported way to follow a run and MUST NOT be relied on for refresh latency — no surface follows a session by reading its record or its files, on a timer or otherwise. The event history of Section 18 remains the durable record of what was published and the record replay reads (REQ-SESSION-150); it is not a channel a surface watches. Neither is the export of REQ-SESSION-199: it is a file a user asked for at a moment, and building a surface on repeating it is the same defect under another name.
- **REQ-SESSION-072** — Any state persisted while a run is under way MUST already carry that run's current metric aggregates (REQ-SESSION-168), so a reader never finds a saved state whose counters lag the transcript saved beside them. Every such save is durable when it is requested (REQ-SESSION-067), including one taken where no asynchronous runtime is active.

### 11. Run Status Lifecycle and Results

- **REQ-SESSION-073** — The persisted `execution_status` vocabulary is closed and consists of exactly these fourteen values: `idle` (initial; also after continuing past a message limit), `running` (run start), `background` (a run whose view has been detached, REQ-SESSION-190), `waiting` (a run parked on a provider quota wait, REQ-MONITOR-195), `paused` (interrupt/cancel paths), `paused_message_limit` (automatic message-limit pause), `awaiting_plan_decision` (a run blocked at the plan gate until the user answers, REQ-ORCH-153), `completed` and `failed` (run summary), `stopped` (a run that came to rest without completing and without being cancelled: the user stopped it from the interface, REQ-SESSION-186, or a configured run budget was exhausted, REQ-MONITOR-029), `interrupted` (written only by stale repair), and the transitional statuses `starting`, `pausing`, `cancelling` (which MUST be honored as active claims when persisted). This requirement is the single definition of that vocabulary for the whole product: a document that needs to name a persisted status cites this identifier rather than restating the set, and a domain that introduces a condition needing a status of its own extends this list rather than persisting a value of its own. No part of the product may persist a value outside this set, so a value outside it can only reach a reader from a session record written by a different version of this product. Such a value MUST be treated as non-active (REQ-SESSION-055), MUST be displayed verbatim rather than replaced by a guess, and MUST yield an error run result under REQ-SESSION-076.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 5, 2026-09-29.** Clause 21: a run the
  > user stopped from the interface, gracefully and cleanly or forced, persists `paused`, as a pause does, and never
  > `stopped`. `stopped` remains in the vocabulary for a run that exhausted a configured budget (REQ-MONITOR-029); the
  > vocabulary itself, its fourteen values and everything else this requirement says still govern as written.
- **REQ-SESSION-074** — End-of-run summarization is fixed by REQ-ORCH-082; this domain holds no copy of its arms, states no second ordering, and mints no summary status, severity, or message text of its own. What it relies on that requirement for is that the arms are evaluated in a normative order so that a run matching more than one has exactly one outcome; that the outcome is a status token, a severity, and human-readable text, the token drawn from a vocabulary of its own that is not the persisted `execution_status` vocabulary of REQ-SESSION-073 and not the terminal run-result vocabulary of REQ-ORCH-083; and that a run which resolved nothing is summarized as completed rather than failed, because nothing about it went wrong. The summarized status this domain persists alongside the session record is whatever that requirement produces, and a summarized status matched by none of the mappings this domain states MUST yield an error result under REQ-SESSION-077.
- **REQ-SESSION-075** — *Withdrawn.* Process exit codes are a shell contract and this product has no shell surface; the terminal run-outcome vocabulary the mapping was built on is carried by REQ-SESSION-187.
- **REQ-SESSION-076** — When no progress record exists, the run result MUST be derived from the session's terminal execution status through this total mapping: `completed` → completed; `failed` → failed; `paused`, `paused_message_limit`, `stopped` and `interrupted` → interrupted. Every other persisted status — the six active values of REQ-SESSION-055, `idle`, `awaiting_plan_decision`, and any value from outside the closed vocabulary of REQ-SESSION-073 — MUST yield an error result whose message conveys that the run ended without a terminal status. A session repaired to `interrupted` therefore reports an interrupted run rather than a generic error. This requirement is the single derivation of a run result from an execution status for the whole product: a document that needs one cites this identifier rather than stating a mapping of its own, and a status added to REQ-SESSION-073 is carried into this mapping rather than left to a fallback elsewhere.
- **REQ-SESSION-077** — Stop-reason classification MUST use the closed stop-reason set of REQ-MONITOR-301 and the total stop-reason-to-result mapping that requirement fixes, comparing the recorded stop reason against that set by exact, case-sensitive equality. This domain states no stop-reason strings of its own and no second mapping: one mapping produces the outcome persisted here and the outcome any consumer reads. The result it produces stands whatever the task counts say — in particular `agent_session_aborted` yields failed even where the counts would otherwise read as success, because a run whose child agent aborted MUST NOT report success to an automated consumer. Where the run recorded no stop reason at all, the result is derived from the execution status instead, through REQ-SESSION-076. A recorded stop reason outside the closed set is a defect rather than a value to be classified by a fallback, and MUST produce an error result — never a successful one — as MUST a summarized status matched by none of the mappings of REQ-SESSION-074, REQ-SESSION-076, and this requirement.
- **REQ-SESSION-078** — On every read, display surfaces MUST settle the child-agent tree against the session's own status: when `execution_status` is neither active nor `idle`, any agent still recorded as running/waiting/queued MUST display as done (for completed-like states), failed (for failed/error), or cancelled (anything else), with activity text "ended with the run" and cleared tool indicators. A snapshot written by an earlier version, or left behind by a killed process, MUST NOT be rendered as a finished run whose agents still appear active.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 4, 2026-09-28.** Clause 13: a
  > `paused` agent is displayed as `paused` on every read, never as done, failed or cancelled. Every other agent
  > still recorded as running, waiting or queued is settled as stated.
- **REQ-SESSION-079** — On a session whose `execution_status` is not one of the six active values of REQ-SESSION-055, a transcript tool row persisted with status `running` MUST render with no status indicator and no elapsed timer, and a thinking row carrying no recorded start MUST NOT show a counting timer: a session with no run in progress cannot have a tool call outstanding.
- **REQ-SESSION-187** — A terminal run result MUST carry exactly one outcome from the closed terminal run-result set of REQ-ORCH-083; this domain holds no copy of that set and mints no outcome string of its own. What it relies on that requirement for is that the set is closed and machine-readable, so that the same strings are what the `result` and `session.end` payloads carry (REQ-SESSION-095), what REQ-SESSION-076 and REQ-SESSION-077 produce, and what the interface presents (REQ-SESSION-186). Every derivation that produces a run result MUST be total over the vocabulary it consumes: adding an execution status or a stop-reason class without extending the mappings of REQ-SESSION-076 and REQ-SESSION-077 MUST be an immediate, visible failure rather than a silent default to success. No outcome is expressed as a numeric code anywhere in the product.
