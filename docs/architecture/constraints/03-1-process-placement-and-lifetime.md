# Architectural constraints extracted from the specification — 1. Process placement and lifetime

Part 3 of 22 of [the constraints](../constraints.md), which indexes every part.

## 1. Process placement and lifetime

| # | Constraint | Label | Requirements |
|---|---|---|---|
| P-01 | A run must keep running with **every window that was watching it closed**: `updated_at` keeps advancing, transcript rows keep appearing, the event journal keeps growing, artifacts keep being produced, and the run reaches a terminal `execution_status` on its own. | HARD | REQ-SESSION-096, REQ-SESSION-106 |
| P-02 | Detaching a run to the background **does not move it** — it continues in the same process holding the same session lock. Detach is a view operation plus a status write. | HARD | REQ-SESSION-190 |
| P-03 | A run **never outlives the application process**. Quitting ends every run through the ordinary cancellation and teardown path. | HARD | REQ-SESSION-106, REQ-MONITOR-131, REQ-SHELL-121 |
| P-04 | Opening another project **builds a new main window and closes the old one**, so a window's lifetime is shorter than a workspace session's and shorter than a run's. | HARD | REQ-SHELL-017, REQ-SHELL-021 |
| P-05 | The run's host must load native modules and spawn processes freely: pseudo-terminals with process-group signalling; hook children under a platform-fixed interpreter; stdio tool-server subprocesses whose lifetime is bound to the session lock. | HARD | REQ-ORCH-123, REQ-ORCH-128, REQ-SHELL-110, REQ-HOOKS-030, REQ-HOOKS-033, REQ-SESSION-049 |
| P-06 | The state flush entry point must be usable **where no asynchronous runtime is active**, must not return until the newest requested state is on disk, and a terminal-status save must not return before that status is readable **by a separate process**. | HARD | REQ-SESSION-068, REQ-SESSION-070, REQ-SESSION-072 |
| P-07 | **One process hosts several live runs**, and they must not leak into each other: two runs never lend each other an egress allow-list; one confined and one unconfined run coexist, each following the setting in force when it began. | HARD | REQ-TOOLS-089, REQ-SANDBOX-038, REQ-SANDBOX-096 |
| P-08 | Sandbox availability is probed **at most once per process**, never changes within it, and is cleared only by the explicit re-check control or by restarting the **application**. | HARD | REQ-SANDBOX-067, REQ-SANDBOX-129, REQ-TOOLS-119 |
| P-09 | The availability probe never runs on the thread that draws the interface, while the trial may take up to 5.0 s. | HARD | REQ-SANDBOX-069, REQ-SHELL-150 |
| P-10 | Evaluation and projection work for the requirements board **never** runs on the interface event loop, and the interface accepts input for the whole time a version-control refresh is running. | HARD | REQ-TRACE-337, REQ-TRACE-497, REQ-GIT-102, REQ-LIBRARY-122 |
| P-11 | **No module of the desktop application may launch a requirement-checking or verifier process**, and a guard test must assert it; a consuming surface calls the library directly and receives plain data. | HARD | REQ-TRACE-206, REQ-TRACE-377, REQ-TRACE-378 |
| P-12 | The absence of any time, document or resource limit on the traceability scan is **a deliberate decision and not a gap**, and project-declared conventions run **user-supplied regular expressions** over repository files. | HARD | REQ-TRACE-154, REQ-TRACE-225, REQ-TRACE-073 |
| P-13 | Exactly one executable ships. No console, headless, benchmark or other secondary executable may be published or made available by an installation. The specification fixes **exactly one** reserved argument token — `builtin:code-intelligence`, which names a child the product starts of itself — and states that "no argument vocabulary beyond it is defined for the shipped executable". For the benchmark's iteration child it deliberately fixes **none**: what is compelled is only that "no user or external program can start one" and that "no argument form, flag, or invocation grammar for it is fixed by this document or by any other". A second sentinel is therefore an architect's choice needing its own justification (ADR-0053), not something the specification hands over. | HARD | REQ-STARTUP-002, REQ-STARTUP-015, REQ-MCP-033, REQ-UIBENCH-037; `resolutions/11` (self-invocation flag withdrawn), `resolutions/16` q15, `resolutions/21` q11 |
| P-14 | The specification contemplates several **processes**, and since SR-1 landed it no longer contemplates several **instances**. `REQ-STARTUP-161` fixes at most one instance per user account and makes every window a window of that one instance. What survives: a run may execute in a separate worker process with an identical observable outcome (`REQ-MONITOR-299`); the credential store is still locked across processes, but now because *every window of the one instance reaches the same per-user files* and several read-modify-write sequences can be in flight at once (`REQ-PROVIDER-152`, as amended); `REQ-GIT-124`'s "whether or not this application started it" now covers this instance's own runs and a lock an instance that crashed left behind, not a rival application. | HARD | REQ-STARTUP-161, REQ-MONITOR-299, REQ-PROVIDER-152, REQ-GIT-124 |
| P-15 | Which OS process hosts the run engine, and how many OS threads or worker contexts the runtime uses. | FREE (bounded by P-01 to P-17) | REQ-STARTUP-134 requires only that diagnostics can count and name them |
| P-16 | **A launch is not always a process that stays.** Every launch resolves to exactly one of two outcomes and no third: it becomes the running instance, or it is handed to the instance already running and ends without opening a window. A handed-over launch shows nothing, **writes nothing to the preference store and nothing to any per-user or per-workspace state**, and ends. A record naming a process that cannot be reached must never leave the application unlaunchable: at most one reclaim, two claim attempts, a 5-second hand-over interval, no spin, and no side effect on the probed process. **Measured 2026-09-02, and this is the row the measurement round hit hardest: the platform's own single-instance primitive DOES NOT DELIVER THIS AND HAS BEEN REFUSED.** Against a primary running but not pumping messages it blocked **20,004.6 / 20,010.9 ms** against the 5-second interval, returned false, performed **no reclaim and no retry**, and dropped the hand-over rather than queueing it — the launch ended with **no window on screen**, which is the outcome `REQ-STARTUP-164` closes by saying every path ends with one. It cannot be wrapped: the call is synchronous on the launching process's own main thread and takes no timeout. **The requirement is unchanged; what changed is that its discipline is ours to write on all three platform keys** (ADR-0055 alternative I). Two clauses of the requirement were confirmed rather than falsified and are carried as measured obligations on the replacement: a record left by a process killed without cleanup did not make the application unlaunchable — first-attempt reclaim at **+187 ms**, window at +345/+373 ms, release bracketed to a 67–69 ms window — and 69 probes left the probed process alive, unchanged and uninterrupted. **One residue the requirement does not bound:** it licenses two processes existing "briefly" during a reclaim and nothing makes the reclaimed-from process stand down, so a wedged primary that later recovers still believes it is the instance. | HARD | REQ-STARTUP-161 – REQ-STARTUP-164, REQ-STARTUP-155, REQ-STARTUP-152; `spikes/presenter-liveness-and-instance-claim.md` §5.1–5.5, §6 |
| P-17 | **A benchmark iteration is a fresh child process of the product's own program that the product itself starts**, receiving a stripped environment with `XDG_CONFIG_HOME` and one benchmark-private variable redirected, and the user's real stored settings must hold the same bytes afterwards. Nothing outside the product can start one. The specification does not say how this composes with P-16, and read naively P-16 swallows it. See OQ-43. | HARD / CONFLICT with P-16 | REQ-UIBENCH-037 – REQ-UIBENCH-039, REQ-UIBENCH-046 vs REQ-STARTUP-161 |
