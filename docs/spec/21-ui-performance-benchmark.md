# UI Performance Benchmark

## Overview

The desktop application carries a built-in UI performance benchmark. It captures the UI-visible portion of a persisted session into a self-checksummed JSON fixture, replays that fixture through the desktop application's own rendering path in fresh, environment-pinned, offscreen child processes, and reports timing, memory, responsiveness, and structural determinism metrics. Four operations — capture, replay, inspect, compare — support the workflow "capture once, replay on two product revisions, compare the runs", and all four are reached from the desktop interface and from nowhere else (REQ-UIBENCH-110, REQ-UIBENCH-111). Replay drives seven fixed workload phases per iteration (window construction, bulk state application, incremental appends, simulated token streaming, 1000 tail replacements, an idempotent re-application, and a resize sweep), records one JSON-lines metric record per phase, and derives per-run summaries containing raw values, percentile aggregates, robust memory-trend slopes, and seven boolean determinism, leak, and responsiveness invariants. The benchmark is a report generator, not a gate: invariant violations and crashed iterations are reported in the run summary and in the interface, and never make the operation that produced them fail.

## Requirements

### Identity and desktop surface

- **REQ-UIBENCH-001** — *Withdrawn.* The product ships no separate installed console program and no package-manager-only capability; the benchmark is a built-in part of the desktop application in every installation, as carried by REQ-UIBENCH-110.
- **REQ-UIBENCH-002** — *Withdrawn.* Usage text, help text, and a program-name prefix on error lines are surfaces of a command-line program the product does not have; benchmark failures are reported in the interface under REQ-UIBENCH-114.
- **REQ-UIBENCH-003** — *Withdrawn.* Prompting, progress output, colour, and terminal detection are properties of a command-line program; the offscreen, non-interactive rendering the measurement actually depends on is carried by REQ-UIBENCH-112, and progress reporting and cancellation by REQ-UIBENCH-116.
- **REQ-UIBENCH-004** — *Withdrawn.* There is no published command surface, no argument list to reject, and no exit-2 argument-error class; that the four operations are the whole of the benchmark surface is carried by REQ-UIBENCH-111.
- **REQ-UIBENCH-110** — The benchmark SHALL be a built-in capability of the desktop application, present in every installation of the product without exception and reachable from the desktop interface and from nowhere else. The Settings view's About tab (REQ-SHELL-138) SHALL carry a performance-benchmark card, alongside the diagnostics card of REQ-SHELL-163, from which every operation of REQ-UIBENCH-111 is started; the product SHALL define no other way to start one. Every control on that card SHALL be keyboard-reachable and SHALL carry an accessible name, and the card SHALL remain fully usable at the minimum window size (REQ-SHELL-022).
- **REQ-UIBENCH-112** — Every iteration SHALL render the product interface offscreen. No window belonging to the benchmark SHALL ever appear on a display, take keyboard focus, or change the position, size, or focus of a window the user has open; no iteration SHALL prompt or require any interaction; and a benchmark in progress SHALL leave the rest of the desktop application usable. The only surface through which a running benchmark is observed or stopped is that of REQ-UIBENCH-116.

### Benchmark operations

- **REQ-UIBENCH-005** — *Withdrawn.* Subcommands, positional arguments, and `--output` are a command-line grammar the product does not have; the four operations they described are carried by REQ-UIBENCH-111.
- **REQ-UIBENCH-006** — *Withdrawn.* There is no argument to omit; that capture and replay cannot start until a destination has been chosen is carried by REQ-UIBENCH-111.
- **REQ-UIBENCH-007** — *Withdrawn.* The iteration count is no longer an argument to parse; its control, its default of 3, and the unreachability of a non-integer value are carried by REQ-UIBENCH-113.
- **REQ-UIBENCH-008** — *Withdrawn.* An iteration count below 1 is unreachable through the control of REQ-UIBENCH-113, so the message and the exit code this requirement fixed have nothing to report.
- **REQ-UIBENCH-009** — *Withdrawn.* The product exposes no exit code to any user; operation outcomes are reported under REQ-UIBENCH-114, and the termination status of an iteration process is an internal signal read only by REQ-UIBENCH-041.
- **REQ-UIBENCH-010** — *Withdrawn.* There is no standard output to write a report to; the presentation of an inspect or compare report and its canonical JSON export are carried by REQ-UIBENCH-115.
- **REQ-UIBENCH-011** — *Withdrawn.* Standard-stream behaviour is a property of a command-line program; the capture privacy notice is carried by REQ-UIBENCH-022 and the handling of an iteration process's diagnostic output by REQ-UIBENCH-117.
- **REQ-UIBENCH-111** — Exactly four benchmark operations SHALL be offered, and they SHALL be the whole of the benchmark surface:
  - **capture** — writes the rendered-in-the-UI portion of one stored session out to a fixture file. Its subject SHALL be chosen from the product's own list of stored sessions for the current workspace, so the location rule of REQ-UIBENCH-014 holds by construction; its destination SHALL be chosen through the platform file-save chooser.
  - **replay** — re-renders a fixture in newly started child processes, collecting the results into a run directory. Its fixture and its destination directory SHALL each be chosen through the platform chooser, and its iteration count set through the control of REQ-UIBENCH-113.
  - **inspect** — reduces one chosen run directory to the report of REQ-UIBENCH-067, presented under REQ-UIBENCH-115.
  - **compare** — presents the delta report of REQ-UIBENCH-090 between two chosen run directories under REQ-UIBENCH-115.
  An operation whose inputs are not all chosen SHALL be offered as a disabled control that states which input is still missing. There SHALL be no reachable state in which an operation is started with an input absent, and the product SHALL therefore define no message or refusal for one.
- **REQ-UIBENCH-113** — The replay iteration count SHALL be an integer control whose value defaults to 3 and whose smallest offerable value is 1. A non-integer value and a value below 1 SHALL both be unreachable through that control, and the product SHALL define no error, message, or refusal for either.
- **REQ-UIBENCH-115** — An inspect or compare report SHALL be presented in the interface in a form that shows every value the report carries, and SHALL additionally be exportable in exactly two ways: copied to the clipboard, and saved to a file chosen through the platform chooser. What either route produces SHALL be the report object serialized as JSON with 2-space indentation and lexicographically sorted keys and nothing else, byte-identical between the two routes and independent of the host locale. Presentation SHALL meet the product's 100 ms interface responsiveness budget (REQ-SHELL-150) for a report of a run of up to 10 iterations, measured from the gesture that requests it to the report being usable; a larger run MAY take longer provided the interface stays responsive and the wait is shown.

### The capture operation

- **REQ-UIBENCH-012** — A successful capture reads one stored session — the session chosen under REQ-UIBENCH-111, called `THE SUBJECT` throughout this document, identified by the workspace it belongs to and its session id (REQ-SESSION-001) — and produces one file: the JSON fixture at the chosen destination, carrying the top-level keys fixed by REQ-UIBENCH-018 and no others. It starts no child process and opens no network connection. Nothing is written outside that destination and the parent directories created for it (REQ-UIBENCH-021), and nothing the subject owns is changed by the capture: not its record, not its files, not its lock, verifiable by observing that nothing it owns differs after the operation (REQ-SESSION-156, REQ-SESSION-058). A capture that fails any check of REQ-UIBENCH-013 through REQ-UIBENCH-017 reports the failure under REQ-UIBENCH-114 having created or modified no output file.
- **REQ-UIBENCH-013** — If `THE SUBJECT` no longer exists, or cannot be read when the operation runs — the session having been deleted since it was listed, or its store having become unreadable — capture fails, reports a failure naming the session (REQ-UIBENCH-114), and leaves no output file. Where the store itself will not open, the failure carries the store's own reported reason rather than a generic one, on the terms REQ-SESSION-089 fixes.
- **REQ-UIBENCH-014** — `THE SUBJECT` is resolved as the sessions domain resolves any session: by workspace plus session id, against the sessions of the workspace the window has open, and never by building a path (REQ-SESSION-001, REQ-SESSION-151). Because the subject is chosen from the product's own session list for the current workspace (REQ-UIBENCH-111), a subject outside that set is unreachable and the product defines no message or refusal for one. The workspace root and the session id are taken from the listed session itself rather than derived from any path, so no expansion, symlink resolution or parent-directory check is performed and none can be defeated.
- **REQ-UIBENCH-015** — Session state is loaded exactly as the desktop application loads it, by the precedence REQ-SESSION-036 and REQ-SESSION-037 fix and by no other route: the session's resumable state, which is required, plus its three optional bulk parts — the transcript rows holding `{"events": [...]}`, the edit diffs holding `{"diffs": [...]}`, and the configuration snapshot of the launch audit holding `{"config_snapshot": {...}}`. An absent optional part and an undecodable one degrade identically, and only a failure of the core resumable state fails the load (REQ-SESSION-036). The benchmark relies on REQ-SESSION-037 for the fact that the stored resumable state is the only resumable state and there is no whole-state fallback to try after it; supporting a second route would be a change to REQ-SESSION-036 and REQ-SESSION-037 rather than to this document. Where the resumable state is absent, capture fails and reports the not-found outcome REQ-SESSION-037 fixes, identifying the session.
- **REQ-UIBENCH-016** — The session schema-version check applies on the intake path of REQ-UIBENCH-015, exactly as REQ-SESSION-038 requires of every loader: a declared session `schema_version` greater than the version REQ-SESSION-013 supports makes capture fail with the refusal REQ-SESSION-038 fixes and leaves no output file. The benchmark therefore never accepts a session the desktop application would refuse.
- **REQ-UIBENCH-017** — Capture projects the session against the effective configuration the desktop application has already resolved for the workspace resolved in REQ-UIBENCH-014 — the resolved layered configuration, not any file the benchmark opens for itself. Capture therefore reads no configuration file of its own and declares none mandatory. Two captures of the same unchanged session taken under two different effective configurations may differ in fixture content and in `fixture_checksum`, while `source_checksum` is unchanged between them because it depends on the session's own recorded state alone (REQ-UIBENCH-019). If no effective configuration is available for that workspace, capture fails and reports that (REQ-UIBENCH-114), presents no privacy notice (REQ-UIBENCH-022), and leaves no output file.
- **REQ-UIBENCH-018** — A fixture written by capture is one JSON object whose top-level keys are exactly `schema_version` (the integer 1), `source_checksum`, `transcript` (list), `agents` (list, ordered as the UI displays them), `todos` (list), `artifacts` (list), `kpis` (object), `run_state` (object), and `fixture_checksum` — no more and no fewer. This constrains capture's output only. What a fixture must contain in order to load is the shorter list of REQ-UIBENCH-024, and a fixture produced by other means may carry additional top-level keys and still load (REQ-UIBENCH-026) — with the single exception of the prohibition of REQ-UIBENCH-023, which binds both what capture emits and what loads, so a fixture built elsewhere carrying a prohibited key is refused at load time (REQ-UIBENCH-024).
- **REQ-UIBENCH-019** — `source_checksum` is a SHA-256 digest written as exactly 64 lowercase hexadecimal characters. Its input is the canonical serialization — in the sense REQ-UIBENCH-020 fixes: keys sorted, compact separators, non-ASCII characters escaped, encoded as UTF-8 — of one object holding the session's own recorded state exactly as REQ-UIBENCH-015 read it and before any projection against configuration, under the four fixed keys `resume`, `transcript`, `edit_diffs` and `run_config`. An optional part that was absent contributes its key with a null value, so a session that never held a part stays distinguishable from one whose part is empty. Nothing else contributes: not the session's log, not its summary, not artifact bodies, not its event history, and nothing about where any of them is held. Two sessions whose recorded state agrees therefore produce the same `source_checksum` on any host, whatever its path separator, locale, or filesystem name encoding, and a session whose state has changed since a capture produces a different one.
- **REQ-UIBENCH-020** — `fixture_checksum` is the SHA-256 hex digest of the canonical JSON serialization of the fixture object with the `fixture_checksum` key removed. Canonical serialization means: keys sorted, compact separators (`,` and `:` with no spaces), non-ASCII characters escaped, encoded as UTF-8 bytes. Checksums are therefore identical across locales, platforms, and filesystem encodings.
- **REQ-UIBENCH-021** — The fixture file is written as JSON with 2-space indentation, non-ASCII characters escaped, UTF-8 encoding, and no trailing newline. Missing parent directories of the output path are created. An existing output file is silently overwritten.
- **REQ-UIBENCH-022** — Every successful capture SHALL present a notice in the interface, together with the success outcome of REQ-UIBENCH-114, conveying that the fixture holds transcript and tool content required for faithful rendering and that it should be reviewed before it is shared. The notice SHALL appear on every successful capture without exception and SHALL be dismissible; its exact wording is left to the implementation.
- **REQ-UIBENCH-023** — A fixture must not carry top-level keys named `config`, `credentials`, `environment`, or `workspace`: capture never writes one and the loader refuses one (REQ-UIBENCH-024). Nothing else is stripped or masked: conversation and tool text appear in `transcript` in full, at the length the UI would render. Every successful capture announces that residual content in the interface (REQ-UIBENCH-022).

### Fixture format and validation

- **REQ-UIBENCH-024** — Loading a fixture (by replay and by a child iteration) enforces four checks in this order, each failing the load and each reported as a cause distinguishable from the other three (REQ-UIBENCH-114):
  1. the top-level value is a JSON object and `schema_version` equals 1, else the fixture's schema version is unsupported;
  2. `fixture_checksum` is a string equal to the recomputed canonical checksum (REQ-UIBENCH-020), else the fixture's checksum does not match its content;
  3. no top-level key prohibited by REQ-UIBENCH-023 is present, else the fixture carries excluded content, the report naming the offending key;
  4. the six keys `transcript`, `agents`, `todos`, `artifacts`, `kpis`, `run_state` are all present, else the fixture is missing UI-visible state.
  These four are the only load-time checks; entry-level constraints are enforced later, per REQ-UIBENCH-033. What each of the four failures must convey is fixed here; the wording of each is left to the implementation.
- **REQ-UIBENCH-025** — The checksum covers every top-level key except `fixture_checksum` itself — including `schema_version` and `source_checksum` — so mutating any covered field (for example emptying `transcript`) makes loading fail with the checksum-mismatch diagnostic.
- **REQ-UIBENCH-026** — `source_checksum` is produced by capture but is not required at load time: a hand-built fixture without it (or with an arbitrary value) loads, provided its `fixture_checksum` is consistent. Unknown extra top-level keys other than the four REQ-UIBENCH-023 prohibits are permitted at load time and participate in the checksum.
- **REQ-UIBENCH-027** — A `transcript` entry must carry `timestamp` (a string), `role` (a non-empty string), and `text` (a string). `role` is drawn from the open transcript row-role vocabulary REQ-CHAT-047 defines, which is the single definition of that vocabulary and which this document neither restates nor closes; the benchmark treats the value as opaque display text and never checks it against an enumeration, so a role outside the ones that requirement names never fails a fixture. An entry may also carry, and only, the following optional keys, each with the type and absent-default given: `kind`, a string, default `"message"`; `tool`, a string, default `""`; `detail`, a string, default `""`; `full_text`, a string, defaulting to the value of `text`; `full_detail`, a string, defaulting to the value of `detail`; `diff`, an object or null, default null; `persona`, a string, default `""`; `event_key`, a string, default `""`; `status`, a string treated as opaque display text with no enumeration check, default `""`; `duration`, a number of seconds not less than 0, default null (nothing shown); `started_at`, a string timestamp, default null; `char_count`, a non-negative integer, defaulting to the number of characters in `full_text`; and `stream_id`, a string, default `""`. An entry carrying a key outside the required and optional sets above, or an optional key whose value is of the wrong type, fails the iteration that rebuilds it (REQ-UIBENCH-033) rather than the fixture load. Every entry, including one carrying a nested `diff` payload, is rebuilt through the same rendering path the live application uses; the benchmark defines no rendering path of its own, so an entry renders under replay exactly as it renders live.
- **REQ-UIBENCH-028** — An `agents` entry must carry `id` (a non-empty string), `name` (a non-empty string), and `persona` (a string). Beyond those three it may carry, and only, these display keys, each with the type and absent-default given: `state`, one of the six presentation states `running`, `waiting`, `queued`, `done`, `failed`, `cancelled` fixed by REQ-MONITOR-046, default `queued` — the same value REQ-MONITOR-046 assigns to an unmapped engine state; `model`, a string, default `""`; `task_title`, a string, default `""`; `depth`, a non-negative integer, default 0; `tool_call_count`, a non-negative integer, default 0; `token_count`, a non-negative integer, default 0; `cost_label`, a string the product has already rendered as money and on which the benchmark performs no arithmetic (REQ-PROVIDER-121), default `""`; `elapsed_s`, a number of seconds not less than 0, default null; and `error_text`, a string, default `""`. `state` is therefore optional. The order of the list is the order in which the agents are displayed. A key outside the set above, and a `state` value outside the six, fail the iteration that rebuilds the entry (REQ-UIBENCH-033) and never the fixture load, whose checks REQ-UIBENCH-024 lists exhaustively.
- **REQ-UIBENCH-029** — Each `todos` entry requires `id`, `phase_id`, `status`, and `text`; `phase_name` is optional. `status` is one member of the task display-state vocabulary REQ-CHAT-086 defines, which is the single definition of that set and which this document neither restates nor narrows — in particular a fixture carrying the abandoned display state is valid, and the benchmark refuses no member of it. Violations surface per REQ-UIBENCH-033.
- **REQ-UIBENCH-030** — An `artifacts` entry must carry `id` (a non-empty string), `slug` (a string), and `title` (a string). Beyond those three it may carry, and only, these display keys, each with the type and absent-default given: `kind`, one member of the closed three-value vocabulary `child_report`, `agent_published`, `system` fixed by REQ-LIBRARY-088, default `child_report`; `status`, one member of the artifact status set REQ-LIBRARY-088 forms — the child-report status vocabulary of REQ-ORCH-112 together with `published` — which this document neither restates nor closes and whose membership it accepts as those requirements state it, default `succeeded`; `importance`, either `high` or `normal`, default `normal`; `summary`, a string, default `""`; `source_persona`, a string, default `""`; and `created_at`, a string timestamp, default null. A key outside that set, and a `kind` or `status` value outside the vocabulary the requirement that owns it fixes, fail the iteration per REQ-UIBENCH-033.
- **REQ-UIBENCH-031** — `kpis` must be a JSON object. Each of its keys is optional, so `{}` is a valid value for the whole object and every absent key takes the default given here: `cumulative_tokens`, a non-negative integer, default 0; `cumulative_cost_label`, a string the product has already rendered as money and on which the benchmark performs no arithmetic (REQ-PROVIDER-121), default `""`; `token_history`, a list of non-negative integers, default `[]`; `tool_calls`, a non-negative integer, default 0; `tool_call_breakdown`, an object mapping a tool name to a non-negative integer, default `{}`; `files_touched`, a non-negative integer, default 0; and `uncommitted`, a non-negative integer counting uncommitted changes, default 0. A key outside that set, or a value of the wrong type, fails the iteration per REQ-UIBENCH-033.
- **REQ-UIBENCH-032** — `run_state` must be a JSON object whose keys are drawn from `session_name`, `session_status`, `run_state`, and `active_model`. All four are optional, so `{}` is a valid value, and each absent key takes the default given here: `session_name`, a string, default `""`; `session_status`, a string holding a persisted `execution_status` value; the benchmark treats it as opaque display text and applies no enumeration check, because a fixture may have been captured from another version of the product and may therefore carry a value outside the closed vocabulary of REQ-SESSION-073, which this document neither restates nor polices, default `""`; `run_state`, one member of the normalised presentation vocabulary REQ-NOTIFY-048 closes, which this document does not restate and whose membership it accepts as that requirement states it, default `idle`; and `active_model`, a string, default `""`. Any other value of the inner `run_state` key, and any key outside the four, fail the iteration that rebuilds the object (REQ-UIBENCH-033) rather than the fixture load.
- **REQ-UIBENCH-033** — Entry-level constraints are enforced as an iteration rebuilds the fixture's content, not when the fixture is loaded. An entry in `transcript`, `agents`, `todos`, `artifacts`, `kpis`, or `run_state` that carries a key outside the accepted set, a value of the wrong type, or an enumeration value outside the sets fixed by REQ-UIBENCH-027 through REQ-UIBENCH-032, makes the iteration handling it terminate with a non-zero status. For an iteration at index NNN this is observable as: no `iteration-NNN.jsonl` file in the run directory; an `iteration-NNN.crash` file recording that non-zero status (REQ-UIBENCH-041); an `iteration-NNN.log` holding what that iteration wrote before it stopped (REQ-UIBENCH-117); every remaining iteration still executed; replay still completing normally and reporting the crash count (REQ-UIBENCH-114); and the run summary counting that iteration in `crashes` while it contributes nothing to `iterations` or `records`.

### The replay operation — orchestration

- **REQ-UIBENCH-034** — Replay's observable order of operations is: (1) fully validate and load the fixture (all REQ-UIBENCH-024 errors occur before anything is created on disk); (2) create the output run directory; (3) freeze the fixture into the run directory; (4) run the requested iterations sequentially; (5) compute the run summary; (6) write the summary files.
- **REQ-UIBENCH-035** — The output run directory is created, including missing parents; if it already exists, replay fails (REQ-UIBENCH-114) and creates or modifies nothing inside it.
- **REQ-UIBENCH-036** — The input fixture is copied byte-for-byte to `<output>/fixture.json`, preserving formatting verbatim, and child iterations replay this frozen copy.
- **REQ-UIBENCH-037** — Each of the N iterations runs in a fresh child process of the product's own program, started by the desktop application, writing to `<output>/iteration-NNN.jsonl`, where NNN is the zero-based iteration index zero-padded to 3 digits. Iterations run strictly sequentially in order 0..N−1, never in parallel. How such a process is started is internal to the implementation: it is not a user-invocable surface, no user or external program can start one, and no argument form, flag, or invocation grammar for it is fixed by this document or by any other.
- **REQ-UIBENCH-038** — One temporary settings directory is created per iteration, is used by that iteration alone, and is deleted when that iteration ends; a replay run therefore creates and destroys one such directory per iteration and leaves none behind when it finishes. It isolates each child process both from the user's real application settings and from every other iteration: nothing an iteration stores is visible to any other iteration, so every iteration begins from the same stored-settings state. That isolation is what makes the determinism claim of REQ-UIBENCH-099 hold, since settings written by iteration 0 cannot change what iteration 1 does.
- **REQ-UIBENCH-039** — Each iteration process receives the invoking environment with two changes. First, every environment variable the product itself reads — as configuration, as a diagnostics setting, or in any other role — is removed, so no host environment setting of the product can reach an iteration. Second, a fixed set of overrides is applied that: makes the interface render with no on-screen output; pins one platform-independent widget style; pins a display scale factor of 1; sets `LANG=C` and `LC_ALL=C`; sets the standard user-configuration-home variable `XDG_CONFIG_HOME` to that iteration's temporary settings directory (REQ-UIBENCH-038); and names that same directory in one benchmark-private variable. The names and values of the overrides other than `LANG`, `LC_ALL`, and `XDG_CONFIG_HOME` are private to the implementation and are deliberately not fixed here: because no user and no external program can start an iteration (REQ-UIBENCH-037), nothing outside the product ever has to set, override, or observe them. What is fixed here is their effect. Testable consequence: changing the host's display scaling, widget style, colour theme, locale settings, or any environment variable the product reads, and replaying the same fixture again, leaves the structural counters (`widgets`, `ui_objects`, `transcript_operations`) and all seven invariants unchanged.
- **REQ-UIBENCH-040** — Replay imposes no time limit on a single iteration or on a run as a whole, and never ends an iteration that is still making progress. It cannot, however, wait indefinitely: every wait for the interface to settle is bounded by REQ-UIBENCH-119, so no phase can hang, and the user can stop a run at any point from the surface of REQ-UIBENCH-116. No timeout diagnostic is emitted for a merely slow run and no crash marker is written for one.
- **REQ-UIBENCH-041** — When a child iteration terminates with a non-zero status, or terminates with a zero status without having written its record file (REQ-UIBENCH-052), the parent writes `<output>/iteration-NNN.crash` containing exactly `exit_code=<n>` followed by one newline, where `<n>` is the status the child terminated with, then continues with the remaining iterations. Replay itself still completes normally; crash evidence surfaces in the run summary's `crashes` count and in the retained iteration log of REQ-UIBENCH-117.
- **REQ-UIBENCH-042** — After all iterations, replay computes the same summary `inspect` would produce, adds one top-level `fixture_checksum` key holding the loaded fixture's checksum, and writes `<output>/summary.json` (2-space indent, sorted keys) and `<output>/summary.md`. The top-level `fixture_checksum` key appears only in replay-written summaries, not in ad-hoc `inspect` output.
- **REQ-UIBENCH-043** — `summary.md` is UTF-8 text whose content is, in this order and with nothing else: the line `# Rotaris replay benchmark`; an empty line; the line `Iterations: <n>`, where `<n>` is the summary's `iterations` value; an empty line; then exactly one line for each phase present in the summary's `phases` object, the phases taken in bytewise ascending name order, each reading `- <phase>: wall p50 <x> ms; CPU p50 <y> ms`, where `<x>` and `<y>` are the p50 values of that phase's `wall_ms` and `cpu_ms` blocks. Each is rendered as a fixed-point decimal with exactly three digits after the point, using `.` as the decimal separator whatever the host locale, with no thousands separator and never in exponent notation; a p50 of null renders as `null`. The file ends with a newline. A summary holding no phases yields no phase lines (REQ-UIBENCH-105).
- **REQ-UIBENCH-044** — The resulting run directory is the unit consumed by inspect and compare and contains: `fixture.json` (verbatim input copy), `iteration-NNN.jsonl` (one per iteration that completed all phases), optional `iteration-NNN.crash` markers, optional `iteration-NNN.log` files retained for crashed iterations (REQ-UIBENCH-117), `summary.json`, and `summary.md`.
- **REQ-UIBENCH-116** — While a replay is running, the performance-benchmark card of REQ-UIBENCH-110 SHALL show that it is running and which iteration of how many is in progress, and SHALL offer a cancel control that is keyboard-reachable and carries an accessible name. The progress shown SHALL be conveyed in words and never by colour alone (REQ-SHELL-149), and SHALL be updated without making the interface unresponsive (REQ-SHELL-150). Cancelling SHALL end the iteration in progress and start no further iteration; that iteration is treated as a crash under REQ-UIBENCH-041, the summary is still computed and written over the iterations that completed (REQ-UIBENCH-042), and no child process SHALL still be running once the run has been reported as ended.

### Child iteration behavior

- **REQ-UIBENCH-045** — Every child iteration re-runs all three checks of REQ-UIBENCH-024 against the frozen `fixture.json` before it opens any window. A run directory whose frozen fixture was altered after replay wrote it therefore yields crashed iterations and crash markers, not measurements.
- **REQ-UIBENCH-046** — A replay run leaves the invoking user's stored desktop-application settings exactly as it found them: no such file is created, read, modified, or deleted, and every one of them holds the same bytes after the run as before it. Anything an iteration stores is confined to that iteration's temporary settings directory (REQ-UIBENCH-038) and disappears with it, so a completed run leaves no file behind outside its own output directory. A host on which the desktop application has never been installed or configured therefore replays a fixture to the same structural counters and the same invariant values as a host on which it has been used heavily.
- **REQ-UIBENCH-047** — Before the measured window exists, each iteration selects the same platform-independent widget style its environment already names (REQ-UIBENCH-039), loads the three bundled font families of REQ-SHELL-008 from the product package, and applies the product's default built-in theme `rotaris-dim` (REQ-SHELL-128), so none of the three is taken from the host. The host-font fallback REQ-SHELL-008 permits the application at startup SHALL NOT apply here: an iteration in which a bundled family fails to load terminates with a non-zero status and is counted as a crash (REQ-UIBENCH-041) instead of measuring against host fonts, because a silent fallback would break determinism without being visible anywhere in the report. Testable consequence: installing or removing fonts on the host, changing the host's default widget style, and changing the host's theme preference each leave a replay of the same fixture reporting the same `widgets` values and the same structural counters as before the change.
- **REQ-UIBENCH-048** — The two canonical window sizes are the minimum window size and the opening window size REQ-SHELL-022 fixes, and the measured window is initially sized to the opening one. This requirement relies on that one for both figures and states neither of them again, so a change to the product's window bounds moves the benchmark with it rather than leaving two sets of numbers to be kept in step. Where a later phase names a canonical size it means one of those two.
- **REQ-UIBENCH-049** — Every phase record carries `event_loop_lag_ms`, a number of milliseconds rounded to 3 decimals reporting the longest single interruption to the interface's responsiveness observed between the previous record of that iteration and this one. Responsiveness is observed by a probe scheduled to run every 10 ms, and the reported value is the largest amount by which one probe ran later than the instant it was scheduled for; the observation interval is fixed here so that values produced by two conformant implementations are comparable in magnitude. The value is never negative and is 0 when no probe ran measurably late. It describes that interval alone and is not accumulated, so a delay reported in one record is never reported again in a later one. Observation runs continuously over the measured part of an iteration — it starts before the first phase and stops when the last phase's record is taken — so every instant of the iteration falls inside exactly one record's interval.
- **REQ-UIBENCH-050** — Every record reports, for the process that produced it: `rss_bytes`, its resident memory in bytes; `threads`, the number of operating-system threads it currently has; and `handles`, the number of operating-system handles it currently holds open — open handles on Windows, open file descriptors on POSIX systems — or null. A null is permitted on any platform, and only for the two stated reasons: the platform exposes no such counter, or the count could not be obtained at that moment. It is the only substitute permitted for the value, it is reported in `handles_raw` and nowhere else (REQ-UIBENCH-076), and no invariant reads `handles`. Each record also reports two structural counts of the interface: `widgets`, the number of live visual elements of the constructed window — those that occupy space in the window's layout and can be painted — and `ui_objects`, the broader count of every live interface-framework object owned by that window, visual or not, so `ui_objects` is never smaller than `widgets`. Both are 0 in any record taken while no window exists. `rss_bytes`, `threads`, `widgets`, and `ui_objects` are non-negative integers; `handles` is a non-negative integer or null. Both structural counts are defined against the interface framework the product is built on: their absolute values are comparable between two runs of one product revision — which is all REQ-UIBENCH-054 and REQ-UIBENCH-085 rely on — and are deliberately not comparable between product revisions or between implementations.
- **REQ-UIBENCH-051** — `wall_ms` is the real time and `cpu_ms` the processor time the measuring process spent on a phase, both in milliseconds rounded to 3 decimals. Both cover the phase's work up to the point at which the interface has finished showing that work's effect, or up to the bound of REQ-UIBENCH-119, whichever comes first, so the cost of rendering what a phase changed is charged to that phase and never to a later one; in `resize_sequence` each resize is complete before the next one starts. The remaining values of the record — the process and structural counts of REQ-UIBENCH-050, `markdown_cache`, and `transcript_operations` — describe the state reached once the phase is complete in that sense. `elapsed_s` is the time in seconds, rounded to 3 decimals, since a time origin fixed once per iteration before its first phase, so within one iteration `elapsed_s` never decreases from one of the seven records to the next.
- **REQ-UIBENCH-052** — The child's record file is JSON Lines: one record per phase (7 per healthy iteration), compact separators, non-ASCII escaped, one newline per record. The file is created only after all phases complete: a child that crashes mid-run leaves no record file for that iteration — only the parent's crash marker and the log retained under REQ-UIBENCH-117. On the healthy path the child writes all seven records, closes the window, and only then terminates with a zero status. A child SHALL never terminate with a zero status having written no record file; a parent that observes one treats it as a crash (REQ-UIBENCH-041), so a missing record file is always accompanied by a crash marker explaining it and `iterations` never falls silently.
- **REQ-UIBENCH-117** — Diagnostic output an iteration process writes SHALL be captured by the process that started it and SHALL never appear on any surface the user did not ask for. Where the iteration crashed (REQ-UIBENCH-041), the captured output SHALL be written to `<output>/iteration-NNN.log` and SHALL be reachable from that run's failure and crash reporting (REQ-UIBENCH-114); where the iteration completed, the captured output MAY be discarded. Output from the interface framework itself is expected on this channel during offscreen rendering and SHALL never on its own be treated as a failure: only the child's termination status and the presence of its record file decide whether an iteration crashed (REQ-UIBENCH-041, REQ-UIBENCH-052).
- **REQ-UIBENCH-119** — Every wait for the interface to finish showing a phase's effect (REQ-UIBENCH-051) is bounded at 30 s, measured from the moment that phase's work has been submitted. Where the bound expires, the phase's timing closes at that moment, its record is written with `settle_timed_out` true, and the iteration continues with the next phase; where the interface settled inside the bound, `settle_timed_out` is false. The key is present in every record the benchmark writes (REQ-UIBENCH-062), is reported for information only, and no invariant reads it. A record carrying it as true under-reports the true cost of that phase, and a consumer comparing runs must take that into account. No iteration is ever ended merely because a phase reached the bound.

### Replay phases

- **REQ-UIBENCH-053** — Every iteration executes exactly seven phases, once each, in this fixed order: `construct_window`, `apply_fixture`, `ordered_appends`, `streaming_updates`, `tail_replacements_1000`, `unchanged_state`, `resize_sequence`.
- **REQ-UIBENCH-054** — `construct_window`: the product's main window is created against the interface state the fixture will drive, sized to the opening canonical size of REQ-UIBENCH-048, and shown offscreen (REQ-UIBENCH-112). It is the only phase allowed to change the number of interface elements alive in the process: from the moment this phase's record is taken until the iteration ends, the `widgets` value must not change. This is the canonical rule, and the boolean of REQ-UIBENCH-085 reports exactly it.
- **REQ-UIBENCH-055** — `apply_fixture`: the entire fixture state is applied to the interface in one pass — agents (with `state` values checked against REQ-UIBENCH-028), todos, artifacts, KPIs, session name, session status, run state (with its value checked against REQ-UIBENCH-032), active model, and the complete transcript assigned in bulk rather than entry by entry.
- **REQ-UIBENCH-056** — `ordered_appends`: the transcript is cleared, then every transcript event of the fixture is added back individually, in fixture order, one event per update rather than in bulk — the same way events arrive in the live application.
- **REQ-UIBENCH-057** — `streaming_updates` (simulated token streaming): clears the transcript; for each event in order, the event's `text` is revealed as a sequence of prefixes of lengths 0, 256, 512, … (capped at the full text length), each step performing a full transcript assignment of all previously completed events plus a copy of the current event truncated to the revealed prefix. The final step always includes the full text; an event with empty text still produces exactly one (empty-prefix) step.
- **REQ-UIBENCH-058** — `tail_replacements_1000`: the text of the transcript's last entry is replaced exactly 1000 times, the whole transcript being re-applied after each replacement. Let L be the number of characters in that entry's text when the phase begins, or 1 if that count would be 0. Replacement i, for i from 0 through 999, uses i written in decimal and zero-padded to 8 digits, extended on the right with `x` characters to length L and then truncated to length L. If the transcript holds no entry when the phase begins, one substitute entry is inserted first — `timestamp` `00:00`, `role` `agent`, `text` of 256 `x` characters — so that the 1000 replacements always take place. Resident memory is sampled 11 times, at the replacement indices 0, 100, 200, 300, 400, 500, 600, 700, 800, 900, and 999; each sample is read immediately after the replacement at its index has been applied and the interface has finished showing it, never before. This phase's record carries those 11 values in that order as `rss_samples`, and carries `rss_second_half_growth_bytes`, the value sampled at index 999 minus the value sampled at index 500.
- **REQ-UIBENCH-059** — `unchanged_state`: the fixture's complete state is applied a second time, identical to the state already displayed. The record closing this phase reports the same displayed content, the same `widgets` count, and the same transcript row structure as the state that preceded the phase.
- **REQ-UIBENCH-060** — `resize_sequence`: resizes the window through the minimum canonical size → the opening canonical size → an intermediate 1180×760, which is this requirement's own figure and lies between the two → the minimum canonical size → the opening canonical size, both canonical sizes being REQ-UIBENCH-048's, settling after each resize and ending at the opening canonical size.
- **REQ-UIBENCH-061** — The final (resize-phase) record of each iteration additionally carries `rss_slope_bytes_per_second` — the ordinary-least-squares slope over that iteration's seven per-phase (elapsed_s, RSS) points — and `fixture_checksum`, the checksum of the fixture that was replayed.

### Per-record schema (run schema version 2)

- **REQ-UIBENCH-062** — A phase record is a JSON object whose keys are `schema_version` (the integer 2), `iteration` (integer), `phase` (one of the seven names listed in REQ-UIBENCH-053), `elapsed_s` (seconds to 3 decimals), `wall_ms` and `cpu_ms` (milliseconds to 3 decimals), `rss_bytes` (integer), `threads` (integer), `handles` (integer or null), `widgets` (integer), `ui_objects` (integer), `event_loop_lag_ms` (milliseconds to 3 decimals), `settle_timed_out` (boolean), `markdown_cache` (object), and `transcript_operations` (object). Those keys carry the meanings fixed by REQ-UIBENCH-049, REQ-UIBENCH-050, REQ-UIBENCH-051, REQ-UIBENCH-063, REQ-UIBENCH-064, and REQ-UIBENCH-119. Records of two phases carry additional keys of their own: `tail_replacements_1000` (REQ-UIBENCH-058) and `resize_sequence` (REQ-UIBENCH-061). A record the benchmark writes carries no key beyond those.
- **REQ-UIBENCH-063** — `markdown_cache` reports six values for the cache the interface keeps of rendered message bodies: `hits` and `misses`, running totals over the life of the child process that wrote the record, never reset between phases, so they grow monotonically through that iteration's seven records and are deliberately neither per-phase nor per-iteration figures; `entries` and `chars`, the occupancy at the moment the record was taken, expressed in cached items and in characters of the source text those items were rendered from — never in characters of rendered output, so `chars` is comparable with `max_chars` whatever the rendered form costs; and `max_entries` and `max_chars`, the capacities that occupancy is held to. Every record the benchmark writes reports all six keys, with `max_entries` 256 and `max_chars` 2000000. Whether a record's occupancy actually lies within its stated capacities is not assumed anywhere: REQ-UIBENCH-086 evaluates it and reports the answer, which matters because a run directory may also hold records the benchmark did not write (REQ-UIBENCH-075). The all-zero block of REQ-UIBENCH-076 is a substitution a reader makes for an absent block, never a value the benchmark emits.
- **REQ-UIBENCH-064** — `transcript_operations` is an object of exactly six non-negative integer counters — `noop`, `insert`, `remove`, `update`, `refused`, `reset` — each a running total, over the life of the process that wrote the record, of the transcript updates that fell into that category. Every application of a transcript state to the view is classified by comparing the state being applied with the state currently displayed, and contributes to the counters exactly as follows: `reset` counts one for each application that discards the displayed transcript wholesale and rebuilds it, which is every application that clears the transcript and every application the view cannot reconcile row by row; `refused` counts one for each application the view declines without changing anything, because the incoming state is not a valid successor of the displayed one — it addresses a row the view does not hold, or it would reorder rows already displayed; `noop` counts one for each accepted application in which the incoming state is identical to the displayed one, so no row changes; and every other accepted application contributes one to `insert` for each row added, one to `remove` for each row removed, and one to `update` for each retained row whose content changed, and nothing to `noop`. `refused` is therefore distinguished from `noop` by whether the application was valid, not by whether anything visibly changed: both leave the view unchanged, but only `noop` was accepted. No counter decreases from one record of an iteration to the next, so every phase's block is a cumulative total and the `resize_sequence` record holds that iteration's final totals. The totals are a function of the sequence of transcript states applied and of nothing else, so two iterations replaying the same fixture end with identical values for all six counters; REQ-UIBENCH-083 reports that agreement as a boolean.

### The inspect operation

- **REQ-UIBENCH-065** — Inspect builds its report from the chosen run directory's `iteration-*.jsonl` files together with its `iteration-*.crash` files (REQ-UIBENCH-069), and writes nothing to disk. Record files are read in bytewise ascending filename order and their records concatenated in that order. That read order fixes two things and nothing else: the order of every `*_raw` list in the report, and which record counts as first and last for REQ-UIBENCH-108. Which records belong to which iteration is decided solely by each record's own `iteration` value (REQ-UIBENCH-068, REQ-UIBENCH-073) and never by the name of the file that carried it, so the number of record files present and the reported `iterations` value need not agree. `inspect` never reads `summary.json`, even when the directory holds one, so its report always reflects the record files as they currently stand; `compare` deliberately prefers `summary.json` (REQ-UIBENCH-089).
- **REQ-UIBENCH-066** — Record reading is crash-tolerant: lines that fail JSON or text decoding, and decoded values that are not objects, are skipped. Given a record file ending in a truncated final line, all complete preceding records are still used.
- **REQ-UIBENCH-067** — The summary is a JSON object with top-level keys: `schema_version` (2), `iterations`, `records` (the total count of records read across all record files), `phases`, `crashes`, `fixture_checksums`, `process`, and `invariants` (plus `fixture_checksum` only when written by `replay`, per REQ-UIBENCH-042).
- **REQ-UIBENCH-068** — `iterations` is the number of distinct `iteration` values found across every record read. It is neither the requested iteration count nor the number of record files: an iteration that terminated before its record file was written contributes nothing; all records carrying no `iteration` value form one bucket that counts once; and one `iteration` value appearing in two different files still counts once. The same grouping by `iteration` value governs the per-iteration series of REQ-UIBENCH-073.
- **REQ-UIBENCH-069** — `crashes` is the count of files matching `iteration-*.crash` in the run directory.
- **REQ-UIBENCH-070** — `phases` maps each phase name (sorted) to: percentile blocks for `wall_ms` and `cpu_ms`, plus `rss_bytes_raw`, `threads_raw`, `widgets_raw`, and `operations_raw` (the per-record `transcript_operations`, defaulting to `{}`). Every per-record measurement is retained in its unreduced form in addition to the computed percentile blocks, so a consumer can recompute any statistic from the summary alone.
- **REQ-UIBENCH-071** — A percentile block has the shape `{raw: [...], p50, p95, min, max, mean}`; `min`, `max`, and `mean` are null for empty input, and `mean` is the arithmetic mean.
- **REQ-UIBENCH-072** — `fixture_checksums` is the sorted, de-duplicated list of every `fixture_checksum` value found in records (one per healthy iteration).
- **REQ-UIBENCH-073** — The `process` block contains: `rss_start` (first record in file order), `rss_peak` (maximum), `rss_end` (last record in file order), `rss_slope_bytes_per_second_raw` (the per-iteration in-child OLS slopes), `event_loop_lag_ms` (a percentile block over all records, missing values counted as 0.0), `threads_raw`, `handles_raw`, `widgets_raw`, `rss_theil_sen_bytes_per_second_raw` (one robust slope per iteration, records grouped by their `iteration` value with a default group of 0), `rss_theil_sen_bytes_per_second_p50` (the median of those slopes), and `tail_second_half_growth_bytes_raw` (the values from REQ-UIBENCH-058).
- **REQ-UIBENCH-074** — Inspecting an empty run directory — or a nonexistent path, which yields the same empty file set rather than an error — degrades gracefully: `iterations` 0, `records` 0, empty `phases`, all `process` scalars null and lists empty, and all invariants vacuously true.
- **REQ-UIBENCH-075** — Only files matching `iteration-*.jsonl` and `iteration-*.crash` are consulted; other files in the run directory are ignored. Any matching record file — including hand-added ones — is merged in sorted filename order; inspect trusts the directory contents.
- **REQ-UIBENCH-076** — `wall_ms` and `cpu_ms` must be present in every record read: a record lacking either makes inspect fail with the report of REQ-UIBENCH-097. That strictness is intended and is confined to those two keys, because they are the only values a reader cannot substitute for without inventing a measurement. It is deliberately not extended to `phase` or `iteration`: a record with no `phase` joins no phase block, and a record with no `iteration` joins the single default bucket of REQ-UIBENCH-068 and REQ-UIBENCH-073, both of which lose information without fabricating any. Every other per-record key may be absent, with these reader-side substitutions: a `markdown_cache` that is absent or is not an object reads as all six values 0, which passes the bound check of REQ-UIBENCH-086; a `transcript_operations` that is absent or is not an object reads as `{}`; an absent `event_loop_lag_ms` reads as 0.0; an absent `settle_timed_out` reads as false. An absent `rss_bytes`, `threads`, `widgets`, `ui_objects`, or `handles` contributes nothing at all to the corresponding `*_raw` list — no null and no placeholder is appended — so a `*_raw` list may be shorter than `records`, and a consumer must read each list by its own length and never align it positionally with another. A `handles` that is present and null is the single exception: it is appended as null, because null is a value that key may legitimately take (REQ-UIBENCH-050).

### Statistics semantics

- **REQ-UIBENCH-077** — Percentile: null for empty input; otherwise values are sorted and linearly interpolated between closest ranks at position (n−1)·q (the inclusive/"linear" method). The p50 of an even-sized list is the midpoint average of the two central values.
- **REQ-UIBENCH-078** — Linear (OLS) slope: null for fewer than 2 points; 0.0 when all x values are identical; otherwise the ordinary-least-squares slope.
- **REQ-UIBENCH-079** — Robust (Theil–Sen) slope: null when fewer than two points are supplied. When more than 2000 points are supplied, the series is first thinned to at most 2000 by retaining the point at index 0 and every k-th point after it, with k = ceil(n / 2000); a series of 2000 points or fewer is used whole. The reported value is then the median, computed as in REQ-UIBENCH-077, of the slopes of all pairs of points taken from the retained series, excluding every pair whose two x values are equal. If no pair survives that exclusion the result is null, since a median over an empty input is null.
- **REQ-UIBENCH-080** — Both the least-squares trend and the robust Theil–Sen trend appear in the summary's `process` block, so a single memory outlier cannot mask or fake a leak trend.

### Report invariants

- **REQ-UIBENCH-081** — `invariants` is an object of exactly seven booleans (REQ-UIBENCH-082 through REQ-UIBENCH-087 and REQ-UIBENCH-118); all seven are true for a healthy multi-iteration replay of a valid fixture.
- **REQ-UIBENCH-082** — `fixture_checksum_stable`: at most one distinct `fixture_checksum` value appears across all records — every iteration replayed the same fixture.
- **REQ-UIBENCH-083** — `operation_counts_identical`: the canonical (sorted-keys) serializations of the `transcript_operations` of every `resize_sequence` record — i.e. each iteration's final cumulative counters — are identical across iterations. This is the core determinism claim: fresh processes replaying the same fixture apply identical sequences of transcript updates.
- **REQ-UIBENCH-084** — `thread_delta_within_one`: the maximum minus the minimum native thread count across all records is at most 1 (vacuously true with no thread data).
- **REQ-UIBENCH-085** — `widgets_stable_after_warmup` is true exactly when, within each iteration taken on its own (records grouped by their `iteration` value, as in REQ-UIBENCH-073), every record other than a `construct_window` record reports one and the same `widgets` value; it is true when no such record exists. This is the rule REQ-UIBENCH-054 states, so the two never disagree — including for a hand-assembled run directory (REQ-UIBENCH-075), where records of two different non-construction phases of one iteration reporting different `widgets` values make the boolean false.
- **REQ-UIBENCH-086** — `markdown_cache_bounded`: in every record, `markdown_cache.entries` ≤ `max_entries` and `markdown_cache.chars` ≤ `max_chars` (missing cache info defaults to 0 and passes).
- **REQ-UIBENCH-087** — `tail_second_half_growth_below_64_mib`: every `rss_second_half_growth_bytes` value is strictly less than 64 MiB (67108864 bytes) — the memory-leak tripwire for the 1000-replacement tail phase.
- **REQ-UIBENCH-088** — Invariants are informational: a false invariant never turns inspect, replay, or compare into a failure, never appears in the error inventory of REQ-UIBENCH-097, and never changes the outcome any of them reports (REQ-UIBENCH-114). A consumer that wants a pass or fail must evaluate the JSON itself.
- **REQ-UIBENCH-118** — `interface_lag_within_budget`: every record read reports an `event_loop_lag_ms` strictly below 100 ms, the product's interface responsiveness budget (REQ-SHELL-150), so a replay in which the interface missed that budget at any point in any phase is visible as one false boolean without a reader having to scan the raw values. Missing lag values read as 0.0 (REQ-UIBENCH-076) and pass, and the boolean is vacuously true when no record was read. Like the other six it is informational (REQ-UIBENCH-088). This is the only absolute threshold the benchmark applies to a measured value; every other timing and memory figure it reports is comparative (REQ-UIBENCH-099).

### The compare operation

- **REQ-UIBENCH-089** — Compare loads each of its two chosen run directories from `<dir>/summary.json` when that file exists, otherwise computes the summary from the directory's record files on the fly. Since replay always writes `summary.json`, comparing two replay outputs is a pure file read. This is a deliberate difference from `inspect` (REQ-UIBENCH-065): where a written `summary.json` no longer matches the directory's record files, `compare` reports the file's figures and `inspect` reports the records'.
- **REQ-UIBENCH-090** — The comparison report has the shape `{"base": "<path as given>", "candidate": "<path as given>", "phases": {...}}`, where `phases` covers the sorted union of phase names from both sides, and each phase maps each of the two metrics `wall_ms` and `cpu_ms` to `{"base": <base p50>, "candidate": <candidate p50>, "delta": candidate − base, "percent": delta / base × 100}`.
- **REQ-UIBENCH-091** — Missing-data semantics: if either side lacks the phase/metric p50, `delta` and `percent` are null; if `delta` exists but the base p50 is 0, `percent` is null (no division by zero).
- **REQ-UIBENCH-092** — For every metric entry of the report: `delta` is the candidate run's p50 minus the base run's p50, in the metric's own unit of milliseconds, and `percent` is that same difference expressed as a percentage of the base run's p50. A positive `delta` or `percent` therefore means the candidate was slower than the base, and a negative one means it was faster. Neither value is rounded, clamped, or compared against any threshold, and neither can make the operation fail (REQ-UIBENCH-093).
- **REQ-UIBENCH-093** — Compare compares only per-phase p50 wall and CPU times. It does not compare RSS, invariants, lag, or checksums; it imposes no thresholds; it never verifies the two runs used the same fixture (consumers can check each summary's `fixture_checksum`/`fixture_checksums`); and no content it finds ever makes it fail — it is a report generator, not a pass/fail gate. Comparing two directories that lack both `summary.json` and record files yields an empty `phases` object rather than a failure.

### Failure reporting and error inventory

- **REQ-UIBENCH-094** — *Withdrawn.* The product exposes no exit code to a user; the successful outcome of each operation is reported in the interface under REQ-UIBENCH-114, and the zero termination status of a healthy iteration process is an internal signal covered by REQ-UIBENCH-052.
- **REQ-UIBENCH-095** — *Withdrawn.* There is no argument list to reject and no exit-2 class; every operation input is chosen through the interface and an operation with a missing input cannot be started at all (REQ-UIBENCH-111, REQ-UIBENCH-113).
- **REQ-UIBENCH-096** — *Withdrawn.* An iteration count below 1 is unreachable through the control of REQ-UIBENCH-113, so neither the message nor the exit code this requirement fixed can occur.
- **REQ-UIBENCH-097** — An operation fails, and reports that failure under REQ-UIBENCH-114, in exactly these cases and no others: the chosen session is missing, or its store will not open (REQ-UIBENCH-013); the session's resumable state is absent (REQ-UIBENCH-015); the session schema version is unsupported (REQ-UIBENCH-016); no effective workspace configuration is available during capture (REQ-UIBENCH-017); each of the four fixture validation failures, which must be distinguishable from one another (REQ-UIBENCH-024); the replay output directory already exists (REQ-UIBENCH-035); a fixture or a `summary.json` that cannot be read or decoded; and a phase record missing `wall_ms` or `cpu_ms` during inspect (REQ-UIBENCH-076). Every report identifies which of these causes occurred and the session, path or value that caused it. Nothing else makes an operation fail: in particular a crashed iteration, a false invariant, a `settle_timed_out` record, and a merely slow phase never do.
- **REQ-UIBENCH-114** — Every benchmark operation SHALL report its own outcome in the interface. A success report SHALL identify the operation and where its output was written, if anywhere. A failure report SHALL identify the operation, which cause of REQ-UIBENCH-097 occurred, and the path or value that caused it, SHALL be copyable as text, and SHALL leave the interface usable and the card of REQ-UIBENCH-110 ready to run another operation. A replay that completed with crashed iterations SHALL additionally report how many iterations crashed and SHALL make each retained iteration log (REQ-UIBENCH-117) reachable from that report. What each report must convey is fixed here; its wording is left to the implementation. No benchmark outcome — a failed operation, a crashed iteration, or a false invariant — SHALL affect the desktop application itself, which continues running unchanged.

### Determinism and performance envelope

- **REQ-UIBENCH-098** — Every input that shapes a measurement is fixed by the benchmark rather than taken from the host: rendering produces no on-screen output; the widget style is one platform-independent choice; the display scale factor is 1; the locale is C; every environment variable the product reads is removed from the iteration environment; settings are written to a directory created fresh for each iteration and destroyed with it; typefaces are the three bundled families of REQ-SHELL-008 and the theme is the product's default built-in theme (REQ-SHELL-128), neither taken from the host; the window sizes are those of REQ-UIBENCH-048 and REQ-UIBENCH-060; the seven phases of REQ-UIBENCH-053 run once each in that order; the workloads are fixed (256-character streaming steps, 1000 tail replacements, the fixed resize list); iterations run one at a time in fresh processes; and the fixture is frozen and checksum-verified before each iteration. Testable consequence: changing the host's theme, locale, display scaling, installed fonts, product environment variables, or stored desktop settings between two replays of the same fixture leaves the structural counters, the seven invariants, and the `records` and `iterations` counts identical, while the timing and memory values may differ (REQ-UIBENCH-099).
- **REQ-UIBENCH-099** — The published determinism claim: two fresh offscreen replays of the same fixture produce identical per-iteration cumulative operation counters and satisfy all seven invariants with zero crashes. Timing and memory values (wall, CPU, lag, RSS) are explicitly not expected to be identical between runs — only structural counters must match; timings are reported as distributions. No absolute wall-clock, CPU, or memory figure is fixed for any phase on any hardware, and the benchmark states none: for those metrics it is a comparative instrument, and the only absolute threshold it applies is the responsiveness budget of REQ-UIBENCH-118.
- **REQ-UIBENCH-100** — Replay works from a hand-built minimal fixture with a valid checksum: no captured session is required to run the replay/inspect/compare pipeline.

### Edge cases

- **REQ-UIBENCH-101** — A replay of one iteration is valid: percentile blocks degenerate to single-element raw lists where p50 = p95 = min = max = mean = the value, and `operation_counts_identical` is vacuously true.
- **REQ-UIBENCH-102** — A fixture with an empty transcript: `ordered_appends` appends nothing and `streaming_updates` iterates nothing, but `tail_replacements_1000` still performs all 1000 replacements against the substitute entry, so the tail-leak tripwire always produces data.
- **REQ-UIBENCH-103** — A transcript event whose text is the empty string still produces one streaming step, and the tail phase's minimum replacement width of 1 prevents a zero-width replacement.
- **REQ-UIBENCH-104** — Overwrite asymmetry (deliberate): capture writes to a file chosen through the platform save chooser, which asks for confirmation before replacing an existing file and then overwrites it silently (REQ-UIBENCH-021), while replay refuses an existing output directory outright (REQ-UIBENCH-035) rather than offering to merge or replace it, because a run directory's contents are read as a whole and a partially replaced one would be silently misreported.
- **REQ-UIBENCH-105** — A replay in which every iteration crashed still completes and reports success as an operation (REQ-UIBENCH-114 reporting the crash count), and produces a run directory with no record files, a summary reporting `iterations` 0, `records` 0, `crashes` N, empty `phases`, vacuously-true invariants, and the top-level `fixture_checksum`; `summary.md` shows `Iterations: 0` and no phase bullets.
- **REQ-UIBENCH-106** — Non-ASCII transcript text round-trips through fixtures, records, and summaries as ASCII escape sequences; no checksum or output depends on the host locale or filesystem encoding.
- **REQ-UIBENCH-107** — The summary's `iterations` value can legitimately under-report the requested iteration count when iterations crash before writing records (REQ-UIBENCH-068).
- **REQ-UIBENCH-108** — `process.rss_start` and `process.rss_end` are the `rss_bytes` values of the first and last records in read order (bytewise ascending filename order, then order within each file), not of the lowest- and highest-numbered `iteration` values. For a run directory written by `replay`, where filenames and iteration indices agree, `rss_end` is therefore the last phase of the highest-numbered iteration that produced records.
- **REQ-UIBENCH-109** — `ui_objects` is present in every phase record and is reported for information only: none of the seven invariants of REQ-UIBENCH-081 reads it, no threshold applies to it, and no value it takes — however large, and however much it varies between records or between iterations — makes any operation fail or changes any outcome reported under REQ-UIBENCH-114. `widgets` is the only structural count any invariant constrains (REQ-UIBENCH-085).

## Data & Formats

All formats below are observable contracts of the benchmark: the files it writes, and the reports it presents and exports (REQ-UIBENCH-115).

### Benchmark surface

The benchmark has no command-line surface, no subcommands, no flags, and no exit codes. Its four operations — capture, replay, inspect, compare — are started from the performance-benchmark card in the Settings view's About tab and from nowhere else (REQ-UIBENCH-110, REQ-UIBENCH-111); their inputs are chosen through the product's session list and the platform file choosers; their outcomes are reported in the interface (REQ-UIBENCH-114). Iteration processes are started by the desktop application itself and are not invocable by anything else (REQ-UIBENCH-037).

### Session input (consumed by capture)

Capture reads a session, not a directory. Which session is settled by workspace plus session id (REQ-SESSION-001) and this document names no path; what it reads is the resumable state the sessions domain fixes plus three optional bulk parts, on the precedence of REQ-SESSION-036.

```
THE SUBJECT = (workspace, session id), chosen from the product's own session list
  resumable state                    # required
  transcript rows                    # optional: {"events": [...]}
  edit diffs                         # optional: {"diffs": [...]}
  configuration snapshot             # optional: {"config_snapshot": {...}}, from the launch audit
```

That layout is the one REQ-SESSION-036 defines and REQ-SESSION-037 orders; those requirements are normative for the file names, which of them are required, and the precedence between them, and the sketch above is a reader's aid that neither adds a file nor fixes one. There is no whole-state fallback file (REQ-SESSION-037). A session `schema_version` above the supported version is refused (REQ-UIBENCH-016, REQ-SESSION-038).

### Fixture file (schema version 1)

A single JSON object (2-space indent, ASCII-escaped, UTF-8, no trailing newline):

```
{
  "schema_version": 1,
  "source_checksum": "<sha256 hex over the session's recorded state, canonically serialized>",
  "transcript":  [ { timestamp, role, text, kind?, tool?, detail?, full_text?,
                     full_detail?, diff?, persona?, event_key?, status?,
                     duration?, started_at?, char_count?, stream_id? }, ... ],
  "agents":      [ { id, name, persona, state?, model?, task_title?, depth?,
                     tool_call_count?, token_count?, cost_label?, elapsed_s?,
                     error_text? }, ... ],
  "todos":       [ { id, phase_id, status, text, phase_name? }, ... ],
  "artifacts":   [ { id, slug, title, kind?, status?, importance?, summary?,
                     source_persona?, created_at? }, ... ],
  "kpis":        { cumulative_tokens?, cumulative_cost_label?, token_history?,
                   tool_calls?, tool_call_breakdown?, files_touched?, uncommitted? },
  "run_state":   { session_name?, session_status?, run_state?, active_model? },
  "fixture_checksum": "<sha256 hex of canonical JSON minus this key>"
}
```

Every optional entry key above is closed: a key outside these sets fails the iteration that rebuilds it (REQ-UIBENCH-033). Types and absent-defaults are fixed by REQ-UIBENCH-027 through REQ-UIBENCH-032.

Canonical JSON for checksumming: sorted keys, compact `,`/`:` separators, ASCII-escaped, UTF-8 bytes. Must never contain top-level `config`, `credentials`, `environment`, or `workspace` — capture never writes one and the loader refuses one (REQ-UIBENCH-024).

### Replay run directory

```
<output>/
  fixture.json            # byte-for-byte copy of the input fixture
  iteration-000.jsonl     # one per iteration that completed all phases
  iteration-001.jsonl
  iteration-NNN.crash     # only for crashed iterations; content: "exit_code=<n>\n"
  iteration-NNN.log       # only for crashed iterations; that iteration's captured output
  summary.json            # the inspect report + top-level fixture_checksum
  summary.md              # human digest
```

### Iteration record file (JSON Lines, run schema version 2)

Seven records per healthy iteration, compact separators, ASCII-escaped, one per line:

```
{"schema_version":2,"iteration":0,"phase":"<phase name>","elapsed_s":...,
 "wall_ms":...,"cpu_ms":...,"rss_bytes":...,"threads":...,"handles":<int|null>,
 "widgets":...,"ui_objects":...,"event_loop_lag_ms":...,"settle_timed_out":<bool>,
 "markdown_cache":{"hits":..,"misses":..,"entries":..,"chars":..,
                   "max_entries":256,"max_chars":2000000},
 "transcript_operations":{"noop":..,"insert":..,"remove":..,"update":..,
                          "refused":..,"reset":..}}
```

Phase-specific additions: the `tail_replacements_1000` record adds `rss_samples` (11 values) and `rss_second_half_growth_bytes`; the final `resize_sequence` record adds `rss_slope_bytes_per_second` and `fixture_checksum`.

Phase names: `construct_window`, `apply_fixture`, `ordered_appends`, `streaming_updates`, `tail_replacements_1000`, `unchanged_state`, `resize_sequence`.

### Run summary (`summary.json` / the inspect report)

```
{
  "schema_version": 2,
  "iterations": <distinct iteration count>,
  "records": <record count>,
  "crashes": <crash-marker count>,
  "fixture_checksum": "<only in replay-written summaries>",
  "fixture_checksums": [ ...sorted distinct... ],
  "phases": { "<phase>": { "wall_ms": <pctl block>, "cpu_ms": <pctl block>,
                           "rss_bytes_raw": [...], "threads_raw": [...],
                           "widgets_raw": [...], "operations_raw": [...] } },
  "process": { "rss_start", "rss_peak", "rss_end",
               "rss_slope_bytes_per_second_raw", "event_loop_lag_ms": <pctl block>,
               "threads_raw", "handles_raw", "widgets_raw",
               "rss_theil_sen_bytes_per_second_raw",
               "rss_theil_sen_bytes_per_second_p50",
               "tail_second_half_growth_bytes_raw" },
  "invariants": { "fixture_checksum_stable", "operation_counts_identical",
                  "thread_delta_within_one", "widgets_stable_after_warmup",
                  "markdown_cache_bounded",
                  "tail_second_half_growth_below_64_mib",
                  "interface_lag_within_budget" }
}
```

Percentile block: `{"raw": [...], "p50", "p95", "min", "max", "mean"}` (nulls on empty input).

### `summary.md`

```
# Rotaris replay benchmark

Iterations: <n>

- <phase>: wall p50 <x> ms; CPU p50 <y> ms
...
```

### Comparison report (the compare report)

```
{
  "base": "<path as given>",
  "candidate": "<path as given>",
  "phases": { "<phase>": {
      "wall_ms": {"base", "candidate", "delta", "percent"},
      "cpu_ms":  {"base", "candidate", "delta", "percent"} } }
}
```

`delta` = candidate − base; `percent` = delta / base × 100; nulls per REQ-UIBENCH-091; sign convention per REQ-UIBENCH-092.

### Environment contract

Iteration processes receive the invoking environment with every variable the product itself reads removed, plus overrides that force: rendering with no on-screen output, one fixed platform-independent widget style, display scale factor 1, `LANG=C`, `LC_ALL=C`, `XDG_CONFIG_HOME` set to that iteration's own temporary settings directory, and one benchmark-private variable naming that directory. Only `LANG`, `LC_ALL`, and `XDG_CONFIG_HOME` are named contractually; the remaining override names and values are private to the implementation, because nothing outside the product can start an iteration (REQ-UIBENCH-037, REQ-UIBENCH-039). Run schema version 2 identifies the record and summary formats of this benchmark only.
