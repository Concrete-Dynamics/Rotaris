# Session Persistence, Resume, and Background Sessions

## Overview

Every run persists its complete observable state under a per-session directory inside the workspace, written incrementally and atomically so that a crash loses at most a small, bounded window of recent changes. A persisted session can be listed, resumed with its full transcript and metrics intact, followed live from another process through its durable event history, repaired when the process that owned it died while its record still asserts a run in progress, exported as a standalone trajectory document, and deleted cleanly. One shared run lifecycle serves every way a run can be started — in the foreground of a desktop window, detached into the background, or launched from the requirement board — so locking, background execution, message-limit pauses, cancellation, and terminal results behave identically regardless of how the run was started.

## Requirements

### 1. Storage Locations and On-Disk Layout

- **REQ-SESSION-001** — A session's own files MUST be reachable at `<base_workspace>/.rotaris/sessions/<session_id>/`, where `<base_workspace>` is the workspace the run was started against — the workspace the desktop window has open — and `<session_id>` is the id of REQ-SESSION-009. One workspace path plus one session id MUST resolve to that one directory from every view and every background worker in the application, and binding the run to a worktree MUST NOT move it: per REQ-SESSION-085 the worktree becomes the run's effective root and is what the state records as `workspace_root`, but the directory anchor stays the invoking workspace. Exactly two kinds of session-derived data are written outside that directory: the workspace-level improvement-artifact store of REQ-SESSION-007 and the checkpoint refs of REQ-SESSION-162.
- **REQ-SESSION-002** — After a session's first successful state save, its directory MUST hold `state/`, `evidence/`, `metadata.json`, `summary.md`, `metrics.json`, `issues.json`, and `timeline.jsonl`. Of these, `metadata.json` is written by every save (REQ-SESSION-028); the others are either rewritten by a save or created when absent by diagnostics initialization (REQ-SESSION-132). The remaining names appear only once the matching activity has occurred and MUST NOT be assumed present by a reader: `lock` (only while a process owns the session), `artifacts/` (the per-session artifact store, holding `index.json` and artifact bodies), `evidence/debug.log` (once per-session logging attaches, REQ-SESSION-142), `evidence/events.jsonl` (once the event history opens, REQ-SESSION-089), `evidence/events.meta.json` (only after a trim, REQ-SESSION-144), `.message_limit_paused` (REQ-SESSION-107), `improvement_artifacts/`, and `state/transcript_archive.jsonl`. No other name is written at the session-directory root.
- **REQ-SESSION-003** — `state/` MUST contain `resume.json` (the resumable session state minus bulk fields), `ui_transcript.json` (shape `{"events": [...]}`), and `ui_edit_diffs.json` (shape `{"diffs": [...]}`) from the first state save onward. It MUST contain `run_config.json` — the launch audit of REQ-SESSION-138 — from the moment run startup records that audit, and MUST NOT contain it before then; a session that was created but never run therefore carries no launch audit, and loading it leaves the configuration snapshot empty (REQ-SESSION-036). It MUST additionally contain `transcript_archive.jsonl` once the live transcript has grown past the row cap of REQ-SESSION-192 and pages have been evicted, and MUST NOT contain it before then.
- **REQ-SESSION-004** — Inside `evidence/`, the names `tool-calls.jsonl`, `model-input.jsonl`, `context-selection.jsonl`, `report-validation.jsonl`, `memory.jsonl`, `permissions.jsonl`, and `conversations/index.json` MUST exist from the first state save onward (REQ-SESSION-132); `debug.log` (per-session log), `events.jsonl` (the durable event history), `events.meta.json` (the truncation sidecar), and per-conversation event files under `conversations/event_logs/<conversation_id>/events/*.json` MUST use exactly those names when they are produced, per REQ-SESSION-002.
- **REQ-SESSION-005** — *Withdrawn.* A clean-room product has no predecessor layout to fall back to, so a legacy whole-state `snapshot.json` cannot exist; `state/resume.json` is the only resumable-state file (REQ-SESSION-037).
- **REQ-SESSION-006** — `metadata.json` and `summary.md` MUST be derived sidecars, rebuilt from state on every save; a loader MUST take its facts from the state files and never from these.
- **REQ-SESSION-007** — Improvement artifacts referenced by the session state MUST be persisted under `<session_dir>/improvement_artifacts/` and also copied to the workspace-level store at `<workspace>/.rotaris/improvement_artifacts/`; both copies MUST survive resume.
- **REQ-SESSION-008** — *Withdrawn.* The alias existed only for compatibility with a predecessor layout this product does not have; reaching the session log is a desktop capability and is carried by REQ-SESSION-191.

### 2. Session Identity

- **REQ-SESSION-009** — New session ids MUST have the shape `YYYYMMDD-HHMMSS-` followed by 12 lowercase hexadecimal characters, matching the regular expression `^\d{8}-\d{6}-[0-9a-f]{12}$`. The id MUST be minted before the first state write is persisted, so a caller can name and display the run before any work happens.
- **REQ-SESSION-010** — The session directory's name MUST equal the session id, and subsystems MAY rely on this equivalence as a fallback resolution rule (e.g. resolving a diagnostics key, event-history key, or scheduler binding from a directory path).
- **REQ-SESSION-011** — A caller MUST be able to pre-name a new session by supplying the session id in the run request (so the run is addressable and displayable before any worker output arrives); a supplied new-session id MUST be ignored when the request resumes an existing session.
- **REQ-SESSION-012** — Session ids MUST never be reused. Follower and history consumers are entitled to assume that two different histories never share one session path (see REQ-SESSION-149).

### 3. Resumable State: Schema Rules and Defaults

- **REQ-SESSION-013** — The persisted session-state schema version MUST currently be `1`, and every persisted state MUST carry a `schema_version` field defaulting to the current version.
- **REQ-SESSION-014** — `created_at` and `updated_at` MUST be UTC timestamps; their JSON serializations MUST end with a `Z` suffix. `workspace_root` MUST be persisted as a string path.
- **REQ-SESSION-015** — Loading a state payload with absent optional keys MUST succeed by applying defaults (legacy tolerance is the general schema rule): missing check-suite record loads as null; pre-cost snapshots load with an "unavailable" cost; pre-attribution snapshots load with empty attribution strings. Field defaults MUST include: empty config snapshot, empty transcript events, empty edit-diff list, empty child-state list, empty report-artifact list, null todo states, null outer-loop progress, null token usage, execution status `idle`, empty exhausted-model list, message count 0, null message limit, and null wait state.
- **REQ-SESSION-016** — Run-audit facts MUST be recorded at session start both on the state and into `state/run_config.json`: run intent (default empty), permission mode (default empty), resolved check suite (default null), sandboxed flag (default false), and sandbox backend name (default empty). For snapshots written before these fields existed, the empty/false defaults describe those runs accurately rather than standing in for unknown data, and MUST NOT be backfilled.
- **REQ-SESSION-017** — Requirement attribution fields (`requirement_id`, `unit_id`) MUST default to empty strings for hand-started runs and MUST be set only when requirement-driven execution creates the session. Older snapshots MUST load via defaults without a schema version bump.
- **REQ-SESSION-018** — A session MAY carry an optional worktree binding record with fields `path`, `branch`, `base_branch`, `base_revision`, `created_by_session` (default true), `merge_status` (one of `ready`, `integrating`, `merged`, `merge_failed`; default `ready`), and `integration_session_id` (default null). The default null binding keeps pre-worktree snapshots loadable.
- **REQ-SESSION-019** — The session state MUST carry a `checkpoints` list, ordered oldest-first (newest last), where each entry maps an iteration to the git ref and commit that restore the tree as it stood at the end of that iteration (see Data & Formats). This list is the durable checkpoint mapping and MUST survive resume; entries MUST be pruned together with their refs.
- **REQ-SESSION-020** — The state MUST carry an `internal` boolean (default false). Internal sessions (machinery such as worktree-integration runs) MUST be durable on disk but hidden from normal session listings.
- **REQ-SESSION-021** — The state MUST carry a run-type marker distinguishing ordinary user-task runs (the default) from improvement and integration runs. The run type MUST be stamped at session creation and never changed on resume, so the kind of run is recoverable from disk alone and not only from the live process.
- **REQ-SESSION-022** — Global counters MUST be persisted: total tool-call count, global token aggregate, global cost aggregate, compression count, per-agent metrics (tool-call count, per-tool call counts, token usage, cost, compressions, last prompt-token count), and root-context token count. The default cost aggregate MUST read as "source unavailable" and render as "—", so an unpriced run never displays as free.
- **REQ-SESSION-023** — Compression-deduplication ids MUST be persisted keyed by agent name, with the empty string used for anonymous agents, so that compression accounting is exactly-once across resumes.
- **REQ-SESSION-024** — A provider refusal caused by an exhausted quota (HTTP 429, or an equivalent insufficient-quota rejection) MUST leave a durable mark on the session: the refused model is appended to the persisted `exhausted_provider_models` list as `<provider>/<model>` when the provider is known, and as `<model>` alone when it is not. From that moment on, and equally after the session has been closed and reloaded, no automatic model choice and no automatic retry inside that session may select a model whose identifier matches a list entry by exact string equality in the same form the entry uses. The exclusion binds automatic selection and automatic retry only: a model the user chooses explicitly is always usable, and choosing one MUST remove exactly that entry from the list — the user's choice is the evidence that the quota returned. Nothing else clears the list: it is never cleared on a timer, on resume, or by a quota window the product cannot observe, so an untouched session never silently resumes calling a model that refused it.
- **REQ-SESSION-025** — These interactive-wait fields MUST be persisted with the session and MUST come back unchanged when it is reloaded: `pending_questions`, gaining an entry when a question action fires and losing it when that question's tool result arrives (REQ-SESSION-129); `pending_approvals`, a map from request id to the payload of the tool call suspended on interactive approval, an entry disappearing when the request is answered, when it is cancelled, or when it expires under the approval wait of REQ-TOOLS-055, whose budget is the single configuration key REQ-CONFIG-126 registers — this domain names no key, states no default, and defines no timeout of its own; `wait_state`, non-null while and only while the run is suspended on provider quota; `verifier_state`, where null means that no check is running at that moment and never that a check ran and found nothing; and `gate_warning`, a string that survives across individual checks and is cleared only when a completion gate records a decision (the `completion_gate_decision` timeline entry of REQ-SESSION-134). `pending_questions` and `pending_approvals` are the only inputs to `metadata.json`'s `awaiting_input` (REQ-SESSION-031).
- **REQ-SESSION-026** — A mid-session runtime model override (active model key and runtime model configurations) MUST persist across calls and across reloads of the session.
- **REQ-SESSION-027** — Serialization MUST round-trip loss-free: deserializing a state's own JSON serialization MUST reproduce an equal state.

### 4. Saving State

- **REQ-SESSION-028** — Every state save MUST write the split layout: (re)create the session directory, ensure all inspection files exist (create-if-missing, see REQ-SESSION-132), then atomically write `state/resume.json`, `state/ui_transcript.json`, `state/ui_edit_diffs.json`, `metrics.json`, `summary.md`, and finally `metadata.json`. No whole-state `snapshot.json` may be written.
- **REQ-SESSION-029** — `state/resume.json` MUST hold the session state with its bulk fields emptied: `config_snapshot` written as an empty object, `transcript_events` and `ui_edit_diffs` as empty lists, and every entry of `report_artifacts` reduced to a reference carrying only `id`, `agent_name`, `status`, and `path`. Transcript events, edit diffs, and the config snapshot remain recoverable from `state/ui_transcript.json`, `state/ui_edit_diffs.json`, and `state/run_config.json` respectively (REQ-SESSION-036); a report artifact's body is not duplicated under `state/` and is read from the session artifact store at the `path` its reference carries.
- **REQ-SESSION-030** — `metadata.json` MUST contain exactly these keys: `session_id`, `created_at`, `updated_at` (ISO-8601 strings), `execution_status`, `schema_version`, `internal`, `worktree` (the binding record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Every attribute a listing shows about the session itself MUST be one of these keys — making a new attribute list-visible is a change to this key set, not a reader-side extension — and the only other file a listing may consult is that session's `lock`, and only to decide liveness (REQ-SESSION-056, REQ-SESSION-182). Readers MUST tolerate directories written by older versions by defaulting absent keys: `checkpoint_count` → 0, `task_title` → the session id, `requirement_id` and `unit_id` → empty string, `awaiting_input` → false.
- **REQ-SESSION-031** — `awaiting_input` MUST be true exactly when the state holds any pending approvals or pending questions, so a run that is waiting on human input can be identified from any surface and remains identifiable after a restart.
- **REQ-SESSION-032** — `task_title` MUST be derived from persisted todo state as the last non-blank task name across phases (the newest top-level task), skipping blank names and empty phases; it MUST be empty when there is none.
- **REQ-SESSION-033** — Every state file MUST be written atomically: content is written to a temporary file in the destination directory and atomically renamed into place, a crash during the write therefore leaves either the previous complete file or the new complete file, and never a partially written one. On Windows, a transient access-denied error on the rename (antivirus, indexer, or cloud-sync holding a handle) MUST be retried up to 5 times with exponential backoff starting at 0.05 s (0.05, 0.1, 0.2, 0.4, 0.8 s). The temporary file MUST always be removed.
- **REQ-SESSION-034** — Writes MUST be incremental in the crash-loss sense: the resumable core is one small file, derived sidecars are regenerated, and high-volume history goes to append-only JSON-lines files. A crash MUST lose at most the un-flushed debounce window plus one partial trailing JSON line.
- **REQ-SESSION-035** — A save MUST stamp `updated_at` with the current UTC time before writing.

### 5. Loading State, Legacy Fallback, and Corruption

- **REQ-SESSION-036** — Loading MUST first try the split layout: read `state/resume.json`, then rehydrate transcript events from `state/ui_transcript.json` (key `events`), edit diffs from `state/ui_edit_diffs.json` (key `diffs`), and the config snapshot from `state/run_config.json` (key `config_snapshot`, only when it is an object). Each of these three secondary files is optional. A secondary file that is absent, and a secondary file that is present but cannot be parsed or does not carry its expected key, MUST be treated identically: the corresponding field loads empty, the load succeeds, and a warning is logged and an issue recorded (REQ-SESSION-135) naming the file and the reason. Only `state/resume.json` failing to parse fails a load (REQ-SESSION-041) — these three hold recoverable bulk data whose loss degrades a reopened session rather than invalidating it.
- **REQ-SESSION-037** — `state/resume.json` is the only resumable-state file, and there is no alternative whole-state file to fall back to. If it is absent, loading MUST fail with a not-found error conveying the session id as supplied and that no session state is stored under it in that workspace; the wording is left to the implementation.
- **REQ-SESSION-038** — A `schema_version` greater than the supported version MUST be refused with an error conveying the version found and the version supported — an incompatible snapshot is refused, never lossily restored. The wording is left to the implementation.
- **REQ-SESSION-039** — *Withdrawn.* There is no legacy layout to migrate forward from; every session is written in the split layout from its first save.
- **REQ-SESSION-040** — Two read modes MUST exist: a full open (used to run or resume a session) that applies post-deserialization repairs (see REQ-SESSION-170), and a read-only snapshot read (used by display-only consumers) that performs the same read with no repairs and no filesystem writes.
- **REQ-SESSION-041** — Corruption tolerance MUST live at the consumer: a corrupt `resume.json` propagates a parse error from the loader, and every caller MUST catch it and degrade — the desktop session browser reports the session as unreadable, conveying the session id and the parse detail and leaving every other session usable (REQ-SESSION-182); stale repair treats it as "nothing to do"; checkpoint-ref cleanup skips the session; and listing paths skip the entry. The wording of the report is left to the implementation.

### 6. Session Listing

- **REQ-SESSION-042** — Listing MUST scan the sessions root one level deep and silently skip any entry that is not a directory, holds no `metadata.json`, whose `metadata.json` does not parse as JSON, or whose `updated_at` is absent or unparseable. Surviving entries are returned as the records stored in `metadata.json`, with reader-side defaults applied per REQ-SESSION-030, filtered per REQ-SESSION-044, and ordered by `updated_at` descending so the most recently updated session comes first. Building the list reads no file other than each entry's `metadata.json`; a presentation layer that marks stale sessions additionally reads that session's `lock` file and nothing else (REQ-SESSION-056, REQ-SESSION-182).
- **REQ-SESSION-043** — A missing sessions root MUST produce an empty list rather than an error. A workspace in which no run has yet taken place is an ordinary state.
- **REQ-SESSION-044** — Default listing MUST exclude sessions whose metadata `internal` flag is truthy; an explicit include-internal option MUST return everything (used by recovery and machinery).
- **REQ-SESSION-045** — One corrupt session MUST never cost the listing the others: every other session still appears.

### 7. Session Locking

- **REQ-SESSION-046** — The lock is a file named `lock` at the session-directory root, created via an atomic exclusive-create operation, containing JSON `{"pid": <int>, "host": "<stable identifier of the machine whose process holds the lock>", "acquired_at": "<UTC ISO timestamp>"}`. These three key names and their value types are a machine-readable contract and are the same ones REQ-GIT-020 fixes for this file.
- **REQ-SESSION-047** — Lock acquisition MUST return success/failure rather than raising. When the lock already exists, at most one stale-reap attempt MUST be made (two create attempts total), and the reap MUST happen only when all of the following hold: the file's content parses as the JSON of REQ-SESSION-046, its `host` names this machine, and its `pid` probes dead here. In that case the stale lock is removed and the exclusive create retried once. In every other case — the content is unreadable or does not parse, `host` is absent or names another machine, `pid` is absent or not an integer, `pid` is ≤ 0, or the pid probes alive — the lock MUST be respected, acquisition MUST fail, and the lock file MUST be left exactly as it was found. There is no waiting, no bounded retry loop, and no second reap: a lock file that another party keeps recreating can never make acquisition spin.
- **REQ-SESSION-048** — Creating a session MUST persist the initial state first, then acquire the lock; an acquisition failure at creation raises an error conveying the session id, the pid and host the existing lock records, and that nothing was started. A freshly created session is left lock-held by its creator. The wording is left to the implementation.
- **REQ-SESSION-049** — Releasing the lock MUST first tear down the session-scoped shared services holding long-lived subprocesses (MCP servers, language servers) and then remove the lock file; releasing a missing lock is a no-op.
- **REQ-SESSION-050** — No more than one process may hold a given session's lock at any moment; several locked background sessions MAY nonetheless coexist within a single workspace.

### 8. Process Liveness Probing

- **REQ-SESSION-051** — The pid liveness probe MUST answer "dead" for any pid ≤ 0, MUST never raise, and MUST answer "alive" whenever the outcome is uncertain. The two error directions are not equivalent: answering "dead" for a live process lets a restore run concurrently with work still in flight, while answering "alive" for a dead one costs the user nothing worse than invoking the explicit repair step.
- **REQ-SESSION-052** — On POSIX platforms: a process-not-found result proves death; a permission-denied result MUST count as alive (the probe was refused, not answered); any other probe error MUST count as dead only when the platform semantics prove absence, otherwise alive.
- **REQ-SESSION-053** — On Windows: the probe MUST NOT deliver any signal or console control event to the target process (in particular, implementing the probe as a null signal is a defect there, because it injects a real console interrupt into the target). Only an OS-level "no such process / invalid parameter" error proves absence; a still-running indication means alive; access denied or any other failure MUST count as alive.
- **REQ-SESSION-054** — The following residual limitations are accepted, documented behavior (not defects to be silently "fixed" in ways that break the resolve-toward-alive rule of REQ-SESSION-051): when the operating system recycles a pid onto an unrelated process, the session reports alive until that unrelated process exits; and on Windows an already-exited process can keep reporting alive while any open handle to it survives. Both resolve toward "live", which is the safe direction. A session held from a different machine across a shared filesystem is no longer among these limitations: the lock's `host` field (REQ-SESSION-046) makes that case detectable, and REQ-SESSION-056 resolves it toward "live" by construction, so such a lock is never reclaimed automatically. A lock that cannot be reclaimed automatically and that the user knows to be orphaned is released through the explicit action of REQ-SESSION-183.

### 9. Stale-Session Detection and Repair

- **REQ-SESSION-055** — Exactly six `execution_status` strings assert that a run is in progress: `starting`, `running`, `background`, `waiting`, `pausing`, `cancelling`. `waiting` is one of them because a run parked on a provider quota wait is still alive and the agents parked on that wait must remain visible as such (REQ-MONITOR-195, REQ-MONITOR-291). The test is exact, case-sensitive equality against that set; every other value — whether it belongs to the wider vocabulary of REQ-SESSION-073 or is unknown to this version — MUST answer "no run in progress". Given one persisted status, every surface that asks the question MUST give the same answer: stale detection and repair (REQ-SESSION-057), the worktree-integration precondition (REQ-SESSION-064), the stale marking in the desktop session list (REQ-SESSION-182), and the settling of displayed agent and tool state (REQ-SESSION-078, REQ-SESSION-079).
- **REQ-SESSION-056** — A session counts as **live** exactly when a `lock` file is present and it is not proved unheld: it is proved unheld only when the file parses as the JSON of REQ-SESSION-046, its `host` names this machine, and the `pid` it records probes dead here. A missing lock file is the sole unambiguous signal that no process holds the session; every other case — a lock that cannot be read, a lock that does not parse, a lock whose `host` is absent or names another machine, a lock carrying no pid or a non-integer pid, a pid ≤ 0, or a failed probe — MUST report live. This is exactly the test REQ-SESSION-047 applies before reaping, so liveness and reapability can never disagree (REQ-SESSION-171). An empty session id is never live.
- **REQ-SESSION-057** — A session is **stale** if and only if its metadata `execution_status` is in the active set and the session is not live. Sessions in terminal statuses (`completed`, `failed`, `paused`, `idle`, `paused_message_limit`, `interrupted`, `stopped`, ...) are never stale regardless of lock state.
- **REQ-SESSION-058** — Stale detection MUST read only `metadata.json` (including internal sessions) and the lock file, MUST write nothing to disk (verifiable by fingerprinting the tree before and after), and MUST report an empty result — not raise — over a broken session store.
- **REQ-SESSION-059** — Each detected stale session MUST report: the session id, the stuck execution status, `updated_at` exactly as the dead process left it (detection MUST NOT restamp it; an unparseable timestamp normalizes to the epoch); and a human-readable reason. Exactly two conditions can produce a stale session (REQ-SESSION-056), and the reason MUST say which applied: no lock file is held for the session at all, or the lock names this machine and the pid it records is gone — the second naming that pid. The wording is left to the implementation; the same text is what REQ-SESSION-062 interpolates and what the desktop shows when it announces a repair.
- **REQ-SESSION-060** — Repair MUST be explicit — never triggered automatically from a read path. A repair MUST: re-check liveness; read the state (unreadable state means "nothing to do"); require an active status; set `execution_status` to `interrupted`; flush immediately, bypassing the debounce (the correction must be durable even if the process dies again at once); then best-effort remove the orphaned lock; then write a diagnostics timeline entry. Ordering is mandatory — status first, lock second; releasing the lock first would open a window in which the record still asserts a running session with no lock behind it. A filesystem error during the flush MUST leave everything untouched. Repair MUST never raise.
- **REQ-SESSION-061** — The repaired status MUST be `interrupted`, an existing status word chosen because it sits outside the active set, so a repaired session can never again report as occupied.
- **REQ-SESSION-062** — The repair timeline entry MUST have type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, and metadata `{previous_execution_status, execution_status, reason}`. A diagnostics failure MUST NOT fail the repair.
- **REQ-SESSION-063** — Repair-all MUST repair every stale session and be idempotent: a second pass repairs nothing and rewrites nothing (fingerprint-verifiable). A live session next to a dead one MUST be untouched and keep its lock.
- **REQ-SESSION-064** — Worktree integration's "base not in use" precondition is the one read path allowed to *bypass* (not repair) staleness: a session in an active status whose process is dead MUST be skipped rather than blocking integration forever, with the durable status correction left to the explicit repair action of REQ-SESSION-182; a genuinely live session MUST block integration with the error `A session is still running in the base worktree. Finish it before integrating.`
- **REQ-SESSION-065** — When a run acquires the session lock and has not yet started work, it MUST settle orphaned children: every persisted child-agent record whose state is not in the terminal set `{succeeded, failed, cancelled, blocked}` is set to `cancelled`, given a completion timestamp (UTC ISO with `Z`, only if absent), and has its active-tool list cleared; terminal children keep everything. The operation reports how many records it moved and is idempotent. Holding the lock is itself proof that the previous owner has exited, so this settling step MUST NOT probe process liveness.
- **REQ-SESSION-066** — A session persisted in an active status whose owning process is gone MUST be observable in two ways at once: restoring one of its checkpoints is refused and restores nothing, leaving the working tree byte-identical (REQ-SESSION-164), and the desktop session list shows that session with its stored status marked stale (REQ-SESSION-182). After the repair action of REQ-SESSION-182 has reported that session repaired, the same restore MUST succeed and the same list MUST show `interrupted` with no stale marking.
- **REQ-SESSION-183** — Because a lock that cannot be read, or that names another machine, always counts as live (REQ-SESSION-056) and is never reclaimed automatically, the application MUST offer one explicit, user-confirmed action that releases such a lock. It MUST be offered only for a session that reports live and that no process in this application holds, MUST state before it acts what the lock records — the pid, the host, and when it was acquired — and MUST state that releasing a lock a live run still holds risks two processes writing one session. On confirmation it removes the lock file and nothing else; the session's `execution_status` is left exactly as it stands, so a session that then reads as stale is repaired by the ordinary explicit repair of REQ-SESSION-060. The action MUST never run automatically, MUST never be offered as a remedy inside an error the user did not ask to resolve, and is the only way a lock this machine cannot prove dead is ever removed.

### 10. Save Debouncing and Write Ordering

- **REQ-SESSION-067** — Saves for sessions in status `running` or `idle` MUST be debounced with a 10.0-second window: the first save following an idle interval is written at once, and any save arriving while the window is open is deferred and written when it closes, with no additional calls required. Saves for any other status (terminal or transitional) MUST flush immediately, and MUST flush any parked pending state first. An explicit flush always writes immediately.
- **REQ-SESSION-068** — Saving MUST behave as follows from a caller's point of view. A save request captures the state as it stands at the instant of the request, so that changes made after the request cannot alter the bytes of a write already under way and cannot produce a file that mixes two states. A save that is not written at once MUST still reach disk by the close of the debounce window of REQ-SESSION-067, with no further call from the caller. An explicit flush MUST write immediately and MUST cancel any save still waiting for that window to close, so the window never adds a second write of the same state. The flush entry point MUST be usable from any caller's context, including one where no asynchronous runtime is active, and MUST NOT return until the newest requested state is on disk.
- **REQ-SESSION-069** — When several saves for one session are requested in close succession, the file left on disk MUST correspond to the state of the *last* request, never to an earlier request whose write happened to finish later. In particular, a `running` save requested before a `completed` save MUST NOT be the one that survives, whatever order the two writes complete in. A write abandoned for this reason MUST be reported in the session log as `Dropped a stale session write for <id>: generation <g> lost to <c> (state '<status>' would have overwritten a newer save).`, where `<g>` identifies the abandoned save request, `<c>` the newer request that superseded it, and `<status>` the `execution_status` the abandoned write carried. This ordering rule applies within one session only: a save requested for one session MUST NOT suppress, delay, or discard a save requested for a different session.
- **REQ-SESSION-070** — Two guarantees MUST hold at the call boundary. First, once a flush returns, the persisted state is never older than the newest state any caller has asked to have saved; a flush is permitted to return without writing only in the case where a later save has already made that true. Second, a save carrying a terminal status MUST NOT return before that status can be read from disk by a separate process, so a caller that has been told the run finished can rely on the finish being durable.
- **REQ-SESSION-071** — The debounce window of REQ-SESSION-067 is 10.0 seconds and no supported configuration key changes it. Its observable effect is a bound on write volume: however many saves a `running` or `idle` session requests inside one window, at most two state files are written for them — the save that opened the window and the save that closes it — and the deferred one lands no later than 10.0 seconds after the window opened. That bound is the whole contract and no further coalescing is required: under sustained save pressure a `running` or `idle` session produces at most twelve debounced state writes per minute, and a conforming implementation MUST NOT be expected to produce fewer, nor may a consumer assume it does. Writes that REQ-SESSION-067 and REQ-SESSION-070 require to happen at once (status changes, explicit flushes, terminal statuses) fall outside this bound. A surface that shows a run as it progresses MUST take its updates from the event history of Section 18; re-reading persisted state on a timer is not a supported way to follow a run and MUST NOT be relied on for refresh latency.
- **REQ-SESSION-072** — Any state persisted while a run is under way MUST already carry that run's current metric aggregates (REQ-SESSION-168), so a reader never finds a saved state whose counters lag the transcript saved beside them. Such saves are subject to the debounce window while the status is `running` or `idle`; a save that accompanies a status change, and any save taken where no asynchronous runtime is active, MUST be on disk before the save call returns.

### 11. Run Status Lifecycle and Results

- **REQ-SESSION-073** — The persisted `execution_status` vocabulary is closed and consists of exactly these fourteen values: `idle` (initial; also after continuing past a message limit), `running` (run start), `background` (a run whose view has been detached, REQ-SESSION-190), `waiting` (a run parked on a provider quota wait, REQ-MONITOR-195), `paused` (interrupt/cancel paths), `paused_message_limit` (automatic message-limit pause), `awaiting_plan_decision` (a run blocked at the plan gate until the user answers, REQ-ORCH-153), `completed` and `failed` (run summary), `stopped` (a run that came to rest without completing and without being cancelled: the user stopped it from the interface, REQ-SESSION-186, or a configured run budget was exhausted, REQ-MONITOR-029), `interrupted` (written only by stale repair), and the transitional statuses `starting`, `pausing`, `cancelling` (which MUST be honored as active claims when persisted). This requirement is the single definition of that vocabulary for the whole product: a document that needs to name a persisted status cites this identifier rather than restating the set, and a domain that introduces a condition needing a status of its own extends this list rather than persisting a value of its own. No part of the product may persist a value outside this set, so a value outside it can only reach a reader from a session directory written by a different version of this product. Such a value MUST be treated as non-active (REQ-SESSION-055), MUST be displayed verbatim rather than replaced by a guess, and MUST yield an error run result under REQ-SESSION-076.
- **REQ-SESSION-074** — End-of-run summarization is fixed by REQ-ORCH-082; this domain holds no copy of its arms, states no second ordering, and mints no summary status, severity, or message text of its own. What it relies on that requirement for is that the arms are evaluated in a normative order so that a run matching more than one has exactly one outcome; that the outcome is a status token, a severity, and human-readable text, the token drawn from a vocabulary of its own that is not the persisted `execution_status` vocabulary of REQ-SESSION-073 and not the terminal run-result vocabulary of REQ-ORCH-083; and that a run which resolved nothing is summarized as completed rather than failed, because nothing about it went wrong. The summarized status this domain persists alongside the session record is whatever that requirement produces, and a summarized status matched by none of the mappings this domain states MUST yield an error result under REQ-SESSION-077.
- **REQ-SESSION-075** — *Withdrawn.* Process exit codes are a shell contract and this product has no shell surface; the terminal run-outcome vocabulary the mapping was built on is carried by REQ-SESSION-187.
- **REQ-SESSION-076** — When no progress record exists, the run result MUST be derived from the session's terminal execution status through this total mapping: `completed` → completed; `failed` → failed; `paused`, `paused_message_limit`, `stopped` and `interrupted` → interrupted. Every other persisted status — the six active values of REQ-SESSION-055, `idle`, `awaiting_plan_decision`, and any value from outside the closed vocabulary of REQ-SESSION-073 — MUST yield an error result whose message conveys that the run ended without a terminal status. A session repaired to `interrupted` therefore reports an interrupted run rather than a generic error. This requirement is the single derivation of a run result from an execution status for the whole product: a document that needs one cites this identifier rather than stating a mapping of its own (REQ-MONITOR-031, REQ-EVENTS-027, REQ-ORCH-083), and a status added to REQ-SESSION-073 is carried into this mapping rather than left to a fallback elsewhere.
- **REQ-SESSION-077** — Stop-reason classification MUST use the closed stop-reason set of REQ-MONITOR-301 and the total stop-reason-to-result mapping that requirement fixes, comparing the recorded stop reason against that set by exact, case-sensitive equality. This domain states no stop-reason strings of its own and no second mapping: one mapping produces the outcome persisted here and the outcome any consumer reads. The result it produces stands whatever the task counts say — in particular `agent_session_aborted` yields failed even where the counts would otherwise read as success, because a run whose child agent aborted MUST NOT report success to an automated consumer. Where the run recorded no stop reason at all, the result is derived from the execution status instead, through REQ-SESSION-076. A recorded stop reason outside the closed set is a defect rather than a value to be classified by a fallback, and MUST produce an error result — never a successful one — as MUST a summarized status matched by none of the mappings of REQ-SESSION-074, REQ-SESSION-076, and this requirement.
- **REQ-SESSION-078** — On every read, display surfaces MUST settle the child-agent tree against the session's own status: when `execution_status` is neither active nor `idle`, any agent still recorded as running/waiting/queued MUST display as done (for completed-like states), failed (for failed/error), or cancelled (anything else), with activity text "ended with the run" and cleared tool indicators. A snapshot written by an earlier version, or left behind by a killed process, MUST NOT be rendered as a finished run whose agents still appear active.
- **REQ-SESSION-079** — On a session whose `execution_status` is not one of the six active values of REQ-SESSION-055, a transcript tool row persisted with status `running` MUST render with no status indicator and no elapsed timer, and a thinking row carrying no recorded start MUST NOT show a counting timer: a session with no run in progress cannot have a tool call outstanding.
- **REQ-SESSION-187** — A terminal run result MUST carry exactly one outcome from the closed terminal run-result set of REQ-ORCH-083; this domain holds no copy of that set and mints no outcome string of its own. What it relies on that requirement for is that the set is closed and machine-readable, so that the same strings are what the `result` and `session.end` payloads carry (REQ-SESSION-095), what REQ-SESSION-076 and REQ-SESSION-077 produce, and what the interface presents (REQ-SESSION-186). Every derivation that produces a run result MUST be total over the vocabulary it consumes: adding an execution status or a stop-reason class without extending the mappings of REQ-SESSION-076 and REQ-SESSION-077 MUST be an immediate, visible failure rather than a silent default to success. No outcome is expressed as a numeric code anywhere in the product.

### 12. The Shared Run Lifecycle

- **REQ-SESSION-080** — Exactly one run lifecycle MUST serve every way a run is started: a foreground run in a desktop window, a run detached into the background (REQ-SESSION-190), a run launched from the requirement board (REQ-SESSION-158), and a run started by product machinery such as worktree integration. It MUST return a run result rather than terminating the application, and MUST present nothing to the user itself; even validation failures come back as error results carrying the diagnostic text; no caller may take a different code path.
- **REQ-SESSION-081** — The run request MUST support: the task text, configuration, an existing session id (whose presence means resume), a maximum iteration count, an isolate-in-new-worktree flag, an existing-worktree path, a worktree branch name, requirement attribution (ignored on resume), a pre-chosen new-session id (ignored on resume), a delegation strategy, a run type, and an internal flag.
- **REQ-SESSION-082** — The run request MUST be validated before anything is created, and a failure MUST return an error result (outcome `error`, REQ-SESSION-187) that is explicitly marked as having failed before the run started, so a consumer identifies the case from a field and never by parsing message text. Three combinations MUST be refused, each with a message conveying which fields conflict and what to do instead: the isolate flag together with an existing-worktree path; a worktree branch name without the isolate flag; and any worktree option on a request that resumes an existing session. The wording is left to the implementation. A validation failure MUST carry an empty session id, leave no session behind, and still emit exactly one terminal `result` event to the event sink.
- **REQ-SESSION-083** — The resume path MUST load the session then acquire its lock; a lock held elsewhere fails as a pre-run failure that does not steal the holder's lock, with the session id present in the result and a message conveying the session id and the pid and host the lock records (REQ-SESSION-048). With the lock held and nothing started, orphaned children MUST be settled (REQ-SESSION-065) and the configuration rebound into the session's stored worktree, if any.
- **REQ-SESSION-084** — The create path MUST create the session (lock held by creation, requirement attribution and the internal flag applied, run type stamped) and then bind the worktree: an isolating request creates a worktree owned by the session on a branch of its own, and two launches started at the same instant MUST both end up with a worktree of their own rather than one of them failing on a branch-name collision; attaching an existing worktree MUST record it as not owned by the session, so releasing the session never deletes a tree the caller owns. Collision resolution is not this domain's to invent: the branch name is the generated default of REQ-GIT-007 or the name the request supplied, and a name already taken as a ref or by another worktree receives the deterministic `-2`, `-3`, … suffixes of REQ-GIT-010. Because session ids are never reused (REQ-SESSION-012) a generated name collides only against a leftover branch from a session whose directory was deleted, or against a branch the user created; a supplied name collides whenever the user reuses one. A bind failure MUST release the lock, **delete the just-created session directory** (REQ-SESSION-167), and return an error result whose message conveys that the requested worktree could not be created or attached, carrying the underlying detail.
- **REQ-SESSION-085** — For a worktree-bound run, the run's effective working tree and the state's persisted `workspace_root` are the worktree path, while the session directory itself stays beneath the invoking workspace's `.rotaris` (REQ-SESSION-001). The configuration snapshot rebound to the worktree MUST be flushed to the session immediately after binding. The three requirements that touch the configuration snapshot resolve as follows and MUST be read together: `state/resume.json` never carries it (REQ-SESSION-029); `state/run_config.json` is its one durable copy and is what a load rehydrates it from (REQ-SESSION-036); and because that audit is written by run startup *after* binding and after the sandbox verdict (REQ-SESSION-138), it records the rebound configuration and never the pre-binding one. The rebound snapshot is therefore durable, and the audit is still written exactly once and never rewritten.
- **REQ-SESSION-086** — The sandbox verdict MUST be taken before anything else the run does and recorded on the state (`sandboxed`, `sandbox_backend`). On failure: release the lock; a just-created session is deleted while a resumed session survives, so a failed launch never destroys pre-existing history; the result is an error result carrying the detail.
- **REQ-SESSION-087** — Run startup MUST then, in order and observably: rehydrate metric aggregates from the session (REQ-SESSION-169); attach per-session logging to `evidence/debug.log` at the configured session log level; write the launch audit `state/run_config.json` (REQ-SESSION-138), which is the first point at which the bound worktree and the sandbox verdict are both known; write a `run_start` timeline entry (actor `rotaris`, message conveying that a run is starting for the session and naming its id, metadata carrying the workspace root); persist `execution_status = "running"`; and invoke the caller's session-ready callback.
- **REQ-SESSION-088** — Per-iteration checkpoints MUST record the working tree in the state in which the iteration finished: any end-of-iteration lifecycle hooks that touch the tree MUST have run before the checkpoint is taken. Caller-supplied observers MUST be added alongside, never substituted for, the built-in ones.
- **REQ-SESSION-089** — Durable event-history attachment MUST be unconditional for every run through the shared lifecycle: the store is opened for the session and teed with the caller's own event sink. A store that cannot open MUST degrade to a logged warning (reporting that no event history will be available for later replay or export) with the caller's sink still attached; the run MUST proceed. A `session.start` event MUST be published immediately after attachment so that it is the first event any consumer observes.
- **REQ-SESSION-090** — The `session.start` payload MUST carry enough for a consumer to describe the run without opening the session directory: the session id; the task text; the workspace the run reports for itself; the persona; the permission mode as configured at launch (a later unattended downgrade is reported by permission events instead, so this value MUST NOT be restated when the effective mode changes); the sandbox verdict actually in force — the backend both configured *and* available, not the one merely requested; and the maximum iteration count.
- **REQ-SESSION-091** — A cancellation already requested before the loop exists MUST skip the agent runtime entirely (no model call, no grace-period unwind); the run reports the `interrupted` outcome of REQ-SESSION-187 and the session remains resumable at status `paused`.
- **REQ-SESSION-092** — Cancellation semantics: a graceful stop is requested first (the same path the interface's stop control uses, REQ-SESSION-186); if the loop has not reached a stop check within 30.0 seconds, a hard cancel follows. The stop request MUST be sticky — a cancel arriving before the loop's callbacks are wired replays when they are. A caller that requested cancellation MUST receive an interrupted outcome even when the loop finished first; reporting both an effective cancellation and a successful run to the same caller is forbidden. A cancellation raised from inside the run MUST still release the lock and emit the terminal result event.
- **REQ-SESSION-093** — Every outcome branch MUST persist state before returning: cancelled/interrupted → `execution_status = "paused"` plus a system transcript row `Run paused: interrupted by user.`; runtime exception → `failed` plus a row `Run failed: <formatted error>`; normal completion → status and row from the end-of-run summarization, after which the post-run improvement job is either handed to a caller-provided job sink or awaited inline with its result applied and persisted.
- **REQ-SESSION-094** — Run teardown MUST guarantee, in order, even on any exception: a `run_end` timeline entry (metadata carrying the final execution status); logging cleanup; **lock release**; construction of one run result; publication of `session.end` followed by exactly one `result` event, both delivered over the bus while the sink is still attached (so an attached consumer learns how the run ended); a final notice to the caller about disabled hooks; and finally removal of every per-session binding, ensuring a straggling event can neither be appended to a finished session nor trigger hooks belonging to a subsequent run in the same process.
- **REQ-SESSION-095** — The `session.end` payload MUST mirror the terminal run result (outcome per REQ-SESSION-187, stop reason, iterations completed, duration in seconds, tokens, cost), computed once and used for the event payload, the `result` event and everything the interface presents, so no two of them can differ.
- **REQ-SESSION-096** — A run carried out with no view attached — a background run (REQ-SESSION-106), a run of internal machinery (REQ-SESSION-020), or a board-launched run whose window was never opened (REQ-SESSION-158) — MUST surface nothing of its own beyond its event stream and the files under its session directory, and on success MUST leave an ordinary on-disk session that any fresh reader can load with status `completed`.

### 13. Background Runs and Their Desktop Surface

- **REQ-SESSION-097** — *Withdrawn.* There is no command-line surface; the capabilities its subcommands carried are reachable from the desktop, this domain's share of them through REQ-SESSION-182 (session management), REQ-SESSION-184 (starting runs), REQ-SESSION-188 and REQ-SESSION-189 (event history, replay and export), with checkpoints belonging to domain 06, requirement execution to domain 08, and sign-in, setup and provider removal to domains 04 and 15.
- **REQ-SESSION-098** — *Withdrawn.* Command flags have no surface to appear on; the run options a user chooses are collected by REQ-SESSION-184 and REQ-SHELL-125, and the worktree storage and branch-name defaults are fixed by REQ-GIT-005 and REQ-GIT-007.
- **REQ-SESSION-099** — *Withdrawn.* There is no standard-output stream to hand over; obtaining the stored event lines byte-for-byte is carried by the export of REQ-SESSION-189.
- **REQ-SESSION-100** — *Withdrawn.* The refused combination is unreachable: worktree choices are offered only where a task is being started (REQ-SESSION-184), so no taskless invocation carrying them exists.
- **REQ-SESSION-101** — *Withdrawn.* Refusing a launch that names neither a task nor a session to resume is carried by REQ-SESSION-184; configuration-error reporting belongs to domain 15.
- **REQ-SESSION-102** — *Withdrawn.* Making the session addressable the moment it exists is carried by REQ-SESSION-185.
- **REQ-SESSION-103** — *Withdrawn.* Presenting the run outcome from the one shared derivation is carried by REQ-SESSION-186; there are no exit codes (REQ-SESSION-187).
- **REQ-SESSION-104** — *Withdrawn.* The two-stage stop — graceful first, forced on a second request — is carried by REQ-SESSION-186.
- **REQ-SESSION-105** — *Withdrawn.* Listing sessions, marking stale ones, and repairing them are carried by REQ-SESSION-182.
- **REQ-SESSION-106** — A background run (REQ-SESSION-184, REQ-SESSION-190) MUST carry on unattended with no view attached to it. With every window that was watching it closed, the following MUST all still be observable from the session directory: `updated_at` keeps advancing, new transcript rows keep appearing in `state/ui_transcript.json`, `evidence/events.jsonl` keeps growing, artifacts keep being produced under `artifacts/`, and the run reaches a terminal `execution_status` on its own. A later reattach MUST remain possible: the session is located by workspace plus session id, its persisted state is read back, and a view is bound to that state (REQ-SESSION-196). A background run that outlives the application process itself does not exist: quitting the application ends its runs through the ordinary cancellation and teardown path (REQ-SESSION-092, REQ-SESSION-094), so no run is ever left holding a lock that this machine cannot reclaim.
- **REQ-SESSION-184** — Starting a run MUST be a desktop action, offered wherever a task can be started and collecting, in one place: the task text; whether to resume an existing session or create a new one; Git worktree isolation and its branch name, or an existing worktree to attach; the persona; and the maximum iteration count. The workspace is the one the window has open (REQ-SESSION-001) and is never asked for separately. The dialog that collects worktree isolation and sandbox mode is REQ-SHELL-125, and its branch-name rules are REQ-GIT-007, REQ-GIT-009 and REQ-GIT-010. A launch that names neither a task nor a session to resume MUST be refused before any session directory or lock is created, with a message conveying that a task is required, and MUST leave nothing behind. A run MUST be startable directly into the background — reaching the state of REQ-SESSION-106 without ever having a view attached — and MUST be startable in the foreground and detached afterwards (REQ-SESSION-190); the two produce sessions that differ in nothing but which windows were watching.
- **REQ-SESSION-185** — The session id MUST become visible to the user the moment the session exists — on the `session.start` event, before any work has happened — together with whether the session was created or resumed, so a long-running run is addressable from another window immediately. The created/resumed distinction MUST follow whether the *request* carried an existing session id, so a pre-named new session (REQ-SESSION-011) still reads as created. A run that never starts (validation, lock, or worktree failure) MUST show no session id, because none exists. Wording and placement are left to the implementation.
- **REQ-SESSION-186** — The interface MUST present the terminal outcome of a run and MUST offer a stop control while one is in progress. Both derive from the shared run result of REQ-SESSION-177: the outcome shown is the outcome of REQ-SESSION-187 together with the summary text of REQ-SESSION-074, presented exactly once per run, at the severity that summarization assigned, and an error result is presented as an error carrying its diagnostic text. The stop control's first activation requests the graceful stop of REQ-SESSION-092; a second activation while that stop is still pending forces cancellation, and the control MUST say which of the two the next activation will do. A run stopped gracefully and cleanly by the user persists `stopped`; one that had to be forced, or that was cancelled, persists `paused` (REQ-SESSION-093).
- **REQ-SESSION-190** — Sending a run to the background MUST genuinely detach it: the view stops following the run, the run itself continues in the same process holding the same session lock, and `execution_status` is persisted as `background` at the moment of the hand-off. The action MUST be refused, with a message conveying that there is no run to send, when no run is in progress. A backgrounded run MUST remain observable per REQ-SESSION-106 and re-attachable per REQ-SESSION-196, and MUST reach a terminal status on its own. Because `background` is an active status, a backgrounded run whose process dies reads as stale and is repairable to `interrupted` (REQ-SESSION-057, REQ-SESSION-182).

### 14. Message-Limit Pause and Reattach

- **REQ-SESSION-107** — When a run reaches its message limit, it MUST: create the durable signal file `<session_dir>/.message_limit_paused`; record the message count and limit on the state; set `execution_status = "paused_message_limit"`; and persist immediately (a status change flushes synchronously). It then remains paused until a user reattaches; there is no automatic continuation.
- **REQ-SESSION-108** — The pause MUST take effect at the outer-loop iteration boundary (after an iteration returns, before the next is chosen), so that while paused no agent is part-way through execution and no model request is outstanding.
- **REQ-SESSION-109** — On reattach, if the loaded session's status is `paused_message_limit`, the application MUST immediately present a modal confirmation without requiring the user to navigate to it. It MUST convey the message count reached, the limit that was reached, and the run's input and output token usage as separately identifiable figures. It MUST offer exactly three actions — continue, double the limit, and cancel the run — with continue as the default action bound to Enter and cancel bound to Escape. An entry for continuing a paused session MUST exist in the action vocabulary of REQ-SHELL-048 and MUST be active only in this state. Wording and the remaining key bindings are left to the implementation.
- **REQ-SESSION-110** — Resolving the prompt: "double" doubles the persisted message limit; "cancel" sets status `paused`; "continue" sets status `idle`. In every resolved case the `.message_limit_paused` signal file MUST be removed (missing is fine) and the session saved. A session paused at the limit whose persisted limit is null cannot resume the prompt: its status is set to `paused` and a warning notification conveys that the paused session carries no message limit to resume from. The wording is left to the implementation.
- **REQ-SESSION-111** — The message count and the (possibly doubled) limit MUST be durable across crash and restart via the ordinary snapshot, so the user is never re-prompted for messages already counted. A resumed run MUST seed its counters from the persisted values, falling back to the configured limit (which is then written back to the state when it was null).

### 15. Resume and Continue Semantics

- **REQ-SESSION-112** — To continue a session is to reopen one already saved beneath `<base_workspace>/.rotaris/sessions/` for the same workspace. Everything the session recorded MUST come back: its transcript rows, its stored child-agent state history, its stored tool-event history, its report artifacts, and its configuration snapshot. The test is field-level equality: a state that is saved and then reloaded MUST compare equal on every key of the resumable-state inventory in Data & Formats (REQ-SESSION-027), and that equality MUST still hold after a release-lock, re-acquire, mutate, save and reload cycle.
- **REQ-SESSION-113** — A resumed session keeps its identity wholesale: its worktree binding (worktree options refused on resume), its requirement attribution (request-supplied attribution ignored), its run type (stamped only at creation), and its configuration snapshot; the run executes inside the stored worktree.
- **REQ-SESSION-114** — Intent carry-over on resume: the intent classifier MUST be given the *previous* run's recorded intent (read before it is overwritten). A continuation prompt that classifies as ambiguous (e.g. the user types "continue") inherits the prior intent, and the transcript's status row reads `Intent classified: <intent> (continued from previous run)`; a genuinely new request keeps its own classification.
- **REQ-SESSION-115** — When a new top-level task enters an existing session, the payload handed to the run MUST prepend a fixed continuation preamble (stating that this is a follow-up within an existing session and that prior session context is authoritative), then a `Latest user request:` block, an `Authoritative session handoff:` block (artifact, todo, and progress context), and a `Recent session context:` block. Budgets MUST be exactly: the last 6 transcript events whose role is `user` or `agent` and whose content is not blank, at most 700 characters taken from each such event, at most 3200 characters of history in total, at most 20 todo tasks followed by the literal marker `- [... additional todo tasks elided]` whenever any task was dropped, the last 5 outer-loop iterations, at most 700 characters per structured item, at most 6000 characters for the latest orchestrator artifact against an 8000-character artifact baseline, and task display titles cut to 80 characters with a `...` suffix.
- **REQ-SESSION-116** — The transcript row for the user's new prompt MUST be recorded and persisted before intent classification begins, and every save of the active resumed run flows through the same debounced path as a fresh run.
- **REQ-SESSION-117** — *Withdrawn.* The resume affordances were terminal-UI surfaces; choosing a saved session is carried by the session browser of REQ-SHELL-126 over the session list of REQ-SESSION-182, reached from the action vocabulary of REQ-SHELL-048.
- **REQ-SESSION-118** — Loading a session chosen in the session browser MUST report a failure to the user rather than leaving the choice silently ineffective, distinguishing three cases and conveying the session id in each: no session under that id; a session whose stored state cannot be parsed, carrying the parse detail; and any other failure, carrying its detail. On success the session-scoped model override is restored, the composer's model label updated, the message-limit prompt shown when applicable (REQ-SESSION-109), and the user told which session was loaded. Wording is left to the implementation.
- **REQ-SESSION-119** — *Withdrawn.* The hand-off that persisted `background` without detaching anything was a terminal-UI limitation; a real background hand-off is carried by REQ-SESSION-190.

### 16. Transcript Recording and Persistence

- **REQ-SESSION-120** — The persisted transcript MUST be derived from the run's own conversation events and from nothing a view renders. Two consequences MUST be observable: a run with no view attached persists the same transcript rows it would have persisted with one, so a background session can be reopened with a full transcript; and one recorded conversation yields byte-identical rows whichever view was watching it, so no two views can leave different transcripts of the same run.
- **REQ-SESSION-121** — Persisted transcript rows MUST use the role/shape vocabulary given in Data & Formats, and every row MUST be stamped with `ts` in local wall-clock `HH:MM:SS` form when appended.
- **REQ-SESSION-122** — Persisted-size caps MUST be: 400 characters for a tool row's `detail`, 2000 characters for its `full_text`, and 4000 characters for thinking content. Content longer than its cap is stored cut to the cap, while a streamed thinking row's `chars` counter MUST keep counting past 4000 so that token estimation remains correct. Terminal (shell) tool output MUST keep its line structure in `full_detail` — the field a reopened session renders — while `detail` holds a single line of at most 400 characters. `full_detail` MUST itself be capped at 8000 characters, because every state save rewrites the whole transcript file; when it is cut, the newest output is kept and the cut is made at a line boundary where one falls inside the cap. Every cut in this requirement is marked per REQ-SESSION-194.
- **REQ-SESSION-123** — Each row MUST be published on the wire as a `transcript.row` event (index plus a copy of the row) once on append and once more when the row reaches its final form — intentionally not on every streamed token, so a remote viewer receives the opening token and then the completed text. Publish failures are logged and never raised into the run.
- **REQ-SESSION-124** — Resuming a conversation can replay events; stable per-event identities (per-agent call ids for tool calls, per-agent event ids for committed messages) MUST prevent duplicate rows and double-counted metrics.
- **REQ-SESSION-125** — Reasoning delivered twice — streamed as deltas and then repeated in full alongside the action — MUST end up as exactly one persisted thinking row holding the final full text, with one start timestamp and one settled duration; a second row, whose elapsed-time counter would never stop, MUST NOT appear. Reasoning that was never streamed arrives in one piece and is persisted with no start timestamp, and therefore shows no timer. Where an older version already recorded a burst twice — consecutive thinking rows of the same agent, the content of one being a prefix of the other's — display MUST show only the longer row.
- **REQ-SESSION-126** — A terminal tool row MUST carry a stream identifier of the form `fg:<agent_name>` so that a UI rejoining the session can locate the live terminal buffer the row belongs to.
- **REQ-SESSION-127** — Structured edit diffs MUST live outside the transcript that is fed to the model, keyed `<agent>:<tool_event_key>` and replaced in place on redelivery; at display time each diff is merged beside exactly one tool row.
- **REQ-SESSION-128** — Tool-call metrics MUST be counted into the per-agent and global aggregates at call start, once per stable call id, and each child's live tool set MUST be mirrored onto its persisted child-state record so a snapshot shows what each child is running.
- **REQ-SESSION-129** — Three end-of-activity guarantees MUST hold. When a child agent dies while a tool call is open, that child's persisted record MUST be left with an empty active-tool list and no transcript row of its own left at status `running`; every such row MUST be persisted at status `failed`, keeping whatever output it had already recorded. The tool-row status vocabulary is REQ-MONITOR-105, in which `blocked` denotes a call refused or skipped before it ran and there is no `cancelled` value — a call that was under way and produced no result is a failure, whatever became of the agent that made it, while the child's own record still moves to `cancelled` under REQ-SESSION-065. A verifier check that finishes without ever having been announced — denied by permissions, or out of budget — MUST still produce a verifier row, with the outcome mapping of Data & Formats (passed → `ok`, failed or timeout → `failed`, skipped → `blocked`). A completed question-tool result MUST remove the matching entries from `pending_questions`, which in turn clears `awaiting_input` once no approvals remain (REQ-SESSION-031).
- **REQ-SESSION-130** — At run end, if the conversation left no agent rows (for example when a child agent's summarized report is the entire answer), one agent row per iteration outcome MUST be appended from the progress record so the transcript still shows an answer — but never duplicated on top of real conversation rows.
- **REQ-SESSION-131** — The transcript archive MUST append evicted (older) transcript events one JSON object per line to `<session_dir>/state/transcript_archive.jsonl`, paged in fixed chunks of 50 events, append-only: an archived page is never rewritten, reordered, or trimmed, and a row's index in the whole transcript is preserved by the order of the file. Eviction is driven by REQ-SESSION-192 and is not optional for any caller.
- **REQ-SESSION-192** — The live transcript file `state/ui_transcript.json` MUST be bounded, because every state save rewrites it whole: it MUST hold at most the 5000 most recent rows. When an append would exceed that, the oldest rows MUST be evicted to `state/transcript_archive.jsonl` (REQ-SESSION-131) in whole pages of 50 before the file is written, so a session that runs indefinitely has a bounded save cost and an unbounded, complete history. Eviction MUST NOT change the index any surviving or archived row was given (REQ-SESSION-160), and a reader that asks for a row older than the live window MUST be served it from the archive. Nothing else caps the transcript: row count and the per-row caps of REQ-SESSION-122 are the whole bound, and there is no byte limit on the file.
- **REQ-SESSION-194** — One rule governs every character cap in this domain: whenever stored text is cut to fit a cap it MUST be marked as cut, by appending the marker `...` (three ASCII full stops) and counting that marker inside the cap, so a stored value never exceeds its cap and a reader can always tell a complete value from a shortened one. This applies to `detail`, `full_text`, `full_detail` and thinking content (REQ-SESSION-122), to every per-event, per-item and per-artifact budget of the continuation payload (REQ-SESSION-115), to the task line of `summary.md` (REQ-SESSION-140), to the truncated arguments and results of an error-path tool record (REQ-SESSION-136), and to the compact payload rendering of a replayed event (REQ-SESSION-188). Two exceptions are deliberate: an elided todo list is marked instead by the literal line `- [... additional todo tasks elided]` (REQ-SESSION-115), because what is elided is list entries rather than the end of a string; and a streamed thinking row's `chars` counter keeps counting past the cap (REQ-SESSION-122), because it measures what the model produced and not what was stored. Counts, identifiers, paths and timestamps are never truncated.

### 17. Diagnostics and Evidence Files

- **REQ-SESSION-132** — Diagnostics initialization MUST create, and only when the name is absent: `issues.json` (as `{"issues": []}`), `metrics.json`, `summary.md`, an empty `timeline.jsonl`, `evidence/tool-calls.jsonl`, empty `evidence/model-input.jsonl`, `evidence/context-selection.jsonl`, `evidence/report-validation.jsonl`, `evidence/memory.jsonl`, `evidence/permissions.jsonl`, and `evidence/conversations/index.json` (as `{"conversations": []}`). It MUST NOT create `state/run_config.json`: that file is the launch audit, written exactly once by run startup (REQ-SESSION-138), and an empty placeholder created here would block the audit from ever being recorded. Initialization runs on every state save, so a session's full inspectable shape exists from its first save onward, before any of these files has content.
- **REQ-SESSION-133** — Retention caps (ring-buffer semantics, newest kept) MUST be: issues 500, tool calls 5000, model inputs 5000, context selections 2000, permission decisions 5000, report validations 2000, memory snapshots 2000. A capped append rewrites the file atomically keeping only the newest entries; uncapped files append one line. Appends within one process are serialized.
- **REQ-SESSION-134** — Timeline entries (one JSON object per `timeline.jsonl` line) MUST have the shape `{id: 12 hex chars, timestamp: UTC ISO, type, severity: debug|info|warning|error (default info), actor, message, metadata}`. Ordering contract: the durable line is written before any wire event derived from it, so a failing stream may drop an event while the on-disk record it came from is still retained. Exactly three timeline entry types are bridged to wire events (`completion_gate_decision` → `gate.decision`; `repair_attempt_scheduled` and `repair_escalation` → `gate.repair`, mutually exclusive per decision), and no other timeline type produces an event through this bridge — the `error` event of REQ-SESSION-135 is published by issue recording, not by the timeline. Metadata from which no valid event can be constructed is logged and discarded without failing the iteration.
- **REQ-SESSION-135** — Issue records (in `issues.json`) MUST have the shape `{id: 12 hex chars, timestamp, kind, severity, actor, message, evidence_ref, metadata}`. Every recorded issue also writes a timeline entry of type `issue`; only error-severity issues additionally publish an `error` wire event with `fatal=false` (recording an issue never by itself terminates a run); warning- and info-severity issues publish nothing, so an automated consumer does not read a healthy run as failing.
- **REQ-SESSION-136** — Tool-call records (`evidence/tool-calls.jsonl`) MUST carry `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` plus `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings` only when applicable. Each record also streams a `tool.start`/`tool.finish` event pair; the on-disk record keeps its historical unredacted-arguments shape while the streamed arguments are redacted by the event schema. Outcome-driven automatic issues MUST be filed: shell failure → kind `terminal_shell_failure` (error); suspicious success → `terminal_suspicious_success` (warning); timeout → `terminal_timeout` (error); any other failure → `tool_error` (warning); each referencing `evidence/tool-calls.jsonl`. On error, recorded args/result are truncated to 2000 characters.
- **REQ-SESSION-137** — The permission audit (`evidence/permissions.jsonl`) MUST record decisions as `{timestamp, session_id, agent_id, persona, tool_name, decision, rule_id, source, summary (pre-redacted), reason, request_id?}`. A deny files a `permission_denied` warning issue; a one-time or session-scoped user approval files a `permission_approved` timeline entry. Mid-session mode changes share the file as `{event: "permission_mode_change", requested_mode, effective_mode, previous_mode, source, reason, skipped_personas}` — `skipped_personas` recorded even when empty so silence is unambiguous — and are counted separately in metrics.
- **REQ-SESSION-138** — `state/run_config.json` MUST be written exactly once per session, by run startup (REQ-SESSION-087), at the first moment the configuration the run will actually execute with is settled — after the worktree has been bound (REQ-SESSION-085) and the sandbox verdict taken (REQ-SESSION-086), and before the first iteration. No later configuration change may alter it, and a run that resumes the session MUST NOT rewrite it, so the audit always describes the launch that created the session. It MUST contain `{session_id, workspace_root, created_at, run_intent, permission_mode, check_suite, resolved_playbooks (per persona for the run's intent), hooks (id/name/event/matcher/source with secret-redacted command text), config_snapshot}`, with each persona's system-prompt file resolved into inline `resolved_system_prompt` text.
- **REQ-SESSION-139** — `metrics.json` MUST be rebuilt from the state plus the evidence files on every save and MUST report: session id, status and updated-at; global tool-call, token, cost and compression aggregates; per-agent metrics; the number of tool-call records; a tool-outcomes histogram classifying every recorded call (`outcome_kind` when the record carries one, otherwise derived from `status` and `is_error` into rejected, tool-error, success or unknown) whose bucket totals MUST sum to the tool-call record count; terminal shell-failure, suspicious-success and timeout counts; the 10 slowest tool calls ordered by recorded `elapsed_ms` descending; model-input record and stale-drop counts; context-selection totals; report-validation record and downgrade counts; permission decision, denial, source and mode-change counts; and issue counts in total and by kind. All counts are taken over the records the evidence files still hold after the retention caps of REQ-SESSION-133 have been applied, so a capped file's counts describe what is on disk rather than what the run once produced.
- **REQ-SESSION-140** — `summary.md` MUST contain, in this order: a `# Session <id>` heading; one line each for status, workspace, created and updated; `- Task: <first user event, cut to 240 characters>`; `- Stop reason: <reason>` when a stop reason is recorded, the line being omitted entirely when none is; a Metrics section in which a value that is unavailable renders as `n/a` or `—` and never as `0`; a Warnings section covering stale-input drops, mostly-elided artifacts, report downgrades, permission denials (naming `evidence/permissions.jsonl`), tool errors, and terminal failures, suspicious successes and timeouts; an Agents section; a Slowest Tools section listing the top 5 by recorded `elapsed_ms`; and a closing inspection note naming `issues.json` first, then `timeline.jsonl`, then `evidence/debug.log`.
- **REQ-SESSION-141** — The conversation index (`evidence/conversations/index.json`) MUST hold entries `{conversation_id, agent_name, persona, model, task_id, started_at, ended_at (set when status leaves "running"), status, event_count, path}` where path points at the conversation's event-log directory. Conversation directories are named with 32-character un-hyphenated hexadecimal ids; lookups MUST accept both hyphenated and un-hyphenated forms (direct match, stripped variant, then a directory scan), counting the `*.json` files under `events/`.
- **REQ-SESSION-142** — Per-session debug logging MUST write to `evidence/debug.log` at the configured session log level (default WARNING; the strings DEBUG/INFO/WARNING/ERROR and integer levels accepted; an unknown string falls back to WARNING and logs a warning), and MUST restore prior logging state at run end.
- **REQ-SESSION-191** — For any session it lists, the application MUST offer an action that opens that session's log `evidence/debug.log` for reading and an action that reveals the session directory itself in the platform's file manager, so the log, the timeline, the issues file, the metrics document and the evidence files stay reachable without a shell. Both actions MUST be available whether or not the session is live, MUST write nothing to the session directory, and MUST report the situation rather than appearing to succeed when the file or the directory is missing. Both belong to the action vocabulary of REQ-SHELL-048.

### 18. Durable Per-Session Event History

- **REQ-SESSION-143** — The event history lives at `<session_dir>/evidence/events.jsonl`, holding one serialized wire event per line, ordered as emitted. Each stored line MUST reproduce, byte for byte, what the live stream emitted for that event, so that replaying from disk and subscribing to a running session are interchangeable inputs to one consumer. The truncation sidecar is `evidence/events.meta.json`.
- **REQ-SESSION-144** — The default event cap MUST be 20,000 events, with trim slack of cap ÷ 8. Were there no slack, each event added once the cap is reached would force a full-file rewrite; the slack amortizes that down to about one full rewrite for every cap ÷ 8 events appended. A cap below 8 has no slack and is enforced exactly. A trim keeps the newest cap-many lines, rewrites atomically, recounts from the file afterwards (honest even if something else appended), updates counters only after a successful rewrite, and records `{truncated: true, dropped_events (cumulative across runs), max_events, last_trimmed_at}` in the sidecar. A null cap disables trimming (tooling only); a non-positive cap MUST be rejected as invalid (a configured 0 asks for an empty history, not an unlimited one, and MUST NOT be reinterpreted).
- **REQ-SESSION-145** — The history writer MUST never fail a run: each entry point turns exceptions into logged warnings and signals the outcome through its return value; an event that cannot be serialized is discarded with a warning; a line containing an embedded newline or carriage return is refused (one event = one line); appends MUST NOT allow platform text-mode newline translation to mix line endings with the atomic-rewrite path.
- **REQ-SESSION-146** — Event-history bindings are per session id: a new registration replaces the previous one, lookup never falls through to a different session — history from one run must never be written into another run's file — and storing without a binding is a silent no-op.
- **REQ-SESSION-147** — Persistence MUST happen before forwarding to the caller's event consumer (a tee), so an event that a failing consumer never receives is nevertheless recorded on disk. Detaching the history genuinely stops persistence even for a sink reference that escaped.
- **REQ-SESSION-148** — Reading MUST be streaming (never whole-file), read-only, and forward-compatible: a line whose event-type discriminator is unknown yields an opaque event marked unknown with its raw payload intact — never dropped, never raising (strict decoding is an explicit opt-in). A trailing line left truncated or corrupt by a killed run MUST be skipped with a warning carrying `{line_number, reason, excerpt (at most 200 chars)}`, and the file MUST NOT be rewritten or repaired. A missing history reads as an empty session. A line with no event-type discriminator is malformed (skipped), not "unknown". Which types count as known MUST follow the event schema itself, never a separately maintained list.
- **REQ-SESSION-149** — Tail reads (for live following) MUST return events together with a byte offset that always lands immediately after a fully written line, plus a restart flag. Nothing new → empty events, same offset. A partial trailing line means a live run mid-write: complete lines before it are returned, no warning, and the partial line is read again once whole. The restart flag MUST be true when the file is shorter than the offset or the byte before the offset is not a newline (the cap trimmed the head, or the file was replaced); the caller must then discard derived state. A replacement file of identical length whose offset boundary also falls on a newline is undetectable by this test; the never-reused-id invariant (REQ-SESSION-012) is what rules that case out. Lines that cannot be decoded as UTF-8 are warned about and skipped, with warning line numbers counted from the start of the read. The restart test MUST be evaluated for the whole of a read before any event from that read is handed to a consumer, so no row can be derived from bytes the same read could already tell were misaligned. Rows derived from an *earlier* read that a later read's restart flag invalidates are discarded when the consumer re-seeds (REQ-SESSION-160); having briefly shown them is accepted rather than defended against, because the only alternative — withholding every event until a subsequent read confirms alignment — would delay live following by a whole read interval for a case that arises only when the cap trims the head of a history a follower is watching.
- **REQ-SESSION-150** — Replay filtering MUST support event types, iterations, and inclusive since/until time bounds — all optional, combined with AND; timezone-naive stamps normalize to UTC; an empty result is a valid answer. As the stream is read, each event's owning iteration is determined from the enclosing `iteration.start` and `iteration.end` boundaries; events outside every iteration match no iteration filter, and stamp-less lines match no time filter. Replay is reading, never re-execution, and never modifies the history.
- **REQ-SESSION-151** — Stored-session discovery MUST: treat an *empty* history as present (a run that emitted no events is still a session one can ask about); summarize by counting lines and decoding only the first and last (on a damaged history the count may be off by one, which is acceptable for a chooser; exact figures come from export); report an unreadable history as containing zero events, with a warning, instead of aborting the listing; sort newest first by last-then-first timestamp with the session id as tiebreak, sorting histories with no usable timestamps last. A session id that did not come from the session store itself — one typed by a user, pasted in, or read out of a document — MUST be treated as untrusted: it is resolved and required to land inside the sessions root (path traversal and absolute-path escapes blocked), else no match.
- **REQ-SESSION-152** — *Withdrawn.* The `events` command has no surface to appear on; browsing and replaying a stored history is carried by REQ-SESSION-188 and exporting one by REQ-SESSION-189.
- **REQ-SESSION-153** — An exported trajectory document MUST carry `trajectory_version: 1`; the run's identity (session id, task, and the workspace exactly as the run reported it — never a path belonging to the exporting machine); the permission mode; started and ended timestamps as ISO-8601 UTC; the status; the stop reason; the duration in seconds; `truncated` and `dropped_events`, taken from `evidence/events.meta.json` and reading as `false` and `0` when that sidecar is absent (REQ-SESSION-144); a summary recomputed from the exported events alone and from no other source — event, unknown-event and warning counts; `runs`, the number of `session.start` boundaries in the document, which is where a single-run consumer must split it; iterations; tool calls and tool failures; permission decisions and denials; verifier runs and failures; child agents; errors and fatal errors; per-type event counts; tokens; cost — and the events themselves as the raw stored payloads, with redaction inherited from the wire schema rather than applied again by the exporter, and unknown event types preserved intact.
- **REQ-SESSION-188** — The application MUST let a user inspect a stored event history without leaving it. For the workspace's sessions it MUST show, per session with a stored history, the session id, the event count, the first and last event timestamps, and, for a capped history, that events were dropped and how many (REQ-SESSION-144); a session whose history is empty is still listed (REQ-SESSION-151), a history that cannot be read is listed as holding zero events with a warning, and a workspace with no stored history states that rather than showing an empty area with no explanation. Opening one MUST replay it read-only (REQ-SESSION-150) with filters on event type, iteration, and inclusive since/until bounds, combined with AND, each optional, an empty result being a valid answer that MUST be stated as such. Each replayed event MUST show its timestamp, its type, whether the type was unknown to this version, and a compact rendering of its payload cut to 110 characters per REQ-SESSION-194; the raw stored line MUST be viewable for any event. Warnings about skipped or undecodable lines MUST be shown alongside the events, never in place of them. A time bound the user enters that is not ISO-8601 MUST be refused before the read, with a message conveying which bound and what was entered; wording is left to the implementation. Replay is reading and MUST never modify the history.
- **REQ-SESSION-189** — The application MUST let a user export one or several sessions as trajectory documents (REQ-SESSION-153). The destination MUST be a file the user chooses through the platform's save dialog — there is no implicit destination and nothing is written until a destination is chosen. Exporting exactly one session MUST write one trajectory document. Exporting several MUST write one JSON document of the form `{"trajectory_version": 1, "sessions": [<document>, ...]}` with the documents in the order the user selected them; these two key names are a machine-readable contract, and the batch wrapper carries no fields of its own beyond them, so a consumer that understands one document understands a batch. Two conditions MUST be reported as warnings that do not stop the export: a history holding more than one `session.start` boundary, conveying that the session was resumed, how many runs the document covers, and that its identity is the most recent one; and a capped history, conveying how many events were dropped and that the export is therefore not the complete run. The exported document MUST also be obtainable as the raw stored lines, byte-identical to `evidence/events.jsonl` (REQ-SESSION-143), for a consumer that wants the stream rather than the summary.
- **REQ-SESSION-193** — The key names of the three machine-readable documents this domain publishes are fixed, because a consumer cannot be written against a list of figures. Every key is lower snake case, and the inventory given for each document is exhaustive — a reader may rely on no other key being present, and adding one is a change to that requirement. The `session.start` payload (REQ-SESSION-090) carries `session_id` (string), `task` (string), `workspace_root` (string path, as the run reports it), `persona` (string), `permission_mode` (string, as configured at launch), `sandbox` (object `{"enabled": boolean, "backend": string}` describing the verdict in force), and `max_iterations` (integer or null). `metrics.json` (REQ-SESSION-139) and the trajectory document (REQ-SESSION-153) name each figure listed in their requirement by the same words that requirement uses, joined by underscores, with the trajectory document's top level being exactly `trajectory_version`, `session_id`, `task`, `workspace`, `permission_mode`, `started_at`, `ended_at`, `status`, `stop_reason`, `duration_seconds`, `truncated`, `dropped_events`, `summary`, and `events`. Key order is not significant anywhere.

### 19. Reattach Surfaces and Projections

- **REQ-SESSION-154** — The desktop session list MUST project listing metadata into rows: label = task title, else the launcher-known name, else the session id (a just-launched run keeps its prompt-derived label until metadata carries a title, and a refresh must not strip launcher-known requirement attribution); status from `execution_status` defaulting to idle; branch from the metadata worktree record, else "—"; a relative-time duration label; the worktree path as detail; and `awaiting_input` from metadata (absent → false). The status MUST be rendered from the stored value itself, as text and never by colour alone (REQ-SHELL-149), so every value of REQ-SESSION-073 is distinguishable from every other: a session repaired to `interrupted` reads as interrupted and is never shown as though it had never run, and a value from outside the closed vocabulary is shown verbatim. A stale session (REQ-SESSION-057) MUST additionally carry the stale marking of REQ-SESSION-182 beside that status.
- **REQ-SESSION-155** — `awaiting_input` MUST render as a "waiting for you" tag on session rows and "Waiting for your answer" status text, and MUST drive the requirement board's "Answer" affordance for background runs blocked on approvals or questions — persisted metadata is what lets a background run say it is blocked on a person across every surface and across restarts.
- **REQ-SESSION-156** — Desktop whole-state reads MUST use the read-only snapshot read of REQ-SESSION-040 — no repairs and no writes, verifiable by fingerprinting the session directory before and after the read — and MUST project the persisted state into display models covering the run summary, transcript, agents, artifacts, todos, key metrics, pending questions and approvals (copied, so that display work can never mutate what was read), and the verifier summary. A `verifier_state` that cannot be parsed MUST resolve to idle rather than failing the read, and a persisted `gate_warning` MUST still be reported when the verifier is idle. The result MUST report the elapsed time of the state read and the elapsed time of the projection as separate values. Which parts of a view a user is entitled to see restored from this projection, rather than recomputed or lost, are fixed by REQ-SESSION-196.
- **REQ-SESSION-157** — Pending questions and approvals MUST render as transcript trailer rows — derived from what is pending now and always placed after every recorded row, re-appended by both whole-state and delta paths: a question stepper row of the form `<N> step(s) — <first title>` and one row per approval of the form `Approval needed — <command or tool>`.
- **REQ-SESSION-158** — A desktop board-launched run (a requirement unit) MUST: adopt the worktree the flow provisioned, given by explicit path, refusing a path that is not part of the repository, and record it as not owned by the session so the session never deletes a tree the flow owns (REQ-SESSION-084); make the session id available to the caller as soon as the session exists, without waiting for the run to end; open no window and take no window or keyboard focus, so that several launches in succession leave the user's foreground application unchanged; return an empty session id rather than raising when the launch is refused; and have the caller's completion listener registered before the launch call returns, so that a run finishing immediately still delivers its completion notification. The empty session id is the return value only and is never the whole report: a refused launch MUST also be reported to the user through the notification surface of domain 19, conveying which requirement unit could not be started and why, and the unit's row on the requirement board MUST show it as not started with that reason attached — a refusal that produced no session must never be indistinguishable from a unit nobody has run yet.
- **REQ-SESSION-182** — The application MUST offer one place from which the workspace's sessions are managed, built on the listing of REQ-SESSION-042 and the metadata of REQ-SESSION-030 and reached through the session browser of REQ-SHELL-126. It MUST show, per non-internal session, the row projection of REQ-SESSION-154, and MUST mark a stale session (REQ-SESSION-057) as stale beside its stored status, as text and not by colour alone (REQ-SHELL-149), so the cause of a refused restore or a blocked integration is visible where the session is. It MUST offer these actions, all in the action vocabulary of REQ-SHELL-048: open the session (REQ-SESSION-118); repair one stale session; repair every stale session in the workspace; delete a session (REQ-SESSION-166), behind a confirmation that states the deletion is permanent; and the log and directory actions of REQ-SESSION-191. Repair MUST perform exactly the explicit repair of REQ-SESSION-060 and MUST report, per session repaired, the session id, the status it was stuck in, the new status `interrupted`, and the reason it counted as stale (REQ-SESSION-059); when nothing was stale it MUST say so rather than reporting nothing at all. A session whose stored state cannot be parsed MUST be listed and reported as unreadable (REQ-SESSION-041) while every other session stays usable. Wording throughout is left to the implementation.
- **REQ-SESSION-196** — Reattaching to a session — one that has been running in the background, one whose window was closed, or one being opened again after a restart — MUST restore from persisted state, and not recompute or discard, all of: every transcript row the session recorded, at its own index and in order, with statuses settled per REQ-SESSION-078 and REQ-SESSION-079 and archived pages reachable per REQ-SESSION-192; the todo state; the child-agent tree; the metric aggregates (REQ-SESSION-169); the report artifacts; the pending questions and approvals, as trailer rows per REQ-SESSION-157; the verifier summary and any `gate_warning`; the worktree binding and its branch; the checkpoint list; and the session-scoped model override. Four things are explicitly not restored, because they describe a moment rather than the session: streaming animation and partially streamed text, which come back as the settled rows they became; live terminal buffers, so a terminal tool row shows its recorded output rather than a live screen until a stream is re-attached (REQ-SHELL-110); elapsed-time counters for activity that is no longer running; and scroll position, unless a desktop preference (REQ-SHELL-006) says otherwise. Everything restored MUST come from the read-only snapshot read of REQ-SESSION-040 followed by the tail of REQ-SESSION-159, never from a second, differently derived path.

### 20. Following a Session That a Different Process Owns

- **REQ-SESSION-159** — When a session runs in a process other than the one displaying it — a second window of this application, another instance opened on the same workspace, or a run detached into the background — the only channel to it is the filesystem. Because state files are replaced wholesale on each save and carry no incremental read position, the live transcript MUST instead be followed by tailing `evidence/events.jsonl` and turning `transcript.row` events into the same transcript deltas that a locally executing run yields. Sharing one derivation guarantees that following a session and reopening it afterwards produce identical transcripts.
- **REQ-SESSION-160** — A follower reading the event history MUST reproduce the run's own row numbering. Each row appears at exactly the index the run gave it. A row arriving past the current end fills the indices skipped over with `{"role": "system", "content": "(this line was not recorded)"}`, so that every later row still sits at its own index. A row republished for an index already shown — a settling row arriving behind the tail — replaces that row instead of being appended after it. The first batch produced after seeding, and after any re-seed, starts at row 0. When the history reports a restart (REQ-SESSION-149) every derived row is discarded and the view re-seeds; the re-seeded rows MUST replace the displayed ones in a single step, so the view is never observed empty between the discard and the re-seed. Any error while tailing MUST be surfaced as a request to reconcile from a whole-state read, leaving the rows already shown in place rather than clearing or freezing the view.
- **REQ-SESSION-161** — Everything outside the transcript — todo lists, the agent tree, token counts — MUST come from whole-state reads, which also reconcile anything the tail did not deliver. A delta whose first-touched index falls before the oldest row the consumer still holds from its most recent whole-state read MUST be rejected; a rejection costs exactly one further whole-state read, and the rows on display MUST be unchanged by the delta that was rejected.

### 21. Checkpoints as Session Data

- **REQ-SESSION-162** — Per-iteration git checkpoints MUST persist in two places that stay consistent: refs under `refs/rotaris/checkpoints/` in the run's tree (the isolated worktree for isolated sessions, else the workspace), and the session's `checkpoints` list mapping iteration to ref and commit. Keeping the mapping in the session state is what allows checkpoints to survive a resume and to remain restorable after a crash.
- **REQ-SESSION-163** — `metadata.json`'s `checkpoint_count` MUST mirror the length of the state's checkpoint list (the session list reads metadata only); readers default an absent key to 0 for pre-checkpoint directories.
- **REQ-SESSION-164** — Checkpoint restore for a session that *claims* to be running MUST be refused, because the pre-restore checkpoint this operation records would contend with writes from the supposedly live run; the stale-repair flow exists precisely to make restore available again after a crash. The refusal MUST convey the session id, the status the session records, that nothing was restored and the working tree is unchanged, and — when the session is stale rather than live — that repairing it makes the restore available (REQ-SESSION-182). It MUST be presented as an error on the surface that asked for the restore (REQ-GIT-096); the wording is left to the implementation, and no numeric code is produced (REQ-SESSION-187).
- **REQ-SESSION-165** — *Withdrawn.* Listing and restoring checkpoints has no command surface; the capability is carried by the desktop checkpoint browser of domain 06 (REQ-GIT-096 and the gates of REQ-GIT-058), with this domain's refusal for a busy session staying in REQ-SESSION-164.
- **REQ-SESSION-195** — The session record MUST carry `last_restored_sequence`: the integer sequence of the checkpoint most recently restored into this session's tree, or null when no restore has ever succeeded for the session. It defaults to null, so a state written without it loads unchanged (REQ-SESSION-015), MUST be written as part of the same durable write that reports a restore successful, and MUST be left untouched by every refused and every failed restore. Its only use is to widen the drift candidate set of REQ-GIT-056 so that undoing a rollback never demands a force (REQ-GIT-155); it MUST NOT affect which checkpoints are listed, numbered, pruned, or restorable, and a value naming a checkpoint no longer recorded simply contributes no candidate.

### 22. Session Deletion

- **REQ-SESSION-166** — Deleting a session MUST first best-effort discard the session's checkpoint refs (loading the snapshot to locate the right tree — the worktree for an isolated session, else the workspace root), then remove the session directory ignoring errors. An unreadable session still deletes. Deleting a missing session is a no-op. A ref-cleanup failure logs a warning naming the leftover `refs/rotaris/checkpoints/` location; cleanup stays best-effort so a session still deletes when the repository moved or never existed. Refs MUST be pruned as well, because removing only the directory would leave them behind permanently.
- **REQ-SESSION-167** — The run lifecycle deletes a session in exactly one situation: a *just-created* session whose launch failed before the run started (worktree bind or sandbox failure). A resumed session MUST never be deleted by a failed launch.

### 23. Metrics Continuity Across Resume

- **REQ-SESSION-168** — On every persist, in-process metric aggregates MUST be copied into the state: global tokens, cost, tool calls, compressions, per-agent metrics, and sorted compression-dedup ids. The legacy token-usage field is set only when total tokens exceed 0, else null.
- **REQ-SESSION-169** — At run start and resume, in-process aggregates MUST be rebuilt from the persisted state with graceful fallbacks: a per-agent tool total without per-tool detail restores as a single pseudo-tool entry; zero global tokens falls back to the legacy token-usage field, then to merging per-agent snapshots; global cost, compressions, and tool-call counters are recomputed from agents the same way. Consequence: cumulative token, cost, and tool counters continue across resumes rather than resetting.

### 24. Reasoning-Content Repair at Open

- **REQ-SESSION-170** — The full session open of REQ-SESSION-040 — and only that path, never the read-only snapshot read — MUST run a best-effort repair before the session is handed back. The trigger MUST be a declared property of the model, read from the model-capability metadata the product ships with (REQ-PROVIDER-137), and never an observed failure, a hard-coded list of model identifiers, or a guess from a provider name; when the metadata does not declare the property for the session's default-persona model, the repair MUST NOT run, because rewriting stored conversation files on suspicion is worse than a request the provider might refuse. When that metadata declares that the session's default-persona model rejects requests in which an earlier assistant message carries no reasoning content, every persisted conversation event file under `evidence/conversations/event_logs/*/events/*.json` is examined, and action events whose reasoning content is null or missing, together with agent message events whose message carries no reasoning content, are rewritten atomically (REQ-SESSION-033) with an empty string in place of the missing content. The pass MUST run at most once per open, MUST record and log how many items it changed, and MUST NOT prevent the open from completing when it fails.

### 25. Cross-Cutting Invariants

- **REQ-SESSION-171** — For one pid at one moment, lock reaping, liveness reporting, stale detection and the worktree-integration precondition MUST all reach the same verdict: it MUST NOT be possible to observe one of them treating a process as alive while another treats the same process as gone.
- **REQ-SESSION-172** — Any uncertainty about whether a session is live resolves in favour of "still running"; detection performs no writes; repair is explicit, flushed at once, idempotent, and never raises.
- **REQ-SESSION-173** — The last *requested* save wins on disk, not the last write to finish; a terminal status is always durable before its save call returns; disk is never staler than the newest requested state.
- **REQ-SESSION-174** — Every run through the shared lifecycle persists its full event history regardless of streaming (supplying no event sink still persists the history; it only means nothing is streamed out), and the stored history is exactly the sequence the live stream saw (persist-before-forward tee).
- **REQ-SESSION-175** — History and diagnostics writing never fails a run: the event history, transcript publication, change callbacks, diagnostics writers, and the timeline-to-wire bridge all degrade to logged warnings.
- **REQ-SESSION-176** — Per-session bindings (event sink, event history, transcript recording, hook running, approval handling, audit) bind late by session id and are discarded at run teardown, so that no leftover binding can influence a later run in the same process, and an event arriving after teardown has no destination.
- **REQ-SESSION-177** — The terminal `result` event is delivered exactly once per run — through the event bus for runs that started, written directly to the sink only for runs that never attached anything — and the run outcome of REQ-SESSION-187, the `result` payload, and the human summary all read off one shared derivation.
- **REQ-SESSION-178** — A session list is limited to what `metadata.json` holds, so every list-visible attribute (title, status, staleness inputs, checkpoint count, requirement attribution, awaiting-input) is denormalized into metadata at save time, with reader-side defaults for older directories.
- **REQ-SESSION-179** — Data written by another version of this product is honored but never repaired in place: absent optional state keys load as their defaults (REQ-SESSION-015), absent metadata keys take their reader-side defaults (REQ-SESSION-030), an unparseable secondary state file degrades exactly as an absent one (REQ-SESSION-036), and a schema version newer than this one is refused rather than lossily restored (REQ-SESSION-038). There is no predecessor on-disk layout and no whole-state fallback file (REQ-SESSION-005, REQ-SESSION-037).
- **REQ-SESSION-180** — Displayed liveness is re-derived from the same snapshot that renders the header (agents settled against the execution status; running tool rows neutralized on non-live sessions), so that an internally inconsistent snapshot — from an earlier version or from a killed process — is never rendered as one.
- **REQ-SESSION-181** — The created/resumed announcement of REQ-SESSION-185 follows whether the *run request* carried an existing session id, not what the run internally did: a caller that pre-names a brand-new session (REQ-SESSION-011) still has that session announced as created.

## Data & Formats

All formats below are externally observable: they are files a user can open and wire events a consumer can subscribe to.

### Directory layout

```
<base_workspace>/.rotaris/          # the workspace the run was invoked against, never the worktree
  sessions/<session_id>/
    lock                          # {"pid": <int>, "host": "<machine id>", "acquired_at": "<UTC ISO>"} while owned
    metadata.json                 # derived listing surface (exact keys in REQ-SESSION-030)
    summary.md                    # derived human summary (REQ-SESSION-140)
    timeline.jsonl                # append-only timeline entries (REQ-SESSION-134)
    issues.json                   # {"issues": [...]}, ring-capped at 500
    metrics.json                  # derived metrics document (REQ-SESSION-139)
    .message_limit_paused         # optional durable pause signal (empty file)
    state/
      resume.json                 # resumable state minus bulk fields
      ui_transcript.json          # {"events": [...]}
      ui_edit_diffs.json          # {"diffs": [...]}
      run_config.json             # write-once launch audit, written by run startup (REQ-SESSION-138)
      transcript_archive.jsonl    # evicted transcript pages, once the live window overflows (REQ-SESSION-192)
    evidence/
      debug.log
      tool-calls.jsonl            # capped 5000
      model-input.jsonl           # capped 5000
      context-selection.jsonl     # capped 2000
      report-validation.jsonl     # capped 2000
      memory.jsonl                # capped 2000
      permissions.jsonl           # capped 5000
      events.jsonl                # durable event history, capped 20,000 (+ cap/8 slack)
      events.meta.json            # {"truncated": true, "dropped_events": N, "max_events": N, "last_trimmed_at": "..."}
      conversations/
        index.json                # {"conversations": [...]}
        event_logs/<conv_id>/events/*.json
    artifacts/                    # index.json + artifact bodies
    improvement_artifacts/        # optional
  improvement_artifacts/          # workspace-level copy store
```

### Session id

`YYYYMMDD-HHMMSS-` + 12 lowercase hex characters; regex `^\d{8}-\d{6}-[0-9a-f]{12}$`. The directory name equals the id. Ids are never reused.

### Resumable state (`state/resume.json`)

A single JSON object with `schema_version` (currently 1). Key inventory (bulk fields stripped on write per REQ-SESSION-029; `workspace_root` is the run's effective root, which for a worktree-bound run is the worktree path and not the directory anchor of REQ-SESSION-001): `session_id`, `workspace_root`, `created_at`, `updated_at` (UTC, `Z`-suffixed), `config_snapshot`, `transcript_events`, `ui_edit_diffs`, `child_states`, `report_artifacts` (refs with `id`/`agent_name`/`status`/`path`), `todo_state`, `agent_todo_state`, an outer-loop progress record (nullable), `token_usage` (nullable legacy aggregate), `execution_status`, `exhausted_provider_models`, `message_count`, `message_limit` (nullable), `wait_state` (nullable), `run_intent`, `permission_mode`, `check_suite` (nullable), `sandboxed`, `sandbox_backend`, `requirement_id`, `unit_id`, `worktree` (nullable binding record), `checkpoints`, `last_restored_sequence` (nullable, default null — REQ-SESSION-195), `internal`, `run_type`, `global_tool_call_count`, `global_token_usage`, `global_cost` (default reads as source-unavailable), `global_compressions`, `agent_metrics` (map of agent name to `{tool_call_count, tool_calls, token_usage, cost, compressions, last_prompt_tokens}`), `root_context_tokens`, `seen_compression_ids` (map of agent name to sorted id list), `pending_questions`, `pending_approvals` (map of request id to payload), `verifier_state` (nullable), `gate_warning`, `active_model_key` (nullable), `runtime_model_configs`, `improvement_artifact_ids`.

Worktree binding record: `{path, branch, base_branch, base_revision, created_by_session (default true), merge_status: ready|integrating|merged|merge_failed, integration_session_id (nullable)}`.

Checkpoint entry: `{sequence, ref, commit, created_at, iteration (default 0), child_name (default ""), files (default []), kind: iteration|pre_restore|manual}`; list ordered newest-last.

### Listing metadata (`metadata.json`)

Exactly: `session_id`, `created_at`, `updated_at` (ISO strings), `execution_status`, `schema_version`, `internal`, `worktree` (record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Reader defaults: `checkpoint_count` 0, `task_title` falls back to the session id, attribution empty, `awaiting_input` false.

### Status vocabulary and run outcomes

- Active statuses (assert an in-progress run): `starting`, `running`, `background`, `waiting`, `pausing`, `cancelling`.
- Terminal/idle/blocked statuses: `idle`, `paused`, `paused_message_limit`, `awaiting_plan_decision`, `completed`, `failed`, `stopped`, `interrupted` (repair-only). Together with the six active values this set is the whole closed vocabulary (REQ-SESSION-073), which is the single definition every other document cites.
- Stop reasons and their classification: REQ-MONITOR-301 (this domain restates neither, REQ-SESSION-077).
- Child terminal states: the terminal subset REQ-MONITOR-300 declares absorbing, over the state set of REQ-MONITOR-014; this document holds no copy of either.
- Terminal run outcomes: the closed set of REQ-ORCH-083, carried here through REQ-SESSION-187; this document holds no copy of it. No outcome is expressed as a numeric code.
- Session lock file: `{"pid": <int>, "host": "<machine id>", "acquired_at": "<UTC ISO>"}` — the same shape REQ-GIT-020 fixes.

### Wire and stored events

One serialized event per line of `evidence/events.jsonl`, byte-identical to the live stream. Notable event types with persistence significance: `session.start` (first event of every run; payload per REQ-SESSION-090), `session.end` (mirrors the terminal result), `result` (exactly once per run), `transcript.row` (index + row copy, on append and settle), `tool.start`/`tool.finish`, `iteration.start`/`iteration.end` (iteration attribution boundaries), `gate.decision`, `gate.repair`, `error` (from error-severity issues, `fatal: false`). Unknown event types must survive read and export intact.

### Transcript rows

Persisted dictionaries with roles: `user`; `system`; `agent {name, persona, content}`; `thinking {name, persona, content, started_at?, chars, duration?}`; `tool {name, persona, tool, content (summary), detail (≤400 chars, single line), full_text (≤2000), full_detail (line structure preserved), tool_event_key, tool_terminal, status: running|ok|failed|blocked, started_at, duration?, stream_id? ("fg:<agent_name>" for terminal tools)}`; `verifier` (tool-shaped, `tool_event_key = "verify:<iteration>:<index>"`; check outcomes map passed→ok, failed/timeout→failed, skipped→blocked). Every row carries `ts` in local `HH:MM:SS`. Thinking content caps at 4000 chars while `chars` keeps counting.

Edit diffs persist separately keyed `diff_id = "<agent>:<tool_event_key>"` and merge beside exactly one row at display time.

### Timeline, issues, tool calls, permissions

- Timeline line: `{id: 12 hex, timestamp: UTC ISO, type, severity (default info), actor, message, metadata}`; durable line first, derived wire event second.
- Issue: `{id: 12 hex, timestamp, kind, severity, actor, message, evidence_ref, metadata}`.
- Tool call: `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` + optional `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings`; error-path args/result truncated to 2000 chars.
- Permission decision: `{timestamp, session_id, agent_id, persona, tool_name, decision, rule_id, source, summary, reason, request_id?}`; mode change: `{event: "permission_mode_change", requested_mode, effective_mode, previous_mode, source, reason, skipped_personas}`.
- Repair timeline entry: type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, metadata `{previous_execution_status, execution_status, reason}`.

### Trajectory export document

`trajectory_version: 1`; identity (session id, task, workspace as the run reported it); permission mode; started/ended; status; stop reason; duration; `truncated`/`dropped_events`; recomputed summary (event/unknown/warning counts, `runs` = count of `session.start` boundaries, iterations, tool calls/failures, permission decisions/denials, verifier runs/failures, child agents, errors/fatal errors, per-type counts, tokens, cost); raw stored events (redaction inherited from the wire schema; unknown types intact).
