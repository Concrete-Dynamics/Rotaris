# MCP Server Integration — Desktop Application Surfaces

Part 4 of 6 of [domain 16](../16-mcp-integration.md), which indexes every part. Defines REQ-MCP-091 – REQ-MCP-107.

### Desktop Application Surfaces

- **REQ-MCP-091** — The desktop settings SHALL include a tab labelled "MCP Servers" holding a card headed "Configured servers" with one row per configured server. Each row SHALL show: a status indicator whose state is one of the four of REQ-MCP-092, accompanied by that state as text; the label `{name} · {type}`; a muted secondary line giving the entry's `url` for a remote server and otherwise its configured `command` followed by its configured `args`, joined by single spaces; the server's origin drawn from the vocabulary of REQ-MCP-026; and a toggle switch. The card SHALL list **every** configured server, a server that is disabled included, so the list is a complete picture of what the configuration declares; a disabled row SHALL say so as text and SHALL say which control disabled it (REQ-MCP-115). The switch SHALL read as on if and only if the server is both enabled and available per REQ-MCP-037. Its state at application start SHALL be the entry's configured `enabled` value (REQ-CONFIG-465) and nothing else: no per-user enablement file is read, because none exists (REQ-MCP-115), and every session override of REQ-MCP-094 is discarded at exit. For an unavailable server the switch SHALL be non-interactive and SHALL carry a tooltip stating that the command was not found on the executable search path. With no servers configured the card SHALL show an empty state naming the configuration file as the place tool servers are declared (REQ-CONFIG-350).

- **REQ-MCP-092** — Per-server health SHALL expose exactly the four states of REQ-CONFIG-353: `unknown` (initial on every launch; health is never persisted), `checking` (pulsing indicator), `healthy` (with discovered tool count), and `unreachable` (error text in tooltip). Health SHALL always be written out textually, never encoded only in color; colors map through the active theme. A "Check status" header button (accessible description "Probe every configured MCP server") SHALL probe all configured servers sequentially on a background thread without ever blocking the UI thread; unavailable servers SHALL short-circuit to `unreachable`, without connecting, with detail conveying that the command was not found on the executable search path (REQ-CONFIG-352); the button SHALL disable while a probe runs and re-enable when finished.

- **REQ-MCP-093** — Desktop availability SHALL delegate to the shared rule of REQ-MCP-037.

- **REQ-MCP-094** — Given a server toggled off in the desktop app, when the next run's configuration is projected, then that server SHALL be removed from both the server map and every persona's carried-server list, leaving only enabled-and-available servers. These toggles are **deliberately session-scoped**: they override the configured `enabled` value of REQ-CONFIG-465 for the life of the application process, are never written to disk, and are discarded at exit, so the next launch starts from the configured value again. They are the quick way to take a server out of the next run; making that durable is an `enabled` edit in the configuration file (REQ-MCP-115), which the category says plainly rather than leaving the user to discover that a toggle did not stick.

- **REQ-MCP-095** — First-run machine setup SHALL state, before it begins any check, that it is about to check the developer tooling and the package caches the MCP servers depend on, and the settings surface SHALL offer an action that re-runs exactly those checks on demand. The release-pinned setup manifest SHALL carry the `browser` package's version string character for character as the default entry of REQ-MCP-010 carries it; a build in which the two strings differ SHALL be treated as defective, and the build SHALL check them against each other. The literal wording of the first-run message and the label of the settings action are left to the implementation; what is fixed is that the message states, before any check runs, that developer tooling and the package caches the MCP servers depend on are about to be checked, and that the settings action identifies itself as re-running exactly those checks.

- **REQ-MCP-096** — Package-cache warm-up steps SHALL be derived from the merged server configuration of REQ-MCP-025, considering only `stdio` entries whose resolved command's file name is `uvx`, `uvx.cmd`, `npx` or `npx.cmd`. For a `uvx` entry the package specification SHALL be the value following a `--from` argument, or failing that the first argument containing `==`, and the warm command SHALL be `uvx --from <spec> <executable> --help`. For an `npx` entry the package SHALL be the first argument that does not begin with `-`, with no version pin required, and the warm command SHALL be `npx -y <pkg> --help` with `npx` resolved to an absolute path; the step SHALL be omitted entirely when `npx` is not found on PATH. An entry from which no package specification can be taken SHALL yield no step. `<executable>` in the `uvx` warm command SHALL be the first resolved argument after the package specification that does not begin with `-`, the specification itself excluded; where the entry supplies no such argument the step SHALL be omitted rather than guessed at. The match of the resolved command's file name against `uvx`, `uvx.cmd`, `npx` and `npx.cmd` SHALL be **case-insensitive**, compared without regard to case on every platform alike, so a Windows entry naming `NPX.CMD` warms exactly as one naming `npx.cmd` does. Steps SHALL be identified as `warm:<family>:<package>` with `<family>` being `uvx` or `npx`, labelled `Warm <package>`, and tagged with the capability `"<server> MCP server"`; two entries that produce the same identifier SHALL yield exactly one step. On resume, a step already recorded as completed SHALL be skipped unless the run was started as a manual re-run, in which case it SHALL run again.

- **REQ-MCP-097** — *Withdrawn.* A shell command was its only surface; inspecting the machine's developer tooling, installing what is missing, warming package caches, repairing broken installations, and reporting progress and the final outcome are carried by REQ-MCP-112.

- **REQ-MCP-098** — The desktop SHALL derive its applicable project-initialization task list from the core task registry (which applies REQ-MCP-045) rather than re-deriving prerequisites.

- **REQ-MCP-099** — Deterministic code-intelligence project setup SHALL invoke the command line derived by REQ-MCP-036 and run three steps in order — project creation, project indexing, and memory-store initialization — bounded at 300, 1800 and 120 seconds respectively. Project creation SHALL be skipped when the runtime's per-project marker file is already present, and SHALL never overwrite an existing project. Child processes SHALL be run with UTF-8 input and output encoding; their completion SHALL be polled every 0.25 seconds; on cancellation or timeout the child SHALL be asked to terminate, given 5 seconds to exit and then force-killed — on Windows the whole process tree — and a step whose child exceeded its budget SHALL be reported as failed. The output reported for a failing step SHALL be truncated to its last 400 characters, keeping the end of the output and discarding the beginning. In a workspace that contains no code, the indexing and memory steps SHALL be skipped and reported with status `skipped-no-code` while creation still runs. A configured code-intelligence entry that is remote, or whose arguments contain no server-launch subcommand, SHALL produce a non-retryable failure whose message states that the entry is not a local launch; no substitute command SHALL be attempted. The marker file's name and the three steps' subcommands SHALL be read from the binding manifest of REQ-MCP-116.

  A workspace **contains code** when, walking it from its root, at least one regular file is found whose name-extension appears in the manifest's indexable-extension list; the walk SHALL skip version-control metadata directories and every path the workspace's version-control ignore rules exclude, SHALL traverse dot-prefixed directories that are not so excluded, SHALL follow no symbolic link out of the workspace, and SHALL stop at the first qualifying file. A workspace in which the walk finds none contains no code. The test SHALL be performed once per setup run and its answer used for both steps it gates.

  A failed step SHALL stop the steps that would otherwise follow it: the three are ordered because each depends on the one before, and indexing a project that was never created cannot succeed. A step not attempted for that reason SHALL be reported with status `not-attempted`, distinct from a failure of its own. The status vocabulary for the three steps SHALL therefore be exactly `succeeded`, `failed`, `skipped-no-code` and `not-attempted`, and a run in which any step is `failed` or `not-attempted` SHALL be reported as not having completed setup.

  > **Narrowed by [`PD-MCP-003`](../../product/directives/pd-mcp-003.md#pd-mcp-003), 2026-10-06.** A stopped step is given 2 seconds to
  > exit, not 5, at every stop — an exhausted budget, a cancellation and the application's close alike — and is then
  > force-killed. Everything else above still holds.

- **REQ-MCP-100** — The auxiliary per-agent pop-out window SHALL list the agent's granted MCP tools compactly: one muted line per server in the form "{server}: tool, tool, …", sourced from the run's recorded grant evidence (REQ-MCP-065).

- **REQ-MCP-112** — The machine-setup action of REQ-MCP-095 SHALL be the product's one way to inspect the machine's developer tooling, install what is missing, warm the package caches derived by REQ-MCP-096 for the current workspace's merged configuration, and repair a broken installation. It SHALL run on a background thread without ever blocking the interface, and while it runs it SHALL show which step is in progress and which steps have finished, each finished step carrying its outcome and, where it failed, text describing the failure. It SHALL be cancellable at any point, and cancelling SHALL stop after the step in flight rather than leaving a step half-applied. When it finishes it SHALL state one final outcome, and that outcome SHALL distinguish at least: every step succeeded; some step failed so the machine is only partly set up; and the run was cancelled. A failure or a cancellation SHALL never be reported as success, and neither SHALL fail a run or block the application — a machine that is only partly set up still starts, and the servers whose caches were not warmed behave as REQ-MCP-041 and REQ-MCP-107 describe. The action SHALL be re-runnable on demand as many times as the user wishes, SHALL refuse to start a second concurrent run, and on a re-run SHALL re-execute steps already recorded as completed (REQ-MCP-096). Progress and outcome SHALL be readable as text, never encoded only in colour (REQ-SHELL-149).

- **REQ-MCP-114** — For every agent of a run, the desktop agent inspector SHALL show which MCP servers that agent actually carried, so what a run used can be read after the fact and not only what the configuration declares. Per server it SHALL show the server's name, its transport, its origin from the vocabulary of REQ-MCP-026, and its fate for that agent — carried and connected, or dropped, with the reason drawn from the drop rules that apply: not present in configuration (REQ-MCP-038), disabled (REQ-MCP-040), unavailable (REQ-MCP-041), or tool discovery having failed (REQ-MCP-042). A dropped server SHALL still be listed, with no granted tools under it; a carried server SHALL be listed with the granted tools of REQ-MCP-065. Every one of those states SHALL be conveyed as text (REQ-SHELL-149), and the list SHALL remain readable at the minimum window size (REQ-SHELL-022). The information SHALL be sourced from the run's own recorded evidence, so it reads the same for a finished run as for a running one and does not change when the configuration is later edited.

### Prompt Rendering of the MCP Surface

- **REQ-MCP-101** — The persona system prompt SHALL contain one designated MCP section. An *active* server, for this requirement, is a server the persona carries that survived every drop rule — it is present in configuration (REQ-MCP-038), not disabled (REQ-MCP-040) and not dropped as unavailable (REQ-MCP-041). When the persona has no active server, that section's body SHALL be exactly the literal line `_No MCP servers configured._` and nothing else. Otherwise the body SHALL be a Markdown bullet list with one top-level bullet per active server: a server for which no tool is known (discovery returned nothing, or failed per REQ-MCP-048) SHALL render as its name in code formatting, `` `name` ``; a server with known tools SHALL render as its name in bold code formatting, ``**`name`**``, followed by one indented child bullet per tool, each child bullet being `- `, then the tool name in code formatting, then — only when that tool's description is a non-empty string — ` — ` followed by the description text. The names rendered SHALL be exactly the names of REQ-MCP-062: after grant filtering, after `disabled_tools` removal, and after `tool_name_map` renaming — a renamed tool appears under its replacement name only, which is also the name the model calls (REQ-MCP-005). Servers SHALL be listed in the ascending order of REQ-MCP-117 by the name they are configured under, and a server's tools in that same order by the name printed, so one persona's prompt is byte-identical whenever its inputs are and two personas never disagree about order. The section's heading text is left to the implementation, provided it identifies the section as the persona's MCP servers and provided one heading is used in every prompt the product renders.
  > **Narrowed by [`PD-MCP-001`](../../product/directives/pd-mcp-001.md#pd-mcp-001), 2026-10-06.** Everything above still governs, with one exception: the bundled code-intelligence runtime's usage-instruction tool is rendered with the description the product wrote for it, carried by the binding manifest, in place of the one its server reports.

- **REQ-MCP-102** — A persona's prompt SHALL carry a fixed project-memories protocol block, placed under the code-intelligence server's entry in the MCP section (REQ-MCP-101), if and only if that persona's granted tools for that server include both the project-memory listing tool and the project-memory reading tool. The block SHALL tell the agent: to read the memories that already exist before it starts exploring the codebase; to write durable findings that are not obvious from the code back through the memory-writing tools it holds; to keep agent-instruction files out of memory; and to keep anything true only of the current run out of memory. Those four points are the block's required content and SHALL all be present; its literal wording is left to the implementation. Every prompt that carries the block SHALL carry the same characters in the same order, so the wording is chosen once and never varies by persona, server or run. A persona missing either gating grant SHALL receive no such block. The two gating tool names SHALL be read from the binding manifest of REQ-MCP-116.

### Validation and Launch Error Semantics

- **REQ-MCP-103** — Configuration validation SHALL report, per persona, an error of the form "Persona '<p>' references unknown MCP server '<s>'" for any carried server name absent from the configuration's server map.

- **REQ-MCP-104** — Configuration validation SHALL report an error when a persona grants MCP tools for a server it does not carry, naming both the persona and the server.

- **REQ-MCP-105** — Persona generic tool names SHALL validate against the public native tool set plus configured MCP server names; any other name is an error naming the persona and the unknown tool. An MCP server name in the generic tool list is legal but warned per REQ-MCP-039.

- **REQ-MCP-106** — Agent construction SHALL fail with an error listing the offending names when an advertised non-MCP tool is not actually registered; MCP server names SHALL be exempt from this prompt/tool mismatch guard.

- **REQ-MCP-107** — When a child agent fails to launch and an MCP connection error appears anywhere in the failure's cause chain, exactly one diagnostic SHALL be produced and delivered through both channels of REQ-MCP-044 — never zero, never two. The diagnostic SHALL be chosen from the root cause by the first matching case of two: (1) the root cause is a failure of the operating system to start the child process at all — whatever error the platform reports for it, a missing executable and an unusable file descriptor alike — and yields a message conveying that the server's configured command could not be started, that it is probably not installed or not on the executable search path, and the two remedies available (install it, or declare that server on the `http` transport instead); (2) any other MCP connection error yields a message conveying that connecting to that server failed. Reducing the enumeration to "the process could not be started" is deliberate: no list of platform error codes has to be maintained for the rule to be testable, and the two former cases carried the same advice anyway. Every variant SHALL name the persona whose launch failed, SHALL name the server, and SHALL reproduce the root cause's own text; the wording around those facts is left to the implementation. A launch failure whose cause chain holds no MCP connection error SHALL yield no MCP diagnostic and no `mcp_config` issue record.
