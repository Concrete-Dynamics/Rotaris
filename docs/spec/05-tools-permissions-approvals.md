# Agent Tooling, Terminal Execution, Permissions, and Approvals

## Overview

Every tool call an agent makes — built-in, custom plugin, or MCP — passes through a single permission gate that resolves to allow, ask, or deny before anything executes; asks are answered by an interactive approval prompt or a fail-safe headless policy, denials are returned to the agent as recoverable tool errors, and every decision is recorded to an append-only per-session audit trail with secrets redacted. Around that gate sits a fixed public tool surface (terminal execution with foreground and background sessions, workspace-fenced file and search tools, a local commit tool, task-list, artifact, delegation, and user-question tools), an opt-in OS-level sandbox that refuses to run commands rather than silently falling back, a host-classifying network egress policy for the fetch tool, and three permission-mode presets ordered by restrictiveness with an automatic downgrade for unattended, unsandboxed runs.

## Requirements

### 1. Public Tool Surface and Persona Grants

**REQ-TOOLS-001** — Given a persona configuration file (`agents.yaml`), the set of tool names a persona may declare under `tools:` is exactly: `ask_questions`, `delegate`, `background_output`, `wait_for_tasks`, `haet`, `haet_edit`, `haet_read`, `read_file`, `write_file`, `terminal`, `git_commit`, `git_read`, `todo`, `fetch`, `grep`, `glob`, `artifact_read`, `artifact_list`, `artifact_write`. The name `haet` is an accepted alias that resolves to the same tool as `haet_edit`. No other value is accepted. In particular `tools:` never names an MCP server: MCP surfaces are granted only through the persona's `mcp_servers` key and narrowed only through `mcp_tools` (REQ-TOOLS-166), so exactly one key grants a server and `tools:` carries public tool names alone.

Every name in that registry additionally carries a **capability declaration**, and this requirement is the product's single definition of it: the registry declares, for each name, three independent facets — whether the tool **reads workspace files**, whether it **writes workspace files**, and whether it **runs commands** — each either declared or not declared, so that a rule anywhere in the product can be resolved against what a tool does rather than against a name list that has to be kept in step by hand. The declaration is a property of the tool and never of the content it is handed: `terminal` declares running commands whatever the command it is given happens to do, and a command that writes a file does not make `terminal` a writer of workspace files. The declarations are:

- reads workspace files: `read_file`, `write_file`, `haet_read`, `haet_edit`, `haet`, `grep`, `glob`, `git_commit`, `git_read`;
- writes workspace files: `write_file`, `haet_edit`, `haet`, `git_commit`;
- runs commands: `terminal`;
- declaring none of the three: `ask_questions`, `delegate`, `background_output`, `wait_for_tasks`, `todo`, `fetch`, `artifact_read`, `artifact_list`, `artifact_write` — each reaches the user, another agent, the network, or the artifact store, and none of those is the workspace file tree (REQ-TOOLS-007).

`git_commit` declares both reading and writing workspace files because it records a commit in the repository that lives inside the workspace, even though it leaves the working tree's contents alone (REQ-TOOLS-142). A name added to this registry later carries its own declaration from the moment it is added, so a requirement resolved against the declaration needs no amendment when the registry grows. A tool that is not a member of this registry — a custom plugin tool (section 23) or a tool published by an MCP server (section 24) — carries no declaration at all, and a facet is never inferred from its name, its description, or anything the tool says about itself. An undeclared tool is read fail-closed, in the direction of the rule reading it: a rule that grants or widens on the strength of a declared facet treats an undeclared tool as declaring nothing and does not grant it, while a rule that withholds, refuses, or blocks on the strength of a declared facet treats an undeclared tool as declaring all three and withholds, refuses, or blocks it. A requirement in any other domain that needs the declaration cites this requirement and states only what it does with it; no requirement in any other domain holds a second copy of the facets or of the per-tool declarations above.

**REQ-TOOLS-002** — An entry in a persona's `tools:` list is accepted only when it is one of the public tool names of REQ-TOOLS-001. Any other entry fails configuration validation, and the resulting error identifies the persona, the rejected entry, and the accepted public tool names. An entry that names a server configured for the workspace fails like any other unrecognized entry, and its error additionally says that MCP servers are granted through `mcp_servers`. A persona whose `custom_tools:` plugin registers under a name that persona also declares under `tools:` likewise fails validation, so no persona ever holds two different tools under one name.

**REQ-TOOLS-003** — The verification-gate capabilities of section 22 are outside the public tool surface, and so is any capability not named in REQ-TOOLS-001. No configuration makes them callable by a persona: naming one under `tools:` is rejected like any other unrecognized entry (REQ-TOOLS-002), and no persona's prompt ever lists them among its tools. They are reachable only from the run that maintains the verification gate.

**REQ-TOOLS-004** — Missing tool prerequisites degrade availability rather than failing agent construction: a declared tool whose runtime prerequisite is absent is removed from the agent's tool set, and each removal is recorded with a stable, machine-readable reason code. Reasons that must be distinguishable: delegation tools declared without a delegation runtime; `ask_questions` declared without a user-prompt channel; artifact tools declared without an artifact store; and `artifact_write` declared by a persona that lacks `can_publish_artifacts: true`. The concrete spelling of each code is an implementation choice, provided it is stable and documented.

**REQ-TOOLS-005** — Declaring `delegate` surfaces three tools to the agent — `delegate`, `background_output`, and `wait_for_tasks` — in both the prompt's tool listing and the callable tool set.

**REQ-TOOLS-006** — A persona's declared tool set is narrowed by up to four controls, applied in this order, each able only to remove tools — never to restore one an earlier control removed, and never to add one the persona did not declare:

1. a run-scoped allow-list that applies to the orchestrator (default) persona alone; when one is present the surviving set is the intersection of that list with the persona's declared tools, and no control below it widens the result;
2. `coordinator_only: true`;
3. `read_only: true`, which reduces the set to the read-only class of REQ-TOOLS-007;
4. the per-persona `tool_restrictions` map.

Every removal is logged together with the persona and the control that removed it. `coordinator_only: true` removes exactly `terminal`, `write_file`, `haet_edit`, `haet`, and `git_commit`, and removes nothing else: every other tool the persona declared survives it, including the whole read-only class of REQ-TOOLS-007 (`grep`, `glob`, `fetch`, `haet_read`, `read_file`, `git_read`, `artifact_read`, `artifact_list`, `artifact_write`) and the delegation and task-list tools. A coordinator can therefore read, search, fetch, delegate, track, and publish, while being unable to modify the workspace or run a command. Consequently the surviving set always contains `delegate`, `background_output`, `wait_for_tasks`, `todo`, `grep`, and `glob` when the persona declared them, and never contains the five removed names.

The run-scoped allow-list is a field of the run configuration produced when a run is started from the desktop interface, recorded in that session's run-configuration record. It is per-run: it has no configuration-file key, no other source, and is absent by default, in which case it narrows nothing. A name in the list that the orchestrator persona never declared is ignored — the control is an intersection and can only remove — and every such name is logged once for the run, so a typo is visible without ever widening what the run may do.

**REQ-TOOLS-007** — The read-only tool class is exactly {`grep`, `glob`, `fetch`, `haet_read`, `read_file`, `git_read`, `artifact_read`, `artifact_list`, `artifact_write`}. `artifact_write` is deliberately classified read-only because the artifact store is not part of the workspace. The network tool class is exactly {`fetch`}, a subset of the read-only class, split out so presets can gate network access by host before any blanket read-only allow rule.

Both classes are stated against the capability declaration of REQ-TOOLS-001 and are held consistent with it: no member of the read-only class declares writing workspace files or running commands, and no name that declares either is ever a member of it, so a name added to the registry declaring one of those two is outside the class by construction rather than by a second decision. The network class is defined by where the tool sends a request and not by any of the three facets — `fetch` declares none of them, the network not being the workspace file tree — which is why the two classes overlap without either being derivable from the other. Membership of a class is not itself a facet: the classes say what a preset may allow in bulk, while the declaration says what a tool does, and a requirement needing one of them cites the requirement that fixes it rather than reading it off the other.

**REQ-TOOLS-008** — When a persona requests `terminal`, the behavior specified in sections 10–14 is exactly what serves that name. The registered public name is exactly `terminal`.

**REQ-TOOLS-009** — A tool call is governed by the policy, sandbox specification, egress configuration, and artifact store of the run that issued it, and rebuilding the issuing agent — after a retry, after a resume, or after falling back to a different model — leaves all four unchanged. No call is ever decided under, or executed with, a different run's context. When a call cannot be attributed to a run while more than one run is live, it is refused under REQ-TOOLS-020 with a reason naming the ambiguity rather than being attributed to one of the live runs. The rule-less default of REQ-TOOLS-029 applies only to a call that belongs to no run at all.

**REQ-TOOLS-010** — The tool list rendered into an agent's prompt and the set of tools it can actually invoke are produced from the same resolution, so they are always equal.

### 2. Central Permission Gate

**REQ-TOOLS-011** — Every tool dispatch — built-in, custom plugin, and MCP — passes exactly one central allow/ask/deny gate before execution. There is no ungated dispatch path.

**REQ-TOOLS-012** — The decision vocabulary is {`allow`, `ask`, `deny`}. Policy resolution never raises to the dispatcher, and an `ask` is always resolved through the approval flow first, so the dispatcher only ever handles `allow` or `deny`.

> **Narrowed by [`PD-TOOLS-011`](../product/directives.md#pd-tools-011), 2026-10-06.** The decision vocabulary an audit
> entry is read against also holds `user-input`, carried only by the entry of a user's own terminal action (REQ-SHELL-107).
> What this requirement says of policy resolution and the dispatcher is unchanged.

**REQ-TOOLS-013** — A `deny` does not abort the run. It is returned as a tool-result error carrying the original tool-call id so the agent can re-plan. The refusal text is exactly: `Permission denied by rule '<rule_id>'. <reason> The '<tool_name>' call was not executed. Choose a different approach or ask the user to adjust the permission policy.`

**REQ-TOOLS-014** — Loop-control tool names are never gated: `finish`, `finishtool`, `think`, `thinktool`, matched case-insensitively. Such calls resolve to allow with decision source `builtin` and rule id `builtin:meta-tool`.

**REQ-TOOLS-015** — A permission request carries the tool name, the persona, the call's arguments as a name→value mapping, and at most one command facet, which is the value command matchers examine. The facet is the `command` argument when that argument is present and holds a string; failing that, the `url` argument when it is present and holds a string (this is what lets host-scoped rules match `fetch`); otherwise the request has no command facet. The facet is selected purely by argument name, so any tool whose action carries a string `command` argument supplies one. Among the public tools of REQ-TOOLS-001, only `terminal` names an argument `command` and only `fetch` names one `url`: the file-writing tool's operation selector is named `operation` (REQ-TOOLS-135), never `command`, so an operation name such as `create` or `edit` can never occupy the slot a shell command line occupies and no command matcher ever sees one. A custom plugin tool (section 23) that names a string argument `command` does supply a facet and command matchers do examine it; an author who does not want that names the argument something else. When the arguments cannot be rendered at all, the request is formed with an empty argument mapping and no facet, and resolution still yields a decision from tool name and persona alone — a rule constraining arguments, paths, or the command facet cannot match such a request, so no argument-dependent rule can allow it.

**REQ-TOOLS-016** — Two renderings exist and are never substituted for one another. The *request summary* is `<tool>: <redacted command facet>` for a request that has a command facet and `<tool>(<argument keys, sorted, comma-separated>)` for one that does not; apart from the redacted command facet itself it exposes no argument value, only key names. The request summary is what appears as `summary` in audit entries (REQ-TOOLS-079) and in the `permission.decision` and `approval.requested` events (REQ-TOOLS-061, REQ-TOOLS-083), and it is the text quoted in a session rule's description (REQ-TOOLS-024). The *argument summary* of REQ-TOOLS-057 is the other rendering: it lists redacted argument values, and it appears only in the approval payload and the approval dialog — never in an audit entry and never in a stream event.

**REQ-TOOLS-017** — A permission rule may constrain any combination of five facets: tool names (a set, compared case-insensitively), personas, path scope (`inside_workspace` | `outside_workspace`), a command matcher, and an exact argument set. The exact-argument facet matches only when the request's argument mapping and the rule's mapping carry the same set of keys and, for every key, the same textual value; a request carrying an extra key, or missing one the rule names, never matches. A rule fires only when every facet it populates matches; a facet left unpopulated constrains nothing, so a rule populating no facet matches every request. A command matcher that fails while being evaluated leaves its rule unfired and unable to produce an allow, and the resolution falls closed under REQ-TOOLS-020. The textual value of a string argument is the string itself. Every non-string value — number, boolean, null, list, nested object — is compared by its compact JSON encoding: no insignificant whitespace, object keys sorted ascending by code point, and numbers written in the shortest form that round-trips to the same value, so an integral value carries no fractional part and `1` and `1.0` compare equal. `true` compares as `true`, `null` as `null`, and `[1, 2]` as `[1,2]`. A rule author writes that form, and two implementations that agree on JSON agree on which requests a rule matches.

**REQ-TOOLS-018** — Path-scope evaluation considers only argument keys in {`path`, `file_path`, `filename`, `paths`, `base_path`, `dir`, `directory`} (string or list values). Relative paths resolve against the workspace root. `inside_workspace` fires only when every path argument lands inside the root; `outside_workspace` fires as soon as one path escapes it. A request that supplies none of those argument keys can never satisfy a path-scoped rule. A path that cannot be resolved counts as outside (fail-closed).

**REQ-TOOLS-019** — A policy is an ordered list of rules together with a default decision and a preset name. The first rule in list order whose facets all match decides the call, and no later rule affects that outcome; REQ-TOOLS-041 depends on this ordering. A policy is invalid when its preset name is empty, when any rule id is empty, when two rules carry the same id, or when a rule's outcome falls outside the vocabulary of REQ-TOOLS-012. An invalid policy produces an error naming the defect at the latest when the first call would be decided under it, and it never decides a call.

**REQ-TOOLS-020** — Fail-closed is unconditional: any exception during decision resolution yields rule id `failclosed:unresolvable-policy`, decision source `fail-closed`, and decision `ask` on interactive hosts / `deny` on headless hosts — never `allow`. The reason reads: `The permission policy could not be resolved (<detail>); failing closed to <ask|deny>.`

**REQ-TOOLS-021** — When no rule matches, the preset default applies with rule id `preset:<preset_name>`, decision source `preset`, and reason `No rule matched; permission mode '<name>' defaults to <decision>.`

**REQ-TOOLS-022** — A rule-match reason reads `Rule '<id>' (<description>) resolved '<tool>' to <decision>.` with decision source `rule`, or `session-rule` when the matching rule came from a session approval.

**REQ-TOOLS-023** — Approvals granted for the session are matched before any policy rule, most recent grant first, and they outlive the policy: after the policy is replaced or the permission mode is changed mid-session, every session approval granted earlier still matches exactly the calls it matched before — none is dropped, and none starts matching a call it did not match already. Their rule ids are `session:allow:<n>`, numbered from 1 in grant order.

**REQ-TOOLS-024** — A session approval matches only a call carrying the same tool name (compared case-insensitively), the same persona, and — when the approved call had a command facet — a command facet identical to the approved one character for character, compared before redaction. When the approved call had no command facet, the call must carry the same exact argument set as defined in REQ-TOOLS-017. Consequences a test can check: after `git push origin main` is approved for the session, `git push origin release` from that persona asks again, and `git push origin main` from a different persona asks again. The session rule's description reads `Approved for this session: <request summary>`, using the request summary of REQ-TOOLS-016.
  > **Narrowed by [`PD-TOOLS-004`](../product/directives.md#pd-tools-004), 2026-09-23.** The rule above still governs every tool but `write_file` and `haet_edit`; for those two, a session approval matches a later call from the same persona whose path arguments resolve to the same set of paths, whatever its other arguments.

**REQ-TOOLS-025** — When the policy in force is replaced while a run is live, the agent's very next tool call is decided under the replacement, with no restart, no reconnection, and no agent rebuild in between. Decisions already returned keep the outcome they had.

**REQ-TOOLS-026** — If approval resolution raises, or returns another `ask`, the call is denied with source `fail-closed` and a reason ending `Denied because approval resolution failed: <detail>.` or `Denied because approval resolver returned no verdict.` respectively.

**REQ-TOOLS-027** — Every resolved decision, allows included, is recorded to the audit sink. A raising audit sink logs a warning and never breaks dispatch.

**REQ-TOOLS-028** — The decision-source vocabulary recorded in audits and events is exactly: `rule`, `session-rule`, `preset`, `builtin`, `fail-closed`, `user-once`, `user-session`, `user-deny`, `headless-policy`, `timeout`, `cancelled`, `presenter-error`.

> **Narrowed by [`PD-TOOLS-011`](../product/directives.md#pd-tools-011), 2026-10-06.** The vocabulary also holds `user`,
> its thirteenth member, carried only by the audit entry of a user's own terminal action (REQ-SHELL-107). The text above
> states the behavioural target and is kept for that reason.

**REQ-TOOLS-029** — A call that belongs to no run at all is decided by a rule-less default policy whose default decision is allow and whose preset name is reported as `unrestricted`, and a warning is logged for every decision taken under it. This default is never applied to a call that does belong to a run, and no call is ever decided under a policy belonging to a different run (REQ-TOOLS-009).

**REQ-TOOLS-030** — Changing the permission mode mid-session takes effect for every live agent of the named session and for no agent of any other session. With two sessions running at the same time, a mode change in one leaves the decisions produced by the other session's agents unchanged.

**REQ-TOOLS-031** — Hook ordering invariant: policy first, hooks second. User-configured pre-execution hooks run only on the allow branch; a policy-denied call fires no hook. A blocking pre-execution hook returns the hook's refusal as a tool-result error (fallback text: `Blocked by a pre_tool hook. The call was not executed.`). Post-execution hooks see only calls that actually executed and can only append feedback (attached to the observation's extended content, or as a trailing user message when no observation exists) — they can never block. The tool result handed to a post-execution hook is truncated at the cap REQ-HOOKS-066 fixes, which this domain does not restate; what it relies on that requirement for is that the cap is applied before the hook sees the result, so a hook never receives an untruncated observation this domain produced.

**REQ-TOOLS-032** — A tool-call payload the model produced that is not well-formed is repaired before dispatch rather than rejected, and repair is attempted before schema validation, so a payload repair makes valid is dispatched as an ordinary call. Three repairs are required: JSON cut off mid-structure is completed by closing the strings, objects, and arrays still open at the cut; a single object supplied where the schema expects an array is read as a one-element array, for the fields `tasks`, `phases`, `files`, `items`, and `test_cases`; and a truncated run-completion payload is recovered as `{"message": <recovered text>}`. A payload still schema-invalid after repair is returned to the model as a recoverable tool-result error carrying the original tool-call id — the same shape a policy denial takes in REQ-TOOLS-013 — naming the tool and the schema violation and asking for a corrected re-issue. The call is not executed, the host never silently re-sends it, and the run is never ended by it; re-planning is the model's business, exactly as it is after a deny.
  > **Extended by [`PD-TOOLS-007`](../product/directives.md#pd-tools-007), 2026-10-06.** The three repairs above still govern; the directive adds a fourth, for `write_file` alone: a call with a path and content, no `operation` and no field only another operation reads, whose file does not exist, is read as a `create`, and its result says so.

### 3. Terminal Command-Line Pattern Matching

**REQ-TOOLS-033** — A command pattern is compared token by token, never against the raw text of the command line. Pattern text and command segment are each split under shell tokenization rules, and the *i*-th pattern token must glob-match the *i*-th command token. A pattern whose final token is `*` additionally matches any number of further command tokens, so `rm -rf *` fires on a bare `rm -rf`; a pattern without that trailing `*` matches only a segment with exactly as many tokens as the pattern has. The first token of a segment — the command name — is compared without regard to letter case, on every platform and every backend; every later token is compared case-sensitively, on every platform and every backend. One rule therefore behaves identically wherever it runs, while still catching the command names of a shell that does not distinguish case. Observable consequences: `git status` does not fire on `git status-check`, and it does not fire on `git STATUS`, because the differing token is not the command name; `Remove-Item *` fires on `remove-item -Recurse .` on the PowerShell backend of REQ-TOOLS-104; and `rm -rf *` fires on `RM -rf /`. Because later tokens keep their case, a rule that must catch two spellings of a switch lists both (REQ-TOOLS-039).

**REQ-TOOLS-034** — Pattern text that cannot be tokenized, or that is empty, is a policy-construction error raised at policy build time (message pattern: `Command pattern '<text>' is not tokenisable: …` / `… is empty`), so typos fail loudly rather than silently matching nothing.

**REQ-TOOLS-035** — Compound command lines are decomposed on shell operators — `&&`, `||`, `;;`, `;`, `|`, `&`, and newline, longest operator first — respecting single/double quotes and backslash escapes. Each segment is matched independently, so in `git status && rm -rf /` the second segment still triggers the applicable deny rule. The operator that introduced each segment is retained with the segment.

**REQ-TOOLS-036** — A segment is classified "unconfident" (statically unreadable) when any of the following holds: it contains command substitution (`$(…)` or backticks outside single quotes, including inside double quotes); it cannot be tokenized (e.g., unbalanced quotes); it carries no command after redirection stripping; its head is an indirection command ({`eval`, `exec`, `source`, `.`, `xargs`, `env`, `nohup`, `time`} — reason: runs another command through that head); or its head is a shell ({`sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `cmd`, `powershell`, `pwsh`}) with a `-c`/`-Command`/`/c`/`/C` argument (inline script) or with no arguments (interactive/script execution). Redirection tokens (`<`, `>`, `>>`, `2>`, `2>>`, `&>`, `1>`, `<<`, `<<<`, and anything beginning with `>` or `<`) end the token stream considered for matching.

**REQ-TOOLS-037** — Decomposing a command line never raises. A line that cannot be parsed at all still yields exactly one segment, classified unconfident, so every input produces at least one segment for the escalation matcher to fire on.

**REQ-TOOLS-038** — Rules may use any of three command matchers, each evaluated over the segments the command line decomposes into under REQ-TOOLS-035:
- the **pattern matcher** fires when at least one segment matches at least one of the matcher's patterns under the token rules of REQ-TOOLS-033;
- the **escalation matcher** fires when at least one segment is unconfident under REQ-TOOLS-036, which includes a segment whose text is not blank yet yields no command token;
- the **pipe-to-shell matcher** fires when a segment whose first token is one of the shell names listed in REQ-TOOLS-036 was introduced by a `|` operator — that is, it consumes the output of the segment before it (the `curl … | sh` shape).

A matcher decides only whether its own rule fires. It cannot stop an earlier rule from firing, cannot alter a decision already reached, and cannot turn a command that matched no rule into an allow; such a command falls through to the preset default (REQ-TOOLS-021).

**REQ-TOOLS-039** — A starter set of nine command rules exists. The five deny rules occupy positions 1–5 of the set and the four ask rules positions 6–9, so within this family a deny is always reached before an ask:
1. `starter:deny-recursive-delete` (deny), patterns: `rm -rf *`, `rm -fr *`, `rm -Rf *`, `rm -r -f *`, `rm -f -r *`, `rmdir /s *`, `rmdir /S *`, `rd /s *`, `rd /S *`, `del /f *`, `del /F *`.
2. `starter:deny-privilege-escalation` (deny), patterns: `sudo *`, `doas *`, `su *`, `runas *`.
3. `starter:deny-force-push` (deny), patterns: `git push --force *`, `git push -f *`, `git push --delete *`.
4. `starter:deny-package-publish` (deny), patterns: `npm publish *`, `yarn publish *`, `pnpm publish *`, `uv publish *`, `twine upload *`, `cargo publish *`, `gh release create *`.
5. `starter:deny-pipe-to-shell` (deny), using the pipe-to-shell matcher of REQ-TOOLS-038.
6. `starter:ask-unreadable-command` (ask), using the escalation matcher of REQ-TOOLS-038 — a command whose effect cannot be read from the command line alone.
7. `starter:ask-history-rewrite` (ask), patterns: `git reset --hard *`, `git clean -fd *`, `git clean -df *`, `git checkout -- *`, `git rebase *`, `git filter-branch *`.
8. `starter:ask-dependency-install` (ask), patterns: `pip install *`, `uv pip install *`, `uv add *`, `npm install *`, `npm i *`, `yarn add *`, `pnpm add *`, `cargo install *`, `brew install *`, `apt-get install *`.
9. `starter:ask-container-control` (ask), patterns: `docker *`, `podman *`, `kubectl *`, `systemctl *`, `Remove-Item *`.

Every pattern listed above is matched under the token rules of REQ-TOOLS-033: each listed spelling stands on its own, and a spelling that is not listed does not match by inference. A command line carrying a segment classified unconfident under REQ-TOOLS-036 — one whose flags or structure cannot be read statically — is caught by rule 6 and by no pattern rule.

**REQ-TOOLS-040** — The starter destructive set belongs to the shipped presets only. The rule-less `unrestricted` default of REQ-TOOLS-029 does not carry it.

### 4. Permission Mode Presets

**REQ-TOOLS-041** — Exactly three presets ship: `restricted`, `ask`, `autonomous`. This requirement is the product's single definition of the permission-mode preset vocabulary: those three spellings are the whole of it, they are stable persisted values, and no requirement in any other domain holds a second copy of the vocabulary. A requirement that needs it cites this one — together with REQ-TOOLS-046 for how a configured name resolves to a preset, REQ-TOOLS-047 for the restrictiveness ordering, and REQ-TOOLS-067 for the downgrade of a permissive mode — and states only what it adds. The default decision each preset carries is stated by that preset's own requirement — `restricted` deny (REQ-TOOLS-042), `ask` ask (REQ-TOOLS-043), `autonomous` allow (REQ-TOOLS-044) — and is not restated elsewhere either. Rule families are composed into each preset in a fixed order — (1) fetch/egress rules, (2) destructive command rules, (3) network-command classification rule, (4) read-only rules. That order is behaviourally load-bearing: resolution stops at the first matching rule (REQ-TOOLS-019), so a narrow family placed after a family that matches more broadly would never be reached.

**REQ-TOOLS-042** — `restricted`: default decision deny. Rules: the fetch pair, all nine destructive rules, `restricted:network-command` (deny, matching the network-command pattern set), `restricted:read-outside-workspace` (ask; read-only tools with paths outside the workspace), `restricted:read-only-tool` (allow). Semantics: in restricted mode the four ask-class starter rules loosen the flat deny into a prompt for those categories.

**REQ-TOOLS-043** — `ask`: default decision ask. Rules: the fetch pair, all nine destructive rules, `ask:network-command` (ask), `ask:read-only-tool` (allow — reads allowed regardless of path).

**REQ-TOOLS-044** — `autonomous`: default decision allow, carrying only the five destructive deny rules and deliberately no ask rules (unattended they would resolve to fail-safe deny; attended they would prompt in the mode chosen to avoid prompts; and an ask would invert the restrictiveness ordering). The workspace file boundary in autonomous mode is enforced by path-fence errors (REQ-TOOLS-129), not prompts. **REQ-TOOLS-045** — Each supervised preset (`restricted`, `ask`) carries a fetch rule pair ordered ahead of everything else that could match `fetch`: `<preset>:fetch-remote-host` (ask; network tool class; matches URLs whose host is outside the local machine; described as network egress to an outside host) then `<preset>:fetch-local-host` (allow; network access confined to this machine). A URL that cannot be parsed counts as remote and therefore asks.

**REQ-TOOLS-046** — The default preset is `ask`. This requirement is the product's single definition of how a configured mode name resolves to a preset, including the shipped default; no requirement in any other domain holds a second copy of the rule or of the default.

**REQ-TOOLS-050** — An `ask` suspends exactly one tool call. Other agents in the session keep running; each wait is identified by its own request id rather than by the conversation it came from.

**REQ-TOOLS-051** — Approval options are exactly: approve once, approve for the session, deny. Wait terminal states are exactly: resolved, cancelled, timed out.

**REQ-TOOLS-052** — Approval responses map to decisions as follows:

- cancelled → deny, source `cancelled`, reason ending `…the approval request was cancelled.`
- approve once → allow, rule id `approval:once`, source `user-once`, reason `The user approved '<tool>' once (rule '<pending rule>' asked).`
- approve for session → allow, rule id `approval:session`, source `user-session`, and a session rule is added per REQ-TOOLS-024.
- deny → deny, source `user-deny`, reason ending `…the user denied the request.`

### 6. Headless / Unattended Resolution

**REQ-TOOLS-065** — `runtime.headless_approval_policy` ∈ {`deny` (default), `abort`}; unrecognized values behave like `deny`. Under `deny`, the single tool call is refused and the agent may re-plan. Under `abort`, the call is refused and the session's registered abort hook is invoked to stop the run; if no abort hook is registered, a warning is logged and the behavior degrades to `deny`. Reasons state that no approval UI is available in this host (the abort variant adds that the headless approval policy aborts the run); decision source is `headless-policy`.

**REQ-TOOLS-066** — When no approval resolver is wired at all, a built-in fail-safe resolver answers every `ask` with deny, source `headless-policy`, and a reason stating no interactive approval is available so the request was denied fail-safe.

### 8. Permission Audit Trail

**REQ-TOOLS-078** — Permission decisions are recorded into the session's permission audit (REQ-SESSION-137), in the order the decisions were taken. Where that audit is held is the sessions domain's and is not fixed here. Once recorded, an entry's content is never altered and no entry is ever inserted ahead of an entry already present; the only permitted removal is retention trimming, which keeps the 5000 most recent entries (REQ-SESSION-133), so beyond that count each new entry displaces the oldest one still held, and the record must retain enough to say that entries were dropped. A reader therefore sees a suffix of the session's decision history, in the order the decisions were taken, every retained entry exactly as it was recorded — every field, adding nothing and dropping nothing.

That last guarantee has to survive leaving this application, or the audit is only as trustworthy as the surface rendering it. The audit MUST therefore be obtainable as a file the user chooses, yielding every field of every entry to a stock parser on a machine carrying none of this product's code, with the order preserved, nothing omitted, and a statement of how many entries the retention cap dropped (REQ-SESSION-199, on the pattern REQ-EVENTS-166 fixes). This is the record a user consults precisely when they do not trust what the interface tells them, so no part of it may be reachable only through this application. The export is a user-initiated action producing a file and never a way to watch a run (REQ-SESSION-071).

**REQ-TOOLS-079** — A decision entry carries: `timestamp` (ISO-8601 UTC), `session_id`, `agent_id`, `persona`, `tool_name`, `decision` (`allow`|`ask`|`deny`), `rule_id`, `source` (a decision-source value per REQ-TOOLS-028), `summary` (the request summary of REQ-TOOLS-016 — `<tool>: <redacted command facet>`, or `<tool>(<sorted argument keys>)` for a call with no command facet), `reason`, plus `request_id` only when the decision resolved a raised approval, plus the entry identifier this requirement fixes below. Beyond the redacted command facet carried inside `summary`, an entry contains no argument values. That absence is not incidental bookkeeping: it is the property that makes the audit safe to hand to the user as a file, and it is the property the export test of REQ-TOOLS-190 turns on. A change to this requirement that let argument values into an entry would withdraw the audit's export with it.

An entry MUST also be identifiable. The permission audit is one of the three record kinds a locator may name, and REQ-EVENTS-056 — which fixes the locator's form, the closed set of record-kind tokens and the token that names this record — makes **this requirement the only place the identifier of an audit entry may be fixed**, and forbids a locator naming a kind whose own requirement gives its entries none. The obligation is therefore stated here: the audit MUST give every decision entry an identifier that distinguishes it from every other entry the audit holds for that session — the mode-change entries of REQ-TOOLS-082 included, since those are interleaved with the decision entries in the same audit — that does not change once the entry has been recorded, and that is not reused after the retention trimming of REQ-TOOLS-078 has displaced the entry that held it, so a locator written earlier can never come to name a different decision than the one it was written for. A locator whose entry has since been displaced simply does not resolve, which REQ-EVENTS-056 states is an ordinary outcome rather than damage.

**That identifier is a field of the entry.** It is carried inside the entry itself and not beside it, which is why the field set stated above names it. The reason is the export and not tidiness: REQ-EVENTS-056 requires a locator naming an audit entry to resolve **through the export**, on a machine carrying none of this product's code and with nothing beyond a stock parser, and an identifier that is not part of the entry does not survive the entry being exported. A locator this product wrote would then be unresolvable at exactly the point where the audit stops being a rendering this application controls and becomes a record the user holds — which is the whole reason the audit is an audit rather than a screen (REQ-TOOLS-078, REQ-SESSION-199). It follows that the identifier MUST be carried under the same field in every entry the audit holds and in every export of it, so that a reader on such a machine can tell which field of an exported entry a locator's record id names; an identifier present in an export but not locatable as the identifier resolves nothing.

This fixes where a **decision** entry's identifier lives and nothing else. The mode-change entries of REQ-TOOLS-082 are unaffected and their field set is unchanged: no locator names one, REQ-EVENTS-056's record ids are the identifiers of the entries locators name, and the obligation above is that a decision entry be distinguishable from every other entry the audit holds — which is satisfied without giving an identifier to an entry no locator can name.

**The no-argument-values property above is untouched, and this MUST NOT be read as an opening to it.** The identifier MUST NOT be derived from, and MUST NOT disclose, any argument of the call the entry decided: it identifies an entry and conveys nothing about what the call contained. The audit's eligibility for export under REQ-TOOLS-190's redaction-safety test is therefore unaffected by the identifier being carried in the entry.

**REQ-TOOLS-080** — Every entry is recorded against the session whose call was decided, and never against another session's. An agent that serves one session and then another records each entry against the session it was serving when that decision was taken. Each entry names the agent id and persona of the agent whose call produced it. A decision taken outside every registered session records no entry and reports no error, so a one-off agent leaves no audit entry behind. Where the audit is held is REQ-TOOLS-078's and is fixed nowhere in this document; what this requirement fixes is which session an entry belongs to, which is unchanged by where the audit lives.

**REQ-TOOLS-081** — Per-entry side effects: a `deny` additionally records a `permission_denied` issue (severity warning; actor = agent id or persona; message `Permission denied for <summary or tool>: <reason>`; evidence reference locating the decision in the permission audit, which is the locator of REQ-EVENTS-056 and nothing else: its form, the closed set of record-kind tokens, and which of those tokens names the permission audit are all fixed there and are deliberately not spelled again here, so that the token cannot drift between the record that emits this reference and the record it points into; its record id is the entry identifier REQ-TOOLS-079 is obliged to give; metadata: tool, rule, source, persona). A `user-once`/`user-session` approval emits a `permission_approved` timeline event (`The user approved <summary or tool>`). Every entry also publishes a `permission.decision` event on the session event bus.

**REQ-TOOLS-082** — A mode change writes an entry into the same audit as the decision entries, interleaved in write order, so a reader taking that audit in the order it was recorded — on a surface that renders it, or in the export of REQ-TOOLS-078 — can determine which mode governed any decision by taking the nearest preceding mode-change entry: `{timestamp, event: "permission_mode_change", session_id, agent_id: <source>, requested_mode, effective_mode, previous_mode, source, reason, skipped_personas: [...]}`. `skipped_personas` is always present, including when empty, so an entry that reached every agent is distinguishable from an entry that simply omits the field. An accompanying `permission_mode_changed` timeline event reads `Permission mode changed from '<prev>' to '<effective>'` optionally followed by the reason and, when applicable, `(not applied to persona-pinned agents: a, b)`.

**REQ-TOOLS-083** — The `permission.decision` stream event carries `tool_name`, `decision`, `source`, `rule_id`, `summary` (the request summary of REQ-TOOLS-016), and `request_id`, which is empty whenever the decision was never put to a person — consumers must read an empty `request_id` as unpaired. No published `permission.decision` event ever carries an unmasked credential in `summary`.

### 9. Network Egress Policy and the fetch Tool

**REQ-TOOLS-084** — The order in which the denied list, the allowed list and the configured default disposition are consulted, and the consequence that a denial outranks a broader allow wildcard, are fixed by REQ-SANDBOX-003 and REQ-SANDBOX-014; this domain holds no copy of them. What it relies on them for is that classifying a host yields exactly one of the three dispositions before the `fetch` tool opens any connection. This domain adds only the fail-closed reading it needs: a host that cannot be read (REQ-TOOLS-086) is denied, and no unreadable or ambiguous input is ever classified as allowed.

**REQ-TOOLS-085** — Host patterns support exactly one wildcard form: a single leading `*.`. `*.example.com` matches one or more leading labels (`api.example.com`, `a.b.example.com`) but not bare `example.com`, and not a different domain that merely ends with the same characters — matching compares whole DNS labels, never raw substrings. A `*` anywhere else raises an error at pattern build (message naming the pattern and the only supported form) rather than matching literally or silently matching nothing.

**REQ-TOOLS-086** — REQ-SANDBOX-006 owns host normalization for matching and classification, including unbracketed canonical IPv6. Brackets are added only when constructing a URL authority. When no host can be read, the canonical result is empty and callers MUST classify it as unknown and deny it under REQ-SANDBOX-008.

**REQ-TOOLS-087** — "Local" means genuine loopback only: the names {`localhost`, `localhost.localdomain`, `ip6-localhost`} and loopback IP addresses. Private-range and link-local addresses (e.g., `169.254.169.254`, internal `10.x`) deliberately count as remote — they are exactly what a policy gates. A hostless or unreadable URL counts as remote.

**REQ-TOOLS-088** — Configuration. The egress disposition key `runtime.network_egress_policy`, its accepted values, its shipped default and the matching of a stored spelling are fixed by REQ-SANDBOX-001 and REQ-SANDBOX-002; the two host-list keys `runtime.network_allowed_hosts` and `runtime.network_denied_hosts`, their defaults and their load-time normalization are fixed by REQ-SANDBOX-003 and REQ-SANDBOX-004. This domain holds no copy of any of them. What it relies on those requirements for is that the disposition reaching the `fetch` tool is always one of a closed set of three, so REQ-TOOLS-084 never has to decide what an unrecognized disposition means, and that the two host lists arrive already normalized, so the pattern matching of REQ-TOOLS-085 sees no leading or trailing whitespace, no upper case and no blank entry.

**REQ-TOOLS-089** — The egress policy carried by a run's fetch tool is always built from that run's own runtime configuration; two runs in one process never lend each other an allow-list. Tightening the configured host lists observably changes the policy the agent's fetch tool enforces. A fully permissive policy exists only as the fallback for callers with no configuration at all.

**REQ-TOOLS-090** — `fetch` classifies a host before any connection to it is opened — for the URL the agent supplied and again for every redirect target — so no request and no redirect ever reaches a host the policy denies, and a permitted host cannot hand the request on to a denied one. A single call follows at most 20 redirect hops; a chain that would exceed that returns failure kind `too_many_redirects`.

**REQ-TOOLS-091** — The `ask` disposition belongs to the permission gate, not the fetch executor: by execution time the gate has already resolved the ask for the host the agent named, and that host is pre-seeded as permitted. A redirect onto an unseen host that classifies as `ask` is refused (there is no way to prompt mid-request) with an instruction to request the final host directly. A redirect staying on an already-permitted host (path change, http→https) is not re-gated.

**REQ-TOOLS-092** — Fetch refusals and failures are machine-readable with stable kinds: `egress_denied` (requested host denied), `egress_redirect_denied` (hop denied or ask-on-hop), `egress_policy_error` (a pattern could not be applied — refused, not ignored), `too_many_redirects`, `invalid_request` (the call itself was malformed and no connection was attempted; what makes a request malformed is REQ-SANDBOX-020's and is not restated here), `timeout`, `network_error`, `http_error` (status ≥ 400, with detail `HTTP request completed with status code <n>.` and the observation marked as an error). This requirement is the product's single definition of the fetch failure-kind vocabulary: the set is closed and is exactly those eight spellings, and no requirement in any other domain holds a second copy of it — a requirement that needs the vocabulary cites this one and states only what it adds, such as the `error_class` value or the detail content that accompanies a kind. `invalid_request` carries the same spelling as the terminal observation's member of the same name (REQ-TOOLS-112, REQ-SANDBOX-087), so one word means one thing across the product. The first four kinds are policy refusals — something for the agent to re-plan around — and are distinguishable as a group from `timeout` and `network_error`, which are transient transport faults worth retrying, and from `invalid_request`, which is a fault in the call. Refusals name the blocked host and the governing setting, e.g. `Network egress to <host> was refused: the egress policy (runtime.network_egress_policy) resolves that host to 'deny'.` Error observations include a `[fetch_diagnostic]` JSON block.

**REQ-TOOLS-093** — Fetch action surface: `url` (required), `max_lines` (default 1000), `from_line`/`to_line` (line-range selection), `timeout` (per-call override; otherwise the configured default `runtime.tool_call_timeout`, default 30 s (REQ-CONFIG-115); with no configuration at all the executor's own fallback is 10.0 s). Observation metadata: `url`, `final_url`, `status_code`, `content_type`, `truncated`. The tool returns raw text (including raw HTML) truncated to `max_lines`; a single call retrieves a single resource.

**REQ-TOOLS-094** — Terminal commands that reach the network are recognized by a set of leading-token patterns evaluated under REQ-TOOLS-033. This requirement is the product's single definition of that catalogue: the set is closed and is exactly the patterns listed below, no requirement in any other domain holds a second copy of them, and a requirement that needs the catalogue cites this one and states only what it adds. The recognizer is a pattern matcher in the sense of REQ-TOOLS-038, so a command line is first cut into segments under REQ-TOOLS-035 and each segment is judged on its own leading tokens; one matching segment settles the whole line, and `date && curl https://example.com` is therefore network-reaching. Each pattern is matched under the token rules of REQ-TOOLS-033: matching is by whole tokens, so `curl` matches the segment `curl https://example.com` but never `curling`, and a trailing `*` stands for zero or more further tokens, so a bare `curl` or a bare `npx` submitted with no arguments matches. Requiring at least one further token would leave the trivial bypass of splitting a command across an interactive invocation. The catalogue is a set and not a sequence: the grouping and ordering below are for reading convenience only, carry no meaning, and establish no first-match precedence among the patterns. The patterns:

- transfer and remote-shell clients: `curl *`, `wget *`, `http *`, `https *`, `ssh *`, `scp *`, `sftp *`, `rsync *`, `nc *`, `ncat *`, `telnet *`, `ftp *`;
- version control: `git push *`, `git pull *`, `git fetch *`, `git clone *`, `git remote *`, `git ls-remote *`, `git submodule update *`, `gh *`;
- Python packaging: `pip install *`, `pip download *`, `pip index *`, `pip3 install *`, `pip3 download *`, `uv add *`, `uv sync *`, `uv lock *`, `uv pip install *`, `uv tool install *`, `uv publish *`, `poetry add *`, `poetry install *`;
- JavaScript packaging: `npm install *`, `npm i *`, `npm ci *`, `npm update *`, `npm audit *`, `npm publish *`, `npx *`, `yarn add *`, `yarn install *`, `yarn up *`, `yarn publish *`, `pnpm add *`, `pnpm install *`, `pnpm update *`, `pnpm publish *`, `pnpm dlx *`;
- other language toolchains: `cargo add *`, `cargo fetch *`, `cargo install *`, `cargo update *`, `cargo publish *`, `go get *`, `go install *`, `go mod download *`, `go mod tidy *`;
- system and container package managers: `brew install *`, `brew update *`, `brew upgrade *`, `brew fetch *`, `apt install *`, `apt update *`, `apt upgrade *`, `apt-get install *`, `apt-get update *`, `apt-get upgrade *`, `docker pull *`, `docker push *`.

A command line no segment of which matches any of these patterns is not recognized as network-reaching — `ls -la`, `git status`, `pytest -q`, `cat notes.txt`, and an inline `python -c '…'` snippet all classify as local — and nothing is recognized by inference from a listed spelling. Presets attach the recognizer as `<preset>:network-command` — deny in `restricted`, ask in `ask`, absent from `autonomous` — and that rule id is what appears in the refusal text and in the audit entry. The recognizer is a permission decision about the command string, not enforcement: outside the sandbox nothing prevents a command the recognizer misses from reaching the network. Kernel-level egress control for terminal commands exists only inside the sandbox and is a single on/off switch (REQ-TOOLS-117); per-host filtering of terminal traffic is out of scope for this specification. Because the recognizer is a permission heuristic and never an enforcement boundary, the closed list above is a complete specification of the rule's behavior rather than a claim to catch every network-reaching command; an escaping command line is instead caught, where it is statically unreadable, by the escalation matcher of REQ-TOOLS-038.

### 10. Terminal Tool — Foreground Execution

**REQ-TOOLS-095** — The tool name is `terminal`. Its annotations declare it not read-only, potentially destructive, non-idempotent, and open-world. Creating it with a nonexistent working directory fails with `working_dir '<d>' is not a valid directory`.

**REQ-TOOLS-096** — Action schema: `command` (string; an empty string polls for more output after a soft pause; with `is_input=true` it may instead be a special key: `C-c`, `C-d`, `C-z`, any `C-<letter>`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `HOME`, `END`, `PGUP`, `PGDN`, `TAB`, `ESC`, `BS`, `ENTER`), `is_input` (bool), `timeout` (float ≥ 0, hard wall-clock), `reset` (bool), `background` (bool), `session_id` (format `ts_XXXXXXXX`), `session_action` (`query`|`kill`|`send_input`|`send_signal`|`list`), `signal` (`SIGTERM`|`SIGINT`|`SIGKILL`|`SIGHUP`), `input_data` (string). One command per call; sequences are expressed with `&&`/`;`.

**REQ-TOOLS-097** — A foreground command is bounded in two ways, and whichever bound is reached first governs the call. (1) A hard wall-clock timeout: the call's own `timeout` when it supplies one, otherwise `runtime.shell_command_timeout` (default 100 s, REQ-CONFIG-116) for every action that is not keystroke input. On reaching it the entire process tree the command started is terminated, the terminal session is restarted, and the observation of REQ-TOOLS-099 is returned; everything the shell had accumulated — working directory, exported variables, aliases, background jobs — is gone, and the observation says so. (2) A soft pause: when the call supplies no `timeout` and the command has produced no output for 30 seconds — the no-output window, fixed for every backend and platform — the call returns early under REQ-TOOLS-098 with exit code −1 while the process keeps running. The soft pause applies only to a call that supplied no `timeout`. Supplying one is the agent declaring how long it is prepared to wait, so such a call is bounded by its own hard timeout alone and never returns early for silence.

Captured foreground output is capped at 100,000 characters per call. When a command produces more, the capture is truncated from the oldest end so the most recent output always survives, and the truncation is stated in the observation's detail and recorded as `output_truncated: true` in the `[terminal_diagnostic]` block (REQ-TOOLS-100); an untruncated capture omits that key.

**REQ-TOOLS-098** — A soft-paused call returns exit code −1 with no `failure_kind`, while its process keeps running. When capture is empty, the observation MUST state the elapsed no-output window under REQ-TOOLS-097 and the active backend's capture semantics. A merged PTY backend MUST explain that both stdout and stderr are captured, that the process may still be running, and that the agent can poll with an empty `command` or interrupt with `C-c` and `is_input=true`. Advice to re-run with `2>&1` is permitted only when the active backend excludes stderr from capture. Every observation MUST render `[terminal_output]` followed by captured text or `(no output)`.

**REQ-TOOLS-099** — Hard-timeout observation contract: `exit_code` 124, `timeout` true, `is_error` true, `failure_kind` `"timeout"`, `timeout_seconds`, `kill_status` ∈ {`session_reset`, `reset_failed`}, `session_reinitialized` (bool), `backend` (REQ-TOOLS-100), and a detail stating the command exceeded its timeout, the session was forcibly restarted to terminate the process tree, and shell state was lost (with failure variants embedding the underlying error). Those two values are the two outcomes of the one kill path this product has — restarting the session succeeded, or it did not. Two further values, which named the kill path of a second terminal backend, are withdrawn together with that backend (REQ-TOOLS-100): no observation carries them and no consumer may expect them.

  > **Narrowed by [`PD-TOOLS-001`](../product/directives.md#pd-tools-001), 2026-09-18.** The contract above
  > is untouched: the tree is still terminated, the session is still restarted, and the observation still
  > states that shell state was lost. The directive names one thing that happens *after* the restart: the
  > shell's working directory and exported variables, snapshotted before the respawn, are re-applied to the

**REQ-TOOLS-100** — Observation `failure_kind` values are exactly {`timeout`, `invalid_request`, `execution_error`, `sandbox_unavailable`}; `backend` is stamped on every observation and names the terminal backend that ran the command. Exactly one terminal backend ships, and the name it stamps is `single-session`. A second name this field once carried is withdrawn together with the pooled backend it described: nothing ever stated when that backend was used, what selected it, or whether it had to exist, it could not be provided on the platform whose shell REQ-TOOLS-104 mandates, and it was required to be observationally identical to the shipped backend in every respect but its own name. The field itself is deliberately kept rather than removed, so that adding a backend in a later release changes what this field says and not the shape of an observation; a consumer therefore reads `backend` as a name to record and report, and must not treat the single value shipped today as a closed vocabulary. Every observation carries a `[terminal_diagnostic]` JSON block (sorted keys, null-valued keys dropped) including backend, command, detail, error class, exit code, failure kind, kill status, outcome kind, outcome severity, output-truncated (only when the capture was truncated under REQ-TOOLS-097), session-reinitialized, timeout, timeout seconds, warnings, working directory, and session fields when applicable. Output captured before a hard timeout is labeled `[partial_terminal_output]` instead of `[terminal_output]`.

**REQ-TOOLS-101** — Request validation failures return `invalid_request` observations (the fixed compatibility error class `ValueError`, independent of implementation language) for: `reset=true` with `is_input=true` (`Cannot use reset=True with is_input=True in the same terminal call.`); `background=true` with `is_input=true` or `reset=true`; `background=true` with an empty command (`A command is required when background=True.`); an unknown `session_action`; and `send_input` without `input_data`. `failure_kind` and outcome kind are the stable product codes. Schema-level refusals for these cases MUST preserve this diagnostic contract through the tool gate.

**REQ-TOOLS-102** — `reset=true` creates a fresh session before running anything. An empty command with reset returns a confirmation observation (text stating the session has been reset and all previous environment variables and session state cleared; command label `[RESET]`; exit code 0). With a command, the reset note is prepended and the command label becomes `[RESET] <command>`.

**REQ-TOOLS-103** — A terminal call always returns either an ordinary observation or a structured error observation. A failure of the terminal backend never surfaces to the agent as a partial or malformed observation, whatever the backend is (REQ-TOOLS-100) and however it failed. Any failure occurring before the command completes is returned as an `execution_error` observation whose detail states that terminal execution failed before completion and quotes the underlying error. The bounded recovery ladder this requirement previously fixed — a limited number of backend recoveries inside a rolling window, after which the call reported that the backend's server might be unreachable — is withdrawn with the pooled backend it belonged to (REQ-TOOLS-100): it described a recovery path only that backend had, and named a separate server the shipped backend does not run. What survives is the guarantee, which was never the ladder's: the agent's next observation is always well-formed and always says what went wrong.

**REQ-TOOLS-104** — On Windows the terminal runs commands through PowerShell rather than bash, and the tool description says so: it must warn that a bash heredoc never returns and that bash arrays, `[[ … ]]`, and `source` are unavailable, while stating that `&&`, `;`, `2>&1`, and `$env:VAR` work. Availability of this backend is decided solely by whether a supported PowerShell interpreter (`pwsh` or `powershell`) is present on the host, never by how quickly anything on the host responds: two hosts with the same software installed report the same availability whether idle or fully loaded, and a slow host is never reported as lacking PowerShell.

**REQ-TOOLS-105** — Visibility: an executing command is displayed as `$ <command>` in the status pane and as `terminal: $ <command>` in the transcript, with timeout/reset/input flags visible; the action's own rendering is `$ command [timeout: Ns] [reset terminal] [background] [session: id] [action]`.

**REQ-TOOLS-106** — The terminal tool must load and register successfully however the application process was started and whatever that process's own standard output and standard error are attached to — a console, a pipe, or nothing at all — and whether or not those streams report a character encoding. What the agent observes is identical in every one of those cases: the same tool surface and the same observations. A launch context in which the application's own streams carry no encoding information is never a reason for the tool to be missing from an agent's tool set (REQ-TOOLS-004), and never changes the encoding of anything the tool captures from a command it runs.

**REQ-TOOLS-187** — Foreground terminal concurrency is fixed by the shell session, not by the backend. Each terminal session runs at most one foreground command at a time: a second foreground call against a session whose previous foreground command has not returned waits for it, so a session's shell state (working directory, exported variables) is never mutated by two commands at once. Terminal sessions belonging to different agents run their foreground commands concurrently, bounded only by host resources. Because the rule attaches to the shell session and not to the backend, it does not vary with the value of `backend` (REQ-TOOLS-100): an observer given the same sequence of calls must see the same ordering, the same observations and the same shell state whichever backend ran them, so a backend added in a later release cannot change foreground concurrency and the backend name stays the only thing about an observation a backend gets to decide. Background sessions (section 11) are unaffected — they never occupy a terminal session and always run concurrently, up to `runtime.shell_max_background_sessions`.

### 11. Terminal Tool — Background Sessions

**REQ-TOOLS-107** — `background=true` spawns the command in its own OS subprocess (shell-interpreted; stdout and stderr merged to a pipe; stdin piped; working directory = the tool's working dir; its own process group on POSIX) and returns immediately with text `Background session started: <ts_XXXXXXXX>` plus the command, `session_status="running"`, and exit code 0. Session ids are `ts_` followed by 8 hexadecimal characters derived from the command and a monotonic timestamp, collision-checked.

**REQ-TOOLS-108** — Limits and defaults: maximum concurrent background sessions from `runtime.shell_max_background_sessions` (default 20, range 1–64 — the key, its default and its range are REQ-CONFIG-116's and are not restated here) — exceeding it is an `execution_error` reading `Maximum background terminal sessions (<n>) reached. Kill or wait for existing sessions before starting new ones.` Per-session wall-clock timeout defaults to `runtime.shell_background_timeout` (default 3600 s, minimum 1) unless the action supplies one. Output is buffered up to 1 MB per session and truncated silently from the oldest end, with the read cursor adjusted so polling stays consistent.

**REQ-TOOLS-109** — Background termination protocol: SIGTERM, then a grace wait of up to 5 seconds (returning as soon as the process exits), then SIGKILL. A background timeout sets status `timeout` and exit code 124; an explicit kill sets status `killed` and exit code −1. The status vocabulary is exactly {`running`, `completed` (exit 0), `failed` (nonzero), `killed`, `timeout`}.

**REQ-TOOLS-110** — Session actions: `query` (the default when `session_id` is set) returns only output new since the last poll (placeholder `(no new output since last poll)`) plus status and exit code; `kill` returns the final output; `send_input` writes bytes to stdin (result `Sent <n> byte(s) to session <id>.`; a closed pipe logs a warning); `send_signal` sends SIGTERM/SIGINT/SIGKILL/SIGHUP (default SIGTERM; result `Sent <sig> to session <id>.`); `list` needs no session id and returns an aligned text table plus structured entries `{session_id, command, status, exit_code, started_at (ISO-8601)}`, with a per-row status glyph (`▶`/`✓`/`✗`). An unknown session id yields `invalid_request` with `Unknown background session: '<id>'`.

> **Extended by [`PD-TOOLS-010`](../product/directives.md#pd-tools-010), 2026-10-06.** `send_signal SIGINT` stops
> a background session whose command takes SIGINT's default: where the session's shell is `dash` on Linux, a
> SIGINT its fork window lost is sent once more to the command it cost. Every action above is unchanged.

**REQ-TOOLS-111** — Executor teardown MUST terminate its terminal-tool process trees, including background terminal sessions, and close every terminal resource it holds. Application shutdown and crash cleanup MUST apply that scope to owned terminal-tool processes. Hook descendants follow REQ-HOOKS-033's explicit survival exception; hook help MUST disclose that exception. Hook timeout and bounded-output collection remain governed by the hooks domain.

### 12. Terminal Outcome Classification

**REQ-TOOLS-112** — Every terminal observation carries an `outcome_kind` from {`success`, `shell_failure`, `suspicious_success`, `soft_pause`, `timeout`, `invalid_request`, `execution_error`, `background_running`, `background_terminal`, `sandbox_unavailable`} and an `outcome_severity` from {`info`, `warning`, `error`}. The classification is decided by the following tests in order, the first one that applies deciding both fields:
1. a `failure_kind` is present — `timeout` → `timeout` / error; `invalid_request` → `invalid_request` / warning; `execution_error` → `execution_error` / error; `sandbox_unavailable` → `sandbox_unavailable` / error;
2. the observation reports a background session — status `running` → `background_running`, any terminal status of REQ-TOOLS-109 → `background_terminal`;
3. exit code −1 → `soft_pause` / warning;
4. a non-zero exit code → `shell_failure` / error;
5. exit code 0 with at least one output-derived warning from REQ-TOOLS-113 → `suspicious_success` / warning;
6. otherwise → `success` / info.

`background_running` always carries severity `info`: a session that is still running has reported nothing to be concerned about. `background_terminal` takes its severity from the session's final status of REQ-TOOLS-109 — `completed` → `info`, `killed` → `warning` (the agent or the user ended it deliberately, so it is neither a clean finish nor a fault), and `failed` or `timeout` → `error`. Severity therefore never asserts a problem the status does not report, and a background failure reads at the same severity a foreground failure of the same shape would.

**REQ-TOOLS-113** — Three independent checks run over the output of a command that exited 0. Each contributes at most one warning, and one or more warnings makes the observation `suspicious_success`:
- **Literal failure markers**, searched case-insensitively anywhere in the output, in this fixed order: `Traceback (most recent call last):`, `ERROR: file or directory not found`, `no tests ran`, `AssertionError`, `FAILED ` (the trailing space is part of the marker). The earliest marker in that order that is present produces the single marker warning, whose text names the marker that matched; further markers present in the same output add nothing.
- **A reported error count**: a line of the form `Found <n> error` or `Found <n> errors` where `<n>` is not zero, matched case-insensitively like the other two checks, so `found 3 errors` warns exactly as `Found 3 errors` does. `Found 0 errors` must not warn, in any casing.
- **A test-runner failure banner**: a line consisting of one or more `=` characters, then text, then one or more `=` characters, whose text contains `failed` case-insensitively.

Independently of exit code, a pipeline check adds the warning `Pipeline command may have hidden an upstream failure exit code.` when the command line contains `|` and the output contains, case-insensitively, any of `error:`, `failed`, `traceback`, or `no tests ran`. That warning is the only output-derived warning a non-zero-exit (`shell_failure`) observation can carry. Warnings are de-duplicated with the first occurrence keeping its position, and the resulting list appears both in the observation's `warnings` field and in the `[terminal_diagnostic]` block.

### 13. OS-Level Sandbox

**REQ-TOOLS-114** — The sandbox is opt-in per session: `runtime.sandbox_mode` ∈ {`off` (default), `workspace-write`, `read-only`}, case-insensitive. A YAML bare `off` parsed as boolean false is coerced to the string `"off"`. Unrecognized values are rejected at load and at assignment — never assumed off; the vocabulary and its validation are the ones fixed by REQ-SANDBOX-048. The desktop session dialog offers a per-session selector over exactly those three values, and a session started without touching it takes the configured value. There is no launch-time override of any kind.

**REQ-TOOLS-115** — Platform backends: macOS uses the system sandbox facility (backend name `seatbelt`); Linux and WSL2 use bubblewrap (backend name `bubblewrap`); native Windows has no backend and reports unavailable with remediation text directing the user to run inside a WSL2 distribution with bubblewrap installed, or to leave the sandbox off. Sandboxing is per-command wrapping of the command string; no containers are involved.

**REQ-TOOLS-116** — Writability model: `workspace-write` makes the workspace (or its active worktree) plus `runtime.sandbox_writable_roots` writable and the rest of the filesystem read-only; `read-only` makes nothing writable except temporary directories. `.git` and `.rotaris` stay read-only even when they sit inside a writable root, and no setting can turn that exclusion off — write access to either directory would let a run break out of, or quietly widen, its own confinement (repository hook scripts execute outside the sandbox; the configuration directory is what decides the sandbox's boundaries in the first place). Entries in `runtime.sandbox_writable_roots` must be absolute paths (POSIX or Windows spelling); a relative entry is rejected with `runtime.sandbox_writable_roots entry '<e>' must be an absolute path`.

**REQ-TOOLS-117** — Network inside the sandbox is closed by default; `runtime.sandbox_allow_network: true` opens it. The switch is binary — no per-host filtering for sandboxed terminal commands.

**REQ-TOOLS-118** — There is no silent fallback, structurally: if the sandbox cannot wrap a command, the command is not run. At session start, a session that requires an unavailable sandbox fails to start with reason and remediation; this is the canonical reading of the overlap with REQ-TOOLS-070, so the unavailable-at-start case never yields a running session. At command time, the terminal returns a `sandbox_unavailable` observation instead of executing, with exit code 126 ("found but could not be executed" — preventing the classifier from calling it a success) and detail `This session requires the OS-level sandbox, but the command could not be sandboxed and was therefore not run: <error>`. This refusal is not retryable into an unsandboxed execution path.

**REQ-TOOLS-119** — Sandbox availability is established by exercising the sandbox, never inferred from configuration: the check confirms the host platform, then the presence of the backend executable, then runs one throwaway command through exactly the wrapping that real commands go through. A trial is abandoned after 5.0 seconds. Only a clear success yields "available"; a timeout, an error, or a result that cannot be read yields "unavailable". Within one process the verdict never changes, and asking for it concurrently returns the same verdict as asking once. Three distinguishable reason-and-remediation pairs exist — unsupported platform, missing backend executable, and failed trial — and on Linux the failed-trial remediation names the kernel restriction on unprivileged user namespaces. Availability is established only by a real backend on a real host: a simulated, stubbed, or recorded backend never yields "available", and conformance to this requirement is demonstrated by running the trial, and a subsequent sandboxed command, end to end on each supported platform of REQ-TOOLS-115 rather than against a substitute.

**REQ-TOOLS-120** — Wrapping scope: only actions that introduce a new command string are wrapped — including `background=true` spawns (otherwise one flag would escape the sandbox). Keystroke input, empty output polls, and session-control actions (`list`/`query`/`kill`/`send_input`/`send_signal`) are not wrapped. `background` outranks `session_id` in both dispatch and wrap decisions, so supplying both cannot spawn unsandboxed. Retries wrap the original action exactly once — wrappers never nest.

**REQ-TOOLS-121** — The command echoed back in a sandboxed observation is the command string the agent supplied, not the wrapped form that was actually executed. The wrapper's own argument list (profile text, launcher flags) never appears in agent-visible output, so the agent cannot mistake wrapper mechanics for part of its own command and try to edit them on a retry.

**REQ-TOOLS-122** — Sandbox launch failures are re-labeled: an observation from a wrapped command with a nonzero exit, no prior failure kind, and output consisting only of sandbox-launcher-prefixed lines (`bwrap:`, `sandbox-exec:`, `sandbox_apply:`) is re-stamped `sandbox_unavailable` (error, with detail stating the sandbox failed to start so the command did not run and this is a host problem). Requiring every line to match the launcher prefix keeps failing test suites from reading as broken sandboxes. **REQ-TOOLS-123** — Sandboxed execution MUST keep standard temporary locations and basic device files usable in both modes. ### 14. Terminal Live Streaming

**REQ-TOOLS-126** — Streaming configuration: `runtime.terminal_stream_enabled` (default true; disabling costs the live view, never the command), `runtime.terminal_stream_interval_ms` (default 100, valid range 20–2000; output sampling period), `runtime.terminal_stream_buffer_kb` (default 256, valid range 0–8192; per-stream replay buffer, 0 disables replay). The sampling period is a **ceiling on batching rather than a fixed cadence**, and what may arm an earlier frame — input the user has directed at a stream whose control they have taken, and nothing else — is REQ-CONFIG-117's, which this requirement cites rather than restates. The rate at which frames reach surfaces is bounded in aggregate by REQ-MONITOR-306, across every live stream of every session delivered to every window: **the number of streams a configuration allows to be live is not a multiplier on this per-stream period.** That citation is stated here because an implementer reading this requirement alone would otherwise build per-stream sampling with no aggregate at all.

**REQ-TOOLS-127** — A foreground command's live output is published on a stream named `fg:<scope>`, where `<scope>` is the identifier of the run the command belongs to, or the literal `root` when the command belongs to no run. A background session publishes on `bg:<session_id>` using its `ts_XXXXXXXX` id. Frames are typed `delta` (the text appended since the previous frame), `screen` (a complete replacement of the displayed text), or `meta`. Streaming changes nothing the agent sees: with or without a consumer attached, and whether or not publishing succeeds, the command still runs to completion and the observation returned is identical — the only detectable difference is whether a live preview existed. A completed stream — foreground and background alike — ends with a `screen` frame whose text equals the observation's final output text, so the live view finishes on the same text the observation reports rather than on a partial capture, and the stream is then closed carrying the command's exit code. That closing frame is a **literal replacement of the displayed text and carries an explicit marker saying that it is one**: its text is plain on the terms this requirement already fixes — capped, and truncated from the oldest end — and it is the only frame of a stream of which any of that is true. Every earlier frame stays faithful to what the command actually wrote, which is what REQ-SHELL-095 and REQ-SHELL-098 need in order to present a character grid with cursor addressing, alternate-screen fidelity, per-cell attributes and sixteen colours. **The two bind different instants and therefore do not conflict**: those requirements govern the stream while the process is running, and this frame is the one emitted after it has exited — when there is no cursor to paint (REQ-SHELL-098), no alternate screen left to be in, and no further output to attribute to a cell.

**REQ-TOOLS-128** — Displays can talk back through a registered stream-control channel — send-keys, resize, and interrupt for foreground; send-keys, interrupt (SIGINT), and kill for background — without knowing what drives the stream. A stream info record carries the command, a running flag, start time, exit code, and a `truncated` flag set once replay frames were dropped.

### 15. Workspace File Tools and the Path Fence

**REQ-TOOLS-129** — A central workspace-boundary check governs file access: relative paths resolve against the workspace root; the candidate is resolved to its real path (following symlinks and junctions, so a link that escapes the root resolves outside and is rejected); a path outside the root fails with `Path '<resolved>' is outside workspace root '<root>'` unless the outside-workspace opt-out is enabled.

**REQ-TOOLS-130** — The opt-out is `runtime.allow_outside_workspace` (default false). It is set through the layered YAML configuration surface or through the confirmed desktop control of REQ-TOOLS-191, and by no other means: no launch-time override, no per-run flag, no environment variable ever turns it on. It governs the file tools and the permission gate's workspace-root scoping.

**REQ-TOOLS-131** — The desktop status strip always shows a file-access flag: `workspace-scoped` normally, `outside-workspace!` when the opt-out is on, with tooltip/accessible text explaining whether agents may read and write outside the workspace folder.

**REQ-TOOLS-132** — `read_file` and `write_file` share the following behavior. A location designated an additional read-only root can be read even though it lies outside the fence of REQ-TOOLS-129, and every write to one is refused; the exception covers reads only. A file counts as binary when a NUL byte appears within its first 8192 bytes. Text is decoded as UTF-8 and, failing that, as latin-1, so a read never fails for encoding reasons alone. Content hashes reported to callers are SHA-256. A write is atomic: a reader running concurrently with a write sees either the whole previous content or the whole new content, never a partial file, and a write interrupted part-way leaves the previous content in place. For each path the 10 most recent writes stay available to `undo` (REQ-TOOLS-135). An additional read-only root is designated by the configuration key `runtime.additional_read_only_roots`, a list of absolute paths (POSIX or Windows spelling) defaulting to empty; a relative entry is rejected at load and at assignment with `runtime.additional_read_only_roots entry '<e>' must be an absolute path`, matching the rule and message shape of `runtime.sandbox_writable_roots` (REQ-TOOLS-116). Configuration is the only designation: no launch-time flag and no built-in list of locations exists, so nothing outside the workspace is readable unless the user wrote it into the configuration. A path under such a root is readable exactly as REQ-TOOLS-129 would allow one inside the workspace; every write to one is refused with the path-fence error even when `runtime.allow_outside_workspace` is on, and the roots grant nothing to the search tools of section 16, which stay workspace-confined.

**REQ-TOOLS-133** — Read-before-write: editing a file never read through this engine instance is rejected with `You must read <rel> before editing it. Call read_file(path="<rel>") first, then retry your edit.` Every successful write records the new content as read, so consecutive edits work.

**REQ-TOOLS-134** — `read_file` contract: accepts `path` (with `file_path` accepted as an alias), `offset` (1-based, default 1), `limit` (default 2000 lines), and `grep` (regex filter, with `grep_context` default 3; matching lines prefixed `>`, groups separated by `---`, headed by `N match(es) for '<pattern>':` or `No matches for pattern …`). Content is returned line-numbered (`N: line`) with a metadata header `[path: … | total_lines: … | shown: lines A-B | truncated: true]`. Output is capped at 30,000 characters with a continuation hint `(Output capped at ~30000 chars. <n> more lines. Use offset=<k> to continue.)`. Reading a directory returns an entry listing (subdirectories suffixed `/`, entries whose name is one of the ignore components of REQ-TOOLS-140 skipped, `(empty directory)` placeholder). Binary files are rejected (`Binary file (<n> bytes). Cannot display content.`). A missing path returns a recovery message containing a listing of the parent directory and up to 5 close-match suggestions — the names scoring at least 0.45 under the similarity function of REQ-TOOLS-188, comparing the requested base name against each candidate base name after lower-casing both, listed highest score first with ties broken by ascending name.

**REQ-TOOLS-135** — The `write_file` action names its operation selector `operation`; the argument name `command` is deliberately not used for it, so a `write_file` call never supplies a command facet (REQ-TOOLS-015). Operations: `create` (fails if the file exists: `File already exists: <p>. Use 'overwrite' or 'edit'.`), `edit` (old-string/new-string; identical strings rejected), `overwrite` (requires an existing, previously read file), `insert` (`insert_line` ≥ 0, 0 = beginning; a line beyond the file length is rejected), `undo` (pops the per-path undo stack; `No edit history for <p>.` when empty). Success messages report lines changed/created/inserted/replaced. Every success carries a structured diff payload for UI rendering that is excluded from model-visible content.

**REQ-TOOLS-136** — Edit matching runs four levels, and the first level that produces any match decides the outcome: (1) exact; (2) exact after trailing whitespace is stripped from every line on both sides; (3) exact after one and the same leading-whitespace prefix is added to or removed from every line of the candidate, so a block differing only by a uniform indentation shift still matches; (4) fuzzy — the single best-scoring window of the same number of lines, accepted only at similarity ≥ 0.85. A match above level 1 is flagged in the result (`Match level: <level>`; a fuzzy match adds `(similarity: 0.NN)` and `Verify the result.`). When no level matches, the message names the levels tried and the file's line count and suggests a fresh read or `overwrite`. When a level matches more than once, the result is `Found <n> occurrences of old_str at lines <a, b, …>` with guidance to add surrounding context or set replace-all. Replace-all replaces every exact occurrence as plain text. Level 4 scores each candidate window with the similarity function of REQ-TOOLS-188, comparing the window's text against the old-string text; when two windows score equally the one starting on the lower line number wins, so a fuzzy edit is deterministic on any given file.

**REQ-TOOLS-137** — The hash-anchored read and edit tools (`haet_read`, `haet_edit`, and the alias `haet`) enforce the same workspace fence as REQ-TOOLS-129 and honor the same `runtime.allow_outside_workspace` opt-out. Their record of which files have been read is scoped to the workspace root and shared by every run in that workspace, so a file read during one run can be edited by a later run without being read again. Their action surface is fixed by REQ-TOOLS-189.

**REQ-TOOLS-188** — One similarity function serves every threshold in this domain. For two strings *a* and *b*, similarity(*a*, *b*) = 1 − editDistance(*a*, *b*) / max(length(*a*), length(*b*)), where editDistance is the unit-cost edit distance over Unicode code points — insertion, deletion, and substitution each costing 1 — length is counted in code points, and the similarity of two empty strings is 1. The result lies in [0, 1] and is symmetric in its arguments. The 0.85 fuzzy-edit threshold of REQ-TOOLS-136 and the 0.45 filename-suggestion cutoff of REQ-TOOLS-134 are both read against this function and against no other, so two implementations of this specification return the same score for the same pair of strings and accept the same edits and suggestions.

**REQ-TOOLS-189** — Action surface of the hash-anchored tools. `haet_read` accepts `path` (with `file_path` accepted as an alias), `offset` (1-based, default 1), and `limit` (default 2000 lines), and returns line-numbered content in the format of REQ-TOOLS-134 with one addition: its metadata header carries `content_hash`, the SHA-256 digest of the file's exact bytes on disk at the moment of the read, rendered as 64 lowercase hexadecimal characters. `haet_edit`, and its alias `haet`, accepts `path` (same alias), `content_hash` (required), `old_string`, `new_string`, and `replace_all` (default false).

Given `haet_edit` is called, when the SHA-256 digest of the file's current bytes differs from the supplied `content_hash`, then the edit SHALL NOT be applied and the call SHALL fail with a message that names the path, states that the file changed since that hash was taken, and directs the caller to read it again before retrying; the message SHALL NOT quote the file's current content. A matching hash is what satisfies the read-before-write rule of REQ-TOOLS-133 for these tools, so a caller holding a current hash never has to read a file twice.

`haet_edit` matches `old_string` at level 1 of REQ-TOOLS-136 only — exact text, with no trailing-whitespace normalization, no indentation shift, and no fuzzy window — because the anchoring hash exists precisely to make the edit exact; a failure to match reports the path and directs the caller to read the file again, and multiple occurrences with `replace_all` false are reported as REQ-TOOLS-136 reports them. Writes are atomic and enter the same per-path undo history as REQ-TOOLS-132's writes. A successful edit reports the file's new `content_hash`, so consecutive edits chain without an intervening read.

### 22. Verification-Gate Capabilities (Outside the Public Tool Surface)

**REQ-TOOLS-159** — A probe capability checks a candidate verification command before the real suite is ever run. It takes the command, the role it would fill (`test`, `typecheck`, `lint`, or `other`), and a working directory, and it answers with exactly one verdict from `verified`, `empty`, `unavailable`, `undecidable`, rendered as a single line of the form `'<cmd>': <verdict> — <note>`. The working directory is resolved beneath the workspace root; one that would escape the workspace tree is ignored without an error and the workspace root is used instead. A probe is bounded by a default timeout of 30 s. The four verdicts are distinguished by how far the candidate command got, and exactly one is returned:
- `verified` — the command ran to completion and its output identified at least one check it executed;
- `empty` — the command ran to completion and reported that it executed no checks at all (an empty suite, a filter matching nothing);
- `unavailable` — the command could not be started: its program is not present, is not executable, or the working directory could not be used. This is a fact about the host, and the note names what was missing;
- `undecidable` — the command started but its outcome cannot be read as evidence about a suite: it exceeded the probe timeout, produced output the probe cannot interpret, or ended without an attributable exit status. This is a fact about the command, and the note says which of the three occurred.

The line between the last two is therefore *could not start* against *started and told us nothing usable*, which is also the line between a verdict the user fixes by installing something and one they fix by changing the command.

**REQ-TOOLS-160** — The verification-gate check set has exactly one writer: a capability taking the proposed set of checks and a reason for the change. It declines in-band — as an ordinary reply the caller reads, never as a retryable error — in three cases, and the decline says which case applies:
- no reason was supplied — the decline asks for one and states that the reason is what the user is shown when their gate changes;
- the proposed suite is not valid — the decline says so and quotes the validation failure;
- the change is one the caller may not make on its own, namely removing the only check for a role, demoting a blocking check to advisory, or emptying the suite — the decline gives the specific reason, states that such a change has to go through an approval-gated proposal instead, and instructs the caller to report it and stop rather than pursue the same outcome another way.

Every write and every decline is recorded so the run that owns the gate can report it. This capability and the probe of REQ-TOOLS-159 are outside the public tool surface (REQ-TOOLS-003) and are available only to the run that maintains the gate. Where writes and declines are recorded is fixed by REQ-TOOLS-190.

**REQ-TOOLS-190** — Verification-gate writes and declines are recorded into a durable verification-gate record held with the session (REQ-SESSION-001), in the order the attempts were made, under the same never-altered, never-reordered, 5000-entry retention rule the permission audit obeys (REQ-TOOLS-078). This document fixes the record's content and its ordering, and no path, file name or directory for it. An entry carries: `timestamp` (ISO-8601 UTC), `session_id`, `agent_id`, `persona`, `outcome` (`write` | `decline`), `decline_case` (`missing_reason` | `invalid_suite` | `requires_proposal`; empty for a write), `reason` (the caller's stated reason for the change, empty when none was supplied), `checks` (the proposed check set as the caller supplied it), and `detail` (the validation failure or the specific reason quoted in a decline; empty for a write). Every attempt produces exactly one entry, so a decline is exactly as durable as a write and a reader can reconstruct what was attempted as well as what took effect. Each entry additionally emits a timeline event so the run that owns the gate can report it (REQ-ORCH-126), and a failed evidence recording logs a warning without turning a decline into an error the caller would retry.

The record MUST also be obtainable as a file the user chooses, under the export obligation REQ-SESSION-199 places on the records it names and REQ-EVENTS-166 states in full; neither is restated here. Two consequences are worth naming because they are what a reader of *this* record wants: the export carries the declines as well as the writes, in the order the attempts were made, and it states how many entries the retention cap dropped, so a trimmed record can never be mistaken for a complete one. Like every export, it is a user-initiated action producing a file and never a way to watch a run (REQ-SESSION-071).

**Whether a record is offered as an export turns on redaction safety, and never on who reads it.** This requirement is the product's single statement of that test, and no requirement in any other domain holds a second copy of it: **a record gains an export when it carries no unredacted user or tool content, and does not gain one when it does.** That only this application reads a record is *not* a reason to withhold an export and never was — a record only this application can read is exactly the record a user needs their own copy of, since it is what they consult when they do not trust this application's rendering of events. This record qualifies because everything it holds is the caller's own stated reason, the check set it proposed, and the product's own validation detail. The permission audit qualifies for one specific reason, which is worth naming because it is the property and not the record that earns the export: REQ-TOOLS-079 gives an entry no argument values at all beyond the redacted command facet inside `summary`.

**The tool-call evidence record of REQ-SESSION-136 does not qualify, and MUST NEVER gain an export — not under this rule, and not under any later widening of it.** It deliberately holds the arguments an agent passed exactly as they were passed, unredacted, which is the whole reason it exists and is the reason the wire never carries them. Anything that exported it would hand a user's prompts, file paths, command lines and any secret that passed through them to a file this product no longer controls. A future requirement proposing such an export is in conflict with this one and MUST be refused rather than reconciled; a future requirement proposing an export for some *other* record is settled by applying the test above to that record's own content, and never by arguing from this list.

### 23. Custom Tool Plugins

**REQ-TOOLS-161** — A persona lists custom tools as file paths under the `custom_tools:` key of its `agents.yaml` entry; each listed file is loaded when that persona's agent is built. That property is not incidental: it is what makes REQ-TOOLS-163's privilege statement a description of what happens rather than an aspiration, and a plugin mechanism that could not satisfy it would not be this mechanism. **REQ-TOOLS-162** — Duplicate registered plugin tool names after configuration resolution are a startup error.

**REQ-TOOLS-163** — A plugin executes inside the host process and therefore holds exactly the operating-system privileges that process holds; plugin code gets no confinement of its own. **REQ-TOOLS-164** — Load failures degrade availability, they never fail agent construction. ### 25. Secret Redaction

**REQ-TOOLS-171** — One shared redaction pass backs every surface on which text that might carry a credential is rendered or persisted — the approval prompt, the audit log, the event stream, application log files, user-visible error text, persisted documents, and lifecycle-hook payloads — so those surfaces can never drift; none of them carries redaction rules of its own. This requirement is the product's single definition of the redaction algorithm, of the redaction marker, of the stored-secret display mask, and of the credential value-prefix list, and no requirement in any other domain holds a second copy of any of the four: a requirement that needs one of them cites this one and states only what it adds.

The pass applies four ordered layers: (1) `key=value` / `key: value` assignments with secret-looking keys; (2) `--flag value` pairs with secret-looking flags; (3) the value following one of the credential scheme keywords `Bearer`, `Basic`, or `token`, the keywords compared without regard to case so that `bearer`, `BASIC` and `Token` trigger masking exactly as `Bearer`, `Basic` and `token` do; (4) a value-shape sweep for the known credential prefixes `ghp_`, `ghs_`, `ghu_`, `gho_`, `sk-`, `sk_`, `iv1.`, `eyj`, recognized only where the prefix begins at a token boundary, so an ordinary word that merely contains one of those sequences is left alone while a value written as `Bearer ghp_…` is still caught. The prefix comparison ignores letter case, so a JWT beginning `eyJ` is caught by the `eyj` prefix and `GHP_…` is caught by `ghp_`; a masking rule that changing capitalization could evade would be no rule at all. Token-boundary recognition is unaffected by that.

In layers (1), (2) and (3) the replaced value extends over exactly one value token and no further: where the value opens with a single or a double quote it ends at the matching closing quote and the quote characters themselves are retained around the mask; otherwise it ends at the first whitespace character following it, or at the end of the string where none follows. `--token abc def` therefore masks to `--token *** def`, `password: a b` masks to `password: *** b`, and `password: "a b"` masks to `password: "***"`.

The mask is `***`: one fixed marker, identical on every surface, carrying no character of the value it replaced and no indication of that value's length, so neither a credential nor its size can be inferred from redacted text. Masking replaces the credential value alone; the program name, subcommands, and flag names around it survive unchanged, so whoever reads the prompt or the audit line can still tell what was about to run — `Bearer sk-live-1` becomes `Bearer ***` and `Bearer` stays legible. The key names of REQ-TOOLS-172 and the value prefixes of layer (4) are the complete set this pass recognizes: an implementation recognizing exactly those and nothing further is conformant, and no further name, prefix, or resemblance-based heuristic is added, so a string carrying none of them is guaranteed to reach its destination unaltered. Redaction is idempotent — re-running over redacted text changes nothing.

A secret the user themselves supplied and the product stored — a provider API key, a pasted subscription token, a tool-server secret — is additionally *shown back* to that user, which the redaction marker cannot serve: a marker carrying nothing at all would leave the user unable to tell which of their keys is stored. One **display mask** covers every such rendering. A stored secret value of 4 characters or fewer renders as `****`; a longer value renders as its first 2 characters, then `****`, then its last 2 characters (for example `sk****10`). The masked middle is that fixed four-character mark whatever the value's length, so a rendering is 4 characters for a short value and 8 characters for every other one and never discloses how long the stored value is — a rendering whose length tracked the secret's length would leak the one property of a credential its owner most easily recognizes, and no surface produces one. A value of zero length never reaches the mask, because a surface that stores secrets refuses to store one.

The display mask and the redaction marker are two different things and are never substituted for one another. The marker replaces a credential found in text that was on its way somewhere else — a log line, an audit entry, an event, a prompt — and reveals no character of it. The display mask is the deliberate rendering of a value the user stored on purpose, and it is the only rendering of a stored secret that any user interface ever shows: no surface reveals a stored secret in clear, and none renders one by any other rule. A requirement that needs the display mask cites this one and states only where it applies and what it adds.

**REQ-TOOLS-172** — A key name is reduced to segments by stripping any leading run of `-` and then splitting what remains on every run of characters that is neither a letter nor a digit. The name counts as secret-looking when one of those whole segments, compared case-insensitively, is `key`, `keys`, `apikey`, `apikeys`, `token`, `tokens`, `secret`, `secrets`, `password`, `passwords`, `passwd`, `credential`, `credentials`, `auth`, `authorization`, or `bearer`. This requirement is the product's single definition of that test; no requirement in any other domain holds a second copy of it, and a requirement that needs the test cites this one and states only what it adds.

`api_key` and `api_keys` are covered by the `key`/`keys` segments; a name written without separators at all is one segment, so `apiKey` and `APIKEY` are covered by the `apikey` segment. Because whole segments must match, `GITHUB_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `Authorization`, and `MY_PASSWORD` are secret-looking while a `keyboard_layout` variable and a `--secretly-verbose` flag are not — the latter's segments are `secretly` and `verbose`, and neither is a listed word. Segmenting on every non-alphanumeric run rather than on underscores alone matters because layer 2 of REQ-TOOLS-171 matches flag names, which are conventionally hyphenated: `--api-key`, `--auth-token`, and `--client-secret` are secret-looking, and a test segmenting on underscores alone would leave that layer unable to recognize the names it exists to catch.

When the key itself is secret-looking, its entire value is masked wherever the redaction pass reaches it — in argument summaries, in stream event arguments, and under a mapping key of a structured payload — not merely the credential-shaped part of it, so a value that looks like ordinary prose is masked as completely as one that looks like a token.

**REQ-TOOLS-173** — Every published stream event that carries tool arguments or a permission summary carries them redacted: the arguments on `tool.start` and the summaries on `permission.decision` and `approval.requested` never contain an unmasked credential, no matter how the event was assembled or which of its fields were set last. Values are rendered as strings and clipped at 240 characters.

**REQ-TOOLS-174** — The desktop status strip permanently displays a `redaction: always on` flag with an explanation that anything resembling a credential is masked before it reaches a model or the transcript.

### 26. Cross-Cutting Ordering, Isolation, and Lifecycle

**REQ-TOOLS-175** — Dispatch order per tool call: (1) permission resolution (never raises; ask brokered to approval or headless policy), (2) on allow — pre-execution hooks (may block), (3) tool execution, (4) post-execution hooks (feedback only), (5) observation normalization and diagnostics. A deny or hook block returns a tool-result error event and the run continues.

**REQ-TOOLS-176** — Permission state never crosses a session or run boundary, and nothing falls back from one session or run to another when its own state is missing. Observable consequences: an approval answered in one session's window never authorizes a call in another session; the decisions of one run never appear in another run's audit trail; a mode change in one session never alters what another session's agents may do; and a call that cannot be attributed to a run never borrows a live run's sandbox specification or egress configuration (REQ-TOOLS-009, REQ-TOOLS-029). A session's permission state can be discarded and reset explicitly, and after a discard no earlier state of that session influences a later decision.

**REQ-TOOLS-177** — Teardown ordering: discarding a session's approval host cancels all waiting approvals (waiters resolve cancelled → deny); run or scheduler stop releases blocked calls the same way; discarding the session's mode override at run end prevents a resumed session from inheriting a mid-run switch.

**REQ-TOOLS-178** — The approval wait and the user-question wait share one budget, `runtime.approval_timeout_seconds`, whose default REQ-CONFIG-126 states and which this domain does not restate, and one reading of zero: a configured `0` waits indefinitely, and a negative value is rejected when the configuration is loaded (REQ-TOOLS-055). "Wait for me" therefore means the same thing on both barriers.

**REQ-TOOLS-179** — Exit-code contract across the terminal surface: 124 = hard timeout (foreground and background); 126 = sandbox unavailable (the command never ran); −1 = soft pause (foreground) or killed (background); 0/nonzero = the command's real outcome.

**REQ-TOOLS-180** — Run completion signalling: agents are constructed with no built-in run-termination tool. A run terminates when the agent produces a message addressed to the user and requests no tool call in that same turn; that message is then exposed as the child's final response, giving delegation a deterministic handoff value. The never-gated names of REQ-TOOLS-014 are retained for personas/providers that still surface such a tool. Correction prompts describe the observable behavior (ending the turn), never a tool name.

### 27. Event-Stream Integration

**REQ-TOOLS-181** — The `session.start` event carries `permission_mode` (the effective preset) and `sandboxed` (the configured-and-available verdict). `tool.start`/`tool.finish` events carry redacted arguments and outcome/duration. `permission.decision` and `approval.requested` are emitted with redacted summaries per REQ-TOOLS-061/083.

**REQ-TOOLS-182** — The event envelope carries `schema_version`, `event`, an ISO-8601 UTC `timestamp`, and `session_id`. Consumers must ignore unknown fields for forward compatibility.

**REQ-TOOLS-183** — Consumers pair approvals to decisions by `request_id` and must treat an empty request id as unpaired. Pairing works from either side: a `permission.decision` event carries a non-empty `request_id` exactly when the decision it reports resolved a raised approval under the strict pairing test of REQ-TOOLS-062, so every `approval.requested` event that was answered is matched by exactly one `permission.decision` event carrying the same id, and a live consumer never has to infer the pairing from ordering or timing. A decision that was never put to a person carries an empty id, which is the only reading of "unpaired".

### 28. Desktop Surfaces

**REQ-TOOLS-184** — The desktop status strip permanently shows, with explanatory tooltips whose wording mirrors the settings pages: `mode: <preset>`, the workspace-scope flag (REQ-TOOLS-131), `redaction: always on`, an optional armed-state indicator, an `unsaved settings` flag, and a background-session count. Every one of these flags is text, never colour alone (REQ-SHELL-149). Each flag reflects a change in the state it reports within 100 ms of that change becoming observable to the application, which is also the budget for presenting a queued approval dialog after the previous one closes (REQ-TOOLS-063); the strip coalesces changes arriving faster than that rather than redrawing per change, and it never redraws when nothing it displays has changed. The background-session count conveys how many background terminal sessions (REQ-TOOLS-107) are in the `running` state; its exact wording is left to the implementation.

**REQ-TOOLS-185** — Approval visibility beyond the dialog: a pending-approval row remains visible on a live run's monitor; pending approvals are projected into the transcript; the pending-approval store emits updates only on change; queued requests display serially; an answer travels to the waiting agent; a session observer publishes and clears pending approvals.

**REQ-TOOLS-186** — The runtime settings page exposes sandbox mode, network egress policy, and permission mode under an explicit Save/Discard flow, and an operator-set egress value demonstrably reaches the live run's policy.

**REQ-TOOLS-191** — The `runtime` settings category (REQ-CONFIG-269) exposes the workspace-scope opt-out `runtime.allow_outside_workspace` as a labelled toggle under the same Save/Discard flow as REQ-TOOLS-186. Given the toggle is off, when the user turns it on, then an explicit confirmation SHALL be required before the change is staged; the confirmation SHALL state that agents will be able to read and write files anywhere the application itself can reach, and declining SHALL restore the previous position without staging a change. Turning the toggle off requires no confirmation. Saving the change SHALL make the new value govern the next tool call decided under it, exactly as REQ-TOOLS-025 governs a replaced policy, and the status strip flag of REQ-TOOLS-131 SHALL follow the saved value. This control is the only user-facing way to set the opt-out; it replaces the removed launch-time flag.

**REQ-TOOLS-192** — The unattended-run advisory of REQ-TOOLS-072 SHALL be presented in the desktop interface at the point the run is started: given a non-empty advisory, when the user starts a run whose session will have no approval presenter, then the advisory SHALL be shown before the run begins, together with the run's effective permission mode and sandbox status (REQ-TOOLS-071), and with a control that opens the `runtime` settings category (REQ-CONFIG-269) at the three settings the advisory names. The presentation SHALL be dismissible and SHALL never block or cancel the launch. Given an empty advisory, nothing is shown. This requirement carries the capability of announcing an unattended run's permission posture that previously reached the user only as text printed by a shell entry point.

## Data & Formats

### Where this domain's material is kept (workspace-observable)

Files below are files because a user reads or edits them, or because a filesystem guarantee is what protects them; the records below are records because they are the application's own high-volume, queried, transactional state rather than material a person edits, and each names the requirement that owns where it lives. This document fixes no path for any record. Being a record says where a thing is kept and says nothing about whether the user may have a copy of it: a record is offered as an export when it carries no unredacted user or tool content, and is not when it does, which is the test REQ-TOOLS-190 fixes.

- `<workspace>/.rotaris/agents.yaml` — workspace configuration, including all `runtime.*` keys below; the desktop mode selector persists `runtime.permission_mode` here.
- `secrets.yaml` — in the global config directory and `<workspace>/.rotaris/`; MCP secrets; atomically written; `.rotaris/` is auto-appended to the workspace `.gitignore`.
- The permission audit — permission decisions and mode changes, recorded in decision order, never altered, ring-capped at 5000 (REQ-TOOLS-078, REQ-SESSION-137). It is a durable record rather than a file, and the file the user gets is its export (REQ-SESSION-199).
- The tool-call evidence record — tool-call outcomes, including terminal outcome kinds and warnings (REQ-SESSION-136); its ring cap is not fixed here and is REQ-SESSION-133's. It holds the arguments an agent passed unredacted, and is for that reason the one record on this list that is never offered as an export and never may be (REQ-TOOLS-190).
- The verification-gate record — verification-gate writes and declines, ring-capped at 5000 (REQ-TOOLS-190). It is a durable record rather than a file, and the file the user gets is its export (REQ-TOOLS-190, on the terms REQ-SESSION-199 fixes).
- Session evidence issues (`permission_denied` kind) and timeline events (`permission_approved`, `permission_mode_changed`, `permission_mode_downgraded`).
- Session state snapshot (recorded for audit visibility in the session's launch audit, REQ-SESSION-138): `permission_mode` (effective preset at run start; empty on pre-feature snapshots), `sandboxed` (bool), `sandbox_backend` (`seatbelt`/`bubblewrap`/empty), `pending_approvals` (live map keyed by request id), the task list, and transcript events including any downgrade notice.
- `<workspace>/.rotaris/plugins/` — the designated workspace plugin folder listed by the settings inventory. Its members are the plugin modules the host process can load in-process (REQ-TOOLS-161, REQ-TOOLS-165); this document fixes no file extension, language or packaging form for them.

### Record shapes

Permission decision entry (field set; no encoding is fixed by naming one — REQ-TOOLS-078):
`timestamp` (ISO-8601 UTC), `session_id`, `agent_id`, `persona`, `tool_name`, `decision` (`allow|ask|deny`), `rule_id`, `source` (one of the 12 decision-source values), `summary` (the redacted request summary of REQ-TOOLS-016), `reason`, optional `request_id` (only when an approval was raised). Carries no argument values beyond the redacted command facet inside `summary`. Each entry additionally carries an identifier, the one a locator names it by (REQ-TOOLS-079, REQ-EVENTS-056), as a field of the entry and under the same field in every entry and every export, so that a locator resolves against an exported audit on a machine carrying none of this product's code. Mode-change entries carry no such identifier and their field set below is unchanged, because no locator names one.

Mode-change entry (same audit as the decision entries, interleaved in write order — REQ-TOOLS-082):
`{timestamp, event: "permission_mode_change", session_id, agent_id, requested_mode, effective_mode, previous_mode, source, reason, skipped_personas: [...]}` — `skipped_personas` present even when empty.

Approval payload:
`{request_id (hex UUID), session_id, agent_id, persona, tool_name, command (redacted), argument_summary, rule_id, reason}`.

Verification-gate record entry (REQ-TOOLS-190):
`{timestamp (ISO-8601 UTC), session_id, agent_id, persona, outcome: "write"|"decline", decline_case: "missing_reason"|"invalid_suite"|"requires_proposal"|"", reason, checks, detail}`.

Stream events (envelope: `schema_version`, `event`, `timestamp` ISO-8601 UTC, `session_id`; unknown fields ignored):
- `approval.requested`: `request_id`, `agent_name` (may be empty), `persona`, `tool_name`, `rule_id`, `summary` (redacted), `resolver` (`"brokered"|"headless"`), `timeout_seconds` (nullable), `unattended_reason`.
- `permission.decision`: `request_id` (empty = unpaired), `tool_name`, `decision`, `source`, `rule_id`, `summary` (re-redacted on construction/assignment).
- `session.start`: includes `permission_mode`, `sandboxed`.
- `tool.start` / `tool.finish`: redacted arguments (values clipped at 240 chars), outcome, duration.

Terminal observation extras:
- `[terminal_diagnostic]` JSON block (sorted keys, nulls dropped): backend, command, detail, error_class, exit_code, failure_kind, kill_status, outcome_kind, outcome_severity, output_truncated (present only when the capture was truncated), session_reinitialized, timeout, timeout_seconds, warnings, working_dir, session fields when applicable.
- Output section labels: `[terminal_output]`, `[partial_terminal_output]` (timed-out), `(no output)` placeholder, `[RESET]` command label.
- Background list entries: `{session_id, command, status, exit_code, started_at (ISO-8601)}` plus an aligned text table with `▶/✓/✗` status glyphs.
- Fetch error observations: `[fetch_diagnostic]` JSON block; observation metadata `url`, `final_url`, `status_code`, `content_type`, `truncated`.

Identifier formats:
- Terminal background session ids: `ts_` + 8 hex characters.
- Delegated task ids: `bg_` + 8 hex characters.
- Artifact ids: `art_` + 8 hex characters.
- Task-list phase/task ids: 8 hex characters.
- Approval request ids: hexadecimal UUID.
- Session approval rule ids: `session:allow:<n>` (1-based). Other rule-id spellings: `builtin:meta-tool`, `preset:<preset_name>`, `failclosed:unresolvable-policy`, `approval:once`, `approval:session`, `starter:*` (nine spellings per REQ-TOOLS-039), `<preset>:fetch-remote-host`, `<preset>:fetch-local-host`, `<preset>:network-command`, `restricted:read-outside-workspace`, `restricted:read-only-tool`, `ask:read-only-tool`.
