# Desktop Shell, Navigation, and Window Management

## Overview

Rotaris presents a single main desktop window containing seven primary views selected from a left-hand navigation rail, framed by a title bar (brand, workspace, and session status) and a bottom status strip (workspace, branch, safety, cost, and cloud indicators). The shell owns global keyboard shortcuts and a command palette, responsive compact layouts with overlay drawers, user-resizable and persistent pane layouts, auxiliary per-persona agent windows, a terminal pop-out window with an interactive character-grid terminal, transient and persistent notification surfaces, theming with accessibility floors, and guarded window-close / workspace-switch / session-switch flows. Preferences persist in a single per-user store; all shell behavior below is stated as externally observable requirements.

## Requirements

### Application entry, demo mode, and preference store

- **REQ-SHELL-001**: *Withdrawn.* The product is a single graphical desktop application with no command-line surface, so there is no argument vocabulary to specify; the capabilities the arguments carried are now reachable from the desktop interface — workspace selection through REQ-SHELL-010 and REQ-SHELL-021, demo mode through REQ-SHELL-162, diagnostics capture through REQ-SHELL-163, and the running version through REQ-SHELL-033 and REQ-SHELL-140.
- **REQ-SHELL-002**: *Withdrawn.* There is no command-line surface on which to print a version and no exit code to report it with; the running version is read from the title-bar version label (REQ-SHELL-033) and, as selectable text, from the About page's Version row (REQ-SHELL-140).
- **REQ-SHELL-003**: *Withdrawn.* There is no command-line invocation to reject; the diagnostics controls of REQ-SHELL-163 offer only valid capture levels and choose the output folder through the platform folder chooser, so an invalid diagnostics selection is unreachable rather than diagnosed.
- **REQ-SHELL-004**: *Withdrawn.* Process exit codes are a script-oriented surface this product does not offer; the observable shutdown obligations that mattered are stated in REQ-SHELL-121.
- **REQ-SHELL-005**: In demo mode (REQ-SHELL-162) each of the seven primary views opens populated from sample data carried inside the build, and the process opens no outbound network connection for its whole lifetime: cloud-credit polling is not started (REQ-SHELL-015) and no request reaches a model provider. An action that could only complete against a live service is declined with one of the exact sentences listed in REQ-SHELL-149; the decline is always shown, never silent, and the view's contents are unchanged afterwards — no partial application. Starting or continuing a run is one of those actions: in demo mode the send control and Ctrl+Return decline with "Runs are unavailable in demo mode.", the composer keeps the text the user typed, and no session state changes.
- **REQ-SHELL-006**: All user preferences resolve to a single platform-standard per-user preference store scoped by organization name "Rotaris" and application name "Rotaris"; this scoping is established before the first preference read so that no preference is ever read from or written to a differently scoped store. This store is the desktop-scoped preference surface, disjoint from the layered YAML configuration surface: no key of this document is ever read from or written to a YAML configuration file, and no YAML configuration field is ever read from or written to this store (REQ-CONFIG-463). The store's physical path and on-disk encoding are implementation choices, constrained only by these observable properties, which are the whole of the requirement: it is the host platform's own standard per-user application-settings location for that organization and application pair; where the platform offers more than one such location it is the one local to this machine and not replicated, copied or synchronised to any other machine or to any other copy of the user's profile, which is the selection REQ-STARTUP-145 fixes for the product's per-user directories, cited here for its terms and stated here because this store is not one of those directories and therefore does not inherit it — the reason is the keys, not tidiness, since this store holds paths that describe *this* machine and nothing else (`workspace/lastOpened` and `diagnostics/outputDir`, REQ-STARTUP-146, REQ-SHELL-163), and a replicated store would answer a launch on one machine with a folder that exists only on another; it is readable and writable by the invoking user account and needs no elevation; it lies outside every workspace directory, so no preference ever appears inside a project or in that project's version control; it is created on first write, and its absence is not an error but the state in which every key answers with its declared default; and a value written to it is the value read back after the process has been restarted, subject to the tolerant integer parsing of REQ-SHELL-069. Two conformant builds may therefore lay the same keys out differently on disk. Because this document defines the store, it also registers what may live in it, as domain 15 registers the layered YAML surface: the store's key set is exactly the keys listed in the per-user preference store table of this document's Data & Formats section, and a key that does not appear in that table does not exist. The meaning and default of a key may be owned by the document whose behavior it serves — the `interface/` toggles and the tool-row `display/` preferences by REQ-CONFIG-405, `display/showReasoning` by REQ-CHAT-167, the `panels/` layout keys by REQ-SHELL-069, the diagnostics keys by REQ-SHELL-163, `workspace/lastOpened` and `updates/dismissedVersion` by REQ-STARTUP-146, the per-workspace composer draft by REQ-CHAT-015, the requirements board keys by domain 08 — but a key reaches the store only by being registered in that table. The keys are slash-namespaced, as that table's namespace list states; no key of any other form exists, so a document that needs a new preference registers it in that table rather than minting a key of its own, and a preference key named in another document but absent from that table is not a preference of this product.
- **REQ-SHELL-162**: Demo mode SHALL be reachable from the desktop interface and from nowhere else. The command palette SHALL carry a shortcut-less entry labelled "Open demo window", present in every window and in the composer's slash catalogue on the terms of REQ-SHELL-048 and REQ-SHELL-056. Activating it SHALL build a new main window in demo mode, show it, and leave the window that issued the request open and unchanged — the replacement semantics of REQ-SHELL-017 SHALL NOT apply. Demo mode is a property of a window fixed when that window is built: it SHALL NOT be turned on or off in a window that is already open, SHALL NOT be written to the preference store, and SHALL NOT be inherited by a window the workspace-replacement flow builds from a window that is not in demo mode. A demo window SHALL be identifiable as one without relying on colour: the title bar SHALL carry a "Demo" marker beside the wordmark whose accessible name states that the window shows built-in sample data, and the marker SHALL be present for the whole life of the window. A demo window SHALL never write `workspace/lastOpened` and SHALL never raise the first-launch workspace prompt of REQ-SHELL-011.
- **REQ-SHELL-163**: Diagnostics capture SHALL be reachable from the desktop interface and from nowhere else. The Settings view's About tab (REQ-SHELL-138) SHALL carry a diagnostics card holding three controls, each keyboard-reachable and each carrying an accessible name: a capture-level control (accessible name "Diagnostics capture") whose selectable values are exactly `off`, `light` and `deep` and which shows `off` whenever nothing has been stored; an output-folder control (accessible name "Diagnostics output folder") that displays the folder currently in force as selectable text and, when activated, opens the platform folder chooser limited to selecting directories to change it; and a control that opens this window's diagnostics run directory in the OS file manager, enabled only while such a directory exists for this window. Because the level control offers only the three valid levels and the folder is chosen through the platform chooser, an invalid diagnostics selection is unreachable, and the product SHALL define no error, message or refusal for one. A change to either choice SHALL take effect for windows built afterwards and SHALL NOT alter the capture already running in an open window; the card SHALL say so in words. The two choices SHALL live in the per-user preference store as `diagnostics/level` (default `off`) and `diagnostics/outputDir` (default unset, meaning the product's own default location, REQ-STARTUP-131), and SHALL NOT appear in the layered YAML configuration surface (REQ-SHELL-006).

### Startup sequencing

- **REQ-SHELL-007**: The application window icon is the product brand mark from the moment the first window appears, so taskbar and window-switcher entries carry the logo.
- **REQ-SHELL-008**: Bundled font families for the display, body, and monospace roles are made available before the first window paints; if loading a bundled font fails, the application continues with host system fonts and does not abort.
- **REQ-SHELL-009**: The stored theme choice is applied ahead of the first window becoming visible. Reading that preference never writes it back, so on a machine where the recorded theme name does not map to an installed theme the recorded value stays exactly as the user left it.
- **REQ-SHELL-010**: Startup workspace resolution follows this precedence: (a) a workspace the window was explicitly built for — the folder chosen through the replacement flow of REQ-SHELL-017, or a folder a launch of the application carried and for which the one running instance built this window (REQ-STARTUP-163) — wins, is resolved on the terms REQ-STARTUP-163 fixes for when two directory strings name the same directory, which this clause cites rather than restating, and is immediately persisted in that resolved form as the last-opened workspace with no onboarding prompt; (b) otherwise a remembered last-opened workspace that still exists as a directory is used with no prompt; (c) otherwise the current working directory is used and a first-launch prompt is scheduled after the window is shown.
- **REQ-SHELL-011**: Deferred first-paint work uses one shared delay of **650 ms**, measured from the moment the window is shown, so the complete desktop paints before anything is put in front of it. This document owns window management, and this requirement is the product's single definition of that delay: every offer deferred to first paint waits the same interval, and a document that needs to say how long such work is deferred SHALL cite this identifier rather than restating the figure. The first-launch workspace prompt is deferred by that delay. The prompt is the platform's own folder-picker dialog, window title "Open a project folder", limited to selecting directories and initially pointed at the current workspace (or, when there is none, the user's home directory). The deferred prompt is a one-shot offer that SHALL be abandoned unshown whenever the question it asks has already been answered by the time that delay elapses: if the user has by then started the workspace-open flow of REQ-SHELL-021, or a workspace has by then been chosen by any route, the prompt SHALL NOT appear. Two folder choosers are therefore never on screen at once, and the deferred prompt never appears over a chooser the user opened. A prompt abandoned this way SHALL show no reminder — the reminder of REQ-SHELL-012 belongs only to a chooser the user actually saw and cancelled.
- **REQ-SHELL-012**: Cancelling the first-launch chooser leaves the default desktop fully usable and shows a transient notification: "Open a project folder when you're ready by selecting the workspace path in the title bar."
- **REQ-SHELL-013**: On a bundled (standalone) runtime that still requires machine setup, the setup modal is scheduled after the window is shown, at the shared deferred first-paint delay of REQ-SHELL-011; after it completes, setup state is refreshed, the asynchronous Git refresh starts, and only then does first-launch workspace onboarding continue. On other runs the Git refresh starts at window activation.
- **REQ-SHELL-014**: Git status discovery never starts before the window is on screen (REQ-SHELL-013 fixes the exact point for each kind of run), and the window remains fully usable while a discovery is outstanding: views can be switched, text can be typed, and shortcuts fire. The discovery itself displays nothing that blocks input — no modal dialog, no progress dialog, no busy cursor — which leaves dialogs scheduled by other requirements, such as the first-launch folder prompt (REQ-SHELL-011) and the machine-setup modal (REQ-SHELL-013), free to appear while a discovery is still running. A failed discovery raises the persistent ERROR notice of REQ-SHELL-116 reading "Git status could not be refreshed: {message}"; it stays on screen until the user dismisses it and is never withdrawn on a timer.
- **REQ-SHELL-015**: Activation ordering: the window is shown first; the software-update check starts only once a window is visible (so its notification always lands on a visible window); cloud-credit polling starts at the same point unless running in demo mode.
- **REQ-SHELL-164**: Where this document requires a platform-native dialog — the folder choosers of REQ-SHELL-011, REQ-SHELL-021 and REQ-SHELL-163, and the native message boxes of REQ-SHELL-119 — the product SHALL be answerable only for what it supplies to the host: the dialog's title, its initial location or selection, its restriction to directories where one is stated, the button set and which button is the default, and the correct interpretation of every answer the dialog can return. Keyboard traversal, focus order, localization of platform-supplied button text, high-contrast rendering and screen-reader behaviour inside such a dialog are inherited from the host; they are not requirements on this product, and a host whose native dialog falls short of them does not put the product out of conformance with REQ-SHELL-144, whose sweep covers the seven primary views and the product's own windows. Two obligations survive whatever the host does: a dialog dismissed by any means the host offers — Escape, the window close control, or a platform-specific gesture — SHALL be treated as the identical answer to its Cancel button, with the same consequences the requirement states for Cancel; and no native dialog SHALL be the only route to a capability, so every flow a native dialog guards also states what the product does when that dialog is cancelled.
- **REQ-SHELL-016**: Deferred startup offers (project-initialization resolution and the hook-trust review offer) are issued only after window construction completes; a window created and destroyed immediately must not crash or deliver the offers.

### Workspace selection and replacement

- **REQ-SHELL-017**: Opening another project builds a new main window on the selected folder, shows it, and then closes the old window. Only if the old window closes successfully is the new window recorded as current, the last-opened-workspace preference updated, and the new window activated.
  > **Extended by [`PD-SHELL-001`](../product/directives.md#pd-shell-001), 2026-09-12.** This still
  > governs in full, and remains what happens when a chosen folder replaces the window. The directive
  > adds a second route beside it, taken by its own two gestures, on which a main window is added and
  > no window is closed.
- **REQ-SHELL-018**: If the old window refuses to close (for example the user cancels an unsaved-settings dialog or an active-run confirmation), the replacement window is discarded and nothing changes: the old window, the current workspace, and the stored preference all remain as they were.
- **REQ-SHELL-019**: If constructing the replacement window fails, the old window stays open and shows the error notification "Could not open the selected project: {reason}".
- **REQ-SHELL-020**: Only workspace-open requests originating from the currently active window are honored; requests from stale windows are ignored. This governs requests raised inside a window. A launch of the application carrying a workspace directory originates in no window and is not such a request: it is honored under REQ-STARTUP-163, which adds a main window rather than replacing one, and the several main windows the one running instance may hold at once (REQ-STARTUP-161) are not stale windows of each other — each honors the requests raised inside it while it is the active one.
- **REQ-SHELL-021**: Activating the title-bar workspace chip evaluates the same three gates as a window close, in the same fixed order as REQ-SHELL-119 — unsaved settings, then worktree integration, then active runs — and any of them ends the flow. (1) With unsaved settings present, the save/discard/cancel dialog of REQ-SHELL-124 is raised: Cancel ends the flow with nothing changed, a Save that fails also ends it, and Save-that-succeeds or Discard lets evaluation continue. (2) While a worktree integration is running, the request is declined outright with the transient error notification of REQ-SHELL-112 reading "Finish the worktree integration before opening another project.". (3) With a run active, it is declined the same way with "Finish the active run before opening another project.". A decline shows no folder chooser and changes no window, workspace or stored preference. When no gate stops it, the chooser opens pointed at the current workspace. Cancelling the chooser leaves the window, the workspace and the stored preference exactly as they were and may show the reminder of REQ-SHELL-012. Selecting the folder that is already open builds no replacement window and leaves the current window in place; whether the selected folder is the one already open is decided by the rule REQ-STARTUP-163 fixes for when two directory strings name the same directory, which this requirement cites rather than restating, so this decision, REQ-STARTUP-052's and the window-reuse decision REQ-STARTUP-163 makes for itself are all taken on one rule.
  > **Narrowed by [`PD-SHELL-001`](../product/directives.md#pd-shell-001), 2026-09-12.** The three
  > gates above govern every activation of the chip but the two add-a-window gestures that directive
  > names, on which they are not evaluated because such a request adds a window rather than displacing
  > one. Every other activation is the replacement route and this requirement governs it in full.
  >
  > **Extended by [`PD-WORKSPACE-001`](../product/directives.md#pd-workspace-001), 2026-09-12.** The
  > sentence above still governs — selecting the folder already open builds no replacement window and
  > leaves the current window in place — and the directive adds an offer of a new session beside it.
  > What it changes is that this outcome is no longer silent; no window, workspace or preference moves.

### Main window structure

- **REQ-SHELL-022**: The main window carries the title "Rotaris", opens at 1440×900 logical pixels, and refuses to be resized below 1000×680 in either dimension. This document owns window management, and this requirement is the product's single definition of the main window's opening size and of its minimum size: a document that needs to name either figure, or to require that a control of its own be reachable and fully labelled at the minimum, SHALL cite this identifier rather than restating a number, and no surface declares a minimum window size of its own. At that 1000×680 minimum, and on every one of the seven primary views, the following all hold and are individually checkable: every control the view offers lies wholly inside the window bounds; every control is reached by Tab traversal; every control's label is rendered in full, the only exceptions being the elisions REQ-SHELL-082 and REQ-SHELL-087 permit; and no control requires horizontal scrolling to reach (REQ-SHELL-064, REQ-SHELL-065, REQ-SHELL-106).
  > **Extended by [`PD-SHELL-003`](../product/directives.md#pd-shell-003), 2026-09-24.** On Windows and Linux the main window is frameless, shows no native menu or toolbar, and carries minimize, maximize/restore and guarded close controls in the product-drawn title bar. The title and geometry above still govern unchanged.
- **REQ-SHELL-023**: The window hosts exactly seven primary views in this fixed order: Overview, Workspace, Mission, Requirements, Git, Library, Settings. Exactly one is visible at a time; Requirements is the fourth entry, ordered after Mission and before Git.
- **REQ-SHELL-024**: Vertical layout, top to bottom: title bar; a persistent-notice banner slot; a horizontal region of navigation rail beside the active view; status strip.
- **REQ-SHELL-025**: View switching semantics: switching to an unknown view identifier is a silent no-op. Leaving the Settings view with unsaved changes triggers the save/discard/cancel dialog (REQ-SHELL-124) and cancelling aborts the navigation. A successful switch updates the rail's selected state and the recorded active view (which other behaviors, such as Escape handling, read).
- **REQ-SHELL-026**: The view shown at startup is Overview.

### Navigation rail

- **REQ-SHELL-027**: The rail shows one button per primary view, in view order, each with a distinct icon and a text label beneath it. Labels: "Overview", "Workspace", "Mission", "Requirements", "Git", "Library", "Settings".
- **REQ-SHELL-028**: Rail selection is mutually exclusive: whenever a view is showing, exactly one rail button is in the checked state, and checking a button unchecks the one that was checked before. Each button is an individual stop in the window's tab order (REQ-SHELL-032) and shows a pointing-hand cursor under the pointer. Each rail icon is declared at 17×17 logical pixels and drawn under the scaling rule of REQ-SHELL-030. Every button carries the tooltip and the accessible description "Open {Label}". A click checks the button and switches the view, as do Space and Return on the focused button; a checked state that no user gesture produced updates the rail's appearance only — it switches no view and causes no other navigation effect. The rail is not an arrow-navigable group: while a rail button holds focus, Arrow Up, Arrow Down, Arrow Left and Arrow Right SHALL move no rail selection and switch no view. Movement between rail buttons is by Tab and Shift+Tab only (REQ-SHELL-032). This is exactly the difference REQ-SHELL-153 preserves between the rail and the shell's vertical navigation lists, and it is deliberate: the rail's activation both selects and navigates, so arrow keys must not be able to traverse it.
- **REQ-SHELL-029**: Rail labels render at 9 px, and in every built-in theme each item shows its complete label with no ellipsis and no clipped glyph. The rail is consequently never narrower than its widest label needs: it uses the theme's declared item and rail widths (54 px and 68 px respectively in the default theme, REQ-SHELL-129) whenever those already accommodate the labels, and exceeds them when they do not. The width is re-derived after every theme change, including a change to a theme with a larger type scale.
- **REQ-SHELL-030**: An icon declared at L logical pixels is rendered from artwork whose raster resolution is at least ceil(L × device pixel ratio) device pixels in each dimension, so the drawn icon is never an enlargement of a smaller raster. Measured at 100%, 125%, 150%, 175% and 200% OS display scaling, the icon covers L logical pixels — the same physical area of the screen at every one of those factors, within one device pixel. Resting and selected rail icons use two distinct theme inks, and each clears the 3:1 non-text contrast floor of REQ-SHELL-144 against the rail background.
- **REQ-SHELL-031**: A theme change fully recolors the rail, including baked icon inks and hover/selected treatments; no stale-theme icon color survives a switch.
- **REQ-SHELL-032**: Every rail button is its own stop in the window's normal tab order, and each announces a non-empty accessible name (the Workspace button, for instance, announces "Open Workspace").

### Title bar

- **REQ-SHELL-033**: The title bar is a fixed-height strip (44 px in the default theme) with a bottom hairline, containing left to right: the brand mark (22×22, accessible name "Rotaris"), the wordmark "Rotaris", a version label `v{version}` in small monospace, the workspace chip (centered region), the session chip, and the improvement-analysis indicator.
  > **Extended by [`PD-SHELL-003`](../product/directives.md#pd-shell-003), 2026-09-24.** The product-drawn title bar additionally ends with the main window's minimize, maximize/restore and close controls on Windows and Linux; the contents and ordering above remain intact ahead of them.
- **REQ-SHELL-034**: If the brand image asset is missing or unrenderable, the title bar degrades to a letter placeholder "R" in a dashed accent frame without crashing.
- **REQ-SHELL-035**: The workspace chip behaves as a button: accessible name "Open project folder", tooltip "Open another project folder", pointing-hand cursor, keyboard focusable, activated by left-click release inside it or by Return/Enter/Space. It displays a folder icon, the workspace path in small monospace, a separator, and the session name (an em dash when none). Its accessible description is "Current project: {path}. Opens the native project folder chooser." Activation opens the workspace chooser flow (REQ-SHELL-021).
- **REQ-SHELL-036**: The session chip carries the accessible name "Session status" and the accessible description "Session is {status}", and displays a status dot — 6 px in the default theme — followed by the text "session {status}". The status word is always a member of the normalised run lifecycle vocabulary of REQ-NOTIFY-048, which is the product's single definition of it; this document declares no status word of its own, holds no copy of the member list, and never renders a raw backend or persisted status string. What the chip contributes is how those members are coloured. They fall into five colour groups — {`running`, `starting`}, the waiting family {`pausing`, `paused`, `cancelling`}, {`completed`}, {`failed`, `stopped`}, and {`idle`} — and each group resolves to a single theme state colour that the chip's dot and pill share with every status tag drawn elsewhere in the product, so one status word is never shown in two different colours at the same moment. The mapping is one group to each of the five state text colours the theme declares (REQ-SHELL-145): {`running`, `starting`} use `running`; the waiting family uses `waiting`; {`completed`} uses `done`; {`failed`, `stopped`} uses `fail`; and {`idle`} uses `info`. No group borrows another's colour and no group falls back to plain text colour, so all five are distinguishable from one another as well as from ordinary text. A member the vocabulary gains is given its group here rather than acquiring a colour of its own. The dot pulses for `running` and `starting` and for no other status; otherwise it is drawn at full opacity with no animation. Chip text measures at least 4.5:1 against the title-bar background it is actually painted on.
- **REQ-SHELL-037**: The improvement-analysis indicator (a slightly smaller pulsing dot plus the label "Reviewing run for improvements…") is visible only while improvement analysis is active, carries the accessible name "Improvement analysis status", and its description states the user may continue working.

### Status strip

- **REQ-SHELL-038**: The status strip is a fixed-height bottom row (26 px in the default theme) with a top hairline. Items left to right: workspace path (link), checked-out branch, spacer, safety flags, model, tokens, cost, cloud credit (link; present only under the condition in REQ-SHELL-046), background-session count. Every item carries an accessible name; the names are "Workspace folder", "Checked-out branch", "Safety settings in force", "Model runs use", "Tokens used", "Cost so far", "Rotaris Cloud credit", and "Background sessions".
- **REQ-SHELL-039**: The strip holds two kinds of item. An item that opens something is a link: link colour, underline, pointing-hand cursor, its own keyboard focus stop, activated by click or by Return. Every other item is inert text — arrow cursor, no focus stop, no link styling — but an inert item is still exposed to assistive technology with its accessible name, and with its tooltip sentence as its accessible description where it has a tooltip (REQ-SHELL-058). Exactly two items are ever links, the workspace path and the cloud credit, and each is a link whenever it is on screen. Both have visibility conditions (REQ-SHELL-046, REQ-SHELL-047), so the strip may show two links, one, or none — never a third.
- **REQ-SHELL-040**: Activating the workspace-path link opens the workspace folder in the OS file manager; activating the cloud-credit link opens the configured cloud account/quick-start page in the default browser. Neither failure is silent. When the host has no handler for a folder or a URL, or the handler cannot be launched, the transient error notification of REQ-SHELL-112 SHALL appear, and it SHALL convey both that the folder or the page could not be opened and the path or URL that was attempted, so the user can reach it by another route; its wording is left to the implementation. The link SHALL stay enabled and SHALL remain activatable again, and nothing else about the strip SHALL change. The About page keeps its own inline-caption reporting of the same kind of failure (REQ-SHELL-141, REQ-SHELL-142).
- **REQ-SHELL-041**: Each safety flag shows a short form and carries one full-sentence explanation, and its tooltip and its accessible description are the identical joined string "{short form} — {explanation}". The flags appear left to right in this fixed order, each with the display condition given: "● CB armed", shown only while the circuit breaker is enabled — "Circuit breaker: Rotaris stops a run that keeps repeating a failing step."; "redaction: always on", shown unconditionally — "Secret redaction: anything that looks like a credential is masked before it reaches a model or the transcript."; "unsaved settings", shown only while the Settings view holds unsaved edits, its explanation conveying exactly two things and no more — that the Settings view is holding edits which have not been saved, and that runs keep using the last saved values until they are saved — with the wording of that sentence left to the implementation; then exactly one of "outside-workspace!" (file access is not confined to the workspace) or "workspace-scoped" (it is), one of which is always present; and "mode: {mode}", shown unconditionally — "Permission mode {mode}: how much agents may do without asking. Change it under the composer or in Settings → Runtime." Short forms and explanations use the same words as the Settings controls that produce them, so a flag can be matched to its setting by name.
- **REQ-SHELL-042**: The branch item shows a branch icon in accent color (re-rendered on theme change), the branch name, and an "↑{n}" ahead marker; its tooltip names the branch and states how many commits it is ahead, with a noun agreeing with that number under REQ-SHELL-044 and its wording otherwise left to the implementation.
- **REQ-SHELL-043**: The model item is painted at full text strength rather than the muted treatment used by its neighbours, and carries the tooltip "Runs started from this window use {model}. Change it in the composer or in Settings → Models."
- **REQ-SHELL-044**: The tokens item reads the running total of tokens used, its digits grouped into thousands with commas, then a space, then "tok" — for example "12,480 tok". The background-sessions item reads the number of sessions currently in the background followed by a noun that agrees with that number ("1 bg session", "3 bg sessions"). This is the general rule for the whole shell: wherever a count is shown with a noun, the noun agrees with the count, and the literal parenthesised "(s)" form is never rendered anywhere in the product. Neither of these two items is hidden at a count of zero — a count of zero is a known value, unlike the unavailable figures REQ-SHELL-045 and REQ-SHELL-046 withhold — so before any tokens have been consumed the strip reads "0 tok", and with no background sessions it reads "0 bg sessions", subject only to the responsive hiding of REQ-SHELL-047.
- **REQ-SHELL-045**: No cost item is present until at least one session has reported usage and a cost figure exists for it; the word "cost" is never shown in the strip without a figure preceding it. Once present the item reads "{figure} cost", the figure being the model provider's reported cost for this workspace's runs so far, or the literal "n/a" for a model with no published pricing. The figure is rendered by the product's single money rule (REQ-PROVIDER-121) and by no other: exact decimal arithmetic rather than binary floating point, rounded half-up, to two decimal places — or to four when the magnitude is below $0.01, so a cost that is small but not nothing is never rendered as zero. The currency is the one the provider reports the cost in, shown as the symbol $, € or £ for USD, EUR and GBP and otherwise as the amount followed by the upper-cased currency code. Costs reported in different currencies are never added together into one figure; where this workspace's runs have been billed in more than one currency, each currency is shown as its own figure within the item, separated so that each remains individually readable. Its tooltip and accessible description read "Cost of this workspace's runs so far: {figure}. Reported by the model provider; an unpriced model reads n/a."

### Commands, shortcuts, palette, and keyboard help

- **REQ-SHELL-048**: The window offers one vocabulary of named actions, and every surface presents it the same way: an action that has a keyboard shortcut appears in the command palette under the same label with that shortcut shown beside it, appears in the keyboard-help dialog (REQ-SHELL-054), and appears in the composer's slash catalogue (REQ-SHELL-056). None of those surfaces offers an action the others omit, with two exceptions: the composer-only additions enumerated in REQ-SHELL-056, and the Escape overlay-dismissal entry, which is excluded from all three surfaces alike — it appears in neither the command palette, nor the keyboard-help dialog, nor the composer's slash catalogue. Escape is a contextual dismissal rather than an invocable action: it has nothing to do when there is nothing to dismiss, so listing it among things the user may choose to do would offer an action the window often cannot carry out. Its label "Close current overlay" exists to name the binding in this document, not to be presented as a command. The convention itself stays discoverable because keyboard help states it in prose (REQ-SHELL-054) and because the drawer close controls name it in their tooltip (REQ-SHELL-062). No surface presents an action the window cannot carry out. Shortcuts fire only while a Rotaris window holds keyboard focus and have no effect while another application is focused.
- **REQ-SHELL-049**: The authoritative shortcut table: Ctrl+1 … Ctrl+7 open the seven views in view order (labels "Open Overview", "Open Workspace", …); Ctrl+K opens the command palette; Ctrl+, opens Settings ("Open Settings"); Ctrl+F opens transcript search ("Search transcript"; switches to Workspace and opens the search panel); Ctrl+L focuses the run composer ("Focus run prompt"; switches to Workspace); Ctrl+Return starts or continues a run ("Start or continue run"; switches to Workspace and submits only when the send control is enabled); Ctrl+Shift+T opens the terminal window ("Open terminal"); F1 shows keyboard help ("Show keyboard help"); Escape carries the label "Close current overlay", with the scope and precedence defined in REQ-SHELL-055. "About & Legal" is a palette-only entry with no shortcut.
- **REQ-SHELL-050**: Composer key handling: Enter submits when the composer has focus; Shift+Enter adds a line break instead of submitting; Ctrl+Return is the window-wide fallback submit.
- **REQ-SHELL-051**: The command palette is an application-modal dialog titled "Rotaris commands", 560×420, accessible name "Rotaris command palette", containing a heading "Commands", a filter field (placeholder "Type an action…", accessible name "Filter commands"), and a results list (accessible name "Available commands").
- **REQ-SHELL-052**: Palette filtering is a case-folded substring match over each command's label, hidden keywords, and identifier; an empty query matches everything; the list refreshes on every keystroke; the first row is auto-selected whenever there are results; Return activates the current row; activation closes the dialog first and then runs the command.
- **REQ-SHELL-053**: Palette rows show the command label followed by its shortcut when one exists. Hidden keywords make commands findable by everyday words — e.g. the terminal command is found by "shell", "console", or "bash", but not by "worktree" — and the keywords themselves are never displayed.
- **REQ-SHELL-054**: F1 opens an informational dialog titled "Rotaris keyboard help" listing "{shortcut} — {label}" (shortcut emphasized) for every registered command that has a shortcut, excluding the Escape/overlay-dismissal entry. In place of that entry the dialog SHALL carry a short prose line conveying what Escape does and where it applies — that it closes the overlay in front, and only on the Workspace view (REQ-SHELL-055) — so the convention is discoverable without being offered as a command; the wording of that line is left to the implementation.
- **REQ-SHELL-055**: Window-level Escape is live only while the Workspace view is showing, and resolves in this order: (1) with the transcript search panel visible, the panel closes and focus returns to the composer; (2) otherwise both compact overlay drawers close and the layout reflows. On the other six views, window-level Escape produces no effect. Modal surfaces answer Escape themselves and always before the window sees it, so while any modal surface is open window-level Escape never fires. The command palette (REQ-SHELL-051) and the keyboard-help dialog (REQ-SHELL-054) close on Escape with no command run and nothing changed. Every confirmation, warning and save/discard/cancel dialog this document defines treats Escape as identical to its declining answer, carrying the same consequences that answer carries: the unsaved-settings dialog blocks the transition (REQ-SHELL-124), the kill confirmation leaves the process alone (REQ-SHELL-092), the quit prompt aborts the close (REQ-SHELL-119), and the no-credit confirmation starts no run (REQ-SHELL-158). One qualification applies throughout: where a declining answer would additionally open an external page or hand something to an external handler, Escape performs the refusal alone and does not perform the external open — dismissing a dialog never launches anything outside the application. An informational dialog whose only answer is acknowledgement closes on Escape, which acknowledges it. The indeterminate non-cancellable progress dialog of REQ-SHELL-117 does not close on Escape at all, because it has no answer to give.
- **REQ-SHELL-056**: The composer's slash-command catalogue is the one REQ-CHAT-028 to REQ-CHAT-034 define, and this document holds no copy of its membership, of the description any command carries, of the reason an unavailable command gives, or of when the catalogue is rebuilt. What this document relies on that catalogue for is that every command-palette entry of REQ-SHELL-049 is also reachable by typing, which is the third surface of the one action vocabulary REQ-SHELL-048 requires, and that a mirrored entry keeps the description, behaviour and availability gating the catalogue's own entry for that name already fixes. What this document contributes to it is the naming of a generated entry. Each generated entry — one per user-invocable skill — SHALL take its name from the skill's declared name reduced to catalogue normal form: lower-cased, each run of whitespace or underscores replaced by a single hyphen, every character outside `a`–`z`, `0`–`9` and `-` removed, and leading and trailing hyphens trimmed; a declared name that reduces to the empty string yields no entry at all. Its description SHALL be the skill's own one-line description where it declares one, and otherwise a sentence stating that the skill is available and naming it. Built-in commands SHALL always win a name collision: when a generated name equals a built-in command's name, or a generated name already accepted in the same rebuild, the entry SHALL be offered under the first free name formed by appending `-2`, `-3`, … to it, and its description SHALL additionally name the skill it came from — so a skill is never silently unreachable from the composer and a built-in command never changes meaning because a skill was installed. `/model <name>` and `/persona <name>` take their arguments from configuration and generate no additional catalogue entries.
- **REQ-SHELL-057**: Shortcuts are written with the host platform's own key names — "Ctrl" on Windows and Linux, the command symbol on macOS. A chord string is split on "+", and a trailing "++" denotes the plus key. Each key is drawn as a separate keycap in small monospace inside a hairline border, but assistive technology receives the whole written sequence as one accessible name: a three-key chord is never announced as three unrelated labels. A sequence that cannot be parsed is displayed verbatim.
- **REQ-SHELL-058**: Any element that shows a tooltip exposes that identical sentence as its accessible description, whether or not the element takes keyboard focus, with the platform-formatted shortcut appended in parentheses where the element has one. No information in the shell is available on hover alone.
- **REQ-SHELL-165**: A shortcut of REQ-SHELL-049 that the host operating system or the active input method has already claimed SHALL NOT be contested. Given a chord the host or an active IME consumes before the window sees it, when the user presses that chord, then the product SHALL take no action for it and SHALL NOT intercept, re-register, or otherwise work around the host's claim. The binding SHALL NOT be silently remapped to some other chord: a shortcut this document names is that chord or nothing. No action is lost to a claimed chord, because every shortcut-bearing action is also a command-palette entry and a slash-catalogue entry (REQ-SHELL-048), and the palette needs only Ctrl+K — or, if that too is claimed, the palette entry reachable from the composer catalogue. Where the product can determine that a chord it registered will never be delivered to it, the keyboard-help dialog (REQ-SHELL-054) and the palette row (REQ-SHELL-053) SHALL present that action with no shortcut beside it rather than presenting one that does nothing. Where it cannot determine that — the ordinary case, since hosts do not generally publish their reservations — the chord is still shown, and no notification, banner, or error is raised about it.

### Resizable panes: dividers, persistence, reset

- **REQ-SHELL-066**: Every multi-pane divider has a 6 px grab area painting a hairline, and can never collapse a pane below that pane's minimum size.
- **REQ-SHELL-067**: Divider drags persist the resulting sizes with a 250 ms debounce; sizes are also captured immediately at moments such as entering compact mode. Capture before first layout is a silent no-op (uninitialized sizes are never persisted).
- **REQ-SHELL-068**: Every divider is keyboard-operable: it takes focus, carries an accessible name beginning with "Resize " (every multi-pane view names its dividers), arrow keys move it by 16 px (left/up shrinks, right/down grows, orientation-aware, clamped at the neighbor's minimum), and Home restores that divider's declared defaults and persists them.
- **REQ-SHELL-069**: Pane layouts are remembered per user and not per workspace: opening a second workspace shows the same pane sizes as the first. They live under the `panels/` namespace of the per-user preference store, keyed by a per-view string that is stable across releases, alongside that view's pane count and one schema-version stamp covering every stored layout (currently 1). Declared defaults are restored instead of stored values whenever nothing is stored, the stored version is not 1, the stored pane count differs from the view's current pane count, or the stored state is empty. Integer values are parsed tolerantly, so a value returned as a string is accepted. Pane sizes are never written under `workspaces/`. The per-view key strings are exactly the lower-cased view names of REQ-SHELL-023 — `overview`, `workspace`, `mission`, `requirements`, `git`, `library`, `settings` — and a view carrying more than one independent multi-pane arrangement keys each of them `{view}.{arrangement}`, the arrangement part being a lower-case ASCII identifier that view declares. A key that has been used is never reassigned to a different view or arrangement: the vocabulary may gain a key and a key may be retired, but a retired key is never reused, so a stored layout written by an older release can only ever fail to match and fall back to declared defaults — it can never be applied to the wrong panes.
- **REQ-SHELL-070**: Settings offers exactly one control for this, accessible name "Reset panel sizes". Activating it takes effect immediately and asks for no confirmation: every registered divider in every view — including views not on screen at the time — is at its declared default size afterwards, and the notification "Panel sizes reset to defaults." is shown. The result outlives the process: after a relaunch every divider is still at its declared default.
- **REQ-SHELL-071**: A view whose dividers declare no default sizes still opens with a determinate split: the same view at the same window size always produces the same pane proportions, no pane opens at zero size, and no pane opens below its declared minimum. The split is computed by equal division subject to minimums, and by no other rule: the space available along the divider's axis, less the space the dividers themselves occupy, is divided equally among the panes; any pane that equal division would leave below its declared minimum is fixed at that minimum and removed from the division, and the remaining space is divided equally among the panes still free, repeating until no pane is below its minimum. Rounding of the remaining logical pixels goes to the leading panes — leftmost for a horizontal split, topmost for a vertical one — one pixel each in order, so the result is exact rather than approximate; the acceptance tolerance is one logical pixel per pane. Where the minimums together exceed the space available, every pane takes its minimum and the view is at the size below which REQ-SHELL-022 refuses to resize. Once such a divider is dragged, the dragged sizes are persisted and restored under REQ-SHELL-069 like any other.

### Terminal output grid

- **REQ-SHELL-095**: Terminal output is presented as a character grid rather than an append-only text log, which is checkable by behaviour: a command that addresses the cursor overwrites the cells it addresses instead of appending new lines; a command that enters the alternate screen replaces the visible content and, on leaving it, restores what was there before; and a progress indicator that rewrites its own line is seen updating in place, not repeated line after line. The grid renders the screen state it is given and emits the user's keystrokes; its accessible name is "Terminal output", and it accepts keyboard focus both by click and by Tab traversal.
- **REQ-SHELL-096**: Key encoding vocabulary sent to the backend: arrow keys → UP/DOWN/LEFT/RIGHT; Home/End → HOME/END; Page Up/Down → PGUP/PGDN; Tab → TAB; Backspace → BS; Esc → ESC; Return/Enter → ENTER; Ctrl+A…Z → "C-{lowercase letter}". Printable text is sent verbatim. A key with no encoding in this vocabulary produces no transmission at all; the grid does not substitute some other sequence.
- **REQ-SHELL-097**: Key handling priority, in order: (1) copy beats interrupt — Ctrl+C with an active selection (and Ctrl+Shift+C always) copies instead of interrupting; (2) Shift+Tab always moves focus out and is never forwarded, so keyboard focus can always leave an armed terminal; plain Tab also traverses while unarmed; (3) scrollback keys — Page Up/Down and Home/End scroll local history while unarmed; while armed, their Shift- or Ctrl-modified forms still scroll and the unmodified forms go to the process; (4) while unarmed, any printable or named key raises the rejected-input event and is consumed; (5) while armed, keys are forwarded per REQ-SHELL-096.
- **REQ-SHELL-098**: The grid's background is the theme's terminal background colour, and that colour fills the entire widget area throughout a window resize, so no frame ever exposes the platform's default surface colour. The 16 ANSI colours are theme tokens. Reverse video swaps a cell's foreground and background; bold, italic and underline are applied per cell; selected cells are filled with a dedicated selection colour. The cursor is painted only when all three of these hold at once — the process is running, the grid has keyboard focus, and the view is scrolled to the tail — and it is drawn as a filled block while control has been taken and as a hollow outline while the terminal is read-only.
- **REQ-SHELL-099**: The grid's accessible description states the input mode, switching between "Live output of the running command. You have control: what you type is sent to the command. Shift+Tab leaves the terminal, Shift+Page Up scrolls back." and the equivalent ending "Read-only until you take control."
- **REQ-SHELL-100**: Geometry: cell size derives from the theme's monospace face and is re-measured on theme change, after which the grid dimensions are re-reported (otherwise a running command would keep writing into a stale-shaped screen); a fixed 6 px padding gutter surrounds the grid; the grid never reports fewer than 20 columns × 4 rows; the preferred size is 80×24 cells. Grid dimensions are reported to the backend only while the grid is visible and meaningfully laid out, and only when they change — a placeholder-size viewport must never shrink the emulated screen and discard output.
- **REQ-SHELL-101**: Scrollback behaviour: the vertical scrollbar's range equals the number of retained history rows; a refresh leaves the view at the tail only when it was already at the tail, and otherwise leaves the visible rows where they are; wheel scrolling moves the view in the wheel's direction by an amount proportional to the wheel delta, one standard wheel notch scrolling exactly 3 rows and a high-resolution or fractional delta scrolling in the same proportion, with the fractional remainder accumulated across events so that slow continuous scrolling loses no motion and eventually advances a row; scrolling is clamped at both ends of the retained history and never wraps; dragging selects whole cells and yields the same selection whether it was dragged forwards or backwards; text extracted from a selection right-trims each row and joins rows with newlines; and a copy attempted with an empty selection puts nothing on the clipboard and reports failure.

### Terminal stream state, delivery, and audit

- **REQ-SHELL-102**: For any one stream, the transcript preview and the terminal window show the same thing at the same time: identical visible screen cells, identical running-or-exited state, and identical truncation indication. Moving between the two never shows the user older output in one than in the other.
- **REQ-SHELL-103**: A command's execution is not throttled by the terminal display. Its completion time and its output are the same whether the terminal window is open, closed, hidden or visible, and when repaints cannot keep up with the rate at which output arrives, no output is dropped and none is shown out of order. The rate at which frames reach the display is bounded in aggregate across every live stream by REQ-MONITOR-306, which this requirement cites rather than restating: that bound is on delivery and never on the command, and it is honoured by delivering the same output in larger steps rather than by dropping any of it.
- **REQ-SHELL-104**: Opening a terminal for a command that has already produced output shows the retained output at once — the grid is never blank while history exists for that stream — and no line is ever shown twice, including in the moment when retained output and freshly arriving output are both being displayed. A session read back from storage produces no terminal tabs at all, so commands that ended before the session was stored never appear as live terminals.
- **REQ-SHELL-105**: Stream metadata updates synchronize the displayed command, truncation flag, and running state, and may be applied idempotently. A stream transitions from running to closed exactly once, recording the exit code. The count of running streams feeds the toolbar control. Starting a new session clears all stream state; attaching to another session supersedes the earlier attachment; detaching keeps existing screens readable.
- **REQ-SHELL-106**: Write-back semantics: sending keys to a stream that no longer accepts input fails predictably (reported per REQ-SHELL-094); a resize always resizes the emulated screen — even when the backend is gone — and then the real terminal when possible; kill succeeds only when the stream has a registered kill capability and otherwise reports failure; whether input can be taken at all is queryable and drives control enablement.
- **REQ-SHELL-107**: User terminal input is not an agent tool call: it bypasses permission patterns but is written to the session's permission audit log as user-originated input. Typed characters accumulate per stream and are written to the log as a single entry when Enter submits the line — a held key must not flood the log; Backspace removes from the pending buffer; navigation keys are not logged; a control sequence flushes the pending line and then logs "sent C-{letter}"; taking control, releasing control, and kill log their own sentences. Both the typed line and the command context are secret-redacted before logging. See Data & Formats for the entry shape.
- **REQ-SHELL-108**: The Workspace toolbar terminal control is always enabled, including before any command has ever run, so the feature stays discoverable from a cold start. Its label is "Terminal" or "Terminal ({n})" when any stream is live; accessible name "Open terminal" or "Open terminal ({n} running)"; its tooltip/description states total and running counts, or explains that a terminal appears when an agent runs a command. The total count only ever climbs within a session.
- **REQ-SHELL-109**: Auto-open preference (default off, persisted): when a stream changes while the window is closed, the preference is on, and that stream is running, the terminal window opens without taking keyboard focus. The window is never auto-opened for a stream that has already exited.
- **REQ-SHELL-110**: When session focus changes: stream state is cleared, the terminal window (if open) is closed, streams re-attach to the newly focused session, and the toolbar count resets; if the window had been open, it reopens for the new session without taking focus, so a user who was watching a terminal does not silently lose the window. Focusing an empty session identifier leaves everything closed.
- **REQ-SHELL-111**: Starting a new session closes and discards the terminal window, clears all stream state, resets the toolbar count to zero, and also closes all persona windows and artifact dialogs.

- **REQ-SHELL-166**: Interactive terminal input and resize SHALL be demonstrated against a real pseudo-terminal rather than a simulated stream, and SHALL meet the following criteria while a command that echoes its input is running. Echo latency: with take-control armed, the character a keystroke produces is visible in the grid within the 100 ms gesture budget of REQ-SHELL-150, measured from the key press to the frame that shows it. Ordering and fidelity: keystrokes reach the process in the order they were pressed with no character dropped, duplicated, or reordered, and what reaches it is exactly the vocabulary of REQ-SHELL-096 — a control chord arrives as its control byte, printable text arrives verbatim, and a key with no encoding transmits nothing at all. Interrupt and end input: a running command that acts on them is observably affected within 500 ms of the control being activated. Resize: once a grid resize has settled, the size the process itself reports for its terminal equals the columns and rows the grid last reported, no later than the first output the process writes after the resize; a full-screen program repaints to the new size with no corrupted cells; and the emulated screen is resized even when the backend is gone (REQ-SHELL-106). Throughput: a command producing output faster than the grid can repaint still finishes with the same output and the same exit status it would have produced with no terminal window open at all (REQ-SHELL-103).

### Window close, quit protection, shutdown

- **REQ-SHELL-119**: Window-close guards are evaluated in this fixed order, and any of them can abort the close: (1) with unsaved settings present, a user-initiated close raises the save/discard/cancel dialog of REQ-SHELL-124, where Cancel aborts the close; (2) while a worktree integration is running, the close is refused unconditionally by an informational dialog titled "Integration in progress" whose body reads "Keep Rotaris open until the isolated worktree integration finishes."; (3) with runs active, a user-initiated close asks "Quit while a run is active?" — "Quit while {n} runs are active?" for more than one — states that Rotaris will request shutdown of the run(s) and that in-flight work may not finish, and offers Yes and Cancel with Cancel as the default; any answer other than Yes aborts the close.
- **REQ-SHELL-120**: Once the guards pass, the window is committed to closing: no new background work may start on the closing window.
- **REQ-SHELL-121**: Shutdown is clean and complete, and is checkable from outside the process. Active runs are asked to stop before the process ends, and no run keeps consuming a model provider afterwards. Once the last main window has gone, no persona window, artifact dialog or terminal window is left on screen — the one running instance may hold several main windows at once (REQ-STARTUP-161), and closing one takes only its own auxiliary windows with it (REQ-SHELL-123). A diagnostics run that was in progress leaves a complete, readable diagnostics directory rather than a truncated one. An update download that was in progress leaves behind no partially written and no locked file. The shutdown itself raises no error dialog and produces no crash report.
- **REQ-SHELL-169**: A launch of the application that arrives while this instance is shutting down SHALL be refused rather than admitted, and SHALL be honoured once the shutdown has finished. Shutting down means the interval that begins when the ordered shutdown effects REQ-MONITOR-131 fixes begin and ends when the process ends, the force-exit allowance that requirement carries included; this document holds no copy of that allowance. Throughout that interval the instance SHALL build no window for the launch, SHALL open no workspace for it, and SHALL start and write nothing on its behalf — in particular the window REQ-STARTUP-162 would otherwise have an instance with no window open build for a launch SHALL NOT be built while this interval is running. Admitting the launch would mean two instances of the application briefly existed, which REQ-STARTUP-161 exists to prevent, at the moment the product is least able to reason about its own state; refusing is also the shape REQ-STARTUP-161 already has, since a launch never starts a rival process.

  The instance SHALL answer the launch rather than ignore it, and its answer SHALL convey that the application is shutting down. Silence is not equivalent to refusal here: a launch that goes unanswered treats the instance as unreachable and reclaims the record after the interval REQ-STARTUP-164 fixes, which is the path that requirement keeps for a process that *cannot* answer, and taking it for a process that can answer would produce the two simultaneous processes this refusal exists to avoid.

  What the user is told. Where a main window of the shutting-down instance is on screen, that window SHALL be surfaced on the terms REQ-SHELL-161 fixes, and it is already stating that stopping is under way and how much of the allowance remains (REQ-MONITOR-283); no dialog, banner, notification or error SHALL be raised in addition, and no surface SHALL report that a launch was refused. Where no window of that instance is on screen, the user SHALL still be told that the application is finishing shutting down and will open when it has, so that a launch which appears to do nothing for the length of the allowance is not mistaken for one that failed. REQ-STARTUP-162's silence governs a launch that has been handed over and has ended; a launch that has been refused and is waiting is neither, and what that waiting launch shows is domain 11's to state rather than this document's.

  What happens once the shutdown has finished. The refused launch SHALL resume resolving the instance record on the terms REQ-STARTUP-164 fixes, and SHALL reach the outcome that requirement requires — exactly one instance running and a window on screen — later than an admitted launch would have reached it rather than not at all. Where the record was released as the process ended, the launch becomes the running instance and opens a window, honouring any workspace directory it carried exactly as REQ-STARTUP-163 requires of a launch that becomes the instance. Where the record instead passed to a successor rather than being released, as it does during the update restart of REQ-STARTUP-121, the launch is handed to that successor, which is not itself shutting down; in neither case does a third process start. The wait is bounded, because the force-exit allowance guarantees the process ends; and where a force exit leaves the instance record behind, REQ-MONITOR-131 having permitted the ordered effects to be left incomplete, the launch resolves that record exactly as REQ-STARTUP-164 already resolves one naming a process that is no longer running. A waiting launch SHALL NOT hold the exiting instance open, delay its teardown, or change when the force exit falls due: the refusal costs the user the remainder of the shutdown and nothing else.
- **REQ-SHELL-122**: The count the quit prompt reports is the number of runs active at that moment: on a host that coordinates several sessions it is the number of sessions currently running; on a single-run host it is 1 while a run is active and 0 otherwise. The prompt's singular and plural wording follows that number (REQ-SHELL-119, REQ-SHELL-044). A session counts as an active run exactly when its displayed status (REQ-SHELL-036) is busy under REQ-NOTIFY-050, which is the single definition of that test; this document holds no copy of the member list it draws on. Those are the statuses in which work is still in flight and a model provider may still be consumed, and the remaining members of REQ-NOTIFY-048 do not count, because quitting in those states loses no in-flight work, which is the only thing the prompt warns about. That same four-status test is what "a run is active" means throughout this domain: the workspace-open gate of REQ-SHELL-021, the close guard of REQ-SHELL-119, and the refusals of REQ-SHELL-125 and REQ-SHELL-126 all apply it. REQ-SHELL-155 is the one exception and states its own stricter test, under which a run whose liveness cannot be determined counts as live.
- **REQ-SHELL-123**: Auxiliary windows (persona, terminal) belong to their main window and are destroyed with it even if an explicit close was missed; a terminal window that outlives its stream attachment shows retained screens read-only.
- **REQ-SHELL-124**: The unsaved-settings dialog is a warning titled "Unsaved settings" asking "Save workspace settings before leaving?" with the informative line "Discard restores the last saved values." and buttons Save (default), Discard (destructive), Cancel. Save proceeds only if saving succeeds (a failed save blocks the transition); Discard restores the saved values and proceeds; Cancel blocks. The same gate protects leaving the Settings view, opening another workspace, and closing the window.

### Shell accessibility contract

- **REQ-SHELL-144**: Two contrast thresholds apply: 4.5:1 for normal text, and 3:1 for large text — 18 px or larger, or 14 px or larger when bold — and for non-text boundaries such as borders, focus rings and icons. Measured over all seven primary views and every tab page inside them: no interactive control announces an empty accessible name, and every rendered label meets its threshold against the background actually painted behind it once all styling has been applied.
- **REQ-SHELL-145**: Theme tokens carry these guarantees, each measured against every background the token is actually painted on: every state text colour (running, waiting, done, info, fail), the primary, secondary and tertiary text colours, and the readable accent shade clear 4.5:1 on every text background; strong borders and the focus colour clear 3:1 on every boundary background; a primary button's label stays at or above 4.5:1 in its rest, hover and pressed states; disabled text is dimmer than enabled text — below half the enabled contrast ratio — while still clearing 3:1; every persona base colour and every shade given to a concurrently running instance clears 4.5:1, and no two concurrently running instances are given the same shade.
- **REQ-SHELL-146**: Auxiliary windows meet the same contract independently of the main sweep: the terminal window has all controls named and no contrast violations both while a command runs and after it exits, and its empty state is announced and explained.
- **REQ-SHELL-147**: Every dropdown in every primary view sizes itself to its selected entry (over-long values may elide visually but are announced in full); a dropdown must never visually swallow its current value when space is tight.
- **REQ-SHELL-148**: Self-painted navigation controls draw the keyboard-focus ring entirely within their own bounds, at the theme's focus-ring width and color, so no part of the ring is cut off; divider handles take focus and are named (REQ-SHELL-068).
- **REQ-SHELL-160**: Four properties of this contract are settled from rendered output on a real display and not from theme tokens, and each has the acceptance criterion given. (a) **Contrast**: the ratios of REQ-SHELL-144 and REQ-SHELL-145 are measured from the pixels actually painted, sampling the rendered label against the rendered background behind it after all styling, states and overlays have been applied — a token pair that computes correctly but paints over a different surface fails. (b) **Native surfaces**: on each supported platform, and in each built-in theme, the native dialogs, menus, text caret and disabled text of REQ-SHELL-130 are inspected on screen; the criterion is that no native surface presents a light background while a dark theme is active, or the reverse, and that text on those surfaces still clears 4.5:1. (c) **Focus indication**: on each supported platform every focusable control of REQ-SHELL-148, including self-painted navigation controls and divider handles, shows a focus ring that is wholly within the control's own bounds and clears 3:1 against the surface it is drawn on. (d) **Scaling**: the icon rule of REQ-SHELL-030 is measured at 100%, 125%, 150%, 175% and 200% OS display scaling, and again after the window is dragged between two monitors set to different scale factors; the criterion is that the icon covers its declared logical size within one device pixel in each case and is never drawn from artwork smaller than the required raster. A build that cannot demonstrate all four does not meet this domain's accessibility contract.
- **REQ-SHELL-149**: State is never conveyed by color alone anywhere in the shell: the session chip carries the status word beside its dot; the take-control button re-labels for its state; transient acknowledgement kinds carry the word-form accessible names REQ-NOTIFY-019 fixes; the active theme is shown as text; keycap sequences announce the written chord; demo-mode and service-unavailable refusals use explicit messages — exactly "Artifacts are read-only in demo mode.", "Artifact not found in the loaded session.", "Proposal actions are unavailable in demo mode.", "Settings are read-only in demo mode.", "Worktree integration is unavailable in demo mode.", and "Runs are unavailable in demo mode."

### Update responsiveness

- **REQ-SHELL-150**: A rapid succession of changes never makes the shell unresponsive and never leaves it showing stale content. A single isolated change is visible without perceptible delay. While changes keep arriving, the affected surface is redrawn at least once every 120 ms, and after the last change of a burst the surface shows that final change. No intermediate state of a burst is required to be drawn. These are the numeric acceptance thresholds, all measured while the shell is under a sustained burst of changes at a rate the display cannot match: a user gesture — a keystroke, a click, a view switch, a divider drag — is acknowledged on screen within **100 ms** of the gesture; the interval between consecutive repaints of a surface that has pending changes never exceeds **120 ms**; and the final state of a burst is on screen within **120 ms** of the last change arriving. A build that misses any of the three under sustained load fails this requirement, whatever its average behaviour.
- **REQ-SHELL-151**: A surface that is not on screen — a hidden or closed window, or a panel behind another view — consumes no redraw work while it is not on screen, and shows fully current content the instant it becomes visible: it never presents a stale frame first, and no catch-up redraw is visible after it appears. This holds for the persona windows, for the terminal window, and for the shell's panels. The acceptance criterion for "consumes no redraw work" is stated as work rather than as a CPU share, because it must be checkable on any hardware: while a surface is off screen, zero repaints of that surface are performed and zero repaint or refresh timers belonging to it are running, however fast changes arrive for it. When it becomes visible again, its first painted frame already carries the current state, and it reaches that visible state within the **100 ms** gesture budget of REQ-SHELL-150.

### Tab strips and vertical navigation lists

- **REQ-SHELL-152**: Tab strips throughout the shell behave alike. When a strip first appears, its first tab is the active one. From the keyboard, Left and Right move to the neighbouring tab and select it in the same step, Home selects the first tab and End the last, and movement stops at either end rather than wrapping around. Switching tabs exchanges panes that are already built, so no tab shows an intermediate blank state. A selection restored from a stored key the strip does not contain leaves the tab that is currently active still active — for example, a stale `interface/settingsTab` value falls back to the models category — and never clears the selection. A selection the user did not make produces no effect beyond showing that tab's pane.
- **REQ-SHELL-153**: Vertical navigation lists throughout the shell behave alike. Arrow Up, Arrow Down, Home and End move focus without changing the selection, and selecting requires Space or Enter, so moving focus across entries never causes the passed-over destinations to be shown. The selected entry is marked by a rule down its left edge, and its accessible description says so in words: "Selected, marked with a rule down its left edge." for the selected entry and "Not selected." for the others. Entry glyphs are sized from the theme's type scale, so icons grow when text does. The main window's navigation rail is not a vertical navigation list in this sense: it follows the button semantics of REQ-SHELL-027 through REQ-SHELL-032.

### Miscellaneous shell behaviors and edge cases

- **REQ-SHELL-154**: Artifact detail dialogs are per-artifact windows: a repeat request for the same artifact raises the open dialog instead of opening a second one; in demo mode the request is refused with "Artifacts are read-only in demo mode."; an unknown artifact identifier answers "Artifact not found in the loaded session." All artifact dialogs close on window close and on new session.
- **REQ-SHELL-155**: Restoring a checkpoint while a run is live is refused, and a run whose liveness cannot be determined counts as live for this purpose, so the restore is refused there too. The refusal SHALL be reported on the transient error notification of REQ-SHELL-112, the same surface the workspace-open and new-session refusals use, and SHALL convey three things: that nothing was restored; that the reason is a live run, or that liveness could not be read and is therefore treated as live; and that finishing or cancelling the run makes restore available. The wording is left to the implementation. A refused restore SHALL change nothing at all — no file, no checkpoint record, no view contents — and SHALL leave the checkpoint listing exactly as it was, so a refusal is never a partial restore. **That refusal is a condition holding for the whole of the restore and not a test taken once**, on the terms REQ-SESSION-164 fixes; this requirement holds no copy of them and states no window of its own. What follows here is only what the shell owes: a restore refused because a session became live after the question was answered SHALL be reported on the same surface, in the same terms, as one refused at the moment it was asked — the user is not shown a different kind of failure according to when the refusal was reached. A session recorded as running whose process is no longer present has its recorded status corrected, and the correction is announced through a WARNING notice titled "Session marked interrupted". **That title and that shape are the SINGLE-session case, and a repair that corrects several sessions at once is announced once rather than once each** (accepted amendment 2026-09-06, OQ-46). One repaired session SHALL keep the title above word for word. A batch SHALL raise exactly one WARNING notice that conveys how many sessions were repaired, names them, and carries an action routing to the surface the affected-session list is reached from; its own title is left to the implementation, subject to being distinguishable from the singular one. The action SHALL be a member of REQ-NOTIFY-044's closed vocabulary and this amendment adds none to it. The realistic failure is plural rather than exceptional — a run-host crash stales one session per in-flight run, and concurrent runs are a supported shape (REQ-MONITOR-249 to REQ-MONITOR-258) — so five notices saying the same thing about five identifiers is not a report of it. **Every repaired session still receives its own timeline entry** (REQ-SESSION-062); this requirement governs what is shown and never what is recorded. **Continuation is offered only once the relevant batch has settled**: no session of a batch may be offered for continuation while another session of that same batch is still being repaired, so the list the user acts on is never a partly repaired one. At startup the window requests the checkpoint listing for the session that is selected first.
- **REQ-SHELL-156**: While the checkpoint backend is busy, a checkpoint-listing request retries every 150 ms with a single pending retry that always targets the latest requested session — clicking quickly from one session to the next cannot accumulate queued retries.
- **REQ-SHELL-157**: Prompt history and stash persist per workspace and survive a restart with no action by the user; where they are held is REQ-LIBRARY-138's and this document names no location. No partly applied change to either list is ever observable, and no leftover working state is left behind by a save. A failed save raises the persistent notice "Could not save prompt history" — "Rotaris will keep prompts in memory for this window." — and prompts continue to work in memory for that window.
- **REQ-SHELL-158**: When the most recently polled cloud-credit balance shows no credit, starting a run raises a confirmation offering "Start anyway". It is raised on either condition, and either alone is enough: the polled balance is at or below zero, or that same poll reported the service declining new work (admission not allowed, REQ-PROVIDER-130). The two need not agree, and no reconciliation between them is attempted. The confirmation's title and body SHALL convey three things — that the account has no credit or is being refused new work; that a run on a cloud model may therefore fail partway or not start at all; and that the choice is between starting anyway and topping up — with their wording left to the implementation. It offers exactly two answers: "Start anyway", and a declining answer whose own label states that it opens the account page; the declining answer is the default. The confirmation is answered from that already-polled balance: no network request is made between the user asking for the run and the confirmation appearing, so the confirmation cannot be delayed by a slow or unreachable cloud service. Choosing "Start anyway" starts the run; choosing the declining answer starts no run and opens the cloud account page in the default browser; dismissing the dialog with Escape starts no run and opens nothing (REQ-SHELL-055).
- **REQ-SHELL-159**: A workspace's composer draft is stored under `workspaces/{workspace-key}/composerDraft` in the per-user preference store, with the empty string as its default, and is written with debouncing while the user types rather than on every keystroke: the write is issued 400 ms after the last keystroke, and is additionally flushed immediately — without waiting out the interval — whenever the composer loses focus, the active view changes, the workspace is replaced, or the window closes. Survival of an abnormal termination is deliberately not promised, and the bound is stated instead: a power loss or a killed process may lose at most the keystrokes of the last debounce interval, and nothing earlier, because every deliberate departure from the composer has already flushed. A draft is never left half-written: a write either lands whole or does not land, so the text read back is always text the user actually typed at some moment. The text standing in the composer when the workspace is closed is the text the composer holds when that workspace is opened again.
- **REQ-SHELL-167**: Every numeric constant stated in this document is normative and individually checkable, with exactly one class of exception: a value qualified "in the default theme" is a theme token (REQ-SHELL-129), where the requirement is that the value is read from the active theme and that the default theme declares the stated number — another built-in or future theme may declare a different one, and the layout must follow it. In particular the following are normative and not merely the current values: the auxiliary window sizes 820×620 (REQ-SHELL-072) and 900×620 (REQ-SHELL-081), which are the sizes the window opens at when the display work area can hold them, and otherwise the largest size within that work area preserving the stated aspect — the user may resize freely afterwards, and this document does not require an auxiliary window's size to be remembered; the elision caps of 28 characters on a terminal tab label, 12 on a background-session identifier (REQ-SHELL-082) and 90 on a command label (REQ-SHELL-087), each counted in characters as the user sees them and each keeping the full text in the tooltip and accessible description; and the responsive thresholds of 1180 px and 1080 px in the status strip (REQ-SHELL-047) and 1180 px for Workspace compact mode (REQ-SHELL-059); and the 650 ms deferred first-paint delay (REQ-SHELL-011). A build that misses any of these misses the requirement that states it. The transient acknowledgement surface contributes no constant to this inventory: this document states none of its figures, which belong to REQ-NOTIFY-011, REQ-NOTIFY-013 and REQ-NOTIFY-022 and are cited from REQ-SHELL-112 and REQ-SHELL-113.
- **REQ-SHELL-168**: This window hosts the run surfaces REQ-ORCH-155 closes, the plan gate of REQ-ORCH-153 and REQ-ORCH-154 among them. Each is presented inside the primary view of REQ-SHELL-023 that carries the run it belongs to, and every action such a surface offers is an entry of the one action vocabulary of REQ-SHELL-048, so it is presented identically on every surface that vocabulary reaches. What each of those surfaces must convey is fixed by the requirement that names it, and this document holds no copy of it; what this document contributes is that they are hosted here rather than anywhere else, that they are reached like every other action, and that they carry the shell obligations every surface carries (REQ-SHELL-149, REQ-SHELL-135, REQ-SHELL-022). The plan gate is the one surface in this document that no dismissal answers: window-level Escape (REQ-SHELL-055) does not answer it, and neither does switching view, closing the view, nor closing the window — it resolves only through the three answers REQ-ORCH-153 fixes, because any other route would be the default answer that requirement forbids. A session waiting at that gate is consequently not an active run for the third close guard of REQ-SHELL-119 — it is waiting on the user rather than executing, and presents as paused under REQ-NOTIFY-049 — so closing the window raises no run-active prompt on its account, ends nothing, and leaves the decision still pending when that session is opened again.

## Data & Formats

### Application entry

The product has no command-line surface, no flags, no subcommands, no script-oriented output and no
meaningful process exit code. Every capability is reached from the desktop interface: a workspace
through REQ-SHELL-010 and REQ-SHELL-021, demo mode through REQ-SHELL-162, diagnostics capture
through REQ-SHELL-163, and the running version through REQ-SHELL-033 and REQ-SHELL-140. How many
processes that entry may produce is not this document's to fix: at most one instance of the
application runs per user account, and a further launch is handed to it rather than starting a rival
(REQ-STARTUP-161, REQ-STARTUP-162). Every window this document describes — main, persona and
terminal — is a window of that one instance, and several main windows on several workspaces are
ordinary rather than exceptional. The one case in which a launch is neither handed over nor made the
instance straight away is a launch arriving while this instance is shutting down, which REQ-SHELL-169
refuses for the remainder of the shutdown and honours once it has finished.

### Diagnostics capture vocabulary

Capture level is one of exactly `off`, `light`, `deep` — the value stored under `diagnostics/level`
and the only values the About-tab control offers (REQ-SHELL-163). `diagnostics/outputDir` holds an
absolute directory path chosen through the platform folder chooser, or is unset to mean the
product's own default location (REQ-STARTUP-131).

### Per-user preference store

Keys are slash-namespaced. The namespaces in use are `workspace/` (startup workspace state), `appearance/` (theme), `ui/` (motion), `interface/` (shell toggles), `display/` (transcript display), `panels/` (pane layouts), `updates/` (update state), `diagnostics/` (diagnostics capture), `requirements/` (requirements board state), `hooks/` (external hook enablement), and
`workspaces/` (per-workspace state).

This table is the registry REQ-SHELL-006 makes closed: every key the product may store is listed here, whatever document owns the behavior behind it, and a key absent from it does not exist. No key of any other form — in particular no dot-namespaced `desktop.*` key — is a key of this store.

### Per-workspace prompt storage

Prompt history and stash are held per workspace in the durable store the application keeps for it (REQ-LIBRARY-138); this document names no path and fixes no format. No partly applied change is observable and no leftover working state is left behind. Save failure degrades to in-memory behavior with a persistent notice (REQ-SHELL-157).

### Terminal stream event model

- Each terminal stream has a stable identifier shaped `{kind}:{key}`. Two kinds exist: `fg:` for an agent's foreground terminal, where the key identifies the agent, and `bg:` for a background-session terminal, where the key is the session identifier. An identifier carrying no `:` separator, or an unrecognized kind, resolves to the fallback display name "Terminal". These raw identifiers appear in permission-audit summaries but never in window labels or accessible names (REQ-SHELL-082).
- Output is delivered per stream as ordered frames carrying a monotonically increasing sequence number. Metadata frames convey command text, running state, and truncation state, and applying the same metadata frame twice has the same effect as applying it once; data frames advance the emulated screen. How fast frames may be delivered is not per-stream alone: the aggregate rate across every live stream is bounded by REQ-MONITOR-306, and this appendix holds no copy of that bound. A viewer that attaches after output has already been produced is given the output accumulated so far, and a frame whose sequence number has already been applied to a stream is not applied to it again (REQ-SHELL-104).
- Each live stream may expose a control surface with: send-keys (text plus an optional end-of-line), optional resize (columns, rows), and optional kill. Absence of a capability makes the corresponding UI action fail predictably.
- The key encoding vocabulary is the one REQ-SHELL-096 fixes, shared between user input and the agent's own input path; this appendix holds no copy of it.

### Permission audit entries for user terminal actions

Each entry records: decision `user-input`, source `user`, tool name `terminal`, the reason sentence "The user acted in the terminal directly; no policy applies.", and a summary of the form `terminal {stream-id}: {detail} (in: {command})`. One entry per submitted line of typed input; control sequences log as "sent C-{letter}"; take-control, release-control, and kill log their own sentences. Typed lines and command text pass through the shared redaction pass of REQ-TOOLS-171 before writing; this appendix states no redaction rule of its own.

### Bundled assets read by the shell

- A third-party license bundle as a plain-text file shipped inside the installed build (opened locally from the About page; may legitimately be absent).
- A build-identifier text file (single stripped line; absent/unreadable means no build id).
- A vector brand-mark asset (missing or unrenderable degrades to the "R" placeholder).
- Three bundled font families covering display, body, and monospace roles (failure to load falls back to host fonts).

Base `https://rotaris.ai` with paths `/privacy`, `/eula`, `/terms`, `/acceptable-use`, `/widerruf`, opened in the system default browser.
