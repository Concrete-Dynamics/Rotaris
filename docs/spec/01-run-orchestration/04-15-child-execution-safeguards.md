# Multi-Agent Run Orchestration — 15. Child Execution Safeguards

Part 4 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-088 – REQ-ORCH-112.

### 15. Child Execution Safeguards

- **REQ-ORCH-088** — A hard per-child timeout (default 1200 s) MUST bound each child's execution. On expiry: gracefully pause the child; then, if the role has a configured fallback model not yet attempted for this child, retry once on it; otherwise record the child failed with a timeout issue and a report of the form "Child timed out after <N>s" carrying the last/final response extracted from the transcript.

> **Extended by [`PD-ORCH-017`](../../product/directives/pd-orch-017.md#pd-orch-017):** delegated children have no fixed model-step cap; this timeout still applies.

  > **Narrowed by [`PD-ORCH-004`](../../product/directives/pd-orch-004.md#pd-orch-004), 2026-09-23; revision 5, 2026-10-06.** The expiry path above still governs; a child that completed a tool call within its final stall window additionally reports the paths it changed and, unless it is itself a continuation, offers its parent one continuation, telling it that a continuation starts with no memory. The graceful pause is bounded (revision 5): what the child has in flight at the expiry has at most 30 s to end, and is then aborted, a cut model step's streamed reasoning kept in the transcript alone.
- **REQ-ORCH-089** — A stall watchdog MUST provide visibility only and never cancel work. Stall threshold = per-role override else the default 90 s; evaluation cadence = max(1, min(threshold/6, 5)) seconds; a warning ("child appears stalled: no model event or token for N seconds") is emitted on stall entry and at most every max(threshold, 30) seconds thereafter; a stall diagnostics issue records active tools, the last 5 tool calls, and the last model event type; a stall callback fires on each evaluation with stalled/recovered so a UI badge can update. This cadence is the run evaluating its own children while it executes them, and is not a surface re-reading persisted state to discover what a run did (REQ-SESSION-071): it survives the withdrawal of the session-polling cadences (REQ-MONITOR-287) and is not to be removed by association with them. When active tool calls exist, the condition is reported at informational level as waiting on N active tool calls instead of as a stall.
- **REQ-ORCH-090** — An unresponsive-model fallback (default 120 s, minimum 30) MUST apply only before ANY model event has been received for the child and only when the threshold is below the child timeout. On expiry the conversation is gracefully paused (force-closed if stuck) and the role's fallback model is tried once per child by rebuilding the agent and transparently re-running — the child keeps running rather than being killed. Without a configured fallback, the child simply continues waiting under the full child timeout. A timeline event and an issue record the occurrence.
- **REQ-ORCH-091** — Rate-limit and quota handling MUST distinguish generic rate-limit errors (HTTP 429 / "Too Many Requests" / rate-limit phrasing) from provider quota exhaustion (structured insufficient-quota codes) and proceed in order: (a) models known exhausted are remembered session-wide and excluded from candidates; (b) at most one same-tier automatic model fallback per child, choosing a candidate of the failing model's tier (excluding exhausted and already-attempted pairs) and transparently re-running; (c) otherwise a suspended wait: wait time = the provider's Retry-After value when present (minimum 1 s), else exponential local backoff 60·2^(attempt−1) seconds capped at 300 s; generic rate limits auto-resume after the wait, but provider-exhausted models NEVER auto-resume (they wait indefinitely for a user decision); (d) the user may resolve a wait with keep-waiting, cancel-run, or change-model; a manual model change rebuilds the agent, re-runs, and persists the override in session state for the rest of the session. A change-model resolution that cannot be applied MUST NOT be silently discarded: the wait continues on the model it already had, no override is persisted, a `model_override_rejected` issue is recorded naming the model that was asked for and why it could not be applied, and the user is told that the model was not changed and that the wait is still outstanding, so the same choice can be made again or a different one taken. Silently ignoring the choice is forbidden — a user who believes the model changed would otherwise wait indefinitely on the model that had already failed.
  > **Narrowed by [`PD-ORCH-013`](../../product/directives/pd-orch-013.md#pd-orch-013), 2026-10-06.** In (d), the override persisted
  > by a manual model change stands for the rest of the session except for a pair the user later chooses explicitly for
  > the entry agent — from the run header, the inspector or a wait surface: that choice takes the override of the chosen
  > pair back, and the entry agent runs on the pair chosen. Everything else in (a) to (d) is as stated.
- **REQ-ORCH-092** — A failed model call MUST be retried according to the class of the failure: a transient failure up to the configured transient-retry count (default 1), a validation failure up to the configured validation-retry count (default 0). The delay before retry attempt n MUST be min(2.0, n) seconds. A transient failure MUST be recorded as a `transient_llm_error` issue. When the applicable retry budget is exhausted, or the failure falls into neither class and no other recovery in this section applies to it, the child MUST be marked `failed` with a report conveying that the child failed and carrying the formatted error. A failure is **transient** when the call produced no usable answer for a reason outside the content of the request and expected to differ on repetition: a connection, DNS, or TLS error; a request timeout; an HTTP status of 408, 425, 500, 502, 503, or 504; and a provider-signalled temporary overload. A failure is **validation-class** when the provider answered but the answer did not satisfy the structured-output contract asked of it: unparseable JSON, a schema violation, or a value outside a constrained enumeration. Every other failure — authentication, authorization, an HTTP 400 that is not the context-window rejection of REQ-ORCH-093, a missing or unknown model, a content-policy refusal — falls into neither class and fails the child at once. Rate-limit and quota failures, HTTP 429 included, are handled by REQ-ORCH-091 before this requirement is reached and are never spent from the transient budget; a context-window rejection is handled by REQ-ORCH-093 for the same reason.
- **REQ-ORCH-093** — A model call rejected because the conversation no longer fits the model's context MUST be recovered by condensing the conversation and retrying the call, at most twice for one call; where the condensation itself fails, the original rejection MUST be surfaced unchanged and the call fails. The same recovery MUST apply when a parent is resumed, and each parent-resume attempt MUST be bounded by the child timeout of REQ-ORCH-088. The occurrence MUST be recorded as an `llm_bad_request` issue for a child's own call and as a `parent_resume_bad_request` issue for a parent resume.
- **REQ-ORCH-094** — Pending user steering prompts for a child MUST be injected into the live conversation as clearly marked steering messages (from the watchdog loop and between execution passes), marked as delivered, and MUST reset the loop supervisor's consecutive-activation counter (steering counts as a new user instruction).
- **REQ-ORCH-095** — When a child's conversation run ends, what the child did MUST be assessed into exactly one of six categories: work was carried out; the request was answered; only bookkeeping took place; a tool call was attempted but malformed; text was produced and nothing was acted on; nothing happened at all. Only the first is accepted without further prompting. For each of the other five the child MAY be re-prompted once, and only once, in the same conversation — with one exception: on an answer-only route (REQ-ORCH-015) the answered category is accepted as success immediately. Where that single re-prompt has been used and the run still ends in the answered or text-only category, the child MAY be marked succeeded as a text-only completion. Any other non-work ending after the re-prompt MUST mark the child `failed` and MUST record an `incomplete_execution` issue naming the category assessed. The six categories have exactly these identifiers, listed in the order the prose above describes them: `work_performed`, `answered`, `bookkeeping_only`, `malformed_tool_call`, `text_only`, `no_activity`. Those strings are exact wherever a category is recorded.
- **REQ-ORCH-096** — Where the child runtime reports that it cannot make progress, the child MUST NOT be failed on that report alone: it receives one corrective message in its existing conversation and is resumed. Repeated such reports are governed by the same consecutive-activation rule as REQ-ORCH-102 — the third intervention with no intervening user instruction escalates the child per REQ-ORCH-106. A runtime error status, as distinct from a stuck report, MUST fail the child at once with no corrective attempt, and the terminal failure report MUST be built from what the transcript already holds. Exhausted stuck-recovery MUST be recorded with the existing issue kind `circuit_breaker_escalation` — the same kind REQ-ORCH-106 records — because it is the same escalation reached by the same consecutive-activation rule; its reason states that stuck-recovery was exhausted, which is what tells the two occasions apart. No further issue kind is introduced for it.
- **REQ-ORCH-097** — After each successful execution pass, per-child tool-call counters MUST be accumulated (feeding UI counters and the verifier's change detection), and cumulative token/cost snapshots MUST be replaced, not summed (summing cumulative totals would double-count).
  > **Narrowed by [`PD-ORCH-008`](../../product/directives/pd-orch-008.md#pd-orch-008), 2026-10-06.** The tool-call counters are accumulated as each call completes, not after the pass; the pass's end adds only what was not counted as it completed. The snapshot replacement above is unchanged.
- **REQ-ORCH-098** — Whatever terminal state a child reaches, and whether or not its execution raised, that child MUST be fully torn down: its conversation is closed, a `child_conversation_closed` timeline event is emitted for it, any wait or pending user prompt registered against it is discarded rather than left outstanding, and it no longer counts as an active child or against its model's concurrency cap. Teardown MUST NOT cost the run its responsiveness: an interrupt requested while a child is being torn down MUST still take effect and produce the outcome of REQ-ORCH-136.

### 16. Loop Supervision (Hidden)

- **REQ-ORCH-099** — Loop supervision MUST be invisible: the supervisor is not a role, is never registered or listed, has no observable side effect when no loop is detected, and its corrective messages read as natural user instructions that never mention monitoring, detection, or injection.

  > **Narrowed by [`PD-ORCH-001`](../../product/directives/pd-orch-001.md#pd-orch-001), 2026-09-16.** Every clause above still
  > holds wherever supervision is active. The directive names one case in which it is not: while
  > REQ-ORCH-153's plan gate holds the run, supervision is not active for the entry agent, so no corrective
  > message is written at all. The invisibility this requirement demands is preserved by the supervisor not
  > firing rather than by what it would have said.
- **REQ-ORCH-100** — Supervisor defaults MUST be: activation mode `independent` (alternative: `weighted`); tool-call threshold 60; message-count threshold 60; weights 0.6 (tools) / 0.4 (messages) with target score 1.0; recent-event window 24; transcript excerpt cap 8000 characters; repetition threshold 4; cycle threshold 3; enabled true. These are the canonical values: the fingerprint-based repetition and cycle triggers of REQ-ORCH-101 are the primary detection path and the raw-count thresholds are the backstop behind them. Two of the supervisor's settings are deliberately not fixed here. The classifier model MUST NOT be a model identity named by this document: its default is the `small_model` capability slot of REQ-PROVIDER-088, resolved by that requirement's own rules, so a deployment resolves the classifier from its own configured catalogue and no third party's model name is shipped as a default. The bound on one loop-classification call is likewise not this domain's: it is the registered configuration key `runtime.loop_classification_timeout`, whose value, value space, and default are REQ-CONFIG-467's. This domain states no bound of its own on a classification call and none on an activation cycle.
  > **Narrowed by [`PD-MONITOR-007`](../../product/directives/pd-monitor-007.md#pd-monitor-007), 2026-10-06.** The classifier's model is
  > followed through the session's override at each classification, and a pair held out of quota is not called: the
  > supervisor proceeds as on a classification that did not answer. The defaults are as stated.
- **REQ-ORCH-101** — For each observed child event, triggers MUST be evaluated in this order, and the first that fires wins: (1) repetition — the same action observed 4 times in a row fires "repeated action"; (2) cycles — a repeating sequence of 2 to 4 distinct actions, observed 3 times over, fires "repeated cycle"; (3) raw counts — in `weighted` mode a score of (tool calls / tool threshold)·0.6 + (messages / message threshold)·0.4 reaching 1.0 fires, and in `independent` mode either count reaching its own threshold fires on its own. Two actions count as the same action only when their tool name and the whole of their arguments are identical: no part of the argument content may be disregarded when comparing, so two long edits differing only near their end MUST be treated as different actions. This requirement is the product's single definition of when two agent actions count as the same action. A document that needs to decide sameness — for repetition detection, for cycle detection, or for any count of repeated work — cites this identifier and holds no rule of its own, and no rule anywhere may decide sameness from a prefix, an excerpt, a normalized rendering, or any bounded number of characters of an argument, because each of those makes the two long edits above compare equal, which this requirement forbids. Only the most recent events, up to the configured event window (default 24), are considered.

  > **Narrowed by [`PD-ORCH-001`](../../product/directives/pd-orch-001.md#pd-orch-001), 2026-09-16.** The order, the triggers
  > and the sameness rule above are untouched. The directive narrows *when* they are evaluated: no event of a
  > run held at REQ-ORCH-153's plan gate is an observed event for the entry agent, because the hold withholds
  > every writing tool and the reading a plan requires trips trigger (1) on the gate's own side effect.

  > *Noted 2026-10-20 ([OQ-364](../../architecture/open-questions/66-spikes-and-later-questions-33.md#oq-364), ruled under
  > [R-072](../../product/requests.md#r-072)):* "the whole of their arguments" is their value read as JSON — every member of
  > every object at every depth, arrays in order, nothing trimmed, cased, cut or disregarded. The order in which an object's
  > members were written is no part of it, so one argument object sent with its keys in another order is the same action.
  > The normalized rendering this requirement forbids is one that disregards part of that value, as its stated reason says;
  > an encoding that keeps every member whole is not one. Arguments that do not parse as JSON are compared whole as text.
  > REQ-NOTIFY-108's "no normalisation of the compared text" is read the same way. The requirement's text is unchanged.
- **REQ-ORCH-102** — On trigger, the supervisor MUST snapshot the pending activation, increment the consecutive-activation counter, and pause the child. If the counter exceeds 2 (the third activation without an intervening user instruction), it MUST escalate regardless of classification, with an escalation signal carrying session id, activation count, and a repeated-loop reason. Otherwise an LLM classifier judges whether a loop exists over the recent transcript tail (bounded by the event window and character cap).
- **REQ-ORCH-103** — The classifier contract is JSON `{loop_detected: bool, reason, corrective_message}` where the corrective message is at most 90 words, in natural user voice, and redirects to a different concrete approach or asks for a viability assessment, drawing on the transcript (dynamic, never templated). `loop_detected = false` MUST result in an invisible no-op resume.
- **REQ-ORCH-104** — Classifier failure or timeout MUST fall back on evidence: for repetition/cycle triggers, always declare a loop with a deterministic "pause and reassess" message naming the circled tool and a path anchor; for raw-count triggers, declare a loop only from repeated identical assistant messages (last 3 normalized-equal) or ≥ 4 consecutive same-tool calls — never from counts alone; for stuck-mode triggers, ALWAYS recover with a deterministic corrective message, overriding even a classifier that declined recovery.
  > **Narrowed by [`PD-ORCH-016`](../../product/directives/pd-orch-016.md#pd-orch-016), 2026-10-07.** Its clause "≥ 4 consecutive
  > same-tool calls" counts only calls that are the same action by REQ-ORCH-101's comparison — the same tool name and
  > identical whole arguments; calls of one tool with differing arguments are counts alone. The rest of the requirement
  > governs as written.
  > **Narrowed by [`PD-ORCH-009`](../../product/directives/pd-orch-009.md#pd-orch-009) revision 5, 2026-10-14 (revision 4, 2026-10-14; revision 3,
  > 2026-10-13).** Its stuck-mode clause does not reach four turns the run itself follows up: the one empty turn of an entry role
  > that `PD-ORCH-009`'s answer re-prompt answers (revision 3), a delegated child's empty turn that REQ-ORCH-095's re-prompt
  > answers (revision 4, OQ-283), an execution iteration's root turn that REQ-ORCH-078's plan correction follows (revision 4,
  > OQ-284), and a parent's empty turn while a child of its is pending or ended unobserved, which the run follows by waiting
  > and resuming the parent with its children's reports (revision 5, OQ-296). On each, a stuck trigger the turn armed is
  > withdrawn, so no classification is asked and no corrective message joins the run's own. Disjoint from `PD-ORCH-016`'s
  > raw-count case; the rest of the requirement governs as written.
- **REQ-ORCH-105** — After every activation cycle, regardless of outcome, tool/message counters and fingerprints MUST reset to zero. The consecutive-activation counter resets only on a new user instruction — a real user message, injected steering, or a todo-correction message all count. Supervisor state MUST be strictly session-scoped, never leaking across sessions.
- **REQ-ORCH-106** — Supervisor escalation MUST surface as: the child transitioned to failed; an escalation error issue ("child aborted after repeated activations"); a report carrying the escalation signal; and, at loop level, a session abort ending the run with stop reason `agent_session_aborted`.
- **REQ-ORCH-107** — Disabling supervision via configuration MUST construct no supervisor and no model client; the runtime distinguishes "intentionally disabled" from "not yet built" and tolerates the absence; the setting round-trips through configuration files; configurations without the field deserialize as enabled; a host-level toggle propagates into the run configuration.

### 17. Child Report Artifacts and Summarization

- **REQ-ORCH-108** — Every child reaching a terminal state MUST produce a machine-readable report artifact before its parent resumes. The report is produced by a low-cost summarizing pass whose instructions are narrow enough that it can only condense what already happened and can never carry the task forward. Parents consume the report in place of replaying raw transcript, and a dependency is treated as having succeeded only once its report has been stored.
- **REQ-ORCH-109** — The report schema is defined in Data & Formats. Runner-owned fields — verification results, completion-gate decision, repair record, gate state, requirement-coverage evidence, and scope-drift findings — MUST be structurally stripped from any model-produced payload before validation, so that a summarizing model can neither write nor overwrite deterministically produced evidence, cannot assert that its own work cleared the gate, cannot invent repair attempts, and cannot conceal files it failed to account for. This enforcement is structural, not dependent on prompt compliance.
- **REQ-ORCH-110** — The report-producing pass MUST be bounded and MUST always yield a report. The transcript it is given is capped at 12000 characters in total and 2000 characters for any one event. At most two attempts are made to obtain a well-formed report, the second being told what was wrong with the first. If the second attempt is also unusable, or the pass exceeds the summary timeout (default 120 s), a report MUST still be produced without any further model call: it carries an error entry of type "summary_failure", and its summary is taken from the first 220 characters of the child's final message or, where there is none, from the tools the child used. In every report, the agent name and role MUST equal the values the run holds for that child, whatever the summarizing pass produced. The final-response field MUST be populated only where the child's last assistant message was not followed by further tool activity; otherwise that text appears as the last response instead. Key findings MUST be rendered as bullet text.
  > **Narrowed by [`PD-ORCH-007`](../../product/directives/pd-orch-007.md#pd-orch-007), 2026-10-06.** The child's task, kept as the transcript's start, is exempt from the 2,000 characters per event and is kept whole within the 12,000 total; every other event keeps the 2,000.
- **REQ-ORCH-111** — A child MUST receive its report without any model call when all of the following hold: its role is `tester`; its terminal state is `succeeded`; its transcript holds at most 8 events; it made at least one tool call; and it produced a final response. The report is then built deterministically from the transcript, with status `succeeded`. That summary MUST be the child's final response itself, taken from its head and capped at 220 characters — the same cap REQ-ORCH-110 applies to its own no-model fallback — with a truncation marker stating how many characters were omitted where the response was longer. No text of the run's own composition is added, so a deterministic summary carries only what the child actually said and can never read as an assessment the run did not make.
- **REQ-ORCH-112** — The status a child report carries MUST be one of exactly `succeeded`, `partial`, `failed`, `cancelled`, and `blocked`, and the set is closed. `cancelled` is a member of it: a child settled by cancellation still produces a report (REQ-ORCH-108, REQ-ORCH-133), and that report's status is how the cancellation is read back. This requirement is the product's single definition of the child-report status vocabulary — a document that names a child report's status, carries one on the wire, or stores one alongside a materialized report cites this identifier rather than restating the set. No status outside that set is ever recorded, stored, or published: a summarizing pass that produced one is normalized by the mapping below before the report exists, so a consumer only ever reads a member. Report status maps to child terminal state as: succeeded → succeeded; partial → succeeded at the graph level (the loop, not the child ledger, decides what partial means for the task); failed → failed; cancelled → cancelled; blocked → blocked; anything else → failed. A `partial` report unblocking its dependents is deliberate and MUST NOT be treated as a defect to correct: `partial` means the child did usable work and stored a report, so a dependent may proceed on that report exactly as it would on a `succeeded` one, while the loop's task-level bookkeeping independently re-queues the task under REQ-ORCH-074. The two decisions are about different things — whether a sibling has findings worth handing on, and whether the top-level task is finished — and neither constrains the other.
