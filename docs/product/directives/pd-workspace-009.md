### PD-WORKSPACE-009 — the file-access flag and the autonomous prompt state the workspace boundary per tool

The status strip's `workspace-scoped` flag SHALL carry one fixed explanation that states the boundary as OQ-464 ruled it, per tool: "File access: Rotaris's file tools read and write inside this workspace folder only; terminal commands and MCP tools reach what OS confinement allows, or everything this account can where none is active." REQ-WORKSPACE-022's `outside-workspace!` explanation, the five flags, their conditions and the short forms are unchanged, and REQ-TOOLS-131's tooltip explains whether the file tools may read and write outside the workspace folder in those words. PD-WORKSPACE-007's statement that the file-access pair's fixed sentences still govern is a scoping sentence and no ruling of the owner's (OQ-191 disputed five other statements); for the `workspace-scoped` sentence it yields to this directive, and the `outside-workspace!` sentence it keeps. The explanation SHALL NOT vary with the focused session's confinement result: that fact is reported by REQ-SANDBOX-121's indicator beside the flag (PD-SHELL-008), and the plain disclosure of REQ-SANDBOX-130 stays on the two surfaces that requirement names. The `autonomous` confirmation of REQ-CONFIG-327 SHALL say, in substance, three things: that mutating tools inside the workspace will be invoked without a prompt, except for the destructive commands the starter rules always deny; that a file tool reaching a path outside the workspace is refused by the path fence and never asked about, unless access beyond the workspace is on; and that terminal commands and MCP tools are not judged by the paths they reach and are bounded only by OS confinement where it is active. REQ-CONFIG-327's clause "while any call reaching a path outside the workspace continues to require approval" and the sentence calling that guard "a behavioral promise the prompt makes and the runtime must keep" no longer govern; the promise the runtime keeps is REQ-TOOLS-044's. The access-beyond-the-workspace confirmation, Cancel as the default, and the restore-without-writing rule of REQ-CONFIG-327 are unchanged, and no tool's boundary moves: the fence of REQ-TOOLS-129, the opt-out of REQ-TOOLS-130 and the gate's scoping of REQ-TOOLS-018 stand as built.

**Why, and what it costs.** OQ-464 ruled the boundary per tool: the fence binds every first-party tool that takes a path, the gate's key scoping binds a path key and never parses `command`, and the terminal and MCP are bounded by ADR-0022's confinement where it exists and by nothing on native Windows (IC-8), the platform REQ-SANDBOX-130 expects most users to be on. Against that record "agents may read and write inside this workspace folder only" is true of the file tools and false of a shell command, and "any call reaching a path outside the workspace continues to require approval" is false even of the file tools, which REQ-TOOLS-044 has refused by the fence, never asked, under `autonomous`. A string conditioned on confinement was refused because REQ-SHELL-041 and REQ-WORKSPACE-022 fix one explanation per flag as the pair a reader compares, REQ-TOOLS-184 has the strip mirror the settings pages, REQ-CONFIG-302(b) makes `workspace-write` bound writes and not reads, and the confinement fact already has its own item and its own disclosure. What it costs: the `workspace-scoped` tooltip is longer and names two further concepts, the pair is no longer a symmetric sentence, the autonomous prompt says more than before, and the product still does nothing new on a host that cannot confine — the words are made true, the boundary is not made wider, and a user on native Windows is told, at the flag and at the prompt, that the terminal reaches whatever the account can. The shipped autonomous prompt had already dropped REQ-CONFIG-327's clause with no directive; that departure is recorded as a defect and settled here.
