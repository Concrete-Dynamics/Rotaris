| T-31 | A session with no presenter routes every ask through a headless policy; with no resolver wired at all a built-in fail-safe denies. **Never a silent allow, never a hang.** **The *never a hang* half is now measured reachable, and it is reachable ONLY UNDER AN APPLICATION-WIDE PROHIBITION THIS ROW DID NOT MENTION AND NOW DOES: no synchronous platform-dialog call may ever be made on the main process.** While a synchronous native dialog is open, **no main-process JavaScript runs at all** — 0 timer firings, 0 handled renderer messages, 0 replies to the run host, over 6,489 ms and 7,339 ms, with maximum channel gaps of 6,601–8,964 ms across all four probes; only the run-host-to-renderer direct port survived, at 267 ms. The approval dialog of `REQ-TOOLS-063` is **not** the exposure and is measured harmless at a 266–267 ms maximum gap. The exposure is every *other* native dialog, and they belong to domains that never read an approvals record: the folder choosers of `REQ-SHELL-164` (`REQ-WORKSPACE-009` via `REQ-WORKSPACE-016`, `REQ-SHELL-011`, `-021`, `-163`) and the message boxes of `REQ-SHELL-119`, of which "quit while a run is active?" is raised precisely when an approval is most likely to be in flight. The asynchronous forms measured 267–303 ms with the identical native dialog on screen, so **the remedy is free and the failure mode of not applying it is a user silently denying their own agent's tool calls while picking a folder.** Two further conditions: the liveness check **must be gap-based**, because a blocked main queues rather than drops — all 84 outstanding replies arrived when the block ended, the last at 7,885 ms — so a "did the reply arrive" check reports success eight seconds late and never fires; and no platform signal for an unresponsive main is usable from the run host, which was checked rather than assumed. ***The `never a silent allow` half remains unexercised by any measurement***: the spike measured detection, not the decision path — no gate, no pending-approval map, no headless policy — and the direction of the failure is a property of the gate rather than of the channel. | HARD | REQ-TOOLS-064 – REQ-TOOLS-066, REQ-TOOLS-063, REQ-SHELL-164, REQ-SHELL-119, REQ-WORKSPACE-009; `spikes/presenter-liveness-and-instance-claim.md` §4.1–4.6, §6; ADR-0019 obligation 3, ADR-0048 |

| T-39 | **Re-derived 2026-09-02: the conflict is gone and this row's own statement of it was falsified by an applied ruling.** *It read: "Custom tool plugins are `*.py` files executing inside the host process with exactly that process's OS privileges and no confinement of their own", labelled CONFLICT with the runtime. **The extension half is withdrawn and must not be cited.*** ESC-7 was ruled and applied: the `*.py` extension is withdrawn from all four sites it occupied, and `REQ-TOOLS-161` now **owns** what a plugin file is — a module the host process can load and call directly — and states that **no language, runtime, packaging form or file extension is fixed anywhere in this specification**. | T-41 | **Re-derived, and the conflict narrowed rather than closing.** The three-against-one conflict this row recorded is **dissolved on two of its three sides**: `REQ-TOOLS-053` and `REQ-TOOLS-069` no longer test presence, so they no longer contradict `REQ-TOOLS-064`'s never-a-hang rule — a wedged presenter is not one an approval can be put in front of, and ADR-0019's liveness revocation is now the requirement's own test (T-25). **What survives is narrower and is a defect rather than a design gap**: `REQ-SANDBOX-101` still says "Only the presence of that channel is tested, not whether it later answers" **and** asserts that its condition is "exactly the one fixed by `REQ-TOOLS-053` and `REQ-TOOLS-069`".
