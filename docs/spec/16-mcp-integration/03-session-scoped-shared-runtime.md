# MCP Server Integration — Session-Scoped Shared Runtime

Part 3 of 6 of [domain 16](../16-mcp-integration.md), which indexes every part. Defines REQ-MCP-066 – REQ-MCP-111.

### Session-Scoped Shared Runtime

- **REQ-MCP-066** — Within one session there SHALL be exactly one shared connection per server, opened on first demand, reused by every agent in the run, and closed exactly once when the session ends. Teardown SHALL occur on session-lock release and at application exit; a run the application performs in the background SHALL use the same shared-connection behavior as a run the user is watching.

- **REQ-MCP-067** — Session connection handling SHALL provide these observable guarantees under concurrent use: two agents that request the same server at the same time SHALL both use the same connection, and when both requests have been served exactly one connection — and for `stdio`, exactly one server process — SHALL exist for that server; while one server is still starting, tool calls to servers that are already connected SHALL complete without waiting for that startup to finish; a connection request issued after session shutdown SHALL fail with an error naming the server and SHALL leave no connection open; a request to release a connection that has since been superseded SHALL leave the current connection open and usable; and shutdown SHALL be callable any number of times without error, with no server process and no connection left open once the first call has returned.

- **REQ-MCP-068** — The end of one child conversation SHALL leave the session's shared server connections open: after a child finishes, every server it used SHALL still be connected and immediately usable by the next child of the same session, and every `stdio` server process SHALL still be running. Connections and server processes SHALL close only at the session-end teardown of REQ-MCP-066. Tool calls requested concurrently over one connection SHALL all complete, and each SHALL receive the response belonging to its own request and to no other. The session SHALL keep emitting its events while a tool call is outstanding, so no surface stalls for the duration of a call. Specifically: the `tool.start` of REQ-EVENTS-057 SHALL be observable before the call returns, its matching `tool.finish` SHALL follow when the call settles, and every other event of the catalog of REQ-EVENTS-041 that the session would otherwise have emitted SHALL be emitted at its normal point, neither withheld nor deferred until the outstanding call completes. This holds on every channel that carries the session event stream and for every surface fed by it, and it holds however many calls are outstanding at once.

- **REQ-MCP-069** — Given a failure creating the connection for one server, when the session tool source is built, then that server is logged and skipped (its tools absent) and the run continues. Tools from all connected servers SHALL be merged into one aggregate surface, with each tool call routed to the connection of its owning server. Opening a connection and listing its tools SHALL run under a caller-supplied budget whose default is 30 seconds.

  A server that becomes unreachable after its connection was established — a remote endpoint that stops answering, a `stdio` child that exits — SHALL be handled per call and never by failing the run: the call in flight ends as a failed tool call exactly as an exhausted allowance does (REQ-MCP-003), a warning naming the server SHALL be delivered through REQ-MCP-044 at most once per server per session, and the product SHALL neither retry the call nor reconnect on its own. A later call to the same server SHALL be attempted, re-establishing the connection if the transport requires it, and SHALL succeed if the server has recovered. Tools of every other server SHALL stay callable throughout. A probe (REQ-MCP-054) run afterwards SHALL report what it observes at that moment and SHALL NOT report a remembered outcome.

- **REQ-MCP-070** — A connected server whose configured name is `lsp` SHALL be initialized before any of its tools are offered to the agent: when a workspace root is known and the server reports a tool named `lsp_init`, that tool SHALL be called once with the arguments `{"root": "<workspace_root>"}` and SHALL be given 15 seconds to answer. Should that call fail or exhaust its budget, the server SHALL contribute no tools to the agent that triggered the connection and the run SHALL continue; a later agent of the same session that needs the server SHALL make the connection and the initialization call over again rather than inherit the earlier outcome. A server named `lsp` that reports no `lsp_init` tool SHALL be offered as it is; with no known workspace root the call SHALL be skipped; and a server configured under any other name SHALL never receive this call.
  > **Narrowed by [`PD-MCP-002`](../../product/directives/pd-mcp-002.md#pd-mcp-002), 2026-10-06.** For a connection established by a run in an isolated working tree, `lsp_init` is called with that tree's root.

- **REQ-MCP-071** — A connected server carrying the built-in code-intelligence name SHALL be probed once per connection established in the session, before that server's tools are offered to the agent, by calling the runtime's project-memory listing tool with empty arguments and allowing it 15 seconds to answer; the tool SHALL be found by matching the trailing segment of its reported name, so a client-side server prefix (REQ-MCP-057) still matches. Should that call fail or exhaust its budget, a warning SHALL be delivered through REQ-MCP-044 telling the user that the server's symbol-level tools remain usable but may not be pointed at this project; the connection SHALL stay open, the server's tools SHALL still be offered to the agent exactly as the persona's grants allow, and no corrective action SHALL be attempted. A server reporting no memory-listing tool SHALL NOT be probed and SHALL produce no such warning. The literal name of the memory-listing tool SHALL be read from the binding manifest of REQ-MCP-116.

- **REQ-MCP-072** — *Withdrawn.* Its only host was the terminal user interface, which the product does not have; the Windows `stdio` launch guarantee it stated is carried by REQ-MCP-113.

- **REQ-MCP-113** — On Windows, a `stdio` server launched by the desktop application SHALL start and its tools SHALL become available to the persona carrying it. No such launch SHALL be reported to the user as failed for a reason belonging to the host rather than to the server, and launching the same server repeatedly SHALL give the same result every time. The host condition this guarantee exists to defeat is stated so it can be tested negatively: the application is a graphical process that owns no console and whose own standard input, output and error may be absent, closed, or attached to something that is not a usable pipe. The product SHALL therefore create the child's three standard streams itself for every `stdio` launch, never inherit or reuse the parent's, never require a console to exist, and never allocate or show one; a console window SHALL NOT appear at any point in a launch. The same rule SHALL apply on every platform, so one launch path serves all of them, and it SHALL apply equally to the reserved token of REQ-MCP-033, whose child is the application's own executable. A launch that fails for a reason belonging to the server or its command — the command not being on PATH, or the child exiting — is unaffected and is reported by REQ-MCP-041 and REQ-MCP-107 as before.

### User Toggles and Server Management

- **REQ-MCP-073** — *Withdrawn.* A slash command and a text-mode command palette are surfaces of a terminal user interface the product does not have; reaching MCP server management is carried by REQ-MCP-108.

- **REQ-MCP-074** — *Withdrawn.* A modal text-mode table was its only surface; listing every configured server and toggling one for the session is carried by REQ-MCP-091 and REQ-MCP-108.

- **REQ-MCP-075** — *Withdrawn.* It described a column of the withdrawn text-mode table; per-server state on the surface that remains is the four-state health of REQ-MCP-092 together with the availability of REQ-MCP-037, both shown as text.

- **REQ-MCP-076** — *Withdrawn.* The file existed only to persist the withdrawn terminal-UI toggles, and a second global enablement store would contradict the `enabled` field of REQ-CONFIG-465 with no stated precedence between them; durable per-server enablement is carried by REQ-MCP-115.

- **REQ-MCP-077** — *Withdrawn.* It stated resilience rules for the withdrawn toggle file; the default it protected — a server the user has not turned off is enabled — is the `true` default of the `enabled` field (REQ-CONFIG-465), and REQ-MCP-115 carries the rest.

- **REQ-MCP-078** — Enablement SHALL be consulted afresh at every persona resolution, so a server that is disabled — by its configured `enabled` field (REQ-CONFIG-465) or by the session override of REQ-MCP-094 — is excluded from the next constructed agent. Changing either during an active run SHALL never crash the run and SHALL take effect on the next run iteration.

- **REQ-MCP-079** — *Withdrawn.* The terminal information pane was its only surface; listing every configured server before a run with its computed availability and its origin is carried by REQ-MCP-091, and showing the servers a running or finished agent actually carried is carried by REQ-MCP-114.

- **REQ-MCP-080** — *Withdrawn.* A modal text-mode screen was its only surface; reading a server's merged secrets with every value masked is carried by REQ-MCP-109 and editing them is carried by REQ-MCP-110.

- **REQ-MCP-081** — Wherever a stored secret value is rendered it SHALL be replaced by the mask REQ-TOOLS-171 fixes, and this domain holds no second definition of that mask. What this requirement relies on REQ-TOOLS-171 for is the mask itself: one fixed marker, identical on every surface, carrying no character of the value it replaced and no indication of that value's length, so two masked secrets of different lengths are indistinguishable and neither a credential nor its size can be inferred from a rendering. What this requirement adds is that the substitution is **unconditional** for a value read out of the secrets store of REQ-MCP-082: it SHALL NOT depend on the entry's key being secret-looking (REQ-TOOLS-172) or on the value carrying a recognized credential prefix, because a value's presence in that store is already what establishes it as a credential. A raw stored secret value SHALL never appear in a log line, a notification, a rendered list or table, an exported document, or any other rendering the product produces. A zero-length value never reaches this rule: the product refuses to store one (REQ-MCP-084) and a zero-length value found in a hand-edited file is skipped at load (REQ-MCP-082), so no rendering ever shows a mask standing for a value that is not there.

- **REQ-MCP-108** — MCP server management SHALL have exactly one venue: the `mcp` settings category of REQ-CONFIG-269, inside the Settings view of REQ-SHELL-023. That category SHALL hold the server list of REQ-MCP-091, the health probe of REQ-MCP-092, the secrets surface of REQ-MCP-109 and REQ-MCP-110, the search-key control of REQ-MCP-111 and the machine-setup action of REQ-MCP-112, and no other surface of the product SHALL offer a second way to enable, disable, probe or hold secrets for a server. Opening it SHALL be an action of the one vocabulary of REQ-SHELL-048, so it appears in the command palette, the keyboard-help dialog and the composer's slash catalogue alike, under a label naming MCP servers and a description saying it manages them. Every control the category holds SHALL be keyboard-reachable and fully labelled at the minimum window size (REQ-SHELL-022), and every state it shows SHALL be readable as text and never by colour alone (REQ-SHELL-149). The category SHALL open, and every control within it SHALL respond, within the product's 100 ms interface responsiveness budget; work that cannot finish inside it — probing (REQ-MCP-092), setup (REQ-MCP-112) — SHALL show its progress rather than block.

- **REQ-MCP-115** — Per-server enablement SHALL have exactly two controls and no third store. The durable one is the entry's `enabled` field in the layered YAML configuration, defaulting to `true` where absent (REQ-CONFIG-465): it survives restarts, merges by the ordinary scope rules of REQ-MCP-025, is picked up by an ordinary configuration reload, and is what a user edits — by hand or through a settings surface that writes configuration — to turn a server off for good. The transient one is the desktop toggle of REQ-MCP-094, which overrides the durable value for the current session only. No separate per-user enablement file SHALL exist, so no precedence between two stores has to be defined and two running instances cannot race over one. The MCP category SHALL make plain, for each row, which of the two is in force: a row whose configured value is `false` SHALL read as configured off, a row overridden for the session SHALL read as overridden for this session and SHALL say that the change is not persistent, and the category SHALL name `enabled` and the configuration file as the way to make it persistent (REQ-CONFIG-350, REQ-CONFIG-437). Restarting the application SHALL discard every override and return every row to its configured value.

### Secrets Storage and Environment Resolution

- **REQ-MCP-082** — Secrets SHALL be stored in a `secrets.yaml` per scope, next to the scope's `agents.yaml`: global in the per-user configuration directory REQ-CONFIG-001 fixes, which is the per-user location REQ-STARTUP-145 fixes, and workspace in `<workspace>/.rotaris/`. The format is a YAML mapping of server name → map of environment key → value. How that file is written is REQ-CONFIG-216's and is cited here rather than restated: this document holds no copy of the write's atomicity, of the directory creation, of the file protection every write leaves in place, or of what happens when that protection cannot be applied. *This requirement formerly restated the write as "atomic (temp file then rename) with parent directories auto-created" and stated no file protection at all. That restatement is withdrawn rather than narrowed: it was a second, shorter statement of one write, and once REQ-CONFIG-216 fixed a mode for this file it became a text a build could satisfy while leaving a credentials file world-readable. Nothing it guaranteed is lost — REQ-CONFIG-216 holds the atomicity and the directory creation, and adds the protection this text never had.* An unreadable file, invalid YAML, or a non-mapping root SHALL load as empty; non-mapping server values are skipped; keys and values are coerced to strings. An entry whose key is empty, or whose coerced value is the empty string, SHALL be skipped at load with a warning naming the scope, the server and the key, so no zero-length secret ever reaches environment resolution (REQ-MCP-087), URL substitution (REQ-MCP-088) or masking (REQ-MCP-081); a server left with no entries by that skipping loads as though it had none.

- **REQ-MCP-083** — The merged secrets view SHALL combine global then workspace per key, with workspace winning on collision.

- **REQ-MCP-084** — Secret mutation semantics: setting SHALL create the server entry as needed; setting a key to the empty string SHALL be **refused** — the store SHALL report that a value is required, write nothing, and leave any existing value for that key untouched, so an empty value can neither be created nor used to clear one; unsetting a missing key SHALL report not-found without error and SHALL remove a server entry that becomes empty; clear-all SHALL report the number of removed keys and perform no write when nothing was removed; a failed atomic write SHALL remove its temp file and propagate the error.

- **REQ-MCP-085** — *Withdrawn.* A command group invoked from a shell was its only surface; setting, unsetting, clearing and listing stored secrets, with the same scope choice and the same masking, are carried by REQ-MCP-109 and REQ-MCP-110.

- **REQ-MCP-086** — *Withdrawn.* A shell subcommand was its only surface; storing the built-in `web_search` server's API key without the user having to name either the server or the environment variable is carried by REQ-MCP-111.

- **REQ-MCP-087** — Environment resolution at configuration load SHALL apply, per server `env` entry: (1) a value that is exactly `${VAR}` (full-value match) is replaced by the process environment's value; when the variable is unset, the key is omitted entirely — the literal placeholder is never passed to a server; (2) any other value is kept as-is; (3) stored secrets for that server are overlaid last and always override shell-derived values. Resolution SHALL happen during loading so every downstream consumer (agent construction, discovery, health probes) sees the resolved environment.

- **REQ-MCP-088** — For remote servers, every `${VAR}` occurrence inside the URL (substring, not full-match) SHALL be replaced using this precedence: (1) a stored secret for that server, (2) the process environment. An unresolvable placeholder SHALL stay literal with a warning stating it could not be resolved. This is how the default web-search URL receives its API key.

- **REQ-MCP-089** — During configuration load, the workspace `.gitignore` SHALL be best-effort amended to exclude `.rotaris/`: idempotent, tolerant of an existing entry with or without a trailing slash, written atomically, and reporting failure without raising.

- **REQ-MCP-090** — The effective environment reaching a spawned server SHALL follow this precedence chain: explicit `env` over `envFile` (discovery merge) → full-value `${VAR}` expansion from the shell → secrets overlay, where workspace secrets beat global secrets beat shell values.

- **REQ-MCP-109** — The `mcp` settings category SHALL hold a secrets surface that reads the stored secrets of REQ-MCP-082 without ever revealing one. It SHALL offer both views over the same data: an **all-servers** view listing every server that holds at least one stored secret, and a **per-server** view for one server chosen from the configured server names. Both views SHALL show, per entry, the server, the key, the value masked per REQ-MCP-081, and the scope the entry came from — `Workspace` or `Global` — with the merged view of REQ-MCP-083 determining which entry is shown where a key exists in both, and the overridden global entry SHALL NOT be listed a second time. Servers, and keys within a server, SHALL be listed in the ascending order of REQ-MCP-117. The per-server view SHALL additionally show the keys of the chosen server's configured `env` block, in that same order, marking which of them a stored secret satisfies, so a user can see at a glance what a server still needs. Empty states SHALL be distinguishable and SHALL each name what is missing: no server is configured; the chosen server holds no stored secret; no server holds any stored secret at all. The surface SHALL never render a raw value, SHALL never offer a reveal control, and SHALL never place a value on the clipboard.

- **REQ-MCP-110** — The secrets surface SHALL let the user add a secret, change an existing one, delete one, and clear every secret of one server, and these SHALL be the only ways the product writes `secrets.yaml`. Every write SHALL name a scope: the surface SHALL offer a `Workspace` / `Global` choice that opens on `Workspace` (REQ-CONFIG-463), and adding, changing, deleting and clearing SHALL each affect the chosen scope alone — deleting a workspace entry SHALL leave a global entry of the same key in place, and the merged view (REQ-MCP-083) SHALL immediately show that global entry instead. The value field SHALL never echo what is typed in clear text and SHALL never be pre-filled with an existing stored value, so changing a secret means supplying it afresh. A write SHALL be refused, with a notice stating which requirement is unmet, when no server is chosen, when the key is empty, or when the value is empty (REQ-MCP-084); a refused write SHALL change nothing. A completed write SHALL confirm what happened, conveying the server, the key, the scope, and — for an add or a change — the new value masked per REQ-MCP-081; a delete SHALL confirm the server, the key and the scope, or state that the key was not present in that scope, which is not an error; a clear SHALL convey how many keys were removed, or that the server had none. The wording of each confirmation is left to the implementation. Per-edit confirmation SHALL be the whole of the feedback: no aggregate summary SHALL be produced when the surface closes, and closing SHALL discard nothing, every edit having already been written. A stored secret SHALL take effect on the next configuration load, and the surface SHALL say so rather than implying that a run already in flight changes.

- **REQ-MCP-111** — The `mcp` settings category SHALL hold a dedicated control that stores the built-in `web_search` server's API key without the user having to name either the server or the environment variable. Supplying a value through it SHALL write that value through the secrets store of REQ-MCP-082 under the `web_search` entry, keyed by `ROTARIS_SEARCH_API_KEY` (REQ-CONFIG-181), in the scope the user chose, defaulting to `Workspace` (REQ-CONFIG-463); the stored value SHALL thereafter satisfy the URL placeholder of REQ-MCP-088 with no further configuration, and the entry SHALL stop being reported as unresolved. The control SHALL obey REQ-MCP-110 in every other respect — the field does not echo, an empty value is refused and writes nothing, and the confirmation conveys the variable, the scope and the value masked per REQ-MCP-081. Its wording and label are left to the implementation, provided they identify what the key is for without requiring the user to know the variable's name. The control SHALL be visible whether or not `web_search` is currently enabled, since supplying the key is a prerequisite for enabling it usefully.
