# Settings and Configuration — Requirements-board configuration

Part 5 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-183 – REQ-CONFIG-218.

### Requirements-board configuration

- **REQ-CONFIG-183** — Every model under `requirements:` **forbids unknown keys**: an unrecognized key anywhere in this block is a hard load failure. This is the opposite of the top-level policy, where an unrecognized key is silently dropped (REQ-CONFIG-040). The section also validates on assignment. That rule is **unweakened** for a key this specification has never defined — one the user mistyped, or one something other than this product wrote — because this block drives runs nobody is watching (REQ-CONFIG-198), and quietly ignoring a key here would let such a run proceed under settings its author believed they had given it. What such a failure conveys to the user, and what recovers from it, is REQ-CONFIG-478's and is not restated here.

  **One case is carved out of that rule, and the reason is what bounds the carve-out.** A key this specification itself defined and has since withdrawn, and a key this specification names as not a configuration key of this domain, SHALL NOT fail the load. Such a key is **reported and ignored**: it contributes nothing to the merged configuration, every other key in the file is loaded exactly as though it were absent, and the workspace opens. This is a deliberate departure from the rule above rather than a boundary of it, and it is stated with its grounds so that it is not later read as an inconsistency to tidy away. An unknown key a stranger or a slip of the keyboard put in the file, and a withdrawn key **this product solicited** — shipped, documented as a key, and invited the user to write — are not the same case, and treating them alike turns this product's own deprecation into the user's outage. In the **global** scope the two are not even comparable in cost: one line in one file would stop *every* workspace opening at once, and no surface of the product is reachable from that state to repair it, the settings screen that edits that very file included. The carve-out reaches exactly the two kinds of key named in its first sentence — one this specification defined and withdrew, and one this specification names as not a configuration key of this domain — and nothing else: not a key that merely resembles a withdrawn one, not a key some other product withdrew, and not any other fatal condition of REQ-CONFIG-233.

  **What the report conveys** is fixed here, because a reported-and-ignored key is not a fatal failure and REQ-CONFIG-478's floor does not reach it. It identifies the file by its full path and by which scope it belongs to (REQ-CONFIG-001) and identifies the key by its full path within that file; it conveys that the key was **withdrawn rather than mistyped**, so that a user does not go looking for a spelling error that is not there; it conveys what became of what that key configured — for `store_subpath`, that delivery records are no longer files in the workspace and that no configuration key names a location for them (REQ-CONFIG-192); for `worktree_subpath`, that requirement-unit checkouts are placed at a location this domain registers no key for (REQ-CONFIG-194, REQ-GIT-137) — and it conveys that the key is being ignored and that the rest of the configuration loaded, so that a user is not left to guess what the report cost them. It is a warning that does not interrupt the load (REQ-CONFIG-233), is raised once per offending key per load, and its wording is left to the implementation. This rule is written against the property *this specification names the key* — as withdrawn, or as one this domain does not register — and not against a list, so a key withdrawn by a later amendment is covered without this requirement being amended.

  **Nothing here licenses the product to change the user's file.** The key stays exactly where the user wrote it; nothing is removed, rewritten, or repaired on their behalf; and removing it stays theirs to do whenever they choose, which is a choice a file leaves open and a store would not (REQ-CONFIG-477, ground 3). The difference this carve-out makes is that they can now do it from inside a running product, with their workspace open, rather than from outside a product they cannot start.
- **REQ-CONFIG-184** — With no `requirements:` block in any scope the board is still available and usable: `requirements.enabled` is true, no source is declared so the built-in source applies (REQ-CONFIG-185), and `requirements.scheduling.mode` is `manual`.
- **REQ-CONFIG-185** — `requirements.enabled` (bool, default true); false removes the board from view and halts refreshes and requirement runs alike. `requirements.sources` (list, default empty); leaving the list empty selects the built-in source for any workspace that has a store. The list **replaces** rather than extends.
- **REQ-CONFIG-186** — Two requirement sources with the same `id` are rejected at load with a message explaining that attribution and collision reporting need unique ids.
- **REQ-CONFIG-187** — A requirement source entry accepts these fields. `id`: string, required, non-blank, unique across sources. `type`: one of `reqtocode`, `markdown`, `yaml`, `json`, default `reqtocode`; any other value is rejected at load. `enabled`: bool, default true, where false keeps the entry in the file while excluding it from refreshes and from requirement runs. `root`: workspace-relative string or null. `glob`: string or null, required when `type` is `markdown`, `yaml` or `json`, optional for `reqtocode`. `writable`: bool or null, where null leaves the decision to the adapter selected by `type`. `fields`: the field-path map of REQ-CONFIG-188. `options`: map of string to string, default empty, handed to the adapter unaltered and replaced wholesale by any layer that states it.
- **REQ-CONFIG-188** — The requirement field map defaults are: `id` → `frontmatter.id`; `title` → `heading` (the document's first top-level heading); `description` → `body`; `lifecycle` → `frontmatter.status`; `req_type` → `frontmatter.type`; `parent` → `frontmatter.epic`; `relations` → empty map (relation kind to field path, replaced not merged); `trace_required` and `test_required` → unset. Leaving `id` unmapped is rejected as a configuration error; no identifier is ever invented on the user's behalf. Where a path is unset, the reading defaults are: lifecycle `draft`, type `product`, a flat (parentless) store, and trace/test both required.
- **REQ-CONFIG-189** — `requirements.refresh`: `incremental` (bool, default true; false makes every pass re-read everything and exists for diagnosis); `debounce_ms` (int ≥ 0, default **400**, so a burst within the window causes one evaluation); `triggers` (list, default all eight of `commit`, `merge`, `source-edit`, `branch-switch`, `test-run`, `run-completion`, `worktree-integration`, `manual`; **replaces** the default list); `max_workers` (int ≥ 1, default **1**, so refreshes serialize and consumers never observe a half-built index); `timeout_seconds` (float > 0, default **120.0**; overrunning it marks the refresh failed and **keeps the previously built index intact**); `watch_filesystem` (bool, default true; false confines refreshing to the other triggers plus explicit requests).
- **REQ-CONFIG-190** — `requirements.evidence`: `follow_source_flags` (bool, default true — the source's own flags win and the per-type blocks apply only where the source says nothing); per-type obligation blocks for `product`, `technical` and `epic`, each with the five obligations `implementation`, `test`, `verification`, `execution`, `integration` valued `required`, `optional` or `not-applicable`. Defaults: product = implementation/test/verification required, execution/integration optional; technical = the same but integration `not-applicable`; epic = **all five `not-applicable`**, since an epic asserts nothing itself.
- **REQ-CONFIG-191** — `requirements.evidence.stale_on_lost_ancestor` (bool, default true): once the commit a verification was recorded against has fallen out of the current head's ancestry, that evidence reads **stale instead of failed**. `stale_on_trace_move` (bool, default true): a trace or covering test that has moved or disappeared renders the evidence stale **even though the requirement text was never touched**.
- **REQ-CONFIG-192** — `requirements.delivery` configures the requirement **delivery store**, which holds operational records only; requirement text is never written there. That store is not configuration and REQ-CONFIG-477's boundary does not reach it: only this application reads a delivery record, the records are high-volume, queried and transactional, and the delivery state, the requirement's history, this requirement's `history_limit` prune and the audit entry are written **together, indivisibly**, so no failure can leave a state recorded without its audit entry or an audit entry for a state that was never recorded. The store therefore holds records rather than files, and **no key of this domain names a directory, a file or a document format for it**; `store_subpath`, which named the directory beneath the workspace configuration directory that once held delivery records, tombstones and audit entries, is withdrawn with the directory it named and is no longer a recognized field — a file that still states it is **reported and ignored** rather than rejected, the workspace opening and every other key in the file loading as though it were absent, which is the same consequence REQ-CONFIG-194 records for `worktree_subpath` and is stated here rather than discovered. It is not treated as an unknown key under `requirements:` would be, precisely because an earlier statement of this specification invited it; that departure, its grounds, and what the report conveys are REQ-CONFIG-183's and are not restated here. This requirement states the withdrawal and what became of what the key configured; that one states what the user is told and that they keep their workspace. The remaining fields are unchanged in meaning. `schema_version` (int ≥ 1, default **1**) is written into every record produced, and a record whose `schema_version` exceeds the supported version is reported as unsupported and is not interpreted. `retain_tombstones` (bool, default true) keeps the ids of requirements the sources have stopped declaring, so a retained id is never issued again; this is the delivery store's own record of retired ids and is a different thing from the retired-identifier log the traceability toolchain keeps as a file in the user's repository (REQ-TRACE-130, REQ-TRACE-513). `audit_trail` (bool, default true) records each state transition with the actor, the time, and the stated reason. `history_limit` (int ≥ 1, default **200**) is the number of history entries kept per requirement; older entries are pruned. The reader supports exactly the versions **1 through the configured `schema_version`**, which as shipped is the single version `1`; a record whose `schema_version` is higher is reported as unsupported and is not interpreted, and a record whose value is below 1, absent, or not an integer is reported as unreadable. Neither is rewritten, migrated in place, or deleted — a record this build cannot interpret is carried untouched rather than repaired. Such a record is reported in three places and nowhere else: the requirement it belongs to is listed on the board with its delivery history shown as unavailable for that reason rather than being hidden or shown as empty; a message identifying the record and the version it carries is written to the session log; and the same message is returned by any surface that reads delivery records. A workspace holding an unsupported record still opens and still runs.
- **REQ-CONFIG-193** — `requirements.execution` branch naming: `branch_template` (default `rotaris/req/{requirement_id}/{unit_id}`, placeholders `{requirement_id}`, `{unit_id}`, `{slug}`; a namespace distinct from session branches, which use `rotaris/session/<id>`) and `integration_branch_template` (default `rotaris/req/{req}/integration/{id}`, placeholders `{req}` and `{id}`, with the older spellings `{requirement_id}` and `{integration_id}` still accepted).
- **REQ-CONFIG-194** — `requirements.execution` remaining fields. `worktree_subpath` is **not** among them and is not a configuration key. What this document owns here is the configuration surface and nothing else: exactly one key names an isolated-checkout storage subpath, `worktree_storage_subpath` (REQ-CONFIG-068, REQ-CONFIG-010), and that key names the per-session one; no key of this domain names the directory holding requirement-unit checkouts. Where requirement-unit checkouts are placed is not configurable and is not stated here — REQ-GIT-137 fixes that location, and REQ-GIT-138 relies on this domain registering no key for it. A `worktree_subpath` key written under `requirements.execution` is a key this specification names as not a configuration key of this domain, so a file that states it is **reported and ignored** rather than rejected and the workspace opens; what that report conveys, and why this case is not treated as an unknown key would be, are REQ-CONFIG-183's and are not restated here. The fields are: `target_branch` (string or null; null selects whichever branch was checked out when the run began); `run_check_suite` (bool, default true — a workspace with no suite yields a "not verified" outcome); `run_reqtocode_verification` (bool, default true); `retry_limit` (int ≥ 0, default **1**; once spent, the requirement moves to blocked and the most recent failure is named; 0 means no retry at all); `keep_failed_worktrees` (bool, default true — deleting them is something only the user does, never the scheduler); `unit_timeout_minutes` (int ≥ 1, default **120**; on overrun the unit is failed with an explicit reason instead of being left to run without end).
- **REQ-CONFIG-195** — `requirements.execution.decomposition`: `enabled` (bool, default true; false collapses each requirement into a single unit); `max_units` (int ≥ 1, default **6**; a plan proposing more units than that is **refused outright, not quietly trimmed**); `require_confirmation` (bool, default false — either way the plan is stored and can be inspected).
- **REQ-CONFIG-196** — `requirements.scheduling`: `mode` (`manual` or `automatic`, default `manual`); `max_concurrent_units` (int ≥ 1, default **2**, counted across every requirement — work that meets the cap **waits in the queue and is never turned away**); `max_concurrent_requirements` (int ≥ 1, default **2**, independent of unit count); `avoid_file_conflicts` (bool, default true, delaying units whose predicted file sets overlap instead of letting the collision surface at integration time); `priority_order` (list, default `critical`, `high`, `normal`, `low`, `none` — priority decides queue position only and **cannot promote work ahead of something it depends on**); `auto_release_dependents` (bool, default false, so clearing a blocker makes the dependent eligible for scheduling while the decision to start it stays with a person); `queue_limit` (int ≥ 0, default **0**, where **0 means unbounded**).
- **REQ-CONFIG-197** — `requirements.board`: `default_sort` (`priority`, `id`, `state`, `health` or `epic`, default `priority`, with ties broken by `id` so the order is deterministic); `group_by` (`state`, `epic` or `source`, default `state`); `filters` (a sub-block of `epics`, `sources`, `lifecycles`, `states` and `priorities` lists plus a `text` string, every one of them empty by default, so a board whose filters have never been set shows everything on first open; whatever the block holds is applied when the board opens, and being configuration it survives a restart); `show_deprecated` (bool, default false — deprecated requirements are read in and marked deprecated either way, the flag deciding only whether they are listed by default); `live_updates` (bool, default true); `card_limit` (int ≥ 0, default **0**, where **0** means no limit). Because a section overlay is recursive (REQ-CONFIG-048), a layer that states one field of `board:` overlays that field alone: an unrelated `board:` edit leaves `filters` and every other sibling exactly as the lower layer left them, and a stated `filters` sub-block likewise overlays only the lists it names.
- **REQ-CONFIG-198** — `requirements.personas` maps five board activities to role names: `source_discovery`, `decomposition`, `impact_analysis` and `migration_analysis` default to `requirements-engineer`, and `execution` defaults to `coding-agent`. A mapped name matching no configured role is not a load error; the workspace's `default_persona` is used instead at the moment that role is needed (REQ-CONFIG-233), so an unrecognized name can never make a workspace fail to open. `requirements.human_in_the_loop`: `escalate` (list, default all seven of `contradictory-requirements`, `unclear-scope`, `competing-requirements`, `breaking-change`, `unclear-superseding`, `risky-migration`, `architectural-decision`; a stated list replaces the default, so exactly the listed conditions interrupt a run and no condition outside it does); `require_review_before_done` (bool, default true; false lets a run that has passed verification close the requirement without a person); `allow_force_done` (bool, default false; every use is recorded in the audit trail with the actor and the stated reason); `confirm_migration_worklist` (bool, default true; false leaves the worklist computed and stored while it stops interrupting the board, and the confirmation is refused for any actor that is not an identified person whatever this flag holds); `confirm_source_writes` (bool, default false); `answer_timeout_minutes` (int ≥ 0, default **0**, meaning wait without limit; on expiry the question is recorded as unanswered and no answer is ever supplied on the user's behalf). This field and the desktop preference `requirements/answerWaitSeconds` (REQ-CONFIG-405, REQ-CONFIG-413) each govern a disjoint set of runs, so exactly one applies to any given run and the two can never disagree observably: **a run a person started from the desktop application takes its budget from `requirements/answerWaitSeconds` and this field is not consulted; every other run — a run the board scheduled, and any other run started without a person present — takes its budget from `answer_timeout_minutes`.** How long an unattended run waits is a property of who is watching it, which is why the desktop's own value wins for runs that desktop starts, exactly as the released-run elevation is a desktop preference and not a workspace field (REQ-CONFIG-408). Both spell "no limit" as zero. Any surface that displays the budget states which of the two is in force for the run it is describing. `requirements.change`: `analyze_changes` (bool, default true; false parks each change in a needs-update state until a person handles it); `adopt_hash_after_verification` (bool, default true — a verdict of no behavioural impact adopts the new hash only once verification has passed, never on the verdict alone); `propagate_evidence_loss` (bool, default true — a deleted covering test or a dropped trace moves the requirement out of done with no textual analysis step); `gate_on_dependencies` (bool, default true); `report_dangling_dependents` (bool, default true — removing a requirement surfaces its dependents as dangling and never deletes them). An actor counts as **a person** exactly when the action arrives through an interactive surface in direct answer to a prompt the product raised for that specific action, with that surface attached to a window. An action arriving from an agent, from a hook, from a scheduled or otherwise unattended run, or from a replay of recorded events is never a person, whatever it claims about itself, and a confirmation reaching one of those hosts is refused and recorded as unanswered rather than assumed. The audit record names the operating-system account the interactive session was running under together with the surface the answer came from; the product maintains no identity of its own and asks for none.

### Provider/model discovery snapshot

- **REQ-CONFIG-199** — The snapshot is a YAML document in the global scope written with insertion order preserved (not alphabetized) and with unknown keys forbidden at every level.
- **REQ-CONFIG-200** — The snapshot carries `version` (int, default 1). Any value other than 1 is rejected with an "unsupported version" error: the format is deliberately **not** forward compatible.
- **REQ-CONFIG-201** — Each snapshot provider carries an id, a required display name, an optional family and base URL, a **required** authenticated flag, a list of discovered models, five optional slot suggestions (`default_summary_model`, `large_model`, `medium_model`, `small_model`, `fallback_model`) and a required discovery timestamp. Duplicate model ids within one provider are rejected.
- **REQ-CONFIG-202** — Each snapshot model carries a required id, an optional display name, capability, limit and pricing maps, and a **required** discovery timestamp that must be an ISO-8601 UTC string; a non-string value is rejected naming the field.
- **REQ-CONFIG-203** — Providers whose authenticated flag is false contribute **nothing** to the merged configuration — not even entries in `unavailable_models`.
- **REQ-CONFIG-204** — Each authenticated provider's non-null slot suggestions are contributed to the snapshot layer. Where two or more authenticated providers suggest a value for the same slot, exactly one of those suggestions reaches the merged configuration, chosen deterministically: authenticated providers are considered in ascending code-point order of their provider id, and the **first** provider offering a non-null suggestion for a slot wins it; later suggestions for that slot are ignored. The order is therefore independent of the order the snapshot happens to store providers in, of the order the user signed in, and of the machine — the same snapshot always produces the same slot values. Ordering among providers inside this layer settles nothing about ordering between layers, which stays fixed and total (REQ-CONFIG-031, REQ-CONFIG-449).
- **REQ-CONFIG-205** — Each discovered model becomes a `models:` entry keyed by its qualified id, **unless** the user already declared that key in YAML with both `provider` and `model_id` set — that counts as a complete override and discovery skips the key entirely.
- **REQ-CONFIG-206** — A discovered model classified unavailable, **and** never mentioned by the user in YAML, is recorded under `unavailable_models:` instead of `models:`, which keeps any client construction from reaching it while still letting pickers display it alongside the reason. The asymmetry is deliberate: once a user names a model anywhere in YAML it stays a configured model, even where the provider marks it unavailable.
- **REQ-CONFIG-207** — Fields synthesized per discovered model: `provider` (literally `deepseek` or `claude-code` for those two providers, otherwise `openai`), `model_id` (the id with a leading `<provider>/` prefix stripped when present), `auth_provider` (the provider id), `base_url` (the provider's, falling back to the catalog provider's default), `max_input_tokens`/`max_output_tokens` from the model's limits, `api_key` and `api_key_env` both null, `api_mode` (only when the discovered value is exactly `chat` or `responses`, otherwise null), and the two per-token prices from the model's pricing map.
- **REQ-CONFIG-208** — An `unavailable_models:` record carries the model id, a display name, the sign-in provider, a machine-readable reason code, one reason sentence in plain language resolved once at load so that every surface shows identical wording, and an optional provider-supplied detail that is trimmed and omitted when blank. The record's shape differs from a `models:` entry and carries no field from which a client could be constructed (REQ-CONFIG-454). The reason-code vocabulary is **closed** and is exactly `not-entitled`, `deprecated`, `retired`, `region-restricted`, `quota-exceeded`, `unsupported`, `unknown`. It is a machine-readable contract: a surface may branch on these values. A provider-supplied classification that is not one of them is recorded as `unknown` and the provider's own wording is carried in the optional detail, so nothing the provider says is lost and no unpublished code ever reaches a consumer.

### Snapshot read/write semantics

- **REQ-CONFIG-209** — A missing snapshot file reads as absent, not as an error.
- **REQ-CONFIG-210** — Any read failure — I/O error, YAML error, schema violation — is surfaced as a single error naming the snapshot path and carrying the underlying detail, and the cached entry for that path is dropped. The configuration load catches it and continues (REQ-CONFIG-021).
- **REQ-CONFIG-211** — Within one running process, an updated `project_settings.yaml` is observed on the next load whenever its modification time or its byte size differs from what the previous read saw. A rewrite that leaves both unchanged is **not** observed before the process restarts, and that is accepted rather than defended against: the product's own snapshot writer always advances the file's modification time (REQ-CONFIG-212), so every rewrite the product itself performs is observed, and the unobserved case needs an external writer that deliberately restores both the previous timestamp and the previous byte size. No content hashing is performed on this path.
- **REQ-CONFIG-212** — Snapshot writes are atomic (staged beside the target, then swapped), create missing parent directories, set mode `0644`, leave the swapped-in file's modification time at the moment of the write so the change is always detectable (REQ-CONFIG-211), leave no temporary file behind, and drop the cached entry for that path afterwards.
- **REQ-CONFIG-213** — Before a snapshot is written the payload is examined field by field and the write is **refused**, naming the dotted path of the offending field, where it would persist a credential; this is the same screen REQ-PROVIDER-086 states from the writing side. A key name triggers refusal when it meets the secret-looking key test of REQ-TOOLS-172, and additionally when it carries the segment `session` or contains `ghu_` anywhere within it — two triggers this screen adds because a persisted catalog must carry less than a rendered line of text may. A string value triggers refusal when it begins with one of the credential value prefixes of REQ-TOOLS-171. Neither the key test nor the prefix list is restated here; what this requirement relies on them for is that both comparisons ignore letter case, so `api_key`, `apiKey` and `API-KEY` all trip the key test and a value beginning `eyJ` trips the `eyj` prefix. Keys the snapshot format itself requires are exempt, since the document could otherwise never be written at all: the two per-token price keys beneath a `pricing` parent, and the token-limit keys beneath a `limits` parent, which REQ-CONFIG-202 requires and REQ-CONFIG-207 reads back — both carry public metadata. Those two are the **complete** exempt set and no further key is exempt: a snapshot field added later that trips the screen is renamed so that it does not, rather than added to this list, because every exemption is a hole in a check whose whole purpose is to be unconditional. The provider `authenticated` flag (REQ-CONFIG-201) needs no exemption, its single segment under REQ-TOOLS-172 being `authenticated` and not `auth`.

### Secrets

- **REQ-CONFIG-214** — `secrets.yaml` is a two-level mapping: tool-server name → environment-variable name → value. It may exist in either scope.
- **REQ-CONFIG-215** — Global and workspace secret files merge **per key within a server**: a workspace file that sets one key for a server does not discard the global file's other keys for that same server.
- **REQ-CONFIG-216** — Secret writes are atomic and create the target directory when missing. On any failure the staged file is removed and the failure is reported. Every write leaves `secrets.yaml` at mode `0600` — owner read and write, no group or other bit ever set — and applies that protection explicitly on every write rather than letting the file inherit whatever mask or parent directory happens to be in force. On a platform with no POSIX file mode, no mode bit is set or reported and the protection is instead the explicit owner-only access control REQ-PROVIDER-016 fixes for the credential store, which is cited here and not restated. This is deliberately **not** the `0644` that REQ-CONFIG-444 and REQ-CONFIG-212 fix for ordinary configuration, and the reason is the file rather than the domain: `secrets.yaml` is the one file of this document's configuration set that holds credentials by design (REQ-CONFIG-007), so it is protected by what it carries and not by the class of file it is. Nor is the platform-default fallback REQ-CONFIG-444 permits available here — leaving a platform's own default in place is what this requirement forbids. Where the required protection cannot be applied the write does not happen: the staged file is removed and the failure is reported on this requirement's own terms above, so no secret is ever left on disk at a weaker protection than this requirement fixes.
- **REQ-CONFIG-217** — Setting a secret creates the server's sub-map when absent. Unsetting a single secret reports whether anything was removed and **writes nothing** when the key did not exist; removing a server's last key removes the server entry entirely. Unsetting all of a server's secrets reports the count removed and writes only when something was removed.
- **REQ-CONFIG-218** — Stored secrets for a tool server are overlaid **after** environment expansion, so a stored secret always beats the shell environment for the same key.
