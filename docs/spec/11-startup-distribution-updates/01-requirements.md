# Application Startup, Distribution, and Updates — Product identity, entry points, and version reporting

Part 1 of 10 of [domain 11](../11-startup-distribution-updates.md), which indexes every part. Defines REQ-STARTUP-001 – REQ-STARTUP-026.

## Requirements

### Product identity, entry points, and version reporting

**REQ-STARTUP-001** — *Withdrawn.* It required publication as two packages of one language ecosystem, which describes a different product: this product is a single desktop application, and the form in which it is packaged and published is an architecture decision rather than a behavior a user observes. What it protected — that a release carries exactly one product version, which every artifact of that release declares — is carried by REQ-STARTUP-158, and the guard that enforces it is REQ-STARTUP-028.

**REQ-STARTUP-002** — Exactly one executable entry point SHALL exist and be shipped as a standalone binary: the desktop application `rotaris`, which on Windows opens no console window. No console, headless, benchmark or other secondary executable SHALL be published, and no installation SHALL make one available. The one exception is not an entry point a user invokes: the application launches its own executable as a child process to host the bundled code-intelligence tool server, on the terms of REQ-MCP-033 and REQ-STARTUP-015.

**REQ-STARTUP-003** — *Withdrawn.* Its only surface was a command-line invocation of the application as a module of its language runtime, which this product does not offer; the single desktop entry point is REQ-STARTUP-002.

**REQ-STARTUP-004** — The product SHALL report its version from its own installation metadata. When that metadata is absent, the reported version SHALL be the literal string `0+unknown`. Standalone bundles SHALL always report the true release version and never `0+unknown`.

> **Narrowed by [`PD-STARTUP-003`](../../product/directives/pd-startup-003.md#pd-startup-003), 2026-10-06.** With no metadata the
> running desktop reports `dev`, as REQ-STARTUP-007 states, not `0+unknown`. The first and last sentences still
> govern.

**REQ-STARTUP-005** — *Withdrawn.* Its only surface was a command-line flag writing to standard output and setting a process exit code, neither of which this product has; reading the running version is carried by REQ-STARTUP-007 and by the About surface of REQ-SHELL-140, which presents it as selectable text with no window construction or network activity of its own.

**REQ-STARTUP-006** — *Withdrawn.* Its only surface was a console subcommand, and the automatic pre-step it excepted itself from was withdrawn with REQ-STARTUP-100; reading the running version is carried by REQ-STARTUP-007 and REQ-SHELL-140.

**REQ-STARTUP-007** — The running desktop SHALL treat its own version as: the version its own installation metadata declares (REQ-STARTUP-004); else the literal `dev` when no such metadata is present; and exactly `0.1.0` in demo mode (REQ-SHELL-162). This value SHALL be the one the About surface presents (REQ-SHELL-140) and the one compared against the release feed. When the running version is not a parseable release version (e.g. `dev`), the update comparison is unanswerable and no update SHALL ever be offered (see REQ-STARTUP-109).

**REQ-STARTUP-158** — A release SHALL carry exactly one product version. Every artifact that release publishes SHALL declare, and SHALL report at run time, that same version, and a release in which any published artifact declares a version other than the release's SHALL NOT be publishable; the pre-build guard of REQ-STARTUP-028 is where that is decided, and REQ-STARTUP-031 is where the version appears in each artifact's name. This requirement fixes how many versions a release has and says nothing about the form in which the product is packaged or the channel through which it is published, neither of which is a behavior a user observes.

**REQ-STARTUP-159** — What the user installs SHALL be self-contained, and the user SHALL be able to install the product and run it with nothing else installed and nothing else fetched. On a machine of any platform key of REQ-STARTUP-030 (on Linux, the baseline of REQ-STARTUP-024) carrying no separately installed language runtime, framework, or component of the product obtained by any other route, and with all outbound network access blocked, installing that platform's published artifact and starting it SHALL produce each of these observations: the desktop entry point paints its main window (REQ-STARTUP-002); its About surface presents the true release version and never `0+unknown` (REQ-STARTUP-004, REQ-STARTUP-007, REQ-STARTUP-158, REQ-SHELL-140); and every data asset the product reads at run time resolves from within what was installed, with no additional download — the pricing and model tables, the prompt templates, the CA root bundle used for setup downloads (REQ-STARTUP-083), the font families registered at startup (REQ-STARTUP-040), the keys against which a release's manifest signature is verified (REQ-STARTUP-167), and `THIRD-PARTY-LICENSES.txt` (REQ-STARTUP-141). "From within what was installed" reaches an asset the artifact resolved out of a preparation it made of itself, and equally one it resolved out of the run-scoped placement a run that could make no preparation puts its payload in (REQ-STARTUP-165), each of those being derived from the artifact alone and fetching nothing; it does not reach anything obtained from the network or from a separately installed component. No startup path SHALL fail, and no startup path SHALL exit non-zero, because installation or version metadata for a component of the product is unavailable. The machine tools of REQ-STARTUP-058, the package caches of REQ-STARTUP-064, and the language servers the bundled code-intelligence runtime provisions at the first use of a language (REQ-MCP-118) are the only things fetched after installation, and only where the machine does not already supply them; their absence degrades individual capabilities without preventing this first run (REQ-STARTUP-077). The runtime itself is inside what was installed (REQ-STARTUP-015, REQ-MCP-033); its language servers are obtained by the runtime's own providers, into the per-user data directory of REQ-STARTUP-145, only when a symbol-level tool is first used for that language, and are declared in the setup manifest (REQ-STARTUP-058) and listed by REQ-STARTUP-142 like the machine tools are. A language whose server is absent loses that language's symbol-level tools and nothing else: the runtime's pattern-search and memory tools keep working, the failure is the server's own error result and never a host failure (REQ-MCP-113), and this first run is unaffected. *Amended 2026-09-06 under ESC-32 (IC-7 adopted, option 2): the sentence previously read "The machine tools of REQ-STARTUP-058 and the package caches of REQ-STARTUP-064 are the only things fetched after installation"; the bundled runtime's first execution (ADR-0035) measured that the runtime obtains its language servers at first use, and the owner ruled them tools provisioned after installation rather than payload to bundle.*

### Standalone build command

**REQ-STARTUP-008** — A single version-controlled build command per OS SHALL produce the standalone binary. This command is maintainer-side release tooling driven by the release pipeline of REQ-STARTUP-027; it is not a surface of the shipped product and is reachable by no user of the application. It SHALL accept a target name from exactly {`rotaris`}, an optional bundle mode from exactly {`onedir`, `onefile`} (default `onedir`), and an optional output directory. On success it SHALL print `{target} ({mode}) -> {artifact_path}` to stdout and exit 0.

**REQ-STARTUP-009** — Build error semantics: an unknown target SHALL be rejected before any build work begins, with a message naming the valid targets; a missing build configuration SHALL fail naming the expected path; a failure of the underlying freeze step SHALL be reported with its exit code, never swallowed. All handled failures SHALL print `error: <reason>` to stderr and exit 1. Command-line usage errors (unknown subcommand or choice) SHALL exit 2.

**REQ-STARTUP-010** — A bundle-mode value other than exactly `onedir` or `onefile` SHALL be rejected as an error (typos never fall back to a default).

**REQ-STARTUP-011** — Artifact locations relative to the output directory: `onefile` produces `<dist>/<target>[.exe]`; `onedir` produces `<dist>/<target>/<target>[.exe]`. The default output directory SHALL be `dist/` in the checkout.

**REQ-STARTUP-012** — *Withdrawn.* It stated the self-containment claim in terms of one language ecosystem — an absent interpreter and two uninstalled packages of that ecosystem — which describes a different product. The claim itself is behavior a user observes and is preserved in full, technology-neutrally, by REQ-STARTUP-159: same platform baseline, same blocked network, same first paint, same true release version on the About surface, same run-time data assets resolving from what was installed, and the same prohibition on a startup path failing for want of installation metadata.

**REQ-STARTUP-013** — Bundle mode SHALL be assigned per artifact as follows: the Windows portable executable of REQ-STARTUP-031 SHALL be the only artifact published in `onefile` mode — observable as a single executable file that runs with no support tree beside it; the payload wrapped by the Windows installer, the payload inside the macOS disk image, and the payload inside the Linux AppImage SHALL each be a `onedir` tree — observable as the layout of REQ-STARTUP-011, the executable sitting inside a directory together with its support files. Every other published artifact SHALL likewise carry a `onedir` payload; no artifact besides the Windows portable executable SHALL be a `onefile` bundle.

**REQ-STARTUP-014** — The macOS desktop build SHALL be produced as an application bundle named `rotaris.app` with bundle identifier `ai.rotaris.app`.

**REQ-STARTUP-015** — Bundled tool-server hosting: the bundled code-intelligence server SHALL be launched by the application as a child process of its own, on the terms REQ-MCP-033 fixes. This domain relies on that requirement for how the launch is performed and for the reserved command token it turns on, and states no launch mechanism of its own. What this domain fixes is what the launch is observable as: the server is started from what the user installed and needs nothing fetched or separately installed to run (REQ-STARTUP-159); the reserved token is a sentinel for a child process the product starts internally, not a user-facing invocation, and no argument vocabulary beyond it is defined for the shipped executable (REQ-STARTUP-002); and a process started as that child presents no user interface and opens no window (REQ-MCP-033, REQ-MCP-113). Exactly one copy of the bundled tool server's license text SHALL be present inside the desktop bundle (REQ-STARTUP-142).

### Windows installer and portable executable

**REQ-STARTUP-016** — The Windows installer SHALL install strictly per-user with no elevation prompt: default install location `%LOCALAPPDATA%\Rotaris`, with the chosen directory remembered in the per-user registry under `HKCU\Software\Rotaris` (value `InstallDir`). Per-user installation SHALL allow the in-app updater to replace files without administrator rights.

**REQ-STARTUP-017** — Interactive installation SHALL flow Welcome → Directory → Install → Finish, warn on abort, and offer a checked-by-default "Launch Rotaris" checkbox on the Finish page. Silent installation (`/S`, with optional `/D=<dir>` to set the directory) SHALL show no pages and never auto-launch the app.

> REQ-STARTUP-174) starts the updated application when it completes; a silent installation started any other way still
> never auto-launches. The interactive flow is unchanged.


**REQ-STARTUP-018** — Installation SHALL: copy the application tree into the install directory; create a Start Menu folder `Rotaris` containing shortcuts `Rotaris` (to the app) and `Uninstall Rotaris`; write a per-user uninstall registry entry under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` with `DisplayName`, `DisplayVersion`, `Publisher` = `Rotaris`, `DisplayIcon`, `UninstallString`, `NoModify`=1, `NoRepair`=1; and write an `Uninstall.exe` into the install directory.

**REQ-STARTUP-019** — Uninstallation (including silent `Uninstall.exe /S`) SHALL remove only what installation created: the shortcuts, the installed tree, the uninstaller, the install directory only if it is then empty, and both registry keys. Per-user configuration and data directories and per-workspace `.rotaris/` state SHALL never be touched by uninstall.

**REQ-STARTUP-020** — The Windows portable artifact SHALL be a single self-contained executable that runs from any location when double-clicked, without installation.

**REQ-STARTUP-165** — An artifact published in `onefile` mode (REQ-STARTUP-013) MAY prepare itself once for launching and start from that preparation on every later run of the same artifact. The first-paint bound of REQ-STARTUP-155 is what makes such a preparation necessary rather than merely permitted, because only the run that performs it is exempt from that bound. Where an artifact prepares itself, all of the following SHALL hold, and they are the whole of what this document fixes about it: the form a preparation takes, what it is called, and where within the storage named below it is placed are implementation choices, and no user-facing surface of this product exposes any of them.

(a) *It never lands beside the artifact.* The preparation SHALL be held in the per-user data directories of REQ-STARTUP-145, which that requirement fixes as the per-user location local to this machine and not replicated to another machine — a property this clause relies on and does not state for itself, because a replicated preparation would be a payload one machine prepared, appearing under another machine's per-user directories. It SHALL NOT be written into the directory the artifact was launched from, onto the medium carrying the artifact, or anywhere else that travels with the artifact. Starting the artifact SHALL write nothing to that directory and nothing to that medium. It follows, and SHALL be observable, that the artifact starts and runs when launched from read-only media and from removable media; that such a medium is left byte-for-byte unchanged by starting the artifact from it; and that the artifact remains exactly what REQ-STARTUP-013 and REQ-STARTUP-020 require of it — a single executable file that runs with no support tree beside it. A preparation is not a published artifact: it is never offered for download, never listed in a checksum manifest, and its existence changes nothing about the closed artifact set of REQ-STARTUP-031 or about what a user copies when they copy the artifact.

(b) *A different artifact prepares afresh.* A preparation belongs to exactly the artifact that produced it. An artifact SHALL start from a preparation only where that preparation was produced by an artifact of identical content, so that a new version and a rebuilt artifact of the same version each prepare afresh; running a given artifact SHALL always run that artifact's own code, whatever has run on the machine before it. A preparation belonging to an artifact that is no longer run SHALL be identifiable as belonging to that artifact, so that it can be removed without disturbing any other, and removing it SHALL be indistinguishable from that artifact never having prepared (clause (c)).

(c) *An unusable preparation is redone, never reported; a preparation that cannot be made at all is reported.* A preparation that is incomplete, unreadable, or not the one belonging to this artifact SHALL cause the artifact to prepare again, and SHALL NOT cause the launch to fail, to warn, or to report anything at all to the user. Preparing is the recovery path and SHALL never be the failure path. Deleting or corrupting a preparation between runs SHALL therefore cost at most one repeated preparation, and SHALL never prevent the artifact from starting nor cause it to run any code but its own.

Where a run produces no usable preparation at all — the storage of clause (a) refusing the write, being full, or being unavailable, so that redoing it does not succeed either — that run SHALL still start the artifact and SHALL run it with every behavior of clause (f) unchanged. Not being able to prepare SHALL never be a reason the product does not run, and SHALL never cause the launch to fail. Such a run SHALL be exempt from the first-paint bound on the terms REQ-STARTUP-155 states, because it performs exactly the work a preparation exists to avoid.

Such a run still has to put what the artifact carries somewhere before it can run it, because that payload cannot be executed without existing as files. What it places is **not** a preparation and SHALL NOT be kept as one: it SHALL serve that one run, SHALL be removed when the run ends, and SHALL never be started from again, so the next launch of that artifact does exactly what this one did rather than inheriting anything from it. Where it may go is a closed set of two, and this clause is where that set is fixed. It SHALL be placed in per-user storage of the machine that ran the artifact: the per-user data directories of REQ-STARTUP-145, which is where it goes wherever they will accept it; or, only where those directories accept no write at all, the storage the platform designates for a user's transient files. There is no third permitted location, and no reading of this clause admits one. Every prohibition of clause (a) that protects the artifact holds over that placement unchanged — it SHALL NOT be written into the directory the artifact was launched from, onto the medium carrying the artifact, or anywhere else that travels with the artifact — and it SHALL raise no elevation prompt (REQ-STARTUP-087). It SHALL NOT be placed in storage replicated to another machine or to another copy of the user's profile. That prohibition is stated here rather than left to clause (a) because only the **first** of this clause's two permitted locations inherits it: the per-user data directories carry it from REQ-STARTUP-145, and the platform's transient-files storage is not those directories and inherits nothing from that requirement, so it is bound by this sentence instead. What the notice below names is still the storage a preparation could not be made in, never the placement this paragraph permits, which stays an implementation choice under this requirement's preamble exactly as a preparation's placement does. Where neither kind of storage accepts any write, there is nowhere on that machine the artifact's contents can be run from at all, and this clause's obligation to start is not reached. That bounds the sentence above which says not being able to prepare is never a reason the product does not run: that sentence is about preparing, and this residual case is a machine with no per-user storage that will accept a write of any kind, which no build can start from and for which this document fixes no behavior.

That outcome SHALL be reported, and it is the one preparation outcome that is: once per such run, after the window is painted, on the persistent, non-modal, non-blocking notice surface the update offer of REQ-STARTUP-116 appears on, at warning severity. The notice SHALL convey three things, its wording left to the implementation: that the artifact could not prepare itself and is therefore starting the slow way; which storage it could not prepare into, named as the per-user data location of clause (a) and REQ-STARTUP-145 and never as the placement within it, which stays an implementation choice under this requirement's preamble; and that every launch will cost what this one cost until that storage accepts a preparation. It SHALL NOT state or imply that the artifact cannot be used. Without this the recovery path degenerates into preparing on every launch, silently, and a user sees only an artifact that has become permanently slow with nothing anywhere saying why.

(d) *Preparing needs nothing the artifact did not bring, and no elevation.* The preparation SHALL be produced from the artifact alone. It SHALL issue no network request, so REQ-STARTUP-159's claim — that the artifact starts and runs on a machine carrying no separately installed component of the product and with all outbound network access blocked — holds for the run that prepares exactly as for every later run. Preparing SHALL raise no elevation prompt and SHALL write nothing outside the per-user directories of REQ-STARTUP-145 (REQ-STARTUP-087). That prohibition governs a preparation — the thing this requirement keeps between runs — and it has exactly one exception, which is the run-scoped placement clause (c) permits where those directories accept no write at all, itself bounded by clause (c)'s own closed set of two locations and by every prohibition of clause (a) that protects the artifact. That single exception is stated so a build has somewhere lawful to put a payload it must run, and it licenses nothing further: no other write of any kind leaves the per-user directories of REQ-STARTUP-145, and neither clause may be read as permitting a write to a location neither of them names.

(e) *The artifact stays the thing that is updated.* A run started from a preparation SHALL be able to identify the artifact file the launch started from. That file, and never the preparation, is the update target REQ-STARTUP-106 classifies and the thing REQ-STARTUP-125 replaces.

(f) *Nothing else about the run differs.* Apart from the first-run exemption of REQ-STARTUP-155, no behavior this document specifies differs between a run started from a preparation and a run started any other way: the same release version is reported (REQ-STARTUP-004, REQ-STARTUP-007, REQ-STARTUP-158), the same installation flavour is classified (REQ-STARTUP-106), the same single-instance resolution applies (REQ-STARTUP-161, REQ-STARTUP-164), and no surface anywhere in the product reports that a preparation was made, reused, superseded, or redone. This silence covers those four outcomes and no fifth: a run that could produce no preparation at all is reported, on the terms clause (c) states, and this clause SHALL NOT be read as forbidding that notice.

**REQ-STARTUP-021** — Windows binaries are unsigned; first-launch OS trust prompts (SmartScreen) are expected and SHALL be disclosed in the release notes caveat (REQ-STARTUP-035). That absence reaches the operating system's own trust decision about a downloaded file and reaches nothing else: the update path still establishes who published a release, through the signed checksum manifest of REQ-STARTUP-167.

### macOS disk image

**REQ-STARTUP-022** — The macOS artifact SHALL be a compressed disk image whose volume is named `Rotaris <version>`, containing the application bundle and an `/Applications` symlink for drag-to-install. It SHALL be native ARM64 only.

**REQ-STARTUP-023** — By design no code signature and no notarization ticket are applied to the macOS artifacts; the first-launch Gatekeeper confirmation is therefore expected and SHALL be disclosed in the release notes caveat (REQ-STARTUP-035). That absence reaches the operating system's own trust decision about a downloaded file and reaches nothing else: the update path still establishes who published a release, through the signed checksum manifest of REQ-STARTUP-167.

### Linux AppImage

**REQ-STARTUP-024** — The Linux artifact SHALL be an AppImage that runs without being extracted first on an unmodified Ubuntu 24.04 installation — the oldest system-library baseline the artifact is required to support. It SHALL carry a desktop entry with `Type=Application`, `Name=Rotaris`, `Terminal=false`, categories `Development;IDE;`, an application icon, and an Exec line that accepts an optional directory the desktop environment supplies when the user opens a folder with the application — a file-manager "open with" or drag-onto-icon gesture. A directory the operating system hands the application this way is the explicitly opened workspace of REQ-STARTUP-041 (a). This registration is the only path by which anything outside the application selects a workspace; it is a graphical gesture, and the application defines no argument vocabulary a user could type.

**REQ-STARTUP-025** — The AppImage SHALL be built against the oldest supported base OS, so that changing the build environment can never quietly narrow the set of distributions on which the published artifact runs.

### Platform scope

**REQ-STARTUP-026** — The platform keys a release publishes for SHALL be exactly the three of REQ-STARTUP-030. A release's asset list SHALL therefore contain no filename bearing a Windows-ARM64 or macOS-Intel platform key, and no download surface SHALL present a download for either. A visitor on Windows ARM64 SHALL be presented the `windows-x64` artifacts, those being the only Windows downloads offered at all. Running a `windows-x64` artifact under Windows-on-ARM x64 emulation is an expectation and not a supported configuration: it carries no acceptance criterion of its own, no release is blocked by a failure observed only under emulation, and the release gate of REQ-STARTUP-156 exercises exactly the three platform keys of REQ-STARTUP-030 and no fourth. A download surface reached from a platform for which the release publishes no artifact — Windows ARM64 and Intel macOS being the two such platforms — SHALL state which artifact it is offering instead, SHALL state that the artifact is built for a different processor architecture and is not tested on the visitor's platform, and SHALL still offer the download rather than withholding it; on Intel macOS, where no artifact can run at all, it SHALL instead state that this release publishes no macOS build for that architecture and offer no macOS download. The wording is left to the implementation.
