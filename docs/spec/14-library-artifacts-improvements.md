# Library, Artifacts, and Improvement Proposals

## Overview

After every completed task run the product may perform an optional, strictly non-blocking background analysis that writes an on-disk "improvement artifact" containing evidence-backed improvement proposals authored by a dedicated analysis model. Users review, edit, approve, reject, defer, or delete those proposals from four surfaces — a desktop Library view, a desktop dashboard card, a terminal-UI review screen, and a CLI — all of which read and mutate the same workspace-scoped artifact files. Approved proposals are applied only by a separately started improvement run whose workspace effects are checkpointed and reversible. The same domain covers the per-session store of agent-published reports and deliverables (browsable and editable in the Library and via agent-facing tools), per-persona memory files re-injected into future runs, and the saved-prompt stash and prompt history.

## Requirements

### 1. Improvement lifecycle and run classification

**REQ-LIBRARY-001** — The improvement feature MUST implement a four-stage, human-gated lifecycle: (1) after a task run completes, an analysis pass authors evidence-backed proposals; (2) a human reviews each proposal; (3) a separate improvement run applies only approved proposals; (4) applied changes are reversible via rollback. A task run MUST never modify its own configuration, personas, or gates as a side effect of analysis.

**REQ-LIBRARY-002** — Every run MUST persist exactly one run-type value drawn from `task_run`, `improvement_run`, and `integration_run`, and that value MUST be readable from the session's persisted state. Every improvement artifact MUST carry it as `source_run_type`; a stored payload that omits the field reads as `task_run`. Only `task_run` is eligible for post-run analysis: wherever this document keys behaviour off the run type, `integration_run` is treated exactly as `improvement_run`, and neither produces analysis (REQ-LIBRARY-005, REQ-LIBRARY-032). The product therefore never writes an artifact whose `source_run_type` is anything but `task_run`; the schema still accepts one so that an imported or hand-written artifact remains readable, and REQ-LIBRARY-034 keeps it out of analysis history. What classifies a run as `integration_run` is not defined in this domain — see Open Questions.

**REQ-LIBRARY-003** — Deterministic, non-model parts of the product may gather evidence but MUST never author user-reviewable proposals. Proposals are authored exclusively by the model-backed post-run analyst; each artifact records the authoring model identifier (`collector_model`, nullable).

**REQ-LIBRARY-004** — Task completion MUST never be delayed or altered by improvement analysis. Given a completing task run, when it reaches its terminal state, then the terminal result is reported to the host before any analysis work begins, and the host receives a self-contained analysis job it may execute afterward.

**REQ-LIBRARY-005** — An improvement run MUST never trigger another improvement analysis (no self-chaining). Given a run of type `improvement_run` (or `integration_run`) reaching a terminal state, then no post-run analysis occurs and no new proposals appear. End-to-end, an approval-driven improvement run performs zero analysis passes.

### 2. Proposal data model and validation

**REQ-LIBRARY-006** — The proposal category vocabulary MUST be closed with exactly 10 values: `documentation_update`, `agents_md_update`, `workspace_note`, `config_change`, `tool_enablement`, `dependency_install`, `persona_or_prompt_adjustment`, `persona_memory_update`, `preflight_check`, `verifier_gate_update`.

**REQ-LIBRARY-007** — Review status MUST have exactly 4 values: `pending_review`, `approved`, `rejected`, `deferred`. Risk MUST have exactly 3 values: `low`, `medium`, `high`.

**REQ-LIBRARY-008** — A proposal MUST carry: `id` (format `imp_` + 8 base62 characters), `category`, `summary` (minimum length 1), `evidence` (list), `recommended_action` (minimum length 1), `risk` (default `low`), `status` (default `pending_review`), `target_persona` (nullable), `proposed_verifier_section` (nullable mapping), `created_at` (UTC timestamp, defaults to creation time).

**REQ-LIBRARY-009** — Proposal construction MUST be rejected — no proposal exists afterwards, and the reported error names the field at fault — in each of these cases: (a) `evidence` is empty; (b) `category` is `persona_memory_update` and `target_persona` is missing, empty, or entirely whitespace; (c) `category` is `verifier_gate_update` and `proposed_verifier_section` is missing, is not a mapping, or is not a self-contained, valid gate-configuration block. A reviewer can check the consequence directly: a gate change written only as prose in `summary` or `recommended_action` never becomes a proposal and never appears on a review surface. The gate-configuration schema that decides (c) is not fixed by this document — see Open Questions.

**REQ-LIBRARY-010** — An evidence entry MUST carry `kind` (non-empty once surrounding whitespace is stripped), `text` (non-empty), the nullable ids `source_task_id`, `source_artifact_id`, and `source_session_id`, and an optional `excerpt`. `kind` is an open vocabulary: `transcript_observation`, `repeated_tool_failure`, `missing_resource`, `child_report_finding`, `repeated_search`, and `other` label analyst-authored evidence, while `verifier_gate_state` is reserved for the entry the product stamps onto a gate proposal (REQ-LIBRARY-029) and MUST NOT be the only entry a proposal carries (REQ-LIBRARY-159). What `excerpt` holds depends on the entry: quoted source text where the entry cites a transcript or a document, and the dedupe key on a `verifier_gate_state` entry. No consumer may assume `excerpt` is verbatim source text.

**REQ-LIBRARY-011** — The run-level artifact container MUST carry: `artifact_id` (format `impart_` + 8 base62 characters), `source_session_id` (the legacy input key `session_id` MUST be accepted as an alias), `source_run_type` (default `task_run`), `generated_at` (UTC), `collector_model` (nullable), `proposals` (list, may be empty), `considered_session_ids` (order-preserving, deduplicated), `notes` (nullable), `checkpoints` (list of rollback checkpoint records; may be absent on older artifacts), `rolled_back_at` (nullable timestamp).

**REQ-LIBRARY-012** — An artifact's rollback point MUST be the entry of its `checkpoints` list whose `kind` is `pre_improvement` and whose `sequence` is the highest among entries of that kind; because sequence numbers are unique within an artifact (REQ-LIBRARY-071), that selection is never ambiguous. An artifact holding no such entry has no rollback point, and every surface MUST report the absence rather than fail on it — for example the `no rollback point recorded` line of REQ-LIBRARY-082 and the `no` column value of REQ-LIBRARY-081. The current `applied` and `pre_rollback` checkpoints are chosen by the same rule applied to those kinds: highest `sequence`, otherwise none.

**REQ-LIBRARY-013** — Generated identifiers MUST be exactly 8 base62 characters (zero-padded) after the type prefix (`imp_`, `impart_`), and successive generations MUST differ even when produced in immediate succession.

**REQ-LIBRARY-014** — Validating a raw artifact payload MUST fail with an error message prefixed `malformed improvement artifact: ` when the payload does not satisfy the schema. An artifact whose `proposals` list is empty is valid. Re-validating an already-valid artifact round-trips losslessly.

### 3. Post-run analyst behavior

**REQ-LIBRARY-015** — The post-run analyst is a dedicated model-backed pass invoked at most once per terminal task run, with a configurable wall-clock timeout defaulting to 60 seconds. The analyst MUST never raise into its caller: every failure path yields an empty artifact whose `notes` field explains the failure.

**REQ-LIBRARY-016** — An analysis pass MUST end in one of exactly two ways: an artifact whose proposals all satisfy REQ-LIBRARY-009, or the recovery outcome of REQ-LIBRARY-022. A reply that offers nothing to propose is a success and MUST yield an artifact whose `proposals` list is empty, never an error. A reply that cannot be turned into valid proposals — because it is not the machine-readable form REQ-LIBRARY-020 accepts, or because its entries fail REQ-LIBRARY-009 — MUST take that recovery path, and nothing from it may reach an artifact file or any review surface. Every proposal that does reach a review surface MUST consequently carry at least one evidence entry; name exactly one `target_persona` when its category is `persona_memory_update`; carry a complete `proposed_verifier_section` when its category is `verifier_gate_update` (REQ-LIBRARY-063); hold a category from the closed vocabulary of REQ-LIBRARY-006, an unrecognised value having been coerced under REQ-LIBRARY-021 rather than the proposal dropped; and not repeat an outstanding gate proposal (REQ-LIBRARY-026).

**REQ-LIBRARY-017** — Analysis MUST draw only on material belonging to the run that triggered it: that run's progress, its todo state, its child reports, its gate evidence, its transcript, and the bounded prior-artifact history of REQ-LIBRARY-034. Data from another run, another session, or another workspace MUST NOT inform it. Every proposal in an artifact MUST therefore be attributable to material that existed in the session named by that artifact's `source_session_id` at the moment the run reached its terminal state, and every prior artifact that informed it MUST be named through `considered_session_ids` (REQ-LIBRARY-025).

**REQ-LIBRARY-018** — The volume of evidence one analysis pass consumes MUST be bounded, so that the outcome a user sees does not change with the size of the run: a very long transcript, a large set of child reports, or a workspace holding many prior artifacts MUST still produce a result within the timeout of REQ-LIBRARY-039. Wherever evidence text is shortened to respect a bound, the shortening MUST be marked with `…`, so that any excerpt reaching an artifact file is either complete or visibly cut. The bound values themselves are not fixed by this document — see Open Questions.

**REQ-LIBRARY-019** — Of the six evidence sources named in REQ-LIBRARY-017, one that could not be obtained MUST NOT be treated as one that was obtained and reported nothing; in particular a gate report that failed to run MUST NOT be indistinguishable from a gate that ran and found nothing. Neither case may cause the analysis to fail (REQ-LIBRARY-033). Where the difference reaches an artifact file it MUST be visible there: a gate proposal made without a known gate state or configuration fingerprint records the literal `unknown` in place of the missing value (REQ-LIBRARY-029) instead of asserting a state nobody observed. Whether the distinction has any further consequence a user or external system can observe is unresolved — see Open Questions.

**REQ-LIBRARY-020** — Analyst output parsing MUST: strip one leading/trailing Markdown code fence if present; require a JSON object containing a `proposals` list of objects; assign a fresh proposal id when the model omits one; backfill each evidence entry's `source_session_id` with the current session id; and stringify a non-string `notes` value.

**REQ-LIBRARY-021** — Given a proposal whose category value is not in the closed vocabulary, the proposal MUST be kept with its category coerced to `workspace_note` rather than dropped — surfacing evidence outranks category fidelity.

**REQ-LIBRARY-022** — On the first parse or validation failure the analyst MUST retry exactly once, re-issuing the same request augmented with the parse error and a demand for corrected machine-readable output only (at most 2 model calls total). If the retry also fails, the result is an empty artifact with `notes` = `collector parse failed: <err>`.

**REQ-LIBRARY-023** — On timeout the result MUST be an empty artifact with `notes` = `collector timed out after <t> seconds`. On any other crash, `notes` = `collector crashed: <exc>`.

**REQ-LIBRARY-024** — A provider that never answers MUST NOT extend anything the user is waiting on. Within `runtime.improvement_collector_timeout` seconds of the pass starting, the empty-artifact outcome of REQ-LIBRARY-023 MUST have taken effect and the analysis MUST read as finished on every surface — its activity indicators gone (REQ-LIBRARY-125) and its notice, if any, already posted — even though the provider call has not returned. For as long as that call stays outstanding the application MUST still accept composer input, MUST still start new runs on request, and MUST still begin shutting down on request. Whether the process may block on the outstanding call before it exits is unresolved — see Open Questions (REQ-LIBRARY-127).

**REQ-LIBRARY-025** — The produced artifact's `considered_session_ids` MUST record the source-session id of each prior workspace artifact supplied as history, deduplicated in encounter order.

**REQ-LIBRARY-026** — After parsing, each `verifier_gate_update` proposal MUST be stamped with a citation of the gate evidence it was made from and dropped when it repeats a prior gate proposal that is still `pending_review` with the same dedupe key. This deduplication MUST be enforced by the product itself rather than merely requested of the model.

### 4. Gate evidence

**REQ-LIBRARY-027** — Gate evidence MUST be a JSON value that survives being written into an artifact file and read back unchanged. One capture MUST yield one gate description: the text a person reads (REQ-LIBRARY-028), the evidence entry stored on a proposal, and the dedupe key computed for it (REQ-LIBRARY-029) MUST all describe that same captured state, so no two of them can disagree about the gate. The record MUST carry the gate's overall state; the fingerprint of the gate configuration it was taken from; where the check suite was obtained and the form in which it was declared; for every configured check its name, command, verification role, severity, and working directory; the probe results; the per-check outcomes; the checks that could not be executed; and the verification roles no configured check covers. The serialized key names are not fixed by this document — see Open Questions.

**REQ-LIBRARY-028** — Gate evidence MUST have exactly one text rendering, used both where a person reads it and where it is stored in an evidence entry, so the two can never differ. A record carrying no gate state MUST render as the empty string; a workspace whose gate is satisfied therefore contributes no gate text anywhere and produces no gate-related signal. Otherwise the rendering MUST contain one line beginning `gate state: ` and naming the state; one line per configured check beginning `check <name> [<role>/<severity>]`; one line per probe result; one line per check outcome; one sentence naming every check that could not be executed and therefore demonstrated nothing; and one sentence naming every verification role for which tooling is present but no configured check exists. The wording of the probe lines, the outcome lines and those two sentences, and the order in which the per-check lines appear, are not fixed by this document — see Open Questions.

**REQ-LIBRARY-029** — After stamping, a gate proposal's `evidence` list MUST hold exactly one entry whose `kind` is `verifier_gate_state`, and that entry MUST be the last one: an entry of that kind already present is removed and the new one appended, so stamping twice never leaves two. That entry's `text` MUST read `gate state <state> at fingerprint <first 12 characters of the fingerprint>`, with the literal `unknown` in place of whichever of the two values is missing, and its `excerpt` MUST be the dedupe key. The dedupe key MUST be a 16-character lowercase hexadecimal digest covering both halves of the suggestion: the proposed gate-configuration block, and the gate situation it was made from (state, configuration fingerprint, the checks that could not run, and the uncovered verification roles). Changing either half MUST change the key, so the same block re-proposed against a materially different gate situation counts as a new suggestion and is not suppressed. Proposals of every other category MUST be left untouched by this step. The digest function, and how the two halves are canonicalised before digesting, are not fixed by this document — see Open Questions.

**REQ-LIBRARY-030** — Gate-proposal duplicate detection MUST compare the new proposal's key against the key recorded on each earlier gate proposal when that earlier proposal was created, never against a key freshly recomputed from current evidence. Only prior proposals still in `pending_review` suppress a new one; proposals in `rejected` or `approved` status MUST never suppress a new proposal.

**REQ-LIBRARY-031** — Uncovered-role detection MUST consider exactly three verification roles: `test`, `typecheck`, and `lint`. A role MUST be reported as uncovered when the workspace carries a marker for that role and no configured check declares it. A role for which the workspace carries no marker MUST NOT be reported, and neither MUST a role that some configured check declares — including a check that failed or could not be executed. Which markers count as evidence that a role is present is not fixed by this document — see Open Questions.

### 5. Post-run capture and eligibility

**REQ-LIBRARY-032** — Analysis capture MUST yield no job at all (not an empty artifact) when ANY of the following holds: the run type is not `task_run`; no analyst is configured; the setting `runtime.improvement_collector_enabled` is false; the run's stop reason is one of `stopped by user`, `interrupted by user`, `agent session aborted`; or no session directory exists.

**REQ-LIBRARY-033** — Evidence MUST be frozen at capture time by taking independent snapshots of run progress, todo state, transcript events, child reports, workspace history, and gate evidence, so that subsequent work cannot mutate what is reviewed. A failing transcript-context supplier degrades to empty context; child-report coercion failures degrade to an empty list.

**REQ-LIBRARY-034** — Workspace history supplied to the analyst MUST be bounded and filtered: prior artifacts whose `source_run_type` is not `task_run` are excluded, the current session's own artifact is excluded, and at most 5 prior artifacts are included, newest first.

**REQ-LIBRARY-035** — Running a captured analysis job MUST produce exactly one of the following observable outcomes, and MUST never propagate a failure into the run that produced it: (a) cancellation requested before the job starts — no artifact file is written and no notice is published; (b) the pass cannot be started, or fails in a way REQ-LIBRARY-022 and REQ-LIBRARY-023 do not already cover — no artifact file is written, no notice is published, and a warning is recorded in the application log; (c) cancellation observed after the artifact was produced but before it was stored — no artifact file is written and no notice is published; (d) the write fails — no artifact exists to report, the store is left exactly as it was (REQ-LIBRARY-047), and the failure stays out of the run's result (REQ-LIBRARY-161); (e) success — exactly one artifact file is written with cross-artifact duplicate suppression applied (REQ-LIBRARY-046), and the surfaces of REQ-LIBRARY-124 report that artifact and the number of proposals it holds.

**REQ-LIBRARY-036** — Session snapshots MUST persist the session's `run_type` and the list of improvement artifact ids produced for the session, so artifacts re-associate with a session across resumes.

**REQ-LIBRARY-037** — Post-run analysis MUST use the model named by `improvement_collector_model` when that setting holds a value, and the configured medium-tier model otherwise. An explicit request to enable the feature while neither resolves MUST be refused with the message `medium_model must be configured to enable the post-run improvement collector.` and MUST leave `runtime.improvement_collector_enabled` as it was. The refusal covers only an explicit enable: a workspace running on the default-on setting of REQ-LIBRARY-038 with no resolvable model MUST NOT fail — it takes the no-analyst path of REQ-LIBRARY-032, captures no job, writes no artifact, and shows the user nothing. Whether that silence is the intended treatment of the default configuration is unresolved — see Open Questions. The wall-clock bound on the pass is `runtime.improvement_collector_timeout` (REQ-LIBRARY-039).

### 6. Configuration

**REQ-LIBRARY-038** — Setting `runtime.improvement_collector_enabled` (boolean, default `true`) is the master switch. When false, no analysis runs and no completion notification of any kind is shown.

**REQ-LIBRARY-039** — Setting `runtime.improvement_collector_timeout` (integer seconds, default `60`, minimum `1`) bounds analyst wall-clock time before the empty-artifact fallback.

**REQ-LIBRARY-040** — `improvement_collector_model` (nullable string, default null) is a first-class startup model slot with an independent thinking-mode override, persisted and round-tripped like other model slots; the minimal bootstrap configuration template includes both keys as null. When unset it falls back to the medium-tier model.

**REQ-LIBRARY-041** — The desktop Settings view MUST expose the master switch as a runtime toggle row labelled "Improvement loop", loading from and saving back to `runtime.improvement_collector_enabled`, and participating in unsaved-changes detection.

### 7. On-disk persistence of improvement artifacts

**REQ-LIBRARY-042** — Improvement artifacts MUST be stored as one JSON file per artifact at `<workspace>/.rotaris/improvement_artifacts/<artifact_id>.json`, indented with two spaces. The store is keyed by workspace, not by session: a review decision recorded by one session MUST still be present after the application restarts, and MUST be what every other session in the same workspace reports once it refreshes (REQ-LIBRARY-164). Coordination between processes goes no further than the whole-file atomic replacement of REQ-LIBRARY-043 and REQ-LIBRARY-158 — there is no locking — so two processes recording decisions on the same artifact at the same instant may leave only one of them recorded. That outcome and the agreement guarantee of REQ-LIBRARY-164 are in tension; which is canonical is unresolved — see Open Questions.

**REQ-LIBRARY-043** — Every write to the store MUST be atomic as seen by a reader: at any instant a concurrent read returns either the complete previous file or the complete new one, never a partial, empty, or unparseable file, and a write interrupted by a crash or power loss MUST leave the artifact readable. Any transient file a write creates MUST be gone from the store directory once the write has finished, whether it succeeded or failed, and MUST never be named so that the id listing of REQ-LIBRARY-045 could mistake it for an artifact. On Windows a replacement that fails only because another process momentarily holds the file MUST be retried — up to 5 attempts in total, with a short pause before each retry — before the write is reported as failed.

**REQ-LIBRARY-044** — On first store access (list, load, or save), artifacts found at the legacy per-session location `.rotaris/sessions/<session_id>/improvement_artifacts/*.json` MUST be imported into the workspace store when absent there; malformed legacy files are skipped with a logged warning and are never fatal.

**REQ-LIBRARY-045** — Listing artifact ids returns lexicographically sorted file stems; listing full artifacts returns newest-first by `generated_at`; a "latest artifact" query optionally filters by source session; loading an unknown id fails with a not-found error whose message is `improvement artifact not found: <path>`.

**REQ-LIBRARY-046** — Cross-artifact duplicate suppression, which MUST be applied to every save an analysis pass makes, drops a proposal from the artifact being written when some other artifact in the same workspace already holds an open proposal with the same key. The key is the triple (`category`, `target_persona`, `recommended_action`); text is compared ignoring letter case and ignoring differences in leading, trailing, and repeated whitespace, and two proposals that both lack a `target_persona` match on that element. Open means a status of `pending_review`, `approved`, or `deferred`; a `rejected` proposal MUST NOT suppress anything, so an idea the user turned down can be raised again. Whenever at least one proposal was dropped, the line `Suppressed duplicate proposals already covered by: <ids>.` MUST be appended to the written artifact's `notes`, naming the covering artifacts in ascending lexicographic order.

**REQ-LIBRARY-047** — A save MUST be all-or-nothing: either a schema-valid artifact lands on disk, or the file already there is left untouched and the save reports failure. An artifact that duplicate suppression (REQ-LIBRARY-046) has altered MUST still satisfy the schema after the alteration. Each successful save MUST also record a history version holding exactly the state that was stored (REQ-LIBRARY-049). Recording that version is best-effort: when the artifact file is written but its version cannot be, the save MUST still report success, the change the user asked for MUST still take effect, and the failure MUST appear only in the application log. Review decisions, edits, and deletions therefore keep working in a workspace whose `history/` directory cannot be written.

**REQ-LIBRARY-048** — When no explicit write cause is given, a write for an artifact with neither an existing file nor recorded history is attributed `collected` (only initial analysis writes first); any other implicit write defaults to `edit`. Explicit causes are used by review (`status_change`), editing (`edit`), deletion (`delete`), checkpointing (`checkpoint`), and rollback (`rollback`).

### 8. Versioned artifact history

**REQ-LIBRARY-049** — Every artifact write MUST also append the written state at `<workspace>/.rotaris/improvement_artifacts/history/<artifact_id>/<version>.json` (version zero-padded to 6 digits), containing `{version (≥ 1, monotonically increasing), recorded_at (UTC), cause, artifact (full copy)}`, written atomically. The `history/` directory can never collide with an artifact file because artifact ids carry the `impart_` prefix and history is not a `.json` file at that level.

**REQ-LIBRARY-050** — The history cause vocabulary MUST be exactly: `collected`, `status_change`, `edit`, `delete`, `checkpoint`, `rollback`, `unknown` (the last meaning pre-history state already on disk).

**REQ-LIBRARY-051** — Reading the history of a pre-history artifact MUST synthesize a version 1 from the current file with cause `unknown` and `recorded_at` equal to the artifact's `generated_at`, writing nothing — opening a workspace never rewrites untouched files. The first history-aware overwrite MUST first seed the pre-existing on-disk state as version 1 so it is preserved rather than lost.

**REQ-LIBRARY-052** — At most 25 versions per artifact are retained by default, and retention MUST be applied after each version is appended. For a keep count N ≥ 2 the retained set is version 1 together with the newest N−1 versions, so the state as first recorded is never what pruning gives up; with N = 1 only the newest version survives; with N ≤ 0 no version files are kept. Pruning MUST remove the oldest droppable version first, a droppable version being any version that is neither version 1 nor the newest. Which configuration key, if any, sets N is not stated in this document — see Open Questions.

**REQ-LIBRARY-053** — History enumeration MUST be defensive: unreadable or corrupt version files are skipped with a warning; listing returns newest-first; loading a missing version fails with `improvement artifact '<id>' has no recorded version <n>`; an unknown artifact yields an empty history.

**REQ-LIBRARY-054** — Given approve → edit → reject applied to one proposal, then four retrievable states exist — the initially collected state plus one recorded state for each mutation — with distinct causes and timestamps; and current-state reads MUST be completely unaffected by the presence or absence of history.

### 9. Review API (status, edit, delete)

**REQ-LIBRARY-055** — Setting a proposal's status MUST rewrite only the matching proposal, persist atomically with cause `status_change`, return the updated artifact, and survive full reload from disk. An unknown proposal id fails with `proposal '<pid>' not found in artifact '<aid>'`.

**REQ-LIBRARY-056** — Editing a proposal MUST be restricted to the two user-editable free-text fields, `summary` and `recommended_action`; evidence and category remain analyst-authored and immutable through this path. Blank replacement text fails schema validation; unknown proposals fail with the not-found error; the write cause is `edit`.

**REQ-LIBRARY-057** — Deleting a proposal MUST remove exactly the target proposal (others untouched), persist with cause `delete`, and fail with the not-found error for unknown ids. An artifact may end with zero proposals and remains valid.

**REQ-LIBRARY-058** — The approved-proposal filter MUST return only proposals whose status is `approved`.

### 10. Improvement executor (approval-gated application)

**REQ-LIBRARY-059** — The executor's instructions MUST declare: it executes approved proposals only; never resumes, reopens, or reinterprets the original user task; never proposes new improvements; makes the minimal change needed for each proposal; skips unsafe or ambiguous proposals with a stated reason; never expands scope; summarizes applied versus skipped work; and must not trigger another improvement run from its own output.

**REQ-LIBRARY-060** — An improvement run's work plan MUST be derived from the artifact's `approved` proposals and from nothing else. It MUST consist of a single phase named `improvement_run` holding one task per approved proposal whose category is not `verifier_gate_update`. When the artifact holds no approved proposal, building the plan MUST fail with an error stating that an improvement run cannot start without at least one explicitly approved proposal, and no run starts. When every approved proposal is a `verifier_gate_update`, the plan MUST contain no phases at all; those proposals are applied by the product itself (REQ-LIBRARY-063).

**REQ-LIBRARY-061** — Each generated task MUST embed, in its payload: `Proposal: <id> (<category>)`, `Risk: <level>`, `Summary:`, `Recommended action:`, optional `Target persona:`, and an `Evidence:` list of `- [<kind>] <text>` lines. The task name is `Apply improvement <id>: <first 60 characters of summary>`.

**REQ-LIBRARY-062** — `persona_memory_update` tasks MUST additionally name the workspace-relative file `.rotaris/persona_memory/<persona>.md` in the task payload and instruct the executor to append to or update that file while keeping it inside the 200-line cap.

**REQ-LIBRARY-063** — An approved `verifier_gate_update` MUST never become agent work. The product itself MUST write the proposal's `proposed_verifier_section` into the workspace's gate configuration through the same write path and the same validation as any other gate-configuration change, and MUST require no authorisation beyond the recorded human approval of that exact block. Each gate proposal handled this way MUST be reported as one line reading `<proposal_id>: <outcome>`. The permitted `<outcome>` values are not fixed by this document — see Open Questions.

**REQ-LIBRARY-064** — Preparing an improvement run MUST: load the artifact, filter to approved proposals, build the todo, apply gate proposals, and — as the last step before the run edits the workspace — record the pre-run rollback checkpoint (skippable for dry runs). Rejected proposals MUST never leak into the run payload. A workspace that is not a Git working tree still prepares the run and simply gets no rollback point.

**REQ-LIBRARY-065** — Completing an improvement run records a post-run `applied` checkpoint. This is the reference point a later rollback compares against to tell which changes the run itself produced from which changes the user produced after it. If recording it is skipped, only that distinction is lost; the pre-run point remains usable and rollback still works.

**REQ-LIBRARY-066** — End-to-end acceptance: a completed task run causes exactly one analyst invocation; the resulting artifact's proposals all start `pending_review`; user decisions survive reload; run preparation yields only approved proposals; and the resulting improvement run performs no second analysis pass.

### 11. Rollback of an applied improvement run

**REQ-LIBRARY-067** — Improvement checkpoints MUST live under the dedicated Git ref namespace `refs/rotaris/improvements/<artifact_id>/<sequence>`, disjoint from the session-checkpoint namespace (`refs/rotaris/checkpoints/...`), so that neither feature's pruning can delete the other's refs.

**REQ-LIBRARY-068** — Checkpoint kinds MUST be `pre_improvement` (the state a rollback restores), `applied` (the state the run left, used to measure later user changes), and `pre_rollback` (safety point so an undo of the undo works). Each checkpoint record carries: `sequence` (≥ 0), `ref`, `commit`, `kind`, `created_at`, `files` (paths changed, display only), `proposal_ids` (proposals the guarded run was about to apply), and `tree_root` (the Git top-level it was taken against, enabling cross-worktree refusal).

**REQ-LIBRARY-069** — A workspace with nothing uncommitted MUST still receive a rollback point: the checkpoint records the state the tree is currently in, is registered under the artifact's own ref (REQ-LIBRARY-067), and a later rollback restores that state. The one case in which no checkpoint is produced is a repository holding neither a commit nor any file to record. That case MUST NOT be treated as an error and MUST be reported as the reason `The workspace has no committed content and no files to record, so no rollback point could be taken.`

**REQ-LIBRARY-070** — Before an improvement run edits the workspace, the artifact MUST hold exactly one usable rollback point. When it already holds a `pre_improvement` checkpoint that no rollback has consumed — that is, while `rolled_back_at` is null — that checkpoint MUST be kept and reused rather than superseded; a second attempt after a partly failed run therefore restores the state that existed before the first attempt. Once `rolled_back_at` is set, the next run MUST take a fresh checkpoint. A workspace outside a Git working tree MUST NOT block or fail the run: the run proceeds and its outcome carries the reason `<tree> is not inside a Git working tree, so no rollback point could be taken for this improvement run.`

**REQ-LIBRARY-071** — An artifact retains at most 10 checkpoints by default. A retained checkpoint MUST stay restorable for as long as it is retained, whatever happens to branches, resets, or repository housekeeping in the meantime; only retention pruning may remove one. When the limit is exceeded, the oldest checkpoints MUST be dropped first and their refs deleted with them, except that the newest `pre_improvement` checkpoint is never dropped, so an artifact cannot lose its rollback point to pruning. Sequence numbers MUST be unique within an artifact and MUST never be re-issued: a new checkpoint MUST NOT take a number already used by any ref under `refs/rotaris/improvements/<artifact_id>/`, even when the artifact file itself records no checkpoint at that number. Which configuration key, if any, sets the limit is not stated in this document — see Open Questions.

**REQ-LIBRARY-072** — Asking what a rollback would do MUST have no side effects: it MUST NOT touch the working tree, MUST NOT write to the store, and MUST NOT raise. Every refusal comes back as a finished sentence ready to display, and those sentences MUST be: `No improvement artifact <id> exists in this workspace.` when the artifact is unknown; `No rollback point was recorded for improvement <id>.`, or the non-Git reason of REQ-LIBRARY-070, when there is no usable point; `That rollback point was taken in <A>, not in <B>. Restoring it here would overwrite a working tree it never described.` when the recorded tree differs from the current one; `Improvement <id> has a recorded rollback point but its Git snapshot is gone, so it can no longer be rolled back.` when the recorded snapshot no longer resolves; and a sentence describing a failed repository inspection. A preview that succeeds MUST report every path that differs between the working tree and the rollback point, each labelled with what the rollback would do to that path stated from the user's side — a path the run created is labelled `delete` — together with the paths carrying work done since the run (REQ-LIBRARY-073) and the dirty-blocked reason when one applies. The complete label vocabulary and the wording of the inspection-failure sentence are not fixed by this document — see Open Questions.

**REQ-LIBRARY-073** — Work done after an improvement run MUST be measured against the newest checkpoint that still resolves and whose `kind` is `applied` or `pre_rollback`. Neither the current HEAD nor the pre-run checkpoint may serve as that baseline: an edit the run itself made MUST NOT be reported as work done since the run. When the artifact has no resolvable post-run checkpoint, the rollback MUST report nothing at risk and MUST NOT block on that ground, and a working tree identical to the newest post-run checkpoint MUST likewise report nothing at risk. Whether the search over recorded checkpoints is bounded is unresolved — see Open Questions.

**REQ-LIBRARY-074** — The dirty refusal message MUST read: `<N> change(s) made since the improvement run would be overwritten: <first 5 paths>[ and <n> more]. Roll back again with force to overwrite them.` A force flag bypasses only this one check and nothing else.

**REQ-LIBRARY-075** — Rollback MUST proceed in this order: load → point present → tree match → ref resolves → diff and dirty check → record a `pre_rollback` safety checkpoint first (failure here blocks with "Could not record a safety checkpoint before the rollback: <reason>" — an irreversible rollback is forbidden) → restore the tree → set the applied proposals back to `pending_review` and stamp `rolled_back_at`. Rollback never raises; every refusal returns a not-restored result with a blocked reason and an untouched tree.

**REQ-LIBRARY-076** — Post-restore status reversal MUST cover only proposals named in the checkpoint's `proposal_ids` that are currently `approved`; an older checkpoint with no recorded ids falls back to reverting every still-approved proposal. If persisting the reversal fails after the tree is restored, the result reports restored-with-warning: "The workspace was rolled back, but the reversal could not be recorded on improvement <id>: <err>. Its proposals still read as approved even though their changes are gone."

**REQ-LIBRARY-077** — After a restore, every path the checkpoint covers MUST hold the content that checkpoint recorded: a path the run created is gone, a path the run deleted is present again with its original content, and a path the run modified reads as it did before the run. The rollback MUST itself be undoable from the `pre_rollback` safety checkpoint of REQ-LIBRARY-075. Restoration goes through the repository, so the repository's own line-ending normalisation applies to restored files exactly as it does to session-checkpoint restores. Whether the recorded content is therefore restored byte-for-byte or subject to that normalisation is unresolved — see Open Questions.

**REQ-LIBRARY-078** — The tree-mismatch comparison MUST compare fully resolved paths, case-insensitively on Windows.

### 12. CLI (`improvements` command group)

**REQ-LIBRARY-079** — The CLI MUST expose a command group named `improvements` with help text "Inspect improvement artifacts and roll back an applied improvement run.", visible in the top-level CLI help. Every subcommand accepts `--workspace`/`-w`, defaulting to the resolved current directory.

**REQ-LIBRARY-080** — Every `improvements` subcommand MUST exit `0` when it completed the action it describes, including a rollback the user declined at the confirmation prompt, which leaves the workspace untouched; `1` when a rollback was refused or failed, with the reason written to stderr; and `2` when the named artifact does not exist in the workspace, or when a rollback was invoked without `--yes` on a stdin that cannot answer a prompt.

**REQ-LIBRARY-081** — `improvements list` MUST print the workspace's artifacts newest first by `generated_at`, under the header `ARTIFACT  GENERATED  ROLLBACK  PROPOSALS`, the first three columns padded to widths 18, 25, and 8 and the last column unpadded. Each row gives the artifact id; its `generated_at` as an ISO 8601 timestamp truncated to whole seconds; `yes` when the artifact has a rollback point per REQ-LIBRARY-012 and `no` when it has none; and its proposal counts as `<status>=<count>` pairs separated by single spaces, in the status order declared in REQ-LIBRARY-007 (`pending_review`, `approved`, `rejected`, `deferred`), omitting any status whose count is zero and printing `none` when the artifact holds no proposals at all. A workspace with no artifacts MUST print `No improvement artifacts exist in <workspace>.` to stderr and exit 0.

**REQ-LIBRARY-082** — `improvements show <artifact-id>` MUST print `Artifact <id>`, then indented lines `generated` (the artifact's `generated_at` as an ISO 8601 timestamp truncated to whole seconds), `session` (its `source_session_id`), `proposals` (the status counts defined in REQ-LIBRARY-081) and `rollback` — the last reading `no rollback point recorded` when the artifact has no rollback point and otherwise `<ref> (<commit>)` with the commit abbreviated to 12 characters — followed, only when `rolled_back_at` is set, by `rolled back <timestamp>`. It MUST then print the artifact's proposals in stored order under the header `PROPOSAL  STATUS  RISK  SUMMARY`, the first three columns padded to widths 14, 15, and 7, and then `History:` followed by the artifact's recorded versions newest first under the header `VER  RECORDED  CAUSE`, the version right-aligned in a width of 4. Every artifact has at least one recorded version (REQ-LIBRARY-051), so the history section is never empty. An artifact id absent from the workspace MUST print `No improvement artifact <id> exists in <workspace>.` to stderr and exit 2.

**REQ-LIBRARY-083** — `improvements rollback <artifact-id> [--force] [--yes/-y]` MUST print the preview before doing anything else. When the rollback would change files it prints `Rolling back improvement <id> would change <N> file(s):` followed by one line per path, `  <action> <path>`, the action padded to 9 characters, the lines in ascending path order, and the action stated from the user's side per REQ-LIBRARY-072. When it would change nothing it prints `Rolling back improvement <id> would change nothing.` instead. When work exists that the rollback would overwrite it additionally prints `Warning: <N> change(s) made since the improvement run would be overwritten:` followed by those paths. If the rollback is blocked and `--force` was not supplied, the blocking reason MUST go to stderr and the command MUST exit 1 with the workspace untouched.

**REQ-LIBRARY-084** — Rollback confirmation MUST behave as follows: without `--yes` on a non-interactive stdin, refuse with `Error: a non-interactive rollback requires --yes.` and exit 2 — never hang waiting on a pipe. Interactively, ask `Roll back improvement <id> in <tree>? [y/N]`, accepting only `y`/`yes` case-insensitively; a decline prints `Rollback cancelled.` and exits 0 with the workspace untouched.

**REQ-LIBRARY-085** — Successful rollback output MUST be: `Rolled back improvement <id>; <N> file(s) changed.`, then optionally `<N> proposal(s) returned to pending_review: <ids>`, then `Safety checkpoint <seq> holds the pre-rollback state.` A post-restore bookkeeping warning goes to stderr without changing the exit code (the tree is already restored).

**REQ-LIBRARY-086** — The line formats of REQ-LIBRARY-081, REQ-LIBRARY-082, and REQ-LIBRARY-083 are the output contract of the `improvements` command group, and the CLI MUST emit exactly those lines rather than variants of them. They do not bind the other surfaces: the desktop Library and dashboard (REQ-LIBRARY-109, REQ-LIBRARY-129) and the terminal-UI review screen (REQ-LIBRARY-145) render the same underlying state in the formats this document specifies for them. What is required across surfaces is agreement about the state itself (REQ-LIBRARY-164), not identical text.

### 13. Session artifact store (agent reports and published deliverables)

**REQ-LIBRARY-087** — The per-session artifact store MUST live under `<session_dir>/artifacts/`: one `<id>.json` full record per artifact, one Markdown sidecar `<id>.md`, and an `index.json` of metadata entries sorted by creation time. All writes are atomic, mutations are serialized within the process, and the store outlives loop iterations so earlier-phase findings remain available to later children.

**REQ-LIBRARY-088** — An artifact record MUST carry: `id`, formed as `art_` followed by 8 base62 characters; `slug`, kebab-case, at most 64 characters, made unique within the session by appending `-2`, `-3`, and so on; `title`; `kind`, one of `child_report`, `agent_published`, `system`; `source_task_id`; `canonical_name`; `source_persona`; `status`, which is `succeeded` unless set otherwise, `published` for an agent publish, and the report's own status for a materialised child report; `summary`; `key_findings`; `highlight_paths[]`; `snippets[]`; `edited_files[]`; `created_files[]`; `tags[]`; `supersedes` and `superseded_by`; `created_by`; `consumed_by[]`; the ids linking the record to its timeline entry and to its conversation; `importance`, which MUST be `high` when the record is a child report whose status is anything other than `succeeded` and `normal` in every other case; `created_at`; `edited_at`, null until a person edits the body; and `body_markdown`. The names of the timeline and conversation link fields, and the closed set of values `status` may take, are not fixed by this document — see Open Questions.

**REQ-LIBRARY-089** — Artifact tags MUST come from a closed vocabulary of exactly six values: `research`, `planning`, `implementation`, `review`, `verification`, `errors`. A publish carrying any other tag MUST be refused whole — no record is created, no file is written, and no partial state is left behind — with an error that begins `Invalid tag(s): `, names the rejected tags, and continues `Valid tags are: ` followed by the six permitted values in the order given here. Whether a tag is matched exactly as supplied or after normalisation is not fixed by this document — see Open Questions.

**REQ-LIBRARY-090** — Each artifact MUST have a Markdown sidecar that opens with YAML frontmatter carrying `id`, `slug`, `title` (JSON-quoted), `kind`, `status`, the record's timestamps, and — only when the record has them — its source ids, its tags, and its supersession links. The frontmatter is followed by `# <title>` and then by these sections in this order: Summary; Key Findings; Highlight Paths, one line per path formatted `` - `path` — reason ``; Snippets, one fenced code block per path; Edited Files, one line per file formatted `` - `path` (change_type) ``; Created Files. Whether a section with no content is omitted or emitted with an empty body is not stated in this document — see Open Questions.

**REQ-LIBRARY-091** — Store hydration MUST tolerate: a missing directory or index (zero artifacts), a corrupt index (warning, zero artifacts), index entries whose JSON file is missing (warning, skipped), and per-record validation failures (skipped). Hydration never raises.

**REQ-LIBRARY-092** — Materializing a child report MUST be idempotent keyed on the task id (falling back to the canonical agent name): a re-materialization updates in place, preserving id, slug, title, creation time, supersession links, consumers, and edit timestamp, instead of duplicating. Every terminal child report is materialized (kind `child_report`), and a timeline diagnostic event of kind `artifact_published` is recorded with the artifact id linked back onto the record.

**REQ-LIBRARY-093** — Publishing MUST create a record whose `kind` is `agent_published` and whose `status` is `published`, whose `body_markdown` is the submitted body unchanged, whose `key_findings` is that same body, and whose `summary` is the body's first line truncated to at most 280 characters. `created_by` MUST name the publishing agent instance by its canonical name rather than by its persona, so two instances sharing a persona stay distinguishable in every artifact listing. A publish that names a supersedes target by id or by slug MUST mark that target superseded by the new record and MUST record the reverse link on the new record (REQ-LIBRARY-095).

**REQ-LIBRARY-094** — Body editing MUST overwrite only the Markdown body and stamp `edited_at`; everything else on the record — its slug, its title, its tags, its snippets, and its source ids — stays immutable through every editing surface. An unknown reference fails with `Unknown artifact: '<ref>'`.

**REQ-LIBRARY-095** — Supersession MUST link both directions, re-render both sidecars, and refuse self-supersession (`An artifact cannot supersede itself`) and unknown ids.

**REQ-LIBRARY-096** — Listing MUST hide superseded artifacts by default, require ALL given tags when tags are supplied, and sort ascending by creation time; lookup accepts id or slug; marking an artifact consumed appends the actor at most once and persists.

**REQ-LIBRARY-097** — A newly created agent MUST be given a `PRIOR SIBLING ARTIFACT INDEX` context block listing the session's existing artifacts, one artifact per line, each line carrying that artifact's slug, id, persona, status, and its summary truncated to at most 160 characters. The block MUST NOT exceed 10,000 characters; when not every artifact fits, the block MUST end with a marker stating how many were left out and naming the `artifact_list` tool as the way to reach them. Artifacts whose status is `failed`, `blocked`, or `partial` MUST be ordered ahead of artifacts whose status is `succeeded`, so a failure is never the entry elided while a success survives. The ordering within those two groups and the wording of the elision marker are not fixed by this document — see Open Questions.

**REQ-LIBRARY-098** — Explicitly attached artifacts MUST be injected as a `PRIOR AGENT CONTEXT (FULL)` block within a 48,000-character budget, reporting unresolvable references and elided ids; both injection paths record a context-selection diagnostic.

**REQ-LIBRARY-099** — The agent-facing `artifact_read(id_or_slug, sections=[])` tool MUST return the full Markdown body by default, or a filtered view of sections from {`summary`, `key_findings`, `snippets`, `highlights`, `files`}; a miss returns the error observation `Artifact not found: <ref>`; every successful read marks the reading persona as a consumer.

**REQ-LIBRARY-100** — The agent-facing `artifact_list` tool MUST accept kind, persona, tags, `limit` (default 20, range 1..200), and an include-superseded flag, and return `<N> artifact(s):` plus one line per record formatted `- <id> [<slug>] persona=<p> status=<s> tags=[…] — <title>`, or `No artifacts found.` when empty.

**REQ-LIBRARY-101** — The agent-facing `artifact_write(slug, title, body, tags=[], supersedes=None)` tool MUST publish and reply `Published artifact <id> (slug: <slug>).`, validate tags per REQ-LIBRARY-089, and associate the produced artifact with the publishing agent in the session's delegation graph when one exists.

### 16. Desktop background improvement analysis

**REQ-LIBRARY-122** — The desktop contract for background analysis is as follows. The completed run's terminal state MUST already be written to disk and visible on screen before any analysis begins, and the analysis itself MUST run off the UI thread. Throughout, the user can keep typing in the composer and can start new runs. The only progress signal is a pulsing activity indicator — announced to assistive technology and labelled "Reviewing run for improvements…" — placed both in the application title bar and in the workspace run header; the finished run's own status is left alone, and there is no modal, no percentage readout, and no cancel control. When the analysis ends, both indicators disappear, the proposal library is re-read, and a persistent notice is posted. Quitting the application cancels the analysis that is running and any that are queued, discards the artifacts they would have written, withholds their completion notices, and MUST NOT hand the work to a durable out-of-process service that would outlive the application.

**REQ-LIBRARY-123** — Analyses MUST be performed one at a time and in the order in which the runs that produced them finished, so their artifacts and their completion notices appear in that same order and never interleave. A run's terminal state MUST already be readable from its session state on disk before that run's analysis begins, so an analysis interrupted part-way can never leave the run itself looking unfinished. A job captured while the application is shutting down MUST be cancelled rather than started, producing no artifact and no notice (REQ-LIBRARY-127).

**REQ-LIBRARY-124** — On job completion: a result carrying an artifact id causes the proposal list to be re-read. A non-cancelled result with one or more proposals publishes a persistent success notice titled `<N> improvement proposal ready` / `<N> improvement proposals ready` (singular/plural) with action label "Review proposals" that opens the Library on the proposals tab; a result with zero proposals publishes an info notice "Improvement analysis complete — no proposals" with no action; a cancelled or artifact-less result publishes nothing. A worker failure produces no user-visible signal (see Open Questions).

**REQ-LIBRARY-125** — While analysis is running, two activity indicators MUST be visible: one in the application title bar and one in the workspace run header. Both MUST carry the label "Reviewing run for improvements…". The title-bar indicator MUST expose the accessible name "Improvement analysis status" and the accessible description "Reviewing the completed run for improvements in the background. You can continue working."; the run-header indicator MUST expose an accessible description of the same activity, whose exact text this document does not fix — see Open Questions. Both MUST be present only while analysis is active and MUST be gone once it ends. Neither may change the completed run's own status chip, and no control — the send button included — may be disabled while analysis runs. The indicators' size, colour, and animation are presentation choices this document does not fix — see Open Questions.

**REQ-LIBRARY-126** — With several sessions running at once, the indicators of REQ-LIBRARY-125 MUST be visible whenever at least one session's analysis is in progress and hidden only when none is. One session's analysis finishing MUST NOT hide them while another session's analysis is still running. Once the application is shutting down they MUST be hidden regardless of what any session last reported (REQ-LIBRARY-127).

**REQ-LIBRARY-127** — Shutting the application down MUST leave nothing of analysis behind: a job that had not yet started MUST NOT start, an analysis in progress MUST be cancelled so that no artifact is written for it, no completion notice may be posted for any cancelled job, and the activity indicators MUST end hidden. No analysis may continue past the process's exit, and none may be handed to anything that outlives it (REQ-LIBRARY-122). Whether shutdown may wait for an in-flight provider call to return before the process exits, and whether any bound applies to that wait, is unresolved — see Open Questions (REQ-LIBRARY-024).

Opening an artifact from the Library requires it to belong to the loaded session, otherwise "Artifact not found in the loaded session." Superseded artifacts are hidden from the Library table. Each row exposes id, slug, title, kind, status, persona, producer (canonical instance or creator), summary, relative created label, and edited flag; "ready" means status ∈ {`succeeded`, `published`}.

### 19. Prompt stash and prompt history

**REQ-LIBRARY-137** — Prompt history MUST front-insert each sent or queued prompt, suppressing only adjacent duplicates (a new entry equal to the current front item is not added). The stash front-inserts non-empty text. Popping a stash entry removes and returns it by index; an out-of-range index returns an empty string without error. Every mutation triggers the library-changed refresh-and-persist cycle.

**REQ-LIBRARY-138** — Saved prompts MUST persist in a single JSON file `<workspace>/.rotaris/rotaris-prompts.json` shaped `{"history": [...], "stash": [...]}`, written with 2-space indentation, a trailing newline, flushed to disk, and replaced atomically (temporary file prefix `.rotaris-prompts-`). The file is saved on every library change. A save failure surfaces a persistent desktop error notice "Could not save prompt history" with detail "Rotaris will keep prompts in memory for this window."

**REQ-LIBRARY-139** — History is capped at 200 entries and the stash at 100, enforced on both load and save with silent truncation of the oldest entries. A missing, corrupt, or wrongly typed file loads as empty state; loaded entries are stringified and blank entries removed. (Whether these are the intended limits is asked in Open Questions.)

**REQ-LIBRARY-140** — The workspace composer MUST show a ghost "Stash" button ("Stash prompt for later") that stashes the current composer text, and the transcript toolbar a ghost "Apply stash (<count>)" button (accessible name "Manage prompt stash", tooltip "Apply or pop a stashed prompt") whose count updates live.

**REQ-LIBRARY-141** — The stash dialog MUST be titled "Prompt stash", minimum 560×360, with the intro "Apply copies the selected prompt into the composer and keeps it in the stash. Pop copies it and removes it from the stash.", the first row pre-selected, and buttons Close / secondary "Apply" / primary "Pop". Apply copies without removing; Pop removes and copies. The empty state shows a disabled list with "No stashed prompts. Use Stash beside the composer first." and disabled Apply/Pop.

**REQ-LIBRARY-142** — Two slash commands MUST mirror the stash controls. `/stash`, described as "Stash the composer prompt", stashes the composer's current text exactly as the composer's Stash button does (REQ-LIBRARY-140). `/pop`, described as "Apply a stashed prompt", opens the prompt stash dialog (REQ-LIBRARY-141); the command itself removes nothing, and the user's choice of Apply or Pop inside that dialog decides whether the entry stays in the stash. The slash catalogue MUST be rebuilt whenever the library changes, so both commands always reflect the current stash. Text beginning with a slash command is ordinary prompt text as far as prompt history is concerned and MUST be recorded there like any other sent prompt (REQ-LIBRARY-137); whether that squares with REQ-LIBRARY-137's rule of recording sent and queued prompts, given that a slash command is handled locally and never sent, is unresolved — see Open Questions.

**REQ-LIBRARY-143** — Demo mode MUST present read-only sample library content (sample prompt history and stash entries, sample artifacts, and sample proposals) with every mutating action refused per REQ-LIBRARY-119. (The seed content itself is not fixed here — see Open Questions.)

### 20. Terminal-UI surfaces

**REQ-LIBRARY-144** — The terminal UI's proposal review screen is modal and reviews a single artifact. Its header reads `Improvement proposals (session <sid>, artifact <aid>) — a:approve  r:reject  d:defer  p:pending  s:start  esc:close`, and the key bindings are exactly: `a` approve, `r` reject, `d` defer, `p` reset to pending, `s` start improvement run, `escape` close. An artifact with no proposals renders "No proposals in this artifact." and no table.

**REQ-LIBRARY-145** — The screen's table has columns Status/Category/Summary with row-cursor selection keyed by proposal id and status labels rendering `pending_review` as `pending` (others verbatim); the table takes focus when non-empty. Status changes persist through the same on-disk review API the desktop uses, update the visible cell in place, and notify `Proposal <id> marked <label>.`

**REQ-LIBRARY-146** — Conflict handling: a proposal that vanished due to an external edit causes the artifact to reload from disk with the warning `Proposal <id> no longer exists.`; a persistence I/O failure notifies the error `Failed to persist approval: <err>`.

**REQ-LIBRARY-147** — Starting an improvement run from the review screen MUST depend on what is approved and on whether this surface can start a run at all. With no approved proposal, warn "No proposals approved — nothing to do." and start nothing, leaving the screen open. With at least one approved proposal but no way to start a run from here, notify `Approved <N> proposal(s). Run the Improver via the CLI to apply them.` and close the screen, the decisions already being on disk. With a way to start a run, a failure notifies `Failed to start improvement run: <exc>` and leaves the screen open, and success notifies `Started improvement run with <N> proposal(s).` and closes it. **REQ-LIBRARY-148** — Entry points MUST include a command-palette entry "Improvement Proposals" (description "Review post-run improvement proposals"), a palette cheatsheet entry, and the slash command `/improvements`; invoking any of them opens the latest workspace artifact. With no active session, warn "No active session — start a run first."; with no artifacts, inform "No improvement artifacts yet — finish a task run first."; listing or loading errors notify `Could not list improvement artifacts: <err>` / `Could not load improvement artifact: <err>`.

**REQ-LIBRARY-149** — Proposals MUST always be reachable in the terminal UI through the palette entry and the slash command of REQ-LIBRARY-148, whether or not any notification announced them, so no proposal can become unreachable because a notification was missed, dismissed, or never shown. Whether the terminal UI also announces new proposals proactively is not settled here — see Open Questions.

### 21. Persona memory

**REQ-LIBRARY-150** — Persona memory MUST be stored as one Markdown file per persona at `<workspace>/.rotaris/persona_memory/<persona>.md` — deliberately visible, inspectable, and hand-editable. Persona names MUST match `^[A-Za-z0-9_.\-]+$`; anything else is rejected with `Invalid persona name for persona memory: … (allowed: alphanumerics, underscore, dot, dash).`, preventing directory escape.

**REQ-LIBRARY-151** — Persona memory MUST be bounded to 200 lines, enforced on both read and write. On read, the file on disk is never modified (direct user edits stay the source of truth; only the injected context is protected); on write, content is truncated before persisting, newline-terminated, and written atomically. Truncation is logged.

**REQ-LIBRARY-152** — Loading persona memory MUST return "no memory" for a missing, unreadable, or blank file; otherwise the (possibly truncated) content.

**REQ-LIBRARY-153** — Memory is injected only at agent-creation time, as a context block named `persona_memory_<persona>`; an agent is given the file belonging to the persona it is being created as, and never another persona's file. Manual edits are picked up on the next persona load.

**REQ-LIBRARY-154** — A primary task run MUST never write persona memory. Mutation happens only via the approval-gated executor (directed at the file path per REQ-LIBRARY-062) or by direct manual edits.

**REQ-LIBRARY-155** — End-to-end acceptance: a task run yields a `persona_memory_update` proposal targeting one persona; nothing is on disk before approval; after approval and execution the memory file exists; a later load returns it for the target persona only, while unrelated personas still get no memory.

### 22. Ordering, timing, and concurrency

**REQ-LIBRARY-156** — For a completed desktop run the observable ordering MUST be: terminal session state persisted → analysis job captured (evidence snapshotted) → queued to the background worker → analyst runs (within its timeout) → artifact saved with duplicate suppression → proposals re-read into the UI → notice published. The user may start follow-up work at any point after the first step.

**REQ-LIBRARY-157** — Analysis activity MUST be published as its own independent flag that never alters the run state or session status fields.

**REQ-LIBRARY-158** — Within one process, session-artifact-store mutations are serialized and the record and index are persisted together; across processes, safety for both the session artifact store and the improvement artifact store is limited to atomic whole-file replacement — there is no file locking, and external-edit conflicts are detected only opportunistically (e.g. the terminal UI's reload-on-vanished-proposal path). (Multi-process conflict outcomes are unresolved — see Open Questions.)

### 23. Cross-cutting invariants

**REQ-LIBRARY-159** — No proposal with an empty `evidence` list may exist anywhere: construction MUST fail (REQ-LIBRARY-009), storing one MUST fail validation (REQ-LIBRARY-014, REQ-LIBRARY-047), and a proposal returned without evidence MUST NOT be repaired into existence by supplying evidence on its behalf. The `verifier_gate_state` entry the product stamps onto a gate proposal (REQ-LIBRARY-029) is not such a repair: it is added to a proposal that already carries at least one analyst-authored entry, and it MUST NOT be the only entry that proposal holds. Reading every artifact file in a workspace MUST therefore find, on every proposal, at least one evidence entry, and at least one whose `kind` is not `verifier_gate_state`.

**REQ-LIBRARY-160** — A task run MUST NOT change the workspace as a consequence of its analysis. Across a completed task run, the only paths analysis may create or modify are the artifact and its history under `.rotaris/improvement_artifacts/`; every other path — configuration files, personas, persona memory, gate configuration, and all the rest — MUST hold the same content afterwards as before, and no path outside that directory may be created or deleted. A change a proposal describes takes effect only once that proposal's status is `approved` and a run of type `improvement_run` applies it; a `verifier_gate_update` takes effect only through the deterministic writer of REQ-LIBRARY-063, from the complete block already inside the proposal, and never through an agent.

**REQ-LIBRARY-161** — No analysis failure may show up in the task run itself. For every failure mode — the pass cannot be constructed, the model call raises, the output fails to parse twice, the timeout elapses, or the artifact cannot be written — the run's terminal state, its recorded result, and the moment that result is reported MUST match what the same run would have produced with `runtime.improvement_collector_enabled` set to false; in particular the result reaches the host before any analysis work begins (REQ-LIBRARY-004). The worst outcome a user may observe is an artifact holding no proposals whose `notes` names the failure, or no artifact at all.

**REQ-LIBRARY-162** — Every mutation of an artifact — a status change, an edit, a deletion, a recorded checkpoint, and a rollback — MUST go through the write path of REQ-LIBRARY-047 and MUST leave behind a recorded version naming its cause from the vocabulary of REQ-LIBRARY-050. For as long as those versions survive retention (REQ-LIBRARY-052), the exact `summary` and `recommended_action` a proposal carried at each recorded decision point MUST be readable back from history, and pruning MUST give up intermediate versions before it gives up either version 1 or the newest version.

**REQ-LIBRARY-163** — A rollback MUST never leave the workspace in a state the user cannot get back out of. It MUST refuse to proceed when a `pre_rollback` safety checkpoint cannot be recorded first, when the working tree holds work done since the run and `--force` was not given, and when the recorded checkpoint belongs to a different working tree than the one being restored. Every refusal MUST leave both the working tree and the artifact file exactly as they were and MUST come back as a displayable reason rather than a failure the caller has to handle (REQ-LIBRARY-072, REQ-LIBRARY-075). When a rollback does proceed, every proposal it undid MUST return to `pending_review`, so no proposal reads as `approved` while its changes are gone; when that update cannot be persisted, the discrepancy MUST be reported to the user (REQ-LIBRARY-076) rather than passed over. A workspace with no Git repository MUST lose only the rollback capability: analysis, review, and application all continue to work.

**REQ-LIBRARY-164** — The desktop Library, the dashboard card, the terminal-UI review screen, and the CLI MUST all read and write the same artifact files under `.rotaris/improvement_artifacts/`, with the same review semantics. A decision recorded on any one of them MUST be the state each of the others reports at its next refresh — the Library's update cycle (REQ-LIBRARY-105), the dashboard card's live update (REQ-LIBRARY-130), the review screen's reload (REQ-LIBRARY-146), and any fresh CLI invocation — and no surface may hold a private copy that can disagree with the files. How each surface presents that state remains its own (REQ-LIBRARY-086).

## Data & Formats

### Improvement artifact file

- Location: `<workspace>/.rotaris/improvement_artifacts/<artifact_id>.json`, JSON, 2-space indent, atomic replace.
- Top level: `artifact_id` (`impart_` + 8 base62), `source_session_id` (input alias `session_id` accepted), `source_run_type` (`task_run` | `improvement_run` | `integration_run`), `generated_at` (UTC ISO), `collector_model` (string | null), `proposals[]`, `considered_session_ids[]`, `notes` (string | null), `checkpoints[]`, `rolled_back_at` (UTC ISO | null).
- Proposal: `id` (`imp_` + 8 base62), `category` (10-value vocabulary), `summary`, `evidence[]` (≥ 1), `recommended_action`, `risk` (`low`|`medium`|`high`), `status` (`pending_review`|`approved`|`rejected`|`deferred`), `target_persona` (string | null), `proposed_verifier_section` (mapping | null), `created_at`.
- Evidence: `kind`, `text`, `source_task_id`/`source_artifact_id`/`source_session_id` (nullable), `excerpt` (optional).
- Checkpoint record: `sequence`, `ref`, `commit`, `kind` (`pre_improvement`|`applied`|`pre_rollback`), `created_at`, `files[]`, `proposal_ids[]`, `tree_root`.

### Artifact history files

`<workspace>/.rotaris/improvement_artifacts/history/<artifact_id>/<version>.json` — version zero-padded to 6 digits; contents `{version, recorded_at, cause, artifact}` with cause ∈ {`collected`, `status_change`, `edit`, `delete`, `checkpoint`, `rollback`, `unknown`}. Retention 25 versions per artifact (version 1 protected while keep ≥ 2).

### Git ref namespaces

Improvement checkpoints: `refs/rotaris/improvements/<artifact_id>/<sequence>`. Session checkpoints (adjacent domain): `refs/rotaris/checkpoints/...`. The namespaces are disjoint and pruned independently. Checkpoint retention: 10 per artifact, newest `pre_improvement` exempt.

### Gate evidence mapping

JSON-serializable record carrying: gate state; configuration fingerprint; where the check suite was obtained and how it was declared; one entry per configured check (name, command, verification role, severity, working directory); probe results; per-check outcomes; and optionally the checks that could not be run and the verification roles left uncovered (serialized key names not fixed — see Open Questions). Rendered text lines: one line starting `gate state: `, one line per check starting `check <name> [<role>/<severity>]`, one line per probe and per outcome, one sentence for checks that never ran and one for uncovered roles; empty string when there is no state. Stamped gate evidence entry: `kind` = `verifier_gate_state`, text `gate state <state> at fingerprint <12 chars>` (`unknown` substituted for a missing state or fingerprint), `excerpt` = the dedupe key — 16 lowercase hex characters digesting the proposed block together with the gate state, fingerprint, unrunnable checks, and uncovered roles.

### Analyst I/O

Input: the six frozen snapshots of REQ-LIBRARY-017 — run progress, todo state, child reports, gate evidence, transcript summary, recent workspace improvement history — with an unavailable source kept distinguishable from an empty one (REQ-LIBRARY-019) and at most 5 prior artifacts of history (REQ-LIBRARY-034). Volume is bounded and elisions are marked with `…`; the bound values are not fixed here (REQ-LIBRARY-018, Open Questions). Accepted model reply: a single JSON object carrying a `proposals` list and optional `notes` (an enclosing Markdown fence is tolerated and stripped).

### Session artifact store

Layout: `<session_dir>/artifacts/<id>.json` (full record), `<id>.md` (Markdown sidecar), `index.json` (metadata entries sorted by creation time). Record ids `art_` + 8 base62; slugs kebab-case ≤ 64 chars, uniquified `-2`, `-3`, …; kinds `child_report` | `agent_published` | `system`; tags from {`research`, `planning`, `implementation`, `review`, `verification`, `errors`}. Sidecar: YAML frontmatter (`id`, `slug`, JSON-quoted `title`, `kind`, `status`, optional source ids/tags/supersession links, timestamps), then `# <title>`, then fixed sections: Summary; Key Findings; Highlight Paths; Snippets; Edited Files; Created Files. Timeline diagnostic event kind on materialization/publish: `artifact_published`.

### Injected context blocks

- `PRIOR SIBLING ARTIFACT INDEX` — every artifact rendered on its own single line carrying slug, id, persona, status and a ≤ 160-character summary; 10,000-char budget, unsuccessful statuses ordered ahead of `succeeded` (REQ-LIBRARY-097), elision marker naming the omitted count and the `artifact_list` tool.
- `PRIOR AGENT CONTEXT (FULL)` — full bodies of explicitly attached artifacts, 48,000-char budget, missing references and elided ids reported.
- `persona_memory_<persona>` — the persona's memory file content (≤ 200 lines), injected at agent creation only.

### Saved-prompts file

`<workspace>/.rotaris/rotaris-prompts.json` — `{"history": [<string>...], "stash": [<string>...]}`, 2-space indent, trailing newline, atomic replace (temp prefix `.rotaris-prompts-`), history ≤ 200 entries, stash ≤ 100 entries.

### Persona memory files

`<workspace>/.rotaris/persona_memory/<persona>.md` — plain Markdown, ≤ 200 lines, newline-terminated, atomic writes; persona names constrained to `^[A-Za-z0-9_.\-]+$`.

### Configuration keys

- `runtime.improvement_collector_enabled: bool = true`
- `runtime.improvement_collector_timeout: int = 60` (min 1)
- `improvement_collector_model: string | null = null` (+ independent thinking override), fallback: medium-tier model.

### CLI output formats

- `improvements list`: header `ARTIFACT  GENERATED  ROLLBACK  PROPOSALS` (widths 18/25/8); status counts `pending_review=1 approved=2` in status declaration order, `none` when empty; timestamps second-precision ISO.
- `improvements show`: `Artifact <id>` + indented `generated`/`session`/`proposals`/`rollback` (`<ref> (<12-char commit>)` or `no rollback point recorded`) + optional `rolled back <ts>`; proposal table `PROPOSAL  STATUS  RISK  SUMMARY` (widths 14/15/7); `History:` table `VER  RECORDED  CAUSE` (version right-aligned width 4).
- `improvements rollback`: preview lines per REQ-LIBRARY-083; confirmation `Roll back improvement <id> in <tree>? [y/N]`; success lines per REQ-LIBRARY-085. Exit codes 0/1/2 per REQ-LIBRARY-080.

### Desktop notices and labels

Persistent notices: `<N> improvement proposal(s) ready` (success, action "Review proposals"), "Improvement analysis complete — no proposals" (info), `Proposal marked <status with spaces>` (success, action "Undo"), "Could not save prompt history". Relative time labels: `now` (< 60 s), `<n>m` (< 1 h), `<n>h` (< 24 h), `<n>d` otherwise. Activity label: "Reviewing run for improvements…".
