# Command Sandboxing and Network Egress Policy — Terminal-tool enforcement

Part 3 of 6 of [domain 10](../10-sandbox-network-egress.md), which indexes every part. Defines REQ-SANDBOX-080 – REQ-SANDBOX-126.

### Terminal-tool enforcement

- **REQ-SANDBOX-080** — Every newly submitted terminal command in a session with an active confinement mode is confined, whether it runs in the foreground or is started in the background. A background command is confined on exactly the terms its foreground equivalent would be, so asking for background execution is not a way around the sandbox.
- **REQ-SANDBOX-081** — Confinement is applied only to a NEW command string. Excluded: text directed at an already-running process as its input, because confining it would deliver the wrapper text into that process's input, whereas an interrupt keystroke must arrive unaltered; a command that is empty or only whitespace, which is a request to collect further pending output; a request to list sessions; and a control call that carries only a session identifier. A request carrying BOTH a background flag and a session identifier counts as a new spawn and is confined, so that this documented-invalid combination cannot become a single-field bypass.
- **REQ-SANDBOX-082** — Wrapping is idempotent per issuance: a repeated or retried command is wrapped exactly once; wrappers never nest.
- **REQ-SANDBOX-083** — Wrap-time failure (unavailability, or ANY error raised while wrapping, e.g. a broken platform integration): the command is not executed — nothing reaches the shell or the background registry — and a refusal observation is returned with: `failure_kind` `sandbox_unavailable`, `is_error` true, exit code 126 — the conventional code for a command that exists but could not be run, chosen so that outcome classification cannot mistake a command that never executed for a successful one — outcome kind `sandbox_unavailable` with severity `error`, `error_class` fixed to `SandboxUnavailableError`, and a detail recording that the session requires OS-level confinement, that confinement could not be applied, that the command was consequently not executed, and what the underlying error was. The machine-readable product classification is the stable `failure_kind`/outcome pair. An implementation exception name MAY appear only in optional, redacted diagnostic detail; it MUST NOT change `error_class`.
- **REQ-SANDBOX-084** — Such a failure must not be absorbed by general-purpose error or retry handling: under no circumstances may a confinement failure lead to the command being run without confinement.
- **REQ-SANDBOX-085** — A command whose confining invocation was rendered successfully but failed at startup — the kernel refusing the namespace, for instance — is relabelled `sandbox_unavailable` only when all four of these hold: the command was confined by this call; the exit status is nonzero; no failure kind has been assigned yet, so a command stopped by the hard timeout stays `timeout`; and every non-empty line of the command's captured output begins with a launcher prefix, `bwrap:` for bubblewrap or `sandbox-exec:` or `sandbox_apply:` for Seatbelt. The test covers standard output and standard error together, as one set of captured lines, not standard error alone: its purpose is to establish that the command produced no output of its own, and a line on standard output is exactly such evidence, so a command that wrote an ordinary line to standard output before the launcher failed is NOT relabelled. One non-empty line without such a prefix, on either stream, prevents relabelling, so a program that merely fails inside a working sandbox is never reported as broken confinement; a command that produced no output at all is not relabelled either. The detail states that confinement could not be started, that the command therefore never executed, that the cause lies in the host's configuration rather than in the command, and that neither retrying nor rewording the command changes the outcome. The relabelling applies to a foreground result and equally to the result of polling or terminating a background command, since a background spawn returns before the failure is visible and the failure first shows at the next poll.
- **REQ-SANDBOX-086** — The reported observation shows the command as the agent submitted it, not the confining invocation; showing the latter would obscure the request and encourage the model to alter the confinement machinery instead. Background execution must still be demonstrably confined — polled output reflects the confined execution — while the observation text continues to show the submitted command.
- **REQ-SANDBOX-087** — The terminal tool's model-facing documentation must explain that `failure_kind` `sandbox_unavailable` indicates the command never executed, that the cause is the host's configuration, that neither a retry nor a reformulated command helps, and that the detail and output should be relayed to the user. `sandbox_unavailable` is part of the observation's `failure_kind` vocabulary alongside `timeout`, `invalid_request`, `execution_error`.
- **REQ-SANDBOX-088** — With no sandbox configured, the shell receives exactly the characters the caller submitted, with no probing and no added cost.
- **REQ-SANDBOX-089** — Sandboxing does not change terminal session scheduling: a sandboxed terminal session serializes its commands exactly as an unsandboxed one.

### Session binding and launch

- **REQ-SANDBOX-090** — Configuration that sets no confinement mode means `off`. A confinement-mode value that the session layer cannot recognize is an error and must never be treated as "no confinement": such a value indicates validation did not run, and quietly settling on `off` there would be precisely the kind of unannounced downgrade this specification rules out.
- **REQ-SANDBOX-091** — Confinement is rooted at whichever directory the session genuinely executes in — an isolated worktree while worktree isolation is in use, otherwise the workspace itself — so that the writable area coincides with the location of the files the run works on. The configured additional writable roots and the network opt-in are carried through into that confinement.
- **REQ-SANDBOX-092** — The check performed before a run starts either names the mechanism that will confine it or fails with a reason and remediation; it never returns a "no confinement" result, so a caller that receives a positive answer can rely on the next command actually being confined. Mode `off` is not treated as a failure.
- **REQ-SANDBOX-093** — Confinement status is a pair (active, backend name), where active requires the mode to be both selected AND actually available; selection alone is insufficient. Mode off → (false, ""); selected but unavailable → (false, ""), with the backend name left empty so that no record names a mechanism that never ran; selected and available → (true, name).
- **REQ-SANDBOX-094** — A run whose configuration asks for confinement the host cannot deliver does not start, and starting it without confinement is prohibited. Whatever confinement fact is recorded for a run always agrees with the verdict that governed whether it was allowed to start, so no run is ever recorded as confined while its commands ran unconfined, nor recorded as unconfined while confinement applied.
- **REQ-SANDBOX-095** — On a host that cannot deliver the requested confinement, session start fails and reports the availability reason and remediation of REQ-SANDBOX-071. No usable session, and no shell able to run a command outside confinement, is left behind. This requirement is canonical for the whole domain and agrees with REQ-TOOLS-118: a session requiring confinement the host cannot deliver DOES NOT START. The alternative reading — a session that starts and refuses every command — is rejected: it produces a run that can plan but never act, which serves the user worse than an immediate refusal carrying a reason and a remediation. The `sandbox_unavailable` refusal of REQ-SANDBOX-083 is not thereby unreachable; it remains the outcome whenever wrapping fails at command time on a host where confinement was proved available at start (REQ-SANDBOX-078).
- **REQ-SANDBOX-096** — Runs are isolated from one another: when one process hosts two live runs, one confined and one not, the commands of each follow the setting in force when that run began. An altered confinement setting applies to the next session started, with no re-registration or process restart.
- **REQ-SANDBOX-097** — Ordering at launch: the availability decision is settled before the run does anything else, so a request for confinement the host cannot deliver fails immediately with that mechanism's reason rather than at the first shell command — and certainly never by executing that command unconfined. When it fails, the session lock is released and anything this launch created is cleaned up. The decision is written into run state before the session is announced as ready.

### Downgrade of unattended permissive runs

- **REQ-SANDBOX-098** — The confinement input to permission-mode resolution requires both selection AND availability; configuration alone never satisfies it. Because a run requesting confinement the host cannot deliver never starts (REQ-SANDBOX-095), no live run ever reaches mode resolution in the "selected but unavailable" state, so at resolution time confinement is inactive exactly when `runtime.sandbox_mode` is `off` and active exactly when a non-off mode was proved available under REQ-SANDBOX-067. Selection alone must never count as present: treating it as present would remove the tightening while commands executed unconfined, which is the combination this requirement exists to prevent.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The pair above still governs confinement status; it no longer feeds a downgrade — the status is recorded, and the mode is unaffected by it.
- **REQ-SANDBOX-099** — The downgrade of a permissive mode for an unattended, unconfined run — its three conditions, the mode it downgrades to, the modes it leaves untouched, and the fact that resolution never raises — is fixed by REQ-TOOLS-067; this domain holds no copy of it and states no second rule. What it adds is the reading of that requirement's confinement condition within this domain: confinement counts as active exactly when a `runtime.sandbox_mode` other than `off` was proved available under REQ-SANDBOX-067, and selection alone never satisfies it (REQ-SANDBOX-098).
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The reading above still governs confinement status; there is no downgrade for it to feed — the requested mode always applies.
- **REQ-SANDBOX-100** — Resolution yields four things: the mode that will apply, the mode that was requested, a flag true only when the applied mode is more restrictive than the requested one, and a user-facing reason. The reason is produced only while that flag is true, and it names both modes, states that nothing can answer an approval prompt for this run and that confinement is not active, and quotes `runtime.allow_unsandboxed_autonomous: true` as the workspace setting that keeps the requested mode in place. When the flag is false the applied mode equals the requested mode and no reason is shown.
- **REQ-SANDBOX-101** — A run counts as attended when, at the moment its mode is resolved, an approval prompt for its session can be put in front of a person; otherwise it is unattended and eligible for tightening. The condition is exactly the one REQ-TOOLS-053 fixes and REQ-TOOLS-069 applies to a run, and this domain holds no second copy of it. It is a test of **capability, not of registration**: a presenter that is registered but cannot actually put a prompt in front of anyone does not make a run attended, so a conformance test written from this requirement and one written from REQ-TOOLS-053 must agree on every case, and a session whose presenter is present but wedged is unattended under both. What the test deliberately does not reach is what happens *after* a prompt that can be shown has been shown: whether it is ever answered is settled by `runtime.approval_timeout_seconds` and `runtime.headless_approval_policy` (REQ-SANDBOX-053, REQ-SANDBOX-102), and a presentation that fails at the moment it is attempted is settled by the `presenter-error` denial of REQ-TOOLS-058. Neither of those is an input to mode resolution, and neither re-resolves a mode already resolved. A session that cannot put a prompt to a person — because no presenter was ever wired for it, or because the presenter it had was torn down — is unattended and is tightened; and every run being desktop-started, that is the only way an unattended run arises. A session that can put a prompt to a person is attended and keeps its requested mode.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The attended/unattended test above still governs; it no longer alters any mode — an unattended run keeps its requested mode.
- **REQ-SANDBOX-102** — That tightening never goes further than `ask` is REQ-TOOLS-067's and is not restated here. What this domain relies on it for is that a tightened run still reaches the approval path rather than a flat deny, so that where no prompt can be shown each such ask is then settled by `runtime.headless_approval_policy` (default deny; `abort` halts the run).
- **REQ-SANDBOX-103** — Each agent in a run resolves its own effective mode against the conditions in force when that agent starts work — whether a prompt can be answered for the session, whether confinement is active, and the value of `runtime.allow_unsandboxed_autonomous` — so a change to any of those inputs governs agents that start afterwards without the run being restarted. The requested mode is whichever of these is present, highest precedence first: a persona-level pin, then a session-level override, then `runtime.permission_mode`. Where that agent is tightened, a warning naming the persona it applied to is logged.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The precedence above still governs; no agent is ever tightened — each applies the recorded name directly.
- **REQ-SANDBOX-104** — The announcement made at run start stamps the effective permission mode, the confinement flag, and the backend name from one reading of status, so the stored snapshot and the mode decision cannot conflict. Tightening is surfaced three ways: a logged warning; a system message in the run transcript; and a diagnostics timeline event `permission_mode_downgraded` (actor `permissions`) with metadata `requested_mode` and `effective_mode`.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The stamp above still governs; no downgrade is ever surfaced — the announcement records the requested (= effective) mode, and no `permission_mode_downgraded` event is emitted.
- **REQ-SANDBOX-105** — The chain end to end, for an `autonomous` run with no approval presenter on a host where the launcher exists but the trial fails, in three cases. Where `runtime.sandbox_mode` is `off`, no confinement was requested, so the run starts, is tightened to `ask` under REQ-SANDBOX-099, and is recorded as unconfined with an empty backend name. Where a non-off mode is requested, the run does not start at all (REQ-SANDBOX-095, REQ-SANDBOX-126) and no mode resolution occurs, since there is no run to resolve for. On the same host once the trial succeeds and a non-off mode is requested, the run keeps `autonomous` — confinement being active removes the third tightening condition — and is recorded as confined together with the backend name.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The start/refuse cases above still govern; the tightening case no longer applies — an `off` run starts and keeps `autonomous`.
- **REQ-SANDBOX-106** — A permission-mode change made part-way through a session is resolved on exactly the terms used at run start (REQ-SANDBOX-099), against that session's approval channel and its current confinement status, and agents already working receive the new mode without a restart. What the session stores is the REQUESTED mode, not the effective one, so agents started later resolve again for the circumstances then in force. A persona-level pin is not always overridden, and the direction of the change decides. Comparing the requested mode against the pin by the restrictiveness ordering REQ-TOOLS-047 fixes, which is not restated here (REQ-SANDBOX-046): where the change is MORE RESTRICTIVE than the pin, the pin gives way and that persona takes the new mode; where the change would be MORE PERMISSIVE than the pin, the pin stands, that persona keeps its pinned mode, and the persona is listed in `skipped_personas`; where the change equals the pin, nothing about that persona changes and it is not listed, since nothing was skipped in effect. The asymmetry follows the fail-closed posture of this domain: a user tightening mid-session must be able to tighten everything, while loosening must never happen behind a pin the user deliberately set. The change appends one entry to the session audit log with `event` `permission_mode_change` carrying `timestamp`, `session_id`, `agent_id`, `requested_mode`, `effective_mode`, `previous_mode`, `source`, `reason`, and `skipped_personas`; a companion diagnostics timeline event `permission_mode_changed` (actor `permissions`) repeats `requested_mode`, `effective_mode`, `previous_mode`, `source`, and `skipped_personas`. Failing to write that record never prevents the change taking effect. An override belongs to one session: it is never visible to another run in the same process, and it does not outlive the run, so a resumed session starts again from the mode its configuration names.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The change mechanics above still govern; the resolution step no longer applies — the change is applied directly, and agents started later apply the recorded name directly.
- **REQ-SANDBOX-107** — The per-session launch dialog of REQ-SANDBOX-119 produces an advisory before launch whenever the session being started would be unattended under REQ-SANDBOX-101. It is empty when such work can proceed (confinement active, or the permissive mode opted into). Otherwise it is a corrective sentence that names the mode that will apply, notes that tightening occurred where it did, explains that every tool call would be refused because no approval prompt can be answered, and lists the corrections — setting `runtime.permission_mode: autonomous` together with `runtime.allow_unsandboxed_autonomous: true`, or enabling `runtime.sandbox_mode`. It advises rather than blocks: because `ask` is the shipped default, blocking would block every workspace that has not been configured. The dialog displays the advisory and the launch proceeds, and the run reports whatever refusals then occur.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The advisory above still governs except that it never claims a downgrade was applied; an `autonomous` run proceeds with an empty advisory.

### Persistence, events, and audit

- **REQ-SANDBOX-108** — The session's resumable state carries `sandboxed` (bool, default false) and `sandbox_backend` (string, default ""), stamped at run start, so a completed session can later be checked for whether its shell ran unconfined; the same two facts are recorded once into the launch audit (REQ-SESSION-016, REQ-SESSION-138), which is what makes the check answerable after the run is over. Where that state is held is REQ-SESSION-001's and is not fixed here. A state written before these keys existed reads back as unconfined with an empty backend, which correctly describes those runs, and no schema migration is needed.
- **REQ-SANDBOX-109** — The run-start event on the session event stream, which every run emits, carries `sandboxed` (bool) — the availability VERDICT, not the configured mode.
- **REQ-SANDBOX-110** — The run-start event carries `permission_mode`, whose value is drawn from the preset vocabulary REQ-TOOLS-041 fixes (not restated here) and which SHALL report the EFFECTIVE mode after any tightening — the mode the run's decisions will actually resolve under — never the requested mode. This is the only reading consistent with the single-reading stamp of REQ-SANDBOX-104, and it makes `permission_mode: autonomous` alongside `sandboxed: false` unreachable on a run whose decisions all resolve as `ask`. The requested mode is not lost: whenever the two differ, the `permission_mode_downgraded` timeline event of REQ-SANDBOX-104 is emitted from that same reading of status and carries `requested_mode` and `effective_mode`, so a reader can always recover both, and the absence of that event means the two were equal. The audit trail (REQ-SANDBOX-104, REQ-SANDBOX-112) remains the authoritative record of the mode that applied.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The event above still governs and still carries the mode the run resolves under; the two are now always equal, so `permission_mode: autonomous` alongside `sandboxed: false` is reachable.
- **REQ-SANDBOX-111** — *Withdrawn.* Its only observable surface was a process's standard output and its exit status, neither of which exists in a graphical-only product; the machine-readable record of a run refused for unavailable confinement is carried by REQ-SANDBOX-126.
- **REQ-SANDBOX-112** — Permission decisions, the fetch host rules and network-command rules among them, are recorded into the session's permission audit (REQ-TOOLS-078, REQ-SESSION-137), each entry recording the identifier of the rule that decided; a refusal states which rule produced it. A user must be able to read that audit outside this application, so a confinement decision can be checked without trusting this application's own account of it (REQ-SESSION-199).
- **REQ-SANDBOX-126** — Given a run is refused at start because the host cannot deliver the confinement mode its configuration selects (REQ-SANDBOX-094, REQ-SANDBOX-095), then that refusal SHALL be the first and only entry on that run's event stream: a terminal result entry with status `error` whose text carries the availability reason and the remediation of REQ-SANDBOX-071 verbatim, with no run-start event, no agent activity, and no tool event before or after it. The text is the same text the launch notice of REQ-SANDBOX-120 shows, so the recorded stream and what the user was told never differ. No session snapshot is written for such a run, since REQ-SANDBOX-095 leaves no session behind.
