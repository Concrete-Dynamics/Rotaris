# Agent Tooling, Terminal Execution, Permissions, and Approvals — 14. Terminal Live Streaming

Part 5 of 9 of [domain 05](../05-tools-permissions-approvals.md), which indexes every part. Defines REQ-TOOLS-126 – REQ-TOOLS-147.

### 14. Terminal Live Streaming

**REQ-TOOLS-126** — Streaming configuration: `runtime.terminal_stream_enabled` (default true; disabling costs the live view, never the command), `runtime.terminal_stream_interval_ms` (default 100, valid range 20–2000; output sampling period), `runtime.terminal_stream_buffer_kb` (default 256, valid range 0–8192; per-stream replay buffer, 0 disables replay). The sampling period is a **ceiling on batching rather than a fixed cadence**, and what may arm an earlier frame — input the user has directed at a stream whose control they have taken, and nothing else — is REQ-CONFIG-117's, which this requirement cites rather than restates. The rate at which frames reach surfaces is bounded in aggregate by REQ-MONITOR-306, across every live stream of every session delivered to every window: **the number of streams a configuration allows to be live is not a multiplier on this per-stream period.** That citation is stated here because an implementer reading this requirement alone would otherwise build per-stream sampling with no aggregate at all.

**REQ-TOOLS-127** — A foreground command's live output is published on a stream named `fg:<scope>`, where `<scope>` is the identifier of the run the command belongs to, or the literal `root` when the command belongs to no run. A background session publishes on `bg:<session_id>` using its `ts_XXXXXXXX` id. Frames are typed `delta` (the text appended since the previous frame), `screen` (a complete replacement of the displayed text), or `meta`. Streaming changes nothing the agent sees: with or without a consumer attached, and whether or not publishing succeeds, the command still runs to completion and the observation returned is identical — the only detectable difference is whether a live preview existed. A completed stream — foreground and background alike — ends with a `screen` frame whose text equals the observation's final output text, so the live view finishes on the same text the observation reports rather than on a partial capture, and the stream is then closed carrying the command's exit code. That closing frame is a **literal replacement of the displayed text and carries an explicit marker saying that it is one**: its text is plain on the terms this requirement already fixes — capped, and truncated from the oldest end — and it is the only frame of a stream of which any of that is true. Every earlier frame stays faithful to what the command actually wrote, which is what REQ-SHELL-095 and REQ-SHELL-098 need in order to present a character grid with cursor addressing, alternate-screen fidelity, per-cell attributes and sixteen colours. **The two bind different instants and therefore do not conflict**: those requirements govern the stream while the process is running, and this frame is the one emitted after it has exited — when there is no cursor to paint (REQ-SHELL-098), no alternate screen left to be in, and no further output to attribute to a cell.

**REQ-TOOLS-128** — Displays can talk back through a registered stream-control channel — send-keys, resize, and interrupt for foreground; send-keys, interrupt (SIGINT), and kill for background — without knowing what drives the stream. A stream info record carries the command, a running flag, start time, exit code, and a `truncated` flag set once replay frames were dropped.

### 15. Workspace File Tools and the Path Fence

**REQ-TOOLS-129** — A central workspace-boundary check governs file access: relative paths resolve against the workspace root; the candidate is resolved to its real path (following symlinks and junctions, so a link that escapes the root resolves outside and is rejected); a path outside the root fails with `Path '<resolved>' is outside workspace root '<root>'` unless the outside-workspace opt-out is enabled.

**REQ-TOOLS-130** — The opt-out is `runtime.allow_outside_workspace` (default false). It is set through the layered YAML configuration surface or through the confirmed desktop control of REQ-TOOLS-191, and by no other means: no launch-time override, no per-run flag, no environment variable ever turns it on. It governs the file tools and the permission gate's workspace-root scoping.

**REQ-TOOLS-131** — The desktop status strip always shows a file-access flag: `workspace-scoped` normally, `outside-workspace!` when the opt-out is on, with tooltip/accessible text explaining whether agents may read and write outside the workspace folder.

**REQ-TOOLS-132** — `read_file` and `write_file` share the following behavior. A location designated an additional read-only root can be read even though it lies outside the fence of REQ-TOOLS-129, and every write to one is refused; the exception covers reads only. A file counts as binary when a NUL byte appears within its first 8192 bytes. Text is decoded as UTF-8 and, failing that, as latin-1, so a read never fails for encoding reasons alone. Content hashes reported to callers are SHA-256. A write is atomic: a reader running concurrently with a write sees either the whole previous content or the whole new content, never a partial file, and a write interrupted part-way leaves the previous content in place. For each path the 10 most recent writes stay available to `undo` (REQ-TOOLS-135). An additional read-only root is designated by the configuration key `runtime.additional_read_only_roots`, a list of absolute paths (POSIX or Windows spelling) defaulting to empty; a relative entry is rejected at load and at assignment with `runtime.additional_read_only_roots entry '<e>' must be an absolute path`, matching the rule and message shape of `runtime.sandbox_writable_roots` (REQ-TOOLS-116). Configuration is the only designation: no launch-time flag and no built-in list of locations exists, so nothing outside the workspace is readable unless the user wrote it into the configuration. A path under such a root is readable exactly as REQ-TOOLS-129 would allow one inside the workspace; every write to one is refused with the path-fence error even when `runtime.allow_outside_workspace` is on, and the roots grant nothing to the search tools of section 16, which stay workspace-confined.

**REQ-TOOLS-133** — Read-before-write: editing a file never read through this engine instance is rejected with `You must read <rel> before editing it. Call read_file(path="<rel>") first, then retry your edit.` Every successful write records the new content as read, so consecutive edits work.

**REQ-TOOLS-134** — `read_file` contract: accepts `path` (with `file_path` accepted as an alias), `offset` (1-based, default 1), `limit` (default 2000 lines), and `grep` (regex filter, with `grep_context` default 3; matching lines prefixed `>`, groups separated by `---`, headed by `N match(es) for '<pattern>':` or `No matches for pattern …`). Content is returned line-numbered (`N: line`) with a metadata header `[path: … | total_lines: … | shown: lines A-B | truncated: true]`. Output is capped at 30,000 characters with a continuation hint `(Output capped at ~30000 chars. <n> more lines. Use offset=<k> to continue.)`. Reading a directory returns an entry listing (subdirectories suffixed `/`, entries whose name is one of the ignore components of REQ-TOOLS-140 skipped, `(empty directory)` placeholder). Binary files are rejected (`Binary file (<n> bytes). Cannot display content.`). A missing path returns a recovery message containing a listing of the parent directory and up to 5 close-match suggestions — the names scoring at least 0.45 under the similarity function of REQ-TOOLS-188, comparing the requested base name against each candidate base name after lower-casing both, listed highest score first with ties broken by ascending name.

**REQ-TOOLS-135** — The `write_file` action names its operation selector `operation`; the argument name `command` is deliberately not used for it, so a `write_file` call never supplies a command facet (REQ-TOOLS-015). Operations: `create` (fails if the file exists: `File already exists: <p>. Use 'overwrite' or 'edit'.`), `edit` (old-string/new-string; identical strings rejected), `overwrite` (requires an existing, previously read file), `insert` (`insert_line` ≥ 0, 0 = beginning; a line beyond the file length is rejected), `undo` (pops the per-path undo stack; `No edit history for <p>.` when empty). Success messages report lines changed/created/inserted/replaced. Every success carries a structured diff payload for UI rendering that is excluded from model-visible content.

**REQ-TOOLS-136** — Edit matching runs four levels, and the first level that produces any match decides the outcome: (1) exact; (2) exact after trailing whitespace is stripped from every line on both sides; (3) exact after one and the same leading-whitespace prefix is added to or removed from every line of the candidate, so a block differing only by a uniform indentation shift still matches; (4) fuzzy — the single best-scoring window of the same number of lines, accepted only at similarity ≥ 0.85. A match above level 1 is flagged in the result (`Match level: <level>`; a fuzzy match adds `(similarity: 0.NN)` and `Verify the result.`). When no level matches, the message names the levels tried and the file's line count and suggests a fresh read or `overwrite`. When a level matches more than once, the result is `Found <n> occurrences of old_str at lines <a, b, …>` with guidance to add surrounding context or set replace-all. Replace-all replaces every exact occurrence as plain text. Level 4 scores each candidate window with the similarity function of REQ-TOOLS-188, comparing the window's text against the old-string text; when two windows score equally the one starting on the lower line number wins, so a fuzzy edit is deterministic on any given file.

**REQ-TOOLS-137** — The hash-anchored read and edit tools (`haet_read`, `haet_edit`, and the alias `haet`) enforce the same workspace fence as REQ-TOOLS-129 and honor the same `runtime.allow_outside_workspace` opt-out. Their record of which files have been read is scoped to the workspace root and shared by every run in that workspace, so a file read during one run can be edited by a later run without being read again. Their action surface is fixed by REQ-TOOLS-189.

**REQ-TOOLS-188** — One similarity function serves every threshold in this domain. For two strings *a* and *b*, similarity(*a*, *b*) = 1 − editDistance(*a*, *b*) / max(length(*a*), length(*b*)), where editDistance is the unit-cost edit distance over Unicode code points — insertion, deletion, and substitution each costing 1 — length is counted in code points, and the similarity of two empty strings is 1. The result lies in [0, 1] and is symmetric in its arguments. The 0.85 fuzzy-edit threshold of REQ-TOOLS-136 and the 0.45 filename-suggestion cutoff of REQ-TOOLS-134 are both read against this function and against no other, so two implementations of this specification return the same score for the same pair of strings and accept the same edits and suggestions.

**REQ-TOOLS-189** — Action surface of the hash-anchored tools. `haet_read` accepts `path` (with `file_path` accepted as an alias), `offset` (1-based, default 1), and `limit` (default 2000 lines), and returns line-numbered content in the format of REQ-TOOLS-134 with one addition: its metadata header carries `content_hash`, the SHA-256 digest of the file's exact bytes on disk at the moment of the read, rendered as 64 lowercase hexadecimal characters. `haet_edit`, and its alias `haet`, accepts `path` (same alias), `content_hash` (required), `old_string`, `new_string`, and `replace_all` (default false).

Given `haet_edit` is called, when the SHA-256 digest of the file's current bytes differs from the supplied `content_hash`, then the edit SHALL NOT be applied and the call SHALL fail with a message that names the path, states that the file changed since that hash was taken, and directs the caller to read it again before retrying; the message SHALL NOT quote the file's current content. A matching hash is what satisfies the read-before-write rule of REQ-TOOLS-133 for these tools, so a caller holding a current hash never has to read a file twice.

`haet_edit` matches `old_string` at level 1 of REQ-TOOLS-136 only — exact text, with no trailing-whitespace normalization, no indentation shift, and no fuzzy window — because the anchoring hash exists precisely to make the edit exact; a failure to match reports the path and directs the caller to read the file again, and multiple occurrences with `replace_all` false are reported as REQ-TOOLS-136 reports them. Writes are atomic and enter the same per-path undo history as REQ-TOOLS-132's writes. A successful edit reports the file's new `content_hash`, so consecutive edits chain without an intervening read.

### 16. Search Tools (grep, glob)

**REQ-TOOLS-138** — Both search tools are read-only, workspace-confined, and use no shell or network. `grep` accepts `pattern` (regex; an invalid pattern returns `Invalid regex pattern: <detail>`), `paths` (a list; a singular `path` key and a bare-string `paths` value are normalized), and `max_matches` (default 100). Output is one `file:line:content` line per match, or `No matches found`.

**REQ-TOOLS-139** — Search scan filters (applying to grep scans and glob): non-files and symlinks are skipped; paths outside the workspace and paths containing a hard-coded ignore component are skipped; the workspace's `.gitignore` is honored when gitignore support is available (directories pruned during traversal, files filtered); files over 2 MiB are skipped; probably-binary files (NUL within the first 1024 bytes) are skipped. Tools that act on one named file (`read_file`, `haet_read`) skip the gitignore filter entirely: naming a path explicitly is treated as the caller's decision, and the file is served even when the workspace ignores it.

**REQ-TOOLS-140** — The hard-coded ignore components are: `.git`, `.hg`, `.svn`, `.idea`, `.vscode`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.tox`, `.venv`, `__pycache__`, `dist`, `venv`, `node_modules`, `.pnpm`, `.next`, `.nuxt`, `coverage`, `.turbo`, `cache`, `build`, `out`, `target`, `.nx`, `.rotaris`.

> **Extended by [`PD-TOOLS-012`](../../product/directives/pd-tools-012.md#pd-tools-012), 2026-10-07.** The list above still governs; the directive adds one member, the directory holding the code-intelligence runtime's per-project marker, named by the first segment of the marker path in REQ-MCP-116's binding manifest, so REQ-TOOLS-139's scans and REQ-TOOLS-134's listings skip it as they skip `.rotaris`, and a file in it named by its path is still served.

**REQ-TOOLS-141** — `glob` accepts `pattern` (e.g., `**/*.py`) and `base_path` (a relative directory; a base outside the workspace or not a directory is silently ignored and the workspace root used). Results are workspace-relative POSIX paths, deduplicated and sorted alphabetically, or `No files found`. Absolute path patterns are relativized to the workspace or dropped. Observable results (filters, format, ordering, caps) are identical whether or not an external search accelerator is present on the host.

### 17. Local Git Tools

**REQ-TOOLS-142** — `git_commit` accepts `message` (required) and `files` (optional list). With no file list, all tracked changes are staged; with a list, every path is validated against the workspace (an escaping path errors with `Path escapes workspace: <p>`) and staged explicitly in workspace-relative POSIX form. The tool is local-only: no push, no remote interaction ever.

**REQ-TOOLS-143** — Failure surfaces: not inside a git repository is detected up front; staging failures pass through the underlying error output; nothing staged errors with `No changes to commit.` plus a hint listing modified tracked files and untracked files with `Pass these paths in the files field or use files=null to stage all tracked changes.` (or noting the working tree is clean); commit and revision-resolution failures pass through underlying output. A success observation carries `commit_sha` (the new HEAD) and `files_staged` (the staged file list).

**REQ-TOOLS-193** — *New 2026-09-18 under OQ-61.* `git_read` answers repository-identity reads for the worktree the calling run occupies, without spawning a process and without reading the working tree: operations exactly `head` and `read_ref`, and an unknown operation errors with `Unsupported operation: <op>`. `head` resolves the worktree's `HEAD` to the commit it names and the branch it sits on, answering `{ commit: <sha>, branch: <name> }`, or `{ commit: <sha>, detached: true }` when `HEAD` names a commit directly. `read_ref` takes `ref` (a branch name) and resolves `refs/heads/<ref>` to its commit, answering `{ commit: <sha>, ref: <ref> }` and erroring with `Unknown ref: <ref>` otherwise. Resolution follows the worktree's `gitdir:` pointer to the git directory and its `commondir`, reading `HEAD`, loose refs and `packed-refs`; no subprocess is spawned and no command is run. The tool declares reading — it reads repository files, though they lie above the workspace fence — and neither writing nor running, and joins the read-only class of REQ-TOOLS-007; its confinement is its own whitelist rather than the path fence of REQ-TOOLS-129, which continues to refuse every direct read of the same metadata. Any other repository path — configuration, hooks, objects, the index, logs — is refused with `Git metadata '<p>' is not readable through this tool.` A worktree root that resolves to no git directory answers `Not a git repository: <root>.`

### 18. Task-List Tool (todo)

**REQ-TOOLS-144** — Operations are exactly `replace`, `add_phase`, `add_task`, `update`, `remove_task`; an unknown operation errors with `Unsupported operation: <op>`. Phases contain ordered tasks; both carry stable auto-generated 8-hex-character ids; names need not be unique; targeting is always by id. Task states: `PENDING`, `IN_PROGRESS`, `COMPLETED`, `ABANDONED`.

**REQ-TOOLS-147** — Ergonomics: `add_task` accepts a nested task payload or flat fields (`title` accepted as an alias for `name`); a missing phase or task id errors with a hint enumerating the available phases/tasks; a no-op `update` is an error (`Todo update made no changes…`).
