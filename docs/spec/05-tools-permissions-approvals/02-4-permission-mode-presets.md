# Agent Tooling, Terminal Execution, Permissions, and Approvals — 4. Permission Mode Presets

Part 2 of 9 of [domain 05](../05-tools-permissions-approvals.md), which indexes every part. Defines REQ-TOOLS-041 – REQ-TOOLS-077.

### 4. Permission Mode Presets

**REQ-TOOLS-041** — Exactly three presets ship: `restricted`, `ask`, `autonomous`. This requirement is the product's single definition of the permission-mode preset vocabulary: those three spellings are the whole of it, they are stable persisted values, and no requirement in any other domain holds a second copy of the vocabulary. A requirement that needs it cites this one — together with REQ-TOOLS-046 for how a configured name resolves to a preset, REQ-TOOLS-047 for the restrictiveness ordering, and REQ-TOOLS-067 for the downgrade of a permissive mode — and states only what it adds. The default decision each preset carries is stated by that preset's own requirement — `restricted` deny (REQ-TOOLS-042), `ask` ask (REQ-TOOLS-043), `autonomous` allow (REQ-TOOLS-044) — and is not restated elsewhere either. Rule families are composed into each preset in a fixed order — (1) fetch/egress rules, (2) destructive command rules, (3) network-command classification rule, (4) read-only rules. That order is behaviourally load-bearing: resolution stops at the first matching rule (REQ-TOOLS-019), so a narrow family placed after a family that matches more broadly would never be reached.

**REQ-TOOLS-042** — `restricted`: default decision deny. Rules: the fetch pair, all nine destructive rules, `restricted:network-command` (deny, matching the network-command pattern set), `restricted:read-outside-workspace` (ask; read-only tools with paths outside the workspace), `restricted:read-only-tool` (allow). Semantics: in restricted mode the four ask-class starter rules loosen the flat deny into a prompt for those categories.

**REQ-TOOLS-043** — `ask`: default decision ask. Rules: the fetch pair, all nine destructive rules, `ask:network-command` (ask), `ask:read-only-tool` (allow — reads allowed regardless of path).

**REQ-TOOLS-044** — `autonomous`: default decision allow, carrying only the five destructive deny rules and deliberately no ask rules (unattended they would resolve to fail-safe deny; attended they would prompt in the mode chosen to avoid prompts; and an ask would invert the restrictiveness ordering). The workspace file boundary in autonomous mode is enforced by path-fence errors (REQ-TOOLS-129), not prompts. This is exclusive and normative: no preset ever attaches a path-scoped ask rule to `autonomous`, and a path outside the workspace under `autonomous` never raises an approval prompt — it either succeeds because the opt-out of REQ-TOOLS-130 is on, or fails with the path-fence error of REQ-TOOLS-129.

**REQ-TOOLS-045** — Each supervised preset (`restricted`, `ask`) carries a fetch rule pair ordered ahead of everything else that could match `fetch`: `<preset>:fetch-remote-host` (ask; network tool class; matches URLs whose host is outside the local machine; described as network egress to an outside host) then `<preset>:fetch-local-host` (allow; network access confined to this machine). A URL that cannot be parsed counts as remote and therefore asks.

**REQ-TOOLS-046** — The default preset is `ask`. An unrecognized configured mode name resolves to the strictest preset (`restricted`) with a logged warning; an empty/absent name resolves to the default. Preset resolution never raises. This requirement is the product's single definition of how a configured mode name resolves to a preset, including the shipped default; no requirement in any other domain holds a second copy of the rule or of the default.

**REQ-TOOLS-047** — Restrictiveness is totally ordered: `restricted` (0) < `ask` (1) < `autonomous` (2). Startup refuses to proceed if any preset lacks a rank. Rank lookup resolves names exactly like preset resolution (empty → default, unknown → strictest) but silently. This requirement is the product's single definition of that ordering, and every comparison of two modes by restrictiveness anywhere in the product is this one; no requirement in any other domain holds a second copy of it.

**REQ-TOOLS-048** — At agent construction the requested permission mode is selected as follows. A persona-level `permission_mode` pin takes precedence over an active mid-session override, except that an override at least as restrictive as the pin (by the order of REQ-TOOLS-047) takes precedence over the pin instead — the same direction-sensitive rule that governs live agents in REQ-TOOLS-074. With neither a pin nor an override, `runtime.permission_mode` applies, defaulting to `ask`. The selected name is then put through the downgrade rule of REQ-TOOLS-067 for that agent's own context, and the result is the effective mode.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The selection above still governs; the downgrade step no longer applies — the effective mode equals the selected name, for every agent, with no re-resolution.

**REQ-TOOLS-049** — Global user configuration is overlaid by workspace `.rotaris/` configuration under the configuration domain's layering rules. This release's permission rule lists are shipped preset definitions. The authorable surface consists of the existing permission modes, grants and declared permission controls. Custom rule-list authoring requires a separately specified schema, validation and layering contract before being offered.

### 5. Interactive Approval Flow

**REQ-TOOLS-050** — An `ask` suspends exactly one tool call. Other agents in the session keep running; each wait is identified by its own request id rather than by the conversation it came from.

**REQ-TOOLS-051** — Approval options are exactly: approve once, approve for the session, deny. Wait terminal states are exactly: resolved, cancelled, timed out.

**REQ-TOOLS-052** — Approval responses map to decisions as follows:
- timeout → deny, source `timeout`, reason ending `Denied because no answer arrived within <N> seconds.`
- cancelled → deny, source `cancelled`, reason ending `…the approval request was cancelled.`
- approve once → allow, rule id `approval:once`, source `user-once`, reason `The user approved '<tool>' once (rule '<pending rule>' asked).`
- approve for session → allow, rule id `approval:session`, source `user-session`, and a session rule is added per REQ-TOOLS-024.
- deny → deny, source `user-deny`, reason ending `…the user denied the request.`
  > **Narrowed by [`PD-TOOLS-005`](../../product/directives/pd-tools-005.md#pd-tools-005), 2026-09-23 (revision 2, 2026-10-06).** The mappings above still govern; after one timeout the run treats the user as away, and until they next send input to the session further asks resolve at once under the headless approval policy of REQ-TOOLS-065 — every approval wait still outstanding in the run ending the same way at that moment — except the approval the question tool's own call needs, which still prompts and waits.

**REQ-TOOLS-053** — A session counts as interactive exactly when an approval prompt for that session can be put in front of a person. A session that cannot prompt anyone is not interactive and never borrows another session's ability to prompt. Everything handed to the prompt is JSON-serializable in full (REQ-TOOLS-056). Prompting never stalls the rest of the session: while one agent waits for its answer, the session's other agents keep running and can raise approvals of their own. Registering a run-abort hook for a session (REQ-TOOLS-065) neither makes that session interactive nor takes away prompting it already has.

**REQ-TOOLS-054** — Approval wait semantics: creating a wait with an empty request id is rejected; creating a duplicate pending id is rejected with `Approval '<id>' is already pending.`; resolving or cancelling an unknown id reports failure without side effect; waiting on an unknown id resolves cancelled immediately; a request discarded before it was ever shown counts as cancelled; a bulk-cancel releases every waiter (used on run cancellation, shutdown, and host teardown).
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 3).** When a run comes to rest by a pause, a stop, a quit or a crash, the waiters released are recorded as withdrawn, and their calls as interrupted and never run; never as denied.

**REQ-TOOLS-055** — The approval timeout is `runtime.approval_timeout_seconds`, the single key REQ-CONFIG-126 registers for this bound, carrying the default that requirement states, which is not restated here; this domain declares no second key and no second default. Its value space is a free-floating number of seconds — any float at least 0 — and not a fixed ladder of offered waits, so every surface that writes the setting accepts any value the space permits. A negative value is rejected when the configuration is loaded. A value of 0 means the wait never expires by itself, and such a wait is still released by run cancellation, shutdown, or host teardown (REQ-TOOLS-054). The same setting and the same zero-means-indefinite reading govern the user-question wait (REQ-TOOLS-158, REQ-TOOLS-178).
  > **Narrowed by [`PD-TOOLS-005`](../../product/directives/pd-tools-005.md#pd-tools-005), 2026-09-23 (revision 2, 2026-10-06).** The key, its value space and its reading of 0 still govern; while a run treats the user as away, an approval ask is not put to the wait at all (the question tool's own excepted), and a wait outstanding when the user is marked away ends at once rather than at its timeout.

**REQ-TOOLS-056** — The approval payload (rendered by hosts and persisted into session state) carries: `request_id` (hexadecimal UUID), `session_id`, `agent_id` (falling back to persona for display), `persona`, `tool_name`, `command` (secret-redacted), `argument_summary`, `rule_id`, `reason`.

**REQ-TOOLS-057** — The argument summary renders sorted `key=value` lines; any value whose key looks secret is masked outright; all values are redacted; each rendered value is clipped at 240 characters with a trailing `…`; the summary is empty when the request carries a command (the command line is shown instead). The argument summary appears in the approval payload and the approval dialog only; the audit trail's `summary` field is the request summary of REQ-TOOLS-016, and both are produced by the redaction pass of REQ-TOOLS-171, so neither can display an unmasked credential.

**REQ-TOOLS-058** — If presenting the prompt raises, the pending request is discarded and the call is denied with source `presenter-error` and a reason stating the approval request could not be shown.

> **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 6, 2026-10-06.** Clause 38: a
> presentation answered "not shown" once the quit is under way is held for the quit to withdraw, not denied
> `presenter-error`.

**REQ-TOOLS-059** — Approval responses can come only from the host UI. Nothing in agent output or tool output can satisfy an approval.

**REQ-TOOLS-060** — Pending approvals are visible in session state as a mapping from request id to payload, written when presented and removed on answer, timeout, or cancellation.

**REQ-TOOLS-061** — Every `ask` — interactive or headless — publishes an `approval.requested` stream event before the wait begins, carrying: `request_id`, `agent_name` (verbatim from the deciding context; empty when unknown, never backfilled from persona), `persona`, `tool_name`, `rule_id`, a redacted `summary`, `resolver` (`"brokered"` | `"headless"`), `timeout_seconds` (null on the headless path, meaning no wait occurs at all), and `unattended_reason` (`"headless-policy"` on the headless path, else empty). A failed event publish never fails the dispatch.

**REQ-TOOLS-062** — A recorded decision carries the approval `request_id` only when it directly resolved a raised approval; pairing is checked strictly (the source must be an approval-resolution source; session id and tool name must match) and any mismatch yields an empty id. Sources eligible to claim a request id: `user-once`, `user-session`, `user-deny`, `headless-policy`, `timeout`, `cancelled`, `presenter-error`, `fail-closed`.

**REQ-TOOLS-063** — The desktop approval prompt is a modal dialog titled "Permission required" whose minimum size is 560×380 logical pixels (REQ-SHELL-022), containing: the headline `Allow <agent> to run <tool>?`; the requester line `Requested by <agent> (<persona> persona).`; a read-only monospace detail box holding the redacted command facet exactly as the approval payload's `command` field carries it (REQ-TOOLS-056) when the request has a command facet, and otherwise the argument summary of REQ-TOOLS-057, whose accessible description states that credentials are masked and which shows `No arguments were reported for this call.` when there is nothing to display; a fine-print line `Matched rule: <rule_id>` followed by the decision reason; and exactly three buttons — Deny (danger styling), Approve for this session (secondary styling), and Approve once (primary styling). The dialog has no default action: no button is activated by Enter, and initial keyboard focus is placed on Deny, so a keystroke aimed at whatever the user was doing when the dialog appeared can never approve a call they have not read. Every way out of the dialog yields one of the three answers of REQ-TOOLS-051: pressing Escape and closing the window each answer Deny, so dismissing the dialog is never read as approval and no exit path leaves the request unanswered. If the chosen answer cannot be delivered to the waiting agent, the dialog stays open with all three buttons disabled and shows a status line saying the answer could not be delivered. Multiple pending requests are shown one at a time — exactly one approval dialog is open per window, and approval dialogs never stack — and a request that is answered or cancelled elsewhere while its dialog is open closes that dialog without asking for a second answer. Queued requests are shown in the order their `approval.requested` events were published (REQ-TOOLS-061), oldest first, and the next queued request is presented as soon as the open dialog closes; a request that timed out or was cancelled while queued is dropped from the queue without ever being shown and counts as cancelled under REQ-TOOLS-054. When more than one request is pending the dialog states how many others are waiting, so the user knows the queue exists. Each presentation makes the dialog the focused window of its parent.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 4, 2026-09-28.** Clauses 9 and 15:
  > a dialog the application's quit closes answers nothing, and the quit withdraws the request. Closing the dialog
  > answers Deny in every other case, as stated.

**REQ-TOOLS-064** — A session for which no approval presenter is registered — one for which the modal dialog of REQ-TOOLS-063 cannot be shown — resolves every `ask` through the headless approval policy of REQ-TOOLS-065: never a silent allow, never a hang.

> **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 6, 2026-10-06.** Clause 38: an ask
> made after the quit revoked the last window's presenter and before the shutdown is not resolved by the headless
> policy; it is held unshown and withdrawn by the quit.

### 6. Headless / Unattended Resolution

**REQ-TOOLS-065** — `runtime.headless_approval_policy` ∈ {`deny` (default), `abort`}; unrecognized values behave like `deny`. Under `deny`, the single tool call is refused and the agent may re-plan. Under `abort`, the call is refused and the session's registered abort hook is invoked to stop the run; if no abort hook is registered, a warning is logged and the behavior degrades to `deny`. Reasons state that no approval UI is available in this host (the abort variant adds that the headless approval policy aborts the run); decision source is `headless-policy`.

**REQ-TOOLS-066** — When no approval resolver is wired at all, a built-in fail-safe resolver answers every `ask` with deny, source `headless-policy`, and a reason stating no interactive approval is available so the request was denied fail-safe.

### 7. Effective Mode, Downgrade, and Mid-Session Change

**REQ-TOOLS-067** — A permissive mode (one whose preset default is allow; today only `autonomous`) is downgraded to `ask` for a run that is simultaneously (a) unattended (no interactive approval host), (b) unsandboxed (sandbox not both configured and available), and (c) not opted in via `runtime.allow_unsandboxed_autonomous: true` (default false, per-workspace). `ask` and `restricted` pass through untouched. Unrecognized mode names have already resolved to the strictest preset and are never downgraded. Downgrade evaluation never raises. A downgrade never goes further than `ask`; each ask it produces is then settled by the headless approval policy of REQ-TOOLS-065. This requirement is the product's single definition of the downgrade — its three conditions, the mode it downgrades to, and the modes it leaves alone — and no requirement in any other domain holds a second copy of it.
  > **Superseded by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The text above states the behavioural target and is kept for that reason; it no longer states what this product does — the requested mode always applies.

**REQ-TOOLS-068** — The downgrade reason shown to the user follows this verbatim pattern: `Permission mode '<requested>' was downgraded to 'ask' for this run: it is unattended (no interactive approval available) and runs without the OS-level sandbox. Set runtime.allow_unsandboxed_autonomous: true in the workspace config to run unattended in '<requested>' mode anyway.`
  > **Superseded by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The text above states the behavioural target and is kept for that reason; no downgrade reason is ever produced.

**REQ-TOOLS-069** — A run is attended exactly when its session can put an approval prompt in front of a person (REQ-TOOLS-053), and unattended otherwise. An attended run keeps the permission mode it asked for. A run whose session has no approval presenter registered — because none was ever wired for that session (REQ-TOOLS-066), or because the session's presenter was torn down (REQ-TOOLS-177) — cannot prompt anyone and therefore meets condition (a) of REQ-TOOLS-067. This product has no entry point that starts a run outside the desktop application, so an unattended run is always a desktop-started run whose session never gained, or has lost, the ability to show the dialog of REQ-TOOLS-063; there is no separate launch surface that produces one.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The attended test above still governs; it no longer alters any mode — an unattended run keeps the mode it asked for, as an attended one does. Written 2026-10-07 ([OQ-222](../../architecture/open-questions.md)).

**REQ-TOOLS-070** — For the downgrade test of REQ-TOOLS-067, a run counts as sandboxed only when `runtime.sandbox_mode` requests a sandbox *and* that sandbox has been proved usable on this host (REQ-TOOLS-119); configuration by itself does not satisfy the test. REQ-TOOLS-118 is canonical where the two overlap: a session that requests a sandbox unavailable on this host does not start at all, so no live run ever reaches the downgrade test in the "requested but not usable" state. At downgrade-evaluation time a run is therefore unsandboxed exactly when `runtime.sandbox_mode` is `off`, and sandboxed exactly when it requested a sandbox that was proved usable under REQ-TOOLS-119. The `sandbox_unavailable` refusal of REQ-TOOLS-118 stays reachable for a wrap that fails at command time on a host where the sandbox was proved usable at start (REQ-TOOLS-122), and that failure still refuses to execute rather than widening what the run may do.
  > **Superseded by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The text above states the behavioural target and is kept for that reason; there is no downgrade test — the requested mode always applies.

**REQ-TOOLS-071** — At run start the effective mode is announced: session state records the effective permission mode, whether the run is sandboxed, and the sandbox backend name. A downgrade is additionally written to the transcript (live recorder when available, else appended as a system event), to the diagnostics timeline as a `permission_mode_downgraded` event carrying requested and effective mode metadata, and to the log.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The announcement above still governs and records the requested (= effective) mode; no downgrade is ever written to the transcript, the diagnostics timeline or the log, and no `permission_mode_downgraded` event is emitted. Written 2026-10-07 ([OQ-222](../../architecture/open-questions.md)).

**REQ-TOOLS-072** — Before the application starts an unattended run it computes an advisory string for the workspace, and presents it per REQ-TOOLS-192. The advisory is informational and never blocks the launch. It is the empty string exactly when the effective mode of an unattended run in that workspace raises no `ask` at all — that is, when no tool call would be routed to the headless resolver that refuses it (REQ-TOOLS-065, REQ-TOOLS-066); today that is the case only when the effective mode is `autonomous`. Otherwise it is non-empty, and it names all three settings that resolve the condition — `runtime.permission_mode` set to `autonomous`, `runtime.allow_unsandboxed_autonomous` set to `true`, and `runtime.sandbox_mode` set to a backend available on this host — and states that a downgrade was applied whenever REQ-TOOLS-067 downgraded the mode.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The advisory above still governs except that it never states a downgrade was applied, and an `autonomous` run's advisory is empty. Written 2026-10-07 ([OQ-222](../../architecture/open-questions.md)).

**REQ-TOOLS-073** — A mid-session mode change has two halves: every live policy context in the session receives the new preset, effective on its next dispatch; and a session-level override records the requested (not effective) mode name for agents built later, which re-resolve the downgrade for their own context. The change itself is re-resolved through the downgrade rule — switching to `autonomous` mid-run on an unattended, unsandboxed session still downgrades.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The two halves above still govern; the re-resolution step no longer applies — the change is applied directly, and agents built later apply the recorded name directly.

**REQ-TOOLS-074** — A session-wide mode change applies to an agent whose persona pins `permission_mode` only when the new mode is at least as restrictive as the pin under the order of REQ-TOOLS-047. A change that would loosen such an agent leaves that agent deciding calls under its pin, while still applying to every unpinned agent in the session. The personas the change did not reach are listed alphabetically in the `skipped_personas` field of the mode-change audit entry (REQ-TOOLS-082), in the log line for the change, and in the confirmation shown to the user, so the user can see exactly which agents kept their previous mode.

**REQ-TOOLS-075** — Session mode overrides are per-session: setting one with an empty session id is rejected; lookup never falls back to another session; the override is discarded at run end so a resumed session does not inherit a previous run's switch; a global reset exists for cleanup.

**REQ-TOOLS-076** — Every mode change is audited with source `"user"`; a failed audit write never blocks the change itself.

**REQ-TOOLS-077** — The desktop mode selector lists presets strictest-first (`restricted`, `ask`, `autonomous`), shows the mode currently in effect, and persists the choice to `runtime.permission_mode` in `<workspace>/.rotaris/agents.yaml`, surviving restart. That write commits that one key and nothing else: settings edits left pending on any other surface stay pending, and choosing a permission mode neither commits nor discards them. A control whose whole subject is how much an agent is allowed to do must not carry unrelated changes into effect as a side effect of being used, because the surprise would land in a security-relevant setting. Choosing `autonomous` requires an explicit confirmation, and declining restores the previous selection. The selector is usable mid-run — it forwards to the running session per REQ-TOOLS-073 and the transcript announces the change. The effective mode is also visible in the status bar and in the runtime settings page.
