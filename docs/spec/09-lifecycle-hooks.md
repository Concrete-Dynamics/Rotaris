# User-Defined Lifecycle Hook Commands

## Overview

Users can attach shell commands ("hooks") to named points during a run: around tool calls, and at session, iteration, child-agent, and verifier boundaries. Every hook is handed a secret-masked JSON description of what happened on standard input, is given a wall-clock budget to finish in, and answers with its exit status. Only a hook attached to the point before a tool call is capable of stopping anything. Hooks are declared in layered YAML configuration; commands declared by a repository stay inert until the user reviews and approves them; hooks configured for an external agent can optionally be imported; and every invocation is recorded both in session diagnostics and on the event stream.

## Requirements

### Event Model

- **REQ-HOOKS-001** — The system SHALL recognize exactly seven hook events in two families: tool events `pre_tool` and `post_tool`, and lifecycle events `session_start`, `session_end`, `iteration_end`, `child_completed`, and `verifier_finished`. No other event name is valid in configuration. This requirement is the product's single definition of the hook event vocabulary and of its division into the two families: a document that needs to name a hook event, to state how many there are, or to say which family one belongs to SHALL cite this identifier rather than restating the set, and a surface needing a new lifecycle point extends this list here rather than admitting an event name of its own.

- **REQ-HOOKS-002** — Only tool hooks SHALL be able to influence the run via exit code. Lifecycle hooks are strictly informational: given a lifecycle hook with any configuration (including `required: true`), when it exits with any code, then the run proceeds unaffected.

- **REQ-HOOKS-003** — Events SHALL fire at these points: `pre_tool` immediately before a permitted tool call runs; `post_tool` once a tool call has run; `session_start` once per run, ahead of the first iteration; `session_end` once per run, on each of the ways a run can finish: success, failure, a requested stop, cancellation, and interruption; `iteration_end` at the close of each finished iteration; `child_completed` once a delegated child agent has finished, whatever its final state; `verifier_finished` once for every completion-verifier pass, executed or skipped.

- **REQ-HOOKS-004** — Permission policy SHALL be evaluated before hooks: given a tool call the policy denies, no hook process starts and no hook event fires for that call. `post_tool` SHALL fire only for calls that ran to completion — not for a policy denial, and not for a call stopped by a `pre_tool` hook.

- **REQ-HOOKS-005** — Given a tool call that ran but did not succeed (the tool returned an error rather than an observation), the `post_tool` hooks SHALL still fire, and the payload's `result` field SHALL carry `{"error": "<text>"}`.

- **REQ-HOOKS-006** — Given a programmatic request to fire a lifecycle event name the system does not recognize, the engine SHALL do nothing and return zero outcomes (recording the fact at debug log level only), so that new event names can be introduced without breaking older components.

### Configuration Schema and Validation

- **REQ-HOOKS-007** — Hooks SHALL be declared under a `hooks:` key of the layered YAML agent configuration, in either the global scope (the per-user configuration directory's `agents.yaml`) or the workspace scope (`<workspace>/.rotaris/agents.yaml`).

- **REQ-HOOKS-008** — Each hook entry SHALL support exactly these fields with these defaults:
  - `event` (string, required, no default): must name one of the seven events listed in REQ-HOOKS-001; surrounding whitespace is removed before validation.
  - `command` (string, required): must not be blank or whitespace-only; otherwise kept exactly as written (no whitespace trimming).
  - `name` (string, default `""`): display label; if it reduces to empty after trimming, the hook's stable id is displayed instead, in the form REQ-HOOKS-018 fixes.
  - `matcher` (string, default `""`): empty selects every applicable occurrence; trimmed; must parse as a valid command pattern when configuration is loaded.
  - `timeout_seconds` (number, default `60.0`): must be strictly greater than 0.
  - `required` (boolean, default `false`): has meaning only for `pre_tool` (see REQ-HOOKS-048).
  - `enabled` (boolean, default `true`): `false` leaves the entry declared but non-executing; the entry keeps its place in the list, so ids assigned to the entries around it do not shift.
  - `source` (string, default `""`): filled in while loading; any value written by hand SHALL be replaced.

  This requirement is the product's single definition of the hook entry schema — the field set, each field's type, whether it is required, and its default: a document that presents, validates, stores, or documents a hook entry SHALL cite this identifier rather than restating any of those, and a field a surface needs is added here rather than declared elsewhere. Where such a document also needs the form of the stable id a nameless entry is reported by, it cites REQ-HOOKS-018 for that, which this requirement does not restate.

- **REQ-HOOKS-009** — The hooks section SHALL support: `enabled` (boolean, default `true`) as a single on/off control for the whole feature — when `false`, nothing runs but declarations remain; `entries` (list, default empty — no hooks ship with the product); and `superseded_entries` (list, default empty, filled in only while loading, never written by hand).

- **REQ-HOOKS-010** — A list-shorthand spelling `hooks: [ <entries> ]` SHALL be accepted and normalized to `hooks: { entries: [...] }`; both spellings produce identical behavior, including the recorded declaring scope.

- **REQ-HOOKS-011** — A bare `hooks:` key (YAML null) and a bare `entries:` key SHALL parse as *unset*, not *empty*: the inherited entry list is kept. A `hooks:` value that is neither a mapping nor a list SHALL fail loading with an error of the form: `Invalid 'hooks' section: expected a mapping or a list of hook entries, got <type>`.

- **REQ-HOOKS-012** — An invalid entry SHALL make configuration loading fail: the load SHALL surface an error naming the YAML path of the offending field, SHALL produce no configuration, and SHALL neither drop, ignore, nor repair the entry. `<i>` is the entry's position within the `entries` list of the scope being loaded, counted from `0` across every declared entry, entries with `enabled: false` included:
  - Unknown event name — path `hooks.entries.<i>.event`; message `hook event '<v>' is not a known lifecycle hook event; expected one of: ...`, quoting the rejected value and listing all seven names of REQ-HOOKS-001.
  - Matcher that will not tokenize, an unclosed quote for instance — path `hooks.entries.<i>.matcher`; message `hook matcher '<v>' is not a usable command pattern: ...`.
  - Blank or whitespace-only command — path `hooks.entries.<i>.command`; message `hook 'command' must not be blank`.
  - `timeout_seconds` of zero or less — path `hooks.entries.<i>.timeout_seconds`; the message SHALL quote the rejected value and state that the budget must be greater than zero.

  The YAML paths are a machine-readable contract and SHALL be produced exactly as given. The message texts are human-readable: each SHALL convey the information stated for it above — which field was rejected, the value that was rejected, and what was expected, listing all seven event names in the unknown-event case — and the exact wording is left to the implementation. Where several entries are invalid at once, the load SHALL report every one of them, in ascending `<i>` order within a scope and in scope-precedence order across scopes, each with its own path and message, so that a user correcting a configuration file is not led through the failures one at a time.

### Configuration Layering and Provenance

- **REQ-HOOKS-013** — Scope precedence SHALL be: built-in defaults, then global, then workspace. A scope that supplies an `entries` list SHALL substitute its own list for the inherited one in full, which lets a narrower scope remove an entry it inherited; a scope that supplies only `enabled` SHALL leave the inherited entries in place.

- **REQ-HOOKS-014** — Every entry SHALL be tagged with the scope that declared it (`default`, `global`, or `workspace`) while that scope is being loaded, ahead of the merge, so the tag is still accurate after merging. A configuration assembled in memory without going through the loader SHALL resolve as scope `default`.

- **REQ-HOOKS-015** — When one scope's `entries` list supersedes an inherited list, the displaced entries — together with anything previously displaced — SHALL be kept in the winning scope's `superseded_entries`. Keeping them is purely a record; it grants nothing and decides nothing about trust.

- **REQ-HOOKS-016** — *Withdrawn.* Its only surface was a command-line `--config <path>` override, and the product has no command-line entry point; the capability it carried — letting a deliberate act by the user, rather than the accident of opening a checkout, decide that a configuration source's hooks may run — is carried by the review dialog of REQ-HOOKS-104 to REQ-HOOKS-108 and by the decision management of REQ-HOOKS-136.

### Hook Identity and Ordering

- **REQ-HOOKS-017** — When `hooks.enabled` is `false`, both the effective hook set and the resolved superseded set SHALL be empty.

- **REQ-HOOKS-018** — Each resolved hook SHALL have a stable id of the form `<source>:<index>:<event>` (e.g. `workspace:0:post_tool`) unless it carries an explicit external identity (see REQ-HOOKS-114). `<index>` is the entry's ordinal within the list declared by its own scope, assigned while disabled entries are still present, so switching one entry off leaves every other entry's id unchanged. Each scope has its own independent index sequence.

- **REQ-HOOKS-019** — Selecting the hooks for one event SHALL preserve declaration order, and that same order SHALL govern execution, for tool events and lifecycle events alike (REQ-HOOKS-040).

- **REQ-HOOKS-020** — The scope names treated as trusted SHALL be exactly `default`, `global`, and `workspace` (the last only once approved, see REQ-HOOKS-090). Any other scope value SHALL be refused by the trust gate; there is no permissive branch for unfamiliar scopes. Imported external hooks use the scope value `external:claude-code`, which is intentionally not in this set.

### Matcher Semantics

- **REQ-HOOKS-021** — Matchers SHALL apply only to tool events. A lifecycle event has nothing to select against, so its hooks fire on every occurrence whatever `matcher` says.

- **REQ-HOOKS-022** — An empty matcher SHALL select every tool call, whether or not that call supplies a shell command.

- **REQ-HOOKS-023** — A hook that carries a non-empty set of tool names (only imported hooks do) SHALL match when the tool name is a member of that set, compared exactly; its string matcher plays no part.

- **REQ-HOOKS-024** — Where the call supplies a non-blank shell command, the matcher SHALL be read as a command pattern and tested against every segment of a command line built from several commands, so that in `git status && rm -rf /` the second command is examined too.

- **REQ-HOOKS-025** — A command pattern SHALL be evaluated as follows. The candidate command line is first divided, outside quotes, at each of `&&`, `||`, `;`, `|`, `&`, and a line break; the pattern is tested against each resulting segment, and a match on any segment is a match (so `rm -rf /` inside `git status && rm -rf /` is examined). Within a segment, both pattern and candidate are split into tokens under one quoting convention used on every platform alike: a token break falls at each run of whitespace that lies outside quotes; a single-quoted or double-quoted run groups its contents into the surrounding token and the quote characters themselves are removed; and a backslash is an ordinary literal character, never an escape and never a quote, so a Windows candidate such as `copy C:\repo\a C:\repo\b` splits into exactly three tokens with every separator intact. An unterminated quote makes the text untokenizable, which REQ-HOOKS-028 resolves as "no match". Tokens are compared position by position, each comparison a case-sensitive glob in which `*` is the only metacharacter and matches any run of characters, the empty run included; `?`, `[`, `]`, and every other character are compared literally, so `git push -?` matches the literal token `-?` and nothing else. The segment matches only when its token count equals the pattern's, with one exception: where the pattern's final token is a bare `*`, the segment may carry any number of further tokens, zero included. Matching is positional and never a substring search: `echo git push` does not match `git push *`. This requirement, together with REQ-HOOKS-027 for which text a matcher is compared against and REQ-HOOKS-029 for where that text is taken from, is the product's single definition of hook matcher evaluation: the separator set the command line is divided at, the quoting and tokenizing convention, the glob comparison, and the trailing-`*` rule are stated here and nowhere else, and a document that needs any of them SHALL cite this identifier rather than restating it. In particular no other document may state a separator set, a backslash convention, or a fallback to the tool name of its own; where one did, this requirement governs.

- **REQ-HOOKS-026** — Consequence to document and test: `git push *` (with space) matches both `git push` and `git push --force`; `git push*` (no space) is a two-token pattern that matches `git push` on its own and nothing longer.

- **REQ-HOOKS-027** — An empty matcher selects every tool call (REQ-HOOKS-008, REQ-HOOKS-022); what follows governs non-empty matchers only. Where the text a matcher is tested against (REQ-HOOKS-029) is empty or whitespace only, the matcher SHALL instead be compared with the tool name as one case-sensitive shell-style glob: `read_f*` selects `read_file` and does not select `READ_FILE`. Where that text is non-blank — a file-editing tool's requested action name included — the call SHALL be matched as a command pattern under REQ-HOOKS-024 and REQ-HOOKS-025, and the tool name SHALL play no part.

- **REQ-HOOKS-028** — Matching SHALL be defined for every input: a command line that cannot be tokenized (for example an unclosed quote), or a matcher that will not parse at match time, SHALL yield "no match" rather than turning the tool call into a failure.

- **REQ-HOOKS-029** — The text a matcher is tested against SHALL be the same facet the permission policy matches on, taken from the call's arguments: for the shell tool (`terminal`) that is the command line; for a file-editing tool it is the name of the action requested — one of `create`, `edit`, `overwrite`, `insert`, `undo` — so the matcher `create` selects every file creation whatever the path.

### Execution Engine

- **REQ-HOOKS-030** — Each invocation SHALL run the configured `command` as a newly started process handed to the host platform's command interpreter, so that operators, quoting, redirection, and executable lookup written into `command` take effect exactly as they would were the same line typed at that platform's shell prompt. The interpreter SHALL be, on a POSIX host, the standard shell at `/bin/sh` invoked with the command as a single argument to `-c`; and on a Windows host, the command processor named by the `ComSpec` environment variable, or `cmd.exe` where that variable is unset or blank, invoked with the command as a single argument to `/c`. No other interpreter SHALL be selected, and the choice SHALL NOT vary with the content of `command`, so that the same declaration behaves identically on every machine of a given platform. The process's working directory SHALL be the tree the run is changing: the isolated worktree for a run confined to one, and otherwise the workspace itself (REQ-HOOKS-084). The payload's `workspace` field reports the base workspace and not that working directory (REQ-HOOKS-057).

- **REQ-HOOKS-031** — The payload SHALL be delivered as exactly one UTF-8 JSON object written to the hook process's standard input, and standard input SHALL then be closed, so that a hook reading to end-of-input terminates. No part of the payload SHALL be placed on the process's command line or in its environment: a tool argument containing `; rm -rf /` reaches the hook only as text inside the JSON document and is never interpreted. A hook that writes to standard output or standard error before or while it reads the payload SHALL NOT stall the invocation. Whatever the process wrote SHALL be reported subject to the limits of REQ-HOOKS-037, except in the two cases where there is nothing to report: the grace period of REQ-HOOKS-033 also expired, or no process was started at all (REQ-HOOKS-035). The last byte written SHALL be the closing brace of the JSON object: no trailing newline, and no other trailing byte, SHALL follow it, so that a hook comparing raw bytes rather than parsing them sees exactly the document and nothing more.

- **REQ-HOOKS-032** — The hook process SHALL inherit the host environment, with any per-run variable overrides supplied by the embedding application taking precedence. The product itself contributes no hook-specific environment variables. Per-run overrides are an embedding facility only: no host is required to offer them, the desktop application supplies none, and no configuration key, preference, or user interface for setting them SHALL exist. A hook that needs a variable therefore sets it in its own `command`, and a run started from the desktop application sees exactly the environment the application itself was started with.

- **REQ-HOOKS-033** — Each invocation SHALL be bounded by the hook's `timeout_seconds` of wall-clock time. On expiry the hook process SHALL be terminated, and at most a further 5.0 seconds SHALL be spent completing that termination and collecting output the process had already produced; where that grace period also expires, the outcome reports empty output rather than the run waiting any longer. Termination SHALL reach only the process that was started and SHALL NOT be widened to its process group. The fate of that process's descendants is deliberately left to the platform and SHALL NOT be constrained: a descendant is permitted to outlive both the hook process and the run, whether or not it detached first, and the run SHALL neither wait for it, track it, nor report it. In particular, collecting the terminated process's output SHALL NOT block on a stream a surviving descendant still holds open; the grace period bounds that collection and expiring it yields empty output. Where the host cannot complete the termination even after the grace period, the invocation SHALL nevertheless finish within the bound below: the outcome is completed and returned, the run continues, and the still-running process is recorded only as a log entry — no user-facing warning beyond the ordinary timeout warning of REQ-HOOKS-052 is produced, and no run status is affected. The outcome SHALL record `timed_out = true` and no exit status (surfaced per REQ-HOOKS-036). The invocation SHALL therefore return no later than `timeout_seconds` plus 5.0 seconds of grace plus the time taken to start one process: a hook given a 0.3 s budget whose command sleeps for 60 s SHALL return without waiting for that sleep, and far inside the 60 s.

- **REQ-HOOKS-034** — Given a resolved hook whose timeout is zero or negative because it was constructed programmatically without configuration validation, execution SHALL substitute the 60-second default instead of running with no limit.

- **REQ-HOOKS-035** — If the command cannot be launched at all (for example because the working directory does not exist), the outcome SHALL have no exit code, empty output, a description of the launch failure, and a user-facing warning containing "could not run"; no error propagates into the run.

- **REQ-HOOKS-036** — The state in which a hook returned no exit status at all (launch failure, termination on timeout, or a process ended by a signal from any other source) SHALL be represented by one fixed value that means the same thing on every operating system, rather than by whatever a platform reports for a signalled process; consumers must therefore read the `timed_out` flag rather than infer anything from an exit value. That fixed value is `-1`, and it is what appears wherever an outcome's exit code is recorded verbatim — the session timeline entry's `exit_code` metadata and its message text (REQ-HOOKS-119). On the session event stream the same state is normalized to `exit_code: null` (REQ-HOOKS-125), so a stream consumer never sees `-1`.

- **REQ-HOOKS-037** — Standard output and standard error SHALL be captured separately and decoded as UTF-8, with bytes that are not valid UTF-8 replaced rather than causing the capture to fail. Each stream SHALL be limited to 16384 bytes, the two limits applying independently of one another. The limit SHALL count bytes of the decoded text's UTF-8 encoding, and the cut SHALL be taken at a character boundary: the retained portion is the longest prefix of the decoded text whose UTF-8 encoding is at most 16384 bytes, so no partial character is ever retained. Where a stream exceeded that limit, the retained portion SHALL be followed by the marker `\n[truncated: <total> bytes of output, 16384 kept]`, `<total>` being the size the stream would have had untruncated. The marker SHALL be appended beyond the limit and SHALL NOT count toward it. A stream at or below the limit SHALL carry no marker. This rule — count the retained portion only, append any marker beyond the limit — governs every truncation in this domain (REQ-HOOKS-052, REQ-HOOKS-066). This requirement is the product's single definition of the cap on hook output: the 16384-byte figure, the fact that it applies to each stream separately rather than to the two combined, the character-boundary cut, and the truncation marker are stated here and nowhere else, and a document that reports, stores, or configures hook output SHALL cite this identifier rather than restating the figure or asserting that output beyond it is discarded.

- **REQ-HOOKS-038** — Each outcome SHALL record the elapsed wall-clock time as a whole number of milliseconds, measured over the entire invocation including any timeout handling.

- **REQ-HOOKS-039** — Every invocation SHALL yield an outcome, whatever the host does. An interpreter or executable that is not installed, a working directory that cannot be used, and a process ended by a signal SHALL each yield an outcome carrying one of the warnings defined in REQ-HOOKS-052, after which the tool call or lifecycle point continues. A hook process ended by a signal it did not receive from the timeout path SHALL be treated as a process that produced no exit status: the outcome carries the fixed no-exit-status value of REQ-HOOKS-036 (`-1` where an exit code is recorded verbatim, `null` on the session event stream), `timed_out = false`, and the abnormal-termination warning of REQ-HOOKS-052 — never the platform's raw signal number, and never the "exited `<code>`" warning, which is reserved for a process that did exit. A diagnostics location that cannot be written SHALL NOT produce a warning and SHALL NOT change the outcome; it degrades to a log entry per REQ-HOOKS-121. None of these conditions SHALL raise an error into the run, end the run, alter its terminal status, or leave it waiting beyond the bound of REQ-HOOKS-033.

- **REQ-HOOKS-040** — Every applicable hook for an event SHALL run, in declaration order, even after one of them has decided to stop the call; the decision that takes effect is the first stopping outcome, determined once all applicable hooks have finished. Dispatch SHALL NOT stop early on a refusal, and the difference is observable and relied upon: the later hooks' side effects on the working tree, their `hook.start`/`hook.finish` pairs, their `hook_run` timeline entries, and their contribution to the failure tallies of REQ-HOOKS-055 all occur exactly as they would have with no refusal. The hooks of one event occurrence SHALL run one after another rather than concurrently, in declaration order, each finishing — normally or under the bound of REQ-HOOKS-033 — before the next starts; this holds for tool events and lifecycle events alike, so an occurrence with N applicable hooks is bounded by the sum of their individual bounds.

- **REQ-HOOKS-041** — Where a session has no hook eligible to run for an event, that event SHALL yield zero outcomes and nothing observable: no process is started, no `hook.start` or `hook.finish` is published, no timeline entry and no issue is recorded, and nothing is read or written on account of hooks. The once-per-session announcement of hooks the trust gate withheld (REQ-HOOKS-127) is the only event this rule does not suppress.

- **REQ-HOOKS-042** — Where a session has several tool calls outstanding at the same moment, the following SHALL hold. A hook's failures count against one allowance per stable id for the whole session, whichever call produced them, so three failures spread over three simultaneous calls switch the hook off at precisely the point three consecutive failures would (REQ-HOOKS-055). Reaching that point SHALL yield one switch-off warning and one switched-off id and no repeat of either, however many outstanding calls met the failing hook at once. A hook that consumes its entire budget on one call SHALL NOT delay the hooks of any other outstanding call, which begin and finish on their own schedule. These are invariants, not best-effort behavior: no maximum number of simultaneously outstanding tool calls is fixed, and each guarantee — one failure tally per stable id for the whole session, one switch-off warning and one switched-off id however many calls met the failing hook at once, one `hook.start`/`hook.finish` pair and one timeline entry per invocation, and no cross-call delay — SHALL hold at every degree of concurrency the host reaches.

### Exit-Code Semantics and Blocking

- **REQ-HOOKS-043** — For `pre_tool`: exit `0` lets the call proceed with no feedback and no warning; exit `2` stops the call, and what the hook wrote to standard error becomes the refusal that reaches the agent in place of the tool's output; any other exit produces a warning and the call proceeds.

- **REQ-HOOKS-044** — For `post_tool`: exit `0` yields nothing; exit `2` puts what the hook wrote to standard error into the conversation in addition to whatever the tool itself produced (the call already happened and is not rolled back); any other exit produces a warning.

- **REQ-HOOKS-045** — For lifecycle events: any non-zero exit — `2` included — is a warning only; the outcome always records that nothing was stopped, whatever `required` says. A lifecycle hook exiting `2` does count as a failure against the switch-off allowance, unlike a tool hook exiting `2`.

- **REQ-HOOKS-046** — Exit `2` from a `pre_tool` or `post_tool` hook is the hook working as designed and SHALL NOT count against the failure allowance: a guard that correctly stops calls is never switched off for doing so (five consecutive stops leave it enabled and file no failure issue). Exactly four situations count as a failure: the budget expired, the process could not be started, the process ended abnormally without an exit status (REQ-HOOKS-039), and the process exited with a code this specification assigns no meaning to.

- **REQ-HOOKS-047** — Nothing except a `pre_tool` hook SHALL ever be capable of stopping a call, regardless of what any other resolution step concludes; this SHALL be enforced rather than merely assumed.

- **REQ-HOOKS-048** — `required: true` SHALL NOT be interpreted as "any non-zero exit stops the call". A `pre_tool` hook that ran to completion and exited 1, 3, or 127 is simply misbehaving: warning, call proceeds, `required` or not. `required` changes behavior only where the hook returned no verdict at all (timeout or launch failure): without it, such a case proceeds with a warning; with it, the call is stopped and the agent is told which of the two happened. On a `post_tool` hook and on any lifecycle hook the flag is simply ignored.

### Message Formats (Agent- and User-Visible)

- **REQ-HOOKS-049** — The refusal an agent receives from a stopping `pre_tool` hook SHALL be exactly: `Blocked by hook '<name>'. <reason> The '<tool>' call was not executed. Choose a different approach or ask the user to adjust the hook configuration.` With an empty tool name the middle sentence reads `The call was not executed.`

- **REQ-HOOKS-050** — The `<reason>` in the refusal SHALL be: the hook's trimmed standard error; or `The hook gave no reason.` when the hook exited 2 having written nothing to standard error; or `The hook timed out after <budget> s.` when a `required` hook timed out; or `The hook could not be started.` when a `required` hook failed to launch.

- **REQ-HOOKS-051** — `post_tool` feedback text SHALL be: `Hook '<name>' reported after the '<tool>' call: <stderr>` (or `after the call:` with no tool name); empty standard error renders as `(the hook wrote nothing to stderr)`. Where one call produces several such texts they SHALL be joined with `\n` before delivery.

- **REQ-HOOKS-052** — Warning texts SHALL be:
  - launch failure: `Hook '<name>' (<event>) could not run: <crash reason>`
  - timeout: `Hook '<name>' (<event>) timed out after <budget> s and was terminated.`
  - abnormal termination, the process having been ended without an exit status by something other than the timeout path (REQ-HOOKS-039): a warning conveying the hook's display name, its event, and that the process was ended before it could return an exit status. It SHALL NOT quote a platform signal number, SHALL NOT read as a timeout, and SHALL NOT take the "exited `<code>`" form, which is reserved for a process that did exit; the wording is otherwise left to the implementation.
  - exit code with no assigned meaning: `Hook '<name>' (<event>) exited <code>.` followed, where either stream produced text, by an excerpt taken from standard error — or from standard output where standard error is empty — with each run of whitespace reduced to a single space and the result limited to 200 characters, a trailing `…` marking an excerpt that was cut. The 200 characters count the retained text alone and the `…` is appended beyond them, under the truncation rule of REQ-HOOKS-037. How the excerpt is joined to the sentence before it is left to the implementation, subject only to the excerpt remaining separately identifiable as the hook's own output rather than reading as a continuation of the sentence.

  `<name>` is the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); `<event>` is one of the seven event names. `<budget>` SHALL convey the hook's configured `timeout_seconds` as a number of seconds; how many decimal places it carries, and whether a whole number is written bare, are left to the implementation, provided one rendering is used consistently wherever a budget reaches the user or the agent in this domain (REQ-HOOKS-050).

- **REQ-HOOKS-053** — On the invocation that reaches the switch-off limit (see REQ-HOOKS-055), the warning SHALL gain, on that occasion only: `Hook '<name>' failed <count> times and is disabled for the rest of this session.`

- **REQ-HOOKS-054** — At the end of a run the switched-off-hook advisory SHALL be delivered on the host's notice channel (REQ-HOOKS-087). It SHALL be the empty string where that run switched no hook off. Otherwise it SHALL convey `<N>` — the number of hooks switched off under REQ-HOOKS-055 — that they were switched off for the rest of this session after failing repeatedly, and where the command output can be read (REQ-HOOKS-137). Like every user-facing count in this domain (REQ-HOOKS-101, REQ-HOOKS-106), the advisory SHALL be grammatically correct for the count it carries, so an `<N>` of 1 reads in the singular throughout and no `hook(s)` or `was/were` construction is emitted literally; the wording is otherwise left to the implementation. The advisory SHALL disclose that count and nothing further: no hook name, no command, no matcher, and no other configuration text SHALL appear in it. Hook warnings SHALL reach the user's warning channel only; no hook warning text SHALL appear in anything delivered to the agent.

### Failure Budget and Auto-Disable

- **REQ-HOOKS-055** — Once one hook (identified by stable id) has failed three times inside a single session, it SHALL be switched off and not invoked again before that session ends. The switch-off warning is emitted on the third failure and on no other occasion; afterwards the hook is skipped without comment — zero outcomes, no further warnings. (Five failing rounds therefore produce outcome counts 1, 1, 1, 0, 0 with exactly one switch-off warning.)

- **REQ-HOOKS-056** — Once switched off, the hook's id SHALL be visible in the engine's set of switched-off hooks, and an event whose hooks have all been switched off reports "no hooks". Failure tallies and the switched-off set belong to a single session; the next run begins with both empty.

### Payload Content and Redaction

- **REQ-HOOKS-057** — A tool payload SHALL always carry exactly the keys `event`, `tool_name`, `arguments`, `session_id`, `workspace` (path as a string), and `command` (the empty string for a tool that has no shell command, so that a hook script may index all six keys unconditionally). The `result` key SHALL appear only when a result exists — in practice only on `post_tool`; a `pre_tool` payload never has it.

- **REQ-HOOKS-058** — A lifecycle payload SHALL always carry `event`, `session_id`, and `workspace`; whatever fields the particular occurrence contributes are placed as siblings of those three, not nested under a sub-object. An occurrence that contributes no fields produces a payload of exactly those three keys.

- **REQ-HOOKS-059** — The names `event`, `session_id`, and `workspace` SHALL be reserved: caller-supplied lifecycle fields using those names are dropped without comment, so event data cannot impersonate the session identity that a shared hook script may branch on.

- **REQ-HOOKS-060** — Secret masking SHALL follow the payload's structure and reach every level of it: every string, however deeply nested, is passed through one common masking routine, and the surrounding shapes are left as they are rather than being flattened.

- **REQ-HOOKS-061** — Masking SHALL be the one shared redaction pass of REQ-TOOLS-171, applied to hook text exactly as it is applied to every other surface that carries tool arguments or configuration text. This domain declares no masking of its own and holds no copy of the pass's ordered layers, of the credential value prefixes it recognizes, or of the mask string; which key and flag names count as credential names is the test of REQ-TOOLS-172, of which this domain likewise holds no copy. What this domain relies on that pass for is that a recognized value is replaced while the text around it stays legible, so `Bearer sk-live-1` becomes `Bearer ***` and `Bearer` stays readable, and that masking is idempotent, so masking an already-masked string leaves it unchanged. Three further properties of that pass are what make the payload contract of REQ-HOOKS-067 checkable, and they SHALL hold wherever hook text is masked. First, the value a layer replaces SHALL extend over exactly one value token and no further: where the value opens with a single or a double quote it ends at the matching closing quote and the quote characters themselves are retained around the `***`; otherwise it ends at the first whitespace character following it, or at the end of the string where none follows — so `--token abc def` masks to `--token *** def`, `password: a b` masks to `password: *** b`, and `password: "a b"` masks to `password: "***"`. Second, the `Bearer`, `Basic`, and `token` scheme keywords SHALL be compared without regard to case, so that `bearer`, `BASIC`, and `Token` trigger masking exactly as they do. Third, the credential names and value prefixes that pass recognizes SHALL be a complete set rather than an open one: an implementation recognizing exactly them and nothing further is conformant, and no further name, prefix, or resemblance-based heuristic SHALL be added, so that a string carrying none of them is guaranteed to reach a hook unaltered (REQ-HOOKS-062).

- **REQ-HOOKS-062** — A string stored under a mapping key that names a credential SHALL arrive as `***` in its entirety, whatever the string looks like: `{"password": "the meeting is at noon"}` reaches the hook as `{"password": "***"}`. A string stored under any other key SHALL arrive unaltered but for whatever the passes of REQ-HOOKS-061 find within it, so `{"note": "run the tests"}` arrives verbatim. A mapping key names a credential exactly when it meets the secret-looking key-name test of REQ-TOOLS-172, which this requirement cites and does not restate, so a name is a credential name both as a mapping key and as the left-hand side of a `key=value` assignment inside a string. Where a credential-named key holds a list or a mapping rather than a string, the container SHALL NOT be replaced wholesale: its shape SHALL be preserved as REQ-HOOKS-060 requires, and every string within it, at every depth and whatever the intervening keys are called, SHALL arrive as `***` in its entirety exactly as though it were itself stored directly under a credential-named key. Non-string scalars within such a container are unchanged, and the container's own nested mapping keys are masked under REQ-HOOKS-063. So `{"tokens": ["abc", {"live": "def"}]}` reaches the hook as `{"tokens": ["***", {"live": "***"}]}`, which both keeps the structure a hook script indexes into and leaks nothing.

- **REQ-HOOKS-063** — Building a payload SHALL always produce one JSON object that parses (REQ-HOOKS-067), SHALL never fail, and SHALL never alter the caller's data. The substitutions below apply at every nesting level:
  - A value JSON cannot express is written as its text form; where producing that text form itself raises, the placeholder `<unrepresentable <TypeName>>` is written instead, `<TypeName>` naming the value's type.
  - Ordered and unordered collections are written as JSON arrays; not-a-number and positive and negative infinity are written in text form so that the document stays valid JSON; raw byte values are decoded as UTF-8 with replacement and then masked.
  - A container encountered again while it is still being walked is written as `"<recursive>"`; a value merely referenced from two places is written out in full at each of them.
  - A value nested more than 12 levels deep is written as its masked text form.
  - Mapping keys are converted to text and masked.
  - Where iterating the top-level mapping itself raises, the result is still a JSON object: a single key `payload` holding the masked text form of the offending value.

  Depth SHALL be counted with the top-level payload object at level 0, the values it holds directly at level 1, and so on; a value lying at a level greater than 12 is the one written as its masked text form. Not-a-number, positive infinity, and negative infinity SHALL be written as the JSON strings `"NaN"`, `"Infinity"`, and `"-Infinity"` respectively, which keeps the document parseable by a hook script that does no more than call a standard JSON parser.

- **REQ-HOOKS-064** — Masking an already-masked payload SHALL change nothing, and the caller's own data SHALL still hold the original values afterwards, since masking works on a copy.

- **REQ-HOOKS-065** — Where the engine is wired into real tool dispatch, arguments SHALL be shaped as follows: for the `terminal` tool, `arguments.command` holds the shell line next to the action's other (masked) fields; for a tool provided over MCP, that tool's own fields sit under `arguments.data` (so `arguments.data.api_key` arrives as `"***"`).

- **REQ-HOOKS-066** — The `post_tool` payload's `result` SHALL render what the agent was given for that call: `{"observation": "<text>"}` where the call produced an observation, `{"error": "<text>"}` where it produced an error (REQ-HOOKS-005). Where the call produced exactly one such item, `result` is that object; where it produced several, `result` is an array of them in the order the agent received them; where it produced none, the `result` key is absent altogether. Each `<text>` SHALL be limited to 4096 characters, and text that was cut SHALL end with the marker `\n[truncated: <total> characters]`, `<total>` being its length in characters before cutting. The 4096 characters count the retained text alone and the marker is appended beyond them, under the truncation rule of REQ-HOOKS-037.

- **REQ-HOOKS-067** — The bytes written to standard input SHALL form one valid JSON document and nothing else, and decoding it SHALL reproduce exactly the structure described in REQ-HOOKS-057 to REQ-HOOKS-066. Characters outside ASCII are carried as UTF-8. A Windows path such as `C:\repo\src` is escaped on the wire and decodes back to one backslash per separator. A hook that reads standard input to end-of-input, decodes UTF-8, and parses the result as JSON therefore recovers the payload unchanged, with no framing, length prefix, or second document to strip first. No trailing newline and no other trailing byte SHALL follow the object: the last byte written is the closing brace, as REQ-HOOKS-031 requires, so a hook comparing raw bytes and a hook parsing them agree on where the document ends.

### Tool-Dispatch Integration

- **REQ-HOOKS-068** — Tool hooks SHALL sit entirely within the branch the permission engine takes for permitted calls: only a permitted call reaches hook dispatch, and a denied call gets the permission system's own refusal with no hook process started. It follows that a `pre_tool` hook whose matcher targets something the built-in policy always denies (for example destructive commands rejected in every mode) will never fire; hooks cover the cases the policy leaves open.

- **REQ-HOOKS-069** — Hooks SHALL be attached per session and looked up per call: changing a session's attached hook set takes effect on the very next call, and a session with nothing attached dispatches exactly as though the feature were absent (one lookup and nothing more, with no extra content added to results). Attaching under an empty session identifier SHALL be rejected with an error; looking up an empty or unknown identifier yields nothing; detaching an unknown identifier does nothing and is not an error; attaching again replaces the previous set entirely.

- **REQ-HOOKS-070** — Sessions SHALL be isolated from one another: hooks attached to one session never fire for another session's tool calls, and there is no fallback to some other session's set. A tool call belonging to no session runs no hooks.

- **REQ-HOOKS-071** — A `pre_tool` stop SHALL reach the agent as an error result bearing the same call correlation id and tool name as the attempted call, containing the refusal text unchanged, delivered on the tool-result channel so the agent can choose another approach. The tool itself is never invoked for a stopped call.

- **REQ-HOOKS-072** — Stopping a call SHALL count as one refused tool invocation and nothing more: the run's terminal status is untouched by it, and the agent goes on to its next piece of work.

- **REQ-HOOKS-073** — The dispatcher SHALL consult hooks only for the events the session has actually declared hooks for: a session declaring only `post_tool` hooks incurs no cost at `pre_tool`.

- **REQ-HOOKS-074** — `post_tool` feedback SHALL travel in the same correlated result message that carries whatever the tool itself returned, so that no additional content is placed between an assistant's tool-call block and the corresponding results — an arrangement some model providers reject when several calls are issued together. Where the call produced no observation (the tool errored), the feedback SHALL instead be delivered as a following user-role message so that it is not dropped.

### Lifecycle Event Delivery

- **REQ-HOOKS-075** — Lifecycle payloads SHALL carry these data fields beside the three base keys of REQ-HOOKS-058. A string field whose value is absent SHALL be rendered as `""`; a string field holding a value of an unexpected type SHALL be converted to text, and where that conversion fails the field SHALL be `""`. An `iteration` that is not a whole number SHALL be reported as `0` (REQ-HOOKS-077). No field value can cause payload construction to fail.
  - `session_start`: `task` (string) — the run's own statement of the task, which need not repeat the user's prompt word for word.
  - `session_end`: `status` (string) — the run's terminal status, or `""` where no status could be derived, which consumers SHALL read as *unknown* and not as failure.
  - `child_completed`: `child_id`, `child_name`, `persona`, `state`, `status`, `summary` (all strings).
  - `verifier_finished`: `iteration` (integer), `executed` (boolean), `passed` (boolean), `skip_reason` (string), `failed_checks` (array of strings — the names of the failed checks that block).
  - `iteration_end`: `iteration` (integer), `outcome` (string), `child_name` (string), `status` (string), `summary` (string).

  The vocabularies these fields carry are owned by other domains and SHALL be exactly those, not a parallel set defined here. `session_end.status` carries one value of the run status vocabulary of REQ-EVENTS-026 — `completed`, `failed`, `max_iterations`, `interrupted`, `error` — or `""` where no status could be derived. `child_completed.state` carries the child's terminal state under REQ-ORCH-041: `succeeded`, `failed`, `cancelled`, or `blocked`. `child_completed.status` carries the child's report status under REQ-ORCH-112: `succeeded`, `partial`, `failed`, `cancelled`, or `blocked`. `iteration_end.outcome` carries the report status, after any rewrite, that REQ-ORCH-074 dispatched on, drawn from that same report-status vocabulary. `iteration_end.status` carries the terminal state recorded for the iteration's own record under REQ-ORCH-041 — which is why the two fields exist side by side and may legitimately differ, a `blocked` outcome being recorded as a `succeeded` iteration. A value the owning domain does not list SHALL be carried through as text rather than corrected or dropped, and `""` SHALL be read as *unknown* and never as failure.

  `executed` and `passed` SHALL always be present and SHALL always be JSON booleans: an occurrence supplying neither, or supplying a value that is not a boolean, yields `false` — never `""`, never an absent key, and never a string — so a hook script may test them without first checking their type. The `""` fallback of this requirement governs string fields only, and the `0` fallback of REQ-HOOKS-077 governs `iteration` only.

- **REQ-HOOKS-076** — Each lifecycle occurrence SHALL fire each attached hook exactly once. In a run in which all five events occur once, the order is `session_start`, `child_completed`, `verifier_finished`, `iteration_end`, `session_end`, matching where each occurs.

- **REQ-HOOKS-077** — Iteration numbers in `iteration_end` payloads SHALL begin at 1 for the first completed iteration and follow the loop from there (iterations 1, 2, 7 report 1, 2, 7, never a fixed 0). An iteration value that is not a whole number is reported as 0.

- **REQ-HOOKS-078** — Given a run with no hooks for a lifecycle event, no payload SHALL be assembled and no process started for occurrences of that event.

- **REQ-HOOKS-079** — A lifecycle occurrence SHALL always complete. A hook that cannot be executed SHALL yield the matching warning of REQ-HOOKS-052; data the payload cannot render SHALL be substituted per REQ-HOOKS-063 with no warning at all; any other fault raised while delivering the event SHALL reduce to a log entry. In each case the occurrence's remaining hooks still run, the run continues to its next step, its terminal status is unaffected, and no error reaches the agent. No such condition SHALL hold the run beyond the per-hook bound of REQ-HOOKS-033.

- **REQ-HOOKS-080** — Lifecycle hooks SHALL run in line with the run loop: a hook that consumes its whole budget holds the run up for that long, and `timeout_seconds` is the user's means of controlling this. Ordering guarantees: the `iteration_end` hook for iteration N finishes before iteration N+1 begins, and a `session_end` hook is guaranteed to run before shutdown.

- **REQ-HOOKS-081** — `session_start` SHALL fire ahead of the first iteration; `session_end` SHALL fire once per run on every exit path, after the final status has been decided. The status string SHALL be derived once per run and used for both destinations, so the value a `session_end` hook reads on standard input is character-for-character the value carried by the session-end wire event; the two can never disagree about how the run ended, and both carry `""` where the status could not be derived.

- **REQ-HOOKS-082** — `iteration_end` hooks SHALL finish before that iteration's checkpoint is taken, so that any edit such a hook makes to the working tree — reformatting sources, emitting a build artifact — is captured by that iteration's checkpoint rather than the next one's.

### Run Wiring, Notices, Teardown

- **REQ-HOOKS-083** — A hook declared in the layered YAML configuration SHALL execute only where the trust gate permitted it, on every host alike — the desktop application and any programmatic embedding of its engine: a run's native hook set starts from the gate's permitted output, never from the raw resolved configuration, and the policy toggles of REQ-HOOKS-116 then remove any native hook switched off there. Hooks imported from an external agent are outside this gate's remit and are governed instead by the toggles of REQ-HOOKS-115 to REQ-HOOKS-117.

- **REQ-HOOKS-084** — The trust decision SHALL be looked up against the base workspace — the repository the user opened and reviewed — even when the run itself executes inside a throwaway isolated worktree; the hook processes still start in whichever tree the run is changing.

- **REQ-HOOKS-085** — A failure to assemble the run's hook set at start-up SHALL NOT end the run: the run continues with no hooks and logs a warning (`Could not resolve this run's hooks; continuing without them.`).

- **REQ-HOOKS-086** — Where the trust gate withheld hooks, the notice SHALL be recorded in two places: as an issue in the session's diagnostics with kind `hook_trust`, severity `warning`, actor `hooks`, and metadata carrying `blocked` (how many were withheld), `restored` (how many were reinstated per REQ-HOOKS-098) and `workspace` (the path the trust decision was looked up against, as a string), so that a run whose notices no one was watching can still be accounted for afterwards; and as text on the desktop notice channel, where it becomes the persistent unreviewed-hooks warning of REQ-NOTIFY-224. Between them the notice and the `blocked — not reviewed` status of REQ-HOOKS-103 SHALL let the user tell hooks withheld on purpose apart from hooks that are broken, which the `hook_failure` issues of REQ-HOOKS-120 record instead.

- **REQ-HOOKS-087** — At the end of a run, on both the success and failure paths: any switched-off-hook advisory is sent to the host's notice channel, and the session's hook attachment is removed, so that an attachment left behind cannot cause one run's hooks to fire for a later run started inside the same process.

- **REQ-HOOKS-088** — A run in which nothing was withheld and nothing was switched off SHALL produce no hook notices at all.

- **REQ-HOOKS-089** — A run started from the desktop interface and a run started by a programmatic embedding of the engine SHALL share one execution lifecycle, so that neither can execute a hook the other would withhold: in a desktop run an `iteration_end` hook from an approved workspace demonstrably executes, and one from an unapproved workspace demonstrably does not, accompanied by a warning notice whose text contains "not been reviewed" and never contains the repository's command text.

### Workspace Trust Gate

- **REQ-HOOKS-090** — The gate SHALL decide on the declared provenance of a hook and SHALL NOT judge what its command does: no command is inspected for apparent danger, and no such inspection may be relied on to withhold anything. (Comparing the fingerprint of REQ-HOOKS-091, which covers command text, detects change to the declared set; it is not a judgement about the command.) For hooks resolved from the layered YAML configuration the rules are: a `global` or `default` hook is always permitted; a `workspace` hook is permitted only while a stored approval exists whose fingerprint equals the fingerprint of the current workspace hook set (REQ-HOOKS-091); an entry carrying no scope tag resolves as `default` before the gate is applied (REQ-HOOKS-014) and is therefore permitted; a hook carrying any other scope value is withheld, with no permissive branch for an unfamiliar value. Declaration order SHALL be preserved within the permitted group and within the withheld group. Hooks imported from an external agent carry scope `external:claude-code` and do not reach this gate at all (REQ-HOOKS-117), so this scope vocabulary says nothing about whether they run.

- **REQ-HOOKS-091** — The workspace hook fingerprint SHALL be the SHA-256 digest, rendered as 64 lowercase hexadecimal characters, of the canonical JSON document `{"version": 1, "hooks": [ {command, event, matcher, name, required, timeout_seconds}, ... ]}` — keys sorted, compact separators, ASCII-escaped — built from the workspace-scoped entries in declaration order. Observable consequences: computing the digest repeatedly over the same set yields the same 64 characters every time; the digest changes when any `command`, `event`, `matcher` (a matcher widened to empty included), `name`, `required`, or `timeout_seconds` changes, and when an entry is added, removed, or moved; it does not change when a `global` or `default` hook is edited; a workspace declaring no hooks yields the digest of the empty list, which equals the digest computed where only always-trusted-scope hooks are present and differs from that of every non-empty workspace set. `enabled` and `source` are not part of the document, so toggling `enabled` alone leaves the digest unchanged. `version` is part of the document, so raising it invalidates every stored decision. The fingerprinted list SHALL cover every workspace-scoped entry in declaration order, entries with `enabled: false` included. The consequence is deliberate and is the reading coherent with REQ-HOOKS-093: what the user reviews and allows is the set of commands the workspace declares, so an entry the user read while it was switched off may later be switched on without a fresh review, while rewriting, adding, removing, or reordering any entry — switched off or not — invalidates the decision at once. Excluding disabled entries was rejected because it would make a bare `enabled` toggle revoke the approval, contradicting this requirement's own statement that toggling `enabled` alone leaves the digest unchanged. Each entry object SHALL carry exactly those six keys and no others, and each SHALL carry a **resolved effective value** of its declared type rather than the literal text of the declaration: no key is ever absent and no value is ever JSON `null`, so an entry declaring no `matcher` contributes `""` and one declaring no `timeout_seconds` contributes the resolved default of REQ-HOOKS-008 as a JSON number. Two declarations that would run identically therefore hash identically. Because a resolved default is part of the hashed document, changing the value of any default of REQ-HOOKS-008 that reaches this document SHALL be accompanied by raising `version`; a default changed without that would invalidate every stored decision while leaving the review unaware it had been reopened. This requirement is the product's single definition of the workspace hook fingerprint — the digest algorithm, the canonical document it is taken over, the six fields, the resolved-value rule, and what does and does not change the digest: a document that stores, compares, or displays a hook-set digest SHALL cite this identifier rather than restating any of them.

- **REQ-HOOKS-092** — The first encounter with an unapproved workspace that declares hooks SHALL withhold those hooks and make a review request pending, carrying the fully resolved absolute workspace path with symbolic links followed, the fingerprint of the pending set, and exactly the workspace-declared hooks in declaration order — entries with `enabled: false` included, matching the fingerprinted list of REQ-HOOKS-091, and marked as currently inert so the user can see which of the commands under review would not run as things stand. No review is pending when the workspace declares no hooks, or when a stored decision — approval or rejection — already covers the current set.

- **REQ-HOOKS-093** — Decision lifecycle:
  - Approving lets the workspace hooks run on later loads and clears the pending review.
  - Any change to the workspace hook set (rewriting, adding, removing, reordering) invalidates the decision: the hooks are withheld again and a fresh review with a new fingerprint becomes pending. An approval granted for one set therefore confers nothing on a command that has since been altered, nor on an entry added beside it.
  - A rejection persists: it is stored, it keeps withholding, and the user is not asked again while the set is unchanged; the question returns once the hooks change.
  - Clearing the decision re-applies the gate immediately; clearing when none is stored is harmless (a file that is not there is treated as success), while a removal that fails for any other reason SHALL surface as an error — an approval that survives an attempted revocation would keep letting hooks run.

- **REQ-HOOKS-094** — Reading a stored decision SHALL default to "not approved" and SHALL never fail outright: a missing file or state directory, unparsable JSON, a truncated file, JSON whose top level is the wrong type, an empty object, a missing fingerprint, a fingerprint that is not 64 hex characters, a `trusted` value that is not strictly a boolean (a number or a string is never taken as consent), a decision timestamp that cannot be parsed, an unrecognized version, or finding a directory at the path the file was expected at — each of these reads as "no decision", hence not approved. A decision timestamp with no timezone is taken as UTC.

- **REQ-HOOKS-095** — A decision recorded against one hook set SHALL NOT carry over to a different one: where the stored fingerprint and the computed fingerprint differ, the hooks are withheld. Transplanting a `.rotaris/` state directory from a checkout whose hooks were approved into a checkout whose hooks are different therefore confers no permission on the latter.

- **REQ-HOOKS-096** — A decision SHALL be stored at `<workspace>/.rotaris/hook-trust.json` as a JSON object carrying exactly the four keys `version` (the value `1`), `digest` (the fingerprint of REQ-HOOKS-091, 64 lowercase hexadecimal characters), `trusted` (a strict boolean) and `decided_at` (a timezone-aware UTC ISO-8601 timestamp), serialized with sorted keys, two-space indentation, and a single trailing newline. This requirement is the product's single definition of the trust decision file — its path, its four keys, and its serialization: a document that reads, writes, or presents a stored hook trust decision SHALL cite this identifier rather than restating any of them. Writing a decision SHALL: check the shape of the fingerprint first (reporting `Not a hook-set digest: ...` and writing nothing if it is malformed); create the `.rotaris` directory if it is absent; write the file atomically; and report any write failure rather than absorb it — a caller that wrongly believed a rejection had been persisted would go on invoking the very hooks the user declined.

- **REQ-HOOKS-097** — The workspace SHALL be reduced to an absolute path with symbolic links followed before the decision file is located, so an approval granted under an absolute path still applies when the same workspace is later referred to as `.`. The set permitted to run SHALL be exactly the in-memory sequence that was fingerprinted, with no reload between fingerprinting and permitting. The disk is consulted only when that sequence actually contains workspace hooks.

### Scope Fallback on Refusal

- **REQ-HOOKS-098** — Substitution of one scope's list for another's SHALL apply only among trusted scopes. Where workspace hooks were withheld, the global and default entries that their list had displaced SHALL be put back into the permitted set — but only entries whose own scope is always trusted, so that a displaced workspace-scoped list cannot regain execution by way of this fallback. Reinstated entries are appended after the permitted entries, keeping the relative order they held in the scope they came from. An entry is not added a second time: an inherited entry counts as already present both when its stable id is already permitted and when a permitted entry carries the same `event`, `matcher`, `command`, `required` and `timeout_seconds` compared after the resolution REQ-HOOKS-091 applies, the `name` playing no part in that comparison — a hook re-declared under a different name still runs the same command on the same event, and running it twice is what this rule exists to prevent. The gate's result exposes the permitted set (originally permitted, then reinstated, in declaration order), the withheld set, the reinstated set, and a notice string.

- **REQ-HOOKS-099** — Reinstatement follows from withholding and is not a lasting merge: once the user approves the workspace list, it substitutes for the inherited one in full (withheld and reinstated sets both empty, notice empty).

- **REQ-HOOKS-100** — End-to-end guarantee: given an unapproved workspace whose hook list is hostile, no process is started for the repository's hook; a `pre_tool` guard declared in global scope still stops the command it was written to stop; a `session_end` hook declared in global scope still fires; and the notice the user sees names neither, giving only how many were withheld and which configuration file declared them.

### Untrusted-Hooks Notice Hygiene

- **REQ-HOOKS-101** — The withheld-hooks notice SHALL be the empty string when nothing was withheld; otherwise exactly: `Skipped <N> hook(s) declared by this workspace's .rotaris/agents.yaml: workspace hooks run shell commands and this workspace has not been reviewed and trusted yet. Review the hooks in Rotaris to allow them to run.` — with singular and plural forms used correctly ("1 hook", never "1 hooks"). Where reinstatement returned the user's own hooks, the notice gains: ` Your own <M> configured hook(s) still run(s).` (singular/plural on both the noun and the verb).

- **REQ-HOOKS-102** — Notices and diagnostics about withheld hooks SHALL disclose only how many hooks were withheld and the path of the configuration file that declared them (plus the counts and workspace path of REQ-HOOKS-086). The `name` and the `command` of a withheld workspace hook SHALL appear on none of these surfaces: the notice text, the hooks settings tab and every other window of the desktop interface, the application log, the session's issue record, its timeline, anything exported from either (REQ-SESSION-199), and the session event stream. Given an entry whose `name` embeds an ANSI escape sequence that clears the terminal and whose `command` pipes a download into a shell, no escape byte, no fragment of that command, and no host name taken from it SHALL be present in any of them. The review dialog of REQ-HOOKS-106, which the user opens deliberately, is the only surface on which that text is displayed. The conflict with the `hook_name` field REQ-HOOKS-123 places on every `hook.start` and `hook.finish` SHALL be resolved in favour of this rule: the `hook.finish` announcing a withheld hook (REQ-HOOKS-126) carries that hook's stable id in `hook_name` — never its configured display name, and never an empty string — so the field stays populated and correlatable while no text the repository wrote ever leaves the gate.

### Desktop Settings and Review Dialog

- **REQ-HOOKS-103** — The hooks settings tab SHALL present a tree table whose accessible name is `Lifecycle hooks`, holding one top-level row per owning agent — `Rotaris` for this product's own hooks and `Claude Code` for imported ones, corresponding to the agent ids `rotaris` and `claude-code` of REQ-HOOKS-115 — with that agent's hooks as child rows. Each hook row SHALL show, in this column order: name, event, matcher — rendered as `every matching call` where the matcher is empty — source, and status. The source column SHALL render the entry's declaring scope (REQ-HOOKS-014, REQ-HOOKS-020) as a human-readable label rather than as the raw scope value, so that a user reads where a hook came from — the workspace, their own global configuration, or the built-in defaults — without having to know the vocabulary; the exact wording of those labels is left to the implementation. The status column SHALL carry exactly one of `inactive`, `disabled by agent`, `disabled`, `blocked — not reviewed`, `active`, selected by taking the first condition that applies in the order that vocabulary is listed: `inactive` where the hook cannot run for a reason declared in configuration rather than chosen on this tab — `hooks.enabled` is `false` (REQ-HOOKS-009, REQ-HOOKS-017), or the entry's own `enabled` is `false` (REQ-HOOKS-008), or the row is an imported record discovery marked unusable (REQ-HOOKS-113); `disabled by agent` where the row's owning agent toggle in the external-hooks policy file is `false` (REQ-HOOKS-115, REQ-HOOKS-116); `disabled` where that agent toggle is on but the row's own per-hook toggle is `false`; `blocked — not reviewed` where a workspace-scoped hook was withheld by the trust gate; and `active` where none of the four applies. A workspace hook the trust gate withheld therefore shows `blocked — not reviewed`, and shows `active` once the workspace is approved and nothing else suppresses it.

- **REQ-HOOKS-104** — The tab SHALL offer a "Review workspace hooks" button that opens the review dialog, together with a summary label describing the current decision ("not been reviewed" before any decision; "will not run" after a rejection) and a notice pointing at the pending review (its title contains "unreviewed"); the dialog never opens on its own. The tab SHALL also offer a control that re-reads the hook sources and re-projects the table, so that a hook added to a configuration file or to the external agent's settings while the application is open becomes visible without a relaunch; re-reading SHALL start no hook process and SHALL change no decision, and it governs runs started afterwards on the terms of REQ-HOOKS-131. Command text SHALL NOT appear anywhere else in the window — not in the table, in tooltips, in notices, or in accessible descriptions.

- **REQ-HOOKS-105** — The trust summary the settings surfaces work from SHALL report, for the workspace it was asked about: the workspace path; a status drawn from `none`, `review`, `trusted`, `refused`; the current workspace fingerprint (REQ-HOOKS-091); one entry per hook stating whether the gate permitted or withheld it; the workspace-declared hooks awaiting review; and the trust notice text of REQ-HOOKS-101. The status SHALL be `none` where the workspace declares no hooks, `review` where it declares hooks no stored decision covers, `trusted` where a stored approval matches the current fingerprint, and `refused` where a stored rejection matches it. Hooks reinstated under REQ-HOOKS-098 SHALL be reported as permitted even though the workspace's own list had displaced them, so that the summary describes what will actually run. Hook text in the summary SHALL be masked per REQ-HOOKS-133. A configuration that cannot be read SHALL yield a summary carrying no hook entries rather than an error, and that summary SHALL report status `none`: nothing could be read, so nothing can run, and REQ-NOTIFY-227 closes the hook-trust vocabulary at four statements and admits no fifth. In that state the settings tab SHALL show no hook rows and SHALL raise no pending-review notice, and the read failure SHALL degrade to a log entry in the manner of REQ-HOOKS-121 rather than becoming a warning of its own.

- **REQ-HOOKS-106** — The review dialog SHALL be modal, SHALL be titled `Review this workspace's hooks`, and SHALL be at least 620×440 logical pixels in size — the unit REQ-SHELL-022 uses for every window dimension in this product, so the minimum holds as the same physical area at every display scaling factor (REQ-SHELL-030). It SHALL state the workspace path; SHALL state how many hooks the workspace declares and that they are declared in `.rotaris/agents.yaml`, worded correctly for that count so an `N` of 1 reads in the singular and no `hook(s)` construction is emitted literally (REQ-HOOKS-054, REQ-HOOKS-101); and SHALL state that the entries are shell commands supplied by the repository's authors that will run on this machine under the user's own account. Each hook SHALL be rendered read-only in a fixed-width block carrying its name, its event, `matches` followed by the matcher (or `every tool call` where the matcher is empty), `timeout <n>s` annotated `(blocks the tool call on failure)` where `required` is true and `(advisory)` otherwise, and the command exactly as written — no re-wrapping, escaping, abbreviation, or styling that would let the displayed text differ from the text that will execute. An entry declared with `enabled: false` SHALL be shown too, marked as currently inert (REQ-HOOKS-092). This dialog SHALL be the only surface in the product that displays a hook command (REQ-HOOKS-102).

- **REQ-HOOKS-107** — Dialog buttons SHALL be "Do not run these hooks" (reject role, the default, holding initial focus and activated by Enter) and "Allow these hooks" (styled to signal risk, requiring an explicit click), each with an accessible description of what it will do. Leaving without choosing counts as rejection: Escape, the window close control, and any other dismissal all resolve as not approved. However the dialog is left, it SHALL report its decision once and only once — the first exit path taken is the one that reports. A failure to write the decision is shown as an error label in the dialog rather than passing unnoticed.

- **REQ-HOOKS-108** — Whole-flow guarantees: rejecting writes `trusted: false` to the workspace decision file and does not ask again on reload; approving writes `trusted: true`, the tab moves the row to `active`, and the summary status becomes `trusted`.

- **REQ-HOOKS-109** — Agent rows and hook rows in the tab SHALL carry checkboxes; clearing one is saved to the global external-hooks policy file, persists across a refresh of the tab, and never alters the external agent's own settings file. A change made while a run is under way SHALL take effect for runs started afterwards and SHALL NOT alter the hook set of the run already executing (REQ-HOOKS-131); the tab SHALL convey that, so a user clearing a checkbox mid-run is not left believing a hook has just been stopped.

- **REQ-HOOKS-136** — The hooks settings tab SHALL be the product's one venue for granting, refusing, and revisiting a workspace's hook trust decision, and every transition of REQ-HOOKS-093 SHALL be reachable from it. Given a workspace with a stored decision of either kind, the tab SHALL offer a control that clears that decision; activating it SHALL remove the stored decision, SHALL re-apply the gate immediately so the summary status of REQ-HOOKS-105 returns to `review` where the workspace declares hooks and `none` where it does not, and SHALL leave those hooks withheld until the user allows them again. Given no stored decision, the control SHALL be absent or inert, and clearing when none is stored SHALL be harmless. A clear that fails for any reason other than the decision file already being absent SHALL be reported on the tab as an error rather than absorbed, for the reason REQ-HOOKS-096 gives. Opening the review dialog again while a decision is stored SHALL present the current workspace hook set exactly as REQ-HOOKS-106 requires and SHALL replace the stored decision with whichever the user then takes. No other surface of the product, and no configuration key, preference, or environment variable, SHALL be able to approve a workspace's hooks.

- **REQ-HOOKS-137** — The hooks settings tab SHALL show the hook invocations of the session the user is looking at, so that the command output the advisory of REQ-HOOKS-054 and the issues of REQ-HOOKS-120 point at is reachable without leaving the application. For each invocation, in the order the invocations happened, it SHALL show: the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); the event; the tool name where there is one; the exit status as the timeline records it (REQ-HOOKS-119, so `-1` where the hook produced no exit status); the elapsed duration; whether the invocation timed out; whether it stopped the call; and the captured standard output and standard error, masked per REQ-HOOKS-133 and already limited per REQ-HOOKS-037. A hook the trust gate withheld SHALL appear as withheld with its reason, identified by stable id and without its command (REQ-HOOKS-102). A hook switched off by the failure budget SHALL be shown as switched off after its last recorded invocation. A session with no invocations SHALL show an explicit empty state rather than a blank area. The list is read-only: opening it SHALL start no process, publish no wire event, and write nothing to the session's diagnostics.

- **REQ-HOOKS-138** — The surfaces on which hook activity reaches a user SHALL be exactly these and no others: the notice channel (REQ-HOOKS-054, REQ-HOOKS-085, REQ-HOOKS-086, and the notices REQ-NOTIFY-223 to REQ-NOTIFY-228 define); the hooks settings tab (REQ-HOOKS-103 to REQ-HOOKS-105, REQ-HOOKS-136, REQ-HOOKS-137) and the review dialog it opens (REQ-HOOKS-106); the session's durable diagnostics (REQ-HOOKS-118 to REQ-HOOKS-120); the session event stream (REQ-HOOKS-123 to REQ-HOOKS-127); and the application log. A hook invocation SHALL NOT be written into the run's transcript, into an agent's activity text, or onto any other live run surface: a hook is the user's own code and its execution is not part of what an agent did. The only hook text ever placed in front of an agent is the refusal of REQ-HOOKS-049 and the feedback of REQ-HOOKS-051, and neither is a user-facing surface.

### External-Agent Hook Import (Claude Code)

- **REQ-HOOKS-110** — Discovery SHALL read the user-level Claude Code settings JSON — by default `~/.claude/settings.json`, which the environment variable `ROTARIS_CLAUDE_SETTINGS_PATH` can point elsewhere — and SHALL only ever read it (the file is byte-for-byte unchanged after any toggling in the interface). A problem reading it yields no records plus one of: `Claude Code global settings were not found.` / `Claude Code hooks could not be read: <err>` / `Claude Code global settings contain no hook declarations.`

- **REQ-HOOKS-111** — Event mapping SHALL be: `PreToolUse` → `pre_tool`, `PostToolUse` → `post_tool`, `SessionStart` → `session_start`, `SessionEnd` → `session_end`, `SubagentStop` → `child_completed`. Any other external event produces a record marked unusable with the explanation `The Claude Code <event> lifecycle event has no Rotaris equivalent.`

- **REQ-HOOKS-112** — Tool-matcher mapping (for the two tool events only): empty or `*` selects all tools; otherwise the matcher is split at `|` and `,` into selectors, each selector is mapped to a set of this product's tool names — `Bash` → {`terminal`}, `PowerShell` → {`terminal`}, `Read` → {`read_file`, `haet_read`}, `Edit` → {`haet_edit`}, `Write` → {`write_file`} — and the union of those sets becomes the imported hook's set of tool names (matched exactly, per REQ-HOOKS-023). Surrounding whitespace on a selector is ignored, and an empty selector between two delimiters contributes nothing. A matcher containing any regular-expression metacharacter (`^ $ . * + ? [ ] ( ) { } \`) is unusable (`Regular-expression matchers are unavailable in Rotaris.`), as is a selector that is not recognized (`Claude Code tool selector '<x>' has no Rotaris equivalent.`).

- **REQ-HOOKS-113** — Every unusable record SHALL remain visible with its explanation rather than being dropped silently. Further explanations: a handler that is not a command handler (`<type> handlers are unavailable in Rotaris.`), a blank command (`The command handler has no command.`), an `if` predicate (`` Claude Code `if` predicates require tool arguments that Rotaris does not expose here. ``), a timeout that cannot be parsed (`The command handler timeout is invalid.`), and a timeout of zero or less (`The command handler timeout must be positive.`).

- **REQ-HOOKS-114** — A usable record SHALL become an effective hook with: display name `Claude Code <event>`, `<event>` being the external event name; the event it maps to under REQ-HOOKS-111; an empty matcher string; the command exactly as declared externally; the handler's timeout in seconds, or `60` where the handler declares none; `required = false`; scope `external:claude-code`; the set of tool names derived under REQ-HOOKS-112; and a stable identity `claude-code:` followed by 20 hexadecimal characters taken from a SHA-256 digest over the record's identifying facets — agent id, source path, event, external matcher, the handler's canonical JSON, the index of the handler group, and the index of the handler within that group. Observable consequences: rediscovering the same unchanged file yields the same identity every time; changing any one of those facets yields a different identity; and two otherwise identical handlers at different positions in the file have different identities. Stability across independent implementations is not required — a policy file (REQ-HOOKS-115) records one installation's choices and is not a portable document — but the identity SHALL nevertheless be fully determined rather than left to an implementation's convenience. The digest input SHALL be the UTF-8 encoding of the canonical JSON document `{"agent": "<agent id>", "event": "<external event name>", "group_index": <n>, "handler": <the handler exactly as declared, canonicalized the same way>, "handler_index": <m>, "matcher": "<external matcher>", "source": "<absolute source path>"}` with keys sorted, compact separators, and ASCII escaping; the identity is `claude-code:` followed by the first 20 characters of the SHA-256 digest of those bytes, rendered in lowercase hexadecimal.

- **REQ-HOOKS-115** — The global runtime policy SHALL live at `<config-dir>/external-hooks.json`, where `<config-dir>` is the value of the environment variable `ROTARIS_CONFIG_DIR` when that variable is set to a non-blank value (leading and trailing whitespace ignored, `~` expanded) and otherwise the per-user global configuration directory of REQ-CONFIG-001, which resolves per platform. It is stored as JSON `{"version": 1, "agents": {<agent-id>: bool}, "hooks": {<record-id>: bool}}`, with keys sorted, two-space indentation, and an atomic write. A policy file that cannot be read or does not parse loads as empty, meaning everything is on. Any agent or hook not mentioned defaults to on. A hook is on when both its agent toggle and its own toggle are on, so switching an individual hook off survives switching its whole agent off and on again.

- **REQ-HOOKS-116** — The same policy file SHALL also govern this product's own hooks, which are grouped under the agent id `rotaris` (imported ones under `claude-code`): a native hook is skipped when either the `rotaris` agent toggle or an entry under its own stable id is `false`. The run's hook set is assembled as the surviving native, trust-gated hooks in declaration order, followed by the enabled imported hooks.

- **REQ-HOOKS-117** — When a run's hook set is assembled, only records that are usable and switched on are placed in it, and that set is then fixed for the run (REQ-HOOKS-131); an imported hook that is selected runs through the ordinary engine and receives the native payload shape, while one that is switched off never starts a process. The workspace trust gate does not apply to imported hooks — the settings toggles are how the user consents to them — and their scope value would in any case be withheld as unrecognized if it ever reached the gate.

### Persistence, Audit, Diagnostics

- **REQ-HOOKS-118** — A snapshot of the effective hook set SHALL be recorded once at session start into the session's launch audit (REQ-SESSION-138), as `"hooks": [ {hook_id, name, event, matcher, source, command}, ... ]` covering the enabled resolved set, with each command stored masked. The masking is not a property of where the record is kept and does not lapse because it is a record rather than a file: a hook command line often contains a credential, and the audit outlives the run, is readable by anything that can reach the store, and is carried into whatever is exported from the session. A credential must therefore never be written into it in the first place. Editing the configuration afterwards cannot alter this record. A run with hooks switched off, or with none at all, records an explicit empty list, so that an auditor can distinguish "there were no hooks" from "this was not recorded"; entries that are switched off do not appear.

- **REQ-HOOKS-119** — Every completed invocation SHALL add one `hook_run` entry to the session's timeline (REQ-SESSION-134): `severity` = `warning` where the outcome carried a warning and `info` otherwise; `actor` = the hook's display name; `message` = `Hook '<name>' (<event>) exited <exit_code> in <duration_ms> ms` (with `<exit_code>` rendered as `-1` where the hook produced no exit status, per REQ-HOOKS-036); `metadata` = `{hook_id, hook_name, event, source, exit_code, duration_ms, timed_out, blocked}` — `exit_code` here likewise carries `-1`, not `null`, for that state — plus `tool_name` where there is one and `stdout` / `stderr` only where non-empty (already limited to 16 KiB each under REQ-HOOKS-037, and masked under REQ-HOOKS-133 before being recorded, since a timeline entry outlives the run, is readable by anything that can reach the store, and is carried into the export of REQ-SESSION-199). Entries appear in the order the invocations happened.

- **REQ-HOOKS-120** — Every outcome carrying a warning SHALL additionally record an issue in the session's issue record (REQ-SESSION-135): kind `hook_failure`, severity `warning`, actor = hook name, message = the warning text, with the same metadata. A guard that legitimately stopped a call records nothing. Hooks withheld by the gate are recorded under kind `hook_trust` (REQ-HOOKS-086).

- **REQ-HOOKS-121** — The durable diagnostics entry SHALL be written before the corresponding completion event is published, so that an event lost on the stream does not also take the evidence of the invocation with it. Where the diagnostics directory cannot be written to, the entry degrades to a log line instead: the trail is kept wherever keeping it is possible, and its loss never interferes with the run.

- **REQ-HOOKS-122** — Hook processes SHALL be exempt from the tool permission policy and from any sandbox: they are the user's own code, executing directly on the host. Nothing else in the system observes them, so the diagnostics written under REQ-HOOKS-118 to REQ-HOOKS-121 are the sole evidence that a hook executed at all — which is what those requirements exist to guarantee.

### Wire Events

- **REQ-HOOKS-123** — Two event types SHALL exist on the session event stream: `hook.start` and `hook.finish`, both carrying `hook_id`, `hook_name`, `lifecycle_point` (the hook event name), `scope` (the configuration source, which for an imported hook is `external:claude-code`, REQ-HOOKS-114), and `tool_name` (empty for lifecycle hooks). `hook_name` carries the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); on the `hook.finish` announcing a hook the trust gate withheld it carries the stable id whatever the configuration says (REQ-HOOKS-102, REQ-HOOKS-126).

- **REQ-HOOKS-124** — `hook.start` SHALL additionally carry `command`, holding the configured command with the masking of REQ-HOOKS-061 applied; an unmasked hook command line SHALL never appear on the stream. For every invocation the `hook.start` SHALL become observable before that invocation's `hook.finish` and before any effect the hook process has, so that a consumer reading the stream while a hook is still occupying its budget sees the `hook.start` with no `hook.finish` yet paired to it. `hook.start` has no counterpart in the durable diagnostics, which record completed invocations only (REQ-HOOKS-119).

- **REQ-HOOKS-125** — `hook.finish` SHALL carry `exit_code` (integer or `null`, with the no-exit-status state always appearing as `null` here), `duration_ms` (number or `null`), `blocked` (which can be true only for `pre_tool`), `timed_out`, `skipped`, `skip_reason`, and `output` = standard output and standard error, each trimmed and each limited to 16 KiB, joined with `\n` and masked as part of constructing the event; they are joined because a refusal reason arrives on standard error while ordinary output arrives on standard output.

- **REQ-HOOKS-126** — A hook the trust gate withheld SHALL produce only a `hook.finish`, with `skipped = true`, `skip_reason = "untrusted_workspace"` (the only defined reason), null `exit_code` and `duration_ms`, and `hook_name` carrying the hook's stable id rather than its configured display name (REQ-HOOKS-102, REQ-HOOKS-123); no process existed, so no `hook.start` accompanies it. The reason for emitting anything at all is that a configured hook absent from the stream could not be told apart from one that ran and had no effect.

- **REQ-HOOKS-127** — Each hook the trust gate withheld SHALL be announced exactly once per session as one `hook.finish` of the shape given in REQ-HOOKS-126, however many tool calls and lifecycle points follow in that session and however many times the announcement is triggered. The announcement SHALL be observable no later than the session's first hook-related event, so a consumer attached from the start of the session sees every withheld hook before the first `hook.start`. Triggering the announcement again SHALL add no further events to the stream.

- **REQ-HOOKS-128** — Publishing to the stream SHALL be attempted but not depended upon, and SHALL be isolated from the rest: a broken stream or an event that cannot be constructed reduces to a log entry and never causes a hook to be skipped, to fail, or to run twice. The error path for a withheld-hook publication logs the hook id only and never the command, which at that point is still an unmasked shell command line.

### Cross-Cutting Invariants

- **REQ-HOOKS-129** — No hook-related condition SHALL end a run, alter its terminal status, or leave it waiting beyond the per-hook bound of REQ-HOOKS-033. Anything that goes wrong while executing a hook, building a payload, publishing a wire event, or emitting a notice SHALL reduce to a user-facing warning where REQ-HOOKS-052 defines one for it, and to a log entry in every other case; no other hook fault is surfaced to the user as a warning. The withheld-hooks notice (REQ-HOOKS-086, REQ-HOOKS-101), the switched-off advisory (REQ-HOOKS-054), and the start-up message of REQ-HOOKS-085 are notices about configuration rather than execution faults and are unaffected by this rule. The only hook outcome that changes what the run does is a `pre_tool` hook's stopping verdict (REQ-HOOKS-043, REQ-HOOKS-048), which refuses one tool call and nothing further (REQ-HOOKS-072).

- **REQ-HOOKS-130** — Every hook actually invoked for an event occurrence SHALL produce exactly one outcome, exactly one `hook_run` timeline entry, and exactly one `hook.start`/`hook.finish` pair: N occurrences of an event with one applicable hook produce N of each, never more and never fewer. Two cases produce fewer records by design: a hook the trust gate withheld produces exactly one `hook.finish` and nothing else — no outcome, no timeline entry, no `hook.start` (REQ-HOOKS-126); and a hook switched off by the failure budget produces none of them for occurrences after the switch-off (REQ-HOOKS-055). Records may also be absent where the durable trail could not be written (REQ-HOOKS-121) or the stream could not be published to (REQ-HOOKS-128); neither loss changes how many times the hook actually ran.

- **REQ-HOOKS-131** — The hook set resolved for a run SHALL be fixed when the run starts: configuration edited on disk while the run is under way SHALL NOT change which hooks run, nor the snapshot of REQ-HOOKS-118, nor the fingerprint the trust decision was checked against. Two within-session changes are defined, and both replace or remove whole entries rather than editing one: a session's attachment may be replaced in full, taking effect from the next tool call (REQ-HOOKS-069), and a hook may be switched off for the remainder of the session by the failure budget (REQ-HOOKS-055). A change to the external-hooks policy file (REQ-HOOKS-115, REQ-HOOKS-116) made while a run is under way SHALL NOT affect that run: the agent and per-hook toggles are read once, when the run's hook set is assembled, and never again, so clearing a checkbox governs runs started afterwards only (REQ-HOOKS-109, REQ-HOOKS-117). This is a third within-session change only in appearance; the run's set is unchanged by it.

- **REQ-HOOKS-132** — The stable hook id SHALL be unique within one loaded configuration, SHALL be unaffected by neighbouring entries being switched off, and SHALL be the key that links warnings, diagnostics files, wire events, the switched-off set, the desktop policy toggles, and the start-up snapshot to one another.

- **REQ-HOOKS-133** — Text drawn from configuration or from tool arguments SHALL be masked per REQ-HOOKS-061 and REQ-HOOKS-062 wherever it is carried. The channels that carry such text are exactly these six: the JSON payload on a hook's standard input, at every level of it (REQ-HOOKS-060); the `command` recorded for each hook in the launch audit (REQ-HOOKS-118); the `stdout` and `stderr` recorded in each `hook_run` timeline entry (REQ-HOOKS-119); the `command` field of `hook.start` (REQ-HOOKS-124); the `output` field of `hook.finish` (REQ-HOOKS-125); and the hook data reported by the desktop trust summary (REQ-HOOKS-105), which the invocation list of REQ-HOOKS-137 also displays. It follows that, given a hook whose command contains `--token ghp_example` and a tool argument containing `api_key=secretvalue`, neither `ghp_example` nor `secretvalue` SHALL appear in the payload the hook reads, in the launch audit, in the timeline, in anything exported from either, or in any event on the session stream.

- **REQ-HOOKS-134** — Directions of failure are fixed: reading a trust decision defaults to "not approved" when anything is wrong; failing to write a trust decision is reported rather than absorbed, since an absorbed rejection would leave hooks running; and a hook that fails to execute lets the agent carry on (warning, then proceed) — except a `required` pre-tool hook that returned no verdict, which stops the call.

### Performance Contracts

- **REQ-HOOKS-135** — Validating hook configuration (REQ-HOOKS-012), resolving the effective hook set (REQ-HOOKS-013 to REQ-HOOKS-018), computing a workspace fingerprint (REQ-HOOKS-091), and building a payload (REQ-HOOKS-063) SHALL each be possible with no run under way, and doing any of them SHALL leave every run untouched: no hook process is started, no wire event is published, no session diagnostics are written, and no run's hook set changes. Taken with REQ-HOOKS-041, REQ-HOOKS-073, and REQ-HOOKS-078, this bounds what a run does on account of hooks: a session with no hooks starts no process and writes no hook record for any event, and a session declaring hooks for one event builds payloads for that event alone. The numeric bounds are fixed by REQ-HOOKS-139.

- **REQ-HOOKS-139** — The numeric bounds of this domain SHALL be as follows, measured under one reference condition: a single execution thread on a contemporary developer workstation with a solid-state disk and a warm file-system cache, timing the named operation alone and excluding application start-up. Validating hook configuration (REQ-HOOKS-012), resolving the effective hook set (REQ-HOOKS-013 to REQ-HOOKS-018), computing a workspace fingerprint (REQ-HOOKS-091), and applying the trust gate (REQ-HOOKS-090) SHALL each complete within **50 ms** for a configuration declaring up to 100 entries across all scopes, and SHALL grow no worse than linearly in the number of entries beyond that. Building one payload (REQ-HOOKS-063) SHALL complete within **10 ms** for a payload carrying up to 100 KB of text after masking, growing no worse than linearly in the total length of the strings it carries. Deciding that an event occurrence has no applicable hook and returning (REQ-HOOKS-041, REQ-HOOKS-073, REQ-HOOKS-078) SHALL cost under **1 ms**, so a session with no hooks pays no measurable cost per call. The hooks settings tab and its status column (REQ-HOOKS-103), the trust summary (REQ-HOOKS-105), the review dialog (REQ-HOOKS-106), and the invocation list (REQ-HOOKS-137) SHALL each meet the product's interface responsiveness budget, measured from the user's gesture to the surface being usable. Nothing here bounds the wall-clock time spent inside a hook process, which is the user's own code and is bounded only by `timeout_seconds` and the grace period of REQ-HOOKS-033. This requirement is the product's single definition of the numeric bounds on hook work — the reference condition they are measured under, the 50 ms configuration bound at 100 entries, the 10 ms payload bound at 100 KB, and the 1 ms no-applicable-hook bound: a document that needs to state how fast any hook operation must be SHALL cite this identifier rather than restating a figure, and a new hook surface is added to this list rather than given a bound of its own. The interface responsiveness budget the hook surfaces meet is not this domain's own figure: it is the product-wide budget REQ-SHELL-150 fixes, which this requirement cites and holds no copy of, so the hook surfaces meet the same budget as every other surface rather than a budget of their own.

## Data & Formats

### Configuration (YAML)

Declared under `hooks:` in `agents.yaml` at either scope. The entry's field set, each field's type, whether it is required, and its default are fixed by REQ-HOOKS-008 and the event names by REQ-HOOKS-001; the block below illustrates them and adds nothing to them. Both spellings are equivalent:

```yaml
hooks:
  enabled: true            # feature on/off, default true
  entries:
    - event: pre_tool      # one of the seven event names
      command: "./check.sh"
      name: "Guard"        # optional display label
      matcher: "git push *" # optional; empty = every occurrence
      timeout_seconds: 60.0 # > 0; default 60.0
      required: false
      enabled: true
```

```yaml
hooks:                     # list shorthand
  - event: session_end
    command: "notify-send done"
```

Scopes: built-in defaults, then `agents.yaml` in the per-user configuration directory (global, REQ-CONFIG-001), then `<workspace>/.rotaris/agents.yaml` (workspace). Both directories are addressed by their current names only; no earlier or alternative directory name is looked for, adopted, or migrated from.

### Hook stdin payload (JSON, UTF-8, one object)

Tool events:

```json
{
  "event": "pre_tool",
  "tool_name": "terminal",
  "arguments": { "command": "git push origin main", "token": "***" },
  "session_id": "<id>",
  "workspace": "<absolute path>",
  "command": "git push origin main"
}
```

- `command` is `""` for tools with no shell command; for a file-editing tool the text matched against is the requested action name (`create`/`edit`/`overwrite`/`insert`/`undo`).
- Tools provided over MCP place their fields under `arguments.data`.
- `post_tool` adds `result`: `{"observation": "<text>"}` or `{"error": "<text>"}` (object or array; at most 4096 characters per text, with a truncation marker).

Lifecycle events: always `event`, `session_id`, `workspace`, plus that event's own top-level fields (REQ-HOOKS-075). Event data cannot replace those three base keys.

Every string at every level is masked by the shared redaction pass of REQ-TOOLS-171, over the key-name test of REQ-TOOLS-172, as REQ-HOOKS-061 and REQ-HOOKS-062 apply them to the payload.

### Trust decision file

The path, the four keys and the serialization are fixed by REQ-HOOKS-096; the block below illustrates them and adds nothing to them:

```json
{
  "decided_at": "2026-08-29T12:00:00+00:00",
  "digest": "<64 lowercase hex chars>",
  "trusted": true,
  "version": 1
}
```

`decided_at` is a timezone-aware UTC ISO-8601 value ending `+00:00`. Any file that is not exactly version 1 and correctly shaped reads as not approved (REQ-HOOKS-094).

The `digest` value is the workspace hook fingerprint of REQ-HOOKS-091, which is the single definition of the digest algorithm, of the canonical document it is taken over, and of what does and does not change it; this appendix holds no copy of any of them.

### External-hooks policy file

The path, the document shape and the toggle semantics are fixed by REQ-HOOKS-115 and REQ-HOOKS-116; the block below illustrates them and adds nothing to them. `<config-dir>/external-hooks.json`, where `<config-dir>` is `ROTARIS_CONFIG_DIR` when set to a non-blank value and the per-user global configuration directory of REQ-CONFIG-001 otherwise:

```json
{
  "agents": { "claude-code": true, "rotaris": true },
  "hooks": { "claude-code:<20 hex>": false, "workspace:0:pre_tool": false },
  "version": 1
}
```

Keys sorted, two-space indentation, trailing newline, atomic write; a missing or malformed file means everything on; ids not mentioned default to on; a hook runs when its agent and its own toggle are both on. Agent ids: `rotaris` for this product's own hooks, `claude-code` for imported ones.

### Session diagnostics

The records named below belong to the session and this domain fixes no path, file name or directory for any of them; where a session's record is held is REQ-SESSION-001's and REQ-SESSION-198's, and the closed set of files a session still keeps is REQ-SESSION-002's. What follows states only what this domain records into them. Each is reachable outside this application through the export of REQ-SESSION-199, which is why the masking rule of REQ-HOOKS-133 binds every one.

- The launch audit (REQ-SESSION-138): `"hooks": [ {hook_id, name, event, matcher, source, command}, ... ]` — enabled set only, commands masked, explicit `[]` when there are none.
- The timeline (REQ-SESSION-134): one `hook_run` entry per completed invocation (fields per REQ-HOOKS-119). `exit_code` is `-1` where the hook produced no exit status.
- The issue record (REQ-SESSION-135): `hook_failure` entries for outcomes carrying a warning; a `hook_trust` entry (metadata `blocked`, `restored`, `workspace`) when the gate withheld hooks.

### Wire events (session stream)

- `hook.start`: `hook_id`, `hook_name`, `lifecycle_point`, `scope`, `tool_name`, `command` (masked). Published before the process starts.
- `hook.finish`: the same identity fields plus `exit_code` (int|null), `duration_ms` (number|null), `blocked`, `timed_out`, `skipped`, `skip_reason` (`"untrusted_workspace"` is the only defined value), `output` (masked, standard output and standard error joined with `\n`).

### Environment variables

- `ROTARIS_CLAUDE_SETTINGS_PATH` — points at the external agent settings file (default `~/.claude/settings.json`).
- `ROTARIS_CONFIG_DIR` — points at the configuration directory used to locate `external-hooks.json`; when unset or blank that directory is the per-user global configuration directory of REQ-CONFIG-001.
