# Session Persistence, Resume, and Background Sessions — 1. Where a Session Is Stored

Part 1 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-001 – REQ-SESSION-202.

## Requirements

### 1. Where a Session Is Stored

- **REQ-SESSION-001** — A session's durable record MUST be reachable from the workspace the run was started against — the workspace the desktop window has open — together with the session id of REQ-SESSION-009. One workspace plus one session id MUST resolve to that one record from every view and every background worker in the application, and binding the run to a worktree MUST NOT move it: per REQ-SESSION-085 the worktree becomes the run's effective root and is what the state records as `workspace_root`, but the record stays anchored to the invoking workspace. The record lives in that workspace's durable session store, which is machine-local and is found through the workspace identifier rather than through a path (REQ-SESSION-197, REQ-SESSION-198). Exactly two kinds of session-derived data are held outside that session's **own record**: the improvement artifacts of REQ-SESSION-007, which are additionally reachable at workspace scope and are held at that scope in the same workspace store rather than in any session's record (REQ-LIBRARY-042), and the checkpoint refs of REQ-SESSION-162, which are objects in the user's own repository and outside any store this application keeps. The per-session files of REQ-SESSION-002 belong to the same record and are not a third kind.
- **REQ-SESSION-002** — Beside its stored record a session MUST have a place on disk holding exactly three kinds of file and nothing else: its log (REQ-SESSION-142), its human-readable summary (REQ-SESSION-140), and the bodies of the artifacts, attachments and images the session produced or received, which the record references and never holds inside itself. Each appears only once the matching activity has occurred and MUST NOT be assumed present by a reader — a session that produced no artifact has no artifact bodies, and a session whose logging never attached has no log. That set is closed, and closed deliberately: no other per-session file is written there, and in particular no file is ever written to signal anything to another process, which is what forbids a control channel over the filesystem into a session (REQ-SESSION-159). The place MUST be reachable through the reveal action of REQ-SESSION-191, MUST be held with the store rather than inside the workspace (REQ-SESSION-198), and MUST be removed with the session (REQ-SESSION-166).
- **REQ-SESSION-003** — *Withdrawn.* Every part of the split state layout it fixed is a record in the store rather than a file: the resumable state, the transcript rows, the edit diffs, the launch audit and the released transcript pages. Both guarantees it carried are held elsewhere and neither is lost — that a session created but never run carries no launch audit and loads with an empty configuration snapshot is REQ-SESSION-138's, and that released pages come to exist only once the resident window overflows is REQ-SESSION-131's and REQ-SESSION-192's.
- **REQ-SESSION-004** — *Withdrawn.* The evidence files it named are records in the store rather than files, and what it guaranteed by requiring them to exist from the first save — that a reader of a session that produced none of a given kind gets an empty answer rather than a failure — is REQ-SESSION-132's. The one name that survives as a file is the session log, fixed by REQ-SESSION-142 and opened by REQ-SESSION-191; the durable event history and the record of what a trim dropped are REQ-SESSION-143's and REQ-SESSION-144's.
- **REQ-SESSION-005** — *Withdrawn.* A clean-room product has no predecessor layout to fall back to, so a legacy whole-state document cannot exist; the stored resumable state is the only resumable state (REQ-SESSION-037).
- **REQ-SESSION-006** — The listing record (REQ-SESSION-030) and the human-readable summary (REQ-SESSION-140) MUST both be derived, rebuilt from state on every save; a loader MUST take its facts from the session state and never from either. The summary stays a file precisely because nothing in the application reads it: it exists so a person can open it, and it is on no path a run waits for.
- **REQ-SESSION-007** — An improvement artifact referenced by the session state MUST remain retrievable in two ways that do not depend on each other: as that session's own artifact, and from the workspace-scoped improvement library, so that an artifact one session produced is available to a later run in the same workspace. Both retrievals MUST survive resume, and neither may fail because the other was used. Whether the body is held once and referenced twice or held twice is not observable and is not fixed here; what is fixed is that deleting the session removes the session's own reference and never reduces the workspace-scoped library (REQ-SESSION-166).
- **REQ-SESSION-008** — *Withdrawn.* The alias existed only for compatibility with a predecessor layout this product does not have; reaching the session log is a desktop capability and is carried by REQ-SESSION-191.
- **REQ-SESSION-197** — A workspace MUST carry a stable identifier of its own, written into the workspace's `.rotaris/` beside the configuration the user edits, in a form a person can read and version control can track. It MUST be minted once, when the product first prepares the workspace, and MUST NOT change afterwards for any reason — not when the workspace is moved, renamed, copied, or carried through a synchronising folder, and not when it is opened by a different version of this product. It is the workspace's name for its durable session store (REQ-SESSION-198), which is located by that identifier and never by the workspace's path, so moving or renaming a workspace folder preserves its session history and a workspace found at a new path is the same workspace. Three consequences MUST hold, and all three are intended. Because the identifier travels with the workspace while the store does not, the same workspace opened on two machines resolves to two stores and each machine keeps its own session history (REQ-SESSION-198). Because the identifier is the only thing binding a workspace to its sessions, the product MUST NOT mint a replacement over an identifier it can read, and MUST report an identifier it cannot read as a condition to be resolved rather than overwriting it — overwriting it would silently orphan every session recorded under it. And a workspace whose store holds nothing for this identifier lists no sessions, which is an ordinary state and not an error (REQ-SESSION-043). **One narrow exception, and only one.** The restore of REQ-SESSION-201 MAY establish this workspace's identifier as the identifier the artifact carries, and no other action ever may. It exists because the identifier file need not travel with a user's version control, so on the recovery journey the backup was minted for — the machine is gone, the repository is cloned onto another one, the workspace is opened once, and the artifact is then restored — the freshly prepared workspace has already minted an identifier of its own while the artifact carries the original, and the restored sessions would land in a store the open workspace can never resolve to, with editing a file by hand as the only remedy. Five conditions bind the exception, and it is unavailable unless every one of them holds. **Only there.** It is available only inside the restore action of REQ-SESSION-201; no other path gains it, ever — not opening or preparing a workspace, not the explicit repair of REQ-SESSION-060, not a migration, not an update, and not a later convenience however similar the situation looks. **Only on explicit confirmation.** It MUST require the user to confirm it, and the confirmation MUST name both identifiers — the one this workspace carries now and the one the artifact was taken from — and MUST state that the sessions this workspace's own store holds become unreachable from this workspace once it is done. It MUST never happen automatically, MUST NOT be the default or the pre-selected outcome, and reporting the mismatch and going no further MUST remain a correct outcome of the restore. **The absent case is not this exception.** Where the workspace carries no identifier at all, the restore establishes one exactly as first preparation does, by a create that succeeds only where nothing is there to replace, and no confirmation of this kind is required or offered — establishing an identifier where none exists replaces nothing and orphans nothing. **An unreadable identifier is still reported and never overwritten.** An identifier that is present but cannot be read MUST be reported as a condition for the user to resolve, by this action as by every other; the exception is for an identifier the product can read and can therefore name to the user, and is not a repair for one it cannot. **The displaced store is kept.** The store the replaced identifier named MUST be moved aside and retained, never deleted, and the confirmation MUST say that it is kept and where it went, so that a user who confirms this and then finds they meant something else still has their history. **Why the exception is confined, and not merely that it is.** The rule it is an exception to is what keeps a workspace's sessions attached to it when its folder is moved, renamed, copied, or merely spelled differently — the ordinary and frequent way products of this kind lose a user's history, and the whole reason this requirement binds sessions to an identifier rather than to a path. That protection earns its place on every path a user takes, and the recovery it makes awkward arises once in a workspace's life if it arises at all. So the recovery is paid for exactly once, inside a single action a person asked for and confirmed in as many words, rather than by relaxing the rule generally — which would trade a protection that applies constantly for a recovery that applies rarely. An implementation that finds this exception useful anywhere else has drawn the wrong lesson from it.
- **REQ-SESSION-198** — The durable session store for a workspace MUST be machine-local: held in the per-user location REQ-STARTUP-145 fixes, never inside the workspace and never anywhere the workspace's own location may be synchronised or shared from. Which per-user location that is — the one local to this machine rather than the one a platform replicates to the user's other machines or to another copy of their profile — is REQ-STARTUP-145's to state and is cited here rather than restated, because a store this requirement relies on being one machine's own is not one machine's own the moment it is replicated to a second. This holds always, and MUST NOT be made conditional on detecting that a particular workspace is on shared storage: such detection is unreliable, and a second storage layout would be a second thing to get right on a path where being wrong costs a user their history. Four properties follow and MUST be observable. A workspace on a network share or in a synchronising folder MUST be fully usable — sessions start, run, are listed and are resumed there exactly as anywhere else. The user's own material — their repository, their requirement documents, their configuration, personas and model slots — MUST stay exactly where they put it and MUST be untouched by this rule. A session recorded on one machine MUST NOT appear on another, which is what makes a lock naming another machine evidence that something is wrong rather than an ordinary condition (REQ-SESSION-046, REQ-SESSION-048, REQ-SESSION-054). And the per-session files of REQ-SESSION-002 MUST be held with the store rather than inside the workspace, so that one session's record is never split across storage a synchronising client may reach and storage it may not. A store that cannot be opened is not worked around: no session in that workspace starts, and the condition is reported with its reason (REQ-SESSION-089).
- **REQ-SESSION-200** — Because the durable session store is machine-local (REQ-SESSION-198), backing up, copying, cloning or synchronising a workspace does **not** carry that workspace's session history with it, and the product MUST state that property itself rather than leave a user to infer it from an absence. What sits outside such a backup MUST be named rather than implied: every session record the store holds — the resumable state, the transcript rows and their released pages, the durable event history, the timeline, the issues record, the metrics document, and the evidence records with the permission audit among them — the workspace-scoped improvement library (REQ-SESSION-007), and the per-session files held with the store (REQ-SESSION-002), which are the session log, the summary, and the artifact, attachment and image bodies. What *is* carried MUST be named alongside it, because the statement is otherwise alarming rather than informative: the user's own material — their repository, their requirement documents, their configuration, personas and model slots — travels exactly as they left it; the workspace identifier travels with the workspace, so a workspace moved, renamed or restored on this machine finds its own sessions again (REQ-SESSION-197); and checkpoints are objects in the user's repository (REQ-SESSION-162). The statement MUST also convey where the two remedies are, since naming a gap without naming its fix is not a disclosure: the whole-store backup of REQ-SESSION-201 for carrying the store itself, and the exports of REQ-SESSION-189 and REQ-SESSION-199 for carrying individual records into a form other software can read. It MUST be reachable in the ordinary course of managing a workspace's sessions (REQ-SESSION-182), and MUST NOT be delivered only as part of a failure or a remediation message — a user who has already restored a workspace and found no history in it has been told too late, which is the precise failure this requirement exists to prevent. The wording is left to the implementation; what is fixed is what it conveys.
- **REQ-SESSION-201** — The application MUST offer a user-initiated action that produces one artifact holding the whole of a workspace's durable session store, and a second that restores such an artifact. **One artifact, the whole store.** The backup MUST cover everything that workspace's store holds — every session's record, and the workspace-scoped improvement library (REQ-SESSION-007) — together with the per-session files held with the store (REQ-SESSION-002), because those are equally outside anything a workspace backup reaches (REQ-SESSION-200). It MUST NOT reach outside that store: the repository, the requirement documents, the configuration, the personas and the model slots are the user's own material, are already where the user keeps them, and are not this artifact's to duplicate. The destination MUST be a file the user chooses through the platform's save dialog, with no implicit destination and nothing written until a destination is chosen (REQ-SESSION-189). **A backup in progress MAY be abandoned by the user, and abandoning it MUST cost nothing.** Abandoning it MUST discard whatever partial artifact had been produced, MUST leave the store exactly as it was, and MUST NOT leave a partial, truncated or otherwise unreadable file at the destination the user chose — a file that is there and cannot be restored is worse than no file, because a user who has one believes they have a backup. This is stated rather than left to follow from the mechanism: a backup of a large store is a multi-second action taken while runs continue, so a user will meet the question of whether they may stop one, and a requirement that enumerates what a backup does while saying nothing about stopping it leaves that case answered by nothing. Abandoning MUST NOT be confused with failing: a backup the user stopped is not a condition to report as a fault. **It is valid while runs are live.** Taking a backup MUST NOT require any session to be stopped, MUST NOT pause, delay, throttle or otherwise disturb a run, and MUST NOT be refused because a session is live. What it produces MUST be a state of the store that a reader could have observed at one moment: never a mixture of parts taken before and after a write, and never an artifact that restores to a store no run could have left behind. **Restore is explicit.** A restore MUST be an action a person takes deliberately; nothing may restore on its own — not at startup, not on finding an artifact, not as a repair, and not as a consequence of any other action. Before anything is changed the product MUST convey which workspace the artifact was taken from, when it was taken, and what the restore will do to the store that is there now. **Restore never silently merges.** A restore MUST NOT combine an artifact's contents with an existing store. Where the target store already holds sessions, what becomes of them MUST be an outcome the user chose while being told what it does to them; a session present in the target and absent from the artifact MUST NOT quietly survive, and one present in the artifact and absent from the target MUST NOT quietly appear, without that having been stated first. **Restore is refused rather than half-done.** A restore MUST be refused while any session in the target store is live (REQ-SESSION-159), for the same reason REQ-SESSION-164 refuses a checkpoint restore on a session that claims to be running: it would contend with writes from a run still recording itself. **That refusal holds for the whole of the restore and not only at the moment it is asked for.** It is not discharged by answering the question once and then proceeding on the answer: a session that becomes live after the question was answered and before the restore has finished is a session the user was never told about, so what becomes of it cannot be an outcome the user chose, and replacing it destroys a run on the strength of a fact that had already stopped being true. From the moment the product answers that question until the restore has completed or been abandoned, no session in the target store may become live; where one has, the restore MUST be refused rather than carried through. Whether the refusal of new runs is put in force before the question is asked, or the question is asked again once that refusal is in force, is left to the implementation — what is fixed is that there is no window between the two into which a run may be admitted. **A restore never disturbs a live session.** It MUST NOT stop, cancel, interrupt, or require a run that is under way to give up the store it is recording into; the obligation the backup carries not to pause, delay, throttle or otherwise disturb a run holds here too, and the restore's remedy on finding a live session is to refuse, never to clear it out of the way. A run that is asked to stand aside and whose record is then replaced has been destroyed by the restore whether or not it complied, which is the outcome this clause exists to make impossible. **A lock this machine cannot prove dead is reported, not treated as a live run, and MUST NOT make a store permanently unrestorable.** The refusal above exists because a run still recording itself would contend with the replacement; a lock record naming a machine other than this one is not such a run — nothing on this machine is writing under it, and by REQ-SESSION-198 the store is this machine's own, so such a record is the condition REQ-SESSION-048 describes rather than a run in progress. Where the target store holds such records, the restore MUST report them **together, as one condition covering all of them**, stating how many there are and what they mean, and the user MAY then confirm the restore and proceed; it MUST NOT require them to be cleared one at a time through REQ-SESSION-183 as a precondition, and MUST NOT simply refuse. Without this the requirements compose into a store that cannot be restored at all: such a lock counts as live by construction (REQ-SESSION-056), is never reaped (REQ-SESSION-047), and has one per-session confirmed release as its only remedy (REQ-SESSION-183) — so the recovery action a user reaches for when a store has gone wrong is blocked by exactly the records that recovery is about to replace. **The confirmation MUST state the risk rather than only the condition**: if that store genuinely is reachable from another machine, a run there may be writing now, and the restore replaces what it writes. Proceeding MUST be a choice the user makes having been told that, MUST NOT be automatic, and MUST NOT be the default or pre-selected outcome. This changes nothing about a lock naming **this** machine, which is a run in this application and is refused as before. A restore that fails for any reason MUST leave the store exactly as it was — there is no partly restored store, and no reader may observe one. **Nothing bounds how long a restore takes, and that silence is deliberate.** The backup carries timing obligations because it runs while sessions are live; the restore carries none because it cannot run while one is — by the clause above nothing in the target store is live for its duration to disturb, so there is no run whose progress a slow restore could damage and no budget this requirement owes. That absence is a decision rather than an omission, and it is not licence in the other direction: it does not permit a restore to run alongside a live session, which is precisely what is forbidden above. **A restore under way MUST be visible to the user who asked for it, and that is a separate obligation from its duration.** The absence of a duration bound is a statement about not disturbing runs; it says nothing about what a person waiting on the action is shown, and the two MUST NOT be collapsed. The request MUST be acknowledged within the gesture budget the shell carries for any other action (REQ-SHELL-150), and while the restore runs the product MUST convey that a restore is under way and that the workspace's sessions are unavailable until it finishes. **What is required is acknowledgement, not progress reporting.** No proportion completed, no list of stages, and no estimate of remaining time is required, and none may be represented as more precise than it is; a restore that reports stages would have to report from inside a sequence whose value is that it is indivisible, and nothing here may be read as licence to make that sequence interruptible in order to have something to report. The obligation exists because the interval scales with how much the store holds, and nothing in this product bounds that: no requirement caps how many sessions a workspace keeps or discards them with age. A workspace that answers nothing for several seconds is therefore a state this requirement permits, and it MUST NOT present as a product that has stopped responding. **The artifact names its workspace.** It MUST carry the workspace identifier it was taken from (REQ-SESSION-197), and a restore into a store belonging to a different identifier MUST be reported as what it is rather than performed silently, so a backup cannot be poured into the wrong workspace by accident. Where the two identifiers differ, and only here, the user MAY confirm that this workspace takes the artifact's identifier: that is the single exception REQ-SESSION-197 permits to its rule that an identifier the product can read is never replaced, every condition on it is stated there and binds this action, and it is what makes this action complete on the recovery journey it exists for — a machine lost, a repository cloned onto another, a workspace opened once, and the artifact then restored. Reporting the mismatch and going no further MUST remain available as the outcome, and no other action in this product may establish an identifier over one it can read. **It is not an export, and neither substitutes for the other.** This does not duplicate REQ-SESSION-199 or REQ-SESSION-189 and MUST NOT be collapsed into either: an **export** is a record rendered so that software knowing nothing about this product can read it, and is what discharges REQ-EVENTS-166; a **backup** is the store rendered so that this product can put it back, and discharges nothing about readability. Different artifacts, different purposes. The backup MUST NOT be offered as a way to read a record, and no export may be offered as a way to restore one. Nor does the artifact collide with REQ-SESSION-028's rule that no second, whole-state copy of a session is written anywhere: that rule governs what a *save* writes, and forbids the product keeping a duplicate the store could disagree with. This artifact is written only when a user asks for it, is never read back in place of the store, and is never consulted by anything the product does except a restore the user asked for. **It is not a channel.** Like the exports, the backup is a user-initiated action producing a file at the moment it is asked for: it MUST NOT refresh itself, MUST NOT be offered or usable as a way to observe a run in progress, and no surface may be built on repeating it (REQ-SESSION-071, REQ-SESSION-199). Finally, because the artifact is the store whole, it necessarily carries records that deliberately have no export because they hold unredacted user and tool content — the tool-call evidence of REQ-SESSION-136 among them. That is not a widening of what may be exported, because the artifact is not readable material handed to other software; but where this action is offered the product MUST convey that the artifact carries the store's contents in full, so that a user deciding where to put it decides knowing that.
- **REQ-SESSION-202** — Where this machine has a place for a workspace's durable session store and no store is in it, that MUST count as a store that could not be opened, and MUST NOT be treated as a workspace for which this machine holds no store (REQ-SESSION-043). The two look alike from outside and are not alike. A workspace this machine has never run has nothing kept for it at all; a workspace whose store has a place and is not in it has had something happen to it — a restore that failed part way (REQ-SESSION-201), a copy or a move interrupted before it finished, a deletion that took part of what it found, or a person tidying by hand — and which of those it was is not knowable afterwards. The condition persists until something resolves it, and it is stated here rather than left to the mechanisms that produce it, because closing one route to it does not close the others. **The product MUST NOT put a new store there, and MUST NOT report the workspace as holding no sessions.** Either would replace an unknown with a silent fresh start: whatever sessions the workspace had, if it had any, become unreferenced, and the user is told by an empty list that this workspace has no history on this machine — learning otherwise, if ever, long after the moment they could have acted. That is the harm REQ-SESSION-197 forbids one level up, where an identifier the product can read is never minted over and an identifier it cannot read is reported as a condition for the user to resolve rather than overwritten; the same rule governs the store that identifier names. **It is reported and refused as any other store that cannot be opened is.** No session in that workspace starts (REQ-SESSION-198, REQ-SESSION-089, REQ-EVENTS-084), the listing reports the condition rather than an empty list (REQ-SESSION-043), and what is reported MUST say what was actually found — that the place for this workspace's store exists and the store is not in it — because there is no store present to give a reason of its own, so the store's own reason that REQ-SESSION-089 otherwise carries unaltered does not exist for this condition and MUST NOT be invented. **The product MUST NOT resolve it by itself.** An action that establishes a new store in that place MUST be one the user takes deliberately, having been told what was found and that it recovers nothing that may have been there; it MUST NOT be automatic, MUST NOT be the default or pre-selected outcome, and MUST NOT be reached as a side effect of starting a run, opening or preparing the workspace, or repairing anything else — the product cannot tell an empty place from a store that was carried off somewhere else moments ago, and every resolution it could reach on its own is the one that discards the possibility. **This is REQ-EVENTS-179's family and MUST answer the same way.** That requirement governs a store that opens, reports itself usable, and then fails, and resolves it into REQ-EVENTS-084; this one governs a store that is not there at all, and resolves into the same place, so the answer does not turn on which of the two a reader happens to meet. Its check does not reach this condition and cannot be made to: an operation that reads and writes the store's own contents is answered perfectly by an empty store the attempt itself brought into being, so an absent store passes a check built to catch a store that does not work. What the product must establish before it uses a store is therefore not only that the store works, but that it is the store this machine already had — which is why creating one is right where nothing is kept for the workspace and wrong where a place is kept and the store is missing from it. **What this does not reach.** A workspace for which nothing is kept at all remains REQ-SESSION-043's ordinary empty state, unchanged. A place that is itself absent is an absence and not this condition, including while a restore is under way (REQ-SESSION-201). And a store that is present and holds no sessions is not this condition either: it opened, and it lists empty.
