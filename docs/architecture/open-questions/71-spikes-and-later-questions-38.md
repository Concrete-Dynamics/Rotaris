**OQ-543 — Does REQ-MONITOR-166's "explicit empty sparkline" ask for a mark a sighted operator can read, when OQ-540's empty form draws its axes in `--rt-viz-grid` at about 1.3:1?** *(REQ-MONITOR-166, REQ-SHELL-144, REQ-SHELL-149, §1.3, [OQ-540](../../archive/architecture/open-questions/71-spikes-and-later-questions-38-continued-3.md#oq-540). Raised 2026-11-05 by the fresh-context `review-ui` critique of the Overview's iteration-3 pack, executing the Overview audit's item 11 ([the brief](../../design/briefs/overview.md)); numbered after OQ-542.)*

**What is open.** OQ-540 ruled that below two samples the design `Sparkline` keeps its box, carries an accessible name stating that there is no token history yet, draws no series, and strokes any placeholder mark in `--rt-viz-grid`, "§1.3's token for chart rules". Built that way on 2026-11-05, the empty form's one mark, an empty pair of axes, measures 1.32:1 on the card ground at 1400×900 and 1.28:1 at 1000×680 on `rotaris-dim` (pixels sampled from the drive captures), against 6.18:1 for the drawn series. The same execution removed the cost caption's "no history yet · " clause, because the clause leaving at the second sample shrank the Tokens card by 17.81 px at 1000 wide, against OQ-540's "a card does not reflow when the second sample arrives". So the accessible name states the absence, while a sighted operator has only a faint mark. REQ-SHELL-144's 3:1 non-text floor names borders, focus rings and icons, not chart rules, so the critique filed no finding against the build.

**What the build proceeds under.** OQ-540 as ruled and built: the axes in `--rt-viz-grid`, the name "No token history yet", the caption the cost label alone.

**What decides it.** One ruling: the empty form stands (explicit by its name and its shape, and a chart rule needs no contrast floor), or REQ-MONITOR-166's "explicit" is read to need a visible statement — a mark at the 3:1 floor in a token §1.3 already names, or a visible word inside the sparkline's box so the card still does not reflow.

**OQ-549 — Is a workspace with no layout file and no requirement directory REQ-TRACE-231's workspace "with no requirement source", or a source that holds no documents?** *(REQ-TRACE-231, REQ-TRACE-515, REQ-TRACE-038, REQ-TRACE-039, REQ-TRACE-444, REQ-NOTIFY-006. Raised 2026-11-11 while repairing UIR-310 of that day's critique for [R-099](../../product/requests.md#r-099) ([the requirements-board brief](../../design/briefs/requirements-board.md)); numbered after OQ-548.)*

**What is open.** REQ-TRACE-231 gives "a workspace with no requirement source" an empty state that "says what a requirement source is and describes how one is configured". REQ-TRACE-515 reads that same state as the one "which says the source holds no documents". The layout always resolves, to the default directory `docs/requirements` where no `rotaris-traceability.json` names one (REQ-TRACE-038, REQ-TRACE-039), so the engine reports a store for a workspace nobody configured and whose default directory does not exist. Measured on the built application at `ab29f51b` (`pnpm app:drive`, a workspace with neither the file nor the directory): the board drew the state of a store that holds nothing, under the sentence "The requirement source is configured but holds no requirement documents yet." The engine reported no store only when the read failed (a layout file that does not parse), and the board drew REQ-TRACE-231's state there, over the error. Nothing states which of the two a missing default directory is.

**What the build proceeds under.** The engine's report, unchanged: a resolved layout is a store. Three things were built on 2026-11-11 so that no state says what does not hold. The store state's title no longer says "is configured", and its help says where the board looks, what a requirement document is and how to name another directory, which is what REQ-TRACE-231 asks of its own state. A source that could not be read is stated as that, with the engine's report and the act of correcting what it names; it is no longer told to configure one. REQ-TRACE-231's state stays in the view for a projection that reports no store and no error, which this build cannot produce: the service reports no store only after a failed read (`apps/desktop/src/workspace-service/delivery.ts`), and a failed read always carries its error (`packages/workspace/src/delivery/projection.ts`). So no workspace is drawn REQ-TRACE-231's state today, and what it asks, what a source is and how one is configured, is said by the store state's help. The projection tells an existing directory that can be written from every other case (`BoardProjection.source.canCreate`), and does not tell a missing directory from one that cannot be written: the "New requirement" control stays enabled over a missing directory, and its pane then gives a reason that is not the true one ([the note](../../defects/the-new-requirement-pane-says-read-only-of-a-store-directory-that-does-not-exist.md)).

**What decides it.** One ruling: a missing default directory with no layout file is "no requirement source", and the projection says so (the board then draws REQ-TRACE-231's state and its "New requirement" control is unavailable, as it is there); or the default layout is a source whether or not its directory exists, REQ-TRACE-231's state is read as the store that holds nothing, and the projection carries why nothing can be created. Not ruled in this round: either changes what the workspace service's projection reports, which the round's surfaces do not reach.

**OQ-550 — On a Settings category whose body draws a filled control, which fill yields while the save bar's Save stands?** *([§1.7](../../design/README/01-1-the-design-language.md) "One filled control", REQ-CONFIG-270, REQ-CONFIG-329, [`PD-CONFIG-009`](../../product/directives/pd-config-009.md#pd-config-009). Raised 2026-11-11 by the decision of UIR-307 for [R-099](../../product/requests.md#r-099); numbered after OQ-549.)*

**What is open.** §1.7 allows a view one filled control. The save bar, which REQ-CONFIG-270 keeps reachable from every category, draws its Save filled while unsaved changes stand. Four categories draw a filled control in their body as well: Models ("Add endpoint", PD-CONFIG-009), Hooks, Project and MCP Servers. Measured on Models at 1000×680 with one unsaved change (`pnpm app:drive`): two filled controls, "Save" and "Add endpoint". The other three were read in the source. PD-CONFIG-009 counts the category's body and says so; the 2026-11-09 repair of MCP Servers (FND-3, the comment in `packages/ui/src/settings/McpSettings.tsx`) counted three fills in the body and did not name the save bar.

**What the build proceeds under.** The body's fill stays and the save bar's Save is filled beside it. The two do not always stand in one frame: the save bar scrolls with the category ([the note](../../defects/the-settings-save-bar-scrolls-out-of-view-with-its-category.md)), which is a defect against REQ-CONFIG-270 and not an answer to this question.

**What decides it.** One ruling for every category: §1.7's count on Settings is the category body's and the save bar is the frame's; or a body's fill is drawn as a hairline while Save stands; or the save bar's Save is a hairline wherever a body holds a fill. Not ruled in this round: the second and third each change a control's drawing in answer to state elsewhere on the view, on four categories of which three were not captured.
