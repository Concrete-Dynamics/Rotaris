# Application Startup, Distribution, and Updates — Cross-cutting invariants

Part 8 of 10 of [domain 11](../11-startup-distribution-updates.md), which indexes every part. Defines REQ-STARTUP-150 – REQ-STARTUP-155.

### Cross-cutting invariants

**REQ-STARTUP-150** — Silence/visibility invariants: a launch that is handed to an instance already running is always silent — it surfaces a window and reports nothing at all (REQ-STARTUP-162); a failed update **check** is always invisible (log only); a failed update **install** is always visible (persistent error notice); a machine-setup failure is always recoverable (Retry or Continue-without-tool — the app never refuses to start because of setup) and is reported again at the point a degraded capability is used (REQ-STARTUP-154); a build not running from a released standalone artifact, and a demo window on any runtime, perform no update network traffic at all (REQ-STARTUP-057, REQ-STARTUP-106); an artifact preparing itself for launch, reusing a preparation, or redoing an unusable one is always silent — nothing is reported to the user on any of those paths — while an artifact that could produce no preparation at all is always warned about and, on the terms REQ-STARTUP-165 (c) states, never prevented from running, that being the one preparation outcome the product reports (REQ-STARTUP-165 (c), REQ-STARTUP-165 (f)); and a workspace on shared or synchronised storage is always warned about and never refused, while an unclassifiable one is passed over in silence (REQ-STARTUP-166).

**REQ-STARTUP-151** — Ordering invariants: a launch resolves the single-instance record before it builds anything (REQ-STARTUP-164), so no window is ever constructed by a launch that turns out to be a hand-over; the desktop paints before setup, setup before workspace onboarding, and repository discovery waits for setup when setup is pending; the update check and the workspace-storage determination of REQ-STARTUP-166 start only after the window is shown; an artifact that prepares itself completes that preparation before it paints, a run that can make no preparation completes the run-scoped placement REQ-STARTUP-165 (c) permits before it paints, and an artifact prepares afresh before running a version it has not prepared for (REQ-STARTUP-165); update install order download → verify → apply is monotone with failure stopping it; setup steps run in deterministic plan order with completion persisted at every step boundary; and the version guard and the package-pin guard precede all release builds.

**REQ-STARTUP-152** — The following agreements SHALL hold, each decidable from published artifacts, observed network traffic, and process output alone. The filenames a release publishes as assets, the filenames its `SHA256SUMS.txt` lists, and the filename an update client asks for on a given platform SHALL all be values of the single naming scheme of REQ-STARTUP-031 and SHALL agree, the manifest listing every published asset but itself and the signature published over it (REQ-STARTUP-032, REQ-STARTUP-108). A launch-time update check SHALL reach the host and path of REQ-STARTUP-105 and no other host or path. A `SHA256SUMS.txt` exactly as published SHALL be consumable unmodified both by the update path and by `sha256sum -c`, with no reformatting step in between (REQ-STARTUP-032, REQ-STARTUP-113); the signature over it is detached and leaves those bytes untouched, which is why both consumers still read the same file. The signature a release publishes over its `SHA256SUMS.txt` SHALL verify against a key carried inside the published artifacts of that same release, decidable from the published artifacts alone (REQ-STARTUP-167). The tool and MCP package versions a build provisions and warms SHALL be the versions pinned in the manifest that same build ships, and the same versions its `THIRD-PARTY-LICENSES.txt` reports (REQ-STARTUP-058, REQ-STARTUP-059, REQ-STARTUP-142). The executables an installation makes available SHALL be exactly the one entry point of REQ-STARTUP-002, and launching that entry point twice on one user account SHALL leave exactly one process of the application running, the second launch having been handed to the first (REQ-STARTUP-161, REQ-STARTUP-164). A preparation an artifact makes of itself in order to run (REQ-STARTUP-165) is not an executable an installation makes available and does not bear on that agreement: it is never installed, never registered, never placed on a search path, and never a thing a user is offered or directed to launch — launching the artifact is the only way it is ever reached. The same holds on the same terms of the run-scoped placement of REQ-STARTUP-165 (c). For every combination of preference values, configuration values, repository-root layout-configuration values, and environment variables a user can produce, the release source used by the update check SHALL still be the endpoint of REQ-STARTUP-105 (REQ-STARTUP-111).

**REQ-STARTUP-155** — Startup and setup timing SHALL be bounded as follows, each bound measured on the supported baseline of REQ-STARTUP-159 and REQ-STARTUP-024. The main window SHALL be painted within 5 seconds of the application being launched. That bound is on the launch that becomes the running instance; a launch handed to an instance already running paints no window of its own, is bounded instead by the hand-over interval of REQ-STARTUP-164, and where it does cause a window to be built (REQ-STARTUP-162, REQ-STARTUP-163) that window is bounded by this same 5 seconds. The bound SHALL be the same for every published artifact and every bundle mode — the `onefile` Windows portable executable of REQ-STARTUP-013 is given no larger budget than the `onedir` flavours, and no per-flavour differential is specified. There is exactly one exemption from it, stated next; it reaches no other artifact, no other bundle mode, and no other run.

**First-run exemption.** Where an artifact published in `onefile` mode prepares itself for launching under REQ-STARTUP-165, the run that performs that preparation is exempt from the 5-second bound, for the preparation it performs and for nothing else. Every other run of that artifact is bound by the 5 seconds exactly as every other artifact is. **"First run" means the first run of a given version of that artifact, on a machine, for the user who runs it — never the first run of the product and never the first run of the artifact family.** A machine that has already run an earlier version still performs a first run of the version now in front of it; a user who runs a version another user of the same machine has already run still performs a first run of it; and a run that prepares again because the existing preparation is incomplete, unreadable, or not the one belonging to this artifact (REQ-STARTUP-165 (c)) is a first run of that version for this purpose, so recovering from an unusable preparation never makes a build non-conformant. A run that produced no usable preparation at all, because the storage of REQ-STARTUP-165 (a) would not accept one, performs that same work and is exempt on the same terms and for the same reason: the condition lies in the machine's storage rather than in the build, and a build SHALL NOT be judged non-conformant for it. That run is the one preparation outcome that is not silent, and REQ-STARTUP-165 (c) fixes what it reports and where. This is still one exemption — it covers the run that does a preparation's work, however that run ends — and it still reaches no other artifact and no other bundle mode. Once an artifact has prepared, every later run of that same artifact SHALL paint within the 5 seconds this requirement fixes. The exemption reaches the first paint alone: the fast-path decision below is not exempt, and neither is the setup-pass bound below it. The exemption is stated so that a reader cannot take the silence of REQ-STARTUP-013 and REQ-STARTUP-031 — both of which are unchanged — as licensing a per-flavour budget: there is no per-flavour budget, only a per-artifact-version first run.

The fast-path decision of REQ-STARTUP-066 — establishing that the plan is empty — SHALL be reached within the 100 ms interface-responsiveness budget of REQ-SHELL-150 and SHALL delay neither the first paint nor the post-show activation of REQ-STARTUP-043. A setup pass in which every manifest tool is already satisfied (REQ-STARTUP-069) SHALL be bounded by the probe timeout it is built from and no more: its wall time SHALL NOT exceed the sum of the per-probe timeouts of REQ-STARTUP-063 over the manifest's tools, counted twice for the detect and record steps that both probe. No further timing is specified, and that is deliberate: download durations depend on the network, per-step pacing depends on the machine, and the visual rendering of the setup dialog and the update banner beyond their widget structure, text and accessibility metadata is a design matter this document does not fix. A build SHALL NOT be judged non-conformant for any of those three.
