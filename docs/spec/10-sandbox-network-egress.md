# Command Sandboxing and Network Egress Policy

## Overview

The product gates outbound network access and confines shell command execution. Per-workspace configuration controls three cooperating surfaces: a per-host egress policy applied to the built-in URL-fetch tool (allow/ask/deny with allow and deny host lists), permission-layer gating of network-reaching terminal commands, and an operating-system confinement layer — inactive unless the workspace turns it on — that restricts terminal commands to a declared set of writable paths and carries a single on/off switch for network access. Every ambiguous or failing path resolves closed: an unclassifiable host is denied, confinement that cannot be proven working refuses to run commands rather than running them unconfined, and a permissive mode requested where no one can answer a prompt is tightened unless confinement is active or the workspace has explicitly opted out of that tightening.

## Requirements

### Egress configuration surface

- **REQ-SANDBOX-001** — The setting `runtime.network_egress_policy` (string) is the default disposition for a fetch target matching neither host list. Accepted values are exactly `allow`, `ask`, `deny`. The shipped default is `ask`.
- **REQ-SANDBOX-002** — The disposition is matched with surrounding whitespace removed and letter case ignored, so `  ASK ` selects the `ask` policy. Any other spelling is refused rather than stored: a configuration file carrying it fails to load, and no later route that changes the setting on a running product — the desktop settings surface included — can install a value the loader would have refused, so the previously effective disposition stays in force. The refusal quotes the rejected value and lists `allow`, `ask`, and `deny`.
- **REQ-SANDBOX-003** — `runtime.network_allowed_hosts` and `runtime.network_denied_hosts` are lists of host patterns, each defaulting to the empty list. Allowed-list entries are permitted regardless of the default disposition; denied-list entries are refused even when an allow entry or a permissive default would otherwise permit them.
- **REQ-SANDBOX-004** — At configuration load, each host-pattern entry is whitespace-trimmed and lowercased, and blank entries are dropped (given `"  GitHub.com "`, the stored value is `github.com`; given `"   "`, the entry is dropped). Wildcard grammar is NOT validated at load time; invalid wildcards surface at classification time (REQ-SANDBOX-016) and at UI entry (REQ-SANDBOX-114).
- **REQ-SANDBOX-005** — Configuration layers per field: a workspace-level config file at `<workspace>/.rotaris/agents.yaml` overrides the global config field-by-field; a field the workspace leaves unset keeps the global value, not the shipped default. All sandbox and egress fields participate in this layering.

### Host identity normalization

- **REQ-SANDBOX-006** — Before any list matching or classification, a URL or bare host name is reduced to one canonical host string by: folding to lower case; discarding a `user:pw@` prefix; discarding a `:port` suffix; removing the brackets around an IPv6 literal; removing one trailing root dot; and expressing non-ASCII labels in their IDNA (punycode) form. Required results: `https://Example.COM/path?q=1` → `example.com`; `http://user:pw@api.example.com:8443/x` → `api.example.com`; `example.com:8080` → `example.com`; `example.com.` → `example.com`; `http://[::1]:9000/` → `::1`; `127.0.0.1` → `127.0.0.1`; input that is empty or only whitespace → the empty string `""`. That empty string is the "unknown host" referred to throughout this domain.
- **REQ-SANDBOX-007** — Unicode and punycode spellings of one name are interchangeable in both directions: `https://bücher.example/` and `XN--BCHER-KVA.example` both reduce to `xn--bcher-kva.example`, so a list entry written either way matches a fetch target written either way and neither spelling slips past an entry written in the other. Where IDNA conversion of a name does not succeed, the trimmed lower-cased original text stands as that host's canonical string; being non-empty it is still compared against both host lists literally and is never treated as the unknown host of REQ-SANDBOX-008.
- **REQ-SANDBOX-008** — Input that cannot be reduced to a host yields the unknown host — the empty string `""`, never a partial or guessed name — and the unknown host resolves closed everywhere it can flow: classification yields deny; it matches no pattern; it counts as remote (and is therefore gated).

### Host pattern grammar and matching

- **REQ-SANDBOX-009** — The pattern grammar is: an exact host name, or a single leading `*.` wildcard — nothing else. Patterns are trimmed, lowercased, and trailing-dot-stripped before use. An empty pattern is an error.
- **REQ-SANDBOX-010** — Any use of `*` not forming a single leading `*.` is rejected with an error whose message contains "not supported" and shows the only supported form with an example such as `*.example.com`. Patterns that must be rejected (never silently treated as literal host names): `api.*.com`, `exa*ple.com`, `*`, `*.*.com`, `example.*`. Rationale: accepting such a pattern quietly would leave an operator with a list that reads as configured while permitting no host at all.
- **REQ-SANDBOX-011** — Matching advances label by label; a hit that lands part-way through a label never counts. An exact pattern matches by equality after normalization (case-insensitive). A leading `*.` stands in for at least one label positioned to the left of the pattern's remainder, so `*.example.com` covers `api.example.com` and `a.b.example.com`, while bare `example.com` falls outside it. Excluding the bare name is intentional and mirrors the usual reading of wildcard certificates; operator documentation must state it, since covering both the bare name and its subdomains takes two entries.
- **REQ-SANDBOX-012** — Lookalike domains never match: `*.example.com` does not match `evilexample.com` or `evil-example.com`; exact `example.com` does not match `evil-example.com`, `example.com.evil.test`, or `notexample.com`.
- **REQ-SANDBOX-013** — The empty/unknown host matches no pattern of either kind.

### Egress classification

- **REQ-SANDBOX-014** — The denied list is consulted first, then the allowed list, then the default disposition. A specific denied entry therefore outranks a broader allowed wildcard: host `metadata.example.com` with allowed `["*.example.com"]`, denied `["metadata.example.com"]`, and default `allow` classifies as deny.
- **REQ-SANDBOX-015** — An allow-listed host is allowed even under a deny default (`registry.npmjs.org` with allowed `["*.npmjs.org"]` and default deny → allow). A host matching neither list resolves to the configured default disposition (under the shipped `ask` default, it routes to the approval path).
- **REQ-SANDBOX-016** — Classification fails closed: an unreadable/empty host resolves to deny; an unrecognized default-disposition string resolves to deny; the default disposition is compared after trim/lowercase. If a stored pattern is invalid (an unsupported wildcard reached the configuration), applying the policy is an error and the fetch is refused with `failure_kind` `egress_policy_error` (REQ-SANDBOX-032) — never treated as a literal, never fail-open.
- **REQ-SANDBOX-017** — The disposition vocabulary is exactly the strings `allow`, `ask`, `deny`, shared by the configuration field, classification results, and the permission engine's decision vocabulary.

### Local vs. remote classification

- **REQ-SANDBOX-018** — A target is on this machine when its canonical host string (REQ-SANDBOX-006) is exactly `localhost`, `localhost.localdomain`, or `ip6-localhost`, or is the IPv4 loopback literal `127.0.0.1` (reached through any URL spelling) or the IPv6 loopback literal `::1`. The test is textual and performs no name resolution, so a name that happens to resolve to a loopback address is still remote. Private-range and link-local addresses are remote and therefore gated: `169.254.169.254` (cloud metadata) and `10.0.0.5` both classify as remote. Open Question 19 records what is undetermined about the loopback range.
- **REQ-SANDBOX-019** — Anything not local is remote, including unparseable input: `""` and `"not a url at all"` count as remote, so an unreadable fetch target is gated rather than slipping through. `http://localhost:5173/index.html` is local.

### Fetch tool — request surface and defaults

- **REQ-SANDBOX-020** — A fetch request takes: `url` (required, no default); `max_lines` (integer, default 1000); `from_line` and `to_line` (optional, 1-based and inclusive, naming the first and last body line to return and defaulting to the first and last line of the body); and `timeout` (optional number, refused when negative, replacing the default of REQ-SANDBOX-021 for that call only). `timeout: 0` is accepted and carried through as given rather than being treated as absent. Open Question 10 records what `timeout: 0` means and how a refused parameter value is reported.
- **REQ-SANDBOX-021** — When the fetch tool is registered for a run, its default timeout is the run's `runtime.tool_timeout` (default 30 seconds). Used without run wiring, the built-in default is 10.0 seconds. (Exact interplay is flagged in Open Questions.)

### Fetch tool — egress enforcement

- **REQ-SANDBOX-022** — Before any connection is opened, the policy is applied to the host of the requested URL and, separately, to the host of each redirect target. A server whose host resolves to deny observes zero connection attempts and zero requests.
- **REQ-SANDBOX-023** — Redirects are never followed automatically; each hop is re-classified before it is fetched. When a permitted host redirects to a denied host, the request is refused at that hop and the denied server sees nothing.
- **REQ-SANDBOX-024** — The redirect hop budget is 20. Exceeding it yields `failure_kind` `too_many_redirects`, `error_class` `TooManyRedirects`, and a detail stating that the fetch gave up after 20 redirect hops and never arrived at a terminal response.
- **REQ-SANDBOX-025** — Refusals produced by the policy report stable `failure_kind` values intended for programmatic reading: `egress_denied` (the named URL was denied), `egress_redirect_denied` (a redirect hop was denied or unapproved), `egress_policy_error` (the policy could not be applied), `too_many_redirects`. These are distinct from `network_error` / `timeout` / `http_error`, so a policy refusal (something to re-plan around) is always distinguishable from a transient transport fault (something to retry).
- **REQ-SANDBOX-026** — Every egress refusal (`egress_denied`, `egress_redirect_denied`, `egress_policy_error`) carries `error_class` `NetworkEgressDenied`, `is_error` true, an absent/null `status_code`, and a `detail` stating which host was refused and which policy input produced that outcome (the `runtime.network_egress_policy` setting or one of the host lists).
- **REQ-SANDBOX-027** — Under the `ask` disposition, approval for the URL the agent named is obtained before the fetch runs, so once the request is in flight that host counts as permitted for the rest of that request. Every hop is still classified against the policy (REQ-SANDBOX-022, REQ-SANDBOX-023); what an already-permitted host changes is only how an `ask` verdict resolves mid-chain. A hop landing on a host already permitted within this request is followed without a further approval, so a path-only redirect and an `http`→`https` redirect on the same host both complete under the shipped default, as does a redirect onto a host on the allow list. A `deny` verdict refuses the hop whatever preceded it (REQ-SANDBOX-014), and a hop onto a new host classifying `ask` is refused (REQ-SANDBOX-028).
- **REQ-SANDBOX-028** — A redirect onto a NEW host that classifies as `ask` is refused, since no approval can be sought once a request is in flight: `failure_kind` `egress_redirect_denied`, with a detail explaining that the hop originated from the requested URL, that the destination host was never approved, and that access to that destination has to be asked for as its own request when it is actually required.
- **REQ-SANDBOX-029** — Deny verdicts distinguish position: the initially named URL → `egress_denied`; a redirect hop to a host outside the permitted set → `egress_redirect_denied`.
- **REQ-SANDBOX-030** — A host allowed by verdict during a redirect chain remains permitted for later hops within the same request; hops returning to an already-permitted host are not re-gated.
- **REQ-SANDBOX-031** — Redirect target resolution: an absolute redirect target is used as given; a relative location value is resolved against the current URL; a redirect response without a location ends the chain and that response is the final result. (End-to-end behavior for unusual combinations is an Open Question.)
- **REQ-SANDBOX-032** — When the policy itself cannot be applied to a host (e.g. an invalid stored pattern), the request is refused with `failure_kind` `egress_policy_error` and a detail naming the host and embedding the underlying error. The request is never executed — fail-closed, never fail-open.
- **REQ-SANDBOX-033** — Non-refusal failure outcomes: a timeout yields `failure_kind` `timeout` with a detail naming the timeout in seconds; any other transport failure before a response yields `network_error`; an HTTP status ≥ 400 yields `is_error` true, `failure_kind` `http_error`, and a detail naming the status code.
- **REQ-SANDBOX-034** — Response shaping: the body is split into lines; the `from_line`/`to_line` window is taken (1-based, both ends inclusive, a window reaching past the end of the body yielding the lines that exist); if the selection holds more than `max_lines` lines, only its first `max_lines` lines are returned and `truncated` is true; otherwise every selected line is returned and `truncated` is false. Lines left out by the window alone never make `truncated` true.
- **REQ-SANDBOX-035** — The fetch result exposes the fields listed in Data & Formats: `url` (as requested), `final_url`, `status_code`, `content_type`, `truncated`, `failure_kind`, `timeout_seconds`, `error_class`, `detail`.
- **REQ-SANDBOX-036** — Model-facing rendering is fixed in structure and free in wording. A policy refusal or transport failure renders, in order: a first line identifying the failure; a `[fetch_diagnostic]` block holding the result fields of REQ-SANDBOX-035 as one JSON object whose keys are in sorted order and whose null-valued fields are left out, `failure_kind` always among the keys present; and, when a body was received, a `[fetch_output]` block holding it. A success renders the header lines `url`, `final_url`, `status_code`, `content_type`, `truncated` in that order, one per line, followed by the body.
- **REQ-SANDBOX-037** — A fetch executed without run-scoped egress configuration defaults to a permissive policy (disposition `allow`, empty lists), so a wiring gap breaks nothing; this is not ungated overall because permission-layer gating of remote fetches still applies ahead of execution.
- **REQ-SANDBOX-038** — The effective egress policy is read from the owning run's current configuration at each fetch call: an edit to the host lists takes effect on the following fetch with no restart, and two concurrent runs in one process each apply their own lists — one run's permitted hosts never extend to another.

### Permission-layer gating of network access

- **REQ-SANDBOX-039** — The fetch tool (model-facing tool name `fetch`) is classified both read-only and network-reaching. Host-scoped fetch gating is evaluated BEFORE any blanket read-only allowance (first match wins), so read-only status cannot bypass egress gating.
- **REQ-SANDBOX-040** — Each supervised mode (`restricted`, `ask`) carries two fetch rules, in order: `{mode}:fetch-remote-host` (decision ask; covers a fetch whose target is off-machine) then `{mode}:fetch-local-host` (decision allow; covers a fetch whose target stays on this machine). Both precede the mode's `{mode}:read-only-tool` rule.
- **REQ-SANDBOX-041** — A remote fetch under a supervised mode resolves through the remote-host rule (ask); when no approval channel is registered, the ask resolves fail-safe to deny. A loopback fetch (e.g. `http://127.0.0.1:5173/...`) resolves allow through the local-host rule.
- **REQ-SANDBOX-042** — The gated subject of a fetch permission decision is the URL itself; the URL appears as the gated command in decisions and the audit trail.
- **REQ-SANDBOX-043** — A terminal command line is network-reaching exactly when at least one of its segments opens with one of the 51 command prefixes catalogued in Data & Formats. A line is cut into segments at the shell operators `&&`, `||`, `;`, `|`, `&`, and newline; each segment is judged on its own leading tokens once surrounding whitespace is removed, and one matching segment settles the whole line, so `date && curl https://example.com` is network-reaching. A line no segment of which matches is not network-reaching: `ls -la`, `git status`, `pytest -q`, `cat notes.txt`, and an inline `python -c '...'` snippet all classify as local. The catalogue is a set, not a sequence — the order in which the prefixes are listed carries no meaning and there is no first-match precedence among them. Open Question 18 records what is undetermined about a prefix's trailing `*`.
- **REQ-SANDBOX-044** — The network-command rule per mode: `restricted` → deny (rule id `restricted:network-command`), `ask` → ask (rule id `ask:network-command`). Each matches its mode's default decision; the rules exist so refusals and the audit log name a specific rule id.
- **REQ-SANDBOX-045** — The `autonomous` mode carries NO fetch rules and NO network-command rule — only its destructive-command deny rules. Rationale: in that mode nothing is available to respond to a prompt, so such a rule would settle on deny and make the most permissive mode stricter than intended. `curl` or `pip install` under autonomous resolves allow via the mode default.
- **REQ-SANDBOX-046** — Mode defaults: `restricted` = deny, `ask` = ask, `autonomous` = allow. A missing/empty mode name resolves to `ask`; an unrecognized name resolves to `restricted` with a logged warning. Permissiveness ordering: restricted < ask < autonomous.
- **REQ-SANDBOX-047** — For terminal commands, network access is all-or-nothing: confinement either opens or closes the network for the whole command and cannot distinguish destinations within it. Per-host allow/ask/deny is available only for the built-in fetch tool, whose connections the product makes itself. The limitation must be documented; destination-aware filtering of terminal traffic is out of scope.

### Sandbox configuration surface

- **REQ-SANDBOX-048** — `runtime.sandbox_mode` (string): `off` | `workspace-write` | `read-only`; default `off` (the sandbox is opt-in). Comparison ignores letter case; a value outside those three spellings fails validation both at load and at assignment, and the message names the bad value together with all three valid modes.
- **REQ-SANDBOX-049** — A bare YAML `sandbox_mode: off` (which YAML 1.1 parses as boolean false) must be read as the `off` mode, not rejected as a type error.
- **REQ-SANDBOX-050** — `runtime.sandbox_writable_roots` (list of strings, default empty) names absolute paths that are writable inside the sandbox in addition to the workspace. An entry keeps its text apart from stripped leading and trailing whitespace: no case folding, no separator rewriting, no symlink resolution. An entry that is not absolute is refused with a message that quotes the entry and states that an absolute path is required. Absoluteness is decided by spelling rather than by the host performing the check, so `/opt/cache` and `C:\Builds\cache` are both accepted in the same file on either platform and one configuration file serves a mixed fleet. A path need not exist when the configuration is read. Open Question 11 records what is undetermined about blank entries and about roots missing at launch.
- **REQ-SANDBOX-051** — `runtime.sandbox_allow_network` (bool, default false): grants confined processes network access. It has effect only while a confinement mode other than `off` is selected. The shipped posture is closed.
- **REQ-SANDBOX-052** — `runtime.allow_unsandboxed_autonomous` (bool, default false): per-workspace opt-in to run unattended in a permissive mode without a sandbox. Its documentation must warn that it belongs in one workspace's configuration rather than the global one.
- **REQ-SANDBOX-053** — Adjacent settings that interact with this domain: `runtime.permission_mode` default `ask`; `runtime.headless_approval_policy` default `deny` (alternative `abort`; an unrecognized value behaves like deny) — governs how an ask resolves with no approval UI; `runtime.approval_timeout_seconds` default 300.0, with 0 meaning wait without limit.
- **REQ-SANDBOX-054** — All six sandbox/egress fields (`sandbox_mode`, `sandbox_writable_roots`, `sandbox_allow_network`, `network_egress_policy`, `network_allowed_hosts`, `network_denied_hosts`) survive a write-then-read cycle through the workspace YAML file: the configuration loaded afterwards is the same effective configuration that was saved, and a further save-and-load changes nothing again. The load-time normalizations stated elsewhere still apply on the way in — host patterns arrive trimmed and lower-cased with blanks dropped (REQ-SANDBOX-004), writable-root entries arrive trimmed (REQ-SANDBOX-050), and a YAML boolean false for `sandbox_mode` arrives as `off` (REQ-SANDBOX-049) — so what round-trips is the normalized value, not necessarily the raw text a user first typed.

### Confinement model

- **REQ-SANDBOX-055** — The mode spellings `off`, `workspace-write`, `read-only` are stable persisted values and must not change across releases.
- **REQ-SANDBOX-056** — The workspace-relative subpaths `.git` and `.rotaris` are always read-only inside the sandbox, even within an otherwise writable workspace. The exclusion is fixed: no setting and no configuration combination removes it. A confined command must therefore never be able to install a repository hook that would later run outside confinement, nor to write the configuration that governs a later run.
- **REQ-SANDBOX-057** — The exclusion attaches to the name a command would use rather than to whatever the name ultimately points at: when that name is a link, or a file standing in for a repository directory, writing through it is still refused.
- **REQ-SANDBOX-058** — Effective writable roots by mode, under an active confinement mode: `read-only` grants none; `workspace-write` grants the workspace root first and then each configured additional root, duplicates removed keeping the first occurrence. Separately from the configured roots, every active mode leaves the platform's temporary location writable (REQ-SANDBOX-075, REQ-SANDBOX-076), so `read-only` means "no writable root beyond the temporary location", not "no writable path at all". Mode `off` renders no confinement whatsoever (REQ-SANDBOX-074), so effective writable roots do not apply to it and writes are bounded only by the host operating system.
- **REQ-SANDBOX-059** — The network inside the sandbox stays closed unless `sandbox_allow_network` is true.
- **REQ-SANDBOX-060** — Read access is intentionally unrestricted: a confined command can still read anywhere on the filesystem (e.g. reading `/etc/passwd` succeeds). Only write confinement and the network switch are enforced; restricting reads is deliberately not attempted, because ordinary developer tooling depends on wide read access.
- **REQ-SANDBOX-061** — Backend parity: the same configuration must produce identical write verdicts on both supported platforms, including for a protected subpath that does not yet exist (a fresh worktree with no `.git`/`.rotaris` must still deny creating or writing under those names) and for one that does. Absent that parity, a result observed on one platform would say nothing about the other.
- **REQ-SANDBOX-062** — The sandbox wrapper never changes the working directory: the command runs in the persistent shell's current directory identically on all platforms, sandboxed or not.
- **REQ-SANDBOX-063** — The submitted command travels into the confined environment as a SINGLE shell argument (`/bin/sh -c '<command>'`) and is never split apart again: a compound line containing variable references and quoted arguments with spaces arrives unchanged as the last token of the rendered invocation.
- **REQ-SANDBOX-064** — A workspace path containing quote or backslash characters must not be able to alter the confinement that is applied: every path embedded in the confinement rules and every argument of the rendered invocation must be quoted such that no crafted path can end its enclosing literal and introduce rules of its own.

### Sandbox availability

- **REQ-SANDBOX-065** — The confinement mechanism follows from the host operating system alone: macOS → Seatbelt (launcher `sandbox-exec`); Linux, a WSL2 distribution included → bubblewrap (launcher `bwrap`); every other operating system → no mechanism, `available` false and backend name `unavailable`. The choice is made before PATH is consulted and before any trial runs, so on macOS without `sandbox-exec` the diagnostic still names Seatbelt and on Linux without `bwrap` it still names bubblewrap, rather than either reporting an unsupported platform. Open Question 12 records what is undetermined about legacy platform identifiers.
- **REQ-SANDBOX-066** — Availability probing proceeds in increasing order of cost: platform check, then launcher lookup on PATH, then a trial launch. No subprocess is spawned once an earlier step has already failed.
- **REQ-SANDBOX-067** — Availability must be demonstrated rather than inferred: locating the launcher on PATH is required but does not settle the question, because a host that restricts unprivileged user namespaces can have the launcher installed while every launch fails. A disposable trial confinement is therefore launched at most once per process, and its result is cached for later probes.
- **REQ-SANDBOX-068** — The one success criterion for the trial is termination with exit status 0 inside the trial timeout; whatever the trial writes to its output is irrelevant to a success verdict. Every other outcome yields `available` false with a reason identifying which of these occurred: the trial did not finish within 5 seconds and was terminated; the trial could not be started at all, with the reported launch error; the trial exited with status N, the reason then carrying the first non-empty line of its diagnostic output; the trial exited with status N having produced no output, which the reason states. An outcome that cannot be interpreted counts as a failure and never as a success — a wrong `unavailable` costs only stricter prompting, a wrong `available` would let commands run against the host with no confinement.
- **REQ-SANDBOX-069** — The trial launch timeout is 5.0 seconds (the probe may run on a UI thread and must stay short).
- **REQ-SANDBOX-070** — The trial goes through the real mechanism, never a stand-in. On macOS it runs `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` — the widest ruleset that still engages Seatbelt, so a failure implicates the mechanism rather than any single restriction. On Linux it uses the option rendering the product would produce for a read-only confinement rooted at `/` with no carve-outs and no writable roots, keeps the network namespace separate whatever `runtime.sandbox_allow_network` says, and runs a program that exits 0. Rendering the trial invocation reads no path on the filesystem. Open Question 13 records the unsettled point between this requirement, REQ-SANDBOX-079, and Data & Formats over the trial's final tokens.
- **REQ-SANDBOX-071** — The availability verdict is a value with: `available` (bool); a backend name (`seatbelt` | `bubblewrap` | `unavailable`); `reason`; `remediation` — reason and remediation empty when available. Every surface that reports availability (desktop status, command-line errors, logs) presents that same text, so the guidance a user sees never differs by surface.
- **REQ-SANDBOX-072** — The unavailability error renders as the reason, then the remediation on its own line; with no remediation, just the reason; with no reason, a generic line reporting that no OS-level confinement can be used on this host.
- **REQ-SANDBOX-073** — Diagnostic content per scenario. Each string quoted below must appear literally in the reason or the remediation as indicated, and each stated fact must be conveyed; the wording around them is free.
  - Native Windows: the reason states that no OS-level confinement is available on native Windows and names both supported pairings, macOS with Seatbelt and Linux with bubblewrap. The remediation offers two courses — running under a WSL2 distribution with bubblewrap installed, quoting `sudo apt-get install bubblewrap`, or leaving `runtime.sandbox_mode` at `off`.
  - Unrecognized operating system: the reason quotes the platform identifier actually detected and does not claim the host is Windows. The remediation names macOS and Linux/WSL2 as the supported hosts.
  - Seatbelt selected on a host that is not macOS, or its launcher not found: the text quotes `sandbox-exec`, states that macOS supplies it, and suggests checking that `/usr/bin` is on PATH.
  - Bubblewrap launcher not found: the remediation quotes both `sudo apt-get install bubblewrap` and `sudo dnf install bubblewrap`.
  - Bubblewrap trial failure: the reason carries the launcher's own diagnostic output as described in REQ-SANDBOX-068. The remediation quotes `kernel.apparmor_restrict_unprivileged_userns` and `/proc/sys/kernel/unprivileged_userns_clone` as the controls gating unprivileged user namespaces, quotes `bwrap --ro-bind / / --proc /proc --unshare-net -- true` as a command to try by hand, and states that a workspace requesting confinement keeps failing for as long as the launcher fails — never that its runs proceed unconfined, which REQ-SANDBOX-074 and REQ-SANDBOX-084 forbid.
  - Seatbelt trial failure: the remediation quotes `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` as a command to try by hand.
- **REQ-SANDBOX-074** — There is no silent fallback: preparing a command for confinement either yields a NEW confined command string or reports an availability error; it never yields the original command. The single exception is mode `off`, which passes the command through unchanged on every platform and performs no probing.

### Rendered OS confinement (observable invocations)

- **REQ-SANDBOX-075** — Observable behavior of the macOS profile: everything is refused unless allowed. Permitted in every active mode — executing and forking processes, reading sysctl values, sending signals, reading any path on the filesystem, writing under the temporary locations `/tmp`, `/private/tmp`, `/var/tmp`, `/private/var/tmp`, `/private/var/folders`, and writing data to the device nodes `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/tty`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr`, `/dev/dtracehelper`. In `workspace-write`, each effective writable root of REQ-SANDBOX-058 additionally permits writes throughout its subtree, one allowance per root, with the protected subpaths of REQ-SANDBOX-056 denied; those denials appear after every allowance in the profile, the position at which they take effect, so a write under `<workspace>/.git` or `<workspace>/.rotaris` fails while a write elsewhere in the workspace succeeds. In `read-only` no writable root appears and writes succeed only at the temporary locations and device nodes named above. The network is permitted or refused as a whole according to `runtime.sandbox_allow_network`, with no distinction by destination (REQ-SANDBOX-047).
- **REQ-SANDBOX-076** — Linux confinement invocation behavior: the entire root filesystem bound read-only; device and proc filesystems provided; a fresh empty temp filesystem at `/tmp`; each effective writable root re-bound writable; the excluded subpaths applied after those writable binds, since ordering decides the outcome and an exclusion placed before the workspace bind would simply be covered over; the network namespace kept separate unless the opt-in grants network; and the confined process terminated together with its parent.
- **REQ-SANDBOX-077** — On Linux the rendering for a protected subpath (`.git`, `.rotaris`) turns on where the path sits and whether it exists, and in every case a write to that name inside confinement fails:
  - (a) The path lies outside every writable root, as in `read-only` mode: nothing extra is rendered. The read-only root already refuses the write, and the session starts normally.
  - (b) The path exists inside a writable root: it is re-bound read-only in the form that tolerates a missing source, `--ro-bind-try <p> <p>`. Its real contents stay readable, so `git status` keeps working under confinement; writes to it fail; and the command still starts if the path is removed between rendering and launch.
  - (c) The path does not exist inside a writable root, as in a freshly created worktree holding neither directory: an empty read-only filesystem is mounted at that name, rendered `--tmpfs <p>` followed by `--remount-ro <p>`. The name reads as empty and nothing can be created under it. A confined command must not be able to bring `.git` or `.rotaris` into existence where they were absent.
- **REQ-SANDBOX-078** — Where the existence check of REQ-SANDBOX-077 races a filesystem change, the outcome lands on the restrictive side: a protected subpath created after the check stays hidden behind the empty read-only mount, its real content neither readable nor writable inside that command; a protected subpath deleted after the check does not stop the command starting, the tolerant bind of case (b) accepting a missing source; and a symlink with no target counts as an absent path, taking case (c). If the carve-out cannot be established at launch, the command does not run: it is refused exactly as in REQ-SANDBOX-083, with `failure_kind` `sandbox_unavailable` and exit code 126, and under no circumstances does it run with the carve-out missing. Open Question 14 records whether such a failure also ends the session.
- **REQ-SANDBOX-079** — Final wrapped command shapes: macOS — `sandbox-exec -p '<profile>' /bin/sh -c '<command>'`; Linux — `bwrap <options…> -- /bin/sh -c '<command>'`. All items are shell-quoted.

### Terminal-tool enforcement

- **REQ-SANDBOX-080** — Every newly submitted terminal command in a session with an active confinement mode is confined, whether it runs in the foreground or is started in the background. A background command is confined on exactly the terms its foreground equivalent would be, so asking for background execution is not a way around the sandbox.
- **REQ-SANDBOX-081** — Confinement is applied only to a NEW command string. Excluded: text directed at an already-running process as its input, because confining it would deliver the wrapper text into that process's input, whereas an interrupt keystroke must arrive unaltered; a command that is empty or only whitespace, which is a request to collect further pending output; a request to list sessions; and a control call that carries only a session identifier. A request carrying BOTH a background flag and a session identifier counts as a new spawn and is confined, so that this documented-invalid combination cannot become a single-field bypass.
- **REQ-SANDBOX-082** — Wrapping is idempotent per issuance: a repeated or retried command is wrapped exactly once; wrappers never nest.
- **REQ-SANDBOX-083** — Wrap-time failure (unavailability, or ANY error raised while wrapping, e.g. a broken platform integration): the command is not executed — nothing reaches the shell or the background registry — and a refusal observation is returned with: `failure_kind` `sandbox_unavailable`, `is_error` true, exit code 126 — the conventional code for a command that exists but could not be run, chosen so that outcome classification cannot mistake a command that never executed for a successful one — outcome kind `sandbox_unavailable` with severity `error`, `error_class` set to the type name of the failure, and a detail recording that the session requires OS-level confinement, that confinement could not be applied, that the command was consequently not executed, and what the underlying error was.
- **REQ-SANDBOX-084** — Such a failure must not be absorbed by general-purpose error or retry handling: under no circumstances may a confinement failure lead to the command being run without confinement.
- **REQ-SANDBOX-085** — A command whose confining invocation was rendered successfully but failed at startup — the kernel refusing the namespace, for instance — is relabelled `sandbox_unavailable` only when all four of these hold: the command was confined by this call; the exit status is nonzero; no failure kind has been assigned yet, so a command stopped by the hard timeout stays `timeout`; and every non-empty line of the command's captured output begins with a launcher prefix, `bwrap:` for bubblewrap or `sandbox-exec:` or `sandbox_apply:` for Seatbelt. One non-empty line without such a prefix prevents relabelling, so a program that merely fails inside a working sandbox is never reported as broken confinement; a command that produced no output at all is not relabelled either. The detail states that confinement could not be started, that the command therefore never executed, that the cause lies in the host's configuration rather than in the command, and that neither retrying nor rewording the command changes the outcome. The relabelling applies to a foreground result and equally to the result of polling or terminating a background command, since a background spawn returns before the failure is visible and the failure first shows at the next poll. Open Question 15 records which output streams the prefix test covers.
- **REQ-SANDBOX-086** — The reported observation shows the command as the agent submitted it, not the confining invocation; showing the latter would obscure the request and encourage the model to alter the confinement machinery instead. Background execution must still be demonstrably confined — polled output reflects the confined execution — while the observation text continues to show the submitted command.
- **REQ-SANDBOX-087** — The terminal tool's model-facing documentation must explain that `failure_kind` `sandbox_unavailable` indicates the command never executed, that the cause is the host's configuration, that neither a retry nor a reformulated command helps, and that the detail and output should be relayed to the user. `sandbox_unavailable` is part of the observation's `failure_kind` vocabulary alongside `timeout`, `invalid_request`, `execution_error`.
- **REQ-SANDBOX-088** — With no sandbox configured, the shell receives exactly the characters the caller submitted, with no probing and no added cost.
- **REQ-SANDBOX-089** — Sandboxing does not change terminal session scheduling: a sandboxed terminal session serializes its commands exactly as an unsandboxed one.

### Session binding and launch

- **REQ-SANDBOX-090** — Configuration that sets no confinement mode means `off`. A confinement-mode value that the session layer cannot recognize is an error and must never be treated as "no confinement": such a value indicates validation did not run, and quietly settling on `off` there would be precisely the kind of unannounced downgrade this specification rules out.
- **REQ-SANDBOX-091** — Confinement is rooted at whichever directory the session genuinely executes in — an isolated worktree while worktree isolation is in use, otherwise the workspace itself — so that the writable area coincides with the location of the files the run works on. The configured additional writable roots and the network opt-in are carried through into that confinement.
- **REQ-SANDBOX-092** — The check performed before a run starts either names the mechanism that will confine it or fails with a reason and remediation; it never returns a "no confinement" result, so a caller that receives a positive answer can rely on the next command actually being confined. Mode `off` is not treated as a failure.
- **REQ-SANDBOX-093** — Confinement status is a pair (active, backend name), where active requires the mode to be both selected AND actually available; selection alone is insufficient. Mode off → (false, ""); selected but unavailable → (false, ""), with the backend name left empty so that no record names a mechanism that never ran; selected and available → (true, name).
- **REQ-SANDBOX-094** — A run whose configuration asks for confinement the host cannot deliver does not start, and starting it without confinement is prohibited. Whatever confinement fact is recorded for a run always agrees with the verdict that governed whether it was allowed to start, so no run is ever recorded as confined while its commands ran unconfined, nor recorded as unconfined while confinement applied.
- **REQ-SANDBOX-095** — On a host that cannot deliver the requested confinement, session start fails and reports the availability reason and remediation of REQ-SANDBOX-071. No usable session, and no shell able to run a command outside confinement, is left behind. Open Question 9 records the conflict between this requirement and REQ-SANDBOX-098 / REQ-SANDBOX-105 over whether such a session starts at all.
- **REQ-SANDBOX-096** — Runs are isolated from one another: when one process hosts two live runs, one confined and one not, the commands of each follow the setting in force when that run began. An altered confinement setting applies to the next session started, with no re-registration or process restart.
- **REQ-SANDBOX-097** — Ordering at launch: the availability decision is settled before the run does anything else, so a request for confinement the host cannot deliver fails immediately with that mechanism's reason rather than at the first shell command — and certainly never by executing that command unconfined. When it fails, the session lock is released and anything this launch created is cleaned up. The decision is written into run state before the session is announced as ready.

### Downgrade of unattended permissive runs

- **REQ-SANDBOX-098** — The confinement input to permission-mode resolution requires both selection AND availability. Confinement that is selected but cannot start counts as absent for the purposes of tightening, and the terminal additionally refuses every command, so the run ends up more restricted, never quietly less. Treating it as present would remove the tightening while commands executed unconfined — precisely the combination this requirement exists to prevent. Whether such a run reaches the point of refusing commands at all, or never starts (REQ-SANDBOX-095), is Open Question 9.
- **REQ-SANDBOX-099** — Resolving the effective mode: a requested mode whose default decision is allow (currently `autonomous`) becomes `ask` when all three of the following hold — the run has no interactive approver, confinement is not active, and the workspace has not opted in. Any single one of those three being false leaves the requested mode in place. `ask` and `restricted` are unchanged; an unrecognized name first becomes `restricted` and so is never tightened further; a missing or empty name becomes `ask`. Resolution never raises an error.
- **REQ-SANDBOX-100** — Resolution yields four things: the mode that will apply, the mode that was requested, a flag true only when the applied mode is more restrictive than the requested one, and a user-facing reason. The reason is produced only while that flag is true, and it names both modes, states that nothing can answer an approval prompt for this run and that confinement is not active, and quotes `runtime.allow_unsandboxed_autonomous: true` as the workspace setting that keeps the requested mode in place. When the flag is false the applied mode equals the requested mode and no reason is shown.
- **REQ-SANDBOX-101** — A run counts as attended when, at the moment its mode is resolved, the session has an approval channel registered that can put a prompt to a person; otherwise it is unattended and eligible for tightening. Only the presence of that channel is tested, not whether it later answers: an unanswered prompt is settled instead by `runtime.approval_timeout_seconds` and `runtime.headless_approval_policy` (REQ-SANDBOX-053, REQ-SANDBOX-102). Command-line runs placed in the background, headless runs, and any surface that registers no approver are unattended and are tightened; a desktop session with a live prompt surface is attended and keeps its requested mode.
- **REQ-SANDBOX-102** — Tightening never goes further than `ask`. Where no prompt can be shown, each such ask is then settled by `runtime.headless_approval_policy` (default deny; `abort` halts the run).
- **REQ-SANDBOX-103** — Each agent in a run resolves its own effective mode against the conditions in force when that agent starts work — whether a prompt can be answered for the session, whether confinement is active, and the value of `runtime.allow_unsandboxed_autonomous` — so a change to any of those inputs governs agents that start afterwards without the run being restarted. The requested mode is whichever of these is present, highest precedence first: a persona-level pin, then a session-level override, then `runtime.permission_mode`. Where that agent is tightened, a warning naming the persona it applied to is logged.
- **REQ-SANDBOX-104** — The announcement made at run start stamps the effective permission mode, the confinement flag, and the backend name from one reading of status, so the stored snapshot and the mode decision cannot conflict. Tightening is surfaced three ways: a logged warning; a system message in the run transcript; and a diagnostics timeline event `permission_mode_downgraded` (actor `permissions`) with metadata `requested_mode` and `effective_mode`.
- **REQ-SANDBOX-105** — The chain end to end: for an `autonomous` run with no available approver, where the launcher exists but the trial fails, the run proceeds under `ask` and is recorded as unconfined (this half is subject to Open Question 9, which asks whether such a run starts at all); on the same host once the trial succeeds, the run keeps `autonomous` and is recorded as confined together with the backend name.
- **REQ-SANDBOX-106** — A permission-mode change made part-way through a session is resolved on exactly the terms used at run start (REQ-SANDBOX-099), against that session's approval channel and its current confinement status, and agents already working receive the new mode without a restart. What the session stores is the REQUESTED mode, not the effective one, so agents started later resolve again for the circumstances then in force. A persona-level pin is not always overridden; every persona whose pin is left standing is reported to the caller and listed in `skipped_personas`. Open Question 16 records which direction of change gives way to a pin. The change appends one entry to the session audit log with `event` `permission_mode_change` carrying `timestamp`, `session_id`, `agent_id`, `requested_mode`, `effective_mode`, `previous_mode`, `source`, `reason`, and `skipped_personas`; a companion diagnostics timeline event `permission_mode_changed` (actor `permissions`) repeats `requested_mode`, `effective_mode`, `previous_mode`, `source`, and `skipped_personas`. Failing to write that record never prevents the change taking effect. An override belongs to one session: it is never visible to another run in the same process, and it does not outlive the run, so a resumed session starts again from the mode its configuration names.
- **REQ-SANDBOX-107** — Surfaces that hand off work to be performed without a supervisor produce an advisory before launch. It is empty when such work can proceed (confinement active, or the permissive mode opted into). Otherwise it is a corrective sentence that names the mode that will apply, notes that tightening occurred where it did, explains that every tool call would be refused because no approval prompt can be answered, and lists the corrections — setting `runtime.permission_mode: autonomous` together with `runtime.allow_unsandboxed_autonomous: true`, or enabling `runtime.sandbox_mode`. It advises rather than blocks: because `ask` is the shipped default, blocking would block every workspace that has not been configured. Callers display the advisory and proceed, and the run reports whatever refusals then occur.

### Persistence, events, and audit

- **REQ-SANDBOX-108** — The session snapshot (`state/resume.json` in the session directory) carries `sandboxed` (bool, default false) and `sandbox_backend` (string, default ""), stamped at run start, so a completed session can later be checked for whether its shell ran unconfined. Snapshots written before these keys existed read back as unconfined with an empty backend, which correctly describes those runs, and no schema migration is needed.
- **REQ-SANDBOX-109** — The machine-readable run-start event of a headless/streamed run carries `sandboxed` (bool) — the availability VERDICT, not the configured mode.
- **REQ-SANDBOX-110** — The run-start event carries `permission_mode`, whose value is one of `restricted`, `ask`, `autonomous`. Whether that field must report the requested mode or the effective mode after tightening is not settled here: reporting the requested mode lets an event show `permission_mode: autonomous` alongside `sandboxed: false` while every decision in the run resolves as `ask`, which conflicts with the single-reading stamp REQ-SANDBOX-104 requires. Open Question 6 asks which is canonical. Whichever is chosen, the audit trail (REQ-SANDBOX-104, REQ-SANDBOX-112) is the authoritative record of the mode that actually applied.
- **REQ-SANDBOX-111** — When a non-interactive run asks for confinement the host cannot deliver, it is refused BEFORE the event stream begins: standard output contains a single result event with status `error` whose text carries the mechanism's reason and remediation (for example, that the launcher was absent from PATH, together with how to install it), and the process exits with code 1.
- **REQ-SANDBOX-112** — Permission decisions, the fetch host rules and network-command rules among them, are appended to the session audit log — a JSON-lines file at `<session_dir>/evidence/permissions.jsonl` — each entry recording the identifier of the rule that decided; a refusal states which rule produced it.

### Desktop settings and launch surfaces

- **REQ-SANDBOX-113** — The desktop settings surface (runtime section) exposes all six sandbox/egress settings so that no YAML has to be edited by hand: a sandbox-mode selector; a writable-roots list with an entry field and add button; a toggle for allowing network inside the sandbox; an egress-policy selector; allowed-hosts and denied-hosts lists each with an entry field and add button; and a per-list problem label. All six round-trip: saving writes the workspace config the product loader reads back, and a reopened settings view shows every value on its control.
- **REQ-SANDBOX-114** — Each control validates on the same terms as the stored schema, so nothing invalid can reach the saved policy: entering a relative writable root is rejected at the control with a problem message mentioning "absolute path", with nothing stored and no unsaved-changes state; entering a host pattern with a wildcard other than a single leading one is rejected with a problem message describing the wildcard restriction and showing the supported form `*.example.com`.
- **REQ-SANDBOX-115** — The controls teach the two rules users most often get backwards: the egress-policy description states that a denied host stays denied (deny wins), and the host-lists description states that `*.example.com` does not match `example.com` on its own.
- **REQ-SANDBOX-116** — A label reflects the current availability result: that confinement is turned off, when it is; an active state naming the backend when a non-off mode is selected on a capable host; and, on a host that cannot deliver it, an unavailable state carrying the mechanism's reason and remediation and warning that sessions will fail to start rather than start unconfined. Selecting a mode on such a host is still STORED, since the setting exists for hosts that can honor it.
- **REQ-SANDBOX-117** — Loosening the default disposition to `allow` requires an explicit confirmation first; declining leaves both the stored policy and the control showing the earlier value.
- **REQ-SANDBOX-118** — Saving validates every value against the stored schema before anything is written. If any value is refused, the surface reports which one and writes nothing: the workspace configuration on disk is left exactly as it was and still loads. Reloading the workspace re-reads that file and refills the controls, without marking the form as holding unsaved changes and without writing anything back. Open Question 17 records whether edits not yet saved reach a run started in the meantime.
- **REQ-SANDBOX-119** — The per-session launch dialog offers an enable-OS-sandbox checkbox: checked launches the session with mode `workspace-write`; unchecked with `off`. On a host where the probe reports unavailable, the checkbox is disabled and cleared, and the mechanism's reason AND remediation appear both in the tooltip and as text visible without hovering, since a tooltip alone does not count as informing the user. A workspace that requests no confinement launches as usual.
- **REQ-SANDBOX-120** — Where the workspace configuration itself demands confinement on a host that cannot deliver it, the launch dialog's checkbox remains CHECKED and disabled, so the host never appears to switch the setting off. The run then fails before the agent loop begins, with a notice whose title conveys that the run did not get underway and whose body carries the reason and remediation. Neither a session nor a session lock remains afterwards.
- **REQ-SANDBOX-121** — A workspace indicator naming the backend appears only for a session whose recorded result is confined, and is hidden for sessions that are not. With several sessions open it tracks the focused one, and `sandboxed`/`sandbox_backend` are recorded in each session's snapshot.
- **REQ-SANDBOX-122** — There is no CLI launch flag for the sandbox: CLI and headless surfaces read `runtime.sandbox_mode` from configuration only; only the desktop offers the per-session override.

### Contracts with neighboring subsystems

- **REQ-SANDBOX-123** — Verification checks and probes run through the same terminal enforcement point as everything else, so permission policy, confinement, and timeout-termination semantics apply to them without modification; no separate, less-checked execution path exists for them.
- **REQ-SANDBOX-124** — Lifecycle hooks that the user configures sit deliberately OUTSIDE both confinement and the permission policy: they are the user's own code, executed in the user's shell on the host. Accountability for them rests on the audit trail, and the boundary must be stated in the documentation.
- **REQ-SANDBOX-125** — No model-provider integration may expose provider-side tool execution that steps around these layers: provider-supplied built-in tools are off by default, and any tool call routed from a provider is executed by the product's own execution path so that permission gating and confinement continue to apply.

## Data & Formats

### Configuration fields (workspace/global YAML)

| Key | Type | Default | Values / constraints |
| --- | --- | --- | --- |
| `runtime.network_egress_policy` | string | `ask` | `allow` \| `ask` \| `deny`; case-insensitive; unknown rejected by name |
| `runtime.network_allowed_hosts` | list[string] | `[]` | host patterns; trimmed+lowercased; blanks dropped |
| `runtime.network_denied_hosts` | list[string] | `[]` | host patterns; same normalization |
| `runtime.sandbox_mode` | string | `off` | `off` \| `workspace-write` \| `read-only`; YAML boolean false reads as `off` |
| `runtime.sandbox_writable_roots` | list[string] | `[]` | absolute paths only; POSIX and Windows spellings accepted |
| `runtime.sandbox_allow_network` | bool | `false` | meaningful only when sandbox on |
| `runtime.allow_unsandboxed_autonomous` | bool | `false` | per-workspace opt-in |
| `runtime.permission_mode` | string | `ask` | `restricted` \| `ask` \| `autonomous` |
| `runtime.headless_approval_policy` | string | `deny` | `deny` \| `abort`; unknown behaves as deny |
| `runtime.approval_timeout_seconds` | number | `300.0` | `0` = wait without limit |
| `runtime.tool_timeout` | number | `30` | fetch default timeout when run-wired |

Workspace config lives at `<workspace>/.rotaris/agents.yaml` and overrides the global config per field.

### Host pattern grammar

`pattern := exact-host | "*." host` — a single leading `*.` and nothing else; comparison by whole label; the wildcard stands for at least one leading label and does not include the bare name itself; any other use of `*` is a configuration error.

### Fetch result shape

Fields: `url` (requested), `final_url`, `status_code` (null on refusal), `content_type`, `truncated` (bool), `failure_kind`, `timeout_seconds`, `error_class`, `detail`.

`failure_kind` vocabulary (fetch): `egress_denied`, `egress_redirect_denied`, `egress_policy_error`, `too_many_redirects`, `timeout`, `network_error`, `http_error`. Egress refusals carry `error_class: NetworkEgressDenied`; the redirect-budget failure carries `error_class: TooManyRedirects`.

Model-facing rendering: failure = error header + `[fetch_diagnostic]` JSON block (sorted keys, nulls omitted) + optional `[fetch_output]`; success = `url:` / `final_url:` / `status_code:` / `content_type:` / `truncated:` header lines + body.

### Terminal observation additions

`failure_kind` vocabulary (terminal): `timeout`, `invalid_request`, `execution_error`, `sandbox_unavailable`. Sandbox refusal observation: exit code `126`, outcome kind `sandbox_unavailable`, severity `error`. Sandbox-launcher output prefixes used for relabeling: `bwrap:`, `sandbox-exec:`, `sandbox_apply:`.

### Network-reaching command pattern catalog (token-prefix; 51 patterns)

An unordered set; listed alphabetically for reading convenience only. Order carries no meaning and there is no first-match precedence — a segment either opens with one of these prefixes or it does not.

`apt install *`, `apt-get install *`, `apt-get update *`, `brew install *`, `brew update *`, `cargo fetch *`, `cargo install *`, `cargo publish *`, `curl *`, `docker pull *`, `docker push *`, `ftp *`, `gh *`, `git clone *`, `git fetch *`, `git ls-remote *`, `git pull *`, `git push *`, `git remote *`, `git submodule update *`, `go get *`, `go install *`, `http *`, `https *`, `nc *`, `ncat *`, `npm ci *`, `npm i *`, `npm install *`, `npm publish *`, `npx *`, `pip download *`, `pip install *`, `pip3 install *`, `pnpm add *`, `pnpm dlx *`, `pnpm install *`, `poetry add *`, `poetry install *`, `rsync *`, `scp *`, `sftp *`, `ssh *`, `telnet *`, `uv add *`, `uv pip install *`, `uv sync *`, `uv tool install *`, `wget *`, `yarn add *`, `yarn install *`.

Compound command lines decompose on `&&`, `||`, `;`, `|`, `&`, and newline; any matching segment classifies the line.

### Permission rule identifiers (observable in refusals and audit)

Format `{mode}:{rule-name}`. Known ids in this domain: `restricted:fetch-remote-host`, `restricted:fetch-local-host`, `ask:fetch-remote-host`, `ask:fetch-local-host`, `restricted:network-command`, `ask:network-command`, `{mode}:read-only-tool`; mode-default decisions appear as `preset:{mode}`.

### Rendered OS confinement invocations

- macOS: `sandbox-exec -p '<profile>' /bin/sh -c '<command>'`, where the profile is default-deny, allows exec/fork/sysctl-read/signal, allows whole-filesystem reads, allows writes to the temp subpaths and device nodes listed in REQ-SANDBOX-075 plus one allowance per writable root, then denies each carve-out (after all allows), then allows or denies network wholesale.
- Linux: `bwrap --die-with-parent --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp [--bind <root> <root> …] [carve-outs] [--unshare-net] -- /bin/sh -c '<command>'`, with carve-outs rendered per REQ-SANDBOX-077 (`--ro-bind-try <p> <p>` when present; `--tmpfs <p>` + `--remount-ro <p>` when absent; nothing when outside writable roots).
- Availability trials: `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` (macOS); on Linux, the product's own read-only-rooted rendering with the network namespace unshared, ending in a program that exits 0 — whether those final tokens are `-- true` or `-- /bin/sh -c 'true'` is Open Question 13. Trial timeout 5.0 s.

### Persistence and event shapes

- Session snapshot `state/resume.json`: keys `sandboxed` (bool, default false), `sandbox_backend` (string, default ""). Older snapshots without the keys read as unsandboxed.
- Run-start stream event: includes `sandboxed` (bool, availability verdict) and `permission_mode` (see REQ-SANDBOX-110 and Open Questions).
- Diagnostics timeline event on downgrade: name `permission_mode_downgraded`, actor `permissions`, metadata `requested_mode`, `effective_mode`.
- Diagnostics timeline event on a mid-session mode change: name `permission_mode_changed`, actor `permissions`, metadata `requested_mode`, `effective_mode`, `previous_mode`, `source`, `skipped_personas`.
- Permission audit log: JSON lines at `<session_dir>/evidence/permissions.jsonl`; entries name the deciding rule id. A mid-session mode change appends an entry with `event: permission_mode_change` plus `timestamp`, `session_id`, `agent_id`, `requested_mode`, `effective_mode`, `previous_mode`, `source`, `reason`, `skipped_personas` (list of strings, empty when no persona pin was left standing).
- Process exit codes: headless run refused for an unavailable sandbox exits 1; a sandbox-refused command's observation reports exit code 126.

REQ-SANDBOX-095 against REQ-SANDBOX-098 and REQ-SANDBOX-105: on a host that cannot deliver a selected confinement mode, does session start fail outright and leave no session (REQ-SANDBOX-094, REQ-SANDBOX-095, REQ-SANDBOX-111, REQ-SANDBOX-116, REQ-SANDBOX-120), or does the session start with every command refused as `sandbox_unavailable` (REQ-SANDBOX-083, REQ-SANDBOX-098), so that a tightened run proceeds and is recorded as unconfined (REQ-SANDBOX-105)? 10. REQ-SANDBOX-020: what does `timeout: 0` mean for a fetch — no time limit, as `runtime.approval_timeout_seconds: 0` means for approvals, or a deadline that has already expired? And what does a request carrying an invalid parameter (a negative `timeout`, `from_line` greater than `to_line`, `max_lines` of zero or less) return, given that the fetch `failure_kind` vocabulary has no member for a malformed request?
11. REQ-SANDBOX-050: is an entry of `runtime.sandbox_writable_roots` that is empty or whitespace-only dropped, as a blank host pattern is under REQ-SANDBOX-004, or refused as not absolute? And is a configured root that does not exist on the host at launch an error, or silently skipped?
12. REQ-SANDBOX-065: which platform identifier strings beyond the current one for each family must be recognized as Linux and as macOS? The set of legacy identifiers is not enumerated anywhere in this domain, so the mapping cannot be tested exhaustively.
13. REQ-SANDBOX-070 against REQ-SANDBOX-079 and Data & Formats: does the Linux availability trial end in `-- true`, or in the `-- /bin/sh -c 'true'` form every rendered session invocation uses? The trial is described both as the product's own rendering and as ending in a bare `true`.
14. REQ-SANDBOX-078: when a carve-out mount cannot be established at launch, is only that command refused (REQ-SANDBOX-083, exit code 126), or does the whole session end? Both readings appear in this domain.
15. REQ-SANDBOX-085: does the launcher-prefix test apply to standard error alone, or to standard output and standard error as captured together? The answer decides whether a command that writes an ordinary line to stdout before the launcher fails is relabelled.
