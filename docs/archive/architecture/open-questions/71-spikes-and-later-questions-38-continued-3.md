**OQ-537 — While no provider is authenticated, does the Overview's onboarding empty state keep its first-use copy and its filled “Open Workspace”, or name the precondition and offer Settings?** *(REQ-MONITOR-165, REQ-NOTIFY-006, REQ-NOTIFY-010, REQ-WORKSPACE-152, REQ-WORKSPACE-137. Raised 2026-11-03 by [R-093](../../../product/requests.md#r-093), the Overview audit of 2026-11-02, candidate (a) ([the brief](../../../design/briefs/overview.md)); numbered from OQ-493: OQ-462 to OQ-492 are the hardening orchestration's.)*

**What is open.** REQ-MONITOR-165: “An onboarding empty state is shown when there is nothing to display”. It fixes no copy. REQ-NOTIFY-006 asks for “at least one instruction or control that would put something in it”, and REQ-NOTIFY-010 for “a primary action appropriate to what it holds”. With no provider authenticated, “Open Workspace” succeeds, but the run it leads to is refused by REQ-WORKSPACE-137. The step that succeeds is the no-provider notice's “Add a provider” (REQ-WORKSPACE-152 (3)). The Overview audit (item 2, candidate (a)) found that the first-launch journey misleads at that control, and guide 04 §6 checks for a notice with a notice action rather than first-use copy.

**What the build proceeds under.** The empty state as built under REQ-MONITOR-165, which fixes no copy. Audit item 2 waits on this question.

**What decides it.** A reading of REQ-NOTIFY-006 and REQ-NOTIFY-010 for the Overview: while no provider is authenticated, the hint and control key to the precondition (REQ-WORKSPACE-137's “Open Settings”), or the first-use copy stands.

Ruled as the keyed reading, with no directive. REQ-NOTIFY-006 asks for a sentence naming why the region holds nothing and a control that would put something in it; with no authenticated provider the Overview holds nothing because no run can start, and "Open Workspace" leads to the step REQ-WORKSPACE-137 refuses, so it puts nothing in the region and today's hint names the wrong reason. The predicate is the one main already raises the notice from (`providers.list().some((row) => row.authenticated)`), so the hint and the notice cannot disagree; no channel, store column or state owner is added. The ruling binds this view and this predicate only and licenses no empty state keyed to another condition; REQ-WORKSPACE-137's other refusal, "No model configured" with a provider authenticated, was not measured and is left alone. The hint's voice belongs to OQ-515; this ruling fixes its terms, not its tone. It executes as `build-ui` on the Overview's empty state (audit item 2), with the `overview-proof` suite's `empty` launch asserting the keyed hint and control and a launch with an authenticated provider holding today's copy, captured under §7's "Overview" row. **OQ-538 — Should a tile that cannot hold a figure in this build, Cloud credit, keep the first place in the Overview's right column?** *(REQ-MONITOR-173. Raised 2026-11-03 by [R-093](../../../product/requests.md#r-093), the Overview audit of 2026-11-02, candidate (e) ([the brief](../../../design/briefs/overview.md)); numbered from OQ-493: OQ-462 to OQ-492 are the hardening orchestration's.)*

**What is open.** REQ-MONITOR-173 puts “the cloud-credit tile first (the balance determines whether provider quotas are reachable at all)”. In a build where no hosted account can connect, the tile holds only `—` (the Overview audit, candidate (e)).

**What the build proceeds under.** REQ-MONITOR-173's order.

**What decides it.** One ruling: the order stands, or a directive over REQ-MONITOR-173 lowers or hides the tile while no account can connect.

**Ruled 2026-11-03 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended that REQ-MONITOR-173's order stand with no directive and that the bare `—` tile be drawn as the signed-out rendering REQ-PROVIDER-120 already fixes; Advocate B (the system's lens) recommended the same, with a defect note first and `build-ui` on the credit tile. Ruled: the order stands, read as written, and no directive is minted. Three grounds in the record decide it. First, REQ-MONITOR-173 carries its own reason, "the balance determines whether provider quotas are reachable at all", which no build suspends: REQ-SHELL-158 starts the start-anyway confirmation from the same balance, and the first place is where a reader learns whether a hosted account exists and what it gates. Second, the entry's alternative, hiding or lowering the tile while no account can connect, is a state no requirement admits: REQ-MONITOR-185 says the `signed_out` phase "has something to show, so the tile is never drawn as an empty card", REQ-NOTIFY-209 says none of the four phases "renders as blank or as an absence", and REQ-PROVIDER-120 fixes the signed-out rendering to the letter: value `—`, tag "Not signed in", detail "Sign in to Rotaris Cloud to see your credit." and a "Sign in" button as the only control. A directive over REQ-MONITOR-173 alone could not reach it; one narrowing all three, keyed to a build condition no operator can observe, would be lifted the day ADR-0048's "no hosted account in this build" stops being true. Third, the record already places absence where it belongs: REQ-SHELL-046 and REQ-MONITOR-178 withhold the status-strip chip until a balance is ready; the Overview tile is the surface that explains the state. Candidate (e) is therefore a conformance gap, not a fault in the order: the built tile draws a bare `—` and invented copy where REQ-PROVIDER-120 fixes title, tag, detail and control, and §1.11 of [the design language](../../../design/README/01-1-the-design-language.md) says the specification's wording wins over invented copy; the tile reads as a metric card because it is drawn as one, and item 9's seam repair stands beside this. The build proceeds under REQ-MONITOR-173's order unchanged, PD-LIBRARY-002 untouched; nothing in `docs/product/` or §1 moves. What executes it: `build-ui`, on the Overview's cloud-credit tile, drawing REQ-PROVIDER-120's signed-out rendering with the state carried by tag text and outline shape (REQ-MONITOR-188), the strings verbatim, after a defect note under `docs/defects/` records the shortfall against REQ-PROVIDER-120 and REQ-MONITOR-185; its evidence is `pnpm overview-proof`'s `empty` and `run` launches and a `review-ui` capture of the signed-out tile. Whether "Sign in" can complete with no reachable hosted service is not settled here; if it cannot, the refusal is REQ-SHELL-040 and REQ-SHELL-112's, in the same note, with the hosted-cloud work `docs/architecture/codebase/` lists as owed. What reopens it: a `review-ui` pass after the correct rendering and item 9's seam are built that still finds the first card read as filler or as a metric card; a ruled answer that no build will ever connect a hosted account, which removes the stated reason; or an owner request that builds without a hosted service omit the hosted-cloud surfaces, logged in `docs/product/requests.md`, not the consortium's to make.

**OQ-485 — Does main leave a line in the application log for a message it refuses at a process boundary?** *(ADR-0002 consequence 11, ADR-0044, PD-MONITOR-002, `docs/architecture/hardening.md` §3.5 row 7. Raised 2026-11-04 by hrd2's bundle F3 (`thin-packages`), building the process link's tests; numbered in the hardening orchestration's range.)*

**What is open.** `ProcessLink` (`packages/shell/src/process-link.ts`) reads every message from a child with `ProcessMessageSchema.safeParse` and drops one it cannot read with no trace: nothing is logged and the request it may have answered stays pending. A run host or workspace service speaking another contract version (`v`), or a reply kind main does not know, therefore reads in main as `NoReplyWithinBound` at the request's bound, with nothing in the log that says a message arrived and was refused. No requirement or decision says whether such a drop is recorded; the brief that raised this assumed it was ("dropped and logged").

The renderer's boundary is the same shape. `dispatchCommand` (`apps/desktop/src/main/command-dispatch.ts`) answers a request `CommandRequestSchema` cannot read, or one past OQ-467's bounds, `command.malformed` as a value and writes no line, where a throwing handler leaves one `error` line and a refused sender one `warning` line. `pnpm driver-proof` step 9e measured it on 2026-11-04: an unknown kind and a 2,000,000-character prompt sent by the page itself each left no line of the product's.

**What the build proceeds under.** Both as built: the process link's drop silent, the request left to its deadline and the next valid message answered (`packages/shell/src/process-link.test.ts`), and a malformed command answered with no line (`driver-proof` step 9e), each citing this entry.

**What decides it.** A ruling on whether a refused process message leaves one line (at which level, naming what, under PD-MONITOR-002's rule that the log never carries a payload) or stays silent, and whether a burst of them is bounded.

**Ruled 2026-11-04 under the owner's delegation (R-072).** Advocate A (the user's lens) recommended one `warning` line per refused message at each boundary, naming the child or the window, the class of refusal, the issue paths capped so they cannot become a payload, and the pending `id` where readable, with the first refusal of a class written in full and the rest of a 60 s window counted into one line at its close or at the link's end; Advocate B (the system's lens) recommended the same line and level through an injected callback the shell takes from main, with an unknown kind never echoed because it is the page's own string, and bursts folded per link and per sender to at most one line per 60 s carrying the count. Ruled with both, the system's advocate's rule on what the line may name folded into the user's advocate's bound: a message refused at either process boundary leaves one line in the application log at `warning`, and a burst of them is bounded. The ground is PD-MONITOR-002 read with its first execution: the log a packaged build keeps "is the one a person can read after an incident", main's own line for something refused or not done is `warning` and only a loss is `error`, and a dropped message loses nothing main owns, since the request is still answered by its deadline, so `warning`, which the default threshold keeps. ADR-0044's Versioning bullet names the very case this silence hides, "a stale renderer survives an in-place update", and its consequence 4 wants a dropped payload observable rather than a silent divergence; its consequence 3 (main adds no work on the relay path) is met because the line is written on the failure branch only and the bound keeps a flood from becoming event-loop load. ADR-0002 consequence 11(b), every acknowledgement bounded and expiry refusing rather than proceeding (the clause `ProcessLink`'s header cites as "consequence 11"), is unchanged: a request whose reply main could not read still ends `NoReplyWithinBound` at its bound, and answering it early on a readable `id` is a protocol change this ruling does not make and this entry does not ask for. What the line names, and never carries, follows OQ-467 and PD-MONITOR-002: at the process link, the child (run host or workspace service), the class (a contract version `v` against `CONTRACT_SCHEMA_VERSION`, both numbers given where `v` is a number and "not a number" where it is not; a reply or event kind main does not know, the kind's text never echoed; a shape it cannot read), the first issue paths cut to a fixed depth and length, and the pending `id` where it is a number; at the renderer boundary, the window the request was raised for and `malformedHeadline`'s text, which names the field and the bound, and the `kind` only where it is a member of the command union. No value and no payload reach the log by any route, the command's request least of all. The bound is per boundary and per class (per link at the process link, per sender at the renderer): the first refusal of a class opens a 60 s window on the clock ports (`rotaris/no-bare-timers`) and is written in full, refusals inside the window are counted, one line gives the count when the window closes or the link is closed or ended, and the next refusal after that opens a new window, so a flooding child or a compromised page writes at most two lines per class per minute. `packages/shell` takes the sink injected, as main's `appLog` wired at both `ProcessLink` constructions in `apps/desktop/src/main/index.ts`, because the shell may not import Electron. No requirement addresses a refused process message, so this fills a gap and departs from none; no directive is minted. The build proceeds under this ruling: `process-link.ts` and `command-dispatch.ts` write the line and keep the bound; `process-link.test.ts` turns the silent-drop case into one line, no payload, the request still waiting to its bound and the next valid message answered, plus a burst folded on `FakeClock`; command-dispatch's tests assert the `warning` line and a property case that no payload substring reaches it; `pnpm driver-proof` step 9e reads exactly one `warning` line per malformed command with the 2,000,000-character prompt and the unknown kind's text absent, the whole driver suite rerun per `pnpm verify:plan`; `docs/architecture/hardening.md` §3.5 row 7, the process view (`views/02`) and `driver-proof`'s record cite this ruling in the same commit, and one row goes to `first-executions.md`.
