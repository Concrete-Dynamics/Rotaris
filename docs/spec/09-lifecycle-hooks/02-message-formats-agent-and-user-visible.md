# User-Defined Lifecycle Hook Commands — Message Formats (Agent- and User-Visible)

Part 2 of 6 of [domain 09](../09-lifecycle-hooks.md), which indexes every part. Defines REQ-HOOKS-049 – REQ-HOOKS-089.

### Message Formats (Agent- and User-Visible)

- **REQ-HOOKS-049** — The refusal an agent receives from a stopping `pre_tool` hook SHALL be exactly: `Blocked by hook '<name>'. <reason> The '<tool>' call was not executed. Choose a different approach or ask the user to adjust the hook configuration.` With an empty tool name the middle sentence reads `The call was not executed.`

- **REQ-HOOKS-050** — The `<reason>` in the refusal SHALL be: the hook's trimmed standard error; or `The hook gave no reason.` when the hook exited 2 having written nothing to standard error; or `The hook timed out after <budget> s.` when a `required` hook timed out; or `The hook could not be started.` when a `required` hook failed to launch.

- **REQ-HOOKS-051** — `post_tool` feedback text SHALL be: `Hook '<name>' reported after the '<tool>' call: <stderr>` (or `after the call:` with no tool name); empty standard error renders as `(the hook wrote nothing to stderr)`. Where one call produces several such texts they SHALL be joined with `\n` before delivery.

- **REQ-HOOKS-052** — Warning texts SHALL be:
  - launch failure: `Hook '<name>' (<event>) could not run: <crash reason>`
  - timeout: `Hook '<name>' (<event>) timed out after <budget> s and was terminated.`
  - abnormal termination, the process having been ended without an exit status by something other than the timeout path (REQ-HOOKS-039): a warning conveying the hook's display name, its event, and that the process was ended before it could return an exit status. It SHALL NOT quote a platform signal number, SHALL NOT read as a timeout, and SHALL NOT take the "exited `<code>`" form, which is reserved for a process that did exit; the wording is otherwise left to the implementation.
  - exit code with no assigned meaning: `Hook '<name>' (<event>) exited <code>.` followed, where either stream produced text, by an excerpt taken from standard error — or from standard output where standard error is empty — with each run of whitespace reduced to a single space and the result limited to 200 characters, a trailing `…` marking an excerpt that was cut. The 200 characters count the retained text alone and the `…` is appended beyond them, under the truncation rule of REQ-HOOKS-037. How the excerpt is joined to the sentence before it is left to the implementation, subject only to the excerpt remaining separately identifiable as the hook's own output rather than reading as a continuation of the sentence.

  `<name>` is the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); `<event>` is one of the seven event names. `<budget>` SHALL convey the hook's configured `timeout_seconds` as a number of seconds; how many decimal places it carries, and whether a whole number is written bare, are left to the implementation, provided one rendering is used consistently wherever a budget reaches the user or the agent in this domain (REQ-HOOKS-050).

- **REQ-HOOKS-053** — On the invocation that reaches the switch-off limit (see REQ-HOOKS-055), the warning SHALL gain, on that occasion only: `Hook '<name>' failed <count> times and is disabled for the rest of this session.`

- **REQ-HOOKS-054** — At the end of a run the switched-off-hook advisory SHALL be delivered on the host's notice channel (REQ-HOOKS-087). It SHALL be the empty string where that run switched no hook off. Otherwise it SHALL convey `<N>` — the number of hooks switched off under REQ-HOOKS-055 — that they were switched off for the rest of this session after failing repeatedly, and where the command output can be read (REQ-HOOKS-137). Like every user-facing count in this domain (REQ-HOOKS-101, REQ-HOOKS-106), the advisory SHALL be grammatically correct for the count it carries, so an `<N>` of 1 reads in the singular throughout and no `hook(s)` or `was/were` construction is emitted literally; the wording is otherwise left to the implementation. The advisory SHALL disclose that count and nothing further: no hook name, no command, no matcher, and no other configuration text SHALL appear in it. Hook warnings SHALL reach the user's warning channel only; no hook warning text SHALL appear in anything delivered to the agent.

### Failure Budget and Auto-Disable

- **REQ-HOOKS-055** — Once one hook (identified by stable id) has failed three times inside a single session, it SHALL be switched off and not invoked again before that session ends. The switch-off warning is emitted on the third failure and on no other occasion; afterwards the hook is skipped without comment — zero outcomes, no further warnings. (Five failing rounds therefore produce outcome counts 1, 1, 1, 0, 0 with exactly one switch-off warning.)

- **REQ-HOOKS-056** — Once switched off, the hook's id SHALL be visible in the engine's set of switched-off hooks, and an event whose hooks have all been switched off reports "no hooks". Failure tallies and the switched-off set belong to a single session; the next run begins with both empty.

### Payload Content and Redaction

- **REQ-HOOKS-057** — A tool payload SHALL always carry exactly the keys `event`, `tool_name`, `arguments`, `session_id`, `workspace` (path as a string), and `command` (the empty string for a tool that has no shell command, so that a hook script may index all six keys unconditionally). The `result` key SHALL appear only when a result exists — in practice only on `post_tool`; a `pre_tool` payload never has it.

- **REQ-HOOKS-058** — A lifecycle payload SHALL always carry `event`, `session_id`, and `workspace`; whatever fields the particular occurrence contributes are placed as siblings of those three, not nested under a sub-object. An occurrence that contributes no fields produces a payload of exactly those three keys.

- **REQ-HOOKS-059** — The names `event`, `session_id`, and `workspace` SHALL be reserved: caller-supplied lifecycle fields using those names are dropped without comment, so event data cannot impersonate the session identity that a shared hook script may branch on.

- **REQ-HOOKS-060** — Secret masking SHALL follow the payload's structure and reach every level of it: every string, however deeply nested, is passed through one common masking routine, and the surrounding shapes are left as they are rather than being flattened.

- **REQ-HOOKS-061** — Masking SHALL be the one shared redaction pass of REQ-TOOLS-171, applied to hook text exactly as it is applied to every other surface that carries tool arguments or configuration text. This domain declares no masking of its own and holds no copy of the pass's ordered layers, of the credential value prefixes it recognizes, or of the mask string; which key and flag names count as credential names is the test of REQ-TOOLS-172, of which this domain likewise holds no copy. What this domain relies on that pass for is that a recognized value is replaced while the text around it stays legible, so `Bearer sk-live-1` becomes `Bearer ***` and `Bearer` stays readable, and that masking is idempotent, so masking an already-masked string leaves it unchanged. Three further properties of that pass are what make the payload contract of REQ-HOOKS-067 checkable, and they SHALL hold wherever hook text is masked. First, the value a layer replaces SHALL extend over exactly one value token and no further: where the value opens with a single or a double quote it ends at the matching closing quote and the quote characters themselves are retained around the `***`; otherwise it ends at the first whitespace character following it, or at the end of the string where none follows — so `--token abc def` masks to `--token *** def`, `password: a b` masks to `password: *** b`, and `password: "a b"` masks to `password: "***"`. Second, the `Bearer`, `Basic`, and `token` scheme keywords SHALL be compared without regard to case, so that `bearer`, `BASIC`, and `Token` trigger masking exactly as they do. Third, the credential names and value prefixes that pass recognizes SHALL be a complete set rather than an open one: an implementation recognizing exactly them and nothing further is conformant, and no further name, prefix, or resemblance-based heuristic SHALL be added, so that a string carrying none of them is guaranteed to reach a hook unaltered (REQ-HOOKS-062).

- **REQ-HOOKS-062** — A string stored under a mapping key that names a credential SHALL arrive as `***` in its entirety, whatever the string looks like: `{"password": "the meeting is at noon"}` reaches the hook as `{"password": "***"}`. A string stored under any other key SHALL arrive unaltered but for whatever the passes of REQ-HOOKS-061 find within it, so `{"note": "run the tests"}` arrives verbatim. A mapping key names a credential exactly when it meets the secret-looking key-name test of REQ-TOOLS-172, which this requirement cites and does not restate, so a name is a credential name both as a mapping key and as the left-hand side of a `key=value` assignment inside a string. Where a credential-named key holds a list or a mapping rather than a string, the container SHALL NOT be replaced wholesale: its shape SHALL be preserved as REQ-HOOKS-060 requires, and every string within it, at every depth and whatever the intervening keys are called, SHALL arrive as `***` in its entirety exactly as though it were itself stored directly under a credential-named key. Non-string scalars within such a container are unchanged, and the container's own nested mapping keys are masked under REQ-HOOKS-063. So `{"tokens": ["abc", {"live": "def"}]}` reaches the hook as `{"tokens": ["***", {"live": "***"}]}`, which both keeps the structure a hook script indexes into and leaks nothing.

- **REQ-HOOKS-063** — Building a payload SHALL always produce one JSON object that parses (REQ-HOOKS-067), SHALL never fail, and SHALL never alter the caller's data. The substitutions below apply at every nesting level:
  - A value JSON cannot express is written as its text form; where producing that text form itself raises, the placeholder `<unrepresentable <TypeName>>` is written instead, `<TypeName>` naming the value's type.
  - Ordered and unordered collections are written as JSON arrays; not-a-number and positive and negative infinity are written in text form so that the document stays valid JSON; raw byte values are decoded as UTF-8 with replacement and then masked.
  - A container encountered again while it is still being walked is written as `"<recursive>"`; a value merely referenced from two places is written out in full at each of them.
  - A value nested more than 12 levels deep is written as its masked text form.
  - Mapping keys are converted to text and masked.
  - Where iterating the top-level mapping itself raises, the result is still a JSON object: a single key `payload` holding the masked text form of the offending value.

  Depth SHALL be counted with the top-level payload object at level 0, the values it holds directly at level 1, and so on; a value lying at a level greater than 12 is the one written as its masked text form. Not-a-number, positive infinity, and negative infinity SHALL be written as the JSON strings `"NaN"`, `"Infinity"`, and `"-Infinity"` respectively, which keeps the document parseable by a hook script that does no more than call a standard JSON parser.

- **REQ-HOOKS-064** — Masking an already-masked payload SHALL change nothing, and the caller's own data SHALL still hold the original values afterwards, since masking works on a copy.

- **REQ-HOOKS-065** — Where the engine is wired into real tool dispatch, arguments SHALL be shaped as follows: for the `terminal` tool, `arguments.command` holds the shell line next to the action's other (masked) fields; for a tool provided over MCP, that tool's own fields sit under `arguments.data` (so `arguments.data.api_key` arrives as `"***"`).

- **REQ-HOOKS-066** — The `post_tool` payload's `result` SHALL render what the agent was given for that call: `{"observation": "<text>"}` where the call produced an observation, `{"error": "<text>"}` where it produced an error (REQ-HOOKS-005). Where the call produced exactly one such item, `result` is that object; where it produced several, `result` is an array of them in the order the agent received them; where it produced none, the `result` key is absent altogether. Each `<text>` SHALL be limited to 4096 characters, and text that was cut SHALL end with the marker `\n[truncated: <total> characters]`, `<total>` being its length in characters before cutting. The 4096 characters count the retained text alone and the marker is appended beyond them, under the truncation rule of REQ-HOOKS-037.

- **REQ-HOOKS-067** — The bytes written to standard input SHALL form one valid JSON document and nothing else, and decoding it SHALL reproduce exactly the structure described in REQ-HOOKS-057 to REQ-HOOKS-066. Characters outside ASCII are carried as UTF-8. A Windows path such as `C:\repo\src` is escaped on the wire and decodes back to one backslash per separator. A hook that reads standard input to end-of-input, decodes UTF-8, and parses the result as JSON therefore recovers the payload unchanged, with no framing, length prefix, or second document to strip first. No trailing newline and no other trailing byte SHALL follow the object: the last byte written is the closing brace, as REQ-HOOKS-031 requires, so a hook comparing raw bytes and a hook parsing them agree on where the document ends.

### Tool-Dispatch Integration

- **REQ-HOOKS-068** — Tool hooks SHALL sit entirely within the branch the permission engine takes for permitted calls: only a permitted call reaches hook dispatch, and a denied call gets the permission system's own refusal with no hook process started. It follows that a `pre_tool` hook whose matcher targets something the built-in policy always denies (for example destructive commands rejected in every mode) will never fire; hooks cover the cases the policy leaves open.

- **REQ-HOOKS-069** — Hooks SHALL be attached per session and looked up per call: changing a session's attached hook set takes effect on the very next call, and a session with nothing attached dispatches exactly as though the feature were absent (one lookup and nothing more, with no extra content added to results). Attaching under an empty session identifier SHALL be rejected with an error; looking up an empty or unknown identifier yields nothing; detaching an unknown identifier does nothing and is not an error; attaching again replaces the previous set entirely.

- **REQ-HOOKS-070** — Sessions SHALL be isolated from one another: hooks attached to one session never fire for another session's tool calls, and there is no fallback to some other session's set. A tool call belonging to no session runs no hooks.

- **REQ-HOOKS-071** — A `pre_tool` stop SHALL reach the agent as an error result bearing the same call correlation id and tool name as the attempted call, containing the refusal text unchanged, delivered on the tool-result channel so the agent can choose another approach. The tool itself is never invoked for a stopped call.

- **REQ-HOOKS-072** — Stopping a call SHALL count as one refused tool invocation and nothing more: the run's terminal status is untouched by it, and the agent goes on to its next piece of work.

- **REQ-HOOKS-073** — The dispatcher SHALL consult hooks only for the events the session has actually declared hooks for: a session declaring only `post_tool` hooks incurs no cost at `pre_tool`.

- **REQ-HOOKS-074** — `post_tool` feedback SHALL travel in the same correlated result message that carries whatever the tool itself returned, so that no additional content is placed between an assistant's tool-call block and the corresponding results — an arrangement some model providers reject when several calls are issued together. Where the call produced no observation (the tool errored), the feedback SHALL instead be delivered as a following user-role message so that it is not dropped.

### Lifecycle Event Delivery

- **REQ-HOOKS-075** — Lifecycle payloads SHALL carry these data fields beside the three base keys of REQ-HOOKS-058. A string field whose value is absent SHALL be rendered as `""`; a string field holding a value of an unexpected type SHALL be converted to text, and where that conversion fails the field SHALL be `""`. An `iteration` that is not a whole number SHALL be reported as `0` (REQ-HOOKS-077). No field value can cause payload construction to fail.
  - `session_start`: `task` (string) — the run's own statement of the task, which need not repeat the user's prompt word for word.
  - `session_end`: `status` (string) — the run's terminal status, or `""` where no status could be derived, which consumers SHALL read as *unknown* and not as failure.
  - `child_completed`: `child_id`, `child_name`, `persona`, `state`, `status`, `summary` (all strings).
  - `verifier_finished`: `iteration` (integer), `executed` (boolean), `passed` (boolean), `skip_reason` (string), `failed_checks` (array of strings — the names of the failed checks that block).
  - `iteration_end`: `iteration` (integer), `outcome` (string), `child_name` (string), `status` (string), `summary` (string).

  The vocabularies these fields carry are owned by other domains and SHALL be exactly those, not a parallel set defined here. `session_end.status` carries one value of the run status vocabulary of REQ-EVENTS-026 — `completed`, `failed`, `max_iterations`, `interrupted`, `error` — or `""` where no status could be derived. `child_completed.state` carries the child's terminal state under REQ-ORCH-041: `succeeded`, `failed`, `cancelled`, or `blocked`. `child_completed.status` carries the child's report status under REQ-ORCH-112: `succeeded`, `partial`, `failed`, `cancelled`, or `blocked`. `iteration_end.outcome` carries the report status, after any rewrite, that REQ-ORCH-074 dispatched on, drawn from that same report-status vocabulary. `iteration_end.status` carries the terminal state recorded for the iteration's own record under REQ-ORCH-041 — which is why the two fields exist side by side and may legitimately differ, a `blocked` outcome being recorded as a `succeeded` iteration. A value the owning domain does not list SHALL be carried through as text rather than corrected or dropped, and `""` SHALL be read as *unknown* and never as failure.

  `executed` and `passed` SHALL always be present and SHALL always be JSON booleans: an occurrence supplying neither, or supplying a value that is not a boolean, yields `false` — never `""`, never an absent key, and never a string — so a hook script may test them without first checking their type. The `""` fallback of this requirement governs string fields only, and the `0` fallback of REQ-HOOKS-077 governs `iteration` only.

- **REQ-HOOKS-076** — Each lifecycle occurrence SHALL fire each attached hook exactly once. In a run in which all five events occur once, the order is `session_start`, `child_completed`, `verifier_finished`, `iteration_end`, `session_end`, matching where each occurs.

- **REQ-HOOKS-077** — Iteration numbers in `iteration_end` payloads SHALL begin at 1 for the first completed iteration and follow the loop from there (iterations 1, 2, 7 report 1, 2, 7, never a fixed 0). An iteration value that is not a whole number is reported as 0.

- **REQ-HOOKS-078** — Given a run with no hooks for a lifecycle event, no payload SHALL be assembled and no process started for occurrences of that event.

- **REQ-HOOKS-079** — A lifecycle occurrence SHALL always complete. A hook that cannot be executed SHALL yield the matching warning of REQ-HOOKS-052; data the payload cannot render SHALL be substituted per REQ-HOOKS-063 with no warning at all; any other fault raised while delivering the event SHALL reduce to a log entry. In each case the occurrence's remaining hooks still run, the run continues to its next step, its terminal status is unaffected, and no error reaches the agent. No such condition SHALL hold the run beyond the per-hook bound of REQ-HOOKS-033.

- **REQ-HOOKS-080** — Lifecycle hooks SHALL run in line with the run loop: a hook that consumes its whole budget holds the run up for that long, and `timeout_seconds` is the user's means of controlling this. Ordering guarantees: the `iteration_end` hook for iteration N finishes before iteration N+1 begins, and a `session_end` hook is guaranteed to run before shutdown.

- **REQ-HOOKS-081** — `session_start` SHALL fire ahead of the first iteration; `session_end` SHALL fire once per run on every exit path, after the final status has been decided. The status string SHALL be derived once per run and used for both destinations, so the value a `session_end` hook reads on standard input is character-for-character the value carried by the session-end wire event; the two can never disagree about how the run ended, and both carry `""` where the status could not be derived.

- **REQ-HOOKS-082** — `iteration_end` hooks SHALL finish before that iteration's checkpoint is taken, so that any edit such a hook makes to the working tree — reformatting sources, emitting a build artifact — is captured by that iteration's checkpoint rather than the next one's.

### Run Wiring, Notices, Teardown

- **REQ-HOOKS-083** — A hook declared in the layered YAML configuration SHALL execute only where the trust gate permitted it, on every way a run can be started alike (REQ-SESSION-080), because the gate is a property of the run and not of the surface that began it: a run's native hook set starts from the gate's permitted output, never from the raw resolved configuration, and the policy toggles of REQ-HOOKS-116 then remove any native hook switched off there. Hooks imported from an external agent are outside this gate's remit and are governed instead by the toggles of REQ-HOOKS-115 to REQ-HOOKS-117.

- **REQ-HOOKS-084** — The trust decision SHALL be looked up against the base workspace — the repository the user opened and reviewed — even when the run itself executes inside a throwaway isolated worktree; the hook processes still start in whichever tree the run is changing.

- **REQ-HOOKS-085** — A failure to assemble the run's hook set at start-up SHALL NOT end the run: the run continues with no hooks and logs a warning (`Could not resolve this run's hooks; continuing without them.`).

- **REQ-HOOKS-086** — Where the trust gate withheld hooks, the notice SHALL be recorded in two places: as an issue in the session's diagnostics with kind `hook_trust`, severity `warning`, actor `hooks`, and metadata carrying `blocked` (how many were withheld), `restored` (how many were reinstated per REQ-HOOKS-098) and `workspace` (the path the trust decision was looked up against, as a string), so that a run whose notices no one was watching can still be accounted for afterwards; and as text on the desktop notice channel, where it becomes the persistent unreviewed-hooks warning of REQ-NOTIFY-224. Between them the notice and the `blocked — not reviewed` status of REQ-HOOKS-103 SHALL let the user tell hooks withheld on purpose apart from hooks that are broken, which the `hook_failure` issues of REQ-HOOKS-120 record instead.

- **REQ-HOOKS-087** — At the end of a run, on both the success and failure paths: any switched-off-hook advisory is sent to the host's notice channel, and the session's hook attachment is removed, so that an attachment left behind cannot cause one run's hooks to fire for a later run started inside the same process.

- **REQ-HOOKS-088** — A run in which nothing was withheld and nothing was switched off SHALL produce no hook notices at all.

- **REQ-HOOKS-089** — Every way a run is started SHALL share one execution lifecycle, so that no way of starting a run can execute a hook another would withhold: the trust gate is a property of the run, never of the surface that began it. The ways a run can be started are REQ-SESSION-080's closed set and are not enumerated a second time here. The testable consequence is unchanged: in a run an `iteration_end` hook from an approved workspace demonstrably executes, and one from an unapproved workspace demonstrably does not, accompanied by a warning notice whose text contains "not been reviewed" and never contains the repository's command text. This requirement formerly stated the guarantee as a comparison between a desktop run and a run started by a programmatic embedding of the engine. That second case is withdrawn because the product offers no embedding surface and no programmatic entry point (REQ-EVENTS-178), which would make the comparison vacuous; the guarantee is **not** narrowed with it, and a way of starting a run added later is inside it from the moment it exists rather than on being named here.
