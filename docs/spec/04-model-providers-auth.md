# Model Providers, Sign-In, and Model Routing

## Overview

Rotaris connects to a fixed set of AI model providers plus user-defined OpenAI-compatible endpoints. Users sign in per provider using a device-code flow, a browser authorization-code-with-PKCE flow, or a pasted API key/token; credentials are persisted per provider in a per-user credential store, transparently refreshed, and never written to logs, config snapshots, or workspace files. After sign-in, the product discovers each provider's model catalog over the wire (or from a fixed offline list), persists the discovered catalog to a per-user snapshot, automatically assigns models to small/medium/large capability slots, and merges the snapshot into the effective configuration at load time. The desktop interface exposes sign-in, sign-out, provider settings, catalog refresh, model slot assignment, subscription usage, and hosted-account credit displays with the information content, timeouts, and error classifications specified below. The product has no command-line entry point and no text-mode interface of its own: every user-facing surface named in this document is reached from the desktop window.

## Requirements

### Provider Catalog and Transparency Metadata

- **REQ-PROVIDER-001** — The application ships a built-in catalog of exactly six providers with stable identifiers, in this fixed order: `concrete-cloud`, `copilot`, `codex`, `openai-compatible`, `claude-code`, `deepseek`. Their display names are, respectively: "Rotaris Cloud (recommended)", "GitHub Copilot", "OpenAI Codex", "OpenAI-compatible", "Claude Code (subscription)", "DeepSeek". Enumerating the catalog returns entries in that order, with the hosted provider first (it is the first row in the sign-in menu).

- **REQ-PROVIDER-002** — Every catalog entry carries this attribute set, and any read of the catalog on a given build returns the same values: identifier; display name; sign-in method; model-catalog (discovery) endpoint URL, which a `local-sdk` entry declares as absent (REQ-PROVIDER-005); discovery authorization header scheme, which is `Bearer` for every entry that declares a discovery endpoint; default API base URL, which a `local-sdk` entry likewise declares as absent; connection mode, mandatory and drawn from `hosted-cloud`, `direct`, `local-sdk`, `custom`; operator name (optional); privacy-policy URL (optional); availability, which reads available unless the build declares the entry unavailable; unavailability reason (optional). Discovery endpoint and base URL are independent attributes: a built-in entry's discovery URL is the one declared in REQ-PROVIDER-005 and need not equal `<base URL>/models`. Endpoint and base-URL values a user supplies for an `openai-compatible` instance are held against that instance (REQ-PROVIDER-052) and leave the catalog entry they were seeded from unchanged.

- **REQ-PROVIDER-003** — Catalog integrity is validated, and violations are rejected as errors: every built-in entry must declare a connection mode; hosted-cloud and direct entries must yield a non-empty destination hostname derived from their default base URL; a `local-sdk` entry must declare neither a discovery endpoint nor a default base URL, and a build that gives one either value is rejected; a custom-mode entry must NOT declare a fixed operator name; any entry marked unavailable must supply an unavailability reason.

- **REQ-PROVIDER-004** — Destination-host resolution: for local-sdk and custom modes the destination host is empty/none; for all other modes it is the hostname parsed from the default base URL (e.g. `rotaris.ai`, `api.githubcopilot.com`, `chatgpt.com`, `api.deepseek.com`).

- **REQ-PROVIDER-005** — Fixed per-provider endpoints and transparency metadata. Each built-in entry declares its discovery URL outright; for `deepseek` that URL deliberately differs from `<base>/models`, and deriving a discovery URL from a base URL (REQ-PROVIDER-053) applies only to user-supplied `openai-compatible` endpoints.
  - `concrete-cloud`: discovery `https://rotaris.ai/v1/models`, base `https://rotaris.ai/v1`, operator "Concrete Dynamics UG (haftungsbeschränkt)", privacy URL `https://rotaris.ai/privacy`.
  - `copilot`: discovery `https://api.githubcopilot.com/models`, base `https://api.githubcopilot.com`, operator "GitHub".
  - `codex`: discovery `https://chatgpt.com/backend-api/codex/models`, base `https://chatgpt.com/backend-api/codex`, operator "OpenAI".
  - `openai-compatible`: discovery `https://api.openai.com/v1/models`, base `https://api.openai.com/v1`. These are the values the sign-in prompt offers as defaults (REQ-PROVIDER-052); what an instance actually calls is the value stored for that instance.
  - `claude-code`: both fields are absent rather than holding a placeholder string — this entry declares no discovery URL and no default base URL at all (REQ-PROVIDER-003), so there is no value for any code path to dial and no sentinel string forms part of the contract. Its destination host is empty (REQ-PROVIDER-004) and its catalog is served offline (REQ-PROVIDER-047). Asking this entry for a discovery URL or a base URL SHALL yield nothing; a code path that requires one SHALL fail before opening any connection rather than falling back to another entry's value.
  - `deepseek`: discovery `https://api.deepseek.com/models`, base `https://api.deepseek.com/v1`, operator "DeepSeek".

- **REQ-PROVIDER-006** — The hosted provider `concrete-cloud` ships marked unavailable with unavailability reason "Rotaris Cloud is coming soon." This "coming soon" state is a static catalog attribute of the build, not a runtime probe: no health check, remote flag, configuration value, or user action ever flips it, and it changes only when a later build ships the entry marked available. Nothing in the running product writes the availability attribute.

- **REQ-PROVIDER-007** — Looking up an unknown provider id in the catalog is an error; listing the catalog preserves the fixed insertion order.

### Sign-In Methods, Token Model, and Status Classification

- **REQ-PROVIDER-008** — Each provider has exactly one sign-in method drawn from: device-code flow, browser authorization-code-with-PKCE flow, or API key. The mapping is: `copilot` → device code; `codex` → PKCE; `concrete-cloud` → PKCE (OIDC); `deepseek` → API key; `claude-code` → pasted subscription token (API-key style); user-defined OpenAI-compatible instances → API key.

- **REQ-PROVIDER-009** — Provider ids have no aliases: each built-in provider is addressable by exactly the identifier REQ-PROVIDER-001 gives it, and no alternative spelling of any id resolves. For an id outside the fixed mapping, sign-in resolution succeeds (as API-key style) only when the stored credential is tagged with the provider family "openai-compatible"; otherwise the id is unknown and a warning "Unknown auth provider: <id>" is logged. Querying the sign-in method for such an unknown id yields none.

- **REQ-PROVIDER-010** — A credential-status query answers with exactly one value out of the vocabulary `authenticated`, `unauthenticated`, `expired`, `refreshing`. Only the first three are ever returned: no credential state, clock reading, or concurrent operation makes a query answer `refreshing`. A status query sends no network traffic — with every provider host unreachable it returns the value it would have returned with connectivity — and its answer is fixed by the stored credential (REQ-PROVIDER-011) and the current system time alone, so two queries against the same stored credential at the same clock reading agree.

- **REQ-PROVIDER-011** — A stored credential comprises: an access token, a refresh token, an expiry expressed as a Unix timestamp where `0` means "no expiry" (API keys never expire), an optional account id, and a string-to-string extras map. A credential is expired when the current time is at or past the expiry timestamp, unless the expiry is `0`.

- **REQ-PROVIDER-012** — An interactive sign-in that needs the user to act shows one of two prompts. A device-code prompt shows the verification URI, the user code, the polling interval, and how long the code stays valid. A browser (PKCE) prompt shows the authorization URL to open. Every authentication attempt ends in exactly one outcome: success, or failure carrying a message that is shown to the user and recorded as that provider's last error (REQ-PROVIDER-057).

- **REQ-PROVIDER-013** — An authentication attempt issued by a caller that cannot itself wait for the result must reach an outcome within 30 seconds; once that deadline passes the attempt is reported as failed and no credential is written. The reported failure SHALL convey that the attempt did not reach an outcome within the 30-second limit, which provider it was for, and that nothing was stored so a retry is safe; its exact wording is left to the implementation. When such an attempt fails before any provider has been contacted, the failure result is the only output: no traceback, warning, or other diagnostic is written to the log or shown anywhere in the interface.

- **REQ-PROVIDER-148** — Sign-in method vocabulary. A provider's sign-in method is exactly one of three machine-readable tokens — `device-code`, `browser-pkce`, `api-key` — and these are the values the mapping of REQ-PROVIDER-008 yields, the values recorded and compared wherever a method is stored, and the only values any surface branches on. Each token has exactly one user-visible label, used identically everywhere a provider's method is displayed (REQ-PROVIDER-140, REQ-PROVIDER-141, REQ-PROVIDER-142) and in every message that names a method. A label SHALL convey how the user completes that sign-in — a code shown by the application and entered at the provider's site, a browser page that completes the sign-in, or a key the user pastes — and SHALL NOT name a command; its wording is otherwise left to the implementation. A provider id that resolves to no method (REQ-PROVIDER-009) has neither token nor label, and surfaces describe it as having its authentication managed by model configuration (REQ-PROVIDER-118).

### Credential Persistence — Location, Format, Protection

- **REQ-PROVIDER-014** — Credentials are stored one JSON file per provider at `<per-user data directory for application "rotaris">/tokens/<provider_id>.json` (on Linux: `~/.local/share/rotaris/tokens/`). The credential directory is never located inside a workspace or repository.

- **REQ-PROVIDER-015** — *Withdrawn.* A clean-room product has no earlier installation, directory, or product name to adopt from, so there is no legacy credential or state directory to rename; the per-user locations of REQ-PROVIDER-014 and REQ-PROVIDER-084 are the only ones ever read or written.

- **REQ-PROVIDER-016** — The credential store's protection is applied explicitly on every supported platform and is never left to inheritance. On POSIX systems the credential directory is created with mode `0700` and every credential file with mode `0600`: no group or other bit is ever set on either. On Windows no POSIX mode bits are set and none are reported; instead the credential directory and every file within it are created with an explicit access control list that grants full control to the owning user account and to the local system account and to no one else, with inheritance from the parent directory disabled, so protection does not depend on how the user profile directory happens to be configured. If the required protection cannot be applied, the credential is NOT written: the operation fails and reports an error naming the credential store path and stating that no credential was stored.

- **REQ-PROVIDER-017** — The credential file is a JSON object with keys `access_token`, `refresh_token`, `expires_at`, `account_id`, and `extra` (an object of strings), serialized with 2-space indentation. Loading tolerates a missing `expires_at` (defaults to 0.0), missing `account_id`, and missing `extra`. A corrupt or key-missing file logs a warning that names the provider id but never the file contents, and is treated as no credential (unauthenticated).

- **REQ-PROVIDER-018** — Credential writes are atomic: a reader of `<provider_id>.json` sees either the previous content or the complete new content, never a partial or truncated file, and a write that fails leaves the previous file untouched. The new content is staged in a temporary file inside the credential directory whose name starts with the provider id and ends in `.tmp`, carries mode `0600` on POSIX, and is renamed onto `<provider_id>.json`; a failed write deletes that temporary file and reports the error. Once any credential operation has finished, whether it succeeded or failed, the credential directory holds nothing but `<provider_id>.json` files.

- **REQ-PROVIDER-019** — Deleting a stored credential removes the file if present and logs "Deleted stored tokens for <id>". A credential-existence check is a pure file-existence test. Enumerating stored provider ids returns the sorted basenames (without extension) of `*.json` files in the credential directory.

### GitHub Copilot Sign-In (Device Code + Session Exchange)

- **REQ-PROVIDER-020** — Copilot sign-in uses the OAuth Device Flow (RFC 8628) against `https://github.com/login/device/code` and `https://github.com/login/oauth/access_token` with the fixed client id `Iv1.b507a08c87ecfe98`. No `scope` parameter is sent.

- **REQ-PROVIDER-021** — Device-code request and poll requests carry headers `Accept: application/json`, `User-Agent: GithubCopilot/0.28.0`, `Editor-Version: vscode/1.99.1`, `Editor-Plugin-Version: copilot-chat/0.28.0`, with a 30-second HTTP timeout.

- **REQ-PROVIDER-022** — The user prompt presents the server's verification URI, user code, poll interval, and prompt lifetime; when the server omits the lifetime it defaults to 900 seconds.

- **REQ-PROVIDER-023** — Polling semantics: sleep `interval + 3.0` seconds per cycle. On `authorization_pending`, continue. On `slow_down`, adopt the server's new interval when it is a positive integer, otherwise add 5 seconds to the current interval. Any other error code fails the flow with that error string. A non-200 poll response fails with "Token poll HTTP <status>". A triggered cancellation signal aborts with error "Cancelled by user".

- **REQ-PROVIDER-024** — The device flow must yield a GitHub App user token prefixed `ghu_`. Any other prefix is rejected immediately with an error stating the prefix seen and that the client id is probably not a GitHub App. A stored token whose prefix is anything other than `ghu_` classifies as unauthenticated (REQ-PROVIDER-027), forcing the user back through the device flow.

- **REQ-PROVIDER-025** — Immediately after the device flow the `ghu_` token is traded for a short-lived bearer scoped to Copilot's model API: `GET https://api.github.com/copilot_internal/v2/token`, header `Authorization: token <ghu_ token>`, 15-second timeout. The response supplies the bearer, its expiry as a Unix timestamp, the API base host to use for that account's tenant (it differs between individual and business/enterprise accounts), and an optional SKU string. The expiry stored is always the one the response gives; no fixed bearer lifetime is assumed anywhere, and the credential counts as expired 60 seconds ahead of it (REQ-PROVIDER-027). HTTP 401 and HTTP 404 are both authorization failures — 404 is the status returned both for a token that is not a GitHub App user token and for an account with no Copilot entitlement. Every other status, and any body that is not JSON, is a transient error. When no bearer can be obtained, sign-in fails with "Copilot session exchange failed: <detail>".

- **REQ-PROVIDER-026** — The persisted Copilot credential layout: access token = session bearer; refresh token = the durable `ghu_` token from the device flow; expiry = bearer expiry; extras record the tenant API base under key `api_base` and optionally the SKU under key `sku`.

- **REQ-PROVIDER-027** — Copilot status classification: empty access token → unauthenticated; a refresh token present but not `ghu_`-prefixed → unauthenticated (forces re-auth); expiry ≤ 0 → expired (a session bearer always carries an expiry, so its absence is treated as unusable); within 60 seconds of expiry → expired; otherwise authenticated. Non-interactive refresh puts the stored `ghu_` token back through the session exchange of REQ-PROVIDER-025 to obtain a new bearer and expiry; a missing or non-`ghu_` refresh token fails with "Stored token cannot be refreshed; re-authentication required".

### OpenAI Codex Sign-In (Authorization Code + PKCE)

- **REQ-PROVIDER-028** — Codex sign-in uses browser PKCE against issuer `https://auth.openai.com` with client id `app_EMoamEEZ73f0CkXaXp7hrann`. The authorization URL carries: `response_type=code`, the client id, the redirect URI, scopes `openid profile email offline_access api.connectors.read api.connectors.invoke`, an S256 PKCE challenge whose verifier is 43 characters drawn from the RFC 7636 unreserved set, `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, a 32-byte URL-safe random state, and `originator=codex_cli_rs`.

- **REQ-PROVIDER-029** — The local callback server binds `127.0.0.1` on a port taken from a build-declared ordered list of fixed ports, tried in order; the build ships the list `1455, 1457` for `codex`, because the redirect URI must be one the identity service already accepts and a dynamically assigned port therefore cannot be used. No port outside the declared list is ever bound for this flow. If every listed port is busy, authentication fails with an error that names the ports it tried and states that one of them must be free for sign-in to complete. Changing the declared list is build data, not a change of behavior. The callback path is `/auth/callback`.

- **REQ-PROVIDER-030** — Callback handling: requests to other paths receive HTTP 404. An `error` query parameter fails the flow with the error description (or the error code) and renders an HTML page "Authentication Failed / You can close this tab." A missing `code` renders "Error / No code received." Success renders "Success! / You can close this tab." and captures the code. A state mismatch is treated as CSRF: it is logged and the flow yields no code.

- **REQ-PROVIDER-031** — The flow waits at most 300 seconds for the callback. A cancellation request ends the wait with "Cancelled by user"; expiry of the 300 seconds ends it with "Authentication timed out", or with the error the callback recorded when there is one. However the wait ends — code received, cancelled, or timed out — the loopback listener is closed and its port released before the sign-in call returns, on every supported operating system: the call always returns rather than hanging, and a sign-in started immediately afterwards binds port 1455 (or 1457) successfully.

- **REQ-PROVIDER-032** — Code exchange POSTs `grant_type=authorization_code` together with the PKCE verifier to `<issuer>/oauth/token` with a 30-second timeout. Any response other than HTTP 200 fails with "Token exchange HTTP <status>". On success the token lifetime comes from the response and is 3600 seconds when the response omits it. The account id is taken from the JWT claims of the id token first and of the access token second, using the first of these that is present: a top-level `chatgpt_account_id` claim; `chatgpt_account_id` inside the `https://api.openai.com/auth` claim object; the first entry of an `organizations` claim list. When none of them yields a value, sign-in still succeeds and the credential is stored without an account id, which later requests then omit (REQ-PROVIDER-076, REQ-PROVIDER-124). Extras record `auth_mode="chatgpt"`, `requested_scopes` (the scope string that was requested), and `scope` (the granted scope string) whenever the response returns one.

- **REQ-PROVIDER-033** — Codex refresh POSTs `grant_type=refresh_token`. Failures yield "Token refresh failed: HTTP <status>" or "Refresh request failed: <exc>". Success keeps the previous refresh token when the response omits one, and re-derives the account id.

- **REQ-PROVIDER-034** — Codex credential status: an empty access token reads unauthenticated; a credential whose expiry has passed reads expired; any other stored credential reads authenticated. The scopes a credential was granted never affect this answer — a credential granted fewer scopes than were requested still reads authenticated, and no request is refused locally on scope grounds. The absence of a local scope check is the intended contract: only the provider knows what a grant permits, so the product never second-guesses it. A provider that refuses a request for want of a scope surfaces its own refusal through the requirement that owns that call, and a refusal carrying HTTP 401 or 403 takes the credential-hygiene path of REQ-PROVIDER-098.

- **REQ-PROVIDER-035** — A token-exchange operation (RFC 8693) trades a stored id token for an API key beginning `sk-`, requesting the OpenAI API-key token type. When the exchange is refused with error `invalid_subject_token` and a message naming a missing `organization_id`, the message reported to the user instead tells them to select or create an organization with the provider and then re-authenticate Codex from provider settings (REQ-PROVIDER-141). Every other refusal is reported with the HTTP status and the provider's own message, the response body being cut to its first 500 characters before it is shown or logged. The exchange has exactly one trigger: it runs on demand, immediately before a request for a configured model that names `codex` as its sign-in provider and is dispatched against an API-key-style endpoint rather than the subscription endpoint, and it runs nowhere else. The derived `sk-` key lives in process memory for the lifetime of the process only — it is never written to the credential store, the snapshot, a log, an event, or any other file (REQ-PROVIDER-086, REQ-PROVIDER-131) — and it is re-derived when it is rejected or when the process restarts. A failed exchange fails that model call alone and never deletes or invalidates the stored codex credential.

- **REQ-PROVIDER-036** — Sign-in surfaces brand the codex provider "(Sign in with ChatGPT)": the display label becomes "OpenAI Codex (Sign in with ChatGPT)", and when the PKCE prompt carries no user code, the prompt message is "Sign in with ChatGPT to authenticate Codex."

### Rotaris Cloud Sign-In (OIDC PKCE, Coming-Soon Gating)

- **REQ-PROVIDER-037** — Rotaris Cloud sign-in uses OIDC Authorization Code + PKCE with public client id `rotaris-ai`. The issuer is a configuration value on the layered YAML configuration surface (any trailing slash stripped), and the API base is a configuration value defaulting to the catalog's `concrete-cloud` base `https://rotaris.ai/v1`. Where the environment variables `ROTARIS_OIDC_ISSUER` and `ROTARIS_API_BASE_URL` are present in the environment the application was started with, each overrides the corresponding configured value, so a deployment can point the flow at a different issuer without editing configuration. When neither route supplies an issuer, authentication fails before any request with a message stating that the Rotaris Cloud issuer must be configured before sign-in and naming the configuration key that supplies it.

- **REQ-PROVIDER-038** — OIDC discovery performs `GET <issuer>/.well-known/openid-configuration` with a 30-second timeout. The response must be JSON; its `issuer` must equal the configured issuer exactly (else "OIDC discovery issuer did not match configured issuer"); and it must supply `authorization_endpoint`, `token_endpoint`, and `revocation_endpoint` (else "OIDC discovery omitted a required endpoint").

- **REQ-PROVIDER-039** — Unlike codex, the cloud loopback callback binds an ephemeral port on `127.0.0.1` with path `/callback`, and the flow itself opens the system default browser in addition to delivering the URL through the prompt callback. Callback wait timeout is 300 seconds. The success page SHALL state that authentication succeeded, that the browser tab can be closed, and that the user should return to the Rotaris window; its exact wording is left to the implementation.

- **REQ-PROVIDER-040** — Token exchange and refresh both target the discovered token endpoint with the public client id and no client secret. The stored credential's extras record `issuer`, `token_endpoint`, `revocation_endpoint`, and `api_base` so refresh and revocation work without re-discovery. A stored credential missing this endpoint metadata refuses to refresh with "Stored OIDC token endpoint is missing" / "Stored OIDC metadata is incomplete". When the token response omits a lifetime, the default is 900 seconds.

- **REQ-PROVIDER-041** — Sign-out for `concrete-cloud` first attempts best-effort remote revocation: a POST of the refresh token with `token_type_hint=refresh_token` to the stored revocation endpoint, 10-second timeout. Any revocation failure is logged at debug level and never blocks local credential deletion.

- **REQ-PROVIDER-042** — *Withdrawn.* Its only surface was the command-line provider menu; the coming-soon marking of the hosted provider in the chooser, and the refusal to authenticate it, are carried by REQ-PROVIDER-142, and the desktop health check, authenticate action, and add-provider dialog by REQ-PROVIDER-043.

- **REQ-PROVIDER-043** — Desktop coming-soon gating: both the provider health check and the authenticate action short-circuit for the unavailable cloud provider, returning the provider status `coming_soon` of REQ-NOTIFY-200 with availability false and the unavailability reason as detail. The desktop "Add provider" dialog also excludes the cloud provider (and the generic openai-compatible family) from its built-in list.

### Claude Code Subscription Provider (Pasted Token, Local Runtime)

- **REQ-PROVIDER-044** — The `claude-code` provider mints no token of its own. Whenever the credential subsystem asks that provider to authenticate — which is every caller other than the paste-token sign-in of REQ-PROVIDER-046 — the attempt fails with a message telling the user to mint a subscription token with the external Claude Code tool's `claude setup-token` command and then paste it into that sign-in. Its refresh step makes no external call: it succeeds and returns the stored token when one is stored, and fails when none is.

- **REQ-PROVIDER-045** — Subscription-token validation: an empty token → "Subscription token is required. Run 'claude setup-token' to mint one."; the token must be a legal ASCII header value (see REQ-PROVIDER-062); a token starting `sk-ant-api` is rejected with an explanation that it is an Anthropic API key and would bill the API rather than the subscription; anything not starting `sk-ant-oat` is rejected with "Expected a subscription OAuth token starting with 'sk-ant-oat' (minted by 'claude setup-token')." Status classification reuses this validation — an invalid stored token reads as unauthenticated.

- **REQ-PROVIDER-046** — The `claude-code` paste-token sign-in, reached from the sign-in action of REQ-PROVIDER-142, is the one path that stores a subscription token, and it takes that token from the user rather than from the provider's authenticate step (REQ-PROVIDER-044). It shows numbered setup instructions — install and sign in to the external Claude Code tool, run `claude setup-token`, paste the `sk-ant-oat` token it prints — and states that the token is kept locally with owner-only file permissions (mode `0600` where the platform has them, REQ-PROVIDER-016) and is never written to workspace files, logs, or session snapshots. It then prompts for the token with the input hidden under the label "Claude Code subscription token (sk-ant-oat...)", applies the validation of REQ-PROVIDER-045, and runs offline model discovery (REQ-PROVIDER-047).

- **REQ-PROVIDER-047** — Claude-code model discovery is static and offline: after token validation it returns a fixed catalog of exactly three version-independent aliases — `opus` ("Claude Opus (subscription)"), `sonnet` ("Claude Sonnet (subscription)"), `haiku` ("Claude Haiku (subscription)") — with qualified ids `claude-code/<alias>`, no network call, and no HTTP status.

- **REQ-PROVIDER-048** — Conflicting-credential precheck: the presence of any of the environment variables `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, or an `apiKeyHelper` entry in `~/.claude/settings.json`, outranks the subscription token in the external tool's own credential chain; if any is present, the subscription runtime refuses to run with a credential-conflict error naming the conflicting sources and suggesting remediation (e.g. `unset ANTHROPIC_API_KEY`, remove apiKeyHelper). This check runs before every subscription-runtime prompt.

- **REQ-PROVIDER-049** — The subscription runtime injects the stored token as environment variable `CLAUDE_CODE_OAUTH_TOKEN` for the external local-runtime subprocess. This domain fixes no per-model parallelism default of its own and holds no list of provider names that carry one: the cap in force for a model is the one its provider's catalogue entry declares, under REQ-MONITOR-021. A catalogue entry that declares no cap leaves the models configured against it unbounded, and a cap the user sets for a model replaces whatever the entry declared.

### DeepSeek and OpenAI-Compatible Endpoints (API Keys, Labelled Instances)

- **REQ-PROVIDER-050** — DeepSeek is a plain API-key provider: its interactive authenticate step always fails with a message stating that the provider uses a stored API key and that the key is created or replaced from provider settings (REQ-PROVIDER-141); status is authenticated if and only if a key is stored. Sign-in prompts with hidden input "DeepSeek API key", validates by discovery against the DeepSeek catalog endpoint, and persists the key only AFTER discovery succeeds with at least one model.

- **REQ-PROVIDER-051** — OpenAI-compatible endpoints are user-defined, labelled instances with ids `openai-compatible--<slug>`, where the slug is the label lowercased with every run of non-alphanumeric characters collapsed to a single `-` and trimmed. A label that normalizes to nothing is rejected with "Label must contain at least one letter or number." Multiple instances are supported simultaneously.

- **REQ-PROVIDER-052** — Sign-in for an OpenAI-compatible instance (the custom mode of the add-provider dialog, REQ-PROVIDER-117) collects three fields: a label (required), an endpoint URL defaulting to `https://api.openai.com/v1`, and a masked required API key. If an instance with the derived id already has credentials or a catalog-snapshot entry and re-auth was not requested, the user must confirm "Replace the existing provider instance '<label>'?" (default No), otherwise the sign-in returns "cancelled". Discovery must succeed with at least one model before the key is persisted. On success the credential extras record `provider_family` = "openai-compatible" and `api_base` = the normalized URL.

- **REQ-PROVIDER-053** — Base-URL normalization: trims whitespace and trailing slashes; an empty URL → "API base URL must not be empty."; the URL must include a scheme and hostname (else "API base URL must include a scheme and hostname."); a path ending in `/models` is trimmed off, so pasting the models endpoint itself works. The models endpoint is then `<base>/models`.

- **REQ-PROVIDER-054** — Programmatic instance registration validates label/URL/key; rejects a duplicate id with "Provider <id> already exists; re-authenticate the existing endpoint."; runs discovery with the API key redacted as `[redacted]` in any error text; fails on zero discovered models with "no models discovered."; saves the credential; persists the discovered models; and on a snapshot-write failure rolls back by deleting the just-saved credential and reports "Could not save provider <id>: <error>". The success message is "Added <label>; discovered N model(s)."

- **REQ-PROVIDER-055** — Instance deletion: only ids matching the `openai-compatible--` prefix are deletable ("Provider <id> is built-in or not user-defined."); an unknown instance yields "Unknown user-defined provider: <id>."; otherwise deletion removes the snapshot entry and the credential and reports "Deleted user-defined provider <id>." along with flags stating whether credentials and/or the snapshot entry were removed. Workspace model references are deliberately NOT rewritten.

- **REQ-PROVIDER-056** — *Withdrawn.* Its only surface was a command-line subcommand with a confirmation flag and exit codes; deleting a user-defined instance, with the confirmation that names the instance and states that workspace model references are left unchanged, is carried by REQ-PROVIDER-141, and the deletion semantics themselves remain in REQ-PROVIDER-055.

### Credential Lifecycle (Get, Renew, Sign-Out, Errors)

- **REQ-PROVIDER-057** — Fetching a usable token for a provider: load the stored credential; if status is authenticated, return the access token as-is; if expired, attempt a silent refresh — on success, persist the credential, re-stage any external bridge artifacts (REQ-PROVIDER-063), and return the new token; on refresh failure, log "Token refresh failed for <id>, re-authenticating" and fall through. Without an interaction callback, the fall-through records the per-provider last error "Authentication required" and returns nothing; with a callback, the full interactive sign-in runs and the credential is persisted on success. Every failure path records a retrievable per-provider last error; every success clears it.

- **REQ-PROVIDER-058** — An unconditional renew operation refreshes a stored credential even when it is still valid (so a credential does not expire part-way through a run); when the provider cannot refresh without user interaction, renew returns nothing and records the reason as the last error.

- **REQ-PROVIDER-059** — A non-blocking status query classifies a provider without performing network I/O; an unknown provider or absent credential classifies as unauthenticated. The asynchronous status check yields the same classification.

- **REQ-PROVIDER-060** — Sign-out for a provider deletes the stored credential and forgets any cached in-process provider state and last error; for `codex` it additionally deletes the staged external-runtime bridge credential, best-effort with a warning on failure.

- **REQ-PROVIDER-061** — Saving a credential also rewrites that provider's external bridge artifacts, and they are on disk before the save call returns: a `codex` credential is mirrored into the secondary credential store the external agent runtime reads, recorded under the vendor key "openai" with its expiry expressed in milliseconds; a `copilot` credential is staged into the workspace-scoped gateway files of REQ-PROVIDER-063 whenever a workspace root is known, and is skipped without error when none is. A failure to write either artifact — including the empty-token failure of REQ-PROVIDER-065 — is logged as a warning and never turns a successful credential save into a failed one; the missing artifact then surfaces as an authentication error on the next model call.

### Credential Bridges and Key Hygiene

- **REQ-PROVIDER-062** — API-key header validation: a key must be pure ASCII ("API key must contain ASCII characters only. Re-enter its exact value.") and contain no control characters (0x00–0x1F, 0x7F) ("API key must not contain control characters. Re-enter its exact value."). This applies to pasted keys and to tokens used for API-key-provider discovery.

- **REQ-PROVIDER-063** — Copilot gateway staging publishes two files in the staging directory `copilot-gateway` beneath the workspace's `.rotaris/` state directory, so the full path is `<workspace root>/.rotaris/copilot-gateway/`. That name is part of the observable contract, because consumers are pointed at the directory through `GITHUB_COPILOT_TOKEN_DIR` (REQ-PROVIDER-064). The directory carries the same protection as the credential store (REQ-PROVIDER-016): POSIX mode `0700`, and on Windows an explicit access control list granting the owning user account and the local system account only. Both files carry POSIX mode `0600` and the equivalent Windows access control list, and staging fails without writing either file when that protection cannot be applied. Each is written so that a reader sees either the previous content or the complete new content and never a partial file, and each is on disk before the staging call reports success. The files are `access-token`, plain text holding the durable `ghu_` token, or the session bearer when no refresh token is stored; and `api-key.json`, compact JSON of the form `{"token": <bearer>, "expires_at": <int>, "endpoints": {"api": <base>}, "sku"?: <string>}`. When no API base is stored for the account, the value written for `endpoints.api` is `https://api.githubcopilot.com`. Because the durable token is published here, nothing that reads these files ever has to start a second device-code flow.

- **REQ-PROVIDER-064** — Gateway environment contract: the environment variable `GITHUB_COPILOT_TOKEN_DIR` is set to the workspace's staging directory (pinned per workspace so concurrent application instances never share staged credentials), and `GITHUB_COPILOT_ACCESS_TOKEN` is defaulted (never overwritten if already set) to the sentinel value `managed-by-rotaris`, which signals that credential acquisition and refresh are performed by the application and must not be attempted by the consumer of these files. The product's obligation ends at publishing the files and the variables: whether a consumer honors the contract is outside the product's control and is never asserted by the product. A consumer that ignores them surfaces as an authentication failure on the next model call (REQ-PROVIDER-061), not as a staging error, and the product SHALL NOT probe, verify, or wait on the consumer's behavior.

- **REQ-PROVIDER-065** — Staging Copilot credentials with an empty access token fails with the error "Cannot stage Copilot tokens: access_token is empty", and neither staged file is created or overwritten. On the credential-save path that failure is absorbed as a warning per REQ-PROVIDER-061 and the credential save still succeeds.

### Run-Time Credential Priming and Transparent Refresh

- **REQ-PROVIDER-066** — The set of providers to prime for a run is the union of the sign-in providers behind all configured slot models and personas, plus the sign-in provider of every configured model. All of them are primed, regardless of which personas the run turns out to use.

- **REQ-PROVIDER-067** — A priming pass runs once at run start. For each provider: authenticated and not expiring within the refresh margin → counted as authenticated, and (for copilot) bridge files are re-staged; authenticated-but-expiring-soon or expired → an unconditional renew is performed rather than a plain token fetch, which would hand back a token that is still valid but close to expiry. Failures are collected into an unresolved map with reasons and logged as warnings — priming never fails the run. Constants: refresh margin 300.0 seconds (renew when within 5 minutes of expiry); poll interval 60.0 seconds.

- **REQ-PROVIDER-068** — A run is wrapped in a keep-fresh scope. Opening it yields the priming report of REQ-PROVIDER-067 — the providers found authenticated, the providers renewed, and the map of providers that could not be resolved with a reason for each — reported as ok exactly when that map is empty. For as long as the run lasts, a credential carrying an expiry is renewed before it lapses, with the check running at least once every 60 seconds. Credentials with no expiry (API keys) are never renewed on that schedule, and a credential that was already unresolved when the run started is not retried: it is reported once in the opening report instead of producing a warning at every check. A failure during a check is logged as a warning, the remaining providers are still checked, and refreshing continues until the run ends. No refresh happens after the run ends.

### Model Discovery (Catalog Sync)

- **REQ-PROVIDER-069** — Discovery dispatch: `codex` → the dedicated subscription discovery (REQ-PROVIDER-076); `claude-code` → the offline static catalog (REQ-PROVIDER-047); every other provider → HTTP GET of the provider's models endpoint with headers `Authorization: Bearer <token>` and `User-Agent: rotaris/discovery`, default timeout 10 seconds. For API-key provider families the token is header-validated (REQ-PROVIDER-062) before any request.

- **REQ-PROVIDER-070** — Copilot discovery adds the full editor-identity header set (`Copilot-Integration-Id: vscode-chat`, `Editor-Version`, `Editor-Plugin-Version`, `OpenAI-Intent: conversation-panel`, `User-Agent`, `Accept: application/json`); the endpoint does not return a usable model list without them. When a tenant API base is stored from the session exchange, the discovery endpoint's scheme and host are swapped to it while the `/models` path is kept.

- **REQ-PROVIDER-071** — Discovery reports either a model list or an error, and an error that came from an HTTP response also reports that response's status code. The mapping is: a timeout or transport failure → "Discovery request failed: <exc>", no status; HTTP 401 or 403 → "Authentication failed for <display name>: <status>"; HTTP 500 or above → "Discovery request failed: <reason phrase, or `HTTP <status>` when the response supplies none>"; a body that does not parse as JSON → "Invalid response format: <exc>"; a payload that is not a JSON object → "Invalid response format: expected JSON object"; a payload whose `data` field is absent or is not a list → "Invalid response format: expected data list"; an entry of `data` that is not an object → "Invalid response format: expected model objects". A `data` list that is present and empty is not an error: discovery succeeds with zero models, which is the condition that opens the recovery choice of REQ-PROVIDER-097. The mapping is total: any other non-2xx status — 404, 408, 429, and every other 4xx — fails discovery reporting that status, with a message conveying that the provider refused the catalog request for a reason other than authentication, and for HTTP 429 additionally that the refusal was a rate limit and the read can be retried later. No response is left unclassified, and no unmapped status is silently treated as success.

- **REQ-PROVIDER-072** — Each discovered model captures: its id; a qualified id `<provider-or-instance id>/<id>`; an optional display name (payload `display_name`, falling back to `name`); a capabilities object; a limits object (payload `context_length` mapped into `context_window` when it is an integer); pricing only for `concrete-cloud` (decimal-string `prompt_usd_per_token` / `completion_usd_per_token` mapped to floating-point input/output cost per token, with negative or non-finite values rejected); and the raw payload item. The capabilities object always carries the image-input declaration of REQ-PROVIDER-149 and, when the provider reports one, the image token cost of REQ-PROVIDER-150. Known token limits are injected when missing (REQ-PROVIDER-078 to 080).

- **REQ-PROVIDER-073** — Copilot catalog handling separates dropping from annotating. An entry that declares a capability type other than `chat` — an embeddings model, for example — is dropped and never appears in the catalog; an entry that declares no capability type is kept. Every kept entry is annotated and none is hidden: an entry the payload marks as switched off by account policy is recorded with availability code `policy_disabled` and the provider's policy terms text as its unavailability detail; an entry whose advertised endpoints yield no route the product can dispatch to (REQ-PROVIDER-074) is recorded `no_supported_route` and carries no detail; every other entry is recorded `available` together with the API mode chosen for it. An entry that omits the capability, policy, or endpoint fields is treated as available. The payload key paths at which the capability type, the policy state, and the policy terms text are read are build data: they are declared once in the build's catalog-payload mapping for this provider and applied to every entry. This specification fixes the behavior for each value found, not the path it is found at, so a build that follows a provider's payload change to a new path changes no behavior here; an entry that carries nothing at a declared path is treated as omitting that field.

- **REQ-PROVIDER-074** — Advertised Copilot endpoints are normalized before a route is chosen: each string is trimmed of surrounding whitespace; a string that is not a path — anything not starting with `/`, a websocket URL for instance — is discarded; a path that does not already start with a version segment of the form `/v<digits>` gets `/v1` prepended; repeated values are reduced to their first occurrence. The route follows from the normalized set: an empty set gives chat mode; otherwise the presence of `/v1/chat/completions` gives chat mode, and it wins when both endpoints are advertised; otherwise the presence of `/v1/responses` gives responses mode; otherwise the model has no supported route (REQ-PROVIDER-073).

- **REQ-PROVIDER-075** — The model availability vocabulary is `available`, `policy_disabled`, `no_supported_route`; an absent or empty code means available. Each non-available code renders as exactly one actionable sentence — `policy_disabled`: "Your provider account has this model switched off. Enable it in the provider's settings, then refresh the model catalog."; `no_supported_route`: "The provider offers this model only on an endpoint Rotaris cannot send requests to."; any code outside the vocabulary: "The provider will not accept requests for this model." The provider's own detail text follows that sentence, separated by a single space and ending in exactly one sentence-terminating character, and is left out when it is empty or when it repeats the sentence.

- **REQ-PROVIDER-076** — Codex subscription discovery: `GET https://chatgpt.com/backend-api/codex/models?client_version=0.144.6` with headers `Authorization: Bearer <token>`, `originator: codex_cli_rs`, `OpenAI-Beta: responses=experimental`, `User-Agent: rotaris/discovery`, and `chatgpt-account-id: <account id>` when an account id is stored. Payload items must carry a non-empty string `slug` (else "Invalid response format: expected model slug"); entries with `supported_in_api == false` or `visibility == "hide"` are skipped. Captured capabilities: reasoning levels (from `supported_reasoning_levels`) and input modalities, an `image` entry among the modalities setting the image-input declaration of REQ-PROVIDER-149 to true and its absence from a present modality list setting it to false; limits: `context_window`, falling back to `max_context_window`. The 401/403, ≥500, and format error semantics match generic discovery.

- **REQ-PROVIDER-077** — Hosted-cloud slot suggestions: after a successful `concrete-cloud` discovery, a second best-effort `GET <base>/model-suggestions` is parsed for roles `small`, `medium`, `large`, `fallback`; each suggested id is qualified with the provider prefix and kept only if it names a model that was actually discovered. Any error or shape problem yields no suggestions.

- **REQ-PROVIDER-149** — Image-input declaration. Every model entry — discovered, persisted in the snapshot, or declared in YAML — SHALL carry an image-input declaration: a boolean `accepts_image_input` in the entry's capabilities object stating whether the model accepts image input alongside text. It is populated from three sources and the first that supplies a value wins: (1) an explicit `accepts_image_input` on a user-authored YAML model entry; (2) the provider's own report from the most recent successful discovery for that model — the codex input modalities of REQ-PROVIDER-076, or the capabilities object a generic provider returns (REQ-PROVIDER-072); (3) the shipped model-capability metadata of REQ-PROVIDER-137 for a model that metadata knows. A later discovery replaces a value that came from an earlier discovery or from shipped metadata, and never overrides an explicit YAML declaration. Where no source supplies a value the declaration is absent, and absent SHALL be read everywhere as "this model does not announce image input": the attachment gate of REQ-CHAT-171 is closed, attachment affordances are disabled, and no image is sent. A declaration SHALL NOT be inferred from a model's name or id. The declaration SHALL be observable wherever models are listed or selected — the provider list (REQ-PROVIDER-140), the startup model assignment editor (REQ-PROVIDER-144), the model picker (REQ-PROVIDER-145), and runtime model override selection (REQ-PROVIDER-146) — as a labelled indicator that reads identically in every one of them and never relies on colour alone (REQ-SHELL-149). A model whose declaration is absent is presented exactly as one that declares false, because neither announces image input.

- **REQ-PROVIDER-150** — Image token cost. A model entry MAY additionally declare an image token cost in its capabilities object, as either `image_input_tokens` — a positive integer count of input tokens one image contributes — or `image_input_tokens_per_megapixel` — a positive number of input tokens per megapixel of decoded image area — or both. The cost is populated from the same three sources, with the same precedence, as the declaration of REQ-PROVIDER-149. A cost declared for a model that does not accept image input is ignored, and declaring a cost never by itself turns the image-input declaration true. Token estimation (REQ-CHAT-174) charges each attachment the per-megapixel rate multiplied by the attachment's decoded area, rounded up to a whole token, when that rate is declared and the image's dimensions are readable; otherwise the fixed count when one is declared. Where the entry declares neither, or declares only a rate for an image whose dimensions cannot be read, the cost is unknown: the estimator SHALL NOT substitute a guessed figure and SHALL NOT count the attachment as zero, but SHALL treat it as an unknown non-zero amount and mark the whole estimate a lower bound. Money follows the same route as text: estimated image tokens are input tokens and are priced with the entry's `input_cost_per_token`. Where a provider prices images per image rather than per token, that price is carried in the entry's pricing block as a decimal string and every amount derived from it is computed and rendered under the single money rule of REQ-PROVIDER-121 — exact decimal arithmetic, never binary floating point — so no image amount is computed any other way.

### Known Token Limits and Normalization

- **REQ-PROVIDER-078** — Canonical limit extraction reads the payload's limit fields in a fixed key order and takes the first acceptable value it finds, skipping keys that are absent or hold an unacceptable value. Input-limit key order: `context_tokens`, `max_input_tokens`, `context_window`, `max_context_window_tokens`, `max_context_tokens`, `context_length`, `max_prompt_tokens`, `input_tokens`, `token_limit`, `max_tokens`. Output-limit key order: `output_tokens`, `max_output_tokens`, `max_completion_tokens`. A value is acceptable when it is a positive integer (a boolean never qualifies, whatever its numeric value), a positive float with no fractional part, or a string of digits optionally grouped with `_` or `,` that parses to a positive integer. Zero, negative, and non-integral values are unacceptable and the search continues past them; when no key yields an acceptable value that limit is absent.

- **REQ-PROVIDER-079** — The build carries a table of known (input, output) token-limit pairs keyed `provider/model`, covering the OpenAI, Anthropic, and DeepSeek model families, together with one provider-wide entry `deepseek/` whose pair is (1,048,576, 384,000). The individual model rows are build data, revised without a change to this specification; what is normative is that every key has the form `provider/model` or `provider/`, that every value is a pair of positive integers, that the `deepseek/` row ships with the pair named above, that the table is consulted only through the lookup below, and that a table with no matching row changes nothing other than leaving those limits unknown. A lookup tries, in order: the qualified id as written; then the id with recognized trailing suffixes removed one at a time — `-latest`, `-YYYY-MM-DD`, `-YYYYMMDD`, and a DeepSeek four-digit release suffix — each successively shortened form being tried as it is produced; then the provider-wide entry for that provider. For lookup purposes `codex` and `copilot` are read as `openai`, and an `openai-compatible--<slug>` instance is tried under its own id first and under the bare `openai-compatible` prefix second. A model that matches nothing yields no known limits.

- **REQ-PROVIDER-080** — Known-limit application fills gaps only: if discovery already produced both limits, they are returned untouched; otherwise the input/output values from the known table are injected when resolvable.

### Automatic Slot Selection from a Discovered Catalog

- **REQ-PROVIDER-081** — Automatic tier assignment fills the large, medium, and small picks from a provider's discovered models, in that order, matching case-insensitively against the model id and yielding qualified ids. The build carries a fixed ordered preference per tier over model-family name fragments, with a secondary fallback list consulted when no preferred fragment matches; both lists are build data and are not themselves normative — what is normative is the invariants below, the tie-break, and determinism. Where several discovered models match at the same preference rank, the tie is broken by taking the lowest qualified id in ascending code-point order, so the same catalog always produces the same three picks whatever order discovery returned it in. The observable invariants are: an id containing `mini` or `nano` is never chosen as the large pick; the medium pick is never the model already chosen as large; the small pick is never one of the two already chosen; and any tier is left empty when nothing matches, with REQ-PROVIDER-082 deciding how that gap is closed.

- **REQ-PROVIDER-082** — Only models recorded as available (REQ-PROVIDER-075) may be assigned to a slot; unavailable models are still written to the snapshot but never fill one. Gaps in the tier picks of REQ-PROVIDER-081 are closed in a fixed order: `large_model` takes the large pick, else the medium pick, else the small pick; `medium_model` takes the medium pick, else the small pick, else the large pick; `small_model` takes the small pick, else the medium pick, else the large pick; `default_summary_model` takes the medium pick, else the small pick, else the large pick. A slot still empty after that takes a single deterministic choice from the provider's available models — the same model for every such slot, and the same model on every run over an unchanged catalog: the available model with the lowest qualified id in ascending code-point order, which is defined for every catalog and independent of discovery order and of the snapshot's stored ordering. Where the hosted provider returned server-side suggestions (REQ-PROVIDER-077), the suggestion for a role replaces the pick for that role. `fallback_model` takes the `fallback` suggestion when one was returned and otherwise the small pick; when neither exists the field is left unset and the default of REQ-PROVIDER-088 applies.

- **REQ-PROVIDER-083** — The persisted snapshot's model list is ordered with the picked (small/medium/large) models first, then the rest sorted by qualified id. Previously known models that a refresh did not re-discover are PRESERVED (sorted, appended) rather than dropped, and counted separately. Every model row records a shared ISO-8601 UTC discovery timestamp.

### Provider/Model Snapshot Persistence (On-Disk Catalog)

- **REQ-PROVIDER-084** — The discovered-provider catalog persists as a YAML file `project_settings.yaml` in the per-user config directory for application "rotaris", which is the directory REQ-CONFIG-001 fixes for the running platform (on Linux, `~/.config/rotaris/project_settings.yaml`). The document has `version: 1` (any other version is rejected with "unsupported project snapshot version") and a `providers` map of id → provider record; unknown keys are rejected. A provider record has: id, display name, optional family, optional base URL, an authenticated flag, a list of model records, per-slot fields `default_summary_model`, `large_model`, `medium_model`, `small_model`, `fallback_model`, and a discovery timestamp that must be ISO-8601 with a UTC offset. A model record has: id, optional display name, capabilities, limits, pricing, and its discovery timestamp. Duplicate model ids keep the first occurrence and log a warning.

- **REQ-PROVIDER-085** — A snapshot write is atomic: a concurrent reader sees either the previous document or the complete new one and never a partial file, and a write that fails leaves the previous document intact. The file carries mode `0644`. Its YAML is emitted with mapping keys in the order they were written rather than sorted, and with non-ASCII characters written literally rather than escaped. Two reads of a snapshot with no write in between return equal results. A snapshot that cannot be parsed, or that violates REQ-PROVIDER-084, fails the read with "Invalid project snapshot at <path>: <detail>".

- **REQ-PROVIDER-086** — Every snapshot write is preceded by a scan of the whole payload, and the write is refused when anything secret-like is found. A mapping key counts as secret-like when it meets the secret-looking key test of REQ-TOOLS-172, which this requirement neither restates nor varies; this screen adds two triggers of its own, both because a persisted catalog must carry less than a rendered line of text may: a key whose lower-cased form carries the segment `session`, and a key whose lower-cased form contains `ghu_` anywhere within it. A string value counts as secret-like when it begins with one of the credential value prefixes of REQ-TOOLS-171; this domain holds no copy of that list, and what it relies on it for is that the comparison ignores letter case and that the prefix is recognized at a token boundary, so a value written as `Bearer ghp_…` is caught as surely as a bare one. Where REQ-TOOLS-171 masks a matching value in text, this screen instead refuses the write outright — a document that is going to sit on disk is not made safe by masking part of it. A refused write leaves the existing file untouched and reports "Refusing to write snapshot: secret-like field detected: <path>", where `<path>` locates the offending field within the document. Two families of key that the format itself requires are exempt, since the document could otherwise never be written at all: the two per-token price keys beneath a model's `pricing` block, and the token-limit keys beneath a model's `limits` block (REQ-PROVIDER-084). Those two are the complete exempt set and no further key is exempt: a snapshot field added later that trips the screen is renamed so that it does not, rather than added to this list, because every exemption is a hole in a check whose whole purpose is to be unconditional. The provider `authenticated` flag needs no exemption — under REQ-TOOLS-172's whole-segment comparison its single segment is `authenticated`, which is not the segment `auth`.

- **REQ-PROVIDER-087** — The snapshot supports upserting one provider record (creating the file when absent) and removing one provider record (reporting whether anything was removed).

### Configuration: Model Slots, Routing Fields, Snapshot Merge

- **REQ-PROVIDER-088** — The root configuration exposes seven named capability slots: `small_model`, `medium_model`, `large_model`, `fallback_model`, `default_summary_model`, `improvement_collector_model`, `gatekeeper_model`. These seven are the editable "startup model" fields written by guided assignment (REQ-PROVIDER-100) and the startup model assignment editor (REQ-PROVIDER-144). Wherever a persona or a nested configuration section names one of the literal slot names in place of a model, that name is replaced by the slot's value while configuration is being loaded, so no alias reaches a run. An alias whose slot has no value SHALL NOT fail the load: it resolves to `fallback_model` when that slot has a value, and otherwise leaves the naming field unset and records a configuration validation warning naming the persona or section and the empty slot, so the gap is visible before a run is started rather than at dispatch. Resolution of an unset slot, taking the first listed source that has a value: `fallback_model` ← `small_model`; `default_summary_model` ← the literal `gpt-5-mini`; `improvement_collector_model` ← `medium_model`; `gatekeeper_model` ← `small_model`, then `default_summary_model`, then `fallback_model`. `fallback_model` is the model substituted whenever the primary choice for a call cannot be used. Every slot has a sibling field `<slot>_thinking` accepting exactly `low`, `medium`, `high`, or `max`; leaving it unset is the one way to say that the provider or endpoint decides the level. `auto` is not part of the vocabulary — it would have been indistinguishable from unset in every stored value and every display — and a configuration that carries it, or any other value outside the four, is rejected with a message naming the field and the accepted levels.

- **REQ-PROVIDER-089** — Per-model configuration fields relevant to routing: provider, model id, optional API key / API-key environment-variable name / base URL, an optional sign-in provider reference (when set, credentials come from the credential subsystem instead of static keys), an API mode ("chat" | "responses" | unset — filled by discovery, user-overridable), a switch to disable the responses API, maximum input/output token limits, a per-model timeout (unset → the global runtime model timeout), a retry count (unset → default 5), sampling parameters, optional explicit pricing (both input and output values must be set to take effect), a thinking level drawn from the vocabulary of REQ-PROVIDER-088, an optional image-input declaration and image token cost (REQ-PROVIDER-149, REQ-PROVIDER-150), and a maximum-parallel-requests value (defaults per REQ-PROVIDER-049).

- **REQ-PROVIDER-090** — Unavailable models are kept in a separate configuration map from usable models, carrying id, display name, sign-in provider, availability reason code, the resolved reason sentence, and the provider's detail text. No code path can construct a model client from an unavailable entry, while pickers can still display the row with its reason.

- **REQ-PROVIDER-091** — Configuration loading merges the snapshot into the effective configuration: each authenticated snapshot provider's slot picks seed the root slots; each snapshot model becomes a configured model entry keyed by qualified id, whose provider family is `deepseek` or `claude-code` for those families and the generic OpenAI-compatible dialect otherwise, whose model id is the qualified id with the provider prefix stripped, whose sign-in provider is the provider id, whose base URL comes from the snapshot or the catalog default, with limits, API mode, and pricing carried through from discovery. A user-authored YAML entry with a complete provider and model id overrides the snapshot entry of the same name. Models marked unavailable in the catalog land in the unavailable-models map UNLESS the user explicitly named them in YAML (then they stay configured). An invalid snapshot is ignored with a warning "Ignoring project settings snapshot: ...".

- **REQ-PROVIDER-092** — A configured model that names a sign-in provider is dispatched with a credential taken from the credential store rather than any static key, and an expired credential is renewed before the request leaves, so no request carries a credential the store already knows to be expired. Copilot requests carry the editor-identity headers of REQ-PROVIDER-070 and use the staged workspace credentials of REQ-PROVIDER-063. A Copilot model discovered as responses-only is invocable: its requests go to the responses endpoint, the limits discovery recorded for it apply, and it reports no pricing (both per-token costs read as zero). A codex model's requests authenticate with the stored subscription credential.

### Provider Sign-In Flow

- **REQ-PROVIDER-093** — *Withdrawn.* Its whole surface was a command-line subcommand with arguments, a cancellation key, and process exit codes; starting a sign-in, forcing re-authentication, scoping it to a workspace, and reporting its outcome are carried by REQ-PROVIDER-142.

- **REQ-PROVIDER-094** — *Withdrawn.* Its whole surface was a text-mode provider menu with an arrow-key selector and a numbered fallback prompt; the provider chooser, its catalog ordering, the codex branding, the coming-soon marking, the rejection of an unknown provider id, and the cancelled outcome are carried by REQ-PROVIDER-142.

- **REQ-PROVIDER-095** — Before the application contacts any provider for a sign-in, it creates the per-user configuration directory for the application when that directory is absent. Which directory that is on each platform is fixed by REQ-CONFIG-001; this domain relies on that location and names no path of its own. A failure to create it, or an inability to resolve the location at all, does not stop sign-in: the attempt carries on and a warning is recorded that names the directory and the underlying error.

- **REQ-PROVIDER-096** — OAuth-provider sign-in sequence: check status → if re-authentication was requested, discard the stored authentication first, reporting that the stored authentication for that provider was discarded, and force re-authentication → if already authenticated and re-authentication was not requested, skip the flow and report that the stored authentication is being used; otherwise run interactive authentication with the prompt callback. The two prompts of REQ-PROVIDER-012 are presented in the authentication dialog of REQ-PROVIDER-116: a device-code prompt presents the verification URI as an activatable link together with the user code, and a browser prompt presents the authorization URL as an activatable link together with a statement that the browser should already have opened. Authentication failure reports the provider's error and ends the attempt in failure.

- **REQ-PROVIDER-097** — After authentication, models are discovered, with recovery. A discovery error ends sign-in in failure, reporting the provider and the discovery error. Discovery that succeeds with zero models does not end sign-in: it presents a recovery choice offering exactly four options — retry discovery, choose a different provider, edit the workspace configuration by hand, or abandon sign-in — with abandon taken as the default whenever the choice is dismissed without a selection. Retry may be taken twice; from the third time onward the retry option is refused, reporting that the retry limit was reached, and the same choice is presented again. Choosing a different provider restarts sign-in at the provider chooser of REQ-PROVIDER-142. Editing by hand writes a minimal `.rotaris/agents.yaml` when none exists and opens that file in the application's own configuration editor — never in an external program, and never by inspecting an editor environment variable — validates the workspace configuration when the user applies the change, reports any validation errors, and ends sign-in reporting that manual configuration is required. Abandoning ends sign-in reporting that discovery was abandoned. Every one of these outcomes leaves the credential just stored in place.

- **REQ-PROVIDER-098** — Post-refresh credential hygiene: when discovery fails with HTTP 401/403, the stored authentication is discarded ("Discarded stored authentication for <name>.") EXCEPT for `codex`, whose stored credential survives a refused catalog read, so a later attempt does not force a fresh sign-in.

- **REQ-PROVIDER-099** — On successful discovery, the models are persisted to the snapshot (using the stored API base for the base URL) and sign-in finishes with "Login complete for <name>; discovered N model(s)." A minimal `.rotaris/agents.yaml` (default persona `orchestrator`) is bootstrapped when absent, and the bootstrap is reported. The user is then offered the chance to open the workspace configuration for editing (default declined); accepting opens `.rotaris/agents.yaml` in the application's own configuration editor, validates it when the change is applied, and reports any errors, sign-in then reporting that manual configuration is required. Configuration validation warnings raised at this point are reported as warnings that state the configuration problem and identify sign-in as the moment it was found.

- **REQ-PROVIDER-100** — The OpenAI-compatible sign-in additionally offers guided slot assignment: the user is offered the chance to configure the startup model assignments now (default accepted), which walks all seven slot fields of REQ-PROVIDER-088 with one picker per field whose choices are the authenticated snapshot models plus the models declared in global or workspace YAML, each choice labelled with its provider display name, the model's label, and its qualified id, and each showing the model's image-input declaration (REQ-PROVIDER-149); each slot is followed by a thinking-level picker only when the chosen model supports reasoning levels (REQ-PROVIDER-137), and that picker carries an explicit "leave to the provider" choice rather than a numeric sentinel. The user is then offered persona-specific model overrides (default declined), walking each persona with an explicit "inherit the default" choice alongside the model choices. Results are written to `.rotaris/agents.yaml`. The slot values shown as current are the pre-sign-in values, captured before the new provider was persisted. The same walk is reachable at any later time from the startup model assignment editor (REQ-PROVIDER-144).

### Subscription Usage Endpoints and Rendering

- **REQ-PROVIDER-123** — Subscription-usage fetching supports exactly the providers codex, copilot, and claude-code; any other provider yields an empty result. The default HTTP client uses a 5-second timeout and follows redirects. All failures raise a dedicated usage error type; callers degrade to placeholders and nothing is retried at this layer.

- **REQ-PROVIDER-124** — Codex usage: `GET https://chatgpt.com/backend-api/wham/usage` with the OAuth bearer, `User-Agent: codex-cli`, and a `ChatGPT-Account-Id` header when an account id is stored. The payload's primary and secondary rate-limit windows are read in that order; a window that is absent, or whose used-percent value is missing, non-numeric, boolean, or not finite, is skipped rather than failing the whole read; a usable percent is clamped into 0–100 and rounded to an integer under the rounding rule of REQ-PROVIDER-127. Labels resolve by the window's declared length in seconds: 18,000 → "Codex 5-hour window"; 604,800 → "Codex weekly window". When the length is absent or matches neither value, the window keeps the label its position implies — "Codex 5-hour window" for the primary window and "Codex weekly window" for the secondary one. Rendering: the used label is "<n>% used"; the detail is "<100−n>% remaining[ · resets <relative>]" where the reset comes from an absolute reset timestamp or a reset-after-seconds value. No usable windows → errors "Codex usage response contains no rate-limit windows" / "... no usable windows".

- **REQ-PROVIDER-125** — Copilot usage: `GET https://api.github.com/copilot_internal/user` authenticated with the stored GitHub `ghu_` token (the credential's refresh-token field; the short-lived model bearer minted by the session exchange is not accepted here, so it is never sent — a missing `ghu_` token errors "Copilot GitHub token is unavailable"), with headers `User-Agent: GithubCopilot/0.28.0` and `Copilot-Integration-Id: vscode-chat`. The quota snapshot with id "premium_interactions" is selected. One label is used for that snapshot whatever billing arrangement the account is on: it conveys that the figure is the Copilot premium-request allowance for the signed-in account, and its wording is left to the implementation. No payload field selects between alternative labels, and the read never branches on a billing kind. A quota flagged unlimited renders as a single row labelled "Unlimited" with 0% used and the detail "No plan allowance cap". Otherwise both an entitlement and a remaining-quota value must be present, and their absence fails the read with "Copilot plan allowance is incomplete". The used label reports the used amount against the entitlement as "<used> / <entitlement>", where used = entitlement − remaining and both numbers are written with thousands separators and without trailing fractional zeros. The used percent is 100 minus the payload's reported remaining percent when it reports one, and otherwise (entitlement − remaining) ÷ entitlement × 100; either way it is clamped into 0–100 and rounded to an integer under the rounding rule of REQ-PROVIDER-127. The detail is "<n>% remaining[ · resets <Mon D>][ · <n> overage]", where the reset date comes from the UTC quota-reset-date field when present and from the plain one otherwise, and the overage clause appears only for a non-zero overage count.

- **REQ-PROVIDER-126** — Claude Code usage: `GET https://api.anthropic.com/api/oauth/usage` with the subscription OAuth bearer plus headers `anthropic-beta: oauth-2025-04-20` and `anthropic-version: 2023-06-01` (no API key involved; not billed against the API). Windows: `five_hour` → "Claude Code 5-hour window"; `seven_day` → "Claude Code 7-day window"; each carries a utilization percent and an ISO-8601 reset timestamp; rendering matches codex ("<n>% used", "<m>% remaining · resets <relative>"). No usable windows → "Claude Code usage response contains no usable windows".

- **REQ-PROVIDER-127** — Reset-label formats: under 60 seconds → "in <1m"; then "in Xd[ Yh]", "in Xh[ Ym]", "in Xm". Calendar reset labels render "<Mon> <day>" (e.g. "Feb 3"). Percentages clamp to 0–100 and are then rounded half-up to a whole number — the same direction the money rule of REQ-PROVIDER-121 uses for every amount that is not a balance — so a value exactly halfway between two integers rounds away from zero. That single rule governs every percentage this domain displays. Numeric parsing accepts integers, floats, and comma-grouped numeric strings; booleans are rejected.

### Rotaris Cloud Account Credit

- **REQ-PROVIDER-128** — Credit reads perform `GET <api_base>/account/usage-status`, where the API base comes from the stored credential's `api_base` extra, falling back to the catalog default so a credential stored without that extra still works; an unusable stored base errors "Rotaris Cloud API base is unusable: <base>". Headers: the bearer plus `User-Agent: rotaris/account`; timeout 5 seconds.

- **REQ-PROVIDER-129** — The blocking account-status read: with no stored cloud credential it fails with a DISTINCT sign-in-required error ("Not signed in to Rotaris Cloud") whose meaning is "sign in", not "retry". Before reading, it puts the stored credential through the standard token fetch so an access token whose lifetime elapsed during a long-running session is renewed rather than reported as a rejected credential; that step fails with the recorded authentication error or "Rotaris Cloud sign-in has expired". HTTP 401/403 → "Rotaris Cloud rejected the stored credential; sign in again."; other HTTP errors → "Rotaris Cloud account request failed (<status>)" / "... failed"; a non-object body → "... response is not an object".

- **REQ-PROVIDER-130** — Credit payload contract: a required credit object (missing → an error stating the response "carries no credit block") with an atomic balance and an atomic scale — balance = atomic ÷ scale computed in exact decimal arithmetic, never in binary floating point (a non-number → "Rotaris Cloud credit balance is not a number", a non-positive scale → "... scale is not positive"); a state mapping to available | exhausted | overdrafted with unknown values degrading to "unknown" (forward compatibility: a new backend state must not break installed clients); an admission-allowed boolean (default false); an optional currency code (upper-cased, default "USD"); and an optional latest-settled-usage record (ISO-8601 occurrence time, status, cost) — a partially unusable usage record is dropped rather than failing the whole reading, so the balance still renders.

### Cross-Cutting Invariants

- **REQ-PROVIDER-131** — No credential value is readable in a log file, in user-visible error text, in a snapshot, in an event stream, or in a hook payload. One shared set of redaction rules covers all of them — no venue, the event stream included, carries rules of its own — and those rules are REQ-TOOLS-171's: the ordered layers, the credential value-prefix list, and the mask are fixed there and are neither restated nor varied here. What this domain relies on them for is that every credential shape a provider integration can produce is recognized wherever it occurs in text, and that the replacement is one fixed marker, identical in every venue, carrying no character of the value it replaced and no indication of its length, so neither a credential nor its size can be inferred from redacted text. Where a value is held under a mapping key that meets the secret-looking key test of REQ-TOOLS-172, the whole value is masked whatever it looks like; that is what keeps a credential out of a hook payload as surely as out of a log line. The 2+4+2 mask of REQ-PROVIDER-107 is a different thing and is never used as the redaction marker: it exists only as the deliberate rendering of a key the user themselves stored, and it is the only rendering of a stored key that any user interface shows.

- **REQ-PROVIDER-132** — Health issues for configured providers are summarized uniformly: an API-key-flow provider missing credentials → "<name> is missing an API key." (flagged as editable); an expired credential → "<name> authentication is expired."; otherwise "<name> is not authenticated."

- **REQ-PROVIDER-133** — Ordering invariant: for key-based providers, credentials are persisted only AFTER successful validation/discovery (sign-in, validated key update, programmatic registration), so a bad key is never stored silently — with the explicit exceptions of a save on which the user deliberately opted out of validation (REQ-PROVIDER-141) and the desktop's raw key-save path (which performs header validation only).

- **REQ-PROVIDER-134** — Ordering invariant: on-disk bridge artifacts are rewritten as part of every credential save and are on disk before that save returns, so an external consumer reading them can never observe an older credential than the store holds. Run-start priming also rewrites the bridge for a credential it found valid and did not renew, because that workspace may never have had the files written at all.

- **REQ-PROVIDER-135** — The generic `openai-compatible` catalog id is a template/family, never a credentialed provider itself: sign-out targets, the desktop add-provider list, and instance ids all exclude it; only `openai-compatible--<label>` instances hold credentials.

- **REQ-PROVIDER-136** — Static custom provider/model declarations in configuration (a `models.yml`-style declaration file) remain supported alongside discovery; ordinary onboarding does not need them. YAML-declared models with a complete provider and model id always override snapshot entries of the same name.

- **REQ-PROVIDER-137** — Thinking/reasoning levels shown for a model come from the model-capability metadata the product ships with: a model supports levels only when a reasoning-effort parameter is a supported parameter for it; the UI level set is (low, medium, high, max) minus levels the metadata disclaims (a disclaimed low removes "low"; a disclaimed extra-high removes "max"); the "max" level corresponds to the metadata's extra-high reasoning effort. Unknown or custom models expose no levels, and the thinking column collapses to the provider default.

- **REQ-PROVIDER-138** — *Withdrawn.* It existed only to stop a command-line flag mixing sign-out with a task; that sign-out is an action of its own and never carries a task is stated by REQ-PROVIDER-143.

- **REQ-PROVIDER-139** — *Withdrawn.* It fixed process exit codes for command-line subcommands that no longer exist, and the product exposes no exit status to a user; each outcome it encoded is reported to the user by the action that produced it (REQ-PROVIDER-142 sign-in, REQ-PROVIDER-143 sign-out, REQ-PROVIDER-141 deletion, REQ-PROVIDER-147 refresh).

- **REQ-PROVIDER-151** — Consumed remote contracts. Every remote payload shape this document states — discovery, subscription usage, and account credit — is a contract the product *consumes*, never one it defines, and behavior is fixed by what the product does with each value rather than by any promise about what a provider will keep sending. A payload carrying fields this build does not know SHALL be accepted with those fields ignored. A payload missing a value a read requires SHALL fail that read with the error the owning requirement names, and SHALL NOT be repaired by guessing a value. No read of a remote payload ever fails a run, deletes a credential, or changes a catalog attribute except where a requirement says so explicitly. Following a provider's payload change therefore costs a build's mapping data (REQ-PROVIDER-073, REQ-PROVIDER-079) and no behavior stated here.

- **REQ-PROVIDER-152** — Concurrent access to the shared stores. The credential files (REQ-PROVIDER-014) and the provider snapshot (REQ-PROVIDER-084) are per-user and may be reached by more than one application instance at once. Every write remains atomic per file, so no reader ever sees a partial document. In addition, every read-modify-write sequence over one of those files — saving a credential, deleting one, upserting a provider record, removing one — SHALL be performed while holding an exclusive lock taken on a lock file adjacent to the target, so that two instances serialize instead of interleaving and neither silently loses the other's change. A lock that cannot be taken within 5 seconds fails that operation with an error stating that another instance is updating the store and that the action can be retried; the operation never proceeds without the lock. A lock left behind by a process that is no longer running is reclaimed rather than blocking forever, and a lock held by a live process is never broken. Reads take no lock, because atomic writes already make every read consistent.

## Data & Formats

All formats below are externally observable (on disk, on the wire, or in process environments) and are normative.

### Stored credential file (per provider)

Path: `<per-user data dir for "rotaris">/tokens/<provider_id>.json`. JSON object, 2-space indented:

```json
{
  "access_token": "<string>",
  "refresh_token": "<string>",
  "expires_at": 0.0,
  "account_id": null,
  "extra": { "<string>": "<string>" }
}
```

- `expires_at` is a Unix timestamp; `0` means no expiry. Missing `expires_at`/`account_id`/`extra` are tolerated on load.
- Well-known extras keys: `api_base` (tenant or instance API base), `sku` (Copilot), `provider_family` ("openai-compatible" for instances), `auth_mode`/`requested_scopes`/`scope` (codex), `issuer`/`token_endpoint`/`revocation_endpoint` (hosted cloud OIDC).

### Provider/model snapshot

Path: `<per-user config dir for "rotaris">/project_settings.yaml`. YAML, keys unsorted, Unicode allowed, file mode 0644, atomic writes, unknown keys rejected:

```yaml
version: 1
providers:
  <provider-id>:
    id: <provider-id>
    display_name: <string>
    family: <string, optional>
    base_url: <string, optional>
    authenticated: <bool>
    default_summary_model: <qualified id, optional>
    large_model: <qualified id, optional>
    medium_model: <qualified id, optional>
    small_model: <qualified id, optional>
    fallback_model: <qualified id, optional>
    discovered_at: <ISO-8601 with UTC offset>
    models:
      - id: <qualified id>
        display_name: <string, optional>
        capabilities: { accepts_image_input: <bool>, image_input_tokens: <int, optional>, image_input_tokens_per_megapixel: <number, optional>, ... }
        limits: { context_window: <int>, ... }
        pricing: { input_cost_per_token: <float>, output_cost_per_token: <float>, image_cost_per_image: <decimal string, optional> }
        discovered_at: <ISO-8601 with UTC offset>
```

Secret-like keys or values abort the write (REQ-PROVIDER-086). The key test is REQ-TOOLS-172's and the value-prefix list is REQ-TOOLS-171's; neither is restated here. The exempt keys are the two per-token price fields beneath `pricing` and the token-limit keys beneath `limits`, and no other.

### Identifiers

- Qualified model id: `<provider-or-instance id>/<model id>` (e.g. `claude-code/sonnet`, `openai-compatible--my-lab/gpt-4o`).
- OpenAI-compatible instance id: `openai-compatible--<slug>`; slug = label lowercased, non-alphanumeric runs collapsed to `-`, trimmed, non-empty.

### Copilot gateway staging files

Per-workspace staging directory `<workspace root>/.rotaris/copilot-gateway/`, published via environment variable `GITHUB_COPILOT_TOKEN_DIR`. Directory protection matches the credential store (POSIX `0700`; on Windows an explicit ACL for the owning user and the local system account); both files carry POSIX mode `0600` and the equivalent Windows ACL:

- `access-token` — plain text; the durable `ghu_` token from the device flow (or the session bearer when no refresh token exists).
- `api-key.json` — compact JSON: `{"token": "<bearer>", "expires_at": <int unix ts>, "endpoints": {"api": "<base url>"}, "sku": "<string, optional>"}`.

Environment: `GITHUB_COPILOT_ACCESS_TOKEN` is defaulted (never overwritten) to the sentinel `managed-by-rotaris`. The subscription runtime for claude-code receives the stored token as `CLAUDE_CODE_OAUTH_TOKEN`.

### Discovery response (consumed contract)

Generic providers: a JSON object with a `data` list of model objects, each with `id` and optional `display_name`/`name`, capability and limit objects (including `context_length`, and including whatever the provider reports about accepted input modalities, from which the image-input declaration of REQ-PROVIDER-149 and any image token cost of REQ-PROVIDER-150 are taken), and — for the hosted cloud — decimal-string per-token prices (`prompt_usd_per_token`, `completion_usd_per_token`). Codex: a JSON object with a `models` list whose items carry `slug`, `supported_in_api`, `visibility`, `supported_reasoning_levels`, `input_modalities`, `context_window`/`max_context_window`. Hosted-cloud suggestions endpoint (`<base>/model-suggestions`): roles `small`, `medium`, `large`, `fallback` naming discovered model ids.

### Subscription usage payloads (consumed contracts)

- Codex (`.../wham/usage`): a `rate_limit` object holding `primary_window` and `secondary_window`, each with `used_percent`, `limit_window_seconds` (18,000 = 5-hour, 604,800 = weekly), and a reset timestamp or reset-after-seconds.
- Copilot (`.../copilot_internal/user`): quota snapshots; the `premium_interactions` snapshot with `unlimited`, entitlement, remaining quota, remaining percent, overage count, and a UTC quota reset date.
- Claude Code (`.../api/oauth/usage`): windows `five_hour` and `seven_day`, each `{utilization: <percent>, resets_at: <ISO-8601>}`.

### Cloud account credit payload (consumed contract)

`GET <api_base>/account/usage-status` returns a JSON object with: a required `credit` object carrying `balance_atomic` (number) and `atomic_scale` (positive number), a `state` string (available | exhausted | overdrafted; unknown values degrade to "unknown"), `admission_allowed` (boolean, default false), optional `currency` (upper-cased, default "USD"), and optional `latest_settled_usage` `{occurred_at: <ISO-8601>, status: <string>, cost_usd: <number>}`.

### Rendering formats

- Stored-key display mask (REQ-PROVIDER-107): `****` for values ≤ 4 chars; else first 2 + `****` + last 2. This is the rendering of a key the user themselves stored and is not the redaction marker.
- Redaction marker: not restated here — REQ-TOOLS-171 (REQ-PROVIDER-131).
- Money: exact decimal arithmetic; balances floored, other amounts rounded half-up; 2 decimal places (4 below $0.01 magnitude); $/€/£ symbols, otherwise `<amount> <CODE>`.
- Percentages: clamped to 0–100, then rounded half-up to a whole number (REQ-PROVIDER-127).
- Relative reset labels: "in <1m", "in Xd[ Yh]", "in Xh[ Ym]", "in Xm"; calendar labels "<Mon> <day>".
- Timestamps persisted in the snapshot are ISO-8601 with a UTC offset.

### Workspace bootstrap

A minimal `.rotaris/agents.yaml` (YAML; default persona `orchestrator`) is bootstrapped when absent during sign-in flows; guided slot assignment and the startup-models editor write the seven slot fields and per-persona overrides into the same file.
