### PD-CHAT-013 — a tool call held for approval reads `waiting`, not `running`

A tool row whose status is `running` and is not settled, and whose call is named by a brokered approval request that is still pending — its `approval.requested` published (REQ-TOOLS-061), its dialog open or queued (REQ-TOOLS-063), and the request not yet answered, cancelled, timed out or withdrawn (REQ-TOOLS-054) — MUST render a still `◉ waiting for approval` in `--rt-wait` in place of REQ-CHAT-060's pulsing `◉ running…`, MUST NOT pulse while it does, and MUST state in its accessible description that the call is waiting for approval, so the wait is never carried by colour alone (REQ-SHELL-149). The row's stored status stays `running`, and the tool status vocabulary stays closed to the four values of REQ-CHAT-046. When the request leaves the pending set the row MUST follow REQ-CHAT-060 and REQ-MONITOR-105 unchanged: the pulsing `◉ running…` on an approval, `blocked · <seconds>s` with its reason reachable on a deny or a withdrawal, and REQ-MONITOR-228's correction where the run ends first. A headless ask never waits and is never in this case. The duration is unchanged and counts from the call's start. So that a pending request can be matched to the row it holds, the approval payload MUST carry `call_id`, the stable per-tool-call key of REQ-CHAT-046, beside the nine fields REQ-TOOLS-056 names and the `session_scope` field PD-TOOLS-021 adds; the field is added and nothing in that list is displaced. Every other row, and every row with `ok`, `failed` or `blocked`, is unchanged.

**Why, and what it costs.** The gate opens a call's record before it asks for approval (`tool.start` precedes the ask, REQ-EVENTS-076), so a call held at REQ-TOOLS-063's dialog is stored `running` and drawn with the pulse — the transcript tells the operator that work is happening at the moment the run is waiting on them. REQ-TOOLS-063 shows one request at a time and REQ-CHAT-051's trailer row sits at the foot of the transcript, so with parallel calls neither says which pulsing row is the held one. The design language already has the state: §1.3 names axis X **waiting**, §1.11 names it `waiting`, and §1.8 permits the pulse only while a state is actively running, which a held call is not. A fifth persisted status was declined: REQ-CHAT-060 and REQ-CHAT-046 close the vocabulary, REQ-MONITOR-228 would have to correct it at a run's end, and the wait is a passing fact the run already owns as its pending approvals, so the cue is drawn from that set and nothing is written to history. The cost: the literal `◉ running…` is given up for that one case; the approval payload gains a field REQ-TOOLS-056 does not name, beside the `session_scope` field PD-TOOLS-021 adds in the same round, because joining by tool name is ambiguous when two calls of one tool are held — an extension of the field list, displacing none of it; and the duration a held call settles with still counts the time spent waiting, which this directive leaves as it is. Whether operators tell the rows apart is measured only in the built app. Raised as [OQ-520](../../archive/architecture/open-questions/70-spikes-and-later-questions-37-continued-3.md#oq-520).
