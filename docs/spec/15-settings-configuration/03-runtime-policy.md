# Settings and Configuration — Runtime policy

Part 3 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-111 – REQ-CONFIG-470.

### Runtime policy

- **REQ-CONFIG-111** — The `runtime:` section validates **on assignment as well as on load**, so a settings surface writing an invalid value onto a loaded configuration is refused at the moment of the write, not silently at the next load.
- **REQ-CONFIG-112** — Concurrency and depth: `max_children` (int, default **20**, total child agents in a run); `max_active_children` (int, default **6**, concurrent fan-out); `max_depth` (int, default **3**, delegation depth); `max_iterations` (int, default **20**, iteration cap); `message_limit` (int ≥ 1 or null, default null).

This requirement is the product's single definition of `message_limit` — its name, its value space and its default — and no requirement in any other domain holds a second copy of any of the three: a requirement that needs the limit cites this one and states only what it adds, such as what a run does when it reaches the limit or how a paused run is resumed. Its value space is exactly a positive integer or null: **null is the default and means no limit is applied**, so an unconfigured installation never reaches a message-limit pause, and null is also what a run carries when no limit was set for it. **Zero is not a permitted value**: it is rejected at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried, rather than being read as a second spelling of "disabled" — one spelling of "no limit" is what keeps a stored `0` from meaning "unlimited" in one domain and "stop at once" in another. A negative value is rejected the same way.
- **REQ-CONFIG-113** — Child timing: `child_timeout` (int seconds, default **1200**, hard per-child wall clock); `child_stall_timeout` (int seconds, default **90**, no-event threshold before a child is reported stalled).
  > **Narrowed by [`PD-ORCH-004`](../../product/directives/pd-orch-004.md#pd-orch-004) revision 5, 2026-10-06.** `child_timeout` is the
  > instant the child is asked to land; what it has in flight then has at most 30 s more to end, and the child's
  > execution is then aborted, so the hard wall clock is `child_timeout` plus at most 30 s.
- **REQ-CONFIG-114** — `llm_response_timeout` (int seconds, default **120**, minimum **30**): when no model event arrives within this window the role's `fallback_model` is engaged and **the child keeps running**. This is distinct from `child_timeout`, which ends the child.
- **REQ-CONFIG-115** — Model and tool timing: `model_timeout` (int seconds, default **120**, global model HTTP timeout overridden per model by REQ-CONFIG-086); `tool_call_timeout` (int seconds, default **30**, one tool call other than a terminal command); `summary_timeout` (int seconds, default **120**, generating a summary). The last two carry the names and defaults REQ-NOTIFY-100 fixes for those bounds, and no second key names either bound.
- **REQ-CONFIG-116** — Terminal execution: `shell_command_timeout` (int seconds, default **100**, one foreground command, named and defaulted per REQ-NOTIFY-100); `shell_max_background_sessions` (int, default **20**, range **1–64**); `shell_background_timeout` (int seconds ≥ 1, default **3600**, hard wall clock for a background command, enforced by a graceful termination signal followed by a forced kill). The maximum on the background-session count is stated rather than left open because that count is a multiplier on live terminal streams, whose delivery REQ-MONITOR-306 bounds in aggregate: with no ceiling the worst-case staleness of a live surface cannot be computed from a configuration at all, only observed after the fact, and with one it is `(agents + maximum) × windows ÷ 1,000` seconds. The figure is **64**, which is the ceiling REQ-TRACE-481 fixes for a concurrency control and is taken here for the same reason it gives: an input needs some upper bound, and a figure no machine could actually service is of no use to anyone. It bounds what may be configured and nothing else — the effective limit and the message on reaching it stay REQ-TOOLS-108's, and a value outside the range is **rejected** at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried, never clamped to the nearest bound and never ignored.
- **REQ-CONFIG-117** — Live terminal streaming: `terminal_stream_enabled` (bool, default true — disabling it removes the live view, never the command); `terminal_stream_interval_ms` (int, default **100**, range **20–2000**); `terminal_stream_buffer_kb` (int, default **256**, range **0–8192**, where **0 disables replay** for a display attaching mid-command). `terminal_stream_interval_ms` is a **ceiling on batching and not a fixed cadence**: a stream MAY frame its output sooner than the period, and MUST do so when input the user has directed at a stream whose control they have taken arms the next frame of that stream, so that REQ-SHELL-166's echo criterion is met at every value this range permits. Two bounds hold that licence and neither is relaxable by configuration: no two frames of one stream are ever closer together than **20 milliseconds**, and what reaches surfaces stays inside REQ-MONITOR-306's aggregate. **Output alone never arms a frame**, and neither does input an agent sends to its own terminal session; both are framed at the period, so the licence is spent only where a person is waiting to see their own keystroke. Read as a fixed cadence the key would put REQ-SHELL-166 out of reach at its own default and at every larger value in its range, which is why the reading is fixed here rather than left for an implementer to derive.
- **REQ-CONFIG-118** — Improvement collection: `improvement_collector_enabled` (bool, default true — one collection pass follows each finished top-level task run, and that pass can neither delay nor modify the run); `improvement_collector_timeout` (int seconds ≥ 1, default **60**; exceeding it falls back to an empty artifact).
- **REQ-CONFIG-119** — `claude_sdk_native_loop` (bool, default true): children routed to the locally installed agent-SDK provider run on that SDK's own loop with the product's tools published in-process. Setting it false falls back to a one-shot completion path that **discards tools and streaming**.
- **REQ-CONFIG-120** — Retries: `auto_retries_transient` (int, default **1**), `auto_retries_validation` (int, default **0**).
- **REQ-CONFIG-121** — `session_log_level` (string, default `WARNING`) sets the verbosity of the per-session debug log. The documented vocabulary is `DEBUG`/`INFO`/`WARNING`/`ERROR`; the value is **not** validated against that list.
- **REQ-CONFIG-122** — `permission_mode` (string) selects the permission preset a run starts from. The preset vocabulary is REQ-TOOLS-041's, the shipped default and the resolution of an unrecognized or absent name are REQ-TOOLS-046's, and the strictest-first ordering the settings surface presents them in is REQ-TOOLS-047's; this domain holds no copy of any of the three. What it adds is that the preset is selected by a `runtime:` key of that name, which layers per field and validates on assignment as well as on load (REQ-CONFIG-111) — and that, because an unrecognized value resolves rather than fails, a configuration carrying one still loads.
- **REQ-CONFIG-123** — `allow_outside_workspace` (bool, default false) opts out of workspace fencing for file access.
- **REQ-CONFIG-124** — `allow_unsandboxed_autonomous` (bool, default false) is the opt-in named by the downgrade rule of REQ-TOOLS-067. What that rule does — which modes it downgrades, the three conditions it downgrades on, and the mode it downgrades to — is fixed there and not restated here; this key is one of the three conditions and nothing more. What this domain adds is that it is a `runtime:` key with that name and that default, layering per field like every other, and the guidance that it belongs in a workspace configuration rather than the global one (REQ-SANDBOX-052).
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The key above still exists with the same default and layering; it no longer has any effect on any run.
- **REQ-CONFIG-125** — Approval fallback: this requirement registers `headless_approval_policy` (string) in `runtime:` and holds no copy of its accepted values, its shipped default, the reading of an unrecognized value, or what each value does to a refused call, all of which are REQ-TOOLS-065's. What this domain adds is that it is a `runtime:` key of the primary configuration document, that it therefore validates on assignment as well as on load (REQ-CONFIG-111), that it layers per field like every other runtime key (REQ-CONFIG-031), and that — because an unrecognized value resolves rather than fails — a configuration carrying one still loads (REQ-CONFIG-233).
- **REQ-CONFIG-126** — `approval_timeout_seconds` (float ≥ 0, default **300.0**) is how long a tool call waits for interactive approval before being denied. **A value of 0 means wait without a limit**; such a wait is still ended by cancelling the run. One setting covers two barriers: the same key, the same default and the same reading of zero govern the wait on a question put to the user as well as the wait on an approval (REQ-TOOLS-055, REQ-TOOLS-178, REQ-TRACE-467), and no second key names either wait. Its value space is the free-floating one REQ-TOOLS-055 fixes — any float at least 0, a negative value rejected at load and on assignment (REQ-CONFIG-111) — rather than a fixed list of offered stops, so an editing surface may suggest values but accepts every value the space permits (REQ-CONFIG-446).
- **REQ-CONFIG-127** — Confinement: this requirement registers three keys in `runtime:` and holds no copy of their vocabularies, defaults or validation rules, which are the sandbox-and-egress domain's. `sandbox_mode` (string) — vocabulary, shipped default and validation per REQ-SANDBOX-048, and the YAML boolean-false spelling per REQ-SANDBOX-049. `sandbox_writable_roots` (list of strings) — default, entry form and the absolute-path rule with its message shape per REQ-SANDBOX-050. `sandbox_allow_network` (bool) — default and the condition under which it has effect per REQ-SANDBOX-051. What this domain adds is only that all three are `runtime:` keys of the primary configuration document, that they therefore validate on assignment as well as on load (REQ-CONFIG-111), that they layer per field like every other runtime key (REQ-CONFIG-031), and that they are among the six values the security policy card writes (REQ-CONFIG-312).
- **REQ-CONFIG-128** — Egress: this requirement registers three keys in `runtime:` and holds no copy of their vocabularies, defaults, normalization or precedence, which are the sandbox-and-egress domain's. `network_egress_policy` (string) — disposition vocabulary, shipped default and the matching of a stored spelling per REQ-SANDBOX-001 and REQ-SANDBOX-002. `network_allowed_hosts` and `network_denied_hosts` (lists) — defaults, load-time entry normalization, the pattern grammar and the rule that a denial outranks an allow and a permissive default, per REQ-SANDBOX-003, REQ-SANDBOX-004, REQ-SANDBOX-009 and REQ-SANDBOX-014. What this domain adds is the same three facts REQ-CONFIG-127 adds for the confinement keys: they are `runtime:` keys, they validate on assignment as well as on load, they layer per field, and they complete the six values the security policy card writes (REQ-CONFIG-312).
- **REQ-CONFIG-129** — Completion checking: `classify_completion` (bool, default true) runs a post-iteration model check on the small tier — a "needs iteration" verdict re-queues, and a verdict that cannot be read is **resolved as complete**, so a momentary model failure cannot wedge a run. `validate_intent` (bool, default false) is deprecated and superseded by it.
- **REQ-CONFIG-130** — Persistence loop: `relentless` (bool, default false) keeps the loop running when the task list empties, checking fulfilment against the original request and appending remediation tasks; `relentless_max_cycles` (int ≥ 1, default **3**) hard-caps remediation cycles.
- **REQ-CONFIG-131** — Diagnostics and shutdown: `memory_diagnostics_enabled` (bool, default false — enables allocation tracking with snapshots written to the session's evidence stream); `memory_diagnostics_top_frames` (int, default **8**, range **0–50**, where **0** records aggregate memory only); `graceful_pause_tool_deadline` (float seconds, default **30.0**, range **5.0–120.0**, how long in-flight tool calls are awaited during pause or shutdown); `shutdown_drain_timeout` (float seconds ≥ 0, default **120.0**, grace for still-running background children at natural run conclusion, where **0 disables draining**).
- **REQ-CONFIG-467** — `loop_classification_timeout` (float seconds > 0, default **2.0**) bounds one loop-classification call and is the key REQ-NOTIFY-100 names for that bound. It sits in `runtime:` beside the other operation bounds so that each of the seven can be changed without changing another. The configured value is an upper bound only: a classification call is allowed no more than whatever remains of the activation budget of REQ-NOTIFY-106 when it is dispatched, so raising this key can never lengthen a call past that budget. This key is the product's single definition of that bound: it is the only key naming it, the value registered here is the value in force, and no other section — `circuit_breaker:` included (REQ-CONFIG-136) — carries a second key or a second default for it. A requirement that needs the bound cites this key and states no figure of its own.
- **REQ-CONFIG-468** — `additional_read_only_roots` (list of strings, default empty) designates locations outside the workspace that the file-reading tools may read and that every write is refused against (REQ-TOOLS-132). Each entry must be absolute in either POSIX or Windows spelling; a relative entry is rejected at load **and on assignment** (REQ-CONFIG-111) with a message naming the offending entry and stating the absolute-path rule, matching the rule and message shape of `sandbox_writable_roots` (REQ-CONFIG-127). Configuration is the only designation: no other surface widens the read fence, and the key grants nothing to confinement, which imposes no read restriction of its own (REQ-SANDBOX-053).
- **REQ-CONFIG-469** — `keep_going` (bool, default false) is the configured keep-going criterion of REQ-MONITOR-302, which ties run completion to verification evidence: while it is on, a completion-based stop is not taken while the most recent verification suite holds a failed or timed-out check. It is distinct from `relentless` (REQ-CONFIG-130), which audits fulfilment against the original request; the two are independent and either may be set without the other. It is a Tier B setting: the value a run uses is the one the interface holds when the run starts (REQ-CONFIG-262, REQ-CONFIG-263), so it can be set for the workspace on the settings screen and varied for a single run without being written to a file, and nothing else configures it.
- **REQ-CONFIG-473** — `event_retention_per_session` (int ≥ 0, default **20000**) is the retention cap on one session's stored event history: it bounds how many events that history keeps, and events beyond the cap are discarded oldest first, so a history that outgrew the cap holds the later part of the run rather than the earlier part. **A value of 0 means the history is never trimmed.** A negative value is not a permitted configuration value and is rejected at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried; it is never coerced to zero and never ignored. It sits in `runtime:` beside the other operation bounds. This requirement registers the key, its default and its value space; when a trim happens, how it is performed, and how a consumer learns that events were dropped are the event store's (REQ-EVENTS-091), which this key configures and which restates none of the above.
- **REQ-CONFIG-474** — `task_consecutive_retry_limit` (int ≥ 1, default **3**) is the per-task consecutive-retry limit REQ-ORCH-077 requires to be a setting of its own: it bounds how many consecutive pending-outcome iterations one task may accumulate before that task is abandoned. This requirement registers the key, its type and its default and holds no copy of the rule that consumes it — what the counter is kept over, what resets it, and what abandoning the task does are REQ-ORCH-077's. It sits in `runtime:` beside the other run budgets and is deliberately separate from `max_iterations` (REQ-CONFIG-112), so that either can be changed without changing the other; sharing one value is what made the guard unreachable. It layers per field and validates on assignment as well as on load (REQ-CONFIG-111).
- **REQ-CONFIG-475** — `relentless_audit_timeout` (int seconds ≥ 1, default **60**) bounds the single fulfilment-audit model call relentless mode makes before it decides whether to extend a run (REQ-ORCH-079). This requirement registers the key, its type and its default and holds no copy of the rule that consumes it — when the audit runs, what it compares, and the rule that a failed, timed-out or unparseable audit is neither retried nor allowed to extend the run are REQ-ORCH-079's. It sits in `runtime:` beside `relentless` and `relentless_max_cycles` (REQ-CONFIG-130), layers per field, and validates on assignment as well as on load (REQ-CONFIG-111).
- **REQ-CONFIG-476** — `run_start_mode` (string, exactly `auto` or `plan`, default `auto`) selects the run-start mode of REQ-ORCH-152. This requirement registers the key, its accepted values and its default and holds no copy of what either mode does: that `auto` applies no gate, that `plan` engages the gate of REQ-ORCH-153, and that the setting outlives the run that used it and governs the next run started in the same workspace are REQ-ORCH-152's. A value outside the two is **rejected** at load and on assignment (REQ-CONFIG-111), with a message naming the value and both accepted spellings, and is never coerced: a mis-spelled `plan` quietly read as `auto` would remove a gate the user asked for, which is why this key is not given the coercion an unrecognized permission mode receives (REQ-CONFIG-122, REQ-CONFIG-233). Being persistent, it is an ordinary `runtime:` key of the primary configuration document, layered per field like every other. It is the only key naming the run-start mode: every surface that offers the mode — the settings screen (REQ-CONFIG-320) and the surface a run is started from (REQ-ORCH-152) — writes this same key, and no surface holds a run-start mode of its own that a later load would not read back.

### Compression and circuit breaker

- **REQ-CONFIG-132** — `compressor:` fields: `model` (string, subject to tier-alias substitution; shipped default is the `small_model` alias); `timeout_seconds` (int, default **120**); `default_threshold` (int, default **265000**, the token capacity assumed whenever the running model advertises none); `threshold_percentage` (int, default **60**; the range accepted from a hand-authored file is **1–100**, while every editing surface offers **50–95** (REQ-CONFIG-446); **60** is the single authoritative default, and every surface, hint and document that names the auto-compression trigger names that same figure — there is no second value anywhere in the product); `chars_per_token` (int, default **4**, the token-estimation heuristic); `preserve_recent_turns` (int, default **4**, turns never compressed).
- **REQ-CONFIG-133** — `compressor.auto_threshold_ratio` (float, default **0.35**) is retained for configuration compatibility only and does not participate in threshold resolution; `threshold_percentage` is authoritative.
- **REQ-CONFIG-134** — The compression trigger is resolved as `capacity × threshold_percentage / 100`, with capacity chosen in this priority order: (1) the model's explicit `context_compression_threshold`; (2) the smaller of the model's advertised `max_input_tokens` and the configured `default_threshold`; (3) `default_threshold`, falling back to **265000** when that is unset or zero.
- **REQ-CONFIG-135** — Whenever a compression trigger is resolved, the resulting token number is accompanied by a statement naming the four inputs that produced it: the `threshold_percentage` applied, the capacity it was applied to, the model's advertised input limit and the configured `default_threshold`. That statement is the reason the user is given for a compression having fired, and it is surfaced in exactly two places. It is emitted on the session's event stream as part of the event that reports the compression, carrying the four inputs and the resulting token number as **separate machine-readable fields** so a consumer never has to parse a sentence; and it is rendered, from those fields, as the reason line of the transcript entry that reports the compression in the desktop transcript. The same fields are written to the per-session debug log at informational level. A compression is never reported to the user without them.
  > **Narrowed by [`PD-ORCH-014`](../../product/directives/pd-orch-014.md#pd-orch-014), 2026-10-06.** "The session's event stream" is read
  > as the session's timeline (OQ-53's ruling): the event that reports the compression is the `context_compressed` timeline
  > entry, which carries the four inputs and the resulting token number as separate fields.
- **REQ-CONFIG-136** — `circuit_breaker:` fields: `enabled` (bool, default true; false bypasses evaluation entirely); `model` (string, shipped default the `small_model` alias); `activation_mode` (`independent` or `weighted`, default `independent`, enforced against that vocabulary). The section carries **no** timeout field of its own. The bound on the loop-classification call this section configures is `runtime.loop_classification_timeout` (REQ-CONFIG-467), which is the single key that names it; a `timeout_seconds` key under `circuit_breaker:` is not a recognized field and is reported like any other unknown key in a merged section (REQ-CONFIG-233). Two keys naming one bound is what let two different values for it stand at once, so the second is removed rather than kept in step by hand.
- **REQ-CONFIG-137** — Circuit-breaker thresholds: `tool_call_threshold` (int ≥ 1, default **60**); `message_count_threshold` (int ≥ 1, default **60**); `tool_weight` (float **0.0–1.0**, default **0.6**); `message_weight` (float **0.0–1.0**, default **0.4**); `target_score` (float > 0, default **1.0**); `max_recent_events` (int ≥ 4, default **24**); `max_transcript_chars` (int ≥ 500, default **8000**); `repetition_threshold` (int ≥ 2, default **4**); `cycle_threshold` (int ≥ 2, default **3**).
- **REQ-CONFIG-138** — The two weights are bounded individually and are **not** constrained to sum to 1.0; a configuration whose weights sum to any value in range loads without complaint.

### Verification suite

- **REQ-CONFIG-139** — `verifier.checks` (list or unset, default unset) is three-valued per REQ-CONFIG-056. The resolver must never conflate an explicit empty list with a failed auto-detection.
- **REQ-CONFIG-140** — `verifier.gate_completion` (bool, default true). While true, an iteration that changed at least one file cannot be reported complete while any check of severity `blocking` is failing. While false, the suite still runs and every result is still reported, but no result withholds completion. An iteration that changed no file is never gated at either setting.
- **REQ-CONFIG-141** — `verifier.suite_timeout` (int seconds ≥ 1 or null, default **900**) caps a full suite execution. A check runs under whichever is lower: its own timeout, or whatever remains of the suite budget. Once that budget is exhausted, checks that never started are recorded **skipped** — neither run nor failed, and **a skipped check can never block completion**. Null means no suite budget — per-check timeouts only.
- **REQ-CONFIG-142** — `verifier.author_gate` (bool, default true): a designated role authors the suite once the technology stack settles and writes it into `verifier.checks`. False turns each such write into a proposal that needs approval before it lands. The setting stops mattering the moment `verifier.checks` holds a value: an already-declared suite is not authored a second time.
- **REQ-CONFIG-143** — `verifier.probe_timeout` (int seconds ≥ 1, default **30**) budgets one calibration probe and is deliberately independent of the suite budget.
- **REQ-CONFIG-144** — `verifier.max_repair_attempts` (int, default **2**) is how many extra passes a gated task is granted to fix what the suite reported; every pass is handed the failing output and re-runs the suite afterwards. Once those passes are used up the task terminates in a verification-failed state that **names the offending checks**, instead of looping on to the global iteration cap. **0** reports without retrying. The setting applies only while `gate_completion` is true.
- **REQ-CONFIG-145** — A check entry requires `name` (non-blank string) and `command` (non-blank string), and accepts `timeout` (int seconds ≥ 1, default **600**), `severity` (`blocking` or `advisory`, default `blocking`; an advisory result is reported and has no gating effect), `role` (`test`, `typecheck`, `lint`, `other`, or unset — unset means deliberately unstated), `cwd` (workspace-relative directory or unset, defaulting to the workspace root, which lets a single gate span several projects held in one workspace), and `failure_pattern` (string or unset, default unset — a regular expression the check declares so that a run recognizes a failure the command reported without failing its exit status). This document registers `failure_pattern` as a field of the entry, its type and its default, and holds no copy of what is done with it: that it is honoured for a check of role `test` and for no other role, that a check declaring one is recorded failed when the pattern matches whatever the exit status was, and that a check declaring none is recorded on its exit status alone are REQ-ORCH-123's. Being an accepted field is what keeps a check that declares one from being read as an entry with an unrecognized key.
- **REQ-CONFIG-146** — Check errors are raised **at load time**, each naming the offending check: blank name; blank command; blank `cwd` (with guidance to omit it for the root); an absolute `cwd` in either POSIX or Windows spelling; a `cwd` containing any parent-directory component after separator normalization; and a `failure_pattern` that is present but is not a usable regular expression, reported with the offending pattern text, so a typo in it fails loudly at load rather than silently matching nothing while a suite is running. A `cwd` that is inside the workspace but simply does not exist is a **different** condition, answered at run time rather than at load.
- **REQ-CONFIG-147** — Two check entries with the same name are rejected at load with a message naming the duplicate.
- **REQ-CONFIG-470** — `integration:` is a section-class key (REQ-CONFIG-047) holding one field, `validation_command` (string or null, default null), which is the only way the repository's own narrow validation is identified for worktree integration (REQ-GIT-156). Left null, no validation clause is produced and no validation runs. It is never inferred from the workspace's contents and never chosen by an agent, and this domain neither runs it nor gates on it: the load path validates its type and merges it per field like any other section, and the domain that owns integration decides what is done with it. It is distinct from `verifier.checks` (REQ-CONFIG-139), which this domain does gate on.
