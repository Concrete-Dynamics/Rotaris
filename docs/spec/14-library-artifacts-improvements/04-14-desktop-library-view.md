# Library, Artifacts, and Improvement Proposals — 14. Desktop Library view

Part 4 of 7 of [domain 14](../14-library-artifacts-improvements.md), which indexes every part. Defines REQ-LIBRARY-102 – REQ-LIBRARY-173.

### 14. Desktop Library view

**REQ-LIBRARY-102** — The Library MUST be one of seven top-level views held in a fixed navigation order — dashboard, workspace, mission, requirements, git, library, settings — each reachable with `Ctrl+<1-based index>`, which places the Library at `Ctrl+6`, and it MUST carry the navigation label "Library". Notifications and actions MUST be able to deep-link to the Library with either the artifacts tab or the proposals tab already active. The view order and its shortcuts are a global contract this domain does not own and MUST NOT restate normatively: REQ-SHELL-023 is canonical for the seven views and their order, and REQ-SHELL-049 is canonical for the shortcut table that binds `Ctrl+1` through `Ctrl+7` to them in that order. What this domain requires is only that the Library is one of those views, that it carries the navigation label "Library", and that it is reachable by whatever key REQ-SHELL-049 assigns it; should that assignment ever change, this requirement follows it rather than contradicting it.

**REQ-LIBRARY-103** — The Library MUST show a page title "Library", a single search field (placeholder "Search prompts, artifacts, and proposals…", accessible name "Search Library") that live-filters on every text change, and exactly three tabs in order: "Prompts", "Artifacts", "Improvement proposals". Tabs MUST be addressable by stable names (`prompts`, `artifacts`, `proposals`) rather than positions; activating an unknown tab name is ignored. Those three names are a closed set, and this requirement is the product's single definition of it: a document that names a Library tab — to open one, to route an action to one, or to validate a value against them — SHALL cite this identifier rather than holding a second copy of the list, and the set grows only by being amended here.

**REQ-LIBRARY-104** — Search MUST use case-insensitive substring matching. The searched text per row is: for artifacts, title + producer + persona + kind + status; for proposals, summary + category + status + recommended action; for prompts and stash entries, the prompt text itself. One query filters all three tabs simultaneously.

**REQ-LIBRARY-105** — The Library MUST agree with what is stored without the user reloading anything. Once a burst of changes has settled, all three tabs MUST show the stored state including the last change of that burst; no change may be lost because a later one overtook it. A change that arrives while the Library is off screen MUST be visible the next time the Library is shown, with no manual refresh. Updates MUST NOT disturb work in progress: text being typed in the search field is never cleared or reordered, and a selected proposal stays selected across updates (REQ-LIBRARY-111). A "library change" — the event this cycle, the saved-prompts write of REQ-LIBRARY-138, and the slash-catalogue rebuild of REQ-LIBRARY-142 all key off — is exactly a change to one of the four things the Library shows: the prompt history, the prompt stash, the session artifact store, or the workspace's improvement artifacts. Nothing else is one. A settings change that touches none of them — enabling a tool server, switching a skills mode, changing a model slot — MUST NOT count as a library change, MUST NOT write the stored prompts, and MUST NOT rebuild the Library's tables.

**REQ-LIBRARY-106** — The Prompts tab MUST show two side-by-side cards in a drag-resizable split whose position persists across restarts (splitter handle accessible name "Resize the prompt stash and history columns"; minimum column width 240 px). Left, accented card "Prompt stash": list (accessible name "Stashed prompts"), empty label "No stashed prompts.", secondary button "Use" and primary button "Use and remove". Right card "Prompt history": list (accessible name "Prompt history"), empty label "Prompt history is empty.", secondary button "Use selected".

**REQ-LIBRARY-107** — Double-clicking a stash or history row, or clicking one of the buttons of REQ-LIBRARY-106, MUST load that prompt text into the workspace composer, switch to the workspace view, and focus the composer. Whether the entry survives that MUST never be implicit: keeping and removing are separate stash actions, exactly as they are in the stash dialog (REQ-LIBRARY-141). "Use" and a double-click on a stash row copy the prompt and leave the entry in the stash; only "Use and remove" removes it, keyed by the entry's original index so a filtered view removes the right item. Prompt history offers no removal at all: "Use selected" and a double-click both copy without removal. There is therefore no asymmetry left to reconcile — the stash is the column that can be emptied, and emptying it is always a deliberate act.

**REQ-LIBRARY-108** — The Artifacts tab MUST show one accented card "Session artifacts" with the note "Everything agents published or reported in the loaded session.", a flat table (accessible name "Session artifacts") with columns Title, Producer, Persona, Kind, Status, Created; the status cell appends ` · edited` when the record has been hand-edited; columns auto-size to contents on every refresh; the empty label is "No artifacts have been published in this session."; and a primary "Inspect / edit selected" button. Double-clicking a row or clicking the button requests opening the inspector for that artifact.

**REQ-LIBRARY-109** — The Proposals tab MUST show, beside the improvement-artifact list of REQ-LIBRARY-166, an accented card "Improvement proposals" with the note "Evidence-backed suggestions from the improvement collector after each run.", a flat table (accessible name "Improvement proposals") with columns Summary, Category, Risk, Status, Created; category is displayed with underscores replaced by spaces; status displays `pending_review` as `pending` and other statuses verbatim; the empty label is "No proposals yet. They appear here after a run's improvement collector finds signals."; below the table a word-wrapped detail label reads "Select a proposal to see its recommended action." with no selection and `Recommended action: <text>` otherwise.

**REQ-LIBRARY-110** — The proposals action row MUST contain secondary buttons "Approve", "Reject", "Defer" (mapping to statuses `approved`, `rejected`, `deferred`) and the "Reset to pending" button of REQ-LIBRARY-175 (mapping to status `pending_review`), a spacer, then "Edit" and "Delete". With no selection all are disabled; the button matching the selected proposal's current status is disabled (the current status cannot be re-applied); Edit and Delete require a selection. Activating a status button requests that status change for the selected proposal and its owning artifact.

**REQ-LIBRARY-111** — Proposal-table refresh MUST preserve the selection by proposal id across rebuilds; if the previously selected row disappeared, the first row is selected; the detail label and button states are recomputed after every rebuild.

**REQ-LIBRARY-112** — A deep-link focus on a specific proposal id MUST select and scroll to that row when present.

**REQ-LIBRARY-113** — The proposal editor dialog MUST be modal, titled "Edit improvement proposal", minimum width 480 px, with a "Summary" single-line field (accessible name "Proposal summary") and a "Recommended action" multi-line field fixed at 90 px height (accessible name "Proposal recommended action"), a validation label in the theme's failure color, and buttons Cancel plus primary "Save changes". Validation runs on every keystroke — "Summary cannot be empty." then "Recommended action cannot be empty." — with Save disabled while invalid; accepted values are whitespace-trimmed. Double-clicking a proposal row also opens the editor.

**REQ-LIBRARY-114** — Activating Delete MUST request deletion of the selected proposal from its owning artifact (confirmation handled per REQ-LIBRARY-118).

**REQ-LIBRARY-166** — The Proposals tab MUST also list the workspace's improvement artifacts themselves, so a user can see and act on artifacts and not only on the flattened proposal rows of REQ-LIBRARY-120. The list MUST be a table (accessible name "Improvement artifacts") ordered newest first by `generated_at`, one row per artifact, each row carrying the artifact id, its `generated_at` rendered as a local date and time to whole-second precision, whether the artifact has a rollback point per REQ-LIBRARY-012 stated in words rather than by colour alone, and its proposal counts per status in the order `pending_review`, `approved`, `rejected`, `deferred` declared by REQ-LIBRARY-007, omitting a status whose count is zero and stating in words that the artifact holds no proposals when none of the four is present. Selecting a row MUST filter the proposals table of REQ-LIBRARY-109 to that artifact's proposals; a selection cleared MUST return it to every artifact's proposals. A workspace holding no improvement artifacts MUST show an empty label saying so, and a listing failure MUST degrade to an empty list and report the failure per REQ-LIBRARY-173 rather than leaving the tab blank without explanation. The search field of REQ-LIBRARY-103 MUST match an artifact row on its artifact id.

**REQ-LIBRARY-167** — Selecting an improvement artifact in the list of REQ-LIBRARY-166 MUST show that artifact's detail without leaving the Library. The detail MUST convey: the artifact id; its `generated_at`; the id of the session it was produced from (`source_session_id`); its proposal counts per status as defined in REQ-LIBRARY-166; whether a rollback point exists and, when one does, which recorded checkpoint it is, identified by its Git reference and by its commit abbreviated to 12 characters; and, only when `rolled_back_at` is set, that the artifact has already been rolled back and when. It MUST list the artifact's proposals in stored order with their id, status, risk, and summary. It MUST carry the "Roll back" action of REQ-LIBRARY-169 and the "Start improvement run" action of REQ-LIBRARY-172. Requesting the detail of an artifact id that is absent from the workspace MUST report that absence to the user and change nothing. All wording here is left to the implementation.

**REQ-LIBRARY-168** — The recorded version history of an improvement artifact (REQ-LIBRARY-049 through REQ-LIBRARY-054) MUST be readable from the artifact detail of REQ-LIBRARY-167, so the audit trail the write path keeps is reachable by a user and not only by a program. The history MUST be listed newest first, one row per retained version, each row carrying the version number, the time it was recorded, and its cause from the vocabulary of REQ-LIBRARY-050. Every artifact has at least one recorded version (REQ-LIBRARY-051), so the history is never empty. Selecting a version MUST show the `summary` and `recommended_action` each proposal carried in that version (REQ-LIBRARY-162), read-only: this surface inspects history and MUST NOT write to the store, MUST NOT restore a version, and MUST NOT alter the current artifact. A recorded version that could not be read MUST be skipped and its absence stated, per REQ-LIBRARY-053, rather than failing the listing.

**REQ-LIBRARY-176** — **The improvement store exports.** A workspace's improvement artifacts MUST be obtainable as a file the user chooses, in a form that yields every field of every artifact, every proposal and every retained version to a stock parser on a machine with none of this product's code present. That guarantee is REQ-EVENTS-166's and is not restated in a second form here; this requirement applies it to the improvement store on the same terms REQ-SESSION-199 applies it to the timeline, the issues record, the metrics document and the permission audit. The export MUST be offered both for a single artifact and for every artifact of the workspace, MUST be reachable from the artifact detail of REQ-LIBRARY-167 and from the artifact list of REQ-LIBRARY-166, and MUST be available whether or not any session is live, because artifacts are workspace-scoped and outlive the session that produced them (REQ-LIBRARY-042).

What it MUST carry is the artifact container's fields (REQ-LIBRARY-011), each proposal's fields including its evidence entries (REQ-LIBRARY-008, REQ-LIBRARY-010) in stored order, and **the recorded version history REQ-LIBRARY-168 calls "the audit trail the write path keeps"** — every retained version with its `version`, its `recorded_at`, its cause from the closed vocabulary of REQ-LIBRARY-050, and the state that version holds, so the `summary` and `recommended_action` each proposal carried at each recorded decision point leave the machine with the artifact rather than being readable only on screen (REQ-LIBRARY-049, REQ-LIBRARY-162). **The history exports as an audit**: every retained version in the order the versions were recorded, none omitted, and — where retention has dropped intermediate versions (REQ-LIBRARY-052) — a statement that it has and how many, so a pruned history can never be mistaken for a complete one. REQ-LIBRARY-052 is what obliges the store to retain enough to say so; that obligation is stated there and is not restated here. A recorded version that cannot be read MUST be reported as skipped rather than dropped without trace, which is what REQ-LIBRARY-053 already requires of the listing.

That statement accounts for pruning and for nothing else. REQ-LIBRARY-047 makes recording a version best-effort and places it **outside** the artifact write's all-or-nothing boundary, so a version can also be absent because it was **never recorded** — a different thing from a pruned one, and one the user was told about only in the application log. **The export MUST tell the two apart.** It MUST carry, for each artifact, **two separate figures** — how many versions retention dropped (REQ-LIBRARY-052) and how many were never recorded (REQ-LIBRARY-047) — each identified by which of the two it is. It MUST NOT merge them into one figure for absent versions, MUST NOT state either without saying which it is, and MUST NOT carry either in a shape shared with the export of a store whose absences have only one cause (REQ-TRACE-514), because a shape that fits both erases the distinction. Where neither has occurred each figure MUST still be stated, as zero, so that a complete history says so and silence never has to be interpreted. The two mean different things to a user reading an audit trail — a pruned version is the record working as designed, a never-recorded one is a gap in the record — and an export that presented them alike would report a defect as a policy, or a policy as a defect. Neither obligation to retain enough to state a figure is this requirement's: they are REQ-LIBRARY-052's and REQ-LIBRARY-047's, stated there and not restated here. What this requirement adds is that the export MUST NOT convey, by its wording or by its shape, that the versions it carries together with those two figures are every version this artifact's mutations should have produced, since neither figure is a reconstruction of what a missing version held.

Exporting MUST write nothing to the store, MUST NOT create, restore or repair a version, and MUST NOT alter the current artifact — the same read-only discipline REQ-LIBRARY-168 places on the history surface. **It is not a channel**: it is a user-initiated action producing a file at the moment it is asked for, it MUST NOT refresh itself, and no surface may be built on repeating it. A workspace holding no artifacts, or an artifact holding no proposals or no readable version, MUST export an empty record of that kind rather than nothing at all, so that absence is distinguishable from failure. **The destination is the one write this domain makes whose target the product does not choose**, and it may be anywhere the user's save dialog reaches — removable media, storage shared with another machine, a folder a synchronisation client replicates, or a directory the user has the previous export open in. Where the file the user chose already exists, replacing it MUST take the retry ladder REQ-TRACE-061 states for a replacement onto storage this product does not choose; that requirement states the ladder and it is not restated here. **This domain states no replacement ladder of its own.** REQ-LIBRARY-043's was withdrawn with the document layout it governed, and the reason it gave — that no writer outside this application can reach a record **in the store** (REQ-LIBRARY-158) — does not reach a destination outside the store that the user named, so it is cited here as inapplicable rather than reinstated. A failure MUST be reported per REQ-LIBRARY-173 and MUST leave the store exactly as it stands.

**Why it exists and where its boundary is.** Improvement artifacts were material a user could open and read for themselves before they became records the application keeps (REQ-LIBRARY-042); without an export, moving them into that store would be a straight reduction in what a user owns about their own runs. A record gains an export when it carries no unredacted user or tool content, and the improvement store qualifies because what it holds is the analyst's own proposals and the evidence entries backing them, written to be reviewed. The export MUST therefore carry the artifact exactly as stored, adding nothing to it and reaching nothing it does not already hold: in particular it MUST NOT resolve an evidence entry's `source_session_id`, `source_artifact_id` or `source_task_id` into the material those ids name, because a session's tool-call evidence deliberately holds unredacted arguments and never gains an export of its own (REQ-SESSION-136). An export that followed those ids would become the export that record is denied.

**REQ-LIBRARY-174** — Improvement proposals MUST always be reachable from the desktop interface without depending on any notification having been seen. The window's action vocabulary MUST carry an entry labelled "Improvement proposals", described as reviewing post-run improvement proposals, presented on the terms REQ-SHELL-048 fixes — in the command palette, in keyboard help if it is given a shortcut, and in the composer's slash catalogue. Activating it MUST open the Library on the proposals tab (REQ-LIBRARY-103) with the workspace's newest improvement artifact selected in the list of REQ-LIBRARY-166. A proposal that a missed, dismissed, or never-shown notice failed to announce is therefore still reachable. With no workspace artifacts, the tab MUST open and state that no improvement artifacts exist yet and that finishing a task run produces them; with no active session the entry MUST still open the tab rather than refuse, because artifacts are workspace-scoped and outlive the session that produced them (REQ-LIBRARY-042). A failure to list or load artifacts MUST be reported per REQ-LIBRARY-173. The wording of these states is left to the implementation.

**REQ-LIBRARY-175** — The proposals action row of REQ-LIBRARY-110 MUST offer a fourth review decision, "Reset to pending", mapping to status `pending_review`, so a decision recorded by mistake can be returned to the undecided state at any time and not only through the Undo offered immediately after it (REQ-LIBRARY-116). It obeys exactly the rules the other three status buttons obey: it is disabled with no selection, it is disabled when the selected proposal is already `pending_review`, and activating it goes through the confirmation, persistence, notification, and undo path of REQ-LIBRARY-115. The dashboard card's inline actions (REQ-LIBRARY-129) MUST offer it on the same terms.

### 15. Desktop review-action handling

**REQ-LIBRARY-115** — Applying a status from the desktop MUST first ask for confirmation in a dialog titled `Approve proposal?`, `Reject proposal?`, `Defer proposal?`, or `Reset proposal to pending review?` according to the action button of REQ-LIBRARY-110. The body MUST contain the proposal's summary, the line `Category: <category with underscores replaced by spaces>`, and the sentence "This records a review decision; it does not execute workspace changes." The choices are Yes and Cancel with Cancel selected by default, and choosing Cancel MUST change nothing in the store and nothing on screen. On confirmation the new status is written to the owning artifact and the workspace's artifacts are re-read so the change is reflected everywhere. A failure MUST notify `Could not update proposal: <err>` and leave the displayed status as it was. Success MUST post a persistent success notice titled `Proposal marked <status with underscores replaced by spaces>`, carrying the proposal summary as its message and offering an "Undo" action (REQ-LIBRARY-116).

**REQ-LIBRARY-116** — Activating Undo MUST re-apply the proposal's previous status without asking for confirmation, and the undo MUST itself leave a recorded history version of cause `status_change` (REQ-LIBRARY-162), so the record shows both the decision and its reversal rather than erasing the decision. Undo MUST always read the stored artifact first and act on what it finds there, never on the state the notice was posted from, and MUST NOT create, restore, or repair anything. Given a proposal or an artifact that no longer exists, Undo MUST write nothing and MUST report that the proposal it would have reverted is gone. Given a proposal whose status was changed again from another surface after the decision the notice announced, Undo MUST write nothing and MUST report that the proposal has since changed and name the status it now holds, leaving the user to decide again; it MUST NOT overwrite the newer decision. In both cases the notice's Undo action is spent and MUST NOT be offered again, and the proposal surfaces MUST re-read the stored state. The wording of those reports is left to the implementation.

**REQ-LIBRARY-117** — A successful edit notifies "Proposal updated."; edit failures (missing proposal, I/O errors, validation errors) notify `Could not update proposal: <err>`.

**REQ-LIBRARY-118** — Deletion MUST always be confirmed first with a dialog "Delete proposal?" whose body contains the summary plus "This permanently removes the proposal. This cannot be undone." (Yes/Cancel, default Cancel). Success notifies "Proposal deleted."; failure notifies `Could not delete proposal: <err>`.

**REQ-LIBRARY-119** — In demo mode (no live configuration backend), all three proposal actions MUST refuse with the error notification "Proposal actions are unavailable in demo mode.", and opening an artifact editor MUST refuse with "Artifacts are read-only in demo mode."

**REQ-LIBRARY-120** — The desktop proposal list MUST flatten every workspace artifact's proposals (all artifacts × all proposals) into display rows carrying `{id, artifact id, category, summary, recommended action, risk, status, created label}`; a listing I/O failure degrades to an empty list. The created label is relative: `now` (< 60 s), `<n>m` (< 1 h), `<n>h` (< 24 h), else `<n>d`.

**REQ-LIBRARY-121** — Refreshing with unchanged proposal data MUST be a no-op: no change event fires and no visible rebuild occurs.

**REQ-LIBRARY-172** — Starting an improvement run over an artifact's approved proposals MUST be reachable from the desktop interface, and from nowhere else. The improvement-artifact detail of REQ-LIBRARY-167 MUST carry a "Start improvement run" action. Given an artifact with no proposal in status `approved`, activating it MUST start nothing and MUST tell the user that nothing is approved, leaving the Library as it was — this is the same condition the plan builder refuses on (REQ-LIBRARY-060). Given at least one approved proposal, activating it MUST prepare the run per REQ-LIBRARY-064, including the pre-run rollback checkpoint, and start a run of type `improvement_run` over exactly those proposals and nothing else. A start that fails MUST leave the Library as it was and report the failure and its reason. A start that succeeds MUST report how many proposals the run will apply and MUST make the run observable on the desktop exactly as any other run is. The wording of these reports is left to the implementation.

**REQ-LIBRARY-173** — Because several surfaces and several runs of the one instance mutate the same store (REQ-LIBRARY-042, REQ-LIBRARY-158, REQ-LIBRARY-164), every desktop review action MUST cope with the stored state having moved underneath it, and MUST say so rather than fail silently. Given an action whose target proposal or artifact is no longer present in the store, the action MUST write nothing, MUST re-read the workspace's artifacts so the surfaces show what is actually stored, and MUST post a warning naming the proposal that no longer exists. Given a persistence failure while recording a decision, an edit, or a deletion, the action MUST post an error carrying the underlying reason and MUST leave the displayed state as it was (REQ-LIBRARY-115, REQ-LIBRARY-117, REQ-LIBRARY-118), the store being unchanged by a failed save (REQ-LIBRARY-047). Given a listing or loading failure, the affected surface MUST degrade to showing nothing rather than stale content and MUST post an error carrying the reason. No failure in this requirement may be reported by silence. The wording of these notices is left to the implementation.
