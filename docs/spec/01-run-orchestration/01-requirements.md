# Multi-Agent Run Orchestration — 1. Run Entry and Session Setup

Part 1 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-001 – REQ-ORCH-027.

## Requirements

### 1. Run Entry and Session Setup

- **REQ-ORCH-001** — *Withdrawn.* The requirement fixed parity between a background command-line host and an interactive terminal-UI host, neither of which this product has; the capability it protected — a run reaching the same outcome however it is watched — is carried by REQ-ORCH-150.
- **REQ-ORCH-002** — The top-level user task MUST be given to a single configurable entry role (default role name `orchestrator`). This entry role is an ordinary configurable role whose orchestration authority derives entirely from its instructions and granted tool set; each iteration of the outer loop starts it fresh as that iteration's root agent.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** An iteration resumed after a pause, a stop, a quit or a crash restores its entry agent from its recorded conversation rather than starting it fresh.
- **REQ-ORCH-003** — The user's original request text MUST be captured at run start, before any later modification of the work plan, and MUST remain available unchanged as the anchor for intent evaluation and end-of-run fulfillment auditing.
- **REQ-ORCH-004** — Given a fresh session, when a run starts, a new todo list MUST be created with a single initial phase (named "main") containing the task. Given a resumed session, the new top-level task MUST be appended to the session's existing todo state. The execution payload handed to the root agent MUST carry the conversation context in effect, the artifacts recorded for the session, the todo state as it currently stands, and the progress accumulated before this run.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 4, 2026-09-28.** Clause 17: a
  > continue that resumes an open iteration appends its message as a task that closes with the resumed iteration —
  > done when it succeeds, pending when it is cancelled or fails. Every other new top-level task is appended as
  > stated.
  > Revision 6 (2026-10-06), clause 25: a continue that states no new request — the Continue action, "continue without
  > them", the message-limit resolution's 'continue' and 'double' — appends no task while the todo holds its last
  > request's task pending or held by the open iteration.
- **REQ-ORCH-150** — Given the same task, the same configuration, and the same run options, a run MUST reach the same orchestration outcome — the same intent handling, the same delegation and iteration rules, the same verification gating, the same stop reason, and the same terminal status — whether its view is attached in the desktop interface for the whole run, attached for part of it, or never opened at all. Attaching a view, detaching it, closing the window, and switching to another view (REQ-SHELL-023) MUST change only what the user is shown and MUST NOT change what the run does, what it records, or when it stops. Exactly one behavior is permitted to differ with attachment: how a message-limit pause is surfaced and resolved — with a view attached the run presents the dialog of REQ-ORCH-086, and with none attached it takes the detached path of REQ-ORCH-087. Every run option this domain defines, the run override of REQ-ORCH-025 included, is chosen in the desktop interface and is available to every run alike.
- **REQ-ORCH-151** — The application MAY have more than one run in flight at once, in the same workspace or in different ones, and every run MUST be isolated from every other. Each run's iteration ledger, child records, task ids, canonical-name scope, message counter, consecutive-retry counters, repair budgets, loop-supervisor state (REQ-ORCH-105), artifact store (REQ-ORCH-149), session snapshot, and session diagnostics MUST be scoped to its own session id and MUST never be read or written by another run. A run's stop reason, terminal status, and the sequence of states each of its children passes through MUST NOT depend on how many other runs are in flight, or on the order in which concurrent runs interleave. The per-model concurrency cap of REQ-ORCH-050 is likewise scoped to one run, so a run can never be starved of model slots by another run; contention for a provider across concurrent runs is handled by the rate-limit and quota rules of REQ-ORCH-091 instead.
- **REQ-ORCH-152** — A run-start mode MUST be settable to exactly one of `auto` or `plan`, defaulting to `auto`. The setting is persistent — it outlives the run that used it and governs the next run started in the same workspace until the user changes it — and is offered both where a run is started in the desktop interface and in the settings interface. In `auto` mode no gate applies and the run proceeds exactly as the rest of this document describes. In `plan` mode the gate of REQ-ORCH-153 applies.

  > **Narrowed by [`PD-ORCH-003`](../../product/directives/pd-orch-003.md#pd-orch-003), 2026-09-17.** The setting, its two
  > values, its default, its persistence and both surfaces that offer it are untouched. The directive names
  > one case in which the mode does not govern the next run started in the same workspace: a session that
  > already holds an approval taken at REQ-ORCH-153's gate, whose release now lasts for the session rather
  > than for the one run that received it. Such a session is re-armed by starting a new session, or by the
  > user choosing `plan` again on the run-start control, and by nothing else.
  > Revision 2 (2026-09-28): a continue that resumes an iteration a rest left open runs that iteration unheld, and a
  > gate that would hold the run holds before its first new iteration.
  > Revision 3 (2026-10-06): so does one a crash left open, once the crash is recorded; and choosing `plan` in the
  > Settings Runtime category re-arms no session, the run-start control being the composer's chip.
- **REQ-ORCH-153** — In `plan` mode, and where the classified intent is not a member of the answer group of REQ-ORCH-021 (`question`, `exploration`), the run MUST produce a plan and MUST block before any file-modifying work is done. The block is a property of the run and not of any one role, and it withholds capability rather than preventing the run from starting: the run's root execution record is created with the entry role exactly as REQ-ORCH-072 requires of every iteration of every run. While the gate is held, every agent of the run — the entry role included — MUST hold **planning grants**: the tool set it would otherwise hold, less every tool the public tool-name registry declares as writing workspace files or running commands (REQ-TOOLS-001), with a tool the registry carries no declaration for counting as declaring all three. That withholding MUST be enforced where a call is dispatched, so such a call is refused whichever role issues it and by whatever route the tool reached that role. While the gate is held the run MUST NOT spawn a child whose role holds such a tool, MUST NOT run a hook command (REQ-HOOKS-126), and MUST NOT run a check suite. A run taken under a `single` override is neither exempted from the gate nor prevented from starting by it: its entry role is granted the direct-work bundle by REQ-ORCH-025, and while the gate is held that bundle is narrowed by this requirement exactly as every other role's set is. Approval MUST install the run's execution grants for the remainder of the run — from that point every agent holds the set it would have held with no gate in force. What this requirement blocks is the work the run's agents do and never the product's own recording: the session, the plan, the todo state, the run's events and every other application-owned record MUST remain writable throughout, and no refusal under this requirement is a refusal to record. The plan MUST be presented verbatim as the producing role wrote it — never summarized, truncated, or re-rendered into another form — together with the classified intent and the todo state the plan implies. The run MUST wait indefinitely for an explicit answer and MUST NOT proceed on a timeout, on the view being closed, or on any default. The answers offered MUST be exactly three: approve, which releases execution; revise, which starts another plan cycle under REQ-ORCH-154; and cancel, which stops the run with stop reason `user_cancelled`. While the run is blocked at the gate its session execution status MUST be `awaiting_plan_decision`, and the pending decision MUST survive a restart of the application in the same way a message-limit pause does (REQ-ORCH-087). The hold is not a termination: it MUST raise no terminal run status and no terminal result, and the run the user approves, revises or cancels is the run that reached the gate (REQ-ORCH-154), whether or not the process that hosted it outlived the hold.

  > **Superseded by [`PD-ORCH-002`](../../product/directives/pd-orch-002.md#pd-orch-002), 2026-09-16; revision 2,
  > 2026-09-17.** The presentation clause — verbatim monospace without re-rendering — is superseded: the
  > plan is presented formatted as rendered Markdown by default, with an immediate toggle to edit source in
  > a monospace field. Implied tasks are deduplicated and revision feedback is disclosed progressively. Under
  > revision 2 the gate expanded takes the whole reading area with no transcript drawn beneath it, and
  > collapsed is a bar above the transcript; the three answers of this requirement are offered in **both**
  > states. All gating, capability withholding, and three-answer decision mechanics remain fully governed by
  > this requirement. Revision 3 (2026-10-07): every part of the expanded gate but the plan is bounded below the
  > plan's floor, a later cycle's 'You asked for' line capped and scrolling as the implied todo is; a revision field
  > the user drags taller keeps that height; a gate shorter than its parts scrolls with its three answers pinned.
- **REQ-ORCH-154** — A plan awaiting a decision MUST be directly editable by the user, and the edited text is the plan the run carries out; editing alone never approves it. Choosing revise MUST start a further plan cycle in which the producing role is given the plan as it currently stands together with the changes the user stated, and MUST yield a fresh plan for the same three-way decision; this document places no limit on how many such cycles a user may run. Approval is one-way for the run that received it: once execution has been released the run MUST NOT return to the gate, a plan produced later in the same run MUST NOT block execution, and a change to the mode setting made while a run is in flight takes effect only for the next run. Every plan cycle, the decision taken, and the text that was approved MUST be recorded in the session's durable record, with a `plan_gate_opened` timeline event when the gate blocks and a `plan_gate_resolved` timeline event naming the answer when it releases.

  > **Narrowed by [`PD-ORCH-002`](../../product/directives/pd-orch-002.md#pd-orch-002), 2026-09-16.** Directly editable
  > source text remains available via the "Edit source" view of the plan gate, while formatted Markdown
  > serves as the default inspection view. The revision changes field is disclosed progressively.


### 2. Pre-Flight Intent Classification

- **REQ-ORCH-005** — Intent classification MUST complete before the coordinator is initialized, and the classified intent MUST be in effect before the first iteration so that intent-dependent behavior (capability gating, playbook cells, budget clamps, route-aware guards) applies from iteration 1.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 7, 2026-10-06.** Clause 40: the
  > Continue action and a message-limit resolution make no classification call and carry the intent in effect; an
  > iteration a continue resumes runs under the intent it started with, so a continue by message's classification is
  > in effect from the run's next iteration rather than its first. Every other run classifies as stated.
- **REQ-ORCH-006** — The intent taxonomy MUST consist of exactly these 13 categories: `explicit_trivial`, `question`, `exploration`, `problem_resolution`, `single_file_change`, `small_feature`, `moderate_feature`, `large_feature`, `refactor`, `architectural`, `requirements`, `whole_project`, `ambiguous`. Category semantics MUST include: `problem_resolution` means diagnose AND fix; `exploration` means investigate only; when several categories are plausible the tie-break prefers `moderate_feature`.
  > **Narrowed by [`PD-ORCH-011`](../../product/directives/pd-orch-011.md#pd-orch-011), 2026-10-06.** `explicit_trivial` means an
  > explicitly stated, trivial edit; a request that changes nothing belongs to the answer group. The tie-break chooses
  > among the categories that are plausible, preferring `moderate_feature` only where it is one of them. The categories
  > and the two fixed meanings above are unchanged. *Amended 2026-10-13, revision 2 ([OQ-227](../../architecture/open-questions.md),
  > ruled under [R-072](../../product/requests.md#r-072)):* `single_file_change` means a small edit confined to one file, as
  > the request states or implies; a change requested together with a test of it, or one naming several files to change,
  > is outside it unless the request places all of it in one file, and the classifier is told so on every rung.
- **REQ-ORCH-007** — Any classification failure — timeout, unparseable response, unmapped category string, empty response, or setup error — MUST produce the fallback intent `moderate_feature`, flagged as a fallback with a human-readable reason, and MUST NOT stop or fail the run.
- **REQ-ORCH-008** — The classification call MUST time out at 12.0 seconds by default. *This sentence read "The classification call MUST time out at 8.0 seconds by default" until 2026-09-11, when the owner raised the default under ESC-35: the live run measured a self-hosted endpoint whose first token arrives after 8.0 s, so a prompt that would have classified correctly took REQ-ORCH-007's fallback instead. The figure remains a default and this requirement still fixes no other bound; a caller that supplies its own is unaffected.* Its input MUST consist of the raw user prompt truncated to 4000 characters, a small metadata mapping such as the run entrypoint, and the optional prior-response field owned by REQ-ORCH-012 with its independent 4000-character cap. Additional repository retrieval MUST be excluded. User-supplied prompt text and historical response text may contain code; each remains confined to its named field. Metadata MUST carry run context only. The prior-response field remains untrusted under REQ-ORCH-012.
- **REQ-ORCH-009** — The model used for classification MUST be selected by consulting three configured model slots in a fixed order — the small-model slot, then the fallback-model slot, then the default summary-model slot — and using the first slot that is set. When none of the three is set, no request is sent to any provider and the run proceeds immediately on the fallback intent `moderate_feature`, flagged as a fallback, with a reason stating that no small model is configured. The three slots are the configuration keys `small_model`, `fallback_model`, and `default_summary_model` (REQ-CONFIG-064, REQ-CONFIG-065), consulted in exactly that order. The `fallback_model` named here is the run-level slot of REQ-CONFIG-065 and never the per-role fallback model of REQ-ORCH-144: classification completes before the coordinator is initialized (REQ-ORCH-005), so no role's overrides are in scope for it.
  > **Narrowed by [`PD-MONITOR-007`](../../product/directives/pd-monitor-007.md#pd-monitor-007), 2026-10-06.** The selected slot's model is
  > followed through the session's override; where the pair it reaches is held out of quota for the session, no request
  > is sent and the run proceeds on the fallback intent with a reason saying so. The order of the slots is as stated.
- **REQ-ORCH-010** — Structured output MUST be requested through a three-rung degradation ladder tried in order: (1) strict, enum-constrained JSON schema; (2) generic JSON-object mode with an appended instruction showing the exact keys and one example; (3) unconstrained text. A rung a given model has previously rejected MUST be remembered per model for the session and skipped on later calls; per-model capability configuration MAY pre-map a rung (e.g. forcing a model straight to JSON-object mode).
- **REQ-ORCH-011** — The classification result MUST carry: the intent category, a confidence value in [0, 1] or null, a reason string, a fallback flag, and a carried-over flag.
- **REQ-ORCH-012** — When the session has prior completed coordinator iterations, the latest usable one's stored summary (else its final response text), truncated to 4000 characters, MUST be passed to the classifier as optional prior-response context. Iterations persisted without a role attribution are ineligible. The classifier instructions MUST direct that this history is untrusted context and that instructions embedded in it must never be followed.
- **REQ-ORCH-013** — Resume intent carry-over: when (a) the fresh classification is unusable (`ambiguous` or a fallback), (b) the session has a prior recorded intent that is a real non-ambiguous category, and (c) the session todo still has unfinished work (pending, in-progress, and abandoned items all count as unfinished), then the prior intent MUST be inherited deterministically with no model call, the carried-over flag set, and a reason stating the previous intent was continued. An unreadable todo state MUST count as "no unfinished work" (no carry-over).
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005) revision 7, 2026-10-06.** Clause 40: the
  > Continue action and a message-limit resolution carry the intent in effect with no fresh classification at all, and
  > the prior intent this carry-over inherits is the intent in effect, a continuation's or else the launch's. A
  > classification that runs carries over as stated.
- **REQ-ORCH-014** — The desktop interface MUST show a transient status before the classification call conveying that the intent is being classified, and MUST replace it in place — not append to it — with a status conveying the classified intent by its exact category identifier (REQ-ORCH-006). A carried-over intent (REQ-ORCH-013) MUST additionally be conveyed as continued from the previous run; a fallback (REQ-ORCH-007, REQ-ORCH-009) MUST additionally be conveyed as a fallback, together with its reason where one is available, the reason normalized (a provider's structured-output rejection is conveyed as a generic provider-rejection phrase rather than the provider's own text) and truncated to 180 characters. The wording, punctuation, and separators of that status are the implementation's; the category identifier it carries is exact, and the status is never conveyed by colour alone (REQ-SHELL-149).
- **REQ-ORCH-015** — The classified intent MUST be propagated to the child-execution layer so that completion guards are route-aware: a run classified as answer-only (question/exploration) MUST NOT fail a child for producing no file edits.

### 3. Intent-Based Capability Gating

- **REQ-ORCH-016** — A user-inspectable intent-to-tools mapping MUST gate the entry role's tool set. Exactly the two simplest intents (`explicit_trivial`, `single_file_change`) grant the entry role the direct-work bundle; every other intent applies no mapping entry, leaving the role's configured coordination-only restrictions in force. A `single` run override (REQ-ORCH-025) grants the direct-work bundle whatever the classified intent is, and is the only input to this mapping besides the intent itself; a `swarm` override is not an input to it. The direct-work bundle MUST be defined by capability and not by a literal list of tool names: it is todo management and delegation, the search, fetch, and artifact-read capabilities, and every tool the public tool-name registry declares as reading workspace files, writing workspace files, or running commands (REQ-TOOLS-001). Resolving the bundle against the registry's own per-tool declarations means a tool added to that registry later joins the bundle, or stays out of it, by its own declaration and with no amendment here. Under a `single` override the `delegate` tool is withheld notwithstanding this bundle, per REQ-ORCH-025. While a run is held at the plan gate the bundle is narrowed by REQ-ORCH-153 for as long as it is held; that narrowing only removes tools and never adds one, and approval restores the bundle this requirement grants.
- **REQ-ORCH-017** — Mapping errors MUST fail safe: an unknown intent key, a malformed tool list, or an unreadable mapping file results in no tool restriction being applied, with a logged warning. Obsolete instruction-text entries in the mapping MUST be rejected.
- **REQ-ORCH-018** — The intent tool gate MUST apply only to the configured entry role; other roles' tool sets are unaffected by intent.

### 4. Behavior Playbook Matrix

- **REQ-ORCH-019** — Per-intent behavior MUST be drawn from a playbook matrix whose row is selected by three keys — role, classified intent, and model tier — and which the user can override per REQ-ORCH-026. The playbook rendered for a role MUST form part of the instructions that role is given, for every role that has a matching row and not only for the coordinator; a role with no matching row is given no playbook text at all (REQ-ORCH-023). The cell selected for the run MUST be recorded per REQ-ORCH-027, so which row was in force is verifiable after the run. The model-tier vocabulary is exactly `small`, `medium`, and `large`, ordered small < medium < large, together with the wildcard `any`, which matches every tier when it appears in a matrix key and is never itself a role's tier. A model's tier is the tier alias it resolves through (REQ-CONFIG-070, REQ-CONFIG-071), and a role's tier is that of the model it is configured on.
- **REQ-ORCH-020** — A rendered playbook MUST contain all eight slots, each exactly once, in this order: ROUTE, AUTONOMY, RESEARCH, CHUNKING, VERIFY, ARTIFACT, OUTPUT, BUDGET. Where one role produces output that a different role will carry out (for example a plan written for an implementer), the CHUNKING and OUTPUT slots MUST be taken from the tier of the role that will carry the work out, and only when that tier is lower than the producing role's own; this substitution MUST never move a slot to a higher tier. "Lower" is decided by the small < medium < large ordering of REQ-ORCH-019. The producer-to-consumer pairings are exactly two: `planner` and `architect` each produce for the role that will carry the work out, identified by the same mapping REQ-ORCH-022 uses (refactor work → `refactorer`, requirements work → `requirements-engineer`, architectural work → `architect`, `coding-agent` otherwise). No other pairing exists, so no other role's CHUNKING or OUTPUT slot is ever substituted.
- **REQ-ORCH-021** — Intents MUST resolve through groups: answer = {question, exploration}; clarify = {ambiguous, requirements}; micro = {explicit_trivial, single_file_change}; fix = {problem_resolution, refactor}; small-build = {small_feature}; medium-build = {moderate_feature}; large-build = {large_feature, architectural, whole_project}. Lookup order is: concrete intent → its group → a default row. Tier lookup is: concrete tier → an all-tiers wildcard.
- **REQ-ORCH-022** — The coordinator's playbook row MUST be keyed on the model tier of whichever role will actually carry out the work, not on the coordinator's own tier: refactor work → the refactoring role (`refactorer`), requirements work → `requirements-engineer`, architectural work → `architect`, and `coding-agent` in every other case. As a consequence, whether a planning step comes first depends on that role's tier: when it sits on the largest tier it scopes its own work, so mid-size features and restructuring work do not compel a separate planning step.
- **REQ-ORCH-023** — When a tier cannot be resolved, the medium tier MUST be used and the rendered playbook header MUST state that the model size is undetermined and larger capacity must not be assumed. A role with no matrix row receives no playbook. A cell marked as not routed renders text instructing the role to treat its assignment as narrow because it is outside the standard flow.
- **REQ-ORCH-024** — The BUDGET slot MUST be enforced, not advisory: the resolved cell's budget clamps the runtime child-limit policy for that iteration — tight = {max active children 2, max total children 6, max depth 2}; normal = {4, 12, 3}; wide = no clamp. Clamps only narrow (a tighter configured limit always wins), and any budget-resolution failure falls back to the configured policy unchanged.
- **REQ-ORCH-025** — A user-selected run override MUST be supported as a final layer, chosen in the desktop interface where the run is started, placed after everything else and taking precedence over the matrix cell. There are exactly two. A `swarm` override demands maximum parallel delegation (overlapping ownership of the same work slice remains forbidden); it changes instruction text only, and the entry role keeps its coordinating status and its coordination-only tool set. A `single` override declares that the entry role will complete the task itself, and MUST take effect as a capability change rather than as advice: for that run the entry role does not act as coordinator, so the constraints of REQ-ORCH-029 — which bind it only while it does — do not apply; it is granted the direct-work bundle of REQ-ORCH-016 whatever the classified intent is; and the `delegate` tool MUST be withheld from every role for the whole run, so the demand not to delegate is enforced structurally and no delegated child is ever spawned. The run's own root execution record is not a delegated child and is unaffected by that withholding: REQ-ORCH-072 creates one for each iteration of every run, a `single` run included, so a `single` run is exactly one root execution record per iteration and zero delegated children. A `single` override is valid at every intent, is never narrowed to the two simplest ones, and is never downgraded to guidance the role may disregard.
  > **Narrowed by [`PD-ORCH-006`](../../product/directives/pd-orch-006.md#pd-orch-006) (revision 3), 2026-10-07.** Where the intent-to-tools mapping in force, built-in or a user's file, grants the entry role the direct-work bundle, a `swarm` override changes nothing that run holds or is told: it keeps the bundle with `delegate` in it and is given the directive's direct-work statement and no `swarm` text on any turn, so the coordination-only tool set and the demand for maximum parallel delegation above do not reach it. On every other run the `swarm` sentence governs as written.
- **REQ-ORCH-026** — Playbook content MUST be overridable at two scopes: a global user-configuration directory, and the workspace directory `<workspace>/.rotaris/playbooks/`. Where both scopes define the same field, the workspace value is the one that takes effect; fields the workspace leaves undefined keep their global value, and fields neither scope defines keep the built-in value. An override MAY supply different text for a slot variant the built-in catalogue already defines. An override MUST NOT introduce a slot name or a variant identifier that the catalogue does not define; such a name MUST be ignored, leaving the catalogued content in force, and MUST produce a warning naming it. So that the set an override may address is knowable without reading the product's source, the built-in catalogue MUST be user-inspectable: the settings interface MUST list every slot, every variant identifier defined for it, and the built-in text of each, and that listing is the definition of what an override may address. No variant text is fixed by this document — only the eight slot names of REQ-ORCH-020, the slot semantics, and the lookup rules of REQ-ORCH-021 — so an implementation authors the catalogue's text to those semantics. After an explicit reload, every subsequently rendered playbook MUST reflect the override files as they stand on disk at the time of the reload. The global scope is the per-user configuration directory of REQ-CONFIG-001, and the global-scope override directory is that directory's `playbooks/` subdirectory, mirroring the workspace-scope path.
- **REQ-ORCH-027** — The resolved playbook cell in effect for a run MUST be recorded as an audit payload in the session's run-configuration record (see Data & Formats).
