# Settings and Configuration

## Overview

The product is configured by optional YAML files kept in two directory scopes — a per-user global directory and a per-workspace `.rotaris/` directory — folded together with built-in defaults, auto-discovered third-party tool-server declarations, and a machine-written provider/model discovery snapshot into a single validated configuration on every load. Precedence is fixed and total, the overlay is at most one level deep, and lists never append. Absence of every configuration file is a normal state that loads on defaults alone, while a malformed primary file aborts the load with a message naming the file. The desktop settings screen edits a narrow, enumerable subset of these keys and writes them back atomically; a save is followed by an immediate reload so the change is observable without a restart, while every key outside that subset takes effect at the next load. The product is one desktop application: it is configured from that screen and from the two scopes' files, and from nowhere else — there is no command-line invocation, no flag, no subcommand and no text-mode surface through which a user configures or drives it. The settings screen distinguishes deferred edits (committed by an explicit Save, revertible by Discard) from immediately-committed preferences, and demands confirmation before changes that widen what an agent may reach.

## Requirements

### Configuration sources, scopes and locations

- **REQ-CONFIG-001** — Configuration is read from exactly two directory scopes: a per-user **global** scope and a per-workspace scope at `<workspace root>/.rotaris/`. The global scope resolves per platform to the conventional user configuration directory for the application name `rotaris` — on Linux `~/.config/rotaris/`, on macOS `~/Library/Application Support/rotaris/`, on Windows `%LOCALAPPDATA%\rotaris\rotaris\`. Which per-user location that is, on a platform offering more than one, is REQ-STARTUP-145's: the location local to this machine and not replicated to another machine or to another copy of the user's profile. The spellings above are that location on each platform rather than a second definition of it, and this domain states no rule of its own about it.
- **REQ-CONFIG-477** — Configuration MUST be held as files, and MUST NOT be moved into a store that only this application can read. This is a stated **boundary**, not an artifact of how the product was first built: it is recorded here so that moving configuration into an application-owned store is a change someone has to argue for against these grounds, rather than an optimisation that can be made quietly while every requirement of this document still appears to be satisfied. Four grounds reach the conclusion and each is independently sufficient.
  1. **A file carries what this release does not understand; a record with a fixed field set cannot.** An unrecognized top-level key is reported as a warning, contributes nothing to the merge, and is nevertheless still in the file afterwards, so a document authored against a later release loads, is edited, and is written back by an earlier one without losing the key (REQ-CONFIG-040, REQ-CONFIG-233); a key outside the layered model may additionally be read by a separate parse of the same file, `rotaris.delegation_strategy` being the shipped case. Every writer of `agents.yaml` is required not to discard content it could not interpret (REQ-CONFIG-442, REQ-CONFIG-458), and the file is what makes that possible. `requirements:` is the deliberate exception in the other direction — an unrecognized key there is a hard load failure, though a key this specification itself withdrew is reported and ignored instead (REQ-CONFIG-183) — and it is an exception about a *configuration block*, not a licence to store configuration the way the product stores its own records. That the withdrawn key survives in the file after being reported, and is removed only when its owner decides to remove it, is this ground doing its work rather than an exception to it.
  2. **The product shows the user the file's own contents, not a rendering of the merged result.** The advanced runtime card renders the chosen scope's **raw** `runtime:` mapping read directly from that scope's file rather than from the merged configuration, exactly so a user can tell a setting stated globally from one stated in this workspace from one inherited from the built-in defaults (REQ-CONFIG-471). That distinction is a distinction between two files, and there is nothing raw to render when there is no file. It is also a capability the product has already declined to lose once: when the surface that first carried it was withdrawn, the capability was deliberately re-sited rather than dropped (REQ-CONFIG-445).
  3. **Version control stays the user's choice.** These are the user's own text, in the user's own directories: diffable, mergeable, reviewable, copyable between machines, and quotable in a bug report. The product's own best-effort ignore rule keeps the workspace configuration directory out of version control unless the user decides otherwise (REQ-CONFIG-013, REQ-CONFIG-456), and *deciding otherwise* is a choice a file leaves open. A store the application keeps for itself forecloses it for every user at once.
  4. **Three of the five layers are not per workspace.** The fold is one fixed, total order over built-in defaults, auto-discovered tool servers, the global discovery snapshot, the global scope, and the workspace scope (REQ-CONFIG-031). The first three are not workspace-scoped at all, and the global scope is per user. A store scoped to one workspace could hold at most the last layer, so migrating configuration would put a single, fixed, total merge across two different storage models with different failure modes — at no gain, since the workspace layer is hand-edited exactly as the global one is.

  What this boundary covers is the configuration file set of REQ-CONFIG-003 through REQ-CONFIG-008 together with the persona, model-slot and section content those files carry. It says nothing about the operational records the product writes for itself, which are governed where they are defined — the requirement delivery store is the case in point (REQ-CONFIG-192).
- **REQ-CONFIG-002** — When a load is requested with no workspace named, the workspace root is the current working directory.
- **REQ-CONFIG-003** — `agents.yaml` is the primary configuration file and is read from both scopes. It is optional in each.
- **REQ-CONFIG-004** — `models.yml` is an optional secondary file read from both scopes. Only its top-level `models:` mapping is consumed; every other top-level key in it is ignored without warning or error.
- **REQ-CONFIG-005** — Within a single scope, that scope's `models.yml` entries overlay that scope's `agents.yaml` `models:` block per field. A global `models.yml` still loses to a workspace `agents.yaml` (REQ-CONFIG-031).
- **REQ-CONFIG-006** — `project_settings.yaml` is read from the **global scope only**. It is machine-written (the persisted result of provider sign-in plus model discovery) and is not intended for hand authoring.
- **REQ-CONFIG-007** — `secrets.yaml` may exist in either scope and supplies per-tool-server environment secrets. It is never committed to version control by the product (REQ-CONFIG-013).
- **REQ-CONFIG-008** — Third-party tool-server declarations reach the product by auto-discovery as well as by hand-authored configuration. Where that discovery looks — the project-level and user-level locations and their per-platform spellings — is fixed by REQ-MCP-017, and the shape of a discovered file, the keys it accepts and how it is parsed are fixed by REQ-MCP-018 through REQ-MCP-024 and REQ-MCP-027, which produce entries in the server-entry schema of REQ-MCP-001; this domain holds no copy of any of them and names no discovery location of its own. What this requirement records is only that discovery contributes to the configuration surface: whatever it yields enters the fold as its own layer, contributing `mcp_servers:` entries and nothing else (REQ-CONFIG-031, REQ-CONFIG-033), and each such entry is observable afterwards with the provenance that says it came from discovery rather than from a file in either scope (REQ-CONFIG-222).
- **REQ-CONFIG-009** — That user-level discovery is skipped entirely on Windows when the environment variable naming its location is unset, leaving only the project-level location searched, is fixed by REQ-MCP-017 and is not restated here. What this domain relies on it for is that the skip is not an error: a load in that state produces a discovery layer built from the project-level location alone, or no discovery layer at all (REQ-CONFIG-033), and never a fatal or a warning of this domain's severity taxonomy (REQ-CONFIG-233).
- **REQ-CONFIG-010** — The scope directories also hold state that is not configuration and never takes part in the merge. Under `<workspace>/.rotaris/`: the workspace's stable identifier, whose form and rules are REQ-SESSION-197's and which this domain neither names nor validates; custom tool plugins in `tools/`, inventory plugins in `plugins/`, and per-session isolated checkouts in the directory named by `worktree_storage_subpath` (default `worktrees/`), which is the **only** key naming that directory (REQ-CONFIG-068, REQ-CONFIG-194). Requirement-unit checkouts are placed elsewhere, at a location no key of this domain names (REQ-GIT-137). Under the global scope: custom tool plugins in `tools/`. Provider credentials live in the platform's per-user **data** directory, which is a different directory from the per-user configuration directory, and remain individually protected files rather than records in any store (REQ-PROVIDER-016). The staged gateway credentials of REQ-PROVIDER-063 are held under that same per-user data directory, one directory per workspace named by the workspace identifier, and are **not** under `<workspace>/.rotaris/`. Four kinds of state that were once directories here no longer are, and no key of this domain names a location for any of them. Session records, post-run improvement artifacts (REQ-LIBRARY-042) and requirement delivery records (REQ-CONFIG-192) are held in the store the application keeps for the workspace; the staged gateway credentials just named are held as individually protected files under the per-user data directory rather than in any store, for the reason REQ-PROVIDER-063 gives. That the workspace configuration directory therefore holds only the workspace identifier, plugins and checkouts beside the configuration files themselves is a consequence worth stating, because what a workspace-wide ignore rule (REQ-CONFIG-013) covers is now a much smaller set than it was. One consequence of that ignore rule needs stating plainly, because two requirements read as though they disagree and do not. REQ-SESSION-197 requires the workspace identifier to be human-readable and in a form version control can track; REQ-CONFIG-013 appends `.rotaris/` to the workspace's `.gitignore` by default. What REQ-SESSION-197 fixes is the identifier's **form** — a small plain-text value a person can read, diff and copy, rather than something only this application can interpret — and not an obligation on this product to commit it. Under the default ignore, the identifier travels with a folder that is moved, renamed or copied, and does not travel through a fresh clone; a clone therefore mints its own identifier and starts with an empty local session history, which is what REQ-SESSION-198 requires of a machine that has not run the workspace before. A user who wants the identifier committed can commit it by their own version-control means; the ignore rule is a default about what is staged by accident, not a prohibition, and that the choice remains theirs at all is exactly what ground 3 of REQ-CONFIG-477 relies on a file for.
- **REQ-CONFIG-011** — Provider credentials are never stored in any configuration file in either scope; they live only in the per-user data directory's credential store.
- **REQ-CONFIG-012** — A workspace with no `.rotaris/` directory at all, and a user with no global configuration directory at all, must both load successfully on built-in defaults. Absence is never an error at any level of the file set.
- **REQ-CONFIG-013** — Every configuration load makes a best-effort, idempotent attempt to keep the workspace configuration directory out of version control: if `<workspace>/.gitignore` contains no line that, once trimmed and stripped of a trailing `/`, equals `.rotaris`, the line `.rotaris/` is appended (adding a missing trailing newline first). A missing `.gitignore` is created. The write is atomic. Any failure — unreadable file, undecodable text, write error — is swallowed and never fails the configuration load.
- **REQ-CONFIG-014** — The configuration file set has no read cache: every load re-reads `agents.yaml` and `models.yml` from disk, so any surface performing a load observes the current file contents.

### File format and parse-time error semantics

- **REQ-CONFIG-015** — Configuration files are YAML parsed in a safe subset that cannot construct arbitrary language objects from document tags.
- **REQ-CONFIG-016** — A missing configuration file yields an empty mapping and is not an error.
- **REQ-CONFIG-017** — A file that is empty, whitespace-only, or contains only comments parses to nothing and yields an empty mapping. It is not an error and is indistinguishable from a missing file for load purposes.
- **REQ-CONFIG-018** — A YAML syntax error in `agents.yaml` or `models.yml` **aborts the load** with an error whose message names the full path of the offending file and carries the parser's own detail, including the line and column of the fault.
- **REQ-CONFIG-019** — A file whose top-level document is not a mapping (a list, a scalar) **aborts the load** with an error naming the file and stating that top-level content must be a mapping.
- **REQ-CONFIG-020** — YAML 1.1 boolean folding is handled symmetrically wherever it bites. For any field whose accepted values are a string vocabulary, a value the parser folded to a boolean is coerced back to a lower-cased string before validation: the negative spellings `off`, `false` and `no` become `"off"`, `"false"` and `"no"`, and the affirmative spellings `on`, `true` and `yes` become `"on"`, `"true"` and `"yes"`. The coerced string is then validated against that field's vocabulary like any other string. `sandbox_mode: off` therefore loads as the accepted value `off`, while `sandbox_mode: on` is rejected as an unrecognized confinement mode with a message naming the value and the accepted list (REQ-CONFIG-127) — never as a type error, and never silently accepted.
- **REQ-CONFIG-462** — Configuration files are read as UTF-8. A file whose bytes cannot be decoded as UTF-8 is treated exactly as malformed content of that file's severity class (REQ-CONFIG-024): `agents.yaml` and `models.yml` **abort the load** with an error naming the full path and stating that the file must be UTF-8 text; the discovery snapshot, `secrets.yaml` and a discovered `mcp.json` each degrade per their own rule and contribute nothing. A byte-order mark at the start of a file is accepted and discarded. This is a distinct condition from malformed markup and its message says so.
- **REQ-CONFIG-021** — A malformed or schema-invalid `project_settings.yaml` snapshot is **not** fatal: it is logged as ignored, treated as absent, and the load continues on the remaining layers.
- **REQ-CONFIG-022** — A malformed `secrets.yaml` (unparseable YAML, or a non-mapping top level) yields an empty secret set **silently** — no warning, no exception. Within it, a server entry whose value is not a mapping is skipped; keys and values are coerced to strings.
- **REQ-CONFIG-023** — A malformed discovered `mcp.json` never prevents the product's own configuration from loading. Unreadable files, JSON syntax errors, and non-object top levels each produce a warning naming the file and contribute nothing.
- **REQ-CONFIG-024** — The severity split is a contract: missing and empty files are silent; the primary configuration files are fatal on malformed markup; the discovery snapshot, the secrets file, and third-party discovery all degrade instead of aborting.

### First-run bootstrap

- **REQ-CONFIG-025** — When `<workspace>/.rotaris/agents.yaml` is absent, a minimal starter file is written on first run. The starter document is **scope-independent**: the same content is written for the global `agents.yaml` when a writer bootstraps that file instead (REQ-CONFIG-030), nothing in it being specific to a workspace. Its content is a short comment header explaining that the file overrides built-in roles, models and tool servers, a `default_persona` key (parameterized, shipped value `orchestrator`), and twelve explicitly-null keys: `default_summary_model`, `default_summary_model_thinking`, `large_model`, `large_model_thinking`, `medium_model`, `medium_model_thinking`, `small_model`, `small_model_thinking`, `fallback_model`, `fallback_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`.
- **REQ-CONFIG-026** — Bootstrap creates missing parent directories and **never clobbers** an existing file unless overwrite is explicitly requested; when it declines it reports that it skipped because the file exists.
- **REQ-CONFIG-027** — The bootstrap write is atomic — content is staged beside the target and swapped into place — with a resulting file mode of `0644`. A crash mid-write can never leave a truncated `agents.yaml`, and no temporary file is left behind on any path.
- **REQ-CONFIG-028** — A workspace counts as "needs bootstrap" when the target file is absent or when its text is empty after trimming whitespace; in either case the starter file is written. Two further conditions are reported as needing attention but are **never** written over: a path that is a directory, and a file whose bytes cannot be decoded as UTF-8. For those two the bootstrap declines exactly as REQ-CONFIG-026 requires, and the user-visible outcome is the fatal load error of REQ-CONFIG-462 naming the path. **A target the product cannot read at all takes that same declining path, and is named here so that the two lists above are not read as covering the space between them.** A path that exists and whose content cannot be obtained — refused by the operating system, or failing to be read for any other reason — is neither absent nor empty, so it is not a workspace needing bootstrap and MUST NOT have the starter file written over it; and it is neither a directory nor a decoding failure, so nothing above would otherwise say what becomes of it. It declines as those two do, reporting the path and what prevented the read. The rule the three share, stated so it survives a later edit to any of the lists: **the starter file is written only where the product has established that nothing is there, and never where it has failed to establish anything.** Not being able to read a file is not evidence that the file is empty.
- **REQ-CONFIG-029** — Bootstrap detection and the bootstrap write address the workspace configuration directory by its current name only, as does every other read and write in this specification (REQ-CONFIG-058).
- **REQ-CONFIG-030** — The startup model-preference write path (REQ-CONFIG-248) bootstraps a missing workspace `agents.yaml` before writing, so a first slot or role edit made through it both creates and populates that file. **A global-scoped edit through the same path bootstraps a missing global `agents.yaml` in exactly the same way**, with the same starter content (REQ-CONFIG-025), the same parent-directory creation, the same refusal to clobber, and the same atomic write and file mode: the path behaves identically in both scopes, so a user's first global model preference is never lost for want of a file. Bootstrap remains scoped to the file being written — a workspace-scoped edit never creates the global file, and a global-scoped edit never creates the workspace one. The other two writers do not bootstrap: with no file present the desktop save starts from an empty document (REQ-CONFIG-256), as does the scoped per-field write path (REQ-CONFIG-441).

### Layering and precedence

- **REQ-CONFIG-031** — Configuration layers fold in a fixed, total order, later winning: (1) built-in defaults; (2) auto-discovered tool servers; (3) the global provider/model discovery snapshot; (4) the global scope's `agents.yaml` + `models.yml`; (5) the workspace scope's `agents.yaml` + `models.yml`. Those five are the whole of the layered configuration surface and there is no sixth layer: the product accepts no configuration file from outside the two scopes, because it has no command-line invocation with which to name one (REQ-CONFIG-234, REQ-STARTUP-111). There is no per-key inversion — a workspace file can never lose to a global file.
- **REQ-CONFIG-032** — The built-in default layer is copied per load; a load can never mutate the shipped defaults for the remainder of the process.
- **REQ-CONFIG-033** — The auto-discovery layer contributes **only** `mcp_servers:` entries and is skipped entirely when nothing was discovered.
- **REQ-CONFIG-034** — The discovery-snapshot layer contributes only `models:`, `unavailable_models:`, and the five startup slots `large_model`, `medium_model`, `small_model`, `fallback_model`, `default_summary_model`, and only for providers whose snapshot entry is marked authenticated.
- **REQ-CONFIG-035** — A load that completes successfully yields a configuration that is already fully resolved, so no caller has to finish the job: `workspace_root` holds the resolved workspace path; no reference field still holds a tier alias (REQ-CONFIG-073); the reasoning-effort model entries of REQ-CONFIG-076 and REQ-CONFIG-079 exist and every slot and role that asked for an effort points at one; the document satisfies the schema (REQ-CONFIG-229); `max_input_tokens` and `max_output_tokens` carry values only where the entry stated neither (REQ-CONFIG-096); every `mcp_servers:` entry carries a provenance value (REQ-CONFIG-222); and every environment placeholder and stored secret has been resolved (REQ-CONFIG-218, REQ-CONFIG-224, REQ-CONFIG-225). A stored secret value can never itself be the cause of a schema failure.
- **REQ-CONFIG-036** — Per-role reasoning synthesis must run **after** tier-alias substitution, so a role targeting a tier layers its own effort on top of the slot's resolved model rather than on the raw alias.
- **REQ-CONFIG-037** — Known-token-limit back-fill runs **after** schema validation; placeholder and secret resolution runs after validation too, so secret values never pass through schema validation.
- **REQ-CONFIG-038** — Tool-server provenance is computed after validation but before secret resolution.
- **REQ-CONFIG-039** — Auto-discovered locations are applied user-level first, then project-level, so a project-level declaration of the same server name beats the user-level one. The winning source per server name is recorded and observable (REQ-CONFIG-222).

### Merge disciplines

- **REQ-CONFIG-040** — The merge recognizes exactly four classes of top-level key: replace-if-not-null, named-entry, section, and computed (REQ-CONFIG-041, REQ-CONFIG-043, REQ-CONFIG-047, REQ-CONFIG-049). A top-level key belonging to none of them contributes nothing to the merged configuration and is neither reported nor rejected. Contributing nothing to the merge is not the same as having no effect: such a key may still be read by a surface that parses the same file separately — `rotaris.delegation_strategy` is the shipped case (see Data & Formats). `display` is a section-class key (REQ-CONFIG-047, REQ-CONFIG-172) and `inject_agents_md` a replace-if-not-null key (REQ-CONFIG-466); both are merged by the load path and read back by the surfaces that write them. An unrecognized top-level key is **reported as a warning** naming the key and the file it was read from, and still contributes nothing to the merged configuration; it is never fatal, so a file authored against a later release still loads (REQ-CONFIG-233).
- **REQ-CONFIG-041** — **Replace-if-not-null class.** `default_persona`, `default_summary_model`, `default_summary_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`, `gatekeeper_model`, `gatekeeper_model_thinking`, `small_model`, `small_model_thinking`, `medium_model`, `medium_model_thinking`, `large_model`, `large_model_thinking`, `fallback_model`, `fallback_model_thinking`, `worktree_storage_subpath`, `inject_agents_md`. A higher layer replaces the value only when it supplies a non-null value.
- **REQ-CONFIG-042** — `skills` is a **section-class** key (REQ-CONFIG-047), so a layer overlays only what it states: a layer stating `skills.enabled` leaves both override maps inherited, and a layer stating an entry of `skills.overrides` or `skills.invocation_overrides` overlays that skill's policy alone while every other skill's inherited policy survives (REQ-CONFIG-048). A workspace scope therefore cannot discard the global scope's per-skill policies wholesale; to change one, it states that one. A bare `skills:` carrying no value is coerced to an empty section and changes nothing (REQ-CONFIG-054).
- **REQ-CONFIG-043** — **Named-entry class.** `personas`, `models`, `mcp_servers`, `unavailable_models`. Entries union by name across layers. When a name exists in both layers and both values are mappings, the entry's immediate fields are overlaid (higher layer wins per field); otherwise the higher layer's value replaces outright.
- **REQ-CONFIG-044** — A named entry present only in a lower layer survives into the merged result. A workspace file that declares no `mcp_servers:` at all must not erase globally declared servers; a role defined only globally must survive a workspace file that defines other roles.
- **REQ-CONFIG-045** — List-valued fields **inside** a named entry are replaced wholesale, never appended: a role's `tools`, `delegates_to`, `custom_tools` and `mcp_servers` lists are fully restated by any layer that declares them. To add one tool to an inherited role, the full list must be restated.
- **REQ-CONFIG-046** — Mapping-valued fields inside a named entry are likewise replaced wholesale (for example a role's `tool_restrictions` or `mcp_tools` map) — the overlay reaches exactly one level: top-level key → named entry → whole field value.
- **REQ-CONFIG-047** — **Section class.** `runtime`, `verifier`, `compressor`, `circuit_breaker`, `transcript`, `display`, `initialization`, `project_init`, `requirements`, `skills`, `hooks`, `checkpoints`, `integration` (REQ-CONFIG-470). A higher layer's section overlays the inherited section **per field**; unstated fields are inherited. Setting one field of `requirements` keeps every other inherited `requirements` field.
- **REQ-CONFIG-048** — A section overlay is **recursive through nested mappings**: wherever both layers hold a mapping at the same path, the higher layer's fields overlay the inherited ones and every field it does not state is inherited, at any depth. Changing `requirements.board.card_limit` alone therefore leaves the rest of `board:` — `filters` included — exactly as the lower layer left it (REQ-CONFIG-197), and a global per-skill policy survives a workspace file that states a different skill (REQ-CONFIG-042). Recursion stops at any value that is not a mapping: a list is replaced wholesale wherever it appears (REQ-CONFIG-050), and the value of a named entry's field remains one level deep (REQ-CONFIG-046).
- **REQ-CONFIG-049** — **Computed class.** `workspace_root`, `metadata_workspace_root`, `mcp_server_sources`, `resolved_persona_model_tiers` are produced by the loader and are never merged from a file. A `workspace_root` written into a file has no effect.
- **REQ-CONFIG-050** — No key anywhere in the system merges list **contents**. Any list-valued setting — role tool lists, verification checks, hook entries, requirement sources, refresh triggers, escalation triggers, source-file extensions, host lists, writable roots — is replaced by a layer that states it.
- **REQ-CONFIG-051** — The end-to-end merge must satisfy, for a two-scope fixture: workspace role fields win per field while unstated role fields are inherited; a workspace role may reference a model declared in a global `models.yml`; a role's tool list equals the workspace's list exactly; a globally-only role survives; models from all four files coexist as a union; and a workspace `runtime:` block stating only two fields keeps every other runtime field at its inherited value.
- **REQ-CONFIG-461** — The merge disciplines of REQ-CONFIG-040 to REQ-CONFIG-050 are the only merge rules in the product. No consumer replaces a configuration document as a whole, and any example configuration, comment header or document shipped with the product describes these rules and no other. A shipped example that describes whole-document replacement is wrong and is corrected, not honoured.

### Null, absent and empty semantics

- **REQ-CONFIG-052** — For a replace-class key, `null` and absent are behaviorally identical: writing `large_model: null` in a workspace file cannot clear a value inherited from a lower layer.
- **REQ-CONFIG-053** — Inside a named entry, `null` **can** clear: a role override that writes a bare `system_prompt_file:` clears the inherited value, because entry fields are overlaid without a null guard.
- **REQ-CONFIG-054** — A bare section key (`verifier:`, `checkpoints:`, `initialization:`, `project_init:`, `hooks:` with no value) means "unset" and is coerced to an empty section rather than raising a type error.
- **REQ-CONFIG-055** — `hooks: {entries: }` (a bare `entries` key) means the hook list is **unset** — inherit the lower layer's list. `hooks: {entries: []}` means an explicit empty list that **replaces** the inherited list. These two must stay distinguishable.
- **REQ-CONFIG-056** — Three settings are deliberately three-valued and must stay distinguishable across the merge: `verifier.checks` (unset = auto-detect a suite; `[]` = this workspace explicitly runs no verification; a list = the stated suite), `checkpoints.enabled` (unset = on for isolated sessions only; `true` = always; `false` = never), and `hooks.entries` (unset vs. explicit empty).
- **REQ-CONFIG-057** — A per-model `max_parallel` written explicitly as `null` is distinguishable from an omitted `max_parallel` and defeats the provider-conditional default of REQ-CONFIG-095.

### Legacy migration

- **REQ-CONFIG-058** — *Withdrawn.* There is no earlier directory name for this product to adopt from, so directory adoption specifies a rename whose source can never be named; renaming a directory the product cannot identify is a risk taken for no benefit. The three directories of REQ-CONFIG-001, REQ-CONFIG-011 and the Data & Formats layout are addressed by their current names only, and a directory under any other name is left untouched.
- **REQ-CONFIG-059** — *Withdrawn.* It described the failure handling of the directory adoption withdrawn by REQ-CONFIG-058.
- **REQ-CONFIG-060** — *Withdrawn.* It described the success logging of the directory adoption withdrawn by REQ-CONFIG-058.
- **REQ-CONFIG-061** — *Withdrawn.* It described how often the directory adoption withdrawn by REQ-CONFIG-058 was attempted.
- **REQ-CONFIG-062** — Legacy role-name canonicalization is applied **per scope, before any cross-scope merge**, so a workspace file using an old role spelling still overrides the canonically-named role from a lower layer. Canonicalization rewrites the top-level `default_persona` string, each key of the `personas:` mapping, each role's own `name` field, every entry of a role's `delegates_to` list, and every key of a role's `tool_restrictions` mapping. The shipped alias vocabulary contains exactly one mapping: `oracle` → `codebase-analyst`. Two differently-spelled keys that canonicalize to the same role within one file are field-merged (later key wins per field), never silently dropped. Non-string keys and non-mapping role values pass through untouched.

### Top-level keys and model slots

- **REQ-CONFIG-063** — `default_persona` (string) names the role used when none is requested. Shipped default: `orchestrator`.
- **REQ-CONFIG-064** — `small_model`, `medium_model`, `large_model` (string or null) name entries of `models:` that the three tier aliases resolve to. Shipped defaults: small and medium both `gpt-4o-mini`, large `gpt-4o`.
- **REQ-CONFIG-065** — `default_summary_model` (string) names the model that summarizes child work. `improvement_collector_model`, `gatekeeper_model` and `fallback_model` (string or null) name the models used respectively for the post-run improvement collection pass, the gate-authoring role, and the retry issued when a child's model fails to answer within the configured limits (REQ-CONFIG-110, REQ-CONFIG-114). Each must name an entry of `models:` or a tier alias and is reported by referential validation otherwise (REQ-CONFIG-232), which also reports `default_summary_model` when it is left unset. `fallback_model` resolves to whatever `small_model` resolves to when it is unset or null (REQ-CONFIG-067), and its shipped value is the tier alias `small_model`. All four ship as tier aliases rather than as concrete model names, so a workspace that has never been configured resolves them through the three tier slots and no slot is left unset at referential validation (REQ-CONFIG-232): `default_summary_model` ships as `small_model`, `improvement_collector_model` ships as `small_model`, `gatekeeper_model` ships as `medium_model`, and `fallback_model` ships as `small_model`. Summarizing child work and collecting improvement notes are bulk passes over text the run has already produced, while authoring a gate is a judgement the run is then held to, which is why the gate slot alone ships on the middle tier. What this requirement fixes about these slots is the shipped value each carries in the primary configuration document and the referential rule each is checked by; the set of capability slots and the order in which an **unset** slot resolves through the others are REQ-PROVIDER-088's, which this document neither restates nor varies. What it relies on that requirement for is that every source in that order is another slot of the same set rather than a literal model name, so an unset slot never resolves to a value referential validation would then report as unknown (REQ-CONFIG-232).
- **REQ-CONFIG-066** — Each of those slots has a `<slot>_thinking` companion (`default_summary_model_thinking`, `improvement_collector_model_thinking`, `gatekeeper_model_thinking`, `small_model_thinking`, `medium_model_thinking`, `large_model_thinking`, `fallback_model_thinking`) accepting a reasoning level or null. Default null.
- **REQ-CONFIG-067** — `fallback_model` is resolved before referential validation runs: unset or written as null, it resolves to whatever `small_model` resolves to, so referential validation never reports it as unset (REQ-CONFIG-232). Its shipped value is the tier alias `small_model` (REQ-CONFIG-065), which tier-alias substitution replaces with the concrete model name (REQ-CONFIG-073). A stated value naming no configured model is reported, with the message naming both the field and the offending value.
- **REQ-CONFIG-068** — `worktree_storage_subpath` (string, default `worktrees`) is the subdirectory under the workspace configuration directory where per-session isolated checkouts are stored.
- **REQ-CONFIG-069** — The reasoning-level vocabulary for slots and models is exactly `auto`, `low`, `medium`, `high`, `max`. The per-role vocabulary adds two: `default` and `provider_default`.
- **REQ-CONFIG-070** — The tier-alias vocabulary is exactly the three strings `small_model`, `medium_model`, `large_model`.
- **REQ-CONFIG-071** — `resolved_persona_model_tiers` is a computed, non-serialized map recording which roles referenced a tier alias before substitution, so a surface can report "this role is on the medium tier" rather than a raw model id.
- **REQ-CONFIG-072** — `metadata_workspace_root` and `resolved_persona_model_tiers` are excluded from any serialized form of the configuration.

### Tier aliases and reasoning-effort synthesis

- **REQ-CONFIG-073** — After merging, any reference field whose string value equals `small_model`, `medium_model` or `large_model` is substituted with the concrete model name that slot holds. Substitution applies to `default_summary_model`, `improvement_collector_model`, `gatekeeper_model`, `fallback_model`; each role's `model`, `summary_model` and `fallback_model`; and `compressor.model` and `circuit_breaker.model`.
- **REQ-CONFIG-074** — An alias is registered only when the slot's own value is not itself another alias name. `small_model: medium_model` therefore registers no substitution for `small_model` and the literal string survives to fail referential validation later. A self-reference (`small_model: small_model`) behaves the same way.
- **REQ-CONFIG-075** — Before a role's `model` is substituted, the original tier name is recorded for that role (REQ-CONFIG-071).
- **REQ-CONFIG-076** — When a `<slot>_thinking` value is set, a synthetic model entry is created by copying the slot's resolved base model, applying the reasoning level to the copy, registering it under a reserved name of the form `__startup_slot__:<slot>`, and repointing the slot at it.
- **REQ-CONFIG-077** — Slot-to-slot alias chains are followed when resolving a slot's base model, with cycle detection. A cycle is logged naming the chain and the reasoning override is skipped.
- **REQ-CONFIG-078** — Every failure mode of slot reasoning synthesis is a **warning, never a load failure**: unresolvable slot, base model absent from `models:`, or a circular chain each log and skip.
- **REQ-CONFIG-079** — A role's `thinking` value is honored as follows: absent/null → inherit, no synthesis; `default` → normalized to unset, meaning "inherit whatever the selected model or slot is configured with"; `provider_default` → a synthetic copy is created with the reasoning effort **cleared**, so any configured effort (including framework defaults) is removed; any of `auto`/`low`/`medium`/`high`/`max` → a synthetic copy carrying that level. The synthetic is registered under a reserved name of the form `__persona__:<role name>`.
- **REQ-CONFIG-080** — Role reasoning synthesis fails soft: an unconfigured model or an absent base model logs a warning naming the role and skips.
- **REQ-CONFIG-081** — The reserved synthetic name prefixes `__startup_slot__:` and `__persona__:` are loader-owned. A user-authored model entry using either prefix is overwritten.

### Model entries

- **REQ-CONFIG-082** — A `models:` entry requires exactly two fields: `provider` (string, the provider name used by the dispatch layer) and `model_id` (string, the provider-local model id). Every other field has a default.
- **REQ-CONFIG-083** — Credential fields: `api_key` (secret string, default null — redacted in any diagnostic rendering of the configuration), `api_key_env` (string, default null — names an environment variable holding the key), `auth_provider` (string, default null — when set, credentials come from the sign-in subsystem instead of the two preceding fields).
- **REQ-CONFIG-084** — Endpoint fields: `base_url` (string or null), `disable_streaming` (bool, default false — forces a non-streaming request for endpoints that reject streaming), `disable_responses_api` (bool, default false — forces the chat-completions path; automatically enabled when `auth_provider` is `copilot`), `api_mode` (`chat`, `responses`, or null; null means the provider's own default).
- **REQ-CONFIG-085** — Budget fields: `max_input_tokens` and `max_output_tokens` (int or null, back-filled from a known-limits table when unset), `context_compression_threshold` (int or null, per-model compression trigger).
- **REQ-CONFIG-086** — Timeout and retry fields: `timeout` (int seconds or null; overrides `runtime.model_timeout`; null means use the global value), `num_retries` (int or null; overrides the dispatch layer's default of **5**).
- **REQ-CONFIG-087** — Sampling fields, all null by default unless noted: `temperature` (float), `top_p` (float), `top_k` (int, applied only where the target provider accepts it), `presence_penalty` (float), `repetition_penalty` (float), `seed` (int), `extra_body` (mapping, default empty — extra provider-specific request-body fields).
- **REQ-CONFIG-088** — Pricing fields `input_cost_per_token` and `output_cost_per_token` (float ≥ 0, null default) **only take effect when both are set**. Setting one alone has no observable effect.
- **REQ-CONFIG-089** — Reasoning fields: `thinking` (level or null) and `reasoning_effort` (string or null). An explicit `reasoning_effort` **overrides** the value derived from `thinking`.
- **REQ-CONFIG-090** — `thinking` accepts legacy boolean spellings for backward compatibility: `true` is read as `high`, `false` is read as unset.
- **REQ-CONFIG-091** — `reasoning_effort_map` (mapping from a normalized reasoning level to a provider-dialect string, default empty) adapts the normalized vocabulary to a custom endpoint's own spelling.
- **REQ-CONFIG-092** — Exactly four effort strings reach a provider unchanged: `low`, `medium`, `high`, `xhigh`. Any other configured level is first looked up in the model's `reasoning_effort_map`, and where that map holds an entry for the level the mapped string is sent verbatim. Where it does not, the level is normalized instead: `max` reaches a provider as `xhigh` (REQ-CONFIG-093). The level `auto` has no normalization and, absent a map entry for it, **no reasoning-effort field is sent at all** — the request carries none and the provider's own default governs, which is exactly what `auto` means. The same holds for any other level that has neither a map entry nor a normalization: the field is omitted rather than guessed at, and a warning naming the model and the level is logged once per model per load. An explicitly configured `reasoning_effort` string bypasses this path entirely and is sent verbatim (REQ-CONFIG-089). No value outside `low`, `medium`, `high`, `xhigh`, a `reasoning_effort_map` value, and an explicit `reasoning_effort` ever reaches a provider.
- **REQ-CONFIG-093** — An effort a user selects as `Max` is stored as the normalized level `max` and reaches a provider as `xhigh` (REQ-CONFIG-092). `auto` is a configuration-only level and this reading is canonical: **no editing surface offers `auto` as a selectable effort**, so no surface can create one. A value already stored is a different matter and is governed by the general rule of REQ-CONFIG-318 — a stored `auto` is appended to that control's options, is displayed under its own name, and is shown as the current selection, so it is never displayed as, and never confused with, the unset level (REQ-CONFIG-254, REQ-CONFIG-332). A stored `auto` is rewritten only when the user selects a different level; no repopulation, no re-selection of the entry already shown, and no model change may replace it (REQ-CONFIG-334). A configuration is therefore free to state `auto` and an editing surface can neither offer it nor silently take it away.
- **REQ-CONFIG-094** — `max_parallel` (int ≥ 1 or null) caps how many child agents may run against this model at once. A spawn that would exceed the cap is refused, and the refusal is reported to the requester as an error: it is neither queued for later nor dropped without a report. **What counts against the cap** is every child agent currently running against that `models:` entry, counted by the entry's key, across the whole process and at every delegation depth — children of the entry role and children of children alike, and children belonging to any other session running in the same process. Two different `models:` keys never share a count even where they name the same provider model, since the cap is a property of the configured entry; a loader-owned synthetic copy (REQ-CONFIG-081) counts against the entry it was copied from, so adding a reasoning variant cannot double a cap. A child stops counting the moment it finishes, however it finished. The refusal must convey which model entry the cap belongs to, the cap's value, that the limit is currently reached rather than that the model is unavailable, and that the request may be made again once a child running on that entry finishes; the wording is left to the implementation.
- **REQ-CONFIG-095** — When `max_parallel` is not explicitly stated, it defaults by provider: `deepseek` → **3**, `claude-code` → **2**, every other provider → unlimited. Explicitly writing `max_parallel: null` on either capped provider yields unlimited.
- **REQ-CONFIG-096** — Known token limits are back-filled after validation and fill **only** fields still unset, so an explicitly stated `max_input_tokens` or `max_output_tokens` is never overwritten. Candidates are tried in this order: the `models:` key itself when it contains a `/`; the bare `model_id`; `model_id` with a leading provider prefix removed; then each of those three re-qualified as `<provider id>/<candidate>`, taking the entry's sign-in provider id before its dispatch provider id, with a repeated candidate tried once only. For this lookup the provider ids `codex` and `copilot` are both treated as `openai`. When no candidate matches, both fields remain null. The known-limits table is **static data shipped and versioned with the product**: it is compiled in, read from no file and fetched over no network, so a load's outcome never depends on anything outside the installation. Its contents are not enumerated in this specification and may change with any release without amending it, because it is a convenience and never a source of truth — limits the discovery snapshot advertises are written into the entry before back-fill runs (REQ-CONFIG-207) and therefore win, an explicitly stated limit always wins, and a miss is silent and never an error. There is no user override path for the table itself: a user who disagrees with it states `max_input_tokens` or `max_output_tokens` on the model entry.
- **REQ-CONFIG-097** — The shipped default model set contains exactly two entries, both reading their key from the environment variable `OPENAI_API_KEY`: `gpt-4o` (provider `openai`, model id `gpt-4o`) and `gpt-4o-mini` (provider `openai`, model id `gpt-4o-mini`).

### Role (persona) entries

- **REQ-CONFIG-098** — A `personas:` entry requires `name` (string) and `model` (string, a model key or a tier alias). Every other field has a default.
- **REQ-CONFIG-099** — `purpose` (string or null) is a one-line description and **must not contain a newline**; a multi-line value is rejected at load with a message stating the single-line rule.
- **REQ-CONFIG-100** — Prompt fields: `system_prompt` (inline prompt text, null default) and `system_prompt_file` (path to a prompt file, null default) each supply the role's prompt in place of the built-in one; `model_family_variants` (map, null default) associates a model-family key such as `claude`, `gpt` or `gemini` with extra prompt text appended to the role's prompt when the role's resolved model belongs to that family. A family key is tested **case-insensitively as a substring**, against the resolved model entry's `model_id` first and, where that does not match, against the entry's `provider`; both the key and the field are lower-cased before the test. **Every** variant whose key matches applies — the feature is additive, not a first-match choice — and the matching variants are appended in ascending code-point order of their keys, each as its own block after the role's prompt, so the result never depends on the order the mapping happens to be written in. A key matching neither field contributes nothing and is not an error, since a configuration may carry variants for models it is not currently using.
- **REQ-CONFIG-101** — Capability lists, each defaulting to empty and each replaced wholesale on override: `tools` (friendly tool names), `delegates_to` (roles this one may spawn), `custom_tools` (plugin tools), `mcp_servers` (tool servers offered to this role).
- **REQ-CONFIG-102** — `mcp_tools` (map from server name to a list of tool names, null default) narrows what a role sees of a server. **With the map unset, or with no key present for a given server, the role receives every tool that server publishes** — which is what keeps configurations authored before this key existed working unchanged. `disabled_tools` on the server is then evaluated over any such grant, and removal wins over inclusion.
- **REQ-CONFIG-103** — `tool_restrictions` (map from name to allowed-tool list, null default) restricts named entities; an entity absent from the map is unrestricted.
- **REQ-CONFIG-104** — `coordinator_only` (bool, default false). This document fixes the field — its name, its type, its default, and that it is a per-role key of a `personas:` entry replaced wholesale on override like the capability lists of REQ-CONFIG-101. What the flag removes from the role's tool set is fixed by REQ-TOOLS-006, and the public tool names it removes are those of the registry REQ-TOOLS-001 fixes; this document holds no copy of either and states no second withholding rule. What it relies on that requirement for is that the removal is total for the role — a withheld tool is neither offered to the role nor callable by it, and a call naming one is refused — and that the removal only ever subtracts, so setting the flag can never hand a role a tool its `tools` list did not name. Which tools survive the flag is REQ-TOOLS-006's answer and not this document's, so a reader settles that question there rather than by comparing two lists.
- **REQ-CONFIG-105** — `read_only` (bool, default false). This document fixes the field on the same terms as REQ-CONFIG-104. While true, the role's tool set is reduced to the read-only tool class REQ-TOOLS-007 fixes, applied in the order REQ-TOOLS-006 fixes; this document holds no copy of that class and adds no member to it. What it relies on those requirements for is that the class is a **closed** set of public tool names, from which three consequences follow that this document depends on: a tool the class does not name is withheld, so a built-in introduced later is safe by default and reaches read-only roles only once the class itself names it; a plugin tool (`custom_tools`) and a tool-server tool are never in the class and are therefore withheld outright while the flag is true, whatever they declare about themselves, because a read-only guarantee asserted by a third party is not one the product can keep — which is the fail-closed reading of an undeclared tool REQ-TOOLS-001 already fixes, this flag being a rule that withholds; and the reduction only ever subtracts. `artifact_write` is a member of that class and remains separately subject to REQ-CONFIG-106, which is this document's own gate and is not affected by the flag. Default-deny is deliberate: a role the user marked read-only must not gain a mutating tool by the mere fact that nobody classified it.
- **REQ-CONFIG-106** — `can_publish_artifacts` (bool, default false) gates `artifact_write`: naming that tool in `tools` is not sufficient on its own, and the role is handed it only while this flag is true.
- **REQ-CONFIG-107** — `skip_auto_sibling_context` (bool, default false) suppresses the automatically prepended index of prior sibling artifacts.
- **REQ-CONFIG-108** — `stall_timeout` (int seconds or null) substitutes for `runtime.child_stall_timeout` on children of this role and no others.
- **REQ-CONFIG-109** — `permission_mode` (string or null) overrides `runtime.permission_mode` for this role. Accepted values are `restricted`, `ask`, `autonomous`; **an unrecognized value falls back to `restricted`** rather than failing the load.
- **REQ-CONFIG-110** — `fallback_model` (string or null) must name an entry in `models:` and is retried **once** when the role's child hits the hard timeout. `summary_model` (string or null) names the model used for this role's summaries. `thinking` carries the per-role reasoning level of REQ-CONFIG-079.

### Runtime policy

- **REQ-CONFIG-111** — The `runtime:` section validates **on assignment as well as on load**, so a settings surface writing an invalid value onto a loaded configuration is refused at the moment of the write, not silently at the next load.
- **REQ-CONFIG-112** — Concurrency and depth: `max_children` (int, default **20**, total child agents in a run); `max_active_children` (int, default **6**, concurrent fan-out); `max_depth` (int, default **3**, delegation depth); `max_iterations` (int, default **20**, iteration cap); `message_limit` (int ≥ 1 or null, default null).

This requirement is the product's single definition of `message_limit` — its name, its value space and its default — and no requirement in any other domain holds a second copy of any of the three: a requirement that needs the limit cites this one and states only what it adds, such as what a run does when it reaches the limit or how a paused run is resumed. Its value space is exactly a positive integer or null: **null is the default and means no limit is applied**, so an unconfigured installation never reaches a message-limit pause, and null is also what a run carries when no limit was set for it. **Zero is not a permitted value**: it is rejected at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried, rather than being read as a second spelling of "disabled" — one spelling of "no limit" is what keeps a stored `0` from meaning "unlimited" in one domain and "stop at once" in another. A negative value is rejected the same way.
- **REQ-CONFIG-113** — Child timing: `child_timeout` (int seconds, default **1200**, hard per-child wall clock); `child_stall_timeout` (int seconds, default **90**, no-event threshold before a child is reported stalled).
- **REQ-CONFIG-114** — `llm_response_timeout` (int seconds, default **120**, minimum **30**): when no model event arrives within this window the role's `fallback_model` is engaged and **the child keeps running**. This is distinct from `child_timeout`, which ends the child.
- **REQ-CONFIG-115** — Model and tool timing: `model_timeout` (int seconds, default **120**, global model HTTP timeout overridden per model by REQ-CONFIG-086); `tool_call_timeout` (int seconds, default **30**, one tool call other than a terminal command); `summary_timeout` (int seconds, default **120**, generating a summary). The last two carry the names and defaults REQ-NOTIFY-100 fixes for those bounds, and no second key names either bound.
- **REQ-CONFIG-116** — Terminal execution: `shell_command_timeout` (int seconds, default **100**, one foreground command, named and defaulted per REQ-NOTIFY-100); `shell_max_background_sessions` (int, default **20**, range **1–64**); `shell_background_timeout` (int seconds ≥ 1, default **3600**, hard wall clock for a background command, enforced by a graceful termination signal followed by a forced kill). The maximum on the background-session count is stated rather than left open because that count is a multiplier on live terminal streams, whose delivery REQ-MONITOR-306 bounds in aggregate: with no ceiling the worst-case staleness of a live surface cannot be computed from a configuration at all, only observed after the fact, and with one it is `(agents + maximum) × windows ÷ 1,000` seconds. The figure is **64**, which is the ceiling REQ-TRACE-481 fixes for a concurrency control and is taken here for the same reason it gives: an input needs some upper bound, and a figure no machine could actually service is of no use to anyone. It bounds what may be configured and nothing else — the effective limit and the message on reaching it stay REQ-TOOLS-108's, and a value outside the range is **rejected** at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried, never clamped to the nearest bound and never ignored.
- **REQ-CONFIG-117** — Live terminal streaming: `terminal_stream_enabled` (bool, default true — disabling it removes the live view, never the command); `terminal_stream_interval_ms` (int, default **100**, range **20–2000**); `terminal_stream_buffer_kb` (int, default **256**, range **0–8192**, where **0 disables replay** for a display attaching mid-command). `terminal_stream_interval_ms` is a **ceiling on batching and not a fixed cadence**: a stream MAY frame its output sooner than the period, and MUST do so when input the user has directed at a stream whose control they have taken arms the next frame of that stream, so that REQ-SHELL-166's echo criterion is met at every value this range permits. Two bounds hold that licence and neither is relaxable by configuration: no two frames of one stream are ever closer together than **20 milliseconds**, and what reaches surfaces stays inside REQ-MONITOR-306's aggregate. **Output alone never arms a frame**, and neither does input an agent sends to its own terminal session; both are framed at the period, so the licence is spent only where a person is waiting to see their own keystroke. Read as a fixed cadence the key would put REQ-SHELL-166 out of reach at its own default and at every larger value in its range, which is why the reading is fixed here rather than left for an implementer to derive.
- **REQ-CONFIG-118** — Improvement collection: `improvement_collector_enabled` (bool, default true — one collection pass follows each finished top-level task run, and that pass can neither delay nor modify the run); `improvement_collector_timeout` (int seconds ≥ 1, default **60**; exceeding it falls back to an empty artifact).
- **REQ-CONFIG-119** — `claude_sdk_native_loop` (bool, default true): children routed to the locally installed agent-SDK provider run on that SDK's own loop with the product's tools published in-process. Setting it false falls back to a one-shot completion path that **discards tools and streaming**.
- **REQ-CONFIG-120** — Retries: `auto_retries_transient` (int, default **1**), `auto_retries_validation` (int, default **0**).
- **REQ-CONFIG-121** — `session_log_level` (string, default `WARNING`) sets the verbosity of the per-session debug log. The documented vocabulary is `DEBUG`/`INFO`/`WARNING`/`ERROR`; the value is **not** validated against that list.
- **REQ-CONFIG-122** — `permission_mode` (string) selects the permission preset a run starts from. The preset vocabulary is REQ-TOOLS-041's, the shipped default and the resolution of an unrecognized or absent name are REQ-TOOLS-046's, and the strictest-first ordering the settings surface presents them in is REQ-TOOLS-047's; this domain holds no copy of any of the three. What it adds is that the preset is selected by a `runtime:` key of that name, which layers per field and validates on assignment as well as on load (REQ-CONFIG-111) — and that, because an unrecognized value resolves rather than fails, a configuration carrying one still loads.
- **REQ-CONFIG-123** — `allow_outside_workspace` (bool, default false) opts out of workspace fencing for file access.
- **REQ-CONFIG-124** — `allow_unsandboxed_autonomous` (bool, default false) is the opt-in named by the downgrade rule of REQ-TOOLS-067. What that rule does — which modes it downgrades, the three conditions it downgrades on, and the mode it downgrades to — is fixed there and not restated here; this key is one of the three conditions and nothing more. What this domain adds is that it is a `runtime:` key with that name and that default, layering per field like every other, and the guidance that it belongs in a workspace configuration rather than the global one (REQ-SANDBOX-052).
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The key above still exists with the same default and layering; it no longer has any effect on any run.
- **REQ-CONFIG-125** — Approval fallback: this requirement registers `headless_approval_policy` (string) in `runtime:` and holds no copy of its accepted values, its shipped default, the reading of an unrecognized value, or what each value does to a refused call, all of which are REQ-TOOLS-065's. What this domain adds is that it is a `runtime:` key of the primary configuration document, that it therefore validates on assignment as well as on load (REQ-CONFIG-111), that it layers per field like every other runtime key (REQ-CONFIG-031), and that — because an unrecognized value resolves rather than fails — a configuration carrying one still loads (REQ-CONFIG-233).
- **REQ-CONFIG-126** — `approval_timeout_seconds` (float ≥ 0, default **300.0**) is how long a tool call waits for interactive approval before being denied. **A value of 0 means wait without a limit**; such a wait is still ended by cancelling the run. One setting covers two barriers: the same key, the same default and the same reading of zero govern the wait on a question put to the user as well as the wait on an approval (REQ-TOOLS-055, REQ-TOOLS-178, REQ-TRACE-467), and no second key names either wait. Its value space is the free-floating one REQ-TOOLS-055 fixes — any float at least 0, a negative value rejected at load and on assignment (REQ-CONFIG-111) — rather than a fixed list of offered stops, so an editing surface may suggest values but accepts every value the space permits (REQ-CONFIG-446).
- **REQ-CONFIG-127** — Confinement: this requirement registers three keys in `runtime:` and holds no copy of their vocabularies, defaults or validation rules, which are the sandbox-and-egress domain's. `sandbox_mode` (string) — vocabulary, shipped default and validation per REQ-SANDBOX-048, and the YAML boolean-false spelling per REQ-SANDBOX-049. `sandbox_writable_roots` (list of strings) — default, entry form and the absolute-path rule with its message shape per REQ-SANDBOX-050. `sandbox_allow_network` (bool) — default and the condition under which it has effect per REQ-SANDBOX-051. What this domain adds is only that all three are `runtime:` keys of the primary configuration document, that they therefore validate on assignment as well as on load (REQ-CONFIG-111), that they layer per field like every other runtime key (REQ-CONFIG-031), and that they are among the six values the security policy card writes (REQ-CONFIG-312).
- **REQ-CONFIG-128** — Egress: this requirement registers three keys in `runtime:` and holds no copy of their vocabularies, defaults, normalization or precedence, which are the sandbox-and-egress domain's. `network_egress_policy` (string) — disposition vocabulary, shipped default and the matching of a stored spelling per REQ-SANDBOX-001 and REQ-SANDBOX-002. `network_allowed_hosts` and `network_denied_hosts` (lists) — defaults, load-time entry normalization, the pattern grammar and the rule that a denial outranks an allow and a permissive default, per REQ-SANDBOX-003, REQ-SANDBOX-004, REQ-SANDBOX-009 and REQ-SANDBOX-014. What this domain adds is the same three facts REQ-CONFIG-127 adds for the confinement keys: they are `runtime:` keys, they validate on assignment as well as on load, they layer per field, and they complete the six values the security policy card writes (REQ-CONFIG-312).
- **REQ-CONFIG-129** — Completion checking: `classify_completion` (bool, default true) runs a post-iteration model check on the small tier — a "needs iteration" verdict re-queues, and a verdict that cannot be read is **resolved as complete**, so a momentary model failure cannot wedge a run. `validate_intent` (bool, default false) is deprecated and superseded by it.
- **REQ-CONFIG-130** — Persistence loop: `relentless` (bool, default false) keeps the loop running when the task list empties, checking fulfilment against the original request and appending remediation tasks; `relentless_max_cycles` (int ≥ 1, default **3**) hard-caps remediation cycles.
- **REQ-CONFIG-131** — Diagnostics and shutdown: `memory_diagnostics_enabled` (bool, default false — enables allocation tracking with snapshots written to the session's evidence stream); `memory_diagnostics_top_frames` (int, default **8**, range **0–50**, where **0** records aggregate memory only); `graceful_pause_tool_deadline` (float seconds, default **30.0**, range **5.0–120.0**, how long in-flight tool calls are awaited during pause or shutdown); `shutdown_drain_timeout` (float seconds ≥ 0, default **120.0**, grace for still-running background children at natural run conclusion, where **0 disables draining**).
- **REQ-CONFIG-467** — `loop_classification_timeout` (float seconds > 0, default **2.0**) bounds one loop-classification call and is the key REQ-NOTIFY-100 names for that bound. It sits in `runtime:` beside the other operation bounds so that each of the seven can be changed without changing another. The configured value is an upper bound only: a classification call is allowed no more than whatever remains of the activation budget of REQ-NOTIFY-106 when it is dispatched, so raising this key can never lengthen a call past that budget. This key is the product's single definition of that bound: it is the only key naming it, the value registered here is the value in force, and no other section — `circuit_breaker:` included (REQ-CONFIG-136) — carries a second key or a second default for it. A requirement that needs the bound cites this key and states no figure of its own.
- **REQ-CONFIG-468** — `additional_read_only_roots` (list of strings, default empty) designates locations outside the workspace that the file-reading tools may read and that every write is refused against (REQ-TOOLS-132). Each entry must be absolute in either POSIX or Windows spelling; a relative entry is rejected at load **and on assignment** (REQ-CONFIG-111) with a message naming the offending entry and stating the absolute-path rule, matching the rule and message shape of `sandbox_writable_roots` (REQ-CONFIG-127). Configuration is the only designation: no other surface widens the read fence, and the key grants nothing to confinement, which imposes no read restriction of its own (REQ-SANDBOX-053).
- **REQ-CONFIG-469** — `keep_going` (bool, default false) is the configured keep-going criterion of REQ-MONITOR-302, which ties run completion to verification evidence: while it is on, a completion-based stop is not taken while the most recent verification suite holds a failed or timed-out check. It is distinct from `relentless` (REQ-CONFIG-130), which audits fulfilment against the original request; the two are independent and either may be set without the other. It is a Tier B setting: the value a run uses is the one the interface holds when the run starts (REQ-CONFIG-262, REQ-CONFIG-263), so it can be set for the workspace on the settings screen and varied for a single run without being written to a file, and nothing else configures it.
- **REQ-CONFIG-473** — `event_retention_per_session` (int ≥ 0, default **20000**) is the retention cap on one session's stored event history: it bounds how many events that history keeps, and events beyond the cap are discarded oldest first, so a history that outgrew the cap holds the later part of the run rather than the earlier part. **A value of 0 means the history is never trimmed.** A negative value is not a permitted configuration value and is rejected at load and on assignment (REQ-CONFIG-111) with a message naming the key and the value it carried; it is never coerced to zero and never ignored. It sits in `runtime:` beside the other operation bounds. This requirement registers the key, its default and its value space; when a trim happens, how it is performed, and how a consumer learns that events were dropped are the event store's (REQ-EVENTS-091), which this key configures and which restates none of the above.
- **REQ-CONFIG-474** — `task_consecutive_retry_limit` (int ≥ 1, default **3**) is the per-task consecutive-retry limit REQ-ORCH-077 requires to be a setting of its own: it bounds how many consecutive pending-outcome iterations one task may accumulate before that task is abandoned. This requirement registers the key, its type and its default and holds no copy of the rule that consumes it — what the counter is kept over, what resets it, and what abandoning the task does are REQ-ORCH-077's. It sits in `runtime:` beside the other run budgets and is deliberately separate from `max_iterations` (REQ-CONFIG-112), so that either can be changed without changing the other; sharing one value is what made the guard unreachable. It layers per field and validates on assignment as well as on load (REQ-CONFIG-111).
- **REQ-CONFIG-475** — `relentless_audit_timeout` (int seconds ≥ 1, default **60**) bounds the single fulfilment-audit model call relentless mode makes before it decides whether to extend a run (REQ-ORCH-079). This requirement registers the key, its type and its default and holds no copy of the rule that consumes it — when the audit runs, what it compares, and the rule that a failed, timed-out or unparseable audit is neither retried nor allowed to extend the run are REQ-ORCH-079's. It sits in `runtime:` beside `relentless` and `relentless_max_cycles` (REQ-CONFIG-130), layers per field, and validates on assignment as well as on load (REQ-CONFIG-111).
- **REQ-CONFIG-476** — `run_start_mode` (string, exactly `auto` or `plan`, default `auto`) selects the run-start mode of REQ-ORCH-152. This requirement registers the key, its accepted values and its default and holds no copy of what either mode does: that `auto` applies no gate, that `plan` engages the gate of REQ-ORCH-153, and that the setting outlives the run that used it and governs the next run started in the same workspace are REQ-ORCH-152's. A value outside the two is **rejected** at load and on assignment (REQ-CONFIG-111), with a message naming the value and both accepted spellings, and is never coerced: a mis-spelled `plan` quietly read as `auto` would remove a gate the user asked for, which is why this key is not given the coercion an unrecognized permission mode receives (REQ-CONFIG-122, REQ-CONFIG-233). Being persistent, it is an ordinary `runtime:` key of the primary configuration document, layered per field like every other. It is the only key naming the run-start mode: every surface that offers the mode — the settings screen (REQ-CONFIG-320) and the surface a run is started from (REQ-ORCH-152) — writes this same key, and no surface holds a run-start mode of its own that a later load would not read back.

### Compression and circuit breaker

- **REQ-CONFIG-132** — `compressor:` fields: `model` (string, subject to tier-alias substitution; shipped default is the `small_model` alias); `timeout_seconds` (int, default **120**); `default_threshold` (int, default **265000**, the token capacity assumed whenever the running model advertises none); `threshold_percentage` (int, default **60**; the range accepted from a hand-authored file is **1–100**, while every editing surface offers **50–95** (REQ-CONFIG-446); **60** is the single authoritative default, and every surface, hint and document that names the auto-compression trigger names that same figure — there is no second value anywhere in the product); `chars_per_token` (int, default **4**, the token-estimation heuristic); `preserve_recent_turns` (int, default **4**, turns never compressed).
- **REQ-CONFIG-133** — `compressor.auto_threshold_ratio` (float, default **0.35**) is retained for configuration compatibility only and does not participate in threshold resolution; `threshold_percentage` is authoritative.
- **REQ-CONFIG-134** — The compression trigger is resolved as `capacity × threshold_percentage / 100`, with capacity chosen in this priority order: (1) the model's explicit `context_compression_threshold`; (2) the smaller of the model's advertised `max_input_tokens` and the configured `default_threshold`; (3) `default_threshold`, falling back to **265000** when that is unset or zero.
- **REQ-CONFIG-135** — Whenever a compression trigger is resolved, the resulting token number is accompanied by a statement naming the four inputs that produced it: the `threshold_percentage` applied, the capacity it was applied to, the model's advertised input limit and the configured `default_threshold`. That statement is the reason the user is given for a compression having fired, and it is surfaced in exactly two places. It is emitted on the session's event stream as part of the event that reports the compression, carrying the four inputs and the resulting token number as **separate machine-readable fields** so a consumer never has to parse a sentence; and it is rendered, from those fields, as the reason line of the transcript entry that reports the compression in the desktop transcript. The same fields are written to the per-session debug log at informational level. A compression is never reported to the user without them.
- **REQ-CONFIG-136** — `circuit_breaker:` fields: `enabled` (bool, default true; false bypasses evaluation entirely); `model` (string, shipped default the `small_model` alias); `activation_mode` (`independent` or `weighted`, default `independent`, enforced against that vocabulary). The section carries **no** timeout field of its own. The bound on the loop-classification call this section configures is `runtime.loop_classification_timeout` (REQ-CONFIG-467), which is the single key that names it; a `timeout_seconds` key under `circuit_breaker:` is not a recognized field and is reported like any other unknown key in a merged section (REQ-CONFIG-233). Two keys naming one bound is what let two different values for it stand at once, so the second is removed rather than kept in step by hand.
- **REQ-CONFIG-137** — Circuit-breaker thresholds: `tool_call_threshold` (int ≥ 1, default **60**); `message_count_threshold` (int ≥ 1, default **60**); `tool_weight` (float **0.0–1.0**, default **0.6**); `message_weight` (float **0.0–1.0**, default **0.4**); `target_score` (float > 0, default **1.0**); `max_recent_events` (int ≥ 4, default **24**); `max_transcript_chars` (int ≥ 500, default **8000**); `repetition_threshold` (int ≥ 2, default **4**); `cycle_threshold` (int ≥ 2, default **3**).
- **REQ-CONFIG-138** — The two weights are bounded individually and are **not** constrained to sum to 1.0; a configuration whose weights sum to any value in range loads without complaint.

### Verification suite

- **REQ-CONFIG-139** — `verifier.checks` (list or unset, default unset) is three-valued per REQ-CONFIG-056. The resolver must never conflate an explicit empty list with a failed auto-detection.
- **REQ-CONFIG-140** — `verifier.gate_completion` (bool, default true). While true, an iteration that changed at least one file cannot be reported complete while any check of severity `blocking` is failing. While false, the suite still runs and every result is still reported, but no result withholds completion. An iteration that changed no file is never gated at either setting.
- **REQ-CONFIG-141** — `verifier.suite_timeout` (int seconds ≥ 1 or null, default **900**) caps a full suite execution. A check runs under whichever is lower: its own timeout, or whatever remains of the suite budget. Once that budget is exhausted, checks that never started are recorded **skipped** — neither run nor failed, and **a skipped check can never block completion**. Null means no suite budget — per-check timeouts only.
- **REQ-CONFIG-142** — `verifier.author_gate` (bool, default true): a designated role authors the suite once the technology stack settles and writes it into `verifier.checks`. False turns each such write into a proposal that needs approval before it lands. The setting stops mattering the moment `verifier.checks` holds a value: an already-declared suite is not authored a second time.
- **REQ-CONFIG-143** — `verifier.probe_timeout` (int seconds ≥ 1, default **30**) budgets one calibration probe and is deliberately independent of the suite budget.
- **REQ-CONFIG-144** — `verifier.max_repair_attempts` (int, default **2**) is how many extra passes a gated task is granted to fix what the suite reported; every pass is handed the failing output and re-runs the suite afterwards. Once those passes are used up the task terminates in a verification-failed state that **names the offending checks**, instead of looping on to the global iteration cap. **0** reports without retrying. The setting applies only while `gate_completion` is true.
- **REQ-CONFIG-145** — A check entry requires `name` (non-blank string) and `command` (non-blank string), and accepts `timeout` (int seconds ≥ 1, default **600**), `severity` (`blocking` or `advisory`, default `blocking`; an advisory result is reported and has no gating effect), `role` (`test`, `typecheck`, `lint`, `other`, or unset — unset means deliberately unstated), `cwd` (workspace-relative directory or unset, defaulting to the workspace root, which lets a single gate span several projects held in one workspace), and `failure_pattern` (string or unset, default unset — a regular expression the check declares so that a run recognizes a failure the command reported without failing its exit status). This document registers `failure_pattern` as a field of the entry, its type and its default, and holds no copy of what is done with it: that it is honoured for a check of role `test` and for no other role, that a check declaring one is recorded failed when the pattern matches whatever the exit status was, and that a check declaring none is recorded on its exit status alone are REQ-ORCH-123's. Being an accepted field is what keeps a check that declares one from being read as an entry with an unrecognized key.
- **REQ-CONFIG-146** — Check errors are raised **at load time**, each naming the offending check: blank name; blank command; blank `cwd` (with guidance to omit it for the root); an absolute `cwd` in either POSIX or Windows spelling; a `cwd` containing any parent-directory component after separator normalization; and a `failure_pattern` that is present but is not a usable regular expression, reported with the offending pattern text, so a typo in it fails loudly at load rather than silently matching nothing while a suite is running. A `cwd` that is inside the workspace but simply does not exist is a **different** condition, answered at run time rather than at load.
- **REQ-CONFIG-147** — Two check entries with the same name are rejected at load with a message naming the duplicate.
- **REQ-CONFIG-470** — `integration:` is a section-class key (REQ-CONFIG-047) holding one field, `validation_command` (string or null, default null), which is the only way the repository's own narrow validation is identified for worktree integration (REQ-GIT-156). Left null, no validation clause is produced and no validation runs. It is never inferred from the workspace's contents and never chosen by an agent, and this domain neither runs it nor gates on it: the load path validates its type and merges it per field like any other section, and the domain that owns integration decides what is done with it. It is distinct from `verifier.checks` (REQ-CONFIG-139), which this domain does gate on.

### Lifecycle hooks

- **REQ-CONFIG-148** — `hooks:` accepts two spellings: a mapping (`{enabled: …, entries: [...]}`) and a bare list, which is normalized to a mapping with that list as its `entries`. Any other type aborts the load with a message stating that a mapping or a list of entries was expected and naming the type received. Normalization happens before both validation and scope merging, so the shorthand never surfaces as a type error.
- **REQ-CONFIG-149** — `hooks.enabled` (bool, default true) is the master switch; the default only matters once entries exist. The product ships **no** hooks of its own.
- **REQ-CONFIG-150** — A layer that states `hooks.entries` supplies the entire hook list for that load; entries declared by lower layers are not added to it. A layer that states only `hooks.enabled` leaves the inherited list exactly as it stands.
- **REQ-CONFIG-151** — Each hook entry is stamped with its originating scope — exactly `default`, `global` or `workspace`, the vocabulary REQ-HOOKS-014 fixes — **during load, per scope, before merging**, because provenance is unrecoverable once a higher layer's list has replaced a lower one. Non-mapping entries pass through unstamped. An entry with a blank stamp is read as `default`.
- **REQ-CONFIG-152** — When a layer replaces the inherited hook list, the replaced entries are carried forward into `hooks.superseded_entries` (any already-superseded entries first, then the entries being displaced), so a trust gate retains the information. Non-mapping entries are filtered out of the carried list; when nothing would be carried, the section is unchanged. `superseded_entries` is loader-populated and never hand-written.
- **REQ-CONFIG-153** — After a workspace file has replaced a hook list declared in the global scope, every displaced global entry is still enumerable through `hooks.superseded_entries` and is still offered for trust review. Hook entries arriving with a checked-out repository therefore cannot remove a globally declared hook from the user's view, whether or not the repository's own entries are refused at the trust prompt. **A displaced entry never runs**: list replacement is the merge semantic and is not softened (REQ-CONFIG-150), so supersession is a disclosure, not a partial disabling. It is shown with the status `superseded`, which states that the entry was declared in a lower-precedence scope and replaced by a higher one and names the scope that replaced it; that status is evaluated ahead of every other in the precedence order of REQ-CONFIG-359 and its row carries no checkbox, since there is nothing about it for the user to switch. A trust decision recorded against a displaced entry is retained, so the entry returns with that decision intact if a later load leaves it active.
- **REQ-CONFIG-154** — The hook entry schema — which fields an entry accepts, which are required, the type and default of each, and the generated stable id that stands in for an entry with no name — is fixed by REQ-HOOKS-008, with the id's form fixed by REQ-HOOKS-018; this domain holds no copy of any of it and accepts no field of its own. What it adds is where an entry is written and how it gets there: entries are declared under `hooks.entries` in either scope's `agents.yaml` (REQ-CONFIG-148, REQ-CONFIG-150), the loader stamps each with its originating scope before merging (REQ-CONFIG-151), and the whole entry is validated at load rather than at the moment the hook would fire (REQ-CONFIG-158).
- **REQ-CONFIG-155** — A hook command **executes on the machine with the invoking user's own privileges and is not subject to the agent permission policy**. This is a security-relevant property of the feature that surfaces must present accordingly (REQ-CONFIG-355, REQ-CONFIG-356).
- **REQ-CONFIG-156** — How a matcher is evaluated is fixed by REQ-HOOKS-025, REQ-HOOKS-027 and REQ-HOOKS-029: the separators a candidate command line is divided at, the token comparison applied within a segment, the reading of an empty matcher, the reading of an unparseable one, and which facet of a call the matcher is tested against are all theirs, and this domain holds no copy of any of them and states no second division rule. What this domain adds is only the configuration surface: `matcher` is one of the hook entry fields of REQ-HOOKS-008, it is a string, its default is empty, and it is validated at load — an unusable pattern is rejected there rather than at the moment a hook would fire (REQ-CONFIG-158).
- **REQ-CONFIG-157** — The `event` vocabulary — the seven names, their division into tool events and lifecycle events, and the fact that no other name is valid in configuration — is fixed by REQ-HOOKS-001; the cap on how much of a hook's output is retained is fixed by REQ-HOOKS-037; and what a hook's exit status means for the call and for the loop is fixed by REQ-HOOKS-043 to REQ-HOOKS-045 and REQ-HOOKS-048. This domain holds no copy of any of them, states no event name of its own, states no second output cap, and assigns no meaning to any exit status. What it adds is that `event` is a required hook entry field written in the YAML surface and that a name outside the vocabulary is rejected at load (REQ-CONFIG-158).
- **REQ-CONFIG-158** — Hook entries are validated at load rather than at the moment a hook would fire. Which conditions make an entry invalid, the YAML path reported for each, the information each message must convey, and the reporting of several invalid entries at once are fixed by REQ-HOOKS-012; what a hook's exit status, its `required` flag and an overrun of its `timeout_seconds` do to the call are fixed by REQ-HOOKS-043 to REQ-HOOKS-048. This domain holds no copy of either and states no rule of its own for any of them. What it relies on that validation for is this domain's own severity contract: a hook entry that fails validation is **fatal** to the load and produces no configuration (REQ-CONFIG-233), so no surface of this domain ever holds a hook entry the owner would have refused, and no entry is silently dropped or repaired on the way through the layering. What this domain adds is that `enabled: false` keeps the entry in place in the declared list, so the positions the stable ids of REQ-HOOKS-018 are generated from do not shift for neighbouring entries (REQ-CONFIG-154).

### Checkpoints, initialization and project classification

- **REQ-CONFIG-159** — `checkpoints.enabled` (bool or unset, default unset) is three-valued: left unset it is on for isolated sessions and off for the rest; `true` turns it on for every session; **a written `false` stays off even when a session is isolated**.
- **REQ-CONFIG-160** — `checkpoints.max_per_session` (int ≥ 1, default **50**) is the number of checkpoints retained per session; older ones are pruned so the product's checkpoint references cannot grow without bound.
- **REQ-CONFIG-161** — `checkpoints.include_untracked` (bool, default true) includes files version control does not yet track, because a file the agent has only just created is among the changes a user is most likely to want reverted.
- **REQ-CONFIG-162** — `initialization:` is a section the product **writes back** into the workspace `agents.yaml`, not merely reads. Its fields are `completed` (list of task ids that ran successfully, default empty), `skipped` (list of task ids the user deferred, default empty), `last_run` (ISO-8601 UTC timestamp string or null), and `classification` (`code`, `non-code`, or null).
- **REQ-CONFIG-163** — A workspace reads as never initialized exactly when `initialization.last_run` is null and `initialization.completed` and `initialization.skipped` are both empty. A finished initialization pass always records its timestamp in `last_run`, including a pass that added no id to either list, so such a workspace does not read as never initialized.
- **REQ-CONFIG-164** — A task counts as resolved when it appears in either `completed` or `skipped`.
- **REQ-CONFIG-165** — `project_init.source_extensions` (list of strings) is the extension set that decides whether a workspace counts as a code project. The shipped value is exactly these 23 entries: `.py`, `.js`, `.ts`, `.jsx`, `.tsx`, `.rs`, `.go`, `.java`, `.c`, `.cpp`, `.h`, `.hpp`, `.rb`, `.php`, `.swift`, `.kt`, `.scala`, `.cs`, `.fs`, `.ex`, `.exs`, `.r`, `.jl`. When no file in the workspace carries one of them, the workspace is classified `non-code` and code-oriented onboarding is skipped. Stating the key **substitutes** the whole list; it never adds to the shipped one. Entries are normalized before they are compared: surrounding whitespace is stripped, letters are lower-cased, and a leading dot is supplied when the author omitted it, so `py`, `.PY` and ` .py ` are all read as `.py`, while an entry that reduces to nothing or to a bare dot is dropped.

### Portable skills

- **REQ-CONFIG-166** — `skills.enabled` (bool, default true) is the master switch. It decides whether portable skills are attached to agents at the point of **creation**; changing it leaves agents that are already running untouched. The same holds for every per-skill policy of REQ-CONFIG-167 and REQ-CONFIG-168: the master switch and the per-skill policies are read once, when an agent is created, so a policy changed mid-session governs the next agent created and never retracts or attaches a skill on an agent already running. There is no mid-session re-attachment path and the master switch does not gate one.
- **REQ-CONFIG-167** — `skills.overrides` (map from skill name to load mode, default empty) accepts exactly the values `off`, `name-only`, `user-invocable-only`, `on`.
- **REQ-CONFIG-168** — `skills.invocation_overrides` (map from skill name to invocation mode, default empty) accepts exactly the values `default`, `manual-only`, `auto-only`.
- **REQ-CONFIG-169** — A layer overlays the `skills` block per field and per skill name: stating `enabled` leaves both override maps inherited, and stating one skill's policy leaves every other skill's inherited policy in place (REQ-CONFIG-042, REQ-CONFIG-048). To return a skill to a policy the lower layer overrode, the higher layer states that policy explicitly (REQ-CONFIG-258).
- **REQ-CONFIG-170** — Skill-name collisions across scopes resolve **workspace wins**; the losing paths remain disclosable to the user (REQ-CONFIG-347).

### Display and transcript settings

- **REQ-CONFIG-171** — *Withdrawn.* Its only subject was the leader key of a text-mode interface, and the product has no text-mode interface; `tui` is consequently not a recognized top-level key and a file that still carries one is reported as an unknown key and contributes nothing (REQ-CONFIG-040, REQ-CONFIG-233). No capability is lost: keyboard access to the desktop application is owned by the desktop-shell domain, not configured from `agents.yaml`.
- **REQ-CONFIG-172** — The display block is the top-level `display:` key and accepts `show_tool_results` (bool, default true), `tool_result_max_lines` (int ≥ 0, default **10**, where **0** means no limit), `show_tool_inputs` (bool, default true) and `tool_input_max_lines` (int ≥ 0, default **2**, where **0** means no limit). These four values govern what the desktop transcript draws on a tool row (REQ-CHAT-166); eliding a tool result in the display never removes content from the model's context and never removes it from the session record. `display` is a **section-class** key (REQ-CONFIG-047), so it merges across scopes per field like any other section and the settings surface reads it back on the next load (REQ-CONFIG-175, REQ-CONFIG-472).
- **REQ-CONFIG-173** — `transcript.max_in_memory_events` (int, default **100**, range **50–1000**): beyond this count the oldest events are evicted to an on-disk archive and replaced with page markers that can be loaded by scrolling back.
- **REQ-CONFIG-174** — `transcript.archive_page_size` (int, default **50**, range **10–200**) is the number of events per archive page.
- **REQ-CONFIG-175** — The display block is written into `agents.yaml` by the settings surface (REQ-CONFIG-472) and **is consumed by the load path**: a value written there is read back on the next load and survives a restart. Round trip is a contract — a display preference set on the settings screen, written to a scope's `agents.yaml` and re-loaded must come back on its control with the value the user chose, not with the built-in default. The same holds for the workspace-instruction injection switch (REQ-CONFIG-466).
- **REQ-CONFIG-466** — `inject_agents_md` (bool, default true) is a recognized top-level replace-if-not-null key (REQ-CONFIG-041) deciding whether the workspace's instruction files are prepended to an agent's prompt. It is merged, read back on every load, and settable from `agents.yaml` in either scope as well as programmatically. Left unstated it is on, which is why a workspace that has never configured it behaves as though the key did not exist.

### Tool-server (MCP) entries

- **REQ-CONFIG-176** — A tool server is declared as a named entry under the top-level `mcp_servers:` key of `agents.yaml`, in either scope, and is merged as a named-entry section (REQ-CONFIG-043). That is what this document fixes about it: that the entry lives on this YAML surface, under that key, and layers like any other named entry. The fields the entry accepts, their types and their defaults are fixed by REQ-MCP-001; this document holds no copy of them and accepts no field that requirement does not name, apart from the `enabled` field REQ-CONFIG-465 adds. What it relies on REQ-MCP-001 for is that an entry's field set is closed and validated before any of the entry-derived rules of this document are applied.
- **REQ-CONFIG-177** — Transport shape is enforced at load: `command` is required for `stdio`; `url` is required for `http` and for `sse`. Each violation is rejected with a message naming the missing field and the transport.
- **REQ-CONFIG-178** — `request_timeout` overrides the per-tool-call default of **300 seconds**.
- **REQ-CONFIG-179** — `tools` (list of tool descriptors, each with a name and an optional description defaulting to empty) caches the server's advertised surface.
- **REQ-CONFIG-180** — `disabled_tools` (list, default empty) hides tools from agents. It matches **original, server-reported** names. `tool_name_map` (map from original name to friendly rename, default empty) renames tools, and the rename is reflected in the prompt's tool-server section. Renaming is applied **after** disabling, so disabling must always be expressed with the original name.
- **REQ-CONFIG-181** — Three tool servers are declared in the built-in defaults: a web-search server on the `http` transport whose `url` embeds an environment-variable placeholder for its API key (the same key the secrets surface of REQ-MCP-110 writes into `secrets.yaml`) and whose `request_timeout` is **600** seconds; a browser-automation server on the `stdio` transport launched at a pinned package version; and a code-intelligence server on the `stdio` transport, also at a pinned version. A language-server bridge is not among the defaults and remains declarable by a user like any other entry. The three entries are named `web_search`, `browser` and `code_intelligence`, and the search server's `url` placeholder names the environment variable `ROTARIS_SEARCH_API_KEY`, which is the same name the desktop secrets surface (REQ-MCP-109, REQ-MCP-110) writes into `secrets.yaml` under the `web_search` entry. Until that key is supplied the search entry's `url` still carries an unresolved placeholder, so the entry is present but marked unavailable and no request is sent to it (REQ-CONFIG-225). Of the three, only `code_intelligence` is enabled by default, because it is the only one that neither sends anything off the machine nor requires a credential; `web_search` and `browser` are declared with `enabled: false` (REQ-CONFIG-465), and a user turns each on deliberately. Which third-party services fill the three roles — the endpoints, commands, package identities and pinned versions — is left to the implementation and may change between releases; whichever services are chosen are declared under these three names, on the transports and with the timeout stated above, and a user replaces any of them by declaring an `mcp_servers:` entry of the same name.
- **REQ-CONFIG-465** — A tool server entry SHALL accept an `enabled` field of boolean type, defaulting to `true` where absent. Given an entry with `enabled: false`, when configuration resolves, then the entry is present in the resolved configuration and observable with its provenance (REQ-CONFIG-222), no connection to it is attempted, and none of its tools enter the tool registry or any tool-name validation set (REQ-CONFIG-231). Setting the field to `true` in a higher layer enables the entry under the named-entry merge rule of REQ-CONFIG-043 without the entry having to be restated.
- **REQ-CONFIG-182** — The code-intelligence server's default `args` carry no project-root argument; the directory it is to operate on is supplied when the server is launched, so a session running inside an isolated checkout gets that checkout rather than the workspace root. A configuration that does state a project root in `args` binds the server to that one directory for the whole session. The product withdraws **no** tool of its own in that case: it does not inspect a third-party server's advertised surface for tools it judges to be about project selection or configuration, and it never hides a published tool by guessing at its purpose. A user who wants such tools hidden names them in that entry's `disabled_tools` (REQ-CONFIG-180), which is the one mechanism for the job and works the same for every server; the names are the server's own, and the user reads them from the server's advertised surface (REQ-CONFIG-179).

### Requirements-board configuration

- **REQ-CONFIG-183** — Every model under `requirements:` **forbids unknown keys**: an unrecognized key anywhere in this block is a hard load failure. This is the opposite of the top-level policy, where an unrecognized key is silently dropped (REQ-CONFIG-040). The section also validates on assignment. That rule is **unweakened** for a key this specification has never defined — one the user mistyped, or one something other than this product wrote — because this block drives runs nobody is watching (REQ-CONFIG-198), and quietly ignoring a key here would let such a run proceed under settings its author believed they had given it. What such a failure conveys to the user, and what recovers from it, is REQ-CONFIG-478's and is not restated here.

  **One case is carved out of that rule, and the reason is what bounds the carve-out.** A key this specification itself defined and has since withdrawn, and a key this specification names as not a configuration key of this domain, SHALL NOT fail the load. Such a key is **reported and ignored**: it contributes nothing to the merged configuration, every other key in the file is loaded exactly as though it were absent, and the workspace opens. This is a deliberate departure from the rule above rather than a boundary of it, and it is stated with its grounds so that it is not later read as an inconsistency to tidy away. An unknown key a stranger or a slip of the keyboard put in the file, and a withdrawn key **this product solicited** — shipped, documented as a key, and invited the user to write — are not the same case, and treating them alike turns this product's own deprecation into the user's outage. In the **global** scope the two are not even comparable in cost: one line in one file would stop *every* workspace opening at once, and no surface of the product is reachable from that state to repair it, the settings screen that edits that very file included. The carve-out reaches exactly the two kinds of key named in its first sentence — one this specification defined and withdrew, and one this specification names as not a configuration key of this domain — and nothing else: not a key that merely resembles a withdrawn one, not a key some other product withdrew, and not any other fatal condition of REQ-CONFIG-233.

  **What the report conveys** is fixed here, because a reported-and-ignored key is not a fatal failure and REQ-CONFIG-478's floor does not reach it. It identifies the file by its full path and by which scope it belongs to (REQ-CONFIG-001) and identifies the key by its full path within that file; it conveys that the key was **withdrawn rather than mistyped**, so that a user does not go looking for a spelling error that is not there; it conveys what became of what that key configured — for `store_subpath`, that delivery records are no longer files in the workspace and that no configuration key names a location for them (REQ-CONFIG-192); for `worktree_subpath`, that requirement-unit checkouts are placed at a location this domain registers no key for (REQ-CONFIG-194, REQ-GIT-137) — and it conveys that the key is being ignored and that the rest of the configuration loaded, so that a user is not left to guess what the report cost them. It is a warning that does not interrupt the load (REQ-CONFIG-233), is raised once per offending key per load, and its wording is left to the implementation. This rule is written against the property *this specification names the key* — as withdrawn, or as one this domain does not register — and not against a list, so a key withdrawn by a later amendment is covered without this requirement being amended.

  **Nothing here licenses the product to change the user's file.** The key stays exactly where the user wrote it; nothing is removed, rewritten, or repaired on their behalf; and removing it stays theirs to do whenever they choose, which is a choice a file leaves open and a store would not (REQ-CONFIG-477, ground 3). The difference this carve-out makes is that they can now do it from inside a running product, with their workspace open, rather than from outside a product they cannot start.
- **REQ-CONFIG-184** — With no `requirements:` block in any scope the board is still available and usable: `requirements.enabled` is true, no source is declared so the built-in source applies (REQ-CONFIG-185), and `requirements.scheduling.mode` is `manual`.
- **REQ-CONFIG-185** — `requirements.enabled` (bool, default true); false removes the board from view and halts refreshes and requirement runs alike. `requirements.sources` (list, default empty); leaving the list empty selects the built-in source for any workspace that has a store. The list **replaces** rather than extends.
- **REQ-CONFIG-186** — Two requirement sources with the same `id` are rejected at load with a message explaining that attribution and collision reporting need unique ids.
- **REQ-CONFIG-187** — A requirement source entry accepts these fields. `id`: string, required, non-blank, unique across sources. `type`: one of `reqtocode`, `markdown`, `yaml`, `json`, default `reqtocode`; any other value is rejected at load. `enabled`: bool, default true, where false keeps the entry in the file while excluding it from refreshes and from requirement runs. `root`: workspace-relative string or null. `glob`: string or null, required when `type` is `markdown`, `yaml` or `json`, optional for `reqtocode`. `writable`: bool or null, where null leaves the decision to the adapter selected by `type`. `fields`: the field-path map of REQ-CONFIG-188. `options`: map of string to string, default empty, handed to the adapter unaltered and replaced wholesale by any layer that states it.
- **REQ-CONFIG-188** — The requirement field map defaults are: `id` → `frontmatter.id`; `title` → `heading` (the document's first top-level heading); `description` → `body`; `lifecycle` → `frontmatter.status`; `req_type` → `frontmatter.type`; `parent` → `frontmatter.epic`; `relations` → empty map (relation kind to field path, replaced not merged); `trace_required` and `test_required` → unset. Leaving `id` unmapped is rejected as a configuration error; no identifier is ever invented on the user's behalf. Where a path is unset, the reading defaults are: lifecycle `draft`, type `product`, a flat (parentless) store, and trace/test both required.
- **REQ-CONFIG-189** — `requirements.refresh`: `incremental` (bool, default true; false makes every pass re-read everything and exists for diagnosis); `debounce_ms` (int ≥ 0, default **400**, so a burst within the window causes one evaluation); `triggers` (list, default all eight of `commit`, `merge`, `source-edit`, `branch-switch`, `test-run`, `run-completion`, `worktree-integration`, `manual`; **replaces** the default list); `max_workers` (int ≥ 1, default **1**, so refreshes serialize and consumers never observe a half-built index); `timeout_seconds` (float > 0, default **120.0**; overrunning it marks the refresh failed and **keeps the previously built index intact**); `watch_filesystem` (bool, default true; false confines refreshing to the other triggers plus explicit requests).
- **REQ-CONFIG-190** — `requirements.evidence`: `follow_source_flags` (bool, default true — the source's own flags win and the per-type blocks apply only where the source says nothing); per-type obligation blocks for `product`, `technical` and `epic`, each with the five obligations `implementation`, `test`, `verification`, `execution`, `integration` valued `required`, `optional` or `not-applicable`. Defaults: product = implementation/test/verification required, execution/integration optional; technical = the same but integration `not-applicable`; epic = **all five `not-applicable`**, since an epic asserts nothing itself.
- **REQ-CONFIG-191** — `requirements.evidence.stale_on_lost_ancestor` (bool, default true): once the commit a verification was recorded against has fallen out of the current head's ancestry, that evidence reads **stale instead of failed**. `stale_on_trace_move` (bool, default true): a trace or covering test that has moved or disappeared renders the evidence stale **even though the requirement text was never touched**.
- **REQ-CONFIG-192** — `requirements.delivery` configures the requirement **delivery store**, which holds operational records only; requirement text is never written there. That store is not configuration and REQ-CONFIG-477's boundary does not reach it: only this application reads a delivery record, the records are high-volume, queried and transactional, and the delivery state, the requirement's history, this requirement's `history_limit` prune and the audit entry are written **together, indivisibly**, so no failure can leave a state recorded without its audit entry or an audit entry for a state that was never recorded. The store therefore holds records rather than files, and **no key of this domain names a directory, a file or a document format for it**; `store_subpath`, which named the directory beneath the workspace configuration directory that once held delivery records, tombstones and audit entries, is withdrawn with the directory it named and is no longer a recognized field — a file that still states it is **reported and ignored** rather than rejected, the workspace opening and every other key in the file loading as though it were absent, which is the same consequence REQ-CONFIG-194 records for `worktree_subpath` and is stated here rather than discovered. It is not treated as an unknown key under `requirements:` would be, precisely because an earlier statement of this specification invited it; that departure, its grounds, and what the report conveys are REQ-CONFIG-183's and are not restated here. This requirement states the withdrawal and what became of what the key configured; that one states what the user is told and that they keep their workspace. The remaining fields are unchanged in meaning. `schema_version` (int ≥ 1, default **1**) is written into every record produced, and a record whose `schema_version` exceeds the supported version is reported as unsupported and is not interpreted. `retain_tombstones` (bool, default true) keeps the ids of requirements the sources have stopped declaring, so a retained id is never issued again; this is the delivery store's own record of retired ids and is a different thing from the retired-identifier log the traceability toolchain keeps as a file in the user's repository (REQ-TRACE-130, REQ-TRACE-513). `audit_trail` (bool, default true) records each state transition with the actor, the time, and the stated reason. `history_limit` (int ≥ 1, default **200**) is the number of history entries kept per requirement; older entries are pruned. The reader supports exactly the versions **1 through the configured `schema_version`**, which as shipped is the single version `1`; a record whose `schema_version` is higher is reported as unsupported and is not interpreted, and a record whose value is below 1, absent, or not an integer is reported as unreadable. Neither is rewritten, migrated in place, or deleted — a record this build cannot interpret is carried untouched rather than repaired. Such a record is reported in three places and nowhere else: the requirement it belongs to is listed on the board with its delivery history shown as unavailable for that reason rather than being hidden or shown as empty; a message identifying the record and the version it carries is written to the session log; and the same message is returned by any surface that reads delivery records. A workspace holding an unsupported record still opens and still runs.
- **REQ-CONFIG-193** — `requirements.execution` branch naming: `branch_template` (default `rotaris/req/{requirement_id}/{unit_id}`, placeholders `{requirement_id}`, `{unit_id}`, `{slug}`; a namespace distinct from session branches, which use `rotaris/session/<id>`) and `integration_branch_template` (default `rotaris/req/{req}/integration/{id}`, placeholders `{req}` and `{id}`, with the older spellings `{requirement_id}` and `{integration_id}` still accepted).
- **REQ-CONFIG-194** — `requirements.execution` remaining fields. `worktree_subpath` is **not** among them and is not a configuration key. What this document owns here is the configuration surface and nothing else: exactly one key names an isolated-checkout storage subpath, `worktree_storage_subpath` (REQ-CONFIG-068, REQ-CONFIG-010), and that key names the per-session one; no key of this domain names the directory holding requirement-unit checkouts. Where requirement-unit checkouts are placed is not configurable and is not stated here — REQ-GIT-137 fixes that location, and REQ-GIT-138 relies on this domain registering no key for it. A `worktree_subpath` key written under `requirements.execution` is a key this specification names as not a configuration key of this domain, so a file that states it is **reported and ignored** rather than rejected and the workspace opens; what that report conveys, and why this case is not treated as an unknown key would be, are REQ-CONFIG-183's and are not restated here. The fields are: `target_branch` (string or null; null selects whichever branch was checked out when the run began); `run_check_suite` (bool, default true — a workspace with no suite yields a "not verified" outcome); `run_reqtocode_verification` (bool, default true); `retry_limit` (int ≥ 0, default **1**; once spent, the requirement moves to blocked and the most recent failure is named; 0 means no retry at all); `keep_failed_worktrees` (bool, default true — deleting them is something only the user does, never the scheduler); `unit_timeout_minutes` (int ≥ 1, default **120**; on overrun the unit is failed with an explicit reason instead of being left to run without end).
- **REQ-CONFIG-195** — `requirements.execution.decomposition`: `enabled` (bool, default true; false collapses each requirement into a single unit); `max_units` (int ≥ 1, default **6**; a plan proposing more units than that is **refused outright, not quietly trimmed**); `require_confirmation` (bool, default false — either way the plan is stored and can be inspected).
- **REQ-CONFIG-196** — `requirements.scheduling`: `mode` (`manual` or `automatic`, default `manual`); `max_concurrent_units` (int ≥ 1, default **2**, counted across every requirement — work that meets the cap **waits in the queue and is never turned away**); `max_concurrent_requirements` (int ≥ 1, default **2**, independent of unit count); `avoid_file_conflicts` (bool, default true, delaying units whose predicted file sets overlap instead of letting the collision surface at integration time); `priority_order` (list, default `critical`, `high`, `normal`, `low`, `none` — priority decides queue position only and **cannot promote work ahead of something it depends on**); `auto_release_dependents` (bool, default false, so clearing a blocker makes the dependent eligible for scheduling while the decision to start it stays with a person); `queue_limit` (int ≥ 0, default **0**, where **0 means unbounded**).
- **REQ-CONFIG-197** — `requirements.board`: `default_sort` (`priority`, `id`, `state`, `health` or `epic`, default `priority`, with ties broken by `id` so the order is deterministic); `group_by` (`state`, `epic` or `source`, default `state`); `filters` (a sub-block of `epics`, `sources`, `lifecycles`, `states` and `priorities` lists plus a `text` string, every one of them empty by default, so a board whose filters have never been set shows everything on first open; whatever the block holds is applied when the board opens, and being configuration it survives a restart); `show_deprecated` (bool, default false — deprecated requirements are read in and marked deprecated either way, the flag deciding only whether they are listed by default); `live_updates` (bool, default true); `card_limit` (int ≥ 0, default **0**, where **0** means no limit). Because a section overlay is recursive (REQ-CONFIG-048), a layer that states one field of `board:` overlays that field alone: an unrelated `board:` edit leaves `filters` and every other sibling exactly as the lower layer left them, and a stated `filters` sub-block likewise overlays only the lists it names.
- **REQ-CONFIG-198** — `requirements.personas` maps five board activities to role names: `source_discovery`, `decomposition`, `impact_analysis` and `migration_analysis` default to `requirements-engineer`, and `execution` defaults to `coding-agent`. A mapped name matching no configured role is not a load error; the workspace's `default_persona` is used instead at the moment that role is needed (REQ-CONFIG-233), so an unrecognized name can never make a workspace fail to open. `requirements.human_in_the_loop`: `escalate` (list, default all seven of `contradictory-requirements`, `unclear-scope`, `competing-requirements`, `breaking-change`, `unclear-superseding`, `risky-migration`, `architectural-decision`; a stated list replaces the default, so exactly the listed conditions interrupt a run and no condition outside it does); `require_review_before_done` (bool, default true; false lets a run that has passed verification close the requirement without a person); `allow_force_done` (bool, default false; every use is recorded in the audit trail with the actor and the stated reason); `confirm_migration_worklist` (bool, default true; false leaves the worklist computed and stored while it stops interrupting the board, and the confirmation is refused for any actor that is not an identified person whatever this flag holds); `confirm_source_writes` (bool, default false); `answer_timeout_minutes` (int ≥ 0, default **0**, meaning wait without limit; on expiry the question is recorded as unanswered and no answer is ever supplied on the user's behalf). This field and the desktop preference `requirements/answerWaitSeconds` (REQ-CONFIG-405, REQ-CONFIG-413) each govern a disjoint set of runs, so exactly one applies to any given run and the two can never disagree observably: **a run a person started from the desktop application takes its budget from `requirements/answerWaitSeconds` and this field is not consulted; every other run — a run the board scheduled, and any other run started without a person present — takes its budget from `answer_timeout_minutes`.** How long an unattended run waits is a property of who is watching it, which is why the desktop's own value wins for runs that desktop starts, exactly as the released-run elevation is a desktop preference and not a workspace field (REQ-CONFIG-408). Both spell "no limit" as zero. Any surface that displays the budget states which of the two is in force for the run it is describing. `requirements.change`: `analyze_changes` (bool, default true; false parks each change in a needs-update state until a person handles it); `adopt_hash_after_verification` (bool, default true — a verdict of no behavioural impact adopts the new hash only once verification has passed, never on the verdict alone); `propagate_evidence_loss` (bool, default true — a deleted covering test or a dropped trace moves the requirement out of done with no textual analysis step); `gate_on_dependencies` (bool, default true); `report_dangling_dependents` (bool, default true — removing a requirement surfaces its dependents as dangling and never deletes them). An actor counts as **a person** exactly when the action arrives through an interactive surface in direct answer to a prompt the product raised for that specific action, with that surface attached to a window. An action arriving from an agent, from a hook, from a scheduled or otherwise unattended run, or from a replay of recorded events is never a person, whatever it claims about itself, and a confirmation reaching one of those hosts is refused and recorded as unanswered rather than assumed. The audit record names the operating-system account the interactive session was running under together with the surface the answer came from; the product maintains no identity of its own and asks for none.

### Provider/model discovery snapshot

- **REQ-CONFIG-199** — The snapshot is a YAML document in the global scope written with insertion order preserved (not alphabetized) and with unknown keys forbidden at every level.
- **REQ-CONFIG-200** — The snapshot carries `version` (int, default 1). Any value other than 1 is rejected with an "unsupported version" error: the format is deliberately **not** forward compatible.
- **REQ-CONFIG-201** — Each snapshot provider carries an id, a required display name, an optional family and base URL, a **required** authenticated flag, a list of discovered models, five optional slot suggestions (`default_summary_model`, `large_model`, `medium_model`, `small_model`, `fallback_model`) and a required discovery timestamp. Duplicate model ids within one provider are rejected.
- **REQ-CONFIG-202** — Each snapshot model carries a required id, an optional display name, capability, limit and pricing maps, and a **required** discovery timestamp that must be an ISO-8601 UTC string; a non-string value is rejected naming the field.
- **REQ-CONFIG-203** — Providers whose authenticated flag is false contribute **nothing** to the merged configuration — not even entries in `unavailable_models`.
- **REQ-CONFIG-204** — Each authenticated provider's non-null slot suggestions are contributed to the snapshot layer. Where two or more authenticated providers suggest a value for the same slot, exactly one of those suggestions reaches the merged configuration, chosen deterministically: authenticated providers are considered in ascending code-point order of their provider id, and the **first** provider offering a non-null suggestion for a slot wins it; later suggestions for that slot are ignored. The order is therefore independent of the order the snapshot happens to store providers in, of the order the user signed in, and of the machine — the same snapshot always produces the same slot values. Ordering among providers inside this layer settles nothing about ordering between layers, which stays fixed and total (REQ-CONFIG-031, REQ-CONFIG-449).
- **REQ-CONFIG-205** — Each discovered model becomes a `models:` entry keyed by its qualified id, **unless** the user already declared that key in YAML with both `provider` and `model_id` set — that counts as a complete override and discovery skips the key entirely.
- **REQ-CONFIG-206** — A discovered model classified unavailable, **and** never mentioned by the user in YAML, is recorded under `unavailable_models:` instead of `models:`, which keeps any client construction from reaching it while still letting pickers display it alongside the reason. The asymmetry is deliberate: once a user names a model anywhere in YAML it stays a configured model, even where the provider marks it unavailable.
- **REQ-CONFIG-207** — Fields synthesized per discovered model: `provider` (literally `deepseek` or `claude-code` for those two providers, otherwise `openai`), `model_id` (the id with a leading `<provider>/` prefix stripped when present), `auth_provider` (the provider id), `base_url` (the provider's, falling back to the catalog provider's default), `max_input_tokens`/`max_output_tokens` from the model's limits, `api_key` and `api_key_env` both null, `api_mode` (only when the discovered value is exactly `chat` or `responses`, otherwise null), and the two per-token prices from the model's pricing map.
- **REQ-CONFIG-208** — An `unavailable_models:` record carries the model id, a display name, the sign-in provider, a machine-readable reason code, one reason sentence in plain language resolved once at load so that every surface shows identical wording, and an optional provider-supplied detail that is trimmed and omitted when blank. The record's shape differs from a `models:` entry and carries no field from which a client could be constructed (REQ-CONFIG-454). The reason-code vocabulary is **closed** and is exactly `not-entitled`, `deprecated`, `retired`, `region-restricted`, `quota-exceeded`, `unsupported`, `unknown`. It is a machine-readable contract: a surface may branch on these values. A provider-supplied classification that is not one of them is recorded as `unknown` and the provider's own wording is carried in the optional detail, so nothing the provider says is lost and no unpublished code ever reaches a consumer.

### Snapshot read/write semantics

- **REQ-CONFIG-209** — A missing snapshot file reads as absent, not as an error.
- **REQ-CONFIG-210** — Any read failure — I/O error, YAML error, schema violation — is surfaced as a single error naming the snapshot path and carrying the underlying detail, and the cached entry for that path is dropped. The configuration load catches it and continues (REQ-CONFIG-021).
- **REQ-CONFIG-211** — Within one running process, an updated `project_settings.yaml` is observed on the next load whenever its modification time or its byte size differs from what the previous read saw. A rewrite that leaves both unchanged is **not** observed before the process restarts, and that is accepted rather than defended against: the product's own snapshot writer always advances the file's modification time (REQ-CONFIG-212), so every rewrite the product itself performs is observed, and the unobserved case needs an external writer that deliberately restores both the previous timestamp and the previous byte size. No content hashing is performed on this path.
- **REQ-CONFIG-212** — Snapshot writes are atomic (staged beside the target, then swapped), create missing parent directories, set mode `0644`, leave the swapped-in file's modification time at the moment of the write so the change is always detectable (REQ-CONFIG-211), leave no temporary file behind, and drop the cached entry for that path afterwards.
- **REQ-CONFIG-213** — Before a snapshot is written the payload is examined field by field and the write is **refused**, naming the dotted path of the offending field, where it would persist a credential; this is the same screen REQ-PROVIDER-086 states from the writing side. A key name triggers refusal when it meets the secret-looking key test of REQ-TOOLS-172, and additionally when it carries the segment `session` or contains `ghu_` anywhere within it — two triggers this screen adds because a persisted catalog must carry less than a rendered line of text may. A string value triggers refusal when it begins with one of the credential value prefixes of REQ-TOOLS-171. Neither the key test nor the prefix list is restated here; what this requirement relies on them for is that both comparisons ignore letter case, so `api_key`, `apiKey` and `API-KEY` all trip the key test and a value beginning `eyJ` trips the `eyj` prefix. Keys the snapshot format itself requires are exempt, since the document could otherwise never be written at all: the two per-token price keys beneath a `pricing` parent, and the token-limit keys beneath a `limits` parent, which REQ-CONFIG-202 requires and REQ-CONFIG-207 reads back — both carry public metadata. Those two are the **complete** exempt set and no further key is exempt: a snapshot field added later that trips the screen is renamed so that it does not, rather than added to this list, because every exemption is a hole in a check whose whole purpose is to be unconditional. The provider `authenticated` flag (REQ-CONFIG-201) needs no exemption, its single segment under REQ-TOOLS-172 being `authenticated` and not `auth`.

### Secrets

- **REQ-CONFIG-214** — `secrets.yaml` is a two-level mapping: tool-server name → environment-variable name → value. It may exist in either scope.
- **REQ-CONFIG-215** — Global and workspace secret files merge **per key within a server**: a workspace file that sets one key for a server does not discard the global file's other keys for that same server.
- **REQ-CONFIG-216** — Secret writes are atomic and create the target directory when missing. On any failure the staged file is removed and the failure is reported. Every write leaves `secrets.yaml` at mode `0600` — owner read and write, no group or other bit ever set — and applies that protection explicitly on every write rather than letting the file inherit whatever mask or parent directory happens to be in force. On a platform with no POSIX file mode, no mode bit is set or reported and the protection is instead the explicit owner-only access control REQ-PROVIDER-016 fixes for the credential store, which is cited here and not restated. This is deliberately **not** the `0644` that REQ-CONFIG-444 and REQ-CONFIG-212 fix for ordinary configuration, and the reason is the file rather than the domain: `secrets.yaml` is the one file of this document's configuration set that holds credentials by design (REQ-CONFIG-007), so it is protected by what it carries and not by the class of file it is. Nor is the platform-default fallback REQ-CONFIG-444 permits available here — leaving a platform's own default in place is what this requirement forbids. Where the required protection cannot be applied the write does not happen: the staged file is removed and the failure is reported on this requirement's own terms above, so no secret is ever left on disk at a weaker protection than this requirement fixes.
- **REQ-CONFIG-217** — Setting a secret creates the server's sub-map when absent. Unsetting a single secret reports whether anything was removed and **writes nothing** when the key did not exist; removing a server's last key removes the server entry entirely. Unsetting all of a server's secrets reports the count removed and writes only when something was removed.
- **REQ-CONFIG-218** — Stored secrets for a tool server are overlaid **after** environment expansion, so a stored secret always beats the shell environment for the same key.

### Third-party discovery and placeholder expansion

- **REQ-CONFIG-219** — A discovered file's server map is read from a `mcpServers` key, falling back to a `servers` key — the cross-client interoperability point. A non-mapping value at either yields nothing, without a warning.
- **REQ-CONFIG-220** — A discovered server name must begin with an ASCII letter and may otherwise contain only ASCII letters, digits, underscores and hyphens; a name outside that shape is skipped with a warning naming both the name and the file. A non-object entry is skipped with a warning. Any failure while building a single entry skips **that entry only**, with a warning naming the server and the file.
- **REQ-CONFIG-221** — For a discovered entry with no explicit `type`, the transport is inferred: `http` when a `url` is present, otherwise `stdio`. An HTTP or SSE entry carries `url`, `headers`, `env` and `cwd`; a stdio entry carries `command`, `args` (defaulting to empty), `env` and `cwd`. Discovered entries therefore never set `request_timeout`, `disabled_tools`, `tool_name_map` or a cached tool list — those are configuration-file-only.
- **REQ-CONFIG-222** — Every tool server in the final configuration carries a provenance value observable to the user: `yaml` when the name appeared in either scope's `agents.yaml` `mcp_servers:` block (the union of both scopes, determined before the merge), otherwise the discovery source tag (`discovered-project` or `discovered-user`), otherwise `default`.
- **REQ-CONFIG-223** — There is no blanket environment-variable override mechanism over configuration keys. Environment variables enter configuration at four narrow points only: a tool server's `env` values, a tool server's `url`, discovered-file placeholders, and a model entry's `api_key_env`.
- **REQ-CONFIG-224** — In a configured tool server's `env` values, the placeholder pattern is **anchored**: only a value that is entirely `${VAR}` is expanded. `prefix-${VAR}` is preserved as a literal string. When the named variable is absent from the environment, **the key is omitted from the resolved environment entirely** — the literal placeholder is never handed to the server process. Non-placeholder values are preserved verbatim.
- **REQ-CONFIG-225** — In a configured tool server's `url`, the placeholder pattern is **unanchored**, so placeholders embedded within the address are substituted in place. The resolution order is shell environment first, then stored secrets, with the later overriding the earlier. A placeholder that neither source resolves is **left in the address literally** — it is never replaced with an empty string, because an address silently shortened by a missing key can reach an unintended host — and a warning is emitted naming the tool server, the variable and the file the entry came from. An entry whose resolved `url` still carries a placeholder is retained in the configuration and marked unavailable, so no request is ever sent to it and any attempt to use it is refused with a reason naming the unresolved variable. An unresolved placeholder never fails the load.
- **REQ-CONFIG-226** — Discovered files use a different placeholder dialect, applied to every `env` value and to `cwd` (which is additionally path-normalized): `${workspaceFolder}` expands to the workspace root path; `${env:NAME}` expands to the named environment variable **or the empty string when absent**; any other placeholder is left literally in place and logged as unknown.
- **REQ-CONFIG-227** — A discovered server entry may name an `envFile`. A relative path resolves **against the directory of the discovered file**, not the workspace. The file is read with a minimal dotenv grammar: blank lines and lines beginning with `#` are skipped; lines without `=` are skipped; key and value are trimmed; a value wrapped in matching single or double quotes is unquoted by one layer; later duplicates win. An unreadable file yields nothing with a warning naming the file.
- **REQ-CONFIG-228** — Values from an `envFile` are overlaid by the entry's explicit `env` map: an explicit entry beats the file.

### Validation and error reporting

- **REQ-CONFIG-229** — Validation has exactly two stages with different failure modes. **Schema validation** raises and is fatal: structural and typing problems abort the load. **Referential validation** returns a list of human-readable messages and **never raises**; an empty list means valid, and callers decide what to do with the list.
- **REQ-CONFIG-230** — Referential validation reads the discovery snapshot to determine whether any provider is configured; **any** failure reading it is swallowed and treated as "no snapshot". When no provider is present, an actionable sign-in hint is appended to the relevant messages; when a provider is present the messages stay terse. A user who has never signed in therefore gets guidance while a signed-in user gets a plain report of a genuine misconfiguration.
- **REQ-CONFIG-231** — Referential messages are produced in this order. An empty `models:` map reports that no models are configured, with the sign-in hint appended per REQ-CONFIG-230. Then, per role: `model` naming no configured model; `summary_model` naming no configured model, checked only where one is stated; a `delegates_to` entry naming no configured role; an `mcp_servers` entry naming no configured tool server; an `mcp_tools` key for a server the role does not list in `mcp_servers`, since such a grant confers nothing and must not read as a working restriction; a tool named more than once across `tools` and `custom_tools` taken together, reported sorted; and a name in `tools` that is neither an accepted public tool name nor the name of a configured tool server, reported together with the sorted list of accepted names. Tool names that exist for internal use only are outside the accepted set and are therefore reported by that last rule. The accepted set is exactly the public tool-name registry REQ-TOOLS-001 fixes: this specification fixes the validation rule, the order the messages are produced in and the requirement that the message carry the accepted names sorted, and reads the name set from that registry rather than restating it, so a name added there is accepted here with no change to this document. That registry also carries the per-tool capability declaration of REQ-TOOLS-001 — whether each name reads workspace files, writes workspace files, or runs commands — which this document neither restates nor varies. What this requirement relies on it for is only that the registry it validates names against is the same registry a rule elsewhere resolves a capability against, so a name this validation accepts always carries a declaration and a name it rejects never reaches one; a requirement in any domain that resolves a rule against a tool's capabilities cites REQ-TOOLS-001 for the declaration itself rather than this requirement, which fixes no capability of its own.
- **REQ-CONFIG-232** — Remaining referential rules: a `default_persona` naming no existing role; `default_summary_model` unset, or naming an unknown model; each of `small_model`, `medium_model` and `large_model` unset or naming an unknown model, and `fallback_model` naming an unknown model — it cannot be unset by the time this runs (REQ-CONFIG-067) — with the message naming both the field and the offending value; `compressor.model` naming an unknown model; and delegation cycles, reported as a cycle path sliced from the first repetition so that the message names the cycle itself rather than the whole traversal.
- **REQ-CONFIG-233** — The severity taxonomy across the whole load is a contract. **Fatal**: YAML syntax error; a primary configuration file that is not valid UTF-8 (REQ-CONFIG-462); non-mapping top level; a `hooks:` value that is neither mapping nor list; a bad hook event, matcher or blank command; a bad confinement mode, egress disposition or relative writable root; a bad check name, command, `cwd` or `failure_pattern` (REQ-CONFIG-146); a run-start mode outside `auto` and `plan` (REQ-CONFIG-476); a duplicate check name or duplicate requirement source id; an unknown key under `requirements:` that this specification has never defined (REQ-CONFIG-183). **Silent**: a missing or empty file; extra top-level keys in `models.yml` (REQ-CONFIG-004). **Warn and continue**: an unknown top-level key, and an unknown key inside a merged section other than `requirements`, each reported naming the key and the file and each contributing nothing (REQ-CONFIG-040); a key under `requirements:` that this specification itself defined and has since withdrawn, or that it names as not a configuration key of this domain, which is reported and ignored while the load completes and the workspace opens (REQ-CONFIG-183); a corrupt discovery snapshot; a circular startup-model alias chain; a reasoning override on an unconfigured or missing base model; a tool-server `url` left carrying an unresolved placeholder (REQ-CONFIG-225). **Coerce**: an unknown permission mode (runtime or per role) → `restricted`; an unknown non-interactive approval policy → behaves as `deny`; an unknown board role name → the workspace default role. **Report, not fatal**: every referential error. This requirement fixes the severity of each condition and nothing else; what a **fatal** outcome conveys to the user and what recovers from it is REQ-CONFIG-478's, and what the withdrawn-key warning conveys is REQ-CONFIG-183's.

### Startup configuration validation and recovery

- **REQ-CONFIG-234** — *Withdrawn.* Its whole surface was a `-c`/`--config` file named on a command line, and the product has no command-line invocation. No capability is lost: the layered configuration surface is the two scopes of REQ-CONFIG-001 and nothing else (REQ-CONFIG-031, REQ-STARTUP-111), a user who wants different configuration edits the global or the workspace file directly or through the settings screen (REQ-CONFIG-256, REQ-CONFIG-441), and the related question of letting a deliberate act rather than the accident of opening a checkout decide whose hooks may run is carried by the hook review of REQ-HOOKS-016.
- **REQ-CONFIG-235** — *Withdrawn.* It described how the file withdrawn by REQ-CONFIG-234 was folded in as a sixth layer; there is no sixth layer, and the fixed, total order of the five that remain is stated by REQ-CONFIG-031.
- **REQ-CONFIG-236** — *Withdrawn.* It described the post-merge passes applied to the file withdrawn by REQ-CONFIG-234 and the hook scope stamp that file carried. The passes themselves are unchanged and apply to every layer (REQ-CONFIG-035, REQ-CONFIG-036, REQ-CONFIG-037); the hook scope stamp vocabulary is exactly `default`, `global` and `workspace` (REQ-CONFIG-151, REQ-HOOKS-014).
- **REQ-CONFIG-237** — Schema failures are reported to the user as one line per problem: `<dotted.path>: <message>`, with an empty path rendered as `config`, and the framework's "field required" phrasing rewritten as "missing required field". If the conversion produces nothing, exactly one generic line stating the configuration is invalid is emitted — the list is never empty.
- **REQ-CONFIG-238** — Missing-field errors whose path is `models` → `<name>` → `<field>` are not reported one line per model. They are gathered and reported as exactly **two** lines: the first names every affected model, models in sorted order and each model's required fields in sorted order; the second states that a `models:` entry is replaced as a whole across configuration scopes, so an override of that model has to repeat `provider` and `model_id` even when only some other field is being changed.
- **REQ-CONFIG-239** — When at least one reported message starts with a model-incomplete prefix, mentions the incomplete-model phrasing, and names `model_id` or `provider`, the application reports that incomplete provider model overrides were detected, runs a model refresh across all providers **without prompting**, reports the refresh result, and **retries the configuration load once**. If the retry also fails, every message is reported to the user as a configuration error, each naming what it names, and the workspace does not open on that configuration; no internal diagnostic detail is shown with them.
- **REQ-CONFIG-240** — *Withdrawn.* It enumerated the flags of a run command, and the product has no command line. Every capability those flags carried is reached from the desktop: the workspace whose configuration directory is read through the chooser of REQ-SHELL-021 and REQ-STARTUP-041; resuming a session through REQ-SESSION-182 and REQ-SESSION-184; isolation, worktree use and the worktree branch name through the session-launch dialog of REQ-GIT-118 and REQ-GIT-158; the run's role and its iteration cap through the run overlays of REQ-CONFIG-263; access beyond the workspace through REQ-TOOLS-191 and the confirmation of REQ-CONFIG-327; and signing a provider out through REQ-CONFIG-383. The additional configuration file is withdrawn with REQ-CONFIG-234, and the machine-readable output format is withdrawn outright — a stream shaped for a script has no reader in a graphical application, and exporting a session's events is REQ-EVENTS-173.
- **REQ-CONFIG-241** — *Withdrawn.* It described two flags of REQ-CONFIG-240. Both settings survive as run overlays applied from the interface's live state (REQ-CONFIG-263): the run's default role comes from the composer's role selector and, unlike the flag, **is** checked against the configured role set before it is applied, and access beyond the workspace is the confirmed control of REQ-TOOLS-191 and REQ-CONFIG-327.
- **REQ-CONFIG-242** — *Withdrawn.* It stated that a flag's iteration cap was passed to the run rather than written into `runtime.max_iterations`. The capability — an iteration cap that governs one run without being committed to a file — is exactly the Tier B rule of REQ-CONFIG-262 and REQ-CONFIG-263, over the control of REQ-CONFIG-325.
- **REQ-CONFIG-243** — *Withdrawn.* Its whole surface was a sign-out flag. Signing out of a provider, clearing its stored credentials while retaining its configuration, is the Log out action of REQ-CONFIG-383 over the semantics of REQ-PROVIDER-143.
- **REQ-CONFIG-244** — *Withdrawn.* It specified argument-shape checks and process exit codes for the flags of REQ-CONFIG-240. Nothing is lost: each choice those flags carried is made through a control that offers only valid values, so an invalid selection is unreachable rather than diagnosed, and the product exposes no exit status to a user.
- **REQ-CONFIG-245** — Two recovery paths run when referential validation fails while a person is present. (1) If any message contains the sign-in hint, the user is told so and the sign-in flow is offered without leaving the workspace unopened (REQ-CONFIG-371, REQ-PROVIDER-142); on failure the sign-in's own message is reported and no configuration is loaded; on success the message is reported and the configuration is **reloaded and re-validated**. (2) If any remaining message mentions an unknown model, every message is reported as a configuration error, the user is told that the model slots need attention, and the Models category opens in a model-fixing state (REQ-CONFIG-272, REQ-CONFIG-329); the application continues normally once the user leaves it. Neither path is entered without the user seeing what was wrong first.
- **REQ-CONFIG-246** — For a run no person is watching — one the board scheduled, and any other run started without a person present (REQ-CONFIG-198) — both recovery paths of REQ-CONFIG-245 are skipped and referential errors are **always** fatal to that run: there is neither an inline sign-in nor a model editor to offer, so the run ends and every message is recorded against it as the reason it did not start. A referential failure never silently starts a run on a configuration the product could not validate.
- **REQ-CONFIG-478** — A configuration this build refuses to load MUST leave the user able to load it, and the product MUST say what to change. This is the single definition of what a **fatal** load failure (REQ-CONFIG-233) conveys and what recovers from it. It states a floor that the requirements fixing individual fatal conditions add to rather than replace — REQ-CONFIG-237 owns the line form the messages take, REQ-CONFIG-018, REQ-CONFIG-019 and REQ-CONFIG-462 each add what their own condition must name, and REQ-CONFIG-239 owns the one retry there is; none of them is restated here. It was minted because one such failure was reachable by writing a key this specification itself once defined, and **that route is now closed at its source rather than made survivable here**: a withdrawn key under `requirements:`, and a key this specification names as not a configuration key of this domain, no longer fail the load at all but are reported and ignored, on the terms REQ-CONFIG-183 states — which is also where what *that* report conveys is now fixed, this requirement's floor reaching only failures that are fatal. `requirements.delivery.store_subpath` (REQ-CONFIG-192) and `requirements.execution.worktree_subpath` (REQ-CONFIG-194) are exactly those keys and are consequently outside this requirement. What remains within it is every other fatal condition REQ-CONFIG-233 lists — an unrecognized key under `requirements:` that this specification has never defined among them — and the floor stated below is what each of those failures must meet.

  **What the report conveys.** It MUST identify the offending file by its full path and by which scope it belongs to (REQ-CONFIG-001), MUST identify the rejected key or value by its full path within that file, and MUST convey that this build does not recognize it. The additional obligations this requirement used to carry for a key the specification names as withdrawn, or as not a configuration key of this domain, are **not withdrawn but relocated**: that case is no longer fatal and is REQ-CONFIG-183's, which states what its report conveys, including the withdrawn-rather-than-mistyped statement and what became of what the key configured. Nothing that was owed to a user is owed less; it is owed by a different requirement about a different outcome. Opening a workspace is a workflow a user starts, so this failure MUST present as REQ-NOTIFY-001's *failed with one concrete next step named* rather than as a bare error, and the step it names is correcting the rejected key or value in the named file and opening the workspace again. Its wording is left to the implementation; what is fixed is what it conveys.

  **What recovers it, stated as a guarantee rather than left to be discovered.** Correcting the rejected key or value in the named file — removing the key, or replacing the value with one this build accepts — and loading again MUST be sufficient: no other change is required, nothing outside that file has to be repaired, and nothing has been written on the user's behalf in the meantime. The load fails as a whole rather than falling back to a default, repairing the value, or rewriting the file — the same rule REQ-GIT-071 fixes for the values that domain rejects, which this requirement states for this domain's fatal load failures and does not vary. The application MUST continue to run with that workspace's configuration unloaded; a fatal failure in one workspace's scope MUST NOT prevent any other workspace from opening; and nothing in the workspace other than that file is disturbed by the refusal — the repository, the requirement documents and the workspace's session history are untouched. Where the rejected key or value sits in the **global** scope, no workspace opens until it is corrected, which is why naming the scope is not optional: that difference is the whole difference between a five-second edit and an unexplained product. That consequence now falls only where the user's file states something this product has never defined; the one condition that could produce it over a key **this product itself invited** is out of this requirement and reported without failing the load (REQ-CONFIG-183), which is what keeps this floor a statement about genuine faults rather than about our own deprecations.

  **The remedy is available because configuration is a file the user owns and can edit with anything** (REQ-CONFIG-477, ground 3). This requirement adds no surface and grants the product no licence to edit the user's file for them; it fixes what must be true of the refusal so that the file remains a way out rather than a dead end.
- **REQ-CONFIG-247** — First-run onboarding review is detected as follows: the **raw** workspace `agents.yaml` has null for **all** of `small_model`, `medium_model`, `large_model`, `default_summary_model`, `fallback_model`, `improvement_collector_model`, while the **resolved** configuration has a non-null value for at least one of them. This is true after a browser-based sign-in whose slot assignments land only in the discovery snapshot, and false for endpoint providers that write slot assignments directly into `agents.yaml`.

### Write-back: what each surface persists and where

- **REQ-CONFIG-248** — The startup model-preference write path writes a scope's `agents.yaml` — `<workspace>/.rotaris/agents.yaml` for a workspace-scoped edit and the global `agents.yaml` for a global-scoped one (REQ-CONFIG-259). It bootstraps a missing file first (REQ-CONFIG-030), reads any existing document tolerantly, applies its changes, and writes atomically with the file's key order preserved and never alphabetized, leaving mode `0644`. It bootstraps whichever scope's file it is about to write, global as well as workspace, with the same starter content (REQ-CONFIG-025, REQ-CONFIG-030).
- **REQ-CONFIG-249** — That path accepts slot names from exactly this set: `default_summary_model`, `improvement_collector_model`, `gatekeeper_model`, `small_model`, `medium_model`, `large_model`, `fallback_model`. Any other name is rejected with an error naming the unknown field.
- **REQ-CONFIG-250** — Slot assignment asymmetry: a slot set to null is written as an explicit null (the slot is *set to null*, not removed), whereas a slot's reasoning companion set to null **removes the key** rather than writing null. An unknown slot name in the reasoning map is rejected naming the slot.
- **REQ-CONFIG-251** — Role overrides are written under a `personas:` mapping keyed by the **canonical** role name; any legacy alias key whose canonical name is now present is deleted, so writing preferences migrates a file still using old spellings. If the role mapping ends up empty, the `personas:` key is removed entirely.
- **REQ-CONFIG-252** — The startup-preference write touches only the slot keys, their reasoning companions and the role mapping; everything else in the file is left exactly as the file states it. **Comments and formatting are preserved.** The write is a targeted edit of the existing document rather than a re-emission of the whole of it, so a hand-authored file keeps its comment text, its blank lines and its indentation — including the comment header the first-run bootstrap wrote into the file it created (REQ-CONFIG-025), which a user would otherwise lose the first time they changed a model from the desktop. Editing models from the interface therefore costs the user nothing observable in their own file, and the earlier statement that comments and formatting are lost is withdrawn. Key order preserved and never alphabetized is REQ-CONFIG-248's rule and is unaffected by this one. **This is the discipline every writer of `agents.yaml` follows** — the startup model-preference path (REQ-CONFIG-248), the desktop save (REQ-CONFIG-256), the scoped per-field write path (REQ-CONFIG-441) and the first-run bootstrap (REQ-CONFIG-027) — and it is stated once here rather than repeated in each of them. It is the same discipline that already forbids any of them to discard content it could not interpret (REQ-CONFIG-442, REQ-CONFIG-458): a writer that preserves an unrecognized key but discarded the comment explaining it would honour the letter of that rule and defeat its purpose.
- **REQ-CONFIG-253** — Reading model preferences back for an editor resolves each slot from the **raw** file first: a raw string that is itself another slot name is followed recursively with cycle detection (a cycle yields no value); a raw string naming a concrete model is returned as-is; an absent or non-string raw value falls back to the resolved configuration with synthetic names unwrapped.
- **REQ-CONFIG-254** — A stored reasoning level of `auto` is presented under its **own** label, distinct from the label an unset level carries, so the two are always told apart on screen. "Provider default" labels the unset entry alone (REQ-CONFIG-332, REQ-CONFIG-340); a stored `auto` is appended to the control's options and shown as the current selection (REQ-CONFIG-093, REQ-CONFIG-318), and the two entries are never rendered with the same text on the same control. Reading model preferences back therefore reports a stored `auto` as `auto` and an unset level as unset, and the presentation filter never folds one into the other.
- **REQ-CONFIG-255** — Each role's preference record exposes: the raw configured model (absent when the role is not overridden), the effective resolved model with a role-level synthetic unwrapped but a slot-level synthetic left wrapped, whether the value is inherited, the built-in default model for that role so a surface can offer "back to default", and the raw reasoning value after the presentation filter. The tier names offered in place of a concrete model in a role editor are exactly `small_model`, `medium_model`, `large_model`.
- **REQ-CONFIG-256** — The desktop save path writes to `<workspace>/.rotaris/agents.yaml`. An existing file that is not a mapping is refused with an error saying so. A missing file starts from an empty document. Written keys are exactly: the five model slots (**only when the store value is non-empty**, so an empty selection leaves the existing key alone); each slot's reasoning companion (null **removes** the key); `runtime.max_depth`, `runtime.max_active_children`, `runtime.max_iterations`, `runtime.allow_outside_workspace`, `runtime.permission_mode`, `runtime.improvement_collector_enabled`, `runtime.keep_going`, `runtime.run_start_mode` (REQ-CONFIG-476), plus all six confinement/egress fields; `circuit_breaker.enabled`; `compressor.threshold_percentage`; the delegation strategy; the four `display:` fields (REQ-CONFIG-472), written per field so a `display:` key this screen does not offer is left as the file states it; `skills.enabled`, `skills.overrides` and `skills.invocation_overrides`; and workspace-scoped role values and unsets. Skill policies are written into the **workspace** file only and carry no per-field scope of their own; because `skills` is section-class and its two override maps overlay per skill name (REQ-CONFIG-042, REQ-CONFIG-048), doing so overlays exactly the skills the workspace names and **never discards the global scope's policy for any other skill**. A save is therefore not a wholesale replacement of the user's skill policy, and the only skill a workspace save can change is one the user changed on this screen (REQ-CONFIG-258).
- **REQ-CONFIG-257** — A pre-existing non-mapping value at any of the sections the desktop save writes into is **silently replaced with a fresh mapping** rather than raising.
- **REQ-CONFIG-258** — Skill maps are written **sparsely**: only skills whose load mode differs from `name-only` land in the load-override map, and only skills whose invocation mode differs from `default` land in the invocation-override map. Skill names are normalized on write. `name-only` and `default` are the implicit baselines that are never persisted — **except where a lower layer states a policy for that skill**, in which case the baseline is written out explicitly so that the choice the user made in the higher scope is what the merge produces. Omitting it there would silently leave the lower layer's override winning and make returning one skill to the baseline impossible from the screen (REQ-CONFIG-169).
- **REQ-CONFIG-259** — Role edits carry a per-field scope of `workspace` or `global`. The desktop save always writes the workspace file, and **additionally** writes the global `agents.yaml` when any role value or unset is scoped global. The global file is likewise refused when it is not a mapping, with an error that identifies it as the global file. After writing, the configuration is reloaded, pending unsets are cleared, and change notifications are emitted.
- **REQ-CONFIG-260** — A save is validated before any file is touched. Where the schema rejects any of the six confinement/egress values, nothing is written and the user is shown a single sentence carrying the first complaint, with framework prefixes and multi-line detail stripped out. A rejected save leaves the workspace file exactly as it was and still loadable (REQ-CONFIG-458).
- **REQ-CONFIG-463** — **Default write scope.** Where an editing surface writes configuration and the user has not chosen a scope, it writes the **workspace** scope. This holds for the desktop save (REQ-CONFIG-256), the startup model-preference path (REQ-CONFIG-248) and the scoped per-field write path (REQ-CONFIG-441). Only three things are written user-wide without asking, each because it describes the machine or the account rather than the project: desktop preferences (REQ-CONFIG-405), provider credentials and the provider catalog including endpoints added from the Models category (REQ-CONFIG-329), and theme and reduced motion (REQ-CONFIG-406). A surface that offers a scope choice — the role edit scope (REQ-CONFIG-259) and the tool-server secrets surface (REQ-MCP-110) — opens on `workspace` and writes global only when global is chosen.

### When a change takes effect

- **REQ-CONFIG-261** — **Tier A — written and reloaded immediately.** A desktop settings save re-runs the configuration load at the end, so a saved change is reflected in the loaded configuration within the same action, with no restart. The diagnostics toggle of REQ-CONFIG-471 behaves the same way and reports the new state and the scope it was written to.
- **REQ-CONFIG-262** — **Tier B — applied per run from live UI state, not from the last save.** When a run starts, the loaded configuration is copied and the settings store's **current** values are layered on top, so what a run uses is what is on screen at that moment, not whatever was last committed to the file. The dirty flag therefore governs the **file**, not the **next run**: tightening the security policy and launching a run without pressing Save still yields the tighter policy.
- **REQ-CONFIG-263** — Tier B overlays: the five model slots, **synthesizing slot-level reasoning variants on the fly** exactly as the loader does; the default role from the composer's role selector when that role exists; every role whose `model` equals either the slot name or the slot's previous value is repointed at the new slot value (first match wins); a session-wide model override that applies to the entry role only, with delegated children still running on their own configured models; a session reasoning override applied to the entry role only; a `single` delegation strategy that **strips the delegate tool from every role**; tool servers filtered to those both enabled and available in the UI, with each role's server list filtered to that set; and `runtime.max_depth`, `runtime.max_active_children`, `runtime.max_iterations`, `runtime.allow_outside_workspace`, `runtime.permission_mode`, `runtime.improvement_collector_enabled`, `runtime.keep_going` (REQ-CONFIG-469), `circuit_breaker.enabled`, `compressor.threshold_percentage` and the six security fields.
- **REQ-CONFIG-264** — The permission-mode overlay sets the runtime field only; per-role permission pins are deliberate configuration and are never widened by it.
- **REQ-CONFIG-265** — **Tier C — read at the next configuration load.** Everything outside tiers A and B — verification, hooks, checkpoints, requirements, transcript, project classification, model entries beyond the five slots, and tool-server definitions — takes effect when the workspace is next opened or the application is next started.
- **REQ-CONFIG-266** — Bounds on how soon a change made outside the running application is observed: a rewritten discovery snapshot is picked up once its modification time or its byte size differs (REQ-CONFIG-211); a change to the set of published desktop artifacts is reflected within **750 ms**; and the resolved per-user configuration directory is fixed for the life of the process, so a change to it takes a restart. The **published desktop artifact set** is the current workspace's artifact library — the artifacts written through `artifact_write` (REQ-CONFIG-106) and enumerated by `artifact_list`, owned by the library-and-artifacts domain — and a change to it means any addition, removal or revision of an entry in that library, whoever made it. **750 ms** is an upper bound on how long such a change may take to appear, not a polling interval; a change made inside this process appears without waiting for it.

### Settings screen: structure and navigation

- **REQ-CONFIG-267** — Settings is a full view inside the application's navigation, not a modal dialog. Leaving it is therefore a navigation event, and the unsaved-changes guard lives in the navigation path rather than in a dialog dismissal.
- **REQ-CONFIG-268** — The screen presents categories in exactly this order: Models, Personas, Runtime, Interface, Display, Skills, Instructions, Hooks, MCP Servers, Plugins, Tools, Project, About. The first eleven are the configuration categories; Project (initialization) and About (about and legal) complete the bar.
- **REQ-CONFIG-269** — The category identifiers are exactly `models`, `personas`, `runtime`, `interface`, `display`, `skills`, `instructions`, `hooks`, `mcp`, `plugins`, `tools`, `project`, `about`, in the order the categories are presented (REQ-CONFIG-268). The identifier is the value persisted under `interface/settingsTab` (REQ-CONFIG-405). The vocabulary may gain a value, and a value may be retired, but a value that has been used is never reassigned to a different category (REQ-CONFIG-459). An identifier that is not in the list — retired, unknown or absent — selects `models` (REQ-CONFIG-271).
- **REQ-CONFIG-270** — Save, Discard and the save-status indicator are visible and operable from every category: no category's own content can push them out of view, and each acts on the whole set of pending settings changes rather than on the category currently displayed.
- **REQ-CONFIG-271** — The selected category persists as a **user-wide** preference (not per workspace). On restart the last valid category is restored; a missing, stale or unknown identifier falls back to **Models**.
- **REQ-CONFIG-272** — Requesting a category by identifier returns the identifier actually selected. Requesting an unknown identifier selects Models and returns `models` rather than raising, which is what makes deep links from elsewhere in the application safe.
- **REQ-CONFIG-273** — Reading the current category with nothing selected yields `models`. A category-changed notification is emitted only for a real selection.
- **REQ-CONFIG-274** — At the minimum window size, which is REQ-SHELL-022's and is not restated here, every category's content can be reached by vertical scrolling alone, and no category requires horizontal scrolling at that size. What this requirement relies on that one for is a single figure the whole product is measured against, so a change to it can never leave one screen checked at one size and another at a different one.
- **REQ-CONFIG-275** — The skill policy controls, the tool-server enablement controls and the Instructions, Plugins and Tools inventories are reachable from Settings and from no other view of the application.
- **REQ-CONFIG-276** — Four categories are read-only inventories rendering the same three columns — Name, Source, Description — with an explanatory empty state shown instead of an empty table: Instructions, Hooks, Plugins and Tools. As shipped, Hooks has grown past that shape into a dedicated surface with a column set of its own plus a trust verdict (REQ-CONFIG-354), which leaves three generic inventories.

### Settings screen: save, discard and dirty state

- **REQ-CONFIG-279** — The screen's outward contract is a set of intent notifications, not file writes: it signals that a save was requested, that a discard was requested, and that each immediately-applied preference changed. The host commits; the screen never names a file.
- **REQ-CONFIG-280** — The save-status indicator reads as settled when clean and as having unsaved changes when dirty, and carries an accessible name identifying it as the settings save status. The dirty state is conveyed **in words**; colour only reinforces it, using a text-contrast colour step rather than a saturated one.
- **REQ-CONFIG-281** — Save is offered only while the form is dirty and a configuration service is present; Discard is offered whenever the form is dirty. With no configuration service a dirty form can therefore be discarded but never saved. A save nevertheless executed after the service has gone away produces the read-only notice of REQ-CONFIG-283 and writes nothing. In that state the unsaved-changes guard drops Save entirely and offers Discard and Cancel with Cancel as the default (REQ-CONFIG-286), so the guard never presents a Save that cannot succeed and the user is always left a way to leave the screen.
- **REQ-CONFIG-282** — Both actions notify unconditionally on click; the screen itself neither confirms nor debounces, and has no Cancel button of its own.
- **REQ-CONFIG-283** — Save has exactly three outcomes: with no configuration service, an error notice stating settings are read-only in the current mode and no write; on a write or validation failure, a reported error titled as a save failure carrying the exception text and offering a **Retry** action, with the form left dirty; on success, the dirty flag is cleared (returning the indicator to settled and disabling both buttons) and a success notice is shown.
- **REQ-CONFIG-284** — The save handler catches **every** failure; none propagates out of it. An I/O failure and a validation failure are reported with the detail that kind of failure carries; a failure of any other kind is reported through the same save-failure path, stating that the save did not complete and carrying the underlying detail unaltered. In all three cases the outcome is the failure outcome of REQ-CONFIG-283 — the form is left dirty, a Retry action is offered, and the screen stays usable. No failure inside a save is allowed to leave Settings in a state the user cannot act on.
- **REQ-CONFIG-285** — Discard restores **the last saved values**, not the values at the start of the session, and is unconditional — no confirmation of its own.
- **REQ-CONFIG-286** — The unsaved-changes guard returns immediately when the form is clean. Otherwise it asks whether to save before leaving and offers three buttons in the order Save, Discard, Cancel with **Save as the default**. Save runs the save and yields its success flag — **so a failed save keeps the user in Settings**; Discard discards and proceeds; Cancel stays. A dismissal that is neither answered nor cancelled proceeds. The guard's text must convey that discarding restores the last saved values of the workspace configuration and that it does **not** undo desktop preferences, hook policy, provider changes, or theme and reduced motion (REQ-CONFIG-418); the wording is left to the implementation. **With no configuration service present** the guard offers two buttons only, Discard and Cancel, with **Cancel as the default**, and its text additionally conveys that settings are read-only in the current mode so the pending changes cannot be saved (REQ-CONFIG-281). A Save that cannot succeed is never offered as a button, and never as the default.
- **REQ-CONFIG-287** — The guard fires at exactly three moments: when navigating away from Settings to a different view while dirty (Settings-to-Settings navigation is free); before the project/workspace chooser opens, ahead of any active-run checks; and on a **user-initiated** window close only — a programmatic close does not prompt, and a cancelled guard leaves the window open. At close time the unsaved-settings prompt precedes any integration-in-progress prompt. A cancelled guard changes nothing about work already in flight: a provider probe or health check running when the guard fires keeps running, and its result lands on the still-open screen through the ordinary completion path (REQ-CONFIG-373, REQ-CONFIG-376). The guard neither cancels nor waits for such an operation, and a result arriving after the screen has gone is handled by REQ-CONFIG-374.
- **REQ-CONFIG-288** — **The composer's permission-mode control writes only its own key, and commits nothing else.** The decision this requirement previously handed over is taken here rather than left open, and it is taken against the coupling: the save path of REQ-CONFIG-283 is **not** shared with that control, and choosing a permission mode in the composer no longer commits every other pending Settings edit. The control writes the single permission-mode key through the scoped per-field write path (REQ-CONFIG-441), which overlays only the key it names and leaves every other key in that scope's file exactly as the file states it (REQ-CONFIG-443), into the scope of REQ-CONFIG-463, refusing the write outright if the target file cannot be read (REQ-CONFIG-442); it then reloads, so the new mode is in force without a restart (REQ-CONFIG-261) and still writes and applies immediately (REQ-CONFIG-328). Every pending Settings edit stays pending, stays dirty, and is still undone by Discard. **Why the coupling is refused rather than preserved:** the surprise landed in a security-relevant control, and a user who narrows or widens one run's permission mode has not asked for unrelated, half-finished configuration edits to be written to disk as a side effect — least of all the confinement and egress fields the same screen edits (REQ-CONFIG-289). Nothing here narrows REQ-CONFIG-418: the composer's control does not defer to Save, so it does not participate in Save and Discard, exactly as the diagnostics toggle of REQ-CONFIG-471 does not; and nothing here weakens REQ-CONFIG-423, which continues to require the settings screen to show the mode actually in force.

### Settings screen: security policy controls and confirmations

- **REQ-CONFIG-298** — Confinement and egress are presented in a single card in which every control carries a hint visible on screen — not text hidden in a tooltip — stating what that control does. For a workspace that has configured none of the six values, the card opens on the shipped defaults: confinement `off`, in-confinement network access off, egress `ask`, and all three lists empty.
- **REQ-CONFIG-299** — The card's introduction must state that these are **workspace defaults applied to every new session**, not retroactive changes to running sessions.
- **REQ-CONFIG-300** — Control order within the card: confinement mode selector; confinement-mode hint; a computed availability verdict (selectable text); an in-confinement network toggle (default off); writable-roots editor (placeholder illustrating an absolute path); egress policy selector; egress hint; allowed-hosts editor (placeholder illustrating both an exact host and a wildcard); denied-hosts editor (placeholder illustrating a metadata host), whose hint additionally states that an entry there wins over the allowed list.
- **REQ-CONFIG-301** — The confinement-mode selector offers exactly the modes REQ-SANDBOX-048 fixes and the egress selector exactly the dispositions REQ-SANDBOX-001 fixes; neither vocabulary is defined here, and a control offers no value outside the one it is bound to. - **REQ-CONFIG-302** — The hint texts are the user-visible statement of the policy. Every one of the following must be stated in substance in the card: (a) with confinement `off` a terminal command runs straight on the machine; (b) `workspace-write` permits writes inside the session's workspace and inside the listed writable roots and nowhere else; (c) `read-only` permits no write at all; (d) confinement needs an operating-system backend, and a run asking for confinement on a host that has none fails rather than running unconfined; (e) a writable root is an absolute path kept writable in addition to the workspace, and a relative path is refused; (f) a host in neither egress list is treated according to the selected disposition; (g) an entry in the denied list wins over the allowed list; (h) a host that cannot be read is denied; (i) the only accepted wildcard is a single leading `*.`, which matches subdomains but not the bare name, so covering the bare name takes a second entry; and (j) the in-confinement network toggle applies only while confinement is in force, the egress policy governing the agent's own fetch tool either way.
- **REQ-CONFIG-303** — The two rules users most often get backwards must be reachable by assistive technology, not only visually: the egress selector's accessible description states the denied-wins rule, and the allowed-hosts editor's accessible description states that a wildcard does not cover the bare domain.
- **REQ-CONFIG-304** — A writable-root entry is validated at the control: trimmed; an empty value is refused asking for a path; a value that is absolute in **either** POSIX or Windows spelling is accepted (so a shared workspace configuration stays portable across machines); anything else is refused with a message naming the value, stating it is not absolute, and showing one example of each spelling. The accepted value is stored trimmed but otherwise unchanged — no case folding, no separator rewriting.
- **REQ-CONFIG-305** — A host-pattern entry is validated at the control: trimmed, lowercased, trailing dot removed. Empty is refused with a message showing both an exact-host and a wildcard example. An entry containing `*` is checked against the shared host-matching rules, which accept no wildcard shape other than one leading `*.`; the remainder after the wildcard must be non-empty or the entry is refused naming the value. Accepted wildcard patterns are stored **as typed after lowercasing**; accepted exact hosts are stored **normalized**. An entry that normalizes to nothing is refused as unreadable.
- **REQ-CONFIG-306** — The host validator used by the settings control is the same one the runtime fetch check uses, so what the settings screen accepts and what the runtime enforces can never diverge.
- **REQ-CONFIG-307** — Exactly three transitions in this card demand confirmation, and all three are **widening** transitions: selecting confinement mode `off`, selecting egress disposition `allow`, and switching in-confinement network access on. Each is a warning prompt with Yes and Cancel and **Cancel as the default**. The confinement prompt must state that terminal commands will run directly on the host with no path limit beyond the permission mode; the egress prompt must state that agents will open any host not on the denied list without asking, and that denied hosts still win; the in-confinement network prompt must state that commands running inside confinement will be able to reach the network, and that the egress policy still governs the agent's own fetch tool either way.
- **REQ-CONFIG-308** — Anything other than an affirmative answer restores the control from the stored value and returns **without writing**. Cancelling therefore leaves both the stored disposition and the visible control at their previous values.
- **REQ-CONFIG-309** — Every one of these handlers returns immediately when the incoming value is empty or already equals the stored value, so a programmatic repopulation can never raise a confirmation prompt.
- **REQ-CONFIG-310** — Moving to `workspace-write`, `read-only`, `ask` or `deny`, and switching in-confinement network access **off**, are narrowing transitions and are stored without any confirmation. Switching in-confinement network access **on** confirms first, like the other two widening transitions (REQ-CONFIG-307, REQ-CONFIG-460); there is no widening change in this card that is stored unconfirmed.
- **REQ-CONFIG-311** — Repopulating this card from stored values must not emit changes and must not mark the form dirty; the card is repopulated only when at least one of its six values actually changed, so a repeated status refresh does not re-probe the operating system for confinement availability.
- **REQ-CONFIG-312** — The six configuration keys this card writes are exactly `sandbox_mode`, `sandbox_allow_network`, `network_egress_policy` (scalars) and `sandbox_writable_roots`, `network_allowed_hosts`, `network_denied_hosts` (lists). Round trip is a contract: setting mode `workspace-write`, writable root `/srv/build-cache`, in-confinement network on, disposition `deny`, allowed host `*.example.com`, denied host `metadata.example.com` and saving must produce exactly those six values in the workspace configuration's runtime section, and a second settings view opened over the same workspace must show all six back on their controls — lists as **ordered arrays**, the wildcard **verbatim**, the booleans as real booleans.

### Settings screen: confinement availability verdict

- **REQ-CONFIG-313** — The availability verdict is computed for the mode **currently being edited**, not the last saved one, so it never describes a mode the user is not looking at.
- **REQ-CONFIG-314** — The availability verdict has exactly four outcomes and exactly one is shown. (1) The mode being edited is outside the vocabulary REQ-SANDBOX-048 fixes (not restated here): the sentence names the value and tells the user to pick one from the list. (2) Confinement is in force: the sentence names the backend and states that it encloses every terminal command run in this workspace. (3) A backend exists but the mode being edited is `off`: the sentence names the backend and states that confinement is available but is not applied because the mode is off. (4) No backend exists: the sentence says so, then repeats the cause and the suggested fix the backend reported (REQ-CONFIG-316), and closes with the clause of REQ-CONFIG-315. The verdict is not composed by this screen from evidence of its own: it is a query to the platform confinement service owned by the sandbox-and-egress domain, asked about the host the run would execute on, answering with three fields — a **backend name**, a short identifier of the operating-system mechanism that would enclose the command, absent when there is none; a **cause** sentence; and a **suggested-fix** sentence, the last two absent when a backend is present. A backend is whatever that service reports; the settings screen tests for its presence, renders those fields, and invents no text of its own.
- **REQ-CONFIG-315** — The closing clause of the no-backend verdict is chosen by the mode being edited: with `off` it advises leaving the mode off until a backend is available; with `workspace-write` or `read-only` it states that a run asking for that mode will fail rather than start (REQ-CONFIG-317).
- **REQ-CONFIG-316** — Where the backend reports a cause and a suggested fix, both are shown as the backend worded them and are not re-written, since they name the missing mechanism and the supported way to obtain it. On a platform that has no backend at all, unavailable is the expected verdict and is not presented as an error. Which platforms those are is a property of the platform confinement service and is deliberately not enumerated here: this screen must behave identically on a host that never had a backend and on one whose backend is merely missing, so that adding support for a platform changes no requirement of this domain. The screen therefore branches on the presence of a backend name and never on a platform identity.
- **REQ-CONFIG-317** — Selecting a mode the current host cannot run is **allowed and stored**: the setting is kept for a host that can run it. The verdict simply reports that a run would fail rather than start.
- **REQ-CONFIG-318** — A stored confinement mode outside the known vocabulary must never crash the screen: the selector **adds the unknown value as an item** so it stays visible, and the verdict reports it as unrecognized. The general rule for placing a stored value into any selector is to append it when it is not already among the options, rather than quietly substituting the first entry — on a security control, displaying a setting nobody selected does more harm than displaying one the product cannot classify.
- **REQ-CONFIG-319** — Every verdict branch uses a text-contrast colour step rather than a saturated indicator step, because the saturated step does not meet the 4.5:1 text contrast requirement.

### Settings screen: lifecycle hooks surface

- **REQ-CONFIG-354** — The hooks table shows five columns — Hook, Event, Matches, Source, Status — and is **hierarchical**: top-level rows are agent groups and child rows are individual hooks. After every rebuild the tree is fully expanded and columns are sized to content.
- **REQ-CONFIG-355** — **A hook's command is never shown in the table.** The author of a workspace hook is whoever authored the repository, so the command text is revealed only in a review dialog the user chooses to open.
- **REQ-CONFIG-356** — The command-viewing action starts disabled with a reason directing the user to select a hook, and is enabled only when **exactly one** row is selected and it carries a non-empty command. The dialog renders the command as **plain text**, never as rich text — a hook command must never be interpreted as markup.
- **REQ-CONFIG-357** — An agent group row shows the group label with an empty event and matcher, a source reading as the global runtime policy, and an empty status; it is checkable and its tooltip states that it controls that agent's hooks **for future sessions**.
- **REQ-CONFIG-358** — A hook row shows its name, event, matcher (or a phrase meaning "every matching call" when the matcher is empty), scope label and status. A hook is checkable **only when it is compatible**; an incompatible hook renders without a checkbox, and the status column's tooltip carries the compatibility reason, defaulting to a statement that it runs during future sessions.
- **REQ-CONFIG-359** — Hook status is evaluated in this precedence order and the order is load-bearing: superseded by a higher-precedence scope → superseded, naming the scope that replaced it and carrying no checkbox (REQ-CONFIG-153); not compatible → inactive with the compatibility reason; the agent group disabled → disabled by agent; the hook itself disabled → disabled; not yet allowed → blocked pending review; otherwise → active. An incompatible hook inside a disabled group therefore reports inactive, not disabled-by-agent, and a superseded hook reports superseded whatever else is true of it.
- **REQ-CONFIG-360** — Hook and group checkboxes write to an **external hook policy store immediately**: they are outside the Settings save/discard lifecycle, Save is not involved, and Discard will not undo them.
- **REQ-CONFIG-361** — A hook or group checkbox that the user changes is committed immediately (REQ-CONFIG-360). Nothing else writes: a check state that changes while the table is being repopulated, a change in any column other than the checkbox column, and a row whose identity cannot be read all leave the stored policy untouched. After the commit the table shows the value the user set, neither losing nor reversing it.
- **REQ-CONFIG-362** — The hooks surface rebuilds **only when the underlying hook summary actually changed**; rebuilding on unrelated status refreshes would discard wherever the user had scrolled to. When no configuration or no workspace is available the summary is empty.
- **REQ-CONFIG-363** — The hook summary is readable from outside the screen, recomputes lazily when nothing is cached, and always yields an empty summary rather than nothing. It must be externally invalidatable so a notification action elsewhere can force a refresh.
- **REQ-CONFIG-364** — The hooks empty state states that no compatible hooks are available and names both places hooks may be declared (the external client's global settings and the product's own configuration file). It is keyed on **hooks**, not on groups: a workspace with agent groups but no hooks still shows it.
- **REQ-CONFIG-365** — The trust status label is the status text followed by an external notice when one exists — except that a notice meaning only "the external client declares no hooks" is suppressed as noise.
- **REQ-CONFIG-366** — The workspace-hook review action is enabled only when the summary has items pending review; while disabled, the stated reason is that the workspace contributes no hooks of its own for review. Opening the review dialog is the host's responsibility; the screen only states the intent.

### Settings screen: provider management

- **REQ-CONFIG-367** — A provider row consists of a status line (an indicator whose tooltip is the provider detail, the provider label, a status word, and a detail line), an optional data-destination line, and a right-aligned action row.
- **REQ-CONFIG-368** — The status word is always spelled out beside the indicator and is displayed with underscores replaced by spaces. This screen defines no provider status vocabulary of its own and publishes no value of its own: **REQ-NOTIFY-200 is the product's single definition of the provider status indicator**, and this row relies on it for the closed set of states and for the condition that admits each. The fallback to an idle rendering (REQ-CONFIG-369) exists only so that a value from a future release, or a corrupted one, cannot break the row.
- **REQ-CONFIG-369** — Status colours come in **pairs** — one step for the indicator (which owes 3:1 contrast) and a different step for the word (which owes 4.5:1) — because no single step of a colour ramp satisfies both. The mapping is total over the states REQ-NOTIFY-200 defines: `checking` → informational; `healthy` → success; `warning` → caution; `unauthenticated` and `error` → failure; `unknown`, `coming_soon` and any value the row does not recognize → idle.
- **REQ-CONFIG-370** — At most one destination sentence is rendered per provider row, chosen by connection mode and composed from catalog-supplied fields, with no second hand-maintained provider list: `local-sdk` states that the locally installed agent SDK is invoked and that traffic reaches the provider through it; `rotaris-cloud` names the managed service and the host traffic is sent to; `direct` names the operating organization, omitted where the catalog gives none, and the destination; `custom` names the destination or, where the catalog gives none, refers the user to the configured `base_url`. Any other mode renders no destination line at all. The line is word-wrapped and carries an accessible name identifying it as that provider's destination. The three fields come from the provider's own catalog entry and from nowhere else: `service_name` (string or absent) is the managed service named by the `rotaris-cloud` sentence, `operator_name` (string or absent) is the operating organization named by the `direct` sentence, and `destination_host` (string or absent) is the host named by the `rotaris-cloud`, `direct` and `custom` sentences. Each is presentation text and none is used to route a request. Where a mode's sentence needs a field the catalog does not carry, that mode's stated fallback applies — `direct` omits the organization, `custom` refers the user to the configured `base_url` — and where `rotaris-cloud` carries neither field its sentence is omitted rather than rendered with a gap.
- **REQ-CONFIG-371** — Provider row actions, where *busy* means an operation for that provider is in flight and *actionable* means the provider is available and not busy: **Quick Start** is rendered only for a provider whose catalog entry carries a quick-start URL and is presented as the row's primary action; **Check** is enabled when a provider service exists and the provider is actionable; **Authenticate**/**Re-authenticate** is enabled when the provider has an authentication flow and is actionable; **Log out** is enabled when credentials are stored and the provider is not busy; **Delete** is rendered only for a user-defined provider, is enabled while it is not busy, and is presented as destructive. Exactly one tooltip is shown, chosen in this order: the provider's own detail while the provider is unavailable; then an explanation that the provider offers no authentication flow, where that applies; then a message that an operation is in progress, while busy; then the action's own description. The same rules apply whether the row is being built or refreshed in place. **Availability is a statement about the local prerequisite for reaching a thing, and nothing else**, and the same rule governs the tool-server rows (REQ-CONFIG-349, REQ-CONFIG-352): a provider whose connection mode is `local-sdk` is unavailable exactly when the SDK executable it invokes is not found on the executable search path; a provider on any other connection mode is unavailable exactly when neither its catalog entry nor its configuration supplies a usable address; and a stdio tool server is unavailable exactly when its `command` is not found on the executable search path, an `http` or `sse` tool server exactly when it has no usable `url`, which includes a `url` still carrying an unresolved placeholder (REQ-CONFIG-225). Everything else leaves the thing available: being unauthenticated, failing a health check, reporting an error status, and being busy are all availability-neutral, and available is the default where no prerequisite is missing. The detail a row shows for an unavailable thing names the missing prerequisite.
- **REQ-CONFIG-372** — Three different notions of "already authenticated" exist in this flow and must be reconciled deliberately: the action's **text** is chosen by whether credentials are stored, its **accessible name** by whether the provider is currently connected, and the re-authentication flag passed to the dialog by whether the status is outside the set {unauthenticated, unknown}. A provider with stored credentials that is not currently connected therefore reads as "Re-authenticate" visually and as "Authenticate" to assistive technology.
- **REQ-CONFIG-373** — Starting any provider operation marks that provider busy and immediately refreshes the row, which is what greys its actions and shows the operation-in-progress tooltips. On completion the busy marker is cleared **before** the refresh, so the row does not rebuild still-busy.
- **REQ-CONFIG-374** — Provider work must check that the screen still exists before touching it or the store. **An operation completing after Settings has been destroyed must not crash.**
- **REQ-CONFIG-375** — A health check is started on construction for every provider that has an authentication flow; providers without one are never probed. A check sets the row to checking with a "checking health" detail before it starts.
- **REQ-CONFIG-376** — A row is rebuilt once its in-flight check lands, discarding any control captured earlier. Status is published **one notification earlier** than the clearing of the busy marker, so anything keyed on status alone can catch the row while it is still busy. That gap is real and observable.
- **REQ-CONFIG-377** — Repeated status notifications must not grow the interface: pushing many status/detail updates through must leave the provider's row controls the same objects, show the last value, and leave the total control count unchanged.
- **REQ-CONFIG-378** — The add-endpoint action is enabled only when a provider service exists **and** no registration is already in flight; registration is globally serialized under a single reserved operation identity. The add dialog offers two outcomes: submitting a label, URL and key registers a new endpoint; selecting a built-in provider instead switches to authenticating that provider — so "add endpoint" doubles as the entry point for first-time authentication of a built-in provider that has no row yet, for which a provider record is synthesized as unavailable and unauthenticated because none exists.
- **REQ-CONFIG-379** — Field validation for the add dialog lives **in the dialog**, not in the screen: submitting with empty fields sets the dialog's status to a message naming the missing required field. Registration failures are reported **inside the dialog** rather than on a row.
- **REQ-CONFIG-380** — Registration success ordering: an unsuccessful result sets the dialog error and **leaves the dialog open**; a vanished service sets a service-unavailable error; otherwise the provider catalog is refreshed, the dialog is accepted and released, and the new provider is **health-checked immediately** without the user asking.
- **REQ-CONFIG-381** — Once an authentication attempt reports a connected provider, the usage limits of the subscription-backed providers are refreshed without blocking or closing the authentication dialog and without marking any provider row busy; a refresh that fails, or one for a provider that is still unauthenticated, reports the limits as unavailable rather than raising. For the managed-cloud provider a credit-balance refresh is requested after **every** authentication or logout attempt, successful or not, so the balance on display is never one belonging to a different account.
- **REQ-CONFIG-382** — Managed-cloud sign-in can be requested from elsewhere in the application: the request selects Settings and then runs exactly the flow that the managed-cloud provider row's authenticate action runs. Where no managed-cloud provider is present the request has no effect and reports no error.
- **REQ-CONFIG-383** — Log out asks a plain confirmation question (not a warning) naming the provider and asking whether to remove stored authentication, using the platform's default button placement. Anything but an affirmative answer returns. On confirmation the row goes to checking with a "logging out" detail, and the operation drives the provider to unauthenticated, not connected, with the service's own detail message.
- **REQ-CONFIG-384** — Deleting a user-defined endpoint first computes this workspace's references to it by prefix-matching `<provider id>/` against every model slot and every role model, formatted as a comma-joined list of "slot X" and "persona Y" items, or a phrase meaning none in this workspace.
- **REQ-CONFIG-385** — The deletion confirmation is a warning with Yes and Cancel and **Cancel as the default**, and must promise exactly three facts that the implementation then keeps: deletion is **user-wide** across every workspace on the machine; the listed references are **left unchanged for manual repair**; and **other workspaces were not inspected**. Cancelling must not invoke the delete operation at all. On confirmation the row goes to checking with a deleting detail; a failed result sets the row to error with the result message; success refreshes the catalog and the row disappears along with its delete action.
- **REQ-CONFIG-386** — Result-merge rules when a provider operation returns a replacement record: with no existing row the replacement is **appended** and a change is announced (this is the first-time-authentication path); with an existing row the replacement **inherits the user-defined flag from the existing entry**, so a service result cannot change whether a provider is user-defined; and if the replacement's status is an error **and** the existing entry had credentials, the replacement's credential flag is forced back to true — a failed health check must not make Log out disappear.
- **REQ-CONFIG-387** — A "successful" operation with an **unconnected** result is still a dialog-level failure: the dialog stays open showing the result detail. A connected result accepts and releases the dialog. A failed operation sets the row to error with the message and not-connected, and mirrors the message into any open dialog.
- **REQ-CONFIG-388** — With no providers at all, a compact empty state states that no providers were discovered and that a provider or model endpoint must be configured before starting a run.
- **REQ-CONFIG-389** — The provider list shows **no** built-in or merely-referenced provider by default; a row appears only once a provider is authenticated. The one exception is the managed-cloud provider: its row is shown whether or not it has been authenticated, and which is shown with its quick-start action **in addition to** the normal actions rather than instead of them. A provider that is only referenced by a model slot — a deleted custom endpoint included — must **not** cause a row to reappear.

### Settings screen: project initialization and machine setup

- **REQ-CONFIG-390** — The Project category holds an initialization card with a status headline, a mouse-selectable detail line, a progress indicator hidden by default and deliberately **indeterminate**, because progress arrives as discrete steps rather than as a completion fraction, and an action row with a primary action plus an availability explanation.

- **REQ-CONFIG-392** — The detail sentence must state, per initialization state: on error, the recorded error text, followed — where tasks are still pending — by a statement that nothing was recorded so those tasks can be run again; while running, which tasks are running and that the view updates when the run finishes; when pending, which tasks have not been run; when skipped, which tasks were skipped and that they can be run at any time, preceded by the completed sentence where any task has completed; when completed, which tasks completed, the calendar date taken from the date part of `initialization.last_run` and omitted where `last_run` is null, and the classification sentence of REQ-CONFIG-393; when nothing applies, that no task applies yet, that tasks appear once the tool they depend on has been configured, and that the user should look at the MCP Servers category and then reload the workspace. Tasks are named by their registry labels (REQ-CONFIG-395), never by the ids stored in `initialization.completed` and `initialization.skipped`.
- **REQ-CONFIG-393** — Exactly one classification sentence is rendered, chosen by `initialization.classification`: `non-code` states that the workspace holds documentation rather than code and that no code memories were produced as a result; `code` states that code memories were created from the workspace's sources. A null value, and any value outside that vocabulary, renders no sentence at all.
- **REQ-CONFIG-394** — The headline's accessible description is set to the detail sentence, so assistive technology reading the headline also hears the explanation.
- **REQ-CONFIG-395** — Initialization task labels come from a registry, so a task registered later appears in this category without changes to the settings surface. The screen must not hard-code task names.
- **REQ-CONFIG-396** — The machine-setup card shows a status line, a mouse-selectable versions line, and a repair action whose accessible description names the tool classes re-probed. The action only states intent; the host performs the repair.
- **REQ-CONFIG-397** — The machine-setup record is read from `<per-user data dir>/setup/state.json`. With no such record, the status line states that machine setup has not run and the versions line states that no managed tool versions are recorded. With a record, the outcome maps to: `complete` → setup completed successfully; `degraded` → usable, with part of the machine tooling missing; `cancelled` → setup was interrupted and can be picked up again; `running` → the record shows a pass in progress that this window did not complete and that may no longer be running, since at most one instance of the application runs (REQ-STARTUP-161) and a recorded `running` outcome with no pass executing is what an interrupted launch leaves behind rather than evidence of a second process; any other value → a line naming that value as the last result, or naming it unknown where the record carries no outcome. Versions render as a comma-joined list of name-and-version pairs sorted by name, or a line stating that no satisfying versions are recorded. The record is a JSON object with three recognized keys: `outcome` (string — `complete`, `degraded`, `cancelled`, `running`, or any other value, handled as above; a missing or non-string value reads as no outcome recorded), `completed_at` (ISO-8601 UTC string, optional, unused by this screen) and `versions` (object mapping a managed tool name to its satisfying version string; a missing, empty or non-object value reads as no versions recorded, and an entry whose value is not a string is skipped). Unknown keys are ignored rather than rejected, since this file is written by the machine-setup subsystem and read here. An unreadable file, invalid JSON, and a top level that is not an object all read exactly as no record at all, which is not an error.
- **REQ-CONFIG-398** — The About category draws on **locally held data alone** — it displays with no provider, no workspace and no authentication present — and is constructed with the application version.

### Released-run permissions and the answer-wait budget

- **REQ-CONFIG-408** — The released-run permission switch is placed beneath the permission mode it supersedes, yet it is a **desktop preference rather than a workspace configuration field**, and takes no Save. The elevation describes how *this desktop* starts board runs, not the project; storing it in the workspace would raise privileges for every unattended run of that repository and would ship along to anyone who checked it out.
- **REQ-CONFIG-409** — The released-run permission switch's label and accessible name both state that released requirement runs use full permissions. Its accessible description must state that, while the switch is on, a released requirement runs with the elevation of REQ-CONFIG-411 — the full tool set — and never pauses for approval, which is what lets it finish unattended; and that, while it is off, the run obeys the permission mode above it and does pause, with the board showing which run is waiting. A note beneath the row must state that nothing is watching a released run, so a run that does pause stays paused until a person returns to it.
- **REQ-CONFIG-410** — This row is the **only** surface where the behavior remains visible once the user has silenced the release-time disclosure.
- **REQ-CONFIG-411** — "Full permissions" resolves to `autonomous`, defined in exactly one place. Elevation applies **both** `permission_mode = autonomous` **and** `allow_unsandboxed_autonomous = true`; either alone is a no-op, with the preset missing, the very first call that needs approval is refused by the policy engine; with the opt-in missing, the preset is reduced immediately back to `ask`.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The elevation above still governs; the reduction no longer applies — the preset alone now satisfies it.
- **REQ-CONFIG-412** — Both released-run settings take effect on the **next run started**, never on a run already in flight.
- **REQ-CONFIG-413** — The answer-wait budget is chosen from ten discrete stops rather than typed as a free number. In order: 5 minutes (**300** s), 10 minutes (**600** s), 30 minutes (**1800** s), 1 hour (**3600** s), 2 hours (**7200** s), 5 hours (**18000** s), 12 hours (**43200** s), 1 day (**86400** s), 2 days (**172800** s) and Indefinitely (**0**, meaning no limit). Indefinitely is the default. The control's accessible name states that it sets how long a released run waits to be answered. This preference is authoritative for runs started from this desktop and the workspace field `requirements.human_in_the_loop.answer_timeout_minutes` is not consulted for them; that field governs every other run (REQ-CONFIG-198). The control's hint says so, so a user is never left thinking a workspace value is being overridden silently.
- **REQ-CONFIG-414** — Moving the slider updates a readout to the stop's label and rewrites the slider's accessible description to a sentence naming the wait, then stores the seconds. The readout must be initialized **before** the change connection is made, so loading does not write.
- **REQ-CONFIG-415** — The timeout semantics are stated in the interface and must hold: on expiry, **the pending request is denied and the run proceeds without that call** rather than being aborted; and **cancelling the run terminates the wait at once**, whatever the budget is set to.
- **REQ-CONFIG-416** — The released-run permission switch and the answer-wait budget are presented together, the switch above the budget. The budget applies at every permission mode: no permission mode removes a run's ability to ask for an answer, and the budget governs that wait whichever mode is in force.

### Persistence destinations and reload discipline

- **REQ-CONFIG-417** — Five persistence destinations are reachable from the settings screen. (1) **Workspace/global configuration**, committed by Save: the five model slots and their reasoning strengths, roles per the role edit scope, delegation strategy, depth and fan-out, the four runtime toggles including `runtime.keep_going` (REQ-CONFIG-323), permission mode, the run-start mode (REQ-CONFIG-476), compression threshold, iteration cap, the six confinement/egress fields, the four tool-row display fields (REQ-CONFIG-472), and the skills master switch and per-skill policies (REQ-CONFIG-256). Destination 1 is committed by Save with exactly one stated exception: the diagnostics toggle of REQ-CONFIG-471 writes its single key immediately, into the scope that card has selected, and is consequently not undone by Discard — the card says so in words. (2) **Desktop preferences**, written the moment the control moves (REQ-CONFIG-405). (3) **The external hook policy store**, written immediately by the hook checkboxes (REQ-CONFIG-360). (4) **Provider credential storage and the provider catalog**, written asynchronously by the authentication, logout, registration and deletion operations, entirely outside the dirty flag. (5) **Theme and reduced motion**, persisted by their own services, which this screen only invokes (REQ-CONFIG-406). Tool-server enablement is not a further destination and is not written to any configuration file: toggling a server records a session-scoped override (REQ-CONFIG-349) that a run picks up per REQ-CONFIG-263.
- **REQ-CONFIG-418** — **Only destination 1 participates in Save and Discard, and only through the controls that defer to Save** — the diagnostics toggle of REQ-CONFIG-471 writes into that destination immediately and is not undone by Discard either. A user who changes a preference, flips a hook checkbox, deletes a provider and then presses Discard undoes **none** of it; Discard restores only the workspace configuration. The exclusion is deliberate and is not narrowed: each of the other four destinations is committed the moment the user acts, and undoing one means acting again — a hook re-checked, a preference re-toggled, a provider re-authenticated. What the resolution does narrow is the silence: the Discard control's explanation and the unsaved-changes guard's text (REQ-CONFIG-286) must both state that Discard restores the workspace configuration and does **not** undo desktop preferences, hook policy, provider changes, or theme and reduced motion.
- **REQ-CONFIG-419** — **No reload path may emit a change notification.** Every repopulation is either suppressed or equality-guarded. Violating this marks Settings dirty on open and can write back what was just read. This is a tested contract: after saving and marking clean, deliberately writing different values into the store and then reloading must show the **file's** values, leave the form clean, and produce **no** dirty transition at any point.
- **REQ-CONFIG-420** — After any status refresh, the save-status indicator, the security policy card including its confinement availability verdict, and the hooks surface all show current values, values changed outside the settings screen included. A refresh never discards an edit the user has in progress — with the single exception REQ-CONFIG-423 states for the permission-mode field, where a mode already applied to a live run displaces an unsaved selection — and never moves the user's position in a scrolled area elsewhere on the screen.
- **REQ-CONFIG-421** — After any refresh, provider status, the skill table, the tool-server rows and the inventories show current values; a change in a tool server's health in particular is shown without the user closing and re-opening Settings. Where the data behind the model grid, the provider rows, the runtime controls or the role table is unchanged, those controls keep their current selection, focus and scroll position.
- **REQ-CONFIG-422** — A theme change must invalidate **every** rebuild fingerprint, because indicator colours, health colours and the confinement verdict are resolved to finished colours when a control is built and cannot be recomputed by restyling alone. Any control that bakes a resolved colour into a built widget must be rebuilt on theme change.
- **REQ-CONFIG-423** — The permission-mode control on this screen shows the permission mode currently held in the pending settings state, and that state is the single source the control reads. A change to the same field made while Settings is open by any other surface — the composer's control, which writes that key alone (REQ-CONFIG-288), or any other writer of it — lands in that pending state, and the control therefore shows it after the next status refresh (REQ-CONFIG-420). The refresh is equality-guarded like every other repopulation, so it neither emits a change nor marks the form dirty (REQ-CONFIG-419). A control on this screen never continues to display a permission mode that the pending state no longer holds. **For this one field the last write wins over an unsaved selection on this screen**, and that is deliberate: where a permission mode has been changed elsewhere and applied to a live run, a settings screen that went on showing the user's unsaved choice would be showing a mode no run is operating under. This is the stated exception to REQ-CONFIG-420's rule that a refresh never discards an edit in progress; it reaches this field and no other, and it is the price of the two commit policies REQ-CONFIG-328 keeps.
- **REQ-CONFIG-424** — The screen must construct successfully with no provider service and no configuration service: Save is disabled, the tool-server probe is disabled, provider actions do nothing, the hook summary is empty, and only the Tools inventory has rows.
- **REQ-CONFIG-425** — Immediately after construction, the host selects the restored category and then marks the settings state clean, so **Settings always starts clean by definition** and any dirtiness produced while wiring up is cleared.
- **REQ-CONFIG-426** — The host can deep-link into a category (for example jumping straight to Hooks from a notification action, or to About from a legal entry point) and can start managed-cloud sign-in through the screen after navigating to it. This is why category selection must tolerate arbitrary identifier strings.

### The shared model picker

- **REQ-CONFIG-427** — Every model selector on the screen — the slot selectors and the per-role model selectors alike — marks model availability the same way (REQ-CONFIG-428, REQ-CONFIG-429). No selector presents an unavailable model differently from any other selector.
- **REQ-CONFIG-428** — A model the provider account has switched off is **listed, greyed and unselectable, never dropped**. Omitting it would put the picker silently at odds with the provider's own account settings and hide from the user that the model they are after needs only to be switched back on there. The row is left both disabled and unselectable while the surrounding control stays enabled, which is precisely what keeps the row's explanation reachable.
- **REQ-CONFIG-429** — An unavailable model's reason must reach both the pointer and assistive technology over four channels, none of which is colour on its own: the reason is set as the item's tooltip and as its accessible description; the item's text ends with a suffix stating in words that the model is unavailable; the item carries an icon; and the item is drawn in a distinct foreground colour. All four are required. The distinct foreground colour must itself meet the 4.5:1 text contrast floor of REQ-CONFIG-434, and the reason shown is the sentence resolved once at load per REQ-CONFIG-208.
- **REQ-CONFIG-430** — Where the stored selection names a model the provider account cannot currently use, that model is the selection the control shows, and the control itself carries the model's unavailability reason (REQ-CONFIG-208) as both its tooltip and its accessible description. A control never shows an empty selection because the model it is pinned to has become unavailable.
- **REQ-CONFIG-431** — Refilling a picker with a new catalog and the same current model emits **no** change notification. Refilling with a catalog of only usable models clears the icon, the suffix, the control tooltip and the control accessible description — decoration is not sticky.
- **REQ-CONFIG-432** — The bare model name is carried in a dedicated data slot; the display text is decorated and is **not** equal to the identifier. Anything reading a picker back must read the data slot, not the text. This holds for **every** model control without exception, the model-slot control included: a decorated label — an unavailability suffix, an icon, any other decoration — can never round-trip into a stored value, and a stored model-slot value is always the bare identifier.
- **REQ-CONFIG-433** — Two projections of the model list exist and are not interchangeable: one listing **everything** including refused models (used to populate pickers), and one listing **usable models only** (used by first-run checks, run-start validation, and rebuild fingerprints). Role pickers are built from slot-name pseudo-options plus the everything-projection entries not shadowed by a slot name, so unavailable concrete models are greyed there too.

### Presentation and accessibility rules

- **REQ-CONFIG-434** — **Colour never carries state alone.** Every status indicator has its status written out beside it; text uses a colour step meeting 4.5:1 contrast and indicators use a saturated step meeting 3:1.
- **REQ-CONFIG-435** — Health-to-colour mapping is resolved as the control is drawn, against whichever theme is active, and never frozen earlier while the user's theme is still unknown: `unknown` → idle, `checking` → waiting, `healthy` → success, `unreachable` → failure, with **idle as the fallback for any unrecognized value**.
- **REQ-CONFIG-436** — The values the security controls offer are exactly the schema vocabularies, which are fixed by REQ-SANDBOX-048 (confinement mode), REQ-SANDBOX-001 (egress disposition) and REQ-TOOLS-041 (permission mode) and are not restated here; the controls bound to them are REQ-CONFIG-301's and REQ-CONFIG-324's. Every value a control produces is assigned through the validating runtime policy before any file is written (REQ-CONFIG-111), so a value the schema would reject is refused at the control that produced it, with the reason shown on that control's problem line (REQ-CONFIG-290, REQ-CONFIG-291), and never reaches a configuration file.
- **REQ-CONFIG-437** — Empty states name the remedy, not just the condition: the role table's empty state directs the user to add roles to the workspace configuration; the tool-server empty state names the configuration file; the initialization empty state names the category where a dependency is configured.
- **REQ-CONFIG-438** — Provider action buttons are compact and fixed-width so a five-action row fits inside the minimum window width.
- **REQ-CONFIG-439** — A refresh of a table, grid or row is atomic as seen from outside: when the refresh call returns, only current content is displayed, and no row or control belonging to the superseded content is still visible or still accepts input.

### The scoped per-field write path

- **REQ-CONFIG-440** — *Withdrawn.* It enumerated a second set of settings screens belonging to a text-mode interface, and the product has one settings surface. Every capability those screens carried is held by the desktop settings screen or by the domain that owns it: provider settings by REQ-CONFIG-329 and REQ-CONFIG-367 to REQ-CONFIG-389; compression settings by REQ-CONFIG-325 and REQ-CONFIG-446; tool-result display settings by REQ-CONFIG-472; tool-server enablement by REQ-CONFIG-348 and REQ-CONFIG-349; tool-server secret editing, with its workspace/global scope choice, by REQ-MCP-109 and REQ-MCP-110 over the store of REQ-CONFIG-214 to REQ-CONFIG-218; and the developer options by REQ-CONFIG-471, which also states what is shown when no configuration is available.
- **REQ-CONFIG-441** — The scoped per-field write path is the writer used by any surface that changes part of a section rather than the enumerable key set of the desktop save (REQ-CONFIG-256), the shipped cases being the diagnostics toggle of REQ-CONFIG-471 and the composer's permission-mode control (REQ-CONFIG-288). It targets the global `agents.yaml` when the requested scope is global, and the workspace `agents.yaml` otherwise; with no scope requested it targets the workspace file (REQ-CONFIG-463). It reads the existing document, applies its update **per field** — overlaying only the keys it names, recursively through nested mappings exactly as a section merge does (REQ-CONFIG-048) — and writes atomically with key order preserved, comments and formatting preserved (REQ-CONFIG-252), and mode `0644` (REQ-CONFIG-444). Where the target file does not exist it starts from an **empty** document and creates the file holding only the keys it wrote, together with any missing parent directory, exactly as the desktop save does for a missing file (REQ-CONFIG-256); it does not write the starter document, which stays the business of the two writers REQ-CONFIG-030 names. A setting a user changes in a workspace that has never been configured is therefore kept rather than dropped — which matters most for the permission mode, where losing the write would leave a run at a mode the user did not choose.
- **REQ-CONFIG-442** — When the existing file cannot be parsed, or parses to a non-mapping, the scoped per-field write path **refuses the write**: nothing is written, the file is left exactly as it stands, and the user is told that the target file could not be read, which file it is, and what the parse fault was. No writer of `agents.yaml` ever discards content it could not parse (REQ-CONFIG-256, REQ-CONFIG-458).
- **REQ-CONFIG-443** — Because the update is applied per field (REQ-CONFIG-441), a writer that emits a **partial** section changes only the keys it emits: the diagnostics toggle writing one `runtime:` key leaves every other runtime setting in that scope's file untouched, exactly as the two writers that emit complete sections do.
- **REQ-CONFIG-444** — Every writer of `agents.yaml` — the startup model-preference path (REQ-CONFIG-248), the desktop save (REQ-CONFIG-256), the scoped per-field write path (REQ-CONFIG-441) and the first-run bootstrap (REQ-CONFIG-027) — leaves the file at mode `0644`. On a platform with no POSIX file mode the requirement is satisfied by leaving the platform's own default in place.
- **REQ-CONFIG-445** — *Withdrawn.* Its surface was the developer-options screen of the text-mode interface withdrawn by REQ-CONFIG-440. The capability — reading the **per-scope raw** runtime mapping directly from the chosen scope's file rather than from the merged configuration, so a user can see whether a setting is stated globally or in this workspace — is carried by the advanced runtime card of REQ-CONFIG-471.
- **REQ-CONFIG-446** — `compressor.threshold_percentage` is edited from the desktop compression control, and every value that control offers must be accepted by the schema (REQ-CONFIG-132). The same holds for every other vocabulary shared between an editing control and the schema: what a control offers, the schema accepts. The intended user-selectable range is **50–95** (REQ-CONFIG-325), and the schema's wider **1–100** exists only so that a hand-authored file outside that range still loads. A value authored outside 50–95 is accepted, used, and shown on the control clamped to the nearest offered stop only for display — the stored value is never rewritten by opening the screen (REQ-CONFIG-419).
- **REQ-CONFIG-447** — *Withdrawn.* Its whole surface was a configuration subcommand with an argument, a secure prompt, a workspace option, a global flag and an exit code, and the product has no command line. The capability is carried in full by the desktop secrets surface: storing the search server's API key under that server's entry, keyed by its API-key environment-variable name (`ROTARIS_SEARCH_API_KEY`, REQ-CONFIG-181), with a `Workspace`/`Global` scope choice opening on `Workspace` (REQ-MCP-110, REQ-CONFIG-463), a value field that never echoes what is typed, a refusal that writes nothing when the value is empty, and a confirmation that reports the value masked (REQ-MCP-081) rather than in clear. The write itself is unchanged and remains governed by REQ-CONFIG-216 and REQ-CONFIG-217.

### Cross-cutting invariants

- **REQ-CONFIG-448** — Absence is never an error at any level of the configuration file set.
- **REQ-CONFIG-449** — Layer order is fixed and total, with no per-key precedence inversion.
- **REQ-CONFIG-450** — The overlay is one level deep for named entries (REQ-CONFIG-046) and recursive through nested mappings inside a section (REQ-CONFIG-048); lists never append anywhere.
- **REQ-CONFIG-451** — A null at the top level cannot clear an inherited value; a null inside a named entry can.
- **REQ-CONFIG-452** — Hook provenance is stamped before merging, because it is unrecoverable afterwards; superseded hook lists are preserved, because dropping them is a privilege-reduction vector.
- **REQ-CONFIG-453** — Credentials never enter the discovery snapshot (REQ-CONFIG-213) and are redacted wherever a model entry is rendered (REQ-TOOLS-171).
- **REQ-CONFIG-454** — Unavailable models are structurally incapable of producing a client.
- **REQ-CONFIG-455** — Loader-owned synthetic model names are reserved and may be overwritten without notice.
- **REQ-CONFIG-456** — The workspace configuration directory is kept out of version control on every load, best-effort.
- **REQ-CONFIG-457** — Built-in defaults are copied per load and never mutated by a load.
- **REQ-CONFIG-458** — No surface writes a configuration it cannot load back.
- **REQ-CONFIG-459** — The settings category identifier vocabulary is append-only; an existing identifier is never re-pointed at a different category.
- **REQ-CONFIG-460** — Permission-widening changes are confirmed with the cancelling option as the default, and are not written when cancelled.

### Directory layout

```
<per-user config dir>/            # global scope, always loaded
  agents.yaml                     # global overrides
  models.yml                      # optional static / custom provider declarations
  secrets.yaml                    # tool-server environment secrets (optional)
  project_settings.yaml           # machine-written provider/model discovery snapshot
  tools/                          # global custom tool plugins

<per-user data dir>/              # NOT configuration
  setup/state.json                # machine-setup record
  <credential store>              # provider credentials
  copilot-gateway/                # staged gateway credentials, one dir per workspace
    <workspace identifier>/       # never inside the workspace (REQ-PROVIDER-063)

<workspace>/.rotaris/             # workspace scope, higher precedence
  agents.yaml                     # slots, roles, runtime, sections
  models.yml                      # optional static / custom provider declarations
  secrets.yaml                    # tool-server environment secrets (optional)
  <workspace identifier>          # stable, human-readable, travels with the workspace (REQ-SESSION-197)
  plugins/                        # workspace plugins (inventory source; no extension fixed — REQ-TOOLS-161)
  tools/                          # workspace custom tool plugins
  worktrees/                      # per-session isolated checkouts

<workspace>/.mcp.json             # third-party tool-server discovery (locations per REQ-MCP-017)
<workspace>/AGENTS.md             # instruction file (inventory source)
<workspace>/AGENTS.override.md    # instruction file (inventory source)
<user-level>/mcp.json             # third-party tool-server discovery (locations per REQ-MCP-017)
```

The two discovery paths appear above only so the layout is complete. Their per-platform spellings, and the condition under which the user-level one is skipped, are REQ-MCP-017's and are not restated here (REQ-CONFIG-008, REQ-CONFIG-009).

Both per-user roots above — the configuration one and the data one — are the per-user location REQ-STARTUP-145 fixes: local to this machine, never replicated to another machine or to another copy of the user's profile. This domain names no other per-user location and states no second rule for one (REQ-CONFIG-001).

Everything in the layout above is a **file**, and that is deliberate: REQ-CONFIG-477 states the boundary and the grounds that reach it. Session records, post-run improvement artifacts and requirement delivery records are **not** in the layout because they are no longer directories in the workspace (REQ-CONFIG-010, REQ-CONFIG-192); they are held in the store the application keeps for the workspace, and no key of this domain names a location for them.

### Discovery snapshot document

```yaml
version: 1                         # only 1 accepted
providers:
  <provider id>:
    id: <string>
    display_name: <string>         # required
    family: <string|null>
    base_url: <string|null>
    authenticated: <bool>          # required; false ⇒ contributes nothing
    discovered_at: <ISO-8601 UTC>  # required
    default_summary_model: <string|null>
    large_model: <string|null>
    medium_model: <string|null>
    small_model: <string|null>
    fallback_model: <string|null>
    models:
      - id: <string>               # required, unique within the provider
        display_name: <string|null>
        capabilities: {…}
        limits: {…}
        pricing: {<name>: <float>}
        discovered_at: <ISO-8601 UTC>   # required
```

Unknown keys are forbidden at every level. Written with insertion order preserved, mode `0644`, atomically, after a secret scan.

### Secrets document

```yaml
<tool server name>:
  <ENV_VAR_NAME>: <value>
```

Merged per key within a server across scopes; unreadable or malformed content yields no secrets, silently. Written atomically and left at mode `0600`, or at the equivalent explicit owner-only protection on a platform with no POSIX mode — the one file in the layout above protected as a credential store rather than as configuration (REQ-CONFIG-216).
