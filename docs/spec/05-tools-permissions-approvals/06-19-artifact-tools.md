### 19. Artifact Tools

**REQ-TOOLS-148** — `artifact_read(id_or_slug, sections=[])` returns the full Markdown body by default; `sections` may filter to any of `summary`, `key_findings`, `snippets`, `highlights`, `files`. An unknown reference errors with `Artifact not found: <ref>`. Reading marks the artifact as consumed by the reading persona.

**REQ-TOOLS-149** — `artifact_list(artifact_kind?, persona?, tags[], limit=20 (range 1–200), include_superseded=false)` renders one line per artifact in the form `- <id> [<slug>] persona=<p> status=<s> tags=[…] — <title>`. The tag filter is an AND-match over the closed tag vocabulary REQ-TOOLS-150 takes from REQ-LIBRARY-089: an artifact is listed only if it carries every requested tag. Superseded artifacts are omitted unless `include_superseded` is true. With no results the output is `No artifacts found.` Lines are rendered newest first by publication time, ties broken by ascending artifact id, so the ordering is total and reproducible for any set of artifacts. A `limit` outside 1–200 is clamped to the nearer bound rather than rejected — below 1 becomes 1, above 200 becomes 200 — and the observation states the limit actually applied whenever clamping changed it, so a mistaken argument costs the agent an accurate line of output rather than a whole turn.

**REQ-TOOLS-150** — `artifact_write(slug, title, body, tags[], supersedes?)`: tags are drawn from the closed vocabulary of REQ-LIBRARY-089, which is the product's single definition of the artifact tag vocabulary; this domain lists no tag of its own and states no rejection message. What it relies on that requirement for is the permitted values, the normalisation applied to a supplied tag, the collapsing of a duplicate, and the whole-call refusal — with its message — of a publish carrying anything outside the set. `supersedes` marks an older artifact obsolete (still readable, hidden from default listings). The result reads `Published artifact <art_id> (slug: <slug>).` The writing agent's identity (persona, canonical name, task id) is attributed to the artifact. The tool is only available when the persona has `can_publish_artifacts: true`.

**REQ-TOOLS-151** — Artifact ids use the shape `art_` followed by 8 hexadecimal characters, referenced consistently across delegation attachments and tool descriptions.

### 20. Delegation Tools

**REQ-TOOLS-152** — `delegate` accepts these action fields:
- `persona` (required) — the target persona; the aliases `coder` → `coding-agent` and `playwright` → `ui-verifier` are accepted, and an unknown value is rejected with a message listing the known personas and the supported aliases;
- `task_name` (required);
- `task` (required) — the instruction text, carrying the labeled sections TASK, EXPECTED OUTCOME, MUST DO, MUST NOT DO, CONTEXT;
- `depends_on` — `bg_XXXXXXXX` task ids that must all finish successfully before the child starts; each upstream task's summary and key findings appear in the child's payload;
- `inherited_context` — ids of already-completed sibling tasks whose reports are carried into the child without imposing any ordering; an id naming a failed or unfinished task is ignored, and an id referring to nothing rejects the call;
- `category` ∈ {`quick`, `deep`, `planning`, `research`} — a routing hint, not a model name;
- `session_id` — reuse a previous delegation's session for a retry or a follow-up;
- `run_in_background` (default true) — the call does not block, and a system notification is injected into the caller's conversation when the child finishes;
- `attach_artifacts` — artifact ids or slugs whose full bodies are placed at the head of the child's payload (REQ-TOOLS-154); an id that resolves to nothing produces a warning instead of a rejection, and when the attached bodies exceed the payload size budget the surplus artifacts are dropped whole — the caller's `task` text is never truncated to make room — and the observation warns how many attachments were dropped for size;
- `suppress_auto_context` — omits the automatic index of prior sibling artifacts; a persona-level setting can force the same omission.

The attached-artifact section of the child's payload is budgeted at 100,000 characters. Attachments are considered in the order the caller listed them; the first whose full body would carry the section past the budget is dropped, and so is every attachment after it. Dropping is therefore deterministic, order-preserving, and never partial — a body is carried whole or not at all — and the observation warns how many were dropped for size (REQ-TOOLS-153).

Ids that resolve to nothing are handled by field and never uniformly: an id in `inherited_context` that names no task at all refuses the call, an id in `inherited_context` naming a task that failed or has not finished is ignored without refusing, and an id or slug in `attach_artifacts` that resolves to nothing produces a warning and never refuses. A refusal raised here creates no child and issues no task id, and is reported with status `rejected` (REQ-TOOLS-153); the spawn validation of REQ-ORCH-046 may refuse a call for reasons of its own, and those refusals are reported the same way.

What the caller observes is fixed by REQ-TOOLS-153 and by nothing else: the call returns as soon as the child has been accepted, carrying the canonical name, status, task id and any warning that requirement specifies, and the parent's turn continues — `delegate` neither suspends nor ends it, in background or foreground. This requirement together with REQ-TOOLS-153 (what the caller observes) and REQ-TOOLS-154 (how the child's payload is assembled) is the whole of the `delegate` contract, and a requirement in another domain that depends on it cites these three rather than restating any part of them.

**REQ-TOOLS-153** — The `delegate` observation carries `canonical_name` (the child's name after de-duplication), `status` ∈ {`queued`, `waiting_on_dependencies`, `waiting_on_model_slot`, `rejected`}, `task_id` in the `bg_XXXXXXXX` shape, and a human-readable message that includes any alias resolution and any attachment warning. When the target model has no free slot the task is enqueued rather than rejected, and the message conveys that the task is queued behind that model's slot cap, names the model, gives how many of its slots are in use out of how many exist, and states that the task starts by itself once a slot opens; the model name and the two counts are required content and the wording around them is the implementation's. `delegate` never suspends the parent conversation. The call returns as soon as the child has been accepted, carrying the status above, and the parent's turn continues. With `run_in_background: true` (the default) it ends there: the parent learns of completion through the system notification of REQ-TOOLS-152. `run_in_background: false` does not change the `delegate` call at all — it enrolls the parent in a wait for that one task through exactly the mechanism of REQ-TOOLS-156, as though the parent had called `wait_for_tasks` with the returned task id immediately afterwards, so the parent is paused non-blockingly and resumed with the structured summary that requirement specifies. There is one waiting mechanism in the product, not two.

A `waiting_on_dependencies` message names the tasks that are blocking the child. A `rejected` observation carries the reason, is flagged as an error, and carries no task id, because a refusal creates no child and issues none (REQ-TOOLS-152); every other status carries one. The observation renders to the model as `Task '<canonical>': <status> — <message>`, followed by a `task_id: <id>` line wherever a task id was issued. That two-line shape is fixed here because its fields are machine-readable — the canonical name, the status drawn from the closed set above, and the `task_id:` key and its `bg_XXXXXXXX` value — while `<message>` carries only the content this requirement states and its wording is the implementation's. This requirement is the product's single definition of what a `delegate` call returns and how it reads, the model-visible rendering included: the run-orchestration domain cites it (REQ-ORCH-033, REQ-ORCH-037, REQ-ORCH-050) rather than restating any part of it, and no requirement in any other domain holds a second copy of the rendering.

**REQ-TOOLS-154** — The child's payload is assembled in this observable order: (1) a workspace-root prefix giving the absolute workspace path and instructing the child to treat any other absolute path it encounters as stale; (2) for the acceptance persona only, a verifier-evidence prefix — and a delegation to that persona is refused outright while the verification gate is failing; (3) the baseline sibling-artifact index, unless suppressed under REQ-TOOLS-152; (4) the full bodies of attached artifacts; (5) the inherited-context block; (6) the caller's `task` text. The acceptance persona is the role REQ-ORCH-028 names for final acceptance, `verifier`; no other persona receives the prefix. The prefix carries what REQ-ORCH-129 specifies for the verification-evidence block — a heading stating that the bound suite has already been executed and must not be executed again, followed by a per-check table giving the check, its command, its status, its exit code, and the path to its full output — and the refusal named above is the delegation refusal of REQ-ORCH-039. A child spawned with a non-empty `depends_on` additionally receives the prior-agent-context block of REQ-ORCH-047 — that requirement fixes what the block carries and the once-only condition on its injection — which is delivered at the moment the child becomes ready rather than at spawn, and is placed ahead of (1), so it is the first content that child sees. The six items above together with that block are the whole of the payload order; a requirement in another domain that depends on the order cites this requirement rather than restating any part of it.

**REQ-TOOLS-155** — `background_output(task_id, detail_level='summary'|'verbatim')` statuses: `ok` (a report with agent/persona, status, summary, artifacts, key findings, and last reply; verbatim detail adds the exact last reply, touched files, highlighted paths, and snippets), `still_running` (`Task <id> is still running (state: <state>).`), `not_found`. Results are parent-scoped: a task whose parent is not the caller reads as `not_found` — an agent can fetch only its own children's results.

**REQ-TOOLS-156** — `wait_for_tasks(task_ids=[])`: an empty list means all of the caller's own active background children. An agent cannot wait for its own task (`An agent cannot wait for its own task.`) nor for anything but its direct children (`An agent can wait only for its direct child tasks.`). If everything requested is already terminal, the call returns immediately (zero-delay path) with a message conveying that every task the call requested was already complete and how many were requested; N = 0 — a call that requested nothing, because the caller named no ids and had no active background children — is a valid case and returns the same way, conveying that there was nothing to wait for. The count is required content; the wording around it is the implementation's. Otherwise the parent conversation is paused non-blockingly and resumed with a structured summary when the tasks finish. A parent has at most one wait outstanding at a time, and an outstanding wait does not survive the end of the parent's conversation.

This is the product's only waiting mechanism, whatever enrolled the parent in it: an explicit `wait_for_tasks` call, a `delegate` carrying `run_in_background: false` (REQ-TOOLS-153), or an orchestration pass that waits for the children it has just spawned. In every case the waited-for set is exactly the tasks named — for a pass waiting on freshly spawned children, exactly those children — and the caller's own task is never a member of it, so no wait can ever depend on the completion of the agent that is waiting. The wait ends when every task in the set has reached a terminal state, whichever way each reached it, finished, failed, or cancelled alike, or when the run is cancelled; nothing else ends it. No deadline of its own bounds a wait, and none is needed: each child is bounded by the hard per-child timeout of REQ-ORCH-088 and every non-terminal child record is closed by the sweeps of REQ-ORCH-052 and REQ-ORCH-053, so the waited-for set always reaches a terminal state and a wait can never outlive the children it waits on. A separate deadline MUST NOT be imposed — it could only fire in a state those guarantees already exclude, and firing it would resume a parent whose children still hold model slots. What a resumed parent is shown, and the suppression of a completion notification for a task a resume has already announced, are the run's (REQ-ORCH-063) and are not restated here.

This requirement is the product's single definition of the wait — its entry conditions, its refusals, its immediate-return case, and what ends it — and a requirement in another domain that depends on it cites this one rather than restating any part of it (REQ-ORCH-037, REQ-ORCH-057, REQ-ORCH-062).

### 21. User-Question Tool (ask_questions)

**REQ-TOOLS-157** — An `ask_questions` action carries 1 to 10 steps. Each step has an id that is unique within the action, a title that is not empty, an optional description, 0 to 8 options whose labels are not empty, and `allow_freeform` (default true). A step that offers no options with `allow_freeform` false is rejected. Every one of these violations is reported as a validation error when the action is constructed, before any prompt reaches the user.

**REQ-TOOLS-158** — Execution blocks on the user-prompt channel up to the response timeout of REQ-TOOLS-178, which is the shared budget `runtime.approval_timeout_seconds` and carries whatever default and reading of zero REQ-CONFIG-126 states; this requirement declares no timeout of its own. Outcomes: an answers mapping (`step_id → {selected_option, freeform_text}`, rendered under a `## User Answers` heading); cancelled (`Questions were cancelled.` — covering user cancellation, run stop, a reentrant second prompt, a presenter failure with the prompt discarded, and contexts with no conversation); or timed out (`User did not respond within <N> seconds.`). Only one prompt may be pending per conversation (reentrancy guard).

### 22. Verification-Gate Capabilities (Outside the Public Tool Surface)

**REQ-TOOLS-159** — A probe capability checks a candidate verification command before the real suite is ever run. It takes the command, the role it would fill (`test`, `typecheck`, `lint`, or `other`), and a working directory, and it answers with exactly one verdict from `verified`, `empty`, `unavailable`, `undecidable`, rendered as a single line of the form `'<cmd>': <verdict> — <note>`. The working directory is resolved beneath the workspace root; one that would escape the workspace tree is ignored without an error and the workspace root is used instead. A probe is bounded by a default timeout of 30 s. The four verdicts are distinguished by how far the candidate command got, and exactly one is returned:
- `verified` — the command ran to completion and its output identified at least one check it executed;
- `empty` — the command ran to completion and reported that it executed no checks at all (an empty suite, a filter matching nothing);
- `unavailable` — the command could not be started: its program is not present, is not executable, or the working directory could not be used. This is a fact about the host, and the note names what was missing;
- `undecidable` — the command started but its outcome cannot be read as evidence about a suite: it exceeded the probe timeout, produced output the probe cannot interpret, or ended without an attributable exit status. This is a fact about the command, and the note says which of the three occurred.

The line between the last two is therefore *could not start* against *started and told us nothing usable*, which is also the line between a verdict the user fixes by installing something and one they fix by changing the command.

**REQ-TOOLS-160** — The verification-gate check set has exactly one writer: a capability taking the proposed set of checks and a reason for the change. It declines in-band — as an ordinary reply the caller reads, never as a retryable error — in three cases, and the decline says which case applies:
- no reason was supplied — the decline asks for one and states that the reason is what the user is shown when their gate changes;
- the proposed suite is not valid — the decline says so and quotes the validation failure;
- the change is one the caller may not make on its own, namely removing the only check for a role, demoting a blocking check to advisory, or emptying the suite — the decline gives the specific reason, states that such a change has to go through an approval-gated proposal instead, and instructs the caller to report it and stop rather than pursue the same outcome another way.

Every write and every decline is recorded so the run that owns the gate can report it. This capability and the probe of REQ-TOOLS-159 are outside the public tool surface (REQ-TOOLS-003) and are available only to the run that maintains the gate. Where writes and declines are recorded is fixed by REQ-TOOLS-190.

**REQ-TOOLS-190** — Verification-gate writes and declines are recorded into a durable verification-gate record held with the session (REQ-SESSION-001), in the order the attempts were made, under the same never-altered, never-reordered, 5000-entry retention rule the permission audit obeys (REQ-TOOLS-078). This document fixes the record's content and its ordering, and no path, file name or directory for it. An entry carries: `timestamp` (ISO-8601 UTC), `session_id`, `agent_id`, `persona`, `outcome` (`write` | `decline`), `decline_case` (`missing_reason` | `invalid_suite` | `requires_proposal`; empty for a write), `reason` (the caller's stated reason for the change, empty when none was supplied), `checks` (the proposed check set as the caller supplied it), and `detail` (the validation failure or the specific reason quoted in a decline; empty for a write). Every attempt produces exactly one entry, so a decline is exactly as durable as a write and a reader can reconstruct what was attempted as well as what took effect. Each entry additionally emits a timeline event so the run that owns the gate can report it (REQ-ORCH-126), and a failed evidence recording logs a warning without turning a decline into an error the caller would retry.

The record MUST also be obtainable as a file the user chooses, under the export obligation REQ-SESSION-199 places on the records it names and REQ-EVENTS-166 states in full; neither is restated here. Two consequences are worth naming because they are what a reader of *this* record wants: the export carries the declines as well as the writes, in the order the attempts were made, and it states how many entries the retention cap dropped, so a trimmed record can never be mistaken for a complete one. Like every export, it is a user-initiated action producing a file and never a way to watch a run (REQ-SESSION-071).

**Whether a record is offered as an export turns on redaction safety, and never on who reads it.** This requirement is the product's single statement of that test, and no requirement in any other domain holds a second copy of it: **a record gains an export when it carries no unredacted user or tool content, and does not gain one when it does.** That only this application reads a record is *not* a reason to withhold an export and never was — a record only this application can read is exactly the record a user needs their own copy of, since it is what they consult when they do not trust this application's rendering of events. This record qualifies because everything it holds is the caller's own stated reason, the check set it proposed, and the product's own validation detail. The permission audit qualifies for one specific reason, which is worth naming because it is the property and not the record that earns the export: REQ-TOOLS-079 gives an entry no argument values at all beyond the redacted command facet inside `summary`.

**The tool-call evidence record of REQ-SESSION-136 does not qualify, and MUST NEVER gain an export — not under this rule, and not under any later widening of it.** It deliberately holds the arguments an agent passed exactly as they were passed, unredacted, which is the whole reason it exists and is the reason the wire never carries them. Anything that exported it would hand a user's prompts, file paths, command lines and any secret that passed through them to a file this product no longer controls. A future requirement proposing such an export is in conflict with this one and MUST be refused rather than reconciled; a future requirement proposing an export for some *other* record is settled by applying the test above to that record's own content, and never by arguing from this list.
