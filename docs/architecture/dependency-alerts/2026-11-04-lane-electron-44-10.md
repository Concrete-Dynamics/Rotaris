**Why 44.10.0.** It was the newest 44 release past `minimumReleaseAge`'s seven days (published 2026-10-27; 44.10.1 on
2026-10-31 and 44.10.2 on 2026-11-03 were younger), and it is outside all four ranges above. It declares the same three
dependencies as 44.3.0 (`@electron/get` `^5.0.0`, `@electron-internal/extract-zip` `^1.0.1`, `@types/node` `^24.9.0`), so
the lockfile moved only Electron's own lines, and `pnpm install --frozen-lockfile` then fetched the runtime.

**Why not 45.** Dependabot's `electron` group (pull request #49, 44.3.0 → 45.0.0 with electron-builder and electron-vite)
stays open and red: its `gate` job (CI runs 41876152753 and 41876164187) died on the same JavaScript heap exhaustion as
`main`'s gate since that day, and its `package` job refused the packaged launch, "pnpm package refused: expected one
session, found 0", where `main`'s `package` job under 44.3.0 passed (run 41829796480). A major moves the Chromium and Node
lines the build toolchain's rules were measured against ([ADR-0056](../adr/0056-the-build-toolchain/11-the-electron-pin-moves-to-44100-2026-11-04-r-091.md)).
The move to 45 is that pull request's, and its packaged-launch refusal is
[a note](../../defects/the-packaged-app-under-electron-45-opens-no-session-in-the-package-jobs-launch.md).

**After:** the whole tree's report lists no Electron advisory; 3 high, 5 moderate remain, all in the build and test tools
(`undici` 6.28.1 under `node-gyp`, `@vitest/mocker` 4.1.11, `minimatch`), as §3 of
[the audit reading](2026-11-01-audit-gate.md) recorded them. The `undici` copy is
[a note](../../defects/the-build-tools-undici-6-copy-sits-inside-three-high-advisories-and-keeps-the-vulnerabilities-check-open.md).

## 3. The audit that blocks now reads the runtime

`pnpm deps:audit:runtime` (`pnpm audit --json | node tools/runtime-audit/cli.mjs`) runs in `ci.yml`'s gate job after
`pnpm deps:audit` and before `pnpm check`, blocking. It reads the whole tree's report and keeps only the advisories at high
and above whose package is the shipped runtime (`SHIPPED_RUNTIME`, Electron alone), so the build tools' advisories stay
report-only as the audit reading left them; a report it cannot read (an error object, an empty pipe) exits 2, never 0.
An exception is written as the production audit's are (`auditConfig.ignoreGhsas`, the audit reading's §4): pnpm 11.9.0
drops an ignored advisory from the report's `advisories` (measured here by ignoring GHSA-xjj6-f33q-929c for one run, then
removing it), while `metadata.vulnerabilities` still counts it, so the module reads `advisories` alone. The release SBOM
corrects the same blind spot by adding Electron (`tools/sbom/sbom.mjs`).

**First execution, on this tree:** fed the report read at 44.3.0, the command printed
`electron 44.3.0: high GHSA-jr5w-w6x2-84p9 (>=44.0.0-alpha.1 <44.9.1; fixed in >=44.9.1) …` and exited 1 (also under
`cmd`, the shell pnpm runs a script with on Windows, so the pipe's status is the module's); fed an error object it exited
2; `pnpm deps:audit:runtime` over the moved tree read "shipped runtime (electron): no advisory at high or above" and exited
0. `tools/runtime-audit/runtime-audit.test.ts` holds the selection, the refusal, the pin (one exact Electron, the
lockfile's, at or above the fixed version of every Electron advisory these readings name) and the CI step.

## 4. Verification on this tree

- **The runtime.** `ELECTRON_RUN_AS_NODE=1 electron -p process.versions` gives Electron 44.10.0, Node 24.22.1, Chromium
  152.0.7977.169, V8 15.2.124.45-electron.0 and `modules` 149 (arm64): the binary interface is unchanged.
- **The fuses.** @electron/fuses read the 44.10.0 `electron.exe` as the nine fuses 44.3.0 carries, in the same states
  (`apps/desktop/scripts/build-hooks.test.ts`'s fixture). A scratch copy was refused by `checkFuses` fuse by fuse, then,
  flipped with `electron-builder.yml`'s map, read back as asked.
- **`pnpm build`** and `pnpm code-intel:bundle` green.
- **Proofs**, one at a time after the build, no other tree's Electron running at the start, host CPU 26 to 83 % at each
  launch from other sessions: `driver-proof` 42 passed, 1 failed, 2 noted (the failure is step 8's `1000×682`, the known
  Windows reading of
  [its note](../../defects/driver-and-git-proofs-read-the-window-two-pixels-taller-at-150-percent-display-scale.md), which
  the sighting list now carries); `sessions-proof` 11 scenarios passed; `terminal-stream-proof` passed; `sandbox-proof`
  passed (IC-8 not discharged, as on every Windows host); `store-resolution-proof` 38 checks passed; `part-h-proof`
  passed. Each launch loads the store and terminal bindings into Electron's own processes.
- `pnpm verify:plan --base=origin/main` named no proof suite and asked for review of the two manifests; Electron is the
  runtime of every proof, and the six above were chosen for the processes, the store, the terminal and the renderer's
  perimeter, not the whole sweep the acceptance round runs.

**Not here, and why.** `pnpm package` does not run on this host
(`docs/defects/pnpm-package-on-the-windows-arm64-host-fails-rebuilding-node-pty-for-want-of-spectre-mitigated-libraries.md`),
so ADR-0056's rule 4 for 44.10.0, the bindings rebuilt and loaded under the packaged binary, is CI's `package` job on the
landed head. No Linux or macOS artifact was produced (IC-3).
