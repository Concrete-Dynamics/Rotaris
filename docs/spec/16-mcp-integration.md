# MCP Server Integration

## Overview

The product integrates external MCP (Model Context Protocol) servers as tool providers for its agent personas. Server entries come from three merged sources: layered YAML configuration, files named `mcp.json` picked up automatically from well-known locations, and three shipped default entries (a remote web-search server, a headless browser-automation server, and a bundled code-intelligence server). Each persona carries a subset of servers and, optionally, a per-server tool allow-list; whatever a persona's prompt lists is precisely what that persona may invoke — no more, no less. A missing or broken server never fails a run: it is skipped, a warning reaches the user, and the run proceeds. Within one session each server has exactly one shared connection, opened on first demand and closed a single time when the session ends. Users manage servers from the desktop application alone: the MCP category of the settings view lists every configured server with health probing and a session enable toggle, and holds the secrets surface whose values are always masked wherever they are rendered.

## Requirements

### Server Configuration Model

- **REQ-MCP-001** — A server entry SHALL support exactly these fields with these defaults: `type` (one of `"stdio"`, `"http"`, `"sse"`; default `"stdio"`), `command` (string, optional), `args` (list of strings, default empty), `env` (string-to-string map, default empty), `cwd` (string, optional), `url` (string, optional), `headers` (string-to-string map, optional), `request_timeout` (integer seconds, optional), `disabled_tools` (list of strings, default empty), `tool_name_map` (string-to-string map, default empty), `tools` — an optional static tool-metadata list, default empty, whose entries carry a required `name` and a `description` defaulting to `""` — and `enabled` (boolean, default `true`). What `enabled` does once the entry resolves is fixed by REQ-CONFIG-465, which this requirement relies on for that behavior and does not restate; the field is named in this set because the set is closed, and a schema declaring "exactly these fields" while a field four requirements require is declared only elsewhere is wrong rather than narrower.

  This requirement is the product's single definition of the tool-server entry schema — the field set, each field's name, its type, whether it is optional, and its default. A document that presents, validates, stores, merges, or documents a server entry SHALL cite this identifier rather than restating any of those, and a field a surface needs is added here rather than declared elsewhere. What a citing document may add is where the entry is written and what its scope does with it; it may not hold a second copy of the field list, and a shorter list elsewhere is a stale copy rather than a narrower schema.

- **REQ-MCP-002** — A server entry that comes from a YAML scope SHALL be rejected at configuration load, with an error naming the offending server, its transport type and the offending field, when a `stdio` entry omits `command` or supplies a `command` that is the empty string or is entirely whitespace, when an `http`/`sse` entry omits `url` or supplies an empty `url`, or when `request_timeout` is set to a value that is not a whole number greater than zero (REQ-MCP-003). An absent `command` and an empty `command` are the same defect and SHALL be reported alike, so no `stdio` entry reaching a later stage ever carries an empty command. The same defects in an entry read from an `mcp.json` discovery file SHALL NOT fail loading; that entry alone is dropped with a warning (REQ-MCP-018, REQ-MCP-023). Every defect found SHALL be reported, not only the first.

- **REQ-MCP-003** — `request_timeout` is a whole number of seconds. When it is set on a server entry, every individual tool call to that server SHALL be allowed that many seconds, measured from the dispatch of the call to the receipt of its result, and the same allowance SHALL apply to every tool that server exposes. The allowance is per call: each call starts with the full budget regardless of time consumed by earlier calls. `request_timeout` SHALL NOT govern tool discovery (REQ-MCP-046) or health probing (REQ-MCP-054), each of which carries its own budget. When `request_timeout` is unset the allowance is the product-wide default of 300 seconds. A `request_timeout` that is zero, negative, or not a whole number SHALL be rejected at configuration load exactly as the defects of REQ-MCP-002 are, and SHALL never be silently treated as unset. When the allowance is exhausted, the call SHALL end as a failed tool call and SHALL NOT be retried by the product: the agent SHALL receive a tool result marked as an error conveying that the named server did not answer within the allowance; the tool row SHALL settle as `failed` in the vocabulary of REQ-MONITOR-105; the connection SHALL be left open and usable for later calls; and the run SHALL continue, its outcome unaffected except through whatever the agent then does. This holds whether the allowance came from `request_timeout` or from the 300-second default, and holds for every transport.

- **REQ-MCP-004** — A tool SHALL be denied when any candidate spelling of REQ-MCP-057, derived from the name the server itself reports, matches an entry of `disabled_tools`. A denied tool SHALL appear neither in the persona prompt nor among the tools the persona can call, and SHALL stay denied even when a persona grant names it: denial outranks every grant (REQ-MCP-056).

- **REQ-MCP-005** — `tool_name_map` SHALL map names the server reports (keys) to replacement names (values). A rename SHALL be applied only to tools that survive `disabled_tools` filtering (REQ-MCP-049) and SHALL leave the tool's description unchanged. A replacement name SHALL be the name the model both sees and calls: it is the name printed in the prompt (REQ-MCP-101), the name the model writes in a tool call, and the name the product maps back to the server-reported name when it dispatches that call, so the original name SHALL NOT remain callable once a rename covers it. Matching in `disabled_tools` and in persona grants SHALL nevertheless be performed against the candidate spellings of REQ-MCP-057 derived from the server-reported name only, so an entry written against a replacement name SHALL match nothing; renaming is a presentation decision and never a permission decision. Two entries of one server's `tool_name_map` SHALL NOT map to the same replacement name, and a replacement name SHALL NOT equal the reported name of another surviving tool of the same server; either collision is a configuration error naming the server and both names.

- **REQ-MCP-006** — The runtime tool surface of a server SHALL always come from live discovery (REQ-MCP-046); the static `tools` list on a server entry SHALL have no effect on which tools are advertised or callable.

- **REQ-MCP-007** — A persona SHALL support: `mcp_servers` (list of server names it carries) and `mcp_tools`, an optional per-server tool grant map (server name drawn from `mcp_servers` → list of original tool names). Given a carried server with no grant entry (or the whole map unset), the persona receives every tool that server exposes; given a grant entry that is an empty list, the persona receives none of that server's tools. Server-level `disabled_tools` applies on top of any grant.

- **REQ-MCP-008** — The top-level configuration SHALL carry a named map of server entries under `mcp_servers` and a machine-maintained per-server origin map under `mcp_server_sources` (values per REQ-MCP-026). The origin map SHALL never be user-settable; hand-written values are overwritten during loading.

- **REQ-MCP-009** — Resolving a persona's server set SHALL be side-effect free on configuration: given the same configuration shared across personas and repeated resolutions, when any persona is resolved, then no configured entry (including its `args` list) is observably changed and every resolution yields identical results.

- **REQ-MCP-117** — Wherever this domain requires servers, tool names, secret keys or secret rows to be presented or written in ascending order, that order SHALL be ascending code-point order over the raw string — comparing Unicode scalar values position by position, shorter string first where one is a prefix of the other — case-sensitive, and identical on every platform and under every locale the product runs in. No locale-aware collation, case-folding or accent-folding SHALL be applied. This one rule SHALL govern every ordered presentation in this domain, so two surfaces listing the same names never disagree: the server list and the per-server secret rows of REQ-MCP-109, the expected-keys hint of REQ-MCP-109, and the servers and tools of the prompt's MCP section (REQ-MCP-101).

### Shipped Default Servers

- **REQ-MCP-010** — The built-in defaults SHALL contain exactly three server entries and no others, declared under the names REQ-CONFIG-181 fixes — `web_search`, `browser` and `code_intelligence`:
  - **`web_search`**: remote transport over HTTP, whose `url` embeds a `${VAR}` placeholder naming `ROTARIS_SEARCH_API_KEY`, the environment variable that carries its API key (substituted per REQ-MCP-088), with `request_timeout` 600 and `enabled: false` (REQ-CONFIG-181, REQ-CONFIG-465);
  - **`browser`**: `stdio` transport whose `command` is `npx` and whose `args` carry the non-interactive install flag `-y`, name the package at an exact `MAJOR.MINOR.PATCH` version (never a range and never a floating tag), and select headless operation; declared with `enabled: false`;
  - **`code_intelligence`**: `stdio` transport whose `command` is the reserved bundled-runtime token of REQ-MCP-033 and whose `args` select stdio transport and the host-integration mode in which the server does not advertise its own file-read, directory-listing or shell tools while continuing to advertise its pattern-search tool, and which carries no project path — the path is supplied per run by REQ-MCP-034. This is the one default entry that is enabled by default (REQ-CONFIG-181).

  On these three entries, no field beyond those named above SHALL be set; every other field takes the default given in REQ-MCP-001. In particular, only the `web_search` entry carries a `request_timeout`, so tool calls to the `browser` and `code_intelligence` defaults are bounded by the 300-second default of REQ-MCP-003, and none of the three carries `disabled_tools`, `tool_name_map` or a static `tools` list.

  The `web_search` URL template, the `browser` package identifier, its pinned version string and its headless argument, and the arguments that select the `code_intelligence` transport and host-integration mode are identities of the third-party services filling the three roles. REQ-CONFIG-181 leaves those identities to the implementation and permits them to change between releases; this document therefore does not fix them, and fixes instead the roles, the names, the transports, the timeout, the enablement, and — for `code_intelligence` — the binding manifest of REQ-MCP-116.

- **REQ-MCP-011** — The default `code_intelligence` entry SHALL pin the bundled runtime to one exact release, written as a complete `MAJOR.MINOR.PATCH` version string. That entry SHALL NOT name a branch, a repository revision, a floating tag such as `latest`, or a version range; the pin SHALL be verifiable by inspecting the shipped default entry alone, and the version string SHALL be identical to the one the binding manifest of REQ-MCP-116 records. Two installations of the same product build SHALL consequently start the same runtime version. The distribution identifier to which the pin applies is a third-party identity left to the implementation by REQ-CONFIG-181 and is recorded in that manifest rather than fixed here; the pinning discipline above is what this document fixes, and a build that violates it is defective.

- **REQ-MCP-012** — No default server named `lsp` SHALL ship, and no default persona SHALL reference one. The name remains user-configurable; a persona referencing `lsp` (or any name) without a matching server entry SHALL fail validation per REQ-MCP-103.

- **REQ-MCP-013** — No git-inspection MCP server SHALL ship in the defaults or be referenced by any default persona. Read-only git inspection SHALL remain achievable as a user configuration pattern by combining a user-added server with a per-server tool allow-list (e.g. granting only a status tool) and/or `disabled_tools`. This requirement and REQ-MCP-015 are canonical for the shipped defaults: any other description of the product that claims a git-inspection server among the defaults, or that limits project-memory writing to a single persona, describes something the product does not do and is a defect in that description rather than a second reading of this domain.

A row naming no server means an empty `mcp_servers` list for that persona. The table is closed for this domain's purposes without claiming to enumerate every built-in persona: the delegation role vocabulary is owned by REQ-ORCH-028, and the two further rows here — `intent-classifier` and `project-initializer` — are personas that are not delegation targets. A built-in persona that does not appear in this table SHALL carry an empty `mcp_servers` list and therefore no MCP tools at all, so adding one can never widen the MCP surface without amending this table.

  | orchestrator | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | intent-classifier | (none) | — |
  | architect | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | coding-agent | `code_intelligence` | READ + EDIT + MEMORY-WRITE |
  | tester | `browser`, `code_intelligence` | READ + EDIT + MEMORY-WRITE |
  | docs-writer | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |

  | librarian | `web_search` | — (no `code_intelligence` server) |

  Where a persona carries the `browser` or the `web_search` server it SHALL have no `mcp_tools` entry for that server, and SHALL therefore receive that server's whole discovered surface (REQ-MCP-007). A persona carrying a server the built-in defaults declare with `enabled: false` receives that server's tools only once the user enables it (REQ-CONFIG-465); until then the server is absent from the run exactly as REQ-MCP-078 describes, without warning.

- **REQ-MCP-015** — The four code-intelligence grant tiers SHALL be composed from the tool names the pinned runtime of REQ-MCP-011 reports, with exactly these cardinalities and coverage:
  - **READ** — ten tools: symbol lookup, per-file symbol overview, referencing-symbol search, implementation search, declaration search, pattern search, per-file diagnostics, project-memory listing, project-memory reading, and usage-instruction retrieval.
  - **EDIT** — seven tools: symbol-body replacement, insertion before a symbol, insertion after a symbol, symbol rename, safe symbol deletion, single-file content replacement, and cross-file content replacement. Carried only by coding-agent, tester and refactorer.
  - **MEMORY-WRITE** — two tools: project-memory writing and project-memory editing. Carried by every persona that carries the code-intelligence server.
  - **ONBOARDING** — one tool: project onboarding. Carried only by project-initializer.

  The four tiers are pairwise disjoint sets of tool names, so a persona's `code_intelligence` grant holds a countable number of names: 12 for READ + MEMORY-WRITE, 19 for READ + EDIT + MEMORY-WRITE, and 13 for READ + MEMORY-WRITE + ONBOARDING. No built-in grant SHALL name the runtime's memory-deletion, memory-rename or dashboard-opening tools, and every name appearing in a built-in grant SHALL be a name the pinned runtime returns from `tools/list`.

  The literal name strings are the pinned runtime's own vocabulary, which REQ-CONFIG-181 leaves to the implementation; they SHALL be recorded once in the binding manifest of REQ-MCP-116 and read from there by every part of the product that needs them, and SHALL NOT be written out a second time anywhere. The tiers above are therefore defined by capability and bound to strings by that manifest, and a grant is verifiable without this document naming a string: the build SHALL check that the manifest's four tiers have exactly the cardinalities and the coverage stated above, that they are pairwise disjoint, that no tier holds a never-grant name, and that every name in all four tiers plus the three never-grant names is reported by the pinned runtime's `tools/list`. A build failing any of those checks SHALL be treated as defective and SHALL NOT ship. An upstream rename therefore fails a build rather than silently degrading a grant at run time through REQ-MCP-058.

### Configuration Auto-Discovery (`mcp.json`)

- **REQ-MCP-017** — Discovery SHALL read at most two files: the project-level `<workspace_root>/.mcp.json` (origin tag `discovered-project`) and one user-level file (origin tag `discovered-user`) located per platform: macOS `~/Library/Application Support/mcp.json`; Windows `%APPDATA%/mcp.json` (when `APPDATA` is unset, user-level discovery is skipped entirely); other systems `~/.config/mcp.json`. This requirement is the product's single definition of where `.mcp.json` auto-discovery looks, including the skipping of user-level discovery when `APPDATA` is unset; the shape of a discovery file, the keys it accepts, and how it is parsed are owned by REQ-MCP-018 through REQ-MCP-024 and REQ-MCP-027, which together produce entries in the server-entry schema of REQ-MCP-001. No requirement in any domain SHALL hold a second copy of the locations, the file's shape, or the parsing rules; a requirement that needs them SHALL cite the requirement here that owns the part it needs and state only what it adds.

- **REQ-MCP-018** — A discovery file's servers SHALL be read from the top-level key `mcpServers`, or failing that `servers` (checked in that order); if neither holds an object, the file contributes nothing. A missing file SHALL be silently ignored; unreadable or invalid JSON SHALL log a warning naming the file and contribute nothing; a JSON root that is not an object SHALL log a warning and contribute nothing. None of these conditions may fail configuration loading.

- **REQ-MCP-019** — Discovered server names SHALL match `^[a-zA-Z][a-zA-Z0-9_-]*$`; a non-matching name SHALL be skipped with a warning naming the offending name and file. A server entry whose value is not an object SHALL likewise be skipped with a warning.

- **REQ-MCP-020** — Per-entry transport determination SHALL be: an explicit `type` wins; otherwise `http` when a `url` is present, else `stdio`. Stdio entries SHALL accept `command`, `args` (default empty), `env`, `cwd`, and `envFile`; remote entries SHALL accept `url` and `headers` while retaining `env` and `cwd`.

- **REQ-MCP-021** — An `envFile` path SHALL resolve relative to the declaring file's directory and be parsed line-by-line as `KEY=VALUE`, skipping blank lines and `#` comments and stripping single or double quotes around values. An unreadable `envFile` SHALL log a warning and yield an empty map without aborting discovery. Explicit `env` entries SHALL override `envFile` entries on key collision.

- **REQ-MCP-022** — In discovered `env` values and `cwd`, the placeholder `${workspaceFolder}` SHALL resolve to the workspace root and `${env:VAR}` SHALL resolve to the process environment (empty string when unset); `cwd` SHALL additionally be path-normalized. Any other `${...}` placeholder SHALL stay literal with a warning.

- **REQ-MCP-023** — Any failure while parsing one server entry (for example, a stdio entry without a command, or with a command that is empty or whitespace) SHALL skip only that entry with a warning naming the server and its source; discovery of the remaining entries continues. A key inside a server entry that is not one of those REQ-MCP-020 and REQ-MCP-021 accept SHALL NOT be such a failure: it is ignored, and the entry loads on its remaining keys (REQ-MCP-027).

- **REQ-MCP-024** — On a name collision between the user-level and project-level discovery files, the project-level entry SHALL win.

- **REQ-MCP-025** — Whole-configuration merge order for servers SHALL be: built-in defaults → discovered `mcp.json` servers → global `agents.yaml` (per-user configuration directory) → workspace `agents.yaml` (`<workspace>/.rotaris/agents.yaml`). Same-named entries from later scopes merge field-wise into earlier ones. Consequences that SHALL hold: discovered servers override same-named defaults; YAML in either scope overrides discovered entries; global YAML servers survive a workspace configuration that has no server section at all.

- **REQ-MCP-026** — After merging, the origin map SHALL record, per final server name: `"yaml"` when any YAML scope named it, else the discovery tag (`"discovered-project"` / `"discovered-user"`), else `"default"`.

- **REQ-MCP-027** — A discovery file SHALL be consumed read-only: after any number of configuration loads, every `mcp.json` the product has read SHALL be byte-for-byte identical to its content before those loads — nothing rewritten, reformatted, reordered, or added. A file that uses only the keys named in REQ-MCP-018, REQ-MCP-020 and REQ-MCP-021 SHALL load without the user editing it first. What the agent runtime receives SHALL be the normalized description of REQ-MCP-043, never the discovery file's own shape. A key inside a server entry that lies outside that set SHALL be **ignored with a warning** naming the file, the server and the key, and SHALL NOT cause the entry to be skipped: a file written for another client loads on the keys this product understands, and a mistyped key is still reported rather than swallowed. The warning SHALL be emitted at most once per (file, server, key) per configuration load.

### Command Resolution

- **REQ-MCP-028** — Path-like commands SHALL never be rewritten by shorthand resolution: commands starting with `/`, `./`, `../`, or `~`, containing a backslash, or in drive-letter form (`X:...`) pass through unchanged.

- **REQ-MCP-029** — A fixed known-executable set SHALL pass through unchanged: `npx`, `npm`, `node`, `uvx`, `uv`, `pipx`, `pip`, `python`, `python3`, `deno`, `bun`, `docker`, `podman`, `bash`, `sh`, `zsh`, `fish`, `cmd`, `powershell`, `pwsh`, `go`, `cargo`, `java`. An empty command is likewise never rewritten — shorthand resolution invents no command — but an entry carrying one never reaches a run: it is rejected at load from a YAML scope and dropped from a discovery file (REQ-MCP-002, REQ-MCP-023), and were one to arise from any other path it is unavailable, never active (REQ-MCP-037).

- **REQ-MCP-030** — The shorthand `uvx:<pkg>` SHALL resolve to command `uvx` with `<pkg>` prepended to the arguments; bare `uvx:` passes through unchanged. When `uvx` is not on PATH, a warning SHALL be logged naming the original command, but resolution still occurs (availability is judged separately, REQ-MCP-037).

- **REQ-MCP-031** — The shorthand `npm:<pkg>`, or any command starting with `@` (a scoped package), SHALL resolve to command `npx` with arguments `-y <pkg>` prepended; bare `npm:` passes through unchanged; a missing `npx` logs the analogous warning.

- **REQ-MCP-032** — Any other bare command name SHALL pass through unchanged — no implicit package-manager guessing for unscoped names.

- **REQ-MCP-033** — The reserved command token `builtin:code-intelligence` SHALL be accepted in place of a real executable for the bundled code-intelligence runtime. It SHALL be recognized before every other rule of this section, so it is never treated as a path (REQ-MCP-028), as a known executable (REQ-MCP-029), as a `uvx:`/`npm:` shorthand (REQ-MCP-030, REQ-MCP-031) or as a bare name (REQ-MCP-032), and it SHALL never be looked up on PATH. A `stdio` entry whose `command` equals that token SHALL resolve to a launch of the bundled code-intelligence server: in an interpreted installation, through the application's own language runtime; in a frozen single-binary installation, through the application's own executable with the same token `builtin:code-intelligence` as its first argument — one literal serves as both the token and the sentinel, so there is nothing else to keep in step. A process started with that first argument SHALL answer the MCP protocol as the code-intelligence server on its standard streams, SHALL present no user interface of any kind, SHALL open no window, and SHALL terminate with the exit status the server produced — whatever that status is, the parent process observes the server's own code and no substitute. The token SHALL be usable by a user in a hand-written entry exactly as the defaults use it, and a `stdio` entry carrying it SHALL count as available unconditionally (REQ-MCP-037).

- **REQ-MCP-034** — When a `stdio` entry's resolved arguments contain the code-intelligence runtime's server-launch subcommand and contain no project-selection argument (neither the explicit project-path option nor the option that takes the project from the working directory), the command line resolved for a run SHALL be the configured one with exactly two further arguments appended at the end of the argument list: the project-path option, followed by that run's workspace root as a separate argument. The match SHALL be made on the presence of the launch subcommand alone, independently of the entry's configured name, so any entry that launches that runtime is bound and no other `stdio` entry is altered. A project-selection argument already present SHALL be left exactly as configured. For a run against an isolated working tree, the appended path SHALL be that tree's root. A server launched with a project path SHALL NOT advertise its project-switching or configuration-introspection tools in `tools/list`. The literal spellings of the launch subcommand and of the two project-selection options SHALL be read from the binding manifest of REQ-MCP-116 and SHALL NOT be written out anywhere else.

- **REQ-MCP-035** — Filesystem-server path fill-in: given a stdio server one of whose resolved arguments is exactly one of the recognized filesystem-server package identifiers — `@modelcontextprotocol/server-filesystem` or `filesystem-mcp` — then, taking the arguments that follow that one as the path arguments: with no path arguments, the workspace root SHALL be appended; with exactly one path argument that does not exist on disk and a server whose configured name is literally `filesystem`, everything after the package identifier SHALL be replaced by the workspace root, accompanied by a warning naming the server, the missing path, and the substituted workspace root; in every other case the arguments SHALL be left untouched.
  > **Narrowed by [`PD-MCP-002`](../product/directives.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, the root this fill-in appends or substitutes is that tree's root; a path the user configured is left as configured.

- **REQ-MCP-036** — A command-line invocation of the code-intelligence runtime SHALL be derivable from the configured server entry, so that the project setup of REQ-MCP-099 drives the same build the server itself runs. The derived invocation is a command plus an argument list: the command is the entry's resolved `command` (shorthands of REQ-MCP-030 to REQ-MCP-033 expanded), and the argument list is exactly the prefix of the entry's resolved arguments that precedes the first occurrence of the server-launch subcommand, that subcommand and everything after it excluded. Transport, mode and project-selection arguments SHALL therefore never appear in the derived invocation. No invocation SHALL be derived for a remote entry, for an entry whose `command` is empty, or for an entry whose arguments contain no launch subcommand; in each of those cases the dependent setup task SHALL be reported as unavailable with the non-retryable failure of REQ-MCP-099, and no substitute command SHALL be used. The literal spelling of the launch subcommand SHALL be read from the binding manifest of REQ-MCP-116. This derivation exists so the product can run the runtime's own executable as a child process; it is not a surface any user drives.

### Availability and Drop-Not-Fail Semantics

- **REQ-MCP-037** — A single availability rule SHALL be used by every surface (agent construction, desktop UI, initialization-task gating): `http`/`sse` servers count as available unconditionally (nothing probes reachability at configuration time); a `stdio` server whose `command` is the reserved token of REQ-MCP-033 counts as available unconditionally, because what it resolves to ships with the application; every other `stdio` server is available if and only if its command — after shorthand resolution (and, when a workspace is supplied, the full stdio resolution path) — is found on PATH. A `stdio` entry whose `command` is empty or whitespace is **unavailable**; it is never reported as active by any surface, and REQ-MCP-002 and REQ-MCP-023 mean such an entry should not have survived loading in the first place. Supplying a workspace root SHALL never change the answer. No two surfaces may disagree on availability for the same configuration.

- **REQ-MCP-038** — Given a persona referencing a server name absent from configuration, when the persona is resolved, then a warning SHALL be produced naming both the server and the persona, and the run proceeds without that server.

- **REQ-MCP-039** — Given a persona whose generic tool list names a configured MCP server, when the persona is resolved, then the name SHALL be treated as an MCP server with a logged warning advising the user to move it to the server list (see also REQ-MCP-105).

- **REQ-MCP-040** — A server that is disabled SHALL be skipped at persona resolution with an informational log naming the server and stating which of the two controls disabled it: its configured `enabled: false` (REQ-CONFIG-465) or the session override of REQ-MCP-094. A skipped server SHALL produce no warning and no session issue — turning a server off is a choice, not a fault.

- **REQ-MCP-041** — Given an unavailable stdio server carried by a persona, when the agent is constructed, then the server SHALL be dropped with a per-persona warning stating the command was not found on PATH and tools will not be available; additionally, a detailed log line including both the raw and resolved command SHALL be emitted at most once per server per process. The run SHALL never fail for this reason, and the UI SHALL show the server as unavailable.

- **REQ-MCP-042** — Given a server whose most recent tool-discovery attempt failed (REQ-MCP-048), when a persona carrying it is resolved, then a warning SHALL be produced stating the server failed tool discovery and its tools may be unavailable.

- **REQ-MCP-043** — The per-server description handed to the agent runtime SHALL be normalized to exactly the following keys and no others: a transport discriminator distinguishing stdio, streamable HTTP and SSE; for stdio — `command` (resolved per REQ-MCP-028 to REQ-MCP-035), `args` (the resolved argument list), `env` (the resolved environment of REQ-MCP-087), and `cwd` (the entry's configured value, or the workspace root when unset); for remote transports — `url` and, when configured, `headers`; and, when `request_timeout` is set, a numeric `timeout` in seconds. A key not in that list SHALL be absent, and `timeout` SHALL be absent when `request_timeout` is unset, so a consumer can compare the description's key set against this list exactly. Tool disabling, renaming and grants SHALL be applied by the product before this description is produced (REQ-MCP-049, REQ-MCP-059) and SHALL NOT be expressed as additional keys. A remote entry SHALL NOT be subjected to a PATH check while this description is produced. The transport discriminator SHALL take exactly the values `stdio`, `http` and `sse` — the same three tokens the `type` field of REQ-MCP-001 uses, so the domain carries one transport vocabulary and not two, `http` denoting streamable HTTP. This description SHALL be produced for every agent backend the product supports: a backend that cannot be given external tool servers is not a supported backend, and no run path SHALL substitute a backend that silently drops the MCP surface.
  > **Narrowed by [`PD-MCP-002`](../product/directives.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, an unset `cwd` defaults to that tree's root; a configured `cwd` is unchanged.

- **REQ-MCP-044** — Every warning accumulated during agent construction SHALL be delivered through two channels: a transient acknowledgement of the Warning kind (REQ-NOTIFY-019), which stays on screen for the acknowledgement lifetime of REQ-NOTIFY-011 and for no other span, and a persisted session issue record with kind `mcp_config`, severity `warning`, and actor `orchestrator`, visible in the session's issues file after the run. This document states no lifetime of its own, REQ-NOTIFY-011 being the product's single definition of one and expressly forbidding a surface from declaring another; the durable half of this delivery is the issue record and never the acknowledgement, so no obligation here turns on how long the acknowledgement is readable. *Amended 2026-09-06 under ESC-33: the first channel previously read "a UI toast of severity 'warning' with an 8-second auto-dismiss". The notice pipeline's first execution (ADR-0049, Part V) found that figure to be a second copy of the lifetime REQ-NOTIFY-011 fixes at 4200 ms, and the owner ruled the copy the defect rather than the definition. The 8 s is not preserved anywhere: a warning that must outlive the acknowledgement is a persistent notice under REQ-NOTIFY-040, not a longer transient.*

- **REQ-MCP-045** — The project-initialization task registry SHALL use the availability rule of REQ-MCP-037 to decide whether the code-intelligence setup task applies to a workspace: the server must be configured and its command must resolve.

### Tool Discovery, Caching, and Health Probing

- **REQ-MCP-046** — Tool discovery SHALL connect to a server over its configured transport, perform the MCP `initialize` handshake followed by `tools/list`, and return the server's tool metadata (name, description). The default discovery timeout SHALL be 30 seconds.

- **REQ-MCP-047** — Discovery SHALL be stable and SHALL not re-interrogate an unchanged server. Within the lifetime of one process, repeated discovery requests for a server whose name, `type`, `command`, `args`, `env`, `cwd`, `url`, `headers` and workspace root are all unchanged SHALL yield the same tool list every time, and the server SHALL observe at most one `initialize`/`tools/list` exchange arising from them. A difference in any one of those nine values SHALL make the next request interrogate the server afresh. Reloading the configuration SHALL likewise make the next request for every server interrogate it afresh, so a server that failed discovery before the reload but answers after it SHALL produce no further REQ-MCP-042 warning. This stability is **held for the life of the running instance and never persisted**: no discovery result, failure memory or health outcome SHALL be written to disk or carried across application launches, so a relaunch interrogates every server afresh. Because at most one instance of the application runs (REQ-STARTUP-161), that memory is the whole application's: every window and every run observes the same tool list for a server whose nine values are unchanged — the workspace root being one of those nine, so two windows on different workspaces are correctly interrogated separately — and there is no second holder of a tool list anywhere to wait on, lock against, or invalidate.

- **REQ-MCP-048** — Discovery failure SHALL never raise to the caller: on any connection, protocol, or timeout error the request SHALL return an empty tool list, a warning SHALL be logged at most once per identity noting that the persona prompt will list this server with no tool details attached, and the failure SHALL be remembered for that identity so REQ-MCP-042 warnings can fire later.

- **REQ-MCP-049** — Post-discovery filtering SHALL apply in this order: (1) drop names listed in `disabled_tools` (original names); (2) apply `tool_name_map` renames, preserving descriptions.

- **REQ-MCP-050** — Discovery SHALL use the same resolved command and arguments as launch (so workspace binding per REQ-MCP-034 applies to discovery too), the configured `env`, and `cwd` defaulting to the workspace root.
  > **Narrowed by [`PD-MCP-002`](../product/directives.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, discovery's default `cwd` is that tree's root, as launch's is.

- **REQ-MCP-051** — Given a stdio discovery in which the tool list was already received before a transport-teardown error occurs, when the connection is torn down, then the received tools SHALL be returned and the teardown error ignored (logged at debug level); an error occurring before the list was received SHALL count as a discovery failure per REQ-MCP-048.

- **REQ-MCP-052** — Discovered tool entries with an empty or non-string name SHALL be dropped; a missing description SHALL become `""`.

- **REQ-MCP-053** — Every tool-discovery request SHALL return a result — the server's tool list, or the empty list of REQ-MCP-048 — no later than the configured discovery timeout plus 5 seconds, measured from the moment the request is issued; with the 30-second default of REQ-MCP-046 that upper bound is 35 seconds. The bound SHALL hold for every caller and every surface that can trigger discovery. No discovery request SHALL fail to return, and an outstanding discovery request SHALL never delay process exit past that bound.

- **REQ-MCP-054** — Any configured server SHALL be probeable on demand, and a probe SHALL return within a default budget of 8 seconds. Each probe SHALL report the state of the server at the moment it runs: probing the same server n times SHALL cause the server to be contacted n times, and no probe SHALL report an outcome carried over from an earlier probe or from tool discovery. A probe reports one of two outcomes — `healthy`, together with the number of tools the server listed on that contact, or `unreachable`, together with human-readable text describing the failure instead of a count. A probe SHALL never raise an error to its caller, SHALL leave the result and the warnings of any later discovery request unchanged, and SHALL still run for a server whose earlier discovery failed.

### Per-Persona Tool Grants

- **REQ-MCP-055** — Grant resolution for a persona SHALL be defined per carried server, by these five cases: (a) a carried name absent from the configuration's server map contributes no tools and produces the warning of REQ-MCP-038; (b) a carried server with no `mcp_tools` entry is unrestricted and contributes every one of its discovered tools that survives REQ-MCP-004; (c) a carried server whose `mcp_tools` entry is an empty list contributes none of its tools; (d) a carried server whose `mcp_tools` entry names tools contributes exactly those of its discovered tools that the decision of REQ-MCP-056 allows, entries matching no discovered tool being inert per REQ-MCP-058; and (e) an `mcp_tools` entry naming a server the persona does not carry is a validation error (REQ-MCP-104). Cases (b) and (c) SHALL be distinguishable in the resulting surface: (b) yields that server's whole surviving surface, (c) yields nothing at all from that server.

- **REQ-MCP-056** — The grant decision for (server, tool) SHALL be: if any candidate spelling of the tool name (REQ-MCP-057) matches `disabled_tools`, the tool is denied regardless of grants; otherwise an unrestricted grant allows it; otherwise it is allowed if and only if a candidate spelling intersects the grant set.

- **REQ-MCP-057** — Candidate spellings for a tool name SHALL be the literal name plus, when the name begins with `<server>_`, `mcp-<server>-`, or `mcp__<server>__`, the unprefixed remainder — added, never substituted — so that a name carrying a client-side server prefix and a grant or disable entry written against the server-reported name still match each other in either direction.

- **REQ-MCP-058** — A grant entry that names a tool the server never reports SHALL be inert: configuration validation, agent construction and the run SHALL all succeed unaffected, and every other tool the same persona grants and the server does report SHALL still be granted. Each unmatched (server, tool) pair SHALL be reported once per process at informational level, stating that the entry matched no tool on that server; the same pair SHALL NOT be reported a second time in that process.

- **REQ-MCP-059** — Grants SHALL be enforced before the model ever sees a tool: filtering happens per server (so server attribution is preserved), a tool that was denied or never granted is absent from the tool list the model receives, and one server's unrestricted grant never leaks another server's withheld tool. When narrowing occurs, a debug log states how many of the server's tools were granted.

- **REQ-MCP-060** — When a connected server publishes a changed tool list after the initial handshake, the persona's callable tool set SHALL be recomputed by the same decision used at connect time (REQ-MCP-056, REQ-MCP-057), and the recomputed set SHALL govern every tool call that persona issues from the moment the update is received onward. A mid-run update SHALL only ever **narrow** that set: a name the update withdraws, or that the recomputed decision now denies, ceases to be callable at once, and calling it is refused per REQ-MCP-062; a name the update introduces that was not present at connect time SHALL NOT become callable for the remainder of that connection, whatever the persona's grants say, because the persona's prompt was rendered before it existed and REQ-MCP-062 forbids a callable name the prompt never printed. An update in which nothing survives the decision therefore empties that server's contribution rather than preserving the previous set: the recomputed set always governs, with no exception for the empty case. Narrowing SHALL NOT close the connection, fail the run, or re-render the prompt.

- **REQ-MCP-061** — A persona's callable tool set SHALL be a function of configuration alone. Where no carried server has an `mcp_tools` entry and no carried server has a non-empty `disabled_tools`, that set SHALL be exactly every tool discovered for the persona's carried servers, with nothing withheld. Where either does apply, the identical filtered set SHALL be observed whether the persona runs in a run the user is watching or in a run the application performs in the background. No configuration and no way of starting a run SHALL hand a persona a tool its grants exclude.

- **REQ-MCP-062** — For every persona and every server that persona carries, the set of tool names printed under that server in the prompt's MCP section (REQ-MCP-101) SHALL be set-equal, **at the moment the prompt is rendered**, to the set of tool names the persona can call on that server: a printed name SHALL be callable, and a name the persona can call SHALL be printed. Calling a name that the prompt does not print SHALL be refused. The names compared are those remaining after denial (REQ-MCP-004), grant filtering (REQ-MCP-056) and renaming (REQ-MCP-005) — a renamed tool is printed and called under its replacement name, and under no other. A mid-run tool-list update may afterwards remove a printed name from the callable set (REQ-MCP-060); it may never add one, so the equality is only ever weakened in the safe direction and the prompt never advertises a name the persona was not granted.

- **REQ-MCP-063** — When two personas of one session carry the same server under different grants, each SHALL see and be able to call only the tools its own grant allows, both at the same time; widening or narrowing one persona's grant SHALL leave the tool set the other persona sees and can call unchanged. How many personas use a server SHALL NOT change how many server processes or connections the session creates — that count stays at one per server for the whole session (REQ-MCP-066).

- **REQ-MCP-064** — Post-connect probes (REQ-MCP-070, REQ-MCP-071) SHALL read the server's unfiltered tool list, so no grant or disable configuration can disarm them.

- **REQ-MCP-065** — Each child run's persisted state SHALL record both its granted native tools and its granted MCP tools as a per-server map of tool-name lists. The desktop agent inspector SHALL render MCP tools grouped per server under a heading whose accessible name is "MCP server <name>", and SHALL match called-tool indicators prefix-tolerantly (a call logged under a name that carries a client-side server prefix still marks the corresponding granted original name as used).

### Session-Scoped Shared Runtime

- **REQ-MCP-066** — Within one session there SHALL be exactly one shared connection per server, opened on first demand, reused by every agent in the run, and closed exactly once when the session ends. Teardown SHALL occur on session-lock release and at application exit; a run the application performs in the background SHALL use the same shared-connection behavior as a run the user is watching.

- **REQ-MCP-067** — Session connection handling SHALL provide these observable guarantees under concurrent use: two agents that request the same server at the same time SHALL both use the same connection, and when both requests have been served exactly one connection — and for `stdio`, exactly one server process — SHALL exist for that server; while one server is still starting, tool calls to servers that are already connected SHALL complete without waiting for that startup to finish; a connection request issued after session shutdown SHALL fail with an error naming the server and SHALL leave no connection open; a request to release a connection that has since been superseded SHALL leave the current connection open and usable; and shutdown SHALL be callable any number of times without error, with no server process and no connection left open once the first call has returned.

- **REQ-MCP-068** — The end of one child conversation SHALL leave the session's shared server connections open: after a child finishes, every server it used SHALL still be connected and immediately usable by the next child of the same session, and every `stdio` server process SHALL still be running. Connections and server processes SHALL close only at the session-end teardown of REQ-MCP-066. Tool calls requested concurrently over one connection SHALL all complete, and each SHALL receive the response belonging to its own request and to no other. The session SHALL keep emitting its events while a tool call is outstanding, so no surface stalls for the duration of a call. Specifically: the `tool.start` of REQ-EVENTS-057 SHALL be observable before the call returns, its matching `tool.finish` SHALL follow when the call settles, and every other event of the catalog of REQ-EVENTS-041 that the session would otherwise have emitted SHALL be emitted at its normal point, neither withheld nor deferred until the outstanding call completes. This holds on every channel that carries the session event stream and for every surface fed by it, and it holds however many calls are outstanding at once.

- **REQ-MCP-069** — Given a failure creating the connection for one server, when the session tool source is built, then that server is logged and skipped (its tools absent) and the run continues. Tools from all connected servers SHALL be merged into one aggregate surface, with each tool call routed to the connection of its owning server. Opening a connection and listing its tools SHALL run under a caller-supplied budget whose default is 30 seconds.

  A server that becomes unreachable after its connection was established — a remote endpoint that stops answering, a `stdio` child that exits — SHALL be handled per call and never by failing the run: the call in flight ends as a failed tool call exactly as an exhausted allowance does (REQ-MCP-003), a warning naming the server SHALL be delivered through REQ-MCP-044 at most once per server per session, and the product SHALL neither retry the call nor reconnect on its own. A later call to the same server SHALL be attempted, re-establishing the connection if the transport requires it, and SHALL succeed if the server has recovered. Tools of every other server SHALL stay callable throughout. A probe (REQ-MCP-054) run afterwards SHALL report what it observes at that moment and SHALL NOT report a remembered outcome.

- **REQ-MCP-070** — A connected server whose configured name is `lsp` SHALL be initialized before any of its tools are offered to the agent: when a workspace root is known and the server reports a tool named `lsp_init`, that tool SHALL be called once with the arguments `{"root": "<workspace_root>"}` and SHALL be given 15 seconds to answer. Should that call fail or exhaust its budget, the server SHALL contribute no tools to the agent that triggered the connection and the run SHALL continue; a later agent of the same session that needs the server SHALL make the connection and the initialization call over again rather than inherit the earlier outcome. A server named `lsp` that reports no `lsp_init` tool SHALL be offered as it is; with no known workspace root the call SHALL be skipped; and a server configured under any other name SHALL never receive this call.
  > **Narrowed by [`PD-MCP-002`](../product/directives.md#pd-mcp-002), 2026-10-06.** For a connection established by a run in an isolated working tree, `lsp_init` is called with that tree's root.

- **REQ-MCP-071** — A connected server carrying the built-in code-intelligence name SHALL be probed once per connection established in the session, before that server's tools are offered to the agent, by calling the runtime's project-memory listing tool with empty arguments and allowing it 15 seconds to answer; the tool SHALL be found by matching the trailing segment of its reported name, so a client-side server prefix (REQ-MCP-057) still matches. Should that call fail or exhaust its budget, a warning SHALL be delivered through REQ-MCP-044 telling the user that the server's symbol-level tools remain usable but may not be pointed at this project; the connection SHALL stay open, the server's tools SHALL still be offered to the agent exactly as the persona's grants allow, and no corrective action SHALL be attempted. A server reporting no memory-listing tool SHALL NOT be probed and SHALL produce no such warning. The literal name of the memory-listing tool SHALL be read from the binding manifest of REQ-MCP-116.

- **REQ-MCP-072** — *Withdrawn.* Its only host was the terminal user interface, which the product does not have; the Windows `stdio` launch guarantee it stated is carried by REQ-MCP-113.

- **REQ-MCP-113** — On Windows, a `stdio` server launched by the desktop application SHALL start and its tools SHALL become available to the persona carrying it. No such launch SHALL be reported to the user as failed for a reason belonging to the host rather than to the server, and launching the same server repeatedly SHALL give the same result every time. The host condition this guarantee exists to defeat is stated so it can be tested negatively: the application is a graphical process that owns no console and whose own standard input, output and error may be absent, closed, or attached to something that is not a usable pipe. The product SHALL therefore create the child's three standard streams itself for every `stdio` launch, never inherit or reuse the parent's, never require a console to exist, and never allocate or show one; a console window SHALL NOT appear at any point in a launch. The same rule SHALL apply on every platform, so one launch path serves all of them, and it SHALL apply equally to the reserved token of REQ-MCP-033, whose child is the application's own executable. A launch that fails for a reason belonging to the server or its command — the command not being on PATH, or the child exiting — is unaffected and is reported by REQ-MCP-041 and REQ-MCP-107 as before.

### User Toggles and Server Management

- **REQ-MCP-073** — *Withdrawn.* A slash command and a text-mode command palette are surfaces of a terminal user interface the product does not have; reaching MCP server management is carried by REQ-MCP-108.

- **REQ-MCP-074** — *Withdrawn.* A modal text-mode table was its only surface; listing every configured server and toggling one for the session is carried by REQ-MCP-091 and REQ-MCP-108.

- **REQ-MCP-075** — *Withdrawn.* It described a column of the withdrawn text-mode table; per-server state on the surface that remains is the four-state health of REQ-MCP-092 together with the availability of REQ-MCP-037, both shown as text.

- **REQ-MCP-076** — *Withdrawn.* The file existed only to persist the withdrawn terminal-UI toggles, and a second global enablement store would contradict the `enabled` field of REQ-CONFIG-465 with no stated precedence between them; durable per-server enablement is carried by REQ-MCP-115.

- **REQ-MCP-077** — *Withdrawn.* It stated resilience rules for the withdrawn toggle file; the default it protected — a server the user has not turned off is enabled — is the `true` default of the `enabled` field (REQ-CONFIG-465), and REQ-MCP-115 carries the rest.

- **REQ-MCP-078** — Enablement SHALL be consulted afresh at every persona resolution, so a server that is disabled — by its configured `enabled` field (REQ-CONFIG-465) or by the session override of REQ-MCP-094 — is excluded from the next constructed agent. Changing either during an active run SHALL never crash the run and SHALL take effect on the next run iteration.

- **REQ-MCP-079** — *Withdrawn.* The terminal information pane was its only surface; listing every configured server before a run with its computed availability and its origin is carried by REQ-MCP-091, and showing the servers a running or finished agent actually carried is carried by REQ-MCP-114.

- **REQ-MCP-080** — *Withdrawn.* A modal text-mode screen was its only surface; reading a server's merged secrets with every value masked is carried by REQ-MCP-109 and editing them is carried by REQ-MCP-110.

- **REQ-MCP-081** — Wherever a stored secret value is rendered it SHALL be replaced by the mask REQ-TOOLS-171 fixes, and this domain holds no second definition of that mask. What this requirement relies on REQ-TOOLS-171 for is the mask itself: one fixed marker, identical on every surface, carrying no character of the value it replaced and no indication of that value's length, so two masked secrets of different lengths are indistinguishable and neither a credential nor its size can be inferred from a rendering. What this requirement adds is that the substitution is **unconditional** for a value read out of the secrets store of REQ-MCP-082: it SHALL NOT depend on the entry's key being secret-looking (REQ-TOOLS-172) or on the value carrying a recognized credential prefix, because a value's presence in that store is already what establishes it as a credential. A raw stored secret value SHALL never appear in a log line, a notification, a rendered list or table, an exported document, or any other rendering the product produces. A zero-length value never reaches this rule: the product refuses to store one (REQ-MCP-084) and a zero-length value found in a hand-edited file is skipped at load (REQ-MCP-082), so no rendering ever shows a mask standing for a value that is not there.

- **REQ-MCP-108** — MCP server management SHALL have exactly one venue: the `mcp` settings category of REQ-CONFIG-269, inside the Settings view of REQ-SHELL-023. That category SHALL hold the server list of REQ-MCP-091, the health probe of REQ-MCP-092, the secrets surface of REQ-MCP-109 and REQ-MCP-110, the search-key control of REQ-MCP-111 and the machine-setup action of REQ-MCP-112, and no other surface of the product SHALL offer a second way to enable, disable, probe or hold secrets for a server. Opening it SHALL be an action of the one vocabulary of REQ-SHELL-048, so it appears in the command palette, the keyboard-help dialog and the composer's slash catalogue alike, under a label naming MCP servers and a description saying it manages them. Every control the category holds SHALL be keyboard-reachable and fully labelled at the minimum window size (REQ-SHELL-022), and every state it shows SHALL be readable as text and never by colour alone (REQ-SHELL-149). The category SHALL open, and every control within it SHALL respond, within the product's 100 ms interface responsiveness budget; work that cannot finish inside it — probing (REQ-MCP-092), setup (REQ-MCP-112) — SHALL show its progress rather than block.

- **REQ-MCP-115** — Per-server enablement SHALL have exactly two controls and no third store. The durable one is the entry's `enabled` field in the layered YAML configuration, defaulting to `true` where absent (REQ-CONFIG-465): it survives restarts, merges by the ordinary scope rules of REQ-MCP-025, is picked up by an ordinary configuration reload, and is what a user edits — by hand or through a settings surface that writes configuration — to turn a server off for good. The transient one is the desktop toggle of REQ-MCP-094, which overrides the durable value for the current session only. No separate per-user enablement file SHALL exist, so no precedence between two stores has to be defined and two running instances cannot race over one. The MCP category SHALL make plain, for each row, which of the two is in force: a row whose configured value is `false` SHALL read as configured off, a row overridden for the session SHALL read as overridden for this session and SHALL say that the change is not persistent, and the category SHALL name `enabled` and the configuration file as the way to make it persistent (REQ-CONFIG-350, REQ-CONFIG-437). Restarting the application SHALL discard every override and return every row to its configured value.

### Secrets Storage and Environment Resolution

- **REQ-MCP-082** — Secrets SHALL be stored in a `secrets.yaml` per scope, next to the scope's `agents.yaml`: global in the per-user configuration directory REQ-CONFIG-001 fixes, which is the per-user location REQ-STARTUP-145 fixes, and workspace in `<workspace>/.rotaris/`. The format is a YAML mapping of server name → map of environment key → value. How that file is written is REQ-CONFIG-216's and is cited here rather than restated: this document holds no copy of the write's atomicity, of the directory creation, of the file protection every write leaves in place, or of what happens when that protection cannot be applied. *This requirement formerly restated the write as "atomic (temp file then rename) with parent directories auto-created" and stated no file protection at all. That restatement is withdrawn rather than narrowed: it was a second, shorter statement of one write, and once REQ-CONFIG-216 fixed a mode for this file it became a text a build could satisfy while leaving a credentials file world-readable. Nothing it guaranteed is lost — REQ-CONFIG-216 holds the atomicity and the directory creation, and adds the protection this text never had.* An unreadable file, invalid YAML, or a non-mapping root SHALL load as empty; non-mapping server values are skipped; keys and values are coerced to strings. An entry whose key is empty, or whose coerced value is the empty string, SHALL be skipped at load with a warning naming the scope, the server and the key, so no zero-length secret ever reaches environment resolution (REQ-MCP-087), URL substitution (REQ-MCP-088) or masking (REQ-MCP-081); a server left with no entries by that skipping loads as though it had none.

- **REQ-MCP-083** — The merged secrets view SHALL combine global then workspace per key, with workspace winning on collision.

- **REQ-MCP-084** — Secret mutation semantics: setting SHALL create the server entry as needed; setting a key to the empty string SHALL be **refused** — the store SHALL report that a value is required, write nothing, and leave any existing value for that key untouched, so an empty value can neither be created nor used to clear one; unsetting a missing key SHALL report not-found without error and SHALL remove a server entry that becomes empty; clear-all SHALL report the number of removed keys and perform no write when nothing was removed; a failed atomic write SHALL remove its temp file and propagate the error.

- **REQ-MCP-085** — *Withdrawn.* A command group invoked from a shell was its only surface; setting, unsetting, clearing and listing stored secrets, with the same scope choice and the same masking, are carried by REQ-MCP-109 and REQ-MCP-110.

- **REQ-MCP-086** — *Withdrawn.* A shell subcommand was its only surface; storing the built-in `web_search` server's API key without the user having to name either the server or the environment variable is carried by REQ-MCP-111.

- **REQ-MCP-087** — Environment resolution at configuration load SHALL apply, per server `env` entry: (1) a value that is exactly `${VAR}` (full-value match) is replaced by the process environment's value; when the variable is unset, the key is omitted entirely — the literal placeholder is never passed to a server; (2) any other value is kept as-is; (3) stored secrets for that server are overlaid last and always override shell-derived values. Resolution SHALL happen during loading so every downstream consumer (agent construction, discovery, health probes) sees the resolved environment.

- **REQ-MCP-088** — For remote servers, every `${VAR}` occurrence inside the URL (substring, not full-match) SHALL be replaced using this precedence: (1) a stored secret for that server, (2) the process environment. An unresolvable placeholder SHALL stay literal with a warning stating it could not be resolved. This is how the default web-search URL receives its API key.

- **REQ-MCP-089** — During configuration load, the workspace `.gitignore` SHALL be best-effort amended to exclude `.rotaris/`: idempotent, tolerant of an existing entry with or without a trailing slash, written atomically, and reporting failure without raising.

- **REQ-MCP-090** — The effective environment reaching a spawned server SHALL follow this precedence chain: explicit `env` over `envFile` (discovery merge) → full-value `${VAR}` expansion from the shell → secrets overlay, where workspace secrets beat global secrets beat shell values.

- **REQ-MCP-109** — The `mcp` settings category SHALL hold a secrets surface that reads the stored secrets of REQ-MCP-082 without ever revealing one. It SHALL offer both views over the same data: an **all-servers** view listing every server that holds at least one stored secret, and a **per-server** view for one server chosen from the configured server names. Both views SHALL show, per entry, the server, the key, the value masked per REQ-MCP-081, and the scope the entry came from — `Workspace` or `Global` — with the merged view of REQ-MCP-083 determining which entry is shown where a key exists in both, and the overridden global entry SHALL NOT be listed a second time. Servers, and keys within a server, SHALL be listed in the ascending order of REQ-MCP-117. The per-server view SHALL additionally show the keys of the chosen server's configured `env` block, in that same order, marking which of them a stored secret satisfies, so a user can see at a glance what a server still needs. Empty states SHALL be distinguishable and SHALL each name what is missing: no server is configured; the chosen server holds no stored secret; no server holds any stored secret at all. The surface SHALL never render a raw value, SHALL never offer a reveal control, and SHALL never place a value on the clipboard.

- **REQ-MCP-110** — The secrets surface SHALL let the user add a secret, change an existing one, delete one, and clear every secret of one server, and these SHALL be the only ways the product writes `secrets.yaml`. Every write SHALL name a scope: the surface SHALL offer a `Workspace` / `Global` choice that opens on `Workspace` (REQ-CONFIG-463), and adding, changing, deleting and clearing SHALL each affect the chosen scope alone — deleting a workspace entry SHALL leave a global entry of the same key in place, and the merged view (REQ-MCP-083) SHALL immediately show that global entry instead. The value field SHALL never echo what is typed in clear text and SHALL never be pre-filled with an existing stored value, so changing a secret means supplying it afresh. A write SHALL be refused, with a notice stating which requirement is unmet, when no server is chosen, when the key is empty, or when the value is empty (REQ-MCP-084); a refused write SHALL change nothing. A completed write SHALL confirm what happened, conveying the server, the key, the scope, and — for an add or a change — the new value masked per REQ-MCP-081; a delete SHALL confirm the server, the key and the scope, or state that the key was not present in that scope, which is not an error; a clear SHALL convey how many keys were removed, or that the server had none. The wording of each confirmation is left to the implementation. Per-edit confirmation SHALL be the whole of the feedback: no aggregate summary SHALL be produced when the surface closes, and closing SHALL discard nothing, every edit having already been written. A stored secret SHALL take effect on the next configuration load, and the surface SHALL say so rather than implying that a run already in flight changes.

- **REQ-MCP-111** — The `mcp` settings category SHALL hold a dedicated control that stores the built-in `web_search` server's API key without the user having to name either the server or the environment variable. Supplying a value through it SHALL write that value through the secrets store of REQ-MCP-082 under the `web_search` entry, keyed by `ROTARIS_SEARCH_API_KEY` (REQ-CONFIG-181), in the scope the user chose, defaulting to `Workspace` (REQ-CONFIG-463); the stored value SHALL thereafter satisfy the URL placeholder of REQ-MCP-088 with no further configuration, and the entry SHALL stop being reported as unresolved. The control SHALL obey REQ-MCP-110 in every other respect — the field does not echo, an empty value is refused and writes nothing, and the confirmation conveys the variable, the scope and the value masked per REQ-MCP-081. Its wording and label are left to the implementation, provided they identify what the key is for without requiring the user to know the variable's name. The control SHALL be visible whether or not `web_search` is currently enabled, since supplying the key is a prerequisite for enabling it usefully.

### Desktop Application Surfaces

- **REQ-MCP-091** — The desktop settings SHALL include a tab labelled "MCP Servers" holding a card headed "Configured servers" with one row per configured server. Each row SHALL show: a status indicator whose state is one of the four of REQ-MCP-092, accompanied by that state as text; the label `{name} · {type}`; a muted secondary line giving the entry's `url` for a remote server and otherwise its configured `command` followed by its configured `args`, joined by single spaces; the server's origin drawn from the vocabulary of REQ-MCP-026; and a toggle switch. The card SHALL list **every** configured server, a server that is disabled included, so the list is a complete picture of what the configuration declares; a disabled row SHALL say so as text and SHALL say which control disabled it (REQ-MCP-115). The switch SHALL read as on if and only if the server is both enabled and available per REQ-MCP-037. Its state at application start SHALL be the entry's configured `enabled` value (REQ-CONFIG-465) and nothing else: no per-user enablement file is read, because none exists (REQ-MCP-115), and every session override of REQ-MCP-094 is discarded at exit. For an unavailable server the switch SHALL be non-interactive and SHALL carry a tooltip stating that the command was not found on the executable search path. With no servers configured the card SHALL show an empty state naming the configuration file as the place tool servers are declared (REQ-CONFIG-350).

- **REQ-MCP-092** — Per-server health SHALL expose exactly the four states of REQ-CONFIG-353: `unknown` (initial on every launch; health is never persisted), `checking` (pulsing indicator), `healthy` (with discovered tool count), and `unreachable` (error text in tooltip). Health SHALL always be written out textually, never encoded only in color; colors map through the active theme. A "Check status" header button (accessible description "Probe every configured MCP server") SHALL probe all configured servers sequentially on a background thread without ever blocking the UI thread; unavailable servers SHALL short-circuit to `unreachable`, without connecting, with detail conveying that the command was not found on the executable search path (REQ-CONFIG-352); the button SHALL disable while a probe runs and re-enable when finished.

- **REQ-MCP-093** — Desktop availability SHALL delegate to the shared rule of REQ-MCP-037.

- **REQ-MCP-094** — Given a server toggled off in the desktop app, when the next run's configuration is projected, then that server SHALL be removed from both the server map and every persona's carried-server list, leaving only enabled-and-available servers. These toggles are **deliberately session-scoped**: they override the configured `enabled` value of REQ-CONFIG-465 for the life of the application process, are never written to disk, and are discarded at exit, so the next launch starts from the configured value again. They are the quick way to take a server out of the next run; making that durable is an `enabled` edit in the configuration file (REQ-MCP-115), which the category says plainly rather than leaving the user to discover that a toggle did not stick.

- **REQ-MCP-095** — First-run machine setup SHALL state, before it begins any check, that it is about to check the developer tooling and the package caches the MCP servers depend on, and the settings surface SHALL offer an action that re-runs exactly those checks on demand. The release-pinned setup manifest SHALL carry the `browser` package's version string character for character as the default entry of REQ-MCP-010 carries it; a build in which the two strings differ SHALL be treated as defective, and the build SHALL check them against each other. The literal wording of the first-run message and the label of the settings action are left to the implementation; what is fixed is that the message states, before any check runs, that developer tooling and the package caches the MCP servers depend on are about to be checked, and that the settings action identifies itself as re-running exactly those checks.

- **REQ-MCP-096** — Package-cache warm-up steps SHALL be derived from the merged server configuration of REQ-MCP-025, considering only `stdio` entries whose resolved command's file name is `uvx`, `uvx.cmd`, `npx` or `npx.cmd`. For a `uvx` entry the package specification SHALL be the value following a `--from` argument, or failing that the first argument containing `==`, and the warm command SHALL be `uvx --from <spec> <executable> --help`. For an `npx` entry the package SHALL be the first argument that does not begin with `-`, with no version pin required, and the warm command SHALL be `npx -y <pkg> --help` with `npx` resolved to an absolute path; the step SHALL be omitted entirely when `npx` is not found on PATH. An entry from which no package specification can be taken SHALL yield no step. `<executable>` in the `uvx` warm command SHALL be the first resolved argument after the package specification that does not begin with `-`, the specification itself excluded; where the entry supplies no such argument the step SHALL be omitted rather than guessed at. The match of the resolved command's file name against `uvx`, `uvx.cmd`, `npx` and `npx.cmd` SHALL be **case-insensitive**, compared without regard to case on every platform alike, so a Windows entry naming `NPX.CMD` warms exactly as one naming `npx.cmd` does. Steps SHALL be identified as `warm:<family>:<package>` with `<family>` being `uvx` or `npx`, labelled `Warm <package>`, and tagged with the capability `"<server> MCP server"`; two entries that produce the same identifier SHALL yield exactly one step. On resume, a step already recorded as completed SHALL be skipped unless the run was started as a manual re-run, in which case it SHALL run again.

- **REQ-MCP-097** — *Withdrawn.* A shell command was its only surface; inspecting the machine's developer tooling, installing what is missing, warming package caches, repairing broken installations, and reporting progress and the final outcome are carried by REQ-MCP-112.

- **REQ-MCP-098** — The desktop SHALL derive its applicable project-initialization task list from the core task registry (which applies REQ-MCP-045) rather than re-deriving prerequisites.

- **REQ-MCP-099** — Deterministic code-intelligence project setup SHALL invoke the command line derived by REQ-MCP-036 and run three steps in order — project creation, project indexing, and memory-store initialization — bounded at 300, 1800 and 120 seconds respectively. Project creation SHALL be skipped when the runtime's per-project marker file is already present, and SHALL never overwrite an existing project. Child processes SHALL be run with UTF-8 input and output encoding; their completion SHALL be polled every 0.25 seconds; on cancellation or timeout the child SHALL be asked to terminate, given 5 seconds to exit and then force-killed — on Windows the whole process tree — and a step whose child exceeded its budget SHALL be reported as failed. The output reported for a failing step SHALL be truncated to its last 400 characters, keeping the end of the output and discarding the beginning. In a workspace that contains no code, the indexing and memory steps SHALL be skipped and reported with status `skipped-no-code` while creation still runs. A configured code-intelligence entry that is remote, or whose arguments contain no server-launch subcommand, SHALL produce a non-retryable failure whose message states that the entry is not a local launch; no substitute command SHALL be attempted. The marker file's name and the three steps' subcommands SHALL be read from the binding manifest of REQ-MCP-116.

  A workspace **contains code** when, walking it from its root, at least one regular file is found whose name-extension appears in the manifest's indexable-extension list; the walk SHALL skip version-control metadata directories and every path the workspace's version-control ignore rules exclude, SHALL traverse dot-prefixed directories that are not so excluded, SHALL follow no symbolic link out of the workspace, and SHALL stop at the first qualifying file. A workspace in which the walk finds none contains no code. The test SHALL be performed once per setup run and its answer used for both steps it gates.

  A failed step SHALL stop the steps that would otherwise follow it: the three are ordered because each depends on the one before, and indexing a project that was never created cannot succeed. A step not attempted for that reason SHALL be reported with status `not-attempted`, distinct from a failure of its own. The status vocabulary for the three steps SHALL therefore be exactly `succeeded`, `failed`, `skipped-no-code` and `not-attempted`, and a run in which any step is `failed` or `not-attempted` SHALL be reported as not having completed setup.

  > **Narrowed by [`PD-MCP-003`](../product/directives.md#pd-mcp-003), 2026-10-06.** A stopped step is given 2 seconds to
  > exit, not 5, at every stop — an exhausted budget, a cancellation and the application's close alike — and is then
  > force-killed. Everything else above still holds.

- **REQ-MCP-100** — The auxiliary per-agent pop-out window SHALL list the agent's granted MCP tools compactly: one muted line per server in the form "{server}: tool, tool, …", sourced from the run's recorded grant evidence (REQ-MCP-065).

- **REQ-MCP-112** — The machine-setup action of REQ-MCP-095 SHALL be the product's one way to inspect the machine's developer tooling, install what is missing, warm the package caches derived by REQ-MCP-096 for the current workspace's merged configuration, and repair a broken installation. It SHALL run on a background thread without ever blocking the interface, and while it runs it SHALL show which step is in progress and which steps have finished, each finished step carrying its outcome and, where it failed, text describing the failure. It SHALL be cancellable at any point, and cancelling SHALL stop after the step in flight rather than leaving a step half-applied. When it finishes it SHALL state one final outcome, and that outcome SHALL distinguish at least: every step succeeded; some step failed so the machine is only partly set up; and the run was cancelled. A failure or a cancellation SHALL never be reported as success, and neither SHALL fail a run or block the application — a machine that is only partly set up still starts, and the servers whose caches were not warmed behave as REQ-MCP-041 and REQ-MCP-107 describe. The action SHALL be re-runnable on demand as many times as the user wishes, SHALL refuse to start a second concurrent run, and on a re-run SHALL re-execute steps already recorded as completed (REQ-MCP-096). Progress and outcome SHALL be readable as text, never encoded only in colour (REQ-SHELL-149).

- **REQ-MCP-114** — For every agent of a run, the desktop agent inspector SHALL show which MCP servers that agent actually carried, so what a run used can be read after the fact and not only what the configuration declares. Per server it SHALL show the server's name, its transport, its origin from the vocabulary of REQ-MCP-026, and its fate for that agent — carried and connected, or dropped, with the reason drawn from the drop rules that apply: not present in configuration (REQ-MCP-038), disabled (REQ-MCP-040), unavailable (REQ-MCP-041), or tool discovery having failed (REQ-MCP-042). A dropped server SHALL still be listed, with no granted tools under it; a carried server SHALL be listed with the granted tools of REQ-MCP-065. Every one of those states SHALL be conveyed as text (REQ-SHELL-149), and the list SHALL remain readable at the minimum window size (REQ-SHELL-022). The information SHALL be sourced from the run's own recorded evidence, so it reads the same for a finished run as for a running one and does not change when the configuration is later edited.

### Prompt Rendering of the MCP Surface

- **REQ-MCP-101** — The persona system prompt SHALL contain one designated MCP section. An *active* server, for this requirement, is a server the persona carries that survived every drop rule — it is present in configuration (REQ-MCP-038), not disabled (REQ-MCP-040) and not dropped as unavailable (REQ-MCP-041). When the persona has no active server, that section's body SHALL be exactly the literal line `_No MCP servers configured._` and nothing else. Otherwise the body SHALL be a Markdown bullet list with one top-level bullet per active server: a server for which no tool is known (discovery returned nothing, or failed per REQ-MCP-048) SHALL render as its name in code formatting, `` `name` ``; a server with known tools SHALL render as its name in bold code formatting, ``**`name`**``, followed by one indented child bullet per tool, each child bullet being `- `, then the tool name in code formatting, then — only when that tool's description is a non-empty string — ` — ` followed by the description text. The names rendered SHALL be exactly the names of REQ-MCP-062: after grant filtering, after `disabled_tools` removal, and after `tool_name_map` renaming — a renamed tool appears under its replacement name only, which is also the name the model calls (REQ-MCP-005). Servers SHALL be listed in the ascending order of REQ-MCP-117 by the name they are configured under, and a server's tools in that same order by the name printed, so one persona's prompt is byte-identical whenever its inputs are and two personas never disagree about order. The section's heading text is left to the implementation, provided it identifies the section as the persona's MCP servers and provided one heading is used in every prompt the product renders.
  > **Narrowed by [`PD-MCP-001`](../product/directives.md#pd-mcp-001), 2026-10-06.** Everything above still governs, with one exception: the bundled code-intelligence runtime's usage-instruction tool is rendered with the description the product wrote for it, carried by the binding manifest, in place of the one its server reports.

- **REQ-MCP-102** — A persona's prompt SHALL carry a fixed project-memories protocol block, placed under the code-intelligence server's entry in the MCP section (REQ-MCP-101), if and only if that persona's granted tools for that server include both the project-memory listing tool and the project-memory reading tool. The block SHALL tell the agent: to read the memories that already exist before it starts exploring the codebase; to write durable findings that are not obvious from the code back through the memory-writing tools it holds; to keep agent-instruction files out of memory; and to keep anything true only of the current run out of memory. Those four points are the block's required content and SHALL all be present; its literal wording is left to the implementation. Every prompt that carries the block SHALL carry the same characters in the same order, so the wording is chosen once and never varies by persona, server or run. A persona missing either gating grant SHALL receive no such block. The two gating tool names SHALL be read from the binding manifest of REQ-MCP-116.

### Validation and Launch Error Semantics

- **REQ-MCP-103** — Configuration validation SHALL report, per persona, an error of the form "Persona '<p>' references unknown MCP server '<s>'" for any carried server name absent from the configuration's server map.

- **REQ-MCP-104** — Configuration validation SHALL report an error when a persona grants MCP tools for a server it does not carry, naming both the persona and the server.

- **REQ-MCP-105** — Persona generic tool names SHALL validate against the public native tool set plus configured MCP server names; any other name is an error naming the persona and the unknown tool. An MCP server name in the generic tool list is legal but warned per REQ-MCP-039.

- **REQ-MCP-106** — Agent construction SHALL fail with an error listing the offending names when an advertised non-MCP tool is not actually registered; MCP server names SHALL be exempt from this prompt/tool mismatch guard.

- **REQ-MCP-107** — When a child agent fails to launch and an MCP connection error appears anywhere in the failure's cause chain, exactly one diagnostic SHALL be produced and delivered through both channels of REQ-MCP-044 — never zero, never two. The diagnostic SHALL be chosen from the root cause by the first matching case of two: (1) the root cause is a failure of the operating system to start the child process at all — whatever error the platform reports for it, a missing executable and an unusable file descriptor alike — and yields a message conveying that the server's configured command could not be started, that it is probably not installed or not on the executable search path, and the two remedies available (install it, or declare that server on the `http` transport instead); (2) any other MCP connection error yields a message conveying that connecting to that server failed. Reducing the enumeration to "the process could not be started" is deliberate: no list of platform error codes has to be maintained for the rule to be testable, and the two former cases carried the same advice anyway. Every variant SHALL name the persona whose launch failed, SHALL name the server, and SHALL reproduce the root cause's own text; the wording around those facts is left to the implementation. A launch failure whose cause chain holds no MCP connection error SHALL yield no MCP diagnostic and no `mcp_config` issue record.

## Data & Formats

### `mcp.json` discovery files

```json
{
  "mcpServers": {
    "my-server": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "some-package"],
      "env": {"KEY": "${env:KEY}"},
      "envFile": ".env",
      "cwd": "${workspaceFolder}/sub"
    },
    "remote": {"url": "https://example.test/mcp", "headers": {"X-Auth": "..."}}
  }
}
```

Top-level key `mcpServers` or `servers` (that order). Server names match `^[a-zA-Z][a-zA-Z0-9_-]*$`. Explicit `type` wins; else `url` implies `http`; else `stdio`. Files are read but never rewritten (REQ-MCP-027).

### YAML configuration (server + persona surface)

Under `mcp_servers:` (a named map) in global or workspace `agents.yaml` — fields per REQ-MCP-001. Personas carry `mcp_servers: [name, ...]` and optionally `mcp_tools: {server: [original tool name, ...]}` as an allow-list. The machine-maintained origin map `mcp_server_sources` records `"yaml" | "discovered-project" | "discovered-user" | "default"` per server and is never user-settable.

### Normalized runtime server description

Exactly these keys, no others (REQ-MCP-043):
- stdio: `{transport, command, args, env, cwd, [timeout]}` (`cwd` defaults to the workspace root)
- streamable HTTP / SSE: `{transport, url, [headers], [timeout]}`

`transport` takes exactly `stdio`, `http` (streamable HTTP) or `sse` — the same vocabulary as `type` in REQ-MCP-001. `timeout` is `request_timeout` as a number (seconds).

### Per-server enablement

No separate enablement file exists. The durable control is the entry's `enabled` field in the layered YAML configuration, default `true` (REQ-CONFIG-465); the desktop toggle is a session override that is never written to disk and is discarded at exit (REQ-MCP-094, REQ-MCP-115).

### Secrets — `secrets.yaml`

Per scope, next to `agents.yaml` (global config dir; workspace `.rotaris/`):

```yaml
my-server:
  API_KEY: "value"
```

How the file is written — atomicity, directory creation, and the owner-only protection every write leaves in place — is REQ-CONFIG-216's and this appendix holds no copy of it. Malformed content loads as empty; workspace beats global per key. An empty key or an empty value is skipped at load and refused at write, so masking's shortest input is one character. Every rendering of a stored secret value is masked by REQ-MCP-081, which this line does not restate. That requirement takes the mask itself from REQ-TOOLS-171, the product's single definition of it, and adds only that a value read out of this store is masked unconditionally; there is one mask across the product, not one for stored secrets and another for command lines and argument summaries.

### Ordering

One rule for every ordered presentation in this domain (REQ-MCP-117): ascending code-point order on the raw string, case-sensitive, locale-independent.

### Health probe outcome

Healthy or unreachable; the number of tools the server reported when healthy; human-readable error text when unreachable. Each probe opens its own connection and reports only that connection's outcome (REQ-MCP-054).

### Session diagnostics and run state

- Session issues file: one record per delivered MCP warning — kind `mcp_config`, severity `warning`, actor `orchestrator`, plus the warning text.
- Child-run state snapshot: `granted_tools` (native) and `granted_mcp_tools: {server: [tool, ...]}`.

### Project setup step status

`succeeded` | `failed` | `skipped-no-code` | `not-attempted` (REQ-MCP-099).

### Setup warm steps

Ids `warm:<family>:<package>` (families: uvx, npx), labels `Warm <package>`, capability tag `"<server> MCP server"`. Warm commands: `uvx --from <spec> <executable> --help`; `npx -y <pkg> --help`.
