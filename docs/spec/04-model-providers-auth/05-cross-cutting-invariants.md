# Model Providers, Sign-In, and Model Routing — Cross-Cutting Invariants

Part 5 of 7 of [domain 04](../04-model-providers-auth.md), which indexes every part. Defines REQ-PROVIDER-131 – REQ-PROVIDER-152.

### Cross-Cutting Invariants

- **REQ-PROVIDER-131** — No credential value is readable in a log file, in user-visible error text, in a snapshot, in an event stream, or in a hook payload. One shared set of redaction rules covers all of them — no venue, the event stream included, carries rules of its own — and those rules are REQ-TOOLS-171's: the ordered layers, the credential value-prefix list, and the mask are fixed there and are neither restated nor varied here. What this domain relies on them for is that every credential shape a provider integration can produce is recognized wherever it occurs in text, and that the replacement is one fixed marker, identical in every venue, carrying no character of the value it replaced and no indication of its length, so neither a credential nor its size can be inferred from redacted text. Where a value is held under a mapping key that meets the secret-looking key test of REQ-TOOLS-172, the whole value is masked whatever it looks like; that is what keeps a credential out of a hook payload as surely as out of a log line. The stored-secret display mask is a different thing from the redaction marker and is never used as it; both are REQ-TOOLS-171's and neither is restated here. What this domain relies on that requirement for is that the two are never substituted for one another: the marker replaces a credential found in text on its way somewhere else, while the display mask is the deliberate rendering of a key the user themselves stored, and REQ-PROVIDER-107 states where that rendering applies in this domain.

- **REQ-PROVIDER-132** — Health issues for configured providers are summarized uniformly: an API-key-flow provider missing credentials → "<name> is missing an API key." (flagged as editable); an expired credential → "<name> authentication is expired."; otherwise "<name> is not authenticated."

- **REQ-PROVIDER-133** — Ordering invariant: for key-based providers, credentials are persisted only AFTER successful validation/discovery (sign-in, validated key update, programmatic registration), so a bad key is never stored silently — with the explicit exceptions of a save on which the user deliberately opted out of validation (REQ-PROVIDER-141) and the desktop's raw key-save path (which performs header validation only).

- **REQ-PROVIDER-134** — Ordering invariant: on-disk bridge artifacts are rewritten as part of every credential save and are on disk before that save returns, so an external consumer reading them can never observe an older credential than the store holds. Run-start priming also rewrites the bridge for a credential it found valid and did not renew, because that workspace may never have had the files written at all.

- **REQ-PROVIDER-135** — The generic `openai-compatible` catalog id is a template/family, never a credentialed provider itself: sign-out targets, the desktop add-provider list, and instance ids all exclude it; only `openai-compatible--<label>` instances hold credentials.

- **REQ-PROVIDER-136** — Static custom provider/model declarations in configuration (a `models.yml`-style declaration file) remain supported alongside discovery; ordinary onboarding does not need them. YAML-declared models with a complete provider and model id always override snapshot entries of the same name.

- **REQ-PROVIDER-137** — Thinking/reasoning levels shown for a model come from the model-capability metadata the product ships with: a model supports levels only when a reasoning-effort parameter is a supported parameter for it; the UI level set is (low, medium, high, max) minus levels the metadata disclaims (a disclaimed low removes "low"; a disclaimed extra-high removes "max"); the "max" level corresponds to the metadata's extra-high reasoning effort. Unknown or custom models expose no levels, and the thinking column collapses to the provider default.

- **REQ-PROVIDER-138** — *Withdrawn.* It existed only to stop a command-line flag mixing sign-out with a task; that sign-out is an action of its own and never carries a task is stated by REQ-PROVIDER-143.

- **REQ-PROVIDER-139** — *Withdrawn.* It fixed process exit codes for command-line subcommands that no longer exist, and the product exposes no exit status to a user; each outcome it encoded is reported to the user by the action that produced it (REQ-PROVIDER-142 sign-in, REQ-PROVIDER-143 sign-out, REQ-PROVIDER-141 deletion, REQ-PROVIDER-147 refresh).

- **REQ-PROVIDER-151** — Consumed remote contracts. Every remote payload shape this document states — discovery, subscription usage, and account credit — is a contract the product *consumes*, never one it defines, and behavior is fixed by what the product does with each value rather than by any promise about what a provider will keep sending. A payload carrying fields this build does not know SHALL be accepted with those fields ignored. A payload missing a value a read requires SHALL fail that read with the error the owning requirement names, and SHALL NOT be repaired by guessing a value. No read of a remote payload ever fails a run, deletes a credential, or changes a catalog attribute except where a requirement says so explicitly. Following a provider's payload change therefore costs a build's mapping data (REQ-PROVIDER-073, REQ-PROVIDER-079) and no behavior stated here.

- **REQ-PROVIDER-152** — Concurrent access to the shared stores. The credential files (REQ-PROVIDER-014) and the provider snapshot (REQ-PROVIDER-084) are per-user, so every window of the one running instance reaches the same files (REQ-STARTUP-161) and several read-modify-write sequences over one of them can be in flight at once — two windows signing in to different providers, or a window and a background run. Every write remains atomic per file, so no reader ever sees a partial document. In addition, every read-modify-write sequence over one of those files — saving a credential, deleting one, upserting a provider record, removing one — SHALL be performed while holding an exclusive lock taken on a lock file adjacent to the target, so that overlapping sequences serialize instead of interleaving and neither silently loses the other's change. A lock that cannot be taken within 5 seconds fails that operation with an error conveying that the store is being updated and that the action can be retried; the wording is left to the implementation and SHALL NOT assert that a second instance of the application is running, because none can be. The operation never proceeds without the lock. A lock left behind by a process that is no longer running is reclaimed rather than blocking forever, and a lock held by a live process is never broken — the lock is still needed against a process other than the current instance in exactly two states, neither of them routine: a lock left by an instance that crashed or was force-quit, and the brief overlap while an in-place update hands over to its successor (REQ-STARTUP-121). Reads take no lock, because atomic writes already make every read consistent.
