# Agent Tooling, Terminal Execution, Permissions, and Approvals — 8. Permission Audit Trail

Part 3 of 9 of [domain 05](../05-tools-permissions-approvals.md), which indexes every part. Defines REQ-TOOLS-078 – REQ-TOOLS-094.

### 8. Permission Audit Trail

**REQ-TOOLS-078** — Permission decisions are recorded into the session's permission audit (REQ-SESSION-137), in the order the decisions were taken. Where that audit is held is the sessions domain's and is not fixed here. Once recorded, an entry's content is never altered and no entry is ever inserted ahead of an entry already present; the only permitted removal is retention trimming, which keeps the 5000 most recent entries (REQ-SESSION-133), so beyond that count each new entry displaces the oldest one still held, and the record must retain enough to say that entries were dropped. A reader therefore sees a suffix of the session's decision history, in the order the decisions were taken, every retained entry exactly as it was recorded — every field, adding nothing and dropping nothing.

That last guarantee has to survive leaving this application, or the audit is only as trustworthy as the surface rendering it. The audit MUST therefore be obtainable as a file the user chooses, yielding every field of every entry to a stock parser on a machine carrying none of this product's code, with the order preserved, nothing omitted, and a statement of how many entries the retention cap dropped (REQ-SESSION-199, on the pattern REQ-EVENTS-166 fixes). This is the record a user consults precisely when they do not trust what the interface tells them, so no part of it may be reachable only through this application. The export is a user-initiated action producing a file and never a way to watch a run (REQ-SESSION-071).

**REQ-TOOLS-079** — A decision entry carries: `timestamp` (ISO-8601 UTC), `session_id`, `agent_id`, `persona`, `tool_name`, `decision` (`allow`|`ask`|`deny`), `rule_id`, `source` (a decision-source value per REQ-TOOLS-028), `summary` (the request summary of REQ-TOOLS-016 — `<tool>: <redacted command facet>`, or `<tool>(<sorted argument keys>)` for a call with no command facet), `reason`, plus `request_id` only when the decision resolved a raised approval, plus the entry identifier this requirement fixes below. Beyond the redacted command facet carried inside `summary`, an entry contains no argument values. That absence is not incidental bookkeeping: it is the property that makes the audit safe to hand to the user as a file, and it is the property the export test of REQ-TOOLS-190 turns on. A change to this requirement that let argument values into an entry would withdraw the audit's export with it.

An entry MUST also be identifiable. The permission audit is one of the three record kinds a locator may name, and REQ-EVENTS-056 — which fixes the locator's form, the closed set of record-kind tokens and the token that names this record — makes **this requirement the only place the identifier of an audit entry may be fixed**, and forbids a locator naming a kind whose own requirement gives its entries none. The obligation is therefore stated here: the audit MUST give every decision entry an identifier that distinguishes it from every other entry the audit holds for that session — the mode-change entries of REQ-TOOLS-082 included, since those are interleaved with the decision entries in the same audit — that does not change once the entry has been recorded, and that is not reused after the retention trimming of REQ-TOOLS-078 has displaced the entry that held it, so a locator written earlier can never come to name a different decision than the one it was written for. A locator whose entry has since been displaced simply does not resolve, which REQ-EVENTS-056 states is an ordinary outcome rather than damage.

**That identifier is a field of the entry.** It is carried inside the entry itself and not beside it, which is why the field set stated above names it. The reason is the export and not tidiness: REQ-EVENTS-056 requires a locator naming an audit entry to resolve **through the export**, on a machine carrying none of this product's code and with nothing beyond a stock parser, and an identifier that is not part of the entry does not survive the entry being exported. A locator this product wrote would then be unresolvable at exactly the point where the audit stops being a rendering this application controls and becomes a record the user holds — which is the whole reason the audit is an audit rather than a screen (REQ-TOOLS-078, REQ-SESSION-199). It follows that the identifier MUST be carried under the same field in every entry the audit holds and in every export of it, so that a reader on such a machine can tell which field of an exported entry a locator's record id names; an identifier present in an export but not locatable as the identifier resolves nothing.

This fixes where a **decision** entry's identifier lives and nothing else. The mode-change entries of REQ-TOOLS-082 are unaffected and their field set is unchanged: no locator names one, REQ-EVENTS-056's record ids are the identifiers of the entries locators name, and the obligation above is that a decision entry be distinguishable from every other entry the audit holds — which is satisfied without giving an identifier to an entry no locator can name.

**The no-argument-values property above is untouched, and this MUST NOT be read as an opening to it.** The identifier MUST NOT be derived from, and MUST NOT disclose, any argument of the call the entry decided: it identifies an entry and conveys nothing about what the call contained. The audit's eligibility for export under REQ-TOOLS-190's redaction-safety test is therefore unaffected by the identifier being carried in the entry.

**REQ-TOOLS-080** — Every entry is recorded against the session whose call was decided, and never against another session's. An agent that serves one session and then another records each entry against the session it was serving when that decision was taken. Each entry names the agent id and persona of the agent whose call produced it. A decision taken outside every registered session records no entry and reports no error, so a one-off agent leaves no audit entry behind. Where the audit is held is REQ-TOOLS-078's and is fixed nowhere in this document; what this requirement fixes is which session an entry belongs to, which is unchanged by where the audit lives.

**REQ-TOOLS-081** — Per-entry side effects: a `deny` additionally records a `permission_denied` issue (severity warning; actor = agent id or persona; message `Permission denied for <summary or tool>: <reason>`; evidence reference locating the decision in the permission audit, which is the locator of REQ-EVENTS-056 and nothing else: its form, the closed set of record-kind tokens, and which of those tokens names the permission audit are all fixed there and are deliberately not spelled again here, so that the token cannot drift between the record that emits this reference and the record it points into; its record id is the entry identifier REQ-TOOLS-079 is obliged to give; metadata: tool, rule, source, persona). A `user-once`/`user-session` approval emits a `permission_approved` timeline event (`The user approved <summary or tool>`). Every entry also publishes a `permission.decision` event on the session event bus.

**REQ-TOOLS-082** — A mode change writes an entry into the same audit as the decision entries, interleaved in write order, so a reader taking that audit in the order it was recorded — on a surface that renders it, or in the export of REQ-TOOLS-078 — can determine which mode governed any decision by taking the nearest preceding mode-change entry: `{timestamp, event: "permission_mode_change", session_id, agent_id: <source>, requested_mode, effective_mode, previous_mode, source, reason, skipped_personas: [...]}`. `skipped_personas` is always present, including when empty, so an entry that reached every agent is distinguishable from an entry that simply omits the field. An accompanying `permission_mode_changed` timeline event reads `Permission mode changed from '<prev>' to '<effective>'` optionally followed by the reason and, when applicable, `(not applied to persona-pinned agents: a, b)`.

**REQ-TOOLS-083** — The `permission.decision` stream event carries `tool_name`, `decision`, `source`, `rule_id`, `summary` (the request summary of REQ-TOOLS-016), and `request_id`, which is empty whenever the decision was never put to a person — consumers must read an empty `request_id` as unpaired. No published `permission.decision` event ever carries an unmasked credential in `summary`.

### 9. Network Egress Policy and the fetch Tool

**REQ-TOOLS-084** — The order in which the denied list, the allowed list and the configured default disposition are consulted, and the consequence that a denial outranks a broader allow wildcard, are fixed by REQ-SANDBOX-003 and REQ-SANDBOX-014; this domain holds no copy of them. What it relies on them for is that classifying a host yields exactly one of the three dispositions before the `fetch` tool opens any connection. This domain adds only the fail-closed reading it needs: a host that cannot be read (REQ-TOOLS-086) is denied, and no unreadable or ambiguous input is ever classified as allowed.

**REQ-TOOLS-085** — Host patterns support exactly one wildcard form: a single leading `*.`. `*.example.com` matches one or more leading labels (`api.example.com`, `a.b.example.com`) but not bare `example.com`, and not a different domain that merely ends with the same characters — matching compares whole DNS labels, never raw substrings. A `*` anywhere else raises an error at pattern build (message naming the pattern and the only supported form) rather than matching literally or silently matching nothing.

**REQ-TOOLS-086** — REQ-SANDBOX-006 owns host normalization for matching and classification, including unbracketed canonical IPv6. Brackets are added only when constructing a URL authority. When no host can be read, the canonical result is empty and callers MUST classify it as unknown and deny it under REQ-SANDBOX-008.

**REQ-TOOLS-087** — "Local" means genuine loopback only: the names {`localhost`, `localhost.localdomain`, `ip6-localhost`} and loopback IP addresses. Private-range and link-local addresses (e.g., `169.254.169.254`, internal `10.x`) deliberately count as remote — they are exactly what a policy gates. A hostless or unreadable URL counts as remote.

**REQ-TOOLS-088** — Configuration. The egress disposition key `runtime.network_egress_policy`, its accepted values, its shipped default and the matching of a stored spelling are fixed by REQ-SANDBOX-001 and REQ-SANDBOX-002; the two host-list keys `runtime.network_allowed_hosts` and `runtime.network_denied_hosts`, their defaults and their load-time normalization are fixed by REQ-SANDBOX-003 and REQ-SANDBOX-004. This domain holds no copy of any of them. What it relies on those requirements for is that the disposition reaching the `fetch` tool is always one of a closed set of three, so REQ-TOOLS-084 never has to decide what an unrecognized disposition means, and that the two host lists arrive already normalized, so the pattern matching of REQ-TOOLS-085 sees no leading or trailing whitespace, no upper case and no blank entry.

**REQ-TOOLS-089** — The egress policy carried by a run's fetch tool is always built from that run's own runtime configuration; two runs in one process never lend each other an allow-list. Tightening the configured host lists observably changes the policy the agent's fetch tool enforces. A fully permissive policy exists only as the fallback for callers with no configuration at all.

**REQ-TOOLS-090** — `fetch` classifies a host before any connection to it is opened — for the URL the agent supplied and again for every redirect target — so no request and no redirect ever reaches a host the policy denies, and a permitted host cannot hand the request on to a denied one. A single call follows at most 20 redirect hops; a chain that would exceed that returns failure kind `too_many_redirects`.

**REQ-TOOLS-091** — The `ask` disposition belongs to the permission gate, not the fetch executor: by execution time the gate has already resolved the ask for the host the agent named, and that host is pre-seeded as permitted. A redirect onto an unseen host that classifies as `ask` is refused (there is no way to prompt mid-request) with an instruction to request the final host directly. A redirect staying on an already-permitted host (path change, http→https) is not re-gated.

**REQ-TOOLS-092** — Fetch refusals and failures are machine-readable with stable kinds: `egress_denied` (requested host denied), `egress_redirect_denied` (hop denied or ask-on-hop), `egress_policy_error` (a pattern could not be applied — refused, not ignored), `too_many_redirects`, `invalid_request` (the call itself was malformed and no connection was attempted; what makes a request malformed is REQ-SANDBOX-020's and is not restated here), `timeout`, `network_error`, `http_error` (status ≥ 400, with detail `HTTP request completed with status code <n>.` and the observation marked as an error). This requirement is the product's single definition of the fetch failure-kind vocabulary: the set is closed and is exactly those eight spellings, and no requirement in any other domain holds a second copy of it — a requirement that needs the vocabulary cites this one and states only what it adds, such as the `error_class` value or the detail content that accompanies a kind. `invalid_request` carries the same spelling as the terminal observation's member of the same name (REQ-TOOLS-112, REQ-SANDBOX-087), so one word means one thing across the product. The first four kinds are policy refusals — something for the agent to re-plan around — and are distinguishable as a group from `timeout` and `network_error`, which are transient transport faults worth retrying, and from `invalid_request`, which is a fault in the call. Refusals name the blocked host and the governing setting, e.g. `Network egress to <host> was refused: the egress policy (runtime.network_egress_policy) resolves that host to 'deny'.` Error observations include a `[fetch_diagnostic]` JSON block.

> **Narrowed by [`PD-TOOLS-013`](../../product/directives/pd-tools-013.md#pd-tools-013), 2026-10-13 (revision 2).** The fetch vocabulary also
> holds `interrupted` (`error_class` `InterruptedError`), carried by a fetch its run's signal ended before it completed. It
> sits outside the three groups (policy refusal, transient fault, call fault): it is the run's rest, not the fetch's. A
> deadline that expired first still reads `timeout`, and the eight kinds above and everything else here still govern.

**REQ-TOOLS-093** — Fetch action surface: `url` (required), `max_lines` (default 1000), `from_line`/`to_line` (line-range selection), `timeout` (per-call override; otherwise the configured default `runtime.tool_call_timeout`, default 30 s (REQ-CONFIG-115); with no configuration at all the executor's own fallback is 10.0 s). Observation metadata: `url`, `final_url`, `status_code`, `content_type`, `truncated`. The tool returns raw text (including raw HTML) truncated to `max_lines`; a single call retrieves a single resource.

**REQ-TOOLS-094** — Terminal commands that reach the network are recognized by a set of leading-token patterns evaluated under REQ-TOOLS-033. This requirement is the product's single definition of that catalogue: the set is closed and is exactly the patterns listed below, no requirement in any other domain holds a second copy of them, and a requirement that needs the catalogue cites this one and states only what it adds. The recognizer is a pattern matcher in the sense of REQ-TOOLS-038, so a command line is first cut into segments under REQ-TOOLS-035 and each segment is judged on its own leading tokens; one matching segment settles the whole line, and `date && curl https://example.com` is therefore network-reaching. Each pattern is matched under the token rules of REQ-TOOLS-033: matching is by whole tokens, so `curl` matches the segment `curl https://example.com` but never `curling`, and a trailing `*` stands for zero or more further tokens, so a bare `curl` or a bare `npx` submitted with no arguments matches. Requiring at least one further token would leave the trivial bypass of splitting a command across an interactive invocation. The catalogue is a set and not a sequence: the grouping and ordering below are for reading convenience only, carry no meaning, and establish no first-match precedence among the patterns. The patterns:

- transfer and remote-shell clients: `curl *`, `wget *`, `http *`, `https *`, `ssh *`, `scp *`, `sftp *`, `rsync *`, `nc *`, `ncat *`, `telnet *`, `ftp *`;
- version control: `git push *`, `git pull *`, `git fetch *`, `git clone *`, `git remote *`, `git ls-remote *`, `git submodule update *`, `gh *`;
- Python packaging: `pip install *`, `pip download *`, `pip index *`, `pip3 install *`, `pip3 download *`, `uv add *`, `uv sync *`, `uv lock *`, `uv pip install *`, `uv tool install *`, `uv publish *`, `poetry add *`, `poetry install *`;
- JavaScript packaging: `npm install *`, `npm i *`, `npm ci *`, `npm update *`, `npm audit *`, `npm publish *`, `npx *`, `yarn add *`, `yarn install *`, `yarn up *`, `yarn publish *`, `pnpm add *`, `pnpm install *`, `pnpm update *`, `pnpm publish *`, `pnpm dlx *`;
- other language toolchains: `cargo add *`, `cargo fetch *`, `cargo install *`, `cargo update *`, `cargo publish *`, `go get *`, `go install *`, `go mod download *`, `go mod tidy *`;
- system and container package managers: `brew install *`, `brew update *`, `brew upgrade *`, `brew fetch *`, `apt install *`, `apt update *`, `apt upgrade *`, `apt-get install *`, `apt-get update *`, `apt-get upgrade *`, `docker pull *`, `docker push *`.

A command line no segment of which matches any of these patterns is not recognized as network-reaching — `ls -la`, `git status`, `pytest -q`, `cat notes.txt`, and an inline `python -c '…'` snippet all classify as local — and nothing is recognized by inference from a listed spelling. Presets attach the recognizer as `<preset>:network-command` — deny in `restricted`, ask in `ask`, absent from `autonomous` — and that rule id is what appears in the refusal text and in the audit entry. The recognizer is a permission decision about the command string, not enforcement: outside the sandbox nothing prevents a command the recognizer misses from reaching the network. Kernel-level egress control for terminal commands exists only inside the sandbox and is a single on/off switch (REQ-TOOLS-117); per-host filtering of terminal traffic is out of scope for this specification. Because the recognizer is a permission heuristic and never an enforcement boundary, the closed list above is a complete specification of the rule's behavior rather than a claim to catch every network-reaching command; an escaping command line is instead caught, where it is statically unreadable, by the escalation matcher of REQ-TOOLS-038.
