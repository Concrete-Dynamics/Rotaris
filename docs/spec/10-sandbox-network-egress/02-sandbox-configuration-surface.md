# Command Sandboxing and Network Egress Policy — Sandbox configuration surface

Part 2 of 6 of [domain 10](../10-sandbox-network-egress.md), which indexes every part. Defines REQ-SANDBOX-048 – REQ-SANDBOX-128.

### Sandbox configuration surface

- **REQ-SANDBOX-048** — `runtime.sandbox_mode` (string): `off` | `workspace-write` | `read-only`; default `off` (the sandbox is opt-in). Comparison ignores letter case; a value outside those three spellings fails validation both at load and at assignment, and the message names the bad value together with all three valid modes. This requirement is the product's single definition of the confinement-mode vocabulary, its shipped default and its validation, and the three spellings are stable persisted values (REQ-SANDBOX-055); no requirement in any other domain holds a second copy of the vocabulary, the default or the validation rule, and a requirement that needs them cites this one and states only what it adds. Those three are the whole vocabulary: an opportunistic fourth value — one meaning "confine where the host provides a mechanism and run without confinement where it does not" — is deliberately not offered, because a mode that can silently resolve to no confinement would have a run report protection it does not have, which is the silent fallback REQ-SANDBOX-074 forbids. A host that cannot provide the confinement a run asked for is settled by the availability verdict and the refusal that follows it (REQ-SANDBOX-071, REQ-SANDBOX-084), never by weakening the mode the user selected.
- **REQ-SANDBOX-049** — A bare YAML `sandbox_mode: off` (which YAML 1.1 parses as boolean false) must be read as the `off` mode, not rejected as a type error.
- **REQ-SANDBOX-050** — `runtime.sandbox_writable_roots` (list of strings, default empty) names absolute paths that are writable inside the sandbox in addition to the workspace. An entry keeps its text apart from stripped leading and trailing whitespace: no case folding, no separator rewriting, no symlink resolution. An entry that is empty or only whitespace names nothing and is DROPPED at load, exactly as a blank host pattern is under REQ-SANDBOX-004 — trimming already happens first, so treating the residue as a non-absolute path would refuse a whole configuration file over a stray blank line. An entry that is non-blank and not absolute is refused, both at load and at assignment, with a message that names the configuration key, quotes the entry, and states that an absolute path is required, following the rule and message shape REQ-TOOLS-116 fixes for this family of keys. Absoluteness is decided by spelling rather than by the host performing the check, so `/opt/cache` and `C:\Builds\cache` are both accepted in the same file on either platform and one configuration file serves a mixed fleet. A path need not exist when the configuration is read; REQ-SANDBOX-058 settles what happens to a root that is still missing at launch. This requirement is the product's single definition of the key, its default and its entry rules; a requirement that needs them cites this one and states only what it adds, and REQ-CONFIG-468 follows the same rule and message shape for a neighbouring key.
- **REQ-SANDBOX-051** — `runtime.sandbox_allow_network` (bool, default false): grants confined processes network access. It has effect only while a confinement mode other than `off` is selected. The shipped posture is closed. This requirement is the product's single definition of the key and its default; a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-052** — `runtime.allow_unsandboxed_autonomous` (bool, default false): per-workspace opt-in to run unattended in a permissive mode without a sandbox. Its documentation must warn that it belongs in one workspace's configuration rather than the global one.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The key above still exists with the same default and layering; it no longer has any effect on any run.
- **REQ-SANDBOX-053** — Adjacent settings that interact with this domain: `runtime.permission_mode`, whose preset vocabulary is REQ-TOOLS-041's and whose resolution and shipped default are REQ-TOOLS-046's, neither restated here; `runtime.headless_approval_policy`, whose accepted values, shipped default, reading of an unrecognized value and effect on a refused call are REQ-TOOLS-065's and are not restated here — what this domain relies on that requirement for is that an ask raised by a session with no registered approval presenter (REQ-TOOLS-053) always resolves without a prompt and never resolves to allow; `runtime.approval_timeout_seconds`, the single key REQ-CONFIG-126 registers for that bound, whose default this domain does not restate and on whose reading of a stored `0` — a wait without limit — REQ-SANDBOX-020 relies (REQ-TOOLS-055, REQ-TOOLS-178). `runtime.additional_read_only_roots` (REQ-TOOLS-132) is adjacent but does NOT interact with confinement: OS confinement imposes no read restriction whatsoever (REQ-SANDBOX-060), so that key widens the file tools' path fence alone and neither grants nor removes anything inside the sandbox.
- **REQ-SANDBOX-054** — All six sandbox/egress fields (`sandbox_mode`, `sandbox_writable_roots`, `sandbox_allow_network`, `network_egress_policy`, `network_allowed_hosts`, `network_denied_hosts`) survive a write-then-read cycle through the workspace YAML file: the configuration loaded afterwards is the same effective configuration that was saved, and a further save-and-load changes nothing again. The load-time normalizations stated elsewhere still apply on the way in — host patterns arrive trimmed and lower-cased with blanks dropped (REQ-SANDBOX-004), writable-root entries arrive trimmed (REQ-SANDBOX-050), and a YAML boolean false for `sandbox_mode` arrives as `off` (REQ-SANDBOX-049) — so what round-trips is the normalized value, not necessarily the raw text a user first typed.

### Confinement model

- **REQ-SANDBOX-055** — The mode spellings `off`, `workspace-write`, `read-only` are stable persisted values and must not change across releases.
- **REQ-SANDBOX-056** — The workspace-relative subpaths `.git` and `.rotaris` are always read-only inside the sandbox, even within an otherwise writable workspace. The exclusion is fixed: no setting and no configuration combination removes it. A confined command must therefore never be able to install a repository hook that would later run outside confinement, nor to write the configuration that governs a later run.
- **REQ-SANDBOX-057** — The exclusion attaches to the name a command would use rather than to whatever the name ultimately points at: when that name is a link, or a file standing in for a repository directory, writing through it is still refused.
- **REQ-SANDBOX-058** — Effective writable roots by mode, under an active confinement mode: `read-only` grants none; `workspace-write` grants the workspace root first and then each configured additional root, duplicates removed keeping the first occurrence. A configured additional root that does not exist on the host when the invocation is rendered is SKIPPED rather than treated as an error: the remaining roots apply, the command starts, and the skip is recorded as a log entry naming the path. A configured root is optional convenience and must not be able to stop a session; refusing to start on a missing one would make an unused entry fatal. The consequence is stated plainly so it cannot surprise: a skipped root is not writable inside that command even if the command itself creates the directory, because the writable set is fixed when the invocation is rendered and the next command re-renders it. The workspace root itself is not optional — it always exists, being the directory the session runs in (REQ-SANDBOX-091). Separately from the configured roots, every active mode leaves the platform's temporary location writable (REQ-SANDBOX-075, REQ-SANDBOX-076), so `read-only` means "no writable root beyond the temporary location", not "no writable path at all". Mode `off` renders no confinement whatsoever (REQ-SANDBOX-074), so effective writable roots do not apply to it and writes are bounded only by the host operating system.
- **REQ-SANDBOX-059** — The network inside the sandbox stays closed unless `sandbox_allow_network` is true.
- **REQ-SANDBOX-060** — Read access is intentionally unrestricted: a confined command can still read anywhere on the filesystem (e.g. reading `/etc/passwd` succeeds). Only write confinement and the network switch are enforced; restricting reads is deliberately not attempted, because ordinary developer tooling depends on wide read access.
- **REQ-SANDBOX-061** — Backend parity: the same configuration must produce identical write verdicts on both supported platforms, including for a protected subpath that does not yet exist (a fresh worktree with no `.git`/`.rotaris` must still deny creating or writing under those names) and for one that does. Absent that parity, a result observed on one platform would say nothing about the other.
- **REQ-SANDBOX-062** — The sandbox wrapper never changes the working directory: the command runs in the persistent shell's current directory identically on all platforms, sandboxed or not.
- **REQ-SANDBOX-063** — The submitted command travels into the confined environment as a SINGLE shell argument (`/bin/sh -c '<command>'`) and is never split apart again: a compound line containing variable references and quoted arguments with spaces arrives unchanged as the last token of the rendered invocation.
- **REQ-SANDBOX-064** — A workspace path containing quote or backslash characters must not be able to alter the confinement that is applied: every path embedded in the confinement rules and every argument of the rendered invocation must be quoted such that no crafted path can end its enclosing literal and introduce rules of its own.

### Sandbox availability

- **REQ-SANDBOX-065** — The confinement mechanism follows from the host operating system alone: macOS → Seatbelt (launcher `sandbox-exec`); Linux, a WSL2 distribution included → bubblewrap (launcher `bwrap`); every other operating system → no mechanism, `available` false and backend name `unavailable`. The choice is made before PATH is consulted and before any trial runs, so on macOS without `sandbox-exec` the diagnostic still names Seatbelt and on Linux without `bwrap` it still names bubblewrap, rather than either reporting an unsupported platform. The set of recognized platform identifiers is CLOSED and contains exactly two members: the identifier the host runtime reports for the macOS family, `darwin`, and the one it reports for the Linux family, `linux` — which a WSL2 distribution also reports. Comparison is by exact equality after trimming and lowercasing. Every other identifier, `win32` included, is unrecognized and yields `available` false with backend name `unavailable` and the diagnostics of REQ-SANDBOX-073. No legacy or historical identifier is recognized and none may be added: a clean-room product has no earlier release to stay compatible with, and an open-ended list of aliases could not be tested exhaustively — which is the very defect this closes.
- **REQ-SANDBOX-066** — Availability probing proceeds in increasing order of cost: platform check, then launcher lookup on PATH, then a trial launch. No subprocess is spawned once an earlier step has already failed.
- **REQ-SANDBOX-067** — Availability must be demonstrated rather than inferred: locating the launcher on PATH is required but does not settle the question, because a host that restricts unprivileged user namespaces can have the launcher installed while every launch fails. A disposable trial confinement is therefore launched at most once per process, and its result is cached for later probes. The verdict is binary: there is no partial or degraded availability, so a host whose namespace restrictions are only partly in force is either able to complete the trial, in which case it is `available`, or it is not. A cached verdict is never re-derived on its own; it is cleared only by the explicit re-check of REQ-SANDBOX-129 or by restarting the application. A host that completes the trial but later refuses a real confinement is not a hole in this rule: that command is refused by REQ-SANDBOX-083 or relabelled by REQ-SANDBOX-085 and never runs unconfined.
- **REQ-SANDBOX-068** — The one success criterion for the trial is termination with exit status 0 inside the trial timeout; whatever the trial writes to its output is irrelevant to a success verdict. Every other outcome yields `available` false with a reason identifying which of these occurred: the trial did not finish within 5 seconds and was terminated; the trial could not be started at all, with the reported launch error; the trial exited with status N, the reason then carrying the first non-empty line of its diagnostic output; the trial exited with status N having produced no output, which the reason states. An outcome that cannot be interpreted counts as a failure and never as a success — a wrong `unavailable` costs only stricter prompting, a wrong `available` would let commands run against the host with no confinement.
- **REQ-SANDBOX-069** — The trial launch timeout is 5.0 seconds. It is a hard bound, not a hint: a trial still running at 5.0 seconds is terminated and counts as a failure under REQ-SANDBOX-068, is never extended, and is never retried within the same process. A launcher slow enough to approach the bound is therefore reported unavailable, and the user's remedy is the re-check of REQ-SANDBOX-129. The probe never runs on the thread that draws the interface, so no surface waits on it (REQ-SANDBOX-129).
- **REQ-SANDBOX-070** — The trial goes through the real mechanism, never a stand-in. On macOS it runs `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` — the widest ruleset that still engages Seatbelt, so a failure implicates the mechanism rather than any single restriction. On Linux it uses the option rendering the product would produce for a read-only confinement rooted at `/` with no carve-outs and no writable roots, keeps the network namespace separate whatever `runtime.sandbox_allow_network` says, and ends in the same final tokens every rendered session invocation ends in — `-- /bin/sh -c 'true'` (REQ-SANDBOX-079), never a bare `-- true`, so that the interpreter step a real command depends on is exercised by the trial rather than left untested. The macOS trial deliberately does not follow that pattern: it stays the literal `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true`, because Seatbelt's failure mode is the profile rather than the exec chain and because REQ-SANDBOX-073 offers that exact line to the user as a command to run by hand. Rendering either trial invocation reads no path on the filesystem.
- **REQ-SANDBOX-071** — The availability verdict is a value with: `available` (bool); a backend name (`seatbelt` | `bubblewrap` | `unavailable`); `reason`, one sentence naming the cause; `remediation`, one sentence naming the suggested fix — reason and remediation empty when available. Those three fields are the complete answer the platform confinement service gives, and every surface that reports availability presents that same text: the desktop settings surface (REQ-SANDBOX-116), the per-session launch dialog (REQ-SANDBOX-119, REQ-SANDBOX-120), the run-refusal record of REQ-SANDBOX-126, and the application log. The guidance a user sees therefore never differs by surface.
- **REQ-SANDBOX-072** — The unavailability error renders as the reason, then the remediation on its own line; with no remediation, just the reason; with no reason, a generic line reporting that no OS-level confinement can be used on this host.
- **REQ-SANDBOX-073** — Diagnostic content per scenario. Each string quoted below must appear literally in the reason or the remediation as indicated, and each stated fact must be conveyed; the wording around them is free.
  - Native Windows: the reason states that no OS-level confinement is available on native Windows and names both supported pairings, macOS with Seatbelt and Linux with bubblewrap. The remediation offers two courses — running under a WSL2 distribution with bubblewrap installed, quoting `sudo apt-get install bubblewrap`, or leaving `runtime.sandbox_mode` at `off`.
  - Unrecognized operating system: the reason quotes the platform identifier actually detected and does not claim the host is Windows. The remediation names macOS and Linux/WSL2 as the supported hosts.
  - Seatbelt selected on a host that is not macOS, or its launcher not found: the text quotes `sandbox-exec`, states that macOS supplies it, and suggests checking that `/usr/bin` is on PATH.
  - Bubblewrap launcher not found: the remediation quotes both `sudo apt-get install bubblewrap` and `sudo dnf install bubblewrap`.
  - Bubblewrap trial failure: the reason carries the launcher's own diagnostic output as described in REQ-SANDBOX-068. The remediation quotes `kernel.apparmor_restrict_unprivileged_userns` and `/proc/sys/kernel/unprivileged_userns_clone` as the controls gating unprivileged user namespaces, quotes `bwrap --ro-bind / / --proc /proc --unshare-net -- true` as a command to try by hand, and states that a workspace requesting confinement keeps failing for as long as the launcher fails — never that its runs proceed unconfined, which REQ-SANDBOX-074 and REQ-SANDBOX-084 forbid.
  - Seatbelt trial failure: the remediation quotes `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` as a command to try by hand.
- **REQ-SANDBOX-074** — There is no silent fallback: preparing a command for confinement either yields a NEW confined command string or reports an availability error; it never yields the original command. The single exception is mode `off`, which passes the command through unchanged on every platform and performs no probing.

### Rendered OS confinement (observable invocations)

- **REQ-SANDBOX-075** — Observable behavior of the macOS profile: everything is refused unless allowed. Permitted in every active mode — executing and forking processes, reading sysctl values, sending signals, reading any path on the filesystem, writing under the temporary locations `/tmp`, `/private/tmp`, `/var/tmp`, `/private/var/tmp`, `/private/var/folders`, and writing data to the device nodes `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/tty`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr`, `/dev/dtracehelper`. In `workspace-write`, each effective writable root of REQ-SANDBOX-058 additionally permits writes throughout its subtree, one allowance per root, with the protected subpaths of REQ-SANDBOX-056 denied; those denials appear after every allowance in the profile, the position at which they take effect, so a write under `<workspace>/.git` or `<workspace>/.rotaris` fails while a write elsewhere in the workspace succeeds. In `read-only` no writable root appears and writes succeed only at the temporary locations and device nodes named above. The network is permitted or refused as a whole according to `runtime.sandbox_allow_network`, with no distinction by destination (REQ-SANDBOX-047).
- **REQ-SANDBOX-076** — Linux confinement invocation behavior: the entire root filesystem bound read-only; device and proc filesystems provided; a fresh empty temp filesystem at `/tmp`; each effective writable root re-bound writable; the excluded subpaths applied after those writable binds, since ordering decides the outcome and an exclusion placed before the workspace bind would simply be covered over; the network namespace kept separate unless the opt-in grants network; and the confined process terminated together with its parent.
- **REQ-SANDBOX-077** — On Linux the rendering for a protected subpath (`.git`, `.rotaris`) turns on where the path sits and whether it exists, and in every case a write to that name inside confinement fails:
  - (a) The path lies outside every writable root, as in `read-only` mode: nothing extra is rendered. The read-only root already refuses the write, and the session starts normally.
  - (b) The path exists inside a writable root: it is re-bound read-only in the form that tolerates a missing source, `--ro-bind-try <p> <p>`. Its real contents stay readable, so `git status` keeps working under confinement; writes to it fail; and the command still starts if the path is removed between rendering and launch.
  - (c) The path does not exist inside a writable root, as in a freshly created worktree holding neither directory: an empty read-only filesystem is mounted at that name, rendered `--tmpfs <p>` followed by `--remount-ro <p>`. The name reads as empty and nothing can be created under it. A confined command must not be able to bring `.git` or `.rotaris` into existence where they were absent.

  Every carve-out of this requirement exists only inside the confined process's own mount view and leaves nothing behind on the host: once the command ends, the host filesystem holds exactly what it held before with respect to that name, so a protected subpath absent under case (c) is still absent afterwards and no empty directory remains for anything to clean up. A backend that cannot establish a carve-out without creating a host-visible file or directory SHALL NOT create one; it refuses the command under REQ-SANDBOX-083 instead.
- **REQ-SANDBOX-078** — Where the existence check of REQ-SANDBOX-077 races a filesystem change, the outcome lands on the restrictive side: a protected subpath created after the check stays hidden behind the empty read-only mount, its real content neither readable nor writable inside that command; a protected subpath deleted after the check does not stop the command starting, the tolerant bind of case (b) accepting a missing source; and a symlink with no target counts as an absent path, taking case (c). If the carve-out cannot be established at launch, the command does not run: it is refused exactly as in REQ-SANDBOX-083, with `failure_kind` `sandbox_unavailable` and exit code 126, and under no circumstances does it run with the carve-out missing. That refusal is scoped to the one command and SHALL NOT end the session: the session already passed the start-time availability gate (REQ-SANDBOX-094), the cause is per-command and may be a transient filesystem race, and the next command submitted is rendered and launched afresh. A session that keeps failing this way keeps refusing commands and never runs one unconfined.
- **REQ-SANDBOX-079** — Final wrapped command shapes: macOS — `sandbox-exec -p '<profile>' /bin/sh -c '<command>'`; Linux — `bwrap <options…> -- /bin/sh -c '<command>'`. All items are shell-quoted. Each confined command starts a fresh inner shell initialized from the session's configured working directory and environment. Working-directory changes, exports and aliases inside that invocation end with it. Unconfined foreground commands retain the persistent-shell contract of REQ-TOOLS-097. Tool descriptions and observations MUST explain which lifetime is in force; the confinement wrapper preserves the configured initial working directory under REQ-SANDBOX-062.
- **REQ-SANDBOX-127** — The rendered invocation is a means, not the contract. A confinement backend SHALL be judged conformant only by the observable effect on a live process on a real host of the platform concerned, and a rendering that matches REQ-SANDBOX-075 to REQ-SANDBOX-079 word for word but does not produce that effect is non-conformant. The effects that must be demonstrated on each supported platform, under an active confinement mode, are: a write inside an effective writable root of REQ-SANDBOX-058 succeeds; a write anywhere outside every effective writable root and outside the platform's temporary locations is refused; a write under `<root>/.git` or `<root>/.rotaris` is refused whether or not the subpath existed beforehand (REQ-SANDBOX-056, REQ-SANDBOX-061, REQ-SANDBOX-077); a read of a path outside every writable root succeeds (REQ-SANDBOX-060); an outbound socket is refused while `runtime.sandbox_allow_network` is false and succeeds while it is true (REQ-SANDBOX-059); and the working directory the command observes is unchanged by confinement (REQ-SANDBOX-062). No backend may be reported `available` on the strength of a rendered string alone, and no substitute or emulated backend may satisfy this check on behalf of an absent one.
- **REQ-SANDBOX-128** — A denial that occurs INSIDE an active confinement is the host operating system's own. The product does not interpret, translate, normalize, annotate, or retry it: whatever error the platform gives the confined program is what that program sees, the program's own output reaches the terminal observation unchanged, and no requirement in this domain turns on a particular error number or system-log entry. A write refused by confinement is therefore indistinguishable, to the agent and to the user, from a write refused by ordinary file permissions, and that is deliberate — the alternative would require the product to parse platform-specific errors it cannot enumerate. Such a command is an ordinary nonzero-exit command: it is never labelled `sandbox_unavailable`, which REQ-SANDBOX-085's launcher-prefix test reserves for confinement that failed to START.
