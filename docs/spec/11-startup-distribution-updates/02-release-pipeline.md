# Application Startup, Distribution, and Updates — Release pipeline

Part 2 of 10 of [domain 11](../11-startup-distribution-updates.md), which indexes every part. Defines REQ-STARTUP-027 – REQ-STARTUP-156.

### Release pipeline

**REQ-STARTUP-027** — A release SHALL be triggered only by pushing a tag of the exact grammar `v<major>.<minor>.<patch>`, optionally followed by a PEP 440 prerelease suffix `a<N>`, `b<N>`, or `rc<N>` (e.g. `v1.2.3`, `v1.2.3rc1`). Refs that do not match this grammar — `vlatest`, `v1.2.3dev1`, `1.2.3`, `v1.2`, `v1.2.3-rc1`, and branch refs among them — SHALL NOT trigger a release; when a candidate string is validated, the rejection message SHALL name the offending tag and describe the expected shape.

**REQ-STARTUP-028** — Before any build, a guard SHALL verify that the tag version equals every product version the build declares (REQ-STARTUP-158). On mismatch it SHALL fail (exit code 1, stopping all platform builds) with a message that names the tag version, every declared version that differs from it, and the location of each place a version is declared, and instructs that the product releases one version and that every such place must be bumped to the tag. The same pre-build guard stage SHALL additionally enforce the package-pin agreement of REQ-STARTUP-059 and SHALL fail the same way — one stage, one exit code, all platform builds stopped — so that no platform is ever built from a release whose pins disagree.

**REQ-STARTUP-029** — Release-channel classification SHALL map plain `X.Y.Z` to `stable` and any `aN`/`bN`/`rcN` suffix to `prerelease`; an invalid version string SHALL be an error stating it is not a supported product version.

**REQ-STARTUP-030** — The build matrix SHALL cover exactly `windows-x64`, `macos-arm64`, and `linux-x86_64`, and a failure on one platform SHALL NOT cancel the others. The final release SHALL publish whatever artifacts survived, and a separate overall status SHALL still report failure when any platform failed, so a partial release is visible.

> **Narrowed by [`PD-STARTUP-001`](../../product/directives/pd-startup-001.md#pd-startup-001), 2026-09-25.** Until the directive is
> withdrawn the build matrix covers `windows-x64` alone. A failure of that one platform is a failed release
> rather than a partial one; the overall status still reports it.

**REQ-STARTUP-031** — Artifact names SHALL come from a single authority shared with the updater, with these exact shapes: `Rotaris-{v}-windows-x64-setup.exe` (installer), `Rotaris-{v}-windows-x64-portable.exe` (portable), `Rotaris-{v}-macos-arm64.dmg`, and `Rotaris-{v}-linux-x86_64.AppImage`. Requesting an unknown artifact kind SHALL error listing the known kinds. Per-platform kinds: windows-x64 → setup, portable; macos-arm64 → dmg; linux-x86_64 → appimage. No console archive kind exists, the console binaries it carried having been withdrawn with REQ-STARTUP-002.

**REQ-STARTUP-032** — Each release SHALL publish a checksum manifest named `SHA256SUMS.txt`: one line per asset in the form `<sha256hex>  <filename>` (two-space separator), sorted by filename, compatible with `sha256sum -c`. Each release SHALL also publish, beside that manifest, a detached signature over the manifest's exact published bytes, named `SHA256SUMS.txt.sig` (REQ-STARTUP-167). The manifest SHALL list every other published asset and SHALL list neither itself nor that signature: the signature is what establishes the manifest rather than something the manifest establishes, and a manifest cannot carry a digest computed over a file derived from the manifest itself. The signature is detached, so the manifest's bytes are the same bytes whether they are read by the update path or by `sha256sum -c` (REQ-STARTUP-152).

**REQ-STARTUP-167** — The checksum manifest of REQ-STARTUP-032 SHALL be signed, and the update path SHALL install nothing whose manifest signature it has not verified. This requirement is the product's single definition of publisher authenticity for updates; a document that needs to say what an update establishes about who published it cites this identifier rather than restating it.

Every published artifact SHALL carry within itself the verification counterpart of the release signing key, and SHALL resolve it from within what was installed with no additional download (REQ-STARTUP-159). The set of keys a build accepts SHALL be fixed when that build is produced. Nothing at run time SHALL add to it, replace it, or disable it — no configuration value, no preference, no environment variable, no interface control, and nothing the product downloads (REQ-STARTUP-111, REQ-STARTUP-146, REQ-STARTUP-147) — because a trust anchor a network can replace establishes nothing. A signature made by a key the running build does not carry SHALL be treated as not verifying.

What this establishes, and what it does not, are both observable. An update this product installs is established as the bytes the manifest names (REQ-STARTUP-123) **and** as having been published by a holder of a key the running build was built to trust; the manifest no longer establishes only what was downloaded over the same connection the download came from. It is not established as reviewed, safe, or correct. It says nothing about the artifacts themselves carrying a code signature: the artifacts stay unsigned by design, and this requirement changes nothing about what an operating system does with a downloaded file, so the first-launch platform trust prompts of REQ-STARTUP-021 and REQ-STARTUP-023 are exactly as they were.

A release published without a signature this build can verify SHALL NOT be installed by this build under any circumstance. There SHALL be no override, no confirmation, no setting, and no retry by which a user installs an update whose manifest signature did not verify; the refusal is the intended outcome and not a condition to be worked around (REQ-STARTUP-123).

**REQ-STARTUP-168** — The release signing key of REQ-STARTUP-167 SHALL be replaceable without stranding installations already in the field, and the product SHALL state what happens where it cannot be. The obligations below are behavioral; how a key is generated, held, or transferred is an architecture decision and is fixed nowhere in this document.

(a) *A build may trust more than one key.* What a build carries under REQ-STARTUP-167 SHALL be a set rather than a single value, so that a build produced before a rotation and a build produced after it can both verify the same release. How many members that set holds is an implementation choice and no surface of the product reports it.

(b) *A release SHALL be verifiable by the installations it is offered to.* A release SHALL be signed with a key carried by every published artifact this product may offer that release to as an update (REQ-STARTUP-107). This is decidable before publishing, from the releases already published and the keys their artifacts carry, and it SHALL be decided then rather than discovered afterwards; the release gate of REQ-STARTUP-156 is where it is decided.

(c) *A key that must be withdrawn is withdrawn, and the cost is visible rather than hidden.* Where a key is withdrawn before (b) can be satisfied — the case a compromise produces — the installations that carry only that key SHALL refuse the install on the terms of REQ-STARTUP-123 and SHALL NOT install unverified. Those installations SHALL keep working exactly as they did: a build whose trusted set no longer covers current releases loses the ability to update itself and loses nothing else, and its update *check* stays silent as REQ-STARTUP-110 and REQ-STARTUP-150 require, the visible refusal arising only where a user asks for the install.

(d) *A withdrawn key is withdrawn wherever it still can be.* Once a key has been withdrawn, no release SHALL be signed with it and no build produced afterwards SHALL carry its verification counterpart. Builds already published keep what they were built with; this document specifies no mechanism by which a published build's trusted set changes after publication, and REQ-STARTUP-167 forbids one from existing.

**REQ-STARTUP-033** — The generated changelog SHALL compare against the previous tag: with no previous tag, the body is exactly `First release — no previous tag to compare against.`; with a previous tag but no commits, `No commits since <prev>.`; otherwise `Changes since <prev>:` followed by one bullet per commit subject (merge commits excluded).

**REQ-STARTUP-034** — The published release SHALL be named `Rotaris <version>` and flagged prerelease when the channel is `prerelease`.

**REQ-STARTUP-035** — The release body SHALL contain the following elements, each individually checkable, in this order: (1) the heading `## Rotaris {v}`; (2) a line stating the release was built from tag `v{v}`, containing that tag string literally; (3) a table with exactly one row per published asset except `SHA256SUMS.txt` and the signature published over it (REQ-STARTUP-032), each row carrying that asset's filename and its SHA-256 hex digest, the digest being the same value that release's `SHA256SUMS.txt` lists for the same filename (REQ-STARTUP-032); (4) present if and only if at least one platform of REQ-STARTUP-030 contributed no asset, a blockquote reading `**Not built in this release: <platform labels>.** Those builds failed; the artifacts above are unaffected. Use the previous release for the missing platforms.`; (5) a verification hint naming the command `sha256sum -c SHA256SUMS.txt` for macOS and Linux and, for Windows, the command `certutil -hashfile <filename> SHA256` — chosen because it is present on every supported Windows installation and needs nothing installed — together with a statement that the hexadecimal digest the Windows command prints is compared, ignoring case and ignoring any spacing the command inserts, against the line of `SHA256SUMS.txt` carrying that filename; (6) a caveat stating that the binaries carry no code signature, naming both SmartScreen and Gatekeeper, and stating that the checksum manifest published with the release is signed and that the product verifies that signature before it installs an update (REQ-STARTUP-167), so a reader does not take the absence of a code signature to mean the update path establishes nothing about who published the release; (7) a `## Changes` section whose content is the changelog of REQ-STARTUP-033.

> written for `macos-arm64` or `linux-x86_64` while the directive stands, because those builds were not

**REQ-STARTUP-036** — *Withdrawn.* Its whole surface was the publication of two packages of one language ecosystem to that ecosystem's package index, which describes a different product; where and how the product is published is an architecture decision, not a behavior a user observes. Nothing a user can see is lost: the artifacts a release publishes are exactly those of REQ-STARTUP-031, a release carries one product version (REQ-STARTUP-158), and a prerelease tag publishes those same artifacts under a release flagged prerelease (REQ-STARTUP-029, REQ-STARTUP-034).

**REQ-STARTUP-037** — A licence-inventory generation and validation step (REQ-STARTUP-143) SHALL run per platform before freezing, and its failure SHALL fail that platform's release.

**REQ-STARTUP-038** — Every published stable release SHALL satisfy the following distribution claims, each independently verifiable: each desktop artifact the official download page offers SHALL have the same filename and the same SHA-256 digest as the asset of that name in the most recent GitHub release of the product repository; the desktop artifact SHALL run with nothing else installed and with no network access (REQ-STARTUP-159); and the release SHALL have been produced by the tag-triggered pipeline of REQ-STARTUP-027 and published together with a `SHA256SUMS.txt` covering every published asset it is required to cover and with a signature over that manifest which verifies against a key the release's own artifacts carry (REQ-STARTUP-032, REQ-STARTUP-167). No download surface SHALL state a distribution claim that contradicts these.

**REQ-STARTUP-156** — Release acceptance SHALL rest only on evidence the product itself can produce, and SHALL be exactly the following set, each of which is decidable inside the pipeline or on a machine the release owner provisions for the purpose: the version guard and package-pin guard of REQ-STARTUP-028 passed; the notices validation of REQ-STARTUP-037 and REQ-STARTUP-143 passed on every platform that contributed an asset; `SHA256SUMS.txt` covers every published asset it is required to cover and every listed digest matches its asset (REQ-STARTUP-032); the signature published over that manifest verifies, and it verifies against a key carried by every published artifact this release may be offered to as an update, so no installation in the field is stranded by this release (REQ-STARTUP-167, REQ-STARTUP-168 (b)); the release body carries the seven elements of REQ-STARTUP-035; and, on each of the three platform keys of REQ-STARTUP-030, every published artifact of that platform key has been downloaded and launched to first paint under the conditions REQ-STARTUP-159 states, so the offline-run claim of that requirement is observed rather than assumed.

The launch check SHALL be performed on a machine brought to those conditions, and not on whatever machine is to hand: a gate that tests something weaker than the requirement can pass while the requirement fails, which is a defect in the gate whatever the requirement's other outcomes. The conditions are REQ-STARTUP-159's own and are not restated here beyond naming what the gate SHALL establish before it may record a pass. (1) The machine is one of that platform key and, on Linux, the unmodified baseline REQ-STARTUP-024 names — not a machine the release owner has configured for building, testing, or development, and not one carrying the toolchain a build was produced with. (2) It carries no separately installed language runtime, framework, or component of the product obtained by any other route. (3) All outbound network access is blocked for the duration of the check. (4) The artifact under test is the published asset, obtained through the download surface a user would use and matching the digest that release's `SHA256SUMS.txt` lists for it (REQ-STARTUP-032, REQ-STARTUP-038). That the release owner controls the machine means only that they provision it and may restore it between releases; it never licenses taking the check on a machine that does not meet those four conditions. A check for which all four cannot be established SHALL be recorded as not performed and SHALL fail the gate; it SHALL NOT be recorded as a pass on the strength of a launch observed under other conditions.

Every published artifact of a platform key is checked, not one artifact per platform key, because REQ-STARTUP-159 makes the claim of each published artifact and two flavours of one platform key do not share a launch path (REQ-STARTUP-031, REQ-STARTUP-013). For an artifact that prepares itself (REQ-STARTUP-165) the check SHALL observe two runs on that same machine: the run that prepares, which establishes that the artifact starts and is exempt from the first-paint bound under REQ-STARTUP-155, and a later run of that same artifact, which is where that bound is observed. Recording only the first would leave the bound untested for exactly the artifact the exemption was written for.

Behaviors owned outside the product SHALL NOT be release gates and SHALL NOT be asserted as requirements: how the release page renders, what the release host does with the prerelease flag, how the release API answers when rate limits are exhausted, the exact wording or sequence of the operating system's own first-launch trust warnings, and what a silent installation contributes to shell integration are each observed and disclosed rather than guaranteed, and none of them SHALL block or retract a release. This is consistent with REQ-STARTUP-110: an update check that fails because an externally owned behavior changed is invisible by design, so no release needs to be held against it.
