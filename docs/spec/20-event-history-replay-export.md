# Machine-Readable Event Stream, Replay, and Trajectory Export

## Overview

A run of the agent is consumable by software as well as readable by a person. Every run raises a stream of events — one JSON object per runtime event — covering session boundaries, iterations, tool calls, permission decisions, hooks, checkpoints, gates, approvals, transcript rows, usage, errors, and a single terminal outcome. That stream is delivered live to whatever is watching the run and, whether or not anything is, is recorded event by event into a durable per-session history that only this application reads. That history can afterwards be listed, filtered, and replayed from the desktop interface, exported as JSON lines identical to the ones the run emitted, or converted into one portable JSON document per run for offline scoring and comparison. Those two exports are how a history leaves this application, and each is readable with a stock JSON parser on a machine carrying none of this product's code (REQ-EVENTS-166). Human-readable text never travels on the event channel; it reaches the user through the interface's own surfaces. Masking is part of what an event *is*, not something a later stage applies, so the stored history and any exported document can only ever contain what the emitted event already contained.

## Requirements

### A. Withdrawn command-line surfaces

This product is one graphical desktop application. It has no command-line interface, no headless
entry point, and no full-screen text-mode interface, so no requirement of this domain is expressed
as a shell invocation, a flag, a subcommand, an exit code, or a byte stream on standard output. The
capabilities this section once carried are reachable from the desktop interface under Section P.

**REQ-EVENTS-001** — *Withdrawn.* The product has no command-line surface, so there are no two surfaces to hold to observable equality; the equality that remains — every run leaving the same stored history whatever observes it — is carried by REQ-EVENTS-081.

**REQ-EVENTS-002** — *Withdrawn.* There is no invocation to carry an output-format flag; the machine-readable event stream is not an alternative to human output but is produced unconditionally by every run (REQ-EVENTS-081) and reachable through Section P.

**REQ-EVENTS-003** — *Withdrawn.* No flag exists to carry a rejected value, and there is no process exit code.

**REQ-EVENTS-004** — *Withdrawn.* No invocation exists that could pair an output format with a missing task.

**REQ-EVENTS-005** — *Withdrawn.* There is no non-interactive execution path and no standard output an interface could contend for; every run executes inside the desktop application.

**REQ-EVENTS-006** — *Withdrawn.* The inspect, replay, and export capabilities of the `events` command group are carried by the desktop session-history surface of REQ-EVENTS-168, REQ-EVENTS-170 and REQ-EVENTS-173.

**REQ-EVENTS-007** — *Withdrawn.* There is no workspace flag; a history surface reads the workspace its window has open, per REQ-EVENTS-168.

**REQ-EVENTS-008** — *Withdrawn.* The four filter axes are carried by REQ-EVENTS-171 as controls on the history surface, and the JSON-lines form of the selection by REQ-EVENTS-172.

**REQ-EVENTS-009** — *Withdrawn.* Selecting several sessions for one export, and choosing where the document is written, are carried by REQ-EVENTS-173.

**REQ-EVENTS-010** — *Withdrawn.* No flags exist to constrain; the listing capability is carried by REQ-EVENTS-168.

**REQ-EVENTS-011** — *Withdrawn.* There is no command group to invoke without a subcommand, and no exit code.

**REQ-EVENTS-012** — *Withdrawn.* There is no headless surface, no stdout to keep free of setup output, and no exit code; first-run setup is the desktop application's own start-up concern and belongs to no requirement of this domain.

### B. Live event channel semantics

**REQ-EVENTS-013** — The live event channel MUST carry exactly one JSON object per runtime event and no other content: no human-readable text, no progress rendering, and nothing a component other than this product constructed may be placed on it. Human-readable messages produced during a run — including those produced while a run is being stopped — reach the user through the desktop notice channel, the session transcript, and the session's durable diagnostics, never through this channel. This specification fixes which events occur and in what relative order (REQ-EVENTS-076); it fixes no arrival frequency, and a consumer MUST NOT derive one from event spacing.

**REQ-EVENTS-014** — *Withdrawn.* There is no alternative text output stream to keep free of events; the human-readable presentation of a run is the desktop interface, which is fed by the same events and never by a parallel text rendering. The guarantee that a run records its durable history whatever is observing it is carried by REQ-EVENTS-081.

**REQ-EVENTS-015** — Observation MUST change only what is observed, never the work performed. Given two otherwise identical runs, one observed by an attached live consumer (REQ-EVENTS-164, REQ-EVENTS-165) and one observed by none, the two runs MUST leave the same kinds of durable record for their sessions — the same evidence records, present or absent alike — and their stored histories MUST hold the same number of events, of the same types, in the same order, each event carrying the same set of field names. Comparing the two histories event by event and field by field, only these values may differ: timestamps, durations, the session id, per-run identifiers (`call_id`, `request_id`, `child_id`, `hook_id`, checkpoint `ref` and `sequence`), and token and cost figures. Every other field MUST compare equal, and both runs MUST reach the same terminal status.

**REQ-EVENTS-016** — For any run that actually starts, the emitted stream MUST begin with a `session.start` event, MUST end with a `result` event, MUST contain exactly one `result` event, and MUST place `session.end` before `result`.

**REQ-EVENTS-017** — Every event delivered on the live channel, every event held in a stored history, and every non-empty line of an exported history (REQ-EVENTS-172), MUST parse as exactly one JSON object; MUST carry the four envelope fields of REQ-EVENTS-036 with the types stated there; MUST carry an `event` value drawn from the catalog of REQ-EVENTS-041; and MUST carry every payload field listed for that type under "Event catalog and payload fields", each of the type stated there, falling back to that field's documented default where the run has no value for it. A payload field may therefore be null or empty, but MUST NOT be absent. For a run that started and reached its terminal `result`, a consumer that decodes and validates every event of that run MUST reject none of them.

**REQ-EVENTS-018** — The moment `session.start` is emitted, the desktop interface MUST make observable that a session began, stating whether it was created or resumed and naming its session id. The announcement MUST NOT be placed on the live event channel (REQ-EVENTS-013). Its wording and placement are the implementation's; the two facts it carries are not. A run that never starts MUST announce nothing.

**REQ-EVENTS-019** — At the end of a run the desktop interface MUST report the outcome exactly once for that run. The report MUST state the terminal status of REQ-EVENTS-026 in words; MUST carry the run summary — the `summary` field of the terminal `result` payload — where that summary is neither empty nor only whitespace; MUST carry the `error` field of that payload where the status is `error`; and, where the summary is empty, MUST still convey the status rather than reporting nothing. The status is therefore always recoverable from the report and never inferred from the presence or absence of a summary. Wording is the implementation's, subject to those obligations.

### C. Terminal outcome and statuses

**REQ-EVENTS-020** — Every way a run can end MUST produce exactly one terminal `result` event. There is no path — success, failure, refusal before start, crash, or a stop the user asked for — on which a run's event sequence ends without one.

**REQ-EVENTS-021** — Given a run refused before it starts — an invalid run configuration, a prerequisite the host cannot supply, or any other condition detected before the run loop exists — the entire event sequence for that run MUST consist of exactly one `result` event with status `error`, no `session.start` may be emitted, and the reason MUST be reported to the user per REQ-EVENTS-019.

**REQ-EVENTS-022** — Given a failure the run does not itself handle, the stream MUST end with a `result` event whose status is `error`; that `result` MUST be the last event delivered on the live channel and the last record the run contributes to its stored history; and the failure MUST be reported to the user per REQ-EVENTS-019. No event for that session may be observed on any channel after that `result`.

**REQ-EVENTS-023** — Given the user stops or cancels a run, the stream MUST end with a `result` event of status `interrupted`, and the outcome report of REQ-EVENTS-019 MUST state that the run was interrupted.

**REQ-EVENTS-024** — Given an execution sandbox that was requested but that the host cannot supply, the run MUST be refused before it starts on the terms of REQ-EVENTS-021: no `session.start` may be emitted, and the event sequence MUST consist of exactly one `result` with status `error`. The `error` field of that `result` payload MUST contain, as unaltered substrings, both the reason the sandbox backend gave for refusing and the corrective step that backend suggested, so that a consumer can act on the backend's own wording without inspecting the host itself.

**REQ-EVENTS-025** — *Withdrawn.* The application does not exit when a run ends, so a run's terminal status is the whole of its machine-readable outcome (REQ-ORCH-083) and no mapping onto a process exit code exists to state. The status vocabulary itself is unaffected and is carried by REQ-EVENTS-026.

**REQ-EVENTS-026** — The run status vocabulary on the wire MUST be exactly the closed terminal run-result set of REQ-ORCH-083; this document holds no copy of that set and mints no status string of its own. What it relies on that requirement for is that the set is closed and machine-readable, so that a status read off the wire is the same value the run recorded. That vocabulary is closed for the `status` field of a terminal `result` payload: a value outside it MUST NOT be emitted. Given a derivation that produced an unrecognized value, the run MUST report `error` — never a successful status — and MUST record a diagnostic that quotes the unrecognized value, so the defect is evidenced rather than silently rewritten.

**REQ-EVENTS-027** — Terminal status MUST be decided from the `stop_reason` the run recorded, matched against the closed stop-reason set of REQ-MONITOR-301 by exact, case-sensitive equality and classified by the total mapping that requirement fixes; the terminal result that mapping produces is the status this document emits on the wire (REQ-EVENTS-026). This document holds no copy of that set and no second mapping: `agent_session_aborted` therefore yields `failed` even where the run otherwise appears to have finished its work, exactly as REQ-MONITOR-301 says, and a recorded stop reason outside the closed set is a defect, not a value for a fallback to classify — it MUST yield `error` with the diagnostic REQ-EVENTS-026 requires, and MUST NOT be reported as a successful status. Where the run recorded no stop reason at all, the session's persisted `execution_status` decides instead, through the total mapping of REQ-SESSION-076 over the closed vocabulary of REQ-SESSION-073; this document restates neither that vocabulary nor that mapping, and any status those requirements do not map to a definite outcome yields `error`, never a successful status.

**REQ-EVENTS-028** — Given a cancellation requested before the run loop exists, the run MUST NOT start and MUST still produce an `interrupted` terminal result. Given a cancellation was requested at any point, `interrupted` MUST win over an apparently completed outcome.

### D. Stream writer robustness

**REQ-EVENTS-029** — Each event MUST be added to the session's history as exactly one record, made durable individually at the moment it is raised and never in accumulated batches. Durable individually is not an optimization and serves no reader: it is what makes the durable record REQ-EVENTS-072 binds an event to already written and readable at the moment that event can be observed on any channel, so a run killed between the two leaves a record with no event and never an event with no record; and it is what leaves a session abandoned by a crash or a force-quit holding its history complete to the last event raised. The history is **not** thereby the more complete of that session's two records, and no reader, no surface and no recovery path may treat it as one. This requirement formerly reasoned from a debounced state snapshot that could lag by its whole window; no save is deferred behind a timer, parked, or coalesced with a later one any more, so every save that was requested is durable and every save that was interrupted is absent whole (REQ-SESSION-067, REQ-SESSION-034). The two records therefore agree at the point the session was abandoned, and such a session — opened from its persisted record once its stale lock has been settled (REQ-SESSION-047, REQ-SESSION-196) — is restored from that record alone and is never completed from the history, which would be a second derivation of state the product does not have (REQ-SESSION-196). Two observables follow and MUST hold however the history is stored. First, an event is either wholly in the history or wholly absent from it: no reader may observe a partial, half-written or unparseable record that this product's own store produced. Second, the durability that makes an event readable MUST be reached before that event is observable anywhere, so no arrangement that defers several events' durability to one later step is permitted, whatever it costs. A recording step that fails is governed by REQ-EVENTS-088. Delivery to a live consumer MUST likewise be per event, never in accumulated batches.

**REQ-EVENTS-030** — Events raised concurrently MUST NOT interleave within a record. However many events a run raises at once, every record of the history MUST be one complete, independently parseable event, and no record may contain fragments of two. This binds the *ordering* as well as the content: the history holds concurrently raised events in the order they were raised, each whole.

**REQ-EVENTS-031** — Given a live consumer that goes away — it detaches, its channel closes, or delivery to it fails with an equivalent error — delivery to that consumer MUST stop permanently and silently and the run MUST continue to completion. A consumer that takes one event and detaches MUST end its own delivery only, leaving the run to finish and leaving the stored history complete.

**REQ-EVENTS-032** — Given an event that cannot be serialized, that one event MUST NOT be delivered or stored; a warning MUST be recorded stating the event type concerned and why serialization failed; delivery MUST stay open; and every subsequent event MUST still be recorded, so the history carries exactly one record fewer than the number of events the run raised. One unserializable event MUST NOT truncate the stream, MUST NOT suppress the terminal `result`, and MUST NOT change the run's outcome.

**REQ-EVENTS-033** — *Withdrawn.* There is no standard output whose destination could be re-resolved or found absent; the durable history has exactly one destination per session, and the failure to open it is governed by REQ-EVENTS-084.

**REQ-EVENTS-034** — Closing the event channel MUST make any outstanding event durable, MUST be idempotent, MUST cause any later event to be dropped rather than delivered or stored, and MUST NOT damage or shorten the durable history it was recording into.

**REQ-EVENTS-035** — The event channel and the session's store MUST be established before any part of run start-up can fail, so that even a run refused before it starts produces its terminal `result` (REQ-EVENTS-021), and MUST be closed unconditionally after the run. A store that cannot be opened at all is the one exception, and it is not a partial state: no session comes into existence and the run is refused before it starts (REQ-EVENTS-084).

### E. Event envelope and schema versioning

**REQ-EVENTS-036** — Every event, of every type, MUST carry the same envelope fields: `schema_version` (integer), `event` (string type discriminator), `timestamp` (string), and `session_id` (string, defaulting to the empty string).

**REQ-EVENTS-037** — `timestamp` MUST be an ISO-8601 instant in UTC including an explicit `+00:00` offset.

**REQ-EVENTS-038** — The event schema version MUST be `1`. It MUST be versioned independently of the on-disk session snapshot version; the two numbers may differ and MUST NOT be assumed to move together.

**REQ-EVENTS-039** — Backward compatibility: given a line carrying keys it does not know — extra envelope keys, extra payload keys, or both — a consumer built against schema version `1` MUST decode that line successfully, MUST populate every field it does know from the values that line carries, and MUST let neither the presence nor the content of an unknown key alter a known field or cause the line to be rejected. Adding a payload field, adding an envelope field, or adding an event type MUST leave `schema_version` at `1`. The version MUST be raised only for a change a version-1 consumer cannot absorb: removing or renaming a field or an event type, changing the type of an existing field, or changing the meaning of an existing value.

**REQ-EVENTS-040** — Field validation, including redaction, MUST be re-applied when a field is assigned after construction, so that no caller can produce an event carrying an unmasked secret by mutating an already-built event.

### F. Event catalog and per-type behavioral guarantees

**REQ-EVENTS-041** — The published event catalog MUST contain exactly these 23 types, discriminated by `event`: `session.start`, `session.end`, `iteration.start`, `iteration.end`, `child.spawn`, `child.transition`, `child.complete`, `tool.start`, `tool.finish`, `permission.decision`, `verifier.result`, `verifier.progress`, `transcript.row`, `usage.update`, `error`, `result`, `hook.start`, `hook.finish`, `checkpoint.created`, `checkpoint.restored`, `gate.decision`, `gate.repair`, `approval.requested`.

**REQ-EVENTS-042** — On `session.start`, the sandbox flag MUST report whether a sandbox is actually available and in force for this run, never merely what was requested; the flag MUST NOT read `true` when no sandbox actually came up. The permission mode reported MUST be the mode configured at start; any later downgrade is reported by subsequent permission events, not by revising this field.

**REQ-EVENTS-043** — `checkpoint.created` MUST report the number of changed paths as a count and MUST NOT enumerate the paths, so that an event line stays a fixed size no matter how many paths changed.

**REQ-EVENTS-044** — `checkpoint.restored` MUST report whether the restore happened, the safety checkpoint sequence (which MUST be read explicitly and MUST NOT be inferred from the restored flag, because a refused restore can still have produced one), a changed-path count of `0` when refused, and a blocking reason that is empty on success.

**REQ-EVENTS-045** — `gate.decision` MUST report the decision (`passed`, `gated`, or `exempt`), its reason, the unsatisfied checks, the advisory-only failures, and any model verdict that was overruled — the verdict MUST remain visible even when the gate decided against it.

**REQ-EVENTS-046** — `gate.repair` MUST report the action (`retry` or `escalate`), the 1-based attempt number, the configured maximum attempts, and the remaining attempts carried explicitly and clamped at zero or above. A gated iteration MUST produce exactly one repair event; `retry` and `escalate` are alternatives, and exactly one of them is chosen.

**REQ-EVENTS-047** — Each hook that executes MUST produce exactly one `hook.start` and one `hook.finish` carrying the same `hook_id`, and that `hook.finish` MUST report `skipped` false. Given a hook the trust gate of REQ-HOOKS-090 withheld — a workspace-scoped hook for which no stored approval matches the current workspace hook-set fingerprint, or a hook carrying a scope outside REQ-HOOKS-020's trusted set — exactly one event MUST be emitted for it: a `hook.finish` with `skipped` true, `skip_reason` exactly `untrusted_workspace` (one of the two values REQ-HOOKS-126 defines; the other, `plan_gate`, belongs to the separate case of REQ-ORCH-153 and is not this sentence's), `exit_code` null and `duration_ms` null, and `hook_name` carrying the hook's stable id rather than its configured display name (REQ-HOOKS-102). No `hook.start` bearing that `hook_id` may appear. A hook that produced no exit code MUST report `exit_code` as null; a numeric stand-in such as `0` or `-1` MUST NOT be substituted, even where the durable timeline records that state as `-1` (REQ-HOOKS-119).

**REQ-EVENTS-048** — `lifecycle_point` MUST carry exactly one of the seven hook events of REQ-HOOKS-001 — `pre_tool`, `post_tool`, `session_start`, `session_end`, `iteration_end`, `child_completed`, `verifier_finished` — and no other value. On every `hook.finish` whose `lifecycle_point` is not `pre_tool`, `blocked` MUST be false. Only a hook running at `pre_tool` may report `blocked` true, so a consumer may read `blocked` true as implying that lifecycle point.

**REQ-EVENTS-049** — `approval.requested` MUST reach every channel while the request is still outstanding, and therefore MUST precede the `permission.decision` carrying the same `request_id`. `resolver` MUST carry exactly one of the two values REQ-TOOLS-061 fixes, `brokered` or `headless`. `timeout_seconds` MUST be null exactly when `resolver` is `headless`, which never waits for a response, and MUST otherwise carry the wait in seconds (default `300.0`, REQ-EVENTS-167). `unattended_reason` MUST be the empty string on every request a person could still answer, and MUST be exactly `headless-policy` — the only defined value, spelled as REQ-TOOLS-061 spells it — on every request none can, which is exactly the requests whose `resolver` is `headless`. Expiry of the wait MUST NOT be reported on this event; it is reported on the paired `permission.decision` (REQ-EVENTS-051).

**REQ-EVENTS-050** — `approval.requested` MUST name the blocked agent by its canonical name when the resolver knows it, and MUST report an empty name rather than a guess when it does not. The persona field MUST always be populated truthfully; when the agent name is empty it is the only value a consumer can route on. For a top-level agent the reported name may be a persona label for which no `child.spawn` was ever emitted. A consumer that cannot match the two MUST conclude the agent is not a child rather than assume an event went missing.

**REQ-EVENTS-051** — A `permission.decision` that resolves a previously announced approval MUST carry the same request identifier as its `approval.requested`. A decision reached without ever asking a human MUST claim no request identifier. A request raised for one call MUST NOT be claimed by another. A fail-closed timeout MUST also be reported as a resolving `permission.decision`.

**REQ-EVENTS-052** — `transcript.row` MUST carry the transcript row verbatim in `row` and its position in `index`. A row that is produced incrementally MUST yield exactly two events for its `index` — one when the row first appears and one when it has reached its final form — and none for any state in between, so an answer produced token by token yields two events for its row rather than one per token. A row that is already in its final form when it first appears MUST yield exactly one event for its `index`: there is no separate settling state to announce, and a second event carrying an identical row would be indistinguishable from a genuine revision. One or two events per index is therefore the whole contract, and never more. The semantics are upsert by `index`, never append: a consumer MUST replace whatever it holds at that index rather than adding a row. Indices MUST be assigned contiguously from `0` in row order, so an index higher than the next one a consumer expects is evidence that events were lost. A consumer that detects such a gap MUST NOT invent a row to stand in for one it never received, and MUST NOT go on applying increments over a transcript it knows to be incomplete: it stops consuming increments and reconciles from a whole read of the session, which recovers the rows themselves rather than standing in for them (REQ-SESSION-161, REQ-MONITOR-226). The live stream is never rewound; what the stream dropped is recoverable *as events* only from the session's stored history (REQ-EVENTS-083), which remains the only complete record of them. Clearing the transcript restarts indices at `0`.

**REQ-EVENTS-053** — A `usage.update` MUST NOT be emitted when it would carry no figures, that is when `tokens` and `cost` are each either null or an empty object, so that a consumer never receives an empty payload it could mistake for a reset to zero. Every emitted `usage.update` carries run-to-date cumulative totals, so the most recent one supersedes all earlier ones (REQ-EVENTS-136). **The emission trigger is the completed provider request** (accepted amendment 2026-09-06, OQ-8): exactly one `usage.update` MUST be emitted when a completed provider request contributes new usage to those cumulative totals, and the trigger MUST NOT be widened to a smaller unit than a request or narrowed to the surviving requests alone. **Usage a failed or partial request reported MUST be counted**, because the provider reported it as spent and a retry does not unspend it; a request whose reported usage leaves the cumulative totals unchanged MUST raise no event, which is what keeps a provider that reports nothing from producing a stream of identical payloads. **Sampling is a separate cadence and MUST NOT drive this event**: REQ-MONITOR-166's token-history sampling is taken on its own interval and neither raises nor suppresses a `usage.update`. The terminal `session.end` of REQ-SESSION-094 carries the final cumulative totals whether or not the last request moved them, so a consumer that missed an update still ends holding the run's whole figure. The event's volume against REQ-EVENTS-091's cap is therefore bounded by the number of provider requests a run makes, which is what makes it bounded at all.

**REQ-EVENTS-054** — `verifier.progress` MUST be emitted for exactly three phases, spelled on the wire `started` (the suite began), `check_started`, and `check_finished`. `check` MUST name the check the event concerns on `check_started` and `check_finished`, and MUST be the empty string on `started`. `index` MUST be the 1-based position of the check for `check_started` and `check_finished`, and `0` for `started`. `total` MUST be the number of checks in the suite. `elapsed_s` MUST be the seconds since the suite began; `deadline_s` MUST be the suite's time budget in seconds, or null where none applies. `status` MUST be present only on `check_finished`, where it MUST carry exactly one of the five check statuses REQ-ORCH-123 fixes, spelled on the wire exactly as that requirement spells them, and MUST be the empty string on the other two phases. This document holds no copy of that vocabulary; what it fixes is that the field is present on `check_finished` alone.

**REQ-EVENTS-055** — `verifier.result` MUST carry the iteration number, `passed`, the per-check details in `checks`, and a `summary` that is a non-empty human-readable string. Each entry of `checks` MUST carry exactly these fields: `name` (the check name, `:subdir`-qualified as REQ-ORCH-122 qualifies it), `command` (masked per REQ-EVENTS-059), `status` (one of the five of REQ-ORCH-123), `severity` (`blocking` or `advisory`), `exit_code` (integer or null), `duration_ms` (float or null), `skip_reason` (empty unless `status` is `skipped`), and `output_path` (the path at which that check's full output was retained, recorded with the check under REQ-ORCH-123 and reachable in full after the run has ended; empty where none was written). `passed` MUST report whether the suite blocks completion under REQ-ORCH-116 — false exactly when at least one blocking check ended in a status that gates — and MUST NOT be read as an assertion that verification occurred: a suite that was skipped executed no check, blocks nothing, and therefore reports `passed` true with an empty `checks` list. The gate's own `exempt` decision on `gate.decision` is the authoritative signal that nothing was verified. The summary MUST identify which of exactly three outcomes occurred and MUST carry the information needed to act on it: that every check passed; that specific checks failed, in which case it MUST name each failed check; or that the suite was skipped, in which case it MUST state the reason. Its wording is the implementation's.

**REQ-EVENTS-056** — An issue recorded during a run (REQ-SESSION-135) MUST reach the wire as an `error` event only when its severity is `error`. Issues at `warning`, `info` or `debug` severity — the other three members of the severity vocabulary REQ-SESSION-134 fixes — MUST produce no event at all, so that a healthy run does not appear to be failing. An `error` event derived from a recorded issue MUST set `fatal` to false, MUST carry the issue's `kind` verbatim in `error_class`, and MUST carry in `detail` a locator naming the issue it was derived from, by which that issue can be found without searching. The `error_class` vocabulary is open-ended and owned by whichever domain records the issue (`hook_failure` and `hook_trust` from REQ-HOOKS-120 and REQ-HOOKS-086, `permission_denied` from REQ-TOOLS-081, and others); a consumer MUST treat an unfamiliar kind as opaque text rather than rejecting the event.

**This requirement is the single definition of the locator**, for this document and for every other; a requirement that needs one cites this identifier rather than restating it, as REQ-SESSION-135's `evidence_ref` and REQ-TOOLS-081's evidence reference do. A locator MUST have the form `<record kind>#<record id>`, a record-kind token and a record id joined by a single `#`, and both halves are a machine-readable contract.

**The record-kind tokens are fixed here and are exactly three**, lower snake case: `issues` for the session's issues record (REQ-SESSION-135), `permission_audit` for the session's permission audit (REQ-SESSION-137, REQ-TOOLS-078), and `tool_call_evidence` for the session's tool-call evidence record (REQ-SESSION-136). Each token names the record rather than the thing recorded: the tool-call evidence record's token is `tool_call_evidence` and deliberately not `tool_calls`, which is already the name of a count in the trajectory summary (REQ-EVENTS-136), and a token that reads like a document key in the same exported material invites exactly the confusion a machine-readable contract exists to prevent. A locator MUST NOT name any other record kind; admitting a fourth is an amendment to this requirement and to nothing else, because a token that drifts between the record emitting a reference and the record it points into breaks documents already in a user's hands. The `detail` of an `error` event is always an `issues` locator, since the event is derived from an issue.

**The record id is the identifier the named kind's own requirement gives its entries, and this requirement fixes none of them**: for `issues` it is the issue's `id`, the 12 hexadecimal characters REQ-SESSION-135 fixes; for `tool_call_evidence` it is the record's `call_id` (REQ-SESSION-136); for `permission_audit` it is the identifier REQ-TOOLS-079 gives a decision entry, and that requirement is the only place it may be fixed. Any such identifier MUST distinguish one entry of that kind from every other entry of that kind within the same session record, MUST NOT change once the entry is recorded, and MUST NOT be reused after the retention cap of REQ-SESSION-133 has displaced the entry that held it — otherwise a locator written earlier would silently resolve to a different entry than the one it was written for. **A locator MUST NOT name an entry that has no such identifier, and a record kind whose own requirement gives none of its entries one MUST NOT be named at all**, because such a locator resolves nowhere and states a reference the product cannot honour. A kind MAY hold entries of more than one shape and give an identifier to only some of them — the permission audit does, identifying the decision entries REQ-TOOLS-079 governs and not the mode-change entries of REQ-TOOLS-082 — and such a kind is nameable while the entries that have no identifier are not. That is this rule applied rather than an exception to it, and it is stated because the alternative reading makes `permission_audit` unnameable and REQ-TOOLS-081's evidence reference impossible to write.

**A locator resolves through an export as well as inside this application, where the named kind has an export.** For a kind that has one (`issues` and `permission_audit`, through REQ-SESSION-199), the identifier MUST be present in what that export produces, so that a reader holding one exported record can find the entry another exported record names, on a machine carrying none of this product's code and with nothing beyond a stock parser (REQ-EVENTS-166). For a kind that has none — `tool_call_evidence`, which must never gain one (REQ-TOOLS-190, REQ-SESSION-136) — the locator still names the entry unambiguously inside this application, and a reader of an export that carries such a locator must come back to the application to see what it names. That is the intended outcome and MUST NOT be treated as a defect to close, and it MUST NOT be closed by widening an export.

**No export may resolve a locator.** A locator MUST be carried as the opaque string it is: no export may inline, expand, dereference or replace it with the entry it names, and no export may be made self-contained by following one. This is not tidiness — the issues record is full of locators into the tool-call evidence record, which holds the arguments an agent passed exactly as they were passed, so an export that followed them would become the export that record must never have (REQ-TOOLS-190, REQ-SESSION-136, REQ-LIBRARY-176 for the same rule stated over a different record). A locator whose entry the retention cap has since displaced simply does not resolve; that is an ordinary outcome and MUST NOT be read as damage or as a reason to repair anything.

**REQ-EVENTS-057** — A completed tool call MUST produce a `tool.start` and a matching `tool.finish` sharing a call identifier, with the finish carrying status, duration in milliseconds, and an error description when the call failed. The `status` on `tool.finish` MUST carry exactly one of the three settled values of REQ-MONITOR-105 — `ok`, `failed`, or `blocked` — and never that vocabulary's `running`, which describes a call a `tool.finish` has by definition ended.

**REQ-EVENTS-058** — The `status` on `session.end` MUST carry exactly one value of the run status vocabulary of REQ-EVENTS-026, or the empty string where no status could be derived. A consumer MUST read the empty string as *unknown* and never as failure. This matches the reading REQ-HOOKS-075 gives the same field in a hook's `session_end` payload, so one word means the same thing on the wire and in a hook payload; a value outside the vocabulary MUST NOT be emitted here.

**REQ-EVENTS-176** — Recording a notice to a session's timeline under REQ-NOTIFY-268 MUST NOT by itself publish any event. A `warning` notice produces no event at all, consistent with REQ-EVENTS-056, and an `error` notice produces one only by way of the error-severity issue the underlying condition was recorded as (REQ-SESSION-135) — so one failure reaches the event stream exactly once, whether or not it was also shown to the user, and a consumer counting `error` events counts failures rather than renderings. The timeline entry remains the durable record of what the user was told, and REQ-EVENTS-072's ordering rule binds the issue-derived `error` event to its issue record, not to the notice.

### G. Redaction and payload bounding

**REQ-EVENTS-059** — Masking MUST be a property of the event definition rather than of any particular producer: for the fields below, no event delivered on the live channel, no event held in a stored history, and no event inside an exported history or an exported document may carry a value to which the masking of REQ-EVENTS-060 and REQ-EVENTS-063 has not been applied — whatever code produced the event, and whether the field was populated when the event was built or set on it afterwards. The masked fields MUST be: `arguments` on `tool.start`; `summary` on `permission.decision`; `command` on `hook.start`; `output` on `hook.finish`; `summary` on `approval.requested`; `command` within each entry of `checks` on `verifier.result`; and every string at any nesting depth within `row` on `transcript.row`. The mask literal MUST be exactly the three characters `***`, with nothing appended to it.

**REQ-EVENTS-060** — Argument masking MUST render every argument value as a string, since `arguments` is a string-to-string map on the wire. A value whose key names a credential MUST be replaced in its entirety by the mask literal, leaving no fragment of the original value. Key matching MUST be performed on a normalized form of the key in which every `_`, `-` and camel-case boundary becomes a single space and every letter is lower-cased, so that `apiKey`, `api_key`, `API-KEY` and `api key` all match alike; a key whose normalized form contains any of `api key`, `token`, `secret`, `password`, `credentials`, or `auth` MUST count as naming a credential. That list of six is closed: masking is deterministic and testable, and a producer MUST NOT extend or narrow it, so two builds mask the same argument identically. A credential-shaped substring appearing inside the text of a value whose key does not name a credential MUST also be replaced by the mask literal, with the surrounding text left readable. Credential-shaped means exactly these four forms and no others, each recognized by its shape rather than by any measure of the value's randomness: an assignment inside the text — `key=value`, `key: value`, or `key value` where the key is quoted or preceded by a flag marker — whose key normalizes to one of the six fragments above, in which the value alone is masked; an `Authorization` header value or a bearer credential, in which everything after the scheme word is masked; the userinfo password of a URL of the form `scheme://user:password@host`, in which the password alone is masked; and the body of a PEM-delimited private key block, in which everything between the delimiters is masked. No entropy or length heuristic may be used, so an ordinary hash, identifier or path is never masked by accident.

**REQ-EVENTS-061** — Each rendered tool-argument value MUST be clipped to 240 characters plus a trailing single-character ellipsis, so a clipped value is 241 characters long and is distinguishable from an untruncated one. Ordinary short values MUST remain fully readable.

**REQ-EVENTS-062** — Masking MUST be idempotent: re-applying it to already-masked content MUST change nothing, so validation on construction, on assignment, and on re-parse all agree.

**REQ-EVENTS-063** — Masking MUST be applied to a transcript row string before that string is clipped, never after, so that no clipped string can retain a fragment of a value masking would have replaced. Clipping MUST be to 16,000 characters followed by a single `…`, making a clipped string 16,001 characters and distinguishable from one that fitted; the limit counts characters, not bytes. Values inside a row that are not strings MUST pass through unchanged.

### H. Serialization and parsing

**REQ-EVENTS-064** — An event MUST serialize to compact JSON with no spaces after separators, with object keys sorted, and with non-ASCII characters escaped (so that the output survives non-UTF-8 consoles and so that line separators embedded in text cannot break a line). Two equal events MUST serialize to byte-identical lines, so that a consumer comparing two runs sees stable output.

**REQ-EVENTS-065** — A serialized event MUST occupy exactly one line: embedded newlines in payload text MUST be escaped, and a line break that somehow survives serialization MUST raise rather than be emitted.

**REQ-EVENTS-066** — Non-string mapping keys inside a payload MUST be converted to strings before serialization, so that a payload containing, for example, integer keys cannot break serialization mid-stream.

**REQ-EVENTS-067** — Round-trip fidelity: for every event type, serializing an event, decoding the JSON, and re-validating it MUST yield an equal event of the same type, field for field.

**REQ-EVENTS-068** — Strict parsing MUST reject a line whose `event` value lies outside the known catalog, raising a validation error instead of inferring a type. A consumer encountering such a line SHOULD skip it.

### I. Emission sites, ordering, and delivery guarantees

**REQ-EVENTS-069** — Each run MUST publish its lifecycle pair exactly once: one `session.start` and one `session.end`, both to every attached live consumer and in the session's stored history. Counting either type across the events of a single run MUST give exactly one, and no duplicate pair describing that run may be observed on either channel. A stored history covering several runs of one session (REQ-EVENTS-097) MUST therefore contain as many pairs as it contains runs.

**REQ-EVENTS-070** — For a run that started, the terminal `session.end` and `result` MUST be delivered through the normal event delivery path, while delivery is still active, so that an attached consumer observes how the run ended — exactly once, never zero times and never twice. Only a run that never started (and therefore has no session to address) may deliver its terminal result by the direct path; the two paths are mutually exclusive.

**REQ-EVENTS-071** — For a run that started, every way it can end — normal completion, failure, and abrupt termination alike — MUST end it with its `session.end` followed by its terminal `result`, on the live channel and in the stored history alike. (A run that never started emits the terminal `result` alone, per REQ-EVENTS-021 and REQ-EVENTS-024.) After that `result`, no further event bearing that session id may be observed anywhere: the stored history gains no further record and no consumer receives another event. A later run MUST NOT be refused on the grounds that an earlier run used the same session id, MUST observe only the events it raised itself, and MUST NOT have any of its events delivered to a consumer that attached to the earlier run. Where the terminal status cannot be determined, the terminal pair MUST still be emitted, carrying the status REQ-EVENTS-027 assigns to a state that is not terminal.

**REQ-EVENTS-072** — Where an event mirrors a durable record, that record MUST already be written and readable by the time the event can be observed on any channel. A consumer holding such an event MUST therefore find the matching record already written, and a run killed between the two MUST leave a record with no event, never an event with no record. The pairs are exactly these, named by the record each one binds to and by the requirement that owns that record, and no other catalog type has a durable counterpart this rule binds: `tool.start` and `tool.finish` against the session's tool-call evidence record (REQ-SESSION-136); `permission.decision` against the session's permission audit record (REQ-TOOLS-078, REQ-SESSION-137); `error` against the issue record its `detail` locates (REQ-EVENTS-056, REQ-SESSION-135); `gate.decision` and `gate.repair` against the `completion_gate_decision`, `repair_attempt_scheduled` and `repair_escalation` timeline entries they are bridged from (REQ-SESSION-134); `checkpoint.created` and `checkpoint.restored` against the `checkpoint_created` and `checkpoint_restored` timeline entries (REQ-GIT-048, REQ-GIT-062); and `hook.finish` against the `hook_run` timeline entry (REQ-HOOKS-119) — `hook.start` has no counterpart, because the invocation record is written only once the invocation has completed. Where the store can make the durable record and the event one indivisible step, it MUST, because that is what puts the ordering beyond the reach of a defect; where it cannot, the ordering above is still required and is still what a consumer may rely on.

**REQ-EVENTS-073** — Malformed source data behind a derived event MUST NOT abort the iteration it came from, nor the run. Exactly one of two things MUST happen, and which one MUST be decided by whether the event's identity survives. The event MUST be emitted with the malformed portion coerced where the catalog's declared type can be reached by a total conversion: a scalar of the wrong type rendered as its string form for a declared string field; a value absent, null, or of an irreconcilable type replaced by that field's declared default; a number truncated toward zero for a declared integer field; a mapping key that is not a string converted per REQ-EVENTS-066. No event MUST be emitted, and a warning MUST be recorded instead, where the event cannot be identified or rendered at all: the event type is missing or outside the catalog of REQ-EVENTS-041; the payload is not a mapping; a value has no textual form (a self-referential structure among them); or a string still carries a record separator after escaping, which REQ-EVENTS-065 forbids emitting. Either way the iteration MUST continue, its `iteration.end` MUST still be emitted, and the run's terminal status MUST be what it would have been had the source data been well formed.

**REQ-EVENTS-074** — An exception raised by a consumer MUST NOT fail the run: the exception MUST be swallowed into a logged warning. A faulty consumer may lose events for itself; the run's progress and outcome are unaffected.

**REQ-EVENTS-075** — Event delivery MUST be addressed per session: events for one session MUST NEVER be delivered to a consumer registered for another session, and there MUST be no fallback across sessions. Registering delivery for an empty session id MUST be rejected as invalid. Publishing when no consumer is registered MUST do nothing and MUST NOT raise.

**REQ-EVENTS-076** — Within a run the following orderings MUST hold, judged alike by delivery order on the live channel and by position in the stored history: `session.start` precedes every other event of that run; `iteration.start` precedes its matching `iteration.end`; `child.spawn` precedes every other event naming that child, `child.complete` included; `tool.start` precedes the `tool.finish` sharing its `call_id`; `session.end` precedes `result`. Within a single iteration in which each of the following occurs once, their relative order MUST be `hook.start`, `hook.finish`, `checkpoint.created`, `approval.requested`, `permission.decision`, `gate.decision`, `gate.repair`, and none of them may be emitted more than once for the same occurrence.

**REQ-EVENTS-077** — `child.spawn` MUST be announced exactly once per child even when the spawn is reported through more than one internal path. `child.transition` MUST carry a real prior state, MUST suppress a repeated notification of the same state, and a child first seen partway through its life MUST still get a `child.spawn` emitted ahead of any other event referring to it.

**REQ-EVENTS-078** — Consumer-delivery failures MUST be isolated from the publisher and other consumers. A durable-store recording failure MUST follow REQ-EVENTS-088: stop admission for affected runs and initiate controlled cancellation. Failed persistence MUST publish no authoritative event. This distinction applies at every emission point, including hooks and iterations.

### J. Durable per-session event store (write side)

**REQ-EVENTS-079** — *Withdrawn.* The durable history is a record only this application reads, and this document no longer fixes a path, a file name, or an enclosing directory for it; where a session's records are kept is settled by the storage decision and by domain 07, not here. Nothing behavioural is withdrawn with the path. That a session has exactly one history, that a resumed run adds to that same history rather than starting a second one, and that a history belongs to exactly one workspace's sessions are carried by REQ-EVENTS-097, REQ-EVENTS-085 and REQ-EVENTS-131; that a truncation record exists only once a trim has dropped events is REQ-EVENTS-087's and REQ-EVENTS-092's. The line-delimited form the path named is **not** withdrawn — it moves whole to the export, where REQ-EVENTS-090 fixes its record terminator, REQ-EVENTS-172 produces it, and REQ-EVENTS-166 states what it must guarantee to a reader who has none of this product's code.

**REQ-EVENTS-080** — A stored event MUST hold, verbatim, the serialized form the live stream would have emitted for that same event — same field names, same schema version, same key ordering, byte for byte — so that a consumer written for the live stream reads a stored event unchanged and vice versa. That form is what the history stores and what an export emits (REQ-EVENTS-104, REQ-EVENTS-134, REQ-EVENTS-172); any value derived from it for querying or presentation is a copy and MUST NOT be read back in place of it, nor written into an export. Where a derived value and the stored form disagree, the stored form is the record (REQ-EVENTS-085).

**REQ-EVENTS-081** — Every run MUST leave a stored history, with no exception and no excluded path: the guarantee spans every run that goes through the shared run lifecycle (REQ-SESSION-089, REQ-SESSION-174), whatever started it and whatever is watching it. The runs it spans are the ways a run can be started, which REQ-SESSION-080 closes: a run the user drives from the Workspace view, a run continuing in the background while the user is elsewhere, a run of a session opened in a second window of the same instance, a run launched from the requirement board, and a run of the product's own machinery such as worktree integration, alike. This enumeration formerly also named a run driven by a programmatic embedding of the engine. No such run exists — there is no library, package, plugin host or endpoint through which code the user did not launch may start a run, drive one, or subscribe to one (REQ-EVENTS-178) — so that case is struck from the list. **The guarantee is not narrowed by the correction:** it spans every run through the shared run lifecycle, whether or not this document happens to name the way that run was started, and a way of starting a run added later is inside it from the moment it exists rather than on being listed here. Given the same task, any two of those MUST leave the same kinds of durable evidence record for their sessions, and their stored histories MUST match one another under the field-by-field comparison of REQ-EVENTS-015. Whether a live consumer is attached decides only where events are additionally forwarded, never whether they are recorded. A run refused before it starts is not an exception to this rule but falls outside it: no session comes into existence for such a run, so there is no history it failed to leave (REQ-EVENTS-021, REQ-EVENTS-084).

**REQ-EVENTS-082** — Recording MUST be independent of consumption. Where a consumer is attached and fails on every event it receives, the session's stored history MUST still contain that run's complete event sequence — the same events, in the same order, that a fault-free consumer would have received — and the run MUST still reach its terminal `result` carrying the status that outcome maps to (REQ-EVENTS-027).

**REQ-EVENTS-083** — A session's history MUST exist from the start of a run (REQ-EVENTS-087) and MUST contain every event raised for that session, in emission order, up to and including that run's terminal `result`. Once that `result` has been recorded the history MUST gain no further record: any event bearing that session id raised afterwards MUST leave the history exactly as it stands, unless a later run resumes the same session, which adds its own events per REQ-EVENTS-097.

**REQ-EVENTS-084** — Given a session's durable store that cannot be opened, the session MUST NOT start. There is no state in which a run has somewhere to record itself but not somewhere to be recorded, so there is nothing left to degrade to: the run MUST be refused before it starts on the terms of REQ-EVENTS-021 — no `session.start` is emitted, the entire event sequence is exactly one `result` with status `error`, and no session is left behind. The reason reported to the user (REQ-EVENTS-019) MUST state that the session's durable store could not be opened, and MUST carry the store's own reported reason unaltered rather than a generic failure, so the user can act on the actual cause. Running while unable to persist anything and reporting that as a warning is not permitted: it produces work whose record cannot be recovered, which is a worse outcome for the user than not starting. This requirement governs opening the store only; a write that fails *during* a run is REQ-EVENTS-088's and is unchanged. A store that reports itself opened and then fails on the first operation issued against it is neither of those and is REQ-EVENTS-179's, which resolves that case into this one: such a store counts as a store that could not be opened and is refused on exactly the terms above.

**REQ-EVENTS-179** — A store that reports itself open is not yet known to be usable, and the product MUST establish that it is before the run starts. Between REQ-EVENTS-084, which governs a store that cannot be opened, and REQ-EVENTS-088, which governs a recording step that fails once a run is under way, lies a third condition that belongs to neither as they stand: the store opens, reports the open a success, reports itself writable, and then fails on the first operation issued against it. **Nothing the store reports about itself is sufficient evidence that it works.** A store may report that it opened, report that it is not read-only, return every setting the product asked it to apply read back exactly as applied, and create whatever further files it keeps alongside itself at their expected sizes, and still fail on the next operation; and it may fail on that operation every time while everything issued after it succeeds. The check MUST therefore be an operation that actually reads and writes the store's own contents — a write made and then undone, so the store is left exactly as it was found and no record is added to any session — and MUST NOT be a reading back of what the store says about its state. It belongs where REQ-EVENTS-035 puts establishing the store, before any part of run start-up can fail, and MUST be made before REQ-EVENTS-087 brings the session's history into existence, so that no history is created in a store that cannot hold it. **Where that operation fails, the store counts as a store that could not be opened.** REQ-EVENTS-084 then governs unaltered: the run is refused before it starts on REQ-EVENTS-021's terms, no `session.start` is emitted, no session is left behind, and the reason reported to the user carries the store's own reported reason unaltered rather than a generic failure (REQ-SESSION-089). **The failure MUST NOT be absorbed.** It MUST NOT be retried into success, swallowed, or reduced to a warning, and a store that fails this check and then works MUST still refuse the run: exactly one attempt is made and its outcome decides. Retrying past this failure yields a product that runs on storage it has already been told is unsound, with no later moment at which it can say so, which is the silent degradation REQ-EVENTS-084 exists to forbid — and it is the likelier mistake here, because the failure can be perfectly reproducible at the first operation and absent from every operation after it. **Both neighbouring requirements keep their scope.** REQ-EVENTS-084 continues to govern a store that fails to open; REQ-EVENTS-088 continues to govern a recording failure once a run is under way, and this requirement does not reach it, because when this check is made no run has started, no event has been recorded, and there is no history for a reader to find incomplete.

**REQ-EVENTS-085** — A stored session's identity MUST be resolved in this order: the id supplied for it with leading and trailing whitespace removed, whenever that leaves a non-empty value; failing that, the identity the session itself is recorded under; failing both, the empty string. That resolved identity is the one reported for the session in a listing (REQ-EVENTS-129) and the one an export falls back to (REQ-EVENTS-139), and it MUST NOT change because an individual recorded event carries a different `session_id`. The stored form of a recorded event MUST NOT be altered to impose it (REQ-EVENTS-080, REQ-EVENTS-095).

**REQ-EVENTS-086** — An absent store cap — and only an absent cap — MUST mean unbounded. A cap of zero or a negative cap MUST be rejected with a clear error stating that a numeric cap must be greater than zero and that unbounded is requested by supplying no cap at all. A configured `0` asks for an empty store and therefore MUST NOT be reinterpreted as "no limit".

**REQ-EVENTS-087** — Initializing a store MUST, before the first event lands, bring the session's history into existence as an open and empty history, so that a session whose run recorded nothing stays distinguishable from a session that has no history at all (REQ-EVENTS-125), and so that every reading surface sees the session's full set of evidence records from that moment on rather than watching them appear one by one. Initialization failure MUST be reported as a failure rather than raising, and where the store cannot be opened at all the session does not start (REQ-EVENTS-084). No truncation record may exist for a session until a trim has actually dropped events.

**REQ-EVENTS-088** — Recording failures MUST return a failure outcome with a diagnostic. A serialization failure MUST drop that one event with a warning and let later events land. A durable recording step that fails or whose durability cannot be confirmed MUST mark the affected store failed for the current execution, stop admission of affected work and initiate controlled cancellation of its runs. Further authoritative writes and publication for those runs MUST stop. The last durable transcript and whole-event boundary MUST remain intact. Exactly one failure notification per affected run MUST identify the last durable event ordinal, explain the failure, and provide a recovery action. This notification and subsequent cancellation status MUST be explicitly labeled in-memory and shown outside the authoritative transcript. Terminal persistence failure MUST leave completion unconfirmed; caller outcomes MUST disclose that uncertainty, and success notifications MUST be suppressed. Cleanup MUST detach bindings and attempt lock release under REQ-SESSION-094. Restoring writable storage and reopening the saved session MUST establish recovery before further execution is admitted. Pre-start store failures remain governed by REQ-EVENTS-179.

**REQ-EVENTS-089** — An event whose serialized form contains a carriage return or line feed MUST be refused rather than recorded, because such a character would split one record across two lines in any line-delimited rendering of the history — the export of REQ-EVENTS-090 and REQ-EVENTS-172 above all — and corrupt both.

**REQ-EVENTS-090** — In any line-delimited rendering of a history, a single line feed MUST be the record terminator on every platform, for every event and however the history was assembled, so that the same history exported on two platforms is byte-identical and equals the bytes the wire carried. This is the export's format (REQ-EVENTS-172, REQ-EVENTS-166); it is not a property of how the history is stored, and a store that does not separate its records by newlines does not violate it.

**REQ-EVENTS-091** — The cap MUST be the value of the configuration key `runtime.event_retention_per_session`, which REQ-CONFIG-473 registers; this document fixes the behavior the cap governs and not the key's registration, its validation, or its default, all of which are that requirement's. What the cap bounds is **how many events one session's history keeps**. A cap of `0` means the history is never trimmed: no headroom applies, no trim runs however long the history grows, and the truncation record carries the cap as null (REQ-EVENTS-092). A negative value is rejected by configuration validation rather than clamped, so it never reaches a store. For a positive cap, the history MAY hold up to `cap + (cap ÷ 8, rounded down)` events; recording an event that leaves the history holding more than that figure MUST be followed by a trim before any further event is recorded. A cap below 8 therefore trims at exactly the cap, and a cap set to the default REQ-CONFIG-473 registers trims once the history exceeds 22,500 events. A trim MUST keep the newest `cap` events and discard the rest, and MUST count from the history's current contents rather than from a figure carried over from earlier appends. A trim MUST be observable only as a single step: no reader may observe a history part-way through one, and an interruption MUST leave either the whole untrimmed history or the whole trimmed history and never something between them. A trim that did not complete — including one that ran out of room — MUST leave the previous contents in force, MUST NOT be reflected in the truncation record, and MUST record a warning; the history then exceeds its cap, which is a bounded and visible cost, rather than losing events to a failed trim.

**REQ-EVENTS-092** — When a trim drops events, the session MUST carry a truncation record holding exactly four facts: whether the history is truncated, the cumulative number of dropped events, the cap in force (or null for unbounded), and the ISO-8601 UTC instant of the last trim. It MUST be made durable in the same indivisible step as the trim that produced it, so it can never report a trim that did not happen or omit one that did. A session with no truncation record — including a session with no stored history at all — MUST read as not truncated with zero drops; that absence is a definite answer and MUST NOT be reported as an unknown figure or raised as a failure, which is what lets a listing, a history surface and an export state `false` and `0` for an intact history rather than leaving the field blank. The truncation record MUST NOT be held as an event of the history, so the invariant that every record of a history is a wire event continues to hold, and it MUST NOT appear among the events any export emits; the exported document carries the same two figures under its own key names instead (REQ-EVENTS-140).

**REQ-EVENTS-093** — *Withdrawn.* It fixed three interchangeable filesystem paths — a session directory, a history file, a marker file — by which store metadata could be located, and none of the three exists. A session's truncation figures are read from that session's own record, and the one behavioural guarantee this requirement carried, that a session with no store at all reports no truncation rather than failing, has been moved into REQ-EVENTS-092 and is stated there in full.

**REQ-EVENTS-094** — Dropped-event counts MUST accumulate over the life of one session id and MUST NEVER be reset. A session resumed later — within the launch of the application that first ran it or in any later launch — MUST report the session's cumulative loss, because reporting a lower figure would understate how much history an export is missing. The count MUST NOT depend on a separate record being found at the time a store is opened: a resumed session reporting zero because such a record went missing is exactly the failure this requirement exists to prevent. The figure is read after the fact by the listing (REQ-EVENTS-129), by the history surface (REQ-EVENTS-168), and by the export document and its disclosure (REQ-EVENTS-140, REQ-EVENTS-173); no reader compares it against a figure it read earlier itself.

**REQ-EVENTS-095** — The store MUST NOT apply a second masking pass. What is stored is exactly what the schema already masked: a credential can reach the stored history only if it was present on the wire.

**REQ-EVENTS-096** — *Withdrawn.* The store cap is a registered configuration key, `runtime.event_retention_per_session`, rather than a property of how a store is attached; the behavior the cap governs is carried by REQ-EVENTS-091, and the key's registration, its default, and its value space by REQ-CONFIG-473.

**REQ-EVENTS-097** — A resumed session MUST add its events to the same history. A session run twice therefore holds both runs' events in one history, in one continuous emission order, with `session.start` … `result` appearing twice.

**REQ-EVENTS-098** — Writes to one session's history MUST be serialized so that no two events can interleave within a record and a trim cannot race the recording of an event. A session's history MUST have at most one writer, and the right to write it is exactly the right to hold that session's lock (REQ-SESSION-056). Anything that does not hold the lock MUST NOT write that session's history, and a run that cannot take the session's lock does not start (REQ-SESSION-083), so nothing ever records beside the holder and racing trims and racing truncation records cannot arise. Because the application runs as a single instance, the writer is always this application's own run host, and a session left open by a launch that has ended is settled by the stale-lock path (REQ-SESSION-047) before any run writes to that session again; the single-writer rule therefore defends a state that should not arise rather than arbitrating between rival processes. Serialization is required even where the store's own guarantees already make two writers unable to corrupt one another, because what is at stake is emission **order** (REQ-EVENTS-076) as much as record integrity, and no store supplies that on its own. Reading is unrestricted and needs no lock: a session's history MAY be read while the run that owns it is still writing it — by the listing summary of REQ-EVENTS-126, by the history surface of REQ-EVENTS-168, and by an export — because reading never writes (REQ-EVENTS-100).

**Three properties of the store follow from unrestricted reading, and each is a conformance property of the store rather than a tuning choice.** They are stated as three because the first two are absolute and the third deliberately is not. *Does not block* and *costs nothing* are different claims; only the first is required of a store, and a suite that tests them alike rejects every store there could be, a correct one included.

**(a) Neither side may stop the other, and blocking is what is prohibited.** No reader — whatever it reads, however much of a history it reads, and however long it takes — may prevent a write to that session's history, hold one off indefinitely, or cause one to fail; and no writer may prevent a read, hold one off indefinitely, or cause one to fail. Where a store makes either side wait for the other, that wait MUST be bounded and MUST end in the operation being carried out rather than abandoned or refused. **A store in which one side can block, starve or fail the other does not satisfy this requirement.**

**(b) A reader MUST come to observe what the writer recorded.** What the writer has durably recorded MUST become observable to a reader that reads the history again. How soon is not fixed here, and a reader MAY observe a record later than the writer made it — but *later* MUST NOT mean *not at all*. **A store in which a reader can read one session's history repeatedly and never observe events that session's writer durably recorded does not satisfy this requirement, and fails it no less for reporting nothing.** A write that reports success and a read that reports success while the two disagree about what the history holds is exactly what this clause exists to catch: nothing on either side raises anything a user, a surface or a conformance test would otherwise notice, and events the run recorded are simply absent from what anyone can read.

**(c) Either side MAY cost the other measurable time, and that is not a violation.** Concurrent reading that measurably raises the writer's latency has not blocked the writer. No store can offer concurrent access at no scheduling cost, so an implementation MUST NOT be judged against a claim that a writer's timings are unaffected by a concurrent reader, and a conformance test asserting that rejects every store there could be. What this requirement forbids is (a) and (b); what bounds the cost is not this requirement's to fix and is fixed where publication latency is fixed (REQ-MONITOR-218, REQ-MONITOR-222).

### K. Reading a stored session (replay primitives)

**REQ-EVENTS-099** — Reading MUST be streaming and lazy: a reader MUST pull no further than the caller has consumed, and reading a long history MUST NOT require holding the whole history in memory. One reader MUST serve two kinds of source alike — a session's stored history, and any sequence of lines the caller supplies — so that a stored history, an exported history (REQ-EVENTS-172), a captured stream, or any other line source is read by the same code under the same rules. Reading an export with the same reader that reads the store is what keeps the export a first-class record rather than a write-only formality.

**REQ-EVENTS-100** — Reading MUST be read-only: it MUST NEVER rewrite, compact, or repair what it reads. Repeated reads of a damaged source MUST leave it byte-for-byte as it was found.

**REQ-EVENTS-101** — A session with no stored history MUST read as an empty session; this is a successful outcome and MUST NOT be an error, since a session may have emitted nothing yet, or may be examined in the window before any event has landed. A source that cannot be read at all (for example, an exported file the reader lacks permission to open) MUST log a warning and read as empty.

**REQ-EVENTS-102** — Reading MUST be forward compatible. When a stored event carries a type that is absent from this build's catalog, the reader MUST still return it, preserving the raw payload untouched and setting a flag that marks the type as unrecognized. It MUST NEVER be dropped and MUST NEVER raise. The set of recognized types MUST be derived from the current event catalog rather than written out separately, so that adding a type to the catalog immediately makes it recognized.

**REQ-EVENTS-103** — Reading a stored record MUST preserve its decoded payload exactly as the source holds it, and MUST make available the record's 1-based position in the source read and whether its `event` value belongs to the catalog of REQ-EVENTS-041. An envelope field that is missing, or whose JSON type is not the type REQ-EVENTS-036 declares, MUST NOT fail the read and MUST NOT disturb any other field: `event`, `session_id` and `timestamp` read as the empty string unless the record supplies a JSON string, and `schema_version` and `iteration` read as having no value unless the record supplies a JSON number — no other JSON type may stand in for one. A record whose `event` therefore reads as empty counts as damaged rather than unrecognized (REQ-EVENTS-106).

**REQ-EVENTS-104** — A stored record MUST yield a line byte-identical to the one the live stream would have written for that event, taken from what the record itself holds and never rebuilt by serializing a decoded copy, so that a type outside this build's catalog reproduces exactly as well. Rebuilding is forbidden because byte-identity would then be a property of a serializer confronted with payload shapes it has never seen, rather than a property of what was stored.

**REQ-EVENTS-105** — Tolerant reading MUST be what a caller gets unless strict validation is asked for explicitly. No history-reading surface may fail, and no record may be withheld from its output, because a stored record carries an `event` value outside the catalog of REQ-EVENTS-041 (REQ-EVENTS-102, REQ-EVENTS-159). Where strict validation is requested instead, the read MUST stop at the first such record and report it as a validation failure, consistent with the strict-parsing rule of REQ-EVENTS-068: records preceding it are still produced, records following it are not.

**REQ-EVENTS-106** — A damaged line met while reading a source through MUST be skipped rather than ending the read, and MUST produce exactly one warning. Each warning MUST carry the line's 1-based position in the source, a reason, and the first 200 characters of the offending line. Every warning MUST be logged, and MUST be presented wherever this specification requires it to be surfaced (REQ-EVENTS-170). The rendered one-line form MUST be `line {n}: {reason}`; the excerpt is carried by the warning but is not part of that rendering. The reasons MUST distinguish four cases: bytes that cannot be decoded as UTF-8, naming the decoding failure — since a line this product produced carries only ASCII (REQ-EVENTS-064), undecodable bytes mean the source was damaged after it was produced, and they MUST be skipped a line at a time rather than ending the read; a line that is not valid JSON, quoting the decoder's own message; a line that is valid JSON but not an object; and an object carrying no non-empty string `event` value, which counts as damaged rather than as an unrecognized type, since no type can be determined at all. Every event read before a damaged line MUST still be returned, and every event after it MUST still be read. All four cases MUST remain implemented in full, because the reader also reads line sequences the caller supplies (REQ-EVENTS-099) — an exported history copied between machines, edited by hand, or truncated in transit among them. What they no longer describe is this product's own store: a history this product wrote holds no partial record (REQ-EVENTS-029, REQ-EVENTS-088), so a stored history cannot present a damaged record and a reader of one raises no warning of this kind.

**REQ-EVENTS-107** — Blank and whitespace-only lines MUST be skipped silently with no warning.

### L. Withdrawn resumable following of a growing store

A session is either owned by this application's run host and live, or it is not running and exists as a
persisted record. No session executes anywhere this application can only watch. A live session
therefore reaches every surface over the application's own channels (REQ-EVENTS-164, REQ-EVENTS-165),
and a session that is not live is opened from its persisted record and may be continued
(REQ-SESSION-196); a session left behind by a crash or a force-quit becomes an ordinary persisted
session once its stale lock has been settled (REQ-SESSION-047). A resumable byte-offset read existed so
that a run which could not be talked to could be watched through the file it was writing, and there is
no such run.

The stored history itself is unaffected. It is still recorded one durable record per event as that
event is raised (REQ-EVENTS-029), each record still holding byte-for-byte what the wire carried
(REQ-EVENTS-080), and it is still read — whole, and by a read that never writes — by the replay
primitives of Section K, the listing of Section N, the export of Section O, and the surfaces of
Section P. What is withdrawn is only the protocol for reading it a piece at a time while it grows.

**REQ-EVENTS-108** — *Withdrawn.* No session executes where this application can only watch it, so nothing reads a history a piece at a time while it grows. Every remaining reader takes the streaming, lazy whole-history read of REQ-EVENTS-099, which accepts a session's stored history or any sequence of lines: the listing summary of REQ-EVENTS-126, the history surface of REQ-EVENTS-168, an export (REQ-EVENTS-132, REQ-EVENTS-172), and the reattach of REQ-SESSION-196. No reader carries a position from one read into a later one.

**REQ-EVENTS-109** — *Withdrawn.* Part of the resumable read withdrawn by REQ-EVENTS-108; there is no offset to return unchanged.

**REQ-EVENTS-110** — *Withdrawn.* The rule held an incomplete final line without warning so that a follower would collect it whole on its next read, and there is no next read to hold it for. It has since lost its subject as well as its consumer: an event is now recorded whole or not at all (REQ-EVENTS-029, REQ-EVENTS-088), so a stored history has no incomplete final record to hold. An incomplete final line remains possible in a line source a caller supplies — an exported history damaged in transit among them — and is read as a damaged line and skipped with a warning under REQ-EVENTS-106, which also holds the rule that every event before it is still returned.

**REQ-EVENTS-111** — *Withdrawn.* The restart flag, and the comparison of the truncation record's dropped-event count against the same reader's previous read, defended a reader that carried a byte offset across reads into a history a trim had shortened from the front. No reader carries one (REQ-EVENTS-108). The truncation record is *not* withdrawn with it, and the consumers were enumerated before the withdrawal rather than assumed away: REQ-EVENTS-092 still requires the four facts to be recorded on every trim that drops events, REQ-EVENTS-094 still accumulates the dropped-event count over the life of a session id, and that count is still reported by the listing (REQ-EVENTS-129), presented beside the event count on the history surface (REQ-EVENTS-168), and carried into the export document and its disclosure (REQ-EVENTS-140, REQ-EVENTS-173), with domain 07 holding three more (REQ-SESSION-144, REQ-SESSION-153, REQ-SESSION-188). What did go with the follower is the marker's *second* job, trim detection for a reader holding a position. The indivisibility a trim must show a reader is likewise untouched and stays required by REQ-EVENTS-091; only the file the marker used to occupy, and the three-way path resolution REQ-EVENTS-093 fixed for it, are gone.

**REQ-EVENTS-112** — *Withdrawn.* Part of the resumable read withdrawn by REQ-EVENTS-108. A session with no stored history reads as an empty session, which is a successful outcome, under REQ-EVENTS-101.

**REQ-EVENTS-113** — *Withdrawn.* Part of the resumable read withdrawn by REQ-EVENTS-108; there is no offset to advance past a damaged line, and no read that could meet the same line twice. Skipping a damaged line with exactly one warning and reading on is REQ-EVENTS-106's.

**REQ-EVENTS-114** — *Withdrawn.* Warnings were numbered from the start of a read to avoid the full scan the resumable read existed to avoid. With no resumable read, REQ-EVENTS-106's numbering — the line's 1-based position in the source being read — has no exception.

**REQ-EVENTS-115** — *Withdrawn.* Bytes that cannot be decoded are a property of the file, not of how it is read, and the rule outlives the resumable read that carried it: it is now the first of the four damage cases REQ-EVENTS-106 fixes, which owns every read-damage warning, and it is stated there in full.

**REQ-EVENTS-116** — *Withdrawn.* Exactly-once, in-order delivery across successive reads was the resumable read's obligation. A single read of a stored history returns every event it holds, once and in emission order, under REQ-EVENTS-083 and REQ-EVENTS-099; exactly-once, in-order delivery of a live session's events is the live channel's obligation under REQ-EVENTS-165.

### M. Query, filtering, and replay semantics

**REQ-EVENTS-117** — A query MUST support four independent filter axes: event types, iteration numbers, a lower time bound, and an upper time bound. An axis left unset MUST impose no restriction. Axes that are set MUST be combined with AND. Both time bounds MUST be inclusive. A query MUST be able to report whether it filters anything at all. Results MUST always be returned in original emission order — the order the history holds them in — and a filter MUST NOT reorder, deduplicate, or collapse them.

**REQ-EVENTS-118** — An empty result MUST be a normal, successful answer at every layer — query, replay, and the surfaces of Section P — and MUST NEVER be an error. A run that performed no tool calls simply yields zero matching events, which is a valid result.

**REQ-EVENTS-119** — Iteration attribution MUST be derived from iteration boundaries as the history is read: an event carrying an explicit iteration number retains it, while every other event takes whichever iteration is currently open; after an iteration ends, the context closes and subsequent events belong to no iteration; events before any iteration (such as `session.start`) MUST match no iteration filter. Asking for an iteration MUST therefore return the tool calls, permission decisions, and errors that happened inside it, not only the events that explicitly record the iteration number.

**REQ-EVENTS-120** — An event `timestamp` and a query's lower and upper bounds MUST all be read as ISO-8601 instants, a value carrying no offset being read as UTC, and MUST be compared as absolute instants: a bound written in one offset MUST select exactly the same events as the identical instant written in any other. An event whose `timestamp` is empty or is not a parseable instant MUST match no query that sets either bound, and MUST still be returned by a query that sets neither. A history mixing offsets, or mixing stamped and unstamped events, MUST still yield the complete matching set for a bounded query: setting a time bound may never end a read early and may never turn it into an error. Timestamps are wall-clock and carry no monotonic guarantee, and the comparison is therefore defined on the stamp alone: every event bearing an instant equal to a bound is selected, ties are neither broken nor reordered but returned in stored order (REQ-EVENTS-117), and a clock that moved backwards mid-run may make a bounded query select a set that is not contiguous in the history. That is a permitted outcome, never an error, and no requirement obliges a reader to detect or correct it.

**REQ-EVENTS-121** — Unknown event types MUST remain fully queryable: they MUST be selectable by type filter and MUST inherit iteration context exactly like known events.

**REQ-EVENTS-122** — Filtering MUST be applied per event during the read: querying a long history MUST NOT build the whole event list in memory, and the read MUST stop advancing once the caller stops consuming.

**REQ-EVENTS-123** — Replaying a session means reading its stored history, never re-executing anything. Replay MUST leave the history exactly as it stood before it, whether or not the session is live.

### N. Session discovery and listing

**REQ-EVENTS-124** — Listing MUST return every session of the workspace that has a stored history (REQ-EVENTS-125 defines what counts as having one) and nothing else. The order MUST be descending by the instant of the session's last event; where that instant is missing, empty, or unparseable, by the instant of its first event; and a session yielding no parseable instant at all MUST sort after every session that yields one. Sessions that still compare equal MUST be ordered by session id, descending. A workspace in which no session has ever run MUST yield an empty listing, not an error.

**REQ-EVENTS-125** — A session counts as having a stored history from the moment its history is opened for it (REQ-EVENTS-087); a history holding no event still qualifies, so that a run which recorded nothing stays distinguishable from a session that has no history at all. Sessions with no history MUST simply be absent from the listing rather than causing an error.

**REQ-EVENTS-126** — Summarizing a session for the listing MUST yield its event count and the instants of its earliest and latest stored events — enough to derive the time span — and MUST NOT require decoding, or reading whole, every event of that history. This is a bound on what a listing costs, not a prescription of how a summary is obtained: a listing of a workspace holding long histories MUST stay within the interaction budget REQ-EVENTS-175 and REQ-SHELL-150 fix, however many events those histories hold. The listed count is a count of the events the history holds, and it MUST equal the number of events replay returns for that session (REQ-EVENTS-127), because a history holds no record that replay would skip: an event is stored whole or not at all (REQ-EVENTS-029). A listing therefore no longer differs from replay on any session, and any figure a reader takes from the listing is the figure the export will report.

**REQ-EVENTS-127** — Unknown event types MUST be counted in the listing, otherwise the listed total would not match what replay produces.

**REQ-EVENTS-128** — A history that cannot be summarized MUST summarize as empty with a logged warning; a single unreadable session MUST NEVER fail the listing as a whole.

**REQ-EVENTS-129** — Each listed session MUST report: session id (resolved per REQ-EVENTS-085), the location of the session's own files — where the session keeps whatever is not held as a record, its log among them — event count, first timestamp, last timestamp, truncation flag, and dropped-event count. Truncation MUST be carried beside the count on purpose: a capped history's count is a count of survivors.

**REQ-EVENTS-130** — A session identity supplied to a reading surface — chosen in the interface, or carried in a document, a link, or a stored preference — MUST be treated as untrusted and MUST be resolved before it is used to read anything. It MUST resolve only within the workspace the window has open; an identity naming a session of any other workspace, and an identity shaped so as to reach outside it — an absolute path or one containing parent-directory traversal among them — MUST resolve to "not found" and MUST widen nothing about what the surface reads. An empty identity, and an identity for which the workspace holds no session with a stored history, MUST also resolve to "not found".

**REQ-EVENTS-131** — A history surface MUST read the sessions of the workspace its window has open, resolved by the same rule a run of that workspace uses when deciding which workspace's sessions it is recording into, so that the surface always finds the sessions runs produced and never a second workspace's. A session's history belongs to exactly one workspace's sessions, and no surface may present one workspace's history among another's.

### O. Trajectory export

**REQ-EVENTS-132** — An export MUST produce, for each session, a single self-contained JSON document. It MUST hold the identity fields of the run, the events in their original order, and a summary block. The document MUST remain usable away from the machine that produced it: it MUST remain readable once the session it describes has been deleted and once the store that held it is gone, MUST NOT embed absolute paths local to the producing machine apart from the workspace path the run recorded in its own events, and MUST be readable with any standard JSON parser without any of this product's code present (REQ-EVENTS-166).

**REQ-EVENTS-133** — The trajectory document version MUST be `1` and MUST carry its own version number, separate from the event schema version. Each embedded event states its own schema version, so revising the enclosing document format does not alter the event format.

**REQ-EVENTS-134** — The exported events MUST be the stored payloads in order, copied exactly as stored and never rebuilt by re-serializing a decoded copy (REQ-EVENTS-080, REQ-EVENTS-104), with no second masking pass — this is what lets an older build read a newer store's export, and it guarantees the exported events are exactly the events that were emitted.

**REQ-EVENTS-135** — Every number in the summary MUST be computed afresh from the exported events, so the summary cannot drift from what it describes. In particular, the sum of the per-type counts MUST equal the total event count.

**REQ-EVENTS-136** — The summary MUST report: total event count; count of events of unrecognized type; count of unreadable lines skipped while reading; number of runs (occurrences of `session.start`); number of distinct iterations started; iterations completed as reported by the last `session.end`; tool calls started and tool calls finished with an error; permission decisions and the subset that denied; verifier runs and the subset that did not pass; child agents spawned; errors and the subset flagged fatal; per-type event counts with sorted keys including unknown types; and token and cost figures taken from the most recent usage or session-end payload (usage accumulates, so the latest figure is the total).

**REQ-EVENTS-137** — When the source history contained unreadable lines, the document MUST disclose that through its skipped-line count rather than quietly presenting a shorter event list.

**REQ-EVENTS-138** — Run identity — task, workspace, persona, permission mode — MUST come from the last `session.start`. The latest-run segment begins at that event and extends through the remaining exported events. Outcome — status, stop reason, duration, iterations completed — MUST use the last `session.end` within that segment. When that end supplies no status, status and stop reason MUST use the last `result` within the segment. When neither supplies a status, export status MUST be `unknown`, stop reason and end timestamp MUST be empty strings, and duration MUST be zero. A terminal outcome's end timestamp MUST be its event timestamp; its supplied duration takes precedence over elapsed time derived from the start and terminal timestamps. If retention removed every start boundary, the retained events form an identity-unknown segment and the truncation disclosure remains required. Summary event counts describe the entire exported history; latest-run outcome fields describe this segment. The runs count discloses how many start boundaries the exported history retains. No outcome may be borrowed across a retained start boundary.

**REQ-EVENTS-139** — The exported session id MUST be resolved in this precedence: an explicitly supplied id wins; otherwise the first event's session id; only when no event carries an id does the identity the session is recorded under apply — so that a session whose record was copied or renamed still exports under the id recorded in its own events.

**REQ-EVENTS-140** — Truncation MUST be reflected in the document: a history a trim has dropped events from exports with the truncation flag set and the cumulative dropped count (REQ-EVENTS-094); an intact history exports as not truncated with a dropped count of zero (REQ-EVENTS-092). The two figures MUST be carried on the document itself, so a reader learns the history is incomplete from the document alone without access to the store it came from.

**REQ-EVENTS-141** — Unknown event types MUST survive export verbatim and MUST be counted separately as well as in the per-type totals; a future event type or field MUST round-trip into the document unchanged.

**REQ-EVENTS-142** — A session whose history was opened but never written to MUST export as a valid empty document: the identity the session is recorded under (REQ-EVENTS-139), an empty event list, a zero event count, and empty start time and status.

**REQ-EVENTS-143** — A credential present in the run but masked on the wire MUST appear nowhere in the export document, while the surrounding context (tool name, masked argument marker) MUST remain present and readable.

**REQ-EVENTS-144** — Batch export MUST produce one trajectory document (REQ-EVENTS-132) per selected session, in the order those sessions are listed in the selection (REQ-EVENTS-173), wrapped in one batch document. **This requirement is the single definition of that wrapper**, for this document and for every other; a requirement that needs to name the wrapper cites this identifier rather than restating its shape. Which of the two forms an export produces — the trajectory document alone for one selected session, the wrapper for several — is REQ-EVENTS-173's and REQ-SESSION-189's, and is not fixed here.

The wrapper's key names are a machine-readable contract and are exactly `trajectory_version`, `count` and `trajectories`, in lower snake case. `trajectory_version` MUST carry the trajectory document version of REQ-EVENTS-133, so a batch and every document inside it declare the same version and a consumer learns from one place which format it is reading. `count` MUST be the number of trajectory documents the batch holds. `trajectories` MUST be those documents themselves, unaltered and in selection order. That inventory is exhaustive and closed: the wrapper MUST carry no key of its own beyond those three, and a reader may rely on no other being present — so a consumer that understands one trajectory document understands a batch, and the wrapper is the only thing it must learn. Key order is not significant (REQ-EVENTS-145 fixes the serialization).

`count` MUST equal the number of elements in `trajectories`. It is carried rather than left to be inferred because a reader on a machine with none of this product's code must be able to check that the batch they hold is the batch that was written, without trusting the producer (REQ-EVENTS-166's third obligation) — the same reason the truncation figures travel on the document itself (REQ-EVENTS-140), and the reader-side counterpart of the all-or-nothing rule REQ-EVENTS-157 states for producing a batch at all.

**REQ-EVENTS-145** — Writing an export to a file MUST create missing parent directories, MUST write pretty-printed JSON with sorted keys, two-space indentation, and a trailing newline, and MUST become visible at its destination in one step, so that whatever else is reading or watching that destination sees either no document or the whole document, and never a partial, empty or unparseable one. This is the only place this document requires a file to be replaced in one step; the same obligation on the stored history became REQ-EVENTS-091's indivisible trim, and the guarantee is the same in both — a concurrent reader never observes an intermediate state. The one-step-visibility obligation above is the product's single statement of what an export write owes the destination a user chose, and it is not confined to the exports this document names: a requirement in another domain whose export writes to such a destination cites this identifier rather than stating a second obligation, as REQ-SESSION-189 and REQ-SESSION-199 do. It binds every export write whatever form the exported document takes; the document-form clauses above bind an export written as a JSON document.

The type control MUST offer the catalog of REQ-EVENTS-041 together with any unrecognized type present in the history being read, so an unknown type stays selectable (REQ-EVENTS-121). An axis left unset MUST restrict nothing, and a filter that matches no event MUST present as an empty result — never as an error or a failure (REQ-EVENTS-118). Time bounds MUST be entered through a date-and-time control, so an unreadable bound is unreachable from this surface; where a bound is nevertheless supplied as text, it MUST be rejected in place, naming which bound was rejected and quoting the value, and no store content may be read on account of the rejected query.

**REQ-EVENTS-172** — The surface MUST be able to hand the user the currently selected events as JSON lines, each line byte-identical to what the live stream emitted for that event (REQ-EVENTS-080, REQ-EVENTS-104) and terminated by a single line feed on every platform (REQ-EVENTS-090), whether by copying them or by writing them to a file the user chooses. Each line MUST be emitted from what the stored record holds, in stored order — a concatenation, never a re-serialization. For an unfiltered selection those lines MUST equal the run's lines exactly, in number and in bytes; for a filtered selection they MUST equal the corresponding subset. The output MUST carry events and nothing else: no warning, no heading, no row rendering, and no value derived from an event for querying or presentation may appear in it, so a consumer reads exported output and live output interchangeably. This is the **history export**, and it is one of the two forms REQ-EVENTS-166 obliges: it MUST be available whether or not the session is live, and what it produces MUST be a file or a copy the user now holds, never a channel the surface keeps open.

**REQ-EVENTS-173** — The surface MUST offer an export action over one or more selected sessions, producing the trajectory document of REQ-EVENTS-132 for a single session and the batch document of REQ-EVENTS-144 for several, in the order the sessions are listed in the selection. The action MUST be offered whether or not a selected session is live, and a live session MUST export the history as it stands at the moment the action was taken (REQ-EVENTS-098, REQ-EVENTS-123). The destination MUST be chosen through the platform's own file chooser; the document MUST be written atomically with missing parent directories created (REQ-EVENTS-145). On success the surface MUST state how many trajectory documents were written and the absolute path they were written to. The export MUST still be produced, and MUST NOT be reported as a failure, in either of two cases, each of which MUST be disclosed to the user: the session holds more than one run, where the disclosure MUST state how many runs the document spans — the figure the document's `summary.runs` carries — and that the identity fields describe the most recent of them (REQ-EVENTS-138); and the store is truncated, where the disclosure MUST state how many events were dropped — the figure the document's `dropped_events` carries — and that the document therefore does not cover the whole history. Where both apply, both MUST be disclosed. Wording is the implementation's; the figures and the facts are not.

**REQ-EVENTS-174** — Given a session identity that resolves to no stored history under the workspace the window has open, the surface MUST report that in place, naming both the identity exactly as it was supplied and the absolute path of the workspace searched, and MUST NOT present the condition as an empty result — so a session that was looked for in the wrong workspace is distinguishable from a session that recorded nothing, which is an ordinary empty result under REQ-EVENTS-118. An identity that attempts to reach outside the workspace (REQ-EVENTS-130) MUST produce the same report and MUST disclose nothing about whether anything exists under the identity it named.

**REQ-EVENTS-175** — Reading a history MUST NOT block the interface. Given a session whose history has already been read, a change to any filter of REQ-EVENTS-171 MUST be reflected within 100 ms of the interaction. Given a history still being read, the surface MUST present a progress state and MUST remain interactive, and reading MUST stay incremental and lazy (REQ-EVENTS-099, REQ-EVENTS-122, REQ-EVENTS-126) so that neither a long history nor a workspace holding many sessions is ever held whole in memory. Cancelling a read MUST leave the history exactly as it stood (REQ-EVENTS-100).

### Q. Cross-cutting integration invariants

**REQ-EVENTS-160** — For any run, the stored history MUST equal the emitted stream exactly: same payloads, same order, same envelopes; the first stored event `session.start`, the last `result`, exactly one `result`, and every stored event carrying the session's id.

**REQ-EVENTS-161** — The terminal `result` event MUST reach the store as well as any live consumer, so the history's last record is independent evidence that the terminal event traversed the normal delivery path.

**REQ-EVENTS-162** — An exported trajectory's event list MUST equal the lines the live stream emitted for the same run, and its summary counts MUST agree with what actually happened during the run. This is the conformance test for REQ-EVENTS-166: because the export rather than the write path is now what a third party reads, an export that drifts from the wire breaks the guarantee outright, and this equality is what detects that.

**REQ-EVENTS-163** — The per-session evidence records are distinct contracts and MUST NOT be conflated by a consumer: the tool-call evidence record holds arguments exactly as they were passed, with no masking applied; the permission audit (REQ-TOOLS-078) and the verification-gate record (REQ-TOOLS-190) each hold their own record under their own retention rule; while the event history holds only masked wire events, under this document's cap and trim rules alone. A figure taken from one of these MUST NOT be assumed to agree with a figure taken from another: they are capped independently and record different things.

**Not every record named above has an export, and this requirement does not grant one.** Which records are exportable is settled by the redaction-safety test REQ-TOOLS-190 states and owns, and is restated nowhere. Under it the event history has the two exports of REQ-EVENTS-166, the permission audit has the one REQ-SESSION-199 requires, and the verification-gate record has the one REQ-TOOLS-190 requires. **The tool-call evidence record has none, and MUST NEVER gain one** (REQ-SESSION-136, REQ-TOOLS-190): it holds the arguments an agent passed exactly as they were passed, unredacted, and that is precisely why it is named here as a contract a consumer must not conflate with the masked event history. Where exports exist, they are as distinct as the records behind them and MUST NOT be presented as one document or reconciled against each other. Nothing in this requirement may be read as offering an export to a record that has none.

**REQ-EVENTS-164** — A programmatic consumer MUST be able to iterate a run's events asynchronously while the run is still in progress, receiving the same events, in the same order, that the live stream carries. Pending events MUST be buffered up to 1024; while 1024 are outstanding, each further event MUST be discarded rather than blocking the run, and the number discarded MUST be readable by the caller once iteration has ended, so that an incomplete stream is detectable rather than silent. Discarding events MUST NOT affect the caller's ability to obtain the run's terminal outcome, which the call itself returns rather than requiring it to be recovered from the stream. Iteration MUST end once the `result` event has been yielded. The discard count MUST be readable at any time, during iteration as well as after it, and MUST only ever rise, so that a caller can notice a backlog while it can still act on it rather than learning of the loss only once the run is over; it MUST NOT be reset by reading it. This programmatic interface MUST carry its own version, independent of the event schema version, whose current value MUST be the string `"1"`.

**REQ-EVENTS-165** — A live consumer MUST receive every event raised for the session it is registered for, in emission order, with no event delivered twice and none skipped where the consumer returns normally; delivery MUST complete before the run proceeds past the operation that raised the event, so a slow consumer delays the run rather than losing or reordering events. Every event delivered MUST already satisfy the validation of REQ-EVENTS-017, so a consumer never receives a partially populated or unmasked event. A consumer that fails MUST NOT fail the run (REQ-EVENTS-074); the contract is nevertheless that a consumer returns without failing and does not block. That contract MUST be enforced rather than left advisory: delivery of one event to one consumer MUST be bounded at 5 seconds, and a consumer that has not returned by then MUST be treated exactly as one that went away under REQ-EVENTS-031 — delivery to it stops permanently, a warning is recorded naming the session and the event type that was outstanding, and the run proceeds. No other consumer's delivery is affected, and recording is unaffected (REQ-EVENTS-082). A bound is required because an unbounded wait would let one faulty consumer stall a run indefinitely, which REQ-EVENTS-074 already refuses to allow for a consumer that fails outright.

**REQ-EVENTS-166** — **A user MUST always be able to get a run's history out of this application in a form software that knows nothing about this product can read.** The stored history is a record only this application reads; this requirement is the obligation that makes that acceptable, and it is discharged by **export**. It is the single definition of what an export of a session record must guarantee, for this document and for every other.

Two exports of the event history MUST exist and MUST both satisfy the guarantee below: the line-delimited history export of REQ-EVENTS-172, which is the run's own lines, and the trajectory document of REQ-EVENTS-132.

The guarantee. Decoding one exported event line, reading a whole exported history, or reading an exported trajectory document MUST require nothing beyond a standard JSON parser and this specification: no part of the agent runtime, no configuration loading, no network access, no access to the store the export was taken from, and no access to the workspace the run took place in. An exported history or an exported document copied to another machine — one carrying none of this product's code, and no copy of the store — MUST yield **every field of every event** when read there with a stock JSON parser, and MUST yield them unaltered: the same field names, the same values, the same schema version, and the same events in the same order the run emitted them (REQ-EVENTS-080, REQ-EVENTS-134, REQ-EVENTS-162). Nothing about the export may be conditional on this application still being installed, on the session still existing, or on the session not being live.

Three obligations attach to every export this requirement governs.

1. **Reachable whether or not the session is live.** An export MUST be offered for a session that is running and for a session that is not, and MUST NOT require the run to end first (REQ-EVENTS-098, REQ-EVENTS-173). A live session exports its record as it stands at the moment the action was taken.
2. **An export is not a channel.** It MUST be a user-initiated action that yields a file or a copy the user then holds, taken once per request. No surface may follow a run through an export, no export may be repeated on a timer or re-taken to observe progress, and no export may be the way any part of this product learns what a run is doing (REQ-SESSION-071, REQ-EVENTS-123). What a run is doing reaches a surface through what the application publishes for it and by no other route; an export is how a record leaves.
3. **The export carries the record's own integrity properties.** Whatever ordering, append-only character, or completeness the record has where it is stored MUST be evident in what is exported — the events in emission order, the count of what was dropped where anything was (REQ-EVENTS-137, REQ-EVENTS-140) — because an export that a reader cannot check against the record it claims to be is decorative.

**This requirement is the pattern for every other session record a user could previously have read for themselves**, the session timeline, the recorded issues, the metrics document and the permission audit among them. Each such record is exported in a form a stock tool can read, reachable whether or not the session is live, and under the three obligations above; the export of each is owned by the domain that owns the record, and that domain cites this identifier for what its export must guarantee rather than restating it. The permission audit is the case that decides the shape of the rule, because it is exactly the record a user consults when they do not trust this application's rendering of events: an audit only this application can read is a materially weaker audit, and its export inherits the ordering and append-only obligations its own requirement states.

**REQ-EVENTS-167** — The wait for a human approval is not this document's to fix: its configuration key, its value space, its default, and the reading of a configured `0` are REQ-CONFIG-126's, and this document holds no copy of any of them. What this document requires is that the wait in force for a request MUST be visible to a consumer as the `timeout_seconds` field on `approval.requested`, so that a consumer reading the wire learns how long the request will be held without consulting the configuration — and, per REQ-EVENTS-049, that the field is null exactly on the resolver that never waits.

**REQ-EVENTS-177** — The verification-gate log of REQ-TOOLS-190 MUST NOT gain an event type in the catalog of REQ-EVENTS-041. Every write and every decline it records is an attempt an agent made through a tool, and is therefore already observable on the stream as the `tool.start` / `tool.finish` pair of REQ-EVENTS-057 for that call, with the decline carried as that call's failure; the gate's own reasoning — its `outcome`, `decline_case`, `reason`, `checks` and `detail` — stays durable in the verification-gate record REQ-TOOLS-190 fixes and in the timeline entry that requirement also writes. A consumer needing that detail MUST read that record rather than expect a wire event, and MUST NOT treat the absence of such an event as evidence that no gate decision was taken. This is a deliberate exclusion, not an omission: the catalog stays at the 23 types of REQ-EVENTS-041.

**REQ-EVENTS-178** — The product is one desktop application and offers no embedding surface and no programmatic entry point: there is no library, package, plugin host, or endpoint through which code the user did not launch may start a run, drive a run, or subscribe to this application's runs, and no requirement of this document is satisfied by one. The consumer contracts of REQ-EVENTS-164 and REQ-EVENTS-165 are not an exception and MUST NOT be read as one: the consumer they describe is this application consuming its own runs in its own process — the session-history surface of Section P, the run views, and the desktop notice channel — so the interface version REQ-EVENTS-164 fixes versions an internal contract and not a published one. What may leave the application is a file, never a connection: the exported history of REQ-EVENTS-172 and the exported trajectory document of Section O, each readable with a stock JSON parser and nothing else (REQ-EVENTS-166). This is a deliberate exclusion rather than an omission — a programmatic driving surface would be a second way to start work, carrying its own permission, approval, and sandbox behavior to hold in step with the desktop one — and it is why the withdrawn surfaces of Section A are not partially reinstated in another form.

## Data & Formats

### What a session keeps, and who reads it

A session's records are durable records that only this application reads. This document fixes no path, no file name and no enclosing directory for any of them (REQ-EVENTS-079 withdrawn); where they live is domain 07's and the storage decision's.

| Record | Contract |
| --- | --- |
| the event history | one record per wire event, in emission order, each holding verbatim what the live stream emitted (REQ-EVENTS-080); at most one writer, being the holder of the session's lock (REQ-EVENTS-098) |
| the truncation record | the four facts of REQ-EVENTS-092; exists only once a trim has dropped events; absent reads as not truncated, zero dropped |
| tool-call evidence | separate contract: arguments verbatim, unredacted (REQ-SESSION-136) |
| the permission audit | separate contract (REQ-TOOLS-078, REQ-SESSION-137) |
| the verification-gate record | separate contract (REQ-TOOLS-190); deliberately produces no wire event (REQ-EVENTS-177) |

None of these is conflated with another and no figure taken from one describes another (REQ-EVENTS-163). A session is identified by its session id, but an exported document prefers the id the events themselves recorded (REQ-EVENTS-139).

### Record locators

A reference from one record to an entry of another is the string `<record kind>#<record id>`, fixed by
REQ-EVENTS-056 and restated here rather than defined. The record-kind token set is closed at three, and
each id is the identifier the named kind's own requirement gives its entries:

| Token | Record | Record id | Has an export? |
| --- | --- | --- | --- |
| `issues` | the session's issues record (REQ-SESSION-135) | the issue's `id`, 12 hex characters | yes (REQ-SESSION-199) |
| `permission_audit` | the session's permission audit (REQ-SESSION-137, REQ-TOOLS-078) | REQ-TOOLS-079's to fix; a field of the decision entry, and mode-change entries have none | yes (REQ-SESSION-199) |
| `tool_call_evidence` | the tool-call evidence record (REQ-SESSION-136) | the record's `call_id` | **never** (REQ-TOOLS-190) |

A locator is carried opaquely: no export dereferences one, and where the named kind has no export the
locator names something a reader must return to the application to see (REQ-EVENTS-056).

### Line format — the export

One JSON object per line, compact (no whitespace after separators), object keys sorted, non-ASCII escaped, terminated by a single line feed on every platform (REQ-EVENTS-090). Two equal events produce byte-identical lines. The event as delivered live, the event as stored, and the line handed over by REQ-EVENTS-172 are byte-identical for the same event. This format is what leaves the application; it is not a claim about how the history is stored, and a store whose records are not separated by newlines satisfies it by exporting in this form.

### Run status vocabulary

Exactly the closed terminal run-result set of REQ-ORCH-083, carried onto the wire by REQ-EVENTS-026; this document holds no copy of it. The application does not exit when a run ends, so no process exit code is fixed by this document or by any other (REQ-EVENTS-025 withdrawn, REQ-ORCH-083).

### Truncation record (REQ-EVENTS-092)

Four facts, carried with the session's own record and made durable in the same indivisible step as the trim that produced them:

| Fact | Type | Meaning |
| --- | --- | --- |
| truncated | bool | whether any event was ever dropped |
| dropped events | int | cumulative over the life of this session id, across runs and across launches of the application (REQ-EVENTS-094) |
| cap in force | int or null | null when unbounded |
| last trimmed at | string | ISO-8601 UTC |

An absent truncation record means zero drops, and so does a session with no stored history at all; neither is an unknown figure and neither is a failure. These are not event records and never appear among the events an export emits; the trajectory document carries the first two under its own key names (REQ-EVENTS-140, and the document's key inventory is REQ-SESSION-193's).
