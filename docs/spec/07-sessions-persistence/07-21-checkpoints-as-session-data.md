# Session Persistence, Resume, and Background Sessions — 21. Checkpoints as Session Data

Part 7 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-162 – REQ-SESSION-181.

### 21. Checkpoints as Session Data

- **REQ-SESSION-162** — Per-iteration git checkpoints MUST persist in two places that stay consistent: refs under `refs/rotaris/checkpoints/` in the run's tree (the isolated worktree for isolated sessions, else the workspace), and the session's `checkpoints` list mapping iteration to ref and commit. Keeping the mapping in the session state is what allows checkpoints to survive a resume and to remain restorable after a crash.
- **REQ-SESSION-163** — The listing record's `checkpoint_count` MUST mirror the length of the state's checkpoint list (the session list reads the listing record only); readers default an absent value to 0 for records written before checkpoints existed.
- **REQ-SESSION-164** — Checkpoint restore for a session that *claims* to be running MUST be refused, because the pre-restore checkpoint this operation records would contend with writes from the supposedly live run; the stale-repair flow exists precisely to make restore available again after a crash. The refusal MUST convey the session id, the status the session records, that nothing was restored and the working tree is unchanged, and — when the session is stale rather than live — that repairing it makes the restore available (REQ-SESSION-182). It MUST be presented as an error on the surface that asked for the restore (REQ-GIT-096); the wording is left to the implementation, and no numeric code is produced (REQ-SESSION-187). **That refusal holds for the whole of the restore and not only at the moment it is asked for.** It is not discharged by answering the question once and proceeding on the answer. From the moment the product answers it until the restore has completed or been abandoned, no session in the workspace may become live; where one has, the restore MUST be refused rather than carried through, and where the restore has already begun to change the working tree it MUST be undone to the state it started from. Whether new runs are refused before the question is asked, or the question is asked again once that refusal is in force, is left to the implementation; what is fixed is that there is no window between the two into which a run may be admitted. **This restore never disturbs a live session either.** It MUST NOT stop, cancel, interrupt, or require a run that is under way to give up the working tree it is changing; the remedy on finding a live session is to refuse, never to clear it out of the way. **The reason this is stated here rather than left to follow from the sentence above.** What this operation replaces is the user's own working tree, not a record the product keeps, so a run admitted while it proceeds has the files it is reading and writing changed beneath it — and unlike a store the product owns, nothing about the working tree is under this product's control to put back. A run that is asked to stand aside and whose files are then replaced has been damaged by the restore whether or not it complied. The same rule governs the whole-store restore of REQ-SESSION-201, which cites this requirement as its precedent; both are one rule and neither is the other's exception.
- **REQ-SESSION-165** — *Withdrawn.* Listing and restoring checkpoints has no command surface; the capability is carried by the desktop checkpoint browser of domain 06 (REQ-GIT-096 and the gates of REQ-GIT-058), with this domain's refusal for a busy session staying in REQ-SESSION-164.
- **REQ-SESSION-195** — The session record MUST carry `last_restored_sequence`: the integer sequence of the checkpoint most recently restored into this session's tree, or null when no restore has ever succeeded for the session. It defaults to null, so a state written without it loads unchanged (REQ-SESSION-015), MUST be written as part of the same durable write that reports a restore successful, and MUST be left untouched by every refused and every failed restore. Its only use is to widen the drift candidate set of REQ-GIT-056 so that undoing a rollback never demands a force (REQ-GIT-155); it MUST NOT affect which checkpoints are listed, numbered, pruned, or restorable, and a value naming a checkpoint no longer recorded simply contributes no candidate.

### 22. Session Deletion

- **REQ-SESSION-166** — Deleting a session MUST first best-effort discard the session's checkpoint refs (loading the state to locate the right tree — the worktree for an isolated session, else the workspace root), then remove the session's record and its files (REQ-SESSION-002) together, ignoring errors, so a deletion never leaves a listed session with no record, or files with no session. An unreadable session still deletes. Deleting a missing session is a no-op. A ref-cleanup failure logs a warning naming the leftover `refs/rotaris/checkpoints/` location; cleanup stays best-effort so a session still deletes when the repository moved or never existed. Refs MUST be pruned as well, because removing only the record would leave them behind permanently. The workspace-scoped improvement library is not part of the session and MUST NOT be reduced by the deletion (REQ-SESSION-007).
- **REQ-SESSION-167** — The run lifecycle deletes a session in exactly one situation: a *just-created* session whose launch failed before the run started (worktree bind or sandbox failure). A resumed session MUST never be deleted by a failed launch.

### 23. Metrics Continuity Across Resume

- **REQ-SESSION-168** — On every persist, in-process metric aggregates MUST be copied into the state: global tokens, cost, tool calls, compressions, per-agent metrics, and sorted compression-dedup ids. The legacy token-usage field is set only when total tokens exceed 0, else null.
- **REQ-SESSION-169** — At run start and resume, in-process aggregates MUST be rebuilt from the persisted state with graceful fallbacks: a per-agent tool total without per-tool detail restores as a single pseudo-tool entry; zero global tokens falls back to the legacy token-usage field, then to merging per-agent snapshots; global cost, compressions, and tool-call counters are recomputed from agents the same way. Consequence: cumulative token, cost, and tool counters continue across resumes rather than resetting.

### 24. Reasoning-Content Repair at Open

- **REQ-SESSION-170** — The full session open of REQ-SESSION-040 — and only that path, never the read-only snapshot read — MUST run a best-effort repair before the session is handed back. The trigger MUST be a declared property of the model, read from the model-capability metadata the product ships with (REQ-PROVIDER-137), and never an observed failure, a hard-coded list of model identifiers, or a guess from a provider name; when the metadata does not declare the property for the session's default-persona model, the repair MUST NOT run, because rewriting stored conversation files on suspicion is worse than a request the provider might refuse. When that metadata declares that the session's default-persona model rejects requests in which an earlier assistant message carries no reasoning content, every persisted conversation event the session recorded is examined, and action events whose reasoning content is null or missing, together with agent message events whose message carries no reasoning content, are rewritten with an empty string in place of the missing content, in one durable operation so that no reader observes the session part-way through the pass. The pass MUST run at most once per open, MUST record and log how many items it changed, and MUST NOT prevent the open from completing when it fails.

### 25. Cross-Cutting Invariants

- **REQ-SESSION-171** — For one pid at one moment, lock reaping, liveness reporting, stale detection and the worktree-integration precondition MUST all reach the same verdict: it MUST NOT be possible to observe one of them treating a process as alive while another treats the same process as gone.
- **REQ-SESSION-172** — Any uncertainty about whether a session is live resolves in favour of "still running"; detection performs no writes; repair is explicit, made durable at once, idempotent, and never raises.
- **REQ-SESSION-173** — The last *requested* save wins in the record, not the last write to finish; a terminal status is always durable before its save call returns; disk is never staler than the newest requested state.
- **REQ-SESSION-174** — Every run through the shared lifecycle persists its full event history regardless of streaming (supplying no event sink still persists the history; it only means nothing is streamed out), and the stored history is exactly the sequence the live stream saw (persist-before-forward tee).
- **REQ-SESSION-175** — History and diagnostics writing never fails a run: the event history, transcript publication, change callbacks, diagnostics writers, and the timeline-to-wire bridge all degrade to logged warnings.
- **REQ-SESSION-176** — Per-session bindings (event sink, event history, transcript recording, hook running, approval handling, audit) bind late by session id and are discarded at run teardown, so that no leftover binding can influence a later run in the same process, and an event arriving after teardown has no destination.
- **REQ-SESSION-177** — The terminal `result` event is delivered exactly once per run — through the event bus for runs that started, written directly to the sink only for runs that never attached anything — and the run outcome of REQ-SESSION-187, the `result` payload, and the human summary all read off one shared derivation.
- **REQ-SESSION-178** — A session list is limited to what the listing record holds, so every list-visible attribute (title, status, staleness inputs, checkpoint count, requirement attribution, awaiting-input) is denormalized into that record at save time, with reader-side defaults for older records.
- **REQ-SESSION-179** — Data written by another version of this product is honored but never repaired in place: absent optional state keys load as their defaults (REQ-SESSION-015), absent metadata keys take their reader-side defaults (REQ-SESSION-030), an undecodable secondary state part degrades exactly as an absent one (REQ-SESSION-036), and a schema version newer than this one is refused rather than lossily restored (REQ-SESSION-038). There is no predecessor layout and no whole-state fallback record (REQ-SESSION-005, REQ-SESSION-037).
- **REQ-SESSION-180** — Displayed liveness is re-derived from the same snapshot that renders the header (agents settled against the execution status; running tool rows neutralized on non-live sessions), so that an internally inconsistent snapshot — from an earlier version or from a killed process — is never rendered as one.

  > derived liveness leaves a `paused` agent `paused`; a session at rest with paused agents is consistent, and every
  > other agent is settled as stated.
- **REQ-SESSION-181** — The created/resumed announcement of REQ-SESSION-185 follows whether the *run request* carried an existing session id, not what the run internally did: a caller that pre-names a brand-new session (REQ-SESSION-011) still has that session announced as created.
