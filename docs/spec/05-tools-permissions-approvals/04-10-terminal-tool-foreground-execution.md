# Agent Tooling, Terminal Execution, Permissions, and Approvals — 10. Terminal Tool — Foreground Execution

Part 4 of 9 of [domain 05](../05-tools-permissions-approvals.md), which indexes every part. Defines REQ-TOOLS-095 – REQ-TOOLS-125.

### 10. Terminal Tool — Foreground Execution

**REQ-TOOLS-095** — The tool name is `terminal`. Its annotations declare it not read-only, potentially destructive, non-idempotent, and open-world. Creating it with a nonexistent working directory fails with `working_dir '<d>' is not a valid directory`.

**REQ-TOOLS-096** — Action schema: `command` (string; an empty string polls for more output after a soft pause; with `is_input=true` it may instead be a special key: `C-c`, `C-d`, `C-z`, any `C-<letter>`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `HOME`, `END`, `PGUP`, `PGDN`, `TAB`, `ESC`, `BS`, `ENTER`), `is_input` (bool), `timeout` (float ≥ 0, hard wall-clock), `reset` (bool), `background` (bool), `session_id` (format `ts_XXXXXXXX`), `session_action` (`query`|`kill`|`send_input`|`send_signal`|`list`), `signal` (`SIGTERM`|`SIGINT`|`SIGKILL`|`SIGHUP`), `input_data` (string). One command per call; sequences are expressed with `&&`/`;`.

**REQ-TOOLS-097** — A foreground command is bounded in two ways, and whichever bound is reached first governs the call. (1) A hard wall-clock timeout: the call's own `timeout` when it supplies one, otherwise `runtime.shell_command_timeout` (default 100 s, REQ-CONFIG-116) for every action that is not keystroke input. On reaching it the entire process tree the command started is terminated, the terminal session is restarted, and the observation of REQ-TOOLS-099 is returned; everything the shell had accumulated — working directory, exported variables, aliases, background jobs — is gone, and the observation says so. (2) A soft pause: when the call supplies no `timeout` and the command has produced no output for 30 seconds — the no-output window, fixed for every backend and platform — the call returns early under REQ-TOOLS-098 with exit code −1 while the process keeps running. The soft pause applies only to a call that supplied no `timeout`. Supplying one is the agent declaring how long it is prepared to wait, so such a call is bounded by its own hard timeout alone and never returns early for silence.

Captured foreground output is capped at 100,000 characters per call. When a command produces more, the capture is truncated from the oldest end so the most recent output always survives, and the truncation is stated in the observation's detail and recorded as `output_truncated: true` in the `[terminal_diagnostic]` block (REQ-TOOLS-100); an untruncated capture omits that key.

**REQ-TOOLS-098** — A soft-paused call returns exit code −1 with no `failure_kind`, while its process keeps running. When capture is empty, the observation MUST state the elapsed no-output window under REQ-TOOLS-097 and the active backend's capture semantics. A merged PTY backend MUST explain that both stdout and stderr are captured, that the process may still be running, and that the agent can poll with an empty `command` or interrupt with `C-c` and `is_input=true`. Advice to re-run with `2>&1` is permitted only when the active backend excludes stderr from capture. Every observation MUST render `[terminal_output]` followed by captured text or `(no output)`.

**REQ-TOOLS-099** — Hard-timeout observation contract: `exit_code` 124, `timeout` true, `is_error` true, `failure_kind` `"timeout"`, `timeout_seconds`, `kill_status` ∈ {`session_reset`, `reset_failed`}, `session_reinitialized` (bool), `backend` (REQ-TOOLS-100), and a detail stating the command exceeded its timeout, the session was forcibly restarted to terminate the process tree, and shell state was lost (with failure variants embedding the underlying error). Those two values are the two outcomes of the one kill path this product has — restarting the session succeeded, or it did not. Two further values, which named the kill path of a second terminal backend, are withdrawn together with that backend (REQ-TOOLS-100): no observation carries them and no consumer may expect them.

  > **Narrowed by [`PD-TOOLS-001`](../../product/directives/pd-tools-001.md#pd-tools-001), 2026-09-18.** The contract above
  > is untouched: the tree is still terminated, the session is still restarted, and the observation still
  > states that shell state was lost. The directive names one thing that happens *after* the restart: the
  > shell's working directory and exported variables, snapshotted before the respawn, are re-applied to the
  > fresh shell and named in the detail beside the loss. Aliases, functions and background jobs are not
  > restored.

**REQ-TOOLS-100** — Observation `failure_kind` values are exactly {`timeout`, `invalid_request`, `execution_error`, `sandbox_unavailable`}; `backend` is stamped on every observation and names the terminal backend that ran the command. Exactly one terminal backend ships, and the name it stamps is `single-session`. A second name this field once carried is withdrawn together with the pooled backend it described: nothing ever stated when that backend was used, what selected it, or whether it had to exist, it could not be provided on the platform whose shell REQ-TOOLS-104 mandates, and it was required to be observationally identical to the shipped backend in every respect but its own name. The field itself is deliberately kept rather than removed, so that adding a backend in a later release changes what this field says and not the shape of an observation; a consumer therefore reads `backend` as a name to record and report, and must not treat the single value shipped today as a closed vocabulary. Every observation carries a `[terminal_diagnostic]` JSON block (sorted keys, null-valued keys dropped) including backend, command, detail, error class, exit code, failure kind, kill status, outcome kind, outcome severity, output-truncated (only when the capture was truncated under REQ-TOOLS-097), session-reinitialized, timeout, timeout seconds, warnings, working directory, and session fields when applicable. Output captured before a hard timeout is labeled `[partial_terminal_output]` instead of `[terminal_output]`.

> **Narrowed by [`PD-TOOLS-013`](../../product/directives/pd-tools-013.md#pd-tools-013), 2026-10-07.** The `failure_kind` vocabulary also
> holds `interrupted`, carried by a foreground call its run cancelled before the command completed. The other four values
> and everything else above still govern.

**REQ-TOOLS-101** — Request validation failures return `invalid_request` observations (the fixed compatibility error class `ValueError`, independent of implementation language) for: `reset=true` with `is_input=true` (`Cannot use reset=True with is_input=True in the same terminal call.`); `background=true` with `is_input=true` or `reset=true`; `background=true` with an empty command (`A command is required when background=True.`); an unknown `session_action`; and `send_input` without `input_data`. `failure_kind` and outcome kind are the stable product codes. Schema-level refusals for these cases MUST preserve this diagnostic contract through the tool gate.

**REQ-TOOLS-102** — `reset=true` creates a fresh session before running anything. An empty command with reset returns a confirmation observation (text stating the session has been reset and all previous environment variables and session state cleared; command label `[RESET]`; exit code 0). With a command, the reset note is prepended and the command label becomes `[RESET] <command>`.

**REQ-TOOLS-103** — A terminal call always returns either an ordinary observation or a structured error observation. A failure of the terminal backend never surfaces to the agent as a partial or malformed observation, whatever the backend is (REQ-TOOLS-100) and however it failed. Any failure occurring before the command completes is returned as an `execution_error` observation whose detail states that terminal execution failed before completion and quotes the underlying error. The bounded recovery ladder this requirement previously fixed — a limited number of backend recoveries inside a rolling window, after which the call reported that the backend's server might be unreachable — is withdrawn with the pooled backend it belonged to (REQ-TOOLS-100): it described a recovery path only that backend had, and named a separate server the shipped backend does not run. What survives is the guarantee, which was never the ladder's: the agent's next observation is always well-formed and always says what went wrong.

**REQ-TOOLS-104** — On Windows the terminal runs commands through PowerShell rather than bash, and the tool description says so: it must warn that a bash heredoc never returns and that bash arrays, `[[ … ]]`, and `source` are unavailable, while stating that `&&`, `;`, `2>&1`, and `$env:VAR` work. Availability of this backend is decided solely by whether a supported PowerShell interpreter (`pwsh` or `powershell`) is present on the host, never by how quickly anything on the host responds: two hosts with the same software installed report the same availability whether idle or fully loaded, and a slow host is never reported as lacking PowerShell.

**REQ-TOOLS-105** — Visibility: an executing command is displayed as `$ <command>` in the status pane and as `terminal: $ <command>` in the transcript, with timeout/reset/input flags visible; the action's own rendering is `$ command [timeout: Ns] [reset terminal] [background] [session: id] [action]`.

**REQ-TOOLS-106** — The terminal tool must load and register successfully however the application process was started and whatever that process's own standard output and standard error are attached to — a console, a pipe, or nothing at all — and whether or not those streams report a character encoding. What the agent observes is identical in every one of those cases: the same tool surface and the same observations. A launch context in which the application's own streams carry no encoding information is never a reason for the tool to be missing from an agent's tool set (REQ-TOOLS-004), and never changes the encoding of anything the tool captures from a command it runs.

**REQ-TOOLS-187** — Foreground terminal concurrency is fixed by the shell session, not by the backend. Each terminal session runs at most one foreground command at a time: a second foreground call against a session whose previous foreground command has not returned waits for it, so a session's shell state (working directory, exported variables) is never mutated by two commands at once. Terminal sessions belonging to different agents run their foreground commands concurrently, bounded only by host resources. Because the rule attaches to the shell session and not to the backend, it does not vary with the value of `backend` (REQ-TOOLS-100): an observer given the same sequence of calls must see the same ordering, the same observations and the same shell state whichever backend ran them, so a backend added in a later release cannot change foreground concurrency and the backend name stays the only thing about an observation a backend gets to decide. Background sessions (section 11) are unaffected — they never occupy a terminal session and always run concurrently, up to `runtime.shell_max_background_sessions`.

### 11. Terminal Tool — Background Sessions

**REQ-TOOLS-107** — `background=true` spawns the command in its own OS subprocess (shell-interpreted; stdout and stderr merged to a pipe; stdin piped; working directory = the tool's working dir; its own process group on POSIX) and returns immediately with text `Background session started: <ts_XXXXXXXX>` plus the command, `session_status="running"`, and exit code 0. Session ids are `ts_` followed by 8 hexadecimal characters derived from the command and a monotonic timestamp, collision-checked.

**REQ-TOOLS-108** — Limits and defaults: maximum concurrent background sessions from `runtime.shell_max_background_sessions` (default 20, range 1–64 — the key, its default and its range are REQ-CONFIG-116's and are not restated here) — exceeding it is an `execution_error` reading `Maximum background terminal sessions (<n>) reached. Kill or wait for existing sessions before starting new ones.` Per-session wall-clock timeout defaults to `runtime.shell_background_timeout` (default 3600 s, minimum 1) unless the action supplies one. Output is buffered up to 1 MB per session and truncated silently from the oldest end, with the read cursor adjusted so polling stays consistent.

**REQ-TOOLS-109** — Background termination protocol: SIGTERM, then a grace wait of up to 5 seconds (returning as soon as the process exits), then SIGKILL. A background timeout sets status `timeout` and exit code 124; an explicit kill sets status `killed` and exit code −1. The status vocabulary is exactly {`running`, `completed` (exit 0), `failed` (nonzero), `killed`, `timeout`}.

**REQ-TOOLS-110** — Session actions: `query` (the default when `session_id` is set) returns only output new since the last poll (placeholder `(no new output since last poll)`) plus status and exit code; `kill` returns the final output; `send_input` writes bytes to stdin (result `Sent <n> byte(s) to session <id>.`; a closed pipe logs a warning); `send_signal` sends SIGTERM/SIGINT/SIGKILL/SIGHUP (default SIGTERM; result `Sent <sig> to session <id>.`); `list` needs no session id and returns an aligned text table plus structured entries `{session_id, command, status, exit_code, started_at (ISO-8601)}`, with a per-row status glyph (`▶`/`✓`/`✗`). An unknown session id yields `invalid_request` with `Unknown background session: '<id>'`.

> **Extended by [`PD-TOOLS-010`](../../product/directives/pd-tools-010.md#pd-tools-010), 2026-10-06.** `send_signal SIGINT` stops
> a background session whose command takes SIGINT's default: where the session's shell is `dash` on Linux, a
> SIGINT its fork window lost is sent once more to the command it cost. Every action above is unchanged.

**REQ-TOOLS-111** — Executor teardown MUST terminate its terminal-tool process trees, including background terminal sessions, and close every terminal resource it holds. Application shutdown and crash cleanup MUST apply that scope to owned terminal-tool processes. Hook descendants follow REQ-HOOKS-033's explicit survival exception; hook help MUST disclose that exception. Hook timeout and bounded-output collection remain governed by the hooks domain.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 3).** A pause does not end the background terminal sessions its agents started while the application stays open; a stop, a quit and a crash end them as stated.

### 12. Terminal Outcome Classification

**REQ-TOOLS-112** — Every terminal observation carries an `outcome_kind` from {`success`, `shell_failure`, `suspicious_success`, `soft_pause`, `timeout`, `invalid_request`, `execution_error`, `background_running`, `background_terminal`, `sandbox_unavailable`} and an `outcome_severity` from {`info`, `warning`, `error`}. The classification is decided by the following tests in order, the first one that applies deciding both fields:
1. a `failure_kind` is present — `timeout` → `timeout` / error; `invalid_request` → `invalid_request` / warning; `execution_error` → `execution_error` / error; `sandbox_unavailable` → `sandbox_unavailable` / error;
2. the observation reports a background session — status `running` → `background_running`, any terminal status of REQ-TOOLS-109 → `background_terminal`;
3. exit code −1 → `soft_pause` / warning;
4. a non-zero exit code → `shell_failure` / error;
5. exit code 0 with at least one output-derived warning from REQ-TOOLS-113 → `suspicious_success` / warning;
6. otherwise → `success` / info.

`background_running` always carries severity `info`: a session that is still running has reported nothing to be concerned about. `background_terminal` takes its severity from the session's final status of REQ-TOOLS-109 — `completed` → `info`, `killed` → `warning` (the agent or the user ended it deliberately, so it is neither a clean finish nor a fault), and `failed` or `timeout` → `error`. Severity therefore never asserts a problem the status does not report, and a background failure reads at the same severity a foreground failure of the same shape would.

**REQ-TOOLS-113** — Three independent checks run over the output of a command that exited 0. Each contributes at most one warning, and one or more warnings makes the observation `suspicious_success`:
- **Literal failure markers**, searched case-insensitively anywhere in the output, in this fixed order: `Traceback (most recent call last):`, `ERROR: file or directory not found`, `no tests ran`, `AssertionError`, `FAILED ` (the trailing space is part of the marker). The earliest marker in that order that is present produces the single marker warning, whose text names the marker that matched; further markers present in the same output add nothing.
- **A reported error count**: a line of the form `Found <n> error` or `Found <n> errors` where `<n>` is not zero, matched case-insensitively like the other two checks, so `found 3 errors` warns exactly as `Found 3 errors` does. `Found 0 errors` must not warn, in any casing.
- **A test-runner failure banner**: a line consisting of one or more `=` characters, then text, then one or more `=` characters, whose text contains `failed` case-insensitively.

Independently of exit code, a pipeline check adds the warning `Pipeline command may have hidden an upstream failure exit code.` when the command line contains `|` and the output contains, case-insensitively, any of `error:`, `failed`, `traceback`, or `no tests ran`. That warning is the only output-derived warning a non-zero-exit (`shell_failure`) observation can carry. Warnings are de-duplicated with the first occurrence keeping its position, and the resulting list appears both in the observation's `warnings` field and in the `[terminal_diagnostic]` block.
  > **Narrowed by [`PD-TOOLS-003`](../../product/directives/pd-tools-003.md#pd-tools-003), 2026-09-23.** Every check above still governs; the fifth marker, `FAILED `, matches case-sensitively — only `FAILED ` in capitals warns.

### 13. OS-Level Sandbox

**REQ-TOOLS-114** — The sandbox is opt-in per session: `runtime.sandbox_mode` ∈ {`off` (default), `workspace-write`, `read-only`}, case-insensitive. A YAML bare `off` parsed as boolean false is coerced to the string `"off"`. Unrecognized values are rejected at load and at assignment — never assumed off; the vocabulary and its validation are the ones fixed by REQ-SANDBOX-048. The desktop session dialog offers a per-session selector over exactly those three values, and a session started without touching it takes the configured value. There is no launch-time override of any kind.

**REQ-TOOLS-115** — Platform backends: macOS uses the system sandbox facility (backend name `seatbelt`); Linux and WSL2 use bubblewrap (backend name `bubblewrap`); native Windows has no backend and reports unavailable with remediation text directing the user to run inside a WSL2 distribution with bubblewrap installed, or to leave the sandbox off. Sandboxing is per-command wrapping of the command string; no containers are involved.

**REQ-TOOLS-116** — Writability model: `workspace-write` makes the workspace (or its active worktree) plus `runtime.sandbox_writable_roots` writable and the rest of the filesystem read-only; `read-only` makes nothing writable except temporary directories. `.git` and `.rotaris` stay read-only even when they sit inside a writable root, and no setting can turn that exclusion off — write access to either directory would let a run break out of, or quietly widen, its own confinement (repository hook scripts execute outside the sandbox; the configuration directory is what decides the sandbox's boundaries in the first place). Entries in `runtime.sandbox_writable_roots` must be absolute paths (POSIX or Windows spelling); a relative entry is rejected with `runtime.sandbox_writable_roots entry '<e>' must be an absolute path`.

**REQ-TOOLS-117** — Network inside the sandbox is closed by default; `runtime.sandbox_allow_network: true` opens it. The switch is binary — no per-host filtering for sandboxed terminal commands.

**REQ-TOOLS-118** — There is no silent fallback, structurally: if the sandbox cannot wrap a command, the command is not run. At session start, a session that requires an unavailable sandbox fails to start with reason and remediation; this is the canonical reading of the overlap with REQ-TOOLS-070, so the unavailable-at-start case never yields a running session. At command time, the terminal returns a `sandbox_unavailable` observation instead of executing, with exit code 126 ("found but could not be executed" — preventing the classifier from calling it a success) and detail `This session requires the OS-level sandbox, but the command could not be sandboxed and was therefore not run: <error>`. This refusal is not retryable into an unsandboxed execution path.

**REQ-TOOLS-119** — Sandbox availability is established by exercising the sandbox, never inferred from configuration: the check confirms the host platform, then the presence of the backend executable, then runs one throwaway command through exactly the wrapping that real commands go through. A trial is abandoned after 5.0 seconds. Only a clear success yields "available"; a timeout, an error, or a result that cannot be read yields "unavailable". Within one process the verdict never changes, and asking for it concurrently returns the same verdict as asking once. Three distinguishable reason-and-remediation pairs exist — unsupported platform, missing backend executable, and failed trial — and on Linux the failed-trial remediation names the kernel restriction on unprivileged user namespaces. Availability is established only by a real backend on a real host: a simulated, stubbed, or recorded backend never yields "available", and conformance to this requirement is demonstrated by running the trial, and a subsequent sandboxed command, end to end on each supported platform of REQ-TOOLS-115 rather than against a substitute.

**REQ-TOOLS-120** — Wrapping scope: only actions that introduce a new command string are wrapped — including `background=true` spawns (otherwise one flag would escape the sandbox). Keystroke input, empty output polls, and session-control actions (`list`/`query`/`kill`/`send_input`/`send_signal`) are not wrapped. `background` outranks `session_id` in both dispatch and wrap decisions, so supplying both cannot spawn unsandboxed. Retries wrap the original action exactly once — wrappers never nest.

**REQ-TOOLS-121** — The command echoed back in a sandboxed observation is the command string the agent supplied, not the wrapped form that was actually executed. The wrapper's own argument list (profile text, launcher flags) never appears in agent-visible output, so the agent cannot mistake wrapper mechanics for part of its own command and try to edit them on a retry.

**REQ-TOOLS-122** — Sandbox launch failures are re-labeled: an observation from a wrapped command with a nonzero exit, no prior failure kind, and output consisting only of sandbox-launcher-prefixed lines (`bwrap:`, `sandbox-exec:`, `sandbox_apply:`) is re-stamped `sandbox_unavailable` (error, with detail stating the sandbox failed to start so the command did not run and this is a host problem). Requiring every line to match the launcher prefix keeps failing test suites from reading as broken sandboxes. Background sessions receive the same re-read at `query`/`kill` time, since a spawn returns before the launcher can fail.

**REQ-TOOLS-123** — Sandboxed execution MUST keep standard temporary locations and basic device files usable in both modes. REQ-SANDBOX-077 owns protected-path preservation: confinement leaves the host's `.git` and `.rotaris` paths in their original state, including absence, and a backend unable to guarantee that preservation MUST refuse the command under REQ-SANDBOX-083. The command's working directory remains governed by REQ-SANDBOX-062/079; the confined invocation's shell-state lifetime is distinct from the unconfined persistent shell.

**REQ-TOOLS-124** — The sandbox specification is resolved afresh for each call, from the configuration belonging to the run that issued the call and from the conversation's actual working directory (worktree-aware). The "configured and available" verdict is reported identically by the session state snapshot (`sandboxed` flag and backend name), the workspace badge in the UI, and the `session.start` stream event's `sandboxed` field.

**REQ-TOOLS-125** — Sandbox status feeds the permission downgrade (REQ-TOOLS-067/070). The status is reported as a pair: an active flag, true only when the sandbox is both requested and proved usable, and a backend name, which is the backend's name when active and the empty string otherwise.
  > **Narrowed by [`PD-TOOLS-002`](../../product/directives/pd-tools-002.md#pd-tools-002), 2026-09-21.** The pair above still governs; it no longer feeds a downgrade — the status is recorded, and the mode is unaffected by it.
