## The tag workflow, the manifest, the signature and the key record — 2026-10-22, first execution (R-080; `first-release-plan.md` §4.2, §4.7, §4.8)

*REQ-STARTUP-027 to 035, 037, 038, 152, 167, 168; `PD-STARTUP-001`. Reported in place under the standing policy; row in
`../first-executions.md`; the plan's §4.2 note carries the stages.* The Decision's "the checksums manifest is generated by
the release pipeline from the emitted assets" and ESC-8's "the pipeline must know which keys the artifacts of every
still-offerable release carry" are built: `.github/workflows/release.yml` and `tools/release-pipeline/`
(`pnpm release:pipeline`). **What this record decided held as written.** Four things it left open were decided here:

1. **One verifier.** The pipeline does not read the signature format a second time. `verify` imports the updater's
   `verifyDetachedSignature` and `RELEASE_SIGNING_KEYS` from `apps/desktop/src/main/updater/keys.ts`, so what the gate
   decides is what an installed build will decide. Signing is Node's `crypto.sign` with Ed25519 over the manifest's exact
   bytes. Ed25519 is deterministic, so this is byte for byte the `openssl pkeyutl -sign -rawin` form "The updater" item 1
   names. The private key is read from `ROTARIS_RELEASE_SIGNING_KEY` and is never written to disk. OQ-83 is not ruled by
   this.
2. **The key record's form and its timing.** `tools/release-pipeline/key-record.json`, schema version 1: per release,
   the version and the `sha256:` fingerprints of the SPKI DER of each key its build carries. A release's own row is
   committed **before** its tag, and `preflight` refuses a build whose carried set differs from it. This record's "a
   record the pipeline has to keep deliberately" therefore cannot fall behind the builds it describes. `verify` then
   holds the signing key in every older row (REQ-STARTUP-168 (b)).
3. **A build with an empty key set is not releasable.** This record names no such refusal. `first-release-plan.md`
   §4.6 says "the release still compiles the key in". Before this execution, a tag on a tree whose set is empty would
   have built and shipped a product that could never update itself, and nothing would have refused it. `preflight`
   now refuses it in the guard stage, before any platform builds.
4. **The secret's exposure.** The signing job runs in the `release` environment, holds a read-only token and installs no
   dependency. The tool needs Node's own modules and two TypeScript files of erasable syntax, so no third-party install
   script runs beside the key. The one job with a write token creates the draft and holds no secret.

**Executed:** 64 unit cases in `tools/release-pipeline/`. Among them, `updater-agreement.test.ts` runs a release the
pipeline wrote and signed through `runInstall` and sees it installed, and runs one signed by a key the build does not
carry and sees it refused at the signature with nothing downloaded. `actionlint` 1.7.7 found nothing in either
workflow. **Not executed:** the workflow on a tag (R-080 forbids publishing). On `main` a tag would stop at the guard
for O-2. After O-2 it would stop at the notices step (O-3, O-11, OQ-74) and at the portable, whose launcher stub (P4)
is still unbuilt. The stub's spike needs a Windows x64 host, and the record's first-release plan schedules it as §4.5.
