# Model Providers, Sign-In, and Model Routing — Desktop Application Surfaces

Part 4 of 7 of [domain 04](../04-model-providers-auth.md), which indexes every part. Defines REQ-PROVIDER-116 – REQ-PROVIDER-130.

### Desktop Application Surfaces

- **REQ-PROVIDER-116** — Provider authentication dialog: window title "Authenticate <name>" or "Re-authenticate <name>" (minimum width 500). API-key flows show the instruction "Enter the provider API key. It will be validated with the provider's model catalog endpoint before it is saved." and a password-masked input; OAuth flows show "Start authentication. Rotaris will open or display the provider's official sign-in flow here." The confirm button is labelled "Authenticate"; the busy state disables it and shows "Authenticating and checking provider health…". Submitting an empty key → "API key is required." Cancel triggers a cancellation signal consumed by the sign-in flow to abort a pending device/PKCE wait early rather than waiting out the multi-minute timeout. Authentication runs off the UI thread; prompts open the system browser and render as rich text: device flow "Open <link> and enter code <code>."; PKCE "Your browser should have opened automatically. If it didn't, open this link to complete authentication:" followed by the link.

- **REQ-PROVIDER-117** — Add-provider dialog: a selector of "OpenAI-compatible endpoint (custom URL)" plus every built-in provider that is not authenticated, excluding Rotaris Cloud and the generic openai-compatible family. Selecting a built-in switches the dialog into "Authenticate" mode; custom mode collects an endpoint label, URL (default `https://api.openai.com/v1`), and API key (all required, each with its own "<field> is required." error), with button "Add endpoint" and busy text "Validating endpoint and discovering models…". A destination hint states where model traffic goes, derived from the catalog's connection mode: custom → "Custom endpoint — model traffic is sent to the base URL you enter below."; local-sdk → "Rotaris invokes the Claude Agent SDK installed locally; traffic goes through that SDK."; hosted-cloud → "Rotaris-managed cloud service — destination: rotaris.ai."; direct → "Direct provider API — <operator>, destination: <host>."

- **REQ-PROVIDER-118** — The desktop provider health check verifies the stored credential and then makes the provider's free catalog call, and reduces what it finds to one provider status. This domain declares no status vocabulary of its own and assigns no state: REQ-NOTIFY-200 is the product's single definition of the provider status indicator, and what this requirement relies on it for is the closed set of states, the condition that admits each, and the precedence applied where more than one condition holds. What this requirement supplies is the observations the check produces and the detail text each carries: the provider is the cloud provider the build marks unavailable, reported with availability false and the catalog's unavailability reason as detail (REQ-PROVIDER-043); the provider has no sign-in flow at all ("Authentication is managed by model configuration."); no credential is stored ("Not authenticated."); the stored credential is expired ("Authentication expired; re-authentication required."); the health check itself raised, the raised message being the detail; the catalog call was refused for authentication, which is exactly HTTP 401 or 403 (REQ-PROVIDER-071), that refusal being the detail; the catalog call failed for any other reason — a transport failure, a timeout, a server error, a malformed payload, or any other refused status — with the reported failure as detail; the catalog call succeeded, carrying the validation success message and refreshing that provider's stored catalog projection. Which observation holds is read from the outcome itself, so no status is ever decided by searching an error message for a phrase. Authenticating from the desktop runs the validated key update of REQ-PROVIDER-108 for API-key providers and, for OAuth providers, an optional sign-out first when re-authenticating, then interactive authentication, then validation; the first of those steps to fail ends the attempt, and its message is the detail of the returned provider status. Sign-out from the desktop has exactly the effect specified by REQ-PROVIDER-102.

- **REQ-PROVIDER-119** — Desktop subscription usage display: the Overview shows live subscription usage windows for each of {codex, copilot, claude-code} that appears as the sign-in provider (or provider) of any configured model. Fetches run concurrently (one worker per provider) so startup waits at most one provider timeout. Failure or missing authentication degrades to a fixed placeholder row per provider, each carrying a label, the used-label "Usage unavailable", a used percentage of 0, and a remediation detail: codex → "Codex usage" / "Sign in to Codex or retry when OpenAI usage data is available."; copilot → "Copilot plan allowance" / "Sign in to Copilot or retry when GitHub usage data is available."; claude-code → "Claude Code usage" / "Run 'claude setup-token' and sign in again, or retry when Anthropic usage data is available." The row stays visible in every case, so a provider never silently disappears from the Overview.

- **REQ-PROVIDER-120** — The Rotaris Cloud credit tile carries the card title "Rotaris Cloud credit" and has five renderings. Signed out: value "—", tag "Not signed in", detail "Sign in to Rotaris Cloud to see your credit.", and a "Sign in" button as the only control. Loading: value "…", tag "Checking…", detail "Reading your Rotaris Cloud balance.", refresh disabled; this rendering appears only when no balance has been shown yet — once a balance is on screen it stays on screen through every later read until a new value replaces it. Ready: the balance followed by "left", a tag naming the credit state returned by the backend, one of the four states `available`, `exhausted`, `overdrafted`, `unknown` (REQ-PROVIDER-130) — those four tokens are the machine-readable values, while the tag shows a distinct human-readable phrase per state, conveying respectively that credit is available, that it is used up, that the account is in overdraft, and that the backend reported a state this build does not recognize; the four phrases are distinguishable from one another by their text alone and their exact wording is left to the implementation — and a detail line of either "last call <amount>" or "No billed calls yet."; when the payload's admission-allowed flag is false the tile additionally shows the warning "! This account cannot pay for the next call. Runs on Rotaris Cloud models will fail until it is topped up." and an "Open Rotaris Cloud" button. Error: value "—", tag "Unavailable", detail "Rotaris Cloud credit could not be read.", the error text selectable, and the Refresh control relabelled "Retry". Which rendering is showing must be readable from the tag text and the outline shape alone: colour is never the only carrier of that distinction.

- **REQ-PROVIDER-121** — The credit balance is read once when the window opens, again every 120,000 ms (2 minutes) for as long as the window stays open, and whenever the user asks for a refresh. At most one read is outstanding at a time: a refresh asked for while a read is still running is declined and starts nothing, so no two reads overlap and no request is duplicated. The window stays responsive while a read is in progress. Amounts are computed and rendered in exact decimal arithmetic, never in binary floating point: a balance is rounded down (toward negative infinity), every other amount is rounded half-up, both to 2 decimal places, or to 4 when the magnitude is below $0.01. An amount that is not a balance, is greater than zero, and that this rounding would render as zero renders instead as the floor `< 0.0001`, so a small non-zero amount is never rendered as zero; zero itself renders `0.00`, and a balance and a negative amount are rounded as above and never floored (accepted amendment 2026-09-29, ESC-42). The currencies USD, EUR, and GBP render with the symbols $, €, £; any other currency renders as "<amount> <CODE>", and the floor takes the same placement, `< $0.0001` and `< 0.0001 <CODE>` (accepted amendment 2026-09-29, ESC-42). This is the one money rule for this domain: every monetary amount the domain computes or displays is produced under it, including the per-token pricing carried through discovery (REQ-PROVIDER-072) and any image pricing a model entry declares (REQ-PROVIDER-150). No amount is computed in binary floating point anywhere.

  > **Narrowed by [`PD-MONITOR-001`](../../product/directives/pd-monitor-001.md#pd-monitor-001), 2026-09-16.** The arithmetic
  > rule is untouched and is the reason that directive exists: a cost the provider reported is **added** to a
  > run's total in exact decimal arithmetic and never multiplied, which is what let one branch of OQ-62 be
  > ruled while the three that multiply a rate stay blocked on OQ-21. What is narrowed is the currency table:
  > an amount a provider reports **without naming a currency** renders as the amount alone, under the rounding
  > above, rather than under a symbol or a code the product chose for it. Since revision 3 (2026-09-29, ESC-42) that rounding
  > includes the floor: such an amount greater than zero that would read as zero renders bare, `< 0.0001`.
  >
  > **Revision 2, 2026-09-23.** The arithmetic rule now also governs a multiplication: a configured per-token
  > price times a whole token count, computed exactly, for a request the provider did not price.

- **REQ-PROVIDER-122** — Cloud-billing awareness is active when ANY of the small/medium/large slots, the active model, or the session model override resolves to a model whose sign-in provider is `concrete-cloud` (a delegating run's children spend the same balance). The desktop tracks a temporary session model override distinct from the persistent slots; the desktop composer command `/model <name>` sets it (REQ-PROVIDER-146). Precedence is fixed here and applied by the run-orchestration domain: while a session model override is set it outranks both the active model and the persistent slot value for every call it covers; clearing it restores the persistent value and has no other effect; it is never written to `.rotaris/agents.yaml`, never merged into the snapshot, and never outlives the session that set it.

- **REQ-PROVIDER-140** — Provider list. The desktop presents one list of providers, and it is the single place a provider's identity and credential state are read. The set listed is the union of the ids holding a stored credential, the built-in catalog ids, and the snapshot ids, each appearing exactly once, ordered by id. Each row shows: the display name and the id; the sign-in method label of REQ-PROVIDER-148, or the statement that authentication is managed by model configuration when the provider resolves to no method; whether the provider is authenticated; the masked form of the stored key (REQ-PROVIDER-107) when a key is stored and nothing at all when none is; the base URL when one is stored or defaulted for it; and the provider health status of REQ-PROVIDER-118. Where a provider's models are shown beneath it, each model row carries the image-input declaration of REQ-PROVIDER-149. The masked form is the only rendering of a stored key anywhere in the interface (REQ-PROVIDER-131). Every row and every control within it is reachable and labelled at the minimum window size (REQ-SHELL-022), and no state a row conveys is carried by colour alone (REQ-SHELL-149).

- **REQ-PROVIDER-141** — Provider settings. Selecting a provider from the list of REQ-PROVIDER-140 opens its settings, which offer exactly these actions, each named from the one action vocabulary of REQ-SHELL-048: save, validate, re-authenticate, sign out, and — for a user-defined `openai-compatible--*` instance only — delete. The settings carry a masked API-key field, enabled only when the provider's method is `api-key` (REQ-PROVIDER-148) and stating that leaving it empty keeps the current key, and a base-URL field. Saving stores a new key only when the field is non-empty and discovery validated it (REQ-PROVIDER-108); an API-key provider that has no stored credential and an empty key field is refused, stating that a key is required and naming the provider; the base URL is written only when its value changed, and a changed base URL re-runs discovery against the new base when a key is stored, then updates both the credential's `api_base` extra and the snapshot's base URL. Skipping validation on a save is an explicit opt-in the user must make, and is one of the exceptions named in REQ-PROVIDER-133. Any failure reports an error and leaves the settings open with nothing written; success reports that the settings were saved. Validate re-runs discovery for a provider that has stored credentials, persists the models on success, and reports the provider and the number of models discovered; it refuses a provider with no stored credential, stating that it is not authenticated. Re-authenticate on an API-key provider moves focus to the key field and states that a replacement key must be entered and saved; on any other provider it signs out and then runs interactive authentication in place (REQ-PROVIDER-096, REQ-PROVIDER-116), reporting either that the provider was re-authenticated or the provider's error. Delete requires a confirmation that names the instance and states that workspace model references will not be changed — declining leaves everything untouched — and then applies REQ-PROVIDER-055. Closing the settings while a validation or re-authentication is still running neither loses the window nor blocks it, and the closed surface raises no further notifications. Every action here leaves the window responsive to input within 100 ms, the work itself running off the interface thread.

- **REQ-PROVIDER-142** — Sign-in and provider chooser. The desktop offers a sign-in action, reachable from the provider list (REQ-PROVIDER-140) and from the add-provider dialog (REQ-PROVIDER-117), which runs the flow of REQ-PROVIDER-096 for one provider, optionally with re-authentication forced, and against a named workspace when the flow needs one (REQ-PROVIDER-063). Started without a provider already chosen, it presents the provider chooser: all six catalog providers in catalog order (REQ-PROVIDER-001), the codex entry branded per REQ-PROVIDER-036, and any entry the build marks unavailable shown as coming soon and not selectable for sign-in. Reaching such an entry by any route fails before any authentication, with the catalog's unavailability reason (REQ-PROVIDER-006) as the reported cause, and is recorded as a failed sign-in. Dismissing the chooser cancels the sign-in, which is reported as cancelled and stores nothing. A request naming an id that is neither in the catalog nor a known instance is refused, naming the id that was asked for. The outcome — signed in, with the provider and the number of models discovered (REQ-PROVIDER-099); cancelled; or failed with the provider's error — is reported to the user, and no process exit status is exposed anywhere.

- **REQ-PROVIDER-143** — Sign-out action. The desktop offers a sign-out action for one provider, reachable both from that provider's settings (REQ-PROVIDER-141) and on its own. Invoked without a provider already chosen, it offers only those providers holding a stored credential at that moment, each labelled with its catalog display name, or with its snapshot display name and its id for a user-defined instance, or with its bare id when neither is known; when no provider holds a credential it states that none is signed in and offers nothing to confirm. Dismissing it cancels and changes nothing. Sign-out applies REQ-PROVIDER-102 and reports that outcome. Signing out is an action of its own: it never carries a task, and it never starts, resumes, or interrupts a run.

- **REQ-PROVIDER-144** — Startup model assignment editor. The desktop provides one editor over persistent model assignments: a table whose rows are, first, the seven startup slots of REQ-PROVIDER-088 and then one row per persona, sorted, each row showing its target, its scope (startup or persona), its selection, and its thinking level. An unset slot is shown as unset. A persona row that inherits shows the default it inherits and the model that default resolves to; a persona row pointed at a tier alias shows the alias with its resolved model, or the alias with the fact that the slot is unconfigured (REQ-PROVIDER-088). The thinking column shows the level, or states that the provider or endpoint decides. Choosing a model opens the picker of REQ-PROVIDER-145; changing the model re-derives that row's legal thinking choices from the shipped model-capability metadata (REQ-PROVIDER-137) and resets a now-illegal thinking value to unset. Saving writes `.rotaris/agents.yaml` and reports the path written; a write failure is reported as an error naming the file and the underlying cause, and leaves the editor open with the user's choices intact. The same editor serves onboarding, under a heading that frames it as a review of the assignments and with a save-and-continue action in place of a plain save.

- **REQ-PROVIDER-145** — Model picker. The model picker presents the models a target can be pointed at. It carries a header reporting authentication across the provider catalog: either that every catalog provider is authenticated, or one entry per provider that is not, naming the provider and directing the user to the sign-in action for it (REQ-PROVIDER-142). Such a hint SHALL NOT name a command of any kind, and in particular SHALL NOT direct the user to a third-party command-line tool, because the credential this product uses for a provider is the one the product's own sign-in flow mints (REQ-PROVIDER-024). A picker opened for a persona shows fixed rows ahead of the model rows: an inherit-the-default row naming the default and the model it resolves to, then one row per tier alias — `small_model`, `medium_model`, `large_model` — each showing the alias with its resolved model, or the alias with the fact that its slot is unconfigured. Models already present in configuration are listed as soon as the picker opens, with configuration named as their source; each provider's live catalog is fetched separately, that provider showing as still loading until its result arrives and then adding or updating rows. Every model row shows the image-input declaration of REQ-PROVIDER-149. When loading settles the picker reports how many runtime models were loaded followed by any per-provider errors, or states that no runtime models are available when no row was produced. A refresh action re-fetches the live catalogs, discarding only the rows those catalogs contributed and leaving the fixed rows and the configuration rows in place. Confirming a row selects it; dismissing the picker changes nothing.

- **REQ-PROVIDER-146** — Runtime model override selection. The desktop provides a temporary per-run model override, opened by the composer command `/model` and by an action on the run's own surface. It lists the provider catalogs of configured and authenticated providers, showing that catalogs are loading and then reporting how many runtime models were loaded together with the first error when there was one, or stating that runtime model selection is unavailable and why when no catalog could be loaded. Confirming a row selects that provider, model, qualified id, and limits; a row that carries no available model says so and selects nothing; a reload action re-fetches the catalogs; dismissing cancels. The selection applies to the current session only, takes the precedence fixed by REQ-PROVIDER-122, and is never written to `.rotaris/agents.yaml`.

- **REQ-PROVIDER-147** — Catalog refresh action. The desktop offers a catalog refresh that re-syncs discovered models without re-authenticating, for one provider or for all of them. Bulk refresh targets every catalog and snapshot provider and silently skips the unauthenticated ones. Refreshing one provider that is not authenticated is not silently skipped: it reports that the provider was skipped because it is not authenticated, directs the user to sign in to that provider (REQ-PROVIDER-142), and counts as a failure rather than as a skip. Targeting an id that is not known reports the id asked for and the known ids. While it runs it reports which provider is being refreshed, and reports each success with the provider and the number of models discovered, together with the number of previously known models preserved (REQ-PROVIDER-083) whenever any were. When it finishes it reports each non-zero count — providers succeeded, providers failed, providers skipped as not authenticated — omitting any count that is zero, and states plainly whether the refresh completed with nothing failed and nothing skipped or finished with failures or skips. The skipped count covers bulk-mode skips only, never a provider the user targeted explicitly. Number agreement and exact wording are left to the implementation. A refresh never blocks the window, which stays responsive to input within 100 ms while it runs.

### Subscription Usage Endpoints and Rendering

- **REQ-PROVIDER-123** — Subscription-usage fetching supports exactly the providers codex, copilot, and claude-code; any other provider yields an empty result. The default HTTP client uses a 5-second timeout and follows redirects. All failures raise a dedicated usage error type; callers degrade to placeholders and nothing is retried at this layer.

- **REQ-PROVIDER-124** — Codex usage: `GET https://chatgpt.com/backend-api/wham/usage` with the OAuth bearer, `User-Agent: codex-cli`, and a `ChatGPT-Account-Id` header when an account id is stored. The payload's primary and secondary rate-limit windows are read in that order; a window that is absent, or whose used-percent value is missing, non-numeric, boolean, or not finite, is skipped rather than failing the whole read; a usable percent is clamped into 0–100 and rounded to an integer under the rounding rule of REQ-PROVIDER-127. Labels resolve by the window's declared length in seconds: 18,000 → "Codex 5-hour window"; 604,800 → "Codex weekly window". When the length is absent or matches neither value, the window keeps the label its position implies — "Codex 5-hour window" for the primary window and "Codex weekly window" for the secondary one. Rendering: the used label is "<n>% used"; the detail is "<100−n>% remaining[ · resets <relative>]" where the reset comes from an absolute reset timestamp or a reset-after-seconds value. No usable windows → errors "Codex usage response contains no rate-limit windows" / "... no usable windows".

- **REQ-PROVIDER-125** — Copilot usage: `GET https://api.github.com/copilot_internal/user` authenticated with the stored GitHub `ghu_` token (the credential's refresh-token field; the short-lived model bearer minted by the session exchange is not accepted here, so it is never sent — a missing `ghu_` token errors "Copilot GitHub token is unavailable"), with headers `User-Agent: GithubCopilot/0.28.0` and `Copilot-Integration-Id: vscode-chat`. The quota snapshot with id "premium_interactions" is selected. One label is used for that snapshot whatever billing arrangement the account is on: it conveys that the figure is the Copilot premium-request allowance for the signed-in account, and its wording is left to the implementation. No payload field selects between alternative labels, and the read never branches on a billing kind. A quota flagged unlimited renders as a single row labelled "Unlimited" with 0% used and the detail "No plan allowance cap". Otherwise both an entitlement and a remaining-quota value must be present, and their absence fails the read with "Copilot plan allowance is incomplete". The used label reports the used amount against the entitlement as "<used> / <entitlement>", where used = entitlement − remaining and both numbers are written with thousands separators and without trailing fractional zeros. The used percent is 100 minus the payload's reported remaining percent when it reports one, and otherwise (entitlement − remaining) ÷ entitlement × 100; either way it is clamped into 0–100 and rounded to an integer under the rounding rule of REQ-PROVIDER-127. The detail is "<n>% remaining[ · resets <Mon D>][ · <n> overage]", where the reset date comes from the UTC quota-reset-date field when present and from the plain one otherwise, and the overage clause appears only for a non-zero overage count.

- **REQ-PROVIDER-126** — Claude Code usage: `GET https://api.anthropic.com/api/oauth/usage` with the subscription OAuth bearer plus headers `anthropic-beta: oauth-2025-04-20` and `anthropic-version: 2023-06-01` (no API key involved; not billed against the API). Windows: `five_hour` → "Claude Code 5-hour window"; `seven_day` → "Claude Code 7-day window"; each carries a utilization percent and an ISO-8601 reset timestamp; rendering matches codex ("<n>% used", "<m>% remaining · resets <relative>"). No usable windows → "Claude Code usage response contains no usable windows".

- **REQ-PROVIDER-127** — Reset-label formats: under 60 seconds → "in <1m"; then "in Xd[ Yh]", "in Xh[ Ym]", "in Xm". Calendar reset labels render "<Mon> <day>" (e.g. "Feb 3"). Percentages clamp to 0–100 and are then rounded half-up to a whole number — the same direction the money rule of REQ-PROVIDER-121 uses for every amount that is not a balance — so a value exactly halfway between two integers rounds away from zero. That single rule governs every percentage this domain displays. Numeric parsing accepts integers, floats, and comma-grouped numeric strings; booleans are rejected.

### Rotaris Cloud Account Credit

- **REQ-PROVIDER-128** — Credit reads perform `GET <api_base>/account/usage-status`, where the API base comes from the stored credential's `api_base` extra, falling back to the catalog default so a credential stored without that extra still works; an unusable stored base errors "Rotaris Cloud API base is unusable: <base>". Headers: the bearer plus `User-Agent: rotaris/account`; timeout 5 seconds.

- **REQ-PROVIDER-129** — The blocking account-status read: with no stored cloud credential it fails with a DISTINCT sign-in-required error ("Not signed in to Rotaris Cloud") whose meaning is "sign in", not "retry". Before reading, it puts the stored credential through the standard token fetch so an access token whose lifetime elapsed during a long-running session is renewed rather than reported as a rejected credential; that step fails with the recorded authentication error or "Rotaris Cloud sign-in has expired". HTTP 401/403 → "Rotaris Cloud rejected the stored credential; sign in again."; other HTTP errors → "Rotaris Cloud account request failed (<status>)" / "... failed"; a non-object body → "... response is not an object".

- **REQ-PROVIDER-130** — Credit payload contract: a required credit object (missing → an error stating the response "carries no credit block") with an atomic balance and an atomic scale — balance = atomic ÷ scale computed in exact decimal arithmetic, never in binary floating point (a non-number → "Rotaris Cloud credit balance is not a number", a non-positive scale → "... scale is not positive"); a state mapping to available | exhausted | overdrafted with unknown values degrading to "unknown" (forward compatibility: a new backend state must not break installed clients); an admission-allowed boolean (default false); an optional currency code (upper-cased, default "USD"); and an optional latest-settled-usage record (ISO-8601 occurrence time, status, cost) — a partially unusable usage record is dropped rather than failing the whole reading, so the balance still renders.
