# Application Startup, Distribution, and Updates — Data & Formats

Part 9 of 10 of [domain 11](../11-startup-distribution-updates.md), which indexes every part.

## Data & Formats

All formats below are externally observable (on disk, on the wire, or in process output).

- **Release tag grammar** (REQ-STARTUP-027): `v<major>.<minor>.<patch>` with optional `a<N>` / `b<N>` / `rc<N>` suffix. Plain versions are `stable`; suffixed are `prerelease` (REQ-STARTUP-029); ordering is REQ-STARTUP-109's.
- **Release artifact names** (single authority, REQ-STARTUP-031): `Rotaris-{v}-windows-x64-setup.exe`, `Rotaris-{v}-windows-x64-portable.exe`, `Rotaris-{v}-macos-arm64.dmg`, `Rotaris-{v}-linux-x86_64.AppImage`. There is no console-archive kind.
- **Checksum manifest** `SHA256SUMS.txt` (REQ-STARTUP-032, parsed per REQ-STARTUP-113): `"<sha256hex>  <filename>\n"` per asset, two-space separator, sorted by filename, `sha256sum -c` compatible, never self-listed, and never listing the signature published over it.
- **Manifest signature** `SHA256SUMS.txt.sig` (REQ-STARTUP-032, REQ-STARTUP-167): a detached signature over the manifest's exact published bytes, published as an asset of the same release, absent from the manifest and from the release-body asset table (REQ-STARTUP-035), and verified before the manifest is parsed (REQ-STARTUP-122). Every published artifact carries within itself the set of keys it accepts; that set is fixed when the build is produced and nothing at run time adds to, replaces, or disables it (REQ-STARTUP-167, REQ-STARTUP-168). The form of a key, the form of a signature, and how many keys a build carries are implementation choices and no surface of the product reports them.
- **Release feed consumption** (GitHub latest-release JSON): fields consumed are `tag_name`, `draft`, `prerelease`, `body`, and `assets[]` entries' `name`, `browser_download_url`, and integer `size` (0 when absent). Asset downloads follow a 302 redirect to a storage host.
- **Windows installer surface**: silent flags `/S` and `/D=<dir>`; per-user registry writes under `HKCU\Software\Rotaris` (`InstallDir`) and `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` (`DisplayName`, `DisplayVersion`, `Publisher`, `DisplayIcon`, `UninstallString`, `NoModify`, `NoRepair`); Start Menu folder `Rotaris` with `Rotaris.lnk` and `Uninstall Rotaris.lnk`.
- **Linux desktop entry**: `Type=Application`, `Name=Rotaris`, `Terminal=false`, `Categories=Development;IDE;`, Exec accepting an optional path argument, named icon.
- **Single-instance record** (REQ-STARTUP-161, REQ-STARTUP-164): one record per user account, outside every workspace and outside the desktop preference store, in the per-user location REQ-STARTUP-145 fixes, naming the process that is currently the running instance and how a launch reaches it. Its form and its placement within that location are implementation choices; the observable contract is that a launch either claims it and becomes the instance or is handed to the instance it names, that a launch waits at most 5 s for a hand-over that goes **unanswered**, and that at most one reclaim and two claim attempts occur before the launch ends. The 5 s bounds an unanswered hand-over and not a refused one: an instance that answers by refusing because it is shutting down stops that interval running at all, and the launch then waits for the shutdown instead, bounded by the force-exit allowance rather than by this figure (REQ-STARTUP-164, REQ-SHELL-169, REQ-MONITOR-131). No configuration key and no environment variable affects it (REQ-STARTUP-146, REQ-STARTUP-147).
- **Launch preparation** (REQ-STARTUP-165): where a `onefile` artifact prepares itself for launching, the preparation is held in the per-user data directories of REQ-STARTUP-145 — which that requirement fixes as the machine-local, non-replicated per-user location — and never beside the artifact or on the medium carrying it; it belongs to exactly the artifact contents that produced it, so a new or rebuilt artifact prepares afresh; an incomplete, unreadable, or foreign preparation is silently redone rather than reported, while a run that produces no usable preparation at all still starts, is exempt from the first-paint bound, and raises a persistent warning notice — the one preparation outcome reported anywhere — putting what it must run in a run-scoped placement that is removed when the run ends and that may lie only in those same per-user data directories or, where they accept no write at all, in the platform's per-user transient storage; it is produced from the artifact alone with no network request and no elevation; and it is not a published artifact — it never appears in `SHA256SUMS.txt`, never in the artifact set of REQ-STARTUP-031, and never as a download. Its form, its name, and its location within that storage are implementation choices. The update target stays the artifact the launch started from and is never the preparation (REQ-STARTUP-106, REQ-STARTUP-125).
- **Workspace-storage classification** (REQ-STARTUP-166): a workspace resolves to exactly one of three states — reachable by another machine, replicated by a file-synchronisation agent, or not classifiable. The first two raise a persistent warning notice and refuse nothing; the third is silent. The classification is derived from storage rather than from a failure, is not persisted anywhere, and adds no key to the desktop preference store (REQ-STARTUP-146).
- **Per-user setup layout** (under the per-user data directory of REQ-STARTUP-145, which is the machine-local, non-replicated one): `tools/<tool>/<version>/` (managed tool trees), `setup/state.json` (durable record, schema 1 — fields in REQ-STARTUP-071, of which `outcome`, `completed_at` and `versions` are fixed names shared with REQ-CONFIG-397), `setup/setup.lock` (transient JSON `{pid, created}`), `setup/cache/{downloads,uv,npm}/`. Partial downloads appear as `<name>.partial` beside their cache destination and stay eligible for resumption indefinitely (REQ-STARTUP-084).
- **Setup manifest** (schema 1, REQ-STARTUP-058, REQ-STARTUP-059, REQ-STARTUP-061): per-tool probe command and version args, optional minimum version, provisioned version, per-platform-key artifacts (HTTPS URL, 64-hex SHA-256, layout, expected executables), license, capabilities; plus exact MCP package pins. Fingerprint = SHA-256 over canonical JSON (sorted keys, compact separators).
- **Setup outcome vocabulary**: `complete` | `degraded` | `cancelled` | `already-running` (REQ-STARTUP-074); the first three, plus `running` and empty, are also the values persisted as `outcome` in the durable record. There is no textual output contract carrying them: they are rendered in the setup dialog (REQ-STARTUP-093), the settings card (REQ-STARTUP-102) and the per-step surface (REQ-STARTUP-153).
- **Persisted settings**: the desktop preference store REQ-SHELL-006 defines. Its scoping, its closed key table, and its on-disk form are stated there and are not restated here. The keys whose meaning this domain owns are `workspace/lastOpened` (string path) and `updates/dismissedVersion` (single version string), both registered in that table (REQ-STARTUP-146); `diagnostics/level` and `diagnostics/outputDir` are read from the same store and owned by REQ-SHELL-163.
- **Diagnostics run directory** (REQ-STARTUP-131, REQ-STARTUP-132): `<base>/<UTC yyyymmddTHHMMSSZ>-<pid>/` containing `manifest.json` (schema 3, self-checksummed), `metrics-NN.jsonl` and `spans-NN.jsonl` (rotating, 8 MiB × 4 each, REQ-STARTUP-133), `snapshots/NNNN-<reason>.json` (16 MiB total budget, REQ-STARTUP-133), `summary.json` (schema 3, REQ-STARTUP-137) and `summary.md`. JSON-lines readers tolerate a truncated final line (REQ-STARTUP-138).
- **Environment variables**: read — `APPIMAGE`, `ROTARIS_BUNDLED`, `COMSPEC`, and on a platform whose artifact form publishes one, the variable naming the artifact file a launch started from (REQ-STARTUP-147); written for children — `PATH`/`Path`, `UV_CACHE_DIR`, `npm_config_cache`. No environment variable configures diagnostics or the update check (REQ-STARTUP-129, REQ-STARTUP-111); a variable naming the artifact decides only which file an update replaces.
- **Key behavioral constants.** Every figure listed here is fixed by the requirement named beside it and restated here for convenience only; where this list and that requirement differ, the requirement governs. Three classes of figure are deliberately not among them, because this document states none of them and only cites them: the deferred first-paint delay, stated once by REQ-SHELL-011 and cited per REQ-STARTUP-044; the minimum window size and what must hold at it, stated once by REQ-SHELL-022 and cited per REQ-STARTUP-042; and every figure of the transient acknowledgement surface — its lifetime, its bounded width and its placement — stated once by REQ-NOTIFY-011, REQ-NOTIFY-013 and REQ-NOTIFY-012 and cited per REQ-STARTUP-054. The list: first paint within 5 s of launch — with the single first-run exemption REQ-STARTUP-155 states for a `onefile` artifact preparing itself, "first run" meaning the first run of that artifact version on a machine for that user (REQ-STARTUP-165) — and the empty-plan fast-path decision within the interface-responsiveness budget (REQ-STARTUP-155); single-instance hand-over wait 5 s, with at most one reclaim and two claim attempts (REQ-STARTUP-164); update-check timeout 10.0 s (REQ-STARTUP-105); update download/hash chunk 1 MiB (REQ-STARTUP-124); installer-hand-off auto-close 1200 ms (REQ-STARTUP-119); update-worker shutdown join 5000 ms (REQ-STARTUP-046); tool probe timeout 10 s (REQ-STARTUP-063); warm-up timeout 180 s (REQ-STARTUP-076); tool download connect timeout 30 s with 1 MiB blocks (REQ-STARTUP-084); setup lock staleness 900 s (REQ-STARTUP-072); banner summary limit 160 chars (REQ-STARTUP-112); setup dialog 760×560 (REQ-STARTUP-090); diagnostics 250 ms heartbeat, 1000 ms metric sampling, 300 s deep-mode interval, 2.0 s tracing window and 1.0 s slow threshold (REQ-STARTUP-133); diagnostics 1000 ms lag trigger, 60 s trigger cooldown, 256 MiB memory-growth trigger and 8-thread growth trigger (REQ-STARTUP-135); diagnostics 1 s close join (REQ-STARTUP-139); notices-exception expiry at most 365 days after review (REQ-STARTUP-143).
- **Diagnostics file layout**: field names and nesting are implementation-chosen and stable within a schema version; units are fixed — milliseconds for durations, bytes for memory and written volume, bytes per second for rates, whole numbers for percentages, ISO-8601 UTC for timestamps (REQ-STARTUP-157).
- **Exit codes**: pipeline only; see REQ-STARTUP-149. The application defines none.
- **Application entry**: one graphical entry point (REQ-STARTUP-002), and at most one running instance of it per user account (REQ-STARTUP-161) — a launch either becomes that instance or is silently handed to it, and several workspaces and several windows are windows of the one instance (REQ-STARTUP-162, REQ-STARTUP-163). The one directory a launch may carry is the workspace the operating system hands it (REQ-STARTUP-024, REQ-STARTUP-041); there is no argument vocabulary, no subcommand, no flag, no standard-output contract and no text-mode interface; the one reserved token `builtin:code-intelligence` is a sentinel for a child process the product starts itself (REQ-MCP-033, REQ-STARTUP-015).
