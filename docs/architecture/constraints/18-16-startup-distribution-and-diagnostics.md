# Architectural constraints extracted from the specification — 16. Startup, distribution and diagnostics

## 16. Startup, distribution and diagnostics

| # | Constraint | Label | Requirements |
|---|---|---|---|
| B-01 | The startup order is fixed and observable, with four steps **before any window exists**; **constructing a window without showing it must produce no network traffic**. | HARD | REQ-STARTUP-040, REQ-STARTUP-043, REQ-SHELL-015, REQ-WORKSPACE-014, REQ-WORKSPACE-141 |
| B-02 | **One shared deferred first-paint delay** serves every deferred offer, and the deferred workspace prompt is a one-shot abandoned unshown if already answered. | HARD | REQ-SHELL-011, REQ-STARTUP-044, REQ-WORKSPACE-008 |
| B-03 | First paint within **5 seconds on every published artifact and every bundle mode, with no per-flavour differential** — **and now exactly one exemption, which the requirement states and closes**: the run of a `onefile` artifact that performs its own preparation, and no other artifact, bundle mode or run. *Measured, and this row is why SR-7 exists: the `onefile` portable produced by the packaging tool's own target reached first paint in **13,287–19,580 ms** across four bundle weights **including a zero-payload build**, with no available setting closing the gap (deflate 7,433 ms; uncompressed 5,307 ms and a half-gigabyte "single executable file"). The same payload as an installed directory tree paints in **664–1,561 ms**, and 1,232–1,593 ms from a path never launched before. So the flavours that pass leave the product roughly **3.4–4.4 s** of the budget for everything ADR-0055 puts in front of first paint, which is a real budget and not a generous one. Not measured, and binding: the macOS `.dmg` and the Linux AppImage were not built.* ***The exemption's own arithmetic is now measured and SR-7's gate condition is met (2026-09-02).*** The **cached** launch of a prepared `onefile` portable is **575.5–723.1 ms warm and 897.3–1,242.5 / 964.0–1,414.6 ms cold** across two independent replicates, against 5,000 ms; the **exempt preparing** run lands **inside the bound it is exempt from** at 1,634.7–2,091.3 ms warm, and 3,798.8–3,909.8 ms when restricted to one core; and the fast-path version check costs **0.14–0.49 ms warm, 0.37 ms on a cold first touch**, against 709.6–845.0 ms for the cheapest launch-time digest of the artifact and 4.43–5.50 s for a digest of the prepared tree. **So the portable stops being a special case**: packaging and runtime consume 0.58–1.41 s of the 5,000 ms, against 0.66–1.56 s for the installed flavour, leaving the same order of headroom — and B-03's "no per-flavour differential" is met by construction rather than by argument. **Two qualifications the headline loses and this row must not:** the measured application contains **no product at all** — no framework, no store, no native module, no preload, no theming, and none of `REQ-STARTUP-040`'s icon, font registration or theme restore — and the clock starts at process creation from a parent rather than at a double-click, so **every figure here is a lower bound and the 3.6–4.4 s of apparent headroom is what ADR-0055's whole sequence must fit inside.** *One figure this record repeatedly mis-attributed:* the 13,287–19,580 ms above is the **packaging tool's** extraction cost, not this mechanism's — the launcher writes the same 507.9 MiB tree in 410.7–565.7 ms — so anywhere the record prices the preparing run in tens of seconds it is quoting the wrong number. | HARD | REQ-STARTUP-155, REQ-STARTUP-165, REQ-STARTUP-040; `spikes/packaged-first-paint.md` §5, §9; `spikes/cached-portable-launch.md` §4, §5, §6, §14, §15 |
| B-04 | **Four published artifacts and no others**, from a single naming authority; one single-file artifact; per-user Windows install with no elevation; a stated distribution baseline. | HARD | REQ-STARTUP-013, REQ-STARTUP-014, REQ-STARTUP-016, REQ-STARTUP-020, REQ-STARTUP-022, REQ-STARTUP-024, REQ-STARTUP-031 |
| B-05 | Binaries are **deliberately unsigned and un-notarized**, and the platforms' warnings are expected and disclosed. | HARD | REQ-STARTUP-021, REQ-STARTUP-023 |
| B-06 | The update check contacts **exactly one endpoint**, once per window activation, only after the window is visible, and **cannot be disabled by any user-reachable means** — with the acceptance criterion stated over four closed configuration enumerations. | HARD | REQ-STARTUP-105, REQ-STARTUP-111, REQ-STARTUP-114, REQ-STARTUP-152 |
| B-07 | Asset selection is **exact-name matching only**; verification is against a published checksums manifest, never self-listed; a release with no manifest is refused as unverifiable; **no signature is verified**. | HARD | REQ-STARTUP-032, REQ-STARTUP-108, REQ-STARTUP-113, REQ-STARTUP-123 |
| B-08 | **Every** filename a release publishes, its manifest lists, and the client asks for are values of **one** naming scheme and must agree. | HARD | REQ-STARTUP-035, REQ-STARTUP-152 |
| B-09 | **Four apply strategies selected by installation flavour, not by operating system**, each with a fixed observable result, including one platform where **the installed bundle is left byte-for-byte unchanged and never replaced automatically**. | HARD | REQ-STARTUP-115, REQ-STARTUP-119, REQ-STARTUP-125, REQ-NOTIFY-220 |
| B-10 | **Not one file of the existing installation is moved or modified before the replacement has been fetched in full and verified.** | HARD | REQ-STARTUP-126 |
| B-11 | **Re-derived, and the difference is the whole preparation trap.** Flavour classification and the update target are **both taken from the artifact the launch started from, however the running image was started, and never from a copy the artifact made of itself in order to run**. Where an artifact starts from a preparation, the running image sits **inside** that preparation and is not the artifact; classifying or targeting from it "would replace a copy the product can recreate at will and leave the file the user actually holds untouched, which is the one outcome an update must not produce". On Windows the discriminator is the installer's own per-user registry record **plus the artifact resolving inside the directory that value names**. A build not running from a released artifact is classified not updatable and issues no request at all. | HARD | REQ-STARTUP-106, REQ-STARTUP-125, REQ-STARTUP-165 |
| B-23 | **New. A `onefile` artifact may prepare itself once, and the specification fixes eight things about it while deliberately fixing no mechanism.** `REQ-STARTUP-165`: the preparation is held in the per-user data directories of `REQ-STARTUP-145`, **on the machine that ran the artifact and in storage local to it** rather than storage shared with or replicated to another machine; it is **never** written beside the artifact or onto the medium carrying it, so the artifact starts from read-only and removable media and leaves such a medium byte-for-byte unchanged; it is produced **from the artifact alone**, issues no network request and raises no elevation prompt; a preparation is **not a published artifact** and does not change the closed set of `REQ-STARTUP-031`; **nothing else about the run differs** — same version, same flavour classification, same single-instance resolution; and preparing, reusing and redoing are **always silent**, with `REQ-STARTUP-150` restating that nothing is reported to the user on any of those paths. **What it does not fix is the form, the name and the placement within that storage** — those are implementation choices and no user-facing surface exposes any of them. ***The specification defect this row reported is CLOSED and the sentence that reported it is withdrawn (2026-09-02). It is not closed by a measurement; it is closed by an amendment, and it is closed the conservative way rather than the permissive way this record predicted.*** It read: "One case has no stated outcome — a per-user root that is unwritable or full, where clause (c)'s recovery path *is* preparing, so prepare-again degenerates into preparing on every launch, silently." Clause (c) now **fixes a closed set of two permitted locations** for a run-scoped placement — the per-user data directories of `REQ-STARTUP-145` wherever they accept a write, or, **only** where those accept no write at all, the storage the platform designates for a user's transient files, with "no third permitted location, and no reading of this clause admits one" — clause (d) states that placement as its **single** exception, and the residual case is bounded away in terms: where neither kind of storage accepts any write, "there is nowhere on that machine the artifact's contents can be run from at all, and this clause's obligation to start is not reached". The placement is **not a preparation**: it serves one run, is removed when the run ends, is never started from again, and carries every prohibition of clause (a) unchanged. **And the degradation is no longer silent** — such a run is the one preparation outcome that **is** reported, once, after the window is painted, at warning severity, naming the storage it could not prepare into. **Four outcomes silent, one loud, and ADR-0054 names implementing four-silent-one-loud from a habit of *the-preparation-is-silent* as the specific error to prevent.** *Two clauses of this row are still unverified by any measurement and are named in `open-questions.md` rather than absorbed:* the no-usable-preparation branch and its notice were **not attempted** by spike 20, and clause (d)'s "issues no network request and raises no elevation prompt" is true only by construction of the spike's own launcher — no network capture and no privilege trace was taken. | HARD | REQ-STARTUP-165, REQ-STARTUP-145, REQ-STARTUP-150, REQ-STARTUP-151, REQ-STARTUP-155, REQ-STARTUP-159, REQ-STARTUP-087; `spikes/cached-portable-launch.md` §10, §14 |
| B-24 | **New. The product must determine directly whether an opened workspace sits on shared or synchronised storage, and must never infer it from a failure.** `REQ-STARTUP-166`: the determination is made **from the storage the workspace directory sits on**, not from a write that failed, a lock that collided or a session that was refused, "so a user is told before the situation costs them anything rather than afterwards". It is made for **every** workspace and by **every** path that opens one — startup resolution, a directory a launch carries to an already-running instance, and the project switch — and is part of the **post-show** background activation, so it never delays first paint or the moment the interface accepts input. Where either condition is found the user is warned at warning severity on the persistent non-modal notice surface, and the notice **SHALL NOT state or imply that the workspace cannot be used**; an unclassifiable workspace is passed over in silence. **Note what the warning is and is not about**: it is about the user's own files and a second machine working in the same folder, **not** about the store, which is no longer there (W-01). | HARD | REQ-STARTUP-166, REQ-STARTUP-043, REQ-STARTUP-150, REQ-SESSION-198 |
| B-12 | A failed **check** is always invisible; a failed **install** is always visible with copyable detail and a retry action; progress is reported **inside the offer notice, updated in place, never replaced**; **exactly one waved-off version is remembered — never a list**. | HARD | REQ-STARTUP-110, REQ-STARTUP-116 – REQ-STARTUP-120, REQ-STARTUP-150, REQ-SHELL-118, REQ-NOTIFY-218 |
| B-13 | Shutdown is checkable from outside the process, leaves no partially written or locked update file, and waits for in-flight update work at most a stated allowance. | HARD | REQ-SHELL-121, REQ-STARTUP-046 |
| B-14 | Demo mode is a **property of a window fixed at construction**, never toggled, never persisted, never inherited; demo content is a **constant of the build**, derived from no clock, host, directory or random source. | HARD | REQ-SHELL-005, REQ-SHELL-162, REQ-STARTUP-055 – REQ-STARTUP-057 |
| B-15 | When diagnostics is off, **no diagnostics files, timers or instrumentation of any kind exist — zero work, zero disk writes**, with exactly one activation source. | HARD | REQ-STARTUP-129, REQ-STARTUP-130 |
| B-16 | Every metric record carries thread names, **the count and names of the concurrent execution contexts the application itself creates**, one per-view entry for each of the seven views, and **counts only** for session stores. | HARD | REQ-STARTUP-134 |
| B-17 | **No diagnostics file may contain session content of any kind**, and stack frames identify source files **by base name only**. | HARD | REQ-STARTUP-134, REQ-STARTUP-136 |
| B-18 | The recorder is bounded on disk with further writes **refused without raising an error**, and every bound and cadence in force is readable from the manifest. | HARD | REQ-STARTUP-133, REQ-STARTUP-157 |
| B-19 | A diagnostics view that cannot read or render its own data reports that **within itself and nowhere else**, publishing no notice and no acknowledgement. | HARD | REQ-NOTIFY-267 |
| B-20 | Every run-time data asset resolves from what was installed, with **no download, under blocked network**. | HARD | REQ-STARTUP-159 |
| B-21 | Bundle mode, installer technology, build tooling, and the field names and nesting of diagnostics files. | FREE | REQ-STARTUP-157 (units and stability are fixed; names are not) |
| B-22 | Demo-mode process-wide network silence against a demo window opened from a non-demo window in the same process. | CONFLICT | REQ-SHELL-005 vs REQ-SHELL-162, REQ-STARTUP-057 |
