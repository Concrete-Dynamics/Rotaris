# UI Performance Benchmark — Child iteration behavior

Part 2 of 5 of [domain 21](../21-ui-performance-benchmark.md), which indexes every part. Defines REQ-UIBENCH-045 – REQ-UIBENCH-080.

### Child iteration behavior

- **REQ-UIBENCH-045** — Every child iteration re-runs all three checks of REQ-UIBENCH-024 against the frozen `fixture.json` before it opens any window. A run directory whose frozen fixture was altered after replay wrote it therefore yields crashed iterations and crash markers, not measurements.
- **REQ-UIBENCH-046** — A replay run leaves the invoking user's stored desktop-application settings exactly as it found them: no such file is created, read, modified, or deleted, and every one of them holds the same bytes after the run as before it. Anything an iteration stores is confined to that iteration's temporary settings directory (REQ-UIBENCH-038) and disappears with it, so a completed run leaves no file behind outside its own output directory. A host on which the desktop application has never been installed or configured therefore replays a fixture to the same structural counters and the same invariant values as a host on which it has been used heavily.
- **REQ-UIBENCH-047** — Before the measured window exists, each iteration selects the same platform-independent widget style its environment already names (REQ-UIBENCH-039), loads the three bundled font families of REQ-SHELL-008 from the product package, and applies the product's default built-in theme `rotaris-dim` (REQ-SHELL-128), so none of the three is taken from the host. The host-font fallback REQ-SHELL-008 permits the application at startup SHALL NOT apply here: an iteration in which a bundled family fails to load terminates with a non-zero status and is counted as a crash (REQ-UIBENCH-041) instead of measuring against host fonts, because a silent fallback would break determinism without being visible anywhere in the report. Testable consequence: installing or removing fonts on the host, changing the host's default widget style, and changing the host's theme preference each leave a replay of the same fixture reporting the same `widgets` values and the same structural counters as before the change.
- **REQ-UIBENCH-048** — The two canonical window sizes are the minimum window size and the opening window size REQ-SHELL-022 fixes, and the measured window is initially sized to the opening one. This requirement relies on that one for both figures and states neither of them again, so a change to the product's window bounds moves the benchmark with it rather than leaving two sets of numbers to be kept in step. Where a later phase names a canonical size it means one of those two.
- **REQ-UIBENCH-049** — Every phase record carries `event_loop_lag_ms`, a number of milliseconds rounded to 3 decimals reporting the longest single interruption to the interface's responsiveness observed between the previous record of that iteration and this one. Responsiveness is observed by a probe scheduled to run every 10 ms, and the reported value is the largest amount by which one probe ran later than the instant it was scheduled for; the observation interval is fixed here so that values produced by two conformant implementations are comparable in magnitude. The value is never negative and is 0 when no probe ran measurably late. It describes that interval alone and is not accumulated, so a delay reported in one record is never reported again in a later one. Observation runs continuously over the measured part of an iteration — it starts before the first phase and stops when the last phase's record is taken — so every instant of the iteration falls inside exactly one record's interval.
- **REQ-UIBENCH-050** — Every record reports, for the process that produced it: `rss_bytes`, its resident memory in bytes; `threads`, the number of operating-system threads it currently has; and `handles`, the number of operating-system handles it currently holds open — open handles on Windows, open file descriptors on POSIX systems — or null. A null is permitted on any platform, and only for the two stated reasons: the platform exposes no such counter, or the count could not be obtained at that moment. It is the only substitute permitted for the value, it is reported in `handles_raw` and nowhere else (REQ-UIBENCH-076), and no invariant reads `handles`. Each record also reports two structural counts of the interface: `widgets`, the number of live visual elements of the constructed window — those that occupy space in the window's layout and can be painted — and `ui_objects`, the broader count of every live interface-framework object owned by that window, visual or not, so `ui_objects` is never smaller than `widgets`. Both are 0 in any record taken while no window exists. `rss_bytes`, `threads`, `widgets`, and `ui_objects` are non-negative integers; `handles` is a non-negative integer or null. Both structural counts are defined against the interface framework the product is built on: their absolute values are comparable between two runs of one product revision — which is all REQ-UIBENCH-054 and REQ-UIBENCH-085 rely on — and are deliberately not comparable between product revisions or between implementations. **The counting rule stated here is framework-neutral and is the operative one.** `widgets` counts **every** element that occupies layout space and can be painted, whatever produced it, including the painted content of whatever the window is currently displaying: a rendered paragraph, code block or list item inside a transcript row is a `widget`, and an element whose box is degenerate at the moment of counting is not, however much application structure it represents. The clause about the interface framework explains only why absolute numbers do not travel between revisions or implementations; it does **not** license a product to count only the elements its own layout declares and to leave out what it drew. A consequence follows immediately from this and is stated in REQ-UIBENCH-054 rather than left for a reader to discover: a count defined this way necessarily changes when the displayed content changes, so it cannot be invariant across an iteration whose whole purpose is to apply content.
- **REQ-UIBENCH-051** — `wall_ms` is the real time and `cpu_ms` the processor time the measuring process spent on a phase, both in milliseconds rounded to 3 decimals. Both cover the phase's work up to the point at which the interface has finished showing that work's effect, or up to the bound of REQ-UIBENCH-119, whichever comes first, so the cost of rendering what a phase changed is charged to that phase and never to a later one; in `resize_sequence` each resize is complete before the next one starts. The remaining values of the record — the process and structural counts of REQ-UIBENCH-050, `markdown_cache`, and `transcript_operations` — describe the state reached once the phase is complete in that sense. `elapsed_s` is the time in seconds, rounded to 3 decimals, since a time origin fixed once per iteration before its first phase, so within one iteration `elapsed_s` never decreases from one of the seven records to the next.
- **REQ-UIBENCH-052** — The child's record file is JSON Lines: one record per phase (7 per healthy iteration), compact separators, non-ASCII escaped, one newline per record. The file is created only after all phases complete: a child that crashes mid-run leaves no record file for that iteration — only the parent's crash marker and the log retained under REQ-UIBENCH-117. On the healthy path the child writes all seven records, closes the window, and only then terminates with a zero status. A child SHALL never terminate with a zero status having written no record file; a parent that observes one treats it as a crash (REQ-UIBENCH-041), so a missing record file is always accompanied by a crash marker explaining it and `iterations` never falls silently.
- **REQ-UIBENCH-117** — Diagnostic output an iteration process writes SHALL be captured by the process that started it and SHALL never appear on any surface the user did not ask for. Where the iteration crashed (REQ-UIBENCH-041), the captured output SHALL be written to `<output>/iteration-NNN.log` and SHALL be reachable from that run's failure and crash reporting (REQ-UIBENCH-114); where the iteration completed, the captured output MAY be discarded. Output from the interface framework itself is expected on this channel during offscreen rendering and SHALL never on its own be treated as a failure: only the child's termination status and the presence of its record file decide whether an iteration crashed (REQ-UIBENCH-041, REQ-UIBENCH-052).
- **REQ-UIBENCH-119** — Every wait for the interface to finish showing a phase's effect (REQ-UIBENCH-051) is bounded at 30 s, measured from the moment that phase's work has been submitted. Where the bound expires, the phase's timing closes at that moment, its record is written with `settle_timed_out` true, and the iteration continues with the next phase; where the interface settled inside the bound, `settle_timed_out` is false. The key is present in every record the benchmark writes (REQ-UIBENCH-062). No threshold applies to it and it never turns an operation into a failure (REQ-UIBENCH-097), but it is **not** ignored by the report: the two invariants whose values are only measurements when the interface has settled — the memory tripwire of REQ-UIBENCH-087 and the structural-count rule of REQ-UIBENCH-085 — read it, and a record carrying it as true makes each of them false rather than letting a figure taken mid-work be reported as a pass. A record carrying it as true under-reports the true cost of that phase, and a consumer comparing runs must take that into account. No iteration is ever ended merely because a phase reached the bound.

### Replay phases

- **REQ-UIBENCH-053** — Every iteration executes exactly seven phases, once each, in this fixed order: `construct_window`, `apply_fixture`, `ordered_appends`, `streaming_updates`, `tail_replacements_1000`, `unchanged_state`, `resize_sequence`.
- **REQ-UIBENCH-054** — `construct_window`: the product's main window is created against the interface state the fixture will drive, sized to the opening canonical size of REQ-UIBENCH-048, and shown offscreen (REQ-UIBENCH-112).

  **The element-count invariant this requirement used to state is relaxed, and what follows is the relaxation.** It required that `construct_window` be the only phase allowed to change the number of interface elements alive in the process, so that from the moment its record is taken until the iteration ends the `widgets` value must not change. Under the counting rule REQ-UIBENCH-050 fixes, that rule is not satisfiable by any implementation this product is permitted to have: the count includes the painted content of whatever the window is displaying, so it rises the first time transcript content is applied and moves again whenever the displayed content or the window's geometry changes. The only structure that could hold the old rule is one that paints the transcript as a single undifferentiated surface, and that structure is refused, because it forfeits native text selection, keyboard navigation and per-row accessible names (REQ-CHAT-075, REQ-CHAT-077, REQ-CHAT-065, REQ-SHELL-144) — a screen-reader user losing access to the conversation is not a price this product pays for a benchmark number that is informational in any case (REQ-UIBENCH-088). The old rule is therefore withdrawn as **unsatisfiable by any admissible implementation**, not merely as unmet.

  **What this phase still fixes.** `construct_window` remains the phase at which the window's own structure is built, and the count its record reports is the structure-only figure every later count is read against. A later record reporting a `widgets` value **below** the `construct_window` figure means window structure was destroyed rather than content drawn, and is a defect.

  **What replaces the invariant is a bound on the count's variation, stated over the two places where the displayed state is known not to change.** Within each iteration taken on its own:
  1. across the 1000 replacements of `tail_replacements_1000`, every replacement displays content of the same shape — the same rows in the same order, the last of them holding text of the same length L (REQ-UIBENCH-058) — so of the 11 `widgets_samples` that phase records, **no value may be greater than the value before it**; and
  2. `unchanged_state` applies a state identical to the one already displayed, at unchanged window geometry (REQ-UIBENCH-059), so the `widgets` value that phase's record reports **must equal** the `widgets` value the `tail_replacements_1000` record reports.

  Between any other pair of records the count may legitimately differ, because what is displayed differs, and a difference there is not a finding. Together the two clauses keep the property the withdrawn invariant existed to establish — that interface elements are not accumulated by repeated work, which is the only failure a benchmark can distinguish from drawing — while giving up the property no admissible implementation can deliver. Both clauses are read only from records whose `settle_timed_out` is false, for the reason REQ-UIBENCH-087 gives. This is the canonical rule, and the boolean of REQ-UIBENCH-085 reports exactly it.
- **REQ-UIBENCH-055** — `apply_fixture`: the entire fixture state is applied to the interface in one pass — agents (with `state` values checked against REQ-UIBENCH-028), todos, artifacts, KPIs, session name, session status, run state (with its value checked against REQ-UIBENCH-032), active model, and the complete transcript assigned in bulk rather than entry by entry.
- **REQ-UIBENCH-056** — `ordered_appends`: the transcript is cleared, then every transcript event of the fixture is added back individually, in fixture order, one event per update rather than in bulk — the same way events arrive in the live application.
- **REQ-UIBENCH-057** — `streaming_updates` (simulated token streaming): clears the transcript; for each event in order, the event's `text` is revealed as a sequence of prefixes of lengths 0, 256, 512, … (capped at the full text length), each step performing a full transcript assignment of all previously completed events plus a copy of the current event truncated to the revealed prefix. The final step always includes the full text; an event with empty text still produces exactly one (empty-prefix) step.
- **REQ-UIBENCH-058** — `tail_replacements_1000`: the text of the transcript's last entry is replaced exactly 1000 times, the whole transcript being re-applied after each replacement. Let L be the number of characters in that entry's text when the phase begins, or 1 if that count would be 0. Replacement i, for i from 0 through 999, uses i written in decimal and zero-padded to 8 digits, extended on the right with `x` characters to length L and then truncated to length L. If the transcript holds no entry when the phase begins, one substitute entry is inserted first — `timestamp` `00:00`, `role` `agent`, `text` of 256 `x` characters — so that the 1000 replacements always take place. Resident memory is sampled 11 times, at the replacement indices 0, 100, 200, 300, 400, 500, 600, 700, 800, 900, and 999; each sample is read immediately after the replacement at its index has been applied and the interface has finished showing it, never before. This phase's record carries those 11 values in that order as `rss_samples`, and carries `rss_second_half_growth_bytes`, the value sampled at index 999 minus the value sampled at index 500. The structural count `widgets` (REQ-UIBENCH-050) is sampled at the same 11 replacement indices and at the same moment as the resident-memory sample beside it, and this phase's record carries those 11 values in that order as `widgets_samples`. It is sampled here and in no other phase because this is the one phase across which the displayed content keeps its shape while the work is repeated a thousand times, which is what makes an element that accumulates distinguishable from an element that was drawn; the rule the samples are read against is REQ-UIBENCH-054's.
- **REQ-UIBENCH-059** — `unchanged_state`: **the state already displayed is applied a second time** — the fixture's complete state in every part except the transcript, which carries the entries `tail_replacements_1000` left displayed: the fixture's entries with the last one's text as replacement 999 wrote it, or the single substitute entry with that text where the fixture's transcript was empty (REQ-UIBENCH-058, REQ-UIBENCH-102) — so that what is applied is identical, field for field, to what the interface is already showing. That state is constructed from the fixture together with REQ-UIBENCH-058's replacement rule and is never read back out of the view, so two iterations apply the same state and the phase stays deterministic (REQ-UIBENCH-098). The phase therefore measures the cost of applying an unchanged state, and the application it performs is classified as a `noop` (REQ-UIBENCH-064). The record closing this phase reports the same displayed content, the same `widgets` count, and the same transcript row structure as the record that preceded it.

  The earlier form of this requirement applied **the fixture's** complete state and called that identical to the state already displayed. It is not, and measurably is not: `tail_replacements_1000` leaves the transcript's last entry holding replacement 999's text, so re-applying the fixture changes that row back. The phase as written measured a one-row update rather than an unchanged application, recorded an `update` where the phase's own name promises a `noop`, and could not honour its closing sentence about reporting the same displayed content as the state before it. The phase is corrected to do what it is named for and what its guarantee states, rather than the guarantee being weakened to match a state the previous phase happened to leave behind.
- **REQ-UIBENCH-060** — `resize_sequence`: resizes the window through the minimum canonical size → the opening canonical size → an intermediate 1180×760, which is this requirement's own figure and lies between the two → the minimum canonical size → the opening canonical size, both canonical sizes being REQ-UIBENCH-048's, settling after each resize and ending at the opening canonical size.
- **REQ-UIBENCH-061** — The final (resize-phase) record of each iteration additionally carries `rss_slope_bytes_per_second` — the ordinary-least-squares slope over that iteration's seven per-phase (elapsed_s, RSS) points — and `fixture_checksum`, the checksum of the fixture that was replayed.

### Per-record schema (run schema version 2)

- **REQ-UIBENCH-062** — A phase record is a JSON object whose keys are `schema_version` (the integer 2), `iteration` (integer), `phase` (one of the seven names listed in REQ-UIBENCH-053), `elapsed_s` (seconds to 3 decimals), `wall_ms` and `cpu_ms` (milliseconds to 3 decimals), `rss_bytes` (integer), `threads` (integer), `handles` (integer or null), `widgets` (integer), `ui_objects` (integer), `event_loop_lag_ms` (milliseconds to 3 decimals), `settle_timed_out` (boolean), `markdown_cache` (object), and `transcript_operations` (object). Those keys carry the meanings fixed by REQ-UIBENCH-049, REQ-UIBENCH-050, REQ-UIBENCH-051, REQ-UIBENCH-063, REQ-UIBENCH-064, and REQ-UIBENCH-119. Records of two phases carry additional keys of their own: `tail_replacements_1000` (REQ-UIBENCH-058) and `resize_sequence` (REQ-UIBENCH-061). A record the benchmark writes carries no key beyond those.
- **REQ-UIBENCH-063** — `markdown_cache` reports six values for the cache the interface keeps of rendered message bodies: `hits` and `misses`, running totals over the life of the child process that wrote the record, never reset between phases, so they grow monotonically through that iteration's seven records and are deliberately neither per-phase nor per-iteration figures; `entries` and `chars`, the occupancy at the moment the record was taken, expressed in cached items and in characters of the source text those items were rendered from — never in characters of rendered output, so `chars` is comparable with `max_chars` whatever the rendered form costs; and `max_entries` and `max_chars`, the capacities that occupancy is held to. Every record the benchmark writes reports all six keys, with `max_entries` 256 and `max_chars` 2000000. Whether a record's occupancy actually lies within its stated capacities is not assumed anywhere: REQ-UIBENCH-086 evaluates it and reports the answer, which matters because a run directory may also hold records the benchmark did not write (REQ-UIBENCH-075). The all-zero block of REQ-UIBENCH-076 is a substitution a reader makes for an absent block, never a value the benchmark emits.
- **REQ-UIBENCH-064** — `transcript_operations` is an object of exactly six non-negative integer counters — `noop`, `insert`, `remove`, `update`, `refused`, `reset` — each a running total, over the life of the process that wrote the record, of the transcript updates that fell into that category. Every application of a transcript state to the view is classified by comparing the state being applied with the state currently displayed, and contributes to the counters exactly as follows: `reset` counts one for each application that discards the displayed transcript wholesale and rebuilds it, which is every application that clears the transcript and every application the view cannot reconcile row by row; `refused` counts one for each application the view declines without changing anything, because the incoming state is not a valid successor of the displayed one — it addresses a row the view does not hold, or it would reorder rows already displayed; `noop` counts one for each accepted application in which the incoming state is identical to the displayed one, so no row changes; and every other accepted application contributes one to `insert` for each row added, one to `remove` for each row removed, and one to `update` for each retained row whose content changed, and nothing to `noop`. `refused` is therefore distinguished from `noop` by whether the application was valid, not by whether anything visibly changed: both leave the view unchanged, but only `noop` was accepted. No counter decreases from one record of an iteration to the next, so every phase's block is a cumulative total and the `resize_sequence` record holds that iteration's final totals. The totals are a function of the sequence of transcript states applied and of nothing else, so two iterations replaying the same fixture end with identical values for all six counters; REQ-UIBENCH-083 reports that agreement as a boolean.

### The inspect operation

- **REQ-UIBENCH-065** — Inspect builds its report from the chosen run directory's `iteration-*.jsonl` files together with its `iteration-*.crash` files (REQ-UIBENCH-069), and writes nothing to disk. Record files are read in bytewise ascending filename order and their records concatenated in that order. That read order fixes two things and nothing else: the order of every `*_raw` list in the report, and which record counts as first and last for REQ-UIBENCH-108. Which records belong to which iteration is decided solely by each record's own `iteration` value (REQ-UIBENCH-068, REQ-UIBENCH-073) and never by the name of the file that carried it, so the number of record files present and the reported `iterations` value need not agree. `inspect` never reads `summary.json`, even when the directory holds one, so its report always reflects the record files as they currently stand; `compare` deliberately prefers `summary.json` (REQ-UIBENCH-089).
- **REQ-UIBENCH-066** — Record reading is crash-tolerant: lines that fail JSON or text decoding, and decoded values that are not objects, are skipped. Given a record file ending in a truncated final line, all complete preceding records are still used.
- **REQ-UIBENCH-067** — The summary is a JSON object with top-level keys: `schema_version` (2), `iterations`, `records` (the total count of records read across all record files), `phases`, `crashes`, `fixture_checksums`, `process`, and `invariants` (plus `fixture_checksum` only when written by `replay`, per REQ-UIBENCH-042).
- **REQ-UIBENCH-068** — `iterations` is the number of distinct `iteration` values found across every record read. It is neither the requested iteration count nor the number of record files: an iteration that terminated before its record file was written contributes nothing; all records carrying no `iteration` value form one bucket that counts once; and one `iteration` value appearing in two different files still counts once. The same grouping by `iteration` value governs the per-iteration series of REQ-UIBENCH-073.
- **REQ-UIBENCH-069** — `crashes` is the count of files matching `iteration-*.crash` in the run directory.
- **REQ-UIBENCH-070** — `phases` maps each phase name (sorted) to: percentile blocks for `wall_ms` and `cpu_ms`, plus `rss_bytes_raw`, `threads_raw`, `widgets_raw`, and `operations_raw` (the per-record `transcript_operations`, defaulting to `{}`). Every per-record measurement is retained in its unreduced form in addition to the computed percentile blocks, so a consumer can recompute any statistic from the summary alone.
- **REQ-UIBENCH-071** — A percentile block has the shape `{raw: [...], p50, p95, min, max, mean}`; `min`, `max`, and `mean` are null for empty input, and `mean` is the arithmetic mean.
- **REQ-UIBENCH-072** — `fixture_checksums` is the sorted, de-duplicated list of every `fixture_checksum` value found in records (one per healthy iteration).
- **REQ-UIBENCH-073** — The `process` block contains: `rss_start` (first record in file order), `rss_peak` (maximum), `rss_end` (last record in file order), `rss_slope_bytes_per_second_raw` (the per-iteration in-child OLS slopes), `event_loop_lag_ms` (a percentile block over all records, missing values counted as 0.0), `threads_raw`, `handles_raw`, `widgets_raw`, `rss_theil_sen_bytes_per_second_raw` (one robust slope per iteration, records grouped by their `iteration` value with a default group of 0), `rss_theil_sen_bytes_per_second_p50` (the median of those slopes), `tail_second_half_growth_bytes_raw` (the values from REQ-UIBENCH-058), and `widgets_samples_raw` (one list per `tail_replacements_1000` record, in read order, each holding that record's 11 `widgets_samples` values unreduced). The last of these is carried so that the boolean of REQ-UIBENCH-085 can be recomputed from the summary alone, which is the principle REQ-UIBENCH-070 states for every other per-record measurement.
- **REQ-UIBENCH-074** — Inspecting an empty run directory — or a nonexistent path, which yields the same empty file set rather than an error — degrades gracefully: `iterations` 0, `records` 0, empty `phases`, all `process` scalars null and lists empty, and all invariants vacuously true.
- **REQ-UIBENCH-075** — Only files matching `iteration-*.jsonl` and `iteration-*.crash` are consulted; other files in the run directory are ignored. Any matching record file — including hand-added ones — is merged in sorted filename order; inspect trusts the directory contents.
- **REQ-UIBENCH-076** — `wall_ms` and `cpu_ms` must be present in every record read: a record lacking either makes inspect fail with the report of REQ-UIBENCH-097. That strictness is intended and is confined to those two keys, because they are the only values a reader cannot substitute for without inventing a measurement. It is deliberately not extended to `phase` or `iteration`: a record with no `phase` joins no phase block, and a record with no `iteration` joins the single default bucket of REQ-UIBENCH-068 and REQ-UIBENCH-073, both of which lose information without fabricating any. Every other per-record key may be absent, with these reader-side substitutions: a `markdown_cache` that is absent or is not an object reads as all six values 0, which passes the bound check of REQ-UIBENCH-086; a `transcript_operations` that is absent or is not an object reads as `{}`; an absent `event_loop_lag_ms` reads as 0.0; an absent `settle_timed_out` reads as false. An absent `rss_bytes`, `threads`, `widgets`, `ui_objects`, or `handles` contributes nothing at all to the corresponding `*_raw` list — no null and no placeholder is appended — so a `*_raw` list may be shorter than `records`, and a consumer must read each list by its own length and never align it positionally with another. A `handles` that is present and null is the single exception: it is appended as null, because null is a value that key may legitimately take (REQ-UIBENCH-050).

### Statistics semantics

- **REQ-UIBENCH-077** — Percentile: null for empty input; otherwise values are sorted and linearly interpolated between closest ranks at position (n−1)·q (the inclusive/"linear" method). The p50 of an even-sized list is the midpoint average of the two central values.
- **REQ-UIBENCH-078** — Linear (OLS) slope: null for fewer than 2 points; 0.0 when all x values are identical; otherwise the ordinary-least-squares slope.
- **REQ-UIBENCH-079** — Robust (Theil–Sen) slope: null when fewer than two points are supplied. When more than 2000 points are supplied, the series is first thinned to at most 2000 by retaining the point at index 0 and every k-th point after it, with k = ceil(n / 2000); a series of 2000 points or fewer is used whole. The reported value is then the median, computed as in REQ-UIBENCH-077, of the slopes of all pairs of points taken from the retained series, excluding every pair whose two x values are equal. If no pair survives that exclusion the result is null, since a median over an empty input is null.
- **REQ-UIBENCH-080** — Both the least-squares trend and the robust Theil–Sen trend appear in the summary's `process` block, so a single memory outlier cannot mask or fake a leak trend.
