# Multi-Agent Run Orchestration — 12. Result Retrieval and Voluntary Waiting

Part 3 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-061 – REQ-ORCH-087.

### 12. Result Retrieval and Voluntary Waiting

- **REQ-ORCH-061** — A `background_output` tool MUST retrieve a completed task's report by task id, returning: `ok` with the report text; `still_running` with a message naming the id and its current state; or `not_found`. Lookups are parent-scoped: a task id belonging to a different parent also returns `not_found`. A `detail_level` of `summary` returns agent/status/summary/artifacts/key findings/last reply; `verbatim` additionally returns the exact last reply, the union of touched files (edited, created, artifact paths), and highlighted paths with snippets.
- **REQ-ORCH-062** — The `wait_for_tasks` contract is fixed by REQ-TOOLS-156: what an empty task list means, when the call returns without suspending, which requests it refuses and in what words, and the fact that this is the product's only waiting mechanism. This domain restates none of it, states no second waiting path, and fixes no message or error text for one. What it relies on that requirement for is that the waited-for set never includes the caller's own task, so a wait can never depend on the agent that is waiting, and that the wait ends when every task in that set is terminal, whichever way each reached it. The obligations this domain adds are these. A parent has at most one wait outstanding, and an outstanding wait does not survive the end of the parent's conversation. This document places no maximum duration on a wait, and none is needed: every child is already bounded by the hard child timeout of REQ-ORCH-088, and every non-terminal child record is closed by the sweeps of REQ-ORCH-052 and REQ-ORCH-053, so the waited-for set always reaches a terminal state and a wait can never outlive the children it waits on. A separate deadline MUST NOT be imposed: it could only ever fire in a state those guarantees already exclude, and firing it would resume a parent whose children are still holding model slots.
- **REQ-ORCH-063** — Wait resolution: the drain spawns ready children, collects reports for the waited set, and resumes the parent with a message stating the waited-for background tasks completed, followed by the results, once the waited set is fully covered. A transient window where a task's execution handle has vanished but its record still reads running MUST NOT be treated as completion. Matching notifications are discarded so no completion is double-announced.
  > **Narrowed by [`PD-TOOLS-006`](../../product/directives/pd-tools-006.md#pd-tools-006), revision 11, 2026-10-15 (OQ-333).** The message above still governs; after each reported child's result it adds one line naming that child's `todo_item` when the item is still `IN_PROGRESS` in the caller's own plan and no non-terminal child of the caller holds it, telling the caller to close it with `update` once it accepts the report.
- **REQ-ORCH-064** — Time spent blocked in a voluntary wait MUST NOT register as in-flight tool activity for graceful-pause purposes, so a parent legitimately blocked for minutes is not force-closed.
- **REQ-ORCH-065** — Any role holding the `delegate` tool MUST be able to delegate in its turn, subject to REQ-ORCH-046. Every delegation made during one iteration, at any depth, MUST count against that iteration's own set of child records and against the same limits and scheduling as delegations made by the entry role; the counters do not restart at a deeper level, and one ledger covers the whole iteration (REQ-ORCH-072 creates one per iteration). A child MUST see only what its payload gives it (REQ-ORCH-035) and never its parent's conversation. Every child MUST run in the resolved workspace root; a delegation whose child would run in any other directory MUST fail with an error naming both the expected workspace root and the directory that differed.

### 13. Iteration Loop and Stop Conditions

- **REQ-ORCH-066** — The iteration-loop mode MUST be first-class for long-running autonomous work: usable by the entry role for the whole run or by a delegated child for a bounded subproblem, and functional whether or not a view is attached to the session (REQ-ORCH-150).
- **REQ-ORCH-067** — Each iteration MUST: read the plan/progress state; select the next incomplete anchored task — the first pending task scanning phases in insertion order (so phase order "main" → queued-prompt phases → remediation phases is the priority order); do work for that one task only; verify; update progress; and hand the next iteration compacted state (todo, artifact set, progress, reports) rather than raw transcript. Iteration boundaries MUST be visible in session state and transcript via iteration-start and iteration-end events carrying iteration number, task id/name, outcome, and summary.
- **REQ-ORCH-068** — Before an iteration closes it MUST have updated the todo and progress records, resolved the task it selected into one of three outcomes (marked complete, given up on, or returned to the pending queue), and emitted a report artifact. On verification failure there is no silent roll-over into a second task: the iteration ends with the current task still anchored, set back to pending with a continuation payload.
- **REQ-ORCH-069** — Stop conditions MUST be evaluated between iterations (never mid-iteration; a long iteration may therefore overshoot the time limit), first match wins: (1) all non-abandoned tasks completed → stop reason `tasks_complete`; (2) completed iteration count ≥ the iteration limit → `iteration_limit_reached`; (3) elapsed wall time since run start ≥ the optional time limit → `time_limit_reached`; (4) no pending task → `no_pending_tasks`. Loop-level stops: a user stop → `user_cancelled`; a cancellation → `user_cancelled`; child escalation → `agent_session_aborted`; message-limit cancel → `message_limit_reached`. Every stop reason this document names is a member of the closed set of REQ-MONITOR-301 and is recorded as the token that requirement fixes; this domain mints no stop-reason string of its own, holds no copy of that set, and states no mapping from a stop reason onto a terminal result. That closed set draws no distinction between a person stopping the run and a person cancelling it — both record `user_cancelled` — so the two paths differ in what the run does on the way out and not in what it records. Where a surface explains a stop to a person it MUST convey which of those tokens the run recorded and, for a budget stop, which budget ran out; that sentence is a presentation of the recorded token and never the recorded value itself, and its wording is the implementation's. A stop reason arrived at here is not necessarily final: REQ-ORCH-071 and REQ-ORCH-079 may extend the run before it ends, in which case the loop continues and stop conditions are evaluated again at the next boundary.
  > **Extended by [`PD-ORCH-009`](../../product/directives/pd-orch-009.md#pd-orch-009), 2026-10-06 (revision 2, 2026-10-07).** The stop
  > conditions above are unchanged. An execution iteration whose entry role ended its turn without writing an answer first
  > asks it once more, unless an earlier turn of the same execution wrote one, and the run tells the person when it still
  > wrote none.
- **REQ-ORCH-070** — The iteration limit MUST default to 20; the time limit is optional with no default.
- **REQ-ORCH-071** — Queued prompts extend a finishing run only when the stop reason would be `tasks_complete`: they are appended as a new phase named "Queued Prompts" with tasks named "Queued Prompt: <first 8 characters of the prompt id>", marked triggered, the total task count incremented, and the loop continues. The queued-prompt read MUST be scoped by session id so that concurrent runs never cross-trigger (REQ-ORCH-151). A queued prompt arriving under any other stop reason (e.g. `iteration_limit_reached`) MUST NOT extend the run. Where a queued prompt and relentless mode (REQ-ORCH-079) both apply to the same stop, this requirement MUST be evaluated first and wins: the queued prompt extends the run, and relentless mode is not evaluated for that stop at all — it is evaluated afresh at the next stop the run reaches, by which time the queued prompt's own work is part of what it audits. A queued prompt carries an explicit user instruction, which takes precedence over a model's judgment that the original request is unmet. The two never extend one stop together.
- **REQ-ORCH-072** — Iteration mechanics: the selected task flips to in-progress; a fresh per-iteration ledger of delegated children is created under the budget-clamped policy; the iteration's **root execution record** is created with the entry role and the task's execution payload and transitioned to running. That record is the run's own and is **not a delegated child**: it never arrives through a `delegate` call, it counts against none of the admission limits of REQ-ORCH-046 (depth, total, active), it holds no per-model slot of REQ-ORCH-050, and it is not presented as a task agent (REQ-MONITOR-043, REQ-MONITOR-089, REQ-CHAT-068). It carries an identity of the same shape a delegated child carries — a canonical name and a task id, in the same namespace — so a lookup naming the root resolves to it rather than reporting it unknown; the parent-scoping of REQ-TOOLS-155 and REQ-TOOLS-156 is unchanged by that, so an agent asking about a record it does not own is refused for that reason and never told the root does not exist. Every delegated child of the iteration names the root execution record as its parent and sits one level deeper than it.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** An iteration left open by a pause, a stop, a quit or a crash resumes with its own root restored, rather than a new root.
- **REQ-ORCH-073** — An iteration that raises an unhandled error MUST be caught: the task is marked abandoned, the abandoned count incremented, and the loop continues with the next task.
- **REQ-ORCH-074** — Outcome dispatch on the iteration's (possibly rewritten) report status: `succeeded` → task completed; `failed`/`cancelled` → in-flight children cancelled, task abandoned, and if the report carries an escalation signal the run ends with stop reason `agent_session_aborted`; `blocked` → task reverted to pending, in-flight children NOT cancelled (the next iteration collects their results), and the iteration's own record recorded as succeeded rather than blocked, so that a host status display does not present a deliberate deferral as a failure; any other status (e.g. `partial`) → task reverted to pending.
- **REQ-ORCH-075** — Incomplete-todo re-queue: when a report says succeeded but the agent's own todo list still holds pending/in-progress items after correction retries are exhausted, the same top-level task MUST be re-queued (not abandoned) with a continuation payload built from the stripped base payload plus a continuation marker block stating that success was declared with N todo items incomplete (naming up to the first 5) and instructing the agent to continue from the todo list and not end its turn until every remaining item is complete. Still-running background children MUST be enumerated in the payload with an instruction not to re-delegate them.
  > **Narrowed by [`PD-ORCH-012`](../../product/directives/pd-orch-012.md#pd-orch-012), 2026-10-06.** "The agent's own todo list"
  > ranges over the items the task answers for: those not already open when the task was first taken up (its plan cycle,
  > else its first iteration), a record kept with the task. An item left open before then does not re-queue it and stays
  > open in the plan.
  > **Extended by [`PD-ORCH-015`](../../product/directives/pd-orch-015.md#pd-orch-015), 2026-10-07.** The continuation payload also carries
  > the answer the held iteration wrote, cut to 6,000 characters, to the same task's next fresh root only; a re-queue or a
  > give-up for an open plan is announced in a `system` transcript row.
- **REQ-ORCH-076** — Continuation and verification-failure marker blocks MUST be stripped from a task payload before a new one is appended, so that such markers do not pile up across repeated re-queues of the same task.
- **REQ-ORCH-077** — Consecutive-retry limit per task: consecutive pending-outcome iterations per task id are counted; when the count reaches the per-task consecutive-retry limit, the task MUST be abandoned to break the loop. That limit MUST be a configuration setting of its own, separate from the iteration limit of REQ-ORCH-070 and defaulting to 3. Sharing the iteration limit's value made the guard unreachable — a re-queued task is selected again by REQ-ORCH-067, so the per-task counter and the completed-iteration counter advance in step and the global stop of REQ-ORCH-069 always fires first — and a guard that can never fire is no guard at all. The counter resets on any forward progress.
- **REQ-ORCH-078** — Todo-correction retries MUST reuse the validation-retry setting (default 0): with 0, an incomplete-todo success re-queues without an in-conversation retry; with a positive value, a correction message is sent into the same conversation up to that many times first.
  > **Narrowed by [`PD-ORCH-015`](../../product/directives/pd-orch-015.md#pd-orch-015), 2026-10-07.** The correction count is the larger
  > of 1 and the validation-retry setting, so a setting of 0 still sends one correction; the setting's own default is
  > unchanged.
- **REQ-ORCH-079** — Relentless mode (default off) MUST apply only where the run would otherwise stop for `tasks_complete` or `no_pending_tasks`; it MUST NOT apply to any other member of the closed stop-reason set of REQ-MONITOR-301, and a member added to that set is outside its scope until this requirement is changed to admit it. It is evaluated only after REQ-ORCH-071 has been evaluated and has not extended the run. Where it applies, a model call using the summarizer's model compares the summaries of the run's completed iterations against the original user request captured at run start (REQ-ORCH-003). Where the call reports the request fully met, or where the run has no completed iteration summaries to compare, the run stops with the stop reason it already had. Otherwise a phase named "Relentless Remediation <n>" MUST be appended — n is 1 for the first such phase in the run and increases by one for each further one — holding exactly one task whose payload carries the original request, the finding, and the gaps still outstanding, and the loop continues. At most the configured maximum number of cycles (default 3) of remediation phases MAY be appended in one run; once that many exist the run stops normally. The audit call MUST be bounded by its own timeout, default 60 s. A failed, timed-out, or unparseable audit MUST NOT be retried and MUST NOT extend the run: the run stops with the stop reason it already had, exactly as it does when the audit reports the request fully met. Failing open here is deliberate and matches REQ-ORCH-007 and REQ-ORCH-113 — a model call that could not answer never prolongs a run.
- **REQ-ORCH-080** — On stop with active background children, the loop MUST drain before stopping: wait up to the shutdown-drain timeout (default 120 s; 0 disables) for still-running background children without cancelling them; children still running afterwards are logged, a drain-timeout warning issue is recorded, and teardown then cancels them.
- **REQ-ORCH-081** — Exactly one session-start event (task, workspace, role, permission mode, sandboxed flag, iteration limit) and exactly one session-end event (status, stop reason, iterations completed, duration) MUST be emitted per run, with every exit path funnelling through a single final handler. A host that publishes richer versions MUST be able to disable loop-level publication so consumers never see doubles; session lifecycle observer hooks fire either way.
- **REQ-ORCH-082** — The run-progress summary MUST be derived by evaluating these rules in order and taking the first that matches: (1) stop reason `user_cancelled` → status "paused", severity warning, message conveying that the run came to rest because a person stopped it, and not asserting which of the two person-stops it was; (2) no completed tasks and no abandoned tasks → status "completed", severity information, message conveying that the run ended without resolving any task and naming the stop reason that ended it; (3) no abandoned tasks → status "completed", severity information, message conveying that the run completed; (4) no completed tasks → status "failed", severity error, message conveying the failure, carrying the latest recorded failure detail where there is one and otherwise the number of tasks abandoned; (5) otherwise → status "completed", severity warning, message conveying that the run completed with failures and carrying both the completed count and the abandoned count. Rule 2 exists so that a run which resolved nothing is not reported in the same words as one that finished its work: it is not a failure, since nothing failed, but it MUST NOT read as an ordinary completion either. Rule 1 covers every stop a person asked for during the run, because the closed set of REQ-MONITOR-301 records `user_cancelled` for a user stop and for a mid-run cancellation alike; a run ended either way therefore reports the same summary, and no rule of this list may distinguish the two, there being nothing on the stop-reason axis to distinguish them by. Where the two are told apart at all it is on the persisted-status axis, which REQ-SESSION-073 owns and this domain does not read here; the `paused` token rule 1 emits names a state of this summary line and is not that persisted status. This summary is a status line with its own vocabulary {paused, completed, failed}; it does NOT determine the terminal run result, which follows REQ-ORCH-083 and uses a different vocabulary. The status token, the severity, and the counts or failure detail each rule names are the contract; the wording of the message is the implementation's. This requirement is the single definition of end-of-run summarization for the whole product: a document that needs to state how a finished run is summarized cites this identifier rather than restating these rules.
- **REQ-ORCH-083** — The terminal run result MUST use exactly the statuses `completed`, `failed`, `max_iterations`, `interrupted`, `error`, and the set is closed. This requirement is the single definition of that vocabulary for the whole product: a document that needs to name a terminal run result cites this identifier rather than restating the set, and a document that produces one produces a member of it. `completed` says the work finished; `failed` says the run stopped because the work could not be carried out; `max_iterations` says a configured run budget was exhausted, which is a wall-clock budget as readily as an iteration count (REQ-MONITOR-301); `interrupted` says a person stopped the run; `error` says the outcome could not be determined at all. A value outside the set is a defect and MUST raise rather than be presented as a guessed result. Which stop reason yields which of these is not fixed here: the stop-reason axis, its closed set, and its total mapping onto this vocabulary are REQ-MONITOR-301's, and this document holds no copy of any of them. Where the run recorded no stop reason at all, the result follows from the session's persisted execution status through the single mapping of REQ-SESSION-076, which this document likewise does not restate. This domain fixes no process exit code: the application does not exit when a run ends, so a run's terminal status is the whole of its machine-readable outcome here, and any mapping from that status onto a process exit code belongs to whatever surface needs one. Result construction MUST never raise.

### 14. Message-Limit Soft Pause

- **REQ-ORCH-084** — A message limit MUST be configurable as a positive integer or null, defaulting to null (disabled). It is independent of and coexists with the iteration limit (the hard ceiling); whichever fires first governs. One "message" equals one completed iteration.
- **REQ-ORCH-085** — Each completed iteration MUST increase the run's message counter by one, and the counter MUST survive a host restart by forming part of the persisted session snapshot; a new session begins at zero. When the counter reaches the message limit in force, the pause MUST take effect at an iteration boundary: no further iteration begins, and while the run is paused the loop issues no model request and spawns no child. Background children left running by an earlier iteration under REQ-ORCH-074 are unaffected by the pause and continue. The host MUST be told the run has paused, together with the current count and the limit in force.
- **REQ-ORCH-086** — Pause resolution MUST offer exactly three actions: continue (resume; the counter keeps accumulating), double (the limit is doubled for this session only, then resume), and cancel (stop with stop reason `message_limit_reached`). The desktop interface presents them as a modal dialog showing the current count, the limit in force, and the estimated token usage so far, with the three actions rendered in the one action vocabulary of REQ-SHELL-048; every action MUST be reachable from the keyboard and fully labelled at the minimum window size (REQ-SHELL-022), and the shortcut assignments are the desktop shell's to make. Resolving "double" when the limit is null leaves it null without error.
- **REQ-ORCH-087** — Where no view is attached to the session when that boundary is reached, the run MUST auto-pause there all the same, record the pause durably before it stops — the session execution status `paused_message_limit` together with the count reached and the limit in force — and never auto-continue. The pause MUST survive the application being closed and reopened, and MUST be recoverable from the session's persisted record alone, so that a session paused this way is found in that state without the run that paused it still existing and without any surface having observed the pause happen. How the store holds that state is REQ-SESSION-107's to fix and this domain restates no mechanism for it; what this domain requires is the durability and the status. Attaching a view to the session MUST immediately present the dialog of REQ-ORCH-086, and resolving it MUST clear the recorded pause in the same durable act that records the resolution, so no session is ever left recorded as paused after it has been resolved (REQ-SESSION-110); a command-palette entry for continuing the paused session is active only while the session is in that state.
