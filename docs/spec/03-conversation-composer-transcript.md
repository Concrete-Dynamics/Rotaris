# Conversation, Composer, and Transcript

## Overview

The conversation surface belongs to the single desktop application, and is backed by one queued-prompt service, one structured-question mechanism, and one session persistence model. The user types prompts into a composer that adapts to run state (start a run, continue a session, or queue a follow-up for a running iteration), invokes slash commands with inline discovery and validation, and reads a live transcript that renders user prompts, agent messages, streamed reasoning, tool calls with grouped and collapsible output, user-only edit diffs, pending-question and pending-approval prompts, and a task plan. Steering a live agent with text is a separate surface owned by the run-monitoring domain (REQ-MONITOR-070, REQ-MONITOR-137) and is not a composer mode. Prompt history, stashed drafts, and todo edits all persist to well-defined on-disk formats, and destructive operations always require explicit confirmation.

## Requirements

### 1. Desktop Composer: Input, Shortcuts, and State

- **REQ-CHAT-001** — The desktop composer MUST be a multiline text input where **Enter** (no modifier) submits, **Shift+Enter** inserts a newline, and a global **Ctrl+Return** shortcut submits the composer's contents from anywhere in the window, including while keyboard focus sits on another widget. The composer additionally accepts image attachments on the terms of REQ-CHAT-169; submission sends the text and the attached images together as one prompt.
- **REQ-CHAT-002** — These shortcuts MUST be honoured anywhere in the desktop main window: **Ctrl+L** moves keyboard focus to the composer, **Ctrl+F** opens transcript search, **F1** opens keyboard help, and **Escape** dismisses the topmost overlay in this order — the slash suggestion popup if it is showing (REQ-CHAT-026), otherwise the search panel, otherwise any open drawer. While a modal dialog is on screen the modal owns Escape (REQ-CHAT-101) and this global binding does not apply.
- **REQ-CHAT-003** — Submitting empty or whitespace-only text MUST do nothing except return keyboard focus to the composer: no run starts, no transcript row appears, no history entry is recorded.
- **REQ-CHAT-004** — The composer placeholder MUST be one of exactly these four strings, chosen by the first condition that holds, in the order given: (1) "Run active — write a follow-up for the next iteration…" whenever a locally owned run is active; (2) "Describe how to continue this session…" whenever the loaded session reports itself busy while no local run exists; (3) "Message orchestrator — type / for commands, ↑ for history…" whenever a named session is loaded and neither of the first two conditions holds — the same state in which REQ-CHAT-005 labels the primary action `Continue run`; (4) "Describe the outcome you want…" when no session is loaded, the state in which REQ-CHAT-005 labels the primary action `Start run` and REQ-CHAT-073 shows the same sentence in the empty transcript. The four conditions are exhaustive and, taken in order, mutually exclusive, so the placeholder is always determined by the composer's mode alone.
- **REQ-CHAT-005** — The primary action button beside the composer MUST state the composer's current mode via its label — `Queue` while a local run is active, `Continue run` when a named session is loaded with no active run, else `Start run` — and there MUST NOT be a separate in-composer mode label.
- **REQ-CHAT-006** — The composer text area MUST stay editable in every run state, including while a run is active. The permission-mode chip and the Stash button MUST stay enabled in every run state. The composer's persona, model, and reasoning chips select what the **next** run starts with, and MUST therefore be disabled in exactly these run states: starting, running, pausing, paused, cancelling, and the synthetic recovery state of REQ-CHAT-008. They MUST be enabled in the idle, completed, failed, and cancelled states. Each disabled chip MUST state its reason, drawn from the same set of reason texts REQ-CHAT-078 gives the run controls, and MUST publish it through both its tooltip and its accessible description per REQ-CHAT-007. This requirement is canonical for the three composer chips; the run header's own model and reasoning selectors (REQ-CHAT-078) are separate controls that change the **live** run and follow the opposite rule, being enabled only while a run is running and locally owned.
- **REQ-CHAT-007** — Sending MUST be refused in two situations, each with its reason readable by the user: while a run is cancelling, the reason MUST be exactly "Wait for the current run to finish cancelling."; while an unanswered project-setup prompt gates execution, the reason MUST convey exactly two facts — that the project setup prompt has to be answered before a prompt can be sent, and that nothing else in the application is blocked meanwhile — with its wording, punctuation, and sentence count left to the implementation. Every control this domain disables MUST publish its unavailability reason through both its tooltip and its accessible description; greying the control alone does not satisfy this.
- **REQ-CHAT-008** — The run-state label MUST use exactly this vocabulary: idle → `Ready`; starting → `Starting run…`; running → `Run active`; pausing → `Pausing after current step…`; paused → `Paused`; completed → `Completed`; failed → `Run failed`; cancelling → `Cancelling…`; cancelled → `Cancelled`; and a synthetic `Run needs recovery` when the persisted session claims busy but no local run exists.
- **REQ-CHAT-009** — The composer MUST carry four selector chips: persona; model, which until model options have been loaded MUST show a neutral loading label that names no vendor and no specific model, and MUST be disabled while it shows it, so no run can be started against a model the user never chose; reasoning effort, labelled `reasoning: low`, `reasoning: medium`, or `reasoning: high` and defaulting to **high**; and permission mode, labelled `mode: <name>`. Selecting the permission mode that grants autonomous execution MUST first raise a warning confirmation dialog in which Cancel holds initial keyboard focus, so that confirming by reflex (Enter or Space) leaves the previous mode in place.
- **REQ-CHAT-010** — Composer geometry defaults MUST be: composer block default height 150 px, minimum 110 px; transcript area minimum 180 px; composer widget minimum height 48 px. The divider between transcript and composer MUST be user-draggable and its position persisted across launches.
- **REQ-CHAT-011** — Given no active run, when the user submits non-empty text, the frontend MUST validate that a run can start; on success it MUST set the session status to starting, append a transcript row of kind `user` (displayed role `you`, timestamp formatted `HH:MM:SS` 24-hour), and record the text in prompt history. Validation also covers the attachments carried by the composer: a submission whose attachments fail REQ-CHAT-170 or whose selected model does not announce image input (REQ-CHAT-171) is refused before the run starts, with the composer contents and the remaining attachments preserved.
- **REQ-CHAT-012** — When starting a run fails for any reason (including "a run is already active" and workspace-isolation refusals), the typed text MUST be restored into the composer unchanged and an error notice raised with the failure reason (e.g. "A run is already active."). The user's text is never lost by a failed submission.
- **REQ-CHAT-013** — In demo mode (no run backend attached), a submission MUST append the user row plus a system row reading "Demo mode: run bridge is disabled." and start nothing.
- **REQ-CHAT-158** — The run header MUST carry a run-timing indicator rendering a duration as `M:SS`, or as `H:MM:SS` once the value reaches one hour. While a run is active the value MUST count the time spent inside the model call currently in flight and MUST restart from `0:00` each time the run moves on to the next model call within the same run, so a model call that is taking an unusual length of time is visible as a rising number. Once the run reaches a terminal state the value MUST freeze at that run's total wall-clock duration and stay frozen until a subsequent run starts; before any run has been started in the window the indicator MUST show no duration rather than a zero. It MUST advance at least once per second while a run is active, under the live-refresh rules of REQ-CHAT-063, and a tick MUST NOT write session state or cause a transcript publication (REQ-MONITOR-108).

### 2. Desktop Prompt Drafts and History Recall

- **REQ-CHAT-014** — The composer draft MUST be published to application state only after a 200 ms debounce following the last keystroke, on focus-out, or on submit — never per keystroke — so that typing cannot trigger per-keystroke transcript or state re-computation.
- **REQ-CHAT-015** — An unsent composer draft MUST outlive the application process. Text left in the composer MUST be stored per workspace in the platform's native settings storage, and MUST reappear in the composer character-for-character the next time a window is opened on that workspace, including after the application has been quit and relaunched. A draft stored against one workspace MUST NOT appear in the composer of any other workspace.
- **REQ-CHAT-016** — Shell-style history recall MUST work as follows: history is ordered newest-first; the first **Up** press saves the current composer text as a draft and loads the newest entry; each further Up moves toward older entries, clamped at the oldest; **Down** walks newer and, past the newest entry, restores the saved draft; every recall places the cursor at the end of the text; any other keypress (including suggestion-popup interaction and submit) resets the history walk.
- **REQ-CHAT-017** — A history entry MUST be recorded only when the text is non-empty and differs from the current newest entry (head dedupe). History MUST be recorded on run start, on continue, and on successful queueing.

### 3. Desktop Slash Commands: Parsing and Execution

- **REQ-CHAT-018** — Slash parsing rules: a command is a **single-line** text starting with `/`. A slash followed by whitespace (`"/ "`) is an escape that makes the text an ordinary prompt. Any text containing a newline is always an ordinary prompt. The first token after `/`, lowercased, is the command name; the remainder, stripped, is the argument string.
- **REQ-CHAT-019** — When submitted text parses as a slash command, the suggestion popup MUST be hidden and the composer cleared **before** the command runs. Consequence: a command whose own action submits the composer finds the field already empty and therefore cannot loop on the text that invoked it.
- **REQ-CHAT-020** — Command execution MUST report exactly one of these outcomes: executed; not-a-command; unknown command (message `Unknown command /<name>`); unavailable (the command's own stated reason, or the default `/<name> is not available right now.`); failed (the message of the command's raised error). Every outcome except not-a-command counts as handled (the text is never treated as a prompt).
- **REQ-CHAT-021** — Any non-executed outcome of a recognized-as-slash submission MUST restore the exact typed text into the composer (cursor at end) and raise a **persistent** notice titled "Command not run" (not a transient toast) carrying the outcome message. An unknown or unavailable command MUST never start a run.
- **REQ-CHAT-022** — Command registration semantics: registration order is preserved; names are lowercased on registration; registering a name that already exists **replaces** the earlier command; lookup is case-insensitive. Filter matching MUST rank name-prefix matches ahead of name-substring matches ahead of description-substring matches, preserving registration order within each rank; an empty filter lists every command.
- **REQ-CHAT-023** — Once text is recognized as a slash command (executed or not), it MUST never be forwarded to any agent as prompt content.

### 4. Desktop Slash Suggestions and Live Highlighting

- **REQ-CHAT-024** — The suggestion popup MUST open exactly when the composer holds single-line text starting with `/` with no whitespace yet after the name token (a bare `/` lists everything); typing an argument (whitespace after the name) or reaching zero matches closes it. The popup MUST never take keyboard focus, MUST anchor directly above the composer at the composer's width, and MUST show at most **8** rows (scrolling beyond).
- **REQ-CHAT-025** — Each popup row MUST render `/name — description [argument hint]` plus a kind badge drawn from the closed set `action`, `skill`, and `prompt` — the last marking an entry that came from a prompt file under REQ-CHAT-160. Unavailable commands MUST stay listed, styled as disabled text, with their unavailability reason exposed as tooltip and accessible description.
- **REQ-CHAT-026** — While the suggestion popup is showing, these keys MUST take effect on the popup and MUST NOT reach the composer's ordinary bindings: **Escape** dismisses the popup and leaves the composer text exactly as the user typed it; **Up** and **Down** move the highlighted row and stop at the first and last rows without wrapping, and MUST NOT walk prompt history; **Tab** replaces the composer text with `/name ` — one trailing space, caret after it — and does not submit; **Enter** performs the same completion, except when the composer already holds exactly `/name`, in which case it submits; clicking a row activates that row. **Shift+Enter** inserts a newline, and the resulting multi-line text dismisses the popup. Once the popup is dismissed the section 1 bindings apply again. Discovery from typing `/`, through moving the selection and completing it, to submission MUST be completable without a pointing device.
- **REQ-CHAT-027** — As the user types a single-line slash command, the leading `/name` token MUST be drawn in one of three states that differ from each other in both colour and font weight: **resolved** — the token exactly names a registered command — in the accent colour, bold; **partial** — the token is a prefix of at least one registered command but is not an exact name — in a lightened accent colour, not bold; **unknown** — no command matches — in the failure colour, bold. Weight therefore distinguishes partial from the other two independently of colour, so the states remain tellable apart without colour vision. Argument text following the name MUST be drawn in a secondary colour distinct from all three. Text spanning more than one line, and text using the `/ ` escape of REQ-CHAT-018, MUST receive no highlighting at all. The four colours MUST be taken from exactly these roles of the active theme (REQ-SHELL-145): **resolved** from the readable accent shade; **partial** from that same accent shade blended toward the surface behind it; **unknown** from the `fail` state text colour; and argument text from the secondary text colour. Every one of the four MUST then be lightened or darkened until it reaches a contrast ratio of at least **4.5:1** against the surface it is painted on, and no rendered colour may be identical to any other of the four.

### 5. Desktop Slash Command Catalogue

- **REQ-CHAT-028** — The slash catalogue MUST be rebuilt whenever the command library, the settings, or the set of discovered skills changes, and the rebuilt catalogue MUST be usable without restarting the application. Every command-palette entry MUST also be reachable as a slash command whose name is the palette entry lowercased with each run of characters outside `[a-z0-9:_.-]` collapsed to a single `-`, and whose description is the palette label with ` (<shortcut>)` appended when that palette entry has a keyboard shortcut. Where mirroring a palette entry yields a name that REQ-CHAT-029, REQ-CHAT-030, or REQ-CHAT-031 already defines, the description, behaviour, and availability gating stated there are what the user gets; the mirrored entry MUST NOT displace them.
- **REQ-CHAT-029** — `/stop` (description "Cancel the active run"), `/pause`, and `/compress` (description "Compress agent context") MUST be offered only while the frontend reports a run in the running state. In every other run state all three MUST remain listed but unavailable, with the reason "No run is active.", and MUST NOT start, continue, or queue anything. `/stop` accepted during a live run MUST cancel that run and MUST NOT send any text to an agent.
- **REQ-CHAT-030** — `/clear` (description "Clear the transcript") and `/search` MUST be offered only while the transcript holds at least one row; against an empty transcript both MUST remain listed but unavailable, with the reason "The transcript is empty.". Because of this gating, and because REQ-CHAT-073 disables the toolbar Clear action on an empty transcript, the "Transcript is already empty." outcome of REQ-CHAT-082 is reachable only when the transcript empties between the moment a control is offered and the moment it is activated.
- **REQ-CHAT-031** — The catalogue MUST also include `/new` ("Start a new session"); `/resume` and `/sessions` (both "Browse and resume sessions"); `/worktree` ("Create a git worktree"), unavailable with reason "No git service is available for this workspace." when no git service exists; `/stash` ("Stash the composer prompt"); and `/pop` ("Apply a stashed prompt", opening the stash dialog).
- **REQ-CHAT-032** — `/model <name>` MUST produce exactly these outcomes. With no argument: failure with the message "Usage: /model <name>". With a name the provider reports as withheld: failure with "<name> is unavailable. <reason>", where `<reason>` is the provider's own explanation. With a name absent from the configured catalogue: failure with "Unknown model '<name>'. Available: <catalogue>", using the literal `none` in place of the catalogue when no models are configured. On success: the model chip MUST show the new name, the selection MUST become the session's active model, and the notice "Model set to <name>." MUST be shown. While no models are configured the command MUST be listed as unavailable with the reason "No models are configured. Choose one in Settings.". The "Available: <catalogue>" clause MUST name every configured model, in the order the configured catalogue itself lists them, with no cap on how many are named; the separator and punctuation joining the names are left to the implementation, the clause being read by a person and never parsed.
- **REQ-CHAT-033** — `/persona <name>` semantics mirror `/model`: usage and unknown-name errors (e.g. "Unknown persona '<name>'. Available: …", whose available-list clause follows the same rule REQ-CHAT-032 states), and success sets the persona chip and notifies "Persona set to <name>.".
- **REQ-CHAT-034** — Every discovered skill a user may invoke MUST be reachable as a slash command under its normalized name and under each of its slash-trigger keywords. Where such a name is already taken, the command already holding it keeps it and the skill's registration for that name is skipped. Skills marked automatic-only MUST NOT appear in the catalogue at all. Invoking a skill command while skills are turned off MUST fail with "Skills are disabled. Enable them in Settings.". Otherwise the skill MUST be attached to the next prompt the user submits, regardless of any automatic selection heuristics, in the payload shape REQ-CHAT-162 fixes, and the notice "Skill loaded for the next prompt: <name>" MUST be shown. After a skill rescan, the catalogue MUST list exactly the rescanned set. A skill counts as user-invocable exactly when the invocation mode derived by REQ-WORKSPACE-056 and REQ-WORKSPACE-063 is `default` or `manual-only`; a skill whose mode is `auto-only` is the automatic-only case named above. A skill whose frontmatter states neither `user-invocable` nor `disable-model-invocation` derives the `default` mode and is therefore user-invocable, so being listed is what a skill gets by saying nothing. A skill whose load mode is `off` (REQ-WORKSPACE-062) MUST NOT appear in the catalogue either, and "skills are turned off" above means the `skills.enabled` switch of REQ-WORKSPACE-064.
- **REQ-CHAT-159** — Every catalogue command that takes an argument MUST follow the outcome pattern REQ-CHAT-032 fixes for `/model`: invoked with no argument it MUST fail with a usage message naming the command and the argument it expects; invoked with a value that is not recognized it MUST fail with a message naming the rejected value and listing the values that are available, in the order their own source lists them and uncapped; and on success it MUST apply the change and report what was set. Beyond the commands named in REQ-CHAT-029 to REQ-CHAT-034, the catalogue MUST include `/theme <name>`, matching registered theme names case-insensitively and applying the chosen theme, and `/logout <provider>`, signing out of the named provider — in each case the value vocabulary and the effect belong to the settings and model-provider domains respectively, and only the command surface is fixed here. Where a palette entry mirrored by REQ-CHAT-028 yields one of these names, the argument handling stated here is what the user gets.
- **REQ-CHAT-160** — Markdown files held in prompt roots MUST become slash commands, so a user can keep re-used prompts on disk. The roots MUST be searched in exactly this order, the first root to yield a given normalized name winning outright over every later one: `<workspace>/.agents/prompts/`, then `~/.agents/prompts/`, then the `prompts/` directory of the user-global configuration directory. Only files lying directly inside a root count. Each file MUST register under the name `prompts:<normalized stem>` and, when that name is still free, under the bare normalized stem as well. Normalization lowercases, replaces every run of characters outside `[a-z0-9:_-]` with a single `-`, and strips leading and trailing `-`; a stem normalizing to empty yields no command. Optional YAML frontmatter supplies `description` and `argument-hint`, which become the entry's description and argument hint; a file whose frontmatter is malformed or that cannot be read MUST be skipped with a logged reason and MUST NOT prevent any other file from registering. Where a name is already held by another command, the command already holding it keeps it and this registration is skipped. The catalogue MUST be rebuilt when the prompt roots change, per REQ-CHAT-028.
- **REQ-CHAT-161** — Invoking a prompt command MUST expand these placeholders in the file's body before the body is used, in one left-to-right pass so that an expanded value is never itself rescanned: `$$` becomes a single literal `$`; `$ARGUMENTS` becomes the argument string exactly as typed, with surrounding whitespace stripped; `$1` through `$9` become the corresponding positional arguments; and `$UPPER_NAME` — a `$` followed by one or more characters drawn from `[A-Z0-9_]` — becomes the value of the first `NAME=value` pair present in the argument string. A `$1`–`$9` for a position that was not supplied, and a `$UPPER_NAME` with no matching pair, MUST both expand to the empty string, so an unsupplied placeholder never leaves its own text in the prompt. Positional splitting MUST split on runs of whitespace, except that a span enclosed in matching single or double quotes forms one argument with the quotes removed and any whitespace inside preserved; an unterminated quote MUST be treated as though closed at the end of the argument string. No other escaping is recognized. The expanded body MUST then be delivered exactly as though the user had typed it: queued while a run is active (REQ-CHAT-035), otherwise used to start or continue a run (REQ-CHAT-011). The unexpanded body MUST never reach a model.
- **REQ-CHAT-162** — The catalogue MUST offer a command that lists the discovered skills into the transcript as a single system row, and a command that loads a skill from a path. The listing MUST carry, per skill, its normalized name, its scope, whether it is already in context, its trigger keywords, its description clipped to **120** characters with an ellipsis, and the path of its `SKILL.md`, and MUST report how many skills were listed. Loading MUST accept a path under the rules of REQ-WORKSPACE-057, MUST surface a load failure without registering anything, and on success MUST re-register skill commands per REQ-CHAT-034 and report the loaded skill's name. Both capabilities MUST also be reachable from the settings surface that manages skills, so neither depends on the user knowing a command name. When a skill is attached to the next prompt under REQ-CHAT-034, the payload delivered with that prompt MUST identify itself as the body of a skill document, name the skill, name the absolute path it was read from, and carry the skill file's body verbatim with nothing inserted into or removed from it; the delimiters, labels, and ordering of the three identifying facts are left to the implementation provided all three are recoverable and the body is unaltered. Attaching a skill MUST mark it as in context. A skill file that cannot be read MUST report the skill's name and the reason and MUST deliver nothing. A system row a skill command writes MUST be saved with the session.

### 6. Desktop Prompt Queue

- **REQ-CHAT-035** — While a local run is active, an ordinary (non-slash) submission MUST be queued for the running session instead of starting a run. On success the queue gains an item with a unique id and the typed text, the text is recorded in history, and a toast reads "Message queued for the next iteration.". On failure (the run no longer accepts prompts) the composer text MUST be restored and an error toast reads "Message could not be queued because the run is no longer active.".
- **REQ-CHAT-036** — Queued messages MUST render in a persistent panel directly above the composer with header "Queued messages (N)" and hint "Sent after current iteration", a scroll area capped at 150 px, and one row per prompt. The panel MUST be hidden while the queue is empty.
- **REQ-CHAT-037** — Each queue row MUST be an initially read-only single-line editor with **Edit/Save** and **Delete** actions. Saving emptied text reverts to the original; saving unchanged text is a no-op. Edits and deletions round-trip through the queue service; if the service refuses because the prompt was already picked up, the visible queue MUST re-synchronize from the service and a toast MUST read "Queued message was already picked up and cannot be edited." or "…cannot be deleted." accordingly.
- **REQ-CHAT-038** — Queued-prompt service semantics: each queued prompt carries content, an optional context snapshot, a unique (UUID-style) id, a creation timestamp, a status progressing `QUEUED → TRIGGERED → COMPLETED`, and a session ownership field (empty = unscoped). Submitting or updating with empty content MUST be rejected with an invalid-value error. Removing or updating a prompt that is not in the QUEUED state MUST fail: unknown id → not-found error; already-triggered → an invalid-state error stating it was already triggered. The `QUEUED → TRIGGERED` transition MUST be atomic and MUST succeed for exactly one caller: a second caller attempting the same transition on the same prompt MUST observe that the prompt is no longer QUEUED and MUST leave it alone, so a prompt is consumed exactly once however many runs are eligible to consume it.
- **REQ-CHAT-039** — Session scoping: ownership may come from an explicit session id or from a `session_id` key in the context snapshot. A prompt scoped to a session MUST be visible/consumable only by that session's runs; an unscoped prompt MUST be consumable by any run but invisible to session-scoped listings. Ownership MUST be preserved across edit and trigger.
- **REQ-CHAT-040** — Queued prompts MUST be consumed at the end of every iteration of the run, which is what the composer's own wording promises the user (REQ-CHAT-035, REQ-CHAT-036). At each iteration boundary, every prompt then QUEUED for the run MUST become a task named "Queued Prompt: <first 8 characters of the prompt id>" carrying the prompt text as its content, placed in a plan phase named "Queued Prompts", and MUST move to the TRIGGERED status by the atomic transition of REQ-CHAT-038; the run MUST then carry on executing those tasks. In consequence a run that has finished every task it holds MUST NOT report completion while prompts remain QUEUED for it, and a user watching the plan sees the run pick the queue up rather than stop. A run that is paused MUST NOT consume queued prompts while it stays paused; the prompts it holds are consumed at the first iteration boundary after it resumes, and remain visible and editable in the panel of REQ-CHAT-036 meanwhile.
- **REQ-CHAT-041** — A prompt queued anywhere in the application MUST be visible to and consumable by every window and every run sharing the same process, subject to the session scoping of REQ-CHAT-039 and to the exactly-once consumption of REQ-CHAT-038. The desktop's queued-messages panel MUST show exactly the prompts that are in the QUEUED status and belong to the focused run's session; queue activity in any other session MUST leave that panel unchanged.

### 7. Desktop Prompt Stash and Prompt Persistence

- **REQ-CHAT-042** — The composer's **Stash** button MUST push the trimmed composer text onto the top of the stash and clear the composer. The transcript toolbar MUST show an "Apply stash (N)" affordance with the live stash count.
- **REQ-CHAT-043** — The stash dialog (title "Prompt stash", minimum size 560×360) MUST list stashed prompts with intro copy "Apply copies the selected prompt into the composer and keeps it in the stash. Pop copies it and removes it from the stash."; **Apply** copies the selection into the composer keeping the entry; **Pop** copies and removes it. With an empty stash the dialog shows a disabled hint row "No stashed prompts. Use Stash beside the composer first." with Apply/Pop disabled.
- **REQ-CHAT-044** — Applying or popping a stashed entry into a non-empty composer MUST append it after one blank line (`<current>\n\n<stashed>`); into an empty composer it replaces the text; the composer takes focus afterwards.
- **REQ-CHAT-045** — Desktop prompt history and stash MUST persist per workspace to `<workspace>/.rotaris/rotaris-prompts.json`, holding a pretty-printed JSON object `{"history": [...], "stash": [...]}` that ends with a newline. Writing MUST be atomic: interrupting the application mid-save MUST leave either the previous file or the complete new one, never a partial or truncated file. History MUST retain at most **200** entries and the stash at most **100**, discarding the oldest beyond those limits. Blank entries MUST be discarded when loading. A file that is absent, or whose contents cannot be parsed, MUST load as empty history and empty stash rather than reporting an error. If saving fails, a persistent notice titled "Could not save prompt history" MUST be raised carrying the underlying reason, and the session MUST continue with in-memory history and stash. Pretty-printing MUST use **two spaces** per indentation level, MUST emit the two keys in the order `history` then `stash`, and MUST emit both keys even when their arrays are empty, so a written file always parses back to the same shape it was written from.

### 8. Desktop Transcript Model and Projection

- **REQ-CHAT-046** — Each transcript row MUST carry, where its category makes the field meaningful: a display timestamp, which may be empty; a role, being `you`, an agent name, `system`, or an intent marker; the row text; a row category; the tool name and the result detail; the **untruncated** tool input and output, retained so that expansion and copy can present them in full; a structured diff, on edit-diff rows only; the persona; a stable per-tool-call key; a tool status drawn from `running`, `ok`, `failed`, `blocked`; a duration; a start time; a streamed-character count, on reasoning rows; and a live-terminal stream id. The row-category vocabulary MUST be exactly: agent message, tool call, system notice, user prompt, intent note, structured-question prompt, approval prompt, user-only edit diff, streamed reasoning, delegation-context header, verifier output, and folded tool group. A user-prompt row additionally carries the ordered list of image attachments submitted with it (REQ-CHAT-173), each entry giving the stored reference, the declared media type and the byte size; a row submitted without attachments carries an empty list.
- **REQ-CHAT-047** — Persisted session rows MUST map to display kinds by role: `user` → user (displayed role becomes `you`); `system` → system; `tool` → tool; `thinking` → thinking; `verifier` → verifier; any other role → message with that role name as the display role.
- **REQ-CHAT-048** — Duplicate-reasoning hygiene: per agent, an unstamped (no duration) thinking row whose content equals the immediately previous thinking row's content MUST project to zero rows, so sessions recorded with duplicated streamed reasoning display each burst once.
- **REQ-CHAT-049** — Dead-session hygiene: when a session is not running, an unstamped thinking row MUST NOT present as live (its live start marker is dropped), and a tool row still marked running MUST display with no status and no live timer. A session with no run in progress MUST therefore never appear to be in the middle of a tool call.
- **REQ-CHAT-050** — A user-only edit diff MUST be displayed as its own row directly beneath the tool row for the call that produced it, and MUST be displayed at most once however often the transcript is re-projected. The row's text form is a header line `<path>[ [Created]] +A -R` — where `A` is the number of added lines, `R` the number of removed lines, and ` [Created]` is present only when the file did not exist before the call — followed by one `[<line>]± <text>` line per changed line, and, when the diff is cut short, a final line "… +N more lines, diff truncated". At most **50** added-or-removed lines MUST be rendered before the truncation line is emitted. A tool call that failed to write MUST carry no diff row at all, and an undo MUST render the diff of the restoration rather than reversing the original row. Edit-diff content MUST be excluded from everything a model can see: prompt text, summaries, compression input, and token estimates.
- **REQ-CHAT-051** — Whenever the run is waiting on the user, trailer rows MUST follow every recorded row, in this order: first, while structured questions are pending, a single question row reading "N step(s) — <title of the first step>" and attributed to the agent that asked; then one approval row per pending approval, reading "Approval needed — " followed by the name of the command or tool awaiting approval. Each trailer row MUST appear as soon as its pending state exists and disappear as soon as that state clears, whether the transcript was rebuilt in full or updated incrementally.
- **REQ-CHAT-052** — The transcript MUST never show rows that disagree with the session record. When a live update cannot be applied to the rows already on screen — because it concerns rows the view no longer holds, or a position outside the rows the view currently shows — the view MUST decline it and MUST re-read and re-project the whole session before showing anything further; it MUST NOT approximate by fitting the update to the nearest position it does hold. Declining is an ordinary reported outcome, not an error: it MUST NOT interrupt the user or leave the transcript blank. Correctness outranks update latency — the view MUST NOT display content it cannot confirm in order to avoid a re-read.
- **REQ-CHAT-053** — Appending rows, dropping rows from the end, replacing rows in place without changing their number, and extending the last streamed row while appending after it MUST each leave the reader's scroll position where it was and leave every row's expanded or collapsed state as the user set it. Only changes matching none of those shapes may reset the view, and such a reset MUST still restore the reader's position by the anchor rule of REQ-CHAT-071.
- **REQ-CHAT-054** — Message deduplication: a replayed message event with an already-seen stable event id MUST persist once; a cumulative committed-text snapshot MUST update the current response row in place rather than appending; a streamed response MUST finalize in place; a response arriving after a tool boundary or as a new streaming segment MUST become a distinct row.

### 9. Desktop Transcript Rendering

- **REQ-CHAT-055** — The transcript MUST scale to long conversations: the work of painting and measuring MUST depend on how many rows are visible and how many rows changed, not on how many rows the transcript holds in total. With 1000 or more rows present, scrolling, expanding a row, and running a search MUST each respond within the latency budget of REQ-CHAT-157, and appending a row MUST cost no more than it does on an empty transcript.
- **REQ-CHAT-056** — Rows of the agent-message category MUST render Markdown, with fenced code blocks in a monospace face on a shaded background of their own, bold text at a heavier weight than body text, italic text slanted, inline code spans in a monospace face, and hyperlinks in a colour distinct from body text and activatable per REQ-CHAT-076. Markdown that is still incomplete because it arrived mid-stream MUST render without raising an error and without altering the appearance of rows around it. Rendering MUST complete synchronously and MUST NOT issue any network request. An artifact an agent publishes MUST appear as an ordinary agent-message row carrying an activatable reference that opens that artifact in the library surface: the transcript has no artifact row category of its own (REQ-CHAT-046 closes the vocabulary) and no partial / hidden / full artifact display setting exists anywhere in the product.
- **REQ-CHAT-057** — Row layout MUST use a timestamp column of 52 px, a role column of 112 px, a minimum row height of 30 px, and timestamps painted in the monospace stack at 8 pt. Attribution — the role line, plus a task line when the row belongs to a named task — MUST be drawn only on the first row of a block, a block beginning at every row whose role differs from the row above it. Continuation rows MUST instead show a 2 px bar in the role gutter, coloured by the persona. Row margins are **10 px horizontally** and **5 px vertically**, so consecutive rows sit closer together than a row sits to the edge of the transcript area.
- **REQ-CHAT-058** — Desktop transcript memory MUST stay bounded however long the conversation grows: retained row measurements and retained row renderings MUST each be held only up to a fixed limit, beyond which the least recently used are discarded. A retained rendering MUST be reused only while everything that determines the row's appearance is unchanged — its identity, its content, the width it was laid out for, and its expansion state — so that inserting, removing, or reordering rows can never make one row display another row's content. Rows that are live (a running tool, verifier, or group, or reasoning still streaming) MUST be redrawn on every repaint rather than reused, so their elapsed times keep advancing. Switching theme MUST redraw every row in the new theme while leaving every row's expanded or collapsed state exactly as the user set it.
- **REQ-CHAT-059** — Row expansion state MUST be keyed by stable identity — tool/verifier rows by their tool-call key (content-hash fallback), thinking rows by start time (text-hash fallback), delegation headers by agent, groups by the key of the group's **first** member — so an opened box stays open while the group grows, while rows are inserted above it, and across model resets.

- **REQ-CHAT-163** — Text taken from a model stream for display MUST satisfy three rules. A chunk carrying a tool call MUST NOT appear anywhere in the visible message text. Content the provider marks as internal deliberation MUST appear only in the reasoning channel — a streamed-reasoning row — and never in an agent-message row. A delta consisting only of whitespace MUST be kept exactly as received and MUST NOT be dropped or collapsed, since discarding it would join Markdown blocks that must stay apart; with REQ-CHAT-157 this means the finished message equals the concatenation of the deltas received, character for character. Reasoning MUST be recognized from all three shapes providers use to carry it — a dedicated reasoning field on the delta, a thinking block inside the content, and a list of reasoning items — so that no provider's deliberation reaches the answer body for want of being recognized.
- **REQ-CHAT-164** — While a model call is in flight and the provider has produced no output of any kind for **10 seconds**, the live row for that call MUST replace its animated indicator with a stalled indicator stating that the model is not producing output and showing the elapsed seconds, so that a stall is distinguishable from ordinary slow generation. The indicator MUST revert to the ordinary animated form as soon as any further output arrives. It MUST NOT append a row of its own, MUST NOT cancel or retry the call, and MUST NOT change what the model eventually receives or what the transcript records. When a streamed phase completes, its animation MUST stop where it stands and no completion row MUST be appended.
- **REQ-CHAT-165** — The desktop MUST keep the whole conversation readable while holding only a bounded number of rows resident, so resident memory stays flat as a session grows without bound (REQ-CHAT-157). Rows beyond the resident bound MUST be released to the session record rather than lost, and MUST be brought back on demand: scrolling toward the top of the transcript MUST load the next older span and place it above the rows already shown, leaving the reader's position undisturbed by the anchor rule of REQ-CHAT-071 and leaving every row's expanded or collapsed state as the user set it. Loading MUST happen off the interface thread and MUST NOT block input. Reaching the oldest recorded row MUST be distinguishable from a load that failed; a failed load MUST report that older messages could not be loaded, MUST leave the rest of the transcript usable, and MUST be re-attemptable by scrolling again. A row brought back MUST be identical to the row that was released, so paging can never change what the transcript says.

### 10. Desktop Tool, Thinking, and Grouped Rows

- **REQ-CHAT-060** — A tool row MUST render a monospace header `▸ toolname args`, with the chevron and tool name in the tool accent colour and the outcome appended on the same line: `ok · <seconds>s`, the duration carrying one decimal place (for example `ok · 3.2s`), when the call succeeded; `failed` when it did not; and a pulsing `◉ running…` while it is still in flight. A row whose tool status is `blocked` MUST render `blocked · <seconds>s` in the theme's `fail` state text colour, and where the reason the call was blocked is known that reason MUST be reachable from the row — through the expansion of REQ-CHAT-061 and through the row's accessible description — so a blocked call is never mistaken for one that ran and failed. A row persisted with a ✓, ✗, or ! glyph already written into its text MUST render without that glyph, so the outcome is stated exactly once. The tool status vocabulary is closed to the four values `running`, `ok`, `failed`, and `blocked` named in REQ-CHAT-046 and fixed by REQ-MONITOR-105; there is no fifth value and no fallback that draws an unrecognized marker as its own literal text. A row carrying no status renders no outcome (REQ-CHAT-049), and a value outside the four MUST be treated as `failed` rather than displayed.
- **REQ-CHAT-061** — Clicking a tool row's header MUST expand it into a card that shows the **untruncated** call input and result, each introduced by a small caption in capitals reading `INPUT` and `OUTPUT` respectively. A collapsed tool row shows instead a single dimmed preview line introduced by `⤷`. A tool row with nothing extra to reveal MUST be non-interactive.
- **REQ-CHAT-062** — Thinking rows MUST summarize as `▸ reasoning · <N>s · ~<T> tok`; while streaming they render `◉ reasoning… <N>s · ~<T> tok` with both numbers counting upward, where the token figure is the streamed character count divided by 4. They are collapsible by click. A live thinking row MUST stop presenting as live after 3600 seconds without completion.
- **REQ-CHAT-063** — While any row is live — a running tool, verifier, or group, or reasoning that is still streaming and unstamped — the desktop transcript MUST refresh those rows at least once every **1000 ms**, and at least once every **250 ms** while a terminal stream is live, so their elapsed times advance and their spinners animate. Every live row MUST keep advancing regardless of how many rows sit below it. When no row is live, nothing in the transcript may animate or repaint on a timer. Timed refreshes MUST NOT move the reader's scroll position, change any row's expansion state, or make rows that are not live flicker or reflow.
- **REQ-CHAT-064** — Folding rule: a run of at least **2** consecutive tool rows that belong to the same agent and whose tool names map to the same family MUST collapse into a single group header row labelled with that family's activity word. Family membership: read/read_file/list_dir/list_files/glob/view → "reading"; edit/edit_file/write/write_file/create_file/str_replace/str_replace_editor/apply_patch → "editing"; grep/grep_search/search/codebase_search/web_search → "searching"; bash/execute/execute_bash/terminal/run_command → "running". A tool name outside those lists forms a family of its own, labelled with that tool name, so it folds only with consecutive calls to the same tool. Any intervening message, thinking, different-agent, or different-family row ends the run and prevents rows on either side of it from folding together.
- **REQ-CHAT-065** — A group header MUST carry the number of members with each outcome (ok, failed, blocked, running), the sum of the members' durations, the earliest member start time, and — while a member is in flight — that call's text. It MUST also carry the searchable text of its members, capped at **2000** characters, so REQ-CHAT-074 can match inside a collapsed group. The header MUST take its colour from the most severe member outcome, and while any member is running its duration MUST count upward. Expanding a group MUST keep the header on screen and reveal its members beneath it. Copying a group, and the group's accessible description, MUST both yield a readable summary that starts with "<family> ×N" and continues with the per-outcome counts (for example "reading ×4 · 3 ok · 1 failed"), and MUST NOT emit raw tool input or output. The header's colour is chosen by this severity ordering, highest first: `failed`, then `blocked`, then `running`, then `ok` — so one failed member colours the whole group as failed however many members succeeded, a group with no failure but a blocked member reads as blocked, and a group is only ever coloured as running or as ok when nothing in it went wrong.
- **REQ-CHAT-066** — The structured-questions tool row MUST never fold into a group, and an unsettled live terminal row MUST never fold into a group (its live preview must stay visible). Incremental updates to grouped transcripts MUST remain incremental, refusing (and falling back to a full refresh) only when the update and the view describe different transcripts.
- **REQ-CHAT-067** — A persisted display setting MUST auto-collapse all but the most recent tool-call/result pair (the last two tool rows; fewer than two → none collapse) to name-plus-chevron; it defaults **off**; per-row manual expansion overrides it; question rows and live terminal rows are exempt; toggling takes effect immediately. The tool-grouping display setting defaults **on**. Both of these are desktop preferences and are stored in the desktop preference store (REQ-CONFIG-405), not in the YAML configuration surface.
- **REQ-CHAT-166** — Tool-row content MUST be governed by persisted settings offered in the settings surface and mirrored into the catalogue by REQ-CHAT-028: whether tool results are shown, defaulting **shown**; whether tool inputs are shown, defaulting **shown**; and a rendered-line cap for each, defaulting to **10** lines for results and **2** for inputs, offered as the values 1, 2, 5, 10, 20, 50, and unlimited. These four are workspace configuration, written to and read back from the `display` section of the workspace `agents.yaml` (REQ-CONFIG-172, REQ-CONFIG-175). A cap MUST affect only what is drawn: the session record MUST retain the full text (REQ-CHAT-046), so raising a cap or reopening the session shows the rest without re-running anything. Truncation MUST be marked in the drawn text, stating that the result or the input was cut short and how many further lines exist. Expanding a row per REQ-CHAT-061 MUST show the untruncated value whatever these settings say, and a change to any of them MUST take effect immediately on the rows already on screen.
- **REQ-CHAT-167** — A persisted desktop preference MUST control whether reasoning bodies are shown, defaulting **off** so that reasoning rows summarize per REQ-CHAT-062 and reveal nothing until asked. It is global to the transcript — changing it changes every reasoning row at once — and MUST be reachable both from the settings surface and from the command palette, and therefore as a slash command (REQ-CHAT-028). Toggling MUST report the new state, MUST take effect immediately on the rows already on screen, and MUST NOT move the reader's position (REQ-CHAT-071). A row the user has expanded or collapsed by hand keeps the state the user gave it, overriding the preference for that row until its expansion state is reset (REQ-CHAT-059). The preference is stored in the desktop preference store (REQ-CONFIG-405), not in the YAML configuration surface.
- **REQ-CHAT-068** — Selecting a child agent MUST place a collapsible delegation-context header row above that agent's transcript; selecting a root agent MUST NOT produce one. Expanded, the row MUST show the task name, the persona, the task category, whether the task runs in the background or blocks its parent, the full task text, the task's dependencies, and the context inherited from the parent. Collapsed, it MUST show a single summary line conveying exactly three facts — the child agent's name, its persona, and its task, the task compacted to at most **110** characters with an ellipsis where it is cut — with the arrangement, separators, and any leading marker left to the implementation. A delegation payload whose fields are missing or unreadable MUST still produce a row showing the fields that could be read, and MUST NOT surface an error to the user or prevent the rest of the transcript from rendering; a summary line that cannot name all three facts MUST name those it can rather than showing a placeholder for the rest.
- **REQ-CHAT-069** — A transcript scope toggle MUST switch between "All activity" and "This task". Filtering keeps rows of kinds user, system, question, approval, and verifier (run-owned) plus the selected agent's rows; verifier rows MUST never be filtered out per agent. The toggle MUST name the agent "This task" refers to and show that agent's state and its live elapsed wall-clock time (REQ-MONITOR-111), so the reader can tell whose output is being shown without leaving the transcript. With no agent selected, "This task" MUST be unavailable with that as its stated reason rather than filtering the transcript to nothing.

### 11. Desktop Transcript Scrolling, Tail-Follow, and Search

- **REQ-CHAT-070** — The transcript MUST be in exactly one of two states, following the tail or not, and MUST be following whenever its scrollbar rests at its maximum. While following, the transcript MUST show a border treatment that is absent while not following, and its accessible description MUST state which of the two states is current, so the distinction is available without seeing the border. Only movement the reader causes may change the state; keyboard scrolling re-derives it, while scrolls the application performs itself — pinning to the bottom, restoring an anchor, jumping to a search match — MUST leave it unchanged. After the set of rows changes, the reader's position MUST be restored by locating the anchored row again, never by re-applying a stored pixel offset. The accessible description MUST convey which of the two states is current and, while not following, that new output is arriving out of view; its wording is left to the implementation, provided the two states are never described by the same text.
- **REQ-CHAT-071** — Before rows move, the view MUST record the identity and viewport offset of the top visible row and restore that anchor after geometry settles, so text does not jump under the reader when heights above the viewport change.
- **REQ-CHAT-072** — When rows are appended while the reader is not following the tail, a hidden "New output" toolbar button MUST appear labeled "N new update(s)", counted in **displayed** rows (grouping-aware). Clicking it re-enables tail-follow and hides itself; resuming follow by scrolling also hides it.
- **REQ-CHAT-073** — With zero transcript rows the transcript area MUST show an empty state ("No transcript yet" / "Describe the outcome you want. Rotaris will show agent activity and results here.") and the Clear action MUST be disabled.
- **REQ-CHAT-074** — Transcript search: opened by toolbar button or Ctrl+F as an inline panel with input placeholder "Search transcript…", a count label, and Previous/Next/Close. Matching is case-folded substring over role + text + tool name + detail (for group headers: role + family + the capped member blob, so a hit inside a collapsed group lands on its visible header), indexed against **displayed** rows. The count shows "X of Y" or "0 results". Enter in the field means Next. Navigation wraps in both directions. Showing a match disables tail-follow, selects the row, scrolls it to center, and paints a match highlight. Matches recompute automatically whenever rows change while the panel is open with a query. Closing the panel refocuses the composer.

### 16. Structured Questions: Tool Contract

### 27. Cross-Cutting Invariants

- **REQ-CHAT-153** — No user-only display content may reach a model. Edit-diff rows (REQ-CHAT-050), the focused-agent indicator of REQ-CHAT-069, delegation-context headers, the queued-messages panel, temporary client-side ids (REQ-CHAT-089), and every truncation marker added for display (REQ-CHAT-166) MUST be absent from prompt text sent to a model, from summaries, from compression input, and from token estimates. Consequently, adding any of them to the view MUST leave a conversation's token estimate unchanged, and a model MUST never be able to quote them back. Image attachments are not user-only display content: they are submitted deliberately by the user, they are part of the prompt sent to the model, and they count toward token estimation on the terms of REQ-CHAT-174. This requirement therefore does not exclude them.
- **REQ-CHAT-154** — Transcript memory MUST be bounded — the row-measurement and rendered-row caches of REQ-CHAT-058, together with the bounded residency and on-demand paging of REQ-CHAT-165 — and update cost MUST be proportional to what changed, not to the transcript's length.
- **REQ-CHAT-155** — Confirmation MUST precede destruction throughout the domain: transcript clearing requires the explicit confirmation dialog of REQ-CHAT-083; widening to autonomous permission mode requires the confirmation of REQ-CHAT-009; stale queue edits are refused with explanatory toasts rather than applied.
- **REQ-CHAT-156** — Composer input MUST remain reachable during runs — the composer stays editable and its primary action is labelled `Queue` (REQ-CHAT-005, REQ-CHAT-006) — so a running agent never locks the user out of typing.
- **REQ-CHAT-168** — Every parenthetical plural marker written in this document — "step(s)", "update(s)", "agent(s)", "skill(s)", "match(es)", and any other of that shape — is illustrative and MUST NOT be rendered literally. A message carrying a count MUST be grammatically correct for the count it carries, including the singular case and the zero case, with the wording left to the implementation. This rule applies to human-readable messages only; a string that is part of a machine-readable contract is unaffected.

### 28. Performance Targets (runtime-verifiable)

- **REQ-CHAT-157** — Streamed output and interface updates SHOULD appear on screen within **200 ms** of being produced. While an animation is running, the composer MUST still accept and display keystrokes within that same budget. Transcript size MUST NOT erode interactivity: the budget MUST hold with 1000 or more rows present, and the on-demand paging of REQ-CHAT-165 MUST keep resident memory flat as the conversation grows without bound. Partial streamed output MUST render without dropping or duplicating any character, so the finished message equals the concatenation of the deltas received. These budgets are acceptance criteria, measured on the machine under test rather than against named reference hardware, and the performance-benchmark domain's replay harness (`REQ-UIBENCH-*`) is the authority that accepts or rejects them: a build that misses any of them under that harness's stated fixture load fails this domain, whatever its average behaviour.

### 29. Image Attachments

- **REQ-CHAT-169** — The desktop composer SHALL accept image attachments by drag-and-drop onto the composer and by an explicit file picker. Attachments form an ordered list held alongside the composer text; each is presented as a removable entry showing its filename, declared media type and byte size, and removing one SHALL leave the text and the other attachments untouched. A submission carries the text and the ordered attachment list as a single prompt; an empty text with at least one attachment is a valid submission.
- **REQ-CHAT-170** — Accepted media types SHALL be exactly `image/png`, `image/jpeg`, `image/webp` and `image/gif`, determined from the file's content rather than its extension. A single attachment SHALL NOT exceed **10 MiB** and one submission SHALL NOT carry more than **10** attachments or more than **25 MiB** in total. A file that is rejected — unsupported type, over a ceiling, unreadable — SHALL be reported with the reason and the offending filename, and SHALL leave the composer text and every already-accepted attachment in place. The message states what was rejected and why; its wording is left to the implementation.
- **REQ-CHAT-171** — Attachment is gated on the selected model. A model entry declares whether it accepts image input; the model-providers domain owns that declaration. Given a selected model that does not announce image input, the attachment affordances SHALL be disabled and SHALL state that the selected model does not accept images, and no attachment SHALL be sent. Given a selected model that announces image input, the affordances SHALL be enabled. The gate is evaluated against the model actually selected for the submission, not the workspace default.
- **REQ-CHAT-172** — While the composer holds at least one attachment, the model selection surface SHALL either exclude models that do not announce image input or present them as unselectable with that reason given; it SHALL NOT allow a silent selection that would discard the attachments. Where the selected model is changed to one without image input while attachments are held, the user SHALL be told that the attachments cannot be sent to that model, and the attachments SHALL NOT be discarded without the user's action.
- **REQ-CHAT-173** — An accepted attachment SHALL be stored under the owning session's directory and referenced from the transcript row and the session snapshot by a relative path and a content digest, never inlined as bytes into the snapshot. Re-opening a session SHALL re-project the user-prompt row with its attachments visible as thumbnails, each expandable to the stored image. Given a stored attachment that is missing or whose digest does not match, the row SHALL state that the image is no longer available rather than failing to render, and the rest of the transcript SHALL be unaffected.
- **REQ-CHAT-174** — Token estimation SHALL count attachments using the cost the selected model declares for image input, and a conversation's estimate SHALL change when an attachment is added or removed. Where the model declares no image cost, estimation SHALL treat the attachment as an unknown non-zero cost and SHALL mark the estimate as a lower bound rather than reporting a figure that is knowably wrong.

## Data & Formats

### On-disk files (externally observable)

| File | Format | Semantics |
| --- | --- | --- |
| `<workspace>/.rotaris/rotaris-prompts.json` | JSON object `{"history": [...], "stash": [...]}`, pretty-printed, trailing newline | Desktop prompt history (≤200) and stash (≤100); atomic writes; blanks dropped on load; malformed/absent → empty |
| Prompt roots: `<workspace>/.agents/prompts/`, `~/.agents/prompts/`, `<user config dir>/prompts/` | Markdown with optional YAML frontmatter | Prompt-file slash commands (REQ-CHAT-160); first root to yield a normalized name wins; unreadable or malformed files skipped with a logged reason |
| Workspace `agents.yaml` | YAML config | The `display` section — tool result and input visibility and their line caps (REQ-CHAT-166, REQ-CONFIG-172, REQ-CONFIG-175) |
| Desktop preference store | key/value | Per-workspace composer draft (REQ-CHAT-015); transcript display preferences — auto-collapse, tool grouping, reasoning visibility (REQ-CHAT-067, REQ-CHAT-167); divider position (REQ-CHAT-010). Written user-wide under REQ-CONFIG-405 and disjoint from the YAML surface |

### Session snapshot transcript rows

Persisted transcript rows are objects with fields: `ts` (timestamp), `content`, `tool`, `detail`, `full_text`, `full_detail`, `persona`, `tool_event_key`, `status`, `duration`, `started_at`, `chars`, `stream_id`; row roles include `user`, `system`, `tool`, `thinking`, `verifier`, and free-form agent names. The session snapshot also carries user-only edit diffs (separate from transcript events), planner and agent todo state, pending questions, and pending approvals. It is the single record the transcript projects from, and the record rows are released to and paged back from under REQ-CHAT-165; no second on-disk transcript format exists.

### Structured-question answer payload

Resolved answers are a map `{<step_id>: {"selected_option": string|null, "freeform_text": string|null}}`; the model-visible rendering is a `## User Answers` section with `- **<step_id>**: <value>` lines and `(no answer)` for unanswered steps.

### Custom prompt-command files

Markdown files with optional YAML frontmatter (`description`, `argument-hint`), discovered per REQ-CHAT-160; body placeholders `$$`, `$ARGUMENTS`, `$1`–`$9`, `$UPPER_NAME`, expanded per REQ-CHAT-161, with an unsupplied value expanding to the empty string.
