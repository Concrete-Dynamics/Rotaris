# Agent Tooling, Terminal Execution, Permissions, and Approvals — 1. Public Tool Surface and Persona Grants

Part 1 of 9 of [domain 05](../05-tools-permissions-approvals.md), which indexes every part. Defines REQ-TOOLS-001 – REQ-TOOLS-040.

## Requirements

### 1. Public Tool Surface and Persona Grants

**REQ-TOOLS-001** — Given a persona configuration file (`agents.yaml`), the set of tool names a persona may declare under `tools:` is exactly: `ask_questions`, `delegate`, `background_output`, `wait_for_tasks`, `haet`, `haet_edit`, `haet_read`, `read_file`, `write_file`, `terminal`, `git_commit`, `git_read`, `todo`, `fetch`, `grep`, `glob`, `artifact_read`, `artifact_list`, `artifact_write`. The name `haet` is an accepted alias that resolves to the same tool as `haet_edit`. No other value is accepted. In particular `tools:` never names an MCP server: MCP surfaces are granted only through the persona's `mcp_servers` key and narrowed only through `mcp_tools` (REQ-TOOLS-166), so exactly one key grants a server and `tools:` carries public tool names alone.

Every name in that registry additionally carries a **capability declaration**, and this requirement is the product's single definition of it: the registry declares, for each name, three independent facets — whether the tool **reads workspace files**, whether it **writes workspace files**, and whether it **runs commands** — each either declared or not declared, so that a rule anywhere in the product can be resolved against what a tool does rather than against a name list that has to be kept in step by hand. The declaration is a property of the tool and never of the content it is handed: `terminal` declares running commands whatever the command it is given happens to do, and a command that writes a file does not make `terminal` a writer of workspace files. The declarations are:

- reads workspace files: `read_file`, `write_file`, `haet_read`, `haet_edit`, `haet`, `grep`, `glob`, `git_commit`, `git_read`;
- writes workspace files: `write_file`, `haet_edit`, `haet`, `git_commit`;
- runs commands: `terminal`;
- declaring none of the three: `ask_questions`, `delegate`, `background_output`, `wait_for_tasks`, `todo`, `fetch`, `artifact_read`, `artifact_list`, `artifact_write` — each reaches the user, another agent, the network, or the artifact store, and none of those is the workspace file tree (REQ-TOOLS-007).

`git_commit` declares both reading and writing workspace files because it records a commit in the repository that lives inside the workspace, even though it leaves the working tree's contents alone (REQ-TOOLS-142). A name added to this registry later carries its own declaration from the moment it is added, so a requirement resolved against the declaration needs no amendment when the registry grows. A tool that is not a member of this registry — a custom plugin tool (section 23) or a tool published by an MCP server (section 24) — carries no declaration at all, and a facet is never inferred from its name, its description, or anything the tool says about itself. An undeclared tool is read fail-closed, in the direction of the rule reading it: a rule that grants or widens on the strength of a declared facet treats an undeclared tool as declaring nothing and does not grant it, while a rule that withholds, refuses, or blocks on the strength of a declared facet treats an undeclared tool as declaring all three and withholds, refuses, or blocks it. A requirement in any other domain that needs the declaration cites this requirement and states only what it does with it; no requirement in any other domain holds a second copy of the facets or of the per-tool declarations above.

**REQ-TOOLS-002** — An entry in a persona's `tools:` list is accepted only when it is one of the public tool names of REQ-TOOLS-001. Any other entry fails configuration validation, and the resulting error identifies the persona, the rejected entry, and the accepted public tool names. An entry that names a server configured for the workspace fails like any other unrecognized entry, and its error additionally says that MCP servers are granted through `mcp_servers`. A persona whose `custom_tools:` plugin registers under a name that persona also declares under `tools:` likewise fails validation, so no persona ever holds two different tools under one name.

**REQ-TOOLS-003** — The verification-gate capabilities of section 22 are outside the public tool surface, and so is any capability not named in REQ-TOOLS-001. No configuration makes them callable by a persona: naming one under `tools:` is rejected like any other unrecognized entry (REQ-TOOLS-002), and no persona's prompt ever lists them among its tools. They are reachable only from the run that maintains the verification gate.

**REQ-TOOLS-004** — Missing tool prerequisites degrade availability rather than failing agent construction: a declared tool whose runtime prerequisite is absent is removed from the agent's tool set, and each removal is recorded with a stable, machine-readable reason code. Reasons that must be distinguishable: delegation tools declared without a delegation runtime; `ask_questions` declared without a user-prompt channel; artifact tools declared without an artifact store; and `artifact_write` declared by a persona that lacks `can_publish_artifacts: true`. The concrete spelling of each code is an implementation choice, provided it is stable and documented.

**REQ-TOOLS-005** — Declaring `delegate` surfaces three tools to the agent — `delegate`, `background_output`, and `wait_for_tasks` — in both the prompt's tool listing and the callable tool set.

**REQ-TOOLS-006** — A persona's declared tool set is narrowed by up to four controls, applied in this order, each able only to remove tools — never to restore one an earlier control removed, and never to add one the persona did not declare:

1. a run-scoped allow-list that applies to the orchestrator (default) persona alone; when one is present the surviving set is the intersection of that list with the persona's declared tools, and no control below it widens the result;
2. `coordinator_only: true`;
3. `read_only: true`, which reduces the set to the read-only class of REQ-TOOLS-007;
4. the per-persona `tool_restrictions` map.

Every removal is logged together with the persona and the control that removed it. `coordinator_only: true` removes exactly `terminal`, `write_file`, `haet_edit`, `haet`, and `git_commit`, and removes nothing else: every other tool the persona declared survives it, including the whole read-only class of REQ-TOOLS-007 (`grep`, `glob`, `fetch`, `haet_read`, `read_file`, `git_read`, `artifact_read`, `artifact_list`, `artifact_write`) and the delegation and task-list tools. A coordinator can therefore read, search, fetch, delegate, track, and publish, while being unable to modify the workspace or run a command. Consequently the surviving set always contains `delegate`, `background_output`, `wait_for_tasks`, `todo`, `grep`, and `glob` when the persona declared them, and never contains the five removed names.

The run-scoped allow-list is a field of the run configuration produced when a run is started from the desktop interface, recorded in that session's run-configuration record. It is per-run: it has no configuration-file key, no other source, and is absent by default, in which case it narrows nothing. A name in the list that the orchestrator persona never declared is ignored — the control is an intersection and can only remove — and every such name is logged once for the run, so a typo is visible without ever widening what the run may do.

**REQ-TOOLS-007** — The read-only tool class is exactly {`grep`, `glob`, `fetch`, `haet_read`, `read_file`, `git_read`, `artifact_read`, `artifact_list`, `artifact_write`}. `artifact_write` is deliberately classified read-only because the artifact store is not part of the workspace. The network tool class is exactly {`fetch`}, a subset of the read-only class, split out so presets can gate network access by host before any blanket read-only allow rule.

Both classes are stated against the capability declaration of REQ-TOOLS-001 and are held consistent with it: no member of the read-only class declares writing workspace files or running commands, and no name that declares either is ever a member of it, so a name added to the registry declaring one of those two is outside the class by construction rather than by a second decision. The network class is defined by where the tool sends a request and not by any of the three facets — `fetch` declares none of them, the network not being the workspace file tree — which is why the two classes overlap without either being derivable from the other. Membership of a class is not itself a facet: the classes say what a preset may allow in bulk, while the declaration says what a tool does, and a requirement needing one of them cites the requirement that fixes it rather than reading it off the other.

**REQ-TOOLS-008** — When a persona requests `terminal`, the behavior specified in sections 10–14 is exactly what serves that name. The registered public name is exactly `terminal`.

**REQ-TOOLS-009** — A tool call is governed by the policy, sandbox specification, egress configuration, and artifact store of the run that issued it, and rebuilding the issuing agent — after a retry, after a resume, or after falling back to a different model — leaves all four unchanged. No call is ever decided under, or executed with, a different run's context. When a call cannot be attributed to a run while more than one run is live, it is refused under REQ-TOOLS-020 with a reason naming the ambiguity rather than being attributed to one of the live runs. The rule-less default of REQ-TOOLS-029 applies only to a call that belongs to no run at all.

**REQ-TOOLS-010** — The tool list rendered into an agent's prompt and the set of tools it can actually invoke are produced from the same resolution, so they are always equal.

### 2. Central Permission Gate

**REQ-TOOLS-011** — Every tool dispatch — built-in, custom plugin, and MCP — passes exactly one central allow/ask/deny gate before execution. There is no ungated dispatch path.

**REQ-TOOLS-012** — The decision vocabulary is {`allow`, `ask`, `deny`}. Policy resolution never raises to the dispatcher, and an `ask` is always resolved through the approval flow first, so the dispatcher only ever handles `allow` or `deny`.

> **Narrowed by [`PD-TOOLS-011`](../../product/directives/pd-tools-011.md#pd-tools-011), 2026-10-06.** The decision vocabulary an audit
> entry is read against also holds `user-input`, carried only by the entry of a user's own terminal action (REQ-SHELL-107).
> What this requirement says of policy resolution and the dispatcher is unchanged.

**REQ-TOOLS-013** — A `deny` does not abort the run. It is returned as a tool-result error carrying the original tool-call id so the agent can re-plan. The refusal text is exactly: `Permission denied by rule '<rule_id>'. <reason> The '<tool_name>' call was not executed. Choose a different approach or ask the user to adjust the permission policy.`

**REQ-TOOLS-014** — Loop-control tool names are never gated: `finish`, `finishtool`, `think`, `thinktool`, matched case-insensitively. Such calls resolve to allow with decision source `builtin` and rule id `builtin:meta-tool`.

**REQ-TOOLS-015** — A permission request carries the tool name, the persona, the call's arguments as a name→value mapping, and at most one command facet, which is the value command matchers examine. The facet is the `command` argument when that argument is present and holds a string; failing that, the `url` argument when it is present and holds a string (this is what lets host-scoped rules match `fetch`); otherwise the request has no command facet. The facet is selected purely by argument name, so any tool whose action carries a string `command` argument supplies one. Among the public tools of REQ-TOOLS-001, only `terminal` names an argument `command` and only `fetch` names one `url`: the file-writing tool's operation selector is named `operation` (REQ-TOOLS-135), never `command`, so an operation name such as `create` or `edit` can never occupy the slot a shell command line occupies and no command matcher ever sees one. A custom plugin tool (section 23) that names a string argument `command` does supply a facet and command matchers do examine it; an author who does not want that names the argument something else. When the arguments cannot be rendered at all, the request is formed with an empty argument mapping and no facet, and resolution still yields a decision from tool name and persona alone — a rule constraining arguments, paths, or the command facet cannot match such a request, so no argument-dependent rule can allow it.

**REQ-TOOLS-016** — Two renderings exist and are never substituted for one another. The *request summary* is `<tool>: <redacted command facet>` for a request that has a command facet and `<tool>(<argument keys, sorted, comma-separated>)` for one that does not; apart from the redacted command facet itself it exposes no argument value, only key names. The request summary is what appears as `summary` in audit entries (REQ-TOOLS-079) and in the `permission.decision` and `approval.requested` events (REQ-TOOLS-061, REQ-TOOLS-083), and it is the text quoted in a session rule's description (REQ-TOOLS-024). The *argument summary* of REQ-TOOLS-057 is the other rendering: it lists redacted argument values, and it appears only in the approval payload and the approval dialog — never in an audit entry and never in a stream event.

**REQ-TOOLS-017** — A permission rule may constrain any combination of five facets: tool names (a set, compared case-insensitively), personas, path scope (`inside_workspace` | `outside_workspace`), a command matcher, and an exact argument set. The exact-argument facet matches only when the request's argument mapping and the rule's mapping carry the same set of keys and, for every key, the same textual value; a request carrying an extra key, or missing one the rule names, never matches. A rule fires only when every facet it populates matches; a facet left unpopulated constrains nothing, so a rule populating no facet matches every request. A command matcher that fails while being evaluated leaves its rule unfired and unable to produce an allow, and the resolution falls closed under REQ-TOOLS-020. The textual value of a string argument is the string itself. Every non-string value — number, boolean, null, list, nested object — is compared by its compact JSON encoding: no insignificant whitespace, object keys sorted ascending by code point, and numbers written in the shortest form that round-trips to the same value, so an integral value carries no fractional part and `1` and `1.0` compare equal. `true` compares as `true`, `null` as `null`, and `[1, 2]` as `[1,2]`. A rule author writes that form, and two implementations that agree on JSON agree on which requests a rule matches.

**REQ-TOOLS-018** — Path-scope evaluation considers only argument keys in {`path`, `file_path`, `filename`, `paths`, `base_path`, `dir`, `directory`} (string or list values). Relative paths resolve against the workspace root. `inside_workspace` fires only when every path argument lands inside the root; `outside_workspace` fires as soon as one path escapes it. A request that supplies none of those argument keys can never satisfy a path-scoped rule. A path that cannot be resolved counts as outside (fail-closed).

**REQ-TOOLS-019** — A policy is an ordered list of rules together with a default decision and a preset name. The first rule in list order whose facets all match decides the call, and no later rule affects that outcome; REQ-TOOLS-041 depends on this ordering. A policy is invalid when its preset name is empty, when any rule id is empty, when two rules carry the same id, or when a rule's outcome falls outside the vocabulary of REQ-TOOLS-012. An invalid policy produces an error naming the defect at the latest when the first call would be decided under it, and it never decides a call.

**REQ-TOOLS-020** — Fail-closed is unconditional: any exception during decision resolution yields rule id `failclosed:unresolvable-policy`, decision source `fail-closed`, and decision `ask` on interactive hosts / `deny` on headless hosts — never `allow`. The reason reads: `The permission policy could not be resolved (<detail>); failing closed to <ask|deny>.`

**REQ-TOOLS-021** — When no rule matches, the preset default applies with rule id `preset:<preset_name>`, decision source `preset`, and reason `No rule matched; permission mode '<name>' defaults to <decision>.`

**REQ-TOOLS-022** — A rule-match reason reads `Rule '<id>' (<description>) resolved '<tool>' to <decision>.` with decision source `rule`, or `session-rule` when the matching rule came from a session approval.

**REQ-TOOLS-023** — Approvals granted for the session are matched before any policy rule, most recent grant first, and they outlive the policy: after the policy is replaced or the permission mode is changed mid-session, every session approval granted earlier still matches exactly the calls it matched before — none is dropped, and none starts matching a call it did not match already. Their rule ids are `session:allow:<n>`, numbered from 1 in grant order.

**REQ-TOOLS-024** — A session approval matches only a call carrying the same tool name (compared case-insensitively), the same persona, and — when the approved call had a command facet — a command facet identical to the approved one character for character, compared before redaction. When the approved call had no command facet, the call must carry the same exact argument set as defined in REQ-TOOLS-017. Consequences a test can check: after `git push origin main` is approved for the session, `git push origin release` from that persona asks again, and `git push origin main` from a different persona asks again. The session rule's description reads `Approved for this session: <request summary>`, using the request summary of REQ-TOOLS-016.
  > **Narrowed by [`PD-TOOLS-004`](../../product/directives/pd-tools-004.md#pd-tools-004), 2026-09-23.** The rule above still governs every tool but `write_file` and `haet_edit`; for those two, a session approval matches a later call from the same persona whose path arguments resolve to the same set of paths, whatever its other arguments.

**REQ-TOOLS-025** — When the policy in force is replaced while a run is live, the agent's very next tool call is decided under the replacement, with no restart, no reconnection, and no agent rebuild in between. Decisions already returned keep the outcome they had.

**REQ-TOOLS-026** — If approval resolution raises, or returns another `ask`, the call is denied with source `fail-closed` and a reason ending `Denied because approval resolution failed: <detail>.` or `Denied because approval resolver returned no verdict.` respectively.

**REQ-TOOLS-027** — Every resolved decision, allows included, is recorded to the audit sink. A raising audit sink logs a warning and never breaks dispatch.

**REQ-TOOLS-028** — The decision-source vocabulary recorded in audits and events is exactly: `rule`, `session-rule`, `preset`, `builtin`, `fail-closed`, `user-once`, `user-session`, `user-deny`, `headless-policy`, `timeout`, `cancelled`, `presenter-error`.

> **Narrowed by [`PD-TOOLS-011`](../../product/directives/pd-tools-011.md#pd-tools-011), 2026-10-06.** The vocabulary also holds `user`,
> its thirteenth member, carried only by the audit entry of a user's own terminal action (REQ-SHELL-107). The text above
> states the behavioural target and is kept for that reason.

**REQ-TOOLS-029** — A call that belongs to no run at all is decided by a rule-less default policy whose default decision is allow and whose preset name is reported as `unrestricted`, and a warning is logged for every decision taken under it. This default is never applied to a call that does belong to a run, and no call is ever decided under a policy belonging to a different run (REQ-TOOLS-009).

**REQ-TOOLS-030** — Changing the permission mode mid-session takes effect for every live agent of the named session and for no agent of any other session. With two sessions running at the same time, a mode change in one leaves the decisions produced by the other session's agents unchanged.

**REQ-TOOLS-031** — Hook ordering invariant: policy first, hooks second. User-configured pre-execution hooks run only on the allow branch; a policy-denied call fires no hook. A blocking pre-execution hook returns the hook's refusal as a tool-result error (fallback text: `Blocked by a pre_tool hook. The call was not executed.`). Post-execution hooks see only calls that actually executed and can only append feedback (attached to the observation's extended content, or as a trailing user message when no observation exists) — they can never block. The tool result handed to a post-execution hook is truncated at the cap REQ-HOOKS-066 fixes, which this domain does not restate; what it relies on that requirement for is that the cap is applied before the hook sees the result, so a hook never receives an untruncated observation this domain produced.

**REQ-TOOLS-032** — A tool-call payload the model produced that is not well-formed is repaired before dispatch rather than rejected, and repair is attempted before schema validation, so a payload repair makes valid is dispatched as an ordinary call. Three repairs are required: JSON cut off mid-structure is completed by closing the strings, objects, and arrays still open at the cut; a single object supplied where the schema expects an array is read as a one-element array, for the fields `tasks`, `phases`, `files`, `items`, and `test_cases`; and a truncated run-completion payload is recovered as `{"message": <recovered text>}`. A payload still schema-invalid after repair is returned to the model as a recoverable tool-result error carrying the original tool-call id — the same shape a policy denial takes in REQ-TOOLS-013 — naming the tool and the schema violation and asking for a corrected re-issue. The call is not executed, the host never silently re-sends it, and the run is never ended by it; re-planning is the model's business, exactly as it is after a deny.
  > **Extended by [`PD-TOOLS-007`](../../product/directives/pd-tools-007.md#pd-tools-007), 2026-10-06.** The three repairs above still govern; the directive adds a fourth, for `write_file` alone: a call with a path and content, no `operation` and no field only another operation reads, whose file does not exist, is read as a `create`, and its result says so.

### 3. Terminal Command-Line Pattern Matching

**REQ-TOOLS-033** — A command pattern is compared token by token, never against the raw text of the command line. Pattern text and command segment are each split under shell tokenization rules, and the *i*-th pattern token must glob-match the *i*-th command token. A pattern whose final token is `*` additionally matches any number of further command tokens, so `rm -rf *` fires on a bare `rm -rf`; a pattern without that trailing `*` matches only a segment with exactly as many tokens as the pattern has. The first token of a segment — the command name — is compared without regard to letter case, on every platform and every backend; every later token is compared case-sensitively, on every platform and every backend. One rule therefore behaves identically wherever it runs, while still catching the command names of a shell that does not distinguish case. Observable consequences: `git status` does not fire on `git status-check`, and it does not fire on `git STATUS`, because the differing token is not the command name; `Remove-Item *` fires on `remove-item -Recurse .` on the PowerShell backend of REQ-TOOLS-104; and `rm -rf *` fires on `RM -rf /`. Because later tokens keep their case, a rule that must catch two spellings of a switch lists both (REQ-TOOLS-039).

**REQ-TOOLS-034** — Pattern text that cannot be tokenized, or that is empty, is a policy-construction error raised at policy build time (message pattern: `Command pattern '<text>' is not tokenisable: …` / `… is empty`), so typos fail loudly rather than silently matching nothing.

**REQ-TOOLS-035** — Compound command lines are decomposed on shell operators — `&&`, `||`, `;;`, `;`, `|`, `&`, and newline, longest operator first — respecting single/double quotes and backslash escapes. Each segment is matched independently, so in `git status && rm -rf /` the second segment still triggers the applicable deny rule. The operator that introduced each segment is retained with the segment.

**REQ-TOOLS-036** — A segment is classified "unconfident" (statically unreadable) when any of the following holds: it contains command substitution (`$(…)` or backticks outside single quotes, including inside double quotes); it cannot be tokenized (e.g., unbalanced quotes); it carries no command after redirection stripping; its head is an indirection command ({`eval`, `exec`, `source`, `.`, `xargs`, `env`, `nohup`, `time`} — reason: runs another command through that head); or its head is a shell ({`sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `cmd`, `powershell`, `pwsh`}) with a `-c`/`-Command`/`/c`/`/C` argument (inline script) or with no arguments (interactive/script execution). Redirection tokens (`<`, `>`, `>>`, `2>`, `2>>`, `&>`, `1>`, `<<`, `<<<`, and anything beginning with `>` or `<`) end the token stream considered for matching.

**REQ-TOOLS-037** — Decomposing a command line never raises. A line that cannot be parsed at all still yields exactly one segment, classified unconfident, so every input produces at least one segment for the escalation matcher to fire on.

**REQ-TOOLS-038** — Rules may use any of three command matchers, each evaluated over the segments the command line decomposes into under REQ-TOOLS-035:
- the **pattern matcher** fires when at least one segment matches at least one of the matcher's patterns under the token rules of REQ-TOOLS-033;
- the **escalation matcher** fires when at least one segment is unconfident under REQ-TOOLS-036, which includes a segment whose text is not blank yet yields no command token;
- the **pipe-to-shell matcher** fires when a segment whose first token is one of the shell names listed in REQ-TOOLS-036 was introduced by a `|` operator — that is, it consumes the output of the segment before it (the `curl … | sh` shape).

A matcher decides only whether its own rule fires. It cannot stop an earlier rule from firing, cannot alter a decision already reached, and cannot turn a command that matched no rule into an allow; such a command falls through to the preset default (REQ-TOOLS-021).

**REQ-TOOLS-039** — A starter set of nine command rules exists. The five deny rules occupy positions 1–5 of the set and the four ask rules positions 6–9, so within this family a deny is always reached before an ask:
1. `starter:deny-recursive-delete` (deny), patterns: `rm -rf *`, `rm -fr *`, `rm -Rf *`, `rm -r -f *`, `rm -f -r *`, `rmdir /s *`, `rmdir /S *`, `rd /s *`, `rd /S *`, `del /f *`, `del /F *`.
2. `starter:deny-privilege-escalation` (deny), patterns: `sudo *`, `doas *`, `su *`, `runas *`.
3. `starter:deny-force-push` (deny), patterns: `git push --force *`, `git push -f *`, `git push --delete *`.
4. `starter:deny-package-publish` (deny), patterns: `npm publish *`, `yarn publish *`, `pnpm publish *`, `uv publish *`, `twine upload *`, `cargo publish *`, `gh release create *`.
5. `starter:deny-pipe-to-shell` (deny), using the pipe-to-shell matcher of REQ-TOOLS-038.
6. `starter:ask-unreadable-command` (ask), using the escalation matcher of REQ-TOOLS-038 — a command whose effect cannot be read from the command line alone.
7. `starter:ask-history-rewrite` (ask), patterns: `git reset --hard *`, `git clean -fd *`, `git clean -df *`, `git checkout -- *`, `git rebase *`, `git filter-branch *`.
8. `starter:ask-dependency-install` (ask), patterns: `pip install *`, `uv pip install *`, `uv add *`, `npm install *`, `npm i *`, `yarn add *`, `pnpm add *`, `cargo install *`, `brew install *`, `apt-get install *`.
9. `starter:ask-container-control` (ask), patterns: `docker *`, `podman *`, `kubectl *`, `systemctl *`, `Remove-Item *`.

Every pattern listed above is matched under the token rules of REQ-TOOLS-033: each listed spelling stands on its own, and a spelling that is not listed does not match by inference. A command line carrying a segment classified unconfident under REQ-TOOLS-036 — one whose flags or structure cannot be read statically — is caught by rule 6 and by no pattern rule.

**REQ-TOOLS-040** — The starter destructive set belongs to the shipped presets only. The rule-less `unrestricted` default of REQ-TOOLS-029 does not carry it.
