| D-01 | **Re-derived. The layout is gone; a closed *set* survives and a location rule replaces it.** `REQ-SESSION-003`, `REQ-SESSION-004`, `REQ-SESSION-005` and `REQ-SESSION-010` are withdrawn, each naming its successor. What is fixed now: a session's record is reached by **one workspace plus one session id** and by nothing else, and lives in a store found through the workspace identifier **rather than through a path**; beside it a session has a place holding **exactly three kinds of file and nothing else** — its log, its human-readable summary, and the bodies of artifacts, attachments and images. | D-13 | **Re-derived: a file became a record and the field set survived.** The **listing record** holds exactly twelve fields with fixed reader-side defaults, and building a listing MUST read **nothing but listing records** — not the session's state, not its transcript, not its history — so that **the cost of a listing grows with the number of sessions and with nothing else**. | D-14 | **Re-derived, and it survives — the mechanism was nearly withdrawn with its stated reason and both requirements in fact stand.** The resident transcript is bounded at **5000** rows; when an append would exceed that, the oldest rows are released in whole pages of **50** *before the append is made*; releasing MUST NOT change the index any row was given, and a reader asking for a row older than the resident window MUST be served it **from the released pages**. Released pages are retained unaltered, in release order, and **never rewritten, reordered or trimmed**. `REQ-SESSION-192` declares itself the product's **single definition of transcript residency** and `REQ-SESSION-131` the single definition of the released-page store; a document relying on either cites the identifier and holds no copy of the cap. `REQ-CHAT-165` depends on both by name. *The stated purposes changed — a bounded resident cost and an unbounded complete history, rather than bounding what a whole-file save rewrites — and the observables did not.* | HARD | REQ-SESSION-131, REQ-SESSION-192, REQ-CHAT-165, REQ-EVENTS-052 |

| D-25 | **Re-derived: the conflict is gone and exactly one ladder remains.** This row recorded two incompatible Windows replace-retry schedules. `REQ-LIBRARY-043`'s ladder is withdrawn with its document layout, and the requirement gives the reason: **no writer outside this application can reach a record in that store** (`REQ-LIBRARY-158`). `REQ-SESSION-033`'s ladder is **narrowed, not withdrawn** — it survives precisely because its file *is* reachable by one — and declares itself "the only replacement ladder this domain states" (D-06). **The resolution is one-sided, and that is what closes OQ-11**: not that neither ladder has a file left to govern, which is false, but that one of the two lost its subject while the other kept it. Nothing remains to reconcile. **The gap OQ-44 names is unchanged in kind and sharper in contrast:** the one ladder the corpus states is in the sessions domain, and `REQ-TRACE-061` — which faces exactly the case it was written for — still requires a failed replace **re-raised** with no ladder at all. Same gap, two sites. **Measured 2026-09-02, and the gap changes character from *sufficient and unspecified* to *necessary and unspecified*.** On shared storage **6.2 % of rename-over-existing calls failed with no other opener present at all** — 37 of 600 first attempts, against **0 of 300** on local storage — so a ladder stops being a defence against a rare foreign handle and becomes the normal path for roughly one document write in sixteen. | D-27 | The in-memory representation of session state and the concrete serializer. **Handle lifetime is free on the write side and not on the read side, and the two halves must be read separately.** *Write side, free:* no file in the product is replaced by rename over a handle its own writer holds — every append-and-compact store is a record now and the one file still opened in append mode (**the session's log**, `REQ-SESSION-142`) is never compacted (see D-28, withdrawn). ***The fact survives and the name does not.*** A previous pass called that file `evidence/debug.log`. **That path is withdrawn and must not be cited**: it belonged to the session-directory layout domain 18 carried, `REQ-SESSION-142` now names only "the session's log, which is a file so that a person can open it in an ordinary text reader", and `REQ-SESSION-002` closes the per-session set at three **kinds** and fixes no filenames at all. *Read side, not free:* ADR-0004 rule 1 still forbids a reader holding a descriptor across a call, on every thread including the traceability engine's worker threads. **The rule is unchanged; its stated cause was wrong and is corrected by measurement.** It is not that the runtime declines to request share-delete — `spikes/windows-writer-handle-compaction.md` §3.2 shows an `unlink` **succeeds** against a runtime-held handle, from another process too, while both fail against a holder requesting read/write sharing without delete. The accurate statement is that **the replace-by-rename call cannot replace a destination with any open handle, whatever its share mode, and fails even where the holder explicitly permits delete.** The blocker is the chosen replace mechanism, not the share mode and not the filesystem — which is why the correct trigger for revisiting is a binding exposing the platform's own file-replacement call, measured succeeding against a held reader that went on seeing complete previous contents. **A second measurement has since added a cause the first one could not see and it is not a foreign handle at all**: on shared storage the replace-by-rename call fails at **6.2 %** with **no other opener present**, so the read-side rule is necessary but is no longer the whole story and the ladder is a normal-path requirement rather than a rare-contention defence (D-25). *Buffering:* also not free — `REQ-EVENTS-029` read with D-16 forbids group commit across events, **and the per-event insert is now measured to cost −4 to +31 µs at p50 inside the transaction that is already committing the row it is paired with**, so the prohibition costs nothing rather than being a cost the design absorbs. *Directory flush:* the two spikes appear to disagree and do not. The writer-handle spike measured success on a **write-opened** directory handle, 200 of 200; the storage spike measured `EPERM` on **every** spelling including local NTFS. **The reconciliation is handle mode and it is INFERRED rather than measured** — both figures are kept rather than one being picked — and what the pair establishes operationally is that the naive call an implementer would add **fails everywhere**, so no durability step may assume the containing directory is flushed (OQ-12). | FREE (write side) / HARD (read side, and no group commit) | REQ-SESSION-142, REQ-EVENTS-029, REQ-EVENTS-098; `spikes/windows-writer-handle-compaction.md` §3.1–3.3; `spikes/remote-and-synchronised-storage.md` §8; `spikes/commit-on-the-publish-path.md` §5.2 |
