# Session Persistence, Resume, and Background Sessions

## Overview

Every run persists its complete observable state in the workspace's durable session store, recorded as the run proceeds and never in a way a reader can observe half-applied, so that a crash loses only work for which no save was ever requested. That store is machine-local and is found through a stable workspace identifier that travels with the workspace (REQ-SESSION-197, REQ-SESSION-198); a small, closed set of per-session files sits beside it for the things a person opens directly. Because the store is machine-local, backing up a workspace does not back up its sessions — a property the product states rather than leaving a user to discover (REQ-SESSION-200), and for which it offers a backup of the whole store that is valid while runs are live and a restore that is always explicit (REQ-SESSION-201). A session is in one of two conditions and never a third (REQ-SESSION-159): it is live, owned and executed by the one running instance of the application, which publishes its progress to every surface that instance shows; or it is not running, and exists as a persisted record that is opened and continued from that record. A persisted session can be listed, resumed with its full transcript and metrics intact, repaired when the process that owned it died while its record still asserts a run in progress, exported — as a standalone trajectory document, and as the timeline, issues, metrics and permission-audit records in a form a stock tool can read (REQ-SESSION-199) — and deleted cleanly. One shared run lifecycle serves every way a run can be started — in the foreground of a desktop window, detached into the background, or launched from the requirement board — so locking, background execution, message-limit pauses, cancellation, and terminal results behave identically regardless of how the run was started.

## Requirements

### 1. Where a Session Is Stored

- **REQ-SESSION-001** — A session's durable record MUST be reachable from the workspace the run was started against — the workspace the desktop window has open — together with the session id of REQ-SESSION-009. One workspace plus one session id MUST resolve to that one record from every view and every background worker in the application, and binding the run to a worktree MUST NOT move it: per REQ-SESSION-085 the worktree becomes the run's effective root and is what the state records as `workspace_root`, but the record stays anchored to the invoking workspace. The record lives in that workspace's durable session store, which is machine-local and is found through the workspace identifier rather than through a path (REQ-SESSION-197, REQ-SESSION-198). Exactly two kinds of session-derived data are held outside that session's **own record**: the improvement artifacts of REQ-SESSION-007, which are additionally reachable at workspace scope and are held at that scope in the same workspace store rather than in any session's record (REQ-LIBRARY-042), and the checkpoint refs of REQ-SESSION-162, which are objects in the user's own repository and outside any store this application keeps. The per-session files of REQ-SESSION-002 belong to the same record and are not a third kind.
- **REQ-SESSION-002** — Beside its stored record a session MUST have a place on disk holding exactly three kinds of file and nothing else: its log (REQ-SESSION-142), its human-readable summary (REQ-SESSION-140), and the bodies of the artifacts, attachments and images the session produced or received, which the record references and never holds inside itself. Each appears only once the matching activity has occurred and MUST NOT be assumed present by a reader — a session that produced no artifact has no artifact bodies, and a session whose logging never attached has no log. That set is closed, and closed deliberately: no other per-session file is written there, and in particular no file is ever written to signal anything to another process, which is what forbids a control channel over the filesystem into a session (REQ-SESSION-159). The place MUST be reachable through the reveal action of REQ-SESSION-191, MUST be held with the store rather than inside the workspace (REQ-SESSION-198), and MUST be removed with the session (REQ-SESSION-166).
- **REQ-SESSION-003** — *Withdrawn.* Every part of the split state layout it fixed is a record in the store rather than a file: the resumable state, the transcript rows, the edit diffs, the launch audit and the released transcript pages. Both guarantees it carried are held elsewhere and neither is lost — that a session created but never run carries no launch audit and loads with an empty configuration snapshot is REQ-SESSION-138's, and that released pages come to exist only once the resident window overflows is REQ-SESSION-131's and REQ-SESSION-192's.
- **REQ-SESSION-004** — *Withdrawn.* The evidence files it named are records in the store rather than files, and what it guaranteed by requiring them to exist from the first save — that a reader of a session that produced none of a given kind gets an empty answer rather than a failure — is REQ-SESSION-132's. The one name that survives as a file is the session log, fixed by REQ-SESSION-142 and opened by REQ-SESSION-191; the durable event history and the record of what a trim dropped are REQ-SESSION-143's and REQ-SESSION-144's.
- **REQ-SESSION-005** — *Withdrawn.* A clean-room product has no predecessor layout to fall back to, so a legacy whole-state document cannot exist; the stored resumable state is the only resumable state (REQ-SESSION-037).
- **REQ-SESSION-006** — The listing record (REQ-SESSION-030) and the human-readable summary (REQ-SESSION-140) MUST both be derived, rebuilt from state on every save; a loader MUST take its facts from the session state and never from either. The summary stays a file precisely because nothing in the application reads it: it exists so a person can open it, and it is on no path a run waits for.
- **REQ-SESSION-007** — An improvement artifact referenced by the session state MUST remain retrievable in two ways that do not depend on each other: as that session's own artifact, and from the workspace-scoped improvement library, so that an artifact one session produced is available to a later run in the same workspace. Both retrievals MUST survive resume, and neither may fail because the other was used. Whether the body is held once and referenced twice or held twice is not observable and is not fixed here; what is fixed is that deleting the session removes the session's own reference and never reduces the workspace-scoped library (REQ-SESSION-166).
- **REQ-SESSION-008** — *Withdrawn.* The alias existed only for compatibility with a predecessor layout this product does not have; reaching the session log is a desktop capability and is carried by REQ-SESSION-191.
- **REQ-SESSION-197** — A workspace MUST carry a stable identifier of its own, written into the workspace's `.rotaris/` beside the configuration the user edits, in a form a person can read and version control can track. It MUST be minted once, when the product first prepares the workspace, and MUST NOT change afterwards for any reason — not when the workspace is moved, renamed, copied, or carried through a synchronising folder, and not when it is opened by a different version of this product. It is the workspace's name for its durable session store (REQ-SESSION-198), which is located by that identifier and never by the workspace's path, so moving or renaming a workspace folder preserves its session history and a workspace found at a new path is the same workspace. Three consequences MUST hold, and all three are intended. Because the identifier travels with the workspace while the store does not, the same workspace opened on two machines resolves to two stores and each machine keeps its own session history (REQ-SESSION-198). Because the identifier is the only thing binding a workspace to its sessions, the product MUST NOT mint a replacement over an identifier it can read, and MUST report an identifier it cannot read as a condition to be resolved rather than overwriting it — overwriting it would silently orphan every session recorded under it. And a workspace whose store holds nothing for this identifier lists no sessions, which is an ordinary state and not an error (REQ-SESSION-043). **One narrow exception, and only one.** The restore of REQ-SESSION-201 MAY establish this workspace's identifier as the identifier the artifact carries, and no other action ever may. It exists because the identifier file need not travel with a user's version control, so on the recovery journey the backup was minted for — the machine is gone, the repository is cloned onto another one, the workspace is opened once, and the artifact is then restored — the freshly prepared workspace has already minted an identifier of its own while the artifact carries the original, and the restored sessions would land in a store the open workspace can never resolve to, with editing a file by hand as the only remedy. Five conditions bind the exception, and it is unavailable unless every one of them holds. **Only there.** It is available only inside the restore action of REQ-SESSION-201; no other path gains it, ever — not opening or preparing a workspace, not the explicit repair of REQ-SESSION-060, not a migration, not an update, and not a later convenience however similar the situation looks. **Only on explicit confirmation.** It MUST require the user to confirm it, and the confirmation MUST name both identifiers — the one this workspace carries now and the one the artifact was taken from — and MUST state that the sessions this workspace's own store holds become unreachable from this workspace once it is done. It MUST never happen automatically, MUST NOT be the default or the pre-selected outcome, and reporting the mismatch and going no further MUST remain a correct outcome of the restore. **The absent case is not this exception.** Where the workspace carries no identifier at all, the restore establishes one exactly as first preparation does, by a create that succeeds only where nothing is there to replace, and no confirmation of this kind is required or offered — establishing an identifier where none exists replaces nothing and orphans nothing. **An unreadable identifier is still reported and never overwritten.** An identifier that is present but cannot be read MUST be reported as a condition for the user to resolve, by this action as by every other; the exception is for an identifier the product can read and can therefore name to the user, and is not a repair for one it cannot. **The displaced store is kept.** The store the replaced identifier named MUST be moved aside and retained, never deleted, and the confirmation MUST say that it is kept and where it went, so that a user who confirms this and then finds they meant something else still has their history. **Why the exception is confined, and not merely that it is.** The rule it is an exception to is what keeps a workspace's sessions attached to it when its folder is moved, renamed, copied, or merely spelled differently — the ordinary and frequent way products of this kind lose a user's history, and the whole reason this requirement binds sessions to an identifier rather than to a path. That protection earns its place on every path a user takes, and the recovery it makes awkward arises once in a workspace's life if it arises at all. So the recovery is paid for exactly once, inside a single action a person asked for and confirmed in as many words, rather than by relaxing the rule generally — which would trade a protection that applies constantly for a recovery that applies rarely. An implementation that finds this exception useful anywhere else has drawn the wrong lesson from it.
- **REQ-SESSION-198** — The durable session store for a workspace MUST be machine-local: held in the per-user location REQ-STARTUP-145 fixes, never inside the workspace and never anywhere the workspace's own location may be synchronised or shared from. Which per-user location that is — the one local to this machine rather than the one a platform replicates to the user's other machines or to another copy of their profile — is REQ-STARTUP-145's to state and is cited here rather than restated, because a store this requirement relies on being one machine's own is not one machine's own the moment it is replicated to a second. This holds always, and MUST NOT be made conditional on detecting that a particular workspace is on shared storage: such detection is unreliable, and a second storage layout would be a second thing to get right on a path where being wrong costs a user their history. Four properties follow and MUST be observable. A workspace on a network share or in a synchronising folder MUST be fully usable — sessions start, run, are listed and are resumed there exactly as anywhere else. The user's own material — their repository, their requirement documents, their configuration, personas and model slots — MUST stay exactly where they put it and MUST be untouched by this rule. A session recorded on one machine MUST NOT appear on another, which is what makes a lock naming another machine evidence that something is wrong rather than an ordinary condition (REQ-SESSION-046, REQ-SESSION-048, REQ-SESSION-054). And the per-session files of REQ-SESSION-002 MUST be held with the store rather than inside the workspace, so that one session's record is never split across storage a synchronising client may reach and storage it may not. A store that cannot be opened is not worked around: no session in that workspace starts, and the condition is reported with its reason (REQ-SESSION-089).
- **REQ-SESSION-200** — Because the durable session store is machine-local (REQ-SESSION-198), backing up, copying, cloning or synchronising a workspace does **not** carry that workspace's session history with it, and the product MUST state that property itself rather than leave a user to infer it from an absence. What sits outside such a backup MUST be named rather than implied: every session record the store holds — the resumable state, the transcript rows and their released pages, the durable event history, the timeline, the issues record, the metrics document, and the evidence records with the permission audit among them — the workspace-scoped improvement library (REQ-SESSION-007), and the per-session files held with the store (REQ-SESSION-002), which are the session log, the summary, and the artifact, attachment and image bodies. What *is* carried MUST be named alongside it, because the statement is otherwise alarming rather than informative: the user's own material — their repository, their requirement documents, their configuration, personas and model slots — travels exactly as they left it; the workspace identifier travels with the workspace, so a workspace moved, renamed or restored on this machine finds its own sessions again (REQ-SESSION-197); and checkpoints are objects in the user's repository (REQ-SESSION-162). The statement MUST also convey where the two remedies are, since naming a gap without naming its fix is not a disclosure: the whole-store backup of REQ-SESSION-201 for carrying the store itself, and the exports of REQ-SESSION-189 and REQ-SESSION-199 for carrying individual records into a form other software can read. It MUST be reachable in the ordinary course of managing a workspace's sessions (REQ-SESSION-182), and MUST NOT be delivered only as part of a failure or a remediation message — a user who has already restored a workspace and found no history in it has been told too late, which is the precise failure this requirement exists to prevent. The wording is left to the implementation; what is fixed is what it conveys.
- **REQ-SESSION-201** — The application MUST offer a user-initiated action that produces one artifact holding the whole of a workspace's durable session store, and a second that restores such an artifact. **One artifact, the whole store.** The backup MUST cover everything that workspace's store holds — every session's record, and the workspace-scoped improvement library (REQ-SESSION-007) — together with the per-session files held with the store (REQ-SESSION-002), because those are equally outside anything a workspace backup reaches (REQ-SESSION-200). It MUST NOT reach outside that store: the repository, the requirement documents, the configuration, the personas and the model slots are the user's own material, are already where the user keeps them, and are not this artifact's to duplicate. The destination MUST be a file the user chooses through the platform's save dialog, with no implicit destination and nothing written until a destination is chosen (REQ-SESSION-189). **A backup in progress MAY be abandoned by the user, and abandoning it MUST cost nothing.** Abandoning it MUST discard whatever partial artifact had been produced, MUST leave the store exactly as it was, and MUST NOT leave a partial, truncated or otherwise unreadable file at the destination the user chose — a file that is there and cannot be restored is worse than no file, because a user who has one believes they have a backup. This is stated rather than left to follow from the mechanism: a backup of a large store is a multi-second action taken while runs continue, so a user will meet the question of whether they may stop one, and a requirement that enumerates what a backup does while saying nothing about stopping it leaves that case answered by nothing. Abandoning MUST NOT be confused with failing: a backup the user stopped is not a condition to report as a fault. **It is valid while runs are live.** Taking a backup MUST NOT require any session to be stopped, MUST NOT pause, delay, throttle or otherwise disturb a run, and MUST NOT be refused because a session is live. What it produces MUST be a state of the store that a reader could have observed at one moment: never a mixture of parts taken before and after a write, and never an artifact that restores to a store no run could have left behind. **Restore is explicit.** A restore MUST be an action a person takes deliberately; nothing may restore on its own — not at startup, not on finding an artifact, not as a repair, and not as a consequence of any other action. Before anything is changed the product MUST convey which workspace the artifact was taken from, when it was taken, and what the restore will do to the store that is there now. **Restore never silently merges.** A restore MUST NOT combine an artifact's contents with an existing store. Where the target store already holds sessions, what becomes of them MUST be an outcome the user chose while being told what it does to them; a session present in the target and absent from the artifact MUST NOT quietly survive, and one present in the artifact and absent from the target MUST NOT quietly appear, without that having been stated first. **Restore is refused rather than half-done.** A restore MUST be refused while any session in the target store is live (REQ-SESSION-159), for the same reason REQ-SESSION-164 refuses a checkpoint restore on a session that claims to be running: it would contend with writes from a run still recording itself. **That refusal holds for the whole of the restore and not only at the moment it is asked for.** It is not discharged by answering the question once and then proceeding on the answer: a session that becomes live after the question was answered and before the restore has finished is a session the user was never told about, so what becomes of it cannot be an outcome the user chose, and replacing it destroys a run on the strength of a fact that had already stopped being true. From the moment the product answers that question until the restore has completed or been abandoned, no session in the target store may become live; where one has, the restore MUST be refused rather than carried through. Whether the refusal of new runs is put in force before the question is asked, or the question is asked again once that refusal is in force, is left to the implementation — what is fixed is that there is no window between the two into which a run may be admitted. **A restore never disturbs a live session.** It MUST NOT stop, cancel, interrupt, or require a run that is under way to give up the store it is recording into; the obligation the backup carries not to pause, delay, throttle or otherwise disturb a run holds here too, and the restore's remedy on finding a live session is to refuse, never to clear it out of the way. A run that is asked to stand aside and whose record is then replaced has been destroyed by the restore whether or not it complied, which is the outcome this clause exists to make impossible. **A lock this machine cannot prove dead is reported, not treated as a live run, and MUST NOT make a store permanently unrestorable.** The refusal above exists because a run still recording itself would contend with the replacement; a lock record naming a machine other than this one is not such a run — nothing on this machine is writing under it, and by REQ-SESSION-198 the store is this machine's own, so such a record is the condition REQ-SESSION-048 describes rather than a run in progress. Where the target store holds such records, the restore MUST report them **together, as one condition covering all of them**, stating how many there are and what they mean, and the user MAY then confirm the restore and proceed; it MUST NOT require them to be cleared one at a time through REQ-SESSION-183 as a precondition, and MUST NOT simply refuse. Without this the requirements compose into a store that cannot be restored at all: such a lock counts as live by construction (REQ-SESSION-056), is never reaped (REQ-SESSION-047), and has one per-session confirmed release as its only remedy (REQ-SESSION-183) — so the recovery action a user reaches for when a store has gone wrong is blocked by exactly the records that recovery is about to replace. **The confirmation MUST state the risk rather than only the condition**: if that store genuinely is reachable from another machine, a run there may be writing now, and the restore replaces what it writes. Proceeding MUST be a choice the user makes having been told that, MUST NOT be automatic, and MUST NOT be the default or pre-selected outcome. This changes nothing about a lock naming **this** machine, which is a run in this application and is refused as before. A restore that fails for any reason MUST leave the store exactly as it was — there is no partly restored store, and no reader may observe one. **Nothing bounds how long a restore takes, and that silence is deliberate.** The backup carries timing obligations because it runs while sessions are live; the restore carries none because it cannot run while one is — by the clause above nothing in the target store is live for its duration to disturb, so there is no run whose progress a slow restore could damage and no budget this requirement owes. That absence is a decision rather than an omission, and it is not licence in the other direction: it does not permit a restore to run alongside a live session, which is precisely what is forbidden above. **A restore under way MUST be visible to the user who asked for it, and that is a separate obligation from its duration.** The absence of a duration bound is a statement about not disturbing runs; it says nothing about what a person waiting on the action is shown, and the two MUST NOT be collapsed. The request MUST be acknowledged within the gesture budget the shell carries for any other action (REQ-SHELL-150), and while the restore runs the product MUST convey that a restore is under way and that the workspace's sessions are unavailable until it finishes. **What is required is acknowledgement, not progress reporting.** No proportion completed, no list of stages, and no estimate of remaining time is required, and none may be represented as more precise than it is; a restore that reports stages would have to report from inside a sequence whose value is that it is indivisible, and nothing here may be read as licence to make that sequence interruptible in order to have something to report. The obligation exists because the interval scales with how much the store holds, and nothing in this product bounds that: no requirement caps how many sessions a workspace keeps or discards them with age. A workspace that answers nothing for several seconds is therefore a state this requirement permits, and it MUST NOT present as a product that has stopped responding. **The artifact names its workspace.** It MUST carry the workspace identifier it was taken from (REQ-SESSION-197), and a restore into a store belonging to a different identifier MUST be reported as what it is rather than performed silently, so a backup cannot be poured into the wrong workspace by accident. Where the two identifiers differ, and only here, the user MAY confirm that this workspace takes the artifact's identifier: that is the single exception REQ-SESSION-197 permits to its rule that an identifier the product can read is never replaced, every condition on it is stated there and binds this action, and it is what makes this action complete on the recovery journey it exists for — a machine lost, a repository cloned onto another, a workspace opened once, and the artifact then restored. Reporting the mismatch and going no further MUST remain available as the outcome, and no other action in this product may establish an identifier over one it can read. **It is not an export, and neither substitutes for the other.** This does not duplicate REQ-SESSION-199 or REQ-SESSION-189 and MUST NOT be collapsed into either: an **export** is a record rendered so that software knowing nothing about this product can read it, and is what discharges REQ-EVENTS-166; a **backup** is the store rendered so that this product can put it back, and discharges nothing about readability. Different artifacts, different purposes. The backup MUST NOT be offered as a way to read a record, and no export may be offered as a way to restore one. Nor does the artifact collide with REQ-SESSION-028's rule that no second, whole-state copy of a session is written anywhere: that rule governs what a *save* writes, and forbids the product keeping a duplicate the store could disagree with. This artifact is written only when a user asks for it, is never read back in place of the store, and is never consulted by anything the product does except a restore the user asked for. **It is not a channel.** Like the exports, the backup is a user-initiated action producing a file at the moment it is asked for: it MUST NOT refresh itself, MUST NOT be offered or usable as a way to observe a run in progress, and no surface may be built on repeating it (REQ-SESSION-071, REQ-SESSION-199). Finally, because the artifact is the store whole, it necessarily carries records that deliberately have no export because they hold unredacted user and tool content — the tool-call evidence of REQ-SESSION-136 among them. That is not a widening of what may be exported, because the artifact is not readable material handed to other software; but where this action is offered the product MUST convey that the artifact carries the store's contents in full, so that a user deciding where to put it decides knowing that.
- **REQ-SESSION-202** — Where this machine has a place for a workspace's durable session store and no store is in it, that MUST count as a store that could not be opened, and MUST NOT be treated as a workspace for which this machine holds no store (REQ-SESSION-043). The two look alike from outside and are not alike. A workspace this machine has never run has nothing kept for it at all; a workspace whose store has a place and is not in it has had something happen to it — a restore that failed part way (REQ-SESSION-201), a copy or a move interrupted before it finished, a deletion that took part of what it found, or a person tidying by hand — and which of those it was is not knowable afterwards. The condition persists until something resolves it, and it is stated here rather than left to the mechanisms that produce it, because closing one route to it does not close the others. **The product MUST NOT put a new store there, and MUST NOT report the workspace as holding no sessions.** Either would replace an unknown with a silent fresh start: whatever sessions the workspace had, if it had any, become unreferenced, and the user is told by an empty list that this workspace has no history on this machine — learning otherwise, if ever, long after the moment they could have acted. That is the harm REQ-SESSION-197 forbids one level up, where an identifier the product can read is never minted over and an identifier it cannot read is reported as a condition for the user to resolve rather than overwritten; the same rule governs the store that identifier names. **It is reported and refused as any other store that cannot be opened is.** No session in that workspace starts (REQ-SESSION-198, REQ-SESSION-089, REQ-EVENTS-084), the listing reports the condition rather than an empty list (REQ-SESSION-043), and what is reported MUST say what was actually found — that the place for this workspace's store exists and the store is not in it — because there is no store present to give a reason of its own, so the store's own reason that REQ-SESSION-089 otherwise carries unaltered does not exist for this condition and MUST NOT be invented. **The product MUST NOT resolve it by itself.** An action that establishes a new store in that place MUST be one the user takes deliberately, having been told what was found and that it recovers nothing that may have been there; it MUST NOT be automatic, MUST NOT be the default or pre-selected outcome, and MUST NOT be reached as a side effect of starting a run, opening or preparing the workspace, or repairing anything else — the product cannot tell an empty place from a store that was carried off somewhere else moments ago, and every resolution it could reach on its own is the one that discards the possibility. **This is REQ-EVENTS-179's family and MUST answer the same way.** That requirement governs a store that opens, reports itself usable, and then fails, and resolves it into REQ-EVENTS-084; this one governs a store that is not there at all, and resolves into the same place, so the answer does not turn on which of the two a reader happens to meet. Its check does not reach this condition and cannot be made to: an operation that reads and writes the store's own contents is answered perfectly by an empty store the attempt itself brought into being, so an absent store passes a check built to catch a store that does not work. What the product must establish before it uses a store is therefore not only that the store works, but that it is the store this machine already had — which is why creating one is right where nothing is kept for the workspace and wrong where a place is kept and the store is missing from it. **What this does not reach.** A workspace for which nothing is kept at all remains REQ-SESSION-043's ordinary empty state, unchanged. A place that is itself absent is an absence and not this condition, including while a restore is under way (REQ-SESSION-201). And a store that is present and holds no sessions is not this condition either: it opened, and it lists empty.

### 2. Session Identity

- **REQ-SESSION-009** — New session ids MUST have the shape `YYYYMMDD-HHMMSS-` followed by 12 lowercase hexadecimal characters, matching the regular expression `^\d{8}-\d{6}-[0-9a-f]{12}$`. The id MUST be minted before the first state write is persisted, so a caller can name and display the run before any work happens.
- **REQ-SESSION-010** — *Withdrawn.* Deriving a session's identity from a directory path was a filesystem-mediated resolution rule with nothing left to resolve: a session is addressed by its id, and every per-session binding — diagnostics, event history, scheduler — binds by that id and never falls through to another session (REQ-SESSION-146, REQ-SESSION-176). That ids are never reused, so one id names one session for good, is REQ-SESSION-012's.
- **REQ-SESSION-011** — A caller MUST be able to pre-name a new session by supplying the session id in the run request (so the run is addressable and displayable before any worker output arrives); a supplied new-session id MUST be ignored when the request resumes an existing session.
- **REQ-SESSION-012** — Session ids MUST never be reused. Consumers are entitled to assume that two different histories never share one identity, so a stored history found under an id always belongs to the session that id names.

### 3. Resumable State: Schema Rules and Defaults

- **REQ-SESSION-013** — The persisted session-state schema version MUST currently be `1`, and every persisted state MUST carry a `schema_version` field defaulting to the current version.
- **REQ-SESSION-014** — `created_at` and `updated_at` MUST be UTC timestamps; their JSON serializations MUST end with a `Z` suffix. `workspace_root` MUST be persisted as a string path.
- **REQ-SESSION-015** — Loading a state payload with absent optional keys MUST succeed by applying defaults (legacy tolerance is the general schema rule): missing check-suite record loads as null; pre-cost snapshots load with an "unavailable" cost; pre-attribution snapshots load with empty attribution strings. Field defaults MUST include: empty config snapshot, empty transcript events, empty edit-diff list, empty child-state list, empty report-artifact list, null todo states, null outer-loop progress, null token usage, execution status `idle`, empty exhausted-model list, message count 0, null message limit, and null wait state.
- **REQ-SESSION-016** — Five run-audit facts MUST be recorded in two places that stay consistent — on the session's state, and into the launch audit (REQ-SESSION-138): run intent (default empty), permission mode (default empty), resolved check suite (default null), sandboxed flag (default false), and sandbox backend name (default empty). Each MUST be stamped on the state at the moment it is settled: the run intent, the permission mode and the resolved check suite when the run request is applied, and the sandboxed flag and backend name when the sandbox verdict is taken (REQ-SESSION-086), so that a completed session can afterwards be asked what it actually ran under (REQ-SANDBOX-108). When those same facts reach the launch audit is not this requirement's to state and is fixed by REQ-SESSION-138 alone — once per session, by run startup, after the worktree has been bound and the sandbox verdict taken. This requirement formerly said the facts were recorded "at session start", and that reading is withdrawn rather than reconciled: two of the five are not knowable until the sandbox verdict, and a session created but never run carries no launch audit at all (REQ-SESSION-132, REQ-SESSION-138) while still loading all five state fields at their defaults (REQ-SESSION-015). For snapshots written before these fields existed, the empty/false defaults describe those runs accurately rather than standing in for unknown data, and MUST NOT be backfilled.
- **REQ-SESSION-017** — Requirement attribution fields (`requirement_id`, `unit_id`) MUST default to empty strings for hand-started runs and MUST be set only when requirement-driven execution creates the session. Older snapshots MUST load via defaults without a schema version bump.
- **REQ-SESSION-018** — A session MAY carry a worktree binding record, persisted under the `worktree` key of the resumable state and of the listing metadata. Its field set, the closed `merge_status` vocabulary, and every field default are fixed by REQ-GIT-015; this document holds no copy of any of the three and mints no field of its own. What persistence adds is that the binding is optional and that its own default is null: a session that was never bound to a worktree, and a snapshot written before worktree binding existed, both MUST load with a null binding under the legacy tolerance of REQ-SESSION-015 rather than failing, and a binding that is present MUST be persisted and restored whole, with no field dropped or defaulted on the way through.
- **REQ-SESSION-019** — The session state MUST carry a `checkpoints` list, ordered oldest-first (newest last), where each entry maps an iteration to the git ref and commit that restore the tree as it stood at the end of that iteration (see Data & Formats). This list is the durable checkpoint mapping and MUST survive resume; entries MUST be pruned together with their refs.
- **REQ-SESSION-020** — The state MUST carry an `internal` boolean (default false). Internal sessions (machinery such as worktree-integration runs) MUST be durably recorded but hidden from normal session listings.
- **REQ-SESSION-021** — The state MUST carry a run-type marker distinguishing ordinary user-task runs (the default) from improvement and integration runs. The run type MUST be stamped at session creation and never changed on resume, so the kind of run is recoverable from disk alone and not only from the live process.
- **REQ-SESSION-022** — Global counters MUST be persisted: total tool-call count, global token aggregate, global cost aggregate, compression count, per-agent metrics (tool-call count, per-tool call counts, token usage, cost, compressions, last prompt-token count), and root-context token count. The default cost aggregate MUST read as "source unavailable" and render as "—", so an unpriced run never displays as free.
- **REQ-SESSION-023** — Compression-deduplication ids MUST be persisted keyed by agent name, with the empty string used for anonymous agents, so that compression accounting is exactly-once across resumes.
- **REQ-SESSION-024** — A provider refusal caused by an exhausted quota (HTTP 429, or an equivalent insufficient-quota rejection) MUST leave a durable mark on the session: the refused model is appended to the persisted `exhausted_provider_models` list as `<provider>/<model>` when the provider is known, and as `<model>` alone when it is not. From that moment on, and equally after the session has been closed and reloaded, no automatic model choice and no automatic retry inside that session may select a model whose identifier matches a list entry by exact string equality in the same form the entry uses. The exclusion binds automatic selection and automatic retry only: a model the user chooses explicitly is always usable, and choosing one MUST remove exactly that entry from the list — the user's choice is the evidence that the quota returned. Nothing else clears the list: it is never cleared on a timer, on resume, or by a quota window the product cannot observe, so an untouched session never silently resumes calling a model that refused it.
- **REQ-SESSION-025** — These interactive-wait fields MUST be persisted with the session and MUST come back unchanged when it is reloaded: `pending_questions`, gaining an entry when a question action fires and losing it when that question's tool result arrives (REQ-SESSION-129); `pending_approvals`, a map from request id to the payload of the tool call suspended on interactive approval, an entry disappearing when the request is answered, when it is cancelled, or when it expires under the approval wait of REQ-TOOLS-055, whose budget is the single configuration key REQ-CONFIG-126 registers — this domain names no key, states no default, and defines no timeout of its own; `wait_state`, non-null while and only while the run is suspended on provider quota; `verifier_state`, where null means that no check is running at that moment and never that a check ran and found nothing; and `gate_warning`, a string that survives across individual checks and is cleared only when a completion gate records a decision (the `completion_gate_decision` timeline entry of REQ-SESSION-134). `pending_questions` and `pending_approvals` are the only inputs to the listing record's `awaiting_input` (REQ-SESSION-031).
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 3).** A pending approval or question whose call is cut off by a pause, a stop, a quit or a crash is withdrawn, its entry removed and the withdrawal recorded; it does not come back when the session is reloaded.
- **REQ-SESSION-026** — A mid-session runtime model override (active model key and runtime model configurations) MUST persist across calls and across reloads of the session.
  > **Narrowed by [`PD-MONITOR-006`](../product/directives.md#pd-monitor-006), 2026-10-06.** A switch of the entry model
  > or reasoning level made from the run header or the inspector is not such an override: it holds for its own run and
  > does not persist into the session's next run. A model chosen during a provider wait (REQ-ORCH-091 (d)) is, and
  > persists as stated.
- **REQ-SESSION-027** — Serialization MUST round-trip loss-free: deserializing a state's own JSON serialization MUST reproduce an equal state.

### 4. Saving State

- **REQ-SESSION-028** — A state save MUST be all-or-nothing. The resumable state, the transcript rows, the edit diffs, the metrics document and the listing record are made durable together, and no reader may ever observe a session whose listing record describes a state that was not saved, or whose parts came from two different saves. The write ordering this requirement formerly fixed existed to keep the listing record from advertising a state not yet recorded; the guarantee it bought is now the atomicity itself, and it holds for readers in any process. The human-readable summary is rebuilt by the same save (REQ-SESSION-006, REQ-SESSION-140) and is the one part written as a file, under the replacement rule of REQ-SESSION-033. No second, whole-state copy of the session is written anywhere.
- **REQ-SESSION-029** — Bulk content MUST be held once and referenced, never copied into the resumable state: the transcript rows, the edit diffs and the configuration snapshot are held as their own records and rehydrated on load (REQ-SESSION-036), and a report artifact is carried in the state as a reference holding only `id`, `agent_name`, `status`, and `path`, its body read from the session's artifact store at that reference. The consequence a caller may rely on is that no part of a session's content exists in two places where the two could disagree, and that a save never rewrites content it did not change.
- **REQ-SESSION-030** — The listing record MUST hold exactly these fields: `session_id`, `created_at`, `updated_at` (ISO-8601 strings), `execution_status`, `schema_version`, `internal`, `worktree` (the binding record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Every attribute a listing shows about the session itself MUST be one of these — making a new attribute list-visible is a change to this field set, not a reader-side extension — and the only other thing a listing may consult is that session's lock record, and only to decide liveness (REQ-SESSION-056, REQ-SESSION-182). Readers MUST tolerate records written by older versions by defaulting absent fields: `checkpoint_count` → 0, `task_title` → the session id, `requirement_id` and `unit_id` → empty string, `awaiting_input` → false.
  > **Narrowed by [`PD-SESSION-001`](../product/directives.md#pd-session-001), 2026-10-06 (revision 2 the same day).** The
  > listing record also holds the session's token total, its latest run's duration label (computed from that run's start)
  > and its workspace path, which the sessions card draws as its token label, duration label and detail caption
  > (REQ-MONITOR-171). Every other clause above still governs.
- **REQ-SESSION-031** — `awaiting_input` MUST be true exactly when the state holds any pending approvals or pending questions, so a run that is waiting on human input can be identified from any surface and remains identifiable after a restart.
- **REQ-SESSION-032** — `task_title` MUST be derived from persisted todo state as the last non-blank task name across phases (the newest top-level task), skipping blank names and empty phases; it MUST be empty when there is none.
- **REQ-SESSION-033** — Where this domain replaces a whole file in place — the human-readable summary of REQ-SESSION-140, rewritten by every save, is the one written repeatedly — the replacement MUST be atomic in the sense a reader observes: a concurrent reader opening the file at any moment sees either the previous complete file or the new complete one, and never a partial, empty or unparseable state; a crash during the replacement leaves one of the two. On Windows, a transient access-denied failure of the replacement (antivirus, indexer, or a cloud-sync client holding a handle) MUST be retried, because a foreign handle held for a moment is not a reason to lose a user's file, and any temporary artifact the replacement used MUST always be removed. The ladder is **at most six attempts in total** — the first attempt and at most five retries — with a delay before each retry of **0.05 s, 0.1 s, 0.2 s, 0.4 s and 0.8 s**, so the last attempt begins no more than 1.55 s after the first. *This counting is stated because the earlier wording, "retried up to 5 times with exponential backoff starting at 0.05 s (0.05, 0.1, 0.2, 0.4, 0.8 s)", could be read as five attempts or as six, and two conformant builds would then differ in how much of a transient failure they absorb. It is resolved as six because that is the reading under which every delay the requirement itself lists is used; nothing is narrowed by it, since the alternative reading retries strictly less. Any document that summarises this ladder takes these figures from here.* This rule does not reach the durable store, whose all-or-nothing behaviour is REQ-SESSION-028's, and it is the only replacement ladder this domain states — the export destinations of REQ-SESSION-189 and REQ-SESSION-199 are not this domain's to ladder and cite REQ-TRACE-061 instead, whose figures are that domain's own and are not these.
- **REQ-SESSION-034** — The crash-loss budget MUST be stated in saves rather than in seconds. Because no save is deferred (REQ-SESSION-067), a crash MUST lose only changes for which no save was ever requested: every save that was requested and completed is durable, and every save that was interrupted is absent whole. A partially applied save MUST NOT be observable at any point, and no reader may find a record left half-written by a killed process.

  **What "durable" means, stated in three levels rather than in one word** (accepted amendment 2026-09-06, OQ-12; this requirement is the product's single definition and every other durability claim cites it rather than restating one). The three are different guarantees and MUST NOT be collapsed:
  1. **Process-crash atomicity, for every successful write.** A write this product reports as successful MUST survive the loss of this process at any instant — a kill, a force-quit, a runtime fault — whole and readable. This is the level the paragraph above states and the one every store, every document replacement and every artifact write owes unconditionally. It costs nothing beyond the writes already made and is never traded away.
  2. **Operating-system and power-loss survival, for an acknowledged terminal commit and for a completed backup artifact.** A commit acknowledged at a session's terminal state (REQ-SESSION-094) and a backup artifact reported complete (REQ-SESSION-201) MUST survive loss of the operating system or of power, **subject to the storage device honouring the flushes the product issues** — a condition the product states rather than assumes, because a device that acknowledges a flush it has not performed cannot be detected from software. The stronger commit setting this level requires MUST be preserved and MUST NOT be relaxed as an optimisation; where it is ever reconsidered, the reason MUST be power-loss and operating-system-crash survival, not readability, which the weaker setting already delivers.
  3. **Permitted loss of intermediate updates.** Between those two boundaries, an update made durable at the ordinary commit setting MAY be lost to loss of the operating system or of power, however recently it returned. This is a permitted loss and MUST be stated as one: it is not a defect, it is bounded by how far behind the ordinary setting can be, and level 1 continues to hold over it — what is lost is lost whole, and never half-written.

  **The measurement this definition rests on has not been taken, and saying so is part of the amendment.** No power-loss test has been run on any supported platform, so nothing establishes that a commit acknowledged at level 2 survives a power cut on this storage, and nothing establishes how far behind level 3's loss can actually be. The harness exists and its fault half requires a physical act — a forced power-off, or an operating-system crash — that only the machine's owner can perform. Accepting this wording does not discharge that evidence; the proof is tracked **per supported platform** and stays outstanding until measured. No claim stronger than this text may be made to a user in the meantime.
- **REQ-SESSION-035** — A save MUST stamp `updated_at` with the current UTC time before writing.

### 5. Loading State, Legacy Fallback, and Corruption

- **REQ-SESSION-036** — Loading MUST read the resumable state and then rehydrate the three bulk parts held beside it (REQ-SESSION-029): the transcript rows, the edit diffs, and the configuration snapshot, the last taken from the launch audit of REQ-SESSION-138. Each of the three is optional. A part that is absent, and a part that is present but cannot be decoded or does not carry what it should, MUST be treated identically: the corresponding field loads empty, the load succeeds, and a warning is logged and an issue recorded (REQ-SESSION-135) naming the part and the reason. Only the resumable state itself failing to decode fails a load (REQ-SESSION-041) — these three hold recoverable bulk data whose loss degrades a reopened session rather than invalidating it.
- **REQ-SESSION-037** — The stored resumable state is the only resumable state, and there is no alternative whole-state record to fall back to. Where the workspace's store holds no state under a session id, loading MUST fail with a not-found error conveying the session id as supplied and that no session state is stored under it in that workspace; the wording is left to the implementation. Because the store is machine-local (REQ-SESSION-198), a workspace opened on a machine that has not run it before holds no sessions there, which is an ordinary empty state rather than a failure (REQ-SESSION-043).
- **REQ-SESSION-038** — A `schema_version` greater than the supported version MUST be refused with an error conveying the version found and the version supported — an incompatible snapshot is refused, never lossily restored. The wording is left to the implementation.
- **REQ-SESSION-039** — *Withdrawn.* There is no legacy layout to migrate forward from; every session is recorded the one way this product records a session, from its first save.
- **REQ-SESSION-040** — Two read modes MUST exist: a full open (used to run or resume a session) that applies post-deserialization repairs (see REQ-SESSION-170), and a read-only snapshot read (used by display-only consumers) that performs the same read with no repairs and no filesystem writes.
- **REQ-SESSION-041** — Corruption tolerance MUST live at the consumer: resumable state that cannot be decoded propagates the error from the loader, and every caller MUST catch it and degrade — the desktop session browser reports the session as unreadable, conveying the session id and the parse detail and leaving every other session usable (REQ-SESSION-182); stale repair treats it as "nothing to do"; checkpoint-ref cleanup skips the session; and listing paths skip the entry. The wording of the report is left to the implementation.

### 6. Session Listing

- **REQ-SESSION-042** — Listing MUST be taken from the workspace's stored listing records, silently skipping any record that cannot be decoded or whose `updated_at` is absent or unparseable. Surviving entries are returned as those records hold them, with reader-side defaults applied per REQ-SESSION-030, filtered per REQ-SESSION-044, and ordered by `updated_at` descending so the most recently updated session comes first. Building the list MUST read nothing but those listing records — not a session's state, not its transcript, not its history — so the cost of listing grows with the number of sessions and with nothing else; a presentation layer that marks stale sessions additionally reads that session's lock record and nothing else (REQ-SESSION-056, REQ-SESSION-182).
- **REQ-SESSION-043** — A workspace whose store holds no sessions MUST produce an empty list rather than an error, and so MUST a workspace for which this machine holds no store at all. A workspace in which no run has yet taken place *here* is an ordinary state, and under REQ-SESSION-198 that includes a workspace every one of whose runs happened on another machine. Both of those are the absence of a store, and the empty answer is owed where nothing is kept for the workspace at all. A workspace for which this machine keeps a place for the store while the store is not in it is neither of them and is REQ-SESSION-202's, which resolves that case into a store that could not be opened: it MUST NOT produce an empty list, because an empty list asserts that this workspace has no sessions here when what is true is that the product cannot tell.
- **REQ-SESSION-044** — Default listing MUST exclude sessions whose metadata `internal` flag is truthy; an explicit include-internal option MUST return everything (used by recovery and machinery).
- **REQ-SESSION-045** — One corrupt session MUST never cost the listing the others: every other session still appears.

### 7. Session Locking

- **REQ-SESSION-046** — The session lock MUST be a record held in the same store as the session it locks, claimed by an operation that either succeeds or reports the existing holder, so that two claims on one session can never both succeed and a claim can never partially take effect. It carries `pid` (integer), `host` (a stable identifier of the machine whose process holds the lock) and `acquired_at` (a UTC ISO timestamp). These three names and their value types are a machine-readable contract and are the same ones REQ-GIT-020 fixes. **What supplies `host` is fixed here, because "stable" was stated and left unsourced and the obvious source is not stable.** It MUST be an identifier the product mints once for this machine and keeps in the machine-local location the store lives in (REQ-STARTUP-145), and it MUST NOT be the machine's operating-system name or any other value a user, an administrator, or the machine's own configuration can change. Renaming a machine MUST NOT change it. The reason is that every requirement that reads this field treats a value naming another machine as evidence of a condition that should not arise — REQ-SESSION-056 makes such a lock live by construction, REQ-SESSION-047 never reaps it, and REQ-SESSION-183's per-session confirmed release is the only thing that clears it — so a field that changes when a machine is renamed converts an ordinary administrative act into every one of this workspace's sessions reporting held by a machine that does not exist, each needing to be cleared by hand. The identifier is minted where a store is, so a workspace whose store this machine has never held has no identifier question to answer.
- **REQ-SESSION-047** — Lock acquisition MUST return success/failure rather than raising. When the session is already locked, at most one stale-reap attempt MUST be made (two claims total), and the reap MUST happen only when all of the following hold: the lock record carries the three fields of REQ-SESSION-046 with their stated types, its `host` names this machine, and its `pid` probes dead here. In that case the stale lock is released and the claim retried once. In every other case — the record is unreadable or does not carry those fields, `host` is absent or names another machine, `pid` is absent or not an integer, `pid` is ≤ 0, or the pid probes alive — the lock MUST be respected, acquisition MUST fail, and the lock record MUST be left exactly as it was found. There is no waiting, no bounded retry loop, and no second reap: a lock another party keeps re-claiming can never make acquisition spin. That only one instance of the application runs at a time (REQ-STARTUP-161) is not a reason to weaken any of this. The lock this path exists to reap is the one a *previous* instance left behind when it crashed or was force-quit — the one case in which no process can be asked to release it — and reaping it is what turns such a session back into an ordinary persisted session that opens normally (REQ-SESSION-159).
- **REQ-SESSION-048** — Creating a session MUST persist the initial state first, then acquire the lock; an acquisition failure at creation raises an error conveying the session id, that nothing was started, and what is actually wrong — not merely that a lock was contended. This requirement is the single statement of what such a refusal must convey, and the two cases MUST be distinguished. Where the lock names **this** machine, the refusal conveys that another run in this application holds the session, naming the pid the lock records; the remedy is that run finishing or being stopped. Where the lock names **another** machine, the refusal conveys that the session is held by a different machine, names that machine and when the lock was acquired, and states that this instance cannot establish whether that run is still going — and, because the store is machine-local (REQ-SESSION-198), that such a lock means this workspace's session store is reachable from more than one machine, which is the condition the user must resolve rather than a lock to be cleared. Explicit release (REQ-SESSION-183) is named as the only remedy in that second case and is never taken automatically. **A third case exists and this requirement covers it, because the two above are keyed on what the lock says and a lock may say nothing.** Where the lock record is present but cannot be read, or does not carry the fields of REQ-SESSION-046, the refusal MUST convey that a lock is present and could not be read, MUST NOT name a machine or a pid it does not have, and MUST NOT be reported as either of the cases above — the product does not know which of them it is, and saying so is the honest report. Explicit release (REQ-SESSION-183) is the remedy here as in the second case, and for the same reason: the session counts as live (REQ-SESSION-056) and is never reaped (REQ-SESSION-047). This case is not an unlikely one — REQ-SESSION-056 and REQ-SESSION-183 both name it explicitly — and the enumeration above would otherwise leave the single statement of this refusal with nothing to say about a condition its own neighbours describe. A freshly created session is left lock-held by its creator. The wording is left to the implementation.
- **REQ-SESSION-049** — Releasing the lock MUST first tear down the session-scoped shared services holding long-lived subprocesses (MCP servers, language servers) and then release the lock; releasing a lock that is not held is a no-op.
- **REQ-SESSION-050** — A session MUST be owned by at most one run at any moment, and holding that session's lock (REQ-SESSION-046) is what owning it consists of. Because only one instance of the application runs (REQ-STARTUP-161), a second claim on a live session can arise in exactly two ways, and the lock refuses both: a further run started inside this same instance, which is refused outright (REQ-SESSION-083), and a lock left behind by an instance that is gone, which is reaped (REQ-SESSION-047) or explicitly released (REQ-SESSION-183) before ownership passes. Several locked background sessions MAY nonetheless coexist within a single workspace: the limit is one run per session, not one run per workspace.

### 8. Process Liveness Probing

- **REQ-SESSION-051** — The pid liveness probe MUST answer "dead" for any pid ≤ 0, MUST never raise, and MUST answer "alive" whenever the outcome is uncertain. The two error directions are not equivalent: answering "dead" for a live process lets a restore run concurrently with work still in flight, while answering "alive" for a dead one costs the user nothing worse than invoking the explicit repair step.
- **REQ-SESSION-052** — On POSIX platforms: a process-not-found result proves death; a permission-denied result MUST count as alive (the probe was refused, not answered); any other probe error MUST count as dead only when the platform semantics prove absence, otherwise alive.
- **REQ-SESSION-053** — On Windows: the probe MUST NOT deliver any signal or console control event to the target process (in particular, implementing the probe as a null signal is a defect there, because it injects a real console interrupt into the target). Only an OS-level "no such process / invalid parameter" error proves absence; a still-running indication means alive; access denied or any other failure MUST count as alive.
- **REQ-SESSION-054** — The following residual limitations are accepted, documented behavior (not defects to be silently "fixed" in ways that break the resolve-toward-alive rule of REQ-SESSION-051): when the operating system recycles a pid onto an unrelated process, the session reports alive until that unrelated process exits; and on Windows an already-exited process can keep reporting alive while any open handle to it survives. Both resolve toward "live", which is the safe direction. A session held from a different machine is no longer among these limitations: the lock's `host` field (REQ-SESSION-046) makes that case detectable, and REQ-SESSION-056 resolves it toward "live" by construction, so such a lock is never reclaimed automatically. Since the store became machine-local (REQ-SESSION-198), a lock naming another machine is no longer the ordinary consequence of a workspace on shared storage but evidence that the store itself is reachable from more than one machine — a state that should not arise. The `host` field is kept as the defence against it and as what makes the pid probe sound at all, since probing a pid recorded by another machine would be meaningless; the condition is reported as that state rather than as a lock conflict (REQ-SESSION-048). **That inference is only sound because REQ-SESSION-046 fixes what supplies `host`.** A field taken from the machine's operating-system name would make renaming a machine produce the same evidence — every lock this machine wrote would name a machine that no longer exists, and the product would report a state that should not arise for a state that arises routinely. A machine that has been renamed MUST be indistinguishable here from one that has not. A lock that cannot be reclaimed automatically and that the user knows to be orphaned is released through the explicit action of REQ-SESSION-183.

### 9. Stale-Session Detection and Repair

- **REQ-SESSION-055** — Exactly six `execution_status` strings assert that a run is in progress: `starting`, `running`, `background`, `waiting`, `pausing`, `cancelling`. `waiting` is one of them because a run parked on a provider quota wait is still alive and the agents parked on that wait must remain visible as such (REQ-MONITOR-195, REQ-MONITOR-291). The test is exact, case-sensitive equality against that set; every other value — whether it belongs to the wider vocabulary of REQ-SESSION-073 or is unknown to this version — MUST answer "no run in progress". Given one persisted status, every surface that asks the question MUST give the same answer: stale detection and repair (REQ-SESSION-057), the worktree-integration precondition (REQ-SESSION-064), the stale marking in the desktop session list (REQ-SESSION-182), and the settling of displayed agent and tool state (REQ-SESSION-078, REQ-SESSION-079).
- **REQ-SESSION-056** — A session counts as **live** exactly when a lock record is present and it is not proved unheld: it is proved unheld only when the record carries the three fields of REQ-SESSION-046 with their stated types, its `host` names this machine, and the `pid` it records probes dead here. The absence of a lock record is the sole unambiguous signal that no process holds the session; every other case — a record that cannot be read, one that does not carry those fields, one whose `host` is absent or names another machine, one carrying no pid or a non-integer pid, a pid ≤ 0, or a failed probe — MUST report live. This is exactly the test REQ-SESSION-047 applies before reaping, so liveness and reapability can never disagree (REQ-SESSION-171). An empty session id is never live.
- **REQ-SESSION-057** — A session is **stale** if and only if its metadata `execution_status` is in the active set and the session is not live. Sessions in terminal statuses (`completed`, `failed`, `paused`, `idle`, `paused_message_limit`, `interrupted`, `stopped`, ...) are never stale regardless of lock state.
- **REQ-SESSION-058** — Stale detection MUST read only the listing record (including internal sessions) and the lock record, MUST write nothing at all — no state, no file, and no lock touched, which a caller may verify by observing that nothing the session owns has changed — and MUST report an empty result, not raise, over a store it cannot read.
- **REQ-SESSION-059** — Each detected stale session MUST report: the session id, the stuck execution status, `updated_at` exactly as the dead process left it (detection MUST NOT restamp it; an unparseable timestamp normalizes to the epoch); and a human-readable reason. Exactly two conditions can produce a stale session (REQ-SESSION-056), and the reason MUST say which applied: no lock is held for the session at all, or the lock names this machine and the pid it records is gone — the second naming that pid. The wording is left to the implementation; the same text is what REQ-SESSION-062 interpolates and what the desktop shows when it announces a repair.
- **REQ-SESSION-060** — Repair MUST be explicit — never triggered automatically from a read path. A repair MUST: re-check liveness; read the state (unreadable state means "nothing to do"); require an active status; set `execution_status` to `interrupted`; make that correction durable before going further, so it survives the process dying again at once; then best-effort release the orphaned lock; then write a diagnostics timeline entry. Ordering is mandatory — status first, lock second; releasing the lock first would open a window in which the record still asserts a running session with no lock behind it. A failure to make the correction durable MUST leave everything untouched. Repair MUST never raise.
- **REQ-SESSION-061** — The repaired status MUST be `interrupted`, an existing status word chosen because it sits outside the active set, so a repaired session can never again report as occupied.
- **REQ-SESSION-062** — The repair timeline entry MUST have type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, and metadata `{previous_execution_status, execution_status, reason}`. A diagnostics failure MUST NOT fail the repair. **One entry per repaired session, whatever the batch** (accepted amendment 2026-09-06, OQ-46): a repair that corrects several sessions at once writes this entry into each of their records, unchanged and unabbreviated, because the entry is the session's own record of what was done to it and a session whose entry was folded into another's has no record of its repair. What the *user* is shown for such a batch is one aggregate announcement and is REQ-SHELL-155's, not this requirement's; the two are deliberately separate, so a change to the announcement never silently reduces what is recorded.
- **REQ-SESSION-063** — Repair-all MUST repair every stale session and be idempotent: a second pass repairs nothing and rewrites nothing (fingerprint-verifiable). A live session next to a dead one MUST be untouched and keep its lock.
- **REQ-SESSION-064** — Worktree integration's "base not in use" precondition is the one read path allowed to *bypass* (not repair) staleness: a session in an active status whose process is dead MUST be skipped rather than blocking integration forever, with the durable status correction left to the explicit repair action of REQ-SESSION-182; a genuinely live session MUST block integration with the error `A session is still running in the base worktree. Finish it before integrating.`
- **REQ-SESSION-065** — When a run acquires the session lock and has not yet started work, it MUST settle orphaned children: every persisted child-agent record whose state is not in the terminal set `{succeeded, failed, cancelled, blocked}` is set to `cancelled`, given a completion timestamp (UTC ISO with `Z`, only if absent), and has its active-tool list cleared; terminal children keep everything. The operation reports how many records it moved and is idempotent. Holding the lock is itself proof that the previous owner has exited, so this settling step MUST NOT probe process liveness.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 2).** The settle still runs, and no longer touches a `paused` agent: that agent is resumed with its iteration instead of being cancelled.
- **REQ-SESSION-066** — A session persisted in an active status whose owning process is gone MUST be observable in two ways at once: restoring one of its checkpoints is refused and restores nothing, leaving the working tree byte-identical (REQ-SESSION-164), and the desktop session list shows that session with its stored status marked stale (REQ-SESSION-182). After the repair action of REQ-SESSION-182 has reported that session repaired, the same restore MUST succeed and the same list MUST show `interrupted` with no stale marking.
- **REQ-SESSION-183** — Because a lock that cannot be read, or that names another machine, always counts as live (REQ-SESSION-056) and is never reclaimed automatically, the application MUST offer one explicit, user-confirmed action that releases such a lock. It MUST be offered only for a session that reports live and that no process in this application holds, MUST state before it acts what the lock records — the pid, the host, and when it was acquired — and, where that host is not this machine, what that means rather than only what it says: that the session is held by a different machine and that this instance cannot establish whether that run is still going (REQ-SESSION-048). It MUST state that releasing a lock a live run still holds risks two runs writing one session. On confirmation it releases the lock and nothing else; the session's `execution_status` is left exactly as it stands, so a session that then reads as stale is repaired by the ordinary explicit repair of REQ-SESSION-060. The action MUST never run automatically, MUST never be offered as a remedy inside an error the user did not ask to resolve, and is the only way a lock this machine cannot prove dead is ever removed.

### 10. Save Ordering and Durability

- **REQ-SESSION-067** — A save MUST be made durable when it is requested, whatever the session's status. No save is deferred behind a timer, parked, or coalesced with a later one. The ten-second window this requirement formerly imposed on `running` and `idle` sessions existed because a save rewrote whole documents and the cost had to be bounded; a save now records only what changed, so the window buys nothing and costs the one thing that mattered — it was the interval in which a change could be published before it was recorded, which persist-before-publish (REQ-MONITOR-221) forbids and which now cannot arise. Two consequences MUST hold: there is no state a caller must remember to flush, and REQ-SESSION-034's crash-loss budget is stated in saves rather than in seconds. An explicit flush remains available for callers that need to know a save has landed (REQ-SESSION-068, REQ-SESSION-070) and is a no-op where nothing is outstanding.
- **REQ-SESSION-068** — Saving MUST behave as follows from a caller's point of view. A save request captures the state as it stands at the instant of the request, so that changes made after the request cannot alter what a save already under way records and cannot produce a record mixing two states. Every save reaches the store without a further call from the caller and without a timer (REQ-SESSION-067). An explicit flush MUST make the newest requested state durable and MUST NOT return before it is; the flush entry point MUST be usable from any caller's context, including one where no asynchronous runtime is active.
- **REQ-SESSION-069** — When several saves for one session are requested in close succession, the state left in the store MUST correspond to the *last* request, never to an earlier request whose write happened to finish later. In particular, a `running` save requested before a `completed` save MUST NOT be the one that survives, whatever order the two writes complete in. This ordering rule applies within one session only: a save requested for one session MUST NOT suppress, delay, or discard a save requested for a different session. This requirement formerly also fixed the exact session-log line by which a write *abandoned* for this reason was reported. **That line is withdrawn, and no conformance test may look for it.** Because no save is deferred behind a timer, parked, or coalesced with a later one (REQ-SESSION-067), requested saves are made durable in the order they were requested and there is no write left in flight to be overtaken and discarded — the condition the message reported cannot arise. The ordering guarantee above is unaffected and is unchanged in strength: it now holds by construction rather than by detecting the race and abandoning the loser, which is what REQ-SESSION-173 states as an invariant. Nothing may manufacture an abandoned write in order to keep the message reachable, because deferring or parking a save to create that race is exactly what REQ-SESSION-067 forbids.
- **REQ-SESSION-070** — Two guarantees MUST hold at the call boundary. First, once a flush returns, the persisted state is never older than the newest state any caller has asked to have saved; a flush is permitted to return without writing only in the case where a later save has already made that true. Second, a save carrying a terminal status MUST NOT return before that status can be read back by any other reader of the store, so a caller that has been told the run finished can rely on the finish being durable.
- **REQ-SESSION-071** — No bound on write volume is stated and none is needed: a save records only what changed and is durable when requested (REQ-SESSION-067), and no supported configuration key changes when a save happens. What this requirement fixes is the rule that outlived the write-volume bound, and it has no exception anywhere in the product. A surface that shows a run as it progresses MUST take its updates from what the application publishes for that run as it produces them (REQ-SESSION-159, REQ-SESSION-161); re-reading persisted state on a timer is not a supported way to follow a run and MUST NOT be relied on for refresh latency — no surface follows a session by reading its record or its files, on a timer or otherwise. The event history of Section 18 remains the durable record of what was published and the record replay reads (REQ-SESSION-150); it is not a channel a surface watches. Neither is the export of REQ-SESSION-199: it is a file a user asked for at a moment, and building a surface on repeating it is the same defect under another name.
- **REQ-SESSION-072** — Any state persisted while a run is under way MUST already carry that run's current metric aggregates (REQ-SESSION-168), so a reader never finds a saved state whose counters lag the transcript saved beside them. Every such save is durable when it is requested (REQ-SESSION-067), including one taken where no asynchronous runtime is active.

### 12. The Shared Run Lifecycle

- **REQ-SESSION-080** — Exactly one run lifecycle MUST serve every way a run is started: a foreground run in a desktop window, a run detached into the background (REQ-SESSION-190), a run launched from the requirement board (REQ-SESSION-158), and a run started by product machinery such as worktree integration. It MUST return a run result rather than terminating the application, and MUST present nothing to the user itself; even validation failures come back as error results carrying the diagnostic text; no caller may take a different code path.
- **REQ-SESSION-081** — The run request MUST support: the task text, configuration, an existing session id (whose presence means resume), a maximum iteration count, an isolate-in-new-worktree flag, an existing-worktree path, a worktree branch name, requirement attribution (ignored on resume), a pre-chosen new-session id (ignored on resume), a delegation strategy, a run type, and an internal flag.
- **REQ-SESSION-082** — The run request MUST be validated before anything is created, and a failure MUST return an error result (outcome `error`, REQ-SESSION-187) that is explicitly marked as having failed before the run started, so a consumer identifies the case from a field and never by parsing message text. Three combinations MUST be refused, each with a message conveying which fields conflict and what to do instead: the isolate flag together with an existing-worktree path; a worktree branch name without the isolate flag; and any worktree option on a request that resumes an existing session. The wording is left to the implementation. A validation failure MUST carry an empty session id, leave no session behind, and still emit exactly one terminal `result` event to the event sink.
- **REQ-SESSION-083** — The resume path MUST load the session then acquire its lock; a lock held elsewhere fails as a pre-run failure that does not steal the holder's lock, with the session id present in the result and a message carrying exactly what REQ-SESSION-048 requires a refusal to convey — including, where the lock names another machine, that the session is held by a different machine rather than that a lock was contended. With the lock held and nothing started, orphaned children MUST be settled (REQ-SESSION-065) and the configuration rebound into the session's stored worktree, if any.
- **REQ-SESSION-084** — The create path MUST create the session record (lock held by creation, requirement attribution and the internal flag applied, run type stamped) and then bind the worktree: an isolating request creates a worktree owned by the session on a branch of its own, and two launches started at the same instant MUST both end up with a worktree of their own rather than one of them failing on a branch-name collision; attaching an existing worktree MUST record it as not owned by the session, so releasing the session never deletes a tree the caller owns. Collision resolution is not this domain's to invent: the branch name is the generated default of REQ-GIT-007 or the name the request supplied, and a name already taken as a ref or by another worktree receives the deterministic `-2`, `-3`, … suffixes of REQ-GIT-010. Because session ids are never reused (REQ-SESSION-012) a generated name collides only against a leftover branch from a session that was deleted, or against a branch the user created; a supplied name collides whenever the user reuses one. A bind failure MUST release the lock, **discard the just-created session record and its files** (REQ-SESSION-167), and return an error result whose message conveys that the requested worktree could not be created or attached, carrying the underlying detail.
- **REQ-SESSION-085** — For a worktree-bound run, the run's effective working tree and the state's persisted `workspace_root` are the worktree path, while the session's record stays anchored to the invoking workspace (REQ-SESSION-001). The configuration snapshot rebound to the worktree MUST be made durable immediately after binding. The three requirements that touch the configuration snapshot resolve as follows and MUST be read together: the resumable state never carries it (REQ-SESSION-029); the launch audit is its one durable copy and is what a load rehydrates it from (REQ-SESSION-036); and because that audit is written by run startup *after* binding and after the sandbox verdict (REQ-SESSION-138), it records the rebound configuration and never the pre-binding one. The rebound snapshot is therefore durable, and the audit is still written exactly once and never rewritten.
- **REQ-SESSION-086** — The sandbox verdict MUST be taken before anything else the run does and recorded on the state (`sandboxed`, `sandbox_backend`). On failure: release the lock; a just-created session's record is discarded while a resumed session survives, so a failed launch never destroys pre-existing history; the result is an error result carrying the detail.
- **REQ-SESSION-087** — Run startup MUST then, in order and observably: rehydrate metric aggregates from the session (REQ-SESSION-169); attach per-session logging to the session log at the configured level (REQ-SESSION-142); record the launch audit (REQ-SESSION-138), which is the first point at which the bound worktree and the sandbox verdict are both known; write a `run_start` timeline entry (actor `rotaris`, message conveying that a run is starting for the session and naming its id, metadata carrying the workspace root); persist `execution_status = "running"`; and invoke the caller's session-ready callback.
- **REQ-SESSION-088** — Per-iteration checkpoints MUST record the working tree in the state in which the iteration finished: any end-of-iteration lifecycle hooks that touch the tree MUST have run before the checkpoint is taken. Caller-supplied observers MUST be added alongside, never substituted for, the built-in ones.
- **REQ-SESSION-089** — Durable recording MUST be unconditional for every run through the shared lifecycle: the session's record is opened before the run starts and the durable event history is teed with the caller's own event sink. A record that cannot be opened MUST refuse the run rather than degrade it — the launch fails as a pre-run failure conveying the session id, that nothing was started, which store could not be opened, and the reason the store itself gave. A record that reports itself opened and then fails on the first operation issued against it counts as a record that could not be opened and takes the same refusal (REQ-EVENTS-179): the record is exercised rather than merely opened before the run is allowed to start, because what a store reports about its own state is not evidence that it works, and a failure met there MUST NOT be retried into success. This requirement formerly let the run proceed on a logged warning that no event history would be available. That partial failure no longer exists: the session's state, its lock and its event history are one object (REQ-SESSION-198), so there is no coherent state in which a run has somewhere to record itself but nowhere to be recorded, and a run that executes while quietly unable to persist anything produces work no one can recover — a worse outcome for a user than not starting. A `session.start` event MUST be published immediately after the record is opened, so that it is the first event any consumer observes.
- **REQ-SESSION-090** — The `session.start` payload MUST carry enough for a consumer to describe the run without opening the session's record: the session id; the task text; the workspace the run reports for itself; the persona; the permission mode as configured at launch (a later unattended downgrade is reported by permission events instead, so this value MUST NOT be restated when the effective mode changes); the sandbox verdict actually in force — the backend both configured *and* available, not the one merely requested; and the maximum iteration count.
- **REQ-SESSION-091** — A cancellation already requested before the loop exists MUST skip the agent runtime entirely (no model call, no grace-period unwind); the run reports the `interrupted` outcome of REQ-SESSION-187 and the session remains resumable at status `paused`.
- **REQ-SESSION-092** — Cancellation semantics: a graceful stop is requested first (the same path the interface's stop control uses, REQ-SESSION-186); if the loop has not reached a stop check within 30.0 seconds, a hard cancel follows. The stop request MUST be sticky — a cancel arriving before the loop's callbacks are wired replays when they are. A caller that requested cancellation MUST receive an interrupted outcome even when the loop finished first; reporting both an effective cancellation and a successful run to the same caller is forbidden. A cancellation raised from inside the run MUST still release the lock and emit the terminal result event.
- **REQ-SESSION-093** — Every outcome branch MUST persist state before returning: cancelled/interrupted → `execution_status = "paused"` plus a system transcript row `Run paused: interrupted by user.`; runtime exception → `failed` plus a row `Run failed: <formatted error>`; normal completion → status and row from the end-of-run summarization, after which the post-run improvement job is either handed to a caller-provided job sink or awaited inline with its result applied and persisted.
- **REQ-SESSION-094** — Run teardown MUST retain the session lock through terminal persistence and publication. It MUST attempt, in order: a `run_end` timeline entry carrying the final execution status; logging cleanup; construction of one run result; durable persistence of terminal state and `session.end` followed by exactly one `result`; delivery of the committed terminal events over the bus while the sink remains attached; and the final disabled-hooks notice. Guaranteed cleanup MUST then detach the sink, remove every per-session binding, and release the lock, including when an earlier step raises. Terminal persistence failure follows REQ-EVENTS-078/088's recording-failure contract: completion remains unconfirmed and the last durable boundary is preserved. A failed commit MUST publish no authoritative terminal event. Straggling events MUST have no binding through which they could append to the finished session or trigger a later run's hooks.
- **REQ-SESSION-095** — The `session.end` payload MUST mirror the terminal run result (outcome per REQ-SESSION-187, stop reason, iterations completed, duration in seconds, tokens, cost), computed once and used for the event payload, the `result` event and everything the interface presents, so no two of them can differ.
- **REQ-SESSION-096** — A run carried out with no view attached — a background run (REQ-SESSION-106), a run of internal machinery (REQ-SESSION-020), or a board-launched run whose window was never opened (REQ-SESSION-158) — MUST surface nothing of its own beyond its event stream and its persisted record, and on success MUST leave an ordinary persisted session that any fresh reader can load with status `completed`.

### 14. Message-Limit Pause and Reattach

- **REQ-SESSION-107** — When a run reaches its message limit, it MUST record the message count and the limit on the state, set `execution_status = "paused_message_limit"`, and make that durable at once. The paused condition MUST be recoverable from the record alone, so a session reopened after a crash or a restart is still paused at its limit and is never silently resumed: the persisted status is the signal, and no separate marker is written outside the record for another process to see. It then remains paused until a user reattaches; there is no automatic continuation.
- **REQ-SESSION-108** — The pause MUST take effect at the outer-loop iteration boundary (after an iteration returns, before the next is chosen), so that while paused no agent is part-way through execution and no model request is outstanding.

  > a pause stops every agent before its next model step, mid-iteration, and leaves the iteration open. Once the
  > pause has landed, no agent executes and no model request is outstanding.
- **REQ-SESSION-109** — On reattach, if the loaded session's status is `paused_message_limit`, the application MUST immediately present a modal confirmation without requiring the user to navigate to it. It MUST convey the message count reached, the limit that was reached, and the run's input and output token usage as separately identifiable figures. It MUST offer exactly three actions — continue, double the limit, and cancel the run — with continue as the default action bound to Enter and cancel bound to Escape. Wording and the remaining key bindings are left to the implementation.
- **REQ-SESSION-110** — Resolving the prompt: "double" doubles the persisted message limit; "cancel" sets status `paused`; "continue" sets status `idle`. In every resolved case the paused-at-limit condition MUST be cleared by the status the resolution writes, and the session saved. A session paused at the limit whose persisted limit is null cannot resume the prompt: its status is set to `paused` and a warning notification conveys that the paused session carries no message limit to resume from. - **REQ-SESSION-111** — The message count and the (possibly doubled) limit MUST be durable across crash and restart through the ordinary save, so the user is never re-prompted for messages already counted. ### 15. Resume and Continue Semantics

- **REQ-SESSION-112** — To continue a session is to reopen one already recorded for the same workspace (REQ-SESSION-001). Everything the session recorded MUST come back: its transcript rows, its stored child-agent state history, its stored tool-event history, its report artifacts, and its configuration snapshot. The test is field-level equality: a state that is saved and then reloaded MUST compare equal on every key of the resumable-state inventory in Data & Formats (REQ-SESSION-027), and that equality MUST still hold after a release-lock, re-acquire, mutate, save and reload cycle.
- **REQ-SESSION-113** — A resumed session keeps its identity wholesale: its worktree binding (worktree options refused on resume), its requirement attribution (request-supplied attribution ignored), its run type (stamped only at creation), and its configuration snapshot; the run executes inside the stored worktree.
- **REQ-SESSION-114** — Intent carry-over on resume: the intent classifier MUST be given the *previous* run's recorded intent (read before it is overwritten). A continuation prompt that classifies as ambiguous (e.g. the user types "continue") inherits the prior intent, and the transcript's status row reads `Intent classified: <intent> (continued from previous run)`; a genuinely new request keeps its own classification.

### 16. Transcript Recording and Persistence

- **REQ-SESSION-120** — The persisted transcript MUST be derived from the run's own conversation events and from nothing a view renders. Two consequences MUST be observable: a run with no view attached persists the same transcript rows it would have persisted with one, so a background session can be reopened with a full transcript; and one recorded conversation yields identical rows, field for field, whichever view was watching it, so no two views can leave different transcripts of the same run.
- **REQ-SESSION-121** — Persisted transcript rows MUST use the role/shape vocabulary given in Data & Formats, and every row MUST be stamped with `ts` in local wall-clock `HH:MM:SS` form when appended.
- **REQ-SESSION-122** — Persisted-size caps MUST be: 400 characters for a tool row's `detail`, 2000 characters for its `full_text`, and 4000 characters for thinking content. Content longer than its cap is stored cut to the cap, while a streamed thinking row's `chars` counter MUST keep counting past 4000 so that token estimation remains correct. Terminal (shell) tool output MUST keep its line structure in `full_detail` — the field a reopened session renders — while `detail` holds a single line of at most 400 characters. `full_detail` MUST itself be capped at 8000 characters, because a single tool row must not be able to grow a session's record without bound; when it is cut, the newest output is kept and the cut is made at a line boundary where one falls inside the cap. Every cut in this requirement is marked per REQ-SESSION-194.
- **REQ-SESSION-123** — Each row MUST be published on the wire as a `transcript.row` event (index plus a copy of the row) once on append and once more when the row reaches its final form — intentionally not on every streamed token, so a surface following the run receives the opening token and then the completed text. Publish failures are logged and never raised into the run.
- **REQ-SESSION-124** — Resuming a conversation can replay events; stable per-event identities (per-agent call ids for tool calls, per-agent event ids for committed messages) MUST prevent duplicate rows and double-counted metrics.
- **REQ-SESSION-125** — Reasoning delivered twice — streamed as deltas and then repeated in full alongside the action — MUST end up as exactly one persisted thinking row holding the final full text, with one start timestamp and one settled duration; a second row, whose elapsed-time counter would never stop, MUST NOT appear. Reasoning that was never streamed arrives in one piece and is persisted with no start timestamp, and therefore shows no timer. Where an older version already recorded a burst twice — consecutive thinking rows of the same agent, the content of one being a prefix of the other's — display MUST show only the longer row.
- **REQ-SESSION-126** — A terminal tool row MUST carry a stream identifier of the form `fg:<agent_name>` so that a UI rejoining the session can locate the live terminal buffer the row belongs to.
- **REQ-SESSION-127** — Structured edit diffs MUST live outside the transcript that is fed to the model, keyed `<agent>:<tool_event_key>` and replaced in place on redelivery; at display time each diff is merged beside exactly one tool row.
- **REQ-SESSION-128** — Tool-call metrics MUST be counted into the per-agent and global aggregates at call start, once per stable call id, and each child's live tool set MUST be mirrored onto its persisted child-state record so a snapshot shows what each child is running.
- **REQ-SESSION-129** — Three end-of-activity guarantees MUST hold. When a child agent dies while a tool call is open, that child's persisted record MUST be left with an empty active-tool list and no transcript row of its own left at status `running`; every such row MUST be persisted at status `failed`, keeping whatever output it had already recorded. The tool-row status vocabulary is REQ-MONITOR-105, in which `blocked` denotes a call refused or skipped before it ran and there is no `cancelled` value — a call that was under way and produced no result is a failure, whatever became of the agent that made it, while the child's own record still moves to `cancelled` under REQ-SESSION-065. A verifier check that finishes without ever having been announced — denied by permissions, or out of budget — MUST still produce a verifier row, with the outcome mapping of Data & Formats; the check-outcome vocabulary that mapping is taken over is the closed five-value set of REQ-ORCH-123, which this document holds no copy of. A completed question-tool result MUST remove the matching entries from `pending_questions`, which in turn clears `awaiting_input` once no approvals remain (REQ-SESSION-031).
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 2).** A tool call cut off by a pause, a stop, a quit or a crash is recorded as interrupted and its agent left `paused`, for the agent to see when it resumes; a child that ends otherwise is unchanged.
- **REQ-SESSION-130** — At run end, if the conversation left no agent rows (for example when a child agent's summarized report is the entire answer), one agent row per iteration outcome MUST be appended from the progress record so the transcript still shows an answer — but never duplicated on top of real conversation rows.
- **REQ-SESSION-131** — Transcript rows released from the resident window (REQ-SESSION-192) MUST be retained in the session's record unaltered, in whole pages of 50 rows, in the order they were released, and a retained page MUST never be rewritten, reordered or trimmed — so a row read back out of it is identical to the row that was released and keeps the index it was given. Release is driven by REQ-SESSION-192 and is not optional for any caller. This requirement is the product's single definition of the released-page store: that pages are whole and fixed at 50 rows, that they accumulate and are never disturbed, and that a released row comes back unchanged. A document that relies on released rows still being retrievable — on bringing older rows back on demand unchanged included — cites this identifier and holds no copy of the page size or the retention rule.
- **REQ-SESSION-192** — The transcript a session keeps resident MUST be bounded at the 5000 most recent rows. When an append would exceed that, the oldest rows MUST be released in whole pages of 50 (REQ-SESSION-131) before the append is made, so a session that runs indefinitely has a bounded resident cost and an unbounded, complete history. Releasing a row MUST NOT change the index it or any surviving row was given — the index REQ-EVENTS-052 assigns a row is that row's identity for the life of the session — and a reader that asks for a row older than the resident window MUST be served it from the released pages. Nothing else caps the transcript: the resident row count and the per-row caps of REQ-SESSION-122 are the whole bound, and there is no byte limit. This requirement is the product's single definition of transcript residency: the resident row cap, the point at which release happens, the stability of a row's index across release, and the guarantee that a row older than the resident window is served from the released pages. A document that relies on the transcript being bounded — on keeping the whole conversation readable while only a bounded number of rows stay resident, or on older rows staying reachable after resume — cites this identifier and holds no copy of the cap.
- **REQ-SESSION-194** — One rule governs every character cap in this domain: whenever stored text is cut to fit a cap it MUST be marked as cut, by appending the marker `...` (three ASCII full stops) and counting that marker inside the cap, so a stored value never exceeds its cap and a reader can always tell a complete value from a shortened one. This applies to `detail`, `full_text`, `full_detail` and thinking content (REQ-SESSION-122), to every per-event, per-item and per-artifact budget of the continuation payload (REQ-SESSION-115), to the task line of `summary.md` (REQ-SESSION-140), to the truncated arguments and results of an error-path tool record (REQ-SESSION-136), and to the compact payload rendering of a replayed event (REQ-SESSION-188). Two exceptions are deliberate: an elided todo list is marked instead by the literal line `- [... additional todo tasks elided]` (REQ-SESSION-115), because what is elided is list entries rather than the end of a string; and a streamed thinking row's `chars` counter keeps counting past the cap (REQ-SESSION-122), because it measures what the model produced and not what was stored. Counts, identifiers, paths and timestamps are never truncated.
  > **Narrowed by [`PD-SESSION-003`](../product/directives.md#pd-session-003), 2026-10-07.** For the arguments of an
  > error-path tool record (REQ-SESSION-136), what is never truncated wins over the cap: where the paths, identifiers,
  > counts and timestamps alone pass 2,000 characters, the free text is cut to the marker and the stored arguments exceed
  > the cap. Every other clause above still governs.

### 17. Diagnostics and Evidence Records

- **REQ-SESSION-132** — A record kind a session has never written MUST read as empty rather than as missing, and MUST NOT require a placeholder to be created for it to do so. This covers the issues record, the timeline, the tool-call, model-input, context-selection, report-validation and memory records, the permission audit, and the conversation index: reading any of them for a session that produced none of that kind succeeds and yields nothing, so no consumer has to distinguish "never initialized" from "empty" and no save has to create anything to keep that true. The launch audit is the one deliberate exception and is not covered by this rule: it is recorded exactly once by run startup (REQ-SESSION-138), and a session created but never run genuinely has none — which is how a reader tells a session that was never launched from one that was launched and recorded nothing.
- **REQ-SESSION-133** — Retention caps (ring-buffer semantics, newest kept) MUST be: issues 500, tool calls 5000, model inputs 5000, context selections 2000, permission decisions 5000, report validations 2000, memory snapshots 2000. A capped record kind retains only the newest entries, and the trim MUST take effect in the same durable operation that records the entry, so a reader never observes more than the cap and never observes a partly applied trim. Where a cap has dropped entries the record MUST retain enough to say that it has, because counts taken over what remains describe what is stored rather than what the run produced (REQ-SESSION-139) and an export must be able to state it (REQ-SESSION-199).
- **REQ-SESSION-134** — Timeline entries MUST have the shape `{id: 12 hex chars, timestamp: UTC ISO, type, severity: debug|info|warning|error (default info), actor, message, metadata}`. Ordering contract: the durable entry is recorded before any wire event derived from it, so a failing stream may drop an event while the durable record it came from is still retained. Exactly three timeline entry types are bridged to wire events (`completion_gate_decision` → `gate.decision`; `repair_attempt_scheduled` and `repair_escalation` → `gate.repair`, mutually exclusive per decision), and no other timeline type produces an event through this bridge — the `error` event of REQ-SESSION-135 is published by issue recording, not by the timeline. Metadata from which no valid event can be constructed is logged and discarded without failing the iteration.
- **REQ-SESSION-135** — Issue records MUST have the shape `{id: 12 hex chars, timestamp, kind, severity, actor, message, evidence_ref, metadata}`. `id` is what a locator names this issue by, and it MUST be unique among the session's issues and MUST NOT be reused once the retention cap of REQ-SESSION-133 has displaced the issue that held it. `evidence_ref` MUST be either empty — where the issue is evidence of nothing beyond itself — or a locator of the form REQ-EVENTS-056 fixes, naming the record kind and the entry the issue was raised about; its form, its closed record-kind token set and the rule that no export may resolve one are that requirement's and are not restated here. Every recorded issue also writes a timeline entry of type `issue`; only error-severity issues additionally publish an `error` wire event with `fatal=false` (recording an issue never by itself terminates a run); warning- and info-severity issues publish nothing, so an automated consumer does not read a healthy run as failing.
- **REQ-SESSION-136** — Tool-call records MUST carry `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` plus `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings` only when applicable. Each record also streams a `tool.start`/`tool.finish` event pair; the durable record keeps the unredacted arguments while the streamed arguments are redacted by the event schema, so what an agent was actually asked to run stays auditable even though it is never put on the wire. Outcome-driven automatic issues MUST be filed: shell failure → kind `terminal_shell_failure` (error); suspicious success → `terminal_suspicious_success` (warning); timeout → `terminal_timeout` (error); any other failure → `tool_error` (warning); each referencing the tool-call record. On error, recorded args/result are truncated to 2000 characters.
  > **Narrowed by [`PD-SESSION-003`](../product/directives.md#pd-session-003), 2026-10-07.** On error the 2,000 characters
  > are counted over the arguments' JSON text, the arguments keep their shape, only free-text values are cut (longest first,
  > each marked), a value whose key names a path, an identifier or a timestamp is never cut, and the arguments go over 2,000
  > only when those values alone do. Every other clause above still governs.
- **REQ-SESSION-137** — The permission audit MUST record decisions with the field set REQ-TOOLS-079 fixes, which is that requirement's and is cited here rather than restated: this domain fixes that the audit exists, that it is part of the session's durable record, and what its export must make evident, and fixes no field of an entry. As that requirement states it, a decision entry carries `timestamp`, `session_id`, `agent_id`, `persona`, `tool_name`, `decision`, `rule_id`, `source`, `summary` (pre-redacted), `reason`, `request_id` only where the decision resolved a raised approval, **and the entry identifier, which is a field of the entry**. *This requirement formerly stated the field set as a closed literal object that named no identifier. That statement is withdrawn rather than corrected in place, because a second enumeration of one record shape is what let the two documents drift: read as closed it now contradicts REQ-TOOLS-079, and a build following it would export an audit whose locators do not resolve on a machine carrying none of this product's code — the exact failure REQ-EVENTS-056 and REQ-TOOLS-079 exist to prevent, and one nothing errors on. Nothing this requirement guaranteed is lost: every field it named is named by REQ-TOOLS-079, which additionally carries the identifier, the no-argument-values property and the export reasoning this text never held.* A deny files a `permission_denied` warning issue; a one-time or session-scoped user approval files a `permission_approved` timeline entry. Mid-session mode changes share the audit, interleaved with decision entries in write order, in the shape REQ-TOOLS-082 fixes; that shape is cited and not restated here, including its rule that `skipped_personas` is present even when empty so that silence is unambiguous. *A shorter enumeration of it formerly stood here and is withdrawn on the same ground as the one above: it omitted fields REQ-TOOLS-082 requires, so the two documents described two different records. What this domain adds and keeps is below.* A mode-change entry has no entry identifier and none is owed to it (REQ-TOOLS-079, REQ-EVENTS-056), so the export obligation of REQ-SESSION-199 to carry an identifier reaches the entries that have one and no others. Mode changes are counted separately in metrics. The audit is append-only in the sense a reader may rely on: a recorded decision is never altered or removed except by the retention cap of REQ-SESSION-133, and entries stand in the order the decisions were taken. Those two properties MUST be evident in what the export of REQ-SESSION-199 produces, because an audit only this application can read is a materially weaker audit.
- **REQ-SESSION-138** — The launch audit MUST be recorded exactly once per session, by run startup (REQ-SESSION-087), at the first moment the configuration the run will actually execute with is settled — after the worktree has been bound (REQ-SESSION-085) and the sandbox verdict taken (REQ-SESSION-086), and before the first iteration. No later configuration change may alter it, and a run that resumes the session MUST NOT rewrite it, so the audit always describes the launch that created the session. A session that was created but never run therefore carries no launch audit at all, and loading it leaves the configuration snapshot empty (REQ-SESSION-036) rather than presenting a placeholder as a record of a launch that never happened. It MUST contain `{session_id, workspace_root, created_at, run_intent, permission_mode, check_suite, resolved_playbooks (per persona for the run's intent), hooks (id/name/event/matcher/source with secret-redacted command text), config_snapshot}`, with each persona's system-prompt file resolved into inline `resolved_system_prompt` text.
- **REQ-SESSION-139** — The metrics document MUST be rebuilt from the state plus the evidence records on every save and MUST report: session id, status and updated-at; global tool-call, token, cost and compression aggregates; per-agent metrics; the number of tool-call records; a tool-outcomes histogram classifying every recorded call (`outcome_kind` when the record carries one, otherwise derived from `status` and `is_error` into rejected, tool-error, success or unknown) whose bucket totals MUST sum to the tool-call record count; terminal shell-failure, suspicious-success and timeout counts; the 10 slowest tool calls ordered by recorded `elapsed_ms` descending; model-input record and stale-drop counts; context-selection totals; report-validation record and downgrade counts; permission decision, denial, source and mode-change counts; and issue counts in total and by kind. All counts are taken over the entries the evidence records still hold after the retention caps of REQ-SESSION-133 have been applied, so a capped record's counts describe what is stored rather than what the run once produced.
- **REQ-SESSION-140** — `summary.md` MUST contain, in this order: a `# Session <id>` heading; one line each for status, workspace, created and updated; `- Task: <first user event, cut to 240 characters>`; `- Stop reason: <reason>` when a stop reason is recorded, the line being omitted entirely when none is; a Metrics section in which a value that is unavailable renders as `n/a` or `—` and never as `0`; a Warnings section covering stale-input drops, mostly-elided artifacts, report downgrades, permission denials (naming the permission audit), tool errors, and terminal failures, suspicious successes and timeouts; an Agents section; a Slowest Tools section listing the top 5 by recorded `elapsed_ms`; and a closing inspection note saying where the rest of the record is obtained — the issues record, the timeline, the metrics document and the permission audit through the export of REQ-SESSION-199, and the session log as a file. The summary is itself a file (REQ-SESSION-006) and is replaced under REQ-SESSION-033, so a person reading it while a run writes it never sees it half-written.

  > mostly-elided artifacts are the attached artifacts a delegated agent's `PRIOR AGENT CONTEXT (FULL)` block left out
  > because they did not fit its budget (REQ-LIBRARY-098), each agent-and-artifact pair once, counted from the timeline's
  > `context_selection` entries. This still governs in full.
- **REQ-SESSION-141** — The conversation index MUST hold entries `{conversation_id, agent_name, persona, model, task_id, started_at, ended_at (set when status leaves "running"), status, event_count}`, where `event_count` is the number of events recorded for that conversation. A conversation MUST be resolvable by its id given in either hyphenated or un-hyphenated form, because both forms of one id reach a reader through exported material; the id is a lookup key and never a path, and no resolution rule that scans a directory or counts files is required or permitted.
- **REQ-SESSION-142** — Per-session debug logging MUST write to the session's log, which is a file so that a person can open it in an ordinary text reader (REQ-SESSION-002, REQ-SESSION-191), at the configured session log level (default WARNING; the strings DEBUG/INFO/WARNING/ERROR and integer levels accepted; an unknown string falls back to WARNING and logs a warning), and MUST restore prior logging state at run end.
- **REQ-SESSION-191** — For any session it lists, the application MUST offer three actions: one that opens that session's log for reading; one that reveals the session's files — the log, the summary and the artifact bodies of REQ-SESSION-002 — in the platform's file manager; and one that exports the session's timeline, issues, metrics and permission-audit records (REQ-SESSION-199). The third is not an addition for its own sake: those four are records rather than files, so the file manager no longer reaches them, and without the export moving them into the store would be a straight reduction in what a user owns about their own runs. All three MUST be available whether or not the session is live, MUST write nothing to the session's own record or files, and MUST report the situation rather than appearing to succeed when the log, the files, or a record is missing. All three belong to the action vocabulary of REQ-SHELL-048.
- **REQ-SESSION-199** — The timeline (REQ-SESSION-134), the issues record (REQ-SESSION-135), the metrics document (REQ-SESSION-139) and the permission audit (REQ-SESSION-137) MUST each be obtainable as a file the user chooses, in a form that yields every field of every entry to a stock parser on a machine with none of this product's code present — the same guarantee REQ-EVENTS-166 makes for the event history and REQ-SESSION-189 discharges for it. Each MUST be exportable whether or not the session is live, and exporting MUST NOT disturb the session: nothing is written to its record, and no run pauses for it. Where a session holds no entries of a kind, the export MUST produce an empty record of that kind rather than nothing at all, so that absence is distinguishable from failure. Three further obligations bind it. **It is not a channel.** The export is a user-initiated action producing a file at the moment it is asked for; it MUST NOT be offered or usable as a way to observe a run in progress, MUST NOT refresh itself, and no surface may be built on repeating it (REQ-SESSION-071, REQ-SESSION-159). **The audit exports as an audit.** The permission audit's export MUST make evident the properties the record itself has (REQ-SESSION-137): every entry in the order the decisions were taken, none omitted, and — where the retention cap of REQ-SESSION-133 has dropped earlier entries — a statement that it has and how many, so a capped audit can never be mistaken for a complete one. **It exists to be checked against.** These four are the records this application's own surfaces render, and the export is what lets a user who does not trust that rendering read the record for themselves; an export that summarised, reordered or filtered what the surface shows would defeat the only reason it exists. **A locator resolves against it.** Where an entry of an exported kind can be named by a locator (REQ-EVENTS-056) — an issue by its `id`, a permission-audit **decision** entry by the identifier REQ-TOOLS-079 gives it — the export MUST carry that identifier for every entry it emits **that has one**, so that a locator carried in one exported record resolves against another on a machine with none of this product's code and with nothing beyond a stock parser. Two consequences are stated so neither is inferred. An entry whose own requirement gives it no identifier is not one this obligation reaches: a permission-audit mode-change entry has none and is owed none (REQ-TOOLS-082, REQ-TOOLS-079), and a kind that holds entries of more than one shape is nameable while its unidentified entries are not, which REQ-EVENTS-056 states. And where the record's own shape holds an identifier the export MUST carry it inside the entry, as the permission audit's does; where a shape is closed against additions and an identifier must nonetheless travel, it MUST be carried beside the entry and MUST be locatable as the identifier there, since a value an exported document carries under no known field resolves nothing. The export MUST NOT resolve a locator itself: what a locator names is never inlined, expanded or replaced by the entry it points at, because an export that followed a locator into the tool-call evidence record would become the export that record must never have (REQ-EVENTS-056, REQ-TOOLS-190, REQ-SESSION-136). **The destination is written whole or not at all, and a replacement is retried.** What an export write owes its destination is REQ-EVENTS-145's — that obligation is cited here and none of it is restated, so a change to it changes this requirement with it. This requirement adds only which part of it is load-bearing here and what happens when it fails: the one-step-visibility obligation is what stops a user's previous export being destroyed by a write that does not complete, and it is required of these exports whatever form each takes, the line-delimited forms included. Where the chosen destination already holds a file, replacing it MUST take the bounded retry ladder of REQ-TRACE-061 — cited, not restated, and this domain states no ladder of its own for it; REQ-SESSION-033's ladder governs the summary file on this machine's own storage and is not this one. The reason is the destination rather than the record: this is a write whose target the product does not choose, and a save dialog reaches removable media, storage shared with another machine, a synchronising client's folder, and a directory in which another application holds the previous export open. On such storage a replacement fails transiently with no other opener present at all, so an export a user asked for would otherwise fail for a condition of storage the user can neither act on nor reproduce. **It is not a backup, and does not become one.** These exports are how records leave this application in a form other software reads; they are not restorable by this product and MUST NOT be presented as protecting a user's history against the loss of a machine. That is REQ-SESSION-201's artifact, which is a different thing for a different purpose and does not duplicate this one.

### 18. Durable Per-Session Event History

- **REQ-SESSION-143** — The durable event history is part of the session's record and holds every event the run published, in the order it was emitted. A stored event MUST reproduce every field of what the live stream emitted for that event, adding nothing and dropping nothing, so that reading the stored history and subscribing to a running session are interchangeable inputs to one consumer. Getting that history out of the product is the export's obligation and not the write path's: REQ-SESSION-189 writes it as one event per line in the envelope the event schema fixes, and that is where REQ-EVENTS-166's guarantee — every field readable by a stock parser on a machine with none of this product's code — is discharged. The record of what a trim dropped is REQ-SESSION-144's and belongs to the same session record.
- **REQ-SESSION-144** — The event history is capped, and neither the cap nor the trim is this domain's to fix. The configuration key, its default, its value space, the rejection of a negative value, and the meaning of a configured `0` are REQ-CONFIG-473's. How a trim is performed — the headroom permitted above the cap before a trim runs, which events a trim keeps, that it counts from the history's current contents rather than from a carried-over figure, that it takes effect in one step with no intermediate state a reader can observe, and that a trim which did not complete leaves the previous contents in force, records a warning, and is not reflected in the record of what was dropped — is REQ-EVENTS-091's. This domain holds no copy of the cap, of the headroom figure, or of the trim rule, and states no second reading of a cap of `0`. What it adds is where the record of a trim lives and what a reader may conclude from it: the truncation record belongs to the session's own record, it exists only once a trim has dropped events, and its absence MUST read as no events having been dropped rather than as an unknown figure — which is what lets `truncated` and `dropped_events` be reported as `false` and `0` for an intact history (REQ-SESSION-153) and lets a listing state a session's dropped count (REQ-SESSION-188).
- **REQ-SESSION-145** — The history writer MUST never **raise** into a run: each entry point turns exceptions into logged warnings and signals the outcome through its return value, so no caller of the writer ever has to catch. **What the run then does with that return value is not this requirement's** (amended 2026-09-06 under OQ-42): a *serialization* failure drops that one event with a warning and lets later events land, and a *durable recording* failure is REQ-EVENTS-088's — admission stops for the affected runs and controlled cancellation begins. *The clause "an event that cannot be recorded is discarded with a warning rather than raised" is withdrawn as a statement about durable failures and survives only for the serialization case REQ-EVENTS-088 names; read whole, it said a run goes on recording nothing, which REQ-EVENTS-088 forbids.* Not raising and not stopping are different properties, and this requirement owns only the first. The line discipline the exported form depends on — that no stored event's serialization embeds a carriage return or line feed, so one event is always one line — is REQ-EVENTS-089's and is discharged where the lines are produced, by the export of REQ-SESSION-189.
- **REQ-SESSION-146** — Event-history bindings are per session id: a new registration replaces the previous one, lookup never falls through to a different session — history from one run must never be written into another run's record — and storing without a binding is a silent no-op.
- **REQ-SESSION-147** — Persistence MUST happen before forwarding to the caller's event consumer (a tee), so an event that a failing consumer never receives is nevertheless durably recorded. Detaching the history genuinely stops persistence even for a sink reference that escaped.
- **REQ-SESSION-148** — Reading a stored history MUST be streaming — never materializing the whole history at once, so a history of any size is readable in bounded memory — read-only, and forward-compatible: an event whose type discriminator is unknown yields an opaque event marked unknown with its payload intact — never dropped, never raising (strict decoding is an explicit opt-in). An entry that cannot be decoded MUST be skipped with the read-damage warning of REQ-EVENTS-106, whose fields this document holds no copy of, its excerpt cut to 200 characters, and a reader MUST NOT rewrite or repair the history. A missing history reads as an empty session. An entry with no event-type discriminator is malformed (skipped), not "unknown". Which types count as known MUST follow the event schema itself, never a separately maintained list.
- **REQ-SESSION-149** — *Withdrawn.* The resumable byte-offset tail, its restart flag and the discard-and-re-seed of derived state existed only so that a surface could follow a session executing in a process this application does not own, and no such session exists (REQ-SESSION-159). Nothing that reads a *stored* history is withdrawn with it: streaming, read-only, forward-compatible reading stays with REQ-SESSION-148 over the reader-warning rule of REQ-EVENTS-106, summarizing a history by decoding only its first and last line stays with REQ-SESSION-151 and REQ-EVENTS-126, replay stays with REQ-SESSION-150, and export stays with REQ-SESSION-189. A reattach reads the session's persisted state and needs no offset, no restart flag and no re-seed (REQ-SESSION-196).
- **REQ-SESSION-150** — Replay filtering MUST support event types, iterations, and inclusive since/until time bounds — all optional, combined with AND; timezone-naive stamps normalize to UTC; an empty result is a valid answer. As the stream is read, each event's owning iteration is determined from the enclosing `iteration.start` and `iteration.end` boundaries; events outside every iteration match no iteration filter, and stamp-less lines match no time filter. Replay is reading, never re-execution, and never modifies the history.
- **REQ-SESSION-151** — Stored-session discovery MUST: treat an *empty* history as present (a run that emitted no events is still a session one can ask about); summarize by counting the recorded events and decoding only the first and the last (on a damaged history the count may be off by one, which is acceptable for a chooser; exact figures come from export); report an unreadable history as containing zero events, with a warning, instead of aborting the listing; sort newest first by last-then-first timestamp with the session id as tiebreak, sorting histories with no usable timestamps last. A session id that did not come from the session store itself — one typed by a user, pasted in, or read out of a document — MUST be treated as untrusted: it is used only as a lookup key against this workspace's own sessions, MUST NOT be used to build a path or to name anything outside them, and where it matches no session the answer is no match rather than an error.
- **REQ-SESSION-152** — *Withdrawn.* The `events` command has no surface to appear on; browsing and replaying a stored history is carried by REQ-SESSION-188 and exporting one by REQ-SESSION-189.
- **REQ-SESSION-153** — An exported trajectory document MUST carry `trajectory_version: 1`; the run's identity (session id, task, and the workspace exactly as the run reported it — never a path belonging to the exporting machine); the permission mode; started and ended timestamps as ISO-8601 UTC; the status; the stop reason; the duration in seconds; `truncated` and `dropped_events`, taken from the truncation record and reading as `false` and `0` when there is none (REQ-SESSION-144); a summary recomputed from the exported events alone and from no other source — event, unknown-event and warning counts; `runs`, the number of `session.start` boundaries in the document, which is where a single-run consumer must split it; iterations; tool calls and tool failures; permission decisions and denials; verifier runs and failures; child agents; errors and fatal errors; per-type event counts; tokens; cost — and the events themselves as the raw stored payloads, with redaction inherited from the wire schema rather than applied again by the exporter, and unknown event types preserved intact. **Two scopes travel in one document and MUST NOT be read as one** (REQ-EVENTS-138, accepted amendment 2026-09-06, A6): the identity and outcome fields — task, workspace, permission mode, status, stop reason, started and ended timestamps, duration — describe the **latest run segment**, the events from the last retained `session.start` onward, while every count in the summary describes the **whole exported history**, which is why `runs` is carried at all and why it is the figure a single-run consumer splits on. This requirement states no derivation of its own for those fields; REQ-EVENTS-138 owns it, including what an unfinished segment exports and the prohibition on borrowing an outcome across a retained start boundary.
- **REQ-SESSION-188** — The application MUST let a user inspect a stored event history without leaving it. For the workspace's sessions it MUST show, per session with a stored history, the session id, the event count, the first and last event timestamps, and, for a capped history, that events were dropped and how many (REQ-SESSION-144); a session whose history is empty is still listed (REQ-SESSION-151), a history that cannot be read is listed as holding zero events with a warning, and a workspace with no stored history states that rather than showing an empty area with no explanation. Opening one MUST replay it read-only (REQ-SESSION-150) with filters on event type, iteration, and inclusive since/until bounds, combined with AND, each optional, an empty result being a valid answer that MUST be stated as such. Each replayed event MUST show its timestamp, its type, whether the type was unknown to this version, and a compact rendering of its payload cut to 110 characters per REQ-SESSION-194; the stored event MUST be viewable in full, exactly as it was recorded, for any event. Warnings about skipped or undecodable lines MUST be shown alongside the events, never in place of them. A time bound the user enters that is not ISO-8601 MUST be refused before the read, with a message conveying which bound and what was entered; wording is left to the implementation. Replay is reading and MUST never modify the history.
- **REQ-SESSION-189** — The application MUST let a user export one or several sessions as trajectory documents (REQ-SESSION-153). The destination MUST be a file the user chooses through the platform's save dialog — there is no implicit destination and nothing is written until a destination is chosen. Exporting exactly one session MUST write one trajectory document. Exporting several MUST write one batch document holding those trajectory documents in the order the user selected them; the wrapper's key names, its closed inventory and the count it carries are REQ-EVENTS-144's, and this requirement holds no copy of them. *This requirement formerly fixed the wrapper itself, as `{"trajectory_version": 1, "sessions": [<document>, ...]}`, and declared that it carried no field of its own beyond those two key names. That inventory is withdrawn: REQ-EVENTS-144 requires the wrapper to carry the count of documents it holds, and a wrapper cannot both carry that count and carry nothing beyond two keys — the two statements could not both be satisfied by one build. What the withdrawn clause protected is not lost, because REQ-EVENTS-144's inventory is equally closed and equally exhaustive, so a consumer that understands one document still understands a batch. No conformance test may look for a `sessions` key on a batch document.* Two conditions MUST be reported as warnings that do not stop the export: a history holding more than one `session.start` boundary, conveying that the session was resumed, how many runs the document covers, and that its identity is the most recent one; and a capped history, conveying how many events were dropped and that the export is therefore not the complete run. The exported document MUST also be obtainable as the plain event stream, for a consumer that wants the stream rather than the summary: one event per line, each line the envelope the event schema fixes, carrying every field the live stream emitted (REQ-SESSION-143) and readable by a stock JSON parser on a machine with none of this product's code present (REQ-EVENTS-166). That line-delimited form is where the stock-parser guarantee for the event history is discharged, since the history is no longer kept as a file, and it MUST be produced for any session the application can list, whether or not that session is live. How the chosen destination is written is not this requirement's: what an export write owes its destination is REQ-EVENTS-145's, including that the document becomes visible there in one step, and where that destination already holds a file the replacement MUST take the bounded retry ladder of REQ-TRACE-061. Both are cited and neither is restated, for the reason REQ-SESSION-199 states for the same destination — a file the user names may sit on storage this product neither chose nor can characterise.
- **REQ-SESSION-193** — The key names of the three machine-readable documents this domain publishes are fixed, because a consumer cannot be written against a list of figures. Every key is lower snake case, and the inventory given for each document is exhaustive — a reader may rely on no other key being present, and adding one is a change to that requirement. The `session.start` payload (REQ-SESSION-090) carries `session_id` (string), `task` (string), `workspace_root` (string path, as the run reports it), `persona` (string), `permission_mode` (string, as configured at launch), `sandbox` (object `{"enabled": boolean, "backend": string}` describing the verdict in force), and `max_iterations` (integer or null). The metrics document (REQ-SESSION-139) and the trajectory document (REQ-SESSION-153) name each figure listed in their requirement by the same words that requirement uses, joined by underscores, with the trajectory document's top level being exactly `trajectory_version`, `session_id`, `task`, `workspace`, `permission_mode`, `started_at`, `ended_at`, `status`, `stop_reason`, `duration_seconds`, `truncated`, `dropped_events`, `summary`, and `events`. Key order is not significant anywhere. The batch wrapper that carries several trajectory documents together (REQ-SESSION-189) is **not** one of these three documents and its key inventory is not fixed here: it is REQ-EVENTS-144's, equally closed and equally exhaustive, and this requirement holds no copy of it.

### 19. Reattach Surfaces and Projections

- **REQ-SESSION-154** — The desktop session list MUST project listing metadata into rows: label = task title, else the launcher-known name, else the session id (a just-launched run keeps its prompt-derived label until metadata carries a title, and a refresh must not strip launcher-known requirement attribution); status from `execution_status` defaulting to idle; branch from the metadata worktree record, else "—"; a relative-time duration label; the worktree path as detail; and `awaiting_input` from metadata (absent → false). The status MUST be rendered from the stored value itself, as text and never by colour alone (REQ-SHELL-149), so every value of REQ-SESSION-073 is distinguishable from every other: a session repaired to `interrupted` reads as interrupted and is never shown as though it had never run, and a value from outside the closed vocabulary is shown verbatim. A stale session (REQ-SESSION-057) MUST additionally carry the stale marking of REQ-SESSION-182 beside that status.
- **REQ-SESSION-155** — `awaiting_input` MUST render as a "waiting for you" tag on session rows and "Waiting for your answer" status text, and MUST drive the requirement board's "Answer" affordance for background runs blocked on approvals or questions — persisted metadata is what lets a background run say it is blocked on a person across every surface and across restarts.
- **REQ-SESSION-156** — Desktop whole-state reads MUST use the read-only snapshot read of REQ-SESSION-040 — no repairs and no writes, verifiable by observing that nothing the session owns is changed by the read — and MUST project the persisted state into display models covering the run summary, transcript, agents, artifacts, todos, key metrics, pending questions and approvals (copied, so that display work can never mutate what was read), and the verifier summary. A `verifier_state` that cannot be parsed MUST resolve to idle rather than failing the read, and a persisted `gate_warning` MUST still be reported when the verifier is idle. The result MUST report the elapsed time of the state read and the elapsed time of the projection as separate values. Which parts of a view a user is entitled to see restored from this projection, rather than recomputed or lost, are fixed by REQ-SESSION-196.
- **REQ-SESSION-157** — Pending questions and approvals MUST render as transcript trailer rows — derived from what is pending now and always placed after every recorded row, re-appended by both whole-state and delta paths: a question stepper row of the form `<N> step(s) — <first title>` and one row per approval of the form `Approval needed — <command or tool>`.
- **REQ-SESSION-158** — A desktop board-launched run (a requirement unit) MUST: adopt the worktree the flow provisioned, given by explicit path, refusing a path that is not part of the repository, and record it as not owned by the session so the session never deletes a tree the flow owns (REQ-SESSION-084); make the session id available to the caller as soon as the session exists, without waiting for the run to end; open no window and take no window or keyboard focus, so that several launches in succession leave the user's foreground application unchanged; return an empty session id rather than raising when the launch is refused; and have the caller's completion listener registered before the launch call returns, so that a run finishing immediately still delivers its completion notification. The empty session id is the return value only and is never the whole report: a refused launch MUST also be reported to the user through the notification surface of domain 19, conveying which requirement unit could not be started and why, and the unit's row on the requirement board MUST show it as not started with that reason attached — a refusal that produced no session must never be indistinguishable from a unit nobody has run yet.
- **REQ-SESSION-182** — The application MUST offer one place from which the workspace's sessions are managed, built on the listing of REQ-SESSION-042 and the metadata of REQ-SESSION-030 and reached through the session browser of REQ-SHELL-126. It MUST show, per non-internal session, the row projection of REQ-SESSION-154, and MUST mark a stale session (REQ-SESSION-057) as stale beside its stored status, as text and not by colour alone (REQ-SHELL-149), so the cause of a refused restore or a blocked integration is visible where the session is. It MUST offer these actions, all in the action vocabulary of REQ-SHELL-048: open the session (REQ-SESSION-118); repair one stale session; repair every stale session in the workspace; delete a session (REQ-SESSION-166), behind a confirmation that states the deletion is permanent; the log, files and export actions of REQ-SESSION-191; and the whole-store backup and restore of REQ-SESSION-201, which are workspace-scoped rather than per-session. The backup disclosure of REQ-SESSION-200 MUST be reachable from here; nothing stops the product stating it elsewhere as well, but this is the surface it may not be missing from. Repair MUST perform exactly the explicit repair of REQ-SESSION-060 and MUST report, per session repaired, the session id, the status it was stuck in, the new status `interrupted`, and the reason it counted as stale (REQ-SESSION-059); when nothing was stale it MUST say so rather than reporting nothing at all. A session whose stored state cannot be parsed MUST be listed and reported as unreadable (REQ-SESSION-041) while every other session stays usable. Wording throughout is left to the implementation.
- **REQ-SESSION-196** — Reattaching to a session — one that has been running in the background, one whose window was closed, or one being opened again after a restart — MUST restore from persisted state, and not recompute or discard, all of: every transcript row the session recorded, at its own index and in order, with statuses settled per REQ-SESSION-078 and REQ-SESSION-079 and archived pages reachable per REQ-SESSION-192; the todo state; the child-agent tree; the metric aggregates (REQ-SESSION-169); the report artifacts; the pending questions and approvals, as trailer rows per REQ-SESSION-157; the verifier summary and any `gate_warning`; the worktree binding and its branch; the checkpoint list; and the session-scoped model override. Four things are explicitly not restored, because they describe a moment rather than the session: streaming animation and partially streamed text, which come back as the settled rows they became; live terminal buffers, so a terminal tool row shows its recorded output rather than a live screen until a stream is re-attached (REQ-SHELL-110); elapsed-time counters for activity that is no longer running; and scroll position, unless a desktop preference (REQ-SHELL-006) says otherwise. Everything restored MUST come from the read-only snapshot read of REQ-SESSION-040. This requirement formerly completed that snapshot from the session's own stored `transcript.row` events, for any row a debounced save had not yet written; no save is deferred any more (REQ-SESSION-067), so a row the session recorded is a row its persisted state already holds and there is nothing left to complete. The entitlement is unchanged and is now met by the snapshot alone. What must not be lost with the mechanism is the rule it protected: there MUST NOT be a second, differently derived path — a row the session recorded is a row a reattach restores whether or not any window was watching (REQ-SESSION-034), and a surface that then goes on to follow a still-live session receives exactly the rows that session records (REQ-SESSION-120, REQ-SESSION-159) rather than deriving them a second way.

### 20. Live Sessions and Sessions at Rest

- **REQ-SESSION-159** — A session is in exactly one of two conditions, and this requirement is the product's single definition of them; a document that needs to name a session's condition cites this identifier rather than restating it. Either the session is **live** — the one running instance of the application (REQ-STARTUP-161) owns it, holds its lock (REQ-SESSION-050) and is executing it — or it is **not running**, and exists only as its persisted record. REQ-SESSION-056's `live` is the record-observable approximation of the first condition and is deliberately not identical to it, because it resolves every uncertainty toward running (REQ-SESSION-051, REQ-SESSION-172): a lock left behind by an instance that crashed, and a lock this machine cannot prove unheld, both report live there while being, respectively, a session at rest and a session this instance may not touch. Where the two differ, REQ-SESSION-056 governs every decision taken from the record — reaping, stale detection, listing, the integration precondition — and this requirement governs what a surface may do with the session. A live session reaches every surface of that instance through the updates the application publishes for it as the run proceeds (REQ-SESSION-071, REQ-SESSION-161): which window started the run, whether any window is still watching it, and whether it was detached into the background (REQ-SESSION-190) make no difference to what a surface receives, because all of those are the same instance. A session that is not running is opened from its persisted record and may be continued (REQ-SESSION-196, REQ-SESSION-112). There is no third condition in which a session executes somewhere this application can only watch, and the filesystem is never a channel between a run and a surface: no surface follows a session by reading its record or its files, and no file this product writes into a session's own place on disk is a signal to another process (REQ-SESSION-002). A session left behind by a crash or a force-quit is not a third condition either — it is a not-running session whose record still asserts a run, settled by the lock reap of REQ-SESSION-047 and the explicit repair of REQ-SESSION-060, after which it opens like any other persisted session. The only session this instance can neither view nor continue is one whose lock it cannot prove unheld — a lock naming another machine, or one that cannot be read (REQ-SESSION-056); such a session MUST be refused rather than watched (REQ-SESSION-083), with the explicit release of REQ-SESSION-183 as the remedy, so it is unreachable only while something else may still be running it and never permanently. This requirement formerly held that when a session runs in a process other than the one displaying it — a second window of this application, another instance opened on the same workspace, or a run detached into the background — the only channel to it is the filesystem, and required the live transcript to be followed by tailing the stored event history. The first and third of those cases are inside the one instance and are served by published updates; the second does not arise, because a second launch of the application surfaces the running instance rather than starting a rival process. The reason that requirement gave for sharing one derivation — that following a session and reopening it afterwards must produce identical transcripts — is **not** withdrawn along with the mechanism: it now holds by construction, because only one derivation of a transcript remains (REQ-SESSION-196), so the equality REQ-MONITOR-242 requires can no longer be broken by two paths disagreeing. The durable event history itself is untouched in substance: it remains the record of every event the run published, field for field (REQ-SESSION-143), what replay reads (REQ-SESSION-150) and what a user can take away whole (REQ-SESSION-189). What is withdrawn is following it live, not writing it or reading it.
- **REQ-SESSION-160** — *Withdrawn.* Reproducing the run's row numbering from a tail of the event history was the follower's half of a derivation no surface performs any more (REQ-SESSION-159), and everything in it that outlives the tail is owned elsewhere. That transcript row indices are assigned contiguously from `0` and that a consumer replaces the row at an index rather than appending after it is REQ-EVENTS-052's; that a row keeps the index it was given when older pages are evicted is REQ-SESSION-192's. The placeholder row and the discard-and-re-seed rule are withdrawn outright: a surface that detects it has missed an update reconciles from a whole-session read (REQ-SESSION-161), which recovers the rows themselves rather than standing in for them with a placeholder, and leaves the displayed rows in place until the replacement set is ready.
- **REQ-SESSION-161** — Everything outside the transcript — todo lists, the agent tree, token counts — MUST come from a whole-session read of the session's state rather than from transcript increments, and a whole-session read is also what reconciles anything an increment did not deliver, including an update a surface has detected that it missed. For a live session that read is the whole-session update the application publishes on request; for a session that is not running it is the read-only snapshot read of REQ-SESSION-040. Because that published update deliberately omits the transcript (REQ-MONITOR-216), reconciling a *transcript* increment a surface missed MUST also re-deliver the transcript: for a live session the run republishes it from the lowest index it still holds, which the increment channel already expresses and which a cleared transcript already uses (REQ-MONITOR-214, REQ-MONITOR-215, REQ-MONITOR-229); for a session that is not running it comes from the projection of the snapshot read (REQ-SESSION-156). A reconciliation that left the transcript alone would not satisfy the requirement that what a surface shows after the read equals the persisted record (REQ-MONITOR-226). Neither read is ever performed on a timer (REQ-SESSION-071): a whole-session read happens when a surface opens a session and when it has something to reconcile, and at no other time. An increment whose first-touched row index falls before the oldest row the consumer still holds from its most recent whole-session read MUST be declined; declining costs exactly one further whole-session read, and the rows on display MUST be unchanged by the increment that was declined.

### 21. Checkpoints as Session Data

- **REQ-SESSION-162** — Per-iteration git checkpoints MUST persist in two places that stay consistent: refs under `refs/rotaris/checkpoints/` in the run's tree (the isolated worktree for isolated sessions, else the workspace), and the session's `checkpoints` list mapping iteration to ref and commit. Keeping the mapping in the session state is what allows checkpoints to survive a resume and to remain restorable after a crash.
- **REQ-SESSION-163** — The listing record's `checkpoint_count` MUST mirror the length of the state's checkpoint list (the session list reads the listing record only); readers default an absent value to 0 for records written before checkpoints existed.
- **REQ-SESSION-164** — Checkpoint restore for a session that *claims* to be running MUST be refused, because the pre-restore checkpoint this operation records would contend with writes from the supposedly live run; the stale-repair flow exists precisely to make restore available again after a crash. The refusal MUST convey the session id, the status the session records, that nothing was restored and the working tree is unchanged, and — when the session is stale rather than live — that repairing it makes the restore available (REQ-SESSION-182). It MUST be presented as an error on the surface that asked for the restore (REQ-GIT-096); the wording is left to the implementation, and no numeric code is produced (REQ-SESSION-187). **That refusal holds for the whole of the restore and not only at the moment it is asked for.** It is not discharged by answering the question once and proceeding on the answer. From the moment the product answers it until the restore has completed or been abandoned, no session in the workspace may become live; where one has, the restore MUST be refused rather than carried through, and where the restore has already begun to change the working tree it MUST be undone to the state it started from. Whether new runs are refused before the question is asked, or the question is asked again once that refusal is in force, is left to the implementation; what is fixed is that there is no window between the two into which a run may be admitted. **This restore never disturbs a live session either.** It MUST NOT stop, cancel, interrupt, or require a run that is under way to give up the working tree it is changing; the remedy on finding a live session is to refuse, never to clear it out of the way. **The reason this is stated here rather than left to follow from the sentence above.** What this operation replaces is the user's own working tree, not a record the product keeps, so a run admitted while it proceeds has the files it is reading and writing changed beneath it — and unlike a store the product owns, nothing about the working tree is under this product's control to put back. A run that is asked to stand aside and whose files are then replaced has been damaged by the restore whether or not it complied. The same rule governs the whole-store restore of REQ-SESSION-201, which cites this requirement as its precedent; both are one rule and neither is the other's exception.
- **REQ-SESSION-165** — *Withdrawn.* Listing and restoring checkpoints has no command surface; the capability is carried by the desktop checkpoint browser of domain 06 (REQ-GIT-096 and the gates of REQ-GIT-058), with this domain's refusal for a busy session staying in REQ-SESSION-164.
- **REQ-SESSION-195** — The session record MUST carry `last_restored_sequence`: the integer sequence of the checkpoint most recently restored into this session's tree, or null when no restore has ever succeeded for the session. It defaults to null, so a state written without it loads unchanged (REQ-SESSION-015), MUST be written as part of the same durable write that reports a restore successful, and MUST be left untouched by every refused and every failed restore. Its only use is to widen the drift candidate set of REQ-GIT-056 so that undoing a rollback never demands a force (REQ-GIT-155); it MUST NOT affect which checkpoints are listed, numbered, pruned, or restorable, and a value naming a checkpoint no longer recorded simply contributes no candidate.

### 22. Session Deletion

- **REQ-SESSION-166** — Deleting a session MUST first best-effort discard the session's checkpoint refs (loading the state to locate the right tree — the worktree for an isolated session, else the workspace root), then remove the session's record and its files (REQ-SESSION-002) together, ignoring errors, so a deletion never leaves a listed session with no record, or files with no session. An unreadable session still deletes. Deleting a missing session is a no-op. A ref-cleanup failure logs a warning naming the leftover `refs/rotaris/checkpoints/` location; cleanup stays best-effort so a session still deletes when the repository moved or never existed. Refs MUST be pruned as well, because removing only the record would leave them behind permanently. The workspace-scoped improvement library is not part of the session and MUST NOT be reduced by the deletion (REQ-SESSION-007).
- **REQ-SESSION-167** — The run lifecycle deletes a session in exactly one situation: a *just-created* session whose launch failed before the run started (worktree bind or sandbox failure). A resumed session MUST never be deleted by a failed launch.

### 23. Metrics Continuity Across Resume

- **REQ-SESSION-168** — On every persist, in-process metric aggregates MUST be copied into the state: global tokens, cost, tool calls, compressions, per-agent metrics, and sorted compression-dedup ids. The legacy token-usage field is set only when total tokens exceed 0, else null.
- **REQ-SESSION-169** — At run start and resume, in-process aggregates MUST be rebuilt from the persisted state with graceful fallbacks: a per-agent tool total without per-tool detail restores as a single pseudo-tool entry; zero global tokens falls back to the legacy token-usage field, then to merging per-agent snapshots; global cost, compressions, and tool-call counters are recomputed from agents the same way. Consequence: cumulative token, cost, and tool counters continue across resumes rather than resetting.

### 24. Reasoning-Content Repair at Open

- **REQ-SESSION-170** — The full session open of REQ-SESSION-040 — and only that path, never the read-only snapshot read — MUST run a best-effort repair before the session is handed back. The trigger MUST be a declared property of the model, read from the model-capability metadata the product ships with (REQ-PROVIDER-137), and never an observed failure, a hard-coded list of model identifiers, or a guess from a provider name; when the metadata does not declare the property for the session's default-persona model, the repair MUST NOT run, because rewriting stored conversation files on suspicion is worse than a request the provider might refuse. When that metadata declares that the session's default-persona model rejects requests in which an earlier assistant message carries no reasoning content, every persisted conversation event the session recorded is examined, and action events whose reasoning content is null or missing, together with agent message events whose message carries no reasoning content, are rewritten with an empty string in place of the missing content, in one durable operation so that no reader observes the session part-way through the pass. The pass MUST run at most once per open, MUST record and log how many items it changed, and MUST NOT prevent the open from completing when it fails.

### 25. Cross-Cutting Invariants

- **REQ-SESSION-171** — For one pid at one moment, lock reaping, liveness reporting, stale detection and the worktree-integration precondition MUST all reach the same verdict: it MUST NOT be possible to observe one of them treating a process as alive while another treats the same process as gone.
- **REQ-SESSION-172** — Any uncertainty about whether a session is live resolves in favour of "still running"; detection performs no writes; repair is explicit, made durable at once, idempotent, and never raises.
- **REQ-SESSION-173** — The last *requested* save wins in the record, not the last write to finish; a terminal status is always durable before its save call returns; disk is never staler than the newest requested state.
- **REQ-SESSION-174** — Every run through the shared lifecycle persists its full event history regardless of streaming (supplying no event sink still persists the history; it only means nothing is streamed out), and the stored history is exactly the sequence the live stream saw (persist-before-forward tee).
- **REQ-SESSION-175** — History and diagnostics writing never fails a run: the event history, transcript publication, change callbacks, diagnostics writers, and the timeline-to-wire bridge all degrade to logged warnings.
- **REQ-SESSION-176** — Per-session bindings (event sink, event history, transcript recording, hook running, approval handling, audit) bind late by session id and are discarded at run teardown, so that no leftover binding can influence a later run in the same process, and an event arriving after teardown has no destination.
- **REQ-SESSION-177** — The terminal `result` event is delivered exactly once per run — through the event bus for runs that started, written directly to the sink only for runs that never attached anything — and the run outcome of REQ-SESSION-187, the `result` payload, and the human summary all read off one shared derivation.
- **REQ-SESSION-178** — A session list is limited to what the listing record holds, so every list-visible attribute (title, status, staleness inputs, checkpoint count, requirement attribution, awaiting-input) is denormalized into that record at save time, with reader-side defaults for older records.
- **REQ-SESSION-179** — Data written by another version of this product is honored but never repaired in place: absent optional state keys load as their defaults (REQ-SESSION-015), absent metadata keys take their reader-side defaults (REQ-SESSION-030), an undecodable secondary state part degrades exactly as an absent one (REQ-SESSION-036), and a schema version newer than this one is refused rather than lossily restored (REQ-SESSION-038). There is no predecessor layout and no whole-state fallback record (REQ-SESSION-005, REQ-SESSION-037).
- **REQ-SESSION-180** — Displayed liveness is re-derived from the same snapshot that renders the header (agents settled against the execution status; running tool rows neutralized on non-live sessions), so that an internally inconsistent snapshot — from an earlier version or from a killed process — is never rendered as one.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005) revision 4, 2026-09-28.** Clause 13: the re-
  > derived liveness leaves a `paused` agent `paused`; a session at rest with paused agents is consistent, and every
  > other agent is settled as stated.
- **REQ-SESSION-181** — The created/resumed announcement of REQ-SESSION-185 follows whether the *run request* carried an existing session id, not what the run internally did: a caller that pre-names a brand-new session (REQ-SESSION-011) still has that session announced as created.

## Data & Formats

The shapes below are observable three ways: as wire events a consumer subscribes to, as the files listed here, and as the exports of REQ-SESSION-189 and REQ-SESSION-199. Where a shape is a machine-readable contract its field names are fixed and are stated as such; where a shape is only ever read by this application, what is fixed is the field set and what each field means, and no encoding is fixed by naming one.

### Where things are kept

Only what a person or another tool opens directly is a file; everything else a session records is held in
the workspace's durable session store, and what makes that store reachable is the workspace identifier
rather than a path (REQ-SESSION-197, REQ-SESSION-198).

```
the workspace, exactly where the user keeps it
  .rotaris/
    the workspace identifier        # stable, human-readable, travels with the workspace (REQ-SESSION-197)
    configuration, personas, model slots   # YAML the user edits; version control tracks it

this machine's own per-user storage  # never inside the workspace, never on synchronised storage
  the workspace's durable session store, located by the workspace identifier and never by path
    per session: the listing record (REQ-SESSION-030); the resumable state; the transcript rows and
      their released pages (REQ-SESSION-131, REQ-SESSION-192); the edit diffs; the launch audit
      (REQ-SESSION-138); the lock record (REQ-SESSION-046); the durable event history and the record
      of what a trim dropped (REQ-SESSION-143, REQ-SESSION-144); the timeline; the issues record;
      the metrics document; the evidence records — tool calls, model inputs, context selections,
      report validations, memory, the permission audit, and the conversation index with its events;
      the checkpoint list; the delegated-child records
  per session, as files held with the store (REQ-SESSION-002)
    the session log                 # REQ-SESSION-142; opened by REQ-SESSION-191
    the summary                     # REQ-SESSION-140; derived, written for a person to read
    artifact, attachment and image bodies   # referenced by the record, never held inside it

the user's own repository
  refs/rotaris/checkpoints/         # checkpoint refs (REQ-SESSION-162)
```

The four records a file manager no longer reaches — the timeline, the issues record, the metrics document
and the permission audit — are obtained through the export of REQ-SESSION-199; the event history through
the export of REQ-SESSION-189.

Nothing under `this machine's own per-user storage` is reached by backing up, copying or synchronising the
workspace, which is what REQ-SESSION-200 obliges the product to say and REQ-SESSION-201 gives the user a
remedy for. Everything under `the workspace` and `the user's own repository` travels with the user's own
material and needs nothing from this product.

### Session id

`YYYYMMDD-HHMMSS-` + 12 lowercase hex characters; regex `^\d{8}-\d{6}-[0-9a-f]{12}$`. The id is a lookup key and never a path (REQ-SESSION-010, REQ-SESSION-151). Ids are never reused (REQ-SESSION-009, REQ-SESSION-012).

### Resumable state

One record carrying `schema_version` (currently 1). Field inventory (bulk content referenced rather than copied, per REQ-SESSION-029; `workspace_root` is the run's effective root, which for a worktree-bound run is the worktree path and not the anchoring workspace of REQ-SESSION-001): `session_id`, `workspace_root`, `created_at`, `updated_at` (UTC, `Z`-suffixed), `config_snapshot`, `transcript_events`, `ui_edit_diffs`, `child_states`, `report_artifacts` (refs with `id`/`agent_name`/`status`/`path`), `todo_state`, `agent_todo_state`, an outer-loop progress record (nullable), `token_usage` (nullable legacy aggregate), `execution_status`, `exhausted_provider_models`, `message_count`, `message_limit` (nullable), `wait_state` (nullable), `run_intent`, `permission_mode`, `check_suite` (nullable), `sandboxed`, `sandbox_backend`, `requirement_id`, `unit_id`, `worktree` (nullable binding record), `checkpoints`, `last_restored_sequence` (nullable, default null — REQ-SESSION-195), `internal`, `run_type`, `global_tool_call_count`, `global_token_usage`, `global_cost` (default reads as source-unavailable), `global_compressions`, `agent_metrics` (map of agent name to `{tool_call_count, tool_calls, token_usage, cost, compressions, last_prompt_tokens}`), `root_context_tokens`, `seen_compression_ids` (map of agent name to sorted id list), `pending_questions`, `pending_approvals` (map of request id to payload), `verifier_state` (nullable), `gate_warning`, `active_model_key` (nullable), `runtime_model_configs`, `improvement_artifact_ids`.

Worktree binding record: the field set, the closed `merge_status` vocabulary and the defaults of REQ-GIT-015; this document holds no copy of any of them (REQ-SESSION-018). Persisted under `worktree`, null where the session has none.

Checkpoint entry: the persisted checkpoint record of REQ-GIT-016 — its field set, its defaults, and its closed `kind` vocabulary — which this document holds no copy of. What this document adds is where the record lives and in what order (REQ-SESSION-162): under `checkpoints`, the list ordered newest-last.

### Listing record

Exactly: `session_id`, `created_at`, `updated_at` (ISO strings), `execution_status`, `schema_version`, `internal`, `worktree` (record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Reader defaults: `checkpoint_count` 0, `task_title` falls back to the session id, attribution empty, `awaiting_input` false. The field set and those defaults are fixed by REQ-SESSION-030, and a listing reads nothing else but the lock record (REQ-SESSION-042).

### Status vocabulary and run outcomes

- Active statuses (assert an in-progress run): `starting`, `running`, `background`, `waiting`, `pausing`, `cancelling` (REQ-SESSION-055).
- Terminal/idle/blocked statuses: `idle`, `paused`, `paused_message_limit`, `awaiting_plan_decision`, `completed`, `failed`, `stopped`, `interrupted` (repair-only). Together with the six active values this set is the whole closed vocabulary (REQ-SESSION-073), which is the single definition every other document cites.
- Stop reasons and their classification: REQ-MONITOR-301 (this domain restates neither, REQ-SESSION-077).
- Child terminal states: the terminal subset REQ-MONITOR-300 declares absorbing, over the state set of REQ-MONITOR-014; this document holds no copy of either.
- Terminal run outcomes: the closed set of REQ-ORCH-083, carried here through REQ-SESSION-187; this document holds no copy of it. No outcome is expressed as a numeric code.
- Session lock record: `{"pid": <int>, "host": "<machine id>", "acquired_at": "<UTC ISO>"}` — the same three field names and value types REQ-GIT-020 fixes. A `host` that is not this machine is never reaped and is reported as a session held by another machine (REQ-SESSION-047, REQ-SESSION-048).

### Wire and stored events

Every event the run published, recorded in the order emitted, each reproducing every field the live stream emitted (REQ-SESSION-143); the line-delimited form a user can take away is the export's (REQ-SESSION-189). The event catalogue itself, and each type's payload fields, are fixed by REQ-EVENTS-041 and the event-history document's own catalogue; this document holds no copy of either and lists below only the types with persistence significance: `session.start` (first event of every run; payload per REQ-SESSION-090), `session.end` (mirrors the terminal result), `result` (exactly once per run), `transcript.row` (index + row copy, on append and settle), `tool.start`/`tool.finish`, `iteration.start`/`iteration.end` (iteration attribution boundaries), `gate.decision`, `gate.repair`, `error` (from error-severity issues, `fatal: false`). Unknown event types must survive read and export intact.

### Transcript rows

Persisted dictionaries with roles: `user`; `system`; `agent {name, persona, content}`; `thinking {name, persona, content, started_at?, chars, duration?}`; `tool {name, persona, tool, content (summary), detail (≤400 chars, single line), full_text (≤2000), full_detail (line structure preserved), tool_event_key, tool_terminal, status (one value of the four-value tool-row status vocabulary REQ-MONITOR-105 fixes, not copied here), started_at, duration?, stream_id? ("fg:<agent_name>" for terminal tools)}`; `verifier` (tool-shaped, `tool_event_key = "verify:<iteration>:<index>"`; a check outcome reaches this row's `status` through the mapping of REQ-NOTIFY-142, total over the closed five-value check-outcome set of REQ-ORCH-123 and into the row-status vocabulary of REQ-MONITOR-105 — neither set nor mapping is copied here, REQ-SESSION-129). Every row carries `ts` in local `HH:MM:SS`. Thinking content caps at 4000 chars while `chars` keeps counting.

Edit diffs persist separately keyed `diff_id = "<agent>:<tool_event_key>"` and merge beside exactly one row at display time.

### Timeline, issues, tool calls, permissions

- Timeline entry: `{id: 12 hex, timestamp: UTC ISO, type, severity (default info), actor, message, metadata}`; durable entry first, derived wire event second (REQ-SESSION-134).
- Issue: `{id: 12 hex, timestamp, kind, severity, actor, message, evidence_ref, metadata}` (REQ-SESSION-135). `evidence_ref` is empty or a `<record kind>#<record id>` locator whose form and closed token set are REQ-EVENTS-056's; nothing that reads or exports these records resolves one.
- Tool call: `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` + optional `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings`; error-path args/result truncated to 2000 chars (REQ-SESSION-136).
- Permission decision: `{timestamp, session_id, agent_id, persona, tool_name, decision, rule_id, source, summary, reason, request_id?}`; mode change: `{event: "permission_mode_change", requested_mode, effective_mode, previous_mode, source, reason, skipped_personas}` (REQ-SESSION-137). Entries stand in the order the decisions were taken and are never altered; the export of REQ-SESSION-199 must show that, and must say so where the retention cap has dropped earlier entries.
- Repair timeline entry: type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, metadata `{previous_execution_status, execution_status, reason}`.

### Trajectory export document

The document's content is fixed by REQ-SESSION-153 and its top-level key names by REQ-SESSION-193; the outline below restates neither and is given so the file's shape is readable beside the rest of this section. `trajectory_version: 1`; identity (session id, task, workspace as the run reported it); permission mode; started/ended; status; stop reason; duration; `truncated`/`dropped_events`; recomputed summary (event/unknown/warning counts, `runs` = count of `session.start` boundaries, iterations, tool calls/failures, permission decisions/denials, verifier runs/failures, child agents, errors/fatal errors, per-type counts, tokens, cost); raw stored events (redaction inherited from the wire schema; unknown types intact).

Several sessions exported together are wrapped in the batch document of REQ-EVENTS-144, whose closed
three-key inventory is that requirement's and is neither restated nor extended here.
