# Machine-Readable Event Stream, Replay, and Trajectory Export — P. Session history in the desktop interface

Part 5 of 7 of [domain 20](../20-event-history-replay-export.md), which indexes every part. Defines REQ-EVENTS-146 – REQ-EVENTS-178.

### P. Session history in the desktop interface

**Replacement retries (REQ-EVENTS-145, accepted amendment 2026-09-06).** Every export format governed by this requirement MUST use the bounded replacement retry policy of REQ-TRACE-061. Exhaustion MUST report a recoverable export failure and preserve the previous destination file. This includes trajectory, batch, and line-delimited exports. REQ-SESSION-033 remains the owner of the local summary-file policy.

**REQ-EVENTS-146** — *Withdrawn.* There is no command group and no process exit code. The two conditions this contract distinguished — no stored history for the named session, and a time bound that cannot be read — are reported in place by REQ-EVENTS-174 and REQ-EVENTS-171 respectively, and an empty result remains an ordinary success (REQ-EVENTS-118).

**REQ-EVENTS-147** — *Withdrawn.* The listing capability, its ordering, and every column it carried are held by REQ-EVENTS-168; character-cell padding and an arrow glyph have no meaning in a rendered table.

**REQ-EVENTS-148** — *Withdrawn.* The empty-listing capability is held by REQ-EVENTS-169.

**REQ-EVENTS-149** — *Withdrawn.* The per-event row, its fields, its unknown-type marker and its detail rendering are held by REQ-EVENTS-170.

**REQ-EVENTS-150** — *Withdrawn.* Obtaining the selected events as JSON lines byte-identical to the stored lines is held by REQ-EVENTS-172.

**REQ-EVENTS-151** — *Withdrawn.* Keeping damaged-line warnings out of the machine-readable output while still showing them to a person is held by REQ-EVENTS-170 and REQ-EVENTS-172.

**REQ-EVENTS-152** — *Withdrawn.* Reporting a session that resolves to no store, and refusing to disclose anything about a path outside the workspace, are held by REQ-EVENTS-174.

**REQ-EVENTS-153** — *Withdrawn.* Rejecting an unreadable time bound before any store is read is held by REQ-EVENTS-171.

**REQ-EVENTS-154** — *Withdrawn.* Writing an export to a chosen destination, atomically and with parents created, and confirming what was written and where, are held by REQ-EVENTS-173.

**REQ-EVENTS-155** — *Withdrawn.* There is no standard output to write a document to; a document reaches the user as a file under REQ-EVENTS-173.

**REQ-EVENTS-156** — *Withdrawn.* The multi-run and truncation disclosures, and the rule that neither is a failure, are held by REQ-EVENTS-173.

**REQ-EVENTS-157** — Given an export of several sessions in which any one of them cannot be resolved, the export MUST NOT proceed: no file may be written and no partial document may be produced, and the unresolved session MUST be reported per REQ-EVENTS-174.

**REQ-EVENTS-158** — *Withdrawn.* There is only one surface, so there is no second one to hold to byte-identical output.

**REQ-EVENTS-159** — Every history-reading surface MUST tolerate unknown event types and damaged lines without failing; each surface MUST adopt the reader's tolerance rather than making a separate determination of its own.

**REQ-EVENTS-168** — The desktop interface MUST offer a session-history surface for the workspace the window has open, reached through a named action in the vocabulary of REQ-SHELL-048 and from a session in the session browser of REQ-SHELL-126. It MUST list every session of that workspace that holds a stored history (REQ-EVENTS-124, REQ-EVENTS-131) in the order of REQ-EVENTS-124, presenting for each the seven facts of REQ-EVENTS-129: session id, where the session's own files are, event count, first timestamp, last timestamp, whether the history is truncated, and the dropped-event count. The time span MUST be presented as the absence of any timestamp where the session has none; as the first timestamp alone where there is no last timestamp or the two are equal; and otherwise as both. Truncation MUST be presented beside the count, never instead of it, and MUST NOT be conveyed by colour alone (REQ-SHELL-149), because a truncated history's count is a count of survivors. There is no workspace to choose and no path to type: the surface reads the window's workspace and no other. Opening it MUST start no run, publish no event, and write nothing to any session's record (REQ-EVENTS-100, REQ-EVENTS-123).

**REQ-EVENTS-169** — Given no session in the workspace holds a stored history, the surface MUST present its empty condition, MUST name the absolute path of the workspace it searched, and MUST NOT present this as an error — a workspace whose runs recorded nothing, and one that has never been run in, are both ordinary states. The wording is the implementation's; the workspace named and the fact that the search succeeded are not.

**REQ-EVENTS-170** — Selecting a session MUST present its events, one row per matching event in emission order, each row carrying: the event's `timestamp`, or an explicit marker of its absence where it has none; the `event` value; a marker that the type falls outside this build's catalog, where it does, conveyed in text and not by colour alone (REQ-SHELL-149); and a detail rendering of the payload with the four envelope fields removed, serialized as one compact JSON object with sorted keys and clipped to 110 characters followed by a single `…`, so a clipped detail is 111 characters and is distinguishable from one that fitted — the same counting rule REQ-EVENTS-061 and REQ-EVENTS-063 use, so one rule governs every clip in this document. An event of an unrecognized type MUST be shown and flagged, never omitted, and MUST NOT stop the surface. Warnings about damaged lines met while reading (REQ-EVENTS-106) MUST be presented in this surface alongside the events, each naming the line's position and its reason, and MUST NOT be interleaved into any machine-readable output the surface produces (REQ-EVENTS-172).

**REQ-EVENTS-171** — The surface MUST offer controls for exactly the four filter axes of REQ-EVENTS-117: event types, iteration numbers, an inclusive lower time bound, and an inclusive upper time bound. The type control MUST offer the catalog of REQ-EVENTS-041 together with any unrecognized type present in the history being read, so an unknown type stays selectable (REQ-EVENTS-121). An axis left unset MUST restrict nothing, and a filter that matches no event MUST present as an empty result — never as an error or a failure (REQ-EVENTS-118). Time bounds MUST be entered through a date-and-time control, so an unreadable bound is unreachable from this surface; where a bound is nevertheless supplied as text, it MUST be rejected in place, naming which bound was rejected and quoting the value, and no store content may be read on account of the rejected query.

**REQ-EVENTS-172** — The surface MUST be able to hand the user the currently selected events as JSON lines, each line byte-identical to what the live stream emitted for that event (REQ-EVENTS-080, REQ-EVENTS-104) and terminated by a single line feed on every platform (REQ-EVENTS-090), whether by copying them or by writing them to a file the user chooses. Each line MUST be emitted from what the stored record holds, in stored order — a concatenation, never a re-serialization. For an unfiltered selection those lines MUST equal the run's lines exactly, in number and in bytes; for a filtered selection they MUST equal the corresponding subset. The output MUST carry events and nothing else: no warning, no heading, no row rendering, and no value derived from an event for querying or presentation may appear in it, so a consumer reads exported output and live output interchangeably. This is the **history export**, and it is one of the two forms REQ-EVENTS-166 obliges: it MUST be available whether or not the session is live, and what it produces MUST be a file or a copy the user now holds, never a channel the surface keeps open.

**REQ-EVENTS-173** — The surface MUST offer an export action over one or more selected sessions, producing the trajectory document of REQ-EVENTS-132 for a single session and the batch document of REQ-EVENTS-144 for several, in the order the sessions are listed in the selection. The action MUST be offered whether or not a selected session is live, and a live session MUST export the history as it stands at the moment the action was taken (REQ-EVENTS-098, REQ-EVENTS-123). The destination MUST be chosen through the platform's own file chooser; the document MUST be written atomically with missing parent directories created (REQ-EVENTS-145). On success the surface MUST state how many trajectory documents were written and the absolute path they were written to. The export MUST still be produced, and MUST NOT be reported as a failure, in either of two cases, each of which MUST be disclosed to the user: the session holds more than one run, where the disclosure MUST state how many runs the document spans — the figure the document's `summary.runs` carries — and that the identity fields describe the most recent of them (REQ-EVENTS-138); and the store is truncated, where the disclosure MUST state how many events were dropped — the figure the document's `dropped_events` carries — and that the document therefore does not cover the whole history. Where both apply, both MUST be disclosed. Wording is the implementation's; the figures and the facts are not.

**REQ-EVENTS-174** — Given a session identity that resolves to no stored history under the workspace the window has open, the surface MUST report that in place, naming both the identity exactly as it was supplied and the absolute path of the workspace searched, and MUST NOT present the condition as an empty result — so a session that was looked for in the wrong workspace is distinguishable from a session that recorded nothing, which is an ordinary empty result under REQ-EVENTS-118. An identity that attempts to reach outside the workspace (REQ-EVENTS-130) MUST produce the same report and MUST disclose nothing about whether anything exists under the identity it named.

**REQ-EVENTS-175** — Reading a history MUST NOT block the interface. Given a session whose history has already been read, a change to any filter of REQ-EVENTS-171 MUST be reflected within 100 ms of the interaction. Given a history still being read, the surface MUST present a progress state and MUST remain interactive, and reading MUST stay incremental and lazy (REQ-EVENTS-099, REQ-EVENTS-122, REQ-EVENTS-126) so that neither a long history nor a workspace holding many sessions is ever held whole in memory. Cancelling a read MUST leave the history exactly as it stood (REQ-EVENTS-100).

### Q. Cross-cutting integration invariants

**REQ-EVENTS-160** — For any run, the stored history MUST equal the emitted stream exactly: same payloads, same order, same envelopes; the first stored event `session.start`, the last `result`, exactly one `result`, and every stored event carrying the session's id.

**REQ-EVENTS-161** — The terminal `result` event MUST reach the store as well as any live consumer, so the history's last record is independent evidence that the terminal event traversed the normal delivery path.

**REQ-EVENTS-162** — An exported trajectory's event list MUST equal the lines the live stream emitted for the same run, and its summary counts MUST agree with what actually happened during the run. This is the conformance test for REQ-EVENTS-166: because the export rather than the write path is now what a third party reads, an export that drifts from the wire breaks the guarantee outright, and this equality is what detects that.

**REQ-EVENTS-163** — The per-session evidence records are distinct contracts and MUST NOT be conflated by a consumer: the tool-call evidence record holds arguments exactly as they were passed, with no masking applied; the permission audit (REQ-TOOLS-078) and the verification-gate record (REQ-TOOLS-190) each hold their own record under their own retention rule; while the event history holds only masked wire events, under this document's cap and trim rules alone. A figure taken from one of these MUST NOT be assumed to agree with a figure taken from another: they are capped independently and record different things.

**Not every record named above has an export, and this requirement does not grant one.** Which records are exportable is settled by the redaction-safety test REQ-TOOLS-190 states and owns, and is restated nowhere. Under it the event history has the two exports of REQ-EVENTS-166, the permission audit has the one REQ-SESSION-199 requires, and the verification-gate record has the one REQ-TOOLS-190 requires. **The tool-call evidence record has none, and MUST NEVER gain one** (REQ-SESSION-136, REQ-TOOLS-190): it holds the arguments an agent passed exactly as they were passed, unredacted, and that is precisely why it is named here as a contract a consumer must not conflate with the masked event history. Where exports exist, they are as distinct as the records behind them and MUST NOT be presented as one document or reconciled against each other. Nothing in this requirement may be read as offering an export to a record that has none.

**REQ-EVENTS-164** — A programmatic consumer MUST be able to iterate a run's events asynchronously while the run is still in progress, receiving the same events, in the same order, that the live stream carries. Pending events MUST be buffered up to 1024; while 1024 are outstanding, each further event MUST be discarded rather than blocking the run, and the number discarded MUST be readable by the caller once iteration has ended, so that an incomplete stream is detectable rather than silent. Discarding events MUST NOT affect the caller's ability to obtain the run's terminal outcome, which the call itself returns rather than requiring it to be recovered from the stream. Iteration MUST end once the `result` event has been yielded. The discard count MUST be readable at any time, during iteration as well as after it, and MUST only ever rise, so that a caller can notice a backlog while it can still act on it rather than learning of the loss only once the run is over; it MUST NOT be reset by reading it. This programmatic interface MUST carry its own version, independent of the event schema version, whose current value MUST be the string `"1"`.

**REQ-EVENTS-165** — A live consumer MUST receive every event raised for the session it is registered for, in emission order, with no event delivered twice and none skipped where the consumer returns normally; delivery MUST complete before the run proceeds past the operation that raised the event, so a slow consumer delays the run rather than losing or reordering events. Every event delivered MUST already satisfy the validation of REQ-EVENTS-017, so a consumer never receives a partially populated or unmasked event. A consumer that fails MUST NOT fail the run (REQ-EVENTS-074); the contract is nevertheless that a consumer returns without failing and does not block. That contract MUST be enforced rather than left advisory: delivery of one event to one consumer MUST be bounded at 5 seconds, and a consumer that has not returned by then MUST be treated exactly as one that went away under REQ-EVENTS-031 — delivery to it stops permanently, a warning is recorded naming the session and the event type that was outstanding, and the run proceeds. No other consumer's delivery is affected, and recording is unaffected (REQ-EVENTS-082). A bound is required because an unbounded wait would let one faulty consumer stall a run indefinitely, which REQ-EVENTS-074 already refuses to allow for a consumer that fails outright.

**REQ-EVENTS-166** — **A user MUST always be able to get a run's history out of this application in a form software that knows nothing about this product can read.** The stored history is a record only this application reads; this requirement is the obligation that makes that acceptable, and it is discharged by **export**. It is the single definition of what an export of a session record must guarantee, for this document and for every other.

Two exports of the event history MUST exist and MUST both satisfy the guarantee below: the line-delimited history export of REQ-EVENTS-172, which is the run's own lines, and the trajectory document of REQ-EVENTS-132.

The guarantee. Decoding one exported event line, reading a whole exported history, or reading an exported trajectory document MUST require nothing beyond a standard JSON parser and this specification: no part of the agent runtime, no configuration loading, no network access, no access to the store the export was taken from, and no access to the workspace the run took place in. An exported history or an exported document copied to another machine — one carrying none of this product's code, and no copy of the store — MUST yield **every field of every event** when read there with a stock JSON parser, and MUST yield them unaltered: the same field names, the same values, the same schema version, and the same events in the same order the run emitted them (REQ-EVENTS-080, REQ-EVENTS-134, REQ-EVENTS-162). Nothing about the export may be conditional on this application still being installed, on the session still existing, or on the session not being live.

Three obligations attach to every export this requirement governs.

1. **Reachable whether or not the session is live.** An export MUST be offered for a session that is running and for a session that is not, and MUST NOT require the run to end first (REQ-EVENTS-098, REQ-EVENTS-173). A live session exports its record as it stands at the moment the action was taken.
2. **An export is not a channel.** It MUST be a user-initiated action that yields a file or a copy the user then holds, taken once per request. No surface may follow a run through an export, no export may be repeated on a timer or re-taken to observe progress, and no export may be the way any part of this product learns what a run is doing (REQ-SESSION-071, REQ-EVENTS-123). What a run is doing reaches a surface through what the application publishes for it and by no other route; an export is how a record leaves.
3. **The export carries the record's own integrity properties.** Whatever ordering, append-only character, or completeness the record has where it is stored MUST be evident in what is exported — the events in emission order, the count of what was dropped where anything was (REQ-EVENTS-137, REQ-EVENTS-140) — because an export that a reader cannot check against the record it claims to be is decorative.

**This requirement is the pattern for every other session record a user could previously have read for themselves**, the session timeline, the recorded issues, the metrics document and the permission audit among them. Each such record is exported in a form a stock tool can read, reachable whether or not the session is live, and under the three obligations above; the export of each is owned by the domain that owns the record, and that domain cites this identifier for what its export must guarantee rather than restating it. The permission audit is the case that decides the shape of the rule, because it is exactly the record a user consults when they do not trust this application's rendering of events: an audit only this application can read is a materially weaker audit, and its export inherits the ordering and append-only obligations its own requirement states.

**REQ-EVENTS-167** — The wait for a human approval is not this document's to fix: its configuration key, its value space, its default, and the reading of a configured `0` are REQ-CONFIG-126's, and this document holds no copy of any of them. What this document requires is that the wait in force for a request MUST be visible to a consumer as the `timeout_seconds` field on `approval.requested`, so that a consumer reading the wire learns how long the request will be held without consulting the configuration — and, per REQ-EVENTS-049, that the field is null exactly on the resolver that never waits.

**REQ-EVENTS-177** — The verification-gate log of REQ-TOOLS-190 MUST NOT gain an event type in the catalog of REQ-EVENTS-041. Every write and every decline it records is an attempt an agent made through a tool, and is therefore already observable on the stream as the `tool.start` / `tool.finish` pair of REQ-EVENTS-057 for that call, with the decline carried as that call's failure; the gate's own reasoning — its `outcome`, `decline_case`, `reason`, `checks` and `detail` — stays durable in the verification-gate record REQ-TOOLS-190 fixes and in the timeline entry that requirement also writes. A consumer needing that detail MUST read that record rather than expect a wire event, and MUST NOT treat the absence of such an event as evidence that no gate decision was taken. This is a deliberate exclusion, not an omission: the catalog stays at the 23 types of REQ-EVENTS-041.

**REQ-EVENTS-178** — The product is one desktop application and offers no embedding surface and no programmatic entry point: there is no library, package, plugin host, or endpoint through which code the user did not launch may start a run, drive a run, or subscribe to this application's runs, and no requirement of this document is satisfied by one. The consumer contracts of REQ-EVENTS-164 and REQ-EVENTS-165 are not an exception and MUST NOT be read as one: the consumer they describe is this application consuming its own runs in its own process — the session-history surface of Section P, the run views, and the desktop notice channel — so the interface version REQ-EVENTS-164 fixes versions an internal contract and not a published one. What may leave the application is a file, never a connection: the exported history of REQ-EVENTS-172 and the exported trajectory document of Section O, each readable with a stock JSON parser and nothing else (REQ-EVENTS-166). This is a deliberate exclusion rather than an omission — a programmatic driving surface would be a second way to start work, carrying its own permission, approval, and sandbox behavior to hold in step with the desktop one — and it is why the withdrawn surfaces of Section A are not partially reinstated in another form.
