# Architectural constraints extracted from the specification — 5. Update channels, latency and view isolation

Part 7 of 22 of [the constraints](../constraints.md), which indexes every part.

## 5. Update channels, latency and view isolation

| # | Constraint | Label | Requirements |
|---|---|---|---|
| U-01 | **Two payload shapes**: an incremental transcript update carrying the lowest row index whose content may still change, the rows from there on, new diffs and the persona set; and one whole-session update carrying the session record with unbounded collections emptied. **Every publication on either channel carries a sequence number** from one counter per session **shared by both channels**, starting at 1 and raised by exactly one per publication. | HARD | REQ-MONITOR-214, REQ-MONITOR-216 |
| U-02 | The whole-session update carries **every field of the session record that any surface is able to display**, not a curated subset. | HARD | REQ-MONITOR-217 |
| U-03 | A row a view has not yet seen is published **immediately — no minimum wait, debounce or delay floor of any size, on any platform**. Growth of an already-visible row is coalesced into a trailing **50 ms** tick; coalescing loses nothing; pending publications flush at run end. | HARD | REQ-MONITOR-218 – REQ-MONITOR-220, REQ-MONITOR-294 |
| U-04 | Run activity appears on live surfaces within **250 ms at the 95th percentile**, at zero rows and at thousands alike; an update at 10,000 rows costs **no more than 2x** the same update to an empty session, measured run to surface; a session with nothing happening does no work at all. *Measured, and both pass with room: relay p95 1.133 ms at 0 rows and 1.291 ms at 10,000; ratio 1.14 against a ceiling of 2, and 1.19 at `REQ-SESSION-192`'s actual 5,000-row cap. **Two caveats travel with those figures and must not be dropped when they are quoted.** The measured interval **excludes the commit `REQ-MONITOR-221` requires before publication**, so every figure is a lower bound on the interval the requirement bounds. And the ratio passes because a ~500 µs transport floor dwarfs an O(N) store apply at 2.83 ns per resident row — the margin is supplied by the transport, not by the store, so a regression in the apply stage would not appear in an end-to-end p95 at all.* | HARD | REQ-MONITOR-222, REQ-MONITOR-223; `spikes/ipc-hop-latency.md` §4.1, §6, §7.3, §8 |
| U-05 | Each run surface reflects a state change within **100 ms of the run recording it, at the 95th percentile**. **The percentile is now stated in the requirement (SR-8) rather than inferred**, together with the clause that "a single update took longer is not by itself non-conformant", and the requirement says why: so the figure reads the same way as `REQ-MONITOR-222`'s. *This row previously read as an absolute bound, and the reading decides the verdict: measured p95 5.951 ms unloaded and 7.807 ms under load — 8× to 40× inside — while 24 of 9,000 samples exceeded 100 ms, worst 124.983 ms in an unloaded run. SR-8 ruled the absolute reading unsatisfiable in principle for any userspace program on a preemptive operating system, which is a defect rather than a requirement.* | HARD | REQ-ORCH-155; `spikes/ipc-hop-latency.md` §4.3, §6 |
| U-06 | A stage that cannot correctly apply an increment must **decline it and re-render from a whole read**, and must never render a result differing from what a whole read would produce. Declining must not interrupt the user or blank the transcript. **The same three things are now required on a second trigger**: a publication whose sequence number is not the one expected means an update was lost, and the surface must record a diagnostic, stop consuming increments and re-render from a whole read **on the publication that reveals the gap rather than after any delay**. The path therefore has two entrances and both must be exercised deliberately, because neither fires in normal operation. A number at or **below** the expectation is a superseded publication rather than a gap, and is what discharges `REQ-MONITOR-225`'s stale-read rule. | HARD | REQ-MONITOR-224, REQ-MONITOR-225, REQ-MONITOR-226, REQ-CHAT-052 |
| U-07 | **No view may hold a run open, slow it down, or change its outcome.** A run observed by nothing, by a healthy view, or by a broken one reaches the same terminal result, persisted record, event sequence and timing. | HARD | REQ-MONITOR-226, REQ-MONITOR-232, REQ-MONITOR-293, REQ-ORCH-138, REQ-EVENTS-015, REQ-EVENTS-081, REQ-EVENTS-082 |
| U-08 | **The in-process event-bus consumer contract is the opposite**: delivery of one event to one consumer completes before the run proceeds past the operation that raised it — a slow consumer delays the run — bounded at **5 seconds**, after which that consumer is detached permanently. | HARD | REQ-EVENTS-031, REQ-EVENTS-165 |
| U-09 | The asynchronous programmatic consumer buffers up to **1024** pending events and discards rather than blocking beyond that, exposing a discard count that only rises. | HARD | REQ-EVENTS-164 |
| U-10 | Delivery is **addressed per session** with no fallback across sessions; registering for an empty session id is rejected; per-session bindings bind late and are discarded at teardown. | HARD | REQ-EVENTS-075, REQ-SESSION-146, REQ-SESSION-176 |
| U-11 | Following a session and reopening it afterwards must produce **identical transcripts**, and the persisted record is authoritative wherever the two could disagree. **The guarantee survives SR-2; its mechanism is gone and it is now true by construction.** `REQ-SESSION-159` as amended says so in terms: the reason it gave for sharing one derivation "is **not** withdrawn along with the mechanism — it now holds by construction, because only one derivation of the transcript remains". That derivation is `REQ-SESSION-196`'s snapshot read completed from the session's own stored `transcript.row` events under `REQ-EVENTS-052`'s replace-at-index semantics, "never from a second, differently derived path". Two paths can no longer disagree because there is only one. | HARD | REQ-SESSION-159, REQ-SESSION-196, REQ-MONITOR-242, REQ-MONITOR-292 |
| U-12 | Approval and question rows are **not recorded history**: they are computed from what is pending now, always follow every recorded row, and are appended identically by both paths. | HARD | REQ-MONITOR-230, REQ-SESSION-157, REQ-CHAT-051 |
| U-13 | Once terminal, the displayed transcript must equal the persisted record **including corrections only a terminal state determines**. | HARD | REQ-MONITOR-228, REQ-SESSION-079 |
| U-14 | A display tick must not alter a row, write session state, or cause a transcript publication. | HARD | REQ-MONITOR-108, REQ-MONITOR-110, REQ-CHAT-158 |
| U-15 | **Re-reading persisted state on a timer is not a supported way to follow a run, and the rule now has no exception anywhere in the product.** `REQ-SESSION-071` as amended says so in those words — "no surface follows a session by reading its files, on a timer or otherwise" — and the carve-out this row used to record went with the foreign session. `REQ-MONITOR-246` survives and is what replaced it: everything outside the transcript reaches a surface on the whole-session update and by no other route, and a whole-state read happens **only when something asks for one** — a reconcile after a missed publication, a declined increment, a focus change, or opening a session that is not running. | HARD | REQ-SESSION-071, REQ-MONITOR-246, REQ-SESSION-161 |
| U-16 | **Withdrawn with the cadences it recorded.** `REQ-MONITOR-288` is withdrawn and `REQ-MONITOR-287` now opens "this domain fixes no cadence for polling a session's own state". The 750 ms foreign poll went with the foreign session (SR-2); the 2000 ms local reconcile is replaced by U-01's per-session sequence number and U-06's immediate gap-driven reconcile, which is strictly stronger — a lost update is caught on the very next publication rather than up to 2000 ms later, and a session with nothing happening does **no periodic work at all**. The figures `REQ-MONITOR-287` still fixes are unrelated to following a run and are cited where each is used. | WITHDRAWN | REQ-MONITOR-287, REQ-MONITOR-288 |
| U-17 | Control operations must be issuable against a run in a **different process**, with arguments limited to text, numbers, booleans and simple collections; the result is a boolean plus an optional string populated for exactly two operations; a control answers `false` rather than raising and is safe from concurrent callers. | HARD | REQ-MONITOR-004 – REQ-MONITOR-007, REQ-MONITOR-011, REQ-MONITOR-013 |
| U-18 | **The conflict is dissolved, and the replacement rule is stronger than the one withdrawn.** This row recorded that a session running in another process could be reached only through the filesystem, which contradicted U-17's requirement that every control be issuable across the boundary. `REQ-SESSION-159` as amended states the opposite as a rule: "the filesystem is never a channel between a run and a surface — no surface follows a session by reading its files". U-17's boundary is now unambiguously the run host against the window (`REQ-MONITOR-013`), which is a boundary inside one instance and has a channel. | WITHDRAWN (conflict dissolved) | REQ-SESSION-159, REQ-SESSION-161, REQ-MONITOR-013, REQ-MONITOR-243 |
| U-19 | The wire encoding of either update channel. | FREE | — |
| U-20 | **One counter shared by two channels makes per-session ordering a property of the transport across channel *names*, not merely within one.** `REQ-MONITOR-214` fixes a single counter per session raised by one per publication on either channel, and U-06 makes an unexpected number mean an update was lost. If a whole-session update can overtake a transcript increment for the same session — across two named IPC channels, across the run-host-to-main and main-to-renderer hops, or through any coalescing in the relay — the surface observes a gap that nothing was lost from and reconciles anyway. The failure is not silent, which is what makes it tolerable, but it is a self-inflicted reconcile rate on the one path the design needs to keep rare. **This is invisible in the payload types and no type check will catch it.** | HARD (derived) | REQ-MONITOR-214, REQ-MONITOR-226 |
| U-22 | **New. No host may treat persistence as a liveness signal, or request a save in order to make a session appear live.** With `REQ-SESSION-067`'s window withdrawn there is no longer any relationship between how often a session is saved and whether it is running, and `REQ-MONITOR-239` closes the door on anything reintroducing one. Liveness is the lock record's (C-06, C-07); a save is a save. | HARD | REQ-MONITOR-239, REQ-SESSION-067 |
| U-21 | **The subscription handler is part of the determinism surface.** A surface that has observed a gap stops consuming increments (U-06), so publications arriving while it reconciles must be **dropped, not queued and not replayed**. This is not an efficiency: I-11 requires the six apply counters to be byte-identical across iterations in fresh processes, and if publications arriving during a recovery reached the apply stage the `refused` total would depend on how many happened to arrive inside the recovery window. Exactly one `refused` is counted per recovery episode — on the publication that revealed the gap — followed by exactly one `reset`. A violation is a benchmark failure, not a performance problem. | HARD (derived) | REQ-MONITOR-226, REQ-UIBENCH-064, REQ-UIBENCH-083 |
