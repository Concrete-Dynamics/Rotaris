# User-Defined Lifecycle Hook Commands — Workspace Trust Gate

Part 3 of 6 of [domain 09](../09-lifecycle-hooks.md), which indexes every part. Defines REQ-HOOKS-090 – REQ-HOOKS-138.

### Workspace Trust Gate

- **REQ-HOOKS-090** — The gate SHALL decide on the declared provenance of a hook and SHALL NOT judge what its command does: no command is inspected for apparent danger, and no such inspection may be relied on to withhold anything. (Comparing the fingerprint of REQ-HOOKS-091, which covers command text, detects change to the declared set; it is not a judgement about the command.) For hooks resolved from the layered YAML configuration the rules are: a `global` or `default` hook is always permitted; a `workspace` hook is permitted only while a stored approval exists whose fingerprint equals the fingerprint of the current workspace hook set (REQ-HOOKS-091); an entry carrying no scope tag resolves as `default` before the gate is applied (REQ-HOOKS-014) and is therefore permitted; a hook carrying any other scope value is withheld, with no permissive branch for an unfamiliar value. Declaration order SHALL be preserved within the permitted group and within the withheld group. Hooks imported from an external agent carry scope `external:claude-code` and do not reach this gate at all (REQ-HOOKS-117), so this scope vocabulary says nothing about whether they run.

- **REQ-HOOKS-091** — The workspace hook fingerprint SHALL be the SHA-256 digest, rendered as 64 lowercase hexadecimal characters, of the canonical JSON document `{"version": 1, "hooks": [ {command, event, matcher, name, required, timeout_seconds}, ... ]}` — keys sorted, compact separators, ASCII-escaped — built from the workspace-scoped entries in declaration order. Observable consequences: computing the digest repeatedly over the same set yields the same 64 characters every time; the digest changes when any `command`, `event`, `matcher` (a matcher widened to empty included), `name`, `required`, or `timeout_seconds` changes, and when an entry is added, removed, or moved; it does not change when a `global` or `default` hook is edited; a workspace declaring no hooks yields the digest of the empty list, which equals the digest computed where only always-trusted-scope hooks are present and differs from that of every non-empty workspace set. `enabled` and `source` are not part of the document, so toggling `enabled` alone leaves the digest unchanged. `version` is part of the document, so raising it invalidates every stored decision. The fingerprinted list SHALL cover every workspace-scoped entry in declaration order, entries with `enabled: false` included. The consequence is deliberate and is the reading coherent with REQ-HOOKS-093: what the user reviews and allows is the set of commands the workspace declares, so an entry the user read while it was switched off may later be switched on without a fresh review, while rewriting, adding, removing, or reordering any entry — switched off or not — invalidates the decision at once. Excluding disabled entries was rejected because it would make a bare `enabled` toggle revoke the approval, contradicting this requirement's own statement that toggling `enabled` alone leaves the digest unchanged. Each entry object SHALL carry exactly those six keys and no others, and each SHALL carry a **resolved effective value** of its declared type rather than the literal text of the declaration: no key is ever absent and no value is ever JSON `null`, so an entry declaring no `matcher` contributes `""` and one declaring no `timeout_seconds` contributes the resolved default of REQ-HOOKS-008 as a JSON number. Two declarations that would run identically therefore hash identically. Because a resolved default is part of the hashed document, changing the value of any default of REQ-HOOKS-008 that reaches this document SHALL be accompanied by raising `version`; a default changed without that would invalidate every stored decision while leaving the review unaware it had been reopened. This requirement is the product's single definition of the workspace hook fingerprint — the digest algorithm, the canonical document it is taken over, the six fields, the resolved-value rule, and what does and does not change the digest: a document that stores, compares, or displays a hook-set digest SHALL cite this identifier rather than restating any of them.

- **REQ-HOOKS-092** — The first encounter with an unapproved workspace that declares hooks SHALL withhold those hooks and make a review request pending, carrying the workspace path resolved as REQ-HOOKS-097 requires, the fingerprint of the pending set, and exactly the workspace-declared hooks in declaration order — entries with `enabled: false` included, matching the fingerprinted list of REQ-HOOKS-091, and marked as currently inert so the user can see which of the commands under review would not run as things stand. No review is pending when the workspace declares no hooks, or when a stored decision — approval or rejection — already covers the current set.

- **REQ-HOOKS-093** — Decision lifecycle:
  - Approving lets the workspace hooks run on later loads and clears the pending review.
  - Any change to the workspace hook set (rewriting, adding, removing, reordering) invalidates the decision: the hooks are withheld again and a fresh review with a new fingerprint becomes pending. An approval granted for one set therefore confers nothing on a command that has since been altered, nor on an entry added beside it.
  - A rejection persists: it is stored, it keeps withholding, and the user is not asked again while the set is unchanged; the question returns once the hooks change.
  - Clearing the decision re-applies the gate immediately; clearing when none is stored is harmless (a file that is not there is treated as success), while a removal that fails for any other reason SHALL surface as an error — an approval that survives an attempted revocation would keep letting hooks run.

- **REQ-HOOKS-094** — Reading a stored decision SHALL default to "not approved" and SHALL never fail outright: a missing file or state directory, unparsable JSON, a truncated file, JSON whose top level is the wrong type, an empty object, a missing fingerprint, a fingerprint that is not 64 hex characters, a `trusted` value that is not strictly a boolean (a number or a string is never taken as consent), a decision timestamp that cannot be parsed, an unrecognized version, or finding a directory at the path the file was expected at — each of these reads as "no decision", hence not approved. A decision timestamp with no timezone is taken as UTC.

- **REQ-HOOKS-095** — A decision recorded against one hook set SHALL NOT carry over to a different one: where the stored fingerprint and the computed fingerprint differ, the hooks are withheld. Transplanting a `.rotaris/` state directory from a checkout whose hooks were approved into a checkout whose hooks are different therefore confers no permission on the latter.

- **REQ-HOOKS-096** — A decision SHALL be stored at `<workspace>/.rotaris/hook-trust.json` as a JSON object carrying exactly the four keys `version` (the value `1`), `digest` (the fingerprint of REQ-HOOKS-091, 64 lowercase hexadecimal characters), `trusted` (a strict boolean) and `decided_at` (a timezone-aware UTC ISO-8601 timestamp), serialized with sorted keys, two-space indentation, and a single trailing newline. This requirement is the product's single definition of the trust decision file — its path, its four keys, and its serialization: a document that reads, writes, or presents a stored hook trust decision SHALL cite this identifier rather than restating any of them. Writing a decision SHALL: check the shape of the fingerprint first (reporting `Not a hook-set digest: ...` and writing nothing if it is malformed); create the `.rotaris` directory if it is absent; write the file atomically; and report any write failure rather than absorb it — a caller that wrongly believed a rejection had been persisted would go on invoking the very hooks the user declined.

- **REQ-HOOKS-097** — The workspace SHALL be resolved before the decision file is located, and it SHALL be resolved on the terms REQ-STARTUP-163 fixes for when two directory strings name the same directory — this requirement cites that rule rather than restating it, and states no rule of its own, because a product that decided the same question two ways could grant an approval under one spelling of a folder and withhold it under another. An approval granted under an absolute path therefore still applies when the same workspace is later referred to as `.`, and it applies under every other spelling that rule reconciles. Where that rule declines to reconcile two spellings, they are different workspaces here as everywhere else, so the approval does not carry across and the set goes back under review on REQ-HOOKS-092's terms — the safe direction, and the reason nothing is lost by not reconciling them. Resolving the workspace changes nothing else about the decision: it stays keyed by that workspace together with the fingerprint of the hook set, so any change to the set still withdraws the approval. The set permitted to run SHALL be exactly the in-memory sequence that was fingerprinted, with no reload between fingerprinting and permitting. The disk is consulted only when that sequence actually contains workspace hooks.

### Scope Fallback on Refusal

- **REQ-HOOKS-098** — Substitution of one scope's list for another's SHALL apply only among trusted scopes. Where workspace hooks were withheld, the global and default entries that their list had displaced SHALL be put back into the permitted set — but only entries whose own scope is always trusted, so that a displaced workspace-scoped list cannot regain execution by way of this fallback. Reinstated entries are appended after the permitted entries, keeping the relative order they held in the scope they came from. An entry is not added a second time: an inherited entry counts as already present both when its stable id is already permitted and when a permitted entry carries the same `event`, `matcher`, `command`, `required` and `timeout_seconds` compared after the resolution REQ-HOOKS-091 applies, the `name` playing no part in that comparison — a hook re-declared under a different name still runs the same command on the same event, and running it twice is what this rule exists to prevent. The gate's result exposes the permitted set (originally permitted, then reinstated, in declaration order), the withheld set, the reinstated set, and a notice string.

- **REQ-HOOKS-099** — Reinstatement follows from withholding and is not a lasting merge: once the user approves the workspace list, it substitutes for the inherited one in full (withheld and reinstated sets both empty, notice empty).

- **REQ-HOOKS-100** — End-to-end guarantee: given an unapproved workspace whose hook list is hostile, no process is started for the repository's hook; a `pre_tool` guard declared in global scope still stops the command it was written to stop; a `session_end` hook declared in global scope still fires; and the notice the user sees names neither, giving only how many were withheld and which configuration file declared them.

### Untrusted-Hooks Notice Hygiene

- **REQ-HOOKS-101** — The withheld-hooks notice SHALL be the empty string when nothing was withheld; otherwise exactly: `Skipped <N> hook(s) declared by this workspace's .rotaris/agents.yaml: workspace hooks run shell commands and this workspace has not been reviewed and trusted yet. Review the hooks in Rotaris to allow them to run.` — with singular and plural forms used correctly ("1 hook", never "1 hooks"). Where reinstatement returned the user's own hooks, the notice gains: ` Your own <M> configured hook(s) still run(s).` (singular/plural on both the noun and the verb).

- **REQ-HOOKS-102** — Notices and diagnostics about withheld hooks SHALL disclose only how many hooks were withheld and the path of the configuration file that declared them (plus the counts and workspace path of REQ-HOOKS-086). The `name` and the `command` of a withheld workspace hook SHALL appear on none of these surfaces: the notice text, the hooks settings tab and every other window of the desktop interface, the application log, the session's issue record, its timeline, anything exported from either (REQ-SESSION-199), and the session event stream. Given an entry whose `name` embeds an ANSI escape sequence that clears the terminal and whose `command` pipes a download into a shell, no escape byte, no fragment of that command, and no host name taken from it SHALL be present in any of them. The review dialog of REQ-HOOKS-106, which the user opens deliberately, is the only surface on which that text is displayed. The conflict with the `hook_name` field REQ-HOOKS-123 places on every `hook.start` and `hook.finish` SHALL be resolved in favour of this rule: the `hook.finish` announcing a withheld hook (REQ-HOOKS-126) carries that hook's stable id in `hook_name` — never its configured display name, and never an empty string — so the field stays populated and correlatable while no text the repository wrote ever leaves the gate.

### Desktop Settings and Review Dialog

- **REQ-HOOKS-103** — The hooks settings tab SHALL present a tree table whose accessible name is `Lifecycle hooks`, holding one top-level row per owning agent — `Rotaris` for this product's own hooks and `Claude Code` for imported ones, corresponding to the agent ids `rotaris` and `claude-code` of REQ-HOOKS-115 — with that agent's hooks as child rows. Each hook row SHALL show, in this column order: name, event, matcher — rendered as `every matching call` where the matcher is empty — source, and status. The source column SHALL render the entry's declaring scope (REQ-HOOKS-014, REQ-HOOKS-020) as a human-readable label rather than as the raw scope value, so that a user reads where a hook came from — the workspace, their own global configuration, or the built-in defaults — without having to know the vocabulary; the exact wording of those labels is left to the implementation. The status column SHALL carry exactly one of `inactive`, `disabled by agent`, `disabled`, `blocked — not reviewed`, `active`, selected by taking the first condition that applies in the order that vocabulary is listed: `inactive` where the hook cannot run for a reason declared in configuration rather than chosen on this tab — `hooks.enabled` is `false` (REQ-HOOKS-009, REQ-HOOKS-017), or the entry's own `enabled` is `false` (REQ-HOOKS-008), or the row is an imported record discovery marked unusable (REQ-HOOKS-113); `disabled by agent` where the row's owning agent toggle in the external-hooks policy file is `false` (REQ-HOOKS-115, REQ-HOOKS-116); `disabled` where that agent toggle is on but the row's own per-hook toggle is `false`; `blocked — not reviewed` where a workspace-scoped hook was withheld by the trust gate; and `active` where none of the four applies. A workspace hook the trust gate withheld therefore shows `blocked — not reviewed`, and shows `active` once the workspace is approved and nothing else suppresses it.

- **REQ-HOOKS-104** — The tab SHALL offer a "Review workspace hooks" button that opens the review dialog, together with a summary label describing the current decision ("not been reviewed" before any decision; "will not run" after a rejection) and a notice pointing at the pending review (its title contains "unreviewed"); the dialog never opens on its own. The tab SHALL also offer a control that re-reads the hook sources and re-projects the table, so that a hook added to a configuration file or to the external agent's settings while the application is open becomes visible without a relaunch; re-reading SHALL start no hook process and SHALL change no decision, and it governs runs started afterwards on the terms of REQ-HOOKS-131. Command text SHALL NOT appear anywhere else in the window — not in the table, in tooltips, in notices, or in accessible descriptions.

- **REQ-HOOKS-105** — The trust summary the settings surfaces work from SHALL report, for the workspace it was asked about: the workspace path; a status drawn from `none`, `review`, `trusted`, `refused`; the current workspace fingerprint (REQ-HOOKS-091); one entry per hook stating whether the gate permitted or withheld it; the workspace-declared hooks awaiting review; and the trust notice text of REQ-HOOKS-101. The status SHALL be `none` where the workspace declares no hooks, `review` where it declares hooks no stored decision covers, `trusted` where a stored approval matches the current fingerprint, and `refused` where a stored rejection matches it. Hooks reinstated under REQ-HOOKS-098 SHALL be reported as permitted even though the workspace's own list had displaced them, so that the summary describes what will actually run. Hook text in the summary SHALL be masked per REQ-HOOKS-133. A configuration that cannot be read SHALL yield a summary carrying no hook entries rather than an error, and that summary SHALL report status `none`: nothing could be read, so nothing can run, and REQ-NOTIFY-227 closes the hook-trust vocabulary at four statements and admits no fifth. In that state the settings tab SHALL show no hook rows and SHALL raise no pending-review notice, and the read failure SHALL degrade to a log entry in the manner of REQ-HOOKS-121 rather than becoming a warning of its own.

- **REQ-HOOKS-106** — The review dialog SHALL be modal, SHALL be titled `Review this workspace's hooks`, and SHALL be at least 620×440 logical pixels in size — the unit REQ-SHELL-022 uses for every window dimension in this product, so the minimum holds as the same physical area at every display scaling factor (REQ-SHELL-030). It SHALL state the workspace path; SHALL state how many hooks the workspace declares and that they are declared in `.rotaris/agents.yaml`, worded correctly for that count so an `N` of 1 reads in the singular and no `hook(s)` construction is emitted literally (REQ-HOOKS-054, REQ-HOOKS-101); and SHALL state that the entries are shell commands supplied by the repository's authors that will run on this machine under the user's own account. Each hook SHALL be rendered read-only in a fixed-width block carrying its name, its event, `matches` followed by the matcher (or `every tool call` where the matcher is empty), `timeout <n>s` annotated `(blocks the tool call on failure)` where `required` is true and `(advisory)` otherwise, and the command exactly as written — no re-wrapping, escaping, abbreviation, or styling that would let the displayed text differ from the text that will execute. An entry declared with `enabled: false` SHALL be shown too, marked as currently inert (REQ-HOOKS-092). This dialog SHALL be the only surface in the product that displays a hook command (REQ-HOOKS-102).

- **REQ-HOOKS-107** — Dialog buttons SHALL be "Do not run these hooks" (reject role, the default, holding initial focus and activated by Enter) and "Allow these hooks" (styled to signal risk, requiring an explicit click), each with an accessible description of what it will do. Leaving without choosing counts as rejection: Escape, the window close control, and any other dismissal all resolve as not approved. However the dialog is left, it SHALL report its decision once and only once — the first exit path taken is the one that reports. A failure to write the decision is shown as an error label in the dialog rather than passing unnoticed.

- **REQ-HOOKS-108** — Whole-flow guarantees: rejecting writes `trusted: false` to the workspace decision file and does not ask again on reload; approving writes `trusted: true`, the tab moves the row to `active`, and the summary status becomes `trusted`.

- **REQ-HOOKS-109** — Agent rows and hook rows in the tab SHALL carry checkboxes; clearing one is saved to the global external-hooks policy file, persists across a refresh of the tab, and never alters the external agent's own settings file. A change made while a run is under way SHALL take effect for runs started afterwards and SHALL NOT alter the hook set of the run already executing (REQ-HOOKS-131); the tab SHALL convey that, so a user clearing a checkbox mid-run is not left believing a hook has just been stopped.

- **REQ-HOOKS-136** — The hooks settings tab SHALL be the product's one venue for granting, refusing, and revisiting a workspace's hook trust decision, and every transition of REQ-HOOKS-093 SHALL be reachable from it. Given a workspace with a stored decision of either kind, the tab SHALL offer a control that clears that decision; activating it SHALL remove the stored decision, SHALL re-apply the gate immediately so the summary status of REQ-HOOKS-105 returns to `review` where the workspace declares hooks and `none` where it does not, and SHALL leave those hooks withheld until the user allows them again. Given no stored decision, the control SHALL be absent or inert, and clearing when none is stored SHALL be harmless. A clear that fails for any reason other than the decision file already being absent SHALL be reported on the tab as an error rather than absorbed, for the reason REQ-HOOKS-096 gives. Opening the review dialog again while a decision is stored SHALL present the current workspace hook set exactly as REQ-HOOKS-106 requires and SHALL replace the stored decision with whichever the user then takes. No other surface of the product, and no configuration key, preference, or environment variable, SHALL be able to approve a workspace's hooks.

- **REQ-HOOKS-137** — The hooks settings tab SHALL show the hook invocations of the session the user is looking at, so that the command output the advisory of REQ-HOOKS-054 and the issues of REQ-HOOKS-120 point at is reachable without leaving the application. For each invocation, in the order the invocations happened, it SHALL show: the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); the event; the tool name where there is one; the exit status as the timeline records it (REQ-HOOKS-119, so `-1` where the hook produced no exit status); the elapsed duration; whether the invocation timed out; whether it stopped the call; and the captured standard output and standard error, masked per REQ-HOOKS-133 and already limited per REQ-HOOKS-037. A hook the trust gate withheld SHALL appear as withheld with its reason, identified by stable id and without its command (REQ-HOOKS-102). A hook switched off by the failure budget SHALL be shown as switched off after its last recorded invocation. A session with no invocations SHALL show an explicit empty state rather than a blank area. The list is read-only: opening it SHALL start no process, publish no wire event, and write nothing to the session's diagnostics.

- **REQ-HOOKS-138** — The surfaces on which hook activity reaches a user SHALL be exactly these and no others: the notice channel (REQ-HOOKS-054, REQ-HOOKS-085, REQ-HOOKS-086, and the notices REQ-NOTIFY-223 to REQ-NOTIFY-228 define); the hooks settings tab (REQ-HOOKS-103 to REQ-HOOKS-105, REQ-HOOKS-136, REQ-HOOKS-137) and the review dialog it opens (REQ-HOOKS-106); the session's durable diagnostics (REQ-HOOKS-118 to REQ-HOOKS-120); the session event stream (REQ-HOOKS-123 to REQ-HOOKS-127); and the application log. A hook invocation SHALL NOT be written into the run's transcript, into an agent's activity text, or onto any other live run surface: a hook is the user's own code and its execution is not part of what an agent did. The only hook text ever placed in front of an agent is the refusal of REQ-HOOKS-049 and the feedback of REQ-HOOKS-051, and neither is a user-facing surface.
