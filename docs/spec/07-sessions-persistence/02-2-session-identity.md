# Session Persistence, Resume, and Background Sessions — 2. Session Identity

Part 2 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-009 – REQ-SESSION-050.

### 2. Session Identity

- **REQ-SESSION-009** — New session ids MUST have the shape `YYYYMMDD-HHMMSS-` followed by 12 lowercase hexadecimal characters, matching the regular expression `^\d{8}-\d{6}-[0-9a-f]{12}$`. The id MUST be minted before the first state write is persisted, so a caller can name and display the run before any work happens.
- **REQ-SESSION-010** — *Withdrawn.* Deriving a session's identity from a directory path was a filesystem-mediated resolution rule with nothing left to resolve: a session is addressed by its id, and every per-session binding — diagnostics, event history, scheduler — binds by that id and never falls through to another session (REQ-SESSION-146, REQ-SESSION-176). That ids are never reused, so one id names one session for good, is REQ-SESSION-012's.
- **REQ-SESSION-011** — A caller MUST be able to pre-name a new session by supplying the session id in the run request (so the run is addressable and displayable before any worker output arrives); a supplied new-session id MUST be ignored when the request resumes an existing session.
- **REQ-SESSION-012** — Session ids MUST never be reused. Consumers are entitled to assume that two different histories never share one identity, so a stored history found under an id always belongs to the session that id names.

### 3. Resumable State: Schema Rules and Defaults

- **REQ-SESSION-013** — The persisted session-state schema version MUST currently be `1`, and every persisted state MUST carry a `schema_version` field defaulting to the current version.
- **REQ-SESSION-014** — `created_at` and `updated_at` MUST be UTC timestamps; their JSON serializations MUST end with a `Z` suffix. `workspace_root` MUST be persisted as a string path.
- **REQ-SESSION-015** — Loading a state payload with absent optional keys MUST succeed by applying defaults (legacy tolerance is the general schema rule): missing check-suite record loads as null; pre-cost snapshots load with an "unavailable" cost; pre-attribution snapshots load with empty attribution strings. Field defaults MUST include: empty config snapshot, empty transcript events, empty edit-diff list, empty child-state list, empty report-artifact list, null todo states, null outer-loop progress, null token usage, execution status `idle`, empty exhausted-model list, message count 0, null message limit, and null wait state.
- **REQ-SESSION-016** — Five run-audit facts MUST be recorded in two places that stay consistent — on the session's state, and into the launch audit (REQ-SESSION-138): run intent (default empty), permission mode (default empty), resolved check suite (default null), sandboxed flag (default false), and sandbox backend name (default empty). Each MUST be stamped on the state at the moment it is settled: the run intent, the permission mode and the resolved check suite when the run request is applied, and the sandboxed flag and backend name when the sandbox verdict is taken (REQ-SESSION-086), so that a completed session can afterwards be asked what it actually ran under (REQ-SANDBOX-108). When those same facts reach the launch audit is not this requirement's to state and is fixed by REQ-SESSION-138 alone — once per session, by run startup, after the worktree has been bound and the sandbox verdict taken. This requirement formerly said the facts were recorded "at session start", and that reading is withdrawn rather than reconciled: two of the five are not knowable until the sandbox verdict, and a session created but never run carries no launch audit at all (REQ-SESSION-132, REQ-SESSION-138) while still loading all five state fields at their defaults (REQ-SESSION-015). For snapshots written before these fields existed, the empty/false defaults describe those runs accurately rather than standing in for unknown data, and MUST NOT be backfilled.
- **REQ-SESSION-017** — Requirement attribution fields (`requirement_id`, `unit_id`) MUST default to empty strings for hand-started runs and MUST be set only when requirement-driven execution creates the session. Older snapshots MUST load via defaults without a schema version bump.
- **REQ-SESSION-018** — A session MAY carry a worktree binding record, persisted under the `worktree` key of the resumable state and of the listing metadata. Its field set, the closed `merge_status` vocabulary, and every field default are fixed by REQ-GIT-015; this document holds no copy of any of the three and mints no field of its own. What persistence adds is that the binding is optional and that its own default is null: a session that was never bound to a worktree, and a snapshot written before worktree binding existed, both MUST load with a null binding under the legacy tolerance of REQ-SESSION-015 rather than failing, and a binding that is present MUST be persisted and restored whole, with no field dropped or defaulted on the way through.
- **REQ-SESSION-019** — The session state MUST carry a `checkpoints` list, ordered oldest-first (newest last), where each entry maps an iteration to the git ref and commit that restore the tree as it stood at the end of that iteration (see Data & Formats). This list is the durable checkpoint mapping and MUST survive resume; entries MUST be pruned together with their refs.
- **REQ-SESSION-020** — The state MUST carry an `internal` boolean (default false). Internal sessions (machinery such as worktree-integration runs) MUST be durably recorded but hidden from normal session listings.
- **REQ-SESSION-021** — The state MUST carry a run-type marker distinguishing ordinary user-task runs (the default) from improvement and integration runs. The run type MUST be stamped at session creation and never changed on resume, so the kind of run is recoverable from disk alone and not only from the live process.
- **REQ-SESSION-022** — Global counters MUST be persisted: total tool-call count, global token aggregate, global cost aggregate, compression count, per-agent metrics (tool-call count, per-tool call counts, token usage, cost, compressions, last prompt-token count), and root-context token count. The default cost aggregate MUST read as "source unavailable" and render as "—", so an unpriced run never displays as free.
- **REQ-SESSION-023** — Compression-deduplication ids MUST be persisted keyed by agent name, with the empty string used for anonymous agents, so that compression accounting is exactly-once across resumes.
- **REQ-SESSION-024** — A provider refusal caused by an exhausted quota (HTTP 429, or an equivalent insufficient-quota rejection) MUST leave a durable mark on the session: the refused model is appended to the persisted `exhausted_provider_models` list as `<provider>/<model>` when the provider is known, and as `<model>` alone when it is not. From that moment on, and equally after the session has been closed and reloaded, no automatic model choice and no automatic retry inside that session may select a model whose identifier matches a list entry by exact string equality in the same form the entry uses. The exclusion binds automatic selection and automatic retry only: a model the user chooses explicitly is always usable, and choosing one MUST remove exactly that entry from the list — the user's choice is the evidence that the quota returned. Nothing else clears the list: it is never cleared on a timer, on resume, or by a quota window the product cannot observe, so an untouched session never silently resumes calling a model that refused it.
- **REQ-SESSION-025** — These interactive-wait fields MUST be persisted with the session and MUST come back unchanged when it is reloaded: `pending_questions`, gaining an entry when a question action fires and losing it when that question's tool result arrives (REQ-SESSION-129); `pending_approvals`, a map from request id to the payload of the tool call suspended on interactive approval, an entry disappearing when the request is answered, when it is cancelled, or when it expires under the approval wait of REQ-TOOLS-055, whose budget is the single configuration key REQ-CONFIG-126 registers — this domain names no key, states no default, and defines no timeout of its own; `wait_state`, non-null while and only while the run is suspended on provider quota; `verifier_state`, where null means that no check is running at that moment and never that a check ran and found nothing; and `gate_warning`, a string that survives across individual checks and is cleared only when a completion gate records a decision (the `completion_gate_decision` timeline entry of REQ-SESSION-134). `pending_questions` and `pending_approvals` are the only inputs to the listing record's `awaiting_input` (REQ-SESSION-031).
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 3).** A pending approval or question whose call is cut off by a pause, a stop, a quit or a crash is withdrawn, its entry removed and the withdrawal recorded; it does not come back when the session is reloaded.
- **REQ-SESSION-026** — A mid-session runtime model override (active model key and runtime model configurations) MUST persist across calls and across reloads of the session.
  > **Narrowed by [`PD-MONITOR-006`](../../product/directives/pd-monitor-006.md#pd-monitor-006), 2026-10-06.** A switch of the entry model
  > or reasoning level made from the run header or the inspector is not such an override: it holds for its own run and
  > does not persist into the session's next run. A model chosen during a provider wait (REQ-ORCH-091 (d)) is, and
  > persists as stated.
- **REQ-SESSION-027** — Serialization MUST round-trip loss-free: deserializing a state's own JSON serialization MUST reproduce an equal state.

### 4. Saving State

- **REQ-SESSION-028** — A state save MUST be all-or-nothing. The resumable state, the transcript rows, the edit diffs, the metrics document and the listing record are made durable together, and no reader may ever observe a session whose listing record describes a state that was not saved, or whose parts came from two different saves. The write ordering this requirement formerly fixed existed to keep the listing record from advertising a state not yet recorded; the guarantee it bought is now the atomicity itself, and it holds for readers in any process. The human-readable summary is rebuilt by the same save (REQ-SESSION-006, REQ-SESSION-140) and is the one part written as a file, under the replacement rule of REQ-SESSION-033. No second, whole-state copy of the session is written anywhere.
- **REQ-SESSION-029** — Bulk content MUST be held once and referenced, never copied into the resumable state: the transcript rows, the edit diffs and the configuration snapshot are held as their own records and rehydrated on load (REQ-SESSION-036), and a report artifact is carried in the state as a reference holding only `id`, `agent_name`, `status`, and `path`, its body read from the session's artifact store at that reference. The consequence a caller may rely on is that no part of a session's content exists in two places where the two could disagree, and that a save never rewrites content it did not change.
- **REQ-SESSION-030** — The listing record MUST hold exactly these fields: `session_id`, `created_at`, `updated_at` (ISO-8601 strings), `execution_status`, `schema_version`, `internal`, `worktree` (the binding record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Every attribute a listing shows about the session itself MUST be one of these — making a new attribute list-visible is a change to this field set, not a reader-side extension — and the only other thing a listing may consult is that session's lock record, and only to decide liveness (REQ-SESSION-056, REQ-SESSION-182). Readers MUST tolerate records written by older versions by defaulting absent fields: `checkpoint_count` → 0, `task_title` → the session id, `requirement_id` and `unit_id` → empty string, `awaiting_input` → false.
  > **Narrowed by [`PD-SESSION-001`](../../product/directives/pd-session-001.md#pd-session-001), 2026-10-06 (revision 2 the same day).** The
  > listing record also holds the session's token total, its latest run's duration label (computed from that run's start)
  > and its workspace path, which the sessions card draws as its token label, duration label and detail caption
  > (REQ-MONITOR-171). Every other clause above still governs.
- **REQ-SESSION-031** — `awaiting_input` MUST be true exactly when the state holds any pending approvals or pending questions, so a run that is waiting on human input can be identified from any surface and remains identifiable after a restart.
- **REQ-SESSION-032** — `task_title` MUST be derived from persisted todo state as the last non-blank task name across phases (the newest top-level task), skipping blank names and empty phases; it MUST be empty when there is none.
- **REQ-SESSION-033** — Where this domain replaces a whole file in place — the human-readable summary of REQ-SESSION-140, rewritten by every save, is the one written repeatedly — the replacement MUST be atomic in the sense a reader observes: a concurrent reader opening the file at any moment sees either the previous complete file or the new complete one, and never a partial, empty or unparseable state; a crash during the replacement leaves one of the two. On Windows, a transient access-denied failure of the replacement (antivirus, indexer, or a cloud-sync client holding a handle) MUST be retried, because a foreign handle held for a moment is not a reason to lose a user's file, and any temporary artifact the replacement used MUST always be removed. The ladder is **at most six attempts in total** — the first attempt and at most five retries — with a delay before each retry of **0.05 s, 0.1 s, 0.2 s, 0.4 s and 0.8 s**, so the last attempt begins no more than 1.55 s after the first. *This counting is stated because the earlier wording, "retried up to 5 times with exponential backoff starting at 0.05 s (0.05, 0.1, 0.2, 0.4, 0.8 s)", could be read as five attempts or as six, and two conformant builds would then differ in how much of a transient failure they absorb. It is resolved as six because that is the reading under which every delay the requirement itself lists is used; nothing is narrowed by it, since the alternative reading retries strictly less. Any document that summarises this ladder takes these figures from here.* This rule does not reach the durable store, whose all-or-nothing behaviour is REQ-SESSION-028's, and it is the only replacement ladder this domain states — the export destinations of REQ-SESSION-189 and REQ-SESSION-199 are not this domain's to ladder and cite REQ-TRACE-061 instead, whose figures are that domain's own and are not these.
- **REQ-SESSION-034** — The crash-loss budget MUST be stated in saves rather than in seconds. Because no save is deferred (REQ-SESSION-067), a crash MUST lose only changes for which no save was ever requested: every save that was requested and completed is durable, and every save that was interrupted is absent whole. A partially applied save MUST NOT be observable at any point, and no reader may find a record left half-written by a killed process.

  **What "durable" means, stated in three levels rather than in one word** (accepted amendment 2026-09-06, OQ-12; this requirement is the product's single definition and every other durability claim cites it rather than restating one). The three are different guarantees and MUST NOT be collapsed:
  1. **Process-crash atomicity, for every successful write.** A write this product reports as successful MUST survive the loss of this process at any instant — a kill, a force-quit, a runtime fault — whole and readable. This is the level the paragraph above states and the one every store, every document replacement and every artifact write owes unconditionally. It costs nothing beyond the writes already made and is never traded away.
  2. **Operating-system and power-loss survival, for an acknowledged terminal commit and for a completed backup artifact.** A commit acknowledged at a session's terminal state (REQ-SESSION-094) and a backup artifact reported complete (REQ-SESSION-201) MUST survive loss of the operating system or of power, **subject to the storage device honouring the flushes the product issues** — a condition the product states rather than assumes, because a device that acknowledges a flush it has not performed cannot be detected from software. The stronger commit setting this level requires MUST be preserved and MUST NOT be relaxed as an optimisation; where it is ever reconsidered, the reason MUST be power-loss and operating-system-crash survival, not readability, which the weaker setting already delivers.
  3. **Permitted loss of intermediate updates.** Between those two boundaries, an update made durable at the ordinary commit setting MAY be lost to loss of the operating system or of power, however recently it returned. This is a permitted loss and MUST be stated as one: it is not a defect, it is bounded by how far behind the ordinary setting can be, and level 1 continues to hold over it — what is lost is lost whole, and never half-written.

  **The measurement this definition rests on has not been taken, and saying so is part of the amendment.** No power-loss test has been run on any supported platform, so nothing establishes that a commit acknowledged at level 2 survives a power cut on this storage, and nothing establishes how far behind level 3's loss can actually be. The harness exists and its fault half requires a physical act — a forced power-off, or an operating-system crash — that only the machine's owner can perform. Accepting this wording does not discharge that evidence; the proof is tracked **per supported platform** and stays outstanding until measured. No claim stronger than this text may be made to a user in the meantime.
- **REQ-SESSION-035** — A save MUST stamp `updated_at` with the current UTC time before writing.

### 5. Loading State, Legacy Fallback, and Corruption

- **REQ-SESSION-036** — Loading MUST read the resumable state and then rehydrate the three bulk parts held beside it (REQ-SESSION-029): the transcript rows, the edit diffs, and the configuration snapshot, the last taken from the launch audit of REQ-SESSION-138. Each of the three is optional. A part that is absent, and a part that is present but cannot be decoded or does not carry what it should, MUST be treated identically: the corresponding field loads empty, the load succeeds, and a warning is logged and an issue recorded (REQ-SESSION-135) naming the part and the reason. Only the resumable state itself failing to decode fails a load (REQ-SESSION-041) — these three hold recoverable bulk data whose loss degrades a reopened session rather than invalidating it.
- **REQ-SESSION-037** — The stored resumable state is the only resumable state, and there is no alternative whole-state record to fall back to. Where the workspace's store holds no state under a session id, loading MUST fail with a not-found error conveying the session id as supplied and that no session state is stored under it in that workspace; the wording is left to the implementation. Because the store is machine-local (REQ-SESSION-198), a workspace opened on a machine that has not run it before holds no sessions there, which is an ordinary empty state rather than a failure (REQ-SESSION-043).
- **REQ-SESSION-038** — A `schema_version` greater than the supported version MUST be refused with an error conveying the version found and the version supported — an incompatible snapshot is refused, never lossily restored. The wording is left to the implementation.
- **REQ-SESSION-039** — *Withdrawn.* There is no legacy layout to migrate forward from; every session is recorded the one way this product records a session, from its first save.
- **REQ-SESSION-040** — Two read modes MUST exist: a full open (used to run or resume a session) that applies post-deserialization repairs (see REQ-SESSION-170), and a read-only snapshot read (used by display-only consumers) that performs the same read with no repairs and no filesystem writes.
- **REQ-SESSION-041** — Corruption tolerance MUST live at the consumer: resumable state that cannot be decoded propagates the error from the loader, and every caller MUST catch it and degrade — the desktop session browser reports the session as unreadable, conveying the session id and the parse detail and leaving every other session usable (REQ-SESSION-182); stale repair treats it as "nothing to do"; checkpoint-ref cleanup skips the session; and listing paths skip the entry. The wording of the report is left to the implementation.

### 6. Session Listing

- **REQ-SESSION-042** — Listing MUST be taken from the workspace's stored listing records, silently skipping any record that cannot be decoded or whose `updated_at` is absent or unparseable. Surviving entries are returned as those records hold them, with reader-side defaults applied per REQ-SESSION-030, filtered per REQ-SESSION-044, and ordered by `updated_at` descending so the most recently updated session comes first. Building the list MUST read nothing but those listing records — not a session's state, not its transcript, not its history — so the cost of listing grows with the number of sessions and with nothing else; a presentation layer that marks stale sessions additionally reads that session's lock record and nothing else (REQ-SESSION-056, REQ-SESSION-182).
- **REQ-SESSION-043** — A workspace whose store holds no sessions MUST produce an empty list rather than an error, and so MUST a workspace for which this machine holds no store at all. A workspace in which no run has yet taken place *here* is an ordinary state, and under REQ-SESSION-198 that includes a workspace every one of whose runs happened on another machine. Both of those are the absence of a store, and the empty answer is owed where nothing is kept for the workspace at all. A workspace for which this machine keeps a place for the store while the store is not in it is neither of them and is REQ-SESSION-202's, which resolves that case into a store that could not be opened: it MUST NOT produce an empty list, because an empty list asserts that this workspace has no sessions here when what is true is that the product cannot tell.
- **REQ-SESSION-044** — Default listing MUST exclude sessions whose metadata `internal` flag is truthy; an explicit include-internal option MUST return everything (used by recovery and machinery).
- **REQ-SESSION-045** — One corrupt session MUST never cost the listing the others: every other session still appears.

### 7. Session Locking

- **REQ-SESSION-046** — The session lock MUST be a record held in the same store as the session it locks, claimed by an operation that either succeeds or reports the existing holder, so that two claims on one session can never both succeed and a claim can never partially take effect. It carries `pid` (integer), `host` (a stable identifier of the machine whose process holds the lock) and `acquired_at` (a UTC ISO timestamp). These three names and their value types are a machine-readable contract and are the same ones REQ-GIT-020 fixes. **What supplies `host` is fixed here, because "stable" was stated and left unsourced and the obvious source is not stable.** It MUST be an identifier the product mints once for this machine and keeps in the machine-local location the store lives in (REQ-STARTUP-145), and it MUST NOT be the machine's operating-system name or any other value a user, an administrator, or the machine's own configuration can change. Renaming a machine MUST NOT change it. The reason is that every requirement that reads this field treats a value naming another machine as evidence of a condition that should not arise — REQ-SESSION-056 makes such a lock live by construction, REQ-SESSION-047 never reaps it, and REQ-SESSION-183's per-session confirmed release is the only thing that clears it — so a field that changes when a machine is renamed converts an ordinary administrative act into every one of this workspace's sessions reporting held by a machine that does not exist, each needing to be cleared by hand. The identifier is minted where a store is, so a workspace whose store this machine has never held has no identifier question to answer.
- **REQ-SESSION-047** — Lock acquisition MUST return success/failure rather than raising. When the session is already locked, at most one stale-reap attempt MUST be made (two claims total), and the reap MUST happen only when all of the following hold: the lock record carries the three fields of REQ-SESSION-046 with their stated types, its `host` names this machine, and its `pid` probes dead here. In that case the stale lock is released and the claim retried once. In every other case — the record is unreadable or does not carry those fields, `host` is absent or names another machine, `pid` is absent or not an integer, `pid` is ≤ 0, or the pid probes alive — the lock MUST be respected, acquisition MUST fail, and the lock record MUST be left exactly as it was found. There is no waiting, no bounded retry loop, and no second reap: a lock another party keeps re-claiming can never make acquisition spin. That only one instance of the application runs at a time (REQ-STARTUP-161) is not a reason to weaken any of this. The lock this path exists to reap is the one a *previous* instance left behind when it crashed or was force-quit — the one case in which no process can be asked to release it — and reaping it is what turns such a session back into an ordinary persisted session that opens normally (REQ-SESSION-159).
- **REQ-SESSION-048** — Creating a session MUST persist the initial state first, then acquire the lock; an acquisition failure at creation raises an error conveying the session id, that nothing was started, and what is actually wrong — not merely that a lock was contended. This requirement is the single statement of what such a refusal must convey, and the two cases MUST be distinguished. Where the lock names **this** machine, the refusal conveys that another run in this application holds the session, naming the pid the lock records; the remedy is that run finishing or being stopped. Where the lock names **another** machine, the refusal conveys that the session is held by a different machine, names that machine and when the lock was acquired, and states that this instance cannot establish whether that run is still going — and, because the store is machine-local (REQ-SESSION-198), that such a lock means this workspace's session store is reachable from more than one machine, which is the condition the user must resolve rather than a lock to be cleared. Explicit release (REQ-SESSION-183) is named as the only remedy in that second case and is never taken automatically. **A third case exists and this requirement covers it, because the two above are keyed on what the lock says and a lock may say nothing.** Where the lock record is present but cannot be read, or does not carry the fields of REQ-SESSION-046, the refusal MUST convey that a lock is present and could not be read, MUST NOT name a machine or a pid it does not have, and MUST NOT be reported as either of the cases above — the product does not know which of them it is, and saying so is the honest report. Explicit release (REQ-SESSION-183) is the remedy here as in the second case, and for the same reason: the session counts as live (REQ-SESSION-056) and is never reaped (REQ-SESSION-047). This case is not an unlikely one — REQ-SESSION-056 and REQ-SESSION-183 both name it explicitly — and the enumeration above would otherwise leave the single statement of this refusal with nothing to say about a condition its own neighbours describe. A freshly created session is left lock-held by its creator. The wording is left to the implementation.
- **REQ-SESSION-049** — Releasing the lock MUST first tear down the session-scoped shared services holding long-lived subprocesses (MCP servers, language servers) and then release the lock; releasing a lock that is not held is a no-op.
- **REQ-SESSION-050** — A session MUST be owned by at most one run at any moment, and holding that session's lock (REQ-SESSION-046) is what owning it consists of. Because only one instance of the application runs (REQ-STARTUP-161), a second claim on a live session can arise in exactly two ways, and the lock refuses both: a further run started inside this same instance, which is refused outright (REQ-SESSION-083), and a lock left behind by an instance that is gone, which is reaped (REQ-SESSION-047) or explicitly released (REQ-SESSION-183) before ownership passes. Several locked background sessions MAY nonetheless coexist within a single workspace: the limit is one run per session, not one run per workspace.
