# Session Persistence, Resume, and Background Sessions — 18. Durable Per-Session Event History

Part 6 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-143 – REQ-SESSION-161.

### 18. Durable Per-Session Event History

- **REQ-SESSION-143** — The durable event history is part of the session's record and holds every event the run published, in the order it was emitted. A stored event MUST reproduce every field of what the live stream emitted for that event, adding nothing and dropping nothing, so that reading the stored history and subscribing to a running session are interchangeable inputs to one consumer. Getting that history out of the product is the export's obligation and not the write path's: REQ-SESSION-189 writes it as one event per line in the envelope the event schema fixes, and that is where REQ-EVENTS-166's guarantee — every field readable by a stock parser on a machine with none of this product's code — is discharged. The record of what a trim dropped is REQ-SESSION-144's and belongs to the same session record.
- **REQ-SESSION-144** — The event history is capped, and neither the cap nor the trim is this domain's to fix. The configuration key, its default, its value space, the rejection of a negative value, and the meaning of a configured `0` are REQ-CONFIG-473's. How a trim is performed — the headroom permitted above the cap before a trim runs, which events a trim keeps, that it counts from the history's current contents rather than from a carried-over figure, that it takes effect in one step with no intermediate state a reader can observe, and that a trim which did not complete leaves the previous contents in force, records a warning, and is not reflected in the record of what was dropped — is REQ-EVENTS-091's. This domain holds no copy of the cap, of the headroom figure, or of the trim rule, and states no second reading of a cap of `0`. What it adds is where the record of a trim lives and what a reader may conclude from it: the truncation record belongs to the session's own record, it exists only once a trim has dropped events, and its absence MUST read as no events having been dropped rather than as an unknown figure — which is what lets `truncated` and `dropped_events` be reported as `false` and `0` for an intact history (REQ-SESSION-153) and lets a listing state a session's dropped count (REQ-SESSION-188).
- **REQ-SESSION-145** — The history writer MUST never **raise** into a run: each entry point turns exceptions into logged warnings and signals the outcome through its return value, so no caller of the writer ever has to catch. **What the run then does with that return value is not this requirement's** (amended 2026-09-06 under OQ-42): a *serialization* failure drops that one event with a warning and lets later events land, and a *durable recording* failure is REQ-EVENTS-088's — admission stops for the affected runs and controlled cancellation begins. *The clause "an event that cannot be recorded is discarded with a warning rather than raised" is withdrawn as a statement about durable failures and survives only for the serialization case REQ-EVENTS-088 names; read whole, it said a run goes on recording nothing, which REQ-EVENTS-088 forbids.* Not raising and not stopping are different properties, and this requirement owns only the first. The line discipline the exported form depends on — that no stored event's serialization embeds a carriage return or line feed, so one event is always one line — is REQ-EVENTS-089's and is discharged where the lines are produced, by the export of REQ-SESSION-189.
- **REQ-SESSION-146** — Event-history bindings are per session id: a new registration replaces the previous one, lookup never falls through to a different session — history from one run must never be written into another run's record — and storing without a binding is a silent no-op.
- **REQ-SESSION-147** — Persistence MUST happen before forwarding to the caller's event consumer (a tee), so an event that a failing consumer never receives is nevertheless durably recorded. Detaching the history genuinely stops persistence even for a sink reference that escaped.
- **REQ-SESSION-148** — Reading a stored history MUST be streaming — never materializing the whole history at once, so a history of any size is readable in bounded memory — read-only, and forward-compatible: an event whose type discriminator is unknown yields an opaque event marked unknown with its payload intact — never dropped, never raising (strict decoding is an explicit opt-in). An entry that cannot be decoded MUST be skipped with the read-damage warning of REQ-EVENTS-106, whose fields this document holds no copy of, its excerpt cut to 200 characters, and a reader MUST NOT rewrite or repair the history. A missing history reads as an empty session. An entry with no event-type discriminator is malformed (skipped), not "unknown". Which types count as known MUST follow the event schema itself, never a separately maintained list.
- **REQ-SESSION-149** — *Withdrawn.* The resumable byte-offset tail, its restart flag and the discard-and-re-seed of derived state existed only so that a surface could follow a session executing in a process this application does not own, and no such session exists (REQ-SESSION-159). Nothing that reads a *stored* history is withdrawn with it: streaming, read-only, forward-compatible reading stays with REQ-SESSION-148 over the reader-warning rule of REQ-EVENTS-106, summarizing a history by decoding only its first and last line stays with REQ-SESSION-151 and REQ-EVENTS-126, replay stays with REQ-SESSION-150, and export stays with REQ-SESSION-189. A reattach reads the session's persisted state and needs no offset, no restart flag and no re-seed (REQ-SESSION-196).
- **REQ-SESSION-150** — Replay filtering MUST support event types, iterations, and inclusive since/until time bounds — all optional, combined with AND; timezone-naive stamps normalize to UTC; an empty result is a valid answer. As the stream is read, each event's owning iteration is determined from the enclosing `iteration.start` and `iteration.end` boundaries; events outside every iteration match no iteration filter, and stamp-less lines match no time filter. Replay is reading, never re-execution, and never modifies the history.
- **REQ-SESSION-151** — Stored-session discovery MUST: treat an *empty* history as present (a run that emitted no events is still a session one can ask about); summarize by counting the recorded events and decoding only the first and the last (on a damaged history the count may be off by one, which is acceptable for a chooser; exact figures come from export); report an unreadable history as containing zero events, with a warning, instead of aborting the listing; sort newest first by last-then-first timestamp with the session id as tiebreak, sorting histories with no usable timestamps last. A session id that did not come from the session store itself — one typed by a user, pasted in, or read out of a document — MUST be treated as untrusted: it is used only as a lookup key against this workspace's own sessions, MUST NOT be used to build a path or to name anything outside them, and where it matches no session the answer is no match rather than an error.
- **REQ-SESSION-152** — *Withdrawn.* The `events` command has no surface to appear on; browsing and replaying a stored history is carried by REQ-SESSION-188 and exporting one by REQ-SESSION-189.
- **REQ-SESSION-153** — An exported trajectory document MUST carry `trajectory_version: 1`; the run's identity (session id, task, and the workspace exactly as the run reported it — never a path belonging to the exporting machine); the permission mode; started and ended timestamps as ISO-8601 UTC; the status; the stop reason; the duration in seconds; `truncated` and `dropped_events`, taken from the truncation record and reading as `false` and `0` when there is none (REQ-SESSION-144); a summary recomputed from the exported events alone and from no other source — event, unknown-event and warning counts; `runs`, the number of `session.start` boundaries in the document, which is where a single-run consumer must split it; iterations; tool calls and tool failures; permission decisions and denials; verifier runs and failures; child agents; errors and fatal errors; per-type event counts; tokens; cost — and the events themselves as the raw stored payloads, with redaction inherited from the wire schema rather than applied again by the exporter, and unknown event types preserved intact. **Two scopes travel in one document and MUST NOT be read as one** (REQ-EVENTS-138, accepted amendment 2026-09-06, A6): the identity and outcome fields — task, workspace, permission mode, status, stop reason, started and ended timestamps, duration — describe the **latest run segment**, the events from the last retained `session.start` onward, while every count in the summary describes the **whole exported history**, which is why `runs` is carried at all and why it is the figure a single-run consumer splits on. This requirement states no derivation of its own for those fields; REQ-EVENTS-138 owns it, including what an unfinished segment exports and the prohibition on borrowing an outcome across a retained start boundary.
- **REQ-SESSION-188** — The application MUST let a user inspect a stored event history without leaving it. For the workspace's sessions it MUST show, per session with a stored history, the session id, the event count, the first and last event timestamps, and, for a capped history, that events were dropped and how many (REQ-SESSION-144); a session whose history is empty is still listed (REQ-SESSION-151), a history that cannot be read is listed as holding zero events with a warning, and a workspace with no stored history states that rather than showing an empty area with no explanation. Opening one MUST replay it read-only (REQ-SESSION-150) with filters on event type, iteration, and inclusive since/until bounds, combined with AND, each optional, an empty result being a valid answer that MUST be stated as such. Each replayed event MUST show its timestamp, its type, whether the type was unknown to this version, and a compact rendering of its payload cut to 110 characters per REQ-SESSION-194; the stored event MUST be viewable in full, exactly as it was recorded, for any event. Warnings about skipped or undecodable lines MUST be shown alongside the events, never in place of them. A time bound the user enters that is not ISO-8601 MUST be refused before the read, with a message conveying which bound and what was entered; wording is left to the implementation. Replay is reading and MUST never modify the history.
- **REQ-SESSION-189** — The application MUST let a user export one or several sessions as trajectory documents (REQ-SESSION-153). The destination MUST be a file the user chooses through the platform's save dialog — there is no implicit destination and nothing is written until a destination is chosen. Exporting exactly one session MUST write one trajectory document. Exporting several MUST write one batch document holding those trajectory documents in the order the user selected them; the wrapper's key names, its closed inventory and the count it carries are REQ-EVENTS-144's, and this requirement holds no copy of them. *This requirement formerly fixed the wrapper itself, as `{"trajectory_version": 1, "sessions": [<document>, ...]}`, and declared that it carried no field of its own beyond those two key names. That inventory is withdrawn: REQ-EVENTS-144 requires the wrapper to carry the count of documents it holds, and a wrapper cannot both carry that count and carry nothing beyond two keys — the two statements could not both be satisfied by one build. What the withdrawn clause protected is not lost, because REQ-EVENTS-144's inventory is equally closed and equally exhaustive, so a consumer that understands one document still understands a batch. No conformance test may look for a `sessions` key on a batch document.* Two conditions MUST be reported as warnings that do not stop the export: a history holding more than one `session.start` boundary, conveying that the session was resumed, how many runs the document covers, and that its identity is the most recent one; and a capped history, conveying how many events were dropped and that the export is therefore not the complete run. The exported document MUST also be obtainable as the plain event stream, for a consumer that wants the stream rather than the summary: one event per line, each line the envelope the event schema fixes, carrying every field the live stream emitted (REQ-SESSION-143) and readable by a stock JSON parser on a machine with none of this product's code present (REQ-EVENTS-166). That line-delimited form is where the stock-parser guarantee for the event history is discharged, since the history is no longer kept as a file, and it MUST be produced for any session the application can list, whether or not that session is live. How the chosen destination is written is not this requirement's: what an export write owes its destination is REQ-EVENTS-145's, including that the document becomes visible there in one step, and where that destination already holds a file the replacement MUST take the bounded retry ladder of REQ-TRACE-061. Both are cited and neither is restated, for the reason REQ-SESSION-199 states for the same destination — a file the user names may sit on storage this product neither chose nor can characterise.
- **REQ-SESSION-193** — The key names of the three machine-readable documents this domain publishes are fixed, because a consumer cannot be written against a list of figures. Every key is lower snake case, and the inventory given for each document is exhaustive — a reader may rely on no other key being present, and adding one is a change to that requirement. The `session.start` payload (REQ-SESSION-090) carries `session_id` (string), `task` (string), `workspace_root` (string path, as the run reports it), `persona` (string), `permission_mode` (string, as configured at launch), `sandbox` (object `{"enabled": boolean, "backend": string}` describing the verdict in force), and `max_iterations` (integer or null). The metrics document (REQ-SESSION-139) and the trajectory document (REQ-SESSION-153) name each figure listed in their requirement by the same words that requirement uses, joined by underscores, with the trajectory document's top level being exactly `trajectory_version`, `session_id`, `task`, `workspace`, `permission_mode`, `started_at`, `ended_at`, `status`, `stop_reason`, `duration_seconds`, `truncated`, `dropped_events`, `summary`, and `events`. Key order is not significant anywhere. The batch wrapper that carries several trajectory documents together (REQ-SESSION-189) is **not** one of these three documents and its key inventory is not fixed here: it is REQ-EVENTS-144's, equally closed and equally exhaustive, and this requirement holds no copy of it.

### 19. Reattach Surfaces and Projections

- **REQ-SESSION-154** — The desktop session list MUST project listing metadata into rows: label = task title, else the launcher-known name, else the session id (a just-launched run keeps its prompt-derived label until metadata carries a title, and a refresh must not strip launcher-known requirement attribution); status from `execution_status` defaulting to idle; branch from the metadata worktree record, else "—"; a relative-time duration label; the worktree path as detail; and `awaiting_input` from metadata (absent → false). The status MUST be rendered from the stored value itself, as text and never by colour alone (REQ-SHELL-149), so every value of REQ-SESSION-073 is distinguishable from every other: a session repaired to `interrupted` reads as interrupted and is never shown as though it had never run, and a value from outside the closed vocabulary is shown verbatim. A stale session (REQ-SESSION-057) MUST additionally carry the stale marking of REQ-SESSION-182 beside that status.
- **REQ-SESSION-155** — `awaiting_input` MUST render as a "waiting for you" tag on session rows and "Waiting for your answer" status text, and MUST drive the requirement board's "Answer" affordance for background runs blocked on approvals or questions — persisted metadata is what lets a background run say it is blocked on a person across every surface and across restarts.
- **REQ-SESSION-156** — Desktop whole-state reads MUST use the read-only snapshot read of REQ-SESSION-040 — no repairs and no writes, verifiable by observing that nothing the session owns is changed by the read — and MUST project the persisted state into display models covering the run summary, transcript, agents, artifacts, todos, key metrics, pending questions and approvals (copied, so that display work can never mutate what was read), and the verifier summary. A `verifier_state` that cannot be parsed MUST resolve to idle rather than failing the read, and a persisted `gate_warning` MUST still be reported when the verifier is idle. The result MUST report the elapsed time of the state read and the elapsed time of the projection as separate values. Which parts of a view a user is entitled to see restored from this projection, rather than recomputed or lost, are fixed by REQ-SESSION-196.
- **REQ-SESSION-157** — Pending questions and approvals MUST render as transcript trailer rows — derived from what is pending now and always placed after every recorded row, re-appended by both whole-state and delta paths: a question stepper row of the form `<N> step(s) — <first title>` and one row per approval of the form `Approval needed — <command or tool>`.
- **REQ-SESSION-158** — A desktop board-launched run (a requirement unit) MUST: adopt the worktree the flow provisioned, given by explicit path, refusing a path that is not part of the repository, and record it as not owned by the session so the session never deletes a tree the flow owns (REQ-SESSION-084); make the session id available to the caller as soon as the session exists, without waiting for the run to end; open no window and take no window or keyboard focus, so that several launches in succession leave the user's foreground application unchanged; return an empty session id rather than raising when the launch is refused; and have the caller's completion listener registered before the launch call returns, so that a run finishing immediately still delivers its completion notification. The empty session id is the return value only and is never the whole report: a refused launch MUST also be reported to the user through the notification surface of domain 19, conveying which requirement unit could not be started and why, and the unit's row on the requirement board MUST show it as not started with that reason attached — a refusal that produced no session must never be indistinguishable from a unit nobody has run yet.
- **REQ-SESSION-182** — The application MUST offer one place from which the workspace's sessions are managed, built on the listing of REQ-SESSION-042 and the metadata of REQ-SESSION-030 and reached through the session browser of REQ-SHELL-126. It MUST show, per non-internal session, the row projection of REQ-SESSION-154, and MUST mark a stale session (REQ-SESSION-057) as stale beside its stored status, as text and not by colour alone (REQ-SHELL-149), so the cause of a refused restore or a blocked integration is visible where the session is. It MUST offer these actions, all in the action vocabulary of REQ-SHELL-048: open the session (REQ-SESSION-118); repair one stale session; repair every stale session in the workspace; delete a session (REQ-SESSION-166), behind a confirmation that states the deletion is permanent; the log, files and export actions of REQ-SESSION-191; and the whole-store backup and restore of REQ-SESSION-201, which are workspace-scoped rather than per-session. The backup disclosure of REQ-SESSION-200 MUST be reachable from here; nothing stops the product stating it elsewhere as well, but this is the surface it may not be missing from. Repair MUST perform exactly the explicit repair of REQ-SESSION-060 and MUST report, per session repaired, the session id, the status it was stuck in, the new status `interrupted`, and the reason it counted as stale (REQ-SESSION-059); when nothing was stale it MUST say so rather than reporting nothing at all. A session whose stored state cannot be parsed MUST be listed and reported as unreadable (REQ-SESSION-041) while every other session stays usable. Wording throughout is left to the implementation.
- **REQ-SESSION-196** — Reattaching to a session — one that has been running in the background, one whose window was closed, or one being opened again after a restart — MUST restore from persisted state, and not recompute or discard, all of: every transcript row the session recorded, at its own index and in order, with statuses settled per REQ-SESSION-078 and REQ-SESSION-079 and archived pages reachable per REQ-SESSION-192; the todo state; the child-agent tree; the metric aggregates (REQ-SESSION-169); the report artifacts; the pending questions and approvals, as trailer rows per REQ-SESSION-157; the verifier summary and any `gate_warning`; the worktree binding and its branch; the checkpoint list; and the session-scoped model override. Four things are explicitly not restored, because they describe a moment rather than the session: streaming animation and partially streamed text, which come back as the settled rows they became; live terminal buffers, so a terminal tool row shows its recorded output rather than a live screen until a stream is re-attached (REQ-SHELL-110); elapsed-time counters for activity that is no longer running; and scroll position, unless a desktop preference (REQ-SHELL-006) says otherwise. Everything restored MUST come from the read-only snapshot read of REQ-SESSION-040. This requirement formerly completed that snapshot from the session's own stored `transcript.row` events, for any row a debounced save had not yet written; no save is deferred any more (REQ-SESSION-067), so a row the session recorded is a row its persisted state already holds and there is nothing left to complete. The entitlement is unchanged and is now met by the snapshot alone. What must not be lost with the mechanism is the rule it protected: there MUST NOT be a second, differently derived path — a row the session recorded is a row a reattach restores whether or not any window was watching (REQ-SESSION-034), and a surface that then goes on to follow a still-live session receives exactly the rows that session records (REQ-SESSION-120, REQ-SESSION-159) rather than deriving them a second way.

### 20. Live Sessions and Sessions at Rest

- **REQ-SESSION-159** — A session is in exactly one of two conditions, and this requirement is the product's single definition of them; a document that needs to name a session's condition cites this identifier rather than restating it. Either the session is **live** — the one running instance of the application (REQ-STARTUP-161) owns it, holds its lock (REQ-SESSION-050) and is executing it — or it is **not running**, and exists only as its persisted record. REQ-SESSION-056's `live` is the record-observable approximation of the first condition and is deliberately not identical to it, because it resolves every uncertainty toward running (REQ-SESSION-051, REQ-SESSION-172): a lock left behind by an instance that crashed, and a lock this machine cannot prove unheld, both report live there while being, respectively, a session at rest and a session this instance may not touch. Where the two differ, REQ-SESSION-056 governs every decision taken from the record — reaping, stale detection, listing, the integration precondition — and this requirement governs what a surface may do with the session. A live session reaches every surface of that instance through the updates the application publishes for it as the run proceeds (REQ-SESSION-071, REQ-SESSION-161): which window started the run, whether any window is still watching it, and whether it was detached into the background (REQ-SESSION-190) make no difference to what a surface receives, because all of those are the same instance. A session that is not running is opened from its persisted record and may be continued (REQ-SESSION-196, REQ-SESSION-112). There is no third condition in which a session executes somewhere this application can only watch, and the filesystem is never a channel between a run and a surface: no surface follows a session by reading its record or its files, and no file this product writes into a session's own place on disk is a signal to another process (REQ-SESSION-002). A session left behind by a crash or a force-quit is not a third condition either — it is a not-running session whose record still asserts a run, settled by the lock reap of REQ-SESSION-047 and the explicit repair of REQ-SESSION-060, after which it opens like any other persisted session. The only session this instance can neither view nor continue is one whose lock it cannot prove unheld — a lock naming another machine, or one that cannot be read (REQ-SESSION-056); such a session MUST be refused rather than watched (REQ-SESSION-083), with the explicit release of REQ-SESSION-183 as the remedy, so it is unreachable only while something else may still be running it and never permanently. This requirement formerly held that when a session runs in a process other than the one displaying it — a second window of this application, another instance opened on the same workspace, or a run detached into the background — the only channel to it is the filesystem, and required the live transcript to be followed by tailing the stored event history. The first and third of those cases are inside the one instance and are served by published updates; the second does not arise, because a second launch of the application surfaces the running instance rather than starting a rival process. The reason that requirement gave for sharing one derivation — that following a session and reopening it afterwards must produce identical transcripts — is **not** withdrawn along with the mechanism: it now holds by construction, because only one derivation of a transcript remains (REQ-SESSION-196), so the equality REQ-MONITOR-242 requires can no longer be broken by two paths disagreeing. The durable event history itself is untouched in substance: it remains the record of every event the run published, field for field (REQ-SESSION-143), what replay reads (REQ-SESSION-150) and what a user can take away whole (REQ-SESSION-189). What is withdrawn is following it live, not writing it or reading it.
- **REQ-SESSION-160** — *Withdrawn.* Reproducing the run's row numbering from a tail of the event history was the follower's half of a derivation no surface performs any more (REQ-SESSION-159), and everything in it that outlives the tail is owned elsewhere. That transcript row indices are assigned contiguously from `0` and that a consumer replaces the row at an index rather than appending after it is REQ-EVENTS-052's; that a row keeps the index it was given when older pages are evicted is REQ-SESSION-192's. The placeholder row and the discard-and-re-seed rule are withdrawn outright: a surface that detects it has missed an update reconciles from a whole-session read (REQ-SESSION-161), which recovers the rows themselves rather than standing in for them with a placeholder, and leaves the displayed rows in place until the replacement set is ready.
- **REQ-SESSION-161** — Everything outside the transcript — todo lists, the agent tree, token counts — MUST come from a whole-session read of the session's state rather than from transcript increments, and a whole-session read is also what reconciles anything an increment did not deliver, including an update a surface has detected that it missed. For a live session that read is the whole-session update the application publishes on request; for a session that is not running it is the read-only snapshot read of REQ-SESSION-040. Because that published update deliberately omits the transcript (REQ-MONITOR-216), reconciling a *transcript* increment a surface missed MUST also re-deliver the transcript: for a live session the run republishes it from the lowest index it still holds, which the increment channel already expresses and which a cleared transcript already uses (REQ-MONITOR-214, REQ-MONITOR-215, REQ-MONITOR-229); for a session that is not running it comes from the projection of the snapshot read (REQ-SESSION-156). A reconciliation that left the transcript alone would not satisfy the requirement that what a surface shows after the read equals the persisted record (REQ-MONITOR-226). Neither read is ever performed on a timer (REQ-SESSION-071): a whole-session read happens when a surface opens a session and when it has something to reconcile, and at no other time. An increment whose first-touched row index falls before the oldest row the consumer still holds from its most recent whole-session read MUST be declined; declining costs exactly one further whole-session read, and the rows on display MUST be unchanged by the increment that was declined.
