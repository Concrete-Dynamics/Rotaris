# Settings and Configuration — Settings screen: security policy controls and confirmations

Part 8 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-298 – REQ-CONFIG-341.

### Settings screen: security policy controls and confirmations

- **REQ-CONFIG-298** — Confinement and egress are presented in a single card in which every control carries a hint visible on screen — not text hidden in a tooltip — stating what that control does. For a workspace that has configured none of the six values, the card opens on the shipped defaults: confinement `off`, in-confinement network access off, egress `ask`, and all three lists empty.
- **REQ-CONFIG-299** — The card's introduction must state that these are **workspace defaults applied to every new session**, not retroactive changes to running sessions.
- **REQ-CONFIG-300** — Control order within the card: confinement mode selector; confinement-mode hint; a computed availability verdict (selectable text); an in-confinement network toggle (default off); writable-roots editor (placeholder illustrating an absolute path); egress policy selector; egress hint; allowed-hosts editor (placeholder illustrating both an exact host and a wildcard); denied-hosts editor (placeholder illustrating a metadata host), whose hint additionally states that an entry there wins over the allowed list.
- **REQ-CONFIG-301** — The confinement-mode selector offers exactly the modes REQ-SANDBOX-048 fixes and the egress selector exactly the dispositions REQ-SANDBOX-001 fixes; neither vocabulary is defined here, and a control offers no value outside the one it is bound to. What this requirement adds is the order in which each control presents them: the confinement selector in the order `off`, `workspace-write`, `read-only`, and the egress selector in the order `allow`, `ask`, `deny`.
- **REQ-CONFIG-302** — The hint texts are the user-visible statement of the policy. Every one of the following must be stated in substance in the card: (a) with confinement `off` a terminal command runs straight on the machine; (b) `workspace-write` permits writes inside the session's workspace and inside the listed writable roots and nowhere else; (c) `read-only` permits no write at all; (d) confinement needs an operating-system backend, and a run asking for confinement on a host that has none fails rather than running unconfined; (e) a writable root is an absolute path kept writable in addition to the workspace, and a relative path is refused; (f) a host in neither egress list is treated according to the selected disposition; (g) an entry in the denied list wins over the allowed list; (h) a host that cannot be read is denied; (i) the only accepted wildcard is a single leading `*.`, which matches subdomains but not the bare name, so covering the bare name takes a second entry; and (j) the in-confinement network toggle applies only while confinement is in force, the egress policy governing the agent's own fetch tool either way.
- **REQ-CONFIG-303** — The two rules users most often get backwards must be reachable by assistive technology, not only visually: the egress selector's accessible description states the denied-wins rule, and the allowed-hosts editor's accessible description states that a wildcard does not cover the bare domain.
- **REQ-CONFIG-304** — A writable-root entry is validated at the control: trimmed; an empty value is refused asking for a path; a value that is absolute in **either** POSIX or Windows spelling is accepted (so a shared workspace configuration stays portable across machines); anything else is refused with a message naming the value, stating it is not absolute, and showing one example of each spelling. The accepted value is stored trimmed but otherwise unchanged — no case folding, no separator rewriting.
- **REQ-CONFIG-305** — A host-pattern entry is validated at the control: trimmed, lowercased, trailing dot removed. Empty is refused with a message showing both an exact-host and a wildcard example. An entry containing `*` is checked against the shared host-matching rules, which accept no wildcard shape other than one leading `*.`; the remainder after the wildcard must be non-empty or the entry is refused naming the value. Accepted wildcard patterns are stored **as typed after lowercasing**; accepted exact hosts are stored **normalized**. An entry that normalizes to nothing is refused as unreadable.
- **REQ-CONFIG-306** — The host validator used by the settings control is the same one the runtime fetch check uses, so what the settings screen accepts and what the runtime enforces can never diverge.
- **REQ-CONFIG-307** — Exactly three transitions in this card demand confirmation, and all three are **widening** transitions: selecting confinement mode `off`, selecting egress disposition `allow`, and switching in-confinement network access on. Each is a warning prompt with Yes and Cancel and **Cancel as the default**. The confinement prompt must state that terminal commands will run directly on the host with no path limit beyond the permission mode; the egress prompt must state that agents will open any host not on the denied list without asking, and that denied hosts still win; the in-confinement network prompt must state that commands running inside confinement will be able to reach the network, and that the egress policy still governs the agent's own fetch tool either way.
- **REQ-CONFIG-308** — Anything other than an affirmative answer restores the control from the stored value and returns **without writing**. Cancelling therefore leaves both the stored disposition and the visible control at their previous values.
- **REQ-CONFIG-309** — Every one of these handlers returns immediately when the incoming value is empty or already equals the stored value, so a programmatic repopulation can never raise a confirmation prompt.
- **REQ-CONFIG-310** — Moving to `workspace-write`, `read-only`, `ask` or `deny`, and switching in-confinement network access **off**, are narrowing transitions and are stored without any confirmation. Switching in-confinement network access **on** confirms first, like the other two widening transitions (REQ-CONFIG-307, REQ-CONFIG-460); there is no widening change in this card that is stored unconfirmed.
- **REQ-CONFIG-311** — Repopulating this card from stored values must not emit changes and must not mark the form dirty; the card is repopulated only when at least one of its six values actually changed, so a repeated status refresh does not re-probe the operating system for confinement availability.
- **REQ-CONFIG-312** — The six configuration keys this card writes are exactly `sandbox_mode`, `sandbox_allow_network`, `network_egress_policy` (scalars) and `sandbox_writable_roots`, `network_allowed_hosts`, `network_denied_hosts` (lists). Round trip is a contract: setting mode `workspace-write`, writable root `/srv/build-cache`, in-confinement network on, disposition `deny`, allowed host `*.example.com`, denied host `metadata.example.com` and saving must produce exactly those six values in the workspace configuration's runtime section, and a second settings view opened over the same workspace must show all six back on their controls — lists as **ordered arrays**, the wildcard **verbatim**, the booleans as real booleans.

### Settings screen: confinement availability verdict

- **REQ-CONFIG-313** — The availability verdict is computed for the mode **currently being edited**, not the last saved one, so it never describes a mode the user is not looking at.
- **REQ-CONFIG-314** — The availability verdict has exactly four outcomes and exactly one is shown. (1) The mode being edited is outside the vocabulary REQ-SANDBOX-048 fixes (not restated here): the sentence names the value and tells the user to pick one from the list. (2) Confinement is in force: the sentence names the backend and states that it encloses every terminal command run in this workspace. (3) A backend exists but the mode being edited is `off`: the sentence names the backend and states that confinement is available but is not applied because the mode is off. (4) No backend exists: the sentence says so, then repeats the cause and the suggested fix the backend reported (REQ-CONFIG-316), and closes with the clause of REQ-CONFIG-315. The verdict is not composed by this screen from evidence of its own: it is a query to the platform confinement service owned by the sandbox-and-egress domain, asked about the host the run would execute on, answering with three fields — a **backend name**, a short identifier of the operating-system mechanism that would enclose the command, absent when there is none; a **cause** sentence; and a **suggested-fix** sentence, the last two absent when a backend is present. A backend is whatever that service reports; the settings screen tests for its presence, renders those fields, and invents no text of its own.
- **REQ-CONFIG-315** — The closing clause of the no-backend verdict is chosen by the mode being edited: with `off` it advises leaving the mode off until a backend is available; with `workspace-write` or `read-only` it states that a run asking for that mode will fail rather than start (REQ-CONFIG-317).
- **REQ-CONFIG-316** — Where the backend reports a cause and a suggested fix, both are shown as the backend worded them and are not re-written, since they name the missing mechanism and the supported way to obtain it. On a platform that has no backend at all, unavailable is the expected verdict and is not presented as an error. Which platforms those are is a property of the platform confinement service and is deliberately not enumerated here: this screen must behave identically on a host that never had a backend and on one whose backend is merely missing, so that adding support for a platform changes no requirement of this domain. The screen therefore branches on the presence of a backend name and never on a platform identity.
- **REQ-CONFIG-317** — Selecting a mode the current host cannot run is **allowed and stored**: the setting is kept for a host that can run it. The verdict simply reports that a run would fail rather than start.
- **REQ-CONFIG-318** — A stored confinement mode outside the known vocabulary must never crash the screen: the selector **adds the unknown value as an item** so it stays visible, and the verdict reports it as unrecognized. The general rule for placing a stored value into any selector is to append it when it is not already among the options, rather than quietly substituting the first entry — on a security control, displaying a setting nobody selected does more harm than displaying one the product cannot classify.
- **REQ-CONFIG-319** — Every verdict branch uses a text-contrast colour step rather than a saturated indicator step, because the saturated step does not meet the 4.5:1 text contrast requirement.

### Settings screen: runtime policy controls

- **REQ-CONFIG-320** — The Runtime category presents, in order: a delegation strategy selector, a run-start mode selector, delegation limits, the runtime policy card, the security policy card, and the advanced runtime card of REQ-CONFIG-471. The run-start mode selector offers exactly the two values REQ-CONFIG-476 registers and no others, its accessible description states that the mode decides whether a run produces a plan and waits for an answer before it changes anything, and it defers to Save like the rest of destination 1 (REQ-CONFIG-417).
- **REQ-CONFIG-321** — The delegation strategy selector offers exactly three options in this order: `orchestrator`, `swarm`, `single`. The selected label is the stored value.
- **REQ-CONFIG-322** — Delegation limits are two numeric controls with hard widget-level clamping, so out-of-range values are unreachable through the UI: depth cap **1–12** inclusive, fan-out limit **1–64** inclusive.
  > **Narrowed by [`PD-CONFIG-003`](../../product/directives/pd-config-003.md#pd-config-003), 2026-10-07.** Delegation limits are
  > three numeric controls: the per-agent timeout (REQ-MONITOR-286) joins them, in whole minutes clamped **1–240**.
- **REQ-CONFIG-323** — The runtime policy card presents four boolean toggles in this order, mapped to these fields: "Circuit breaker" → the circuit-breaker enabled flag; "Allow outside workspace" → `allow_outside_workspace`; "Improvement loop" → the improvement-collector enabled flag; and a keep-going toggle → `keep_going` (REQ-CONFIG-469), whose hint states that a run holds itself open while the last verification suite still has a failing or timed-out check and that no budget is thereby extended. Each toggle's accessible description states whether it is enabled or disabled and is **regenerated on every state change**, whether the change came from the user, from a repopulation, or from a full rebuild — so assistive technology never reports the state the toggle had before it was last moved.
  > **Extended by [`PD-CONFIG-003`](../../product/directives/pd-config-003.md#pd-config-003) revision 2, 2026-10-07.** The four toggles
  > stand as listed; directly after "Improvement loop" the card also shows "Improvement analysis timeout", whole seconds
  > clamped **10–600** over `runtime.improvement_collector_timeout`.
- **REQ-CONFIG-324** — The permission-mode control offers exactly the presets REQ-TOOLS-041 fixes, presented **strictest first** by the restrictiveness ordering of REQ-TOOLS-047, and opens on the shipped default REQ-TOOLS-046 states; none of the three is restated here, and the control offers no value outside the vocabulary it is bound to. What this requirement adds is that the ordering is the one the user sees, and that the control's accessible description explains that it decides how much an agent may do before it has to ask.
- **REQ-CONFIG-325** — Two numeric policy limits are presented with unit suffixes and hard ranges: compression threshold percentage **50–95** with a percent suffix, and iteration cap **1–500** with an iterations suffix. Each writes through on value change; initial values must be applied before the change connection is made so loading cannot write.
  > **Narrowed by [`PD-CONFIG-003`](../../product/directives/pd-config-003.md#pd-config-003) revision 2, 2026-10-07.** The numeric policy
  > limits are three: the improvement analysis timeout joins them, in seconds **10–600** with a seconds suffix.
- **REQ-CONFIG-326** — A non-interactive statement reads that secret redaction is always active (REQ-TOOLS-171, REQ-TOOLS-174). **There is no way to disable redaction from this screen**; the muted presentation communicates a fact about the product rather than a control left off.
- **REQ-CONFIG-327** — Two further confirmations exist in this card, both warning prompts with Yes and Cancel and **Cancel as the default**: turning on access beyond the workspace must say that agents will then be able to read and change files outside the chosen workspace, and that it belongs on only where a task genuinely needs it; moving to `autonomous` must say that mutating tools inside the workspace will be invoked without a prompt, **while any call reaching a path outside the workspace continues to require approval**. That residual guard is a behavioral promise the prompt makes and the runtime must keep. Anything other than an affirmative answer restores the control from the stored value and returns **without writing**, exactly as REQ-CONFIG-308 requires of the confinement card: cancelling leaves the stored value and the visible control both at their previous values, so a cancelled confirmation is never left showing a setting that was not applied.
- **REQ-CONFIG-328** — The permission-mode control on this screen keeps the deferred Save/Discard flow and **never reaches a live run**; the composer's equivalent control writes and applies immediately, and writes that key and no other (REQ-CONFIG-288). Same field, two commit policies, and — since the composer's write is scoped to its own key — two commit policies that cannot commit each other's work. A run whose requested `autonomous` mode is downgraded reports the downgrade elsewhere; this screen does not surface it.
- **REQ-CONFIG-471** — The advanced runtime card is the one place a user reads runtime settings **per scope** and switches memory diagnostics on. It carries a scope selector offering Workspace and Global, opening on Workspace (REQ-CONFIG-463); a read-only rendering of that scope's **raw** `runtime:` mapping, read directly from that scope's file rather than from the merged configuration, so a user can see whether a setting is stated globally, stated in this workspace, or stated nowhere and inherited from the built-in defaults; and a toggle for `memory_diagnostics_enabled` (REQ-CONFIG-131). The rendering is selectable text and is never editable: this card shows what a file says and offers no way to author it (REQ-CONFIG-464), the file itself remaining the place a runtime key is written by hand. The toggle writes through the scoped per-field write path (REQ-CONFIG-441) into the selected scope, which leaves every other runtime key in that file untouched (REQ-CONFIG-443), and is followed by an immediate reload, after which the card reports the new state and the scope it was written to (REQ-CONFIG-261). It is therefore outside the Save/Discard flow and Discard does not undo it, which the card states in words. With no configuration service the card renders its empty state and the toggle is disabled (REQ-CONFIG-424).

### Settings screen: model slots and per-role overrides

- **REQ-CONFIG-329** — The Models category holds two cards: model slots (a grid rebuilt per refresh) and providers (a right-aligned action to add an endpoint plus one row per provider). The add-endpoint action is explicitly for a **user-wide** endpoint, not a workspace-scoped one.
- **REQ-CONFIG-330** — Each model-slot row has three columns: the slot name, a model selector, and a reasoning-strength selector. Accessible names identify the model and the reasoning strength for the named slot, and the reasoning selector's accessible description explains that it sets the reasoning or thinking strength used by that slot's model.
- **REQ-CONFIG-331** — With no slots configured, the grid shows a single message spanning all three columns stating that no model slots are configured for the workspace.
- **REQ-CONFIG-332** — A slot's reasoning-strength options are the levels the selected model offers, preceded by an unset entry displayed as "Provider default"; where the model offers no levels the list is that entry alone. The control is editable only while more than one entry is offered, and is otherwise disabled with a tooltip stating that the model exposes no configurable thinking strength. Where the stored value is non-null and is not among the levels the model offers, it is appended to the list and shown as the current selection, so repopulating the control from configuration never discards a level the catalog has stopped offering; this applies to repopulation only, not to a model change made by the user (REQ-CONFIG-334). Each level is displayed under its own name. A selection resolving to no known entry falls back to the first entry. For a model offering the full set the list is therefore exactly: Provider default, low, medium, high, max — `auto` is never among the levels a model offers (REQ-CONFIG-093) and reaches the list only through the appending rule above, under its own name and never under the unset entry's label (REQ-CONFIG-254). **The set of levels a model offers is read from the model catalog and from nowhere else**: it is the slot/model reasoning vocabulary of REQ-CONFIG-069 less `auto`, intersected with the reasoning levels declared by the resolved model's catalog entry — the capability record the discovery snapshot carries for that model (REQ-CONFIG-202). Where the model entry declares a `reasoning_effort_map` (REQ-CONFIG-091), that map's keys are the offered levels instead, since the author has stated there exactly what the endpoint understands. A model with neither a capability record nor a map offers no levels at all, and the control is then the unset entry alone and disabled.
- **REQ-CONFIG-333** — The reasoning selector persists the option's underlying **value**, never its display text, so "Provider default" is stored as unset rather than as a literal string.
- **REQ-CONFIG-334** — Choosing a different model for a slot clears that slot's reasoning strength to unset whenever the newly chosen model does not offer the strength currently stored, and the clearing is **disclosed, never silent**: the reasoning control states, in its hint and in its accessible description, that the strength that was stored has been cleared because the newly chosen model does not offer it, and names that strength. The wording is left to the implementation. The stored level `auto` is exempt and is never cleared this way: it is not a model-specific level, no model ever offers it (REQ-CONFIG-332), and only an explicit selection by the user may replace it (REQ-CONFIG-093). This rule applies to a model change made in the control; a repopulation from stored configuration preserves the stored strength instead (REQ-CONFIG-332). The order in which the user touches the two controls therefore changes the stored result, which is intended: a strength chosen for a model the user has since moved away from is not carried onto a model that cannot honour it.
- **REQ-CONFIG-335** — The reasoning setter is idempotent: re-selecting the same value does not mark the form dirty, so a rebuild that re-selects the current option cannot dirty the form. The delegation limit setters have no such equality guard and rely instead on suppressed notifications during repopulation.
- **REQ-CONFIG-336** — The Personas category presents an edit-scope selector with exactly two options, Workspace and Global, its accessible description saying that the choice settles whether edits to a role's model and reasoning are recorded for this workspace or for the user as a whole. The displayed labels are capitalized while the stored vocabulary is lowercase (`workspace`, `global`).
  > **Extended by [`PD-CONFIG-001`](../../product/directives/pd-config-001.md#pd-config-001), 2026-09-14.** The selector
  > settles where a role's MCP tool-grant edits are recorded too, on the same terms as a model or
  > reasoning edit; its stated scope over model and reasoning still governs verbatim.
- **REQ-CONFIG-337** — **Changing the edit scope is a read operation, not an edit.** Switching scope re-renders the controls showing that scope's values while the role's effective value is unchanged and the form stays clean. Scope switching shows; it never copies.
- **REQ-CONFIG-338** — The role table has six columns in this order: Persona, Role, Model, Reasoning, Scope, Tools. Model, Reasoning and Scope are interactive; Tools is a comma-joined read-only list — the category does not edit tools inline.
  > **Narrowed by [`PD-CONFIG-001`](../../product/directives/pd-config-001.md#pd-config-001), 2026-09-14.** The Tools
  > cell is interactive for the role's MCP tool grants — one section per configured server, carried
  > state and per-tool selection writing `mcp_tools` (and `mcp_servers` where a carry moved) — while
  > this sentence still governs for the built-in `tools:` list the cell also renders. The column
  > order and the rest of the table are untouched.
- **REQ-CONFIG-339** — Role model options are **slot names first** (de-duplicated, in slot order), then every catalog model whose name is not also a slot name. A role may therefore target a tier (following whatever the slot is set to) as well as a concrete model.
- **REQ-CONFIG-340** — Role reasoning options are built as: `default`, then `provider_default`, then the resolved model's own non-null levels, that set being the one defined by REQ-CONFIG-332 and read from the same place. The displayed model is resolved through the slot map first, so a role pointing at a tier gets that tier's model's levels. The stored value (or `default` when unset) is appended when not already present — an unrecognized stored value is **preserved, not dropped**. Labels are "Default" for `default`, "Provider default" for `provider_default`, and the level name verbatim otherwise. Selecting an option with no underlying value writes the **empty string**, which is the unset spelling on this path.
- **REQ-CONFIG-341** — The Scope column stacks one row per editable field (model and reasoning), each naming the field and the origin the effective value came from. An **Unset** action appears for a field **only when that field's origin equals the currently selected edit scope** — an override can only be cleared at the level being edited. Its tooltip explains that it falls back to the lower-precedence value, and its accessible name identifies the field and the role. Clicking it marks the field's origin as `default` and records a pending unset of (role, field, scope). The origin vocabulary is exactly `workspace`, `global`, `discovered` and `default`, and the precedence chain the column reports is workspace > global > discovered > default, matching the layer order of REQ-CONFIG-031 — `discovered` marks a value contributed by the provider/model discovery snapshot layer (REQ-CONFIG-034) and `default` a built-in, neither of which is a scope the user may edit at, so neither offers an Unset action. With Global selected and per-scope values for default and global, unsetting makes the control display the **default** value. Discarding restores model, scope and reasoning to their previous values — **but the selected edit scope survives Discard**, being a view selection rather than an edit.
