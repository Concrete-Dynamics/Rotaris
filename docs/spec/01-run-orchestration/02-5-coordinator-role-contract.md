# Multi-Agent Run Orchestration — 5. Coordinator Role Contract

Part 2 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-028 – REQ-ORCH-060.

### 5. Coordinator Role Contract

- **REQ-ORCH-028** — The coordinator's instructions MUST carry a routing table from need to specialist role. The default role vocabulary MUST be `orchestrator` (the coordinator itself), `requirements-engineer`, `codebase-analyst`, `librarian`, `architect`, `planner`, `coding-agent`, `tester`, `docs-writer`, `refactorer`, `verifier`, `ui-verifier`, `gatekeeper`. The default routing MUST be: an ambiguous or under-specified request → `requirements-engineer`; a question about the repository as it stands → `codebase-analyst`, which reads the workspace but does not modify it; a question answerable only from outside the repository — third-party documentation, API references, the open web → `librarian`, which likewise does not modify the workspace; design → `architect`; producing an ordered plan, including commissioning whatever research that plan needs → `planner`; implementation → `coding-agent`; testing → `tester`; documentation → `docs-writer`; behavior-preserving restructuring → `refactorer`; final acceptance → `verifier`. Exclusive implementation ownership MUST be measured per todo item and at no other granularity: at most one child at a time may hold an implementation delegation for any one todo item, where an implementation delegation is one whose target role holds a tool the public tool-name registry declares as writing workspace files (REQ-TOOLS-001). Two children working on the same file for two different todo items are therefore not a violation, and two children working on the same todo item are one whatever files they touch. The acceptance role's sign-off before the run is reported successful MUST be an instruction the coordinator is expected to honour and MUST NOT be a run-enforced condition on the run's outcome: the run's own enforcement of whether work is finished is the deterministic completion gate of REQ-ORCH-116, which rests on checks that actually executed rather than on a role's assertion, and the terminal status continues to follow REQ-ORCH-082 and REQ-ORCH-083 from completed and abandoned task counts alone. No status, stop reason, or gate decision is ever made conditional on a role having declared sign-off.
  > **Extended by [`PD-TOOLS-006`](../../product/directives/pd-tools-006.md#pd-tools-006), 2026-09-23; revision 4, 2026-10-07; revision 6, 2026-10-07; revision 8, 2026-10-07.** Ownership stays per todo item exactly as stated. Beside it, a child may declare a write scope, and while it is live the file tools refuse other agents of the run a write into it. Since revision 4, `delegate`'s description tells each caller which REQ-TOOLS-001 facets a child of it would hold as each persona, and to ask a persona only for work its tools allow. Since revision 6, a delegation names the todo item it serves (`todo_item`), and the run refuses an implementation delegation for an item another outstanding implementation child holds, the measure of the ownership above. Since revision 8, the built-in routing table keeps every route and both clauses above and closes with one sentence sending the work a route implies to a persona whose entry in `delegate`'s list allows it.
- **REQ-ORCH-029** — Constraints on the coordinator MUST hold no matter what playbook cell or instruction text is in force, and each is externally checkable from the run's own records. They bind the entry role while it acts as coordinator, which is every run except one taken under a `single` override, where by REQ-ORCH-025 the entry role is the worker, holds the direct-work bundle, and has no delegation tool at all. While the entry role acts as coordinator: it makes no file-modifying tool call and emits no plan, code, or diff of its own authorship; every work item it takes on reaches a specialist through a `delegate` call; work spanning more than one step is accompanied by a todo list it keeps current; no two implementation delegations for the same todo item are outstanding at once; it does not report the run successful while a todo item is non-terminal or while a todo item's recorded state disagrees with what happened; and it issues no delegation whose child would sit deeper than delegation depth 3 (REQ-ORCH-046).
  > **Narrowed by [`PD-ORCH-006`](../../product/directives/pd-orch-006.md#pd-orch-006), 2026-10-06 (revision 2 the same day; revision 3, 2026-10-07, adds REQ-ORCH-025's `swarm` sentence to its narrowing and changes nothing here).** Where the intent-to-tools mapping grants the entry role the direct-work bundle (REQ-ORCH-016: with the built-in mapping, `explicit_trivial` and `single_file_change`), the three constraints that forbid it to do the work itself — no file-modifying call, no plan, code or diff of its own, every work item through `delegate` — do not bind it for that run, and its instructions say it does the work; the other constraints above still bind. Revision 2: on every run, "a todo item is non-terminal" ranges over the items the task in hand answers for, as [`PD-ORCH-012`](../../product/directives/pd-orch-012.md#pd-orch-012) decides them.
- **REQ-ORCH-030** — One attempt at a todo item is one implementation delegation for that item as REQ-ORCH-028 defines it. That attempt counts as failed when its child reaches a terminal state other than `succeeded`, and equally when its child succeeded but the verification evidence recorded for that item afterwards holds at least one blocking check `failed`; a completion-classifier verdict of `NEEDS_ITERATION` is not itself an attempt, because it judges an iteration rather than a delegation. The count is kept per todo item, accumulates across iterations of the same run, and resets only when the item is marked complete. After three failed attempts at the same item the run MUST refuse a fourth implementation delegation for it, with the error observation of REQ-ORCH-038 naming the item, its three failed attempts, and the two permitted next actions; the refusal is enforced by the run and is not left to instruction, so no instruction text can spend a fourth attempt. The two permitted next actions are a diagnosis delegation — to `codebase-analyst` when the unknown lies in the repository, to `librarian` when it lies in a third-party dependency — which carries the accumulated failure context from those attempts and which this rule never refuses, and a failure report to the user. That report MUST convey the item that could not be completed, and for each attempt what was tried and how it failed; its wording is the implementation's.

### 6. Delegation Contract

- **REQ-ORCH-031** — Delegation MUST be an explicit tool call (tool name `delegate`) with required parameters `persona` (target role), `task_name`, and `task`, plus optional `depends_on: list[task_id]`. The task text is instructed to use labeled sections: TASK, EXPECTED OUTCOME, MUST DO, MUST NOT DO, CONTEXT.
- **REQ-ORCH-032** — The optional fields the delegation call accepts beyond those of REQ-ORCH-031, and the handling of each, are fixed by REQ-TOOLS-152; this domain restates none of them. What it relies on that call to provide is: forwarding the reports of already-completed siblings as context without imposing an ordering dependency; a routing hint that is explicitly not a model name; reuse of a previous delegation's session for a retry or follow-up; a background default; attachment of artifact bodies at the head of the child's payload; and suppression of the automatic index of earlier sibling artifacts, which a per-role setting may force independently. The points on which this document previously differed are settled by REQ-TOOLS-152 and are not restated here: what becomes of an `inherited_context` id that resolves to nothing, of one that names a task which failed or has not finished, and of an attachment set that would carry the payload past its size budget are that requirement's to fix, and this domain states no rule of its own for any of them.
- **REQ-ORCH-033** — What a delegation observation carries — the canonical task name, the closed status set it draws on, the task id, and the message accompanying each status — is fixed by REQ-TOOLS-153; this domain restates none of it, mints no delegation status of its own, and states no message text for one (REQ-ORCH-037). What it relies on that requirement for is that every accepted delegation yields an observation the coordinator can read the child's admission from, and that a delegation held behind a per-model cap is reported as held rather than as rejected (REQ-ORCH-050). The one thing this domain adds is the model-visible rendering of that observation, which is of the form `Task '<canonical>': <status> — <message>` followed by a `task_id: <id>` line.
- **REQ-ORCH-034** — Role aliases MUST be resolved before spawn: `coder` → `coding-agent`, and `playwright` → `ui-verifier`. An alias resolves only when its target role actually exists in the current configuration. An unknown role MUST be rejected with a message listing the known role names and the supported aliases rendered as `<alias>-><target>`; when an alias was resolved, the observation message states which alias resolved to which role.
- **REQ-ORCH-035** — The order in which a child's payload is assembled at spawn is fixed by REQ-TOOLS-154; this domain restates none of it. What it relies on that requirement to provide is a place in that order for the two blocks whose content this domain owns — the verification-evidence block of REQ-ORCH-129, supplied for the acceptance role, and the index of earlier sibling artifacts whose suppression REQ-ORCH-032 governs — and that the caller's task text is the last thing the child reads. The one addition this domain makes is positional and applies to no other block: a child spawned with dependencies additionally receives the prior-agent-context block of REQ-ORCH-047 at the moment it becomes ready, placed ahead of everything REQ-TOOLS-154 orders, and it is therefore the first content that child sees.
- **REQ-ORCH-036** — Every spawned child MUST be assigned a task id matching `^bg_[0-9a-f]{8}$`, unique within the session. `depends_on` entries are task ids and are normalized to canonical names at spawn; an unknown task id in `depends_on` MUST be rejected with an error naming it.
- **REQ-ORCH-037** — What the caller observes when a delegation is accepted is fixed by REQ-TOOLS-152 and REQ-TOOLS-153; this domain restates none of it. What it relies on those requirements for is that `delegate` never suspends the parent's conversation. This domain adds no suspend step of its own and none is observable in the transcript; a parent that is to wait for a child is enrolled in the one waiting mechanism of REQ-TOOLS-156, which is the same mechanism `wait_for_tasks` uses (REQ-ORCH-062), and is resumed from it under Section 11.
- **REQ-ORCH-038** — The following delegation attempts MUST be rejected with an error observation and no spawn: unknown role; depth limit exceeded ("Max depth N exceeded"); total-children limit reached ("Max total children N exceeded"); active-children limit reached ("Max active children N exceeded"); unknown dependency; dependency cycle ("Dependency cycle detected"); a dependency owned by a different parent (the rejection names both parents); a malformed inherited-context entry (e.g. empty string); a fourth implementation delegation for a todo item that already has three failed attempts (REQ-ORCH-030).
- **REQ-ORCH-039** — A delegation to the acceptance role MUST be refused, with no child spawned, while the most recent verification evidence available for the task in hand records at least one blocking check as `failed`. The refusal reason MUST name those checks, state that their output is already captured, state that the task is already set to be attempted again, and direct that acceptance be delegated only once those checks pass. Where no verification evidence exists for the task at all, the delegation MUST be allowed and proceeds on the empty-evidence path of REQ-ORCH-129. Checks recorded `timeout`, `skipped`, or `invalid` MUST NOT by themselves cause a refusal; they are disclosed to the acceptance role per REQ-ORCH-129. The asymmetry between this rule and REQ-ORCH-116 is deliberate and MUST be preserved: the completion gate decides whether the work is finished, so a blocking check that never answered its question leaves it unsatisfied, whereas this refusal exists only to stop the acceptance role being asked to bless a result already known to be red. Keying the refusal on `failed` alone is what keeps acceptance reachable when checks timed out, were skipped, or were refused by policy — precisely the case REQ-ORCH-129's list of checks that did not answer their question exists to hand it.

### 7. Child Task State Machine

- **REQ-ORCH-040** — The state a delegated child occupies, the closed set those states are drawn from, and which of them are terminal are fixed by REQ-MONITOR-014 and REQ-MONITOR-300; this domain holds no copy of that set and mints no child state of its own. What it relies on those requirements for is that the set is closed, that a child created with unresolved dependencies begins in `waiting_on_dependencies` and one created behind a per-model cap in `waiting_on_model_slot` and every other child in `queued` (REQ-ORCH-046, REQ-ORCH-050), and that the terminal subset is absorbing, so the sweeps of REQ-ORCH-052 and REQ-ORCH-053 and the waits of REQ-ORCH-062 have a settled condition to test against.
- **REQ-ORCH-041** — The legal-transition table for a delegated child, the rejection of any move outside it, and the completion timestamp stamped on entering a terminal state are fixed by REQ-MONITOR-300, REQ-MONITOR-016, and REQ-MONITOR-017; this domain holds no copy of the table, states no transition of its own, and fixes no wording for the rejection. This identifier remains the citation other documents use for a child's terminal state (REQ-HOOKS-075) and continues to resolve to the vocabulary REQ-MONITOR-300 declares absorbing. What this domain relies on those requirements for is that cancellation settles any non-terminal child to `cancelled` from whatever state it is in (REQ-MONITOR-209), so the cleanup sweeps of REQ-ORCH-052 and REQ-ORCH-053 can never fail partway, and that a rejected transition leaves the child's record untouched, so a rejected move can never be mistaken for progress by the scheduling passes of Section 11.
- **REQ-ORCH-042** — Which child states count against the concurrent-child budget, and which hold a model slot, are fixed by REQ-MONITOR-015 and REQ-MONITOR-020; this domain holds no copy of either rule and names no state of its own on the point. What it relies on those requirements for is that a child parked in `waiting_on_model_slot` consumes no active-child allowance — it is idle and holds no model connection — so children queued behind a model can never trip the active-children limit of REQ-ORCH-046, and that a slot freed by a child reaching a terminal state promotes exactly one held child (REQ-ORCH-050).
- **REQ-ORCH-043** — The persisted per-child record MUST include at least: given and canonical names, role, task payload, dependencies, inherited context, state, spawn and completion timestamps, parent agent identity, depth, conversation identity, category, session id, background flag, task id, launch generation, produced/received artifact ids, resolved model key, the actually granted native tool set, the granted MCP tools per server, and the child's live serialized todo state.

### 8. Child Naming, Limits, and Dependency Graph

- **REQ-ORCH-044** — Child task names MUST be scoped per parent. A reused name is deterministically renamed `<name>_<n>`, where n is the smallest positive integer, counting up from 1, not already in use for that name, and the canonical name is used everywhere the task is referenced (transcripts, dependency resolution, artifacts).
  > **Narrowed by [`PD-ORCH-010`](../../product/directives/pd-orch-010.md#pd-orch-010), 2026-10-06.** A child at any depth is also
  > renamed off the canonical name or persona of its own root and of every root the session has recorded, though no
  > sibling holds the name. A root named like an earlier child is accepted until after the first release.
- **REQ-ORCH-045** — Canonicalization of a task name MUST apply these steps in order: collapse each run of whitespace; replace every character outside `[A-Za-z0-9_.-]` with `-`; strip leading and trailing `-`, `.`, and `_`; and, when nothing remains, use `task`. The result MUST be at most 80 characters. A name that would exceed 80 characters MUST be shortened to 80 characters or fewer and MUST end in an 8-character lowercase hexadecimal suffix derived from the full name as it stood before shortening, so that the same long name always canonicalizes to the same string and two different long names never canonicalize to the same string. The digest is SHA-256 taken over the UTF-8 encoding of the name as it stood after the first three steps and before any shortening, and the suffix is the first 8 characters of that digest's lowercase hexadecimal rendering. A single `-` precedes it. A shortened name is therefore the first 71 characters of the pre-shortening result, then `-`, then the 8-character suffix, which is exactly 80 characters.
- **REQ-ORCH-046** — Spawn validation MUST be applied in this order, and the first check that fails MUST reject the delegation with the error observation of REQ-ORCH-038, creating no child record and issuing no task id: (1) depth — the entry role is at depth 0, a child of an agent at depth d is at depth d+1, and the spawn is rejected when the child's depth would exceed the configured maximum (default 3); (2) total children — the number of children already created in this iteration's ledger has reached the configured maximum (default 20); (3) active children — the number of children in `starting` or `running` has reached the configured maximum (default 6); (4) every id in `depends_on` names an existing child of the same parent; (5) the new dependency edges, added to the edges already present, close no cycle. A delegation that passes validation creates a child whose initial state is `waiting_on_dependencies` when `depends_on` was non-empty and `queued` otherwise; a child whose model key is already at its concurrency cap is reported as `waiting_on_model_slot` per REQ-ORCH-050.
- **REQ-ORCH-047** — A dependent child MUST start only after ALL of its dependencies have both reached `succeeded` AND had their mandatory report artifact stored; a dependency without a stored report does not count as succeeded. When a dependent becomes ready, the framework MUST prepend exactly once (never re-prefixed on later state hops such as promotion out of the model-slot queue) a prior-agent-context block flagged as authoritative — directing the reader to rely on the supplied findings rather than repeating that investigation — containing each dependency's final response (else last response) in per-dependency sections identifying name, role, and status. If reports are missing, no context block is injected.
  > **Narrowed by [`PD-TOOLS-006`](../../product/directives/pd-tools-006.md#pd-tools-006), 2026-10-13 (revision 9, OQ-256).** The block, its authoritative flag and its once-only injection still govern; each dependency's section carries its final response, else last response, else key findings, else summary, under a 100,000-character budget for the block, and an answer that does not fit is cut to the larger of the remainder and 4,000 characters and ends in a marker telling the child what was omitted, that nothing it can reach holds the rest, and that its report must say what it did not receive.
- **REQ-ORCH-048** — When a child reaches `failed` or `cancelled`, every child depending on it that still stands in a state from which REQ-MONITOR-300 makes `blocked` reachable MUST transition to `blocked`, cascading transitively to further dependents; a dependent that is already under way is left to run. This domain holds no copy of the transition table and names no source state of its own. What it relies on REQ-MONITOR-300 for is that those source states are exactly the three a dependent can occupy before it has started, so the cascade never has to decide whether a move it demands is legal, and that `blocked` is absorbing, so a cascaded child settles once. Blocked children are never started automatically. Terminal-state callbacks MUST fire for cascaded records exactly as for directly completed ones.
- **REQ-ORCH-049** — A child MUST be started at most once, however many scheduling passes for the same parent are in flight at the same time. Over the whole run, the number of `child_start` timeline events recorded for any one task id MUST be exactly one for a child that started and zero for one that never did. An attempt to start a child that has already been started, or that has since moved on, MUST be suppressed rather than carried out, and MUST be recorded as a `child_launch_suppressed` timeline event together with a `stale_child_launch_claim` issue naming the child's canonical name and task id.

### 9. Per-Model Concurrency

- **REQ-ORCH-050** — A per-model concurrency cap MUST limit how many children bound to the same model key may be in `starting` or `running` at one time, where a model key is the identifier under which a model is configured (REQ-ORCH-145). A cap the user set for a model always applies; where the user set none, the cap in force is the one the model's provider catalogue entry declares, and this domain holds no list of provider names and no per-name figure of its own (REQ-MONITOR-021). A catalogue entry that declares nothing on the point declares no cap, so every model of such a provider is uncapped, and adding a provider that does declare one caps its models with no amendment here. Exceeding the cap MUST NOT reject the delegation: the child is created, reported with status `waiting_on_model_slot` per REQ-ORCH-033, and held until a slot frees. Held children MUST be released in the order they were held, one returning to `queued` each time a child bound to the same model key reaches a terminal state. A held child that has itself reached a terminal state MUST be dropped rather than released. Where no cap applies to a model, no child bound to it is ever placed in `waiting_on_model_slot` on that account.

### 10. Terminal Marking, Sweeps, and Orphans

- **REQ-ORCH-051** — Marking a child terminal MUST: store its report retrievable by both canonical name and task id; enqueue a completion notification for background-flagged children (carrying task id, canonical name, description, state, duration since spawn, count of still-running siblings, and produced artifact ids) while foreground children produce no notification; cascade blocking on failure/cancellation; and release the model slot. A child's result lives only for the duration of the session unless an explicit artifact write is performed, which is the only way a durable artifact-store record comes into being.
- **REQ-ORCH-052** — An idempotent finalize-incomplete sweep MUST close every non-terminal child record as `cancelled` through the normal terminal-marking path (so slots release, blocking cascades, and callbacks fire), re-checking per record because closing one can cascade-block another. Every exit path from an iteration — blocked delegation, plain re-queue, cancellation, crash — MUST leave both the record for the iteration itself and every child record it holds in a terminal state, so that a finished run never leaves behind a record that still reads as running.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** An exit from an iteration by a pause, a stop, a quit or a crash leaves every unfinished agent in the resumable state `paused`, and the iteration open; every other exit is unchanged.
- **REQ-ORCH-053** — On session continue, a run that has just acquired the session lock MUST settle every non-terminal child record read back from the previous run (e.g. after a killed host or hard cancel) to `cancelled` before its first iteration, so reattached sessions never show phantom running agents.
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** The settle still runs, and no longer touches a `paused` agent: that agent is resumed with its iteration instead of being cancelled.
- **REQ-ORCH-054** — A newly-terminal query MUST return terminal children the parent has not yet observed and mark them observed; calling it again immediately returns nothing.

### 11. Parent Suspension, Resume, and Notifications

- **REQ-ORCH-055** — A parent MUST be resumed whenever at least one direct child reaches a terminal state the parent has not observed; multiple terminal events may batch into one resume. On resume the parent receives the newly-terminal children's structured reports, the current state of all its direct children, and scheduling metadata, and may then continue orchestrating, work locally, spawn more children, or end generation again.
- **REQ-ORCH-056** — After a parent is resumed, the run MUST keep scheduling on that parent's behalf until all three of the following hold at the same time, and MUST then leave the parent idle: the parent has no outstanding wait request; no completion notification for it is still undelivered; and every child of it that could be started has been started at least once. A parent whose remaining children are all waiting on dependencies that have not been met MUST NOT be resumed again on that account alone: a child that has already been attempted does not by itself cause a further resume, so a run can never alternate between starting and resuming indefinitely without some child changing state.
- **REQ-ORCH-057** — Foreground pass: ready children are spawned, and a parent that is to wait for them is enrolled in the one waiting mechanism of REQ-TOOLS-156 (REQ-ORCH-037), over the freshly spawned children only and never over the outer task. This document describes no second waiting path and adds no suspend step of its own; what it relies on that mechanism for is that the parent is resumed once the waited-for children are terminal. On that resume, now-duplicate notifications MUST be discarded and the parent MUST receive a message stating that child task updates are available, including per-child report blocks; when other children still run, the guidance states how many are still running in the background; when none remain, the guidance states that all background tasks finished and encourages issuing the next batch of delegations in parallel before ending the turn.
- **REQ-ORCH-058** — Background pass: spawn ready background children, then resume the parent immediately with a message stating background tasks have started, instructing it to continue productive work and to use the waiting tool only when specific results are needed, plus an active-background-tasks list of the form `- <canonical> \`<task_id>\`: <name>`.
- **REQ-ORCH-059** — For each background child that completed, a completion notification MUST be injected into the parent conversation without triggering generation (fire-and-forget), containing: a background-task-completed banner; the task id; the description (canonical name plus given name); the duration in seconds; published artifacts when any; when others still run, the remaining count with an explicit promise of notification when all complete and an instruction not to poll but continue productive work, plus a usage hint for the output-retrieval tool (summary and verbatim forms); otherwise a statement that all background tasks have completed. Open-todo reminder lines are appended. After injection, the parent is resumed with an empty message. This delivery MUST work even when the child completes while the parent is mid-turn (the parent is interrupted for injection without force-closing its conversation), and a completion delivered via a wait or foreground resume MUST have its matching notification discarded so it is announced exactly once.
- **REQ-ORCH-060** — Each per-child report block in a resume message MUST show the canonical name, role, and status, optional artifact descriptions, then the result text (final response, else last response, else key findings) capped at 4000 characters with a truncation marker stating how many characters were omitted.
