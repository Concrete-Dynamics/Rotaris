# User-Defined Lifecycle Hook Commands — External-Agent Hook Import (Claude Code)

Part 4 of 6 of [domain 09](../09-lifecycle-hooks.md), which indexes every part. Defines REQ-HOOKS-110 – REQ-HOOKS-139.

### External-Agent Hook Import (Claude Code)

- **REQ-HOOKS-110** — Discovery SHALL read the user-level Claude Code settings JSON — by default `~/.claude/settings.json`, which the environment variable `ROTARIS_CLAUDE_SETTINGS_PATH` can point elsewhere — and SHALL only ever read it (the file is byte-for-byte unchanged after any toggling in the interface). A problem reading it yields no records plus one of: `Claude Code global settings were not found.` / `Claude Code hooks could not be read: <err>` / `Claude Code global settings contain no hook declarations.`

- **REQ-HOOKS-111** — Event mapping SHALL be: `PreToolUse` → `pre_tool`, `PostToolUse` → `post_tool`, `SessionStart` → `session_start`, `SessionEnd` → `session_end`, `SubagentStop` → `child_completed`. Any other external event produces a record marked unusable with the explanation `The Claude Code <event> lifecycle event has no Rotaris equivalent.`

- **REQ-HOOKS-112** — Tool-matcher mapping (for the two tool events only): empty or `*` selects all tools; otherwise the matcher is split at `|` and `,` into selectors, each selector is mapped to a set of this product's tool names — `Bash` → {`terminal`}, `PowerShell` → {`terminal`}, `Read` → {`read_file`, `haet_read`}, `Edit` → {`haet_edit`}, `Write` → {`write_file`} — and the union of those sets becomes the imported hook's set of tool names (matched exactly, per REQ-HOOKS-023). Surrounding whitespace on a selector is ignored, and an empty selector between two delimiters contributes nothing. A matcher containing any regular-expression metacharacter (`^ $ . * + ? [ ] ( ) { } \`) is unusable (`Regular-expression matchers are unavailable in Rotaris.`), as is a selector that is not recognized (`Claude Code tool selector '<x>' has no Rotaris equivalent.`).

- **REQ-HOOKS-113** — Every unusable record SHALL remain visible with its explanation rather than being dropped silently. Further explanations: a handler that is not a command handler (`<type> handlers are unavailable in Rotaris.`), a blank command (`The command handler has no command.`), an `if` predicate (`` Claude Code `if` predicates require tool arguments that Rotaris does not expose here. ``), a timeout that cannot be parsed (`The command handler timeout is invalid.`), and a timeout of zero or less (`The command handler timeout must be positive.`).

- **REQ-HOOKS-114** — A usable record SHALL become an effective hook with: display name `Claude Code <event>`, `<event>` being the external event name; the event it maps to under REQ-HOOKS-111; an empty matcher string; the command exactly as declared externally; the handler's timeout in seconds, or `60` where the handler declares none; `required = false`; scope `external:claude-code`; the set of tool names derived under REQ-HOOKS-112; and a stable identity `claude-code:` followed by 20 hexadecimal characters taken from a SHA-256 digest over the record's identifying facets — agent id, source path, event, external matcher, the handler's canonical JSON, the index of the handler group, and the index of the handler within that group. Observable consequences: rediscovering the same unchanged file yields the same identity every time; changing any one of those facets yields a different identity; and two otherwise identical handlers at different positions in the file have different identities. Stability across independent implementations is not required — a policy file (REQ-HOOKS-115) records one installation's choices and is not a portable document — but the identity SHALL nevertheless be fully determined rather than left to an implementation's convenience. The digest input SHALL be the UTF-8 encoding of the canonical JSON document `{"agent": "<agent id>", "event": "<external event name>", "group_index": <n>, "handler": <the handler exactly as declared, canonicalized the same way>, "handler_index": <m>, "matcher": "<external matcher>", "source": "<absolute source path>"}` with keys sorted, compact separators, and ASCII escaping; the identity is `claude-code:` followed by the first 20 characters of the SHA-256 digest of those bytes, rendered in lowercase hexadecimal.

- **REQ-HOOKS-115** — The global runtime policy SHALL live at `<config-dir>/external-hooks.json`, where `<config-dir>` is the value of the environment variable `ROTARIS_CONFIG_DIR` when that variable is set to a non-blank value (leading and trailing whitespace ignored, `~` expanded) and otherwise the per-user global configuration directory of REQ-CONFIG-001, which resolves per platform and is the per-user location REQ-STARTUP-145 fixes. **That variable relocates this one file and reaches nothing else.** It SHALL NOT move the layered configuration scopes of REQ-CONFIG-001, the credential store (REQ-PROVIDER-014), the durable session store (REQ-SESSION-198), the desktop preference store (REQ-SHELL-006), or anything else this product keeps in a per-user location; where it is set, the location of every one of those is unchanged. The bound is stated because REQ-STARTUP-145 fixes which per-user location the product uses and this variable is the only thing in this document that names a different one: a variable that could be read as an override of that requirement would let a user relocate the product's stores onto storage shared with another machine, which is the outcome the machine-local rule exists to prevent, and nothing about a hook policy file requires that reach. It is stored as JSON `{"version": 1, "agents": {<agent-id>: bool}, "hooks": {<record-id>: bool}}`, with keys sorted, two-space indentation, and an atomic write. A policy file that cannot be read or does not parse loads as empty, meaning everything is on. Any agent or hook not mentioned defaults to on. A hook is on when both its agent toggle and its own toggle are on, so switching an individual hook off survives switching its whole agent off and on again.

- **REQ-HOOKS-116** — The same policy file SHALL also govern this product's own hooks, which are grouped under the agent id `rotaris` (imported ones under `claude-code`): a native hook is skipped when either the `rotaris` agent toggle or an entry under its own stable id is `false`. The run's hook set is assembled as the surviving native, trust-gated hooks in declaration order, followed by the enabled imported hooks.

- **REQ-HOOKS-117** — When a run's hook set is assembled, only records that are usable and switched on are placed in it, and that set is then fixed for the run (REQ-HOOKS-131); an imported hook that is selected runs through the ordinary engine and receives the native payload shape, while one that is switched off never starts a process. The workspace trust gate does not apply to imported hooks — the settings toggles are how the user consents to them — and their scope value would in any case be withheld as unrecognized if it ever reached the gate.

### Persistence, Audit, Diagnostics

- **REQ-HOOKS-118** — A snapshot of the effective hook set SHALL be recorded once at session start into the session's launch audit (REQ-SESSION-138), as `"hooks": [ {hook_id, name, event, matcher, source, command}, ... ]` covering the enabled resolved set, with each command stored masked. The masking is not a property of where the record is kept and does not lapse because it is a record rather than a file: a hook command line often contains a credential, and the audit outlives the run, is readable by anything that can reach the store, and is carried into whatever is exported from the session. A credential must therefore never be written into it in the first place. Editing the configuration afterwards cannot alter this record. A run with hooks switched off, or with none at all, records an explicit empty list, so that an auditor can distinguish "there were no hooks" from "this was not recorded"; entries that are switched off do not appear.

- **REQ-HOOKS-119** — Every completed invocation SHALL add one `hook_run` entry to the session's timeline (REQ-SESSION-134): `severity` = `warning` where the outcome carried a warning and `info` otherwise; `actor` = the hook's display name; `message` = `Hook '<name>' (<event>) exited <exit_code> in <duration_ms> ms` (with `<exit_code>` rendered as `-1` where the hook produced no exit status, per REQ-HOOKS-036); `metadata` = `{hook_id, hook_name, event, source, exit_code, duration_ms, timed_out, blocked}` — `exit_code` here likewise carries `-1`, not `null`, for that state — plus `tool_name` where there is one and `stdout` / `stderr` only where non-empty (already limited to 16 KiB each under REQ-HOOKS-037, and masked under REQ-HOOKS-133 before being recorded, since a timeline entry outlives the run, is readable by anything that can reach the store, and is carried into the export of REQ-SESSION-199). Entries appear in the order the invocations happened.

- **REQ-HOOKS-120** — Every outcome carrying a warning SHALL additionally record an issue in the session's issue record (REQ-SESSION-135): kind `hook_failure`, severity `warning`, actor = hook name, message = the warning text, with the same metadata. A guard that legitimately stopped a call records nothing. Hooks withheld by the gate are recorded under kind `hook_trust` (REQ-HOOKS-086).

- **REQ-HOOKS-121** — The durable diagnostics entry SHALL be written before the corresponding completion event is published, so that an event lost on the stream does not also take the evidence of the invocation with it. Where the diagnostics directory cannot be written to, the entry degrades to a log line instead: the trail is kept wherever keeping it is possible, and its loss never interferes with the run.

- **REQ-HOOKS-122** — Hook processes SHALL be exempt from the tool permission policy and from any sandbox: they are the user's own code, executing directly on the host. Nothing else in the system observes them, so the diagnostics written under REQ-HOOKS-118 to REQ-HOOKS-121 are the sole evidence that a hook executed at all — which is what those requirements exist to guarantee.

### Wire Events

- **REQ-HOOKS-123** — Two event types SHALL exist on the session event stream: `hook.start` and `hook.finish`, both carrying `hook_id`, `hook_name`, `lifecycle_point` (the hook event name), `scope` (the configuration source, which for an imported hook is `external:claude-code`, REQ-HOOKS-114), and `tool_name` (empty for lifecycle hooks). `hook_name` carries the hook's display name, or its stable id where no name is configured (REQ-HOOKS-008); on the `hook.finish` announcing a hook the trust gate withheld it carries the stable id whatever the configuration says (REQ-HOOKS-102, REQ-HOOKS-126).

- **REQ-HOOKS-124** — `hook.start` SHALL additionally carry `command`, holding the configured command with the masking of REQ-HOOKS-061 applied; an unmasked hook command line SHALL never appear on the stream. For every invocation the `hook.start` SHALL become observable before that invocation's `hook.finish` and before any effect the hook process has, so that a consumer reading the stream while a hook is still occupying its budget sees the `hook.start` with no `hook.finish` yet paired to it. `hook.start` has no counterpart in the durable diagnostics, which record completed invocations only (REQ-HOOKS-119).

- **REQ-HOOKS-125** — `hook.finish` SHALL carry `exit_code` (integer or `null`, with the no-exit-status state always appearing as `null` here), `duration_ms` (number or `null`), `blocked` (which can be true only for `pre_tool`), `timed_out`, `skipped`, `skip_reason`, and `output` = standard output and standard error, each trimmed and each limited to 16 KiB, joined with `\n` and masked as part of constructing the event; they are joined because a refusal reason arrives on standard error while ordinary output arrives on standard output.

- **REQ-HOOKS-126** — A hook a gate withheld SHALL produce only a `hook.finish`, with `skipped = true`, a `skip_reason` drawn from the closed set this requirement defines, null `exit_code` and `duration_ms`, and `hook_name` carrying the hook's stable id rather than its configured display name (REQ-HOOKS-102, REQ-HOOKS-123); no process existed, so no `hook.start` accompanies it. The reason for emitting anything at all is that a configured hook absent from the stream could not be told apart from one that ran and had no effect. The defined reasons are exactly two. `"untrusted_workspace"` is a hook the trust gate withheld, announced once per session under REQ-HOOKS-127. `"plan_gate"` is a hook invocation withheld while a run is held at the plan gate (REQ-ORCH-153): it SHALL be emitted once per withheld invocation rather than once per session, because that hold ends when the user answers and the same hook runs normally for the rest of the run — a hook withheld at the gate is not run late and never runs twice for one moment that passed while the gate was held.

- **REQ-HOOKS-127** — Each hook the trust gate withheld SHALL be announced exactly once per session as one `hook.finish` of the shape given in REQ-HOOKS-126, however many tool calls and lifecycle points follow in that session and however many times the announcement is triggered. The announcement SHALL be observable no later than the session's first hook-related event, so a consumer attached from the start of the session sees every withheld hook before the first `hook.start`. Triggering the announcement again SHALL add no further events to the stream.

- **REQ-HOOKS-128** — Publishing to the stream SHALL be attempted but not depended upon, and SHALL be isolated from the rest: a broken stream or an event that cannot be constructed reduces to a log entry and never causes a hook to be skipped, to fail, or to run twice. The error path for a withheld-hook publication logs the hook id only and never the command, which at that point is still an unmasked shell command line.

### Cross-Cutting Invariants

- **REQ-HOOKS-129** — No hook-related condition SHALL end a run, alter its terminal status, or leave it waiting beyond the per-hook bound of REQ-HOOKS-033. Anything that goes wrong while executing a hook, building a payload, publishing a wire event, or emitting a notice SHALL reduce to a user-facing warning where REQ-HOOKS-052 defines one for it, and to a log entry in every other case; no other hook fault is surfaced to the user as a warning. The withheld-hooks notice (REQ-HOOKS-086, REQ-HOOKS-101), the switched-off advisory (REQ-HOOKS-054), and the start-up message of REQ-HOOKS-085 are notices about configuration rather than execution faults and are unaffected by this rule. The only hook outcome that changes what the run does is a `pre_tool` hook's stopping verdict (REQ-HOOKS-043, REQ-HOOKS-048), which refuses one tool call and nothing further (REQ-HOOKS-072).

- **REQ-HOOKS-130** — Every hook actually invoked for an event occurrence SHALL produce exactly one outcome, exactly one `hook_run` timeline entry, and exactly one `hook.start`/`hook.finish` pair: N occurrences of an event with one applicable hook produce N of each, never more and never fewer. Two cases produce fewer records by design: a hook the trust gate withheld produces exactly one `hook.finish` and nothing else — no outcome, no timeline entry, no `hook.start` (REQ-HOOKS-126); and a hook switched off by the failure budget produces none of them for occurrences after the switch-off (REQ-HOOKS-055). Records may also be absent where the durable trail could not be written (REQ-HOOKS-121) or the stream could not be published to (REQ-HOOKS-128); neither loss changes how many times the hook actually ran.

- **REQ-HOOKS-131** — The hook set resolved for a run SHALL be fixed when the run starts: configuration edited on disk while the run is under way SHALL NOT change which hooks run, nor the snapshot of REQ-HOOKS-118, nor the fingerprint the trust decision was checked against. Two within-session changes are defined, and both replace or remove whole entries rather than editing one: a session's attachment may be replaced in full, taking effect from the next tool call (REQ-HOOKS-069), and a hook may be switched off for the remainder of the session by the failure budget (REQ-HOOKS-055). A change to the external-hooks policy file (REQ-HOOKS-115, REQ-HOOKS-116) made while a run is under way SHALL NOT affect that run: the agent and per-hook toggles are read once, when the run's hook set is assembled, and never again, so clearing a checkbox governs runs started afterwards only (REQ-HOOKS-109, REQ-HOOKS-117). This is a third within-session change only in appearance; the run's set is unchanged by it.

- **REQ-HOOKS-132** — The stable hook id SHALL be unique within one loaded configuration, SHALL be unaffected by neighbouring entries being switched off, and SHALL be the key that links warnings, diagnostics files, wire events, the switched-off set, the desktop policy toggles, and the start-up snapshot to one another.

- **REQ-HOOKS-133** — Text drawn from configuration or from tool arguments SHALL be masked per REQ-HOOKS-061 and REQ-HOOKS-062 wherever it is carried. The channels that carry such text are exactly these six: the JSON payload on a hook's standard input, at every level of it (REQ-HOOKS-060); the `command` recorded for each hook in the launch audit (REQ-HOOKS-118); the `stdout` and `stderr` recorded in each `hook_run` timeline entry (REQ-HOOKS-119); the `command` field of `hook.start` (REQ-HOOKS-124); the `output` field of `hook.finish` (REQ-HOOKS-125); and the hook data reported by the desktop trust summary (REQ-HOOKS-105), which the invocation list of REQ-HOOKS-137 also displays. It follows that, given a hook whose command contains `--token ghp_example` and a tool argument containing `api_key=secretvalue`, neither `ghp_example` nor `secretvalue` SHALL appear in the payload the hook reads, in the launch audit, in the timeline, in anything exported from either, or in any event on the session stream.

- **REQ-HOOKS-134** — Directions of failure are fixed: reading a trust decision defaults to "not approved" when anything is wrong; failing to write a trust decision is reported rather than absorbed, since an absorbed rejection would leave hooks running; and a hook that fails to execute lets the agent carry on (warning, then proceed) — except a `required` pre-tool hook that returned no verdict, which stops the call.

### Performance Contracts

- **REQ-HOOKS-135** — Validating hook configuration (REQ-HOOKS-012), resolving the effective hook set (REQ-HOOKS-013 to REQ-HOOKS-018), computing a workspace fingerprint (REQ-HOOKS-091), and building a payload (REQ-HOOKS-063) SHALL each be possible with no run under way, and doing any of them SHALL leave every run untouched: no hook process is started, no wire event is published, no session diagnostics are written, and no run's hook set changes. Taken with REQ-HOOKS-041, REQ-HOOKS-073, and REQ-HOOKS-078, this bounds what a run does on account of hooks: a session with no hooks starts no process and writes no hook record for any event, and a session declaring hooks for one event builds payloads for that event alone. The numeric bounds are fixed by REQ-HOOKS-139.

- **REQ-HOOKS-139** — The numeric bounds of this domain SHALL be as follows, measured under one reference condition: a single execution thread on a contemporary developer workstation with a solid-state disk and a warm file-system cache, timing the named operation alone and excluding application start-up. Validating hook configuration (REQ-HOOKS-012), resolving the effective hook set (REQ-HOOKS-013 to REQ-HOOKS-018), computing a workspace fingerprint (REQ-HOOKS-091), and applying the trust gate (REQ-HOOKS-090) SHALL each complete within **50 ms** for a configuration declaring up to 100 entries across all scopes, and SHALL grow no worse than linearly in the number of entries beyond that. Building one payload (REQ-HOOKS-063) SHALL complete within **10 ms** for a payload carrying up to 100 KB of text after masking, growing no worse than linearly in the total length of the strings it carries. Deciding that an event occurrence has no applicable hook and returning (REQ-HOOKS-041, REQ-HOOKS-073, REQ-HOOKS-078) SHALL cost under **1 ms**, so a session with no hooks pays no measurable cost per call. The hooks settings tab and its status column (REQ-HOOKS-103), the trust summary (REQ-HOOKS-105), the review dialog (REQ-HOOKS-106), and the invocation list (REQ-HOOKS-137) SHALL each meet the product's interface responsiveness budget, measured from the user's gesture to the surface being usable. Nothing here bounds the wall-clock time spent inside a hook process, which is the user's own code and is bounded only by `timeout_seconds` and the grace period of REQ-HOOKS-033. This requirement is the product's single definition of the numeric bounds on hook work — the reference condition they are measured under, the 50 ms configuration bound at 100 entries, the 10 ms payload bound at 100 KB, and the 1 ms no-applicable-hook bound: a document that needs to state how fast any hook operation must be SHALL cite this identifier rather than restating a figure, and a new hook surface is added to this list rather than given a bound of its own. The interface responsiveness budget the hook surfaces meet is not this domain's own figure: it is the product-wide budget REQ-SHELL-150 fixes, which this requirement cites and holds no copy of, so the hook surfaces meet the same budget as every other surface rather than a budget of their own.
