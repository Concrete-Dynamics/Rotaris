# Model Providers, Sign-In, and Model Routing — Provider Catalog and Transparency Metadata

Part 1 of 7 of [domain 04](../04-model-providers-auth.md), which indexes every part. Defines REQ-PROVIDER-001 – REQ-PROVIDER-049.

## Requirements

### Provider Catalog and Transparency Metadata

- **REQ-PROVIDER-001** — The application ships a built-in catalog of exactly six providers with stable identifiers, in this fixed order: `concrete-cloud`, `copilot`, `codex`, `openai-compatible`, `claude-code`, `deepseek`. Their display names are, respectively: "Rotaris Cloud (recommended)", "GitHub Copilot", "OpenAI Codex", "OpenAI-compatible", "Claude Code (subscription)", "DeepSeek". Enumerating the catalog returns entries in that order, with the hosted provider first (it is the first row in the sign-in menu).

- **REQ-PROVIDER-002** — Every catalog entry carries this attribute set, and any read of the catalog on a given build returns the same values: identifier; display name; sign-in method; model-catalog (discovery) endpoint URL, which a `local-sdk` entry declares as absent (REQ-PROVIDER-005); discovery authorization header scheme, which is `Bearer` for every entry that declares a discovery endpoint; default API base URL, which a `local-sdk` entry likewise declares as absent; connection mode, mandatory and drawn from `hosted-cloud`, `direct`, `local-sdk`, `custom`; operator name (optional); privacy-policy URL (optional); availability, which reads available unless the build declares the entry unavailable; unavailability reason (optional). Discovery endpoint and base URL are independent attributes: a built-in entry's discovery URL is the one declared in REQ-PROVIDER-005 and need not equal `<base URL>/models`. Endpoint and base-URL values a user supplies for an `openai-compatible` instance are held against that instance (REQ-PROVIDER-052) and leave the catalog entry they were seeded from unchanged.

- **REQ-PROVIDER-003** — Catalog integrity is validated, and violations are rejected as errors: every built-in entry must declare a connection mode; hosted-cloud and direct entries must yield a non-empty destination hostname derived from their default base URL; a `local-sdk` entry must declare neither a discovery endpoint nor a default base URL, and a build that gives one either value is rejected; a custom-mode entry must NOT declare a fixed operator name; any entry marked unavailable must supply an unavailability reason.

- **REQ-PROVIDER-004** — Destination-host resolution: for local-sdk and custom modes the destination host is empty/none; for all other modes it is the hostname parsed from the default base URL (e.g. `rotaris.ai`, `api.githubcopilot.com`, `chatgpt.com`, `api.deepseek.com`).

- **REQ-PROVIDER-005** — Fixed per-provider endpoints and transparency metadata. Each built-in entry declares its discovery URL outright; for `deepseek` that URL deliberately differs from `<base>/models`, and deriving a discovery URL from a base URL (REQ-PROVIDER-053) applies only to user-supplied `openai-compatible` endpoints.
  - `concrete-cloud`: discovery `https://rotaris.ai/v1/models`, base `https://rotaris.ai/v1`, operator "Concrete Dynamics UG (haftungsbeschränkt)", privacy URL `https://rotaris.ai/privacy`.
  - `copilot`: discovery `https://api.githubcopilot.com/models`, base `https://api.githubcopilot.com`, operator "GitHub".
  - `codex`: discovery `https://chatgpt.com/backend-api/codex/models`, base `https://chatgpt.com/backend-api/codex`, operator "OpenAI".
  - `openai-compatible`: discovery `https://api.openai.com/v1/models`, base `https://api.openai.com/v1`. These are the values the sign-in prompt offers as defaults (REQ-PROVIDER-052); what an instance actually calls is the value stored for that instance.
  - `claude-code`: both fields are absent rather than holding a placeholder string — this entry declares no discovery URL and no default base URL at all (REQ-PROVIDER-003), so there is no value for any code path to dial and no sentinel string forms part of the contract. Its destination host is empty (REQ-PROVIDER-004) and its catalog is served offline (REQ-PROVIDER-047). Asking this entry for a discovery URL or a base URL SHALL yield nothing; a code path that requires one SHALL fail before opening any connection rather than falling back to another entry's value.
  - `deepseek`: discovery `https://api.deepseek.com/models`, base `https://api.deepseek.com/v1`, operator "DeepSeek".

- **REQ-PROVIDER-006** — The hosted provider `concrete-cloud` ships marked unavailable with unavailability reason "Rotaris Cloud is coming soon." This "coming soon" state is a static catalog attribute of the build, not a runtime probe: no health check, remote flag, configuration value, or user action ever flips it, and it changes only when a later build ships the entry marked available. Nothing in the running product writes the availability attribute.

- **REQ-PROVIDER-007** — Looking up an unknown provider id in the catalog is an error; listing the catalog preserves the fixed insertion order.

### Sign-In Methods, Token Model, and Status Classification

- **REQ-PROVIDER-008** — Each provider has exactly one sign-in method drawn from: device-code flow, browser authorization-code-with-PKCE flow, or API key. The mapping is: `copilot` → device code; `codex` → PKCE; `concrete-cloud` → PKCE (OIDC); `deepseek` → API key; `claude-code` → pasted subscription token (API-key style); user-defined OpenAI-compatible instances → API key.

- **REQ-PROVIDER-009** — Provider ids have no aliases: each built-in provider is addressable by exactly the identifier REQ-PROVIDER-001 gives it, and no alternative spelling of any id resolves. For an id outside the fixed mapping, sign-in resolution succeeds (as API-key style) only when the stored credential is tagged with the provider family "openai-compatible"; otherwise the id is unknown and a warning "Unknown auth provider: <id>" is logged. Querying the sign-in method for such an unknown id yields none.

- **REQ-PROVIDER-010** — A credential-status query answers with exactly one value out of the vocabulary `authenticated`, `unauthenticated`, `expired`, `refreshing`. Only the first three are ever returned: no credential state, clock reading, or concurrent operation makes a query answer `refreshing`. A status query sends no network traffic — with every provider host unreachable it returns the value it would have returned with connectivity — and its answer is fixed by the stored credential (REQ-PROVIDER-011) and the current system time alone, so two queries against the same stored credential at the same clock reading agree.

- **REQ-PROVIDER-011** — A stored credential comprises: an access token, a refresh token, an expiry expressed as a Unix timestamp where `0` means "no expiry" (API keys never expire), an optional account id, and a string-to-string extras map. A credential is expired when the current time is at or past the expiry timestamp, unless the expiry is `0`.

- **REQ-PROVIDER-012** — An interactive sign-in that needs the user to act shows one of two prompts. A device-code prompt shows the verification URI, the user code, the polling interval, and how long the code stays valid. A browser (PKCE) prompt shows the authorization URL to open. Every authentication attempt ends in exactly one outcome: success, or failure carrying a message shown to the user. Recording a provider last error follows REQ-PROVIDER-057, including REQ-PROVIDER-013's pre-contact exception.

- **REQ-PROVIDER-013** — An authentication attempt issued by a caller that cannot itself wait for the result must reach an outcome within 30 seconds; once that deadline passes the attempt is reported as failed and no credential is written. The reported failure SHALL convey that the attempt did not reach an outcome within the 30-second limit, which provider it was for, and that nothing was stored so a retry is safe; its exact wording is left to the implementation. When such an attempt fails before any provider has been contacted, the failure result is the only output: no traceback, warning, or other diagnostic is written to the log or shown anywhere in the interface.

- **REQ-PROVIDER-148** — Sign-in method vocabulary. A provider's sign-in method is exactly one of three machine-readable tokens — `device-code`, `browser-pkce`, `api-key` — and these are the values the mapping of REQ-PROVIDER-008 yields, the values recorded and compared wherever a method is stored, and the only values any surface branches on. Each token has exactly one user-visible label, used identically everywhere a provider's method is displayed (REQ-PROVIDER-140, REQ-PROVIDER-141, REQ-PROVIDER-142) and in every message that names a method. A label SHALL convey how the user completes that sign-in — a code shown by the application and entered at the provider's site, a browser page that completes the sign-in, or a key the user pastes — and SHALL NOT name a command; its wording is otherwise left to the implementation. A provider id that resolves to no method (REQ-PROVIDER-009) has neither token nor label, and surfaces describe it as having its authentication managed by model configuration (REQ-PROVIDER-118).

### Credential Persistence — Location, Format, Protection

- **REQ-PROVIDER-014** — Credentials are stored one JSON file per provider at `<per-user data directory for application "rotaris">/tokens/<provider_id>.json` (on Linux: `~/.local/share/rotaris/tokens/`). The credential directory is never located inside a workspace or repository, and the per-user data directory it sits in is the one REQ-STARTUP-145 fixes, which that requirement fixes as the per-user location local to this machine and not replicated to another machine or to another copy of the user's profile. This requirement relies on that property and does not state it for itself; the reason it relies on it is local, and is why the property matters here at all: the protection REQ-PROVIDER-016 applies to a file does not survive that file being replicated somewhere else. REQ-PROVIDER-063's staged gateway credentials sit under the same directory and inherit the same bound from the same place.

- **REQ-PROVIDER-015** — *Withdrawn.* A clean-room product has no earlier installation, directory, or product name to adopt from, so there is no legacy credential or state directory to rename; the per-user locations of REQ-PROVIDER-014 and REQ-PROVIDER-084 are the only ones ever read or written.

- **REQ-PROVIDER-016** — The credential store's protection is applied explicitly on every supported platform and is never left to inheritance. On POSIX systems the credential directory is created with mode `0700` and every credential file with mode `0600`: no group or other bit is ever set on either. On Windows no POSIX mode bits are set and none are reported; instead the credential directory and every file within it are created with an explicit access control list that grants full control to the owning user account and to the local system account and to no one else, with inheritance from the parent directory disabled, so protection does not depend on how the user profile directory happens to be configured. If the required protection cannot be applied, the credential is NOT written: the operation fails and reports an error naming the credential store path and stating that no credential was stored.

- **REQ-PROVIDER-017** — The credential file is a JSON object with keys `access_token`, `refresh_token`, `expires_at`, `account_id`, and `extra` (an object of strings), serialized with 2-space indentation. Loading tolerates a missing `expires_at` (defaults to 0.0), missing `account_id`, and missing `extra`. A corrupt or key-missing file logs a warning that names the provider id but never the file contents, and is treated as no credential (unauthenticated).

- **REQ-PROVIDER-018** — Credential writes are atomic: a reader of `<provider_id>.json` sees either the previous content or the complete new content, never a partial or truncated file, and a write that fails leaves the previous file untouched. The new content is staged in a temporary file inside the credential directory whose name starts with the provider id and ends in `.tmp`, carries mode `0600` on POSIX, and is renamed onto `<provider_id>.json`; a failed write deletes that temporary file and reports the error. The credential directory MAY also hold the adjacent coordination lock files owned by REQ-PROVIDER-152. Each completed operation MUST remove its own temporary files; overlapping operations retain their active staging and lock files. Credential enumeration MUST include only provider JSON files. Exclusive read-modify-write locking and dead-owner reclamation remain governed by REQ-PROVIDER-152.

- **REQ-PROVIDER-019** — Deleting a stored credential removes the file if present and logs "Deleted stored tokens for <id>". A credential-existence check is a pure file-existence test. Enumerating stored provider ids returns the sorted basenames (without extension) of `*.json` files in the credential directory.

### GitHub Copilot Sign-In (Device Code + Session Exchange)

- **REQ-PROVIDER-020** — Copilot sign-in uses the OAuth Device Flow (RFC 8628) against `https://github.com/login/device/code` and `https://github.com/login/oauth/access_token` with the fixed client id `Iv1.b507a08c87ecfe98`. No `scope` parameter is sent.

- **REQ-PROVIDER-021** — Device-code request and poll requests carry headers `Accept: application/json`, `User-Agent: GithubCopilot/0.28.0`, `Editor-Version: vscode/1.99.1`, `Editor-Plugin-Version: copilot-chat/0.28.0`, with a 30-second HTTP timeout.

- **REQ-PROVIDER-022** — The user prompt presents the server's verification URI, user code, poll interval, and prompt lifetime; when the server omits the lifetime it defaults to 900 seconds.

- **REQ-PROVIDER-023** — Polling semantics: sleep `interval + 3.0` seconds per cycle. On `authorization_pending`, continue. On `slow_down`, adopt the server's new interval when it is a positive integer, otherwise add 5 seconds to the current interval. Any other error code fails the flow with that error string. A non-200 poll response fails with "Token poll HTTP <status>". A triggered cancellation signal aborts with error "Cancelled by user".

- **REQ-PROVIDER-024** — The device flow must yield a GitHub App user token prefixed `ghu_`. Any other prefix is rejected immediately with an error stating the prefix seen and that the client id is probably not a GitHub App. A stored token whose prefix is anything other than `ghu_` classifies as unauthenticated (REQ-PROVIDER-027), forcing the user back through the device flow.

- **REQ-PROVIDER-025** — Immediately after the device flow the `ghu_` token is traded for a short-lived bearer scoped to Copilot's model API: `GET https://api.github.com/copilot_internal/v2/token`, header `Authorization: token <ghu_ token>`, 15-second timeout. The response supplies the bearer, its expiry as a Unix timestamp, the API base host to use for that account's tenant (it differs between individual and business/enterprise accounts), and an optional SKU string. The expiry stored is always the one the response gives; no fixed bearer lifetime is assumed anywhere, and the credential counts as expired 60 seconds ahead of it (REQ-PROVIDER-027). HTTP 401 and HTTP 404 are both authorization failures — 404 is the status returned both for a token that is not a GitHub App user token and for an account with no Copilot entitlement. Every other status, and any body that is not JSON, is a transient error. When no bearer can be obtained, sign-in fails with "Copilot session exchange failed: <detail>".

- **REQ-PROVIDER-026** — The persisted Copilot credential layout: access token = session bearer; refresh token = the durable `ghu_` token from the device flow; expiry = bearer expiry; extras record the tenant API base under key `api_base` and optionally the SKU under key `sku`.

- **REQ-PROVIDER-027** — Copilot status classification: empty access token → unauthenticated; a refresh token present but not `ghu_`-prefixed → unauthenticated (forces re-auth); expiry ≤ 0 → expired (a session bearer always carries an expiry, so its absence is treated as unusable); within 60 seconds of expiry → expired; otherwise authenticated. Non-interactive refresh puts the stored `ghu_` token back through the session exchange of REQ-PROVIDER-025 to obtain a new bearer and expiry; a missing or non-`ghu_` refresh token fails with "Stored token cannot be refreshed; re-authentication required".

### OpenAI Codex Sign-In (Authorization Code + PKCE)

- **REQ-PROVIDER-028** — Codex sign-in uses browser PKCE against issuer `https://auth.openai.com` with client id `app_EMoamEEZ73f0CkXaXp7hrann`. The authorization URL carries: `response_type=code`, the client id, the redirect URI, scopes `openid profile email offline_access api.connectors.read api.connectors.invoke`, an S256 PKCE challenge whose verifier is 43 characters drawn from the RFC 7636 unreserved set, `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, a 32-byte URL-safe random state, and `originator=codex_cli_rs`.

- **REQ-PROVIDER-029** — The local callback server binds `127.0.0.1` on a port taken from a build-declared ordered list of fixed ports, tried in order; the build ships the list `1455, 1457` for `codex`, because the redirect URI must be one the identity service already accepts and a dynamically assigned port therefore cannot be used. No port outside the declared list is ever bound for this flow. If every listed port is busy, authentication fails with an error that names the ports it tried and states that one of them must be free for sign-in to complete. Changing the declared list is build data, not a change of behavior. The callback path is `/auth/callback`.

- **REQ-PROVIDER-030** — Callback handling: requests to other paths receive HTTP 404. An `error` query parameter fails the flow with the error description (or the error code) and renders an HTML page "Authentication Failed / You can close this tab." A missing `code` renders "Error / No code received." Success renders "Success! / You can close this tab." and captures the code. A state mismatch is treated as CSRF: it is logged and the flow yields no code.

- **REQ-PROVIDER-031** — The flow waits at most 300 seconds for the callback. A cancellation request ends the wait with "Cancelled by user"; expiry of the 300 seconds ends it with "Authentication timed out", or with the error the callback recorded when there is one. However the wait ends — code received, cancelled, or timed out — the loopback listener is closed and its port released before the sign-in call returns, on every supported operating system: the call always returns rather than hanging, and a sign-in started immediately afterwards binds port 1455 (or 1457) successfully.

- **REQ-PROVIDER-032** — Code exchange POSTs `grant_type=authorization_code` together with the PKCE verifier to `<issuer>/oauth/token` with a 30-second timeout. Any response other than HTTP 200 fails with "Token exchange HTTP <status>". On success the token lifetime comes from the response and is 3600 seconds when the response omits it. The account id is taken from the JWT claims of the id token first and of the access token second, using the first of these that is present: a top-level `chatgpt_account_id` claim; `chatgpt_account_id` inside the `https://api.openai.com/auth` claim object; the first entry of an `organizations` claim list. When none of them yields a value, sign-in still succeeds and the credential is stored without an account id, which later requests then omit (REQ-PROVIDER-076, REQ-PROVIDER-124). Extras record `auth_mode="chatgpt"`, `requested_scopes` (the scope string that was requested), and `scope` (the granted scope string) whenever the response returns one.

- **REQ-PROVIDER-033** — Codex refresh POSTs `grant_type=refresh_token`. Failures yield "Token refresh failed: HTTP <status>" or "Refresh request failed: <exc>". Success keeps the previous refresh token when the response omits one, and re-derives the account id.

- **REQ-PROVIDER-034** — Codex credential status: an empty access token reads unauthenticated; a credential whose expiry has passed reads expired; any other stored credential reads authenticated. The scopes a credential was granted never affect this answer — a credential granted fewer scopes than were requested still reads authenticated, and no request is refused locally on scope grounds. The absence of a local scope check is the intended contract: only the provider knows what a grant permits, so the product never second-guesses it. A provider that refuses a request for want of a scope surfaces its own refusal through the requirement that owns that call, and a refusal carrying HTTP 401 or 403 takes the credential-hygiene path of REQ-PROVIDER-098.

- **REQ-PROVIDER-035** — A token-exchange operation (RFC 8693) trades a stored id token for an API key beginning `sk-`, requesting the OpenAI API-key token type. When the exchange is refused with error `invalid_subject_token` and a message naming a missing `organization_id`, the message reported to the user instead tells them to select or create an organization with the provider and then re-authenticate Codex from provider settings (REQ-PROVIDER-141). Every other refusal is reported with the HTTP status and the provider's own message, the response body being cut to its first 500 characters before it is shown or logged. The exchange has exactly one trigger: it runs on demand, immediately before a request for a configured model that names `codex` as its sign-in provider and is dispatched against an API-key-style endpoint rather than the subscription endpoint, and it runs nowhere else. The derived `sk-` key lives in process memory for the lifetime of the process only — it is never written to the credential store, the snapshot, a log, an event, or any other file (REQ-PROVIDER-086, REQ-PROVIDER-131) — and it is re-derived when it is rejected or when the process restarts. A failed exchange fails that model call alone and never deletes or invalidates the stored codex credential.

- **REQ-PROVIDER-036** — Sign-in surfaces brand the codex provider "(Sign in with ChatGPT)": the display label becomes "OpenAI Codex (Sign in with ChatGPT)", and when the PKCE prompt carries no user code, the prompt message is "Sign in with ChatGPT to authenticate Codex."

### Rotaris Cloud Sign-In (OIDC PKCE, Coming-Soon Gating)

- **REQ-PROVIDER-037** — Rotaris Cloud sign-in uses OIDC Authorization Code + PKCE with public client id `rotaris-ai`. The issuer is a configuration value on the layered YAML configuration surface (any trailing slash stripped), and the API base is a configuration value defaulting to the catalog's `concrete-cloud` base `https://rotaris.ai/v1`. Where the environment variables `ROTARIS_OIDC_ISSUER` and `ROTARIS_API_BASE_URL` are present in the environment the application was started with, each overrides the corresponding configured value, so a deployment can point the flow at a different issuer without editing configuration. When neither route supplies an issuer, authentication fails before any request with a message stating that the Rotaris Cloud issuer must be configured before sign-in and naming the configuration key that supplies it.

- **REQ-PROVIDER-038** — OIDC discovery performs `GET <issuer>/.well-known/openid-configuration` with a 30-second timeout. The response must be JSON; its `issuer` must equal the configured issuer exactly (else "OIDC discovery issuer did not match configured issuer"); and it must supply `authorization_endpoint`, `token_endpoint`, and `revocation_endpoint` (else "OIDC discovery omitted a required endpoint").

- **REQ-PROVIDER-039** — Unlike codex, the cloud loopback callback binds an ephemeral port on `127.0.0.1` with path `/callback`, and the flow itself opens the system default browser in addition to delivering the URL through the prompt callback. Callback wait timeout is 300 seconds. The success page SHALL state that authentication succeeded, that the browser tab can be closed, and that the user should return to the Rotaris window; its exact wording is left to the implementation.

- **REQ-PROVIDER-040** — Token exchange and refresh both target the discovered token endpoint with the public client id and no client secret. The stored credential's extras record `issuer`, `token_endpoint`, `revocation_endpoint`, and `api_base` so refresh and revocation work without re-discovery. A stored credential missing this endpoint metadata refuses to refresh with "Stored OIDC token endpoint is missing" / "Stored OIDC metadata is incomplete". When the token response omits a lifetime, the default is 900 seconds.

- **REQ-PROVIDER-041** — Sign-out for `concrete-cloud` first attempts best-effort remote revocation: a POST of the refresh token with `token_type_hint=refresh_token` to the stored revocation endpoint, 10-second timeout. Any revocation failure is logged at debug level and never blocks local credential deletion.

- **REQ-PROVIDER-042** — *Withdrawn.* Its only surface was the command-line provider menu; the coming-soon marking of the hosted provider in the chooser, and the refusal to authenticate it, are carried by REQ-PROVIDER-142, and the desktop health check, authenticate action, and add-provider dialog by REQ-PROVIDER-043.

- **REQ-PROVIDER-043** — Desktop coming-soon gating: both the provider health check and the authenticate action short-circuit for the unavailable cloud provider, returning the provider status `coming_soon` of REQ-NOTIFY-200 with availability false and the unavailability reason as detail. The desktop "Add provider" dialog also excludes the cloud provider (and the generic openai-compatible family) from its built-in list.

### Claude Code Subscription Provider (Pasted Token, Local Runtime)

- **REQ-PROVIDER-044** — The `claude-code` provider mints no token of its own. Whenever the credential subsystem asks that provider to authenticate — which is every caller other than the paste-token sign-in of REQ-PROVIDER-046 — the attempt fails with a message telling the user to mint a subscription token with the external Claude Code tool's `claude setup-token` command and then paste it into that sign-in. Its refresh step makes no external call: it succeeds and returns the stored token when one is stored, and fails when none is.

- **REQ-PROVIDER-045** — Subscription-token validation: an empty token → "Subscription token is required. Run 'claude setup-token' to mint one."; the token must be a legal ASCII header value (see REQ-PROVIDER-062); a token starting `sk-ant-api` is rejected with an explanation that it is an Anthropic API key and would bill the API rather than the subscription; anything not starting `sk-ant-oat` is rejected with "Expected a subscription OAuth token starting with 'sk-ant-oat' (minted by 'claude setup-token')." Status classification reuses this validation — an invalid stored token reads as unauthenticated.

- **REQ-PROVIDER-046** — The `claude-code` paste-token sign-in, reached from the sign-in action of REQ-PROVIDER-142, is the one path that stores a subscription token, and it takes that token from the user rather than from the provider's authenticate step (REQ-PROVIDER-044). It shows numbered setup instructions — install and sign in to the external Claude Code tool, run `claude setup-token`, paste the `sk-ant-oat` token it prints — and states that the token is kept locally with owner-only file permissions (mode `0600` where the platform has them, REQ-PROVIDER-016) and is never written to workspace files, logs, or session snapshots. It then prompts for the token with the input hidden under the label "Claude Code subscription token (sk-ant-oat...)", applies the validation of REQ-PROVIDER-045, and runs offline model discovery (REQ-PROVIDER-047).

- **REQ-PROVIDER-047** — Claude-code model discovery is static and offline: after token validation it returns a fixed catalog of exactly three version-independent aliases — `opus` ("Claude Opus (subscription)"), `sonnet` ("Claude Sonnet (subscription)"), `haiku` ("Claude Haiku (subscription)") — with qualified ids `claude-code/<alias>`, no network call, and no HTTP status.

- **REQ-PROVIDER-048** — Conflicting-credential precheck: the presence of any of the environment variables `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, or an `apiKeyHelper` entry in `~/.claude/settings.json`, outranks the subscription token in the external tool's own credential chain; if any is present, the subscription runtime refuses to run with a credential-conflict error naming the conflicting sources and suggesting remediation (e.g. `unset ANTHROPIC_API_KEY`, remove apiKeyHelper). This check runs before every subscription-runtime prompt.

- **REQ-PROVIDER-049** — The subscription runtime injects the stored token as environment variable `CLAUDE_CODE_OAUTH_TOKEN` for the external local-runtime subprocess. This domain fixes no per-model parallelism default of its own and holds no list of provider names that carry one: the cap in force for a model is the one its provider's catalogue entry declares, under REQ-MONITOR-021. A catalogue entry that declares no cap leaves the models configured against it unbounded, and a cap the user sets for a model replaces whatever the entry declared.
