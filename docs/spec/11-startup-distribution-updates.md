# Application Startup, Distribution, and Updates

## Overview

Rotaris ships as a standalone desktop application on three platforms — Windows, macOS, and Linux — every artifact of a release carrying that release's single product version. It is a graphical application only: it exposes no command-line interface, no subcommands, no flags and no text-mode interface, and every capability it offers is reached from the desktop. At most one instance of it runs per user account: launching it again surfaces the instance that is already running instead of starting a rival, and the several workspaces and several windows a user works in are windows of that one instance. On first launch of a standalone build, the desktop paints immediately, then runs a visible, cancellable, resumable machine-setup pass that probes for required tools (Git, ripgrep, Node-provided package runners), provisions pinned tool versions into a per-user managed directory, and warms MCP package caches — when a tool is unavailable only the features that need it lose capability, and the application itself is never held back. The single-file portable artifact may prepare itself once for launching and start from that preparation afterwards; the preparation is held in per-user machine-local storage and never beside the artifact, so the artifact still runs from read-only and removable media, and only the run that prepares is exempt from the first-paint budget — a run that could prepare no copy at all is exempt on the same terms and is the one preparation outcome the product tells the user about. Opening a workspace held on storage another machine can reach, or that a synchronisation agent replicates, is warned about and never refused. A supported standalone desktop build performs exactly one silent update check per launch, issued against the product's public release feed once the window is visible; a newer release is offered through a dismissible, non-blocking banner that can download, verify the release's checksum manifest against a signing key the application itself carries and the downloaded asset against that manifest, and apply the update to the artifact the launch started from, using a strategy appropriate to the installation flavour. The artifacts themselves carry no code signature and the platform's own first-launch trust prompts are unchanged by that; what the signed manifest adds is who published a release, which the checksums alone never established. An opt-in diagnostics flag records a bounded, content-free UI trace to disk.

## Requirements

### Product identity, entry points, and version reporting

**REQ-STARTUP-001** — *Withdrawn.* It required publication as two packages of one language ecosystem, which describes a different product: this product is a single desktop application, and the form in which it is packaged and published is an architecture decision rather than a behavior a user observes. What it protected — that a release carries exactly one product version, which every artifact of that release declares — is carried by REQ-STARTUP-158, and the guard that enforces it is REQ-STARTUP-028.

**REQ-STARTUP-002** — Exactly one executable entry point SHALL exist and be shipped as a standalone binary: the desktop application `rotaris`, which on Windows opens no console window. No console, headless, benchmark or other secondary executable SHALL be published, and no installation SHALL make one available. The one exception is not an entry point a user invokes: the application launches its own executable as a child process to host the bundled code-intelligence tool server, on the terms of REQ-MCP-033 and REQ-STARTUP-015.

**REQ-STARTUP-003** — *Withdrawn.* Its only surface was a command-line invocation of the application as a module of its language runtime, which this product does not offer; the single desktop entry point is REQ-STARTUP-002.

**REQ-STARTUP-004** — The product SHALL report its version from its own installation metadata. When that metadata is absent, the reported version SHALL be the literal string `0+unknown`. Standalone bundles SHALL always report the true release version and never `0+unknown`.

**REQ-STARTUP-005** — *Withdrawn.* Its only surface was a command-line flag writing to standard output and setting a process exit code, neither of which this product has; reading the running version is carried by REQ-STARTUP-007 and by the About surface of REQ-SHELL-140, which presents it as selectable text with no window construction or network activity of its own.

**REQ-STARTUP-006** — *Withdrawn.* Its only surface was a console subcommand, and the automatic pre-step it excepted itself from was withdrawn with REQ-STARTUP-100; reading the running version is carried by REQ-STARTUP-007 and REQ-SHELL-140.

**REQ-STARTUP-007** — The running desktop SHALL treat its own version as: the version its own installation metadata declares (REQ-STARTUP-004); else the literal `dev` when no such metadata is present; and exactly `0.1.0` in demo mode (REQ-SHELL-162). This value SHALL be the one the About surface presents (REQ-SHELL-140) and the one compared against the release feed. When the running version is not a parseable release version (e.g. `dev`), the update comparison is unanswerable and no update SHALL ever be offered (see REQ-STARTUP-109).

**REQ-STARTUP-158** — A release SHALL carry exactly one product version. Every artifact that release publishes SHALL declare, and SHALL report at run time, that same version, and a release in which any published artifact declares a version other than the release's SHALL NOT be publishable; the pre-build guard of REQ-STARTUP-028 is where that is decided, and REQ-STARTUP-031 is where the version appears in each artifact's name. This requirement fixes how many versions a release has and says nothing about the form in which the product is packaged or the channel through which it is published, neither of which is a behavior a user observes.

**REQ-STARTUP-159** — What the user installs SHALL be self-contained, and the user SHALL be able to install the product and run it with nothing else installed and nothing else fetched. On a machine of any platform key of REQ-STARTUP-030 (on Linux, the baseline of REQ-STARTUP-024) carrying no separately installed language runtime, framework, or component of the product obtained by any other route, and with all outbound network access blocked, installing that platform's published artifact and starting it SHALL produce each of these observations: the desktop entry point paints its main window (REQ-STARTUP-002); its About surface presents the true release version and never `0+unknown` (REQ-STARTUP-004, REQ-STARTUP-007, REQ-STARTUP-158, REQ-SHELL-140); and every data asset the product reads at run time resolves from within what was installed, with no additional download — the pricing and model tables, the prompt templates, the CA root bundle used for setup downloads (REQ-STARTUP-083), the font families registered at startup (REQ-STARTUP-040), the keys against which a release's manifest signature is verified (REQ-STARTUP-167), and `THIRD-PARTY-LICENSES.txt` (REQ-STARTUP-141). "From within what was installed" reaches an asset the artifact resolved out of a preparation it made of itself, and equally one it resolved out of the run-scoped placement a run that could make no preparation puts its payload in (REQ-STARTUP-165), each of those being derived from the artifact alone and fetching nothing; it does not reach anything obtained from the network or from a separately installed component. No startup path SHALL fail, and no startup path SHALL exit non-zero, because installation or version metadata for a component of the product is unavailable. The machine tools of REQ-STARTUP-058, the package caches of REQ-STARTUP-064, and the language servers the bundled code-intelligence runtime provisions at the first use of a language (REQ-MCP-118) are the only things fetched after installation, and only where the machine does not already supply them; their absence degrades individual capabilities without preventing this first run (REQ-STARTUP-077). The runtime itself is inside what was installed (REQ-STARTUP-015, REQ-MCP-033); its language servers are obtained by the runtime's own providers, into the per-user data directory of REQ-STARTUP-145, only when a symbol-level tool is first used for that language, and are declared in the setup manifest (REQ-STARTUP-058) and listed by REQ-STARTUP-142 like the machine tools are. A language whose server is absent loses that language's symbol-level tools and nothing else: the runtime's pattern-search and memory tools keep working, the failure is the server's own error result and never a host failure (REQ-MCP-113), and this first run is unaffected. *Amended 2026-09-06 under ESC-32 (IC-7 adopted, option 2): the sentence previously read "The machine tools of REQ-STARTUP-058 and the package caches of REQ-STARTUP-064 are the only things fetched after installation"; the bundled runtime's first execution (ADR-0035) measured that the runtime obtains its language servers at first use, and the owner ruled them tools provisioned after installation rather than payload to bundle.*

### Standalone build command

**REQ-STARTUP-008** — A single version-controlled build command per OS SHALL produce the standalone binary. This command is maintainer-side release tooling driven by the release pipeline of REQ-STARTUP-027; it is not a surface of the shipped product and is reachable by no user of the application. On success it SHALL print `{target} ({mode}) -> {artifact_path}` to stdout and exit 0.

**REQ-STARTUP-009** — Build error semantics: an unknown target SHALL be rejected before any build work begins, with a message naming the valid targets; a missing build configuration SHALL fail naming the expected path; a failure of the underlying freeze step SHALL be reported with its exit code, never swallowed. All handled failures SHALL print `error: <reason>` to stderr and exit 1. Command-line usage errors (unknown subcommand or choice) SHALL exit 2.

**REQ-STARTUP-010** — A bundle-mode value other than exactly `onedir` or `onefile` SHALL be rejected as an error (typos never fall back to a default).

**REQ-STARTUP-011** — Artifact locations relative to the output directory: `onefile` produces `<dist>/<target>[.exe]`; `onedir` produces `<dist>/<target>/<target>[.exe]`. The default output directory SHALL be `dist/` in the checkout.

**REQ-STARTUP-012** — *Withdrawn.* It stated the self-containment claim in terms of one language ecosystem — an absent interpreter and two uninstalled packages of that ecosystem — which describes a different product. The claim itself is behavior a user observes and is preserved in full, technology-neutrally, by REQ-STARTUP-159: same platform baseline, same blocked network, same first paint, same true release version on the About surface, same run-time data assets resolving from what was installed, and the same prohibition on a startup path failing for want of installation metadata.

**REQ-STARTUP-013** — Bundle mode SHALL be assigned per artifact as follows: the Windows portable executable of REQ-STARTUP-031 SHALL be the only artifact published in `onefile` mode — observable as a single executable file that runs with no support tree beside it; the payload wrapped by the Windows installer, the payload inside the macOS disk image, and the payload inside the Linux AppImage SHALL each be a `onedir` tree — observable as the layout of REQ-STARTUP-011, the executable sitting inside a directory together with its support files. Every other published artifact SHALL likewise carry a `onedir` payload; no artifact besides the Windows portable executable SHALL be a `onefile` bundle.

**REQ-STARTUP-014** — The macOS desktop build SHALL be produced as an application bundle named `rotaris.app` with bundle identifier `ai.rotaris.app`.

**REQ-STARTUP-015** — Bundled tool-server hosting: the bundled code-intelligence server SHALL be launched by the application as a child process of its own, on the terms REQ-MCP-033 fixes. This domain relies on that requirement for how the launch is performed and for the reserved command token it turns on, and states no launch mechanism of its own. What this domain fixes is what the launch is observable as: the server is started from what the user installed and needs nothing fetched or separately installed to run (REQ-STARTUP-159); the reserved token is a sentinel for a child process the product starts internally, not a user-facing invocation, and no argument vocabulary beyond it is defined for the shipped executable (REQ-STARTUP-002); and a process started as that child presents no user interface and opens no window (REQ-MCP-033, REQ-MCP-113). Exactly one copy of the bundled tool server's license text SHALL be present inside the desktop bundle (REQ-STARTUP-142).

### Windows installer and portable executable

**REQ-STARTUP-016** — The Windows installer SHALL install strictly per-user with no elevation prompt: default install location `%LOCALAPPDATA%\Rotaris`, with the chosen directory remembered in the per-user registry under `HKCU\Software\Rotaris` (value `InstallDir`). Per-user installation SHALL allow the in-app updater to replace files without administrator rights.

**REQ-STARTUP-017** — Interactive installation SHALL flow Welcome → Directory → Install → Finish, warn on abort, and offer a checked-by-default "Launch Rotaris" checkbox on the Finish page. Silent installation (`/S`, with optional `/D=<dir>` to set the directory) SHALL show no pages and never auto-launch the app.

**REQ-STARTUP-018** — Installation SHALL: copy the application tree into the install directory; create a Start Menu folder `Rotaris` containing shortcuts `Rotaris` (to the app) and `Uninstall Rotaris`; write a per-user uninstall registry entry under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` with `DisplayName`, `DisplayVersion`, `Publisher` = `Rotaris`, `DisplayIcon`, `UninstallString`, `NoModify`=1, `NoRepair`=1; and write an `Uninstall.exe` into the install directory.

**REQ-STARTUP-019** — Uninstallation (including silent `Uninstall.exe /S`) SHALL remove only what installation created: the shortcuts, the installed tree, the uninstaller, the install directory only if it is then empty, and both registry keys. Per-user configuration and data directories and per-workspace `.rotaris/` state SHALL never be touched by uninstall.

**REQ-STARTUP-020** — The Windows portable artifact SHALL be a single self-contained executable that runs from any location when double-clicked, without installation.

**REQ-STARTUP-165** — An artifact published in `onefile` mode (REQ-STARTUP-013) MAY prepare itself once for launching and start from that preparation on every later run of the same artifact. The first-paint bound of REQ-STARTUP-155 is what makes such a preparation necessary rather than merely permitted, because only the run that performs it is exempt from that bound. Where an artifact prepares itself, all of the following SHALL hold, and they are the whole of what this document fixes about it: the form a preparation takes, what it is called, and where within the storage named below it is placed are implementation choices, and no user-facing surface of this product exposes any of them.

(a) *It never lands beside the artifact.* The preparation SHALL be held in the per-user data directories of REQ-STARTUP-145, which that requirement fixes as the per-user location local to this machine and not replicated to another machine — a property this clause relies on and does not state for itself, because a replicated preparation would be a payload one machine prepared, appearing under another machine's per-user directories. It SHALL NOT be written into the directory the artifact was launched from, onto the medium carrying the artifact, or anywhere else that travels with the artifact. Starting the artifact SHALL write nothing to that directory and nothing to that medium. It follows, and SHALL be observable, that the artifact starts and runs when launched from read-only media and from removable media; that such a medium is left byte-for-byte unchanged by starting the artifact from it; and that the artifact remains exactly what REQ-STARTUP-013 and REQ-STARTUP-020 require of it — a single executable file that runs with no support tree beside it. A preparation is not a published artifact: it is never offered for download, never listed in a checksum manifest, and its existence changes nothing about the closed artifact set of REQ-STARTUP-031 or about what a user copies when they copy the artifact.

(b) *A different artifact prepares afresh.* A preparation belongs to exactly the artifact that produced it. An artifact SHALL start from a preparation only where that preparation was produced by an artifact of identical content, so that a new version and a rebuilt artifact of the same version each prepare afresh; running a given artifact SHALL always run that artifact's own code, whatever has run on the machine before it. A preparation belonging to an artifact that is no longer run SHALL be identifiable as belonging to that artifact, so that it can be removed without disturbing any other, and removing it SHALL be indistinguishable from that artifact never having prepared (clause (c)).

(c) *An unusable preparation is redone, never reported; a preparation that cannot be made at all is reported.* A preparation that is incomplete, unreadable, or not the one belonging to this artifact SHALL cause the artifact to prepare again, and SHALL NOT cause the launch to fail, to warn, or to report anything at all to the user. Preparing is the recovery path and SHALL never be the failure path. Deleting or corrupting a preparation between runs SHALL therefore cost at most one repeated preparation, and SHALL never prevent the artifact from starting nor cause it to run any code but its own.

Where a run produces no usable preparation at all — the storage of clause (a) refusing the write, being full, or being unavailable, so that redoing it does not succeed either — that run SHALL still start the artifact and SHALL run it with every behavior of clause (f) unchanged. Not being able to prepare SHALL never be a reason the product does not run, and SHALL never cause the launch to fail. Such a run SHALL be exempt from the first-paint bound on the terms REQ-STARTUP-155 states, because it performs exactly the work a preparation exists to avoid.

Such a run still has to put what the artifact carries somewhere before it can run it, because that payload cannot be executed without existing as files. What it places is **not** a preparation and SHALL NOT be kept as one: it SHALL serve that one run, SHALL be removed when the run ends, and SHALL never be started from again, so the next launch of that artifact does exactly what this one did rather than inheriting anything from it. Where it may go is a closed set of two, and this clause is where that set is fixed. It SHALL be placed in per-user storage of the machine that ran the artifact: the per-user data directories of REQ-STARTUP-145, which is where it goes wherever they will accept it; or, only where those directories accept no write at all, the storage the platform designates for a user's transient files. There is no third permitted location, and no reading of this clause admits one. Every prohibition of clause (a) that protects the artifact holds over that placement unchanged — it SHALL NOT be written into the directory the artifact was launched from, onto the medium carrying the artifact, or anywhere else that travels with the artifact — and it SHALL raise no elevation prompt (REQ-STARTUP-087). It SHALL NOT be placed in storage replicated to another machine or to another copy of the user's profile. That prohibition is stated here rather than left to clause (a) because only the **first** of this clause's two permitted locations inherits it: the per-user data directories carry it from REQ-STARTUP-145, and the platform's transient-files storage is not those directories and inherits nothing from that requirement, so it is bound by this sentence instead. What the notice below names is still the storage a preparation could not be made in, never the placement this paragraph permits, which stays an implementation choice under this requirement's preamble exactly as a preparation's placement does. Where neither kind of storage accepts any write, there is nowhere on that machine the artifact's contents can be run from at all, and this clause's obligation to start is not reached. That bounds the sentence above which says not being able to prepare is never a reason the product does not run: that sentence is about preparing, and this residual case is a machine with no per-user storage that will accept a write of any kind, which no build can start from and for which this document fixes no behavior.

That outcome SHALL be reported, and it is the one preparation outcome that is: once per such run, after the window is painted, on the persistent, non-modal, non-blocking notice surface the update offer of REQ-STARTUP-116 appears on, at warning severity. The notice SHALL convey three things, its wording left to the implementation: that the artifact could not prepare itself and is therefore starting the slow way; which storage it could not prepare into, named as the per-user data location of clause (a) and REQ-STARTUP-145 and never as the placement within it, which stays an implementation choice under this requirement's preamble; and that every launch will cost what this one cost until that storage accepts a preparation. It SHALL NOT state or imply that the artifact cannot be used. Without this the recovery path degenerates into preparing on every launch, silently, and a user sees only an artifact that has become permanently slow with nothing anywhere saying why.

(d) *Preparing needs nothing the artifact did not bring, and no elevation.* The preparation SHALL be produced from the artifact alone. It SHALL issue no network request, so REQ-STARTUP-159's claim — that the artifact starts and runs on a machine carrying no separately installed component of the product and with all outbound network access blocked — holds for the run that prepares exactly as for every later run. Preparing SHALL raise no elevation prompt and SHALL write nothing outside the per-user directories of REQ-STARTUP-145 (REQ-STARTUP-087). That prohibition governs a preparation — the thing this requirement keeps between runs — and it has exactly one exception, which is the run-scoped placement clause (c) permits where those directories accept no write at all, itself bounded by clause (c)'s own closed set of two locations and by every prohibition of clause (a) that protects the artifact. That single exception is stated so a build has somewhere lawful to put a payload it must run, and it licenses nothing further: no other write of any kind leaves the per-user directories of REQ-STARTUP-145, and neither clause may be read as permitting a write to a location neither of them names.

(e) *The artifact stays the thing that is updated.* A run started from a preparation SHALL be able to identify the artifact file the launch started from. That file, and never the preparation, is the update target REQ-STARTUP-106 classifies and the thing REQ-STARTUP-125 replaces.

(f) *Nothing else about the run differs.* Apart from the first-run exemption of REQ-STARTUP-155, no behavior this document specifies differs between a run started from a preparation and a run started any other way: the same release version is reported (REQ-STARTUP-004, REQ-STARTUP-007, REQ-STARTUP-158), the same installation flavour is classified (REQ-STARTUP-106), the same single-instance resolution applies (REQ-STARTUP-161, REQ-STARTUP-164), and no surface anywhere in the product reports that a preparation was made, reused, superseded, or redone. This silence covers those four outcomes and no fifth: a run that could produce no preparation at all is reported, on the terms clause (c) states, and this clause SHALL NOT be read as forbidding that notice.

### Linux AppImage

**REQ-STARTUP-024** — The Linux artifact SHALL be an AppImage that runs without being extracted first on an unmodified Ubuntu 24.04 installation — the oldest system-library baseline the artifact is required to support. It SHALL carry a desktop entry with `Type=Application`, `Name=Rotaris`, `Terminal=false`, categories `Development;IDE;`, an application icon, and an Exec line that accepts an optional directory the desktop environment supplies when the user opens a folder with the application — a file-manager "open with" or drag-onto-icon gesture. ### Platform scope

**REQ-STARTUP-026** — The platform keys a release publishes for SHALL be exactly the three of REQ-STARTUP-030. A release's asset list SHALL therefore contain no filename bearing a Windows-ARM64 or macOS-Intel platform key, and no download surface SHALL present a download for either. A visitor on Windows ARM64 SHALL be presented the `windows-x64` artifacts, those being the only Windows downloads offered at all. Running a `windows-x64` artifact under Windows-on-ARM x64 emulation is an expectation and not a supported configuration: it carries no acceptance criterion of its own, no release is blocked by a failure observed only under emulation, and the release gate of REQ-STARTUP-156 exercises exactly the three platform keys of REQ-STARTUP-030 and no fourth. A download surface reached from a platform for which the release publishes no artifact — Windows ARM64 and Intel macOS being the two such platforms — SHALL state which artifact it is offering instead, SHALL state that the artifact is built for a different processor architecture and is not tested on the visitor's platform, and SHALL still offer the download rather than withholding it; on Intel macOS, where no artifact can run at all, it SHALL instead state that this release publishes no macOS build for that architecture and offer no macOS download. The wording is left to the implementation.

### Release pipeline

**REQ-STARTUP-027** — A release SHALL be triggered only by pushing a tag of the exact grammar `v<major>.<minor>.<patch>`, optionally followed by a PEP 440 prerelease suffix `a<N>`, `b<N>`, or `rc<N>` (e.g. `v1.2.3`, `v1.2.3rc1`). Refs that do not match this grammar — `vlatest`, `v1.2.3dev1`, `1.2.3`, `v1.2`, `v1.2.3-rc1`, and branch refs among them — SHALL NOT trigger a release; when a candidate string is validated, the rejection message SHALL name the offending tag and describe the expected shape.

**REQ-STARTUP-028** — Before any build, a guard SHALL verify that the tag version equals every product version the build declares (REQ-STARTUP-158). On mismatch it SHALL fail (exit code 1, stopping all platform builds) with a message that names the tag version, every declared version that differs from it, and the location of each place a version is declared, and instructs that the product releases one version and that every such place must be bumped to the tag. The same pre-build guard stage SHALL additionally enforce the package-pin agreement of REQ-STARTUP-059 and SHALL fail the same way — one stage, one exit code, all platform builds stopped — so that no platform is ever built from a release whose pins disagree.

**REQ-STARTUP-029** — Release-channel classification SHALL map plain `X.Y.Z` to `stable` and any `aN`/`bN`/`rcN` suffix to `prerelease`; an invalid version string SHALL be an error stating it is not a supported product version.

**REQ-STARTUP-030** — The build matrix SHALL cover exactly `windows-x64`, `macos-arm64`, and `linux-x86_64`, and a failure on one platform SHALL NOT cancel the others. The final release SHALL publish whatever artifacts survived, and a separate overall status SHALL still report failure when any platform failed, so a partial release is visible.

**REQ-STARTUP-031** — Artifact names SHALL come from a single authority shared with the updater, with these exact shapes: `Rotaris-{v}-windows-x64-setup.exe` (installer), `Rotaris-{v}-windows-x64-portable.exe` (portable), `Rotaris-{v}-macos-arm64.dmg`, and `Rotaris-{v}-linux-x86_64.AppImage`. Requesting an unknown artifact kind SHALL error listing the known kinds. Per-platform kinds: windows-x64 → setup, portable; macos-arm64 → dmg; linux-x86_64 → appimage. No console archive kind exists, the console binaries it carried having been withdrawn with REQ-STARTUP-002.

**REQ-STARTUP-032** — Each release SHALL publish a checksum manifest named `SHA256SUMS.txt`: one line per asset in the form `<sha256hex>  <filename>` (two-space separator), sorted by filename, compatible with `sha256sum -c`. Each release SHALL also publish, beside that manifest, a detached signature over the manifest's exact published bytes, named `SHA256SUMS.txt.sig` (REQ-STARTUP-167). The manifest SHALL list every other published asset and SHALL list neither itself nor that signature: the signature is what establishes the manifest rather than something the manifest establishes, and a manifest cannot carry a digest computed over a file derived from the manifest itself. The signature is detached, so the manifest's bytes are the same bytes whether they are read by the update path or by `sha256sum -c` (REQ-STARTUP-152).

**REQ-STARTUP-167** — The checksum manifest of REQ-STARTUP-032 SHALL be signed, and the update path SHALL install nothing whose manifest signature it has not verified. This requirement is the product's single definition of publisher authenticity for updates; a document that needs to say what an update establishes about who published it cites this identifier rather than restating it.

Every published artifact SHALL carry within itself the verification counterpart of the release signing key, and SHALL resolve it from within what was installed with no additional download (REQ-STARTUP-159). The set of keys a build accepts SHALL be fixed when that build is produced. Nothing at run time SHALL add to it, replace it, or disable it — no configuration value, no preference, no environment variable, no interface control, and nothing the product downloads (REQ-STARTUP-111, REQ-STARTUP-146, REQ-STARTUP-147) — because a trust anchor a network can replace establishes nothing. A signature made by a key the running build does not carry SHALL be treated as not verifying.

What this establishes, and what it does not, are both observable. An update this product installs is established as the bytes the manifest names (REQ-STARTUP-123) **and** as having been published by a holder of a key the running build was built to trust; the manifest no longer establishes only what was downloaded over the same connection the download came from. It is not established as reviewed, safe, or correct. It says nothing about the artifacts themselves carrying a code signature: the artifacts stay unsigned by design, and this requirement changes nothing about what an operating system does with a downloaded file, so the first-launch platform trust prompts of REQ-STARTUP-021 and REQ-STARTUP-023 are exactly as they were.

A release published without a signature this build can verify SHALL NOT be installed by this build under any circumstance. There SHALL be no override, no confirmation, no setting, and no retry by which a user installs an update whose manifest signature did not verify; the refusal is the intended outcome and not a condition to be worked around (REQ-STARTUP-123).

**REQ-STARTUP-168** — The release signing key of REQ-STARTUP-167 SHALL be replaceable without stranding installations already in the field, and the product SHALL state what happens where it cannot be. The obligations below are behavioral; how a key is generated, held, or transferred is an architecture decision and is fixed nowhere in this document.

(a) *A build may trust more than one key.* What a build carries under REQ-STARTUP-167 SHALL be a set rather than a single value, so that a build produced before a rotation and a build produced after it can both verify the same release. How many members that set holds is an implementation choice and no surface of the product reports it.

### Single running instance

**REQ-STARTUP-161** — At most one instance of the application SHALL run per user account on a machine, and launching the application SHALL never produce a second one. This requirement is the product's single definition of application-instance identity; a document that needs to say how many instances exist, or that a state it is guarding against arises from something other than a second instance, cites this identifier rather than restating it. Every launch resolves to exactly one of two outcomes and to no third: it becomes the running instance, or it is handed to the instance that is already running and ends without opening a window of its own. The set of outcomes is closed; *when* a launch reaches one of them is not fixed here, and a launch may be made to wait before reaching either — a launch arriving while the running instance is shutting down is refused for the remainder of that shutdown and then resolves to one of these same two outcomes (REQ-SHELL-169, REQ-STARTUP-164). Waiting is not a third outcome and SHALL NOT be read as one; what this sentence forbids is a launch that ends in some other state, above all a second instance. Several workspaces and several windows are not a second instance and SHALL remain fully available: every main window the product opens — the replacement window of REQ-SHELL-017, the demo window of REQ-SHELL-162, and a window a launch causes to be built (REQ-STARTUP-163) — is a window of the one instance, and no capability of this product SHALL require two of them to be running. To decide which outcome a launch takes, the application SHALL keep one record naming the process that is currently the instance and how a launch reaches it. That record's form and location are implementation choices, constrained only by these observable properties, which are the whole of the requirement: there is exactly one of it per user account; it lies outside every workspace directory, so it never appears in a project or in that project's version control; it is held in the per-user location REQ-STARTUP-145 fixes — local to this machine and not replicated to another machine or to another copy of the user's profile — because this record names a process on **this** machine and a replicated one would offer a launch a process that was never running here, which the resolution of REQ-STARTUP-164 would then have to reclaim on every launch; it is not a key of the desktop preference store, whose key set is closed (REQ-SHELL-006, REQ-STARTUP-146); it is created by the launch that becomes the instance and released when that instance's process ends, a record that outlives its process being settled by REQ-STARTUP-164; and creating, reading and removing it needs no elevation. The application SHALL define no configuration key, environment variable, preference or interface control by which a second instance can be started (REQ-STARTUP-146, REQ-STARTUP-147).

**REQ-STARTUP-162** — Being handed to the running instance SHALL surface that instance to the user and SHALL do nothing else the user can see. The launch that is handed over SHALL show no window, no dialog, no banner, no acknowledgement and no error, SHALL write nothing to the preference store of REQ-SHELL-006 and nothing to any per-user or per-workspace state, and SHALL end. The refusal to start a second instance is silent: the surfaced window is the only thing the user observes, and no surface anywhere in the product reports that a launch was refused. That silence governs a launch that **has been handed over and has ended**, and it is the whole of what this paragraph fixes; it is not a rule about a launch that has been refused and is still waiting, which is a different state and is fixed in the paragraph below. Which window is surfaced: where the instance has main windows open, it SHALL surface the main window that most recently held keyboard focus, and where none has ever held focus, the one built first; a persona window and a terminal window are never surfaced, belonging as they do to a main window (REQ-SHELL-123). Where the instance holds the record but has no window open at all — a state that arises on a platform whose convention is for the process to continue after its last window is closed — it SHALL build and show a main window, resolving that window's workspace exactly as a launch does (REQ-STARTUP-041, REQ-STARTUP-163), and that window SHALL go through the same post-show activation every main window goes through (REQ-STARTUP-043). That clause has exactly one exception and it is the only one: while the instance is shutting down it SHALL NOT build that window (REQ-SHELL-169), because building a window in a process whose exit is already under way would put a workspace on screen inside a process about to end. Surfacing a window means showing it, bringing it out of a minimized state, and asking the host window manager to raise and activate it, on the terms REQ-SHELL-161 fixes for every window this product owns: a declined raise is a supported outcome and not a failure, and the launch still counts as handed over. This domain adds only what the content guarantee means here — the window carries the workspace the launch asked for (REQ-STARTUP-163).

**What a refused launch shows while it waits.** A launch that the running instance refuses because it is shutting down is neither handed over nor the instance, and the silence above does not reach it (REQ-SHELL-169). Where a main window of the shutting-down instance is on screen, that window is surfaced and it is already saying that stopping is under way, so this launch SHALL add nothing to it. Where no window of that instance is on screen, the launch SHALL convey that the application is finishing shutting down and will open when it has; the wording, the surface and its dismissal are left to the implementation, and what is fixed is only that a user who launched the application is not left for the length of the force-exit allowance with nothing to distinguish a launch that is waiting from one that failed. What it conveys SHALL NOT report that a launch was refused, SHALL NOT present the wait as an error, and SHALL NOT offer to start a second instance. It SHALL end when the launch reaches its outcome under REQ-STARTUP-164 — a window of this launch's own or the window it is handed to — and the outcome window is the one thing the user is left looking at, exactly as it is for a launch that never waited.

**REQ-STARTUP-163** — A workspace directory a launch carries SHALL be honoured, whether that launch becomes the instance or is handed to one. A directory the operating system hands a launch — a file-manager "open with", a drag onto the application's icon, or the registration of REQ-STARTUP-024 or its per-platform equivalent — is the explicitly opened workspace of REQ-STARTUP-041 (a), and remains the only path by which anything outside the application selects a workspace. Where the launch becomes the instance, REQ-STARTUP-041 applies unchanged. Where the launch is handed to a running instance: when a main window of that instance already has that directory open, that window SHALL be the one surfaced under REQ-STARTUP-162 and no window SHALL be built; otherwise the instance SHALL build an additional main window on that directory, show it and surface it, and SHALL leave every window already open exactly as it was — the same workspace, the same active view, the same composer contents, the same runs still executing. The replacement semantics of REQ-SHELL-017 and REQ-STARTUP-047 SHALL NOT apply and the gates of REQ-STARTUP-053 and REQ-SHELL-021 SHALL NOT be evaluated: such a launch adds a window rather than displacing one, so an active run, an unsaved settings edit or a running worktree integration in an open window neither blocks it nor is disturbed by it. Nor is it a workspace-open request originating from a window, so REQ-SHELL-020 does not apply to it. The directory SHALL be resolved and persisted as the remembered workspace exactly as REQ-STARTUP-041 (a) requires, and the new window SHALL go through the same post-show activation as any other main window (REQ-STARTUP-043). A launch carrying no directory SHALL cause no window to be built while the instance has one open, and is surfaced under REQ-STARTUP-162 alone.

This requirement is the product's single definition of when two directory strings name the same directory, because that question decides which of the two outcomes above a launch takes and is therefore something a user sees. A document that needs the rule cites this identifier rather than restating it. Two directory strings name the same directory when they agree after all of the following, and the comparison SHALL be made on that resolved form and never on the strings as given. Each is taken to its absolute form, with a home-relative prefix and any relative segments expanded and the platform's separators normalised; a trailing separator carries no meaning and SHALL NOT make two strings differ. Every part of the path that the filesystem itself resolves to another name SHALL be resolved — symbolic links and directory links to the location they name, so that a linked folder and its target are one directory, and any abbreviated alternate spelling the filesystem keeps for a name to the full name it stands for. The results are then compared without regard to case wherever the filesystem holding them does not distinguish case, and with regard to case wherever it does.

Two spellings that reach one directory only through a mapping a user configured outside the filesystem — a network location named directly against the same location reached through a drive letter or mount point bound to it, or a mounted image against the file it was mounted from — SHALL NOT be reconciled, and SHALL be treated as naming different directories. That is deliberate rather than an omission: no test distinguishes those cases reliably on every platform, and treating two genuinely different directories as one would silently merge two workspaces, which is a worse outcome for a user than a second window opened on one folder. The observable cost of not reconciling them is bounded to exactly that second window.

This rule decides window reuse here and the resolution REQ-STARTUP-041 (a) performs, and it decides nothing about which durable record a workspace has: what binds a workspace to its sessions is the identifier REQ-SESSION-197 fixes, which is carried in the workspace and is never derived from a path.

**REQ-STARTUP-164** — A record naming a process that cannot be reached SHALL never leave the application unlaunchable. A launch SHALL resolve the record of REQ-STARTUP-161 in this order and SHALL reach an outcome in bounded time. (1) It attempts to claim the record exclusively; a claim that succeeds makes this process the instance, and startup continues at REQ-STARTUP-040. (2) A claim that fails means a record exists, and the launch attempts to be handed to the instance that record names; the hand-over is complete when that instance acknowledges it, and the launch then ends under REQ-STARTUP-162. (3) Where the hand-over is not acknowledged within 5 seconds — because the record cannot be read, because it identifies no process, because the process it identifies is not running, or because a process that is running does not answer — the launch SHALL reclaim the record and retry the exclusive claim exactly once. There SHALL be at most one reclaim and two claim attempts in total, and no waiting beyond that one interval, so a record that another party keeps recreating can never make a launch spin. **An instance that answers is not an instance that does not answer, and the 5 seconds SHALL NOT be applied to it.** Where the instance answers the hand-over by refusing it because it is shutting down (REQ-SHELL-169), the launch has been answered: this clause is not reached, the 5-second interval SHALL NOT run, the record SHALL NOT be reclaimed, and the launch SHALL wait instead. That wait is bounded by the shutdown itself, whose end the force-exit allowance of REQ-MONITOR-131 guarantees and of which this requirement holds no copy; when the instance's process has ended the deferred launch re-enters this order at clause (1) with its full complement of attempts, and where the shutdown left the record behind it resolves that record exactly as this clause already resolves one naming a process that is no longer running. Without this distinction the refusal of REQ-SHELL-169 would be defeated by the requirement it relies on: a launch refused one second into a shutdown would reclaim the record four seconds later and become the second simultaneous instance that refusal exists to prevent. (4) Where the second claim also fails, another launch has claimed the record inside that interval and is becoming the instance; this launch SHALL attempt the hand-over once more and SHALL then end, having in either case started no rival. Every path therefore ends with exactly one instance running and a window on screen — this launch's own, or the one it was handed to. Probing whether the recorded process is running SHALL have no effect on that process, and a launch SHALL write nothing but the record itself while resolving it. This is the discipline REQ-SESSION-047 and REQ-SESSION-058 apply to a session lock — parse, probe, at most one reap, one retry, no spin, and no side effect on the probed process — and it resolves the ambiguous case in the opposite direction, deliberately. An unreadable session lock resolves toward live because two processes writing one session directory would corrupt it (REQ-SESSION-056); an unreachable instance record resolved toward live would instead leave the user unable to start the application at all, which is the worse outcome and the one this requirement exists to forbid. Reclaiming from a process that is running but unresponsive is the one path by which two processes of the application can briefly exist, and what makes it safe is that a session is protected by its own lock whichever process reaches it (REQ-SESSION-046, REQ-SESSION-047), not by this record.

### Workspace storage

**REQ-STARTUP-166** — The product SHALL determine, directly and without waiting for anything to go wrong, whether an opened workspace sits on storage that is shared with or synchronised to another machine, and SHALL tell the user when it does. The determination SHALL be made from the storage the workspace directory sits on. It SHALL NOT be inferred from a failure — not from a write that failed, not from a lock that collided, and not from a session that was refused — so a user is told before the situation costs them anything rather than afterwards. It SHALL be made for every workspace this domain opens and by every path that opens one: the startup resolution of REQ-STARTUP-041, a directory a launch carries to an instance already running (REQ-STARTUP-163), and the project switch of REQ-STARTUP-047. It SHALL be part of the post-show background activation of REQ-STARTUP-043, so it never delays first paint and never delays the moment the interface accepts input.

Two conditions SHALL be distinguished, and reported as the one that was found wherever the platform lets them be told apart: storage another machine can reach directly, and storage a file-synchronisation agent replicates to another machine. Where the storage cannot be classified, nothing SHALL be reported and nothing else SHALL change. An inconclusive determination is not an error, produces no notice, and never refuses, delays, or degrades anything — the product cannot recognise every such arrangement, and a silent negative is the only safe answer to an unknown.

Where either condition is found, the user SHALL be told on the persistent, non-modal, non-blocking notice surface the update offer of REQ-STARTUP-116 appears on, at warning severity. The notice SHALL convey three things, its wording left to the implementation: which of the two conditions was found; that the product writes into the workspace while it runs — its per-workspace state directory (REQ-STARTUP-145) and, through the work a run does, the user's own files — so that a second machine working in the same folder at the same time, or an agent replicating those writes as they are made, can produce conflicting copies or lose an edit; and that holding the workspace on this machine's own storage avoids both. It SHALL NOT state or imply that the workspace cannot be used.

Nothing SHALL be refused on this account. The workspace SHALL open, every capability SHALL remain available, and no run SHALL be refused because of what this determination found. A session another machine holds is a different condition with a different remedy and is refused where the session domain refuses it (REQ-SESSION-083, REQ-SESSION-183); this notice SHALL NOT be presented as that refusal, SHALL NOT be raised in its place, and SHALL NOT be worded so that a user reads one as the other.

The determination SHALL write nothing: not into the workspace, not into the per-workspace state directory, and not into the desktop preference store, whose key set stays exactly as REQ-STARTUP-146 leaves it. The notice SHALL be raised at most once for each opening of a workspace in a window, SHALL be dismissible as any other notice on that surface is, and SHALL NOT be raised again in that window for that workspace once dismissed; nothing about it survives the window, a persisted suppression being a key that store does not have. A demo window SHALL make no such determination and SHALL raise no such notice (REQ-STARTUP-056).

### Machine-setup manifest and platform keys

**REQ-STARTUP-058** — Each release SHALL carry a pinned machine-tool manifest (schema version 1) declaring, per tool: probe command, version arguments, optional minimum acceptable version, the provisioned version, per-platform archive artifacts (HTTPS URL, 64-hex SHA-256 digest, archive layout, expected executables), license identifier, and the user-facing capabilities the tool enables. The shipped manifest SHALL pin: Git — no minimum (any working system git is reused), provisioned version 2.55.0, a Windows-x64-only archive from the upstream Git-for-Windows release line, license `GPL-2.0-only`, capabilities worktrees and checkpoints; ripgrep — minimum 14.1.0, provisioned 15.2.0, archives for all three platforms from the upstream ripgrep releases, license `Unlicense OR MIT`, capability search. The manifest SHALL further carry a distinct list, **language servers provisioned by the bundled code-intelligence runtime**, separate from the machine tools because the runtime and not the setup flow obtains them, so no probe command, archive or digest applies. For each language the release names it SHALL declare the packages the runtime installs for that language's server: each by name, exact provisioned version (a complete `MAJOR.MINOR.PATCH`, REQ-STARTUP-059's discipline), source URL and license identifier, together with the provisioner family the runtime uses (`npm` or `uvx`). The shipped manifest SHALL name TypeScript — `typescript` 5.9.3 (`Apache-2.0`, the npm registry) and `typescript-language-server` 5.1.3 (`MIT`, the npm registry), provisioner `npm` — and Python — `pyright` 1.1.403 (`MIT`, PyPI), provisioner `uvx`. Each declared version SHALL be identical to the runtime's own default for that server, and the build SHALL check the two against each other (the check of REQ-MCP-095's kind); a build in which they differ SHALL be treated as defective. *Amended 2026-09-06 under ESC-32: the list is new; the machine-tool entries above are unchanged.*

**REQ-STARTUP-059** — The machine-tool manifest a build ships SHALL state exactly one version for every tool-server package it lists, written as a complete version string with no range, alias or floating tag. The identities of the third-party packages the built-in defaults name are not fixed by this document and may change between releases (REQ-CONFIG-181, REQ-MCP-010); what is fixed is the agreement between the two places a build states them. The manifest SHALL pin every package that the built-in default tool-server configuration of that same build launches through `npx` or `uvx`, and for every package named in both places the two version strings SHALL be equal character for character, compared with no case folding, alias expansion, or range interpretation. A default entry naming a package the manifest does not pin, and a pair that disagrees, SHALL each fail the pre-build guard stage of REQ-STARTUP-028 — exit code 1, all platform builds stopped — with a message naming the package, both version strings (or the absence of one), and both file locations. No release SHALL publish a build in which such a pair disagrees. Since a warm-up step is planned only for a specification carrying an exact version (REQ-STARTUP-064), a configured package left unpinned or pinned to `@latest` SHALL never be warmed, whatever the manifest states for it.

**REQ-STARTUP-060** — Platform keys SHALL be `windows-x64`, `macos-arm64`, and `linux-x86_64`, with a raw `<os>-<machine>` fallback for anything else, and SHALL be shared between release artifact naming, updater asset selection, and manifest artifact selection.

**REQ-STARTUP-061** — The manifest fingerprint SHALL be the SHA-256 of the manifest serialized as canonical JSON (sorted keys, compact separators). This fingerprint is the sole identity used to decide whether setup must run again.

**REQ-STARTUP-062** — Deliberate exclusions: Node.js SHALL be supplied by the user and SHALL never be downloaded by setup; no Git MCP server SHALL be shipped, pinned, warmed, or granted (agents use terminal git); the bundled MCP server runtime requires no setup step. The setup dialog's explanation copy SHALL name only Git, Node, ripgrep, and MCP package caches, and SHALL NOT mention internal tooling names.

### Setup planning and probing

**REQ-STARTUP-063** — Tool probing SHALL: resolve the command on the (managed-augmented) PATH; run its version command with a 10-second timeout and, on Windows, with no visible console window; extract the first dotted numeric version from combined stdout+stderr; and treat the tool as satisfied only when the probe exits 0 and (no minimum is declared or the parsed version ≥ the minimum). A missing executable or a probe error yields not-satisfied. For Git specifically, any exit-0 probe satisfies regardless of whether a version could be parsed; a non-zero exit does not.

**REQ-STARTUP-064** — MCP cache warm-up steps SHALL be computed from the merged MCP server configuration of the workspace being opened, so that adding, removing, or repinning a server changes the resulting plan. A configured server SHALL contribute a warm-up step only when it is a stdio server launched through `npx` or `uvx` and its package specification pins an exact version — a parseable version following `==`, or following the last `@`. A specification with no version and a specification pinned to `@latest` SHALL contribute no step; HTTP and SSE servers SHALL contribute no step; a server entry carrying `enabled: false` SHALL contribute no step, because nothing will ever launch it (REQ-CONFIG-465); and a `stdio` entry whose command is the reserved bundled-runtime token SHALL contribute no step, because what it resolves to ships inside the artifact (REQ-MCP-033) — the runtime does; its language servers do not, and they are provisioned by the runtime itself at the first use of a language (REQ-STARTUP-159, REQ-MCP-118), not by a warm-up step of this registry. *Qualified 2026-09-06 under ESC-32: the reason "what it resolves to ships inside the artifact" was written before ADR-0035's first execution measured that the runtime obtains its language servers at run time; the clause's outcome — no step — is unchanged, and the reason is kept beside its qualification.* Steps SHALL be deduplicated by the pair (runner family, package specification), and the step order SHALL be that same pair sorted ascending — runner family first, then package specification, each compared as a sequence of Unicode code points with no case folding — so one key serves both deduplication and ordering, a package configured for two servers is warmed once, and the same merged configuration always yields the same step sequence whatever order the servers appear in. A step's label SHALL be `Warm <package>`. The executed command SHALL be `npx -y <pkg> --help` for the `npx` family and `uvx --from <pkg> <executable> --help` for the `uvx` family, where `<executable>` is the executable that server entry is configured to launch.

**REQ-STARTUP-065** — An `npx` warm-up SHALL be planned only when `npx` resolves on the PATH at plan time, and the discovered absolute launcher path (including the Windows `.CMD` shim) SHALL be used in the executed command. Without `npx`, the warm-up silently disappears from the plan and the MCP server that the default configuration starts through `npx` is reported unavailable until the user installs Node and thereby supplies `npx`.

**REQ-STARTUP-066** — When setup was not manually requested and a durable record exists whose fingerprint equals the current manifest fingerprint and whose outcome is `complete`, or is `degraded` with accepted degradation, the plan SHALL be empty. An empty plan SHALL run no probe command, issue no network request, run no warm-up command, leave `setup/state.json` byte-for-byte unchanged including its recorded timestamps (REQ-STARTUP-074), and show no setup dialog (REQ-STARTUP-096).

**REQ-STARTUP-067** — A non-empty plan SHALL be ordered deterministically: a detect step (`Detect machine tools`); then per manifest tool either a satisfied step (`<name> already installed`, carrying the probed version) or an install step (`Provision <name>`, carrying its capabilities); then warm-up steps whose recorded state is not already complete (all warm-ups rerun under manual repair); then a record step (`Record machine setup`).

**REQ-STARTUP-068** — Top-up: when a record exists with a different non-empty fingerprint, the plan SHALL be marked as a top-up and contain only genuinely missing work — already-satisfied tools re-listed as satisfied with no re-downloads. A top-up SHALL be presented exactly as a first-time run is: the dialog vocabulary of REQ-STARTUP-090 stays two-valued, a top-up that was not manually requested carries the page title `Preparing Rotaris`, and no third page title, explanation text or badge distinguishes it. The distinction is already visible where it matters — the step list shows the already-satisfied tools as satisfied steps and shows only the missing work as install or warm-up steps (REQ-STARTUP-067) — and the top-up marking is internal, used to decide the plan's content and not to change what the user is shown.

**REQ-STARTUP-069** — When a setup pass is required and every manifest tool is already satisfied by an installed tool (REQ-STARTUP-063), the plan SHALL contain no install step and the pass SHALL issue no request to any pinned tool-archive URL. For a workspace whose MCP configuration contributes no warm-up step (REQ-STARTUP-064), the plan SHALL then consist of exactly the detect step, one satisfied step per manifest tool, and the record step, in the order of REQ-STARTUP-067.

### Setup execution: state, locking, resume, cancel, failure

**REQ-STARTUP-070** — Everything setup writes SHALL be rooted in the per-user data directory (REQ-STARTUP-145, which fixes which per-user location that is): managed tools at `tools/<tool>/<provisioned_version>/`; the durable record at `setup/state.json`; caches at `setup/cache/downloads/`, `setup/cache/uv/`, and `setup/cache/npm/`; and a cross-process lock file at `setup/setup.lock`.

**REQ-STARTUP-071** — The durable record (schema version 1) SHALL be a JSON object at `setup/state.json` containing: the manifest fingerprint; an outcome of `running`, `complete`, `degraded`, `cancelled`, or empty; a map of verified tool versions; a map of managed binary directories per tool; per-step state (a stable step identifier, status, elapsed seconds, detail text); a sorted list of degraded capabilities; an accepted-degradation boolean; and started/updated/completed UTC ISO-8601 timestamps. Three of those field names are fixed, because a surface outside this domain reads them: the outcome is the key `outcome`, the completion timestamp is the key `completed_at`, and the verified-tool-version map is the key `versions`, mapping a managed tool name to its satisfying version string (REQ-CONFIG-397). The remaining fields are this domain's own, may be named as the implementation chooses, and are the "unknown keys" REQ-CONFIG-397 requires that reader to ignore rather than reject. Saves SHALL be atomic (same-directory temp file, fsync, rename) with the updated timestamp refreshed on every save and no temp-file litter; a missing or corrupt record SHALL be read as absent, never as an error.

**REQ-STARTUP-072** — The setup lock SHALL be an exclusively-created file (owner-only permissions) containing the holder PID and creation time. A second acquisition fails while the owner is alive. A stale lock — older than 900 seconds AND whose recorded PID is no longer running — SHALL be reclaimed; the liveness probe must have no side effect on the probed process. Release deletes the file.

**REQ-STARTUP-073** — When the lock cannot be acquired, the runner SHALL emit a terminal event with the message `Machine setup is already running`, still activate the managed tool environment for the current process, return the `already-running` outcome, and leave the durable record untouched.

**REQ-STARTUP-074** — Setup outcomes SHALL be exactly: `complete`, `degraded`, `cancelled`, `already-running`. An empty plan returns `degraded` if the record says degraded, else `complete`, writing nothing. A non-empty plan SHALL stamp the record `running` with the new fingerprint (degradation cleared) and persist it before the first step executes.

**REQ-STARTUP-075** — Step execution: previously-completed steps are skipped (counted as done) except detect and record, which always rerun. Cancellation is honored only at step boundaries — cancel never interrupts a running step; when observed, the record is saved with outcome `cancelled` and a cancellation event (`Setup cancelled`) is emitted. Each executed step emits a progress event (label, completed count, total) before work and a completion event (detail, counts, elapsed) after; per-step wall time is measured with a monotonic clock and persisted so timings survive restarts.

**REQ-STARTUP-076** — Step behaviors and detail strings: detect → `Checked system and managed tool paths`; satisfied → records the probed version, detail `<tool> <version|unknown> already installed`; install → download, verify, extract, promote (REQ-STARTUP-082..086), record the managed paths and provisioned version, immediately re-activate the managed environment so later steps see the tool, detail `Installed <path>` (comma-joined for multiple); a platform with no pinned artifact fails the step with `<tool> <version> has no pinned <platform-key> artifact in this release`; warm-up → emits the rendered command line as a detail event, runs with a 180-second timeout, emits combined trimmed output as detail, non-zero exit fails with `command <line> exited <code>: <detail or 'no detail output'>`, an OS/launch error fails with `command <line> failed: <error>`, success detail `Cached <package>`; record → re-probes every manifest tool, saves the satisfied versions, detail `Saved verified machine-tool versions`.

**REQ-STARTUP-077** — Failure semantics: the first failing step stops the run. The record marks that step failed with elapsed time and the error detail; the step's capabilities are unioned (sorted) into the degraded-capabilities list; the outcome becomes `degraded` with accepted-degradation set only when the caller asked to continue on failure; the completion timestamp is stamped; a failure event `{label} failed` is emitted with counts, elapsed, and detail. The application SHALL still open; only the features needing the missing tool warn (per-feature degradation, never a blocked app).

**REQ-STARTUP-078** — Success end state: outcome `complete`, completion timestamp stamped, degradation cleared, and a final completion event with message `Machine setup complete` at full progress.

**REQ-STARTUP-079** — Resume: after a cancellation, a subsequent run SHALL execute only the remaining steps (a warm-up command runs exactly once across cancel + resume); a further run with matching state is a full no-op fast path. An offline warm-up failure under continue-on-failure SHALL persist accepted degradation, the precise degraded capability list, and the OS error text in the step detail.

**REQ-STARTUP-080** — Accepting degradation (the dialog's "Continue without tool") SHALL rewrite the record to outcome `degraded` with accepted-degradation true and a backfilled completion timestamp, so the next launch skips setup despite the failure.

**REQ-STARTUP-081** — Setup SHALL be required exactly when: a manual run is requested; no record exists; the fingerprint mismatches; the outcome is neither `complete` nor `degraded`; or the outcome is `degraded` without accepted degradation.

### Setup downloads, verification, extraction

**REQ-STARTUP-082** — Tool archive downloads SHALL require HTTPS: a non-`https://` URL is refused before any network I/O with the message `tool archives require HTTPS`.

**REQ-STARTUP-083** — TLS verification for setup downloads SHALL trust both the operating system trust store and a CA bundle shipped inside the application, so public downloads succeed even where the packaged runtime lacks the system CA path, while organisation-internal roots remain honored.

**REQ-STARTUP-084** — Tool archive downloads SHALL behave as follows. Every request SHALL carry the header `User-Agent: Rotaris-Setup/1` and SHALL use a per-connection timeout of 30 seconds. The response body SHALL be written in 1 MiB blocks to a file named `<name>.partial` beside the cache destination, and bytes already written SHALL survive termination of the process. When a `<name>.partial` file already exists, the request SHALL carry a `Range` header asking for the bytes from that file's current length onward; the existing bytes SHALL be kept and appended to only when the server answers HTTP 206, and on any other success status the file SHALL be rewritten from the first byte of the response. When the transfer completes, the file's SHA-256 SHALL be compared against the digest pinned in the manifest for that platform key, and only on a match SHALL the file be renamed to its final cache name — so a file present under the final name has always been verified against its pin. A `<name>.partial` file SHALL stay eligible for resumption indefinitely — no age, launch count or manifest change expires it — because eligibility costs nothing: no partial file is ever promoted without matching its pin, so a stale or corrupt one can only cost a repeated transfer, never a wrong install. When the assembled file's digest does not match the pin, the step SHALL delete both the assembled file and the partial file and retry the transfer exactly once from the first byte, with no `Range` header; only if that second, wholly fresh transfer also mismatches SHALL the step fail. A digest mismatch that fails the step SHALL fail it with `SHA-256 mismatch: expected <expected>, actual <actual>`, naming both digests; a transport failure SHALL fail it with `download failed for <url>: <error>`. The cache destination SHALL be `setup/cache/downloads/<url filename>`.

**REQ-STARTUP-085** — Archive extraction SHALL be traversal-safe and link-free: entry names are normalized; absolute paths or `..` components are refused with `archive entry escapes the staging directory: <name>`; symlinks and hard links are refused; only `zip`, `tar.gz`, and `tar.xz` archives are accepted. Executable permissions are preserved (zip) or applied (tar), and the declared expected executables are forced executable on POSIX.

**REQ-STARTUP-086** — Promotion SHALL be atomic: extraction happens into a hidden sibling staging directory; all expected executables must exist in staging or the step fails with `archive is missing expected executables: <names>`; only then is the whole tree renamed into the final managed location. A pre-existing destination with intact executables is reused; an incomplete one fails with `managed tool directory is incomplete: <path>`. Staging is always cleaned up; after a cancelled or failed run, a managed tool directory is either absent or complete — never partially extracted.

**REQ-STARTUP-087** — Setup SHALL never require elevation or mutate the machine: everything it writes lives under per-user configuration/data directories (REQ-STARTUP-145); the OS PATH is never persistently modified; nothing is registered with an OS package database; no administrator/sudo prompt is ever raised.

### Managed tool environment

**REQ-STARTUP-088** — Activating the managed environment SHALL mutate only the current process environment: every existing managed binary directory (ordered by tool) is prepended to PATH (on Windows, both `Path` and `PATH`), and the package-runner caches are redirected to app-owned directories via `UV_CACHE_DIR` and `npm_config_cache` (created on demand). Managed directories take precedence over system tools of the same name for the app's own child processes.

**REQ-STARTUP-089** — Activation SHALL occur at every point where the process (or its children) might launch tools: desktop startup before window construction, the start of every setup run, immediately after each successful install step, on a lock collision, and when degradation is accepted — so probes, warm-ups, terminal tools, and MCP servers all observe provisioned tools.

**REQ-STARTUP-091** — Dialog contents and accessible names: a status line (`Machine setup current action`, initially `Ready to start`); a 0–100 progress bar (`Machine setup progress`); a step list (`Machine setup steps`); a `Show details` disclosure button (`Show machine setup details`) toggling a read-only, copyable details pane (`Machine setup details`, hidden by default; button text flips to `Hide details`); and an action row with `Cancel`, a hidden-until-relevant `Retry`, `Continue without tool` (accessible description `Open Rotaris with a warning for capabilities that still need this tool`), `Resume setup`, and `Open Rotaris`. The disclosure SHALL be keyboard reachable (focus + Enter opens the details).

**REQ-STARTUP-092** — Setup runs on a background worker; interactive runs SHALL NOT auto-accept degradation. Event rendering: progress → status text updates and a list row `▶ {message}`; completion → row `✓ {message} ({elapsed}s)` with the per-step elapsed time shown to one decimal place; failure → status update and row `Failed — {message}`; any event carrying a total sets the bar to the completed share of the total as a whole percent (fractions discarded), with the text `{completed}/{total} — {percent}%`. Detail messages stream live into the details pane.

**REQ-STARTUP-093** — Terminal-outcome buttons appear only after the worker has fully stopped: `complete` → progress 100, status `Machine setup complete`, and the dialog auto-accepts into the app with no extra click; `already-running` → a status conveying that a machine-setup pass is already in progress and that this dialog is not the one running it, with `Open Rotaris`; the wording is left to the implementation, and it SHALL NOT state that a second instance of the application is running, at most one being able to (REQ-STARTUP-161); `cancelled` → status `Setup paused. Completed steps are saved.` with `Resume setup` and `Open Rotaris` (resume restarts the worker and completed steps are skipped); `degraded` or a worker exception → status `A machine tool still needs attention` (or `Machine setup failed` for an exception, whose text is appended to the details) with `Retry` and `Continue without tool`.

**REQ-STARTUP-094** — The Cancel button SHALL set the cancellation flag, disable itself, and show status `Cancelling after the current step…`. Rejecting the dialog (Esc or the close box) while setup runs SHALL convert to a cancel rather than closing.

**REQ-STARTUP-095** — Choosing `Continue without tool` SHALL record the accepted degradation as in REQ-STARTUP-080, make the managed tool directories available to this process (REQ-STARTUP-088), and close the dialog, after which the main window SHALL open and every feature whose capabilities are absent from the record's degraded-capabilities list (REQ-STARTUP-077) SHALL behave exactly as it does after a `complete` setup. The technical detail of the failure, including any operating-system error text, SHALL have been readable in the details pane before the dialog closed. Afterwards the settings machine-setup card SHALL read `Rotaris is open with reduced machine-tool capabilities.` (REQ-STARTUP-102) and the next launch SHALL show no setup dialog (REQ-STARTUP-081).

**REQ-STARTUP-096** — The desktop setup entry point SHALL first activate the managed environment and return `complete` immediately — showing no dialog at all — when setup is not required (a later launch shows nothing). When it does run, warm-ups SHALL be derived from the current workspace's merged MCP configuration so they match what that workspace actually launches.

**REQ-STARTUP-097** — Bundled-runtime detection SHALL be: the process is a standalone (frozen) build, OR the environment variable `ROTARIS_BUNDLED` equals `1` (a test/ops override). Only bundled runtimes schedule the first-launch desktop setup.

### Re-running setup after first launch

**REQ-STARTUP-098** — *Withdrawn.* Its only surface was a console subcommand reporting through stderr, a bare outcome word on stdout and a process exit code, none of which this product has; running machine setup again after first launch is carried by REQ-STARTUP-153 and by the repair action of REQ-STARTUP-103.

**REQ-STARTUP-099** — *Withdrawn.* Its only surface was a second console host offering the same contract as REQ-STARTUP-098; the capability is carried by REQ-STARTUP-153.

**REQ-STARTUP-100** — *Withdrawn.* Its only surface was an automatic pre-step in front of console subcommands; the ordering guarantee it existed to give — the managed environment is active and any required setup has run before anything that needs a provisioned tool is launched — is carried by REQ-STARTUP-089 (activation at desktop startup, before window construction) and by REQ-STARTUP-044 and REQ-STARTUP-096 (the desktop's first-launch setup runs before repository discovery and before workspace onboarding).

**REQ-STARTUP-153** — Machine setup SHALL be re-runnable after first launch from the desktop and from nowhere else. The Project settings category (REQ-CONFIG-269) SHALL carry, alongside the status card of REQ-STARTUP-101, a setup surface listing every step of the recorded plan in the order of REQ-STARTUP-067, each row carrying that step's label and its recorded status, elapsed time and detail text from the durable record (REQ-STARTUP-071, REQ-NOTIFY-265). Two runs SHALL be offered. (a) The whole pass, through the `Repair machine tools` action of REQ-STARTUP-101, which is the manual full re-plan of REQ-STARTUP-103: degradation is not auto-accepted, and the dialog of REQ-STARTUP-090 carries the run. (b) A single step, offered on its own row: activating it SHALL run exactly that step against the current workspace, SHALL never run any other step, and SHALL never re-run a step whose recorded status is already complete — a completed row offers no run at all rather than offering one that silently does nothing. A single-step run SHALL take the lock of REQ-STARTUP-072 and SHALL be refused, with the message of REQ-STARTUP-073, for as long as that lock is held; it SHALL report the tool, the command it ran, the exit status that command returned and the reason it failed within that same surface, publishing no notice (REQ-NOTIFY-236, REQ-NOTIFY-265); and on completion it SHALL write the step's status, elapsed time and detail back into `setup/state.json` and recompute the degraded-capability list and the outcome from the recorded step states exactly as a full pass does (REQ-STARTUP-071, REQ-STARTUP-077). The surface SHALL refresh from the record after any run so it never shows a state the record contradicts. Where no record exists, the surface SHALL state that machine setup has not run and SHALL offer only the whole pass.

### Settings surface for machine setup

**REQ-STARTUP-101** — The Project settings category (REQ-CONFIG-269, REQ-CONFIG-396) SHALL carry a "Machine setup" card with: a status label (accessible name `Machine setup status`); a selectable-text versions label (`Managed machine tool versions`); and a `Repair machine tools` button (accessible description `Re-probe Git, Node, ripgrep, and configured MCP package caches`).

Completed steps are saved.`; `already-running` → an error toast conveying that a machine-setup pass is already in progress and that the repair therefore did not run, its wording left to the implementation and not asserting a second instance of the application (REQ-STARTUP-161).

**REQ-STARTUP-104** — After the post-show first-launch setup finishes, the card SHALL refresh automatically so it reflects the just-finished run without user action.

**REQ-STARTUP-154** — A user SHALL be warned at the moment a degraded capability is exercised, not only in the settings card. Given a capability present in the record's degraded-capabilities list (REQ-STARTUP-077), when the user performs an action that needs it, the action SHALL be declined rather than attempted and failed obscurely, and the transient error notification of REQ-SHELL-112 SHALL convey three things: which capability is unavailable, which machine tool is missing, and that machine setup can be run again from Settings (REQ-STARTUP-153). The wording is left to the implementation. The decline SHALL change nothing — no partial application — and the action SHALL remain available to try again once the tool is provisioned. Capabilities absent from that list SHALL behave exactly as they do after a `complete` setup and SHALL raise no such warning (REQ-STARTUP-095), so the warning appears if and only if the record says the capability is degraded. No warning SHALL be raised at startup for a degradation the user has already accepted (REQ-STARTUP-080): acceptance suppresses the setup dialog, not the point-of-use warning, and the two SHALL NOT be confused.

### Update check: eligibility, endpoint, policy

**REQ-STARTUP-105** — The update check SHALL contact exactly one fixed HTTPS endpoint — the latest-release API of the product's public GitHub release repository (`https://api.github.com/repos/<owner>/<repo>/releases/latest`) — with a request timeout of 10.0 seconds and the request header `Accept: application/vnd.github+json`. Release-asset downloads SHALL follow HTTP redirects (asset URLs answer with a 302 to a storage host).

**REQ-STARTUP-106** — The update path SHALL be selected by installation flavour rather than by operating system; the classification SHALL be stable across launches of the same installation and SHALL take no user input. Any build that is not running from one of the released standalone artifacts of REQ-STARTUP-031 — a build started from a source checkout or from a development environment among them — SHALL be classified not updatable: no check is performed at all, and the process SHALL issue no request to the endpoint of REQ-STARTUP-105 and none to any release-asset URL. Across every flavour, both the classification and the update target SHALL be taken from **the artifact the launch started from**, however the running image was started, and SHALL never be taken from a copy the artifact made of itself in order to run. Where an artifact starts from a preparation (REQ-STARTUP-165), the running image sits inside that preparation and is not the artifact: classifying or targeting from it would replace a copy the product can recreate at will and leave the file the user actually holds untouched, which is the one outcome an update must not produce. The AppImage clause below already states this rule for one flavour; it applies to all of them. An artifact running as an AppImage SHALL be identified from the `APPIMAGE` environment variable published by the AppImage runtime, and this test SHALL be applied before any other flavour test; the update target is the AppImage file named by that variable, never the executable image unpacked from it. A build running from inside a macOS `.app` bundle SHALL have the bundle directory as its target, never the executable inside it. On Windows the single-file portable flavour and an installed directory tree SHALL be classified differently in every case, the portable target being the artifact the launch started from — the single executable file the user downloaded, copied, or double-clicked — and the installed target being the install directory. The discriminator SHALL be the installer's own record: the build is classified installed if and only if the per-user registry value `InstallDir` exists under `HKCU\Software\Rotaris` (REQ-STARTUP-016) and the artifact the launch started from resolves to a path inside the directory that value names; every other Windows standalone build is classified portable. Resolving that test from the artifact rather than from the running image is what keeps a portable running out of a preparation from ever being read as an installed build, whatever directory the preparation happens to occupy. This signal is chosen because only the installer writes it and uninstallation removes it (REQ-STARTUP-019), so the classification follows the installation that actually exists rather than the shape of the files. Where the classification is wrong because a user copied an installed tree elsewhere, the consequence is bounded and safe: the copy is treated as portable, and the portable strategy of REQ-STARTUP-125 replaces it with a self-contained executable that runs from any location.

> **Narrowed by [`PD-STARTUP-004`](../product/directives.md#pd-startup-004), 2026-10-06.** A packaged Windows
> build outside `InstallDir` whose launch carries no `ROTARIS_PORTABLE_ARTIFACT` is classified not updatable, and
> no request is issued; the sentence reading a copied installed tree as portable no longer governs. Every other
> clause still does.

**REQ-STARTUP-107** — An update SHALL be offered only when all three hold: a latest release exists, its version is strictly newer than the running version, and the release contains the asset for this installation flavour on this platform (installer flavour → the setup artifact; portable → portable; app bundle → disk image; AppImage → AppImage). A release lacking this platform's file offers nothing — a real answer, not an error (never a dead download button).

**REQ-STARTUP-108** — When searching the release feed for the artifact of a given product version, platform key, and artifact kind, an asset SHALL count as a match only when its published `name` equals, character for character, the filename REQ-STARTUP-031 fixes for that combination — same letter case, same separators, same literal version text. Abbreviated, re-cased, re-separated, prefix, suffix, and substring matches SHALL all be rejected. A release offering no asset that matches exactly SHALL be treated as carrying no artifact for this platform, and no update SHALL be offered from it (REQ-STARTUP-107).

**REQ-STARTUP-109** — Version comparison SHALL parse both sides through the release-tag grammar and order them strictly-newer only. The order SHALL be the numeric tuple first, and, where two versions share a tuple, the prerelease rank second: a prerelease of a tuple sorts before the plain release of that same tuple, and among prereleases of one tuple the ranking is `a` before `b` before `rc`, ties within a kind broken by the ascending numeric suffix. A running prerelease is therefore offered the stable release of its own numeric tuple — `1.2.3rc1` is offered `v1.2.3` — which is the intended policy and the only one that lets a prerelease reach the release that supersedes it, since the feed filter stated below would otherwise leave it stranded until the next patch. Newer → offer; equal or older → none; a candidate tag outside the grammar (e.g. `v0.102.0-rc1`, `v0.102`) → none; a running version that does not parse (e.g. `dev`) → none, because the comparison cannot be decided. Draft and prerelease payloads SHALL be filtered out of the feed before comparison, so an installed app is only ever offered stable releases while prerelease artifacts stay available for manual download from the release page.

**REQ-STARTUP-110** — Every check failure SHALL be invisible to the user — the app starts silently with only an internal log line: unreachable network, any non-200 status (including 404 with no release yet and 403 rate-limit exhaustion), timeout, unreadable or truncated body, structurally invalid payloads (non-object, draft or prerelease flags, missing or malformed tag). There SHALL be no user-facing failure path for the check.

**REQ-STARTUP-111** — On a supported standalone desktop build the launch-time update check SHALL NOT be disableable by any user-reachable means. The acceptance criterion is positive and rests on four closed enumerations, which together are every configuration surface a user of this product has: the desktop preference store of REQ-SHELL-006 and REQ-CONFIG-463, whose keys are enumerated by REQ-STARTUP-146 for this domain and by REQ-CONFIG-405 and REQ-SHELL-163 elsewhere; the layered YAML configuration surface; the optional traceability layout configuration `rotaris-traceability.json` at the repository root, whose keys are enumerated by REQ-TRACE-040; and the environment variables of REQ-STARTUP-147. A release SHALL be accepted only when, for each of those four enumerations, no entry names update checking, an update endpoint, a release source, or an update channel — a property checkable by reading the enumerations themselves, each of which is maintained by the domain that owns it, this domain owning only REQ-STARTUP-146 and REQ-STARTUP-147. There is no fifth enumeration to maintain, because the product has no command-line arguments (REQ-STARTUP-039) and no text-mode interface. The interface SHALL likewise expose no control, toggle, menu item, or settings entry that turns the check off. Consequently, for every combination of preference values, configuration values, repository-root layout-configuration values, and environment variables a user can produce, such a build SHALL still perform the launch-time check of REQ-STARTUP-114 against the endpoint of REQ-STARTUP-105 and SHALL contact no other release source.

**REQ-STARTUP-112** — The banner summary SHALL be derived from the release body: if a `## Changes` heading exists (case-insensitive), the search starts after it; blank lines, headings, table rows, blockquotes, and code fences are skipped; a leading `- ` or `* ` bullet marker is stripped; the first substantive line is returned, truncated to 160 characters (159 + `…` when longer). An empty or scaffolding-only body yields an empty summary.

**REQ-STARTUP-113** — Checksum-manifest parsing SHALL be the exact inverse of the writer format (two-space split, trimmed name and hash, hash lowercased); malformed lines are skipped, never guessed at; the parser and writer formats SHALL round-trip.

### Update notification UI

**REQ-STARTUP-114** — The desktop update check SHALL run once per window activation, only after the window is visible; it does nothing (and returns without asking) for a build classified not updatable by REQ-STARTUP-106 and for demo windows on every runtime (REQ-STARTUP-057). Only one update operation (check or install) SHALL be in flight at a time; a second request while one runs is refused.

**REQ-STARTUP-115** — Before the network round trip, launch-time cleanup SHALL delete a leftover portable backup executable (`<name>.old`) left by a previous update beside the artifact of REQ-STARTUP-106 — beside the artifact and never beside the running image, which under REQ-STARTUP-165 may be a preparation the artifact made of itself and which never holds a backup at all. For every other flavour this cleanup never deletes anything. A deletion failure (e.g. the OS still holds the file) is tolerated silently and retried on a later launch, and a launch that cannot reach the directory holding the artifact — the medium having been removed, or being read-only — SHALL treat the cleanup as having nothing to do rather than as a failure.

**REQ-STARTUP-116** — When the offered version equals the persisted dismissed version (settings key `updates/dismissedVersion`), the offer SHALL be silently ignored. Otherwise a persistent, non-modal, non-blocking informational notice appears on the shared in-app banner: title `Rotaris {version} is available`, message = the release summary or the fallback `Open the release notes for the full changelog.`, with action `Update now`. The window behind it SHALL remain fully interactive with no active modal.

**REQ-STARTUP-117** — Dismissing the update notice SHALL record only that version string (not a general preference): the check still runs next launch; the same version stays silent; any newer version notifies again. Dismissing an unrelated notice SHALL never record a dismissed update version.

**REQ-STARTUP-118** — While an update download runs, a non-persistent notice titled `Downloading Rotaris {version}` SHALL show the message `{measured} — verifying against the published checksum when it finishes.` Progress SHALL be reported no more often than once per 1 MiB received (REQ-STARTUP-124). When the release feed states a non-zero size for the asset, `{measured}` SHALL be the received share of that size as a whole-number percentage with the fractional part discarded (the same convention as REQ-STARTUP-092), and SHALL be repainted only when that whole percent changes. When the claimed size is 0, `{measured}` SHALL instead be the whole number of MiB received, rendered as `{N} MB`.

**REQ-STARTUP-119** — Applied outcomes: an in-place replacement → persistent success notice titled `Update installed` with the strategy's message and a `Restart now` action; a hand-off → persistent success notice titled `Finish the update` with the message and no action; when the hand-off requires quitting (Windows installer), the window SHALL auto-close after a 1200 ms single delay.

**REQ-STARTUP-120** — Install failure SHALL raise a persistent error notice titled `Update not installed`, message `Rotaris is unchanged. You can try again or download the release manually.`, with the technical reason (e.g. the checksum-mismatch sentence) available as details and a `Try again` action that re-runs the install with the held offer. The installed bytes SHALL be untouched.

**REQ-STARTUP-121** — A `Restart now` action SHALL be offered on the `Update installed` notice and on no other notice, so it is unreachable after a hand-off outcome (REQ-STARTUP-119). Choosing it SHALL leave the user with the updated installation running and with exactly one instance of the application running (REQ-STARTUP-161). The restart is a hand-over of the running instance rather than a second launch, and it is the one case in which this product starts the application while an instance is running: the successor SHALL NOT be handed back to the instance that started it and SHALL NOT surface that instance's windows (REQ-STARTUP-162, REQ-STARTUP-164). In this order: the updated installation is started first; the record of REQ-STARTUP-161 passes from the current instance to the successor rather than being released for anyone to claim; the current window closes only after the successor has started; and the successor keeps running once the current process has exited. A launch arriving during the hand-over SHALL be handed to whichever of the two holds the record at that moment and SHALL never start a third process. When the successor cannot be started, nothing SHALL close — the current instance keeps the record and its window stays open and accepts input as before — and the failure SHALL surface through the `Update not installed` notice of REQ-STARTUP-120.

### Update download, verification, and install strategies

**REQ-STARTUP-122** — The install sequence SHALL be strictly: fetch the `SHA256SUMS.txt` published with that release together with the signature published over it → verify that signature → parse the manifest, and parse it only after the signature has verified → stream the asset into a fresh temporary staging directory (name prefixed `rotaris-update-`) → verify → apply — never proceeding past a failure, and reporting every failure as a single sentence. The signature is checked before the manifest is parsed and before any asset is fetched, so a manifest this build cannot attribute to a publisher it trusts costs the user no download and reaches no parser (REQ-STARTUP-167).

**REQ-STARTUP-123** — Verification SHALL enforce: a release publishing no checksum manifest is refused with `release <version> publishes no checksum file; refusing to install an unverifiable download`; a failed manifest fetch fails with `could not read the checksum file: HTTP <status>`; a downloaded file for which the manifest lists no hash is removed, reporting `no published hash for <name>; the download was discarded`; a hash mismatch deletes the file with `<name> does not match the published hash (expected <e>, got <a>); the download was discarded and nothing was installed`; comparison is case-insensitive.

Verification SHALL further enforce, before the manifest is parsed and before any asset is fetched (REQ-STARTUP-122), three signature outcomes, each of which refuses the install and leaves nothing downloaded: a release publishing no signature over its manifest is refused, conveying that the release publishes no signature for its checksum file and that an update whose publisher cannot be established is not installed; a signature that cannot be fetched fails, conveying that the signature could not be read and carrying the transport status, in the same shape as the manifest-fetch failure above; and a signature that does not verify against a key this build carries (REQ-STARTUP-167) is refused, conveying that the checksum file was not published by a holder of a key this build trusts, that nothing was downloaded and nothing installed, and that the release is to be obtained from the release page instead. The wording of these three is left to the implementation. The four hash outcomes above keep the exact sentences they state, which REQ-STARTUP-120 carries as the technical detail of a failed install.

No refusal in this requirement SHALL be overridable: there is no confirmation, setting, retry, or interface path by which an update whose manifest signature did not verify, or whose asset digest did not match, is installed anyway.

Together the two checks establish both what was downloaded and who published the manifest that names it. The digest comparison detects a corrupted or incomplete transfer. The signature establishes that the manifest came from a holder of a key this build was built to trust, rather than merely from the same connection the download came from — which is what the manifest alone established before REQ-STARTUP-167. Neither check establishes anything about the artifacts themselves carrying a code signature, which by design they do not (REQ-STARTUP-021, REQ-STARTUP-023).

**REQ-STARTUP-124** — Download staging SHALL stream in 1 MiB chunks (matching the hashing granularity), reporting `(bytes_so_far, claimed_total)` with the total possibly 0; a write failure deletes the partial file and fails with `could not write the download to <path>: <error>`.

**REQ-STARTUP-125** — The apply step SHALL be selected by installation flavour (REQ-STARTUP-106), not by operating system, and SHALL produce these observable results. In every case the target is the artifact REQ-STARTUP-106 identifies and never the running image: where the running image is a preparation the artifact made of itself (REQ-STARTUP-165), the replacement still lands on the artifact, so that the file the user holds is the one that becomes the new version and the preparation is left to be superseded on the next launch under REQ-STARTUP-165 (b). **AppImage** → the verified file SHALL first be placed next to the target as a hidden sibling named `.{name}.update` on the same filesystem as the target, then moved onto the AppImage path and left with mode `0755`; the replacement SHALL succeed while the application that is being replaced is still running; outcome replaced, message `The update is installed. Restart Rotaris to run it.`; on failure the sibling file SHALL be removed and the step SHALL report `could not replace <target>: <error>`; whether it succeeded or failed, no `.{name}.update` file and no staging directory SHALL remain. **Windows portable** → the verified file SHALL be placed beside the target, any previous backup SHALL be deleted, the target SHALL be renamed to `<name>.old`, and the new file SHALL then be moved into the target path; the replacement SHALL succeed while the application being replaced is still running, the target being the artifact rather than the file the process is executing; if that final move fails, the backup SHALL be renamed back to the target path before the step reports `could not install the update at <target>: <error>`, so the executable present after a failure is the original one; the `<name>.old` file SHALL remain until a later launch removes it (REQ-STARTUP-115); outcome replaced, with the same message as the AppImage case. Where the artifact sits on media that cannot be written — read-only or removed since launch — the step SHALL fail reporting that it could not install the update at the target, change nothing anywhere, and leave the running application and its preparation exactly as they were. **Windows installer** → the verified setup executable SHALL be started as a process that survives the application exiting, and the application SHALL make no edit of its own to the installed tree; outcome handed-off with quit required, message `Rotaris will close so the installer can replace it.`; if the process cannot be started the step SHALL report `could not start the installer at <path>: <error>`. **macOS** → the verified disk image SHALL be mounted and its mounted volume SHALL be opened in the platform's file browser so the drag-to-install of REQ-STARTUP-022 can be repeated; the installed application bundle SHALL be left byte-for-byte unchanged and SHALL never be replaced automatically; outcome handed-off, message `The verified disk image is open. Drag Rotaris to Applications, then reopen it.` **No released-artifact target** → the step SHALL fail with `this Rotaris was not installed from a released artifact` and change nothing on disk.

**REQ-STARTUP-126** — Invariant: not one file of the existing installation is moved or modified before the replacement has been fetched in its entirety and verified; should any stage fail, what is installed remains byte-for-byte what it was before the attempt.

**REQ-STARTUP-127** — With a hand-off strategy the ordering is reversed — the running application quits or yields to another installer before the replacement is actually in place — and the message shown SHALL describe that hand-off rather than telling the user to restart.

**REQ-STARTUP-128** — Exactly one version, the desktop application's, is compared against the feed, and exactly one artifact, the desktop one, is downloaded; because a release carries a single product version (REQ-STARTUP-158), no other version the product reports can disagree with it.

### Opt-in diagnostics

**REQ-STARTUP-129** — Diagnostics activation SHALL have exactly one source: the desktop preference store (REQ-SHELL-006, REQ-CONFIG-463). The mode SHALL be the stored value of `diagnostics/level`, one of `off`, `light` or `deep`, defaulting to `off` where nothing has been stored or where the stored value is not one of the three; the output base SHALL be the stored value of `diagnostics/outputDir`, unset meaning the default location of REQ-STARTUP-131. Both are set through the Settings controls of REQ-SHELL-163, which offer only those three levels and take the folder from the platform folder chooser — so an invalid selection is unreachable, and this document defines no diagnostics usage error, message or refusal. A change to either choice SHALL take effect for windows built afterwards and SHALL NOT alter a capture already running in an open window (REQ-SHELL-163). No environment variable and no other surface SHALL set either value.

**REQ-STARTUP-130** — When diagnostics is off, no diagnostics files, timers, or instrumentation of any kind SHALL exist — zero work, zero disk writes.

**REQ-STARTUP-131** — Each window with diagnostics enabled SHALL create its own run directory before writing any diagnostics data. Its path SHALL be `<base>/<timestamp>-<pid>/`, where `<base>` is the output base resolved in REQ-STARTUP-129 when one was supplied and otherwise `<workspace>/.rotaris/diagnostics/rotaris`; `<timestamp>` is the window's start time in UTC formatted `yyyymmddTHHMMSSZ`; and `<pid>` is the decimal process id. Creation SHALL be exclusive: a directory of that name that already exists SHALL never be written into, reused, emptied, or overwritten. When the name is already taken, the window SHALL take the first free name formed by appending `-2`, `-3`, … to it, trying each in ascending order and creating it exclusively, until one succeeds — the same deterministic suffixing discipline REQ-GIT-010 uses for branch names. Diagnostics SHALL never silently disable itself for this reason and SHALL never prevent the window from opening; only where no name at all can be created (the base directory itself being unwritable) SHALL the window open with diagnostics inactive, and it SHALL then say so in the diagnostics card of REQ-SHELL-163 rather than failing. The run directory SHALL contain a `snapshots/` subdirectory, created before the first snapshot is written.

**REQ-STARTUP-132** — Written artifacts SHALL be: `manifest.json` (schema version 3; app identity, creation time, platform triple, the full effective configuration including intervals and limits, and a self-checksum equal to the SHA-256 of the manifest's canonical JSON without the checksum field); rotating `metrics-NN.jsonl` and `spans-NN.jsonl` streams; `snapshots/NNNN-<sanitized-reason>.json`; and, at close, `summary.json` plus a human-readable `summary.md`.

**REQ-STARTUP-133** — The following bounds and cadences SHALL hold, and each SHALL also appear in the effective configuration recorded in `manifest.json` (REQ-STARTUP-132) so that every value is readable from the run directory itself. Each JSON-lines stream SHALL occupy at most 4 segment files of at most 8 MiB each; once the fourth segment is full, writing SHALL continue by replacing the oldest segment, so no stream ever exceeds 32 MiB however long the run lasts. Snapshot files SHALL share a total budget of 16 MiB; once it is exhausted, further snapshot writes SHALL be refused without raising an error to the user. Run-wide statistics SHALL be computed from at most 4096 metric samples and at most 1024 span samples, and each cap SHALL be a ring of the most recent samples: once the cap is reached, each new sample SHALL displace the oldest retained one, so the statistics describe the most recent window of the run. This is the reading the rest of the document already assumes — the growth and lag figures are used to judge a session that has been running for a while — and nothing about the run's beginning is lost by it, because `summary.json` reports resident memory at start and at peak from values carried forward independently of the ring (REQ-STARTUP-137). At most 128 distinct span names SHALL be reported individually and every further name SHALL be aggregated under the literal name `__other__`. A heartbeat SHALL run every 250 ms and reported event-loop lag SHALL be the measured interval between consecutive heartbeats minus that 250 ms. Metric records SHALL be produced every 1000 ms. In deep mode an allocation capture SHALL be attempted every 300000 ms, each tracing for 2.0 s, with a slow threshold of 1000 ms, at most 20 sites recorded per capture and at most 10 carried into the summary.

**REQ-STARTUP-134** — Every metric record (one per 1000 ms, REQ-STARTUP-133) SHALL carry at least: process resident and virtual memory; process CPU percentage; the number of operating-system threads the process holds together with their names; the number of concurrent execution contexts the application itself creates and runs its own work in, together with the names it gives them, whatever the runtime it is built on calls them; the process's OS handle or file-descriptor count; the UI threadpool's active and maximum worker counts; live widget and object counts; measured event-loop lag in milliseconds; one per-view entry for each of the seven primary views of REQ-SHELL-023, keyed by that view's lower-cased name and carrying exactly whether the view is currently visible, the number of live widgets it owns, and the number of items in its principal collection; and, for session stores, **counts only** — the number of transcript entries, agents, todos, artifacts, and cache entries. No diagnostics file SHALL contain session content of any kind: no transcript or prompt text, no model or tool output, no file contents, no credentials. Stack frames written into snapshots SHALL identify source files by base name only and SHALL never contain a directory path. The record's field names and JSON layout are governed by REQ-STARTUP-157.

**REQ-STARTUP-135** — Threshold triggers SHALL fire with a per-reason 60-second cooldown: event-loop lag over 1000 ms → a thread snapshot (reason `event-loop-lag`); resident-memory growth of at least 256 MiB over baseline → a snapshot plus an allocation-window request with the baseline rebased (reason `rss-growth`); native-thread growth of at least 8 → a snapshot (reason `thread-growth`).

**REQ-STARTUP-136** — Deep mode SHALL never leave allocation tracing running continuously: allocation evidence SHALL be gathered only inside bounded windows of the length fixed in REQ-STARTUP-133. At most one capture SHALL be in progress at a time: a capture requested while one is running SHALL start no second capture and SHALL add no second entry to the capture counts reported in `summary.json` (REQ-STARTUP-137). When allocation tracing is already owned by something outside the application, the capture SHALL be skipped, recorded with status `skipped`, and the external tracing SHALL be left running and unmodified. After any capture that exceeds the slow threshold of REQ-STARTUP-133 or ends in error, no further automatic capture SHALL be scheduled for the remainder of the run. Closing a window SHALL stop only tracing that the application itself started, SHALL NOT take an allocation snapshot, and SHALL take a thread snapshot instead. Any source path recorded for an allocation site SHALL be reduced to a workspace-relative path or to a bare file name.

**REQ-STARTUP-137** — `summary.json` (schema version 3) SHALL report: the number of metric samples the run produced; resident memory at start, at peak, at end, the end-minus-start delta, and a growth rate in bytes per second fitted over the run's samples; event-loop lag p50, p95 and maximum, together with a boolean flag marking those percentiles as approximate when too few samples were collected; for each reported span name its total count, its failed count, and its p50, p95 and maximum durations; and a diagnostics block containing the degradation reason where one applies, an incomplete flag (REQ-STARTUP-139), the number of allocation captures in each of the statuses `complete`, `slow`, `skipped`, `cancelled` and `error`, the ranked memory-growth sites — each carrying source file, line, sampled retained bytes, sampled retained count, the number of windows in which it appeared and its largest single-window byte total — and the total bytes written as snapshots. `summary.md` SHALL be a human-readable digest of the same run, beginning with the heading `# Rotaris diagnostics summary`, containing a resident-memory line and a section headed `## Top sampled memory-growth sites`. Three derivations are fixed. The growth rate SHALL be the slope of an ordinary least-squares straight-line fit of retained resident-memory samples in bytes against their elapsed time in seconds; with fewer than two retained samples the rate SHALL be reported as 0 and the run flagged as having too few samples. Event-loop-lag percentiles SHALL be flagged approximate whenever fewer than 100 lag samples were retained. Memory-growth sites SHALL be ranked by sampled retained bytes descending, ties broken by source file name and then by line number, both ascending, so the ranking is total and two runs over the same data rank identically. Resident memory at start and at peak SHALL be carried forward across the whole run rather than read from the retained sample ring (REQ-STARTUP-133), and the summary SHALL state whether either cap of REQ-STARTUP-133 was reached during the run.

**REQ-STARTUP-138** — Reading the JSON-lines streams SHALL tolerate a crash-truncated final line, so a crashed session's trace remains readable.

**REQ-STARTUP-139** — The diagnostics lifecycle SHALL be bound to its window: window close stops timers, writes the final snapshot and summaries, and joins any allocation worker with a 1-second cap, marking the capture incomplete when it overruns.

**REQ-STARTUP-140** — When diagnostics is enabled in either mode (`light` or `deep`), the span stream of a run SHALL contain at least one record whose span name is exactly `config.load`, covering the loading of configuration during startup. Every span record SHALL carry the span name, the elapsed wall time in milliseconds, the consumed CPU time in milliseconds, and a boolean flag stating whether the spanned work failed; the field names and JSON layout carrying those values are governed by REQ-STARTUP-157.

**REQ-STARTUP-157** — The diagnostics files are a private format with exactly one consumer: this product's own diagnostics surfaces (REQ-NOTIFY-267). No other program is entitled to read them, no compatibility with any other implementation's diagnostics files is required, and the field names and nesting of `manifest.json`, the metric and span streams, the snapshots and `summary.json` are therefore chosen by the implementation rather than fixed here. What is fixed is that the files are self-describing and internally consistent: each carries the schema version this document states for it (3 for `manifest.json` and `summary.json`, REQ-STARTUP-132 and REQ-STARTUP-137); the names and nesting SHALL be stable for the life of a schema version, so two runs of one build are always readable by the same reader and a changed layout requires a new schema version; every value this document requires SHALL be present in every record that must carry it; and the units SHALL be exactly these, whatever the field is called — a duration is a JSON number of milliseconds, a quantity of memory or of written bytes is an integer number of bytes, a rate is bytes per second, a percentage is a whole number, and a timestamp is an ISO-8601 UTC string. The effective configuration recorded in `manifest.json` (REQ-STARTUP-133) SHALL make every bound and cadence in force readable from the run directory itself, so a run can be interpreted without the build that produced it.

### Persistence, environment, and exit codes

**REQ-STARTUP-145** — Per-user directories SHALL be the platform-conventional configuration and data directories for the application name `rotaris`; per-workspace state lives at `<workspace>/.rotaris/`. There is no legacy directory to adopt: the product SHALL read, rename, import from, or otherwise adopt no per-user or per-workspace directory belonging to any earlier or differently named product, and SHALL create its own directories on first use instead.

**Which per-user location is meant.** Some platforms give a user more than one per-user location: one the platform replicates to the user's other machines or to another copy of their profile, and one that stays on the machine in use. Where a platform offers both, the per-user configuration and data directories of this requirement SHALL be **the location that is local to this machine and is not replicated, copied, or synchronised to any other machine or to any other copy of the user's profile**. Where a platform offers only one, that one is meant and this clause selects nothing. Where the platform's own default for an application's per-user directory is the replicated location, this requirement governs over that default: conformance is decided by whether the directories the product actually writes to are replicated, never by which location the platform would have chosen unasked. This requirement is the product's single statement of which per-user location is meant. Every requirement that places anything in a per-user directory cites this identifier rather than restating the property, and a mechanism placed there inherits it without having to assert it for itself.

It is stated at the definition because it cannot be stated correctly anywhere else. Each thing this product keeps in a per-user directory is individually harmless in a replicated location, and they are jointly wrong: a record that describes *this* machine — which process is the running instance (REQ-STARTUP-161), what this machine's setup has provisioned (REQ-STARTUP-071), what an artifact has prepared on it in order to run (REQ-STARTUP-165), and, in other domains, this machine's own session store (REQ-SESSION-198) and credential store (REQ-PROVIDER-014) — describes a machine it is not on as soon as it is replicated to a second one. A specification that leaves the choice to each mechanism yields a build that is defensible requirement by requirement and wrong overall, which is the failure this clause exists to prevent.

Per-workspace state is not per-user state and nothing in this clause reaches it. `<workspace>/.rotaris/` sits wherever the user put the workspace, on whatever storage they chose; the product SHALL NOT relocate it and SHALL NOT refuse it for being on storage shared with or replicated to another machine, which is a condition it reports and never refuses (REQ-STARTUP-166).

**REQ-STARTUP-146** — All desktop persisted-settings state SHALL live in the desktop preference store of REQ-SHELL-006 and REQ-CONFIG-463. This domain declares no store of its own and states none of that store's properties: it relies on REQ-SHELL-006 for the store's scoping, for its being disjoint from the layered YAML configuration surface, for its closed key table, and for its physical location and on-disk form being implementation choices. The keys owned by this domain are `workspace/lastOpened` (remembered project folder path) and `updates/dismissedVersion` (a single version string). The diagnostics keys this domain reads, `diagnostics/level` and `diagnostics/outputDir`, live in the same store and are owned by REQ-SHELL-163.

**REQ-STARTUP-147** — Environment variables read by this domain: `APPIMAGE` (AppImage self-identity, published by the AppImage runtime), `ROTARIS_BUNDLED` (`1` forces bundled-runtime semantics — a build-and-test override that exposes no product capability and is documented nowhere a user is directed to), the Windows command-interpreter variable (`COMSPEC`, fallback `cmd.exe`) for launching batch shims, and — on a platform whose artifact form publishes one — the variable by which that form names the artifact file a launch started from, which is how the update target of REQ-STARTUP-106 is identified where the running image is a preparation the artifact made of itself (REQ-STARTUP-165). `APPIMAGE` is the only variable of that last kind this document names; every variable of that kind is set by the artifact's own runtime rather than by a user, and its value is a file path and nothing else. No environment variable read by this domain selects a workspace, enables diagnostics, affects the update check in any way (REQ-STARTUP-111, REQ-STARTUP-129), names a release source or an update channel, or permits a second instance of the application to start (REQ-STARTUP-161); a variable naming the artifact a launch started from decides which file an update replaces and decides nothing about whether, when, or where the check happens, so the acceptance criterion of REQ-STARTUP-111 is unaffected by it. Variables written for child processes: `PATH`/`Path` (managed directories prepended), `UV_CACHE_DIR`, `npm_config_cache`.

### Cross-cutting invariants

**REQ-STARTUP-150** — Silence/visibility invariants: a launch that is handed to an instance already running is always silent — it surfaces a window and reports nothing at all (REQ-STARTUP-162); a failed update **check** is always invisible (log only); a failed update **install** is always visible (persistent error notice); a machine-setup failure is always recoverable (Retry or Continue-without-tool — the app never refuses to start because of setup) and is reported again at the point a degraded capability is used (REQ-STARTUP-154); a build not running from a released standalone artifact, and a demo window on any runtime, perform no update network traffic at all (REQ-STARTUP-057, REQ-STARTUP-106); an artifact preparing itself for launch, reusing a preparation, or redoing an unusable one is always silent — nothing is reported to the user on any of those paths — while an artifact that could produce no preparation at all is always warned about and, on the terms REQ-STARTUP-165 (c) states, never prevented from running, that being the one preparation outcome the product reports (REQ-STARTUP-165 (c), REQ-STARTUP-165 (f)); and a workspace on shared or synchronised storage is always warned about and never refused, while an unclassifiable one is passed over in silence (REQ-STARTUP-166).

**REQ-STARTUP-151** — Ordering invariants: a launch resolves the single-instance record before it builds anything (REQ-STARTUP-164), so no window is ever constructed by a launch that turns out to be a hand-over; the desktop paints before setup, setup before workspace onboarding, and repository discovery waits for setup when setup is pending; the update check and the workspace-storage determination of REQ-STARTUP-166 start only after the window is shown; an artifact that prepares itself completes that preparation before it paints, a run that can make no preparation completes the run-scoped placement REQ-STARTUP-165 (c) permits before it paints, and an artifact prepares afresh before running a version it has not prepared for (REQ-STARTUP-165); update install order download → verify → apply is monotone with failure stopping it; setup steps run in deterministic plan order with completion persisted at every step boundary; and the version guard and the package-pin guard precede all release builds.

**REQ-STARTUP-152** — The following agreements SHALL hold, each decidable from published artifacts, observed network traffic, and process output alone. The filenames a release publishes as assets, the filenames its `SHA256SUMS.txt` lists, and the filename an update client asks for on a given platform SHALL all be values of the single naming scheme of REQ-STARTUP-031 and SHALL agree, the manifest listing every published asset but itself and the signature published over it (REQ-STARTUP-032, REQ-STARTUP-108). A launch-time update check SHALL reach the host and path of REQ-STARTUP-105 and no other host or path. A `SHA256SUMS.txt` exactly as published SHALL be consumable unmodified both by the update path and by `sha256sum -c`, with no reformatting step in between (REQ-STARTUP-032, REQ-STARTUP-113); the signature over it is detached and leaves those bytes untouched, which is why both consumers still read the same file. The signature a release publishes over its `SHA256SUMS.txt` SHALL verify against a key carried inside the published artifacts of that same release, decidable from the published artifacts alone (REQ-STARTUP-167). The tool and MCP package versions a build provisions and warms SHALL be the versions pinned in the manifest that same build ships, and the same versions its `THIRD-PARTY-LICENSES.txt` reports (REQ-STARTUP-058, REQ-STARTUP-059, REQ-STARTUP-142). The executables an installation makes available SHALL be exactly the one entry point of REQ-STARTUP-002, and launching that entry point twice on one user account SHALL leave exactly one process of the application running, the second launch having been handed to the first (REQ-STARTUP-161, REQ-STARTUP-164). A preparation an artifact makes of itself in order to run (REQ-STARTUP-165) is not an executable an installation makes available and does not bear on that agreement: it is never installed, never registered, never placed on a search path, and never a thing a user is offered or directed to launch — launching the artifact is the only way it is ever reached. The same holds on the same terms of the run-scoped placement of REQ-STARTUP-165 (c). For every combination of preference values, configuration values, repository-root layout-configuration values, and environment variables a user can produce, the release source used by the update check SHALL still be the endpoint of REQ-STARTUP-105 (REQ-STARTUP-111).

**REQ-STARTUP-155** — Startup and setup timing SHALL be bounded as follows, each bound measured on the supported baseline of REQ-STARTUP-159 and REQ-STARTUP-024. The main window SHALL be painted within 5 seconds of the application being launched. That bound is on the launch that becomes the running instance; a launch handed to an instance already running paints no window of its own, is bounded instead by the hand-over interval of REQ-STARTUP-164, and where it does cause a window to be built (REQ-STARTUP-162, REQ-STARTUP-163) that window is bounded by this same 5 seconds. The bound SHALL be the same for every published artifact and every bundle mode — the `onefile` Windows portable executable of REQ-STARTUP-013 is given no larger budget than the `onedir` flavours, and no per-flavour differential is specified. There is exactly one exemption from it, stated next; it reaches no other artifact, no other bundle mode, and no other run.

**First-run exemption.** Where an artifact published in `onefile` mode prepares itself for launching under REQ-STARTUP-165, the run that performs that preparation is exempt from the 5-second bound, for the preparation it performs and for nothing else. Every other run of that artifact is bound by the 5 seconds exactly as every other artifact is. **"First run" means the first run of a given version of that artifact, on a machine, for the user who runs it — never the first run of the product and never the first run of the artifact family.** A machine that has already run an earlier version still performs a first run of the version now in front of it; a user who runs a version another user of the same machine has already run still performs a first run of it; and a run that prepares again because the existing preparation is incomplete, unreadable, or not the one belonging to this artifact (REQ-STARTUP-165 (c)) is a first run of that version for this purpose, so recovering from an unusable preparation never makes a build non-conformant. A run that produced no usable preparation at all, because the storage of REQ-STARTUP-165 (a) would not accept one, performs that same work and is exempt on the same terms and for the same reason: the condition lies in the machine's storage rather than in the build, and a build SHALL NOT be judged non-conformant for it. That run is the one preparation outcome that is not silent, and REQ-STARTUP-165 (c) fixes what it reports and where. This is still one exemption — it covers the run that does a preparation's work, however that run ends — and it still reaches no other artifact and no other bundle mode. Once an artifact has prepared, every later run of that same artifact SHALL paint within the 5 seconds this requirement fixes. The exemption reaches the first paint alone: the fast-path decision below is not exempt, and neither is the setup-pass bound below it. The exemption is stated so that a reader cannot take the silence of REQ-STARTUP-013 and REQ-STARTUP-031 — both of which are unchanged — as licensing a per-flavour budget: there is no per-flavour budget, only a per-artifact-version first run.

The fast-path decision of REQ-STARTUP-066 — establishing that the plan is empty — SHALL be reached within the 100 ms interface-responsiveness budget of REQ-SHELL-150 and SHALL delay neither the first paint nor the post-show activation of REQ-STARTUP-043. A setup pass in which every manifest tool is already satisfied (REQ-STARTUP-069) SHALL be bounded by the probe timeout it is built from and no more: its wall time SHALL NOT exceed the sum of the per-probe timeouts of REQ-STARTUP-063 over the manifest's tools, counted twice for the detect and record steps that both probe. No further timing is specified, and that is deliberate: download durations depend on the network, per-step pacing depends on the machine, and the visual rendering of the setup dialog and the update banner beyond their widget structure, text and accessibility metadata is a design matter this document does not fix. A build SHALL NOT be judged non-conformant for any of those three.

## Data & Formats

All formats below are externally observable (on disk, on the wire, or in process output).

- **Release tag grammar** (REQ-STARTUP-027): `v<major>.<minor>.<patch>` with optional `a<N>` / `b<N>` / `rc<N>` suffix. Plain versions are `stable`; suffixed are `prerelease` (REQ-STARTUP-029); ordering is REQ-STARTUP-109's.
- **Release artifact names** (single authority, REQ-STARTUP-031): `Rotaris-{v}-windows-x64-setup.exe`, `Rotaris-{v}-windows-x64-portable.exe`, `Rotaris-{v}-macos-arm64.dmg`, `Rotaris-{v}-linux-x86_64.AppImage`. There is no console-archive kind.
- **Checksum manifest** `SHA256SUMS.txt` (REQ-STARTUP-032, parsed per REQ-STARTUP-113): `"<sha256hex>  <filename>\n"` per asset, two-space separator, sorted by filename, `sha256sum -c` compatible, never self-listed, and never listing the signature published over it.
- **Manifest signature** `SHA256SUMS.txt.sig` (REQ-STARTUP-032, REQ-STARTUP-167): a detached signature over the manifest's exact published bytes, published as an asset of the same release, absent from the manifest and from the release-body asset table (REQ-STARTUP-035), and verified before the manifest is parsed (REQ-STARTUP-122). Every published artifact carries within itself the set of keys it accepts; that set is fixed when the build is produced and nothing at run time adds to, replaces, or disables it (REQ-STARTUP-167, REQ-STARTUP-168). The form of a key, the form of a signature, and how many keys a build carries are implementation choices and no surface of the product reports them.
- **Release feed consumption** (GitHub latest-release JSON): fields consumed are `tag_name`, `draft`, `prerelease`, `body`, and `assets[]` entries' `name`, `browser_download_url`, and integer `size` (0 when absent). Asset downloads follow a 302 redirect to a storage host.
- **Windows installer surface**: silent flags `/S` and `/D=<dir>`; per-user registry writes under `HKCU\Software\Rotaris` (`InstallDir`) and `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` (`DisplayName`, `DisplayVersion`, `Publisher`, `DisplayIcon`, `UninstallString`, `NoModify`, `NoRepair`); Start Menu folder `Rotaris` with `Rotaris.lnk` and `Uninstall Rotaris.lnk`.
- **Linux desktop entry**: `Type=Application`, `Name=Rotaris`, `Terminal=false`, `Categories=Development;IDE;`, Exec accepting an optional path argument, named icon.
- **Single-instance record** (REQ-STARTUP-161, REQ-STARTUP-164): one record per user account, outside every workspace and outside the desktop preference store, in the per-user location REQ-STARTUP-145 fixes, naming the process that is currently the running instance and how a launch reaches it. Its form and its placement within that location are implementation choices; the observable contract is that a launch either claims it and becomes the instance or is handed to the instance it names, that a launch waits at most 5 s for a hand-over that goes **unanswered**, and that at most one reclaim and two claim attempts occur before the launch ends. The 5 s bounds an unanswered hand-over and not a refused one: an instance that answers by refusing because it is shutting down stops that interval running at all, and the launch then waits for the shutdown instead, bounded by the force-exit allowance rather than by this figure (REQ-STARTUP-164, REQ-SHELL-169, REQ-MONITOR-131). No configuration key and no environment variable affects it (REQ-STARTUP-146, REQ-STARTUP-147).
- **Launch preparation** (REQ-STARTUP-165): where a `onefile` artifact prepares itself for launching, the preparation is held in the per-user data directories of REQ-STARTUP-145 — which that requirement fixes as the machine-local, non-replicated per-user location — and never beside the artifact or on the medium carrying it; it belongs to exactly the artifact contents that produced it, so a new or rebuilt artifact prepares afresh; an incomplete, unreadable, or foreign preparation is silently redone rather than reported, while a run that produces no usable preparation at all still starts, is exempt from the first-paint bound, and raises a persistent warning notice — the one preparation outcome reported anywhere — putting what it must run in a run-scoped placement that is removed when the run ends and that may lie only in those same per-user data directories or, where they accept no write at all, in the platform's per-user transient storage; it is produced from the artifact alone with no network request and no elevation; and it is not a published artifact — it never appears in `SHA256SUMS.txt`, never in the artifact set of REQ-STARTUP-031, and never as a download. Its form, its name, and its location within that storage are implementation choices. The update target stays the artifact the launch started from and is never the preparation (REQ-STARTUP-106, REQ-STARTUP-125).
- **Workspace-storage classification** (REQ-STARTUP-166): a workspace resolves to exactly one of three states — reachable by another machine, replicated by a file-synchronisation agent, or not classifiable. The first two raise a persistent warning notice and refuse nothing; the third is silent. The classification is derived from storage rather than from a failure, is not persisted anywhere, and adds no key to the desktop preference store (REQ-STARTUP-146).
- **Per-user setup layout** (under the per-user data directory of REQ-STARTUP-145, which is the machine-local, non-replicated one): `tools/<tool>/<version>/` (managed tool trees), `setup/state.json` (durable record, schema 1 — fields in REQ-STARTUP-071, of which `outcome`, `completed_at` and `versions` are fixed names shared with REQ-CONFIG-397), `setup/setup.lock` (transient JSON `{pid, created}`), `setup/cache/{downloads,uv,npm}/`. Partial downloads appear as `<name>.partial` beside their cache destination and stay eligible for resumption indefinitely (REQ-STARTUP-084).
- **Setup manifest** (schema 1, REQ-STARTUP-058, REQ-STARTUP-059, REQ-STARTUP-061): per-tool probe command and version args, optional minimum version, provisioned version, per-platform-key artifacts (HTTPS URL, 64-hex SHA-256, layout, expected executables), license, capabilities; plus exact MCP package pins. Fingerprint = SHA-256 over canonical JSON (sorted keys, compact separators).
- **Setup outcome vocabulary**: `complete` | `degraded` | `cancelled` | `already-running` (REQ-STARTUP-074); the first three, plus `running` and empty, are also the values persisted as `outcome` in the durable record. There is no textual output contract carrying them: they are rendered in the setup dialog (REQ-STARTUP-093), the settings card (REQ-STARTUP-102) and the per-step surface (REQ-STARTUP-153).
- **Persisted settings**: the desktop preference store REQ-SHELL-006 defines. Its scoping, its closed key table, and its on-disk form are stated there and are not restated here. The keys whose meaning this domain owns are `workspace/lastOpened` (string path) and `updates/dismissedVersion` (single version string), both registered in that table (REQ-STARTUP-146); `diagnostics/level` and `diagnostics/outputDir` are read from the same store and owned by REQ-SHELL-163.
- **Diagnostics run directory** (REQ-STARTUP-131, REQ-STARTUP-132): `<base>/<UTC yyyymmddTHHMMSSZ>-<pid>/` containing `manifest.json` (schema 3, self-checksummed), `metrics-NN.jsonl` and `spans-NN.jsonl` (rotating, 8 MiB × 4 each, REQ-STARTUP-133), `snapshots/NNNN-<reason>.json` (16 MiB total budget, REQ-STARTUP-133), `summary.json` (schema 3, REQ-STARTUP-137) and `summary.md`. JSON-lines readers tolerate a truncated final line (REQ-STARTUP-138).
- **Environment variables**: read — `APPIMAGE`, `ROTARIS_BUNDLED`, `COMSPEC`, and on a platform whose artifact form publishes one, the variable naming the artifact file a launch started from (REQ-STARTUP-147); written for children — `PATH`/`Path`, `UV_CACHE_DIR`, `npm_config_cache`. No environment variable configures diagnostics or the update check (REQ-STARTUP-129, REQ-STARTUP-111); a variable naming the artifact decides only which file an update replaces.
- **Key behavioral constants.** Every figure listed here is fixed by the requirement named beside it and restated here for convenience only; where this list and that requirement differ, the requirement governs. Three classes of figure are deliberately not among them, because this document states none of them and only cites them: the deferred first-paint delay, stated once by REQ-SHELL-011 and cited per REQ-STARTUP-044; the minimum window size and what must hold at it, stated once by REQ-SHELL-022 and cited per REQ-STARTUP-042; and every figure of the transient acknowledgement surface — its lifetime, its bounded width and its placement — stated once by REQ-NOTIFY-011, REQ-NOTIFY-013 and REQ-NOTIFY-012 and cited per REQ-STARTUP-054. The list: first paint within 5 s of launch — with the single first-run exemption REQ-STARTUP-155 states for a `onefile` artifact preparing itself, "first run" meaning the first run of that artifact version on a machine for that user (REQ-STARTUP-165) — and the empty-plan fast-path decision within the interface-responsiveness budget (REQ-STARTUP-155); single-instance hand-over wait 5 s, with at most one reclaim and two claim attempts (REQ-STARTUP-164); update-check timeout 10.0 s (REQ-STARTUP-105); update download/hash chunk 1 MiB (REQ-STARTUP-124); installer-hand-off auto-close 1200 ms (REQ-STARTUP-119); update-worker shutdown join 5000 ms (REQ-STARTUP-046); tool probe timeout 10 s (REQ-STARTUP-063); warm-up timeout 180 s (REQ-STARTUP-076); tool download connect timeout 30 s with 1 MiB blocks (REQ-STARTUP-084); setup lock staleness 900 s (REQ-STARTUP-072); banner summary limit 160 chars (REQ-STARTUP-112); setup dialog 760×560 (REQ-STARTUP-090); diagnostics 250 ms heartbeat, 1000 ms metric sampling, 300 s deep-mode interval, 2.0 s tracing window and 1.0 s slow threshold (REQ-STARTUP-133); diagnostics 1000 ms lag trigger, 60 s trigger cooldown, 256 MiB memory-growth trigger and 8-thread growth trigger (REQ-STARTUP-135); diagnostics 1 s close join (REQ-STARTUP-139); notices-exception expiry at most 365 days after review (REQ-STARTUP-143).
- **Diagnostics file layout**: field names and nesting are implementation-chosen and stable within a schema version; units are fixed — milliseconds for durations, bytes for memory and written volume, bytes per second for rates, whole numbers for percentages, ISO-8601 UTC for timestamps (REQ-STARTUP-157).
- **Exit codes**: pipeline only; see REQ-STARTUP-149. The application defines none.
- **Application entry**: one graphical entry point (REQ-STARTUP-002), and at most one running instance of it per user account (REQ-STARTUP-161) — a launch either becomes that instance or is silently handed to it, and several workspaces and several windows are windows of the one instance (REQ-STARTUP-162, REQ-STARTUP-163). The one directory a launch may carry is the workspace the operating system hands it (REQ-STARTUP-024, REQ-STARTUP-041); there is no argument vocabulary, no subcommand, no flag, no standard-output contract and no text-mode interface; the one reserved token `builtin:code-intelligence` is a sentinel for a child process the product starts itself (REQ-MCP-033, REQ-STARTUP-015).
