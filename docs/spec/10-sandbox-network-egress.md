# Command Sandboxing and Network Egress Policy

## Overview

The product gates outbound network access and confines shell command execution. Per-workspace configuration controls three cooperating surfaces: a per-host egress policy applied to the built-in URL-fetch tool (allow/ask/deny with allow and deny host lists), permission-layer gating of network-reaching terminal commands, and an operating-system confinement layer — inactive unless the workspace turns it on — that restricts terminal commands to a declared set of writable paths and carries a single on/off switch for network access. Every ambiguous or failing path resolves closed: an unclassifiable host is denied, confinement that cannot be proven working refuses to run commands rather than running them unconfined, and a permissive mode requested where no one can answer a prompt is tightened unless confinement is active or the workspace has explicitly opted out of that tightening. Confinement is available on two host operating systems and on no others, which is a closed set; on a host outside it the product says plainly, on both the settings surface and the launch surface, that nothing an agent runs there is confined.

## Requirements

### Egress configuration surface

- **REQ-SANDBOX-001** — The setting `runtime.network_egress_policy` (string) is the default disposition for a fetch target matching neither host list. Accepted values are exactly `allow`, `ask`, `deny`. The shipped default is `ask`. This requirement, with REQ-SANDBOX-002 for the matching of a stored spelling and REQ-SANDBOX-017 for the vocabulary's reach, is the product's single definition of the egress disposition vocabulary and its shipped default; no requirement in any other domain holds a second copy of either, and a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-002** — The disposition is matched with surrounding whitespace removed and letter case ignored, so `  ASK ` selects the `ask` policy. Any other spelling is refused rather than stored: a configuration file carrying it fails to load, and no later route that changes the setting on a running product — the desktop settings surface included — can install a value the loader would have refused, so the previously effective disposition stays in force. The refusal quotes the rejected value and lists `allow`, `ask`, and `deny`.
- **REQ-SANDBOX-003** — `runtime.network_allowed_hosts` and `runtime.network_denied_hosts` are lists of host patterns, each defaulting to the empty list. Allowed-list entries are permitted regardless of the default disposition; denied-list entries are refused even when an allow entry or a permissive default would otherwise permit them. This requirement, with REQ-SANDBOX-004 for load-time normalization and REQ-SANDBOX-014 for the order in which the two lists and the default are consulted, is the product's single definition of the two host-list keys, their defaults, their normalization and the rule that a denial wins; no requirement in any other domain holds a second copy of any of those, and a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-004** — At configuration load, each host-pattern entry is whitespace-trimmed and lowercased, and blank entries are dropped (given `"  GitHub.com "`, the stored value is `github.com`; given `"   "`, the entry is dropped). Wildcard grammar is NOT validated at load time; invalid wildcards surface at classification time (REQ-SANDBOX-016) and at UI entry (REQ-SANDBOX-114).
- **REQ-SANDBOX-005** — Configuration layers per field: a workspace-level config file at `<workspace>/.rotaris/agents.yaml` overrides the global config field-by-field; a field the workspace leaves unset keeps the global value, not the shipped default. All sandbox and egress fields participate in this layering.

### Host identity normalization

- **REQ-SANDBOX-006** — Before any list matching or classification, a URL or bare host name is reduced to one canonical host string by: folding to lower case; discarding a `user:pw@` prefix; discarding a `:port` suffix; removing the brackets around an IPv6 literal; removing one trailing root dot; and expressing non-ASCII labels in their IDNA (punycode) form. Required results: `https://Example.COM/path?q=1` → `example.com`; `http://user:pw@api.example.com:8443/x` → `api.example.com`; `example.com:8080` → `example.com`; `example.com.` → `example.com`; `http://[::1]:9000/` → `::1`; `127.0.0.1` → `127.0.0.1`; input that is empty or only whitespace → the empty string `""`. That empty string is the "unknown host" referred to throughout this domain.
- **REQ-SANDBOX-007** — Unicode and punycode spellings of one name are interchangeable in both directions: `https://bücher.example/` and `XN--BCHER-KVA.example` both reduce to `xn--bcher-kva.example`, so a list entry written either way matches a fetch target written either way and neither spelling slips past an entry written in the other. Where IDNA conversion of a name does not succeed, the trimmed lower-cased original text stands as that host's canonical string; being non-empty it is still compared against both host lists literally and is never treated as the unknown host of REQ-SANDBOX-008.
- **REQ-SANDBOX-008** — Input that cannot be reduced to a host yields the unknown host — the empty string `""`, never a partial or guessed name — and the unknown host resolves closed everywhere it can flow: classification yields deny; it matches no pattern; it counts as remote (and is therefore gated).

### Host pattern grammar and matching

- **REQ-SANDBOX-009** — The pattern grammar is: an exact host name, or a single leading `*.` wildcard — nothing else. Patterns are trimmed, lowercased, and trailing-dot-stripped before use. An empty pattern is an error whose message SHALL convey which host list the pattern came from and that a pattern may not be empty; the wording is the implementation's.
- **REQ-SANDBOX-010** — Any use of `*` not forming a single leading `*.` is rejected with an error whose message SHALL convey the rejected pattern, that this use of `*` is not accepted, and the only supported wildcard form, showing the literal example `*.example.com`; that example is fixed because it is a form the user copies, while the sentence around it is the implementation's. Patterns that must be rejected (never silently treated as literal host names): `api.*.com`, `exa*ple.com`, `*`, `*.*.com`, `example.*`. Rationale: accepting such a pattern quietly would leave an operator with a list that reads as configured while permitting no host at all.
- **REQ-SANDBOX-011** — Matching advances label by label; a hit that lands part-way through a label never counts. An exact pattern matches by equality after normalization (case-insensitive). A leading `*.` stands in for at least one label positioned to the left of the pattern's remainder, so `*.example.com` covers `api.example.com` and `a.b.example.com`, while bare `example.com` falls outside it. Excluding the bare name is intentional and mirrors the usual reading of wildcard certificates; operator documentation must state it, since covering both the bare name and its subdomains takes two entries.
- **REQ-SANDBOX-012** — Lookalike domains never match: `*.example.com` does not match `evilexample.com` or `evil-example.com`; exact `example.com` does not match `evil-example.com`, `example.com.evil.test`, or `notexample.com`.
- **REQ-SANDBOX-013** — The empty/unknown host matches no pattern of either kind.

### Egress classification

- **REQ-SANDBOX-014** — The denied list is consulted first, then the allowed list, then the default disposition. A specific denied entry therefore outranks a broader allowed wildcard: host `metadata.example.com` with allowed `["*.example.com"]`, denied `["metadata.example.com"]`, and default `allow` classifies as deny.
- **REQ-SANDBOX-015** — An allow-listed host is allowed even under a deny default (`registry.npmjs.org` with allowed `["*.npmjs.org"]` and default deny → allow). A host matching neither list resolves to the configured default disposition (under the shipped `ask` default, it routes to the approval path).
- **REQ-SANDBOX-016** — Classification fails closed: an unreadable/empty host resolves to deny; an unrecognized default-disposition string resolves to deny; the default disposition is compared after trim/lowercase. If a stored pattern is invalid (an unsupported wildcard reached the configuration), applying the policy is an error and the fetch is refused with `failure_kind` `egress_policy_error` (REQ-SANDBOX-032) — never treated as a literal, never fail-open.
- **REQ-SANDBOX-017** — The disposition vocabulary is exactly the strings `allow`, `ask`, `deny`, shared by the configuration field, classification results, and the permission engine's decision vocabulary.

### Local vs. remote classification

- **REQ-SANDBOX-018** — A target is on this machine when its canonical host string (REQ-SANDBOX-006) is one of the following, and otherwise it is not. (a) Exactly `localhost`, `localhost.localdomain`, or `ip6-localhost`. (b) An IPv4 address literal whose first octet is 127 — the whole `127.0.0.0/8` loopback range, not only `127.0.0.1`, reached through any URL spelling, so `127.0.0.1`, `127.0.0.2` and `127.1.2.3` are all local. The whole range is chosen because every address in it is loopback by definition and none of it leaves the machine, so admitting only the first would gate a genuinely local target. (c) An IPv6 address literal that is the loopback address, in any spelling that canonicalizes to it, `::1` and `0:0:0:0:0:0:0:1` alike. (d) An IPv4-mapped or IPv4-compatible IPv6 literal whose embedded IPv4 address satisfies (b), so `::ffff:127.0.0.1` and `::ffff:7f00:1` are local. The test is textual and performs no name resolution, so a name that happens to resolve to a loopback address is still remote. Everything else is remote and therefore gated, including the unspecified addresses `0.0.0.0` and `::`, private-range addresses such as `10.0.0.5`, and link-local addresses such as `169.254.169.254` (cloud metadata).
- **REQ-SANDBOX-019** — Anything not local is remote, including unparseable input: `""` and `"not a url at all"` count as remote, so an unreadable fetch target is gated rather than slipping through. `http://localhost:5173/index.html` is local.

### Fetch tool — request surface and defaults

- **REQ-SANDBOX-020** — A fetch request takes: `url` (required, no default); `max_lines` (integer, default 1000); `from_line` and `to_line` (optional, 1-based and inclusive, naming the first and last body line to return and defaulting to the first and last line of the body); and `timeout` (optional number, replacing the default of REQ-SANDBOX-021 for that call only). `timeout: 0` is accepted, is carried through as given rather than treated as absent, and means the call has no time limit — the same reading `runtime.approval_timeout_seconds: 0` carries in REQ-SANDBOX-053, so zero means "no deadline" everywhere in this domain and never "a deadline already past". A request is malformed, and is refused before any connection is opened, when any of these holds: `url` is absent, empty, or only whitespace; `timeout` is negative; `max_lines` is less than 1; `from_line` is less than 1; `to_line` is less than 1; or `to_line` is less than `from_line`. A malformed request yields `failure_kind` `invalid_request`, `is_error` true, a null `status_code`, `error_class` `InvalidFetchRequest`, and a detail naming the offending parameter, the value it carried, and the constraint it broke; the wording is otherwise free. Exactly one parameter need be named where several are malformed, but naming all of them is permitted.
- **REQ-SANDBOX-021** — The timeout for a fetch call is settled by exactly one precedence chain, highest first: the `timeout` parameter of that call, where present (REQ-SANDBOX-020); otherwise the owning run's `runtime.tool_call_timeout`, default 30 seconds (REQ-CONFIG-115), whenever the fetch tool is registered for a run; otherwise the built-in default of 10.0 seconds, which applies only where there is no owning run to read a value from. The lower level never overrides the higher, so a run-wired fetch with no `timeout` parameter always uses `runtime.tool_call_timeout` and never 10.0 seconds. The value in force is reported as `timeout_seconds` on the result (REQ-SANDBOX-035) whichever level supplied it.

### Fetch tool — egress enforcement

**Direct transport policy (REQ-SANDBOX-022, accepted OQ-37, 2026-09-07).** Every fetch hop MUST connect directly to its classified destination. Proxy environment variables, system proxy settings and process-global proxy configuration MUST have no effect on this tool. Tool help and direct-connect failures MUST disclose this policy. The tool MUST preserve per-hop classification and its existing failure vocabulary. Future proxy support requires an explicit policy amendment covering both destination and proxy endpoints.

- **REQ-SANDBOX-022** — Before any connection is opened, the policy is applied to the host of the requested URL and, separately, to the host of each redirect target. A server whose host resolves to deny observes zero connection attempts and zero requests.
- **REQ-SANDBOX-023** — Redirects are never followed automatically; each hop is re-classified before it is fetched. When a permitted host redirects to a denied host, the request is refused at that hop and the denied server sees nothing.
- **REQ-SANDBOX-024** — The redirect hop budget is 20. Exceeding it yields `failure_kind` `too_many_redirects`, `error_class` `TooManyRedirects`, and a detail whose required content is the hop budget that was exhausted and the fact that no terminal response was ever reached; the phrasing is the implementation's, and the budget figure is normative while its rendering is not.
- **REQ-SANDBOX-025** — The fetch `failure_kind` vocabulary is fixed by REQ-TOOLS-092 — the closed set of spellings, the fact that it is closed, and the agreement of `invalid_request` with the terminal observation's member of the same name all belong to that requirement, and this domain holds no copy of any of them and mints no further kind. What this domain relies on it for is that every outcome of a fetch this domain specifies reports exactly one of those spellings, and that a policy refusal is always distinguishable programmatically from a transient transport fault and from a malformed call, so an agent can tell what to re-plan around, what to retry, and what to correct. What this domain adds is which outcome each spelling reports: the named URL was denied → `egress_denied`; a redirect hop was denied or unapproved → `egress_redirect_denied`; the policy could not be applied → `egress_policy_error`; the hop budget was exhausted → `too_many_redirects` (REQ-SANDBOX-024); the call was malformed and no connection was attempted → `invalid_request` (REQ-SANDBOX-020); and the transport outcomes `timeout`, `network_error` and `http_error` (REQ-SANDBOX-033).
  > **Narrowed by [`PD-TOOLS-013`](../product/directives.md#pd-tools-013), 2026-10-13 (revision 2).** "Mints no further kind"
  > holds except for `interrupted`, which the directive adds to REQ-TOOLS-092's set for a fetch the run's signal ended: that
  > outcome is the run's rest, so it is neither a policy refusal, nor a transient transport fault, nor a malformed call, and
  > it is distinguishable from all three. Every other clause above still governs.
- **REQ-SANDBOX-026** — Every egress refusal (`egress_denied`, `egress_redirect_denied`, `egress_policy_error`) carries `error_class` `NetworkEgressDenied`, `is_error` true, an absent/null `status_code`, and a `detail` stating which host was refused and which policy input produced that outcome (the `runtime.network_egress_policy` setting or one of the host lists).
- **REQ-SANDBOX-027** — Under the `ask` disposition, approval for the URL the agent named is obtained before the fetch runs, so once the request is in flight that host counts as permitted for the rest of that request. Every hop is still classified against the policy (REQ-SANDBOX-022, REQ-SANDBOX-023); what an already-permitted host changes is only how an `ask` verdict resolves mid-chain. A hop landing on a host already permitted within this request is followed without a further approval, so a path-only redirect and an `http`→`https` redirect on the same host both complete under the shipped default, as does a redirect onto a host on the allow list. A `deny` verdict refuses the hop whatever preceded it (REQ-SANDBOX-014), and a hop onto a new host classifying `ask` is refused (REQ-SANDBOX-028).
- **REQ-SANDBOX-028** — A redirect onto a NEW host that classifies as `ask` is refused, since no approval can be sought once a request is in flight: `failure_kind` `egress_redirect_denied`, with a detail explaining that the hop originated from the requested URL, that the destination host was never approved, and that access to that destination has to be asked for as its own request when it is actually required.
- **REQ-SANDBOX-029** — Deny verdicts distinguish position: the initially named URL → `egress_denied`; a redirect hop to a host outside the permitted set → `egress_redirect_denied`.
- **REQ-SANDBOX-030** — A host allowed by verdict during a redirect chain remains permitted for later hops within the same request; hops returning to an already-permitted host are not re-gated.
- **REQ-SANDBOX-031** — Redirect target resolution, exhaustively: an absolute redirect target is used as given; a relative location value is resolved as a URI reference against the URL of the hop that returned it, and the resolved absolute URL — not the raw header text — is what REQ-SANDBOX-022 classifies before the next connection is opened; a redirect response carrying no location header, or one whose value is empty or only whitespace, ends the chain and that response is the final result, with `final_url` the URL of that hop, its own `status_code`, `truncated` computed from its body as usual, and no `failure_kind` unless its status is ≥ 400, in which case REQ-SANDBOX-033's `http_error` applies — a 3xx with no location is not by itself an error. A location whose host is internationalized is canonicalized by REQ-SANDBOX-006 and REQ-SANDBOX-007 before classification, so a Unicode spelling and its IDNA spelling classify identically and neither slips past a list entry written in the other. A location that cannot be resolved into an absolute URL bearing a host yields the unknown host of REQ-SANDBOX-008, which classifies deny, so the hop is refused with `failure_kind` `egress_redirect_denied` and no connection is opened.
- **REQ-SANDBOX-032** — When the policy itself cannot be applied to a host (e.g. an invalid stored pattern), the request is refused with `failure_kind` `egress_policy_error` and a detail naming the host and embedding the underlying error. The request is never executed — fail-closed, never fail-open.
- **REQ-SANDBOX-033** — Non-refusal failure outcomes, each detail stated as required content with the wording left free: a timeout yields `failure_kind` `timeout`, with a detail conveying the deadline that expired in seconds and which level of REQ-SANDBOX-021 supplied it; any other transport failure before a response yields `network_error`, with a detail conveying the host that was being contacted and the underlying transport error as the platform reported it, unaltered; an HTTP status ≥ 400 yields `is_error` true, `failure_kind` `http_error`, and a detail conveying the numeric status code, which is itself a machine-readable value and is also carried in `status_code`.
- **REQ-SANDBOX-034** — Response shaping: the body is split into lines; the `from_line`/`to_line` window is taken (1-based, both ends inclusive, a window reaching past the end of the body yielding the lines that exist, and a window starting past the end of the body yielding no lines with `truncated` false — an inverted or non-positive window having already been refused as malformed by REQ-SANDBOX-020); if the selection holds more than `max_lines` lines, only its first `max_lines` lines are returned and `truncated` is true; otherwise every selected line is returned and `truncated` is false. Lines left out by the window alone never make `truncated` true.
- **REQ-SANDBOX-035** — The fetch result exposes the fields listed in Data & Formats: `url` (as requested), `final_url`, `status_code`, `content_type`, `truncated`, `failure_kind`, `timeout_seconds`, `error_class`, `detail`.
- **REQ-SANDBOX-036** — Model-facing rendering is fixed in structure and free in wording. A policy refusal or transport failure renders, in order: a first line identifying the failure; a `[fetch_diagnostic]` block holding the result fields of REQ-SANDBOX-035 as one JSON object whose keys are in sorted order and whose null-valued fields are left out, `failure_kind` always among the keys present; and, when a body was received, a `[fetch_output]` block holding it. A success renders the header lines `url`, `final_url`, `status_code`, `content_type`, `truncated` in that order, one per line, followed by the body.
- **REQ-SANDBOX-037** — A fetch executed without run-scoped egress configuration defaults to a permissive policy (disposition `allow`, empty lists), so a wiring gap breaks nothing; this is not ungated overall because permission-layer gating of remote fetches still applies ahead of execution.
- **REQ-SANDBOX-038** — The effective egress policy is read from the owning run's current configuration at each fetch call: a SAVED edit to the host lists takes effect on the following fetch with no restart, while an edit still unsaved on the settings surface reaches nothing (REQ-SANDBOX-118), and two concurrent runs in one process each apply their own lists — one run's permitted hosts never extend to another.

### Permission-layer gating of network access

- **REQ-SANDBOX-039** — The fetch tool (model-facing tool name `fetch`) is classified both read-only and network-reaching. Host-scoped fetch gating is evaluated BEFORE any blanket read-only allowance (first match wins), so read-only status cannot bypass egress gating.
- **REQ-SANDBOX-040** — Each supervised mode (`restricted`, `ask`) carries two fetch rules, in order: `{mode}:fetch-remote-host` (decision ask; covers a fetch whose target is off-machine) then `{mode}:fetch-local-host` (decision allow; covers a fetch whose target stays on this machine). Both precede the mode's `{mode}:read-only-tool` rule.
- **REQ-SANDBOX-041** — A remote fetch under a supervised mode resolves through the remote-host rule (ask); when no approval channel is registered, the ask resolves fail-safe to deny. A loopback fetch (e.g. `http://127.0.0.1:5173/...`) resolves allow through the local-host rule.
- **REQ-SANDBOX-042** — The gated subject of a fetch permission decision is the URL itself; the URL appears as the gated command in decisions and the audit trail.
- **REQ-SANDBOX-043** — Which terminal command lines count as network-reaching is fixed by REQ-TOOLS-094: the catalogue of leading-token prefixes, the fact that it is closed and unordered, the cutting of a compound line into segments, the whole-token comparison, and the reading of a trailing `*` as zero or more further tokens all belong to that requirement, and this domain holds no copy of any of them, adds no prefix of its own, and states no second catalogue. What this domain relies on that requirement for is a single closed verdict on a command line — network-reaching or not — that the per-mode rule of REQ-SANDBOX-044 can attach a decision to, and that the verdict is settled by the command string alone, before execution, so it can be reached at permission time. That the verdict is a permission heuristic and never an enforcement boundary is stated here rather than there only in its consequence for this domain: nothing outside confinement stops a command the recognizer misses from reaching the network, and terminal traffic has no per-host filtering at all (REQ-SANDBOX-047).
- **REQ-SANDBOX-044** — The network-command rule per mode: `restricted` → deny (rule id `restricted:network-command`), `ask` → ask (rule id `ask:network-command`). Each matches its mode's default decision; the rules exist so refusals and the audit log name a specific rule id.
- **REQ-SANDBOX-045** — The `autonomous` mode carries NO fetch rules and NO network-command rule — only its destructive-command deny rules. Rationale: in that mode nothing is available to respond to a prompt, so such a rule would settle on deny and make the most permissive mode stricter than intended. `curl` or `pip install` under autonomous resolves allow via the mode default.
- **REQ-SANDBOX-046** — The permission-mode preset vocabulary, the default decision each preset carries, how a configured name resolves to a preset, and the restrictiveness ordering are fixed by REQ-TOOLS-041, REQ-TOOLS-046 and REQ-TOOLS-047; this domain holds no copy of any of them, mints no further mode, and states no second default. What it relies on those requirements for is that every mode named anywhere in this domain is one of exactly three; that a mode name this domain cannot recognize has already been resolved before any rule here is consulted, so no rule of this domain ever sees an unrecognized name; and that any two modes can be compared by restrictiveness, which is the comparison REQ-SANDBOX-106 performs against a persona pin.
- **REQ-SANDBOX-047** — For terminal commands, network access is all-or-nothing: confinement either opens or closes the network for the whole command and cannot distinguish destinations within it. Per-host allow/ask/deny is available only for the built-in fetch tool, whose connections the product makes itself. The limitation must be documented; destination-aware filtering of terminal traffic is out of scope.

### Sandbox configuration surface

- **REQ-SANDBOX-048** — `runtime.sandbox_mode` (string): `off` | `workspace-write` | `read-only`; default `off` (the sandbox is opt-in). Comparison ignores letter case; a value outside those three spellings fails validation both at load and at assignment, and the message names the bad value together with all three valid modes. This requirement is the product's single definition of the confinement-mode vocabulary, its shipped default and its validation, and the three spellings are stable persisted values (REQ-SANDBOX-055); no requirement in any other domain holds a second copy of the vocabulary, the default or the validation rule, and a requirement that needs them cites this one and states only what it adds. Those three are the whole vocabulary: an opportunistic fourth value — one meaning "confine where the host provides a mechanism and run without confinement where it does not" — is deliberately not offered, because a mode that can silently resolve to no confinement would have a run report protection it does not have, which is the silent fallback REQ-SANDBOX-074 forbids. A host that cannot provide the confinement a run asked for is settled by the availability verdict and the refusal that follows it (REQ-SANDBOX-071, REQ-SANDBOX-084), never by weakening the mode the user selected.
- **REQ-SANDBOX-049** — A bare YAML `sandbox_mode: off` (which YAML 1.1 parses as boolean false) must be read as the `off` mode, not rejected as a type error.
- **REQ-SANDBOX-050** — `runtime.sandbox_writable_roots` (list of strings, default empty) names absolute paths that are writable inside the sandbox in addition to the workspace. An entry keeps its text apart from stripped leading and trailing whitespace: no case folding, no separator rewriting, no symlink resolution. An entry that is empty or only whitespace names nothing and is DROPPED at load, exactly as a blank host pattern is under REQ-SANDBOX-004 — trimming already happens first, so treating the residue as a non-absolute path would refuse a whole configuration file over a stray blank line. An entry that is non-blank and not absolute is refused, both at load and at assignment, with a message that names the configuration key, quotes the entry, and states that an absolute path is required, following the rule and message shape REQ-TOOLS-116 fixes for this family of keys. Absoluteness is decided by spelling rather than by the host performing the check, so `/opt/cache` and `C:\Builds\cache` are both accepted in the same file on either platform and one configuration file serves a mixed fleet. A path need not exist when the configuration is read; REQ-SANDBOX-058 settles what happens to a root that is still missing at launch. This requirement is the product's single definition of the key, its default and its entry rules; a requirement that needs them cites this one and states only what it adds, and REQ-CONFIG-468 follows the same rule and message shape for a neighbouring key.
- **REQ-SANDBOX-051** — `runtime.sandbox_allow_network` (bool, default false): grants confined processes network access. It has effect only while a confinement mode other than `off` is selected. The shipped posture is closed. This requirement is the product's single definition of the key and its default; a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-052** — `runtime.allow_unsandboxed_autonomous` (bool, default false): per-workspace opt-in to run unattended in a permissive mode without a sandbox. Its documentation must warn that it belongs in one workspace's configuration rather than the global one.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The key above still exists with the same default and layering; it no longer has any effect on any run.
- **REQ-SANDBOX-053** — Adjacent settings that interact with this domain: `runtime.permission_mode`, whose preset vocabulary is REQ-TOOLS-041's and whose resolution and shipped default are REQ-TOOLS-046's, neither restated here; `runtime.headless_approval_policy`, whose accepted values, shipped default, reading of an unrecognized value and effect on a refused call are REQ-TOOLS-065's and are not restated here — what this domain relies on that requirement for is that an ask raised by a session with no registered approval presenter (REQ-TOOLS-053) always resolves without a prompt and never resolves to allow; `runtime.approval_timeout_seconds`, the single key REQ-CONFIG-126 registers for that bound, whose default this domain does not restate and on whose reading of a stored `0` — a wait without limit — REQ-SANDBOX-020 relies (REQ-TOOLS-055, REQ-TOOLS-178). `runtime.additional_read_only_roots` (REQ-TOOLS-132) is adjacent but does NOT interact with confinement: OS confinement imposes no read restriction whatsoever (REQ-SANDBOX-060), so that key widens the file tools' path fence alone and neither grants nor removes anything inside the sandbox.
- **REQ-SANDBOX-054** — All six sandbox/egress fields (`sandbox_mode`, `sandbox_writable_roots`, `sandbox_allow_network`, `network_egress_policy`, `network_allowed_hosts`, `network_denied_hosts`) survive a write-then-read cycle through the workspace YAML file: the configuration loaded afterwards is the same effective configuration that was saved, and a further save-and-load changes nothing again. The load-time normalizations stated elsewhere still apply on the way in — host patterns arrive trimmed and lower-cased with blanks dropped (REQ-SANDBOX-004), writable-root entries arrive trimmed (REQ-SANDBOX-050), and a YAML boolean false for `sandbox_mode` arrives as `off` (REQ-SANDBOX-049) — so what round-trips is the normalized value, not necessarily the raw text a user first typed.

### Confinement model

- **REQ-SANDBOX-055** — The mode spellings `off`, `workspace-write`, `read-only` are stable persisted values and must not change across releases.
- **REQ-SANDBOX-056** — The workspace-relative subpaths `.git` and `.rotaris` are always read-only inside the sandbox, even within an otherwise writable workspace. The exclusion is fixed: no setting and no configuration combination removes it. A confined command must therefore never be able to install a repository hook that would later run outside confinement, nor to write the configuration that governs a later run.
- **REQ-SANDBOX-057** — The exclusion attaches to the name a command would use rather than to whatever the name ultimately points at: when that name is a link, or a file standing in for a repository directory, writing through it is still refused.
- **REQ-SANDBOX-058** — Effective writable roots by mode, under an active confinement mode: `read-only` grants none; `workspace-write` grants the workspace root first and then each configured additional root, duplicates removed keeping the first occurrence. A configured additional root that does not exist on the host when the invocation is rendered is SKIPPED rather than treated as an error: the remaining roots apply, the command starts, and the skip is recorded as a log entry naming the path. A configured root is optional convenience and must not be able to stop a session; refusing to start on a missing one would make an unused entry fatal. The consequence is stated plainly so it cannot surprise: a skipped root is not writable inside that command even if the command itself creates the directory, because the writable set is fixed when the invocation is rendered and the next command re-renders it. The workspace root itself is not optional — it always exists, being the directory the session runs in (REQ-SANDBOX-091). Separately from the configured roots, every active mode leaves the platform's temporary location writable (REQ-SANDBOX-075, REQ-SANDBOX-076), so `read-only` means "no writable root beyond the temporary location", not "no writable path at all". Mode `off` renders no confinement whatsoever (REQ-SANDBOX-074), so effective writable roots do not apply to it and writes are bounded only by the host operating system.
- **REQ-SANDBOX-059** — The network inside the sandbox stays closed unless `sandbox_allow_network` is true.
- **REQ-SANDBOX-060** — Read access is intentionally unrestricted: a confined command can still read anywhere on the filesystem (e.g. reading `/etc/passwd` succeeds). Only write confinement and the network switch are enforced; restricting reads is deliberately not attempted, because ordinary developer tooling depends on wide read access.
- **REQ-SANDBOX-061** — Backend parity: the same configuration must produce identical write verdicts on both supported platforms, including for a protected subpath that does not yet exist (a fresh worktree with no `.git`/`.rotaris` must still deny creating or writing under those names) and for one that does. Absent that parity, a result observed on one platform would say nothing about the other.
- **REQ-SANDBOX-062** — The sandbox wrapper never changes the working directory: the command runs in the persistent shell's current directory identically on all platforms, sandboxed or not.
- **REQ-SANDBOX-063** — The submitted command travels into the confined environment as a SINGLE shell argument (`/bin/sh -c '<command>'`) and is never split apart again: a compound line containing variable references and quoted arguments with spaces arrives unchanged as the last token of the rendered invocation.
- **REQ-SANDBOX-064** — A workspace path containing quote or backslash characters must not be able to alter the confinement that is applied: every path embedded in the confinement rules and every argument of the rendered invocation must be quoted such that no crafted path can end its enclosing literal and introduce rules of its own.

### Sandbox availability

- **REQ-SANDBOX-065** — The confinement mechanism follows from the host operating system alone: macOS → Seatbelt (launcher `sandbox-exec`); Linux, a WSL2 distribution included → bubblewrap (launcher `bwrap`); every other operating system → no mechanism, `available` false and backend name `unavailable`. The choice is made before PATH is consulted and before any trial runs, so on macOS without `sandbox-exec` the diagnostic still names Seatbelt and on Linux without `bwrap` it still names bubblewrap, rather than either reporting an unsupported platform. The set of recognized platform identifiers is CLOSED and contains exactly two members: the identifier the host runtime reports for the macOS family, `darwin`, and the one it reports for the Linux family, `linux` — which a WSL2 distribution also reports. Comparison is by exact equality after trimming and lowercasing. Every other identifier, `win32` included, is unrecognized and yields `available` false with backend name `unavailable` and the diagnostics of REQ-SANDBOX-073. No legacy or historical identifier is recognized and none may be added: a clean-room product has no earlier release to stay compatible with, and an open-ended list of aliases could not be tested exhaustively — which is the very defect this closes.
- **REQ-SANDBOX-066** — Availability probing proceeds in increasing order of cost: platform check, then launcher lookup on PATH, then a trial launch. No subprocess is spawned once an earlier step has already failed.
- **REQ-SANDBOX-067** — Availability must be demonstrated rather than inferred: locating the launcher on PATH is required but does not settle the question, because a host that restricts unprivileged user namespaces can have the launcher installed while every launch fails. A disposable trial confinement is therefore launched at most once per process, and its result is cached for later probes. The verdict is binary: there is no partial or degraded availability, so a host whose namespace restrictions are only partly in force is either able to complete the trial, in which case it is `available`, or it is not. A cached verdict is never re-derived on its own; it is cleared only by the explicit re-check of REQ-SANDBOX-129 or by restarting the application. A host that completes the trial but later refuses a real confinement is not a hole in this rule: that command is refused by REQ-SANDBOX-083 or relabelled by REQ-SANDBOX-085 and never runs unconfined.
- **REQ-SANDBOX-068** — The one success criterion for the trial is termination with exit status 0 inside the trial timeout; whatever the trial writes to its output is irrelevant to a success verdict. Every other outcome yields `available` false with a reason identifying which of these occurred: the trial did not finish within 5 seconds and was terminated; the trial could not be started at all, with the reported launch error; the trial exited with status N, the reason then carrying the first non-empty line of its diagnostic output; the trial exited with status N having produced no output, which the reason states. An outcome that cannot be interpreted counts as a failure and never as a success — a wrong `unavailable` costs only stricter prompting, a wrong `available` would let commands run against the host with no confinement.
- **REQ-SANDBOX-069** — The trial launch timeout is 5.0 seconds. It is a hard bound, not a hint: a trial still running at 5.0 seconds is terminated and counts as a failure under REQ-SANDBOX-068, is never extended, and is never retried within the same process. A launcher slow enough to approach the bound is therefore reported unavailable, and the user's remedy is the re-check of REQ-SANDBOX-129. The probe never runs on the thread that draws the interface, so no surface waits on it (REQ-SANDBOX-129).
- **REQ-SANDBOX-070** — The trial goes through the real mechanism, never a stand-in. On macOS it runs `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` — the widest ruleset that still engages Seatbelt, so a failure implicates the mechanism rather than any single restriction. On Linux it uses the option rendering the product would produce for a read-only confinement rooted at `/` with no carve-outs and no writable roots, keeps the network namespace separate whatever `runtime.sandbox_allow_network` says, and ends in the same final tokens every rendered session invocation ends in — `-- /bin/sh -c 'true'` (REQ-SANDBOX-079), never a bare `-- true`, so that the interpreter step a real command depends on is exercised by the trial rather than left untested. The macOS trial deliberately does not follow that pattern: it stays the literal `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true`, because Seatbelt's failure mode is the profile rather than the exec chain and because REQ-SANDBOX-073 offers that exact line to the user as a command to run by hand. Rendering either trial invocation reads no path on the filesystem.
- **REQ-SANDBOX-071** — The availability verdict is a value with: `available` (bool); a backend name (`seatbelt` | `bubblewrap` | `unavailable`); `reason`, one sentence naming the cause; `remediation`, one sentence naming the suggested fix — reason and remediation empty when available. Those three fields are the complete answer the platform confinement service gives, and every surface that reports availability presents that same text: the desktop settings surface (REQ-SANDBOX-116), the per-session launch dialog (REQ-SANDBOX-119, REQ-SANDBOX-120), the run-refusal record of REQ-SANDBOX-126, and the application log. The guidance a user sees therefore never differs by surface.
- **REQ-SANDBOX-072** — The unavailability error renders as the reason, then the remediation on its own line; with no remediation, just the reason; with no reason, a generic line reporting that no OS-level confinement can be used on this host.
- **REQ-SANDBOX-073** — Diagnostic content per scenario. Each string quoted below must appear literally in the reason or the remediation as indicated, and each stated fact must be conveyed; the wording around them is free.
  - Native Windows: the reason states that no OS-level confinement is available on native Windows and names both supported pairings, macOS with Seatbelt and Linux with bubblewrap. The remediation offers two courses — running under a WSL2 distribution with bubblewrap installed, quoting `sudo apt-get install bubblewrap`, or leaving `runtime.sandbox_mode` at `off`.
  - Unrecognized operating system: the reason quotes the platform identifier actually detected and does not claim the host is Windows. The remediation names macOS and Linux/WSL2 as the supported hosts.
  - Seatbelt selected on a host that is not macOS, or its launcher not found: the text quotes `sandbox-exec`, states that macOS supplies it, and suggests checking that `/usr/bin` is on PATH.
  - Bubblewrap launcher not found: the remediation quotes both `sudo apt-get install bubblewrap` and `sudo dnf install bubblewrap`.
  - Bubblewrap trial failure: the reason carries the launcher's own diagnostic output as described in REQ-SANDBOX-068. The remediation quotes `kernel.apparmor_restrict_unprivileged_userns` and `/proc/sys/kernel/unprivileged_userns_clone` as the controls gating unprivileged user namespaces, quotes `bwrap --ro-bind / / --proc /proc --unshare-net -- true` as a command to try by hand, and states that a workspace requesting confinement keeps failing for as long as the launcher fails — never that its runs proceed unconfined, which REQ-SANDBOX-074 and REQ-SANDBOX-084 forbid.
  - Seatbelt trial failure: the remediation quotes `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` as a command to try by hand.
- **REQ-SANDBOX-074** — There is no silent fallback: preparing a command for confinement either yields a NEW confined command string or reports an availability error; it never yields the original command. The single exception is mode `off`, which passes the command through unchanged on every platform and performs no probing.

### Rendered OS confinement (observable invocations)

- **REQ-SANDBOX-075** — Observable behavior of the macOS profile: everything is refused unless allowed. Permitted in every active mode — executing and forking processes, reading sysctl values, sending signals, reading any path on the filesystem, writing under the temporary locations `/tmp`, `/private/tmp`, `/var/tmp`, `/private/var/tmp`, `/private/var/folders`, and writing data to the device nodes `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/tty`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr`, `/dev/dtracehelper`. In `workspace-write`, each effective writable root of REQ-SANDBOX-058 additionally permits writes throughout its subtree, one allowance per root, with the protected subpaths of REQ-SANDBOX-056 denied; those denials appear after every allowance in the profile, the position at which they take effect, so a write under `<workspace>/.git` or `<workspace>/.rotaris` fails while a write elsewhere in the workspace succeeds. In `read-only` no writable root appears and writes succeed only at the temporary locations and device nodes named above. The network is permitted or refused as a whole according to `runtime.sandbox_allow_network`, with no distinction by destination (REQ-SANDBOX-047).
- **REQ-SANDBOX-076** — Linux confinement invocation behavior: the entire root filesystem bound read-only; device and proc filesystems provided; a fresh empty temp filesystem at `/tmp`; each effective writable root re-bound writable; the excluded subpaths applied after those writable binds, since ordering decides the outcome and an exclusion placed before the workspace bind would simply be covered over; the network namespace kept separate unless the opt-in grants network; and the confined process terminated together with its parent.
- **REQ-SANDBOX-077** — On Linux the rendering for a protected subpath (`.git`, `.rotaris`) turns on where the path sits and whether it exists, and in every case a write to that name inside confinement fails:
  - (a) The path lies outside every writable root, as in `read-only` mode: nothing extra is rendered. The read-only root already refuses the write, and the session starts normally.
  - (b) The path exists inside a writable root: it is re-bound read-only in the form that tolerates a missing source, `--ro-bind-try <p> <p>`. Its real contents stay readable, so `git status` keeps working under confinement; writes to it fail; and the command still starts if the path is removed between rendering and launch.
  - (c) The path does not exist inside a writable root, as in a freshly created worktree holding neither directory: an empty read-only filesystem is mounted at that name, rendered `--tmpfs <p>` followed by `--remount-ro <p>`. The name reads as empty and nothing can be created under it. A confined command must not be able to bring `.git` or `.rotaris` into existence where they were absent.

  Every carve-out of this requirement exists only inside the confined process's own mount view and leaves nothing behind on the host: once the command ends, the host filesystem holds exactly what it held before with respect to that name, so a protected subpath absent under case (c) is still absent afterwards and no empty directory remains for anything to clean up. A backend that cannot establish a carve-out without creating a host-visible file or directory SHALL NOT create one; it refuses the command under REQ-SANDBOX-083 instead.
- **REQ-SANDBOX-078** — Where the existence check of REQ-SANDBOX-077 races a filesystem change, the outcome lands on the restrictive side: a protected subpath created after the check stays hidden behind the empty read-only mount, its real content neither readable nor writable inside that command; a protected subpath deleted after the check does not stop the command starting, the tolerant bind of case (b) accepting a missing source; and a symlink with no target counts as an absent path, taking case (c). If the carve-out cannot be established at launch, the command does not run: it is refused exactly as in REQ-SANDBOX-083, with `failure_kind` `sandbox_unavailable` and exit code 126, and under no circumstances does it run with the carve-out missing. That refusal is scoped to the one command and SHALL NOT end the session: the session already passed the start-time availability gate (REQ-SANDBOX-094), the cause is per-command and may be a transient filesystem race, and the next command submitted is rendered and launched afresh. A session that keeps failing this way keeps refusing commands and never runs one unconfined.
- **REQ-SANDBOX-079** — Final wrapped command shapes: macOS — `sandbox-exec -p '<profile>' /bin/sh -c '<command>'`; Linux — `bwrap <options…> -- /bin/sh -c '<command>'`. All items are shell-quoted. Each confined command starts a fresh inner shell initialized from the session's configured working directory and environment. Working-directory changes, exports and aliases inside that invocation end with it. Unconfined foreground commands retain the persistent-shell contract of REQ-TOOLS-097. Tool descriptions and observations MUST explain which lifetime is in force; the confinement wrapper preserves the configured initial working directory under REQ-SANDBOX-062.
- **REQ-SANDBOX-127** — The rendered invocation is a means, not the contract. A confinement backend SHALL be judged conformant only by the observable effect on a live process on a real host of the platform concerned, and a rendering that matches REQ-SANDBOX-075 to REQ-SANDBOX-079 word for word but does not produce that effect is non-conformant. The effects that must be demonstrated on each supported platform, under an active confinement mode, are: a write inside an effective writable root of REQ-SANDBOX-058 succeeds; a write anywhere outside every effective writable root and outside the platform's temporary locations is refused; a write under `<root>/.git` or `<root>/.rotaris` is refused whether or not the subpath existed beforehand (REQ-SANDBOX-056, REQ-SANDBOX-061, REQ-SANDBOX-077); a read of a path outside every writable root succeeds (REQ-SANDBOX-060); an outbound socket is refused while `runtime.sandbox_allow_network` is false and succeeds while it is true (REQ-SANDBOX-059); and the working directory the command observes is unchanged by confinement (REQ-SANDBOX-062). No backend may be reported `available` on the strength of a rendered string alone, and no substitute or emulated backend may satisfy this check on behalf of an absent one.
- **REQ-SANDBOX-128** — A denial that occurs INSIDE an active confinement is the host operating system's own. The product does not interpret, translate, normalize, annotate, or retry it: whatever error the platform gives the confined program is what that program sees, the program's own output reaches the terminal observation unchanged, and no requirement in this domain turns on a particular error number or system-log entry. A write refused by confinement is therefore indistinguishable, to the agent and to the user, from a write refused by ordinary file permissions, and that is deliberate — the alternative would require the product to parse platform-specific errors it cannot enumerate. Such a command is an ordinary nonzero-exit command: it is never labelled `sandbox_unavailable`, which REQ-SANDBOX-085's launcher-prefix test reserves for confinement that failed to START.

### Terminal-tool enforcement

- **REQ-SANDBOX-080** — Every newly submitted terminal command in a session with an active confinement mode is confined, whether it runs in the foreground or is started in the background. A background command is confined on exactly the terms its foreground equivalent would be, so asking for background execution is not a way around the sandbox.
- **REQ-SANDBOX-081** — Confinement is applied only to a NEW command string. Excluded: text directed at an already-running process as its input, because confining it would deliver the wrapper text into that process's input, whereas an interrupt keystroke must arrive unaltered; a command that is empty or only whitespace, which is a request to collect further pending output; a request to list sessions; and a control call that carries only a session identifier. A request carrying BOTH a background flag and a session identifier counts as a new spawn and is confined, so that this documented-invalid combination cannot become a single-field bypass.
- **REQ-SANDBOX-082** — Wrapping is idempotent per issuance: a repeated or retried command is wrapped exactly once; wrappers never nest.
- **REQ-SANDBOX-083** — Wrap-time failure (unavailability, or ANY error raised while wrapping, e.g. a broken platform integration): the command is not executed — nothing reaches the shell or the background registry — and a refusal observation is returned with: `failure_kind` `sandbox_unavailable`, `is_error` true, exit code 126 — the conventional code for a command that exists but could not be run, chosen so that outcome classification cannot mistake a command that never executed for a successful one — outcome kind `sandbox_unavailable` with severity `error`, `error_class` fixed to `SandboxUnavailableError`, and a detail recording that the session requires OS-level confinement, that confinement could not be applied, that the command was consequently not executed, and what the underlying error was. The machine-readable product classification is the stable `failure_kind`/outcome pair. An implementation exception name MAY appear only in optional, redacted diagnostic detail; it MUST NOT change `error_class`.
- **REQ-SANDBOX-084** — Such a failure must not be absorbed by general-purpose error or retry handling: under no circumstances may a confinement failure lead to the command being run without confinement.
- **REQ-SANDBOX-085** — A command whose confining invocation was rendered successfully but failed at startup — the kernel refusing the namespace, for instance — is relabelled `sandbox_unavailable` only when all four of these hold: the command was confined by this call; the exit status is nonzero; no failure kind has been assigned yet, so a command stopped by the hard timeout stays `timeout`; and every non-empty line of the command's captured output begins with a launcher prefix, `bwrap:` for bubblewrap or `sandbox-exec:` or `sandbox_apply:` for Seatbelt. The test covers standard output and standard error together, as one set of captured lines, not standard error alone: its purpose is to establish that the command produced no output of its own, and a line on standard output is exactly such evidence, so a command that wrote an ordinary line to standard output before the launcher failed is NOT relabelled. One non-empty line without such a prefix, on either stream, prevents relabelling, so a program that merely fails inside a working sandbox is never reported as broken confinement; a command that produced no output at all is not relabelled either. The detail states that confinement could not be started, that the command therefore never executed, that the cause lies in the host's configuration rather than in the command, and that neither retrying nor rewording the command changes the outcome. The relabelling applies to a foreground result and equally to the result of polling or terminating a background command, since a background spawn returns before the failure is visible and the failure first shows at the next poll.
- **REQ-SANDBOX-086** — The reported observation shows the command as the agent submitted it, not the confining invocation; showing the latter would obscure the request and encourage the model to alter the confinement machinery instead. Background execution must still be demonstrably confined — polled output reflects the confined execution — while the observation text continues to show the submitted command.
- **REQ-SANDBOX-087** — The terminal tool's model-facing documentation must explain that `failure_kind` `sandbox_unavailable` indicates the command never executed, that the cause is the host's configuration, that neither a retry nor a reformulated command helps, and that the detail and output should be relayed to the user. `sandbox_unavailable` is part of the observation's `failure_kind` vocabulary alongside `timeout`, `invalid_request`, `execution_error`.
- **REQ-SANDBOX-088** — With no sandbox configured, the shell receives exactly the characters the caller submitted, with no probing and no added cost.
- **REQ-SANDBOX-089** — Sandboxing does not change terminal session scheduling: a sandboxed terminal session serializes its commands exactly as an unsandboxed one.

### Session binding and launch

- **REQ-SANDBOX-090** — Configuration that sets no confinement mode means `off`. A confinement-mode value that the session layer cannot recognize is an error and must never be treated as "no confinement": such a value indicates validation did not run, and quietly settling on `off` there would be precisely the kind of unannounced downgrade this specification rules out.
- **REQ-SANDBOX-091** — Confinement is rooted at whichever directory the session genuinely executes in — an isolated worktree while worktree isolation is in use, otherwise the workspace itself — so that the writable area coincides with the location of the files the run works on. The configured additional writable roots and the network opt-in are carried through into that confinement.
- **REQ-SANDBOX-092** — The check performed before a run starts either names the mechanism that will confine it or fails with a reason and remediation; it never returns a "no confinement" result, so a caller that receives a positive answer can rely on the next command actually being confined. Mode `off` is not treated as a failure.
- **REQ-SANDBOX-093** — Confinement status is a pair (active, backend name), where active requires the mode to be both selected AND actually available; selection alone is insufficient. Mode off → (false, ""); selected but unavailable → (false, ""), with the backend name left empty so that no record names a mechanism that never ran; selected and available → (true, name).
- **REQ-SANDBOX-094** — A run whose configuration asks for confinement the host cannot deliver does not start, and starting it without confinement is prohibited. Whatever confinement fact is recorded for a run always agrees with the verdict that governed whether it was allowed to start, so no run is ever recorded as confined while its commands ran unconfined, nor recorded as unconfined while confinement applied.
- **REQ-SANDBOX-095** — On a host that cannot deliver the requested confinement, session start fails and reports the availability reason and remediation of REQ-SANDBOX-071. No usable session, and no shell able to run a command outside confinement, is left behind. This requirement is canonical for the whole domain and agrees with REQ-TOOLS-118: a session requiring confinement the host cannot deliver DOES NOT START. The alternative reading — a session that starts and refuses every command — is rejected: it produces a run that can plan but never act, which serves the user worse than an immediate refusal carrying a reason and a remediation. The `sandbox_unavailable` refusal of REQ-SANDBOX-083 is not thereby unreachable; it remains the outcome whenever wrapping fails at command time on a host where confinement was proved available at start (REQ-SANDBOX-078).
- **REQ-SANDBOX-096** — Runs are isolated from one another: when one process hosts two live runs, one confined and one not, the commands of each follow the setting in force when that run began. An altered confinement setting applies to the next session started, with no re-registration or process restart.
- **REQ-SANDBOX-097** — Ordering at launch: the availability decision is settled before the run does anything else, so a request for confinement the host cannot deliver fails immediately with that mechanism's reason rather than at the first shell command — and certainly never by executing that command unconfined. When it fails, the session lock is released and anything this launch created is cleaned up. The decision is written into run state before the session is announced as ready.

### Downgrade of unattended permissive runs

- **REQ-SANDBOX-098** — The confinement input to permission-mode resolution requires both selection AND availability; configuration alone never satisfies it. Because a run requesting confinement the host cannot deliver never starts (REQ-SANDBOX-095), no live run ever reaches mode resolution in the "selected but unavailable" state, so at resolution time confinement is inactive exactly when `runtime.sandbox_mode` is `off` and active exactly when a non-off mode was proved available under REQ-SANDBOX-067. Selection alone must never count as present: treating it as present would remove the tightening while commands executed unconfined, which is the combination this requirement exists to prevent.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The pair above still governs confinement status; it no longer feeds a downgrade — the status is recorded, and the mode is unaffected by it.
- **REQ-SANDBOX-099** — The downgrade of a permissive mode for an unattended, unconfined run — its three conditions, the mode it downgrades to, the modes it leaves untouched, and the fact that resolution never raises — is fixed by REQ-TOOLS-067; this domain holds no copy of it and states no second rule. What it adds is the reading of that requirement's confinement condition within this domain: confinement counts as active exactly when a `runtime.sandbox_mode` other than `off` was proved available under REQ-SANDBOX-067, and selection alone never satisfies it (REQ-SANDBOX-098).
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The reading above still governs confinement status; there is no downgrade for it to feed — the requested mode always applies.
- **REQ-SANDBOX-100** — Resolution yields four things: the mode that will apply, the mode that was requested, a flag true only when the applied mode is more restrictive than the requested one, and a user-facing reason. The reason is produced only while that flag is true, and it names both modes, states that nothing can answer an approval prompt for this run and that confinement is not active, and quotes `runtime.allow_unsandboxed_autonomous: true` as the workspace setting that keeps the requested mode in place. When the flag is false the applied mode equals the requested mode and no reason is shown.
- **REQ-SANDBOX-101** — A run counts as attended when, at the moment its mode is resolved, an approval prompt for its session can be put in front of a person; otherwise it is unattended and eligible for tightening. The condition is exactly the one REQ-TOOLS-053 fixes and REQ-TOOLS-069 applies to a run, and this domain holds no second copy of it. It is a test of **capability, not of registration**: a presenter that is registered but cannot actually put a prompt in front of anyone does not make a run attended, so a conformance test written from this requirement and one written from REQ-TOOLS-053 must agree on every case, and a session whose presenter is present but wedged is unattended under both. What the test deliberately does not reach is what happens *after* a prompt that can be shown has been shown: whether it is ever answered is settled by `runtime.approval_timeout_seconds` and `runtime.headless_approval_policy` (REQ-SANDBOX-053, REQ-SANDBOX-102), and a presentation that fails at the moment it is attempted is settled by the `presenter-error` denial of REQ-TOOLS-058. Neither of those is an input to mode resolution, and neither re-resolves a mode already resolved. A session that cannot put a prompt to a person — because no presenter was ever wired for it, or because the presenter it had was torn down — is unattended and is tightened; and every run being desktop-started, that is the only way an unattended run arises. A session that can put a prompt to a person is attended and keeps its requested mode.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The attended/unattended test above still governs; it no longer alters any mode — an unattended run keeps its requested mode.
- **REQ-SANDBOX-102** — That tightening never goes further than `ask` is REQ-TOOLS-067's and is not restated here. What this domain relies on it for is that a tightened run still reaches the approval path rather than a flat deny, so that where no prompt can be shown each such ask is then settled by `runtime.headless_approval_policy` (default deny; `abort` halts the run).
- **REQ-SANDBOX-103** — Each agent in a run resolves its own effective mode against the conditions in force when that agent starts work — whether a prompt can be answered for the session, whether confinement is active, and the value of `runtime.allow_unsandboxed_autonomous` — so a change to any of those inputs governs agents that start afterwards without the run being restarted. The requested mode is whichever of these is present, highest precedence first: a persona-level pin, then a session-level override, then `runtime.permission_mode`. Where that agent is tightened, a warning naming the persona it applied to is logged.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The precedence above still governs; no agent is ever tightened — each applies the recorded name directly.
- **REQ-SANDBOX-104** — The announcement made at run start stamps the effective permission mode, the confinement flag, and the backend name from one reading of status, so the stored snapshot and the mode decision cannot conflict. Tightening is surfaced three ways: a logged warning; a system message in the run transcript; and a diagnostics timeline event `permission_mode_downgraded` (actor `permissions`) with metadata `requested_mode` and `effective_mode`.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The stamp above still governs; no downgrade is ever surfaced — the announcement records the requested (= effective) mode, and no `permission_mode_downgraded` event is emitted.
- **REQ-SANDBOX-105** — The chain end to end, for an `autonomous` run with no approval presenter on a host where the launcher exists but the trial fails, in three cases. Where `runtime.sandbox_mode` is `off`, no confinement was requested, so the run starts, is tightened to `ask` under REQ-SANDBOX-099, and is recorded as unconfined with an empty backend name. Where a non-off mode is requested, the run does not start at all (REQ-SANDBOX-095, REQ-SANDBOX-126) and no mode resolution occurs, since there is no run to resolve for. On the same host once the trial succeeds and a non-off mode is requested, the run keeps `autonomous` — confinement being active removes the third tightening condition — and is recorded as confined together with the backend name.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The start/refuse cases above still govern; the tightening case no longer applies — an `off` run starts and keeps `autonomous`.
- **REQ-SANDBOX-106** — A permission-mode change made part-way through a session is resolved on exactly the terms used at run start (REQ-SANDBOX-099), against that session's approval channel and its current confinement status, and agents already working receive the new mode without a restart. What the session stores is the REQUESTED mode, not the effective one, so agents started later resolve again for the circumstances then in force. A persona-level pin is not always overridden, and the direction of the change decides. Comparing the requested mode against the pin by the restrictiveness ordering REQ-TOOLS-047 fixes, which is not restated here (REQ-SANDBOX-046): where the change is MORE RESTRICTIVE than the pin, the pin gives way and that persona takes the new mode; where the change would be MORE PERMISSIVE than the pin, the pin stands, that persona keeps its pinned mode, and the persona is listed in `skipped_personas`; where the change equals the pin, nothing about that persona changes and it is not listed, since nothing was skipped in effect. The asymmetry follows the fail-closed posture of this domain: a user tightening mid-session must be able to tighten everything, while loosening must never happen behind a pin the user deliberately set. The change appends one entry to the session audit log with `event` `permission_mode_change` carrying `timestamp`, `session_id`, `agent_id`, `requested_mode`, `effective_mode`, `previous_mode`, `source`, `reason`, and `skipped_personas`; a companion diagnostics timeline event `permission_mode_changed` (actor `permissions`) repeats `requested_mode`, `effective_mode`, `previous_mode`, `source`, and `skipped_personas`. Failing to write that record never prevents the change taking effect. An override belongs to one session: it is never visible to another run in the same process, and it does not outlive the run, so a resumed session starts again from the mode its configuration names.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The change mechanics above still govern; the resolution step no longer applies — the change is applied directly, and agents started later apply the recorded name directly.
- **REQ-SANDBOX-107** — The per-session launch dialog of REQ-SANDBOX-119 produces an advisory before launch whenever the session being started would be unattended under REQ-SANDBOX-101. It is empty when such work can proceed (confinement active, or the permissive mode opted into). Otherwise it is a corrective sentence that names the mode that will apply, notes that tightening occurred where it did, explains that every tool call would be refused because no approval prompt can be answered, and lists the corrections — setting `runtime.permission_mode: autonomous` together with `runtime.allow_unsandboxed_autonomous: true`, or enabling `runtime.sandbox_mode`. It advises rather than blocks: because `ask` is the shipped default, blocking would block every workspace that has not been configured. The dialog displays the advisory and the launch proceeds, and the run reports whatever refusals then occur.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The advisory above still governs except that it never claims a downgrade was applied; an `autonomous` run proceeds with an empty advisory.

### Persistence, events, and audit

- **REQ-SANDBOX-108** — The session's resumable state carries `sandboxed` (bool, default false) and `sandbox_backend` (string, default ""), stamped at run start, so a completed session can later be checked for whether its shell ran unconfined; the same two facts are recorded once into the launch audit (REQ-SESSION-016, REQ-SESSION-138), which is what makes the check answerable after the run is over. Where that state is held is REQ-SESSION-001's and is not fixed here. A state written before these keys existed reads back as unconfined with an empty backend, which correctly describes those runs, and no schema migration is needed.
- **REQ-SANDBOX-109** — The run-start event on the session event stream, which every run emits, carries `sandboxed` (bool) — the availability VERDICT, not the configured mode.
- **REQ-SANDBOX-110** — The run-start event carries `permission_mode`, whose value is drawn from the preset vocabulary REQ-TOOLS-041 fixes (not restated here) and which SHALL report the EFFECTIVE mode after any tightening — the mode the run's decisions will actually resolve under — never the requested mode. This is the only reading consistent with the single-reading stamp of REQ-SANDBOX-104, and it makes `permission_mode: autonomous` alongside `sandboxed: false` unreachable on a run whose decisions all resolve as `ask`. The requested mode is not lost: whenever the two differ, the `permission_mode_downgraded` timeline event of REQ-SANDBOX-104 is emitted from that same reading of status and carries `requested_mode` and `effective_mode`, so a reader can always recover both, and the absence of that event means the two were equal. The audit trail (REQ-SANDBOX-104, REQ-SANDBOX-112) remains the authoritative record of the mode that applied.
  > **Narrowed by [`PD-TOOLS-002`](../product/directives.md#pd-tools-002), 2026-09-21.** The event above still governs and still carries the mode the run resolves under; the two are now always equal, so `permission_mode: autonomous` alongside `sandboxed: false` is reachable.
- **REQ-SANDBOX-111** — *Withdrawn.* Its only observable surface was a process's standard output and its exit status, neither of which exists in a graphical-only product; the machine-readable record of a run refused for unavailable confinement is carried by REQ-SANDBOX-126.
- **REQ-SANDBOX-112** — Permission decisions, the fetch host rules and network-command rules among them, are recorded into the session's permission audit (REQ-TOOLS-078, REQ-SESSION-137), each entry recording the identifier of the rule that decided; a refusal states which rule produced it. A user must be able to read that audit outside this application, so a confinement decision can be checked without trusting this application's own account of it (REQ-SESSION-199).
- **REQ-SANDBOX-126** — Given a run is refused at start because the host cannot deliver the confinement mode its configuration selects (REQ-SANDBOX-094, REQ-SANDBOX-095), then that refusal SHALL be the first and only entry on that run's event stream: a terminal result entry with status `error` whose text carries the availability reason and the remediation of REQ-SANDBOX-071 verbatim, with no run-start event, no agent activity, and no tool event before or after it. The text is the same text the launch notice of REQ-SANDBOX-120 shows, so the recorded stream and what the user was told never differ. No session snapshot is written for such a run, since REQ-SANDBOX-095 leaves no session behind.

### Desktop settings and launch surfaces

- **REQ-SANDBOX-113** — The desktop settings surface (runtime section) exposes all six sandbox/egress settings so that no YAML has to be edited by hand: a sandbox-mode selector; a writable-roots list with an entry field and add button; a toggle for allowing network inside the sandbox; an egress-policy selector; allowed-hosts and denied-hosts lists each with an entry field and add button; and a per-list problem label. All six round-trip: saving writes the workspace config the product loader reads back, and a reopened settings view shows every value on its control.
- **REQ-SANDBOX-114** — Each control validates on the same terms as the stored schema, so nothing invalid can reach the saved policy: entering a relative writable root is rejected at the control with a problem message mentioning "absolute path", with nothing stored and no unsaved-changes state; entering a host pattern with a wildcard other than a single leading one is rejected with a problem message describing the wildcard restriction and showing the supported form `*.example.com`.
- **REQ-SANDBOX-115** — The controls teach the two rules users most often get backwards: the egress-policy description states that a denied host stays denied (deny wins), and the host-lists description states that `*.example.com` does not match `example.com` on its own.
- **REQ-SANDBOX-116** — A label reflects the current availability result: that confinement is turned off, when it is; an active state naming the backend when a non-off mode is selected on a capable host; and, on a host that cannot deliver it, an unavailable state carrying the mechanism's reason and remediation and warning that sessions will fail to start rather than start unconfined. Selecting a mode on such a host is still STORED, since the setting exists for hosts that can honor it. Where the host provides no confinement mechanism at all, this label is not the whole of what the user must be told: the plain disclosure of REQ-SANDBOX-130 accompanies it, and is shown whatever mode is selected.
- **REQ-SANDBOX-117** — Loosening the default disposition to `allow` requires an explicit confirmation first; declining leaves both the stored policy and the control showing the earlier value.
- **REQ-SANDBOX-118** — Saving validates every value against the stored schema before anything is written. If any value is refused, the surface reports which one and writes nothing: the workspace configuration on disk is left exactly as it was and still loads. Reloading the workspace re-reads that file and refills the controls, without marking the form as holding unsaved changes and without writing anything back. Edits that have not been saved reach NOTHING: a run started while the settings surface holds unsaved sandbox or egress edits uses the configuration persisted on disk, since REQ-SANDBOX-038 reads the owning run's current configuration and that configuration is what the loader read from the file. Any other rule would make a run's confinement and egress policy depend on unwritten interface state that no record could later reproduce. Because that is easy to get wrong, the surface SHALL make it visible: while the runtime section holds unsaved changes to any of the six sandbox/egress settings, it shows an unsaved-changes indication, and starting a session in that state produces a warning conveying which settings differ from the saved configuration and that the run will use the saved values. The warning advises and does not block.
- **REQ-SANDBOX-119** — The per-session launch dialog offers an enable-OS-sandbox checkbox: checked launches the session with mode `workspace-write`; unchecked with `off`. On a host where the probe reports unavailable, the checkbox is disabled and cleared, and the mechanism's reason AND remediation appear both in the tooltip and as text visible without hovering, since a tooltip alone does not count as informing the user. A workspace that requests no confinement launches as usual.
- **REQ-SANDBOX-120** — Where the workspace configuration itself demands confinement on a host that cannot deliver it, the launch dialog's checkbox remains CHECKED and disabled, so the host never appears to switch the setting off. The run then fails before the agent loop begins, with a notice whose title conveys that the run did not get underway and whose body carries the reason and remediation. Neither a session nor a session lock remains afterwards.
- **REQ-SANDBOX-121** — A workspace indicator naming the backend appears only for a session whose recorded result is confined, and is hidden for sessions that are not. With several sessions open it tracks the focused one, and `sandboxed`/`sandbox_backend` are recorded in each session's snapshot.
  > **Narrowed by [`PD-SHELL-008`](../product/directives.md#pd-shell-008), 2026-10-06.** The indicator is a status-strip
  > item after the file-access flag, reading `sandbox: <backend>`, or `sandbox: confined` for a record written before
  > the backend was recorded. The rest above is unchanged.
- **REQ-SANDBOX-122** — The confinement mode in force for a session has exactly two sources and no third: the layered configuration field `runtime.sandbox_mode` (REQ-SANDBOX-048, REQ-SANDBOX-005), and the per-session override offered by the launch dialog of REQ-SANDBOX-119. No environment variable, no launch argument, and no other route of any kind can select or change it, which agrees with REQ-TOOLS-114's rule that no launch-time override exists outside that dialog. A session started without touching the dialog control takes the configured value.
- **REQ-SANDBOX-129** — The runtime section of the desktop settings surface carries a re-check control beside the availability label of REQ-SANDBOX-116. Activating it discards the cached verdict of REQ-SANDBOX-067 and runs a fresh probe, so a user who has just installed the launcher or lifted a namespace restriction can make the product see it without restarting the application. The label enters a checking state within the product's 100 ms interface responsiveness budget and the probe runs off the interface thread, so neither the settings surface nor any other view blocks for the up-to-5.0-second trial of REQ-SANDBOX-069; when the probe finishes the label shows the new verdict's reason and remediation. A fresh verdict governs sessions started afterwards and never changes the recorded confinement fact of a session already running (REQ-SANDBOX-094, REQ-SANDBOX-096).
- **REQ-SANDBOX-130** — On a host for which no confinement mechanism exists at all — any operating system outside the closed two-member set of REQ-SANDBOX-065, native Windows included and most consequentially, it being the desktop platform this product expects most of its users to be on — the product SHALL state that plainly, in its own words, rather than leave the user to infer it from a remediation string, a disabled control, or the absence of an indicator. The fact to be conveyed is a single one and it is the same on both surfaces below: **this host cannot confine anything, so every command an agent runs executes with the same operating-system privileges as the account running the application, reaching whatever that account can read and whatever it can write, and no value of `runtime.sandbox_mode` changes that here.** The disclosure SHALL be text and SHALL NOT rely on colour or on a control's disabled appearance to carry it (REQ-SHELL-149). It SHALL name what would change the answer — running the workspace on a host the product can confine (REQ-SANDBOX-073) — and SHALL NOT present the host as misconfigured or as needing repair, because it is neither: this is a stated limit of the product on that platform, and telling a user to fix something that is not broken teaches them to ignore the notice.

  Two surfaces carry it, and both carry it whatever `runtime.sandbox_mode` is set to, `off` included — `off` being the shipped default (REQ-SANDBOX-048) and therefore the state in which nearly every such user will be:
  - **The settings surface.** The runtime section shows the disclosure alongside the availability label of REQ-SANDBOX-116, without the user having to select a confinement mode first. Selecting one is how a user *asks* about confinement, and a user who never asks is precisely the user who does not know to.
  - **The launch surface.** The per-session launch dialog of REQ-SANDBOX-119 shows the disclosure before the run begins, together with whatever advisory REQ-SANDBOX-107 produces. It is shown for attended and unattended sessions alike, and it is shown when that advisory is empty: an attended run on such a host is exactly as unconfined as an unattended one, so a launch surface that spoke only about who can answer approvals would tell the user the smaller half of what is true. REQ-SANDBOX-107's emptiness rule governs that advisory's own text and does not suppress this disclosure. Like the advisory, the disclosure advises and never blocks a launch.

  This requirement adds no capability and changes no verdict. The set of recognized platforms stays closed at two members and none may be added (REQ-SANDBOX-065); no opportunistic mode that could silently resolve to no confinement is offered (REQ-SANDBOX-048); a run that requests confinement on such a host still does not start (REQ-SANDBOX-095); and a run that requests none still starts and still runs unconfined. What it adds is that the user learns this from the product before their first command runs, rather than from a diagnostic string they would only see by asking for something the host cannot give them.

### Contracts with neighboring subsystems

- **REQ-SANDBOX-123** — Verification checks and probes run through the same terminal enforcement point as everything else, so permission policy, confinement, and timeout-termination semantics apply to them without modification; no separate, less-checked execution path exists for them.
- **REQ-SANDBOX-124** — Lifecycle hooks that the user configures sit deliberately OUTSIDE both confinement and the permission policy: they are the user's own code, executed in the user's shell on the host. Accountability for them rests on the audit trail, and the boundary must be stated in the documentation.
- **REQ-SANDBOX-125** — No model-provider integration may expose provider-side tool execution that steps around these layers: provider-supplied built-in tools are off by default, and any tool call routed from a provider is executed by the product's own execution path so that permission gating and confinement continue to apply.

Workspace config lives at `<workspace>/.rotaris/agents.yaml` and overrides the global config per field.

### Host pattern grammar

`pattern := exact-host | "*." host` — a single leading `*.` and nothing else; comparison by whole label; the wildcard stands for at least one leading label and does not include the bare name itself; any other use of `*` is a configuration error.

### Fetch result shape

Fields: `url` (requested), `final_url`, `status_code` (null on refusal), `content_type`, `truncated` (bool), `failure_kind`, `timeout_seconds`, `error_class`, `detail`.

`failure_kind` vocabulary (fetch): not restated here — REQ-TOOLS-092 (REQ-SANDBOX-025). What this domain adds is the `error_class` each kind carries: egress refusals carry `error_class: NetworkEgressDenied` (REQ-SANDBOX-026); the redirect-budget failure carries `error_class: TooManyRedirects` (REQ-SANDBOX-024); a malformed request carries `error_class: InvalidFetchRequest` (REQ-SANDBOX-020).

Fetch timeout precedence (REQ-SANDBOX-021), highest first: the call's `timeout` parameter; the owning run's `runtime.tool_call_timeout` (30 s); the built-in 10.0 s, reachable only with no owning run. `timeout: 0` means no time limit.

Model-facing rendering: failure = error header + `[fetch_diagnostic]` JSON block (sorted keys, nulls omitted) + optional `[fetch_output]`; success = `url:` / `final_url:` / `status_code:` / `content_type:` / `truncated:` header lines + body.

### Terminal observation additions

`failure_kind` vocabulary (terminal): `timeout`, `invalid_request`, `execution_error`, `sandbox_unavailable`. Sandbox refusal observation: exit code `126`, outcome kind `sandbox_unavailable`, severity `error`. Sandbox-launcher output prefixes used for relabeling: `bwrap:`, `sandbox-exec:`, `sandbox_apply:`; the prefix test spans standard output and standard error together (REQ-SANDBOX-085).

### Network-reaching command pattern catalogue

Not restated here. The catalogue of leading-token prefixes, and the segmentation and token-matching rules that apply it, are REQ-TOOLS-094's; this document holds no copy of them (REQ-SANDBOX-043).

### Permission rule identifiers (observable in refusals and audit)

Format `{mode}:{rule-name}`. Known ids in this domain: `restricted:fetch-remote-host`, `restricted:fetch-local-host`, `ask:fetch-remote-host`, `ask:fetch-local-host`, `restricted:network-command`, `ask:network-command`, `{mode}:read-only-tool`; mode-default decisions appear as `preset:{mode}`.

### Rendered OS confinement invocations

- macOS: `sandbox-exec -p '<profile>' /bin/sh -c '<command>'`, where the profile is default-deny, allows exec/fork/sysctl-read/signal, allows whole-filesystem reads, allows writes to the temp subpaths and device nodes listed in REQ-SANDBOX-075 plus one allowance per writable root, then denies each carve-out (after all allows), then allows or denies network wholesale.
- Linux: `bwrap --die-with-parent --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp [--bind <root> <root> …] [carve-outs] [--unshare-net] -- /bin/sh -c '<command>'`, with carve-outs rendered per REQ-SANDBOX-077 (`--ro-bind-try <p> <p>` when present; `--tmpfs <p>` + `--remount-ro <p>` when absent; nothing when outside writable roots).
- Availability trials: `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` (macOS); on Linux, the product's own read-only-rooted rendering with the network namespace unshared, ending in `-- /bin/sh -c 'true'`, the same final tokens every rendered session invocation uses (REQ-SANDBOX-070, REQ-SANDBOX-079). Trial timeout 5.0 s, a hard bound with no retry within a process.

### Persistence and event shapes

- Session resumable state: keys `sandboxed` (bool, default false), `sandbox_backend` (string, default ""). Older states without the keys read as unsandboxed. This document names no location for it (REQ-SESSION-001).
- Run-start stream event: includes `sandboxed` (bool, availability verdict) and `permission_mode` (the effective mode after tightening, REQ-SANDBOX-110).
- Diagnostics timeline event on downgrade: name `permission_mode_downgraded`, actor `permissions`, metadata `requested_mode`, `effective_mode`.
- Diagnostics timeline event on a mid-session mode change: name `permission_mode_changed`, actor `permissions`, metadata `requested_mode`, `effective_mode`, `previous_mode`, `source`, `skipped_personas`.
- Permission audit (REQ-TOOLS-078, REQ-SESSION-137): entries name the deciding rule id. A mid-session mode change appends an entry with `event: permission_mode_change` plus `timestamp`, `session_id`, `agent_id`, `requested_mode`, `effective_mode`, `previous_mode`, `source`, `reason`, `skipped_personas` (list of strings, empty when no persona pin was left standing).
- Exit codes: a sandbox-refused command's observation reports exit code 126 — a child process's status inside a tool observation, not this product's own.
- Run refused for unavailable confinement: a single terminal result entry with status `error` on the run's event stream, carrying the availability reason and remediation (REQ-SANDBOX-126); nothing precedes or follows it.
