# Command Sandboxing and Network Egress Policy — Egress configuration surface

Part 1 of 6 of [domain 10](../10-sandbox-network-egress.md), which indexes every part. Defines REQ-SANDBOX-001 – REQ-SANDBOX-047.

## Requirements

### Egress configuration surface

- **REQ-SANDBOX-001** — The setting `runtime.network_egress_policy` (string) is the default disposition for a fetch target matching neither host list. Accepted values are exactly `allow`, `ask`, `deny`. The shipped default is `ask`. This requirement, with REQ-SANDBOX-002 for the matching of a stored spelling and REQ-SANDBOX-017 for the vocabulary's reach, is the product's single definition of the egress disposition vocabulary and its shipped default; no requirement in any other domain holds a second copy of either, and a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-002** — The disposition is matched with surrounding whitespace removed and letter case ignored, so `  ASK ` selects the `ask` policy. Any other spelling is refused rather than stored: a configuration file carrying it fails to load, and no later route that changes the setting on a running product — the desktop settings surface included — can install a value the loader would have refused, so the previously effective disposition stays in force. The refusal quotes the rejected value and lists `allow`, `ask`, and `deny`.
- **REQ-SANDBOX-003** — `runtime.network_allowed_hosts` and `runtime.network_denied_hosts` are lists of host patterns, each defaulting to the empty list. Allowed-list entries are permitted regardless of the default disposition; denied-list entries are refused even when an allow entry or a permissive default would otherwise permit them. This requirement, with REQ-SANDBOX-004 for load-time normalization and REQ-SANDBOX-014 for the order in which the two lists and the default are consulted, is the product's single definition of the two host-list keys, their defaults, their normalization and the rule that a denial wins; no requirement in any other domain holds a second copy of any of those, and a requirement that needs them cites this one and states only what it adds.
- **REQ-SANDBOX-004** — At configuration load, each host-pattern entry is whitespace-trimmed and lowercased, and blank entries are dropped (given `"  GitHub.com "`, the stored value is `github.com`; given `"   "`, the entry is dropped). Wildcard grammar is NOT validated at load time; invalid wildcards surface at classification time (REQ-SANDBOX-016) and at UI entry (REQ-SANDBOX-114).
- **REQ-SANDBOX-005** — Configuration layers per field: a workspace-level config file at `<workspace>/.rotaris/agents.yaml` overrides the global config field-by-field; a field the workspace leaves unset keeps the global value, not the shipped default. All sandbox and egress fields participate in this layering.

### Host identity normalization

- **REQ-SANDBOX-006** — Before any list matching or classification, a URL or bare host name is reduced to one canonical host string by: folding to lower case; discarding a `user:pw@` prefix; discarding a `:port` suffix; removing the brackets around an IPv6 literal; removing one trailing root dot; and expressing non-ASCII labels in their IDNA (punycode) form. Required results: `https://Example.COM/path?q=1` → `example.com`; `http://user:pw@api.example.com:8443/x` → `api.example.com`; `example.com:8080` → `example.com`; `example.com.` → `example.com`; `http://[::1]:9000/` → `::1`; `127.0.0.1` → `127.0.0.1`; input that is empty or only whitespace → the empty string `""`. That empty string is the "unknown host" referred to throughout this domain.
- **REQ-SANDBOX-007** — Unicode and punycode spellings of one name are interchangeable in both directions: `https://bücher.example/` and `XN--BCHER-KVA.example` both reduce to `xn--bcher-kva.example`, so a list entry written either way matches a fetch target written either way and neither spelling slips past an entry written in the other. Where IDNA conversion of a name does not succeed, the trimmed lower-cased original text stands as that host's canonical string; being non-empty it is still compared against both host lists literally and is never treated as the unknown host of REQ-SANDBOX-008.
- **REQ-SANDBOX-008** — Input that cannot be reduced to a host yields the unknown host — the empty string `""`, never a partial or guessed name — and the unknown host resolves closed everywhere it can flow: classification yields deny; it matches no pattern; it counts as remote (and is therefore gated).

### Host pattern grammar and matching

- **REQ-SANDBOX-009** — The pattern grammar is: an exact host name, or a single leading `*.` wildcard — nothing else. Patterns are trimmed, lowercased, and trailing-dot-stripped before use. An empty pattern is an error whose message SHALL convey which host list the pattern came from and that a pattern may not be empty; the wording is the implementation's.
- **REQ-SANDBOX-010** — Any use of `*` not forming a single leading `*.` is rejected with an error whose message SHALL convey the rejected pattern, that this use of `*` is not accepted, and the only supported wildcard form, showing the literal example `*.example.com`; that example is fixed because it is a form the user copies, while the sentence around it is the implementation's. Patterns that must be rejected (never silently treated as literal host names): `api.*.com`, `exa*ple.com`, `*`, `*.*.com`, `example.*`. Rationale: accepting such a pattern quietly would leave an operator with a list that reads as configured while permitting no host at all.
- **REQ-SANDBOX-011** — Matching advances label by label; a hit that lands part-way through a label never counts. An exact pattern matches by equality after normalization (case-insensitive). A leading `*.` stands in for at least one label positioned to the left of the pattern's remainder, so `*.example.com` covers `api.example.com` and `a.b.example.com`, while bare `example.com` falls outside it. Excluding the bare name is intentional and mirrors the usual reading of wildcard certificates; operator documentation must state it, since covering both the bare name and its subdomains takes two entries.
- **REQ-SANDBOX-012** — Lookalike domains never match: `*.example.com` does not match `evilexample.com` or `evil-example.com`; exact `example.com` does not match `evil-example.com`, `example.com.evil.test`, or `notexample.com`.
- **REQ-SANDBOX-013** — The empty/unknown host matches no pattern of either kind.

### Egress classification

- **REQ-SANDBOX-014** — The denied list is consulted first, then the allowed list, then the default disposition. A specific denied entry therefore outranks a broader allowed wildcard: host `metadata.example.com` with allowed `["*.example.com"]`, denied `["metadata.example.com"]`, and default `allow` classifies as deny.
- **REQ-SANDBOX-015** — An allow-listed host is allowed even under a deny default (`registry.npmjs.org` with allowed `["*.npmjs.org"]` and default deny → allow). A host matching neither list resolves to the configured default disposition (under the shipped `ask` default, it routes to the approval path).
- **REQ-SANDBOX-016** — Classification fails closed: an unreadable/empty host resolves to deny; an unrecognized default-disposition string resolves to deny; the default disposition is compared after trim/lowercase. If a stored pattern is invalid (an unsupported wildcard reached the configuration), applying the policy is an error and the fetch is refused with `failure_kind` `egress_policy_error` (REQ-SANDBOX-032) — never treated as a literal, never fail-open.
- **REQ-SANDBOX-017** — The disposition vocabulary is exactly the strings `allow`, `ask`, `deny`, shared by the configuration field, classification results, and the permission engine's decision vocabulary.

### Local vs. remote classification

- **REQ-SANDBOX-018** — A target is on this machine when its canonical host string (REQ-SANDBOX-006) is one of the following, and otherwise it is not. (a) Exactly `localhost`, `localhost.localdomain`, or `ip6-localhost`. (b) An IPv4 address literal whose first octet is 127 — the whole `127.0.0.0/8` loopback range, not only `127.0.0.1`, reached through any URL spelling, so `127.0.0.1`, `127.0.0.2` and `127.1.2.3` are all local. The whole range is chosen because every address in it is loopback by definition and none of it leaves the machine, so admitting only the first would gate a genuinely local target. (c) An IPv6 address literal that is the loopback address, in any spelling that canonicalizes to it, `::1` and `0:0:0:0:0:0:0:1` alike. (d) An IPv4-mapped or IPv4-compatible IPv6 literal whose embedded IPv4 address satisfies (b), so `::ffff:127.0.0.1` and `::ffff:7f00:1` are local. The test is textual and performs no name resolution, so a name that happens to resolve to a loopback address is still remote. Everything else is remote and therefore gated, including the unspecified addresses `0.0.0.0` and `::`, private-range addresses such as `10.0.0.5`, and link-local addresses such as `169.254.169.254` (cloud metadata).
- **REQ-SANDBOX-019** — Anything not local is remote, including unparseable input: `""` and `"not a url at all"` count as remote, so an unreadable fetch target is gated rather than slipping through. `http://localhost:5173/index.html` is local.

### Fetch tool — request surface and defaults

- **REQ-SANDBOX-020** — A fetch request takes: `url` (required, no default); `max_lines` (integer, default 1000); `from_line` and `to_line` (optional, 1-based and inclusive, naming the first and last body line to return and defaulting to the first and last line of the body); and `timeout` (optional number, replacing the default of REQ-SANDBOX-021 for that call only). `timeout: 0` is accepted, is carried through as given rather than treated as absent, and means the call has no time limit — the same reading `runtime.approval_timeout_seconds: 0` carries in REQ-SANDBOX-053, so zero means "no deadline" everywhere in this domain and never "a deadline already past". A request is malformed, and is refused before any connection is opened, when any of these holds: `url` is absent, empty, or only whitespace; `timeout` is negative; `max_lines` is less than 1; `from_line` is less than 1; `to_line` is less than 1; or `to_line` is less than `from_line`. A malformed request yields `failure_kind` `invalid_request`, `is_error` true, a null `status_code`, `error_class` `InvalidFetchRequest`, and a detail naming the offending parameter, the value it carried, and the constraint it broke; the wording is otherwise free. Exactly one parameter need be named where several are malformed, but naming all of them is permitted.
- **REQ-SANDBOX-021** — The timeout for a fetch call is settled by exactly one precedence chain, highest first: the `timeout` parameter of that call, where present (REQ-SANDBOX-020); otherwise the owning run's `runtime.tool_call_timeout`, default 30 seconds (REQ-CONFIG-115), whenever the fetch tool is registered for a run; otherwise the built-in default of 10.0 seconds, which applies only where there is no owning run to read a value from. The lower level never overrides the higher, so a run-wired fetch with no `timeout` parameter always uses `runtime.tool_call_timeout` and never 10.0 seconds. The value in force is reported as `timeout_seconds` on the result (REQ-SANDBOX-035) whichever level supplied it.

### Fetch tool — egress enforcement

**Direct transport policy (REQ-SANDBOX-022, accepted OQ-37, 2026-09-07).** Every fetch hop MUST connect directly to its classified destination. Proxy environment variables, system proxy settings and process-global proxy configuration MUST have no effect on this tool. Tool help and direct-connect failures MUST disclose this policy. The tool MUST preserve per-hop classification and its existing failure vocabulary. Future proxy support requires an explicit policy amendment covering both destination and proxy endpoints.

- **REQ-SANDBOX-022** — Before any connection is opened, the policy is applied to the host of the requested URL and, separately, to the host of each redirect target. A server whose host resolves to deny observes zero connection attempts and zero requests.
- **REQ-SANDBOX-023** — Redirects are never followed automatically; each hop is re-classified before it is fetched. When a permitted host redirects to a denied host, the request is refused at that hop and the denied server sees nothing.
- **REQ-SANDBOX-024** — The redirect hop budget is 20. Exceeding it yields `failure_kind` `too_many_redirects`, `error_class` `TooManyRedirects`, and a detail whose required content is the hop budget that was exhausted and the fact that no terminal response was ever reached; the phrasing is the implementation's, and the budget figure is normative while its rendering is not.
- **REQ-SANDBOX-025** — The fetch `failure_kind` vocabulary is fixed by REQ-TOOLS-092 — the closed set of spellings, the fact that it is closed, and the agreement of `invalid_request` with the terminal observation's member of the same name all belong to that requirement, and this domain holds no copy of any of them and mints no further kind. What this domain relies on it for is that every outcome of a fetch this domain specifies reports exactly one of those spellings, and that a policy refusal is always distinguishable programmatically from a transient transport fault and from a malformed call, so an agent can tell what to re-plan around, what to retry, and what to correct. What this domain adds is which outcome each spelling reports: the named URL was denied → `egress_denied`; a redirect hop was denied or unapproved → `egress_redirect_denied`; the policy could not be applied → `egress_policy_error`; the hop budget was exhausted → `too_many_redirects` (REQ-SANDBOX-024); the call was malformed and no connection was attempted → `invalid_request` (REQ-SANDBOX-020); and the transport outcomes `timeout`, `network_error` and `http_error` (REQ-SANDBOX-033).
  > **Narrowed by [`PD-TOOLS-013`](../../product/directives/pd-tools-013.md#pd-tools-013), 2026-10-13 (revision 2).** "Mints no further kind"
  > holds except for `interrupted`, which the directive adds to REQ-TOOLS-092's set for a fetch the run's signal ended: that
  > outcome is the run's rest, so it is neither a policy refusal, nor a transient transport fault, nor a malformed call, and
  > it is distinguishable from all three. Every other clause above still governs.
- **REQ-SANDBOX-026** — Every egress refusal (`egress_denied`, `egress_redirect_denied`, `egress_policy_error`) carries `error_class` `NetworkEgressDenied`, `is_error` true, an absent/null `status_code`, and a `detail` stating which host was refused and which policy input produced that outcome (the `runtime.network_egress_policy` setting or one of the host lists).
- **REQ-SANDBOX-027** — Under the `ask` disposition, approval for the URL the agent named is obtained before the fetch runs, so once the request is in flight that host counts as permitted for the rest of that request. Every hop is still classified against the policy (REQ-SANDBOX-022, REQ-SANDBOX-023); what an already-permitted host changes is only how an `ask` verdict resolves mid-chain. A hop landing on a host already permitted within this request is followed without a further approval, so a path-only redirect and an `http`→`https` redirect on the same host both complete under the shipped default, as does a redirect onto a host on the allow list. A `deny` verdict refuses the hop whatever preceded it (REQ-SANDBOX-014), and a hop onto a new host classifying `ask` is refused (REQ-SANDBOX-028).
- **REQ-SANDBOX-028** — A redirect onto a NEW host that classifies as `ask` is refused, since no approval can be sought once a request is in flight: `failure_kind` `egress_redirect_denied`, with a detail explaining that the hop originated from the requested URL, that the destination host was never approved, and that access to that destination has to be asked for as its own request when it is actually required.
- **REQ-SANDBOX-029** — Deny verdicts distinguish position: the initially named URL → `egress_denied`; a redirect hop to a host outside the permitted set → `egress_redirect_denied`.
- **REQ-SANDBOX-030** — A host allowed by verdict during a redirect chain remains permitted for later hops within the same request; hops returning to an already-permitted host are not re-gated.
- **REQ-SANDBOX-031** — Redirect target resolution, exhaustively: an absolute redirect target is used as given; a relative location value is resolved as a URI reference against the URL of the hop that returned it, and the resolved absolute URL — not the raw header text — is what REQ-SANDBOX-022 classifies before the next connection is opened; a redirect response carrying no location header, or one whose value is empty or only whitespace, ends the chain and that response is the final result, with `final_url` the URL of that hop, its own `status_code`, `truncated` computed from its body as usual, and no `failure_kind` unless its status is ≥ 400, in which case REQ-SANDBOX-033's `http_error` applies — a 3xx with no location is not by itself an error. A location whose host is internationalized is canonicalized by REQ-SANDBOX-006 and REQ-SANDBOX-007 before classification, so a Unicode spelling and its IDNA spelling classify identically and neither slips past a list entry written in the other. A location that cannot be resolved into an absolute URL bearing a host yields the unknown host of REQ-SANDBOX-008, which classifies deny, so the hop is refused with `failure_kind` `egress_redirect_denied` and no connection is opened.
- **REQ-SANDBOX-032** — When the policy itself cannot be applied to a host (e.g. an invalid stored pattern), the request is refused with `failure_kind` `egress_policy_error` and a detail naming the host and embedding the underlying error. The request is never executed — fail-closed, never fail-open.
- **REQ-SANDBOX-033** — Non-refusal failure outcomes, each detail stated as required content with the wording left free: a timeout yields `failure_kind` `timeout`, with a detail conveying the deadline that expired in seconds and which level of REQ-SANDBOX-021 supplied it; any other transport failure before a response yields `network_error`, with a detail conveying the host that was being contacted and the underlying transport error as the platform reported it, unaltered; an HTTP status ≥ 400 yields `is_error` true, `failure_kind` `http_error`, and a detail conveying the numeric status code, which is itself a machine-readable value and is also carried in `status_code`.
- **REQ-SANDBOX-034** — Response shaping: the body is split into lines; the `from_line`/`to_line` window is taken (1-based, both ends inclusive, a window reaching past the end of the body yielding the lines that exist, and a window starting past the end of the body yielding no lines with `truncated` false — an inverted or non-positive window having already been refused as malformed by REQ-SANDBOX-020); if the selection holds more than `max_lines` lines, only its first `max_lines` lines are returned and `truncated` is true; otherwise every selected line is returned and `truncated` is false. Lines left out by the window alone never make `truncated` true.
- **REQ-SANDBOX-035** — The fetch result exposes the fields listed in Data & Formats: `url` (as requested), `final_url`, `status_code`, `content_type`, `truncated`, `failure_kind`, `timeout_seconds`, `error_class`, `detail`.
- **REQ-SANDBOX-036** — Model-facing rendering is fixed in structure and free in wording. A policy refusal or transport failure renders, in order: a first line identifying the failure; a `[fetch_diagnostic]` block holding the result fields of REQ-SANDBOX-035 as one JSON object whose keys are in sorted order and whose null-valued fields are left out, `failure_kind` always among the keys present; and, when a body was received, a `[fetch_output]` block holding it. A success renders the header lines `url`, `final_url`, `status_code`, `content_type`, `truncated` in that order, one per line, followed by the body.
- **REQ-SANDBOX-037** — A fetch executed without run-scoped egress configuration defaults to a permissive policy (disposition `allow`, empty lists), so a wiring gap breaks nothing; this is not ungated overall because permission-layer gating of remote fetches still applies ahead of execution.
- **REQ-SANDBOX-038** — The effective egress policy is read from the owning run's current configuration at each fetch call: a SAVED edit to the host lists takes effect on the following fetch with no restart, while an edit still unsaved on the settings surface reaches nothing (REQ-SANDBOX-118), and two concurrent runs in one process each apply their own lists — one run's permitted hosts never extend to another.

### Permission-layer gating of network access

- **REQ-SANDBOX-039** — The fetch tool (model-facing tool name `fetch`) is classified both read-only and network-reaching. Host-scoped fetch gating is evaluated BEFORE any blanket read-only allowance (first match wins), so read-only status cannot bypass egress gating.
- **REQ-SANDBOX-040** — Each supervised mode (`restricted`, `ask`) carries two fetch rules, in order: `{mode}:fetch-remote-host` (decision ask; covers a fetch whose target is off-machine) then `{mode}:fetch-local-host` (decision allow; covers a fetch whose target stays on this machine). Both precede the mode's `{mode}:read-only-tool` rule.
- **REQ-SANDBOX-041** — A remote fetch under a supervised mode resolves through the remote-host rule (ask); when no approval channel is registered, the ask resolves fail-safe to deny. A loopback fetch (e.g. `http://127.0.0.1:5173/...`) resolves allow through the local-host rule.
- **REQ-SANDBOX-042** — The gated subject of a fetch permission decision is the URL itself; the URL appears as the gated command in decisions and the audit trail.
- **REQ-SANDBOX-043** — Which terminal command lines count as network-reaching is fixed by REQ-TOOLS-094: the catalogue of leading-token prefixes, the fact that it is closed and unordered, the cutting of a compound line into segments, the whole-token comparison, and the reading of a trailing `*` as zero or more further tokens all belong to that requirement, and this domain holds no copy of any of them, adds no prefix of its own, and states no second catalogue. What this domain relies on that requirement for is a single closed verdict on a command line — network-reaching or not — that the per-mode rule of REQ-SANDBOX-044 can attach a decision to, and that the verdict is settled by the command string alone, before execution, so it can be reached at permission time. That the verdict is a permission heuristic and never an enforcement boundary is stated here rather than there only in its consequence for this domain: nothing outside confinement stops a command the recognizer misses from reaching the network, and terminal traffic has no per-host filtering at all (REQ-SANDBOX-047).
- **REQ-SANDBOX-044** — The network-command rule per mode: `restricted` → deny (rule id `restricted:network-command`), `ask` → ask (rule id `ask:network-command`). Each matches its mode's default decision; the rules exist so refusals and the audit log name a specific rule id.
- **REQ-SANDBOX-045** — The `autonomous` mode carries NO fetch rules and NO network-command rule — only its destructive-command deny rules. Rationale: in that mode nothing is available to respond to a prompt, so such a rule would settle on deny and make the most permissive mode stricter than intended. `curl` or `pip install` under autonomous resolves allow via the mode default.
- **REQ-SANDBOX-046** — The permission-mode preset vocabulary, the default decision each preset carries, how a configured name resolves to a preset, and the restrictiveness ordering are fixed by REQ-TOOLS-041, REQ-TOOLS-046 and REQ-TOOLS-047; this domain holds no copy of any of them, mints no further mode, and states no second default. What it relies on those requirements for is that every mode named anywhere in this domain is one of exactly three; that a mode name this domain cannot recognize has already been resolved before any rule here is consulted, so no rule of this domain ever sees an unrecognized name; and that any two modes can be compared by restrictiveness, which is the comparison REQ-SANDBOX-106 performs against a persona pin.
- **REQ-SANDBOX-047** — For terminal commands, network access is all-or-nothing: confinement either opens or closes the network for the whole command and cannot distinguish destinations within it. Per-host allow/ask/deny is available only for the built-in fetch tool, whose connections the product makes itself. The limitation must be documented; destination-aware filtering of terminal traffic is out of scope.
