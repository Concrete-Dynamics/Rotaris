# Desktop Shell, Navigation, and Window Management — Application entry, demo mode, and preference store

Part 1 of 7 of [domain 12](../12-desktop-shell-windows.md), which indexes every part. Defines REQ-SHELL-001 – REQ-SHELL-032.

## Requirements

### Application entry, demo mode, and preference store

- **REQ-SHELL-001**: *Withdrawn.* The product is a single graphical desktop application with no command-line surface, so there is no argument vocabulary to specify; the capabilities the arguments carried are now reachable from the desktop interface — workspace selection through REQ-SHELL-010 and REQ-SHELL-021, demo mode through REQ-SHELL-162, diagnostics capture through REQ-SHELL-163, and the running version through REQ-SHELL-033 and REQ-SHELL-140.
- **REQ-SHELL-002**: *Withdrawn.* There is no command-line surface on which to print a version and no exit code to report it with; the running version is read from the title-bar version label (REQ-SHELL-033) and, as selectable text, from the About page's Version row (REQ-SHELL-140).
- **REQ-SHELL-003**: *Withdrawn.* There is no command-line invocation to reject; the diagnostics controls of REQ-SHELL-163 offer only valid capture levels and choose the output folder through the platform folder chooser, so an invalid diagnostics selection is unreachable rather than diagnosed.
- **REQ-SHELL-004**: *Withdrawn.* Process exit codes are a script-oriented surface this product does not offer; the observable shutdown obligations that mattered are stated in REQ-SHELL-121.
- **REQ-SHELL-005**: In demo mode (REQ-SHELL-162) each of the seven primary views opens populated from sample data carried inside the build, and the process opens no outbound network connection for its whole lifetime: cloud-credit polling is not started (REQ-SHELL-015) and no request reaches a model provider. An action that could only complete against a live service is declined with one of the exact sentences listed in REQ-SHELL-149; the decline is always shown, never silent, and the view's contents are unchanged afterwards — no partial application. Starting or continuing a run is one of those actions: in demo mode the send control and Ctrl+Return decline with "Runs are unavailable in demo mode.", the composer keeps the text the user typed, and no session state changes.
  > **Narrowed by [`PD-SHELL-004`](../../product/directives/pd-shell-004.md#pd-shell-004), 2026-10-06.** The network silence holds
  > for the demo window — nothing it does, or that is done on its behalf, opens a connection — and not for the
  > process: a non-demo window of the same instance checks for updates and reaches its providers normally. Every
  > other sentence above still governs.
- **REQ-SHELL-006**: All user preferences resolve to a single platform-standard per-user preference store scoped by organization name "Rotaris" and application name "Rotaris"; this scoping is established before the first preference read so that no preference is ever read from or written to a differently scoped store. This store is the desktop-scoped preference surface, disjoint from the layered YAML configuration surface: no key of this document is ever read from or written to a YAML configuration file, and no YAML configuration field is ever read from or written to this store (REQ-CONFIG-463). The store's physical path and on-disk encoding are implementation choices, constrained only by these observable properties, which are the whole of the requirement: it is the host platform's own standard per-user application-settings location for that organization and application pair; where the platform offers more than one such location it is the one local to this machine and not replicated, copied or synchronised to any other machine or to any other copy of the user's profile, which is the selection REQ-STARTUP-145 fixes for the product's per-user directories, cited here for its terms and stated here because this store is not one of those directories and therefore does not inherit it — the reason is the keys, not tidiness, since this store holds paths that describe *this* machine and nothing else (`workspace/lastOpened` and `diagnostics/outputDir`, REQ-STARTUP-146, REQ-SHELL-163), and a replicated store would answer a launch on one machine with a folder that exists only on another; it is readable and writable by the invoking user account and needs no elevation; it lies outside every workspace directory, so no preference ever appears inside a project or in that project's version control; it is created on first write, and its absence is not an error but the state in which every key answers with its declared default; and a value written to it is the value read back after the process has been restarted, subject to the tolerant integer parsing of REQ-SHELL-069. Two conformant builds may therefore lay the same keys out differently on disk. Because this document defines the store, it also registers what may live in it, as domain 15 registers the layered YAML surface: the store's key set is exactly the keys listed in the per-user preference store table of this document's Data & Formats section, and a key that does not appear in that table does not exist. The meaning and default of a key may be owned by the document whose behavior it serves — the `interface/` toggles and the tool-row `display/` preferences by REQ-CONFIG-405, `display/showReasoning` by REQ-CHAT-167, the `panels/` layout keys by REQ-SHELL-069, the diagnostics keys by REQ-SHELL-163, `workspace/lastOpened` and `updates/dismissedVersion` by REQ-STARTUP-146, the per-workspace composer draft by REQ-CHAT-015, the requirements board keys by domain 08 — but a key reaches the store only by being registered in that table. The keys are slash-namespaced, as that table's namespace list states; no key of any other form exists, so a document that needs a new preference registers it in that table rather than minting a key of its own, and a preference key named in another document but absent from that table is not a preference of this product.
  > **Narrowed by [`PD-CHAT-010`](../../product/directives/pd-chat-010.md#pd-chat-010), 2026-10-19.** In the registered key set below,
  > `display/autoCollapseTools` and `display/groupToolCalls` are replaced by `display/toolVerbosity` (integer 1–5,
  > default 3), the transcript's tool-verbosity slider. The store's scope, location, physical path and write properties

- **REQ-SHELL-162**: Demo mode SHALL be reachable from the desktop interface and from nowhere else. The command palette SHALL carry a shortcut-less entry labelled "Open demo window", present in every window and in the composer's slash catalogue on the terms of REQ-SHELL-048 and REQ-SHELL-056. Activating it SHALL build a new main window in demo mode, show it, and leave the window that issued the request open and unchanged — the replacement semantics of REQ-SHELL-017 SHALL NOT apply. Demo mode is a property of a window fixed when that window is built: it SHALL NOT be turned on or off in a window that is already open, SHALL NOT be written to the preference store, and SHALL NOT be inherited by a window the workspace-replacement flow builds from a window that is not in demo mode. A demo window SHALL be identifiable as one without relying on colour: the title bar SHALL carry a "Demo" marker beside the wordmark whose accessible name states that the window shows built-in sample data, and the marker SHALL be present for the whole life of the window. A demo window SHALL never write `workspace/lastOpened` and SHALL never raise the first-launch workspace prompt of REQ-SHELL-011.
- **REQ-SHELL-163**: Diagnostics capture SHALL be reachable from the desktop interface and from nowhere else. The Settings view's About tab (REQ-SHELL-138) SHALL carry a diagnostics card holding three controls, each keyboard-reachable and each carrying an accessible name: a capture-level control (accessible name "Diagnostics capture") whose selectable values are exactly `off`, `light` and `deep` and which shows `off` whenever nothing has been stored; an output-folder control (accessible name "Diagnostics output folder") that displays the folder currently in force as selectable text and, when activated, opens the platform folder chooser limited to selecting directories to change it; and a control that opens this window's diagnostics run directory in the OS file manager, enabled only while such a directory exists for this window. Because the level control offers only the three valid levels and the folder is chosen through the platform chooser, an invalid diagnostics selection is unreachable, and the product SHALL define no error, message or refusal for one. A change to either choice SHALL take effect for windows built afterwards and SHALL NOT alter the capture already running in an open window; the card SHALL say so in words. The two choices SHALL live in the per-user preference store as `diagnostics/level` (default `off`) and `diagnostics/outputDir` (default unset, meaning the product's own default location, REQ-STARTUP-131), and SHALL NOT appear in the layered YAML configuration surface (REQ-SHELL-006).

### Startup sequencing

- **REQ-SHELL-007**: The application window icon is the product brand mark from the moment the first window appears, so taskbar and window-switcher entries carry the logo.
- **REQ-SHELL-008**: Bundled font families for the display, body, and monospace roles are made available before the first window paints; if loading a bundled font fails, the application continues with host system fonts and does not abort.
- **REQ-SHELL-009**: The stored theme choice is applied ahead of the first window becoming visible. Reading that preference never writes it back, so on a machine where the recorded theme name does not map to an installed theme the recorded value stays exactly as the user left it.
- **REQ-SHELL-010**: Startup workspace resolution follows this precedence: (a) a workspace the window was explicitly built for — the folder chosen through the replacement flow of REQ-SHELL-017, or a folder a launch of the application carried and for which the one running instance built this window (REQ-STARTUP-163) — wins, is resolved on the terms REQ-STARTUP-163 fixes for when two directory strings name the same directory, which this clause cites rather than restating, and is immediately persisted in that resolved form as the last-opened workspace with no onboarding prompt; (b) otherwise a remembered last-opened workspace that still exists as a directory is used with no prompt; (c) otherwise the current working directory is used and a first-launch prompt is scheduled after the window is shown.
- **REQ-SHELL-011**: Deferred first-paint work uses one shared delay of **650 ms**, measured from the moment the window is shown, so the complete desktop paints before anything is put in front of it. This document owns window management, and this requirement is the product's single definition of that delay: every offer deferred to first paint waits the same interval, and a document that needs to say how long such work is deferred SHALL cite this identifier rather than restating the figure. The first-launch workspace prompt is deferred by that delay. The prompt is the platform's own folder-picker dialog, window title "Open a project folder", limited to selecting directories and initially pointed at the current workspace (or, when there is none, the user's home directory). The deferred prompt is a one-shot offer that SHALL be abandoned unshown whenever the question it asks has already been answered by the time that delay elapses: if the user has by then started the workspace-open flow of REQ-SHELL-021, or a workspace has by then been chosen by any route, the prompt SHALL NOT appear. Two folder choosers are therefore never on screen at once, and the deferred prompt never appears over a chooser the user opened. A prompt abandoned this way SHALL show no reminder — the reminder of REQ-SHELL-012 belongs only to a chooser the user actually saw and cancelled.
- **REQ-SHELL-012**: Cancelling the first-launch chooser leaves the default desktop fully usable and shows a transient notification: "Open a project folder when you're ready by selecting the workspace path in the title bar."
- **REQ-SHELL-013**: On a bundled (standalone) runtime that still requires machine setup, the setup modal is scheduled after the window is shown, at the shared deferred first-paint delay of REQ-SHELL-011; after it completes, setup state is refreshed, the asynchronous Git refresh starts, and only then does first-launch workspace onboarding continue. On other runs the Git refresh starts at window activation.
- **REQ-SHELL-014**: Git status discovery never starts before the window is on screen (REQ-SHELL-013 fixes the exact point for each kind of run), and the window remains fully usable while a discovery is outstanding: views can be switched, text can be typed, and shortcuts fire. The discovery itself displays nothing that blocks input — no modal dialog, no progress dialog, no busy cursor — which leaves dialogs scheduled by other requirements, such as the first-launch folder prompt (REQ-SHELL-011) and the machine-setup modal (REQ-SHELL-013), free to appear while a discovery is still running. A failed discovery raises the persistent ERROR notice of REQ-SHELL-116 reading "Git status could not be refreshed: {message}"; it stays on screen until the user dismisses it and is never withdrawn on a timer.
- **REQ-SHELL-015**: Activation ordering: the window is shown first; the software-update check starts only once a window is visible (so its notification always lands on a visible window); cloud-credit polling starts at the same point unless running in demo mode.
- **REQ-SHELL-164**: Where this document requires a platform-native dialog — the folder choosers of REQ-SHELL-011, REQ-SHELL-021 and REQ-SHELL-163, and the native message boxes of REQ-SHELL-119 — the product SHALL be answerable only for what it supplies to the host: the dialog's title, its initial location or selection, its restriction to directories where one is stated, the button set and which button is the default, and the correct interpretation of every answer the dialog can return. Keyboard traversal, focus order, localization of platform-supplied button text, high-contrast rendering and screen-reader behaviour inside such a dialog are inherited from the host; they are not requirements on this product, and a host whose native dialog falls short of them does not put the product out of conformance with REQ-SHELL-144, whose sweep covers the seven primary views and the product's own windows. Two obligations survive whatever the host does: a dialog dismissed by any means the host offers — Escape, the window close control, or a platform-specific gesture — SHALL be treated as the identical answer to its Cancel button, with the same consequences the requirement states for Cancel; and no native dialog SHALL be the only route to a capability, so every flow a native dialog guards also states what the product does when that dialog is cancelled.
- **REQ-SHELL-016**: Deferred startup offers (project-initialization resolution and the hook-trust review offer) are issued only after window construction completes; a window created and destroyed immediately must not crash or deliver the offers.

### Workspace selection and replacement

- **REQ-SHELL-017**: Opening another project builds a new main window on the selected folder, shows it, and then closes the old window. Only if the old window closes successfully is the new window recorded as current, the last-opened-workspace preference updated, and the new window activated.
  > **Extended by [`PD-SHELL-001`](../../product/directives/pd-shell-001.md#pd-shell-001), 2026-09-12.** This still
  > governs in full, and remains what happens when a chosen folder replaces the window. The directive
  > adds a second route beside it, taken by its own two gestures, on which a main window is added and
  > no window is closed.
- **REQ-SHELL-018**: If the old window refuses to close (for example the user cancels an unsaved-settings dialog or an active-run confirmation), the replacement window is discarded and nothing changes: the old window, the current workspace, and the stored preference all remain as they were.
- **REQ-SHELL-019**: If constructing the replacement window fails, the old window stays open and shows the error notification "Could not open the selected project: {reason}".
- **REQ-SHELL-020**: Only workspace-open requests originating from the currently active window are honored; requests from stale windows are ignored. This governs requests raised inside a window. A launch of the application carrying a workspace directory originates in no window and is not such a request: it is honored under REQ-STARTUP-163, which adds a main window rather than replacing one, and the several main windows the one running instance may hold at once (REQ-STARTUP-161) are not stale windows of each other — each honors the requests raised inside it while it is the active one.
- **REQ-SHELL-021**: Activating the title-bar workspace chip evaluates the same three gates as a window close, in the same fixed order as REQ-SHELL-119 — unsaved settings, then worktree integration, then active runs — and any of them ends the flow. (1) With unsaved settings present, the save/discard/cancel dialog of REQ-SHELL-124 is raised: Cancel ends the flow with nothing changed, a Save that fails also ends it, and Save-that-succeeds or Discard lets evaluation continue. (2) While a worktree integration is running, the request is declined outright with the transient error notification of REQ-SHELL-112 reading "Finish the worktree integration before opening another project.". (3) With a run active, it is declined the same way with "Finish the active run before opening another project.". A decline shows no folder chooser and changes no window, workspace or stored preference. When no gate stops it, the chooser opens pointed at the current workspace. Cancelling the chooser leaves the window, the workspace and the stored preference exactly as they were and may show the reminder of REQ-SHELL-012. Selecting the folder that is already open builds no replacement window and leaves the current window in place; whether the selected folder is the one already open is decided by the rule REQ-STARTUP-163 fixes for when two directory strings name the same directory, which this requirement cites rather than restating, so this decision, REQ-STARTUP-052's and the window-reuse decision REQ-STARTUP-163 makes for itself are all taken on one rule.

### Main window structure

- **REQ-SHELL-022**: The main window carries the title "Rotaris", opens at 1440×900 logical pixels, and refuses to be resized below 1000×680 in either dimension. This document owns window management, and this requirement is the product's single definition of the main window's opening size and of its minimum size: a document that needs to name either figure, or to require that a control of its own be reachable and fully labelled at the minimum, SHALL cite this identifier rather than restating a number, and no surface declares a minimum window size of its own. At that 1000×680 minimum, and on every one of the seven primary views, the following all hold and are individually checkable: every control the view offers lies wholly inside the window bounds; every control is reached by Tab traversal; every control's label is rendered in full, the only exceptions being the elisions REQ-SHELL-082 and REQ-SHELL-087 permit; and no control requires horizontal scrolling to reach (REQ-SHELL-064, REQ-SHELL-065, REQ-SHELL-106).
  > **Extended by [`PD-SHELL-003`](../../product/directives/pd-shell-003.md#pd-shell-003), revised 2026-09-24.** On Windows, Linux and macOS the main window is frameless, shows no native frame, menu or toolbar, and carries minimize, maximize/restore and guarded close controls in the product-drawn title bar. The title and geometry above still govern unchanged.
- **REQ-SHELL-023**: The window hosts exactly seven primary views in this fixed order: Overview, Workspace, Mission, Requirements, Git, Library, Settings. Exactly one is visible at a time; Requirements is the fourth entry, ordered after Mission and before Git.
- **REQ-SHELL-024**: Vertical layout, top to bottom: title bar; a persistent-notice banner slot; a horizontal region of navigation rail beside the active view; status strip.
- **REQ-SHELL-025**: View switching semantics: switching to an unknown view identifier is a silent no-op. Leaving the Settings view with unsaved changes triggers the save/discard/cancel dialog (REQ-SHELL-124) and cancelling aborts the navigation. A successful switch updates the rail's selected state and the recorded active view (which other behaviors, such as Escape handling, read).
- **REQ-SHELL-026**: The view shown at startup is Overview.

### Navigation rail

- **REQ-SHELL-027**: The rail shows one button per primary view, in view order, each with a distinct icon and a text label beneath it. Labels: "Overview", "Workspace", "Mission", "Requirements", "Git", "Library", "Settings".
- **REQ-SHELL-028**: Rail selection is mutually exclusive: whenever a view is showing, exactly one rail button is in the checked state, and checking a button unchecks the one that was checked before. Each button is an individual stop in the window's tab order (REQ-SHELL-032) and shows a pointing-hand cursor under the pointer. Each rail icon is declared at 17×17 logical pixels and drawn under the scaling rule of REQ-SHELL-030. Every button carries the tooltip and the accessible description "Open {Label}". A click checks the button and switches the view, as do Space and Return on the focused button; a checked state that no user gesture produced updates the rail's appearance only — it switches no view and causes no other navigation effect. The rail is not an arrow-navigable group: while a rail button holds focus, Arrow Up, Arrow Down, Arrow Left and Arrow Right SHALL move no rail selection and switch no view. Movement between rail buttons is by Tab and Shift+Tab only (REQ-SHELL-032). This is exactly the difference REQ-SHELL-153 preserves between the rail and the shell's vertical navigation lists, and it is deliberate: the rail's activation both selects and navigates, so arrow keys must not be able to traverse it.
- **REQ-SHELL-029**: Rail labels render at 9 px, and in every built-in theme each item shows its complete label with no ellipsis and no clipped glyph. The rail is consequently never narrower than its widest label needs: it uses the theme's declared item and rail widths (54 px and 68 px respectively in the default theme, REQ-SHELL-129) whenever those already accommodate the labels, and exceeds them when they do not. The width is re-derived after every theme change, including a change to a theme with a larger type scale.
- **REQ-SHELL-030**: An icon declared at L logical pixels is rendered from artwork whose raster resolution is at least ceil(L × device pixel ratio) device pixels in each dimension, so the drawn icon is never an enlargement of a smaller raster. Measured at 100%, 125%, 150%, 175% and 200% OS display scaling, the icon covers L logical pixels — the same physical area of the screen at every one of those factors, within one device pixel. Resting and selected rail icons use two distinct theme inks, and each clears the 3:1 non-text contrast floor of REQ-SHELL-144 against the rail background.
- **REQ-SHELL-031**: A theme change fully recolors the rail, including baked icon inks and hover/selected treatments; no stale-theme icon color survives a switch.
- **REQ-SHELL-032**: Every rail button is its own stop in the window's normal tab order, and each announces a non-empty accessible name (the Workspace button, for instance, announces "Open Workspace").
