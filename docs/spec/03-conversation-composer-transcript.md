# Conversation, Composer, and Transcript

## Overview

The conversation surface exists on two frontends — a desktop application and a terminal UI — sharing one queued-prompt service, one structured-question mechanism, and one session persistence model. The user types prompts into a composer that adapts to run state (start a run, continue a session, queue a follow-up for a running iteration, or steer an active agent), invokes slash commands with inline discovery and validation, and reads a live transcript that renders user prompts, agent messages, streamed reasoning, tool calls with grouped and collapsible output, user-only edit diffs, pending-question and pending-approval prompts, and a task plan. Prompt history, stashed drafts, transcript archives, and todo edits all persist to well-defined on-disk formats, and destructive operations always require explicit confirmation.

## Requirements

### 1. Desktop Composer: Input, Shortcuts, and State

- **REQ-CHAT-001** — The desktop composer MUST be a multiline text input where **Enter** (no modifier) submits, **Shift+Enter** inserts a newline, and a global **Ctrl+Return** shortcut submits the composer's contents from anywhere in the window, including while keyboard focus sits on another widget.
- **REQ-CHAT-002** — These shortcuts MUST be honoured anywhere in the desktop main window: **Ctrl+L** moves keyboard focus to the composer, **Ctrl+F** opens transcript search, **F1** opens keyboard help, and **Escape** dismisses the topmost overlay in this order — the slash suggestion popup if it is showing (REQ-CHAT-026), otherwise the search panel, otherwise any open drawer. While a modal dialog is on screen the modal owns Escape (REQ-CHAT-101) and this global binding does not apply. These are desktop bindings; the terminal leader system of REQ-CHAT-149 does not replace or disable them.
- **REQ-CHAT-003** — Submitting empty or whitespace-only text MUST do nothing except return keyboard focus to the composer: no run starts, no transcript row appears, no history entry is recorded.
- **REQ-CHAT-004** — The composer placeholder MUST be one of exactly these four strings, chosen with the first two taking precedence in the order given: (1) "Run active — write a follow-up for the next iteration…" whenever a locally owned run is active; (2) "Describe how to continue this session…" whenever the loaded session reports itself busy while no local run exists; (3) "Message orchestrator — type / for commands, ↑ for history…"; (4) "Describe the outcome you want…". The condition that selects (3) rather than (4) is not determined — see Open Questions.
- **REQ-CHAT-005** — The primary action button beside the composer MUST state the composer's current mode via its label — `Queue` while a local run is active, `Continue run` when a named session is loaded with no active run, else `Start run` — and there MUST NOT be a separate in-composer mode label.
- **REQ-CHAT-006** — The composer text area MUST stay editable in every run state, including while a run is active. The permission-mode chip and the Stash button MUST stay enabled in every run state. The persona, model, and reasoning chips MUST be disabled whenever the current run state does not permit changing them, and each disabled chip MUST state its reason per REQ-CHAT-007. Which run states disable those three chips is not settled between this requirement and REQ-CHAT-078 — see Open Questions.
- **REQ-CHAT-007** — Sending MUST be refused in two situations, each with its reason readable by the user: while a run is cancelling, the reason MUST be exactly "Wait for the current run to finish cancelling."; while an unanswered project-setup prompt gates execution, the reason MUST begin with the sentence "Answer the project setup prompt first." and MUST go on to tell the user that nothing else in the application is blocked. Every control this domain disables MUST publish its unavailability reason through both its tooltip and its accessible description; greying the control alone does not satisfy this. The remainder of the project-setup reason string is not determined — see Open Questions.
- **REQ-CHAT-008** — The run-state label MUST use exactly this vocabulary: idle → `Ready`; starting → `Starting run…`; running → `Run active`; pausing → `Pausing after current step…`; paused → `Paused`; completed → `Completed`; failed → `Run failed`; cancelling → `Cancelling…`; cancelled → `Cancelled`; and a synthetic `Run needs recovery` when the persisted session claims busy but no local run exists.
- **REQ-CHAT-009** — The composer MUST carry four selector chips: persona; model, which shows the placeholder `copilot/gpt-5` until model options have been loaded; reasoning effort, labelled `reasoning: low`, `reasoning: medium`, or `reasoning: high` and defaulting to **high**; and permission mode, labelled `mode: <name>`. Selecting the permission mode that grants autonomous execution MUST first raise a warning confirmation dialog in which Cancel holds initial keyboard focus, so that confirming by reflex (Enter or Space) leaves the previous mode in place. Whether the model placeholder string is fixed or configurable is not determined — see Open Questions.
- **REQ-CHAT-010** — Composer geometry defaults MUST be: composer block default height 150 px, minimum 110 px; transcript area minimum 180 px; composer widget minimum height 48 px. The divider between transcript and composer MUST be user-draggable and its position persisted across launches.
- **REQ-CHAT-011** — Given no active run, when the user submits non-empty text, the frontend MUST validate that a run can start; on success it MUST set the session status to starting, append a transcript row of kind `user` (displayed role `you`, timestamp formatted `HH:MM:SS` 24-hour), and record the text in prompt history.
- **REQ-CHAT-012** — When starting a run fails for any reason (including "a run is already active" and workspace-isolation refusals), the typed text MUST be restored into the composer unchanged and an error notice raised with the failure reason (e.g. "A run is already active."). The user's text is never lost by a failed submission.
- **REQ-CHAT-013** — In demo mode (no run backend attached), a submission MUST append the user row plus a system row reading "Demo mode: run bridge is disabled." and start nothing.

### 2. Desktop Prompt Drafts and History Recall

- **REQ-CHAT-014** — The composer draft MUST be published to application state only after a 200 ms debounce following the last keystroke, on focus-out, or on submit — never per keystroke — so that typing cannot trigger per-keystroke transcript or state re-computation.
- **REQ-CHAT-015** — An unsent composer draft MUST outlive the application process. Text left in the composer MUST be stored per workspace in the platform's native settings storage, and MUST reappear in the composer character-for-character the next time a window is opened on that workspace, including after the application has been quit and relaunched. A draft stored against one workspace MUST NOT appear in the composer of any other workspace.
- **REQ-CHAT-016** — Shell-style history recall MUST work as follows: history is ordered newest-first; the first **Up** press saves the current composer text as a draft and loads the newest entry; each further Up moves toward older entries, clamped at the oldest; **Down** walks newer and, past the newest entry, restores the saved draft; every recall places the cursor at the end of the text; any other keypress (including suggestion-popup interaction and submit) resets the history walk.
- **REQ-CHAT-017** — A history entry MUST be recorded only when the text is non-empty and differs from the current newest entry (head dedupe). History MUST be recorded on run start, on continue, and on successful queueing.

### 3. Desktop Slash Commands: Parsing and Execution

- **REQ-CHAT-018** — Slash parsing rules: a command is a **single-line** text starting with `/`. A slash followed by whitespace (`"/ "`) is an escape that makes the text an ordinary prompt. Any text containing a newline is always an ordinary prompt. The first token after `/`, lowercased, is the command name; the remainder, stripped, is the argument string.
- **REQ-CHAT-019** — When submitted text parses as a slash command, the suggestion popup MUST be hidden and the composer cleared **before** the command runs. Consequence: a command whose own action submits the composer finds the field already empty and therefore cannot loop on the text that invoked it.
- **REQ-CHAT-020** — Command execution MUST report exactly one of these outcomes: executed; not-a-command; unknown command (message `Unknown command /<name>`); unavailable (the command's own stated reason, or the default `/<name> is not available right now.`); failed (the message of the command's raised error). Every outcome except not-a-command counts as handled (the text is never treated as a prompt).
- **REQ-CHAT-021** — Any non-executed outcome of a recognized-as-slash submission MUST restore the exact typed text into the composer (cursor at end) and raise a **persistent** notice titled "Command not run" (not a transient toast) carrying the outcome message. An unknown or unavailable command MUST never start a run.
- **REQ-CHAT-022** — Command registration semantics: registration order is preserved; names are lowercased on registration; registering a name that already exists **replaces** the earlier command; lookup is case-insensitive. Filter matching MUST rank name-prefix matches ahead of name-substring matches ahead of description-substring matches, preserving registration order within each rank; an empty filter lists every command.
- **REQ-CHAT-023** — Once text is recognized as a slash command (executed or not), it MUST never be forwarded to any agent as prompt content.

### 4. Desktop Slash Suggestions and Live Highlighting

- **REQ-CHAT-024** — The suggestion popup MUST open exactly when the composer holds single-line text starting with `/` with no whitespace yet after the name token (a bare `/` lists everything); typing an argument (whitespace after the name) or reaching zero matches closes it. The popup MUST never take keyboard focus, MUST anchor directly above the composer at the composer's width, and MUST show at most **8** rows (scrolling beyond).
- **REQ-CHAT-025** — Each popup row MUST render `/name — description [argument hint]` plus a kind badge distinguishing `action` commands from `skill` commands. Unavailable commands MUST stay listed, styled as disabled text, with their unavailability reason exposed as tooltip and accessible description.
- **REQ-CHAT-026** — While the suggestion popup is showing, these keys MUST take effect on the popup and MUST NOT reach the composer's ordinary bindings: **Escape** dismisses the popup and leaves the composer text exactly as the user typed it; **Up** and **Down** move the highlighted row and stop at the first and last rows without wrapping, and MUST NOT walk prompt history; **Tab** replaces the composer text with `/name ` — one trailing space, caret after it — and does not submit; **Enter** performs the same completion, except when the composer already holds exactly `/name`, in which case it submits; clicking a row activates that row. **Shift+Enter** inserts a newline, and the resulting multi-line text dismisses the popup. Once the popup is dismissed the section 1 bindings apply again. Discovery from typing `/`, through moving the selection and completing it, to submission MUST be completable without a pointing device.
- **REQ-CHAT-027** — As the user types a single-line slash command, the leading `/name` token MUST be drawn in one of three states that differ from each other in both colour and font weight: **resolved** — the token exactly names a registered command — in the accent colour, bold; **partial** — the token is a prefix of at least one registered command but is not an exact name — in a lightened accent colour, not bold; **unknown** — no command matches — in the failure colour, bold. Weight therefore distinguishes partial from the other two independently of colour, so the states remain tellable apart without colour vision. Argument text following the name MUST be drawn in a secondary colour distinct from all three. Text spanning more than one line, and text using the `/ ` escape of REQ-CHAT-018, MUST receive no highlighting at all. Every one of these colours MUST be taken from the active theme and MUST be lightened or darkened until it reaches a contrast ratio of at least **4.5:1** against the surface it is painted on.

### 5. Desktop Slash Command Catalogue

- **REQ-CHAT-028** — The slash catalogue MUST be rebuilt whenever the command library, the settings, or the set of discovered skills changes, and the rebuilt catalogue MUST be usable without restarting the application. Every command-palette entry MUST also be reachable as a slash command whose name is the palette entry lowercased with each run of characters outside `[a-z0-9:_.-]` collapsed to a single `-`, and whose description is the palette label with ` (<shortcut>)` appended when that palette entry has a keyboard shortcut. Where mirroring a palette entry yields a name that REQ-CHAT-029, REQ-CHAT-030, or REQ-CHAT-031 already defines, the description, behaviour, and availability gating stated there are what the user gets; the mirrored entry MUST NOT displace them.
- **REQ-CHAT-029** — `/stop` (description "Cancel the active run"), `/pause`, and `/compress` (description "Compress agent context") MUST be offered only while the frontend reports a run in the running state. In every other run state all three MUST remain listed but unavailable, with the reason "No run is active.", and MUST NOT start, continue, or queue anything. `/stop` accepted during a live run MUST cancel that run and MUST NOT send any text to an agent.
- **REQ-CHAT-030** — `/clear` (description "Clear the transcript") and `/search` MUST be offered only while the transcript holds at least one row; against an empty transcript both MUST remain listed but unavailable, with the reason "The transcript is empty.". Because of this gating, and because REQ-CHAT-073 disables the toolbar Clear action on an empty transcript, the "Transcript is already empty." outcome of REQ-CHAT-082 is reachable only when the transcript empties between the moment a control is offered and the moment it is activated.
- **REQ-CHAT-031** — The catalogue MUST also include `/new` ("Start a new session"); `/resume` and `/sessions` (both "Browse and resume sessions"); `/worktree` ("Create a git worktree"), unavailable with reason "No git service is available for this workspace." when no git service exists; `/stash` ("Stash the composer prompt"); and `/pop` ("Apply a stashed prompt", opening the stash dialog).
- **REQ-CHAT-032** — `/model <name>` MUST produce exactly these outcomes. With no argument: failure with the message "Usage: /model <name>". With a name the provider reports as withheld: failure with "<name> is unavailable. <reason>", where `<reason>` is the provider's own explanation. With a name absent from the configured catalogue: failure with "Unknown model '<name>'. Available: <catalogue>", using the literal `none` in place of the catalogue when no models are configured. On success: the model chip MUST show the new name, the selection MUST become the session's active model, and the notice "Model set to <name>." MUST be shown. While no models are configured the command MUST be listed as unavailable with the reason "No models are configured. Choose one in Settings.". The separator used between names inside "Available: <catalogue>" is not determined — see Open Questions.
- **REQ-CHAT-033** — `/persona <name>` semantics mirror `/model`: usage and unknown-name errors (e.g. "Unknown persona '<name>'. Available: …"), and success sets the persona chip and notifies "Persona set to <name>.".
- **REQ-CHAT-034** — Every discovered skill a user may invoke MUST be reachable as a slash command under its normalized name and under each of its slash-trigger keywords. Where such a name is already taken, the command already holding it keeps it and the skill's registration for that name is skipped. Skills marked automatic-only MUST NOT appear in the catalogue at all. Invoking a skill command while skills are turned off MUST fail with "Skills are disabled. Enable them in Settings.". Otherwise the skill MUST be attached to the next prompt the user submits, regardless of any automatic selection heuristics, and the notice "Skill loaded for the next prompt: <name>" MUST be shown. After a skill rescan, the catalogue MUST list exactly the rescanned set. The metadata that marks a skill user-invocable rather than automatic-only is not determined here — see Open Questions.

### 6. Desktop Prompt Queue

- **REQ-CHAT-035** — While a local run is active, an ordinary (non-slash) submission MUST be queued for the running session instead of starting a run. On success the queue gains an item with a unique id and the typed text, the text is recorded in history, and a toast reads "Message queued for the next iteration.". On failure (the run no longer accepts prompts) the composer text MUST be restored and an error toast reads "Message could not be queued because the run is no longer active.".
- **REQ-CHAT-036** — Queued messages MUST render in a persistent panel directly above the composer with header "Queued messages (N)" and hint "Sent after current iteration", a scroll area capped at 150 px, and one row per prompt. The panel MUST be hidden while the queue is empty.
- **REQ-CHAT-037** — Each queue row MUST be an initially read-only single-line editor with **Edit/Save** and **Delete** actions. Saving emptied text reverts to the original; saving unchanged text is a no-op. Edits and deletions round-trip through the queue service; if the service refuses because the prompt was already picked up, the visible queue MUST re-synchronize from the service and a toast MUST read "Queued message was already picked up and cannot be edited." or "…cannot be deleted." accordingly.
- **REQ-CHAT-038** — Queued-prompt service semantics: each queued prompt carries content, an optional context snapshot, a unique (UUID-style) id, a creation timestamp, a status progressing `QUEUED → TRIGGERED → COMPLETED`, and a session ownership field (empty = unscoped). Submitting or updating with empty content MUST be rejected with an invalid-value error. Removing or updating a prompt that is not in the QUEUED state MUST fail: unknown id → not-found error; already-triggered → an invalid-state error stating it was already triggered.
- **REQ-CHAT-039** — Session scoping: ownership may come from an explicit session id or from a `session_id` key in the context snapshot. A prompt scoped to a session MUST be visible/consumable only by that session's runs; an unscoped prompt MUST be consumable by any run but invisible to session-scoped listings. Ownership MUST be preserved across edit and trigger.
- **REQ-CHAT-040** — A run that has finished every task it holds MUST NOT report completion while prompts remain QUEUED for it. Each such prompt MUST instead become a task named "Queued Prompt: <first 8 characters of the prompt id>" carrying the prompt text as its content, placed in a plan phase named "Queued Prompts", and MUST move to the TRIGGERED status. The run MUST then carry on executing those tasks. A user watching the plan therefore sees the run pick the queue up rather than stop. Whether this is the only moment at which queued prompts are consumed is unresolved — see Open Questions.
- **REQ-CHAT-041** — A prompt queued from any frontend, or from a headless run, MUST be visible to and consumable by every other frontend and run sharing the same process, subject to the session scoping of REQ-CHAT-039. The desktop's queued-messages panel MUST show exactly the prompts that are in the QUEUED status and belong to the focused run's session; queue activity in any other session MUST leave that panel unchanged.

### 7. Desktop Prompt Stash and Prompt Persistence

- **REQ-CHAT-042** — The composer's **Stash** button MUST push the trimmed composer text onto the top of the stash and clear the composer. The transcript toolbar MUST show an "Apply stash (N)" affordance with the live stash count.
- **REQ-CHAT-043** — The stash dialog (title "Prompt stash", minimum size 560×360) MUST list stashed prompts with intro copy "Apply copies the selected prompt into the composer and keeps it in the stash. Pop copies it and removes it from the stash."; **Apply** copies the selection into the composer keeping the entry; **Pop** copies and removes it. With an empty stash the dialog shows a disabled hint row "No stashed prompts. Use Stash beside the composer first." with Apply/Pop disabled.
- **REQ-CHAT-044** — Applying or popping a stashed entry into a non-empty composer MUST append it after one blank line (`<current>\n\n<stashed>`); into an empty composer it replaces the text; the composer takes focus afterwards.
- **REQ-CHAT-045** — Desktop prompt history and stash MUST persist per workspace to `<workspace>/.rotaris/rotaris-prompts.json`, holding a pretty-printed JSON object `{"history": [...], "stash": [...]}` that ends with a newline. Writing MUST be atomic: interrupting the application mid-save MUST leave either the previous file or the complete new one, never a partial or truncated file. History MUST retain at most **200** entries and the stash at most **100**, discarding the oldest beyond those limits. Blank entries MUST be discarded when loading. A file that is absent, or whose contents cannot be parsed, MUST load as empty history and empty stash rather than reporting an error. If saving fails, a persistent notice titled "Could not save prompt history" MUST be raised carrying the underlying reason, and the session MUST continue with in-memory history and stash. The indentation width used for the pretty-printed output is not determined — see Open Questions.

### 8. Desktop Transcript Model and Projection

- **REQ-CHAT-046** — Each transcript row MUST carry, where its category makes the field meaningful: a display timestamp, which may be empty; a role, being `you`, an agent name, `system`, or an intent marker; the row text; a row category; the tool name and the result detail; the **untruncated** tool input and output, retained so that expansion and copy can present them in full; a structured diff, on edit-diff rows only; the persona; a stable per-tool-call key; a tool status drawn from `running`, `ok`, `failed`, `blocked`; a duration; a start time; a streamed-character count, on reasoning rows; and a live-terminal stream id. The row-category vocabulary MUST be exactly: agent message, tool call, system notice, user prompt, intent note, structured-question prompt, approval prompt, user-only edit diff, streamed reasoning, delegation-context header, verifier output, and folded tool group.
- **REQ-CHAT-047** — Persisted session rows MUST map to display kinds by role: `user` → user (displayed role becomes `you`); `system` → system; `tool` → tool; `thinking` → thinking; `verifier` → verifier; any other role → message with that role name as the display role.
- **REQ-CHAT-048** — Duplicate-reasoning hygiene: per agent, an unstamped (no duration) thinking row whose content equals the immediately previous thinking row's content MUST project to zero rows, so sessions recorded with duplicated streamed reasoning display each burst once.
- **REQ-CHAT-049** — Dead-session hygiene: when a session is not running, an unstamped thinking row MUST NOT present as live (its live start marker is dropped), and a tool row still marked running MUST display with no status and no live timer. A session with no run in progress MUST therefore never appear to be in the middle of a tool call.
- **REQ-CHAT-050** — A user-only edit diff MUST be displayed as its own row directly beneath the tool row for the call that produced it, and MUST be displayed at most once however often the transcript is re-projected. The row's text form is a header line `<path>[ [Created]] +A -R` — where `A` is the number of added lines, `R` the number of removed lines, and ` [Created]` is present only when the file did not exist before the call — followed by one `[<line>]± <text>` line per changed line, and, when the diff is cut short, a final line "… +N more lines, diff truncated". Edit-diff content MUST be excluded from everything a model can see: prompt text, summaries, compression input, and token estimates. The number of diff lines the desktop renders before truncating is not determined — see Open Questions.
- **REQ-CHAT-051** — Whenever the run is waiting on the user, trailer rows MUST follow every recorded row, in this order: first, while structured questions are pending, a single question row reading "N step(s) — <title of the first step>" and attributed to the agent that asked; then one approval row per pending approval, reading "Approval needed — " followed by the name of the command or tool awaiting approval. Each trailer row MUST appear as soon as its pending state exists and disappear as soon as that state clears, whether the transcript was rebuilt in full or updated incrementally.
- **REQ-CHAT-052** — The transcript MUST never show rows that disagree with the session record. When a live update cannot be applied to the rows already on screen — because it concerns rows the view no longer holds, or a position outside the rows the view currently shows — the view MUST decline it and MUST re-read and re-project the whole session before showing anything further; it MUST NOT approximate by fitting the update to the nearest position it does hold. Declining is an ordinary reported outcome, not an error: it MUST NOT interrupt the user or leave the transcript blank. Correctness outranks update latency — the view MUST NOT display content it cannot confirm in order to avoid a re-read.
- **REQ-CHAT-053** — Appending rows, dropping rows from the end, replacing rows in place without changing their number, and extending the last streamed row while appending after it MUST each leave the reader's scroll position where it was and leave every row's expanded or collapsed state as the user set it. Only changes matching none of those shapes may reset the view, and such a reset MUST still restore the reader's position by the anchor rule of REQ-CHAT-071.
- **REQ-CHAT-054** — Message deduplication: a replayed message event with an already-seen stable event id MUST persist once; a cumulative committed-text snapshot MUST update the current response row in place rather than appending; a streamed response MUST finalize in place; a response arriving after a tool boundary or as a new streaming segment MUST become a distinct row.

### 9. Desktop Transcript Rendering

- **REQ-CHAT-055** — The transcript MUST scale to long conversations: the work of painting and measuring MUST depend on how many rows are visible and how many rows changed, not on how many rows the transcript holds in total. With 1000 or more rows present, scrolling, expanding a row, and running a search MUST each respond within the latency budget of REQ-CHAT-157, and appending a row MUST cost no more than it does on an empty transcript.
- **REQ-CHAT-056** — Rows of the agent-message category MUST render Markdown, with fenced code blocks in a monospace face on a shaded background of their own, bold text at a heavier weight than body text, italic text slanted, inline code spans in a monospace face, and hyperlinks in a colour distinct from body text and activatable per REQ-CHAT-076. Markdown that is still incomplete because it arrived mid-stream MUST render without raising an error and without altering the appearance of rows around it. Rendering MUST complete synchronously and MUST NOT issue any network request.
- **REQ-CHAT-057** — Row layout MUST use a timestamp column of 52 px, a role column of 112 px, a minimum row height of 30 px, and timestamps painted in the monospace stack at 8 pt. Attribution — the role line, plus a task line when the row belongs to a named task — MUST be drawn only on the first row of a block, a block beginning at every row whose role differs from the row above it. Continuation rows MUST instead show a 2 px bar in the role gutter, coloured by the persona. Row margins are 10 px and 5 px; which of the two applies to which axis is not determined — see Open Questions.
- **REQ-CHAT-058** — Desktop transcript memory MUST stay bounded however long the conversation grows: retained row measurements and retained row renderings MUST each be held only up to a fixed limit, beyond which the least recently used are discarded. A retained rendering MUST be reused only while everything that determines the row's appearance is unchanged — its identity, its content, the width it was laid out for, and its expansion state — so that inserting, removing, or reordering rows can never make one row display another row's content. Rows that are live (a running tool, verifier, or group, or reasoning still streaming) MUST be redrawn on every repaint rather than reused, so their elapsed times keep advancing. Switching theme MUST redraw every row in the new theme while leaving every row's expanded or collapsed state exactly as the user set it.
- **REQ-CHAT-059** — Row expansion state MUST be keyed by stable identity — tool/verifier rows by their tool-call key (content-hash fallback), thinking rows by start time (text-hash fallback), delegation headers by agent, groups by the key of the group's **first** member — so an opened box stays open while the group grows, while rows are inserted above it, and across model resets.

### 10. Desktop Tool, Thinking, and Grouped Rows

- **REQ-CHAT-060** — A tool row MUST render a monospace header `▸ toolname args`, with the chevron and tool name in the tool accent colour and the outcome appended on the same line: `ok · <seconds>s`, the duration carrying one decimal place (for example `ok · 3.2s`), when the call succeeded; `failed` when it did not; and a pulsing `◉ running…` while it is still in flight. A row persisted with a ✓, ✗, or ! glyph already written into its text MUST render without that glyph, so the outcome is stated exactly once. What a row whose tool status is `blocked` shows in place of the outcome is not determined — see Open Questions.
- **REQ-CHAT-061** — Clicking a tool row's header MUST expand it into a card that shows the **untruncated** call input and result, each introduced by a small caption in capitals reading `INPUT` and `OUTPUT` respectively. A collapsed tool row shows instead a single dimmed preview line introduced by `⤷`. A tool row with nothing extra to reveal MUST be non-interactive.
- **REQ-CHAT-062** — Thinking rows MUST summarize as `▸ reasoning · <N>s · ~<T> tok`; while streaming they render `◉ reasoning… <N>s · ~<T> tok` with both numbers counting upward, where the token figure is the streamed character count divided by 4. They are collapsible by click. A live thinking row MUST stop presenting as live after 3600 seconds without completion.
- **REQ-CHAT-063** — While any row is live — a running tool, verifier, or group, or reasoning that is still streaming and unstamped — the desktop transcript MUST refresh those rows at least once every **1000 ms**, and at least once every **250 ms** while a terminal stream is live, so their elapsed times advance and their spinners animate. Every live row MUST keep advancing regardless of how many rows sit below it. When no row is live, nothing in the transcript may animate or repaint on a timer. Timed refreshes MUST NOT move the reader's scroll position, change any row's expansion state, or make rows that are not live flicker or reflow.
- **REQ-CHAT-064** — Folding rule: a run of at least **2** consecutive tool rows that belong to the same agent and whose tool names map to the same family MUST collapse into a single group header row labelled with that family's activity word. Family membership: read/read_file/list_dir/list_files/glob/view → "reading"; edit/edit_file/write/write_file/create_file/str_replace/str_replace_editor/apply_patch → "editing"; grep/grep_search/search/codebase_search/web_search → "searching"; bash/execute/execute_bash/terminal/run_command → "running". A tool name outside those lists forms a family of its own, labelled with that tool name, so it folds only with consecutive calls to the same tool. Any intervening message, thinking, different-agent, or different-family row ends the run and prevents rows on either side of it from folding together.
- **REQ-CHAT-065** — A group header MUST carry the number of members with each outcome (ok, failed, blocked, running), the sum of the members' durations, the earliest member start time, and — while a member is in flight — that call's text. It MUST also carry the searchable text of its members, capped at **2000** characters, so REQ-CHAT-074 can match inside a collapsed group. The header MUST take its colour from the most severe member outcome, and while any member is running its duration MUST count upward. Expanding a group MUST keep the header on screen and reveal its members beneath it. Copying a group, and the group's accessible description, MUST both yield a readable summary that starts with "<family> ×N" and continues with the per-outcome counts (for example "reading ×4 · 3 ok · 1 failed"), and MUST NOT emit raw tool input or output. The severity ordering among ok, failed, blocked, and running is not determined — see Open Questions.
- **REQ-CHAT-066** — The structured-questions tool row MUST never fold into a group, and an unsettled live terminal row MUST never fold into a group (its live preview must stay visible). - **REQ-CHAT-135** — Agent-scoped views: the transcript shows only the focused agent's output; the unfocused view filters out tool and edit-diff rows and clears the breadcrumb. A top-bar focus badge shows the focused agent's name, live elapsed time (`M:SS` / `H:MM:SS`, frozen at terminal states), and state-based coloring, with fallback text "No agent selected".
- **REQ-CHAT-136** — URLs in transcript text MUST be linkified (`http(s)` URLs, trailing punctuation trimmed); left-clicking a selected URL or link metadata opens the platform browser (with a platform-appropriate opener fallback chain), toasting "Opened in browser" (1.5 s) or "Could not open browser" (warning, 3 s).
- **REQ-CHAT-137** — Selecting transcript text with the mouse MUST select exactly the characters the pointer covers, including inside virtualized and Markdown-rendered rows. **Right-click** MUST copy the current selection to the system clipboard, showing a "Copied to clipboard" toast for **1.5 s** on success. On failure it MUST show a warning toast for **3 s** whose text depends on the platform: on Windows the message MUST state that the copy failed because Windows clipboard integration is unavailable, and MUST NOT mention the Unix clipboard helpers; on every other platform the message MUST state that the copy failed and MUST direct the user to `xclip`, `xsel`, or `wl-copy`, or to a terminal supporting OSC 52. Right-clicking with nothing selected MUST NOT report success, and MUST NOT trigger the left-click actions of REQ-CHAT-076. Authentication rows MUST remain selectable and copyable, rendering a `🔐 provider` header, a status line, an `Open: <url>` line, and an `Enter code: <code>` line. The exact toast strings are not determined — see Open Questions.
- **REQ-CHAT-138** — The rendered position of every reasoning header MUST be tracked so that a left-click landing on one (when no URL selection takes precedence) toggles reasoning visibility.

### 23. Terminal Transcript Memory, Archive, and Paging

- **REQ-CHAT-139** — Two `agents.yaml` keys MUST govern the terminal's in-memory transcript: `transcript.max_in_memory_events`, defaulting to **100**, accepted from **50** to **1000** inclusive; and `transcript.archive_page_size`, defaulting to **50**, accepted from **10** to **200** inclusive. What the application does with a configured value outside its accepted range — clamp it, reject it, or fall back to the default, and whether the user is told — is not determined; see Open Questions.
- **REQ-CHAT-140** — When the cap is exceeded, the oldest real events MUST be appended to `<session_dir>/state/transcript_archive.jsonl` (one JSON object per line, keys sorted; concurrent writers never interleave lines) and replaced in memory by a single page sentinel of the form `{"role": "page", "offset": N, "count": M}` for the newest archived page. Sentinels are never re-archived.
- **REQ-CHAT-141** — Scrolling near the top (within 3 rows, not via programmatic scrolling) MUST load the oldest sentinel's page from disk off the UI thread and replace the sentinel with its events; when older pages remain, a predecessor sentinel is inserted so repeated scroll-up walks the entire archive backwards; an empty page removes its sentinel; a read failure toasts "Failed to load older messages".
- **REQ-CHAT-142** — The transcript widget's refresh interval MUST be at least **120 ms**. While paused, scroll position restores by block identity plus offset after content changes; follow mode re-pins to the bottom after layout settles and on every resize.

### 24. Terminal Search, Clearing, and Compression

- **REQ-CHAT-143** — Transcript search (search chord or `/search`) MUST open a modal with input placeholder "Search transcript…", a status line, and a results list. The index snapshots the transcript at open time; searchable text concatenates content, reasoning, agent name, tool name, persona, phase, and role; each result's display text prefers content → reasoning → tool name → `[name]` → `(empty)`, truncated at 100 characters with `…`, prefixed by a per-role icon (user 🙂, agent 🤖, tool 🔧, system ⚙, child 👶, thinking 💭, edit-diff 📝, other 📄). Status messages: "No transcript to search.", "N events in transcript." (empty query), "No results.", "N match(es).". Matching is case-insensitive substring. Selecting a result dismisses the modal and scrolls the transcript **proportionally** (event index over total mapped onto the scroll range — approximate, not exact row navigation). Escape dismisses with no side effects.
- **REQ-CHAT-144** — `/clear` in the terminal MUST use a two-step timed confirmation: with a transcript present, the first invocation arms a **5-second** window and warns "Run /clear again within 5s to clear the transcript."; a second invocation inside the window clears the transcript events, live streams, and open tool events, resets render state, persists the session, and toasts "Transcript cleared."; an empty transcript warns "No transcript to clear.".
- **REQ-CHAT-145** — `/compress` ("Force context compression for all running agents"): with no active agents it toasts "No running agents to compress."; with N active conversations it toasts "Compressing context for N agent(s)…", shows a per-agent "compressing" live-activity entry for the duration, compresses all conversations concurrently (unconditionally, per REQ-CHAT-081), toasts "Compression failed for <name>: <reason>" per failed agent (reason truncated to 120 characters), and finishes with "Context compressed for N agent(s)." when any succeeded.

### 25. Terminal Todo Pane

- **REQ-CHAT-146** — The terminal todo pane MUST be display-only (editing is a desktop-only capability). Border title ` todo `; the border subtitle names the source — `plan` (planner-maintained), `agent` (agent-maintained), or the focused child's canonical name when that child carries its own todo (priority: focused child > agent > plan). The border turns the success color when a non-empty todo is present.
- **REQ-CHAT-147** — Content MUST comprise a summary line `[x] C  [>] I  [ ] P  [-] F` counting completed / in-progress / pending / abandoned tasks, then per phase a line `<name lowercased>  N tasks` with `[x]` (accent) for completed tasks and `[ ]` for all other statuses. Empty state: "No tasks yet." / "The agent's todo list will appear here once it starts planning.".
- **REQ-CHAT-148** — Queued prompts consumed at run completion MUST become visible in the todo pane as the "Queued Prompts" phase with tasks named "Queued Prompt: <first 8 chars of id>" (per REQ-CHAT-040), making queue progress observable.

### 26. Terminal Keyboard Leader System

- **REQ-CHAT-149** — All single-stroke Ctrl+letter application commands are replaced by a leader-chord system: default leader **Ctrl+X**, configurable via the `tui.keyboard.leader` configuration key (accepted values: `Ctrl+<letter>` in any casing, normalized, or `Esc`); an invalid value normalizes to Ctrl+X and sets a startup warning "Invalid tui.keyboard.leader '<v>'; using Ctrl+X.". Chords: `P` palette, `M` models, `Q` quit, `S` stash, `R` reasoning, `E` multiline, `/` search, `?` help.
- **REQ-CHAT-150** — While the leader is armed, a transient indicator (the highlighted hints of REQ-CHAT-105) MUST show; the armed state cancels on any unmapped key or after **2 seconds**; Ctrl+C during the armed state cancels the leader without triggering the double-Ctrl+C interrupt.
- **REQ-CHAT-151** — The command palette screen MUST combine a searchable command list (upper two-thirds) with a static shortcut cheat sheet (bottom third), entries formatted `key combo — description — context`, and the cheat sheet MUST reflect the configured leader.
- **REQ-CHAT-152** — The leader system of this section governs the terminal frontend only; it does not replace or disable the desktop shortcuts of REQ-CHAT-001 and REQ-CHAT-002, which remain in force in the desktop window. Within the terminal, the leader MUST NOT capture the composer's submission keys of REQ-CHAT-104 (Enter, Ctrl+J, Ctrl+Enter), nor Ctrl+arrow keys, which move focus between widgets, nor Alt+arrow keys, which navigate artifacts. Every leader chord and palette action MUST also be reachable through a slash command, so a terminal that swallows the chord still leaves the action available; the commands enumerated in REQ-CHAT-117 and REQ-CHAT-118 include no equivalent for the multiline toggle (REQ-CHAT-104) or the reasoning toggle (REQ-CHAT-128), and which requirement is canonical is unresolved — see Open Questions.

### 27. Cross-Cutting Invariants

- **REQ-CHAT-153** — No user-only display content may reach a model. Edit-diff rows (REQ-CHAT-050, REQ-CHAT-133), the focused-agent badge, delegation-context headers, the queued-prompt section, and every truncation marker added for display MUST be absent from prompt text sent to a model, from summaries, from compression input, and from token estimates. Consequently, adding any of them to the view MUST leave a conversation's token estimate unchanged, and a model MUST never be able to quote them back.
- **REQ-CHAT-154** — Both frontends MUST guarantee bounded transcript memory (terminal: the block, row, and Markdown-source caches of REQ-CHAT-126 plus the disk archive of REQ-CHAT-140; desktop: the row-height and rendered-row caches of REQ-CHAT-058) and update cost proportional to the change, not the transcript length.
- **REQ-CHAT-155** — Confirmation MUST precede destruction throughout the domain: transcript clearing requires explicit confirmation on both frontends (dialog vs. timed re-invocation); widening to autonomous permission mode requires confirmation; stale queue edits are refused with explanatory toasts rather than applied.
- **REQ-CHAT-156** — Composer input MUST remain reachable during runs on both frontends (desktop: editable composer with `Queue` labeling; terminal: queue/steer routing) — a running agent never locks the user out of typing.

### 28. Performance Targets (runtime-verifiable)

- **REQ-CHAT-157** — Streamed output and interface updates SHOULD appear on screen within **200 ms** of being produced. While an animation is running, the composer MUST still accept and display keystrokes within that same budget. Transcript size MUST NOT erode interactivity: the desktop MUST hold to the budget with 1000 or more rows present, and the terminal's archive paging MUST keep its resident memory flat as the conversation grows without bound. Partial streamed output MUST render without dropping or duplicating any character, so the finished message equals the concatenation of the deltas received.

## Data & Formats

### On-disk files (externally observable)

| File | Format | Semantics |
| --- | --- | --- |
| `<workspace>/.rotaris/rotaris-prompts.json` | JSON object `{"history": [...], "stash": [...]}`, pretty-printed, trailing newline | Desktop prompt history (≤200) and stash (≤100); atomic writes; blanks dropped on load; malformed/absent → empty |
| `<workspace>/.rotaris/prompt_history.json` | JSON array of strings | Terminal prompt history (≤50 kept on load); atomic writes; malformed → logged, empty |
| `~/.config/rotaris/prompt_stash.json` (user-global config dir) | JSON array of strings | Terminal stash, LIFO; atomic writes; created on first push; corrupt/non-list → empty |
| `<session_dir>/state/transcript_archive.jsonl` | JSON lines, one object per event, sorted keys | Archived terminal transcript pages (default 50 events/page); appended under a lock so lines never interleave |
| Workspace `agents.yaml` | YAML config | `display.*` (tool result/input visibility and line caps), `transcript.max_in_memory_events`, `transcript.archive_page_size`, `tui.keyboard.leader` |
| Platform-native settings storage | key/value | Desktop per-workspace composer draft; desktop UI display toggles (auto-collapse, grouping) |

### Session snapshot transcript rows

Persisted transcript rows are objects with fields: `ts` (timestamp), `content`, `tool`, `detail`, `full_text`, `full_detail`, `persona`, `tool_event_key`, `status`, `duration`, `started_at`, `chars`, `stream_id`; row roles include `user`, `system`, `tool`, `thinking`, `verifier`, and free-form agent names. The session snapshot also carries user-only edit diffs (separate from transcript events), planner and agent todo state, pending questions, and pending approvals. The terminal archive uses the same event objects plus in-memory page sentinels `{"role": "page", "offset": N, "count": M}` (sentinels themselves are never written to the archive).

### Structured-question answer payload

Resolved answers are a map `{<step_id>: {"selected_option": string|null, "freeform_text": string|null}}`; the model-visible rendering is a `## User Answers` section with `- **<step_id>**: <value>` lines and `(no answer)` for unanswered steps.

### Custom prompt-command files

Markdown files with optional YAML frontmatter (`description`, `argument-hint`); body placeholders `$$`, `$ARGUMENTS`, `$1`–`$9`, `$UPPER_NAME` (per REQ-CHAT-122).
