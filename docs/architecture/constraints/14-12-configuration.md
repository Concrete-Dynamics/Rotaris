# Architectural constraints extracted from the specification — 12. Configuration

Part 14 of 22 of [the constraints](../constraints.md), which indexes every part.

## 12. Configuration

| # | Constraint | Label | Requirements |
|---|---|---|---|
| G-01 | **Five layers, fixed and total, with no sixth and no per-key inversion**; there is no command line with which to name a configuration file, so no such file exists. | HARD | REQ-CONFIG-031, REQ-CONFIG-234, REQ-CONFIG-235, REQ-CONFIG-449 |
| G-02 | **Four merge classes with different overlay depths**: named entries overlay exactly one level while sections recurse to any depth. **No key anywhere merges list contents.** | HARD | REQ-CONFIG-040, REQ-CONFIG-043, REQ-CONFIG-046 – REQ-CONFIG-050, REQ-CONFIG-450, REQ-CONFIG-461 |
| G-03 | **Absent, explicit null and value must remain distinguishable through the merge, with a different null policy per merge class**; at the top level a null cannot clear, inside a named entry it can. | HARD | REQ-CONFIG-052 – REQ-CONFIG-057, REQ-CONFIG-451 |
| G-04 | Passes run in a fixed order relative to each other, with three per scope **before** any cross-scope merge because provenance is unrecoverable afterwards, and secret resolution **after** validation so a stored secret can never cause a schema failure. | HARD | REQ-CONFIG-035 – REQ-CONFIG-039, REQ-CONFIG-062, REQ-CONFIG-067, REQ-CONFIG-073, REQ-CONFIG-096, REQ-CONFIG-148, REQ-CONFIG-151, REQ-CONFIG-452 |
| G-05 | A completed load is **fully resolved; no caller finishes the job**. | HARD | REQ-CONFIG-035 |
| G-06 | **No read cache for the primary files.** The snapshot has a modification-time-or-size cache with the false negative **accepted rather than defended against**, and no content hashing on that path. | HARD | REQ-CONFIG-014, REQ-CONFIG-210, REQ-CONFIG-211 |
| G-07 | The severity taxonomy is a **closed, total contract** across the whole load, with a deliberate inversion for one section and a deliberate refusal to coerce one key. | HARD | REQ-CONFIG-024, REQ-CONFIG-183, REQ-CONFIG-233, REQ-CONFIG-476 |
| G-08 | **Validation happens on assignment as well as on load** for two sections, and every value a security control produces is assigned through the validating policy **before any file is written**. | HARD | REQ-CONFIG-111, REQ-CONFIG-183, REQ-CONFIG-436 |
| G-09 | YAML is parsed in a **safe subset**, and boolean folding is undone **per field against that field's vocabulary** before validation, never as a type error and never silently accepted. | HARD | REQ-CONFIG-015, REQ-CONFIG-020, REQ-CONFIG-090 |
| G-10 | One key is read by a **separate parse of the same file**, belongs to no merge class, contributes nothing to the merged configuration and is neither reported nor rejected — yet is read. | HARD (and odd) | REQ-CONFIG-040 |
| G-11 | A rejected value fails the load **as a whole**; nothing that depends on it starts; **no session directory and no lock are created**; the application continues with no workspace configuration loaded. | HARD | REQ-GIT-071, REQ-GIT-138, REQ-CONFIG-246 |
| G-12 | Branch-namespace validation happens **at configuration load, on a rendered example**, so a template that reaches a forbidden namespace only after substitution is caught. | HARD | REQ-GIT-009, REQ-GIT-138, REQ-GIT-139 |
| G-13 | **Re-derived 2026-09-02: half of this row was reversed by an applied ruling and said the opposite of the corpus.** *It read: "Writers preserve key order and never alphabetise, **and comments are lost on the round-trip paths** — stated as an observable cost." **The second clause is withdrawn and must not be cited.*** ESC-2 was ruled and applied: `REQ-CONFIG-252` now states that **comments, formatting and layout are preserved**, the write being a targeted edit of the existing document rather than a re-emission of the whole of it, **including the comment header the first-run bootstrap wrote** (`REQ-CONFIG-025`) — and it is now the single statement of that discipline for every writer of `agents.yaml`. The requirement records in its own text that "the earlier statement that comments and formatting are lost is withdrawn". **What survives unchanged is the key-order half**: writers preserve key order and never alphabetise (`REQ-CONFIG-248`), which the ruling explicitly left untouched. *The observable cost this row recorded no longer exists, and preserving comments was found to be **less** work than deliberately discarding them, because only parse-then-re-emit loses them.* | HARD | REQ-CONFIG-199, REQ-CONFIG-248, REQ-CONFIG-252, REQ-CONFIG-441, REQ-CONFIG-025; ESC-2 |
| G-14 | **No surface writes a configuration it cannot load back**; the whole save is validated **before any file is touched**; the scoped per-field writer refuses an unparseable or non-mapping file. | HARD | REQ-CONFIG-256, REQ-CONFIG-259, REQ-CONFIG-260, REQ-CONFIG-442, REQ-CONFIG-458 |
| G-15 | **Three effect tiers**, of which the middle is architectural: at run start the loaded configuration is copied and the settings store's **current** values are layered on top, **synthesising slot-level variants on the fly exactly as the loader does**. | HARD | REQ-CONFIG-261 – REQ-CONFIG-265 |
| G-16 | **Five persistence destinations, only one of which participates in Save and Discard**, with one stated exception that is not undone by Discard. | HARD | REQ-CONFIG-417, REQ-CONFIG-418, REQ-CONFIG-471 |
| G-17 | A change to the published artifact set is reflected within **750 ms**, and that figure is **an upper bound, not a polling interval**. | HARD | REQ-CONFIG-266 |
| G-18 | The settings screen's outward contract is **a set of intent notifications, not file writes**; the host commits and the screen never names a file. | HARD | REQ-CONFIG-279 |
| G-19 | ***Re-derived 2026-09-02: this row is no longer an escalation and the sentence that made it one is withdrawn.*** *It read: "The shared save path between the settings screen and the composer's permission-mode control, which the specification explicitly hands over for decision", labelled ESCALATION.* **ESC-1 was ruled and applied and the coupling is gone.** `REQ-CONFIG-288` no longer states the coupling in the present tense — it records the decision against it — and the composer's control writes its single key through the scoped per-field writer of `REQ-CONFIG-441`, committing nothing else, so pending Settings edits stay pending, stay dirty and are still undone by Discard. `REQ-CONFIG-423`'s guarantee was preserved by amending its **antecedent** rather than the guarantee, and now says a change to the permission mode made "by **any** other surface" lands in the pending settings state; `REQ-CONFIG-418` needed no change. `REQ-TOOLS-077` stated the same refused coupling from domain 05 and was amended with it. **What constrains the architecture now is the positive rule**: a security-relevant control commits its own key and nothing else. *One consumer has not been swept and is reported rather than repaired: ADR-0037 still says `REQ-CONFIG-288` "has not been amended, and this record must not pretend otherwise" and treats `REQ-CONFIG-423`'s second sentence as having lost its antecedent — both statements are now false.* | HARD (was ESCALATION) | REQ-CONFIG-288, REQ-CONFIG-441, REQ-CONFIG-423, REQ-CONFIG-418, REQ-TOOLS-077; ESC-1 |
