# Session Persistence, Resume, and Background Sessions — 16. Transcript Recording and Persistence

Part 5 of 9 of [domain 07](../07-sessions-persistence.md), which indexes every part. Defines REQ-SESSION-120 – REQ-SESSION-199.

### 16. Transcript Recording and Persistence

- **REQ-SESSION-120** — The persisted transcript MUST be derived from the run's own conversation events and from nothing a view renders. Two consequences MUST be observable: a run with no view attached persists the same transcript rows it would have persisted with one, so a background session can be reopened with a full transcript; and one recorded conversation yields identical rows, field for field, whichever view was watching it, so no two views can leave different transcripts of the same run.
- **REQ-SESSION-121** — Persisted transcript rows MUST use the role/shape vocabulary given in Data & Formats, and every row MUST be stamped with `ts` in local wall-clock `HH:MM:SS` form when appended.
- **REQ-SESSION-122** — Persisted-size caps MUST be: 400 characters for a tool row's `detail`, 2000 characters for its `full_text`, and 4000 characters for thinking content. Content longer than its cap is stored cut to the cap, while a streamed thinking row's `chars` counter MUST keep counting past 4000 so that token estimation remains correct. Terminal (shell) tool output MUST keep its line structure in `full_detail` — the field a reopened session renders — while `detail` holds a single line of at most 400 characters. `full_detail` MUST itself be capped at 8000 characters, because a single tool row must not be able to grow a session's record without bound; when it is cut, the newest output is kept and the cut is made at a line boundary where one falls inside the cap. Every cut in this requirement is marked per REQ-SESSION-194.
- **REQ-SESSION-123** — Each row MUST be published on the wire as a `transcript.row` event (index plus a copy of the row) once on append and once more when the row reaches its final form — intentionally not on every streamed token, so a surface following the run receives the opening token and then the completed text. Publish failures are logged and never raised into the run.
- **REQ-SESSION-124** — Resuming a conversation can replay events; stable per-event identities (per-agent call ids for tool calls, per-agent event ids for committed messages) MUST prevent duplicate rows and double-counted metrics.
- **REQ-SESSION-125** — Reasoning delivered twice — streamed as deltas and then repeated in full alongside the action — MUST end up as exactly one persisted thinking row holding the final full text, with one start timestamp and one settled duration; a second row, whose elapsed-time counter would never stop, MUST NOT appear. Reasoning that was never streamed arrives in one piece and is persisted with no start timestamp, and therefore shows no timer. Where an older version already recorded a burst twice — consecutive thinking rows of the same agent, the content of one being a prefix of the other's — display MUST show only the longer row.
- **REQ-SESSION-126** — A terminal tool row MUST carry a stream identifier of the form `fg:<agent_name>` so that a UI rejoining the session can locate the live terminal buffer the row belongs to.
- **REQ-SESSION-127** — Structured edit diffs MUST live outside the transcript that is fed to the model, keyed `<agent>:<tool_event_key>` and replaced in place on redelivery; at display time each diff is merged beside exactly one tool row.
- **REQ-SESSION-128** — Tool-call metrics MUST be counted into the per-agent and global aggregates at call start, once per stable call id, and each child's live tool set MUST be mirrored onto its persisted child-state record so a snapshot shows what each child is running.
- **REQ-SESSION-129** — Three end-of-activity guarantees MUST hold. When a child agent dies while a tool call is open, that child's persisted record MUST be left with an empty active-tool list and no transcript row of its own left at status `running`; every such row MUST be persisted at status `failed`, keeping whatever output it had already recorded. The tool-row status vocabulary is REQ-MONITOR-105, in which `blocked` denotes a call refused or skipped before it ran and there is no `cancelled` value — a call that was under way and produced no result is a failure, whatever became of the agent that made it, while the child's own record still moves to `cancelled` under REQ-SESSION-065. A verifier check that finishes without ever having been announced — denied by permissions, or out of budget — MUST still produce a verifier row, with the outcome mapping of Data & Formats; the check-outcome vocabulary that mapping is taken over is the closed five-value set of REQ-ORCH-123, which this document holds no copy of. A completed question-tool result MUST remove the matching entries from `pending_questions`, which in turn clears `awaiting_input` once no approvals remain (REQ-SESSION-031).
  > **Narrowed by [`PD-ORCH-005`](../../product/directives/pd-orch-005.md#pd-orch-005), 2026-09-27 (revision 2).** A tool call cut off by a pause, a stop, a quit or a crash is recorded as interrupted and its agent left `paused`, for the agent to see when it resumes; a child that ends otherwise is unchanged.
- **REQ-SESSION-130** — At run end, if the conversation left no agent rows (for example when a child agent's summarized report is the entire answer), one agent row per iteration outcome MUST be appended from the progress record so the transcript still shows an answer — but never duplicated on top of real conversation rows.
- **REQ-SESSION-131** — Transcript rows released from the resident window (REQ-SESSION-192) MUST be retained in the session's record unaltered, in whole pages of 50 rows, in the order they were released, and a retained page MUST never be rewritten, reordered or trimmed — so a row read back out of it is identical to the row that was released and keeps the index it was given. Release is driven by REQ-SESSION-192 and is not optional for any caller. This requirement is the product's single definition of the released-page store: that pages are whole and fixed at 50 rows, that they accumulate and are never disturbed, and that a released row comes back unchanged. A document that relies on released rows still being retrievable — on bringing older rows back on demand unchanged included — cites this identifier and holds no copy of the page size or the retention rule.
- **REQ-SESSION-192** — The transcript a session keeps resident MUST be bounded at the 5000 most recent rows. When an append would exceed that, the oldest rows MUST be released in whole pages of 50 (REQ-SESSION-131) before the append is made, so a session that runs indefinitely has a bounded resident cost and an unbounded, complete history. Releasing a row MUST NOT change the index it or any surviving row was given — the index REQ-EVENTS-052 assigns a row is that row's identity for the life of the session — and a reader that asks for a row older than the resident window MUST be served it from the released pages. Nothing else caps the transcript: the resident row count and the per-row caps of REQ-SESSION-122 are the whole bound, and there is no byte limit. This requirement is the product's single definition of transcript residency: the resident row cap, the point at which release happens, the stability of a row's index across release, and the guarantee that a row older than the resident window is served from the released pages. A document that relies on the transcript being bounded — on keeping the whole conversation readable while only a bounded number of rows stay resident, or on older rows staying reachable after resume — cites this identifier and holds no copy of the cap.
- **REQ-SESSION-194** — One rule governs every character cap in this domain: whenever stored text is cut to fit a cap it MUST be marked as cut, by appending the marker `...` (three ASCII full stops) and counting that marker inside the cap, so a stored value never exceeds its cap and a reader can always tell a complete value from a shortened one. This applies to `detail`, `full_text`, `full_detail` and thinking content (REQ-SESSION-122), to every per-event, per-item and per-artifact budget of the continuation payload (REQ-SESSION-115), to the task line of `summary.md` (REQ-SESSION-140), to the truncated arguments and results of an error-path tool record (REQ-SESSION-136), and to the compact payload rendering of a replayed event (REQ-SESSION-188). Two exceptions are deliberate: an elided todo list is marked instead by the literal line `- [... additional todo tasks elided]` (REQ-SESSION-115), because what is elided is list entries rather than the end of a string; and a streamed thinking row's `chars` counter keeps counting past the cap (REQ-SESSION-122), because it measures what the model produced and not what was stored. Counts, identifiers, paths and timestamps are never truncated.
  > **Narrowed by [`PD-SESSION-003`](../../product/directives/pd-session-003.md#pd-session-003), 2026-10-07.** For the arguments of an
  > error-path tool record (REQ-SESSION-136), what is never truncated wins over the cap: where the paths, identifiers,
  > counts and timestamps alone pass 2,000 characters, the free text is cut to the marker and the stored arguments exceed
  > the cap. Every other clause above still governs.

### 17. Diagnostics and Evidence Records

- **REQ-SESSION-132** — A record kind a session has never written MUST read as empty rather than as missing, and MUST NOT require a placeholder to be created for it to do so. This covers the issues record, the timeline, the tool-call, model-input, context-selection, report-validation and memory records, the permission audit, and the conversation index: reading any of them for a session that produced none of that kind succeeds and yields nothing, so no consumer has to distinguish "never initialized" from "empty" and no save has to create anything to keep that true. The launch audit is the one deliberate exception and is not covered by this rule: it is recorded exactly once by run startup (REQ-SESSION-138), and a session created but never run genuinely has none — which is how a reader tells a session that was never launched from one that was launched and recorded nothing.
- **REQ-SESSION-133** — Retention caps (ring-buffer semantics, newest kept) MUST be: issues 500, tool calls 5000, model inputs 5000, context selections 2000, permission decisions 5000, report validations 2000, memory snapshots 2000. A capped record kind retains only the newest entries, and the trim MUST take effect in the same durable operation that records the entry, so a reader never observes more than the cap and never observes a partly applied trim. Where a cap has dropped entries the record MUST retain enough to say that it has, because counts taken over what remains describe what is stored rather than what the run produced (REQ-SESSION-139) and an export must be able to state it (REQ-SESSION-199).
- **REQ-SESSION-134** — Timeline entries MUST have the shape `{id: 12 hex chars, timestamp: UTC ISO, type, severity: debug|info|warning|error (default info), actor, message, metadata}`. Ordering contract: the durable entry is recorded before any wire event derived from it, so a failing stream may drop an event while the durable record it came from is still retained. Exactly three timeline entry types are bridged to wire events (`completion_gate_decision` → `gate.decision`; `repair_attempt_scheduled` and `repair_escalation` → `gate.repair`, mutually exclusive per decision), and no other timeline type produces an event through this bridge — the `error` event of REQ-SESSION-135 is published by issue recording, not by the timeline. Metadata from which no valid event can be constructed is logged and discarded without failing the iteration.
- **REQ-SESSION-135** — Issue records MUST have the shape `{id: 12 hex chars, timestamp, kind, severity, actor, message, evidence_ref, metadata}`. `id` is what a locator names this issue by, and it MUST be unique among the session's issues and MUST NOT be reused once the retention cap of REQ-SESSION-133 has displaced the issue that held it. `evidence_ref` MUST be either empty — where the issue is evidence of nothing beyond itself — or a locator of the form REQ-EVENTS-056 fixes, naming the record kind and the entry the issue was raised about; its form, its closed record-kind token set and the rule that no export may resolve one are that requirement's and are not restated here. Every recorded issue also writes a timeline entry of type `issue`; only error-severity issues additionally publish an `error` wire event with `fatal=false` (recording an issue never by itself terminates a run); warning- and info-severity issues publish nothing, so an automated consumer does not read a healthy run as failing.
- **REQ-SESSION-136** — Tool-call records MUST carry `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` plus `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings` only when applicable. Each record also streams a `tool.start`/`tool.finish` event pair; the durable record keeps the unredacted arguments while the streamed arguments are redacted by the event schema, so what an agent was actually asked to run stays auditable even though it is never put on the wire. Outcome-driven automatic issues MUST be filed: shell failure → kind `terminal_shell_failure` (error); suspicious success → `terminal_suspicious_success` (warning); timeout → `terminal_timeout` (error); any other failure → `tool_error` (warning); each referencing the tool-call record. On error, recorded args/result are truncated to 2000 characters.

  > are counted over the arguments' JSON text, the arguments keep their shape, only free-text values are cut (longest first,
  > each marked), a value whose key names a path, an identifier or a timestamp is never cut, and the arguments go over 2,000
  > only when those values alone do. Every other clause above still governs.

- **REQ-SESSION-137** — The permission audit MUST record decisions with the field set REQ-TOOLS-079 fixes, which is that requirement's and is cited here rather than restated: this domain fixes that the audit exists, that it is part of the session's durable record, and what its export must make evident, and fixes no field of an entry. As that requirement states it, a decision entry carries `timestamp`, `session_id`, `agent_id`, `persona`, `tool_name`, `decision`, `rule_id`, `source`, `summary` (pre-redacted), `reason`, `request_id` only where the decision resolved a raised approval, **and the entry identifier, which is a field of the entry**. *This requirement formerly stated the field set as a closed literal object that named no identifier. That statement is withdrawn rather than corrected in place, because a second enumeration of one record shape is what let the two documents drift: read as closed it now contradicts REQ-TOOLS-079, and a build following it would export an audit whose locators do not resolve on a machine carrying none of this product's code — the exact failure REQ-EVENTS-056 and REQ-TOOLS-079 exist to prevent, and one nothing errors on. Nothing this requirement guaranteed is lost: every field it named is named by REQ-TOOLS-079, which additionally carries the identifier, the no-argument-values property and the export reasoning this text never held.* A deny files a `permission_denied` warning issue; a one-time or session-scoped user approval files a `permission_approved` timeline entry. Mid-session mode changes share the audit, interleaved with decision entries in write order, in the shape REQ-TOOLS-082 fixes; that shape is cited and not restated here, including its rule that `skipped_personas` is present even when empty so that silence is unambiguous. *A shorter enumeration of it formerly stood here and is withdrawn on the same ground as the one above: it omitted fields REQ-TOOLS-082 requires, so the two documents described two different records. What this domain adds and keeps is below.* A mode-change entry has no entry identifier and none is owed to it (REQ-TOOLS-079, REQ-EVENTS-056), so the export obligation of REQ-SESSION-199 to carry an identifier reaches the entries that have one and no others. Mode changes are counted separately in metrics. The audit is append-only in the sense a reader may rely on: a recorded decision is never altered or removed except by the retention cap of REQ-SESSION-133, and entries stand in the order the decisions were taken. Those two properties MUST be evident in what the export of REQ-SESSION-199 produces, because an audit only this application can read is a materially weaker audit.
- **REQ-SESSION-138** — The launch audit MUST be recorded exactly once per session, by run startup (REQ-SESSION-087), at the first moment the configuration the run will actually execute with is settled — after the worktree has been bound (REQ-SESSION-085) and the sandbox verdict taken (REQ-SESSION-086), and before the first iteration. No later configuration change may alter it, and a run that resumes the session MUST NOT rewrite it, so the audit always describes the launch that created the session. A session that was created but never run therefore carries no launch audit at all, and loading it leaves the configuration snapshot empty (REQ-SESSION-036) rather than presenting a placeholder as a record of a launch that never happened. It MUST contain `{session_id, workspace_root, created_at, run_intent, permission_mode, check_suite, resolved_playbooks (per persona for the run's intent), hooks (id/name/event/matcher/source with secret-redacted command text), config_snapshot}`, with each persona's system-prompt file resolved into inline `resolved_system_prompt` text.
- **REQ-SESSION-139** — The metrics document MUST be rebuilt from the state plus the evidence records on every save and MUST report: session id, status and updated-at; global tool-call, token, cost and compression aggregates; per-agent metrics; the number of tool-call records; a tool-outcomes histogram classifying every recorded call (`outcome_kind` when the record carries one, otherwise derived from `status` and `is_error` into rejected, tool-error, success or unknown) whose bucket totals MUST sum to the tool-call record count; terminal shell-failure, suspicious-success and timeout counts; the 10 slowest tool calls ordered by recorded `elapsed_ms` descending; model-input record and stale-drop counts; context-selection totals; report-validation record and downgrade counts; permission decision, denial, source and mode-change counts; and issue counts in total and by kind. All counts are taken over the entries the evidence records still hold after the retention caps of REQ-SESSION-133 have been applied, so a capped record's counts describe what is stored rather than what the run once produced.
  > **Narrowed by [`PD-TOOLS-013`](../../product/directives/pd-tools-013.md#pd-tools-013), 2026-10-13 (revision 2).** A record that carries no
  > `outcome_kind` and whose failure kind is `interrupted` (a call its run cancelled, a released delegation wait) is derived
  > into a fifth bucket, `interrupted`, rather than tool-error. Every other derivation, the rule that an `outcome_kind` the
  > record carries is its bucket, and the sum of the buckets to the record count still govern.
- **REQ-SESSION-140** — `summary.md` MUST contain, in this order: a `# Session <id>` heading; one line each for status, workspace, created and updated; `- Task: <first user event, cut to 240 characters>`; `- Stop reason: <reason>` when a stop reason is recorded, the line being omitted entirely when none is; a Metrics section in which a value that is unavailable renders as `n/a` or `—` and never as `0`; a Warnings section covering stale-input drops, mostly-elided artifacts, report downgrades, permission denials (naming the permission audit), tool errors, and terminal failures, suspicious successes and timeouts; an Agents section; a Slowest Tools section listing the top 5 by recorded `elapsed_ms`; and a closing inspection note saying where the rest of the record is obtained — the issues record, the timeline, the metrics document and the permission audit through the export of REQ-SESSION-199, and the session log as a file. The summary is itself a file (REQ-SESSION-006) and is replaced under REQ-SESSION-033, so a person reading it while a run writes it never sees it half-written.
  > **Extended by [`PD-SESSION-002`](../../product/directives/pd-session-002.md#pd-session-002), 2026-10-07.** The Warnings section's
  > mostly-elided artifacts are the attached artifacts a delegated agent's `PRIOR AGENT CONTEXT (FULL)` block left out
  > because they did not fit its budget (REQ-LIBRARY-098), each agent-and-artifact pair once, counted from the timeline's
  > `context_selection` entries. This still governs in full.
- **REQ-SESSION-141** — The conversation index MUST hold entries `{conversation_id, agent_name, persona, model, task_id, started_at, ended_at (set when status leaves "running"), status, event_count}`, where `event_count` is the number of events recorded for that conversation. A conversation MUST be resolvable by its id given in either hyphenated or un-hyphenated form, because both forms of one id reach a reader through exported material; the id is a lookup key and never a path, and no resolution rule that scans a directory or counts files is required or permitted.
- **REQ-SESSION-142** — Per-session debug logging MUST write to the session's log, which is a file so that a person can open it in an ordinary text reader (REQ-SESSION-002, REQ-SESSION-191), at the configured session log level (default WARNING; the strings DEBUG/INFO/WARNING/ERROR and integer levels accepted; an unknown string falls back to WARNING and logs a warning), and MUST restore prior logging state at run end.
  > **Narrowed by [`PD-SESSION-004`](../../product/directives/pd-session-004.md#pd-session-004), 2026-11-01.** The session log stays one file and holds at most 32 MiB; past it the oldest whole lines are dropped behind one WARNING marker line. Everything else above still governs.
- **REQ-SESSION-191** — For any session it lists, the application MUST offer three actions: one that opens that session's log for reading; one that reveals the session's files — the log, the summary and the artifact bodies of REQ-SESSION-002 — in the platform's file manager; and one that exports the session's timeline, issues, metrics and permission-audit records (REQ-SESSION-199). The third is not an addition for its own sake: those four are records rather than files, so the file manager no longer reaches them, and without the export moving them into the store would be a straight reduction in what a user owns about their own runs. All three MUST be available whether or not the session is live, MUST write nothing to the session's own record or files, and MUST report the situation rather than appearing to succeed when the log, the files, or a record is missing. All three belong to the action vocabulary of REQ-SHELL-048.
- **REQ-SESSION-199** — The timeline (REQ-SESSION-134), the issues record (REQ-SESSION-135), the metrics document (REQ-SESSION-139) and the permission audit (REQ-SESSION-137) MUST each be obtainable as a file the user chooses, in a form that yields every field of every entry to a stock parser on a machine with none of this product's code present — the same guarantee REQ-EVENTS-166 makes for the event history and REQ-SESSION-189 discharges for it. Each MUST be exportable whether or not the session is live, and exporting MUST NOT disturb the session: nothing is written to its record, and no run pauses for it. Where a session holds no entries of a kind, the export MUST produce an empty record of that kind rather than nothing at all, so that absence is distinguishable from failure. Three further obligations bind it. **It is not a channel.** The export is a user-initiated action producing a file at the moment it is asked for; it MUST NOT be offered or usable as a way to observe a run in progress, MUST NOT refresh itself, and no surface may be built on repeating it (REQ-SESSION-071, REQ-SESSION-159). **The audit exports as an audit.** The permission audit's export MUST make evident the properties the record itself has (REQ-SESSION-137): every entry in the order the decisions were taken, none omitted, and — where the retention cap of REQ-SESSION-133 has dropped earlier entries — a statement that it has and how many, so a capped audit can never be mistaken for a complete one. **It exists to be checked against.** These four are the records this application's own surfaces render, and the export is what lets a user who does not trust that rendering read the record for themselves; an export that summarised, reordered or filtered what the surface shows would defeat the only reason it exists. **A locator resolves against it.** Where an entry of an exported kind can be named by a locator (REQ-EVENTS-056) — an issue by its `id`, a permission-audit **decision** entry by the identifier REQ-TOOLS-079 gives it — the export MUST carry that identifier for every entry it emits **that has one**, so that a locator carried in one exported record resolves against another on a machine with none of this product's code and with nothing beyond a stock parser. Two consequences are stated so neither is inferred. An entry whose own requirement gives it no identifier is not one this obligation reaches: a permission-audit mode-change entry has none and is owed none (REQ-TOOLS-082, REQ-TOOLS-079), and a kind that holds entries of more than one shape is nameable while its unidentified entries are not, which REQ-EVENTS-056 states. And where the record's own shape holds an identifier the export MUST carry it inside the entry, as the permission audit's does; where a shape is closed against additions and an identifier must nonetheless travel, it MUST be carried beside the entry and MUST be locatable as the identifier there, since a value an exported document carries under no known field resolves nothing. The export MUST NOT resolve a locator itself: what a locator names is never inlined, expanded or replaced by the entry it points at, because an export that followed a locator into the tool-call evidence record would become the export that record must never have (REQ-EVENTS-056, REQ-TOOLS-190, REQ-SESSION-136). **The destination is written whole or not at all, and a replacement is retried.** What an export write owes its destination is REQ-EVENTS-145's — that obligation is cited here and none of it is restated, so a change to it changes this requirement with it. This requirement adds only which part of it is load-bearing here and what happens when it fails: the one-step-visibility obligation is what stops a user's previous export being destroyed by a write that does not complete, and it is required of these exports whatever form each takes, the line-delimited forms included. Where the chosen destination already holds a file, replacing it MUST take the bounded retry ladder of REQ-TRACE-061 — cited, not restated, and this domain states no ladder of its own for it; REQ-SESSION-033's ladder governs the summary file on this machine's own storage and is not this one. The reason is the destination rather than the record: this is a write whose target the product does not choose, and a save dialog reaches removable media, storage shared with another machine, a synchronising client's folder, and a directory in which another application holds the previous export open. On such storage a replacement fails transiently with no other opener present at all, so an export a user asked for would otherwise fail for a condition of storage the user can neither act on nor reproduce. **It is not a backup, and does not become one.** These exports are how records leave this application in a form other software reads; they are not restorable by this product and MUST NOT be presented as protecting a user's history against the loss of a machine. That is REQ-SESSION-201's artifact, which is a different thing for a different purpose and does not duplicate this one.
