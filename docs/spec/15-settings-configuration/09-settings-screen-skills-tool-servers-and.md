# Settings and Configuration — Settings screen: skills, tool servers and inventories

Part 9 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-342 – REQ-CONFIG-398.

### Settings screen: skills, tool servers and inventories

- **REQ-CONFIG-342** — The Skills category's master switch sits in the card header, defaults to on, and carries an accessible description saying that the switch settles whether portable skills are attached to agents at the point of **creation**.
- **REQ-CONFIG-343** — The skill table has seven columns: Skill, Source, Path, Trigger, Invocation, Load, Description, which are REQ-WORKSPACE-067's columns with its per-row invocation selector drawn as a column (accepted amendment 2026-09-27, ESC-38). The description is also exposed as a tooltip. The empty state states that no portable skills were discovered.
- **REQ-CONFIG-344** — Skill policy labels differ from the persisted tokens and the persisted token is what is written. Load: displayed `on-demand` → stored `name-only`; `always` → `on`; `manual only` → `user-invocable-only`; `hidden` → `off`. Trigger: displayed `default (both)` → stored `default`; `manual only` → `manual-only`; `auto only` → `auto-only`. Persisting a display label instead of its token would produce unreadable configuration.
- **REQ-CONFIG-345** — Each skill selector carries an accessible name identifying it as that skill's invocation policy or load policy and naming the skill. A stored value outside the vocabularies of REQ-CONFIG-167 and REQ-CONFIG-168 is handled by the general rule of REQ-CONFIG-318: it is **appended to the selector's options and shown as the current selection**, never left as an empty selection and never quietly replaced by the first option. A selector therefore always displays the policy actually stored, and re-saving without touching it cannot silently rewrite a value the product does not recognize.
- **REQ-CONFIG-346** — At the minimum window size, the Trigger and Load selectors must be fully readable: their column widths are at least their natural size and **no policy name is elided**.
- **REQ-CONFIG-347** — When a skill's name collides across scopes, the Source cell is annotated with an information marker and its tooltip discloses that the workspace copy wins and lists the ignored duplicate paths, one per line.
- **REQ-CONFIG-348** — The MCP Servers category shows one row per configured server: a health indicator, the server name and transport, a description, its provenance, and an enable toggle. The health indicator pulses only while a check is in flight, and its tooltip carries the health detail or, failing that, the health word.
- **REQ-CONFIG-349** — A server's enable toggle is initialized from "enabled **and** available" and is **disabled entirely when the server is unavailable**, with a tooltip stating that the command was not found on the executable search path. Toggling a server off records both the disabled state and a marker that the value was overridden for this session, distinct from the configured value.
- **REQ-CONFIG-350** — With no servers, a compact empty state names the configuration file as the place tool servers are declared. **The screen enables and disables servers but does not create, edit or remove them**; registering a new tool server is a file edit. This is a deliberate boundary and not a gap: a tool-server declaration carries a command line or an address and is reviewed as configuration, alongside the hook commands the screen also declines to author (REQ-CONFIG-464).
- **REQ-CONFIG-464** — The settings screen **edits values; it does not author configuration objects**. It never creates, duplicates, renames or deletes a role; it never edits a role's tool, delegation, custom-tool or tool-server lists, so the Tools column stays read-only (REQ-CONFIG-338); it never creates or removes a tool server (REQ-CONFIG-350) or a lifecycle hook; and it offers no per-file switch over individual instruction files, the Instructions category remaining a read-only inventory (REQ-CONFIG-276, REQ-CONFIG-277). Each of those is a configuration-file edit, and the empty states name the file that has to be edited (REQ-CONFIG-437). The screen's own scope is the enumerable value set of REQ-CONFIG-417 destination 1 plus the immediate preferences.

- **REQ-CONFIG-351** — The category header offers a status probe whose accessible description states that it probes every configured server. It is enabled **only when a configuration service is available**.
- **REQ-CONFIG-352** — The probe partitions servers before probing: a server that is **not available** is marked unreachable immediately with the detail that its command was not found on the executable search path, and **is never probed**; a server that is available and present in the configuration's server map is marked as checking and added to the probe set; a server that is available but absent from the map is left untouched. If the probe set ends up empty the action returns **without disabling the button**, so it stays usable when there is nothing to probe. A probe already in flight prevents a second one from starting, so repeated clicks cannot start two.
- **REQ-CONFIG-353** — Per-server results map to healthy or unreachable with the error string as detail, and a discovered tool count carried through only when it is an integer (otherwise absent). When the probe finishes, the action is re-enabled if a service still exists. The observable health vocabulary is exactly `unknown`, `checking`, `healthy`, `unreachable`.

### Settings screen: lifecycle hooks surface

- **REQ-CONFIG-354** — The hooks table shows five columns — Hook, Event, Matches, Source, Status — and is **hierarchical**: top-level rows are agent groups and child rows are individual hooks. After every rebuild the tree is fully expanded and columns are sized to content.
- **REQ-CONFIG-355** — **A hook's command is never shown in the table.** The author of a workspace hook is whoever authored the repository, so the command text is revealed only in a review dialog the user chooses to open.
- **REQ-CONFIG-356** — The command-viewing action starts disabled with a reason directing the user to select a hook, and is enabled only when **exactly one** row is selected and it carries a non-empty command. The dialog renders the command as **plain text**, never as rich text — a hook command must never be interpreted as markup.
- **REQ-CONFIG-357** — An agent group row shows the group label with an empty event and matcher, a source reading as the global runtime policy, and an empty status; it is checkable and its tooltip states that it controls that agent's hooks **for future sessions**.
- **REQ-CONFIG-358** — A hook row shows its name, event, matcher (or a phrase meaning "every matching call" when the matcher is empty), scope label and status. A hook is checkable **only when it is compatible**; an incompatible hook renders without a checkbox, and the status column's tooltip carries the compatibility reason, defaulting to a statement that it runs during future sessions.
- **REQ-CONFIG-359** — Hook status is evaluated in this precedence order and the order is load-bearing: superseded by a higher-precedence scope → superseded, naming the scope that replaced it and carrying no checkbox (REQ-CONFIG-153); not compatible → inactive with the compatibility reason; the agent group disabled → disabled by agent; the hook itself disabled → disabled; not yet allowed → blocked pending review; otherwise → active. An incompatible hook inside a disabled group therefore reports inactive, not disabled-by-agent, and a superseded hook reports superseded whatever else is true of it.
- **REQ-CONFIG-360** — Hook and group checkboxes write to an **external hook policy store immediately**: they are outside the Settings save/discard lifecycle, Save is not involved, and Discard will not undo them.
- **REQ-CONFIG-361** — A hook or group checkbox that the user changes is committed immediately (REQ-CONFIG-360). Nothing else writes: a check state that changes while the table is being repopulated, a change in any column other than the checkbox column, and a row whose identity cannot be read all leave the stored policy untouched. After the commit the table shows the value the user set, neither losing nor reversing it.
- **REQ-CONFIG-362** — The hooks surface rebuilds **only when the underlying hook summary actually changed**; rebuilding on unrelated status refreshes would discard wherever the user had scrolled to. When no configuration or no workspace is available the summary is empty.
- **REQ-CONFIG-363** — The hook summary is readable from outside the screen, recomputes lazily when nothing is cached, and always yields an empty summary rather than nothing. It must be externally invalidatable so a notification action elsewhere can force a refresh.
- **REQ-CONFIG-364** — The hooks empty state states that no compatible hooks are available and names both places hooks may be declared (the external client's global settings and the product's own configuration file). It is keyed on **hooks**, not on groups: a workspace with agent groups but no hooks still shows it.
- **REQ-CONFIG-365** — The trust status label is the status text followed by an external notice when one exists — except that a notice meaning only "the external client declares no hooks" is suppressed as noise.
- **REQ-CONFIG-366** — The workspace-hook review action is enabled only when the summary has items pending review; while disabled, the stated reason is that the workspace contributes no hooks of its own for review. Opening the review dialog is the host's responsibility; the screen only states the intent.

### Settings screen: provider management

- **REQ-CONFIG-367** — A provider row consists of a status line (an indicator whose tooltip is the provider detail, the provider label, a status word, and a detail line), an optional data-destination line, and a right-aligned action row.
- **REQ-CONFIG-368** — The status word is always spelled out beside the indicator and is displayed with underscores replaced by spaces. This screen defines no provider status vocabulary of its own and publishes no value of its own: **REQ-NOTIFY-200 is the product's single definition of the provider status indicator**, and this row relies on it for the closed set of states and for the condition that admits each. The fallback to an idle rendering (REQ-CONFIG-369) exists only so that a value from a future release, or a corrupted one, cannot break the row.
- **REQ-CONFIG-369** — Status colours come in **pairs** — one step for the indicator (which owes 3:1 contrast) and a different step for the word (which owes 4.5:1) — because no single step of a colour ramp satisfies both. The mapping is total over the states REQ-NOTIFY-200 defines: `checking` → informational; `healthy` → success; `warning` → caution; `unauthenticated` and `error` → failure; `unknown`, `coming_soon` and any value the row does not recognize → idle.
- **REQ-CONFIG-370** — At most one destination sentence is rendered per provider row, chosen by connection mode and composed from catalog-supplied fields, with no second hand-maintained provider list: `local-sdk` states that the locally installed agent SDK is invoked and that traffic reaches the provider through it; `rotaris-cloud` names the managed service and the host traffic is sent to; `direct` names the operating organization, omitted where the catalog gives none, and the destination; `custom` names the destination or, where the catalog gives none, refers the user to the configured `base_url`. Any other mode renders no destination line at all. The line is word-wrapped and carries an accessible name identifying it as that provider's destination. The three fields come from the provider's own catalog entry and from nowhere else: `service_name` (string or absent) is the managed service named by the `rotaris-cloud` sentence, `operator_name` (string or absent) is the operating organization named by the `direct` sentence, and `destination_host` (string or absent) is the host named by the `rotaris-cloud`, `direct` and `custom` sentences. Each is presentation text and none is used to route a request. Where a mode's sentence needs a field the catalog does not carry, that mode's stated fallback applies — `direct` omits the organization, `custom` refers the user to the configured `base_url` — and where `rotaris-cloud` carries neither field its sentence is omitted rather than rendered with a gap.
  > **Narrowed by [`PD-PROVIDER-001`](../../product/directives/pd-provider-001.md#pd-provider-001), 2026-10-06.** The hosted mode's
  > sentence, its fields and its fallbacks are unchanged; the mode is spelt `hosted-cloud`, as REQ-PROVIDER-002
  > spells it, here and in the vocabulary table below, whose `rotaris-cloud` names the same mode.
- **REQ-CONFIG-371** — Provider row actions, where *busy* means an operation for that provider is in flight and *actionable* means the provider is available and not busy: **Quick Start** is rendered only for a provider whose catalog entry carries a quick-start URL and is presented as the row's primary action; **Check** is enabled when a provider service exists and the provider is actionable; **Authenticate**/**Re-authenticate** is enabled when the provider has an authentication flow and is actionable; **Log out** is enabled when credentials are stored and the provider is not busy; **Delete** is rendered only for a user-defined provider, is enabled while it is not busy, and is presented as destructive. Exactly one tooltip is shown, chosen in this order: the provider's own detail while the provider is unavailable; then an explanation that the provider offers no authentication flow, where that applies; then a message that an operation is in progress, while busy; then the action's own description. The same rules apply whether the row is being built or refreshed in place. **Availability is a statement about the local prerequisite for reaching a thing, and nothing else**, and the same rule governs the tool-server rows (REQ-CONFIG-349, REQ-CONFIG-352): a provider whose connection mode is `local-sdk` is unavailable exactly when the SDK executable it invokes is not found on the executable search path; a provider on any other connection mode is unavailable exactly when neither its catalog entry nor its configuration supplies a usable address; and a stdio tool server is unavailable exactly when its `command` is not found on the executable search path, an `http` or `sse` tool server exactly when it has no usable `url`, which includes a `url` still carrying an unresolved placeholder (REQ-CONFIG-225). Everything else leaves the thing available: being unauthenticated, failing a health check, reporting an error status, and being busy are all availability-neutral, and available is the default where no prerequisite is missing. The detail a row shows for an unavailable thing names the missing prerequisite.
- **REQ-CONFIG-372** — Three different notions of "already authenticated" exist in this flow and must be reconciled deliberately: the action's **text** is chosen by whether credentials are stored, its **accessible name** by whether the provider is currently connected, and the re-authentication flag passed to the dialog by whether the status is outside the set {unauthenticated, unknown}. A provider with stored credentials that is not currently connected therefore reads as "Re-authenticate" visually and as "Authenticate" to assistive technology.
- **REQ-CONFIG-373** — Starting any provider operation marks that provider busy and immediately refreshes the row, which is what greys its actions and shows the operation-in-progress tooltips. On completion the busy marker is cleared **before** the refresh, so the row does not rebuild still-busy.
- **REQ-CONFIG-374** — Provider work must check that the screen still exists before touching it or the store. **An operation completing after Settings has been destroyed must not crash.**
- **REQ-CONFIG-375** — A health check is started on construction for every provider that has an authentication flow; providers without one are never probed. A check sets the row to checking with a "checking health" detail before it starts.
- **REQ-CONFIG-376** — A row is rebuilt once its in-flight check lands, discarding any control captured earlier. Status is published **one notification earlier** than the clearing of the busy marker, so anything keyed on status alone can catch the row while it is still busy. That gap is real and observable.
- **REQ-CONFIG-377** — Repeated status notifications must not grow the interface: pushing many status/detail updates through must leave the provider's row controls the same objects, show the last value, and leave the total control count unchanged.
- **REQ-CONFIG-378** — The add-endpoint action is enabled only when a provider service exists **and** no registration is already in flight; registration is globally serialized under a single reserved operation identity. The add dialog offers two outcomes: submitting a label, URL and key registers a new endpoint; selecting a built-in provider instead switches to authenticating that provider — so "add endpoint" doubles as the entry point for first-time authentication of a built-in provider that has no row yet, for which a provider record is synthesized as unavailable and unauthenticated because none exists.
- **REQ-CONFIG-379** — Field validation for the add dialog lives **in the dialog**, not in the screen: submitting with empty fields sets the dialog's status to a message naming the missing required field. Registration failures are reported **inside the dialog** rather than on a row.
- **REQ-CONFIG-380** — Registration success ordering: an unsuccessful result sets the dialog error and **leaves the dialog open**; a vanished service sets a service-unavailable error; otherwise the provider catalog is refreshed, the dialog is accepted and released, and the new provider is **health-checked immediately** without the user asking.
- **REQ-CONFIG-381** — Once an authentication attempt reports a connected provider, the usage limits of the subscription-backed providers are refreshed without blocking or closing the authentication dialog and without marking any provider row busy; a refresh that fails, or one for a provider that is still unauthenticated, reports the limits as unavailable rather than raising. For the managed-cloud provider a credit-balance refresh is requested after **every** authentication or logout attempt, successful or not, so the balance on display is never one belonging to a different account.
- **REQ-CONFIG-382** — Managed-cloud sign-in can be requested from elsewhere in the application: the request selects Settings and then runs exactly the flow that the managed-cloud provider row's authenticate action runs. Where no managed-cloud provider is present the request has no effect and reports no error.
- **REQ-CONFIG-383** — Log out asks a plain confirmation question (not a warning) naming the provider and asking whether to remove stored authentication, using the platform's default button placement. Anything but an affirmative answer returns. On confirmation the row goes to checking with a "logging out" detail, and the operation drives the provider to unauthenticated, not connected, with the service's own detail message.
- **REQ-CONFIG-384** — Deleting a user-defined endpoint first computes this workspace's references to it by prefix-matching `<provider id>/` against every model slot and every role model, formatted as a comma-joined list of "slot X" and "persona Y" items, or a phrase meaning none in this workspace.
- **REQ-CONFIG-385** — The deletion confirmation is a warning with Yes and Cancel and **Cancel as the default**, and must promise exactly three facts that the implementation then keeps: deletion is **user-wide** across every workspace on the machine; the listed references are **left unchanged for manual repair**; and **other workspaces were not inspected**. Cancelling must not invoke the delete operation at all. On confirmation the row goes to checking with a deleting detail; a failed result sets the row to error with the result message; success refreshes the catalog and the row disappears along with its delete action.
- **REQ-CONFIG-386** — Result-merge rules when a provider operation returns a replacement record: with no existing row the replacement is **appended** and a change is announced (this is the first-time-authentication path); with an existing row the replacement **inherits the user-defined flag from the existing entry**, so a service result cannot change whether a provider is user-defined; and if the replacement's status is an error **and** the existing entry had credentials, the replacement's credential flag is forced back to true — a failed health check must not make Log out disappear.
- **REQ-CONFIG-387** — A "successful" operation with an **unconnected** result is still a dialog-level failure: the dialog stays open showing the result detail. A connected result accepts and releases the dialog. A failed operation sets the row to error with the message and not-connected, and mirrors the message into any open dialog.
- **REQ-CONFIG-388** — With no providers at all, a compact empty state states that no providers were discovered and that a provider or model endpoint must be configured before starting a run.
- **REQ-CONFIG-389** — The provider list shows **no** built-in or merely-referenced provider by default; a row appears only once a provider is authenticated. The one exception is the managed-cloud provider: its row is shown whether or not it has been authenticated, and which is shown with its quick-start action **in addition to** the normal actions rather than instead of them. A provider that is only referenced by a model slot — a deleted custom endpoint included — must **not** cause a row to reappear.
  > **Narrowed by [`PD-CONFIG-002`](../../product/directives/pd-config-002.md#pd-config-002), 2026-10-06.** The first sentence no
  > longer governs: the list shows every provider REQ-PROVIDER-140 lists, authenticated or not. The managed-cloud
  > quick-start rule and the rule that a reference by a model slot alone causes no row still govern.

### Settings screen: project initialization and machine setup

- **REQ-CONFIG-390** — The Project category holds an initialization card with a status headline, a mouse-selectable detail line, a progress indicator hidden by default and deliberately **indeterminate**, because progress arrives as discrete steps rather than as a completion fraction, and an action row with a primary action plus an availability explanation.
- **REQ-CONFIG-391** — Initialization state is evaluated in this order with these outcomes: (1) a recorded error → headline "failed", action labelled as a retry, enabled; (2) running → headline "initializing", action disabled, the stated reason being that a run is already under way for this workspace; (3) pending → headline "pending", action enabled; (4) skipped → headline "deferred", action enabled; (5) completed → headline "initialized", action **disabled** with a reason that every task is already resolved; (6) otherwise → headline "nothing to initialize yet", action **disabled** with a reason that no task applies yet.
- **REQ-CONFIG-392** — The detail sentence must state, per initialization state: on error, the recorded error text, followed — where tasks are still pending — by a statement that nothing was recorded so those tasks can be run again; while running, which tasks are running and that the view updates when the run finishes; when pending, which tasks have not been run; when skipped, which tasks were skipped and that they can be run at any time, preceded by the completed sentence where any task has completed; when completed, which tasks completed, the calendar date taken from the date part of `initialization.last_run` and omitted where `last_run` is null, and the classification sentence of REQ-CONFIG-393; when nothing applies, that no task applies yet, that tasks appear once the tool they depend on has been configured, and that the user should look at the MCP Servers category and then reload the workspace. Tasks are named by their registry labels (REQ-CONFIG-395), never by the ids stored in `initialization.completed` and `initialization.skipped`.
- **REQ-CONFIG-393** — Exactly one classification sentence is rendered, chosen by `initialization.classification`: `non-code` states that the workspace holds documentation rather than code and that no code memories were produced as a result; `code` states that code memories were created from the workspace's sources. A null value, and any value outside that vocabulary, renders no sentence at all.
- **REQ-CONFIG-394** — The headline's accessible description is set to the detail sentence, so assistive technology reading the headline also hears the explanation.
- **REQ-CONFIG-395** — Initialization task labels come from a registry, so a task registered later appears in this category without changes to the settings surface. The screen must not hard-code task names.
- **REQ-CONFIG-396** — The machine-setup card shows a status line, a mouse-selectable versions line, and a repair action whose accessible description names the tool classes re-probed. The action only states intent; the host performs the repair.
- **REQ-CONFIG-397** — The machine-setup record is read from `<per-user data dir>/setup/state.json`. With no such record, the status line states that machine setup has not run and the versions line states that no managed tool versions are recorded. With a record, the outcome maps to: `complete` → setup completed successfully; `degraded` → usable, with part of the machine tooling missing; `cancelled` → setup was interrupted and can be picked up again; `running` → the record shows a pass in progress that this window did not complete and that may no longer be running, since at most one instance of the application runs (REQ-STARTUP-161) and a recorded `running` outcome with no pass executing is what an interrupted launch leaves behind rather than evidence of a second process; any other value → a line naming that value as the last result, or naming it unknown where the record carries no outcome. Versions render as a comma-joined list of name-and-version pairs sorted by name, or a line stating that no satisfying versions are recorded. The record is a JSON object with three recognized keys: `outcome` (string — `complete`, `degraded`, `cancelled`, `running`, or any other value, handled as above; a missing or non-string value reads as no outcome recorded), `completed_at` (ISO-8601 UTC string, optional, unused by this screen) and `versions` (object mapping a managed tool name to its satisfying version string; a missing, empty or non-object value reads as no versions recorded, and an entry whose value is not a string is skipped). Unknown keys are ignored rather than rejected, since this file is written by the machine-setup subsystem and read here. An unreadable file, invalid JSON, and a top level that is not an object all read exactly as no record at all, which is not an error.
- **REQ-CONFIG-398** — The About category draws on **locally held data alone** — it displays with no provider, no workspace and no authentication present — and is constructed with the application version.
