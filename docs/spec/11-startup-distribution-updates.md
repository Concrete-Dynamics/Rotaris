# Application Startup, Distribution, and Updates

## Overview

Rotaris ships as a standalone desktop application on three platforms — Windows, macOS, and Linux — and as a pair of Python packages that release together under one product version. It is a graphical application only: it exposes no command-line interface, no subcommands, no flags and no text-mode interface, and every capability it offers is reached from the desktop. On first launch of a standalone build, the desktop paints immediately, then runs a visible, cancellable, resumable machine-setup pass that probes for required tools (Git, ripgrep, Node-provided package runners), provisions pinned tool versions into a per-user managed directory, and warms MCP package caches — when a tool is unavailable only the features that need it lose capability, and the application itself is never held back. A supported standalone desktop build performs exactly one silent update check per launch, issued against the product's public release feed once the window is visible; a newer release is offered through a dismissible, non-blocking banner that can download, verify against published checksums, and apply the update using a strategy appropriate to the installation flavour. An opt-in diagnostics flag records a bounded, content-free UI trace to disk.

## Requirements

### Product identity, entry points, and version reporting

**REQ-STARTUP-001** — The product SHALL be published as two Python packages — a core engine package (`rotaris-core`) and a desktop application package (`rotaris`) — that always release together under a single identical product version. A release in which the two packages declare different versions SHALL NOT be publishable.

**REQ-STARTUP-002** — Exactly one executable entry point SHALL exist and be shipped as a standalone binary: the desktop application `rotaris`, which on Windows opens no console window. No console, headless, benchmark or other secondary executable SHALL be published, and no installation SHALL make one available. The one exception is not an entry point a user invokes: the application launches its own executable as a child process to host the bundled code-intelligence tool server, on the terms of REQ-MCP-033 and REQ-STARTUP-015.

**REQ-STARTUP-003** — *Withdrawn.* Its only surface was a command-line invocation of the application as a Python module, which this product does not offer; the single desktop entry point is REQ-STARTUP-002.

**REQ-STARTUP-004** — Each package SHALL report its version from its installed distribution metadata. When that metadata is absent, the reported version SHALL be the literal string `0+unknown`. Standalone bundles SHALL always report the true release version and never `0+unknown`.

**REQ-STARTUP-005** — *Withdrawn.* Its only surface was a command-line flag writing to standard output and setting a process exit code, neither of which this product has; reading the running version is carried by REQ-STARTUP-007 and by the About surface of REQ-SHELL-140, which presents it as selectable text with no window construction or network activity of its own.

**REQ-STARTUP-006** — *Withdrawn.* Its only surface was a console subcommand, and the automatic pre-step it excepted itself from was withdrawn with REQ-STARTUP-100; reading the running version is carried by REQ-STARTUP-007 and REQ-SHELL-140.

**REQ-STARTUP-007** — The running desktop SHALL treat its own version as: the installed desktop-package metadata version; else the literal `dev` when no metadata is installed; and exactly `0.1.0` in demo mode (REQ-SHELL-162). This value SHALL be the one the About surface presents (REQ-SHELL-140) and the one compared against the release feed. When the running version is not a parseable release version (e.g. `dev`), the update comparison is unanswerable and no update SHALL ever be offered (see REQ-STARTUP-109).

### Standalone build command

**REQ-STARTUP-008** — A single version-controlled build command per OS SHALL produce the standalone binary. This command is maintainer-side release tooling driven by the release pipeline of REQ-STARTUP-027; it is not a surface of the shipped product and is reachable by no user of the application. It SHALL accept a target name from exactly {`rotaris`}, an optional bundle mode from exactly {`onedir`, `onefile`} (default `onedir`), and an optional output directory. On success it SHALL print `{target} ({mode}) -> {artifact_path}` to stdout and exit 0.

**REQ-STARTUP-009** — Build error semantics: an unknown target SHALL be rejected before any build work begins, with a message naming the valid targets; a missing build configuration SHALL fail naming the expected path; a failure of the underlying freeze step SHALL be reported with its exit code, never swallowed. All handled failures SHALL print `error: <reason>` to stderr and exit 1. Command-line usage errors (unknown subcommand or choice) SHALL exit 2.

**REQ-STARTUP-010** — A bundle-mode value other than exactly `onedir` or `onefile` SHALL be rejected as an error (typos never fall back to a default).

**REQ-STARTUP-011** — Artifact locations relative to the output directory: `onefile` produces `<dist>/<target>[.exe]`; `onedir` produces `<dist>/<target>/<target>[.exe]`. The default output directory SHALL be `dist/` in the checkout.

**REQ-STARTUP-012** — A standalone bundle SHALL run on a machine of any platform key of REQ-STARTUP-030 (on Linux, the baseline of REQ-STARTUP-024) on which no Python interpreter is present and neither Rotaris package is installed, with all outbound network access blocked. Under exactly those conditions: the desktop entry point SHALL paint its main window; its About surface SHALL present the true release version — never `0+unknown` (REQ-STARTUP-004, REQ-STARTUP-007, REQ-SHELL-140); and every data asset the product reads at run time SHALL resolve from inside the artifact with no additional download — the pricing and model tables, the prompt templates, the CA root bundle used for setup downloads (REQ-STARTUP-083), the font families registered at startup (REQ-STARTUP-040), and `THIRD-PARTY-LICENSES.txt` (REQ-STARTUP-141). No startup path SHALL fail or exit non-zero because packaging or distribution metadata for a bundled component is unavailable.

**REQ-STARTUP-013** — Bundle mode SHALL be assigned per artifact as follows: the Windows portable executable of REQ-STARTUP-031 SHALL be the only artifact published in `onefile` mode — observable as a single executable file that runs with no support tree beside it; the payload wrapped by the Windows installer, the payload inside the macOS disk image, and the payload inside the Linux AppImage SHALL each be a `onedir` tree — observable as the layout of REQ-STARTUP-011, the executable sitting inside a directory together with its support files. Every other published artifact SHALL likewise carry a `onedir` payload; no artifact besides the Windows portable executable SHALL be a `onefile` bundle.

**REQ-STARTUP-014** — The macOS desktop build SHALL be produced as an application bundle named `rotaris.app` with bundle identifier `ai.rotaris.app`.

**REQ-STARTUP-015** — Bundled tool-server hosting: the bundled code-intelligence server SHALL be launched by the application as a child process of its own, on the terms REQ-MCP-033 fixes — in a standalone build through the running executable carrying the reserved token `builtin:code-intelligence` as its first argument, and in a non-standalone runtime through the application's own language runtime. That token is a sentinel for a child process the product starts internally; it is not a user-facing invocation, no argument vocabulary beyond it is defined for the executable, and a process started with it presents no user interface and opens no window (REQ-MCP-033, REQ-MCP-113). Exactly one copy of the bundled tool server's license text SHALL be present inside the desktop bundle (REQ-STARTUP-142).

### Windows installer and portable executable

**REQ-STARTUP-016** — The Windows installer SHALL install strictly per-user with no elevation prompt: default install location `%LOCALAPPDATA%\Rotaris`, with the chosen directory remembered in the per-user registry under `HKCU\Software\Rotaris` (value `InstallDir`). Per-user installation SHALL allow the in-app updater to replace files without administrator rights.

**REQ-STARTUP-017** — Interactive installation SHALL flow Welcome → Directory → Install → Finish, warn on abort, and offer a checked-by-default "Launch Rotaris" checkbox on the Finish page. Silent installation (`/S`, with optional `/D=<dir>` to set the directory) SHALL show no pages and never auto-launch the app.

**REQ-STARTUP-018** — Installation SHALL: copy the application tree into the install directory; create a Start Menu folder `Rotaris` containing shortcuts `Rotaris` (to the app) and `Uninstall Rotaris`; write a per-user uninstall registry entry under `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` with `DisplayName`, `DisplayVersion`, `Publisher` = `Rotaris`, `DisplayIcon`, `UninstallString`, `NoModify`=1, `NoRepair`=1; and write an `Uninstall.exe` into the install directory.

**REQ-STARTUP-019** — Uninstallation (including silent `Uninstall.exe /S`) SHALL remove only what installation created: the shortcuts, the installed tree, the uninstaller, the install directory only if it is then empty, and both registry keys. Per-user configuration and data directories and per-workspace `.rotaris/` state SHALL never be touched by uninstall.

**REQ-STARTUP-020** — The Windows portable artifact SHALL be a single self-contained executable that runs from any location when double-clicked, without installation.

**REQ-STARTUP-021** — Windows binaries are unsigned; first-launch OS trust prompts (SmartScreen) are expected and SHALL be disclosed in the release notes caveat (REQ-STARTUP-035).

### macOS disk image

**REQ-STARTUP-022** — The macOS artifact SHALL be a compressed disk image whose volume is named `Rotaris <version>`, containing the application bundle and an `/Applications` symlink for drag-to-install. It SHALL be native ARM64 only.

**REQ-STARTUP-023** — By design no code signature and no notarization ticket are applied to the macOS artifacts; the first-launch Gatekeeper confirmation is therefore expected and SHALL be disclosed in the release notes caveat (REQ-STARTUP-035).

### Linux AppImage

**REQ-STARTUP-024** — The Linux artifact SHALL be an AppImage that runs without being extracted first on an unmodified Ubuntu 24.04 installation — the oldest system-library baseline the artifact is required to support. It SHALL carry a desktop entry with `Type=Application`, `Name=Rotaris`, `Terminal=false`, categories `Development;IDE;`, an application icon, and an Exec line that accepts an optional directory the desktop environment supplies when the user opens a folder with the application — a file-manager "open with" or drag-onto-icon gesture. A directory the operating system hands the application this way is the explicitly opened workspace of REQ-STARTUP-041 (a). This registration is the only path by which anything outside the application selects a workspace; it is a graphical gesture, and the application defines no argument vocabulary a user could type.

**REQ-STARTUP-025** — The AppImage SHALL be built against the oldest supported base OS, so that changing the build environment can never quietly narrow the set of distributions on which the published artifact runs.

### Platform scope

**REQ-STARTUP-026** — The platform keys a release publishes for SHALL be exactly the three of REQ-STARTUP-030. A release's asset list SHALL therefore contain no filename bearing a Windows-ARM64 or macOS-Intel platform key, and no download surface SHALL present a download for either. A visitor on Windows ARM64 SHALL be presented the `windows-x64` artifacts, those being the only Windows downloads offered at all. Running a `windows-x64` artifact under Windows-on-ARM x64 emulation is an expectation and not a supported configuration: it carries no acceptance criterion of its own, no release is blocked by a failure observed only under emulation, and the release gate of REQ-STARTUP-156 exercises exactly the three platform keys of REQ-STARTUP-030 and no fourth. A download surface reached from a platform for which the release publishes no artifact — Windows ARM64 and Intel macOS being the two such platforms — SHALL state which artifact it is offering instead, SHALL state that the artifact is built for a different processor architecture and is not tested on the visitor's platform, and SHALL still offer the download rather than withholding it; on Intel macOS, where no artifact can run at all, it SHALL instead state that this release publishes no macOS build for that architecture and offer no macOS download. The wording is left to the implementation.

### Release pipeline

**REQ-STARTUP-027** — A release SHALL be triggered only by pushing a tag of the exact grammar `v<major>.<minor>.<patch>`, optionally followed by a PEP 440 prerelease suffix `a<N>`, `b<N>`, or `rc<N>` (e.g. `v1.2.3`, `v1.2.3rc1`). Refs that do not match this grammar — `vlatest`, `v1.2.3dev1`, `1.2.3`, `v1.2`, `v1.2.3-rc1`, and branch refs among them — SHALL NOT trigger a release; when a candidate string is validated, the rejection message SHALL name the offending tag and describe the expected shape.

**REQ-STARTUP-028** — Before any build, a guard SHALL verify that the tag version equals the declared version of both packages. On mismatch it SHALL fail (exit code 1, stopping all platform builds) with a message that names all three values and both manifest locations and instructs that the product releases one version and both manifests must be bumped to the tag. The same pre-build guard stage SHALL additionally enforce the package-pin agreement of REQ-STARTUP-059 and SHALL fail the same way — one stage, one exit code, all platform builds stopped — so that no platform is ever built from a release whose pins disagree.

**REQ-STARTUP-029** — Release-channel classification SHALL map plain `X.Y.Z` to `stable` and any `aN`/`bN`/`rcN` suffix to `prerelease`; an invalid version string SHALL be an error stating it is not a supported product version.

**REQ-STARTUP-030** — The build matrix SHALL cover exactly `windows-x64`, `macos-arm64`, and `linux-x86_64`, and a failure on one platform SHALL NOT cancel the others. The final release SHALL publish whatever artifacts survived, and a separate overall status SHALL still report failure when any platform failed, so a partial release is visible.

**REQ-STARTUP-031** — Artifact names SHALL come from a single authority shared with the updater, with these exact shapes: `Rotaris-{v}-windows-x64-setup.exe` (installer), `Rotaris-{v}-windows-x64-portable.exe` (portable), `Rotaris-{v}-macos-arm64.dmg`, and `Rotaris-{v}-linux-x86_64.AppImage`. Requesting an unknown artifact kind SHALL error listing the known kinds. Per-platform kinds: windows-x64 → setup, portable; macos-arm64 → dmg; linux-x86_64 → appimage. No console archive kind exists, the console binaries it carried having been withdrawn with REQ-STARTUP-002.

**REQ-STARTUP-032** — Each release SHALL publish a checksum manifest named `SHA256SUMS.txt`: one line per asset in the form `<sha256hex>  <filename>` (two-space separator), sorted by filename, compatible with `sha256sum -c`. The manifest SHALL never list itself.

**REQ-STARTUP-033** — The generated changelog SHALL compare against the previous tag: with no previous tag, the body is exactly `First release — no previous tag to compare against.`; with a previous tag but no commits, `No commits since <prev>.`; otherwise `Changes since <prev>:` followed by one bullet per commit subject (merge commits excluded).

**REQ-STARTUP-034** — The published release SHALL be named `Rotaris <version>` and flagged prerelease when the channel is `prerelease`.

**REQ-STARTUP-035** — The release body SHALL contain the following elements, each individually checkable, in this order: (1) the heading `## Rotaris {v}`; (2) a line stating the release was built from tag `v{v}`, containing that tag string literally; (3) a table with exactly one row per published asset except `SHA256SUMS.txt`, each row carrying that asset's filename and its SHA-256 hex digest, the digest being the same value that release's `SHA256SUMS.txt` lists for the same filename (REQ-STARTUP-032); (4) present if and only if at least one platform of REQ-STARTUP-030 contributed no asset, a blockquote reading `**Not built in this release: <platform labels>.** Those builds failed; the artifacts above are unaffected. Use the previous release for the missing platforms.`; (5) a verification hint naming the command `sha256sum -c SHA256SUMS.txt` for macOS and Linux and, for Windows, the command `certutil -hashfile <filename> SHA256` — chosen because it is present on every supported Windows installation and needs nothing installed — together with a statement that the hexadecimal digest the Windows command prints is compared, ignoring case and ignoring any spacing the command inserts, against the line of `SHA256SUMS.txt` carrying that filename; (6) a caveat stating that the binaries carry no code signature and naming both SmartScreen and Gatekeeper; (7) a `## Changes` section whose content is the changelog of REQ-STARTUP-033.

**REQ-STARTUP-036** — Python-package publication to PyPI SHALL occur only for the `stable` channel, SHALL explicitly build and upload both packages, SHALL run after the binary release is published, and SHALL never gate or retract it — a PyPI failure leaves the binary release intact. Prerelease tags publish binaries only (flagged prerelease) and never touch PyPI.

**REQ-STARTUP-037** — A licence-inventory generation and validation step (REQ-STARTUP-143) SHALL run per platform before freezing, and its failure SHALL fail that platform's release.

**REQ-STARTUP-038** — Every published stable release SHALL satisfy the following distribution claims, each independently verifiable: each desktop artifact the official download page offers SHALL have the same filename and the same SHA-256 digest as the asset of that name in the most recent GitHub release of the product repository; the desktop artifact SHALL run with no separately installed Python (REQ-STARTUP-012); and the release SHALL have been produced by the tag-triggered pipeline of REQ-STARTUP-027 and published together with a `SHA256SUMS.txt` covering every other published asset (REQ-STARTUP-032). No download surface SHALL state a distribution claim that contradicts these.

**REQ-STARTUP-156** — Release acceptance SHALL rest only on evidence the product itself can produce, and SHALL be exactly the following set, each of which is decidable inside the pipeline or on a machine the release owner controls: the version guard and package-pin guard of REQ-STARTUP-028 passed; the notices validation of REQ-STARTUP-037 and REQ-STARTUP-143 passed on every platform that contributed an asset; `SHA256SUMS.txt` covers every other published asset and every listed digest matches its asset (REQ-STARTUP-032); the release body carries the seven elements of REQ-STARTUP-035; and, on each of the three platform keys of REQ-STARTUP-030, the published artifact has been downloaded and launched to first paint at least once, so the offline-run claim of REQ-STARTUP-012 is observed rather than assumed. Behaviors owned outside the product SHALL NOT be release gates and SHALL NOT be asserted as requirements: how the release page renders, what the release host does with the prerelease flag, how the release API answers when rate limits are exhausted, the exact wording or sequence of the operating system's own first-launch trust warnings, and what a silent installation contributes to shell integration are each observed and disclosed rather than guaranteed, and none of them SHALL block or retract a release. This is consistent with REQ-STARTUP-110: an update check that fails because an externally owned behavior changed is invisible by design, so no release needs to be held against it.

### Desktop launch and startup sequence

**REQ-STARTUP-039** — *Withdrawn.* Its only surface was a command-line argument vocabulary, which this product does not have; every capability those arguments carried is reached from the desktop instead — the workspace a launch opens through REQ-STARTUP-041 and the chooser of REQ-STARTUP-052 and REQ-SHELL-021, demo mode through REQ-SHELL-162, the running version through REQ-STARTUP-007 and REQ-SHELL-140, and diagnostics capture through REQ-STARTUP-129 and the Settings controls of REQ-SHELL-163.

**REQ-STARTUP-040** — At startup, before any window exists, the desktop SHALL: fix its persisted-settings identity to organization `Rotaris`, application `Rotaris`; set the branded application icon so taskbar/switcher/window chrome carry the product mark; register bundled font families so branded fonts render from first paint; and restore the persisted theme choice.

**REQ-STARTUP-041** — Startup workspace resolution SHALL behave as: (a) a directory the operating system hands the launch — the folder the user opened the application with, through the registration of REQ-STARTUP-024 or its per-platform equivalent — is expanded/resolved, immediately persisted as the remembered workspace (settings key `workspace/lastOpened`), and suppresses the first-launch workspace prompt; (b) with no such directory and a remembered value that is still an existing directory, that directory is reopened without any prompt and the remembered value is not rewritten; (c) with no such directory and no valid remembered directory, the process working directory is used (REQ-SHELL-010) and the first-launch workspace prompt is scheduled — the stale remembered value is preserved, not cleared.

**REQ-STARTUP-042** — The main window SHALL be usable at a minimum geometry of 1000×680.

**REQ-STARTUP-043** — Background activation (repository status discovery, the update check, and the cloud-credit poll) SHALL start only after the window is shown. The update check SHALL be initiated only from this post-show activation and never during window construction, so constructing a window without showing it produces no network traffic.

**REQ-STARTUP-044** — Deferred first-paint work SHALL use one shared 650 ms delay after show, and exactly one of two mutually exclusive schedules SHALL apply: (a) when the runtime is bundled and machine setup is required, the sequence is: window visible → (650 ms) → modal machine-setup dialog → refresh of the settings machine-setup card → start of repository status discovery → then the first-launch workspace prompt if onboarding was also pending; repository discovery SHALL NOT start before setup completes in this schedule; (b) otherwise, when onboarding is pending, the workspace prompt fires after the same 650 ms.

**REQ-STARTUP-045** — Closing the window before a deferred prompt fires SHALL cancel the pending prompt; it must never fire against a destroyed window.

**REQ-STARTUP-046** — Closing a window SHALL behave as follows. When a run is active, a confirmation SHALL be presented before anything is torn down; declining it SHALL abort the close, leaving the window open and accepting input and the run still executing (REQ-STARTUP-047 depends on this refusal). The confirmation SHALL offer exactly two answers — close anyway, and return to the window — with the returning answer the default, and Escape and the dialog's close control both SHALL be treated as that returning answer (REQ-SHELL-055). Its text SHALL convey exactly three things: that a run is still executing, that closing the window ends it, and that the alternative is to return to the window and let it finish; the wording is left to the implementation. Declining SHALL leave every piece of window state untouched — the same workspace, the same active view, the same composer contents, the same pending deferred prompts, the same in-flight update work, and the same persisted settings values as before the attempt — so that a declined close is indistinguishable from a close never attempted. Once closing has begun: no deferred prompt or deferred activation still pending SHALL start (REQ-STARTUP-045); no further background activity of REQ-STARTUP-043 SHALL be initiated; an update check, download, or install still in flight SHALL be waited for at most 5000 ms, after which the close SHALL complete whether or not that work finished; diagnostics SHALL be finalized as in REQ-STARTUP-139; and every dialog and child window opened from this window SHALL be closed. After the close completes, no window, prompt, dialog, or toast belonging to that window SHALL appear.

**REQ-STARTUP-047** — Switching projects at runtime SHALL: build and show a replacement window for the selected folder, then close the old window; if the old window refuses to close (e.g. the user declines the active-run confirmation), the replacement SHALL be discarded and nothing changes; on success the remembered-workspace setting is updated and the replacement window goes through the same post-show activation (including a fresh update check for that window). If constructing the replacement fails, an error toast `Could not open the selected project: {reason}` SHALL appear on the old window, which remains fully usable.

**REQ-STARTUP-048** — Project switching SHALL only be honored for the current primary window.

### First-launch workspace onboarding

**REQ-STARTUP-049** — The workspace chooser SHALL be the native OS directory dialog, titled exactly `Open a project folder`, restricted to directories, starting at the user's home directory on first launch (or at the current workspace when opened later).

**REQ-STARTUP-050** — On first launch with no remembered workspace, the complete default desktop SHALL be painted and visible before the modal chooser opens.

**REQ-STARTUP-051** — If the user dismisses the chooser at first launch, the default workspace SHALL stay in effect, the desktop SHALL remain fully usable, any remembered value SHALL be left untouched, and a toast SHALL appear containing the sentence `Open a project folder when you're ready by selecting the workspace path in the title bar.`

**REQ-STARTUP-052** — The workspace text rendered in the title bar SHALL itself be a keyboard-reachable, accessible action (accessible name `Open project folder`) that reopens the same chooser rooted at the workspace currently open. Picking a folder other than that one triggers the project switch of REQ-STARTUP-047 and makes the picked folder the remembered workspace; picking the folder already open does nothing.

**REQ-STARTUP-053** — Opening the workspace chooser from a live window SHALL evaluate three gates in one fixed order, the same order and the same gates a window close uses (REQ-SHELL-021, REQ-SHELL-119), and any of them SHALL end the flow. (1) **Unsaved settings**: where the Settings view is holding edits that have not been saved, the save/discard/cancel dialog of REQ-SHELL-124 SHALL be raised; Cancel ends the flow with nothing changed, a Save that fails also ends it, and a Save that succeeds or a Discard lets evaluation continue. No separate refusal message exists for this gate — the dialog is the message, and the user clears the condition by saving or discarding. (2) **Worktree integration running**: refused outright with an error toast reading `Finish the worktree integration before opening another project.` (3) **Run active**: refused outright with an error toast reading `Finish the active run before opening another project.` In each refused case no directory dialog SHALL open, no project switch SHALL occur, the persisted `workspace/lastOpened` value SHALL be unchanged, and the window SHALL go on accepting input exactly as it did before the attempt.

**REQ-STARTUP-054** — Toasts used by onboarding and machine setup SHALL be the window's one transient notification surface (REQ-SHELL-112): word-wrapped at a maximum width of 520 px, appearing top-right under the title bar, and auto-hiding after 4200 ms.

### Demo mode

**REQ-STARTUP-055** — Demo mode (REQ-SHELL-162) SHALL open a desktop window populated with a fixed sample dataset such that each of the following holds at least one item: a running session, its transcript, the agents list, the todo list, the artifacts list, and branch state. The presented content SHALL be a constant of the build — two launches of the same build, on any machine, at any time, SHALL present identical values in those views, and no presented value SHALL be derived from the clock, the host, the working directory, or a random source. The version presented in the interface SHALL be `0.1.0`.

**REQ-STARTUP-056** — Demo windows SHALL never persist the remembered workspace, never prompt for a workspace, never read or mutate real repository/config/run state, and never start the cloud-credit poll. Diagnostics recording still attaches when requested.

**REQ-STARTUP-057** — Demo mode SHALL perform no update network traffic on any runtime. A demo window SHALL issue no request to the endpoint of REQ-STARTUP-105 and none to any release-asset URL, whether or not the runtime is a standalone build, and SHALL therefore never present an update notice; the installation flavour is not consulted, because a demo window is not offering to update the installation it is running from. This is the same answer REQ-STARTUP-114 gives from the other side, and the two SHALL be read together. A non-demo window of the same process is unaffected and checks exactly as REQ-STARTUP-114 requires.

### Machine-setup manifest and platform keys

**REQ-STARTUP-058** — Each release SHALL carry a pinned machine-tool manifest (schema version 1) declaring, per tool: probe command, version arguments, optional minimum acceptable version, the provisioned version, per-platform archive artifacts (HTTPS URL, 64-hex SHA-256 digest, archive layout, expected executables), license identifier, and the user-facing capabilities the tool enables. The shipped manifest SHALL pin: Git — no minimum (any working system git is reused), provisioned version 2.55.0, a Windows-x64-only archive from the upstream Git-for-Windows release line, license `GPL-2.0-only`, capabilities worktrees and checkpoints; ripgrep — minimum 14.1.0, provisioned 15.2.0, archives for all three platforms from the upstream ripgrep releases, license `Unlicense OR MIT`, capability search.

**REQ-STARTUP-059** — The machine-tool manifest a build ships SHALL state exactly one version for every tool-server package it lists, written as a complete version string with no range, alias or floating tag. The identities of the third-party packages the built-in defaults name are not fixed by this document and may change between releases (REQ-CONFIG-181, REQ-MCP-010); what is fixed is the agreement between the two places a build states them. The manifest SHALL pin every package that the built-in default tool-server configuration of that same build launches through `npx` or `uvx`, and for every package named in both places the two version strings SHALL be equal character for character, compared with no case folding, alias expansion, or range interpretation. A default entry naming a package the manifest does not pin, and a pair that disagrees, SHALL each fail the pre-build guard stage of REQ-STARTUP-028 — exit code 1, all platform builds stopped — with a message naming the package, both version strings (or the absence of one), and both file locations. No release SHALL publish a build in which such a pair disagrees. Since a warm-up step is planned only for a specification carrying an exact version (REQ-STARTUP-064), a configured package left unpinned or pinned to `@latest` SHALL never be warmed, whatever the manifest states for it.

**REQ-STARTUP-060** — Platform keys SHALL be `windows-x64`, `macos-arm64`, and `linux-x86_64`, with a raw `<os>-<machine>` fallback for anything else, and SHALL be shared between release artifact naming, updater asset selection, and manifest artifact selection.

**REQ-STARTUP-061** — The manifest fingerprint SHALL be the SHA-256 of the manifest serialized as canonical JSON (sorted keys, compact separators). This fingerprint is the sole identity used to decide whether setup must run again.

**REQ-STARTUP-062** — Deliberate exclusions: Node.js SHALL be supplied by the user and SHALL never be downloaded by setup; no Git MCP server SHALL be shipped, pinned, warmed, or granted (agents use terminal git); the bundled MCP server runtime requires no setup step. The setup dialog's explanation copy SHALL name only Git, Node, ripgrep, and MCP package caches, and SHALL NOT mention internal tooling names.

### Setup planning and probing

**REQ-STARTUP-063** — Tool probing SHALL: resolve the command on the (managed-augmented) PATH; run its version command with a 10-second timeout and, on Windows, with no visible console window; extract the first dotted numeric version from combined stdout+stderr; and treat the tool as satisfied only when the probe exits 0 and (no minimum is declared or the parsed version ≥ the minimum). A missing executable or a probe error yields not-satisfied. For Git specifically, any exit-0 probe satisfies regardless of whether a version could be parsed; a non-zero exit does not.

**REQ-STARTUP-064** — MCP cache warm-up steps SHALL be computed from the merged MCP server configuration of the workspace being opened, so that adding, removing, or repinning a server changes the resulting plan. A configured server SHALL contribute a warm-up step only when it is a stdio server launched through `npx` or `uvx` and its package specification pins an exact version — a parseable version following `==`, or following the last `@`. A specification with no version and a specification pinned to `@latest` SHALL contribute no step; HTTP and SSE servers SHALL contribute no step; a server entry carrying `enabled: false` SHALL contribute no step, because nothing will ever launch it (REQ-CONFIG-465); and a `stdio` entry whose command is the reserved bundled-runtime token SHALL contribute no step, because what it resolves to ships inside the artifact (REQ-MCP-033). Steps SHALL be deduplicated by the pair (runner family, package specification), and the step order SHALL be that same pair sorted ascending — runner family first, then package specification, each compared as a sequence of Unicode code points with no case folding — so one key serves both deduplication and ordering, a package configured for two servers is warmed once, and the same merged configuration always yields the same step sequence whatever order the servers appear in. A step's label SHALL be `Warm <package>`. The executed command SHALL be `npx -y <pkg> --help` for the `npx` family and `uvx --from <pkg> <executable> --help` for the `uvx` family, where `<executable>` is the executable that server entry is configured to launch.

**REQ-STARTUP-065** — An `npx` warm-up SHALL be planned only when `npx` resolves on the PATH at plan time, and the discovered absolute launcher path (including the Windows `.CMD` shim) SHALL be used in the executed command. Without `npx`, the warm-up silently disappears from the plan and the MCP server that the default configuration starts through `npx` is reported unavailable until the user installs Node and thereby supplies `npx`.

**REQ-STARTUP-066** — When setup was not manually requested and a durable record exists whose fingerprint equals the current manifest fingerprint and whose outcome is `complete`, or is `degraded` with accepted degradation, the plan SHALL be empty. An empty plan SHALL run no probe command, issue no network request, run no warm-up command, leave `setup/state.json` byte-for-byte unchanged including its recorded timestamps (REQ-STARTUP-074), and show no setup dialog (REQ-STARTUP-096).

**REQ-STARTUP-067** — A non-empty plan SHALL be ordered deterministically: a detect step (`Detect machine tools`); then per manifest tool either a satisfied step (`<name> already installed`, carrying the probed version) or an install step (`Provision <name>`, carrying its capabilities); then warm-up steps whose recorded state is not already complete (all warm-ups rerun under manual repair); then a record step (`Record machine setup`).

**REQ-STARTUP-068** — Top-up: when a record exists with a different non-empty fingerprint, the plan SHALL be marked as a top-up and contain only genuinely missing work — already-satisfied tools re-listed as satisfied with no re-downloads. A top-up SHALL be presented exactly as a first-time run is: the dialog vocabulary of REQ-STARTUP-090 stays two-valued, a top-up that was not manually requested carries the page title `Preparing Rotaris`, and no third page title, explanation text or badge distinguishes it. The distinction is already visible where it matters — the step list shows the already-satisfied tools as satisfied steps and shows only the missing work as install or warm-up steps (REQ-STARTUP-067) — and the top-up marking is internal, used to decide the plan's content and not to change what the user is shown.

**REQ-STARTUP-069** — When a setup pass is required and every manifest tool is already satisfied by an installed tool (REQ-STARTUP-063), the plan SHALL contain no install step and the pass SHALL issue no request to any pinned tool-archive URL. For a workspace whose MCP configuration contributes no warm-up step (REQ-STARTUP-064), the plan SHALL then consist of exactly the detect step, one satisfied step per manifest tool, and the record step, in the order of REQ-STARTUP-067.

### Setup execution: state, locking, resume, cancel, failure

**REQ-STARTUP-070** — Everything setup writes SHALL be rooted in the per-user data directory: managed tools at `tools/<tool>/<provisioned_version>/`; the durable record at `setup/state.json`; caches at `setup/cache/downloads/`, `setup/cache/uv/`, and `setup/cache/npm/`; and a cross-process lock file at `setup/setup.lock`.

**REQ-STARTUP-071** — The durable record (schema version 1) SHALL be a JSON object at `setup/state.json` containing: the manifest fingerprint; an outcome of `running`, `complete`, `degraded`, `cancelled`, or empty; a map of verified tool versions; a map of managed binary directories per tool; per-step state (a stable step identifier, status, elapsed seconds, detail text); a sorted list of degraded capabilities; an accepted-degradation boolean; and started/updated/completed UTC ISO-8601 timestamps. Three of those field names are fixed, because a surface outside this domain reads them: the outcome is the key `outcome`, the completion timestamp is the key `completed_at`, and the verified-tool-version map is the key `versions`, mapping a managed tool name to its satisfying version string (REQ-CONFIG-397). The remaining fields are this domain's own, may be named as the implementation chooses, and are the "unknown keys" REQ-CONFIG-397 requires that reader to ignore rather than reject. Saves SHALL be atomic (same-directory temp file, fsync, rename) with the updated timestamp refreshed on every save and no temp-file litter; a missing or corrupt record SHALL be read as absent, never as an error.

**REQ-STARTUP-072** — The setup lock SHALL be an exclusively-created file (owner-only permissions) containing the holder PID and creation time. A second acquisition fails while the owner is alive. A stale lock — older than 900 seconds AND whose recorded PID is no longer running — SHALL be reclaimed; the liveness probe must have no side effect on the probed process. Release deletes the file.

**REQ-STARTUP-073** — When the lock cannot be acquired, the runner SHALL emit a terminal event with the message `Machine setup is already running`, still activate the managed tool environment for the current process, return the `already-running` outcome, and leave the durable record untouched.

**REQ-STARTUP-074** — Setup outcomes SHALL be exactly: `complete`, `degraded`, `cancelled`, `already-running`. An empty plan returns `degraded` if the record says degraded, else `complete`, writing nothing. A non-empty plan SHALL stamp the record `running` with the new fingerprint (degradation cleared) and persist it before the first step executes.

**REQ-STARTUP-075** — Step execution: previously-completed steps are skipped (counted as done) except detect and record, which always rerun. Cancellation is honored only at step boundaries — cancel never interrupts a running step; when observed, the record is saved with outcome `cancelled` and a cancellation event (`Setup cancelled`) is emitted. Each executed step emits a progress event (label, completed count, total) before work and a completion event (detail, counts, elapsed) after; per-step wall time is measured with a monotonic clock and persisted so timings survive restarts.

**REQ-STARTUP-076** — Step behaviors and detail strings: detect → `Checked system and managed tool paths`; satisfied → records the probed version, detail `<tool> <version|unknown> already installed`; install → download, verify, extract, promote (REQ-STARTUP-082..086), record the managed paths and provisioned version, immediately re-activate the managed environment so later steps see the tool, detail `Installed <path>` (comma-joined for multiple); a platform with no pinned artifact fails the step with `<tool> <version> has no pinned <platform-key> artifact in this release`; warm-up → emits the rendered command line as a detail event, runs with a 180-second timeout, emits combined trimmed output as detail, non-zero exit fails with `command <line> exited <code>: <detail or 'no detail output'>`, an OS/launch error fails with `command <line> failed: <error>`, success detail `Cached <package>`; record → re-probes every manifest tool, saves the satisfied versions, detail `Saved verified machine-tool versions`.

**REQ-STARTUP-077** — Failure semantics: the first failing step stops the run. The record marks that step failed with elapsed time and the error detail; the step's capabilities are unioned (sorted) into the degraded-capabilities list; the outcome becomes `degraded` with accepted-degradation set only when the caller asked to continue on failure; the completion timestamp is stamped; a failure event `{label} failed` is emitted with counts, elapsed, and detail. The application SHALL still open; only the features needing the missing tool warn (per-feature degradation, never a blocked app).

**REQ-STARTUP-078** — Success end state: outcome `complete`, completion timestamp stamped, degradation cleared, and a final completion event with message `Machine setup complete` at full progress.

**REQ-STARTUP-079** — Resume: after a cancellation, a subsequent run SHALL execute only the remaining steps (a warm-up command runs exactly once across cancel + resume); a further run with matching state is a full no-op fast path. An offline warm-up failure under continue-on-failure SHALL persist accepted degradation, the precise degraded capability list, and the OS error text in the step detail.

**REQ-STARTUP-080** — Accepting degradation (the dialog's "Continue without tool") SHALL rewrite the record to outcome `degraded` with accepted-degradation true and a backfilled completion timestamp, so the next launch skips setup despite the failure.

**REQ-STARTUP-081** — Setup SHALL be required exactly when: a manual run is requested; no record exists; the fingerprint mismatches; the outcome is neither `complete` nor `degraded`; or the outcome is `degraded` without accepted degradation.

### Setup downloads, verification, extraction

**REQ-STARTUP-082** — Tool archive downloads SHALL require HTTPS: a non-`https://` URL is refused before any network I/O with the message `tool archives require HTTPS`.

**REQ-STARTUP-083** — TLS verification for setup downloads SHALL trust both the operating system trust store and a CA bundle shipped inside the application, so public downloads succeed even where the packaged runtime lacks the system CA path, while organisation-internal roots remain honored.

**REQ-STARTUP-084** — Tool archive downloads SHALL behave as follows. Every request SHALL carry the header `User-Agent: Rotaris-Setup/1` and SHALL use a per-connection timeout of 30 seconds. The response body SHALL be written in 1 MiB blocks to a file named `<name>.partial` beside the cache destination, and bytes already written SHALL survive termination of the process. When a `<name>.partial` file already exists, the request SHALL carry a `Range` header asking for the bytes from that file's current length onward; the existing bytes SHALL be kept and appended to only when the server answers HTTP 206, and on any other success status the file SHALL be rewritten from the first byte of the response. When the transfer completes, the file's SHA-256 SHALL be compared against the digest pinned in the manifest for that platform key, and only on a match SHALL the file be renamed to its final cache name — so a file present under the final name has always been verified against its pin. A `<name>.partial` file SHALL stay eligible for resumption indefinitely — no age, launch count or manifest change expires it — because eligibility costs nothing: no partial file is ever promoted without matching its pin, so a stale or corrupt one can only cost a repeated transfer, never a wrong install. When the assembled file's digest does not match the pin, the step SHALL delete both the assembled file and the partial file and retry the transfer exactly once from the first byte, with no `Range` header; only if that second, wholly fresh transfer also mismatches SHALL the step fail. A digest mismatch that fails the step SHALL fail it with `SHA-256 mismatch: expected <expected>, actual <actual>`, naming both digests; a transport failure SHALL fail it with `download failed for <url>: <error>`. The cache destination SHALL be `setup/cache/downloads/<url filename>`.

**REQ-STARTUP-085** — Archive extraction SHALL be traversal-safe and link-free: entry names are normalized; absolute paths or `..` components are refused with `archive entry escapes the staging directory: <name>`; symlinks and hard links are refused; only `zip`, `tar.gz`, and `tar.xz` archives are accepted. Executable permissions are preserved (zip) or applied (tar), and the declared expected executables are forced executable on POSIX.

**REQ-STARTUP-086** — Promotion SHALL be atomic: extraction happens into a hidden sibling staging directory; all expected executables must exist in staging or the step fails with `archive is missing expected executables: <names>`; only then is the whole tree renamed into the final managed location. A pre-existing destination with intact executables is reused; an incomplete one fails with `managed tool directory is incomplete: <path>`. Staging is always cleaned up; after a cancelled or failed run, a managed tool directory is either absent or complete — never partially extracted.

**REQ-STARTUP-087** — Setup SHALL never require elevation or mutate the machine: everything it writes lives under per-user configuration/data directories; the OS PATH is never persistently modified; nothing is registered with an OS package database; no administrator/sudo prompt is ever raised.

### Managed tool environment

**REQ-STARTUP-088** — Activating the managed environment SHALL mutate only the current process environment: every existing managed binary directory (ordered by tool) is prepended to PATH (on Windows, both `Path` and `PATH`), and the package-runner caches are redirected to app-owned directories via `UV_CACHE_DIR` and `npm_config_cache` (created on demand). Managed directories take precedence over system tools of the same name for the app's own child processes.

**REQ-STARTUP-089** — Activation SHALL occur at every point where the process (or its children) might launch tools: desktop startup before window construction, the start of every setup run, immediately after each successful install step, on a lock collision, and when degradation is accepted — so probes, warm-ups, terminal tools, and MCP servers all observe provisioned tools.

### Setup dialog (desktop)

**REQ-STARTUP-090** — One dialog SHALL serve both first launch and repair: modal, window title and accessible name `Rotaris machine setup`, initial size 760×560, page title `Preparing Rotaris` on first launch or `Repair machine tools` for a manual repair, and explanation text `Rotaris is checking Git, Node, ripgrep, and the package caches used by MCP servers.`

**REQ-STARTUP-091** — Dialog contents and accessible names: a status line (`Machine setup current action`, initially `Ready to start`); a 0–100 progress bar (`Machine setup progress`); a step list (`Machine setup steps`); a `Show details` disclosure button (`Show machine setup details`) toggling a read-only, copyable details pane (`Machine setup details`, hidden by default; button text flips to `Hide details`); and an action row with `Cancel`, a hidden-until-relevant `Retry`, `Continue without tool` (accessible description `Open Rotaris with a warning for capabilities that still need this tool`), `Resume setup`, and `Open Rotaris`. The disclosure SHALL be keyboard reachable (focus + Enter opens the details).

**REQ-STARTUP-092** — Setup runs on a background worker; interactive runs SHALL NOT auto-accept degradation. Event rendering: progress → status text updates and a list row `▶ {message}`; completion → row `✓ {message} ({elapsed}s)` with the per-step elapsed time shown to one decimal place; failure → status update and row `Failed — {message}`; any event carrying a total sets the bar to the completed share of the total as a whole percent (fractions discarded), with the text `{completed}/{total} — {percent}%`. Detail messages stream live into the details pane.

**REQ-STARTUP-093** — Terminal-outcome buttons appear only after the worker has fully stopped: `complete` → progress 100, status `Machine setup complete`, and the dialog auto-accepts into the app with no extra click; `already-running` → status `Machine setup is already running in another Rotaris process` with `Open Rotaris`; `cancelled` → status `Setup paused. Completed steps are saved.` with `Resume setup` and `Open Rotaris` (resume restarts the worker and completed steps are skipped); `degraded` or a worker exception → status `A machine tool still needs attention` (or `Machine setup failed` for an exception, whose text is appended to the details) with `Retry` and `Continue without tool`.

**REQ-STARTUP-094** — The Cancel button SHALL set the cancellation flag, disable itself, and show status `Cancelling after the current step…`. Rejecting the dialog (Esc or the close box) while setup runs SHALL convert to a cancel rather than closing.

**REQ-STARTUP-095** — Choosing `Continue without tool` SHALL record the accepted degradation as in REQ-STARTUP-080, make the managed tool directories available to this process (REQ-STARTUP-088), and close the dialog, after which the main window SHALL open and every feature whose capabilities are absent from the record's degraded-capabilities list (REQ-STARTUP-077) SHALL behave exactly as it does after a `complete` setup. The technical detail of the failure, including any operating-system error text, SHALL have been readable in the details pane before the dialog closed. Afterwards the settings machine-setup card SHALL read `Rotaris is open with reduced machine-tool capabilities.` (REQ-STARTUP-102) and the next launch SHALL show no setup dialog (REQ-STARTUP-081).

**REQ-STARTUP-096** — The desktop setup entry point SHALL first activate the managed environment and return `complete` immediately — showing no dialog at all — when setup is not required (a second launch shows nothing). When it does run, warm-ups SHALL be derived from the current workspace's merged MCP configuration so they match what that workspace actually launches.

**REQ-STARTUP-097** — Bundled-runtime detection SHALL be: the process is a standalone (frozen) build, OR the environment variable `ROTARIS_BUNDLED` equals `1` (a test/ops override). Only bundled runtimes schedule the first-launch desktop setup.

**REQ-STARTUP-153** — Machine setup SHALL be re-runnable after first launch from the desktop and from nowhere else. The Project settings category (REQ-CONFIG-269) SHALL carry, alongside the status card of REQ-STARTUP-101, a setup surface listing every step of the recorded plan in the order of REQ-STARTUP-067, each row carrying that step's label and its recorded status, elapsed time and detail text from the durable record (REQ-STARTUP-071, REQ-NOTIFY-265). Two runs SHALL be offered. (a) The whole pass, through the `Repair machine tools` action of REQ-STARTUP-101, which is the manual full re-plan of REQ-STARTUP-103: degradation is not auto-accepted, and the dialog of REQ-STARTUP-090 carries the run. (b) A single step, offered on its own row: activating it SHALL run exactly that step against the current workspace, SHALL never run any other step, and SHALL never re-run a step whose recorded status is already complete — a completed row offers no run at all rather than offering one that silently does nothing. A single-step run SHALL take the lock of REQ-STARTUP-072 and SHALL be refused, with the message of REQ-STARTUP-073, while another process holds it; it SHALL report the tool, the command it ran, the exit status that command returned and the reason it failed within that same surface, publishing no notice (REQ-NOTIFY-236, REQ-NOTIFY-265); and on completion it SHALL write the step's status, elapsed time and detail back into `setup/state.json` and recompute the degraded-capability list and the outcome from the recorded step states exactly as a full pass does (REQ-STARTUP-071, REQ-STARTUP-077). The surface SHALL refresh from the record after any run so it never shows a state the record contradicts. Where no record exists, the surface SHALL state that machine setup has not run and SHALL offer only the whole pass.

### Update check: eligibility, endpoint, policy

**REQ-STARTUP-105** — The update check SHALL contact exactly one fixed HTTPS endpoint — the latest-release API of the product's public GitHub release repository (`https://api.github.com/repos/<owner>/<repo>/releases/latest`) — with a request timeout of 10.0 seconds and the request header `Accept: application/vnd.github+json`. Release-asset downloads SHALL follow HTTP redirects (asset URLs answer with a 302 to a storage host).

**REQ-STARTUP-106** — The update path SHALL be selected by installation flavour rather than by operating system; the classification SHALL be stable across launches of the same installation and SHALL take no user input. Any build that is not running from one of the released standalone artifacts of REQ-STARTUP-031 — a build started from an installed Python environment or from a source checkout among them — SHALL be classified not updatable: no check is performed at all, and the process SHALL issue no request to the endpoint of REQ-STARTUP-105 and none to any release-asset URL. An artifact running as an AppImage SHALL be identified from the `APPIMAGE` environment variable published by the AppImage runtime, and this test SHALL be applied before any other flavour test; the update target is the AppImage file named by that variable. A build running from inside a macOS `.app` bundle SHALL have the bundle directory as its target, never the executable inside it. On Windows the single-file portable flavour and an installed directory tree SHALL be classified differently in every case, the portable target being the running executable file and the installed target being the install directory. The discriminator SHALL be the installer's own record: the build is classified installed if and only if the per-user registry value `InstallDir` exists under `HKCU\Software\Rotaris` (REQ-STARTUP-016) and the running executable resolves to a path inside the directory that value names; every other Windows standalone build is classified portable. This signal is chosen because only the installer writes it and uninstallation removes it (REQ-STARTUP-019), so the classification follows the installation that actually exists rather than the shape of the files. Where the classification is wrong because a user copied an installed tree elsewhere, the consequence is bounded and safe: the copy is treated as portable, and the portable strategy of REQ-STARTUP-125 replaces it with a self-contained executable that runs from any location.

**REQ-STARTUP-107** — An update SHALL be offered only when all three hold: a latest release exists, its version is strictly newer than the running version, and the release contains the asset for this installation flavour on this platform (installer flavour → the setup artifact; portable → portable; app bundle → disk image; AppImage → AppImage). A release lacking this platform's file offers nothing — a real answer, not an error (never a dead download button).

**REQ-STARTUP-108** — When searching the release feed for the artifact of a given product version, platform key, and artifact kind, an asset SHALL count as a match only when its published `name` equals, character for character, the filename REQ-STARTUP-031 fixes for that combination — same letter case, same separators, same literal version text. Abbreviated, re-cased, re-separated, prefix, suffix, and substring matches SHALL all be rejected. A release offering no asset that matches exactly SHALL be treated as carrying no artifact for this platform, and no update SHALL be offered from it (REQ-STARTUP-107).

**REQ-STARTUP-109** — Version comparison SHALL parse both sides through the release-tag grammar and order them strictly-newer only. The order SHALL be the numeric tuple first, and, where two versions share a tuple, the prerelease rank second: a prerelease of a tuple sorts before the plain release of that same tuple, and among prereleases of one tuple the ranking is `a` before `b` before `rc`, ties within a kind broken by the ascending numeric suffix. A running prerelease is therefore offered the stable release of its own numeric tuple — `1.2.3rc1` is offered `v1.2.3` — which is the intended policy and the only one that lets a prerelease reach the release that supersedes it, since the feed filter stated below would otherwise leave it stranded until the next patch. Newer → offer; equal or older → none; a candidate tag outside the grammar (e.g. `v0.102.0-rc1`, `v0.102`) → none; a running version that does not parse (e.g. `dev`) → none, because the comparison cannot be decided. Draft and prerelease payloads SHALL be filtered out of the feed before comparison, so an installed app is only ever offered stable releases while prerelease artifacts stay available for manual download from the release page.

**REQ-STARTUP-110** — Every check failure SHALL be invisible to the user — the app starts silently with only an internal log line: unreachable network, any non-200 status (including 404 with no release yet and 403 rate-limit exhaustion), timeout, unreadable or truncated body, structurally invalid payloads (non-object, draft or prerelease flags, missing or malformed tag). There SHALL be no user-facing failure path for the check.

**REQ-STARTUP-111** — On a supported standalone desktop build the launch-time update check SHALL NOT be disableable by any user-reachable means. The acceptance criterion is positive and rests on three closed enumerations, which together are every configuration surface a user of this product has: the desktop preference store of REQ-SHELL-006 and REQ-CONFIG-463, whose keys are enumerated by REQ-STARTUP-146 for this domain and by REQ-CONFIG-405 and REQ-SHELL-163 elsewhere; the layered YAML configuration surface; and the environment variables of REQ-STARTUP-147. A release SHALL be accepted only when, for each of those three enumerations, no entry names update checking, an update endpoint, a release source, or an update channel — a property checkable by reading the enumerations themselves, each of which is maintained by the domain that owns it, this domain owning only REQ-STARTUP-146 and REQ-STARTUP-147. There is no fourth enumeration to maintain, because the product has no command-line arguments (REQ-STARTUP-039) and no text-mode interface. The interface SHALL likewise expose no control, toggle, menu item, or settings entry that turns the check off. Consequently, for every combination of preference values, configuration values, and environment variables a user can produce, such a build SHALL still perform the launch-time check of REQ-STARTUP-114 against the endpoint of REQ-STARTUP-105 and SHALL contact no other release source.

**REQ-STARTUP-112** — The banner summary SHALL be derived from the release body: if a `## Changes` heading exists (case-insensitive), the search starts after it; blank lines, headings, table rows, blockquotes, and code fences are skipped; a leading `- ` or `* ` bullet marker is stripped; the first substantive line is returned, truncated to 160 characters (159 + `…` when longer). An empty or scaffolding-only body yields an empty summary.

**REQ-STARTUP-113** — Checksum-manifest parsing SHALL be the exact inverse of the writer format (two-space split, trimmed name and hash, hash lowercased); malformed lines are skipped, never guessed at; the parser and writer formats SHALL round-trip.

### Update notification UI

**REQ-STARTUP-114** — The desktop update check SHALL run once per window activation, only after the window is visible; it does nothing (and returns without asking) for a build classified not updatable by REQ-STARTUP-106 and for demo windows on every runtime (REQ-STARTUP-057). Only one update operation (check or install) SHALL be in flight at a time; a second request while one runs is refused.

**REQ-STARTUP-115** — Before the network round trip, launch-time cleanup SHALL delete a leftover portable backup executable (`<name>.old`) from a previous update; for every other flavour this cleanup never deletes anything. A deletion failure (e.g. the OS still holds the file) is tolerated silently and retried on a later launch.

**REQ-STARTUP-116** — When the offered version equals the persisted dismissed version (settings key `updates/dismissedVersion`), the offer SHALL be silently ignored. Otherwise a persistent, non-modal, non-blocking informational notice appears on the shared in-app banner: title `Rotaris {version} is available`, message = the release summary or the fallback `Open the release notes for the full changelog.`, with action `Update now`. **REQ-STARTUP-117** — Dismissing the update notice SHALL record only that version string (not a general preference): the check still runs next launch; the same version stays silent; any newer version notifies again. Dismissing an unrelated notice SHALL never record a dismissed update version.

**REQ-STARTUP-118** — While an update download runs, a non-persistent notice titled `Downloading Rotaris {version}` SHALL show the message `{measured} — verifying against the published checksum when it finishes.` Progress SHALL be reported no more often than once per 1 MiB received (REQ-STARTUP-124). When the release feed states a non-zero size for the asset, `{measured}` SHALL be the received share of that size as a whole-number percentage with the fractional part discarded (the same convention as REQ-STARTUP-092), and SHALL be repainted only when that whole percent changes. When the claimed size is 0, `{measured}` SHALL instead be the whole number of MiB received, rendered as `{N} MB`.

**REQ-STARTUP-119** — Applied outcomes: an in-place replacement → persistent success notice titled `Update installed` with the strategy's message and a `Restart now` action; a hand-off → persistent success notice titled `Finish the update` with the message and no action; when the hand-off requires quitting (Windows installer), the window SHALL auto-close after a 1200 ms single delay.

**REQ-STARTUP-120** — Install failure SHALL raise a persistent error notice titled `Update not installed`, message `Rotaris is unchanged. You can try again or download the release manually.`, with the technical reason (e.g. the checksum-mismatch sentence) available as details and a `Try again` action that re-runs the install with the held offer. The installed bytes SHALL be untouched.

**REQ-STARTUP-121** — A `Restart now` action SHALL be offered on the `Update installed` notice and on no other notice, so it is unreachable after a hand-off outcome (REQ-STARTUP-119). Choosing it SHALL leave the user with the updated installation running, in this order: a fresh instance of the updated installation is started first, the current window closes only after that instance has started, and the started instance keeps running once the current process has exited. When the instance cannot be started, nothing SHALL close — the current window SHALL stay open and accept input as before — and the failure SHALL surface through the `Update not installed` notice of REQ-STARTUP-120.

### Update download, verification, and install strategies

**REQ-STARTUP-122** — The install sequence SHALL be strictly: fetch and parse the `SHA256SUMS.txt` published with that release → stream the asset into a fresh temporary staging directory (name prefixed `rotaris-update-`) → verify → apply — never proceeding past a failure, and reporting every failure as a single sentence.

**REQ-STARTUP-123** — Verification SHALL enforce: a release publishing no checksum manifest is refused with `release <version> publishes no checksum file; refusing to install an unverifiable download`; a failed manifest fetch fails with `could not read the checksum file: HTTP <status>`; a downloaded file for which the manifest lists no hash is removed, reporting `no published hash for <name>; the download was discarded`; a hash mismatch deletes the file with `<name> does not match the published hash (expected <e>, got <a>); the download was discarded and nothing was installed`; comparison is case-insensitive. This check detects a corrupted or incomplete transfer only; it does not establish who produced the artifact, since artifacts are unsigned and the manifest is fetched over the same connection as the download.

**REQ-STARTUP-124** — Download staging SHALL stream in 1 MiB chunks (matching the hashing granularity), reporting `(bytes_so_far, claimed_total)` with the total possibly 0; a write failure deletes the partial file and fails with `could not write the download to <path>: <error>`.

**REQ-STARTUP-125** — The apply step SHALL be selected by installation flavour (REQ-STARTUP-106), not by operating system, and SHALL produce these observable results. **AppImage** → the verified file SHALL first be placed next to the target as a hidden sibling named `.{name}.update` on the same filesystem as the target, then moved onto the AppImage path and left with mode `0755`; the replacement SHALL succeed while the application that is being replaced is still running; outcome replaced, message `The update is installed. Restart Rotaris to run it.`; on failure the sibling file SHALL be removed and the step SHALL report `could not replace <target>: <error>`; whether it succeeded or failed, no `.{name}.update` file and no staging directory SHALL remain. **Windows portable** → the verified file SHALL be placed beside the target, any previous backup SHALL be deleted, the running executable SHALL be renamed to `<name>.old`, and the new file SHALL then be moved into the target path; if that final move fails, the backup SHALL be renamed back to the target path before the step reports `could not install the update at <target>: <error>`, so the executable present after a failure is the original one; the `<name>.old` file SHALL remain until a later launch removes it (REQ-STARTUP-115); outcome replaced, with the same message as the AppImage case. **Windows installer** → the verified setup executable SHALL be started as a process that survives the application exiting, and the application SHALL make no edit of its own to the installed tree; outcome handed-off with quit required, message `Rotaris will close so the installer can replace it.`; if the process cannot be started the step SHALL report `could not start the installer at <path>: <error>`. **macOS** → the verified disk image SHALL be mounted and its mounted volume SHALL be opened in the platform's file browser so the drag-to-install of REQ-STARTUP-022 can be repeated; the installed application bundle SHALL be left byte-for-byte unchanged and SHALL never be replaced automatically; outcome handed-off, message `The verified disk image is open. Drag Rotaris to Applications, then reopen it.` **No released-artifact target** → the step SHALL fail with `this Rotaris was not installed from a released artifact` and change nothing on disk.

**REQ-STARTUP-126** — Invariant: not one file of the existing installation is moved or modified before the replacement has been fetched in its entirety and verified; should any stage fail, what is installed remains byte-for-byte what it was before the attempt.

**REQ-STARTUP-127** — With a hand-off strategy the ordering is reversed — the running application quits or yields to another installer before the replacement is actually in place — and the message shown SHALL describe that hand-off rather than telling the user to restart.

**REQ-STARTUP-128** — Exactly one version, the desktop application's, is compared against the feed, and exactly one artifact, the desktop one, is downloaded; because the product releases a single version (REQ-STARTUP-001), the engine version can never disagree with it.

### Opt-in diagnostics

**REQ-STARTUP-129** — Diagnostics activation SHALL have exactly one source: the desktop preference store (REQ-SHELL-006, REQ-CONFIG-463). The mode SHALL be the stored value of `diagnostics/level`, one of `off`, `light` or `deep`, defaulting to `off` where nothing has been stored or where the stored value is not one of the three; the output base SHALL be the stored value of `diagnostics/outputDir`, unset meaning the default location of REQ-STARTUP-131. Both are set through the Settings controls of REQ-SHELL-163, which offer only those three levels and take the folder from the platform folder chooser — so an invalid selection is unreachable, and this document defines no diagnostics usage error, message or refusal. A change to either choice SHALL take effect for windows built afterwards and SHALL NOT alter a capture already running in an open window (REQ-SHELL-163). No environment variable and no other surface SHALL set either value.

**REQ-STARTUP-130** — When diagnostics is off, no diagnostics files, timers, or instrumentation of any kind SHALL exist — zero work, zero disk writes.

**REQ-STARTUP-131** — Each window with diagnostics enabled SHALL create its own run directory before writing any diagnostics data. Its path SHALL be `<base>/<timestamp>-<pid>/`, where `<base>` is the output base resolved in REQ-STARTUP-129 when one was supplied and otherwise `<workspace>/.rotaris/diagnostics/rotaris`; `<timestamp>` is the window's start time in UTC formatted `yyyymmddTHHMMSSZ`; and `<pid>` is the decimal process id. Creation SHALL be exclusive: a directory of that name that already exists SHALL never be written into, reused, emptied, or overwritten. When the name is already taken, the window SHALL take the first free name formed by appending `-2`, `-3`, … to it, trying each in ascending order and creating it exclusively, until one succeeds — the same deterministic suffixing discipline REQ-GIT-010 uses for branch names. Diagnostics SHALL never silently disable itself for this reason and SHALL never prevent the window from opening; only where no name at all can be created (the base directory itself being unwritable) SHALL the window open with diagnostics inactive, and it SHALL then say so in the diagnostics card of REQ-SHELL-163 rather than failing. The run directory SHALL contain a `snapshots/` subdirectory, created before the first snapshot is written.

**REQ-STARTUP-132** — Written artifacts SHALL be: `manifest.json` (schema version 3; app identity, creation time, platform triple, the full effective configuration including intervals and limits, and a self-checksum equal to the SHA-256 of the manifest's canonical JSON without the checksum field); rotating `metrics-NN.jsonl` and `spans-NN.jsonl` streams; `snapshots/NNNN-<sanitized-reason>.json`; and, at close, `summary.json` plus a human-readable `summary.md`.

**REQ-STARTUP-133** — The following bounds and cadences SHALL hold, and each SHALL also appear in the effective configuration recorded in `manifest.json` (REQ-STARTUP-132) so that every value is readable from the run directory itself. Each JSON-lines stream SHALL occupy at most 4 segment files of at most 8 MiB each; once the fourth segment is full, writing SHALL continue by replacing the oldest segment, so no stream ever exceeds 32 MiB however long the run lasts. Snapshot files SHALL share a total budget of 16 MiB; once it is exhausted, further snapshot writes SHALL be refused without raising an error to the user. Run-wide statistics SHALL be computed from at most 4096 metric samples and at most 1024 span samples, and each cap SHALL be a ring of the most recent samples: once the cap is reached, each new sample SHALL displace the oldest retained one, so the statistics describe the most recent window of the run. This is the reading the rest of the document already assumes — the growth and lag figures are used to judge a session that has been running for a while — and nothing about the run's beginning is lost by it, because `summary.json` reports resident memory at start and at peak from values carried forward independently of the ring (REQ-STARTUP-137). At most 128 distinct span names SHALL be reported individually and every further name SHALL be aggregated under the literal name `__other__`. A heartbeat SHALL run every 250 ms and reported event-loop lag SHALL be the measured interval between consecutive heartbeats minus that 250 ms. Metric records SHALL be produced every 1000 ms. In deep mode an allocation capture SHALL be attempted every 300000 ms, each tracing for 2.0 s, with a slow threshold of 1000 ms, at most 20 sites recorded per capture and at most 10 carried into the summary.

**REQ-STARTUP-134** — Every metric record (one per 1000 ms, REQ-STARTUP-133) SHALL carry at least: process resident and virtual memory; process CPU percentage; the native thread count together with the thread names; the interpreter-level thread count together with its names; the process's OS handle or file-descriptor count; the UI threadpool's active and maximum worker counts; live widget and object counts; measured event-loop lag in milliseconds; one per-view entry for each of the seven primary views of REQ-SHELL-023, keyed by that view's lower-cased name and carrying exactly whether the view is currently visible, the number of live widgets it owns, and the number of items in its principal collection; and, for session stores, **counts only** — the number of transcript entries, agents, todos, artifacts, and cache entries. No diagnostics file SHALL contain session content of any kind: no transcript or prompt text, no model or tool output, no file contents, no credentials. Stack frames written into snapshots SHALL identify source files by base name only and SHALL never contain a directory path. The record's field names and JSON layout are governed by REQ-STARTUP-157.

**REQ-STARTUP-135** — Threshold triggers SHALL fire with a per-reason 60-second cooldown: event-loop lag over 1000 ms → a thread snapshot (reason `event-loop-lag`); resident-memory growth of at least 256 MiB over baseline → a snapshot plus an allocation-window request with the baseline rebased (reason `rss-growth`); native-thread growth of at least 8 → a snapshot (reason `thread-growth`).

**REQ-STARTUP-136** — Deep mode SHALL never leave allocation tracing running continuously: allocation evidence SHALL be gathered only inside bounded windows of the length fixed in REQ-STARTUP-133. At most one capture SHALL be in progress at a time: a capture requested while one is running SHALL start no second capture and SHALL add no second entry to the capture counts reported in `summary.json` (REQ-STARTUP-137). When allocation tracing is already owned by something outside the application, the capture SHALL be skipped, recorded with status `skipped`, and the external tracing SHALL be left running and unmodified. After any capture that exceeds the slow threshold of REQ-STARTUP-133 or ends in error, no further automatic capture SHALL be scheduled for the remainder of the run. Closing a window SHALL stop only tracing that the application itself started, SHALL NOT take an allocation snapshot, and SHALL take a thread snapshot instead. Any source path recorded for an allocation site SHALL be reduced to a workspace-relative path or to a bare file name.

**REQ-STARTUP-137** — `summary.json` (schema version 3) SHALL report: the number of metric samples the run produced; resident memory at start, at peak, at end, the end-minus-start delta, and a growth rate in bytes per second fitted over the run's samples; event-loop lag p50, p95 and maximum, together with a boolean flag marking those percentiles as approximate when too few samples were collected; for each reported span name its total count, its failed count, and its p50, p95 and maximum durations; and a diagnostics block containing the degradation reason where one applies, an incomplete flag (REQ-STARTUP-139), the number of allocation captures in each of the statuses `complete`, `slow`, `skipped`, `cancelled` and `error`, the ranked memory-growth sites — each carrying source file, line, sampled retained bytes, sampled retained count, the number of windows in which it appeared and its largest single-window byte total — and the total bytes written as snapshots. `summary.md` SHALL be a human-readable digest of the same run, beginning with the heading `# Rotaris diagnostics summary`, containing a resident-memory line and a section headed `## Top sampled memory-growth sites`. Three derivations are fixed. The growth rate SHALL be the slope of an ordinary least-squares straight-line fit of retained resident-memory samples in bytes against their elapsed time in seconds; with fewer than two retained samples the rate SHALL be reported as 0 and the run flagged as having too few samples. Event-loop-lag percentiles SHALL be flagged approximate whenever fewer than 100 lag samples were retained. Memory-growth sites SHALL be ranked by sampled retained bytes descending, ties broken by source file name and then by line number, both ascending, so the ranking is total and two runs over the same data rank identically. Resident memory at start and at peak SHALL be carried forward across the whole run rather than read from the retained sample ring (REQ-STARTUP-133), and the summary SHALL state whether either cap of REQ-STARTUP-133 was reached during the run.

**REQ-STARTUP-138** — Reading the JSON-lines streams SHALL tolerate a crash-truncated final line, so a crashed session's trace remains readable.

**REQ-STARTUP-139** — The diagnostics lifecycle SHALL be bound to its window: window close stops timers, writes the final snapshot and summaries, and joins any allocation worker with a 1-second cap, marking the capture incomplete when it overruns.

**REQ-STARTUP-140** — When diagnostics is enabled in either mode (`light` or `deep`), the span stream of a run SHALL contain at least one record whose span name is exactly `config.load`, covering the loading of configuration during startup. Every span record SHALL carry the span name, the elapsed wall time in milliseconds, the consumed CPU time in milliseconds, and a boolean flag stating whether the spanned work failed; the field names and JSON layout carrying those values are governed by REQ-STARTUP-157.

**REQ-STARTUP-157** — The diagnostics files are a private format with exactly one consumer: this product's own diagnostics surfaces (REQ-NOTIFY-267). No other program is entitled to read them, no compatibility with any other implementation's diagnostics files is required, and the field names and nesting of `manifest.json`, the metric and span streams, the snapshots and `summary.json` are therefore chosen by the implementation rather than fixed here. What is fixed is that the files are self-describing and internally consistent: each carries the schema version this document states for it (3 for `manifest.json` and `summary.json`, REQ-STARTUP-132 and REQ-STARTUP-137); the names and nesting SHALL be stable for the life of a schema version, so two runs of one build are always readable by the same reader and a changed layout requires a new schema version; every value this document requires SHALL be present in every record that must carry it; and the units SHALL be exactly these, whatever the field is called — a duration is a JSON number of milliseconds, a quantity of memory or of written bytes is an integer number of bytes, a rate is bytes per second, a percentage is a whole number, and a timestamp is an ISO-8601 UTC string. The effective configuration recorded in `manifest.json` (REQ-STARTUP-133) SHALL make every bound and cadence in force readable from the run directory itself, so a run can be interpreted without the build that produced it.

### Third-party notices

**REQ-STARTUP-141** — A `THIRD-PARTY-LICENSES.txt` file SHALL be included inside every standalone artifact, and the in-app About & Legal surface SHALL open the same bundled file offline.

**REQ-STARTUP-142** — `THIRD-PARTY-LICENSES.txt` SHALL contain one entry for every dependency present in the shipped artifact, each entry naming the component, its version, its license identifier, and its full license text. Dependencies used only for development or CI SHALL NOT appear, and neither of the product's own two packages (REQ-STARTUP-001) SHALL appear. The file SHALL further contain the license texts of the bundled fonts JetBrains Mono, Manrope and Space Grotesk (OFL 1.1) and of the Phosphor Icons set (MIT). It SHALL contain a section titled `Tools provisioned after installation`, generated from the setup manifest of that same build, listing for Git and for ripgrep the name, provisioned version, source URL and license identifier the manifest pins (REQ-STARTUP-058), and stating that those tools are downloaded after installation and are not contained in the artifact. The file header SHALL state the recipient's right to modify and relink components licensed under the LGPL and SHALL give a contact route by which a recipient can request the corresponding sources. That route SHALL be a single address, reachable without registering for or holding an account with any service, monitored by the maintainers, and present as a literal string in the file rather than as a reference to a page that must be visited to find it. The address is a release-time input to the notices generator, not a constant of this specification: a build whose header carries no address, or an address that is only a placeholder, SHALL fail the validation of REQ-STARTUP-143.

**REQ-STARTUP-143** — Notices validation SHALL run before freezing on each platform (REQ-STARTUP-037) and SHALL fail that platform's release job, exiting 1 as a handled error per REQ-STARTUP-149, when any of the following holds: a bundled asset's license file is missing or empty; a dependency in the shipped closure declares no license identifier; a dependency carries no license text and is not covered by the documented, dated maintainer-review table of reviewed exceptions; the setup manifest cannot be read or parsed; or the notices header carries no LGPL corresponding-sources address (REQ-STARTUP-142). The failure message SHALL name the offending component or path. The maintainer-review table SHALL be a version-controlled file in the product repository, held beside the notices generator that reads it, so that adding an exception is a reviewed change and the table can never disagree with the build it covers. Each entry SHALL carry: the component name; the version or version range it covers; the license identifier claimed for it; why no license text is obtainable; the reviewer; the date of review; and an expiry date. An entry SHALL cover a dependency only when the dependency's version falls inside the entry's range and the expiry date has not passed; an expired entry, and an entry whose range excludes the shipped version, SHALL be treated exactly as no entry at all, so the validation fails and the exception is reviewed again. The expiry SHALL be at most 365 days after the review date.

### Website download-page disclosure (upstream requirement in draft)

**REQ-STARTUP-144** — The official download page SHALL carry a network disclosure that is present in the page as delivered and readable without dismissing, accepting, or hovering anything: it SHALL NOT be presented as a modal, an interstitial, a checkbox, or a control revealed only on hover, and every control it does carry SHALL be reachable and operable with the keyboard alone and by touch. Its content SHALL state that first-launch tool provisioning and cache warming may contact GitHub, the Python package-runner host, and package registries when the user has supplied the corresponding runners; that a supported standalone desktop build asks GitHub for a newer release once each time it starts (REQ-STARTUP-105); and that these requests can expose ordinary connection metadata such as an IP address but never carry the user's project files, prompt text, or provider credentials. It SHALL link to the Privacy Policy and SHALL be published in both German and English. It SHALL also carry the statement REQ-STARTUP-026 requires for a visitor whose platform the release publishes no artifact for. The disclosure binds the **promotion** step and not the build: a release SHALL be publishable, and its assets SHALL be downloadable from the release page, before the disclosure has been reviewed; what SHALL NOT happen is that the download page offers that release, or names its version, until confirmation has been recorded that the disclosure still matches the setup and update behavior this document specifies. The checklist item belongs to whoever performs the release — the same person the acceptance criteria of REQ-STARTUP-156 answer to — and no separate owner is created for it, since a gate with a second owner is a gate that stalls. Release bodies SHALL NOT repeat this disclosure.

### Persistence, environment, and exit codes

**REQ-STARTUP-145** — Per-user directories SHALL be the platform-conventional configuration and data directories for the application name `rotaris`; per-workspace state lives at `<workspace>/.rotaris/`. There is no legacy directory to adopt: the product SHALL read, rename, import from, or otherwise adopt no per-user or per-workspace directory belonging to any earlier or differently named product, and SHALL create its own directories on first use instead.

**REQ-STARTUP-146** — All desktop persisted-settings state SHALL live in the desktop preference store of REQ-SHELL-006 and REQ-CONFIG-463, under organization `Rotaris`, application `Rotaris` (on Windows: the registry under `HKCU\Software\Rotaris\Rotaris`), disjoint from the layered YAML configuration surface. The keys owned by this domain are `workspace/lastOpened` (remembered project folder path) and `updates/dismissedVersion` (a single version string). The diagnostics keys this domain reads, `diagnostics/level` and `diagnostics/outputDir`, live in the same store and are owned by REQ-SHELL-163.

**REQ-STARTUP-147** — Environment variables read by this domain: `APPIMAGE` (AppImage self-identity, published by the AppImage runtime), `ROTARIS_BUNDLED` (`1` forces bundled-runtime semantics — a build-and-test override that exposes no product capability and is documented nowhere a user is directed to), and the Windows command-interpreter variable (`COMSPEC`, fallback `cmd.exe`) for launching batch shims. No environment variable read by this domain selects a workspace, enables diagnostics, or affects the update check in any way (REQ-STARTUP-111, REQ-STARTUP-129). Variables written for child processes: `PATH`/`Path` (managed directories prepended), `UV_CACHE_DIR`, `npm_config_cache`.

**REQ-STARTUP-148** — On Windows, every setup child process (probe or warm-up) SHALL run with no visible console window (no window flashes during a quiet startup), and `.bat`/`.cmd` launchers SHALL be executed through the command interpreter with the pinned package arguments preserved verbatim in the child's command line.

**REQ-STARTUP-149** — Exit codes belong to the maintainer-side build and release pipeline only (REQ-STARTUP-008), which is where one program reports to another; the desktop application defines none, having no invocation a user or a script can make (REQ-STARTUP-039). Pipeline exit codes: build/release commands → 0 success, 1 handled error (with `error: …` on stderr), 2 usage error; version-guard and package-pin mismatch → 1, stopping the release (REQ-STARTUP-028); notices validation failure → 1, failing that platform's job (REQ-STARTUP-143).

### Cross-cutting invariants

**REQ-STARTUP-150** — Silence/visibility invariants: a failed update **check** is always invisible (log only); a failed update **install** is always visible (persistent error notice); a machine-setup failure is always recoverable (Retry or Continue-without-tool — the app never refuses to start because of setup) and is reported again at the point a degraded capability is used (REQ-STARTUP-154); a build not running from a released standalone artifact, and a demo window on any runtime, perform no update network traffic at all (REQ-STARTUP-057, REQ-STARTUP-106).

**REQ-STARTUP-151** — Ordering invariants: the desktop paints before setup, setup before workspace onboarding, and repository discovery waits for setup when setup is pending; the update check starts only after the window is shown; update install order download → verify → apply is monotone with failure stopping it; setup steps run in deterministic plan order with completion persisted at every step boundary; the version guard and the package-pin guard precede all release builds; release publication precedes and never depends on PyPI publication; and release publication precedes the download-page promotion the disclosure of REQ-STARTUP-144 gates.

**REQ-STARTUP-152** — The following agreements SHALL hold, each decidable from published artifacts, observed network traffic, and process output alone. The filenames a release publishes as assets, the filenames its `SHA256SUMS.txt` lists, and the filename an update client asks for on a given platform SHALL all be values of the single naming scheme of REQ-STARTUP-031 and SHALL agree, the manifest listing every published asset but itself (REQ-STARTUP-032, REQ-STARTUP-108). A launch-time update check SHALL reach the host and path of REQ-STARTUP-105 and no other host or path. A `SHA256SUMS.txt` exactly as published SHALL be consumable unmodified both by the update path and by `sha256sum -c`, with no reformatting step in between (REQ-STARTUP-032, REQ-STARTUP-113). The tool and MCP package versions a build provisions and warms SHALL be the versions pinned in the manifest that same build ships, and the same versions its `THIRD-PARTY-LICENSES.txt` reports (REQ-STARTUP-058, REQ-STARTUP-059, REQ-STARTUP-142). The executables an installation makes available SHALL be exactly the one entry point of REQ-STARTUP-002. For every combination of preference values, configuration values, and environment variables a user can produce, the release source used by the update check SHALL still be the endpoint of REQ-STARTUP-105 (REQ-STARTUP-111).

**REQ-STARTUP-155** — Startup and setup timing SHALL be bounded as follows, each bound measured on the supported baseline of REQ-STARTUP-012 and REQ-STARTUP-024. The main window SHALL be painted within 5 seconds of the application being launched, and this bound SHALL be the same for every published artifact and every bundle mode — the `onefile` Windows portable executable of REQ-STARTUP-013 is given no larger budget than the `onedir` flavours, and no per-flavour differential is specified. The fast-path decision of REQ-STARTUP-066 — establishing that the plan is empty — SHALL be reached within the 100 ms interface-responsiveness budget of REQ-SHELL-150 and SHALL delay neither the first paint nor the post-show activation of REQ-STARTUP-043. A setup pass in which every manifest tool is already satisfied (REQ-STARTUP-069) SHALL be bounded by the probe timeout it is built from and no more: its wall time SHALL NOT exceed the sum of the per-probe timeouts of REQ-STARTUP-063 over the manifest's tools, counted twice for the detect and record steps that both probe. No further timing is specified, and that is deliberate: download durations depend on the network, per-step pacing depends on the machine, and the visual rendering of the setup dialog and the update banner beyond their widget structure, text and accessibility metadata is a design matter this document does not fix. A build SHALL NOT be judged non-conformant for any of those three.

## Data & Formats

All formats below are externally observable (on disk, on the wire, or in process output).

- **Release tag grammar**: `v<major>.<minor>.<patch>` with optional `a<N>` / `b<N>` / `rc<N>` suffix. Plain versions are `stable`; suffixed are `prerelease`.
- **Release artifact names** (single authority, REQ-STARTUP-031): `Rotaris-{v}-windows-x64-setup.exe`, `Rotaris-{v}-windows-x64-portable.exe`, `Rotaris-{v}-macos-arm64.dmg`, `Rotaris-{v}-linux-x86_64.AppImage`. There is no console-archive kind.
- **Checksum manifest** `SHA256SUMS.txt`: `"<sha256hex>  <filename>\n"` per asset, two-space separator, sorted by filename, `sha256sum -c` compatible, never self-listed.
- **Release feed consumption** (GitHub latest-release JSON): fields consumed are `tag_name`, `draft`, `prerelease`, `body`, and `assets[]` entries' `name`, `browser_download_url`, and integer `size` (0 when absent). Asset downloads follow a 302 redirect to a storage host.
- **Windows installer surface**: silent flags `/S` and `/D=<dir>`; per-user registry writes under `HKCU\Software\Rotaris` (`InstallDir`) and `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Rotaris` (`DisplayName`, `DisplayVersion`, `Publisher`, `DisplayIcon`, `UninstallString`, `NoModify`, `NoRepair`); Start Menu folder `Rotaris` with `Rotaris.lnk` and `Uninstall Rotaris.lnk`.
- **Linux desktop entry**: `Type=Application`, `Name=Rotaris`, `Terminal=false`, `Categories=Development;IDE;`, Exec accepting an optional path argument, named icon.
- **Per-user setup layout** (under the platform data dir for `rotaris`): `tools/<tool>/<version>/` (managed tool trees), `setup/state.json` (durable record, schema 1 — fields in REQ-STARTUP-071, of which `outcome`, `completed_at` and `versions` are fixed names shared with REQ-CONFIG-397), `setup/setup.lock` (transient JSON `{pid, created}`), `setup/cache/{downloads,uv,npm}/`. Partial downloads appear as `<name>.partial` beside their cache destination and stay eligible for resumption indefinitely (REQ-STARTUP-084).
- **Setup manifest** (schema 1): per-tool probe command and version args, optional minimum version, provisioned version, per-platform-key artifacts (HTTPS URL, 64-hex SHA-256, layout, expected executables), license, capabilities; plus exact MCP package pins. Fingerprint = SHA-256 over canonical JSON (sorted keys, compact separators).
- **Setup outcome vocabulary**: `complete` | `degraded` | `cancelled` | `already-running` (REQ-STARTUP-074); the first three, plus `running` and empty, are also the values persisted as `outcome` in the durable record. There is no textual output contract carrying them: they are rendered in the setup dialog (REQ-STARTUP-093), the settings card (REQ-STARTUP-102) and the per-step surface (REQ-STARTUP-153).
- **Persisted settings** (desktop preference store, REQ-SHELL-006): organization/application `Rotaris`/`Rotaris`; keys owned here are `workspace/lastOpened` (string path) and `updates/dismissedVersion` (single version string); `diagnostics/level` and `diagnostics/outputDir` are read from the same store and owned by REQ-SHELL-163. Windows backend is the registry at `HKCU\Software\Rotaris\Rotaris`.
- **Diagnostics run directory**: `<base>/<UTC yyyymmddTHHMMSSZ>-<pid>/` containing `manifest.json` (schema 3, self-checksummed), `metrics-NN.jsonl` and `spans-NN.jsonl` (rotating, 8 MiB × 4 each), `snapshots/NNNN-<reason>.json` (16 MiB total budget), `summary.json` (schema 3) and `summary.md`. JSON-lines readers tolerate a truncated final line.
- **Environment variables**: read — `APPIMAGE`, `ROTARIS_BUNDLED`, `COMSPEC`; written for children — `PATH`/`Path`, `UV_CACHE_DIR`, `npm_config_cache`. No environment variable configures diagnostics or the update check (REQ-STARTUP-129, REQ-STARTUP-111).
- **Key behavioral constants**: deferred first-paint delay 650 ms; update-check timeout 10.0 s; update download/hash chunk 1 MiB; installer-hand-off auto-close 1200 ms; update-worker shutdown join 5000 ms; toast auto-hide 4200 ms; toast max width 520 px; tool probe timeout 10 s; warm-up timeout 180 s; tool download connect timeout 30 s with 1 MiB blocks; setup lock staleness 900 s; banner summary limit 160 chars; setup dialog 760×560; minimum window 1000×680; diagnostics 250 ms heartbeat / 1000 ms sampling / 1000 ms lag trigger / 60 s trigger cooldown / 256 MiB memory-growth trigger / 8-thread growth trigger / 300 s deep interval / 2.0 s tracing window / 1.0 s slow threshold / 1 s close join.
- **Diagnostics file layout**: field names and nesting are implementation-chosen and stable within a schema version; units are fixed — milliseconds for durations, bytes for memory and written volume, bytes per second for rates, whole numbers for percentages, ISO-8601 UTC for timestamps (REQ-STARTUP-157).
- **Exit codes**: pipeline only; see REQ-STARTUP-149. The application defines none.
- **Application entry**: one graphical entry point (REQ-STARTUP-002). There is no argument vocabulary, no subcommand, no flag, no standard-output contract and no text-mode interface; the one reserved token `builtin:code-intelligence` is a sentinel for a child process the product starts itself (REQ-MCP-033, REQ-STARTUP-015).
