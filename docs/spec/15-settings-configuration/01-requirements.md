# Settings and Configuration — Configuration sources, scopes and locations

Part 1 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-001 – REQ-CONFIG-057.

## Requirements

### Configuration sources, scopes and locations

- **REQ-CONFIG-001** — Configuration is read from exactly two directory scopes: a per-user **global** scope and a per-workspace scope at `<workspace root>/.rotaris/`. The global scope resolves per platform to the conventional user configuration directory for the application name `rotaris` — on Linux `~/.config/rotaris/`, on macOS `~/Library/Application Support/rotaris/`, on Windows `%LOCALAPPDATA%\rotaris\rotaris\`. Which per-user location that is, on a platform offering more than one, is REQ-STARTUP-145's: the location local to this machine and not replicated to another machine or to another copy of the user's profile. The spellings above are that location on each platform rather than a second definition of it, and this domain states no rule of its own about it.
- **REQ-CONFIG-477** — Configuration MUST be held as files, and MUST NOT be moved into a store that only this application can read. This is a stated **boundary**, not an artifact of how the product was first built: it is recorded here so that moving configuration into an application-owned store is a change someone has to argue for against these grounds, rather than an optimisation that can be made quietly while every requirement of this document still appears to be satisfied. Four grounds reach the conclusion and each is independently sufficient.
  1. **A file carries what this release does not understand; a record with a fixed field set cannot.** An unrecognized top-level key is reported as a warning, contributes nothing to the merge, and is nevertheless still in the file afterwards, so a document authored against a later release loads, is edited, and is written back by an earlier one without losing the key (REQ-CONFIG-040, REQ-CONFIG-233); a key outside the layered model may additionally be read by a separate parse of the same file, `rotaris.delegation_strategy` being the shipped case. Every writer of `agents.yaml` is required not to discard content it could not interpret (REQ-CONFIG-442, REQ-CONFIG-458), and the file is what makes that possible. `requirements:` is the deliberate exception in the other direction — an unrecognized key there is a hard load failure, though a key this specification itself withdrew is reported and ignored instead (REQ-CONFIG-183) — and it is an exception about a *configuration block*, not a licence to store configuration the way the product stores its own records. That the withdrawn key survives in the file after being reported, and is removed only when its owner decides to remove it, is this ground doing its work rather than an exception to it.
  2. **The product shows the user the file's own contents, not a rendering of the merged result.** The advanced runtime card renders the chosen scope's **raw** `runtime:` mapping read directly from that scope's file rather than from the merged configuration, exactly so a user can tell a setting stated globally from one stated in this workspace from one inherited from the built-in defaults (REQ-CONFIG-471). That distinction is a distinction between two files, and there is nothing raw to render when there is no file. It is also a capability the product has already declined to lose once: when the surface that first carried it was withdrawn, the capability was deliberately re-sited rather than dropped (REQ-CONFIG-445).
  3. **Version control stays the user's choice.** These are the user's own text, in the user's own directories: diffable, mergeable, reviewable, copyable between machines, and quotable in a bug report. The product's own best-effort ignore rule keeps the workspace configuration directory out of version control unless the user decides otherwise (REQ-CONFIG-013, REQ-CONFIG-456), and *deciding otherwise* is a choice a file leaves open. A store the application keeps for itself forecloses it for every user at once.
  4. **Three of the five layers are not per workspace.** The fold is one fixed, total order over built-in defaults, auto-discovered tool servers, the global discovery snapshot, the global scope, and the workspace scope (REQ-CONFIG-031). The first three are not workspace-scoped at all, and the global scope is per user. A store scoped to one workspace could hold at most the last layer, so migrating configuration would put a single, fixed, total merge across two different storage models with different failure modes — at no gain, since the workspace layer is hand-edited exactly as the global one is.

  What this boundary covers is the configuration file set of REQ-CONFIG-003 through REQ-CONFIG-008 together with the persona, model-slot and section content those files carry. It says nothing about the operational records the product writes for itself, which are governed where they are defined — the requirement delivery store is the case in point (REQ-CONFIG-192).
- **REQ-CONFIG-002** — When a load is requested with no workspace named, the workspace root is the current working directory.
- **REQ-CONFIG-003** — `agents.yaml` is the primary configuration file and is read from both scopes. It is optional in each.
- **REQ-CONFIG-004** — `models.yml` is an optional secondary file read from both scopes. Only its top-level `models:` mapping is consumed; every other top-level key in it is ignored without warning or error.
- **REQ-CONFIG-005** — Within a single scope, that scope's `models.yml` entries overlay that scope's `agents.yaml` `models:` block per field. A global `models.yml` still loses to a workspace `agents.yaml` (REQ-CONFIG-031).
- **REQ-CONFIG-006** — `project_settings.yaml` is read from the **global scope only**. It is machine-written (the persisted result of provider sign-in plus model discovery) and is not intended for hand authoring.
- **REQ-CONFIG-007** — `secrets.yaml` may exist in either scope and supplies per-tool-server environment secrets. It is never committed to version control by the product (REQ-CONFIG-013).
- **REQ-CONFIG-008** — Third-party tool-server declarations reach the product by auto-discovery as well as by hand-authored configuration. Where that discovery looks — the project-level and user-level locations and their per-platform spellings — is fixed by REQ-MCP-017, and the shape of a discovered file, the keys it accepts and how it is parsed are fixed by REQ-MCP-018 through REQ-MCP-024 and REQ-MCP-027, which produce entries in the server-entry schema of REQ-MCP-001; this domain holds no copy of any of them and names no discovery location of its own. What this requirement records is only that discovery contributes to the configuration surface: whatever it yields enters the fold as its own layer, contributing `mcp_servers:` entries and nothing else (REQ-CONFIG-031, REQ-CONFIG-033), and each such entry is observable afterwards with the provenance that says it came from discovery rather than from a file in either scope (REQ-CONFIG-222).
- **REQ-CONFIG-009** — That user-level discovery is skipped entirely on Windows when the environment variable naming its location is unset, leaving only the project-level location searched, is fixed by REQ-MCP-017 and is not restated here. What this domain relies on it for is that the skip is not an error: a load in that state produces a discovery layer built from the project-level location alone, or no discovery layer at all (REQ-CONFIG-033), and never a fatal or a warning of this domain's severity taxonomy (REQ-CONFIG-233).
- **REQ-CONFIG-010** — The scope directories also hold state that is not configuration and never takes part in the merge. Under `<workspace>/.rotaris/`: the workspace's stable identifier, whose form and rules are REQ-SESSION-197's and which this domain neither names nor validates; custom tool plugins in `tools/`, inventory plugins in `plugins/`, and per-session isolated checkouts in the directory named by `worktree_storage_subpath` (default `worktrees/`), which is the **only** key naming that directory (REQ-CONFIG-068, REQ-CONFIG-194). Requirement-unit checkouts are placed elsewhere, at a location no key of this domain names (REQ-GIT-137). Under the global scope: custom tool plugins in `tools/`. Provider credentials live in the platform's per-user **data** directory, which is a different directory from the per-user configuration directory, and remain individually protected files rather than records in any store (REQ-PROVIDER-016). The staged gateway credentials of REQ-PROVIDER-063 are held under that same per-user data directory, one directory per workspace named by the workspace identifier, and are **not** under `<workspace>/.rotaris/`. Four kinds of state that were once directories here no longer are, and no key of this domain names a location for any of them. Session records, post-run improvement artifacts (REQ-LIBRARY-042) and requirement delivery records (REQ-CONFIG-192) are held in the store the application keeps for the workspace; the staged gateway credentials just named are held as individually protected files under the per-user data directory rather than in any store, for the reason REQ-PROVIDER-063 gives. That the workspace configuration directory therefore holds only the workspace identifier, plugins and checkouts beside the configuration files themselves is a consequence worth stating, because what a workspace-wide ignore rule (REQ-CONFIG-013) covers is now a much smaller set than it was. One consequence of that ignore rule needs stating plainly, because two requirements read as though they disagree and do not. REQ-SESSION-197 requires the workspace identifier to be human-readable and in a form version control can track; REQ-CONFIG-013 appends `.rotaris/` to the workspace's `.gitignore` by default. What REQ-SESSION-197 fixes is the identifier's **form** — a small plain-text value a person can read, diff and copy, rather than something only this application can interpret — and not an obligation on this product to commit it. Under the default ignore, the identifier travels with a folder that is moved, renamed or copied, and does not travel through a fresh clone; a clone therefore mints its own identifier and starts with an empty local session history, which is what REQ-SESSION-198 requires of a machine that has not run the workspace before. A user who wants the identifier committed can commit it by their own version-control means; the ignore rule is a default about what is staged by accident, not a prohibition, and that the choice remains theirs at all is exactly what ground 3 of REQ-CONFIG-477 relies on a file for.
- **REQ-CONFIG-011** — Provider credentials are never stored in any configuration file in either scope; they live only in the per-user data directory's credential store.
- **REQ-CONFIG-012** — A workspace with no `.rotaris/` directory at all, and a user with no global configuration directory at all, must both load successfully on built-in defaults. Absence is never an error at any level of the file set.
- **REQ-CONFIG-013** — Every configuration load makes a best-effort, idempotent attempt to keep the workspace configuration directory out of version control: if `<workspace>/.gitignore` contains no line that, once trimmed and stripped of a trailing `/`, equals `.rotaris`, the line `.rotaris/` is appended (adding a missing trailing newline first). A missing `.gitignore` is created. The write is atomic. Any failure — unreadable file, undecodable text, write error — is swallowed and never fails the configuration load.
- **REQ-CONFIG-014** — The configuration file set has no read cache: every load re-reads `agents.yaml` and `models.yml` from disk, so any surface performing a load observes the current file contents.

### File format and parse-time error semantics

- **REQ-CONFIG-015** — Configuration files are YAML parsed in a safe subset that cannot construct arbitrary language objects from document tags.
- **REQ-CONFIG-016** — A missing configuration file yields an empty mapping and is not an error.
- **REQ-CONFIG-017** — A file that is empty, whitespace-only, or contains only comments parses to nothing and yields an empty mapping. It is not an error and is indistinguishable from a missing file for load purposes.
- **REQ-CONFIG-018** — A YAML syntax error in `agents.yaml` or `models.yml` **aborts the load** with an error whose message names the full path of the offending file and carries the parser's own detail, including the line and column of the fault.
- **REQ-CONFIG-019** — A file whose top-level document is not a mapping (a list, a scalar) **aborts the load** with an error naming the file and stating that top-level content must be a mapping.
- **REQ-CONFIG-020** — YAML 1.1 boolean folding is handled symmetrically wherever it bites. For any field whose accepted values are a string vocabulary, a value the parser folded to a boolean is coerced back to a lower-cased string before validation: the negative spellings `off`, `false` and `no` become `"off"`, `"false"` and `"no"`, and the affirmative spellings `on`, `true` and `yes` become `"on"`, `"true"` and `"yes"`. The coerced string is then validated against that field's vocabulary like any other string. `sandbox_mode: off` therefore loads as the accepted value `off`, while `sandbox_mode: on` is rejected as an unrecognized confinement mode with a message naming the value and the accepted list (REQ-CONFIG-127) — never as a type error, and never silently accepted.
- **REQ-CONFIG-462** — Configuration files are read as UTF-8. A file whose bytes cannot be decoded as UTF-8 is treated exactly as malformed content of that file's severity class (REQ-CONFIG-024): `agents.yaml` and `models.yml` **abort the load** with an error naming the full path and stating that the file must be UTF-8 text; the discovery snapshot, `secrets.yaml` and a discovered `mcp.json` each degrade per their own rule and contribute nothing. A byte-order mark at the start of a file is accepted and discarded. This is a distinct condition from malformed markup and its message says so.
- **REQ-CONFIG-021** — A malformed or schema-invalid `project_settings.yaml` snapshot is **not** fatal: it is logged as ignored, treated as absent, and the load continues on the remaining layers.
- **REQ-CONFIG-022** — A malformed `secrets.yaml` (unparseable YAML, or a non-mapping top level) yields an empty secret set **silently** — no warning, no exception. Within it, a server entry whose value is not a mapping is skipped; keys and values are coerced to strings.
- **REQ-CONFIG-023** — A malformed discovered `mcp.json` never prevents the product's own configuration from loading. Unreadable files, JSON syntax errors, and non-object top levels each produce a warning naming the file and contribute nothing.
- **REQ-CONFIG-024** — The severity split is a contract: missing and empty files are silent; the primary configuration files are fatal on malformed markup; the discovery snapshot, the secrets file, and third-party discovery all degrade instead of aborting.

### First-run bootstrap

- **REQ-CONFIG-025** — When `<workspace>/.rotaris/agents.yaml` is absent, a minimal starter file is written on first run. The starter document is **scope-independent**: the same content is written for the global `agents.yaml` when a writer bootstraps that file instead (REQ-CONFIG-030), nothing in it being specific to a workspace. Its content is a short comment header explaining that the file overrides built-in roles, models and tool servers, a `default_persona` key (parameterized, shipped value `orchestrator`), and twelve explicitly-null keys: `default_summary_model`, `default_summary_model_thinking`, `large_model`, `large_model_thinking`, `medium_model`, `medium_model_thinking`, `small_model`, `small_model_thinking`, `fallback_model`, `fallback_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`.
- **REQ-CONFIG-026** — Bootstrap creates missing parent directories and **never clobbers** an existing file unless overwrite is explicitly requested; when it declines it reports that it skipped because the file exists.
- **REQ-CONFIG-027** — The bootstrap write is atomic — content is staged beside the target and swapped into place — with a resulting file mode of `0644`. A crash mid-write can never leave a truncated `agents.yaml`, and no temporary file is left behind on any path.
- **REQ-CONFIG-028** — A workspace counts as "needs bootstrap" when the target file is absent or when its text is empty after trimming whitespace; in either case the starter file is written. Two further conditions are reported as needing attention but are **never** written over: a path that is a directory, and a file whose bytes cannot be decoded as UTF-8. For those two the bootstrap declines exactly as REQ-CONFIG-026 requires, and the user-visible outcome is the fatal load error of REQ-CONFIG-462 naming the path. **A target the product cannot read at all takes that same declining path, and is named here so that the two lists above are not read as covering the space between them.** A path that exists and whose content cannot be obtained — refused by the operating system, or failing to be read for any other reason — is neither absent nor empty, so it is not a workspace needing bootstrap and MUST NOT have the starter file written over it; and it is neither a directory nor a decoding failure, so nothing above would otherwise say what becomes of it. It declines as those two do, reporting the path and what prevented the read. The rule the three share, stated so it survives a later edit to any of the lists: **the starter file is written only where the product has established that nothing is there, and never where it has failed to establish anything.** Not being able to read a file is not evidence that the file is empty.
- **REQ-CONFIG-029** — Bootstrap detection and the bootstrap write address the workspace configuration directory by its current name only, as does every other read and write in this specification (REQ-CONFIG-058).
- **REQ-CONFIG-030** — The startup model-preference write path (REQ-CONFIG-248) bootstraps a missing workspace `agents.yaml` before writing, so a first slot or role edit made through it both creates and populates that file. **A global-scoped edit through the same path bootstraps a missing global `agents.yaml` in exactly the same way**, with the same starter content (REQ-CONFIG-025), the same parent-directory creation, the same refusal to clobber, and the same atomic write and file mode: the path behaves identically in both scopes, so a user's first global model preference is never lost for want of a file. Bootstrap remains scoped to the file being written — a workspace-scoped edit never creates the global file, and a global-scoped edit never creates the workspace one. The other two writers do not bootstrap: with no file present the desktop save starts from an empty document (REQ-CONFIG-256), as does the scoped per-field write path (REQ-CONFIG-441).

### Layering and precedence

- **REQ-CONFIG-031** — Configuration layers fold in a fixed, total order, later winning: (1) built-in defaults; (2) auto-discovered tool servers; (3) the global provider/model discovery snapshot; (4) the global scope's `agents.yaml` + `models.yml`; (5) the workspace scope's `agents.yaml` + `models.yml`. Those five are the whole of the layered configuration surface and there is no sixth layer: the product accepts no configuration file from outside the two scopes, because it has no command-line invocation with which to name one (REQ-CONFIG-234, REQ-STARTUP-111). There is no per-key inversion — a workspace file can never lose to a global file.
- **REQ-CONFIG-032** — The built-in default layer is copied per load; a load can never mutate the shipped defaults for the remainder of the process.
- **REQ-CONFIG-033** — The auto-discovery layer contributes **only** `mcp_servers:` entries and is skipped entirely when nothing was discovered.
- **REQ-CONFIG-034** — The discovery-snapshot layer contributes only `models:`, `unavailable_models:`, and the five startup slots `large_model`, `medium_model`, `small_model`, `fallback_model`, `default_summary_model`, and only for providers whose snapshot entry is marked authenticated.
- **REQ-CONFIG-035** — A load that completes successfully yields a configuration that is already fully resolved, so no caller has to finish the job: `workspace_root` holds the resolved workspace path; no reference field still holds a tier alias (REQ-CONFIG-073); the reasoning-effort model entries of REQ-CONFIG-076 and REQ-CONFIG-079 exist and every slot and role that asked for an effort points at one; the document satisfies the schema (REQ-CONFIG-229); `max_input_tokens` and `max_output_tokens` carry values only where the entry stated neither (REQ-CONFIG-096); every `mcp_servers:` entry carries a provenance value (REQ-CONFIG-222); and every environment placeholder and stored secret has been resolved (REQ-CONFIG-218, REQ-CONFIG-224, REQ-CONFIG-225). A stored secret value can never itself be the cause of a schema failure.
- **REQ-CONFIG-036** — Per-role reasoning synthesis must run **after** tier-alias substitution, so a role targeting a tier layers its own effort on top of the slot's resolved model rather than on the raw alias.
- **REQ-CONFIG-037** — Known-token-limit back-fill runs **after** schema validation; placeholder and secret resolution runs after validation too, so secret values never pass through schema validation.
- **REQ-CONFIG-038** — Tool-server provenance is computed after validation but before secret resolution.
- **REQ-CONFIG-039** — Auto-discovered locations are applied user-level first, then project-level, so a project-level declaration of the same server name beats the user-level one. The winning source per server name is recorded and observable (REQ-CONFIG-222).

### Merge disciplines

- **REQ-CONFIG-040** — The merge recognizes exactly four classes of top-level key: replace-if-not-null, named-entry, section, and computed (REQ-CONFIG-041, REQ-CONFIG-043, REQ-CONFIG-047, REQ-CONFIG-049). A top-level key belonging to none of them contributes nothing to the merged configuration and is neither reported nor rejected. Contributing nothing to the merge is not the same as having no effect: such a key may still be read by a surface that parses the same file separately — `rotaris.delegation_strategy` is the shipped case (see Data & Formats). `display` is a section-class key (REQ-CONFIG-047, REQ-CONFIG-172) and `inject_agents_md` a replace-if-not-null key (REQ-CONFIG-466); both are merged by the load path and read back by the surfaces that write them.
  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** `instructions`
  > is a further section-class key holding the per-file `overrides` policy; it merges by the same rules and
  > is read back by the Instructions category. An unrecognized top-level key is **reported as a warning** naming the key and the file it was read from, and still contributes nothing to the merged configuration; it is never fatal, so a file authored against a later release still loads (REQ-CONFIG-233).
- **REQ-CONFIG-041** — **Replace-if-not-null class.** `default_persona`, `default_summary_model`, `default_summary_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`, `gatekeeper_model`, `gatekeeper_model_thinking`, `small_model`, `small_model_thinking`, `medium_model`, `medium_model_thinking`, `large_model`, `large_model_thinking`, `fallback_model`, `fallback_model_thinking`, `worktree_storage_subpath`, `inject_agents_md`. A higher layer replaces the value only when it supplies a non-null value.
- **REQ-CONFIG-042** — `skills` is a **section-class** key (REQ-CONFIG-047), so a layer overlays only what it states: a layer stating `skills.enabled` leaves both override maps inherited, and a layer stating an entry of `skills.overrides` or `skills.invocation_overrides` overlays that skill's policy alone while every other skill's inherited policy survives (REQ-CONFIG-048). A workspace scope therefore cannot discard the global scope's per-skill policies wholesale; to change one, it states that one. A bare `skills:` carrying no value is coerced to an empty section and changes nothing (REQ-CONFIG-054).
- **REQ-CONFIG-043** — **Named-entry class.** `personas`, `models`, `mcp_servers`, `unavailable_models`. Entries union by name across layers. When a name exists in both layers and both values are mappings, the entry's immediate fields are overlaid (higher layer wins per field); otherwise the higher layer's value replaces outright.
- **REQ-CONFIG-044** — A named entry present only in a lower layer survives into the merged result. A workspace file that declares no `mcp_servers:` at all must not erase globally declared servers; a role defined only globally must survive a workspace file that defines other roles.
- **REQ-CONFIG-045** — List-valued fields **inside** a named entry are replaced wholesale, never appended: a role's `tools`, `delegates_to`, `custom_tools` and `mcp_servers` lists are fully restated by any layer that declares them. To add one tool to an inherited role, the full list must be restated.
- **REQ-CONFIG-046** — Mapping-valued fields inside a named entry are likewise replaced wholesale (for example a role's `tool_restrictions` or `mcp_tools` map) — the overlay reaches exactly one level: top-level key → named entry → whole field value.
- **REQ-CONFIG-047** — **Section class.** `runtime`, `verifier`, `compressor`, `circuit_breaker`, `transcript`, `display`, `initialization`, `project_init`, `requirements`, `skills`, `hooks`, `checkpoints`, `integration` (REQ-CONFIG-470). A higher layer's section overlays the inherited section **per field**; unstated fields are inherited. Setting one field of `requirements` keeps every other inherited `requirements` field.
  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** `instructions`
  > joins the section class: a higher layer's `overrides` entry overlays that file's policy alone while every
  > other file's inherited policy survives.
- **REQ-CONFIG-048** — A section overlay is **recursive through nested mappings**: wherever both layers hold a mapping at the same path, the higher layer's fields overlay the inherited ones and every field it does not state is inherited, at any depth. Changing `requirements.board.card_limit` alone therefore leaves the rest of `board:` — `filters` included — exactly as the lower layer left it (REQ-CONFIG-197), and a global per-skill policy survives a workspace file that states a different skill (REQ-CONFIG-042). Recursion stops at any value that is not a mapping: a list is replaced wholesale wherever it appears (REQ-CONFIG-050), and the value of a named entry's field remains one level deep (REQ-CONFIG-046).
- **REQ-CONFIG-049** — **Computed class.** `workspace_root`, `metadata_workspace_root`, `mcp_server_sources`, `resolved_persona_model_tiers` are produced by the loader and are never merged from a file. A `workspace_root` written into a file has no effect.
- **REQ-CONFIG-050** — No key anywhere in the system merges list **contents**. Any list-valued setting — role tool lists, verification checks, hook entries, requirement sources, refresh triggers, escalation triggers, source-file extensions, host lists, writable roots — is replaced by a layer that states it.
- **REQ-CONFIG-051** — The end-to-end merge must satisfy, for a two-scope fixture: workspace role fields win per field while unstated role fields are inherited; a workspace role may reference a model declared in a global `models.yml`; a role's tool list equals the workspace's list exactly; a globally-only role survives; models from all four files coexist as a union; and a workspace `runtime:` block stating only two fields keeps every other runtime field at its inherited value.
- **REQ-CONFIG-461** — The merge disciplines of REQ-CONFIG-040 to REQ-CONFIG-050 are the only merge rules in the product. No consumer replaces a configuration document as a whole, and any example configuration, comment header or document shipped with the product describes these rules and no other. A shipped example that describes whole-document replacement is wrong and is corrected, not honoured.

### Null, absent and empty semantics

- **REQ-CONFIG-052** — For a replace-class key, `null` and absent are behaviorally identical: writing `large_model: null` in a workspace file cannot clear a value inherited from a lower layer.
- **REQ-CONFIG-053** — Inside a named entry, `null` **can** clear: a role override that writes a bare `system_prompt_file:` clears the inherited value, because entry fields are overlaid without a null guard.
- **REQ-CONFIG-054** — A bare section key (`verifier:`, `checkpoints:`, `initialization:`, `project_init:`, `hooks:` with no value) means "unset" and is coerced to an empty section rather than raising a type error.
- **REQ-CONFIG-055** — `hooks: {entries: }` (a bare `entries` key) means the hook list is **unset** — inherit the lower layer's list. `hooks: {entries: []}` means an explicit empty list that **replaces** the inherited list. These two must stay distinguishable.
- **REQ-CONFIG-056** — Three settings are deliberately three-valued and must stay distinguishable across the merge: `verifier.checks` (unset = auto-detect a suite; `[]` = this workspace explicitly runs no verification; a list = the stated suite), `checkpoints.enabled` (unset = on for isolated sessions only; `true` = always; `false` = never), and `hooks.entries` (unset vs. explicit empty).
- **REQ-CONFIG-057** — A per-model `max_parallel` written explicitly as `null` is distinguishable from an omitted `max_parallel` and defeats the provider-conditional default of REQ-CONFIG-095.
