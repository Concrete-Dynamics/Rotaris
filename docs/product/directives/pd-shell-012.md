### PD-SHELL-012 — the terminal window speaks the shown terminal's output politely, only while active, at most 20 lines per update

The terminal window MUST own exactly one polite live region, mounted with the window, present and empty while the empty state of REQ-SHELL-083 shows. While the terminal window is the active window, the region MUST announce the output of the terminal currently shown as it arrives, at most 20 lines per update, the most recent lines where an update carries more; output of a terminal that is not the one shown MUST NOT be announced. While the terminal window is not the active window — including when it was opened or reopened without focus (REQ-SHELL-081, REQ-SHELL-109, REQ-SHELL-110) — the region MUST NOT announce, and output that arrived while it was inactive MUST NOT be replayed when it becomes active; the operator reads it from the grid. The change of the shown terminal from running to exited MUST be announced exactly once, with the exit line. The transcript's embedded preview of the same stream (REQ-SHELL-079, REQ-SHELL-102) MUST NOT be announced while it changes; the terminal window is the only surface that speaks terminal output, as it is the only one that accepts input. No announcement under this directive is assertive.

**Why, and what it costs.** REQ-SHELL-146 asks the terminal window for named controls, contrast while a command runs and after it exits, and an announced empty state, and nothing of running output; the build speaks none of it, so a screen-reader operator who has taken control (REQ-SHELL-166) types into a grid that never answers, on the one surface that accepts input (REQ-SHELL-079). Raised as [OQ-507](../../archive/architecture/open-questions/70-spikes-and-later-questions-37.md#oq-507). Speech is gated on the active window because the record opens and reopens this window without focus and a window that starts talking unasked would speak over the composer; it is polite because agent output is not imperative and assertive speech may clear what is queued; the 20-line cap is the terminal library's own bound for its screen-reader output, taken as a bound on a harm the record names — speech the operator did not start — and not as a measured figure. Speaking only when a command ends was considered and not taken: a command waiting on input would be inaudible where it can be answered. The cost is that an operator who leaves the window hears nothing from it until they return, that a long-running command is heard in 20-line pieces, and that what arrived while the window was inactive is read, not spoken; the gain is that running output and the exit are spoken once, in order, where the operator can act on them. No requirement is displaced: REQ-SHELL-146 and REQ-SHELL-079 govern in full. NVDA's own terminal diffing and VoiceOver (no host, IC-3) may change the result; a reader measurement that 20 lines is wrong, or a `debug-ui`, `review-ui` or autopsy finding of a flood or a lost exit, reopens the question.

> **Extends:** REQ-SHELL-146, REQ-SHELL-079
