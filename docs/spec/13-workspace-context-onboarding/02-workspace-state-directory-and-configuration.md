# Workspace Handling, Context Injection, and Project Onboarding — Workspace State Directory and Configuration Layering

Part 2 of 7 of [domain 13](../13-workspace-context-onboarding.md), which indexes every part. Defines REQ-WORKSPACE-034 – REQ-WORKSPACE-069.

### Workspace State Directory and Configuration Layering

- **REQ-WORKSPACE-034** — Per-workspace state SHALL live under `<workspace>/.rotaris/`. The workspace-scope configuration file is `<workspace>/.rotaris/agents.yaml`; each configuration scope directory is additionally read for a `models.yml` file.

- **REQ-WORKSPACE-035** — *Withdrawn.* The product has no earlier release under another name, so there is no legacy workspace, configuration, or data directory to adopt; `<workspace>/.rotaris/` (REQ-WORKSPACE-034) is the only per-workspace state directory the product ever reads or writes.

- **REQ-WORKSPACE-036** — Configuration SHALL be assembled from five layers, listed here from lowest precedence to highest: built-in defaults, whose hook entries are stamped with origin scope `default`; MCP servers discovered from `.mcp.json` files; provider snapshot models recorded in the per-user configuration directory; global scope, being `<per-user-config-dir>/agents.yaml` together with `models.yml` from the same directory, whose hook entries are stamped `global`; and workspace scope, being `<workspace>/.rotaris/agents.yaml` together with `models.yml` from the same directory, whose hook entries are stamped `workspace`. A setting defined in more than one layer SHALL take its value from the highest-precedence layer that defines it; a setting a layer leaves undefined SHALL keep the value it had from below. A list-valued setting SHALL be replaced whole by the higher layer rather than appended to (REQ-WORKSPACE-125 states the one exception, which applies to untrusted workspace hook lists). The workspace root is the folder the window was opened on (REQ-WORKSPACE-005 through REQ-WORKSPACE-007). The provider snapshot layer is the per-user provider catalog snapshot `project_settings.yaml` in the per-user configuration directory, whose document shape, atomic write, and merge into the effective configuration are specified in the model-providers specification (REQ-PROVIDER-084, REQ-PROVIDER-085, REQ-PROVIDER-091); this domain fixes only its position in the precedence order above and SHALL NOT restate its contents. A snapshot that is absent, or that fails that specification's validation, SHALL contribute nothing and SHALL NOT make configuration load fail.

- **REQ-WORKSPACE-037** — The `.mcp.json` discovery layer of REQ-WORKSPACE-036 SHALL be the discovery specified by REQ-MCP-017 and by the requirements it names: this domain relies on that specification for which two files are read and where they live, for the file's accepted shape and keys, for name and placeholder handling, for the precedence between the user-level and project-level files, and for the guarantee that a malformed file or entry is skipped with a warning and never aborts configuration load. This domain adds only two things and restates nothing else. First, the project-level file is located against the workspace root this domain fixes — the folder the window was opened on (REQ-WORKSPACE-005 through REQ-WORKSPACE-007) — so `${workspaceFolder}` resolves to that same root. Second, whatever discovery yields enters the five-layer assembly of REQ-WORKSPACE-036 at the position stated there, below both YAML scopes.

- **REQ-WORKSPACE-038** — A minimal bootstrap `agents.yaml` SHALL be writable. Its content is fixed rather than generated, and SHALL be exactly the scope-independent starter document of REQ-CONFIG-025: a short comment header conveying that the file is a minimal starting configuration, that editing it overrides the built-in personas, models, and tool servers, and that real models are wired up by authenticating a provider in the Settings Models category (REQ-WORKSPACE-152) — the wording of those three lines being left to the implementation — followed by `default_persona: orchestrator` and by exactly the twelve explicitly-null keys that requirement enumerates: `default_summary_model`, `default_summary_model_thinking`, `large_model`, `large_model_thinking`, `medium_model`, `medium_model_thinking`, `small_model`, `small_model_thinking`, `fallback_model`, `fallback_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`. Because those keys belong to the replace-if-not-null class (REQ-CONFIG-041), writing them as nulls overrides nothing from a lower layer. The file SHALL be written to a temporary file and then put in place by replacement, and SHALL end up with mode 0o644. A write request SHALL do nothing and report the reason "already exists" unless overwriting was explicitly asked for. Bootstrap SHALL be reported as needed when the target path is missing, holds nothing but whitespace or nothing at all, is a directory, or cannot be decoded as text.

- **REQ-WORKSPACE-039** — Saving desktop settings SHALL read `<workspace>/.rotaris/agents.yaml`, change it, and put the result back through an atomic replace. Top-level keys the application does not itself manage SHALL survive the round trip verbatim. The keys the save writes are exactly those REQ-CONFIG-256 enumerates — the model slots and their reasoning companions, the runtime keys including `runtime.allow_outside_workspace` (REQ-WORKSPACE-148) and `runtime.permission_mode`, the six confinement and egress fields, `circuit_breaker.enabled`, `compressor.threshold_percentage`, the delegation strategy, and `skills.enabled`, `skills.overrides` and `skills.invocation_overrides` — and this domain SHALL NOT name a key that requirement does not. A persona edit whose chosen scope is global SHALL be written to the global `agents.yaml` instead of the workspace one. Validation SHALL happen before any file is opened for writing, on the terms of REQ-CONFIG-260: where the schema rejects any of the six confinement or egress values the save SHALL be abandoned, every configuration file SHALL be left byte-for-byte as it was and still loadable, and the user SHALL be shown a single sentence carrying the first complaint. A save that completes SHALL be followed by a configuration reload and by re-projecting the skill list from a freshly discovered catalog.

  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** The
  > save additionally writes the `instructions.overrides` per-file policy into the workspace file, on
  > the same sparse terms as the skill maps; the keys the save writes are otherwise exactly those named
  > above.

- **REQ-WORKSPACE-040** — Writers of the persisted initialization state SHALL round-trip the entire YAML document and land via atomic replace, so that a crash partway through writing cannot leave the user's configuration truncated; when no `agents.yaml` exists, the minimal bootstrap file SHALL be written first.

### Workspace Context Injection (AGENTS.md)

- **REQ-WORKSPACE-041** — Context-file discovery SHALL be workspace-root-only: in the resolved workspace root, `AGENTS.override.md` is used when present, otherwise `AGENTS.md`; nothing else. Those two names are the whole vocabulary. No other directory SHALL be consulted — not an ancestor, not the enclosing repository root, not an intermediate directory, not a user-global location — and no other file name SHALL be read or injected, user-global context files, `CLAUDE.md`, `GEMINI.md`, and any product-named alternative such as a root-level `ROTARIS.md` included, even when such a file is present at the workspace root. This is a closed rule rather than an omission: a multi-level scheme would make what an agent was given depend on where the folder happens to sit in a tree the user did not choose, and the override file already provides the one thing a second level would be for. A broader scheme, if ever wanted, requires its own requirement and is not implied by anything here.

- **REQ-WORKSPACE-042** — Given both `AGENTS.override.md` and `AGENTS.md` exist at the workspace root, only the override file's content SHALL appear in the merged output; the regular file's content SHALL be absent.
  > **Narrowed by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** The
  > suppression is pairwise: `AGENTS.override.md` suppresses `AGENTS.md` alone and
  > `CLAUDE.override.md` suppresses `CLAUDE.md` alone. The text above states the behavioural target
  > and is kept for that reason.

- **REQ-WORKSPACE-043** — Merged-output format: each contributing file's content SHALL be preceded by a one-line HTML comment `<!-- source: {absolute path} -->` on its own line; blocks SHALL be separated by one blank line; concatenation follows discovery order.
  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** The
  > format is unchanged and now covers every enabled file in the directive's discovery order; a file
  > switched off contributes nothing, not even its source comment.

- **REQ-WORKSPACE-044** — Size limits SHALL default to 32,768 bytes for any one context file and 131,072 bytes for the merged output, both measured as UTF-8 bytes and both overridable per call. A file exceeding the per-file limit SHALL be cut back to the last line boundary that fits within it; a file whose very first line already exceeds the limit SHALL contribute nothing at all. Against the total limit, the budget left for a file SHALL be reckoned after its source-comment line has been charged: a file that does not fit whole SHALL be cut down to whatever budget remains, and a file for which no budget remains — including the case where its source comment alone would exhaust it — SHALL be dropped in its entirety, source comment included. A cut made against the total budget SHALL fall back to the last line boundary that fits within the remaining budget, exactly as a cut against the per-file limit does — one truncation rule governs both, so no block ever ends mid-line — and a file whose very first line already exceeds the budget remaining to it SHALL be dropped in its entirety, source comment included, rather than contributing a fragment. Every truncation and every drop SHALL produce a log warning naming the file concerned. The merged output SHALL never exceed the total limit.

- **REQ-WORKSPACE-045** — A whitespace-only context file SHALL be skipped silently (no block, no source comment). An unreadable file (I/O or decoding error) SHALL be skipped with a warning naming the path and the error, without aborting discovery.

- **REQ-WORKSPACE-046** — Merged context SHALL be cached per workspace root and kept for as long as the session lasts; subsequent injections reuse the cache without touching the filesystem. The cache (together with the skill-catalog cache) SHALL be cleared on every session creation, so each new session re-reads context files from disk. An explicit cache-clear operation SHALL force a reload.

- **REQ-WORKSPACE-047** — Given context injection is enabled and the merged content is non-empty, each agent built for that session SHALL receive the content as its own permanently active context block, ordered ahead of the skill catalog, ahead of any always-on skill bodies, and ahead of persona memory. With no context files, or injection disabled, no such unit SHALL be constructed.

- **REQ-WORKSPACE-048** — The per-workspace configuration key `inject_agents_md` (boolean, default `true`) SHALL control injection; when false, no context file is read at all.
  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** The
  > master switch stands above the per-file `instructions.overrides` policy: while false nothing is
  > read, whatever the per-file policies say; while true only the files switched on are read.

- **REQ-WORKSPACE-049** — Discovering and merging workspace context files SHALL complete within 200 ms for a workspace holding up to 20 context files totalling 1 MiB on local storage. It SHALL NOT delay the moment the interface first accepts input, and the window SHALL keep responding to input for as long as it runs. For an unchanged filesystem state, running it again in a separate process SHALL yield byte-identical output: the merged text SHALL carry no timestamp, no process identifier, and no ordering that varies from run to run. The 200 ms figure SHALL be measured under these reference conditions and no others: the workspace on local, non-removable storage; the filesystem cache **cold** for the files concerned, so the figure covers the first read after a workspace is opened rather than a repeat of it; up to 20 context files totalling 1 MiB; and the reported figure being the 95th percentile of at least 20 consecutive cold measurements taken in separate processes, rather than a mean or a best case. Conformance is assessed per machine: a build meets this requirement on a machine when it meets the figure there under those conditions. The determinism and responsiveness guarantees stated here hold unconditionally, on every machine and under every load.
  > **Narrowed by [`PD-WORKSPACE-004`](../../product/directives/pd-workspace-004.md#pd-workspace-004), 2026-10-06.** "Up to 20 context
  > files totalling 1 MiB" reads "every instruction file discovery can reach, totalling up to 1 MiB" — fourteen
  > files, or twelve on Windows — in both places it appears. The figure and every other reference condition are
  > unchanged.

- **REQ-WORKSPACE-050** — When a run executes in an isolated worktree, workspace context files SHALL be read from the run's execution root, while the portable-skill catalog and persona memory SHALL be discovered from the user-selected base workspace, so persistent workspace metadata stays with the base workspace.

### Portable Skill Discovery and Parsing (SKILL.md)

- **REQ-WORKSPACE-051** — Skill discovery SHALL search the locations below in exactly the order given, the first location to yield a particular normalized name winning outright over every later one:
  1. Project scope, covering every directory from the resolved workspace root upwards to and including the enclosing repository root — the nearest ancestor holding a `.git` entry, which may be a directory **or** a file so that a linked worktree root also ends the walk, and the workspace root itself when no such ancestor exists. Directories SHALL be visited nearest first, and within one directory `<dir>/.agents/skills/<name>/SKILL.md` SHALL be searched before `<dir>/.opencode/skills/<name>/SKILL.md`.
  2. User scope, searched in the order `~/.agents/skills`, then `~/.config/opencode/skills`, then `~/.openhands/skills/installed`, then the machine-wide `/etc/codex/skills`.

  Every project-scope location SHALL outrank every user-scope location. Within any of these roots, only immediate child directories count, and only those holding a `SKILL.md` file; children SHALL be visited in ascending name order, so that the outcome never depends on the order the filesystem happens to list them in. On a platform that has no `/etc` hierarchy, user scope SHALL simply end at the three home-relative roots: no platform-specific machine-wide path SHALL be substituted, and the product SHALL declare no fourth user-scope root on any platform. The reason is stated with the rule — a machine-wide directory carries skills the account using the product may not have written, and the platforms that lack `/etc` do not offer a directory with the same ownership guarantees, so silently substituting one would widen what can reach an agent's context on that platform alone.

- **REQ-WORKSPACE-052** — Given `~/.openhands/skills/.installed.json` exists, skill directories whose name (or normalized name) matches a disabled entry SHALL be skipped. Accepted manifest shapes: a map with a `disabled: [names]` list; a map whose values are maps carrying `disabled: true` (any of the entry key, a `name` field, or a `path` field identifies the skill); or a list of maps with `disabled: true`. An unreadable manifest SHALL log a warning and disable nothing.

- **REQ-WORKSPACE-053** — A valid `SKILL.md` SHALL begin with YAML frontmatter delimited by `---` lines; the frontmatter must be a mapping and must contain `name` and `description`. Invalid files SHALL be skipped with a logged reason (e.g. missing frontmatter, malformed YAML, missing required field, unsupported trigger shape, unreadable file) and discovery SHALL continue — an invalid skill never crashes startup. Unknown frontmatter fields SHALL be preserved and available as raw metadata.

- **REQ-WORKSPACE-054** — Skill names SHALL normalize as: lowercase; every run of characters outside `[a-z0-9]` becomes `-`; leading/trailing `-` stripped. A name normalizing to empty is invalid. On collision the earlier (higher-priority) skill SHALL win, and the shadowed one SHALL be recorded and reportable per name.

- **REQ-WORKSPACE-055** — The canonical trigger shape SHALL be `trigger: {type: keyword, keywords: [...]}`; legacy top-level `type:` plus `triggers:` aliases SHALL be accepted and normalized. Only the `keyword` type is supported; the keyword collection SHALL contain nothing but strings; entries are stripped and de-duplicated preserving order. Description whitespace SHALL be collapsed to single spaces.

- **REQ-WORKSPACE-056** — A skill's invocation mode SHALL derive from frontmatter: `user-invocable: false` → auto-only; `disable-model-invocation: true` → manual-only; otherwise default.

- **REQ-WORKSPACE-057** — Manually loading a skill SHALL accept a path to a `SKILL.md` file or a directory containing one, with `~` expansion and relative paths resolved against the workspace root; failures are "SKILL.md not found: {raw}" and "manual skill path must be a SKILL.md file or directory: {raw}". Manual skills carry the scope label `manual`, override a discovered skill of the same normalized name, apply to the current session only, and persist nothing.

- **REQ-WORKSPACE-058** — The skill catalog SHALL be cached per resolved workspace root and cleared on every session creation, so skills are re-discovered from disk at each new session; discovery runs automatically on workspace open with no user action.

- **REQ-WORKSPACE-059** — The sorted, resolved set of all cataloged skill directories SHALL be registered as additional read roots for agent file tools: an agent can read a `SKILL.md` and its sibling resources even when the skill directory lies outside the workspace, while writes to those roots SHALL still be rejected.

### Skill Catalog Injection and Load Policies

- **REQ-WORKSPACE-060** — At agent construction a compact skill catalog SHALL be injected as its own always-active context unit, distinct from the persona prompt, the workspace context unit, and persona memory. Ordering of injected context units SHALL be: workspace context → skill catalog → force-loaded skill bodies → persona memory.
  > **Extended by [`PD-TOOLS-012`](../../product/directives/pd-tools-012.md#pd-tools-012) revision 2, 2026-10-07.** The four units above
  > keep their order; every agent also receives one product statement, naming the product's own workspace directories, as a
  > fifth always-active unit after them, whatever its persona's prompt and whether or not context files are injected.

- **REQ-WORKSPACE-061** — The catalog block SHALL contain a preamble followed by exactly one entry per catalogued skill and nothing else. The preamble SHALL convey three facts, in wording of the implementation's choosing: that every entry below names a `SKILL.md` file that exists on disk; that such a file is to be opened only when the task in hand calls for it; and that none of those files' contents have already been supplied. Each entry SHALL be a single line carrying, in this order, the skill's normalized name, its description, and the absolute path of its `SKILL.md`, in the shape given under Data & Formats. Entries SHALL appear in ascending normalized-name order. No skill's body text SHALL appear anywhere in the block.

- **REQ-WORKSPACE-062** — Each skill SHALL carry a load mode drawn from the closed set `off | name-only | user-invocable-only | on`, defaulting to `name-only`, and offered in the user interface under the labels "hidden" / "on-demand" / "manual only" / "always". The mode determines what an agent ends up with:
  - `name-only`: an entry for the skill is present in the injected catalog, and the user can invoke it.
  - `on`: no entry for the skill is present in the catalog; in its place the skill's body, with the YAML frontmatter removed, is present as an always-active block of its own. That block SHALL be introduced by a statement naming the skill and directing that its guidance apply from that point onwards — unconditionally, with no trigger phrase awaited and no question asked about whether to activate it. Given the body cannot be read, no such block SHALL be present, every other part of the agent's context SHALL be exactly as it would otherwise have been, and a log warning naming the skill SHALL be emitted.
  - `user-invocable-only`: no entry for the skill is present in the catalog, and the user can still invoke it.
  - `off`: the skill appears nowhere and cannot be invoked.

- **REQ-WORKSPACE-063** — Each skill SHALL have an invocation mode from `default | manual-only | auto-only`: manual-only removes it from the model-facing catalog (user command only); auto-only removes it from user invocation (model catalog only). Workspace-configured invocation overrides SHALL take precedence over the frontmatter-derived mode.

- **REQ-WORKSPACE-064** — A global switch `skills.enabled` (default `true`) SHALL control the whole feature: when false, no catalog is injected, no body is force-loaded, and no skill is user-invocable.

- **REQ-WORKSPACE-065** — The chosen per-workspace load and invocation policies SHALL be persisted in `<workspace>/.rotaris/agents.yaml` and SHALL govern agents constructed afterwards. A workspace with no recorded policy SHALL behave as on-demand load with default invocation for every skill (zero-migration default). Policy SHALL be per workspace and SHALL NOT be scoped per persona: every agent built for a session SHALL see the same catalog and the same force-loaded bodies, so a skill can never be visible to one persona and hidden from another. This is a closed rule; per-persona scoping, were it ever wanted, requires its own requirement.

- **REQ-WORKSPACE-066** — Skill bodies SHALL enter model context only through the agent's own filesystem/shell tools, an explicit user command, or the "always" load policy; the framework SHALL NOT pre-fetch or rewrite bodies, and scripts referenced by skills run via the shell with only their stdout/stderr entering context.

### Skill Controls in Settings

- **REQ-WORKSPACE-067** — The Settings Skills tab SHALL show: a header card "Portable skills" with a toggle labeled "Enable skills" (accessible name "Enable portable skills", description "Controls whether any portable skill is injected into newly created agents"); a table with columns Skill, Source, Path, Trigger, Load, Description (description also as tooltip); a Path cell carrying the absolute path of that skill's `SKILL.md`, elided under REQ-WORKSPACE-149 with the full path as its tooltip and accessible description, so the tab answers which file on disk a listed skill came from; a Source cell reading the skill's scope label, which for a skill loaded by hand under REQ-WORKSPACE-151 SHALL read `manual`, marking it as applying to this session only; for a skill that shadows duplicates, a Source cell of `{scope}  ⓘ` with tooltip "Workspace skill wins. Ignored duplicate(s):" followed by the shadowed `SKILL.md` paths; a per-row invocation selector (accessible name "Invocation policy for {name}") offering "default (both)", "manual only", "auto only"; a per-row load selector (accessible name "Load policy for {name}") offering "on-demand", "always", "manual only", "hidden"; two header actions, "Rescan skills" (REQ-WORKSPACE-069) and "Load skill file…" (REQ-WORKSPACE-151); and the empty state "No portable skills were discovered." The tab SHALL show no per-agent in-context indicator and SHALL offer no composer chip: what an agent will receive is read from the Load column together with the `manual` scope label.

- **REQ-WORKSPACE-068** — Policy setters SHALL reject unsupported values with the errors "Unsupported skill load mode: …" / "Unsupported skill invocation mode: …", mark settings dirty, and emit a change notification. Saving SHALL write only non-default policies, keyed by normalized skill name, into `skills.overrides` and `skills.invocation_overrides`.

- **REQ-WORKSPACE-069** — Rescan behavior: the skill list SHALL be re-projected from a fresh catalog on configuration load and save; the typeable-command catalogue SHALL be rebuilt whenever the library or settings change; and session creation clears both discovery caches. In addition, the Settings Skills tab SHALL carry a "Rescan skills" action (accessible description stating that it re-reads skill files from disk for this workspace). Activating it SHALL clear the skill-catalog cache for the resolved workspace root, re-run discovery against the filesystem, re-project the table, and rebuild the typeable-command catalogue; it SHALL change no load or invocation policy, SHALL NOT mark settings dirty, and SHALL govern agents constructed afterwards while leaving agents already built untouched. Without it a `SKILL.md` added to disk during a session would be unreachable until a new session began.
