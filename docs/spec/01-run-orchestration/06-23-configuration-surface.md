# Multi-Agent Run Orchestration — 23. Configuration Surface

Part 6 of 8 of [domain 01](../01-run-orchestration.md), which indexes every part. Defines REQ-ORCH-143 – REQ-ORCH-149.

### 23. Configuration Surface

- **REQ-ORCH-143** — All defaults in the Data & Formats configuration table MUST hold, and MUST be verified by configuration-default tests. Additional validation: duplicate check names are a load-time configuration error; the graceful-pause tool deadline is bounded to [5, 120] seconds; the unresponsive-model threshold has a floor of 30 seconds.
- **REQ-ORCH-144** — Per-role overrides MUST include: a per-role stall threshold (for slow reasoning models); a fallback model (used at most once per child on hard timeout or unresponsive model); a thinking toggle; a coordination-only tool profile (delegation and todo maintenance permitted; reading, editing, and execution withheld); a read-only profile; an allowed-delegates list; a suppress-sibling-context flag; an artifact-publishing flag; a summarizer-model override; and a permission mode.
- **REQ-ORCH-145** — Per-model settings MUST include: a per-model parallelism cap (REQ-ORCH-050); a per-model HTTP timeout overriding the runtime model timeout; and a per-model retry count overriding the provider default of 5.
- **REQ-ORCH-146** — For a provider that ships its own native agentic loop, a runtime toggle (default enabled) MUST run children on that provider under the native loop; disabling it falls back to a degraded single-shot mode that discards tool use and streaming. A deprecated intent-validation toggle (default false) is retained for configuration compatibility, superseded by completion classification.
- **REQ-ORCH-156** — Every duration stated in this domain is a wall-clock duration measured against a monotonic clock from the start point the requirement stating it names, and every one of them bounds only what this run controls. A budget fixes when the run takes its stated action, not the total time that may elapse: where the action can only be taken at a boundary it is taken at the first boundary at or after the budget expires, so a long iteration may overshoot the time limit exactly as REQ-ORCH-069 already states, and a budget spent inside a provider call is measured from the moment the run issued the call rather than from when the provider began work. Where two budgets bound the same activity the smaller governs and expiry of the smaller never resets the larger (REQ-ORCH-124). Conformance to every duration in this domain MUST be demonstrable with a controlled clock, so no conformance claim here depends on real provider latency or on the wall-clock cost of a live model call.

### 24. Persistence

- **REQ-ORCH-147** — The session records and workspace-level files in Data & Formats MUST be produced as described. The session records this domain names are part of the session's durable record, whose form, layout, and store are the session-persistence domain's to fix (REQ-SESSION-001); this domain names what must be held and holds no copy of where or how. A session's persisted state MUST durably hold at least: the resolved check suite, the message count and active message limit, the run intent, the todo state, the loop progress record, and improvement artifact ids.
- **REQ-ORCH-148** — The gate-state metadata file is tool-managed and never hand-authored; the editable gate lives in the user configuration (REQ-ORCH-125).
- **REQ-ORCH-149** — The session artifact store MUST be session-scoped, hydrated from the session's durable record where the session has one and held only in memory where it has none, shared across iterations, and the source of the auto-injected sibling summaries in child payloads. An artifact's body is held as a file on disk and referenced from the record rather than kept inside it, so a body of any size is readable as an ordinary file while its identity, its ownership, and its ordering come from the record; where those bodies live is the session-persistence domain's to fix (REQ-SESSION-001, REQ-SESSION-002) and is not fixed here.
