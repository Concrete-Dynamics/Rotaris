# Desktop Shell, Navigation, and Window Management — Title bar

Part 2 of 7 of [domain 12](../12-desktop-shell-windows.md), which indexes every part. Defines REQ-SHELL-033 – REQ-SHELL-071.

### Title bar

- **REQ-SHELL-033**: The title bar is a fixed-height strip (44 px in the default theme) with a bottom hairline, containing left to right: the brand mark (22×22, accessible name "Rotaris"), the wordmark "Rotaris", a version label `v{version}` in small monospace, the workspace chip (centered region), the session chip, and the improvement-analysis indicator.
  > **Extended by [`PD-SHELL-003`](../../product/directives/pd-shell-003.md#pd-shell-003), revised 2026-09-24.** The product-drawn title bar additionally ends with the main window's minimize, maximize/restore and close controls on Windows, Linux and macOS; the contents and ordering above remain intact ahead of them.
- **REQ-SHELL-034**: If the brand image asset is missing or unrenderable, the title bar degrades to a letter placeholder "R" in a dashed accent frame without crashing.
- **REQ-SHELL-035**: The workspace chip behaves as a button: accessible name "Open project folder", tooltip "Open another project folder", pointing-hand cursor, keyboard focusable, activated by left-click release inside it or by Return/Enter/Space. It displays a folder icon, the workspace path in small monospace, a separator, and the session name (an em dash when none). Its accessible description is "Current project: {path}. Opens the native project folder chooser." Activation opens the workspace chooser flow (REQ-SHELL-021).
- **REQ-SHELL-036**: The session chip carries the accessible name "Session status" and the accessible description "Session is {status}", and displays a status dot — 6 px in the default theme — followed by the text "session {status}". The status word is always a member of the normalised run lifecycle vocabulary of REQ-NOTIFY-048, which is the product's single definition of it; this document declares no status word of its own, holds no copy of the member list, and never renders a raw backend or persisted status string. What the chip contributes is how those members are coloured. They fall into five colour groups — {`running`, `starting`}, the waiting family {`pausing`, `paused`, `cancelling`}, {`completed`}, {`failed`, `stopped`}, and {`idle`} — and each group resolves to a single theme state colour that the chip's dot and pill share with every status tag drawn elsewhere in the product, so one status word is never shown in two different colours at the same moment. The mapping is one group to each of the five state text colours the theme declares (REQ-SHELL-145): {`running`, `starting`} use `running`; the waiting family uses `waiting`; {`completed`} uses `done`; {`failed`, `stopped`} uses `fail`; and {`idle`} uses `info`. No group borrows another's colour and no group falls back to plain text colour, so all five are distinguishable from one another as well as from ordinary text. A member the vocabulary gains is given its group here rather than acquiring a colour of its own. The dot pulses for `running` and `starting` and for no other status; otherwise it is drawn at full opacity with no animation. Chip text measures at least 4.5:1 against the title-bar background it is actually painted on.
- **REQ-SHELL-037**: The improvement-analysis indicator (a slightly smaller pulsing dot plus the label "Reviewing run for improvements…") is visible only while improvement analysis is active, carries the accessible name "Improvement analysis status", and its description states the user may continue working.

### Status strip

- **REQ-SHELL-038**: The status strip is a fixed-height bottom row (26 px in the default theme) with a top hairline. Items left to right: workspace path (link), checked-out branch, spacer, safety flags, model, tokens, cost, cloud credit (link; present only under the condition in REQ-SHELL-046), background-session count. Every item carries an accessible name; the names are "Workspace folder", "Checked-out branch", "Safety settings in force", "Model runs use", "Tokens used", "Cost so far", "Rotaris Cloud credit", and "Background sessions".
  > **Narrowed by [`PD-SHELL-008`](../../product/directives/pd-shell-008.md#pd-shell-008), 2026-10-06.** The strip also carries
  > REQ-SANDBOX-121's indicator, `sandbox: <backend>`, right after the file-access flag and before the mode flag, with
  > the accessible name "Confinement backend". Every other item, its order and its name are unchanged.
- **REQ-SHELL-039**: The strip holds two kinds of item. An item that opens something is a link: link colour, underline, pointing-hand cursor, its own keyboard focus stop, activated by click or by Return. Every other item is inert text — arrow cursor, no focus stop, no link styling — but an inert item is still exposed to assistive technology with its accessible name, and with its tooltip sentence as its accessible description where it has a tooltip (REQ-SHELL-058). Exactly two items are ever links, the workspace path and the cloud credit, and each is a link whenever it is on screen. Both have visibility conditions (REQ-SHELL-046, REQ-SHELL-047), so the strip may show two links, one, or none — never a third.
- **REQ-SHELL-040**: Activating the workspace-path link opens the workspace folder in the OS file manager; activating the cloud-credit link opens the configured cloud account/quick-start page in the default browser. Neither failure is silent. When the host has no handler for a folder or a URL, or the handler cannot be launched, the transient error notification of REQ-SHELL-112 SHALL appear, and it SHALL convey both that the folder or the page could not be opened and the path or URL that was attempted, so the user can reach it by another route; its wording is left to the implementation. The link SHALL stay enabled and SHALL remain activatable again, and nothing else about the strip SHALL change. The About page keeps its own inline-caption reporting of the same kind of failure (REQ-SHELL-141, REQ-SHELL-142).
- **REQ-SHELL-041**: Each safety flag shows a short form and carries one full-sentence explanation, and its tooltip and its accessible description are the identical joined string "{short form} — {explanation}". The flags appear left to right in this fixed order, each with the display condition given: "● CB armed", shown only while the circuit breaker is enabled — "Circuit breaker: Rotaris stops a run that keeps repeating a failing step."; "redaction: always on", shown unconditionally — "Secret redaction: anything that looks like a credential is masked before it reaches a model or the transcript."; "unsaved settings", shown only while the Settings view holds unsaved edits, its explanation conveying exactly two things and no more — that the Settings view is holding edits which have not been saved, and that runs keep using the last saved values until they are saved — with the wording of that sentence left to the implementation; then exactly one of "outside-workspace!" (file access is not confined to the workspace) or "workspace-scoped" (it is), one of which is always present; and "mode: {mode}", shown unconditionally — "Permission mode {mode}: how much agents may do without asking. Change it under the composer or in Settings → Runtime." Short forms and explanations use the same words as the Settings controls that produce them, so a flag can be matched to its setting by name.
- **REQ-SHELL-042**: The branch item shows a branch icon in accent color (re-rendered on theme change), the branch name, and an "↑{n}" ahead marker; its tooltip names the branch and states how many commits it is ahead, with a noun agreeing with that number under REQ-SHELL-044 and its wording otherwise left to the implementation.
- **REQ-SHELL-043**: The model item is painted at full text strength rather than the muted treatment used by its neighbours, and carries the tooltip "Runs started from this window use {model}. Change it in the composer or in Settings → Models."
- **REQ-SHELL-044**: The tokens item reads the running total of tokens used, its digits grouped into thousands with commas, then a space, then "tok" — for example "12,480 tok". The background-sessions item reads the number of sessions currently in the background followed by a noun that agrees with that number ("1 bg session", "3 bg sessions"). This is the general rule for the whole shell: wherever a count is shown with a noun, the noun agrees with the count, and the literal parenthesised "(s)" form is never rendered anywhere in the product. Neither of these two items is hidden at a count of zero — a count of zero is a known value, unlike the unavailable figures REQ-SHELL-045 and REQ-SHELL-046 withhold — so before any tokens have been consumed the strip reads "0 tok", and with no background sessions it reads "0 bg sessions", subject only to the responsive hiding of REQ-SHELL-047.
  > **Narrowed by [`PD-SHELL-006`](../../product/directives/pd-shell-006.md#pd-shell-006), 2026-10-06.** Four tool results keep the
  > marker their requirements spell, wherever the tool row draws them: REQ-TOOLS-110's `byte(s)`, REQ-TOOLS-134's
  > `match(es)`, REQ-LIBRARY-100's `artifact(s)` and REQ-LIBRARY-089's `Invalid tag(s): `. Every other string still
  > agrees with its count.
- **REQ-SHELL-045**: No cost item is present until at least one session has reported usage and a cost figure exists for it; the word "cost" is never shown in the strip without a figure preceding it. Once present the item reads "{figure} cost", the figure being the model provider's reported cost for this workspace's runs so far, or the literal "n/a" for a model with no published pricing. The figure is rendered by the product's single money rule (REQ-PROVIDER-121) and by no other: exact decimal arithmetic rather than binary floating point, rounded half-up, to two decimal places — or to four when the magnitude is below $0.01, so a cost that is small but not nothing is never rendered as zero. What delivers that property is the rule's floor: a cost greater than zero that four places would still render as zero renders as `< 0.0001` (`< $0.0001` in US dollars), and zero renders `0.00` (accepted amendment 2026-09-29, ESC-42). The currency is the one the provider reports the cost in, shown as the symbol $, € or £ for USD, EUR and GBP and otherwise as the amount followed by the upper-cased currency code. Costs reported in different currencies are never added together into one figure; where this workspace's runs have been billed in more than one currency, each currency is shown as its own figure within the item, separated so that each remains individually readable. Its tooltip and accessible description read "Cost of this workspace's runs so far: {figure}. Reported by the model provider; an unpriced model reads n/a."
- **REQ-SHELL-046**: No cloud-credit item is present in the strip until a credit balance for the signed-in account is available; while signed out, and before any balance has arrived, the strip contains no such item. Once present the item reads "{balance} credit", with " ⚠ no credit" appended for as long as the cloud service is declining new work for want of credit — that is, for as long as the account payload's admission-allowed flag is false (REQ-PROVIDER-130). The balance is rendered by the product's single money rule (REQ-PROVIDER-121): exact decimal arithmetic, a balance rounded **down** toward negative infinity rather than half-up, to two decimal places or four when the magnitude is below $0.01, in the currency the account reports, shown as $, € or £ for USD, EUR and GBP and otherwise as the amount followed by the upper-cased currency code. The {state} substituted into its tooltip is one of exactly the four credit states of REQ-PROVIDER-130 — `available`, `exhausted`, `overdrafted`, `unknown` — rendered one-to-one as a single readable word each, so the state is always recoverable from the text; a state the backend reports that is none of the first three renders as `unknown` rather than failing the read. Its text is tinted with the accent colour while credit remains, and with a warning colour measuring at least 4.5:1 against the strip background once credit is exhausted. Its tooltip and accessible description read "Rotaris Cloud · {state}. Opens the account page, where credit is topped up."; activating it opens that page per REQ-SHELL-040.
- **REQ-SHELL-047**: Responsive hiding: when the window is narrower than 1180 px the workspace-path item is hidden; below 1080 px the background-session item is also hidden. This document owns the status strip, and this requirement is the product's single definition of the strip's responsive-elision thresholds: a document that needs to state at what width a strip item stops being shown SHALL cite this identifier rather than restating either figure. An item added to the strip is given its threshold here rather than acquiring one elsewhere.
  > **Narrowed by [`PD-SHELL-008`](../../product/directives/pd-shell-008.md#pd-shell-008), 2026-10-06.** The sandbox indicator is given
  > no threshold: it is shown at every width.

### Commands, shortcuts, palette, and keyboard help

- **REQ-SHELL-048**: The window offers one vocabulary of named actions, and every surface presents it the same way: an action that has a keyboard shortcut appears in the command palette under the same label with that shortcut shown beside it, appears in the keyboard-help dialog (REQ-SHELL-054), and appears in the composer's slash catalogue (REQ-SHELL-056). None of those surfaces offers an action the others omit, with two exceptions: the composer-only additions enumerated in REQ-SHELL-056, and the Escape overlay-dismissal entry, which is excluded from all three surfaces alike — it appears in neither the command palette, nor the keyboard-help dialog, nor the composer's slash catalogue. Escape is a contextual dismissal rather than an invocable action: it has nothing to do when there is nothing to dismiss, so listing it among things the user may choose to do would offer an action the window often cannot carry out. Its label "Close current overlay" exists to name the binding in this document, not to be presented as a command. The convention itself stays discoverable because keyboard help states it in prose (REQ-SHELL-054) and because the drawer close controls name it in their tooltip (REQ-SHELL-062). No surface presents an action the window cannot carry out. Shortcuts fire only while a Rotaris window holds keyboard focus and have no effect while another application is focused.
- **REQ-SHELL-049**: The authoritative shortcut table: Ctrl+1 … Ctrl+7 open the seven views in view order (labels "Open Overview", "Open Workspace", …); Ctrl+K opens the command palette; Ctrl+, opens Settings ("Open Settings"); Ctrl+F opens transcript search ("Search transcript"; switches to Workspace and opens the search panel); Ctrl+L focuses the run composer ("Focus run prompt"; switches to Workspace); Ctrl+Return starts or continues a run ("Start or continue run"; switches to Workspace and submits only when the send control is enabled); Ctrl+Shift+T opens the terminal window ("Open terminal"); F1 shows keyboard help ("Show keyboard help"); Escape carries the label "Close current overlay", with the scope and precedence defined in REQ-SHELL-055. "About & Legal" is a palette-only entry with no shortcut.
- **REQ-SHELL-050**: Composer key handling: Enter submits when the composer has focus; Shift+Enter adds a line break instead of submitting; Ctrl+Return is the window-wide fallback submit.
- **REQ-SHELL-051**: The command palette is an application-modal dialog titled "Rotaris commands", 560×420, accessible name "Rotaris command palette", containing a heading "Commands", a filter field (placeholder "Type an action…", accessible name "Filter commands"), and a results list (accessible name "Available commands").
- **REQ-SHELL-052**: Palette filtering is a case-folded substring match over each command's label, hidden keywords, and identifier; an empty query matches everything; the list refreshes on every keystroke; the first row is auto-selected whenever there are results; Return activates the current row; activation closes the dialog first and then runs the command.
- **REQ-SHELL-053**: Palette rows show the command label followed by its shortcut when one exists. Hidden keywords make commands findable by everyday words — e.g. the terminal command is found by "shell", "console", or "bash", but not by "worktree" — and the keywords themselves are never displayed.
- **REQ-SHELL-054**: F1 opens an informational dialog titled "Rotaris keyboard help" listing "{shortcut} — {label}" (shortcut emphasized) for every registered command that has a shortcut, excluding the Escape/overlay-dismissal entry. In place of that entry the dialog SHALL carry a short prose line conveying what Escape does and where it applies — that it closes the overlay in front, and only on the Workspace view (REQ-SHELL-055) — so the convention is discoverable without being offered as a command; the wording of that line is left to the implementation.
- **REQ-SHELL-055**: Window-level Escape is live only while the Workspace view is showing, and resolves in this order: (1) with the transcript search panel visible, the panel closes and focus returns to the composer; (2) otherwise both compact overlay drawers close and the layout reflows. On the other six views, window-level Escape produces no effect. Modal surfaces answer Escape themselves and always before the window sees it, so while any modal surface is open window-level Escape never fires. The command palette (REQ-SHELL-051) and the keyboard-help dialog (REQ-SHELL-054) close on Escape with no command run and nothing changed. Every confirmation, warning and save/discard/cancel dialog this document defines treats Escape as identical to its declining answer, carrying the same consequences that answer carries: the unsaved-settings dialog blocks the transition (REQ-SHELL-124), the kill confirmation leaves the process alone (REQ-SHELL-092), the quit prompt aborts the close (REQ-SHELL-119), and the no-credit confirmation starts no run (REQ-SHELL-158). One qualification applies throughout: where a declining answer would additionally open an external page or hand something to an external handler, Escape performs the refusal alone and does not perform the external open — dismissing a dialog never launches anything outside the application. An informational dialog whose only answer is acknowledgement closes on Escape, which acknowledges it. The indeterminate non-cancellable progress dialog of REQ-SHELL-117 does not close on Escape at all, because it has no answer to give.
- **REQ-SHELL-056**: The composer's slash-command catalogue is the one REQ-CHAT-028 to REQ-CHAT-034 define, and this document holds no copy of its membership, of the description any command carries, of the reason an unavailable command gives, or of when the catalogue is rebuilt. What this document relies on that catalogue for is that every command-palette entry of REQ-SHELL-049 is also reachable by typing, which is the third surface of the one action vocabulary REQ-SHELL-048 requires, and that a mirrored entry keeps the description, behaviour and availability gating the catalogue's own entry for that name already fixes. What this document contributes to it is the naming of a generated entry. Each generated entry — one per user-invocable skill — SHALL take its name from the skill's declared name reduced to catalogue normal form: lower-cased, each run of whitespace or underscores replaced by a single hyphen, every character outside `a`–`z`, `0`–`9` and `-` removed, and leading and trailing hyphens trimmed; a declared name that reduces to the empty string yields no entry at all. Its description SHALL be the skill's own one-line description where it declares one, and otherwise a sentence stating that the skill is available and naming it. Built-in commands SHALL always win a name collision: when a generated name equals a built-in command's name, or a generated name already accepted in the same rebuild, the entry SHALL be offered under the first free name formed by appending `-2`, `-3`, … to it, and its description SHALL additionally name the skill it came from — so a skill is never silently unreachable from the composer and a built-in command never changes meaning because a skill was installed. `/model <name>` and `/persona <name>` take their arguments from configuration and generate no additional catalogue entries.
- **REQ-SHELL-057**: Shortcuts are written with the host platform's own key names — "Ctrl" on Windows and Linux, the command symbol on macOS. A chord string is split on "+", and a trailing "++" denotes the plus key. Each key is drawn as a separate keycap in small monospace inside a hairline border, but assistive technology receives the whole written sequence as one accessible name: a three-key chord is never announced as three unrelated labels. A sequence that cannot be parsed is displayed verbatim.
- **REQ-SHELL-058**: Any element that shows a tooltip exposes that identical sentence as its accessible description, whether or not the element takes keyboard focus, with the platform-formatted shortcut appended in parentheses where the element has one. No information in the shell is available on hover alone.
- **REQ-SHELL-165**: A shortcut of REQ-SHELL-049 that the host operating system or the active input method has already claimed SHALL NOT be contested. Given a chord the host or an active IME consumes before the window sees it, when the user presses that chord, then the product SHALL take no action for it and SHALL NOT intercept, re-register, or otherwise work around the host's claim. The binding SHALL NOT be silently remapped to some other chord: a shortcut this document names is that chord or nothing. No action is lost to a claimed chord, because every shortcut-bearing action is also a command-palette entry and a slash-catalogue entry (REQ-SHELL-048), and the palette needs only Ctrl+K — or, if that too is claimed, the palette entry reachable from the composer catalogue. Where the product can determine that a chord it registered will never be delivered to it, the keyboard-help dialog (REQ-SHELL-054) and the palette row (REQ-SHELL-053) SHALL present that action with no shortcut beside it rather than presenting one that does nothing. Where it cannot determine that — the ordinary case, since hosts do not generally publish their reservations — the chord is still shown, and no notification, banner, or error is raised about it.

### Compact layout and overlay drawers

- **REQ-SHELL-059**: The Workspace view enters compact mode when its own width is below 1180 px, evaluated on every resize and once shortly after construction. In compact mode the context sidebar (agents & todos) and the inspector are removed from the docked three-pane arrangement and shown as full-height overlay drawers above the content — sidebar pinned to the left edge, inspector right-aligned — with visibility following stored drawer-open state. Above the breakpoint they re-dock (sidebar left, inspector right, center stretching), and remembered widths are re-applied once the re-docked panes have actually been shown.
- **REQ-SHELL-060**: Compact drawers are mutually exclusive: opening one closes the other. The drawer toggles are no-ops outside compact mode.
- **REQ-SHELL-061**: With the window at its 1000×680 minimum and the Workspace view showing: both overlay drawers are closed, the centre panel measures at least 850 px wide, the queued-prompts area (height capped at 150 px) and the send control are both fully visible, and activating a drawer toggle leaves exactly one drawer open.
- **REQ-SHELL-062**: Compact-only chrome: sidebar and inspector toggle buttons and drawer close buttons appear only in compact mode. Toggle labels flip between "Agents & todos"/"Hide agents & todos" and "Inspector"/"Hide inspector"; toggle accessible names are "Toggle agents and todos drawer" and "Toggle agent inspector drawer". Close buttons are "×" controls with accessible names "Close agents and todos drawer" / "Close inspector drawer" and tooltip "Close drawer (Escape)". Escape closes drawers per REQ-SHELL-055.
- **REQ-SHELL-063**: Selecting an agent while compact opens the inspector drawer and closes the sidebar drawer.
- **REQ-SHELL-064**: Default pane metrics: sidebar default/min/max width 236/180/520 px; inspector 288/220/560 px; composer pane default height 150 px. Crossing the compact breakpoint and back preserves widths the user set. At the 1000×680 minimum the view never requires horizontal scrolling, because its own minimum width stays within 1000 px.
- **REQ-SHELL-065**: At 1440×900 both side panels are visible and the center panel is at least 700 px wide. The workspace context toolbar must not clip any visible control at 1000×680 even in its busiest state (terminal count and new-output control both showing).

### Resizable panes: dividers, persistence, reset

- **REQ-SHELL-066**: Every multi-pane divider has a 6 px grab area painting a hairline, and can never collapse a pane below that pane's minimum size.
- **REQ-SHELL-067**: Divider drags persist the resulting sizes with a 250 ms debounce; sizes are also captured immediately at moments such as entering compact mode. Capture before first layout is a silent no-op (uninitialized sizes are never persisted).
- **REQ-SHELL-068**: Every divider is keyboard-operable: it takes focus, carries an accessible name beginning with "Resize " (every multi-pane view names its dividers), arrow keys move it by 16 px (left/up shrinks, right/down grows, orientation-aware, clamped at the neighbor's minimum), and Home restores that divider's declared defaults and persists them.
- **REQ-SHELL-069**: Pane layouts are remembered per user and not per workspace: opening a second workspace shows the same pane sizes as the first. They live under the `panels/` namespace of the per-user preference store, keyed by a per-view string that is stable across releases, alongside that view's pane count and one schema-version stamp covering every stored layout (currently 1). Declared defaults are restored instead of stored values whenever nothing is stored, the stored version is not 1, the stored pane count differs from the view's current pane count, or the stored state is empty. Integer values are parsed tolerantly, so a value returned as a string is accepted. Pane sizes are never written under `workspaces/`. The per-view key strings are exactly the lower-cased view names of REQ-SHELL-023 — `overview`, `workspace`, `mission`, `requirements`, `git`, `library`, `settings` — and a view carrying more than one independent multi-pane arrangement keys each of them `{view}.{arrangement}`, the arrangement part being a lower-case ASCII identifier that view declares. A key that has been used is never reassigned to a different view or arrangement: the vocabulary may gain a key and a key may be retired, but a retired key is never reused, so a stored layout written by an older release can only ever fail to match and fall back to declared defaults — it can never be applied to the wrong panes.
- **REQ-SHELL-070**: Settings offers exactly one control for this, accessible name "Reset panel sizes". Activating it takes effect immediately and asks for no confirmation: every registered divider in every view — including views not on screen at the time — is at its declared default size afterwards, and the notification "Panel sizes reset to defaults." is shown. The result outlives the process: after a relaunch every divider is still at its declared default.
- **REQ-SHELL-071**: A view whose dividers declare no default sizes still opens with a determinate split: the same view at the same window size always produces the same pane proportions, no pane opens at zero size, and no pane opens below its declared minimum. The split is computed by equal division subject to minimums, and by no other rule: the space available along the divider's axis, less the space the dividers themselves occupy, is divided equally among the panes; any pane that equal division would leave below its declared minimum is fixed at that minimum and removed from the division, and the remaining space is divided equally among the panes still free, repeating until no pane is below its minimum. Rounding of the remaining logical pixels goes to the leading panes — leftmost for a horizontal split, topmost for a vertical one — one pixel each in order, so the result is exact rather than approximate; the acceptance tolerance is one logical pixel per pane. Where the minimums together exceed the space available, every pane takes its minimum and the view is at the size below which REQ-SHELL-022 refuses to resize. Once such a divider is dragged, the dragged sizes are persisted and restored under REQ-SHELL-069 like any other.
