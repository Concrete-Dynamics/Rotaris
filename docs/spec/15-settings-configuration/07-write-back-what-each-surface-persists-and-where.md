# Settings and Configuration — Write-back: what each surface persists and where

Part 7 of 13 of [domain 15](../15-settings-configuration.md), which indexes every part. Defines REQ-CONFIG-248 – REQ-CONFIG-297.

### Write-back: what each surface persists and where

- **REQ-CONFIG-248** — The startup model-preference write path writes a scope's `agents.yaml` — `<workspace>/.rotaris/agents.yaml` for a workspace-scoped edit and the global `agents.yaml` for a global-scoped one (REQ-CONFIG-259). It bootstraps a missing file first (REQ-CONFIG-030), reads any existing document tolerantly, applies its changes, and writes atomically with the file's key order preserved and never alphabetized, leaving mode `0644`. It bootstraps whichever scope's file it is about to write, global as well as workspace, with the same starter content (REQ-CONFIG-025, REQ-CONFIG-030).
- **REQ-CONFIG-249** — That path accepts slot names from exactly this set: `default_summary_model`, `improvement_collector_model`, `gatekeeper_model`, `small_model`, `medium_model`, `large_model`, `fallback_model`. Any other name is rejected with an error naming the unknown field.
- **REQ-CONFIG-250** — Slot assignment asymmetry: a slot set to null is written as an explicit null (the slot is *set to null*, not removed), whereas a slot's reasoning companion set to null **removes the key** rather than writing null. An unknown slot name in the reasoning map is rejected naming the slot.
- **REQ-CONFIG-251** — Role overrides are written under a `personas:` mapping keyed by the **canonical** role name; any legacy alias key whose canonical name is now present is deleted, so writing preferences migrates a file still using old spellings. If the role mapping ends up empty, the `personas:` key is removed entirely.
- **REQ-CONFIG-252** — The startup-preference write touches only the slot keys, their reasoning companions and the role mapping; everything else in the file is left exactly as the file states it. **Comments and formatting are preserved.** The write is a targeted edit of the existing document rather than a re-emission of the whole of it, so a hand-authored file keeps its comment text, its blank lines and its indentation — including the comment header the first-run bootstrap wrote into the file it created (REQ-CONFIG-025), which a user would otherwise lose the first time they changed a model from the desktop. Editing models from the interface therefore costs the user nothing observable in their own file, and the earlier statement that comments and formatting are lost is withdrawn. Key order preserved and never alphabetized is REQ-CONFIG-248's rule and is unaffected by this one. **This is the discipline every writer of `agents.yaml` follows** — the startup model-preference path (REQ-CONFIG-248), the desktop save (REQ-CONFIG-256), the scoped per-field write path (REQ-CONFIG-441) and the first-run bootstrap (REQ-CONFIG-027) — and it is stated once here rather than repeated in each of them. It is the same discipline that already forbids any of them to discard content it could not interpret (REQ-CONFIG-442, REQ-CONFIG-458): a writer that preserves an unrecognized key but discarded the comment explaining it would honour the letter of that rule and defeat its purpose.
- **REQ-CONFIG-253** — Reading model preferences back for an editor resolves each slot from the **raw** file first: a raw string that is itself another slot name is followed recursively with cycle detection (a cycle yields no value); a raw string naming a concrete model is returned as-is; an absent or non-string raw value falls back to the resolved configuration with synthetic names unwrapped.
- **REQ-CONFIG-254** — A stored reasoning level of `auto` is presented under its **own** label, distinct from the label an unset level carries, so the two are always told apart on screen. "Provider default" labels the unset entry alone (REQ-CONFIG-332, REQ-CONFIG-340); a stored `auto` is appended to the control's options and shown as the current selection (REQ-CONFIG-093, REQ-CONFIG-318), and the two entries are never rendered with the same text on the same control. Reading model preferences back therefore reports a stored `auto` as `auto` and an unset level as unset, and the presentation filter never folds one into the other.
- **REQ-CONFIG-255** — Each role's preference record exposes: the raw configured model (absent when the role is not overridden), the effective resolved model with a role-level synthetic unwrapped but a slot-level synthetic left wrapped, whether the value is inherited, the built-in default model for that role so a surface can offer "back to default", and the raw reasoning value after the presentation filter. The tier names offered in place of a concrete model in a role editor are exactly `small_model`, `medium_model`, `large_model`.
- **REQ-CONFIG-256** — The desktop save path writes to `<workspace>/.rotaris/agents.yaml`. An existing file that is not a mapping is refused with an error saying so. A missing file starts from an empty document. Written keys are exactly: the five model slots (**only when the store value is non-empty**, so an empty selection leaves the existing key alone); each slot's reasoning companion (null **removes** the key); `runtime.max_depth`, `runtime.max_active_children`, `runtime.max_iterations`, `runtime.allow_outside_workspace`, `runtime.permission_mode`, `runtime.improvement_collector_enabled`, `runtime.keep_going`, `runtime.run_start_mode` (REQ-CONFIG-476), plus all six confinement/egress fields; `circuit_breaker.enabled`; `compressor.threshold_percentage`; the delegation strategy; the four `display:` fields (REQ-CONFIG-472), written per field so a `display:` key this screen does not offer is left as the file states it; `skills.enabled`, `skills.overrides` and `skills.invocation_overrides`; and workspace-scoped role values and unsets. Skill policies are written into the **workspace** file only and carry no per-field scope of their own; because `skills` is section-class and its two override maps overlay per skill name (REQ-CONFIG-042, REQ-CONFIG-048), doing so overlays exactly the skills the workspace names and **never discards the global scope's policy for any other skill**. A save is therefore not a wholesale replacement of the user's skill policy, and the only skill a workspace save can change is one the user changed on this screen (REQ-CONFIG-258).

- **REQ-CONFIG-257** — A pre-existing non-mapping value at any of the sections the desktop save writes into is **silently replaced with a fresh mapping** rather than raising.
- **REQ-CONFIG-258** — Skill maps are written **sparsely**: only skills whose load mode differs from `name-only` land in the load-override map, and only skills whose invocation mode differs from `default` land in the invocation-override map. Skill names are normalized on write. `name-only` and `default` are the implicit baselines that are never persisted — **except where a lower layer states a policy for that skill**, in which case the baseline is written out explicitly so that the choice the user made in the higher scope is what the merge produces. Omitting it there would silently leave the lower layer's override winning and make returning one skill to the baseline impossible from the screen (REQ-CONFIG-169).
  > **Extended by [`PD-WORKSPACE-002`](../../product/directives/pd-workspace-002.md#pd-workspace-002), 2026-09-21.** The same
  > sparse discipline governs the `instructions.overrides` map: only files switched to `off` land in it, and
  > an `on` that returns a file to its baseline removes that file's key — except where a lower layer states a
  > policy for that file, in which case the baseline is written explicitly.
- **REQ-CONFIG-259** — Role edits carry a per-field scope of `workspace` or `global`. The desktop save always writes the workspace file, and **additionally** writes the global `agents.yaml` when any role value or unset is scoped global. The global file is likewise refused when it is not a mapping, with an error that identifies it as the global file. After writing, the configuration is reloaded, pending unsets are cleared, and change notifications are emitted.
- **REQ-CONFIG-260** — A save is validated before any file is touched. Where the schema rejects any of the six confinement/egress values, nothing is written and the user is shown a single sentence carrying the first complaint, with framework prefixes and multi-line detail stripped out. A rejected save leaves the workspace file exactly as it was and still loadable (REQ-CONFIG-458).
- **REQ-CONFIG-463** — **Default write scope.** Where an editing surface writes configuration and the user has not chosen a scope, it writes the **workspace** scope. This holds for the desktop save (REQ-CONFIG-256), the startup model-preference path (REQ-CONFIG-248) and the scoped per-field write path (REQ-CONFIG-441). Only three things are written user-wide without asking, each because it describes the machine or the account rather than the project: desktop preferences (REQ-CONFIG-405), provider credentials and the provider catalog including endpoints added from the Models category (REQ-CONFIG-329), and theme and reduced motion (REQ-CONFIG-406). A surface that offers a scope choice — the role edit scope (REQ-CONFIG-259) and the tool-server secrets surface (REQ-MCP-110) — opens on `workspace` and writes global only when global is chosen.

### When a change takes effect

- **REQ-CONFIG-261** — **Tier A — written and reloaded immediately.** A desktop settings save re-runs the configuration load at the end, so a saved change is reflected in the loaded configuration within the same action, with no restart. The diagnostics toggle of REQ-CONFIG-471 behaves the same way and reports the new state and the scope it was written to.
- **REQ-CONFIG-262** — **Tier B — applied per run from live UI state, not from the last save.** When a run starts, the loaded configuration is copied and the settings store's **current** values are layered on top, so what a run uses is what is on screen at that moment, not whatever was last committed to the file. The dirty flag therefore governs the **file**, not the **next run**: tightening the security policy and launching a run without pressing Save still yields the tighter policy.
- **REQ-CONFIG-263** — Tier B overlays: the five model slots, **synthesizing slot-level reasoning variants on the fly** exactly as the loader does; the default role from the composer's role selector when that role exists; every role whose `model` equals either the slot name or the slot's previous value is repointed at the new slot value (first match wins); a session-wide model override that applies to the entry role only, with delegated children still running on their own configured models; a session reasoning override applied to the entry role only; a `single` delegation strategy that **strips the delegate tool from every role**; tool servers filtered to those both enabled and available in the UI, with each role's server list filtered to that set; and `runtime.max_depth`, `runtime.max_active_children`, `runtime.max_iterations`, `runtime.allow_outside_workspace`, `runtime.permission_mode`, `runtime.improvement_collector_enabled`, `runtime.keep_going` (REQ-CONFIG-469), `circuit_breaker.enabled`, `compressor.threshold_percentage` and the six security fields.
  > **Extended by [`PD-CONFIG-003`](../../product/directives/pd-config-003.md#pd-config-003), 2026-10-07 (revision 2 the same day).** Tier B
  > also overlays `runtime.child_timeout`, so the per-agent timeout on screen governs the next run start, saved or not, and
  > (revision 2) `runtime.improvement_collector_timeout`, likewise.
- **REQ-CONFIG-264** — The permission-mode overlay sets the runtime field only; per-role permission pins are deliberate configuration and are never widened by it.
- **REQ-CONFIG-265** — **Tier C — read at the next configuration load.** Everything outside tiers A and B — verification, hooks, checkpoints, requirements, transcript, project classification, model entries beyond the five slots, and tool-server definitions — takes effect when the workspace is next opened or the application is next started.
- **REQ-CONFIG-266** — Bounds on how soon a change made outside the running application is observed: a rewritten discovery snapshot is picked up once its modification time or its byte size differs (REQ-CONFIG-211); a change to the set of published desktop artifacts is reflected within **750 ms**; and the resolved per-user configuration directory is fixed for the life of the process, so a change to it takes a restart. The **published desktop artifact set** is the current workspace's artifact library — the artifacts written through `artifact_write` (REQ-CONFIG-106) and enumerated by `artifact_list`, owned by the library-and-artifacts domain — and a change to it means any addition, removal or revision of an entry in that library, whoever made it. **750 ms** is an upper bound on how long such a change may take to appear, not a polling interval; a change made inside this process appears without waiting for it.

### Settings screen: structure and navigation

- **REQ-CONFIG-267** — Settings is a full view inside the application's navigation, not a modal dialog. Leaving it is therefore a navigation event, and the unsaved-changes guard lives in the navigation path rather than in a dialog dismissal.
- **REQ-CONFIG-268** — The screen presents categories in exactly this order: Models, Personas, Runtime, Interface, Display, Skills, Instructions, Hooks, MCP Servers, Plugins, Tools, Project, About. The first eleven are the configuration categories; Project (initialization) and About (about and legal) complete the bar.
- **REQ-CONFIG-269** — The category identifiers are exactly `models`, `personas`, `runtime`, `interface`, `display`, `skills`, `instructions`, `hooks`, `mcp`, `plugins`, `tools`, `project`, `about`, in the order the categories are presented (REQ-CONFIG-268). The identifier is the value persisted under `interface/settingsTab` (REQ-CONFIG-405). The vocabulary may gain a value, and a value may be retired, but a value that has been used is never reassigned to a different category (REQ-CONFIG-459). An identifier that is not in the list — retired, unknown or absent — selects `models` (REQ-CONFIG-271).
- **REQ-CONFIG-270** — Save, Discard and the save-status indicator are visible and operable from every category: no category's own content can push them out of view, and each acts on the whole set of pending settings changes rather than on the category currently displayed.
- **REQ-CONFIG-271** — The selected category persists as a **user-wide** preference (not per workspace). On restart the last valid category is restored; a missing, stale or unknown identifier falls back to **Models**.
- **REQ-CONFIG-272** — Requesting a category by identifier returns the identifier actually selected. Requesting an unknown identifier selects Models and returns `models` rather than raising, which is what makes deep links from elsewhere in the application safe.
- **REQ-CONFIG-273** — Reading the current category with nothing selected yields `models`. A category-changed notification is emitted only for a real selection.
- **REQ-CONFIG-274** — At the minimum window size, which is REQ-SHELL-022's and is not restated here, every category's content can be reached by vertical scrolling alone, and no category requires horizontal scrolling at that size. What this requirement relies on that one for is a single figure the whole product is measured against, so a change to it can never leave one screen checked at one size and another at a different one.
- **REQ-CONFIG-275** — The skill policy controls, the tool-server enablement controls and the Instructions, Plugins and Tools inventories are reachable from Settings and from no other view of the application.
- **REQ-CONFIG-276** — Four categories are read-only inventories rendering the same three columns — Name, Source, Description — with an explanatory empty state shown instead of an empty table: Instructions, Hooks, Plugins and Tools. As shipped, Hooks has grown past that shape into a dedicated surface with a column set of its own plus a trust verdict (REQ-CONFIG-354), which leaves three generic inventories.

  > is no longer one of the read-only three: it renders a fourth column carrying a per-file on/off switch, so
  > two generic inventories remain — Plugins and Tools. Its empty state is unchanged. The text above states
  > the behavioural target and is kept for that reason.
- **REQ-CONFIG-277** — Inventory contents: **Instructions** lists the workspace's `AGENTS.md` and `AGENTS.override.md` when present, source `workspace`, each described by its **absolute path**. **Plugins** lists every file under `<workspace>/.rotaris/plugins` that the host process can load as a plugin module, in sorted file-name order, source `workspace`, again described by absolute path. What a plugin file is, and which files that folder listing therefore reaches, is REQ-TOOLS-161's and REQ-TOOLS-165's; this document holds no second definition and fixes no file extension, language or packaging form for them. **Tools** lists the friendly tool names from the tool-name map, sorted by name, source `built-in`, with the implementing type name as description. Tools is populated **unconditionally**, including with no workspace; Instructions and Plugins are empty without one.

- **REQ-CONFIG-278** — With no workspace configured, the screen still constructs without error and the workspace-derived inventories show their empty states.

### Settings screen: save, discard and dirty state

- **REQ-CONFIG-279** — The screen's outward contract is a set of intent notifications, not file writes: it signals that a save was requested, that a discard was requested, and that each immediately-applied preference changed. The host commits; the screen never names a file.
- **REQ-CONFIG-280** — The save-status indicator reads as settled when clean and as having unsaved changes when dirty, and carries an accessible name identifying it as the settings save status. The dirty state is conveyed **in words**; colour only reinforces it, using a text-contrast colour step rather than a saturated one.
- **REQ-CONFIG-281** — Save is offered only while the form is dirty and a configuration service is present; Discard is offered whenever the form is dirty. With no configuration service a dirty form can therefore be discarded but never saved. A save nevertheless executed after the service has gone away produces the read-only notice of REQ-CONFIG-283 and writes nothing. In that state the unsaved-changes guard drops Save entirely and offers Discard and Cancel with Cancel as the default (REQ-CONFIG-286), so the guard never presents a Save that cannot succeed and the user is always left a way to leave the screen.
- **REQ-CONFIG-282** — Both actions notify unconditionally on click; the screen itself neither confirms nor debounces, and has no Cancel button of its own.
- **REQ-CONFIG-283** — Save has exactly three outcomes: with no configuration service, an error notice stating settings are read-only in the current mode and no write; on a write or validation failure, a reported error titled as a save failure carrying the exception text and offering a **Retry** action, with the form left dirty; on success, the dirty flag is cleared (returning the indicator to settled and disabling both buttons) and a success notice is shown.
- **REQ-CONFIG-284** — The save handler catches **every** failure; none propagates out of it. An I/O failure and a validation failure are reported with the detail that kind of failure carries; a failure of any other kind is reported through the same save-failure path, stating that the save did not complete and carrying the underlying detail unaltered. In all three cases the outcome is the failure outcome of REQ-CONFIG-283 — the form is left dirty, a Retry action is offered, and the screen stays usable. No failure inside a save is allowed to leave Settings in a state the user cannot act on.
- **REQ-CONFIG-285** — Discard restores **the last saved values**, not the values at the start of the session, and is unconditional — no confirmation of its own.
- **REQ-CONFIG-286** — The unsaved-changes guard returns immediately when the form is clean. Otherwise it asks whether to save before leaving and offers three buttons in the order Save, Discard, Cancel with **Save as the default**. Save runs the save and yields its success flag — **so a failed save keeps the user in Settings**; Discard discards and proceeds; Cancel stays. A dismissal that is neither answered nor cancelled proceeds. The guard's text must convey that discarding restores the last saved values of the workspace configuration and that it does **not** undo desktop preferences, hook policy, provider changes, or theme and reduced motion (REQ-CONFIG-418); the wording is left to the implementation. **With no configuration service present** the guard offers two buttons only, Discard and Cancel, with **Cancel as the default**, and its text additionally conveys that settings are read-only in the current mode so the pending changes cannot be saved (REQ-CONFIG-281). A Save that cannot succeed is never offered as a button, and never as the default.
- **REQ-CONFIG-287** — The guard fires at exactly three moments: when navigating away from Settings to a different view while dirty (Settings-to-Settings navigation is free); before the project/workspace chooser opens, ahead of any active-run checks; and on a **user-initiated** window close only — a programmatic close does not prompt, and a cancelled guard leaves the window open. At close time the unsaved-settings prompt precedes any integration-in-progress prompt. A cancelled guard changes nothing about work already in flight: a provider probe or health check running when the guard fires keeps running, and its result lands on the still-open screen through the ordinary completion path (REQ-CONFIG-373, REQ-CONFIG-376). The guard neither cancels nor waits for such an operation, and a result arriving after the screen has gone is handled by REQ-CONFIG-374.
- **REQ-CONFIG-288** — **The composer's permission-mode control writes only its own key, and commits nothing else.** The decision this requirement previously handed over is taken here rather than left open, and it is taken against the coupling: the save path of REQ-CONFIG-283 is **not** shared with that control, and choosing a permission mode in the composer no longer commits every other pending Settings edit. The control writes the single permission-mode key through the scoped per-field write path (REQ-CONFIG-441), which overlays only the key it names and leaves every other key in that scope's file exactly as the file states it (REQ-CONFIG-443), into the scope of REQ-CONFIG-463, refusing the write outright if the target file cannot be read (REQ-CONFIG-442); it then reloads, so the new mode is in force without a restart (REQ-CONFIG-261) and still writes and applies immediately (REQ-CONFIG-328). Every pending Settings edit stays pending, stays dirty, and is still undone by Discard. **Why the coupling is refused rather than preserved:** the surprise landed in a security-relevant control, and a user who narrows or widens one run's permission mode has not asked for unrelated, half-finished configuration edits to be written to disk as a side effect — least of all the confinement and egress fields the same screen edits (REQ-CONFIG-289). Nothing here narrows REQ-CONFIG-418: the composer's control does not defer to Save, so it does not participate in Save and Discard, exactly as the diagnostics toggle of REQ-CONFIG-471 does not; and nothing here weakens REQ-CONFIG-423, which continues to require the settings screen to show the mode actually in force.

### Settings screen: validated list editors

- **REQ-CONFIG-289** — Three security controls use one reusable validated add/remove list editor: confinement writable roots, egress allowed hosts, egress denied hosts. Each editor shows a title, a word-wrapped explanatory hint, a bounded-height list, an entry field with Add and Remove actions, and a hidden problem line.
- **REQ-CONFIG-290** — **Nothing invalid reaches the store.** Every value is checked by the control that produced it, so an assignment-time schema rejection is never the first the user hears of a problem they could have been told about at the field they typed into.
- **REQ-CONFIG-291** — A refusal is rendered as a sentence beginning with a refusal marker and carrying the reason **in words**; colour only reinforces it, using the text-contrast colour step. The same sentence is exposed as the control's accessible description. The problem line is hidden again on any successful add or remove, and on any programmatic repopulation.
- **REQ-CONFIG-292** — Normalization runs **before** the duplicate check, so two spellings that normalize to the same entry collide and the second is refused with a message naming the value as already listed.
- **REQ-CONFIG-293** — Remove is disabled while nothing is selected, and both its tooltip and its accessible description state the reason, switching between "removes the selected entry" and "select an entry first". Availability is recomputed on every selection change and after every mutation. Pressing Remove with nothing selected still produces an explanatory refusal. Removal deletes **every** selected row.
- **REQ-CONFIG-294** — Pressing Enter in an editor's entry field performs the same add as the Add action. An accepted value empties the field; a refused value leaves the typed text in the field exactly as it was typed.
- **REQ-CONFIG-295** — Repopulating an editor from stored values must not emit a change: the editor returns early when the incoming list already equals the current one, and otherwise suppresses change notifications across the repopulation. Were a reload to emit, Settings would turn dirty and the following save would persist precisely the values it had only just loaded.
- **REQ-CONFIG-296** — The empty-state message is shown exactly when the list is empty, recomputed after construction and after every mutation, so an editor emptied by removal returns to its empty state without a rebuild.
- **REQ-CONFIG-297** — A refused entry leaves the form **clean**: a refusal is not a change. Adding a relative writable root must leave the list empty, the stored list empty, and the dirty flag false; the same holds for a refused host pattern.
