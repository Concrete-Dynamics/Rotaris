> **Retired — not part of the product.** The product owner scoped the product to a single Electron

## Overview

Rotaris provides a full-screen interactive terminal user interface (TUI) launched from the CLI when no task argument is given (or when a task is given without the background flag). The TUI presents a live agent-run experience: a scrolling transcript with streaming model output, an input composer with slash commands and prompt history, a right-hand rail showing agent tree status, session/model information, and todo progress, plus modal screens for settings, model selection, session management, search, and artifact editing. All user-visible state (sessions, transcript archive, prompt history, stash, toggles) persists to well-defined files so sessions can be resumed after exit.

## Requirements

### 1. Launch and startup

- **REQ-TUI-001** — Given the CLI `run` command is invoked with no task argument, the interactive TUI starts. Given a task argument without the background flag, the task executes inside the interactive TUI.
- **REQ-TUI-002** — The `run` command accepts at least these options with these observable semantics: an optional positional task; `--background`/`-b`; `--workspace`/`-w` (default: current working directory, resolved to an absolute path); `--session`/`-s` (continue an existing session by id); `--isolate` (create a dedicated git worktree for the new session); `--worktree <path>` (attach the new session to an existing git worktree); `--worktree-branch <name>` (branch name used by `--isolate`; when omitted the branch name is derived from the session id); `--config`/`-c` (a config file whose contents merge over the loaded configuration); `--persona`/`-p` (overrides the configured default persona); `--max-iterations <n>` (overrides the configured `runtime.max_iterations` cap); `--unsafe-outside-workspace` (permits writes outside the workspace); `--output-format` accepting `text` (default) or `stream-json`; `--logout <provider>` (clears the provider's stored credentials while leaving its configuration in place, then exits without starting the TUI).
- **REQ-TUI-003** — `--output-format` admits exactly two values, `text` and `stream-json`. With `text`, the default, stdout carries human-readable progress. With `stream-json`, every line written to stdout is one complete JSON object and stdout carries nothing else; diagnostics, warnings, and errors are written to stderr. A value outside that pair is refused: stderr receives a message naming both the value supplied and the two permitted values, and the process exits with code 2. Requesting `stream-json` without a task argument is likewise refused with exit code 2 and the message "Error: --output-format stream-json requires a task; it cannot start the interactive TUI." Given a task argument, `stream-json` executes it in background mode with or without `--background`, so the interactive TUI is never presented under this format.
- **REQ-TUI-004** — Given any worktree/isolation option without both a task and background mode, the command prints "Worktree session options require a task with --background." and exits with code 1.
- **REQ-TUI-005** — Given configuration cannot be loaded at startup, the launcher makes at most one automatic recovery attempt and then loads configuration once more, so a single invocation attempts the load at most twice in total. If configuration is still unusable after the second attempt, every collected error message is written to stderr on its own line prefixed `Config error: `, nothing is written to stdout, and the process exits with code 1 without starting the TUI. The automatic recovery attempt is made only where every collected failure is that a configuration artifact the launcher owns is absent — the workspace `.rotaris/` directory, the workspace `agents.yaml`, or the global `agents.yaml`: recovery creates the missing artifacts with the defaults this document specifies and then reloads. A configuration file that is present but cannot be parsed, and one that loads and then fails validation, is never rewritten and triggers no recovery attempt, so those invocations load exactly once. Where recovery ran, one line per artifact created is written to stderr before the reload, so the repair is user-visible even when the second attempt then succeeds.
- **REQ-TUI-006** — Given configuration validation reports that no models are configured (and the invocation is interactive, not background), the launcher prints "No models configured. Launching 'rotaris-cli login' to set up a provider..." and runs the provider login flow inline; if login fails, the process exits with code 1 after printing the login error.
- **REQ-TUI-007** — Given remaining validation errors reference an unknown model (interactive invocation), the launcher prints the errors plus a notice that a startup model editor is launching, then starts the TUI with the startup-models repair modal already open over the main screen.
- **REQ-TUI-008** — Onboarding review: when the raw workspace configuration file has all six startup model slots unset (small, medium, large, default-summary, fallback, improvement-collector) while the resolved configuration has at least one set (i.e., an automatic login populated a model snapshot only), the TUI opens the startup-models screen BEFORE the main screen; the main screen appears only after that modal closes.
- **REQ-TUI-009** — Where startup finds the configuration valid and needs no repair screen, the first surface a user sees is the main screen with nothing layered over it; the only notification raised by startup itself is the invalid-leader warning of REQ-TUI-028, and only where the configured leader value was refused. The provider health check of REQ-TUI-010 delays neither that first paint nor the acceptance of keystrokes: a prompt may be typed and submitted before the check reports, and its warning appears whenever it arrives. Time-driven display — animation frames, elapsed and countdown values, and expiry of an open leader-chord window — keeps advancing with no keyboard or mouse activity, at the cadences of REQ-TUI-206.
- **REQ-TUI-010** — The startup health check examines the providers referenced by the configured models. However many problems it finds, at most one warning toast is raised per startup; that toast carries the surfaced problem's message and has a 12 s lifetime, and the remaining problems raise no toast. Where the surfaced problem is one the user can correct by entering an API key, the provider settings screen (REQ-TUI-169) for that provider opens without being asked for, and at most one such screen opens by itself per startup. A problem is one the user can correct by entering an API key — and therefore auto-opens the screen — in exactly these cases: a provider referenced by a configured model has no stored credential; the stored credential was refused by the provider as invalid, revoked, or expired; or the provider's configuration leaves a required connection value (key or base URL) unset. Every other problem raises the toast alone and opens nothing, including network failures and timeouts, quota and rate-limit conditions, an unknown or unavailable model id, and a provider whose sign-in is an interactive login flow rather than a key. Where several problems are found, the one surfaced is chosen deterministically: problems of error severity rank ahead of problems of warning severity; within a severity, problems rank by the startup model slot whose model referenced the provider, in the slot order given in REQ-TUI-008; a remaining tie is broken by provider name in ascending code-point order. The first problem in that order supplies the toast message and is the only one that may auto-open the screen.
- **REQ-TUI-011** — While the TUI runs, an interrupt (Ctrl+C, or SIGINT delivered to the process) is resolved by the precedence of REQ-TUI-033; where neither the pending-chord branch nor the copy-selection branch applies, it is a graceful quit request and follows REQ-TUI-128: the first such request asks the active run to stop and arms the force deadline, and a second request inside that window force-quits. A SIGINT that reaches the process other than as a Ctrl+C key press — from `kill -INT`, from a process-group signal, or from any other external source — is always a graceful quit request attributed to "SIGINT": the pending-chord and copy-selection branches of REQ-TUI-033 depend on keyboard state and therefore apply only to the key press. After the TUI exits, interrupt handling behaves as it did before the TUI started, so a subsequent Ctrl+C in the same shell has its usual effect.
- **REQ-TUI-012** — The CLI `sessions` subcommand writes one line per known session to stdout as `<session_id>  <updated_at>  <schema_version>  <status>`, with ` (stale)` appended to the line of any session judged stale. A session is judged stale exactly when its recorded status is one that implies a live owner — `running`, `waiting`, or `background` — while no live process holds that session's lock. With `--repair` it additionally rewrites every stale session to status `interrupted` (a full member of the execution-status vocabulary of REQ-TUI-124) before printing, so the listing shows the repaired status; the repair report is written to stderr, leaving stdout a pure listing, as one line per changed session naming that session's id and its new status followed by one line giving the number of sessions changed. The `version` subcommand prints exactly `Rotaris <version>`. The `logout [provider]` subcommand reports three distinguishable outcomes — credentials deleted, nothing stored to delete, deletion refused — exiting 0 for the first two, 2 when the named provider is not a known provider, and 1 when the operating system refused the deletion.
- **REQ-TUI-013** — Every CLI subcommand except `setup` and `version` performs first-run environment preparation before its own work. All preparation output goes to stderr, so stdout stays exactly as specified for that subcommand (`stream-json` lines, session listings, version text) whether or not preparation ran. Once preparation has completed successfully, later invocations write no preparation output to either stream. Preparation performs exactly these steps, each skipped when its result already exists: create the global configuration directory; create a global `agents.yaml` holding the documented defaults; create the workspace `.rotaris/` directory and its `sessions/` subdirectory. Preparation keeps no separate marker or state file: a later invocation determines that preparation has already run by finding each of those artifacts present, and therefore performs and prints nothing. Preparation never overwrites, rewrites, or migrates the contents of an artifact that already exists.

### 2. Application shell and layout

- **REQ-TUI-014** — The application window title is "Rotaris". The default notification (toast) lifetime is 8 seconds.
- **REQ-TUI-015** — The main screen is composed of: a one-row top bar docked at the top; a two-column body whose left column holds the transcript view, the input composer, and a run spinner, and whose right rail stacks an agents panel, an info panel, a todo panel, and a one-row status bar; and a bottom key-hint footer row.
- **REQ-TUI-016** — Column proportions are left:right = 7:3. Right-rail vertical proportions are agents:info:todo = 3:2:2. Both ratios are fixed: neither is configurable, and no alternative proportion is offered.
- **REQ-TUI-017** — Each right-rail panel scrolls vertically and independently; scrolling one panel never scrolls another. The status bar occupies exactly one row and has no border.
- **REQ-TUI-018** — At startup, before any session exists, an initial refresh populates the info panel from configuration (MCP server availability and the full tool list are visible pre-session).
- **REQ-TUI-019** — Given a submission — normal or steering — while no session and no configuration are available: no run starts, the submitted text is still recorded as a `user` transcript event, the composer clears as for any accepted submission, a toast of warning severity with the default lifetime of REQ-TUI-014 states that there is no active session and names both ways to create one (the palette entry "New session" and the `/new` command), and the system transcript line "No active session — message recorded in transcript only." is appended below the user event.
- **REQ-TUI-020** — Input routing: a normal submission while a run is active is queued for the next iteration; while idle it echoes the user message to the transcript and starts a new run. A steering submission while a run is active is delivered as steering; while idle it starts a run.
- **REQ-TUI-021** — A copy action with an active text selection copies the selection to the clipboard, clears the selection, and notifies "Copied to clipboard" (1.5 s) on success or a platform-specific failure message (warning, 3 s); with nothing selected the action is a no-op.
- **REQ-TUI-022** — Each completed run produces exactly one run-completed toast. Its body is the same summary text that REQ-TUI-120 appends as a system transcript event, and its severity is the severity carried by that summary. That severity follows from the execution status the run completed with, by this total mapping over the vocabulary of REQ-TUI-124: `idle` and `background` carry information severity; `paused`, `paused_message_limit`, `stopped`, `waiting`, and `interrupted` carry warning severity; `failed` carries error severity. The toast lifetime is the default of REQ-TUI-014, except that an error-severity run-completed toast lasts 10 s.
- **REQ-TUI-023** — The run spinner uses the 10-frame braille cycle `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` ticking at 0.1 s, is active only while the session execution status is "running", renders the frame plus the label "running" (plus ` (<session_id>)` when known) with a bold-green spinner and dim label, and performs no refreshes while idle.

### 3. Theming

- **REQ-TUI-024** — Exactly three built-in themes exist: `mono`, `tokyo-night`, and `dark`. The default theme is `mono`, which uses a pure-black (#000000) background. Selecting an unknown theme name is an error that reports the unknown name and lists the available names.
- **REQ-TUI-025** — Every theme supplies a value for each semantic color role, and the role set is identical across themes: background roles (base, overlay, selection, toast), foreground roles (normal, muted, dim, subtle), border roles (normal, input, focus, active), and the named accents this document uses (green, cyan, yellow, blue, red, purple). No role may be left unset, so every rendered element draws its colors from the active theme. After a theme switch, every visible surface uses the values of the newly selected theme, and none retains a value that belongs only to the previous theme. Every built-in theme meets a measurable contrast floor, stated as the WCAG 2.1 relative contrast ratio between a value and the background role it is drawn over: the normal foreground role and every named accent used to draw text reach at least 4.5:1 over the base, overlay, selection, and toast backgrounds they may appear on; the muted, dim, and subtle foreground roles reach at least 3.0:1 over those same backgrounds; and every border role, and every glyph that carries state meaning on its own, reaches at least 3.0:1 over the background behind it. A palette that misses any of those floors is not a valid built-in theme.
- **REQ-TUI-026** — Themes are switchable at runtime via `/theme <name>` and via palette entries labeled `Theme: <name>`; a successful switch restyles immediately and notifies `Theme: <name>`; an invalid name notifies the error text.
- **REQ-TUI-027** — `/theme` with no argument produces the error "Usage: /theme <name>. Available: mono, tokyo-night, dark". Theme names are matched case-insensitively (input is lower-cased).

### 4. Keyboard model: leader chords, global keys, quit

- **REQ-TUI-028** — The leader key is configurable via the `tui.keyboard.leader` configuration key, default `Ctrl+X`. Accepted forms: `esc`/`escape` (normalized to `Esc`) and `ctrl+<letter>` (normalized to `Ctrl+<UPPERCASE>`). Any other value falls back to `Ctrl+X` and a warning toast (6 s) "Invalid tui.keyboard.leader '<raw>'; using Ctrl+X." shows at startup.
- **REQ-TUI-029** — Leader chords: `p` opens the command palette; `m` opens runtime model selection; `q` quits gracefully; `s` stashes composer input or saves the active editor/screen; `r` toggles reasoning visibility; `e` toggles the multiline composer; `/` opens transcript search; `?` opens help. Chords display as e.g. `Ctrl+X P` (second key upper-cased except `?` and `/`).
- **REQ-TUI-030** — Pressing the leader key opens a chord window lasting 5.0 s and takes keyboard focus away from whatever held it. While the window is open: no keystroke reaches the composer or any other widget, so nothing typed during the window appears in the input; the composer meta bar shows yellow hints listing every chord mnemonic of REQ-TUI-029 and `esc:dismiss`; Escape or Ctrl+C closes the window with no other effect; a key matching a chord mnemonic closes the window and performs that chord; and any other key closes the window and does nothing else. With no key pressed, the window closes by itself once 5.0 s have elapsed, silently. However the window closes, the yellow hints disappear and input focus returns to the composer input.
- **REQ-TUI-031** — Inside an open chord window, a mnemonic pressed with Ctrl held performs the same chord as the bare key, so leader then Ctrl+S performs the `s` chord; the upper- and lower-case forms of a mnemonic letter perform the same chord. The `?` mnemonic is recognised however the terminal reports the question-mark key, including when it arrives as a shifted `/`. Modifiers are ignored entirely when matching a chord: any combination of Ctrl, Alt, Shift, and Meta held with a mnemonic performs that mnemonic's chord, and only a keystroke whose base character is not a mnemonic falls to the "any other key" rule of REQ-TUI-030.
- **REQ-TUI-032** — Bindings available on the main screen: the `q` key, in either case, force-quits (shown in the footer as "Force Quit"); Ctrl+Down/Up/Right/Left move agent focus to child/parent/next sibling/previous sibling; Alt+Down/Up move artifact focus to the next/previous artifact; Alt+Right enters the artifact inspector and Alt+Left leaves it. A screen or modal that defines its own meaning for one of these keys wins while it is open — for example the `q` key closes the help screen instead of quitting (REQ-TUI-036) — and a key typed into a text-entry field inserts its character rather than triggering the binding, so typing `q` into the composer never quits. The agent-focus keys additionally act while the composer holds focus (REQ-TUI-177), and the artifact keys likewise act while the composer holds focus (REQ-TUI-180).
- **REQ-TUI-033** — Ctrl+C precedence: (a) if a leader chord is pending, cancel only the pending state; (b) else if text is selected anywhere on screen, copy it (with the success/failure toasts of REQ-TUI-021); (c) else treat as a graceful quit request attributed to "Ctrl+C". Branches (a) and (b) apply only to Ctrl+C arriving as a key press; an interrupt arriving as a signal goes directly to branch (c) per REQ-TUI-011.
- **REQ-TUI-034** — A single press of `q` is an immediate force quit with no grace period: MCP connections are shut down, the run is force-interrupted, the visible activity text becomes "Force quitting...", and the process exits with code 130.
- **REQ-TUI-035** — Escape while the artifact inspector is open exits the inspector, with a discard confirmation when the editor has unsaved changes.
- **REQ-TUI-036** — The help screen (leader `?` or `/help`) is titled "Keyboard Shortcuts and Slash Commands". It shows a `Leader: <leader>` line, one line per leader chord with that chord's description, then a "Slash commands" section containing one `/<name>  <description>` line for each built-in command of REQ-TUI-047 and REQ-TUI-054, quoting those descriptions verbatim. Escape or the `q` key (in either case, displayed as `Q` in hints per the chord convention of REQ-TUI-029) closes the screen and returns to the main screen; while the help screen is open, that key does not force-quit. The footer hint reads "Esc or Q closes". Below the built-in section, and only where at least one such command is registered, the screen shows a separately headed section listing the commands registered at runtime from discovered skills and custom prompt files (REQ-TUI-054, REQ-TUI-055) in the same `/<name>  <description>` form, quoting each command's registered description; the two headings make a built-in command distinguishable from a registered one. Built-in commands are listed in the order of REQ-TUI-047 and registered commands in the order they were registered.

### 5. Input composer

- **REQ-TUI-037** — The composer consists of a one-line meta bar, a single-line input, a hidden multiline editor, and a slash-command overlay. Its border title is " prompt " and its border subtitle shows the application version as ` v<version> `.
- **REQ-TUI-038** — The input placeholder initially reads "Describe the next task... (Enter sends)" and, once running inside the full application, "Describe the next task... (Enter sends, <leader chord E> toggles multiline)".
- **REQ-TUI-039** — Composer modes: inline (default; Enter submits) and multiline (Ctrl+J submits; Ctrl+Enter submits as steering). Toggling multiline→inline collapses newlines to spaces; inline→multiline carries the text over. Submitting from multiline clears the editor and returns to inline mode. The toggle is reachable via leader `e` and a clickable "toggle" meta-bar segment.
- **REQ-TUI-040** — Composer key bindings: Ctrl+Enter submits the current text as steering (works even while other bindings compete); Up/Down navigate prompt history.
- **REQ-TUI-041** — Submission handling: text that is empty or whitespace-only is ignored and nothing is submitted. Text beginning with `/` is offered to the slash-command registry first. Where a registered command claims it, that command runs, and the typed text itself is neither submitted to the agent as a prompt nor added to prompt history — although the command may, as its own effect, send content of its own to the agent (REQ-TUI-054, REQ-TUI-055). The composer clears once the command has run without raising; where the command handler raises, the toast "Error executing command: <error>" appears and the composer retains the text exactly as typed. Text beginning with `/` that no registered command claims is treated as ordinary prompt text (REQ-TUI-046). Ordinary text is added to prompt history, submitted as a normal or steering prompt according to the key used, and the composer clears.
- **REQ-TUI-042** — The composer meta bar carries these segments, left to right. (1) A status segment reading `$ <state>  mode <inline|multiline>  send <enter|ctrl+j>`, where `<state>` is the session's current execution status drawn from the vocabulary of REQ-TUI-124 — `idle`, and the pre-session condition in which no session exists yet, both render as `ready`, and every other status renders as its own name — extended with `steer ctrl+enter` while a run is active, and replaced by the yellow leader hints of REQ-TUI-030 while a chord window is open. (2) A `toggle <chord>` segment; clicking it switches composer mode. (3) A model segment showing the active model key in blue followed by ` thinking` in purple when that model has thinking enabled, or the text `no model` in the subtle style when no model is active, then `swap <chord M>`; clicking it opens the runtime model picker. (4) A stash segment reading `stash(<n>)` in blue when the stash holds entries and a dim `stash` when it is empty, followed by its chord; clicking it stashes the composer contents. (5) `⏱ <elapsed>` whenever the run timer has a displayable value per REQ-TUI-114, and nothing at all when it does not. (6) A `settings <chord P>` segment; clicking it opens the command palette. No segment other than these six appears, and every chord rendered here reflects the configured leader key.
- **REQ-TUI-043** — Prompt history is a FIFO ring of capacity 50 with shell-style cursor semantics: index 0 is oldest; the cursor position one past the newest means "unsent" (empty field). Appending ignores blank/whitespace-only text, evicts the oldest entry beyond capacity, resets the cursor to unsent, and persists. Previous navigation walks older entries and clamps at the oldest; next walks newer and yields the empty string at the unsent position; previous on an empty history leaves the field untouched.
- **REQ-TUI-044** — History persists as a JSON array at `<workspace>/.rotaris/prompt_history.json`, written atomically (temp file then rename). On load, entries beyond the newest 50 are discarded; corrupt or non-array JSON loads as empty history with a logged warning. Without a workspace configuration there is no history file and history is session-only.
- **REQ-TUI-045** — After history navigation in inline mode the caret moves to the end of the field.

### 6. Slash commands

- **REQ-TUI-046** — Dispatch splits the submitted text at the first run of whitespace after the leading `/`: the command name is the characters between that `/` and the first whitespace character (or the end of the text when there is none), and the argument string is everything following that whitespace run. Names are compared ignoring case. Apart from that separation the argument string is passed on unchanged, so its internal spacing and quoting survive and any number of spaces may sit between the name and the arguments. A bare `/`, and any name for which no command is registered, is not dispatched; such text is handled as an ordinary prompt per REQ-TUI-041.
- **REQ-TUI-047** — The built-in command set (each with the listed description and effect): `/stop` "Stop the current run"; `/pause` "Pause the current run"; `/resume` "Resume a previous session" (opens the session picker); `/new` "Start a new session"; `/mcp` "Open MCP server management"; `/improvements` "Review post-run improvement proposals"; `/tools` "Toggle tool events visibility"; `/background` "Send session to background"; `/stash` "Stash current input"; `/pop` "Pop stashed input"; `/theme <name>` "Switch theme (usage: /theme <name>)"; `/logout <provider>` "Sign out of an auth provider (usage: /logout <provider>)"; `/compress` "Force context compression for all running agents"; `/help` "Show slash commands and leader shortcuts"; `/model` "Open runtime model selection"; `/quit` "Quit the application gracefully"; `/clear` "Clear the transcript (confirmation required)"; `/cancel` "Cancel the active modal or generation"; `/search` "Search the transcript"; plus the two skill commands `/skills` and `/skill` specified in REQ-TUI-054 with the descriptions given there. Invoking a built-in command produces the effect described by the requirement that specifies it. Commands registered from discovered skills and from custom prompt files (REQ-TUI-054, REQ-TUI-055) are registered at runtime and are not part of this built-in set.
- **REQ-TUI-048** — `/logout` with an empty argument reports the error "Usage: /logout <provider>. Example: /logout openai-compatible--my-label".
- **REQ-TUI-049** — `/cancel` resolves by context: the message-limit modal cancels; the quota-wait modal resolves as "keep waiting"; the discard-artifact-edits modal cancels; any other non-main screen is dismissed; on the main screen with no active run it warns "Nothing active to cancel."; with an active run it stops the run.
- **REQ-TUI-050** — Clearing the transcript demands two invocations of `/clear`. Against an empty transcript the command warns "No transcript to clear." and alters nothing. Against a non-empty transcript, the first invocation warns "Run /clear again within 5s to clear the transcript." and opens a 5.0 s confirmation window. A second `/clear` inside that window leaves the transcript showing nothing whatever — no event, no streaming preview, no tool entry still in progress — records the emptied transcript with the session so a later load of that session also shows nothing, and notifies "Transcript cleared." Where 5.0 s pass without a second invocation, the next `/clear` counts as a first invocation again.
- **REQ-TUI-051** — `/search` warns "No active session to search." when no session exists and "Transcript is empty — nothing to search." when the transcript is empty; otherwise it opens the transcript-search modal.
- **REQ-TUI-052** — Slash autocomplete: while the inline input holds a single `/`-prefixed token with no whitespace, an overlay (docked at the bottom, width 40, bordered) lists `/name  description` rows filtered live by case-insensitive substring on name or description. The overlay never takes input focus. Up/Down move the highlight; Tab/Enter/Right select; Escape hides; Backspace edits the filter (an emptied filter hides the overlay). Selecting writes `/<name>` into the input with the caret at the end. Enter while the overlay is visible selects the highlighted command instead of submitting the prompt.
- **REQ-TUI-053** — An inline suggester shows `/<first-match> - <description>` as a completion hint while typing a single slash token; it is suppressed for `/ ` and once whitespace appears.
- **REQ-TUI-054** — Skill commands. `/skills` ("List discovered SKILL.md files") appends one system transcript message in which each discovered skill contributes a line `- <name> [<scope>] in_context=yes|no triggers=/x,/y`, a single-line description truncated to at most 120 characters with a trailing `...` when truncated, and the skill file's path. `in_context=yes` means that skill's body has already been injected into the current session; otherwise `no`. The command then notifies "Listed N skill(s)." with N the number listed. When nothing was discovered it appends no transcript message and notifies "No SKILL.md files discovered." `/skill <path>` ("Load a SKILL.md for this session") with an empty argument reports "Usage: /skill <path-to-SKILL.md-or-directory>" and loads nothing; the path may name a SKILL.md file or a directory containing one; one enclosing pair of single or double quotes is stripped before the path is used; a path that fails validation reports the validation error text and loads nothing. Every cataloged skill also gets a slash command under its name normalized by the rule of REQ-TUI-055, and under each of its declared `/keyword` triggers that no other command already owns. Invoking such a command sends the skill body to the agent as a steering prompt shaped `[SKILL.md]\nName: …\nSource: …\n\n<body>` and marks that skill in-context. Discovery walks exactly two roots, in this order: the workspace root `<workspace>/.rotaris/skills/`, then the user root `<global config dir>/skills/`; each is walked recursively and every `SKILL.md` found beneath it is cataloged. Where two cataloged skills normalize to the same command name, the one discovered first owns the command and the later one registers none, though both are still listed by `/skills`. The `<scope>` value is one of exactly three words: `project` for a skill found under the workspace root, `user` for one found under the user root, and `session` for one loaded by `/skill <path>` from a location under neither root. No other scope value exists.
- **REQ-TUI-055** — Custom prompt commands. Markdown files are read from `~/.codex/prompts/*.md` and then `~/.agents/prompts/*.md`, taking each root's files in ascending file-name order; when two files normalize to the same name, the file read first wins and the later one registers nothing. Optional YAML frontmatter supplies `description` and `argument-hint`, which give the displayed description `Prompt: <description> <hint>`. Each prompt registers as `/prompts:<name>` and, when no other command already owns the bare name, additionally as `/<name>`. Normalization lower-cases the name and keeps only characters in `[a-z0-9:_-]`, replacing each run of other characters with a single `-`. Invoking a prompt command expands its body and sends the result to the agent as a steering prompt. Expansion replaces `$$` with a literal `$`; `$ARGUMENTS` with the argument string exactly as typed; `$1` through `$9` with positional arguments obtained by splitting the argument string under shell quoting rules, so a quoted run stays a single argument (`$10` and higher are not placeholders); and `$NAME` with the value of a `NAME=value` token in the arguments, where NAME is upper-case. A placeholder with no corresponding value expands to the empty string. Where frontmatter supplies no `description`, the displayed description is `Prompt: <name>`, naming the normalized command name; where it supplies a description but no `argument-hint`, the hint and the space preceding it are omitted, so the displayed description ends with the description text.

### 9. Transcript memory bounds and scroll-back archive

- **REQ-TUI-082** — Configuration keys: `transcript.max_in_memory_events` default 100 (valid range 50..1000) and `transcript.archive_page_size` default 50 (valid range 10..200).

In both cases the newest events stay visible and memory use stays bounded. Report artifacts retained in session state are likewise bounded to the newest 100. ### 14. Run lifecycle, execution status, and shutdown

- **REQ-TUI-115** — At most one run executes at a time; a run is "active" from start until its task completes, and the UI can query run-activity at any time.
- **REQ-TUI-116** — Starting a run is observable as: a session is created first if none exists (REQ-TUI-148); the submitted text appears as a `user` transcript event; and exactly one system status event exists for that run, updated in place rather than duplicated — first "Classifying intent...", then "Intent classified: <intent>", then the run's full classification status text. When intent classification falls back, a warning toast `Intent classifier fallback: <reason>` shows for 8 s in addition. A run started in a resumed session keeps the intent already recorded for that session instead of classifying again. The `<intent>` value is one of the thirteen categories of the taxonomy fixed by REQ-ORCH-006 in the run-orchestration domain: `explicit_trivial`, `question`, `exploration`, `problem_resolution`, `single_file_change`, `small_feature`, `moderate_feature`, `large_feature`, `refactor`, `architectural`, `requirements`, `whole_project`, `ambiguous`. The run's full classification status text is that same `Intent classified: <intent>` line carrying whichever suffix REQ-ORCH-014 defines for the case: a carried-over intent appends the continued-from-previous-run suffix, and a fallback appends the fallback suffix with its reason where one is available. Where neither case applies, the unsuffixed line is the final text and the status event receives no further update.
- **REQ-TUI-117** — Session-scoped diagnostics record timeline events for intent classification, run start, permission-mode downgrade (when it occurs), compression, and run end, attributed to the TUI actor, and run logging is directed to the session's debug log.
- **REQ-TUI-118** — Pre-run inline authentication: when the active model's provider is unauthenticated, the transcript gains "Authentication required for <provider>…"; device-code prompts render as a system message with the verification URL, `Enter code: **<code>**`, and `_Expires in <n>s_`; success appends "Authenticated with <provider> ✓". For an API-key provider failure, the provider settings screen opens for exactly one retry; final failure appends the failure text plus "Run aborted.", sets execution status `failed`, and completes the run with an error toast.
- **REQ-TUI-119** — A run launched from the interactive TUI must not grant a permission request on the user's behalf. Where the permission mode that would otherwise be in force permits unattended approval, the run operates under the `ask` mode instead, so every request is put to the user; the one exception is a workspace that has explicitly opted into unattended operation. A reduction of this kind is written to the session diagnostics timeline of REQ-TUI-117, and the mode the transcript reports for that run is the reduced one. Each permission decision made during a session appears in that session's audit record. The permission-mode vocabulary is the three presets fixed by REQ-TOOLS-041 in the tools and permissions domain — `restricted`, `ask`, and `autonomous` — of which only `autonomous` permits unattended approval and is therefore the only mode this reduction affects. The opt-in that suppresses the reduction is the workspace configuration key `runtime.allow_unsandboxed_autonomous` (default false) named by REQ-TOOLS-068; where it is set true in the workspace configuration, the requested mode is kept and no reduction is recorded.
- **REQ-TUI-120** — On run completion, a progress summary yields (execution status, text, severity); the text is appended as a system event and surfaced as a run-completed toast. Any post-run improvement analysis executes only after the terminal state has been flushed synchronously (slow analysis can never keep a finished run looking live).
- **REQ-TUI-121** — Cancellation mapping: a cancelled run maps to execution status `stopped` with the system line "Run forcefully stopped by user." when the force deadline has passed, otherwise to `paused` with "Run paused: interrupted by user." (duplicate-suppressed); the cancellation still propagates.
- **REQ-TUI-122** — Any other run failure sets execution status `failed` and both appends and toasts `Run failed: <formatted runtime error>` (rate-limit errors are formatted human-readably).
- **REQ-TUI-123** — Once a run has finished, whatever its outcome, and before the interface accepts the next submission, every one of the following is observable: no streaming preview, no run spinner, and no tool entry still in progress is on screen; the run timer reads the frozen total of REQ-TUI-114 for the run just finished; no quota-wait record is held, and neither the quota-wait nor the message-limit modal is displayed; the session's closing statistics and state are already on disk, so terminating the process at that instant loses nothing; the run-completed toast of REQ-TUI-022 has been raised; the artifacts of the finished run are still browsable per REQ-TUI-185; the composer meta bar reads as idle; and a quit requested while the run was still going carries through to an exit instead of being dropped.
- **REQ-TUI-124** — This domain sets and displays exactly these execution-status values: `running`, `waiting` (a provider-quota wait), `paused`, `paused_message_limit`, `idle`, `stopped`, `failed`, `background`, and `interrupted` — the last recorded by `sessions --repair` (REQ-TUI-012) for a session whose owning process ended without recording a terminal state; it displays like any other non-running status and raises no modal of its own when such a session is loaded. The vocabulary is closed: the progress summarization performed at run completion records a status already named here — in practice `idle`, `stopped`, or `failed` — and never introduces a status of its own. For any status other than `running`, neither a streaming preview nor a tool entry still in progress is left on screen. Loading a different session replaces every displayed figure with that session's own values: after the switch no token total, tool-call count, or compression count belonging to the previously loaded session is visible anywhere.
- **REQ-TUI-125** — Stop: with no active run, warn "No active run to stop."; otherwise signal a graceful interrupt (or cancel the task), set status `paused`, clear wait state, request a save (a save failure toasts the error "Run stopped but save failed: …"), and notify "Run stopped."
- **REQ-TUI-126** — Pause: with no active run, warn "No active run to pause."; otherwise request a graceful interrupt and toast the warning "Pausing run… current step will complete first."
- **REQ-TUI-127** — Following an interrupt, the execution status recorded for the session is `paused`, and no pending quota wait is recorded against it. Neither the quota-wait modal nor the message-limit modal is on screen afterwards, and loading that session again — in this process or a later one — raises neither modal of its own accord.
- **REQ-TUI-128** — Graceful quit (sources: Ctrl+C, `/quit`, leader `q`): with no active run, exit cleanly at once. With an active run: mark exit-pending, arm a 2.0 s force deadline, request a graceful interrupt, append the synchronously-flushed system line "<source> requested shutdown. Waiting for active agents to stop before exit. The app will force quit in 2s if still blocked.", set every live agent's activity to "Stopping... force quit in 2s" (icon `!`, phase "stopping"), and toast "Stopping agents... force quit in 2s if still blocked." (title "Quit requested", warning, 4 s). A second quit request during the window appends "<source> requested immediate force quit." and force-quits immediately.
- **REQ-TUI-129** — Shutdown countdown (0.25 s tick): the stopping activity text counts down whole seconds ("Stopping... force quit in <n>s", then "Force quitting..."). If the run ends first, MCP shuts down and the app exits cleanly; if the deadline passes, the transcript gains "Graceful shutdown timed out. Force quitting now." and the process force-quits with exit code 130.
- **REQ-TUI-130** — A normal submission made while a run is active is queued for the next iteration and notifies "Prompt queued for the next iteration." When no child is active at all, the steering text is queued instead and a warning reads "No active child to steer; queued for the next iteration." The "first" active child is the first active agent in the flattened tree order of REQ-TUI-089 — roots newest-first by start time, children nested under their parents in that same order — so the recipient is deterministic and is the topmost active row the agents panel shows.
- **REQ-TUI-131** — Force compression: with no running agents, warn "No running agents to compress."; otherwise notify "Compressing context for <n> agent(s)…", badge each agent's live activity as compressing, compress concurrently per agent, toast each failure as "Compression failed for <name>: <reason capped at 120 chars>", and finish with "Context compressed for <n> agent(s)."
- **REQ-TUI-132** — Message-limit pause: when the message limit is reached, execution status `paused_message_limit` persists and a modal shows — title "Message limit reached (<count>/<limit>)", body including "Estimated token usage: Input: <n> / Output: <n>" (thousands-separated), options `C`/Enter Continue, `D` Double the limit to `<limit×2>`, `X`/Esc Cancel, with matching buttons (Continue focused). - **REQ-TUI-133** — Reattached message-limit pause: loading a session whose status is `paused_message_limit` re-shows the modal without an active run; resolving it deletes the durable signal file `<session_dir>/.message_limit_paused` and sets status `paused` (cancel) or `idle` (continue/double). ### 15. Live run event handling and activity mapping

- **REQ-TUI-136** — Intra-iteration progress persists with a 0.25 s debounce; iteration boundaries persist immediately; every persist first applies the transcript memory-bound trim (REQ-TUI-083), which by that requirement leaves archive-restored events in place.
- **REQ-TUI-137** — Scheduler diagnostic issues surface as toasts: a quota-exhaustion issue shows its message verbatim; a child failure shows `<actor> failed: <message>`, except that no failure toast is raised for an agent already reported as quota-exhausted. Issues agreeing in kind, actor, and text produce exactly one toast and later repeats are suppressed. The toast timeout is 10 s for error severity and 8 s for every other severity. Each model reported as exhausted is added to the session's exhausted-provider-models list and persists there with the session. Duplicate suppression is scoped to the run: the record of already-toasted issues is cleared when a run starts, so an issue recurring any number of times within one run is reported exactly once, and the same issue recurring in a later run is reported again exactly once.
- **REQ-TUI-138** — Observable effects of run events (each applied safely from background work, per REQ-TUI-198): a child spawn records one `child` transcript event per canonical name (skipped for parentless/top-level children) and syncs the agents panel; a child entering running resets the timer segment and sets "Thinking..." activity; a child reaching a terminal state syncs and persists; todo-state changes update the todo panel; last-prompt token counts update the live context readout; token aggregates record into session state; iteration end maps the outcome to activity ("Completed", `✗` plus a failed report summary, or "Continuing next iteration"), appends the report artifact, and persists the child's final response text into the transcript.
- **REQ-TUI-139** — Stall detection: a stall sets the agent's activity to `[!] Waiting on LLM (<n>s)…` with phase "stalled" (recovery restores "Thinking...") and creates/marks the live stream entry so the in-transcript bold-yellow "Waiting on LLM (Ns)… (model is not streaming)" line shows a live counter.
- **REQ-TUI-140** — Streaming chunks: a chunk with no visible text but with reasoning renders the thinking phase; completely empty chunks are suppressed (optionally logged at debug level).
- **REQ-TUI-141** — Within one agent turn, streamed text is presented as a single message that grows: each piece of the model's output is shown once, in the order produced, whichever way the provider delivers it — as increments, or by resending the whole message so far — so text already on screen is never repeated. Where a tool entry appears part-way through a turn, the message text produced before it is final, remains above it, and is not reordered around it. A turn producing no visible text leaves no empty message behind. Reasoning captured during the turn appears as a `thinking` event placed ahead of the text and tool entries it preceded, carrying a duration rounded to 0.1 s. When the turn ends, the persisted transcript holds the final message text exactly once and retains no partial snapshot of it.
- **REQ-TUI-142** — A tool call occupies one transcript entry for its whole lifetime. Successive updates about that call change the icon, phase, and content of the entry where it already stands, and never append a second entry for it. Entries belong to the agent that made the call, so the same call made by two agents shows as two entries. The displayed content becomes the result text whenever an update supplies replacement text and whenever the call failed; a successful completion carrying no result text leaves the command line already displayed as the content. `completed`, `failed`, and `blocked` are terminal phases: an entry that has reached one of them shows no further change, and a subsequent call from that agent begins a fresh entry.
- **REQ-TUI-143** — Live-activity mapping from run events: tool actions show an animated icon with `$ <command>` summaries for terminal commands (suffixes `(input)`, `[timeout: Ns]`, `[reset]` when applicable) or `<tool>: <first-arg>` otherwise, text capped at 90 characters with `…`; observations map success→`✓` "completed", terminal failures→`✗` "failed", suspicious/soft-pause→`!` "blocked"; user rejections→`✗ <tool> blocked: <reason>`; agent errors→`✗` failed; tool-call status events map completed-like statuses to `✓` and blocked/cancelled/error/failed to `✗ <title> failed`, else animated; hook executions→`[HOOK] Hook ran|blocked|failed: <tool>`; conversation errors→`✗ <code>: <detail>`; agent message events→"Calling <tool>" / "Response ready" (with preview) / "Thinking..."; compression events→`[COMP]` "Compressing context…" / "Context compressed".
- **REQ-TUI-144** — A parent agent whose children are still active shows a synthetic waiting badge ("Waiting on child agents" with the `◴◷◶◵` animation). A summarizing child shows "Summarizing response" (animated, bold cyan) unless a terminal/stopping phase already applies; when a summarizing child turns terminal its badge becomes "Completed" or `✗ Failed`.

### 16. Stream text and reasoning extraction

- **REQ-TUI-145** — Visible stream text is derived from each delta as follows: content the provider marks as the model's private reasoning yields no visible text and is treated as reasoning instead (REQ-TUI-146); a delta carrying only tool-call data yields no visible text; content delivered as a list of parts is joined with newlines so the part boundaries survive; and a whitespace-only delta is emitted verbatim, so a blank-line delta between blocks and a space-only delta between words both reach the display and neither paragraphs nor words run together. Plain string deltas are emitted after the sanitizing pass required for terminal-safe rendering. That pass makes exactly these changes and no others: byte sequences that do not decode as valid text become the Unicode replacement character rather than causing the delta to be dropped; terminal escape sequences — ANSI control sequences and operating-system commands alike — are removed, so streamed model output can never move the cursor, restyle the screen, or address the terminal; and C0 and C1 control characters other than newline and tab are removed. Every other character, whitespace included, passes through unchanged, so the pass never trims, collapses, or normalizes text.
- **REQ-TUI-146** — Reasoning is extracted from a delta in each of these three shapes: a dedicated reasoning field on the delta; a list of thinking blocks, from each of which the first non-empty of `thinking` then `text` is taken; and a list of reasoning items, from each of which the first non-empty of `text` then `content` is taken. Fragments found within one delta are concatenated in the order they appear. A delta that yields reasoning is treated as reasoning-bearing even when it yields no visible text, so the thinking phase of REQ-TUI-071 renders. Fragments are joined with a single newline, matching the part-joining rule of REQ-TUI-145, so block boundaries within one delta survive into the rendered reasoning body.
- **REQ-TUI-147** — Mid-stream guard: if appending a delta makes the accumulated live content identifiable as the model's private reasoning, the live stream is wiped and the phase reverts to "thinking" (private reasoning is never displayed, even partially).

### 17. Session management: new, resume, picker, background

- **REQ-TUI-148** — New session: without a session manager or configuration, error "No session manager or config available." Otherwise the runtime model override resets to the configured starting model, a session is created with an embedded configuration snapshot, and the session lock is acquired. A lock conflict errors "Session lock conflict: <error>"; other failures error "Unable to create session: <error>"; success toasts "Created session **<id>**".
- **REQ-TUI-149** — Session picker (via `/resume` or the palette): a modal table with columns "Session ID", "Created At", "Status", one row per known session. An empty list toasts "No sessions found." (info); a listing failure errors "Unable to list sessions: <error>". Selecting a row closes the picker and loads that session.
- **REQ-TUI-150** — Loading a picked session: a missing session errors "Session **<id>** not found."; a corrupt snapshot errors "Corrupt session snapshot: <error>"; other failures error "Unable to load session: <error>". Success restores per-session model overrides (invalid stored model configurations are ignored with a log entry), updates the composer's model display, re-shows the message-limit modal if the loaded status is `paused_message_limit`, and toasts "Loaded session **<id>**".
- **REQ-TUI-151** — Session persistence contract: sessions live under `<workspace>/.rotaris/sessions/<session_id>/` with a versioned snapshot; active sessions save with debounced incremental writes and terminal sessions immediately; a lock enforces single active ownership per session id; that lock is exclusive and its acquisition is immediate — it never waits, blocks, or retries — so a second process attaching to a session another live process owns fails at once with the lock-conflict error of REQ-TUI-148 and loads nothing, leaving the owning process undisturbed; the lock is released when its owning process exits, and a lock whose owning process is no longer alive is treated as free and taken over by the next process to attach; partially recoverable snapshots load with warnings; continuing a session fully restores transcript, child-state history, tool events, report artifacts, and the configuration snapshot.
- **REQ-TUI-152** — Send to background: with no active run, warn "No active run to send to background." With one, the active run is first interrupted gracefully exactly as REQ-TUI-125 interrupts it, so that no streaming preview, spinner, or unfinished tool entry survives the handoff and REQ-TUI-124 continues to hold; the session status is then set to `background` and the session is saved (a save failure errors "Background handoff save failed: <error>"). - **REQ-TUI-153** — Reattach paths: the session picker, the CLI `run --session <id>` flag, and the paused-message-limit reattach modal all restore persisted session state.
- **REQ-TUI-154** — The runtime model override and any synthesized runtime model configurations mirror into session state on every sync/persist and restore on load; the override is session-scoped and is never written to the workspace configuration file.

### 23. Transcript search

- **REQ-TUI-186** — The transcript search modal opens via leader `/` or `/search` (guards per REQ-TUI-051). Layout: an input with placeholder "Search transcript…", a status line, and a results list. Escape dismisses with no side effects.

- **REQ-TUI-190** — The status bar is a single row under the right rail with three parts: the workspace path (dim, flexible width), a ` · ` separator, and the git branch (bold green, right-aligned).
- **REQ-TUI-191** — Workspace resolution: the session's workspace root wins over the configured workspace root; the value re-syncs on every poll and immediately on session/workspace switch.
- **REQ-TUI-192** — Path display: the home directory collapses to `~` (honoring a HOME environment override; home itself renders `~`; paths outside home render absolute), and the path is middle-truncated with a single `…` to fit the width budget (branch and separator reserve their width first; the path never shrinks below 4 characters; an unknown width falls back to 80).
- **REQ-TUI-193** — The status bar's branch name comes from running `git rev-parse --abbrev-ref HEAD` with the workspace path as its working directory and a 1.0 s timeout. Detection never blocks interaction: keystrokes are accepted and the display keeps updating while it is in flight. Outcomes are decided by exit code and standard output alone; the command's standard error is never parsed, so the display never depends on the wording, version, or locale of an external tool's messages. Exit code 0 with non-empty output shows the trimmed output as the branch name, except that the literal output `HEAD` — git's own report of a detached head — shows `[detached]`. Every other outcome hides the branch and its ` · ` separator entirely, leaving the workspace path to occupy the row alone: exit code 0 with empty output, any non-zero exit, a failure to start the process, and a timeout are all treated alike.
- **REQ-TUI-194** — Refresh cadence: an initial refresh at startup, a 10.0 s poll, an immediate refresh on workspace change, and a re-render on resize. Async results that arrive after the workspace changed mid-flight are discarded. The bar always occupies a visible row on the main screen and survives arbitrary interaction without crashing.

### 25. Clipboard integration

- **REQ-TUI-195** — Copy attempts external clipboard tools in order — `clip`, `clip.exe`, `xclip -selection clipboard`, `xsel --clipboard --input`, `wl-copy`, `pbcopy` — each with a 2 s subprocess timeout and UTF-8 piped input; these give verifiable success. On total failure it falls back to the OSC 52 terminal escape sequence (`ESC ] 5 2 ; c ; <base64> BEL`) written to the terminal. That path is fire-and-forget — the terminal cannot acknowledge it — and is reported as success, but its notification differs from the verified case: it must convey that the text was handed to the terminal and that the terminal may or may not have accepted it, so an unverified copy is never presented as a confirmed one. Exact wording is left to the implementation. The copied text is also retained in an in-application clipboard.
- **REQ-TUI-196** — The copy-failure message is platform-aware: on Windows "Copy failed — Windows clipboard integration is unavailable"; elsewhere "Copy failed — install xclip, xsel, wl-copy, or use a terminal with OSC52".

### 26. Sign-out from the TUI

- **REQ-TUI-197** — Logout (via `/logout <provider>` or the palette logout entries): an unknown provider surfaces the error text as an error toast; an OS failure toasts `Logout failed for <normalized id>: <error>`; success toasts the operation's own message and severity (deleted vs. nothing-to-delete outcomes are distinguished). Provider ids are normalized (trimmed, lower-cased) for messages.

### 27. Cross-cutting invariants

- **REQ-TUI-198** — Updates produced by background work are applied safely to the display: if the application is already stopping or has stopped, such an update is discarded without crashing or printing a traceback; unrelated errors are still reported normally.
- **REQ-TUI-199** — Persisted transcript content is never mutated by display settings: visibility toggles and line limits change only what is drawn on screen, while complete tool inputs/results and reasoning stay in session state for model context and later re-display.
- **REQ-TUI-200** — Random-interaction resilience: arbitrary key presses, resizes, and clicks on every surface (agents panel, stash flows, quota modal, model picker, reasoning toggles, status bar, artifact editor) must not crash; the same holds for display updates that arrive on their own timing rather than in response to input, which likewise produce no traceback and no error toast (REQ-TUI-100).
- **REQ-TUI-201** — The literal text a registered slash command claims is never submitted to the agent as a prompt and never appears in the transcript as a `user` event; where a command sends anything to the agent it is that command's own content, as specified by the requirement defining it. Slash handling behaves identically in inline and multiline composer modes. Text beginning with `/` that no registered command claims is not slash handling at all and is submitted as an ordinary prompt (REQ-TUI-041, REQ-TUI-046).
- **REQ-TUI-202** — Final session state is always flushed synchronously at run end and when recording shutdown messages, bypassing debounced saving, so state survives an immediate process exit.
- **REQ-TUI-203** — The tool-events visibility toggle governs both transcript tool results and the agents-panel recent-activity feed (a single toggle controls both surfaces).
- **REQ-TUI-204** — Accessibility: statuses are conveyed with text labels and glyphs, never color alone; all themes preserve the chrome/content visual hierarchy and meet the contrast floors of REQ-TUI-025.
- **REQ-TUI-205** — What is drawn is fixed by the session state together with the clock reading at the moment of drawing, and by nothing else. Two renders of the same session state taken at the same clock reading and animation phase produce identical output. Nothing outside that pair may influence the result: not the enumeration order of any collection, not randomness, and not the order in which the process happened to receive the state. This holds for the transcript, the command palette, the status bar, the agent tree, the settings screens, and streaming-Markdown output. The only content permitted to differ between two renders of identical state is the content this document defines as advancing with the clock — spinner and braille animation frames, elapsed values, and countdown values — and that content follows from the clock reading alone. Values this document derives from timestamps recorded in session state, such as the root ordering of REQ-TUI-089 and the elapsed figures of REQ-TUI-090, REQ-TUI-097, and REQ-TUI-098, are part of that state and reproduce identically.
- **REQ-TUI-207** — *Withdrawn.* It was minted into a series already declared closed, and the display baseline it fixes belongs to a terminal the product does not have. The desktop equivalent is carried by REQ-SHELL-061, which fixes the minimum window size at which the whole working surface stays usable, together with REQ-SHELL-059 and REQ-SHELL-047, which require the layout to degrade at stated thresholds rather than fail; the contrast floors that made colour legible are carried by REQ-SHELL-145.

## Data & Formats

All formats below are externally observable (files a user or another process can read, or wire/terminal formats).

### Persistent files

| Path | Format | Contents |
| --- | --- | --- |
| `<workspace>/.rotaris/prompt_history.json` | JSON array of strings | Last ≤50 submitted prompts, oldest first; written atomically. |
| `<global config dir>/prompt_stash.json` | JSON array of strings | LIFO prompt stash; global, cross-workspace; written atomically. |
| `<global config dir>/mcp_toggles.json` | JSON object `{name: bool}` | MCP server enablement; absent names default enabled; written atomically. |
| `<workspace>/.rotaris/agents.yaml` | YAML | Project-scope configuration; the TUI writes `display`, `compressor`, and `runtime` sections via atomic merge-updates preserving unrelated keys. |
| `<global config dir>/agents.yaml` | YAML | Global-scope configuration; receives global-scope writes (e.g. memory diagnostics). |
| `<workspace>/.rotaris/sessions/<id>/` | directory | Versioned session snapshot (transcript events incl. tool/system/thinking/child events, child states, todo states, edit diffs, token usage, runtime model overrides, execution status, wait state, message count/limit, exhausted provider models, report artifacts), lock file, debug log, diagnostics timeline, conversation persistence directory, and `.message_limit_paused` signal file. |
| `<workspace>/.rotaris/sessions/<id>/state/transcript_archive.jsonl` | JSON lines | Append-only transcript archive; one JSON object per line, deterministic key order, non-native values stringified; fixed-size pages of `archive_page_size` lines. |

The global configuration directory is the platform-conventional per-user configuration directory for the application name "rotaris". The product adopts no directory belonging to any earlier or differently named product and creates its own on first use (REQ-STARTUP-145).

### Transcript event shape (behavioral)

Each transcript event is a JSON-serializable object with at least a `role` field. Persisted roles: `user`, `agent`, `thinking`, `child`, `tool` (result events carry a `phase` in {completed, failed, blocked} once terminal; input events carry none), `edit_diff`, `system`, and the archive placeholder `{"role": "page", "offset": <page>, "count": <events>}`. Display-only synthesized roles (live stream, queued prompt, breadcrumb) never persist. Thinking events may carry a duration rounded to 0.1 s.

### Configuration keys consumed by this domain

`tui.keyboard.leader` (default `Ctrl+X`); `display.show_tool_results` (default true), `display.show_tool_inputs` (default true), `display.tool_result_max_lines` (default 10; 0 = unlimited), `display.tool_input_max_lines` (default 2; 0 = unlimited); `transcript.max_in_memory_events` (default 100; 50..1000), `transcript.archive_page_size` (default 50; 10..200); `compressor.threshold_percentage`; `runtime.max_iterations`; `runtime.allow_outside_workspace`; `runtime.memory_diagnostics_enabled` (per scope).

### Custom prompt command files

Markdown files under `~/.codex/prompts/*.md` and `~/.agents/prompts/*.md`, optionally with YAML frontmatter keys `description` and `argument-hint`. Placeholders in the body: `$$`, `$ARGUMENTS`, `$1`..`$9`, `$NAME` (from `NAME=value` arguments).

### Skill injection format

A loaded skill is delivered to the agent as a steering prompt shaped `[SKILL.md]\nName: <name>\nSource: <source>\n\n<body>`.

### Terminal/OS protocols

- Clipboard fallback: OSC 52 escape sequence `ESC ] 5 2 ; c ; <base64 payload> BEL`.
- External clipboard tools tried in order: `clip`, `clip.exe`, `xclip -selection clipboard`, `xsel --clipboard --input`, `wl-copy`, `pbcopy`.
- Browser opening: the platform's default browser handler is tried first; if it reports failure, the first of `xdg-open`, `gio`, `open` found on PATH is launched detached with its stdout/stderr discarded (the `gio` form takes an extra `open` argument). Only when none of these succeeds is the attempt a failure.

### Exit codes

| Code | Condition |
| --- | --- |
| 0 | Normal exit. |
| 1 | Configuration load/validation failure; login failure; worktree-option misuse; OS-level logout failure. |
| 2 | `--output-format stream-json` without a task; an unrecognised `--output-format` value; unknown logout provider. |
| 130 | Force quit (immediate `q`, second quit request, or graceful-shutdown timeout). |
