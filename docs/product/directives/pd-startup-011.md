### PD-STARTUP-011 — a run directory carries the application log, and a window with no workspace writes under the per-user data directory

REQ-STARTUP-132's written artifacts SHALL further include `app-log-NN.jsonl`: one record per line the application log records, after PD-MONITOR-002's threshold and REQ-TOOLS-171's redaction pass, as `{at, level, source, message}`, bounded as REQ-STARTUP-133 bounds every JSON-lines stream, read as REQ-STARTUP-138 reads one, and named in the manifest's `captured` list so a reader knows an absent stream is unbuilt and not lost. The stream SHALL carry the instance's whole log for as long as its window lives — every window's lines and main's own, unfiltered by window — and SHALL begin at the capture's start: lines recorded before it are not carried, because REQ-STARTUP-130 permits no work at `off`. REQ-STARTUP-134's ban on session content binds the stream as written and by kind: a folder path, a provider's error text and a child process's own diagnostic lines are permitted; no line at any level SHALL quote transcript or prompt text, model output, a tool's result, a file's contents or a credential, whoever produced the text, and a writer that would otherwise quote one SHALL write its source, kind and byte length instead. The obligation sits on each writer of the application log, held by a test beside it, and the stream SHALL NOT be filtered a second time. A window that holds no workspace and whose `diagnostics/outputDir` is unset SHALL take `<per-user data directory>/diagnostics/rotaris` (REQ-STARTUP-145, whose machine-local clause it inherits) as its base, fixed when the window is built and unmoved by a workspace opened later; REQ-STARTUP-131's inactive case stays the one it names, that base itself being unwritable. The diagnostics card of REQ-SHELL-163 SHALL show that folder as the one in force and SHALL say in words that a run directory holds this application's log for every open window, that the log includes folder paths and error messages, and that it holds no conversation, model output or file contents.

**Why, and what it costs.** A packaged Windows build writes its application log to a standard output nobody reads (`docs/architecture/hardening/02-the-findings.md` §3.4), and REQ-SHELL-163's card is the one switch a user has to keep a log they can read after an incident; REQ-STARTUP-132 enumerates a closed set the stream is not in, and REQ-STARTUP-131 names no base for a window with no workspace — the welcome window and a refused or failed open, the launches where a fault leaves no other trace — so the build's inactive window departed from its "SHALL never silently disable itself" either way. The content rule is applied by kind, not by provenance, because reducing every forwarded line to a length would make the run-directory copy weaker than the standard output in exactly the incident it exists for; the cost is that the guarantee rests on each writer and its test, and a third-party tool server's standard error, forwarded at `debug` when `ROTARIS_APP_LOG_LEVEL` admits it, is recorded as that process wrote it. What else it costs: a run directory under workspace A holds paths and error text from workspace B, kept out of every capture by REQ-GIT-003 and said on the card, but shared with whoever A's `.rotaris/` is shared with; a per-user folder the user may not look in, reachable through the card's open-folder control, where nothing removes old run directories, each stream bounded at 32 MiB but their number unbounded; and three back-pointers, while the metric and span streams, the snapshots and the summaries stay owed. Given up on purpose: a per-window attribution of lines, which the run host's lines cannot keep and which would promise a scope REQ-STARTUP-134 does not ask for; and a buffer of lines before the first window, which REQ-STARTUP-130 forbids. Raised by [OQ-480](../../archive/architecture/open-questions/71-spikes-and-later-questions-38-continued-4.md#oq-480).

> **First execution of the per-user base and the card's words, 2026-11-04, built under [R-091](../requests.md#r-091)'s acceptance plan `hrda` (REQ-STARTUP-131's and REQ-STARTUP-132's back-pointers, REQ-SHELL-163's):** the mechanism held as written and the launch it names was not reached. **What was built:** `diagnosticsBase` resolves the chosen folder, else the workspace's default, else `perUserDiagnosticsBase(<per-user data directory>)`, never none, main passing `resolveUserDirs().data` as `DiagnosticsCapturesDeps.perUserData`; the "nowhere to be written" inactive reason is gone; `DiagnosticsCaptures.folderFor` answers the card's folder in force from the workspace the window was built for, so a workspace opened later moves neither the capture nor the folder shown; the card says the three sentences at every level and always shows a folder (`main/diagnostics.test.ts`, `commands/diagnostics.test.ts`, `settings/DiagnosticsCard.test.ts`). **What the launch found** (`pnpm app:drive` at `light`, Windows 11 ARM64, Node 26.13.0, Electron 44.3.0, no other tree's Electron running): a launch given no folder built its window for the working directory and wrote `app-log-01.jsonl` under that folder's `.rotaris/diagnostics/rotaris`, not under the per-user folder; a launch given a regular file had its open refused (`workspace.not-a-folder`) and its capture inactive with `ENOTDIR`. Every main window is built for a folder and its capture is fixed then, so no launch reaches the per-user base, and the refused open this directive's reasons name keeps no log: raised as [OQ-541](../../architecture/open-questions/71-spikes-and-later-questions-38.md#oq-541), the build proceeding as ruled. The card, driven to Settings › About in the refused-file window, showed the three sentences, the folder in force and the inactive reason.

> **First execution of the content rule at each writer, 2026-11-04, built under [R-091](../requests.md#r-091)'s acceptance plan `hrda` (REQ-STARTUP-134, REQ-TOOLS-171, PD-MONITOR-002):** one writer quoted model output and now says its source, kind and length; the others held. **What the writers were found doing:** the intent classifier's warning for a structured rung answered without JSON, and its fallback reason that the run host's pre-flight writes as the `intent:` line, each quoted the first 60 characters of the model's answer (`packages/engine/src/intent/classifier.ts`); the adoption interpretation's line named the answer's length in characters, without its kind; the run host's MCP host and the MCP transport wrote no line carrying a tool's result or the model's arguments, and forward a server's standard error at `debug` as the process wrote it, as this directive permits. **What was built:** `sessionContentInLog(kind, source, text)` in `@rotaris/kernel` (`log-content.ts`) words the replacement once, `<kind> from <source>, <n> bytes, not quoted`, and the classifier's two lines and the adoption line use it; a test beside each writer holds the line to source, kind and byte length and never the text (`kernel/src/log-content.test.ts`, `engine/src/intent/intent.test.ts`, `run-host/intent.test.ts`, `run-host/dispatch.test.ts`, `run-host/mcp.test.ts`, `mcp/src/mcp.test.ts`), and `app-log.test.ts`'s redaction case stands; nothing in the stream is filtered further. Read as permitted by kind and left as written: a hook's output in its failure warning (REQ-HOOKS' warning text, a child process's own lines), a provider's error text, and the verification-only capture seams' DOM reads, which a packaged build does not carry.
