# Desktop Shell, Navigation, and Window Management

## Overview

Rotaris presents a single main desktop window containing seven primary views selected from a left-hand navigation rail, framed by a title bar (brand, workspace, and session status) and a bottom status strip (workspace, branch, safety, cost, and cloud indicators). The shell owns global keyboard shortcuts and a command palette, responsive compact layouts with overlay drawers, user-resizable and persistent pane layouts, auxiliary per-persona agent windows, a terminal pop-out window with an interactive character-grid terminal, transient and persistent notification surfaces, theming with accessibility floors, and guarded window-close / workspace-switch / session-switch flows. Preferences persist in a single per-user store; all shell behavior below is stated as externally observable requirements.

## Requirements

### Command line and process lifecycle

- **REQ-SHELL-001**: The application command line accepts: an optional positional argument naming a workspace directory; `--demo` (open with representative built-in sample data); `--version`; `--diagnostics` taking an optional value `light` or `deep` (the bare flag means `light`); and `--diagnostics-output <path>` naming the base directory under which a timestamped diagnostics run is written.
- **REQ-SHELL-002**: Given `--version`, the process prints exactly `Rotaris {version}` to standard output and exits with code 0 without showing a window.
- **REQ-SHELL-003**: A rejected diagnostics invocation — `--diagnostics` given a value that is neither `light` nor `deep`, or `--diagnostics-output` given with no directory after it — produces no window, emits a usage message whose text contains the option that was rejected, and terminates with exit code 2. Nothing is written to the diagnostics output directory in that case.
- **REQ-SHELL-004**: A normal interactive run's process exit code is the desktop event loop's exit status.
- **REQ-SHELL-005**: Under `--demo` each of the seven primary views opens populated from sample data carried inside the build, and the process opens no outbound network connection for its whole lifetime: cloud-credit polling is not started (REQ-SHELL-015) and no request reaches a model provider. An action that could only complete against a live service is declined with one of the exact sentences listed in REQ-SHELL-149; the decline is always shown, never silent, and the view's contents are unchanged afterwards — no partial application.
- **REQ-SHELL-006**: All user preferences resolve to a single platform-standard per-user preference store scoped by organization name "Rotaris" and application name "Rotaris"; this scoping is established before the first preference read so that no preference is ever read from or written to a differently scoped store.

### Startup sequencing

- **REQ-SHELL-007**: The application window icon is the product brand mark from the moment the first window appears, so taskbar and window-switcher entries carry the logo.
- **REQ-SHELL-008**: Bundled font families for the display, body, and monospace roles are made available before the first window paints; if loading a bundled font fails, the application continues with host system fonts and does not abort.
- **REQ-SHELL-009**: The stored theme choice is applied ahead of the first window becoming visible. Reading that preference never writes it back, so on a machine where the recorded theme name does not map to an installed theme the recorded value stays exactly as the user left it.
- **REQ-SHELL-010**: Startup workspace resolution follows this precedence: (a) an explicit command-line workspace argument wins, is normalized to an absolute path, and is immediately persisted as the last-opened workspace with no onboarding prompt; (b) otherwise a remembered last-opened workspace that still exists as a directory is used with no prompt; (c) otherwise the current working directory is used and a first-launch prompt is scheduled after the window is shown.
- **REQ-SHELL-011**: The first-launch workspace prompt is deferred 650 ms after the window is shown so the complete desktop paints first. The prompt is the platform's own folder-picker dialog, window title "Open a project folder", limited to selecting directories and initially pointed at the current workspace (or, when there is none, the user's home directory).
- **REQ-SHELL-012**: Cancelling the first-launch chooser leaves the default desktop fully usable and shows a transient notification: "Open a project folder when you're ready by selecting the workspace path in the title bar."
- **REQ-SHELL-013**: On a bundled (standalone) runtime that still requires machine setup, the setup modal is scheduled 650 ms after the window is shown; after it completes, setup state is refreshed, the asynchronous Git refresh starts, and only then does first-launch workspace onboarding continue. On other runs the Git refresh starts at window activation.
- **REQ-SHELL-014**: Git status discovery never starts before the window is on screen (REQ-SHELL-013 fixes the exact point for each kind of run), and the window remains fully usable while a discovery is outstanding: views can be switched, text can be typed, and shortcuts fire. The discovery itself displays nothing that blocks input — no modal dialog, no progress dialog, no busy cursor — which leaves dialogs scheduled by other requirements, such as the first-launch folder prompt (REQ-SHELL-011) and the machine-setup modal (REQ-SHELL-013), free to appear while a discovery is still running. A failed discovery raises the persistent ERROR notice of REQ-SHELL-116 reading "Git status could not be refreshed: {message}"; it stays on screen until the user dismisses it and is never withdrawn on a timer.
- **REQ-SHELL-015**: Activation ordering: the window is shown first; the software-update check starts only once a window is visible (so its notification always lands on a visible window); cloud-credit polling starts at the same point unless running in demo mode.
- **REQ-SHELL-016**: Deferred startup offers (project-initialization resolution and the hook-trust review offer) are issued only after window construction completes; a window created and destroyed immediately must not crash or deliver the offers.

### Workspace selection and replacement

- **REQ-SHELL-017**: Opening another project builds a new main window on the selected folder, shows it, and then closes the old window. Only if the old window closes successfully is the new window recorded as current, the last-opened-workspace preference updated, and the new window activated.
- **REQ-SHELL-018**: If the old window refuses to close (for example the user cancels an unsaved-settings dialog or an active-run confirmation), the replacement window is discarded and nothing changes: the old window, the current workspace, and the stored preference all remain as they were.
- **REQ-SHELL-019**: If constructing the replacement window fails, the old window stays open and shows the error notification "Could not open the selected project: {reason}".
- **REQ-SHELL-020**: Only workspace-open requests originating from the currently active window are honored; requests from stale windows are ignored.
- **REQ-SHELL-021**: Activating the title-bar workspace chip is declined outright — the transient error notification of REQ-SHELL-112 appears, no folder chooser is shown, and no window, workspace or stored preference changes — in two cases: a worktree integration is running ("Finish the worktree integration before opening another project.") or a run is active ("Finish the active run before opening another project."). The unsaved-settings gate of REQ-SHELL-124 guards this flow as well; answering Cancel there ends the flow with nothing changed. When no gate stops it, the chooser opens pointed at the current workspace. Cancelling the chooser leaves the window, the workspace and the stored preference exactly as they were and may show the reminder of REQ-SHELL-012. Selecting the folder that is already open builds no replacement window and leaves the current window in place.

### Main window structure

- **REQ-SHELL-022**: The main window carries the title "Rotaris", opens at 1440×900 logical pixels, and refuses to be resized below 1000×680 in either dimension. At that 1000×680 minimum, and on every one of the seven primary views, the following all hold and are individually checkable: every control the view offers lies wholly inside the window bounds; every control is reached by Tab traversal; every control's label is rendered in full, the only exceptions being the elisions REQ-SHELL-082 and REQ-SHELL-087 permit; and no control requires horizontal scrolling to reach (REQ-SHELL-064, REQ-SHELL-065, REQ-SHELL-106).
- **REQ-SHELL-023**: The window hosts exactly seven primary views in this fixed order: Overview, Workspace, Mission, Requirements, Git, Library, Settings. Exactly one is visible at a time; Requirements is the fourth entry, ordered after Mission and before Git.
- **REQ-SHELL-024**: Vertical layout, top to bottom: title bar; a persistent-notice banner slot; a horizontal region of navigation rail beside the active view; status strip.
- **REQ-SHELL-025**: View switching semantics: switching to an unknown view identifier is a silent no-op. Leaving the Settings view with unsaved changes triggers the save/discard/cancel dialog (REQ-SHELL-124) and cancelling aborts the navigation. A successful switch updates the rail's selected state and the recorded active view (which other behaviors, such as Escape handling, read).
- **REQ-SHELL-026**: The view shown at startup is Overview.

### Navigation rail

- **REQ-SHELL-027**: The rail shows one button per primary view, in view order, each with a distinct icon and a text label beneath it. Labels: "Overview", "Workspace", "Mission", "Requirements", "Git", "Library", "Settings".
- **REQ-SHELL-028**: Rail selection is mutually exclusive: whenever a view is showing, exactly one rail button is in the checked state, and checking a button unchecks the one that was checked before. Each button is an individual stop in the window's tab order (REQ-SHELL-032) and shows a pointing-hand cursor under the pointer. Each rail icon is declared at 17×17 logical pixels and drawn under the scaling rule of REQ-SHELL-030. Every button carries the tooltip and the accessible description "Open {Label}". A click checks the button and switches the view; a checked state that no user gesture produced updates the rail's appearance only — it switches no view and causes no other navigation effect.
- **REQ-SHELL-029**: Rail labels render at 9 px, and in every built-in theme each item shows its complete label with no ellipsis and no clipped glyph. The rail is consequently never narrower than its widest label needs: it uses the theme's declared item and rail widths (54 px and 68 px respectively in the default theme, REQ-SHELL-129) whenever those already accommodate the labels, and exceeds them when they do not. The width is re-derived after every theme change, including a change to a theme with a larger type scale.
- **REQ-SHELL-030**: An icon declared at L logical pixels is rendered from artwork whose raster resolution is at least ceil(L × device pixel ratio) device pixels in each dimension, so the drawn icon is never an enlargement of a smaller raster. Measured at 100%, 125%, 150%, 175% and 200% OS display scaling, the icon covers L logical pixels — the same physical area of the screen at every one of those factors, within one device pixel. Resting and selected rail icons use two distinct theme inks, and each clears the 3:1 non-text contrast floor of REQ-SHELL-144 against the rail background.
- **REQ-SHELL-031**: A theme change fully recolors the rail, including baked icon inks and hover/selected treatments; no stale-theme icon color survives a switch.
- **REQ-SHELL-032**: Every rail button is its own stop in the window's normal tab order, and each announces a non-empty accessible name (the Workspace button, for instance, announces "Open Workspace").

### Title bar

- **REQ-SHELL-033**: The title bar is a fixed-height strip (44 px in the default theme) with a bottom hairline, containing left to right: the brand mark (22×22, accessible name "Rotaris"), the wordmark "Rotaris", a version label `v{version}` in small monospace, the workspace chip (centered region), the session chip, and the improvement-analysis indicator.
- **REQ-SHELL-034**: If the brand image asset is missing or unrenderable, the title bar degrades to a letter placeholder "R" in a dashed accent frame without crashing.
- **REQ-SHELL-035**: The workspace chip behaves as a button: accessible name "Open project folder", tooltip "Open another project folder", pointing-hand cursor, keyboard focusable, activated by left-click release inside it or by Return/Enter/Space. It displays a folder icon, the workspace path in small monospace, a separator, and the session name (an em dash when none). Its accessible description is "Current project: {path}. Opens the native project folder chooser." Activation opens the workspace chooser flow (REQ-SHELL-021).
- **REQ-SHELL-036**: The session chip carries the accessible name "Session status" and the accessible description "Session is {status}", and displays a status dot — 6 px in the default theme — followed by the text "session {status}". The status word is always one of exactly nine: active, starting, pausing, paused, cancelling, completed, failed, cancelled, idle. Those nine fall into five colour groups — {active, starting}, the waiting family {pausing, paused, cancelling}, {completed}, {failed, cancelled}, and {idle} — and each group resolves to a single theme state colour that the chip's dot and pill share with every status tag drawn elsewhere in the product, so one status word is never shown in two different colours at the same moment. The waiting family uses the theme's `waiting` state colour. The dot pulses for active and starting and for no other status; otherwise it is drawn at full opacity with no animation. Chip text measures at least 4.5:1 against the title-bar background it is actually painted on.
- **REQ-SHELL-037**: The improvement-analysis indicator (a slightly smaller pulsing dot plus the label "Reviewing run for improvements…") is visible only while improvement analysis is active, carries the accessible name "Improvement analysis status", and its description states the user may continue working.

### Status strip

- **REQ-SHELL-038**: The status strip is a fixed-height bottom row (26 px in the default theme) with a top hairline. Items left to right: workspace path (link), checked-out branch, spacer, safety flags, model, tokens, cost, cloud credit (link; present only under the condition in REQ-SHELL-046), background-session count. Every item carries an accessible name; the names are "Workspace folder", "Checked-out branch", "Safety settings in force", "Model runs use", "Tokens used", "Cost so far", "Rotaris Cloud credit", and "Background sessions".
- **REQ-SHELL-039**: The strip holds two kinds of item. An item that opens something is a link: link colour, underline, pointing-hand cursor, its own keyboard focus stop, activated by click or by Return. Every other item is inert text — arrow cursor, no focus stop, no link styling — but an inert item is still exposed to assistive technology with its accessible name, and with its tooltip sentence as its accessible description where it has a tooltip (REQ-SHELL-058). Exactly two items are ever links, the workspace path and the cloud credit, and each is a link whenever it is on screen. Both have visibility conditions (REQ-SHELL-046, REQ-SHELL-047), so the strip may show two links, one, or none — never a third.
- **REQ-SHELL-040**: Activating the workspace-path link opens the workspace folder in the OS file manager; a failure to open is deliberately silent. Activating the cloud-credit link opens the configured cloud account/quick-start page in the default browser.
- **REQ-SHELL-041**: Each safety flag shows a short form and carries one full-sentence explanation, and its tooltip and its accessible description are the identical joined string "{short form} — {explanation}". The flags appear left to right in this fixed order, each with the display condition given: "● CB armed", shown only while the circuit breaker is enabled — "Circuit breaker: Rotaris stops a run that keeps repeating a failing step."; "redaction: always on", shown unconditionally — "Secret redaction: anything that looks like a credential is masked before it reaches a model or the transcript."; "unsaved settings", shown only while the Settings view holds unsaved edits, its explanation stating that runs continue to use the last saved values; then exactly one of "outside-workspace!" (file access is not confined to the workspace) or "workspace-scoped" (it is), one of which is always present; and "mode: {mode}", shown unconditionally — "Permission mode {mode}: how much agents may do without asking. Change it under the composer or in Settings → Runtime." Short forms and explanations use the same words as the Settings controls that produce them, so a flag can be matched to its setting by name.
- **REQ-SHELL-042**: The branch item shows a branch icon in accent color (re-rendered on theme change), the branch name, and an "↑{n}" ahead marker; its tooltip names the branch and states it is N commit(s) ahead.
- **REQ-SHELL-043**: The model item is painted at full text strength rather than the muted treatment used by its neighbours, and carries the tooltip "Runs started from this window use {model}. Change it in the composer or in Settings → Models."
- **REQ-SHELL-044**: The tokens item reads the running total of tokens used, its digits grouped into thousands with commas, then a space, then "tok" — for example "12,480 tok". The background-sessions item reads the number of sessions currently in the background followed by a noun that agrees with that number ("1 bg session", "3 bg sessions").
- **REQ-SHELL-045**: No cost item is present until at least one session has reported usage and a cost figure exists for it; the word "cost" is never shown in the strip without a figure preceding it. Once present the item reads "{figure} cost", the figure being the model provider's reported cost for this workspace's runs so far, or the literal "n/a" for a model with no published pricing. Its tooltip and accessible description read "Cost of this workspace's runs so far: {figure}. Reported by the model provider; an unpriced model reads n/a."
- **REQ-SHELL-046**: No cloud-credit item is present in the strip until a credit balance for the signed-in account is available; while signed out, and before any balance has arrived, the strip contains no such item. Once present the item reads "{balance} credit", with " ⚠ no credit" appended for as long as the cloud service is declining new work for want of credit. Its text is tinted with the accent colour while credit remains, and with a warning colour measuring at least 4.5:1 against the strip background once credit is exhausted. Its tooltip and accessible description read "Rotaris Cloud · {state}. Opens the account page, where credit is topped up."; activating it opens that page per REQ-SHELL-040.
- **REQ-SHELL-047**: Responsive hiding: when the window is narrower than 1180 px the workspace-path item is hidden; below 1080 px the background-session item is also hidden.

### Commands, shortcuts, palette, and keyboard help

- **REQ-SHELL-048**: The window offers one vocabulary of named actions, and every surface presents it the same way: an action that has a keyboard shortcut appears in the command palette under the same label with that shortcut shown beside it, appears in the keyboard-help dialog (REQ-SHELL-054), and appears in the composer's slash catalogue (REQ-SHELL-056). None of those surfaces offers an action the others omit, with two exceptions stated elsewhere: the composer-only additions enumerated in REQ-SHELL-056, and the Escape overlay-dismissal entry, which REQ-SHELL-054 excludes from keyboard help. No surface presents an action the window cannot carry out. Shortcuts fire only while a Rotaris window holds keyboard focus and have no effect while another application is focused.
- **REQ-SHELL-049**: The authoritative shortcut table: Ctrl+1 … Ctrl+7 open the seven views in view order (labels "Open Overview", "Open Workspace", …); Ctrl+K opens the command palette; Ctrl+, opens Settings ("Open Settings"); Ctrl+F opens transcript search ("Search transcript"; switches to Workspace and opens the search panel); Ctrl+L focuses the run composer ("Focus run prompt"; switches to Workspace); Ctrl+Return starts or continues a run ("Start or continue run"; switches to Workspace and submits only when the send control is enabled); Ctrl+Shift+T opens the terminal window ("Open terminal"); F1 shows keyboard help ("Show keyboard help"); Escape carries the label "Close current overlay", with the scope and precedence defined in REQ-SHELL-055. "About & Legal" is a palette-only entry with no shortcut.
- **REQ-SHELL-050**: Composer key handling: Enter submits when the composer has focus; Shift+Enter adds a line break instead of submitting; Ctrl+Return is the window-wide fallback submit.
- **REQ-SHELL-051**: The command palette is an application-modal dialog titled "Rotaris commands", 560×420, accessible name "Rotaris command palette", containing a heading "Commands", a filter field (placeholder "Type an action…", accessible name "Filter commands"), and a results list (accessible name "Available commands").
- **REQ-SHELL-052**: Palette filtering is a case-folded substring match over each command's label, hidden keywords, and identifier; an empty query matches everything; the list refreshes on every keystroke; the first row is auto-selected whenever there are results; Return activates the current row; activation closes the dialog first and then runs the command.
- **REQ-SHELL-053**: Palette rows show the command label followed by its shortcut when one exists. Hidden keywords make commands findable by everyday words — e.g. the terminal command is found by "shell", "console", or "bash", but not by "worktree" — and the keywords themselves are never displayed.
- **REQ-SHELL-054**: F1 opens an informational dialog titled "Rotaris keyboard help" listing "{shortcut} — {label}" (shortcut emphasized) for every registered command that has a shortcut, excluding the Escape/overlay-dismissal entry.
- **REQ-SHELL-055**: Window-level Escape is live only while the Workspace view is showing, and resolves in this order: (1) with the transcript search panel visible, the panel closes and focus returns to the composer; (2) otherwise both compact overlay drawers close and the layout reflows. On the other six views, window-level Escape produces no effect. This requirement governs the window only; it does not state how modal dialogs respond to Escape (see Open Questions).
- **REQ-SHELL-056**: The composer's slash-command catalogue mirrors every palette command (name derived from the command identifier; description "{label} ({shortcut})"), and additionally offers run-control commands `/stop`, `/pause`, `/compress`, `/clear`, `/new`, `/resume`, `/sessions`, `/search`, `/worktree`, `/stash`, `/pop`; argument commands `/model <name>` and `/persona <name>`; and one command per user-invocable skill. Commands that are currently unavailable carry human-readable reasons, including exactly: "No run is active.", "The transcript is empty.", "No git service is available for this workspace.", and "No models are configured. Choose one in Settings.". The catalogue rebuilds when the library or settings change.
- **REQ-SHELL-057**: Shortcuts are written with the host platform's own key names — "Ctrl" on Windows and Linux, the command symbol on macOS. A chord string is split on "+", and a trailing "++" denotes the plus key. Each key is drawn as a separate keycap in small monospace inside a hairline border, but assistive technology receives the whole written sequence as one accessible name: a three-key chord is never announced as three unrelated labels. A sequence that cannot be parsed is displayed verbatim.
- **REQ-SHELL-058**: Any element that shows a tooltip exposes that identical sentence as its accessible description, whether or not the element takes keyboard focus, with the platform-formatted shortcut appended in parentheses where the element has one. No information in the shell is available on hover alone.

### Compact layout and overlay drawers

- **REQ-SHELL-059**: The Workspace view enters compact mode when its own width is below 1180 px, evaluated on every resize and once shortly after construction. In compact mode the context sidebar (agents & todos) and the inspector are removed from the docked three-pane arrangement and shown as full-height overlay drawers above the content — sidebar pinned to the left edge, inspector right-aligned — with visibility following stored drawer-open state. Above the breakpoint they re-dock (sidebar left, inspector right, center stretching), and remembered widths are re-applied once the re-docked panes have actually been shown.
- **REQ-SHELL-060**: Compact drawers are mutually exclusive: opening one closes the other. The drawer toggles are no-ops outside compact mode.
- **REQ-SHELL-061**: With the window at its 1000×680 minimum and the Workspace view showing: both overlay drawers are closed, the centre panel measures at least 850 px wide, the queued-prompts area (height capped at 150 px) and the send control are both fully visible, and activating a drawer toggle leaves exactly one drawer open.
- **REQ-SHELL-062**: Compact-only chrome: sidebar and inspector toggle buttons and drawer close buttons appear only in compact mode. Toggle labels flip between "Agents & todos"/"Hide agents & todos" and "Inspector"/"Hide inspector"; toggle accessible names are "Toggle agents and todos drawer" and "Toggle agent inspector drawer". Close buttons are "×" controls with accessible names "Close agents and todos drawer" / "Close inspector drawer" and tooltip "Close drawer (Escape)". Escape closes drawers per REQ-SHELL-055.
- **REQ-SHELL-063**: Selecting an agent while compact opens the inspector drawer and closes the sidebar drawer.
- **REQ-SHELL-064**: Default pane metrics: sidebar default/min/max width 236/180/520 px; inspector 288/220/560 px; composer pane default height 150 px. Crossing the compact breakpoint and back preserves widths the user set. At the 1000×680 minimum the view never requires horizontal scrolling, because its own minimum width stays within 1000 px.
- **REQ-SHELL-065**: At 1440×900 both side panels are visible and the center panel is at least 700 px wide. The workspace context toolbar must not clip any visible control at 1000×680 even in its busiest state (terminal count and new-output control both showing).

### Resizable panes: dividers, persistence, reset

- **REQ-SHELL-066**: Every multi-pane divider has a 6 px grab area painting a hairline, and can never collapse a pane below that pane's minimum size.
- **REQ-SHELL-067**: Divider drags persist the resulting sizes with a 250 ms debounce; sizes are also captured immediately at moments such as entering compact mode. Capture before first layout is a silent no-op (uninitialized sizes are never persisted).
- **REQ-SHELL-068**: Every divider is keyboard-operable: it takes focus, carries an accessible name beginning with "Resize " (every multi-pane view names its dividers), arrow keys move it by 16 px (left/up shrinks, right/down grows, orientation-aware, clamped at the neighbor's minimum), and Home restores that divider's declared defaults and persists them.
- **REQ-SHELL-069**: Pane layouts are remembered per user and not per workspace: opening a second workspace shows the same pane sizes as the first. They live under the `panels/` namespace of the per-user preference store, keyed by a per-view string that is stable across releases, alongside that view's pane count and one schema-version stamp covering every stored layout (currently 1). Declared defaults are restored instead of stored values whenever nothing is stored, the stored version is not 1, the stored pane count differs from the view's current pane count, or the stored state is empty. Integer values are parsed tolerantly, so a value returned as a string is accepted. Pane sizes are never written under `workspaces/`.
- **REQ-SHELL-070**: Settings offers exactly one control for this, accessible name "Reset panel sizes". Activating it takes effect immediately and asks for no confirmation: every registered divider in every view — including views not on screen at the time — is at its declared default size afterwards, and the notification "Panel sizes reset to defaults." is shown. The result outlives the process: after a relaunch every divider is still at its declared default.
- **REQ-SHELL-071**: A view whose dividers declare no default sizes still opens with a determinate split: the same view at the same window size always produces the same pane proportions, no pane opens at zero size, and no pane opens below its declared minimum. Once such a divider is dragged, the dragged sizes are persisted and restored under REQ-SHELL-069 like any other.

### Agent (persona) pop-out windows

- **REQ-SHELL-072**: There is at most one auxiliary agent window per persona (not per agent instance). Its title is "Rotaris · {persona}" and its initial size 820×620. Opening a window for an agent reuses the persona's existing window when one is already open and otherwise creates it, selects the tab for the requested instance, and shows/raises/activates the window. An unknown agent identifier is a silent no-op.
- **REQ-SHELL-073**: Explicit pop-out or steer actions always open the persona window. An ordinary agent click opens it only when the interface preference "agent pop-out" is enabled; with the preference off, a click selects the agent in the inspector only and no window is created. The preference persists across windows and restarts (default: off).
- **REQ-SHELL-074**: The persona window contains: a header carrying the persona name beside a monospace summary of how many instances the persona has; one tab per instance of that persona, live or finished alike, whose text is the agent's name and whose tooltip is "{state} · {activity}"; and a card headed "Artifacts by {persona} (all instances)" holding one clickable link per artifact published by any of those instances, reading "No artifacts published yet." while there are none.
- **REQ-SHELL-075**: Each instance tab is a scrollable page presenting, in this order: (a) a heading made of a small status dot that pulses only while that instance is live, the agent's name tinted with the persona's assigned colour, and a muted state label; (b) an "Agent transcript" card (accessible name "{name} transcript", minimum height 260 px, empty state "No transcript activity for this agent yet.") carrying only the transcript entries belonging to that agent, in which terminal output shows the same characters, the same cell styling and the same ordering as the main window's preview of the same stream and lags it by no more than one refresh interval (REQ-SHELL-076); (c) a "Context" card giving context used against the context limit and against the compression threshold, plus "{n} tool calls · {elapsed}"; (d) an "Instance controls" card presenting the Model and Reasoning settings read-only — neither can be altered from this window; (e) a "Current activity" card rendering formatted text; (f) a "Tools and artifacts" card listing native tools, MCP-provided tools grouped by server, and the active tools, entry for entry the same list the inspector shows for that instance; (g) a "Steer agent" card holding a plain-text prompt field (placeholder "Add context or redirect this agent…"), a primary "Send steer" button that submits the text and empties the field and does nothing at all when the field is empty, and a danger-styled "Cancel" button that requests cancellation of that instance.
- **REQ-SHELL-076**: Persona-window refreshes are coalesced at 120 ms, so a rapid series of updates produces a single rebuild per interval, and a window that is hidden or closed is not rebuilt at all. Closing the window hides it rather than destroying it, so reopening is instantaneous; a full session-state replacement still reaches open windows on the same coalescing terms.
- **REQ-SHELL-077**: Incremental transcript updates cause an open persona window to rebuild its filtered per-agent slice, so live output appears without a full-session refresh.
- **REQ-SHELL-078**: All persona windows are closed when the main window closes and when a new session starts (the cache is cleared too); they are owned by their main window and do not outlive it.

### Terminal pop-out window

- **REQ-SHELL-079**: Terminal output reaches the user in two forms: as a live preview embedded in the transcript row — shown in the main window and, for the owning agent, in the persona window's transcript card (REQ-SHELL-075) — and as the pop-out terminal window, which is the only surface that accepts input. Previews keep updating whether the terminal window is open or closed, so closing that window leaves the user looking at a preview that is already current. Every surface calls the feature "terminal".
- **REQ-SHELL-080**: The window is reachable from a running transcript row, from the Workspace toolbar's terminal control, which carries a count of currently running terminals, and via Ctrl+Shift+T. The toolbar control can be used before any command has ever run, and the window's empty state covers that situation.
- **REQ-SHELL-081**: There is a single terminal window per main window: a second request raises the existing window rather than opening another. Its title is "Rotaris · Terminal", or "Rotaris · Terminal — {session label}" when the focused session has a label (its name, or its identifier when unnamed). Initial size: 900×620. When the window opens automatically (REQ-SHELL-108) it must not take keyboard focus.
- **REQ-SHELL-082**: The window shows one tab per known terminal stream (agent-foreground and background-session streams), with the tab set carrying accessible name "Terminal sessions". A tab is labelled with the stream's command text elided to at most 28 characters when a command is known for it, and with the stream's display name when none is; its tooltip is "{name} · running" while the command runs and "{name} · exit N" once it has ended. Raw internal stream identifiers never appear in any label or accessible name: agent streams show the persona's human-readable name (for example "Coder 1"), background streams display "Background session {identifier elided to 12 characters}", and unknown streams display "Terminal".
- **REQ-SHELL-083**: Empty state (no streams): a centered block at most 460 px wide titled "No terminal yet" with the body "A terminal appears here as soon as an agent runs a shell command. Start a run in Workspace and this window fills itself." and an action "Go to Workspace" that navigates the main window to the Workspace view. Tabs are hidden while the empty state shows, and vice versa.
- **REQ-SHELL-084**: Repaint cadence: every 120 ms the window refreshes the header of all tabs — a tab that is not in front must not go on displaying a stale "running" state — while repainting only the grid of the tab in front. This ticking stops while the window is hidden and resumes when shown. Tab creation and relabeling are coalesced on the same 120 ms interval.
- **REQ-SHELL-085**: Bringing a specific stream forward creates its tab only if retained screen state still exists for that stream; when nothing is retained — for instance after a session has been re-read from storage — the window remains on its empty state instead of fabricating a terminal. On show, initial focus goes to the take-control button when it is enabled and unarmed, otherwise to the output grid.
- **REQ-SHELL-086**: Closing the window stops its refresh ticking; the transcript preview keeps streaming; the next open rebuilds the window fresh.

### Terminal tab header, controls, and messaging

- **REQ-SHELL-087**: Each tab's header shows: a small status dot (accessible name "Command status"; active color pulsing while running, idle color otherwise); a selectable monospace command label "$ {command}" elided at 90 characters with the full command in its tooltip (accessible name "Command"); a normally hidden "Earlier output dropped" label (accessible name "Scrollback limit reached", tooltip "This terminal produced more output than Rotaris keeps; the oldest lines are gone.") shown when the screen reports truncation; and an outcome label (accessible name "Command outcome") reading "running", "exit {code}", or "exited" when the code is unknown.
- **REQ-SHELL-088**: The controls row contains, in order: "Take control" (a toggle; accessible name "Take control of this terminal"; its description explains that keystroke forwarding is off by default and why); "Interrupt (Ctrl-C)" (accessible name "Interrupt the running command"); "End input (Ctrl-D)" (accessible name "Send end of input to the running command"); an availability-help control (REQ-SHELL-091); a spacer; "Copy all" (accessible name "Copy all terminal output"; copies the entire screen text to the clipboard); and "Kill" (danger-styled; accessible name "Kill the process behind this terminal"; description "Terminates the running process. Asks for confirmation first."). Kill sits on the far side of the spacer so an adjacent misclick cannot kill a process.
- **REQ-SHELL-089**: No keystroke reaches the process until the user has deliberately armed take-control. Arming flips the button label to "Release control" (the label states the state; state is not conveyed by fill alone), records the audit action "took control of the terminal", shows a persistent warning banner titled "You have control" with the body "You are typing into the agent's terminal. Keys you send become part of the command output the agent reads back.", and focuses the grid. Releasing records "released control of the terminal" and clears the banner (unless a process-exit notice occupies the slot).
- **REQ-SHELL-090**: A key pressed while unarmed is never silently discarded: it triggers (once per tab lifetime, re-enabled if the armed or exited state changes) an informational banner titled "This terminal is read-only" with body "It belongs to the agent. Take control to send what you type to the command." and an action button "Take control" that actually arms the toggle.
- **REQ-SHELL-091**: Once the process exits: take-control is automatically disarmed, grid input is disabled, and the four action controls (take control, interrupt, end input, kill) are disabled with the reason "The process has ended, so it cannot accept input." That reason must be reachable through an enabled, keyboard-focusable help control whose accessible description contains it — never only through tooltips on disabled controls. A one-time informational banner "Process exited" shows "{outcome}. The output stays readable and copyable." The output remains readable, selectable, and copyable.
- **REQ-SHELL-092**: Kill is confirmed first by a dialog titled "Kill this command?" with body "The process behind this terminal is terminated immediately.", impact bullets naming the affected command ("$ {command}", or "The command running in this terminal" when unknown) plus "The agent reads the killed command's output as its result." and "Anything the command had not written yet is lost.", and confirm label "Kill command". Declining leaves the process alone; confirming terminates it.
- **REQ-SHELL-093**: Interrupt and end-input require no arming (their intent is unambiguous): interrupt sends the Ctrl-C control sequence, end-input sends Ctrl-D. Grid resizes are forwarded to the emulated screen and the underlying terminal.
- **REQ-SHELL-094**: Any refused terminal action (send key, interrupt, end input, kill) raises a warning banner titled "The terminal did not take that" with body "Rotaris could not {attempt}. The process may have ended already.", where the attempt phrase is one of "send that key", "send {KEY}", "interrupt the command", "end the command's input", "kill the process". Each tab holds a single persistent banner position, and the newest state replaces whatever occupied it.

### Terminal output grid

- **REQ-SHELL-095**: Terminal output is presented as a character grid rather than an append-only text log, which is checkable by behaviour: a command that addresses the cursor overwrites the cells it addresses instead of appending new lines; a command that enters the alternate screen replaces the visible content and, on leaving it, restores what was there before; and a progress indicator that rewrites its own line is seen updating in place, not repeated line after line. The grid renders the screen state it is given and emits the user's keystrokes; its accessible name is "Terminal output", and it accepts keyboard focus both by click and by Tab traversal.
- **REQ-SHELL-096**: Key encoding vocabulary sent to the backend: arrow keys → UP/DOWN/LEFT/RIGHT; Home/End → HOME/END; Page Up/Down → PGUP/PGDN; Tab → TAB; Backspace → BS; Esc → ESC; Return/Enter → ENTER; Ctrl+A…Z → "C-{lowercase letter}". Printable text is sent verbatim. A key with no encoding in this vocabulary produces no transmission at all; the grid does not substitute some other sequence.
- **REQ-SHELL-097**: Key handling priority, in order: (1) copy beats interrupt — Ctrl+C with an active selection (and Ctrl+Shift+C always) copies instead of interrupting; (2) Shift+Tab always moves focus out and is never forwarded, so keyboard focus can always leave an armed terminal; plain Tab also traverses while unarmed; (3) scrollback keys — Page Up/Down and Home/End scroll local history while unarmed; while armed, their Shift- or Ctrl-modified forms still scroll and the unmodified forms go to the process; (4) while unarmed, any printable or named key raises the rejected-input event and is consumed; (5) while armed, keys are forwarded per REQ-SHELL-096.
- **REQ-SHELL-098**: The grid's background is the theme's terminal background colour, and that colour fills the entire widget area throughout a window resize, so no frame ever exposes the platform's default surface colour. The 16 ANSI colours are theme tokens. Reverse video swaps a cell's foreground and background; bold, italic and underline are applied per cell; selected cells are filled with a dedicated selection colour. The cursor is painted only when all three of these hold at once — the process is running, the grid has keyboard focus, and the view is scrolled to the tail — and it is drawn as a filled block while control has been taken and as a hollow outline while the terminal is read-only.
- **REQ-SHELL-099**: The grid's accessible description states the input mode, switching between "Live output of the running command. You have control: what you type is sent to the command. Shift+Tab leaves the terminal, Shift+Page Up scrolls back." and the equivalent ending "Read-only until you take control."
- **REQ-SHELL-100**: Geometry: cell size derives from the theme's monospace face and is re-measured on theme change, after which the grid dimensions are re-reported (otherwise a running command would keep writing into a stale-shaped screen); a fixed 6 px padding gutter surrounds the grid; the grid never reports fewer than 20 columns × 4 rows; the preferred size is 80×24 cells. Grid dimensions are reported to the backend only while the grid is visible and meaningfully laid out, and only when they change — a placeholder-size viewport must never shrink the emulated screen and discard output.
- **REQ-SHELL-101**: Scrollback behaviour: the vertical scrollbar's range equals the number of retained history rows; a refresh leaves the view at the tail only when it was already at the tail, and otherwise leaves the visible rows where they are; wheel scrolling moves the view in the wheel's direction by an amount proportional to the wheel delta; dragging selects whole cells and yields the same selection whether it was dragged forwards or backwards; text extracted from a selection right-trims each row and joins rows with newlines; and a copy attempted with an empty selection puts nothing on the clipboard and reports failure.

### Terminal stream state, delivery, and audit

- **REQ-SHELL-102**: For any one stream, the transcript preview and the terminal window show the same thing at the same time: identical visible screen cells, identical running-or-exited state, and identical truncation indication. Moving between the two never shows the user older output in one than in the other.
- **REQ-SHELL-103**: A command's execution is not throttled by the terminal display. Its completion time and its output are the same whether the terminal window is open, closed, hidden or visible, and when repaints cannot keep up with the rate at which output arrives, no output is dropped and none is shown out of order.
- **REQ-SHELL-104**: Opening a terminal for a command that has already produced output shows the retained output at once — the grid is never blank while history exists for that stream — and no line is ever shown twice, including in the moment when retained output and freshly arriving output are both being displayed. A session read back from storage produces no terminal tabs at all, so commands that ended before the session was stored never appear as live terminals.
- **REQ-SHELL-105**: Stream metadata updates synchronize the displayed command, truncation flag, and running state, and may be applied idempotently. A stream transitions from running to closed exactly once, recording the exit code. The count of running streams feeds the toolbar control. Starting a new session clears all stream state; attaching to another session supersedes the earlier attachment; detaching keeps existing screens readable.
- **REQ-SHELL-106**: Write-back semantics: sending keys to a stream that no longer accepts input fails predictably (reported per REQ-SHELL-094); a resize always resizes the emulated screen — even when the backend is gone — and then the real terminal when possible; kill succeeds only when the stream has a registered kill capability and otherwise reports failure; whether input can be taken at all is queryable and drives control enablement.
- **REQ-SHELL-107**: User terminal input is not an agent tool call: it bypasses permission patterns but is written to the session's permission audit log as user-originated input. Typed characters accumulate per stream and are written to the log as a single entry when Enter submits the line — a held key must not flood the log; Backspace removes from the pending buffer; navigation keys are not logged; a control sequence flushes the pending line and then logs "sent C-{letter}"; taking control, releasing control, and kill log their own sentences. Both the typed line and the command context are secret-redacted before logging. See Data & Formats for the entry shape.
- **REQ-SHELL-108**: The Workspace toolbar terminal control is always enabled, including before any command has ever run, so the feature stays discoverable from a cold start. Its label is "Terminal" or "Terminal ({n})" when any stream is live; accessible name "Open terminal" or "Open terminal ({n} running)"; its tooltip/description states total and running counts, or explains that a terminal appears when an agent runs a command. The total count only ever climbs within a session.
- **REQ-SHELL-109**: Auto-open preference (default off, persisted): when a stream changes while the window is closed, the preference is on, and that stream is running, the terminal window opens without taking keyboard focus. The window is never auto-opened for a stream that has already exited.
- **REQ-SHELL-110**: When session focus changes: stream state is cleared, the terminal window (if open) is closed, streams re-attach to the newly focused session, and the toolbar count resets; if the window had been open, it reopens for the new session without taking focus, so a user who was watching a terminal does not silently lose the window. Focusing an empty session identifier leaves everything closed.
- **REQ-SHELL-111**: Starting a new session closes and discards the terminal window, clears all stream state, resets the toolbar count to zero, and also closes all persona windows and artifact dialogs.

### Transient and persistent feedback surfaces

- **REQ-SHELL-112**: The main window's transient notification is one word-wrapped label, at most 520 px wide, placed at the top right just below the title bar, drawn above the window's other content, and removed 4200 ms after it appears. Its error variant is bordered in the theme's failure colour, which clears 3:1 against the surface behind it (REQ-SHELL-144); after a theme change the notification is still recognisably the error variant. While it is visible, resizing the window keeps it anchored at the top right.
- **REQ-SHELL-113**: The general toast stack sits bottom-right at a fixed width of 360 px, shows at most 3 toasts (the oldest is dismissed beyond that), defaults to a 4200 ms timeout (a non-positive timeout never expires), and offers kinds info/ok/warn/fail with glyphs "i", "✓", "!", "×" and word-form accessible names "Notice: {title}", "Done: {title}", "Warning: {title}", "Failed: {title}" (state is never color-alone). Each toast has a close control ("Dismiss {title}"); toasts never steal focus; the newest toast occupies the position nearest the corner and pushes older ones away from it; a toast arrives with an upward entry animation driven by the theme's motion tokens, and under reduced motion that animation is omitted entirely while the final position and opacity are unchanged. Toasts carry only low-risk acknowledgements: a failure, and anything the user still needs after the toast expires, is shown as a persistent banner instead.
- **REQ-SHELL-114**: A single persistent notice at a time is surfaced by an inline banner under the title bar, carrying severity, title, message, optional copyable details (a copy control appears when details exist), an optional action (label plus action identifier), and a persistence flag. Dismissing clears the notice; dismissing an update-offer notice first records the offered version as waved-off (REQ-SHELL-118).
- **REQ-SHELL-115**: A banner action or an empty-state action performs exactly one of the following, and an action offered under the same identifier from two different places produces the same result in both: navigate to any of the seven primary views; retry the last run or the drafted run; open a named Settings tab, Hooks included; save settings; open a Library tab (artifacts, proposals); install an available update; restart the application; open the cloud account page; start project initialization; resolve project initialization; focus a named session; undo a proposal. No banner or empty-state action performs Git remediation. The terminal window's empty-state "Go to Workspace" action (REQ-SHELL-083) produces the same result as the corresponding view-navigation action offered from a banner.
- **REQ-SHELL-116**: The shell's standard error surface is a persistent ERROR notice with title, message, optional copyable details, and an optional action; it is used for Git refresh failures, checkpoint failures, settings save failures, run failures, and similar.
- **REQ-SHELL-117**: Long-running worktree-merge and checkpoint operations show an indeterminate, window-modal, non-cancellable progress dialog that appears immediately, titled "Merging worktrees" / "Checkpoints" with accessible names "Worktree integration progress" / "Checkpoint progress".
- **REQ-SHELL-118**: The update check begins only after the window is visible. Exactly one waved-off version is remembered at a time, never a list, so a release newer than the waved-off one is offered afresh. An available update raises a persistent INFO notice titled "Rotaris {version} is available" carrying the action "Update now". Download progress is reported into that same notice in whole percentage steps, without a second notice appearing. Dismissing any banner other than the update notice never records a waved-off version.

### Window close, quit protection, shutdown

- **REQ-SHELL-119**: Window-close guards are evaluated in this fixed order, and any of them can abort the close: (1) with unsaved settings present, a user-initiated close raises the save/discard/cancel dialog of REQ-SHELL-124, where Cancel aborts the close; (2) while a worktree integration is running, the close is refused unconditionally by an informational dialog titled "Integration in progress" whose body reads "Keep Rotaris open until the isolated worktree integration finishes."; (3) with runs active, a user-initiated close asks "Quit while a run is active?" — "Quit while {n} runs are active?" for more than one — states that Rotaris will request shutdown of the run(s) and that in-flight work may not finish, and offers Yes and Cancel with Cancel as the default; any answer other than Yes aborts the close.
- **REQ-SHELL-120**: Once the guards pass, the window is committed to closing: no new background work may start on the closing window.
- **REQ-SHELL-121**: Shutdown is clean and complete, and is checkable from outside the process. Active runs are asked to stop before the process ends, and no run keeps consuming a model provider afterwards. Once the main window has gone, no persona window, artifact dialog or terminal window is left on screen. A diagnostics run that was in progress leaves a complete, readable diagnostics directory rather than a truncated one. An update download that was in progress leaves behind no partially written and no locked file. The shutdown itself raises no error dialog, produces no crash report, and does not change the exit code the run would otherwise have had (REQ-SHELL-004).
- **REQ-SHELL-122**: The count the quit prompt reports is the number of runs active at that moment: on a host that coordinates several sessions it is the number of sessions currently running; on a single-run host it is 1 while a run is active and 0 otherwise. The prompt's singular and plural wording follows that number (REQ-SHELL-119).
- **REQ-SHELL-123**: Auxiliary windows (persona, terminal) belong to their main window and are destroyed with it even if an explicit close was missed; a terminal window that outlives its stream attachment shows retained screens read-only.
- **REQ-SHELL-124**: The unsaved-settings dialog is a warning titled "Unsaved settings" asking "Save workspace settings before leaving?" with the informative line "Discard restores the last saved values." and buttons Save (default), Discard (destructive), Cancel. Save proceeds only if saving succeeds (a failed save blocks the transition); Discard restores the saved values and proceeds; Cancel blocks. The same gate protects leaving the Settings view, opening another workspace, and closing the window.

### Sessions: new, browse, focus

- **REQ-SHELL-125**: Starting a new session while a single-run host has an active run is refused with the error notification "Finish or cancel the active run before starting a new session." Otherwise a modal dialog titled "Start session", at least 460 px wide, collects two optional choices: Git worktree isolation, for which the user either supplies a branch name or accepts a generated one, and the session's sandbox mode. Cancel ends the flow and clears nothing. Accepting clears session state, closes every pop-out window, dialog and terminal window, empties the composer, and leaves the Workspace view showing. On a multi-session host the previous session's focus is released first, and its run carries on in the background.
- **REQ-SHELL-126**: Opening the session browser while a single-run host has an active run is refused with "Finish or cancel the active run before switching sessions." Otherwise a searchable session list appears; typing narrows it; resuming returns the selected session and focuses it.
- **REQ-SHELL-127**: Focusing a session: multi-session hosts switch focus (a refusal means no switch happens); single-run hosts load the persisted session; both land on the Workspace view. A focus change re-binds composer and recovery state, restores the per-session sandbox badge, and swaps terminal stream attachment per REQ-SHELL-110.

### Theming

- **REQ-SHELL-128**: Three built-in themes are offered in order: "rotaris-dim" (the default), "nocturne", and "high-contrast". Requesting an unknown theme name degrades silently to the default — a stale stored value must never prevent startup or raise an error.
- **REQ-SHELL-129**: Each theme declares a light/dark flag, token groups (color, spacing, radius, size, typography, motion, elevation), and hard accessibility floors of 4.5:1 for text contrast and 3.0:1 for boundary contrast. Default-theme shell metrics: navigation rail width 68, nav item width 54, status dot 6, focus ring 2, hairline 1, title bar height 44, status bar height 26 (px); spacing scale 4/8/12/16/24; corner radii 5/8/14 and a fully rounded "pill" value.
- **REQ-SHELL-130**: Applying a theme updates, in effect: all styled application widgets, native dialog/menu/caret/disabled-text colors (a dark theme must not leave light native surfaces), every live top-level window (windows that are mid-close are skipped safely, without crashing), and finally notifies self-painting widgets. Re-selecting the already-active theme still applies fully (startup idempotence).
- **REQ-SHELL-131**: A theme choice is committed to the preference store at the moment it is made, so a choice followed immediately by a crash or a power loss is still in force at the next launch. A stored theme name is not rejected when it is read back; an unrecognised name degrades per REQ-SHELL-128.
- **REQ-SHELL-132**: End-to-end theme-switch guarantees: after a switch, no widget in any of the seven primary views retains a color from the previous palette; unsent composer text, the active view, and every divider's sizes are preserved; the choice persists and is reapplied on next launch; a stored name for a removed theme degrades to the default at startup; each built-in theme renders all seven primary views without error.
- **REQ-SHELL-133**: The Settings interface tab carries a theme dropdown with accessible name "Theme" and a non-empty accessible description, listing every registered theme by its display label and opening with the running theme already selected. A hint label beside the dropdown shows the description of whichever theme is currently highlighted. Choosing a theme applies it at once, with no relaunch. Which theme is active is legible as text and not by colour alone.
- **REQ-SHELL-134**: Derived colors (persona shades, chips) that miss their contrast floor on their actual background are corrected by raising perceptual lightness only — hue and saturation preserved, adjustment only upward, capped near-white — never by darkening.

### Motion and reduced motion

- **REQ-SHELL-135**: Reduced-motion resolution precedence: (1) an explicitly stored in-app setting; (2) OS-level detection — on Windows, the "Turn off all window animations" accessibility setting; (3) otherwise motion is on. The value is read at each animation start rather than cached, so flipping the in-app setting takes effect without relaunch.
- **REQ-SHELL-136**: Under reduced motion: status-dot pulsing never starts and dots rest at full opacity; toggle knobs land instantly; spinners paint a static arc with no animation timer running; the toast rise is skipped while the final position and opacity are kept. Outcomes are always preserved; only travel is removed.
- **REQ-SHELL-137**: Spinners: sizes small/medium/large are 12/16/24 px with stroke widths 1.25/1.5/2.0; one revolution takes 800 ms at 16 ms frames with a 90° head arc over a faint track; the default accessible name is "Working" (an unnamed turning shape is invisible to a screen reader); animation runs only while the spinner is visible.

### Shell accessibility contract

- **REQ-SHELL-144**: Two contrast thresholds apply: 4.5:1 for normal text, and 3:1 for large text — 18 px or larger, or 14 px or larger when bold — and for non-text boundaries such as borders, focus rings and icons. Measured over all seven primary views and every tab page inside them: no interactive control announces an empty accessible name, and every rendered label meets its threshold against the background actually painted behind it once all styling has been applied.
- **REQ-SHELL-145**: Theme tokens carry these guarantees, each measured against every background the token is actually painted on: every state text colour (running, waiting, done, info, fail), the primary, secondary and tertiary text colours, and the readable accent shade clear 4.5:1 on every text background; strong borders and the focus colour clear 3:1 on every boundary background; a primary button's label stays at or above 4.5:1 in its rest, hover and pressed states; disabled text is dimmer than enabled text — below half the enabled contrast ratio — while still clearing 3:1; every persona base colour and every shade given to a concurrently running instance clears 4.5:1, and no two concurrently running instances are given the same shade.
- **REQ-SHELL-146**: Auxiliary windows meet the same contract independently of the main sweep: the terminal window has all controls named and no contrast violations both while a command runs and after it exits, and its empty state is announced and explained.
- **REQ-SHELL-147**: Every dropdown in every primary view sizes itself to its selected entry (over-long values may elide visually but are announced in full); a dropdown must never visually swallow its current value when space is tight.
- **REQ-SHELL-148**: Self-painted navigation controls draw the keyboard-focus ring entirely within their own bounds, at the theme's focus-ring width and color, so no part of the ring is cut off; divider handles take focus and are named (REQ-SHELL-068).
- **REQ-SHELL-149**: State is never conveyed by color alone anywhere in the shell: the session chip carries the status word beside its dot; the take-control button re-labels for its state; toast kinds have word-form accessible names; the active theme is shown as text; keycap sequences announce the written chord; demo-mode and service-unavailable refusals use explicit messages — exactly "Artifacts are read-only in demo mode.", "Artifact not found in the loaded session.", "Proposal actions are unavailable in demo mode.", "Settings are read-only in demo mode.", and "Worktree integration is unavailable in demo mode."

### Update responsiveness

- **REQ-SHELL-150**: A rapid succession of changes never makes the shell unresponsive and never leaves it showing stale content. A single isolated change is visible without perceptible delay. While changes keep arriving, the affected surface is redrawn at least once every 120 ms, and after the last change of a burst the surface shows that final change. No intermediate state of a burst is required to be drawn.
- **REQ-SHELL-151**: A surface that is not on screen — a hidden or closed window, or a panel behind another view — consumes no redraw work while it is not on screen, and shows fully current content the instant it becomes visible: it never presents a stale frame first, and no catch-up redraw is visible after it appears. This holds for the persona windows, for the terminal window, and for the shell's panels.

### Tab strips and vertical navigation lists

- **REQ-SHELL-152**: Tab strips throughout the shell behave alike. When a strip first appears, its first tab is the active one. From the keyboard, Left and Right move to the neighbouring tab and select it in the same step, Home selects the first tab and End the last, and movement stops at either end rather than wrapping around. Switching tabs exchanges panes that are already built, so no tab shows an intermediate blank state. A selection restored from a stored key the strip does not contain leaves the tab that is currently active still active — for example, a stale `interface/settingsTab` value falls back to the models category — and never clears the selection. A selection the user did not make produces no effect beyond showing that tab's pane.
- **REQ-SHELL-153**: Vertical navigation lists throughout the shell behave alike. Arrow Up, Arrow Down, Home and End move focus without changing the selection, and selecting requires Space or Enter, so moving focus across entries never causes the passed-over destinations to be shown. The selected entry is marked by a rule down its left edge, and its accessible description says so in words: "Selected, marked with a rule down its left edge." for the selected entry and "Not selected." for the others. Entry glyphs are sized from the theme's type scale, so icons grow when text does. The main window's navigation rail is not a vertical navigation list in this sense: it follows the button semantics of REQ-SHELL-027 through REQ-SHELL-032.

### Miscellaneous shell behaviors and edge cases

- **REQ-SHELL-154**: Artifact detail dialogs are per-artifact windows: a repeat request for the same artifact raises the open dialog instead of opening a second one; in demo mode the request is refused with "Artifacts are read-only in demo mode."; an unknown artifact identifier answers "Artifact not found in the loaded session." All artifact dialogs close on window close and on new session.
- **REQ-SHELL-155**: Restoring a checkpoint while a run is live is refused, and a run whose liveness cannot be determined counts as live for this purpose, so the restore is refused there too. A session recorded as running whose process is no longer present has its recorded status corrected, and the correction is announced through a WARNING notice titled "Session marked interrupted". At startup the window requests the checkpoint listing for the session that is selected first.
- **REQ-SHELL-156**: While the checkpoint backend is busy, a checkpoint-listing request retries every 150 ms with a single pending retry that always targets the latest requested session — clicking quickly from one session to the next cannot accumulate queued retries.
- **REQ-SHELL-157**: Prompt history and stash persist per workspace under `<workspace>/.rotaris/` using atomic writes that leave no temporary files behind. A failed save raises the persistent notice "Could not save prompt history" — "Rotaris will keep prompts in memory for this window." — and prompts continue to work in memory for that window.
- **REQ-SHELL-158**: When the most recently polled cloud-credit balance shows no credit, starting a run raises a confirmation offering "Start anyway". The confirmation is answered from that already-polled balance: no network request is made between the user asking for the run and the confirmation appearing, so the confirmation cannot be delayed by a slow or unreachable cloud service. Choosing "Start anyway" starts the run; declining starts no run and opens the cloud account page in the default browser.
- **REQ-SHELL-159**: A workspace's composer draft is stored under `workspaces/{workspace-key}/composerDraft` in the per-user preference store, with the empty string as its default, and is written with debouncing while the user types rather than on every keystroke. The text standing in the composer when the workspace is closed is the text the composer holds when that workspace is opened again.

## Data & Formats

### Command-line grammar

```
rotaris [workspace] [--demo] [--version] [--diagnostics [light|deep]] [--diagnostics-output DIR]
```

`--version` output format: `Rotaris {version}\n` on stdout, exit 0. Usage errors exit 2.

### Per-user preference store

A single platform-standard per-user preference store, scoped by organization "Rotaris" and application "Rotaris". The physical location and encoding are platform-defined (see Open Questions); the observable contract is the key set, value semantics, and defaults:

Keys are slash-namespaced. The namespaces in use are `workspace/` (startup workspace state), `appearance/` (theme), `ui/` (motion), `interface/` (shell toggles), `display/` (transcript display), `panels/` (pane layouts), `updates/` (update state), and `workspaces/` (per-workspace state).

| Key | Meaning | Default |
|---|---|---|
| `workspace/lastOpened` | workspace path used by startup resolution | unset |
| `appearance/theme` | active theme name; unknown values degrade to the default theme | unset → default |
| `ui/reduced_motion` | reduced-motion override; boolean; absent means "user has not said" | unset |
| `interface/agentPopout` | agent click opens the persona window | false |
| `interface/terminalPopout` | auto-open the terminal window when a command starts | false |
| `interface/worktreeCleanupPrompt` | offer worktree cleanup after merges | true |
| `interface/settingsTab` | last Settings category; stale values fall back to the models category | models |
| `display/autoCollapseTools` | collapse tool output by default | false |
| `display/groupToolCalls` | group consecutive tool calls | true |
| `panels/version` | one schema-version stamp covering all stored pane layouts | 1 when written |
| `panels/{view-key}/state`, `panels/{view-key}/panes` | per-divider layout state and pane count, global per user, keyed by a stable per-view string | unset |
| `updates/dismissedVersion` | the single remembered waved-off version | unset |
| `workspaces/{workspace-key}/composerDraft` | per-workspace composer draft, debounced writes, keyed by workspace path | `""` |

Pane-size values are never written under `workspaces/`. Preference values may come back from native stores as strings; integer parsing is tolerant.

### Workspace-local files

`<workspace>/.rotaris/` holds per-workspace prompt history and stash, written atomically with no leftover temporary files. Save failure degrades to in-memory behavior with a persistent notice (REQ-SHELL-157).

### Terminal stream event model

- Each terminal stream has a stable identifier shaped `{kind}:{key}`. Two kinds exist: `fg:` for an agent's foreground terminal, where the key identifies the agent, and `bg:` for a background-session terminal, where the key is the session identifier. An identifier carrying no `:` separator, or an unrecognized kind, resolves to the fallback display name "Terminal". These raw identifiers appear in permission-audit summaries but never in window labels or accessible names (REQ-SHELL-082).
- Output is delivered per stream as ordered frames carrying a monotonically increasing sequence number. Metadata frames convey command text, running state, and truncation state, and applying the same metadata frame twice has the same effect as applying it once; data frames advance the emulated screen. A viewer that attaches after output has already been produced is given the output accumulated so far, and a frame whose sequence number has already been applied to a stream is not applied to it again (REQ-SHELL-104).
- Each live stream may expose a control surface with: send-keys (text plus an optional end-of-line), optional resize (columns, rows), and optional kill. Absence of a capability makes the corresponding UI action fail predictably.
- Key vocabulary shared between user input and the agent's own input path: `UP DOWN LEFT RIGHT HOME END PGUP PGDN TAB BS ESC ENTER` and `C-<lowercase letter>` for Ctrl chords; all other input is verbatim text.

### Permission audit entries for user terminal actions

Each entry records: decision `user-input`, source `user`, tool name `terminal`, the reason sentence "The user acted in the terminal directly; no policy applies.", and a summary of the form `terminal {stream-id}: {detail} (in: {command})`. One entry per submitted line of typed input; control sequences log as "sent C-{letter}"; take-control, release-control, and kill log their own sentences. Typed lines and command text are secret-redacted before writing.

### Bundled assets read by the shell

- A third-party license bundle as a plain-text file shipped inside the installed build (opened locally from the About page; may legitimately be absent).
- A build-identifier text file (single stripped line; absent/unreadable means no build id).
- A vector brand-mark asset (missing or unrenderable degrades to the "R" placeholder).
- Three bundled font families covering display, body, and monospace roles (failure to load falls back to host fonts).

### Legal document URL set

Base `https://rotaris.ai` with paths `/privacy`, `/eula`, `/terms`, `/acceptable-use`, `/widerruf`, opened in the system default browser.
