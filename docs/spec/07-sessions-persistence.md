# Session Persistence, Resume, and Background Sessions

## Overview

Every run persists its complete observable state under a per-session directory inside the workspace, written incrementally and atomically so that a crash loses at most a small, bounded window of recent changes. A persisted session can be listed, resumed with its full transcript and metrics intact, followed live from another process through its durable event history, repaired when the process that owned it died while its record still asserts a run in progress, exported as a standalone trajectory document, and deleted cleanly. One shared run lifecycle serves every host — interactive terminal UI, headless command line, embedding API, and desktop — so locking, background execution, message-limit pauses, cancellation, and terminal results behave identically regardless of how the run was started.

## Requirements

### 1. Storage Locations and On-Disk Layout

- **REQ-SESSION-001** — A session's own files MUST be reachable at `<base_workspace>/.rotaris/sessions/<session_id>/`, where `<base_workspace>` is the workspace path the run was invoked against (`--workspace/-w`, defaulting to the current directory) and `<session_id>` is the id of REQ-SESSION-009. One workspace path plus one session id MUST resolve to that one directory from every surface — terminal UI, full CLI, headless CLI, embedding API, and desktop — and binding the run to a worktree MUST NOT move it: per REQ-SESSION-085 the worktree becomes the run's effective root and is what the state records as `workspace_root`, but the directory anchor stays the invoking workspace. Exactly two kinds of session-derived data are written outside that directory: the workspace-level improvement-artifact store of REQ-SESSION-007 and the checkpoint refs of REQ-SESSION-162.
- **REQ-SESSION-002** — After a session's first successful state save, its directory MUST hold `state/`, `evidence/`, `metadata.json`, `summary.md`, `metrics.json`, `issues.json`, and `timeline.jsonl`. Of these, `metadata.json` is written by every save (REQ-SESSION-028); the others are either rewritten by a save or created when absent by diagnostics initialization (REQ-SESSION-132). The remaining names appear only once the matching activity has occurred and MUST NOT be assumed present by a reader: `lock` (only while a process owns the session), `artifacts/` (the per-session artifact store, holding `index.json` and artifact bodies), `evidence/debug.log` (once per-session logging attaches, REQ-SESSION-142), `evidence/events.jsonl` (once the event history opens, REQ-SESSION-089), `evidence/events.meta.json` (only after a trim, REQ-SESSION-144), `.message_limit_paused` (REQ-SESSION-107), `improvement_artifacts/`, `state/transcript_archive.jsonl`, and the `run.log` alias. Apart from a `snapshot.json` inherited from the legacy layout (REQ-SESSION-005), no other name is written at the session-directory root.
- **REQ-SESSION-003** — `state/` MUST contain `resume.json` (the resumable session state minus bulk fields), `ui_transcript.json` (shape `{"events": [...]}`), `ui_edit_diffs.json` (shape `{"diffs": [...]}`), and `run_config.json` (written once at session start). For sessions driven by the terminal UI host it MAY additionally contain `transcript_archive.jsonl` (evicted transcript pages).
- **REQ-SESSION-004** — Inside `evidence/`, the names `tool-calls.jsonl`, `model-input.jsonl`, `context-selection.jsonl`, `report-validation.jsonl`, `memory.jsonl`, `permissions.jsonl`, and `conversations/index.json` MUST exist from the first state save onward (REQ-SESSION-132); `debug.log` (per-session log), `events.jsonl` (the durable event history), `events.meta.json` (the truncation sidecar), and per-conversation event files under `conversations/event_logs/<conversation_id>/events/*.json` MUST use exactly those names when they are produced, per REQ-SESSION-002.
- **REQ-SESSION-005** — Session directories written by older versions MAY additionally hold a whole-state `snapshot.json`. The current version MUST never write that file and MUST read it only when `state/resume.json` is absent (see REQ-SESSION-037).
- **REQ-SESSION-006** — `metadata.json` and `summary.md` MUST be derived sidecars, rebuilt from state on every save; a loader MUST take its facts from the state files and never from these.
- **REQ-SESSION-007** — Improvement artifacts referenced by the session state MUST be persisted under `<session_dir>/improvement_artifacts/` and also copied to the workspace-level store at `<workspace>/.rotaris/improvement_artifacts/`; both copies MUST survive resume.
- **REQ-SESSION-008** — `run.log` at the session-directory root MUST be a backward-compatible alias for `evidence/debug.log`: a relative symlink where the platform permits, else a one-time file copy. It MUST be created only when the session's log actually lives at `evidence/debug.log`, and MUST never be overwritten if it already exists.

### 2. Session Identity

- **REQ-SESSION-009** — New session ids MUST have the shape `YYYYMMDD-HHMMSS-` followed by 12 lowercase hexadecimal characters, matching the regular expression `^\d{8}-\d{6}-[0-9a-f]{12}$`. The id MUST be minted before the first state write is persisted, so a host can name and display the run before any work happens.
- **REQ-SESSION-010** — The session directory's name MUST equal the session id, and subsystems MAY rely on this equivalence as a fallback resolution rule (e.g. resolving a diagnostics key, event-history key, or scheduler binding from a directory path).
- **REQ-SESSION-011** — A host MUST be able to pre-name a new session by supplying the session id in the run request (so the run is addressable and displayable before any worker output arrives); a supplied new-session id MUST be ignored when the request resumes an existing session.
- **REQ-SESSION-012** — Session ids MUST never be reused. Follower and history consumers are entitled to assume that two different histories never share one session path (see REQ-SESSION-149).

### 3. Resumable State: Schema Rules and Defaults

- **REQ-SESSION-013** — The persisted session-state schema version MUST currently be `1`, and every persisted state MUST carry a `schema_version` field defaulting to the current version.
- **REQ-SESSION-014** — `created_at` and `updated_at` MUST be UTC timestamps; their JSON serializations MUST end with a `Z` suffix. `workspace_root` MUST be persisted as a string path.
- **REQ-SESSION-015** — Loading a state payload with absent optional keys MUST succeed by applying defaults (legacy tolerance is the general schema rule): missing check-suite record loads as null; pre-cost snapshots load with an "unavailable" cost; pre-attribution snapshots load with empty attribution strings. Field defaults MUST include: empty config snapshot, empty transcript events, empty edit-diff list, empty child-state list, empty report-artifact list, null todo states, null outer-loop progress, null token usage, execution status `idle`, empty exhausted-model list, message count 0, null message limit, and null wait state.
- **REQ-SESSION-016** — Run-audit facts MUST be recorded at session start both on the state and into `state/run_config.json`: run intent (default empty), permission mode (default empty), resolved check suite (default null), sandboxed flag (default false), and sandbox backend name (default empty). For snapshots written before these fields existed, the empty/false defaults describe those runs accurately rather than standing in for unknown data, and MUST NOT be backfilled.
- **REQ-SESSION-017** — Requirement attribution fields (`requirement_id`, `unit_id`) MUST default to empty strings for hand-started runs and MUST be set only when requirement-driven execution creates the session. Older snapshots MUST load via defaults without a schema version bump.
- **REQ-SESSION-018** — A session MAY carry an optional worktree binding record with fields `path`, `branch`, `base_branch`, `base_revision`, `created_by_session` (default true), `merge_status` (one of `ready`, `integrating`, `merged`, `merge_failed`; default `ready`), and `integration_session_id` (default null). The default null binding keeps pre-worktree snapshots loadable.
- **REQ-SESSION-019** — The session state MUST carry a `checkpoints` list, ordered oldest-first (newest last), where each entry maps an iteration to the git ref and commit that restore the tree as it stood at the end of that iteration (see Data & Formats). This list is the durable checkpoint mapping and MUST survive resume; entries MUST be pruned together with their refs.
- **REQ-SESSION-020** — The state MUST carry an `internal` boolean (default false). Internal sessions (machinery such as worktree-integration runs) MUST be durable on disk but hidden from normal session listings.
- **REQ-SESSION-021** — The state MUST carry a run-type marker distinguishing ordinary user-task runs (the default) from improvement and integration runs. The run type MUST be stamped at session creation and never changed on resume, so the kind of run is recoverable from disk alone and not only from the live process.
- **REQ-SESSION-022** — Global counters MUST be persisted: total tool-call count, global token aggregate, global cost aggregate, compression count, per-agent metrics (tool-call count, per-tool call counts, token usage, cost, compressions, last prompt-token count), and root-context token count. The default cost aggregate MUST read as "source unavailable" and render as "—", so an unpriced run never displays as free.
- **REQ-SESSION-023** — Compression-deduplication ids MUST be persisted keyed by agent name, with the empty string used for anonymous agents, so that compression accounting is exactly-once across resumes.
- **REQ-SESSION-024** — A provider refusal caused by an exhausted quota (HTTP 429, or an equivalent insufficient-quota rejection) MUST leave a durable mark on the session: the refused model is appended to the persisted `exhausted_provider_models` list as `<provider>/<model>` when the provider is known, and as `<model>` alone when it is not. From that moment on, and equally after the session has been closed and reloaded, no automatic model choice and no automatic retry inside that session may select a model whose identifier matches a list entry by exact string equality in the same form the entry uses.
- **REQ-SESSION-025** — These interactive-wait fields MUST be persisted with the session and MUST come back unchanged when it is reloaded: `pending_questions`, gaining an entry when a question action fires and losing it when that question's tool result arrives (REQ-SESSION-129); `pending_approvals`, a map from request id to the payload of the tool call suspended on interactive approval, an entry disappearing when the request is answered, when it times out, or when it is cancelled; `wait_state`, non-null while and only while the run is suspended on provider quota; `verifier_state`, where null means that no check is running at that moment and never that a check ran and found nothing; and `gate_warning`, a string that survives across individual checks and is cleared only when a completion gate records a decision (the `completion_gate_decision` timeline entry of REQ-SESSION-134). `pending_questions` and `pending_approvals` are the only inputs to `metadata.json`'s `awaiting_input` (REQ-SESSION-031).
- **REQ-SESSION-026** — A mid-session runtime model override (active model key and runtime model configurations) MUST persist across calls and across reloads of the session.
- **REQ-SESSION-027** — Serialization MUST round-trip loss-free: deserializing a state's own JSON serialization MUST reproduce an equal state.

### 4. Saving State

- **REQ-SESSION-028** — Every state save MUST write the split layout: (re)create the session directory, ensure all inspection files exist (create-if-missing, see REQ-SESSION-132), then atomically write `state/resume.json`, `state/ui_transcript.json`, `state/ui_edit_diffs.json`, `metrics.json`, `summary.md`, and finally `metadata.json`. No whole-state `snapshot.json` may be written.
- **REQ-SESSION-029** — `state/resume.json` MUST hold the session state with its bulk fields emptied: `config_snapshot` written as an empty object, `transcript_events` and `ui_edit_diffs` as empty lists, and every entry of `report_artifacts` reduced to a reference carrying only `id`, `agent_name`, `status`, and `path`. Transcript events, edit diffs, and the config snapshot remain recoverable from `state/ui_transcript.json`, `state/ui_edit_diffs.json`, and `state/run_config.json` respectively (REQ-SESSION-036); a report artifact's body is not duplicated under `state/` and is read from the session artifact store at the `path` its reference carries.
- **REQ-SESSION-030** — `metadata.json` MUST contain exactly these keys: `session_id`, `created_at`, `updated_at` (ISO-8601 strings), `execution_status`, `schema_version`, `internal`, `worktree` (the binding record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Every attribute a listing shows about the session itself MUST be one of these keys — making a new attribute list-visible is a change to this key set, not a reader-side extension — and the only other file a listing may consult is that session's `lock`, and only to decide liveness (REQ-SESSION-056, REQ-SESSION-105). Readers MUST tolerate directories written by older versions by defaulting absent keys: `checkpoint_count` → 0, `task_title` → the session id, `requirement_id` and `unit_id` → empty string, `awaiting_input` → false.
- **REQ-SESSION-031** — `awaiting_input` MUST be true exactly when the state holds any pending approvals or pending questions, so a run that is waiting on human input can be identified from any surface and remains identifiable after a restart.
- **REQ-SESSION-032** — `task_title` MUST be derived from persisted todo state as the last non-blank task name across phases (the newest top-level task), skipping blank names and empty phases; it MUST be empty when there is none.
- **REQ-SESSION-033** — Every state file MUST be written atomically: content is written to a temporary file in the destination directory and atomically renamed into place, a crash during the write therefore leaves either the previous complete file or the new complete file, and never a partially written one. On Windows, a transient access-denied error on the rename (antivirus, indexer, or cloud-sync holding a handle) MUST be retried up to 5 times with exponential backoff starting at 0.05 s (0.05, 0.1, 0.2, 0.4, 0.8 s). The temporary file MUST always be removed.
- **REQ-SESSION-034** — Writes MUST be incremental in the crash-loss sense: the resumable core is one small file, derived sidecars are regenerated, and high-volume history goes to append-only JSON-lines files. A crash MUST lose at most the un-flushed debounce window plus one partial trailing JSON line.
- **REQ-SESSION-035** — A save MUST stamp `updated_at` with the current UTC time before writing.

### 5. Loading State, Legacy Fallback, and Corruption

- **REQ-SESSION-036** — Loading MUST first try the split layout: read `state/resume.json`, then rehydrate transcript events from `state/ui_transcript.json` (key `events`), edit diffs from `state/ui_edit_diffs.json` (key `diffs`), and the config snapshot from `state/run_config.json` (key `config_snapshot`, only when it is an object). Each of these three secondary files is optional; a missing one leaves the corresponding field empty (partial recovery, not failure).
- **REQ-SESSION-037** — If `state/resume.json` is absent, the loader MUST fall back to the legacy whole-state `snapshot.json`. If that is also absent, loading MUST fail with a not-found error whose message is `Session snapshot not found for <id>`.
- **REQ-SESSION-038** — On either load path, a `schema_version` greater than the supported version MUST be refused with the error message `Unsupported session schema version: <n>` — an incompatible snapshot is refused, never lossily restored.
- **REQ-SESSION-039** — A legacy-layout session, once resumed and saved, MUST transition permanently to the split layout: subsequent loads read `state/`, and the original `snapshot.json` MUST be left on disk byte-identical — never rewritten, never deleted, never preferred again.
- **REQ-SESSION-040** — Two read modes MUST exist: a full open (used to run or resume a session) that applies post-deserialization repairs (see REQ-SESSION-170), and a read-only snapshot read (used by display-only consumers) that performs the same read with no repairs and no filesystem writes.
- **REQ-SESSION-041** — Corruption tolerance MUST live at the consumer: a corrupt `resume.json` propagates a parse error from the loader, and every user-facing caller MUST catch it and degrade — the terminal UI picker notifies `Corrupt session snapshot: <detail>`, stale repair treats it as "nothing to do", checkpoint-ref cleanup skips the session, and listing paths skip the entry.

### 6. Session Listing

- **REQ-SESSION-042** — Listing MUST scan the sessions root one level deep and silently skip any entry that is not a directory, holds no `metadata.json`, whose `metadata.json` does not parse as JSON, or whose `updated_at` is absent or unparseable. Surviving entries are returned as the records stored in `metadata.json`, with reader-side defaults applied per REQ-SESSION-030, filtered per REQ-SESSION-044, and ordered by `updated_at` descending so the most recently updated session comes first. Building the list reads no file other than each entry's `metadata.json`; a presentation layer that marks stale sessions additionally reads that session's `lock` file and nothing else (REQ-SESSION-056, REQ-SESSION-105).
- **REQ-SESSION-043** — A missing sessions root MUST produce an empty list rather than an error. A workspace in which no run has yet taken place is an ordinary state.
- **REQ-SESSION-044** — Default listing MUST exclude sessions whose metadata `internal` flag is truthy; an explicit include-internal option MUST return everything (used by recovery and machinery).
- **REQ-SESSION-045** — One corrupt session MUST never cost the listing the others: every other session still appears.

### 7. Session Locking

- **REQ-SESSION-046** — The lock is a file named `lock` at the session-directory root, created via an atomic exclusive-create operation, containing JSON `{"pid": <int>, "acquired_at": "<UTC ISO timestamp>"}`.
- **REQ-SESSION-047** — Lock acquisition MUST return success/failure rather than raising. When the lock already exists, exactly one stale-reap attempt MUST be made (two create attempts total): read the existing lock's pid; if the pid parses and that process is alive, acquisition fails and the lock is respected; if the pid is unreadable, absent, or dead, the stale lock is removed and the exclusive create retried once.
- **REQ-SESSION-048** — Creating a session MUST persist the initial state first, then acquire the lock; an acquisition failure at creation raises an error with the message `Unable to acquire lock for session <id>`. A freshly created session is left lock-held by its creator.
- **REQ-SESSION-049** — Releasing the lock MUST first tear down the session-scoped shared services holding long-lived subprocesses (MCP servers, language servers) and then remove the lock file; releasing a missing lock is a no-op.
- **REQ-SESSION-050** — No more than one process may hold a given session's lock at any moment; several locked background sessions MAY nonetheless coexist within a single workspace.

### 8. Process Liveness Probing

- **REQ-SESSION-051** — The pid liveness probe MUST answer "dead" for any pid ≤ 0, MUST never raise, and MUST answer "alive" whenever the outcome is uncertain. The two error directions are not equivalent: answering "dead" for a live process lets a restore run concurrently with work still in flight, while answering "alive" for a dead one costs the user nothing worse than invoking the explicit repair step.
- **REQ-SESSION-052** — On POSIX platforms: a process-not-found result proves death; a permission-denied result MUST count as alive (the probe was refused, not answered); any other probe error MUST count as dead only when the platform semantics prove absence, otherwise alive.
- **REQ-SESSION-053** — On Windows: the probe MUST NOT deliver any signal or console control event to the target process (in particular, implementing the probe as a null signal is a defect there, because it injects a real console interrupt into the target). Only an OS-level "no such process / invalid parameter" error proves absence; a still-running indication means alive; access denied or any other failure MUST count as alive.
- **REQ-SESSION-054** — The following residual limitations are accepted, documented behavior (not defects to be silently "fixed" in ways that break the resolve-toward-alive rule of REQ-SESSION-051): when the operating system recycles a pid onto an unrelated process, the session reports alive until that unrelated process exits; a session driven from a different machine across a shared filesystem reports as dead on this machine (an unsupported topology); and on Windows an already-exited process can keep reporting alive while any open handle to it survives.

### 9. Stale-Session Detection and Repair

- **REQ-SESSION-055** — Exactly five `execution_status` strings assert that a run is in progress: `starting`, `running`, `background`, `pausing`, `cancelling`. The test is exact, case-sensitive equality against that set; every other value — whether it belongs to the wider vocabulary of REQ-SESSION-073 or is unknown to this version — MUST answer "no run in progress". Given one persisted status, every surface that asks the question MUST give the same answer: stale detection and repair (REQ-SESSION-057), the worktree-integration precondition (REQ-SESSION-064), the ` (stale)` suffix in `sessions` output (REQ-SESSION-105), and the settling of displayed agent and tool state (REQ-SESSION-078, REQ-SESSION-079).
- **REQ-SESSION-056** — A session counts as **live** exactly when a `lock` file is present and the pid it records probes alive. A missing lock file is the sole unambiguous signal that no process holds the session; every other case — a lock that cannot be read, a lock carrying no pid or a non-integer pid, a pid ≤ 0, or a failed probe — MUST report live. An empty session id is never live.
- **REQ-SESSION-057** — A session is **stale** if and only if its metadata `execution_status` is in the active set and the session is not live. Sessions in terminal statuses (`completed`, `failed`, `paused`, `idle`, `paused_message_limit`, `interrupted`, `stopped`, ...) are never stale regardless of lock state.
- **REQ-SESSION-058** — Stale detection MUST read only `metadata.json` (including internal sessions) and the lock file, MUST write nothing to disk (verifiable by fingerprinting the tree before and after), and MUST report an empty result — not raise — over a broken session store.
- **REQ-SESSION-059** — Each detected stale session MUST report: the session id, the stuck execution status, `updated_at` exactly as the dead process left it (detection MUST NOT restamp it; an unparseable timestamp normalizes to the epoch); and a human-readable reason that is either `no lock file is held for this session` or `process <pid> is gone`.
- **REQ-SESSION-060** — Repair MUST be explicit — never triggered automatically from a read path. A repair MUST: re-check liveness; read the state (unreadable state means "nothing to do"); require an active status; set `execution_status` to `interrupted`; flush immediately, bypassing the debounce (the correction must be durable even if the process dies again at once); then best-effort remove the orphaned lock; then write a diagnostics timeline entry. Ordering is mandatory — status first, lock second; releasing the lock first would open a window in which the record still asserts a running session with no lock behind it. A filesystem error during the flush MUST leave everything untouched. Repair MUST never raise.
- **REQ-SESSION-061** — The repaired status MUST be `interrupted`, an existing status word chosen because it sits outside the active set, so a repaired session can never again report as occupied.
- **REQ-SESSION-062** — The repair timeline entry MUST have type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, and metadata `{previous_execution_status, execution_status, reason}`. A diagnostics failure MUST NOT fail the repair.
- **REQ-SESSION-063** — Repair-all MUST repair every stale session and be idempotent: a second pass repairs nothing and rewrites nothing (fingerprint-verifiable). A live session next to a dead one MUST be untouched and keep its lock.
- **REQ-SESSION-064** — Worktree integration's "base not in use" precondition is the one read path allowed to *bypass* (not repair) staleness: a session in an active status whose process is dead MUST be skipped rather than blocking integration forever, with the durable status correction left to the explicit repair command; a genuinely live session MUST block integration with the error `A session is still running in the base worktree. Finish it before integrating.`
- **REQ-SESSION-065** — When a run acquires the session lock and has not yet started work, it MUST settle orphaned children: every persisted child-agent record whose state is not in the terminal set `{succeeded, failed, cancelled, blocked}` is set to `cancelled`, given a completion timestamp (UTC ISO with `Z`, only if absent), and has its active-tool list cleared; terminal children keep everything. The operation reports how many records it moved and is idempotent. Holding the lock is itself proof that the previous owner has exited, so this settling step MUST NOT probe process liveness.
- **REQ-SESSION-066** — A session persisted in an active status whose owning process is gone MUST be observable in two ways at once: `checkpoints restore -s <id> --sequence N` is refused and restores nothing, leaving the working tree byte-identical (REQ-SESSION-164), and `sessions` lists that session with its stored status followed by the suffix ` (stale)` (REQ-SESSION-105). After `sessions --repair` has printed a repair line for that session, the same `checkpoints restore` invocation MUST succeed and the same `sessions` invocation MUST show `interrupted` with no suffix.

### 10. Save Debouncing and Write Ordering

- **REQ-SESSION-067** — Saves for sessions in status `running` or `idle` MUST be debounced with a 10.0-second window: the first save following an idle interval is written at once, and any save arriving while the window is open is deferred and written when it closes, with no additional calls required. Saves for any other status (terminal or transitional) MUST flush immediately, and MUST flush any parked pending state first. An explicit flush always writes immediately.
- **REQ-SESSION-068** — Saving MUST behave as follows from a caller's point of view. A save request captures the state as it stands at the instant of the request, so that changes made after the request cannot alter the bytes of a write already under way and cannot produce a file that mixes two states. A save that is not written at once MUST still reach disk by the close of the debounce window of REQ-SESSION-067, with no further call from the caller. An explicit flush MUST write immediately and MUST cancel any save still waiting for that window to close, so the window never adds a second write of the same state. The flush entry point MUST be usable from any host context, including one where no asynchronous runtime is active, and MUST NOT return until the newest requested state is on disk.
- **REQ-SESSION-069** — When several saves for one session are requested in close succession, the file left on disk MUST correspond to the state of the *last* request, never to an earlier request whose write happened to finish later. In particular, a `running` save requested before a `completed` save MUST NOT be the one that survives, whatever order the two writes complete in. A write abandoned for this reason MUST be reported in the session log as `Dropped a stale session write for <id>: generation <g> lost to <c> (state '<status>' would have overwritten a newer save).`, where `<g>` identifies the abandoned save request, `<c>` the newer request that superseded it, and `<status>` the `execution_status` the abandoned write carried. This ordering rule applies within one session only: a save requested for one session MUST NOT suppress, delay, or discard a save requested for a different session.
- **REQ-SESSION-070** — Two guarantees MUST hold at the call boundary. First, once a flush returns, the persisted state is never older than the newest state any caller has asked to have saved; a flush is permitted to return without writing only in the case where a later save has already made that true. Second, a save carrying a terminal status MUST NOT return before that status can be read from disk by a separate process, so a caller that has been told the run finished can rely on the finish being durable.
- **REQ-SESSION-071** — The debounce window of REQ-SESSION-067 is 10.0 seconds and no supported configuration key changes it. Its observable effect is a bound on write volume: however many saves a `running` or `idle` session requests inside one window, at most two state files are written for them — the save that opened the window and the save that closes it — and the deferred one lands no later than 10.0 seconds after the window opened. Writes that REQ-SESSION-067 and REQ-SESSION-070 require to happen at once (status changes, explicit flushes, terminal statuses) fall outside this bound. A surface that shows a run as it progresses MUST take its updates from the event history of Section 18; re-reading persisted state on a timer is not a supported way to follow a run and MUST NOT be relied on for refresh latency.
- **REQ-SESSION-072** — Any state persisted while a run is under way MUST already carry that run's current metric aggregates (REQ-SESSION-168), so a reader never finds a saved state whose counters lag the transcript saved beside them. Such saves are subject to the debounce window while the status is `running` or `idle`; a save that accompanies a status change, and any save taken where no asynchronous runtime is active, MUST be on disk before the save call returns.

### 11. Run Status Lifecycle, Results, and Exit Codes

- **REQ-SESSION-073** — The persisted `execution_status` vocabulary MUST include at least: `idle` (initial; also after continuing past a message limit), `running` (run start), `background` (terminal-UI background hand-off), `paused` (interrupt/cancel paths), `paused_message_limit` (automatic message-limit pause), `completed` and `failed` (run summary), `stopped` (a terminal-UI stop path), `interrupted` (written only by stale repair), and the transitional statuses `starting`, `pausing`, `cancelling` (which MUST be honored as active claims when persisted). The set is open-ended for hosts; unknown statuses MUST be treated as non-active unless listed in REQ-SESSION-055.
- **REQ-SESSION-074** — End-of-run summarization MUST map the finished loop to a status, human-readable text, and severity: stopped-by-user → (`paused`, `Run paused: interrupted by user.`, warning); zero abandoned tasks → (`completed`, `Run completed.`, information); zero completed tasks → (`failed`, `Run failed: <latest failure | N task(s) abandoned.>`, error); mixed → (`completed`, `Run completed with failures: X completed, Y abandoned.`, warning).
- **REQ-SESSION-075** — Terminal run-result statuses MUST map to process exit codes through one total mapping: `completed` → 0, `failed` → 1, `error` → 1, `max_iterations` → 2, `interrupted` → 130 (the conventional SIGINT code). Adding a new status without extending the mapping MUST be an immediate error, not a silent default.
- **REQ-SESSION-076** — When no progress record exists, the run result MUST be derived from the session's terminal execution status: `completed` → completed, `failed` → failed, `paused` → interrupted, `paused_message_limit` → interrupted. `idle` and `running` MUST NOT appear in this mapping, since neither is terminal; both MUST yield an error result with the message `Run ended without a terminal status.`
- **REQ-SESSION-077** — Stop-reason classification MUST compare the recorded stop reason by exact, case-sensitive equality against fixed sets: `{stopped by user, interrupted by user, user cancelled at message limit}` → interrupted; `{agent session aborted}` → failed whatever the task counts say (a run whose child agent aborted MUST NOT report success to an automated consumer); `iteration limit reached` together with a summarized status of `completed` → max-iterations. A summarized status matched by none of these rules and none of the mappings of REQ-SESSION-074 and REQ-SESSION-076 MUST produce an error result — never a successful one.
- **REQ-SESSION-078** — On every read, display surfaces MUST settle the child-agent tree against the session's own status: when `execution_status` is neither active nor `idle`, any agent still recorded as running/waiting/queued MUST display as done (for completed-like states), failed (for failed/error), or cancelled (anything else), with activity text "ended with the run" and cleared tool indicators. A snapshot written by an earlier version, or left behind by a killed process, MUST NOT be rendered as a finished run whose agents still appear active.
- **REQ-SESSION-079** — On a session whose `execution_status` is not one of the five active values of REQ-SESSION-055, a transcript tool row persisted with status `running` MUST render with no status indicator and no elapsed timer, and a thinking row carrying no recorded start MUST NOT show a counting timer: a session with no run in progress cannot have a tool call outstanding.

### 12. The Shared Run Lifecycle

- **REQ-SESSION-080** — Exactly one run lifecycle MUST serve every host (interactive CLI, headless CLI, embedding API, desktop). It MUST return a run result rather than exiting the process and MUST print nothing itself; even validation failures come back as error results carrying the diagnostic text; no host may take a different code path.
- **REQ-SESSION-081** — The run request MUST support: the task text, configuration, an existing session id (whose presence means resume), a maximum iteration count, an isolate-in-new-worktree flag, an existing-worktree path, a worktree branch name, requirement attribution (ignored on resume), a pre-chosen new-session id (ignored on resume), a delegation strategy, a run type, and an internal flag.
- **REQ-SESSION-082** — Pre-run validation failures MUST use these exact messages (each prefixed `Error: `, which doubles as the machine marker for "failed before start"): isolate plus worktree → `Error: choose either --isolate or --worktree, not both.`; worktree branch without isolate → `Error: --worktree-branch requires --isolate.`; any worktree option while resuming → `Error: worktree options apply only when creating a new session.`. A validation failure MUST carry an empty session id, leave no session behind, and still emit exactly one terminal `result` event to the event sink.
- **REQ-SESSION-083** — The resume path MUST load the session then acquire its lock; a lock held elsewhere fails with `Error: unable to acquire lock for session <id>` (a pre-run failure that does not steal the holder's lock, with the session id present in the result). With the lock held and nothing started, orphaned children MUST be settled (REQ-SESSION-065) and the configuration rebound into the session's stored worktree, if any.
- **REQ-SESSION-084** — The create path MUST create the session (lock held by creation, requirement attribution and the internal flag applied, run type stamped) and then bind the worktree: `--isolate` creates a worktree owned by the session on a branch of its own, and two launches started at the same instant MUST both end up with a worktree of their own rather than one of them failing on a branch-name collision; attaching an existing worktree MUST record it as not owned by the session, so releasing the session never deletes a tree the host owns. A bind failure MUST release the lock, **delete the just-created session directory** (REQ-SESSION-167), and return `Error: could not create or attach the requested worktree: <detail>`.
- **REQ-SESSION-085** — For a worktree-bound run, the run's effective working tree and the state's persisted `workspace_root` are the worktree path, while the session directory itself stays beneath the invoking workspace's `.rotaris` (REQ-SESSION-001). The configuration snapshot rebound to the worktree MUST be flushed to the session immediately after binding.
- **REQ-SESSION-086** — The sandbox verdict MUST be taken before anything else the run does and recorded on the state (`sandboxed`, `sandbox_backend`). On failure: release the lock; a just-created session is deleted while a resumed session survives, so a failed launch never destroys pre-existing history; the result is `Error: <detail>`.
- **REQ-SESSION-087** — Run startup MUST then, in order and observably: rehydrate metric aggregates from the session (REQ-SESSION-169); attach per-session logging to `evidence/debug.log` at the configured session log level; write a `run_start` timeline entry (actor `background`, a value retained for continuity in the on-disk record; message `Starting background run for session <id>`, metadata carrying the workspace root); persist `execution_status = "running"`; and invoke the host's session-ready callback.
- **REQ-SESSION-088** — Per-iteration checkpoints MUST record the working tree in the state in which the iteration finished: any end-of-iteration lifecycle hooks that touch the tree MUST have run before the checkpoint is taken. Host-supplied observers MUST be added alongside, never substituted for, the built-in ones.
- **REQ-SESSION-089** — Durable event-history attachment MUST be unconditional for every run through the shared lifecycle: the store is opened for the session and teed with the host's own event sink. A store that cannot open MUST degrade to a logged warning (reporting that no event history will be available for later replay or export) with the host's sink still attached; the run MUST proceed. A `session.start` event MUST be published immediately after attachment so that it is the first event any consumer observes.
- **REQ-SESSION-090** — The `session.start` payload MUST carry enough for a consumer to describe the run without opening the session directory: the session id; the task text; the workspace the run reports for itself; the persona; the permission mode as configured at launch (a later unattended downgrade is reported by permission events instead, so this value MUST NOT be restated when the effective mode changes); the sandbox verdict actually in force — the backend both configured *and* available, not the one merely requested; and the maximum iteration count.
- **REQ-SESSION-091** — A cancellation already requested before the loop exists MUST skip the agent runtime entirely (no model call, no grace-period unwind); the run reports interrupted with exit code 130 and the session remains resumable at status `paused`.
- **REQ-SESSION-092** — Cancellation semantics: a graceful stop is requested first (the same path a console interrupt uses); if the loop has not reached a stop check within 30.0 seconds, a hard cancel follows. The stop request MUST be sticky — a cancel arriving before the loop's callbacks are wired replays when they are. A caller that requested cancellation MUST receive an interrupted outcome even when the loop finished first; reporting both an effective cancellation and a successful run to the same caller is forbidden. A console interrupt raised inside the run MUST still release the lock and emit the terminal result event.
- **REQ-SESSION-093** — Every outcome branch MUST persist state before returning: cancelled/interrupted → `execution_status = "paused"` plus a system transcript row `Run paused: interrupted by user.`; runtime exception → `failed` plus a row `Run failed: <formatted error>`; normal completion → status and row from the end-of-run summarization, after which the post-run improvement job is either handed to a host-provided job sink or awaited inline with its result applied and persisted.
- **REQ-SESSION-094** — Run teardown MUST guarantee, in order, even on any exception: a `run_end` timeline entry (metadata carrying the final execution status); logging cleanup; **lock release**; construction of one run result; publication of `session.end` followed by exactly one `result` event, both delivered over the bus while the sink is still attached (so an attached consumer learns how the run ended); a final notice to the host about disabled hooks; and finally removal of every per-session binding, ensuring a straggling event can neither be appended to a finished session nor trigger hooks belonging to a subsequent run in the same process.
- **REQ-SESSION-095** — The `session.end` payload MUST mirror the terminal run result (status, stop reason, iterations completed, duration in seconds, tokens, cost), computed once and used for both the event payload and the exit code, so the two can never differ.
- **REQ-SESSION-096** — A successful embedded (API-hosted) run MUST print nothing to stdout or stderr and MUST leave an ordinary on-disk session that any fresh reader can load with status `completed`.

### 13. Command-Line Surface for Background Runs

- **REQ-SESSION-097** — Two command-line front-ends MUST share identical run semantics: the full CLI (which can also start the terminal UI) and a headless CLI that pulls in no terminal-UI dependencies at all (usable in CI and in containers). Headless subcommands MUST include: `run`, `sessions`, `version`, `setup`, `login`, `logout`, `checkpoints` (`list`|`restore`), `events` (`list`|`replay`|`export`), `requirements` (`run`|`list`|`verify`|`evaluate`|`migrate`), and `providers` (`delete`).
- **REQ-SESSION-098** — The `run` command MUST accept: `--background/-b` (headless execution), `--workspace/-w` (default: current directory), `--session/-s <id>` (continue an existing session), `--isolate`, `--worktree PATH`, `--worktree-branch NAME` (when omitted, the branch name is generated from the session id inside the `rotaris/session/<id>` namespace; the worktree itself is created under the configured storage subpath, default `worktrees`), `--config/-c`, `--persona/-p`, `--max-iterations N`, `--unsafe-outside-workspace`, `--output-format text|stream-json`, and `--logout PROVIDER`.
- **REQ-SESSION-099** — `--output-format stream-json` MUST give stdout over entirely to the JSON-lines event stream — one serialized event per line and nothing else on that channel — and send every human-readable line to stderr. It implies `--background`. An invocation carrying neither a task nor `--session/-s <id>` MUST be refused with `Error: --output-format stream-json requires a task; it cannot start the interactive TUI.` and exit code 2; `--session/-s <id>` without a task is a resume and MUST be accepted (REQ-SESSION-101). An unrecognized `--output-format` value MUST exit 2 with a message naming the accepted values `text` and `stream-json`. The flag changes only where output goes; the run itself executes identically.
- **REQ-SESSION-100** — Worktree session options on an interactive (non-background, taskless) invocation MUST be refused with `Worktree session options require a task with --background.` and exit code 1.
- **REQ-SESSION-101** — Headless `run` requires a task or a session id: otherwise `Error: task is required for headless mode` on stderr with exit code 1. Configuration errors MUST print `Config error: <message>` per line on stderr with exit code 1, after a single non-interactive recovery attempt for stale-model-snapshot errors.
- **REQ-SESSION-102** — The session-announce line MUST print the moment the session exists (on the `session.start` event, before the run — for a long-running job this is what makes the session addressable from a different terminal): `Created session <id>` for a new session, `Resuming session <id>` when the request carried a session id; printed once; on the stream-JSON path it goes to stderr. A run that never starts (validation, lock, or worktree failure) MUST announce no session id. Note: the created/resuming choice follows whether the *request* resumed a session, so a pre-named new session still announces `Created session <id>`.
- **REQ-SESSION-103** — Outcome reporting MUST derive from the same run result on both output channels: an error result prints to stderr prefixed `Error: ` exactly once; interrupted with no stop reason prints a blank line then `Interrupted.`; failed prints the summary on stderr; a summary equal to the sentinel `Run completed.` prints `Done.` (a success line that existing scripts match on); otherwise the summary is printed. The process exit code MUST equal the run result's exit code.
- **REQ-SESSION-104** — Console interrupts in the CLI host: the first Ctrl-C requests a graceful stop, the second forces cancellation; the handler's own messages go to the terminal (stderr when streaming) so an interrupt cannot corrupt the JSON stream.
- **REQ-SESSION-105** — The `sessions` command (`--workspace/-w`, `--repair`) MUST: with `--repair`, print `No session was left marked as running by a stopped process.` when nothing was stale, else one line per repair of the form `  repaired <id>  <old-status> -> interrupted  (<reason>)`. The listing then prints, per non-internal session, `  <session_id>  <updated_at>  <schema_version>  <status>`, where a stale session's status carries the suffix ` (stale)`, making the cause of a blocked restore or integration visible. Exit code 0.
- **REQ-SESSION-106** — A headless background run (`run --background`, REQ-SESSION-098) MUST carry on unattended with no UI present. With the launching terminal closed, the following MUST all still be observable from the session directory: `updated_at` keeps advancing, new transcript rows keep appearing in `state/ui_transcript.json`, `evidence/events.jsonl` keeps growing, artifacts keep being produced under `artifacts/`, and the run reaches a terminal `execution_status` on its own. A later reattach from the same workspace MUST remain possible: the session is located by workspace plus session id, its persisted state is read back, and a UI is bound to that state. (The terminal UI's own `/background` hand-off persists state without detaching a worker; see REQ-SESSION-119.)

### 14. Message-Limit Pause and Reattach

- **REQ-SESSION-107** — When a headless/background run reaches its message limit, it MUST: create the durable signal file `<session_dir>/.message_limit_paused`; record the message count and limit on the state; set `execution_status = "paused_message_limit"`; and persist immediately (a status change flushes synchronously). It then remains paused until a user reattaches; there is no automatic continuation.
- **REQ-SESSION-108** — The pause MUST take effect at the outer-loop iteration boundary (after an iteration returns, before the next is chosen), so that while paused no agent is part-way through execution and no model request is outstanding.
- **REQ-SESSION-109** — On reattach, if the loaded session's status is `paused_message_limit`, the terminal UI MUST immediately show a confirmation prompt without user navigation, displaying the message count, the limit, and token usage in the form `Input: N / Output: M`. Keyboard bindings: `c`/Enter = continue, `d` = double the limit, `x`/Escape = cancel the run. A command-palette entry "Continue paused session" MUST exist and be active only in this state.
- **REQ-SESSION-110** — Resolving the prompt: "double" doubles the persisted message limit; "cancel" sets status `paused`; "continue" sets status `idle`. In every resolved case the `.message_limit_paused` signal file MUST be removed (missing is fine) and the session saved. A session paused at the limit whose persisted limit is null cannot resume the prompt: its status is set to `paused` with the warning notification `Paused session has no message limit to resume.`
- **REQ-SESSION-111** — The message count and the (possibly doubled) limit MUST be durable across crash and restart via the ordinary snapshot, so the user is never re-prompted for messages already counted. A resumed run MUST seed its counters from the persisted values, falling back to the configured limit (which is then written back to the state when it was null).

### 15. Resume and Continue Semantics

- **REQ-SESSION-112** — To continue a session is to reopen one already saved beneath `<base_workspace>/.rotaris/sessions/` for the same workspace. Everything the session recorded MUST come back: its transcript rows, its stored child-agent state history, its stored tool-event history, its report artifacts, and its configuration snapshot. The test is field-level equality: a state that is saved and then reloaded MUST compare equal on every key of the resumable-state inventory in Data & Formats (REQ-SESSION-027), and that equality MUST still hold after a release-lock, re-acquire, mutate, save and reload cycle.
- **REQ-SESSION-113** — A resumed session keeps its identity wholesale: its worktree binding (worktree options refused on resume), its requirement attribution (request-supplied attribution ignored), its run type (stamped only at creation), and its configuration snapshot; the run executes inside the stored worktree.
- **REQ-SESSION-114** — Intent carry-over on resume: the intent classifier MUST be given the *previous* run's recorded intent (read before it is overwritten). A continuation prompt that classifies as ambiguous (e.g. the user types "continue") inherits the prior intent, and the transcript's status row reads `Intent classified: <intent> (continued from previous run)`; a genuinely new request keeps its own classification.
- **REQ-SESSION-115** — When a new top-level task enters an existing session, the payload handed to the run MUST prepend a fixed continuation preamble (stating that this is a follow-up within an existing session and that prior session context is authoritative), then a `Latest user request:` block, an `Authoritative session handoff:` block (artifact, todo, and progress context), and a `Recent session context:` block. Budgets MUST be exactly: the last 6 transcript events whose role is `user` or `agent` and whose content is not blank, at most 700 characters taken from each such event, at most 3200 characters of history in total, at most 20 todo tasks followed by the literal marker `- [... additional todo tasks elided]` whenever any task was dropped, the last 5 outer-loop iterations, at most 700 characters per structured item, at most 6000 characters for the latest orchestrator artifact against an 8000-character artifact baseline, and task display titles cut to 80 characters with a `...` suffix.
- **REQ-SESSION-116** — The transcript row for the user's new prompt MUST be recorded and persisted before intent classification begins, and every save of the active resumed run flows through the same debounced path as a fresh run.
- **REQ-SESSION-117** — The terminal UI's resume affordances (a `/resume` slash command, a command-palette entry "Continue session", and the cheatsheet entry) MUST all open the session picker: a modal table with columns `Session ID`, `Created At`, `Status`, listing non-internal sessions. An empty list notifies `No sessions found.`; a listing failure notifies `Unable to list sessions: <detail>` at error severity; selecting a row returns that session id.
- **REQ-SESSION-118** — Loading after picking MUST map errors to notifications: not found → `Session <id> not found.`; a value/parse error → `Corrupt session snapshot: <detail>`; anything else → `Unable to load session: <detail>`. On success the session-scoped model override is restored, the composer's model label updated, the message-limit prompt shown when applicable, and `Loaded session <id>` notified.
- **REQ-SESSION-119** — The terminal UI's background hand-off (`/background`) MUST persist the current session with `execution_status = "background"` and notify `Session saved. Background execution not yet supported — session state preserved.` — that is, in this host the hand-off persists state but does not detach a live worker. With no active run it warns `No active run to send to background.` Because `background` is an active status, such a session correctly reads as stale after the UI process exits (no lock) and is repairable to `interrupted`.

### 16. Transcript Recording and Persistence

- **REQ-SESSION-120** — The persisted transcript MUST be derived from the run's own conversation events and from nothing a host renders. Two consequences MUST be observable: a run with no UI attached persists the same transcript rows it would have persisted with one, so a headless session can be reopened with a full transcript; and one recorded conversation yields byte-identical rows whichever host drove it, so no two hosts can leave different transcripts of the same run.
- **REQ-SESSION-121** — Persisted transcript rows MUST use the role/shape vocabulary given in Data & Formats, and every row MUST be stamped with `ts` in local wall-clock `HH:MM:SS` form when appended.
- **REQ-SESSION-122** — Persisted-size caps MUST be: 400 characters for a tool row's `detail`, 2000 characters for its `full_text`, and 4000 characters for thinking content. Content longer than its cap is stored cut to the cap, while a streamed thinking row's `chars` counter MUST keep counting past 4000 so that token estimation remains correct. Terminal (shell) tool output MUST keep its line structure in `full_detail` — the field a reopened session renders — while `detail` holds a single line of at most 400 characters.
- **REQ-SESSION-123** — Each row MUST be published on the wire as a `transcript.row` event (index plus a copy of the row) once on append and once more when the row reaches its final form — intentionally not on every streamed token, so a remote viewer receives the opening token and then the completed text. Publish failures are logged and never raised into the run.
- **REQ-SESSION-124** — Resuming a conversation can replay events; stable per-event identities (per-agent call ids for tool calls, per-agent event ids for committed messages) MUST prevent duplicate rows and double-counted metrics.
- **REQ-SESSION-125** — Reasoning delivered twice — streamed as deltas and then repeated in full alongside the action — MUST end up as exactly one persisted thinking row holding the final full text, with one start timestamp and one settled duration; a second row, whose elapsed-time counter would never stop, MUST NOT appear. Reasoning that was never streamed arrives in one piece and is persisted with no start timestamp, and therefore shows no timer. Where an older version already recorded a burst twice — consecutive thinking rows of the same agent, the content of one being a prefix of the other's — display MUST show only the longer row.
- **REQ-SESSION-126** — A terminal tool row MUST carry a stream identifier of the form `fg:<agent_name>` so that a UI rejoining the session can locate the live terminal buffer the row belongs to.
- **REQ-SESSION-127** — Structured edit diffs MUST live outside the transcript that is fed to the model, keyed `<agent>:<tool_event_key>` and replaced in place on redelivery; at display time each diff is merged beside exactly one tool row.
- **REQ-SESSION-128** — Tool-call metrics MUST be counted into the per-agent and global aggregates at call start, once per stable call id, and each child's live tool set MUST be mirrored onto its persisted child-state record so a snapshot shows what each child is running.
- **REQ-SESSION-129** — Three end-of-activity guarantees MUST hold. When a child agent dies while a tool call is open, that child's persisted record MUST be left with an empty active-tool list and no transcript row of its own left at status `running`. A verifier check that finishes without ever having been announced — denied by permissions, or out of budget — MUST still produce a verifier row, with the outcome mapping of Data & Formats (passed → `ok`, failed or timeout → `failed`, skipped → `blocked`). A completed question-tool result MUST remove the matching entries from `pending_questions`, which in turn clears `awaiting_input` once no approvals remain (REQ-SESSION-031).
- **REQ-SESSION-130** — At run end, if the conversation left no agent rows (for example when a child agent's summarized report is the entire answer), one agent row per iteration outcome MUST be appended from the progress record so the transcript still shows an answer — but never duplicated on top of real conversation rows.
- **REQ-SESSION-131** — The terminal-UI transcript archive MUST append evicted (older) transcript events one JSON object per line to `<session_dir>/state/transcript_archive.jsonl`, paged in fixed chunks with a default page size of 50, append-only.

### 17. Diagnostics and Evidence Files

- **REQ-SESSION-132** — Diagnostics initialization MUST create, and only when the name is absent: `state/run_config.json`, `issues.json` (as `{"issues": []}`), `metrics.json`, `summary.md`, an empty `timeline.jsonl`, `evidence/tool-calls.jsonl`, empty `evidence/model-input.jsonl`, `evidence/context-selection.jsonl`, `evidence/report-validation.jsonl`, `evidence/memory.jsonl`, `evidence/permissions.jsonl`, and `evidence/conversations/index.json` (as `{"conversations": []}`). Where `state/run_config.json` is created here, its content MUST be the launch audit of REQ-SESSION-138; initialization MUST NOT leave an empty placeholder that would then block the audit from ever being recorded. Initialization runs on every state save, so a session's full inspectable shape exists from its first save onward, before any of these files has content.
- **REQ-SESSION-133** — Retention caps (ring-buffer semantics, newest kept) MUST be: issues 500, tool calls 5000, model inputs 5000, context selections 2000, permission decisions 5000, report validations 2000, memory snapshots 2000. A capped append rewrites the file atomically keeping only the newest entries; uncapped files append one line. Appends within one process are serialized.
- **REQ-SESSION-134** — Timeline entries (one JSON object per `timeline.jsonl` line) MUST have the shape `{id: 12 hex chars, timestamp: UTC ISO, type, severity: debug|info|warning|error (default info), actor, message, metadata}`. Ordering contract: the durable line is written before any wire event derived from it, so a failing stream may drop an event while the on-disk record it came from is still retained. Exactly three timeline entry types are bridged to wire events (`completion_gate_decision` → `gate.decision`; `repair_attempt_scheduled` and `repair_escalation` → `gate.repair`, mutually exclusive per decision), and no other timeline type produces an event through this bridge — the `error` event of REQ-SESSION-135 is published by issue recording, not by the timeline. Metadata from which no valid event can be constructed is logged and discarded without failing the iteration.
- **REQ-SESSION-135** — Issue records (in `issues.json`) MUST have the shape `{id: 12 hex chars, timestamp, kind, severity, actor, message, evidence_ref, metadata}`. Every recorded issue also writes a timeline entry of type `issue`; only error-severity issues additionally publish an `error` wire event with `fatal=false` (recording an issue never by itself terminates a run); warning- and info-severity issues publish nothing, so an automated consumer does not read a healthy run as failing.
- **REQ-SESSION-136** — Tool-call records (`evidence/tool-calls.jsonl`) MUST carry `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` plus `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings` only when applicable. Each record also streams a `tool.start`/`tool.finish` event pair; the on-disk record keeps its historical unredacted-arguments shape while the streamed arguments are redacted by the event schema. Outcome-driven automatic issues MUST be filed: shell failure → kind `terminal_shell_failure` (error); suspicious success → `terminal_suspicious_success` (warning); timeout → `terminal_timeout` (error); any other failure → `tool_error` (warning); each referencing `evidence/tool-calls.jsonl`. On error, recorded args/result are truncated to 2000 characters.
- **REQ-SESSION-137** — The permission audit (`evidence/permissions.jsonl`) MUST record decisions as `{timestamp, session_id, agent_id, persona, tool_name, decision, rule_id, source, summary (pre-redacted), reason, request_id?}`. A deny files a `permission_denied` warning issue; a one-time or session-scoped user approval files a `permission_approved` timeline entry. Mid-session mode changes share the file as `{event: "permission_mode_change", requested_mode, effective_mode, previous_mode, source, reason, skipped_personas}` — `skipped_personas` recorded even when empty so silence is unambiguous — and are counted separately in metrics.
- **REQ-SESSION-138** — `state/run_config.json` MUST be written once at session start (a configuration change made afterwards must not alter the recorded audit) and contain `{session_id, workspace_root, created_at, run_intent, permission_mode, check_suite, resolved_playbooks (per persona for the run's intent), hooks (id/name/event/matcher/source with secret-redacted command text), config_snapshot}`, with each persona's system-prompt file resolved into inline `resolved_system_prompt` text.
- **REQ-SESSION-139** — `metrics.json` MUST be rebuilt from the state plus the evidence files on every save and MUST report: session id, status and updated-at; global tool-call, token, cost and compression aggregates; per-agent metrics; the number of tool-call records; a tool-outcomes histogram classifying every recorded call (`outcome_kind` when the record carries one, otherwise derived from `status` and `is_error` into rejected, tool-error, success or unknown) whose bucket totals MUST sum to the tool-call record count; terminal shell-failure, suspicious-success and timeout counts; the 10 slowest tool calls ordered by recorded `elapsed_ms` descending; model-input record and stale-drop counts; context-selection totals; report-validation record and downgrade counts; permission decision, denial, source and mode-change counts; and issue counts in total and by kind. All counts are taken over the records the evidence files still hold after the retention caps of REQ-SESSION-133 have been applied, so a capped file's counts describe what is on disk rather than what the run once produced.
- **REQ-SESSION-140** — `summary.md` MUST contain, in this order: a `# Session <id>` heading; one line each for status, workspace, created and updated; `- Task: <first user event, cut to 240 characters>`; `- Stop reason: <reason>` when a stop reason is recorded, the line being omitted entirely when none is; a Metrics section in which a value that is unavailable renders as `n/a` or `—` and never as `0`; a Warnings section covering stale-input drops, mostly-elided artifacts, report downgrades, permission denials (naming `evidence/permissions.jsonl`), tool errors, and terminal failures, suspicious successes and timeouts; an Agents section; a Slowest Tools section listing the top 5 by recorded `elapsed_ms`; and a closing inspection note naming `issues.json` first, then `timeline.jsonl`, then `evidence/debug.log`.
- **REQ-SESSION-141** — The conversation index (`evidence/conversations/index.json`) MUST hold entries `{conversation_id, agent_name, persona, model, task_id, started_at, ended_at (set when status leaves "running"), status, event_count, path}` where path points at the conversation's event-log directory. Conversation directories are named with 32-character un-hyphenated hexadecimal ids; lookups MUST accept both hyphenated and un-hyphenated forms (direct match, stripped variant, then a directory scan), counting the `*.json` files under `events/`.
- **REQ-SESSION-142** — Per-session debug logging MUST write to `evidence/debug.log` at the configured session log level (default WARNING; the strings DEBUG/INFO/WARNING/ERROR and integer levels accepted; an unknown string falls back to WARNING and logs a warning), and MUST restore prior logging state at run end.

### 18. Durable Per-Session Event History

- **REQ-SESSION-143** — The event history lives at `<session_dir>/evidence/events.jsonl`, holding one serialized wire event per line, ordered as emitted. Each stored line MUST reproduce, byte for byte, what the live stream emitted for that event, so that replaying from disk and subscribing to a running session are interchangeable inputs to one consumer. The truncation sidecar is `evidence/events.meta.json`.
- **REQ-SESSION-144** — The default event cap MUST be 20,000 events, with trim slack of cap ÷ 8. Were there no slack, each event added once the cap is reached would force a full-file rewrite; the slack amortizes that down to about one full rewrite for every cap ÷ 8 events appended. A cap below 8 has no slack and is enforced exactly. A trim keeps the newest cap-many lines, rewrites atomically, recounts from the file afterwards (honest even if something else appended), updates counters only after a successful rewrite, and records `{truncated: true, dropped_events (cumulative across runs), max_events, last_trimmed_at}` in the sidecar. A null cap disables trimming (tooling only); a non-positive cap MUST be rejected as invalid (a configured 0 asks for an empty history, not an unlimited one, and MUST NOT be reinterpreted).
- **REQ-SESSION-145** — The history writer MUST never fail a run: each entry point turns exceptions into logged warnings and signals the outcome through its return value; an event that cannot be serialized is discarded with a warning; a line containing an embedded newline or carriage return is refused (one event = one line); appends MUST NOT allow platform text-mode newline translation to mix line endings with the atomic-rewrite path.
- **REQ-SESSION-146** — Event-history bindings are per session id: a new registration replaces the previous one, lookup never falls through to a different session — history from one run must never be written into another run's file — and storing without a binding is a silent no-op.
- **REQ-SESSION-147** — Persistence MUST happen before forwarding to the host's event consumer (a tee), so an event that a failing consumer never receives is nevertheless recorded on disk. Detaching the history genuinely stops persistence even for a sink reference that escaped.
- **REQ-SESSION-148** — Reading MUST be streaming (never whole-file), read-only, and forward-compatible: a line whose event-type discriminator is unknown yields an opaque event marked unknown with its raw payload intact — never dropped, never raising (strict decoding is an explicit opt-in). A trailing line left truncated or corrupt by a killed run MUST be skipped with a warning carrying `{line_number, reason, excerpt (at most 200 chars)}`, and the file MUST NOT be rewritten or repaired. A missing history reads as an empty session. A line with no event-type discriminator is malformed (skipped), not "unknown". Which types count as known MUST follow the event schema itself, never a separately maintained list.
- **REQ-SESSION-149** — Tail reads (for live following) MUST return events together with a byte offset that always lands immediately after a fully written line, plus a restart flag. Nothing new → empty events, same offset. A partial trailing line means a live run mid-write: complete lines before it are returned, no warning, and the partial line is read again once whole. The restart flag MUST be true when the file is shorter than the offset or the byte before the offset is not a newline (the cap trimmed the head, or the file was replaced); the caller must then discard derived state. A replacement file of identical length whose offset boundary also falls on a newline is undetectable by this test; the never-reused-id invariant (REQ-SESSION-012) is what rules that case out. Lines that cannot be decoded as UTF-8 are warned about and skipped, with warning line numbers counted from the start of the read.
- **REQ-SESSION-150** — Replay filtering MUST support event types, iterations, and inclusive since/until time bounds — all optional, combined with AND; timezone-naive stamps normalize to UTC; an empty result is a valid answer. As the stream is read, each event's owning iteration is determined from the enclosing `iteration.start` and `iteration.end` boundaries; events outside every iteration match no iteration filter, and stamp-less lines match no time filter. Replay is reading, never re-execution, and never modifies the history.
- **REQ-SESSION-151** — Stored-session discovery MUST: treat an *empty* history as present (a run that emitted no events is still a session one can ask about); summarize by counting lines and decoding only the first and last (on a damaged history the count may be off by one, which is acceptable for a chooser; exact figures come from export); report an unreadable history as containing zero events, with a warning, instead of aborting the listing; sort newest first by last-then-first timestamp with the session id as tiebreak, sorting histories with no usable timestamps last. A session id from CLI input MUST be treated as untrusted: it is resolved and required to land inside the sessions root (path traversal and absolute-path escapes blocked), else no match.
- **REQ-SESSION-152** — The `events` CLI (both front-ends) MUST exit 0 on success **including an empty result**; exit 2 when the session has no stored history in the workspace (`No stored session <id> exists in <workspace>.`) or when a `--since`/`--until` value is not ISO-8601 (`Error: --since expects an ISO-8601 timestamp, not '<value>'.`). `events list` prints aligned rows `<id>  <count> events  <start -> end>` with the suffix `  truncated (-<dropped>)` on capped histories; no sessions produces a stderr notice. `events replay <id> [-t type]... [-i iteration]... [--since] [--until] [--json]` prints human rows `  <timestamp>  <type>[ (unknown)]  <compact payload, at most 110 chars>` or, with `--json`, the stored lines byte-for-byte; warnings about skipped lines are written to stderr even in JSON mode, so that a pipe carries events only. `events export <id>... [-o file]` exports the ids given, in the order supplied, as trajectory documents (REQ-SESSION-153) — a single document for one id, a batch for several; a resumed session (multiple runs in one history) warns `Warning: session <id> holds N runs (it was resumed); this document covers all of them, and its identity is the most recent one.`; a capped history warns `Warning: session <id> dropped N event(s) to the store cap; this export is not the complete run.` — warnings, not failures.
- **REQ-SESSION-153** — An exported trajectory document MUST carry `trajectory_version: 1`; the run's identity (session id, task, and the workspace exactly as the run reported it — never a path belonging to the exporting machine); the permission mode; started and ended timestamps as ISO-8601 UTC; the status; the stop reason; the duration in seconds; `truncated` and `dropped_events`, taken from `evidence/events.meta.json` and reading as `false` and `0` when that sidecar is absent (REQ-SESSION-144); a summary recomputed from the exported events alone and from no other source — event, unknown-event and warning counts; `runs`, the number of `session.start` boundaries in the document, which is where a single-run consumer must split it; iterations; tool calls and tool failures; permission decisions and denials; verifier runs and failures; child agents; errors and fatal errors; per-type event counts; tokens; cost — and the events themselves as the raw stored payloads, with redaction inherited from the wire schema rather than applied again by the exporter, and unknown event types preserved intact.

### 19. Reattach Surfaces and Projections

- **REQ-SESSION-154** — The desktop session list MUST project listing metadata into rows: label = task title, else the launcher-known name, else the session id (a just-launched run keeps its prompt-derived label until metadata carries a title, and a refresh must not strip launcher-known requirement attribution); status from `execution_status` defaulting to idle; branch from the metadata worktree record, else "—"; a relative-time duration label; the worktree path as detail; and `awaiting_input` from metadata (absent → false).
- **REQ-SESSION-155** — `awaiting_input` MUST render as a "waiting for you" tag on session rows and "Waiting for your answer" status text, and MUST drive the requirement board's "Answer" affordance for background runs blocked on approvals or questions — persisted metadata is what lets a background run say it is blocked on a person across every surface and across restarts.
- **REQ-SESSION-156** — Desktop whole-state reads MUST use the read-only snapshot read of REQ-SESSION-040 — no repairs and no writes, verifiable by fingerprinting the session directory before and after the read — and MUST project the persisted state into display models covering the run summary, transcript, agents, artifacts, todos, key metrics, pending questions and approvals (copied, so that display work can never mutate what was read), and the verifier summary. A `verifier_state` that cannot be parsed MUST resolve to idle rather than failing the read, and a persisted `gate_warning` MUST still be reported when the verifier is idle. The result MUST report the elapsed time of the state read and the elapsed time of the projection as separate values.
- **REQ-SESSION-157** — Pending questions and approvals MUST render as transcript trailer rows — derived from what is pending now and always placed after every recorded row, re-appended by both whole-state and delta paths: a question stepper row of the form `<N> step(s) — <first title>` and one row per approval of the form `Approval needed — <command or tool>`.
- **REQ-SESSION-158** — A desktop board-launched run (a requirement unit) MUST: adopt the worktree the flow provisioned, given by explicit path, refusing a path that is not part of the repository, and record it as not owned by the session so the session never deletes a tree the flow owns (REQ-SESSION-084); make the session id available to the caller as soon as the session exists, without waiting for the run to end; open no window and take no window or keyboard focus, so that several launches in succession leave the user's foreground application unchanged; return an empty session id rather than raising when the launch is refused; and have the caller's completion listener registered before the launch call returns, so that a run finishing immediately still delivers its completion notification.

### 20. Following a Session That a Different Process Owns

- **REQ-SESSION-159** — When a session runs in a different process — launched from a terminal, from a CI job, from a second desktop window, or as a detached background run — the only channel to it is the filesystem. Because state files are replaced wholesale on each save and carry no incremental read position, the live transcript MUST instead be followed by tailing `evidence/events.jsonl` and turning `transcript.row` events into the same transcript deltas that a locally executing run yields. Sharing one derivation guarantees that following a session and reopening it afterwards produce identical transcripts.
- **REQ-SESSION-160** — A follower reading the event history MUST reproduce the run's own row numbering. Each row appears at exactly the index the run gave it. A row arriving past the current end fills the indices skipped over with `{"role": "system", "content": "(this line was not recorded)"}`, so that every later row still sits at its own index. A row republished for an index already shown — a settling row arriving behind the tail — replaces that row instead of being appended after it. The first batch produced after seeding, and after any re-seed, starts at row 0. When the history reports a restart (REQ-SESSION-149) every derived row is discarded and the view re-seeds. Any error while tailing MUST be surfaced as a request to reconcile from a whole-state read, leaving the rows already shown in place rather than clearing or freezing the view.
- **REQ-SESSION-161** — Everything outside the transcript — todo lists, the agent tree, token counts — MUST come from whole-state reads, which also reconcile anything the tail did not deliver. A delta whose first-touched index falls before the oldest row the consumer still holds from its most recent whole-state read MUST be rejected; a rejection costs exactly one further whole-state read, and the rows on display MUST be unchanged by the delta that was rejected.

### 21. Checkpoints as Session Data

- **REQ-SESSION-162** — Per-iteration git checkpoints MUST persist in two places that stay consistent: refs under `refs/rotaris/checkpoints/` in the run's tree (the isolated worktree for isolated sessions, else the workspace), and the session's `checkpoints` list mapping iteration to ref and commit. Keeping the mapping in the session state is what allows checkpoints to survive a resume and to remain restorable after a crash.
- **REQ-SESSION-163** — `metadata.json`'s `checkpoint_count` MUST mirror the length of the state's checkpoint list (the session list reads metadata only); readers default an absent key to 0 for pre-checkpoint directories.
- **REQ-SESSION-164** — Checkpoint restore for a session that *claims* to be running MUST be refused, because the pre-restore checkpoint this operation records would contend with writes from the supposedly live run; the stale-repair flow exists precisely to make restore available again after a crash.
- **REQ-SESSION-165** — The checkpoints CLI MUST operate by session id: `checkpoints list -s <id> [-w]` and `checkpoints restore -s <id> --sequence N [--force] [--yes] [-w]`, where `--force` overwrites uncommitted changes in the way and `--yes` skips the confirmation prompt.

### 22. Session Deletion

- **REQ-SESSION-166** — Deleting a session MUST first best-effort discard the session's checkpoint refs (loading the snapshot to locate the right tree — the worktree for an isolated session, else the workspace root), then remove the session directory ignoring errors. An unreadable session still deletes. Deleting a missing session is a no-op. A ref-cleanup failure logs a warning naming the leftover `refs/rotaris/checkpoints/` location; cleanup stays best-effort so a session still deletes when the repository moved or never existed. Refs MUST be pruned as well, because removing only the directory would leave them behind permanently.
- **REQ-SESSION-167** — The run lifecycle deletes a session in exactly one situation: a *just-created* session whose launch failed before the run started (worktree bind or sandbox failure). A resumed session MUST never be deleted by a failed launch.

### 23. Metrics Continuity Across Resume

- **REQ-SESSION-168** — On every persist, in-process metric aggregates MUST be copied into the state: global tokens, cost, tool calls, compressions, per-agent metrics, and sorted compression-dedup ids. The legacy token-usage field is set only when total tokens exceed 0, else null.
- **REQ-SESSION-169** — At run start and resume, in-process aggregates MUST be rebuilt from the persisted state with graceful fallbacks: a per-agent tool total without per-tool detail restores as a single pseudo-tool entry; zero global tokens falls back to the legacy token-usage field, then to merging per-agent snapshots; global cost, compressions, and tool-call counters are recomputed from agents the same way. Consequence: cumulative token, cost, and tool counters continue across resumes rather than resetting.

### 24. Reasoning-Content Repair at Open

- **REQ-SESSION-170** — The full session open of REQ-SESSION-040 — and only that path, never the read-only snapshot read — MUST run a best-effort repair before the session is handed back. When the session's default-persona model rejects requests in which an earlier assistant message carries no reasoning content, every persisted conversation event file under `evidence/conversations/event_logs/*/events/*.json` is examined, and action events whose reasoning content is null or missing, together with agent message events whose message carries no reasoning content, are rewritten atomically (REQ-SESSION-033) with an empty string in place of the missing content. The pass MUST run at most once per open, MUST record and log how many items it changed, and MUST NOT prevent the open from completing when it fails.

### 25. Cross-Cutting Invariants

- **REQ-SESSION-171** — For one pid at one moment, lock reaping, liveness reporting, stale detection and the worktree-integration precondition MUST all reach the same verdict: it MUST NOT be possible to observe one of them treating a process as alive while another treats the same process as gone.
- **REQ-SESSION-172** — Any uncertainty about whether a session is live resolves in favour of "still running"; detection performs no writes; repair is explicit, flushed at once, idempotent, and never raises.
- **REQ-SESSION-173** — The last *requested* save wins on disk, not the last write to finish; a terminal status is always durable before its save call returns; disk is never staler than the newest requested state.
- **REQ-SESSION-174** — Every run through the shared lifecycle persists its full event history regardless of streaming (supplying no event sink still persists the history; it only means nothing is streamed out), and the stored history is exactly the sequence the live stream saw (persist-before-forward tee).
- **REQ-SESSION-175** — History and diagnostics writing never fails a run: the event history, transcript publication, change callbacks, diagnostics writers, and the timeline-to-wire bridge all degrade to logged warnings.
- **REQ-SESSION-176** — Per-session bindings (event sink, event history, transcript recording, hook running, approval handling, audit) bind late by session id and are discarded at run teardown, so that no leftover binding can influence a later run in the same process, and an event arriving after teardown has no destination.
- **REQ-SESSION-177** — The terminal `result` event is delivered exactly once per run — through the event bus for runs that started, written directly to the sink only for runs that never attached anything — and the exit code, the `result` payload, and the human summary all read off one shared derivation.
- **REQ-SESSION-178** — A session list is limited to what `metadata.json` holds, so every list-visible attribute (title, status, staleness inputs, checkpoint count, requirement attribution, awaiting-input) is denormalized into metadata at save time, with reader-side defaults for older directories.
- **REQ-SESSION-179** — Legacy data is honored but never rewritten: the legacy whole-state file loads when the split layout is absent, remains byte-identical forever after, and the session migrates forward on its first save.
- **REQ-SESSION-180** — Displayed liveness is re-derived from the same snapshot that renders the header (agents settled against the execution status; running tool rows neutralized on non-live sessions), so that an internally inconsistent snapshot — from an earlier version or from a killed process — is never rendered as one.
- **REQ-SESSION-181** — The CLI's created/resuming announcement follows whether the *host request* carried an existing session id, not what the run internally did: a host that pre-names a brand-new session still announces `Created session <id>`.

## Data & Formats

All formats below are externally observable: they are files a user can open, wire events a consumer can subscribe to, or command output a script can parse.

### Directory layout

```
<base_workspace>/.rotaris/          # the workspace the run was invoked against, never the worktree
  sessions/<session_id>/
    lock                          # {"pid": <int>, "acquired_at": "<UTC ISO>"} while owned
    metadata.json                 # derived listing surface (exact keys in REQ-SESSION-030)
    summary.md                    # derived human summary (REQ-SESSION-140)
    timeline.jsonl                # append-only timeline entries (REQ-SESSION-134)
    issues.json                   # {"issues": [...]}, ring-capped at 500
    metrics.json                  # derived metrics document (REQ-SESSION-139)
    .message_limit_paused         # optional durable pause signal (empty file)
    run.log                       # optional backward-compatible alias for evidence/debug.log
    state/
      resume.json                 # resumable state minus bulk fields
      ui_transcript.json          # {"events": [...]}
      ui_edit_diffs.json          # {"diffs": [...]}
      run_config.json             # write-once launch audit (REQ-SESSION-138)
      transcript_archive.jsonl    # optional; terminal-UI evicted transcript pages
    evidence/
      debug.log
      tool-calls.jsonl            # capped 5000
      model-input.jsonl           # capped 5000
      context-selection.jsonl     # capped 2000
      report-validation.jsonl     # capped 2000
      memory.jsonl                # capped 2000
      permissions.jsonl           # capped 5000
      events.jsonl                # durable event history, capped 20,000 (+ cap/8 slack)
      events.meta.json            # {"truncated": true, "dropped_events": N, "max_events": N, "last_trimmed_at": "..."}
      conversations/
        index.json                # {"conversations": [...]}
        event_logs/<conv_id>/events/*.json
    artifacts/                    # index.json + artifact bodies
    improvement_artifacts/        # optional
    snapshot.json                 # legacy layout only; read-only fallback
  improvement_artifacts/          # workspace-level copy store
```

### Session id

`YYYYMMDD-HHMMSS-` + 12 lowercase hex characters; regex `^\d{8}-\d{6}-[0-9a-f]{12}$`. The directory name equals the id. Ids are never reused.

### Resumable state (`state/resume.json`)

A single JSON object with `schema_version` (currently 1). Key inventory (bulk fields stripped on write per REQ-SESSION-029; `workspace_root` is the run's effective root, which for a worktree-bound run is the worktree path and not the directory anchor of REQ-SESSION-001): `session_id`, `workspace_root`, `created_at`, `updated_at` (UTC, `Z`-suffixed), `config_snapshot`, `transcript_events`, `ui_edit_diffs`, `child_states`, `report_artifacts` (refs with `id`/`agent_name`/`status`/`path`), `todo_state`, `agent_todo_state`, an outer-loop progress record (nullable), `token_usage` (nullable legacy aggregate), `execution_status`, `exhausted_provider_models`, `message_count`, `message_limit` (nullable), `wait_state` (nullable), `run_intent`, `permission_mode`, `check_suite` (nullable), `sandboxed`, `sandbox_backend`, `requirement_id`, `unit_id`, `worktree` (nullable binding record), `checkpoints`, `internal`, `run_type`, `global_tool_call_count`, `global_token_usage`, `global_cost` (default reads as source-unavailable), `global_compressions`, `agent_metrics` (map of agent name to `{tool_call_count, tool_calls, token_usage, cost, compressions, last_prompt_tokens}`), `root_context_tokens`, `seen_compression_ids` (map of agent name to sorted id list), `pending_questions`, `pending_approvals` (map of request id to payload), `verifier_state` (nullable), `gate_warning`, `active_model_key` (nullable), `runtime_model_configs`, `improvement_artifact_ids`.

Worktree binding record: `{path, branch, base_branch, base_revision, created_by_session (default true), merge_status: ready|integrating|merged|merge_failed, integration_session_id (nullable)}`.

Checkpoint entry: `{sequence, ref, commit, created_at, iteration (default 0), child_name (default ""), files (default []), kind: iteration|pre_restore|manual}`; list ordered newest-last.

### Listing metadata (`metadata.json`)

Exactly: `session_id`, `created_at`, `updated_at` (ISO strings), `execution_status`, `schema_version`, `internal`, `worktree` (record or null), `checkpoint_count`, `task_title`, `requirement_id`, `unit_id`, `awaiting_input`. Reader defaults: `checkpoint_count` 0, `task_title` falls back to the session id, attribution empty, `awaiting_input` false.

### Status vocabulary and exit codes

- Active statuses (assert an in-progress run): `starting`, `running`, `background`, `pausing`, `cancelling`.
- Terminal/idle statuses observed: `idle`, `paused`, `paused_message_limit`, `completed`, `failed`, `stopped`, `interrupted` (repair-only). The set is open-ended for hosts.
- Child terminal states: `succeeded`, `failed`, `cancelled`, `blocked`.
- Result-to-exit-code mapping: `completed` 0, `failed` 1, `error` 1, `max_iterations` 2, `interrupted` 130.

### Wire and stored events

One serialized event per line of `evidence/events.jsonl`, byte-identical to the live stream. Notable event types with persistence significance: `session.start` (first event of every run; payload per REQ-SESSION-090), `session.end` (mirrors the terminal result), `result` (exactly once per run), `transcript.row` (index + row copy, on append and settle), `tool.start`/`tool.finish`, `iteration.start`/`iteration.end` (iteration attribution boundaries), `gate.decision`, `gate.repair`, `error` (from error-severity issues, `fatal: false`). Unknown event types must survive read and export intact.

### Transcript rows

Persisted dictionaries with roles: `user`; `system`; `agent {name, persona, content}`; `thinking {name, persona, content, started_at?, chars, duration?}`; `tool {name, persona, tool, content (summary), detail (≤400 chars, single line), full_text (≤2000), full_detail (line structure preserved), tool_event_key, tool_terminal, status: running|ok|failed|blocked, started_at, duration?, stream_id? ("fg:<agent_name>" for terminal tools)}`; `verifier` (tool-shaped, `tool_event_key = "verify:<iteration>:<index>"`; check outcomes map passed→ok, failed/timeout→failed, skipped→blocked). Every row carries `ts` in local `HH:MM:SS`. Thinking content caps at 4000 chars while `chars` keeps counting.

Edit diffs persist separately keyed `diff_id = "<agent>:<tool_event_key>"` and merge beside exactly one row at display time.

### Timeline, issues, tool calls, permissions

- Timeline line: `{id: 12 hex, timestamp: UTC ISO, type, severity (default info), actor, message, metadata}`; durable line first, derived wire event second.
- Issue: `{id: 12 hex, timestamp, kind, severity, actor, message, evidence_ref, metadata}`.
- Tool call: `{timestamp, agent_name, tool_name, call_id, status, elapsed_ms, is_error}` + optional `args`, `result`, `outcome_kind`, `exit_code`, `failure_kind`, `warnings`; error-path args/result truncated to 2000 chars.
- Permission decision: `{timestamp, session_id, agent_id, persona, tool_name, decision, rule_id, source, summary, reason, request_id?}`; mode change: `{event: "permission_mode_change", requested_mode, effective_mode, previous_mode, source, reason, skipped_personas}`.
- Repair timeline entry: type `session.interrupted_recovered`, severity `warning`, actor `rotaris`, message `Session was still marked '<status>' but <reason>; status set to 'interrupted'.`, metadata `{previous_execution_status, execution_status, reason}`.

### Trajectory export document

`trajectory_version: 1`; identity (session id, task, workspace as the run reported it); permission mode; started/ended; status; stop reason; duration; `truncated`/`dropped_events`; recomputed summary (event/unknown/warning counts, `runs` = count of `session.start` boundaries, iterations, tool calls/failures, permission decisions/denials, verifier runs/failures, child agents, errors/fatal errors, per-type counts, tokens, cost); raw stored events (redaction inherited from the wire schema; unknown types intact).

## Open Questions

1. Under sustained save pressure on a `running` session, how many on-disk writes per minute may the debounce of REQ-SESSION-067 produce? "One write per closed window" is required; whether any further coalescing is expected of a conforming implementation is undetermined.
2. When two processes attempt the exclusive create of the same session `lock` at the same instant, exactly one must win (REQ-SESSION-050). Is anything required of the loser beyond the failures of REQ-SESSION-048 and REQ-SESSION-083 — a bounded retry, a wait, a distinct message?
3. REQ-SESSION-054 accepts pid recycling, cross-machine sessions on a shared filesystem, and Windows exited-but-still-handled processes as permanent limitations. Should the `lock` file instead carry a disambiguator (for example the owning process's start time) so that at least pid recycling becomes detectable?
4. When a follower tails a history that is being trimmed at that moment (REQ-SESSION-144, REQ-SESSION-149), must the restart flag be guaranteed to fire before any row derived from misaligned bytes can be displayed, or is briefly showing rows that are then discarded acceptable?
5. REQ-SESSION-073 calls the `execution_status` vocabulary open-ended for hosts. Is a host actually permitted to persist a value outside the listed set, and if so what governs how that value is displayed and mapped to a run result, beyond the "not active" rule of REQ-SESSION-055?
6. REQ-SESSION-036 defines degradation only for an *absent* secondary state file. If `state/ui_transcript.json`, `state/ui_edit_diffs.json` or `state/run_config.json` is present but unparseable, must the load degrade the same way (field left empty), or fail like a corrupt `resume.json` (REQ-SESSION-041)?
7. What must a desktop reattach to a command-line background run restore? REQ-SESSION-154 to REQ-SESSION-157 define the projections, but not which parts of a view a user is entitled to see restored rather than recomputed from scratch.
8. Is there an upper bound on the persisted transcript — row count, or total bytes of `state/ui_transcript.json` — beyond the per-row caps of REQ-SESSION-122, given that every save rewrites that file whole?
9. Which historical on-disk layouts must the legacy fallback of REQ-SESSION-037 accept? Only a session-root `snapshot.json` is specified; whether other pre-split arrangements must also load is unresolved.
10. A session repaired to `interrupted` (REQ-SESSION-061) that holds no progress record falls through the mapping of REQ-SESSION-076, which has no `interrupted` entry, and so yields a generic error result (`Run ended without a terminal status.`). Should `interrupted` be added to that mapping, or is the generic error the intended answer?
11. Should a session repaired to `interrupted` be visually distinguishable in the desktop list (REQ-SESSION-154) from one that has never been run? Rendering both identically is accurate about busy-ness but loses information.
12. **Conflict.** REQ-SESSION-029, REQ-SESSION-085 and REQ-SESSION-138 disagree about the configuration snapshot: 029 empties `config_snapshot` out of `state/resume.json` and points readers at `state/run_config.json`; 138 makes `state/run_config.json` write-once at session start and forbids later change; yet 085 requires the configuration rebound at worktree binding to be flushed to the session. Which is canonical — does `resume.json` keep a live `config_snapshot` after all, is `run_config.json` rewritten once binding is done, or is the rebound snapshot simply not durable?
13. **Conflict.** REQ-SESSION-047 disagrees with REQ-SESSION-056, REQ-SESSION-171 and REQ-SESSION-172 about a malformed lock. 047 reaps a `lock` whose pid is unreadable or absent; 056 requires exactly that case to report *live*, and 172 requires every uncertainty to resolve toward "still running". Which is canonical? Reaping risks stealing a live session's lock; reporting live makes a malformed lock unremovable, because a session that reports live is never stale and so never reaches repair (REQ-SESSION-057, REQ-SESSION-060).
14. **Conflict.** REQ-SESSION-074 offers two arms that both match a run finishing with zero completed *and* zero abandoned tasks ("zero abandoned → `completed`" and "zero completed → `failed`"). Which arm governs a run that produced no tasks at all?
15. **Conflict.** REQ-SESSION-099 and REQ-SESSION-101 assign different exit codes to the same invocation: `run --output-format stream-json` with neither a task nor `--session/-s` matches 099 (exit 2) and 101 (exit 1). Which exit code and which message are canonical?
16. REQ-SESSION-024 does not say whether `exhausted_provider_models` is ever cleared within a session — for example when a provider's quota window resets — nor whether the exclusion binds a model the user selects explicitly, or only automatic selection and automatic retry.
17. REQ-SESSION-025 requires a `pending_approvals` entry to disappear when its request "times out", but no timeout duration is fixed anywhere in this specification, and whether it is configurable is undetermined.
18. REQ-SESSION-066 and REQ-SESSION-164 require `checkpoints restore` to be refused for a session that claims a run in progress, but neither fixes the message text or the exit code the CLI returns for that refusal.
19. REQ-SESSION-084 requires two simultaneous `--isolate` launches to survive a worktree branch-name collision, but no resolution rule is given. With names generated as `rotaris/session/<id>` (REQ-SESSION-098) from ids that are never reused (REQ-SESSION-012), what produces a collision at all, and what branch name does the losing launch use instead?
20. REQ-SESSION-090 fixes the information a `session.start` payload carries but not its key names or value types, so payload compatibility with an existing consumer cannot be checked against this specification. The same gap applies to the key names of `metrics.json` (REQ-SESSION-139) and of the trajectory export document (REQ-SESSION-153).
21. Character caps appear throughout (REQ-SESSION-115, REQ-SESSION-122, REQ-SESSION-140), but only the todo list (`- [... additional todo tasks elided]`) and task titles (`...`) say what marks an elision. Is truncated text marked in the other cases, and is a tool row's `full_detail` capped at all?
22. REQ-SESSION-129 requires a dead child's open tool rows not to remain at status `running`, but does not say which status they take instead — `failed`, `blocked`, or `cancelled` (the child record itself becomes `cancelled` under REQ-SESSION-065).
23. REQ-SESSION-152 leaves three `events` details open: the exact text of the stderr notice printed when the workspace holds no stored sessions; where `events export` writes its document when `-o` is omitted; and how a batch export of several ids is structured, since REQ-SESSION-153 defines only a single-run document.
24. REQ-SESSION-158 requires a refused board launch to return an empty session id instead of raising, which leaves no channel for the reason. How is such a refusal reported to the user?
25. REQ-SESSION-170 conditions the reasoning-content repair on the session's default-persona model rejecting requests whose earlier assistant messages lack reasoning content, but does not say how that property of a model is established — a capability flag, an enumerated model list, or an observed failure.
