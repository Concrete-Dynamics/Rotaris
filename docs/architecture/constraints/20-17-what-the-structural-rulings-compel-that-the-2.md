| W-21 | **New. This row covers the other half, which has no constraint anywhere else and which **filters engines** exactly as W-03 does: "a reader MUST NOT be able to delay or block the writer… a store in which one blocks the other does not satisfy this requirement". Read with C-04 and U-03 — no delay floor of any size before publishing an unseen row — it is the sharpest single constraint the store must meet. ***Measured 2026-09-02, and the requirement is UNSATISFIABLE ON ITS LITERAL READING by any store whatever.*** A **compliant** reader — whole-session reads back to back, 147–1,603 ms per pass over 47,695–82,405 rows, inside read transactions — took the writer's commit from **p50 163.6 → 345.9 µs and p95 271.7 → 898.9 µs**, with **zero errors and zero lock contention**. | W-24 | **New. The whole-store backup and restore, and what the architecture may not choose about it.** `REQ-SESSION-201` is HARD and most of its content belongs above; it is here because four of the properties it forces are properties of a *mechanism* the specification deliberately does not name, and because it lands entirely on the store this section governs. **What the requirement fixes:** one artifact holding the whole store plus `REQ-SESSION-002`'s per-session files and nothing outside the store; a destination the user chooses through the platform's save dialog with nothing written until it is chosen; validity **while runs are live** — the backup must not stop, pause, delay, throttle or disturb a run and must not be refused because a session is live; a result that is "a state of the store that a reader could have observed at one moment"; a restore that is explicit, never automatic, never a repair, never silently merging, refused while any session in the target is live, and leaving the store exactly as it was where it fails; an artifact carrying the workspace identifier, with a restore into a different identifier reported rather than performed. **What the architecture therefore may not do** (ADR-0058): take the artifact by copying the store's files, because a file copy of a live store is not a state any reader could have observed; offer a merge; leave a partly restored store observable; or restore anything without the user having asked. **What the architecture chose and owns**, because the requirement fixes the outcome and not the means: an engine-level consistent-snapshot copy taken inside a read transaction; whole-store replacement with the displaced store **moved aside under a UTC timestamp and kept**, never deleted, extending W-17's never-delete-a-store rule to a second operation; three refusal gates before any mutation; and dropping lock rows whose `host` is not this machine on the way in (ADR-0005), because `REQ-SESSION-056` resolves a foreign-host lock toward live and `REQ-SESSION-047` never reaps it, so fidelity would make every session that was live at backup time permanently unreachable. ***"None of it is measured" is withdrawn (2026-09-02) and replaced by a split, because the two halves are now in different states and reporting them as one misprices both.*** **The backup half is measured and the choice is vindicated.** A naive file copy of a live store was unopenable **625 times in 627** — 150/152 under write-ahead logging and **475/475** under a rollback journal, so the rollback case is worse rather than a safe fallback — while the engine-level snapshot produced **8 valid snapshots out of 8** during 108,525 concurrent commits, integrity-clean, checksum-clean and monotonic, at a median **1,077 ms per 41 MB** on local storage. **And the trap is recorded so it is not fallen into twice**: the gentle version of that experiment, a realistic 20 commits per second against a small store, returns **0 bad copies in 40** — the obvious test gives a false all-clear and makes the choice look arbitrary. ***THE RESTORE HALF HAS NOW BEEN RUN (spike 22, 2026-09-02), AND "it is still spike 22 in every part" IS WITHDRAWN AND MUST NOT BE CITED.*** **The mechanism as the record wrote it does not work: 0 of 30.** Three defects were found by executing it, each on its first execution, none by any reading. **(1)** The staging store is opened read-write and no step closed it, so the rename of that directory failed `EPERM` in 30 of 30; `REQ-SESSION-201` gains a durative refusal and a prohibition on disturbing a live run; `REQ-SESSION-202` is minted for the end state defect 3 produced. **What the measurement confirmed, so no later pass disturbs it**: all three identifier cases including ESC-26's confirmed establishment and all five unreadable shapes; all three refusal gates including the older-schema case that must **not** refuse; ADR-0005 consequence 11's lock-row correction *against its own counterfactual*; the one-rename installation, with 20 of 20 gap observations seeing an absent store directory and never a mixed one; and the displaced store retained, openable and with its bodies intact. **Eight defects the spike found are NOT corrected and are listed in the gate verdict rather than here** — chiefly the unbounded close handshake (no result in 15,000 ms, twice), the container layout becoming the store's layout, and the undeleted staging copy. **Three inputs are still missing**: how far the write-ahead log grows while the snapshot's read transaction pins it on a large store under a live run — the snapshot's *correctness* is settled and its *log growth* is not, and it is the only input the mid-copy checkpoint and progress-reporting questions turn on; | W-27 | **New, from measurement. ONE STORE, ONE CANONICAL PATH SPELLING — and this is a correctness rule whose violation is silent.** The store's path is resolved **once**, in the workspace service, and the **resolved** path is handed to the run host; no other process derives a store path, from an identifier, from a last-seen path, or from anything else (W-18). **Why it is a rule rather than a happy consequence:** where one store file is reached through two path spellings, two writers each report **full success** while up to **95 % of committed rows vanish** — 20 of 20 trials wrong, 11 of them losing rows, final counts as low as 32 against an expected 600 — and `integrity_check` passes on **every one**, because the store is not corrupt, it is merely short. There is no error to detect and therefore no repair to offer. This needs no network: it is a same-machine hazard the moment two processes disagree about how to spell one path, and W-25 records that two spellings failing to canonicalise is a bounded outcome for the *workspace service* precisely because this row makes it impossible for the *store*. **The architecture already prevented this and prevented it by accident**; one sentence naming the reason turns a happy consequence into a guarantee, and the spike's own words are that it was prevented "by accident, not by stated intent". **A conformance test should open one store two ways and assert the product refuses**, because this is the one rule here whose violation looks like success. *Related and decided with it:* an exclusive locking mode is the obvious fix for a network path, is documented, and worked in the measurement — and is **refused**, because it is incompatible with the two-writer process table of W-02 and would make the other connection fail. | RULING (from measurement) | REQ-SESSION-197, REQ-SESSION-198, REQ-EVENTS-098; `spikes/remote-and-synchronised-storage.md` §4.5, §11 items 4–5; ADR-0058 rule 6, W-02, W-18, W-25 |

| W-29 | **New, from measurement. THREE RULES ABOUT REPLACING A DIRECTORY, ALL THREE WRITTEN BECAUSE THE RECORD GOT THEM WRONG ON PAPER AND MEASUREMENT SHOWED IT.** *(1)* **No connection may be open on *either* directory a rename touches — not the one being renamed, and not the one being renamed onto.** The old rule said "on the target", the staging store is not the target until the rename it is blocking has happened, and the mechanism therefore satisfied its own protective rule and still could not complete: `EPERM`, 30 of 30, against 30 of 30 with the connection closed first. This binds any later directory-renaming mechanism and not only the restore, and it is ADR-0004 rule 1 one level up — a single held handle anywhere inside a directory is fatal from **any** process, whether a plain descriptor, a store connection in this process, a store connection in another, or a process's current directory (0 of 30 in each case). *A corollary that is not hygiene:* an open store directory holds `workspace.db`, `-shm` and `-wal`; only a clean close leaves `workspace.db` alone, so closing is what makes the directory renameable at all. *(2)* **A reversal must be at least as robust as the step it undoes.** The record treated "the install fails" and "the reversal also fails" as independent events. They are the same event: a rename onto a name that does not exist succeeds 30 of 30, the two ways it fails are a held handle and an occupied name, and where the install failed on an occupied name the reversal was a rename onto that same occupied name and failed identically. A reversal that works only when nothing went wrong is a second copy of the failing step, and it will be exercised for the first time on the day it is needed. ADR-0058's reversal is now displace-then-rename, which is the shape ADR-0054's commit step was already corrected into — **the same platform fact broke both, independently, in two records**. *(3)* **A store directory that exists and holds no database MUST NOT be reachable, and this is testable.** It was reachable, durably, in 20 of 20 occupied-name failures, surviving re-open and restart. `REQ-SESSION-043` fixes what an *absent* store means and nothing fixed what a *present but empty* one means; `REQ-SESSION-202` now does, and the reversal's displace step is what keeps the mechanism from producing it. **Do not read consequence 7's confirmed absent-directory observable as covering this**: the gap on the normal path is 3–5 ms and was never mixed, and that is a different state from a directory that stays empty for ever. | RULING (from measurement) | REQ-SESSION-043, REQ-SESSION-202, REQ-SESSION-201; `spikes/backup-restore-mechanism.md` §4, §5.1–5.3, §14 D1/D4; ADR-0058, ADR-0054, ADR-0004 rule 1 |
| W-30 | **New. THE REFUSAL-WHILE-LIVE IS A CONDITION THAT HOLDS THROUGHOUT, NOT A TEST TAKEN ONCE — and the specification now says so.** `REQ-SESSION-201`'s "refused while any session in the target store is live" attached *refused* to the decision to begin and was satisfiable by one evaluation at the request. Measured: the predicate itself is correct in 30 of 30 — it refuses a live lock, admits one this machine proves dead, refuses one naming another machine — and the mechanism still destroyed a session, because the gate ran before the run host was told to refuse runs and nothing re-checked. **The requirement now states that the refusal holds for the whole of the restore**, that no session in the target may become live between the answer and the completion or abandonment, and — the clause that makes it testable *before* data is lost — that **a restore never disturbs a live session**: it may not stop, cancel, interrupt or require a run under way to give up the store it is recording into, and the remedy on finding one live is to refuse, never to clear it out of the way. The specification deliberately does **not** pick which end of the window is closed; the architecture must. **Two obligations therefore fall on ADR-0002 consequence 11 that consequence 11 does not state**: the refusal of new runs must be in force before liveness is judged, and the failure path must **release** the run host.
