# How an installed Rotaris updates itself

SWR-3003. A Rotaris that was downloaded rather than `pip install`ed has no
package manager behind it, so it asks GitHub once per launch whether a newer
release exists, and offers to fetch it.

The pip packages are not covered here and never check: `pip install --upgrade
rotaris-core rotaris` is the mechanism those users already have.

## What happens on launch

1. Rotaris works out how it was installed. A source checkout or a pip install
   stops here — the check does not run at all.
2. It asks `https://api.github.com/repos/Concrete-Dynamics/Rotaris/releases/latest`,
   with a ten-second timeout.
3. Anything other than a published release with a newer `v<x>.<y>.<z>` tag ends
   the same way: nothing is shown, a line goes to the log, and the window opens
   normally. That covers being offline, being behind a captive portal, the
   unauthenticated rate limit, a draft or pre-release, and the 404 GitHub returns
   while the repository has no release yet.
4. If there is something newer *and* the release carries a file this
   installation can use, a banner appears over the open window: the version, the
   first line of the changelog, **Update now**, and **Dismiss**.

Dismissing records that one version under `updates/dismissedVersion`. The banner
stays away for that release and comes back for the next one.

## What "Update now" does per installation

The strategy follows the installation flavour, not the operating system —
Windows ships two flavours whose update paths have nothing in common.

| Installed as | Downloads | Then |
| --- | --- | --- |
| Windows installer (`%LOCALAPPDATA%\Rotaris`) | `Rotaris-<v>-windows-x64-setup.exe` | Starts the installer and closes Rotaris |
| Windows portable (`.exe`) | `Rotaris-<v>-windows-x64-portable.exe` | Renames the running file aside, moves the new one in, offers **Restart now** |
| Linux AppImage | `Rotaris-<v>-linux-x86_64.AppImage` | Replaces the file `$APPIMAGE` names, offers **Restart now** |
| macOS `.app` | `Rotaris-<v>-macos-arm64.dmg` | Opens the verified disk image; you drag Rotaris to Applications |

Two of those hand off rather than restart, for reasons that are not cosmetic:

- **Windows installer.** The installed tree is a directory of DLLs the running
  process has mapped. Nothing can replace it in place, so Rotaris closes and lets
  NSIS do the work it already does on a fresh install — including removing files
  this version has and the next one does not.
- **macOS.** The bundle is unsigned and un-notarized. A disk image the
  application downloads for itself is marked `com.apple.quarantine`, and a bundle
  installed under that mark is one macOS reports as damaged and refuses to open.
  Handing you the image avoids shipping an update that bricks the app. This
  changes when Rotaris is signed.

## What "verified" means here

Every download is hashed and compared against the `SHA256SUMS.txt` published with
the release — the same file `sha256sum -c` reads, generated by the same code that
named the artifacts.

That is **integrity, not authenticity**. It catches a truncated download, a
corrupted mirror, and a proxy that mangled the bytes. It does not catch someone
who controls the connection, because the manifest arrives over that same
connection and nothing Rotaris ships is signed. Signing and notarization are
tracked separately; until they exist, the checksum is a consistency check, not a
proof of origin.

A mismatch deletes the download and installs nothing. The installation is not
touched until a verified replacement exists, so a failure at any stage leaves you
running exactly what you were running.

## Turning it off

Dismissing the banner suppresses that version. There is no global switch: the
check is one request per launch, it produces no UI unless there is something to
say, and it never installs anything without being asked.

## Where the code is

| Concern | File |
| --- | --- |
| Install detection, version compare, asset selection, checksum parsing | `src/rotaris_core/updates/check.py` |
| Download, verification, the four install strategies | `src/rotaris_core/updates/apply.py` |
| The worker thread and its signals | `apps/rotaris/src/rotaris/services/update_bridge.py` |
| The banner, the actions, the dismissed version | `apps/rotaris/src/rotaris/views/main_window.py` |

The artifact names come from `src/rotaris_core/packaging/release.py`, the same
module the release workflow uploads with. Renaming an artifact there changes what
the updater downloads, which is why that module is the only place the names
appear — see [`releasing.md`](releasing.md).

Tests: `tests/unit/updates/`, `tests/integration/test_update_api.py`,
`tests/integration/test_update_download.py`, and
`apps/rotaris/tests/test_update_ui.py` for the flow through the real window.
