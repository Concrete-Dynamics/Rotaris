# Resolution Record — Domain 09, User-Defined Lifecycle Hook Commands

This record disposes of every open question raised in the draft of
[`../09-lifecycle-hooks.md`](../09-lifecycle-hooks.md) (domain 09, requirement prefix `REQ-HOOKS`).
The body of that specification has been amended so that each decision below is stated normatively in
place; the numbering of the original open questions is preserved here so the draft and the resolved
specification can be read against each other.

The product-owner decisions of 2026-08-30 that governed the dispositions:

1. **Compatibility ambition is behavioral inspiration only.** No obligation to match any other
   implementation's formats, surface, exit codes, or event vocabulary. Under-determined cases are
   decided here on their merits, never preserved for compatibility.
2. **Defect policy: omit what conflicts.** Internal contradictions are resolved toward the reading
   more coherent with the rest of the document; where no coherent reading exists, the behavior is
   withdrawn rather than reproduced.
3. **Unbuilt-but-intended behavior stays in scope.** A requirement is not dropped merely because it
   describes intent.
4. **The product is one Electron desktop application.** It has no command-line interface and no
   terminal user interface — removed, not deferred. Domains 17 and 18 are retired and the `REQ-TUI`
   and `REQ-CLI` identifiers are withdrawn, so no requirement here cites them. Requirements in this
   domain whose only observable surface was a shell invocation are **withdrawn**, and every
   capability that reached a user only through such a surface is carried by a new desktop-reachable
   requirement. See the graphical-only sweep below. Running external programs is untouched: hook
   commands, agent tool execution, tool servers on the stdio transport, and version-control
   invocations all remain fully in scope — what is removed is any way for a *user* to drive this
   product from a shell.
5. **Message text states required information content, not exact wording**, except where a string is
   part of a machine-readable contract (an event field value, an enum, a parseable output format).
   Open questions asking only about phrasing, punctuation, separators, or inflection of a
   human-readable message are resolved by fixing the information the message must carry and leaving
   the wording to the implementation.

Cross-domain vocabulary was taken from `01-run-orchestration.md` (child terminal states REQ-ORCH-041,
report status REQ-ORCH-112, iteration outcome dispatch REQ-ORCH-074), `12-desktop-shell-windows.md`
(logical pixels, REQ-SHELL-022 and REQ-SHELL-030), `15-settings-configuration.md` (the per-user
global configuration directory, REQ-CONFIG-001), `19-notifications-errors-recovery.md` (hook notices
and the closed four-statement hook-trust vocabulary, REQ-NOTIFY-223 to REQ-NOTIFY-228) and
`20-event-history-replay-export.md` (run status vocabulary REQ-EVENTS-026, event catalog
REQ-EVENTS-041, hook event shape REQ-EVENTS-047). No other specification was consulted, and no
identifier, name, or phrasing was taken from any other implementation.

New requirements added by these resolutions: **REQ-HOOKS-136** through **REQ-HOOKS-139**. No
requirement identifier was renumbered, reused, or deleted. Of the 36 open questions raised in the
draft, all 36 are resolved: none omitted, none moot, and none escalated.

Two amendments fall outside the numbered questions and are recorded here for completeness. The
Data & Formats prose describing a one-off rename of directories left behind by an earlier product
name is deleted under the no-legacy-adoption decision: a clean-room product has no earlier directory
to migrate from, and both configuration directories are now addressed by their current names only.
And REQ-HOOKS-115's `<config-dir>` is restated as the per-user global configuration directory of
REQ-CONFIG-001, which resolves per platform, in place of `~/.config/rotaris` on every platform —
a direct contradiction with domain 15 about the same directory.

## Graphical-only sweep

The product has no command-line interface and no terminal user interface, so a requirement reachable
only from a shell is withdrawn and its capability re-sited on the desktop.

| Withdrawn | Why its only surface was a shell | Capability now carried by |
| --- | --- | --- |
| **REQ-HOOKS-016** — a configuration file named by a `--config <path>` override carries no scope tag, resolves as scope `default`, and is therefore trusted | The override existed only as a command-line flag; without an argv there is no way to name such a file, and no other reading of the requirement survives | The capability is *deliberate user consent to a configuration source's hooks, as opposed to hooks that arrived with a checkout*. It is carried by the review dialog of REQ-HOOKS-104 to REQ-HOOKS-108 — where the user reads the commands and allows or refuses them — and by **REQ-HOOKS-136** (new), which lets the user revisit, change, or clear that decision at any time from the hooks settings tab. REQ-HOOKS-090's citation of REQ-HOOKS-016 is removed; REQ-HOOKS-014 already fixes that an untagged entry resolves as scope `default`. |

Three further requirements named a shell venue beside a desktop one. Each keeps its substance and
loses only the shell half, so nothing is withdrawn and no capability moves:

- **REQ-HOOKS-083** — "on every host alike — desktop, headless, and programmatic embedding" becomes
  "the desktop application and any programmatic embedding of its engine". A programmatic embedding
  is not a user entry point; it is the engine layer the desktop application itself drives.
- **REQ-HOOKS-086** — the sentence requiring headless runs to print the withheld-hooks notice to the
  console is removed. The capability it served — telling hooks withheld on purpose apart from hooks
  that are broken — is restated over the surfaces that do exist: the desktop notice channel
  (REQ-NOTIFY-224), the `blocked — not reviewed` row status of REQ-HOOKS-103, and the `hook_failure`
  issues of REQ-HOOKS-120, which record the broken ones separately.
- **REQ-HOOKS-089** — "Desktop and headless runs SHALL share one execution lifecycle" becomes a run
  started from the desktop interface and a run started by a programmatic embedding of the engine.
  The invariant is the point of the requirement and is preserved intact.

**REQ-HOOKS-102** listed "console output" among the surfaces a withheld hook's name and command must
never reach. Since there is no console venue, the list now names the desktop interface itself and the
application log, which widens the guarantee rather than narrowing it.

## Dispositions

| OQ # | Disposition | Decision taken | Requirements touched |
| --- | --- | --- | --- |
| 1 | RESOLVED | Deliberate, and now stated as such rather than left as a note. Termination reaches only the process that was started and is never widened to its process group; the fate of that process's descendants is left to the platform and is explicitly unconstrained — a descendant may outlive both the hook process and the run, whether or not it detached first, and the run neither waits for it, tracks it, nor reports it. Collecting the terminated process's output never blocks on a stream a surviving descendant still holds open: the 5.0 s grace period bounds that collection, and expiring it yields empty output. | REQ-HOOKS-033 |
| 2 | RESOLVED | The invocation finishes regardless. The outcome is completed and returned, the run continues, and the still-running process is recorded as a log entry only. No user-facing warning beyond the ordinary timeout warning of REQ-HOOKS-052 is produced and no run status is affected, so a host that cannot kill a process can never stall a run or change how it ended. | REQ-HOOKS-033, REQ-HOOKS-129 |
| 3 | RESOLVED | No — hook invocations stay off the run transcript and the agent activity views, because a hook is the user's own code and its execution is not part of what an agent did. The surface set is closed explicitly instead: notice channel, hooks settings tab and the review dialog it opens, session diagnostics files, session event stream, application log. Since withdrawing the headless console notice removed the only "see what the hooks actually did" surface a non-desktop user had, the settings tab gains a read-only per-session invocation list — display name or stable id, event, tool name, exit status as the timeline records it, duration, timed-out and blocked flags, and the masked captured output — and that list is what the switched-off advisory now directs the user to. | REQ-HOOKS-137 (new), REQ-HOOKS-138 (new), REQ-HOOKS-054 |
| 4 | RESOLVED | Users may rely on it; an implementation may not stop dispatching. Every applicable hook runs, in declaration order, and the first stopping outcome is the verdict, decided once all of them have finished. The later hooks' side effects on the working tree, their `hook.start`/`hook.finish` pairs, their `hook_run` timeline entries, and their contribution to the failure tallies of REQ-HOOKS-055 all occur exactly as they would have with no refusal. | REQ-HOOKS-040 |
| 5 | RESOLVED | Yes to both, for lifecycle events and tool events alike. Declaration order governs selection and execution, and the hooks of one occurrence run one after another rather than concurrently, each finishing — normally or under the REQ-HOOKS-033 bound — before the next starts, so an occurrence with N applicable hooks is bounded by the sum of their individual bounds. | REQ-HOOKS-019, REQ-HOOKS-040, REQ-HOOKS-080 |
| 6 | RESOLVED | Embedders only. No host is required to offer per-run environment overrides, the desktop application supplies none, and no configuration key, preference, or user interface for setting them exists. The product contributes no hook-specific variables of its own; a hook needing a variable sets it inside its own `command`, and a run started from the desktop application sees exactly the environment the application itself was started with. | REQ-HOOKS-032 |
| 7 | RESOLVED | Bounds are fixed under one stated reference condition — a single execution thread on a contemporary developer workstation with a solid-state disk and a warm file-system cache, the operation timed alone. 50 ms to validate, resolve, fingerprint, or trust-gate a configuration of up to 100 entries across all scopes, growing no worse than linearly beyond; 10 ms to build a payload carrying up to 100 KB of text after masking, linear in total string length; under 1 ms to decide that an occurrence has no applicable hook, so a session with no hooks pays no measurable per-call cost; and the product's 100 ms interface responsiveness budget for the settings tab, the trust summary, the review dialog and the invocation list. Time spent inside a hook process is deliberately unbounded except by `timeout_seconds` and the 5.0 s grace period. | REQ-HOOKS-139 (new), REQ-HOOKS-135 |
| 8 | RESOLVED | No maximum is fixed, and the guarantees are invariants rather than best-effort behavior: one failure tally per stable id for the whole session whichever call produced the failures, one switch-off warning and one switched-off id however many outstanding calls met the failing hook at once, one `hook.start`/`hook.finish` pair and one timeline entry per invocation, and no cross-call delay from a hook that consumes its entire budget. Every one of them holds at every degree of concurrency the host reaches. | REQ-HOOKS-042 |
| 9 | RESOLVED | Exhaustive, not a floor. The listed credential names and the eight value prefixes are the complete set that masking recognizes; an implementation recognizing exactly these and nothing further is conformant, and adding a further name, prefix, or resemblance-based heuristic is a defect rather than an improvement. This is the only reading under which REQ-HOOKS-062's guarantee — that a string under a non-credential key arrives unaltered — is testable in both directions. | REQ-HOOKS-061 |
| 10 | RESOLVED | The headless half of the question falls away with the shell surfaces; the desktop half was a real gap and is closed. The hooks settings tab is the product's one venue for the whole decision lifecycle of REQ-HOOKS-093: the review dialog grants or refuses, and a new control clears a stored decision, re-applying the gate at once so the summary status returns to `review` — or to `none` where the workspace declares no hooks — and the hooks are withheld again until allowed afresh. Reopening the dialog while a decision is stored replaces it. A failed clear is reported on the tab, never absorbed. No configuration key, preference, or environment variable can approve a workspace's hooks. | REQ-HOOKS-136 (new), REQ-HOOKS-093, REQ-HOOKS-105 |
| 11 | RESOLVED | Under the message-text decision no literal is fixed. What is fixed is the machine-readable YAML path `hooks.entries.<i>.timeout_seconds` and the information the message must carry: which field was rejected, the value that was rejected, and that the budget must be greater than zero. The three literals the draft quoted for the other validation failures are restated the same way, so all four failures obey one rule and the paths alone are the contract. | REQ-HOOKS-012 |
| 12 | RESOLVED | All of them. A failing load reports every invalid entry it found, in ascending `<i>` order within a scope and in scope-precedence order across scopes, each with its own path and message, so a user correcting a configuration file is not led through the failures one at a time. No entry is dropped, ignored, or repaired, and no configuration is produced. | REQ-HOOKS-012 |
| 13 | RESOLVED | `*` is the only metacharacter. `?`, `[`, `]` and every other character are compared literally, so `git push -?` matches the literal token `-?` and nothing else and there are no character classes to place anywhere. The single structural exception stays: where the pattern's final token is a bare `*`, the segment may carry any number of further tokens, zero included. Comparison is case-sensitive, positional, and never a substring search. | REQ-HOOKS-025, REQ-HOOKS-026 |
| 14 | RESOLVED | Two answers. Interpreter: on a POSIX host the standard shell at `/bin/sh`, the command passed as a single argument to `-c`; on Windows the processor named by `ComSpec`, or `cmd.exe` where that variable is unset or blank, the command passed as a single argument to `/c`. No other interpreter is ever selected and the choice never varies with the content of `command`, so one declaration behaves identically on every machine of a given platform — PowerShell is deliberately not chosen. Payload field: `workspace` reports the base workspace, while the process's working directory is the tree the run is changing, which is the isolated worktree where the run is confined to one. The two are different on purpose and both are now stated where they are used. | REQ-HOOKS-030, REQ-HOOKS-057, REQ-HOOKS-084 |
| 15 | RESOLVED | To the decoded text, counted as the UTF-8 encoding of what is retained, with the cut at a character boundary: the retained portion is the longest prefix of the decoded text whose UTF-8 encoding is at most 16384 bytes, so a multi-byte character is never split. The marker is appended beyond the limit and does not count toward it. This is stated as the truncation rule for the whole domain, so the 200-character excerpt of REQ-HOOKS-052 and the 4096-character result text of REQ-HOOKS-066 follow it too. | REQ-HOOKS-037, REQ-HOOKS-052, REQ-HOOKS-066 |
| 16 | RESOLVED | The fixed value is canonical. A hook ended by a signal that did not come from the timeout path reports the no-exit-status value — `-1` wherever an exit code is recorded verbatim, `null` on the session event stream — with `timed_out` false, and never the platform's raw signal number. It does not produce the "exited `<code>`" warning, which is reserved for a process that did exit. It produces the abnormal-termination warning that REQ-HOOKS-039 referred to but REQ-HOOKS-052 never defined; that gap is closed by adding the warning, which conveys the hook's display name, its event, and that the process ended before returning an exit status, and which quotes no signal number and does not read as a timeout. | REQ-HOOKS-036, REQ-HOOKS-039, REQ-HOOKS-052 |
| 17 | RESOLVED | Two parts. `<budget>` must convey the configured `timeout_seconds` as a number of seconds; how many decimal places it carries and whether a whole number is written bare are left to the implementation, provided one rendering is used consistently wherever a budget reaches the user or the agent in this domain. The trailing `…` is appended beyond the 200 characters and does not count toward them, under the domain-wide truncation rule of REQ-HOOKS-037. | REQ-HOOKS-050, REQ-HOOKS-052 |
| 18 | RESOLVED | It inflects. One rule now governs every user-facing count in this domain: the text is grammatically correct for the count it carries, so an `<N>` of 1 reads in the singular throughout and no `hook(s)` or `was/were` construction is ever emitted literally. The advisory's fixed content is the count, that those hooks were switched off for the rest of this session after failing repeatedly, and where the command output can be read; the wording is the implementation's. | REQ-HOOKS-054, REQ-HOOKS-101 |
| 19 | RESOLVED | Exactly one value token and no further. A value opening with a single or a double quote ends at its matching closing quote and the quote characters are retained around the `***`; an unquoted value ends at the first whitespace after it, or at the end of the string where none follows. So `--token abc def` masks to `--token *** def`, `password: a b` to `password: *** b`, and `password: "a b"` to `password: "***"`. Masking to end of line was rejected: it erases legitimate text that merely happens to follow a credential, and it would make a masked command line unreadable to the user in the review dialog and in `state/run_config.json`. | REQ-HOOKS-061 |
| 20 | RESOLVED | The container is walked, not replaced wholesale. Its shape is preserved as REQ-HOOKS-060 requires, and every string within it at every depth — whatever the intervening keys are called — arrives as `***` in its entirety, exactly as though it were itself stored directly under a credential-named key; non-string scalars within it are unchanged. `{"tokens": ["abc", {"live": "def"}]}` reaches the hook as `{"tokens": ["***", {"live": "***"}]}`. This satisfies both requirements at once instead of sacrificing either: nothing leaks, and a hook script indexing into the structure still finds the structure it expected. | REQ-HOOKS-060, REQ-HOOKS-062 |
| 21 | RESOLVED | The top-level payload object is level 0, the values it holds directly are level 1, and so on; the value written as its masked text form is the one lying at a level greater than 12. Not-a-number, positive infinity, and negative infinity are written as the JSON strings `"NaN"`, `"Infinity"`, and `"-Infinity"`, which keeps the document parseable by a hook script that does no more than call a standard JSON parser. | REQ-HOOKS-063 |
| 22 | RESOLVED | The vocabularies are owned by other domains and are cited rather than duplicated. `session_end.status` carries one value of the run status vocabulary of REQ-EVENTS-026 — `completed`, `failed`, `max_iterations`, `interrupted`, `error` — or `""` for unknown. `child_completed.state` carries a child's terminal state under REQ-ORCH-041: `succeeded`, `failed`, `cancelled`, `blocked`. `child_completed.status` carries the child report status of REQ-ORCH-112: `succeeded`, `partial`, `failed`, `cancelled`, `blocked`. `iteration_end.outcome` carries the report status, after any rewrite, that REQ-ORCH-074 dispatched on, from that same report-status vocabulary; `iteration_end.status` carries the terminal state recorded for the iteration's own record under REQ-ORCH-041 — which is why both fields exist and may legitimately differ, a `blocked` outcome being recorded as a `succeeded` iteration. A value the owning domain does not list is carried through as text rather than corrected, and `""` reads as unknown, never as failure. | REQ-HOOKS-075 |
| 23 | RESOLVED | Disabled entries are included, in the fingerprinted list and in the pending-review list alike. Since `enabled` is not part of an entry's document, switching an entry on or off changes neither the digest nor the stored decision: what the user reviewed and allowed is the set of commands the workspace declares, so an entry read while switched off may later be switched on without a fresh review, while rewriting, adding, removing, or reordering any entry invalidates the decision at once. Excluding them was rejected because a bare `enabled` toggle would then revoke the approval, contradicting REQ-HOOKS-091's own statement that toggling `enabled` alone leaves the digest unchanged. The review dialog marks such an entry as currently inert, so consent is informed. | REQ-HOOKS-091, REQ-HOOKS-092, REQ-HOOKS-106 |
| 24 | RESOLVED | The five values are selected by first-match in the order the vocabulary is listed. `inactive` — the hook cannot run for a reason declared in configuration rather than chosen on the tab: `hooks.enabled: false`, the entry's own `enabled: false`, or an imported record discovery marked unusable. `disabled by agent` — the row's owning agent toggle in the external-hooks policy file is false. `disabled` — that agent toggle is on but the row's own per-hook toggle is false. `blocked — not reviewed` — a workspace-scoped hook the trust gate withheld. `active` — none of the four applies. First-match in listed order means a hook that is both declared off and toggled off reads as `inactive`, the condition the user cannot change from this tab. | REQ-HOOKS-103 |
| 25 | RESOLVED | Cross-implementation stability is not required — a policy file records one installation's choices and is not a portable document — but the identity is nevertheless fully determined so it is reproducible by inspection. The digest input is the UTF-8 encoding of the canonical JSON document `{"agent", "event", "group_index", "handler", "handler_index", "matcher", "source"}` with keys sorted, compact separators and ASCII escaping, the handler canonicalized the same way; the identity is `claude-code:` followed by the first 20 characters of the SHA-256 digest in lowercase hexadecimal. | REQ-HOOKS-114 |
| 26 | RESOLVED | Yes, they are masked, and the masking-channel list grows from five channels to six to say so. The session directory is readable by anyone who can look inside it, which is the same reason REQ-HOOKS-118 already stores the command masked; leaving the captured streams unmasked there would have defeated the guarantee the rest of the requirement makes. | REQ-HOOKS-119, REQ-HOOKS-133 |
| 27 | RESOLVED | One quoting convention on every platform alike, not the host's own. A token break falls at each run of whitespace outside quotes; a single- or double-quoted run groups its contents into the surrounding token and the quote characters are removed; a backslash is an ordinary literal character, never an escape and never a quote. A Windows candidate such as `copy C:\repo\a C:\repo\b` therefore splits into exactly three tokens with every separator intact, and a matcher written once behaves identically wherever it runs. An unterminated quote makes the text untokenizable, which REQ-HOOKS-028 resolves as "no match". | REQ-HOOKS-025, REQ-HOOKS-028 |
| 28 | RESOLVED | The final byte is the closing brace. No trailing newline and no other trailing byte may follow the object, so a hook comparing raw bytes and a hook parsing them agree on where the document ends. | REQ-HOOKS-031, REQ-HOOKS-067 |
| 29 | RESOLVED | Under the message-text decision the separator is not fixed: how the excerpt is joined to the sentence before it is left to the implementation, subject to one constraint that is normative — the excerpt must remain separately identifiable as the hook's own output and must not read as a continuation of the sentence. What is fixed is the excerpt's content: standard error, or standard output where standard error is empty, whitespace runs collapsed to single spaces, 200 characters retained with `…` appended beyond them. | REQ-HOOKS-052 |
| 30 | RESOLVED | Without regard to case, like every other comparison in the masking rule. `bearer`, `BASIC`, and `Token` trigger masking exactly as `Bearer`, `Basic`, and `token` do. A case-sensitive pass would have been a silent hole an attacker controls by choosing capitalization. | REQ-HOOKS-061 |
| 31 | RESOLVED | The marker extends beyond the 4096 characters; only the retained text counts toward the limit. This is the domain-wide truncation rule of REQ-HOOKS-037 applied here, so a hook parsing a truncated `result` text can subtract the marker without first guessing whether it was inside or outside the budget. | REQ-HOOKS-066, REQ-HOOKS-037 |
| 32 | RESOLVED | `executed` and `passed` are always present and always JSON booleans. An occurrence supplying neither, or supplying a value that is not a boolean, yields `false` — never `""`, never an absent key, and never a string — so a hook script may test them without first checking their type. A field declared boolean never holds a string; the `""` fallback governs string fields only and the `0` fallback governs `iteration` only. `false` was chosen over an absent key because a verifier pass no one can confirm ran, or ran and passed, must not read as one that did. | REQ-HOOKS-075, REQ-HOOKS-077 |
| 33 | RESOLVED | The stable id, never the configured display name and never an empty string. | 34 | RESOLVED | `none`. Nothing could be read, so nothing can run, and REQ-NOTIFY-227 closes the hook-trust vocabulary at four statements and admits no fifth for this case. | 35 | RESOLVED | Logical pixels — the unit REQ-SHELL-022 uses for every window dimension in this product, so the 620×440 minimum holds as the same physical area at every display scaling factor (REQ-SHELL-030) and is testable as written. | 36 | RESOLVED | Only runs started afterwards. REQ-HOOKS-131's fixed-at-run-start rule is canonical, and REQ-HOOKS-117's "at run time" is restated to mean *when the run's hook set is assembled*: the agent and per-hook toggles are read once, then never again for that run.
