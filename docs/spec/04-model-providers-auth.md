# Model Providers, Sign-In, and Model Routing

## Overview

Rotaris connects to a fixed set of AI model providers plus user-defined OpenAI-compatible endpoints. Users sign in per provider using a device-code flow, a browser authorization-code-with-PKCE flow, or a pasted API key/token; credentials are persisted per provider in a per-user credential store, transparently refreshed, and never written to logs, config snapshots, or workspace files. After sign-in, the product discovers each provider's model catalog over the wire (or from a fixed offline list), persists the discovered catalog to a per-user snapshot, automatically assigns models to small/medium/large capability slots, and merges the snapshot into the effective configuration at load time. Command-line, terminal-UI, and desktop surfaces expose sign-in, sign-out, provider settings, catalog refresh, model slot assignment, subscription usage, and hosted-account credit displays with the exact user-visible messages, timeouts, and exit codes specified below.

## Requirements

### Provider Catalog and Transparency Metadata

- **REQ-PROVIDER-001** — The application ships a built-in catalog of exactly six providers with stable identifiers, in this fixed order: `concrete-cloud`, `copilot`, `codex`, `openai-compatible`, `claude-code`, `deepseek`. Their display names are, respectively: "Rotaris Cloud (recommended)", "GitHub Copilot", "OpenAI Codex", "OpenAI-compatible", "Claude Code (subscription)", "DeepSeek". Enumerating the catalog returns entries in that order, with the hosted provider first (it is the first row in the sign-in menu).

- **REQ-PROVIDER-002** — Every catalog entry carries this attribute set, and any read of the catalog on a given build returns the same values: identifier; display name; sign-in method; model-catalog (discovery) endpoint URL; discovery authorization header scheme, which is `Bearer` for all six built-in entries; default API base URL; connection mode, mandatory and drawn from `hosted-cloud`, `direct`, `local-sdk`, `custom`; operator name (optional); privacy-policy URL (optional); availability, which reads available unless the build declares the entry unavailable; unavailability reason (optional). Discovery endpoint and base URL are independent attributes: a built-in entry's discovery URL is the one declared in REQ-PROVIDER-005 and need not equal `<base URL>/models`. Endpoint and base-URL values a user supplies for an `openai-compatible` instance are held against that instance (REQ-PROVIDER-052) and leave the catalog entry they were seeded from unchanged.

- **REQ-PROVIDER-003** — Catalog integrity is validated, and violations are rejected as errors: every built-in entry must declare a connection mode; hosted-cloud and direct entries must yield a non-empty destination hostname derived from their default base URL; a custom-mode entry must NOT declare a fixed operator name; any entry marked unavailable must supply an unavailability reason.

- **REQ-PROVIDER-004** — Destination-host resolution: for local-sdk and custom modes the destination host is empty/none; for all other modes it is the hostname parsed from the default base URL (e.g. `rotaris.ai`, `api.githubcopilot.com`, `chatgpt.com`, `api.deepseek.com`).

- **REQ-PROVIDER-005** — Fixed per-provider endpoints and transparency metadata. Each built-in entry declares its discovery URL outright; for `deepseek` that URL deliberately differs from `<base>/models`, and deriving a discovery URL from a base URL (REQ-PROVIDER-053) applies only to user-supplied `openai-compatible` endpoints.
  - `concrete-cloud`: discovery `https://rotaris.ai/v1/models`, base `https://rotaris.ai/v1`, operator "Concrete Dynamics UG (haftungsbeschränkt)", privacy URL `https://rotaris.ai/privacy`.
  - `copilot`: discovery `https://api.githubcopilot.com/models`, base `https://api.githubcopilot.com`, operator "GitHub".
  - `codex`: discovery `https://chatgpt.com/backend-api/codex/models`, base `https://chatgpt.com/backend-api/codex`, operator "OpenAI".
  - `openai-compatible`: discovery `https://api.openai.com/v1/models`, base `https://api.openai.com/v1`. These are the values the sign-in prompt offers as defaults (REQ-PROVIDER-052); what an instance actually calls is the value stored for that instance.
  - `claude-code`: both fields hold a placeholder that names no reachable host. No name resolution, connection, or request is ever directed at either value, and this provider's catalog is served offline (REQ-PROVIDER-047).
  - `deepseek`: discovery `https://api.deepseek.com/models`, base `https://api.deepseek.com/v1`, operator "DeepSeek".

- **REQ-PROVIDER-006** — The hosted provider `concrete-cloud` ships marked unavailable with unavailability reason "Rotaris Cloud is coming soon." This "coming soon" state is a static catalog attribute of the build, not a runtime probe.

- **REQ-PROVIDER-007** — Looking up an unknown provider id in the catalog is an error; listing the catalog preserves the fixed insertion order.

### Sign-In Methods, Token Model, and Status Classification

- **REQ-PROVIDER-008** — Each provider has exactly one sign-in method drawn from: device-code flow, browser authorization-code-with-PKCE flow, or API key. The mapping is: `copilot` → device code; `codex` → PKCE; `concrete-cloud` → PKCE (OIDC); `deepseek` → API key; `claude-code` → pasted subscription token (API-key style); user-defined OpenAI-compatible instances → API key.

- **REQ-PROVIDER-009** — The legacy id `geraet-cloud` is accepted as an alias for `concrete-cloud`; the canonical id remains `concrete-cloud`. For an id outside the fixed mapping, sign-in resolution succeeds (as API-key style) only when the stored credential is tagged with the provider family "openai-compatible"; otherwise the id is unknown and a warning "Unknown auth provider: <id>" is logged. Querying the sign-in method for such an unknown id yields none.

- **REQ-PROVIDER-010** — A credential-status query answers with exactly one value out of the vocabulary `authenticated`, `unauthenticated`, `expired`, `refreshing`. Only the first three are ever returned: no credential state, clock reading, or concurrent operation makes a query answer `refreshing`. A status query sends no network traffic — with every provider host unreachable it returns the value it would have returned with connectivity — and its answer is fixed by the stored credential (REQ-PROVIDER-011) and the current system time alone, so two queries against the same stored credential at the same clock reading agree.

- **REQ-PROVIDER-011** — A stored credential comprises: an access token, a refresh token, an expiry expressed as a Unix timestamp where `0` means "no expiry" (API keys never expire), an optional account id, and a string-to-string extras map. A credential is expired when the current time is at or past the expiry timestamp, unless the expiry is `0`.

- **REQ-PROVIDER-012** — An interactive sign-in that needs the user to act shows one of two prompts. A device-code prompt shows the verification URI, the user code, the polling interval, and how long the code stays valid. A browser (PKCE) prompt shows the authorization URL to open. Every authentication attempt ends in exactly one outcome: success, or failure carrying a message that is shown to the user and recorded as that provider's last error (REQ-PROVIDER-057).

- **REQ-PROVIDER-013** — An authentication attempt issued by a caller that cannot itself wait for the result must reach an outcome within 30 seconds; once that deadline passes the attempt is reported as failed and no credential is written. When such an attempt fails before any provider has been contacted, the failure result is the only output: no traceback, warning, or other diagnostic reaches stdout, stderr, or the log.

### Credential Persistence — Location, Format, Protection

- **REQ-PROVIDER-014** — Credentials are stored one JSON file per provider at `<per-user data directory for application "rotaris">/tokens/<provider_id>.json` (on Linux: `~/.local/share/rotaris/tokens/`). The credential directory is never located inside a workspace or repository.

- **REQ-PROVIDER-015** — Legacy directory adoption: per-user config/data directories (and the per-workspace state directory `.rotaris` versus the legacy `.geraet-ai`) created under the product's previous name "geraet-ai" are adopted by renaming the legacy directory onto the new path exactly once, and only while the new path is still absent. Should that rename raise, the product keeps reading and writing the legacy location instead of failing. Credentials minted before the rename therefore remain usable.

- **REQ-PROVIDER-016** — On POSIX systems the credential directory is created with mode `0700` and every credential file with mode `0600`: no group or other bit is ever set on either. On Windows no POSIX mode bits are set and none are reported; credential files there carry only the ACLs inherited from the user profile directory (Open Question 4).

- **REQ-PROVIDER-017** — The credential file is a JSON object with keys `access_token`, `refresh_token`, `expires_at`, `account_id`, and `extra` (an object of strings), serialized with 2-space indentation. Loading tolerates a missing `expires_at` (defaults to 0.0), missing `account_id`, and missing `extra`. A corrupt or key-missing file logs a warning that names the provider id but never the file contents, and is treated as no credential (unauthenticated).

- **REQ-PROVIDER-018** — Credential writes are atomic: a reader of `<provider_id>.json` sees either the previous content or the complete new content, never a partial or truncated file, and a write that fails leaves the previous file untouched. The new content is staged in a temporary file inside the credential directory whose name starts with the provider id and ends in `.tmp`, carries mode `0600` on POSIX, and is renamed onto `<provider_id>.json`; a failed write deletes that temporary file and reports the error. Once any credential operation has finished, whether it succeeded or failed, the credential directory holds nothing but `<provider_id>.json` files.

- **REQ-PROVIDER-019** — Deleting a stored credential removes the file if present and logs "Deleted stored tokens for <id>". A credential-existence check is a pure file-existence test. Enumerating stored provider ids returns the sorted basenames (without extension) of `*.json` files in the credential directory.

### GitHub Copilot Sign-In (Device Code + Session Exchange)

- **REQ-PROVIDER-020** — Copilot sign-in uses the OAuth Device Flow (RFC 8628) against `https://github.com/login/device/code` and `https://github.com/login/oauth/access_token` with the fixed client id `Iv1.b507a08c87ecfe98`. No `scope` parameter is sent.

- **REQ-PROVIDER-021** — Device-code request and poll requests carry headers `Accept: application/json`, `User-Agent: GithubCopilot/0.28.0`, `Editor-Version: vscode/1.99.1`, `Editor-Plugin-Version: copilot-chat/0.28.0`, with a 30-second HTTP timeout.

- **REQ-PROVIDER-022** — The user prompt presents the server's verification URI, user code, poll interval, and prompt lifetime; when the server omits the lifetime it defaults to 900 seconds.

- **REQ-PROVIDER-023** — Polling semantics: sleep `interval + 3.0` seconds per cycle. On `authorization_pending`, continue. On `slow_down`, adopt the server's new interval when it is a positive integer, otherwise add 5 seconds to the current interval. Any other error code fails the flow with that error string. A non-200 poll response fails with "Token poll HTTP <status>". A triggered cancellation signal aborts with error "Cancelled by user".

- **REQ-PROVIDER-024** — The device flow must yield a GitHub App user token prefixed `ghu_`. Any other prefix is rejected immediately with an error stating the prefix seen and that the client id is probably not a GitHub App. Stored legacy `gho_`-prefixed tokens (from earlier builds) classify as unauthenticated, forcing the user back through the device flow.

- **REQ-PROVIDER-025** — Immediately after the device flow the `ghu_` token is traded for a short-lived bearer scoped to Copilot's model API: `GET https://api.github.com/copilot_internal/v2/token`, header `Authorization: token <ghu_ token>`, 15-second timeout. The response supplies the bearer, its expiry as a Unix timestamp, the API base host to use for that account's tenant (it differs between individual and business/enterprise accounts), and an optional SKU string. The expiry stored is always the one the response gives; no fixed bearer lifetime is assumed anywhere, and the credential counts as expired 60 seconds ahead of it (REQ-PROVIDER-027). HTTP 401 and HTTP 404 are both authorization failures — 404 is the status returned both for a legacy `gho_`-prefixed token and for an account with no Copilot entitlement. Every other status, and any body that is not JSON, is a transient error. When no bearer can be obtained, sign-in fails with "Copilot session exchange failed: <detail>".

- **REQ-PROVIDER-026** — The persisted Copilot credential layout: access token = session bearer; refresh token = the durable `ghu_` token from the device flow; expiry = bearer expiry; extras record the tenant API base under key `api_base` and optionally the SKU under key `sku`.

- **REQ-PROVIDER-027** — Copilot status classification: empty access token → unauthenticated; a refresh token present but not `ghu_`-prefixed → unauthenticated (forces re-auth); expiry ≤ 0 → expired (a session bearer always carries an expiry, so its absence is treated as unusable); within 60 seconds of expiry → expired; otherwise authenticated. Non-interactive refresh puts the stored `ghu_` token back through the session exchange of REQ-PROVIDER-025 to obtain a new bearer and expiry; a missing or non-`ghu_` refresh token fails with "Stored token cannot be refreshed; re-authentication required".

### OpenAI Codex Sign-In (Authorization Code + PKCE)

- **REQ-PROVIDER-028** — Codex sign-in uses browser PKCE against issuer `https://auth.openai.com` with client id `app_EMoamEEZ73f0CkXaXp7hrann`. The authorization URL carries: `response_type=code`, the client id, the redirect URI, scopes `openid profile email offline_access api.connectors.read api.connectors.invoke`, an S256 PKCE challenge whose verifier is 43 characters drawn from the RFC 7636 unreserved set, `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, a 32-byte URL-safe random state, and `originator=codex_cli_rs`.

- **REQ-PROVIDER-029** — The local callback server binds `127.0.0.1` on fixed port 1455, falling back to 1457; only these two fixed ports are used, never a dynamically assigned one. If both ports are busy, authentication fails with an error telling the user to free those ports. The callback path is `/auth/callback`.

- **REQ-PROVIDER-030** — Callback handling: requests to other paths receive HTTP 404. An `error` query parameter fails the flow with the error description (or the error code) and renders an HTML page "Authentication Failed / You can close this tab." A missing `code` renders "Error / No code received." Success renders "Success! / You can close this tab." and captures the code. A state mismatch is treated as CSRF: it is logged and the flow yields no code.

- **REQ-PROVIDER-031** — The flow waits at most 300 seconds for the callback. A cancellation request ends the wait with "Cancelled by user"; expiry of the 300 seconds ends it with "Authentication timed out", or with the error the callback recorded when there is one. However the wait ends — code received, cancelled, or timed out — the loopback listener is closed and its port released before the sign-in call returns, on every supported operating system: the call always returns rather than hanging, and a sign-in started immediately afterwards binds port 1455 (or 1457) successfully.

- **REQ-PROVIDER-032** — Code exchange POSTs `grant_type=authorization_code` together with the PKCE verifier to `<issuer>/oauth/token` with a 30-second timeout. Any response other than HTTP 200 fails with "Token exchange HTTP <status>". On success the token lifetime comes from the response and is 3600 seconds when the response omits it. The account id is taken from the JWT claims of the id token first and of the access token second, using the first of these that is present: a top-level `chatgpt_account_id` claim; `chatgpt_account_id` inside the `https://api.openai.com/auth` claim object; the first entry of an `organizations` claim list. When none of them yields a value, sign-in still succeeds and the credential is stored without an account id, which later requests then omit (REQ-PROVIDER-076, REQ-PROVIDER-124). Extras record `auth_mode="chatgpt"`, `requested_scopes` (the scope string that was requested), and `scope` (the granted scope string) whenever the response returns one.

- **REQ-PROVIDER-033** — Codex refresh POSTs `grant_type=refresh_token`. Failures yield "Token refresh failed: HTTP <status>" or "Refresh request failed: <exc>". Success keeps the previous refresh token when the response omits one, and re-derives the account id.

- **REQ-PROVIDER-034** — Codex credential status: an empty access token reads unauthenticated; a credential whose expiry has passed reads expired; any other stored credential reads authenticated. The scopes a credential was granted never affect this answer — a credential granted fewer scopes than were requested still reads authenticated, and no request is refused locally on scope grounds (Open Question 12).

- **REQ-PROVIDER-035** — A token-exchange operation (RFC 8693) trades a stored id token for an API key beginning `sk-`, requesting the OpenAI API-key token type. When the exchange is refused with error `invalid_subject_token` and a message naming a missing `organization_id`, the message reported to the user instead tells them to select or create an organization and then run `rotaris-cli login codex --reauth`. Every other refusal renders as "API key exchange HTTP <status>: <message>", with the response body cut to its first 500 characters. (Open Question 13 records what invokes this exchange and where its result is kept.)

- **REQ-PROVIDER-036** — Sign-in surfaces brand the codex provider "(Sign in with ChatGPT)": the display label becomes "OpenAI Codex (Sign in with ChatGPT)", and when the PKCE prompt carries no user code, the prompt message is "Sign in with ChatGPT to authenticate Codex."

### Rotaris Cloud Sign-In (OIDC PKCE, Coming-Soon Gating)

- **REQ-PROVIDER-037** — Rotaris Cloud sign-in uses OIDC Authorization Code + PKCE with public client id `rotaris-ai`. The issuer comes from environment variable `ROTARIS_OIDC_ISSUER` (trailing slash stripped); the API base comes from environment variable `ROTARIS_API_BASE_URL`, defaulting to `https://rotaris.ai/v1`. When the issuer variable is unset, authentication fails with "ROTARIS_OIDC_ISSUER must be configured for Rotaris Cloud login".

- **REQ-PROVIDER-038** — OIDC discovery performs `GET <issuer>/.well-known/openid-configuration` with a 30-second timeout. The response must be JSON; its `issuer` must equal the configured issuer exactly (else "OIDC discovery issuer did not match configured issuer"); and it must supply `authorization_endpoint`, `token_endpoint`, and `revocation_endpoint` (else "OIDC discovery omitted a required endpoint").

- **REQ-PROVIDER-039** — Unlike codex, the cloud loopback callback binds an ephemeral port on `127.0.0.1` with path `/callback`, and the flow itself opens the system default browser in addition to delivering the URL through the prompt callback. Callback wait timeout is 300 seconds. The success page reads "Success! You can close this tab and return to the terminal."

- **REQ-PROVIDER-040** — Token exchange and refresh both target the discovered token endpoint with the public client id and no client secret. The stored credential's extras record `issuer`, `token_endpoint`, `revocation_endpoint`, and `api_base` so refresh and revocation work without re-discovery. A stored credential missing this endpoint metadata refuses to refresh with "Stored OIDC token endpoint is missing" / "Stored OIDC metadata is incomplete". When the token response omits a lifetime, the default is 900 seconds.

- **REQ-PROVIDER-041** — Sign-out for `concrete-cloud` (and its alias) first attempts best-effort remote revocation: a POST of the refresh token with `token_type_hint=refresh_token` to the stored revocation endpoint, 10-second timeout. Any revocation failure is logged at debug level and never blocks local credential deletion.

- **REQ-PROVIDER-042** — CLI coming-soon gating: the provider menu lists Rotaris Cloud suffixed " — Coming soon"; explicitly selecting it (or passing it as an argument) fails before any authentication with the catalog's unavailability reason ("Rotaris Cloud is coming soon."), reported as a failed sign-in.

- **REQ-PROVIDER-043** — Desktop coming-soon gating: both the provider health check and the authenticate action short-circuit for the unavailable cloud provider, returning provider status "coming_soon" with availability false and the unavailability reason as detail. The desktop "Add provider" dialog also excludes the cloud provider (and the generic openai-compatible family) from its built-in list.

### Claude Code Subscription Provider (Pasted Token, Local Runtime)

- **REQ-PROVIDER-044** — The `claude-code` provider mints no token of its own. Whenever the credential subsystem asks that provider to authenticate — which is every caller other than the `rotaris-cli login claude-code` command of REQ-PROVIDER-046 — the attempt fails with a message telling the user to run `claude setup-token` and then `rotaris-cli login claude-code` to paste the resulting subscription token. Its refresh step makes no external call: it succeeds and returns the stored token when one is stored, and fails when none is.

- **REQ-PROVIDER-045** — Subscription-token validation: an empty token → "Subscription token is required. Run 'claude setup-token' to mint one."; the token must be a legal ASCII header value (see REQ-PROVIDER-062); a token starting `sk-ant-api` is rejected with an explanation that it is an Anthropic API key and would bill the API rather than the subscription; anything not starting `sk-ant-oat` is rejected with "Expected a subscription OAuth token starting with 'sk-ant-oat' (minted by 'claude setup-token')." Status classification reuses this validation — an invalid stored token reads as unauthenticated.

- **REQ-PROVIDER-046** — `rotaris-cli login claude-code` is the one path that stores a subscription token, and it takes that token from the user rather than from the provider's authenticate step (REQ-PROVIDER-044). It prints numbered setup instructions — install and sign in to the external Claude Code tool, run `claude setup-token`, paste the `sk-ant-oat` token it prints — and states that the token is kept locally with owner-only file permissions (mode `0600` where the platform has them, REQ-PROVIDER-016) and is never written to workspace files, logs, or session snapshots. It then prompts for the token with the input hidden under the label "Claude Code subscription token (sk-ant-oat...)", applies the validation of REQ-PROVIDER-045, and runs offline model discovery (REQ-PROVIDER-047).

- **REQ-PROVIDER-047** — Claude-code model discovery is static and offline: after token validation it returns a fixed catalog of exactly three version-independent aliases — `opus` ("Claude Opus (subscription)"), `sonnet` ("Claude Sonnet (subscription)"), `haiku` ("Claude Haiku (subscription)") — with qualified ids `claude-code/<alias>`, no network call, and no HTTP status.

- **REQ-PROVIDER-048** — Conflicting-credential precheck: the presence of any of the environment variables `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, or an `apiKeyHelper` entry in `~/.claude/settings.json`, outranks the subscription token in the external tool's own credential chain; if any is present, the subscription runtime refuses to run with a credential-conflict error naming the conflicting sources and suggesting remediation (e.g. `unset ANTHROPIC_API_KEY`, remove apiKeyHelper). This check runs before every subscription-runtime prompt.

- **REQ-PROVIDER-049** — The subscription runtime injects the stored token as environment variable `CLAUDE_CODE_OAUTH_TOKEN` for the external local-runtime subprocess. Default per-model concurrency: maximum 2 parallel requests for provider `claude-code` and 3 for `deepseek`; unlimited for other providers — all unless explicitly configured by the user.

### DeepSeek and OpenAI-Compatible Endpoints (API Keys, Labelled Instances)

- **REQ-PROVIDER-050** — DeepSeek is a plain API-key provider: its interactive authenticate step always fails with "This provider uses a stored API key. Run 'rotaris-cli login deepseek' to create or update it."; status is authenticated if and only if a key is stored. Sign-in prompts with hidden input "DeepSeek API key", validates by discovery against the DeepSeek catalog endpoint, and persists the key only AFTER discovery succeeds with at least one model.

- **REQ-PROVIDER-051** — OpenAI-compatible endpoints are user-defined, labelled instances with ids `openai-compatible--<slug>`, where the slug is the label lowercased with every run of non-alphanumeric characters collapsed to a single `-` and trimmed. A label that normalizes to nothing is rejected with "Label must contain at least one letter or number." Multiple instances are supported simultaneously.

- **REQ-PROVIDER-052** — CLI sign-in for an OpenAI-compatible instance prompts: "OpenAI-compatible label" (required), "Endpoint URL" defaulting to `https://api.openai.com/v1`, and a hidden required "API key". If an instance with the derived id already has credentials or a catalog-snapshot entry and re-auth was not requested, the user must confirm "Replace the existing provider instance '<label>'?" (default No), otherwise the sign-in returns "cancelled". Discovery must succeed with at least one model before the key is persisted. On success the credential extras record `provider_family` = "openai-compatible" and `api_base` = the normalized URL.

- **REQ-PROVIDER-053** — Base-URL normalization: trims whitespace and trailing slashes; an empty URL → "API base URL must not be empty."; the URL must include a scheme and hostname (else "API base URL must include a scheme and hostname."); a path ending in `/models` is trimmed off, so pasting the models endpoint itself works. The models endpoint is then `<base>/models`.

- **REQ-PROVIDER-054** — Programmatic instance registration validates label/URL/key; rejects a duplicate id with "Provider <id> already exists; re-authenticate the existing endpoint."; runs discovery with the API key redacted as `[redacted]` in any error text; fails on zero discovered models with "no models discovered."; saves the credential; persists the discovered models; and on a snapshot-write failure rolls back by deleting the just-saved credential and reports "Could not save provider <id>: <error>". The success message is "Added <label>; discovered N model(s)."

- **REQ-PROVIDER-055** — Instance deletion: only ids matching the `openai-compatible--` prefix are deletable ("Provider <id> is built-in or not user-defined."); an unknown instance yields "Unknown user-defined provider: <id>."; otherwise deletion removes the snapshot entry and the credential and reports "Deleted user-defined provider <id>." along with flags stating whether credentials and/or the snapshot entry were removed. Workspace model references are deliberately NOT rewritten.

- **REQ-PROVIDER-056** — CLI deletion surface: `rotaris-cli providers delete <provider> [--yes/-y]`. Without `--yes`, an interactive confirmation "Delete <id> user-wide? Workspace model references will not be changed." (default No) is required; declining prints "Deletion cancelled." Failure exits with code 2 and the message on stderr. The headless frontend additionally refuses non-interactive deletion without `--yes`: "Error: non-interactive provider deletion requires --yes" (exit 2).

### Credential Lifecycle (Get, Renew, Sign-Out, Errors)

- **REQ-PROVIDER-057** — Fetching a usable token for a provider: load the stored credential; if status is authenticated, return the access token as-is; if expired, attempt a silent refresh — on success, persist the credential, re-stage any external bridge artifacts (REQ-PROVIDER-063), and return the new token; on refresh failure, log "Token refresh failed for <id>, re-authenticating" and fall through. Without an interaction callback, the fall-through records the per-provider last error "Authentication required" and returns nothing; with a callback, the full interactive sign-in runs and the credential is persisted on success. Every failure path records a retrievable per-provider last error; every success clears it.

- **REQ-PROVIDER-058** — An unconditional renew operation refreshes a stored credential even when it is still valid (so a credential does not expire part-way through a run); when the provider cannot refresh without user interaction, renew returns nothing and records the reason as the last error.

- **REQ-PROVIDER-059** — A non-blocking status query classifies a provider without performing network I/O; an unknown provider or absent credential classifies as unauthenticated. The asynchronous status check yields the same classification.

- **REQ-PROVIDER-060** — Sign-out for a provider deletes the stored credential and forgets any cached in-process provider state and last error; for `codex` it additionally deletes the staged external-runtime bridge credential, best-effort with a warning on failure.

- **REQ-PROVIDER-061** — Saving a credential also rewrites that provider's external bridge artifacts, and they are on disk before the save call returns: a `codex` credential is mirrored into the secondary credential store the external agent runtime reads, recorded under the vendor key "openai" with its expiry expressed in milliseconds; a `copilot` credential is staged into the workspace-scoped gateway files of REQ-PROVIDER-063 whenever a workspace root is known, and is skipped without error when none is. A failure to write either artifact — including the empty-token failure of REQ-PROVIDER-065 — is logged as a warning and never turns a successful credential save into a failed one; the missing artifact then surfaces as an authentication error on the next model call.

### Credential Bridges and Key Hygiene

- **REQ-PROVIDER-062** — API-key header validation: a key must be pure ASCII ("API key must contain ASCII characters only. Re-enter its exact value.") and contain no control characters (0x00–0x1F, 0x7F) ("API key must not contain control characters. Re-enter its exact value."). This applies to pasted keys and to tokens used for API-key-provider discovery.

- **REQ-PROVIDER-063** — Copilot gateway staging publishes two files in a staging directory beneath the workspace's `.rotaris/` state directory (Open Question 14). Each is written so that a reader sees either the previous content or the complete new content and never a partial file, and each is on disk before the staging call reports success. The files are `access-token`, plain text holding the durable `ghu_` token, or the session bearer when no refresh token is stored; and `api-key.json`, compact JSON of the form `{"token": <bearer>, "expires_at": <int>, "endpoints": {"api": <base>}, "sku"?: <string>}`. When no API base is stored for the account, the value written for `endpoints.api` is `https://api.githubcopilot.com`. Because the durable token is published here, nothing that reads these files ever has to start a second device-code flow.

- **REQ-PROVIDER-064** — Gateway environment contract: the environment variable `GITHUB_COPILOT_TOKEN_DIR` is set to the workspace's staging directory (pinned per workspace so concurrent application instances never share staged credentials), and `GITHUB_COPILOT_ACCESS_TOKEN` is defaulted (never overwritten if already set) to the sentinel value `managed-by-rotaris`, which signals that credential acquisition and refresh are performed by the application and must not be attempted by the consumer of these files.

- **REQ-PROVIDER-065** — Staging Copilot credentials with an empty access token fails with the error "Cannot stage Copilot tokens: access_token is empty", and neither staged file is created or overwritten. On the credential-save path that failure is absorbed as a warning per REQ-PROVIDER-061 and the credential save still succeeds.

### Run-Time Credential Priming and Transparent Refresh

- **REQ-PROVIDER-066** — The set of providers to prime for a run is the union of the sign-in providers behind all configured slot models and personas, plus the sign-in provider of every configured model. All of them are primed, regardless of which personas the run turns out to use.

- **REQ-PROVIDER-067** — A priming pass runs once at run start. For each provider: authenticated and not expiring within the refresh margin → counted as authenticated, and (for copilot) bridge files are re-staged; authenticated-but-expiring-soon or expired → an unconditional renew is performed rather than a plain token fetch, which would hand back a token that is still valid but close to expiry. Failures are collected into an unresolved map with reasons and logged as warnings — priming never fails the run. Constants: refresh margin 300.0 seconds (renew when within 5 minutes of expiry); poll interval 60.0 seconds.

- **REQ-PROVIDER-068** — A run is wrapped in a keep-fresh scope. Opening it yields the priming report of REQ-PROVIDER-067 — the providers found authenticated, the providers renewed, and the map of providers that could not be resolved with a reason for each — reported as ok exactly when that map is empty. For as long as the run lasts, a credential carrying an expiry is renewed before it lapses, with the check running at least once every 60 seconds. Credentials with no expiry (API keys) are never renewed on that schedule, and a credential that was already unresolved when the run started is not retried: it is reported once in the opening report instead of producing a warning at every check. A failure during a check is logged as a warning, the remaining providers are still checked, and refreshing continues until the run ends. No refresh happens after the run ends.

### Model Discovery (Catalog Sync)

- **REQ-PROVIDER-069** — Discovery dispatch: `codex` → the dedicated subscription discovery (REQ-PROVIDER-076); `claude-code` → the offline static catalog (REQ-PROVIDER-047); every other provider → HTTP GET of the provider's models endpoint with headers `Authorization: Bearer <token>` and `User-Agent: rotaris/discovery`, default timeout 10 seconds. For API-key provider families the token is header-validated (REQ-PROVIDER-062) before any request.

- **REQ-PROVIDER-070** — Copilot discovery adds the full editor-identity header set (`Copilot-Integration-Id: vscode-chat`, `Editor-Version`, `Editor-Plugin-Version`, `OpenAI-Intent: conversation-panel`, `User-Agent`, `Accept: application/json`); the endpoint does not return a usable model list without them. When a tenant API base is stored from the session exchange, the discovery endpoint's scheme and host are swapped to it while the `/models` path is kept.

- **REQ-PROVIDER-071** — Discovery reports either a model list or an error, and an error that came from an HTTP response also reports that response's status code. The mapping is: a timeout or transport failure → "Discovery request failed: <exc>", no status; HTTP 401 or 403 → "Authentication failed for <display name>: <status>"; HTTP 500 or above → "Discovery request failed: <reason phrase, or `HTTP <status>` when the response supplies none>"; a body that does not parse as JSON → "Invalid response format: <exc>"; a payload that is not a JSON object → "Invalid response format: expected JSON object"; a payload whose `data` field is absent or is not a list → "Invalid response format: expected data list"; an entry of `data` that is not an object → "Invalid response format: expected model objects". A `data` list that is present and empty is not an error: discovery succeeds with zero models, which is the condition that opens the recovery menu of REQ-PROVIDER-097. (Open Question 15 records the unmapped 4xx statuses.)

- **REQ-PROVIDER-072** — Each discovered model captures: its id; a qualified id `<provider-or-instance id>/<id>`; an optional display name (payload `display_name`, falling back to `name`); a capabilities object; a limits object (payload `context_length` mapped into `context_window` when it is an integer); pricing only for `concrete-cloud` (decimal-string `prompt_usd_per_token` / `completion_usd_per_token` mapped to floating-point input/output cost per token, with negative or non-finite values rejected); and the raw payload item. Known token limits are injected when missing (REQ-PROVIDER-078 to 080).

- **REQ-PROVIDER-073** — Copilot catalog handling separates dropping from annotating. An entry that declares a capability type other than `chat` — an embeddings model, for example — is dropped and never appears in the catalog; an entry that declares no capability type is kept. Every kept entry is annotated and none is hidden: an entry the payload marks as switched off by account policy is recorded with availability code `policy_disabled` and the provider's policy terms text as its unavailability detail; an entry whose advertised endpoints yield no route the product can dispatch to (REQ-PROVIDER-074) is recorded `no_supported_route` and carries no detail; every other entry is recorded `available` together with the API mode chosen for it. An entry that omits the capability, policy, or endpoint fields is treated as available. (Open Question 16 records the exact payload key paths.)

- **REQ-PROVIDER-074** — Advertised Copilot endpoints are normalized before a route is chosen: each string is trimmed of surrounding whitespace; a string that is not a path — anything not starting with `/`, a websocket URL for instance — is discarded; a path that does not already start with a version segment of the form `/v<digits>` gets `/v1` prepended; repeated values are reduced to their first occurrence. The route follows from the normalized set: an empty set gives chat mode; otherwise the presence of `/v1/chat/completions` gives chat mode, and it wins when both endpoints are advertised; otherwise the presence of `/v1/responses` gives responses mode; otherwise the model has no supported route (REQ-PROVIDER-073).

- **REQ-PROVIDER-075** — The model availability vocabulary is `available`, `policy_disabled`, `no_supported_route`; an absent or empty code means available. Each non-available code renders as exactly one actionable sentence — `policy_disabled`: "Your provider account has this model switched off. Enable it in the provider's settings, then refresh the model catalog."; `no_supported_route`: "The provider offers this model only on an endpoint Rotaris cannot send requests to."; any code outside the vocabulary: "The provider will not accept requests for this model." The provider's own detail text follows that sentence, separated by a single space and ending in exactly one sentence-terminating character, and is left out when it is empty or when it repeats the sentence.

- **REQ-PROVIDER-076** — Codex subscription discovery: `GET https://chatgpt.com/backend-api/codex/models?client_version=0.144.6` with headers `Authorization: Bearer <token>`, `originator: codex_cli_rs`, `OpenAI-Beta: responses=experimental`, `User-Agent: rotaris/discovery`, and `chatgpt-account-id: <account id>` when an account id is stored. Payload items must carry a non-empty string `slug` (else "Invalid response format: expected model slug"); entries with `supported_in_api == false` or `visibility == "hide"` are skipped. Captured capabilities: reasoning levels (from `supported_reasoning_levels`) and input modalities; limits: `context_window`, falling back to `max_context_window`. The 401/403, ≥500, and format error semantics match generic discovery.

- **REQ-PROVIDER-077** — Hosted-cloud slot suggestions: after a successful `concrete-cloud` discovery, a second best-effort `GET <base>/model-suggestions` is parsed for roles `small`, `medium`, `large`, `fallback`; each suggested id is qualified with the provider prefix and kept only if it names a model that was actually discovered. Any error or shape problem yields no suggestions.

### Known Token Limits and Normalization

- **REQ-PROVIDER-078** — Canonical limit extraction reads the payload's limit fields in a fixed key order and takes the first acceptable value it finds, skipping keys that are absent or hold an unacceptable value. Input-limit key order: `context_tokens`, `max_input_tokens`, `context_window`, `max_context_window_tokens`, `max_context_tokens`, `context_length`, `max_prompt_tokens`, `input_tokens`, `token_limit`, `max_tokens`. Output-limit key order: `output_tokens`, `max_output_tokens`, `max_completion_tokens`. A value is acceptable when it is a positive integer (a boolean never qualifies, whatever its numeric value), a positive float with no fractional part, or a string of digits optionally grouped with `_` or `,` that parses to a positive integer. Zero, negative, and non-integral values are unacceptable and the search continues past them; when no key yields an acceptable value that limit is absent.

- **REQ-PROVIDER-079** — The build carries a table of known (input, output) token-limit pairs keyed `provider/model`, covering the OpenAI, Anthropic, and DeepSeek model families (Open Question 17), together with one provider-wide entry `deepseek/` whose pair is (1,048,576, 384,000). A lookup tries, in order: the qualified id as written; then the id with recognized trailing suffixes removed one at a time — `-latest`, `-YYYY-MM-DD`, `-YYYYMMDD`, and a DeepSeek four-digit release suffix — each successively shortened form being tried as it is produced; then the provider-wide entry for that provider. For lookup purposes `codex` and `copilot` are read as `openai`, and an `openai-compatible--<slug>` instance is tried under its own id first and under the bare `openai-compatible` prefix second. A model that matches nothing yields no known limits.

- **REQ-PROVIDER-080** — Known-limit application fills gaps only: if discovery already produced both limits, they are returned untouched; otherwise the input/output values from the known table are injected when resolvable.

### Automatic Slot Selection from a Discovered Catalog

- **REQ-PROVIDER-081** — Automatic tier assignment fills the large, medium, and small picks from a provider's discovered models, in that order, matching case-insensitively against the model id and yielding qualified ids. The build carries a fixed ordered preference per tier over model-family name fragments, with a secondary fallback list consulted when no preferred fragment matches (Open Question 18), and the same catalog always produces the same three picks. The observable invariants are: an id containing `mini` or `nano` is never chosen as the large pick; the medium pick is never the model already chosen as large; the small pick is never one of the two already chosen; and any tier is left empty when nothing matches, with REQ-PROVIDER-082 deciding how that gap is closed.

- **REQ-PROVIDER-082** — Only models recorded as available (REQ-PROVIDER-075) may be assigned to a slot; unavailable models are still written to the snapshot but never fill one. Gaps in the tier picks of REQ-PROVIDER-081 are closed in a fixed order: `large_model` takes the large pick, else the medium pick, else the small pick; `medium_model` takes the medium pick, else the small pick, else the large pick; `small_model` takes the small pick, else the medium pick, else the large pick; `default_summary_model` takes the medium pick, else the small pick, else the large pick. A slot still empty after that takes a single deterministic choice from the provider's available models — the same model for every such slot, and the same model on every run over an unchanged catalog (Open Question 19). Where the hosted provider returned server-side suggestions (REQ-PROVIDER-077), the suggestion for a role replaces the pick for that role. `fallback_model` takes the `fallback` suggestion when one was returned and otherwise the small pick; when neither exists the field is left unset and the default of REQ-PROVIDER-088 applies.

- **REQ-PROVIDER-083** — The persisted snapshot's model list is ordered with the picked (small/medium/large) models first, then the rest sorted by qualified id. Previously known models that a refresh did not re-discover are PRESERVED (sorted, appended) rather than dropped, and counted separately. Every model row records a shared ISO-8601 UTC discovery timestamp.

### Provider/Model Snapshot Persistence (On-Disk Catalog)

- **REQ-PROVIDER-084** — The discovered-provider catalog persists as a YAML file `project_settings.yaml` in the per-user config directory for application "rotaris" (e.g. `~/.config/rotaris/project_settings.yaml`). The document has `version: 1` (any other version is rejected with "unsupported project snapshot version") and a `providers` map of id → provider record; unknown keys are rejected. A provider record has: id, display name, optional family, optional base URL, an authenticated flag, a list of model records, per-slot fields `default_summary_model`, `large_model`, `medium_model`, `small_model`, `fallback_model`, and a discovery timestamp that must be ISO-8601 with a UTC offset. A model record has: id, optional display name, capabilities, limits, pricing, and its discovery timestamp. Duplicate model ids keep the first occurrence and log a warning.

- **REQ-PROVIDER-085** — A snapshot write is atomic: a concurrent reader sees either the previous document or the complete new one and never a partial file, and a write that fails leaves the previous document intact. The file carries mode `0644`. Its YAML is emitted with mapping keys in the order they were written rather than sorted, and with non-ASCII characters written literally rather than escaped. Two reads of a snapshot with no write in between return equal results. A snapshot that cannot be parsed, or that violates REQ-PROVIDER-084, fails the read with "Invalid project snapshot at <path>: <detail>".

- **REQ-PROVIDER-086** — Every snapshot write is preceded by a scan of the whole payload, and the write is refused when anything secret-like is found. A mapping key counts as secret-like when its lower-cased form contains `api_key`, `access_token`, `refresh_token`, or `ghu_`, or when splitting that lower-cased form on non-alphanumeric characters produces any of the words `auth`, `authorization`, `token`, `secret`, `password`, `apikey`, `bearer`, `credential`, `session`. A string value counts as secret-like when — compared case-insensitively, and after discarding one leading `Bearer ` prefix — it begins with `ghp_`, `ghs_`, `ghu_`, `gho_`, `sk-`, `sk_`, `iv1.`, or `eyj`. A refused write leaves the existing file untouched and reports "Refusing to write snapshot: secret-like field detected: <path>", where `<path>` locates the offending field within the document. The keys `input_cost_per_token` and `output_cost_per_token` inside a model's pricing block are the only exception.

- **REQ-PROVIDER-087** — The snapshot supports upserting one provider record (creating the file when absent) and removing one provider record (reporting whether anything was removed).

### Configuration: Model Slots, Routing Fields, Snapshot Merge

- **REQ-PROVIDER-088** — The root configuration exposes seven named capability slots: `small_model`, `medium_model`, `large_model`, `fallback_model`, `default_summary_model`, `improvement_collector_model`, `gatekeeper_model`. These seven are the editable "startup model" fields written by guided assignment (REQ-PROVIDER-100) and the startup-models editor (REQ-PROVIDER-112). Wherever a persona or a nested configuration section names one of the literal slot names in place of a model, that name is replaced by the slot's value while configuration is being loaded, so no alias reaches a run (Open Question 21 covers an alias whose slot has no value). Resolution of an unset slot, taking the first listed source that has a value: `fallback_model` ← `small_model`; `default_summary_model` ← the literal `gpt-5-mini`; `improvement_collector_model` ← `medium_model`; `gatekeeper_model` ← `small_model`, then `default_summary_model`, then `fallback_model`. `fallback_model` is the model substituted whenever the primary choice for a call cannot be used. Every slot has a sibling field `<slot>_thinking` accepting `auto`, `low`, `medium`, `high`, or `max`; leaving it unset means the provider or endpoint decides the level (Open Question 20 covers `auto`).

- **REQ-PROVIDER-089** — Per-model configuration fields relevant to routing: provider, model id, optional API key / API-key environment-variable name / base URL, an optional sign-in provider reference (when set, credentials come from the credential subsystem instead of static keys), an API mode ("chat" | "responses" | unset — filled by discovery, user-overridable), a switch to disable the responses API, maximum input/output token limits, a per-model timeout (unset → the global runtime model timeout), a retry count (unset → default 5), sampling parameters, optional explicit pricing (both input and output values must be set to take effect), a thinking level (legacy booleans are coerced: true → "high", false → unset), and a maximum-parallel-requests value (defaults per REQ-PROVIDER-049).

- **REQ-PROVIDER-090** — Unavailable models are kept in a separate configuration map from usable models, carrying id, display name, sign-in provider, availability reason code, the resolved reason sentence, and the provider's detail text. No code path can construct a model client from an unavailable entry, while pickers can still display the row with its reason.

- **REQ-PROVIDER-091** — Configuration loading merges the snapshot into the effective configuration: each authenticated snapshot provider's slot picks seed the root slots; each snapshot model becomes a configured model entry keyed by qualified id, whose provider family is `deepseek` or `claude-code` for those families and the generic OpenAI-compatible dialect otherwise, whose model id is the qualified id with the provider prefix stripped, whose sign-in provider is the provider id, whose base URL comes from the snapshot or the catalog default, with limits, API mode, and pricing carried through from discovery. A user-authored YAML entry with a complete provider and model id overrides the snapshot entry of the same name. Models marked unavailable in the catalog land in the unavailable-models map UNLESS the user explicitly named them in YAML (then they stay configured). An invalid snapshot is ignored with a warning "Ignoring project settings snapshot: ...".

- **REQ-PROVIDER-092** — A configured model that names a sign-in provider is dispatched with a credential taken from the credential store rather than any static key, and an expired credential is renewed before the request leaves, so no request carries a credential the store already knows to be expired. Copilot requests carry the editor-identity headers of REQ-PROVIDER-070 and use the staged workspace credentials of REQ-PROVIDER-063. A Copilot model discovered as responses-only is invocable: its requests go to the responses endpoint, the limits discovery recorded for it apply, and it reports no pricing (both per-token costs read as zero). A codex model's requests authenticate with the stored subscription credential.

### CLI: Sign-In Command

- **REQ-PROVIDER-093** — Two parallel CLI frontends (an interactive one and a headless one) expose the identical sign-in surface: `rotaris-cli login [PROVIDER] [--reauth] [--workspace/-w PATH]`. With no PROVIDER argument, an interactive provider menu is shown. Ctrl-C prints "Cancelled." and exits with code 1. Sign-in success/failure controls the exit code (0/1).

- **REQ-PROVIDER-094** — The provider menu lists all six catalog providers in catalog order, with labels adjusted: codex branded "(Sign in with ChatGPT)"; unavailable providers suffixed " — Coming soon". In a real TTY, an ANSI arrow-key selector is used (title line "(Use Up/Down, Enter to confirm, Esc to cancel)", wrap-around navigation, Enter confirms, Esc/Ctrl-C/Ctrl-D cancels, cursor hidden, an animated `>>` / `> ` selection prefix); otherwise a numbered fallback prompt appears ("Provider number"; empty or invalid input cancels). Cancelling yields a sign-in result with message "cancelled". An unknown provider argument errors "Unknown provider: <id>" and fails.

- **REQ-PROVIDER-095** — Before it contacts any provider, `rotaris-cli login` creates the per-user configuration directory for the application when that directory is absent (`$HOME/.config/rotaris` on Linux and macOS whenever `HOME` is set). A failure to create it does not stop sign-in: the command emits the warning "Failed to create global config directory: <error>" and carries on.

- **REQ-PROVIDER-096** — OAuth-provider sign-in sequence: check status → if re-auth was requested, discard stored authentication first (info message "Discarded stored authentication for <name>.") and force re-authentication → if already authenticated (and not re-auth) skip with "Using stored authentication for <name>."; otherwise run interactive authentication with the prompt callback. Device-code prompts print an emphasized message plus "URL:" and "Code:" lines (or plain text in the headless frontend); PKCE prompts print the message plus "If your browser did not open, visit: <url>". Authentication failure prints the provider error and returns failure.

- **REQ-PROVIDER-097** — After authentication, models are discovered, with recovery. A discovery error ends sign-in in failure with "Model discovery failed for <name>: <error>". Discovery that succeeds with zero models opens a recovery menu: "No models were discovered. Choose recovery: 1) retry 2) try other provider 3) advanced config 4) abort", where empty or unrecognized input is taken as 4. Option 1 may be taken twice; from the third time onward it is refused with "Model discovery retry limit reached." and the same menu is presented again. Option 2 restarts sign-in from the provider menu of REQ-PROVIDER-094. Option 3, also selected by answering "continue", writes a minimal `.rotaris/agents.yaml` when none exists, opens that file in the user's editor and waits for the editor to exit (Open Question 22), validates the workspace configuration, prints any validation errors, and ends sign-in with the message "manual config required". Option 4 ends sign-in with "Model discovery aborted".

- **REQ-PROVIDER-098** — Post-refresh credential hygiene: when discovery fails with HTTP 401/403, the stored authentication is discarded ("Discarded stored authentication for <name>.") EXCEPT for `codex`, whose stored credential survives a refused catalog read, so a later attempt does not force a fresh sign-in.

- **REQ-PROVIDER-099** — On successful discovery, the models are persisted to the snapshot (using the stored API base for the base URL) and sign-in finishes with "Login complete for <name>; discovered N model(s)." A minimal `.rotaris/agents.yaml` (default persona `orchestrator`) is bootstrapped when absent, and the bootstrap is reported. The user is then offered "Open advanced config in your editor?" (default No); accepting opens the file, validates, and reports errors ("manual config required" on failure). Post-sign-in configuration validation warnings are prefixed "Post-login config warning:".

- **REQ-PROVIDER-100** — The OpenAI-compatible sign-in additionally offers guided slot assignment: "Configure startup model assignments now?" (default Yes) walks all seven slot fields with "Select <field>" pickers whose choices are the authenticated snapshot models plus models declared in global/workspace YAML, labelled "<provider display>: <model label> [<id>]"; each is followed by a thinking-level picker ("Select <slot> thinking (0 disables)") only when the chosen model supports reasoning levels. Then "Configure persona-specific model overrides now?" (default No) walks each persona with 0 = inherit/default. Results are written to `.rotaris/agents.yaml`. Slot defaults shown are the pre-sign-in values (captured before the new provider was persisted).

### CLI: Sign-Out, Provider Management, Catalog Refresh

- **REQ-PROVIDER-101** — Sign-out surfaces: `rotaris-cli logout [PROVIDER]` (both frontends) and `rotaris-cli run --logout <PROVIDER>` (both frontends). The `--logout` help text states that the flag signs out of a provider and exits, gives worked example ids (`copilot`, `codex`, `openai-compatible--my-label`), and says stored credentials are cleared while provider configuration is retained; the `logout` subcommand's provider-argument help adds that omitting the argument selects interactively. With no provider argument in an interactive terminal, a selector titled "Choose provider to sign out of:" lists only those providers holding a stored credential at that moment, labelled with catalog display names, or "<snapshot display name> [<id>]" for user-defined instances, or the bare id. Non-interactive without an argument → "Provider is required when interactive selection is unavailable." (exit 1); zero credentialed providers → "No providers are available for logout." (exit 1); Esc → "Logout cancelled." (exit 1).

- **REQ-PROVIDER-102** — Sign-out core semantics: the target id is trimmed and lowercased; valid targets are the built-in catalog ids (minus the generic `openai-compatible` family id) plus any `openai-compatible--*` instance that has credentials or a snapshot entry. Unknown targets fail with "Unknown provider: '<id>'. Known providers: <sorted list>. OpenAI-compatible instances use ids like 'openai-compatible--my-label'." (exit code 2). Outcomes: credentials existed → "Signed out of <id>." (informational, exit 0); no credentials → "No stored tokens for <id>; nothing to do." (warning, exit 0); an OS error during deletion → "Logout failed for <id>: <exc>" (exit 1). Signing out never removes the provider's snapshot or configuration entry.

- **REQ-PROVIDER-103** — `rotaris-cli providers list` prints one line per provider: `<id>: <display name> (<flow>, authenticated|not authenticated[, key=<mask>][, base_url=<url>])`. `<flow>` names that provider's sign-in method (Open Question 23); `key=<mask>` appears only when a key is stored for the provider, masked per REQ-PROVIDER-107; `base_url=<url>` appears only when a base URL is stored or defaulted for it. The providers printed are the union of the ids holding a stored credential, the built-in catalog ids, and the snapshot ids, each printed once, ordered by id.

- **REQ-PROVIDER-104** — `rotaris-cli providers set-key <provider> [--api-key K] [--no-validate]`: prompts with hidden input when the flag is omitted; validates by discovery unless `--no-validate`; non-API-key providers are refused with "<name> uses <flow>; use reauth instead."; success prints "Updated API key for <name>."; failures exit non-zero.

- **REQ-PROVIDER-105** — `rotaris-cli providers set-base-url <provider> <url> [--no-validate]`: normalizes and validates the URL, re-discovers against the new base when a key exists, updates both the stored credential's `api_base` extra and the snapshot's base URL; success prints "Updated base URL for <name>."

- **REQ-PROVIDER-106** — `rotaris-cli providers validate [PROVIDER]` is an alias for the catalog refresh flow (REQ-PROVIDER-109); `rotaris-cli providers reauth <provider>` runs the sign-in flow with re-auth forced; `rotaris-cli providers delete` behaves per REQ-PROVIDER-056.

- **REQ-PROVIDER-107** — Secret masking for display: values of 4 characters or fewer render as `****`; longer values render as the first 2 characters + `****` + the last 2 (e.g. `sk****10`). This mask is the ONLY user-interface representation of a stored key.

- **REQ-PROVIDER-108** — API-key update semantics behind those commands: the key is stripped and validated; the provider must use the API-key flow; the previous credential extras are preserved and extended (forcing the provider-family and API-base extras for OpenAI-compatible instances); when validating, the key is refused storage on a discovery error ("Validation failed for <name>: ...") or zero models ("... no models discovered."). Provider validation requires stored credentials ("<name> is not authenticated."), re-runs discovery, persists models on success, and reports "Validated <name>; discovered N model(s)."

- **REQ-PROVIDER-109** — Catalog re-sync without re-authentication: `rotaris-cli models refresh [--provider ID] [--workspace/-w PATH]`. Bulk mode (no --provider) targets all catalog and snapshot providers, silently skipping unauthenticated ones; targeting a specific unauthenticated provider reports "Skipped <name>: not authenticated. Run 'rotaris-cli login <id>' first." and counts as a failure. An unknown target: "Unknown provider: <id>. Known providers: <list>." Per-provider progress prints "Refreshing models for <name>...", success "Refreshed <name>; discovered N model(s)[, preserved M previous model(s)]." The closing summary is a comma-joined list of the non-zero counts — "<X> provider succeeded" / "<X> providers succeeded" (singular only at exactly 1), "<Y> failed", "<Z> skipped (not authenticated)" — with a zero count leaving its clause out entirely. That list is prefixed "Refresh complete: " when nothing failed and nothing was bulk-skipped, and "Refresh finished: " otherwise; either way it ends in a period. The skipped count reports bulk-mode skips only, never an explicitly targeted unauthenticated provider (that one is already counted as a failure). The exit code is non-zero when any targeted provider failed or was skipped-by-target.

- **REQ-PROVIDER-110** — Startup recovery: when configuration loading fails with messages of the form "Model '<x>' ... is incomplete: missing required ... 'model_id'/'provider'", the CLI automatically runs a non-interactive bulk model refresh first (warning: "Detected incomplete provider model overrides. Refreshing authenticated provider models...") and retries the load. Both CLI frontends exhibit this recovery.

### Terminal-UI Surfaces

- **REQ-PROVIDER-111** — Provider Settings modal: title "Provider Settings"; a selector over the same set of providers that `rotaris-cli providers list` prints (REQ-PROVIDER-103), each labelled "<display name> [<id>]"; a status line "<display name>: <flow>, key <mask|not set>", where `<flow>` is the label of Open Question 23 and the mask is the one of REQ-PROVIDER-107; a password-masked API-key input with placeholder "leave blank to keep current key", disabled whenever the selected provider's flow is not API key; a Base URL input; and a hint line "Ctrl+S save  |  v validate  |  r reauth  |  esc close". Unset slots display "unset"; persona rows display "default (<default> -> <resolved>)" for inherited values and "<alias> -> <resolved|unconfigured>" for tier-alias picks; the thinking column shows the level or "provider / endpoint default". Changing a model re-derives that row's legal thinking choices from the shipped model-capability metadata and resets an invalid thinking value to the default. Save writes `.rotaris/agents.yaml` and dismisses with the saved path; a write failure notifies "Unable to save startup models: <exc>". An onboarding variant retitles the screen "Review Your Model Assignments" with save-and-continue copy.

- **REQ-PROVIDER-113** — The rich model picker sub-screen carries a header line reporting authentication across the provider catalog: "✓  All providers authenticated" when every catalog provider is authenticated, otherwise one "⚠  <name> not authenticated — <hint>" entry per provider that is not, where the hint is `` `rotaris-cli login <id>` `` and, for copilot, `` `gh auth login --web` `` (Open Question 24). Its title is "Model Picker · Enter/click to confirm · R to refresh · Esc to cancel". A picker opened for a persona shows fixed rows ahead of the model rows: "(inherit default[: <default> → <resolved>])", then one row per tier alias — `small_model`, `medium_model`, `large_model` — rendered "<alias> → <resolved>" with source "alias", and "<alias> → unconfigured" when that slot has no value. The picker ends with the summary "Loaded N runtime model(s)" followed by any per-provider errors, or with "No runtime models available" when no row was produced. `R` re-fetches the live catalogs, discarding only the rows they contributed and leaving the fixed rows in place.

Desktop sign-out has the same effect as CLI sign-out (REQ-PROVIDER-102).

- **REQ-PROVIDER-119** — Desktop subscription usage display: the Overview shows live subscription usage windows for each of {codex, copilot, claude-code} that appears as the sign-in provider (or provider) of any configured model. Fetches run concurrently (one worker per provider) so startup waits at most one provider timeout. Failure or missing authentication degrades to a fixed placeholder row per provider, each carrying a label, the used-label "Usage unavailable", a used percentage of 0, and a remediation detail: codex → "Codex usage" / "Sign in to Codex or retry when OpenAI usage data is available."; copilot → "Copilot plan allowance" / "Sign in to Copilot or retry when GitHub usage data is available."; claude-code → "Claude Code usage" / "Run 'claude setup-token' and sign in again, or retry when Anthropic usage data is available." - **REQ-PROVIDER-120** — The Rotaris Cloud credit tile carries the card title "Rotaris Cloud credit" and has five renderings. Loading: value "…", tag "Checking…", detail "Reading your Rotaris Cloud balance.", refresh disabled; this rendering appears only when no balance has been shown yet — once a balance is on screen it stays on screen through every later read until a new value replaces it. Ready: the balance followed by "left", a tag naming the credit state returned by the backend, one of available, exhausted, overdrafted, unknown (REQ-PROVIDER-130, Open Question 26), and a detail line of either "last call <amount>" or "No billed calls yet."; when the payload's admission-allowed flag is false the tile additionally shows the warning "! Which rendering is showing must be readable from the tag text and the outline shape alone: colour is never the only carrier of that distinction.

- **REQ-PROVIDER-121** — The credit balance is read once when the window opens, again every 120,000 ms (2 minutes) for as long as the window stays open, and whenever the user asks for a refresh. At most one read is outstanding at a time: a refresh asked for while a read is still running is declined and starts nothing, so no two reads overlap and no request is duplicated. The window stays responsive while a read is in progress. Amounts are computed and rendered in exact decimal arithmetic, never in binary floating point: a balance is rounded down (toward negative infinity), every other amount is rounded half-up, both to 2 decimal places, or to 4 when the magnitude is below $0.01. The currencies USD, EUR, and GBP render with the symbols $, €, £; any other currency renders as "<amount> <CODE>".

- **REQ-PROVIDER-122** — Cloud-billing awareness is active when ANY of the small/medium/large slots, the active model, or the session model override resolves to a model whose sign-in provider is `concrete-cloud` (a delegating run's children spend the same balance). The desktop tracks a temporary session model override distinct from the persistent slots; the desktop composer command `/model <name>` sets it. (Exact runtime application of the override belongs to the run-orchestration domain.)

### Subscription Usage Endpoints and Rendering

- **REQ-PROVIDER-123** — Subscription-usage fetching supports exactly the providers codex, copilot, and claude-code; any other provider yields an empty result. The default HTTP client uses a 5-second timeout and follows redirects. All failures raise a dedicated usage error type; callers degrade to placeholders and nothing is retried at this layer.

- **REQ-PROVIDER-124** — Codex usage: `GET https://chatgpt.com/backend-api/wham/usage` with the OAuth bearer, `User-Agent: codex-cli`, and a `ChatGPT-Account-Id` header when an account id is stored. The payload's primary and secondary rate-limit windows are read in that order; a window that is absent, or whose used-percent value is missing, non-numeric, boolean, or not finite, is skipped rather than failing the whole read; a usable percent is clamped into 0–100 and rounded to an integer (Open Question 27). Labels resolve by the window's declared length in seconds: 18,000 → "Codex 5-hour window"; 604,800 → "Codex weekly window". When the length is absent or matches neither value, the window keeps the label its position implies — "Codex 5-hour window" for the primary window and "Codex weekly window" for the secondary one. Rendering: the used label is "<n>% used"; the detail is "<100−n>% remaining[ · resets <relative>]" where the reset comes from an absolute reset timestamp or a reset-after-seconds value. No usable windows → errors "Codex usage response contains no rate-limit windows" / "... no usable windows".

- **REQ-PROVIDER-125** — Copilot usage: `GET https://api.github.com/copilot_internal/user` authenticated with the stored GitHub `ghu_` token (the credential's refresh-token field; the short-lived model bearer minted by the session exchange is not accepted here, so it is never sent — a missing `ghu_` token errors "Copilot GitHub token is unavailable"), with headers `User-Agent: GithubCopilot/0.28.0` and `Copilot-Integration-Id: vscode-chat`. The quota snapshot with id "premium_interactions" is selected. The label is "Copilot AI credits" when the account is on token-based billing (Open Question 28) and "Copilot premium requests" otherwise. A quota flagged unlimited renders as a single row labelled "Unlimited" with 0% used and the detail "No plan allowance cap". Otherwise both an entitlement and a remaining-quota value must be present, and their absence fails the read with "Copilot plan allowance is incomplete". The used label is "<used> / <entitlement>[ credits]", where used = entitlement − remaining and both numbers are written with thousands separators and without trailing fractional zeros. The used percent is 100 minus the payload's reported remaining percent when it reports one, and otherwise (entitlement − remaining) ÷ entitlement × 100; either way it is clamped into 0–100 and rounded to an integer (Open Question 27). The detail is "<n>% remaining[ · resets <Mon D>][ · <n> overage]", where the reset date comes from the UTC quota-reset-date field when present and from the plain one otherwise, and the overage clause appears only for a non-zero overage count.

- **REQ-PROVIDER-126** — Claude Code usage: `GET https://api.anthropic.com/api/oauth/usage` with the subscription OAuth bearer plus headers `anthropic-beta: oauth-2025-04-20` and `anthropic-version: 2023-06-01` (no API key involved; not billed against the API). Windows: `five_hour` → "Claude Code 5-hour window"; `seven_day` → "Claude Code 7-day window"; each carries a utilization percent and an ISO-8601 reset timestamp; rendering matches codex ("<n>% used", "<m>% remaining · resets <relative>"). No usable windows → "Claude Code usage response contains no usable windows".

- **REQ-PROVIDER-127** — Reset-label formats: under 60 seconds → "in <1m"; then "in Xd[ Yh]", "in Xh[ Ym]", "in Xm". Calendar reset labels render "<Mon> <day>" (e.g. "Feb 3"). Percentages clamp to 0–100. Numeric parsing accepts integers, floats, and comma-grouped numeric strings; booleans are rejected.

### Rotaris Cloud Account Credit

- **REQ-PROVIDER-128** — Credit reads perform `GET <api_base>/account/usage-status`, where the API base comes from the stored credential's `api_base` extra, falling back to the catalog default so credentials from before the field existed still work; an unusable stored base errors "Rotaris Cloud API base is unusable: <base>". Headers: the bearer plus `User-Agent: rotaris/account`; timeout 5 seconds.

- **REQ-PROVIDER-129** — The blocking account-status read: with no stored cloud credential it fails with a DISTINCT sign-in-required error ("Not signed in to Rotaris Cloud") whose meaning is "sign in", not "retry". Before reading, it puts the stored credential through the standard token fetch so an access token whose lifetime elapsed during a long-running session is renewed rather than reported as a rejected credential; that step fails with the recorded authentication error or "Rotaris Cloud sign-in has expired". HTTP 401/403 → "Rotaris Cloud rejected the stored credential; sign in again."; other HTTP errors → "Rotaris Cloud account request failed (<status>)" / "... failed"; a non-object body → "... response is not an object".

- **REQ-PROVIDER-130** — Credit payload contract: a required credit object (missing → an error stating the response "carries no credit block") with an atomic balance and an atomic scale — balance = atomic ÷ scale computed in exact decimal arithmetic, never in binary floating point (a non-number → "Rotaris Cloud credit balance is not a number", a non-positive scale → "... scale is not positive"); a state mapping to available | exhausted | overdrafted with unknown values degrading to "unknown" (forward compatibility: a new backend state must not break installed clients); an admission-allowed boolean (default false); an optional currency code (upper-cased, default "USD"); and an optional latest-settled-usage record (ISO-8601 occurrence time, status, cost) — a partially unusable usage record is dropped rather than failing the whole reading, so the balance still renders.

### Cross-Cutting Invariants

- **REQ-PROVIDER-131** — No credential value is readable in a log file, in user-visible error text, in a snapshot, in an event stream, or in a hook payload. One shared set of redaction rules covers all of them — the event stream has no rules of its own — and it replaces every substring matching a known credential shape wherever it occurs in text: GitHub tokens (`ghp_`, `ghs_`, `ghu_`, `gho_`), API keys (`sk-`, `sk_`), and JWT-shaped values (`eyJ...`). Open Question 29 records what the replacement text is. Hook payloads additionally redact any value held under a secret-named key, using the key test of REQ-PROVIDER-086. The masked form of REQ-PROVIDER-107 is the only rendering of a stored key that any user interface shows.

- **REQ-PROVIDER-132** — Health issues for configured providers are summarized uniformly: an API-key-flow provider missing credentials → "<name> is missing an API key." (flagged as editable); an expired credential → "<name> authentication is expired."; otherwise "<name> is not authenticated."

- **REQ-PROVIDER-133** — Ordering invariant: for key-based providers, credentials are persisted only AFTER successful validation/discovery (sign-in, validated key update, programmatic registration), so a bad key is never stored silently — with the explicit exceptions of `--no-validate` on the set-key/set-base-url commands and the desktop's raw key-save path (which performs header validation only).

- **REQ-PROVIDER-134** — Ordering invariant: on-disk bridge artifacts are rewritten as part of every credential save and are on disk before that save returns, so an external consumer reading them can never observe an older credential than the store holds. Run-start priming also rewrites the bridge for a credential it found valid and did not renew, because that workspace may never have had the files written at all.

- **REQ-PROVIDER-135** — The generic `openai-compatible` catalog id is a template/family, never a credentialed provider itself: sign-out targets, the desktop add-provider list, and instance ids all exclude it; only `openai-compatible--<label>` instances hold credentials.

- **REQ-PROVIDER-136** — Static custom provider/model declarations in configuration (a `models.yml`-style declaration file) remain supported alongside discovery; ordinary onboarding does not need them. YAML-declared models with a complete provider and model id always override snapshot entries of the same name.

- **REQ-PROVIDER-137** — Thinking/reasoning levels shown for a model come from the model-capability metadata the product ships with: a model supports levels only when a reasoning-effort parameter is a supported parameter for it; the UI level set is (low, medium, high, max) minus levels the metadata disclaims (a disclaimed low removes "low"; a disclaimed extra-high removes "max"); the "max" level corresponds to the metadata's extra-high reasoning effort. Unknown or custom models expose no levels, and the thinking column collapses to the provider default.

- **REQ-PROVIDER-138** — The `run` subcommand refuses to mix sign-out with a task: `--logout` short-circuits before any configuration load and exits with the sign-out result, in both CLI frontends.

- **REQ-PROVIDER-139** — Exit-code contract (headless frontend, mirrored by the interactive frontend): login 0 success / 1 failure; logout 0 success or no-op, 1 selection/OS failure, 2 unknown provider; providers delete 0 success or cancelled, 2 failure or non-interactive without `--yes`; models refresh 0 when every targeted provider refreshed, 1 otherwise.

## Data & Formats

All formats below are externally observable (on disk, on the wire, or in process environments) and are normative.

### Stored credential file (per provider)

Path: `<per-user data dir for "rotaris">/tokens/<provider_id>.json`. JSON object, 2-space indented:

```json
{
  "access_token": "<string>",
  "refresh_token": "<string>",
  "expires_at": 0.0,
  "account_id": null,
  "extra": { "<string>": "<string>" }
}
```

- `expires_at` is a Unix timestamp; `0` means no expiry. Missing `expires_at`/`account_id`/`extra` are tolerated on load.
- Well-known extras keys: `api_base` (tenant or instance API base), `sku` (Copilot), `provider_family` ("openai-compatible" for instances), `auth_mode`/`requested_scopes`/`scope` (codex), `issuer`/`token_endpoint`/`revocation_endpoint` (hosted cloud OIDC).

### Provider/model snapshot

Path: `<per-user config dir for "rotaris">/project_settings.yaml`. YAML, keys unsorted, Unicode allowed, file mode 0644, atomic writes, unknown keys rejected:

```yaml
version: 1
providers:
  <provider-id>:
    id: <provider-id>
    display_name: <string>
    family: <string, optional>
    base_url: <string, optional>
    authenticated: <bool>
    default_summary_model: <qualified id, optional>
    large_model: <qualified id, optional>
    medium_model: <qualified id, optional>
    small_model: <qualified id, optional>
    fallback_model: <qualified id, optional>
    discovered_at: <ISO-8601 with UTC offset>
    models:
      - id: <qualified id>
        display_name: <string, optional>
        capabilities: { ... }
        limits: { context_window: <int>, ... }
        pricing: { input_cost_per_token: <float>, output_cost_per_token: <float> }
        discovered_at: <ISO-8601 with UTC offset>
```

Secret-like keys or values abort the write (REQ-PROVIDER-086); the pricing cost fields are the only whitelisted exception.

### Identifiers

- Qualified model id: `<provider-or-instance id>/<model id>` (e.g. `claude-code/sonnet`, `openai-compatible--my-lab/gpt-4o`).
- OpenAI-compatible instance id: `openai-compatible--<slug>`; slug = label lowercased, non-alphanumeric runs collapsed to `-`, trimmed, non-empty.

### Copilot gateway staging files

Per-workspace staging directory under the workspace's `.rotaris/` state directory, published via environment variable `GITHUB_COPILOT_TOKEN_DIR`:

- `access-token` — plain text; the durable `ghu_` token from the device flow (or the session bearer when no refresh token exists).
- `api-key.json` — compact JSON: `{"token": "<bearer>", "expires_at": <int unix ts>, "endpoints": {"api": "<base url>"}, "sku": "<string, optional>"}`.

Environment: `GITHUB_COPILOT_ACCESS_TOKEN` is defaulted (never overwritten) to the sentinel `managed-by-rotaris`. The subscription runtime for claude-code receives the stored token as `CLAUDE_CODE_OAUTH_TOKEN`.

### Discovery response (consumed contract)

Generic providers: a JSON object with a `data` list of model objects, each with `id` and optional `display_name`/`name`, capability and limit objects (including `context_length`), and — for the hosted cloud — decimal-string per-token prices (`prompt_usd_per_token`, `completion_usd_per_token`). Codex: a JSON object with a `models` list whose items carry `slug`, `supported_in_api`, `visibility`, `supported_reasoning_levels`, `input_modalities`, `context_window`/`max_context_window`. Hosted-cloud suggestions endpoint (`<base>/model-suggestions`): roles `small`, `medium`, `large`, `fallback` naming discovered model ids.

### Subscription usage payloads (consumed contracts)

- Codex (`.../wham/usage`): a `rate_limit` object holding `primary_window` and `secondary_window`, each with `used_percent`, `limit_window_seconds` (18,000 = 5-hour, 604,800 = weekly), and a reset timestamp or reset-after-seconds.
- Copilot (`.../copilot_internal/user`): quota snapshots; the `premium_interactions` snapshot with `unlimited`, entitlement, remaining quota, remaining percent, overage count, and a UTC quota reset date.
- Claude Code (`.../api/oauth/usage`): windows `five_hour` and `seven_day`, each `{utilization: <percent>, resets_at: <ISO-8601>}`.

### Cloud account credit payload (consumed contract)

`GET <api_base>/account/usage-status` returns a JSON object with: a required `credit` object carrying `balance_atomic` (number) and `atomic_scale` (positive number), a `state` string (available | exhausted | overdrafted; unknown values degrade to "unknown"), `admission_allowed` (boolean, default false), optional `currency` (upper-cased, default "USD"), and optional `latest_settled_usage` `{occurred_at: <ISO-8601>, status: <string>, cost_usd: <number>}`.

### Rendering formats

- Secret mask: `****` for values ≤ 4 chars; else first 2 + `****` + last 2.
- Money: exact decimal arithmetic; balances floored, other amounts rounded half-up; 2 decimal places (4 below $0.01 magnitude); $/€/£ symbols, otherwise `<amount> <CODE>`.
- Relative reset labels: "in <1m", "in Xd[ Yh]", "in Xh[ Ym]", "in Xm"; calendar labels "<Mon> <day>".
- Timestamps persisted in the snapshot are ISO-8601 with a UTC offset.

### Workspace bootstrap

A minimal `.rotaris/agents.yaml` (YAML; default persona `orchestrator`) is bootstrapped when absent during sign-in flows; guided slot assignment and the startup-models editor write the seven slot fields and per-persona overrides into the same file.

## Open Questions

1. Real-service behavior of remote sign-in, catalog, usage, and credit endpoints cannot be confirmed statically; the payload shapes above are stated as the contracts the product consumes.
2. Whether the fixed local loopback callback ports used by one browser sign-in flow remain accepted by the external identity service over time is unverifiable.
3. Whether the external consumer of the staged credential files and environment variables honors that contract cannot be verified without running it.
4. Effective credential-directory protection on Windows relies on inherited user-profile ACLs rather than explicit permission bits, and cannot be confirmed statically.
5. Cross-process concurrency behavior when multiple app instances mutate the shared credential store or provider catalog concurrently is undetermined; writes are atomic per file but there is no inter-process lock.
6. The precise runtime precedence of a temporary per-run model override versus persistent slot defaults inside a live run belongs to another domain and was not traced end-to-end here.
7. Behavior of the raw-mode keyboard selector on unusual terminals or over remote shells is untestable statically.
8. Which models real accounts actually discover, and therefore which concrete slot assignments the automatic tier picker produces in practice, depends on live provider catalogs.
9. The hosted account option's coming-soon state is a static flag in this build; whether and how it flips at runtime (e.g., via an update) could not be determined.
10. REQ-PROVIDER-005: the literal placeholder the `claude-code` catalog entry carries for its discovery endpoint and base URL is not fixed here. Is a specific sentinel string part of the contract, or only the guarantee that neither value is ever dialed?
11. REQ-PROVIDER-013: what message is reported when the 30-second authentication deadline expires? The requirement fixes the deadline and the outcome but not the text.
12. REQ-PROVIDER-034: should any granted-scope set be required for a codex credential to read as authenticated, or is the absence of a scope check the intended contract?
13. REQ-PROVIDER-035: what invokes the RFC 8693 id-token → `sk-` API-key exchange (which command or condition), and where does the resulting key go — stored as the codex credential, returned to the caller, or written somewhere else?
14. REQ-PROVIDER-063: what is the name of the staging subdirectory beneath the workspace `.rotaris/` state directory, and what file modes do `access-token` and `api-key.json` carry? External consumers locate the directory through `GITHUB_COPILOT_TOKEN_DIR`, so the name is part of the observable contract.
15. REQ-PROVIDER-071: HTTP statuses in the 4xx range other than 401 and 403 (404, 408, 429, …) have no mapped discovery message. Which text and which status do they produce?
16. REQ-PROVIDER-073: what are the exact payload key paths for a Copilot catalog entry's capability type, its policy state, and its policy terms text?
17. REQ-PROVIDER-079: the per-model rows of the known-token-limit table are not enumerated (only the `deepseek/` provider-wide pair is). Which model ids and (input, output) pairs must ship?
18. REQ-PROVIDER-081: is the exact ordered preference over model-family fragments normative, or only the stated invariants? Either way, how is a tie broken when several discovered models match the same preference rank?
19. REQ-PROVIDER-082: when no tier pick exists at all, which ordering defines the provider's "first available model" — qualified id ascending, discovery order, or something else?
20. REQ-PROVIDER-088 / REQ-PROVIDER-112 / REQ-PROVIDER-137: `auto` is accepted in the `<slot>_thinking` vocabulary but appears in no UI level set (low/medium/high/max) and in no displayed value (a level, or "provider / endpoint default"). Is `auto` distinct from unset, and should it stay accepted?
21. REQ-PROVIDER-088 / REQ-PROVIDER-113: a persona may be pointed at a tier alias whose slot has no value — the picker renders it "unconfigured". What does load-time alias resolution do in that case: fail the load, leave the persona unset, or fall back to `fallback_model`?
22. REQ-PROVIDER-097 / REQ-PROVIDER-099: how is "the user's editor" chosen (`$VISUAL`, `$EDITOR`, a platform default), and what happens when none is set?
23. REQ-PROVIDER-103 / REQ-PROVIDER-104 / REQ-PROVIDER-111: the `<flow>` label naming a provider's sign-in method appears in several user-visible strings but is never defined. What are the exact labels for the device-code, PKCE, and API-key flows?
24. REQ-PROVIDER-113 / REQ-PROVIDER-024 / REQ-PROVIDER-093: the model picker's unauthenticated hint for copilot is `` `gh auth login --web` ``, yet copilot credentials are minted by the product's own device flow and any stored token that is not `ghu_`-prefixed reads as unauthenticated. Which is canonical — the hint as written, or `rotaris-cli login copilot`?
