# Workspace Handling, Context Injection, and Project Onboarding — Initialization UI, Consent, and Run Gating (Desktop)

Part 4 of 7 of [domain 13](../13-workspace-context-onboarding.md), which indexes every part. Defines REQ-WORKSPACE-102 – REQ-WORKSPACE-132.

### Initialization UI, Consent, and Run Gating (Desktop)

- **REQ-WORKSPACE-102** — Initialization SHALL be resolved automatically exactly once per workspace open, and SHALL NOT begin before the window is on screen and accepting input, so that the window paints and answers input no matter how the resolution goes. A resolution that fails SHALL leave the window fully usable: the error surface SHALL read "Project setup could not be checked" / "Rotaris could not work out whether this workspace still needs setting up. Runs are not blocked; you can check again.", SHALL offer a "Check again" action, and the composer gate of REQ-WORKSPACE-112 SHALL stay off. Activating "Check again" SHALL resolve initialization once more, producing the outcomes of REQ-WORKSPACE-083 when it succeeds and this same error surface when it fails again; such a user-requested check is additional to, and does not consume, the one automatic resolution per workspace open.

- **REQ-WORKSPACE-103** — Background tasks SHALL start immediately, without any dialog and without blocking the interface; nothing renders their progress live; the recorded outcome is visible in Settings Project. Success is silent. No estimate of how long such a task will take, no completion percentage, no progress bar, and no elapsed-time reading SHALL be presented for a background task while it runs: a task the user did not ask for and cannot be blocked by has nothing to report until it has a result. Its only timing contract is the per-stage wall-clock budgets of REQ-WORKSPACE-091, a stage exceeding its budget being a retryable failure. A failed background run SHALL reach an error banner "Project setup did not finish" carrying the task's own summary (fallback "Rotaris could not finish setting this workspace up for code search.") and a "Try again" action; a run that broke down entirely additionally states "Runs are not blocked; you can try again."

- **REQ-WORKSPACE-104** — With the current default task set, a fresh workspace SHALL open without any prompt and without gating runs. The consent dialog and the composer gate SHALL appear only once some pending task requires consent, and SHALL then behave exactly as specified above without further configuration.

- **REQ-WORKSPACE-105** — The initialization state the user interface works from SHALL comprise exactly these nine values: the pending tasks; those pending tasks that require consent; the completed tasks; the skipped tasks; the classification; whether the workspace has never been initialized; the last-run timestamp; whether a run is in progress; and the last error. The setup prompt SHALL be due exactly when at least one consent-requiring task is pending and no run is in progress. Recomputing the state SHALL be idempotent as far as the user can tell: when every one of those nine values comes out equal to the value already on display, nothing visible SHALL change — in particular a configuration reload SHALL NOT reopen a dialog the user has already answered — and the dialog SHALL be opened automatically at most once per workspace open. Task ids SHALL be shown as display labels: `code-intelligence-setup` displays as "Code intelligence project setup" (REQ-WORKSPACE-088), and any other id displays as itself. An id read back from persisted state that matches no currently registered task SHALL be treated as requiring no consent. Two such states SHALL be equal exactly when all nine values are equal, the four task-id collections comparing as **sets** — order within a list SHALL NOT be significant, because that order is the order outcomes happened to be recorded in and carries no meaning the user can see, so a state re-read in a different order SHALL NOT count as a change — while the classification, the never-initialized flag, the last-run timestamp, the in-progress flag, and the last error compare by value, two absent values being equal and an absent value never equal to a present one.

- **REQ-WORKSPACE-106** — The consent dialog SHALL be a non-modal, window-level dialog (the rest of the app stays navigable) titled "Set up this project" with headline "Set up this project?" (or "Nothing to set up") and intro "{n} one-time setup task(s) can run in this workspace. They run once; you can skip them and start any time from Settings › Project." (or "This workspace has no setup task left to run."). Each task renders a card with its label, a live status word (Pending/Running/Done/Skipped/Failed), and its description. Buttons: "Skip for now" (secondary; description "Defer these tasks. You can run them later from Settings › Project.") and "Initialize project" (primary and default; description "Run every listed task now. Each one reports its own result below."). The dialog has four states: prompt → running → done | error.

- **REQ-WORKSPACE-107** — Every dialog exit path SHALL yield an explicit decision: dismissing with Escape, or with the window's own close control, SHALL resolve as a skip. When the underlying prompt request disappears while an auto-opened dialog is still unanswered, the window SHALL close it without recording a skip; a dialog the user opened manually SHALL never be auto-closed.

- **REQ-WORKSPACE-108** — In the running state both buttons SHALL lock with availability reasons (e.g. "Setup is running. It reports each step as it finishes."); a monospace progress log appears seeded with "Setup started. Each step appears here as it finishes." and the status line reads "Setting up this project. This can take a few minutes." Per task the log shows a "▶ {label}" heading, then per step an indented line `{✓|–|✕|•} {name} — {status}[: detail]` (detail rendered verbatim), then a task-outcome line. Done state: headline "Project setup finished", status "Setup finished. The results are listed above.", and a Close button leaving the report readable. Error state: headline "Project setup did not finish", the failure message, and a primary "Retry initialization" button (description "Run the tasks that failed again. Nothing was recorded, so none of them are skipped."); the decision is reopened so closing now records a skip rather than swallowing the tasks.

- **REQ-WORKSPACE-109** — A run's progress SHALL become visible while the run is still under way, not only once it has ended: a task SHALL be announced under its display label as it starts; each of its steps SHALL be shown — name, status, and detail — at the moment that step finishes, rather than being withheld until the task ends; and the task's own outcome SHALL follow its steps. A run SHALL end in exactly one of three ways: with every attempted task's result reported; with the run as a whole reported as having failed, in which case nothing is recorded for any task; or with the run reported as cancelled. Once cancellation has been requested, no task that has not yet started SHALL begin, while a task already under way SHALL be allowed to reach its own conclusion, save that the processes it started are ended as REQ-WORKSPACE-092 requires. Closing the application while a run is under way SHALL raise no dialog and SHALL complete within 5000 ms, the run being stopped by force if it has not ended by then.

- **REQ-WORKSPACE-110** — Pressing Initialize while a run is already live SHALL start nothing and flip the dialog to its in-progress state. Starting a run SHALL re-read the runnable task list, so that following a run that only partly succeeded a retry offers just the outstanding tasks; when nothing remains the dialog says "Everything in this workspace is already set up." When any listed task requires consent and no model is reachable (no active model or no connected provider), the run SHALL refuse up front with "This setup step runs an agent, so it needs a model provider. Authenticate one in Settings, then start it again." and the banner "Project setup needs a provider" — failing fast instead of starting and then surfacing a raw authentication error.

- **REQ-WORKSPACE-111** — The skip path SHALL persist the listed task ids as skipped; a persistence failure keeps the dialog open with "Your choice could not be saved: {exc}". Once skipped, reopening the workspace SHALL never re-prompt.

- **REQ-WORKSPACE-112** — While the setup prompt is unanswered, the composer's Send control SHALL be disabled with the reason "Answer the project setup prompt first. Initialize or skip it in the setup window; nothing else in Rotaris is blocked." The keyboard submit path SHALL be caught separately with error "Project setup is unanswered" / "Initialize this workspace or skip its setup before starting a run." and an "Open project setup" action. This is a composer gate only — no other view is blocked.

- **REQ-WORKSPACE-113** — Manual re-initialization SHALL be exposed in exactly two places — the Workspace sidebar's "Project" section and Settings Project — both opening the same dialog, which lists every runnable task, previously skipped ones included; it SHALL never trigger automatically. Sidebar states: everything resolved or nothing applicable → the section is hidden; pending/skipped → button "Initialize Project…" with hint "Not run yet: {labels}."; running → disabled "Initializing…" with hint "Running the pending setup tasks."; a recorded failure appends "Last run failed: {message}" to the hint.

- **REQ-WORKSPACE-114** — The Settings Project card "Project initialization" SHALL render exactly one of six states at a time:
  - *failed* — a run recorded an error and no run is in progress: headline "Initialization failed"; detail = that error message followed by "Nothing was recorded, so {labels} can be run again."; button "Retry initialization".
  - *running* — a run is in progress: headline "Initializing project…"; an indeterminate progress bar; a disabled "Initializing…" button.
  - *pending* — at least one applicable task is pending: headline "Initialization pending"; detail "Not run yet: {labels}."
  - *deferred* — at least one applicable task is skipped and none is pending: headline "Initialization deferred"; detail "You skipped {labels}. Run them whenever you want.", preceded by "Completed: {labels} on {YYYY-MM-DD}." when at least one task has completed, the date being the date part of the recorded `last_run`.
  - *completed* — every applicable task is completed: headline "Project initialized"; a completed sentence whose wording is left to the implementation and which SHALL convey exactly that every initialization task applying to this workspace has been completed and on what date, that date being the date part of the recorded `last_run`; followed by the classification sentence of REQ-WORKSPACE-101; the button disabled with reason "Every initialization task for this workspace is already resolved."
  - *empty* — no task is applicable to this workspace: headline "Nothing to initialize yet"; detail "No initialization task applies to this workspace. A task appears here once the tool it depends on is configured — add it under MCP Servers and reload the workspace."; the button disabled.

  The six conditions SHALL be evaluated in this fixed order and the first whose condition holds SHALL be the state rendered: *running*, *failed*, *pending*, *deferred*, *completed*, *empty*. What is in flight outranks what has already happened, an unresolved failure outranks work still merely owed, and work still owed outranks work the user deferred, so the card always shows the thing that most needs the user's attention and never has to choose between two conditions arbitrarily.

- **REQ-WORKSPACE-115** — Refreshing the initialization display SHALL show the values the persisted `initialization:` section holds at that moment — its completed list, its skipped list, `last_run`, and `classification` — so that an edit made to that section on disk becomes visible once a refresh has run. A refresh SHALL change nothing else: settings edited but not yet saved SHALL still be there afterwards, and no configuration value outside the `initialization:` section SHALL take a different value because a refresh happened, whether or not the file on disk has been edited since that value was loaded. Whether a run is in progress, and the last error, describe the current session only and SHALL NOT be taken from disk: after a restart the display SHALL show no run in progress and no last error. A refresh SHALL NOT block the interface — the window SHALL keep accepting input for as long as it runs — and the refreshed values SHALL be on screen within 100 ms of the refresh being requested, measured from the user's activation where the user asked for it.

### Workspace Hook Trust Gate

- **REQ-WORKSPACE-116** — Hook execution SHALL be gated as REQ-HOOKS-090 requires — on declared provenance, never on an inspection of what a command does — over the scope vocabulary REQ-HOOKS-020 fixes; this domain restates neither the gate's rules nor that vocabulary. Why this domain depends on it: hooks declared by the workspace arrive with the cloned repository and can therefore run code chosen by someone other than the user, so opening a checkout is never on its own consent to run what it declares, and an unrecognized origin is never treated as safe.

- **REQ-WORKSPACE-117** — The verdict key SHALL be the workspace hook fingerprint of REQ-HOOKS-091, which is the product's single definition of it. This domain holds no copy of the digest algorithm, of the canonical document it is taken over, of the fields that document carries, of the resolved-value rule, or of what does and does not change the digest. What this domain relies on that fingerprint for is that a stored verdict is keyed by it, so a verdict covers exactly the workspace hook set it was recorded against and nothing else.

- **REQ-WORKSPACE-118** — The verdict SHALL persist in the trust decision file of REQ-HOOKS-096, whose path, keys, serialization and write obligations that requirement fixes and this domain does not restate; revoking a verdict follows the decision lifecycle of REQ-HOOKS-093. What this domain relies on is that the verdict lives inside the workspace state directory this domain owns (`<workspace>/.rotaris/`, REQ-WORKSPACE-034), so it travels with the checkout it describes, and that a failed write or a failed revocation is reported rather than absorbed.

- **REQ-WORKSPACE-119** — Reading a stored verdict SHALL follow REQ-HOOKS-094, which fixes every condition that reads as "no verdict" and the strictness applied to each stored field; this domain restates none of them. What this domain relies on is that the reader fails closed and never raises, so an unreadable or foreign `<workspace>/.rotaris/` leaves the workspace unapproved rather than failing the launch.

- **REQ-WORKSPACE-120** — When a trust review is pending, and what the pending review carries, are fixed by REQ-HOOKS-092, and the durability of a recorded refusal by REQ-HOOKS-093; this domain restates neither. What this domain relies on is that opening a workspace never puts the question to the user again while its declared hook set is unchanged, so switching between two checkouts is not a stream of prompts.

- **REQ-WORKSPACE-121** — Partitioning hooks into allowed and blocked is the trust gate of REQ-HOOKS-090 applied to the in-memory resolved set on the terms of REQ-HOOKS-097, which this domain cites and does not restate. What this domain relies on is that the set that was fingerprinted is the set that runs, with no reload between the two, so a workspace file rewritten between the check and the call cannot smuggle a command past the review.

- **REQ-WORKSPACE-122** — When workspace hooks were blocked, the notice is the one REQ-HOOKS-101 fixes, whose text and singular-and-plural forms this domain does not restate, and what may and may not be disclosed about a withheld hook is fixed by REQ-HOOKS-102. What this domain relies on is that a name or command line authored by the repository reaches no notice, toast, transcript or other surface, and that the complete listing appears only inside the review dialog the user opens on purpose.

- **REQ-WORKSPACE-123** — *Withdrawn.* The per-invocation configuration override this described was itself withdrawn with REQ-WORKSPACE-003, so no hook can arrive by that route; the only origin scopes that run without review remain `default` and `global` (REQ-WORKSPACE-116).

- **REQ-WORKSPACE-124** — The hook-model facts the digest and the review surfaces of this domain depend on are stated in the lifecycle-hooks specification and are cited here rather than restated: the hook event vocabulary and its division into blocking-capable tool events and informational lifecycle events (REQ-HOOKS-001, REQ-HOOKS-002); the entry field set with its types and defaults, the default per-hook budget among them (REQ-HOOKS-008); the cap on retained hook output (REQ-HOOKS-037); the failure allowance after which a hook is switched off for the rest of the session (REQ-HOOKS-055); the feature-level `hooks.enabled` control (REQ-HOOKS-009, REQ-HOOKS-017); the rule that a disabled entry keeps its position so the identities of the entries around it do not shift (REQ-HOOKS-018); and matcher evaluation, including what an empty matcher selects and when the tool name is matched instead (REQ-HOOKS-022, REQ-HOOKS-025, REQ-HOOKS-027). This domain holds no copy of any of them, and a figure or a member added to any of those sets is added there rather than here.

### Hook Scope Fallback — Declining Preserves the User's Own Hooks

- **REQ-WORKSPACE-125** — Reinstating the inherited hooks a blocked workspace list had displaced follows REQ-HOOKS-098, which fixes which entries return, the order they take, and the test by which an inherited entry counts as already present; REQ-HOOKS-099 fixes that the reinstatement lapses once the user allows the workspace list. This domain restates none of them. The guarantee it relies on is the one those requirements produce: declaring a hook list the user then refuses can never take away a hook that user configured for themselves, and no hook is run twice because a workspace re-declared it under another name.

- **REQ-WORKSPACE-126** — When inherited hooks were restored this way, the skipped-hooks notice gains the sentence REQ-HOOKS-101 fixes for that case, which this domain does not restate. What this domain relies on is that the notice makes plain that the hooks the user set up for themselves remain untouched.

### Desktop Hook Trust UI

- **REQ-WORKSPACE-127** — Given a pending hook review, the notice the user sees is the persistent warning REQ-NOTIFY-224 fixes, carrying the action that opens the review; this domain restates neither its facts nor its wording, and the issue recorded beside it is REQ-HOOKS-086's. What this domain fixes is when it is published: on startup, once the window is interactive rather than during its construction (REQ-WORKSPACE-141), and never by opening the review dialog unbidden.

- **REQ-WORKSPACE-128** — The hook-trust display reads the trust summary of REQ-HOOKS-105 — its status vocabulary, the condition that selects each status, the reporting of reinstated hooks as permitted, and its behaviour where the configuration cannot be read — and reports it as one of the four statements REQ-NOTIFY-227 fixes. This domain holds no copy of either, and states no fifth status and no fifth statement.

- **REQ-WORKSPACE-129** — The review dialog is the one REQ-HOOKS-106 specifies — its modality, its minimum size, its title, what it states, how each hook is rendered, and that it is the only surface in the product on which a hook command is displayed — with the buttons and their roles fixed by REQ-HOOKS-107. This domain restates none of them and adds no second route to that dialog beyond the settings tab of REQ-HOOKS-104.

- **REQ-WORKSPACE-130** — That every exit path resolves exactly once, that dismissal counts as refusal rather than consent, that both answers are persisted, and that a failed write is reported in the dialog rather than passing unnoticed are fixed by REQ-HOOKS-107 and REQ-HOOKS-108; this domain restates none of them. What this domain adds is what the user is told afterwards: a failed write SHALL be reported as "Could not record your hook decision" / "Rotaris could not write the verdict, so the hooks stay blocked and you will be asked again."; a recorded decision SHALL raise the acknowledgement "This workspace's hooks are allowed to run." or "This workspace's hooks will not run."; the settings tab SHALL refresh afterwards; and the dialog together with the repository-supplied text it displayed SHALL be discarded immediately after resolution (REQ-HOOKS-102).

- **REQ-WORKSPACE-131** — The Settings Hooks tab is the one REQ-HOOKS-103 specifies — its grouping by owning agent, its columns, and its status vocabulary — with the review control and the decision summary beside it fixed by REQ-HOOKS-104 and the decision management by REQ-HOOKS-136. This domain restates none of them, and states no surface that reveals a hook command: REQ-HOOKS-102 admits exactly one, the review dialog. What this domain adds is the tab's empty state, which SHALL convey that no compatible hook was found and name both places one may be declared — the external assistant's own global settings (REQ-WORKSPACE-132) and `agents.yaml` (REQ-WORKSPACE-034) — its wording left to the implementation.

- **REQ-WORKSPACE-132** — Hook records read from the external assistant's user-global settings SHALL appear in the Settings Hooks table as a second agent group, named "Claude Code", with the source label "Claude Code global settings". The group SHALL carry one enable checkbox governing the whole group and one per hook record, and a choice made with either SHALL still be in force after the application is restarted. A record the product cannot run SHALL be listed with its enable control unavailable and with the reason it is incompatible stated in the row, so a discovered record is never silently dropped. These records SHALL lie outside the workspace hook trust gate entirely: no digest covers them, no review decision is required before they run, and they SHALL never be listed in the review dialog of REQ-WORKSPACE-129.

  The settings are read from that assistant's own documented user-global settings file, at the path that assistant publishes for it, and the product SHALL treat that file as **read-only**: it SHALL never create, write, move, or delete it, and a change made in this product SHALL never alter it. A file that is absent, unreadable, or unparseable SHALL yield no records and SHALL raise no error, which is also the ordinary case: discovering nothing SHALL render as the absence of the group entirely, not as an empty group with a heading.

  The per-group and per-record enable choices describe this machine and an external tool rather than the project, so they SHALL be persisted as desktop preferences in the per-user preference store under the registered key `hooks/{record-key}/enabled`, keyed by a stable identifier for the group or record (REQ-SHELL-006, which registers the key set of that store; REQ-CONFIG-463, which makes such a preference user-wide), and SHALL NOT be written into any workspace file, into the layered YAML configuration, or into the external assistant's own file. A choice recorded against a record that is no longer discovered SHALL be retained and SHALL take effect again if that record reappears.
