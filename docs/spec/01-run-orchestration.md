# Multi-Agent Run Orchestration

## Overview

A run takes one top-level user task and executes it through an autonomous, iterative multi-agent process: the task is classified for intent, handed to a coordinator role that delegates work to specialist child agents through an explicit delegation tool, and driven by an outer iteration loop that targets one todo task per iteration, verifies changed work with deterministic checks, and re-queues or abandons tasks based on evidence. The run ends with a well-defined stop reason, a terminal status, durable session records, and per-child machine-readable report artifacts; safety mechanisms (limits, timeouts, a hidden loop monitor, a message-limit soft pause, and cancellation sweeps) guarantee that no run ends with work items or child records left in a non-terminal state.

## Requirements

### 1. Run Entry and Session Setup

- **REQ-ORCH-001** — *Withdrawn.* The requirement fixed parity between a background command-line host and an interactive terminal-UI host, neither of which this product has; the capability it protected — a run reaching the same outcome however it is watched — is carried by REQ-ORCH-150.
- **REQ-ORCH-002** — The top-level user task MUST be given to a single configurable entry role (default role name `orchestrator`). This entry role is an ordinary configurable role whose orchestration authority derives entirely from its instructions and granted tool set; each iteration of the outer loop starts it fresh as that iteration's root agent.

- **REQ-ORCH-004** — Given a fresh session, when a run starts, a new todo list MUST be created with a single initial phase (named "main") containing the task. Given a resumed session, the new top-level task MUST be appended to the session's existing todo state. The execution payload handed to the root agent MUST carry the conversation context in effect, the artifacts recorded for the session, the todo state as it currently stands, and the progress accumulated before this run.

- **REQ-ORCH-150** — Given the same task, the same configuration, and the same run options, a run MUST reach the same orchestration outcome — the same intent handling, the same delegation and iteration rules, the same verification gating, the same stop reason, and the same terminal status — whether its view is attached in the desktop interface for the whole run, attached for part of it, or never opened at all. Exactly one behavior is permitted to differ with attachment: how a message-limit pause is surfaced and resolved — with a view attached the run presents the dialog of REQ-ORCH-086, and with none attached it takes the detached path of REQ-ORCH-087. Every run option this domain defines, the run override of REQ-ORCH-025 included, is chosen in the desktop interface and is available to every run alike.
- **REQ-ORCH-151** — The application MAY have more than one run in flight at once, in the same workspace or in different ones, and every run MUST be isolated from every other. Each run's iteration ledger, child records, task ids, canonical-name scope, message counter, consecutive-retry counters, repair budgets, loop-supervisor state (REQ-ORCH-105), artifact store (REQ-ORCH-149), session snapshot, and session diagnostics MUST be scoped to its own session id and MUST never be read or written by another run. A run's stop reason, terminal status, and the sequence of states each of its children passes through MUST NOT depend on how many other runs are in flight, or on the order in which concurrent runs interleave. The per-model concurrency cap of REQ-ORCH-050 is likewise scoped to one run, so a run can never be starved of model slots by another run; contention for a provider across concurrent runs is handled by the rate-limit and quota rules of REQ-ORCH-091 instead.
- **REQ-ORCH-152** — A run-start mode MUST be settable to exactly one of `auto` or `plan`, defaulting to `auto`. The setting is persistent — it outlives the run that used it and governs the next run started in the same workspace until the user changes it — and is offered both where a run is started in the desktop interface and in the settings interface. In `auto` mode no gate applies and the run proceeds exactly as the rest of this document describes. In `plan` mode the gate of REQ-ORCH-153 applies.

The block is a property of the run and not of any one role, and it withholds capability rather than preventing the run from starting: the run's root execution record is created with the entry role exactly as REQ-ORCH-072 requires of every iteration of every run. While the gate is held, every agent of the run — the entry role included — MUST hold **planning grants**: the tool set it would otherwise hold, less every tool the public tool-name registry declares as writing workspace files or running commands (REQ-TOOLS-001), with a tool the registry carries no declaration for counting as declaring all three. That withholding MUST be enforced where a call is dispatched, so such a call is refused whichever role issues it and by whatever route the tool reached that role. The run MUST wait indefinitely for an explicit answer and MUST NOT proceed on a timeout, on the view being closed, or on any default. The answers offered MUST be exactly three: approve, which releases execution; revise, which starts another plan cycle under REQ-ORCH-154; and cancel, which stops the run with stop reason `user_cancelled`. While the run is blocked at the gate its session execution status MUST be `awaiting_plan_decision`, and the pending decision MUST survive a restart of the application in the same way a message-limit pause does (REQ-ORCH-087). The hold is not a termination: it MUST raise no terminal run status and no terminal result, and the run the user approves, revises or cancels is the run that reached the gate (REQ-ORCH-154), whether or not the process that hosted it outlived the hold.

### 2. Pre-Flight Intent Classification

- **REQ-ORCH-005** — Intent classification MUST complete before the coordinator is initialized, and the classified intent MUST be in effect before the first iteration so that intent-dependent behavior (capability gating, playbook cells, budget clamps, route-aware guards) applies from iteration 1.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005) revision 7, 2026-10-06.** Clause 40: the
  > Continue action and a message-limit resolution make no classification call and carry the intent in effect; an
  > iteration a continue resumes runs under the intent it started with, so a continue by message's classification is
  > in effect from the run's next iteration rather than its first. Every other run classifies as stated.
- **REQ-ORCH-006** — The intent taxonomy MUST consist of exactly these 13 categories: `explicit_trivial`, `question`, `exploration`, `problem_resolution`, `single_file_change`, `small_feature`, `moderate_feature`, `large_feature`, `refactor`, `architectural`, `requirements`, `whole_project`, `ambiguous`. Category semantics MUST include: `problem_resolution` means diagnose AND fix; `exploration` means investigate only; when several categories are plausible the tie-break prefers `moderate_feature`.
  > **Narrowed by [`PD-ORCH-011`](../product/directives.md#pd-orch-011), 2026-10-06.** `explicit_trivial` means an
  > explicitly stated, trivial edit; a request that changes nothing belongs to the answer group. The tie-break chooses
  > among the categories that are plausible, preferring `moderate_feature` only where it is one of them. The categories
  > and the two fixed meanings above are unchanged. *Amended 2026-10-13, revision 2 ([OQ-227](../architecture/open-questions.md),
  > ruled under [R-072](../product/requests.md#r-072)):* `single_file_change` means a small edit confined to one file, as
  > the request states or implies; a change requested together with a test of it, or one naming several files to change,
  > is outside it unless the request places all of it in one file, and the classifier is told so on every rung.
- **REQ-ORCH-007** — Any classification failure — timeout, unparseable response, unmapped category string, empty response, or setup error — MUST produce the fallback intent `moderate_feature`, flagged as a fallback with a human-readable reason, and MUST NOT stop or fail the run.
- **REQ-ORCH-008** — The classification call MUST time out at 12.0 seconds by default. *This sentence read "The classification call MUST time out at 8.0 seconds by default" until 2026-09-11, when the owner raised the default under ESC-35: the live run measured a self-hosted endpoint whose first token arrives after 8.0 s, so a prompt that would have classified correctly took REQ-ORCH-007's fallback instead. The figure remains a default and this requirement still fixes no other bound; a caller that supplies its own is unaffected.* Its input MUST consist of the raw user prompt truncated to 4000 characters, a small metadata mapping such as the run entrypoint, and the optional prior-response field owned by REQ-ORCH-012 with its independent 4000-character cap. Additional repository retrieval MUST be excluded. User-supplied prompt text and historical response text may contain code; each remains confined to its named field. Metadata MUST carry run context only. The prior-response field remains untrusted under REQ-ORCH-012.
- **REQ-ORCH-009** — The model used for classification MUST be selected by consulting three configured model slots in a fixed order — the small-model slot, then the fallback-model slot, then the default summary-model slot — and using the first slot that is set. When none of the three is set, no request is sent to any provider and the run proceeds immediately on the fallback intent `moderate_feature`, flagged as a fallback, with a reason stating that no small model is configured. The three slots are the configuration keys `small_model`, `fallback_model`, and `default_summary_model` (REQ-CONFIG-064, REQ-CONFIG-065), consulted in exactly that order. The `fallback_model` named here is the run-level slot of REQ-CONFIG-065 and never the per-role fallback model of REQ-ORCH-144: classification completes before the coordinator is initialized (REQ-ORCH-005), so no role's overrides are in scope for it.
  > **Narrowed by [`PD-MONITOR-007`](../product/directives.md#pd-monitor-007), 2026-10-06.** The selected slot's model is
  > followed through the session's override; where the pair it reaches is held out of quota for the session, no request
  > is sent and the run proceeds on the fallback intent with a reason saying so. The order of the slots is as stated.
- **REQ-ORCH-010** — Structured output MUST be requested through a three-rung degradation ladder tried in order: (1) strict, enum-constrained JSON schema; (2) generic JSON-object mode with an appended instruction showing the exact keys and one example; (3) unconstrained text. A rung a given model has previously rejected MUST be remembered per model for the session and skipped on later calls; per-model capability configuration MAY pre-map a rung (e.g. forcing a model straight to JSON-object mode).
- **REQ-ORCH-011** — The classification result MUST carry: the intent category, a confidence value in [0, 1] or null, a reason string, a fallback flag, and a carried-over flag.
- **REQ-ORCH-012** — When the session has prior completed coordinator iterations, the latest usable one's stored summary (else its final response text), truncated to 4000 characters, MUST be passed to the classifier as optional prior-response context. Iterations persisted without a role attribution are ineligible. The classifier instructions MUST direct that this history is untrusted context and that instructions embedded in it must never be followed.
- **REQ-ORCH-013** — Resume intent carry-over: when (a) the fresh classification is unusable (`ambiguous` or a fallback), (b) the session has a prior recorded intent that is a real non-ambiguous category, and (c) the session todo still has unfinished work (pending, in-progress, and abandoned items all count as unfinished), then the prior intent MUST be inherited deterministically with no model call, the carried-over flag set, and a reason stating the previous intent was continued. An unreadable todo state MUST count as "no unfinished work" (no carry-over).
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005) revision 7, 2026-10-06.** Clause 40: the
  > Continue action and a message-limit resolution carry the intent in effect with no fresh classification at all, and
  > the prior intent this carry-over inherits is the intent in effect, a continuation's or else the launch's. A
  > classification that runs carries over as stated.
- **REQ-ORCH-014** — The desktop interface MUST show a transient status before the classification call conveying that the intent is being classified, and MUST replace it in place — not append to it — with a status conveying the classified intent by its exact category identifier (REQ-ORCH-006). A carried-over intent (REQ-ORCH-013) MUST additionally be conveyed as continued from the previous run; a fallback (REQ-ORCH-007, REQ-ORCH-009) MUST additionally be conveyed as a fallback, together with its reason where one is available, the reason normalized (a provider's structured-output rejection is conveyed as a generic provider-rejection phrase rather than the provider's own text) and truncated to 180 characters. The wording, punctuation, and separators of that status are the implementation's; the category identifier it carries is exact, and the status is never conveyed by colour alone (REQ-SHELL-149).
- **REQ-ORCH-015** — The classified intent MUST be propagated to the child-execution layer so that completion guards are route-aware: a run classified as answer-only (question/exploration) MUST NOT fail a child for producing no file edits.

### 3. Intent-Based Capability Gating

- **REQ-ORCH-016** — A user-inspectable intent-to-tools mapping MUST gate the entry role's tool set. Exactly the two simplest intents (`explicit_trivial`, `single_file_change`) grant the entry role the direct-work bundle; every other intent applies no mapping entry, leaving the role's configured coordination-only restrictions in force. A `single` run override (REQ-ORCH-025) grants the direct-work bundle whatever the classified intent is, and is the only input to this mapping besides the intent itself; a `swarm` override is not an input to it. The direct-work bundle MUST be defined by capability and not by a literal list of tool names: it is todo management and delegation, the search, fetch, and artifact-read capabilities, and every tool the public tool-name registry declares as reading workspace files, writing workspace files, or running commands (REQ-TOOLS-001). Resolving the bundle against the registry's own per-tool declarations means a tool added to that registry later joins the bundle, or stays out of it, by its own declaration and with no amendment here. Under a `single` override the `delegate` tool is withheld notwithstanding this bundle, per REQ-ORCH-025. While a run is held at the plan gate the bundle is narrowed by REQ-ORCH-153 for as long as it is held; that narrowing only removes tools and never adds one, and approval restores the bundle this requirement grants.
- **REQ-ORCH-017** — Mapping errors MUST fail safe: an unknown intent key, a malformed tool list, or an unreadable mapping file results in no tool restriction being applied, with a logged warning. Obsolete instruction-text entries in the mapping MUST be rejected.
- **REQ-ORCH-018** — The intent tool gate MUST apply only to the configured entry role; other roles' tool sets are unaffected by intent.

### 4. Behavior Playbook Matrix

- **REQ-ORCH-019** — Per-intent behavior MUST be drawn from a playbook matrix whose row is selected by three keys — role, classified intent, and model tier — and which the user can override per REQ-ORCH-026. The playbook rendered for a role MUST form part of the instructions that role is given, for every role that has a matching row and not only for the coordinator; a role with no matching row is given no playbook text at all (REQ-ORCH-023). The cell selected for the run MUST be recorded per REQ-ORCH-027, so which row was in force is verifiable after the run. The model-tier vocabulary is exactly `small`, `medium`, and `large`, ordered small < medium < large, together with the wildcard `any`, which matches every tier when it appears in a matrix key and is never itself a role's tier. A model's tier is the tier alias it resolves through (REQ-CONFIG-070, REQ-CONFIG-071), and a role's tier is that of the model it is configured on.
- **REQ-ORCH-020** — A rendered playbook MUST contain all eight slots, each exactly once, in this order: ROUTE, AUTONOMY, RESEARCH, CHUNKING, VERIFY, ARTIFACT, OUTPUT, BUDGET. Where one role produces output that a different role will carry out (for example a plan written for an implementer), the CHUNKING and OUTPUT slots MUST be taken from the tier of the role that will carry the work out, and only when that tier is lower than the producing role's own; this substitution MUST never move a slot to a higher tier. "Lower" is decided by the small < medium < large ordering of REQ-ORCH-019. The producer-to-consumer pairings are exactly two: `planner` and `architect` each produce for the role that will carry the work out, identified by the same mapping REQ-ORCH-022 uses (refactor work → `refactorer`, requirements work → `requirements-engineer`, architectural work → `architect`, `coding-agent` otherwise). No other pairing exists, so no other role's CHUNKING or OUTPUT slot is ever substituted.
- **REQ-ORCH-021** — Intents MUST resolve through groups: answer = {question, exploration}; clarify = {ambiguous, requirements}; micro = {explicit_trivial, single_file_change}; fix = {problem_resolution, refactor}; small-build = {small_feature}; medium-build = {moderate_feature}; large-build = {large_feature, architectural, whole_project}. Lookup order is: concrete intent → its group → a default row. Tier lookup is: concrete tier → an all-tiers wildcard.
- **REQ-ORCH-022** — The coordinator's playbook row MUST be keyed on the model tier of whichever role will actually carry out the work, not on the coordinator's own tier: refactor work → the refactoring role (`refactorer`), requirements work → `requirements-engineer`, architectural work → `architect`, and `coding-agent` in every other case. As a consequence, whether a planning step comes first depends on that role's tier: when it sits on the largest tier it scopes its own work, so mid-size features and restructuring work do not compel a separate planning step.
- **REQ-ORCH-023** — When a tier cannot be resolved, the medium tier MUST be used and the rendered playbook header MUST state that the model size is undetermined and larger capacity must not be assumed. A role with no matrix row receives no playbook. A cell marked as not routed renders text instructing the role to treat its assignment as narrow because it is outside the standard flow.
- **REQ-ORCH-024** — The BUDGET slot MUST be enforced, not advisory: the resolved cell's budget clamps the runtime child-limit policy for that iteration — tight = {max active children 2, max total children 6, max depth 2}; normal = {4, 12, 3}; wide = no clamp. Clamps only narrow (a tighter configured limit always wins), and any budget-resolution failure falls back to the configured policy unchanged.
- **REQ-ORCH-025** — A user-selected run override MUST be supported as a final layer, chosen in the desktop interface where the run is started, placed after everything else and taking precedence over the matrix cell. There are exactly two. A `swarm` override demands maximum parallel delegation (overlapping ownership of the same work slice remains forbidden); it changes instruction text only, and the entry role keeps its coordinating status and its coordination-only tool set. A `single` override declares that the entry role will complete the task itself, and MUST take effect as a capability change rather than as advice: for that run the entry role does not act as coordinator, so the constraints of REQ-ORCH-029 — which bind it only while it does — do not apply; it is granted the direct-work bundle of REQ-ORCH-016 whatever the classified intent is; and the `delegate` tool MUST be withheld from every role for the whole run, so the demand not to delegate is enforced structurally and no delegated child is ever spawned. The run's own root execution record is not a delegated child and is unaffected by that withholding: REQ-ORCH-072 creates one for each iteration of every run, a `single` run included, so a `single` run is exactly one root execution record per iteration and zero delegated children. A `single` override is valid at every intent, is never narrowed to the two simplest ones, and is never downgraded to guidance the role may disregard.
  > **Narrowed by [`PD-ORCH-006`](../product/directives.md#pd-orch-006) (revision 3), 2026-10-07.** Where the intent-to-tools mapping in force, built-in or a user's file, grants the entry role the direct-work bundle, a `swarm` override changes nothing that run holds or is told: it keeps the bundle with `delegate` in it and is given the directive's direct-work statement and no `swarm` text on any turn, so the coordination-only tool set and the demand for maximum parallel delegation above do not reach it. On every other run the `swarm` sentence governs as written.
- **REQ-ORCH-026** — Playbook content MUST be overridable at two scopes: a global user-configuration directory, and the workspace directory `<workspace>/.rotaris/playbooks/`. Where both scopes define the same field, the workspace value is the one that takes effect; fields the workspace leaves undefined keep their global value, and fields neither scope defines keep the built-in value. An override MAY supply different text for a slot variant the built-in catalogue already defines. An override MUST NOT introduce a slot name or a variant identifier that the catalogue does not define; such a name MUST be ignored, leaving the catalogued content in force, and MUST produce a warning naming it. So that the set an override may address is knowable without reading the product's source, the built-in catalogue MUST be user-inspectable: the settings interface MUST list every slot, every variant identifier defined for it, and the built-in text of each, and that listing is the definition of what an override may address. No variant text is fixed by this document — only the eight slot names of REQ-ORCH-020, the slot semantics, and the lookup rules of REQ-ORCH-021 — so an implementation authors the catalogue's text to those semantics. After an explicit reload, every subsequently rendered playbook MUST reflect the override files as they stand on disk at the time of the reload. The global scope is the per-user configuration directory of REQ-CONFIG-001, and the global-scope override directory is that directory's `playbooks/` subdirectory, mirroring the workspace-scope path.
- **REQ-ORCH-027** — The resolved playbook cell in effect for a run MUST be recorded as an audit payload in the session's run-configuration record (see Data & Formats).

### 5. Coordinator Role Contract

- **REQ-ORCH-028** — The coordinator's instructions MUST carry a routing table from need to specialist role. The default role vocabulary MUST be `orchestrator` (the coordinator itself), `requirements-engineer`, `codebase-analyst`, `librarian`, `architect`, `planner`, `coding-agent`, `tester`, `docs-writer`, `refactorer`, `verifier`, `ui-verifier`, `gatekeeper`. The default routing MUST be: an ambiguous or under-specified request → `requirements-engineer`; a question about the repository as it stands → `codebase-analyst`, which reads the workspace but does not modify it; a question answerable only from outside the repository — third-party documentation, API references, the open web → `librarian`, which likewise does not modify the workspace; design → `architect`; producing an ordered plan, including commissioning whatever research that plan needs → `planner`; implementation → `coding-agent`; testing → `tester`; documentation → `docs-writer`; behavior-preserving restructuring → `refactorer`; final acceptance → `verifier`. Exclusive implementation ownership MUST be measured per todo item and at no other granularity: at most one child at a time may hold an implementation delegation for any one todo item, where an implementation delegation is one whose target role holds a tool the public tool-name registry declares as writing workspace files (REQ-TOOLS-001). Two children working on the same file for two different todo items are therefore not a violation, and two children working on the same todo item are one whatever files they touch. The acceptance role's sign-off before the run is reported successful MUST be an instruction the coordinator is expected to honour and MUST NOT be a run-enforced condition on the run's outcome: the run's own enforcement of whether work is finished is the deterministic completion gate of REQ-ORCH-116, which rests on checks that actually executed rather than on a role's assertion, and the terminal status continues to follow REQ-ORCH-082 and REQ-ORCH-083 from completed and abandoned task counts alone. No status, stop reason, or gate decision is ever made conditional on a role having declared sign-off.
  > **Extended by [`PD-TOOLS-006`](../product/directives.md#pd-tools-006), 2026-09-23; revision 4, 2026-10-07; revision 6, 2026-10-07.** Ownership stays per todo item exactly as stated. Beside it, a child may declare a write scope, and while it is live the file tools refuse other agents of the run a write into it. Since revision 4, `delegate`'s description tells each caller which REQ-TOOLS-001 facets a child of it would hold as each persona, and to ask a persona only for work its tools allow. Since revision 6, a delegation names the todo item it serves (`todo_item`), and the run refuses an implementation delegation for an item another outstanding implementation child holds, the measure of the ownership above.
- **REQ-ORCH-029** — Constraints on the coordinator MUST hold no matter what playbook cell or instruction text is in force, and each is externally checkable from the run's own records. They bind the entry role while it acts as coordinator, which is every run except one taken under a `single` override, where by REQ-ORCH-025 the entry role is the worker, holds the direct-work bundle, and has no delegation tool at all. While the entry role acts as coordinator: it makes no file-modifying tool call and emits no plan, code, or diff of its own authorship; every work item it takes on reaches a specialist through a `delegate` call; work spanning more than one step is accompanied by a todo list it keeps current; no two implementation delegations for the same todo item are outstanding at once; it does not report the run successful while a todo item is non-terminal or while a todo item's recorded state disagrees with what happened; and it issues no delegation whose child would sit deeper than delegation depth 3 (REQ-ORCH-046).
  > **Narrowed by [`PD-ORCH-006`](../product/directives.md#pd-orch-006), 2026-10-06 (revision 2 the same day; revision 3, 2026-10-07, adds REQ-ORCH-025's `swarm` sentence to its narrowing and changes nothing here).** Where the intent-to-tools mapping grants the entry role the direct-work bundle (REQ-ORCH-016: with the built-in mapping, `explicit_trivial` and `single_file_change`), the three constraints that forbid it to do the work itself — no file-modifying call, no plan, code or diff of its own, every work item through `delegate` — do not bind it for that run, and its instructions say it does the work; the other constraints above still bind. Revision 2: on every run, "a todo item is non-terminal" ranges over the items the task in hand answers for, as [`PD-ORCH-012`](../product/directives.md#pd-orch-012) decides them.
- **REQ-ORCH-030** — One attempt at a todo item is one implementation delegation for that item as REQ-ORCH-028 defines it. That attempt counts as failed when its child reaches a terminal state other than `succeeded`, and equally when its child succeeded but the verification evidence recorded for that item afterwards holds at least one blocking check `failed`; a completion-classifier verdict of `NEEDS_ITERATION` is not itself an attempt, because it judges an iteration rather than a delegation. The count is kept per todo item, accumulates across iterations of the same run, and resets only when the item is marked complete. After three failed attempts at the same item the run MUST refuse a fourth implementation delegation for it, with the error observation of REQ-ORCH-038 naming the item, its three failed attempts, and the two permitted next actions; the refusal is enforced by the run and is not left to instruction, so no instruction text can spend a fourth attempt. The two permitted next actions are a diagnosis delegation — to `codebase-analyst` when the unknown lies in the repository, to `librarian` when it lies in a third-party dependency — which carries the accumulated failure context from those attempts and which this rule never refuses, and a failure report to the user. That report MUST convey the item that could not be completed, and for each attempt what was tried and how it failed; its wording is the implementation's.

### 6. Delegation Contract

- **REQ-ORCH-031** — Delegation MUST be an explicit tool call (tool name `delegate`) with required parameters `persona` (target role), `task_name`, and `task`, plus optional `depends_on: list[task_id]`. The task text is instructed to use labeled sections: TASK, EXPECTED OUTCOME, MUST DO, MUST NOT DO, CONTEXT.
- **REQ-ORCH-032** — The optional fields the delegation call accepts beyond those of REQ-ORCH-031, and the handling of each, are fixed by REQ-TOOLS-152; this domain restates none of them. What it relies on that call to provide is: forwarding the reports of already-completed siblings as context without imposing an ordering dependency; a routing hint that is explicitly not a model name; reuse of a previous delegation's session for a retry or follow-up; a background default; attachment of artifact bodies at the head of the child's payload; and suppression of the automatic index of earlier sibling artifacts, which a per-role setting may force independently. The points on which this document previously differed are settled by REQ-TOOLS-152 and are not restated here: what becomes of an `inherited_context` id that resolves to nothing, of one that names a task which failed or has not finished, and of an attachment set that would carry the payload past its size budget are that requirement's to fix, and this domain states no rule of its own for any of them.
- **REQ-ORCH-033** — What a delegation observation carries — the canonical task name, the closed status set it draws on, the task id, and the message accompanying each status — is fixed by REQ-TOOLS-153; this domain restates none of it, mints no delegation status of its own, and states no message text for one (REQ-ORCH-037). What it relies on that requirement for is that every accepted delegation yields an observation the coordinator can read the child's admission from, and that a delegation held behind a per-model cap is reported as held rather than as rejected (REQ-ORCH-050). The one thing this domain adds is the model-visible rendering of that observation, which is of the form `Task '<canonical>': <status> — <message>` followed by a `task_id: <id>` line.
- **REQ-ORCH-034** — Role aliases MUST be resolved before spawn: `coder` → `coding-agent`, and `playwright` → `ui-verifier`. An alias resolves only when its target role actually exists in the current configuration. An unknown role MUST be rejected with a message listing the known role names and the supported aliases rendered as `<alias>-><target>`; when an alias was resolved, the observation message states which alias resolved to which role.
- **REQ-ORCH-035** — The order in which a child's payload is assembled at spawn is fixed by REQ-TOOLS-154; this domain restates none of it. What it relies on that requirement to provide is a place in that order for the two blocks whose content this domain owns — the verification-evidence block of REQ-ORCH-129, supplied for the acceptance role, and the index of earlier sibling artifacts whose suppression REQ-ORCH-032 governs — and that the caller's task text is the last thing the child reads. The one addition this domain makes is positional and applies to no other block: a child spawned with dependencies additionally receives the prior-agent-context block of REQ-ORCH-047 at the moment it becomes ready, placed ahead of everything REQ-TOOLS-154 orders, and it is therefore the first content that child sees.
- **REQ-ORCH-036** — Every spawned child MUST be assigned a task id matching `^bg_[0-9a-f]{8}$`, unique within the session. `depends_on` entries are task ids and are normalized to canonical names at spawn; an unknown task id in `depends_on` MUST be rejected with an error naming it.
- **REQ-ORCH-037** — What the caller observes when a delegation is accepted is fixed by REQ-TOOLS-152 and REQ-TOOLS-153; this domain restates none of it. What it relies on those requirements for is that `delegate` never suspends the parent's conversation. This domain adds no suspend step of its own and none is observable in the transcript; a parent that is to wait for a child is enrolled in the one waiting mechanism of REQ-TOOLS-156, which is the same mechanism `wait_for_tasks` uses (REQ-ORCH-062), and is resumed from it under Section 11.
- **REQ-ORCH-038** — The following delegation attempts MUST be rejected with an error observation and no spawn: unknown role; depth limit exceeded ("Max depth N exceeded"); total-children limit reached ("Max total children N exceeded"); active-children limit reached ("Max active children N exceeded"); unknown dependency; dependency cycle ("Dependency cycle detected"); a dependency owned by a different parent (the rejection names both parents); a malformed inherited-context entry (e.g. empty string); a fourth implementation delegation for a todo item that already has three failed attempts (REQ-ORCH-030).
- **REQ-ORCH-039** — A delegation to the acceptance role MUST be refused, with no child spawned, while the most recent verification evidence available for the task in hand records at least one blocking check as `failed`. The refusal reason MUST name those checks, state that their output is already captured, state that the task is already set to be attempted again, and direct that acceptance be delegated only once those checks pass. Where no verification evidence exists for the task at all, the delegation MUST be allowed and proceeds on the empty-evidence path of REQ-ORCH-129. Checks recorded `timeout`, `skipped`, or `invalid` MUST NOT by themselves cause a refusal; they are disclosed to the acceptance role per REQ-ORCH-129. The asymmetry between this rule and REQ-ORCH-116 is deliberate and MUST be preserved: the completion gate decides whether the work is finished, so a blocking check that never answered its question leaves it unsatisfied, whereas this refusal exists only to stop the acceptance role being asked to bless a result already known to be red. Keying the refusal on `failed` alone is what keeps acceptance reachable when checks timed out, were skipped, or were refused by policy — precisely the case REQ-ORCH-129's list of checks that did not answer their question exists to hand it.

### 7. Child Task State Machine

- **REQ-ORCH-040** — The state a delegated child occupies, the closed set those states are drawn from, and which of them are terminal are fixed by REQ-MONITOR-014 and REQ-MONITOR-300; this domain holds no copy of that set and mints no child state of its own. What it relies on those requirements for is that the set is closed, that a child created with unresolved dependencies begins in `waiting_on_dependencies` and one created behind a per-model cap in `waiting_on_model_slot` and every other child in `queued` (REQ-ORCH-046, REQ-ORCH-050), and that the terminal subset is absorbing, so the sweeps of REQ-ORCH-052 and REQ-ORCH-053 and the waits of REQ-ORCH-062 have a settled condition to test against.
- **REQ-ORCH-041** — The legal-transition table for a delegated child, the rejection of any move outside it, and the completion timestamp stamped on entering a terminal state are fixed by REQ-MONITOR-300, REQ-MONITOR-016, and REQ-MONITOR-017; this domain holds no copy of the table, states no transition of its own, and fixes no wording for the rejection. This identifier remains the citation other documents use for a child's terminal state (REQ-HOOKS-075) and continues to resolve to the vocabulary REQ-MONITOR-300 declares absorbing. What this domain relies on those requirements for is that cancellation settles any non-terminal child to `cancelled` from whatever state it is in (REQ-MONITOR-209), so the cleanup sweeps of REQ-ORCH-052 and REQ-ORCH-053 can never fail partway, and that a rejected transition leaves the child's record untouched, so a rejected move can never be mistaken for progress by the scheduling passes of Section 11.
- **REQ-ORCH-042** — Which child states count against the concurrent-child budget, and which hold a model slot, are fixed by REQ-MONITOR-015 and REQ-MONITOR-020; this domain holds no copy of either rule and names no state of its own on the point. What it relies on those requirements for is that a child parked in `waiting_on_model_slot` consumes no active-child allowance — it is idle and holds no model connection — so children queued behind a model can never trip the active-children limit of REQ-ORCH-046, and that a slot freed by a child reaching a terminal state promotes exactly one held child (REQ-ORCH-050).
- **REQ-ORCH-043** — The persisted per-child record MUST include at least: given and canonical names, role, task payload, dependencies, inherited context, state, spawn and completion timestamps, parent agent identity, depth, conversation identity, category, session id, background flag, task id, launch generation, produced/received artifact ids, resolved model key, the actually granted native tool set, the granted MCP tools per server, and the child's live serialized todo state.

### 8. Child Naming, Limits, and Dependency Graph

- **REQ-ORCH-044** — Child task names MUST be scoped per parent. A reused name is deterministically renamed `<name>_<n>`, where n is the smallest positive integer, counting up from 1, not already in use for that name, and the canonical name is used everywhere the task is referenced (transcripts, dependency resolution, artifacts).
  > **Narrowed by [`PD-ORCH-010`](../product/directives.md#pd-orch-010), 2026-10-06.** A child at any depth is also
  > renamed off the canonical name or persona of its own root and of every root the session has recorded, though no
  > sibling holds the name. A root named like an earlier child is accepted until after the first release.
- **REQ-ORCH-045** — Canonicalization of a task name MUST apply these steps in order: collapse each run of whitespace; replace every character outside `[A-Za-z0-9_.-]` with `-`; strip leading and trailing `-`, `.`, and `_`; and, when nothing remains, use `task`. The result MUST be at most 80 characters. A name that would exceed 80 characters MUST be shortened to 80 characters or fewer and MUST end in an 8-character lowercase hexadecimal suffix derived from the full name as it stood before shortening, so that the same long name always canonicalizes to the same string and two different long names never canonicalize to the same string. The digest is SHA-256 taken over the UTF-8 encoding of the name as it stood after the first three steps and before any shortening, and the suffix is the first 8 characters of that digest's lowercase hexadecimal rendering. A single `-` precedes it. A shortened name is therefore the first 71 characters of the pre-shortening result, then `-`, then the 8-character suffix, which is exactly 80 characters.
- **REQ-ORCH-046** — Spawn validation MUST be applied in this order, and the first check that fails MUST reject the delegation with the error observation of REQ-ORCH-038, creating no child record and issuing no task id: (1) depth — the entry role is at depth 0, a child of an agent at depth d is at depth d+1, and the spawn is rejected when the child's depth would exceed the configured maximum (default 3); (2) total children — the number of children already created in this iteration's ledger has reached the configured maximum (default 20); (3) active children — the number of children in `starting` or `running` has reached the configured maximum (default 6); (4) every id in `depends_on` names an existing child of the same parent; (5) the new dependency edges, added to the edges already present, close no cycle. A delegation that passes validation creates a child whose initial state is `waiting_on_dependencies` when `depends_on` was non-empty and `queued` otherwise; a child whose model key is already at its concurrency cap is reported as `waiting_on_model_slot` per REQ-ORCH-050.
- **REQ-ORCH-047** — A dependent child MUST start only after ALL of its dependencies have both reached `succeeded` AND had their mandatory report artifact stored; a dependency without a stored report does not count as succeeded. When a dependent becomes ready, the framework MUST prepend exactly once (never re-prefixed on later state hops such as promotion out of the model-slot queue) a prior-agent-context block flagged as authoritative — directing the reader to rely on the supplied findings rather than repeating that investigation — containing each dependency's final response (else last response) in per-dependency sections identifying name, role, and status. If reports are missing, no context block is injected.
- **REQ-ORCH-048** — When a child reaches `failed` or `cancelled`, every child depending on it that still stands in a state from which REQ-MONITOR-300 makes `blocked` reachable MUST transition to `blocked`, cascading transitively to further dependents; a dependent that is already under way is left to run. This domain holds no copy of the transition table and names no source state of its own. What it relies on REQ-MONITOR-300 for is that those source states are exactly the three a dependent can occupy before it has started, so the cascade never has to decide whether a move it demands is legal, and that `blocked` is absorbing, so a cascaded child settles once. Blocked children are never started automatically. Terminal-state callbacks MUST fire for cascaded records exactly as for directly completed ones.
- **REQ-ORCH-049** — A child MUST be started at most once, however many scheduling passes for the same parent are in flight at the same time. Over the whole run, the number of `child_start` timeline events recorded for any one task id MUST be exactly one for a child that started and zero for one that never did. An attempt to start a child that has already been started, or that has since moved on, MUST be suppressed rather than carried out, and MUST be recorded as a `child_launch_suppressed` timeline event together with a `stale_child_launch_claim` issue naming the child's canonical name and task id.

### 9. Per-Model Concurrency

- **REQ-ORCH-050** — A per-model concurrency cap MUST limit how many children bound to the same model key may be in `starting` or `running` at one time, where a model key is the identifier under which a model is configured (REQ-ORCH-145). A cap the user set for a model always applies; where the user set none, the cap in force is the one the model's provider catalogue entry declares, and this domain holds no list of provider names and no per-name figure of its own (REQ-MONITOR-021). A catalogue entry that declares nothing on the point declares no cap, so every model of such a provider is uncapped, and adding a provider that does declare one caps its models with no amendment here. Exceeding the cap MUST NOT reject the delegation: the child is created, reported with status `waiting_on_model_slot` per REQ-ORCH-033, and held until a slot frees. Held children MUST be released in the order they were held, one returning to `queued` each time a child bound to the same model key reaches a terminal state. A held child that has itself reached a terminal state MUST be dropped rather than released. Where no cap applies to a model, no child bound to it is ever placed in `waiting_on_model_slot` on that account.

### 10. Terminal Marking, Sweeps, and Orphans

- **REQ-ORCH-051** — Marking a child terminal MUST: store its report retrievable by both canonical name and task id; enqueue a completion notification for background-flagged children (carrying task id, canonical name, description, state, duration since spawn, count of still-running siblings, and produced artifact ids) while foreground children produce no notification; cascade blocking on failure/cancellation; and release the model slot. A child's result lives only for the duration of the session unless an explicit artifact write is performed, which is the only way a durable artifact-store record comes into being.
- **REQ-ORCH-052** — An idempotent finalize-incomplete sweep MUST close every non-terminal child record as `cancelled` through the normal terminal-marking path (so slots release, blocking cascades, and callbacks fire), re-checking per record because closing one can cascade-block another. Every exit path from an iteration — blocked delegation, plain re-queue, cancellation, crash — MUST leave both the record for the iteration itself and every child record it holds in a terminal state, so that a finished run never leaves behind a record that still reads as running.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 2).** An exit from an iteration by a pause, a stop, a quit or a crash leaves every unfinished agent in the resumable state `paused`, and the iteration open; every other exit is unchanged.
- **REQ-ORCH-053** — On session continue, a run that has just acquired the session lock MUST settle every non-terminal child record read back from the previous run (e.g. after a killed host or hard cancel) to `cancelled` before its first iteration, so reattached sessions never show phantom running agents.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 2).** The settle still runs, and no longer touches a `paused` agent: that agent is resumed with its iteration instead of being cancelled.
- **REQ-ORCH-054** — A newly-terminal query MUST return terminal children the parent has not yet observed and mark them observed; calling it again immediately returns nothing.

### 11. Parent Suspension, Resume, and Notifications

- **REQ-ORCH-055** — A parent MUST be resumed whenever at least one direct child reaches a terminal state the parent has not observed; multiple terminal events may batch into one resume. On resume the parent receives the newly-terminal children's structured reports, the current state of all its direct children, and scheduling metadata, and may then continue orchestrating, work locally, spawn more children, or end generation again.
- **REQ-ORCH-056** — After a parent is resumed, the run MUST keep scheduling on that parent's behalf until all three of the following hold at the same time, and MUST then leave the parent idle: the parent has no outstanding wait request; no completion notification for it is still undelivered; and every child of it that could be started has been started at least once. A parent whose remaining children are all waiting on dependencies that have not been met MUST NOT be resumed again on that account alone: a child that has already been attempted does not by itself cause a further resume, so a run can never alternate between starting and resuming indefinitely without some child changing state.
- **REQ-ORCH-057** — Foreground pass: ready children are spawned, and a parent that is to wait for them is enrolled in the one waiting mechanism of REQ-TOOLS-156 (REQ-ORCH-037), over the freshly spawned children only and never over the outer task. This document describes no second waiting path and adds no suspend step of its own; what it relies on that mechanism for is that the parent is resumed once the waited-for children are terminal. On that resume, now-duplicate notifications MUST be discarded and the parent MUST receive a message stating that child task updates are available, including per-child report blocks; when other children still run, the guidance states how many are still running in the background; when none remain, the guidance states that all background tasks finished and encourages issuing the next batch of delegations in parallel before ending the turn.
- **REQ-ORCH-058** — Background pass: spawn ready background children, then resume the parent immediately with a message stating background tasks have started, instructing it to continue productive work and to use the waiting tool only when specific results are needed, plus an active-background-tasks list of the form `- <canonical> \`<task_id>\`: <name>`.
- **REQ-ORCH-059** — For each background child that completed, a completion notification MUST be injected into the parent conversation without triggering generation (fire-and-forget), containing: a background-task-completed banner; the task id; the description (canonical name plus given name); the duration in seconds; published artifacts when any; when others still run, the remaining count with an explicit promise of notification when all complete and an instruction not to poll but continue productive work, plus a usage hint for the output-retrieval tool (summary and verbatim forms); otherwise a statement that all background tasks have completed. Open-todo reminder lines are appended. After injection, the parent is resumed with an empty message. This delivery MUST work even when the child completes while the parent is mid-turn (the parent is interrupted for injection without force-closing its conversation), and a completion delivered via a wait or foreground resume MUST have its matching notification discarded so it is announced exactly once.
- **REQ-ORCH-060** — Each per-child report block in a resume message MUST show the canonical name, role, and status, optional artifact descriptions, then the result text (final response, else last response, else key findings) capped at 4000 characters with a truncation marker stating how many characters were omitted.

### 12. Result Retrieval and Voluntary Waiting

- **REQ-ORCH-061** — A `background_output` tool MUST retrieve a completed task's report by task id, returning: `ok` with the report text; `still_running` with a message naming the id and its current state; or `not_found`. Lookups are parent-scoped: a task id belonging to a different parent also returns `not_found`. A `detail_level` of `summary` returns agent/status/summary/artifacts/key findings/last reply; `verbatim` additionally returns the exact last reply, the union of touched files (edited, created, artifact paths), and highlighted paths with snippets.
- **REQ-ORCH-062** — The `wait_for_tasks` contract is fixed by REQ-TOOLS-156: what an empty task list means, when the call returns without suspending, which requests it refuses and in what words, and the fact that this is the product's only waiting mechanism. This domain restates none of it, states no second waiting path, and fixes no message or error text for one. What it relies on that requirement for is that the waited-for set never includes the caller's own task, so a wait can never depend on the agent that is waiting, and that the wait ends when every task in that set is terminal, whichever way each reached it. The obligations this domain adds are these. A parent has at most one wait outstanding, and an outstanding wait does not survive the end of the parent's conversation. This document places no maximum duration on a wait, and none is needed: every child is already bounded by the hard child timeout of REQ-ORCH-088, and every non-terminal child record is closed by the sweeps of REQ-ORCH-052 and REQ-ORCH-053, so the waited-for set always reaches a terminal state and a wait can never outlive the children it waits on. A separate deadline MUST NOT be imposed: it could only ever fire in a state those guarantees already exclude, and firing it would resume a parent whose children are still holding model slots.
- **REQ-ORCH-063** — Wait resolution: the drain spawns ready children, collects reports for the waited set, and resumes the parent with a message stating the waited-for background tasks completed, followed by the results, once the waited set is fully covered. A transient window where a task's execution handle has vanished but its record still reads running MUST NOT be treated as completion. Matching notifications are discarded so no completion is double-announced.
- **REQ-ORCH-064** — Time spent blocked in a voluntary wait MUST NOT register as in-flight tool activity for graceful-pause purposes, so a parent legitimately blocked for minutes is not force-closed.
- **REQ-ORCH-065** — Any role holding the `delegate` tool MUST be able to delegate in its turn, subject to REQ-ORCH-046. Every delegation made during one iteration, at any depth, MUST count against that iteration's own set of child records and against the same limits and scheduling as delegations made by the entry role; the counters do not restart at a deeper level, and one ledger covers the whole iteration (REQ-ORCH-072 creates one per iteration). A child MUST see only what its payload gives it (REQ-ORCH-035) and never its parent's conversation. Every child MUST run in the resolved workspace root; a delegation whose child would run in any other directory MUST fail with an error naming both the expected workspace root and the directory that differed.

### 13. Iteration Loop and Stop Conditions

- **REQ-ORCH-066** — The iteration-loop mode MUST be first-class for long-running autonomous work: usable by the entry role for the whole run or by a delegated child for a bounded subproblem, and functional whether or not a view is attached to the session (REQ-ORCH-150).
- **REQ-ORCH-067** — Each iteration MUST: read the plan/progress state; select the next incomplete anchored task — the first pending task scanning phases in insertion order (so phase order "main" → queued-prompt phases → remediation phases is the priority order); do work for that one task only; verify; update progress; and hand the next iteration compacted state (todo, artifact set, progress, reports) rather than raw transcript. Iteration boundaries MUST be visible in session state and transcript via iteration-start and iteration-end events carrying iteration number, task id/name, outcome, and summary.
- **REQ-ORCH-068** — Before an iteration closes it MUST have updated the todo and progress records, resolved the task it selected into one of three outcomes (marked complete, given up on, or returned to the pending queue), and emitted a report artifact. On verification failure there is no silent roll-over into a second task: the iteration ends with the current task still anchored, set back to pending with a continuation payload.
- **REQ-ORCH-069** — Stop conditions MUST be evaluated between iterations (never mid-iteration; a long iteration may therefore overshoot the time limit), first match wins: (1) all non-abandoned tasks completed → stop reason `tasks_complete`; (2) completed iteration count ≥ the iteration limit → `iteration_limit_reached`; (3) elapsed wall time since run start ≥ the optional time limit → `time_limit_reached`; (4) no pending task → `no_pending_tasks`. Loop-level stops: a user stop → `user_cancelled`; a cancellation → `user_cancelled`; child escalation → `agent_session_aborted`; message-limit cancel → `message_limit_reached`. Every stop reason this document names is a member of the closed set of REQ-MONITOR-301 and is recorded as the token that requirement fixes; this domain mints no stop-reason string of its own, holds no copy of that set, and states no mapping from a stop reason onto a terminal result. That closed set draws no distinction between a person stopping the run and a person cancelling it — both record `user_cancelled` — so the two paths differ in what the run does on the way out and not in what it records. Where a surface explains a stop to a person it MUST convey which of those tokens the run recorded and, for a budget stop, which budget ran out; that sentence is a presentation of the recorded token and never the recorded value itself, and its wording is the implementation's. A stop reason arrived at here is not necessarily final: REQ-ORCH-071 and REQ-ORCH-079 may extend the run before it ends, in which case the loop continues and stop conditions are evaluated again at the next boundary.
  > **Extended by [`PD-ORCH-009`](../product/directives.md#pd-orch-009), 2026-10-06 (revision 2, 2026-10-07).** The stop
  > conditions above are unchanged. An execution iteration whose entry role ended its turn without writing an answer first
  > asks it once more, unless an earlier turn of the same execution wrote one, and the run tells the person when it still
  > wrote none.
- **REQ-ORCH-070** — The iteration limit MUST default to 20; the time limit is optional with no default.
- **REQ-ORCH-071** — Queued prompts extend a finishing run only when the stop reason would be `tasks_complete`: they are appended as a new phase named "Queued Prompts" with tasks named "Queued Prompt: <first 8 characters of the prompt id>", marked triggered, the total task count incremented, and the loop continues. The queued-prompt read MUST be scoped by session id so that concurrent runs never cross-trigger (REQ-ORCH-151). A queued prompt arriving under any other stop reason (e.g. `iteration_limit_reached`) MUST NOT extend the run. Where a queued prompt and relentless mode (REQ-ORCH-079) both apply to the same stop, this requirement MUST be evaluated first and wins: the queued prompt extends the run, and relentless mode is not evaluated for that stop at all — it is evaluated afresh at the next stop the run reaches, by which time the queued prompt's own work is part of what it audits. A queued prompt carries an explicit user instruction, which takes precedence over a model's judgment that the original request is unmet. The two never extend one stop together.
- **REQ-ORCH-072** — Iteration mechanics: the selected task flips to in-progress; a fresh per-iteration ledger of delegated children is created under the budget-clamped policy; the iteration's **root execution record** is created with the entry role and the task's execution payload and transitioned to running. That record is the run's own and is **not a delegated child**: it never arrives through a `delegate` call, it counts against none of the admission limits of REQ-ORCH-046 (depth, total, active), it holds no per-model slot of REQ-ORCH-050, and it is not presented as a task agent (REQ-MONITOR-043, REQ-MONITOR-089, REQ-CHAT-068). It carries an identity of the same shape a delegated child carries — a canonical name and a task id, in the same namespace — so a lookup naming the root resolves to it rather than reporting it unknown; the parent-scoping of REQ-TOOLS-155 and REQ-TOOLS-156 is unchanged by that, so an agent asking about a record it does not own is refused for that reason and never told the root does not exist. Every delegated child of the iteration names the root execution record as its parent and sits one level deeper than it.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 2).** An iteration left open by a pause, a stop, a quit or a crash resumes with its own root restored, rather than a new root.
- **REQ-ORCH-073** — An iteration that raises an unhandled error MUST be caught: the task is marked abandoned, the abandoned count incremented, and the loop continues with the next task.
- **REQ-ORCH-074** — Outcome dispatch on the iteration's (possibly rewritten) report status: `succeeded` → task completed; `failed`/`cancelled` → in-flight children cancelled, task abandoned, and if the report carries an escalation signal the run ends with stop reason `agent_session_aborted`; `blocked` → task reverted to pending, in-flight children NOT cancelled (the next iteration collects their results), and the iteration's own record recorded as succeeded rather than blocked, so that a host status display does not present a deliberate deferral as a failure; any other status (e.g. `partial`) → task reverted to pending.
- **REQ-ORCH-075** — Incomplete-todo re-queue: when a report says succeeded but the agent's own todo list still holds pending/in-progress items after correction retries are exhausted, the same top-level task MUST be re-queued (not abandoned) with a continuation payload built from the stripped base payload plus a continuation marker block stating that success was declared with N todo items incomplete (naming up to the first 5) and instructing the agent to continue from the todo list and not end its turn until every remaining item is complete. Still-running background children MUST be enumerated in the payload with an instruction not to re-delegate them.
  > **Narrowed by [`PD-ORCH-012`](../product/directives.md#pd-orch-012), 2026-10-06.** "The agent's own todo list"
  > ranges over the items the task answers for: those not already open when the task was first taken up (its plan cycle,
  > else its first iteration), a record kept with the task. An item left open before then does not re-queue it and stays
  > open in the plan.
  > **Extended by [`PD-ORCH-015`](../product/directives.md#pd-orch-015), 2026-10-07.** The continuation payload also carries
  > the answer the held iteration wrote, cut to 6,000 characters, to the same task's next fresh root only; a re-queue or a
  > give-up for an open plan is announced in a `system` transcript row.
- **REQ-ORCH-076** — Continuation and verification-failure marker blocks MUST be stripped from a task payload before a new one is appended, so that such markers do not pile up across repeated re-queues of the same task.
- **REQ-ORCH-077** — Consecutive-retry limit per task: consecutive pending-outcome iterations per task id are counted; when the count reaches the per-task consecutive-retry limit, the task MUST be abandoned to break the loop. That limit MUST be a configuration setting of its own, separate from the iteration limit of REQ-ORCH-070 and defaulting to 3. Sharing the iteration limit's value made the guard unreachable — a re-queued task is selected again by REQ-ORCH-067, so the per-task counter and the completed-iteration counter advance in step and the global stop of REQ-ORCH-069 always fires first — and a guard that can never fire is no guard at all. The counter resets on any forward progress.
- **REQ-ORCH-078** — Todo-correction retries MUST reuse the validation-retry setting (default 0): with 0, an incomplete-todo success re-queues without an in-conversation retry; with a positive value, a correction message is sent into the same conversation up to that many times first.
  > **Narrowed by [`PD-ORCH-015`](../product/directives.md#pd-orch-015), 2026-10-07.** The correction count is the larger
  > of 1 and the validation-retry setting, so a setting of 0 still sends one correction; the setting's own default is
  > unchanged.
- **REQ-ORCH-079** — Relentless mode (default off) MUST apply only where the run would otherwise stop for `tasks_complete` or `no_pending_tasks`; it MUST NOT apply to any other member of the closed stop-reason set of REQ-MONITOR-301, and a member added to that set is outside its scope until this requirement is changed to admit it. It is evaluated only after REQ-ORCH-071 has been evaluated and has not extended the run. Where it applies, a model call using the summarizer's model compares the summaries of the run's completed iterations against the original user request captured at run start (REQ-ORCH-003). Where the call reports the request fully met, or where the run has no completed iteration summaries to compare, the run stops with the stop reason it already had. Otherwise a phase named "Relentless Remediation <n>" MUST be appended — n is 1 for the first such phase in the run and increases by one for each further one — holding exactly one task whose payload carries the original request, the finding, and the gaps still outstanding, and the loop continues. At most the configured maximum number of cycles (default 3) of remediation phases MAY be appended in one run; once that many exist the run stops normally. The audit call MUST be bounded by its own timeout, default 60 s. A failed, timed-out, or unparseable audit MUST NOT be retried and MUST NOT extend the run: the run stops with the stop reason it already had, exactly as it does when the audit reports the request fully met. Failing open here is deliberate and matches REQ-ORCH-007 and REQ-ORCH-113 — a model call that could not answer never prolongs a run.
- **REQ-ORCH-080** — On stop with active background children, the loop MUST drain before stopping: wait up to the shutdown-drain timeout (default 120 s; 0 disables) for still-running background children without cancelling them; children still running afterwards are logged, a drain-timeout warning issue is recorded, and teardown then cancels them.
- **REQ-ORCH-081** — Exactly one session-start event (task, workspace, role, permission mode, sandboxed flag, iteration limit) and exactly one session-end event (status, stop reason, iterations completed, duration) MUST be emitted per run, with every exit path funnelling through a single final handler. A host that publishes richer versions MUST be able to disable loop-level publication so consumers never see doubles; session lifecycle observer hooks fire either way.
- **REQ-ORCH-082** — The run-progress summary MUST be derived by evaluating these rules in order and taking the first that matches: (1) stop reason `user_cancelled` → status "paused", severity warning, message conveying that the run came to rest because a person stopped it, and not asserting which of the two person-stops it was; (2) no completed tasks and no abandoned tasks → status "completed", severity information, message conveying that the run ended without resolving any task and naming the stop reason that ended it; (3) no abandoned tasks → status "completed", severity information, message conveying that the run completed; (4) no completed tasks → status "failed", severity error, message conveying the failure, carrying the latest recorded failure detail where there is one and otherwise the number of tasks abandoned; (5) otherwise → status "completed", severity warning, message conveying that the run completed with failures and carrying both the completed count and the abandoned count. Rule 2 exists so that a run which resolved nothing is not reported in the same words as one that finished its work: it is not a failure, since nothing failed, but it MUST NOT read as an ordinary completion either. Rule 1 covers every stop a person asked for during the run, because the closed set of REQ-MONITOR-301 records `user_cancelled` for a user stop and for a mid-run cancellation alike; a run ended either way therefore reports the same summary, and no rule of this list may distinguish the two, there being nothing on the stop-reason axis to distinguish them by. Where the two are told apart at all it is on the persisted-status axis, which REQ-SESSION-073 owns and this domain does not read here; the `paused` token rule 1 emits names a state of this summary line and is not that persisted status. This summary is a status line with its own vocabulary {paused, completed, failed}; it does NOT determine the terminal run result, which follows REQ-ORCH-083 and uses a different vocabulary. The status token, the severity, and the counts or failure detail each rule names are the contract; the wording of the message is the implementation's. This requirement is the single definition of end-of-run summarization for the whole product: a document that needs to state how a finished run is summarized cites this identifier rather than restating these rules.
- **REQ-ORCH-083** — The terminal run result MUST use exactly the statuses `completed`, `failed`, `max_iterations`, `interrupted`, `error`, and the set is closed. This requirement is the single definition of that vocabulary for the whole product: a document that needs to name a terminal run result cites this identifier rather than restating the set, and a document that produces one produces a member of it. `completed` says the work finished; `failed` says the run stopped because the work could not be carried out; `max_iterations` says a configured run budget was exhausted, which is a wall-clock budget as readily as an iteration count (REQ-MONITOR-301); `interrupted` says a person stopped the run; `error` says the outcome could not be determined at all. A value outside the set is a defect and MUST raise rather than be presented as a guessed result. Which stop reason yields which of these is not fixed here: the stop-reason axis, its closed set, and its total mapping onto this vocabulary are REQ-MONITOR-301's, and this document holds no copy of any of them. Where the run recorded no stop reason at all, the result follows from the session's persisted execution status through the single mapping of REQ-SESSION-076, which this document likewise does not restate. This domain fixes no process exit code: the application does not exit when a run ends, so a run's terminal status is the whole of its machine-readable outcome here, and any mapping from that status onto a process exit code belongs to whatever surface needs one. Result construction MUST never raise.

### 14. Message-Limit Soft Pause

- **REQ-ORCH-084** — A message limit MUST be configurable as a positive integer or null, defaulting to null (disabled). It is independent of and coexists with the iteration limit (the hard ceiling); whichever fires first governs. One "message" equals one completed iteration.
- **REQ-ORCH-085** — Each completed iteration MUST increase the run's message counter by one, and the counter MUST survive a host restart by forming part of the persisted session snapshot; a new session begins at zero. When the counter reaches the message limit in force, the pause MUST take effect at an iteration boundary: no further iteration begins, and while the run is paused the loop issues no model request and spawns no child. Background children left running by an earlier iteration under REQ-ORCH-074 are unaffected by the pause and continue. The host MUST be told the run has paused, together with the current count and the limit in force.
- **REQ-ORCH-086** — Pause resolution MUST offer exactly three actions: continue (resume; the counter keeps accumulating), double (the limit is doubled for this session only, then resume), and cancel (stop with stop reason `message_limit_reached`). The desktop interface presents them as a modal dialog showing the current count, the limit in force, and the estimated token usage so far, with the three actions rendered in the one action vocabulary of REQ-SHELL-048; every action MUST be reachable from the keyboard and fully labelled at the minimum window size (REQ-SHELL-022), and the shortcut assignments are the desktop shell's to make. Resolving "double" when the limit is null leaves it null without error.
- **REQ-ORCH-087** — Where no view is attached to the session when that boundary is reached, the run MUST auto-pause there all the same, record the pause durably before it stops — the session execution status `paused_message_limit` together with the count reached and the limit in force — and never auto-continue. The pause MUST survive the application being closed and reopened, and MUST be recoverable from the session's persisted record alone, so that a session paused this way is found in that state without the run that paused it still existing and without any surface having observed the pause happen. How the store holds that state is REQ-SESSION-107's to fix and this domain restates no mechanism for it; what this domain requires is the durability and the status. Attaching a view to the session MUST immediately present the dialog of REQ-ORCH-086, and resolving it MUST clear the recorded pause in the same durable act that records the resolution, so no session is ever left recorded as paused after it has been resolved (REQ-SESSION-110); a command-palette entry for continuing the paused session is active only while the session is in that state.

### 15. Child Execution Safeguards

- **REQ-ORCH-088** — A hard per-child timeout (default 1200 s) MUST bound each child's execution. On expiry: gracefully pause the child; then, if the role has a configured fallback model not yet attempted for this child, retry once on it; otherwise record the child failed with a timeout issue and a report of the form "Child timed out after <N>s" carrying the last/final response extracted from the transcript.
  > **Narrowed by [`PD-ORCH-004`](../product/directives.md#pd-orch-004), 2026-09-23; revision 5, 2026-10-06.** The expiry path above still governs; a child that completed a tool call within its final stall window additionally reports the paths it changed and, unless it is itself a continuation, offers its parent one continuation, telling it that a continuation starts with no memory. The graceful pause is bounded (revision 5): what the child has in flight at the expiry has at most 30 s to end, and is then aborted, a cut model step's streamed reasoning kept in the transcript alone.
- **REQ-ORCH-089** — A stall watchdog MUST provide visibility only and never cancel work. Stall threshold = per-role override else the default 90 s; evaluation cadence = max(1, min(threshold/6, 5)) seconds; a warning ("child appears stalled: no model event or token for N seconds") is emitted on stall entry and at most every max(threshold, 30) seconds thereafter; a stall diagnostics issue records active tools, the last 5 tool calls, and the last model event type; a stall callback fires on each evaluation with stalled/recovered so a UI badge can update. This cadence is the run evaluating its own children while it executes them, and is not a surface re-reading persisted state to discover what a run did (REQ-SESSION-071): it survives the withdrawal of the session-polling cadences (REQ-MONITOR-287) and is not to be removed by association with them. When active tool calls exist, the condition is reported at informational level as waiting on N active tool calls instead of as a stall.
- **REQ-ORCH-090** — An unresponsive-model fallback (default 120 s, minimum 30) MUST apply only before ANY model event has been received for the child and only when the threshold is below the child timeout. On expiry the conversation is gracefully paused (force-closed if stuck) and the role's fallback model is tried once per child by rebuilding the agent and transparently re-running — the child keeps running rather than being killed. Without a configured fallback, the child simply continues waiting under the full child timeout. A timeline event and an issue record the occurrence.
- **REQ-ORCH-091** — Rate-limit and quota handling MUST distinguish generic rate-limit errors (HTTP 429 / "Too Many Requests" / rate-limit phrasing) from provider quota exhaustion (structured insufficient-quota codes) and proceed in order: (a) models known exhausted are remembered session-wide and excluded from candidates; (b) at most one same-tier automatic model fallback per child, choosing a candidate of the failing model's tier (excluding exhausted and already-attempted pairs) and transparently re-running; (c) otherwise a suspended wait: wait time = the provider's Retry-After value when present (minimum 1 s), else exponential local backoff 60·2^(attempt−1) seconds capped at 300 s; generic rate limits auto-resume after the wait, but provider-exhausted models NEVER auto-resume (they wait indefinitely for a user decision); (d) the user may resolve a wait with keep-waiting, cancel-run, or change-model; a manual model change rebuilds the agent, re-runs, and persists the override in session state for the rest of the session. A change-model resolution that cannot be applied MUST NOT be silently discarded: the wait continues on the model it already had, no override is persisted, a `model_override_rejected` issue is recorded naming the model that was asked for and why it could not be applied, and the user is told that the model was not changed and that the wait is still outstanding, so the same choice can be made again or a different one taken. Silently ignoring the choice is forbidden — a user who believes the model changed would otherwise wait indefinitely on the model that had already failed.
  > **Narrowed by [`PD-ORCH-013`](../product/directives.md#pd-orch-013), 2026-10-06.** In (d), the override persisted
  > by a manual model change stands for the rest of the session except for a pair the user later chooses explicitly for
  > the entry agent — from the run header, the inspector or a wait surface: that choice takes the override of the chosen
  > pair back, and the entry agent runs on the pair chosen. Everything else in (a) to (d) is as stated.
- **REQ-ORCH-092** — A failed model call MUST be retried according to the class of the failure: a transient failure up to the configured transient-retry count (default 1), a validation failure up to the configured validation-retry count (default 0). The delay before retry attempt n MUST be min(2.0, n) seconds. A transient failure MUST be recorded as a `transient_llm_error` issue. When the applicable retry budget is exhausted, or the failure falls into neither class and no other recovery in this section applies to it, the child MUST be marked `failed` with a report conveying that the child failed and carrying the formatted error. A failure is **transient** when the call produced no usable answer for a reason outside the content of the request and expected to differ on repetition: a connection, DNS, or TLS error; a request timeout; an HTTP status of 408, 425, 500, 502, 503, or 504; and a provider-signalled temporary overload. A failure is **validation-class** when the provider answered but the answer did not satisfy the structured-output contract asked of it: unparseable JSON, a schema violation, or a value outside a constrained enumeration. Every other failure — authentication, authorization, an HTTP 400 that is not the context-window rejection of REQ-ORCH-093, a missing or unknown model, a content-policy refusal — falls into neither class and fails the child at once. Rate-limit and quota failures, HTTP 429 included, are handled by REQ-ORCH-091 before this requirement is reached and are never spent from the transient budget; a context-window rejection is handled by REQ-ORCH-093 for the same reason.
- **REQ-ORCH-093** — A model call rejected because the conversation no longer fits the model's context MUST be recovered by condensing the conversation and retrying the call, at most twice for one call; where the condensation itself fails, the original rejection MUST be surfaced unchanged and the call fails. The same recovery MUST apply when a parent is resumed, and each parent-resume attempt MUST be bounded by the child timeout of REQ-ORCH-088. The occurrence MUST be recorded as an `llm_bad_request` issue for a child's own call and as a `parent_resume_bad_request` issue for a parent resume.
- **REQ-ORCH-094** — Pending user steering prompts for a child MUST be injected into the live conversation as clearly marked steering messages (from the watchdog loop and between execution passes), marked as delivered, and MUST reset the loop supervisor's consecutive-activation counter (steering counts as a new user instruction).
- **REQ-ORCH-095** — When a child's conversation run ends, what the child did MUST be assessed into exactly one of six categories: work was carried out; the request was answered; only bookkeeping took place; a tool call was attempted but malformed; text was produced and nothing was acted on; nothing happened at all. Only the first is accepted without further prompting. For each of the other five the child MAY be re-prompted once, and only once, in the same conversation — with one exception: on an answer-only route (REQ-ORCH-015) the answered category is accepted as success immediately. Where that single re-prompt has been used and the run still ends in the answered or text-only category, the child MAY be marked succeeded as a text-only completion. Any other non-work ending after the re-prompt MUST mark the child `failed` and MUST record an `incomplete_execution` issue naming the category assessed. The six categories have exactly these identifiers, listed in the order the prose above describes them: `work_performed`, `answered`, `bookkeeping_only`, `malformed_tool_call`, `text_only`, `no_activity`. Those strings are exact wherever a category is recorded.
- **REQ-ORCH-096** — Where the child runtime reports that it cannot make progress, the child MUST NOT be failed on that report alone: it receives one corrective message in its existing conversation and is resumed. Repeated such reports are governed by the same consecutive-activation rule as REQ-ORCH-102 — the third intervention with no intervening user instruction escalates the child per REQ-ORCH-106. A runtime error status, as distinct from a stuck report, MUST fail the child at once with no corrective attempt, and the terminal failure report MUST be built from what the transcript already holds. Exhausted stuck-recovery MUST be recorded with the existing issue kind `circuit_breaker_escalation` — the same kind REQ-ORCH-106 records — because it is the same escalation reached by the same consecutive-activation rule; its reason states that stuck-recovery was exhausted, which is what tells the two occasions apart. No further issue kind is introduced for it.
- **REQ-ORCH-097** — After each successful execution pass, per-child tool-call counters MUST be accumulated (feeding UI counters and the verifier's change detection), and cumulative token/cost snapshots MUST be replaced, not summed (summing cumulative totals would double-count).
  > **Narrowed by [`PD-ORCH-008`](../product/directives.md#pd-orch-008), 2026-10-06.** The tool-call counters are accumulated as each call completes, not after the pass; the pass's end adds only what was not counted as it completed. The snapshot replacement above is unchanged.
- **REQ-ORCH-098** — Whatever terminal state a child reaches, and whether or not its execution raised, that child MUST be fully torn down: its conversation is closed, a `child_conversation_closed` timeline event is emitted for it, any wait or pending user prompt registered against it is discarded rather than left outstanding, and it no longer counts as an active child or against its model's concurrency cap. Teardown MUST NOT cost the run its responsiveness: an interrupt requested while a child is being torn down MUST still take effect and produce the outcome of REQ-ORCH-136.

### 16. Loop Supervision (Hidden)

- **REQ-ORCH-099** — Loop supervision MUST be invisible: the supervisor is not a role, is never registered or listed, has no observable side effect when no loop is detected, and its corrective messages read as natural user instructions that never mention monitoring, detection, or injection.

  > **Narrowed by [`PD-ORCH-001`](../product/directives.md#pd-orch-001), 2026-09-16.** Every clause above still
  > holds wherever supervision is active. The directive names one case in which it is not: while
  > REQ-ORCH-153's plan gate holds the run, supervision is not active for the entry agent, so no corrective
  > message is written at all. The invisibility this requirement demands is preserved by the supervisor not
  > firing rather than by what it would have said.
- **REQ-ORCH-100** — Supervisor defaults MUST be: activation mode `independent` (alternative: `weighted`); tool-call threshold 60; message-count threshold 60; weights 0.6 (tools) / 0.4 (messages) with target score 1.0; recent-event window 24; transcript excerpt cap 8000 characters; repetition threshold 4; cycle threshold 3; enabled true. These are the canonical values: the fingerprint-based repetition and cycle triggers of REQ-ORCH-101 are the primary detection path and the raw-count thresholds are the backstop behind them. Two of the supervisor's settings are deliberately not fixed here. The classifier model MUST NOT be a model identity named by this document: its default is the `small_model` capability slot of REQ-PROVIDER-088, resolved by that requirement's own rules, so a deployment resolves the classifier from its own configured catalogue and no third party's model name is shipped as a default. The bound on one loop-classification call is likewise not this domain's: it is the registered configuration key `runtime.loop_classification_timeout`, whose value, value space, and default are REQ-CONFIG-467's. This domain states no bound of its own on a classification call and none on an activation cycle.
  > **Narrowed by [`PD-MONITOR-007`](../product/directives.md#pd-monitor-007), 2026-10-06.** The classifier's model is
  > followed through the session's override at each classification, and a pair held out of quota is not called: the
  > supervisor proceeds as on a classification that did not answer. The defaults are as stated.
- **REQ-ORCH-101** — For each observed child event, triggers MUST be evaluated in this order, and the first that fires wins: (1) repetition — the same action observed 4 times in a row fires "repeated action"; (2) cycles — a repeating sequence of 2 to 4 distinct actions, observed 3 times over, fires "repeated cycle"; (3) raw counts — in `weighted` mode a score of (tool calls / tool threshold)·0.6 + (messages / message threshold)·0.4 reaching 1.0 fires, and in `independent` mode either count reaching its own threshold fires on its own. Two actions count as the same action only when their tool name and the whole of their arguments are identical: no part of the argument content may be disregarded when comparing, so two long edits differing only near their end MUST be treated as different actions. This requirement is the product's single definition of when two agent actions count as the same action. A document that needs to decide sameness — for repetition detection, for cycle detection, or for any count of repeated work — cites this identifier and holds no rule of its own, and no rule anywhere may decide sameness from a prefix, an excerpt, a normalized rendering, or any bounded number of characters of an argument, because each of those makes the two long edits above compare equal, which this requirement forbids. Only the most recent events, up to the configured event window (default 24), are considered.

  > **Narrowed by [`PD-ORCH-001`](../product/directives.md#pd-orch-001), 2026-09-16.** The order, the triggers
  > and the sameness rule above are untouched. The directive narrows *when* they are evaluated: no event of a
  > run held at REQ-ORCH-153's plan gate is an observed event for the entry agent, because the hold withholds
  > every writing tool and the reading a plan requires trips trigger (1) on the gate's own side effect.
- **REQ-ORCH-102** — On trigger, the supervisor MUST snapshot the pending activation, increment the consecutive-activation counter, and pause the child. If the counter exceeds 2 (the third activation without an intervening user instruction), it MUST escalate regardless of classification, with an escalation signal carrying session id, activation count, and a repeated-loop reason. Otherwise an LLM classifier judges whether a loop exists over the recent transcript tail (bounded by the event window and character cap).
- **REQ-ORCH-103** — The classifier contract is JSON `{loop_detected: bool, reason, corrective_message}` where the corrective message is at most 90 words, in natural user voice, and redirects to a different concrete approach or asks for a viability assessment, drawing on the transcript (dynamic, never templated). `loop_detected = false` MUST result in an invisible no-op resume.
- **REQ-ORCH-104** — Classifier failure or timeout MUST fall back on evidence: for repetition/cycle triggers, always declare a loop with a deterministic "pause and reassess" message naming the circled tool and a path anchor; for raw-count triggers, declare a loop only from repeated identical assistant messages (last 3 normalized-equal) or ≥ 4 consecutive same-tool calls — never from counts alone; for stuck-mode triggers, ALWAYS recover with a deterministic corrective message, overriding even a classifier that declined recovery.
  > **Narrowed by [`PD-ORCH-016`](../product/directives.md#pd-orch-016), 2026-10-07.** Its clause "≥ 4 consecutive
  > same-tool calls" counts only calls that are the same action by REQ-ORCH-101's comparison — the same tool name and
  > identical whole arguments; calls of one tool with differing arguments are counts alone. The rest of the requirement
  > governs as written.
- **REQ-ORCH-105** — After every activation cycle, regardless of outcome, tool/message counters and fingerprints MUST reset to zero. The consecutive-activation counter resets only on a new user instruction — a real user message, injected steering, or a todo-correction message all count. Supervisor state MUST be strictly session-scoped, never leaking across sessions.
- **REQ-ORCH-106** — Supervisor escalation MUST surface as: the child transitioned to failed; an escalation error issue ("child aborted after repeated activations"); a report carrying the escalation signal; and, at loop level, a session abort ending the run with stop reason `agent_session_aborted`.
- **REQ-ORCH-107** — Disabling supervision via configuration MUST construct no supervisor and no model client; the runtime distinguishes "intentionally disabled" from "not yet built" and tolerates the absence; the setting round-trips through configuration files; configurations without the field deserialize as enabled; a host-level toggle propagates into the run configuration.

### 17. Child Report Artifacts and Summarization

- **REQ-ORCH-108** — Every child reaching a terminal state MUST produce a machine-readable report artifact before its parent resumes. The report is produced by a low-cost summarizing pass whose instructions are narrow enough that it can only condense what already happened and can never carry the task forward. Parents consume the report in place of replaying raw transcript, and a dependency is treated as having succeeded only once its report has been stored.
- **REQ-ORCH-109** — The report schema is defined in Data & Formats. Runner-owned fields — verification results, completion-gate decision, repair record, gate state, requirement-coverage evidence, and scope-drift findings — MUST be structurally stripped from any model-produced payload before validation, so that a summarizing model can neither write nor overwrite deterministically produced evidence, cannot assert that its own work cleared the gate, cannot invent repair attempts, and cannot conceal files it failed to account for. This enforcement is structural, not dependent on prompt compliance.
- **REQ-ORCH-110** — The report-producing pass MUST be bounded and MUST always yield a report. The transcript it is given is capped at 12000 characters in total and 2000 characters for any one event. At most two attempts are made to obtain a well-formed report, the second being told what was wrong with the first. If the second attempt is also unusable, or the pass exceeds the summary timeout (default 120 s), a report MUST still be produced without any further model call: it carries an error entry of type "summary_failure", and its summary is taken from the first 220 characters of the child's final message or, where there is none, from the tools the child used. In every report, the agent name and role MUST equal the values the run holds for that child, whatever the summarizing pass produced. The final-response field MUST be populated only where the child's last assistant message was not followed by further tool activity; otherwise that text appears as the last response instead. Key findings MUST be rendered as bullet text.
  > **Narrowed by [`PD-ORCH-007`](../product/directives.md#pd-orch-007), 2026-10-06.** The child's task, kept as the transcript's start, is exempt from the 2,000 characters per event and is kept whole within the 12,000 total; every other event keeps the 2,000.
- **REQ-ORCH-111** — A child MUST receive its report without any model call when all of the following hold: its role is `tester`; its terminal state is `succeeded`; its transcript holds at most 8 events; it made at least one tool call; and it produced a final response. The report is then built deterministically from the transcript, with status `succeeded`. That summary MUST be the child's final response itself, taken from its head and capped at 220 characters — the same cap REQ-ORCH-110 applies to its own no-model fallback — with a truncation marker stating how many characters were omitted where the response was longer. No text of the run's own composition is added, so a deterministic summary carries only what the child actually said and can never read as an assessment the run did not make.
- **REQ-ORCH-112** — The status a child report carries MUST be one of exactly `succeeded`, `partial`, `failed`, `cancelled`, and `blocked`, and the set is closed. `cancelled` is a member of it: a child settled by cancellation still produces a report (REQ-ORCH-108, REQ-ORCH-133), and that report's status is how the cancellation is read back. This requirement is the product's single definition of the child-report status vocabulary — a document that names a child report's status, carries one on the wire, or stores one alongside a materialized report cites this identifier rather than restating the set. No status outside that set is ever recorded, stored, or published: a summarizing pass that produced one is normalized by the mapping below before the report exists, so a consumer only ever reads a member. Report status maps to child terminal state as: succeeded → succeeded; partial → succeeded at the graph level (the loop, not the child ledger, decides what partial means for the task); failed → failed; cancelled → cancelled; blocked → blocked; anything else → failed. A `partial` report unblocking its dependents is deliberate and MUST NOT be treated as a defect to correct: `partial` means the child did usable work and stored a report, so a dependent may proceed on that report exactly as it would on a `succeeded` one, while the loop's task-level bookkeeping independently re-queues the task under REQ-ORCH-074. The two decisions are about different things — whether a sibling has findings worth handing on, and whether the top-level task is finished — and neither constrains the other.

### 18. Completion Classification and the Deterministic Completion Gate

- **REQ-ORCH-113** — With completion classification enabled (default true), every iteration whose report status is `succeeded` MUST be classified by exactly one small-model call into exactly one of `COMPLETE`, `NEEDS_ITERATION`, `UNCLEAR`. The call MUST be bounded by a 15 s timeout; a timeout, an error, or an answer outside those three values MUST yield `UNCLEAR`. `UNCLEAR` MUST have the same effect as `COMPLETE`, so a failed classification can never hold a run back. `NEEDS_ITERATION` MUST rewrite the report's status to `partial`, which re-queues the task under REQ-ORCH-074, and MUST set the report's message to the classifier's reason together with the original summary. Whichever of the three values results, a `completion_classified` timeline event MUST record it.
- **REQ-ORCH-114** — Classifier model resolution: small model → default summary model → the summarizer's model → skip classification entirely. Inputs are truncated (intent context to 2000 characters, summary to 1500) and open todo items are listed.
  > **Narrowed by [`PD-MONITOR-007`](../product/directives.md#pd-monitor-007), 2026-10-06.** The resolved model is
  > followed through the session's override, and a resolved model held out of quota skips classification. The truncation
  > is as stated.
- **REQ-ORCH-115** — The completion classifier MUST be skipped for reports attributed to the coordinator role (a coordinator summary describes work handed to other roles and still in flight, which the classifier would routinely read as unfinished); the todo state machine and the child graph drive the outcome instead.
- **REQ-ORCH-116** — After the completion classifier, a deterministic completion gate MUST be applied, and its decision MUST override the classifier's verdict. The decision MUST be exactly one of `passed`, `gated`, `exempt`. Where a check suite executed: a check of severity `blocking` leaves the gate unsatisfied unless its status is exactly `passed`, so `failed`, `timeout`, and `skipped` — including a check the permission policy refused — all gate; there are exactly two exceptions — status `invalid`, which never gates, and a check the user skipped under REQ-ORCH-128, which never gates either and is instead named on the decision record. A check of severity `advisory` never gates, but a failing advisory check MUST be named in the recorded decision. Where no check suite executed, the decision MUST be `exempt`; the cases are an iteration that changed no file, a check-suite configuration that is explicitly empty, a workspace in which detection recognized nothing, and a verifier that was missing or failed (REQ-ORCH-131). Where no verification evidence exists at all, the decision MUST be `exempt` with a fixed reason string that is the same for every such decision. Where the gate's decision differs from the classifier's verdict, that verdict MUST be preserved on the decision record. This requirement is the product's single definition of the completion-gate decision — the three values, the point in the sequence at which the gate is applied, what does and does not gate, and the override of the classifier's verdict. A document that needs to name a gate decision, or to state what makes a check suite block completion, cites this identifier and holds no copy of the three values.
- **REQ-ORCH-117** — A gated succeeded report MUST be rewritten to status `partial` (reusing the existing re-queue semantics; no new status vocabulary), with the decision recorded on the report and emitted as a gate-decision timeline event (warning severity when gated). Gating is on by default; when configuration turns it off the checks still execute and their evidence is still reported, but the LLM verdict is what takes effect. An iteration in which no file changed is never subject to gating.
- **REQ-ORCH-118** — Bounded repair loop: a per-task-id repair budget (default 2; 0 = report failure without retrying) resets per run and is released when a task verifies clean (a later regression starts a fresh budget). The repair decision returns either retry — with a reason of the form "Verification failed (<checks>); starting repair attempt N of M." — or escalate, rewriting the report to failed with a message of the form "Verification still failing after M repair attempt(s): <checks>. Escalating instead of retrying." Escalation deliberately does NOT set the session-abort escalation signal, so one red check can never abort the whole session.
- **REQ-ORCH-119** — Repair context MUST render each failing blocking check — name, command, status, exit code, skip reason, full-log path, output excerpt — capped at 6000 characters total (head kept, with an omission marker stating how many characters were dropped), appended to the re-queued task payload after a verification-failure marker with any previous marker blocks stripped first. Timeline events record repair scheduling (warning) and repair escalation (error), and an optional observer hook is invoked on escalation.
- **REQ-ORCH-120** — Only a re-queue that the gate itself triggers MAY consume repair budget. A re-queue caused by unfinished todo items records the gate decision but leaves the budget untouched, so that two separate budgets never contend over one task. In all other respects a repair attempt is an ordinary iteration and counts toward both the message counter and the consecutive-same-task guard.

### 19. Deterministic Verification

- **REQ-ORCH-121** — The check-suite configuration MUST be three-valued: omitted = auto-detect; an explicit empty list = verification intentionally off (a visible decision); a non-empty list = explicit configuration that wins over detection with no fallback alternatives. The resolved suite records a source in {config, detected, explicit_empty, detection_empty}; an empty detection result MUST be surfaced as "nothing recognized", never as "intentionally off". Suite resolution never raises. The resolved suite and its source are persisted in the session snapshot and in the session's run-configuration record.
- **REQ-ORCH-122** — Auto-detection MUST consider only the project markers `pyproject.toml`, `package.json`, and `Makefile`, located at the workspace root and at subproject roots, and MUST synthesize at most one check for each of the semantic roles test, typecheck, and lint; checks of role `other` are not subject to that one-per-role limit. From `pyproject.toml`: declared pytest configuration, or the presence of a `tests/` directory, yields the check `pytest -q` (blocking, role test), narrowed to the test paths the project declares where it declares any; declared mypy configuration or a `mypy.ini` yields `mypy <declared scope, else .>` (blocking, role typecheck); declared ruff configuration or a `ruff.toml` yields `ruff check .` (advisory, role lint). From `package.json`, only the scripts named `test`, `typecheck`, and `lint` are interpreted, invoked as `npm test` for `test` and `npm run <script>` for the others, with `test` and `typecheck` blocking and `lint` advisory. From a `Makefile`, only the targets named `test`, `typecheck`, and `lint` are interpreted, invoked as `make <target>`, with the same severities; a target is recognized as a target name followed by `:` at the start of a line, and pattern rules and variable assignments are not targets. Build scripts and build targets MUST NOT be synthesized into checks. Detection MUST NOT fail the run: a marker that cannot be read or cannot be parsed contributes nothing. Every recognized marker MUST be recorded in the run-configuration record, including a marker whose implied check was dropped by the one-per-role limit. Where a role has more than one candidate, the order of preference is user-configured, then declared by the project (a script or a target), then synthesized; where the preferred command cannot be launched at all, the next candidate of the same role is used. A check detected in a subproject MUST have `:subdir` appended to its name and MUST carry a working directory expressed relative to the workspace root; an absolute working directory, or one resolving outside the workspace, MUST be rejected as a configuration error when the configuration is loaded. Subproject roots MUST be located by scanning for those same three markers to a maximum depth of 3 directory levels below the workspace root, skipping any directory whose name begins with `.`, any directory the workspace's version-control ignore rules exclude, and the conventional dependency and output directories `node_modules`, `venv`, `.venv`, `dist`, `build`, and `target`. At most 25 subproject roots MUST be considered, taken in ascending lexicographic order of their workspace-relative path; where more exist, detection stops at that many and records in the run-configuration record that it did, so a large monorepo degrades visibly rather than silently. A command "cannot be launched" when it never became a running process — the executable was not found, the operating system refused permission, the working directory does not exist, or the run's permission policy refused it — and only then; a command that started and exited with any status, zero or not, has been launched, and its result is recorded under REQ-ORCH-123 rather than falling through to the next candidate of the same role.
- **REQ-ORCH-123** — The check suite MUST run at most once per iteration, and only where that iteration changed at least one file in the workspace. The changed-file set MUST be the union of two independently gathered sources: the files observed to be modified by the iteration's tool calls, and the files the iteration's report declares as edited or created — a file present in only one of the two still counts. Where that union is empty, no check runs and a `verifier_run_skipped` timeline event records the reason. Checks MUST run one at a time, through the same command-execution path the run uses for any other command, which enforces each check's deadline itself rather than trusting the command to exit, applies the run's permission policy, and applies its sandboxing. A check whose command exits 0 while its output reports failing tests MUST be recorded `failed`, not `passed`. A check the permission policy refuses MUST be recorded `skipped`, naming the rule that refused it, and MUST NEVER be recorded `passed`. Check status MUST be one of `passed`, `failed`, `timeout`, `skipped`, `invalid`. The full output of every check MUST be retained in the session's durable record and MUST be reachable in full from that check's own record, by a path recorded with it, after the run that produced it has ended and without that run existing. Check output is held as a file on disk referenced from the record rather than kept inside it, so that an output of any size is readable as an ordinary file; where within the session's own storage those files live is fixed by the domain that owns the session's layout (REQ-SESSION-001, REQ-SESSION-002) and is not fixed here. The zero-exit rule applies to checks of role `test` and to no other role, and recognition MUST be by an explicit declared pattern and never by a heuristic: a check MAY declare a `failure_pattern` regular expression, and where one is declared and matches the check's combined standard output and standard error, the check is recorded `failed` whatever its exit status. A check declaring no pattern is recorded on its exit status alone. The synthesized `pytest -q` check of REQ-ORCH-122 MUST declare a pattern matching pytest's own failure-summary line; the synthesized `npm test` and `make test` checks MUST declare none, because what those commands print is decided by the project rather than by this product. A pattern that fails to compile is a load-time configuration error, reported as REQ-ORCH-143 reports a duplicate check name. The five-value check-status vocabulary named here is the product's single definition of a check's outcome, and it is closed: a document that renders, transports, or maps a check outcome cites this identifier rather than restating the values, and a rendering or mapping of check outcomes MUST be total over all five.
- **REQ-ORCH-124** — Verification budgets MUST be a per-check timeout (default 600 s) and a whole-suite timeout (default 900 s; null means unbounded). A check's effective timeout MUST be the smaller of its own timeout and the suite budget still remaining. A check for which no suite budget remained and which therefore never started MUST be recorded `skipped`; where that check is blocking, it leaves the completion gate unsatisfied on exactly the terms of REQ-ORCH-116, since it never answered its question. The calibration probe has its own timeout (default 30 s) that is not drawn from the suite budget.
- **REQ-ORCH-125** — The verification gate MUST be in exactly one of the lifecycle states `absent`, `pending`, `calibrated`, `stale`, and that state MUST be readable from `<workspace>/.rotaris/verifier.state.json`, a file the tooling writes and maintains and that users are not expected to hand-edit; the editable check suite stays in the user configuration. The state MUST become `stale` when the workspace's recognized project markers change — one added, one removed, or one whose content changed — and MUST NOT become stale for an ordinary source edit. A conventional test directory (`tests/`, per REQ-ORCH-122) MUST count by its presence alone, so adding or editing a test file does not make the state stale. A workspace with neither a recognized marker nor a test directory MUST be in state `absent`. A calibration probe MUST yield exactly one of `verified`, `empty`, `unavailable`, `undecidable`; `empty` is permitted only for a check of role test whose output positively reports that it collected nothing; a probe that was refused by policy, or whose result could not be read, MUST be `undecidable` and MUST leave the gate state unchanged. A `verifier_gate_calibrated` timeline event MUST be emitted when, and only when, at least one probe actually ran.
- **REQ-ORCH-126** — Gate authoring: on the transition from no recognized markers to markers present, a dedicated gate-authoring role (`gatekeeper`, reachable only through the gate-authoring path and never as an ordinary delegation target) MUST author the suite in a detached task beside the loop — never on the iteration's critical path — with the result binding the next iteration (by invalidating the cached suite). Authoring is on by default; when off, writes route to approval-gated proposals instead. The gate's current state travels on every child report, and a `pending` state means "code exists, nothing was verified". All writes go through a single write authority; the probe and gate-write capabilities are internal to the gate-authoring role and MUST NOT be grantable to any other role by configuration, with write authority evaluated at write time. Gate-weakening operations — dropping a role, lowering severity, emptying the suite — are outside all automatic authority and become improvement proposals deduplicated by content. An `invalid` check is repaired deterministically while the run continues — detection and probing are redone, preserving the check's role and severity — at most once for any given role within a session and without invoking a model. Timeline events record gate writes and skipped authoring.
- **REQ-ORCH-127** — Live verification visibility MUST include timeline events for suite start (size and source), each check start (index/total, command, deadline, severity), each check finish (status, exit code, duration, outcome kind, log path; warning severity on a blocking failure), and suite completion or skip — each mirrored by observer hooks for hosts.
- **REQ-ORCH-128** — While a check suite is running, the user MUST be able to skip the check currently executing; invoked at any other time the control MUST do nothing and report no error, so a host may offer it unconditionally. Skipping MUST interrupt the running command and every process it started, by delivering the terminal interrupt signal to the process group. A command that ignores that signal and keeps running MUST be terminated after a grace period of 5 seconds, and its terminal session torn down with it. A check the user skipped MUST be recorded with status `skipped` and never `failed`, MUST be marked as user-initiated, and MUST NOT be counted or reported as a failing check. A user-initiated skip MUST be exempt from the completion gate: it does not leave the gate unsatisfied under REQ-ORCH-116, and because it triggers no gate-driven re-queue it consumes no repair budget under REQ-ORCH-118 and REQ-ORCH-120. The gate decision MUST nonetheless name every user-skipped check, so the record shows exactly which question the user chose not to have answered. The exemption belongs to a skip the user asked for and to nothing else: a check skipped for any other reason — a permission refusal or an exhausted suite budget included — gates on exactly the terms of REQ-ORCH-116.
- **REQ-ORCH-129** — Single execution authority: the acceptance role never re-runs the bound suite. The delegation layer injects into the acceptance role's payload a verification-evidence block whose heading states that the suite has already executed and must not be executed again, containing a per-check table (check, command, status, exit code, full-output path), an explicit list of checks that did not answer their question, and an instruction that any additionally needed command should name the missing role (feeding a gate-update proposal) rather than licensing a suite re-run. An empty evidence block is the fallback: the acceptance role runs commands itself and discloses that it did. The current iteration's evidence is published for host consumption.
- **REQ-ORCH-130** — Requirement-coverage evidence and scope-drift findings, when the workspace has a requirement store and files changed, MUST attach to the report as runner-owned fields that report but never gate, with a timeline event (warning severity when gaps or drift exist).
- **REQ-ORCH-131** — The loop MUST tolerate a missing or failed verifier entirely: no evidence → exempt gate; a broken verifier can never abort an iteration.

### 20. Cancellation and Shutdown

- **REQ-ORCH-132** — Cancelling a run MUST stop every descendant: the stop request sets the stop flag, releases any message-limit pause gate, cancels all pending question prompts and permission approvals (approvals fail safe as denied), gracefully pauses every active conversation (a forced stop additionally closes them), and cancels in-flight work thread-safely — a forced stop performs a second sweep for work created during the first.
- **REQ-ORCH-133** — Bulk child cancellation MUST cancel all active children, wait up to 5 s for them to settle, then mark any still-non-terminal record cancelled with a report stating it was cancelled during parent failure cleanup plus a force-cancelled warning issue. Single user-initiated cancellation MUST cancel the one child, wait up to 5 s, mark it cancelled with a report stating the user cancelled it, emit a user-cancelled timeline event, and return false for unknown or already-terminal children.
- **REQ-ORCH-134** — Graceful pause MUST honor a tool deadline (default 30 s, valid range 5–120): in-flight tool calls are awaited before force-closing. The pause performed to inject a parent notification MUST never force-close (the parent must keep its connections alive to be resumed). Pause and close operations MUST never block the run's event handling (a blocking close must not freeze interrupt handling). Beyond the conversation-lifecycle facts this domain states — the tool deadline and its bounds, the no-force-close rule for a notification pause, the non-blocking rule above, the `child_conversation_closed` event and discarded waits of REQ-ORCH-098, and the context-overflow recovery of REQ-ORCH-093 — the threading model, the shape of streamed model events, and any retry below the classification of REQ-ORCH-092 are implementation design decisions that this document does not constrain and that no conformance claim here depends on.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005), 2026-09-27 (revision 3).** A pause does not wait on a tool call suspended on a person: that call is cut off at once and recorded as interrupted; every other in-flight call is still awaited within the deadline.
- **REQ-ORCH-135** — An iteration cancelled mid-run MUST close its own record as cancelled with a report stating the run was cancelled before the agent finished, then sweep the ledger; bookkeeping errors during this cleanup are swallowed so they never replace the original exception. An iteration that raises closes its record as failed with a report stating it ended with an unhandled error.
  > **Narrowed by [`PD-ORCH-005`](../product/directives.md#pd-orch-005) revision 4, 2026-09-28.** Clauses 2, 3 and
  > 15: an iteration a pause, a stop or a quit leaves with an agent unfinished stays open, and the continue resumes
  > it. This requirement governs the explicit cancel, a run the product ends on its own account, and a rest that
  > finds nothing unfinished.
- **REQ-ORCH-136** — A user-requested interrupt yields stop reason `user_cancelled`, and the terminal run result that stop reason carries is REQ-MONITOR-301's to fix. A child cancelled because the run concluded while it was in flight receives a diagnostic explaining exactly that.

### 21. Post-Run Improvement Pass

- **REQ-ORCH-137** — Once a task run has reached a terminal state, an improvement-collection pass MUST be handed to the host to run away from the run's own critical path, so that the run's duration, stop reason, and terminal status are the same whether that pass runs, is slow, or fails. It MUST be given a snapshot of the evidence it needs — the progress record, the todo state, the transcript events, the child reports, up to 5 improvement artifacts produced by earlier sessions in the same workspace, and the verification-gate evidence — and that snapshot MUST NOT change afterwards, whatever the run or any later run does to the originals. The pass MUST be skipped when the run is not a task run, when the collector is disabled (it is enabled by default), when the run has no durable session record to draw that snapshot from, or when the stop reason is one of `user_cancelled`, `agent_session_aborted`, or `application_shutdown` (each a member of the closed set of REQ-MONITOR-301). That three-token skip list is the single definition of when an improvement pass is not collected, and a document that needs to name it cites this identifier rather than restating it. `application_shutdown` is on the list for the same reason as the other two: a run ended by the application being asked to quit produced no evidence about how the work went, only about when it was cut short, so a pass over it would learn from the shutdown rather than from the run. It MUST be bounded by its own timeout (default 60 s), and any failure, that timeout included, MUST yield an empty improvement artifact rather than an error. The run-type vocabulary is exactly two values. A `task` run carries a top-level user task through the iteration loop, which is every run the rest of this document describes. A `maintenance` run is one the product starts for its own upkeep and which carries no user task; the detached gate-authoring task of REQ-ORCH-126 is the only one this document defines. Only a `task` run performs the improvement pass.

### 22. Observability

- **REQ-ORCH-138** — A host MUST be able to observe a run without taking on all of it: it may subscribe to any subset of the observation points this domain publishes — session start and end, iteration start and end, child lifecycle, todo state changes, verification events, repair escalation, message-limit pause, token metrics — and MUST NOT be required to supply the remainder. An exception raised by anything a host supplies MUST NOT change the run's outcome, stop the run, or be reported as a run failure: the run continues and reaches the same stop reason and terminal status it would have reached with nothing observing it at all.
- **REQ-ORCH-139** — A run MUST record, in the session diagnostics, timeline events named only from the timeline-event vocabulary and issues named only from the issue-kind vocabulary set out in Data & Formats, and MUST NOT use any name outside those vocabularies for them. Those diagnostics form part of the session's durable record and MUST remain readable after the run has ended, whether or not the session is live and whether or not the run that produced them still exists. A user MUST also be able to obtain them outside this application: the timeline and the issue record are among the records the session domain's export reaches (REQ-SESSION-199, offered as an action by REQ-SESSION-191), so a reader holding only what was exported, on a machine carrying none of this product's code, can read every timeline event and every issue this domain requires a run to record, with the names fixed here intact. Reading them — from the store or from an export — is never a way to follow a run as it happens (REQ-SESSION-071): the export is a user-initiated action producing a file, and it is not a second channel onto a live run.
  > **Extended by [`PD-ORCH-014`](../product/directives.md#pd-orch-014), 2026-10-06.** The vocabularies this requirement
  > closes the names to also hold the words that directive adds to domain 01's timeline list and issue kinds, the chat
  > domain's timeline words ([`PD-CHAT-009`](../product/directives.md#pd-chat-009)) and domain 05's two presence words
  > ([`PD-TOOLS-011`](../product/directives.md#pd-tools-011)). The closure itself is unchanged and still governs in full.
- **REQ-ORCH-140** — Every child's conversation transcript MUST form part of the run's own durable record, written by the run itself and not dependent on any host: a run observed by no host, and a run whose host observer raises, MUST leave transcripts that are identical and equally complete, and every event of every child's conversation MUST be recoverable from that record after the run has ended. Nothing about a host — its presence, its absence, the subset of observation points it subscribed to (REQ-ORCH-138), or an exception it raised — MUST change which events are recorded or how complete the record is. Where those transcripts are held is fixed by the domain that owns the session's persistence (REQ-SESSION-001, REQ-SESSION-198) and is not fixed here.
- **REQ-ORCH-141** — Per-child tool-call timing MUST be recorded as diagnostics (call id, status, elapsed milliseconds, arguments/result, outcome kind, exit code), and replayed tool-call ids MUST be deduplicated.
- **REQ-ORCH-142** — The run's own usage aggregate is authoritative for per-iteration token/cost accounting; provider-reported totals are cumulative and MUST be replaced, never summed. Per-agent token, cost, and last-prompt-token snapshots feed the host UI.
- **REQ-ORCH-155** — Every surface this domain requires a user to be shown MUST be reachable in the desktop interface, within the seven primary views of REQ-SHELL-023 and using the one action vocabulary of REQ-SHELL-048. Those surfaces are: the intent status of REQ-ORCH-014; the plan gate of REQ-ORCH-153; the live child graph with each child's state from REQ-ORCH-040 and its role, canonical name, and task id; the model-slot and rate-limit waits of REQ-ORCH-050 and REQ-ORCH-091 with their three resolutions; the message-limit dialog of REQ-ORCH-086; verification progress under REQ-ORCH-127 together with the skip control of REQ-ORCH-128; repair scheduling and repair escalation under REQ-ORCH-119; and the run-progress summary of REQ-ORCH-082. What each surface MUST convey is fixed by the requirement that names it and is normative. Its layout, typography, placement, and animation are not fixed by this domain and are governed by the desktop shell, including REQ-SHELL-149 (state never conveyed by colour alone), REQ-SHELL-135 (reduced motion), and REQ-SHELL-022 (every control reachable and fully labelled at the minimum window size). Each of these surfaces MUST reflect a state change the run has recorded within 100 ms of the run recording it, **at the 95th percentile**. That figure is a percentile and not a bound on every sample: a build meets this requirement when the 95th percentile of the interval, measured from the run recording a change to the surface showing it, is within 100 ms, and a single update that took longer is not by itself non-conformant. The percentile is stated rather than left to be inferred, so that the figure here and the one REQ-MONITOR-222 states are read the same way.

### 23. Configuration Surface

- **REQ-ORCH-143** — All defaults in the Data & Formats configuration table MUST hold, and MUST be verified by configuration-default tests. Additional validation: duplicate check names are a load-time configuration error; the graceful-pause tool deadline is bounded to [5, 120] seconds; the unresponsive-model threshold has a floor of 30 seconds.
- **REQ-ORCH-144** — Per-role overrides MUST include: a per-role stall threshold (for slow reasoning models); a fallback model (used at most once per child on hard timeout or unresponsive model); a thinking toggle; a coordination-only tool profile (delegation and todo maintenance permitted; reading, editing, and execution withheld); a read-only profile; an allowed-delegates list; a suppress-sibling-context flag; an artifact-publishing flag; a summarizer-model override; and a permission mode.
- **REQ-ORCH-145** — Per-model settings MUST include: a per-model parallelism cap (REQ-ORCH-050); a per-model HTTP timeout overriding the runtime model timeout; and a per-model retry count overriding the provider default of 5.
- **REQ-ORCH-146** — For a provider that ships its own native agentic loop, a runtime toggle (default enabled) MUST run children on that provider under the native loop; disabling it falls back to a degraded single-shot mode that discards tool use and streaming. A deprecated intent-validation toggle (default false) is retained for configuration compatibility, superseded by completion classification.
- **REQ-ORCH-156** — Every duration stated in this domain is a wall-clock duration measured against a monotonic clock from the start point the requirement stating it names, and every one of them bounds only what this run controls. A budget fixes when the run takes its stated action, not the total time that may elapse: where the action can only be taken at a boundary it is taken at the first boundary at or after the budget expires, so a long iteration may overshoot the time limit exactly as REQ-ORCH-069 already states, and a budget spent inside a provider call is measured from the moment the run issued the call rather than from when the provider began work. Where two budgets bound the same activity the smaller governs and expiry of the smaller never resets the larger (REQ-ORCH-124). Conformance to every duration in this domain MUST be demonstrable with a controlled clock, so no conformance claim here depends on real provider latency or on the wall-clock cost of a live model call.

### 24. Persistence

- **REQ-ORCH-147** — The session records and workspace-level files in Data & Formats MUST be produced as described. The session records this domain names are part of the session's durable record, whose form, layout, and store are the session-persistence domain's to fix (REQ-SESSION-001); this domain names what must be held and holds no copy of where or how. A session's persisted state MUST durably hold at least: the resolved check suite, the message count and active message limit, the run intent, the todo state, the loop progress record, and improvement artifact ids.
- **REQ-ORCH-148** — The gate-state metadata file is tool-managed and never hand-authored; the editable gate lives in the user configuration (REQ-ORCH-125).
- **REQ-ORCH-149** — The session artifact store MUST be session-scoped, hydrated from the session's durable record where the session has one and held only in memory where it has none, shared across iterations, and the source of the auto-injected sibling summaries in child payloads. An artifact's body is held as a file on disk and referenced from the record rather than kept inside it, so a body of any size is readable as an ordinary file while its identity, its ownership, and its ordering come from the record; where those bodies live is the session-persistence domain's to fix (REQ-SESSION-001, REQ-SESSION-002) and is not fixed here.

## Data & Formats

All formats below are externally observable (in the session's durable record, on disk, in transcripts, in tool observations, or in host events). Exact wording of model-facing guidance messages may vary provided the specified informational content, ordering, and identifiers are preserved; enum values, statuses, stop reasons, event names, issue kinds, configuration keys, and file paths are exact.

### Task identifiers

- Task id: `bg_` followed by 8 lowercase hex characters; regex `^bg_[0-9a-f]{8}$`; unique per session; assigned at spawn for every child (REQ-ORCH-036).

### Stop reasons and run statuses

- Stop reasons: the closed set is fixed by REQ-MONITOR-301; this document holds no copy of it, mints no stop-reason string of its own, and states no mapping from a stop reason onto a run status (REQ-ORCH-069). ### Session records

Where a session's records are held, and in what form, is fixed by the session-persistence domain (REQ-SESSION-001) and is not restated here. What this domain requires a session to hold durably, and what each guarantee is:

- **Each child's conversation transcript** — complete, identical whether or not a host observed the run, and every event of it recoverable after the run has ended (REQ-ORCH-140).
- **Each check's full output** — retained as a file on disk, reachable in full from that check's own record by a path recorded with it (REQ-ORCH-123). The `output_path` a published verification event carries is that path.
- **The per-session log** at the configured session log level, which stays a file readable without this product (REQ-SESSION-142).
- **Memory diagnostics**, when enabled.
- **The run-configuration record** — the resolved check suite with its source, and the playbook-cell audit payload (REQ-ORCH-027, REQ-ORCH-121, REQ-SESSION-138).
- **The message-limit pause** — carried as the session's persisted execution status `paused_message_limit` together with the count reached and the limit in force, and not as a separate marker of any kind (REQ-ORCH-087, REQ-SESSION-107, REQ-SESSION-110).
- **The session's persisted state**, holding at least the fields REQ-ORCH-147 names.
- **The timeline and the issue record**, in the vocabularies below — readable after the run ends, and obtainable outside the application through the export of REQ-SESSION-191, so the names fixed here stay legible to a reader carrying none of this product's code (REQ-ORCH-139).
- **Report artifacts** — bodies on disk, identity and ordering from the record (REQ-ORCH-149).

### Workspace-level files

These two are files in the workspace and stay files: the playbook overrides because a user authors them, and the gate-state record because it belongs to the workspace rather than to any session and travels with the workspace when the workspace is moved or copied.

- `<workspace>/.rotaris/verifier.state.json` — gate lifecycle metadata: state (`absent|pending|calibrated|stale`), marker content fingerprint, probe records. Tool-managed and never hand-authored (REQ-ORCH-125, REQ-ORCH-148).
- `<workspace>/.rotaris/playbooks/` — workspace-scope playbook overrides (field-wise deep merge over the global scope; may re-word variants only).
- The check suite itself lives in the user configuration (three-valued: omitted / empty list / explicit list) with per-check `timeout`, `severity` (`blocking|advisory`), `role` (`test|typecheck|lint|other`), workspace-relative `cwd`, and an optional `failure_pattern` regular expression honored for role `test` only (REQ-ORCH-123).
