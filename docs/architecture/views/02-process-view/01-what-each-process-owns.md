# Process view — five processes and what crosses each boundary — What each process owns

Part 1 of 8 of [the process view](../02-process-view.md), which indexes every part.

## What each process owns

| Process | Owns | Never does |
|---|---|---|
| **main** | window lifecycle and the close guard — since 2026-09-12 **every main window is built, tracked, and coordinated through `MainWindows`** (`apps/desktop/src/main/main-windows.ts`, executing ADR-0055 consequence 6's two entrances and ADR-0048's registry over main windows with Electron and in-memory adapter seams) and lives in a private registry keyed by `webContents` id, so several main windows of the one instance are ordinary rather than exceptional (REQ-STARTUP-161) and every workspace-scoped command is answered for the window that sent it (REQ-SHELL-020); **startup workspace resolution** (REQ-SHELL-010's three-way precedence: an explicitly selected folder, else a remembered one that still names a directory, else the working directory with a chooser scheduled), the one **deferred first-paint offer** (REQ-SHELL-011's 650 ms, per window and abandoned unshown once the question has been answered) and the **gated replacement** (REQ-SHELL-017 – REQ-SHELL-021: build, open the service, show, await the old window's own close, then persist) are main's alone; `workspace/lastOpened` is written by main and by nothing else — the key is registered in `platform`'s `PREFERENCE_KEYS` and deliberately absent from `PREFERENCE_COMMAND_KEYS`, which is an allow-list, so no renderer can read or write it over `prefs.get/set`; **application modality across a window family** (ADR-0048, Part W: `setFamilyModal` disables every persona window while the main window holds an application-modal surface, restores them when it closes, creates a new one disabled while one is up, and restores the family on the main renderer's navigation, reload or crash); **the persona-window registry** (ADR-0048, Part R: one window per persona, hidden on close, destroyed with the main window and on a new session; `main/windows.ts`); **the terminal-window registry** (ADR-0021's and ADR-0047's window, Part AL′: ONE per main window, 900×620, DESTROYED on close and rebuilt on the next open — the deliberate difference from the persona window, ADR-0047 consequence 3 — shown without focus when opened automatically under `interface/terminalPopout` (REQ-SHELL-109, the key REQ-CONFIG-405 registers; until 2026-10-14 `terminal/autoOpen`, carried over once), closed and reopened without focus when the main window's renderer reports a change of the followed session, closed and discarded when a session starts from none, gone with its main window; `TerminalWindows` in `main/windows.ts`, the five `window.*` commands below); the per-window approval **dialog queue** and the pause window; **the authentication recovery dialog** (REQ-NOTIFY-072..075/079/080, the 401 note's part C, 2026-10-02: `main/auth-recovery.ts` over the classifier `main/failure-class.ts` — a failed run's failure matched in REQ-NOTIFY-060's order; for the authentication class main asks the run host `session.authRecovery`, raises the class's error notice and opens ONE modal window 560 px wide over the main window following the session, role `auth-recovery`, its payload read by `authRecovery.payload`; Retry is relayed as `session.authRestart`; Cancel closes it and nothing else); the single current notice; the `UpdateRelay` (sequence-preserving fan-out of the run host's publications to subscribed windows); theme and preferences (ADR-0042); the instance claim; forking and shutting down the two child kinds; **the credential store, the provider catalogue, sign-in, discovery and the snapshot** (ADR-0029/0030, `packages/providers`); the verification seams under `ROTARIS_CAPTURE_PNG` — **compiled in only where `__ROTARIS_SEAMS__` is true** (2026-09-11), and since 2026-09-17 a module of their own rather than six hundred lines inside `main()`: `apps/desktop/src/main/capture/` holds the step grammar and the host main gives it (`host.ts`, with a test over the grammar), the part a shipped build still answers (`probe.ts` — the typed prompt and the photograph that ends the launch), the scriptable half (`seams.ts`) and the theme proof's capture pass (`theme-proof.ts`). The last two are reached by a **dynamic import inside `if (__ROTARIS_SEAMS__)`**: `scripts/package.mjs` builds with `ROTARIS_BUILD=package`, which makes the flag false, rollup removes the branch, and the chunk is then unreferenced and never emitted — leaving only the three the packaged probe itself drives (`_PNG`, `_PROMPT`, `_AFTER_MS`). **Since 2026-10-13 the approval dialog's scripted answer is read under the flag too** (`ROTARIS_CAPTURE_APPROVAL`, `_APPROVAL_MS`, `ROTARIS_CAPTURE_DIALOG_PNG`, parsed by `capture/approval-answers.ts` into one answer per dialog by the tool it asks for, `none` leaving it to its timeout): until then `presentNext` read it behind the run-time `capturing` test alone and a packaged build kept it (`docs/defects/fixed/the-approval-dialogs-scripted-answer-survives-a-packaged-build.md`); the seam check names it. **Since 2026-10-14 every other seam main reads is behind the flag as well, on the read's own line** — the hook review's press, the pause window's and the message boxes' answers, the backup, restore, export, directory and skill-file choosers' paths, the provider dialog's fill, the external-link swallow, the stale question answer, the subscription's delay and hold, the theme, the scale and the network log, and the two not named `ROTARIS_CAPTURE_*`, the rows proof's renderer role (`ROTARIS_ROWS_PROOF`) and the initialization proof's registered task (`ROTARIS_INIT_TEST_TASK`) (`docs/defects/fixed/a-packaged-build-keeps-capture-seams-that-answer-mains-dialogs.md`); `capturing` alone decides nothing scriptable, the seam check's two lists live in `scripts/lib/seam-check.mjs`, and `main/capture/seam-reads.test.ts` and `scripts/lib/seam-check.test.ts` hold the source and the list to that. **Since 2026-10-14 (fin44) the packaged probe answers its three alone**: its `_WAIT`, `_WAIT_MS`, `_END_VIEW`, `_END_VIEW_MS`, `_PROBE` and `_PROMPT_MS` are read behind the flag in `capture/probe.ts`, and the run host's and the workspace service's `_SKILLS_HOME` and `_INSTRUCTIONS_HOME` likewise, so a packaged build always discovers skills and instruction files under the user's own home; the seam check names all eight, and `seam-check.test.ts` fails a capture variable read off the flag in any module a packaged build keeps, the probe's three aside (`docs/defects/fixed/a-packaged-build-still-answers-capture-variables-beyond-the-probes-three.md`). The grip drag (`ROTARIS_CAPTURE_GRIP_DRAG`, fin42) is a seam of `capture/seams.ts`: a real pointer drag of an element's resize grip, compiled out with the rest. **Since 2026-09-27 the run host and the workspace service read seams under the same flag too**: `ROTARIS_CAPTURE_INSTRUCTIONS_MACHINE` in both (the machine-wide instruction base's directory) and `ROTARIS_CAPTURE_MODEL_REQUESTS` in the run host (the scripted client's call record), and since 2026-10-13 (fin42, N51) `ROTARIS_CAPTURE_THROW_ON_ABORT` in the run host (`run-host/throw-on-abort.ts`: each named tool's executor, native or MCP, rejects once its call's signal aborts, which is how `mcp-proof`'s `cancel-throw` launch reaches PD-TOOLS-013 revision 2 (a), the gate's catch, in the built app; the variable's name is written in `host.ts` alone, so the wrapper a packaged build keeps is handed no name and wraps nothing). A packaged build compiles each out, and `scripts/package.mjs` refuses one in which any survives. The gate is build-time and not run-time on purpose: an environment variable cannot turn the seams back on in a binary built without them, and the build asserts it — the deliberately un-numbered **seam check**, which since the same date reads **every emitted file of the main section** rather than `index.js` alone, because a chunk is exactly the shape that surface could come back in; **every renderer command, in a module of its own** (2026-09-17): `apps/desktop/src/main/commands/` holds one facet per family — `dialogs`, `providers`, `session`, `hooks`, `mcp`, `initialization`, `skills`, `shell`, `git`, `checkpoints`, `library`, `improvements`, `config`, `requirements`, `windows`, `workspace` — beside `context.ts`, which names `CommandContext` (the inventory main hands them, which used to be the closure `runCommand` was written inside) and `CommandHandlers` (**total** over `CommandRequest['kind']`, so a kind the contract declares and no facet answers fails to compile rather than answering `command.unimplemented` at run time). `runCommand` itself is three moves — resolve the window the command was raised for, read the request, call the handler the table names — and holds no case; **the window rule is `MainWindows.forCommand(senderId)`** (2026-10-03): a main window answers for itself, a persona or terminal window for the main window that owns it (`ownerOfAuxiliary`, ADR-0048 B), any other sender (an approval dialog, the driver speaking for no window) for the active window — until then a non-main sender fell back to the active window, so with two main windows on two workspaces a persona window's `config.read` and `artifacts.body`/`artifacts.save` and a terminal window's `session.list` answered for the wrong workspace (REQ-MONITOR-069, REQ-STARTUP-163); handlers that key on the sender itself (`session.subscribe`'s relay and follow) are untouched; a facet declares the slice of the context it uses, which is what lets `commands/mcp.test.ts` drive real handlers with a plain object where the run host is; **the checkpoint gate** moved with its commands (`commands/checkpoints.ts`), main keeping only the holder the quit path waits on (REQ-GIT-101); **the driver seam under `ROTARIS_DRIVER`** (2026-09-11, verification only, `main/driver.ts`: a loopback listener on an ephemeral port, minted with a per-launch secret written to the endpoint file the variable names, answering newline-delimited JSON — `waitFor`, `click` (since 2026-10-06 its `settle` presses only once the match has held one box across two of the renderer's frames and is the element at its own centre, then reads what the press met and fails one that met something else, `docs/defects/fixed/driver-proof-clicks-pop-out-at-a-box-the-notice-banner-moves.md`), `type`, `chord`, `inspect`, `probe`, `eval`, `screenshot` (since 2026-09-29 after four frames of the renderer's, so a shot is never the frame before a change), `resize`, `closeWindow` (since 2026-10-14 the host's close of the window, `BrowserWindow.close()`, guarded as a person's close: how `exit-trace-proof`'s `hang-close` closes a window whose renderer is hung, PD-SHELL-010), `quit` (since 2026-09-29 the application's quit, `app.quit()`, unless it names the immediate exit), and `command`, which is relayed to main's own `runCommand` rather than around it; since 2026-09-29 every op may act on a persona window, the approval dialog or the terminal window as well as a main window, named by role (`persona:<persona>`, `approval`, `terminal`, and since 2026-10-02 `auth-recovery`) through `useWindow` or its own `window`, main handing the driver each main window's auxiliary windows (`DriverDeps.auxiliary`). Nothing listens when the variable is unset; no renderer, run host or workspace service message is involved, and no product surface can reach it); **the updater** (ADR-0054's bespoke main-process updater, first-release-plan.md §4.6, built 2026-09-28: `apps/desktop/src/main/updater/` — `classify.ts` decides the installation flavour ONCE from the artifact the launch started from (REQ-STARTUP-106: the `APPIMAGE` variable first, then whether the build is packaged at all, then the macOS bundle, then on Windows the installer's `InstallDir` against the artifact and the launcher's `ROTARIS_PORTABLE_ARTIFACT` — both handed to it by the first statement of main's body, which takes them out of main's own environment, see *The environment a child is started with* below; a source-tree or development launch is not updatable and issues no request), `feed.ts` the one endpoint, the offer rule, the summary, `keys.ts` the compiled-in key set — EMPTY until O-2 — and the Ed25519 signature format, `install.ts` REQ-STARTUP-122's strict sequence with the signature verified before the manifest is parsed and before any asset is fetched, `download.ts` the 1 MiB chunks, `strategies.ts` the portable rename-aside and the installer hand-off (the dmg and AppImage strategies wait for `PD-STARTUP-001`'s withdrawal), `updater.ts` the one held offer, the one operation in flight and the notice it lives in, `successor.ts` main's wait for the restart's successor (it settles once: passed, not started, or refused a record pass — REQ-STARTUP-121), `electron.ts` the one file that touches `net.fetch`, the disk, `reg.exe` and a process. **The environment a child is started with (REQ-STARTUP-106/147; ADR-0054 "The updater", item 6; 2026-09-28).** No
child is handed an environment of its own making: `utilityProcess.fork` gives the run host and each workspace service
main's environment as it stands when they are forked, and the run host hands its own `process.env` on — to the
confinement service that starts tools and terminals, to the hook engine (REQ-HOOKS-032), to the MCP transport and so to
the code-intelligence branch; main's detached spawns (the update successor, the installer hand-off) inherit main's
too. So what main's environment holds after its first statement is what every child of the product receives, and that
statement removes the two variables that name the artifact this launch started from — `APPIMAGE` and
`ROTARIS_PORTABLE_ARTIFACT` — after reading them for the updater's classification (`takeArtifactVariables`,
`packages/platform/src/artifact-environment.ts`). Nothing else is removed. A Rotaris started from inside a Rotaris
terminal therefore classifies from its own launch alone. Whether the specification says so is **OQ-90**.
