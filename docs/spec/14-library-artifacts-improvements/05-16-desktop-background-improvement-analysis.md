# Library, Artifacts, and Improvement Proposals — 16. Desktop background improvement analysis

Part 5 of 7 of [domain 14](../14-library-artifacts-improvements.md), which indexes every part. Defines REQ-LIBRARY-122 – REQ-LIBRARY-164.

### 16. Desktop background improvement analysis

**REQ-LIBRARY-122** — The desktop contract for background analysis is as follows. The completed run's terminal state MUST already be written to disk and visible on screen before any analysis begins, and the analysis itself MUST run off the UI thread. Throughout, the user can keep typing in the composer and can start new runs. The only progress signal is a pulsing activity indicator — announced to assistive technology and labelled "Reviewing run for improvements…" — placed both in the application title bar and in the workspace run header; the finished run's own status is left alone, and there is no modal, no percentage readout, and no cancel control. When the analysis ends, both indicators disappear, the proposal library is re-read, and a persistent notice is posted. Quitting the application cancels the analysis that is running and any that are queued, discards the artifacts they would have written, withholds their completion notices, and MUST NOT hand the work to a durable out-of-process service that would outlive the application.

**REQ-LIBRARY-123** — Analyses MUST be performed one at a time and in the order in which the runs that produced them finished, so their artifacts and their completion notices appear in that same order and never interleave. A run's terminal state MUST already be readable from its persisted session state before that run's analysis begins, so an analysis interrupted part-way can never leave the run itself looking unfinished. A job captured while the application is shutting down MUST be cancelled rather than started, producing no artifact and no notice (REQ-LIBRARY-127).

**REQ-LIBRARY-124** — On job completion: a result carrying an artifact id causes the proposal list to be re-read. A non-cancelled result with one or more proposals publishes a persistent success notice titled `<N> improvement proposal ready` / `<N> improvement proposals ready` (singular/plural) with action label "Review proposals" that opens the Library on the proposals tab; a result with zero proposals publishes an info notice "Improvement analysis complete — no proposals" with no action; a cancelled result publishes nothing, cancellation being something the user asked for (REQ-LIBRARY-127). A worker failure MUST NOT be silent: a job that ended without producing an artifact for any reason other than cancellation MUST publish a warning notice conveying that the completed run could not be reviewed for improvements, naming the run it belonged to, and carrying the failure's reason; it offers no action, because there is nothing for the user to review. This is the case REQ-LIBRARY-035(b) records in the application log, and the log entry stays in addition to the notice. The notice's wording is left to the implementation. It changes nothing about the run itself (REQ-LIBRARY-161).

**REQ-LIBRARY-125** — While analysis is running, two activity indicators MUST be visible: one in the application title bar and one in the workspace run header. Both MUST carry the label "Reviewing run for improvements…". The title-bar indicator MUST expose the accessible name "Improvement analysis status" and the accessible description "Reviewing the completed run for improvements in the background. You can continue working."; the run-header indicator MUST expose an accessible description conveying the same three facts as the title-bar one — that a completed run is being reviewed for improvements, that the review is happening in the background, and that the user can continue working — its wording left to the implementation. Both MUST be present only while analysis is active and MUST be gone once it ends. Neither may change the completed run's own status chip, and no control — the send button included — may be disabled while analysis runs. **REQ-LIBRARY-127** — Shutting the application down MUST leave nothing of analysis behind: a job that had not yet started MUST NOT start, an analysis in progress MUST be cancelled so that no artifact is written for it, no completion notice may be posted for any cancelled job, and the activity indicators MUST end hidden. No analysis may continue past the process's exit, and none may be handed to anything that outlives it (REQ-LIBRARY-122). Shutdown MUST NOT wait for an in-flight provider call to return: the call is abandoned, whatever it eventually answers is discarded unread, and no artifact, notice, or log entry attributable to it may appear afterwards. There is consequently no wait to bound. The time from the user asking to quit to the process exiting MUST NOT depend on whether an analysis was in flight, so an unreachable provider can never hold a quit open.

### 19. Prompt stash and prompt history

**REQ-LIBRARY-137** — Prompt history MUST front-insert each sent or queued prompt and nothing else — composer text consumed locally as a slash command is neither sent nor queued and MUST NOT be recorded (REQ-LIBRARY-142) — suppressing only adjacent duplicates (a new entry equal to the current front item is not added). The stash front-inserts non-empty text. Popping a stash entry removes and returns it by index; an out-of-range index returns an empty string without error. Every mutation triggers the library-changed refresh-and-persist cycle.

**REQ-LIBRARY-138** — Saved prompts — the prompt history and the prompt stash — MUST persist in the durable store the application keeps for the workspace, and MUST still be there after the application restarts without the user having taken any action to save them. *This requirement once said "flushed to disk", the only durability verb the corpus carried, and that phrase promised a level it never named* (accepted amendment 2026-09-06, OQ-12): what is owed here is REQ-SESSION-034's level 1 — a write reported successful survives the loss of this process whole — and surviving a restart is exactly that. Prompts written since the last acknowledged terminal commit are intermediate updates under level 3 and MAY be lost to power loss; this requirement claims nothing stronger and no surface may. Each change to either list MUST be persisted as part of the library-change cycle it belongs to (REQ-LIBRARY-105, REQ-LIBRARY-137), and persisting one entry MUST NOT require rewriting the others: a library change that touches neither list writes neither list. A persistence failure MUST surface a persistent desktop error notice "Could not save prompt history" with detail "Rotaris will keep prompts in memory for this window.", and the prompts MUST stay usable in that window exactly as that detail says.

**REQ-LIBRARY-139** — History is capped at 200 entries and the stash at 100, enforced on both load and save with silent truncation of the oldest entries. Stored prompts that are absent, unreadable, or not of the expected shape load as empty state; loaded entries are stringified and blank entries removed. Those two limits are intended and are fixed by this document: neither is configurable, and no key of any scope changes them. They bound a convenience store rather than a record of work — the durable record of what a run was asked to do lives in the session, not here — so a user losing the two-hundred-and-first oldest prompt loses nothing that is not recoverable elsewhere.

**REQ-LIBRARY-140** — The workspace composer MUST show a ghost "Stash" button ("Stash prompt for later") that stashes the current composer text, and the transcript toolbar a ghost "Apply stash (<count>)" button (accessible name "Manage prompt stash", tooltip "Apply or pop a stashed prompt") whose count updates live.

**REQ-LIBRARY-141** — The stash dialog MUST be titled "Prompt stash", minimum 560×360, with the intro "Apply copies the selected prompt into the composer and keeps it in the stash. Pop copies it and removes it from the stash.", the first row pre-selected, and buttons Close / secondary "Apply" / primary "Pop". Apply copies without removing; Pop removes and copies. The empty state shows a disabled list with "No stashed prompts. Use Stash beside the composer first." and disabled Apply/Pop.

**REQ-LIBRARY-142** — Two slash commands MUST mirror the stash controls. `/stash`, described as "Stash the composer prompt", stashes the composer's current text exactly as the composer's Stash button does (REQ-LIBRARY-140). `/pop`, described as "Apply a stashed prompt", opens the prompt stash dialog (REQ-LIBRARY-141); the command itself removes nothing, and the user's choice of Apply or Pop inside that dialog decides whether the entry stays in the stash. The slash catalogue MUST be rebuilt whenever the library changes, so both commands always reflect the current stash. Composer text that the window consumes as a slash command MUST NOT be recorded in prompt history. Prompt history holds prompts that were sent to a run or queued for one (REQ-LIBRARY-137), and a slash command is handled locally and becomes neither; recording it would fill the history a user reaches for with commands rather than with the prompts they wrote. Text that merely begins with a slash without being a recognised command is ordinary prompt text and, once sent or queued, is recorded like any other.

**REQ-LIBRARY-143** — Demo mode MUST present read-only sample library content (sample prompt history and stash entries, sample artifacts, and sample proposals) with every mutating action refused per REQ-LIBRARY-119. The particular sample text is not contractual and is left to the build; what the seed MUST satisfy is stated as properties, so a demo build can be checked without pinning its prose. All three Library tabs MUST be non-empty, so no tab shows an empty state in demo mode; the sample proposals MUST cover every status of REQ-LIBRARY-007 and every risk level, and MUST come from at least two improvement artifacts, so the artifact list of REQ-LIBRARY-166 and its filtering are both exercised; the sample artifacts MUST include at least one of each `kind` of REQ-LIBRARY-088 and at least one hand-edited record, so the ` · edited` marker is visible; and every sample value MUST be recognisable as sample data rather than as a real workspace's contents. The read-only nature MUST be evident before a user attempts a mutating action and not only in the refusal: every control that would mutate library state MUST be visibly disabled and MUST carry an accessible description saying that demo mode is read-only. The refusals of REQ-LIBRARY-119 remain the answer to a mutating action that is nevertheless reached. Demo mode is itself entered only from the desktop interface (REQ-SHELL-162).

### 21. Persona memory

**REQ-LIBRARY-150** — Persona memory MUST be stored as one Markdown file per persona at `<workspace>/.rotaris/persona_memory/<persona>.md` — deliberately visible, inspectable, and hand-editable. Persona names MUST match `^[A-Za-z0-9_.\-]+$`; anything else is rejected with `Invalid persona name for persona memory: … (allowed: alphanumerics, underscore, dot, dash).`, preventing directory escape.

**REQ-LIBRARY-151** — Persona memory MUST be bounded to 200 lines, enforced on both read and write. On read, the file on disk is never modified (direct user edits stay the source of truth; only the injected context is protected); on write, content is truncated before persisting, newline-terminated, and written atomically. Truncation is logged.

**REQ-LIBRARY-152** — Loading persona memory MUST return "no memory" for a missing, unreadable, or blank file; otherwise the (possibly truncated) content.

**REQ-LIBRARY-153** — Memory is injected only at agent-creation time, as a context block named `persona_memory_<persona>`; an agent is given the file belonging to the persona it is being created as, and never another persona's file. Manual edits are picked up on the next persona load.

**REQ-LIBRARY-154** — A primary task run MUST never write persona memory. Mutation happens only via the approval-gated executor (directed at the file path per REQ-LIBRARY-062) or by direct manual edits.

**REQ-LIBRARY-155** — End-to-end acceptance: a task run yields a `persona_memory_update` proposal targeting one persona; nothing is on disk before approval; after approval and execution the memory file exists; a later load returns it for the target persona only, while unrelated personas still get no memory.

### 22. Ordering, timing, and concurrency

**REQ-LIBRARY-156** — For a completed desktop run the observable ordering MUST be: terminal session state persisted → analysis job captured (evidence snapshotted) → queued to the background worker → analyst runs (within its timeout) → artifact saved with duplicate suppression → proposals re-read into the UI → notice published. The user may start follow-up work at any point after the first step.

**REQ-LIBRARY-157** — Analysis activity MUST be published as its own independent flag that never alters the run state or session status fields.

**REQ-LIBRARY-158** — Within the running instance, session-artifact-store mutations are serialized and the record and its index entry are persisted together (REQ-LIBRARY-087), and every window and every run shares that serialization because there is only one instance (REQ-STARTUP-161). Both the session artifact store and the improvement artifact store are the application's own: **no writer the application does not serialize can reach a stored record** — not the user's own editor, not a version-control operation over the workspace, not an instance left behind by a crash — so the uncoordinated-writer case this requirement used to arbitrate no longer arises, and the file locking it declined is not needed to replace it. What still moves underneath a surface is another surface or another run of this same instance, and that is what the desktop's reload-on-vanished-proposal path exists for (REQ-LIBRARY-173). It resolves exactly as REQ-LIBRARY-042 states: each mutation re-reads before it writes, the read-modify-write takes effect indivisibly, a later decision on the same proposal wins, and no reader ever sees a partial state. The artifact bodies that remain files on disk (REQ-LIBRARY-087, REQ-SESSION-002) sit outside that serialization, and nothing here claims otherwise.

### 23. Cross-cutting invariants

**REQ-LIBRARY-159** — No proposal with an empty `evidence` list may exist anywhere: construction MUST fail (REQ-LIBRARY-009), storing one MUST fail validation (REQ-LIBRARY-014, REQ-LIBRARY-047), and a proposal returned without evidence MUST NOT be repaired into existence by supplying evidence on its behalf. The `verifier_gate_state` entry the product stamps onto a gate proposal (REQ-LIBRARY-029) is not such a repair: it is added to a proposal that already carries at least one analyst-authored entry, and it MUST NOT be the only entry that proposal holds. Reading every stored artifact in a workspace MUST therefore find, on every proposal, at least one evidence entry, and at least one whose `kind` is not `verifier_gate_state`.

**REQ-LIBRARY-160** — A task run MUST NOT change the workspace as a consequence of its analysis. Across a completed task run, the only things analysis may create or modify are the improvement artifact and its recorded version in the store; **every path in the workspace** — configuration files, personas, persona memory, gate configuration, and all the rest — MUST hold the same content afterwards as before, and no path in the workspace may be created or deleted. The guarantee is consequently stronger than it was when the artifact was itself a file in the workspace, and it is stated that way deliberately rather than left to be inferred. A change a proposal describes takes effect only once that proposal's status is `approved` and a run of type `improvement_run` applies it; a `verifier_gate_update` takes effect only through the deterministic writer of REQ-LIBRARY-063, from the complete block already inside the proposal, and never through an agent.

**REQ-LIBRARY-161** — No analysis failure may show up in the task run itself. For every failure mode — the pass cannot be constructed, the model call raises, the output fails to parse twice, the timeout elapses, or the artifact cannot be written — the run's terminal state, its recorded result, and the moment that result is reported MUST match what the same run would have produced with `runtime.improvement_collector_enabled` set to false; in particular the result reaches the host before any analysis work begins (REQ-LIBRARY-004). The worst outcome a user may observe is an artifact holding no proposals whose `notes` names the failure, or no artifact at all.

**REQ-LIBRARY-162** — Every mutation of an artifact — a status change, an edit, a deletion, a recorded checkpoint, and a rollback — MUST go through the write path of REQ-LIBRARY-047 and MUST leave behind a recorded version naming its cause from the vocabulary of REQ-LIBRARY-050. For as long as those versions survive retention (REQ-LIBRARY-052), the exact `summary` and `recommended_action` a proposal carried at each recorded decision point MUST be readable back from history, and pruning MUST give up intermediate versions before it gives up either version 1 or the newest version.

**REQ-LIBRARY-163** — A rollback MUST never leave the workspace in a state the user cannot get back out of. It MUST refuse to proceed when a `pre_rollback` safety checkpoint cannot be recorded first, when the working tree holds work done since the run and the user has not deliberately overridden that refusal (REQ-LIBRARY-170), and when the recorded checkpoint belongs to a different working tree than the one being restored. Every refusal MUST leave both the working tree and the stored artifact exactly as they were and MUST come back as a displayable reason rather than a failure the caller has to handle (REQ-LIBRARY-072, REQ-LIBRARY-075). When a rollback does proceed, every proposal it undid MUST return to `pending_review`, so no proposal reads as `approved` while its changes are gone; when that update cannot be persisted, the discrepancy MUST be reported to the user (REQ-LIBRARY-076) rather than passed over. A workspace with no Git repository MUST lose only the rollback capability: analysis, review, and application all continue to work.

**REQ-LIBRARY-164** — Every surface that shows improvement proposals — the Library's proposals tab, its improvement-artifact list and detail (REQ-LIBRARY-166, REQ-LIBRARY-167), and the dashboard card — MUST read and write the same stored artifacts (REQ-LIBRARY-042), with the same review semantics. A decision recorded on any one of them MUST be the state each of the others reports at its next refresh — the Library's update cycle (REQ-LIBRARY-105) and the dashboard card's live update (REQ-LIBRARY-130) — and no surface may hold a private copy that can disagree with the store; a mutation reads the store immediately before writing it (REQ-LIBRARY-042). How each surface presents that state remains its own.
