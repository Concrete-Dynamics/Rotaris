# MCP Server Integration — Server Configuration Model

Part 1 of 6 of [domain 16](../16-mcp-integration.md), which indexes every part. Defines REQ-MCP-001 – REQ-MCP-027.

## Requirements

### Server Configuration Model

- **REQ-MCP-001** — A server entry SHALL support exactly these fields with these defaults: `type` (one of `"stdio"`, `"http"`, `"sse"`; default `"stdio"`), `command` (string, optional), `args` (list of strings, default empty), `env` (string-to-string map, default empty), `cwd` (string, optional), `url` (string, optional), `headers` (string-to-string map, optional), `request_timeout` (integer seconds, optional), `disabled_tools` (list of strings, default empty), `tool_name_map` (string-to-string map, default empty), `tools` — an optional static tool-metadata list, default empty, whose entries carry a required `name` and a `description` defaulting to `""` — and `enabled` (boolean, default `true`). What `enabled` does once the entry resolves is fixed by REQ-CONFIG-465, which this requirement relies on for that behavior and does not restate; the field is named in this set because the set is closed, and a schema declaring "exactly these fields" while a field four requirements require is declared only elsewhere is wrong rather than narrower.

  This requirement is the product's single definition of the tool-server entry schema — the field set, each field's name, its type, whether it is optional, and its default. A document that presents, validates, stores, merges, or documents a server entry SHALL cite this identifier rather than restating any of those, and a field a surface needs is added here rather than declared elsewhere. What a citing document may add is where the entry is written and what its scope does with it; it may not hold a second copy of the field list, and a shorter list elsewhere is a stale copy rather than a narrower schema.

- **REQ-MCP-002** — A server entry that comes from a YAML scope SHALL be rejected at configuration load, with an error naming the offending server, its transport type and the offending field, when a `stdio` entry omits `command` or supplies a `command` that is the empty string or is entirely whitespace, when an `http`/`sse` entry omits `url` or supplies an empty `url`, or when `request_timeout` is set to a value that is not a whole number greater than zero (REQ-MCP-003). An absent `command` and an empty `command` are the same defect and SHALL be reported alike, so no `stdio` entry reaching a later stage ever carries an empty command. The same defects in an entry read from an `mcp.json` discovery file SHALL NOT fail loading; that entry alone is dropped with a warning (REQ-MCP-018, REQ-MCP-023). Every defect found SHALL be reported, not only the first.

- **REQ-MCP-003** — `request_timeout` is a whole number of seconds. When it is set on a server entry, every individual tool call to that server SHALL be allowed that many seconds, measured from the dispatch of the call to the receipt of its result, and the same allowance SHALL apply to every tool that server exposes. The allowance is per call: each call starts with the full budget regardless of time consumed by earlier calls. `request_timeout` SHALL NOT govern tool discovery (REQ-MCP-046) or health probing (REQ-MCP-054), each of which carries its own budget. When `request_timeout` is unset the allowance is the product-wide default of 300 seconds. A `request_timeout` that is zero, negative, or not a whole number SHALL be rejected at configuration load exactly as the defects of REQ-MCP-002 are, and SHALL never be silently treated as unset. When the allowance is exhausted, the call SHALL end as a failed tool call and SHALL NOT be retried by the product: the agent SHALL receive a tool result marked as an error conveying that the named server did not answer within the allowance; the tool row SHALL settle as `failed` in the vocabulary of REQ-MONITOR-105; the connection SHALL be left open and usable for later calls; and the run SHALL continue, its outcome unaffected except through whatever the agent then does. This holds whether the allowance came from `request_timeout` or from the 300-second default, and holds for every transport.

- **REQ-MCP-004** — A tool SHALL be denied when any candidate spelling of REQ-MCP-057, derived from the name the server itself reports, matches an entry of `disabled_tools`. A denied tool SHALL appear neither in the persona prompt nor among the tools the persona can call, and SHALL stay denied even when a persona grant names it: denial outranks every grant (REQ-MCP-056).

- **REQ-MCP-005** — `tool_name_map` SHALL map names the server reports (keys) to replacement names (values). A rename SHALL be applied only to tools that survive `disabled_tools` filtering (REQ-MCP-049) and SHALL leave the tool's description unchanged. A replacement name SHALL be the name the model both sees and calls: it is the name printed in the prompt (REQ-MCP-101), the name the model writes in a tool call, and the name the product maps back to the server-reported name when it dispatches that call, so the original name SHALL NOT remain callable once a rename covers it. Matching in `disabled_tools` and in persona grants SHALL nevertheless be performed against the candidate spellings of REQ-MCP-057 derived from the server-reported name only, so an entry written against a replacement name SHALL match nothing; renaming is a presentation decision and never a permission decision. Two entries of one server's `tool_name_map` SHALL NOT map to the same replacement name, and a replacement name SHALL NOT equal the reported name of another surviving tool of the same server; either collision is a configuration error naming the server and both names.

- **REQ-MCP-006** — The runtime tool surface of a server SHALL always come from live discovery (REQ-MCP-046); the static `tools` list on a server entry SHALL have no effect on which tools are advertised or callable.

- **REQ-MCP-007** — A persona SHALL support: `mcp_servers` (list of server names it carries) and `mcp_tools`, an optional per-server tool grant map (server name drawn from `mcp_servers` → list of original tool names). Given a carried server with no grant entry (or the whole map unset), the persona receives every tool that server exposes; given a grant entry that is an empty list, the persona receives none of that server's tools. Server-level `disabled_tools` applies on top of any grant.

- **REQ-MCP-008** — The top-level configuration SHALL carry a named map of server entries under `mcp_servers` and a machine-maintained per-server origin map under `mcp_server_sources` (values per REQ-MCP-026). The origin map SHALL never be user-settable; hand-written values are overwritten during loading.

- **REQ-MCP-009** — Resolving a persona's server set SHALL be side-effect free on configuration: given the same configuration shared across personas and repeated resolutions, when any persona is resolved, then no configured entry (including its `args` list) is observably changed and every resolution yields identical results.

- **REQ-MCP-117** — Wherever this domain requires servers, tool names, secret keys or secret rows to be presented or written in ascending order, that order SHALL be ascending code-point order over the raw string — comparing Unicode scalar values position by position, shorter string first where one is a prefix of the other — case-sensitive, and identical on every platform and under every locale the product runs in. No locale-aware collation, case-folding or accent-folding SHALL be applied. This one rule SHALL govern every ordered presentation in this domain, so two surfaces listing the same names never disagree: the server list and the per-server secret rows of REQ-MCP-109, the expected-keys hint of REQ-MCP-109, and the servers and tools of the prompt's MCP section (REQ-MCP-101).

### Shipped Default Servers

- **REQ-MCP-010** — The built-in defaults SHALL contain exactly three server entries and no others, declared under the names REQ-CONFIG-181 fixes — `web_search`, `browser` and `code_intelligence`:
  - **`web_search`**: remote transport over HTTP, whose `url` embeds a `${VAR}` placeholder naming `ROTARIS_SEARCH_API_KEY`, the environment variable that carries its API key (substituted per REQ-MCP-088), with `request_timeout` 600 and `enabled: false` (REQ-CONFIG-181, REQ-CONFIG-465);
  - **`browser`**: `stdio` transport whose `command` is `npx` and whose `args` carry the non-interactive install flag `-y`, name the package at an exact `MAJOR.MINOR.PATCH` version (never a range and never a floating tag), and select headless operation; declared with `enabled: false`;
  - **`code_intelligence`**: `stdio` transport whose `command` is the reserved bundled-runtime token of REQ-MCP-033 and whose `args` select stdio transport and the host-integration mode in which the server does not advertise its own file-read, directory-listing or shell tools while continuing to advertise its pattern-search tool, and which carries no project path — the path is supplied per run by REQ-MCP-034. This is the one default entry that is enabled by default (REQ-CONFIG-181).

  On these three entries, no field beyond those named above SHALL be set; every other field takes the default given in REQ-MCP-001. In particular, only the `web_search` entry carries a `request_timeout`, so tool calls to the `browser` and `code_intelligence` defaults are bounded by the 300-second default of REQ-MCP-003, and none of the three carries `disabled_tools`, `tool_name_map` or a static `tools` list.

  The `web_search` URL template, the `browser` package identifier, its pinned version string and its headless argument, and the arguments that select the `code_intelligence` transport and host-integration mode are identities of the third-party services filling the three roles. REQ-CONFIG-181 leaves those identities to the implementation and permits them to change between releases; this document therefore does not fix them, and fixes instead the roles, the names, the transports, the timeout, the enablement, and — for `code_intelligence` — the binding manifest of REQ-MCP-116.

- **REQ-MCP-011** — The default `code_intelligence` entry SHALL pin the bundled runtime to one exact release, written as a complete `MAJOR.MINOR.PATCH` version string. That entry SHALL NOT name a branch, a repository revision, a floating tag such as `latest`, or a version range; the pin SHALL be verifiable by inspecting the shipped default entry alone, and the version string SHALL be identical to the one the binding manifest of REQ-MCP-116 records. Two installations of the same product build SHALL consequently start the same runtime version. The distribution identifier to which the pin applies is a third-party identity left to the implementation by REQ-CONFIG-181 and is recorded in that manifest rather than fixed here; the pinning discipline above is what this document fixes, and a build that violates it is defective.

- **REQ-MCP-012** — No default server named `lsp` SHALL ship, and no default persona SHALL reference one. The name remains user-configurable; a persona referencing `lsp` (or any name) without a matching server entry SHALL fail validation per REQ-MCP-103.

- **REQ-MCP-013** — No git-inspection MCP server SHALL ship in the defaults or be referenced by any default persona. Read-only git inspection SHALL remain achievable as a user configuration pattern by combining a user-added server with a per-server tool allow-list (e.g. granting only a status tool) and/or `disabled_tools`. This requirement and REQ-MCP-015 are canonical for the shipped defaults: any other description of the product that claims a git-inspection server among the defaults, or that limits project-memory writing to a single persona, describes something the product does not do and is a defect in that description rather than a second reading of this domain.

- **REQ-MCP-014** — Each built-in persona named in the table below SHALL carry exactly the servers listed in its row and no others, and its `mcp_tools` grant for the `code_intelligence` server SHALL be exactly the set union of the tiers named in its row (tiers defined in REQ-MCP-015). A row naming no server means an empty `mcp_servers` list for that persona. The table is closed for this domain's purposes without claiming to enumerate every built-in persona: the delegation role vocabulary is owned by REQ-ORCH-028, and the two further rows here — `intent-classifier` and `project-initializer` — are personas that are not delegation targets. A built-in persona that does not appear in this table SHALL carry an empty `mcp_servers` list and therefore no MCP tools at all, so adding one can never widen the MCP surface without amending this table.

  | Persona | Servers carried | Code-intelligence grant tiers |
  |---|---|---|
  | orchestrator | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | intent-classifier | (none) | — |
  | architect | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | coding-agent | `code_intelligence` | READ + EDIT + MEMORY-WRITE |
  | tester | `browser`, `code_intelligence` | READ + EDIT + MEMORY-WRITE |
  | docs-writer | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | refactorer | `code_intelligence` | READ + EDIT + MEMORY-WRITE |
  | planner | `web_search`, `code_intelligence` | READ + MEMORY-WRITE |
  | requirements-engineer | `code_intelligence` | READ + MEMORY-WRITE |
  | librarian | `web_search` | — (no `code_intelligence` server) |
  | codebase-analyst | `code_intelligence` | READ + MEMORY-WRITE |
  | verifier | `code_intelligence` | READ + MEMORY-WRITE |
  | ui-verifier | `browser`, `code_intelligence` | READ + MEMORY-WRITE |
  | gatekeeper | (none) | — |
  | project-initializer | `code_intelligence` | READ + MEMORY-WRITE + ONBOARDING |

  Where a persona carries the `browser` or the `web_search` server it SHALL have no `mcp_tools` entry for that server, and SHALL therefore receive that server's whole discovered surface (REQ-MCP-007). A persona carrying a server the built-in defaults declare with `enabled: false` receives that server's tools only once the user enables it (REQ-CONFIG-465); until then the server is absent from the run exactly as REQ-MCP-078 describes, without warning.

- **REQ-MCP-015** — The four code-intelligence grant tiers SHALL be composed from the tool names the pinned runtime of REQ-MCP-011 reports, with exactly these cardinalities and coverage:
  - **READ** — ten tools: symbol lookup, per-file symbol overview, referencing-symbol search, implementation search, declaration search, pattern search, per-file diagnostics, project-memory listing, project-memory reading, and usage-instruction retrieval.
  - **EDIT** — seven tools: symbol-body replacement, insertion before a symbol, insertion after a symbol, symbol rename, safe symbol deletion, single-file content replacement, and cross-file content replacement. Carried only by coding-agent, tester and refactorer.
  - **MEMORY-WRITE** — two tools: project-memory writing and project-memory editing. Carried by every persona that carries the code-intelligence server.
  - **ONBOARDING** — one tool: project onboarding. Carried only by project-initializer.

  The four tiers are pairwise disjoint sets of tool names, so a persona's `code_intelligence` grant holds a countable number of names: 12 for READ + MEMORY-WRITE, 19 for READ + EDIT + MEMORY-WRITE, and 13 for READ + MEMORY-WRITE + ONBOARDING. No built-in grant SHALL name the runtime's memory-deletion, memory-rename or dashboard-opening tools, and every name appearing in a built-in grant SHALL be a name the pinned runtime returns from `tools/list`.

  The literal name strings are the pinned runtime's own vocabulary, which REQ-CONFIG-181 leaves to the implementation; they SHALL be recorded once in the binding manifest of REQ-MCP-116 and read from there by every part of the product that needs them, and SHALL NOT be written out a second time anywhere. The tiers above are therefore defined by capability and bound to strings by that manifest, and a grant is verifiable without this document naming a string: the build SHALL check that the manifest's four tiers have exactly the cardinalities and the coverage stated above, that they are pairwise disjoint, that no tier holds a never-grant name, and that every name in all four tiers plus the three never-grant names is reported by the pinned runtime's `tools/list`. A build failing any of those checks SHALL be treated as defective and SHALL NOT ship. An upstream rename therefore fails a build rather than silently degrading a grant at run time through REQ-MCP-058.

- **REQ-MCP-116** — The build SHALL carry exactly one **code-intelligence binding manifest**, and it SHALL be the single place in the product where the pinned runtime's own identifiers are written. It SHALL record: the runtime's distribution identifier and its pinned `MAJOR.MINOR.PATCH` version (REQ-MCP-011); the arguments that select stdio transport and the host-integration mode of REQ-MCP-010; the server-launch subcommand, the explicit project-path option and the project-from-working-directory option of REQ-MCP-034 and REQ-MCP-036; the name of the per-project marker file whose presence skips project creation, and the subcommands of the create, index and memory steps of REQ-MCP-099; the file-name extensions the runtime indexes, which decide whether a workspace contains code (REQ-MCP-099); and the tool names of the four tiers and the three never-grant names of REQ-MCP-015, including the project-memory listing name used by the binding probe of REQ-MCP-071 and the listing/reading pair that gates REQ-MCP-102; and the language servers the runtime provisions for the languages the release names — for each, the packages by name, exact version, source URL, license identifier and provisioner family, as REQ-STARTUP-058's second list declares them, together with the runtime's own path segment under its per-user home where it stores them (*added 2026-09-06 under ESC-32; the disclosure of REQ-MCP-118 reads them from here and nowhere else*). No other part of the product SHALL restate any of those strings, so the shipped default entry, the derived invocation, the setup steps, the probes and the built-in grants cannot drift from one another or from the pinned version. The manifest SHALL be verifiable against the pinned runtime by the build checks of REQ-MCP-015 and REQ-MCP-095, and a build whose manifest does not match the runtime it pins SHALL be treated as defective. The manifest is not a configuration surface: it SHALL NOT be user-editable, SHALL NOT be read from disk at run time from any location a user can write, and SHALL NOT vary by workspace.

- **REQ-MCP-118** — *Minted 2026-09-06 under ESC-32 (IC-7 adopted).* The `mcp` settings category SHALL show, on the code-intelligence surface that carries the project-setup action of REQ-MCP-112 and REQ-MCP-099, a **language-server disclosure**, present whenever that surface is, so it is readable before any fetch it describes can occur. The disclosure SHALL state: that the bundled runtime obtains a language's server at the first use of a symbol-level tool for that language, and that nothing is downloaded before then; the per-user directory the runtime stores them in (REQ-STARTUP-145), as a path; each declared language server with its name, version, license identifier and source, read from the binding manifest of REQ-MCP-116 and restated nowhere; and that a further language the runtime supports obtains its server by the same route and is not declared. The literal wording is the implementation's; what is fixed is the content, and that it is shown where the action is. This is the surfacing REQ-STARTUP-159 relies on when it counts these servers among the things fetched after installation.

- **REQ-MCP-016** — Every persona that carries the `code_intelligence` server per REQ-MCP-014 SHALL list all three of the product's own tool names `grep` (content search), `glob` (path matching) and `read_file` among its non-MCP tools, and SHALL be able to call all three. This is verifiable by inspecting each such persona's non-MCP tool list for those three literal names; it holds regardless of the code-intelligence server withholding its own file-read and directory-listing tools in the mode of REQ-MCP-010.

### Configuration Auto-Discovery (`mcp.json`)

- **REQ-MCP-017** — Discovery SHALL read at most two files: the project-level `<workspace_root>/.mcp.json` (origin tag `discovered-project`) and one user-level file (origin tag `discovered-user`) located per platform: macOS `~/Library/Application Support/mcp.json`; Windows `%APPDATA%/mcp.json` (when `APPDATA` is unset, user-level discovery is skipped entirely); other systems `~/.config/mcp.json`. This requirement is the product's single definition of where `.mcp.json` auto-discovery looks, including the skipping of user-level discovery when `APPDATA` is unset; the shape of a discovery file, the keys it accepts, and how it is parsed are owned by REQ-MCP-018 through REQ-MCP-024 and REQ-MCP-027, which together produce entries in the server-entry schema of REQ-MCP-001. No requirement in any domain SHALL hold a second copy of the locations, the file's shape, or the parsing rules; a requirement that needs them SHALL cite the requirement here that owns the part it needs and state only what it adds.

- **REQ-MCP-018** — A discovery file's servers SHALL be read from the top-level key `mcpServers`, or failing that `servers` (checked in that order); if neither holds an object, the file contributes nothing. A missing file SHALL be silently ignored; unreadable or invalid JSON SHALL log a warning naming the file and contribute nothing; a JSON root that is not an object SHALL log a warning and contribute nothing. None of these conditions may fail configuration loading.

- **REQ-MCP-019** — Discovered server names SHALL match `^[a-zA-Z][a-zA-Z0-9_-]*$`; a non-matching name SHALL be skipped with a warning naming the offending name and file. A server entry whose value is not an object SHALL likewise be skipped with a warning.

- **REQ-MCP-020** — Per-entry transport determination SHALL be: an explicit `type` wins; otherwise `http` when a `url` is present, else `stdio`. Stdio entries SHALL accept `command`, `args` (default empty), `env`, `cwd`, and `envFile`; remote entries SHALL accept `url` and `headers` while retaining `env` and `cwd`.

- **REQ-MCP-021** — An `envFile` path SHALL resolve relative to the declaring file's directory and be parsed line-by-line as `KEY=VALUE`, skipping blank lines and `#` comments and stripping single or double quotes around values. An unreadable `envFile` SHALL log a warning and yield an empty map without aborting discovery. Explicit `env` entries SHALL override `envFile` entries on key collision.

- **REQ-MCP-022** — In discovered `env` values and `cwd`, the placeholder `${workspaceFolder}` SHALL resolve to the workspace root and `${env:VAR}` SHALL resolve to the process environment (empty string when unset); `cwd` SHALL additionally be path-normalized. Any other `${...}` placeholder SHALL stay literal with a warning.

- **REQ-MCP-023** — Any failure while parsing one server entry (for example, a stdio entry without a command, or with a command that is empty or whitespace) SHALL skip only that entry with a warning naming the server and its source; discovery of the remaining entries continues. A key inside a server entry that is not one of those REQ-MCP-020 and REQ-MCP-021 accept SHALL NOT be such a failure: it is ignored, and the entry loads on its remaining keys (REQ-MCP-027).

- **REQ-MCP-024** — On a name collision between the user-level and project-level discovery files, the project-level entry SHALL win.

- **REQ-MCP-025** — Whole-configuration merge order for servers SHALL be: built-in defaults → discovered `mcp.json` servers → global `agents.yaml` (per-user configuration directory) → workspace `agents.yaml` (`<workspace>/.rotaris/agents.yaml`). Same-named entries from later scopes merge field-wise into earlier ones. Consequences that SHALL hold: discovered servers override same-named defaults; YAML in either scope overrides discovered entries; global YAML servers survive a workspace configuration that has no server section at all.

- **REQ-MCP-026** — After merging, the origin map SHALL record, per final server name: `"yaml"` when any YAML scope named it, else the discovery tag (`"discovered-project"` / `"discovered-user"`), else `"default"`.

- **REQ-MCP-027** — A discovery file SHALL be consumed read-only: after any number of configuration loads, every `mcp.json` the product has read SHALL be byte-for-byte identical to its content before those loads — nothing rewritten, reformatted, reordered, or added. A file that uses only the keys named in REQ-MCP-018, REQ-MCP-020 and REQ-MCP-021 SHALL load without the user editing it first. What the agent runtime receives SHALL be the normalized description of REQ-MCP-043, never the discovery file's own shape. A key inside a server entry that lies outside that set SHALL be **ignored with a warning** naming the file, the server and the key, and SHALL NOT cause the entry to be skipped: a file written for another client loads on the keys this product understands, and a mistyped key is still reported rather than swallowed. The warning SHALL be emitted at most once per (file, server, key) per configuration load.
