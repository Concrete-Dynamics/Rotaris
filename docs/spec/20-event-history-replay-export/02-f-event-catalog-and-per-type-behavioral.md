# Machine-Readable Event Stream, Replay, and Trajectory Export — F. Event catalog and per-type behavioral guarantees

Part 2 of 7 of [domain 20](../20-event-history-replay-export.md), which indexes every part. Defines REQ-EVENTS-041 – REQ-EVENTS-068.

### F. Event catalog and per-type behavioral guarantees

**REQ-EVENTS-041** — The published event catalog MUST contain exactly these 23 types, discriminated by `event`: `session.start`, `session.end`, `iteration.start`, `iteration.end`, `child.spawn`, `child.transition`, `child.complete`, `tool.start`, `tool.finish`, `permission.decision`, `verifier.result`, `verifier.progress`, `transcript.row`, `usage.update`, `error`, `result`, `hook.start`, `hook.finish`, `checkpoint.created`, `checkpoint.restored`, `gate.decision`, `gate.repair`, `approval.requested`.

**REQ-EVENTS-042** — On `session.start`, the sandbox flag MUST report whether a sandbox is actually available and in force for this run, never merely what was requested; the flag MUST NOT read `true` when no sandbox actually came up. The permission mode reported MUST be the mode configured at start; any later downgrade is reported by subsequent permission events, not by revising this field.

**REQ-EVENTS-043** — `checkpoint.created` MUST report the number of changed paths as a count and MUST NOT enumerate the paths, so that an event line stays a fixed size no matter how many paths changed.

**REQ-EVENTS-044** — `checkpoint.restored` MUST report whether the restore happened, the safety checkpoint sequence (which MUST be read explicitly and MUST NOT be inferred from the restored flag, because a refused restore can still have produced one), a changed-path count of `0` when refused, and a blocking reason that is empty on success.

**REQ-EVENTS-045** — `gate.decision` MUST report the decision (`passed`, `gated`, or `exempt`), its reason, the unsatisfied checks, the advisory-only failures, and any model verdict that was overruled — the verdict MUST remain visible even when the gate decided against it.

**REQ-EVENTS-046** — `gate.repair` MUST report the action (`retry` or `escalate`), the 1-based attempt number, the configured maximum attempts, and the remaining attempts carried explicitly and clamped at zero or above. A gated iteration MUST produce exactly one repair event; `retry` and `escalate` are alternatives, and exactly one of them is chosen.

**REQ-EVENTS-047** — Each hook that executes MUST produce exactly one `hook.start` and one `hook.finish` carrying the same `hook_id`, and that `hook.finish` MUST report `skipped` false. Given a hook the trust gate of REQ-HOOKS-090 withheld — a workspace-scoped hook for which no stored approval matches the current workspace hook-set fingerprint, or a hook carrying a scope outside REQ-HOOKS-020's trusted set — exactly one event MUST be emitted for it: a `hook.finish` with `skipped` true, `skip_reason` exactly `untrusted_workspace` (one of the two values REQ-HOOKS-126 defines; the other, `plan_gate`, belongs to the separate case of REQ-ORCH-153 and is not this sentence's), `exit_code` null and `duration_ms` null, and `hook_name` carrying the hook's stable id rather than its configured display name (REQ-HOOKS-102). No `hook.start` bearing that `hook_id` may appear. A hook that produced no exit code MUST report `exit_code` as null; a numeric stand-in such as `0` or `-1` MUST NOT be substituted, even where the durable timeline records that state as `-1` (REQ-HOOKS-119).

**REQ-EVENTS-048** — `lifecycle_point` MUST carry exactly one of the seven hook events of REQ-HOOKS-001 — `pre_tool`, `post_tool`, `session_start`, `session_end`, `iteration_end`, `child_completed`, `verifier_finished` — and no other value. On every `hook.finish` whose `lifecycle_point` is not `pre_tool`, `blocked` MUST be false. Only a hook running at `pre_tool` may report `blocked` true, so a consumer may read `blocked` true as implying that lifecycle point.

**REQ-EVENTS-049** — `approval.requested` MUST reach every channel while the request is still outstanding, and therefore MUST precede the `permission.decision` carrying the same `request_id`. `resolver` MUST carry exactly one of the two values REQ-TOOLS-061 fixes, `brokered` or `headless`. `timeout_seconds` MUST be null exactly when `resolver` is `headless`, which never waits for a response, and MUST otherwise carry the wait in seconds (default `300.0`, REQ-EVENTS-167). `unattended_reason` MUST be the empty string on every request a person could still answer, and MUST be exactly `headless-policy` — the only defined value, spelled as REQ-TOOLS-061 spells it — on every request none can, which is exactly the requests whose `resolver` is `headless`. Expiry of the wait MUST NOT be reported on this event; it is reported on the paired `permission.decision` (REQ-EVENTS-051).

**REQ-EVENTS-050** — `approval.requested` MUST name the blocked agent by its canonical name when the resolver knows it, and MUST report an empty name rather than a guess when it does not. The persona field MUST always be populated truthfully; when the agent name is empty it is the only value a consumer can route on. For a top-level agent the reported name may be a persona label for which no `child.spawn` was ever emitted. A consumer that cannot match the two MUST conclude the agent is not a child rather than assume an event went missing.

**REQ-EVENTS-051** — A `permission.decision` that resolves a previously announced approval MUST carry the same request identifier as its `approval.requested`. A decision reached without ever asking a human MUST claim no request identifier. A request raised for one call MUST NOT be claimed by another. A fail-closed timeout MUST also be reported as a resolving `permission.decision`.

**REQ-EVENTS-052** — `transcript.row` MUST carry the transcript row verbatim in `row` and its position in `index`. A row that is produced incrementally MUST yield exactly two events for its `index` — one when the row first appears and one when it has reached its final form — and none for any state in between, so an answer produced token by token yields two events for its row rather than one per token. A row that is already in its final form when it first appears MUST yield exactly one event for its `index`: there is no separate settling state to announce, and a second event carrying an identical row would be indistinguishable from a genuine revision. One or two events per index is therefore the whole contract, and never more. The semantics are upsert by `index`, never append: a consumer MUST replace whatever it holds at that index rather than adding a row. Indices MUST be assigned contiguously from `0` in row order, so an index higher than the next one a consumer expects is evidence that events were lost. A consumer that detects such a gap MUST NOT invent a row to stand in for one it never received, and MUST NOT go on applying increments over a transcript it knows to be incomplete: it stops consuming increments and reconciles from a whole read of the session, which recovers the rows themselves rather than standing in for them (REQ-SESSION-161, REQ-MONITOR-226). The live stream is never rewound; what the stream dropped is recoverable *as events* only from the session's stored history (REQ-EVENTS-083), which remains the only complete record of them. Clearing the transcript restarts indices at `0`.

**REQ-EVENTS-053** — A `usage.update` MUST NOT be emitted when it would carry no figures, that is when `tokens` and `cost` are each either null or an empty object, so that a consumer never receives an empty payload it could mistake for a reset to zero. Every emitted `usage.update` carries run-to-date cumulative totals, so the most recent one supersedes all earlier ones (REQ-EVENTS-136). **The emission trigger is the completed provider request** (accepted amendment 2026-09-06, OQ-8): exactly one `usage.update` MUST be emitted when a completed provider request contributes new usage to those cumulative totals, and the trigger MUST NOT be widened to a smaller unit than a request or narrowed to the surviving requests alone. **Usage a failed or partial request reported MUST be counted**, because the provider reported it as spent and a retry does not unspend it; a request whose reported usage leaves the cumulative totals unchanged MUST raise no event, which is what keeps a provider that reports nothing from producing a stream of identical payloads. **Sampling is a separate cadence and MUST NOT drive this event**: REQ-MONITOR-166's token-history sampling is taken on its own interval and neither raises nor suppresses a `usage.update`. The terminal `session.end` of REQ-SESSION-094 carries the final cumulative totals whether or not the last request moved them, so a consumer that missed an update still ends holding the run's whole figure. The event's volume against REQ-EVENTS-091's cap is therefore bounded by the number of provider requests a run makes, which is what makes it bounded at all.

**REQ-EVENTS-054** — `verifier.progress` MUST be emitted for exactly three phases, spelled on the wire `started` (the suite began), `check_started`, and `check_finished`. `check` MUST name the check the event concerns on `check_started` and `check_finished`, and MUST be the empty string on `started`. `index` MUST be the 1-based position of the check for `check_started` and `check_finished`, and `0` for `started`. `total` MUST be the number of checks in the suite. `elapsed_s` MUST be the seconds since the suite began; `deadline_s` MUST be the suite's time budget in seconds, or null where none applies. `status` MUST be present only on `check_finished`, where it MUST carry exactly one of the five check statuses REQ-ORCH-123 fixes, spelled on the wire exactly as that requirement spells them, and MUST be the empty string on the other two phases. This document holds no copy of that vocabulary; what it fixes is that the field is present on `check_finished` alone.

**REQ-EVENTS-055** — `verifier.result` MUST carry the iteration number, `passed`, the per-check details in `checks`, and a `summary` that is a non-empty human-readable string. Each entry of `checks` MUST carry exactly these fields: `name` (the check name, `:subdir`-qualified as REQ-ORCH-122 qualifies it), `command` (masked per REQ-EVENTS-059), `status` (one of the five of REQ-ORCH-123), `severity` (`blocking` or `advisory`), `exit_code` (integer or null), `duration_ms` (float or null), `skip_reason` (empty unless `status` is `skipped`), and `output_path` (the path at which that check's full output was retained, recorded with the check under REQ-ORCH-123 and reachable in full after the run has ended; empty where none was written). `passed` MUST report whether the suite blocks completion under REQ-ORCH-116 — false exactly when at least one blocking check ended in a status that gates — and MUST NOT be read as an assertion that verification occurred: a suite that was skipped executed no check, blocks nothing, and therefore reports `passed` true with an empty `checks` list. The gate's own `exempt` decision on `gate.decision` is the authoritative signal that nothing was verified. The summary MUST identify which of exactly three outcomes occurred and MUST carry the information needed to act on it: that every check passed; that specific checks failed, in which case it MUST name each failed check; or that the suite was skipped, in which case it MUST state the reason. Its wording is the implementation's.

**REQ-EVENTS-056** — An issue recorded during a run (REQ-SESSION-135) MUST reach the wire as an `error` event only when its severity is `error`. Issues at `warning`, `info` or `debug` severity — the other three members of the severity vocabulary REQ-SESSION-134 fixes — MUST produce no event at all, so that a healthy run does not appear to be failing. An `error` event derived from a recorded issue MUST set `fatal` to false, MUST carry the issue's `kind` verbatim in `error_class`, and MUST carry in `detail` a locator naming the issue it was derived from, by which that issue can be found without searching. The `error_class` vocabulary is open-ended and owned by whichever domain records the issue (`hook_failure` and `hook_trust` from REQ-HOOKS-120 and REQ-HOOKS-086, `permission_denied` from REQ-TOOLS-081, and others); a consumer MUST treat an unfamiliar kind as opaque text rather than rejecting the event.

**This requirement is the single definition of the locator**, for this document and for every other; a requirement that needs one cites this identifier rather than restating it, as REQ-SESSION-135's `evidence_ref` and REQ-TOOLS-081's evidence reference do. A locator MUST have the form `<record kind>#<record id>`, a record-kind token and a record id joined by a single `#`, and both halves are a machine-readable contract.

**The record-kind tokens are fixed here and are exactly three**, lower snake case: `issues` for the session's issues record (REQ-SESSION-135), `permission_audit` for the session's permission audit (REQ-SESSION-137, REQ-TOOLS-078), and `tool_call_evidence` for the session's tool-call evidence record (REQ-SESSION-136). Each token names the record rather than the thing recorded: the tool-call evidence record's token is `tool_call_evidence` and deliberately not `tool_calls`, which is already the name of a count in the trajectory summary (REQ-EVENTS-136), and a token that reads like a document key in the same exported material invites exactly the confusion a machine-readable contract exists to prevent. A locator MUST NOT name any other record kind; admitting a fourth is an amendment to this requirement and to nothing else, because a token that drifts between the record emitting a reference and the record it points into breaks documents already in a user's hands. The `detail` of an `error` event is always an `issues` locator, since the event is derived from an issue.

**The record id is the identifier the named kind's own requirement gives its entries, and this requirement fixes none of them**: for `issues` it is the issue's `id`, the 12 hexadecimal characters REQ-SESSION-135 fixes; for `tool_call_evidence` it is the record's `call_id` (REQ-SESSION-136); for `permission_audit` it is the identifier REQ-TOOLS-079 gives a decision entry, and that requirement is the only place it may be fixed. Any such identifier MUST distinguish one entry of that kind from every other entry of that kind within the same session record, MUST NOT change once the entry is recorded, and MUST NOT be reused after the retention cap of REQ-SESSION-133 has displaced the entry that held it — otherwise a locator written earlier would silently resolve to a different entry than the one it was written for. **A locator MUST NOT name an entry that has no such identifier, and a record kind whose own requirement gives none of its entries one MUST NOT be named at all**, because such a locator resolves nowhere and states a reference the product cannot honour. A kind MAY hold entries of more than one shape and give an identifier to only some of them — the permission audit does, identifying the decision entries REQ-TOOLS-079 governs and not the mode-change entries of REQ-TOOLS-082 — and such a kind is nameable while the entries that have no identifier are not. That is this rule applied rather than an exception to it, and it is stated because the alternative reading makes `permission_audit` unnameable and REQ-TOOLS-081's evidence reference impossible to write.

**A locator resolves through an export as well as inside this application, where the named kind has an export.** For a kind that has one (`issues` and `permission_audit`, through REQ-SESSION-199), the identifier MUST be present in what that export produces, so that a reader holding one exported record can find the entry another exported record names, on a machine carrying none of this product's code and with nothing beyond a stock parser (REQ-EVENTS-166). For a kind that has none — `tool_call_evidence`, which must never gain one (REQ-TOOLS-190, REQ-SESSION-136) — the locator still names the entry unambiguously inside this application, and a reader of an export that carries such a locator must come back to the application to see what it names. That is the intended outcome and MUST NOT be treated as a defect to close, and it MUST NOT be closed by widening an export.

**No export may resolve a locator.** A locator MUST be carried as the opaque string it is: no export may inline, expand, dereference or replace it with the entry it names, and no export may be made self-contained by following one. This is not tidiness — the issues record is full of locators into the tool-call evidence record, which holds the arguments an agent passed exactly as they were passed, so an export that followed them would become the export that record must never have (REQ-TOOLS-190, REQ-SESSION-136, REQ-LIBRARY-176 for the same rule stated over a different record). A locator whose entry the retention cap has since displaced simply does not resolve; that is an ordinary outcome and MUST NOT be read as damage or as a reason to repair anything.

**REQ-EVENTS-057** — A completed tool call MUST produce a `tool.start` and a matching `tool.finish` sharing a call identifier, with the finish carrying status, duration in milliseconds, and an error description when the call failed. The `status` on `tool.finish` MUST carry exactly one of the three settled values of REQ-MONITOR-105 — `ok`, `failed`, or `blocked` — and never that vocabulary's `running`, which describes a call a `tool.finish` has by definition ended.

**REQ-EVENTS-058** — The `status` on `session.end` MUST carry exactly one value of the run status vocabulary of REQ-EVENTS-026, or the empty string where no status could be derived. A consumer MUST read the empty string as *unknown* and never as failure. This matches the reading REQ-HOOKS-075 gives the same field in a hook's `session_end` payload, so one word means the same thing on the wire and in a hook payload; a value outside the vocabulary MUST NOT be emitted here.

**REQ-EVENTS-176** — Recording a notice to a session's timeline under REQ-NOTIFY-268 MUST NOT by itself publish any event. A `warning` notice produces no event at all, consistent with REQ-EVENTS-056, and an `error` notice produces one only by way of the error-severity issue the underlying condition was recorded as (REQ-SESSION-135) — so one failure reaches the event stream exactly once, whether or not it was also shown to the user, and a consumer counting `error` events counts failures rather than renderings. The timeline entry remains the durable record of what the user was told, and REQ-EVENTS-072's ordering rule binds the issue-derived `error` event to its issue record, not to the notice.

### G. Redaction and payload bounding

**REQ-EVENTS-059** — Masking MUST be a property of the event definition rather than of any particular producer: for the fields below, no event delivered on the live channel, no event held in a stored history, and no event inside an exported history or an exported document may carry a value to which the masking of REQ-EVENTS-060 and REQ-EVENTS-063 has not been applied — whatever code produced the event, and whether the field was populated when the event was built or set on it afterwards. The masked fields MUST be: `arguments` on `tool.start`; `summary` on `permission.decision`; `command` on `hook.start`; `output` on `hook.finish`; `summary` on `approval.requested`; `command` within each entry of `checks` on `verifier.result`; and every string at any nesting depth within `row` on `transcript.row`. The mask literal MUST be exactly the three characters `***`, with nothing appended to it.

**REQ-EVENTS-060** — Argument masking MUST render every argument value as a string, since `arguments` is a string-to-string map on the wire. A value whose key names a credential MUST be replaced in its entirety by the mask literal, leaving no fragment of the original value. Key matching MUST be performed on a normalized form of the key in which every `_`, `-` and camel-case boundary becomes a single space and every letter is lower-cased, so that `apiKey`, `api_key`, `API-KEY` and `api key` all match alike; a key whose normalized form contains any of `api key`, `token`, `secret`, `password`, `credentials`, or `auth` MUST count as naming a credential. That list of six is closed: masking is deterministic and testable, and a producer MUST NOT extend or narrow it, so two builds mask the same argument identically. A credential-shaped substring appearing inside the text of a value whose key does not name a credential MUST also be replaced by the mask literal, with the surrounding text left readable. Credential-shaped means exactly these four forms and no others, each recognized by its shape rather than by any measure of the value's randomness: an assignment inside the text — `key=value`, `key: value`, or `key value` where the key is quoted or preceded by a flag marker — whose key normalizes to one of the six fragments above, in which the value alone is masked; an `Authorization` header value or a bearer credential, in which everything after the scheme word is masked; the userinfo password of a URL of the form `scheme://user:password@host`, in which the password alone is masked; and the body of a PEM-delimited private key block, in which everything between the delimiters is masked. No entropy or length heuristic may be used, so an ordinary hash, identifier or path is never masked by accident.

**REQ-EVENTS-061** — Each rendered tool-argument value MUST be clipped to 240 characters plus a trailing single-character ellipsis, so a clipped value is 241 characters long and is distinguishable from an untruncated one. Ordinary short values MUST remain fully readable.

**REQ-EVENTS-062** — Masking MUST be idempotent: re-applying it to already-masked content MUST change nothing, so validation on construction, on assignment, and on re-parse all agree.

**REQ-EVENTS-063** — Masking MUST be applied to a transcript row string before that string is clipped, never after, so that no clipped string can retain a fragment of a value masking would have replaced. Clipping MUST be to 16,000 characters followed by a single `…`, making a clipped string 16,001 characters and distinguishable from one that fitted; the limit counts characters, not bytes. Values inside a row that are not strings MUST pass through unchanged.

### H. Serialization and parsing

**REQ-EVENTS-064** — An event MUST serialize to compact JSON with no spaces after separators, with object keys sorted, and with non-ASCII characters escaped (so that the output survives non-UTF-8 consoles and so that line separators embedded in text cannot break a line). Two equal events MUST serialize to byte-identical lines, so that a consumer comparing two runs sees stable output.

**REQ-EVENTS-065** — A serialized event MUST occupy exactly one line: embedded newlines in payload text MUST be escaped, and a line break that somehow survives serialization MUST raise rather than be emitted.

**REQ-EVENTS-066** — Non-string mapping keys inside a payload MUST be converted to strings before serialization, so that a payload containing, for example, integer keys cannot break serialization mid-stream.

**REQ-EVENTS-067** — Round-trip fidelity: for every event type, serializing an event, decoding the JSON, and re-validating it MUST yield an equal event of the same type, field for field.

**REQ-EVENTS-068** — Strict parsing MUST reject a line whose `event` value lies outside the known catalog, raising a validation error instead of inferring a type. A consumer encountering such a line SHOULD skip it.
