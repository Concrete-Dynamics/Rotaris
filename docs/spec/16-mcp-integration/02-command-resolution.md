# MCP Server Integration — Command Resolution

Part 2 of 6 of [domain 16](../16-mcp-integration.md), which indexes every part. Defines REQ-MCP-028 – REQ-MCP-065.

### Command Resolution

- **REQ-MCP-028** — Path-like commands SHALL never be rewritten by shorthand resolution: commands starting with `/`, `./`, `../`, or `~`, containing a backslash, or in drive-letter form (`X:...`) pass through unchanged.

- **REQ-MCP-029** — A fixed known-executable set SHALL pass through unchanged: `npx`, `npm`, `node`, `uvx`, `uv`, `pipx`, `pip`, `python`, `python3`, `deno`, `bun`, `docker`, `podman`, `bash`, `sh`, `zsh`, `fish`, `cmd`, `powershell`, `pwsh`, `go`, `cargo`, `java`. An empty command is likewise never rewritten — shorthand resolution invents no command — but an entry carrying one never reaches a run: it is rejected at load from a YAML scope and dropped from a discovery file (REQ-MCP-002, REQ-MCP-023), and were one to arise from any other path it is unavailable, never active (REQ-MCP-037).

- **REQ-MCP-030** — The shorthand `uvx:<pkg>` SHALL resolve to command `uvx` with `<pkg>` prepended to the arguments; bare `uvx:` passes through unchanged. When `uvx` is not on PATH, a warning SHALL be logged naming the original command, but resolution still occurs (availability is judged separately, REQ-MCP-037).

- **REQ-MCP-031** — The shorthand `npm:<pkg>`, or any command starting with `@` (a scoped package), SHALL resolve to command `npx` with arguments `-y <pkg>` prepended; bare `npm:` passes through unchanged; a missing `npx` logs the analogous warning.

- **REQ-MCP-032** — Any other bare command name SHALL pass through unchanged — no implicit package-manager guessing for unscoped names.

- **REQ-MCP-033** — The reserved command token `builtin:code-intelligence` SHALL be accepted in place of a real executable for the bundled code-intelligence runtime. It SHALL be recognized before every other rule of this section, so it is never treated as a path (REQ-MCP-028), as a known executable (REQ-MCP-029), as a `uvx:`/`npm:` shorthand (REQ-MCP-030, REQ-MCP-031) or as a bare name (REQ-MCP-032), and it SHALL never be looked up on PATH. A `stdio` entry whose `command` equals that token SHALL resolve to a launch of the bundled code-intelligence server: in an interpreted installation, through the application's own language runtime; in a frozen single-binary installation, through the application's own executable with the same token `builtin:code-intelligence` as its first argument — one literal serves as both the token and the sentinel, so there is nothing else to keep in step. A process started with that first argument SHALL answer the MCP protocol as the code-intelligence server on its standard streams, SHALL present no user interface of any kind, SHALL open no window, and SHALL terminate with the exit status the server produced — whatever that status is, the parent process observes the server's own code and no substitute. The token SHALL be usable by a user in a hand-written entry exactly as the defaults use it, and a `stdio` entry carrying it SHALL count as available unconditionally (REQ-MCP-037).

- **REQ-MCP-034** — When a `stdio` entry's resolved arguments contain the code-intelligence runtime's server-launch subcommand and contain no project-selection argument (neither the explicit project-path option nor the option that takes the project from the working directory), the command line resolved for a run SHALL be the configured one with exactly two further arguments appended at the end of the argument list: the project-path option, followed by that run's workspace root as a separate argument. The match SHALL be made on the presence of the launch subcommand alone, independently of the entry's configured name, so any entry that launches that runtime is bound and no other `stdio` entry is altered. A project-selection argument already present SHALL be left exactly as configured. For a run against an isolated working tree, the appended path SHALL be that tree's root. A server launched with a project path SHALL NOT advertise its project-switching or configuration-introspection tools in `tools/list`. The literal spellings of the launch subcommand and of the two project-selection options SHALL be read from the binding manifest of REQ-MCP-116 and SHALL NOT be written out anywhere else.

- **REQ-MCP-035** — Filesystem-server path fill-in: given a stdio server one of whose resolved arguments is exactly one of the recognized filesystem-server package identifiers — `@modelcontextprotocol/server-filesystem` or `filesystem-mcp` — then, taking the arguments that follow that one as the path arguments: with no path arguments, the workspace root SHALL be appended; with exactly one path argument that does not exist on disk and a server whose configured name is literally `filesystem`, everything after the package identifier SHALL be replaced by the workspace root, accompanied by a warning naming the server, the missing path, and the substituted workspace root; in every other case the arguments SHALL be left untouched.
  > **Narrowed by [`PD-MCP-002`](../../product/directives/pd-mcp-002.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, the root this fill-in appends or substitutes is that tree's root; a path the user configured is left as configured.

- **REQ-MCP-036** — A command-line invocation of the code-intelligence runtime SHALL be derivable from the configured server entry, so that the project setup of REQ-MCP-099 drives the same build the server itself runs. The derived invocation is a command plus an argument list: the command is the entry's resolved `command` (shorthands of REQ-MCP-030 to REQ-MCP-033 expanded), and the argument list is exactly the prefix of the entry's resolved arguments that precedes the first occurrence of the server-launch subcommand, that subcommand and everything after it excluded. Transport, mode and project-selection arguments SHALL therefore never appear in the derived invocation. No invocation SHALL be derived for a remote entry, for an entry whose `command` is empty, or for an entry whose arguments contain no launch subcommand; in each of those cases the dependent setup task SHALL be reported as unavailable with the non-retryable failure of REQ-MCP-099, and no substitute command SHALL be used. The literal spelling of the launch subcommand SHALL be read from the binding manifest of REQ-MCP-116. This derivation exists so the product can run the runtime's own executable as a child process; it is not a surface any user drives.

### Availability and Drop-Not-Fail Semantics

- **REQ-MCP-037** — A single availability rule SHALL be used by every surface (agent construction, desktop UI, initialization-task gating): `http`/`sse` servers count as available unconditionally (nothing probes reachability at configuration time); a `stdio` server whose `command` is the reserved token of REQ-MCP-033 counts as available unconditionally, because what it resolves to ships with the application; every other `stdio` server is available if and only if its command — after shorthand resolution (and, when a workspace is supplied, the full stdio resolution path) — is found on PATH. A `stdio` entry whose `command` is empty or whitespace is **unavailable**; it is never reported as active by any surface, and REQ-MCP-002 and REQ-MCP-023 mean such an entry should not have survived loading in the first place. Supplying a workspace root SHALL never change the answer. No two surfaces may disagree on availability for the same configuration.

- **REQ-MCP-038** — Given a persona referencing a server name absent from configuration, when the persona is resolved, then a warning SHALL be produced naming both the server and the persona, and the run proceeds without that server.

- **REQ-MCP-039** — Given a persona whose generic tool list names a configured MCP server, when the persona is resolved, then the name SHALL be treated as an MCP server with a logged warning advising the user to move it to the server list (see also REQ-MCP-105).

- **REQ-MCP-040** — A server that is disabled SHALL be skipped at persona resolution with an informational log naming the server and stating which of the two controls disabled it: its configured `enabled: false` (REQ-CONFIG-465) or the session override of REQ-MCP-094. A skipped server SHALL produce no warning and no session issue — turning a server off is a choice, not a fault.

- **REQ-MCP-041** — Given an unavailable stdio server carried by a persona, when the agent is constructed, then the server SHALL be dropped with a per-persona warning stating the command was not found on PATH and tools will not be available; additionally, a detailed log line including both the raw and resolved command SHALL be emitted at most once per server per process. The run SHALL never fail for this reason, and the UI SHALL show the server as unavailable.

- **REQ-MCP-042** — Given a server whose most recent tool-discovery attempt failed (REQ-MCP-048), when a persona carrying it is resolved, then a warning SHALL be produced stating the server failed tool discovery and its tools may be unavailable.

- **REQ-MCP-043** — The per-server description handed to the agent runtime SHALL be normalized to exactly the following keys and no others: a transport discriminator distinguishing stdio, streamable HTTP and SSE; for stdio — `command` (resolved per REQ-MCP-028 to REQ-MCP-035), `args` (the resolved argument list), `env` (the resolved environment of REQ-MCP-087), and `cwd` (the entry's configured value, or the workspace root when unset); for remote transports — `url` and, when configured, `headers`; and, when `request_timeout` is set, a numeric `timeout` in seconds. A key not in that list SHALL be absent, and `timeout` SHALL be absent when `request_timeout` is unset, so a consumer can compare the description's key set against this list exactly. Tool disabling, renaming and grants SHALL be applied by the product before this description is produced (REQ-MCP-049, REQ-MCP-059) and SHALL NOT be expressed as additional keys. A remote entry SHALL NOT be subjected to a PATH check while this description is produced. The transport discriminator SHALL take exactly the values `stdio`, `http` and `sse` — the same three tokens the `type` field of REQ-MCP-001 uses, so the domain carries one transport vocabulary and not two, `http` denoting streamable HTTP. This description SHALL be produced for every agent backend the product supports: a backend that cannot be given external tool servers is not a supported backend, and no run path SHALL substitute a backend that silently drops the MCP surface.
  > **Narrowed by [`PD-MCP-002`](../../product/directives/pd-mcp-002.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, an unset `cwd` defaults to that tree's root; a configured `cwd` is unchanged.

- **REQ-MCP-044** — Every warning accumulated during agent construction SHALL be delivered through two channels: a transient acknowledgement of the Warning kind (REQ-NOTIFY-019), which stays on screen for the acknowledgement lifetime of REQ-NOTIFY-011 and for no other span, and a persisted session issue record with kind `mcp_config`, severity `warning`, and actor `orchestrator`, visible in the session's issues file after the run. This document states no lifetime of its own, REQ-NOTIFY-011 being the product's single definition of one and expressly forbidding a surface from declaring another; the durable half of this delivery is the issue record and never the acknowledgement, so no obligation here turns on how long the acknowledgement is readable. *Amended 2026-09-06 under ESC-33: the first channel previously read "a UI toast of severity 'warning' with an 8-second auto-dismiss". The notice pipeline's first execution (ADR-0049, Part V) found that figure to be a second copy of the lifetime REQ-NOTIFY-011 fixes at 4200 ms, and the owner ruled the copy the defect rather than the definition. The 8 s is not preserved anywhere: a warning that must outlive the acknowledgement is a persistent notice under REQ-NOTIFY-040, not a longer transient.*

- **REQ-MCP-045** — The project-initialization task registry SHALL use the availability rule of REQ-MCP-037 to decide whether the code-intelligence setup task applies to a workspace: the server must be configured and its command must resolve.

### Tool Discovery, Caching, and Health Probing

- **REQ-MCP-046** — Tool discovery SHALL connect to a server over its configured transport, perform the MCP `initialize` handshake followed by `tools/list`, and return the server's tool metadata (name, description). The default discovery timeout SHALL be 30 seconds.

- **REQ-MCP-047** — Discovery SHALL be stable and SHALL not re-interrogate an unchanged server. Within the lifetime of one process, repeated discovery requests for a server whose name, `type`, `command`, `args`, `env`, `cwd`, `url`, `headers` and workspace root are all unchanged SHALL yield the same tool list every time, and the server SHALL observe at most one `initialize`/`tools/list` exchange arising from them. A difference in any one of those nine values SHALL make the next request interrogate the server afresh. Reloading the configuration SHALL likewise make the next request for every server interrogate it afresh, so a server that failed discovery before the reload but answers after it SHALL produce no further REQ-MCP-042 warning. This stability is **held for the life of the running instance and never persisted**: no discovery result, failure memory or health outcome SHALL be written to disk or carried across application launches, so a relaunch interrogates every server afresh. Because at most one instance of the application runs (REQ-STARTUP-161), that memory is the whole application's: every window and every run observes the same tool list for a server whose nine values are unchanged — the workspace root being one of those nine, so two windows on different workspaces are correctly interrogated separately — and there is no second holder of a tool list anywhere to wait on, lock against, or invalidate.

- **REQ-MCP-048** — Discovery failure SHALL never raise to the caller: on any connection, protocol, or timeout error the request SHALL return an empty tool list, a warning SHALL be logged at most once per identity noting that the persona prompt will list this server with no tool details attached, and the failure SHALL be remembered for that identity so REQ-MCP-042 warnings can fire later.

- **REQ-MCP-049** — Post-discovery filtering SHALL apply in this order: (1) drop names listed in `disabled_tools` (original names); (2) apply `tool_name_map` renames, preserving descriptions.

- **REQ-MCP-050** — Discovery SHALL use the same resolved command and arguments as launch (so workspace binding per REQ-MCP-034 applies to discovery too), the configured `env`, and `cwd` defaulting to the workspace root.
  > **Narrowed by [`PD-MCP-002`](../../product/directives/pd-mcp-002.md#pd-mcp-002), 2026-10-06.** For a run in an isolated working tree, discovery's default `cwd` is that tree's root, as launch's is.

- **REQ-MCP-051** — Given a stdio discovery in which the tool list was already received before a transport-teardown error occurs, when the connection is torn down, then the received tools SHALL be returned and the teardown error ignored (logged at debug level); an error occurring before the list was received SHALL count as a discovery failure per REQ-MCP-048.

- **REQ-MCP-052** — Discovered tool entries with an empty or non-string name SHALL be dropped; a missing description SHALL become `""`.

- **REQ-MCP-053** — Every tool-discovery request SHALL return a result — the server's tool list, or the empty list of REQ-MCP-048 — no later than the configured discovery timeout plus 5 seconds, measured from the moment the request is issued; with the 30-second default of REQ-MCP-046 that upper bound is 35 seconds. The bound SHALL hold for every caller and every surface that can trigger discovery. No discovery request SHALL fail to return, and an outstanding discovery request SHALL never delay process exit past that bound.

- **REQ-MCP-054** — Any configured server SHALL be probeable on demand, and a probe SHALL return within a default budget of 8 seconds. Each probe SHALL report the state of the server at the moment it runs: probing the same server n times SHALL cause the server to be contacted n times, and no probe SHALL report an outcome carried over from an earlier probe or from tool discovery. A probe reports one of two outcomes — `healthy`, together with the number of tools the server listed on that contact, or `unreachable`, together with human-readable text describing the failure instead of a count. A probe SHALL never raise an error to its caller, SHALL leave the result and the warnings of any later discovery request unchanged, and SHALL still run for a server whose earlier discovery failed.

### Per-Persona Tool Grants

- **REQ-MCP-055** — Grant resolution for a persona SHALL be defined per carried server, by these five cases: (a) a carried name absent from the configuration's server map contributes no tools and produces the warning of REQ-MCP-038; (b) a carried server with no `mcp_tools` entry is unrestricted and contributes every one of its discovered tools that survives REQ-MCP-004; (c) a carried server whose `mcp_tools` entry is an empty list contributes none of its tools; (d) a carried server whose `mcp_tools` entry names tools contributes exactly those of its discovered tools that the decision of REQ-MCP-056 allows, entries matching no discovered tool being inert per REQ-MCP-058; and (e) an `mcp_tools` entry naming a server the persona does not carry is a validation error (REQ-MCP-104). Cases (b) and (c) SHALL be distinguishable in the resulting surface: (b) yields that server's whole surviving surface, (c) yields nothing at all from that server.

- **REQ-MCP-056** — The grant decision for (server, tool) SHALL be: if any candidate spelling of the tool name (REQ-MCP-057) matches `disabled_tools`, the tool is denied regardless of grants; otherwise an unrestricted grant allows it; otherwise it is allowed if and only if a candidate spelling intersects the grant set.

- **REQ-MCP-057** — Candidate spellings for a tool name SHALL be the literal name plus, when the name begins with `<server>_`, `mcp-<server>-`, or `mcp__<server>__`, the unprefixed remainder — added, never substituted — so that a name carrying a client-side server prefix and a grant or disable entry written against the server-reported name still match each other in either direction.

- **REQ-MCP-058** — A grant entry that names a tool the server never reports SHALL be inert: configuration validation, agent construction and the run SHALL all succeed unaffected, and every other tool the same persona grants and the server does report SHALL still be granted. Each unmatched (server, tool) pair SHALL be reported once per process at informational level, stating that the entry matched no tool on that server; the same pair SHALL NOT be reported a second time in that process.

- **REQ-MCP-059** — Grants SHALL be enforced before the model ever sees a tool: filtering happens per server (so server attribution is preserved), a tool that was denied or never granted is absent from the tool list the model receives, and one server's unrestricted grant never leaks another server's withheld tool. When narrowing occurs, a debug log states how many of the server's tools were granted.

- **REQ-MCP-060** — When a connected server publishes a changed tool list after the initial handshake, the persona's callable tool set SHALL be recomputed by the same decision used at connect time (REQ-MCP-056, REQ-MCP-057), and the recomputed set SHALL govern every tool call that persona issues from the moment the update is received onward. A mid-run update SHALL only ever **narrow** that set: a name the update withdraws, or that the recomputed decision now denies, ceases to be callable at once, and calling it is refused per REQ-MCP-062; a name the update introduces that was not present at connect time SHALL NOT become callable for the remainder of that connection, whatever the persona's grants say, because the persona's prompt was rendered before it existed and REQ-MCP-062 forbids a callable name the prompt never printed. An update in which nothing survives the decision therefore empties that server's contribution rather than preserving the previous set: the recomputed set always governs, with no exception for the empty case. Narrowing SHALL NOT close the connection, fail the run, or re-render the prompt.

- **REQ-MCP-061** — A persona's callable tool set SHALL be a function of configuration alone. Where no carried server has an `mcp_tools` entry and no carried server has a non-empty `disabled_tools`, that set SHALL be exactly every tool discovered for the persona's carried servers, with nothing withheld. Where either does apply, the identical filtered set SHALL be observed whether the persona runs in a run the user is watching or in a run the application performs in the background. No configuration and no way of starting a run SHALL hand a persona a tool its grants exclude.

- **REQ-MCP-062** — For every persona and every server that persona carries, the set of tool names printed under that server in the prompt's MCP section (REQ-MCP-101) SHALL be set-equal, **at the moment the prompt is rendered**, to the set of tool names the persona can call on that server: a printed name SHALL be callable, and a name the persona can call SHALL be printed. Calling a name that the prompt does not print SHALL be refused. The names compared are those remaining after denial (REQ-MCP-004), grant filtering (REQ-MCP-056) and renaming (REQ-MCP-005) — a renamed tool is printed and called under its replacement name, and under no other. A mid-run tool-list update may afterwards remove a printed name from the callable set (REQ-MCP-060); it may never add one, so the equality is only ever weakened in the safe direction and the prompt never advertises a name the persona was not granted.

- **REQ-MCP-063** — When two personas of one session carry the same server under different grants, each SHALL see and be able to call only the tools its own grant allows, both at the same time; widening or narrowing one persona's grant SHALL leave the tool set the other persona sees and can call unchanged. How many personas use a server SHALL NOT change how many server processes or connections the session creates — that count stays at one per server for the whole session (REQ-MCP-066).

- **REQ-MCP-064** — Post-connect probes (REQ-MCP-070, REQ-MCP-071) SHALL read the server's unfiltered tool list, so no grant or disable configuration can disarm them.

- **REQ-MCP-065** — Each child run's persisted state SHALL record both its granted native tools and its granted MCP tools as a per-server map of tool-name lists. The desktop agent inspector SHALL render MCP tools grouped per server under a heading whose accessible name is "MCP server <name>", and SHALL match called-tool indicators prefix-tolerantly (a call logged under a name that carries a client-side server prefix still marks the corresponding granted original name as used).
