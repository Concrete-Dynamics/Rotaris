# Workspace Handling, Context Injection, and Project Onboarding

## Overview

The product operates on a user-selected workspace folder: the desktop app resolves which folder to open at startup (remembering the last one, prompting on first launch), shows that folder's path alongside the checked-out git branch in its chrome, keeps per-workspace state in a `.rotaris/` directory layered with global configuration, injects workspace context files (`AGENTS.md`) and a discovered portable-skill catalog (`SKILL.md`) into every agent, runs a one-time background project-initialization step (code-intelligence indexing via a configured MCP server), gates repository-authored hook commands behind an explicit trust review, and guides first-run users toward provider authentication and (on bundled builds) machine tool setup. Throughout, "the code-intelligence runtime" names whatever runtime the build pins behind the MCP server configured under the name `code_intelligence`; that name, the set of built-in server entries it belongs to, and the runtime's own identifiers are fixed elsewhere (REQ-MCP-010, REQ-CONFIG-181, REQ-MCP-116) and this domain names no package, vendor or product of its own. "Claude Code" names an external third-party assistant whose user-global settings may be imported read-only. All quoted strings, sizes, timeouts, and file layouts below are externally observable behavior.

## Requirements

### Application Launch and File-Access Boundary

- **REQ-WORKSPACE-001** — *Withdrawn.* The product is a graphical desktop application with no command-line surface, so it declares no argument vocabulary; workspace selection is carried by REQ-WORKSPACE-009 and REQ-WORKSPACE-016, demo mode by REQ-SHELL-162, diagnostics capture by REQ-SHELL-163, and the running version by REQ-SHELL-033 and REQ-SHELL-140.

- **REQ-WORKSPACE-002** — *Withdrawn.* There are no subcommands and no workspace option; the workspace root is chosen through the folder chooser of REQ-WORKSPACE-009, reached from the title-bar control of REQ-WORKSPACE-016, and applied by the window construction of REQ-WORKSPACE-013.

- **REQ-WORKSPACE-003** — *Withdrawn.* An ad-hoc configuration file named per invocation is reachable only from a shell, and the layered scopes of REQ-WORKSPACE-036 — authored through the Settings view or by hand — are the whole configuration surface.

- **REQ-WORKSPACE-004** — *Withdrawn.* The file-access boundary is not a launch flag; REQ-WORKSPACE-148 states how it is set and shown.

- **REQ-WORKSPACE-148** — The file-access boundary SHALL be the configuration setting `runtime.allow_outside_workspace` (boolean, default `false`, REQ-TOOLS-130), which is reachable through the desktop interface and from nowhere else: the Settings Runtime category (`runtime`, REQ-CONFIG-269) SHALL offer it as a control whose accessible name and description state that turning it on lets agents read and write outside this workspace folder. The setting SHALL be written to the layered YAML configuration by the desktop save of REQ-WORKSPACE-039, so it may be scoped per workspace or globally like any other configuration value, and SHALL NOT be held in the desktop preference store. Given the setting is on, the status-bar file-access flag of REQ-WORKSPACE-022 SHALL read `outside-workspace!`; given it is off, `workspace-scoped`. A change SHALL take effect for runs started afterwards, and the flag SHALL follow the value in force at the moment it is drawn.

### Startup Workspace Resolution and First-Launch Onboarding

- **REQ-WORKSPACE-005** — Given a window is built for an explicitly selected workspace folder — a folder chosen through the chooser of REQ-WORKSPACE-009, or the folder a replacement window is constructed for by the switch of REQ-WORKSPACE-013 — the app SHALL expand and resolve the path, open it directly with no folder chooser, and persist it as the last-opened workspace under the key `workspace/lastOpened` in the per-user preference store (REQ-SHELL-006).

- **REQ-WORKSPACE-006** — Given an ordinary launch with no such explicit selection, the remembered `workspace/lastOpened` value SHALL be used if and only if it names an existing directory; in that case no prompt of any kind is shown.

- **REQ-WORKSPACE-007** — Given an ordinary launch with no explicit selection and no usable remembered path, the app SHALL open on a fallback workspace (default: the directory the application process starts in) for first paint and schedule the first-launch project chooser to appear afterwards. A remembered path that no longer exists SHALL NOT be overwritten in the preference store at this point.

- **REQ-WORKSPACE-008** — The first-launch project chooser SHALL be deferred after first paint by the one shared deferred first-paint delay REQ-SHELL-011 fixes; this domain relies on that requirement for the interval and states no figure of its own. If the window is closed before the delay elapses, the prompt SHALL be cancelled cleanly (no dialog, no crash).

- **REQ-WORKSPACE-009** — Choosing a project folder SHALL use the operating system's native folder chooser, titled "Open a project folder", restricted to directories, starting at the given initial directory or else the user's home directory. The product SHALL be answerable only for what it hands the host dialog — the title, the restriction to directories, and the initial location — and for interpreting every answer that dialog can return (REQ-SHELL-164); keyboard traversal, localization of platform-supplied button text and screen-reader behavior inside a native dialog are inherited and are not requirements on this product. A dismissal by any means the host offers — Cancel, Escape, the window close control, or a platform gesture — SHALL be treated identically: no selection is returned and nothing changes. When the cancelled chooser was the first-launch prompt, a toast SHALL say: "Open a project folder when you're ready by selecting the workspace path in the title bar."

- **REQ-WORKSPACE-010** — Selecting the folder that is already the current workspace SHALL be a no-op.
  > **Superseded by [`PD-WORKSPACE-001`](../product/directives.md#pd-workspace-001), 2026-09-12.** The
  > text above states the behavioural target and is kept for that reason; it no longer states what this
  > product does. Choosing the folder a window already has open now raises a transient notice in that
  > window offering to start a new session in it.

- **REQ-WORKSPACE-011** — On a bundled build that still owes machine setup (see REQ-WORKSPACE-138), the machine-setup modal SHALL be scheduled after first paint with the same shared deferred first-paint delay (REQ-SHELL-011), this domain again stating no figure of its own; only after it completes SHALL the startup git refresh begin and — when this is also a first launch — the workspace chooser prompt continue.

### Workspace Switching

- **REQ-WORKSPACE-012** — Opening another project SHALL be refused while work is in flight, with an error toast stating exactly "Finish the worktree integration before opening another project." while a worktree integration is running, or "Finish the active run before opening another project." while any run is active or the run state is busy.

- **REQ-WORKSPACE-013** — A workspace switch SHALL construct a fresh main window for the selected folder. Given construction fails, the old window SHALL remain fully usable and an error toast SHALL say "Could not open the selected project: {reason}". Given construction succeeds, the replacement window is shown, the old window is closed (and if the old window vetoes its close, the replacement is closed instead and the old window stays), `workspace/lastOpened` is updated, and the git refresh, update check, and cloud-credit polling start on the new window. A background initialization run still under way in the outgoing window SHALL NOT delay or refuse the switch: it SHALL be cancelled on exactly the terms of REQ-WORKSPACE-109 — no task that has not started begins, a task already under way reaches its own conclusion, and every process it launched is ended as REQ-WORKSPACE-092 requires — nothing SHALL be recorded for the cancelled run, so the tasks stay pending and run again the next time that workspace is opened. The replacement window SHALL resolve initialization for its own workspace independently of the outgoing one, and its resolution SHALL NOT wait on the cancellation to finish.

- **REQ-WORKSPACE-014** — Post-show activation order SHALL be: window shown → git refresh starts (skipped until machine setup completes on a bundled first run) → workspace-storage determination starts (REQ-STARTUP-043, REQ-STARTUP-166; skipped entirely in a demo window) → update check starts → cloud-credit polling starts (skipped entirely in a demo window, REQ-SHELL-162). The enumeration here is this domain's view of the same activation REQ-STARTUP-043 fixes; where the two differ, REQ-STARTUP-043 governs and this line is the defect.

- **REQ-WORKSPACE-015** — The main window SHALL be titled "Rotaris" and SHALL host exactly the seven primary views of REQ-SHELL-023, in the fixed order that requirement states; this domain SHALL NOT name a parallel view vocabulary of its own. Its opening geometry and its minimum size are those of the desktop shell specification (REQ-SHELL-022), and every control this domain adds SHALL be reachable and fully labelled at that minimum size.

### Desktop Workspace and Branch Display

- **REQ-WORKSPACE-016** — The title bar SHALL contain a workspace control with accessible name "Open project folder" and accessible description "Current project: {workspace_path}. Opens the native project folder chooser."; it SHALL be keyboard-focusable, and both a mouse click and the Return key SHALL open the folder chooser.

- **REQ-WORKSPACE-017** — The title-bar workspace control SHALL render a folder icon, the workspace path in the monospace face at the smallest text scale, a `·` separator, and the current session name (or `—` when there is none); its rendering SHALL refresh on theme changes so colors follow the active theme.

- **REQ-WORKSPACE-018** — The bottom status bar SHALL keep one fixed height taken from the active theme (it never grows or shrinks with its contents) and lay out, left to right: workspace path (a link), git branch, flexible space, safety flags, model, token count, cost, cloud-credit balance, and background-session count. Of these, only the workspace path and the cloud balance SHALL be activatable; all other readings are non-interactive.

- **REQ-WORKSPACE-019** — The status-bar workspace path SHALL be a link with accessible name "Workspace folder" and tooltip/description "Workspace folder: {path}. Opens it in your file manager."; activating it opens the folder in the OS file manager, and a failure to open SHALL be silent.

- **REQ-WORKSPACE-020** — The status-bar branch item SHALL be non-clickable text with accessible name "Checked-out branch". It SHALL render a branch icon followed by the branch name, and — only when the ahead count of REQ-WORKSPACE-029 is greater than zero — a trailing ` ↑{n}`; the behind count SHALL never appear on this item. Its tooltip and accessible description SHALL be one and the same string: "Branch this workspace is on: {branch}, 1 commit ahead." for an ahead count of exactly one, "Branch this workspace is on: {branch}, {n} commits ahead." for a count above one, and "Branch this workspace is on: {branch}." for a count of zero. The item SHALL render as empty text — no icon, no arrow, no tooltip — exactly when the snapshot's branch name is empty, which per REQ-WORKSPACE-029 covers git being unavailable, the folder not being a repository, a detached HEAD, and an unborn branch. While the active run executes in an isolated worktree, the item SHALL show that worktree's own branch name — the generated branch of REQ-GIT-007 where the run accepted the generated default, or the name the user supplied — rendered exactly as any other branch name is, with the ahead count and the ` ↑{n}` suffix computed against that branch's upstream rather than the base checkout's. A worktree carrying no branch of its own SHALL render as empty text under the rule already stated. Only the accessible description differs: it SHALL additionally convey that the branch belongs to the isolated worktree the active run is using rather than to the folder the window is open on, in wording of the implementation's choosing. No identifier other than a branch name — not the run's identifier, not the worktree's path — SHALL appear on this item.

- **REQ-WORKSPACE-021** — Responsive elision of the status bar SHALL be the hiding REQ-SHELL-047 specifies: this domain relies on that requirement for which of the two labels is hidden first and for the window widths at which each is hidden, and states no width of its own. What this domain adds is that the path label so hidden is the workspace path link of REQ-WORKSPACE-019, and that hiding it removes the label only — the workspace it names is unchanged and remains reachable from the title-bar control of REQ-WORKSPACE-017.

- **REQ-WORKSPACE-022** — The safety flags shown beside the path and branch SHALL be exactly these five, each with an explanation reachable both as its tooltip and as its accessible description:
  - a file-access scope flag, always present, reading `workspace-scoped` while file access is confined to the workspace folder, explained "File access: agents may read and write inside this workspace folder only.", or `outside-workspace!` once the setting of REQ-WORKSPACE-148 has widened it, explained "File access: agents may read and write outside this workspace folder.";
  - a `mode: {permission_mode}` flag, always present, whose substituted value is drawn from exactly the three-value preset vocabulary of REQ-TOOLS-046 — `restricted`, `ask`, `autonomous` — and is the **effective** mode after any downgrade REQ-TOOLS-067 applies, not the requested one, so the flag never claims a permissiveness the run does not have. This domain SHALL NOT define a fourth value or a parallel spelling;
  - a `redaction: always on` flag, always present;
  - a `● CB armed` flag, present only while the circuit breaker is armed;
  - an `unsaved settings` flag, present only while settings hold edits not yet written to disk (REQ-WORKSPACE-039).

  The two file-access explanations above are fixed strings because they are the pair a reader compares. The other four explanations are human-readable message text whose wording is left to the implementation, and each SHALL convey exactly the following and no more: for the mode flag, which permission mode is in force and that it decides whether a tool call is allowed outright, put to the user, or refused; for the redaction flag, that secrets are removed from what is recorded and displayed and that this cannot be turned off; for the circuit-breaker flag, that the circuit breaker is armed and will halt a run that trips it; for the unsaved-settings flag, that the Settings view is holding edits which have not been saved and that runs use the values on screen rather than the values on disk. Every one of the five flags SHALL be distinguishable without relying on colour (REQ-SHELL-149), and each SHALL expose its explanation both as its tooltip and as its accessible description.

### Workspace and Branch Label Rendering

- **REQ-WORKSPACE-023** — *Withdrawn.* There is no terminal status bar; REQ-WORKSPACE-149 carries the home-directory collapsing and literal rendering of the workspace path and branch name in the desktop window chrome.

- **REQ-WORKSPACE-024** — *Withdrawn.* There is no terminal status bar; REQ-WORKSPACE-149 carries middle elision of a path too wide for the space it is drawn in.

- **REQ-WORKSPACE-025** — *Withdrawn.* Branch reading is the workspace git snapshot of REQ-WORKSPACE-029, whose degradation rules already cover an absent git, a folder that is not a repository, a detached HEAD, and an unborn branch.

- **REQ-WORKSPACE-026** — *Withdrawn.* REQ-WORKSPACE-150 carries the refresh cadence, the stale-result guard, and the non-overlap rule for the desktop.

- **REQ-WORKSPACE-027** — *Withdrawn.* REQ-WORKSPACE-149 carries the literal rendering of markup-like characters.

- **REQ-WORKSPACE-149** — Wherever the window chrome displays a workspace path or a branch name — the title-bar control of REQ-WORKSPACE-017, the status-bar path link of REQ-WORKSPACE-019, and the status-bar branch item of REQ-WORKSPACE-020 — the label SHALL be rendered under these three rules.
  1. *Home collapsing.* A resolved path equal to the user's home directory SHALL render as `~`; a path beneath it SHALL render as `~`, the platform path separator, and the remainder relative to home; any other path SHALL render absolute. Collapsing SHALL apply to the displayed label only: the tooltip, the accessible description, and any path handed to the operating system SHALL carry the full absolute path.
  2. *Middle elision.* A label wider than the space available SHALL be shortened from the middle, the removed span standing in as exactly one `…`, so that the beginning and the end of the path both stay legible. The budget is the rendered width available to that label in the layout, so the question of counting units does not arise; the label SHALL be recomputed whenever that width changes. Elision SHALL never change the tooltip or the accessible description, which always carry the full text (REQ-SHELL-022). Where the space available cannot hold even `…`, the label SHALL be hidden entirely rather than drawn clipped, on the terms REQ-WORKSPACE-021 already states for the status bar.
  3. *Literal text.* A path or branch name SHALL be rendered as literal text and SHALL NOT be interpreted as markup, formatting, or a control sequence of any kind, whatever characters it contains, so that a repository cannot influence the window's rendering by the name of a branch.

- **REQ-WORKSPACE-150** — The desktop status bar's git readings SHALL be kept current without user action. On workspace open the bar SHALL render from the snapshot of REQ-WORKSPACE-029 and start a refresh; thereafter it SHALL refresh every 10.0 s for as long as the window is on screen. A workspace or session switch SHALL trigger an immediate refresh rather than waiting for the next interval. Refreshes SHALL run off the interface's own thread of control and SHALL never make the window stop accepting input (REQ-WORKSPACE-028, REQ-WORKSPACE-030). Refreshes SHALL never overlap: a refresh SHALL NOT start while one is outstanding, and the interval SHALL be measured from the completion of the previous refresh. A result arriving after the workspace it was gathered for is no longer the current one SHALL be discarded rather than displayed. While the status bar is not on screen, no refresh SHALL be performed and no refresh timer SHALL be running; when it becomes visible again its first painted frame SHALL already carry current values.

### Git Reading and Degradation

- **REQ-WORKSPACE-028** — Git interaction SHALL be read-only by default. Reads run git as a subprocess in the workspace with a 15 s timeout and UTF-8 decoding with replacement of undecodable bytes; on the read/refresh path any refusal, error, timeout, or missing binary SHALL degrade to an empty result (never an exception surfaced to the user). Mutating operations (worktree create/remove, repository preparation) SHALL instead fail with an error carrying git's own stderr, or — when git is absent — the exact message "Git is not available on this machine, so there is nothing to read or change."

- **REQ-WORKSPACE-029** — A workspace git snapshot SHALL be gathered without the interface ceasing to accept input, and SHALL become visible all at once: anything reading the snapshot while a refresh is under way SHALL see either the whole of the previous snapshot or the whole of the new one and never a mixture of the two, and a change notification SHALL follow the replacement. The snapshot SHALL contain: whether git is available; the current branch name, empty for a detached HEAD and for an unborn branch; the number of commits ahead of and behind the upstream, both zero whenever that comparison cannot be made (no upstream, no repository, or any failure); the list of worktrees, each carrying its branch name or the literal `detached` when it has none, together with a base branch of `main` or `master`; the 30 most recent commits, each with its date expressed relative to the present; the number of paths git reports as changed in the working tree; and diff statistics against HEAD, plus for each worktree the same statistics for its committed changes measured against its merge base with that worktree's base branch.

  Three details of that snapshot are fixed here. *Diff statistics* comprise exactly three non-negative integers and nothing else: the number of files changed, the number of lines inserted, and the number of lines deleted. *The number of changed paths* counts every path the working tree differs from HEAD in, tracked or not — a file the user has just created is a change they can see, so excluding it would make the reading disagree with what the Git view shows — except that a path the repository ignores SHALL NOT be counted, since an ignored path is one the repository has said is not part of it. *A commit's relative date* is human-readable text whose wording is left to the implementation, required only to convey the elapsed time from that commit's author date to the present, coarsened to a single unit, never expressed as a time in the future, and never so coarse that two commits made days apart read alike; the exact instant SHALL remain available as the commit row's tooltip and accessible description.

- **REQ-WORKSPACE-030** — The startup git refresh SHALL run exactly once, after the first frame is shown, without blocking the interface. User-requested git mutations SHALL refresh the snapshot synchronously at their own boundary.

- **REQ-WORKSPACE-031** — Given the `git` binary itself is missing (a version probe fails within the 15 s timeout), a persistent INFO notice with a stable identity SHALL be published: title "Working without Git", message "Git is not installed or not on PATH, so this workspace has no history and no worktrees. Everything else works, and Rotaris makes its changes in place instead of in a worktree of its own." A folder that merely is not a git repository SHALL raise no notice.

- **REQ-WORKSPACE-032** — A "Set up Git here" offer SHALL be available whenever git is installed, and when taken SHALL perform, in order:
  1. Initialize a repository only when the folder is not already one.
  2. Before any write, refuse if the git identity (`user.email`/`user.name`) is unset, with exactly this message:

     ```
     Git does not know who you are yet, so it cannot make a commit. Set that once, from anywhere:

         git config --global user.name "Your Name"
         git config --global user.email "you@example.com"

     Then take this offer again.
     ```
  3. Append (never rewrite) `.gitignore` with the comment line `# Rotaris keeps its sessions and delivery records here.` and the single rule `.rotaris/`, skipping the append when that exact rule is already present.
  4. Stage everything; if nothing ends up staged, fail with "There is nothing to commit yet — this folder is empty apart from what Rotaris keeps for itself. Add a file, then try again."
  5. Create exactly one commit with the message `Initial commit`.

  On success it SHALL report "Committed everything in this folder as “Initial commit”." with the suffix " '.rotaris/' was added to .gitignore." when the rule was added. The operation SHALL be idempotent (taking the offer twice never creates a second commit) and SHALL never contact or configure a remote.

- **REQ-WORKSPACE-033** — Live worktree records SHALL be joined against persisted session records by resolved worktree path, so a worktree row can display its session id, execution status, and merge status.

### Workspace State Directory and Configuration Layering

- **REQ-WORKSPACE-034** — Per-workspace state SHALL live under `<workspace>/.rotaris/`. The workspace-scope configuration file is `<workspace>/.rotaris/agents.yaml`; each configuration scope directory is additionally read for a `models.yml` file.

- **REQ-WORKSPACE-035** — *Withdrawn.* The product has no earlier release under another name, so there is no legacy workspace, configuration, or data directory to adopt; `<workspace>/.rotaris/` (REQ-WORKSPACE-034) is the only per-workspace state directory the product ever reads or writes.

- **REQ-WORKSPACE-036** — Configuration SHALL be assembled from five layers, listed here from lowest precedence to highest: built-in defaults, whose hook entries are stamped with origin scope `default`; MCP servers discovered from `.mcp.json` files; provider snapshot models recorded in the per-user configuration directory; global scope, being `<per-user-config-dir>/agents.yaml` together with `models.yml` from the same directory, whose hook entries are stamped `global`; and workspace scope, being `<workspace>/.rotaris/agents.yaml` together with `models.yml` from the same directory, whose hook entries are stamped `workspace`. A setting defined in more than one layer SHALL take its value from the highest-precedence layer that defines it; a setting a layer leaves undefined SHALL keep the value it had from below. A list-valued setting SHALL be replaced whole by the higher layer rather than appended to (REQ-WORKSPACE-125 states the one exception, which applies to untrusted workspace hook lists). The workspace root is the folder the window was opened on (REQ-WORKSPACE-005 through REQ-WORKSPACE-007). The provider snapshot layer is the per-user provider catalog snapshot `project_settings.yaml` in the per-user configuration directory, whose document shape, atomic write, and merge into the effective configuration are specified in the model-providers specification (REQ-PROVIDER-084, REQ-PROVIDER-085, REQ-PROVIDER-091); this domain fixes only its position in the precedence order above and SHALL NOT restate its contents. A snapshot that is absent, or that fails that specification's validation, SHALL contribute nothing and SHALL NOT make configuration load fail.

- **REQ-WORKSPACE-037** — The `.mcp.json` discovery layer of REQ-WORKSPACE-036 SHALL be the discovery specified by REQ-MCP-017 and by the requirements it names: this domain relies on that specification for which two files are read and where they live, for the file's accepted shape and keys, for name and placeholder handling, for the precedence between the user-level and project-level files, and for the guarantee that a malformed file or entry is skipped with a warning and never aborts configuration load. This domain adds only two things and restates nothing else. First, the project-level file is located against the workspace root this domain fixes — the folder the window was opened on (REQ-WORKSPACE-005 through REQ-WORKSPACE-007) — so `${workspaceFolder}` resolves to that same root. Second, whatever discovery yields enters the five-layer assembly of REQ-WORKSPACE-036 at the position stated there, below both YAML scopes.

- **REQ-WORKSPACE-038** — A minimal bootstrap `agents.yaml` SHALL be writable. Its content is fixed rather than generated, and SHALL be exactly the scope-independent starter document of REQ-CONFIG-025: a short comment header conveying that the file is a minimal starting configuration, that editing it overrides the built-in personas, models, and tool servers, and that real models are wired up by authenticating a provider in the Settings Models category (REQ-WORKSPACE-152) — the wording of those three lines being left to the implementation — followed by `default_persona: orchestrator` and by exactly the twelve explicitly-null keys that requirement enumerates: `default_summary_model`, `default_summary_model_thinking`, `large_model`, `large_model_thinking`, `medium_model`, `medium_model_thinking`, `small_model`, `small_model_thinking`, `fallback_model`, `fallback_model_thinking`, `improvement_collector_model`, `improvement_collector_model_thinking`. Because those keys belong to the replace-if-not-null class (REQ-CONFIG-041), writing them as nulls overrides nothing from a lower layer. The file SHALL be written to a temporary file and then put in place by replacement, and SHALL end up with mode 0o644. A write request SHALL do nothing and report the reason "already exists" unless overwriting was explicitly asked for. Bootstrap SHALL be reported as needed when the target path is missing, holds nothing but whitespace or nothing at all, is a directory, or cannot be decoded as text.

- **REQ-WORKSPACE-039** — Saving desktop settings SHALL read `<workspace>/.rotaris/agents.yaml`, change it, and put the result back through an atomic replace. Top-level keys the application does not itself manage SHALL survive the round trip verbatim. The keys the save writes are exactly those REQ-CONFIG-256 enumerates — the model slots and their reasoning companions, the runtime keys including `runtime.allow_outside_workspace` (REQ-WORKSPACE-148) and `runtime.permission_mode`, the six confinement and egress fields, `circuit_breaker.enabled`, `compressor.threshold_percentage`, the delegation strategy, and `skills.enabled`, `skills.overrides` and `skills.invocation_overrides` — and this domain SHALL NOT name a key that requirement does not. A persona edit whose chosen scope is global SHALL be written to the global `agents.yaml` instead of the workspace one. Validation SHALL happen before any file is opened for writing, on the terms of REQ-CONFIG-260: where the schema rejects any of the six confinement or egress values the save SHALL be abandoned, every configuration file SHALL be left byte-for-byte as it was and still loadable, and the user SHALL be shown a single sentence carrying the first complaint. A save that completes SHALL be followed by a configuration reload and by re-projecting the skill list from a freshly discovered catalog.

  > **Extended by [`PD-WORKSPACE-002`](../product/directives.md#pd-workspace-002), 2026-09-21.** The
  > save additionally writes the `instructions.overrides` per-file policy into the workspace file, on
  > the same sparse terms as the skill maps; the keys the save writes are otherwise exactly those named
  > above.

- **REQ-WORKSPACE-040** — Writers of the persisted initialization state SHALL round-trip the entire YAML document and land via atomic replace, so that a crash partway through writing cannot leave the user's configuration truncated; when no `agents.yaml` exists, the minimal bootstrap file SHALL be written first.

### Workspace Context Injection (AGENTS.md)

- **REQ-WORKSPACE-041** — Context-file discovery SHALL be workspace-root-only: in the resolved workspace root, `AGENTS.override.md` is used when present, otherwise `AGENTS.md`; nothing else. Those two names are the whole vocabulary. No other directory SHALL be consulted — not an ancestor, not the enclosing repository root, not an intermediate directory, not a user-global location — and no other file name SHALL be read or injected, user-global context files, `CLAUDE.md`, `GEMINI.md`, and any product-named alternative such as a root-level `ROTARIS.md` included, even when such a file is present at the workspace root. This is a closed rule rather than an omission: a multi-level scheme would make what an agent was given depend on where the folder happens to sit in a tree the user did not choose, and the override file already provides the one thing a second level would be for. A broader scheme, if ever wanted, requires its own requirement and is not implied by anything here.

  > **Extended by [`PD-WORKSPACE-002`](../product/directives.md#pd-workspace-002), 2026-09-21.** The

- **REQ-WORKSPACE-044** — Size limits SHALL default to 32,768 bytes for any one context file and 131,072 bytes for the merged output, both measured as UTF-8 bytes and both overridable per call. A file exceeding the per-file limit SHALL be cut back to the last line boundary that fits within it; a file whose very first line already exceeds the limit SHALL contribute nothing at all. Against the total limit, the budget left for a file SHALL be reckoned after its source-comment line has been charged: a file that does not fit whole SHALL be cut down to whatever budget remains, and a file for which no budget remains — including the case where its source comment alone would exhaust it — SHALL be dropped in its entirety, source comment included. A cut made against the total budget SHALL fall back to the last line boundary that fits within the remaining budget, exactly as a cut against the per-file limit does — one truncation rule governs both, so no block ever ends mid-line — and a file whose very first line already exceeds the budget remaining to it SHALL be dropped in its entirety, source comment included, rather than contributing a fragment. Every truncation and every drop SHALL produce a log warning naming the file concerned. The merged output SHALL never exceed the total limit.

- **REQ-WORKSPACE-045** — A whitespace-only context file SHALL be skipped silently (no block, no source comment). An unreadable file (I/O or decoding error) SHALL be skipped with a warning naming the path and the error, without aborting discovery.

The cache (together with the skill-catalog cache) SHALL be cleared on every session creation, so each new session re-reads context files from disk. An explicit cache-clear operation SHALL force a reload.

- **REQ-WORKSPACE-047** — Given context injection is enabled and the merged content is non-empty, each agent built for that session SHALL receive the content as its own permanently active context block, ordered ahead of the skill catalog, ahead of any always-on skill bodies, and ahead of persona memory. With no context files, or injection disabled, no such unit SHALL be constructed.

- **REQ-WORKSPACE-048** — The per-workspace configuration key `inject_agents_md` (boolean, default `true`) SHALL control injection; when false, no context file is read at all.

- **REQ-WORKSPACE-049** — Discovering and merging workspace context files SHALL complete within 200 ms for a workspace holding up to 20 context files totalling 1 MiB on local storage. It SHALL NOT delay the moment the interface first accepts input, and the window SHALL keep responding to input for as long as it runs. For an unchanged filesystem state, running it again in a separate process SHALL yield byte-identical output: the merged text SHALL carry no timestamp, no process identifier, and no ordering that varies from run to run. The 200 ms figure SHALL be measured under these reference conditions and no others: the workspace on local, non-removable storage; the filesystem cache **cold** for the files concerned, so the figure covers the first read after a workspace is opened rather than a repeat of it; up to 20 context files totalling 1 MiB; and the reported figure being the 95th percentile of at least 20 consecutive cold measurements taken in separate processes, rather than a mean or a best case. Conformance is assessed per machine: a build meets this requirement on a machine when it meets the figure there under those conditions. The determinism and responsiveness guarantees stated here hold unconditionally, on every machine and under every load.

### Portable Skill Discovery and Parsing (SKILL.md)

- **REQ-WORKSPACE-051** — Skill discovery SHALL search the locations below in exactly the order given, the first location to yield a particular normalized name winning outright over every later one:
  1. Project scope, covering every directory from the resolved workspace root upwards to and including the enclosing repository root — the nearest ancestor holding a `.git` entry, which may be a directory **or** a file so that a linked worktree root also ends the walk, and the workspace root itself when no such ancestor exists. Directories SHALL be visited nearest first, and within one directory `<dir>/.agents/skills/<name>/SKILL.md` SHALL be searched before `<dir>/.opencode/skills/<name>/SKILL.md`.
  2. User scope, searched in the order `~/.agents/skills`, then `~/.config/opencode/skills`, then `~/.openhands/skills/installed`, then the machine-wide `/etc/codex/skills`.

  Every project-scope location SHALL outrank every user-scope location. Within any of these roots, only immediate child directories count, and only those holding a `SKILL.md` file; children SHALL be visited in ascending name order, so that the outcome never depends on the order the filesystem happens to list them in. On a platform that has no `/etc` hierarchy, user scope SHALL simply end at the three home-relative roots: no platform-specific machine-wide path SHALL be substituted, and the product SHALL declare no fourth user-scope root on any platform. The reason is stated with the rule — a machine-wide directory carries skills the account using the product may not have written, and the platforms that lack `/etc` do not offer a directory with the same ownership guarantees, so silently substituting one would widen what can reach an agent's context on that platform alone.

- **REQ-WORKSPACE-052** — Given `~/.openhands/skills/.installed.json` exists, skill directories whose name (or normalized name) matches a disabled entry SHALL be skipped. Accepted manifest shapes: a map with a `disabled: [names]` list; a map whose values are maps carrying `disabled: true` (any of the entry key, a `name` field, or a `path` field identifies the skill); or a list of maps with `disabled: true`. An unreadable manifest SHALL log a warning and disable nothing.

- **REQ-WORKSPACE-053** — A valid `SKILL.md` SHALL begin with YAML frontmatter delimited by `---` lines; the frontmatter must be a mapping and must contain `name` and `description`. Invalid files SHALL be skipped with a logged reason (e.g. missing frontmatter, malformed YAML, missing required field, unsupported trigger shape, unreadable file) and discovery SHALL continue — an invalid skill never crashes startup. Unknown frontmatter fields SHALL be preserved and available as raw metadata.

- **REQ-WORKSPACE-054** — Skill names SHALL normalize as: lowercase; every run of characters outside `[a-z0-9]` becomes `-`; leading/trailing `-` stripped. A name normalizing to empty is invalid. On collision the earlier (higher-priority) skill SHALL win, and the shadowed one SHALL be recorded and reportable per name.

- **REQ-WORKSPACE-055** — The canonical trigger shape SHALL be `trigger: {type: keyword, keywords: [...]}`; legacy top-level `type:` plus `triggers:` aliases SHALL be accepted and normalized. Only the `keyword` type is supported; the keyword collection SHALL contain nothing but strings; entries are stripped and de-duplicated preserving order. Description whitespace SHALL be collapsed to single spaces.

- **REQ-WORKSPACE-056** — A skill's invocation mode SHALL derive from frontmatter: `user-invocable: false` → auto-only; `disable-model-invocation: true` → manual-only; otherwise default.

- **REQ-WORKSPACE-057** — Manually loading a skill SHALL accept a path to a `SKILL.md` file or a directory containing one, with `~` expansion and relative paths resolved against the workspace root; failures are "SKILL.md not found: {raw}" and "manual skill path must be a SKILL.md file or directory: {raw}". Manual skills carry the scope label `manual`, override a discovered skill of the same normalized name, apply to the current session only, and persist nothing.

- **REQ-WORKSPACE-058** — The skill catalog SHALL be cached per resolved workspace root and cleared on every session creation, so skills are re-discovered from disk at each new session; discovery runs automatically on workspace open with no user action.

- **REQ-WORKSPACE-059** — The sorted, resolved set of all cataloged skill directories SHALL be registered as additional read roots for agent file tools: an agent can read a `SKILL.md` and its sibling resources even when the skill directory lies outside the workspace, while writes to those roots SHALL still be rejected.

### Skill Catalog Injection and Load Policies

- **REQ-WORKSPACE-060** — At agent construction a compact skill catalog SHALL be injected as its own always-active context unit, distinct from the persona prompt, the workspace context unit, and persona memory. Ordering of injected context units SHALL be: workspace context → skill catalog → force-loaded skill bodies → persona memory.

- **REQ-WORKSPACE-061** — The catalog block SHALL contain a preamble followed by exactly one entry per catalogued skill and nothing else. The preamble SHALL convey three facts, in wording of the implementation's choosing: that every entry below names a `SKILL.md` file that exists on disk; that such a file is to be opened only when the task in hand calls for it; and that none of those files' contents have already been supplied. Each entry SHALL be a single line carrying, in this order, the skill's normalized name, its description, and the absolute path of its `SKILL.md`, in the shape given under Data & Formats. Entries SHALL appear in ascending normalized-name order. No skill's body text SHALL appear anywhere in the block.

- **REQ-WORKSPACE-062** — Each skill SHALL carry a load mode drawn from the closed set `off | name-only | user-invocable-only | on`, defaulting to `name-only`, and offered in the user interface under the labels "hidden" / "on-demand" / "manual only" / "always". The mode determines what an agent ends up with:
  - `name-only`: an entry for the skill is present in the injected catalog, and the user can invoke it.
  - `on`: no entry for the skill is present in the catalog; in its place the skill's body, with the YAML frontmatter removed, is present as an always-active block of its own. That block SHALL be introduced by a statement naming the skill and directing that its guidance apply from that point onwards — unconditionally, with no trigger phrase awaited and no question asked about whether to activate it. Given the body cannot be read, no such block SHALL be present, every other part of the agent's context SHALL be exactly as it would otherwise have been, and a log warning naming the skill SHALL be emitted.
  - `user-invocable-only`: no entry for the skill is present in the catalog, and the user can still invoke it.
  - `off`: the skill appears nowhere and cannot be invoked.

- **REQ-WORKSPACE-063** — Each skill SHALL have an invocation mode from `default | manual-only | auto-only`: manual-only removes it from the model-facing catalog (user command only); auto-only removes it from user invocation (model catalog only). Workspace-configured invocation overrides SHALL take precedence over the frontmatter-derived mode.

- **REQ-WORKSPACE-064** — A global switch `skills.enabled` (default `true`) SHALL control the whole feature: when false, no catalog is injected, no body is force-loaded, and no skill is user-invocable.

- **REQ-WORKSPACE-065** — The chosen per-workspace load and invocation policies SHALL be persisted in `<workspace>/.rotaris/agents.yaml` and SHALL govern agents constructed afterwards. A workspace with no recorded policy SHALL behave as on-demand load with default invocation for every skill (zero-migration default). Policy SHALL be per workspace and SHALL NOT be scoped per persona: every agent built for a session SHALL see the same catalog and the same force-loaded bodies, so a skill can never be visible to one persona and hidden from another. This is a closed rule; per-persona scoping, were it ever wanted, requires its own requirement.

- **REQ-WORKSPACE-066** — Skill bodies SHALL enter model context only through the agent's own filesystem/shell tools, an explicit user command, or the "always" load policy; the framework SHALL NOT pre-fetch or rewrite bodies, and scripts referenced by skills run via the shell with only their stdout/stderr entering context.

### Skill Controls in Settings

Ignored duplicate(s):" followed by the shadowed `SKILL.md` paths; a per-row invocation selector (accessible name "Invocation policy for {name}") offering "default (both)", "manual only", "auto only"; a per-row load selector (accessible name "Load policy for {name}") offering "on-demand", "always", "manual only", "hidden"; two header actions, "Rescan skills" (REQ-WORKSPACE-069) and "Load skill file…" (REQ-WORKSPACE-151); and the empty state "No portable skills were discovered." In addition, the Settings Skills tab SHALL carry a "Rescan skills" action (accessible description stating that it re-reads skill files from disk for this workspace). ### Project Initialization Framework

- **REQ-WORKSPACE-078** — Persistent initialization state SHALL be the `initialization:` section of `<workspace>/.rotaris/agents.yaml` with fields `completed: [ids]`, `skipped: [ids]`, `last_run: <ISO-8601 UTC>`, `classification: code|non-code|null`. A missing file, missing key, or bare empty section reads as a default state that is "never initialized". Never-initialized SHALL mean: no `last_run` and both lists empty. A task is resolved when its id appears in either list.

- **REQ-WORKSPACE-079** — Recording an outcome SHALL move, not duplicate: the task id is removed from both lists first, then appended to the chosen one. `classification` SHALL be overwritten only by a non-null value. `last_run` SHALL be stamped on every recorded outcome, the degenerate case of "no task applied" included; that stamp on its own is what stops such a workspace from still counting as never initialized. Writes SHALL preserve every other top-level YAML key and be atomic.

- **REQ-WORKSPACE-080** — An initialization task SHALL be described by an id, display label, description, an applicability predicate, a runner, and a consent flag defaulting to false. Registering a duplicate id SHALL fail with "Initialization task '{id}' is already registered" unless replacement is requested; unregistering an unknown id is a no-op. An applicability predicate that raises SHALL be logged and treated as "not applicable". A setup task added after the fact SHALL participate in the prompt and in the setup UI under exactly the rules stated here, with no additional behavior of its own.

- **REQ-WORKSPACE-081** — The task sets SHALL be derived as follows, from the applicability predicate of REQ-WORKSPACE-080 and the two persisted lists of REQ-WORKSPACE-078. A task is *applicable* when its predicate is satisfied, whatever is recorded about it; a predicate that raises counts as not applicable (REQ-WORKSPACE-080). It is *pending* when it is applicable and its id appears in neither the completed list nor the skipped list. It is *runnable* when it is applicable and its id is not in the completed list — a skipped task therefore remains runnable and is offered again by a manual initialization. It is a *background* task when it is pending and does not require consent, and a *consent* task when it is pending and does require consent. An id that a hand-edited file has placed in both lists at once counts as completed, and is therefore neither pending nor runnable. A skipped id is not a pending one, so reopening the workspace SHALL NOT restart a background task the user has skipped; only the manual initialization of REQ-WORKSPACE-113 brings such a task back.

- **REQ-WORKSPACE-082** — The setup prompt SHALL be shown if and only if at least one consent-requiring task is pending. Whether the workspace as a whole has ever been initialized SHALL play no part in that decision, so finishing a background task can never swallow a prompt still owed for a consent-requiring task pending beside it. A task that declares nothing about consent behaves as background.

- **REQ-WORKSPACE-083** — On workspace open, resolution SHALL run once and produce: for a never-initialized workspace with no applicable task, a silent marking as initialized (empty task list, `last_run` stamped) with nothing shown or started; for pending consent tasks, a prompt request listing the runnable tasks; for pending background tasks, an immediate-start list regardless of whether a prompt is also due. Where the sole outstanding work in such a workspace is background work, no marker SHALL be written up front; it is stamped only once that work has run to completion.

- **REQ-WORKSPACE-084** — An execution SHALL attempt every runnable task, in registration order, and SHALL arrive at exactly one outcome per attempted task: a task that succeeds is recorded as completed; a task that reports a skip is recorded as skipped; a task that fails has nothing recorded and therefore remains pending and can be run again later. A task that ends without reporting any of those three outcomes SHALL be treated as a failure and SHALL be reported with an error message describing what went wrong. Whatever outcome a task reaches, the tasks after it in the order SHALL still be attempted; no single task can cut the execution short. An execution that finds no runnable task SHALL nevertheless stamp `last_run` on a never-initialized workspace, so that running nothing leaves the workspace initialized rather than eligible to prompt again.

- **REQ-WORKSPACE-085** — The persisted initialization marker SHALL be written from exactly one place, so a task itself never records its own outcome. A task that ran successfully but whose marker write fails SHALL be downgraded to a retryable failure with error "{label} completed, but the workspace config could not be written: {exc}" and summary "{label} finished, but the result could not be saved. Retry initialization."

- **REQ-WORKSPACE-086** — Skipping SHALL record every given pending task id as skipped; even when the id list is empty the marker is stamped, so after any skip the workspace has left the never-initialized state and the prompt cannot return on the next open.

- **REQ-WORKSPACE-087** — A task result SHALL carry: a status from the closed set success | skipped | failure; an ordered list of step results (name, status, detail) where step status is an open vocabulary (generic success/skipped/failure plus task-specific values such as `skipped-no-code`); a classification to forward into recorded state; an error message (shown next to the retry action); a retryable flag; and a one-to-two-sentence summary. The UI SHALL render each step's detail text, not its status token.

### Registered Setup Task: Code-Intelligence Indexing

- **REQ-WORKSPACE-088** — The single task registered by default SHALL have id `code-intelligence-setup`, label "Code intelligence project setup", description "Index this project's symbols so coding personas can search symbols and references without re-reading the tree.", and SHALL NOT require consent: its outcome depends only on the workspace contents — it consults no model, needs no authenticated provider, and holds no agent conversation — so it starts by itself when the workspace opens, raising no dialog and gating no run.

- **REQ-WORKSPACE-089** — `code-intelligence-setup` SHALL be the whole of that task's identity: no other id SHALL resolve it. In particular the server name `code_intelligence` SHALL NOT identify any registered task, so a workspace whose persisted state records `completed: [code_intelligence]` still owes `code-intelligence-setup` and the indexing runs for it. There is no earlier id to honour either, the product having no earlier release (REQ-WORKSPACE-035); an id read back from persisted state that matches no registered task simply resolves nothing.

- **REQ-WORKSPACE-090** — The task SHALL be applicable exactly when the resolved configuration holds an MCP server named `code_intelligence` (REQ-MCP-010, REQ-CONFIG-181) and that server is launchable on this machine, judged by the one availability rule REQ-MCP-037 fixes for every surface. This domain SHALL NOT declare a second rule, and the consequences it depends on are these. A server of type `http` or `sse` SHALL count as launchable on the strength of its configuration alone. A `stdio` server whose command is the reserved bundled-runtime token `builtin:code-intelligence` SHALL count as launchable unconditionally and SHALL never be looked up on PATH, that token resolving to a runtime the application itself ships (REQ-MCP-033); its applicability therefore does not wait on machine setup. Any other `stdio` server SHALL count as launchable exactly when the executable named by the first token of its expanded command is found on the PATH in force for the application — which, on a bundled build, includes the managed tool directories that REQ-WORKSPACE-138 prepends. The PATH check SHALL be made **after** shorthand expansion, not before: `uvx:pkg` expands to `uvx pkg`, and a command beginning `npm:` or naming an `@scope`-prefixed package expands to `npx -y <pkg>`. An entry written in shorthand SHALL therefore count as launchable whenever the command it expands to is present. A command token that contains a path separator SHALL NOT be looked up on PATH at all: it SHALL be resolved against the entry's `cwd` when it is relative and taken as written when it is absolute, and SHALL count as launchable exactly when the resolved path names an existing regular file that the account running the application may execute. On a platform where executability is not a file attribute, the existence of a regular file at that resolved path is the whole test. A token that cannot be resolved, or that names a directory, SHALL count as not launchable, and the task SHALL simply be inapplicable rather than failing.

- **REQ-WORKSPACE-091** — Setup SHALL consist of exactly three stages, executed in this order, each bounded by its own wall-clock budget: project configuration, 300 s; symbol indexing, 1800 s; memory-layout seeding, 120 s. A stage that exceeds its budget SHALL count as a failed stage, with its processes ended as REQ-WORKSPACE-092 requires and its failure reported as REQ-WORKSPACE-093 requires. No verification stage SHALL run after indexing: a stage that runs to completion and returns a zero exit code is the only signal that it succeeded.
  - Project configuration invokes the tool's own command line to create the project entry. The language selections SHALL be passed on that command line, so the stage completes without ever waiting on an interactive prompt. The languages passed SHALL be derived from the source-file extensions actually present beneath the workspace root, taken from the same configured source-extension set that classification uses (REQ-WORKSPACE-099), and the identifiers passed SHALL be drawn only from those the configured code-intelligence tool reports it accepts: an extension the tool has no identifier for SHALL contribute no language rather than being passed through and failing the stage, and the product SHALL NOT invent an identifier the tool does not declare. Where the derivation yields no language at all, the stage SHALL create the project entry with no language selection rather than refusing to run. The stage SHALL be idempotent: when the runtime's own per-project marker file is already present beneath the workspace root it SHALL report success with the output "project file already exists; left as is", SHALL NOT run creation again, and SHALL leave whatever language selections are recorded in that file untouched. The marker file's name SHALL be read from the code-intelligence binding manifest (REQ-MCP-116) and SHALL NOT be written out in this domain.
  - Symbol indexing builds the symbol cache. For a workspace classified `non-code` (REQ-WORKSPACE-098) it SHALL be skipped, recording step status `skipped-no-code` and detail "No source files found, so there are no symbols to index."
  - Memory-layout seeding initializes the memory layout. For a workspace classified `non-code` it SHALL be skipped, recording step status `skipped-no-code` — the same token indexing records, since it is the same reason — and detail "No source files found, so no memory layout was seeded."

  A stage that fails SHALL end the run: the stages after it SHALL NOT start, nothing SHALL be recorded in persisted state, and the result SHALL be retryable.

  What each stage appends after the prefix derived in REQ-WORKSPACE-096 SHALL be that stage's own subcommand as the configured code-intelligence tool documents it, together with the resolved workspace root passed explicitly, so that no stage depends on the working directory the process happens to have. The product SHALL NOT synthesize a substitute for a subcommand the configured installation does not offer: where a stage's subcommand is unavailable, that stage SHALL fail and be reported under REQ-WORKSPACE-093 as any other stage failure is, retryable, with the stages after it not started — never guessed at. The exact argument vector each stage ran, its return code, and its output SHALL be recorded in the audit trail of REQ-WORKSPACE-095, which is the observable contract for what was invoked.

- **REQ-WORKSPACE-092** — A setup step's captured output SHALL be interpreted as UTF-8, and non-ASCII characters in it SHALL survive into that step's reported detail instead of causing the step to fail. When a step exhausts its time budget, when setup is cancelled, or when the application is closed while setup is running, nothing the step launched SHALL still be running 5 s later — neither the command the step itself started nor anything descended from it. A step that was stopped before finishing SHALL be reported distinguishably from one that ran to completion and returned a non-zero exit code: the detail for an exhausted budget SHALL read "This step did not finish within its time budget."; the detail for a cancelled step SHALL read "Setup was stopped before this step finished."; every other step's detail SHALL be the last 400 bytes of its combined standard output and standard error.

- **REQ-WORKSPACE-093** — Failure reporting SHALL be "{reason}: {detail}" with per-stage reasons "Code intelligence could not create this project's configuration" / "Code intelligence could not index this project's symbols" / "Code intelligence could not seed this project's memory layout"; the result is retryable, and cancelling leaves the task in exactly the same retryable condition a failure would, with summary "Code intelligence setup did not complete for this project. It runs again the next time this workspace is opened."

- **REQ-WORKSPACE-094** — Given the configured `code_intelligence` entry does not start the runtime locally — its type is something other than `stdio`, or its resolved arguments carry no server-launch subcommand — the task SHALL fail non-retryably with error "This workspace's `code_intelligence` entry is not a local launch, so its setup commands cannot be derived from it." and summary "Code intelligence project setup was skipped: the configured `code_intelligence` server is not one Rotaris can run setup commands against." — no substitute invocation SHALL be attempted, which is the outcome REQ-MCP-036 and REQ-MCP-099 already require of a derivation that cannot be made.

- **REQ-WORKSPACE-095** — Success summaries SHALL be, for a code workspace, "Code intelligence is set up for this project and its symbols are indexed.", and for a non-code workspace, "Code intelligence is set up for this project. - **REQ-WORKSPACE-096** — Every setup command SHALL be built from the same configured `code_intelligence` entry that the application uses to launch the MCP server, through the derivation REQ-MCP-036 fixes and no other. This domain relies on that derivation for three things and restates none of them: that the entry's command is resolved through the shorthand and reserved-token rules before anything is cut; that the cut is made at the first occurrence of the runtime's server-launch subcommand, whose literal spelling is read from the binding manifest of REQ-MCP-116 and is written out nowhere in this domain; and that the subcommand and everything after it — the transport, mode and project-selection arguments, which concern the server session only — appear in no setup command. Because the cut point is found by the subcommand rather than by the server name or the executable path, an entry naming a different install location or a different version is still honored and the setup commands run against the same installation the server runs from. What each stage appends after that prefix is stated in REQ-WORKSPACE-091.

- **REQ-WORKSPACE-097** — This domain relies on the code-intelligence server coming up already pinned to the workspace of the run that started it, so that the server is bound to that one project and never offers agents any project-switching capability; the appending rule and the literal spellings of the project-selection options belong to REQ-MCP-034 and REQ-MCP-116 and SHALL NOT be restated here. ### Workspace Classification (code vs non-code)

- **REQ-WORKSPACE-098** — A workspace SHALL classify as `code` when at least one file anywhere beneath the workspace root carries an extension from the configured source-extension set, and as `non-code` in every other case — a verdict that covers empty trees, a workspace directory that does not exist, and documentation-only trees alike. The walk SHALL descend into every subdirectory except `.git/`, and SHALL disregard any path the workspace-root `.gitignore` matches (REQ-WORKSPACE-100). Extension matching SHALL ignore letter case: a candidate's suffix is lower-cased before it is compared against the already-lower-cased set of REQ-WORKSPACE-099, so a file named `Main.PY` classifies its workspace as `code`. The walk SHALL NOT follow symbolic links to directories: such a link SHALL be skipped without descending into it and without contributing a verdict, so no arrangement of links can make the walk loop or fail to terminate, and files belonging to an unrelated tree can never decide this workspace's classification.

- **REQ-WORKSPACE-099** — The default source-extension set SHALL be exactly these 23 entries: `.py .js .ts .jsx .tsx .rs .go .java .c .cpp .h .hpp .rb .php .swift .kt .scala .cs .fs .ex .exs .r .jl`, and the same set SHALL apply everywhere classification is decided. It SHALL be overridable per workspace via `project_init.source_extensions` in `.rotaris/agents.yaml`, with entries normalized (lower-cased, a leading dot added, blanks dropped).

- **REQ-WORKSPACE-100** — Only the `.gitignore` at the workspace root SHALL be consulted; an ignore file in any subdirectory SHALL have no effect on classification. Its patterns SHALL be interpreted with gitignore-style wildcard matching, and a directory pattern SHALL match a candidate path whether or not that path carries a trailing slash. An ignore file that is missing, empty, or unreadable — or an inability to perform the matching at all — SHALL leave classification treating nothing as ignored, and SHALL NOT make classification fail. The full gitignore pattern grammar SHALL be honored, negation patterns (`!`) and `**` path patterns included, with the last pattern matching a path deciding it, so that classification agrees with what the repository itself treats as ignored; a subset that recognized only simple wildcards would classify a workspace as `code` on the strength of files the repository has said are not part of it.

- **REQ-WORKSPACE-101** — The verdict SHALL be recorded in the persisted initialization state, and the Settings Project area SHALL explain outcomes with "No code memories were created — this workspace is a documentation-only project." or "Code memories were created from this workspace's sources."

(1) The Settings Models category (`models`, REQ-CONFIG-269) SHALL offer an action that starts the flow with the catalog step showing, and, per already-configured provider, an action that starts it in re-authenticate mode for that provider — beginning at the authentication step for it, and replacing that provider's stored credential on success while leaving every other provider's snapshot entry untouched. (2) The refusals of REQ-WORKSPACE-137 SHALL carry an action leading to that same Settings surface. (3) On a first launch at which no authenticated provider exists, the window SHALL publish a persistent INFO notice, once the window is interactive and never as a dialog opened unbidden, conveying that no model provider is authenticated yet and that runs cannot start until one is, and carrying an action that starts the flow. That notice SHALL NOT gate any view, SHALL NOT block navigation, and SHALL be dismissible; the only run-time consequence of having no provider is the refusal REQ-WORKSPACE-137 already states. Where a provider's authentication step hands off to an external browser, the interface SHALL say so before the hand-off and SHALL remain usable while it is outstanding.

- **REQ-WORKSPACE-137** — Desktop equivalents: submitting a prompt with no model configured SHALL yield "No model configured" / "Choose a model in Settings before starting a run." with an "Open Settings" action; with providers configured but none connected, "Provider authentication required" / "Authenticate at least one configured provider before starting a run." Provider health and authentication management live in Settings.

### Bundled-Build Machine Setup

- **REQ-WORKSPACE-138** — On bundled builds, machine setup SHALL run when no setup state record exists, the tool-manifest fingerprint changed, or a prior outcome was neither complete nor accepted-degraded; a manually requested run always proceeds. Setup state persists at `<per-user-data-dir>/setup/state.json` (atomic JSON); managed tools install under `<per-user-data-dir>/tools/…`; a lock file (considered stale after 900 s) prevents concurrent runs, a second attempt reporting the outcome "already-running". Activating the managed environment SHALL prepend verified managed tool directories to PATH and pin the package-tool caches (e.g. the `UV_CACHE_DIR` and `npm_config_cache` environment variables) to application-owned cache directories.

- **REQ-WORKSPACE-139** — The machine-setup dialog SHALL be modal, 760×560, titled "Preparing Rotaris" (or "Repair machine tools" for manual runs), explaining "Rotaris is checking Git, Node, ripgrep, and the package caches used by MCP servers." It SHALL stream per-step progress (`▶` running, `✓ … (Xs)` done with duration, `Failed — …`), show a counter `{done}/{total} — {pct}%`, and offer Show/Hide details, Cancel ("Cancelling after the current step…"; then "Setup paused. Completed steps are saved."), Retry, "Continue without tool" (recording an accepted degradation, described as "Open Rotaris with a warning for capabilities that still need this tool"), and Resume/Open. Outcomes: complete | degraded | cancelled | already-running.

- **REQ-WORKSPACE-140** — After the machine-setup modal closes, the machine-setup settings display SHALL refresh and the git refresh SHALL start; then first-launch workspace onboarding continues if it is still owed.

### Cross-Cutting Invariants

- **REQ-WORKSPACE-141** — Desktop workspace-open ordering SHALL be: window constructed → typeable-command catalogue built (and rebuilt on library/settings changes) → window shown → (bundled first run only: machine-setup modal) → git refresh without blocking the interface → update check → cloud-credit polling → once the window is interactive: initialization resolution and hook-review notice → (first launch only, after the shared deferred first-paint delay of REQ-SHELL-011) project chooser.

- **REQ-WORKSPACE-142** — Consent boundary: the only thing in this domain that gates agent execution is an unanswered consent-requiring initialization prompt, and even that gates only the composer. Background setup, git absence, and refused hooks SHALL never block runs.

- **REQ-WORKSPACE-143** — Trust boundary: nothing authored by the repository (workspace-declared hooks) executes without an explicit stored verdict covering the exact reviewed content; every ambiguous state fails closed; refusals are durable decisions; user-authored global and default hooks are never subject to review and survive a refused workspace override.

- **REQ-WORKSPACE-144** — Recording boundary: the persisted initialization marker has exactly one writer; failures record nothing; skips record everything; every recorded outcome stamps the last-run timestamp; the prompt decision is per-task, never per-workspace.

- **REQ-WORKSPACE-145** — Injection separation: the workspace context block, the portable-skill catalog, force-loaded skill bodies, and persona memory are distinct, ordered context units; skill bodies enter model context only by agent retrieval, explicit user command, or the explicit "always" load policy.

- **REQ-WORKSPACE-146** — Determinism: skill discovery order and catalog rendering are deterministic (sorted); the merged workspace context is byte-deterministic for a given filesystem state; hook digests are canonical-JSON SHA-256 and therefore reproducible.

- **REQ-WORKSPACE-147** — Atomic persistence: every at-rest write in this domain — the workspace and global `agents.yaml`, `hook-trust.json`, machine-setup state, and the minimal bootstrap file — SHALL land via an atomic replace-style write, so that a crash partway through writing cannot leave a truncated file behind.

- **REQ-WORKSPACE-153** — Visual appearance: every surface this domain describes SHALL take its colours, spacing, and type from the active theme, and no requirement in this domain fixes a colour value, a font, or a spacing figure. The numbers this domain does state are normative and are not theme tokens: the 1.0 s and 15 s and 10.0 s git timings, the 5 s process-teardown bound and the 5000 ms application-close bound, the 300 s / 1800 s / 120 s stage budgets, the 200 ms context-merge budget, the 100 ms refresh budget, the 900 s lock staleness, and the byte limits of REQ-WORKSPACE-044. Two figures are deliberately not among them, each being stated once elsewhere and only cited here: the status-bar elision thresholds, stated by REQ-SHELL-047 and cited by REQ-WORKSPACE-021; and the deferred first-paint delay, stated by REQ-SHELL-011 and cited by REQ-WORKSPACE-008 and REQ-WORKSPACE-011. Three obligations bind every surface here whatever the theme: no state SHALL be conveyed by colour alone (REQ-SHELL-149); animation SHALL be suppressed under reduced motion (REQ-SHELL-135); and every control this domain adds SHALL be reachable and fully labelled at the minimum window size (REQ-SHELL-022).

## Data & Formats

All formats below are externally observable: they are files a user (or test) can read and write, payloads delivered to agents, or persisted OS-level settings.

### Persisted application settings

- `workspace/lastOpened` — a key of the per-user preference store whose registry REQ-SHELL-006 closes; this appendix holds no copy of the store's shape or of the key's default, and contributes only when this domain writes it: on explicit open and on a successful switch, read at startup, and not cleaned up when stale.

### Workspace state directory `<workspace>/.rotaris/`

- `agents.yaml` — workspace-scope configuration. Known behavioral sections: `default_persona`, model slots, `inject_agents_md` (bool, default true), `skills:` (`enabled`, `overrides`, `invocation_overrides` keyed by normalized skill name), `project_init.source_extensions`, `hooks:` (whose section and entry schema are REQ-HOOKS-007 and REQ-HOOKS-008), and:

  ```yaml
  initialization:
    completed: [code-intelligence-setup]
    skipped: []
    last_run: "2026-08-29T12:00:00+00:00"   # ISO-8601 UTC
    classification: code                     # code | non-code | null
  ```

  Unknown top-level keys survive every save round-trip. There is no legacy state directory to adopt (REQ-WORKSPACE-035).
- `models.yml` — per-scope model definitions (also read in the global scope directory).
- `hook-trust.json` — the hook trust decision file, whose path, keys and serialization are fixed by REQ-HOOKS-096 and whose reading is fixed by REQ-HOOKS-094; this appendix holds no copy of them and contributes only that the file lives in this directory.

### Hook digest payload

Not a format this domain defines. The canonical document the digest is taken over, the fields it carries, the resolved-value rule, and what does and does not change the digest are REQ-HOOKS-091's, which this domain cites (REQ-WORKSPACE-117) and does not restate.

### Merged workspace context (AGENTS.md)

```
<!-- source: C:\path\to\workspace\AGENTS.md -->
{file content, possibly truncated at a line boundary}
```

Blocks separated by one blank line; total ≤ 131,072 bytes; per file ≤ 32,768 bytes (UTF-8 byte counts); deterministic.

### SKILL.md

YAML frontmatter delimited by `---` lines; required `name`, `description`; canonical trigger `trigger: {type: keyword, keywords: [..]}` (legacy `type:`/`triggers:` aliases normalized); optional `user-invocable: false` and `disable-model-invocation: true`; unknown fields preserved. Directory layouts searched: `<dir>/.agents/skills/<name>/SKILL.md`, `<dir>/.opencode/skills/<name>/SKILL.md` per project directory up to the repository root; user-scope roots `~/.agents/skills`, `~/.config/opencode/skills`, `~/.openhands/skills/installed`, `/etc/codex/skills`; disable manifest `~/.openhands/skills/.installed.json` (three accepted shapes, see REQ-WORKSPACE-052).

### Model-facing skill catalog block

Opening statement conveying the three facts of REQ-WORKSPACE-061, followed by one line per skill:

```
- {name}: {description} (SKILL.md: {absolute path})
```

Lines ordered by normalized name. A force-loaded body block carries the activation statement described in REQ-WORKSPACE-062, followed by the skill body with its frontmatter stripped.

### Skill listing and force-loaded body

There is no text-mode listing format and no steering-payload format. The discovered catalog is read in the Settings Skills tab (REQ-WORKSPACE-067), whose columns are Skill, Source, Path, Trigger, Load, Description; a skill loaded by hand for the session (REQ-WORKSPACE-151) carries the scope label `manual`. Invoking a skill's slash command force-loads its body for the session (REQ-WORKSPACE-073), and a force-loaded body reaches the model in the block shape of REQ-WORKSPACE-062 — an activation statement naming the skill, followed by the skill body with its frontmatter stripped — not in a listing format of its own.

### `.mcp.json`

Not a format this domain defines. The locations, the accepted shape and keys, and the parsing rules are REQ-MCP-017 and the requirements it names; this domain contributes only the workspace root the project-level file is located against and the layer discovery occupies in configuration assembly (REQ-WORKSPACE-037, REQ-WORKSPACE-036).

### Code-intelligence artifacts

- The code-intelligence runtime's per-project marker file beneath the workspace root — presence marks the project-configuration stage as already done (idempotence marker, REQ-WORKSPACE-091). Its name is read from the binding manifest (REQ-MCP-116) and is not written out here.
- Default MCP server entry: name `code_intelligence`, `stdio`, reserved command token `builtin:code-intelligence` (REQ-MCP-033), with its arguments, its pinned version and its per-run project binding fixed by REQ-MCP-010, REQ-MCP-011, REQ-MCP-034 and REQ-CONFIG-181. Exactly one such entry ships (REQ-WORKSPACE-097).

### Machine setup state

The per-user data directory named below is the one REQ-STARTUP-145 fixes, which is where that requirement settles which per-user location is meant on a platform offering more than one; this appendix holds no copy of that property and states none of its own. The layout itself is REQ-STARTUP-070's.

- `<per-user-data-dir>/setup/state.json` — atomic JSON outcome record (`complete` | `degraded` | `cancelled` | `already-running`, plus manifest fingerprint).
- `<per-user-data-dir>/tools/…` — managed tool installs; `setup.lock` stale after 900 s.

### Minimal bootstrap `agents.yaml`

Hand-authored content: the three-fact comment header of REQ-WORKSPACE-038, `default_persona: orchestrator`, and the twelve explicitly-null model-slot and thinking keys of REQ-CONFIG-025; mode 0o644; atomic write.

### Provider snapshot

`project_settings.yaml` in the per-user configuration directory — the fourth configuration layer of REQ-WORKSPACE-036. Its document shape, atomic write, file mode, and merge into the effective configuration belong to the model-providers specification (REQ-PROVIDER-084, REQ-PROVIDER-085, REQ-PROVIDER-091) and are not restated here.
