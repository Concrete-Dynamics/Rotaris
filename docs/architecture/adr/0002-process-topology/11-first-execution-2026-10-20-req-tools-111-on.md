# ADR-0002 — Process topology — First execution — 2026-10-20, REQ-TOOLS-111 on Windows (consequence 5)

Part 11 of 11 of [ADR-0002](../0002-process-topology.md), which indexes every part.

## First execution — 2026-10-20, REQ-TOOLS-111 on Windows (consequence 5)

The Windows ARM64 session's C1 (Windows 11 ARM64 (build 26200.9457), Node 24.18.0 arm64, Electron 44.1.1 arm64, dev tree, pwsh 7.6.6, at `0fde55f2`). A scratch driver (never committed) launched the built app on a scripted workspace (every slot `scripted`, `permission_mode: autonomous`, `allow_unsandboxed_autonomous: true`, code intelligence disabled, `delegation_strategy: single`) with `ROTARIS_SCRIPT=terminal:bg,wait:600000`, the background command a PowerShell loop appending `Get-Date -Format o` to `beat.txt` every second; the chain read from `Win32_Process` was main → the run host (its pid from main's `run host hello`) → `pwsh.exe` → its `conhost.exe`.

**(A) the run host alone killed** (`taskkill /F /PID`, no `/T`): met. The shell kept writing for about 4 s (last beat 4.1 s after the kill) and was gone 5 s after it; main logged `run host exited (1)` and `CHILD PROCESS GONE` 4.9 s after the kill, so the shell ended as the run host actually ended. **(B) an orderly `driver.quit()`**: met; the last beat came 0.9 s before the run host's `exited (0)` and nothing was running 5 s after the exit. **(C) main killed** (`taskkill /F /PID`, no `/T`): met; the beats stopped within about 1 s and the run host and the shell were gone 5 s later. No survivor in any path. The mechanism is not the product's: no Job Object exists in this codebase, and the observations fit the job with kill-on-close in which libuv places every child it spawns without `detached` on Windows (public libuv behaviour, not read from a job handle here: `IsProcessInJob` reads true for main, the run host and the shell, and for the session's own node too, which runs inside the host application's job, so the probe cannot tell whose job it is). Not measured: the `ping -n 600` variant (the scratch driver's redirect never wrote, a driver fault), A2's relaunch reading, and a hook's descendants, which the same job would reach at the run host's end (REQ-HOOKS-033, OQ-9).

Consequence 5's "Without the Job Object `REQ-TOOLS-111` is unmet on Windows" is falsified as a prediction and kept as written: with no Job Object of the product's, the background command did not outlive a run-host kill, an orderly quit or a killed main. What makes it so is a dependency's default, which nothing here pins.
